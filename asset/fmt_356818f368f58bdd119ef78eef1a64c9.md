`#endif` // 结束 `#ifndef BAR_H`

## 17.3 static extern

这并不是规范的一部分，但在 C 世界中是 99.999% 常见的。

你可以将 C 文件编译为一种称为对象文件（object files）的中间表示。这些是尚未放入可执行文件的编译机器码。

Windows 中的对象文件具有 `.OBJ` 扩展名；在 Unix 类系统中，它们是 `.o`。

在 `gcc` 中，我们可以使用 `-c`（仅编译！）标志位来构建如下内容：

```bash
gcc -c foo.c      # 生成 foo.o
gcc -c bar.c      # 生成 bar.o
```

然后我们可以将它们链接成一个单一的可执行文件：

```bash
gcc -o foo foo.o bar.o
```

漂亮了，我们从两个对象文件生成了一个可执行文件 `foo`。

但你可能想，何必费此？我们不能直接：

```bash
gcc -o foo foo.c bar.c
```

并一石子二鸟吗？

对于小型程序，这没问题。我经常这样做。

但对于较大的程序，我们可以利用这样一个事实：从源码编译到对象文件相对慢，而链接一组对象文件相对快。

这在只重建比其输出文件新的源文件的工具中体现得尤为明显。

假设你有一千个 C 文件。你可以先编译所有对象文件（缓慢地），然后将所有对象文件合并成可执行文件（快速地）。

现在假设你修改了其中一个 C 源文件——魔法发生了：你只需要为该源文件重新构建那一个对象文件！然后重新构建可执行文件（快速）。所有其他 C 文件都不需要碰。

## 18.2 退出状态 Exit Status

你有没有注意到 `main()` 函数的签名返回类型是 `int`？这是怎么回事？这与一种所谓的“退出状态”有关，它是一个返回给启动它的程序的整数，用于告知程序运行情况如何。

现在，C 语言中有多种程序退出的方法：从 `main()` 返回，或者调用 `exit()` 的变体。

所有这些方法都接受一个 `int` 作为参数。

旁记：你是否注意到在我几乎所有的示例中，即使 `main()` 也应该返回一个 `int`，但我实际上并没有返回任何内容？在任何其他函数中这都是非法的，但 C 中有一个特殊情况：如果执行到 `main()` 的末尾而没有找到 `return`，它会自动返回 0。

但这意味着什么？我们还可以在那里放置什么数字？它们是如何使用的？

规范在这方面既清晰又模糊，这很常见。清晰是因为它列出了你可以做什么，但模糊之处在于它并没有特别限制你。

没有什么让它就此冲前进去搞清楚它

让我们先进入一下“盗梦空间”⁴：事实证明当你运行程序时，你是从另一个程序在运行它。

通常这个另一个程序是某种 shell⁵，它本身并不匹配什么，除了启动其他程序

- 1. shell 启动程序
- 2. shell 通常会进入睡眠状态（对于命令行 shell）
- 3. 你的程序运行
- 4. 你的程序终止
- 5. shell 唤醒并等待另一个命令

现在，在步骤 4 和 5 之间发生了一小段通信：该程序可以返回一个 shell 可以进行插值的状态值。通常，这个值用于指示你的程序的成功或失败，如果适用，还会指示什么类型的失败。

这个值就是我们一直从 `main()` 返回的值。它就是状态。

| 状态 | 描述 |
| --- | --- |
| `EXIT_SUCCESS` 或 0 | 程序成功退出。 |
| `EXIT_FAILURE` | 程序因错误退出。 |

让我们写一个从命令行读取两个数字并相乘程序。我们需要正好两个值。如果没有，我们将打印错误信息并以错误状态退出。

```c
#include <stdio.h>
#include <stdlib.h>
```

```c
int main(int argc, char **argv)
{
  if (argc != 3) {
    printf("usage: mult x y\n");
    return EXIT_FAILURE; // 告诉 shell 它没有成功
  }

  printf("%d\n", atoi(argv[1]) * atoi(argv[2]));

  return 0; // 等于 EXIT_SUCCESS，一切正常。
}
```

现在如果我们尝试运行它，在没有指定正确的命令行参数数量之前，我们会得到预期的效果：

```bash
$ ./mult x y
usage: mult x y

./mult 3 4 5
usage: mult x y
```

```bash
$ ./mult 3 4
12
```

但这并没有真正显示我们返回的退出状态，对吧？不过，我们可以让 shell 打印出来。假设你正在运行 Bash 或另一个 POSIX shell，你可以使用 `echo $?` 来查看。

让我们尝试：

```bash
$ ./mult x y
usage: mult x y
echo $?
1
```

```bash
$ ./mult 3 4 5
usage: mult x y
echo $?
1
```

```bash
$ ./mult 3 4
12
echo $?
0
```

很有意思！我们看到在我的系统中，`EXIT_FAILURE` 是 1。规范没有列出这一点，所以它可以是任何数字。但在你的系统上它也是 1。

### 18.2.1 其他退出状态值

状态 `$0` 绝对意味着成功，但所有其他整数，即使是负数呢？

在这里我们将进入 C 规范并进入 Unix 世界。通常情况下，虽然 `$0` 表示成功，但正非零数表示失败。Bash 虽说退出码应该在 0 到 255 之间，但有些状态码被预留了。

简而言之，如果你想在 Unix 环境中指示不同的错误状态，可以从 1 开始逐递增。

在 Linux 上，如果你尝试任何 0-255 范围内的代码，它将把代码与 `0xff` 进行位与运算，这实际上是将其限制在该范围内。

> *在 Windows 的 cmd.exe 中，输入 echo %errorlevel%。在 PowerShell 中，输入 $LastExitCode。*

# 第19 章 C 预处理器

在你的程序编译之前，它实际上会通过一个名为预处理的阶段。这几乎就像在 C 语言之上有一层先运行的语言。它输出 C 代码，然后对这些代码进行编译。

我们之前在 `#include` 中已经某种程度上见过这一点！这就是 C 预处理器！当它看到指令时，它会在该处包含命名的文件，就像你直接把它写在那里一样。然后编译器会构建整个程序。

但事实证明，它的功能远比包含文件强大得多。你可以定义会被替换的宏……甚至可以定义可以带参数的宏！

## 19.1 #include

让我们从已经见过很多次的内容开始。这当然是将其他源包含到你的源码中的方法。非常常用的头文件。

虽然规范允许 `#include` 有各种行为，但我们将采取一种更务实的方法，讨论它在我见过的每个系统上的工作方式。

我们可以将头文件分为两类：系统和本地。对于内置的内容，如 `stdio.h`、`stdlib.h`、`math.h` 等，你可以使用角括号包含：

```c
#include <stdio.h>
#include <stdlib.h>
```

这当然意味着必须有一种方法从当前目录包含本地文件。这种方法就是：使用双引号：

```c
#include "header.h"
```

或者你很有可能使用正斜杠包含相对目录文件文件如下：

```c
#include "mydir/header.h"
#include "../someheader.py"
```

不要在你的 `#include` 中使用反斜杠 `\` 作为路径分隔符！那是未定义行为！请仅使用正斜杠 `/`，即使在 Windows 上也是如此。

总结来说，系统包含使用角括号（`< >`），你的个人包含使用双引号（`"`）。

## 19.2 简单宏

宏是一个标识符，它在编译器看到它之前就会展开为另一段代码。把它想象成一个占位符——当预处理器看到这些标识符之一时，它将其替换为你定义的另一个值。

使用 `#define`（通常读作 "pound define"）来操作。这里有一个例子：

```c
#include <stdio.h>

#define HELLO "Hello, world"
#define PI 3.14159

int main(void)
{
    printf("%s, %f\n", HELLO, PI);
}
```

在第 3 行和第 4 行我们定义了宏。当它们在代码的其他地方（第 8 行）出现时，会被替换为定义的值。

从编译器的角度来看，这就像我们写的是这些：

```c
#include <stdio.h>

int main(void)
{
    printf("%s, %f\n", "Hello, world", 3.14159);
}
```

看到 `HELLO` 被替换为 `"Hello, world"`，`PI` 被替换为 `3.14159` 了吗？从编译器的角度来看，这些值就像直接出现在代码中一样。如果生成的 C 代码无效，编译器就会报错。
