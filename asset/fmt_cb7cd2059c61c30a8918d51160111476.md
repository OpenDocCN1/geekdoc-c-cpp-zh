## 重温：`setState()`

到目前为止，你一直在使用 `setState()` 来管理组件的内部状态。你可以向函数传递一个对象，并在其中部分更新内部状态。

代码沙练场

```javascript
this.setState({ foo: bar });
```

但 `setState()` 不仅仅接受一个对象。在它的第二个版本中，你可以传递一个函数来更新状态。

代码沙练场

```javascript
this.setState((prevState, props) => {
  ..
});
```

你为什么想要这样做呢？有一个关键情况，使用函数比使用对象更有意义。那就是当你根据之前的状态或 props 更新状态时。如果你不使用函数，内部状态管理可能会导致 bug。

但是，当更新依赖于之前的状态或 props 时，使用对象而不是函数会导致 bug 吗？React 的 `setState()` 方法是异步的。React 会批处理 `setState()` 调用并最终执行它们。可能会出现这种情况：在你赖的 `setState()` 调用中依赖的值之间，之前的状态或 props 发生了变化。

代码沙练场

```javascript
const { fooCount } = this.state;
const { barCount } = this.props;
this.setState({ count: fooCount + barCount });
```

想象一下在你调用 `setState()` 时，`fooCount` 和 `barCount`（状态或 props）在其他地方异步发生了变化。在一个不断增长的应用程序中，你的应用程序会有多个 `setState()` 调用。由于 `setState()` 是异步执行的，你可能会依赖于这个关于过时值的示例。

使用函数的方法，`setState()` 中的函数是一个回调，它在执行回调函数时对状态和 props 进行操作。即使 `setState()` 是异步的，但通过函数，它获取的是执行执行时的状态和 props。

## 代码沙练场

```javascript
this.setState((prevState, props) => {
  const { fooCount } = prevState;
  const { barCount } = props;
  return { count: fooCount + barCount };
});
```

现在，让我们回到你的代码来修复这种行为。我们将共同修复一个 `setState()` 使用并依赖状态或 props 的地方。之后，你也能修复其他地方。

`getSearchTopStories()` 方法依赖于之前的状态，因此它是在 `setState()` 中使用函数对象的完美示例。现在，它看起来像下面的代码段

`src/App.js`

```javascript
setSearchTopStories(result) {
  const { hits, page } = result;
  const { searchKey, results } = this.state;
  const oldHits = results && results[searchKey]
    ? results[searchKey].hits
    : [];
  const updatedHits = [
    ...oldHits,
    ...hits
  ];
  this.setState({
    results: {
      ...results,
      [searchKey]: { hits, page }
    },
    isLoading: false
  });
}
```

你从状态中提取值，因为更新依赖于之前的状态。使用函数方法可以防止过时状态的问题。

`src/App.js`

```javascript
setSearchTopStories(result) {
  const { hits, page } = result;
  this.setState(prevState => {
    ...
  }));
```

你可以将已经实现的块移动到函数中。你只需要操作 `prevState` 而不是 `this.state`。

`src/App.js`

```javascript
setSearchTopStories(result) {
  const { hits, page } = result;
  this.setState(prevState => {
    const { searchKey, results } = prevState;
    oldHits = results && results[searchKey]
      ? results[searchKey].hits
      : [];
    const updatedHits = [
      ...oldHits,
      ...hits
    ];
    return {
      results: {
        ...results,
        [searchKey]: { hits, page }
      },
      isLoading: false
    };
  });
}
```

这将修复过时状态的问题。还有一个改进。由于它是函数，你可以提取该函数以提高可读性。这是使用函数而不是对象的另一个优势。函数可以位于组件外部。但毕竟，你想根据从 API 获取的结果来更新状态。

```javascript
src/App.js
setSearchTopStories(result) {
  const { hits, page } = result;
  this.setState(updateSearchStoriesState(hits, page));
}
```

`updateSearchStories()` 函数必须返回一个函数。它是一个高阶函数。可以将此高阶函数定义在 App 组件之外。注意函数签名现在发生了细微变化。

```javascript
src/App.js
const updateSearchStoriesState = (hits, page) => (prevState) => {
  const { searchKey, results } = prevState;
  const oldHits = results && results[searchKey]
    ? results[searchKey].hits
    : [];
  const updatedHits = [
    ...oldHits,
    ...hits
  ];
  return {
    ...results,
    [searchKey]: { hits: updatedHits, page }
  },
    isLoading: false
  };
};

class App extends Component {
....
};
```

就是这样。`setState()` 中函数优对象的方法解决了潜在的 bug，同时增加了代码的可读性和可维护性。此外，你可以将其导出并作为练习编写测试。

## 驯服状态

之前的章节向你展示了，状态管理在大型应用中是一个至关重要的课题。通常情况下，不仅是 React，许多 SPA 框架都为此苦恼。近年来，应用程序变得越来越复杂。如今 Web 应用程序的一个大挑战就是驯服并控制状态。

与其他解决方案相比，React 已经迈出了巨大一步。单向数据流和用于管理状态的简单 API 是不可或缺的。这些概念让你更容易推导出你的状态以及状态的变化。它让你在组件层面、在某种程度上在应用层面，更容易进行推理。

在一个不断增长的应用程序中，推理状态的变化变得越来越困难。在 `setState()` 中使用对象而非函数来操作状态时可能会引入 Bug。你必须通过提升状态（lift state）来在组件之间共享或隐藏状态。可能会某个组件需要向上移动，因为它的兄弟组件依赖它。也许该组件在组件树中离得很远，你必须跨越整个组件树共享状态。总之，组件参与状态管理的程度越来越大。但根结底，组件的主要职责应该是表示 UI，不是吗？

正因为所有这些原因，存在独立的解决方案来处理状态管理。这些解决方案不仅用于 React。然而，这让 React 生态变成了一个强大的地方。你可以使用不同的解决方案来解决你的问题。为了解决状态管理扩展的问题，你可能听过库 `Redux`¹ 或 `MobX`²。你可以在 React 应用中使用这些解决方案之一。通过扩展 `react-redux`³ 和 `mobx-react`⁴，你可以将它们集成到 React 视图层中。

`Redux` 和 `MobX` 不在本书的范围内。当你读完这本书后，你将获得关于如何继续学习 React 及其生态系统的指导。一条学习路径可以是学习 React。在深入研究外部状态管理主题之前，我建议阅读这篇文章⁶。它旨在让你更好地理解如何学习外部状态管理。

## Eject (弹出)

下一步由你决定。尽管如此，create-react-app 带有一个功能，以保持其可扩展性并防止供应商锁定（vendor lock-in）。供应商锁定通常发生在你投入某项技术但未来没有逃生口时。幸运的是，在 create-react-app 中，你有这样一个名为 "eject" 的逃生口。

在你的 `package.json` 中，你会找到启动、测试和构建应用程序的脚本。最后一个脚本是 eject。你可以尝试它，但没有路可以回了。这是一个单向操作。一旦你执行了 eject，就无法回去了！如果你刚刚开始学习 React，离开 create-react-app 方便的环境是没有意义的。

如果你运行 `npm run eject`，该命令会将所有配置和依赖复制到你的 `package.json` 和一个新的 `config` 文件夹中。你会将整个项目转换为带有包含 Babel 和 Webpack 等工具链的自定义设置。毕竟，你将对所有这些工具拥有完全控制权。

官方文档说，create-react-app 适用于小型到中项目。你不应该觉得有义务使用 "eject" 命令。
