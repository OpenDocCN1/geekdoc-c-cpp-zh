
# Unit testing

Unit testing is an important piece of software development. There are many great resources on getting started with unit testing and test-driven development, including Kent Beck's classic tome, Test-Driven Development: By Example (Allison-Wels).

Each test should exercise a Unit of Code (in C#, this translates to a method), have a meaningful name that describes the test-scenario, and be composed of three parts:

- *Arrange: Sets up any objects or data required for the test
- *Act: Executes the Unit of Code
- *Assert: Validates the results

The popular convention for setting up projects is to create one for each Business project and name the projects <ProjectToTestName>Tests. The project in the sample code for test Chapter 4-Commands; therefore, the Test Project is named Chapter4CommandsTests.

The units in this chapter are by no means extensive, but they illustrate the capabilities gained by adhering to the principle of Separation of Concerns.

# First unit test

The first unit test verifies that the Text property of the command gets in the constructor. The complete unit test is shown in Listing 4-10. The Arrange, Act, and Assert comments are not usually included in the unit tests. They are included in Listing 4-10 to demonstrate the structure of a unit test.

To execute the, run Gallio Icarus - the GUI runner that ships with Gallio. Click Add Files, navigate to your compiled test project, and then click Start to run the tests.

# Listing 4-10: Unit Testing the Constructor Setting the Text Property

```sharp
[Test]
public void Should_Set_Text_Property_In_The_Constructor()
{
    //Arrange
    CustomSaveCommand command;
    //Act
    string expectedValue = "Save";
    command = new CustomSaveCommand(expectedValue);
    //Assert
    Assert.AreEqual(expectedValue, command.Text);
}
```

## Test positive and negative conditions

When writing unit tests, it's important to test success as well as failure conditions. For the CanExecute method of the custom Save command, that means tests cover when the parameter is null or in addition to having a string value. These tests are shown in Listing 4-11.

# Listing 4-11: Testing the CanExecute Event Handler

```sharp
public void Should_Not_Execute_If_Parameter_Is_Null()
{
    ICCommand command = new CustomSaveCommand("**");
    bool canExecute = command.CanExecute(null);
    Assert.IsFalse(canExecute);
}

public void Should_Not_Execute_If_Parameter_Is_Empty_String()
{
    ICCommand command = new CustomSaveCommand("**");
    bool canExecute = command.CanExecute(string.Empty);
    Assert.IsFalse(canExecute);
}

public void Should_Execute_If_Parameter_Is_Not_Empty_String()
{
    ICCommand command = new CustomSaveCommand("**");
    bool canExecute = command.CanExecute("*Test*");
    Assert.IsTrue(canExecute);
}
```

# Traditional!

To fully understand why the ViewModel pattern helps, you need to understand the stands of a "traditional" application architecture.

# Data Access Layer (DAL)

The DAL is the set of classes and methods that get the data out of the data store (such as SQL Server) and populate the Model (see next item). It is also responsible for persisting (saving) any changes to the data back to the data store.

# Model

The Model is the data that composes your application — not the data store itself (for example, the database), but the object graph (see WikiPedia, "object graph") that represents the data for your application. In a sales application, example objects could be classes like Customer, SalesRegion, and SalesPerson.

# Business Layer (BL)

The BL is the implementation of the business rules for the application. This layer ensures that the data in the Model adheres to the law of the land.

# View

The View represents the pieces of the application that interact with the data. For WPF, it is the collection of Windows that compose the application.

The biggest gap with displaying an object graph (Model) in a View is that applications seldom display only one of object at a time. If the Window allows for editing a customer, then it probably needs to display the sales regions, pages, and so forth.

Combining multiple objects into a data object clouds the Model, and placing all code into the view puts too much knowledge in the View - not to mention a total inability to unit test the code.

The command objects are another consideration. There isn't a tidy place in the traditional application layer to place the custom commands. The code contained in the commands is (typically) Business Logic, but the Window needs to bind to the commands and is therefore specific to the View.

# Introducing the ViewModel

The ViewModel fills that gap. It is designed to be a single class that pulls in all the necessary data points and commands into a one-stop shop for a particular view. Each view has its own ViewModel, but that is entirely dependent on your particular application.

As Chapter 3 discusses, WPF automatically monitors any class that implements INotifyPropertyChanged (for items bound to a property of a class) or INotifyCollectionChanged (for items bound to a collection of items). These interfaces should be implemented in one of two cases — the ViewModel or the Model.

Implementing those two interfaces in the ViewModel is more the academic, textbook implementation. This is because it separates user interface code from the Model. It also requires a lot of additional work, because it entails recoding all the properties and collections of your Model to include raising the proper events.
