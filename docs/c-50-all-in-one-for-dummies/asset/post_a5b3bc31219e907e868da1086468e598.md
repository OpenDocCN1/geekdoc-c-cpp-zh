
## 654 Questioning the Client

This gets into the same discussion that I cover several times throughout the book regarding the difference between the library and the language. ASP.NET is a library of tools, and that library is language independent. You orchestrate the functionality of the parts of the library using the language.

There are a few little caveats to web development, however. The client — doesn't care a whit that you are coding in C# — needs some care and feeding. There is no state in web applications, so you need to think a little differently. The client does a lot automatically for you in web development. The server has some security concerns.

Before I dig into the details of using C# with ASP.NET, I'd like to take a tour through the details of web development and point out things you need to keep in mind.

## Questioning the Client

When you're writing a Windows Form, WPF, or console application, your platform for the client is a Windows computer. When you're writing a web application, you have no idea what the platform for your client is. It could be a Mac, any one of 12 Windows operating systems, or Linux. It could be a phone, a tablet, or a notebook. It could be a television, a gaming device, or a refrigerator (really: see Figure 1-3).

The point is that you don't know what you're writing for, so you have a very different development experience for a web browser than you do for a Windows client. You don't know what size the screen is, you don't know what language the machine is set to, you don't know how fast the connection to the Internet is. You know nothing about your client.

You have to question the client. You can't assume much about the browser, so you have to make certain design decisions differently than you usually would.

You can depend on the browser to do some things for you that might be used to do for yourself. The programming details are explained in Chapter 4, but it is important to get a good overview view.

First, the client browser has a built-in scripting system called ECMAScript. Second, the browser can tell you some subset of details about itself, its host machine, and the user that is using it.

## Scripting the client

By now get the idea that communication with the browser occurs via the network, and that the client and browser are disconnected. Although is true, the client isn't completely out in the fog when it comes to interact with the user.

You can send a script along with your HTML document. This script references objects on the screen — just like your C# code — and things happen for the user.

Usually this script is in the JavaScript language. Why not C#? Well, C# isn't a scripting language. C# needs to be compiled, and JavaScript is not compiled. It sits there, in text, waiting for the browser to run it.

The fact that it is in text means you have to be careful not to secure information in a script. Right-click any page in your browser and click View Source to see that page's script code.

A lot of the script that your pages will be generated by ASP.NET. This book is about C#, not JavaScript, so I focus on the server features, not the client features. For now, you should just know that “things are happening” on the client side, however.

## Getting information back from the client

When a browser makes a request to a server, lot of useful information about the client gets along with the page name that is requested. You can reference this in the backward named ServerVariables collection.

This is about as good as learning about the client gets. These details will, hover, help you get the most out of your communication with the client. Here are some examples of the values available:

- AUTH_USER: The logged-in user.
- REMOTE_USER: The same as AUTH_USER.
- CONTENT_LENGTH: Size of the request. This is useful if a file is uploaded.
- HTTP_USER_AGENT: Which browser the client is using.
- REMOTE_ADDR: The IP number of the client computer.
- QUERY_STRING: All the stuff after the question mark in the request. Check out the Address bar of a browser in many web applications to say what I mean.
- ALL_HTTP: Every header variable (request details made available to the server) by the client.

In total, there are usually 63 variables in the header. The most commonly accessed of them are in the System.Web.HttpRequest class. You'll also find the collection of ServerVariables there. You can find out more getting to class in Chapter 4 of this minibook. Search MSDN on ServerVariables to get the complete list.

## Understanding the weaknesses of the browser

As you imagine, there are a few weaknesses to the browser-as-client model. At this point in the book, you should know that the more layers you stack on, the more problems you encounter. Here are a few of these:

- Changing sizes: When you're writing a WPF application in C#, the application will be running on Windows. You might not know which one, but you have a good idea.
- Sporadic implementations: When you're writing a Windows Form, WPF, or console application, your platform for the client is a Windows computer. When you're writing a web application, you have no idea what the platform for your client is.
- Security risk? You betcha. The server will be Internet Information Server 99.5 percent of the time. Other servers implement ASP.NET in one fashion or other, but almost never see them.
