# Asynchronous I/O: Is it worth waiting?

Normally, a program waits for a I/O request to complete before continuing. Call a `read()` method, and you generally don't get control back until the file data is safely in the boat. This is known as asynchronous I/O. Synchronous means "while you wait."

Using asynchronous I/O, you can start cutting up the onions while the hamburger patties are cooking. Once in a while, you peek over to see if the meat is done. When it is, you stop cooking, take the meat off, and slap it on the buns.

The `.IO` classes also support asynchronous I/O. Using asynchronous I/O, the `read()` returns immediately to allow the program to continue doing something else while the I/O request is completed in the background. The program can check a "done" flag at its to decide when the I/O has completed.

The stream concept is fundamental to C I/O. Think of a parade, where "streams" by you, the firsts, and then the floats, and a band by two, some horses, a troupe of Customer objects, a BankAccount, and so on. Viewing a file as a stream of bytes (or characters) is much like a parade. A "stream" is the data in and out of your program.

The .NET classes used in C# include an abstract Stream base class and several subclasses, for working with files on the disk, over a network, or already sitting as chunks of data in memory. Some stream specialize in encrypting and decrypting data, which are provided to help speed up I/O operations that might be slow when using one of the other streams, and you're free to extend Stream with your own subclass if you come up with a great idea for a new stream (although you learn that extending Stream classes in the later section "Exploring More Streams" with Lewis and Clark.).
