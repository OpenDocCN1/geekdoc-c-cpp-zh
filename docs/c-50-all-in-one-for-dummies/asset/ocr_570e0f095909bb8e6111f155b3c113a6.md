You have to question the client. You can't assume much about the browser, so you have to make certain design decisions differently than you usually would.

You can depend on the browser to do some things for you that might be used to do for yourself. The programming details are explained in Chapter 4, but it is important to get a good overview view.

First, the client browser has a built-in scripting system called ECMAScript. Second, the browser can tell you some subset of details about itself, its host machine, and the user that is using it.

# Scripting the client

By now get the idea that communication with the browser occurs via the network, and that the client and browser are disconnected. Although is true, the client isn't completely out in the fog when it comes to interact with the user.

You can send a script along with your HTML document. This script references objects on the screen — just like your C# code — and things happen for the user.

Usually this script is in the JavaScript language. Why not C#? Well, C# isn't a scripting language. C# needs to be compiled, and JavaScript is not compiled. It sits there, in text, waiting for the browser to run it.

The fact that it is in text means you have to be careful not to secure information in a script. Right-click any page in your browser and click View Source to see that page's script code.

A lot of the script that your pages will be generated by ASP.NET. This book is about C#, not JavaScript, so I focus on the server features, not the client features. For now, you should just know that “things are happening” on the client side, however.
