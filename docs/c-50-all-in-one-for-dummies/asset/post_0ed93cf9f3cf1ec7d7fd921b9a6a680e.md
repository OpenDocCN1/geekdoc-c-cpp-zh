
## Setting up a WCF Service to use REST

The template gives you a few important things.

- **Configuration**: The configuration of WCF is a bear (as you can see in Chapter 3) and making REST-capable even worse. The template takes care of the details for you.
- **File formats**: The files for REST aren't any different from WCF, but how you set them up is.
- **Project setup**: Visual Studio helps you set up the project well for a REST project.

One of the changes that the REST template does for you is the routing. Remember that REST is a URI-based format. The routing needs to be set up with the excellent WebServiceHostFactory to direct incoming requests to the appropriate code in the project. Another place where the configuration is tuned is in the config file. Remember that WCF is essentially IIS add-on. REST projects are extensions of ASP.NET MVC. The web.config is built for the project, and you can change it largely without. The routing module especially is important — it makes the code in the global.asax work:

```xml

  </modules>
```

## Setting up a WCF Service to Use REST

### Building a service

Making a service isn't much different from working in WCF: First you build an interface and a method. The contracts look just like what you would expect from Chapter 3 of this minbook. The methods interact with System.ServiceModel.Web and have a slightly different look.

Here's a simple datacontract that grabs the version of the service assembly:

```csharp
namespace Chapter4.REST.Interface
{
    [DataContract]
    public class ServiceVersion
    {
        [DataMember] public String Version;

        public static ServiceVersion Read()
        {
            var asm = Assembly.GetExecutingAssembly();
            var fvi = FileVersionInfo.GetFileInfo(asm.Location);
            var version = String.Format("{0}.{1}", fvi.ProductMajorPart, fvi.ProductMinorPart);
            return new ServiceVersion { Version = version };
        }
    }
}
```

Where interest is the methods. The straight class library of WCF gives away to the controller style classes in REST. Here is the method that interacts with the data contract.

```csharp
[Description("Read the version of this service.")]
[WebGet(Uri="/version", ResponseFormat = WebMessageFormat.Json)]
public ServiceVersion Read()
{
    return ServiceVersion.Read();
}
```

There are two bits above the method code: Description and WebGet. The Description property will change the built-in documentation that is autogenerated by IIS when a user hits the service page. WebGet is the implementation of all the routing that you saw in the global.asax and web.config file.

Now, all you have to do get the version is to go to http://myurl.com/version, and you get a JSON representation of the information returned from the data contract method. This is what makes REST restful and makes things a lot easier. And it's all for free from ASP.NET MVC.

## Handling errors

As you may imagine, errors in the REST space are a little different than what you might experience in SOAP. There are predefined ways to handle errors in REST, and they are the same as what you see on the web. It's the same deal, more or less.

That means you should return 404 (file not found) if you misspell the service, and 500 (internal server error) if a server error occurs. This isn't WCF programming at that; it's a brave new world.

Fortunately, System.ServiceModel.Web has a class called WebFaultException that will help with that. It will take an object and help it into a status code with little fuss. I recommend adding a method like this to your project:

```csharp
private WebFaultException<String> InternalError(Exception ex)
{
    var msg = ex.Message;
    if (ex.InnerException != null)
    {
        msg += " " + ex.InnerException.Message;
    }
    return new WebFaultException<String>(msg, HttpStatusCode.ServerError);
}
```

### Dealing with cache

One thing that you have to handle is the cache. MVC's speed is largely due to caching, which saves data in a buffer that might require other resource usage. Something that tells Context to ignore the cache will help. Here is a little method that I found useful for resetting cache settings for REST:

```csharp
private void SetNoCache()
{
    var cache = HttpContext.Current.Cache;
    cache.Expires(DateTime.Now.AddMinutes(-1));
    cache.SetCache(CachePolicy.NoCache);
    cache.Store();
}
```
