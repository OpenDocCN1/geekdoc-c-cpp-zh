## Encrypting information

Encryption is, at core, a sophisticated process. Five namespaces are devoted to different algorithms. Because encryption is so complex, I'll get into the details in this book.

Nonetheless, it is important that you understand one cryptographic element for a key element of security — encrypting files. When you work with a file in a Forms Application, you risk someone loading it up in a text editor and looking at it, unless you have encrypted the program.

The common encryption scheme Data Encryption Standard (DES) is implemented in .NET. It's not the strongest encryption in these days of 64-bit desktop machines, but it's strong enough to encrypt the data files for a Windows application. You can find the methods to encrypt for DES in the DESCryptoServiceProvider in the System.Security.Cryptography namespace.

## Building Secure Web Forms Applications

Web Forms applications are disconnected, loosely coupled programs that expose a server to potential attacks through the exposed ports used by the applications. By loosely coupled, I mean they have a transact-and-wait relationship with the server. The request is issued, and then the requester waits for the response.

Because of this coupling, building for security becomes more important than ever with a Web Forms application. A side effect is that your application can become less functional.

When building web-based applications, you spend less time worrying about authentication (especially if your application is made publicly available) and more time worrying about crackers. Because you're making a server — usually something you keep private — available to the public, your programs are subject to a whole new set of security rules.

The key to protecting a public server is honesty. You are here to be honest with yourself about the weaknesses of the system. Don't think "Well, a cracker could figure out the password by doing XYZ, but no one would ever do that." Trust me, someone will figure it out.

The two main types of attacks to be concerned about for a Web Forms application are Injection attacks and script exploits.

## SQL Injection attacks

A SQL Injection attack happens when a hacker enters a line of SQL code into an input field to query a database in a form on a Web page (such as the username and password text boxes in a login form). Malicious SQL code causes the database to act in an unexpected way or allow the hacker to gain access to, alter, or damage the database.

The best way to understand how a hacker uses a SQL Injection is to see an example. For instance, a web page accepts a Product ID from the user in a text box and returns product details based on the Product ID the user entered. The code on the server looks like this:

```cs
// GetProductID from user
string productId = TextBox1.Text;
// Get information from the database
string selectString = "SELECT * FROM Items WHERE ProductID = " + productId + "";
SqlCommand cmd = new SqlCommand(selectString, conn);
conn.Open();
SqlDataReader myReader = cmd.ExecuteReader();
//Process results
myReader.Close();
conn.Close();
```

Normally, a user enters the appropriate information into the text box. A cracker attempting a SQL Injection would enter the following string into TextBox1:

```text
FOOBAR';DELETE FROM Items;--
```

The SQL that would be run by your code would look like:

```sql
SELECT * FROM Items WHERE ProductID = 'FOOBAR';DELETE FROM Items;--
```

The SQL Server executes some code you didn't expect; in this case, the code deleted the items table.

## Script exploits

A script exploit is a security flaw that takes advantage of the JavaScript engine in the user's web browser. Script exploits take advantage of one of the most common features of public Forms applications — enabling interaction among users. For instance, a Web Forms application may enable a user to post a comment that others of the site can view, or it may allow a user to fill out an online profile.

If a malicious user were to put some script code in his profile or comment, hacker could take over the browser of the next user who comes to the site. Several outcomes are possible, and none of them are good.

For instance, the cookies collection is available to JavaScript when a user comes to your site. A malicious user would put some script code in his profile that copy the cookies for your site to a remote server. This could give the malicious user access to the current user's session because the session identifier is stored as a cookie. The malicious user would then be able to spoof the current user's identity.

Fortunately, ASP.NET prevents users from typing most script code into a form field and posting it to the server. Try it with a basic Web Forms project by following these steps (you see the error shown in Figure 1-3):
