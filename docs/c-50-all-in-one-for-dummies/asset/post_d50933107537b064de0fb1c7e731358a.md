
# Commanding Attention

## Listing 4-3: Creating a CustomRoutedUICommand

```csharp
public static RoutedUICommand SaveCommand = new RoutedUICommand("Save", typeof(UIElement));
```

The first parameter in the constructor populates the Text property, the second parameter is the name used in serialization of the command (I usually append Command to the text from the first parameter), and the last parameter is the UIElement (In this example, the code states any UIElement can be the parent). There is a fourth parameter in Constructor (not shown here) that is a list of InputGestures.

CustomRoutedUICommands are usually created as static variables so there is only one instance (and makes binding simpler). It's still in the code-behind file, so you do not yet have Separation of Concerns, but you're getting there!

## Command bindings

Unlike built-in commands (which are part of the framework and automatically wired into the CommandManager and the binding system), custom commands are not. You need to make three changes in the XAML to support custom commands:

- Add the namespace for the command to the namespace declaration.
- Change the command assignment to a binding expression.
- Add the command to the bindings collection of the container.

As I explain, you can add custom namespace declarations to the Window to allow XAML access to custom classes and namespaces. The namespace for the custom command (which is the same namespace as the code-behind if the command is a static variable) needs to be added to the Window tag. Listing 4-4 shows an example namespace declaration. The bolded text is what has changed from the default namespace declarations that are in the standard WPF Window.

## Listing 4-4: Updated XAML for CustomRoutedUICommand

```xml
<Window Class="Chapter4.Commands.CommandBindingSample" xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation" xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml" xmlns:Commands="clr-namespace:Chapter4.Commands" Title="Command Binding" Height="122" Width="261">
```

After the namespace is brought into the Window, the command must be inserted into the Window.CommandBindings collection. You need to set three main properties, shown in Listing 4-5:

- Command: The binding to the command object
- CanExecute: Event handler for testing execution status
- Executed: Event handler for the execution of the command

With built-in commands, a simple string assigned to the UIElement. With custom commands, you have to use a binding expression (as discussed in Chapter 3). The format for a static command is

```xaml
{x:Static NamespaceReference:Class.CommandVariableName}
```

The NamespaceReference is the name assigned to the Window tag. Interestingly, the CanExecute and Executed properties are set to the methods — no funky binding required!

## Listing 4-5: Window CommandBindings XAML

```xml
<Window.CommandBindings>
    <CommandBinding Command="{x:Static:CommandBindingSample.SaveCommand}"
                    CanExecute="Save,SaveExecute"
                    Executed="Save,Executed"/>
</Window.CommandBindings>
```

The Command property of the CommandBinding and UIElements use the same bindings expression as shown in Listing 4-6. When a UIElement has a command bound to it, the framework looks for the first match in the CommandBindings section upon the element tree. When one is located, the UIElement uses the assigned event handlers CanExecute and Execute.

## Listing 4-6: Command Assignment to MenuItem and Button

```xml
<MenuItem Command="{x:Static Commands:CommandBindingSample.SaveCommand}"/>
<Button Command="{x:Static Commands:CommandBindingSample.SaveCommand}"
        Content="{Binding Source={RelativeSource Mode=Self}, Path=Command.Text}"/>
```

The CanExecute event handler for a RoutedUICommand uses the CanExecuteRoutedEventArgs object instead of returning True or False.

Setting e.CanExecute to True (can run) or False (cannot run) will enable or disable the command (and any associated UIElements).

If the command is enabled, the Executed event gets executed when the UIElement triggers the command (for example, when a button is clicked).

## Command parameters

The CanExecuteRoutedArgs and ExecutedRoutedArgs contain a property that provides a mechanism for passing objects from the Window into the CanExecute and Executed handlers. In the example 4-5, the text of the TextBox is passed as the parameter. The CanExecute property of the CanExecuteRoutedArgs in the CanExecute event handler is set to False if the string is null, and the Executed event handler displays it back to the user in a message box. Okay, not a realistic example, but it's a demo!

# Practical WPF: Custom commands with ICommand

RoutedCommands solve the problem of getting from the display mechanism (in this case, WPF). To achieve Separation of Concerns by moving the logic from the UI, the command uses the ICommand interface.

- The sender and CanExecuteRoutedEventArgs parameters are not in the signature.
- The CanExecute event handler returns a bool.
- The CanExecuteChanged event is hooked into the CommandManager.
- The Command interface does not have a Text property; this is only necessary if you code binding to labels MenuItems and Buttons.

## Listing 4-9: CustomSaveCommand

```csharp
public class CustomSaveCommand : ICommand
{
    public string Text { get; set; }
    public CustomSaveCommand(string text)
    {
        Text = text;
    }

    public void Execute(object parameter)
    {
        //Insert 'Save' code here
        //Display feedback to user
        MessageBox.Show(parameter.ToString());
    }

    public bool CanExecute(object parameter)
    {
        return !string.IsNullOrEmpty(parameter as string);
    }

    public event EventHandler CanExecuteChanged
    {
        add { CommandManager.RequerySuggested += value; }
        remove { CommandManager.RequerySuggested -= value; }
    }
}
```

In the sample, the custom command is instantiated through the code-behind the same way the custom RoutedUICommand was in the preceding example. The next section details a much better way to handle exposing the commands to the XAML.

## Separation of Concerns and testability

The result for the Window with the custom SaveCommand has the same look and features as the preceding example. The difference between the two is that the business logic is now in a wholly-contained class that is independent of the display mechanism (in this case, WPF).

This allows for execution of the code in the command class without fighting the CommandManager subsystem or the WPF rendering engine. It also allows for the command to be reused for more than one Window.

The unit tests in this chapter use MbUnit, which is part of Gallio. Any test framework will work (including NUnit, XUnit, MSTest, and so forth). You can find Gallio at www.gallio.org. You can find out more about unit testing, test-driven development (TDD) and NUnit on the website at http://csharp102.info.
