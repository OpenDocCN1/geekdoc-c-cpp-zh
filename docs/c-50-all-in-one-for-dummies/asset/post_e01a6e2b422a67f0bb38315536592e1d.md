## Contract driven

In-client server model, an interface defines a contract of sorts between the domain and the user interface. You can use that contract to drive development in the same way that you use a contract to drive a business deal. If you know what I require and I know what you require, we can quickly and easily make a deal.

A web service is required to have an interface that conforms to the Web Services Description Language (WSDL) standard. WSDL describes expected inputs and allowed outputs as an interface would, creating a contract between the service provider and the client.

In .NET, your contract is created automatically from the code for the service. If you call a service in the browser (which isn't the way it's designed to be called — I tell you more about that later in this minibook) of the development machine, you see the test screen in Figure 1-1. Even though the browser gains some important information about the service, it isn't the contract. The contract is behind the Service Description link.

For languages, the client does something essentially the same thing no matter whether it's Java or Basic or PHP or Ruby: At compile time, it reads the WSDL and creates a proxy that the client talks to.

- Brokers the communication process between the client and the service
- Provides type safety, if it's supported
- Generally makes your life easier (and the contract it provides) - is an important part of a developer's work

The contract isn't legally binding (and it contains only a small amount of print). The service provider reserves the right to change the service as it wants and even forge ahead the WSDL with no fear of legal reprisal. Because you're .NET developer, though your WSDL is generated automatically.

## Chunky versus chatty

Although the chunky-chatty services issue might sound like a face-off with candy bars, it isn't.

Rather than perform small, incremental operations via web services, you use them to make large, sweeping "strokes." The length of individual calls might be larger, but the number of communications is fewer, which reduces network overhead.

Suppose that an application changes the settings of a piece of hardware located away from it — perhaps your home heating system (which is a good use of service). The client application (your computer) is absolutely local, the remote device (your heater) is certainly remote, and a network (probably the Internet) is in the middle. If you have a service with a series of individual controls, such as TurnFanOn and TurnFanOff, it's a common interface for a local application, such as connecting a heater directly to your computer.

The following chunk of code gives an example of how chatty sort of interface:

```c
namespace HomeHeater
public class Chatty : IChatty
{
    public bool TurnFanOn()
    {
        return true;
    }
    public bool TurnFanOff()
    {
        return true;
    }
    public bool SetTemperature(int newTemperature)
    {
        return true;
    }
    public bool SetFanSpeed(string newFanSpeed)
    {
        return true;
    }
}
```

The interface in this example is chatty (in case you couldn't tell it from its class name). Every time you change a knob on the controller, a call is made to a service. Move the temperature to 72 degrees and call the service. Turn the fan to its High setting and call the service. Turn the temperature back down to 71 degrees and call the service. The client "chats" with the service.

Nothing is intrinsically wrong with this implementation. For a service, though, with more network overhead for every call, it's not the best way to build methods. Instead, you want your client to change settings and then pull a big lever on the side to make all the changes at once.

A chunky interface provides a domain model for the client to use, with properties to set. Then, after all settings are in the model object, you send the whole shootin' match to the service. It looks like this:

```csharp
namespace Heater{
    public class Chunky : IChunky {
        public bool UpdateHeaterSettings(HeaterModule heaterModule){
            return true;
        }
    }
    public class HeaterModule {
        public int Temperature { get; set; }
        public bool FanOn { get; set; }
        public string FanSpeed { get; set; }
    }
}
```

Now, no matter how often you make changes, the service is called only when you pull the “big lever” (update it). Whether this action prevents users from updating after every change depends on your interface. In general, this design principle is the best one for service development.

You may wonder anyone would bother with a concept as convoluted as web services. I can assure you that many good reasons exist and you will want to use this technology on a project.

## Building Service-Oriented Applications

The first and most obvious use of a service is to create a Service-Oriented Application, or SOA. This overloaded, overused term means that your application (like the heating system I mention in the previous section) uses services to assist a remote client with server communications.

Unfortunately, the term SOA is no longer useful in the marketplace. Many so-called “experts” have chimed in with large, unmanageable ideas for the creation of systemwide services that is impossible for anyone to separate the wheat from the chaff.

The concept is simple: The user interface calls a service at some point to communicate with the server. You do this for two reasons:

- Scalability: It’s the main reason to use service.
- Reusability: Every organization has a list of its participants — clients, users, voters, cooks, or mailing list subscribers. Regardless of the type of participant, all the people on the list have first and last names and other identifying characteristics. Because the services use a common format — usually XML over HTTP — you can easily install parts of the application on their own machines to isolate them physically. Because the functionality of the deleted part is called a service, you can scale the application horizontally — from one to multiple servers.
