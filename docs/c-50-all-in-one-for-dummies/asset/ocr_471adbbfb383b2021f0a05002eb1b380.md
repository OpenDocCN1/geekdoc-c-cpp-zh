# Handling errors

As you may imagine, errors in the REST space are a little different than what you might experience in SOAP. There are predefined ways to handle errors in REST, and they are the same as what you see on the web. It's the same deal, more or less.

That means you should return 404 (file not found) if you misspell the service, and 500 (internal server error) if a server error occurs. This isn't WCF programming at that; it's a brave new world.

Fortunately, System.ServiceModel.Web has a class called WebFaultException that will help with that. It will take an object and help morph it into an HTTP status code with little fuss. I recommend adding a method like this to your project:

```
private WebFaultException<String> InternalError(Exception ex)
var msg = ex.Message;
if (null != ex.InnerException)
{
    msg += " " + ex.InnerException.Message;
}
return new WebFaultException<String>(msg, HttpStatusCode.InternalServerError);
```

# Dealing with the nasty MVC cache

One thing that you have to handle is the cache. MVC's speed is largely due to caching, which saves requested data in a buffer that might require database or other resource usage.

Something that tells the HttpContextContext to ignore the cache will help. Here is a little method that I have found useful for resetting cache settings for REST projects:

```
private void SetNoCache()
{
var cache = HttpContext.Current.Cache;
cache.SetExpires(DateTime.Now.AddMinutes(-1));
cache.SetCacheability(HttpCacheability.NoCache);
cache.SetStore();
}
```
