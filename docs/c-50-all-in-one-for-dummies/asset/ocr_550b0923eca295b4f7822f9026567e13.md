# Get Your ViewModel On 637

Implementing in the Model reduces work, because it merely adds a few lines of code into properties already being implemented in the classes. A main argument against Model implementation revolves around code reuse. For example, if the Model is used by an ASP.NET application, those events are still raised, but no one is listening. This could potentially present a performance issue. Or, if you use the same model for WPF and non-WPF Views, then a simple flag passed to the constructor of the Model classes indicating whether the events should be raised or not resolves issue.

Both ways are valid implementations. Your application and specific situation will most likely dictate that those interfaces are implemented.

In Chapter 3, you discover that if a control doesn't have an explicit DataContext, it is inherited from the closest parent in the control tree that has a DataContext explicitly assigned.

When developing WPF applications using the ViewModel pattern, the instance ViewModel becomes the Window's (or user control's) DataContext.
