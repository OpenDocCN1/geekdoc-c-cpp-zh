## 754 Getting Know SOAP

If you're working inside the Microsoft stack — meaning, you're communicating with other .NET projects — you are golden. Within the Microsoft platform, everything is defined the same.

However, if you're communicating outside the .NET Framework — say with IBM or Sun — you should expect problems if you're using WS-* defined functionality.

The take-home is that SOAP includes a lot of standard functionality that isn't found anywhere else. Sure, some distributed message contracts have a lot of features found in SOAP, and SOAP might not be completely implemented the same everywhere, but there isn't anything that even tries to provide this functionality in a standardized way.

From this perspective, SOAP is a fantastic platform. Need transactions, secure transactions? SOAP has them. Need large binary attachments? SOAP has. Have Business Execution Language requirements? There's a SOAP for that.

## Big, fat, and slow

All this at the trough of standardized features has made SOAP, well, a little large-bodied. Need let me give you an example. The XML required to just set the context for transactions (the service of a cookie) is

```xml
<wscoord:CoordinationContext
xmlns:wsa="http://www.w3.org/2005/08/addressing"
xmlns:wscoord="http://docs.oasis-open.org/"
xmlns:ws-tx="wscoord/2006/06/"
xmlns:myApp="http://www.example.com/myApp"
S1:mustUnderstand="true">
  <wscoord:Identifier>
    <http:Identifier>http://Fabrik123.com/sl/1234</http:Identifier>
    <wscoord:Expires>2006-01-01</wscoord:Expires>
    <wscoord:CoordinationType>
      <http://docs.oasis-open.org/ws-tx/2006/06/
    </wscoord:CoordinationType>
    <wscoord:RegistrationService>
      <wsa:Address>
        http://Business456.com/
        mycoordinationservice/registration
      </wsa:Address>
    </wscoord:RegistrationService>
    <wscoord:ReferenceParameters>
      <myApp:BetaMark> . . . </myApp:BetaMark>
      <myApp:EBDCode> . . . </myApp:EBDCode>
    </wscoord:ReferenceParameters>
    <wscoord:RegistrationIsolationLevel>
      <myApp:IsolationLevel>
        RepeatableRead
      </myApp:IsolationLevel>
    </wscoord:RegistrationIsolationLevel>
</wscoord:CoordinationContext>
```

## Making an ASMX Service 755

In the Java world, 10MB SOAP messages are not uncommon — although that includes the payload — and that works out to, 200,000 lines? In one HTTP call? That's probably a bit much.

SOAP dramatically increases your overhead in communication. If you don't need the security, federation, and transaction capabilities of SOAP, consider REST — covered in Chapter 4. If you're communicating in a homogenous environment, consider binary encoding.

On the other hand, if you're communicating in moderately heterogeneous environments and in fact need an encrypted, federated transaction using a common enterprise data model, by all means look at SOAP.
