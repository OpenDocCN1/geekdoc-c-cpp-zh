# Custom commands with ICommand

Custom RoutedUICommands solve the problem of getting rid of all nasty OnClick event handlers, consolidating execution code into one handler and bringing along the goodness of the CanExecute event handler to enable a more dynamic and intuitive user interface.

To achieve Separation of Concerns by removing the implementation from the commands from the ground up starting with the ICommand interface. The interface for ICommand contains the CanExecute and the Executed event handlers as well as the CanExecuted differences:

The code in Listing 4-9 shows an example Save command. Consider these differences:

+   * The sender and CanExecuteEventArgs/RoutedEventArgs parameters are not in the signature for the event handlers. In this case is a single parameter of object type. This is the "parameter" object passed in the UIElement.

+   * The CanExecute event handler returns a bool. The return value is the mechanism for enabling/disabling commands (instead of setting the CanExecute property of the event argument).

+   * The command doesn't get set in the CommandBindings XAML, but uses the CanExecuteChanged event to tie into the SqlCommand manager. To enable the correct handling of the custom command by the Command subsystem, the QuerySuggested events get hooked into the CanExecuteChanged event.

+   * The Command interface does not have a Text property. This is only necessary if you code binding to populate the labels for MenuItem and Buttons bound to the command. The sample code adds a Text property to enable this, because it's a simple property and not tied into the Dependency or RoutedEvent subsystems, MenuItems will not automatically populate the Header.
