## Model repositories
The pattern is commonly used for Line of Business applications to move data between the data store and the model classes. For the sample ViewModel, I include a very simple interface (shown in Listing 4-18) that has a GetAll method and an Update method (not even remotely a repository, but all that you need (for the examples). Note the use of generics to enforce strong typing in the repositories that implement this interface.

# Listing 4-18: The Repository Interface

```csharp
public interface IRepository<T>
{
    IList<T> GetAll();
    bool Update(T model);
}
```

The repositories in samples return hard-coded values instead of connecting to a data store. It's common practice to create classes that are used only for testing or prototyping. The convention I prefer is to call them by appending Fake to the name (as shown in Listing 4-19) so that other developers have no doubt about their intended purpose. Additionally, the examples do not implement the Update methods because they are not used for the ViewModel samples.

## The Add customer command

Interestingly using the ViewModel pattern, the commands can be developed prior to it, enabling Test Driven Development for the commands. Using the same approach discussed in this chapter, a "Commanding Base" section earlier in this chapter, a CommandBase class (shown in Listing 4-21) is extracted to hold the common properties and the CanExecute event.

## 644 Get Your ViewModel

# Listing 4-21: CommandBase : ICommand

```csharp
public abstract class CommandBase : ICommand
{
    public string Text { get; set; }
    public abstract void Execute(object parameter);
    public abstract bool CanExecute(object parameter);
    public event EventHandler CanExecuteChanged
    {
        add { CommandManager.QuerySuggested += value; }
        remove { CommandManager.QuerySuggested -= value; }
    }
}
```

The AddCustomer (shown in Listing 4-22) takes the Customer list as a parameter and adds another customer to the list. In this example, it's a hard-coded set of values, in which you'd probably have no window (or data entry mechanism) to gather the required information.

The Execute event handler checks that the parameter is List<Customer>. There is an additional check in the Execute method. It is essentially redundant — the command should never execute if the parameter is not IList<Customer>. However, defensive programming kicks in, and I always check to avoid the possibility of throwing an error.

# Listing 4-22: AddCustomer : CommandBase

```csharp
public class AddCustomerCommand : CommandBase
{
    public AddCustomerCommand()
    {
        Text = 'Add Customer';
    }
    public override void Execute(object parameter)
    {
        var list = parameter as IList<Customer>;
        if (list == null)
        {
            return;
        }
        list.Add(new Customer (ID = 4, Name = 'New Customer'));
    }
    public override bool CanExecute(object parameter)
    {
        return parameter is IList<Customer>;
    }
}
```

## Defensive programming or try-catch?

Is it better to code extra lines to prevent exceptions or wrap the code in a try-catch block? Exceptions are expensive and generally should not be considered flow-of-control devices. Just like them, exceptions should be, well, exceptional.

Why don't these samples have try-catch? Merely for brevity. Logging and error handling are necessary in any real code, but may send the reader down a rabbit hole that would detract from the concepts of the current section.

## The ViewModel
So, you're thinking to yourself at this point, "There's a bit of code slog so far. And we haven't even touched the ViewModel yet?" And you're right. However, as soon you see, the ViewModel becomes a rather trivial exercise because of the setup you've already done. There are just three properties in the ViewModel and two lines of code that need to be run in the constructor (and one of them is required by the XAML rendering engine). Yep. That's it.

The image in Figure 4-6 contains two combo boxes that need to be populated. One of the tenets of the ViewModel pattern is to provide a one-stop shop for the view. In addition to the main data (Customers), this includes any reference data (Sales Regions). The ViewModel (shown in Listing 4-24) contains these IList<T> as properties that can be bound to the view and (in this example) are populated in the constructor.

The Window also contains a single Button that needs to be bound to the AddCustomerCommand. Commands require a bit more plumbing because they must be instantiated prior to use. The technique shown in this sample is just in time instantiation and is meant to cut down on resource consumption. If the button never gets clicked, why the command in memory?

# Listing 4-24: The ViewModel

```csharp
public class CustomerMaintenanceViewModel
{
    private ICommand _addCustomerCmd;

    public CustomerMaintenanceViewModel()
    {
        Regions = new SalesRegionRepositoryFake().GetAll();
        Customers = new CustomerRepositoryFake(Regions).GetAll();
    }
    public IList<Customer> Customers { get; set; }
    public IList<SalesRegion> Regions { get; set; }

    public ICommand AddCustomerCmd()
    {
        get { return _addCustomerCmd ?? (_addCustomerCmd = new AddCustomerCommand(this)); }
        set { _addCustomerCmd = value; }
    }
}
```
