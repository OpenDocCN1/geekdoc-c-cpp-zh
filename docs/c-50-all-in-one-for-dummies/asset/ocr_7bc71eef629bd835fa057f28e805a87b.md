The resulting FileStream object fs is then wrapped in a StreamReader sr to provide convenient methods for accessing the file. The StreamReader is finally passed back to Main() for use.

When the file-open process is done, the FileReader calls the ReadToFileConsole() method, which loops through the file lines of text using the ReadLine() call. The program echoes each line to the console with the ubiquitous Console.WriteLine() call before heading back up to the top of the loop to read another line of text. The ReadLine() returns a null when the program reaches the end of the file. When this happens, the method breaks out of the read loop and returns. Main() then closes the object and terminates. (You might say that the parting of this reader program is wrapped in a while loop inside a method that is in a try block wrapped in an enigma.)

The catch block in Main() exists to keep the exception from propagating the foot chain and aborting the program. If the program throws an exception, I have the catch block write a message and then simply swallow (ignore) the error. You're in Main(), so there's nowhere to rethink the exception, and nothing to do but close the stream and close up shop. The catch is to let the user know why the program failed and to ask for a different filename, but this program is so small that it's simpler to let it run again.

Providing an exception handler with a catch block that swallows the exception keeps a program from aborting an unwanted error. However, use this techniqueing and swallow the exception only if an error would be truly, no fake, nondomain. See the more extensive discussion in Book II.
