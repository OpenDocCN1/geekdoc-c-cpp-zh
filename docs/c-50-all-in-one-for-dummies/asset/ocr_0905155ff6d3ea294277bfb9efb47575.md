# Looking back at the DSL Tools

One of the first ways that Microsoft tried to implement code generation back in the day (and it is still around) was through the Environment Design Time Environment (EnvDTE), and by giving developers access to the code files themselves.

This barebones approach provided by EnvDTE isn't really what Microsoft was after. The code of templating was to provide a language of languages, which developers could use to model their own development style. The code generation is almost secondary.

Microsoft's next shot to solving the code-generation problem was the Domain-Specific Languages Tool. The idea was to use the EnvDTE and other markup languages to describe a very high-level idea in a project — for example, any ASPX page. No specific ASPX page: any ASPX page.

That description can then become the code that you ask for for a new ASPX page. See what I mean? When you describe a higher-level concept like requiring a new ASPX page, the DSL emits a concrete version, which you can edit.

# Looking ahead to what it became

Because T4 is designed to generate anything, it can emit any kind of file. If you think about it, it all makes sense. If an entity in your domain model is a product website, T4 would have to emit HTML, CSS, and JavaScript when a new product is added to the database.

The same thing also applies to the language that is emitted as part of the project. T4 doesn't care what code you are emitting. It just wants to stamp out matches the model you define for it. If you set up the model to use C#, that's fine. VB? Fine. T4 is just generating and giving text an extension.
