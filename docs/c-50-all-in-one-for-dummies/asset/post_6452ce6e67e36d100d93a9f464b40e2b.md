
# Installing Visual Studio 507

Then you wait. Visual Studio is big. It takes a while.

The official requirements for Visual Studio are shown in this list:

- * Operating system:
  - Windows 7 XP
  - Windows 8
  - Windows Server 2008 R2 SP1
  - Windows Server 2012

- * Supported architectures:
  - 32-bit (x86)
  - 64-bit (x64)

- * Hardware:
  - 1.6 GHz or faster processor
  - 1GB of RAM
  - 10GB of available hard disk space
  - 5400 RPM drive
  - DirectX 9-capable video card at 1024x768

You can run on this configuration — I have tried it, and it works. It's not pretty. Visual Studio 2012 is all written in WPF, which can (with this size of an application) be a resource hog.

Seeing how that is the case, I am sure you aren't surprised to find that I have a collection of suggestions for installing Visual Studio.

First, here is what I consider to be a realistic base configuration for Visual Studio:

- * 2.4 GHz 64 bit core processor
- 64-bit Windows 8 with 8GB of RAM
- 250GB of available HDD space
- Dual monitors (or a laptop with an external monitor) with one being a touch screen

Seems excessive? It isn't. First, I recommend that you use a virtual machine for any project that does anything to your base install of Windows. Virtual PC is free, and you can usually get a 80-day trial of Windows 8 without a problem. Change the settings on Virtual PC to run the clock only while the machine is running, and you have a perfect test bed.

# Breaking Down the Projects

All is left to do after you have run the setup program and set your defaults is start on a project and get your hands dirty. All the project types (except one or two) in the first two minibooks were Console applications, meaning they are meant to be run at the command prompt. There are a lot more projects available.

Notice four main kinds of projects in the Visual Studio New Project dialog box.

- **Windows Store projects** are full-screen packaged apps that go in the Windows Store for Windows 8 users. (usually) packaged for distribution, but rather deployed to the store for distribution there.

- **Windows projects** are rich client applications that compile into .EXES and run on your computer. Microsoft Word is a Windows application.

- **Web projects** make websites and require a web server to run. (A web server is included with Visual Studio for development purposes.) Microsoft.com is an example of a web application.

- **Special projects** includes things like setup projects (projects that build setup programs) and database projects (projects that give a framework for databases). They are usually used with a Windows or web application. The Setup.exe program you run in the preceding section to install Visual Studio is an example of one of these special projects — a setup project.

## Exploring the New Project dialog box

I start with a breakdown of the New Project dialog box, shown in Figure 1-2. This screen is an important part of the usability of Visual Studio. You open it by clicking the New Project link on the setup page.

The section of the dialog box to the left far is a tree-view selector, similar to the one in Outlook. You have three options — Recent Templates, Installed Templates, and Online Templates. Installed Templates are selected. These templates, as Visual Studio calls them, are projects.

Within the selector is a WPF style tree viewer. Instead of maples and oaks, this tree has all the project categories described in upcoming sections of this chapter.

If you click, for example, the C# option in the tree view, all the projects for Visual C# appear in the window to the right. If you click one of the suboptions, just those project types — for Visual C — appear.

To specify the version of the .NET Framework you would develop for, you can use the drop-down list just above the project list that says .NET Framework 4.5. To change the sorting options, use the Sort By: drop-down list directly to the right. One more step to the right, and you can change your options (icon in the dialog box).

# Understanding solutions and projects

Visual Studio project files, and the solutions that hold them, are a constant topic of interest to Microsoft developers. You work on one solution at a time, with a number of projects within. How you organize your solutions and their projects will make or break when it comes time to find something.

You can think of solutions as folders that hold projects. They're just folders with special properties. In fact, note the checkbox in the lower right corner of 1-2. It's the one labeled Directory for Solution. That's what I mean — the solution is really an organizational “folder” for the projects.

Projects are where you put the code files for your programs. They store all kinds of things, with references to the .NET Framework, resources like graphics, and what file should be used to start the project.

Solutions do the same thing for projects that do for files. They keep the projects in a folder and store certain properties. For instance, they store which project should be started when debugging starts.

Neither the project nor the solutions have much to do with a finished program. They are just simple organizational structures for Visual Studio. The installation of the finished program is determined by the setup project.

In reality, a solution is more than that. It's in a folder that is used by Visual Studio to manage the developer experience. So, inside the folder for the solution is a file describing the projects within and then a bunch of folders with the projects themselves.

There are files for the projects, too — files that describe the resources and references for the project. They are all XML files that contain text references to the values that you set using Visual Studio.

When developing in Visual Studio, you shouldn't worry about that. In 14 years of working in various versions of Visual Studio, I have had to look at a solution or project file only a few times, and only in special situations.
