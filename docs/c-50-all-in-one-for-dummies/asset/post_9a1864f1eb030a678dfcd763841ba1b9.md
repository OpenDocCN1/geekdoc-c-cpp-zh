# Baking Cookies

Cookies are the only thing that a website can directly save on a client without the client's direct permission. It might require the indirect permission, because a user can disable cookies, but passively a cookie can be saved without asking the user, "Is it okay if I save this?"

Cookies are useful for state management. If you know the ID of the client's shopping cart, for instance, you can save ID in a cookie, and even if the client goes away for a week and comes back, you will still be able to go back to the business layer and look up the information.

Cookies are stored in a collection — actually a dictionary of keys and values. If you know what you're looking for, you can query the collection for the value; if you don't, you can loop through the collection until you find it.

The cookies collection is managed using the Request and Response object — using the HttpRequest and HttpResponse classes I cover in the earlier section "Surfing Web Streams."

# Coding for client-side storage

To get a cookie, you have to first leave a cookie. In part of the response to a client — say, after he logs in — you want to tell the platform to save information in the Cookies collection.

# 718 Baking Cookies

Remember that cookies are plain text — anyone can read them. Never store something that can be used by someone wearing a proverbial hat. I almost always create a System.Guid (a globally unique identifier) and use that to track information that I persist somewhere in my back-end data store.

What is even better to store information about the session itself and have an understanding that the information will be removed from the database after some time. This prevents the impersonation of the user by someone who intercepts the cookie. There are a lot of options, but check out the best practices offered by Microsoft and other organizations before setting your cookie strategy.

If I want to store information about the session in the cookie and tell the database that my customer is using session, I generate a Guid and save it in both places. Then I can retrieve the cookie at the next request, compare it to the available Guids in the user collection, and find the user in question.

Here is an example of how to code the cookie based on session information:

```
using System;
using System.Collections.Generic;
using System.Linq;
using System.Web;
using System.Web.UI;
using System.Web.UI.Controls;

namespace Chapter_4
{
    public class Cookies : System.Web.UI.Page
    {
        WebUser currentUser = new WebUser();
        List<WebUser> usersDatabase = new List<WebUser>();
        protected void Load(object sender, EventArgs e)
        {
            if (!IsPostBack)
                // This is a first request, so we need to set the cookie
                Guid sessionGuid = new Guid();
                currentUser.SessionId = sessionGuid;
                // Tell the database about the new user
                usersDatabase.Add(currentUser);
                // Set the cookie
                Response.Cookies.Add(new HttpCookie("SessionId", sessionGuid.ToString()));
            }
        }
    }

    // This Guid would be in the library somewhere,
    // not actually in this file.
    public class WebUser
    {
        public Guid SessionId { get; set; }
    }
}
```

# Wrang cookies on the server

So now the user has the cookie, and the next request comes in. I need to grab the cookie and search my known user base to get the information that I need. The boldface in the following code indicates the code added:

```
using System;
using System.Collections.Generic;
using System.Linq;
using System.Web;
using System.Web.UI;
using System.Web.UI.WebControls;
namespace Chapter_4 {
    public partial class Cookies : System.Web.UI.Page {
        WebUser currentUser = new WebUser();
        List<WebUser> usersInDatabase = new List<WebUser>();
        protected void Page_Load(object sender, EventArgs e) {
            if (!IsPostBack) {
                // This is the first request, so we need to set the cookie
                Guid sessionGuid = new Guid();
                currentUser.SessionId = sessionGuid;
                //Tell the database about the new user
                usersInDatabase.Add(currentUser);
                Response.Cookies.Add(new HttpCookie("SessionId", sessionGuid));
            }
            else {
                // This is the postback so we need to get the cookie
                string cookieSession = Request.Cookies.Get("SessionId").Value;
                Guid sessionGuid = new Guid(cookieSession);
                var returningUser = from u in usersInDatabase
                    where u.SessionId.ToString() == sessionGuid.ToString()
                    select u
                foreach (var user in returningUser)
                    currentUser = user;
            }
        }
        //This class would be in the library somewhere,
        //not actually in this file.
        public class WebUser {
            public Guid SessionId { get; set; }
        }
    }
}
```

# How ASP.NET manages cookies for you

A lot of the stuff you use to store in a cookie is managed by the ASP.NET engine. Session state, the most common example (discussed earlier in the "Surfing Web Streams" section), is now handled by the ViewState object. You can store information in the ViewState like you would in a variable, and the information is encoded for you and kept in a special field in the markup.

ViewState has its problems, and lot people don't like to use it. In fact, many ASP.NET applications in enterprises have turned it off to save bandwidth and prevent poor coding practices. In these cases, a return to cookies is your best bet to maintain a constant communication with the user.

# Tracing with TraceContext

The TraceContext class provides all the detailed server processing information about a web page in ASP.NET. It is exposed in the code-behind of the Trace object and allows you to write messages to the trace log and screen when certain things happen.

The benefit is that this Trace code runs only when you have tracing on. This gives programmers the option to leave tracing code in a working application without impacting the performance or functionality.

This allows you to think about debugging while you code. When I build a web application, I just assume that it will break. Break is. It probably will. Programming is hard, and web programming is harder. It is likely that either you or the environment will have a fault at some point.

Why not make it easy for yourself later on the road?

If you decide which parts of the application are most likely to have problems while you code them, you can insert trace messages as you go. It seems like a defeatist attitude, but really I think it is a realistic attitude. Even if it is just caused by bad data in two years, you're going to spend some time debugging.

To use tracing, you can alter the @Page statement at the top of each page in the application, or use the Web.config file — which is what you're gonna do. If you want to set up the whole site for tracing, just add the following block code to the Web.Config:

```
<configuration>
  <system.web>
    <trace enabled="true" requestLimit="40" localOnly="false" />
  </system.web>
</configuration>
```
