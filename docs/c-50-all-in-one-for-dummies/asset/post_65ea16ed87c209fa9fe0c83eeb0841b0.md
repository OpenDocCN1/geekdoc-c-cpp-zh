# Using information from requests

The request is a place that you can collect information about the user's needs and use it. It Especially on postback (though not just then), there is a lot of information that you can use, using the following:

- **The content of the request.** The type (ContentType) of the request tells you if it has data or just text. I can learn it if it is ISO or Unicode (ContentEncoding). I also know how long the request is (ContentLength).
- **The text of the request itself.** For instance, I have all the text of the URL (Url) and the request before this one (UrlReferrer). If I just want the querystring (part after the question mark), I can get it with QueryString.
- **Whether the user is logged into a domain** (IsAuthenticated) and if so, who the user is (LogonUserId).
- **Access to the collections** (Cookies).

When you have access to the request, you can make decisions about content. If you need to know about their login information, you have check. A cookie — no problem. Confirm the querystring. Whatever needs to be done. You get information to the business layer, get what you need back, compose the new page of controls, and then need to modify the response. That's when you need the `HttpResponse` class.

# Sending the user somewhere else

One of the most common uses of the Response object is to send the user somewhere else entirely. If you look at the request headers and realize (instance) that the user isn't logged into a Windows domain account (using HttpRequest.Authenticated), you can redirect the user to a

```csharp
if(!Request.Authenticated){
  Response.Redirect("login.aspx");
}
```

On the other hand, sometimes you need to tell the user that this isn't the right place to be at. Especially if you have to change the structure of your website, RedirectPermanently tells search engine spiders "nope, this isn't anymore. Go over there and change your index"

For instance, say you have a product line that was moved to a new URL. You could use the QueryString for the product line statement, and if you find it, redirectPermanently to redirect the link permanently.

```csharp
if(Request.QueryString("ProductLineID")==4){
  Response.RedirectPermanently("http://newproduct.com")
}
```

# Changing the request or response directly

Sometimes you want to change things directly.

Response.Write, Response.WriteFile, Response.WriteSubstitution all are designed to allow you to do just that. In the old days (before debugging), you had to use Response.Write to put errors into the HTML that you could view with ViewSource. If you're using ASP.NET MVC, there is still a place for that.

Book III, Chapter 1 covers .NET security, and there is a whole book on security that you should read — Writing Secure Code, Second Edition (Microsoft Press) by Michael Howard and DavidBlanc. I'm only covering security in this chapter because the AspNetHostingPermission is in the System namespace, and I want to give it a little attention.

ASP.NET security is a complex topic. Visitors to websites are often bypassing the Windows security system often occurs. Then, bypassing—called impersonation—allows IIS to do things on behalf of the user even if it isn't really known to Windows.

So ASP.NET websites are run most often with whatever the IIS service is running with. Under normal conditions, the service is a fairly restricted account called Network Service. The fact is, however, that you really have no idea what the permissions will be because a hosting company most likely will be managing that. Your users can have administrative permissions for all you.

You can purposefully restrict the permissions of your users in your code. This prevents someone from finding a way through your code logic to call a method you don't be able to call.
