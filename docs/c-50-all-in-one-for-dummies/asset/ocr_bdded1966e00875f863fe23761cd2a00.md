# Why "SUT"?

The variable name for System Under Test and is a common convention in unit-testing. It clearly delineates what is being tested from other objects that are required for the test. # Model unit tests

There isn't much to test in the model. You don't typically write tests against the .NET Framework itself — one has to assume that it works! The only real logic in this is setting of the IsDirty flag and the raising of the PropertyChanged event when something changes.

The first test is to verify that the IsDirty flag gets set when property changes, and it is very straightforward. You create a new Customer, and assert that the IsDirty flag is False, make a change, and then assert that the IsDirty flag is True. This test is shown in Listing 4-15.

# Listing 4-15: Testing the IsDirty Flag

```
[Test]
public void Should_Set_Is_Dirty_On_Property_Change()
{
    var sut = new Customer();
    Assert.IsFalse(sut.IsDirty);
    sut.Name="New Name";
    Assert.IsTrue(sut.IsDirty);
}
```

The second test is much more involved, because it tests the raising of the PropertyChanged event. You have to create a subscriber to this event (and the WPF rendering engine) automatically attach to this event, but you don't want to re-create the rendering engine just to test one method. To test the event, create a subscriber, raise the event, and then assert that the handler of the event was executed.

Tests of this type are typically done with a mocking framework, such as RhinoMocks (the tool used in the samples). Mocking frameworks allow tests for behavior in addition to state, and because the test needs to validate that an event was raised, RhinoMocks is the perfect fit. A deep dive into mocking and behavior testing is beyond the scope of this book. Look at the code, digest it, and tinker with it. It's a great way to expand your testing knowledge!
