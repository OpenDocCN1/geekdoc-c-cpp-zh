# 1.2.7.2 Streaming Algorithms

The streaming scenario is particularly challenging for clustering algorithms due to the requirements of real-time analysis, and the evolution and concept-drift in the underlying data. While database-centric algorithms require exactly once, since the data cannot be stored at all, streaming algorithms require exactly once. In addition to this challenge, the analysis typically needs to be performed in real time, and changing the patterns in the data need to be properly accounted for in the analysis.

In order to achieve these goals, all streaming methods use a summarization technique to create intermediate representations, which can be used for clustering. One of the first methods in direction uses a microclustering approach [7] to create and maintain the clusters from the underlying data stream. Summary statistics are maintained for the microclusters to enable an effective clustering process. This is combined with a pyramidal tree frame to capture the evolving aspects of the underlying data stream. Stream clustering can also be extended to other data types such as discrete data, massive-domain data, text data, and graph data. A number of unique challenges arise in the distributed setting. A variety of stream clustering algorithms are discussed in detail in Chapter 10.

# 1.2.7.3 The Big Data Framework

While streaming algorithms work under the assumption that the data are large enough to be stored explicitly, the data framework leverages storage technology in order to actually store the data and process it. However, as the subsequent discussion will show, even if the data can be explicitly stored, it is often not easy to process and extract insights from it. This is because an increasing size of the data implies that a distributed file system must be used to store the information, and processing techniques are required in order to ensure scalability. The challenge here is that if large segments of the data are available on different machines in order to extract integrated insights from them, it is desirable to exchange intermediate results, so as to minimize communication costs. As an application programmer, this means some challenges in terms of keeping track of which different parts of the data are stored, and the precise ordering of communications to minimize the costs.

In this context, MapReduce framework [28] provides an effective method for analysis of large amounts of data, where the nature of the computations involves linearly computable functions over the elements of the data. One desirable aspect of this framework is that it abstracts the details of which different parts of the data are stored to the application program. As stated in [28], “The run-time system takes care of the details of partitioning the input data, scheduling the program's execution across a set of machines, handling machine failures, and managing the required inter-machine communication. This allows programs without any expertise in parallel and distributed systems to easily utilize the resources of a large distributed system” p. 107. Many clustering algorithms such as k-means are naturally linear in their scalability with the size of the data. A primer on the MapReduce framework implementation on Apache Hadoop may be found in [84]. The key idea is to use a Map function to distribute the work across the different machines, and provide an automated way to shuffle out smaller data in (key,value) pairs containing intermediate results. The Reduction function is performed from the Map step to obtain the final results.
