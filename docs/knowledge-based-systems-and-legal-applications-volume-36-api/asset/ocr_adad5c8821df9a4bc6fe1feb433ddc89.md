We made our growing lists of class and attribute names available to one another. We were able to resolve most conflicts and identify use of the same name to mean different things as we went along. We did our analysis and developed KANT structures independently, then integrated our work into a single knowledge base which was 'owned' by and located at Surrey. With only one integrated knowledge base version control was simplified and necessary consistency to achieve.

Earlier exercises had indicated that starting to analyse a domain looking for entities and their attributes led to the creation of unnecessary (in the sense that they were never referred to in the rules we wrote) classes and/or attributes. So we decided to generate the knowledge base from rules to keep the knowledge base lean as possible. The greatest boon to this style of development was the 'rule patch', a bit of computer program run at Surrey to provide new facilities for KANT. This patch enabled us to compile rules from KANT if the rules were written in the toolkit language and had been put in specially ruled nodes of KANT structures.

When the compiler noticed that a class or an attribute did not exist in the knowledge base we were able to create the classes and add the necessary attributes from KANT. We could also access the knowledge base via KBB which was a useful way of viewing and editing the class hierarchy and the attributes were the simplest way to add a large number of classes and/or attributes at once, but it also caused problems of control. Using KBB rules, classes and attributes could be added to the knowledge base without having a corresponding KANT node available for inspection. It was tempting to use KBB especially when it was quicker than going through KANT, so the knowledge base got out of step with some of the KANT structures.

In later work, KBB and KANT were combined and the KANT structures were apart from what was in a KANT structure could be said to exist in the knowledge base.

Inspection of the knowledge base was of concern to the Advice System it was for the LOD team, but in a different way. We did not anticipate that members of the public would inspect the knowledge-base as they used the system. Whereas the LOD envisaged that their users would. Our concern was to make the transformations through which the knowledge went as it passed from source to encoded knowledge base available to scrutiny by all interested parties — including representing the interests of the public, advice workers, D(H)SS, future developers of the system and who would maintain it — separately from the use of the system.
