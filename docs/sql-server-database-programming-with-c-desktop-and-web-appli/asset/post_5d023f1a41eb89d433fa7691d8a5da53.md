```csharp
private void cmdLogIn_Click(object sender, EventArgs e)
{
  string username = string.Empty;
  string password = string.Empty;
  SelectionForm selfForm = new SelectionForm();
  IQueryable<Login> login = from lg in cse_dept
                            where lg.user_name == txtUsername.Text && lg.password == txtPassword.Text
                            select lg;
  foreach (log in login)
  {
    username = log.user_name;
    password = log.password;
  }
  if (txtUsername.Text == string.Empty || txtPassword.Text == string.Empty)
  {
    MessageBox.Show("Enter a valid username/password");
  }
  else if (txtUsername.Text == username && txtPassword.Text == password)
  {
    this.Hide();
    selfForm.ShowDialog();
    cse_dept.Connection.Close();
    this.Close();
  }
  else
  {
    MessageBox.Show("The Login failed!");
  }
}
```

# SQL Server Database Programming with C#

As we discussed in the last section when we built the entity classes for this project, all entity classes are related or bounded by using the associations (primary-foreign keys).

Also recall that in Chapter 4, we discovered that most LINQ queries are performed on arrays or collections that implement IEnumerable<T> or IList interfaces, but in LINQ to SQL, they are performed on entity classes that apply the IQueryable<T> interface. This means besides the Standard Query operators, LINQ to SQL have additional queries available since IQueryable<T> inherits IEnumerable<T>. Here querying an entity in LINQ to SQL is used with the IQueryable<T> interface, and the <T> is the type of member of the entity class. In this case, it is a Login table. An iteration loop is used to iterate over the result of this query with the Login table. A similar SQL SELECT statement is executed with the WHERE clause. Two criteria are used for this query, user_name and password, and these two criteria are connected with a AND operator. One point is to be the member of our entity class Login, which is named Logins in this query. The relationships between the Login and Student tables are many-to-one, which means that Many faculty_id and students exist in the Login table but only a single or unique faculty_id is in the Faculty table. In other words, the Login class is the main (child) side of a one-to-many relationship. Therefore, in general the member of this class is named Logins, and 's' is attached to the name of the related class.

- **D.** A foreach loop is used to pick up each class from the selected row, which is obtained from the login query. Then, assign two columns, user_name and password, to our local string variables, username and password. The purpose of this assignment is to avoid the overhead cycles when identifying the validation loop. In other words, we prefer to do validation of this loop you would definitely encounter some bugs. Since we are using a typed table we can access each column by its name without using the field-string and the name for the position of each.

- **E.** An error message displayed if any input box is empty to remind users to enter a valid username and password.

- **F.** If both username and password are correct and matched to both columns queried from the Login table, which means this login process is successful, the SelectionForm is displayed and the current form is removed from the screen. The database connection should be closed to disconnect from our sample database.

- **G.** If no match username and password can be found, an error message is displayed to indicate this situation.

It appears that this query is quite simple and all columns in the Login table have been collected, even if we did not perform any query to that. The reason behind this principle is that no information is actually until all columns in the Login class are referenced, and this is deferred loading. This terminology is used to describe the type of loading in which classes are not actually loaded from the database until they are required or referenced.
