## 2.3.1 Relational Data Model

A data model is a blueprint for developing a database. It describes the structure of the database and various data relationships and constraints on the data. This information is used in building tables, keys and defining relationships. The relational model implies that a user perceives the database as made up of rows or tuples and a column is called an attribute. It ensures that all elements in the tables are represented correctly. In order to achieve these goals, designers use a range of tools. The most commonly used tool is the Entity-Relationship Model (ER). A well-planned model will give consistent results and will allow changes later on. The following section elaborates further on the ER Model.

### 2.3.2 Entity-RELATIONSHIP MODEL (ER)

The Entity-Relationship (ER) model was first proposed and developed by Peter Chen in 1976. Then Charles Bachman and James Martin added some refinements. The model was designed to communicate the database design in the form of a conceptual schema. It is based on the perception that the real world is made of entities and relationships. Entity-Relationship diagrams (ERDs) are used to construct relational tables and are a good vehicle for communicating the database design to either end user. The three major components of ER are entities, relationships, and attributes.

**Entities:** An entity is a data object, either real or abstract, about which we want to collect information. For example, a person, a place, or a thing. An entity translates into a table with the same name. Some common examples are departments, courses, and students. A single occurrence of an entity is an instance.

**Relationships:** A database is made up of related entities. There is a natural association between entities; they are referred to as relationships. For example
- Students take courses
- Departments offer courses
- Employees are assigned to departments

The number of occurrences of one entity associated with a related entity is referred to as cardinality.

**Attributes:** Each entity has properties or values associated with it. The attributes of an entity map into fields in tables. The domain of an attribute is a set of all possible values from which an attribute can derive its value.

## 2.4 IDENTIFYING KEYS

### 2.4.1 PRIMARY KEY AND ENTITY INTEGRITY

An attribute that uniquely identifies one and only one instance of an entity is a primary key. Sometimes a primary key consists of a combination of attributes. It is referred to as a composite key. The entity integrity rule states that no attribute as member of the primary (composite) key may ever accept a null value.

A faculty_id may serve as a primary key for the Faculty entity, assuming that all faculty members have been assigned a unique ObjectID. However, caution must be exercised when picking an attribute as a primary key. Last name may make a good primary key because a department is likely to have more than one person with the same last name. Primary keys for the CSE_DEPT database are shown in 2.7.

Primary keys provide a tuple-level addressing in the relational databases. The DBMS ensures the uniqueness of the primary key. Inserting a duplicate value for a primary key field will fail.

### 2.4.2 CANDIDATE KEY

There can be more than one attribute which uniquely identifies an instance of these entities; these are referred to as candidate keys. Any one of them can serve as a primary key. For example, ID Number as Social Security Number may make a suitable primary key. Candidate keys that are not used as primary key are alternate keys.

### 2.4.3 FOREIGN KEYS AND REFERENTIAL INTEGRITY

Foreign keys are used to create relationships between tables. A foreign key is an attribute in table whose values match those of primary key in another table. Foreign keys are enforced to referential integrity, which states that you may not add a record to a table containing a foreign key unless there is a corresponding record in the table to which it is linked. Furthermore, the referential integrity rule also implies that every value of a foreign key in a table must match either the primary key of a related table or be null. Consider two tables, Course and Faculty, in the sample database, CSE_DEPT. The Course table has a foreign entity faculty_id, which is primary key in the Faculty table. The two tables are thus logically related to the faculty_id link. Referential integrity rules imply that we may not add a record to the Course table with a faculty_id which is not listed in the Faculty table. Secondly, there must be a logical link between the two tables. Secondly, if we change or delete a faculty_id in the Faculty table this must be reflected in the Course table, meaning that all records in the Course table must be modified using a cascade update or cascade delete (Figure 2.8).
