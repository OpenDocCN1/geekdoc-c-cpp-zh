# 2.4 IDENTIFYING KEYS

# 2.4.1 PRIMARY KEY AND ENTITY INTEGRITY

An attribute that uniquely identifies one and only one instance of an entity is a primary key. Sometimes a primary key consists of a combination of attributes. It is referred to as a composite key. The entity integrity rule states that no attribute as a member of the primary (composite) key may ever accept a null value.

A faculty_id may serve as a primary key for the Faculty entity, assuming that all faculty members have been assigned a unique ObjectID. However, caution must be exercised when picking an attribute as a primary key. Last name may make a good primary key because a department is likely to have more than one person with the same last name. Primary keys for the CSE_DEPT database are shown in 2.7.

Primary keys provide a tuple-level addressing in the relational databases. The DBMS ensures the uniqueness of the primary key. Inserting a duplicate value for a primary key field will fail.

# 2.4.2 CANDIDATE KEY

There can be more than one attribute which uniquely identifies an instance of these entities are referred to as candidate keys. Any one of them can serve as a primary key. For example, ID Number as Social Security Number may make a suitable primary key. Candidate keys that are not used as primary key are alternate keys.

# 2.4.3 FOREIGN KEYS AND REFERENTIAL INTEGRITY

Foreign keys are used to create relationships between tables. A foreign key is an attribute in table whose values match those of primary key in another table. Foreign keys are enforced to referential integrity, which states that you may not add a record to a table containing a foreign key unless there is a corresponding record in the table to which it is linked. Furthermore, the referential integrity rule also implies that every value of a foreign key in a table must match either the primary key of a related table or be null.
