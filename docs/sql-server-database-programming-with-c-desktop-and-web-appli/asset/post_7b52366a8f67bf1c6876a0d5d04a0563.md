## 4.7.4.1 Construct an ObjectQuery Instance

The ObjectQuery generic class represents a query that returns a collection of zero or more typed entities. Each object query is typically constructed from an existing object context, instead of being manually constructed, and always belongs to that context. This context provides the connection and metadata that is required to compose and execute the query. The ObjectQuery generic class implements the IQueryable generic interface, whose builder methods enable LINQ queries to be built incrementally.

## 4.7.4.2 Compose a LINQ to Entities Query

Instances of the query generic class, which implements the IQueryable interface, serves as the data source for LINQ to Entities queries. In a query, you specify exactly the information you want to retrieve from the data source. A query can also specify how information should be sorted, grouped, and shaped before it is executed. In LINQ, a query is stored in a variable. A query takes no arguments and returns no data; it only stores the query information. After creating a query you must execute it to retrieve data.

LINQ to Entities queries can be composed in two different syntaxes: query expression syntax and method-based query syntax. We have provided a very detailed discussion about the query expression syntax and method-based query syntax with real code examples in Sections 4.5.1.1 and 4.5.1.2 in this chapter. Refer to these to get a clear picture for these two syntaxes.

## 4.7.4.3 Convert the Query to Command Trees

To execute a LINQ to Entities query against the Entity Framework, the LINQ query must be converted to a command tree representation that is executed against the Entity Framework.

LINQ to Entities queries are comprised of LINQ Standard Query Operators (as Select, Order, and OrderBy) and expressions. LINQ Standard Query Operators are not defined by a class, but are static methods on a class. In LINQ, expressions can contain anything that uses types within the System.Expressions namespace and, by extension, anything that can be represented in a lambda function. This is a superset of the expressions that are allowed by the Entity Framework, which are by definition restricted to operations allowed on the database, and supported by ObjectQuery.

In the Entity Framework, both operators and expressions are represented by a single hierarchy. The command tree is used by the Entity Framework to execute the query. If the LINQ query cannot be expressed as a command tree, an exception will be thrown when the query is being converted. The conversion of LINQ to Entities involves two sub-conversions: the conversion of Standard Query Operators and the conversion of expressions. In general, expressions in LINQ to Entities are evaluated on the server, so the behavior of the expression should not be expected to follow CLR semantics.

## 4.7.4.4 Execute the Query

After the LINQ query is created by the user, it is converted to a representation that is compatible with the Entity Framework (in the form of command trees), which is then executed against the store. At query execution time, all queries (or components of the query) are evaluated on the client or on the server. This includes expressions that are used in result materialization or projection examples.

A query expression can be executed in two ways. LINQ queries are executed each time the variable is iterated, not when the query variable is created; this is referred to as deferred execution. The query can also be forced to execute immediately, which is useful for caching results. The following example shown in Figure 4.43 uses Select to return all the rows from *Faculty* and display the faculty names. Iterating over the query variable in the *foreach* loop causes the query to execute.

When a LINQ to Entities query is executed, some expressions in the query must be executed on the client and on some parts before the query is executed on the server. Client-side evaluation of an expression takes place on the client, the result of that evaluation is substituted for the expression in the query, and the query is then executed on the server. Because queries are executed on the data store, the data store configuration overrides the behavior specified in the client. Null value handling and numerical precision are examples of this. Any exceptions during query execution on the server are passed directly up to the client.

## 4.7.4.5 Materialize the Query

Materialization is the process of returning data to the CLR. LINQ to Entities materialization is usually performed by the Entity Framework, returning one of the following:

- A collection of zero or more typed entities
- Anonymous types.
- Grouping instances.

```csharp
ObjectQuery<Faculty> faculties = from fi in Faculties
where fi.faculty_id == "B788880"
select fi.faculty_name;

Console.WriteLine("Faculty Names:");
foreach (var name in faculties)
{
    Console.WriteLine(name);
}
```

## 4.8 LINQ TO XML

LINQ to XML was developed with Language-Integrated Query over XML in mind and takes advantage of standard query operators and adds query extensions specific to XML. LINQ to XML is a modern in-memory XML programming language to take advantage of the latest .NET Framework innovations. It provides both DOM- and XQuery/XPath-like functionality in a consistent programming experience across the different LINQ-enabled data technologies.

There are two major perspectives for thinking about and understanding LINQ to XML. From one perspective you can think of LINQ to XML as a member of the LINQ Project family technologies providing a consistent query capability with a consistent query experience for objects, relational database (LINQ to SQL, LINQ to DataSet, LINQ to Entities), and other data technologies as they become LINQ-enabled. From another perspective you can think of LINQ to XML as a full feature in-memory XML programming API comparable to a modern, redesigned Document Object Model (DOM) XML Programming API plus a few features from XPath and XSLT.
