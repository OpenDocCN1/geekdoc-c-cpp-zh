In order to recover deleted faculty, the following points must be kept in mind and the following procedures must be followed:

- 1) Recall that we build our database CSE_DEPT, exactly when we set up the relationships among tables, with the Cascade mode for both Update and Delete Rules for INSERT and UPDATE Specification field between the Faculty and Login, Faculty and Course, and Course and Student tables. This means that for deleted, the Faculty is a parent table for the Login and the Course are child tables to Faculty. Similarly, the Course is a parent table for the StudentCourse table and the StudentCourse is a child table to the Course table. The cascading updating and deleting means when a record in the parent table is updated or deleted, all records in the child tables are also updated or deleted. An example of cascading updating and deleting is shown in Figure 7.20. The faculty member Ying Bai with a faculty_id=B78880 is selected for this updating and deleting example.

- 2) As shown in Figure 7.20, the faculty member with a faculty_id=B78880, which is a primary key in the Faculty table, a foreign key in the Login and the Course tables, are updated or deleted from the Faculty table, the related records in the child tables, Login and Course, with the same faculty_id will also be updated or deleted with the associated columns. Two columns, user_name and pass_word, located in the Login table and four associated columns, course_id, located in the Course table will also be updated or deleted.

- 3) An import issue is to recover these deleted records. You have to recover the records in the parent table (Faculty and Course tables), and then recover the records in the child tables. Following the table order in Figure 7.20 and refer to Sections 2.9.4.1-2.9.4.5 in Chapter 2, as well as Figures 7.21-7.24 to recover these records.

# 7.4.3 UPDATE DATA FOR THE COURSE TABLE IN THE SQL DATABASE

In this section, we discuss how to perform data updating for the **Course** table in our sample database via the Course window in our project **RtUpdateDeleteProject** built in the last section. Let's first discuss updating against the **Course** table for the SQL database. To update data against Course table, we do not need to add any new Forms and we will use the Course window as our interface. We need to perform the following steps to complete this data updating:

- 1) Develop codes to update the course record.
- 2) Validate the data updating result.

First us develop the codes for our data updating action.

## 7.4.3.1 Develop Codes to Update the Course Record

Regularly, the **course_id** should not be updated if a course record needs to be updated since a new course can be inserted into the database and an old course can be deleted if not needed. In this project, we update all pieces of information for a course record except its **course_id**. The input dynamic parameter to the updating query includes only one parameter, course_id.

Similarly to updating a record in the Faculty table, the main coding job to update a course record is developed inside the **Update** button's Click method. Now let's start the coding process to update a course record in our sample database.

Open the RTOUpdateDelete Project and the Course Form, double-click on the Update button to open its Click. Enter the codes shown in Figure 7.25 into this method. Let's have a look at this piece of code to see how it works.

- A. The query string is defined first at the beginning of this method. All data columns in the Table table, the course_id, are input parameters. The dynamic parameter @cid represents the original course_id, which is a primary key in the Table and will not be updated.
- B. All components and local variables are declared here such as the Command object and integer variable intUpdate. The latter is used to hold the returned status of the calling of the ExecuteNonQuery() method.
- C. The Command object is initialized and using the Connection object and the Parameter object.
- D. A user-defined method UpdateParameters whose codes are shown in H is called to adding all parameters into the Command's properties. The passing mode used for the argument is passing-by-reference, which means a valid starting address of that Command object is passed into the method, and any modification to this Command object is present and it can be returned to the calling method.
- E. The ExecuteNonQuery() method of the Command class is executed to update a course in the Table. The running result of this method is returned and stored in the local variable intUpdate.
- F. The Command object is released after this data updating action.
- G. The returned value of calling the ExecuteNonQuery() method is equal to the number of rows that have been updated in the Table. A zero means that no row has been updated, an error message is displayed to indicate it if this situation is really occured.
