## 5.14 INTRODUCTION TO RUNTIME OBJECTS

Runtime objects can be defined as: objects or instances used for data connections and operations in a data-driven application are created and implemented during the period of a project run; in other words, objects are created and utilized dynamically. To understand what kind of objects are most popularly used in a data-driven application, let's have a detailed discussion about the most useful classes provided by ADO.NET.

According to Chapter 3, the ADO.NET architecture can be divided into three components: Data Provider, DataSet and a DataTable. These three components are directly related to different classes, which are shown in Figure 5.68.
The Data Provider provides four components

- 1) Data Connection
- 2) Data Command
- 3) DataReader
- 4) TableAdapter (DataAdapter)

All components inside the Data Provider are Data Provider-dependent components, which means that all components, including the Connection, Command, TableAdapter (DataAdapter) and DataReader, are identified and named based on the real data provider, or the database. For example, the Data Provider used for SQL Server database must be identified and named by a prefix Sql, such as

- Data Connection component: SqlConnection
- Data Command component: SqlCommand
- DataAdapter (TableAdapter): SqlDataAdapter (SqlTable)
- DataReader components: SqlDataReader

and the same definition works for all other Data Providers. All classes, methods, properties and constants of these four types of Data Provider are located at four different namespaces: System.Data.OleDb, System.Data.SqlClient, System.Data.Odbc and System.Data.OracleClient.

As shown in Figure 5.68, four kinds of data objects are popularly used in database programming in Visual C#. One must create the connection object based on the real database by using the specific prefix.

However, two components in the ADO.NET are Data Provider-independent: DataSet and DataTable. These two components are located at System.Data. You do not need to use any prefix when you use these two components in your applications. Both DataSet and DataTable can be filled using the DataAdapter or the Adapter components.

ADO.NET provides different classes to allow users to develop data-driven applications using different methods. Among these, two popular methods will be discussed in this chapter in detail.

The first method is to use the so-called DataSetDataAdapter method to build a data-driven application. In a real application, DataSet and DataTable classes have different roles when they are embedded into a DataSet and each table can be filled, inserted, updated and deleted using the different query method provided by the DataAdapter as the SelectCommand, InsertCommand, UpdateCommand or DeleteCommand When shown in Figure 5.68, when you use this, the Command and Parameter objects are embedded or attached to the DataAdapter (represented by a shaded block) and the DataTable is embedded into the DataSet (represented by another shaded block). This method is relatively simple since you do not need to call some specific objects, such as the DataReader or ExecuteNonQuery to complete this data query. You just need to call the associated command of the Table to finish this operation. But this simplicity brings some limitations for your applications. For instance, you cannot access data tables separately to perform multiple specific operations using this single specified DataAdapter.

The second method is to use each object individually, which means that you do not have to use the DataAdapter or embed the DataTable into the DataSet. This provides more flexibility. In this method, no DataAdapter or DataSet is needed, and you can create a new Command object with a New connection, then build a query statement and attach some useful parameter to that query for the DataReader object, also you can perform any data manipulation by calling the ExecuteReader() method or any data manipulation by calling the ExecuteNonQuery() to modify the DataTable.

In addition to these two methods, the LINQ method which was introduced by Microsoft in Visual Studio 2008 is also discussed later in this Chapter.

In this section, we will provide four sample projects to cover these two popular methods and the LINQ method; RTSelect Project, SPSelect Project, LINQSelect, and LINQSPProject, which are associated with four kinds of query methods, Runtime object, Stored Procedures method, LINQ method and LINQ to SQL Server method.

To have a better understanding about the LINQ method, refer to Chapter 4. To better understand these two popular methods, we need to have a clear picture of how to develop a data-driven application using the related classes and methods by ADO.NET.

## 5.14.1 Procedure for Building a Data-Driven Application Using Runtime Objects

First we will concentrate on on traditional runtime object query methods, the LINQ and the stored procedures method, will be discussed later in this chapter.

Recall that we discussed the architecture and important classes of ADO.NET in Chapter 3. To connect and implement a database with a Visual C# project, we need to follow the following sequence listed:

- 1) Create a new Connection String with correct parameters.
- 2) Create a new Connection object using the suitable Connection String built in step 1.
- 3) Call the Open() method to open the database connection using a Try-Catch block.
- 4) Create a new TableAdapter (DataAdapter) object.
- 5) Create a new DataTable object that can be filled with data.

Basically, the similar runtime objects and structures are utilized to develop a data-driven project that can access the different database. For example, three kind of data provider have a need to use the Connection, Command, Adapter and DataReader objects to perform data queries to either a DataSet or DataTable. The DataSet and the DataTable components are provider-independent, but the first four objects are provider-dependent. This means that one must use the prefixes to specify which kind of data provider is utilized for certain databases. A prefix would be used if a SQL Server database is utilized, such as SqlConnection, SqlCommand, SqlDataAdapter and SqlDataReader.

Thus, the differences between the data-driven applications that can access the different database are the provider-dependent components. Among them, the Connection String is a big issue. Different data providers need to use different connection strings to make the correct connection to the associated database.
