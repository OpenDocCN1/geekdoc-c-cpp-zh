Error processing
Before exploring the features offered by Microsoft Windows, let's take a look at how they handle error handling.
When you call a Windows function, it checks the parameters passed to it and then tries to do its job. If you passed an invalid parameter, or if the operation cannot be performed for some other reason, it returns a value indicating an error. Table 1-1 shows the data types for the return values ​​of most Windows functions.

When an error occurs, you should figure out why the call to this function failed. Each error has its own code - a 32-bit number.
When a Windows function detects an error, it uses the thread's local memory mechanism to map the corresponding error code to the calling thread. (Thread local memory is discussed in Chapter 21) This allows threads to work independently of each other without interfering with other people's errors. When the function returns control to you, its return value will indicate that some kind of error has occurred. You can find out which one by calling the GetLastError function.
DWORD GetLastError ();
It simply returns a 32-bit error code for the given stream.
Now that you have an error code, you need to exchange it for something more readable. For a list of error codes defined by Microsoft, see the WinError.h header file. I'll give you a small part of it here to give you an idea of ​​what it looks like:

The Get Last Error function must be called immediately after a failed Windows function call, otherwise the error code may be lost (overwritten
error code of another function OR code ERROR_SUCCESS in case of successful completion of the function).
Some Windows functions always complete successfully, but for different reasons. For example, an attempt to create an “event” kernel object with a specific name might succeed either because you actually created it, or because such an object already exists. But sometimes you need to know the reason for success. Microsoft has chosen to use the last error code setting mechanism to return this information. So even if some functions are successful, you can call GetLast Error and get additional information. These functions include, for example, Create Event. For information on other functions and examples of returning ERROR_ALREADY_EXISTS when a named event exists, see the Platform SDK.
In my opinion, it is especially useful to track the code of the last error during the debugging process. By the way, the debugger in Microsoft Visual Studio allows you to customize the Watch window so that it always shows the code and description of the last error in the current thread. Visual Studio comes with a small utility Error Lookup, which allows you to get a description of an error by its code.
If an application detects an error, it usually notifies the user about it by displaying its description on the screen. In Windows, there is a special function for this that "converts" the error code into its description, - Format Message:
DWORD FormatMessage (DWORD dwFlags, LPCVOID pSource, DWORD dwMessageId, DWORD dwLanguageId, PTSTR pszBuffer, DWORD nSize,
va_list * Arguments);
Format Message - a very rich function in its capabilities, and it is desirable to use it in the formation of all lines shown to the user. The point is that it makes it easy to work with many languages. Format Message determines which language is selected in the system as the main one (this parameter is set via the Regional Settings applet in the Control Panel), and returns the text in the corresponding language. Of course, you must first translate the strings into the required languages ​​and embed this resource into your EXE or DLL module, then the function will automatically select the required language. The ErrorShow sample program at the end of this chapter demonstrates how to call this function to get a textual description of an error from its Microsoft-defined code.
From time to time, someone asks me if Microsoft will compile a complete list of error codes for every possible Windows feature. Answer: alas, no. I will say more, there will never be such a list - it is too difficult to compile and maintain it for more and more new versions of the system.
The problem with such a list is also that you call one API function, and it can call to another, that - to the third, etc. Any of these functions can fail (and for various reasons). Sometimes a higher-level function will itself deal with an error in one of the functions it calls and ultimately do what you want it to do. In general, to create such a list, Microsoft would have to trace the call chains in each function, which is very difficult. And with the advent of a new version of the system, these chains would have to be revised again.
You can do it too
So I showed you how Windows functions report errors. Microsoft allows you to use this mechanism in your own functions. Let's say you are writing a function that will be accessed by other programs. This function call may fail for whatever reason, and you also need to report errors. To this end, you simply set the code of the last error in the stream and return FALSE, INVALID_HANDLE_VALUE, NULL, or whatever is more appropriate in your case. To set the last error code on a stream, you call SetLastError
VOID Set Last Error (DWORD dwErrCode);
and pass it the required 32-bit number. I try to use the codes already defined in WinError.h, provided they match the errors that my functions might report. If you think that none of the codes in WinError.h are good enough for a possible error in your function, define your code. It is a 32-bit value, which is broken down into the fields shown in the following table.
I discuss these fields in more detail in Chapter 24. At the moment, the only field you care about is bit 29. Microsoft promises that all error codes generated by its functions will contain a 0 in this bit. If you define your own error code, write down here 1. Then you have the assurance that your error code will not conflict with the code defined by Microsoft - not now or in the future. Note that Facility code can take 4096 possible values, of which the first 256 are reserved by Microsoft for its own use, and the rest are available for use in applications.to all              those who wish.

The first line reads the error code from the text box. Next, I instantiate the memory block handle and initialize it to NULL. The FormatMessage function itself allocates the necessary block of memory and returns its descriptor to us.
When I call FormatMessage, I am passing the FORMAT_MESSAGEJFROM_ SYS-TEM flag. It tells the function that I want a string that matches the error code defined on the system. In addition, I pass the FORMAT_MESSAGE_ALLOCATE_BUFFER flag to instruct the function to allocate an appropriate block of memory to store the text. The handle to this block will be returned in the hlocal variable. The FORMAT_MESSAGE_IGNORE_INSERTS flag allows you to substitute wildcards in messages that are used by Windows to convey more detailed context information, as shown in the following figure:
Without this flag, it is necessary to pass the values ​​in the Arguments parameter instead of wildcards, but in the case of Error Show this is not possible, since the content of the messages is not known in advance.
The third parameter indicates the code of the error we are interested in, and the fourth is the language in which we want to see its description. Since we want to receive messages passed by Windows, the language identifier is created from a pair of defined constants, resulting in 0 - the value corresponding to the default language set in the operating system. This is an example of a situation in which it is impossible to "sew" a language identifier into the code, since it is impossible to know in advance which language is used in the copy of the operating system where the ErrorShow program will be launched.
If FormatMessage succeeds, the error description is placed in a block of memory, and I copy it into a scrollable window at the bottom of the program window. And if the call to FormatMessage
fails, I try to find the message code in the NetMsg.dll module to see if the error is network related (see Chapter 20 for finding a DLL on disk). Using the NetMsg.dll handle, I call FormatMessage again. The point is that each DLL or EXE module can have its own set of error codes, which are included in the module using the Message Compiler (MC.exe). This is exactly what the Error Lookup utility allows you to do through its Modules dialog box.
