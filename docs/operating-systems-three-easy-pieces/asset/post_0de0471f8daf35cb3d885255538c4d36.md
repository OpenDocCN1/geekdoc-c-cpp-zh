
## 43.8 What About Directories?

Thus far, we've simplified our discussion a bit by only considering indices and data blocks. However, to access a file in a file system (such as /home/remzi/foo, one of our favorite file names), some directories must be accessed too.

Fortunately, directory structure is basically identical to classic UNIX file systems, in that a directory is just a collection of (name, inode number) mappings. For example, when creating a file on disk, LFS must create a new inode, as well as the data block and its inode to refer to this file. Remember that LFS will do so sequentially on the disk (after buffering updates for some time). Thus, creating a file foo in a directory would lead to the following structures:

| b[0];A0 | (foo, k) | b[0];A2 | m[k];A1 |
| :--- | :--- | :--- | :--- |
| --- | --- | --- | --- |
| D_k | l[k] | D_dir | m[dir];A3 |
| A0 | A2 | A3 | imap |

The piece of inode map contains the information for the location of both the directory as well as the newly-created file. Thus, when accessing foo (with inode number k), you would first look in the inode map (usually cached in memory) to find the location of directory (A3); then you read the directory, which gives you the location of data (A2); reading this block gives you the name-to-inode mapping of (foo, k). You then consult the inode map again to find the location of inode (A1), and finally read data block at A0.

There is one other serious problem in LFS, the recursive update problem. The problem arises in any file system that never updates in place (such as LFS), but rather moves updates to new locations on the disk. Specifically, when its location on disk changes would have entailed an update to the directory that points to this file, which would have mandated a change to the parent of that directory, and so on, all up the file system tree. LFS avoids this with the inode map. Even though the location of inode may change, the change is never reflected in the directory itself; rather the map is updated while the directory holds the same name-to-inode mapping. Thus, through indirect, LFS avoids the recursive update problem. LOG-STRUCTURED FILE SYSTEMS.

## 43.9 A New Problem: Garbage Collection

You may have noticed another problem with LFS: it repeatedly writes the latest version of a file (including its inode and data) to new locations on disk. This process, while efficient, implies that LFS leaves old versions of file structures scattered throughout the disk. We naturally call these old versions garbage.

For example, let's imagine the case where we have an existing file referred to by inode $k$, which points to a single data block $D_0$. We now update that block, generating both a new inode and a new data block. The current and live (by the simple act of (logically) updating a data block, a number of new structures must be persisted by LFS, leaving old versions of said blocks on the disk.

As another example, imagine we append a block to original k. In this case, a new version of the inode is generated, the old data block is still pointed to by the inode. Thus, it is still live and part of the current file system:

![](img/133d518e3f69f4ead32c569ae6c49618_1.png)

So what should we do with these older versions of inodes, data blocks, and forth? Could we keep those old versions around and allow users to restore old file versions (for example, if they accidentally overwrite or delete a file, it could be quite nice to do so); such a file system is known as a *versioning file system* because it keeps track of the different versions of a file.

However, LFS instead keeps only the latest live version of a file; thus (in the background), LFS must periodically free these old dead versions of file data, inodes, and other structures, *clean* them; cleaning should make blocks on disk free again for use in subsequent writes. Note that the process of cleaning is a form of garbage collection, a technique that arises in programming languages that automatically free unused memory for programs.

Earlier we discussed segments as important as they are the mechanism that enables large writes to disk in LFS. As it turns out, they are also quite integral to effective cleaning. Imagine what would happen if the LFS cleaner simply went through and single data blocks, nodes, etc., during cleaning. The result: a file system with number of holes between old segments. Performance would drop considerably, as LFS would not be able to find a contiguous region to write sequentially and with high performance.

Instead, the LFS cleans on a segment-segment basis, thus clearing up chunks of space for subsequent writing. The basic process works as follows: Periodically, the LFS reads a number of old (partially-filled) segments, determines which blocks are live within these segments, and writes a new set of segments with the live blocks within them, freeing the old ones for writing. Specifically, we expect the cleaner to read into M existing segments, pack their content into N segments (where N < M), and then write the N segments to disk in new locations. The old M segments are freed and can be used by the file system for subsequent writes.

## 43.10 Determining Liveness

We are now left with two problems, however. The first is mechanism: how can LFS tell which blocks within a segment are live? The second is policy: often should the cleaner run?

We address the mechanism first. Given a data block S, LFS must be able to determine whether D is live. Specifically, LFS adds a little information to each segment which describes where it belongs to. To do so, LFS includes the version number in the segment summary. Finally, using the offset T, and if it points to disk address A, LFS can conclude that D is live. If it points anywhere else, it can conclude this version is no longer needed. Here is a pseudocode summary:

```
(N, T) = Segment Summary[A];
inode = Read(imap[N]);
if (inode[T] == A)
  // block is alive
else
  // block is garbage
```

## 43.11 A Policy Question: Which Blocks To Clean, And When?

On top of the mechanism described above, LFS must include a set of policies to determine both when to clean and which blocks are worth cleaning. Determining when to clean is easier; either periodically, during idle time, or when you have the disk full. Determining which blocks to clean is more challenging, and has been the subject of many research papers. In the original LFS paper [RO91], the authors describe an approach which segregates *hot* and *cold* segments. A hot segment is one in which the contents are frequently over-written; thus, for a segment, the best policy is to wait a long time before cleaning, as more (in new segments) and more blocks are getting over-written may have a few dead blocks but the rest of its contents are relatively stable. Thus, the authors conclude that one should clean cold segments sooner and hot segments later, and develop a heuristic that does exactly that. However, as most policies, this policy isn't perfect; later approaches show how to do better [MR+97].
