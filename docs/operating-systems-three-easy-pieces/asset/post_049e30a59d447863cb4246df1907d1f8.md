> TIP: IT COMPILED OR RAN ≠ IT IS CORRECT
Just because a program compiled(!) or even ran once or many times correctly does not mean the program is correct. Many events may have you to a point where you believe it works, but then changes and it stops. A common student reaction is to say (or yell) "But it worked before!" and blame the compiler, operating system, hardware, or even (dare we say it) The problem is usually all right where you think it would be, in your code. To work and debug it you blame those other components.

When you run this code, it will likely lead to a segmentation fault, which is a fancy term for YOU DID SOMETHING WRONG WITH MEMORY PROGRAMMER AND I AM ANGRY. In this case, the proper code might look like this:

```c
char *src = "hello";
char *dst = (char *) malloc(strlen(src) + 1);
strcpy(dst, src); // work properly
```

Alternately, you could use strdup() and make your life even easier. Read the strdup man page for more information.

# Not Allocating Enough Memory

A related error is not allocating memory, sometimes called a buffer overflow. In the example above, a common error is to make almost enough room for the destination buffer.

```c
char *src = "hello";
char *dst = (char *) malloc(strlen(src)); // too small!
strcpy(dst, src); // work properly
```

Oddly, depending on how memory is implemented and many other details, this program will run seemingly correctly. In some cases, when the string copy executes, it writes one byte too far the end of the allocated space, but in some cases this is harmless, perhaps overwriting a variable that isn't used. In some cases, these overflows can be incredibly harmful, and in fact they are the source of many security vulnerabilities. If the memory library allocated a little extra space anywhere, and thus your program actually doesn't scribble on other variable's value and works quite fine. In even other cases, the program will indeed fail and crash. And thus we learn another valuable lesson: even though it ran once, doesn't mean it's correct.

Although it sounds alike, you will soon learn why such an illegal memory access is called a segmentation fault; if that isn't incentivize to read on, what is?

# Forgetting to Initialize Allocated Memory

With this error, you call malloc() properly, but forget to fill in some values into your newly-allocated data type. Don't do this! If you do forget, your program will eventually encounter an uninitialized read, where it reads from the heap data of unknown value. Who knows what might be in there? If you're lucky, some value that the program still works (e.g., zero). If you're not lucky, something random and harmful.

# Forgetting To Free Memory

Another common error is known as a memory leak, and it occurs when you forget to free memory. In long-running applications or systems (such as the OS itself), this is a huge problem, as slowly leaking leads one to run out of memory, after which a restart is required. Thus, in general, when you are done with a chunk of memory, you should make sure to free it. Note that using a garbage-collected language doesn't help here if you still have a reference to some chunk of memory, no garbage collector will ever free it, and memory leaks remain a problem even in more modern languages.

In some cases, it may seem like not calling free() is reasonable. For example, your program is short-lived, and will soon exit; in this case, when the process dies, the OS will clean up all of its allocated pages and no memory leak will take place per se. While this "works" (see the aside on page 145), it is probably a bad habit to develop, so be wary of choosing such a strategy. One of your goals as a programmer is to develop good habits; one of habits is understanding how you are managing memory, and (in languages like C) the blocks you have allocated. Even if you can get away with not doing so, it is probably good to get in the habit of freeing each and every byte you explicitly allocate.

# Freeing Memory Before You Are Done With

Sometimes a program will free memory before it is finished using; such a mistake is called a dangling pointer, and, as you know, is a bad thing. The subsequent use can crash the program, or overwrite memory (e.g., you called free(), but then called malloc() again to allocate something else, which recycles the already-free memory).

# Freeing Memory Repeatedly

Programs also sometimes free memory more than once; this is known as the double free. The result of doing so is quite undefined. As you can imagine, the memory-allocation library might get confused and all sorts of weird things; crashes are a common outcome.

> ASIDE: Why NO Memory Is Leaked ONCE Your PROCESS EXITS

When you write a short-lived program, you might allocate some space using malloc(). The program runs and is about to complete: is there need to call free() a bunch of times before exiting? While it seems wrong not to do it, no memory will be "lost" in any real sense. The reason is simple: there are two levels of memory management in the system.
The first level of memory management is performed by the OS, which hands memory to processes when they run, and takes it back when processes exit (or otherwise die). The second level of management is within each process, for example the heap when you call malloc() and free(). Even if you fail to call free() (and thus leak memory in the heap), the operating system will reclaim all the memory of heap (including those pages for code, stack, and, as relevant, heap) when the process is finished. No matter what the state of your heap is in address space, the OS takes back all of those pages when the process dies, ensuring that no memory is lost despite the fact you didn't!

Thus, for short-lived programs, leaking memory often does not cause any operational problems (though it may be considered poor form). When you write a long-running server (such as a web server or database management system, which never exits), leaked memory is a much bigger issue, and will eventually lead to a crash when the application runs out of memory. And of course, leaking memory is an even larger issue inside one particular program: the operating system itself. Showing us out those: whose the kernel code has the toughest job of all...

# Calling free() Incorrectly

One last problem is the call of free() incorrectly. After all, free() expects you to pass to it one of the pointers you received from malloc() earlier. When you pass in some other value, bad things can (and do) happen. Thus, invalid frees are dangerous and of course should be avoided.

# Summary

As you can see, there are lots of ways to abuse memory. Because of frequent errors with memory, a whole ecosystem of tools have developed to help find problems in your code. Check both purport [HJ92] and valgrind [SN05]; both are excellent at helping you locate the source of your memory-related problems. Once you become accustomed to using these powerful tools, you will wonder how you survived without them.

# 14.5 Underlying OS Support

You might have noticed that we haven't been talking about system calls when discussing malloc() and free(). The reason for this is simple: they are not system calls, but library calls. Thus the library manages space within your virtual address space, but itself is built on top of system calls which call into the OS to ask for more memory or release back to the system.

Finally, the current system call brk, is used to change the location of the end of the heap. It takes one argument (the address of the new break) and thus increases or decreases the size of the heap based on whether the new break is larger or smaller. An additional call sbrk is passed with an increment but otherwise serves a similar purpose.

Note that you should never directly brk or sbrk. They are used by the memory-allocation library; if you try to use them, you will likely make something (horribly) wrong. Stick to malloc() and free instead.

Finally, you can also obtain memory from the operating system with the mmap() call. By passing the correct arguments, mmap() can create an anonymous memory region within your program — a region which is not associated with any particular file but with swap space, something we will discuss in detail later on virtual memory. This memory can then be treated as a heap and managed as such. Read the manual page of mmap() for details.

# 14.6 Other Calls

There are a few other calls that the memory-allocation library supports. For example, calloc() allocates memory and also zeroes it before returning; this prevents errors where you assume memory is zeroed and forget to initialize it (see the paragraph on "uninitialized reads") The routine realloc() can also be useful, if you've allocated space for something (say, an array), and then need to add something to it: realloc() makes a new region of memory, copies the old region into it, and returns the pointer to the new region.

# 14.7 Summary

We have introduced some of the APIs dealing with memory allocation. As we have just covered the basics; more details are available elsewhere. Read the C book [KR88] and Stevens [SR05] (Chapter 7) for more information. For a cool modern paper on how to detect and correct many of these problems automatically, see Novark et al.
