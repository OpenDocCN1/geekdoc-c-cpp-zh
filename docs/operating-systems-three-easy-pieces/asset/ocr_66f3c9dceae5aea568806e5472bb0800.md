When written to disk, the data block and inode would look like this (note that the inode is as big as the data block, which generally isn't the case; in most systems, data blocks are 4 KB in size, whereas an inode is smaller, under 128 bytes):

This basic idea, of writing all updates (such as data blocks, inodes, etc.) to the disk sequentially, sits at the heart of LPS. If you understand this, you get the basic idea. But as all complicated systems, the devil is in the details.

#  4.2 Writing Sequentially And Effectively

Unfortunately, writing to disk sequentially is not (alone) enough to guarantee efficient writes. For example, if we write a single block to address A at T. We then wait a little, and write to the disk at A + δ (the next block in sequential order), but at time T + δ. In between the first and second writes, unfortunately, the disk has rotated; when you issue the second write, it will wait for most of a rotation before being committed (specifically, if the rotation takes T_rotation - δ before it can commit the second write to the disk surface). And thus you can hopefully see that simply writing to disk in sequential order is not enough to achieve peak performance; rather, you must issue a large number of contiguous writes (or one large write) to the drive in order to achieve good performance.

To achieve this, DFS uses an ancient technique known as buffering. Before writing to the disk, DFS keeps track of updates in memory; when it has received a sufficient number of updates, it writes them all at once, thus ensuring efficient use of the disk.
