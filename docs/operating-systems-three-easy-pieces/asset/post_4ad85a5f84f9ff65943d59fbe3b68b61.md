## Multiprocessor Scheduling (Advanced)

This chapter will introduce the basics of **multiprocessor scheduling**. As this topic is relatively advanced

After years of existence only in the high-end of the computing spectrum, **multiprocessor** systems are increasingly commonplace, and have found their way into desktop machines, laptops, and even mobile devices. The rise of the **multicore** processor, in which multiple CPU cores are packed into a single chip, is the source of this proliferation; these computer architects have had a difficult time making a single CPU faster without using (way) too much power. And we now have a few CPUs available to use, which is a good thing, right?

Of course, there are many difficulties that arise with the arrival of more than a CPU. A primary one is that a typical application (i.e., some C program you wrote) uses only a single CPU; adding more CPUs does not make that application run faster. To remedy this problem, you'll have to rewrite your application to run in **parallel**, perhaps using **threads** (as discussed in great detail in the second piece of this book). Multi-threaded applications can spread across multiple CPUs and thus run faster when given more CPU resources.

### 10.1 Background: Multiprocessor Architecture

To understand the new issues surrounding multiprocessor scheduling, we have to understand a new and fundamental difference between single-CPU hardware and multi-CPU hardware. This difference centers around the use of hardware **caches** (e.g., Figure 10.1), and exactly how data is shared across multiple processors. We now discuss this issue further, at a high level. Details are available elsewhere [CS99], in particular in an upper-level or perhaps computer architecture courses.

In a system with a single CPU, there are a hierarchy of **hardware caches** that in general help the processor run programs. Caches are small, fast memories that (in general) hold copies of *popular* data that is found in the main memory of the system. Main memory, in contrast, holds *all* of the data, but access to this larger memory is slower. By frequently accessed data in a cache, the system can make the large, slow memory appear to be a fast one.

### 10.2 Don't Forget Synchronization

Given that the caches do all of this to provide coherence, programs (or the OS itself) have to worry about anything when they access shared data? The answer, unfortunately, is yes, and is documented in detail in the second piece of this book on the topic of concurrency. While we won't get into the details here, we'll sketch/review of the basic ideas you're familiar with (assuming you with concurrency).

When accessing (and in particular, updating) data items or structures across CPUs, mutual exclusion primitives (such as locks) should likely be used to guarantee correctness (other approaches, like building lock-free data structures, are complex and only used on; see the chapter on details for details). For example, assume we have a shared queue being accessed on multiple CPUs. Without locks, concurrently adding or removing elements from the queue will not work as expected, even with the underlying coherence protocols; one needs locks to atomically update the data structure to its state.
