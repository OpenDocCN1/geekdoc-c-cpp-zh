
# FILE SYSTEM IMPLEMENTATION

> ASIDE: DATA STRUCTURE — THE INODE

The inode is the generic name used in many file systems to describe the structure that holds the metadata for a given file, such as its length, permissions, and location of its constituent parts. The name goes back at least as far as UNIX (and probably further back to Multics if not earlier systems); it is for index node, as the inode is used to index into an on-disk index to find the file of that number. We'll see, design of the inode is one key part of file system design. Most modern systems have some kind of structure that links it to every file they track, but perhaps call different things (such as nodes, inodes, etc.).

Each inode is implicitly referred to by a number (the i-number), which we either call the low-level name of. In vfs and other file systems, given an i-number, you can directly be calculate where the corresponding inode is located. For example, the inode table of vfs is as follows: 20-KB in size (4-KB blocks) and consisting of 80 inodes (assuming each inode is 256 bytes); further assume that the inode range starts at 2KB (the superblock starts at 0KB, the inode bitmap is at address 4KB, the data bitmap at 8KB, and thus the inode comes from address). To read inode number 32, the file system would first calculate the offset into the inode range (32 - sizeof(inode) or 8192), and add it to the start address of the inode disk (inodeStartAddr = 12KB), and thus arrive upon the correct address of the desired inode. Recall that disks are not byte addressable, but rather consist of a large number of addressable sectors, usually 512 bytes. Thus, to fetch the block that contains inode 32, the file system would issue a read to sector 51, or 40, to fetch the desired inode. Generally, the sector of the inode block can be calculated as follows:

```
blk = (inumber(inode_t)) / blockSize;
sector = ((blk * blockSize) + inodeStartAddr) / sectorSize;
```

Inside each inode is virtually all the information you need about a file: its type (e.g., regular file, directory, etc.), its size, etc.), and the number of blocks allocated to it, by protection information (such as owners), who is the can access it, *some* time, including when the file was created, modified, or last accessed, as well as information about where its data blocks reside on disk (e.g., pointers of some kind). One of the most important decisions in file allocation is to support larger files. To do so, add another pointer to the inode: the **double indirect pointer**. This pointer refers to a block that contains pointers each of contains to data blocks. As summing a block size of 4 KB, this structure can accommodate a file of over 4 GB in size (i.e., $12 + 1024 + 1024^2 \times 4$ KB). You may want even more, and we bet you know where this is headed: the **triple indirect pointer**.

Overall, this imbalanced tree is referred to as the **multi-level index approach** pointing to files. Let's examine an example with twelve direct pointers, as well as a single and double indirect block.

Many file systems use a level-index approach, including commonly-used file systems like Linux ext2 [9] and ext3, NetApp's WAAF, as well as the original Unix file system. Other file systems, including SGI XPS and Linux ext4, use extents instead of simple pointers; the earlier aside on how extent-based schemes work (which are akin to segments in the discussion of virtual memory).

You might be wondering: why use an imbalanced tree? Why not a different approach? Well, as it turns out, many researchers have studied file systems and how they are used, and virtually every time they find "truths" that hold across the decades. One finding is that *most files are small*. This imbalanced design reflects such reality; if most files are indeed small, it makes sense to optimize for this case.

# CONSIDER EXTENT-BASED APPROACHES

In comparing the two approaches, pointer-based approaches are the most flexible but use a large amount of metadata per file. Extent-based approaches are less flexible but more compact; particular, they work well when there is enough free space on the disk.
