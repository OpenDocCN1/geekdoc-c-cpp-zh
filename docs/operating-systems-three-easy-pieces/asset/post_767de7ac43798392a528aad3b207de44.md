We briefly highlight the important components of the protocol. First, the LOOKUP message is used to obtain a file handle, which is then subsequently used to access file data. The client passes a directory handle and name of a file to look up, and the handle to that file (directory) its attributes are passed back to the client from the server.

For example, the client already has a file handle for the root directory of a file system (/) (indeed, this would be obtained through the NFS mount protocol, which is how clients and servers first connected together; we do not discuss the mount protocol here for sake of brevity). If an application runs on the client file /foo.txt, the client-side file system sends a request to the server, passing it the root file handle and the name foo.txt; if successful, the file handle (and attributes) will be returned.

If you are wondering, attributes are just metadata that the file system tracks about each file, including fields such as file creation, last modification time, ownership and permissions information, and so forth, the same type of information that you would get back if you called stat() on a file.

Once a file handle is available, the client can use READ and WRITE protocol messages on a file to read or write file, respectively. The READ protocol message requires passing the file handle along with the offset within the file and number of bytes to read. The server then will be able to read the (after all, the handle tells the server which volume and which inode to read from, and the offset and count tells it which bytes of the file to read) and return the data to the client (or an error if there was a failure). WRITE is handled similarly, except the data is passed from the client to the server, and just a success code is returned.

One lasting protocol message is the GETATTR; given a file handle, it simply fetches the attributes for that file, including the last modified time of the file. We will see how this protocol request is important in NFSv2 below when we discuss caching (can you guess?).

## 49.6 From Protocol To Distributed File System

Hopefully we are now getting some sense of how this protocol is turned into a file system across the client-side file and the file server. The client-side file system tracks open files, and generally translates application requests into the relevant set of protocol messages. The server responds to protocol messages, each of which contains all information needed to complete request.

For example, let us consider a simple application which reads a file. In the diagram (Figure 4.5), we show what system calls the application makes, and how the client-side file system and server do in respond to calls.

A few comments about the first. First, notice how the client tracks all relevant state for the file access, including the mapping of the integer file descriptor to an NFS file handle as well as the current file pointer. You have noticed the client does not have to consider the offset to read from (explicitly) which to a properly-formatted read message which tells the server exactly which bytes from the file to read. Upon a successful read, the client updates the current file position; subsequent reads are issued with the same file handle but a different offset.

Second, you may notice where server interactions occur. When the file is open for the first time, the client-side file system sends a LOOKUP request message. Indeed, if a long pathname must be traversed (e.g., /home/remzi/foo.txt, the client would need up three LOOKUPS: one to look up home in the directory /, to look up remzi in home, and finally to look up foo.txt in remzi.

Third, you may notice how each server request has all the information needed to complete the request in its entirety. This design point is critical to be able to gracefully recover the request from server failure, as we will discuss ore detail; it ensures that the server does not need state to be able to respond to the request.

TIP: IDEMPOTENCY IS POWERFUL Idempotency is a useful property when building systems. When an operation can be issued more than once, it is much easier to handle failure of the operation; If an operation is not idempotent, life becomes more difficult.

## 49.7 Handler Failure With Idempotent Operations

When a client sends a message to the server, it sometimes not receive a reply. There are many possible reasons for this failure to respond. In some cases, the message may be dropped by the network; networks do lose messages, and thus either the request or the reply could be lost and the client never receive. It is also possible that the server has crashed, and is currently responding to messages. After a bit, the server will be rebooted and start running, but in the meantime all requests have been lost. In all these cases, clients are left with a question: what should they do when the server does not reply in a timely manner?

In NFS2, a client handles all of these failures in a single, and elegant way: it simply retries the request. Specifically, after sending the request, the client sets a timer to go off after a specified period. If a reply is received before the timer goes off, the timer is canceled and all is well. If the client assumes the request has not been processed and resends it. If the server replies, all is well and the client has neatly handled the problem.
