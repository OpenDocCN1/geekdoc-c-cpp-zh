# Homework (Measurement)

> ASIDE: MEASUREMENT HOMEWORKS

Measurement homeworks are small exercises where you write code to run on a real machine, in order to measure some aspect of OS or hardware performance. The idea behind homeworks is to give you a little bit of hands-on experience with a real operating system.

In this homework, you'll measure the costs of a system call and context switch. Measuring the cost of a system call is relatively easy. For example, you could repeatedly call a system call (e.g., performing a 0-byte read), and time how long it takes; dividing the time by the number of iterations gives you the cost of such a call.

One thing you'll have to take into account is the precision and accuracy of your timer. A typical timer that you use is `gettimeofday()`; read the man page for details. What you see there that `gettimeofday()` returns the time in microseconds since 1970; however, this does not mean that the timer is precise to the microsecond. Measure-back-to-back calls to `gettimeofday()` will tell you about how many iterations of your null-system call are still; you'll have to run in order to get a good measurement. If `gettimeofday()` is not enough for you you might look into the `rdso` instruction available on x86 machines.

Measuring the cost of a context switch is little tricky. The Imbench benchmark does by running two processes on a single CPU, and setting up two UNIX pipes between them a pipe is just one of many ways processes in a UNIX system can communicate with one another. The first process tries to write to a pipe, and waits for a read on the second; upon seeing the first process waiting for something to read from the second pipe, the OS puts the first process in the blocked state, and switches to the other process, which reads from the first pipe and waits for the second. When the second process tries to read from the first pipe again, it blocks, and then the back-and-forth cycle of communication continues. Imbench can make a good estimate of a context switch. You can try to recreate something similar here using pipes, or some other communication mechanism such as UNIX sockets.

One difficulty in measuring context-switch cost arises in systems with more than one CPU; how to ensure that your context-switch processes are located on the same processor. Unfortunately, most operating systems have calls to bind a process to a particular processor; on Linux, for example, the `sched_setaffinity()` call is what you're looking for. By ensuring both processes are on the same processor, you are making sure to measure the cost of OS stopping one process and restoring another on the same CPU.
