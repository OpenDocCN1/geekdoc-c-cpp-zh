## Event-based Concurrency (Advanced)

Thus far, we've written about concurrency as if the only way to build concurrent applications is to use threads. Like many things in life, this is not completely true. Specifically, a different style of concurrent programming is used in both GUI-based applications [O96] as well as some types of internet servers [PD99]. This style, known as event-based concurrency, has become popular in modern systems, including server-side frameworks as node.js [Ni13], but its roots are found in C/Unix systems that we will discuss below.

The problem that event-based concurrency addresses is two-fold. The first is that managing concurrency correctly in multi-threaded applications can be challenging; as we've discussed, missing locks, deadlock, and other nasty problems can arise. The second is that in a multi-threaded application, the developer has little or no control over what is scheduled at a given moment in time; rather, the programmer simply creates threads and hopes that the underlying OS schedules them in a reasonable manner across available CPUs. ### The CRUX: How To Build Concurrency Servers Without Threads

How can we build a concurrent server without using threads, and thus retain control over concurrency as well as avoid some of the problems that seem to plague multi-threaded applications?

## 33.1 The Basic Idea: An Event Loop

The basic approach we'll use, as stated above, is called event-based concurrency. The approach is quite simple: you simply wait for something (i.e., an "event") to occur; when it does, you check what type of event it is and do the small amount of work it requires (which may include I/O requests, or scheduling other events for future handling, etc.). That's it!

Before getting into the details, let's first examine what a canonical event-based server looks like. Such applications are based around a **event loop**. Pseudocode for an event loop looks like this:

```
while (1) {
  events = getEvents();
  for (e in events)
    processEvent(e);
}
```

It's really that simple. The main loop simply waits for something to do (by calling getEvents() in the code above) and then, for each event returned, processes one at a time; the code that processes each event is known as an **event handler**. Importantly, when a handler processes an event, it is the only activity taking place in the system; then, deciding which event handle next is equivalent to scheduling. This explicit control over scheduling is one of the fundamental advantages of the event-based approach.

But this discussion leaves us with a bigger question: how exactly does an event-based server determine which events are taking place, in particular regards to network and disk I/O? Specifically, how can an event server tell if a message has arrived for?

## 33.2 An Important API: select() (or poll())

With that basic loop in mind, we must next address the question of how to receive events. In most systems, a basic API is available via either the select() or poll() system calls.

What these interfaces enable a program to do is simple: check whether there is any incoming I/O that should be attended to. For example, imagine a network application (such as a web server) wishes to check whether any network packets have arrived, in order to serve them. These system calls let you exactly that.

Take select() for example. The manual page (on a Mac) describes the API in this manner:

```
int select(int nfds,
  fd_set *restrict readfds,
  fd_set *restrict writefds,
  fd_set *restrict errorfds,
  struct timeval *restrict timeout);
```

The actual description from the man page: select() examines the I/O descriptor sets whose addresses are passed in readfds, writefds, and errorfds to see some of their descriptors are ready for reading, or ready for writing, or have an exceptional condition pending, respectively. The first nfds descriptors are checked in each set, i.e., the descriptors from 0 through nfds-1 in the descriptor sets are examined. On return, select() replaces the given set with subsets of those descriptors that are ready for the operation. select() returns the number of ready descriptors in all the sets.

> ASIDE: BLOCKING VS. NON-BLOCKING INTERFACES
> Blocking (or synchronous) interfaces do all of their work before returning to the caller; non-blocking (or asynchronous) interfaces begin some work but return immediately, letting whatever needs to be done get in the background.
> The usual culprit in blocking is I/O of some kind. For example, if a call must read from disk to complete, it might block, waiting for the I/O request that has been sent to the disk to return.
> Non-blocking interfaces can be used in any type of programming (e.g., with threads), but are essential in the event-based approach, as a call that blocks will halt progress.

A couple of points about select(). First, note that it lets you whether descriptors can be read from as written to; the former lets a server determine that a new packet has arrived and is in processing, whereas the latter lets the server know when it is OK to reply (i.e., the outbound queue is not full).
Second, the timeout argument. One common usage here is to set the timeout to NULL select to block indefinitely, until some descriptor is ready. However, more robust servers will use some kind of timeout; one common technique is to set the timeout to zero, and then use the select() to return immediately.
