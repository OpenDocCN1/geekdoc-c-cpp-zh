# 5.4 Why? Motivating The API

Of course, one question you might have: why we would build such an interface to what should be the act of creating a new process? Well, as it turns out, the separation of fork() and exec() is essential in building a UNIX shell, which lets the shell run after the call to fork() but before the call to exec(); this code can alter the environment of the out-to-be-run program, and thus enables a variety of interesting features to be readily.

The shell is just a user program. It shows a prompt and then waits for you to type something into it. When you type a command (i.e. the name of an executable program, plus arguments) into it; in most cases, the shell figures out where in the file system it resides, calls fork() to create a new process to run the command, calls some variant of exec() to run the command, and waits for completion by calling wait(). When the child completes, the shell returns from wait() and prints a prompt, ready for your next command.

The separation of fork() and exec() allows the shell to do a whole bunch of things really easily. For example:

```
prompt> p3.c > newfile.txt
```

In the example above, the output of the program wc is redirected into the output file newfile.txt (the greater-sign is how said redirection is indicated). The way the shell accomplishes this task is quite simple: when the child is created, before calling exec(), the shell closes standard output and opens the file newfile.txt. By doing so, any output from the soon-to-running program wc are sent to the file instead of the screen.

Figure 5.4 (page 48) shows a program that does exactly this. The reason for this redirection is due to an assumption about how the operating systems manage file descriptors. Specifically, UNIX systems start looking for file descriptors at zero. In this case, STDOUT.FILENO will be the first available one and then get assigned when open() is called. Subsequent writes by the child process to the standard output file descriptor, for example by routines as print(), will then be routed transparently to the newly-opened file instead of the screen.

Here is the output of running the p4.c program:

```
prompt> /p4
prompt> cat p4.output
      32  109      846 p4.c
prompt>
```

You'll notice (at least two) tidbits about this output. First, when p4 is running, it looks as if nothing has happened; the shell just prints the command and is immediately ready for your next. However, that is not the case; the program p4 did indeed call fork() to create a new child, and then run the wc program via a call to execvp(). You don't see any output to the screen because it has been redirected to the file p4.output, you can see when we call the output file, all the output from running wc is found. Cool?

Pipes are implemented in a similar way, but with the pipe system. In this case, the output of one process is connected to an input pipe, and the input of another process is connected to that same pipe; thus, the output of one process seamlessly is used as input to the next, and long chains of commands can be strung together. As an example, considering how many times said word occurs; with a word in a file, and the utilities grep and wc, it is easy; just grep -o foo file | wc -1 into the command prompt and marvel at the result.

Finally, we have just sketched out the process API at a high level, there is a lot more detail about these calls out to be learned and digested; we'll learn more, for example, about file descriptors when we talk about file systems in the third part of the book. Now, suffice it to say that the fork()/exec() combination is a powerful way to create and manipulate processes.

```
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <string.h>
#include <fcntl.h>
#include <sys/wait.h>

int main(int argc, char *argv[]) {
    int rc = fork();
    if (rc < 0) {
        // fork failed
        fprintf(stderr, "fork failed\n");
        exit(1);
    } else if (rc == 0) {
        // child: redirect standard output to a file
        close(STDOUT_FILENO);
        open(".p4.output", O_CREAT|O_WRONLY|O_TRUNC, S_IRWXU);

        // now exec "wc"...
        char *myargs[3];
        myargs[0] = strdup("wc"); // program: wc (word count)
        myargs[1] = strdup("p4.c"); // arg: file to count
        myargs[2] = NULL; // mark end of array
        execvp(myargs[0], myargs);
    } else {
        // parent goes down this path (main)
        int rc_wait = wait(NULL);
        return 0;
    }
}
```

# 5.5 Process Control And Users

Of fork(), exec(), and wait(), there are many useful interfaces to control processes. The most common is kill(), which is used to send signals to a process. For example, SIGINT (interrupt), SIGSTOP (stop), and SIGCONT (continue) are common signals. A process can use the signal() call to "catch" various signals; doing so ensures that when a signal is delivered to a process, it will suspend its normal execution and run a particular piece of code in response.

This naturally raises the question: can we send a signal to a process, while using them at the same time; if one of these can arbitrarily send signals as SIGINT (to interrupt a process, likely terminating it), the usability and security of everything will be compromised. As a result, modern systems include a strong user. The user, after entering a password to establish credentials, login to gain access to system resources. The user may launch one or many processes, and exercise full control over them (pause them, kill them, etc.). Users generally can control their own processes; it is the job of the operating system to parcel out resources (such as CPU, memory, disk) to each user (and their processes) to meet overall system goals.
