# PAGING: SMALLER TABLES

> TIP: UNDERSTAND TIME-SPACE TRADE-OFFS
When building a data structure, one should always consider time-space trade-offs in its construction. Usually, if you wish to make access to a particular data structure faster, you will have to pay a space-usage penalty for the structure.

Contrast this to a simple (non-paged) linear page table*, which is an array of PTEs indexed by VPN; with such a structure, the entire page table must reside contiguously in physical memory. For a large page table (size 4MB), finding such a large chunk of unused physical memory can be a challenge. With a multi-level structure, we need a level of indirection through use of the page directory, which points to the page table; that indirection allows us to place page-page tables wherever we like in physical memory.

It should be noted that there is a cost to multi-level tables; on a TLB miss, two loads from memory will be required to get the right translation from the page table (one for the page directory, and one for the PTE itself), in contrast to one load with a linear page table. The multi-level table is a small example of a time-space trade-off. We wanted smaller tables (and got them), not for free; although in the common case (TLB hit), performance is identical, a TLB miss suffers from a higher cost with this smaller table.

Another obvious regret remains: whether it is the hardware or OS handling the page-table lookup (on a TLB miss), doing so is undoubtedly more involved than a simple linear page-table lookup. Often we are willing to increase complexity in order to improve performance or reduce overheads; in the case of a multi-level table, we make page-table lookups more complicated in order to save valuable memory.

# A Detailed Multi-Level Example

To understand the idea behind multi-page tables better, let's do an example. Imagine a small address space of size 16KB, 64-byte pages. Thus, we have a 14-bit virtual address space, with 8 bits for the VPN and 6 bits for the offset.
