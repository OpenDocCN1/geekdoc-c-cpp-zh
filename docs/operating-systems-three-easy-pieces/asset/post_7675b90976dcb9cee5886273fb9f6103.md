Here (30.5) is another poor implementation. In this example, we imagine that one does not need to hold a lock in order to signal and wait. What problem could occur here? Think about it!

The issue is a subtle race condition. Specifically, if the parent calls thr_join() and then checks the value of done, it will see that it is 0 and thus try to sleep. But just before it calls to go to sleep, it is interrupted, and the child runs. It changes the state variable done to 1, but no thread is waiting and no thread is woken. When the parent runs again, it sleeps forever, which is sad.

Hopefully, from this simple join example, you can see some of the basic requirements of using condition variables properly. To make sure you understand, we go through a more complicated example: the **producer/consumer** with double-buffer.

> TIP: ALWAYS HOLD THE LOCK WHILE SIGNALING Although it is strictly not necessary in all cases, it is clearly simplest and best to hold the lock while signaling when using condition variables. The example above shows a case where you **must hold the lock for correctness** however, there are some other cases where it is likely OK not to, but probably is something you should avoid. Thus, for simplicity, **hold the lock when calling signaling**.

The converse of this tip, i.e., hold the lock when calling wait, is not just a tip, but mandated by the semantics of wait, because wait always (a) assumes the lock is held when you call it, (b) releases lock when putting the caller to sleep, and (c) re-acquires the lock just before returning. Thus, the generalization of this tip is correct: **hold the lock when calling signal or wait**, and you will always be in good shape.

## 30.2 The Producer/Consumer (Bounded Buffer) Problem

The next synchronization problem we will in in this chapter is known as the producer/consumer problem, or sometimes as bounded buffer problem, which was first posed by Dijkstra [D72]. Indeed, this very producer/consumer problem led Dijkstra and his co-workers to invent the generalized semaphore (which can be used as either a lock or a condition variable) [D01]; we will learn more about semaphores later.

Imagine one or more producers. Producers generate data items and place them in a buffer; consumers grab them from the buffer and consume them in some way.

This arrangement occurs in many real systems. For example, in a multi-threaded web server, a producer puts HTTP requests into a work queue (i.e., the bounded buffer); consumer takes requests out of this queue and processes them.

A bounded buffer is also used when you pipe the output of one program into another, e.g., grep file.txt | wc -l. This example runs two processes concurrently; grep lines from file.txt while using the string foo in what they think is standard output; the UNIX shell redirects the output to what is called a UNIX pipe (created by the pipe system call). The other end of this pipe is connected to the standard input of the process wc, which simply counts the number of lines in it and prints the result.
