# Mechanism: Address Translation

In developing the virtualization of the CPU, we focused on a general mechanism known as limited direct execution (LDE). The idea behind LDE is simple: for the most part let the program run directly on the hardware; however, at certain points in time (such as when a process issues a system call, or a timer interrupt occurs), arrange so the OS gets involved and makes sure the "right" thing happens. Thus, the OS, with a little hardware support, tries its best to get out of the way of the running program to deliver efficient virtualization; however, by interposing at those critical points in time, the OS ensures that it maintains control.

In virtualizing memory, we will pursue a similar strategy for any operating system, attaining both efficiency and control while producing the desired virtualization. Efficiency dictates that we make use of hardware support, which at first will be quite rudimentary (e.g., just a few registers) but will grow to be complex (e.g., TLBs, page-table support, and so forth). Control implies that the OS ensures that no application is allowed to access any memory but its own; thus, to protect applications from one another and the OS from applications, we will need help from the hardware too. Finally, to provide flexibility, we'd like programs to be able to use their address spaces in whatever way they would like, making the system easier to program. And thus we arrive at the refined crux:

> THE CRUX: How to efficiently and flexibly virtualize memory
> How can we build an efficient virtualization of memory? How do we provide the flexibility needed by applications? How do we maintain control over which memory locations an application can access, and thus ensure that application accesses are properly restricted? How do we do all of this efficiently?

# Mechanism: Address Translation

The generic technique we will use, which you can consider an addition to our general approach of limited direct execution, is something is referred to as **hardware-based address translation**, or just *address translation* for short. With address translation, the hardware transforms each memory access (e.g., an instruction fetch, load, or store), changing the **virtual** address provided by the instruction to a **physical** address where the desired information is actually located. Thus, on every memory reference, an address translation is performed by the hardware to redirect application references to their actual locations in memory.

Of course, the hardware alone cannot virtualize memory, as it just provides the low-level mechanism for doing so efficiently. The OS must give at key points to set up the hardware that the correct translations take place; it must manage memory, keeping track of where locations are and which are in use, and judicially intervening to maintain control over how memory is used.

Once again the goal is to create a beautiful illusion that the program has its own memory, where its code and data reside. Behind that virtual reality lies the ugly truth: that many programs are actively sharing memory at the same time, and the CPU (or CPUs) switches between running one program and the next. Through virtualization, the OS (with the hardware's help) turns the ugly reality into a powerful and easy to use abstraction.

# 15.1 Assumptions

Our first attempts at virtualizing memory will be very simple, almost laughably so. Go ahead, all you want; pretty soon it will be the OS laughing at you when you try to understand the ins and outs of TLBs, multi-level page tables, and other wonders. Don't like the idea of the OS laughing at you? Well, you may be out of luck then; that's just how the OS works.

Specifically we will assume that the user's address space must be placed continuously in physical memory. We will also assume, for simplicity, that the size of the address space is not too big; specifically, that it is less than the size of physical memory. Finally, we will also assume that each address space is exactly the same size. Don't worry if these assumptions sound unrealistic; we will manage them as we go, achieving a realistic virtualization of memory.
