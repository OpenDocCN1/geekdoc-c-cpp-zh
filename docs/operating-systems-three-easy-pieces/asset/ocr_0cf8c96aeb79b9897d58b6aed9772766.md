When Thread 0 runs again, it will eventually call sem_post(), incrementing the value of the semaphore to zero, and wake the waiting thread (Thread 1), which will be able to acquire the lock for itself. When Thread 1 finishes, it will again increment the value of the semaphore, restoring it to 1.

In addition to thread actions, the figure shows the scheduler state of each thread: Run (the thread is running), Ready (i.e., runnable but not running), and Sleep (the thread is blocked). Note that when Thread 1 goes first it goes into the sleeping state when it tries to acquire the already-held lock; only when Thread 0 runs again can Thread 1 be awakened and run again.

If you want to work through your own example, try a scenario where multiple threads queue up wanting a lock. What would be the value of the semaphore be during such a trace?
Thus we are to use semaphores as locks. Because locks only have two states (held and not held), we call a semaphore used as a binary semaphore. Note that if you are using a semaphore only in this binary fashion, it could be implemented in a simpler manner than the Generalized semaphores we present here.
