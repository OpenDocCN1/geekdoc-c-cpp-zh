# 36.4 Lowering CPU Overhead With Interrupts

The invention that many engineers came years ago to improve this interaction is something we've seen already: the interrupt. Instead of polling the device repeatedly, the OS can issue a request, but the calling process to sleep, and context switch to another. When the device is finally finished with the operation, it will raise a hardware interrupt, causing the CPU to jump into the OS at a predetermined interrupt routine (ISR) or by some interrupt handler. The handler is just a piece of operating system code that will finish the request (for example, by reading data and perhaps an error code from the device) and wake the process waiting for the I/O, which can then proceed as desired.
Interrupts allow for overlap of computation and I/O, which is for improved utilization. This timeline shows the problem:

| CPU | 1 | 1 | 1 | 1 | p | p | p | p | 1 | 1 | 1 | 1 |
|---|---|---|---|---|---|---|---|---|---|---|---||}{
| Disk | | | | | | | | | 1 | 1 | 1 | 1 |

In the diagram, Process 1 runs on the CPU for some time (indicated by a repeated 1 on the CPU line), and issues an I/O request to disk read some data. Without interrupts, the system simply spins, polling the status of the device repeatedly until the I/O is complete (indicated by a p). The device requests and finally Process 1 can run again.
If we utilize interrupts and allow for overlap, the OS can do something else while waiting for the disk:

| CPU | 1 | 1 | 1 | 1 | 2 | 2 | 2 | 2 | 1 | 1 | 1 | 1 |
|---|---|---|---|---|---|---|---|---|---|---|---||}{
| Disk | | | | | | | | | 1 | 1 | 1 | 1 |

In this example, the OS runs Process 2 on the CPU while the disk services Process 1's request. When the request is finished, an interrupt occurs, and the OS wakes up Process 1 and runs it again. Both the CPU and the disk are properly utilized during the middle stretch.
Note that interrupts are not always the best solution. For example, imagine a device that performs its tasks very quickly: the first poll usually finds the device to be done with task. Using an interrupt in this case will actually slow down the system: switching to another process, handling the interrupt, and switching back to the issuing process is expensive.
