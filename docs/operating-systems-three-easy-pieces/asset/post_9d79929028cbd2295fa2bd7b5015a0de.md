
# ASIDE: EMULATING REFERENCE BITS

As it turns out, you don't need a hardware reference bit in order to get some notion of which pages are in use in a system. In the early 1980's, Babuoglu and Joy showed that protection bits on the VAX can be used to emulate reference bits [BJ81]. The basic idea: if you want to get some understanding of which pages are being used in a system, mark all of the pages as inaccessible; (keep around the information as to which pages are really accessible by the process, perhaps in the "reserved" OS field of the page table) if a process accesses it, it will generate a trap into the OS; the OS will then check if the page should be accessible, and if so, revert the page to its normal protections (e.g., read-only, or read-write). At the time of a replacement, the OS can check which pages remain inaccessible, and thus give an idea of which pages have not been used. The key to this "emulation" of reference bits is reducing overhead while still obtaining a good idea of page usage. The OS must not be too aggressive in marking pages inaccessible, or overhead would be too high. The OS also not be too passive in such marking, or all pages will end up referenced; the OS will again have no idea of which page to evict.

To address these two problems, the developers can use the segmented FIFO replacement [Rl81]. The idea is simple: each process has a maximum number of pages it can keep in memory, known as its resident set (RSS). Each of the pages is kept on a FIFO list; when a process exceeds the RSS, the "first-in" page is evicted. FIFO clearly does not need any support from the hardware, and is easy to implement.

Of course, pure FIFO does not perform particularly well, as saw earlier. To improve FIFO's performance, VMS introduced two second-chance lists where pages are placed before being evicted from memory, specifically a global clean free list and dirty page list. When a page P exceeds its RSS, it is removed from its per-process FIFO; if clean (not modified), it is placed on the end of the clean page list; if dirty (modified), it is placed on the end of the dirty page list. If another process Q seeks, it takes the first free page of the global list. If another page P faults on that page before it is reclaimed, small pages I/O during swapping could be highly inefficient, as disks better with large transfers. To make swapping I/O more efficient, VMS adds a number of optimizations, but most important is clustering. With clustering, VMS groups large batches of pages together and writes them to disk in one full swoop (thus making them clean). Clustering is used in most systems, as the freedom to place pages anywhere within swap space lets the OS perform fewer and bigger writes, and thus improve performance.

# Other Neat Tricks

VMS had two other tricks: demand zeroing and copy-on-write. We describe these lazy optimizations. One form in VMS (and most modern systems) is demand zeroing of pages. To understand this, let's consider the example of adding a page to your heap. In a naive implementation, the OS responds to a request to add a page to your heap by finding a page in physical memory, zeroing it, then mapping it into your address space; otherwise you'd be able to see what was on the page. With demand zeroing, the OS instead does little work when the page is added to your address space; it puts an entry in the page table that marks the page as inactive. If the process then reads or writes the page, it will trap into the OS. When handling the trap, the OS notices (usually through some bits marked in the "reserved" portion of the page table) that this is desired; at this point, the OS does the needed work of finding a physical page, zeroing it, and mapping it into the process. If the process never accesses the page, all work is avoided by virtue of demand zeroing.

Another cool optimization found in VMS (and virtually every modern OS) is copy-on-write (COW), which goes simple: the OS needs to copy a page from one address space to another, instead of copying it, it can map it into the target address space. If both read only the page, no further action is taken, and thus the OS has realized a fast copy without actually moving any data. If, however, one of the address spaces does indeed try to write to the page, it will trap into the OS. The OS will then (lazily) allocate a new page, fill it with the data, and map this new page into the address space of the faulty process. The process then continues and has its own private copy of the page.

COW is useful for number of reasons. Certainly any sort of shared library can be mapped on address spaces of many processes, saving valuable memory. In UNIX systems, COW is even more critical, due to the semantics of fork() and exec(). As you might recall, fork() creates an exact copy of the address space of the caller; with a large address space, making such a copy slow and data-intensive. Even worse, the address space is immediately overwritten by a subsequent call to exec(), which overlays the calling process's address space with that of the soon-to-be-exec program. Instead of performing a copy-on-write fork(), the OS avoids much of the needless copying and retains the correct semantics while improving performance.

# TIP: BE LAZY

Being lazy can be a virtue in both life as well as in operating systems. Laziness can put off work until later, which is beneficial an OS for a number of reasons. First, putting off work might reduce the latency of the current operation, thus improving responsiveness; for example, operating systems report that a file succeeds immediately, and only write to it later in the background. Second, and more importantly, laziness obliterates the need to do the work at all; for example, delaying the execution of a deleted process removes the need to do the work at all. Laziness is also good in life: for example, by putting off your OS project, you may find that the project specification was worked out by your fellow classmates; however, the class project is unlikely to get cancelled, so being too lazy may be problematic, leading to a late project, bad grade, and a sad professor. Don't make professors sad!
