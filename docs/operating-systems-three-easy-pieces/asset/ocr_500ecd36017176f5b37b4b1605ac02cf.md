TIP: USE A LEVEL OF INDIRECTION
People often say that the solution to all problems in Computer Science is simply a level of redirection. This is clearly not true; it is just the solution to most problems (yes, this is still too strong of a comment, but you get the point). You can certainly think of every virtualization we have studied, e.g., virtual memory, or the notion of a file, as simply a level of redirection. And cannot the inode map in LFS is a visualization of inode numbers. Hopefully you can see the great power of redirection in these examples, allowing us to freely move around (such as pages example, or inodes in LFS) without changing every reference to them. Of course, redirection can have a downside too: extra overhead. Next time you have a problem, solving it with redirection, but make sure to think about the overheads of doing so first. As Wheeler famously said, "All problems in computer science can be solved by any level of redirection, except for course of the problem of too many indirections."

The map, unfortunately, needs to be persistent (i.e., written to disk); so LFS can keep track of the locations across crashes, and thus operate as desired. But question: where should the inode reside on disk?

It could live on a fixed part of the disk, course. Unfortunately, as it gets updated frequently, this would then require updates to file structures to be followed by writes to the map, and hence performance would suffer (i.e., there would be more disk seeks, between each update and the fixed location of the map).
Instead, LFS places the inode map right to where it is writing all of the new information. Thus, when appending a data block to a file k, LFS actually writes the new data block, its inode, and a piece of the map all together onto the disk, as follows:

In this picture, the piece of the map array stored in the block marked imap tells LFS that the inode k is at disk address A1; this inode, in turn, tells LFS that its data block D is at address A0.
