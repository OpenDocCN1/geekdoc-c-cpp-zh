With journaling, we logically commit all of this information to the journal for each of our two file creations; because the files are in the same directory, and assuming they have inodes within the same block, if we're not careful, we'll end up writing these blocks over and over.

To remedy this problem, some file systems do not commit update to one disk at a time (e.g., Linux ext3); rather, one can buffer all updates into a global transaction. In our example when the two files are created, the file system marks the in-memory bitmap, inodes of the files, directory data, and directory inode as dirty, and adds them to the list of blocks that form the current transaction. When it is finally to write these blocks to disk (say, after a timeout of 5 seconds), this global transaction is committed containing all of the updates described above. Thus, by buffering updates, a file system can avoid excessive traffic in many cases.

# Making The Log Finite

We have arrived at a basic protocol for updating file-system-on-disk structures. The file system buffers updates in memory for some time; when it is finally time to write to disk, the file system first writes out the details of the transaction to the journal (a.k.a. write-ahead log); after the transaction, the file system checkpoints those blocks to their final locations on disk.

However, the log is of a finite size. If we keep adding transactions to it (as this figure), it will soon fail. What do you think happens then?

| Tx1 | Tx2 | Tx3 | Tx4 | Tx5 | ... |

Two problems arise when the log becomes full. The first is simpler, but less critical: the larger log, the longer recovery will take, as the recovery process must replay all the transactions within the log (in order) to recover. The second is an issue: when the log is full (or nearly full), no further transactions can be committed to the disk, making the file system "less than useful" (i.e., useless).

To address these problems, journaling file systems treat the log as a circular data structure, re-using it over and over; this is to do, if the journal is sometimes restarted, the file system must take action time after a checkpoint. Specifically, once a transaction has been checkpointed, the file system should free the space it was occupied within the journal, allowing the log space to be reused.
