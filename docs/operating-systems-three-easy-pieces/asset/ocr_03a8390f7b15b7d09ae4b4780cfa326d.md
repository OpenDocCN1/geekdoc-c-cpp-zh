# PAGING: INTRODUCTION

ASIDE: DATA STRUCTURE — THE PAGE TABLE
One of the most important data structures in the memory management subsystem of a modern OS is the **page table**. In general, a page table stores **virtual-to-physical address translations**, letting the system know where each page of an address space actually resides in physical memory. Each address space requires such translations, in general there is one page table process in the system. The exact structure of the page table is either determined by the hardware (older systems) or can be more flexibly managed by the OS (modern systems).

Because tables are so big, we don't keep any special on-chip hardware in the MMU to store the page table of the currently-running process. Instead, we store the page table for each process in **memory** somewhere. Let's assume for now that page tables live in physical memory that the OS manages; later we'll see that much of OS memory itself is virtual, and page tables can be stored in virtual memory (and swapped out), but that is too confusing right now, so we'll ignore it. # 18.3 What's Actually In The Page Table?

Let's talk a little about page table organization. The page table is just a data structure that uses to map virtual addresses (or, really virtual page numbers) to physical addresses (physical frame numbers). Thus, any data structure could work. The simplest form is called **linear table**, which is just an array. The OS *indexes* the array by the virtual page number (VPN), and looks up the page-table entry (PTE) in order to find the physical frame number (PFN). For now, we will assume this simple linear structure; in later chapters, we will make use of more advanced data structures to solve some problems with paging.

As the contents of each PTE, we have a number of different bits to understand at some level. A **valid** bit is common to indicate whether the particular translation is valid; for example when a program starts running, it will have code and heap at one end of its address space, and the other end will be marked **invalid**, and if the process tries to access such memory, it will generate a trap to the OS which will terminate the process. Thus, the valid bit is crucial for supporting a sparse address space; by simply marking all the unused pages in the address space invalid, we remove the need to allocate physical frames for those pages and save a great deal of memory.
