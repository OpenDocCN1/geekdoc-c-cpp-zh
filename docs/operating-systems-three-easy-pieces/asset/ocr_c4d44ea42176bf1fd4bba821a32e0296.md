# 39.7 Writing Immediately With fsync()

Most times when a program calls write(), it is just telling the file system: please write this data to persistent storage, at some point in the future. The file system, for several seconds, will buffer such writes in memory for some time (say 5 seconds, or 30); or at later point in time, the write(s) will actually be issued to the storage device. From the perspective of the calling application, writes seem to complete quickly, and only in rare cases (e.g., the machine crashes after the write() call before the write to disk) will be lost.

However, some applications require more than this ever guarantees. For example, in a database management system (DBMS), development of a crash recovery protocol requires the ability to force writes to disk from time to time.

To support these types of applications, most file systems provide additional control APIs. In the UNIX world, the interface provided to applications is fsync(int fd). When a process calls fsync() for a particular file descriptor, the file system responds by forcing dirty (i.e., not yet written) data to disk, for the file referred to by that descriptor. The fsync() routine returns once of these writes are complete.

Here is a example of how to use fsync(). The code below opens a file, writes a chunk of data to it, and then calls fsync() to ensure the writes are forced immediately to disk. The fsync() returns, the application can safely move on, knowing that the data has been persisted (if fsync() is correctly implemented, that is):

```
int fd = open("foo", O_CREAT|O_WRONLY|O_TRUNC,
    S_IRUSR|IWUSR);
assert(fd > -1);
int rc = write(fd, buffer, size);
assert(rc == size);
rc = fsync(fd);
assert(rc == 0);
```

Interestingly, this does not guarantee everything that you might expect; in fsync() the directory that contains the file foo. Adding this step ensures not only the file itself is on disk, but that file, if newly created, is also a part of the directory. Surprisingly, this type of detail is often overlooked, leading to many application-level bugs [P+13,P+14].
