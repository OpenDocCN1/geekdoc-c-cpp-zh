
# Beyond Physical Memory: Policies

In a virtual memory manager, life is easy when you have a lot of free memory. A page fault occurs, you find a free page on the free-page list, congratulations! You did it again. In such a case, this memory forces the OS to start paging to evict is encapsulated within the replacement policy of the OS; historically, it is an interesting set of policies worth knowing a little more about.

Unfortunately, things get a little more interesting when little memory is free. The memory pressure forces us to start out pages to make room for actively-used pages. Deciding which page (or pages) to evict is the replacement policy of the OS; historically, it was one of the most important decisions the early virtual memory systems made, as older systems had little physical memory. Minimally, it is a set of policies worth knowing a little more about. And thus our problem:

> The Crux: How to Decide Which Page to Evict
> How the OS decide which page (or pages) to evict from memory? This decision is made by the replacement policy of the system, which usually follows some general principles (discussed below) but also includes certain tweaks to avoid corner-case behaviors.

## 22.1 Cache Management

Before diving into policies, we describe the problem we are trying to solve in more detail. Given that main memory holds some subset of all the pages in the system, it can rightly be viewed as a cache for virtual memory pages in the system. Our goal in picking a replacement policy for this cache is to minimize the number of cache misses, i.e., to minimize the number of times that we have to fetch a page from disk. The number of cache hits let us calculate the average memory access time (AMAT) for a program (metric computer architects compute for hardware caches [HP06]). Specifically, given these values, we can compute the AMAT of a program as:

```
AMAT = T_M + (P_{Miss} \cdot T_D)
```

where $T_M$ represents the cost of accessing memory, $T_D$ the cost of accessing disk, and $P_{Miss}$ the probability of not finding the data in the cache (a miss); $P_{Miss}$ varies from 0.0 to 1.0, and we refer to a percent miss rate instead of a probability (e.g., a 10% miss rate means $P_{Miss} = 0.10$). Note you pay the cost of accessing memory; when you miss, however, you must additionally pay the cost of fetching from disk.

For example, let us imagine a machine with a (tiny) address space: 4KB, with 256-byte pages. Thus, a virtual address has two components: a 4-bit VPN (the most-significant bits) and an 8-bit offset (the least-significant bits). Thus, in this process the acquire generates memory references ($2^4$ or 16 total virtual pages. i.e., virtual addresses: 0x000, 0x100, 0x200, 0x400, 0x500, 0x600, 0x700, 0x800). These virtual addresses refer to the first byte of each of the first pages of the address space (the page number being the first digit of virtual address).

Let us assume that every virtual page is in memory. Then, our acquire of memory references will encounter the following behavior: hit, hit, miss, hit, hit, hit, hit, hit. We compute the hit rate (the percent of references found in memory): 90%, as 9 out of 10 references are in memory. The miss rate is then 10% ($P_{Miss} = 0.1$). In general, the hit rate may sum to 100%.

To calculate AMAT, we need to know the cost of accessing memory and the cost of accessing disk. Assuming the cost of accessing memory ($T_M$) is around 100 nanoseconds, and the cost of accessing disk ($T_D$) is around 10 milliseconds, we have the following AMAT: $100ns + 0.1 \cdot 10ms$, which is $100ns + 1ms$, or 1 millisecond. If our hit rate had 99.9% ($P_{Miss} = 0.001$), the result is quite different: AMAT is 10.1 microseconds, or 100 times faster. As the hit rate approaches 100%, AMAT approaches 100 nanoseconds.

Unfortunately, as you can see in this example, the cost of disk access is so high in modern systems that even a tiny miss rate will quickly overwhelm the AMAT of running programs. Clearly, we need to avoid as many misses as possible or run slowly the disk. One way to help with this is to carefully design a smart policy, as we do now.

## 22.2 The Optimal Replacement Policy

To understand how a particular replacement policy works, it would be nice to compare it to the best possible replacement policy. As it turns out, an **optimal** policy was developed by Belady many years ago [B66] (which he called MIN). The optimal replacement policy leads to the fewest number of misses overall. Belady showed that a simple (but, unfortunately, difficult to implement!) approach that replaces the page that will be *furthest* in the future is the optimal policy, resulting in the fewest-possible cache misses.

**TIP: COMPARING AGAINST OPTIMAL IS USEFUL**
Although optimal is not very practical as a real policy, it is incredibly useful as a comparison point in simulation or other studies. Saying that your fancy algorithm has 80% hit rate isn't meaningful in isolation; saying that optimal achieves 82% hit rate (and thus your approach is quite close to optimal) makes the result more meaningful and gives it context. Then, in any study you perform, knowing what the optimal is lets you perform a better comparison, showing how much improvement is still possible, and when you can stop making your policy better because it is enough to match the ideal. Hopefully, the intuition behind the optimal policy makes sense. Think about it like this: if you have to throw out some page, why not throw out the one that is needed furthest from now? By doing so, you are essentially saying that all the other pages in the cache are more important than the furthest out. The reason for this is simple: you will refer to the other pages before you refer to the one furthest out.

Let's trace through a simple example to understand the decisions of the optimal policy. Assume a program accesses the following stream of virtual pages: 0, 1, 2, 0, 1, 3, 0, 1, 2. Figure 22.1 shows the behavior of optimal, assuming a cache that fits three pages. In the figure you can see the following actions. Surprisingly the first three accesses are misses as the cache begins in empty state; such a miss is referred to as a cold-start (or compulsory miss). We then refer again to pages 0 and 1, which both hit in the cache. Finally, we reach another miss (page 3), but this time the cache is full; a replacement must take place! The optimal policy examines the future for each page currently in the cache and sees that 0 is accessed almost immediately, and 2 is accessed furthest in the future. The optimal policy has no easy choice: evict page 2, resulting in

## 22.3 A Simple Policy: FIFO

### ASIDE: TYPES OF CACHE MISSES
In the computer architecture world, architects sometimes find it useful to characterize misses by type into one of three categories: compulsory, capacity and conflict misses, sometimes called the Three C's [H87]. A compulsory miss (or cold-start miss) occurs because the cache is empty to begin with this is the first reference to the item; in contrast, a capacity miss occurs because the cache ran out of space and had to evict one to bring a new item into the cache. The third type of miss (a conflict miss) occurs because of limits on where an item can be placed in a hardware cache due to something known as set-associativity; it does not arise in the OS page cache because such caches are always fully-associative, i.e., there are no restrictions on where a page can be placed. See H&P for details [HP06].

Many early systems avoid the complexity of trying to approach and employ simple replacement policies. For example, some used FIFO (first-in, first-out) replacement, where pages were simply placed in a queue when they enter the system; when a replacement occurs, the page on the tail of the queue (the “first-in” page) is evicted. FIFO has one great strength: it is simple to implement.
