When the original team at Sun implemented this solution to the stale-cache problem, they realized a new problem; suddenly, the NFS server was flooded with GETATTR requests. A good engineering principle to follow is design for the **common case**, and to make it work well; although the common case was a file accessed only from a single-client (perhaps repeatedly), the client always had to send GETATTR requests to make sure no one else changed the file. A client thus bumbers “has anyone changed this file?” when most of the time no one had.

To remedy this situation, **attribute cache** was added to each client. A client would still validate the cache before accessing it, but most would just look the cache to fetch the attributes. The attributes for a particular file were placed in the cache when the file was first accessed, and would timeout after a certain amount of time (say 3 seconds). During, those three seconds, all file accesses would determine that it was OK to use the cached file and do so with no network communication with the server.

# 49.10 Assessing NFS Cache Consistency

A few words about NFS cache consistency. The flush-on-close behavior was added to “make sense”, but introduced a certain performance problem. Specifically, if a temporary or short-lived file was created on the client and then deleted, it would still be forced to the server. A mere ideal implementation might keep short-lived files in memory until they are deleted and remove the server interaction entirely, perhaps increasing performance.

More importantly, the addition of an attribute cache into NFS made it very hard to understand or reason about exactly what version of a file one was getting. Sometimes you get the latest version; sometimes you would get an old version simply because your attribute cache hadn't yet timed out and the client was happy to give you what was in client memory. This was fine most of the time, and it (and still does!) occasionally led to odd behavior.

And we have described the oddity that NFS client caching. It serves as an interesting example where details of an implementation serve to define user-observable semantics, instead of the other round.
