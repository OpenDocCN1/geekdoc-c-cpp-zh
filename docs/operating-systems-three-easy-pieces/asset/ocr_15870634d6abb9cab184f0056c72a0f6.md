+   - Inode state: Each inode is checked for corruption or other problems. For example, fsck makes that each allocated inode has a valid type field (e.g., regular file, directory, symbolic link, etc.). There are problems with the inode fields that are not easily fixed; the inode bitmap is suspected and cleared by fsck; the bitmap is correspondingly updated.

+   - Inode links: fsck also verifies the link count of each inode. As you may recall, the link count indicates the number of different directories that contain a reference (i.e., a link) to this file. To verify the link count, fsck scans through the directory tree, starting at the root directory, and builds its own link count for every file and directory in the system. If there is a mismatch between the newly-calculated count and found within an inode, correct action is taken, by fixing the count within the inode. If an allocated inode is discovered to have no directory to it, it moves to the lost+found directory.

+   - Duplicates: fsck also checks for duplicate pointers, i.e., cases where two inodes refer to the same block. If one is outside, it may be cleared. Alternately, the pointed-to-block is copied, giving each inode its own copy as desired.

+   - Bad blocks: A check for bad block pointers is also performed while scanning the list of all pointers. A pointer is considered "bad" if it obviously points to something outside its range, e.g, if it has an address that refers to a block greater than the partition size. As you can see, running a working fsck requires intricate knowledge of the file system, making sure such a piece of code works correctly in all cases can be challenging [G-08]. However, fsck has perhaps more fundamental problem: they are too slow. With a large disk volume, scanning the entire disk to find all the allocated blocks and read the entire directory tree may take many minutes or hours. Performance of fsck, as disks grow in capacity and RAIDs grow in popularity, become prohibitive (despite recent advances [M-13]).

At a higher level, the basic premise of fsck seems just a tad irrational. Consider our example, where just three blocks are written to the disk; it is incredibly expensive to scan the entire disk to fix problems that occurred during an update of three blocks.
