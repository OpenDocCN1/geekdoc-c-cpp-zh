## ASIDE: UNIX SIGNALS

A huge and fascinating infrastructure known as signals is present in all modern UNIX variants. At its simplest, signals provide a way to communicate with a process. Specifically, a signal can be delivered to an application; doing so stops the application from whatever it is doing to run a signal handler, i.e., some code in the application to handle that signal. When finished, the process resumes its previous behavior.

Each signal has a name, as HUP (hang up), INT (interrupt), SEGV (segmentation violation), etc.; see the main page for details. Interestingly, sometimes it is the kernel itself doing the signaling. If your program encounters a segmentation violation, the OS sends a SIGSEGV (prepending SIG to name); to catch that signal, you can actually run some code in response to this erroneous program behavior (which is helpful for debugging). When a signal is sent to a process not configured to handle it the default behavior is enacted; for SEGV, the process is killed.

Below is a simple program that goes into an infinite loop, but has first set up a signal handler to catch SIGHUP:

```c
void handle(int arg) {
    printf("stop wakin' me up...\n");
}

int main(int argc, char *argv[]) {
    signal(SIGHUP, handle);
    while (1) {
        // doin' nothin' except catchin' some signs
    }
    return 0;
}
```

You can send signals to it using the command line tool (this is an odd and aggressive name). Doing so will interrupt the main loop in the program and run the handler handle():

```bash
prompt> ./main &
[3] 36705
prompt> kill -HUP 36705
stop wakin' me up...
prompt> kill -HUP 36705
stop wakin' me up...
```

There is a lot to learn about signals, so much that a single chapter, much less a single page, does not nearly suffice. As always, there is one great source: Stevens and Rago [SR05].

The solution, as described by Adya et al. [A02], is to use an old programming language construct known as a continuation [F84]. Though it sounds complicated, the idea is rather simple: basically, record the needed information for finishing this process in some data structure (i.e., when event happens), look up the needed information and process the event.

In this specific case, the solution would be the socket descriptor (sd) in some kind of data structure (e.g., a hash table), indexed by the file descriptor (fd). When disk I/O completes, the event handler would use the file descriptor to look up the continuation, which will return the value of the socket descriptor to the caller. At this point (finally), the server can then do the last bit of work to write to the data.

### 3.8 What Is Still With Events

There are a few other difficulties with the event-based approach that we should mention. For example, when systems moving from a single CPU to multiple CPUs, the server has to run multiple handlers in parallel; when doing so, usual synchronization problems (e.g., critical sections) arise, and the usual solutions (e.g., locks) must be employed. Thus, on multiprocessor servers, simple event handling without locks is no longer possible.

Another problem with the event-based approach is that it does not integrate well with certain kinds of systems, such as paging. For example, if an event handler faults, it will block, and the server will not make progress until the fault completes. Though the server has been structured to avoid explicit blocking, this type of implicit blocking due to page faults is hard to avoid and can lead to large performance problems.

A third issue is that event-based code can be hard to manage over time, as various routines change. For example, if a routine changes from non-blocking to blocking, the event handler that calls that routine must also change to accommodate its nature.

Finally, as asynchronous I/O is now possible on most platforms, it has taken a long time to get there [PD99], and it quite integrates with asynchronous network/O as simple as you might think. For example, while one would simply like to use select() interface to manage all outstanding I/Os, some combination of select and AIO calls are required.

### 3.9 Summary

We've presented a bare bones introduction to a different style of concurrency based on events. Event-based servers give control of scheduling to the application itself, but so at some cost in complexity and difficulty of integration with other aspects of modern systems (e.g., paging). No single approach has emerged as best; thus, both threads and events are likely to persist as different approaches to the same problem for years to come. Read some research papers (e.g., [A02, PD99, WCB01]) or better yet, write some event-based code to learn more.
