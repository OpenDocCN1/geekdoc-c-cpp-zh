# The Andrew File System (AFS)

The Andrew File System was introduced at Carnegie-Mellon University (CMU) in the 1980's [H+88]. Led by the well-known Professor M. Satya-nararayanan of Carnegie-Mellon University (“Satya”) for short, the main goal of this project was simple: **scale**. Specifically, how can one design a distributed file system such that a server can support as many clients as possible?

Interestingly, there are numerous aspects of design and implementation that affect scalability. Most important is the design of the protocol between clients and servers. In NFS, the protocol forces clients to check with the server to determine if cached contents have changed; each check uses server resources (including CPU and network bandwidth), frequent checks like this will limit the number of clients a server can respond to and thus limit scalability.

AFS differs from NFS in that from the beginning, reasonable behavior was a first-class concern. In NFS, cache consistency is hard to describe because it depends directly on low-level implementation details, including client-side cache timeouts. In AFS, cache consistency is simple and readily understood: when the file is opened, a client will receive the latest consistent copy from the server.

Figure 50.1: AFSv1 Protocol Highlights

One of the basics of all AFS is file-caching on the local disk of the client that is accessing a file. When open() the entire file (if it exists) is fetched from the server and stored in your local disk. Subsequent application read() and write() operations are redirected to the local file system where the file is stored; thus, these operations avoid network communication and are finally, upon close(), the file (if it has been modified) is flushed back to the server. Note the obvious: with cache blocks (without whole files, AFS could cache every block of an entire file) and also in client memory (not local disk).

Let's get into the details bit more. When a client application first calls open(), the AFS-side code (which the AFS designers call Venus) would send a Fetch protocol message to the server. The Fetch protocol message would send the pathname of the desired file (for example, /home/remzi/notes.txt) to the server (the group of which called Venus), which would traverse the pathname, find the desired file, and fetch the entire file back to the client. The client-side code would then cache the file on the local disk of the client (by writing it to local disk). As we said about subsequent read() and write() operations are strictly local in AFS (no communication with the server); they are just redirected to the local copy of the file. read() and write() act just like a call to a local file, once a block is accessed, it may be cached in client memory. AFS also uses client memory to cache copies of blocks that it has in local disk. Finally, when needed, the AFS checks if the file has been modified (i.e., it has been opened for writing); if so, the client checks whether the file has changed using the TestAuth protocol. Thus, the server spent much of its time telling clients whether it was OK to use their cached copies. Most of the time, the answer was that the file had not changed. > TIP: Measure Then Build (Patterson’s Law)
One of our advisors, David Patterson (of RISC and RAID fame), used to always encourage us to measure a system before building. By using evidence, rather than instinct, you can turn the process of building into a more scientific endeavor. When you finally get around to building the new system, two things are better as a result: first, you have evidence that shows you are solving a real problem; second, you have a way to measure your new system in place. And thus we can call this Patterson’s Law.

# 50.2 Problems with Version 1

A few keys with this first version of AFS motivated the designers to rethink their file system. To study the details in detail, the designers of AFS spent a great deal of time measuring their existing prototype to find what was wrong. Such experimentation is a good thing, measurement is the key to understanding how systems work and how to improve them; obtaining concrete, good data is thus a necessary part of systems construction. In this theory, the authors found two main problems with AFSv1:

- Path-traversal costs are too high: When performing a Fetch or Store protocol request, the client passes the pathname (e.g., /home/remzi.txt) to the server. The server, in order to access the file, must perform a full pathname traversal, first looking in the root directory to find home, then in home to find remzi, and so, all the way down the path until the file is located. With many clients accessing the server at once, the designers of AFS found that the server was spending much of its CPU time simply walking down directory paths.
- The client issues too many TestAuth protocol messages: Like NFS and its overabundance of GETATTR protocol messages, AFSv1 generated a large amount of traffic to check whether a local file (or its stat information) was valid with the TestAuth protocol. Thus, servers spent much of their time telling clients whether it was OK to use their cached copies of a file. Most of the time, the answer was that the file had not changed.

There were actually two other problems with AFSv1: load was not balanced across servers, and the server used a single distinct process per client inducing context switching and other overheads.
