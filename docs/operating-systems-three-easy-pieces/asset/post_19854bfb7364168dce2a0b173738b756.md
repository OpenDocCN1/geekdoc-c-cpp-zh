In this pattern of usage, we often find one thread waiting for something, and another thread making that something happens and signaling that it has happened, waking the thread. We are thus using the semaphore as an ordering primitive (similar to our use of condition variables earlier).

A simple example is as follows. Imagine a parent creates another thread and then waits for it to complete its execution (Figure 31.6). When this program runs, we would like to see the following:

parent: begin
child
parent: end

The question is, how to use a semaphore to achieve this effect; as it turns out, the answer is relatively easy to understand. As you can see in the code, the parent calls sem_wait() and the child sem_post() to wait for the condition of the child finishing execution to become true. However, this raises the question: what should be the initial value of this semaphore?

(Again, think about it, instead of reading ahead)
The answer of course, is that the value of the semaphore should be set to 0. There are two cases to consider. First, let us assume that the parent creates the child but the child has not run yet (i.e., it is sitting in a waiting queue but not running). In this case (Figure 31.7, page 394), the parent will call sem_wait() before the child has called sem_post(); we'd like the parent to wait for the child to run. The only way this will happen is if the value of the semaphore is not greater than 0; hence, 0 is the initial value. The parent runs, decrements the semaphore (to -1), then waits (sleeping). When the child finally runs, it will call sem_post(), increment the value of the semaphore to 0, and wake the parent, which will then return from `sem_wait()` and finish the program.

The second case (Figure 31.8) occurs when the child runs to complete before the parent gets a chance to call `sem_wait()`. In this case, the child will first call `sem_post()`, increasing the value of the semaphore from 0 to 1. When the parent gets a chance to run, it will call `sem_wait()` and find the value of the semaphore to be 1; the parent will decrement the value (to 0) and return from `sem_wait()` without waiting, also achieving the desired effect.

# 31.4 The Producer/Consumer (Bounded Buffer) Problem

The next problem we will confirm in this chapter is known as the producer/consumer problem, or sometimes as the bounded buffer problem [D72]. This problem is described in detail in the previous chapter on conditions; see there for details.

# ASIDE: SETTING THE VALUE OF A SEMAPHORE

We've now seen two examples of initializing a semaphore. In the first case, we set the value to 1 to use the semaphore as a lock; in the second, to 0, to use the semaphore for ordering. So what's the general rule for semaphore initialization? One simple way to think about it, thanks to Kivowitz, is to consider the number of resources you are willing to give away after initialization. With the lock, it was 1, because you are willing to have it locked (given away) immediately after initialization. With the ordering case, it was 0, because there is nothing to give away at the start, when the thread is done, at which point the value is incremented to 1. Try this line of thinking on future problems, and if it helps.

# First Attempt

Our first attempt at solving the problem introduces two semaphores, empty and full, which the threads will use to indicate a buffer has been emptied or filled, respectively. In this example, the producer first waits for a buffer to be empty to put data into it, and the consumer similarly waits for a buffer to be filled before using it. Let us imagine that MAX=1 (there is only one buffer in array), and see if this works. Imagine again there are two threads, a producer and a consumer. We examine a specific scenario on a single CPU. Assume the consumer gets to run first. Thus the consumer will hit Line C1 in Figure 31.10, sem_wait(&full). Because full was initialized to 0, the call will decrement full (to -1), block the consumer, and wait for another thread to call sem_post() on full, as desired. Assume the producer runs. It hits Line P1, thus calling the sem_wait(&empty) routine. Unlike the consumer, the producer will continue through this line, empty was initialized to value MAX (in this case, 1). Thus, full will be decremented to 0 and the producer will then continue to P3 and call sem_post(&full); changing the value of full from -1 to 0 and waking the consumer (e.g. move it from blocked).

In this case, one of things could happen. If the producer continues to run, it will loop around and hit Line P1 again. This time, however, it would block, as empty semaphore’s value is 0. If the producer instead interrupted and the consumer began to run, it would return from sem_wait(&full) (Line C1), find that the buffer was full, and consume it. In either case, we achieve the desired behavior.

You can try this example with more threads (e.g., multiple producers, and multiple consumers). It should work.
