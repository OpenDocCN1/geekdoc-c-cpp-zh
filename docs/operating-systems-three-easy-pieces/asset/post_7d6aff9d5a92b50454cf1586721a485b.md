# 39.16 Permission Bits And Access Control Lists

The abstraction of a process showed two central virtualizations: of the CPU and memory. Each of these gave the illusion to a process that it had its own CPU and its own private memory; in reality, the OS underneath used various techniques to share limited physical resources among competing entities in a safe and secure manner.

The file system presents a visual view of a disk, transforming it a bunch of raw blocks into more user-friendly files and directories, described within this chapter. However, the abstraction is notably different from that of the CPU and memory, in that files are common among different users and processes and are not (always) private. Thus, a more comprehensive set of mechanisms for enabling various degrees of sharing are usually present within file systems.

The first form of such mechanisms is the classic permission bits. To see permissions for a file foo.txt, just type:

```
prompt ls -l foo.txt
-rw-r-- 1 remzi wheel 0 Aug 24 16:29 foo.txt
```

We'll pay attention to the first part of this output, namely the -rw-r--. The first character here shows the type of the file: - for a regular file (which foo.txt is), d for directory, l for a symbolic link, and so forth; this is (mostly) not related to permissions, so we'll ignore it now.

We are interested in the permission bits, which are represented by the next characters (rw-r--r--). These bits determine, for each regular file, directory, and others, exactly who can access it and how.

The permissions consist of three groups: what the owner of the file can do to it, what someone in a group can do the file, and what (sometimes referred to as other) can. The abilities the owner, group member, or others have the ability to read the file, write, or, execute it.

In example above the first three characters of the output of ls show that the file is both readable and writable by the group (rw-), only readable by members of the group wheel and also by anyone else in the system (r--- followed by r--).

The owner of the file can readily change these permissions, for example by using the chmod command (to change the file mode). To remove the ability for anyone except the owner to access the file, you could type:

```
prompt chmod 600 foo.txt
```

# ASIDE: SUPERUSER FOR FILE SYSTEMS

Which user is allowed to do privileged operations to help administer the file system? For example, if an inactive user's files need to be deleted to save space, who has the rights to do so?

On local file systems, the common default is for there to be some kind of superuser (i.e., root) who can access all files regardless of privileges. In a distributed file system such as A (which has access control), a group called system:administrators contains users who are trusted to do so. In both cases, these users represent an insecure risk; if an attacker is able to somehow impersonate such user, the attacker can access all the information in the system, violating privacy and protection guarantees.

The execute bit is particularly interesting. For regular files, its presence determines whether a program can be run or not. For example, if we have a simple script hello.csh, we may wish to run it by typing:

```
prompt> ./hello.csh
hello, from shell world.
```

However, if we don't set the execute properly for this file, the following happens:

```
prompt> chmod 600 hello.csh
prompt> ./hello.csh
./hello.csh: Permission denied.
```

For directories, the execute bit behaves a bit differently. Specifically, it enables a user (or group, or everyone) to do things like change directories (i.e., cd) into the directory, and in combination with the writable bit, creates files. The best way to learn more about this: play around with yourself! Don't worry, (probably) won't mess anything badly.

Beyond permissions bits, some file systems, such as the distributed file system known as A (discussed in a later chapter), include more sophisticated controls. A, for example, this does in the form of an access list (ACL). Directory access lists are a more general and powerful way to represent exactly who can access a given resource. In a file system, this enables a user to create a very specific list of who and cannot read, in contrast to the limited owner/group/everyone model of permissions above.

# 39.17 Making And Mounting A File System

We've toured the basic interfaces to access files, directories, and certain types of special links. But there is one more topic we should discuss: how to assemble a full directory tree from many underlying file systems and mounting them to make their contents accessible.

To make a file system provide a tool, usually referred to as mkfs (pronounced “make fs”), that performs exactly this task. The idea is as follows: give the tool, as input, a device (such as a disk partition, e.g., /dev/sda) and a file system type (e.g., ext3), and it simply writes a file system starting with a root directory, onto that partition.

However, once such a file system is created, it needs to be made accessible within the file system tree. This task is achieved via the mount program (which makes the real work). What mount does, simply is to attach an existing directory as a mount point and essentially paste a new file system onto that point.

TIP: BEWARE OF TOCTOU

In 1974, McPhee noted a problem in computer systems. Specifically, McPhee noted that “... if there exists a time interval between a validity-check and the operation, through multitasking, the validity-check variables be be changed during this time interval, resulting in an invalid operation performed by the program.” We call this the Time Of Check To Use (TOCTOU) problem, and also, it can occur.

A simple example, as described by Birman and Didier [BD96], shows how a user can create a race file and cause trouble. Imagine that a mail service runs as root (and thus privileges to access all files on a system). This service appends an incoming message to a user's inbox as follows. First, it calls stat() to get information about the file, specifically ensuring that it is just a regular file owned by the user, and not a link to another file that the mail server should not update. Then, if the check succeeds, the server updates the file with the new message.

Unfortunately, the gap between the check and the update leads to a problem: the attacker (the user, who is receiving the mail) switches the access to file (via a call to rename()) to point to a sensitive file as /etc/passwd (which holds information about users and their passwords). If this switch happens at the right time (between the check and the access), the server will gladly let the attacker write to the sensitive file by sending an email, an escalation in privilege: updating /etc/passwd gives attacker control of the system.

There are not any simple solutions to the TOCTOU problem [T+08]. One approach is to reduce the number of services that need root privileges to run, which helps. The NOFOLLOW flag makes it that open() fails if the target is a symbolic link, avoiding attacks that require such. More radical approaches, such as using a transactional file system [H+18], would solve the problem, there aren't many transactional file systems in wide deployment. The usual, (lame) advice: be careful when you write code that runs with high privileges!

```
prompt> mount -t ext3 /dev/sda /home/users
```

If successful, the mount would make this new file system available. However, note how the new file system is accessed. Look at the contents of the root directory, we will use like this:
