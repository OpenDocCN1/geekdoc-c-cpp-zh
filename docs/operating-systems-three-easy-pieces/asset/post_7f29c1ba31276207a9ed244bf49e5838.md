## 40.4 Directory Organization

In vfs (in many file systems), directories have a simple organization; a directory basically contains a list of (entry, inode number) pairs. For each file or directory in a directory, there is a string and a number in the data block(s) of the directory. For each string, there may also be a length (assuming variable-sized names).

For example, assume a directory dir (inode 5) has three files in it (foo, bar, and foobar.a_pretty_lastname), with inode numbers 12, 13, and 24 respectively. The on-disk data for dir might look like:

| inum | declen | strlen | name |
| :--- | :--- | :--- | :--- |
| 5 | 12 | 2 | |
| 12 | 12 | 3 | foo |
| 12 | 12 | 4 | |
| 13 | 12 | 4 | bar |
| 24 | 36 | 28 | foobar_a_pretty_lastname |

In this example, each entry has an inode number, record length (the total bytes for the name plus any over space), string length (the actual length of the name), and finally the name of the. Note that each directory has two entries, "dot" and "dot-dot"; the directory is the current directory (in this example, dir), whereas dot-dot is the parent directory (in this case, the root).

Deleting a file (e.g., unlink()) can leave an empty space in the middle of the directory, and hence there should be some way to mark that as well (e.g., with a reserved number such as zero). Such a delete is one reason the record length is used: a new entry may reuse an old, big entry and then has extra space within.

## ASIDE: LINKED-BASED APPROACHES

Another simpler approach in designing inodes is to use a linked list. Thus, inside an inode, instead of having multiple pointers, you just need to point to the first block of the file. To handle larger files, add another pointer at the end of that data block, and so on, and you can support large files.

As you might have guessed, linked file allocation performs poorly for some workloads; but thinking about the last block of a file, for example, or just doing random access. Thus, to make linked allocation work better, some systems will use an in-memory table of link information, instead of storing the next pointers with the data blocks themselves. The table is indexed by the address of a data block $D$; the content of an entry is simply $D$'s next pointer, the address of the next block follows $D$. A null-value could be too (indicating an end-of-file), or some other marker to indicate that a block is free. Having such a table of next pointers makes it so that a linked allocation scheme can effectively do random access, by first scanning through the (in memory) table to find the desired block, and then accessing (on disk).

Does such a sound familiar? What we have described the basic structure of what is known as the file allocation system, before NTFS [C94], is based on a simple linked-based allocation scheme. There are no differences from a standard Unix file system too; there are no inodes per se, but rather directory entries which store metadata about a file and refer directly to the first block of said file, which makes creating hard links impossible. See Brouwer [B02] for more of the in details

You might be wondering exactly directories are stored. Often, file systems treat directories as a special type of file. A directory has an inode, in the inode table (with the type field of the inode marked as “directory” instead of “regular file”). The directory has data blocks pointed by the inode (and perhaps, indirect blocks); these data blocks live in the data block region of our file system. On-disk structure remains unchanged.

We should also note again that this simple list of directory entries is not the only way to store such information. For example, XFS [S+96] stores directories in B-tree form, making file create operations (which have to ensure that a file name has not been used before creating) faster than systems with simple lists that must be scanned in their entirety.

## ASIDE: FREE SPACE MANAGEMENT

There are many ways to manage free space; bitmaps are just one way. Some early file systems used free lists, where a single pointer in the super block was kept to point to the first free block; inside that block the next pointer was kept, forming a list through the free blocks of the system. When a block was needed, the head block was used and the list updated accordingly.

Modern file systems use more sophisticated data structures. For example, SGI's XFS [+96] uses some form of a B-tree to compactly represent chunks of the free area. With any data structure, different time-space trade-offs are possible.

## 40.5 Free Space Management

A file system must track which inodes and data blocks are free, and which are not, so that when a new file or directory is allocated, it can find space for it. Thus free space management is important for all file systems. In vfs, we have two bitmaps for this task.

For example, when we create a file, we will have to allocate an inode for it. The file system will search through the bitmap for an inode that is free, and allocate it to; the file system will mark the inode as used (with a 1) and eventually update the on-disk bitmap with the correct information. A similar set of activities take place when a data block is allocated.

Some other considerations might come into play when allocating data blocks for a new file. For example, Linux file systems, as ext2 and ext3, will look for a sequence of blocks (say 8) that are free when a new file is created and needs blocks; by finding such a sequence of free blocks, and then allocating them to the newly-created file, the file system guarantees that a portion of the file is contiguous on the disk, thus improving performance. A pre-allocation policy is thus a commonly-used heuristic for allocating space for data blocks.

## 40.6 Access Paths: Reading and Writing

Now that we have idea of how files and directories are stored on disk, we should be able to follow the flow of operation during the activity of reading or writing a file. Understanding what happens on this access path is the second key in developing an understanding of how a file system works; pay attention!

For the following examples, let us assume that the file system has been mounted and thus that the superblock is already in memory. Everything else (i.e., inodes, directories) is still on the disk.

### Reading A File From Disk

In this simple example, let us assume that you want to simply open a file (e.g., /foo/bar), read it, and then close it. For this example, let's assume the file system is 12KB in size (i., 3 blocks).

When you issue an open ("foo/bar") call, the file system first needs to find the inode for the file, to obtain some basic information about the file (permissions, file size, etc.). To do so, the file system must be able to find the inode, but all it has right now is the full name. The file system must traverse the pathname and thus locate the desired. All traversals begin at the root of the file system, in the root directory which is simply /. Thus, the first thing the FS will read from disk is the inode of the root directory. But where is the inode? To find an inode, we must know its i-number. Usually we find it in its directory; the root has no parent (by definition). Thus the root inode number must be known; the FS must know when the file system is mounted. In Unix file systems, the root inode number is 2. Thus, to begin the process, the FS reads in the block that contains inode number 2 (the first block).

Once the inode is read, the FS can look inside it to find pointers to data blocks, which contain the contents of the root directory. The FS will use these on-pointers to read the directory, in which case its looking for an entry for foo. By reading in one or more directory blocks, it will find foo for foo; once found, the FS will also have the inode number of foo (say it is 44) which it will need next.
