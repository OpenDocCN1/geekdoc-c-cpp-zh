
We attempt our first solution to the problem. Assume we initialize each semaphore (in the forks array) to a value of 1. Also that each philosopher knows its own number (p). We can then write the get_forks() and put_forks() routine (Figure 31.15, page 403). To acquire the forks, the intuition behind this (broken) solution is as follows: we grab a “lock” on each one: the first on the left, and then the one on the right. When we are eating, we release them. Simple, no? Unfortunately, in this case, simple means broken. Can you see the problem? Think about it.

The problem is deadlock. If each philosopher happens to grab the fork on their left before any philosopher can grab the fork on their right, each will be holding one fork and waiting for another, forever. Specifically, philosopher 0 grabs fork 1, philosopher 1 grabs fork 2, philosopher 3 grabs fork 3, and philosopher 4 grabs fork 4; all the forks are acquired, and all are stuck waiting for a fork that another philosopher possesses. We'll study deadlock in detail soon; now, for it is to show that this is not a working solution.

## A Solution: Breaking The Dependency

The simplest way to attack this problem is to change how forks are acquired by each of the philosophers; indeed, is how Dijkstra himself solved the problem. Specifically, let's assume that philosopher 4 (the highest numbered one) gets the fork in a different order than the others (Figure 31.16); the put_forks() code remains the same.

Because the last philosopher tries to grab right before left, there is no situation where each philosopher grabs one fork and is stuck waiting for another; the cycle of waiting is broken. Think through the ramifications of this solution, and you convince yourself that it works.

## 31.7 Thread Throttling

One simple use case for semaphores arises on occasion, and thus we present it here. The specific problem is this: how a programmer prevent "too many" threads from doing something at once and bogging the system down? Answer: decide upon a threshold for "too many", and use a semaphore to limit the number of threads executing the piece of code in question. We call this approach throttling [99], and consider it a form of admission control.

Let's consider a more specific example. Imagine you create hundreds of threads to work on some problem in parallel. However, in a certain part of the code, each thread acquires a large amount of memory to perform the computation; each memory-intensive region. If all of the threads enter the memory-intensive region at the same time, the sum of all the memory allocation will exceed the amount of physical memory on the machine. As a result, the machine will start thrashing (i.e., swapping pages to and from the disk), and the entire computation will slow to a crawl.

A simple semaphore can solve this. By initializing the value of the semaphore to the maximum number of threads you wish to enter the memory-intensive region at once, and putting a sem_wait() and sem_post() around the region, a semaphore can naturally throttle the number of threads that are ever concurrent in the dense region of the code.

## 31.8 How Implement Semaphores

Finally, we use our low-level synchronization primitives, locks and condition variables, to build our own version of semaphores called ... (drum roll here) - Semaphores. This task is fairly straightforward, as you can see in Figure 31.17 (page 405).

In the code above, we use one lock and one condition variable, plus a state variable to track the value of the semaphore. Study the code for yourself until you really understand it. Do it!

One subtle difference between Semaphores and pure semaphores as defined by Dijkstra that we do not maintain the invariant that the value of the semaphore, when negative, reflects the value of waiting threads; indeed, the value will never be lower than zero. This behavior is easier to implement and matches the current Linux implementation.

```c
typedef struct __sem_t {
  int value;
  pthread_cond_t cond;
  pthread_mutex_t lock;
} Zem_t;

// only one thread can call this
void Zem_init(Zem_t *s, int value) {
  s->value = value;
  Cond_init(&s->cond);
  Mutex_init(&s->lock);
}

void Zem_wait(Zem_t *s) {
  Mutex_lock(&s->lock);
  while (s->value <= 0)
    Cond_wait(&s->cond, &s->lock);
  s->value--;
  Mutex_unlock(&s->lock);
}

void Zem_post(Zem_t *s) {
  Mutex_lock(&s->lock);
  s->value++;
  Cond_signal(&s->cond);
  Mutex_unlock(&s->lock);
}
```
