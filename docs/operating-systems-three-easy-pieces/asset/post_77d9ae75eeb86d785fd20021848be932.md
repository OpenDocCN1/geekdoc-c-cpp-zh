
# VIRTUAL MEMORY SYSTEMS

The general weakness exploited in each of these attacks is that the CPUs found in modern systems perform all sorts of crazy behind the scenes tricks to improve performance. One class of technique that lies at the core of the problem is called speculative execution, the CPU guesses instructions will be executed in the future, and starts them ahead of time. If the guesses are correct, the program runs faster; if not, the CPU undoes their effects on architectural state (e.g., registers) tries again, this time going down the right path.

The problem with speculation is that it tends to leave traces of its execution in various parts of the system, such as processor caches, branch predictors, and thus. As the authors of the attacks show, such state can be vulnerable to the contents of memory, even memory that was protected by the MMU.

One avenue to increasing kernel protection was to remove much of the kernel address space from each user process and have a separate kernel page table for most kernel data (called kernel page isolation, or KPTI) [G+17]. Thus, instead of mapping the kernel's code and data structures into each process, only the bare minimum is kept; when switching into the kernel, then, switch to the kernel page table is needed. Doing so improves security and avoids attack vectors, but at a cost: Switching page tables is costly convenience and performance.

Unfortunately, KPTI doesn't solve all the security problems laid above, just most of them. Simple solutions, such as turning off speculation, would make little sense, because systems would run thousands of times slower. Thus, it is an interesting time to be alive, if systems security is yours.

To truly understand these attacks, you (likely) have to learn a bit first. By beginning modern computer architecture, as found in advanced books on the topic, focusing on speculation and all the mechanisms needed to implement it. Definitely read about the Meltdown and Spectre attacks, at the websites mentioned above; they actually also include a useful primer on speculation, so perhaps are not a bad place to start. And study the operating system for further vulnerabilities. Who knows what problems remain?

## 23.3 Summary

You have seen a top-to-bottom review of two virtual memory systems. Mostly, most of the details were easy to follow, as you should have already had a good understanding of the basic mechanisms and policies. More detail on VAX/VMS is available in the excellent (and short) paper by Levy and Lipman [LL82]. We encourage you to read it, as it is a great way to see what the source material behind these chapters is like.

You have also learned a bit about Linux. While a large and complex system, it inherits many good ideas from the past, many of which we have not had room to discuss in detail. For example, Linux performs lazy copy-on-write copying of pages upon fork(), thus lowering overheads by avoiding unnecessary copying. Linux also demands memory-mapping of the /dev/zero device, and has a background swap daemon (swapd) that swaps pages to disk to reduce memory pressure. Indeed, the VM is filled with good ideas taken from the past, and also includes many of its innovations.

To learn more, check out these reasonable (but, alas, outdated) books [BC05, G04]. We encourage you to read them on your own, as we can only provide the merest drop from what is an ocean of complexity. But, you've got to start somewhere. What is any ocean, a multitude of drops? [M04]
