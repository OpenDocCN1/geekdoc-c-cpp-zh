
## 43.12 Crash Recovery And The Log

One final problem: what happens if the system crashes while LFS is writing to disk? As you recall in the previous chapter about journaling, crashes during updates are tricky for file systems, and thus something LFS must consider as well.

During normal operation, LFS buffers writes in a segment, and then (when the segment is full, or when some time has elapsed), writes the segment to disk. LFS organizes these in a log, the checkpoint region points to a head and tail segment, and each segment points to the next to be written. LFS also periodically updates the checkpoint region. Crashes could clearly happen during either of these operations (write to a segment, or write to disk). So how LFS handles crashes during these?

Let's cover the second case. To ensure that CR updates atomically, LFS creates two CR, one at each end of the disk, and writes to them alternately. LFS implements a careful protocol when updating the CR with pointers to inode map and other information; first writes a header (with timestamp), then the body of the CR, and then finally one (also with timestamp). If the system crashes during a CR update, LFS can detect this by seeing an inconsistent pair of timestamps. LFS will always choose the most recent CR that has consistent timestamps, and thus consistent update of CR is achieved.

Let's now address the first case. Because LFS crashes every 30 seconds or so, the snapshot of the file system may be quite old. Thus, upon reboot, LFS can easily recover by simply reading the checkpoint region, and however files; however, the last updates would be lost.

To improve upon this, LFS tries to rebuild many of those segments through a technique known as roll forward. The basic idea is to start with the checkpoint region, find the end of the log (which is included in CR), and then use that to read through the next segments and see if there are any updates. If there are, LFS updates the file system accordingly and recovers much of the data and metadata written since the last checkpoint. See Rosenblum's award-winning dissertation for details.

## 43.13 Summary

LFS introduces a new approach to updating the disk. Instead of writing in places, LFS always writes to unused portion of the disk, and then reclaims that space. This approach, which in database systems is called shadow paging [L77] and in file-system-speak is called copy-on-write, enables efficient writing, as LFS can gather all updates in an in-memory segment and then write them out sequentially.

### TIP: FLAWS INTO VIRUES

Whenever your system has a flaw, see if you can turn it into something useful. NetApp's WAFL does this with old files; by making old versions available, WAFL no longer has to worry about cleaning quite often (though it deletes old versions eventually, in the background) and provides a cool feature. Are there other examples of this? Undoubtedly, but you will have to think of them yourself, because this chapter is over with a capital “O”. The large writes that LFS generates are excellent for performance on many different devices. On hard drives, large writes ensure that positioning is minimized; on parity-based RAIDs, as RAID-4 and RAID-5, they avoid the small-write problem entirely. Recent research on Flash-based SSDs [H17]; thus, surprisingly, LFS-style file systems may be an excellent choice for these new mediums. The downside to this approach is that it generates garbage; old copies of the data are scattered throughout the disk, and if one wants to claim space for subsequent usage, one must clean segments periodically. In particular, WAFL got around cleaning problems by turning them into a feature by providing old versions of the file system via snapshots whenever deleted accidentally.
