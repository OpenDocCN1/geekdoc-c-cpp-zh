
# 338 LOCKS

```c
typedef struct __lock_t {
    int flag;
} lock_t;

void init(lock_t *lock) {
    // 0: lock is available, 1: lock is held
    lock->flag = 0;
}

void lock(lock_t *lock) {
    while (TestAndSet(&lock->flag, 1) == 1) {
        // spin-wait (do nothing)
    }
}

void unlock(lock_t *lock) {
    lock->flag = 0;
}
```

Figure 28.3: A Simple Spin Lock Using Test-and-set

The test-and-set instruction does as follows: it returns the value pointed to by the old_ptr, and simultaneously updates said value to new. The key, is that this sequence of operations is performed atomically. The reason it is called "test and set" is that it enables us to "test" the old value (which is returned) while simultaneously "setting" the memory to a new value: as turns out, this more powerful instruction is enough to build a simple spin lock, as we now examine in 28.3. Or better yet: figure it out yourself!

Let's make sure understand why this lock works. Imagine the case where a thread calls lock() and no other thread currently holds the lock; when TestAndSet(flag, 1), the routine will return the old value of flag, which is 0; thus, the calling thread, which is testing the value of flag, will not get spinning in the while loop and will acquire the lock. The thread will also set the value to 1, indicating that the lock is now held. When the thread is finished with its critical section, it calls unlock() to set the lock back to zero.

The second case we can imagine when one thread already has the lock held (i.e., flag is 1). In this case, thread will call lock() and then call TestAndSet(flag, 1) as well. This time, TestAndSet() will return the old value at flag, which is 1 (because the lock is held), while simultaneously setting it to 1. As long as the lock is held by another thread, TestAndSet() will repeatedly return 1, and thus thread will spin and spin until the lock is finally released. When the flag is finally set to 0 by some other thread, this thread will call TestAndSet() again, which will now return 0 while atomically setting the value to 1 and acquire the lock and enter the critical section.

By both the test (of the old lock value) and set (of the new value) a single atomic operation, we ensure that only one acquires the lock. And that's how to build a working mutual exclusion primitive!

TIP: THINK ABOUT CONCURRENCY AS A MALICIOUS SCHEDULER
From this example, you might get a sense of the approach you need to take to understand concurrent execution. What you should try to do is pretend you are a malicious scheduler, that one interrupts threads at the most inpportune of times in order to foil their feeble attempts at building synchronization primitives. What a mean scheduler you are! Although the exact sequence of interrupts may be improbable, it is possible, and that is all we need to demonstrate that a particular approach does not work. It can be useful to think maliciously! (at least, sometimes)

You may also know why this type of lock is usually referred to as a spin lock. It is the simplest type of lock to build, and simply spins, using CPU cycles, until the lock becomes available. To work correctly on a single processor, it requires a preemptive scheduler (i.e., one that will interrupt a thread via a timer, in order to run a different thread, from time to time). Without preemption, spin locks don't make much sense on a single CPU, as spinning on a CPU will never relinquish it.

## 28.8 Evaluating Spin Locks

Given our basic spin, we can now evaluate how effective it is along our previously described axes. The most important aspect of a lock is correctness: does it provide mutual exclusion? The answer here is yes: the lock only allows a single thread to enter the critical section at a time. Thus, we have a correct lock.

The next axis is fairness. How fair is a spin lock to a waiting thread? Can you guarantee that a waiting thread will ever enter the critical section? The answer here, unfortunately, is bad news: spin locks don't provide any guarantees. Indeed, a thread spinning may spin forever, under contention. Simple spin locks (as discussed thus) are not fair and may lead to starvation.

The final axis is performance. What are the costs of using a spin lock? To analyze this correctly, we suggest thinking about a few different cases. In the first, imagine threads competing for the lock on a single processor; in the second, consider threads spread out across multiple CPUs.

For spin locks, imagine the case where the thread holding the lock could be painful; if preempted within a critical section. The scheduler might then run every other thread (imagine there are N-1 others), each of which tries to acquire the lock. In this case, each of those threads will spin for the duration of a time slice before giving up the CPU, a waste of CPU cycles.

However, on multiple CPUs, spin locks work reasonably well (if the number of threads equals the number of CPUs). The thinking goes as follows: imagine Thread A on CPU 1 and Thread B on CPU 2, both contending for a lock.

```c
int CompareAndSwap(int *ptr, int expected, int new) {
    int original = *ptr;
    if (original == expected)
        *ptr = new;
    return original;
}
```

Figure 28.4: Compare-and-swap

If Thread A (CPU 1) grabs the lock, and Thread B tries to, B will spin on (CPU 2). However, presumably the critical section is short, and thus the lock becomes available, and is acquired by Thread B. Spinning to wait for another processor doesn't waste cycles in this case, and thus can be effective.

The basic idea is for compare-and-swap to test whether the value at ptr is equal to expected; if so, update memory location with new value. If not, do nothing.

With the compare-and-swap instruction, we can build a spin lock similar to test-set. We will make some use of this in the following:

```c
void lock(lock_t *lock) {
    while (CompareAndSwap(&lock->flag, 0, 1) == 1) {
        // spin;
    }
}
```

The rest of the code is the same as the test-set example.

## 28.10 Load-Linked and Store-Conditional

Some platforms provide a pair of instructions that work in concert to build locks. Alpha, the MIPS architecture, PowerPC, and ARM provide similar instructions. The C pseudocode for these instructions is as found below. 

The load-linked operates much like a typical load instruction, and fetches a value from memory and places it in a register. The key difference comes store-conditional, which only succeeds (and updates the value at the address just load-linked) if no intervening store to the address has taken place. In the case of success, the store-conditional returns 1 and updates the value at ptr; if it fails, the value at ptr is not updated and 0 is returned.

As a challenge to yourself, try thinking how to build a lock using load-linked and store-conditional. Then, when you are finished, the lock below provides one simple solution.

```c
void lock(lock_t *lock) {
    while (LoadLinked(&lock->flag) != 0) {
        while (!StoreConditional(&lock->flag, 1)) {
            // spin
        }
    }
}
```

The lock() is the only interesting piece. First, a thread spins waiting for the flag to be set to 0 (and thus indicate the lock is not held). Once, the thread tries to acquire the lock via the store-conditional; if it succeeds, the thread has atomically changed the flag's value to 1 and thus can proceed into the critical section.

Note fellow how the store-conditional might arise. One thread calls lock() and executes the load-linked, returning 0 as the lock is not held. Before it can attempt the store-conditional, it is interrupted and another thread enters the code, also executing the load-linked

```c
int LoadLinked(int *ptr) {
    return ptr;

int StoreConditional(int *ptr, int value) {
  if (no update to *ptr since LoadLinked to this address) {
        *ptr = value;
        return 1; // success!
  } else {
        return 0; // failed to update
  }
}
```
