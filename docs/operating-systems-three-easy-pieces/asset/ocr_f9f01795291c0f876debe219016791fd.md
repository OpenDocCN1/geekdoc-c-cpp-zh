It gets even worse when you consider the fact that a stateful server has to deal with client crashes. Imagine, for example, a client that opens a file and then crashes. The open() uses a file descriptor on the server; how the server know it is OK to close a given file? In normal operation, a client would eventually call close() and inform the server that the file should be closed. However, when a client crashes, the server receives a close(), and has to notice the client has crashed in order to close the file.

For these reasons, the designers of NFS decided to pursue a stateless approach: each client operation carries all the information needed to complete the request. No fancy crash recovery is needed; the server just running again, and a client, at worst, might have to retry a request.

# 49.5 The NFSv2 Protocol

We arrive at the NFSv2 protocol definition. Our problem statement is simple:

> The CRUX: How To Define A Stateless File Protocol
How can we define the network protocol to enable stateless operation? Clearly, stated calls like open() can't be part of the discussion (as it would require the server to track open files); however, the client application will want to call open(), read(), write(), close() and other standard API calls to access files and directories. Thus, as a refined question, how do we define the protocol to be stateless and support the POSIX file system API?

One key to the design of the NFS protocol is understanding the file handle. File handles are used to uniquely describe the file or directory a particular operation is going upon; thus, many of the requests include a file handle.
You think of a file handle as having three components: a volume identifier, an inode number, and a generation number; together, these items comprise a unique identifier for a file or directory that a client wishes to access. The volume identifier informs the server which file system the request refers to NFS server can export more than one file system; the inode number tells the server which file within that partition the request is accessing. Finally, the generation number is needed when reusing an inode number by incrementing it inode number is used, the server ensures that a client with an old file handle cannot accidentally access the new-allocated file.
