More intriguing is the case of write buffering. NFS servers absolutely may not return success on a WRITE protocol until the write has been forced to stable storage (e.g., to disk or some other persistent device). While they can place a copy of the data in server memory, returning success to the client on a WRITE protocol could result in incorrect behavior; can you figure out why?

The answer lies in our assumptions about how clients handle server failure. Imagine the following sequence of writes issued by a client:

```
write(fd, a_buffer, size); // fill 1st block with a’s
write(fd, b_buffer, size); // fill 2nd block with b’s
write(fd, c_buffer, size); // fill 3rd block with c’s
```

These overwrites the three blocks of a file with a’s, then b’s, and c’s. Thus, if the file initially looked like this:

```
xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
yyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyy
zzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzzz
```

We might expect the final result after these writes to be like this, with x’s, y’s and z’s, would be overwritten with a’s, b’s, and c’s.

```
aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbcccccccccccccccccccccccccccccccccc
```

Now let’s assume for the sake of the example that these three clients were issued to the server first WRITE protocol and issued to the disk, and the client informed of its success. Now assume the second write is just in memory, and the server also reports it to the client before forcing to disk; unfortunately, the server crashes before writing to it. The server quickly restarts and recovers the third write request, which all succeeds.

Thus, to the client, all the requests requested, but we are surprised that the file contents like this:

```
aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
yyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyy <--- oops
cccccccccccccccccccccccccccccccccccccccccccccc
```

Yikes! Because the server told the client the second write was successful before committing to it, an old chunk is left in the file, which, depending on the application, may be catastrophic.

> ASIDE: INNOVATION BREEDS INNOVATION
As with many pioneering technologies, bringing NFS into the world also required other fundamental innovations to enable its success. Probably the most lasting is the Virtual File System (VFS) / Virtual Node (vnode) interface, introduced by Sun to allow different file systems to be readily plugged into the operating system [K86].

The VFS layer includes operations that are done to an entire file system, such as mounting and unmounting, getting file-system wide statistics, and forcing all dirty (not yet written) writes to disk. The vnode layer consists of all operations that one can perform on a file, such as open, close, reads, and so forth.

To build a new file system, one simply has to define these 'methods'; the framework then handles the rest, connecting system calls to the particular file system implementation, performing generic functions common to all file systems (e.g., caching) in a centralized manner, and providing a way for multiple file system implementations to operate simultaneously

Although some of the details have changed, many modern systems have some form of a VFS/vnode layer, including Linux, BSD variants, macOS, and even Windows (in the form of the Installable File System). Even if NFS becomes less relevant to the world, some of the necessary foundations it will remain vital.

To avoid this problem, NFS servers must commit each write to stable (persistent) store before success; doing ensures the client to detect server failure during a write, and retry until it finally succeeds. Doing ensures we will never end up with file contents intermingled in the above example.

The problem that this requirement gives rise NFS server implementation, where write performance, without great care, can be the performance bottleneck. Some companies (e.g., Network Appliance) came into existence with the simple objective of building an NFS server that can perform writes quickly; one trick is to put writes in a battery-backed memory, then enabling to reply to WRITE requests without fear of losing the data and without the cost of having to write right away; the second trick is to use a file system design specifically designed to write quickly when one file needs to do so [HLM94, RO91].

ASIDE: KEY NFS TERMS

- The key to realizing the main goal of fast and simple crash recovery in NFS is in the design of a stateless protocol. After a crash, the server can quickly restart and begin serving requests again, clients just retry requests until they succeed.
- Making requests idempotent is a central aspect of the NFS protocol. An operation is idempotent when the effect of performing it times is equal to performing it once. In NFS, idempotency enables client retry without worry, and unifies client-message retransmission and how the client handles server crashes.
- Performance concerns dictate the need for client-side caching and buffering, but introduces a consistency problem.
- NFS implementations provide a solution to cache consistency through multiple means: flush-on-open ensures that when a file is closed, its contents are forced to the server, attribute cache reduces the frequency of checking with the server whether a file has changed (via GETATTR requests).
- NFS servers must commit writes to persistent media before returning success; otherwise data loss can occur.
- To support NFS into the operating system, Sun introduced VFS/vnode interface, enabling multiple file system implementations to coexist in the same operating system. Potency of operations is essential; because a client can safely replay a failed operation, it is OK to do whether or not the server has executed the request. We have also seen how the introduction of caching in multiple-client, single-server system can complicate things. In particular, the system must resolve in order to behave reasonably; however, NFS does in a slightly hot fashion which can occasionally result in weird behavior. Finally, talked about other issues which are certainly relevant: Security in early NFS implementations were remarkably lax; it was rather easy for any user to masquerade as others and gain access. Subsequent integration with more serious authentication services (e.g., Kerberos [NT94]) have addressed these deficiencies.
