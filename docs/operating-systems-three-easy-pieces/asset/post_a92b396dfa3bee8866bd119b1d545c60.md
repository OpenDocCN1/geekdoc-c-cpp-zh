
Of course, to understand what memory accesses this code snippet (which simply initializes an array) will make, we'll have to know (or assume) a few things. First, we'll have to disassemble the result using objdump on Linux, or otool on a Mac) to see what assembly instructions are used to initialize the array in a loop. Here is the resulting assembly code:

```
1024 mov $x0, (%edi,%eax,4)
1028 incl %eax
1032 cmpl $0x038,%eax
1036 jne 0x1024
```

The code, if you know a x86, is actually quite easy to understand. The first instruction moves the value zero (as $0x0) into the virtual memory address of the array; this is computed by taking the contents of %edi and adding %eax multiplied by four. Thus, %edi holds the base address of the array, whereas %eax holds the index (i); we multiply by four because the array is an array of integers, each of four bytes.

The second instruction increments the array held in %eax, and the third instruction compares the contents of register to the value 0x038, or decimal 1000. If the comparison shows two values are not yet equal (which is what the jne instruction tests), the fourth instruction jumps back to the top of the loop.

To understand what memory accesses this sequence makes (at both the virtual and physical levels), we'll have to assume something about where virtual memory code snippet and array are found, and (real realistically) the contents and location of the page table.

For this example, we assume a virtual address size of 64KB (unrealistic). We also assume a page size of 4KB.

All we need to know are the contents of the page table, and its location in physical memory. Let's assume we have a linear (array-based) page table and that it is located at physical address 1KB (1024).

As for contents, we just need a few virtual pages to worry about mapping for this example. First, there is the virtual page code lives on. Because the page size is 4KB, virtual address 1024 resides on the second page of the virtual table (VPN=1 → VPN=0 is the first page). Let's assume our virtual page maps to physical frame 4 (VPN 1 → PFN 4).

Next, there is the array itself. Its size is 4000 bytes (integers), and we assume that it resides at virtual addresses 40000 through 44000 (not including the last byte). The virtual pages for this decimal range are VPN=39 ... VPN=42. Thus, we need mappings for these pages. Let's assume these virtual-to-physical mappings for the example: (VPN 40 → PFN 8, VPN 41 → PFN 9, VPN 42 → PFN 10).

# 18.6 Summary

We have introduced the concept of paging as a solution to our challenge of virtualization. Paging has many advantages over previous approaches (such as segmentation). First, it does not lead to external fragmentation, as paging (by design) divides memory into fixed-sized units. Second, it is flexible, enabling the sparse use of virtual address spaces.

However, implementing paging support without care will lead to a slower machine (with many extra memory accesses to access the page table) as well as memory waste (with memory filled with page tables instead of useful application data). We'll have to think a little harder to come up with a paging system that not only works, but works well. The next two chapters, fortunately, will show us how to do so.
