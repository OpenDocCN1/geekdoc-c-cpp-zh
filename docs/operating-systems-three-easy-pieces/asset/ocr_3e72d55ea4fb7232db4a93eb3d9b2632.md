# Growing The Heap

We should discuss one last mechanism found within allocation libraries. Specifically, what should you do if the heap runs out of space? The simplest approach is to just fail. In some cases this is the only option, and returning NULL is an honorable approach. Don't feel bad! You tried, and though you failed, you fought the fight.

Most traditional allocators start with a small-sized heap and request memory from the OS when they run out. Typically, this make some kind of system call like `sbrk` in UNIX systems to grow the heap, and then allocate new chunks from there. To service the `sbrk` request, the OS finds free physical pages, maps them into the address space of the requesting, and returns the value of the end of the new heap; at that point, a larger heap is available, and the request can be successfully serviced.

# 17.3 Basic Strategies

Now that we have machinery under our belt, let's go over some strategies for managing free space. These approaches are mostly based on plenty policies that you could think up yourself; try before reading and if you come up with all of the alternatives (or maybe some ones!).

The ideal allocator is both fast and minimizes fragmentation. Unfortunately, the stream of allocation and free requests can be arbitrary (after all, they are determined by the programmer), any particular strategy can do quite badly using the wrong set of inputs. Thus, we will not describe a "best" approach, but rather talk about some basics and discuss your pros and cons.

# Best Fit

The best fit strategy is quite simple: first, search through the free list and find chunks of free memory that are as big or bigger than the requested size. then, return the one that is smallest in that group of candidates; this is the called best-fit chunk (it could be called smallest fit too). Pass through the free list to ensure the correct block to return.

The intuition behind best fit is simple: by returning a block that is close to what the user asks, best fit tries to reduce wasted space. However, it is a cost; naive implementations pay a heavy performance penalty when performing an exhaustive search for the correct block.
