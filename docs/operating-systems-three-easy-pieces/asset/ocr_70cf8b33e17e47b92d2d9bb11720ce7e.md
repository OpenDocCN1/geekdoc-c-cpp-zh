# EVENT-BASED CONCURRENCY (ADVANCED)

> TIP: DON'T BLOCK IN EVENT-BASED SERVERS
Event-based servers enable fine-grained control over scheduling of tasks. However, to maintain such control, no call that blocks the execution of the caller can be made; failing to obey this design tip will result in a blocked event-based server, frustrated clients, and serious questions as to whether you ever read this part of the book.

# 33.4 Why Simpler? No Locks Needed

With a single CPU and an event-based application, the problems found in concurrent programs are no longer present. Specifically, only one event is being handled at a time, there is no need to acquire or release locks; the event-based server cannot be interrupted by another thread-cause it is single threaded. Thus, concurrency bugs common in threaded programs are not manifest in the basic event-based approach.

# 33.5 A Problem: Blocking System Calls

Thus far, event-based programming sounds great, right? You program a simple loop, and handle events as they arise. You don't need to think about locking! But there is an issue: what if an event requires that you issue a system call that might block?

For example, imagine a request from a client to a server to read a file from disk and return its contents to the requesting client (much like a simple HTTP request). To service such a request, some event handler will have to issue an `open()` call to open the file, followed by a series of `read()` calls to read the file. When the file is read into memory, the server will likely start sending the results to the client.

Both `open()` and `read()` calls may issue I/O requests to the storage system (when the metadata or data is not in memory already), and may take a long time to serve. With a thread-based server, this is no issue; while the thread issuing the I/O suspends (waiting for the I/O to complete), other threads can run, enabling the server to make progress. Indeed, this is what makes thread-based programming quite natural and straightforward for I/O intensive tasks.

With an event-based approach, however, there are no other threads to run: just the main loop. And this implies that if an event handler issues a call that blocks, the entire server will do just: until the call completes. When the event loop blocks, the system sits idle, and thus is a huge potential waste of resources. We have a rule that must be obeyed in event-based systems: no blocking calls.
