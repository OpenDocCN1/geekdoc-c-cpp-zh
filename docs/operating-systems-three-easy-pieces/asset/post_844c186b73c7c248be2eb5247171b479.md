TIP: ENFORCE LOCK ORDERING BY LOCK ADDRESS
In some cases, a function may grab two (or more) locks; thus, we know we must be careful or deadlock could arise. Imagine a function that is called as follows: `do.something(mutex_t *m1, mutex_t *m2)`. If the code acquires m1 before m2 (or m2 before m1), it could deadlock, as another thread call `do.something(L1, L2)`, while another thread call `do.something(L2, L1)`.

To avoid this issue, the clever programmer can use the address of each lock as a order of locking. By acquiring locks in either high-to-low or low-to-high address order, `do.something()` guarantee that it always acquires locks in the same order, regardless of which order they are passed. The code would look like this:

```c
if (m1 > m2) { // grab in high-to-low address order
  pthread_mutex_lock(m1);
  pthread_mutex_lock(m2);
} else {
  pthread_mutex_lock(m2);
  pthread_mutex_lock(m1);
}
 // Code assumes m1 == m2 (not the same lock)
```

By using this technique, a programmer can ensure a simple and efficient deadlock-free implementation of multi-lock acquisition.

Furthermore, ordering is a convention, and a sloppy programmer can easily ignore the lock ordering and potentially cause deadlock. # Hold-and-wait requirement

The hold-and-wait requirement for deadlock can be avoided by acquiring all locks at once, atomically. In practice, this can be achieved as follows:

```c
pthread_mutex_lock(prevention); // begin acquisition
pthread_mutex_lock(L1);
pthread_mutex_lock(L2);
...
pthread_mutex_unlock(prevention); // end
```

# No Preemption

Because we generally view locks as held until unlock is called, multiple lock acquisition often gets into trouble because waiting for one lock we are holding. Many thread libraries provide a flexible set of interfaces to help avoid this situation. Specifically, the pthread_mutex_trylock() either grabs the lock (if it is available) and returns success or an error indicating the lock is held; in the latter case, you can try again later if you want to grab that lock.

Such an interface could be used to build a deadlock-free, ordering-robust lock acquisition protocol:

```c
top:
pthread_mutex_lock(L1);
if (pthread_mutex_trylock(L2) != 0) {
    pthread_mutex_unlock(L1);
    goto top;
}
```

Note that another thread could follow the same protocol but grab the locks in the other order (L2 then L1) and the program would still be deadlock. One new problem arises, however: livelock. It is possible (though perhaps unlikely) that two threads could be repeatedly attempting this sequence and repeatedly failing to acquire both locks. In this case, both systems are running through this code sequence over and again (though it is not a deadlock), but progress is not being made, hence the name livelock problem, too: for example, one could add a delay before looping and trying over again, decreasing the odds of repeated interference among competing threads.

# Mutual Exclusion

The final technique would be to avoid mutual exclusion. In general, we know this is difficult, because we could design data structures without locks. As a simple example, let us assume we have compare-and-swap instruction, which may be an atomic instruction provided by hardware that does the following:

```c
int CompareAndSwap(int *address, int expected, int new) {
  if (*address == expected) {
    *address = new;
    return 1; // success
  }
  return 0; // failure
}
```

Imagine we wanted to atomically increment a value by a certain amount, using compare-and-swap. We could do so with the following function:

```c
void AtomicIncrement(int *value, int amount) {
  do {
    int old = *value;
  } while (CompareAndSwap(value, old, old + amount) == 0);
}
```

Instead of acquiring a lock, doing the update, and then releasing it, we have built an approach that repeatedly tries to update the value to the new amount using the compare-and-swap.

Let us consider a slightly more complex example: list insertion. Here is code that inserts at the head:

```c
void insert(int value) {
  node_t *n = malloc(sizeof(node_t));
  asert(n != NULL);
  n->value = value;
  n->next = head;
  head = n;
}
```

This code performs a simple insertion, but if called by multiple threads at the "same time", it is a race condition. Can you figure out why? (draw a picture of what could happen to a list if two concurrent inserts take place, assuming, as always, a malicious interleaving). Of course, we could solve this by surrounding this code with a lock acquire and release:

```c
void insert(int value) {
  node_t *n = malloc(sizeof(node_t));
  asert(n != NULL);
  n->value = value;
  pthread_mutex_lock(listlock); // begin critical section
  n->next = head;
  head = n;
  pthread_mutex_unlock(listlock); // end critical section
}
```

In this solution, we are using locks in the traditional manner. Instead, let try to perform this insertion in a lock-free manner simply using the compare-and-swap instruction. Here is one possible approach:

```c
void insert(int value) {
  node_t *n = malloc(sizeof(node_t));
  asert(n != NULL);
  n->value = value;
  do {
    n->next = head;
  } while (CompareAndSwap(&head, n->next, n) == 0);
}
```
