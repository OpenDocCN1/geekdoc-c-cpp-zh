TIP: DO WORK IN THE BACKGROUND
When you have some work to do it is often a good idea to do it in the background to increase efficiency and allow for grouping of operations. Operating systems often do work in the background; for example, many systems buffer file writes before actually writing the data to disk. Doing so has many benefits: increased disk efficiency, as the disk may receive many writes at once and thus be able to schedule them; reduced latency of writes, as the application thinks the writes completed quickly; the possibility of work reduction, as the writes may never go to disk (if the file is deleted); and better use of idle time, as the background work may be possible when the system is otherwise idle, thus better utilizing the hardware[G+95].

## 21.7 Summary

In this brief chapter, we have introduced the notion of accessing more memory than is physically present within a system. To do so requires complexity in page-table structures, a present bit (of some kind) must be included to tell whether the page is in memory or not. When not, the system page-fault handler runs to serve the page fault, and arranges for the transfer of the desired page to memory, perhaps first replacing some pages in memory to make room for those to be swapped in.

Recall, importantly and amazingly!, that actions all take place transparently to the process. As is is accessing its own private, contiguous virtual memory. Behind the scenes, pages are placed in arbitrary (non-contiguous) locations in physical memory, and sometimes they are not present in memory, requiring a fetch from disk. While we hope that in the common case memory access is fast, in some cases it will take multiple disk operations to service it; something as performing a single instruction can, in the worst case, take many milliseconds to complete.

## Questions

- 1. First, open two separate terminal connections to the **same machine**, so that you can easily run something in one window and the other. Now, in window, run `vmstat 1`, which shows statistics about machine usage every second. Read the man page, the associated README, and any other information you need so that you can understand its output. Leave this window running `vmstat` for the rest of the exercises. Now we will run the program `mem.c` but with very little memory usage. This can be accomplished by typing `./mem 1` (which uses 1 MB of memory). How do the CPU usage statistics change when running `mem`? Do the numbers in the `user` column make sense? How does this change when running more than one instance of `mem` at once?

- 2. Let's now looking at the memory statistics running two columns: `swpd` (the amount of virtual memory) and `free` (the amount of idle memory). `./mem 1024` (which allocates 1024 MB) and watch how these values change. In particular, how does the **free** column change when the program exits?

- 3. We'll look at the `swap` columns (**si and so**), which indicate how much is taking place to and from disk. Of course, to activate this, you will need to run `mem` with large amounts of memory. One of the entries in `/proc/meminfo` is the total amount of memory in system. Let's assume it's something 8 GB; if so, start by running `mem 4000` (about 4 GB) and watching the swap in/out columns. Which columns give non-zero values? Then, try with `5000`, `6000`, etc. What happens to these values as the program enters second loop? How much data (total) are swapped in out?

- 4. Do the same experiments as above, but now watch the other statistics (such as CPU utilization, and block/O statistics). How do they change when mem is running?

- 5. Now let's examine performance. Pick an input for mem that comfortably fits in memory (say 4000 if the amount of memory on the system is 8 GB). How long does loop take (and subsequent loops 1, 2, etc.)? Pick a size comfortably by the size of memory (say 12000 against 8 GB). How long, the loops take here? How different is performance when constantly swapping versus fitting everything used by mem? Can you make a graph, with the size of used memory on the y-axis? Finally, how does the performance of the said memory of the first loop compare to that of subsequent loops, for both the case where everything isn't in memory and where it doesn't?

- 6. Swap space isn't infinite. You can use the tool swap with the -s flag to see how much swap space is available. What happens if you try to run mem with increasingly large values, beyond what seems to be available in swap? At what point does memory allocation fail?

- 7. Finally, if you're advanced, you can configure your system to use different swap devices using swap and swapoff. Read the pages for details. If you have access to different hardware, see how the performance of swapping changes when swapping to a classic hard drive, a flash-based SSD, and even a RAID array. How much can swapping performance be improved via newer devices? How close can you get to in-memory performance?
