If you are taking an undergraduate operating systems course, you should already have some idea of what a computer program does when it runs. If not, this book (and the corresponding course) is going to be difficult — so you should probably stop reading this instruction, or run to the nearby bookstore and quickly consume the necessary background material before continuing (both Patt & Patel [PP03] and Bryant & O’Hollar [BOH10] are pretty great books).

So what happens when a program runs?

Well, a running program does one very thing: it executes instructions. Millions (and these days, even billions) of times every second, the processor **fetches** from memory, **decodes** it (i.e., figures out which instruction this is), the processor moves to the next instruction, and **executes** it (i.e., it does the thing that is supposed to do, like add two numbers together, access memory, check a jump to a function, and so forth). After it is done with this instruction, so and on, until the program finally completes¹¹.

Thus, we have just described the basics of the *Von Neumann* model of computing²². Sounds simple, right? But in this class, we will be learning that while a program runs, a lot of wild things are going on with the primary goal of making the system **easy to use**.

There is a body of software, in fact, that is responsible for making it easy to run programs (even allowing you to seemingly run many at the same time), allowing programs to share memory, enabling programs to interact with devices, and other stuff like that. That body of software

## THE CRUX OF THE PROBLEM: HOW TO VIRTUALIZE RESOURCES

One question we will answer in this book is quite simple: how does the operating system visualize resources? This is the crux of our problem. Why the OS does not the main question, as the answer should be obvious: it makes the system easy to use. Thus, we focus on the *how*: what mechanisms and policies are implemented by the OS to attain virtualization? How does the OS do so efficiently? What hardware support is needed?

We will use the "crux of the problem", in shaded boxes like this one, as a way to call out specific problems we are trying to solve in building an operating system. Thus, within a note on a particular topic, you may find one or more cruces (yes, this is the proper plural) which highlight the problem. The details within the chapter, of course, present the solution, or at least the basic parameters of a solution.

is called the **operating system (OS)**², as it is in charge of making sure the system operates correctly and efficiently in an easy-to-use manner.

The primary way the OS does this is through a general technique that we call **virtualization**. Thus, the OS takes a **physical resource** (such as the processor, memory, or a disk) and transforms it into a more generic, powerful, and easy-to-use **virtual form** of itself. Thus, we sometimes refer to the operating system as a **virtual machine**.

In order, to allow users to tell the OS what to do and thus make use of the features of the virtual machine (such as running a program, allocating memory, or accessing a file), the OS also exports some interfaces (**APIs**) that you can call. A typical OS, in fact, exports a few hundred system calls that are available to applications. Because the OS provides these to run programs, access memory and devices, and other related actions, we sometimes say that the OS provides a **standard library** to applications.

Finally, because virtualization allows many programs to run (thus including the CPU), and many programs to concurrently access their own structures and data (thus sharing memory), and many programs to access devices (thus sharing disks and so forth), the OS is sometimes known as a **resource manager**. Each of the CPU, memory, and disk is a **resource** of the system; it is thus the operating system's role to **manage these resources**, doing so efficiently or fairly or indeed with many possible goals in mind. To understand the role of the OS a little better, let's take a look at some examples.

Now, let's do the same thing, but this time, let's run many instances of this same program. Figure 2.2 shows the results of this slightly complicated example.

Well, now things are getting a little more interesting. Even though we have only one processor, anyhow all of these programs seem be running at the same time! How does this happen?

It turns out that the operating system, with some help from the hardware, is in charge of this illusion, i.e., the illusion that the system has a very large number of virtual. Turning a single CPU (or a small set of them) into a seemingly infinite number of CPUs and allowing many programs to seemingly run at once is what we call **virtualizing the CPU**, the focus of the first part of this book.

Of course, to run programs, and stop them, and otherwise tell the OS which programs to run, there need to be some interfaces (APIs) that you can use to communicate your desires to the OS. We'll talk about these APIs throughout this book; indeed, they are the major in which most users interact with operating systems.

You might also note that the ability to run multiple programs at once raises all sorts of questions. If two programs want to run at a particular time, which should run? This question is answered by a **policy of the OS**; policies are used in many places within an OS to answer these types of questions, and we will study them as we learn about the **basic mechanisms** that operating systems implement (such as the ability to run multiple programs at once). Hence the role of the OS as a **resource manager**.
