# LOCK-BASED CONCURRENT DATA STRUCTURES

> TIP: MORE CONCURRENCY ISN’T NECESSILY FASTER
If the scheme you design adds a lot of overhead (for example, acquiring and releasing locks frequently, instead of once), the fact that it is more concurrent may not be important. Simple schemes tend to work well, especially if they use costly routines. Adding more locks and complexity can be your downfall. All of that said, there is one way to really know: build both alternatives (simple but less concurrent, and but more concurrent) and measure how they do. In the end, you can't cheat on performance; your idea is either faster, or it isn't.

# 29.2 Concurrent Linked Lists

We examine a more complicated structure, the linked list. For simplicity, we'll omit of the obvious routines that a list would have and just focus on concurrent insert; we'll leave it to the reader to look about lookup, delete, and so forth. 29.7 shows the code for this rudimentary data structure.

As you can see in the code, the simple code acquires a lock in the insert routine upon entry, and releases it upon exit. Small tricky issue arises if malloc() fails to allocate (a rare case); in this case, the code must release the lock before failing the insert.

This exceptional control flow has shown to be quite prone; a recent study of Linux kernel patches found that a huge fraction of bugs (nearly 40%) are found on rarely-taken code paths (indeed, this observation sparked some of our research, where we removed all memory-faulting paths from a Linux file system, resulting in a more robust system [S11].

Thus, a challenge: we can rewrite the insert and lookup routines to maintain correct under concurrent insert but the case where the failure path also requires us to add the lock to unlock

The answer, in this case, is yes. Specifically, we can rearrange the code so that a lock only surround the actual critical section in the insert, and that a common exit is used in the lookup code. The former works because part of the insert actually not need to be locked; assuming that malloc is thread-safe, can call into it without worry of race conditions or other concurrency bugs. Only when updating the shared list does a lock need to be held. See Figure 29.8 for the details of these modifications.

As for the lookup routine, it is a simple transformation to jump out of the main search loop to a single return path. So doing again reduces the number of lock acquire/release points in the code, and decreases the chances of accidentally introducing bugs (such as forgetting to unlock before returning) into the code.
