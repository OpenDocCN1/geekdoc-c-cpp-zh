# More Than Two Levels

In our example thus far, we've assumed that multi-level page tables only have two levels: a page directory and pieces of the page table. In some cases, a deeper tree is possible (and indeed, needed).

Let's take a simple example and use it to show how a multilevel table can be useful. In this example, assume we have a 30-bit virtual address space, and a 512 (byte) page size. Our virtual address has a 21-bit virtual page number and a 9-bit offset.

Remember our goal in constructing a multi-level page table: to make each piece of the page table fit within a single page. Thus, we've only considered the page table itself, however, if the page directory gets too big?

To determine how many levels are needed in a multi-level to make all pieces of the page table fit within a page, we start by determining how many page-table entries fit within a page. Given our page size of 512 bytes, and using a PTE size of 4 bytes, you should see that you can fit 128 PTEs on a single page. When we index into a page of the page bits, we can conclude we need the least 7 bits (log2128) of the VPN as an index.

You might also notice from the diagram above how many bits are left in the (large) page directory: 14. If our page directory has $2^{14}$ entries, it spans not one 128, and thus our goal of making every piece of the multi-level page table fit into page vanishes.

To remedy this, we build a further level of the tree, by splitting the page directory into multiple pages, and adding another page directory on top of that, to point to the pages of the page directory. We can split our virtual address as:

Now, when indexing the upper-level directory, we use the top bits of the virtual address (PD Index 0 in the diagram); this index can be used to fetch the page-directory entry from the top-level directory. If so, the second level of page directory is consulted by combining the physical frame number from the top-level PDE and next part of the VPN (PD Index 1). Finally, if valid, the PTE address can be formed using the page-table index combined with the second-level PDE. That's a lot of work to look up something in a multi-level table.

```
VPN = (VirtualAddress & VPN_MASK) >> SHIFT
(Success, TlbEntry) = TLB_Lookup(VPN)
if (Success == True) // TLB Hit
    if (CanAccess(TlbEntry.ProtectBits) == True)
        Offset = VirtualAddress & OFFSET_MASK
        PhysAddr = (TlbEntry << SHIFT) | Offset
        Register = AccessMemory(PhysAddr)
    else
        RaiseException(PROTECTION_FAULT)
else // TLB Miss
    // first, get directory entry
    PDIndex = (VPN & PD_MASK) >> SHIFT
    PDEAddr = PDB + (PDIndex + sizeof(PDE))
    PDE = AccessMemory(PDEAddr)
    if (PDE.Valid == False)
        RaiseException(SEGMENTATION_FAULT)
    else
        // if valid, fetch PTE from page table
        PTIndex = (VPN & PT_MASK) >> SHIFT
        PTEAddr = (PDE << SHIFT) + (PTIndex * sizeof(PTE))
        PTE = AccessMemory(PTEAddr)
        if (PTE.Valid == False)
            RaiseException(SEGMENTATION_FAULT)
        else if (CanAccess(PTE.ProtectBits) == False)
            RaiseException(PROTECTION_FAULT)
        else
            Tlb_Insert(VPN, PTE.PFN, PTE.ProtectBits)
Retry()
```

# The Translation Process: Remember the TLB

To summarize the entire process of address translation using a two-level page table, we again present the control flow in algorithmic form (Figure 20.6). The figure shows what happens in hardware (a hardware-managed TLB) upon every memory reference.

As you can see from the figure, before any of the complicated multi-level page access occurs, the hardware first checks the TLB; upon a hit, the physical address is formed directly without accessing the page at all. Only upon a TLB miss does the hardware need to perform the full multi-level lookup. On this path, you can see the cost of our traditional two-level page table: two additional memory accesses to look up a translation.

# Inverted Page Tables

An even more extreme space savings in the world of page tables is found with **inverted page tables**. Here, instead of having many page tables (one per process of the system), we keep a single page table that has an entry for each *physical* page of the system. The entry tells us which process is using this page, and which virtual page of that process maps to this physical page.

Finding the correct entry is now a matter of searching through data structure. A linear scan would be expensive, and thus a hash table is often built over the base structure to speed up lookups. The PowerPC is one example of such architecture [JM98].

More generally, inverted page tables illustrate what we've said from the beginning: page tables are just data structures. You do lots of crazy things with data structures, making them smaller or bigger, making them slower or faster. Multi-level and inverted page tables are just two of many things one could do.

# Swapping the Page Tables to Disk

Finally, we have assumed that page tables reside in kernel-owned physical memory. Even with many tricks to reduce the size of page tables, it is still possible, however they may be too big to fit into memory all at once. Thus, some systems place page tables in **kernel virtual memory**, allowing the system to *swap* some of these page tables to disk when memory pressure gets a little tight. We'll talk more about this in a future chapter (namely the case study of VAX/VMS), once we understand how to move pages in and out of memory in detail.

# Summary

We have seen how real page tables are built; not just as linear arrays but as more complex data structures. The trade-offs they present are in time and space — the bigger table, the faster the TLB miss, the choice of structure depends on the constraints of the given environment. In a memory-constrained system (like other systems), small structures make sense; in a system with a reasonable amount of memory and workloads that use a large number of pages, a bigger table that speeds up TLB misses might be the right choice. With software-managed TLBs, the entire space of data structures opens up to the delight of the operating system innovator (hint: that's you). What new can you come up with? What problems do they solve? Think of these questions as you fall asleep, and dream the big dreams that only operating-system developers can dream.
