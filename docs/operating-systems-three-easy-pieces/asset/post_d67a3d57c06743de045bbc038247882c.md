
## 44.3 Basic Flash Operations

Given this flash organization, there are three low-level operations that a flash chip supports. The read command is used to read a page from the flash; erase and program are used in tandem to write. The details:

- Read (a page): A client of the flash chip can read any page (2KB or 4KB), by specifying the read command and appropriate page number to the device. This operation is typically quite fast, 10s of microseconds or so, regardless of location on the device, and (or less) regardless of the location of the previous request (unlike a disk). Being able to access any location uniformly quickly means the device is a random access device.
- Erase (a block): Before writing to a page within a flash, the nature of the device requires that you first erase the entire block the page lies within. Erase, importantly, destroys the contents of the block (by setting each bit to the value 1); therefore, you must be sure that any data you care about the the block has been copied elsewhere (to memory or perhaps to another flash block) before executing the erase. The erase is expensive, taking a few milliseconds to complete. Once finished, the block is reset and each page is ready to be programmed.
- Program (a page): Once a block has been erased, the program command can be used to change some of the 1s in a page to 0s, and write the desired contents. Programming is less expensive than erasing, but more costly than reading a page, usually taking around 100s of microseconds on modern flash chips.

One way to think about flash chips is that each page has a state associated with it. Pages start in an INVALID state. By erasing the block that a page resides within, you set the state of the page (and all pages within that block) to ERASED, which resets the contents of each page in the block but also makes them programmable. When you program a page, its state changes to VALID, meaning its contents have been be read. Reads do not affect these states (although you should only read from pages that have been programmed). Once a page has been programmed, the only way to change its contents is to erase the entire block within which the page resides. Here is an example of state transition after various erase and program operations within a 4-page block:

```
IIII      Initial: Pages in block are invalid (I)
Erase()   → EEEE    In block set to erased (E)
Program(0) → VEEE    Program page 0; state to valid (V)
Program(0) → error   Cannot re-program page
Program(1) → VEEE    Program page 1
Erase()   → EEEE    Contents erased; all pages programmable
```

## Detailed Example

Because the process of writing (i.e., erasing and programming) is so unusual, let's go through a detailed example to make sure it sense. In this example, imagine we have the following 8-bit pages, within a 4-page block (both unrealistically small, but useful within this example); each page is VALID as each has been programmed.

| Page 0 | Page 1 | Page 2 | Page 3 |
| :--- | :--- | :--- | :--- |
| 00011000 | 11001110 | 00000001 | 00111111 |
| VALID | VALID | VALID | VALID |

Now say we wish to write page 0, filling it with contents. To write any page, we must first erase the entire block. Let's assume we do so, leaving the block in this state:

| Page 0 | Page 1 | Page 2 | Page 3 |
| :--- | :--- | :--- | :--- |
| 11111111 | 11111111 | 11111111 | 11111111 |
| ERASED | ERASED | ERASED | ERASED |

Good news! We could now erase and program page 0, for example with contents 00000111, overwriting the old page 0 (contents 00011000) as desired. After doing so, our block looks like:

| Page 0 | Page 1 | Page 2 | Page 3 |
| :--- | :--- | :--- | :--- |
| 00000111 | 11111111 | 11111111 | 11111111 |
| ERASED | ERASED | ERASED | ERASED |

And now we are: the contents of pages 1, 2, and 3 are all gone! Thus, before overwriting any page within a block, we must first move any data we care about to another location (e.g., memory, or elsewhere on the flash). The nature of erase will have a strong impact on how we design flash-based SSDs, as we'll soon learn.

## Summary

To summarize, reading a page is easy: just read the page. Flash chips do this well, and quickly; in terms of performance, they offer the potential to greatly exceed the random performance of disk drives, which are slow due to mechanical and rotation costs.

Writing a page is trickier; the entire block must be erased (taking care to first move any data we care about to another location), and then the desired page programmed. Not only is this expensive, frequent repetitions of this program/erase cycle can lead to the reliability problem flash chips have: wear out. When designing a storage system with flash, the performance and reliability of writing is a central focus. We'll soon learn more about how modern SSDs attack these issues, delivering excellent performance and reliability despite these limitations.

## 44.4 Flash Performance And Reliability

Because we're interested in building a storage device out of raw chips, it is worthwhile to note their basic performance characteristics. Figure 44.2 presents a rough summary of some numbers found in the popular press [V12]. There, the author presents the basic operation latency of reads, and across SLC, MLC, and TLC flash, which store 1, 2, and 3 bits per cell, respectively.

As we can see from the table, read latencies are quite good, taking 10s of milliseconds to complete. Program latency is higher and variable, as low as 200 milliseconds for SLC, but higher as you pack more bits into each cell; to get write performance, you will have to make use of multiple flash chips in parallel. Furthermore erases are quite expensive, taking a few milliseconds typically. Dealing with this cost is central to modern flash storage design.

Let's consider reliability of flash chips. Unlike mechanical disks, which can fail for a wide variety of reasons (including the gruesome and physical head crash, where the drive actually makes contact with the recording surface), flash chips are pure silicon and in that sense have fewer reliability issues to worry about. The primary concern is wear when a flash block is erased or programmed, it slowly accumulates a little bit of extra wear. Over time, as extra wear builds up, it becomes increasingly difficult to differentiate between a 0 and a 1. At the point where it becomes impossible, the block becomes unusable.

The lifetime of a block is not well known. Manufacturers rate MLC-based blocks as having a 10,000 P/E cycle lifetime; SLC-based chips, because they store only a bit per transistor, are rated much longer than expected [BD10].

One other reliability problem within flash is disturbance. When accessing a particular page within flash, it is possible that some bits get flipped in neighboring pages; such flips are known as read disturbs or program disturbs, depending on whether the page is being read or programmed, respectively.

## 44.5 From Raw Flash to Flash-Based SSDs

Given our basic understanding of flash chips, we now face our next task: how to turn a set of flash chips into something that looks like a storage device. Internally, an SSD consists of some number of flash chips (for persistent storage). An SSD also contains some amount of volatile (i.e., non-persistent) memory (e.g., SRAM); which is useful for caching and buffering as well as control logic to orchestrate device operation. See Agarwal et al for details [A08]; a simplified block diagram is seen in Figure 44.3 (page 595).

One of the essential functions of this control logic is to satisfy reads and writes, turning them into internal flash operations as needed. The flash translation layer, or FTL, provides this functionality. The FTL takes read and write requests on logical blocks (that comprise the device interface) and turns them into low-level read, erase, and program operations on the underlying physical blocks and pages (that capture the actual flash device). The FTL should accomplish this task with the goal of delivering excellent performance and high reliability.
