# 50.3 Improving the Protocol

The two problems above limited the scalability of AFS; each server CPU became the bottleneck of the system, and each server could only serve twenty clients without becoming overloaded. Servers were receiving too many TestAuth messages, and when they received Fetch or Store messages, spending much time traversing the directory hierarchy. Thus, the AFS designers faced with a problem:

> THE CRUX: HOW TO DESIGN A SCALABLE FILE PROTOCOL

How should one redesign the protocol to minimize the number of server interactions, i.e., how could they reduce the number of TestAuth messages? Further, could they design the protocol to make the server interactions efficient? By attacking both of these issues, a new protocol would result in a much more scalable version AFS.

# 50.4 AFS Version 2

AFSv2 introduced the notion of a callback to reduce the number of client/server interactions. A callback is simply a promise from the server to the client that the server will inform the client when a file that the client is caching has been modified. By adding this state to the system, the client no longer needs to contact the server to find out if cached file is still valid. Rather, notice the analogy to polling versus interrupts.

AFSv2 also introduced the notion of a file identifier (FID) (similar to the NFS file handle) instead of pathname. In AFS a copy of FID can specify which file was interested in. An FID contains a uniquifier (to enable reuse of the volume and file IDs when a file is deleted). Thus, instead of sending the pathname to the server and letting the server walk the desired file, the client would walk the pathname, one piece at a time, caching the results and hopefully reducing the load on the server.
