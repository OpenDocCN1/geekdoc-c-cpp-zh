# DISTRIBUTED SYSTEMS

For the server, code is also generated. The steps taken on the server
are as follows:

+   - **Unpack the message.** This step, called unmarshaling or deserialization, takes the information of the incoming message. The
function identifier and arguments are extracted.
- **Call into the actual function.** Finally! We have reached the point
where the remote function is actually executed. The RPC runtime
calls into the function specified by the ID and passes in the desired
arguments.
- **Package the results.** The return argument(s) are marshaled back
in a single reply buffer.
- **Send the reply.** The reply is finally sent to the caller.

There are a few other important to consider in a stub compiler.
The first is complex, i.e., how does one package and send
a complex data structure? For example, when one calls the `write()`
system, one passes in three arguments: an integer file descriptor, a
pointer to a buffer, and a size indicating how many bytes (starting at the
pinter) to be written. If an RPC package is passed a pointer, it needs
to be able to figure out how to interpret that pointer, and perform the
correct action. Usually this is achieved through well-known
types (e.g., `buffer_t`) that is used to pass chunks of data given a size,
which the RPC compiler understands, and by annotating the data structures enabling the compiler to know which bytes
need to be serialized.

Another issue is the organization of the server with regards
to concurrency. A simple server waits for requests in a simple loop,
and handles each request at a time. However, as you might have
gussed, this can be grossly inefficient; if one RPC blocks (e.g., on
I/O), server resources are wasted. Most servers are constructed in
sort of concurrent fashion. A common organization is a thread pool.
in this organization, a finite set of threads are created when the server
starts; when a message arrives, it is dispatched to one of these worker
threads, which then does the work of the RPC call, eventually replying;
during this time, a main thread keeps receiving other requests, and dispatches them to other workers. Such an organization enables concurrent execution within the server, thus increasing its utilization; the
standard costs arise as well, mostly in programming complexity, as the
RPC calls may now need to use locks and other synchronization primitives
to ensure their execution correct order.
