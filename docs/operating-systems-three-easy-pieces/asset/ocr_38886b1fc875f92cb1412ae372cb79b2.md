The slab allocator also goes beyond more segregated list approaches by keeping free objects on the lists in a pre-initialized state. Bonwick shows that initialization and destruction of data structures is costly [B94]; by keeping free objects in a particular list in their initialized state, the slab allocator avoids frequent initialization and destruction cycles per object and thus lowers overheads.

# Buddy Allocation

Because coalescing is critical for an allocator, some approaches have been designed around making coalescing simple. One example is found in the binary buddy allocator [K65].

In such a system, free memory is conceptually thought of as one big space of size 2ⁿ. When a request for memory is made, the search for free space recursively divides free space until a block that is large enough to accommodate the request is found (and a further split into two would result in a space that is too small). At this point, the requested block is returned to the user. Here is an example of a 64KB free space divided in the system for a 7KB block (Figure 17.8, page 193).

In the example, the leftmost 8KB block is allocated (indicated by the darker shade of gray) and returned to the user; note that this scheme can suffer from fragmentation, yet we are allowed to give out power-of-two sized blocks.

The beauty of buddy allocation is found in what happens when block is freed. When returning the 8KB block to the free list, the allocator checks whether the "buddy" 8KB is free; if so, it coalesces the two blocks into a 16KB block. The allocator then checks if the buddy of the 16KB block is still free; if so, it coalesces those two blocks. This recursive merging process continues until the tree, either restoring the entire free space or stopping when a buddy is found to be in.
