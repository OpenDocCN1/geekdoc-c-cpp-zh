# 43.3 How Much To Buffer?

This raises the following question: how many updates does LFS buffer before writing to disk? The answer, of course, depends on the disk itself, specifically how high the positioning overhead is in comparison to the transfer rate; see the FFS chapter for a similar analysis.

For example, assume positioning (i.e., rotation and seek overhead) before each write takes roughly $T_{position}$ seconds. Assume that the transfer rate is $R_{peak}$ MB/s, how much should LFS buffer before writing on a disk?

The way to think about this is that every time you write, the more you write, the better to write in order to *amortize* the cost? Thus, how much more do you have to write in order to achieving peak bandwidth? (obviously), and the closer you get to achieving peak bandwidth.

To obtain a concrete answer, let's assume we are writing out $D$ MB. The time to write out this chunk of data ($T_{write}$) is the positioning time $T_{position}$ plus the time to transfer $D$ ($\frac{D}{R_{peak}}$), or:

$$T_{write} = T_{position} + \frac{D}{R_{peak}} \quad (43.1)$$

And thus the effective rate of writing ($R_{effective}$), which is just the amount of data divided by the total time to write it:

$$R_{effective} = \frac{D}{T_{write} + \frac{D}{R_{peak}}} \quad (43.2)$$

What're interested in is getting the effective rate ($R_{effective}$) close to the peak rate. Specifically, we want the effective rate to be some fraction $F$ of the peak rate, where $\tilde{U} < F < 1$ (a typical $F$ might be 0.9, or 90% of the peak rate). In mathematical form, this means we want $R_{effective} = F \times R_{peak}$.

At this point, we can solve for D:

$$R_{effective} \frac{D}{T_{position} + \frac{D}{R_{peak}}} = F \times R_{peak} \quad (43.3)$$

$$D = F \times R_{peak} \times (T_{position} + \frac{D}{R_{peak}}) \quad (43.4)$$

$$D = (F \times R_{peak} \times T_{position}) + (F \times R_{peak} \times \frac{D}{R_{peak}}) \quad (43.5)$$

$$D = \frac{F}{1-F} \times R_{peak} \times T_{position} \quad (43.6)$$

Let’s do an example, with a disk with positioning time of 10 milliseconds and peak transfer rate of 100 MB/s; assume we want an effective bandwidth of 90% of peak ($F = 0.9$). In this case, $D = \frac{0.9}{0.7} \times 100$ MB/s $\times 0.01$ seconds = $9$ MB. Try different values to see how much we need to buffer in order to approach peak bandwidth. # 43.4 Problem: Finding Inodes

To understand how we find an inode in LFS, let us briefly review how to find an inode in a typical Unix file system such as FFS, or even the old Unix file system, finding inodes is easy, because they are organized in an array and placed at fixed locations.

The old Unix file system keeps all inodes at a fixed position of the disk. Thus, given an inode number and the start address, to find a particular inode, you can calculate its disk address simply by multiplying the inode number by the size of an inode, and adding the start address of the on-disk array; array-based indexing, given an inode number, is fast and straightforward.

Finding an inode number in FFS is only slightly more complicated, because FFS splits up the inode table into chunks and grows inodes within each chunk group. Thus, one must know how each chunk of inodes is and what the start addresses of each. After that, the calculations are also simple.

In LFS, life is more difficult. Why? Well, we’ve managed to scatter the inodes throughout the disk! Worse, we never overwrite in place, and the latest version of an inode (i.e., the one we want) keeps moving.

# 43.5 Solution Through Indirection: The Inode Map

To remedy this, the designers of LFS introduced indirection through a structure called the inode map (imap). The map takes an inode number as input and produces the disk address of the inode. Since inodes move, the imap must be updated. However, the imap is much smaller than the inodes themselves, so we can be more efficient with its updates.

The imap is an array of pointers to inodes. To find an inode, we first look it up in the imap to get its disk address, and then read the inode. Because the imap is small, we can keep it in memory, which reduces the need to read it from disk. When the imap is updated, we write the new imap to the disk just like any other data.

The inode map is the key to making LFS work. It allows us to scatter inodes across the disk for efficiency while still being able to find them quickly.
