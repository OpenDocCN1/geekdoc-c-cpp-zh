# Mechanism: Limited Direct Execution

In order to virtualize the CPU, the operating system needs to somehow share the physical CPU among many jobs seemingly running at the same time. The basic idea is simple: run one process for a little while, then run another one, and so forth. By time sharing the CPU in this manner, virtualization is achieved.

There are a few challenges, however, in building virtualization machinery. The first is performance: how can we implement virtualization without adding excessive overhead to the system? The second is control: how can we run processes efficiently while retaining control over the CPU? Control is particularly important to the OS, as it is in charge of resources; without control, a process could simply run forever and take over the machine, or access information that should not be allowed to access. Obtaining high performance while maintaining control is thus one of the central challenges in building an operating system.

> THE CRUX: How To Efficiently Virtualize The CPU With Control
The OS must virtualize the CPU in an efficient manner while retaining control over the system. To do so, both hardware and operating-system support will be required. The OS will often use a judicious bit of hardware-support to accomplish its work effectively.

## 6.1 Basic Technique: Limited Direct Execution

To make a program run fast as one might expect, not surprisingly OS developers can use a technique, which we can call limited direct execution. The "direct execution" part of the idea is simple: just run the program directly on the CPU. Thus, when the OS wishes to start a program running, it creates a process entry for it in a process list, allocates some memory for it, loads the program code into memory (from disk), allocates its entry point (i.e., the main() routine or something similar), jumps to it, and running the user's code. Figure 6.1 shows this basic direct execution protocol (without any limits, yet), using a normal call and return to jump to the program's main() and later back to the kernel. Sounds simple, no? But this approach gives rise to a few problems in our quest to virtual the CPU. The first is simple: if we just run a program, how can the OS sure the program doesn't do anything we don't want it to, while still running it efficiently? The second: when we are running and switching to another process, how does the operating system stop it from running and switching to another process, thus implementing the time sharing we require to virtualize the CPU?

In answering these questions, we'll get a much better sense of what is needed to virtualize the CPU. In developing these techniques, we'll also see where the "limited" part of the name arises from; without limits on running programs, the OS wouldn't be in control of anything and would be "just a library" — a very sad state of affairs for an aspiring operating system!

## 6.2 Problem #1: Restricted Operations

Direct execution has the obvious advantage of being fast; the program runs natively on the hardware CPU and executes as quickly as one would expect. But running on the CPU introduces a problem: what if the process wishes to perform some kind of restricted operation, such as issuing an I/O request to a disk, or gaining access to more system resources as CPU or memory?

A process must be able to perform I/O and some other restricted operations, but without giving the process complete control over the system. How can the OS and hardware work together to do so?

# ASIDE: WHY SYSTEM CALLS LOOK LIKE PROCEDURE CALLS

You may wonder why a call to a system call, such as open() or read(), looks exactly like a typical procedure call in C; that, if it looks just like a procedure call, how does the system know it's a system call, and do all the right stuff? The simple reason: it is a procedure call, but hidden inside that procedure call is the famous trap instruction. More specifically, when you call open() (for example), you are executing a procedure call into the C library therein, whereas for open() or any of the other system calls provided, the library uses an agreed-upon calling convention with the kernel to put arguments in well-known locations (e.g., on the stack, or in specific registers), puts the system-call number into a well-known location as well (again, onto the stack or a register), and executes the aforementioned trap instruction. The code in the library after the trap returns and returns control to the program that uses the system call. The parts of the C library that make system calls are hard-coded in assembled, as they need to carefully follow convention in order to process arguments and return values correctly, as well as execute the hardware-specific trap instruction. And now know you don't have to write assembly to trap into an OS; somebody has already written assembly for you.

One approach would simply be to let any process whatever it wants in I/O and other related operations. However, doing so would prevent the construction of many kinds of systems that are desirable. For example, if we wish to build a file system that checks permissions granting access to a file, we can't simply let any user process I Os to the disk; if we did, a process could simply read or write the entire disk and all protections would be lost.

Thus, the approach is to introduce a new processor mode, known as user mode; code that runs in user mode is restricted in what it can do. For example, when running in user mode, a process can't issue I/O requests; doing so would result in the processor raising an exception; the OS would then kill the process.

In contrast to user mode is kernel mode, the operating system (or kernel) runs in. In this mode, the kernel can do what it likes, including privileged operations such as issuing I/O requests and requesting all types of restricted instructions.

We are still left with a challenge: what should a user do when it wishes to perform some kind of restricted operation, such as reading from disk? To enable this, virtually all hardware provides the ability for user programs to perform.

> TIP: USE PROTECTED CONTROL TRANSFER
The hardware assists the OS by providing different modes of execution.
In user mode, applications do not have access to hardware.
In kernel mode, the OS has access to the full resources.
Special instructions to trap into the kernel and return-from-trap are also provided, as well as the OS to tell the hardware where the trap table resides. Most operating systems run a few hundred calls (see the POSIX standard for details); early Unix exposed a concise subset of around twenty.

To execute a call, a program must execute a special trap instruction. This instruction simultaneously jumps into the kernel and returns; once in the kernel, the system can now perform whatever operations are needed (if allowed). When finished, the OS calls a special return-from-trap instruction, which as you might expect, returns to the user program while simultaneously reducing level back to user mode.

The hardware needs to be a bit careful when executing a trap, in that it must make sure to save enough of the caller's registers in order to be able to return correctly when the OS issues the return-from-trap. On x86, the processor will push the program counter, flags, and a few other registers onto a per-process kernel stack; the return-from-trap will pop these values off the stack and resume execution of the user program (see the Intel manuals for details). Other hardware systems use different conventions, but the basic concepts are similar across platforms.

There is one important detail left out of this discussion: how does the trap know the calling process can't specify an address to jump to (as you would when making a procedure call); doing so would allow programs to jump anywhere in the kernel. Thus the kernel must carefully control what code executes upon a trap.

The kernel does so by setting up a trap table at boot time. When the machine boots up, it does so in privileged (kernel) mode, and thus to configure hardware as needed. One of the first things the OS does is to tell the hardware what to run when certain exceptional events occur. For example, what code should run when a disk interrupt takes place, or when a keyboard interrupt occurs, or when a program makes a system call?
