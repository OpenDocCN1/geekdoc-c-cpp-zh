# ASIDE: BELADY’S ANOMALY

Belady (of the optimal policy) and colleagues found an interesting reference stream that behaved unexpectedly [BFS69]. The memory-reference stream: 1, 2, 3, 4, 1, 5, 1, 2, 3, 4. The replacement policy they were studying was FIFO. The interesting part: how the cache rate when moving from a cache size of 3 to 4 pages.

In general, you would expect the cache hit rate to increase (get better) when the cache gets larger. But in this case, with FIFO, it gets worse! Calculate the hits and misses yourself and see. This odd behavior is referred to as Belady’s Anomaly (the catch in his co-authors).

Other policies, such as LRU, do not suffer from this problem. Can you prove why? It turns out, LRU has been known as a stack property [M70]. For algorithms with this property, a cache size of N+1 naturally includes the contents of a cache size of N. Thus, when increasing the cache size, hit rate will stay the same or improve. FIFO and thus are susceptible to anomalous behavior.

## 22.4 Another Simple Policy: Random

Another replacement policy is Random, which simply picks a random page to replace under memory pressure. Random has properties similar to FIFO; it is simple to implement, but it doesn't really try to be too intelligent in picking blocks to evict. Let's look at how Random does on our famous reference stream (see Figure 22.3). Of course, Random depends entirely on how lucky (or unlucky) Random gets in its choices. In the example, Random does a little better than FIFO, and a little worse than optimal. In fact, we can run the Random experiment thousands of times and determine how it does in general. Figure 22.4 shows how many Random achieves over 10,000 trials, each with a different random seed. As you can see, sometimes (just over 40% of the trace), Random is as good as optimal, achieving 6 hits on the example trace; sometimes it does much worse, achieving 2 hits or fewer. How Random depends on the luck of the draw.

## 22.5 Using History: LRU

Unfortunately, any policy as FIFO or Random is likely to have a common problem: it might kick out an important page, one that is to be referenced again. FIFO kicks the page that was first brought in; if this happens to be a page with important code or structures upon it, it gets thrown out, even though it will soon be backed in. Thus, FIFO, Random, and similar policies are not likely to approach optimal; something is needed.

As said with scheduling policy, to improve our cache at the future, we once again lean on the past and use history as our guide. For example, if a program has a page in the near past, it is likely to access it in the future.

One type of historical information a page-replacement policy could use *frequency*; if a page has been accessed many times, perhaps it should not be replaced as it clearly has some value. A more commonly-used property of a page is its *recency* of access; the more recently a page has been accessed, the more likely it is to be again.
