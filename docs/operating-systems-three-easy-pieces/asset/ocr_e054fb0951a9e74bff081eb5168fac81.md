NFS, in contrast, can only cache blocks in client memory; as a result, if a file (i.e., a file bigger than the local memory) is re-read, the NFS will need to re-fetch the entire file from the remote server. We also note that NFS in this case increases load, which has an impact on scale as well.

Third, note that sequential writes (of new files) perform similarly on both systems (8,9). AFS, in this case, will write to the local cached copy when the file is closed; the AFS client will force the writes to the server, as per the protocol. NFS will buffer writes in client memory, before forcing some blocks to the server to client-side memory pressure, but definitely writing them to the server when the file is closed, to preserve flush-on-consistency. You might think AFS would be slower, because it writes all data to disk. However, realize that it is writing to a local file system; those writes are first committed to the page cache, and only later (in the background) to disk, and AFS reaps the benefits of the client-side OS caching infrastructure to improve performance.

Fourth, note that AFS performs worse on a sequential overwrite (Workload 10). Thus far, we have assumed that the workloads are creating a new file; in this case, the file exists, and is overwritten. Overwriting is a particularly bad case for AFS, because the client fetches the old file in its entirety; to subsequently overwrite it. NFS, in contrast, will simply overwrite blocks and avoid the initial (useless) read.

Finally, workloads that access a small subset of data within large files perform much better than NFS (Workloads 7, 11).
