## Buddy Allocation

Because coalescing is critical for an allocator, some approaches have been designed around making coalescing simple. One example is found in the binary allocator [K65]. In such a system, free memory is conceptually thought of as one big space of size $2^n$. When a request for memory is made, the search for free space recursively divides space until a block large enough to accommodate the request is found (and a further split into two would result in a space that is too small). At this point, the requested block is returned to the user. Here is an example of free space divided in the system for 8KB block (Figure 17.8). In the example, the leftmost 8KB block is allocated (indicated by darker shade of gray) and returned to the user; note that this scheme can suffer from fragmentation, yet we are allowed to give out power-of-two sized blocks. The beauty of buddy allocation is found in what happens when block is freed. When returning the 8KB block to the free list, the allocator checks whether the "buddy" of 8KB is free; if so, it coalesces the two blocks into 16KB block. The allocator then checks if the buddy of 16KB block is still free; if so, it coalesces those two blocks. This recursive merging process continues until the tree either restores the entire free space or stopping when a buddy is found to be in.

The reason buddy allocation works so well is that it is simple to determine the buddy of a particular block. How, you ask? Think about the addresses of the blocks above. If you think carefully enough, you'll see that the address of each buddy differs by a single bit; which bit is determined by the level in the buddy tree. And thus you have a basic idea of how buddy allocation schemes work. For more detail, as always, see Wilson [W95].

## Other Ideas

One major problem with the approaches above is their lack of scaling. Specifically, searching lists can be quite slow. Thus, advanced allocators use more complex data structures to address these costs, trading simplicity for performance. Examples include balanced binary trees, AVL trees, or partially-ordered trees [W95].

Given that modern systems often have multiple processors and run multi-threaded workloads (something you'll learn about in great detail in the section on Concurrency), it is not surprising that a lot of effort has been spent making allocators work well on multiprocessor systems. Two wonderful examples are found in Berger et al. [B00] and Evans [E06]; check them out for details.

These are two of the thousands of ideas people have had over time about memory allocators; read on your own if you are curious. Read about how the glibc allocator works [S15], to give you a sense of what the real world is like

## 17.5 Summary

In this chapter, we have discussed the rudimentary forms of memory allocators. Such allocators exist everywhere, linked to every C program you write, as well as in the underlying OS which is managing memory for its own data structures. With many systems, there are many trade-offs to be made in building such a system, and the more you know about the exact workload presented to an allocator, the more you could tune it to work better for that workload. Making a fast, space-efficient, scalable allocator that works well for a broad range of workloads remains an on-going challenge in modern computer systems.
