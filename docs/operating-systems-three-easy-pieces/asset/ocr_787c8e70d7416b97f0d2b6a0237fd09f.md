# THE CRUX: HOW TO REDUCE FILE SYSTEM I/O COSTS

The simplest of operations like opening, reading, or writing a file incurs a huge number of I/O operations, scattered over the disk. What can a file system do to reduce the high costs of doing so many I/Os?

# 40.7 Caching and Buffering

As the examples above show, reading and writing files can be expensive, incurring many I/Os to the (slow) disk. To remedy what would clearly be a huge performance problem, file systems aggressively use memory (DRAM) to cache important blocks.

Imagine the open example above: without caching, every file would require at least two reads for every level in the file directory (one to read the inode of the directory in question, and at least one to read its data). With a long pathname (e.g., /1/2/3... /100/file.txt), the file system would literally perform hundreds of reads just to open the file!

Early systems then introduced a fixed-size cache to hold popular blocks. As in our discussion of virtual memory, strategies like LRU and different variants would decide which blocks to keep in cache. This fixed-size cache would usually be allocated at boot time to be roughly 10% of total memory.

This static partitioning of memory, however, can be wasteful; if the file system doesn't need 10% of memory at a given point in time? With the fixed-size approach above, unused pages in the file cannot be re-purposed for some other use, and thus to go waste.

Modern systems, in contrast, employ a dynamic partitioning approach. Specifically, many operating systems integrate virtual memory pages and file pages into a unified page cache [S00]. In this way, memory can be allocated more flexibly from virtual memory and file system, depending on what needs more memory at a given time.
