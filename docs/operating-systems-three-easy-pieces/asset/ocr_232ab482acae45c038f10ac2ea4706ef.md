# INTRODUCTION TO OPERATING SYSTEMS

Usually, on these old mainframe systems, one program ran at a time, as controlled by a human operator. Much of what you think a modern OS would do (e.g., deciding what to run jobs) was performed by this operator, if you were a smart developer, you would be nice to this operator, so that you could move your job to the front of the queue.

This mode of computing was known as batch processing, as a number of jobs were set up and then ran in a "batch" by the operator. Computers, as of that point, were not used in an interactive manner, because of cost: it was too simple to let a user sit in front of the computer and use it, as most of the time it would sit idle then, costing the facility hundreds of thousands of dollars per hour [BH100].

# Beyond Libraries: Protection

In moving beyond a simple library of commonly-used services, operating systems took on a central role in managing machines. One important aspect of this was the realization that code on behalf of the OS was special; it had control of devices and should be treated differently than normal application code. Why is this? Imagine if you allowed any program to read from anywhere on the disk; the notice of privacy goes out the window, and thus, implementing a file system (to manage your files) as a library makes little sense. Instead, something else was needed.

Thus, the idea of a system call was invented, pioneered by the Atlas computing system [K+61,78]. Instead of providing OS routines as a library (where you use a procedure call to access them), the idea was to add a special pair of hardware instructions and hardware state to make the transition into the OS more formal, controlled process.

The difference between a system call and a procedure is that a system call transfers (i.e., jumps) into the OS while simultaneously raising the hardware privilege. User applications in what is referred to as user mode which the hardware restricts what applications can do: for example, an application running in user mode cannot typically access the disk, access any physical memory, or send a packet on the network. When a system call is initiated (usually through a special instruction called a trap), the hardware transfers control to a pre-specified trap handler (that the OS sets up) and simultaneously raises the privilege level to kernel mode. In kernel mode, the OS has access to the hardware and can make more memory available to a program. When the OS is done servicing the request, or initiates an I/O request, it passes control back to the user via a special return-from-trap instruction, which reverts to user mode while simultaneously passing control back to where the application left off.
