# SCHEDULING: PROPORTIONAL SHARE

TIP: USE TICKETS TO REPRESENT SHARES
Of the most powerful (and basic) mechanisms in the design of lottery
(and stride) scheduling is that that of the ticket. The ticket is used to represent
a process’s share of the CPU in these examples, but can be applied much
more broadly. For example, in more recent work on virtual memory man-
gagement for hypervisors, Waldspurger shows how tickets can be used to
represent a guest operating system’s share of memory [W02]. Thus, if you
are ever in need of a mechanism to represent a proportion of ownership,
this concept just might... (wait for it) ... the ticket.

# 9.2 Ticket Mechanisms

Lottery scheduling also provides a number of mechanisms to manip-
ulate tickets in different and sometimes useful ways. One way is with
the concept of ticket currency. Currency allows a user with a set of tick-
to allocate tickets among their own owners in whatever currency they
like; the system then automatically converts currency into the
correct global value.

For example, users A and B have been given one hundred tickets.
User A is running two jobs, A1 and A2, and gives each five hundred tickets
(out of 1000) in A’s currency. User B is running one job and gives
10 tickets (out of 50) to 50 each in the global currency; similarly,
the system converts A1’s allocation from 500 each in A’s currency to B1’ntickets converted to 100 tickets. The ticket is then held over the
global currency (total 200) to determine job runs.

```
User A -> 50 (A’s currency) to A1 -> 50 (global currency)
-> 50 (A’s currency) to A2 -> 50 (global currency)
User B -> 10 (B’s currency) to B1 -> 100 (global currency)
```

Another mechanism is hand off its tickets to another process. With transfers, this ability
is especially useful in a client/server setting, where a client process sends
a message to the server it to do some on the client’s behalf.
To speed up the work, the client can pass the tickets to the server and
thus maximize the performance of the server while the server is handling
the client’s request. When finished, the server then transfers the
ticks back to the client and all as before.

Finally, ticket inflation can be a useful technique. With
inflation, a process can raise or lower the number of tickets it
out course, in a competitive scenario with processes that do not
trust another, this makes little sense; one greedy process could give
itself a vast number of tickets and take over the machine. Rather, inflation
can be applied in an environment where a group of processes trust one
another; in such a case, if one process knows it needs more CPU time,
it can boost its ticket value as a way to reflect that need to the system,
without communicating with any other processes.
