> TIP: MORE CONCURRENCY IS’T NECESSILY FASTER
If the scheme you design adds a lot of overhead (for example, acquiring and releasing locks frequently, instead of once), the fact that it is more concurrent may not be important. Simple schemes tend to work well, especially if they use costly routines. Adding more locks and complexity can be your downfall. All of that said, there is one way to really know: build both alternatives (simple but less concurrent, and but more concurrent) and measure how they do. In the end, you can't cheat on performance; your idea is either faster, or it isn't.

# 29.2 Concurrent Linked Lists

We examine a more complicated structure, the linked list. For simplicity, we'll omit the obvious routines that a list would have and just focus on concurrent insert; we'll leave it to the reader to look about lookup, delete, and so forth. 29.7 shows the code for this rudimentary data structure.

As you can see in the code, the simple code acquires a lock in the insert routine upon entry, and releases it upon exit. Small tricky issue arises if malloc() fails to allocate (a rare case); in this case, the code must release the lock before failing the insert.

This exceptional control flow has shown to be quite prone; a recent study of Linux kernel patches found that a huge fraction of bugs (nearly 40%) are found on rarely-taken code paths (indeed, this observation sparked some of our research, where we removed all memory-faulting paths from a Linux file system, resulting in a more robust system [S11]).

Thus, a challenge: we can rewrite the insert and lookup routines to maintain correctness under concurrent insert, but the case where the failure path also requires us to add the lock to unlock

The answer, in this case, is yes. Specifically, we can rearrange the code so that a lock only surrounds the actual critical section in the insert, and that a common exit is used in the lookup code. The former works because part of the insert actually does not need to be locked; assuming that malloc is thread-safe, we can call into it without worry of race conditions or other concurrency bugs. Only when updating the shared list does a lock need to be held. See Figure 29.8 for the details of these modifications.

As for the lookup routine, it is a simple transformation to jump out of the main search loop to a single return path. So doing so reduces the number of lock acquire/release points in the code, and decreases the chances of accidentally introducing bugs (such as forgetting to unlock before returning) into the code.

```c
// basic node structure
struct __node_t {
    int key;
    struct __node_t *next;
} node_t;

// list structure (one used per list)
struct __list_t {
    node_t *head;
    pthread_mutex_t lock;
} list_t;

void List_Init(list_t *L) {
    L->head = NULL;
    pthread_mutex_init(&L->lock, NULL);
}

int List_Insert(list_t *L, int key) {
    pthread_mutex_lock(&L->lock);
    node_t *new = malloc(sizeof(node_t));
    if (new == NULL) {
        perror("malloc");
        pthread_mutex_unlock(&L->lock);
        return -1; // fail
    }
    new->key = key;
    new->next = L->head;
    L->head = new;
    pthread_mutex_unlock(&L->lock);
    return 0; // success
}

int List_Lookup(list_t *L, int key) {
    pthread_mutex_lock(&L->lock);
    node_t *curr = L->head;
    while (curr) {
        if (curr->key == key) {
            pthread_mutex_unlock(&L->lock);
            return 0; // success
        }
        curr = curr->next;
    }
    pthread_mutex_unlock(&L->lock);
    return -1; // failure
}
```

# Scaling Linked Lists

Though we again have a basic list, it does not scale well. One technique that researchers have explored to enable more concurrency is something called hand-over-hand locking [MS04]. The idea is pretty simple: instead of having a single lock for the list, you instead add a lock per node. When traversing the list, the code first grabs the next node's lock and then releases the current node's.

> TIP: BE WARY OF LOCKS AND CONTROL FLOW
A general design tip, which is useful in concurrent code as well, is to be wary of control flow changes that lead to function returns, exits, or other error conditions. Because many functions will begin by acquiring a lock, allocating some memory, or doing similar operations, when errors arise, the code has to undo all of the state before returning, which is errorprone.

Conceptually, hand-over-hand locking makes some sense; it enables high degree of concurrency. However, in practice, the overhead of acquiring and releasing locks for each node is prohibitive. With very large lists, and a large number of threads, the concurrency enabled by ongoing traversals, performing an operation, and releasing it. Perhaps some kind of hybrid (where you grab a new lock every so node) would be worth investigating.

# 29.3 Concurrent Queues

As you know by now, there is always a standard method to make a concurrent data structure: add a lock. For a queue, we will skip that approach, assuming you can figure it out.

Instead, we take a look at a slightly more concurrent queue designed by Michael and Scott [MS98]. The data structures and code used for this queue are found in Figure 29.9 on the following page.

If you study this queue carefully, you'll notice that there are two locks, one for the head of the queue, and one for the tail. The goal of these two locks is to enable concurrency of enqueue and dequeue operations. In the common case, the enqueue routine will only access the tail lock, and dequeue only the head lock.

One trick used by Michael and Scott is to add a dummy node (allocated in the queue initialization code); this dummy separates the head and tail operations. Study the code, or better yet, type it in, run it, and measure it, to understand how it works.

Queues are commonly used in multi-threaded applications. However, the type of queue used (with just locks) often does not meet the needs of such programs. A more fully developed bounded queue, that enables a thread to wait if the queue is empty or overly full, is the subject of intense study in the next chapter on condition variables. Watch for it!
