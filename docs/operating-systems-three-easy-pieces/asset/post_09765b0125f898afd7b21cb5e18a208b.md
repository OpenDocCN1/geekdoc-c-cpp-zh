
# TIP: BE CAREFUL SETTING THE TIMEOUT VALUE

As you can probably guess from the discussion, setting the timeout value correctly is an important aspect using timeouts to retry messages. If the timeout is too small, the server will re-send messages needlessly, wasting CPU time on the sender and network resources. If the timeout is too large, the server waits too long to retry and thus perceives performance on the server is reduced. The “right” value, from the perspective of a single client, is to wait just long enough to detect packet loss no longer.

However, there are often more than just a single client and server in a distributed system, as we will see in future chapters. In a scenario with many clients sending to a single server, packet loss at the server may be an indicator that the server is overloaded. True, clients might retry in a different adaptive manner; for example, the first time, a client might increase its timeout value to a higher amount, perhaps twice as much as the original value. An exponential back-off scheme, pioneered in the early Aloha network and adopted in early Ethernet [A70], avoids situations where resources are being overloaded by an excess of re-sends. Robust systems strive to avoid of this nature.

The receiver uses its counter as the expected value for the ID of the incoming message from sender. If the ID of the received message (N) matches the receiver’s counter (also N), it acknowledges the message and passes it to the application; in this case, the receiver concludes this is the first time this message has been received. The receiver increments its counter (to (N+1), and waits for the next message.

If the ack is lost, the server’s counter is higher (N+1), and thus the receiver knows it has already received this message. This time, the receiver re-sends N and acknowledges it but does not pass it up to the application. In this simple manner, sequence counters can be used to avoid duplicates.

The most commonly used reliable communication layer is known as TCP/IP, or just TCP for short. TCP has a great deal more sophistication than what we describe above, including handling congestion in the network [Vj88], multiple outstanding requests, and hundreds of other tweaks and optimizations. Read more about it if you’re curious; better yet, take a networking course and learn that material well.

## 48.4 Communication Abstractions

Given a messaging layer, we now approach the next question in this chapter: what abstraction of communication should we use when building a distributed system?

The systems community developed a number of approaches over the years. One body of work OS abstractions and extended them to operate in a distributed environment. For example, **distributed shared memory (DSM)** systems enable processes on different machines to share a large, virtual address space [LH89]. This abstraction turns a distributed computation into something that looks like a multi-threaded application; the only difference is that threads run on different machines instead of different processes within the same machine.

The most DSM systems work through the virtual memory system of the OS. When a page is accessed on one machine, two things can happen. In the first (best), the page is already local on the machine, and thus the page is fetched quickly. In the second case, the page is on some other machine. A page fault occurs, and the page handler sends a message to some other machine to fetch the page, install it in the page of the requesting process, and continue execution.

This approach is not widely used today for a number of reasons. The largest problem for DSM is how it handles failures. Imagine, for example, if a machine fails; what happens to the pages on that machine? What if the data structures of the distributed computation are spread across the entire address space? In this case, parts of these structures would suddenly become unavailable. Dealing with parts of your address space missing is hard; imagine a linked list where a “next” pointer points into a portion of the address space that is gone. Yikes!

A further problem is performance. One usually assumes, when writing, access to memory is cheap. In DSM systems, some accesses are inexpensive, but others cause page faults and expensive fetches from remote machines. Thus, programmers of DSM systems have to be careful about computations that almost no communication occurred at all, defeating the point of such an approach. Though much research was performed in this space, there was little impact; nobody builds reliable distributed systems using DSM today.

## 48.5 Remote Procedure Call (RPC)

While abstractions turned out to be a poor choice for building distributed systems, programming language (PL) abstractions made much more sense. The most dominant abstraction is based on the idea of a **remote procedure call**, or RPC for short [BN84].¹

Remote procedure call packages have a simple goal: to make the process of executing code on a remote machine as simple and straightforward as calling a local function. Thus, to a client, a procedure call is made, and some later time, the results are returned. The server defines some routines that it wishes to export. The rest of the magic is handled by the RPC system, which in general has two pieces: a *stub generator* (sometimes called a *protocol compiler*), and the *run-time library*. We'll now take a look at each of these pieces in more detail.

> In modern programming languages, we might instead say *remote method invocation (RMI)*, but which these languages anyway, with all of their fancy objects?

### Stub Generator

The stub generator’s job is simple: to remove some of the pain of packing function arguments and results into messages by automating it. Numerous benefits are aside: one avoids, the simple mistakes that occur in writing such code by hand; further, a stub compiler can perhaps optimize code and thus improve performance.

The input to such a compiler is the set of calls a server wishes to export. Conceptually, it could be something simple as this:

```
interface {
    int func1(int arg1);
    int func2(int arg1, int arg2);
}
```

The stub generator takes an interface like this and generates a few pieces of code. For the client, a client stub is generated, which contains each of the functions specified in the interface; a client program wishing to use this RPC service would link with this client stub and call into it to make RPCs.

Internally, each of the functions in the client stub do all of the work needed to perform the remote call. To the client, the code just appears as a function call func(x); internally, the code in the client stub func(y) does this:

- Create a message buffer. A message buffer is usually just a contiguous array of bytes of some size.
- Pack the needed information into the message buffer. This information includes some kind of identifier for the function to be called, as well as all of the arguments that the function needs (e.g., in our example, one integer for func1). The process of putting all of this information into a contiguous buffer is sometimes referred to as marshalling of arguments or serialization of the message.
- Send the message to the destination RPC server. The communication with the RPC server, and all of the details required to make it operate correctly, are handled by the RPC run-time library, described further below.
- Wait for the reply. Because function calls are usually synchronous, the client will wait for its completion.
- Unpack return code and other arguments. If the function returns a single return code, this process is straightforward; however, complex functions might return more complex results (e.g., a list), and thus the stub might need to unpack those as well. This step is also known as unmarshalling or deserialization.
- Return to the caller. Finally, just from the client stub back into the client code.
