TIP: USE RANDOMNESS

One of the most beautiful aspects of lottery scheduling is its use of **randomness**. When you have to make a decision, using such a randomized approach is often a robust and simple way of doing so.

Random approaches have at least three advantages over more traditional decisions. First, random often avoids strange corner-behavior that a more traditional algorithm may have trouble handling. For example, consider the LRU replacement policy (studied in more detail in a chapter on virtual memory); while often a replacement algorithm, LRU attains worst-case performance for some cyclic-sequential workload. Random, on the other, has no worst case.

Second, random is lightweight, requiring little to track alternatives. In a traditional fair-share scheduling algorithm, tracking how much CPU each process requires involves per-process accounting, which must be updated after running each process. Doing so randomly necessitates only the minimal of per-process state (e.g., the number of tickets each has).

Finally, random can be quite fast. As long as generating a random number is quick, making the decision is also, and thus random can be used in a number of places where speed is required. The faster the need, the more random tends towards pseudo.

TIP: USE TICKETS TO REPRESENT SHARES

Of the most powerful (and basic) mechanisms in the design of lottery (and stride) scheduling is that that of the ticket. The ticket is used to represent a process’s share of the CPU in these examples, but can be applied much more broadly. For example, in more recent work on virtual memory management for hypervisors, Waldspurger shows how tickets can be used to represent a guest operating system’s share of memory [W02]. Thus, if you are ever in need of a mechanism to represent a proportion of ownership, this concept just might... (wait for it) ... the ticket.

## 9.2 Ticket Mechanisms

Lottery scheduling also provides a number of mechanisms to manipulate tickets in different and sometimes useful ways. One way is with the concept of ticket currency. Currency allows a user with a set of tickets to allocate tickets among their own owners in whatever currency they like; the system then automatically converts currency into the correct global value.

For example, users A and B have been given one hundred tickets. User A is running two jobs, A1 and A2, and gives each five hundred tickets (out of 1000) in A’s currency. User B is running one job and gives 10 tickets (out of 50) to 50 each in the global currency; similarly, the system converts A1’s allocation from 500 each in A’s currency to B1 tickets converted to 100 tickets. The ticket is then held over the global currency (total 200) to determine job runs.

```
User A -> 50 (A’s currency) to A1 -> 50 (global currency)
-> 50 (A’s currency) to A2 -> 50 (global currency)
User B -> 10 (B’s currency) to B1 -> 100 (global currency)
```

Another mechanism is hand off its tickets to another process. With transfers, this ability is especially useful in a client/server setting, where a client process sends a message to the server it to do some on the client’s behalf. To speed up the work, the client can pass the tickets to the server and thus maximize the performance of the server while the server is handling the client’s request. When finished, the server then transfers the tickets back to the client and all as before.

Finally, ticket inflation can be a useful technique. With inflation, a process can raise or lower the number of tickets it has of course, in a competitive scenario with processes that do not trust another, this makes little sense; one greedy process could give itself a vast number of tickets and take over the machine. Rather, inflation can be applied in an environment where a group of processes trust one another; in such a case, if one process knows it needs more CPU time, it can boost its ticket value as a way to reflect that need to the system, without communicating with any other processes.

## 9.3 Implementation

Probably the most amazing about lottery is the simplicity of its implementation. All you need a random generator to pick the winner, a data structure to track the processes, and a way to walk the list.

To make this process most efficient, it might generally be best to organize the list in sorted order, each with the highest tickets to the lowest. The ordering does not affect the correctness of the algorithm; however, it does ensure in general that the fewest number of list iterations are taken, especially if there are a few processes that possess most of the tickets.

To make the dynamics of lottery scheduling more understandable, we now perform a brief study of the completion time of two jobs competing against one another, each with the same number of tickets (100) and run (R, which we will vary).

In this scenario, we'd like for each job to finish at roughly the same time, due to the randomness of lottery scheduling, sometimes one job finishes before the other. To quantify this difference, we define a simple unfairness metric, $U$ which is simply the first job divided by the time that the second job completes. For example, if $R = 10$, and the first job finishes at 10 (and the second job at 20), $U = 10/20 = 0.5$. When both jobs finish nearly the same time, $U$ will be close to 1. In this scenario, that our goal is: a perfectly fair scheduler would achieve $U=1$.

Figure 9.2 plots the unfairness as the length of the two jobs ($R$) is varied from 1 to 1000 over thirty trials (results are generated by the simulator provided at the end of the chapter). As you can see from the graph, when the job length is not very long, average unfairness can be quite severe. As the jobs run for a significant number of time slices does the lottery scheduler approach the desired outcome.
