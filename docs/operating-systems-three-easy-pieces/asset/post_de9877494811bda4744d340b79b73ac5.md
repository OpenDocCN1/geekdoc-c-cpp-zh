> ASIDE: DATA STRUCTURE — THE OPEN FILE TABLE
Each process maintains an array of descriptors, each of which refers to an entry in the system-wide open file table. Each entry in this table tracks under which the file descriptor refers to, the current offset, and other relevant details such as whether the file is readable or writable.

## 39.5 Reading And Writing, But Not Sequentially

Thus far, we've discussed how to read and write files, all access has been sequential; that is, we have either read a file from the beginning to the end, or written a file out of order.
Sometimes, however, it is useful to be able to read or write to a specific offset within a file; for example, if you build an index over a text and use it to lookup a specific word, you may end up reading from random offsets within the document. To do so, we use lseek() system call.

```
off_t lseek(int fd, off_t offset, int whence);
```

The first argument is familiar (a file descriptor). The second argument is the offset, which positions the file offset to a particular location within the file. The third argument, called whence for historical reasons, determines exactly where the seek is performed. From the man page:

- If whence is SEEK_SET, the offset is set to offset bytes.
- If whence is SEEK_CUR, the offset is set to its current location offset bytes.
- If whence is SEEK_END, the offset is set to the size of the file offset bytes.

As you can tell from this description, for each file process opens, the OS tracks a "current" offset, which determines where the next read or write will begin from or writing to the file. Thus, part of the abstraction of an open file is that it has a current offset, which is updated in two ways. First is when a read or write of N bytes takes place. N is added to the current offset; each read or write updates the offset as specified. The second is explicitly with lseek, which changes the offset as specified above.

The offset, as you might have guessed, is kept in that struct file, as referenced from the struct proc. Here is a (simplified) definition of the structure:

```
struct file {
  int ref;
  char readable;
  char writable;
  struct inode *inode;
  uint offset;
};
```

ASIDE: CALLING lseek() Does Not Perform A DISK SEEK
The poorly-named system call lseek() confuses many students trying to understand disks and how the file systems atop them. Do not confuse the two! The lseek() call simply changes a variable in OS memory that tracks, for a particular process, at which its next read will start. A seek occurs when a read or write is issued to the disk is not on the same track as the last, and necessitates a head movement. Making this even more confusing is the fact that calling lseek() to read or write from/to random parts of a file, then reading/writing to these random parts, will indeed lead to more disks. Thus, calling lseek() can lead to a seek in an upcoming read or write, but does not cause any I/O to occur itself.

As you can see in the structure, the OS can use this to determine whether the file is readable or writable (or both), underlying file it refers to (pointed by the struct inode ip), and the current offset (off). There is also a reference count (ref), which we will discuss further.

These file structures represent all of the currently open files in the system; together, they are sometimes referred to as the open file table. The xv kernel keeps these as an array as well, with one lock per entry, as shown here:

```
struct {
    struct spinlock lock;
    struct file[NFILE];
} ftable;
```

Let's make this a bit clearer with a few examples. First, let's track a process that opens a file (size of 300 bytes) and reads it by calling the read() system call, each time reading 100 bytes. Here is a trace of the relevant system calls, along with the values returned by each system call, and the value of the current offset in the file table for this file access:

| System Calls | Return Code | Current Offset |
|---|---|---|
| fd = open("file", O_RDONLY) | 3 | 0 |
| read(fd, buffer, 100) | 100 | 100 |
| read(fd, buffer, 100) | 100 | 200 |
| read(fd, buffer, 100) | 100 | 300 |
| read(fd, buffer, 100) | 0 | 300 |
| close(fd) | 0 | - |

There are a couple of items to note from the trace. First, you can see how the current offset gets initialized to zero when the file is opened. Next, you can see how it is incremented with each read() by the process; this makes it easy for a process to just keeping calling read() to get the next chunk of the file. Finally, you can see how at the end, an attempted read() past the end of the file returns zero, indicating to the process that it has read the file in its entirety.

Second, let's trace a process that opens the same file twice and issues a read to each of them.

| System Calls | Return Code | OFT[10] Offset | OFT[11] Offset |
| --- | --- | --- | --- |
| fd1 = open("file", O_RDONLY) | 3 | 0 | 0 |
| fd2 = open("file", O_RDONLY) | 4 | 0 | 0 |
| read(fd1, buffer, 100) | 100 | 100 | 100 |
| read(fd2, buffer, 100) | 100 | 100 | 100 |
| close(fd1) | 0 | | 100 |
| close(fd2) | 0 | | |

In this example, two file descriptors are allocated (3 and 4), and each refer to a different offset in the open table (in this example, entries 10 and 11, as shown in the table heading; OFT stands for Open File Table). If you trace through what happens, you can see how each current offset is updated.

In one final example, a process uses lseek() to position the offset before reading; in this case, only a single file table entry is needed (as the first example).

| System Calls | Return Code | Current Offset |
| --- | --- | --- |
| fd = open("file", O_RDONLY) | 3 | 0 |
| lseek(fd, 0, SEEK_SET) | 200 | 200 |
| read(fd, buffer, 50) | 50 | 250 |
| close(fd) | 0 | |

Here, the lseek() sets the current offset to 200. The sub-read() then reads the next 50 bytes, and updates the current offset accordingly.

## 39.6 Shared File Table Entries: fork() and dup()

In many cases (as in the examples above), the mapping of file descriptor to an entry in the open table is a one-to-one mapping. For example, when a process runs, it might decide to open a file, and then close it; in this example, each will have a unique entry in the open file table. Even if some process reads the same file at the same time, each has its own offset. In this way, reading or writing a file is independent, and each has its own offset while it accesses the file.

However, there are a few interesting cases where the open file table is shared. One of those cases occurs when a parent process creates a child and waits for fork(). Figure 39.2 shows a small snippet in which a parent creates a child and waits for it to complete. The child adjusts the offset via a call to lseek() and exits.

```
int main(int argc, char *argv[]) {
    int fd = open("file.txt", O_RDONLY);
    assert(fd >= 0);
    int rc = fork();
    if (rc == 0) {
        rc = lseek(fd, 0, SEEK_SET);
        printf("child: %d\n", rc);
    } else if (rc > 0) {
        (void) wait(NULL);
        printf("parent: %d\n", (int)lseek(fd, 0, SEEK_CUR));
    }
    return 0;
}
```

Figure 39.2: Shared/Child File Table Entries (fork-seek.c)

When we run this program, we see the following output:

```
prompt> ./fork-seek
child: 10
parent: 10
prompt>
```

Figure 39.3 shows the relationships that connect each process's private descriptor array, the shared open file table entry, and the reference from it to the underlying file-system inode. Note that we finally use of the reference count here. When a file table is shared, its reference count is incremented; only when both processes close the file (or exit) will the entry be removed.
Sharing file table entries between parent and child is occasionally useful. For example, if you create a number of processes that are cooperatively working on a task, they can write to the same output file without any extra coordination. For more on what is shared by processes when fork() is called, please see the man pages.
