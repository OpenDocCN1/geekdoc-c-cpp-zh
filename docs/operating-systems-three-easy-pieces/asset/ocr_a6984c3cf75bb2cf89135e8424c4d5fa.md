Although you might not understand this example fully at the moment (and we'll learn a lot about it in later chapters, in the section of the book on concurrency), the basic idea is simple. The main program creates two threads using pthread_create(). You can think of a thread as a function running within the same memory space as other functions, with more than one of active at a time. In this example, each thread running in a routine called worker(), in which it increments a counter in a loop for loops number.

Below is a transcript of what happens when we run this program with the input value for the loops set to 1000. The value of loops determines how many each of the workers will increment the counter in a loop. When the program is run with the value of loops set to do you expect the final value of counter to be?

```
prompt> gcc -o thread.c -Wall -pthread
prompt> ./thread 1000
Initial value : 0
Final value : 2000
```

As you probably guessed, when the two threads are finished, the final value of the counter is 2000, as each thread increment the counter 1000 times. Indeed, when the input value of loops set to N, we would expect the final output of the program to be 2N. But life is not so simple, as it turns out. Lets run the same program, but with higher values for loops, and see what happens:

```
prompt> ./thread 100000
Initial value : 0
Final value : 143012 // huh??
prompt> ./thread 100000
Initial value : 0
Final value : 137298 // what the??
```

In this run, when we give an input value of 100,000, instead of getting a final value of 200,000, Then when we run the program a second time, we not only get the wrong value, but also a different value than the last time. If you run the program over and over with high values of loops, you may find that sometimes you get the right answer! Why is this happening?
