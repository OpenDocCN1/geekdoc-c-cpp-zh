# ASIDE: COMPUTING THE “AVERAGE” SEEK

In many books and papers, you will see average disk-seek time cited as being roughly one-third of the full seek time. Where does this come from?

It turns out from a simple calculation based on average seek distance, not time. Imagine the disk as a set of tracks, 0 to $N$. The seek distance between any two tracks $x$ and $y$ is thus computed as the absolute value of the difference between them: $|x - y|$.

To compute the average seek distance, all you need to do is first add all possible seek distances:

```
$$\sum_{x=0}^{N}\sum_{y=0}^{N}|x - y|$$ (37.4)
```

Now, divide this by the number of different seeks: $N^2$. To compute the sum, we'll just use the integral:

```
$$\int_{x=0}^{N}\int_{y=0}^{N}|x - y|dydx$$ (37.5)
```

To compute the inner integral, let's break out the absolute value:

```
$$\int_{y=0}^{x}(x - y)dy + \int_{y=x}^{N}(y - x)dy$$ (37.6)
```

Solving this leads to $(xy - \frac{1}{2}y^2)|_{y=0}^{x} + (\frac{1}{2}y^2 - xy)|_{x}^{N}$ which can be simplified to $(x^2 - Nx + \frac{1}{2}N^2)$. Now we have to compute the outer integral:

```
$$\int_{x=0}^{N}(x^2 - Nx + \frac{1}{2}N^2)dx$$ (37.7)
```

which results in:

```
$$\frac{1}{3}x^3 - \frac{N}{2}x^2 + \frac{N^2}{2}x|_{0}^{N} = \frac{N^3}{3}$$ (37.8)
```

Remember that we still have to divide by the total number of seeks $(N^2)$ to compute the average seek distance: $(\frac{N^3}{3})/(N^2) = \frac{1}{3}N$. Thus the average seek distance on a disk, over all possible seeks, is one-third of the full seek. And now when you hear that an average seek is one-third of a full seek, you'll know where it came from.

## 37.5 Disk Scheduling

Because of the cost of I/O, the OS has historically played a role in deciding the order of I/Os to the disk. More specifically, given a set of I/O requests, the **disk scheduler** examines the requests and decides which one to schedule next [SCL90, JW91].

Unlike job scheduling, where the length of each job is usually unknown, with disk scheduling, we can make a good guess at how long a "job" (i.e., request) will take. By estimating the possible rotational delay of a request, the disk scheduler can know how long each request will take, and thus (greedily) pick the one that will take the least time to service first. Thus, the disk scheduler will try to follow the principle of SJF (shortest job first) in its operation.

### SSTF: Shortest Seek Time First

One early disk scheduling approach is known as **shortest-seek-time-first (SSTF)** (also called *shortest-seek-first* or SSF). SSTF services the queue of I/O requests by track, picking requests on the nearest track to complete. For example, assuming the current position of the head is over the inner track, track 1 and 22 (outer track), we would then issue the request to 21 first, wait for it to complete, and then issue the request to 2 (Figure 37.7).

SSTF works well in this example, however, SSTF is not a panacea, for the following reasons. First, the drive geometry is not available to the host OS; rather, it sees an array of blocks. Fortunately, this problem is easily fixed. Instead of SSTF, an OS can implement **nearest-block-first (NBF)**, which schedules the request with the nearest block address next.

# Elevator (a.k.a. SCAN or C-SCAN)

The answer to this query was developed some time ago (see [CKR72] for example)

SCAN has a number of variants, all of which do about the same thing. For example, Coffman et al., introduced F-SCAN, which freezes the queue to be accessed when it is doing a sweep [CKR72]; this action places requests that come during the sweep into a queue to be serviced later. By avoiding starvation of far-away requests, by delaying the servicing of late-arriving requests (or nearer by requests).

**C-SCAN**

C-SCAN is another common variant, short for Circular SCAN. Instead of sweeping in both directions across the disk, the algorithm only moves from outer-to-inner, and then returns to the outer track to begin again. Doing so is a bit fairer to the middle tracks, i.e., after servicing the outer track, SCAN back-and-forth passes through the middle twice before coming back to the outer track again.

For reasons that should be clear, the SCAN algorithm (and its cousins) is sometimes referred to as the *elevator* algorithm, because it behaves like an elevator which is going up or down and just not servicing requests to floors based on which floor is closer. Imagine how annoying it would be if you were going down from floor 10 to 1, somebody got on at 3 and pressed 4, and the elevator went up to 4 because it was "closer" than 1! As you can see, the elevator algorithm, when used in real life, prevents from taking place in elevators. In disks, it prevents starvation.

Another related problem performed by disk schedulers is I/O merging. For example, imagine a series of requests to blocks 33, then 8, 34, as in Figure 37.8. In this case, the scheduler should merge the requests for 33 and 34 into a single-block request; any reordering that the disk is performed over the merged requests. Merging is particularly important at the OS level, as it reduces the number of requests sent to the disk and thus lowers overhead.
