# 43.8 What About Directories?

Thus far, we've simplified our discussion a bit by only considering indices and data blocks. However, to access a file in a file system (such as /home/remzi/foo, one of our favorite file names), some directories must be accessed too.

Fortunately, directory structure is basically identical to classic UNIX file systems, in that a directory is just a collection of (name, inode number) mappings. For example, when creating a file on disk, LFS must create a new inode, as well as the data block and its inode to refer to this file. Remember that LFS will do so sequentially on the disk (after buffering the updates for some time). Thus, creating a file foo in a directory would lead to the following structures:

| b[0];A0 | (foo, k) | b[0];A2 | m[k];A1 |
| --- | --- | --- | --- |
| D_k | l[k] | D_dir | l[dir] m[dir];A3 |
| A0 | A2 | A3 | imap |

The piece of the inode map contains the information for the location of both the directory dir as well as the newly-created file f. Thus, when accessing foo (with inode number k), you would first look in the inode map (usually cached in memory) to find the location of the directory dir (A3); then you read the directory inode, which gives you the location of the directory data (A2); reading this block gives you the name-to-inode mapping of (foo, k). You then consult the inode map again to find the location of inode number k (A1), and finally read the desired data block at address A0.

There is one other serious problem in LFS, the recursive update problem [Z+12]. The problem arises in any file system that never updates in place (such as LFS), but rather moves updates to new locations on the disk.

Specifically, when we hadn't been an inode, its location on disk changes would have also entailed an update to the directory that points to this file, which would have mandated a change to the parent of that directory, and so on, all way up the file system tree.

LFS avoids this with the inode map. Even though the location of an inode may change, the change is never reflected in the directory itself; rather, the map structure is updated while the directory holds the same name-to-inode mapping. Thus, through indirect, LFS avoids the recursive update problem.
