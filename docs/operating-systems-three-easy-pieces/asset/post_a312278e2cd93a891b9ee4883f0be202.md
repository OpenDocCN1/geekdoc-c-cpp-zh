Because checksums are usually small (e.g., 8 bytes), and disks can only be written in sector-sized chunks (512 bytes) or multiples thereof, one problem arises that is to avoid the above layout. One solution employed by drive manufacturers is to format the drive with 520-byte sectors; an extra 8 bytes per sector can be used to store the checksum. In disks that don't have such functionality, the file system must figure out a way to store the checksums packed into 512-byte blocks. One such possibility is as follows:

| C(0) | D0 | C(1) | D1 | C(2) | D2 | C(3) | D3 | C(4) | D4 |

In this scheme, the $n$ checksums are stored together in a sector, followed by $n$ data blocks, followed by another checksum sector for the next $n$ blocks, and so forth. This approach has the benefit of working on all disks, but can be less efficient; if the file system, wants, to overwrite block $D1$, it has to read the checksum sector containing $C(D1)$, update $C(D1)$ in it, and then write out the checksum sector and new data block $D1$ (thus, one read and two writes). The earlier approach (of one checksum sector) just performs a single write.

# 45.4 Using Checksums

With a layout decided out, we can now proceed to understand how to use the checksums. When reading a block $D$ the client (e.g., file system or storage controller) also reads its checksum from disk $C(D)$, which we call the *stored checksum* (hence the subscript $C_s$). The client then computes the checksum over the retrieved block $D$, which we call the *computed checksum* $C_c$. At this point, the client compares the stored and computed checksum: if they are equal (i.e., $C_c(D) = C_s(D)$), the data has not been corrupted, and can be safely returned to the user. If they do not match (i.e., $C_c(D) \neq C_s(D)$), this implies the data has changed since the time it was stored (since the stored checksum reflects the value of that data at time). In this case, we have a corruption, which our checksum has helped to detect.

Given a corruption, the natural question is what we should do about it? If the storage system has a redundant copy, the answer is: try to use it instead. If the storage system has no such copy, the answer is to return an error. In either case, realize that corruption detection is not a magic bullet; if there is no other way to handle the non-corrupted data, you are simply out of luck.

# 45.5 A New Problem: Misdirected Writes

The basic scheme described above works well in the general case of corrupted blocks. However, modern disks have a couple of unusual failure modes that require different solutions.

The first failure mode of interest is called a misdirected write. This arises in disk and RAID controllers which write the data to disk correctly, except in the wrong location. In a single-disk system, this means that the disk write block $D_x$ not to address $x$ (as desired) but rather to address $y$ (thus "corrupting" $D_y$), in addition, within a multi-disk system, the controller may also write $D_{i,j}$ not to address $x$ of disk but rather to some other disk $j$. # 45.6 One Last Problem: Lost Writes

Unfortunately, misdirected writes are not the last problem but we will address. Specifically, modern storage devices also have an issue known as a lost write, which occurs when the device informs the layer that a write has completed but it never persists; thus, what remains is the old contents of the block rather than the updated contents.
The obvious question here is: which of our checksuming strategies from above (e.g., basic checksums, or physical identity) help to detect lost writes? Unfortunately, the answer is no: the old block likely has a matching checksum, and the physical ID used above (disk number and block offset) will also be correct. This is our final problem:

## CRUX: HOW TO HANDLE LOST WRITES
How should a storage system or disk controller detect lost writes? What additional features are required from the checksum?

There are a number of possible solutions that can help [K+08]. One classic approach [BS04] is to perform a write verify or read-after-write; by immediately rewriting the data after a write, a system can ensure that the data indeed reaches the disk surface. This approach, however, is quite slow, doubling the number of IO needed to complete a write.
Some systems add a checksum elsewhere in the system to detect lost writes. For example, Sun's Zabyte File System (ZFS) includes a checksum in each file inode and indirect block for every block included within a file. Thus, even if the write to a data block itself is lost, the checksum within the inode will not match the data only. Only if the writes to both the inode and the data are simultaneously will such a scheme fail, an unlikely (but unfortunately, possible!) situation.

# 45.7 Scrubbing

Given all of this discussion, you might be wondering: when do these checksums actually get checked? Of course, some amount of occurs when data is accessed by applications, but most data is rarely accessed, and thus would remain unchecked. Unchecked data is problematic for a reliable storage system, as bit rot could eventually affect all copies of particular data.

To remedy this problem, many systems utilize disk scrubbing of [K+08]. By periodically reading every block of the system, and checking checksums are still valid, the disk system can reduce the chances that all copies of certain data become corrupted. Typical systems scan on nightly or weekly basis.

# 45.8 Overheads Of Checksumming

Before closing, we now discuss the overheads of checking for data. There are two distinct kinds of overheads, as is common in computer systems: space and time. Space overhead comes in two forms. The first is on disk (or storage medium) itself; each stored checksum takes up room on the disk, which can no longer be used for data. A typical ratio might be 8-byte checksum per 4 KB block, for 0.19% on-disk space overhead.

The second type of overhead is memory of the system. When accessing data, there must now room in memory for the checksums as well as the data itself. However, if the system simply checks the checksum and then discards it once, this overhead is short-lived and not much of concern. Only if checksums are kept in memory (for an added level of protection against memory corruption [Z+13]) will this small overhead be observable.

While space overheads are small, the overheads induced by checksumming over each block, when the data is accessed (to determine the value of the stored checksum) and when it is accessed (to compute the checksum again and compare against the stored checksum). One approach to reducing CPU overheads, employed by many systems that use checksums (including network stacks), is to combine data copying and checksumming into one streamlined activity; the copy is needed anyhow (e.g., to copy the data from the kernel page cache into a user buffer), combined checksumming can be effective.

Beyond CPU overheads, some checksumming schemes can induce I/O overhead, particularly when checksums are stored distinctly from the data (thus requiring each I/Os to access them), and for any extra I/O needed for background scrubbing. The former can be reduced by design; the latter can be tuned and thus its impact limited, perhaps by controlling when scrubbing activity takes place. The middle of the night, when most (not all!) productive workers have gone to bed, may a good time to perform such scrubbing activity and increase the robustness of the storage system.
