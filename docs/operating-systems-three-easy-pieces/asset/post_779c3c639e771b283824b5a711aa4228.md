# Paging: Faster Translations (TLBs)

Using paging as the core mechanism to support virtual memory can lead to high performance overheads. By chopping the address space into small, fixed-sized units (i.e., pages), paging requires a large amount of mapping information. Because that information is generally stored in physical memory, paging logically requires an extra memory lookup for each virtual address generated by the program. Going to memory for translation information before every instruction fetch or explicit load or store is prohibitively slow. And thus our problem:

> ### The Crux: How To Speed Up Address Translation
How can we speed up address translation, and generally avoid the extra memory reference that paging seems to require? What hardware support is required? What OS involvement is needed?

When we want to make things fast, the OS usually needs some help. And help comes from the OS's old friend: the hardware. To speed address translation, we are going to add what is called (for historical reasons [CP78]) a **translation-aside buffer**, or TLB [CG68, C95]. A TLB is a part of the chip's **memory-management unit (MMU)**, and is simply a hardware cache of all popular virtual-to-physical address translations; thus, a better name would be **address-translation cache**. Upon each virtual memory reference, the hardware first checks the TLB to see if the desired translation is held therein; if so, the translation is performed (quickly) without having to consult the page table (which has all translations). Because of their tremendous performance impact, TLBs in a real sense make virtual memory possible [C95].

# 19.1 TLB Basic Algorithm

19.1 shows a rough sketch of how hardware might handle a virtual translation, (i.e., the page table is an array) and a hardware-managed TLB (i.e., the hardware handles much of the responsibility of page table accesses; we'll explain more about this). The algorithm works like this: extract the page number (VPN) from the virtual address (Line 1 in Figure 19.1), and check if the TLB holds the translation for this VPN (Line 2). If it does, we have a TLB hit, which means the TLB holds the translation. Success! we can now extract the frame number (PFN) from the relevant TLB entry; concatenate it with the offset from the virtual address, and form the desired physical address (PA), and access memory (Lines 5-7), assuming protection checks do not fail (Line 4).

If the CPU does not find the translation in TLB (a TLB miss), we have some more to work in. In this example, the hardware accesses the page table to find the translation (Lines 11–12), and assuming that the memory generated by the process is valid and accessible (Lines 13, 15), updates the TLB with the translation (Line 18). The set of actions are costly, primarily because of the extra memory reference needed to access the page table (Line 12). Finally, TLB is updated, the hardware retries the instruction; this time, the translation is found in TLB, and the memory reference is processed quickly.

# PAGING: FASTER TRANSLATIONS (TLBs)

The TLB, like all caches, is built on the premise that the common case, translations are found (i.e., hits). If so, little overhead is added, as the TLB is near and designed to be quite fast. When a miss occurs, the high cost of paging is incurred; the page table must be accessed to find the translation, and an extra memory reference (or more, with complex page tables) results. If this happens, the program will likely run slower; memory accesses are costly, and TLB misses lead to more accesses. Thus, it is our hope to avoid TLB misses as much as we can.

# 19.2 Example: Access An Array

To clear the operation of TLB, let's examine a simple virtual address trace and see how TLB can improve its performance. In example, let's assume we have an array of 10 4-byte integers in memory, starting at virtual address 100. Further that we have a small 8-bit virtual space, with 16 pages; thus, a virtual address down into a 4-bit VPN (there are 16 virtual pages) and a 4-bit offset (there are 16 bytes on each of those pages). The array's first entry ( four-byte integers fit into that page. Figure 19.2 (page 6) shows the array laid out on each of those pages.

Now let's consider a simple loop that accesses each array element, something that would look like:

```
int sum = 0;
for (i = 0; i < 10; i++) {
  sum += a[i];
}
```

For the sake of simplicity, we will pretend that the only memory accesses the loop generates are i and sum, as well as the instructions themselves. When the first element ([0]) is accessed, the CPU will use to load a virtual address 100. The hardware extracts the VPN from (VPN=6), and uses that to check the TLB for a valid translation. Assuming this is the first time the program accesses the array, the result will be a TLB miss. The next access is to a[1], and there is some news here: a TLB hit! Because the second element of the array is packed next to the first, it lives on the same page; we've already accessed this page when accessing the first element of the array, the translation is already loaded into the TLB. And the reason for our success. Access to a[2] encounters another hit, because it lies on the same page as a[0] and a[1]. When the program accesses a[3], we encounter another TLB miss. However, once again, the next entries a[4] ... a[6] will hit the TLB, as they all reside on the same page in memory. Finally, access to a[7] causes one TLB miss. The hardware again consults the page table to figure out the location of this page in physical memory, and updates the TLB. The final two accesses a[8] and a[9] are the benefits of this TLB when the hardware looks in the TLB for their translations, more than twice.

Let us summarize TLB activity during our ten accesses to the array: miss, hit, hit, hit, hit, hit. Thus, the TLB hit rate, the number of hits divided by the total number of accesses, is 70%. Although this is not too high (indeed, we see rates that approach 100%), it is non-zero.
