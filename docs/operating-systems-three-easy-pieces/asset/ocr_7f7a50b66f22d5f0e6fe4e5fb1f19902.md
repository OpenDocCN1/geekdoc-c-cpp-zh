Next, we have two regions of the address space that may grow (and shrink) while the program runs. Those are the heap (at the top) and the stack (at the bottom). We place them like this because each wishes to be able to grow, and by putting them at opposite ends of the address space, we can allow such growth to happen in opposite directions. The heap starts just after the code (at 1KB) and grows downward (when a user requests more memory via malloc()); the stack grows upward (when a user makes a procedure call). However, this placement of heap and stack is just a convention; we could arrange the address space in a different way if you'd like (as we'll see later: when multiple threads co-exist in an address space, no nice way to divide the address space like this works anyway, etc.).

Of course, when we describe the address space, what we are describing is the abstraction the OS is providing to the running program. The program really isn't in memory at physical addresses 0 through 16KB; rather it is loaded at some arbitrary physical address(es).
