# TIP: USE WHILE (NOT IF) FOR CONDITIONS

When checking for a condition in a multi-threaded program, using a `while` loop is always correct; using an `if` statement might only be, depending on the semantics of signaling. Thus, always use `while` and your code will be as expected.

Using loops around conditional checks also handles the case where spurious wakeups occur. In some thread packages, to details of the implementation, it is possible that two threads get woken up just a single signal has taken place [L11]. Spurious wakeups are further reason to re-check the thread is waiting on.

# 30.3 Covering Conditions

We'll look at one more example of how condition variables can be used. This code is drawn from Lampson and Redell's paper on Pilot [LR80], the same group who first implemented the Mesa semantics described above (the language they used Mesa, hence the name).

The problem they ran into is shown via this simple example, in this case in a multi-threaded memory allocation library. Figure 30.15 shows a snippet which demonstrates the issue.

As you see in the code, when a thread calls into the memory allocation code, it might have to wait in order for more memory to come free. Conversely, when a thread frees memory, it signals that memory is free. However, our code above has a problem: waiting thread (there can be more than one) should be woken?

## CONDITION VARIABLES

```
// how many bytes of the heap are free?
int bytesLeft = MAX_HEAP_SIZE;

// need lock and condition too
cond_t c;
mutex_t m;

void *ptr = allocate(int size) {
    Pthread_mutex_lock(&m);
    while (bytesLeft < size) {
        Pthread_cond_wait(&c, &m); // get mem from heap
    }
    bytesLeft -= size;
    Pthread_mutex_unlock(&m);
    return ptr;
}

void free(void *ptr, int size) {
    Pthread_mutex_lock(&m);
    bytesLeft += size;
    Pthread_cond_signal(&c); // whom to signal??
    Pthread_mutex_unlock(&m);
}
```

Figure 30.15: Covering Conditions: An Example

Consider the following scenario. Assume there are zero bytes free; T1 calls allocate(100), followed by T2 which asks for less memory by calling allocate(10). Both T1 and T2 will wait on the condition and to sleep; there are not enough bytes to satisfy either of these requests.

At that point, assume a third thread, T3, calls free(50). Unfortunately, when it calls while waiting for a waking thread, it might not wake the correct thread, T2 is waiting for only 10 bytes to be free; T3 should remain waiting, as not enough memory is yet free. The code in the figure does not work, as the waking other threads do not know which thread (or threads) to wake up.

The solution suggested by Lampson and Redell is straightforward: replace pthread_signal with pthread_broadcast which wakes up all waiting threads. By doing so, we guarantee that any threads that should be woken are. The downside, of course, can be a negative performance impact, as we might needlessly wake up many other threads that shouldn't (yet) be awake. Those threads will simply wake up, re-check the condition, and then go back to sleep.

Lampson and Redell call such a condition, as it covers all cases where a thread needs to wake up (conservatively); the cost, as we've discussed, is that too many threads might be woken.

The astute reader might also noticed we could have used this approach earlier (see the producer/consumer problem with only a single variable). However, in that case, a better solution was available to us, and thus we used it. In general, if you find that your program only works when you change your signals to broadcasts (but in cases like the memory allocator above), then fix it!

# 30.4 Summary

We have seen the introduction of another important primitive beyond locks: condition variables. By allowing threads to sleep when some program state is not desired, CVs enable us to neatly solve a number of important problems, including the famous (and still important) producer/consumer problem, as well as covering conditions.
