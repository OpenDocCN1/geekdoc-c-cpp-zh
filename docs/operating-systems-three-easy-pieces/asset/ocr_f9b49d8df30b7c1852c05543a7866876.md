You can probably see the problem is using (Figure 49.7). In fact, there are two subproblems. The first subproblem is that the client C2 may write in its cache for a time before propagating them to the server; in this case, while [Fv2] sits in its memory, any access of F from another client (say C3) will fetch the old version of the file [Fv1]). Thus, by buffering writes to the client, other clients get stale versions of the file, which may be undesirable; indeed, imagine the case you log into cache C2, update F and then log into C3 and try to read the file, only to get the old copy! Certainly this would be frustrating. Thus, let us call this aspect of the consistency problem **update visibility**: when updates from one client become visible to other clients?

The second subproblem of cache consistency is a **stale cache**: in this case, C2 has finally flushed its writes to the file server, and thus the server has the latest version. However, C1 still has [Fv1] in its cache: if a program running on C1 reads F, it will get a stale version [Fv1] and not the most recent copy [Fv2], which is (often) undesirable.

NFS2 solve these cache consistency problems in two ways. First, to address update visibility, clients implement what is called **flush-on-open (a.k.a., close-to-open)** consistency semantics; when a file is updated and then followed by a client application, the client flushes all (i.e., dirty pages in the cache) to the server. With flush-on-close, NFS ensures that a subsequent open from another node will see the latest version.

Second, to address stale cache problem, NFS clients first check whether a file has changed before fetching its contents. Specifically, before using a cached block, the client-side file system will issue a GETATTR request to fetch the file’s attributes.
