# FILE SYSTEM IMPLEMENTATION

> ASIDE: READS DON'T ACCESS ALLOCATION STRUCTURES
We've seen many students get confused by allocation structures such as bitmaps. In particular, many often think that when you are reading a file, and not allocating any new blocks, that the bitmap will be consulted. This is not true! Allocation structures, as bitmaps, are only accessed when allocation is needed. The inodes, directories, and indirect blocks have all the information they need to complete a read request; there is no need to make sure a block is allocated when the inode points to.

Once open, the program can issue a read() system call to read the first (at offset 0 unless lseek(i) has been called) will read the first block of the file, consulting the inode to find the location of such a block; it may also update the inode with a new accessed time. The read will further update the in-memory open file table for this file descriptor, updating the file offset that the next read will read the second block, etc.

At some point, the file will be closed. There is much work to be done here; the file descriptor should be deallocated, but for now, that is all the FS needs to do. Do not I/O os cache.
A depiction of this process is found in Figure 40.3 (page 529); in the figure, the time decreases downwards as reads take place in order to finally locate the inode of the file. Afterwards, reading each block requires the file system to consult the inode, then read the block, and then update the inode's last-accessed-time with a field. Spend some time and understand what is going on.
Also note that I/O generated by the open is proportional to the length of the pathname. For each additional directory in the path, we have to read its inode as well as its data. Making this worse would be the presence of large directories; here, we have to read one block to get the contents of a directory, whereas with a large directory, we might have to read many data blocks to find the desired entry. Yes, life can get busy when reading a file; as you're about to find out, writing a file (and especially, creating a new) is even worse.

# Writing A File To Disk

Writing to a file is a similar process. First, the file must be opened (as above). Then, the application can issue write() calls to update the file with new contents. Finally, the file is closed.
