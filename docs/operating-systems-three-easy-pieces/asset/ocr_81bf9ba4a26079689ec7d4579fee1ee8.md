As you can see in the picture, /a fills up most of the data blocks in Group 0, whereas other groups remain empty. If some other files are now created in the root directory (/), there is not much room left for their data in the group.

With the large-file exception (there set to five blocks in each chunk), FFS instead spreads the file spread across groups, and the resulting utilization within any one group is not too high:

```
group inodes      data.a
0 /a----------/aaaaaa-
1               aaaaaaa-
2               aaaaaaa-
3               aaaaaaa-
4               aaaaaaa-
5               aaaaaaa-

```

The astute (that's you) will note that spreading blocks of a file across the disk will hurt performance, particularly in the relatively common of sequential file access (e.g., when a user or application reads chunks 0 through 29 in order). And you are right, oh astute reader of ours! You can address this problem by choosing chunk size carefully.

Specifically, if the chunk size is large enough, the system will spend most of its time transferring from disk and just a (relatively) little time seeking between chunks of the block. This process of reducing overhead by doing more work per unit is called amortization in common techniques.

Let's do an example: assume that the average positioning time (i.e. seek and rotation) for a disk is 10 ms. Assume that the disk transfers at 40 MB/s. If your goal is to spend half your time seeking and achieve 50% of disk performance, then you would need to spend 10 ms transferring for data. The question becomes: how big a chunk have to be in order to spend 10 ms in transfer? Easy just our old file method, in particular the dimensional analysis mentioned in the chapter on disks [AD14]:

| $40\text{ MB}$ | $1024\text{ KB}$ | $1\text{ sec}$ | | $409.6\text{ KB}$ | (41.1) |
|---|---|---|---|---||
| $\text{sec}$ | $1\text{ MB}$ | $1000\text{ pe}$ | | |

Basically what this says is: if you transfer at 40 MB/s, you need to transfer 409.6 KB every time you seek in order to spend half your time seeking and half your transferring. Similarly, you can compute the size of the chunk you need to achieve 90% of peak bandwidth (turns out it is about 3.6MB), or even 99% of peak bandwidth (40.6MB!). As you can see, the closer you want to get to, the bigger these chunks get (see Figure 41.2 for a plot of these values).
