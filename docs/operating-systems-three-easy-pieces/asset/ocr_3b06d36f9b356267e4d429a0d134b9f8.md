# I/O DEVICES

> TIP: INTERRUPTS NOT ALWAYS BETTER THAN PIO
Although interrupts allow for overlap of computation and I/O, they only really make sense for slow devices. Otherwise, the cost of interrupt handling and context switching may outweigh the benefits interrupts provide. There are also cases where a flood of interrupts may overload a system and lead to livelock [MR96]; in such cases, polling provides control to the OS in its scheduling and is again useful.

Another reason not to use interrupts in networks [MR96]. When a huge stream of incoming packets generates each interrupt, it is possible for the OS to livelock, that is, find itself processing interrupts and never allowing a user-level process to run and actually serve the requests. For example, a web server that experiences a load burst because it is top-ranked might occasionally use polling to better control what is happening in the system and allow the web server to serve some requests before going back to the device for more packet arrivals.

Another interrupt-based optimization is coalescing. In such a setup, a device needs to wait for a bit before delivering the interrupt to the CPU. While waiting, other requests may soon complete, and multiple interrupts can be coalesced into a single interrupt delivery, thus lowering the overhead of interrupt processing. For course, waiting too long will increase the latency of a request, a common trade-off in systems. See Ahmad et al. [A11] for an excellent summary.

# 3.5 More Efficient Data Movement With DMA

Unfortunately, this is another aspect of our protocol that requires our attention. In particular, when using programmed I/O (PIO) to transfer a large chunk of data to a device, the CPU is often overburdened by a trivial task, and thus wastes a lot of time and effort that could be better spent on other processes. The timeline illustrates here:

| CPU | 1 | 1 | 1 | 1 | 1 | c | c | 2 | 2 | 2 | 1 | 1 |
| Disk | | | | | | | | 1 | 1 | 1 | 1 |

In the timeline, Process 1 is running and wishes to write data to the disk. It initiates the I/O, which must copy the data from memory to the device explicitly, one word at a time (marked c in the diagram). When the copy is complete, the I/O begins on the disk and the CPU can finally be used for something else.
