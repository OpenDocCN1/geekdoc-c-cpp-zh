# Locks

From the introduction to concurrency, we saw one of the fundamental problems in concurrent programming: we would like to execute a series of instructions atomically, but due to the presence of interrupts on a single processor (or multiple threads executing on multiple processors concurrently), we couldn't. In this chapter, we attack this problem directly, with the introduction of something referred to as a lock. Programmers annotate source code with locks, putting them around critical sections, and thus ensure that any such section executes as if it were a single atomic instruction.

## 28.1 Locks: The Basic Idea

As an example, assume our critical section looks like this, the canonical update of a shared variable:

balance = balance + 1;

Of course, other sections are possible, such as adding an element to a linked list or other complex updates to shared structures, but we'll just keep to this simple example for now. To use a lock, we add some code around the critical section like this:

```c
lock_t mutex; // some globally-allocated lock 'mutex'
...
lock(&mutex);
balance = balance + 1;
unlock(&mutex);
```

A lock is a variable, and thus to use one, you must declare a lock variable of some kind (such as mutex above). This lock variable (or just "lock") holds the state of the lock at any instant in time. It is either available (or unlocked or free) and no thread holds the lock, or acquired (or locked or held), and thus exactly one thread holds the lock and presumably in a critical section. We could store other information in the data type as well, such as which thread holds the lock, or a queue for lock acquisition, but information like that is hidden from the user of the lock.

The semantics of the lock() and unlock() routines are free. Calling the routine lock() tries to acquire the lock; if no other thread holds the lock (i.e., it is free), the thread will acquire the lock and enter the critical section; this thread is said to be the owner of the lock. If another thread calls lock() on that same variable (mutex in this example), it will not return while the lock is held by another thread; in this way, other threads are prevented from entering the critical section while the first thread holds the lock.

Once the owner calls unlock(), the lock is now available (free). If no other thread is waiting for the lock (i.e., no other thread has called lock() and is stuck), the state of the lock is simply changed. If threads are waiting (st in lock()), one of them (eventually) notice informed of this lock's state, acquire it, and enter the critical section.

Locks provide some minimal control over scheduling to programmers. In general, we view threads as entities created by the programmer but scheduled by the OS, in any fashion that the OS chooses. Locks yield some control over that back by putting a lock around a section of code, the programmer can guarantee that no more than a single thread can ever be active within that code. Locks help transform the chaos that is traditional OS scheduling into a more controlled activity.

## 28.2 Thread Locks

The name that POSIX library uses for a lock is a mutex, as it is used to provide mutual exclusion between threads, i.e., if one thread is in the critical section, it excludes the others from entering until it has completed the section. Then, when you see the following POSIX threads code, you should understand that:

```c
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
...
pthread_mutex_lock(&lock);
balance = balance + 1;
pthread_mutex_unlock(&lock);
```

You might also notice here that using different locks to protect different variables allows more threads to be at once (a fine-grained approach), whereas using one big lock for all data structures is a coarse-grained strategy.
