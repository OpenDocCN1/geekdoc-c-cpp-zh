# ASIDE: RISC vs. CISC

In the 1980s, a great battle took place in the computer architecture community. On one side was the CISC camp, which stood for **Complex Instruction Set Computing**; on the other side was RISC, for **Reduced Instruction Set Computing [PS81]**. The RISC side was spear-headed by David Patterson at Berkeley and John Hennessy at Stanford (who are also co-authors of some famous papers [H86]), although later John Cocke was recognized with a Turing Award for his earliest work on RISC [CM89]. CISC instruction sets tend to have a lot of instructions in them, and each is relatively powerful. For example, you might see a copy, which takes two pointers and a few bytes from source to destination. The idea behind CISC was that instructions should be high-level primitives, to make the assembly language easier to use, and to make code compact.

RISC instruction sets are exactly the opposite. A key observation behind RISC is that instructions are really simple targets, and all compilers are really a few primitives that they can use to generate high-performance code. Thus, RISC proponents argued, let's rip out as much from the hardware as possible (especially the microcode), and make what's left simple, uniform, and fast.

In the early days, RISC chips made a huge impact, as they were noticeably faster [BC91]; many papers were written; few companies were formed (e.g., MIPS and Sun). However, CISC manufacturers like Intel incorporated many RISC techniques into the core of their processors, by adding early pipeline stages that transformed complex instructions into micro-instructions which could be processed in RISC-like manner. These innovations, plus a growing number of transistors on each chip, allowed CISC to remain competitive. The end result is that the debate died, and both types of processors can be run to fast.
