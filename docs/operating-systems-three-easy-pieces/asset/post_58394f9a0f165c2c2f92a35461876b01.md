
The performance of the program will be almost as if memory isn’t being virtualized at all, an excellent achievement for an operating system, and certainly essential to the use of paging in modern systems.

However, TLBs do not make the world rosy for every program that exists. In particular, if the number of pages a program accesses in a short period of time exceeds the number of pages that fit into the TLB, the program will generate a large number of TLB misses, and thus run quite a bit slower. We refer to this phenomenon as exceeding the TLB coverage, and it can be a problem for certain programs. One solution, as we will discuss in the next chapter, is to include support for larger page sizes; by mapping data structures into regions of the program's address space that are mapped by larger pages, the effective coverage of the TLB can be increased. Support for larger pages is often exploited by programs such as a database management system (DBMS), which have a bottleneck in the CPU pipeline, in particular with what is called a physically-indexed cache.

One other TLB issue worth mentioning: TLB access can easily become a bottleneck, in particular with what is called a physically-indexed cache. With such a cache, address translation has to take place before the cache is accessed, which can slow things down quite a bit. Because of this potential problem, people have looked into all sorts of clever ways to access caches with virtual addresses, thus avoiding the expensive step of translation in the case of a cache hit. Such a virtually-indexed cache solves some performance problems, but introduces new issues in hardware design as well. See Wiggins’s fine survey for more details [W03].

## Homework (Measurement)

In this homework, you are to measure the size and cost of accessing a TLB. The idea is based on work by Saavedra-Barrera [SB92], who developed a simple but beautiful method to measure numerous aspects of cache hierarchies, with a very simple user-level program. Read his work for more details.

The basic idea is to access some number of pages in a large data structure (e.g., an array) and to time those accesses. For example, let's say the TLB size of 4 (which would be very small, but useful for the purposes of this discussion). If you write a program that touches 4 or fewer pages, repeatedly in a loop, each access should be a TLB hit, and relatively fast. However, once you touch 5 pages or more, repeatedly in cost, to that of a TLB miss.

In this loop, one page of the array is updated, up to the number of pages specified by NUMPAGES. By timing such a loop repeatedly (say, a few hundred times in order to run around once, or however many loops needed for a few seconds), you can time how long each access takes (on average). By looking for jumps in cost as NUMPAGES increases, you can roughly determine whether a second-level TLB exists (and how big it is if it does), and in general get a good sense of how TLB hits and misses affect performance.
