To defend against ROP (its earlier form, the return-to-libc attack [+04]) Linux (and other systems) add another defense, known as address space layout randomization (ASLR). Instead of placing code, stack, and the heap at fixed locations within the virtual address space, the OS randomizes their placement, making it quite challenging to craft the intricate code required to implement this class of attacks. Most attacks on vulnerable programs will cause crashes, but may not be able to gain control of the running program.

Interestingly, you can observe this randomness in practice easily. Here's a piece of code that demonstrates it on a modern Linux system:

```
int main(int argc, char *argv[]) {
    int stack = 0;
    printf("%p\n", &stack);
    return 0;
}
```

In non-ASLR systems, this value of a variable on the stack would be the same. But, as you can see below, the value changes with run:

```
prompt> ./run
0xffd3e55d2b4
prompt> ./run
0xff1033b8f4
prompt> ./run
0xff45522e9a4
```

ASLR is a useful defense for user-level programs that it has also been incorporated into the kernel, in a feature we imaginatively called address space layout randomization (KASLR). However, it turns out the kernel may have even bigger problems to handle, as we discuss next.

# Other Security Problems: Meltdown And Spectre

As we write these two (August, 2018), the world of systems security has turned upside down by two new and related attacks. The first is called Meltdown, and the second Spectre. They were discovered at the same time by four different groups of researchers/engineers, and have led to deep questioning of the fundamental protections offered by computer hardware and the OS above. We see meltdownattack.com and spectreattack.com for papers describing each attack in detail. Spectre is considered the more problematic of the two.
