High reliability will be achieved through the combination of a few different approaches. One main concern, as discussed above, is wear out. If a single block is erased and programmed too often, it becomes unusable; as a result, the FTL should spread writes across the blocks of the flash as evenly as possible, ensuring that all the blocks of the device wear out at the same time; doing so is called leveling and is an essential part of any modern FTL.

Another reliability concern is program disturbance. To minimize disturbance, FTL will necessarily program pages within an erased block in order, from low page to high page. This sequential-programming approach minimizes disturbance and is widely utilized.

# 44.6 FTL Organization: A Bad Approach

The simplest organization of an FTL would be something we call direct-mapped. In this approach, a read to logical page N is mapped directly to a physical page N. A write to logical page N is more complicated; the FTL has first to erase the entire block that page N is contained within; then it has to erase the block; finally, the FTL programs the old pages as well as the new one.

As you can probably guess, the direct-mapped FTL has many problems, both in performance and as reliability. The performance problems come on each write: the device has to erase the entire block (costly), erase it (costly), and then program it (costly). The result is severe write amplification (proportional to the number of pages in a block) and as a result, terrible write performance, even slower than typical hard drives with their mechanical seeks and rotational delays.

Even worse is the reliability of this approach. If system metadata or user file data is overwritten, the same block is erased and programmed, over and over, repeatedly wearing and potentially losing data. The direct-mapped approach gives too much control over wear out evenly across its logical blocks, the underlying physical blocks containing popular data will quickly wear out. For both reliability and performance reasons, a direct-mapped FTL is a bad idea.

# 44.7 A Log-Structured FTL

For these reasons, most FTLs log structured, an idea useful in both storage devices (as we'll see now) and file systems above them (as we'll see in the chapter on log-structured file systems). Upon a write to logical block N, the device appends the write to the new free spot in the currently-written-to-block; we call this style of writing logging. For simplicity, assume that for block N, the device keeps a mapping table (in its memory, and persistent, in some form, the device); this table stores the physical address of each logical block in the ssd.

Let's go through an example to make sure how the basic-based approach works. To the client, the device looks like a typical disk, which it can read and write 512-byte sectors (or groups of sectors). Assume that the SSD is reading or writing 4-KB sized chunks. Let us further assume that the SSD contains some large number of 16-KB blocks, each divided into four 4-KB pages; these parameters are unrealistic (flash blocks usually consist of many pages) but will serve our didactic purposes quite well.

Assume the client issues the following sequence of operations:

- *Write(100)* with contents a1
- *Write(101)* with contents a2
- *Write(2000)* with contents b1
- *Write(2001)* with contents b2

These logical blocks (e.g., 100) are used by the client of the SSD (e.g., a file system) to remember where information is located.

Internally, the device must transform these blocks into the erase and program operations supported by the hardware, and somehow record, for each logical block address, where the data is stored. Assume that all blocks of the SSD are currently not valid, stores its data. and must be erased before any page can be programmed. Here we show the initial state of our SSD, with all pages marked INVALID (i):

| Block | 0 | | 2 |
|---|---|---||
| Page | 00 01 02 03 04 05 06 07 08 09 10 11 |
| Content | | | |
| State | i i i i i i i i i i i i i i i i |

When the first write is received by the SSD (to logical block 100), the FTL decides to write it to physical block 0, which contains four physical pages: 0, 1, 2, and 3. Because the block is not erased, we cannot write to it; the device must first issue an erase command to block 0. Doing so leads to the following state:

| Block | 0 | | 2 |
|---|---|---||
| Page | 00 01 02 03 04 05 06 07 08 09 10 11 |
| Content | | | |
| State | E E E E i i i i i i i i i i i |

Block 0 is now ready to be programmed. Most SSDs will write pages in order (i.e., low to high), reducing reliability problems related to program disturbance. The SSD then directs the write of logical block 100 into physical page 0:

| Block: | 0 | 1 | 2 |
| Page: | 00 01 02 03 04 05 06 07 08 09 10 11 |
| Content: | a1 | | | | | | | | | | | |
| State: | V E E | | | | | | | | | | |

But if the client wants to read logical block 100? How can it find where it is? The SSD must transform a read issued to logical block 100 into a read of physical page. To accommodate functionality, when the FTL writes logical block 100 to physical page 0, it records this fact in an in-memory mapping table. We will track the state of this mapping table in the diagrams as:

| Table: | 100 → 0 | Memory |
| Block: | 0 | 1 | 2 |
| Page: | 00 01 02 03 04 05 06 07 08 09 10 11 |
| Content: | a1 | | | | | | | | | | | | |
| State: | V E E | | | | | | | | | | |

Now you see what happens when the client writes to the SSD. The SSD finds a location for the write, usually picking the next free page; it then programs page with the block's contents, and records the logical-to-physical mapping in its mapping table. Subsequent results use the table to translate the logical block address presented by the client into the physical page needed to read the data.

Let's examine the rest of the writes in our example write stream: 101, 2000, and 2001. After writing these blocks, the state of the device is:

| Table: | 100 → 0 | 101 → 1 | 2000→ 2 | 2001→ 3 | Memory |
| Block: | 0 | 1 | 2 |
| Page: | 00 01 02 03 04 05 06 07 08 09 10 11 |
| Content: | a1 a2 b1 b2 | | | | | | | | | | | |
| State: | V V V | | | | | | | | | | |

The log-based approach by its nature improves performance (erases only required in a while, and the costly read-modify-write of the direct-mapped approach avoided altogether), and greatly enhances reliability. The FTL can spread writes across all pages, performing what is called wear leveling and increasing the lifetime of the device; I'll discuss wear leveling further below.

# ASIDE: FTL MAPPING INFORMATION PERSISTENCE

You might be wondering: what happens if the device loses power? Does the in-memory mapping table disappear? Clearly, such information cannot be lost, otherwise the device would not function as a storage device. An SSD must have some means of recovering mapping information. The simplest thing to do is to record mapping information with each page, what is called an out-of-band (OOB) area. When the device loses power and is restarted, it must reconstruct its mapping table by scanning OOB areas. This basic approach has its problems; scanning a large SSD to find all necessary is slow. To overcome this limitation, some higher-end devices use more logging and checkpointing techniques to speed up recovery; learn more about logging by reading chapters on crash consistency and log-structured file systems [14].

Unfortunately, this basic approach to logging has some downsides. The first is that overwrites of logical blocks we call garbage, i.e., old versions of data around the drive and taking up space. The device needs to periodically perform garbage collection (GC) to find said blocks and space for future writes; excessive garbage collection drives up write amplification and lowers performance. The second is high cost of in-memory mapping tables; the larger the device, the more memory tables need. We will discuss this later.

# 44.8 Garbage Collection

The first cost of any log-structured approach such as this one is that garbage is created, and therefore garbage collection (i.e., dead-block reclamation) must be performed. Let's use our continued example to make sense of this. Recall that logical blocks 100, 101, 2000 and 2001 have been written to the device.

Now, let's assume that blocks 100 and 101 are written again, with contents c1 and c2. The writes are written to the next pages (in this case, pages 4 and 5), and the mapping table is updated accordingly. Note that the device must have first erased block 1 to make such programming possible.
