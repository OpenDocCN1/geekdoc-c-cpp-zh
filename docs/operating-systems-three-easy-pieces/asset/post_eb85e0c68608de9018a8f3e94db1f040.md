- **Data transfer (writes):** Wait until drive status is READY and DRQ (drive request for data); write data to data port.
- **Handle interrupts.** An interrupt for each sector transferred; more complex approaches allow batching and thus one interrupt when the entire transfer is complete.
- **Error handling.** After each operation, read the status register. If the ERROR bit is on, read the error register for details.

Most of this protocol is found in the xv86 IDE driver (Figure 36.6), which (after initialization) works through four primary functions. The first is `ide_rw()`, which queues a request (if there are others pending), or issues it to the disk (via `ide_start_request()`); in either case, the routine waits for the request and the calling process is put to sleep. The second is `ide_start_request()`, which is used to send a request (and data, in the case of a write) to the disk; the `in` and `out` instructions are called to read and write device registers, respectively. The start request uses the third function, `ide_wait_ready()`, to ensure the device is ready before issuing a request to it. Finally, `ide_intr()` is invoked when an interrupt takes place; it reads data from the device (if it is a read, not a write), wakes the process waiting for the I/O complete, and (if there are more requests in the I/O queue) launches the I/O via `ide_start_request()`.

# 36.9 Historical Notes

Before entering, we include a brief historical note on the origin of these fundamental ideas. If you are interested in learning more, read Smotherman's excellent summary [S08].

Interrupts are an ancient idea, existing on the earliest of machines. For example, the UNIVAC in the early 1950's had some form of interrupt vector, although it is unclear in which year this feature was available [S08]. Sadly, even in our infancy, we are beginning to lose the origins of computing history.

There is also debate about which machine first introduced the idea of DMA. For example, Knuth and others point to the DYAC (a “mobile” machine, which at the time it could be hauled in a trailer), whereas others think the IBM SAGE may have been the first [S08]. Either way, by the mid 50's, systems with I/O devices communicated directly with memory and interrupted the CPU when finished existed.

The history here is difficult to trace because the inventions are tied to real, and sometimes obscure, machines. For example, some think that the Lincoln Labs TX-2 machine was first with vectored interrupts [S08], but this is hardly clear.

static int ide_wait_ready() {

```c
static void ide_start_request(struct buf *b) {
    ide_wait_ready();
    outb(0x3f6, 0); // generate interrupt
    outb(0x1f2, 0); // how many sectors?
    outb(0x1f3, b->sector & 0xff); // LBA goes here ...
    outb(0x1f4, (b->sector >> 8) & 0xff); // and here
    outb(0x1f5, (b->sector >> 16) & 0xff); // and here!
    if ((b->flags & B_DIRTY) | ((b->sector>>24)&0x0f)) {
        outb(0x1f7, IDE_CMD_WRITE); // this is a WRITE
        outb(0x1f0, b->data, 512/4); // transfer data too!
    } else {
        outb(0x1f7, IDE_CMD_READ); // this is a READ (no data)
    }
}
```

```c
void ide_rw(struct buf *b) {
    acquire(&ide_lock);
    for (struct buf **pp = &ide_queue; *pp=(*pp)->qnext;) { // walk queue
        *pp = b; // add request to end
        if (ide_queue == b) { // if q is empty
            ide_start_request(b, &ide_lock); // send req to disk
            while ((b->flags & (B_VALID|B_DIRTY)) != B_VALID)
                sleep(b, &ide_lock); // wait for completion
        }
    }
    release(&ide_lock);
}
```

```c
void ide_intr() {
    struct buf *b;
    acquire(&ide_lock);
    if (!(b->flags & B_DIRTY) && ide_wait_ready() >= 0) {
        ins(0x1f0, b->data, 512/4); // if READ: get data
        b->flags |= B_VALID;
    }
    b->flags &= ~B_DIRTY;
    wakeup(b); // wake waiting process
    if ((ide_queue == b->qnext) != 0) // start next request
        ide_start_request(ide_queue); // if (one exists)
    release(&ide_lock);
}
```

Because the ideas are relatively obvious — no Einsteinian leap is required to come up with the idea of letting the CPU do something else while a I/O is pending — perhaps our focus on “who first?” is misguided. What is certainly clear: as people built these early machines, Interrupts, DMA, and related ideas are all direct outcomes of the nature of fast CPUs and slow devices; if you were there at the time, you might have had similar ideas.

# 36.10 Summary

You should now have a very basic understanding of how an OS interacts with a device. Two techniques, the interrupt and DMA, have been introduced to help with device efficiency, and two approaches to access device registers, explicit I/O instructions and memory-mapped I/O, have been described. Finally, the notion of a device driver has been presented, showing how the OS itself can encapsulate low-level details and thus make it easier to build the rest of the OS in a device-neutral fashion.
