
## Scheduling:
The Multi-Level Feedback Queue

In this chapter, we'll tackle the problem of developing one of the most well-known approaches to scheduling, known as the **Multilevel Feedback Queue (MLFQ)**. The Multi-level Feedback Queue scheduler was first described by Corbato et al. in 1962 [C+62] in a system known as the Compatible Time-Sharing System (CTSS), and this work, along with later work on algorithms, led the ACM to award Corbato his highest honor, the **Turing Award**. The scheduler has subsequently been refined throughout the years to the implementations you will encounter in modern systems.

The fundamental problem MLFQ addresses is two-fold. First, it would like to optimize *turnaround time*, which, as we saw in the previous note, is done by running shorter jobs first; unfortunately, the OS doesn't generally know how long a job will run for, exactly the knowledge that algorithms like SJF (or SCFF) require. Second, MLFQ would like to make a system feel responsive to interactive users (i.e., users and waiting for a process to finish) and thus minimize *response time*; unfortunately, algorithms like Round Robin reduce response time but are terrible for turnaround time. Our problem: given that in general do not know anything about a process, how can we build a scheduler to achieve these goals? How can the scheduler, as the system runs, the characteristics of the jobs it is running, and thus make better scheduling decisions?

## The Crux: How To Schedule Without Perfect Knowledge?

How can we design a scheduler that both minimizes response time for interactive jobs while also minimizing turnaround time without *a priori* knowledge of job length?

## SCHEDULING: THE MULTI-LEVEL FEEDBACK QUEUE

> TIP: Learn From History

The multi-level feedback queue is an excellent example of a system that learns from the past to predict the future. Such approaches are common in operating systems (and many other places in Computer Science, including hardware branch predictors and caching algorithms). Such work when jobs have phases of behavior and are predictable; of course, one must be careful with such techniques, as they can easily be driven and a system to make worse decisions than they would have with no knowledge at all.

## 8.1 MLFQ: Basic Rules

To build a scheduler, in this chapter we will describe the basic algorithms behind a multi-level feedback queue; although the specifics of many implemented MLFQs differ [E95], most are similar.

In our treatment, the MLFQ has a distinct number of queues, given a job that is to run on a single priority level. MLFQ uses priorities to decide which job should run at a given time: a job with higher priority (i.e., a job on a higher queue) is chosen to run.

Of course, more than one job may be on a given queue, and thus have the same priority. In this case, we will use round-robin scheduling among those jobs.

Thus, we arrive at the first basic rules for MLFQ:

- Rule 1: If Priority(A) > Priority(B), A runs (B doesn't).
- Rule 2: If Priority(A) = Priority(B), A & B run in turn.

The key to MLFQ scheduling lies in how the scheduler sets priorities. Rather than giving a fixed priority to each job, MLFQ varies the priority of a job based on its observed behavior. If, for example, a job repeatedly relinquishes the CPU while waiting for input from the keyboard, MLFQ will keep its high priority, as this is an interactive process; if, a job uses the CPU intensively for long periods of time, MLFQ will reduce its priority. In this way MLFQ will try to learn about processes and use the history of the job to predict its future.

## 8.2 Attempt #1: To Change Priority

We now decide how MLFQ is going to change the priority level of a job (and thus queue it is on) over the lifetime of a job. To do this, we must keep in mind our workload: a mix of interactive jobs that are short-running (and may frequently relinquish the CPU), and some longer-running “CPU-bound” jobs that need a lot of CPU time where response time is not important. Here is our first attempt at priority-adjustment algorithm:

- Rule 3: If a job enters the system, it is placed at the highest priority (the topmost queue).
- Rule 4a: If a job uses an entire time slice while running, its priority is reduced (i.e., it moves down one queue).
- Rule 4b: If a job gives up the CPU before the time slice is up, it stays at the same priority level.

## Example 3: What About I/O?

Let's now look at an example with some I/O. As Rule 4b states, if a process gives up the processor before using its time slice, we keep it at the same priority. The intent of this rule is simple: if an interactive job, for example, is doing a lot of I/O (say by waiting for user input from keyboard or mouse), it will relinquish the CPU before its time slice is complete; in such case, we don't penalize the job and thus simply keep it at the same level.

Figure 8.5 (in gray) shows an example of how this works, with an interactive job B (in gray) that needs the CPU for only 1 ms before performing an I/O competing with a long-running batch job A (in black). The MLFQ approach keeps B at the highest priority because B releasing the CPU; if B is an interactive job, MLFQ further achieves it goal of running interactive jobs quickly.
