# Avoiding Deadlock

OK, now you figured it out, here is the answer. Imagine two threads, one producer and one consumer. The consumer gets to run first. It acquires the mutex (Line C0) and then calls sem_wait() on the full semaphore (Line C1); because there is no data yet, this causes the consumer to block and yield the CPU; importantly, the consumer still holds the lock.

A producer runs. It has data to produce and if it were able to run, it would be able to wake the consumer thread and all would be good. Unfortunately, the first thing it does is sem_wait() on the binary mutex (Line P0). The lock is already held. Here, the producer is now stuck waiting out.

There is a simple cycle here. The consumer holds the mutex and is waiting for someone to signal full. The producer could signal full but is waiting for the mutex. Thus, the producer and consumer are each stuck waiting for each other: a classic deadlock.

# 31.5 Reader-Writer Locks

Another classic problem stems from the desire for a more flexible locking primitive that admits that data structure accesses might require different kinds of locking. For example, imagine a number of current list operations, including inserts and simple lookups. While inserts change the state of the list (and thus a traditional critical section makes sense), lookups simply read the data structure; as long as we guarantee that no insert is on-going, we can allow many lookups to proceed. The special type of lock we will now develop to support this type of operation is known as a reader-writer lock [CHP71]. The code for such a lock is available in Figure 31.13 (page 40).

The code is pretty simple. If thread wants to update the data structure in question, it will call the pair of synchronization operations `rwlock.acquire_write()`, to acquire a write lock, and `rwlock.release_write()`, to release. Internally, these use the `rwlock` semaphore to ensure that only a single writer can acquire the lock and enter the critical section to update the data structure.

More interesting is the pair of routines to acquire and release read. When acquiring a lock, the first reader acquires `lock` and increments the `readers` variable to track how many readers are currently inside the data structure. The important step then is taken within the lock; in case, `rwlock.acquire_read()` occurs when the first reader acquires the lock, the reader also acquires the lock by calling `sem_wait()` on the semaphore, and then releasing the lock by calling `sem_post()`.

Then once a reader has acquired a lock, more readers will be allowed to acquire the lock too; however, any thread that wishes to wait until all readers are finished; the last one to exit the critical section calls `sem_post()` on "writelock" and enables a waiting writer to acquire the lock.

This approach (as desired), but does have some negatives, especially when it comes to fairness. In particular, it would be relatively easy for readers to starve writers. More sophisticated solutions to this problem exist; can you think of a better implementation? Hint: think what you would need to prevent more readers from entering the lock once a writer is writing.

```c
typedef struct _rwlock_t {
    sem_t lock; // binary semaphore (basic lock)
    sem_t writelock; // allow ONE writer/MANY readers
    int readers; // #readers in critical section
} rwlock_t;

void rwlock_init(rwlock_t *rw) {
    rw->readers = 0;
    sem_init(&rw->lock, 0, 1);
    sem_init(&rw->writelock, 0, 0);
}

void rwlock_acquire_read(rwlock_t *rw) {
    sem_wait(&rw->lock);
    rw->readers++;
    if (rw->readers == 1) {
        sem_wait(&rw->writelock);
    }
    sem_post(&rw->lock);
}

void rwlock_release_read(rwlock_t *rw) {
    sem_post(&rw->lock);
    rw->readers--;
    if (rw->readers == 0) {
        sem_post(&rw->writelock);
    }
}

void rwlock_acquire_write(rwlock_t *rw) {
    sem_wait(&rw->writelock);
}

void rwlock_release_write(rwlock_t *rw) {
    sem_post(&rw->writelock);
}
```

Finally, it should be noted that reader-writer locks should be used with some caution. They often add overhead (especially with sophisticated implementations), and do not end up speeding up performance compared to just simple and fast. Either way, they showcase once again how we can use semaphores in an interesting way.

TIP: SIMPLE AND DUMB CAN BE BETTER (HILL’S LAW)
You should never underestimate the notion that the simple and dumb approach can be the best. With locking, sometimes a spin lock works best, it is easy to implement and fast. Although something reader-writer locks sounds cool, they are complex, and can mean slow. Thus, always try the simple and dumb approach first.
This idea, appealing to simplicity, is found in many places. One early source is Mark Hill's dissertation [H87], which studied how to design caches for CPUs. Hill found that simple direct-mapped caches better than fancy set-associative designs (one reason is that in caching, designs enable faster lookups). As Hill succinctly summarized his work: "Big and dumb is better." And thus we call this similar advice Hill's Law.
