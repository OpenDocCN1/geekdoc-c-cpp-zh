INTERLUDE: MEMORY API

# 14.5 Underlying OS Support

You might have noticed that we haven't been talking about system calls when discussing malloc() and free(). The reason for this is simple: they are not system calls, but library calls. Thus the library manages space within your virtual address space, but itself is built on top of system calls which call into the OS to ask for more memory or release back to the system.

Finally, the current system call brk, is used to change the location of the end of the heap. It takes one argument (the address of the new break) and thus increases or decreases the size of the heap based on whether the new break is larger or smaller. An additional call sbrk is passed with an increment but otherwise serves a similar purpose.

Note that you should never directly call brk or sbrk. They are used by the memory-allocation library; if you try to use them, you will likely make something go (horribly) wrong. Stick to malloc() and free instead.

Finally, you can also obtain memory from the operating system with the mmap() call. By passing the correct arguments, mmap() can create an anonymous memory region within your program — a region which is not associated with any particular file but with swap space, something we will discuss in detail later on virtual memory. This memory can then be treated as a heap and managed as such. Read the manual page of mmap() for more details.

# 14.6 Other Calls

There are a few other calls that the memory-allocation library supports. For example, calloc() allocates memory and also zeroes it before returning; this prevents errors where you assume memory is zeroed and forget to initialize it (see the paragraph on "uninitialized reads") The routine realloc() can also be useful, if you've allocated space for something (say, an array), and then need to add something to it: realloc() makes a new region of memory, copies the old region into it, and returns the pointer to the new region.

# 14.7 Summary

We have introduced some of the APIs dealing with memory allocation. As we have just covered the basics; more details are available elsewhere. Read the C book [KR88] and Stevens [SR05] (Chapter 7) for more information. For a cool modern paper on how to detect and correct many of these problems automatically, see Novark et al. [N+07]; this paper also contains a nice summary of common problems and some neat ideas on how to find and fix them.
