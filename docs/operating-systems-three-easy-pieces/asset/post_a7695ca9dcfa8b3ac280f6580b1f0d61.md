ASIDE: SWAPPING TERMINOLOGY AND OTHER THINGS
Terminology in virtual memory systems can be a little confusing and variable across machines and operating systems. For example, a page fault more generally could refer to any page table that generates a fault of some kind: this could include the type of fault we are discussing here, i.e., a page-not-present fault, but sometimes can refer to illegal accesses. It is indeed odd that what we define as a legal access (a page mapped into the virtual address space of a process, but not in physical memory at the time) is a “fault” at all; it should be called a page miss. But often, when people say a program is “page faulting”, they mean that it is accessing parts of its virtual address space the OS has swapped out to.

We suspect the reason that this behavior became known as a “fault” relates to the memory in the operating system to handle it. When unusual happens, i.e., when something the hardware doesn’t know how to handle orders, the hardware simply transfers control to the OS, hoping it can make things better. In this case, a page that a process wants to access is missing from memory; the hardware does only the thing it can, which is raise an exception, and the OS takes over there. This is identical to what happens when a process does something illegal, is it not strange that we term the activity “fault.”

The act of accessing a page that is not in physical memory is commonly referred to as a page fault.

Upon a page fault, the OS is invoked to service the page fault. A particular piece of code, known as a page-fault handler, runs, and must serve the page fault, as we describe.

## 21.3 The Page Fault

Recall that with TLB misses, we have two types of systems: hardware TLBs (where the hardware looks in the page table to find the desired translation) and software TLBs (where the OS does). In either type of system, if a page is not present, the OS is in charge to handle the page fault. The appropriately-named OS-page fault handler runs to determine what to do. Virtually all systems have hardware-managed TLB, the hardware trusts the OS to manage this important duty.

If a page is not present and has been swapped out, the OS will need to swap the page into memory to service the page fault. Thus, a question arises: how will the OS know to find the desired page? In many systems, the page table is a natural place to store such information. Thus, the OS uses the bits in the PTE normally used for data such as the PFN of the page for a disk address. When the I/O completes, the OS will update the PFN field of the page-table PTE to record the in-memory location of the newly-fetched page, and retry the instruction. This next attempt may generate a TLB miss, which could update the TLB when servicing the page fault to avoid this step. Note that while the I/O is in flight, the process will be in the blocked state. The OS will be free to run other processes while the page fault is being serviced. Because I/O is expensive, this overlap of the I/O (page fault) of one process and the execution of another is yet another way a multiprogrammed system can make the most effective use of its hardware.

## 21.4 What If Memory Is Full?

In the process described above, you may notice that we assume there is plenty of free memory which is page in swap space. Of course, this may not be the case; memory may be full (or close to it). The OS might like to first page out one or more pages to make room for the new page(s) the OS is about to bring in. The process of picking a page to kick out, or replace is known as the page-replacement policy.

As turns out, a lot of thought has been put into creating a good replacement policy, kicking out the wrong page can cause a great cost on program performance. Making the wrong decision can cause a program to run at disk-like speeds instead of memory-like speeds; in current technology that means a program could run 10,000 or 100,000 times.

## 21.5 Page Flow

With all of this, we can now sketch what the OS must do in order to save the soon-to-faulted page to reside within. First, the OS must find a physical frame; if there is no such page, we'll have to wait for the replacement algorithm to run and kick some pages out of memory, freeing them for use here. With a physical frame in, the handler issues the I/O request to read in the page from swap space. Finally, when slow operation completes, the OS updates the page table and retries the instruction. The retry will result in a TLB miss, and then, upon another retry, a TLB hit, at which point the hardware will be able to access the desired item.

From the figure in 2.2, we can see what the hardware does. In this case, the access could be an invalid page, the hardware traps this access, and the OS handler runs, likely terminating the offending process. From the software flow in 2.3, we can see what the OS does; no other bits in the PTE really matter.

## 21.6 When Replacements Actually Occur

Thus the way we described how replacements occur assumes that the OS waits until memory is entirely full, and then only replaces (evicts) a page to make room for other page. As you can imagine, this is a little unrealistic, and there are many reasons for the OS to keep a small portion of memory free proactively.

To keep a small amount of memory free, most operating systems have some kind of high watermark (HW) and low watermark (LW) to help when decide to start evaging pages from memory. This works is as follows: OS notices that there are fewer than LW pages available, a background thread that is responsible for freeing memory runs. The thread evicts pages until there are HW pages available. The background, sometimes called the swap daemon or page daemon, then goes to sleep, happy that it has free some memory for running processes and the OS to use.
