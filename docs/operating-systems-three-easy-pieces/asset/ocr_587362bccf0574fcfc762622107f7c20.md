might be interrupted while acquiring or releasing the lock, and thus cause
other threads to spin-wait for this one to run again. However, the time
spending spin is quite limited (just a few instructions inside the lock and
code, instead of the user-defined critical section), and thus this
approach may be reasonable.

You might also observe that in lock(), when a thread cannot acquire
t lock (it is already held), we are careful to add ourselves to a queue by
calling the gettid() function to get the thread ID of the current thread),
set guard to 0, and yield the CPU. A question for the reader: What would
happen if the release of the guard lock came after the park(), and not
before? Hint: spending bad.

You might further notice that the flag does not get back to 0 when
another gets woken up. Why is this? It is not an error, but
rather necessity! When a thread is woken up, it will be as if it is
turn from park(); however, it does not hold the guard at that point
in the code and thus cannot try to set the flag to 1. Thus, we just
pass the lock directly from releasing the lock to the next thread
acquiring; it flag not set in 0 in-between.

Finally, you might notice the race condition in the solution,
just before the call park(). With the wrong timing, a thread will
be about to park, assuming that it should sleep until the lock is no longer
held. A switch at that time to another thread (say, a thread holding the
lock) could lead to trouble, for example, if then released the
lock. The subsequent park by the first thread would then sleep forever
(potentially), a problem sometimes called the wakeup/waiting race.

Solaris solves this problem by adding a third system call: setpark().nBy calling this, a thread can indicate it is about to park. If it\happens to be interrupted and another thread calls unpark before park is
actually called, the subsequent park returns immediately instead of sleeping. The code modification, inside of lock(), is quite small:

```
1 queue_add(m->q, gettid());
2 setpark(); // new code
3 m->guard = 0;
```

A different solution could pass the guard into the kernel. In that case,
t kernel could take precautions to atomically release the lock and de-queuing the thread.
