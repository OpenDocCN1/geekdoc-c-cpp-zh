# 17.2 Low-level Mechanisms

Before diving into some policy details, we'll cover some mechanisms used in most allocators. First, we'll discuss the basics of splitting and coalescing, common techniques in any allocator. Second, we'll show how we can track the size of allocated regions quickly and with relative ease. Finally, we'll discuss how to build a simple list inside the free space to keep track of what is free and what isn't.

# Splitting and Coalescing

A free list contains a set of elements that describe the free space remaining in the heap. Thus, assume the following 30-byte heap:

| free | used | free |
|---|---|---|
| | 10 | 20 | 30 |

The free list for this heap would have two entries on it. One entry describes the first 10-byte free segment (bytes 0-9), and one entry describes the other free segment (bytes 20-29):

```
head addr:0 len:10 -> addr:20 len:10 -> NULL
```

As described above, a request for anything greater than 10 bytes could fail (returning NULL); there isn't a single contiguous chunk of memory of that size available. A request for exactly that size (10 bytes) could be satisfied either of the free chunks. But what happens if the request is for smaller than 10 bytes?

# Tracking The Size Of Allocated Regions

You might have noticed that the interface to free(void *ptr) does not take a size parameter; thus it is assumed that when given a pointer, the malloc library can quickly determine the size of the region of memory being freed and thus incorporate the space back into the free list.

To accomplish this task, allocators store a little bit of information in a header block which is kept in memory, usually just before the handed-out chunk of memory. Let's look at again (Figure 17.1). In this example, we are examining an allocated block of 20 bytes, pointed to by ptr; imagine the called malloc() and stored the results in ptr;ptr = malloc(20);
The header minimally contains the size of the region (in this case, 20); it may also contain additional fields to speed up deallocation, a magic number to provide additional integrity checking, and other information. Let's assume a simple header which contains the size of the region and a magic number, like this:

```
typedef struct {
  int size;
  int magic;
} header_t;
```

The small but critical detail in the last sentence: the size of the free region is the header plus the size of the space allocated to the user. Thus, when a user requests N bytes of memory, the library does not search for a free chunk of size N; rather, it searches for a free chunk of size N plus the size of the header.

# Embedding A Free List

Thus we have treated our free list as a conceptual entity; it is just describing the free chunks of memory in the heap. But how do we build a list inside the free space itself?

In a more typical list, when allocating a new node, you would just call malloc() when you need space for the node. Unfortunately, within the memory-allocation library, you cannot do this! Instead, you need to build the list inside the free space itself. Don't worry if this sounds a little weird; it is, but not so that you can't!

Assume we have a 4096-byte chunk of memory to manage (i.e., the list). Since this is free list, we have to initialize the list; initially, the list should have one entry, of size 4096 (minus the header). Here is the description of a node of the list:

```
typedef struct __node_t {
int size;
struct __node_t *next;
} node_t;
```

Now let's look at some code that initializes the heap and puts the first element of the free list inside space. We are assuming that the heap is built within free space acquired via a call to the system mmap(); this is not the only way to build such a heap but serves us in this example. Here is the code:

```
// mmap() returns a pointer to a chunk of free space
node_t *head = mmap(NULL, 4096, PROT_READ|PROT_WRITE,
MAP_ANON|MAP_PRIVATE, -1, 0);

head->size = 4096 - sizeof(node_t);
head->next = NULL;
```
