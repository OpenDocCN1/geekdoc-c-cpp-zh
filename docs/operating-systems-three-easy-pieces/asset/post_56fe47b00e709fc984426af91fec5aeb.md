## 39.7 Writing Immediately With fsync()

Most times when a program calls write(), it is just telling the file system: please write this data to persistent storage, at some point in the future. The file system, for several seconds, will buffer such writes in memory for some time (say 5 seconds, or 30); or at later point in time, the write(s) will actually be issued to the storage device. From the perspective of the calling application, writes seem to complete quickly, and only in rare cases (e.g., the machine crashes after the write() call before the write to disk) will be lost.

However, some applications require more than this ever guarantees. For example, in a database management system (DBMS), development of a crash recovery protocol requires the ability to force writes to disk from time to time.

To support these types of applications, most file systems provide additional control APIs. In the UNIX world, the interface provided to applications is fsync(int fd). When a process calls fsync() for a particular file descriptor, the file system responds by forcing dirty (i.e., not yet written) data to disk, for the file referred to by that descriptor. The fsync() routine returns once of these writes are complete.

Here is a example of how to use fsync(). The code below opens a file, writes a chunk of data to it, and then calls fsync() to ensure the writes are forced immediately to disk. The fsync() returns, the application can safely move on, knowing that the data has been persisted (if fsync() is correctly implemented, that is):

```c
int fd = open("foo", O_CREAT|O_WRONLY|O_TRUNC,
    S_IRUSR|IWUSR);
assert(fd > -1);
int rc = write(fd, buffer, size);
assert(rc == size);
rc = fsync(fd);
assert(rc == 0);
```

Interestingly, this does not guarantee everything that you might expect; in fsync() the directory that contains the file foo. Adding this step ensures not only the file itself is on disk, but that file, if newly created, is also a part of the directory. Surprisingly, this type of detail is often overlooked, leading to many application-level bugs [P+13,P+14].

## 39.8 Renaming Files

Once we have a file, it is sometimes useful to be able to give a file a different name. When typing at the command line, this is accomplished with mv command; in this example, the file foo is renamed bar:

```bash
prompt> mv foo bar
```

Using trace, we can see that mv uses the system call rename (char *old, char *new), which precisely takes two arguments: the original name of the file (old) and the new name (new).

One interesting guarantee provided by the rename (call) is that it (usually implemented as an atomic call with respect to system crashes; if the system crashes during renaming, the file will either be named the old name or the new name, and no in-between state can arise. rename() is critical for supporting certain kinds of applications that require an atomic update to file state.

Let's be a more specific here. Imagine that you are using an editor (e.g., emacs), and you insert a line into the middle of a file. The file's name is the same as the example. The editor might update the file to guarantee that the new file has the original contents the line is inserted as follows (ignoring error-checking for simplicity):

```c
int fd = open("foo.txt.tmp", O_WRONLY|O_CREAT|O_TRUNC, S_IRUSR|S_IWUSR);
write(fd, buffer, size); // write out new version of file
fsync(fd);
close(fd);
rename("foo.txt.tmp", "foo.txt");
```

What the editor do in this example is: write out the new version of the file under a temporary name (foo.txt.tmp), force it to disk with fsync(), and then, when the application is certain the new file metadata and contents are on disk, rename the temporary file to the original file's name. This last step atomically swaps the new file into place, while concurrently deleting the old version of the file, and thus an atomic file update is achieved.

## 39.9 Getting Information About Files

Beyond file, we expect the file system to keep a fair amount of information about each file it is storing. We generally call this about metadata. To see the metadata for a certain file, we can use the stat() system calls. These calls take a pathname (or descriptor) to a file and fill in a struct as seen in Figure 9.1.

You can see that there is a lot of information about each file, including its size (in bytes), a low-level name (i.e., inode number), some ownership information, and some information about when the file was accessed or modified, among other things. To see this information, you can use the command line tool stat. In this example, we first create a file (called file) and then use the stat command line tool to learn some things about the file.

```c
struct stat {
    dev_t  st_dev;    // ID of device containing file
    ino_t  st_ino;    // inode number
    mode_t st_mode;   // protection
    nlink_t st_nlink;// // number of hard links
    uid_t  st_uid;    // user ID of owner
    gid_t  st_glid;    // group ID of owner
    dev_t  st_rdev;   // device ID (if special)
    off_t  st_size;   // total size, in bytes
    blk_t st_blocks;  // blocks for filesystem I/O
    blk_t st_blkcnt; // number of blocks allocated
    time_t st_atime;  // time of last access
    time_t st_mtime;  // time of last modification
    time_t st_ctime;  // time of last status change
};
```
