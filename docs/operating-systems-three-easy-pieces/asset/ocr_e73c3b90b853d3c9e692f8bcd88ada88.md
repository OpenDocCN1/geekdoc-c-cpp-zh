# EVENT-BASED CONCURRENCY (ADVANCED)

One thing you might have noticed is that it is painful to check whether an I/O has completed; if a program has tens or hundreds of I/Os issued at a given point in time, it should simply keep checking each of them repeatedly, or wait a little while, or ... ?

To remedy this issue, some systems provide an approach based on the interrupt. This method uses UNIX signals to inform applications when an asynchronous I/O completes, thus removing the need to repeatedly ask the system. This polling vs issue is seen in devices too, or you will see (or already have seen) in the chapter on I/O devices.

In systems without asynchronous I/O, the pure-event asynchronous approach cannot be implemented. However, clever researchers have derived methods that work well fairly in their place. For example, Pai et al. [PD299] describe a hybrid approach in which events are used to process network packets, and a thread pool is used to manage outstanding I/Os. Read their paper for details.

# 33.7 Another Problem: State Management

Another issue with the event-based approach is that code is generally more complicated than traditional thread-based code. The reason is as follows: when an event handler handles an asynchronous I/O, it must pack some program state for the next event handler to handle when the I/O finally completes; this additional work is not needed in thread-based programs, as the state is on the stack of the thread. Arya et al. call this manual stack management, and it is fundamental to event-based programming [A02].

To make this point concrete, let's look at a simple example in which this thread-based server needs to read from a file descriptor (fd) and, once complete, write the data that it read from the file to a network socket (sd). The code (ignoring error checking) looks like this:

```
int rc = read(fd, buffer, size);
rc = write(sd, buffer, size);
```

As you can see, in a multi-threaded program, doing this kind of work is trivial; when the read() returns, the code immediately knows which socket to write to because information is on the stack of the thread (the variable sd).
