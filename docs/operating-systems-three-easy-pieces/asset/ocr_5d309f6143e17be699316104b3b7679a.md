Fortunately, there is a scheduler which does exactly: add preemption to SJF, the Shortest Time-to-Completion First (STCF) or Preemptive Shortest Job First (PSJF) scheduler [CK68]. Any time a new job enters the system, the STCF scheduler determines which of the remaining jobs (including the new job) has the least time left, and schedules that one. Then, in example, STCF would preempt A and run B and C to completion; when A's remaining time matches. Figure 7.5 shows an example.

The result is a much-improved turnaround time: 50 seconds ((120-20)+(20-10)+(30-10)). As before, given our new assumptions, STCF is provably optimal: given that SJF is optimal if all jobs arrive at the same time, you would probably be able to see the intuition behind the optimality of STCF.

# 7.6 A New Metric: Response Time

Thus, if we know jobs, and jobs only used the CPU, and only metric was turnaround time, STCF would be a great policy. In fact, for a number of early batch computing systems, these types of scheduling algorithms made some sense. However, the introduction of time-shared algorithms changed all. Now users would sit at a terminal and demand interactive performance from the system as well. and thus, a new metric was: response time.

We define response as the time when the job arrives in a system to the first time it is scheduled⁴. More formally:

```
$T_{response} = T_{firstrun} - T_{arrival}$
```

> ⁴Some define "response" differently, e.g., to also include the time until the job produces some kind of "response"; our definition is the best-case version of this, essentially assuming that the job produces a response instantaneously.
