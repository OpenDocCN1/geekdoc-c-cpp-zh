
Some additional findings by LSEs are:

- Costly drives with more than one LSE are likely to develop additional errors as cheaper drives
- For most drives, annual error rate increases in year two
- The number of LSEs increase with disk size
- Most disks with LSEs have less than 50
- Disks with LSEs are more likely to develop additional LSEs
- There exists a significant amount of spatial and temporal locality
- Disk scrubbing is useful (most LSEs were found this way)

Some findings about corruption:

- Chance of corruption varies greatly across different drive models within the same drive class
- Age effects across different models
- Workload and disk size have little impact on corruption
- Most disks with corruption only have a few corruptions
- Corruption is not independent within a disk or across disks in RAID
- There exists spatial locality, and some temporal locality
- There is a weak correlation with LSEs

To learn more about these failures, you should likely read the original papers [B07, B08]. But hopefully the main point should be clear: if you wish to build a reliable storage system, you must include machinery to detect and recover from both LSEs and block corruption.

## 45.2 Handling Latent Sector Errors

Given these two modes of partial disk failure, we should now try to see what we can do about them. Let's first tackle the easier of the two, namely latent sector errors.

> CRUX: HOW TO HANDLE LATENT SECTOR ERRORS

How should a storage system handle latent sector errors? How much extra machinery is needed to handle this form of partial failure?

As it turns out, latent sector errors are rather straightforward to handle, as they are (by definition) easily detected. When a storage system accesses a block, and the disk returns an error, the storage system should simply use whatever redundancy mechanism it has to return the correct data. In a mirrored RAID, for example the system should access the alternate copy; in a RAID-4 or RAID-5 system based on parity, the system should reconstruct the block from the other blocks in the parity group. Thus, easily detected problems like LSEs are easily recovered through standard redundancy mechanisms.

## DATA INTEGRITY AND PROTECTION

The growing prevalence of LSEs has influenced RAID designs over the years. One particularly interesting problem arises in RAID-4/5 systems when both full-disks and LSEs occur in tandem. Specifically, when an entire disk fails, the RAID tries to reconstruct the disk (say, onto a hot spot) by reading through all of the other disks in the parity group and recomputing the missing values. If, during reconstruction, an LSE is encountered on one of the other disks, we have a problem: the reconstruction cannot successfully complete.

To combat this, some systems add an extra degree of redundancy. For example, NetApp’s RAID-DP is the equivalent of two parity disks instead of one [C+04]. When an LSE is discovered during reconstruction, the extra parity helps to reconstruct the missing block. As always, there is a cost, in maintaining two parity blocks for each stripe is more costly; however, the log-structured nature of the NetApp WAFL file system offsets that cost in many cases [HLM94]. The remaining cost is space, in the form of an extra disk for the second parity block.

## 45.3 Detecting Corruption: The Checksum

Let's tackle the most challenging problem, that of silent failures via corruption. How can we prevent users from getting bad data when corruption arises, and thus leads to disks returning data?

> CRUX: HOW TO PRESERVE DATA INTEGRITY DESPITE CORRUPTION
Given the silent nature of such failures, what can a storage system do to detect when corruption arises? What techniques are needed? How can one implement them efficiently?

Unlike latent sector errors, detection of corruption is a key problem. How can a client tell that a block has gone bad? Once it is known that a particular block is bad, recovery is the same as before: you need to have some other copy of the block around (and hopefully, one that is not corrupt!). Thus, we focus here on detection techniques.

The primary mechanism used by modern storage systems to preserve data integrity is called the checksum. A checksum is simply the result of a function that takes a chunk of data (say a 4KB block) as input and computes a function over said data, producing a small summary of the contents of the data (say 4 or 8 bytes). This summary is referred to as the checksum. The goal of such a computation is to enable a system to detect if data has somehow corrupted or altered by storing the checksum with the data and then confirming upon later that the data’s checksum matches the original storage value.

## Common Checksum Functions

A number of functions are used to compute checksums, and vary in strength (i.e., how good they are protecting data integrity) and speed (i.e., how quickly they can be computed). A trade-off arises: the more protection you get, the costlier it is.

One simple checksum is based on exclusive or (XOR). To make this concrete, imagine a block of data. If we XOR all the bytes together, we get a checksum. This approach is very fast but has limitations: it cannot detect changes in the same position within each unit.

A slightly more complex algorithm is known as the Fletcher checksum (as you might guess the inventor John G Fletcher [F82]). Specifically, assume a block D consists of bytes $d1 \dots dn$; s1 = $(s1 + dn) \pmod{255}$; s2 in turn is $(s2 + s1) \pmod{255}$. The Fletcher checksum is almost as strong as the CRC, detecting all single-bit, double-bit errors, and many bursts [F04].

A final commonly used checksum is known as a cyclic check (CRC). Assume you wish to compute the checksum over a block D. All you do is as if it is a large number (it is a string of bytes) and divide it by an agreed value $k$. The remainder of this division is the value of the CRC. As it turns out, we can implement this by modulo operation rather efficiently, and hence the popularity of the CRC in networking as well [M13].

Whatever the method used, it is obvious that there is no perfect checksum: it is possible two data blocks with non-identical contents will have identical checksums, something referred to as a collision. Such thing feels intuitive: after all, computing a checksum is taking something large (e.g., 4KB) and producing a summary that is much smaller (e.g., 4 or 8 bytes). Now that you understand a bit about how to compute a checksum, let's next analyze how to use checksums in a storage system. The first question we must address is the layout of the checksum, i.e., how checksums be stored on disk?

The most basic approach stores a checksum with each disc sector (or block). Given a data block D, let us call the checksum over that data $C(D)$. Without checksums, the disk layout looks like this:

| D0 | D1 | D2 | D3 | D4 | D5 | D6 |

With checksums, the layout adds a single checksum for every block:

| D0 | C(D0) | D1 | C(D1) | D2 | C(D2) | D3 | C(D3) | D4 | C(D4) | D5 | C(D5) | D6 | C(D6) |
