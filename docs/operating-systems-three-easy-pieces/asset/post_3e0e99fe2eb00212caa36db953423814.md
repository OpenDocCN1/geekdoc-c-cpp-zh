| Disk 0 | Disk 1 | Disk 2 | Disk 3 | Disk 4 |
|---|---|---|---|--|
| 0 | 1 | 2 | 3 | P0 |
| 4 | 5 | 6 | 7 | P1 |
| 8 | 9 | 10 | 11 | P2 |
| 12 | 13 | 14 | 15 | P3 |

Figure 38.5: Full-stripe Writes In RAID-4

To understand the performance of sequential writes, we must first understand how they are done. When writing a big chunk of data to disk, RAID-4 can perform a simple optimization like a full-stripe write. For example, the case where the blocks 0, 1, 2, and 3 have been sent to the RAID as part of a write request (Figure 38.5).

In this case, the RAID can simply calculate the new value of P0 by performing an XOR across the blocks 0, 1, 2, and then write all of the blocks (including the parity block) to the five disks in parallel (highlighted in gray in the figure). Full-stripe writes are the most efficient way for RAID-4 to write to disk.

Once we understand this, calculating the performance of sequential writes in RAID-4 is easy: the effective bandwidth is also (N-1) MB/s. Even though the parity disk is constant in use during operation, the client does not gain performance advantage from it.

Now let us analyze the performance of random reads. As you can see from the example, a set of 1-block random reads will be spread across the disks of the system but not the parity disk. Thus, the effective performance is: (N-1) MB/s.

Random writes, which we have saved for last, present the most interesting case for RAID-4. Imagine we overwrite block 1 in the example above. We would leave us with a problem: the parity block P0 would no longer accurately reflect the correct value of the stripe; in this example, P0 must also be updated. How can we update both correctly and efficiently?

It turns there are two methods. The first, known as additive parity, requires us to do the following. To compute the value of the new parity block, read in all of the other disks in the stripe in parallel (in the example, 0, 2, and 3) and XOR those with the new block (1). The result is your new parity. To complete the write, you can then write the new data and parity to their respective disks, also in parallel.

The problem with this technique is that it scales with the number of disks, and thus in large RAIDs requires a high number of reads to compute parity. The, subtractive parity method.

For example, imagine this string of 4 data bits, one parity:

| C0 | C1 | C2 | C3 | P |
|---|---|---|---|--|
| 0 | 0 | 1 | 1 | XOR(0,0,1,1) |

Let's imagine that we wish to overwrite C2 with a new value which we will call C2_new. The subtractive method works in three steps. First, we read the old data at C2 ($C_{old} = 1$) and the old parity ($P_{old} = 0$). Then, we compare the old data and the new data; if they are the same (e.g., $C_{new} = C_{old}$), then we know the parity will also remain the same (i.e., $P_{new} = P_{old}$). If, they are different, then we must flip the old parity bit to its current state, that is, if ($P_{old} == 1$), $P_{new}$ will be set to 0; if ($P_{old} == 0$), $P_{new}$ will be set to 1. We can express this whole process nearly with XOR (where $\oplus$ is the XOR operator):

```
$P_{new} = (C_{old} \oplus C_{new}) \oplus P_{old} \quad (38.1)$
```

Because we are using blocks, not bits, we perform calculation over all the bits in the block (e.g., 4096 bytes in each multiplied by 8 bits per byte). In most cases, the new block will be different from the old block and thus the new parity block will too.

You should now be able to figure out when we would use the additive parity calculation and think about how many disks would need to be in the system so that the additive method performs fewer I/Os than the subtractive method; what is the cross-over point?

For this performance analysis, let assume we are using the subtractive method. Thus, for each case, the RAID will perform 4 physical I/Os (two reads and two writes). Imagine there are lots of writes submitted to the RAID; how can RAID4 perform in parallel? To understand, let us look at the RAID-4 layout (Figure 38.6).

| Disk 0 | Disk 1 | Disk 2 | Disk 3 | Disk 4 |
|---|---|---|---|--|
| 0 | 1 | 2 | 3 | P0 |
| *P4 | 5 | 6 | 7 | *P1 |
| 8 | 9 | 10 | 11 | P2 |
| 12 | *13 | 14 | 15 | P3 |

Figure 38.6: Writes To 4, 13, and Even Parity Blocks

Now imagine there 2 small writes submitted to the RAID at the same time, blocks 4 and 13 (marked with * in the diagram). The data for these disks is on 0 and 1, and thus the read and write happen in parallel, which is good. The problem that arises with the parity disk; both the requests have to read the parity blocks for 4 and 13 (marked with *). Hopefully, the issue is now clear: the parity is a bottleneck under this type of workload; sometimes we call this the **small-write problem** for parity-based RAIDs. Thus, even though the disks could be accessed in parallel, the parity prevents any parallelism; all writes to the system will be serialized because of the parity disk. Because the parity disk must perform two I/Os (one read, one write), we can compute the performance of random writes in RAID4 by computing the parity disk's performance on two I/Os, and thus we achieve (R/2) MB/s. RAID-4 throughput under random writes is terrible; it does not improve as you add disks to the system. We conclude by analyzing latency in RAID-4. As you now know, a single read (assuming no failure) is mapped to a single disk, and its latency is equivalent to the latency of a single disk. The latency of a single write requires two reads and two writes; the reads can happen in parallel, and total latency is about twice that of a single disk (with some differences because we have to wait for both reads to complete and get the worst-case positioning cost).

# Level 5: Rotating Parity

To address the small-write problem (at least, partially), Patterson, Gibson, and Katz introduced RAID-5 works almost identically to RAID-4, except that it rotates the parity block across disks (Figure 38.7).

| Disk 0 | Disk 1 | Disk 2 | Disk 3 | Disk 4 |
|---|---|---|---|---|
| 0 | 1 | 2 | 3 | P0 |
| 5 | 6 | 7 | P1 | 4 |
| 10 | 11 | P2 | 8 | 9 |
| 15 | P3 | 12 | 13 | 14 |
| P4 | 16 | 17 | 18 | 19 |

Figure 38.7: RAID-5 With Rotating Parity

As you can see, the parity block for each stripe is now rotated across the disks in order to remove the parity-disk bottleneck for RAID-4.

# RAID-5 Analysis

Much of the analysis for RAID-5 is identical to RAID-4. For example, the effective capacity and failure tolerance of the two levels are identical. Sequential read and write performance and latency of a single request (whether a read or a write) is also same as RAID-4.

Random performance is a little better because we can utilize all disks. Finally, random write performance improves noticeably over RAID-4 as it allows for parallelism across requests. Imagine a write to block 10; this will turn into requests to disk 1 and 4 (for block 1 and its parity) and requests to disk 0 and disk 2 (for block 10 and its parity). Thus, they can proceed in parallel. In fact, we can generally assume that given a large number of random requests, we will be able to keep the disks about evenly busy. If that is the case, our total bandwidth for small writes will be N/4 MB/s. The factor of loss is due to the fact that RAID-5 write generates total 4 I/O operations, which is simply the cost of using parity-based RAID. Because RAID-5 is basically identical to RAID-4 except in the cases where it is better, it has almost completely replaced RAID-4 in the marketplace. The only place where it is not is in systems that know they will perform anything other than a large write, avoiding the small-write problem altogether; in those cases, RAID-4 is sometimes used as it is slightly simpler to build.

# RAID Comparison: A Summary

| RAID-0 | RAID-1 | RAID-4 | RAID-5 |
|---|---|---|---|
| Capacity | $N \cdot B$ | $(N \cdot B)/2$ | $(N-1) \cdot B$ | $(N-1) \cdot B$ |
| Reliability | 0 | 1 (for sure) (if unlikely) | 1 | 1 |
| Throughput | $N \cdot S$ | $(N/2) \cdot S$ | $(N-1) \cdot S$ | $(N-1) \cdot S$ |
| Sequential Read | $N \cdot R$ | $(N/2) \cdot R$ | $(N-1) \cdot R$ | $N \cdot R$ |
| Random Read | $N \cdot R$ | $(N/2) \cdot R$ | $N/2 \cdot R$ | $N/4 \cdot R$ |
| Latency | $T$ | $T$ | $2T$ | $2T$ |
| Read | $T$ | $T$ | $2T$ | $2T$ |
