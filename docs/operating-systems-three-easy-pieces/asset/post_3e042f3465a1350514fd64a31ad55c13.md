## 23.1 VAX/VMS Virtual Memory

The VAX minicomputer architecture was introduced in the late 1970's by Digital Equipment Corporation (DEC). DEC was a massive player in the computer industry during the era of the mini-computer; unfortunately, a series of bad decisions and the advent of the PC slowly (but surely) led to their demise [C03]. The architecture was realized in a number of implementations, using the VAX-11/780 and the less powerful VAX-11/750.

The OS for the system was known as VAX/VMS (or just VMS), one whose primary architects was Dave Cutler, who later led the effort to develop Microsoft's Windows NT [C93]. VMS had the general problem that it would run on a broad range of machines, including inexpensive ones (that is proper plural) extremely high-end and powerful machines in the same architecture family. Thus, the OS had to have mechanisms and policies that worked (and worked) across this range of systems.

As an additional issue, VMS is an excellent example of software used to hide some of the inherent flaws of the architecture. Although the OS often relies on the hardware to build efficient abstractions and illusions, sometimes the hardware designers don't quite get everything right; in the VAX hardware, we'll see a few examples of this, and what the VMS operating system does to build an effective, working system despite these hardware flaws.

## Memory Management Hardware

The VAX-11 provided a 32-bit address space per process, divided into 512-byte pages. Thus, a virtual address consisted of a 23-bit VPN and a 9-bit offset. The upper two bits of the VPN were used to differentiate which segment resided within; thus, the system was a hybrid of paging and segmentation, as we saw previously.

The lower-half of the address space was known as “process space” and is unique to each process. In the first half of process space (known as P0), the user program is found, as well as a heap which grows downward. In the second half of process space (P1), we find the stack, which grows upwards. The upper-half of the address space is known as system space (S), only half of it is used. Protected OS code and data reside here, and the OS is in this shared across processes.

One major concern of the hardware designers was the incredibly small size of pages in the VAX hardware (512 bytes). This size, chosen for historical reasons, had the fundamental problem of making simple linear pages excessively large. Thus, one of the first goals of the VMS designers was to ensure VMS would not overwhelm memory with page tables.

The system reduced the pressure page tables on memory to two; by segmenting the user address space into two, the VAX-11 provides a page table for each of these regions (P0 and P1) per process;

Operating systems often have a problem known as the curse of generality, where they are tasked with general support for a broad class of applications and systems. The fundamental result of the curse is that the OS is not likely to support any one installation well. In the case of VMS, the curse was very real, as the VAX-11 architecture was realized in a number of different implementations. It is no less real today, where Linux is expected to run well on every phone, a TV set-top box, a laptop desktop computer, and a high-end server running thousands of processes in a cloud-based datacenter.

Second, the OS reduces memory pressure even by placing page tables (for P0 and P1, two per process) in kernel virtual memory. When allocating or growing a page table, the kernel allocates space out of its virtual memory, in segment S. If memory comes under pressure, the kernel can swap these page tables out to disk, making physical memory available for others.

Putting page tables in kernel virtual memory means that address translation is even further complicated. For example, to translate a virtual entry in P0 or P1, the hardware has to first look up the page-table entry in its page table (the P0 or P1); however, the hardware must first consult the system page table, the hardware holds the address of the page table, and then finally learn the address of the desired memory access. All of this, fortunately, is made faster by the VAX's hardware-managed TLBs, which usually (hopefully) circumvent this laborious lookup.

## A Real Address Space

One aspect of studying VMS is that we can see how a real address space is constructed (Figure 23.1). Thus far, we have assumed a simple address space of user code, user data, and user heap, but as we can see above, a real address space is notably more complex.

For example, the code segment never begins at page 0. This page, instead, is inaccessible, in order to provide some support for detecting null-pointer accesses. Thus, one concern when designing an address-space is support for debugging, the inaccessible zero page provides here in some form.

Perhaps more importantly, the kernel virtual address space (i.e., its data structures and code) is a part of each user address space. On a context switch, the OS changes the P0 and P1 registers to point to the appropriate page tables of the soon-to-be-run process; however, it does not change the S base and bound registers, and as a result the “same” kernel structures are mapped into each address space.

![](img/133d518e3f69f4caaead32c569ae6c49_315_0.png)

The kernel is mapped into each address space for a number of reasons. This construction makes life easier for the kernel; when, for example, the OS is handed a pointer from a user program, it is easy to copy data from that pointer to its own structures. If the kernel were located entirely in physical memory, it would be hard to do things like swap the page table. With this construction (now used widely), the kernel appears as a library, albeit a protected one.

### ASIDE: WHY POINTER ACCESSES CAUSE FAULTS

You should now have a good understanding of exactly what happens on a null-pointer dereference. A process generates a virtual address of 0, by doing something like

```
int *p = NULL; // set p = 0
*p = 10;      // try to store 10 to virtual addr
```

The hardware tries to look up the VPN (also 0 here) in the TLB, and TLB is consulted, and the entry for VPN 0 is found to be marked invalid. Thus, have an invalid access, which transfers control to the OS (on UNIX systems, processes are sent a signal which allows them to react to such fault; if caught, however, the process is killed).

One last point about this address space relates to protection. Clearly, the OS does not want user access to reading or writing Os data or code. The hardware must support different protection levels for pages to enable this. The VAX did so by specifying, in the page table, which privilege level the CPU must be in order order to access a particular page. Thus, system data and code are set to a higher level of protection than user data and code; an attempted access to information from user code would generate a trap into the OS, and (you guessed it) the likely termination of the offending process.
