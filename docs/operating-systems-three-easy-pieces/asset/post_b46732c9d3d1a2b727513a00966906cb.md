## 41.7 A Few Other Things About FFS

FFS introduced few other innovations too. In particular, the designers were extremely worried about accommodating small files; as it turned out, many files were 2KB or so in size back, and using 4KB blocks, when for transferring data, was not good for space efficiency. This **internal fragmentation** could thus lead to half the disk wasted for a typical file system.

The solution the FFS designers hit upon was simple and solved the problem. They decided to introduce **sub-blocks**, which were 512-byte little blocks that the file system could allocate to files. Thus, if you created a small file (say 1KB in size), it would occupy two sub-blocks and thus not

You might observe that this process is inefficient, requiring a lot of work for the file system (in a lot of extra I/O to perform the copy). And you would be right again! Thus, FFS avoided this selfish by modifying the libc; the library would buffer writes and issue them in 4KB chunks to the file system, avoiding the sub-block specialization in most cases.

A neat thing is that FFS introduced a disk layout that was optimized for performance. In those times (before SCSI and other modern device interfaces), disks were much less sophisticated and required the CPU to control their operation in a more hands-on way. A problem arose in FFS when a file was placed on consecutive sectors of the disk, as on the one in Figure 41.3.

In particular, the problem arose during sequential reads. FFS would first issue a read to block 0; by the time the read was complete, FFS would issue a read to block 1, it was too late: block 1 had rotated the head and now to read block 1 would incur a full rotation.

FFS solved this with a different layout, as you can see in Figure 41.3. FFS has enough time to request the block before it went the disk head. FFS was smart enough to figure out for a particular disk how many blocks it should skip in layout order to avoid the extra rotations; this technique is called parameterized placement, as FFS would know the specific performance parameters of the disk and use those to decide on the staggered layout scheme.

You might be thinking: this scheme isn't so great after all. In fact, you will only get 50% of bandwidth with this type of layout, have to go around each track twice to read each block once. Fortunately, modern disks are much smarter: they internally read the entire track and buffer it in an internal disk cache (often called a track buffer for this reason). Then, on subsequent reads to the track, the disk will just return the desired data from its cache. File systems no longer have to worry about these incredibly low-level details. Abstraction and higher-level interfaces can be a good thing, when designed properly.

Other usability improvements were added as well. FPS was one of the first systems to allow for long file names, enabling more expressive names in the file system instead of the traditional fixed-size approach (e.g., 8 characters). Further, a new concept was called a symbolic link. As discussed in a previous chapter [AD14b], hard links are limited in that they could not point to directories (for fear of introducing loops in the file system hierarchy) and that they can only point to files or directory within the same volume (the node number must still be meaningful). Symbolic links allow the user to create an “alias” to any other file or directory on a system and are much more flexible. FPS also introduced an atomic rename() operation for renaming files. Usability improvements, beyond the basic technology, also likely gained FPS a stronger user base.

## TIP: MAKE THE SYSTEM USABLE

Probably the most basic lesson from FPS is that not only did it introduce the conceptually good idea of disk-aware layout, but it added a number of features that simply made the system more usable. Long file names, symbolic links, and a rename operation that worked atomically improved the utility of the system; while hard to write a research paper about (imagine trying to read a 14-page about “The Symbolic Link: Hard Link’s Lost Cost”), such small features made FPS more powerful and thus likely increased its chances for adoption. Making a system usable is often as more important than it does deep technical innovations.

## 41.8 Summary

The introduction of FPS was a watershed moment in file system history, as it made clear that the problem of file management was one of the most interesting issues within an operating system, and showed how one might begin to deal with that most important of devices, the hard disk. Since that time, hundreds of new file systems have developed, but still today many file systems take cues from FPS (e.g., Linux ext2 and ext3) are obvious intellectual descendants. Certainly all modern systems account for the main lesson of FPS: treat the disk like it’s a disk.
