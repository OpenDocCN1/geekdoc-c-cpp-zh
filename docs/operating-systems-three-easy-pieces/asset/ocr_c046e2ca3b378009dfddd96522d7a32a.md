To reuniteite the other pages of this physical block, and thus be able to refer to them by a single block pointer, the FTL performs what is called a partial merge. In operation, logic blocks 1002 and 1003 are read from physical block 2, and then appended to the log. The resulting state of the SSD is the same as the switch merge above; however, in this case, the FTL had to perform extra I/O to achieve its goals, increasing write amplification.

The final case encountered by the FTL known as a full merge, and requires more even. In this case, the FTL must put together from many blocks to perform cleaning. For example, imagine that logic blocks 0, 4, 8, and 12 are written to log block A. To switch this block into a block-mapped page, the FTL must create a data block containing logic blocks 0, 1, 2, and 3, and then the FTL must merge 1, 2, and 3 from elsewhere and write out 0, 1, 2, and 3. Next, the merge must do the same for logic block 4, finding 5, 6, and 7 and reconciling them into a single physical block. The same must be done for blocks 8 and 12, and then (finally), the log block can be freed. Frequent full merges, as is not surprising, seriously harm performance and thus should be avoided when at possible [GY+09].

# Page Mapping Plus Caching

Given the complexity of the hybrid approach above, others have suggested ways to reduce the memory load of page-mapped FTLs. Probably the simplest is to cache only the active parts of the FTL in memory, reducing the amount of memory needed [GY+09].

This approach can work well. For example, if a given workload accesses a small set of pages, the translations of those pages will be stored in the in-memory FTL, and performance will be excellent without high memory cost. Of course, the approach can also perform poorly. If memory cannot contain the entire set of translations, each access will minimally require an extra read to bring the first mapping before accessing the data. Even, to make room for the new mapping, the FTL might have to evict an old mapping (not yet written to the flash persistently), an extra write will be incurred. However, in many cases, the workload will display locality, and this caching will both reduce memory overheads and keep high performance.
