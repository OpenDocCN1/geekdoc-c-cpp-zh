To reunite the other pages of this physical block, and thus be able to refer to them by a single block pointer, the FTL performs what is called a partial merge. In operation, logic blocks 1002 and 1003 are read from physical block 2, and then appended to the log. The resulting state of the SSD is the same as the switch merge above; however, in this case, the FTL had to perform extra I/O to achieve its goals, increasing write amplification.

The final case encountered by the FTL known as a full merge, and requires more even. In this case, the FTL must put together from many blocks to perform cleaning. For example, imagine that logic blocks 0, 4, 8, and 12 are written to log block A. To switch this block into a block-mapped page, the FTL must create a data block containing logic blocks 0, 1, 2, and 3, and then the FTL must merge 1, 2, and 3 from elsewhere and write out 0, 1, 2, and 3. Next, the merge must do the same for logic block 4, finding 5, 6, and 7 and reconciling them into a single physical block. The same must be done for blocks 8 and 12, and then (finally), the log block can be freed. Frequent full merges, as is not surprising, seriously harm performance and thus should be avoided when possible.

# Page Mapping Plus Caching

Given the complexity of the hybrid approach, others have suggested ways to reduce memory load of page-mapped FTLs. Probably the simplest is to cache only the active parts of the FTL in memory, reducing the amount of memory needed. This approach can work well. For example, if a given workload accesses a small set of pages, the translations of those pages will be stored in the in-memory FTL, and performance will be excellent without high cost. Of course, the approach can also perform poorly. If memory cannot contain the entire set of translations, each access will minimally require an extra read to bring the data. Even, to make room for the new mapping, the FTL might have to evict an old mapping (not yet written to flash), an extra write will be incurred. However, in many cases, the workload will display locality, and this caching will both reduce overheads and keep high performance.

# Wear Leveling

Finally, a related background activity that modern FTLs must implement is wear leveling. The basic idea is simple because multiple erase/program cycles will wear out a flash block, the FTL should try its best to spread work across all the blocks of device evenly. In this manner, all blocks will wear out at the same time, instead of a few "popular" blocks becoming unusable. However, sometimes a block will be filled with long-lived data that does not get overwritten; this, garbage collection will never reclaim the block, and thus does not receive its share of the load. To remedy this, the FTL must periodically read the live data out of such blocks and re-write it elsewhere, making the block available for writing again. This process of wear leveling increases the write amplification of the SSD, and thus decreases performance as I/O is required to ensure that all blocks work at the same rate. Many different algorithms exist in the literature; read more if you are interested.

# Performance

Before closing, we examine the performance and cost of modern SSDs, to understand how they will be used in storage systems. In both cases, we'll compare to classic hard-disk drives (HDDs), and highlight the biggest differences between the two. Unlike disk drives, flash-based SSDs have no mechanical components, and in fact are similar to DRAM, in that they are "random access" devices. The biggest difference in performance, compared to disk drives, is realized when performing random reads and writes; while a typical disk drive can perform only a few hundred IO per second, SSDs can do much better. Here, we use some data from modern SSDs to see how much better SSDs perform; we're particularly interested in how the FTL hide the performance issues of the raw chips.
