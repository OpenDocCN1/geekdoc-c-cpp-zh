> ASIDE: READS DON'T ACCESS ALLOCATION STRUCTURES
We've seen many students get confused by allocation structures such as bitmaps. In particular, many often think that when you are reading a file, and not allocating any new blocks, that the bitmap will be consulted. This is not true! Allocation structures, as bitmaps, are only accessed when allocation is needed. The inodes, directories, and indirect blocks have all the information they need to complete a read request; there is no need to make sure a block is allocated when the inode points to.

Yes, life can get busy when reading a file; as you're about to find out, writing a file (and especially, creating a new) is even worse.

Thus, each write to a file logically generates five I/Os: one to read the data bitmap (which is then updated to the newly-allocated block as used), one to write the bitmap (to reflect its new state to disk), two more to read and write the inode (which is updated with the new block's location), and finally to write the actual block.

The amount of write traffic is worse when one considers a simple and common operation such as file creation. To create a file, the file system must not only allocate an inode, but also allocate space within the directory containing the new file. The total amount of I/O traffic is quite high: one to read the inode bitmap (to find a free inode), one to write the new inode (to initialize it), one to the data of the directory (to link the high-level name of the file to its inode number), and one read and write to the directory inode to update it. If the directory needs to grow to accommodate the new entry, additional I/Os (i.e., to the data bitmap, and the new directory block) will be needed too. All that just to create a file!

# THE CRUX: HOW TO REDUCE FILE SYSTEM I/O COSTS

The simplest of operations like opening, reading, or writing a file incurs a huge number of I/O operations, scattered over the disk. What can a file system do to reduce the high costs of doing so many I/Os?

# 40.7 Caching and Buffering

As the examples above show, reading and writing files can be expensive, incurring many I/Os to the (slow) disk. To remedy what would clearly be a huge performance problem, file systems aggressively use memory (DRAM) to cache important blocks.

Imagine the open example above: without caching, every file would require at least two reads for every level in the file directory (one to read the inode of the directory in question, and at least one to read its data). With a long pathname (e.g., /1/2/3... /100/file.txt), the file system would literally perform hundreds of reads just to open the file!

Early systems then introduced a fixed-size cache to hold popular blocks. As in our discussion of virtual memory, strategies like LRU and different variants would decide which blocks to keep. This fixed-size cache would usually be allocated at boot time to be roughly 10% of memory.

This static partitioning of memory, however, can be wasteful; if the file system doesn't need 10% of memory at a given point in time. With the fixed-size approach above, unused pages in the file cannot be re-purposed for some use.

Modern systems, in contrast, employ a dynamic partitioning approach. Specifically, many operating systems integrate virtual memory and file pages into a unified page cache. In this way, memory can be allocated more flexibly.

> TIP: UNDERSTAND STATIC VS. DYNAMIC PARTITIONING
When dividing a resource among different clients/users, you can use either static partitioning or dynamic partitioning. The static approach simply divides the resource into fixed proportions once; for example, if there are two possible users of memory, you can give some fixed fraction of memory to one user, and to the other. The dynamic approach is more flexible, giving out different amounts of the resource over time; for a period of time, but then later, the system may switch and decide to give a different user a larger share of disk bandwidth.

Each approach has its advantages. Static partitioning ensures each user receives some share of the resource, usually delivers more predictable performance, and is often easier to implement. Dynamic partitioning can achieve better utilization (by letting resource-hungry users consume other idle resources), but can be more complex to implement, and can lead to worse performance for users whose idle resources get consumed by others and take a long time to reclaim when needed. As often case, there is no best method; rather, you should think about the problem and decide which approach is most suitable. Indeed, shouldn't you always be doing that?
