# 43.12 Crash Recovery And The Log

One final problem: what happens if the system crashes while LFS is writing to disk? As you recall in the previous chapter about journaling, crashes during updates are tricky for file systems, and thus something LFS must consider as well.

During normal operation, LFS buffers writes in a segment, and then (when the segment is full, or when some time has elapsed), writes the segment to disk. LFS organizes these in a log, the checkpoint region points to a head and tail segment, and each segment points to the next to be written. LFS also periodically updates the checkpoint region. Crashes could clearly happen during either of these operations (write to a segment, or write to disk). So how LFS handles crashes during these structures?

Let's cover the second case first. To ensure that the CR updates atomically, LFS creates two CR, one at each end of the disk, and writes to them alternately. LFS implements a careful protocol when updating the CR with pointers to the inode map and other information;,, first writes a header (with timestamp), then the body of the CR, and then finally one last (also with a timestamp). If the system crashes during a CR update, LFS can detect this by seeing an inconsistent pair of timestamps. LFS will always choose to the most recent CR that has consistent timestamps, and thus consistent update of the CR is achieved.

Let's now address the first case. Because LFS crashes every 30 seconds or so, the last snapshot of the file system may be quite old. Thus, upon reboot, LFS can easily recover by simply reading the checkpoint region, the im pieces pieces to, and subsequent files and directories; however, the last many of updates would be lost.

To improve upon this, LFS tries to rebuild many of those segments through a technique known as roll forward in the database community. The basic idea is to start with the last checkpoint region, find the end of the log (which is included in the CR), and then use that to read through the next segments and see if there are any updates within. If there are, LFS updates the file system accordingly and thus recovers much of the data and metadata written since the last checkpoint. See Rosenblum's award-winning dissertation for details [R92].

# 43.13 Summary

LFS introduces a new approach to updating the disk. Instead of writing in places, LFS always writes to an unused portion of the disk, and then reclaims that old space through cleaning. This approach, which in database systems is called shadow paging [L77] and in file-system-speak is sometimes called copy-on-write, enables efficient writing, as LFS can gather all updates in an in-memory segment and then write them out sequentially.
