
# The Page Cache

To reduce costs of using persistent storage (the focus of the third part of this book), most systems use aggressive caching subsystems to keep popular data in memory. Linux, in this regard, is no different than traditional operating systems.

The Linux page cache is unified, keeping pages in memory from three sources: memory-mapped files, data and metadata from devices (usually accessed by directing read() and write() calls to the system), and heap stacks that comprise each process (sometimes called anonymous memory, because there is no name file underneath it, but swap space). These entities are kept in a page cache hash table, allowing for quick setup when data is needed.

The page cache tracks clean (read but not updated) or dirty (a.k.a., modified). Dirty data is periodically written to the backstore (i.e., to a specific file data, or to swap for anonymous regions) by background threads (called flush()), ensuring that modified data eventually gets written back to persistent storage. This background activity either after a certain period or if many pages are considered dirty (both configurable parameters).

In some cases, a system runs low on memory, and Linux has to decide which pages to kick out of memory to free space. To do so, Linux uses a modified form of 2Q replacement [JS94], which we describe here.

The basic idea is: standard LRU replacement is effective, but if a process repeatedly accesses a large file (especially one that is nearly the size of memory, or larger), LRU will kick every file out of memory. Even when retaining portions of this file in memory is useful, as they are never re-referenced before getting kicked out of memory.

The Linux version of the 2Q replacement algorithm solves this by keeping two lists, and dividing memory between them. When accessed for the first time, a page is placed on one queue (called A1 in the original paper, but inactive list in Linux); when it is re-referenced, the page is promoted to the other queue (called A2 in the original, but active list in Linux). When memory runs low and eviction takes place, the candidate for replacement is taken from the inactive list. Linux also moves pages from the bottom of the active list to the inactive list, keeping up two-thirds of the total page cache size [G04].

Linux would ideally manage these lists in LRU order, but, as discussed in earlier chapters, doing so is costly. Thus, with many OSes, an approximation of LRU (similar to clock replacement) is used.

This 2 approach generally behaves a bit like LRU, but notably handles the case where a cyclic large-file access occurs by confining the pages of cyclic access to the inactive list. Because said pages are never re-referenced before getting kicked out of memory, they do not flush other useful pages found in the active list.

# ASIDE: THE UBIQUITY OF MEMORY-MAPPING

Memory mapping predates Linux by some years, and is used in many places within Linux and other modern systems. The idea is simple: calling mmap() does not copy an already opened file descriptor, a process is returned a pointer to the beginning of a region of virtual memory where the contents of the file be located. By using that pointer, a process can access any of the file with a simple pointer dereference.

Accesses to a memory-mapped file that have not yet been brought into memory trigger page faults, at which point the OS will page the relevant data and make it accessible by updating the page table (i.e. demand paging).

Every regular Linux process uses memory-mapped files, even the code in main() does not call map() because of how Linux loads the code from the executable and shared library code into memory. Below is (highly abbreviated) output of the pmap command line tool, shows different mapping comprise the virtual address space of a running program (the shell, in this example, tsh). The output shows four columns: the virtual address of the mapping, its size, the protection of bits, and the source of the mapping:

```
0000000000  372K r-x-- tsh
0000000001d95000  178K rw---- [ anon ]
0000000f4e7cf06000 1792K r-x-- libc-2.23.so
0000000f4e7d2d2000   36K r-x-- libcrypt-2.23.so
0000000f4e7d508000  148K r-x-- libinfo.so.5.9
0000000f4e7d731000  152K r-x-- id-2.23.so
0000000f4e7d932000   16K rw---- [ stack ]
```

As you can see from the output, the code of the tsh binary, as code from lib, libcrypt, libinfo, and code from the dynamic linker itself (id.so) are all mapped into the address space. Also present are two anonymous regions, the heap (the second entry, labeled anon) and the stack (labeled stack). Memory-mapped files provide a straightforward and efficient way for the OS to construct a modern address space.

# Security And Buffer Overflows

Probably the biggest difference between modern VM systems (Linux, Solaris, or one of the BSD variants) and ancient (VAX/VMS) is the emphasis on security in the modern era. Protection has always been a serious concern for operating systems, but with machines more interconnected than ever, it is no surprise that developers have implemented a variety of countermeasures to halt wildly hackers from gaining control of systems.

# COMPLETE VIRTUAL MEMORY SYSTEMS

One major threat is found in buffer overflow attacks², which can be used as normal user programs and even the kernel itself. The idea of these attacks is to find a bug in the target system which lets the attacker inject arbitrary data into the target's address space. Such vulnerabilities sometime arise because the developer (erroneously) assumes that input will not be overly long, and then (trustingly) copies the input into a buffer; because the input is in fact too long, it overflows the buffer, overwriting the memory of the target. Code as in the below can be

```
int some_function(char *input) {
char dest_buffer[100];
strcpy(dest_buffer, input); // oops, unbounded copy!
}
```

In many cases, such an overflow is not catastrophic, e.g., bad input inadvertently given to a user program or the OS will probably cause it to crash, without worse. However, malicious programmers can carefully craft the input that overflows the buffer so to inject their own code into the targeted system, essentially allowing them to take over and do their own bidding. If successful a network-connected or even run cycles on the compromised system; the attack can access more resources, and is in a form of what is called privilege escalation (i.e., user gaining kernel access rights). If you can't guess, these are all Bad Things.

The first and most simple defense against buffer overflow is to prevent execution of any code within certain regions of an address space (e.g., within the stack). The NX bit (No-Execute), introduced by AMD in their version of x86 (a similar bit is now available on Intel's), is one such defense; it prevents execution from any page which has its bit set in the paging table entry. The approach prevents code, injected by an attacker into the target's stack, from being executed, and mitigates the problem.

However, clever attackers are clever, and when injected code cannot be edited by the attacker, arbitrary code sequences can be executed by malicious code. The idea is known, in its most general, as a return-oriented programming (ROP) [507], and it really is quite brilliant. The observation about ROP is that there are lots of bits of code (gadgets, in ROP terminology) within any program's address space.

To defend against ROP (its earlier form, the return-to-libc attack [+04]) Linux (and other systems) add another defense, known as address space randomization (ASLR). Instead of placing code, stack, and the heap at fixed locations within the address space, the OS randomizes their placement, making it quite challenging to craft the intricate code to implement this class of attacks. Interestingly, you can observe this randomness in practice easily. Here's a piece of code that demonstrates it on a modern system:

```
int main(int argc, char *argv[]) {
    int stack = 0;
    printf("%p\n", &stack);
    return 0;
}
```

In non-ASLR systems, this value of a variable on the stack would be the same. But, as you can see below, the value changes with run:

