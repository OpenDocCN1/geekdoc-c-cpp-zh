## Non-Deadlock Bugs: Summary

A large fraction (97%) of non-deadlock bugs studied by Lu et al. are either atomicity or order violations. Thus, by carefully thinking about these types of bugs, programmers can likely do a better job of avoiding them. Moreover, as more automated code-checking tools develop, they should likely focus on these two types of bugs as they constitute a large fraction of non-deadlock bugs found in deployment.

Unfortunately, not all bugs are as fixed as the examples we looked at. Some require a deeper understanding of what the program is, or a larger amount of code or data structure reorganization to fix. Read Lu et al.’s (excellent and readable paper) for more details.

## 32.3 Deadlock Bugs

Beyond the concurrency bugs mentioned above, a classic problem that arises in modern systems with complex locking protocols is known as deadlock. Deadlock occurs, for example, when a thread (Thread 1) is holding a lock (L1) and waiting for another (L2); unfortunately, the thread (Thread 2) that is waiting for L2 to be released. Here is a code snippet that demonstrates a potential deadlock:

```
Thread 1:
pthread_mutex_lock(L1);
pthread_mutex_lock(L2);

Thread 2:
pthread_mutex_lock(L2);
pthread_mutex_lock(L1);
```

## Why Do Deadlocks Occur?

As you may be thinking, simple deadlocks such as the one seem readily avoidable. For example, if Thread 1 and 2 both made to grab locks in the same order, the deadlock would never arise. Why do deadlocks happen?

One reason is in large code bases, complex dependencies arise. Take the operating system, for example. The memory system might need to access the file system, the file system might page into disk.

Another reason is due to encapsulation. As software developers, we are taught to hide details of implementations. Unfortunately, this does not mesh well with locking. For example, the Java class and the method invite deadlock. Thus, a partial ordering can be a useful way to structure lock acquisition so to avoid deadlock. ## Conditions for Deadlock

Four conditions need to hold for deadlock to occur [C+71]:

- Mutual exclusion: Threads claim exclusive control of resources they require (e.g., a thread grabs a lock).
- Hold-and-wait: Threads hold resources allocated to them (e.g., locks they have already acquired) while waiting for additional resources (e.g., locks they wish to acquire).
- No preemption: Resources (e.g., locks) cannot be forcibly removed from threads.
- Circular wait: There exists a circular chain of threads such that each thread holds one or more resources (e.g., locks) that are being requested by the next thread in the chain.

If any of these four conditions are not met, deadlock cannot occur. Thus, we first explore techniques to prevent deadlock; each strategy seeks to prevent one of the above conditions from arising and thus is one approach to handling the deadlock problem.

## Prevention Circular Wait

Probably the most practical prevention technique is to write your locking code such that you never induce a circular wait. The most straightforward way to do that is to provide a total ordering on acquisition. For example, if there are only two locks in the system (L1 and L2), you can prevent deadlock by always acquiring L1 before L2. Strict ordering ensures that no circular wait arises, no deadlock.

Of course, in more complex systems, more than two locks will exist, and thus total ordering may be difficult to achieve (and perhaps unnecessary anyhow). Thus, a partial ordering can be a useful way to structure lock acquisition so to avoid deadlock.
