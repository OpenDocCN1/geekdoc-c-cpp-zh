# INTERLUDE: FILES AND DIRECTORIES

TIP: BEWARE OF TOCTOU

In 1974, McPhee noted a problem in computer systems. Specifically, McPhee noted that “... if there exists a time interval between a validity-check and the operation with validity-check, [and,] through multitasking, the validity-check variables be be changed during this time interval, resulting in an invalid operation performed by the control program.” We call this the Time Of Check To Use (TOCTOU) problem, and also, it can occur.

A simple example, as described by Bishol and Didier [BD96], shows how a user can create a raced file and cause trouble. Imagine, that a mail service runs as root (and thus privileges to access all files on a system). This service appends an incoming message to a user's inbox as follows. First, it calls stat() to get information about the file, specifically ensuring that it is just a regular file owned by the user, and not a link to another file that the mail server should not update. Then, if the check succeeds, the server updates the file with the new message.

Unfortunately, the gap between the check and the update leads to a problem: the attacker (in the user, who is receiving the mail, and the attacker) switches the access to file (via a call to rename()) to point to a sensitive file as /etc/passwd (which holds information about users and their passwords). If this switch happens at the right time (between the check and the access), the server will gladly let attacker write to the sensitive file by sending an email, an escalation in privilege: updating /etc/passwd gives attacker control of the system.

There are not any simple solutions to the TOCTOU problem [T+08]. One approach is to reduce the number of services that need root privileges to run, which helps. The NOFOLLOW flag makes it that open() fails if the target is a symbolic link, avoiding attacks that require such. More radical approaches, such as using a transactional file system [H+18], would solve the problem, there aren't many transactional file systems in wide deployment. The usual, (lame) advice: be careful when you write code that runs with high privileges!
