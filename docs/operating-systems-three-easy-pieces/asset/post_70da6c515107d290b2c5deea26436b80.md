
# Lock-based Concurrent Data Structures

Before moving locks, we'll first describe how to use locks in some common data structures. Adding locks to a data structure to make it usable by threads makes the structure thread safe. Of course, exactly how such locks are added determines both the correctness and performance of the data structure. And thus, our challenge:

> CRUX: HOW TO ADD LOCKS TO DATA STRUCTURES
> When a particular data structure, how should we add locks to it, in order to make it work correctly? Further, how do we add locks such that the data structure yields high performance, enabling many threads to access the structure at once, i.e., concurrently?

Of course, we will be hard to cover all data structures or all methods for adding concurrency, as this is a topic that has been studied for years, with (literally) thousands of research papers published about it. Thus, we hope to provide a sufficient introduction to the type of thinking required, and refer you to some good sources of material for further inquiry on your own. We found Moir and Shavit's survey to be a great source of information [MS04].

## 29.1 Concurrent Counters

One of the simplest data structures is a counter. It is a structure that is commonly used and has a simple interface. We define a simple non-concurrent counter in Figure 29.1.

### Simple But Not Scalable

As you can see, the non-synchronized counter is a trivial data structure, requiring a tiny amount of code to implement. Now we have our next challenge: how we can make this thread safe? Figure 29.2 shows how we do so.

```c
typedef struct __counter_t {
    int value;
} counter_t;

void init(counter_t *c) {
    c->value = 0;
}

void increment(counter_t *c) {
    c->value++;
}

void decrement(counter_t *c) {
    c->value--;
}

int get(counter_t *c) {
    return c->value;
}
```

Figure 29.1: A Counter Without Locks

This concurrent counter is simple and works correctly. In fact, it follows a design pattern common to the simplest and most basic concurrent data structures: it adds a single lock, which is acquired when following a routine that manipulates the data structure, and is released when returning from the call. In this manner, it is similar to a data structure built with monitors [BH73], where locks are acquired and released automatically as you call and return from object methods.

At this point, you have a working concurrent data structure. If your data structure is too slow, you'll have to do more than just add a single lock; such optimizations, if needed, are the topic of the rest of the chapter. Note that if the data structure is not too slow, you do not need to do anything; simple will work well.

To understand the performance costs of the simple approach, we run a benchmark in which each thread updates a shared counter a million times; we vary the number of threads. Figure 29.5 shows the total time taken, with one to four threads; each updates the counter one million times. This experiment was run upon an iMac with Intel 2.7 GHz CPUs; with more CPUs, we have to get more total work done per unit time.

From the top line in the figure (labeled ‘Precise’), you can see that the performance of the synchronized counter scales poorly. While a single thread can complete the million counter updates in a tiny amount of time (roughly 0.03 seconds), having two threads each update the counter one million concurrently leads to a massive slowdown (taking over 5 seconds!). It only gets worse with more threads.

```c
typedef struct __counter_t {
    int value;
    pthread_mutex_t lock;
} counter_t;

void init(counter_t *c) {
    c->value = 0;
    pthread_mutex_init(&c->lock, NULL);
}

void increment(counter_t *c) {
    pthread_mutex_lock(&c->lock);
    c->value++;
    pthread_mutex_unlock(&c->lock);
}

void decrement(counter_t *c) {
    pthread_mutex_lock(&c->lock);
    c->value--;
    pthread_mutex_unlock(&c->lock);
}

int get(counter_t *c) {
    pthread_mutex_lock(&c->lock);
    int rc = c->value;
    pthread_mutex_unlock(&c->lock);
    return rc;
}
```

Ideally, you'd like to see the threads complete as quickly as multiple processors as the single thread does. Achieving this is called perfect scaling; even though more work is done, the time taken is not increased.

### Scalable Counting

To make this clear, let's look at an example (Figure 29.3). In this example, each CPU has its own local counter, and the global counter is updated only when the local counter reaches a threshold. The smaller S is, the more it behaves like the non-synchronized counter; the bigger S is, the more scalable it is.

(Note: The OCR text for the table in Figure 29.3 was fragmented in the source. Based on the context of Scalable Counting, the following is the reconstructed logic for a scalable approximate counter.)

```c
typedef struct __counter_t {
    int global;
    pthread_mutex_t glock;
    int local[NUMCPUS];
    pthread_mutex_t locks[NUMCPUS];
    int threshold;
} counter_t;

// init: record threshold, init locks, init values
// of all local counts and global count
void init(counter_t *c, int threshold) {
    c->threshold = threshold;
    c->global = 0;
    pthread_mutex_init(&c->glock, NULL);
    for (int i = 0; i < NUMCPUS; i++) {
        c->local[i] = 0;
        pthread_mutex_init(&c->locks[i], NULL);
    }
}

// update: usually, just grab local lock and update
// local amount; local count has risen 'threshold',
// grab global lock and transfer local values to it
void update(counter_t *c, int threadID, int amt) {
    int cpu = threadID % NUMCPUS;
    pthread_mutex_lock(&c->locks[cpu]);
    c->local[cpu] += amt;
    if (c->local[cpu] >= c->threshold) {
        // transfer to global (assumes amt>0)
        pthread_mutex_lock(&c->glock);
        c->global += c->local[cpu];
        pthread_mutex_unlock(&c->glock);
        c->local[cpu] = 0;
    }
    pthread_mutex_unlock(&c->locks[cpu]);
}

// get: return global amount (approximate)
int get(counter_t *c) {
    pthread_mutex_lock(&c->glock);
    int val = c->global;
    pthread_mutex_unlock(&c->glock);
    return val; // only approximate;
}
```
