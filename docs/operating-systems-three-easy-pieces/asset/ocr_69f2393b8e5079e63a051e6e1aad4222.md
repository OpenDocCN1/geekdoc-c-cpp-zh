# A Dialogue on Memory Virtualization

**Student**: So, we are done with virtualization?

**Professor**: No!

**Student**: Well, no reason to get excited; I was just asking a question. Students are supposed to do that, right?

**Professor**: Well, professors always say that, but really they mean this: ask questions, *if* they are good questions, and *you* have actually put a little thought into them.

**Student**: That sure takes wind out of my sails.

**Professor**: Mission accomplished. In any case, we are not nearly done with virtualization! You have just seen how to virtualize the CPU, but really there is a monster waiting in the closet: Virtualizing memory is complicated and requires us to understand many more intricate details about how the hardware and OS interact.

**Student**: That sounds cool. Why is it so hard?

**Professor**: Well, there are a lot of details, and you have to keep them straight in your head while develop a mental model of what is going on. We'll start, with very basic techniques like/bounds, and slowly add complexity to tackle new challenges, including fun topics like TLBs and multi-level page tables. Eventually, we'll be able to describe the workings of a fully-functional modern virtual memory manager.

**Student**: Not! Any tips for the poor student, inundated with all of this information and generally sleep-deprived?

**Professor**: For the sleep deprivation, *that's easy*: sleep more (and part less). For understanding virtual memory, start with *every address generated by a user program is a virtual address*. The OS is just providing an illusion to each process, specifically that it has its own large and private memory; with some hardware help, the OS will turn these pretend virtual addresses into real physical addresses, and thus be able to locate the desired information.
