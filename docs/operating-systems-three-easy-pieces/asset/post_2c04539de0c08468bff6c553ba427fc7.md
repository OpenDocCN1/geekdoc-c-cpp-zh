## 50.3 Improving the Protocol

The two problems above limited the scalability of AFS; each server CPU became the bottleneck of the system, and each server could only serve twenty clients without becoming overloaded. Servers were receiving too many TestAuth messages, and when they received Fetch or Store messages, spending much time traversing the directory hierarchy. Thus, the AFS designers faced with a problem:

> THE CRUX: HOW TO DESIGN A SCALABLE FILE PROTOCOL

How should one redesign the protocol to minimize the number of server interactions, i.e., how could they reduce the number of TestAuth messages? Further, could they design the protocol to make the server interactions efficient? By attacking both of these issues, a new protocol would result in a much more scalable version AFS.

## 50.4 AFS Version 2

AFSv2 introduced the notion of a callback to reduce the number of client/server interactions. A callback is simply a promise from the server to the client that the server will inform the client when a file that the client is caching has been modified. By adding this state to the system, the client no longer needs to contact the server to find out if cached file is still valid. Rather, notice the analogy to polling versus interrupts.

AFSv2 also introduced the notion of a file identifier (FID) (similar to the NFS file handle) instead of pathname. In AFS a copy of FID can specify which file was interested in. An FID contains a uniquifier (to enable reuse of the volume and file IDs when a file is deleted). Thus, instead of sending the pathname to the server and letting the server walk the desired file, the client would walk the pathname, one piece at a time, caching the results and hopefully reducing the load on the server.

For example, if a client accessed the file /home/remzi/notes.txt, and home was the AFS directory mounted onto (i.e., / was the root directory, but home and its children were in AFS), the client would first Fetch the contents of home, put them in the local-disk cache, and set up a callback on home. Then, the client would Fetch the directory remzi, put it in the local-disk cache, and set up a callback on remzi. Finally the client would Fetch notes.txt

The benefit is obvious: although the first access to /home/remzi.txt generates many client-server messages (as above), it also establishes callbacks for all the directories.

When discussing distributed file systems, much is made of the cache consistency the file systems provide. However, this baseline consistency does not solve all problems with regards to file access from multiple clients. For example, if you are building a repository, with multiple clients performing check-ins and check-outs of code, you can't simply rely on the file system to do all the work for you; rather, you must use explicit file-locking in order to ensure that the "right thing" happens when concurrent access takes place. Indeed, an application that cares about concurrent updates will add extra machinery to handle clients. The baseline consistency described in this chapter and the previous one are useful primarily for casual usage, i.e., when a user logs into a system and expects some reasonable version of their files to show up there. Expecting from more these protocols is setting yourself for failure, disappointment, and tear-frustrated frustration.

## 50.5 Cache Consistency

When we discussed NFS, there were two aspects of cache consistency we considered: update visibility and cache staleness. With update visibility, the question is: will the server be updated with a new version of a file? With cache staleness, the question is: once the server has a new version, how long before clients see the new version instead of an older copy?

Because of callbacks and whole-file caching, the cache consistency provided by AFS is easy to describe and understand. There are two important cases to consider: consistency between processes on different machines, and consistency between processes on the same machine.

Between different machines, AFS makes updates visible at the server and invalidates cached copies at the exact time, which is when the updated file is closed. A client opens a file, and then writes to it (perhaps repeatedly). When it is finally closed, the server then "breaks" callbacks for all clients with cached copies (and thus visible). At this point, the break is accomplished by contacting each client and informing them that the callback on the file is no longer valid. This step ensures that clients will no longer read stale copies of the file; subsequent opens on clients will require a re-fetch of the new version of the file from the server (and will serve to reestablish a callback on it).

AFS makes an exception to this simple model between processes on the same machine. In this case, writes to a file are not immediately visible to other local processes (i.e., a process does not have to wait until a file is closed to see its latest updates), making using a single machine behave exactly as you would expect, as this behavior is expected upon typical UNIX systems. Only when switching to a different machine would you be able to detect the more general ARFS consistency mechanism.

There is one interesting cross-machine case that is worthy of further discussion. In the rare case that processes on different machines are modifying a file at the same time, AFS naturally employs what is known as a *last writer wins* approach (which perhaps should be called *last closer wins*).
