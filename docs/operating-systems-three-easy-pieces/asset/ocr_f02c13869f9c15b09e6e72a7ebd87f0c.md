# 6.3 Problem #2: Switching Between Processes

The next process with direct execution is achieving a switch between processes. Switching between processes should be simple, right? The OS should decide to stop one process and start another. What's the big deal? It is actually a little tricky: specifically, if a process is running on the CPU, then by definition means the OS is not running. If the OS is not running, how can it do anything at all? (hint: it can't) While this sounds philosophical, it is a real problem: there is no way for the OS to take an action if it is not running on the CPU. Thus we arrive at the crux of the problem.

> THE CRUX: How To Regain Control Of The CPU
How can the operating system regain control of the CPU so that it can switch between processes?

# A Cooperative Approach: Wait For System Calls

One approach that some systems have taken in the past (for example, early versions of the Macintosh system [M11], or the old Xerox Alto system [A79l]) is known as the cooperative approach. In this style, the OS trusts the processes of the system to behave reasonably. Processes that are too long are allowed to periodically give up the CPU so that the OS can decide to run some other task.

Thus, you might ask, does a friendly process give up the CPU in this uncertain world? Most processes transfer control to the OS quite frequently by making system calls, for example, to open a file and subsequently read it, or to send a message to another machine, or to create a new process. Systems like this often yield system call, which does nothing except transfer control to the OS so it can run other processes.
