
## 19.5 TLB Issue: Context Switches

With TLBs, some new issues arise when switching between processes (and address spaces). Specifically, the TLB contains virtual-to-physical translations that are only valid for the currently running process; these translations are not meaningful for other processes. As a result, when switching from one process to another, the hardware OS (or both) must be careful that the about-to-be-run process does not accidentally use translations from some previous run.

To understand this situation better, let's look at an example. When one process (P1) is running, it assumes the TLB might caching translations that are valid for it, i.e., that from its 10th page P1 is mapped to physical frame 100.

In the example, assume another process (P2), and the OS might decide to perform a context switch and run it. Assume that the 10th virtual page of P2 is mapped to physical frame 170. If entries for both processes were in the TLB, the contents of the TLB would be:

| VPN | PFN | prot |
| --- | --- | --- |
| 10 | 100 | 1 |
| 10 | 170 | 1 | rwx |

In the TLB above, we clearly have a problem: VPN 10 translates to either PFN 100 (P1) or PFN 170 (P2), but the hardware cannot distinguish which entry is for which process. Thus, we need to do some work in order for the TLB to correctly and efficiently support virtualization across multiple processes. And thus, a crux:

> THE CRUX:
> To Manage TLB Contents On A Context Switch
> When context-switching between processes, the translations in the TLB for the last process are not meaningful to the about-to-be-run process. What should the hardware or OS do to solve this problem?

There are a number of possible solutions to this problem. One approach is to flush the TLB on context switch, emptying it before the new process runs. On a software-based system, this can be accomplished with an explicit (and privileged) hardware instruction; with hardware-managed TLB, the flush could be enacted when the page-table base register is changed (the OS must change on a context switch anyway). In either case, the flush operation sets all valid bits to 0, essentially clearing the contents of the TLB.

By flushing the TLB on each context switch, we now have a working solution, as a process will never accidentally encounter the wrong translations in the TLB. However, there is a cost: each time process runs, it may incur TLB misses as it touches its data and code pages. If the OS switches between processes frequently, this cost may be high.

To reduce this overhead, some systems add hardware support to sharing of the TLB across context switches. In particular, some systems provide an address space identifier (ASID) field in the TLB. You can think of the ASID as a process identifier (PID), but usually it has fewer bits (e.g., 8 bits for ASID, 32 bits for a PID).

If we take our example TLB from above and add ASIDs, it is clear processes can share the TLB: only the ASID field is needed to differentiate identical translations. Here is a depiction of a TLB with the added ASID.

| VPN | PFN | valid | prot | ASID |
|---|---|---|---|---|
| | 100 | 1 | | 1 |
| | | 0 | | |
| 10 | 170 | 1 | rwx | 2 |
| | | — | | |

Thus, with address-space identifiers, the TLB can hold translations from different processes at the same time without any confusion. Of course, the hardware also needs to know which process is currently running in order to perform translations, and thus the OS must, on a context switch, set some privileged register to the ASID of the current process.

As an aside, you may also have thought of another case where two entries of the TLB are remarkably similar. Here are two entries for two different processes with different VPNs that point to the same physical page:

| VPN | PFN | valid | prot | ASID |
|---|---|---|---|---|
| 10 | 101 | 1 | r-x | 1 |
| | | 0 | | |
| 50 | 101 | 1 | r-x | 2 |
| | | 0 | | |

This situation might arise, when two processes share a page (a code page, for example). In the example above, Process 1 is sharing physical page 101 with Process 2; P1 maps this into the 10th page of its address space, whereas P2 maps it to the 50th page of its address space. Sharing of code pages (in binaries, or shared libraries) is useful as it reduces the number of physical pages in use, reducing memory overheads.

## 19.6 Issue: Replacement Policy

As with any cache, and also with the TLB, one more issue that we must consider is cache replacement. Specifically, when we are installing a new entry in the TLB, we have to replace an old one, and thus the question: which one to replace?

> THE CRUX:
> HOW TO DESIGN TLB REPLACEMENT POLICY
> Which TLB entry should be replaced when we add a new one? The goal, of course, is to minimize the miss rate (increase hit rate). We will study policies in detail; one common approach is the least-used (LRU), which evicts the entry that has not been used.

## 19.7 A Real TLB

Finally, let's briefly look at a real TLB. MIPS TLB software is managed, there needs to be instructions to update the TLB. The MIPS TLB provides four instructions: TLBP, which probes the TLB if a particular translation is in; TLBLR, which reads the contents of a TLB entry into registers; TLBI, which replaces a special TLB entry; and TLWI, which replaces a random TLB entry. The OS uses these instructions to manage the TLB’s contents. It is of crucial fact that these instructions are privileged; imagine what a user process could do if it modify the contents of the TLB (hint: just about anything, including taking over the machine, run its malicious “OS”).
