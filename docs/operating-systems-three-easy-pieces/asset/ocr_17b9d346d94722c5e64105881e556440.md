> TIP: LESS CODE IS BETTER CODE (LAUER’S LAW)

Programmers tend to brag about how much code they wrote to do something. Doing so is fundamentally broken. What one should brag about, rather, is how little code one wrote to accomplish a given task. Short, concise code is always preferred; it is likely easier to understand and have fewer bugs. As Hugh Lauer, when discussing the construction of the Pilot operating system “If the same people had twice as much time, they could produce as good of a system in half the cost.”[L81] We’ll call this Lauer’s Law, and it is well worth remembering. So next time you’re bragging about how much code you write to finish the assignment, think again, or better yet, go back, rewrite, and make the code as clear and concise.

In this example, we will use fetch-add-and to build a more interesting ticket lock, introduced by Mellor-Crummey and Scott [MS91]. The lock and unlock code is found in 28.7 (page 344).

Instead of a simple value, solution uses a ticket and turn variable to build a lock. The basic operation is pretty simple: when a thread wishes to acquire a lock, it first does an atomic fetch-add-and on the ticket value; that is now considered this “turn”. The globally shared lock->turn is then used to determine which turn it is; when `mutex == turn` for a given thread, it is thread’s turn to enter the critical section. Unlock is accomplished by incrementing the turn such that the next thread (if there is one) can now enter the critical section.

One note important difference with this solution versus our previous attempts: it ensures progress for all threads. A thread is assigned its ticket value, it will be scheduled at some point in the future (once those in front of it will have passed through the critical section and released the lock). In our previous attempts, no such guarantee existed; a thread spinning on test-and-set (for example) could spin forever even as other threads acquire and release the lock.
