## 26.1 Why Use Threads?

Before getting into the details of threads and some of the problems you might have in writing multi-threaded programs, let's first answer a more simple question. Why should you use threads at all?

As it turns out, there are at least two major reasons you should use threads. The first is simple: parallelism. Imagine you are writing a program that performs operations on large arrays, for example, adding two large arrays together or incrementing the value of each element in the array by some amount. If you are running on just a single processor, the task is straightforward: perform each operation and be done. However, if you are executing the program on a system with multiple processors, you have the potential of speeding up this process by using processors to perform each portion of the work. The task of transforming your single-threaded program into a program that does this sort of work on multiple CPUs is called parallelization, using a thread per CPU to do what is a natural and typical way to make programs run on modern hardware.

The second reason is a subtle way to avoid blocking due to slow I/O. If you are writing a program that performs different types of I/O: either waiting to send or receive a message, or for a page to finish. Instead of waiting, your program may wish to do something else, utilizing the CPU for computation, or even issuing I/O requests. Using threads is a natural way to avoid getting stuck; while one thread in your program waits (i.e.- is blocked) the scheduler can switch to other threads, which are ready to do something else. Thread enables overlap of I/O with other activities within a single program, which makes multiprogramming for processes across programs; as a result, modern server-based applications (web servers, database management systems, and like) make use of threads in their implementations. Of course, in the cases mentioned above, you could use multiple processes instead of threads. However, threads share an address space and thus make it easy to share data, hence a natural choice when constructing these types of programs where little sharing of data structures is needed.

## 26.2 An Example: Thread Creation

Let's get into the details. Say we wanted to run a program that creates two threads, each of which does some work, printing “A” or “B”. The code is shown in Figure 26.2.

The main program creates two threads, each of which will run the function mythread() with different arguments (the string A or B). Once created, it may start running away (depending on the whims of the scheduler); alternately, it may be put in a “ready” state but not “running yet”. Of course, on a multiprocessor, the threads could even be running at the same time, but let’s not worry about this quite yet.

```c
#include <stdio.h>
#include <assert.h>
#include <pthread.h>
#include "common.h"
#include "common_threads.h"

void mythread(void *arg) {
    printf("%s\n", (char *)arg);
    return NULL;
}

int main(int argc, char *argv[]) {
    pthread_t p1, p2;
    int rc;
    printf("main: begin\n");
    // join threads for the threads to finish
    pthread_create(&p1, NULL, mythread, "A");
    pthread_create(&p2, NULL, mythread, "B");
    pthread_join(p1, NULL);
    pthread_join(p2, NULL);
    printf("main: end\n");
    return 0;
}
```

Figure 26.2: Simple Thread Creation (t0.c)

After creating the two threads (let's call them T1 and T2), the main thread calls pthread_join(), waits for a particular thread to complete. It does so, ensuring T1 and T2 will run and when it does, it will print "main exit" and exit. Overall, three threads were employed during this run: the main thread, T1 and T2.

Let us examine the possible ordering of execution of this little program. In the execution diagram (Figure 26.3), time increases in the downwards direction, and each column shows when a different thread (the main one, or Thread 1, or Thread 2) is running.

Note, however, this is not the only possible ordering. In fact, given a sequence of instructions, there are quite a few, depending on which thread the scheduler decides to run at a given point. For example, once a thread is created, it may run immediately, which would lead to the execution shown in Figure 26.4.

We also could see "B" printed before "A", if, say, the scheduler decided to run Thread 2 before even Thread 1 was created; there is no reason to assume that a thread that was created first will run first. Figure 26.5 shows this final ordering, with Thread 2 getting to its stuff before Thread 1.

As you might be able to see, one way to think about thread creation is that it is like making a function call; however, instead of first executing the function and then returning to the caller, the system creates a new thread of execution for the routine that is called, and it runs independently of the caller, perhaps returning before the caller, but perhaps much later.
