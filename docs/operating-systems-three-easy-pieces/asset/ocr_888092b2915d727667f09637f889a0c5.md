What we have demonstrated here is a race condition (or, specifically, a data race); the results depend on the timing execution of the code. With some luck (i.e., context switches at untimely points in the execution),get instead of a nice deterministic computation we get the wrong result. In fact, we get a different result each time; thus (which we use from computers), we call this result terminate, where it is not what the output will be and it is likely to be different races.

Because multiple threads executing this code can result in a race condition, we call this a critical section. A critical section is a piece of code that accesses a shared variable (or more generally, a shared resource) and must not be concurrently executed by more than one thread.

What we really want for this code we call mutual exclusion. This property guarantees that if one thread is executing within the critical section, the others will be prevented from doing so.

Virtually all of these terms, we were coined by Edsger Dijkstra, who was a pioneer in the field and won the Turing Award because of this and other work; see his 1968 paper on “Cooperating Sequential Processes” [D68] for an amazingly clear description of the problem. We’ll be hearing more about Dijkstra in this section of the book.
