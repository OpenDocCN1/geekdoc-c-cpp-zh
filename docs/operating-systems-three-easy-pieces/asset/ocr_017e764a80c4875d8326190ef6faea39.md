TIP: UNDERSTAND THE DURABILITY/PERFORMANCE TRADE-OFF
Storage systems often present a durability/performance trade-off to users. If the user wishes data that is written to be immediately durable, the system must go through the full effort of committing the newly-written data to disk, and then the write is slow (but). However, if the user can tolerate the loss of a little data, the system can buffer writes in memory for some time and write them later (in the background). Doing so makes writes appear quickly; improving performance however, if a crash occurs, writes not committed to disk will be lost, and hence the trade-off. To understand how to make this trade-off properly, it is best to understand what the application using the system requires; for example, while it may be tolerable to lose the last few images downloaded by your web browser, losing part of a database transaction is adding money to your account may be less tolerable. Unless you're rich, of course; in that case, why do you care so much about hoarding the last penny?

Some applications (such as databases) don't enjoy this trade-off. Thus, to avoid unexpected loss due to buffering, they simply force writes to disk, by calling fsync(), by using direct I/O interfaces that work around the cache, or by using the raw disk interface and interfacing the file system altogether. With the tradeoffs made by the system, there are enough controls in place to get the system to do what you want it to, the default will not be satisfying.

# 40.8 Summary

We have seen the machinery required in building a file system. There needs to be some information about each file (metadata), usually stored in a structure called an inode. Directories are just a specific type of file that store name→inode mappings. And other structures are needed too; for example, file systems often use a structure such as a bitmap to track which inodes or data blocks are free or allocated.
The terrific aspect of file design is its freedom; we explore in the coming chapters each take advantage of this freedom to optimize some aspect of the file system. There are clearly many policy decisions we have left unexplored. For example, when a new file is created, where should it be placed on disk? This policy and others will also be the subject of future chapters. Or will they?
