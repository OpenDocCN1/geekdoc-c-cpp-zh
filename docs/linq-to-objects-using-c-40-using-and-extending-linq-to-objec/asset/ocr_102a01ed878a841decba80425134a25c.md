You are not limited to the partitioners Microsoft has built-in. They have allowed for custom partitioners to be written for a specific purpose; this topic is beyond the scope of this book, but search online for Partitioner-ConfigSource for details. To understand each of the built-in partitioners and to understand their relative strengths and weaknesses, each one briefly explained.

**Range Partitioning** The range partitioning scheme breaks an input data set into equal-sized ranges optimized for the number of threads determined available (best case: equal to the number of cores available). Range partitioning is chosen when the data source is indexable (IList<T> and arrays). For indexable sources like these, the length is known when enumerating the data source (to determine the count), and the number of elements per partition for parallel execution is simply calculated upfront.

This partitioning scheme offers great parallel efficiency, largely from not needing any synchronization between participating threads. Threads get a range of data assigned to them and can process data without any interaction (incoming or outgoing) with other threads. The downside of this thread isolation is that other threads cannot help out if one thread gets behind in processing due to uneven utilization; on balance though, this partitioning scheme is efficient.

**Chunk Partitioning** Chunk partitioning is used when a data source isn't indexed (IEnumerable<T>) where the elements can be accessed by index and the count property cannot be ascertained without an enumeration of the entire data source.

Microsoft has optimized this partitioning scheme for a wide variety of queries, and although the exact algorithm isn't known, the responsible team's blog posts indicate that the number of elements per partition is doubled after a certain number of requests and so on. This allows this partitioning scheme to be adaptable from sources with only a few elements to sources with many million elements, keeping each core filled with work, while still balancing their load to ensure the greatest chance of each core finishing to the same time.

As mentioned previously, this partitioning algorithm can't be as exact as range partitioning, and you should strive for using an indexable collection for your parallel data sources whenever possible.
