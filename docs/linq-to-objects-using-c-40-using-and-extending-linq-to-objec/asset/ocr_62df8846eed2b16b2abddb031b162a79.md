The return type of the row values is declared as type List<dynamic>. It could easily have been declared as type List<object>. The downside of declaring the values as type of object rather than dynamic comes down to the ability to retrieve the value members as the underlying type. For example, in Listing 8-14 the statement row[lastNameCol].ToUpper() would fail if the element types were declared as object. The object type doesn't have a method called ToUpper, though the underlying type is representing string. To access that method a type cast needs to be added, bloating the code out to ((string)row[lastNameCol]).ToUpper(). Declaring the element as dynamic in the collection allows the runtime to look up method names using reflection on the underlying type at runtime, however, the particular type of that column value is declared as declared in Excel (in this case a string, but some columns are DateTime and double). The removal of the type cast when calling methods or objects simplifies and improves code readability, at the expense of performance.

The GetExcelEnumerator method could be enhanced by combining the header reading and accessibility in a similar fashion to that used by dynamic lookup in Listing 8-7, which would eliminate the need to hardcode the column index positions and allow the row data to be accessed by column header name using simple property access syntax.
