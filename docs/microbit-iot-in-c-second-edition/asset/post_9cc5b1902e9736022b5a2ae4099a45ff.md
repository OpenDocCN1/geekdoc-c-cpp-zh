
The longest time you can set is around 262 milliseconds, corresponding to the longest time a 32-bit timer running at 4μs per tick can count.
You could get different maximum and minimum rates by programming the timer yourself, but this is a difficult problem.

# Using PWM

Now you know how to use some of the PWM lines. All you have to do is set the value and the period.
The simplest PWM program you can write:

```cpp
#include "MicroBit.h"
MicroBit uBit;
int main() {
  uBit.init();
  uBit.io.P0.setAnalogValue(511);
  uBit.io.P0.setAnalogPeriod(1);
  release_fiber();
  return 0;
}
```

This produces a pulse train consisting of a millisecond wide pulse with a 50% duty cycle, i.e. high for 500ms.

| +8ms | +9ms | +1ms | Measurements |
|---|---|---|---|
| | | | Width: 502.95us |
| | | | Period: 1.0079ms |
| | | | DutyCycle: 49.007838% |
| | | | Frequency: 992.161921Hz |
| | | | Pulse Counters |

You have to set the value first and then set the period, otherwise the PWM line isn't set up properly. You also have to set the period for each pin you are using, even if it sets the same period. Notice that there is no need to put the program into an infinite loop. Once the PWM line has been set up and enabled, it just gets on with generating the pulse train, no matter what the microbit does. In this case the pulse generation continues long after the program has ended.

Just to demonstrate that multiple PWM lines can be used independently of one another, here is a program that sets each one of the three main GPIO lines, P0, P1 and P2, to a different duty cycle:

```cpp
#include "MicroBit.h"
MicroBit uBit;

int main() {
    uBit.init();
    uBit.io.P0.setAnalogValue(200);
    uBit.io.P1.setAnalogValue(511);
    uBit.io.P2.setAnalogValue(800);

    uBit.io.P0.setAnalogPeriod(1);
    uBit.io.P1.setAnalogPeriod(1);
    uBit.io.P2.setAnalogPeriod(1);

    release_fiber();
    return 0;
}
```

Notice that you have to set the value and then period for each pin you are using. You can see the result in the following logic analyzer display:

# How Fast Can You Modulate?

In most cases the whole point is to vary the duty cycle or the period of the pulse train, for reasons that will be discussed later. This means the next question is how fast can you change the characteristic of a PWM line? In other words, how fast can you change the duty cycle?

There is no easy way to give an exact answer and in most applications an exact answer isn't much value. The reason is that for a PWM signal to convey it it generally has to deliver a number of complete cycles with a given duty cycle because the wave pulses are often averaged in applications.

We also have another problem - synchronization. There is no way to swap from one duty cycle to another exactly when a complete duty cycle has just finished. This means that there is going to be a glitch when you switch from one duty cycle to another. Of course, this glitch becomes less important as you slow the rate of duty cycle change and exactly what is usable depends on the application. For example if you change the duty cycle about every 100ms and the pulse width is 50ms then you are going to see roughly two to three pulses per duty cycle:

```cpp
#include "MicroBit.h"
MicroBit uBit;
void loop() {
    volatile int i;
    uBit.init();

    uBit.io.P0.setAnalogValue(200);
    uBit.io.P0.setAnalogPeriodUs(50);

    for (i = 1; i < 100; i++){
        uBit.io.P0.setAnalogValue(200);
        for (j = 1; j < 100; j++){
            uBit.io.P0.setAnalogValue(800);
        }
    }
}
```

This results in a fairly irregular pulse pattern:

![](img/23976341c9281123e7b181beea6e9dbd_75_0.png)

The timing of the change and the time it takes to make the change the glitches between duty cycles.
If you change the busy waits to n=1000 and generate duty cycle changes every millisecond or so the pattern looks a lot better because you are going to see 19 to 20 pulses before each change, and the glitches are still there:

![](img/23976341c9281123e7b181beea6e9dbd_75_1.png)

Is there anything that can be done about the glitching? Yes, you can use a filter to smooth out the high frequency components. But if your aim is to get a clean wave form you have a lot of work to do. The fastest pulse rate is around 50ms on V1 and the usual rule of thumb is that you need ten pulses per conversion, i.e. the maximum frequency you can produce is:
pulse rate/10

This means the fastest signal you can create using the microbit is 1/500ms or 2kHz, which isn't fast enough for many applications. In particular, you can't use it for complex sound synthesis.

You also have 1024 voltage levels you can use. At 3.3v each step corresponds to about 300µV. This is unrealistic for many applications and setting the voltage to the nearest 300mV is more sensible.

To demonstrate the sort of approach that you can use for D-to-A conversion, the following program creates a triangle or ramp waveform:

```cpp
#include "MicroBit.h"

//define wait_us system_timer_wait_us // V2
MicroBit uBit;

int main() {
  int i;
  uBit.init();
  uBit.P0.setAnalogValue(200);
  uBit.P0.setAnalogPeriodUs(50);
  for(i=0;i<1024;i+=10) {
    uBit.io.P0.setAnalogValue(i);
    wait_us(100);
  }
  release_fiber();
  return 0;
}
```

The inner loop for sets values of 0 to 1024 in steps of 10, i.e. 300mV per step and the delay of 100ms produces a total loop time of over 180ms. This means that around three pulses of each duty cycle should be produced - which is far too few, but it is interesting to see what happens. The waveform repeats around 18ms, which makes the frequency around 66Hz. Using an oscilloscope, the measured repeat time is more like 20ms or 50Hz.
