
If you know about the I2C protocol, it is worth saying that the framework deals with the start sequence and the address frame, it checks the NAK/ACK bit from the slave, sends the data bits, checks the NAK/ACK bit from the slave and sends the stop sequence. That is, in normal use, the write transaction sending n bytes is:

```
START| ADDR |ACK|DATA0|ACK|DATA1|ACK|...|DataN|ACK|STOP
```

Notice that it is the slave that sends the ACK bit and if the data is not received correctly it can send ACK instead.

A multibyte transfer is quite different from sending n bytes one at a time.

```
START| ADDR |ACK|DATA0|ACK|STOP
START| ADDR |ACK|DATA1|ACK|STOP
```

You can opt not to send a STOP bit at the end of the write by setting the repeat parameter to true. That is, you can arrange to send START bits, address frames and as long as the entire sequence finishes with one STOP bit, which releases the bus. For multiple writes there is very little point in doing apart from keep control of the bus in multi-master setups. However, when you reads and writes things a little more complicated, see the next section.

A standard interaction between master and slave is writing data to a register. Many devices have internal storage, indeed some I2C devices are nothing but internal storage, e.g. I2C EPROMs. In this case a standard transaction is:

- 1. Send address frame
- 2. Send a data frame with the command to select the register
- 3. Send a data frame containing the byte or word to be written to the register

So, for example, you might use:

```
char buf[]={register,data};
write(address,buf,2);
```

There is also a command that will write the address and the data in one go:

```
int writeRegister(uint8_t address, uint8_t reg, uint8_t value)
```

Notice the command that has to be sent depends on the device and you have to look it up in its datasheet.

Next we have to look at how to read data from the device. Notice that in many transactions a read has to be preceded by a write that tells the device what you want.

## Read

There are two read functions and they broadly copy the write functions:
int read (int address,char * data, int length)
int read (int address,char * data, int length, bool repeated)

They send an address frame and then read as many bytes from the slave specified. In this case the address has to be shifted up one bit and the lower-order bit is automatically set to 1 by the function. That is, you use the write address in a read function.

As with the write function, the framework takes care of all the protocol necessary to send and receive the packets, including adding 1 to the end of the address. The read transaction is:
START| ADDR|DATA|ACK|DATA|ACK|...|DATAN|NAK|STOP

The master sends the address and the slave sends the ACK after the address to acknowledge it has been received and is ready to send data. Then the slave sends bytes one at a time and the master sends ACK in response to each byte. Finally, the master sends a NAK to indicate that the last byte has been read and then a STOP bit. That is the master controls how many bytes are transferred. In the case of the read functions, a block transfer of n bytes is different from transferring n bytes at a time.

A very standard transaction is to read a register. As in the case of writing a register, this involves sending the address and a command to select the register, but then you need to read the returned data. This requires the address frame to be sent again.

That is, to read a register you need a complete write and a complete read operation. So, for example, to read a register, with address reg, you would use something like:

```
char buf[]={reg};
write(address,buf,1);
read(address,buf,1);
```

If the register sends multiple bytes then you can sometimes read one after another without sending an address frame each time as a block transfer. In this case the transaction is:

```
START| ADDR|ACK|register|ACK|STOP|START|ADDR|ACK|data|NAK|STOP
```

Notice that there a STOP followed by START in the middle of the transaction. In principle, a STOP frees the bus and another master could take over or the current master start talking to a device before issuing the next START to read the register.

In theory, and mostly in practice, a multiple interaction with a slave can work with a STOP-START separating each transaction or just repeated START bits and a STOP only at the very end of the transaction. However, you will find that some devices state that they need repeated START and no STOP bits in continued transactions. In this case you need to be careful what you send and receive data. For example, to read a register from a device that requires repeated START bits but no STOP bit you would use:

```
char buf[]={reg};
write(address,buf,1,true);
read(address,buf,1);
```

This would send an address frame, the register address, and then a START bit without a STOP, read the data from the slave and finally send a NAK a STOP.
START| ADDR|ACK|register|ACK|START|ADDR|ACK|data|NAK|STOP

In practice, it doesn't make any difference if you send a STOP in the middle of a write/read transaction, but you need to know about it in case.

There is also a combined readRegister:
int readRegister(uint8_t address, uint8_t reg)

This returns a single-byte result. For a multi-byte reply you can use:
int readRegister(uint8_t address, uint8_t reg, uint8_t* buffer, int length)

This fills the buffer with the number of characters specified by the length parameter.

## Slow Read

This raises for the first time the question of how we cope with the speed at which a slave can respond to a request for data. There are two broad approaches to waiting for data on the I2C bus. The first is simply to request the data and then perform reads in a polling loop. If the device isn't ready with the data it sends a data frame with a NAK bit. The read functions return a MICROBIT_I2C_ERROR if it fails or MICROBIT_OK if it works.
Of course, the polling loop doesn't have to be "tight". The response time is often long enough to do other things and you can use the I2C bus to work with other slave devices while the one you activated gets on trying to get the data you requested. All you have to do is remember to read its data at some time.

The second way is to allow the slave to hold the clock line low after the master has released it. In most cases the master will simply wait moving on to the next frame while the clock is held low. The microbit I2C bus implements this stretching protocol and it will wait until the slave releases the clock.

This is very simple and it means you don't have to implement a polling loop, but also notice that your program is frozen until the slave releases the clock.

## Using The Built-in Devices

As already mentioned, there are two built-in I2C devices, the accelerometer and the magnetometer. The framework provides special functions that work with both of these devices and they are the ones to work with either device. The way they work is fairly straightforward and you can find out more from the documentation.

If you do want to work directly with the internal devices then there is a complication. The different versions of the microbit use different accelerometer and magnetometer chips and even the same version can use one of two types.

This makes programming more difficult and the framework provides a unified way of accessing them all.
