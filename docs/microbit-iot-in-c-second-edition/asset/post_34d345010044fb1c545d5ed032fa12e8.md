
The result is a pulse train with pulses ranging, on a V1 device, from 3.5 to 3.8µs and a 0.1µs pause every 6µs due to the system timer interrupting. There isn't anything that can be done about this 6µs interrupt apart from switching the system timer. A V2 device generates pulses at around 0.9µs with occasional pauses:

## Delay Using Sleep

To generate pulses of a known duration we need to pause the program between state changes. The simplest way of sleeping a fiber is to use the sleep command. This delays for a specified number of milliseconds. Unfortunately this uses the system timer and only works in 6ms.

To try this, include a call to `sleep(9)` to delay the pulse:

```cpp
#include "MicroBit.h"
MicroBit uBit;
int main() {
    uBit.init();
    while (1) {
        uBit.io.P0.setDigitalValue(1);
        uBit.sleep(9);
        uBit.io.P0.setDigitalValue(0);
        uBit.sleep(9);
    }
}
```

You will discover that you get 12ms pulses. This is only useful if you want pulses that are multiples of 6ms or so long that a 6ms error doesn't matter.

There is a microsecond delay function `wait_us()` which is part of the mbed software that the framework is built on and we can call it from a micro:bit program where n is set to a value that depends on the delay you want to generate.

The relationship between n and t, the time delay, is linear:

```
V1 n = 1.333t - 5.83
V2 n = 6.387t - 7.09
```

and it means you can't generate pulses less than about 6µs. For example, if you want pulses of 10ms for V2, n = 57 results in:

## Phased Pulses

As an example of using the output functions, let's try to write a short program that pulses two lines - one high and one low and then one low and one high, i.e. two pulse trains out of phase by 180 degrees. The simplest program to do this job is:

```cpp
#include "MicroBit.h"
MicroBit uBit;
int main()
{
  int i;
  uBit.init();
  while (1) {
    uBit.io.P0.setDigitalValue(1);
    uBit.io.P1.setDigitalValue(0);
    uBit.io.P0.setDigitalValue(0);
    uBit.io.P1.setDigitalValue(1);
  }
}
```

Notice that there is no delay in the loop, so the pulses are produced at the fastest possible speed.

Using logic analyzer reveals that, on a V2, the result isn't what you might expect:

![](img/23976341c9281123e7b181beea6e9dbd_47_0.png)

You can also see that the pulse trains are not 180 degrees out of phase. The top train switches on and the bottom train takes about half a pulse before it switches off whereas the intent is for both actions to occur at the same time. You should also notice that now the pulse is about 1.9µs, which is about double the time for a pulse train on a single line. The point is that it takes quite a long time to access and change the state of an output. The same is true for V1 device but the timings are slightly longer. Of course if we include a delay to increase the pulse width the delay caused by accessing GPIO lines in separate actions isn't so obvious:

![](img/23976341c9281123e7b181beea6e9dbd_47_1.png)

In this case the loop has n = 100:

```cpp
#include "MicroBit.h"
MicroBit uBit;
int main() {
    int i;
    uBit.init(1);
    while (1) {
        for (i = 0; i < 100; i++) {
            uBit.io.P0.setDigitalValue(1);
            uBit.io.P1.setDigitalValue(0);
        }
        for (i = 0; i < 100; i++) {
            uBit.io.P0.setDigitalValue(0);
            uBit.io.P1.setDigitalValue(1);
        }
    }
}
```

You will notice that the pulses are now roughly 17µ wide on V2 and they are changing at what looks like the same time, though of course there is still a lag. In many applications it might not be important. In other applications it could be crucial. For example, if two pulse trains driving different halves of the bridge there would be significant time when both are high - shorting the power supply. A better way to generate multiple pulses is to write directly to the hardware, which is what we do in the next chapter.

## Summary of creating accurate pulses

- For greater than 6µ to accuracy of 6µ use `sleep()`.
- For delays around 12µ use `wait_us()` which is accurate to around 1µ.
- For delays greater than 7µ use busy wait which is accurate to around 1µ.
- Switching GPIO lines takes time and achieving synchronized switching better than 1µ to 10µ is not possible using the framework.

## GPIO Input

GPIO input can be a much more difficult problem than output. At least for output you can see the change in the signal on a logic analyzer and know the exact time it occurred. This makes it possible to track down timing problems and fine-tune things with good accuracy.

Input on the other hand is "silent" and unobservable. Usually the timing of the line is with respect to some other action that the microbit has taken. For example input line is read microseconds after setting the output high. The usual rule of thumb is to assume that it takes as long to read a GPIO line as it does set it. This means we can use the delay mechanisms that we looked at with output for input. In some applications the times are unimportant but in some they are critical.

## A Basic Input Circuit - The Switch

One of the most common input circuits is the switch or button the microbit has two built-in buttons, A and B. If you want another external, you can use any GPIO line and the following circuit:

The 10k switch isn't critical in value. It simply pulls the GPIO line high when it is pressed, a current of a little more than 0.3mA through the resistor. If this is too much, increase the resistance to 100K or even more, but notice that the higher the resistor value, the noisier the input to the GPIO and the more it is susceptible to RF interference.

![](img/23976341c9281123e7b181beea6e9dbd_49_0.png)

If you want a switch that pulls the line high instead of low, just swap the positions of the resistor and the switch in the diagram.

Although the switch is the simplest input device, it is also very difficult to get right. When a user clicks a switch of any sort the action isn't clean - the switch bounces. What this means is that the logic level on the GPIO line goes high then low and bounces between the two until it settles down.

There are electronic ways of debouncing switches, but software does the job much better. All you have to do is put a delay of a millisecond or so after detecting a switch and read the line again. If it is still low then record a switch press. Similarly when the switch is released read the state twice with a delay. You can vary the delay to modify the perceived characteristics of the switch.

## The Potential Divider

If you have an input that is outside the range of 0 to 3.3V, you can reduce it using a simple potential divider. V is the input from the external logic and Vout it the connection to the GPIO input:

![](img/23976341c9281123e7b181beea6e9dbd_50_0.png)

You can spend a lot of time on working out good values of R1 and R2. For loads that take a lot of current you need R1 plus R2 to be small and divided in the same ratio as the voltages. For example, for a 5V device R1=18kΩ and R2=33k work well to drop the voltage to 3.3V.

The problem with a resistive divider is that it can round off fast pulses due to small capacitive effects. This usually isn't a problem, but if it is then the solution is to use an FET buffer.
