
To read the temperature using the Hold master mode you simply send 0xE3 and read three bytes:

```cpp
#include "MicroBit.h"
MicroBit uBit;

int main() {
    uBit.init();
    uint8_t buf[3] = {0};
    uBit.i2c.readRegister(0x80, 0xE3, buf, 3);
    uint8_t msb=buf[0];
    uint8_t lsb=buf[1];
    uint8_t check=buf[2];
    uBit.serial.printf("msb %d\n lsb %d\n checksum %d\n\r",
    msb, lsb, check);

    return 0;
}
```

The buffer is unpacked into three variables with more meaningful names:
msb - most significant byte; lsb - least significant byte; check - checksum.

You should see something like:

- msb 97
- lsb 232
- checksum 217

with the temperature around 20°C.

The logic analyzer reveals what is happening. First we send the usual address frame and write the 0xE3. Then after a short pulse the read address frame is sent and the clock line is held low by the device (lower trace):

![](img/23976341c9281123e7b181beea6e9dbd_113_0.png)

The clock line is held low by the device for over 42ms while it gets the data ready. It is released and the three data frames are sent:

| +500us | | +600us | | +700us | | +800us |
|---|---|---|---|---|---|
| | 0x62 + ACK | | 0x7C + ACK | | 0x09 + NAK | |

This response is a long way down the logic analyzer's trace so keep scrolling until you find it.

While clock stretching is the most simple, it sometimes doesn't work with some slave and master combinations.

Finally we have to find out how to use the No Hold mode or polling method of reading the data. It is sometimes useful, although not in the case of the micro:bit. In this case we can't use the read bytes data command because the data will not be ready to read and the master will not be forced to wait for it. We have to use the two-step, send the command and read the data approach:

```cpp
char buf[4] = {0xF3};
uBit.i2c.write(0x80, buf, 1);
while (uBit.i2c.read(0x80, buf, 3) == MICROBIT_I2C_ERROR){};
```

In theory, this polls repeatedly until the data is returned. In practice, it doesn't work. The reason is that there is a fault in the hardware resetting the I2C bus and retrying whenever it detects a NAK. The framework tries to compensate for this by resetting the I2C bus and retrying. The result is that the data is lost.

In short, you can't use polling with the micro:bit.

# Processing the Data

Our next task isn't really directly related to the problem of using the I2C bus, but it is a very typical next step. The device returns the data in three bytes, but the way that this data relates to the temperature isn't simple.

If you read the datasheet you will discover that the temperature data is the 14-bit value currently by putting together the most and least significant byte and zeroing the bottom two bits. The bottom two bits are used as status bits - bit zero currently isn't used and one is a 0 if the data is a temperature measurement and a 1 if it is a humidity measurement.

To put the two bytes we use:

```cpp
unsigned int data6=((unsigned int) msb << 8) | 
(unsigned int) (lsb & 0xFC);
```

This zeros the bottom two bits, shifts the msb up eight bits and ORs the two together. The result is a 16-bit temperature value with the bottom two bits zeroes.

Now we have raw temperature value, but we still have have to convert it to standard units. The datasheet gives the formula for temperature in degrees (°C) as:
-46.8 + 175.72 * data16 / 2^16

The only problem in implementing this is working out 2^16. You can work out 2^16 with the expression 1<<x, i.e. shift x to the left. This gives:

```cpp
float temp = (float)(-46.8 + (175.72 * data16)/(float)(1<<16));
```

As 2^16 is a constant that works out to 65536, it is more efficient to write:
```cpp
float temp = (float)(-46.8 +(175.72 * data16)/(float)65536);
```

Note the use of floating arithmetic. The micro:bit processor doesn't have hardware floating point, the framework comes with software implementation. Floating arithmetic is slow and it is usual to convert it into scaled integer arithmetic. In this case using floating point is convenient, but there is a snag. The printf function doesn't support floating point. There is another "full" version which does, but this has to be imported into the build.

Overall is easier to work with scaled integer - in this case temperature times 100 - so multiply the expression for temperature by 100 and make use of the fact that dividing by 2^16 is the same as right shifts:

```cpp
int temp= -4685 + ((17572*data16)>>16);
```

Now all we have to do is print the temperature as a correctly scaled value:

```cpp
printf("Temperature %d.%d C \n", temp/100, temp%100);
```

The final program:
```cpp
#include "MicroBit.h"
MicroBit uBit;

int main() {
	uBit.init();
	uint8_t buf[3] = {0};
	uBit.i2c.readRegister(0x80, 0xE3, buf, 3);
	uint8_t msb = buf[0];
	uint8_t lsb = buf[1];
	uint8_t check = buf[2];

	unsigned int data16 = ((unsigned int)msb << 8) | ((unsigned int)lsb & 0xFC);
	int temp = -4685 + ((17572 * data16) >> 16);
	uBit.serial.printf("Temperature %d.%d C \n", temp / 100, temp % 100);

	return 0;
}
```

# Reading the Humidity

The nice about I2C and using a particular device is that it gets easier. Once you have seen how to do it with one device, the skill generalizes and you know how to deal with a particular device other aspects of the device are usually similar.

To read the humidity we can use the same program, we just need to change the command and the formula for the final percentage humidity. The command needed to read the three data bytes is 0xE5 and the formula to convert the 16-bit value to percentage humidity (RH) is:

```cpp
-600 + 12500 * data16 / 2^16
```

This can be implemented in integer arithmetic if we work with RH*100.

Putting all together and reusing some variables from the previous program, we have:
```cpp
uBit.i2c.readRegister(0x80, 0xE5, 3);
msb = buf[0];
lsb = buf[1];
check = buf[2];
uBit.serial.printf("\nmsb %d \nlsb %d \nchecksum %d \n\r", msb, lsb, check);
data16 = ((unsigned int)msb << 8) | (unsigned int) (lsb & 0xFC);
int hum = -600 + (12500 * data16) >> 16;
uBit.serial.printf("Humidity %d %% %d \n", hum / 100, hum % 100);
```

The only unusual part of the program is using %% to print a single character - necessary because %% means something in printf.

# Checksum Calculation

Although computing a checksum or cyclic redundancy check (CRC), which is used to detect accidental changes to raw data not specific to I2C, it is another common task. The datasheet explains that the polynomial used for the CRC is:

X^8+X^3+X^4+X+1

Once you have this information you can work out the divisor by writing a binary number with a one in each location corresponding to a power of X in the polynomial, i.e the 8th, 5th, 4th and 1st bit. Hence the divisor is 0x031.

What you do next is roughly the same for all CRCs. First you put the data that was used to compute the checksum together with the checksum value as the lower-order bits:

```cpp
uint32_t data32 = ((uint32_t)msb << 16) |
(uint32_t) lsb << 8) | (uint32_t) check;
```

Now you have three bytes, ie 24 bits, in a 32-bit variable.

Next adjust the divisor so that its most significant non-zero bit aligns with the most significant bit. Now that you have the data and the divisor aligned, you step through the top bits. For each bit you check if it is a one - XOR the data:

```cpp
uint32_t divisor = 0x031 << 15;
for (int i = 0; i < 16; i++){
    if(data32 & (uint32_t)1<<(23 - i))data32 ^= divisor;
    divisor >>= 1;
}
```

When the loop ends, if there was no error, the data32 should be zero.

A complete function to compute the checksum with some optimizations:

```cpp
uint8_t crcCheck(uint8_t msb, uint8_t lsb, uint8_t check){
    uint32_t data32=((uint32_t)msb << 16) |
    ((uint32_t)lsb << 8)|((uint32_t) check;
    uint32_t divisor = 0x031 << 15;
    for (int i = 0; i < 16; i++){
        if(data32 & (uint32_t)1<<(23 - i))data32 ^= divisor;
        divisor >>= 1;
    }
    return (uint8_t)data32;
}
```

It is rare to get a CRC error on an I2C bus unless it is overloaded or subject to a lot of noise.
