
Once you have the radio configured the low level way of sending and receiving data is to use the send and recv functions which work with a frame buffer:

```
FrameBuffer recv()
int send( FrameBuffer * buffer)
```

```c
The FrameBuffer struct is:
uint8_t length; // The length of the remaining bytes
uint8_t version; // Protocol version code.
uint8_t group; // ID of the group
uint8_t protocol; // Inner protocol id
uint8_t payload[MICROBIT_RADIO_MAX_PACKET_SIZE]; // User data
FrameBuffer *next; // pointer to next buffer
int rssi; // Received signal of this frame;
```

The only difficult fields to deal with are protocol which should be set to either:

```
MICROBIT_PROTOCOL DATAGRAM
MICROBIT_RADIO_PROTOCOL_EVENTBUS
```

or something new you have invented and, at the time of writing, version is set to 1.

There seems to little reason to use the FrameBuffer directly as it provides a set of functions that work with simpler data types. The method can be used to send a simpler types of data:

```
int send(ManagedString data)
send(uint8_t * buffer, int len)
```

In most cases, sending ManagedString is what you want, but an array of integers is also useful. Notice that you are limited to 32bytes in each case. There is also a lower-level function that works with managed type:

```
int send(FrameBuffer data)
```

The FrameBuffer records the data, length and RSSI - Received Signal Indicator. It is an estimated measure of power level that client device is receiving:

```
FrameBuffer(uint8_t *data, int length, int rssi = 0);
```

For receiving data there are two versions of recv:

```
int recv(uint8_t * buf, int len)
```

and

```
FrameBuffer recv()
```

The FrameBuffer version of the function is more useful than might expect because the ManagedString object has a constructor which converts FrameBuffer, allowing you to write things like:

```
ManagedString s = uBit.radio.recv();
```

and the data payload of FrameBuffer will be converted into ManagedString.

## Poll Or Event

If you want to send some data to other microbits the task is easy. All you have to do is create the buffer and use the send method. To receive data we have the usual problem that input is harder than output. In the case of receiving a radio message the solution is to use polling or event. Once you enable the radio it continuously monitors for incoming messages and stores that it receives.

If you use the radio.recv method then it returns the first message that is available or NULL there are no messages ready to process. If you use the recv method then a message is returned or an empty buffer. In either case you can use the recv method to write polling loop. For example:

```
while (1) {
  ManagedString s = uBit.radio.recv();
  if (s.length() != 0) {
    work with data
  }
}
```

The alternative to polling loop is to set up an event handler. Events are only implemented for object and to enable them you need to use:

uBit.messageBus.listen(MICROBIT_ID_RADIO, MICROBIT_RADIO_EVT_DATAGRAM, onData);

where the onData parameter is the function called when there is data to process.

For example:

```
void onData(MicroBitEvent e)
{
    ManagedString s = uBit.radio.recv();
    work with data
}

int main()
{
    uBit.init();

    uBit.messageBus.listen(MICROBIT_ID_RADIO, MICROBIT_RADIO_EVT_DATAGRAM, onData);
    uBit.radio.enable();
    do other tasks
}
```

This is simple, but you have to rely on the queue of incoming messages overflowing while you are processing the data. In many cases the message that you want to send to other microbits is just something has happened. For example, if a button is pressed you might send 1 and when it is released a 2. This works flexible and efficient, but really all you are doing is transferring an event to another microbit. The framework MicroRadioEvent is designed to associate events that occur on the local microbit and pass them via the radio to another microbit. The radio object has an event object, MicroRadioEvent. This object is designed to associate events the received events handled on the remote microbits as if they occurred locally, i.e. they are treated the same as standard events.

The key method of the MicroRadioEvent is listen:

```
int listen(uint16_t id, uint16_t value)
```

which associates the event specified by id and value to the radio channel currently open. The id is that of the component that caused the interrupt value is the exact event. You can use custom values for these or existing event types. For example:

```
int main()
{
    uBit.init();
    uBit.radio.enable();

    uBit.radio.event.listen(MICROBIT_ID_BUTTON_A, MICROBIT_BUTTON_EVT_CLICK);

    while(1) {
        uBit.sleep(1000);
    }
}
```

sets up the radio to pass any Button A clicks over the radio. To respond to them the receiver has to have something like:

```
void onData(MicroBitEvent e)
{
  uBit.display.print("Click");
  return;
}

int main() {
  uBit.init();
  uBit.messageBus.listen(MICROBIT_ID_BUTTON_A, MICROBIT_BUTTON_EVT_CLICK, onData);

  uBit.radio.enable();
  while(1) {
    uBit.sleep(1000);
  }
}
```

If you try this out you will see the micro:bit display the "Click" message when the remote micro:bit has its Button A clicked. Of course, the message is displayed if the local micro:bit has its Button clicked as well. The remote micro:bit cannot tell the difference between an event that originated from another micro:bit or from itself. This is the reason custom events are most often used to uniquely identify events originating over a radio link.

The idea of transmitting local events to other microbits is simple. It would be nice to have sound and a detour into how to make sound on V1 and V2 is justified.

## Producing Sounds

The micro:bit V1 has no standard audio ability and no built-in speaker. If you want to create some sound you have the PWM abilities of one of the pins to create a square wave of the correct frequency. You can easily write a function to do this:

```c
// Function to produce a pitch
void analogPitch(int frequency, int vol, int ms) {
  uBit.io.P0.setAnalogValue(vol);
  uBit.io.P0.setAnalogPeriodUs(100000/frequency);
  uBit.sleep(ms);
  uBit.io.P0.setAnalogValue(0);
}
```

The frequency is in Hertz, the volume runs from 0 to 512 and the duration is in milliseconds. This works with P0 but you can use any pin that supports PWM. To hear the result you need to attach a speaker to the appropriate pin.
nThe micro:bit V2 has a completely new audio system, which is currently undocumented and clearly subject to change – the account given here is incomplete. But it is enough to get started with the most common tasks.
