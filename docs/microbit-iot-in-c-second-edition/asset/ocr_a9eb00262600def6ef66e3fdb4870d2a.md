The second way is to allow the slave to hold the clock line low after the master has released it. In most cases the master will simply wait moving on to the next frame while the clock is held low. The microbit I2C bus implements this clock stretching protocol and it will wait until the slave releases the clock before proceeding.

This is very simple and it means you don't have to implement a polling loop, but also notice that your program is frozen until the slave releases the clock line. Many devices implement both types of slow read protocol and you can use whichever suits your application.

There is also the small speed of the I2C clock. Most slave devices don't have a strict clock rate as they are designed as static devices synced to whatever SCL clock rate the master cares to. If it turns out to be too fast most will use clock stretching. In extreme cases it may be necessary to slow down the slave device, or even speed up the master's clock.

By default the I2C clock runs at 100K you can use the V1 function:

```
or the similar V2 function:
setFrequency(int hz);
```

Notice that hz can only be one of 100000, 250000 or 400000. If you use anything else, the nearest standard value is used.

# Using The Built-in Devices

As already mentioned, there are two built-in I2C devices, the accelerometer and the magnetometer. The framework provides special functions that work with both of these devices and they are the ones to work with either device. The way they work is fairly straightforward and you can find out more from the documentation.

If you do want to work directly with the internal devices then there is a complication. The different versions of the microbit use different accelerometer and magnetometer chips and even the same version can use one of two types.

This makes programming more difficult and the framework provides a unified way of accessing them all.
