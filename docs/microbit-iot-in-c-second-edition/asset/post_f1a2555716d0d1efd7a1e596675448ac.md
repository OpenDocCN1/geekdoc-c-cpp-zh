What happens next depends on the server. As a result of the HTTP GET the server will now send data over the WiFi link and the device will send this over the connection as soon as it gets it. We can't use the waitFor function because it might swap the serial lines and cause a spurious character to be transmitted. Notice that this data is not a direct response to a command and so the device prefixes it with:

+IPD, len:

The +IPD makes it clear to the client that it is a packet of data sent from the server. The len value gives the number of characters after the colon. In principle, what your program should do is not sit in a polling loop looking for +IPD. It should read the digits between the comma and the colon and convert this to an integer. Finally, it should read exactly that number of characters from the serial port.

This can be done, but for a demonstration we simply read any data that is presented on the serial port for a reasonable amount of time in an attempt to capture all of the data. Notice that this is a fine balance between avoiding a buffer overrun because you don't read it enough and not waiting long enough for all of the data.

# A Web Server

The common use for an internet connection on a small device like the microbit is to allow another device to request data. It is fairly easy to create a web server running on the ESP8266, but not easily create Apache or anything advanced. You can reasonably accept a connection and send a web page or two back to the client.

The key differences between client and server mode is that in server mode the device constantly "listening" for clients to make TCP connections on the port. When the device receives a connection it reads all of the data the client has sent and passes it on via the serial port to the microbit. This means that in server mode the microbit has to be constantly on the lookout for new data from the ESP8266. You can do this using an interrupt, but for simplicity this example uses a loop.

There is another difference between client mode and server mode - there can be multiple TCP connections from all the clients that try to connect. The solution to this problem is that the ESP8266 assigns each TCP connection an id number and this is what you need to use to make sure you send the data to the right place. Let's see how it works.

Assuming we are already connected with WiFi and have an IP address, we can set up a server quite easily. First we need to use the CIPMUX=1 to set the device into multiple connection mode. You cannot start a server if CIPMUX=0, the default, single-connection mode. Once multiple connections are allowed you can create server using CIPSERVER=1,port. In this example we are using port 80, the standard port, but you can change this to anything:

```c
int startWiFi() {
  uBit.serial.send("AT+CIPMUX=1\r\n", SYNC_SPINWAIT);
  if (waitForWiFi("OK", 100, 20) == 0) return 0;

  uBit.serial.send("AT+CIPSERVER=1,80\r\n", SYNC_SPINWAIT);
  if (waitForWiFi("OK", 100, 20) == 0) return 0;
}
```

If you run this part of the program you will see the response:
+CIPMUX=1
OK
+CIPSERVER=1,80
OK

Now we just have to wait for a client to make a connection and send some data. This is done by reading serial input and checking for "+IPD":

```c
for (;;) {
  s="";
  do {
    uBit.sleep(100);
    if(s.length()>500) s
    s = uBit.serial.read(500, ASYNC);
  } while (find("+IPD", s) == 0);
  if (DEBUG) debug("\n\rClient Connected\n\r" + s + "\n\r");
```

Notice the start of the infinite loop. What we are going to do is check for a connection, then go back to checking for another connection - hence the outer loop. Once we have a connection is formatted so that the id is just after "+IPD". In multi-connection mode the received data has the format:
+IPD,id,rest of data

Now we need to extract the id so we can use it to communicate with the client. This is just some string handling, but is still messy:

```c
int b = find("+IPD", s);
s = s.substring(b + 1, s.length());
b = find(",", s);
s = s.substring(b + 1, s.length());
b = find(",", s);
Managed id = s.substring(0, b);
if (DEBUG)debug("\n\r id:" + id + "\n\r");
```

The algorithm is:
1. Find "+IPD" and trim the string so it is the start.
2. Find the first comma and trim the string so it is the start.
3. Find the next comma and extract the characters from the start of the string to the next.

Now we have the id we can communicate with the client, but we first need something to send. There are a lot of possible headers we could send, and a reasonable minimum that works with most browsers is:

```c
ManagedString headers = "HTTP/1.0 200 OK\r\n";
headers = headers + "Server: microbit\r\n";
headers = headers + "Content-type: text/html\r\n\r\n";
```

You can include timestamps and other useful information, but this is simple and it works. Notice the blank line at the end of the headers - this is vital. The browser will ignore everything sent to it if you don't have a blank line at the end of the headers.

The html data is a simple JSON-style data object giving humidity and temperature:

```c
ManagedString html="<html><head><title>Temperature</title></head><body>{\"humidity\":81%\",\"temperature\":23.5C}</body></html>\r\n";
ManagedString data=headers+html;
```

Of course, in a real sensor you would add data into the HTML in place of the 81% and 23.5C. It would be easier to combine the headers and the data into a single data string. The only reason for defining them as two separate strings is to make it easier to see what they contain.

Now we want to send the data to the client. This is just a matter of using the IPSEND command again, this time with id specified as the first parameter: IPSEND=id,data length and wait for the response before sending the data.

Notice that we don't have to open a TCP socket as we did in the case of acting as a client. The TCP socket has already been opened by the client connecting to the server and when the transaction is complete we can close it:

```c
ManagedString cmd = "AT+IPSEND="+id+",*ManagedString(data.length()) + "\r\n";
uBit.serial.send(cmd, SYNC_SPINWAIT);
s = 40;
int retry = 0;
do {
	uBit.sleep(100);
	s = s + uBit.serial.read(500, ASYNC);
	retry--;
} while (debug("", s) == 0 && retry != 0);
```

Now, at last, we can send the data to the client:
uBit.serial.send(data, SYNC_SPINWAIT);
if (waitForWiFi("OK", 100, 100) == 0) return 0;
if (DEBUG)debug("\n\rData Sent\n\r");

And wait for it to complete.
Finally we close the connection and complete the loop to wait for another connection:

```c
cmd = "AT+CIPCLOSE=" + id + "\n";
uBit.serial.send(cmd, SYNC_SPINWAIT);
if (waitForWiFi("OK", 100, 100) == 0) return 0;
};
```
