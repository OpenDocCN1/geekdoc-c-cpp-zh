# Summary

- The DHT22 is a low-cost temperature and humidity sensor.
- It uses a custom single wire bus which is not compatible with the standard 1-Wire bus.
- Its asynchronous protocol is easy to implement the timing required.
- The timing may be easy, but unless interrupts are turned off it is unlikely to complete a single reading without error.
- A very simple checksum is used to detect errors.

# # Chapter 9
# DS18B20 1-Wire Temperature Sensor

The 1-Wire bus is a proprietary bus that is very easy to use and has a lot of useful devices you can connect to it. Probably the most popular of all 1-wire devices is the DS18B20 temperature sensor - it is small, very cheap and very easy to use if the processor supports the 1-Wire bus protocol, the micro:bit doesn't. However, the protocol is easy enough to program in C and the micro:bit is fast enough to work with it without needing anything extra. We have to use C for this; Python, for example, just isn't fast enough.

The microbit has an onboard temperature sensor, but this measures the temperature of the CPU and only gives you the air temperature very approximately. The DS18B20 gives you an accurate temperature and you have multiple sensors.

# # The Hardware

The DS18B20 is available in a number of formats but the most common makes it look just like a standard BJT - which can sometimes be a problem when you are trying to find one. You can also get the DS18B20 made up into a waterproof sensor complete with cable. No matter how packaged, it will work at 3.3V or 5V.

![](img/23976341c9281123e7b181beea6e9dbd_136_0.png)

The basic specification of the DS18B20 is:

- Measures temperatures from -55°C to +125°C (-67°F to +257°F)
- ±0.5°C accuracy from -10°C to +85°C
- Thermometer resolution is user-selectable from 9 to 12 Bits
- Converts to 12-bit digital word in 750ms (max)

It can also be powered from the data line, making the bus physically only two wires - data and ground - however this "parasitic power" mode is difficult to make work reliably and best avoided in an initial design. In normal powered mode there are three connections:

![](img/23976341c9281123e7b181beea6e9dbd_137_0.png)

Ground needs to be connected to the system ground, $V_{DD}$ to 3.3V and DQ to the pull-up resistor of an open collector bus.

![](img/23976341c9281123e7b181beea6e9dbd_137_1.png)

There can be multiple devices on the bus and each one has a unique 64-bit laser ROM code, which can be used as an address to select the active devices. For simplicity, it is better to start off with a single device and avoid the problem of enumerating the devices on the bus, although once you know how everything works this isn't difficult to implement.

There is a problem we have to solve, however, the need for fast switching between input and output. Without intervention, changing between output and input mode is done using the system and is comparatively slow, approximately 80µs. In some cases this does matter because the protocol requires data from the master and receives data from the slave. For example, the DHT22 temperature and humidity sensor asks the processor to write to it a measurement and then sends data back without the processor writing anything, which permits the use of a single GPIO line.

In the case of the DS18B20, the protocol is slightly different. The master pulls the line low, then high, and then waits for the slave to respond. The slave then pulls the line low to indicate its presence. The master then switches to input mode and reads the data from the slave. The data is sent in 16-bit blocks, where each bit is represented by the time the line is held low. The first 16 bits are the temperature, the next 16 bits are the humidity, and the last 8 bits are the CRC.

The temperature is sent in a 2's complement format, where the most significant bit is the sign bit. The resolution is 0.0625°C per bit.

![](img/23976341c9281123e7b181beea6e9dbd_138_0.png)

# # Initialization

The first step in the communication is to initialize the bus. The master pulls the line low for at least 480µs, then pulls it high and waits for at least 70µs. The slave then responds by pulling the line low for between 60µs and 240µs. The master then reads the line to see if the slave responded.

```cpp
bool init() {
    bool reset = false;
    for (int i = 0; i < 10; i++) {
        pinWrite(DATA_PIN, LOW);
        delayMicroseconds(480);
        pinWrite(DATA_PIN, HIGH);
        delayMicroseconds(70);
        if (digitalRead(DATA_PIN) == LOW) {
            reset = true;
            break;
        }
    }
    return reset;
}
```

Once the bus is initialized, the master can start requesting data from the slave. Each bit is sent by pulling the line low for 60µs and then letting it high. The master reads the line while it's high.

```cpp
int16_t readData() {
    int16_t data = 0;
    for (int i = 0; i < 16; i++) {
        pinWrite(DATA_PIN, LOW);
        delayMicroseconds(60);
        pinWrite(DATA_PIN, HIGH);
        delayMicroseconds(10);
        if (digitalRead(DATA_PIN) == HIGH) {
            data |= (1 << i);
        }
    }
    return data;
}
```

This is a simplified version of the communication protocol. In a real-world application, you would need to handle the CRC check and other details of the protocol-well.
