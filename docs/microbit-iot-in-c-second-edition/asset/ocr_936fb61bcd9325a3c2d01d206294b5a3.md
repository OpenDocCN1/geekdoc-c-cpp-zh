If you look more closely at the analyzer trace you will find that every now and again there is a pulse only 0.125µs wide - presumably an artifact of the cache in use.
In the case of microbit V2 the situation is more complicated:

![](bbox=[0.137, 0.172, 0.794, 0.273])

You can see that the minimum pulse width is 0.1µs, which is better than times faster than the framework can generate, but the pulse train varies a lot.
Rather than trying to work out exactly what is going on, on the moral of the story is that when you are working at speeds that are close to the execution time of a single instruction, you cannot expect it to be reproducible in a complex modern processor.

If you add busy wait to slow down then the variations due to the processor become less important and the high time is equal to the low time:

```
int main() {
int GPIO = 3;
//GPIO = 2; Uncomment for V2
volatile unsigned int *dirset=(unsigned int*) (0x50000000UL+0x518);
volatile unsigned int *outset=(unsigned int*) (0x50000000UL+0x508);
volatile unsigned int *outclr=(unsigned int*) (0x50000000UL+0x50C);
unsigned int mask = 1 << GPIO;

*dirset = mask;
volatile int i;
int n = 200;
for (; ) {
for (i = 0; i < n; i++) {
*outset = mask;
for (i = 0; i < n; i++) {
*outclr = mask;
}
}
}
```

You can estimate the value of n using:
V1 = n = 0.74*t + 0.88
V2 = n = 4.21*t + 1.85
where t is in microseconds.
