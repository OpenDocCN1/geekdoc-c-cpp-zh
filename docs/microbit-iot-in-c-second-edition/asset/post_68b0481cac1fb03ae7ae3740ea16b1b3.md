## Serial Connections

The serial port is one of the oldest ways of connecting devices together, but it is still very useful. The micro:bit has a single serial interface, but it can be directed to use any of the GPIO pins as Rx and Tx. The software that powers the micro:bit does a lot to make the single-tasking environment that it is based on more like a multi-tasking operating system. The facilities it provides for working with the serial interface are extensive and it is important to know how it all works because it goes well beyond the raw serial facilities on which it is based.

## Serial Protocol

The serial protocol is very simple - it has to be because it was invented in the days when it was generated using electromechanical components, motors and the like. It was designed to make early teletype machines work and hence you will often find abbreviations such as TTY in connection with it. As the electronic device used to work with serial is called a Universal Asynchronous Receiver/Transmitter, the term UART is often used.

The earliest standards are V24 and RS232. However, notice that early communications worked between ±24 and later ±12V. Today serial communications work at logic, or TTL, levels 0 to 5V or 0 to 3.3V. Voltage difference is a problem we will return to. What matters is, irrespective of the voltage, the protocol is always the same.

For the moment the protocol, as already mentioned, is simple. The line rests high and represents a zero. When a device starts to transmit it pulls the line to low to generate a start bit. The width of this bit determines the transmission speed. After the start there are a variable number of data bits, an optional parity bit and finally one or two stop bits.

Originally the purpose of the start bit was to allow the motors to get started and allowing the receiving end to perform any timing. The stop bits were similarly there to give time to come back to their rest. In the early days the protocol was used at very slow speeds - 300 baud per second was considered fast enough. Today the protocol is much the same, but there is little need for multiple stop bits and communication is dispensed with. Transmission speeds are also higher - 9600 or 115200.

To specify what protocol is in use, you will often encounter a short form - e.g. 9600 baud, 8 data bits, no parity, one stop bit.

What is baud? Baud rate refers to the bit time.

| Baud | Bit Time |
| :--- | :--- |
| 300 | ~3ms |
| 9600 | ~104µs |
| 115200 | ~8µs |

Notice baud rate doesn't equate to speed of sending data because there is overhead in start, and perhaps parity bits to include in the calculation.

## Hardware

A simple serial interface has a transmit pin Tx and a receive pin Rx. That is, a serial interface has as few as two wires for two-way communications. Typically you connect the Tx pin on one device to the Rx pin on the other and vice versa. The only problem is that some manufacturers label the pins by what they should be connected to, not they are, and you have to connect Rx to Tx and Tx to Rx, which is not really helpful. You generally need to check with a scope, logic probe or meter if you are in any doubt.

In addition to the Tx and Rx pins, a serial interface also has a lot of control lines. Most of these were designed to help with old-fashioned teleprinters they are not often used. For example RTS (Request To Send) is a line that is used to ask permission to send data from the device at the other end of the connection, CTS (Clear To Send) is a line that indicates that it is okay to send data and so. For many connections between modern devices you can ignore these additional lines and just send and receive data. If you need to interface with something that implements a complex interface you are going to look up the details and hand-craft a program to interact with it. For the rest of this chapter we are going to work with Tx and Rx and ignore additional status and signaling lines.

The UART in the micro:bit CPU can work independently of the rest of the hardware. It will receive and transmit data while the CPU is getting other things. Normally it is connected to pins that are part of the USB port. This means that, by default, sending and receiving serial data works over the USB port, and if it is connected to a serial port driver, you automatically have serial connection that works, assuming you have the correct speed. The fact that the serial device can be connected to any GPIO lines that you can make of it talk to other devices directly and without need to involve the USB port. You can even talk to a device connected to GPIO lines and echo what is going on the USB port.

The micro:bit implements serial communications at 0V to 3.3V and PC-based serial ports usually use +13V to -13V and all RS232-compliant ports use a + to - voltage swing, which is completely incompatible with the micro:bit and most other microprocessors. If you are using the default configuration with the serial device connected via the USB port this isn't a worry. However, if you want to use a GPIO line then you need to do something about level conversions.

To connect to the microbit you need a USB-TTL level serial interface that works between 0V and 3.3V. There are lots on the market. All you have to do is plug the USB port into the PC or device, install a driver and start to transmit data. If you want to work with the USB serial port then you will need a serial terminal on your desktop machine to connect to the microbit. For Windows, simply download PuTTY.

The default for the USB connection is 115200 baud, 8 bits, no parity, one stop bit. If you are using a PC and PuTTY you simply need to set PuTTY to 115200 and it should work.

## Serial Commands

There seem to be a lot of commands relating to the serial port. However, they fall into just three groups initialization, writing and reading. Unfortunately there are many minor changes in the microbit implementation of the serial object.

The initialization commands control how the port works. They all create or work with an instance of MicroBitSerial, but if you want to create an instance of your own dont an instance of uBit. This simply causes a conflict with two instances of MicroBitSerial trying to control the hardware. If you want to use the other features provide by uBit, the simplest thing to do is create a global uBit and initialize it in the usual way. Then use its property to access the MicroBitSerial object that has been created:

```cpp
#include "MicroBit.h"
//define setBaudrate // Uncomment for V2
MicroBit uBit;
int main() {
{
	uBit.init();
	uBit.serial.baud(115200);
	uBit.serial.send("A\r\n");
}
``````

By default this connects to the USB serial so you should see an A printed on the serial console connected to the port. Notice that for V2 the baud is called setBaudrate.

If you don't want to use uBit you need to create MicroBitSerial as a global object. To create the equivalent of the previous program you would use:

```cpp
#include "MicroBit.h"
/* Uncomment for V2
#define setBaudrate
#define USBTX MICROBIT_PIN UART TX
#define USBRX MICROBIT_PIN UART_RX
*/
MicroBitSerial serial(USBTX, USBRX);

int main() {
{
	serial.baud(115200);
	serial.send("A\r\n");
	release_fiber();
}
```
