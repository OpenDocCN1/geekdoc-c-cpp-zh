## 8.5.3 多路合并

典型外部排序算法的第二阶段是将第一阶段创建的运行进行合并。假设我们有 R 个运行需要合并。如果使用简单的两路合并，则 R 个运行（无论其大小如何）将需要经过文件 log R 次。R 应该远小于记录总数（因为初始运行应各自包含许多记录），我们希望进一步减少合并运行所需的遍数。请注意，两路合并并不能很好地利用可用内存。因为合并是对两个运行的顺序过程，每次在内存中只需要一个运行的一个数据块。任何时候在内存中保留一个运行的多个数据块都不会减少合并过程所需的磁盘 I/O（尽管如果一次从文件中读取多个数据块，至少可以利用顺序访问）。因此，替换选择中使用的堆所占用的大部分空间（通常长度为多个数据块）并未被合并过程使用。

如果我们一次合并多个运行，就能更好地利用这部分空间，同时大大减少合并所需的遍数。多路合并与两路合并类似。如果我们有 B 个运行需要合并，每个运行在内存中都有一个数据块，那么 B 路合并算法

从概念上讲，多路合并假设每个运行存储在单独的文件中。然而，实践中并非必要。我们只需要知道每个运行在单个文件中的位置，并在需要从特定运行获取新数据时使用 seekg 移动到适当的数据块。当然，这种方法破坏了对输入文件的顺序处理能力。然而，如果所有运行都存储在单个磁盘驱动器上，那么处理本来就不会真正是顺序的，因为 I/O 读写头会在运行之间交替。因此，多路合并用几次（潜在的）顺序遍换成一次随机访问遍。如果处理本来就不是顺序的（例如所有处理都在单个磁盘驱动器上），这样做不会损失时间。

多路合并可以大大减少所需的遍数。如果内存中有空间存储每个运行的一个数据块，则所有运行可以在一次遍中合并。因此，替换选择可以在一次遍中构建初始运行，多路合并可以在一次遍中合并所有运行，总成本为两次遍。然而，对于真正的大文件，可能运行太多，无法每个都分配到内存中的一个数据块。如果为 B 路合并分配了 B 个数据块的空间，而运行数 R 大于 B，则需要进行多次合并遍。换句话说，先合并前 B 个运行，然后再合并下一个 B 个，依此类推。这些超运行随后会被后续遍按每次 B 个超运行进行合并。

一次遍中能合并多大的文件？假设为替换选择分配了 B 个数据块的堆（产生平均长度为 2B 个数据块的运行），然后进行 B 路合并，我们平均可以在一次多路合并中处理大小为 2B² 个数据块的文件。平均而言，2B^{k+1} 个数据块可以在 k 次 B 路合并中处理。为了体会其增长速度有多快，假设我们有 0.5MB 的工作内存，数据块为 4KB，可得 128 个数据块的工作内存。平均运行大小为 1MB（是工作内存大小的两倍）。一次遍中可以合并 128 个运行。因此，平均而言，大小为 128MB 的文件可以用仅 0.5MB 的工作内存在两次遍中处理（一次构建运行，一次合并）。另一个例子，假设数据块长度为 1KB，工作内存为 1MB = 1024 个数据块。那么平均长度为 2MB 的 1024 个运行（约 2GB）可以在一次合并遍中合并。更大的数据块大小会减少在固定大小工作内存下一次合并遍可处理的文件大小；更小的数据块大小或更大的工作内存会增加一次合并遍可处理的文件大小。两次合并遍允许处理更大的文件。以 0.5MB 工作内存和 4KB 数据块为例，大小为 16GB 的文件可以在两次合并遍中处理，这对大多数应用来说已经足够大。因此，这是一种非常有效的单磁盘驱动器外部排序算法。

图 8.11 显示了对各种大小文件进行排序的运行时间比较，针对以下实现：（1）标准归并排序，两个输入运行和两个输出运行，（2）具有大初始运行的两路归并排序（受可用内存大小限制），（3）在生成大初始运行后执行的 R 路归并排序。在每种情况下，文件由一系列四字节记录组成（二字节键和二字节数据值），或每兆字节文件大小 256K 条记录。我们可以从表中看到，即使使用适度的内存大小（两个数据块）来创建初始运行，也能节省大量时间。对运行进行 4 路合并提供了另一个显著的加速，然而对于 R 超过约 4 或 8 次的大规模多路合并帮助不大，因为确定 R 个运行中下一个最小元素会花费大量时间。

我们从此实验中看到，构建大的初始运行将运行时间减少到标准归并排序的略多于三分之一，具体取决于文件和内存大小。使用多路合并进一步将时间几乎减半。

总之，一个好的外部排序算法应寻求做到以下几点：

- 使初始运行尽可能长。
- 在所有阶段，尽可能多地重叠输入、处理和输出。
- 尽可能多地使用工作内存。应用更多内存通常会加快处理速度。事实上，更多内存的效果通常比更快的磁盘更大。更快的 CPU 对于外部排序的运行时间改善不大，因为磁盘 I/O 速度是限制因素。
