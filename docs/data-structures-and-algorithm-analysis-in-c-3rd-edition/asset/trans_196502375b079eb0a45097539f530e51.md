## 10.2 ISAM

我们如何处理需要频繁更新的大型数据库？线性索引的主要问题是它是一个单一的大型数组，对更新的适应性很差，因为一次更新可能需要更改索引中每个键的位置。倒排列表减少了这个问题，但它们只适用于二级键值远少于记录数的二级键索引。如果线性索引能以某种方式被分割成块，使得单个更新只影响索引的一部分，那么它作为主键索引的表现会很好。这个概念将在本章的其余部分中继续探讨，最终 culminate 为 B+ 树，即今天最广泛使用的索引方法。但首先，我们先研究 ISAM，这是解决需要频繁更新的大型数据库问题的一种早期尝试。它的弱点有助于说明为什么 B+ 树工作得如此出色。

在有效的树索引方案发明之前，使用了各种磁盘索引方法。所有方法都相当笨重，主要是因为没有足够的方法来处理更新。通常，更新会导致索引性能下降。ISAM 就是此类索引的一个例子，在 B 树被采用之前，IBM 广泛使用它。

## 10.3 基于树的索引

当数据库是静态的，即记录很少或从不插入和删除时，线性索引是高效的。ISAM 对于有限数量的更新是足够的，但对于频繁更改则不够好。由于它本质上具有两级索引，ISAM 对于真正的大型数据库也会崩溃，在这种数据库中，圆柱体的数量太多，顶级索引无法放入主内存。

在最一般的形式中，数据库应用程序具有以下特征：

- 1. 大量经常更新的记录集。
- 2. 按一个或多个键的组合进行搜索。
- 3. 使用键范围查询或最小/最大查询。

对于此类数据库，必须找到更好的组织方式。一种方法是使用二叉搜索树（BST）来存储主键和二级键索引。BST 可以存储重复的键值，它们提供高效的插入和删除以及高效的搜索，并且可以执行高效的范围查询。当有足够的主内存时，BST 是实现主键和二级键索引的可行选择。

不幸的是，BST 可能变得不平衡。即使在相对良好的条件下，叶节点的深度也可能相差两倍之多。当树存储在主内存中时，这可能不是一个重要问题，因为搜索和更新所需的时间仍然是 Θ(log n)。然而，当树存储在磁盘上时，树中节点的深度变得至关重要。每当访问 BST 节点 B 时，就有必要访问从根到 B 的路径上的所有节点。此路径上的每个节点都必须从磁盘检索。每次磁盘访问都会返回一个信息块。如果一个节点与其父节点在同一块上，那么一旦其父节点在主内存中，找到该节点的成本就微不足道。因此，希望将子树保存在同一块上。不幸的是，很多时候一个节点并不与其父节点在同一块上。因此，对 BST 的每次访问都可能需要从磁盘读取另一个块。使用缓冲池在内存中存储多个块可以缓解磁盘访问问题，如果 BST 访问显示良好的引用局部性。但缓冲池无法完全消除磁盘 I/O。如果 BST 不平衡，问题会变得更大，因为树深处的节点可能导致读取许多磁盘块。因此，必须解决两个重要问题，才能实现高效的磁盘搜索

## 10.4 2-3 树

本节介绍一种称为 2-3 树的数据结构。2-3 树不是二叉树，而是其形状遵循以下定义：

- 1. 一个节点包含一个或两个键。
- 2. 每个内部节点要么有两个子节点（如果它包含一个键），要么有三个子节点（如果它包含两个键）。因此得名。
- 3. 所有叶节点都在树的同一层，因此树始终是高度平衡的。

除了这些形状属性外，2-3 树还具有类似于 BST 的搜索树属性。对于每个节点，左子树中所有后代的值都小于第一个键的值，而中心子树中的值大于或等于第一个键的值。如果存在右子树（等价于节点存储两个键），则中心子树中所有后代的值都小于第二个键的值，而右子树中的值大于或等于第二个键的值。为了保持这些形状和搜索属性，需要在插入和删除节点时采取特殊操作。与 BST 相比，2-3 树的优势在于 2-3 树可以以相对较低的成本保持高度平衡。
