
按期望访问频率组织记录。虽然其收益可能不如按键值组织时那样大，但（至少近似地）按访问频率组织的成本可能低得多，因此在某些情况下可以加速顺序查找。

假设对于每个键 $k_i$，我们知道键为 $k_i$ 的记录被请求的概率 $p_i$。再假设列表的排序使得最常被请求的记录排在第一位，其次是次常被请求的记录，依此类推。对列表的查找将从第一个位置开始顺序进行。在多次查找的过程中，一次查找所需的期望比较次数为

$\overline{C}_n = 1p_0 + 2p_1 + \dots + np_{n-1}.$

换句话说，访问 $\mathbf{L}[0]$ 中记录的开销为 1（因为只需要查看一个键值），发生这种情况的概率为 $p_0$。访问 $\mathbf{L}[1]$ 中记录的开销为 2（因为我们必须查看第一条和第二条记录的键值），概率为 $p_1$，依此类推。对于 $n$ 条记录，假设所有查找都是针对实际存在的记录，则 $p_0$ 到 $p_{n-1}$ 的概率之和必须为 1。

某些概率分布能给出易于计算的结果。

## 示例 9.1 当每条记录被访问的机会相等时（即对未排序列表进行经典顺序查找），计算查找列表的期望开销。令 $p_i = 1/n$，可得

$\overline{C}_n = \sum_{i=1}^{n} i/n = (n + 1)/2.$

这一结果与我们的预期相符：普通顺序查找平均会访问一半的记录。如果各记录的访问概率确实相等，那么按频率排序并不会带来任何好处。我们在 9.1 节中看到了更一般的情况，即必须考虑查找键与数组中任何记录的键都不匹配的概率（记为 $p_n$）。在这种情况下，按照我们的通用公式，可得

$(1-p_n)\frac{n+1}{2}+p_n n = \frac{n+1 - np_n n - p_n + 2p_n}{2} = \frac{n+1 + p_0(n-1)}{2}.$

因此，$\frac{n+1}{2} \le \overline{C}_n \le n$，具体取决于 $p_0$ 的值。

几何概率分布可能会产生截然不同的结果。

## 示例 9.2 计算按频率排序的列表的期望查找开销，其中概率定义为

p_i = { 1/2^i if 0 ≤ i ≤ n − 2
1/2^n if i = n − 1. }

那么，

C̄_n ≈ Σ_{i=0}^{n-1} (i + 1)/2^{i+1} = Σ_{i=1}^{n} (i/2^i) ≈ 2.

对于这个例子，期望访问次数是一个常数。这是因为访问第一条记录的概率很高（二分之一），访问第二条记录的概率要低得多（四分之一），但仍远高于第三条记录，依此类推。这表明，对于某些概率分布，按频率对列表排序可以产生一种高效的查找技术。

在许多查找应用中，真实的访问模式遵循一条经验法则，称为 80/20 法则。80/20 法则指出，80% 的记录访问集中在 20% 的记录上。80 和 20 这两个值只是估计值；每种数据访问模式都有自己的取值。然而，这种性质的行为在实践中出现得惊人地频繁（这解释了缓存技术的成功，Web 浏览器广泛使用这些技术来加速网页访问，磁盘驱动器和 CPU 制造商也广泛使用它们来加速对存储在较慢内存中的数据的访问；参见 8.3 节关于缓冲池的讨论）。当 80/20 法则适用时，与在无序列表中进行标准顺序查找相比，按访问频率排序的列表可以预期显著提升查找性能。

## 示例 9.3 80/20 法则就是 Zipf 分布的一个例子。

自然出现的分布通常遵循 Zipf 分布。例子包括自然语言（如英语）中单词使用频率的观测结果，以及城市人口的规模（即，将人口的相对比例视为等同于“使用频率”）。Zipf 分布与式 2.10 中定义的调和级数相关。将 n 条记录的分布中第 i 项的 Zipf 频率定义为 1/(i H_n)（参见练习 9.4）。对于成员服从这种 Zipf 分布的序列，其期望开销为

C̄_n = Σ_{i=1}^{n} i / i H_n = n / H_n ≈ n / log_e n.

当频率分布遵循 80/20 法则时，在按频率排序的列表中，平均查找大约会检查 10% 到 15% 的记录。

这是一个可能有用的观察：典型的“真实”记录访问分布，如果按频率对记录排序，那么顺序查找时平均只需访问列表的 10% 到 15%。这意味着，如果我们有一个使用顺序查找的应用，并希望让它稍微快一点（提升一个常数倍数），我们可以做到，而无需对系统进行重大重写来实现诸如查找树之类的东西。但这仅在存在一种（至少近似的）按频率排序记录的简便方法时才成立。

在大多数应用中，我们无法事先知道数据记录的访问频率。更复杂的是，某些记录可能在短时间内被频繁访问，之后便很少被访问。因此，记录的访问概率可能随时间变化（在大多数数据库系统中，这是可以预期的）。自组织列表试图解决这两个问题。

自组织列表根据实际的记录访问模式修改列表中记录的顺序。自组织列表使用启发式方法来决定如何重新排列列表。这些启发式方法类似于管理缓冲池的规则（参见 8.3 节）。事实上，缓冲池就是自组织列表的一种形式。按期望访问频率对缓冲池排序是一个好策略，因为通常我们必须搜索缓冲区的内容，以确定所需信息是否已在主存中。当按访问频率排序时，在必须读取新的信息页时，列表末尾的缓冲区将是最适合重用的一个。下面是管理自组织列表的三种传统启发式方法：

- 1. 保持列表按频率排序的最明显方法是存储每条记录的访问次数，并始终按此顺序维护记录。这种方法称为计数（count）。计数类似于最不经常使用（least frequently used）的缓冲区替换策略。每当一条记录被访问时，如果它的访问次数大于它前面某条记录的访问次数，它就可能向列表前部移动。因此，计数会按照迄今为止实际发生的频率顺序存储记录。除了需要存储访问计数的空间外，计数方法对访问频率随时间的动态变化反应不佳。一旦在频率计数系统下某条记录被访问了大量次数，无论后续的访问历史如何，它都将保持在列表前部附近。

- 2. 当一条记录被找到时，将它移到列表的最前面，并将其他所有记录都向后推一位。这类似于最近最少使用（least recently used）的缓冲区替换策略，称为移至前端（move-to-front）。如果记录存储在链表中，这种启发式方法很容易实现。当记录存储在数组中时，将近末尾处的记录移到前面会导致大量记录（轻微地）改变位置。移至前端方法的花费是有界的，即在至少执行 $n$ 次查找时，它所需的访问次数至多为 $n$ 条记录的 **最优静态排序** 所需访问次数的两倍。换句话说，如果我们事先知道（至少 $n$ 次）查找的序列，并按频率顺序存储记录以使这些访问的总开销最小，那么该开销至少是移至前端启发式方法所需开销的一半。（这一点将在 14.3 节中用均摊分析证明。）最后，移至前端方法能很好地响应访问频率的局部变化，即如果某条记录在短时间内被频繁访问，那么在这段访问期间它将位于列表前部附近。当记录按顺序处理时，特别是这种顺序随后被重复多次时，移至前端方法的表现不佳。

- 3. 将找到的任意记录与列表中紧挨在它前面的记录交换。这种启发式方法称为 **转置**（transpose）。转置方法对于基于链表或数组的列表实现都很好。频繁使用的记录会随着时间推移移到列表前部。曾经被频繁访问但不再使用的记录会慢慢向列表后部漂移。因此，它在访问频率变化方面似乎具有良好的性质。不幸的是，某些病态的访问序列会使转置方法表现不佳。考虑访问列表中最后一条记录（称之为 $X$）的情况。这条记录随后与倒数第二条记录（称之为 $Y$）交换，使 $Y$ 成为最后一条记录。如果现在访问 $Y$，它会与 $X$ 交换。$X$ 和 $Y$ 交替访问的重复序列将不断查找到列表末尾，因为这两条记录都不会向前推进。然而，这种病态情况在实践中并不常见。转置方法的一种变体是按固定的步数将访问的记录在列表中向前移动。

$F\ D\ F\ G\ E\ G\ F\ A\ D\ F\ G\ E.$
