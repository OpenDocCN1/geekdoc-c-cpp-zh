
这是高效的，需要 Θ(n) 时间。然而，它也需要两个大小为 n 的数组。接下来是一个代码片段，它将排列按顺序放置，但仍在同一个数组内完成（因此它是“原地”排序的一个例子）。

```
for (i=0; i<n; i++)
    while (A[i] != i)
        swap(A, i, A[i]);
```

函数 swap(A, i, j) 交换数组 A 中的元素 i 和 j。第二个代码片段实际上能对数组排序，这一点可能并不明显。为了理解其工作原理，请注意 for 循环的每次迭代至少会将值为 i 的整数移动到其在数组中的正确位置，并且在这次迭代中，A[i] 的值必须大于或等于 i。总共最多执行 n 次交换操作，因为一个整数一旦被放置到正确位置就不会再被移出，而每次交换操作至少会将一个整数放到其正确位置。因此，该代码片段的代价为 Θ(n)。然而，它运行所需的时间比第一个代码片段更长。在我的电脑上，第二个版本运行所需的时间几乎是第一个的两倍，但它只需要一半的空间。

关于程序空间和时间需求之间关系的第二条原则适用于处理存储在磁盘上的信息的程序，如第 8 章及以后章节所讨论的那样。奇怪的是，基于磁盘的空间/时间权衡原则几乎与使用主存的程序的空间/时间权衡原则相反。

基于磁盘的空间/时间权衡原则指出，你能使磁盘存储需求越小，程序运行就越快。这是因为从磁盘读取信息的时间与计算时间相比非常巨大，因此几乎任何用于解包数据所需的额外计算量都会小于通过减少存储需求而节省的磁盘读取时间。当然，这一原则并非在所有情况下都成立，但在设计处理存储在磁盘上的信息的程序时，最好牢记这一点。

## 3.10 加速你的程序

在实践中，增长率为 Θ(n) 的算法与增长率为 Θ(n log n) 的算法在运行时间上没有太大差别。然而，增长率为 Θ(n log n) 和 Θ(n²) 的算法在运行时间上却有巨大差异。在学习常见数据结构和算法的过程中，你会看到，一个显而易见的解法需要 Θ(n²) 时间的问题，往往也存在一个需要 Θ(n log n) 时间的解法，这并不罕见。例子包括排序和搜索，这是两个最重要的计算机问题。

示例 3.18 下面是一个真实的故事。几年前，我的一名研究生遇到了一个大问题。他的论文工作涉及对一个大数据库进行若干复杂的操作。他当时正在处理最后一步。“Shaffer 博士，”他说，“我正在运行这个程序，它似乎要花很长时间。”在检查了算法之后，我们意识到它的运行时间是 Θ(n²)，并且可能需要一到两周才能完成。即使我们能在那段时间内让计算机不间断运行，他也希望在毕业前完成论文。幸运的是，我们意识到有一种相当简单的方法可以将该算法转换，使其运行时间变为 Θ(n log n)。到第二天，他修改了程序。它只运行了几个小时，他按时完成了论文。

虽然“代码调优”远不如改变算法以降低其增长率那么重要，但它也能显著改善运行时间。代码调优是一门手工优化程序以使其运行更快或需要更少存储空间的艺术。对于许多程序，代码调优可以将运行时间减少一个数量级，或将存储需求削减一半以上。我曾经调优过一个程序中的关键函数——在不改变其基本算法的情况下——实现了 200 倍的加速。然而，为了获得这种加速，我确实对信息的表示方式做了重大更改，从符号编码方案转换为可以直接进行计算的数字编码方案。

以下是一些通过代码调优加速程序的建议。最重要的一点是要认识到，程序中的大多数语句对程序的运行时间没有太大影响。通常只有少数几个关键子程序，甚至可能是关键子程序中的关键代码行，占据了大部分运行时间。将一个只占总运行时间 1% 的子程序的运行时间减半几乎没有意义。要把注意力集中在程序中影响最大的部分。

在调优代码时，收集良好的计时统计信息非常重要。许多编译器和操作系统都包含性能分析器和其他特殊工具，用于帮助收集时间和空间使用情况的信息。这些工具在试图提高程序效率时非常宝贵，因为它们可以告诉你应该在哪里投入精力。

很多代码调优基于避免工作而非加速工作的原则。常见的情况是，我们可以测试某个条件，从而跳过一些工作。然而，这样的测试从来不是完全没有代价的。必须小心，确保测试的成本不超过节省的工作量。虽然一次测试可能比潜在节省的工作更便宜，但测试必须始终执行，而工作只能在部分情况下被避免。

### 示例 3.19

计算机图形应用中的一个常见操作是，在一组复杂对象中找出哪个包含空间中的给定点。人们已经开发出许多有用的数据结构和算法来处理这个问题的各种变体。大多数此类实现都涉及以下调优步骤。直接测试一个给定的复杂对象是否包含该点相对昂贵。相反，我们可以先检查该点是否位于对象的边界框内。边界框就是包含该对象的最小矩形（通常定义为边与 x 轴和 y 轴垂直）。如果点不在边界框内，那么它不可能在对象内。只有当点在边界框内时，我们才进行对象与点的完整比较。注意，如果点位于边界框之外，我们节省了时间，因为边界框测试比完整对象与点的比较更便宜。但如果点位于边界框内，则该测试是多余的，因为我们仍然需要将点与对象进行比较。通常，通过进行此测试所避免的工作量大于对每个对象进行测试的成本。

### 示例 3.20

第 7.2.3 节介绍了一种名为选择排序的排序算法。该算法的主要特点是，它对要排序的数组中存储的记录进行相对较少的交换。然而，它有时会执行不必要的交换操作，即尝试将一个记录与自身交换。可以通过测试被交换的两个索引是否相同来避免这项工作。然而，这种情况并不经常发生。由于测试的成本与测试成功时节省的工作量相比足够高，添加测试通常会使程序变慢，而不是加快速度。

注意不要使用让程序难以阅读的技巧。大多数代码调优只是清理写得草率的程序，而不是拿一个清晰的程序并添加技巧。特别是，你应该认识到现代编译器在优化表达式方面具有非常强大的能力。这里的“表达式优化”是指对算术或逻辑表达式进行重新排列，以提高运行效率。注意不要为了自己优化表达式而损害编译器为你进行此类优化的能力。始终通过在一组合适的基准输入上运行更改前后的程序，来检查你的“优化”是否确实改善了程序。很多次，我对自己程序中代码调优的积极效果判断错误。大多数时候，我是在尝试优化表达式时出错。要做到比编译器更好是很困难的。

最大的时间和空间改进来自于更好的数据结构或算法。本节的最后思考是：

先调优算法，再调优代码。
