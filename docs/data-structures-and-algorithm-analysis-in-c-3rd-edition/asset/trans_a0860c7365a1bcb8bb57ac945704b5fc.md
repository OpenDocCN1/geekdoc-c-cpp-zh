哪种策略最好？这取决于预期的内存请求类型。如果请求的大小差异很大，最佳适配可能效果很好。如果请求倾向于相似大小，且偶尔出现大和小请求，则首次适配或最差适配可能效果很好。不幸的是，总有一些请求模式是三种顺序适配方法中的一种可以处理的，但另外两种无法处理。例如，如果对包含块 500、700、650、900（按此顺序）的空闲列表发出请求序列 600、650、900、500、100，则所有请求都可以通过首次适配得到满足，但不能通过最佳适配。或者，请求序列 600、500、700、900 可以通过最佳适配得到满足，但不能通过首次适配在同一空闲列表上得到满足。

## Buddy Methods

顺序适配方法依赖于空闲块的链表，在每次内存请求时必须搜索合适的块。因此，在包含 n 个块的空闲列表中，找到合适的空闲块的时间在最坏情况下为 Θ(n)。合并相邻的空闲块有些复杂。最后，我们必须为链表使用额外的空间，或在内存池中使用空间来支持内存管理器操作。在第二种方案中，空闲块和保留块都需要标签和大小字段。空闲块中的字段不占用任何空间（因为它们存储在未被其他用途使用的内存中），但保留块中的字段会产生额外开销。

伙伴系统解决了这些问题中的大多数。搜索合适大小的块是高效的，合并相邻的空闲块很简单，并且无需在保留块中存储标签或其他信息字段。伙伴系统假设内存大小为 2^N，其中 N 为某个整数。空闲块和保留块始终为大小 2^k，其中 k ≤ N。在任何给定时间，可能存在各种大小的空闲块和保留块。伙伴系统为每种大小的空闲块维护一个单独的列表。最多可以有 N 个这样的列表，因为只能有 N 种不同的块大小。

当收到 m 个字的请求时，我们首先确定使 2^k ≥ m 成立的最小 k 值。如果该块大小的空闲列表中存在块，则从该块大小的空闲列表中选择一个大小为 2^k 的块。伙伴系统不担心内部碎片：整个大小为 2^k 的块将被分配。

如果不存在大小为 2^k 的块，则找到下一个更大的块。该块被一分为二（必要时重复），直到创建所需的大小为 2^k 的块为止。此拆分过程中产生的任何其他块都将被放置在适当的空闲列表上。

图 12.14 伙伴系统的示例。(a) 大小为 8 的块。(b) 大小为 4 的块。

伙伴系统的缺点是它允许内部碎片。例如，对 257 个字的请求将需要一个大小为 512 的块。伙伴系统的主要优点是（1）外部碎片更少；（2）搜索合适大小的块比例如最佳适配便宜，因为我们只需要找到大小为 2^k 的块列表上的第一个可用块；并且（3）合并相邻的空闲块很容易。

之所以称此方法为伙伴系统，是因为合并方式如此。任何大小为 2^k 的块的伙伴都是另一个相同大小的块，并且地址相同（即内存中的字节位置，以二进制值读取），只是第 k 位被反转。例如，图 12.14(a) 中起始地址为 0000 的大小为 8 的块，其伙伴的地址为 1000。同样，在图 12.14(b) 中，地址为 0000 的大小为 4 的块，其伙伴为 0100。如果空闲块按地址值排序，则可以通过搜索正确的块大小列表找到伙伴。合并只需将合并伙伴的地址移动到下一个更大的块大小的空闲列表中即可。

## Other Memory Allocation Methods

除了顺序适配和伙伴方法之外，还有许多内存管理的临时方法。如果应用程序足够复杂，可能希望将可用内存划分为几个内存区域，每个区域使用不同的内存管理方案。例如，一些区域可能具有简单的一进一出内存访问模式。该区域因此可以使用简单的栈有效地管理。另一个区域可能只分配固定大小的记录，因此可以用第 4.1.2 节所述的简单空闲列表进行管理。其他区域可能需要本节讨论的通用内存分配方法之一。区域的优点是内存的某些部分

## 12.3.2 Failure Policies and Garbage Collection

在处理一系列请求时，内存管理器可能会遇到无法满足的内存请求。在某些情况下，可能无能为力：可能根本没有足够的空闲内存来满足请求，并且应用程序可能要求立即满足请求。在这种情况下，内存管理器别无选择，只能返回错误，这可能导致应用程序程序失败。然而，在许多情况下，除了简单地返回错误之外还有替代方案。这些可能的选项统称为故障策略。

在某些情况下，可能有足够的空闲内存来满足请求，但它分散在小块中。这在使用顺序适配内存分配方法时可能会发生，其中外部碎片导致了一系列小块，这些小块合计可以满足请求。在这种情况下，可能可以通过移动保留块来压缩内存，从而将空闲空间收集到单个块中。这种方法的问题在于应用程序必须以某种方式能够处理其数据现在已移动到不同位置的事实。如果应用程序程序以任何方式依赖于数据在内存中的绝对位置，这将是灾难性的。处理此问题的一种方法涉及内存管理器返回的句柄。句柄作为对内存位置的第二级间接引用。内存分配例程不返回存储块的指针，而是返回指向句柄的指针，该句柄反过来提供对存储的访问。句柄永远不会移动其位置，但块的位置可能会被移动，并且句柄的值会被更新。当然，这要求内存管理器跟踪句柄以及它们与存储消息的关联方式。图 12.15 说明了这一概念。
