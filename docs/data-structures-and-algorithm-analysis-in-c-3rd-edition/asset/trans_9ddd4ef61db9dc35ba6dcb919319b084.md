

生日问题类似于将记录分配到表（大小为 365）中的槽位，使用生日作为哈希函数。需要注意的是，这一观察并不能告诉我们哪些学生生日相同，也不能说明共享生日落在一年中的哪几天。

为了实用，基于哈希组织的数据库必须将记录存储在不会浪费空间的哈希表中。通常，这意味着哈希表大约半满。由于在这种条件下碰撞极有可能发生（按机会来说，插入到半满表中任意一条记录有一半的概率会发生碰撞），这是否意味着我们不必担心哈希函数避免碰撞的能力？绝对不是。好的哈希函数与坏的哈希函数之间的差异在实践中会产生很大影响。技术上，任何将所有可能键值映射到哈希表槽中的函数都是哈希函数。在极端情况下，甚至将所有记录映射到同一槽的函数也是哈希函数，但它对在搜索操作期间查找记录毫无帮助。

我们希望选择一个哈希函数，使得集合中的实际记录在哈希表中存储的方式使每个槽被填满的概率相等。不幸的是，我们通常无法控制实际记录的键值，因此任何特定哈希函数做得如何取决于键在允许的键范围内的分布。在某些情况下，输入数据在其键范围内分布良好。例如，如果输入是从键范围内均匀选择的随机数集，那么任何将键范围分配给每个哈希表槽获得相等份额的哈希函数也可能将输入记录均匀地分布在表中。然而，在许多应用中，传入的记录高度聚集或分布不良。当输入记录在键范围内分布不佳时，很难设计出一个能很好地将记录分布到表中的哈希函数，尤其是当输入分布事先未知时。

数据值分布不良的原因有很多。

- 1. 自然频率分布往往遵循一个共同模式，其中少数实体频繁出现，而大多数实体相对罕见。例如，考虑美国 100 个最大城市的人口。如果你在数轴上绘制这些人口，大多数会聚集在低侧，而少数异常值在高侧。这就是齐普夫分布的一个例子（参见第 9.2 节）。反过来来看，某人的家乡更可能是某个大城市，而不是某个小镇。
- 2. 收集的数据可能在某种程度上存在偏差。现场样本可能四舍五入到，例如，最近的 5（即所有数字以 5 或 0 结尾）。
- 3. 如果输入是一组常见的英语单词，首字母的分布会很差。

请注意，在示例 2 和 3 中，键的高位或低位都很差地分布。

在设计哈希函数时，我们通常面临两种情况之一。

- 1. 我们对传入键的分布一无所知。在这种情况下，我们希望选择一个哈希函数，使键范围均匀分布在哈希表上，同时避免明显的聚集机会，例如对键值的最高位或最低位敏感的哈希函数。
- 2. 我们对传入键的分布有所了解。在这种情况下，我们应该使用依赖于分布的哈希函数，避免将相关键值的簇分配到同一个哈希表槽中。例如，如果对英语单词进行哈希，我们不应根据第一个字符的值进行哈希，因为这很可能分布不均。

下面是几个哈希函数的例子，说明了这些观点。

### Example 9.5

考虑以下用于将整数哈希到十六个槽的表的哈希函数：

```
int h(int x) {
    return x % 16;
}
```

此哈希函数返回的值完全取决于键的最低有效四位。由于这些位很可能分布不良（例如，大比例的键可能是偶数，这意味着低位为零），结果也会分布不良。此示例表明表大小 M 可以对哈希系统的性能产生很大影响，因为该值通常用作模数，以确保哈希函数产生 0 到 M − 1 范围内的数字。

### Example 9.6

数值的一个好的哈希函数来自平方中值法。平方中值法对键值进行平方，然后取结果的中间 r 位，得到 0 到 2^r − 1 范围内的值。这效果很好，因为键值的多数或全部位都对结果有贡献。例如，考虑键为 10 进制 4 位数字的记录。目标是将这些键值哈希到大小为 100 的表（即 0 到 99 的范围）。该范围相当于 10 进制的两位数字。即 r = 2。如果输入数字为 4567，平方后得到 8 位数字 20857489。该结果的中间两位数字为 57。所有数字（等价于将数字视为二进制时的所有位）都对平方值的中间两位数字有贡献。

### Example 9.7

这里有一个用于字符字符串的哈希函数：

```
int h(char* x) {
    int i, sum;
    for (sum=0, i=0; x[i] != '\0'; i++)
        sum += (int) x[i];
    return sum % M;
}
```

此函数对字符串中字母的 ASCII 值求和。如果哈希表大小 M 很小，此哈希函数应能很好地将字符串均匀分布到哈希表槽中，因为它对所有字符赋予同等权重。这是设计哈希函数的折叠方法的一个例子。请注意，字符串中字符的顺序对结果没有影响。对整数的类似方法将对键值的数字求和，前提是（1）有足够的数字以防止一两个分布不良的数字扭曲过程的结果，以及（2）生成的和远大于 M。与许多其他哈希函数一样，最后一步是对结果应用模运算符，使用表大小 M 生成表范围内的值。如果和不够大，则模运算符将产生不良分布。例如，因为 “A” 的 ASCII 值为 65 而 “Z” 为 90，对于十个大写字母的字符串，sum 总是在 650 到 900 的范围内。对于大小为 100 或更小的哈希表，结果分布合理。对于大小为 1000 的哈希表，分布很糟糕，因为只有槽 650 到 900 才可能是某个键值的归宿，并且即使在这些槽内，值也不是均匀分布的。

### Example 9.8

这里有一个用于字符串的更好的哈希函数。

```
// Use folding on a string, summed 4 bytes at a time
int fold(char* key) {
unsigned int *lkey = (unsigned int *)key;
int intlength = strlen(key)/4;
unsigned int sum = 0;
for(int i=0; i<intlength; i++)
sum += lkey[i];

// Now deal with the extra chars at the end
int extra = strlen(key) - intlength*4;
char temp[4];
lkey = (unsigned int *)temp;
lkey[0] = 0;
for(int i=0; i<extra; i++)
temp[i] = key[intlength*4+i];
sum += lkey[0];
return sum % M;
}
```

此函数将字符串作为输入。它一次处理字符串的四个字节，并将每个四字节块解释为单个（无符号）长整数值。四字节块的整数值相加。最后，通过模运算符将得到的和转换为 0 到 M – 1 的范围。²

例如，如果字符串 “aaaabbbb” 传递给 fold，则前四个字节（“aaaa”）将被解释为整数值 1,633,771,873，而接下来的四个字节（“bbbb”）将被解释为整数值 1,650,614,882。它们的和为 3,284,386,755（作为无符号整数查看）。如果表大小为 101，则模函数将导致此键哈希到表中的槽 75。请注意，对于任何足够长的字符串，整数量的和通常会导致 32 位整数溢出（从而丢失一些高位），因为所得值非常大。但在计算哈希函数的目标下，这不会造成问题。

> ²Recall from Section 2.2 that the implementation for n mod m on many C++ and Java compilers will yield a negative number if n is negative. Implementors for hash functions need to be careful that their hash function does not generate a negative number. This can be avoided either by ensuring that n is positive when computing n mod m, or adding m to the result if n mod m is negative. All computation in fold is done using unsigned long values in part to protect against taking the modulus of a negative number.
