图9.10 预期记录访问次数随α的增长情况。横轴为α的值，纵轴为对哈希表的预期访问次数。实线表示“随机”探测的成本（理论上的成本下界），虚线表示线性探测的成本（一种相对较差的冲突解决策略）。最左侧两条线表示插入（等价于不成功搜索）的成本；最右侧两条线表示删除（等价于成功搜索）的成本。

需要认识到，这些方程描述的是基于一个不切实际假设的预期操作成本，即探测序列是哈希表中槽位的随机排列（从而避免了由聚集引起的所有额外开销）。因此，这些成本是平均情况下的下界估计。在线性探测下，真实的平均成本为：插入或不成功搜索为½(1 + 1/(1 − α)²)，删除或成功搜索为½(1 + 1/(1 − α))。这些结果的证明可在第9.5节引用的参考文献中找到。

图9.10展示了这四个方程的曲线图，帮助你可视化基于负载因子的哈希预期性能。两条实线表示“随机”探测序列下的成本：(1) 插入或不成功搜索；(2) 删除或成功搜索。正如预期，插入或不成功搜索的成本增长更快，因为这些操作通常会沿着探测序列搜索得更远。两条虚线表示线性探测下的相应成本。正如预期，线性探测的成本比“随机”探测增长得更快。

从图9.10可以看出，当哈希表不太满时，哈希的成本通常接近一次记录访问。这是极其高效的，远比需要log n次记录访问的二分查找要好。随着α增大，预期成本也随之增加。对于较小的α值，预期成本较低。在哈希表大约半满之前，成本一直保持在两次以下。当哈希表几乎为空时，向表中添加一条新记录不会显著增加未来搜索操作的成本。然而，一旦哈希表半满，每次额外插入所导致的额外搜索成本会迅速增加。基于这一分析，经验法则是设计哈希系统时使哈希表的使用率永远不超过半满。超过该点后，性能将迅速下降。这要求实现者对表在最大负载时可能包含的记录数量有一定了解，并据此选择表的大小。

你可能会注意到，建议永远不要让哈希表超过半满，这与基于磁盘的空间/时间权衡原则相矛盾，后者力求最小化磁盘空间以提高信息密度。哈希是一种特殊情况，因为它无法从局部性原理中获益。从某种意义上说，哈希系统的实现者尽一切可能消除局部性原理的影响！在精心设计的哈希系统中，给定包含最近访问记录的磁盘块，下一次记录访问落入同一磁盘块的概率不会高于随机概率。这是因为良好的哈希实现打破了搜索键之间的关系。哈希并不通过利用局部性原理来提高性能，而是用更大的哈希表空间来换取记录位于其“归属位置”的更高概率。因此，哈希表可用的空间越多，哈希就应该越高效。

根据记录访问的模式，即使面对冲突，也有可能降低预期访问成本。回想一下80/20规则：80%的访问会落在20%的数据上。换句话说，某些记录被访问得更频繁。如果两条记录哈希到同一个归属位置，哪一条更适合放在归属位置，哪一条放在探测序列更靠后的位置？答案是，访问频率更高的记录应放在归属位置，因为这会减少总的记录访问次数。理想情况下，探测序列中的记录应按其访问频率排序。

实现这一目标的一种近似方法是，在访问记录时修改探测序列中记录的顺序。如果搜索到一条不在其归属位置的记录，可以使用自组织列表启发式方法。例如，如果使用线性探测冲突解决策略，那么每当定位到一条不在其归属位置的记录时，可以将其与探测序列中它前面的记录交换。那条被交换的记录现在离其归属位置更远了，但希望它的访问频率较低。请注意，这种方法不适用于本节中介绍的其他冲突解决策略，因为交换一对记录以改善对其中一条的访问，可能会将另一条从其探测序列中移除。
