

将问题的所有子问题的处理组织起来，以便高效地完成工作。

如果我们需要对整个解空间进行暴力搜索，我们可以使用 **回溯** 来遍历以解树组织的全部可能解。例如，可满足性问题对布尔表达式中包含的 n 个变量的真值赋值有 2ⁿ 种可能的方式。我们可以将此视为一棵解树，因为我们可以选择使第一个变量为 `true` 或 `false`。因此，我们可以将第一个变量为 `true` 的所有解放在树的某一侧，其余解放在另一侧。然后我们通过沿着树的一条分支向下移动来检查解，直到到达我们知道解不可能正确的地方，例如当前的部分赋值集合产生了一个不可满足的表达式。此时我们回溯并向上移动一个节点，然后沿着另一条分支向下。如果失败，我们就知道需要进一步回溯到树中并沿着备选分支进行，直到最终找到满足表达式的解或遍历完整棵树。在某些情况下，我们避免处理许多潜在解，或快速找到一个解。在其他情况下，我们最终会访问 2ⁿ 个可能解中的很大一部分。

**分支限界** 是回溯的扩展，适用于 **优化问题**，例如旅行商问题，我们试图找到穿过城市的最短路径。我们像回溯一样遍历解树。然而，我们记住迄今为止找到的最佳值。沿着给定分支向下进行相当于决定以何种顺序访问城市。因此，解树中的任何节点都代表迄今为止访问的一些城市集合。如果这些距离之和超过迄今为止找到的最佳旅行，则我们知道应停止追求该分支的树。此时我们可以立即回溯并选择另一条分支。如果我们有一种快速找到良好（但不一定是最优）解的方法，我们可以用它作为初始界值，以有效地剪掉树的一部分。

另一种应对策略是为问题找到近似解。寻找近似解的方法有很多种。一种方法是使用启发式方法求解问题，即基于“经验法则”的算法，并不总是给出最佳答案。例如，旅行商问题可以通过使用以下启发式方法近似求解：我们从任意城市开始，然后总是前往最近的未访问城市。这种方法很少给出最短路径，但解可能足够好。旅行商问题还有许多其他启发式方法，效果更好。

一些近似算法具有保证的性能，使得答案将在最佳可能答案的某个百分比范围内。例如，考虑顶点覆盖问题的这个简单启发式：设 M 为 G 中的一个极大（不一定是最大）**匹配**。匹配将顶点配对（通过连接边），使得没有顶点与超过一个伙伴配对。极大意味着尽可能多地选择配对，按某种顺序选择，直到没有更多可选择的配对为止。最大意味着对于给定图，给出最多配对的匹配。如果 OPT 是最小顶点覆盖的大小，则 |M| ≤ 2 · OPT，因为任何顶点覆盖中必须至少包含每条匹配边的其中一个端点。

关于解的保证界限的更好例子来自于求解装箱问题的简单启发式。

> **装箱问题：**
>
> **输入：** 介于 0 和 1 之间的数字 \(x_1, x_2, \dots, x_n\)，以及无限数量的容量为 1 的箱子（没有箱子可以容纳总和超过 1 的数字）。
>
> **输出：** 将数字分配到箱子中所需的箱子数最少。

装箱问题在其判定形式中（即询问项目是否可以装入少于 k 个箱子）已知是 NP-完全的。求解此问题的简单启发式是使用“首次适应”方法。我们将第一个数字放入第一个箱子。然后如果它能放入，我们就将第二个数字放入第一个箱子，否则将其放入第二个箱子。对于每个后续数字，我们只需按生成顺序遍历箱子，并将数字放入第一个能容纳它的箱子中。使用的箱子数不超过数字之和的两倍，因为每个箱子（可能有一个除外）必须至少半满。然而，这种“首次适应”启发式可能会给出远差于最优的结果。考虑以下数字集合：六个大小为 1/7 的数字，六个大小为 1/3 + ε 的数字，以及六个大小为 1/2 + ε 的数字，其中 ε 是一个很小的正数。正确组织时，这需要 6 个箱子。但如果做错了，我们可能会将数字装入 10 个箱子。

更好的启发式是使用递减首次适应。这与首次适应相同，只是我们将箱子按从最满到最不满的顺序排序。然后在决定放置下一个项目的位置时，我们将其放入能容纳它的最满的箱子中。这类似于第 12.3 节中讨论的内存管理的“最佳适应”启发式。关于此启发式的重要之处不仅仅在于它往往比简单的首次适应具有更好的性能。这种递减首次适应启发式可以被证明所需箱子数不超过最优箱子数的 11/9 倍。因此，我们对使用启发式时可能产生的低效率有一个保证。

NP-完全性的理论提供了一种将可处理问题与（可能）不可处理问题分开的技术。回顾第 15.1 节中生成算法的算法，我们可以将其细化为我们怀疑是 NP-完全的问题。面对新问题时，我们可能会在检查其是否可处理（即我们尝试找到多项式时间解）和检查其是否不可处理（我们尝试证明该问题是 NP-完全的）之间交替。虽然证明某个问题是 NP-完全的并不能真正使我们的算法的上界与问题的下界完全匹配，但它几乎一样好。一旦我们意识到一个问题是 NP-完全的，那么我们下一步就必须重新定义问题使其更容易，或者使用本节讨论的“应对”策略之一。

## 17.3 不可能的问题

即使是最好的程序员有时也会编写一个进入无限循环的程序。当然，当你运行一个没有停止的程序时，你无法确定它只是运行缓慢还是进入了无限循环。经过“足够长的时间”后，你会将其关闭。如果你的编译器能在你运行之前查看你的程序并告诉你它会进入无限循环，那不是很好吗？更具体地说，给定一个程序和特定的输入，在不实际运行程序的情况下知道在该输入上执行程序是否会导致无限循环将是有用的。

不幸的是，称为停机问题的问题无法解决。永远不会有计算机程序能够肯定地确定，对于任意程序 P，P 是否会对所有输入停止。甚至也不会有计算机程序能够肯定地确定任意程序 P 是否会对指定的输入 I 停止。这怎么可能？程序员经常查看程序以确定它们是否会停止。 surely 这可以自动化。作为对那些相信任何程序都可以通过这种方式分析的人的警告，请在继续阅读前仔细检查以下代码片段。

```
while (n > 1)
    if (ODD(n))
        n = 3 * n + 1;
    else
        n = n / 2;
```

这是著名的代码片段。此代码为输入值 n 分配的数值序列有时称为柯拉茨序列。 对于所有 n 值，此代码片段是否会停止？没有人知道答案。已尝试的每个输入都会停止。但它总是停止吗？请注意，对于此代码片段，由于我们不知道它是否会停止，我们也不知道其运行时间的上界。至于下界，我们可以很容易地证明为 Ω(log n)（参见练习 3.14）。
