
比基于数组的实现更节省空间，前提是列表中的元素相对较少。相反，当数组接近满时，基于数组的实现变得更节省空间。利用该方程，我们可以求解 n 来确定盈亏平衡点，超过该点基于数组的实现在任何特定情况下都更节省空间。这发生在

n > DE/(P + E).

如果 P = E，则盈亏平衡点为 D/2。这将发生在元素字段为四字节 int 值或指针，而下一个字段为典型的四字节指针时。也就是说，如果链接字段和元素字段大小相同，则只要数组超过半满，基于数组的实现就会更高效。

作为经验法则，当实现的元素数量变化很大或未知时，链表更节省空间。基于数组的列表通常在用户事先大致知道列表将变得多大的情况下更节省空间。

基于数组的列表对于按位置的随机访问更快。位置可以通过 next 和 prev 方法轻松向前或向后调整。这些操作始终需要 Θ(1) 时间。相比之下，单链表没有对前一个元素的显式访问，按位置访问需要我们从前面（或当前位置）沿着列表走到指定位置。这两个操作在平均和最坏情况下都需要 Θ(n) 时间，如果我们假设在每次调用 prev 或 moveToPos 时，列表上的每个位置被访问的可能性相等。

给定指向列表中合适位置的指针，链表的 insert 和 remove 方法仅需要 Θ(1) 时间。基于数组的列表必须在数组内向上或向下移动列表的其余部分。这在平均和最坏情况下需要 Θ(n) 时间。对于许多应用程序，插入和删除元素的时间占主导地位，超过所有其他操作。因此，出于这个原因，链表通常优于基于数组的列表。

在实现基于数组的列表时，实现者可以允许数组的大小根据实际存储的元素数量而增长和缩小。这种数据结构称为动态数组。Java 和 C++/STL Vector 类都实现了动态数组。动态数组允许程序员绕过标准数组的限制，即一旦数组创建后其大小就不能更改。这也意味着在动态数组要使用之前无需为其分配空间。这种方法的缺点是处理数组的空间调整需要时间。每次数组增大时，其内容必须被复制。一个良好的动态数组实现会在增长和缩小数组时保持一种方式，使得一系列插入/删除操作的总体成本相对便宜，即使偶尔的插入/删除操作可能很昂贵。一个简单的经验法则是当数组满时将其大小加倍，并在数组变为四分之一满时将其大小减半。为了分析动态数组操作随时间的总体成本，我们需要使用一种称为 **amortized analysis** 的技术，该技术在第 14.3 节中讨论。

## 4.1.4 元素实现

列表用户必须决定是否希望在包含它的每个列表上存储给定元素的副本。对于整数等小型元素，这是有意义的。如果元素是工资记录，则可能希望列表节点存储指向该记录的指针，而不是存储记录本身的副本。此更改将允许多个列表节点（或其他数据结构）指向同一记录，而不是重复复制记录。不仅可能节省空间，而且还意味着对元素值的修改将在其被引用的所有位置自动反映出来。存储指向每个元素的指针的缺点是指针本身需要空间。如果元素从不被重复，则这种额外的空间会增加不必要的开销。

本节中介绍的用于列表的 **C++** 实现为列表用户提供了是否存储元素副本或元素指针的选择。用户可以将 **E** 声明为例如指向工资记录的指针。在这种情况下，多个列表可以指向记录的同一副本。另一方面，如果用户将 **E** 声明为记录本身，则在将其插入列表时将制作记录的新副本。

使用指向共享元素的指针还是单独的副本是否更有优势，取决于预期应用。一般来说，元素越大且重复越多，使用指向共享元素的指针就越有可能成为更好的方法。

列表类实现者（或任何其他存储用户定义数据元素集合的数据结构）面临的第二个问题是，存储的元素是否都需要是同一类型。这在数据结构中称为 **homogeneity**。在某些应用中，用户希望定义存储在给定列表上的数据元素的类，然后永远不允许将不同类的对象存储在同一列表上。在其他应用中，用户希望允许存储在单个列表上的对象具有不同的类型。

本节中介绍的列表实现要求编译器确保存储在列表上的所有对象都是同一类型。事实上，由于列表是使用模板实现的，编译器为每种数据类型创建一个新类。对于希望最小化编译器创建的类数量的实现者，列表都可以存储一个 **void*** 指针，用户对每个元素执行必要的类型转换，将其转换为和从实际对象类型转换。然而，这种

方法要求用户自行进行类型检查，以强制执行同质性或区分各种对象类型。

除了 C++ 模板之外，列表类的实现者还可以使用其他技术来确保给定列表的元素类型保持固定，同时仍允许不同的列表存储不同的元素类型。一种方法是存储适当类型的对象在列表的头节点中（也许在列表构造函数中作为参数提供适当类型的对象），然后检查该列表上的所有插入操作是否使用相同的元素类型。

用户在使用列表实现时必须面对的第三个问题主要是在不提供自动垃圾回收的语言中编程时才令人担忧。也就是说，当列表被删除或调用 clear 方法时如何处理存储在列表上的对象的内存。列表析构函数和 clear 方法存在问题，因为它们可能被误用，从而导致内存泄漏。存储元素的类型决定了这里是否存在潜在问题。如果元素是 int 等简单类型，则无需显式删除元素。如果元素是用户定义类，则会调用其自己的析构函数。但是，如果列表元素是指向对象的指针呢？那么在基于数组的实现中删除 listArray，或在链表实现中删除链接节点，可能会删除对对象的唯一引用，使其内存空间无法访问。不幸的是，列表实现无法知道给定对象是否在程序的其他部分被指向。因此，列表用户必须负责在适当时删除这些对象。
