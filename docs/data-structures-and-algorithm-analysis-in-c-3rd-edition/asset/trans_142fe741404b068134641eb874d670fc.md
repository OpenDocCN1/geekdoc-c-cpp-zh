一个 32 位的键。当然，这需要一个大小为 64K 的 cnt 数组。只有当记录数接近 64K 或更大时，性能才会良好。换句话说，记录数必须相对于键大小很大，基数排序才有效。在许多排序应用中，基数排序可以通过这种方式进行调优以获得良好的性能。

基数排序依赖于能够基于数字值进行固定次数的多路选择，以及对 bin 的随机访问。因此，对于某些键类型，实现基数排序可能很困难。例如，如果键是实数或任意长度的字符串，则实现时需要格外小心。特别是，基数排序在区分实数或可变长度字符串时，需要小心决定何时找到“最后一位数字”。使用 trie 数据结构（第 13.1 节）实现基数排序的概念最适合这些情况。

此时，敏锐的读者可能会开始质疑我们之前关于键比较需要恒定时间的假设。如果键是“普通整数”值存储在例如整数变量中，那么这个变量的大小与 n 相比如何？事实上，可以肯定的是，32（标准 int 变量中的位数）对于任何实际计算都大于 log n。在这种意义上，比较两个长整数需要 Ω(log n) 的工作。

计算机通常以特定大小的单位进行算术运算，例如 32 位字。无论变量的大小如何，比较都使用这种本地字大小并且需要恒定时间，因为比较是在硬件中实现的。实际上，比较两个 32 位值需要恒定时间，即使 32 远大于 log n。在一定程度上，存在恒定时间操作（例如整数比较）这一命题的真实性取决于观察者的角度。在计算机体系结构的门级，逐位比较。然而，在大多数计算机上，整数的恒定时间比较在实践中是真实的（它们需要固定数量的机器指令），我们依赖于此类假设作为分析的基础。相比之下，基数排序必须对键值进行几次算术计算（每次都需要恒定时间），而此类计算的数量与键长度成正比。因此，基数排序真正需要 Ω(n log n) 的工作来处理 n 个不同的键值。

除了最右边的列外，每个算法的输入都是整数的随机数组。这会影响某些排序算法的计时。例如，选择排序由于记录大小很小而没有得到充分利用，因此表现并不理想。基数排序实现确实利用了这个键范围，因为它不会查看不必要的更多位数。另一方面，它没有优化为使用位移代替除法，即使使用的基数允许这样做。

各种排序算法针对列表大小 10、100、1000、10,000、100,000 和 1,000,000 显示。每个表的最后两列显示算法在大小为 10,000 的输入上的性能，其中数字分别按升序（已排序）和降序（逆序）排列。这些列展示了一些算法的最佳性能和另一些算法的最差性能。它们还表明，对于某些算法，输入的顺序影响很小。

这些数据展示了许多有趣的结果。如预期，O(n²) 排序在大数组上的表现很差。插入排序是这一组中最好的，除非数组已经是逆序。希尔排序对于即使只有 100 个元素的列表也明显优于这些 O(n²) 排序。优化的快速排序对于除 10 个元素以外的所有列表都是总体上最好的算法。即使对于小数组，优化的快速排序也表现良好，因为它在调用插入排序之前执行一次分区步骤。与其他 O(n log n) 排序相比，未优化的堆排序由于类结构的开销而相当慢。当去掉所有这些并将算法实现为直接操作数组时，它仍然比归并排序稍慢。总的来说，优化各种算法对于较大的数组大小会带来明显的改进。

总体而言，基数排序的表现令人惊讶地差。如果代码已调整为使用键值的位移，它可能会大幅改善；但这会严重限制排序可以支持的元素类型的范围。

## 7.9 排序的下界

本书包含许多算法的分析。这些分析通常定义了算法在最坏和平均情况下的上限和下限。对于迄今为止介绍的许多算法，分析很容易。本节考虑一个更困难的任务——对问题的成本而不是算法的分析。问题的上界可以定义为最快已知算法的渐近成本。下界定义了解决该问题的任何算法的最佳可能效率，包括尚未发明的算法。一旦问题的上界和下界相遇，我们就知道没有任何未来的算法可以（渐近地）更高效。

对问题下界的一个简单估计可以通过测量必须读取的输入大小和必须写入的输出大小来获得。任何算法都不能比问题的 I/O 时间更高效。从中我们看到，排序问题无法由任何算法在少于 Ω(n) 时间内解决，因为读取和写入 n 个值需要至少 n 步。或者，任何排序算法都必须至少查看每个输入值以识别输入值是否已按排序顺序排列。因此，基于我们目前对排序算法的了解和输入的大小，我们知道排序问题的下界为 Ω(n)，上界为 O(n log n)。

计算机科学家花费了大量时间设计高效的通用排序算法，但没有人找到一种在最坏或平均情况下快于 O(n log n) 的算法。我们是否应该继续寻找更快的排序算法？
