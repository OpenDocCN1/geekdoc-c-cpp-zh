

使用某种 ADT 的一个应用程序可能会比第二个应用程序更频繁地使用该 ADT 的特定成员函数，或者两个应用程序对各种操作的时序要求可能不同。应用程序需求上的这些差异正是为什么给定的 ADT 可能会有不止一种实现的原因。

**示例 1.5** 用于大型磁盘数据库应用的两种流行实现是哈希（第 9.4 节）和 B+ 树（第 10.5 节）。两者都支持记录的高效插入和删除，并且都支持精确匹配查询。然而，对于精确匹配查询，哈希比 B+ 树更高效。另一方面，B+ 树可以高效地执行范围查询，而哈希对于范围查询则完全低效。因此，如果数据库应用程序将搜索限制为精确匹配查询，则优先选择哈希。另一方面，如果应用程序需要支持范围查询，则优先选择 B+ 树。尽管存在这些性能问题，但这两种实现都解决了同一个问题的不同版本：更新和搜索大量记录的集合。

ADT 的概念可以帮助我们在非计算应用中也聚焦于关键问题。

**示例 1.6** 在操作汽车时，主要活动是转向、加速和制动。在几乎所有乘用车上，你通过转动方向盘来转向，通过踩下油门踏板来加速，通过踩下刹车踏板来制动。汽车的这种设计可以被视为一个 ADT，其操作为“steer”、“accelerate”和“brake”。两辆车可能以截然不同的方式实现这些操作，例如使用不同类型的发动机，或前轮驱动与后轮驱动。然而，大多数驾驶员可以操作许多不同的汽车，因为 ADT 提供了一种统一的操作方法，无需驾驶员了解任何特定发动机或驱动设计的细节。这些差异是有意隐藏的。

ADT 的概念是任何成功的计算机科学家必须理解的一个重要原则的一个实例：通过抽象来管理复杂性。计算机科学的核心主题是复杂性及其处理技术。人类通过为一组对象或概念分配一个标签，然后用该标签代替该集合进行操作来处理复杂性。认知心理学家称这种标签为隐喻。一个特定的标签可能与其他信息或其他标签相关联。这些集合反过来可以被赋予一个标签，形成概念和标签的层次结构。这种标签的层次结构使我们能够专注于重要问题，同时忽略不必要的细节。

**示例 1.7** 我们将标签“硬盘”应用于操纵特定类型存储设备上的数据的硬件集合，并将标签“CPU”应用于控制计算机指令执行的硬件。这些和其他标签被归纳在“计算机”标签之下。由于即使是今天最小的家用计算机也拥有数百万个组件，因此某种形式的抽象对于理解计算机如何运行是必要的。

考虑你如何设计一个复杂的计算机程序，该程序实现并操作一个 ADT。ADT 在程序的一个部分中由特定的数据结构实现。在设计使用 ADT 的程序部分时，你可以以对数据类型操作的术语进行思考，而无需关心数据结构的实现。没有这种简化对复杂程序思考的能力，你就无法理解或实现它。

**示例 1.8** 考虑一个相对简单的磁盘存储数据库系统的设计。通常，在此类程序中，磁盘上的记录是通过缓冲池（参见第 8.3 节）而不是直接访问的。可变长度记录可能会使用内存管理器（参见第 12.3 节）在磁盘文件中找到合适的放置位置。多个索引结构（参见第 10 章）通常用于以各种方式访问记录。因此，我们有一个类链，每个类都有自己的职责和访问权限。来自用户的数据库查询通过搜索索引结构来实现。该索引通过向缓冲池发出请求来请求访问记录。如果记录正在被插入或删除，则此类请求会经过内存管理器，内存管理器反过来与缓冲池交互以获得对磁盘文件的访问权限。这样的程序对于几乎任何人类程序员来说都过于复杂，无法同时记住所有细节。设计和实现此类程序的唯一方法是通过适当的抽象和隐喻的使用。在面向对象编程中，这种抽象是通过使用类来处理的。

数据类型既有逻辑形式也有物理形式。数据类型以 ADT 形式定义的定义是其逻辑形式。数据类型作为数据结构的实现是其物理形式。图 1.1 说明了数据类型逻辑形式与物理形式之间的这种关系。当你实现一个 ADT 时，你处理的是相关数据类型的物理形式。当你在程序的其他地方使用 ADT 时，你关心的是相关数据类型的逻辑形式。本书的某些章节专注于给定数据结构的物理实现。其他章节在更高级别任务的上下文中使用数据结构的逻辑 ADT。

## 1.3 设计模式

在 ADT 之上更高级别的抽象是用于描述程序设计的抽象——即对象和类的交互。经验丰富的软件设计师学习并重用组合软件组件的模式。这些模式后来被称为设计模式。

设计模式体现并概括了对反复出现问题的重要的设计概念。设计模式的主要目标之一是将专家设计师获得的知识快速传递给新程序员。另一个目标是允许程序员之间进行高效的沟通。当你共享与主题相关的技术词汇时，讨论设计问题要容易得多。

权衡是可能的。因此，给定的设计模式可能在其应用上有变化，以匹配给定情况下固有的各种权衡。

本节的其余部分介绍了一些简单的设计模式，这些模式将在本书后面使用。

### 1.3.1 享元

享元设计模式旨在解决以下问题。你有一个包含许多对象的应用程序。其中一些对象在它们包含的信息和它们扮演的角色方面是相同的。但它们必须从各个地方访问，并且在概念上它们确实是不同的对象。由于存在大量相同信息的重复，我们希望利用这个机会通过共享该空间来减少内存成本。一个例子来自表示文档的布局。字母“C”可以合理地由一个描述该字符笔画和边界框的对象来表示。然而，我们不希望在文档中每出现一个“C”时都创建一个单独的“C”对象。解决方案是分配一个共享的“C”对象表示的单一副本。然后，文档中每个需要特定字体、大小和字体的“C”位置都将引用这个单一副本。对特定形式“C”的各种引用实例称为享元。

我们可以用树结构描述页面上的文本布局。树的根代表整个页面。页面有多个子节点，每个列一个。列节点有子节点，每个行一个。而行有子节点，每个字符一个。这些字符的表示是享元。享元包括对共享形状信息的引用，并且可能包含特定于该实例的额外信息。例如，每个“C”的实例将包含对笔画和形状的共享信息的引用，并且还可能包含该字符在页面上的确切位置。

享元在用于存储点对象集合的 PR 四叉树数据结构的实现中使用，描述于第 13.3 节。在 PR 四叉树中，我们再次有一个带叶节点的树。其中许多叶节点表示空区域，因此它们存储的唯一信息是它们为空的事实。这些相同的节点可以使用对享元的单一实例的引用来实现，以获得更好的内存效率。
