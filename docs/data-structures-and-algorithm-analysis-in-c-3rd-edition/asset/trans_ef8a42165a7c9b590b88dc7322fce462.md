
这种方法的一种变体是让 `getblock` 函数再接受一个参数，用于指示信息的“使用模式”。如果模式是 READ，则缓冲区池假定不会对缓冲区内容进行任何修改（因此在缓冲区被复用来存储另一个块时，不需要执行写操作）。如果模式是 WRITE，则缓冲区池假定客户端不会查看缓冲区的内容，因此无需从文件中读取数据。如果模式是 READ AND WRITE，则缓冲区池会从磁盘读取块的现有内容，并在缓冲区被复用时将缓冲区内容写回磁盘。使用“模式”方法可以避免使用 `dirtyblock` 方法。

缓冲区传递 ADT 的一个问题是悬空指针的风险。当缓冲区池使用者在时间 T1 获得某个缓冲区空间的指针时，该指针确实指向当时所需的数据。随着对缓冲区池的进一步请求，任何给定缓冲区中的数据都可能被移除并替换为新数据。如果缓冲区池使用者在稍后的时间 T2 引用 T1 时获得的指针所指向的数据，那么该数据可能已不再有效，因为缓冲区内容在此期间已被替换。因此，指向缓冲区池内存的指针变得“悬空”。为了保证指针不会悬空，如果在两次请求之间发生了对缓冲区池的干预请求，则不应使用该指针。

我们可以通过引入以下概念来解决这个问题：一个用户（或多个用户）获得对某个缓冲区的访问权，然后在使用完毕后释放该缓冲区。为此，我们将添加 `acquireBuffer` 和 `releaseBuffer` 方法。方法 `acquireBuffer` 以块 ID 作为输入，并返回一个指向将用于存储此块的缓冲区的指针。缓冲区池将跟踪当前对该块的活动请求数。方法 `releaseBuffer` 将减少关联块的活跃用户数。与活跃块关联的缓冲区不能被从缓冲区池中刷新出去。如果客户端在不再需要活跃块时忘记释放它们，就会导致问题。如果同时活跃的块总数多于缓冲区池中的缓冲区数量，也会出现问题。然而，缓冲区池在初始化时应始终包含比任何时刻可能活跃的缓冲区数量更多的缓冲区。

到目前为止所介绍的两种 ADT 还有另一个问题：当用户打算完全覆盖某个块的内容，并且不需要读取已在磁盘上的旧内容时。然而，缓冲区池通常无法知道用户是否希望使用旧内容。这在消息传递方法中尤其明显，因为给定的消息可能只覆盖块的一部分。在这种情况下，即使不需要，块也会被读入内存，然后其内容被覆盖。

这种低效可以通过将块的缓冲区分配与实际读取块数据分离开来避免（至少在缓冲区传递版本中如此）。特别是，以下修订后的缓冲区传递 ADT 在 `acquireBuffer` 方法中并不实际读取数据。希望查看旧内容的用户必须发出 `readBlock` 请求以将数据从磁盘读入缓冲区，然后发出 `getDataPointer` 请求以直接访问缓冲区的数据内容。

```
// 缓冲区池中的单个缓冲区
class Buffer {
public:
    // 从磁盘读取关联块（如有必要），并
    // 返回指向数据的指针
    void *readBlock() = 0;

    // 返回指向缓冲区数据数组的指针
    // （不读取磁盘）
    void *getDataPointer() = 0;

    // 将缓冲区内容标记为已更改，以便
    // 刷新块时将其写回磁盘
    void markDirty() = 0;

    // 释放块对该缓冲区的访问。进一步
    // 访问此缓冲区是非法的。
    void releaseBuffer() = 0;
}
```

```
// 缓冲区池
class BufferPool {
public:
    // 构造函数：缓冲区池有 "numbuff" 个缓冲区，每个
    // 包含 "buffsize" 字节的数据。
    BufferPool(int numbuff, int buffsize) = 0;

    // 将一个块关联到缓冲区，返回指向
    // 缓冲区对象的指针
    Buffer *acquireBuffer(int block) = 0;
}
```

同样，可以在 `acquireBuffer` 方法中添加一个模式参数，从而消除对 `readBlock` 和 `markDirty` 方法的需求。

显然，缓冲区传递方法对缓冲区池使用者施加了更多义务。这些义务包括知道块的大小、不破坏缓冲区池的存储空间，以及在块被修改和不再需要时通知缓冲区池。如此多的义务使得这种方法容易出错。一个优点是，在将信息从用户传输到缓冲区时，无需进行额外的复制步骤。如果存储的记录较小，这一点并不重要。如果记录较大（尤其是当记录大小和缓冲区大小相同时，例如实现 B 树时通常如此，见第 10.5 节），那么这种效率问题可能会变得重要。但请注意，内存中的复制时间总是远小于将缓冲区内容写入磁盘所需的时间。对于磁盘 I/O 是程序瓶颈的应用程序，即使在缓冲区池用户和缓冲区之间复制大量信息的时间也可能是微不足道的。缓冲区传递的另一个优点是减少了对于无论如何都将被覆盖的数据的不必要读取操作。

您应该注意到，上述 `BufferPool` 类的实现并未使用模板。相反，空间参数和缓冲区指针被声明为 `void*`。当类使用模板时，这意味着记录类型是任意的，但类知道记录类型是什么。相比之下，对空间使用 `void*` 指针意味着不仅记录类型是任意的，而且缓冲区池甚至不知道用户的记录类型是什么。事实上，给定的缓冲区池可能有多个用户，他们存储多种类型的记录。

在缓冲区池中，用户决定给定记录的存储位置，但对数据传输到后备存储的具体机制没有控制权。这与第 12.3 节中描述的内存管理器形成对比，在内存管理器中，用户将记录传递给管理器，并且对记录的存储位置完全没有控制权。

## 8.4 程序员对文件的视角

C++ 程序员对随机访问文件的逻辑视图是一个单一的字节流。与文件的交互可以被视为一个通信信道，用于发出三种指令之一：从文件中的当前位置读取字节、向文件中的当前位置写入字节，以及移动文件中的当前位置。您通常看不到字节如何存储在扇区、簇等中。从逻辑地址到物理地址的映射由文件系统完成，而扇区级缓冲由磁盘控制器自动完成。

当处理磁盘文件中的记录时，访问顺序对 I/O 时间有很大影响。随机访问过程以与文件中的逻辑顺序无关的顺序处理记录。顺序访问则按照记录在文件中的逻辑出现顺序处理记录。如果磁盘文件的物理布局与其逻辑布局相匹配（正如预期的那样，如果文件是在具有高比例空闲空间的磁盘上创建的），那么顺序处理所需的寻道时间更少。

- `open(char *name, openmode flags)`：打开名为 `name` 的文件进行处理。`flags` 控制各种细节，例如文件是否允许
