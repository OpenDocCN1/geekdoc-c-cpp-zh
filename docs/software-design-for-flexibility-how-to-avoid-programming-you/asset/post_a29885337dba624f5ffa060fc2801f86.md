we will discuss in section 3.1.5. When they fit the domain, they are an excellent strategic choice.

But how do we arrange to build our systems by combining elements of a family of mix-and-match components? We must identify a set of primitive components and a set of combinators that combine components with the same interface as the primitive components. Such sets of combinators are sometimes explicit, but more often implicit, in mathematical notation.

## 2.1.1 Function combinators

The use of functional notation in mathematics is a combinator discipline. A function has a domain, from which its arguments are selected, and a range (codomain) of its possible values. There are combinators that produce new functions as combinations of others. For example, the composition $f \circ g$ of functions $f$ and $g$ is a function that takes arguments in the domain of $g$ and produces values in the codomain of $f$. If two functions have the same domain and codomain, and if arithmetic is defined on their common codomain, then we can define the sum (or product) of the functions as the function that when given an argument in their common domain, is the sum (or product) of the values of the two functions at that argument. Languages that allow first-class procedures provide a mechanism to support this means of combination, but what really matters is a good family of pieces.

Organizing a system around combinators has several advantages. The parts that are made can be arbitrarily matched and matched. Any combination yields a legal program, whose behavior transparently depends only on the behaviors of the parts and the ways that they are combined. The behavior of the part: it is always acceptable to pick up a compound part to use in a new context, without worry about its behavior in that context. Thus programs are easy to write, easy to read, and easy to verify. A program built on combinators is extensible, because introduction of new parts or new combinators does not affect the behavior of existing programs.

We can think of function combinators as implementing wiring diagrams that specify how a function is built by combining its parts.

For example, functional composition represents a box made of two subboxes so that the output of the first feeds the input of the second, as shown in [figure 2.1]. A program that implements this idea is straightforward:

```
(define compose f g)
(lambda args)  (f (apply g args)))
```

![](img/2e72770736573f9ba6300d8cdb1e28c1_44_0.png)

**Figure 2.1** The composition $f \circ g$ of functions $f$ and $g$ is a new function that is defined by this "wiring diagram." The input to $f \circ g$ is given to $g$. The output of $g$ is passed to $f$, and it produces the output of $f \circ g$.

(It gets more exciting if we want to check that the arities match: that the function represented by procedure $f$ takes only one argument, to match the output of $g$. It gets even more fun if $g$ can return multiple values and $f$ must take those arguments. We may also want to check that the arguments passed to the composition are the right number. But these are fine points that we will deal with later.) We can demonstrate composition with a simple example:

```
((compose lambda (x) (list 'foo x)) (lambda (x) (list 'bar x)))
```

It is sometimes nicer to name the procedure that is returned by a combinator. For example, we could write `compose` as

```
(define compose f g)
(define the-composition . args)
(f (apply g args))
```

The name `the-composition` is not defined outside the scope of `compose`, so there is no obvious advantage to this way of writing. We often use anonymous procedures defined by lambda expressions in our programs, as in the first version of `compose`.

With just this combinator we can write some elegant code. Consider the problem of computing the $n$th iterate of a function $f(x)=f^n(x)$. We can write this elegantly as a program:

```
(define ((iterate n) f)
  (if (= n 0)
    identity
    (compose f ((iterate (- n 1)) f))))
```

The result of `(iterate n) f` is a new function of the same type as $f$. It can be used wherever $f$ can be. So `(iterate n)` is itself a combinator. Now we can use this to determine the result of repeatedly squaring a number:

```
((iterate 3) square)
```

Notice the analogy: function composition is like multiplication, so function iteration is like exponentiation. There are many simple combinators that are generally useful in programming. We will present just a few here to get a feeling for the range of possibilities. We can arrange to use two functions in parallel, then combine their results with a specified function (see figure 2.2). This parallel combination is implemented with the procedure

![](img/2e72770736573f9ba6300d8cdb1e28c_46.png)

**Figure 2.2** In parallel-combine the functions $f$ and $g$ take the same number of arguments. The input to the "parallel combination" is passed to both of them. Their outputs are then combined by the function $h$, of two arguments.

```

(parallel-combine (lambda (x y) (list 'foo x y)) (lambda (u v) (list 'bar u v)) (lambda (a b) (a b)))
```

The **parallel-combine** combinator can be useful in organizing a complex process. For example, suppose we have a source of images. We may have one procedure that can estimate the color, another that can give the shape (leaf, root, stalk...). These can be neatly composed with parallel-combine.

## Arity

There are entire families of combinators that we can use in programming that we don't normally think of. Many of these appear in mathematical contexts. For example, tensors are an extension of linear algebra to operators with multiple arguments. But the idea is more general than that: the "tensor combination" of two procedures is just a new procedure that distributes arguments to the two procedures. The need to unbundle a structure, operate on the parts separately, and rebundle the results is ubiquitous in programming. The wiring diagram in figure 2.3 shows spread-combine. It is a generalization of the tensor product in multilinear algebra. In the mathematical tensor product, $f$ and $g$ are linear functions of their inputs, and $h$ is a trace over shared indices; but tensors are the special case that inspired this combinator.

![](img/2e72770736573f9ba6300d8cdb1e28c_47_0.png)

**Figure 2.3** In spread-combine the $n+m$ arguments are split between the functions $f$ and $g$. The first $n$ arguments go to $f$ and the $m$ other arguments go to $g$. The resulting outputs are then combined by the function $h$, of two arguments.

The program to implement spread-combine is a bit more complicated than parallel-combine, because it must distribute the correct arguments to $f$ and $g$. Here is a first draft of that code:

```
(define spread-combine h f g)
(let ((n (get-arity f)))
  (define (the-combination . args)
    (h (apply f (list-head args n))
      (apply g (list-tail args n))))
  the-combination))
```

This code requires a way of determining how many arguments a procedure takes (arity), because it has to pick out the arguments for $f$ and then pass the rest to $g$.

This version of spread-combine is not very good. The most egregious problem is that the-combination takes any number of arguments, so it does not have a well-defined numerical arity, and thus it cannot be passed to another combinator that needs its arity. For example, the result of a spread-combine cannot be passed as the second argument of $f$ to another spread-combine. So, somehow, we have to decorate the-combination with an appropriate arity. Here is a second draft:

```
(define spread-combine h f g)
(let ((n (get-arity f)) (m (get-arity g)))
  (let ((t (+ n m)))
    (define (the-combination . args)
      (h (apply f (list-head args n))
        (apply g (list-tail args n))))
    (restrict-arity the-combination t))))
```

Here, the procedure `the-combination` has its arity specified, so it can be the input to some other combinator that requires an arity. The `restrict-arity` procedure takes a procedure, annotates it so that its arity can be obtained by `get-arity`, and returns the annotated procedure.

This is pretty good, but the best programs are written by paranoid! We want to catch errors as early as possible, before they become hard to locate or cause serious trouble. So let's annotate this code with an assertion in Paranoid Programming Style, to check that we have the right number of arguments to our combination.
