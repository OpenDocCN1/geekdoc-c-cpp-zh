The remaining special path patterns are `and` and `or`, each of which contains a number of subpath patterns. An `and` element must match all of the subpath patterns starting at the current node. An `or` element must match at least one of the subpath patterns starting at the current node.

```lisp
(define (gmatch:compile-elt-lists)
  (gmatch:and map gmatch:compile-path-elts elt-lists))
```

```lisp
(define (gmatch:compile-or elt-lists)
  (gmatch:or map gmatch:compile-path-elts elt-lists))
```

## The procedures `and` and `or` are where the real work happens:

```lisp
(define (gmatch:and matchers)
  (lambda (object dict succeed)
    (if (null? matchers)
        (succeed object dict)
        (let loop ((match matchers) (dict dict))
          ((car matchers) object dict)
          (if (null? (cdr matchers))
              succeed
              (lambda object* dict*
                (loop (cdr matchers) dict*))))))
```

```lisp
(define (gmatch:or matchers)
  (lambda (object dict succeed)
    (let loop ((matches matchers))
      (if (pair? matchers)
          (or ((car matchers) object dict succeed)
              (loop (cdr matchers))))
          #f)))
```

The procedure `compile-var` compiles a pattern variable. It is called from `compile-path` and `compile-target`, and has four mutually exclusive cases to handle variables with or without the optimal name and predicate:

```lisp
(define (gmatch:compile-var var)
  (cond ((match-list? var gmatch:var-type?)
         (gmatch:var-matcher (car var) #f #f))
        ((match-list? var gmatch:var-type?) symbol)
         (gmatch:var-matcher (car var) (cadr var) #f))
        ((match-list? var gmatch:var-type?) symbol?)
         (gmatch:var-matcher (car var) (cadr var) (caddr var)))
        ((match-list? var gmatch:var-type?) symbol?)
         (gmatch:var-matcher (car var) #f (cadr var)))
        else
         (error "Ill-formed variable:" var))))
```

The procedure `var-type` matches the type of a variable. To recognize the four cases of variables, `compile-var` uses a utility procedure `match-list?`, which is true if its first argument is a list and each element of the list satisfies the corresponding predicate.

```lisp
(define match-list? datum)
  (let loop ((preds) (datum))
    (if (pair? preds)
        (and (pair? datum)
            ((car preds) (car datum))
            (loop (cdr preds) (cdr datum)))
        true))
```

The procedure `var-matcher` is the matcher for variables, now that we have decoded their syntax.

```lisp
(define gmatch:var-matcher var-type restriction)
  (define match-var object succeed)
  (and (not restriction)
      (restriction object)
      (if var-name
          (let ((dict* (gmatch:bind var-type var-name dict)))
            (and dict* (succeed object)))
          (succeed object))))
```

`bind` adds a binding for var with object, returning a new dictionary. If the dictionary already has such a binding and its value is different from object, it returns #f to indicate match failure. With this we have finished the graph matcher.

## 4.6 Summary

Patterns are fun, but they are also a very useful way to organize parts of a system. In this chapter we have seen how to build a term-rewriting system. A rule-based term-rewriting system makes it easy to write programs that replace parts of an expression with "equivalent" parts, terminating when no more rules are applicable. Such systems are important components of larger systems that do symbolic manipulation. Algebraic simplification is one application, but compilers do huge amounts of this kind of manipulation to compute optimizations and sometimes generate code. We also saw a flexible way to construct a pattern matcher by "compiling" into a combination of simple matchers that all have the same interface. This makes it easy to add new features and to make such a system very efficient. When we add segment variables which match an unspecified number of elements, we find that we have to implement backtracking because there may be multiple possible matches to any particular data if the pattern has more than one segment variable. This complicates matters significantly. Besides the intrinsic complexity of backtracking, the backtracking in the pattern matcher must be interfaced to the backtracking system that uses the patterns. We will examine more general ways of dealing with backtracking in section 5.4 and investigate even more powerful backtracking strategies in section 7.5.

If we model partially specified data as patterns with holes (represented by pattern variables), we find that we need to match patterns against each other to collect constraints. We explored unification: the process of merging partial information structures of this kind. This is essentially a way of setting up and solving symbolic equations for the missing parts of the data. Unification is very powerful, and we showed how to make a simple type-inference engine using unification in this way.

We found that the ideas of pattern matching can be extended to operate on general graphs rather than just hierarchical expressions. This made it easy to work with complex graphs as chess boards, where we used patterns to specify legal moves. Patterns and pattern matching can be a way to express computational thought, and on some problems it can be more revealing than other programming methods. But be careful: pattern matching is not the answer to all the world's problems, so let's become addicted to it.
