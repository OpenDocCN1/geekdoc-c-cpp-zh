# The Fix

Port forwarding is clunky, many consumers have trouble setting it up correctly, and it’s often a support hassle for developers and publishers. Luckily, another solution exists, and was first described in [Kegel99] by Dan Kegel, as used in the game *Battle-Zone™* published by Activision®.

The core of the problem is that each NAT router is lacking an entry in its session state table for the other peer with whom the internal node wishes to communicate. If we could somehow fool the NAT routers to add such an entry, traffic would flow correctly, and the game could go on!

Remember that when a peer sends a packet out through the NAT router, a tuple is added to the session state table, containing the internal and the external addresses as well as the remote address. As a first approximation, if we assume that a NAT router will preserve the source port of the internal node, assuming that port is not already in use by some other session, we could send packets to the remote node using its public NAT address and the known port.
