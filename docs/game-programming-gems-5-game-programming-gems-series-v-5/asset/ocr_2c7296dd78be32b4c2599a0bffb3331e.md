When a service is reverted to a previous version, the shadow service loads the previous stable version of that service and takes control of its responsibilities. The shadow service will never revert to a previously flagged unstable version or a version marked unusable. Instead, the shadow service will make sure to always run a revision known to be stable.

# Live Updates

With the previously mentioned methods in place, we are now able to ingeniously handle live updates. We push the updates to the revision tables, have the service servers launch the new services in standby, switch control from the old services to the new services, and then shut down the old services to clear up resources.

# Keeping Persistent

To resume functionality in the event of a crash, data must be stored persistently, and in more than just a statistical database. We need valid game state data in order to continue from where we left off. Currently, some online games write the entire game state to disk about every 20 minutes. If a crash were to occur, that saved game state would be reloaded. The problem with this is, since we do not know when a crash will occur, the state may be up to 20 minutes old.

# Backing up Game States

The solution to this is shared memory. Anything loaded into shared memory stays around until you explicitly destroy it, so it is safe for each service to store its game state data in this memory block.
