The calculation of mid ensures that **first** ≤ mid ≤ **last**. This particular:

- If mid is the location of the sought element (checked in the first **if** statement), the loop terminates, and returns the correct position.
- The second **if** statement ensures that either **last** decreases or **first** increases each time through the loop. If the loop does not terminate for other reasons, **eventually first** will be larger than last, and the loop will terminate. If the loop terminates for this, the function returns –1. This is the correct behavior.
- The second **if** statement excludes the irrelevant elements from further search. The number of elements remaining to consider is effectively cut in half.

The implementation of the binary search algorithm is more complicated than the simpler linear search algorithm. Ordinary simpler is better, but for algorithms that process data structures that potentially hold large amounts of data, more complex algorithms using clever tricks that exploit the structure of the data (as binary search does) often outperform simpler, easier-to-code algorithms.

For a comparison of linear vs. binary search, suppose we want to locate an element in a sorted vector. The vector is ordered for binary search, but it can be helpful for linear search as well. The revised linear search is:

```cpp
// This version requires vector a to be sorted in
// ascending order.
int linear_search(const vector<int>& a, int seek) {
    int n = a.size();
    for (int i = 0; i < n && a[i] <= seek; i++) {
        if (a[i] == seek)
            return i; // Return position immediately
        return -1; // Element not found
}
```

Notice that, in the original version of linear search, the search will terminate early when it encounters an element larger than the sought element. Since the vector is sorted, there is no need to continue the search once you have been seeing elements larger than your value: seek cannot appear after a larger element in a sorted vector.

Suppose to search in elements. In the case—looking for an element larger than any currently in the vector—linear search takes n iterations. In the case of an element smaller than any other elements—binary search returns immediately without considering others. The number of iterations thus ranges from i to n, and on average linear search requires comparisons before the loop finishes and returns.

Now consider binary search of a vector that n elements. After each comparison the size of the vector left to consider is half-one. If the sought element is not found on the first probe, the number of remaining elements to consider is half-one of n. After the next iteration through the loop, the search drops to half-one of n. This process of searching the space in half continues each time until the process locates the sought element or runs out of elements to consider. The problem of determining how many times a set of things can be divided in half until only one remains can be solved with a base-2 logarithm. For binary search, the worst case scenario of not finding the sought element requires the loop to make log2 n iterations.

How does this analysis help us determine which search is better? The quality of an algorithm is judged by two key characteristics:

- How much time (processor cycles) does it take to run?
- How much space (memory) does it take to run?

In our situation, both search algorithms process the sequence with only a few local variables, so for large sequences they both require essentially the same space. The difference here is speed. Binary search performs more elaborate calculations each time the loop, and each operation takes time, so perhaps binary search is slower (fewer operations through the loop), but perhaps executes many more times than the loop in binary search, so it is slower.

We can deduce the faster algorithm in two ways: empirically and analytically. An empirical test is an experiment; we implement both and measure their execution time. The analytical approach analyzes the source code to determine how many operations the computer's processor must perform to run the loop on a problem of a particular size.

Listing 12.5 (searchcompare.cpp) measures the running times of the two kinds of searches to compare the two algorithms empirically.

## Listing 12.5: searchcompare.cpp

```cpp
#include <iostream>
#include <algorithm>
#include <vector>
#include <ctime>

using namespace std;

double time_execution(int (*search)(const vector<int>&, int), const vector<int>& v, int trials) {
    int n = v.size();
    double elapsed = 0.0;
    for (int iters = 0; iters < trials; iters++) {
        clock_t start_time = clock();
        for (int i = 0; i < n; i++) {
            search(v, i);
        }
        clock_t end_time = clock();
        elapsed += static_cast<double>(end_time - start_time) / CLOCKS_PER_SEC;
    }
    return elapsed / trials;
}

int main() {
    cout << "----------------------" << endl;
    cout << "Vector       Binary" << endl;
    cout << "Search         Search" << endl;
    cout << "----------------------" << endl;

    for (int size = 0; size < 5000; size += 50) {
        vector<int> list(size);
        for (int i = 0; i < size; i++) {
            list[i] = i;
        }

        cout << setw(7) << size;
        // Search for all elements in list linear search
        // Compute running time over 5 runs
        cout << fixed << setprecision(3) << setw(12)
             << time_execution(linear_search, list, 5)
             << " sec" << endl;

        // Search for all elements in list binary search
        // Compute running time over 25 runs
        cout << fixed << setprecision(3) << setw(12)
             << time_execution(binary_search, list, 25)
             << " sec" << endl;
    }
    return 0;
}
```
