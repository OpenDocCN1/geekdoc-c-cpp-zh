
## 19.4. CATCHING MULTIPLE EXCEPTIONS

```cpp
throw FileNotFoundException(filename);

int main() {
  try {
    vector<int> numbers = load_vector("values.data");
    for (int value : numbers) {
      cout << value << ' ';
    }
    cout << endl;
  } catch (exception& e) {
    cout << e.what() << endl;
  }
}
```

The text file containing the integers to load into the vector has a specific format. The first integer read from the file is not a data element; instead, it specifies the number of integers that follow. This gives us two options for creating and populating the vector:

- 1. Create the vector with sufficient size up front and then use a loop to place individual elements in their proper places.
- 2. Create an empty vector and then use a loop to push_back the individual elements.

Option 1 is more efficient than Option 2. Successive calls to vector<int>::push_back must reallocate and copy elements every time. Option 2 is safer than Option 1 because the number of elements specified at the start may not agree with the actual number of data elements in the file. If the specified number is too small, the function will attempt to overrun the bounds of the vector.

Listing 19.7 (filreadmultitext1.cpp) opts for efficiency at the expense of safety. This means that on a correctly created file. If the file does not exist, load_vector will throw our FileNotFoundException custom exception:

#include <iostream>
#include <fstream>
#include <vector>
#include <string>

using namespace std;

// Exception object to be thrown when a client attempts to
// open a text file with a name that does correspond to a
// file in the current working directory.
class FileNotFoundException : public exception {
    string message; // Identifies the exception and filename
public:
    // Constructor establishes the exception's message
    FileNotFoundException(const string& fname)
        : message(fname + "\ not found\n") {}

    // Reveal message to clients
    const char *what() const override {
        return message.c_str();
    }
};

// Creates and returns a vector of integers from data stored
// in a text file.
// filename: the name of the text file containing the data
// Returns a vector containing the data, if possible
vector<int> load_vector(const string& filename) {
    ifstream fin(filename); // Open the text file for reading
    if (fin.good()) { // Did the open file successfully?
        int n;
        fin >> n; // Size of data set
        vector<int> result(n); // Allocate space for the vector
        int value, i = 0;
        while (fin >> value)
            result.push_back(value); // Append it to the vector
        fin.close(); // Close the file
        return result;
    } else // Could not open the file
        throw FileNotFoundException(filename);
    }
}

int main() {
    try {
        vector<int> numbers = load_vector("values.data");
        for (int value : numbers)
            cout << value << endl;
    } catch (out_of_range& e) {
        cout << "Error: bounds exceeded" << endl;
    } catch (FileNotFoundException& e) {
        cout << e.what() << endl;
    }
}

## 19.5 EXCEPTION MECHANICS

An exception handler within catch block may take a few steps to handle the exception and rethrow the exception or a completely different exception.

```cpp
Listing 19.9: retrow.cpp
#include <iostream>
#include <fstream>
#include <vector>

using namespace std;

void filter(vector<int>& v, int i) {
  v.at(i)++;
}

void compute(vector<int>& a) {
  for (int i = 0; i < 6; i++) {
    try {
      filter(a, i);
    } catch (out_of_range& ex) {
      cout << "********************" << endl;
      cout << "* Loop prematurely" << endl;
      cout << "* when i = " << i << endl;
      cout << "********************" << endl;
      throw ex;
    }
  }
}

int main() {
  vector<int> list { 10, 20, 30, 40, 50 };
  try {
    compute(list);
  } catch (exception& e) {
    cout << "Caught an exception: " << e.what() << endl;
  }
  cout << "Program finished" << endl;
}
```

Listing 19.9 (retrow.cpp) produces the following output:

```
********************
* Loop terminated prematurely
* when i = 5
********************
Caught an exception: invalid vector subscript
Program finished
```

Note that in Listing 19.9 (retrow.cpp) the compute function does not create a new exception object; simply rethrows the same exception that it caught. This concept of intermediate exception handlers is important because a function invocation has complete knowledge of its local context such as the local variables. While an intermediate function (or method) in the call chain has access to information that may be unavailable to all other functions (methods) the catch block in the compute function of Listing 19.9 (retrow.cpp) involves only local variables. The catch block within the main function cannot know what caused compute's failure since i is local to compute. Some general guidelines include:

- Handle exceptions (or up call) as possible to the code that throws the exception.
- Use local information where applicable to correct as much of the problem as possible within that local context:
- Local information which may be important for recovering from the exceptional situation is available; this local information is unavailable to functions or methods up the call chain.
- The lower-level functions/methods that promote exception may be called by many different higher-level functions/methods. If the lower-level functions/methods are responsible for their exception handling, then the higher-level functions/methods may dispense with exception handling making the lower-level methods most robust of use.
- The lower-level functions handle many different kinds of exceptions, do local clean up based on the type of exception, and then draw a type of exception to the higher-level methods. The higher-level method may just need to know there was a problem needing to know exactly what the problem was. For example, in Listing 19.9 (retrow.cpp), the compute function would throw a ComputeException whenever filter throws its out_of_range instead of passing up the call chain the out_of_range object.

If recovery is not possible or desired at the lower levels of the call chain, rethrow the exception so an exception handler up can take steps to recover from the problem in a manner that makes sense in its context.

When a section of code throws an exception, the catch blocks within the exception handler are checked in the order they appear in the++ source code. The first catch that matches the type of the exception is the one executed. When an exception is caught, its type is compared to out_of_range. If it matches, the out_of_range catch block is executed. If not, the exception's type is compared to FormatException. The FormatException catch block is executed in the case of a match. If neither of the two types matches, the catch-all is executed.

When inheritance is involved, the situation becomes more interesting. The comparison performed in each catch tests for assignment compatibility. A reference or pointer to an instance of a derived class can be assigned to a variable to be a pointer to a base class. This upcasting operation is always legal because there is a relationship between a derived class and its base class. This means an exception of type out_of_range is assignable with both out_of_range variables and exception variables. The catch blocks are checked in the order they appear in the source code, the following code would have a problem:

```cpp
try {
    // Execute some code that can throw
    // out_of_range exception
}
catch (exception& e) {
    // Do something here
}
catch (out_of_range& e) {
    // Error, this can never be reached
    // Do something else here
}
```

The out_of_range catch block will never execute unless an out_of_range object is an exception instance also. For this reason it is for a more specific type to follow a more general type in a sequence.
