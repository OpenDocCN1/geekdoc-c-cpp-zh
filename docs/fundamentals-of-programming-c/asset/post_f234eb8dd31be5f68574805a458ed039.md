
# 15.4. SEPARATING METHOD DECLARATIONS AND DEFINITIONS

```cpp
Point(double x, double y): x(x), y(y)
double get_x() const { return x; }
double get_y() const { return y; }
void set_x(double x) { x = x; }
void set_y(double y) { y = y; }
```

could be split up into the declaration:

```cpp
class Point {
    double x;
    double y;
public:
    Point(double x, double y); // No constructor implementation
    double get_x() const; // and no method
    double get_y() const; // implementations
    void set_x(double x);
    void set_y(double y);
}
```

and method implementations:

```cpp
// constructor
Point::Point(double x, double y) : x(x), y(y) {}

// Get the x value
double Point::get_x() const {
    return x;
}

// Get the y value
double Point::get_y() const {
    return y;
}

// Set the x value
void Point::set_x(double x) {
    x = x;
}

// Set the y value
void Point::set_y(double y) {
    y = y;
}
```

The class name prefix as Point:: is necessary not only so a method definition as get_x can be distinguished from a global function, but also to distinguish it from a different class that contains a method with the same name and parameters. A method signature for it is just like a global function, except a method signature includes the class name as well. Each of the following represent distinct signatures:

- get_x() is the signature for a global function named get_x that accepts no parameters.
- Point::get_x() is the signature for a method of the Point class named get_x that accepts no parameters.
- LinearEquation::get_x() is the signature for a method of the LinearEquation class named get_x that accepts no parameters.

Recall from Section 10.3 the return type is not part of a function's signature. Same is true for methods. Many C++ programs avoid the inline style of class declarations and use the class declaration and method definitions for several: If the class is meant to be used in multiple programs, the compiler must recompile each time the header is included by some source file. When the method declarations and definitions are separate, the compiler can compile the code once, and the linker can combine this code with the client code that it uses. Client programs can look at the contents of header files. If method definitions are inline, client programmers can see exactly how the method works. This can be a disadvantage; a client program may make assumptions about how fast a method executes or the particular order in which method processes data. These assumptions can influence how the class changes implementation, the client's previous assumptions may be violated. An improvement in graphics processing may allow animation to run too quickly. For maximum flexibility, client programs should not be able to see the details of implementation because they cannot form such assumptions. Client programs need to know what the method does, not how it accomplishes it.

1. Separate the method declarations from their definitions. Put the class declaration in the header and the method definitions in a .cpp file.
2. Compile the .cpp file into an object file.
3. Provide the client with the .h file and the object file but not the source file.
4. The client code can now be compiled by including the .h file and linking with the object file, but the client has no access to the source code of methods.

Some programmers find the inline style difficult because it provides too much. It complicates what objects of the class are supposed to do. Despite the disadvantages mentioned above, inline methods are sometimes appropriate. For simple classes defined in the same file, the inline style is handy. Listing 15.3 (point.cpp) shows.

the Point class is very simple, and the constructor and methods are obvious. The inline structure makes more sense in this situation. Listing 15.4 (trafficlight.h) contains the interface for a class to create objects that simulate traffic signals.

# Listing 15.4: trafficlight.h

```cpp
class TrafficLight {
public:
    // Constants available to clients
    enum SignalColor { Red, Green, Yellow };
private:
    SignalColor color; // The light's current color: Red, Green, or Yellow
public:
    TrafficLight(SignalColor initial_color);
    void change();
    SignalColor get_color() const;
};
```

 the TrafficLight class defines a public enumerated type (SignalColor) that clients may use. Because the type is defined inside the class, clients must use the fully-qualified name TrafficLight::SignalColor when declaring variables or parameters of the type. The traffic signal implementation code in Listing 15.5 (trafficlight.cpp) defines the TrafficLight methods.

# Listing 15.5: trafficlight.cpp

```cpp
#include "trafficlight.h"

// Ensures a traffic light object is in the state of
// red, green, or yellow. A rogue value makes the traffic light
TrafficLight::TrafficLight(TrafficLight::SignalColor initial_color) {
    switch (initial_color) {
        case Red:
        case Green:
        case Yellow:
            color = initial_color;
            break;
        default:
            color = Red; // Red by default, just in case
    }
}

// Ensures the traffic light's signal sequence
void TrafficLight::change() {
    // Red --> green, green --> yellow, yellow --> red
    // Treat enum as int, compute successor color, then
    // convert back to enum type
    color = static_cast<SignalColor>((color + 1) % 3);
}

// Returns the light's current color so a client
// act accordingly
TrafficLight::SignalColor TrafficLight::get_color() const {
    return color;
}
```

The code with Listing 15.5 (trafficlight.cpp) must #include the trafficlight.h header so the compiler is expose to the Trafficlight declaration; otherwise when compiling trafficlight.cpp the compiler would not know if the method implementations fairly agreed. If the definition of Trafficlight::change in trafficlight.cpp specified parameters but its declaration in trafficlight.h did not, that would be a problem. Furthermore, without including trafficlight.h, the type SignalColor would be an undefined type within trafficlight.
