# 15.4. SEPARATING METHOD DECLARATIONS AND DEFINITIONS

+   * Point :get_x() is the signature for a method of the Point class named get_x() that accepts no parameters.

+   * LinearEquation :get_x() is the signature for a method of the LinearEquation class get_x() that accepts no parameters.

Recall from Section 10.3 the return type is not part of a function's signature. Same is true for methods.

Many C++ programs avoid the inline style of class declarations and use the separate class declaration and method definitions for several:

+   * If the class is meant to be used in multiple programs, the compiler must recompile the methods each time the header is #included by some source file. When the method declarations and definitions are separate, the compiler can compile the code for the definitions once, and the linker can combine this code with the client code that it uses.

+   * Client programs can look at the contents of header files. If method definitions are inline, client programmers can see exactly how the method works. This can be a disadvantage; a client program may make assumptions about how fast a method to execute or the particular order in which method processes data in a vector. These assumptions can influence how the client calls the method. If the class changes the implementation of the method, the client's previous assumptions may be violated. Certain ordering of the data before the change resulted in faster processing may now be slower. An improvement in a graphics processing algorithm may allow an animation to run too quickly when the method is rewritten. For designer's maximum flexibility, client programs should not be able to see the details of a method's implementation because they cannot form such assumptions.

Client programs need to know what the method does, not how it accomplishes it.

+   1. Separate the method declarations from their definitions. Put the class declaration in the header and the method definitions in a .cpp file.
2. Compile the .cpp file into an object file.
3. Provide the client with the .h file and the object file but not the source file containing the method definitions.
4. The client code can now be compiled by including the .h file and linking with the object file, but the client has no access to the source code of the methods.

+   * Some programmers find the inline style difficult because it provides too much. It complicates determining what objects of the class are supposed to do how the how is sprinkled throughout the class declaration.

Despite the disadvantages mentioned above, inline methods are sometimes appropriate. For simple classes defined in the same file that they use, the inline style is handy, Listing 15.3 (point.cpp) shows.
