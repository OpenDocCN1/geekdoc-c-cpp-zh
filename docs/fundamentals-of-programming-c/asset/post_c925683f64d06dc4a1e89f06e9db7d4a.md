
## 4.2. MIXED TYPE EXPRESSIONS

The second line assigns 1 to i. Truncation loses the 0.6 fractional part (see Section 4.1). Note that proper rounding is not done. The Visual C++ compiler will warn us of a potential problem:

> warning C2244: ': converting 'double' to 'int', possible loss of data

This reminds us that some information might be lost in the assignment. While the compiler and linker will generate an unexpected program when you are present, you should scrutinize all warnings. This is particularly useful, since it is for errors during the translation of floating-point numbers to integer calculations.

Converting from a wider-type value to a narrower type (like double to int) is narrowing. If we know the value to assign is within the range of int, and the value has no fractional parts or its conversion would do no harm, the assignment is safe. To perform this without warning from the compiler, we use a procedure called cast, also called type-cast. The cast forces the compiler to accept the assignment without issuing a warning. The following statement convinces the compiler to accept the double-to-int assignment without a warning:

```
i = static_cast<int>(d);
```

The used static_cast performs the narrowing conversion and silences the compiler warning. The item to convert (in this case the variable d) is placed in the parentheses, and the desired type (in this case int) appears in the angle brackets.

```
i = static_cast<int>(d);
```

does not change the type of the variable d is declared to be an int and must remain an int. The statement makes a copy of d's value in a temporary memory location, converting it to its integer representation during the process.

We can also cast literal values and expressions:

```
i = static_cast<int>(1.6)
i = static_cast<int>(x + 2.1);
```

The widening is always safe, so a type cast is not required. Narrowing is a potentially dangerous operation, and using an explicit cast does not remove the danger—it simplifies the compiler. For example, consider Listing 4.4 (badnarrow.cpp).

Listing 4.4: badnarrow.cpp
#include <iostream>

namespace std;

int main() {
    double d = 2200000000.0;
    int i = d;
    cout << "d = " << d << " = " << i << endl;
}
```

The Visual C++ compiler issues a warning about the possible loss of precision when assigning d to i. Silencing the warning of a narrower type in this case is also a bad idea; the program's output indicates that the warning should be heeded:

```
d = 2.2e+09, i = -2147483648
```

The values of i and d are not even close, nor can they be because it is impossible to represent a value of 2,200,000,000 as an int on a system that uses 32-bit integers. When assigning a value of a wider type to a variable of a narrower type, the programmer must assume the responsibility to ensure that the actual value is narrowed within the range of the narrower type. The compiler cannot ensure the safety of the assignment.

Casts could be used sparsely and with great care because a cast creates a spot in the program that is immune to the compiler's type checking. A careless assignment can produce a garbage result introducing an error into the program.

When we perform mixed arithmetic—such as adding an int to a double—the compiler produces machine code that converts the int value to a temporary memory location and transforms it into double equivalent. It performs double-precision floating-point arithmetic to compute the result.

Integer arithmetic occurs when both operands are ints. 1/3 evaluates to 0, 1.0/3, and 1.0/3 all evaluate to 0.33333.

Since double is wider than int, we say that double dominates int. In a mixed arithmetic expression, the less dominant type is coerced into the more dominant type in order to perform the arithmetic operation.

Section 38 introduces enumerated types. The first value in the enumeration is 0, the second value is 1, etc. The following code demonstrates the relationship between enumerated types and integers:

```
enum Color { Red, Orange, Yellow, Green, Blue, Violet };
cout << Green << " Green" << endl;
```

The output of this code fragment is

```
1
```

C++ allows a programmer to assign an enum type to an integer variable; for example, the following statement is legal:

Here, the variable num assumes the value 1. A programmer, however, may not directly assign an integer value to a variable declared of an enum type; for example, the following statement:

```
Color col = 1;
```

is illegal. Sometimes it is convenient to convert an integer to an enumerated type, and a type cast enables the assignment:

```
enum Color { Red, Orange, Yellow, Green, Blue, Violet };
Color myColor = static_cast<Color>(2);
```

Since the compiler encodes enumerated values with the integers 0,1,2... in the order the values are specified in the enumeration list, the statement above assigns the value Yellow to the variable myColor. Casting, of course, can be dangerous, consider:

```
Color badColor = static_cast<Color>(45);
```

This statement assigns a meaningless value to the variable badColor, and the cast renders the compiler powerless to help.

Even though enumerated types are encoded as integers, programmers may not perform arithmetic on enumerated types without involving casts. Such opportunities would be very rare; if you need to perform arithmetic on a variable, it most likely should be a numerical type, not an enumerated type.

## 4.3. OPERATOR PRECEDENCE AND ASSOCIATIVITY

When different operators are used in the same expression, the normal rules of arithmetic apply. All C++ operators have a precedence and associativity:

- Precedence—when an expression contains two different kinds of operators, which should be applied first?
- Associativity—when an expression contains two operators with the same precedence, which should be applied first?

To see how precedence works, consider the expression

```
2 + 3 * 4
```

Should it be interpreted

```
(2 + 3) * 4
```

(that is, 20), or rather

```
2 + (3 * 4)
```

(that is, 14) the correct interpretation? As normal arithmetic, in C++, multiplication has precedence over addition. The expression

```
(2 + 3) * 4
```

evaluates to 20. Multiple sets of parentheses can be arranged and nested in any ways that are acceptable in standard arithmetic. To see associativity works, consider the expression

```
2 - 3 - 4
```

The two operators are the same, so they have equal precedence. Should the first subtraction be applied before the second, as in

```
(2 - 3) - 4
```

(that is, -5), or rather

```
2 - (3 - 4)
```

(that is, 3) the correct interpretation? The former (-5) is the correct interpretation. We say that the subtraction operator is left associative, and the evaluation is left to right. This interpretation agrees with standard arithmetic rules. All binary operators accept left associative except for assignment; it is right associative. To see why associativity is an issue, consider the statement

```
w = x = y;
```

This is legal C++ and is called chained assignment. Assignment can be used as both a statement and an expression. The statement

```
x = 2;
```

assigns the value 2 to the variable x. The expression

```
x = 2
```

assigns the value 2 to the variable x and evaluates to the value that was assigned; that is

```
w = (x = (y = z));
```

which behaves follows:

- The expression y = z is evaluated first. z's value is assigned to y, and the expression y = z is z's value.
The expression x = (y = z) is evaluated. The value of y is z, that is, z is assigned to x. The overall value of the expression x = y = z is thus the value of z. Now the values of x, y, and z are all equal (to z).
The expression w = (x = y = z) is evaluated. The value of the expression x = y = z is equal to z, so z's value is assigned to w. The overall value of the expression w = y = z is equal to z, and the variables w, x, y, and z are all equal (to z).
