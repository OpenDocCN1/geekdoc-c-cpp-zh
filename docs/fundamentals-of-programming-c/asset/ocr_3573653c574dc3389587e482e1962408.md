Similarly, an automobile presents an accelerator pedal to its driver. The user knows that pushing the pedals makes the car go faster. That the pedal is connected to the fuel injection system (and possibly other systems, like cruise control) by a wire, cable, or other type of linkage is of concern only to the automotive designer or mechanic. Most drivers prefer to be oblivious to the under-hood details.

Changing the interface of a class can disturb code that has been written to use objects of that class. For example, what if the maintainers of the Rational class decide that Rational client cannot afford the numerator or denominator values. The set_enumerator and set_denominator, disappear. Unfortunately, both of these methods are public and part of Rational's interface to client. Removing them private, altering the types of parameters or any other changes to the interface would render existing client code unusable. Client code that use set_enumerator according to its original interface will no longer be correct. We say the change in Rational's interface breaks the client.

Client authors have no flexibility to alter the interface of a class once the class has been released for clients to use. On the other hand, altering the private information in a class will not break existing client code that uses it. When the private parts of a class change, clients only require; client programmers do not need to modify their source code. A class, therefore, becomes less resilient to change as many of its components are exposed to clients. To maximize the ability to make improvements to the class in the future, have as much information as possible from clients.

+   **Reducing errors.** Client code cannot misuse the parts of a class that are private since the client cannot see the private parts of a class. Properly restricting client access can make it impossible for a client to put objects into an undefined state. For example, if a client can create an object into an illegal state via the class interface, then the design and/or implementation of the class is faulty. For example, if a client can somehow make a Rational object's denominator zero, one of the methods or a constructor must contain a logic error. Clients should never be able to place an object into an illegal state.

+   **Hiding complexity.** Each class can provide a great deal of functionality. Even though a class may provide a simple interface to clients, the services may require a significant amount of code to accomplish their tasks. One of the challenges of software development is dealing with the overwhelming complexity of the tasks.

It is difficult, not impossible, for a programmer to be aware of all the details of a large system. Classes with well-defined interfaces and hidden implementations provide a means to reduce this complexity. Since private components of a class are hidden, their details cannot contribute to the complexity the client programmer manages.
