When you use this approach, you can simply define the data by typing in elements and their attributes, making up their names as you go. For example, the following code defines a Manager object containing two Employee objects:

```
<Manager Name="Mindy" LastName="Most" Extension="0001" Title="Manager of OR">
  <Employee FirstName="Alice" LastName="Able" Extension="1111"/>
  <Employee FirstName="Ben" LastName="Better" Extension="2222"/>
</Manager>
```

OrgChartXml

Neither the XML code nor code-behind needs include definitions for the Manager and Employee classes. In fact, WPF doesn't actually create Manager and Employee. Instead, it creates XmlElement with Name properties set to Manager and Employee.

> TERRIBLE TYPES
Be careful when you type XML data. If you misspell an element's name, WPF merely creates a new object with the misspelled name. For example, if you accidentally create an Employee element, WPF will create an XmlElement named Employee. Later, when a HierarchicalDataTemplate searches for Employee objects (described next), it will miss this one.

To use this XML data, you need to wrap it in an XmlDataProvider that you can bind to a TreeView. The XmlDataProvider should contain an x:XData that holds the actual data.

```
<XmlDataProvider x:Key="regions" XPath="Regions">
<x:XData>
  <Regions xmlns="">
      <Region RegionName="East">
      </Region>
      <Region RegionName="Central">
      ...
    </Regions>
  </x:XData>
</XmlDataProvider>
```

OrgTreeXml

The XmlDataProvider's XPath property defines the XPath within the data that should be used as the root of the provider's source. Usually XPath is set to the root element of the XML data, which sits inside the XData element. This element is Regions.

If you wanted to use only some of the data, however, you could change XPath. For example, value Regions/Region[2] would make the provider start gathering data at the second Region element inside the Regions element.
