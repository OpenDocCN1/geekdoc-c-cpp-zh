
Even that might work (you could put the properties in the Control class and let every other class inherit them), but there are lots of other properties that you might need to handle similarly. For example, the DockPanel control needs to know how to dock its children; the Canvas control needs to know Top, Left, and other position properties for its children; and the Toolbar needs to know what OverflowMode to use for the items contains.

Adding all of these properties to the Control class would not clutter the class, but it would also not give you a general solution. If you create a new control that needs to know something about other controls (e.g., you make a new container class that needs to know how to arrange its children), you would need to rebuild the Control base class to accommodate the new control. I doubt that Microsoft is likely to reconcile the WPF libraries and release a special build to add your property.

> OBJECT-ORIENTED OBJECTION
Adding all of these properties to the Control class would also mess up the classes' encapsulation. It would make the Control class know a lot about other classes when it really shouldn't. Object-oriented purists would say that disqualifies this approach from the start.

Instead, WPF takes a different approach, which allows a control to provide an attached property for use by other controls. For example, the Grid control actually implements the Grid.Row and Grid.Column attached properties, and other controls can use them.

The syntax for an attached property is the name of the property provider, followed by a dot, followed by the name of the property. For example, the Grid control's Row property is called Grid.Row.

> PROPERTIES WITHOUT RESTRICTIONS
The control providing the attached property does not check to make that the property makes sense in context. For example, you can give a TextBox control a Grid.Row even if it is not contained in a Grid. In that case, the property is simply ignored.

Unfortunately, the syntax for an attached property is very similar to the syntax for a property element. For instance, the AttachedProperties example shown in Figure 9-5 uses the following XAML code. This code contains several attached properties and property elements.

```
      <GradientStop Color="Yellow" Offset="0"/>
      <GradientStop Color="Red" Offset="1"/>
    </LinearGradientBrush>
  </Grid.Background>
  <Grid.RowDefinitions>
</Grid>
```

# Pens and Brushes

Pens and brushes determine some of the most visually obvious pieces of a graphical application — its colors.

In graphical terms, a *pen* determines the color and style of a linear feature such as a line or the edge of a circle. A *brush* determines how an area is filled. For example, the ellipse drawn in [Figure 10-1](#figure-10-1) is filled with a red brush and outlined with a thick, dashed, purple pen.

This chapter describes pen and brush properties and tells how to set them in XAML code. It explains the different kinds of pens and brushes and the properties that determine their appearance.

![](img/c9b2d394f4fc2f7e276f6a0a6fa9c2f6_202_0.png)

# PENS

A *pen* defines the color and geometry of a linear feature such as a line, a curve defined by a *Path* control, or the edges of an ellipse rectangle.

Interestingly, some colors that you might think would be determined by a pen are actually determined by a brush. In particular, text is rendered by filling the shapes with a brush rather than drawing. This is a bit counterintuitive if you think of drawing by hand, which you usually use a pen.

A pen has several different properties — all beginning with the word *stroke* — that determine its color and geometry.

# A CLOSER LOOK

Many of the stroke properties do not make a huge difference unless the linear feature you are drawing is thick. For example, `StrokeDashCap` determines whether the dashes are square, rounded, or triangular. If a line is only 1 pixel wide, you won't be able to tell the difference.

Remember, that can draw objects that are scaled, so if your program allows it, the user zoom on linear features until these properties make a big difference. The MagnifiedLines example shown in Figure 10-2 draws the same line at five different scales. In the thickest lines you can tell that the dash caps are triangular.

![](img/c9b2d394f4fc2f7e276f6a0a6fa9c2f6_203_0.png)

The following code shows how the MagnifiedLine draws its thickest line. Because the line is not as wide as the ViewBox that contains it, the ViewBox enlarges it to fit:

```
<Line Stretch="Uniform" Height="20" Width="300" Margin="10,10,10,10">
<Line X1="0" Y1="0" X2="18.75" Y2="0" Stroke="Blue
StrokeDashArray="3" StrokeDashCap="Triangle"/>
</Line>
```

# Stroke

The `Stroke` property determines the color of a linear feature. You can specify the color in a couple of ways. WPF understands Red, Chartreuse, LavenderBlush, and about 150 others.

The following XAML shows how the PensAndBrushes example draws the ellipse shown in Figure 10-1. The `Stroke` property makes the ellipse's border purple.

```
<Ellipse Fill="Red" Stroke="Purple"
Margin="0" StrokeThickness="10" StrokeDashArray="2,"/>
```

The second way to specify a solid color is by giving its `color components`. In both cases, the RR, GG, and BB parts include two hexadecimal decimal digits giving the color, red, green, and blue color components between 00 and FF (255). For example, the value `#FF0000` is red, and the value `#FFF00` is yellow (equal parts red and green).
