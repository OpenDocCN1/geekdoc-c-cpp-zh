# BINDING XML

The previous two sections explain how to build objects from classes defined in the code-behind and bind them to controls as TreeView. A third approach builds the objects as XML data stored completely in the XAML code.

When you use this approach, you can simply define the data by typing in elements and their attributes, making up their names as you go. For example, the following code defines a Manager object containing two Employee objects:

```xml
<Manager Name="Mindy" LastName="Most" Extension="0001" Title="Manager of OR">
  <Employee FirstName="Alice" LastName="Able" Extension="1111"/>
  <Employee FirstName="Ben" LastName="Better" Extension="2222"/>
</Manager>
```

## OrgChartXml

Neither the XML code nor code-behind needs include definitions for the Manager and Employee classes. In fact, WPF doesn't actually create Manager and Employee. Instead, it creates XmlElement with Name properties set to Manager and Employee.

> TERRIBLE TYPES
> Be careful when you type XML data. If you misspell an element's name, WPF merely creates a new object with the misspelled name. For example, if you accidentally create an Employee element, WPF will create an XmlElement named Employee. Later, when a HierarchicalDataTemplate searches for Employee objects (described next), it will miss this one.

To use this XML data, you need to wrap it in an XmlDataProvider that you can bind to a TreeView. The XmlDataProvider should contain an x:XData that holds the actual data.

```xml
<XmlDataProvider x:Key="regions" XPath="Regions">
<x:XData>
  <Regions xmlns="">
      <Region RegionName="East">
      </Region>
      <Region RegionName="Central">
      ...
    </Regions>
  </x:XData>
</XmlDataProvider>
```

## OrgXml

The XmlDataProvider's XPath property defines the XPath within the data that should be used as the root of the provider. Usually XPath is set to the root element of the XML data, which sits inside XData.

If you wanted to use only some of the data, however, you could change XPath. For example, Regions/Region[2]

> Note that indexing in XML elements like this starts at 1 not 0, so Region[2] is the second element, not the third.

The XML items inside theData can redefine XML namespaces, but usually it's easiest to reset the namespace for all of the elements to an empty string that you don't need to worry about.

# EXTERNAL XML

You can also use an XmlDataProvider to refer to a separate file that contains the data as:

```xml
<XmlDataProvider xKey="OrgChartData" Source="orgchart.xml"
XPath="Regions/">
```

When you bind Views and controls to XML data in your way, you must make a couple of important changes to the way templates refer to the data.

First, because the XML code defines its own data types, you don't need to use a namespace prefix to classes defined in the code-bind.

Second, because the XML objects are XmlElements and not classes defined in the code-bind, you should use XPath instead of Path syntax.

For example, the following code shows the HierarchicalDataTemplate that the OrgChartXml program uses for Regions:

```xml
<HierarchicalDataTemplate
DataType="Region"
ItemsSource="Binding XPath=@RegionName">
  <TextBlock Text="Binding XPath=@RegionName" Foreground="Red">
    <TextBlock.BitmapEffect>
      <OuterlowBitmapEffect/>
    </TextBlock.BitmapEffect>
  </TextBlock>
</HierarchicalDataTemplate>
```

![](img/c9b2d394f4fc2f7e276f6a0a6fa9c2f6_374_0.png)

In this template, the DataType is the simple Region rather than the more complex local: Region.

ItemsSource uses the XPath value *, indicating that the node's children should include all of the nodes of the current node.

Finally, the TextBlock's Text is bound to @RegionName. When the previous programs referred to a Region object, that object's name was stored in its RegionName property.
