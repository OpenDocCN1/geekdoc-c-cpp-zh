
WPF also includes an abundance of new objects to manage animation, resources, events, styles, plates, and other new WPF features.

Your application uses some combination of these objects to build a user interface.

## What Is XAML?

XAML (pronounced *zammel*) stands for “Extensible Application Markup Language.” It is an extension of XML (extensible Markup Language). Microsoft invented XAML to represent WPF interfaces in a static contrast to HTML which represents the contents of a web page. It defines special elements to render windows, controls, resources, styles, and other WPF objects.

A program can use a file containing XAML code to load a user interface. For example, a web browser can load a file containing XAML code and display the user interface (UI) it defines. If you use Expression Blend or Visual Studio to create a WPF application, the application automatically loads the project's XAML for you so you don't need to add code to do it yourself.

> NO XAML REQUIRED

Note that XAML is not required to make a WPF application. A program could build all of the objects that it needs by using code. For example, instead of placing a *Label* object in a XAML file, the program could create an instance of the *Label* class and use that instead. XAML is just there for your convenience. It makes it easier to build and store interfaces.

All of the XML rules apply to XAML files. In particular, XAML files must have a single root element that contains all of the other elements in the file. What element you use as the root element depends on the type of project you are building.

For example, in a compiled application, the root element is a *Window* that represents the window displayed on the desktop. In contrast, a loose XAML page is displayed in a web browser, so the browser plays the role of the grid. In that case, the root element is typically some container control such as a *Grid* or *StackPanel* that can hold all of the other elements.

## CONTROL SNEAK PEEK

> Later chapters describe these controls in detail, but for now, know that a *Grid* arranges controls in rows and columns, and a *StackPanel* arranges controls in a single row either vertically or horizontally.

Each opening element must have a corresponding closing element with the same name beginning with a slash. For example, the following code snippet defines a StackPanel:

```
<StackPanel>
</StackPanel>
```

If an element doesn't need to contain any other elements, you can use a simple shorthand and the opening element with a slash instead of a separate closing element. The following snippet shows an Image object:

```xml
<Image Margin="10" Width="75" Height="75" Source="Volleyball.jpg"/>
```

The preceding snippet also demonstrates attributes. A XAML attribute is a value contained inside an item's tag. The Image object has Margin, Width, Height, and Source with values 10, 75, 75, and Volleyball.jpg.

XAML elements must be properly nested to show how WPF objects contain other objects. The following XAML code shows a Window that contains a StackPanel that holds several other StackPanels, each holding an Image and a Label.

```xml
<Window
xmlns="http://schemas.microsoft.com/winfx/2006/xml/presentation"
xmlns:x="http://schemas.microsoft.com/winfx/2006/xml"
x:Class="Window"
Title="SimpleCritters"
Width="507" Height="156"
FontSize="22" FontWeight="Bold" FontFamily="Comic Sans"
Margin="5">
<StackPanel Orientation="Horizontal" Margin="5">
    <Image Margin="5" Height="50" Source="Frog.jpg"/>
    <Label Margin="5" Content="Frog"/>
    <Image Margin="5" Height="50" Source="Butterfly.jpg"/>
    <Label Margin="5" Content="Butterfly"/>
    <Image Margin="5" Height="50" Source="Shark.jpg"/>
    <Label Margin="5" Content="Shark"/>
    <Image Margin="5" Height="50" Source="Tiger.jpg"/>
    <Label Margin="5" Content="Tiger"/>
    <Image Margin="5" Height="50" Source="Platypus.jpg"/>
    <Label Margin="5" Content="Platypus"/>
</StackPanel>
</Window>
```

## Object Trees

The controls that make up a user interface such as the one shown in Figure 1-2 form a hierarchy with controls containing others, which may contain others. Figure 1-4 shows this program's control hierarchy graphically.

![](img/c9b2d394f4fc2f7e276f6a0a6fa9c2f6_43_1.png)

WPF has two concepts of trees that represent structure: the logical tree and the visual tree. They represent structure similar to the one shown in Figure 1-4.

### Logical Tree

The logical tree is defined by the relationships among objects in the interface. For example, a scrollbar includes a thumb, two arrows at the ends, and clickable areas. Each of those pieces is part of the logical tree.

Why should you care about these trees? First, controls need to inherit properties according to their positions in the logical tree. For example, the preceding XAML code sets the main FontSize, FontWeight, and FontFamily properties:

```xml
FontSize="22" FontWeight="Bold" FontFamily="Comic Sans"
```

These properties are inherited through the logical tree so the Labels at the bottom of the tree will all use these fonts.

### Visual Tree

The second tree is the visual tree. The visual tree represents the structure of components. For example, a scrollbar includes a draggable thumb, two arrows at the ends.

The second reason we care about these trees is that events tend to follow the visual tree. For example, when you click on an arrow in a scrollbar, you don't really want to have to deal with the arrow's events. Instead you let the event propagate up the visual tree to the scrollbar, and you can catch it anywhere.

## Non-Treelike Structure

Because the controls that make up a user interface such as this one naturally form a containment hierarchy, they map fairly into XML. Unfortunately some of the things that make up an interface don't fit quite nicely in a tree structure.

For example, Figure 1-5 shows a more complicated version of the previous user interface.

In this version, all of the Image controls have drop shadows. You could give each Image its drop shadow, but that would mean duplicating code, which would make maintaining the program harder. For example, if you later decided to remove the drop shadows or use some other effect (perhaps to put a glow around the images), you would have to update each control separately.

Rather than repeating the drop shadow code, you could define a Style and apply it to each Image. Now to change each Image, you only need to change the Style.

Similarly, this example defines a style for its Label controls that give them drop shadows, makes them yellow, and changes their text. Unfortunately, each of these styles applies to several controls in the logical hierarchy, and misses quite the nice tree structure shown in Figure 1-4.
