# Dynamically Loaded Skins

One of the drawbacks of the previous skinning techniques is that they only modify existing objects. They can display an Ellipse, Button, or Label with different properties, but they are still the same Ellipse, Button, or Label. For example, you cannot provide one skin that launches with Buttons, another that uses Menus, and a third that uses Labels.

Common solution to this problem is to include every set of controls in every skin and hide the ones that you don't need. For example, you would hide Buttons, Menus, and Labels in every skin. The button-oriented skin would hide the Menus and Labels, the menu-oriented skin would hide the Buttons and Labels, and the label-oriented skin would hide the Buttons and Menus.

Another solution to this problem might be to use separate XAML files then sit on top of the code-behind. Unfortunately, WPF doesn't handle this situation well.

WPF provides methods for loading XAML files with or without event handlers attached. The short version of this is, if you want to load XAML code with event handlers, you can only have one XAML file associated with each code-behind. If you load XAML code without event handlers, you need to wire up the event handlers yourself.

> THE LONGER STORY

If you want to load XAML files with event handlers, then you need to associate the XAML with a class defined in your code-behind. Unfortunately, WPF adds its automatically generated bonus routines to perform some extra such as connecting the XAML events with the event handlers provided by your class. If you try to associate two XAML files with the same class, WPF creates multiple copies of those routines with the same signatures and that confines Visual Studio.
You might try to make multiple classes for the XAML files by inheriting them from a common base class that provides all of the necessary functionality. Sadly, the automatically generated code makes your class inherit from a WPF control type. For example, if your XAML file contains a Grid as its root element, then the code makes your class inherit from the Grid class. That means that you cannot make it inherit from your desired base class.
The only direct solution I've found is to make completely separate classes for each XAML file, but that kind of defeats the goal of trying to use common code-behind.

Wiring up event handlers isn't hard, although it reduces the separation between user interface design and writing the code-behind. Now the interface designer and the programmer agree on the event handlers that the code will use and on the names of the controls they use.
