# ProgressBar

The ProgressBar displays information to the user. As your program performs some consuming task, it can use a ProgressBar to let the user know that the program is still working and to indicate how much it has done.

The control's Minimum, Maximum, and Value properties determine the control's appearance. For example, suppose your program needs 17 large text files. You could set the ProgressBar's Minimum property to 0 and its Maximum property to 17. After processing each file, the program could set the control's Value property to the number of files processed so far. As the program worked through its way, the ProgressBar would fill in a corresponding percentage of itself.

# Spatial Controls

Unfortunately in WPF, the situation isn't quite that simple. As the progress works on the files, it doesn't give CPU long enough for the ProgressBar to refresh itself on the screen so the user doesn't see any change in the control's status.

One way to solve this is to perform the lengthy task on a different thread. A thread is like a lightweight process that can run independently of the main user interface. Now as the thread works, it can update the ProgressBar's Value property. Because the ProgressBar runs in a different thread, it can update independently of the lengthy task.

Sadly, this more complicated approach isn't as easy as it sounds. In WPF (and Windows Forms programming, too), a control can only be accessed by the same thread that created it. The control, the file processing code cannot directly update the ProgressBar because it is running in a separate thread.

The almost final solution is to have the file processing use a Dispatcher to invoke code on the interface thread when necessary.

If you think this all sounds pretty complicated for a simple task as showing progress, you're right! Fortunately, there's a simpler solution.

The BackgroundWorker class can automatically perform a task on a separate thread and provide notification to the interface thread when necessary. Behind the scenes BackgroundWorker handles all of the details about starting itself on a new thread, using a Dispatcher to invoke code on the interface thread, and so, and so forth, all of the details are handled for you.

The UseProgressBar example demonstrates how to show how it's doing as it simulates a long task. The C# code shows how the progress works:

// Simulate a long task.
private void BackgroundWorker_DoWork(Object sender,
System.ComponentModel.DoWorkEventArgs e)
{
    int value = 0;
    Random rand = new Random();
    while (value < 100)
    {
        // Wait a little while.
        Thread.Sleep(200);

        // Add a bit to the progress.
        value += rand.Next(10, 20);

        // Update the UI thread.
        m_BackgroundWorker.ReportProgress(value);
    }
}

The code starts by declaring the BackgroundWorker object. The Window's constructor initializes the object and sets its ReportsProgress property to True so it can generate progress events. It assigns event handlers to the object's DoWork, ProgressChanged, and RunWorkerCompleted events.

When the user clicks the btnDoSomething button defined by the Progress. XAML code, the btnDoSomething_Click event handler executes. That code displays the ProgressBar and progress Label and hides the Button. It then calls the BackgroundWorker’s RunAsync method to start the lengthy task.

When the program calls the BackgroundWorker's RunAsync method, the object raises its DoWork event. The event handler sets a value to 0 and then enters a loop that runs as long as the variable's value is less than 100.

Each time through the loop, the program sleeps for 200 milliseconds to simulate a long task. At this point, a real program would be frantically reading files, generating output, buying and selling stocks, and performing calculations.

After some time, the program generates a random number between 10 and 20 and adds it to the value variable. It then calls the BackgroundWorker's ReportProgress method, passing it to the new value. The worker raises its ProgressChanged event on the interface thread.

The loop continues until the value reaches 100.

When the worker raises ProgressChanged, the program's BackgroundWorker_ProgressChanged event handler executes. Routine runs on the interface thread that the creator so it can directly access the control's value property.

When the loop ends, the BackgroundWorker_DoWork event handler ends, and the BackgroundWorker raises its WorkerCompleted event. The event handler hides the ProgressBar and redraws the Label and its button.
