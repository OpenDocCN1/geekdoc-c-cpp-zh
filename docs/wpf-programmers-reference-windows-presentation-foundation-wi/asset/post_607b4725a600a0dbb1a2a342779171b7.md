This code gets the menu item that triggered the event and looks at the item's Tag property to see which resource file to load. It creates a ResourceDictionary object loaded from the file, removes old resource dictionaries from the application's MergedDictionaries collection, and adds the new dictionary.

## REMOVED RESOURCES REDUCX

The program doesn't remove the first resource dictionary so that WPF doesn't get confused about missing resources and issue a flood of warnings. For more information, see the note “Removed Resources” in the “Dynamic Resources” section of Chapter 12.

When the program loads the new resource dictionary, WPF detects the changes and updates all of the window's dynamic resources.

This technique is what most developers think of skinning in WPF applications: The program loads multiple resource files at run to provide different skins.

## Animated Skins

The skins described in the previous section use separate resource dictionaries to provide different appearances. The program's XAML file sets its control properties to resource values so that when you change the resource values, the interface changes accordingly.

Another way to change property values is to use property animation. Chapter 14 covers property animation in greater detail, but this section explains briefly how to use animation for skinning.

XAML files allow you to define triggers that launch storyboards that represent properties. For example, when the user presses the mouse down over a rectangle, the XAML code can run a storyboard that varies the Rectangle's Width property smoothly from 100 to 200 over a 1-second period.

The AnimatedSkins program uses this technique to provide skinning. Figure 16-9 shows the program displaying its green skin. Figure 16-10 shows its blue skin.

When you click the appropriate control, a trigger launches a storyboard that:

- Resizes the main window and changes its Background brush.
- Hides and displays the small blue or green ellipses in the upper-right corner that you click to switch skins.

## THE PRICE OF COOLNESS

You might argue that coolness isn't really the focus in many applications, and you would be completely correct, but programmers who write skins aren't usually focused on getting by the least possible work. It's hard to argue that most serving anything other than an aesthetic purpose, so long as you're spending extra effort providing skins, it's not completely fair to say that the extra coolness of animated skins isn't worth the effort. By the same token, you could argue that you shouldn't even use WPF and stick with Windows programming, which is generally easy.

That said, however, that animating skins takes a lot of time. Tweaking the animations to give everything the right position, size, and appearance takes time. The AnimatedSkins example program uses two storyboards (one for each skin) but 100 property animations to get everything right. And the differences between these two skins aren't as great as I've seen; you could spend a huge amount of time getting everything right.

One interesting side of this technique is that one animation doesn't need to finish before a new animation can start. ## Dynamically Loaded Skins

One of the drawbacks of the previous skinning techniques is that they only modify existing objects. They can display an Ellipse, Button, or Label with different properties, but they are still the same Ellipse, Button, or Label. For example, you cannot provide one skin that launches with Buttons, another that uses Menus, and a third that uses Labels.

Common solution to this problem is to include every set of controls in every skin and hide the ones that you don't need. For example, you would hide Buttons, Menus, and Labels in every skin. The button-oriented skin would hide the Menus and Labels, the menu-oriented skin would hide the Buttons and Labels, and the label-oriented skin would hide the Buttons and Menus.

Another solution to this problem might be to use separate XAML files and then sit on top of each other.

WPF doesn't handle this well. If you want to load XAML files with event handlers, you must wire them up yourself. If you load XAML code without event handlers, you need to associate the XAML with a class. The only direct solution I've found is to make completely separate classes for each XAML file, but that defeats the goal of trying to use common code-behind.

Wiring up event handlers isn't hard, although it reduces the separation between user interface design and writing the code-behind. Now the interface designer and the programmer agree on the event handlers that the code will use and on the names of the controls they use.

## INTERFACE IRONY

The difficulty of attaching multiple XAML files to the same code-behind seems somewhat ironic given how much emphasis WPF places on separation of interface and code-behind. You can separate an interface from its code only as long as you keep them logically associated with each other.
