
# PROPERTY ODDITY

Sometimes the Properties window doesn't show the properties that you expect. If you select more than one control at the same time ([Shift]+click to select more than one control or [Ctrl]+click to toggle whether a control is selected), then the Properties window displays only properties that are common to all of the selected controls. For example, Grids have a Background property that Rectangles use Fill for the same purpose, if you select a Grid and a Rectangle, then you'll see none of those properties.

Similarly, if you click on a file in the Solution Explorer, you'll see the properties of the file, not the currently selected controls.

The Properties window provides editors for a few complex properties. For example, it provides editors that let you modify a Grid's ColumnDefinitions and RowDefinitions properties, and to generate gradient brushes.

# NECESSARY NAMES

In Figure 2-10, the selected Grid control has no name. You can see the Name textbox near the top of the Properties window below the control's type, System.Windows.Controls.Grid.

If you need to refer to a control in code, either the XAML code or the C# or Visual Basic code the interface, then you should give the control a good name.

Developers often don't give names to controls that are never referred to by the code such as Labels, GroupBoxes and decorative controls, layout controls such as StackPanels, and so forth.

Many C# and Visual Basic developers give a prefix that tells the kind of control followed by a descriptive name. For example, txtFirstName is a TextBox that has a first name. Some links you follow for specific conventions include:

- Microsoft's Visual naming conventions at mdn.microsoft.com/aa263493.aspx
- Microsoft Consulting Service's Visual Basic naming conventions at support.microsoft.com/kb/110264
- More general Microsoft naming guidelines at http://msdn.microsoft.com/xzff53w0.aspx

Using a prefix lets IntelliSense help you find the control you want. For example, if you use txt in a Code Editor, IntelliSense will bring you a list of all available TextBox as you can easily pick the one you want. (This is particularly useful when I teach and I don't know the name of a student's controls. If you use the right prefix, I can use txt and find the control whether they are named txt-FirstName, txtCustomerName, or txtName)

Some developers put the type of control at the end of the name as FirstNameTextBox or FirstNameTextbox. This makes the control's purpose obvious, but it removes the IntelliSense benefit. (I suspect those developers are used to an environment that doesn't have good IntelliSense support.)

# Default Event Handlers

The simplest way to attach code to the user interface is through Window Designer. If you want to add code to a control's default event handler (e.g., a Button's Click event), simply double-click on control. Visual Studio automatically creates an event handler for the event and opens it in the Code Editor (either the C# or Visual Basic depending on the language you're using). It also adds code to the XAML element to attach control to the event handler.

For example, the following code shows the event handler generated when you double-click on a Button named btnGreen while using C#.

```csharp
private void btnGreen_Click(object sender, RoutedEventArgs e)
{
}
```

The XAML code shows the button's definition. Visual Studio automatically attaches the Click="btnGreen_Click" to tie the button to its event handler.

```xml
<Button Height="23" HorizontalAlignment="Left" Margin="10,10,0,0" Name="btnGreen" VerticalAlignment="Top" Width="75" Click="btnGreen_Click">Button</Button>
```

The Click attribute is the only connection between the XAML code and the code-behind. If you need to detach the button from the code, simply remove that attribute. You don't need to remove the event-handler code, although leaving it in will clutter the code.

# Non-Default Event Handlers

If you want to attach to an event other than a control's default event (e.g., a Button's MouseOver event), select the control in the Window Designer. At the top of the Properties window, click on the Events button to view the control's events.

# Handmade Event Handlers

Double-clicking on a control and using the Properties window are the easiest ways to build event handlers, but there's nothing stopping you from doing it by yourself.

Add an attribute to the control's XAML code. For example, to add a ValueChanged event to a Slider, add an attribute to ValueChanged="slider_ValueChanged".

Then add the event handler to your code. You'll need to give the appropriate parameters for the type of event you are creating. For C#, the Slider's ValueChanged event handler would look similar to the following:

```csharp
private void slider_ValueChanged(object sender,
    RoutedPropertyChangedEventArgs<double> e)
{
}
```

In Visual Basic, the code would be similar to the following:

```vb
Private Sub Slider_ValueChanged(ByVal sender As System.Object,
    ByVal As System.Windows.RoutedPropertyChangedArgs(
    Of System.Double)) _
    Handles Slider1.ValueChanged

End Sub
```

The trick to building event handlers by hand lies in knowing what parameters they need. Because they are often complicated, it's usually easier to double-click on the control or use the Properties window.

# Runtime Attached Event Handlers

A Window's controls are objects in the project's code, so you can add event handlers to them at run time. In this case, you don't need to add an attribute to the XAML code to connect to its event handler.

The following C# code attaches the btnRed's Click event to the btnRed_Click handler.

```csharp
btnRed.Click += btnRed_Click;
```

Here's Visual Basic version:

```vb
Add btnRed.Click, AddressOf btnRed_Click
```

# Other Visual Basic Handlers

Visual Basic gives you one additional option for connecting controls to event handlers. Do not include an event attribute in the XAML code. Then add a Handles clause to the event handler's declaration.

The following Visual Basic code shows the declaration for an event handler. The Handles clause at the end indicates that this routine the btnGreen control's Click event.

```vb
Private Sub btnGreen.Click(ByVal sender As System.Object,
    ByVal e As System.Windows.EventArgs)
Handles btnGreen.Click
```

The trick is in knowing what parameters to pass to the routine. Frankly, Visual Basic's Relaxed Delegates lets you simplify the parameter list.

This feature allows you to replace the type of a parameter with a different type as long as you know that the actual value will match the new type at run time. For example, if this event handler only button clicks, then the sender is actually a button. If the event handler doesn't need to use the second parameter, you can declare it using the simple type Object. The simplified version of the event handler is:

```vb
Private Sub btnBlue.Click(ByVal btn As Button,
    ByVal e As Object) Handles btnBlue.Click
```

Finally, if the event handler doesn't need to use the parameters at all, you can omit them in the following code:

```vb
Private Sub btnGr.Click() Handles btnGr.Click
```

This technique isn't as simple as double-clicking on the control in the Window Designer, but it does make the Visual Basic code very simple. Note that you can double-click on the control to create the event handler and remove its parameters, giving you the best of both worlds.
