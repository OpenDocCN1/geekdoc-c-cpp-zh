> Note that indexing in XML elements like this starts at 1 not 0, so Region[2] is the second Region element, not the third.

The XML items inside the x:Data element can redefine XML namespaces, but usually it's easiest to reset the namespace for all of the elements to an empty string that you don't need to worry about using them.

# EXTERNAL XML

You can also use an XmlDataProvider to refer to a separate file that contains the data as:

```
<XmlDataProvider xKey="OrgChartData Source="orgchart.xml"
XPath="Regions/">
```

When you bind Views and controls to XML data in your way, you must make a couple of important changes to the way templates refer to the data.

First, because the XML code defines its own data types, you don't need to use a namespace prefix to classes defined in the code-bind.

Second, because the XML objects are XmlElements and not classes defined in the code-bind, you should use XPath instead of Path syntax.

For example, the following code shows the HierarchicalDataTemplate that the OrgChartXml program uses for Regions:

```
<HierarchicalDataTemplate
DataType="Region"
ItemsSource="Binding XPath=@RegionName">
  <TextBlock Text="Binding XPath=@RegionName" Foreground="Red">
    <TextBlock.BitmapEffect>
      <OuterlowBitmapEffect/>
    </TextBlock.BitmapEffect>
  </TextBlock>
</HierarchicalDataTemplate>
```

![](bbox=[0.833, 0.757, 0.928, 0.773])

In this template, the DataType is the simple Region rather than the more complex local: Region.

ItemsSource uses the XPath value *, indicating that the node's children should include all of the nodes of the current node.

Finally, the TextBlock's Text is bound to @RegionName. When the previous programs referred to a Region object, that object's name was stored in its RegionName property.
