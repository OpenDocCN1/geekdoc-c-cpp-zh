
```cpp
std::cout << std::format("The value of the expression {} < {} is {}\n",
                         first, second, first < second);
std::cout << std::format("The value of the expression {} == {} is {}\n",
                         first, second, first == second);
```

## Comparing Floating-Point Values

Of course, you can also compare floating-point values. Let’s consider some slightly more complicated numerical comparisons. First, define variables with the following statements:

```cpp
int i {-10};
int j {20};
double x {1.5};
double y {-0.25e-10};
```

Now consider the following logical expressions:

```cpp
-1 < y        j < (10 - i)        0.0*x < (3 + y)
```

The comparison operators are all of lower precedence than the arithmetic operators, so none of the parentheses are strictly necessary, but they do help make the expressions clearer. The first comparison evaluates to true because y has a very small negative value (~−0.000000000025), which is greater than −1. The second comparison results in false because the expression 10 − i has the value 20, which is the same as j. The third expression is true because 3 + y is slightly less than 3.

One peculiarity about floating-point comparisons is that not-a-number values are neither less than, greater than, nor equal to any other number. They’re not even equal to another not-a-number value. Let the nan variable be defined as follows (see Chapter 2 for the numeric_limits template):

```cpp
const double nan{ std::numeric_limits<double>::quiet_NaN() };
```

Then all of the following expressions evaluate to false:

```cpp
i < nan     nan > j     nan == nan
```

You can use relational operators to compare values of any of the fundamental types. When you learn about classes, you’ll see how you can arrange for the comparison operators to work with types that you define, too. All you need now is a way to use the result of a comparison to modify the behavior of a program. We’ll look into that shortly. But first: a visit from our outer space...

## The Spaceship Operator

In C++20, a new operator was added to the language to compare values: the three-way comparison operator, denoted <=>. This new operator is better known by its informal name: spaceship operator. It gets this nickname from the fact that the character sequence <=> somewhat resembles a flying saucer!

In a way, `<=>` behaves as `<`, `==`, and `>` all squished into one. Simply put, a `<=>` determines, in a single expression, whether a is less than, equal to, or greater than b. It’s easiest to explain the basic working of `<=>` through some code though. The following example reads an integer and then uses `<=>` to compare that number to zero:

```cpp
// Ex4_02.cpp
// Three-way comparison of integers
import <compare>;  // Required when using operator <=> (even for fundamental types)
import <format>;
import <iostream>;

int main()
{
    std::cout << "Please enter a number: ";

    int value;
    std::cin >> value;

    std::strong_ordering ordering{ value <=> 0 };

    std::cout << std::format("value < 0: {}\n", ordering == std::strong_ordering::less);
    std::cout << std::format("value > 0: {}\n", ordering == std::strong_ordering::greater);
    std::cout << std::format("value == 0: {}\n", ordering == std::strong_ordering::equal);
}
```

For integer operands, operator `<=>` evaluates to a value of type `std::strong_ordering`, a type that for the most part acts as an enumeration type (see Chapter 3) with possible values less, greater, and equal (there’s technically a fourth value as well, but more on that shortly). Based on the value of `ordering`, you can then determine how value is ordered compared to the number zero.

At this point, you may wonder: what’s the point of this operator? And rightfully so. As with all alien encounters, the spaceship operator appears somewhat strange and puzzling at first. After all, the last four lines of Ex4_02 can be written much more economically as follows (analogous to Ex4_01A):

```cpp
std::cout << std::format("value < 0: {}\n", value < 0);
std::cout << std::format("value > 0: {}\n", value > 0);
std::cout << std::format("value == 0: {}\n", value == 0);
```

A lot less typing, and just as efficient (as if performance should even matter for integer comparisons). Indeed: when comparing variables of fundamental types, in isolation, the `<=>` operator makes little to no sense. Comparing variables of more complex types, however, can be expensive. It then can pay off to compare them only once (as in Ex4_02) instead of two to three times (as in Ex4_01). We’ll see examples of that with string objects in Chapter 7. And in Chapter 13, we will show you how adding support for comparisons for your own object types becomes trivial thanks to the `<=>` operator. But all that ultimately builds on `<=>` comparisons of fundamental types. And before we can get to that point, we’ll need to cover some more groundwork in the next two subsections.

## Comparison Categories

The `<=>` operator does not always evaluate to a value of type `std::strong_ordering`. The type it evaluates to depends on the type of its operands. For floating-point numbers `f1` and `f2`, for instance, the type of `f1 <=> f2` would be `std::partial_ordering`. The reason is that mathematically speaking floating-point numbers are not strongly ordered (or totally ordered, as it is more commonly called in mathematics); they are only partially ordered. That is: not all pairs of floating-point numbers are comparable. Concretely, as seen in the previous section, not-a-number values are not ordered with respect to any other number. For that reason, `f1 <=> f2` evaluates to `std::partial_ordering::unordered` if `f1` and/or `f2` is not-a-number.

Table 4-2 shows the three types that can be used for three-way comparisons. Comparing two values of most fundamental or Standard Library types results in a `strong_ordering`. When the values are or contain floating-point values, the result becomes a `partial_ordering`. Comparing standard types never results in a `weak_ordering`, but like all comparison category types, you can use it for user-defined `<=>` operators (see Chapter 13). An example of a weak ordering would be the ordering of points in a Euclidean space based on their distance to the origin.

**Table 4-2.** Comparison Category Types Defined By `<compare>`

| | less | greater | equal | equivalent | unordered | Usage |
|---|---|---|---|---|---|---|
| `strong_ordering` | ✓ | ✓ | ✓ | ✓ | | Integers and pointers |
| `partial_ordering` | ✓ | ✓ | | ✓ | ✓ | Floating-point numbers |
| `weak_ordering` | ✓ | ✓ | | ✓ | | User-defined operators only |

The three comparison category types are defined by the `<compare>` module. Whenever you use the `<=>` operator, even with fundamental types, you have to import the `<compare>` module or you will get a compiler error (you can try it out with Ex4_02).

Notice how only `strong_ordering` uses the term equal, whereas the `partial_ordering` and `weak_ordering` use equivalent. Formally equality implies substitutability, whereas equivalence does not. Substitutability, in turn, more or less means that if `a == b` is true, then `f(a) == f(b)` must be true as well for any function `f`. For floating-point values, for instance, even though `-0.0 == +0.0`, `signbit(-0.0) != signbit(+0.0)` (`signbit()` is a `<cmath>` function that returns—you guessed it—the sign bit of a floating-point number). In other words: `-0.0` and `+0.0` are very nearly equal, but not quite; they are, however, for all intents and purposes, completely equivalent.

**Note** `std::strong_ordering::equivalent` equals `std::strong_ordering::equal`. We recommend you mostly use the latter, as it better expresses the semantics of a strong ordering.

`strong_ordering` values implicitly convert to either `weak_ordering` or `partial_ordering`, and `weak_ordering` values implicitly convert to `partial_ordering`. These conversions have the obvious results. `partial_ordering` values, however, cannot be converted to either of the other types. This makes perfect sense as well: otherwise, what would you do with unordered values?

**Note** The comparison category types of Table 4-2 only act like enumeration types, but they are actually class types. Consequences include that using enum statements will not work for them, and that you cannot use them in the `switch` statement seen later in this chapter either.
