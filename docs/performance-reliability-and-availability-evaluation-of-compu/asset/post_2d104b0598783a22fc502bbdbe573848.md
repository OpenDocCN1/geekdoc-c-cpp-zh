An error is a state of a component of a system (a system substrate) that may cause a subsequent failure (Figure 16.2). A failure occurs when an error is not contained, reaches the system interface, and alters the system. A fault is an event that causes an erroneous substrate [31]. A system with faults that delivers its specified functionality is fault-tolerant; the system does not fail even when there are faulty components.

Summarizing, a fault causes an erroneous substrate. The error can spread through the system because the output of one component may be an input of other components. If the erroneous substrate is not contained, it propagates to the system interface and causes a failure.

→ fault → error → failure → fault → ...

Figure 16.2 Fault, Error, and Failure Sequence.

For instance, consider an air conditioner switch contact that is stuck open; that is, it is always independently on the switch position. Thus, we already failed the beginning of operations (switch position in open) but there is not yet an error. however, if we change the switch position to closed, the fault causes an error (if not contained), which, in turn, causes a malfunctioning (failure) since the switch contact does not close, and the air conditioner does not start.

Hardware faults can be classified by several aspects. A fault may be active or dormant; otherwise, it is dormant. Concerning durations, faults can be permanent, transient, or intermittent. A permanent fault is a component that is out of service. One example is a burnt-out incandescent lamp. A transient fault causes a component to malfunction for some time, but the component is fully restored after that. Intermittent faults, on the other hand, never go away. They oscillate between dormant and active. A loose electrical connection is an example of an intermittent fault. Fault can also be classified as benign and malicious. A fault that only causes a component to go out of service is called benign. Malicious faults produce plausible but incorrect output. As an example, assume an altitude sensor in an airplane that reports 2000 m altitude to one component and 1200 m altitude to another component [218].

A programming bug (fault) causes erroneous states. For instance, assume a function is presumed to calculate the value of three-dimensional space, but it calculates two-thirds of the respective space due to a programming bug. This bug (fault) will run in an erroneous state (error) only when the particular function is executed, and if the erroneous state is not contained, it will propagate to generate a failure. Such an approach is considerably more costly than avoiding or removing faults during the developing or testing phase. However, diagnosing and confirming the underlying fault accountable for an observed failure becomes uncertain if the failure cannot be reproduced. Software testing is suitable for dealing with faults that consistently result in particular circumstances. Testers call such faults Bohrs, a reference to Niels Bohr's atomic model [164, 439]. However, when testers fail to reproduce the failure under similar conditions, the debugging can sometimes lead to the failure but may not reach the fault. For instance, inadequate synchronization in multithreaded programs can yield race conditions depending on the 'threads' timing and operating system schedules. A failure exclusively occurs if the operating system schedules the threads, using the debugging process is uncertain without reproducing faults and failing. A fault can prompt the software systems to manifest an uncontrolled and ever non-deterministic behavior. Software developers may name such faults Mandelbugs (a reference to the prominent researcher in fractal analysis). The literature also designates such faults as Heisenbugs as in Heisenberg's uncertainty principle [439].

As Heisenbugs resemble non-deterministic behaviors, a new execution of the failed operation usually leads to success. Nevertheless, when the specific internal conditions are met, the failure may be exposed. In many cases, simply restarting or rebooting a computer after experiencing a failure can be valuable for preventing future failures. Nevertheless, such actions (software rejuvenation) are only effective if the failure rate increases with the runtime. Many software systems running continuously for long periods tend to manifest degraded performance and reliability due to the increased failure rate. Such a phenomenon is called software aging [439].

As described, service failure is defined as an event that occurs when the delivered service deviates from correct service. An operational mode is a system behavior that delivers a service according to specification. On the other hand, the different ways in which the service deviation are manifested are a system's failure modes [352]. The failure modes may be characterized by the domain, perception, and consequence (see Figure 1.6). The failure domain distinguishes between content and timing failures. A content failure occurs when the information delivered at the service departs from what is defined in the specification. A timing failure occurs when the timing of the information is delivered from the timing specification. The user perception of failures leads us to distinguish them as consistent and inconsistent. A content failure occurs when the incorrect service is identically perceived by system users, whereas the system users perceive an inconsistent failure differently.

Now, consider a random variable $T$ as the time to reach the state $X(t) = 0$, given that the system started in $X(t) = 1$ at time $t=0$. The random variable $T$ represents the time to failure of the system $S$, $F_T(t)$ its cumulative distribution function (CDF), and $f_T(t)$ the respective density function (DF). Figure 16.4 shows these functions. Therefore

$F_T(0) = 0$ and $\lim_{t\to\infty} F_T(t) = 1,$

$f_T(t) = \frac{dF_T(t)}{dt} \quad (16.2.1)$

where $f_T(t) \geq 0$ and $\int_0^{\infty} f_T(t)dt = 1$.

The probability that the system $S$ does not fail up to time $t$ is the system **reliability** ($R(t)$). Here, reliability (also called survivability) is complementary with the cumulative distribution function (see Figure 16.5). In other words, $F_T$ is the **unreliability** function ($UR(t)$). The reliability is formally defined by

$P(T > t) = R(t) = 1 - F(t), \quad (16.2.2)$

$R(0) = 1$ and $\lim_{t\to\infty} R(t) = 0$.
