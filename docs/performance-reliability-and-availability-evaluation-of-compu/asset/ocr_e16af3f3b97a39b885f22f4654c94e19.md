The profiling module execution checks (see the line in red of the profiling module) the stack top and obtains the address of the next instruction to be executed (depicted red on the stack shown on the bottom center of Figure 23.9)7 of the program under analysis. This process continues until the analyzed program finishes. After this process, the profiling module summarizes the sets of addresses obtained, which shows the address where the program under analysis was interrupted. Taking these addresses and the memory map shows the range addresses of functions, methods, or blocks of code and variables generates a report stating addresses of functions, methods, or blocks of code were visited during the program’s execution.

Assuming the program under analysis takes T as its execution time, and considering the sampling frequency ($f_s=1/T_s$), where $T_s$ is the time between interruptions, we obtain the number of samples collected, $n_s=T/T_s$, during the process execution. Considering that the number of addresses sampled that belong to a function $f()$ address range is $m$, hence the time spent within the function $f()$ during the program’s execution under analysis may be estimated

$T_f = \frac{m}{n_s} \times T. (23.6.1)

Such a process is performed for every piece of code (blocks, function, methods), considering the granularity adopted by the profiler.

The GNU Compiler Collection package (gcc package) has a tool named gprof that supports profiling program code written in C and C++, among other languages. The profiling method adopted by the gcc compiler and gprof is based on a statistical profiling strategy as well as the insertion of tiny pieces of extra code (hooks) into the beginning of each C function of the program under evaluation.

The main steps for profiling a C program in two (or more) distinct files (program.c and other module.c) with gcc and gprof are:

+   1. Compile the C program with profiling switch enabled:

```
> gcc -Wall -pg program.c other_module.c -o program -lm
```
