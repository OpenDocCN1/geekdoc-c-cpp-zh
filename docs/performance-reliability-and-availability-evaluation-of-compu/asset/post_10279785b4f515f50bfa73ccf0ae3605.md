## COMMON CAUSE FAILURE

This section shows how to represent CCF using SPN. The system is composed of two classes of servers, server-class 1 (SC1) and server-class 2 (SC2). The number of servers of type SC1 is NS1, and the number of servers of type SC2 is NS2. The time to failure of each server class is exponentially distributed with $MTTF1=10000h$ and $MTTF2=15000h$. Two repair teams are available - so the servers of RS1 and RS2 are active and the time to repair is also exponentially distributed with $MTTR=20h$. The common mean time to failure is assumed to be exponentially distributed with $MTTCF=100000h$.

An availability of such a system is depicted by the SPN shown in Figure 22.37. The number of tokens in S1U denotes the number of servers of class SC1 in the operational state, whereas the number of tokens in S1D represents the number of servers of class SC1 in failure. Likewise, the number of tokens in S2U represents the number of servers of class SC2 in the operational state, and the number of tokens in S2D represents the number of servers class SC2 in failure. The server semantics of transitions FS1 and FS2 are stochastic, and the transitions' server semantics are stochastic. Transition CCF represents the common cause of failure. $MTTF1$ is assigned to FS1, $MTTF2$ is assigned to FS2, and $MTTCF$ is associated with transition CC. RS1 and RS2 have $MTTR$ as their delays. The arcs connecting S1U to CCF are marking dependent, and the weight is equal to #S1U. Similarly, the arcs connecting S2U to CCF are marking dependent, and the weight is #S2U. Likewise, the arcs connecting S1U to S1D are also marking dependent, and the weight is #S1U. The arcs connecting S2U to CCF is marking dependent too, and the weight is equal to #S2U. Transition CCF has this guard expression: (#S1U > 0) OR (#S2U > 0); that is that a CCF comes to effect if at least one server of any class should be operational. The steady-state system availability is defined by

$A = P\{#S1U > 0) \text{OR}(\#S2U > 0)\}$;

hence the downtime in the period T is

$DT = (1 – P\{#S1U > 0) \text{OR}(\#S2U > 0)\}) \times T$.

Assuming the delays in the first paragraph, if NS1 = 3, NS2 = 2, and $T = 525600$ minutes, the steady-state system availability is $A = 0.9998999$, and the yearly downtime is 52.9986 minutes.

## DISASTER RECOVERY

This system is composed of primary data center and recovery cloud (see Figure 22.38). The primary data center provides three web-servers, while two are in standby state. The auto-scaling mechanism in the primary data center reflects the number of web-servers, which is three. The recovery cloud provides two centers. Note that the primary infrastructure automatically scales up every time an active component fails and down whenever the number of active components increases. This model uses the auto-scaling mechanism GWEbDown and GWEbUp. To represent the dependency between VMs and data centers, we include immediate transitions and guard functions for each component representing the virtual machines. As an example, if the data center goes down, the web-servers also become unavailable. Such behavior is modeled by two immediate transitions (TWEbDownDC and TWEbDownHot) and guard functions (GWEbDownDC, GWEbDownHot and GWEbIrep), respectively, the transitions TWEbUpDC and TWEbUpHot, which models the unavailability of the web servers.
