It is fundamental to define what the benchmark is supposed to represent, and the performance study's aim for adopting a specific benchmark [456].

Before introducing the benchmarks, a word of caution could be said about some performance measures and scores usually adopted by some benchmarks. It is always important to stress that the main aims of benchmarks are comparing computer systems' performance. When the computer architects proposed reduced instruction-set computer architectures (RISC architectures), the meaning of the measure 'millions of instructions per second' (MIPS) lost nearly all its significance. For instance, a high-level instruction may require only one CISC (complex instruction-set computer architectures) instruction to be executed, in RISC architectures, would require machine instructions to be executed. Hence, if the execution of the high-level instruction in both architectures is similar, the MIPS are much higher for RISC architectures since the number of instructions executed in the same period is much higher than the respective of machine instructions executed in a CISC computer.

Another popular alternative to performance metrics is million floating-point operations per second (MFLOPS). Floating-point operations are addition, multiplication, division, and subtraction, for example, applied to several high-level single-precision, double-precision, and quad-precision types. This type of data is widely used in scientific calculations and in programming languages using types such as float, real, double. However, MFLOPS is dependent on the program rate which the compiler can simply influence. Therefore, as MIPS metrics, MFLOPS changes according to the mix of integer and floating-point operations. For example, a floating-point instruction program will have a higher MFLOPS rate than an integer instruction program.

Many benchmarks produce their specific scores. Benchmark development general claim is that such scores allow a more straightforward comparison since the end-user only needs to look at their specific scores. Nevertheless, these scores could be biased to specific vendors, compilers, or operating systems. There is enough to consider metrics such as execution time, memory usage, and energy consumption of programs in distinct hardware-software platforms we are interested in, taking into account a set of benchmarks for getting a more balanced view of system performance.

## Workload Characterization

One of the earliest attempts to use benchmarking was found in Auerbach Reports published in 1962. These reports were adopted as specifications of features that vendors offer. Besides, Auerbach described standard configurations to support fair comparisons across vendor lines. The typical tasks of these benchmarks were:
- a) file processing
- b) sorting
- c) matrix inversion

These benchmarks gathered data at three levels:
1) basic operations
2) individual peripheral devices
3) system configurations [27, 237]. The method adopted by Auerbach was to implement a routine to estimate computer system speed (unit of code by unit of time). In this early attempt, no stipulations were made that the benchmark should be executed in computer systems of specific features, leading to biased implementations by vendors to check out new products [237].

In 1969, Buchholz developed a synthetic program for measuring computer system performance. His approach was towards implementing a program that initiates real application. The sample program introduced was written in PL/I. Such work was research for synthetic workload [61].

In 1976, a study group of the US government and industry was formed and implemented a set of benchmarks that contained the required attributes for reproducible results supporting product selections. However, although the benchmark library had been used successfully, there was still not enough information to support a general platform.

Some of the benchmarks mentioned in this section are orders that have been adopted for performance evaluation a long time. These old benchmarks are seminal work on benchmarking computers. Other benchmarks described in this section are important due to their wide acceptance as standards for particular communities or groups. The term benchmark suite denotes a set of benchmarks with a specific set of rules that govern the conditions and methods, such as the test environment, input data, outputs, and evaluation metrics. A benchmark family is a set of benchmarks [317]. Whenever the context is clear, we adopt the term benchmark for all of them, and when required we apply specific terms.

Given that different application domains have different execution characteristics, a wide variety of benchmarks has been developed to characterize these domains. Furthermore, different types of benchmarks must satisfy the needs of many types of users. Designers of new computer systems, for example, often need benchmarks during the early stages of the project; in the initial stages of a project it is common to use simulators, emulators, and prototypes to estimate performance, using benchmarks to exercise the specific parts of interest of the new project instead of being a general benchmark that exploits many characteristics of the system since such a system may not yet be fully implemented.

On the other hand, a large organization that decides to purchase an expensive computer system from several system candidates of different brands and prices can compromise large sums based on broader performance tests results. Consequently, these organizations need more complete benchmarks that more accurately characterize each system candidate's performance and provide reliable guidelines to decide which system to acquire.

## Whetstone

Whetstone is a benchmark for evaluating computer performance focused on floating-point instructions. Whetstone was based on work by Bryan Wilcox from the National Physical Laboratory and implemented by H.J. Curnow of the HM Treasury Technical Support Unit. The first Whetstone benchmark was written in Algo 60 in 1972. The Fortran codes were published in 1973. The first results were published for IBM and ICL mainframes in 1973. The instruction rate was calculated in KiloWhetstone Instructions Per Second or KWIPS. Later, Millions or MWIPS was used. In 1980, facilities were added to time and produce speed ratings in MIPS (GMIPS and TIPS), and MFLOPS (GFLOPS and TFLOPS). Afterward, the benchmark was also converted to Fortran 77, and capable reliable non-official versions were implemented in Basic, Visual Basic, C, C++, Java, and Python programming languages [87, 243, 460, 426].
