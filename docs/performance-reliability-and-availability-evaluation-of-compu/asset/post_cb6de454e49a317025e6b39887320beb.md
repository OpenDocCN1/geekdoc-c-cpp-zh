The number “3” in the hot-standby web server component represents the triple redundancy that exists for component, similar to the redundancy already shown in the primary infrastructure. In order to represent the dependency between the hot-standby components and cloud infrastructure, we include two immediate transitions to each component and three guard functions. For example, if the disaster recovery goes down, the database-server should also become unavailable. This behavior is modeled by the guard function $GDB2dwCS$ and $GDB2rep$. The guard function $GDB2dwCS$ and $GDB2dwCS$ models the unavailability of the database-server from the hot-standby state, whereas the guard function $GDB2dwCS$ enables the transition $TDB2dwCS$, which represents the unavailability of the database-server from up state. Since the database-server cannot be recovered until the cloud is operational, the guard function $GDB2rep$ disables the transition $TDB2rep$.

Important to mention that the dependency between the load balancer and cloud server is similar to the one explained before for basic components. Another dependency exists between primary infrastructure and disaster recovery cloud. This dependency is represented by the failover and failback operations, which are triggered by guard functions. For instance, the failover and failback operations of the database-server are triggered by the guard functions $GDB2fover$ and $GDB2fback$ respectively. The guard function $GDB2fover$ enables the transition $TDB2fover$ if the disaster is detected (indicated by a token in $P_{DC}$).

Table 22.13 shows the input parameters for the proposed disaster recovery model presented in Figure 22.39. These parameters were derived from [92, 183, 212, 245]. Note that we considered three of parameter settings: Very High Availability (VHA), High Availability (HA), and Medium Availability (MA). These settings represent distinct reliability or maintainability conditions such as the existence of spare components on-site for speeding up the repairing activities or more careful choices of hardware and software that are reportedly trustworthy. The SPN model was evaluated for each parameter set, assuming that the disaster recovery (D/R) is enabled, and later,. The Mercury tool was used for all analyses [274]. Table 22.14 presents the metrics employed in our analysis, which are the steady-availability of the system for both cases: disaster recovery (D/R enabled) and disaster recovery (D/R disabled). These metrics are computed the respective expressions based on the probabilities of finding a given number of tokens in specific places of the SPN model. Table 22.15 presents numerical results computed using the SPN models. As expected, VHA settings deliver the highest availability level.
