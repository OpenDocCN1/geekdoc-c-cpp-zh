## 3DMark and PCMark

The FutureMark benchmark is a set of benchmarks implemented by FutureMark Corporation, founded in 1997. Regardless of the company's acquisition and merging, two of the most well-known benchmarks that are part of their product line are 3DMark and PCMark. PCMark evaluates the system and 3DMark is centered on graphics features. 3DMark focuses on rendering and consists of a set of tests that generate a set of specific scores, such as graphics test, physics test, combined test score, which are then adopted to compose 3DMark score by combining these specific scores using weighted harmonic mean. One of the specific scores produced by 3DMark is the graphics test (S). The S score is calculated by executing graphics tests, which produce results in frames per second.

The PCMark suite consists of tests that exercise individual workloads at a time; each gives a specific score. A workload stresses one or more components of the system under evaluation. The most important workloads include pictures, gaming, video playback and image manipulation, web-browsing, and decrypting. A PCMark score is a number describing the overall performance of the system.

## Sandra

Sandra is a benchmark utility for Windows; the first version was launched in 1997 by Soft. Since then, Sandra (and its free version - Sandra Lite) have become widely used. Sandra displays information about hardware devices, energy consumption, buses, video, memory, drives, and in addition, supports evaluation of file systems, network traffic, multimedia processing, and float arithmetic. The test execution provides overall test and individual test results such as processor power, memory bandwidth, and storage.

## SPEC Suite

SPEC stands for Standard Performance Evaluation. This organization was created to define, implement, and validate standardized benchmarks to evaluate computing systems performance and energy consumption. SPEC was founded in 1988 by workstation vendors who recognize the market demanded practical experiments. Then, SPEC expanded from a small group with a single benchmark to become a successful standardization group with more than one hundred members with a family of benchmarks. The original Open Systems Group (OSG) focuses on benchmarks for desktop systems, high-end workstations, and open systems. This group is currently divided into subgroups with specific concerns, such as OSG-Cloud, OSG-CPU, OSG-Storage, and OSG-Virtualization. Nowadays, two of the most important benchmark suites supported by SPEC are SPEC Cloud and SPEC CPU.

The CPU benchmark suite includes benchmarks for measuring and comparing computer system’s processor, memory subsystem, and compiler. SPEC CPU 2017 has benchmarks organized into four groups:

- single copy execution of integer benchmarks
- single copy execution of floating-point benchmarks
- concurrent execution of integer benchmarks
- concurrent execution of floating-point benchmarks

These benchmarks are written in C, C++, and Fortran languages. The essential metrics supported by SPEC CPU are (a) to complete workload and (b) throughput, which is complete jobs per hour. Beside, SPEC CPU incorporates the capacity to measure and report power used.

## TPC Family

The Transaction Processing Performance Council was founded in 1988, aiming at setting standards for transaction performance measurement. The two major activities are (1) creating benchmarks and (2) creating a process for review and monitoring these benchmarks. In 1989, TPC published its first benchmark, TPC Benchmark (TPC-A). TPC-A implemented online transaction processing OLTP application characterized by online sessions, disk input/output, application execution time, and transaction integrity. The workload was intended to reflect OLTP application and measures how many transactions per second system can perform when driven from multiple terminals. However, it does not support transaction types of varying complexities. The second benchmark implemented by TPC was TPC-B, a batch version without network and user interaction, focused on batch transaction processing. However, TPC-B was not as successful as TPC-A.

In 1991, TPC announced its Fair Use policies, which were required to be adopted when TPC results are used in publicity avoiding misappropriation of the TPC’s trademark. In addition, a group of certified TPC auditors was also created to review and approve TPC benchmark test and results before being submitted to the TPC as an official benchmark result or publicized.

The TPC-C benchmark was announced in 1992, and like TPC-A, it was an online transaction processing (OLTP) benchmark. Nevertheless, TPC-C is much more complex than its predecessors since it supported multiple concurrent transaction types either executed online or for deferred execution. As a result, TPC-C is ranked in transactions per minute (tpm) onto one server, and runs the benchmark workload in three virtual machines (VMs) on the system under test. TPC-IoT was designed to verify performance, price-performance, and availability metrics of systems that gather vast data from numbers of devices while running real-time analytic queries. The workload aims for typical activities in IoT systems.

The number of benchmark suites and families available nowadays is extensive. Furthermore, this field is in continuous evolution due to technological advances and new marketplaces. Therefore, this section provides a glimpse of the benchmark arena.

###24.2.2 SYNTHETIC WORKLOAD GENERATION

One difficulty when using benchmarks for evaluating computer system performance is that benchmark designers envision in advance. Specifically, there is no guarantee that the benchmarks cover all scenarios the planner may need. Therefore, another approach consists of creating a software (tool) that automatically creates or injects workloads to the system under evaluation or an emulator or simulator.

Indeed, many authors use the terms traffic injector, trace generator, traffic generators, and workload generators indistinguishably. On the other hand, some authors use the term traffic injector for tools that only replay trace (traces) on the computer system. Others adopt the term trace generator for tools that generate synthetic workloads recorded into a trace file. Many users use the terms traffic injector, trace generator, traffic generators, and workload generators indistinguishably. Some authors use traffic injectors for tools that only replay trace (traces) on the computer system. However, some authors use the terms traffic generators or workload generator to refer to software systems that generate synthetic workloads based on traces or a mathematical model to drive a load into a system, benchmark, system-emulator or simulator. Therefore, we will use the term Workload Automation Software (WAS) or Workload Automation Tool (WAT) as a generic term. However, a more specific term may be adopted with specific explanation.
