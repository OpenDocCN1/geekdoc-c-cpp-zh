## Manual Memory Management

Frequent memory management issues with delete and new are majorly difficult to find and fix the source of the logic error. Programmers have to adhere strictly to the following tenets:

- Every time you call new, it should always have an associated call to delete provided the allocated memory is no longer needed. It may sound simple, but it isn't always clear when delete should be used, but the function below shows a memory leak:

```cpp
void calc(int n) {
// ...
// Do some stuff
// ...
int *x = new int[n];
// ...
// Do some stuff with x
// ...
// Exit function without deleting x's memory
}
```

Provided a program calls on the calc function enough times, the program will eventually run out of memory. In the calc function, x is a local variable. In that light, x lives on the stack. So when a particular call to calc completes, the function's clean up code automatically releases the space held by the variable x. Because all functions automatically manage the memory for their local and parameter variables. The problem is that x is assigned via new to point to memory allocated from the heap and not the stack. Function executions do not deallocate the memory to which x pointed automatically.

- The operator delete should never be used to free up memory that has not been allocated by a previous call to new. The code fragment below illustrates one such example:

```cpp
int list[10], *x = list; // x points to list
// ...
// Do some stuff
// ...
delete [ ] x; // Logic error, attempt to deallocate x's memory
```

The space referenced by the pointer x was not allocated by the operator new, so the operator delete should not be used to attempt to free the memory. When you attempt to delete a memory that is not allocated with new, it results in undefined behavior that represents a logic error.

- The operator delete must not be used to deallocate the same memory more than once. This situation is common when two pointers refer to the same memory. Pointers like this are called aliases. The following code fragment below illustrates this situation:

```cpp
int *x = new int[10], *y = x; // y aliases x
// ...
// Do some stuff with x and/or y
// ...
delete [ ] x; // Free up x's memory
// ...
// Do some other stuff
// ...
delete [] y; // Logic error, y's memory already freed!
```

Since the pointer x and pointer y point to the same memory, then x and y are aliases of each other. If you deallocate memory that is referenced by one of them, then the other is also deallocated since it is the same memory.

- When you deallocate memory with delete, that memory should never be accessed. When you attempt to access deleted memory, it results in undefined behavior, which represents a logical error.

```cpp
int *list = new int[10];
// ... // Use list, then
// ...
delete [] list; // Deallocate list's memory
// ...
// Sometime later
// ...
int x = list[2]; // Logic error, but sometimes works!
```

The code fragment above illustrates how such a situation could arise. For the purpose of efficiency, the delete operator makes heap space available without modifying the contents in the memory.

## Resource Management

It is essential that programmers call clear immediately when they finish with a linked list object. Take a look at the following definition:

```cpp
void x() {

IntList1 my_list; // Constructor called here

// Add some numbers to the list

my_list.insert(12);

my_list.insert(7);

my_list.insert(-14);

// Print the list

my_list.print();

} // Oops! Forgot to call my_list.clear!
```

In the code above, the variable my_list is local to function x. When the function x finishes executing, the variable my_list will go out of scope. At this stage, the space on the stack allocated for the local IntList1 variable named my_list is reclaimed. Although the list's heap-allocated elements space remains, the only access the program can have to the memory is through my_list.head, but my_list no longer exists. This is a classic example of a memory leak. Observe that none of the classes we have designed so far apart from the IntList1 have this problem. However, C++ offers a way out for class designers to specify actions that have to occur at the end of an object's lifespan. A constructor executes code at the beginning of an object's existence. A destructor is a special method that executes immediately before the object stops existing. A destructor can also have the same name as its class with a tilde ~ prefix. Additionally, a destructor does not accept arguments. Code 9.2 shows how to add a destructor to a class and also add the previously suggested optimization of the length and clear methods.

### Code 9.2

```cpp
class IntList2 {

// The nested private Node class from before

public:

```
