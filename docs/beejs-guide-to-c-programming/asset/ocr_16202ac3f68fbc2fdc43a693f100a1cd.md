This is called a fence. So if you want all the writes in a thread to be visible elsewhere, you can put up a release fence in one thread and acquire a fence in another,¹⁰ like how atomic operations work.

Since a consume operation doesn't really make sense on a fence¹¹¹, memory_order_consume is treated as an acquire.

You can put up a fence with any specified order:

```
atomic_thread_fence(memory_order_signal_fence);
```

There's also a lighter version of the fence for use with signal handlers, called atomic_signal_fence().

It works the same way as atomic_thread_fence(), except:

+   - It only deals with visibility of values within the same thread; there is no synchronization with other threads.
- No hardware fence instructions are emitted.

If you want to be sure the effects of non-atomic operations (and relaxed atomic operations) are visible in the signal handler, you can use this fence.

The idea is that the signal handler is executing in this thread, not another, so this is a lighter-weight way of making changes outside the signal handler are visible within it (i.e. they haven't been reordered.
