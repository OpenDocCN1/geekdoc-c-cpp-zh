See how I pass the two incompatible pointers to fun()? One of the types is int32_t* and the other is struct words*.

But they both point to the same object: the 32-bit value at 0x12345678.

So if we look at the fields in the struct words, we see the two 16-bit halves of nhau. Right?

And in the fun() loop, we increment the pointer to the int32_t. That's it. Since the struct points to that same memory, it too, should be updated to the same value.

So let's run it and get this, with the 32-bit value and the two 16-bit portions on the right. It should match:

```
12345679, 12345679
1234567a, 1234567a
1234567b, 1234567b
1234567c, 1234567c
1234567d, 1234567d
```

and it does... UNTIL TOMORROW!

Let's try compiling GCC with -0 and -fstrict-aliasing:

```
12345679, 12345679
1234567a, 1234567a
1234567b, 1234567b
1234567c, 1234567c
1234567d, 1234567c
```

They're off by one! But they point to the same memory! How could this be? Answer: it's undefined behavior to alias memory like that. It is possible, not in a good way.

If your code violates aliasing rules, whether it works or depends on how someone decides to compile and that's a matter beyond your control. You're some kind of omnipotent god.

Unlikely, sorry.

GCC can be forced to not use strict aliasing rules with -fno-strict-aliasing. Compiling the program, above, with -0 and this flag causes the output to be as expected.
