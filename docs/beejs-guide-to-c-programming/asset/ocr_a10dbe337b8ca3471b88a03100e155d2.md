# # Manual Memory Allocation

This is one of the big areas where C likely diverges from languages you already know: *manual memory management.*

Other languages uses reference counting, garbage collection, or other means to determine when to allocate new memory for some data—and when deallocate it when no variables refer to it.

And that's nice. It's nice to not worry about it, to just drop all the references to an item and that at some point the memory associated with it will be freed.

But C's not like that, entirely.

Of course, in C, some variables are automatically allocated and deallocated when they come into scope and leave scope. These automatic variables—they're your run-of-the-mill block scope "local" variables. No problem.

But if you want something to persist longer than a particular block? This is where manual memory management comes play.

You can tell C explicitly to allocate for a number of bytes that you can use as you please. And these bytes will remain allocated until you free that memory¹.

It's important to free the memory you're done! If you don't, we call that a *memory leak* and your process will continue to run until memory is until.

If you manually allocate it, you have to manually free it when you're done with it.

So how do we do this? We're going to learn a new couple of functions, and use the `sizeof` operator to help us learn how many bytes to allocate.

In common parlance, devs say that automatic local variables are "on the stack", and manually-allocated memory is "on the heap". The spec doesn't talk about either of those things, but all C devs will know what you're talking about if you bring them up.

All functions we're going to use in this chapter can be found in `<stdlib.h>`.

# ##12.1 Allocating and Deallocating, `malloc()` and `free()`

The `malloc()` function accepts a number of bytes to allocate, and returns a void pointer to that block of newly-allocated memory.

> ¹Until the program exits, in which case all the memory allocated by it persists. Asterisk: some systems allow you to allocate memory that persists after a program exits, but it's system-dependent, out of scope for this, you'll certainly never do it on accident.
