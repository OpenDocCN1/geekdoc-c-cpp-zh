# Chapter 39. Multithreading

# 39.8 Condition Variables

Condition Variables are the last piece of the puzzle we need to make performant multithreaded applications and to compose more multithreaded structures.

A condition variable provides a way for threads to go to sleep until some event on another thread occurs.

In other words, we might have a number of threads that are going to wait, but they have to wait until some event is true before they're told "wait for it" until they get notified.

And this works hand-in-hand with mutexes since we're going to wait depends on the value of some data, and that data generally needs to be protected by a mutex.

It's important to note that the condition variable itself isn't the holder of any particular data from our perspective. It's the variable by which C keeps track of the waiting/not-waiting status of a particular thread or group of threads.

Let's create a program that runs in groups of 5 numbers from the main thread one at a time. Then, when 5 numbers have been entered, the child thread wakes up, sums up 5 numbers, and produces the result.

The numbers will be stored in a global, shared array, as will index into the array of the about-to-be-entered number

Since these are shared values, we have at least to hide them a mutex for both the main and child threads. (The main thread will write data to them and the child will be reading data from them.)

But that's not enough. The child thread needs to block "sleep" until 5 numbers have been read into the array. And the parent thread needs to wake up the child so it can do its work.

And when it wakes up, it needs to holding that mutex. And it will! When a thread waits on a condition variable, it also acquires a mutex when it wakes up.

All this takes place around an identical variable of type cnd_t that is the condition variable. We create this variable with the cnd_init() function and destroy it when we're done with it with the cnd_destroy() function.

But how does this work? Let's look at the outline of what the child thread will do:

+   1. Lock the mutex with mtx_lock()
2. If we haven't entered all the numbers, wait on the condition variable with cnd_wait()
3. Do the work that needs doing
4. Unlock the mutex with mtx_unlock()

Meanwhile the main thread will be doing:

+   1. Lock the mutex with mtx_lock()
2. Store the recently-read number into the array
3. If the array is full, signal the child to wake up with cnd_signal()
4. Unlock the mutex with mtx_unlock()

If you didn't skip that (OK—I'm not offended), you might notice something weird: how the main thread hold the mutex lock and signal the child, if the child has to hold the mutex lock to wait for the signal? They can't hold both the lock!

And indeed they do! There's behind-the-scenes magic with condition variables: when you cnd_wait(), it releases the mutex you specify and the thread goes to sleep. When someone signals that thread to wake up, it acquires the mutex as if nothing had happened.

It's a little different on the cnd_signal() side of things. This doesn't do anything with the mutex. The signaling thread must manually release the mutex before the waiting threads can wake up.
