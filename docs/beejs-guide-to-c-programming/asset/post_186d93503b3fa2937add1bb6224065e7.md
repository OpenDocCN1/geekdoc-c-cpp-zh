## 20.7 Fake OOP

There's a slightly obvious thing that's sort of OOP-like that you can do with structs.

Since the pointer to struct is the same as a pointer to the first element of the struct, you can freely cast a pointer to the struct to a pointer to the first element.

What this means is we can set up a situation like this:

```c
struct parent {
    int a, b;
};

struct child {
    struct parent super; // MUST be first
    int c, d;
};
```

Then we are able to pass a pointer to a struct child to a function that expects either that or a pointer to a struct parent!

Because parent super is the first item in the struct child, a pointer to any struct child is the same as a pointer to that super field.

Let's set up an example here. We'll make structs as above, but then we'll pass a pointer to a struct child to a function that needs a pointer to a struct parent... and it'll still work.

> super isn't a keyword, incidentally. I'm just stealing some OOP terminology.

## Chapter 20. structs II: More Fun with structs

```c
#include <stdio.h>

struct parent {
    int a, b;
};

struct child {
    struct parent super; // MUST be first
    int c, d;
};

// Making the argument void* so we can pass any type into it
// (namely a struct parent or struct child)
void print_parent(void *p)
{
    // Expects a struct parent-but a struct child will also work
    // because the pointer points to the struct parent in the first
    // field:
    struct parent *self = p;
    printf("Parent: %d, %d\n", self->super.a, self->super.b);
}

void print_child(struct child *self)
{
    printf("Child: %d, %d\n", self->c, self->d);
}
```

```c
int main()
{
    struct child c = {.super.a=1, .super.b=2, .c=3, .d=4};

    print_parent(&c);
    print_child(&c); // Also works even though it's a struct child
}
```

See what we did on the last line of main()? We called print_parent() but passed a struct child* as argument! Even though print_parent() needs the argument to point to a struct parent, we're getting away with it because the first field in the struct child is a struct parent.

Again, this works because a pointer has the same value as a pointer to the first field in struct.

All this hinges on part of the spec:

> §6.7.2.11 [...] A pointer to a structure object, suitably converted, points to its initial member [...], and vice versa.

and

> §6.7.5 An object shall have its stored value accessed only by an lvalue expression that has one of following types:

- * a type compatible with the effective type of the object
- [...]

and my assumption that "suitably converted" means "cast" to the effective type of the initial member.

## 20.8 Bit-Fields

In my experience, these are rarely used, but you might see them out there time to time, especially in lower-level applications that pack bits together into larger spaces.

Let's take a look at some code to demonstrate a use case:

```c
#include <stdio.h>

struct foo {
    unsigned int a;
    unsigned int b;
    unsigned int c;
    unsigned int d;
};
```

```c
int main(void) {
    printf("%u\n", sizeof(struct foo));
}
```

For me, this prints 16. Which makes sense, since unsigneds are 4 bytes on my system.

But if we know all the values that were going to be stored in a and b would be stored in 5 bits, and the values in c, and d would be stored in 3 bits? That's a total of 16 bits. Why have 128 bits reserved for them if we're only going to use 16?

Well, can we call C to pretty-pretty try to pack these values. We can specify the maximum number of bits that values can take (from 1 up to the size of the containing type).

We do this by putting a colon after the field name, followed by the width in bits.

```c
struct foo {
    unsigned int a:5;
    unsigned int b:5;
    unsigned int c:3;
    unsigned int d:3;
};
```

Now when I ask how big my struct foo is, it tells me 16 bytes, but it's only 4. It has "packed" those 4 values down into 4 bytes, which is a four-fold memory savings.

The tradeoff is, that the 5-bit fields can only hold values from 0-31 and the 3-bit fields can only hold values from 0-7. But life's all about compromise, after.

### 20.8.1 Non-Adjacent Bit-fields

Gotcha: C will only combine adjacent bit-fields. If they're interrupted by non-bit-fields, you get not only savings:

```c
struct foo {
    unsigned int a:1;
    // since a is not adjacent to c.
    unsigned int b;
    unsigned int c:1;
    unsigned int d;
};
```

In example, since a is not adjacent to c, they are both "packed" in their own towns.

So we have one each for a, b, c, and d. Since my ints are 4 bytes, the total is 16 bytes.

## 20.9 Unions

These are basically like structs, except the fields overlap in memory. The union will be large enough for the largest field, and you can use only one field at a time.

It's a way to reuse the same memory space for different types of data.

You declare them just like structs, except it's union. Take a look at this:

```c
union foo {
    int a, b, c, d, e, f;
    float g, h;
    char i, j, k, l;
};
```

### 20.9.1 Unions and Type Punning

You can non-portably write to one union field and read from another!
Doing so is type pun², and you'd use it if you really knew what you were doing, typically with some kind of low-level programming.
