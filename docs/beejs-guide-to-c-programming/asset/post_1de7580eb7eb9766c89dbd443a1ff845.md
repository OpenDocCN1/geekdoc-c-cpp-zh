## 26.2.1 Monetary Digit Grouping

OK, it is a trippy one. mon_grouping is a char*, so you might be thinking it's a string. In this case, no, it're an array of chars. It should always end with a theta or CHAR_MAX.

These values describe how group sets of numbers in currency to the *left* of the decimal (the whole number part).

For example, we might have:

```
2 1 0
-- ...
$100,000,000.00
```

These are groups of three. Group 0 (left of the decimal) has 3 digits. Group 1 (next group to the left) has 3 digits, and the last one has 3.

So we could describe these groups, from the right (the decimal) to the left with a bunch of integer values representing the group sizes:

```
3 3 3
```

And that would work for values up to $100,000,000.

But what if we had more? We could keep adding 3s...

```
3 3 3 3 3 3 3 3 3 3 3 3 3
```

but that's crazy. Luckily, we can set theta to indicate that the previous group size repeats:

```
3 0
```

Which means to repeat every 3. That would handle $100, $1,000, $10,000, $10,000,000, $100,000,000,000, and so on.

You can legitimately go crazy with these to indicate some weird groupings.

For example:

```
4 3 2 1 0
```

would indicate:

```
$1, 0, 0, 0, 000, 000, 0000.00
```

One more value that can occur is CHAR_MAX. This indicates that no more grouping should occur, and can appear anywhere in the array, including the first value.

```
3 2 CHAR_MAX
```

would indicate:

```
100000000, 00, 000.00
```

for example.

And simply having CHAR_MAX in the first array position would tell you there to be no grouping at all.

## 26.2.2 Separators and Sign Position

All the sep_by_space variants dealing with spacing around the currency sign. Valid values are:

| Value | Description |
| --- | --- |
| 0 | No space between currency symbol and value. |
| 1 | Separate the currency symbol (and sign, if any) from the value with a space. |
| 2 | Separate the sign symbol from the currency symbol (if adjacent) with a space, otherwise separate the sign symbol from the value with a space. |

The sign_posn variants are determined by the following values:

| Value | Description |
| --- | --- |
| 0 | Put parents around the value and the currency symbol. |
| 1 | Put the sign in front of the currency symbol and value. |
| 2 | Put the sign after the currency symbol and value. |
| 3 | Put the sign directly in front of the currency symbol. |
| 4 | Put the sign directly behind the currency symbol. |

| Macro | Description |
| --- | --- |

| LC_COLLATE | Controls the behavior of the strcoll() and strxfrm() functions. |

## 27.1 What is Unicode?

Back in the day, it was popular in the US-centric world to use 7-bit or 8-bit encoding for characters in memory. This meant we could have 128 or 256 characters (including non-printable characters) total. That was fine, but turned into compatibility nightmare. Chinese has over 50,000 characters, and that's not fitting in a byte. To escape it, Unicode was invented. One character to rule all. It extends out into infinity (effectively) we'll never run out of space for new characters. It has Latin, Greek, cuneiform, emojis... just about everything!

## 27.2 Code Points

I want to talk about two concepts here. It's confusing because they're both numbers for the same thing. But loosely define *code point* to mean a numeric value representing a character. Each code point represents a unique character. And each character has a numeric code point associated with it. For example, in Unicode, the numeric value 66 represents “B”, and 960 represents “n”. Other character mappings use different values, potentially, let’s forget them and concentrate on Unicode, the future! So there’s one thing: a number that represents each character. In Unicode, these numbers run from 0 to 1 million. Got it? Because we’re about to flip the table.

## 27.3 Encoding

If, an 8-bit can hold values from 0-255, inclusive. That’s great for “B” which is 66—that fits in a byte. But “n” is 960, and doesn’t fit in a byte! We need another byte. How do we store all that in memory? Or what about bigger numbers, like 195,024? That’s going to need a number of bytes to hold. The Big Question: how are these numbers represented in memory? This is what we call the encoding of characters. So we have two: the code point which tells us the serial number of a particular character. And the encoding which tells us we’re going to represent that number in memory. There are plenty of encodings. You can make up your own right now if you want! We’re going to look at some really common encodings that we use with Unicode.

| Encoding | Description |
| --- | --- |
| UTF-8 | A byte-oriented encoding that uses a variable number of bytes per character. This is the one we use. |
| UTF-16 | A 16-bit per character encoding. |
| UTF-32 | A 32-bit per character encoding. |

With UTF-16 and UTF-32, the byte order matters, so you might use UTF-16BE for big-endian and UTF-16LE for little-endian. Same for UTF-32. Technically, if unspecified, you should assume big-endian, but Windows uses UTF-16 extensively and little-endian, sometimes it is assumed. Let’s look at some examples. It’s good to write the values in exactly two digits per bit, and to see how things are arranged in memory.

| Character | Code Point | UTF-16BE | UTF-32BE | UTF-16LE | UTF-32LE | UTF-8 |
| --- | --- | --- | --- | --- | --- | --- |
| A | 41 | 0041 | 00000041 | 4100 | 410000041 | 41 |
| B | 42 | 0042 | 00000042 | 4200 | 420000042 | 42 |
| E | 7E | 007E | 0000007E | 7E00 | 7E00007E | 7E |
| π | 3C0 | 03C0 | 000003C0 | C003 | 0000C030 | CF80 |
| € | 20AC | 20AC | 000020AC | AC20 | 0000AC20 | E28AC |

Technically, it’s variable width—a way to represent code points higher than 2^16 by using two UTF-16 characters together.
