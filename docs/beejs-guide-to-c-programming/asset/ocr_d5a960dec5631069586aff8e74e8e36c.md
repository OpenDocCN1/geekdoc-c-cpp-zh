It's because of a mysterious phenomenon called a spurious wakeup. Sometimes, in some implementations, a thread can be woken up by a c_wait() sleep for seemingly no reason. [X-Files music]¹¹. And so we have to check that the condition is still met when we wake up. And if it's not, back to sleep with us!

So let's do this with the main thread:

+   * The main thread will set up the mutex and condition variable, and will launch the child thread.
* Then it will, in an infinite loop, get numbers as input from the console.
* It will also acquire the mutex to store the inputted number into a global array.
* When the array has 5 numbers in it, the main thread will signal the child thread that it's time to wake up and do its work.
* The main thread will unlock the mutex and go back to reading the next number from the console.

Meanwhile, the child thread has been up to its own shenanigans:

+   * The child thread grabs the mutex
* While the condition is not met (i.e. while the shared array doesn't yet have 5 numbers in it), the child sleeps by waiting on the condition variable. When it does, it unlocks the mutex.
* Once the main thread signals the child to wake up, it wakes up to do the work and gets the mutex lock back.
* The child sums the numbers and resets the variable that is the index into the array.
* It releases the mutex and runs again in an infinite loop.

And here's the code! Give it some try so you can see all the above pieces are being handled:

```
#include <stdio.h>
#include <threads.h>
```

```
#define VALUE_COUNT_MAX 5

int value[VALUE_COUNT_MAX]; // Shared global
int value_count = 0; // Shared global, too

mutex_t mtx_; // Mutex around value
cnd_t cnd_var_; // Condition variable on value

void *run(void *arg)
{
    (void)arg;

    for (;;) {
        mutex_lock(&mtx_); // <-- GRAB THE MUTEX

        while (value_count < VALUE_COUNT_MAX) {
            printf("Thread is waiting\n");
            cnd_wait(&cnd_var_, &mtx_); // <-- CONDITION VARIABLE
        }
    }
n}
```
