## 16.2.2.2 static in File Scope

When you get out of file scope, outside blocks, the meaning rather changes.

Variables at file scope also persist between function calls, so that behavior is already there.

Instead, static means in this context is that this variable isn't visible outside of this particular file. Kind like "global", but only in this file.

More on that in the section about building with multiple source files.

## 16.2.3 extern

The extern storage-class specifier gives us a way to refer to objects in other source files.

Let's say, the file bar.c had the following as its entirety:

```c
// bar.c

int a = 37;
```

Just that. Declaring a new int in a file scope.

But if we had another source file, foo.c, and we wanted to refer to the that's in bar.c?

It's easy with the extern keyword:

```c
// foo.c

int main(void)
{
    printf("%d\n", a); // 37, from bar.c!

    a = 99;

    printf("%d\n", a); // Same "a" from bar.c, but it's now 99
}
```

We could also made the extern int in a block scope, and it still would have referred to the a in bar.c.

```c
// foo.c

int main(void)
{
    extern int a;

    printf("%d\n", a); // 37, from bar.c!

    a = 99;

    printf("%d\n", a); // Same "a" from bar.c, but it's now 99
}
```

Now, if a in bar.c had been marked static, this wouldn't have worked. static variables at file scope are not visible outside that file.

A final note about extern on functions. For functions, extern is the default, so it's redundant. You can declare a function static if you only want visible in a single source file.

## 16.2.4 register

This is a keyword to hint the compiler that this variable is frequently-used, and should be made as fast as possible to access. The compiler is under no obligation to agree to it.

Now, modern C compiler optimizers are pretty effective at figuring out this themselves, so it's rare to see these days.

But if you must:

```c
#include <stdio.h>

int main(void)
{
    register int a; // Make "a" as fast to use as possible.

    for (a = 0; a < 10; a++)
        printf("%d\n", a);

}
```

It comes at a price, however. You can't take the address of a register

```c
register int a;
*p = &a; // COMPILER ERROR! Can't take address of a register
```

The same applies to any part of an array:

```c
register int a[] = {11, 22, 33, 44, 55};
*p = &a[0]; // COMPILER ERROR! Can't take address of a[0]
```

Dereferencing any part of an array:

```c
register int a[] = {11, 22, 33, 44, 55};
```

```c
int a = (a + 2); // COMPILER ERROR! Address of a[0]
```

Interestingly, for the equivalent with array notation, gcc only gives:

```c
register int a[] = {11, 22, 33, 44, 55};
```

```c
int a = a[2]; // COMPILER WARNING!
```

with:
warning: ISO C forbids subscribing 'register' array

The fact that you can't take the address of a register variable frees the compiler to make optimizations around assumption that it hasn't figured it out already. Also adding register to a const variable prevents from accidentally passing its pointer to another function that would ignore its 'const'¹².

A bit of historic back: inside the CPU are little dedicated "variables" called 'registers'. They are super fast to access RAM, so using them you get a speed boost. They're not in RAM, so they don't have an associated address (which is why you can't take the address of or get a pointer to them).

But, like I said, modern compilers are really good at producing optimal code, using registers regardless of whether or not you specified the register keyword. Not only that, but the spec allows them to just treat it as if you'd typed out, there are no guarantees.

> ²https://en.wikipedia.org/wiki/Processor_register

## 16.2.5 _Thread_local

When you're using multiple threads and you have some variables in either global or block scope, this is a way to make sure that each thread gets its own copy of the variable. This'll help you avoid race conditions and threads stepping on each other's toes.

If you're in block scope, you have to use this along with either extern or static.

Also, if you include <threads.h>, you can use the more palatable thread_local as an alias for _Thread_local.

More information can be found in the Threads section.

# Chapter 17. Multifile Projects

So far we've been looking at toy programs that fit in a single file. But complex C programs are made up of many files that are all compiled and linked together into a single executable.

## 17.1 Includes and Prototypes

A really common situation is that some of your functions are defined in one file, and you want to call them from another. This actually works out of the box with a warning... let's first try it and then look at the right way to fix the warning. To compile, you'll need to specify all the sources on the command line:

```bash
gcc -o foo bar.c
```

In these examples, foo.c and bar.c get built into the executable named foo. So let's take a look at the source file bar.c:

```c
// File bar.c
int add(int x, int y)
{
    return x + y;
}
```

And file foo.c with main in it:

```c
// File foo.c
#include <stdio.h>

int main(void)
{
    printf("%d\n", add(2, 3)); // 5!
}
```

If we build this with:

```bash
gcc -o foo bar.c
```
error: implicit declaration of function 'add' is invalid in C99(Or you might get a warning. Which you should not ignore. Never ignore warnings in C; address them all.) If you recall the section on prototypes, implicit declarations are banned in modern C and there's legitimate reason to introduce them into new code. What implicit declaration means that we're using a function, add() in this case, without letting C know about it ahead of time. C wants to know what it returns, what types it takes and such things. We saw how that earlier with a function prototype. Indeed, if we add one of foo.c before the call, everything works well:

```c
// File foo.c
#include <stdio.h>

int add(int, int); // Add the prototype

int main(void)
{
    printf("%d\n", add(2, 3)); // 5!
}
```

No more error! But that's a pain—needing to type in a prototype every time you want to use a function. I mean we used printf() right there and didn't need to type in a prototype; what gives? If you remember from back with hello.c at the beginning of the book, we actually did include the prototype for printf() It's in the file std.h! And we included that with. Can we do this with our add() function? Make a prototype for it and put it in a header file? Sure!

Header files in C have a .h extension by default. And they often, but not always, have the same name as the corresponding .c file. So let's make a bar.h for our bar.c file and we'll stick the prototype in it:

```c
// File bar.h
int add(int, int);
```

Now let's modify foo.c to include that file. Assuming it's in the same directory, we include it inside double quotes (as opposed to angle brackets):

```c
// File foo.c
#include <stdio.h>
#include "bar.h" // Include from current directory

int main(void)
{
    printf("%d\n", add(2, 3)); // 5!
}
```

Notice how we don't have the prototype in foo.c anymore—we included it from bar.h. Now any file that adds (add) functionality can #include "bar.h" to get it, and you don't need to worry typing in the prototype.

As you have guessed, #include literally includes the named file right there in your source code, just if you'd typed it in.

And building and running:

```bash
./foo
```

Indeed, we get the result of 2 + 3! Yay! But don't crack your drink of code yet. We're almost there! There's just one more piece of boilerplate we have to add.

## 17.2 Dealing with Repeated Includes

It's not uncommon that a header file will #include other headers needed for the functionality of its corresponding C files. I mean, why not? And it could be that you have a header included multiple times from different places. Maybe there's no problem, but it would cause compiler errors. And we can't control how many places #include it! Even worse when we get into a crazy situation header a.h includes header b.h, and b.h includes a.h. It's an #include infinite cycle! Trying to build such a thing gives an error:

```bash
error: #include nested depth 200 exceeds maximum of 200
```

What we need to do is that if a file gets included once, subsequent includes for file are ignored. The stuff that we're about to do is so common that we should automatically do it every time we make a header file! And the common way to do this is with a preprocessor variable that we set the first time we include the file. And for subsequent includes, we first check to make sure that the variable isn't defined. For variable name, it's super common to use the name of the header file, like bar.h, make it uppercase, and replace the period with an underscore: BAR_H.

(Don't put a leading underscore (a leading underscore followed by a capital letter is reserved) or a double leading underscore (because that's also reserved).

```c
#ifndef BAR_H // IF BAR_H isn't defined...
#define BAR_H // Define it (with no particular value)
```

```c
// File bar.h
int add(int, int);
```
