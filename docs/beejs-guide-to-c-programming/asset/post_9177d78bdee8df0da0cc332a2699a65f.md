## 39.7.1 Difference Mutex Types

As hinted, we have a few mutex types that you can create with mtx_init(). (Some of these types are the result of a bitwise-OR operation, as noted in the table.)

| Type | Description |
| --- | --- |
| mtx_plain | Regular ol' mutex |
| mtx_timed | Mutex that supports timeouts |
| mtx_plain|mtx_recursive | Recursive mutex |
| mtx_timed|mtx_recursive | Recursive mutex that supports timeouts |

"Recursive" means the holder of a lock can call mtx_lock() multiple times on the same lock. They have to unlock an equal number of times before anyone else can take the mutex. This might ease coding from time, especially if you call a function that needs to lock the mutex when you already hold the mutex.

And the timeout gives a thread a chance to get the lock for a while, but then bail out if it can't get it in that timeframe.

For timeout mutex, be sure to create it with mtx_timed:
mtx_init(&serial_mtx, mtx_timed);

And when you want it, you have to specify a time in UTC when it will unlock.

The function times_get() from <time.h> can be of assistance here. It'll get the current time in UTC in a struct timespec which what we need. In fact, it seems to exist merely for this purpose.

It has two fields: tv_sec has the current time since epoch, and tv_nsec has the nanoseconds (billions of a second) as the "fractional" part.

So you can use the current time, and add it to get a specific timeout.
Then call mtx_timedlock() instead of mtx_lock(). If it returns the value thrd_timeout, it is timed out.
struct timespec;

```
timespec_get(&timeout, UTC);    // Get current time
timeout.tv_sec += 1;                   // Timeout 1 second after now
```

```
int result = mtx_timedlock(&serial_mtx, &timeout);

if (result == thrd_timeout) {
    printf("Mutex lock timed out!\n");
}
```

Other than that, timed locks are the same as regular locks.

> You might have expected it to be "time from now", but you'd just like to think that, wouldn't!

## 39.8 Condition Variables

Condition Variables are the last piece of the puzzle we need to make performant multithreaded applications and to compose more multithreaded structures.

A condition variable provides a way for threads to go to sleep until some event on another thread occurs.

In other words, we might have a number of threads that are going to wait, but they have to wait until some event is true before they're told "wait for it" until they get notified.

And this works hand-in-hand with mutexes since we're going to wait depends on the value of some data, and that data generally needs to be protected by a mutex.
