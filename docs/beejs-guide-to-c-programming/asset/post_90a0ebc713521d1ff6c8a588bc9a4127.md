### 27.11.2 UTF-16, UTF-32, char16_t, and char32_t

char16_t and char32_t are a a couple potentially wide character types with sizes of 16 bits and 32 bits, respectively. Not necessarily wide, because if they can't represent every character in the current locale, they lose their wide nature. The spec refers to them as "wide character" types all over the place, so there we are.

These are here to make things a little Unicode-friendly.

To include, `<cuchar.h>`. (That's "u", not "uw").

This header file doesn't exist on OS X—yet. If you just want the types, you can:

```c
#include <stddef.h>

typedef int_least16_char16_t;
typedef int_least32_char32_t;
```

But if you also want the functions, they're all on you.

Assuming you're still good to go, you can declare a string or character of these types with the u and u prefixes:

```c
char16_t *s = u"Hello, world!";
char16_t *c = u"B";
char32_t *t = u"Hello, world!";
char32_t d = u"B";
```

Now—are values used in these stored in UTF-16 or UTF-32? Depends on the implementation.
But you can test to see if they are. If the macros `__STDC_UTF_16__` or `__STDC_UTF_32__` are defined (to 1) it means the types hold UTF-16 or UTF-32, respectively.
If you're curious, and (as I know the values) if UTF-16 or UTF-32, are stored in the native endianness, that you should be able to compare them straight against Unicode code point values:

```c
char16_t pi = u"\u03BC"; // pi symbol
#if __STDC_UTF_16__
pi == 0x03BC; // Always true
#else
pi == 0x030; // Probably not true
#endif
```

You can convert your multibyte encoding to char16_t or char32_t with a number of helper functions.
(Like I said, though, the result might not be UTF-16 or UTF-32 unless the conversion macro is set to 1).
All of these functions are restartable (i.e. you pass in your own `mbstate_t`), and all of them operate character by character.

| Conversion Function | Description |
|---|---|
| mbrtoc16() | Convert a multibyte character to a char16_t character. |
| mbrtoc32() | Convert a multibyte character to a char32_t character. |

## Exiting a Program

Turns out there are a lot of ways to do this, and even ways to set up "hooks" so that a function runs when a program exits.

In this chapter we'll dive in and check them out.

We already covered the meaning of the exit status code in the Exit Status section, jump back there and review if you have to.

All the functions in this section are in `<stdlib.h>`.

### 28.1 Normal Exits

We'll start with the regular ways to exit a program, and then jump to some of the rarer, more esoteric ones.

When you exit a program normally, all open I/O streams are flushed and temporary files removed. Basically it's a nice exit where everything cleaned up and handled. It's what you want to do almost all the time you have reasons to do otherwise.

### 28.1.1 Returning From main()

If you've noticed, normally, all return has a type of int... and you've lately, if ever, returning anything from main() at all.

This is for main() only (and I can't stress this special case only applies to main() and no other functions) have an implicit return if you fall off the end.

You can explicitly return from main() any time you want, and some programmers feel it's more Right to always have a return at the end of main(). But if you leave it, C will put one for you.

So... here are the rules for main():

- You can exit a status from main() with a return statement. main() is the only function with this special behavior. Using return in any other function just returns from function to the caller.
- If you don't explicitly return and just fall off the end of main(), it's just as if you'd returned or EXIT_SUCCESS.

### 28.1.2 exit()

This one has also made an appearance a few times. If you call exit() from anywhere in your program, will exit at that point.

The argument you pass to exit() is the exit status.

### 28.1.3 Setting Up Exit Handlers with atexit()

You can register functions when a program exits whether by returning from main() or calling the exit() function.

A call to atexit() with the handler function name will get it done. You can register multiple exit handlers, and they'll be called in the reverse order of registration.

Here's an example:

```c
#include <stdio.h>
#include <stdlib.h>

void exit_1(void) {
    printf("handler 1\n");
}

void exit_2(void) {
    printf("handler 2\n");
}

int main() {
    atexit(exit_1);
    atexit(exit_2);
    return 0;
}
```
Output:
```
handler 2
handler 1
```

## Signal Handling

Before we start, I'm just going to advise you to generally ignore this entire chapter and use your OS’s (very likely) signal handling functions. Unix-likes have the sigaction() family of functions, and Windows has... whatever it does.

With that out of the variety, what are signals?

### 29.1 What Are Signals?

A signal is raised on a variety of external events. Your program can be configured to be interrupted to handle the signal, and optionally, continue where it left off once the signal has been handled.

Think of it like a function that is automatically called when one of these events occurs.

What are these events? On your system, there are probably a lot of them, but in the C spec there are just a few:

| Signal | Description |
|---|---|
| SIGABRT | Abnormal termination—what happens when abort() is called. |
| SIGFPE | Floating point exception. |
| SIGILL | Illegal instruction. |
| SIGINT | Interrupt—usually the result of CTRL-C being hit. |
| SIGSEGV | “Segmentation Violation”: invalid memory access. |
| SIGTERM | Termination requested. |

You can set up your program to ignore, handle, or allow the default action for each of these by using the signal() function.

### 29.2 Handling Signals with signal()

The signal() takes two parameters: the signal in question, and an action to take when that signal is raised.

The action can be one of three:

- A pointer to a handler function.
