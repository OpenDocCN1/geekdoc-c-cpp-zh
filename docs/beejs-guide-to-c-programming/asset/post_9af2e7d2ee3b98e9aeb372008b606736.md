## 23.2 Multibyte Values

We kinda had this version in a variety of places earlier, but clearly not every value can be stored in a single byte of memory. Things take multiple bytes of memory (assuming they're not chars). You can tell how many bytes by `sizeof`. And you can tell which address in memory is the first byte of the object by using the standard `&` operator, which returns the address of the first byte.

And here's another fun fact! If you iterate over the bytes of any object, you get its object representation. These things with the object representation in memory are equal.

If you want to iterate over the object representation, you should do it with pointers to unsigned char.

Let's make our version of memory(5) that does exactly this:

```c
void *memcopy(void *dest, void *src, size_t n)
{
    // Make local variables for src and dest, but of type unsigned char
    unsigned char *s = src;
    unsigned char *d = dest;

    while (n-- > 0) // For the given number of bytes
        *d++ = *s++; // Copy source to dest byte

    // Most copy functions return a pointer to the dest as a convenience
    // to the caller

    return dest;
}
```

(There are some good examples of post-increment and post-decrement in there for you to study, as well.)

It's important to note that the version, above, is probably less efficient than the one that comes with your system.

But you can pass pointers to anything into it, and it'll copy these objects. Could be int, struct animal*, or anything.

Let's do another example that prints out the object representation bytes of a struct we can see if there's any padding in there and what it holds(6).

```c
#include <stdio.h>
```

```c
struct foo {
    char a;
    int b;
};

int main(void)
{
    struct foo x = {0x12, 0x12345678};
    unsigned char *p = (unsigned char *)&x;

    for (size_t i = 0; i < sizeof(x); i++) {
        printf("%02x\n", p[i]);
    }
}
```

> ^5 https://beej.com/guide/bglcr/html/split/stringref.html#man-memcopy
^6Your compiler is not required to add padding bytes, and the values of any padding bytes that are added are indeterminate.

What we have here is a struct foo's built in such a way that encourage a compiler to inject padding bytes (though it doesn't). And then we get an unsigned char * to the first byte of the struct foo variable x.

From here all we need to know the `sizeof x` and we can loop through many bytes, printing out the values (in hex for ease).

Running this gives a bunch of numbers as output. I have annotated it below to identify where the values were stored:

| Value | Description |
| :--- | :--- |
| x.a == 0x12 | AB |
| | BF | padding bytes with "random" |
| | 26 |
| | 78 |
| | 56 | x.b == 0x12345678 |
| | 34 |
| | 12 |

On all systems, `sizeof(char)` is 1, and we see first byte at the top of the output holding the value 0x12 that we stored.

Then we have padding bytes—for me, we can see those 4 bytes at the end. Notice how they're the same bytes as are in the hex value 0x12345678, but strangely in reverse order.

So that's a little peek under the hood of a more complex entity in memory.

## 23.3 The NULL Pointer and Zero

These things can be used interchangeably:

- * NULL
- '\0'
- (void)*

Personally I always use NULL when I mean NULL, but you might see some other variants from time to time. Though '\0'' (with all bits set to zero) will also compare equal, it's *weird* to compare it to a pointer; you should compare NULL the pointer. (Of course, lots times in string processing, you're comparing the pointer pointers to '\0', and that's right).

0 is called the null pointer constant, and when compared to or assigned to another pointer, it is converted to a null pointer of the same type.

## 23.4 Pointers as Integers

You can cast pointers to integers and vice-versa (since a pointer is just an index into memory), but you only ever need to do this if you're doing some low-level hardware stuff. The results of such machinations are implementation-defined, so they aren't so. And *weird* things could happen.

> This will vary depending on the architecture, but my system is little endian, which means the least-significant byte of the number is stored first. Big endian systems will have the 12 first and the 78 last. But the spec doesn't dictate anything about this representation.

C makes one guarantee, though you can convert a pointer to a `uintptr_t` type and you'll be able to convert it back to a pointer without losing any data.

`uintptr_t` is defined in `<stdint.h>`.

Additionally, if you feel like being signed, you can use `intptr_t` to cause the same effect.

## 23.5 Casting Pointers to other Pointers

There's only one safe pointer conversion:

- 1. Converting to `intptr_t` or `uintptr_t`.
- 2. Converting to and `void*`.

TWO! Two safe pointer conversions.

- 3. Converting to and `char*`.

THREE! Three safe conversions!

- 4. Converting and a pointer to a struct and a pointer to its first member, and vice-versa.

FOUR! safe conversions!
If you cast to a pointer of another type and access the object it points to, the behavior is undefined due to something called *strict aliasing*.

Plain old *aliasing* refers to the ability to have more than one way to access the same object. The access points are aliases for each other.

Strict aliasing says you are only allowed to access an object via compatible types to that object.

For example, this is defined as:

```c
int a = 1;
int *p = &a;
```

p is a pointer to an int, and it points to a compatible.
