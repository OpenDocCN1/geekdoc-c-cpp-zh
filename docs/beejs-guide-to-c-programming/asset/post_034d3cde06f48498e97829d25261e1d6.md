```
call_once() thrd_create() thrd_join()
mtx_lock() mtx_timedlock()
mtx_timedlock() mtx_trylock()
malloc() calloc()
aligned_alloc() dealloc() realloc()
```

call_once()—Synchronizes with all subsequent calls to call_once() for a particular flag. This way subsequent calls can be assured that if another thread sets the flag, you will see it.

thrd_create()—Synchronizes with the beginning of the new thread. The new thread can be sure it sees all shared memory writes from the parent thread before the thrd_create().

thrd_join()—When a thread dies, it synchronizes with this. The thread that has called thrd_join() can be assured that it sees all the latest thread shared writes.

mtx_lock()—Earlier calls to mtx_unlock() on the same mutex synchronize. This is the case that mirrors the acquire-release process we've already talked about. mtx_unlock() performs a release on the mutex variable, any subsequent thread that makes an acquire with mtx_lock() can see all shared memory changes in the critical section.

mtx_timedlock() and mtx_trylock()—Similar to the synchronization with mtx_lock(), if this succeeds, earlier calls to mtx_unlock() synchronize with this one.

**Dynamic Memory Functions**: If you allocate memory, it synchronizes with the previous deallocation of that same memory. All allocations and deallocations of that particular memory region in a single total order that all threads can agree upon. Use at will! They're consistent with the atomic aliases used in C++, if that helps.
But if you want more?

You can do either with a type qualifier or type specifier.
First, specifier! It's the keyword _Atomic with a type in parents⁵—suitable for use with typedef:
```c
typedef _Atomic(double) atomic_double;

atomic_double f;
```

Restrictions on the specifier: the type you're making atomic can't be of array or function, nor can it atomic or otherwise qualified.
Next, qualifier! It's the keyword _Atomic without a type in parents.
So do similar things⁶:

```c
_Atomic(int); // type specifier
_Atomic(int); // type qualifier
```

The thing is, you can include other type qualifiers:
`Atomic volatile int k;`
Restrictions on the qualifier: the type you're making can't be of array or function.

## 40.9 Lock-Free Atomic Variables

Hardware architectures are limited in the amount of data they can atomically read and write. It depends on how it was wired. And it varies.
If you use an atomic type, you can ensure that accesses to it will be atomic... but there's a catch: if hardware can't do it, it's done with a lock instead.

⁵C++23 is adding this as a macro.
⁶The spec notes that they might differ in size, representation, and alignment.

Atomic access becomes a lock, which is rather slower and has some implications for signal handlers. Atomic flags are the only atomic type guaranteed to be lock-free in all implementations. In typical desktop world, larger types are likely lock-free.

First of all, some macros—you can use these at compile time with #if. They apply to signed and unsigned types.

| Atomic Type | Lock Free Macro |
| :--- | :--- |
| atomic_bool | ATOMIC_BOOL_FREE |
| atomic_char | ATOMIC_CHAR_FREE |
| atomic_char16_t | ATOMIC_CHAR16_T_FREE |
| atomic_char32_t | ATOMIC_CHAR32_T_FREE |
| atomic_wchar_t | ATOMIC_WCHAR_FREE |
| atomic_short | ATOMIC_SHORT_FREE |
| atomic_int | ATOMIC_INT_FREE |
| atomic_long | ATOMIC_LONG_FREE |
| atomic_llong | ATOMIC_LLONG_FREE |
| atomic_intptr_t | ATOMIC_POINTER_FREE |

These macros can have three different values:

| Value | Meaning |
| :--- | :--- |
| 0 | Never lock-free. |
| 1 | Sometimes lock-free. |
| 2 | Always lock-free. |

Wait—how can something be lock-free? This means the answer isn't known at compile-time, but could be known at runtime. Maybe the answer varies on whether you're running this code on Intel or AMD, or something like that. But you can also test at runtime with `atomic_is_lock_free()`. This function returns true or false if the particular type is atomic.

So why do we care? Lock-free is faster, so maybe there's a speed concern you'd code around. Maybe you need to use an atomic variable in a signal handler.

## 40.9.1 Signal Handlers and Lock-Free Atoms

If you read or write a shared variable (static duration or `Thread_local`) in a signal handler, it has undefined behavior... Unless you do one of the following:

- Read a variable of `volatile sig_atomic_t`.
- Read or write a lock-free atomic variable.

As far I can tell, lock-free atomic variables are one of the few ways you get information out of a signal handler.

I just pulled that example out of nowhere. It doesn't matter on Intel/AMD, but it could matter somewhere, dangit!

The spec is vague, in my read, about the memory order when it comes to acquiring or releasing atomic variables in the signal handler. C++ says, and it makes sense, that accesses are unsequenced with respect to the rest of the program. The signal can be raised, after all, at any time. I'm assuming C's behavior is similar.

## 40.10 Atomic Flags

There's only one type the standard guarantees be lock-free: `atomic_flag`. This is an opaque type for test-and-set operations.

It can be either set or clear. You can initialize it to clear:

```c
atomic_flag f = ATOMIC_INIT;
```

You can set the flag atomically with `atomic_flag_test_and_set()`, which will set the flag and return its previous status as a Bool (true for set).

You can clear the flag atomically with `atomic_flag_clear()`.

Here's an example where we init the flag, set it twice, then clear it again.

```c
#include <stdio.h>
#include <stdbool.h>
#include <atomic.h>

atomic_flag f = ATOMIC_INIT;

int main(void) {
    bool r = atomic_flag_test_and_set(&f);
    printf("Value: %d\n", r); // 0

    r = atomic_flag_test_and_set(&f);
    printf("Value: %d\n", r); // 1

    atomic_flag_clear(&f);
    r = atomic_flag_test_and_set(&f);
    printf("Value: %d\n", r); // 0
}
```

## 40.11 Atomic structs and unions

Using the _Atomic qualifier or specifier, you can make atomic structs or unions! Pretty astounding.

If there's not a lot of data in there (a handful of bytes), the resulting atomic type may be lock-free. Test it with `atomic_is_lock_free()`.

```c
#include <stdio.h>
#include <atomic.h>

int main(void) {
    struct point {
        float x, y;
    }
```
