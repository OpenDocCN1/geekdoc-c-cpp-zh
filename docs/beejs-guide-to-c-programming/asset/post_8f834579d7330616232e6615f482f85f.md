
# Chapter 14. Types II: Way More Types!

On my system, FLT_DIG is 6, so I can be sure that if I print out 6 digit float, I'll get the same thing back.(It could be more digits—some will come back with more digits. But 6 is definitely coming back.)

For example, printing out floats following this pattern of increasing digits, we apparently made it to 8 digits before something goes wrong, but that we're back to 7 correct digits.

```
0.12345
0.123456
0.1234567
0.12345678
0.123456791 <-- Things start wrong
0.1234567910
```

Let's do another demo. In this code we have two floats that both numbers have FLT_DIG significant digits¹². Then we add them together, for what should be 12 significant digits. But that's more than we can store in a float and recover as a string—so when we print it out, thing starts going wrong after the 7th significant digit.

```c
#include <stdio.h>
#include <float.h>

int main(void) {
    // Both these numbers have 6 significant digits, so they can be
    // stored accurately in a float:

    float f = 3.14159f;
    float g = 0.000002653538;

    printf("%.5f\n", f); // 3.14159 correct!
    printf("%.11f\n", g); // 0.000002653538 correct!

    // Now add them up
    f += g;                // 3.141592653538 is what f _should_be

    printf("%.11f\n", f); // 3.141592653724101 wrong!
}
```

(The above code has an f over the numeric constants—this indicates that the constant is float, as opposed to the double of double. More on this later.)

Remember that FLT_DIG is the safe number of digits you can store in a float. Sometimes you get one or two out of it. But sometimes you'll get FLT_DIG digits back. The sure thing is: if you store any number of digits up and including FLT_DIG in a float, you're sure to get them back correctly.

So's the story. FLT_DIG. The End.
...Or is it?

## 14.4.2 Converting to Decimal and Binary

But storing a base 10 in a floating point number and getting it out is only half the story.

> ¹²This program runs as its comments indicate on a system with FLT_DIG of 6 that uses IEEE-754 base-2 floating point numbers. Otherwise, you might get different output.

Turns out floating point numbers can encode numbers that require more decimal places to print completely. It's just your big decimal number might not map to one of those.

That is, when you look at floating point numbers from one to the next, there's a gap. If you try to encode a decimal in that gap, you'll use the closest floating point number. That is why you can only encode FLT_DIG for a float.

But what about floating point numbers that aren't in the gap? How many places do you need to print those out accurately?

Another way to phrase this question is for any given floating point number, how many decimal digits do I have to preserve if I convert the decimal number back into an identical floating point number? That is, how many digits do I have to print in base 10 to recover all the digits in base 2 in the original number?

Sometimes it might only be a few. But to be sure, you'll want to convert to decimal with a certain safe number of decimal places. Number is encoded in the following macros:

| Macro | Description |
|---|---|
| FLT_DECIMAL_DIG | Number of decimal digits encoded in a float. |
| DBL_DECIMAL_DIG | Number of decimal digits encoded in a double. |
| LDBL_DECIMAL_DIG | Number of decimal digits encoded in a long double. |
| DECIMAL_DIG | Same as the widest encoding, LDBL_DECIMAL_DIG. |

Let's see an example where DBL_DIG is 15 (so that we have a constant), but DBL_DECIMAL_DIG is 17 (so we have to convert to 17 decimal numbers to preserve all the bits of the original double).

Let's assign 15 digits to 0.123456789012345 to x, and let's assign the 1 significant digit number 0.0000000000000006 to y.

```
x is: 0.123456789012345      Printed to 17 decimal places
y is: 0.0000000000000006
```

But let's add them together. let's look: 0.12345678901234536, but that's more than DBL_DIG, so strange things might happen.

```
x + y = not quite right: 0.12345678901234559      Should end in 4560!
```

What's we get for printing more than DBL_DIG, right? But check this out... that number above, is exactly representable as it is! If we assign 0.12345678901234559 (17 digits) to z and print, we get:
z is: 0.12345678901234559      17 digits correct!

But then,-- if we truncated z down to 15 digits, it wouldn't have the same value. To preserve all the bits of a double, we need DBL_DECIMAL_DIG and not just DBL_DIG.

All said, it's clear that we're messing with decimal numbers in general, it's not safe to print more than FLT_DIG, DBL_DIG, or LDBL_DIG to be sensible in relation to the original base and any subsequent. But when converting from float to a decimal representation and back to float, definitely use FLT_DECIMAL_DIG to do so that all the bits are preserved.

## 14.5 Constant Types

When you write down a constant, like 1234, is what type? Let's look what type the constant is, and how to force it to choose a specific type.

### 14.5.1 Hexadecimal Octal

In addition to decimal, C also supports constants of different bases. If you lead a number with 0x, it is read as a hex number:

```c
int a = 0xA2B; // Hexadecimal
int b = 0xa2b; // Case doesn't matter for digits
printf("%x", a); // Print hex number, "a2b"
```

If you lead a number with 0, it is read as octal number:

```c
int a = 012;
printf("%o\n", a); // Print octal number, "12"
```

This is particularly problematic for beginners who try to pad decimal numbers on the left to line up nice, inadvertently changing the base of the number:

```c
int x = 11111; // Decimal 11111
int y = 01111; // Decimal 73 (Octal 111)
int z = 011111; // Decimal 55 (Octal 111)
```

### 14.5.1.1 A Note on Binary

An unofficial extension in many compilers allows you to represent a binary number with a 0b prefix:

```c
int x = 0b101010; // Binary 101010
printf("%d\n", x); // Prints 42 decimal
```

There's no printf() format specifier for printing a binary number. You have to do it with bitwise operations.

### 14.5.2 Integer Constants

You can force an integer to be a certain type by adding a suffix to it that indicates the type. We have some assignments to demo but most often the suffix is not needed to be precise. The compiler is pretty good at making types compatible.

```c
int x = 1234;
long int x = 1234L;
long long int x = 1234LL;
unsigned int x = 1234U;
unsigned int x = 1234UL;
unsigned long int x = 1234LLU;
```

The suffix can be uppercase or lowercase. The U and L or LL can appear either first.

| Type | Suffix |
|---|---|
| int | None |
| long int | L |
| long long int | LL |

> ¹³It's really surprising that C doesn't have this in the spec. In the C99 Rationale document, they write, "A proposal to add binary constants was rejected due to lack of precedent and insufficient utility." Which seems kind of silly in light of some of the other features they kitchen-sinked in there! I'll bet one of the next releases has it.

| Type | Suffix |
|---|---|
| unsigned int | U |
| unsigned long int | UL |
| unsigned long int | ULL |

I mentioned in the table that “no suffix” means int... but it’s actually more complex than that. So what happens when you have an unsuffixed number like:

```c
int x = 1234;
```

What type is it?

What C will generally do is choose the smallest type from int that can hold the value. But specifically, that depends on the number’s base (decimal, hex, or octal). The spec has a great table indicating which type gets used for what unsuffixed value. In fact, I’m just going to copy it whole right here.

C11 §6.4.4.1 reads, “The type of an integer constant is the first of the corresponding list in which its value can be represented.”

And then goes on to show this table:

| Suffix | Decimal Constant | Octal or Hexadecimal Constant |
|---|---|---|
| none | int long int | int unsigned int long int unsigned long int unsigned long long int |
| u or U | unsigned int unsigned long int unsigned long long int | unsigned int unsigned long int unsigned long int unsigned long long int |
| l or L | long int long int | long int unsigned long int long int unsigned long long int |
| both u or U and l or L | unsigned long int unsigned long long int | unsigned long int unsigned long long int |
| ll or LL | long int | long int long int unsigned long long int |
| both u or U and ll or LL | unsigned long int unsigned long long int | unsigned long int unsigned long long int |

What’s saying that is, for example, if you specify a number like 123456789U, first C will see if it is unsigned int. If it doesn’t fit it, it’ll try unsigned long int. And then unsigned long long int. It’ll use the smallest type that can hold the number.
