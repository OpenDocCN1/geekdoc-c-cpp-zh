In a multithreaded scenario, we might have something like this pseudocode:

```
int x = 0, y = 0;
```

```
thread1() {
    x = 2;
    y = 3;
}
```

```
thread2() {
    while (y != 3) {} // spin
    printf("x is now %d\n", x); // 2? ...or 0?
}
```

What is the output from thread 2?

Well, if x gets assigned 2 before y is assigned 3, then I'd expect the output to be the very sensible:

x is now 2

Two threads synchronize when they agree on the state of shared memory. As we see, they're not always in agreement with the code. So how do they agree?

Using atomic variables can force the agreement¹. If a thread writes to an atomic variable, it's saying "anyone who reads this variable will also see all the changes I made to memory (atomic or not) up and including the atomic variable.

Or, in more human terms, let's sit around the conference table and make sure we're on the same page as to pieces of shared memory hold values. You agree the memory changes you've made up-to-and the atomic store will be visible to me after I do a load of the same atomic variable.

So we can easily fix our example:

```
int x = 0;
atomic int y = 0; // Make atomic
```

```
thread1() {
    x = 2;
    y = 3; // Synchronize on
}
```

```
thread2() {
    while (y != 3) {} // Synchronize on read
    printf("x is now %d\n", x); // 2, period.
}
```

Because the threads synchronize across y, all writes in thread 1 that happened before the write to y are visible in thread 2 after the write from y (the while loop).

It's important to note a couple of things:

- 1. Nothing sleeps. The synchronization is not a blocking operation. Both threads are running full bore until they exit. Even the one in the spin loop isn't blocking anyone from running.
- 2. The synchronization happens when one thread reads an atomic variable another thread writes. When thread 2 reads, all previous memory writes in thread 1 (namely setting x) will be visible in thread 2.
- 3. Notice that x isn't atomic. That's BECAUSE we're not synchronizing over x, and the synchronization over y when we write in thread 1 means that all previous writes—including x—in thread 1 will become visible to other threads... if those threads read y to synchronize.

Forcing synchronization is inefficient and can be a lot slower than using a regular variable. This is why we don't use atomics unless we have to for a particular application.

## 40.4 Acquire and Release

More terminology! It'll pay off to learn this now.

When a thread reads an atomic variable, it is said to be an acquire operation.

When a thread writes an atomic variable, it is said to be a release operation.

What are these? Let's line them up with terms you already know when it comes to atomic variables:

**Read = Load** — Acquire. When you compare an atomic variable or read it to copy it to another variable.
**Write = Store** — Release. When you assign a value into an atomic variable.

When using atomics with these acquire/release semantics, C spells out what can happen when.

Acquire/release form the basis for the synchronization we just talked about.

When a thread reads an atomic variable, it can see values set in another thread that released that variable.

In other words:

When a thread reads an atomic variable, it can see values set in another thread that wrote to that same variable.

The synchronization happens across the acquire/release pair.

More details:

With read/acquire of a particular atomic variable:

- * All writes (atomic or non-atomic) in another thread that happened before that other thread wrote/stored this atomic variable are now visible in this thread.
- The new value of the atomic variable by the other thread is also visible in this thread.
- No reads or writes of any variables/memory in the current thread can be reordered to before this acquire.
- The acquire acts as a one-way barrier when it comes to code reordering; reads and writes in the current thread can be moved down from before the acquire to after it. But, more importantly for synchronization, nothing can move up from after the acquire to before it.

With write/store/release of a particular atomic variable:

- All writes (atomic or non-atomic) in the current thread that happened before this release become visible to other threads that have read/loaded/acquired the same atomic variable.
- The value written to this atomic variable by this thread is visible to other threads.
- No reads or writes of any variables/memory in the current thread can be reordered after this release.
- The release acts as a one-way barrier when it comes to code reordering; reads and writes in the current thread can be moved down from before the release to after it. But, more importantly for synchronization, nothing can move up from after the release to before it.
