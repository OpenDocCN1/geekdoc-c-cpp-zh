## 2.2.6.1 Script Breakdown

BaseInputController.cs derives from MonoBehaviour.

```cs
public class BaseInputController : MonoBehaviour
{}
```

The input scripts use CheckInput() as their default main update function, which is intended to be called from the player class. This CheckInput() only contains the very least amount required for input. It takes the axis input from the input class:

```cs
public virtual void CheckInput()
```

The Input class provides an interface to Unity's input systems. It may be used for everything from gyroscope input on mobile devices to keyboard presses. Unity's input system has a vertical axis setup, where developers can name an axis in the Input Manager section of the Unity editor. The Input Manager is available in Unity via the Edit -> Project Settings -> Input.

By default, Unity has inputs set up for horizontal and vertical axis axes. Their names are Horizontal and Vertical, and they are accessible via Input.GetAxis(), passing in the name of the virtual axis as a parameter and receiving the return value of a float between -1 and 1. The float variable horz and vert hold the return values:

```cs
// override with your own code to deal with input
horz=Input.GetAxis("Horizontal");
vert=Input.GetAxis("Vertical");
```

A function is provided to return the value of horz, the horizontal axis provided by the virtual axis named Horizontal:

```cs
public virtual float GetHorizontal()
{
  // returns our cached horizontal input axis value
  return horz;
}
```

A function is provided to return the value of vert, the vertical axis provided by the virtual axis named Vertical:

```cs
public virtual float GetVertical()
{
    // returns our cached vertical input value
    return vert;
}
```

GetFire() returns the value of the Boolean Fire. GetRespawn() returns the value of the Boolean shouldRespawn. At this stage, you may notice that there is no actual code to set either Fire or shouldRespawn in this default input script. They are both provided as a guide and with the intention of being built upon on a case-by-case basis depending on what the game requires:

```cs
public virtual bool GetFire(){
    return Fire;
}

public bool GetRespawn(){
    return shouldRespawn;
}
```

It may be useful in some circumstances to have a movement vector rather than having to process the numbers from horz and vert. GetMovementDirectionVector() will return a Vector3 type based on the current state of input. Here, TEMPVec receives input values and gets returned by the function:

```cs
public virtual Vector3 GetMovementDirectionVector(){
    // temp vector for movement dir gets set to the value of an
    // otherwise unused vector that always has the value of 0,0,0
    TEMPVec=zeroVector;
}
```

The vector starts out at 0,0,0, but its x and y values will be set to the values of horizontal and vert, respectively. Finally, the vector in TEMPVec is returned:

```cs
TEMPVec.x=horz;
TEMPVec.y=vert;

// return the movement vector
return TEMPVec;
```

## 3 Player Structure

A player can take just about any form—humans, aliens, animals, vehicles; designing a structure that can deal with all of them is a challenge in itself. The way that players store data, the data they need to store, the various types of movement de codes and their control systems make for hundreds of different possible combinations. Dealing with a player structure in a modular way requires a careful consideration not just for how to deal with all these different scenarios but also for how our components will need to communicate with each other and communicate with the rest of the game—for example, player objects often need to communicate with the game states, etc.), and players may also need to interact with the environment and other objects within.

The overall player structure for this book may be broken down into several main components, as shown in Figure 3.1.

- 1. **Game-specific player controller.** This is a script to deal with game-specific player actions. For example, some games may require a vehicle that requires weapons, whereas some games may not. The "game-specific control script will "add on" the specific extra functionality and tie together the main components to work or communicate with other game-specific elements.
- 2. **Movement controller.** The movement controller takes the job of moving the player around and defines the type of player we are using. For example, a vehicle-based player would have a vehicle-based movement control script that would drive the wheels, turn them, or operate extra vehicle features.

![](img/041dca164b58875f4f1a64abb3328f5c_51_0.png)

- 3. **Player manager.** This script is intended to be a bridge between the player controller and user manager.
- 4. **Data manager.** The data manager takes care of player stats, such as score, level, etc.

### 3.1 Game-Specific Player Controller

The player controller derives from a movement controller (which specializes in nothing more than movement of a particular type) and builds on its movement to provide full player logic.

The movement controllers are explained later in this book. Chapter 5 outlines three movement controllers for three player types: a spaceship, a humanoid player, and a wheeled vehicle.

What logic goes into the player controllers depends on the game; the example games in this book use the movement controllers from Chapter 5 and add extra functionality to them, by combining the movement controller with weapon controllers to make armed players or controlling the AI controller to have computer players.

For real examples of player controllers, take a look at the example games in Chapters 10 to 13.
