### I.1.1 Manager and Controller Scripts

I am a strong believer in manager and controller scripts. I like to try and split things into separate areas; for example, in the Metal Vehicle Doom game, I have race controller scripts and a global race controller script. The race controller scripts are attached to the players and their tracks on the positions, way, and other player-specific race information. The global race controller script talks to all the race controller scripts attached to the players to determine who is winning and when the race starts or finishes. By keeping this logic separate from the other game scripts and contained in their own controller scripts, it makes easier to migrate them from project to project. Essentially, I can take the race controller and global race controller scripts out of the game and apply them to another game, perhaps one that features a completely different type of gameplay—for example, alien characters running around a track of cars. As long as I apply the correct control scripts, the race logic is in place, and I can access it in the new game.

In the framework that this book contains, there are individual manager and controller scripts dealing with user data, input game functions, and user interface. We look at those details in Chapter 2, but as you read this chapter, you should keep in mind the idea of separated scripts dedicated to managing particular parts of the game structure. It was important to design scripts as standalone so that they may be used in more than one situation. For example, our weapon slot manager will not care what kind of weapon is in any of the slots. The weapon slot manager is merely an interface between the player and the weapon, taking a call to “fire” and responding to it telling the weapon in the currently selected weapon slot to fire. What happens on the player end will not affect the slot manager as anything that happens with the weapon itself will not affect the slot manager. It doesn't care how your code talks to it in the proper way and as long as your weapons receive commands in the proper way. It doesn't even matter what type of slot manager is attached to. If you decide to attach the weapon slot manager to a car, a boat, a telegraph pole, etc., it doesn't really matter as when you want to fire, you use the correct function in the slot manager to tell it a weapon to fire.

Since our code logic is controlled by manager and controller scripts, we need to be a little smart about how we put everything together. Some manager scripts might benefit from being static and available globally (for all other scripts to access), whereas others might be better attached to other scripts. We deal with this on a case-by-case basis. To get started, we will be looking at some of the ways that these manager scripts can communicate with each other.

As a final note for the topic in this section, you may be wondering what the difference between managers and controllers. There really isn't all that, and I have only chosen to differentiate for my own sanity. I see controllers as larger systems, like game state, and smaller scripts applied to gameObject, such as.

### I.1.2 Script Communication

An important part of our structures is how our scripts communicate with each other. There are several ways:

- Direct referencing: The easiest way to have scripts talk to each other is to have direct references via variables.
- SendMessage: A way to send a message to a gameObject and call a function in its attached scripts.
- Static variables: A static variable is useful in that it extends across the entire system, accessible from every other script.

#### 2. GameObject SendMessage

SendMessage is a great way to send a message to a gameObject and call a function in one of its scripts when we do not need any return result. For example:

```csharp
gameObject.SendMessage("DoSomething");
```

SendMessage may also take parameters, such as setting whether the engine should throw an error when there is no receiver. You can also pass a parameter into the function just as you were in a regular function call:

```csharp
gameObject.SendMessage("AddScore", 2, SendMessageOptions.RequireReceiver);
gameObject.SendMessage("AddScore", 2, SendMessageOptions.DontRequireReceiver);
```

#### 3. Static variables

A static variable is useful in that it extends across the entire system; it will be accessible from every other script. This is a particularly useful behavior for a game control script, where several different scripts communicate with it to do things like the player's score, lose a life, or perhaps change a level. Example declaration of a static variable might be:

```csharp
private static GameController aController;
```

Although static variables extend the entire program, you can have private and public static variables.

##### Public static

A public static variable exists everywhere in the system and may be accessed from other classes and types of script. Imagine a situation where a player control script needs to tell the game controller script whenever a player picks up a banana. We could deal with it like this:

1. In our GameController.cs game controller script, we set up a public static:
```csharp
public static GameController gateway;
```

2. When the game controller (GameController) runs its Start() function, it stores a reference to itself in the public static variable like this:
```csharp
gateway = this;
```

3. In any other class, we can now access the game controller by referring to its type followed by that static variable (GameController.gateway) such as:
```csharp
GameController.gateway.GetBanana();
```
