Now, if a TestUser logs in to the computer and runs the Invoice application, it runs absolutely fine showing the same output as the one shown in Figure 36.19. You may now wonder how did that happen and how did the TestUser get access to the MyLogo application? Let’s not be anxious and try to understand the reasons why the ACL security is violated. When the DummyUser added a reference and compiled the Invoice application, a local copy of the MyLogo.exe was stored in the Invoice\bin\Debug folder of the Invoice application. When TestUser logged in and executed the Invoice application, the application used the local copy of MyLogo.exe. Note that in this case, MyLogo.exe is a private assembly for the Invoice application. You can find more information about private assemblies in Chapter 33, .NET Assemblies.

As you learned a while ago, the security provided through ACL is not fool proof and is inconsistent. This is because the ACL security applies on a system level; it is not stored in the file or application and hence is non-transferable between different user accounts or locations on the computer. This calls for another means of security that can be implemented at the application level—a security that is embedded within the application. This is where role-based security comes in the picture. With role-based security, you can implement security at assembly, class, or method level such that irrespective of where the application is, access is granted to only those users who have the right permissions.

In the In Depth section of this chapter, you learned that role-based security uses principals, identities, and roles to allow access to the users. Let’s now try to protect the MyLogo application by using the role-based security.

- 14. Login as DummyUser and in the MyLogo application, add the code (Listing 36.5) in the UserControl1() method of the UserControl1 class:

## Listing 36.5: Using Role-Based Security in the MyLogo Application

```
using System;
using System.Collections.Generic;
using System.Linq;
using System.Text;
using System.Windows;
using System.Windows.Controls;
using System.Windows.Data;
using System.Windows.Documents;
using System.Windows.Input;
using System.Windows.Media;
using System.Windows.Media.Imaging;
using System.Windows.Navigation;
using System.Windows.Shapes;
using System.Threading;
using System.Security.Principal;
namespace MyLogo
{
    /// <summary>
    /// Interaction logic for UserControl1.xaml
    /// </summary>
    public partial class UserControl1 : UserControl {
        public UserControl1() {
            AppDomain.CurrentDomain.SetPrincipalPolicy(PrincipalPolicy.
                WindowsPrincipal);
            WindowsPrincipal winP = (WindowsPrincipal)Thread.CurrentPrincipal;
            WindowsIdentity winI=(WindowsIdentity)winP.Identity;
            if (winI.Name == "Avantika-pc\\TestUser")
                MessageBox.Show("TestUser, you do not have the permissions.The logo will not be visible to you");
            else
                InitializeComponent();
                MessageBox.Show("User Account Details\n\nUser Name: "
                +winI.Name+"\nAuthentication Type: " + winI.AuthenticationType);
        }
    }
```

In Listing 36.5, two using directives are added for the System.Threading and System.Security.Principal namespaces. In the constructor of the UserControl1 class, the principal policy of the current application domain is set to WindowsPrincipal principal policy. The WindowsPrincipal principal policy causes the user groups in the Windows operating system to be mapped as roles in .NET. A Windows principal object named winP is created on the current thread by using the CurrentPrincipal property of the Thread class. Next, a Windows identity object named winI is created through the Identity property of the winP object. Now, in the if statement, the Name property of the winI identity object is checked to see whether the current user is TestUser. If the current user is TestUser, then the TestUser, you do not have the permissions. The logo will not be visible to you is displayed.

## NOTE

If you want to allow or deny permissions to a user group rather than a particular user using role-based security, then you can add the following code:

```
AppDomain.CurrentDomain.SetPrincipalPolicy(PrincipalPolicy.WindowsPrincipal);
WindowsPrincipal winP = (WindowsPrincipal)Thread.CurrentPrincipal;
WindowsIdentity winI=(WindowsIdentity)winP.Identity;
if (winP.IsInRole("BUILTIN\\Users"))
    MessageBox.Show("Users, you do not have the permissions.The logo will not be visible to you");
else
    InitializeComponent();
    MessageBox.Show("User Account Details\n\nUser Name: "+winI.Name+"\nAuthentication Type: " + winI.AuthenticationType);
```

Here, the IsInRole() method of the WindowsPrincipal class is used to check if the currently logged-in user belongs to a built-in group named Users. In case the currently logged-in user belongs to the Users group, Users, you do not have the permissions. The logo will not be visible to you message appears.

## Performing Role-Based Security Checks

As you learned in the In Depth section, apart from using the principal and identity objects explicitly to allow or deny access to users, you can also use the imperative or declarative role-based checks on your application. You can use the imperative and declarative security checks on assembly, class, or method level.

Let’s create a standalone WPF application named Album (on the CD-ROM) and implement imperative as well as declarative security checks in the application. In the Album application, there are two windows – MainWindow and Window1. MainWindow has a list of images and two buttons named EditImage and Exit. When a user clicks the EditImage button, an imperative or declarative security check is used to authorize the user. If the user has the right permissions, then Window1 opens allowing the user to edit an image. In case the user does not have the right permissions, Window1 does not appear; instead, a message box appears conveying about the non-authorization of the user.
