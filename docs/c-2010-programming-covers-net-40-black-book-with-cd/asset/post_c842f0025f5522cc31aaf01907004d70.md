
In the preceding syntax, access-modifier is the modifier that determines the accessibility of the event; event is a C# keyword; type is the type of the event, which should necessarily be a delegate type; and the event-name is any valid C# identifier.

You need to define a method to listen to an event (that represents the event listener, which is called by the corresponding delegate) to handle the event and then bind this method to the event using the overloaded += operator, as follows:

```
class-object.event-name += new class-object.delegate-name(method-name);
```

Similarly, when you wish to detach from a source of events, you can use the overloaded -= operator, as follows:

```
class-object.event-name -= new class-object.delegate-name(method-name);
```

Let’s consider a scenario where a system object tracks the state of a database and its records. When the database manager object adds, deletes, or even modifies a row, it directly notifies this system object that the database has been changed. This process is time consuming because the database manager needs to know all the internals of the system object. If the system object is changed, or additional system objects are added, the program needs major modifications to reflect changes.

C# provides event sources and event handlers that help in solving the problem of object notifications, without requiring detailed information about external objects within the event-generating system.

Let’s now learn about event sources, event handlers, events and delegates, and multiple event handlers.

## Event Sources

An event source is an object that notifies other objects or tasks that something has happened. Event notification in C# takes the form of callbacks. The event source sends out a general message when it wants to notify other objects about a change, and then any object interested in the message can read and interpret it. The event handling is in the form of publish-and-subscribe, which requires a generalized broadcast mechanism and that all objects receive all messages.

In C#, each event source maintains all the events published by it. Events in C# are considered to be asynchronous from the perspective of the caller. The occurrence of a callback depends upon the event-firing object rather than its caller.

## Event Handlers

Event handlers receive event notifications. When an event source notifies that an event is called, all the event handlers that have registered for the notification of that event start executing. An event handler may be either a static or a non-static method of a class. In case of a static method, event handlers simply respond to a given event source and take a course of action based on the information passed to the handler. The entire state of the object can be considered, allowing an object to make decisions for a given event for non-static event handlers.

Let’s consider an event handler that deals with the problem of account underflows. The event of account underflows occurs when the owner of an account withdraws an amount that would make the account negative. In such a situation, you might want to send the user an email message to notify him that unless the account is brought to balance that day, the user is charged a fee. To do this, the event handler needs to be notified of the fact that a debit had driven the balance negative.

## Events and Delegates

The entire event mechanism in C# is based around delegates. A delegate acts as a medium between the event source and the event handler methods. It carries the information about the event to the event handler and allows it to carry information back to the event source.

To learn how to implement events, let’s look at a simple example of firing an event and receiving notification that an event has occurred. In this example, a simple class contains an event that can be fired. The first two elements you need are the event itself and a delegate that is called when the event is fired.

Following are the method definitions that are needed in the code to handle these two items:

```
// This is the event itself
public event ValueChangedEventHandler Changed;

// Allow a handler for the event
public delegate void ValueChangedEventHandler();
```

After creating an event and declaring a delegate that is called when the event is fired, the next task is to use a method that fires the event. This method is used to make the connection between the object event source and the method that might be assigned to handle the event, as shown in the following code snippet:

```
// This method is used to fire the event
protected virtual void OnChanged()
{
    if (Changed != null)
        Changed();
    else
        Console.WriteLine("Event fired. No handler!");
}
```

In the preceding code snippet, you can see that the event-firing mechanism is simple and it looks exactly like a function call. Similar to a function or a method call, the event handler can accept arguments. For example, the value of the nValue variable in a class has been changed. If you want to inform the listeners about this change, you have to fire an event. The following code snippet shows how to fire an event:

```
public void SetValue( int nv )
{
    if ( nValue != nv )
    {
        nValue = nv;
        // Fire the event
        OnChanged();
    }
}
```

The event mechanism is by no means automatic. If a method in a class modifies the internal member variable directly, without calling a method, the event is not fired. Consider the following code snippet, which declares a method named BadMethod():

```
public void BadMethod()
{
    nValue++;
}
```

In this case, the event denoting that the variable has changed is not fired because the CLR does not recognize that the event is tied to the value of the variable. While working with events, which check these types of values, you need to ensure that you are always calling the event-firing mechanism when appropriate. The best way to fire an event is to embed that event in the accessor. The following code snippet shows how to define an event handler in another class:

```
public static void HandleChange()
{
    Console.WriteLine("Handler Called");
}
public static void Main()
{
    EventTestClass tc = new EventTestClass(3);
    // Create a handler for this class
    tc.Changed += new EventTestClass.ValueChangedEventHandler(
        HandleChange);
}
```

In the preceding code snippet, you can see that we have selected a static method as the event handler. The signature of the event handler method must match with the signature of the event itself. In this case, the delegate method signature specifies a method that contains no arguments and returns no value (a void return). Notice that the event handler method contains the same signature. If you try to use a method that accepts any arguments or returns any sort of value for this event handler, the compiler flags it as an error. Suppose you want to pass the current value of a variable to a method and you want the event handler to test whether or not this value is acceptable, you can modify the delegate to read the code, as follows:

```
public delegate Boolean ValueChangedEventHandler(int nValue);
```

If a delegate is modified, you also need to modify the event-firing mechanism in the OnChanged() method of the event source to read the code, as shown in the following code snippet:

```
protected virtual void OnChanged()
{
    if (Changed != null)
        if (Changed(nValue))
            ; // Commit the change
}
```

Meanwhile, in the event handler object, the code needs to be modified to validate the input. The following code snippet shows you how to declare the required range of values for the variable:

```
public static Boolean HandleChange(int nValue)
{
    if (nValue <= 0 || nValue >= 10)
        return false;
    return true;
}
```

As you can see, the HandleChange() method forces the member variable in the event source class to be between the values of 1 and 9. Any other value triggers the return of a false condition, which prevents the event source from setting the value in the member variable. Returning to the example of a class that monitors for negative balances, you can see that you could use event handlers to reject a transaction that would cause the balance to go negative.

## Multiple Event Handlers

We can add single as well as multiple event handlers to a single event. As you have learned earlier that while setting the event handler in place for a given event in a given event source object, you used the += operator to add the event handler. The reason for using only the += operator and not the = or any other operator is that additional handlers can be defined for the event from either the same event-handling object or multiple ones.

As you probably noticed in the preceding section, the event source called the delegate for the event handler only once. In this case, the event source does not know that multiple handlers are available to handle the event. It is also not aware of the fact that any one of the other event handlers might have been called.

For example, if you add two different event handlers that return a Boolean value to indicate whether a given value is correct or not, then how can the CLR use that value and chain to the next delegate? The answer is a multicast delegate, which is the only sort that can be used to chain event handlers and cannot return a value.
