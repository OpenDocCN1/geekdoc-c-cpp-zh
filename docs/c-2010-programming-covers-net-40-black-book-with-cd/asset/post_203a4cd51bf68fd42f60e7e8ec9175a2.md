In .NET framework, the MSIL code can be considered as one of the four types of code – valid, invalid, type-safe, and verifiably type-safe code. Table 36.1 lists different types of MSIL code:

## Table 36.1: Types of MSIL Code at Runtime

| MSIL Code | Description |
|---|---|
| Valid | Refers to the MSIL code that follows the .NET syntax and conventions and therefore, can be converted to the native code. Valid MSIL code may use pointer arithmetic that is not type-safe. |
| Invalid | Refers to the MSIL code that cannot be converted to native code. |
| Type-Safe | Refers to the MSIL code in which types access and interact with one another only through their public contracts or methods. |
| Verifiably Type-Safe | Refers to the type-safe MSIL code that has passed the verification process. |

Now, let’s learn about type-safe and verifiably type-safe code in details.

## Type-Safe Code

An MSIL code in which one type accesses the other types in the code only through a well-defined and authorized way is considered as a type-safe code. The well-defined and authorized means of access is by using the public methods and fields. If one or more types access the private fields or methods of another type, the MSIL code is not considered as type-safe. This implies that a type in the type-safe MSIL code cannot access the memory locations of another type unless it has the permission to do so. This memory segregation and type-safety of the MSIL code prevents infringement of types, which in turn ensures that there is no unwanted and malicious manipulation of one type by another. This eventually strengthens the security and reliability of the application.

## Verifiably Type-Safe MSIL Code

A verifiably type-safe code is always valid and type-safe; however, a type-safe code may not be verifiably type-safe. This may happen because of inadequacy of the verification process or the language compiler. The CLR uses an inbuilt verification algorithm to verify the type-safety of the MSIL code. You can also check whether the MSIL code is verifiably type-safe by using the PEVerify tool (peverify.exe), which is a .NET Framework utility that allows you to ensure that your MSIL code is verifiably type-safe. You can use the PEVerify tool at the Visual Studio 2010 Command Prompt and pass the assembly that contains the intended metadata and MSIL code. The syntax for using the PEVerify tool at the command prompt is:

```
peverify assemblyname [switches]
```

In the preceding syntax:

- `peverify` — the PEVerify tool
- `assemblyname` — name of the assembly for which you want to perform the verification process
- `[switches]` — optional set of switches

The PEVerify tool has a number of switches, some of which are listed in Table 36.2:

**Table 36.2: Switches of the PEVerify Tool**

| Switch | Description |
|---|---|
| `/help` or `/?` | Shows the syntax and switches of the PEVerify tool |
| `/md` | Verifies the metadata in the assembly |
| `/il` | Verifies the MSIL code in the assembly |
| `/clock` | Shows the time taken (in milliseconds) for verification |
| `/hresult` | Shows the error codes in hexadecimal format |
| `/unique` | Hides any repeating error codes |
| `/quiet` | Shows only the status of the verification, not the error codes |
| `/verbose` | Shows additional information about the verification process |
| `/ignore=<errorhexcode>[, errorhexcode, errorhexcode…]` | Ignores the specified error codes (in hexadecimal format) |
| `/ignore=@filename` | Ignores the error codes given in the specified response file |
| `/nologo` | Hides the product version and copyright information |

Note that the PEVerify tool performs the verification in the absence of any or all of the switches listed in Table 36.2. The PEVerify tool validates the metadata first and if there are no errors, it verifies the MSIL code. In case of any error in the verification of the metadata, the MSIL code is not verified. However, if you specify the `/md` and `/il` switches, the MSIL code is verified irrespective of whether there are errors in the metadata.

If the MSIL code undergoes the verification process but does not pass the verification, then an exception occurs and the execution of the application is halted. In case you are certain that your code is completely trusted to be type-safe, then you can bypass the verification. You can also bypass the verification if you want to run a non-type-safe code. However, running a non-type-safe code is not recommended as it may lead to unpredictable results. To bypass the verification, you need to set the SkipVerification property of the SecurityPermission attribute to false at the assembly level.

> **NOTE**
> 
> The verification process is performed by the CLR only on managed code; unmanaged code does not undergo the verification process and therefore, is run in a full-trust environment.

In this way, you can use the PEVerify tool to ensure the type-safety of your .NET application, making it secure and reliable to be run on the users' computers. With this, you learned to take the first step in securing your applications. Now, let's discuss the security changes in .NET Framework 4.

## Security Changes in the .NET Framework 4

Security is one of the key features of Web applications. The security prevents Web applications from unauthorized access or hacking. The hackers generally manipulate the functionality of the Web application and therefore, makes the Web application irrelevant for the user. Security also provides defense against threats or virus attacks. Without security, a developer cannot think of developing a Web application. Therefore, .NET Framework includes the security feature since its release which is widely used to secure the Web application. There are various types of security mechanism present in .NET related to identify the identity of the user that will be discussed later in this chapter. Now, Microsoft has enhanced the security feature in .NET Framework 4 by making some important changes to make the Web application more secure from unauthorized access. You should note that in .NET Framework 4, there are two major changes with respect to security in comparison in the earlier versions:

- The Machine-wide security policy has been eliminated
- The security transparency code has become the default enforcement mechanism

Let's discuss the changes and enhancements in the security feature in .NET Framework 4 one by one.

## Security Policy Simplification

The .NET Framework provided Code Access Security (CAS) mechanism. This mechanism is used for controlling and configuring the ability of managed code. The CAS mechanism was powerful but was complicated, as this policy was applicable for native applications and therefore the security guarantee was limited. Therefore, developers look for alternating solutions, such as operating system-level solutions. This problem was solved in .NET Framework 4 by turning off the machine-wide security. The shared and hosted Web applications can now run more securely. The security policy in .NET Framework 4 has been simplified using transparency model. This model allows you to run the Web applications without concerning the CAS policies.

> **NOTE**
> As a result of security policy changes in .NET Framework 4, you may encounter compilation warnings runtime exceptions if your try to use the obsolete CAS policy types and members, either implicitly or explicitly.
> However, you can avoid the warnings and errors by using the <NetFx40_LegacySecurityPolicy> configuration element in the runtime settings schema to opt into the obsolete CAS policy behaviour.

## Security Transparency Level 2

The Security transparency feature was first introduced in .NET Framework 2.0 and was used basically for improving the efficiency of code validation. In .NET Framework 4, this mechanism is basically used to separate the code that executes as a part of the Web application from the code that executes as a part of infrastructure. The Security Transparency acts like an obstacle between the critical code and the transparent code. The critical code can do privileged things, such as modifications in the database, while the transparent code can run command within the limited permissions and cannot call critical code. The main aim of the security transparency is to provide effective mechanism to isolate code on the basis of privileges.

## Obsolete Permission Requests

In .NET Framework 4, the runtime support is omitted that is used to implement the Deny, RequestMinimum, RequestOptional, and RequestRefuse permission requests. These requests are threat to security when they are not properly used. These set of permissions requests can easily be override, cannot be used outside the application, and cannot provide least privilege model. Therefore, .NET Framework 4 removed the runtime calling of these permission requests.
