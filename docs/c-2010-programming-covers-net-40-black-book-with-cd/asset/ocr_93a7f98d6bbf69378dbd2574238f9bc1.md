Note that there can be several <user> elements in the <credentials> element. If a user requesting for the Web application has any of the user name and password combination, then that user becomes an authenticated user. If you have specified Passport as the value for the mode attribute of the <authentication> element, then you need to define the <passport> element as the child of the <authentication> element. The <passport> element has only one attribute named redirectUrl. This attribute refers to the URL to which users are redirected for authentication with Microsoft Passport. The default value of this attribute is internal.

# The <authorization> Element

As you know, after authentication, a user needs to be authorized to access and use an ASP.NET application. You can use the <authorization> element in the web.config file to specify the kind of authorization you want to implement for the Web application. In the <authorization> element, you can specify the user names and/or roles that an authenticated user must have to perform an action in the Web application. Similar to the <authentication> element, you can define the <authorization> element in the machine.config or web.config file of the Web application, website, Web page, or any subdirectory.

The <authorization> element also appears in the <system.web> element. The syntax of the <authorization> element is as follows:

```
<authorization>
  <allow users="comma-separated list of users"
        roles="comma-separated list of roles"
        verbs="comma-separated list of verbs"/>
  <deny users="comma-separated list of users"
        roles="comma-separated list of roles"
        verbs="comma-separated list of verbs"/>
</authorization>
```

In the preceding syntax, you can see that the <authorization> element does not have any attributes but can have two child elements, <allow> and <deny>. The <allow> element enable you to specify the users, roles, and HTTP transmission methods that have the permission to access the Web application. On the other hand, the <deny> element enable you to specify the users, roles, and HTTP transmission methods that are denied access to the Web application. Both these elements can have three attributes, as listed in Table 36.18:

| Table 36.18: Attributes of the <allow> and <deny> Elements |
| Attribute | Description |
| Users | Allows you to specify a comma-separated list of user names that are granted/denied access to the Web application. The default value for this attribute is an asterisk (*) indicating that all authenticated users have/do not have access to the Web application. You can also use a question mark (?) to allow/deny access only to anonymous users. |
| Roles | Allows you to specify a comma-separated list of roles that are granted/denied access to the Web application. An empty string ("") indicates that users that have no roles are granted/denied access. |
| Verbs | Allows you to specify a comma-separated list of HTTP transmission methods that have/do not have access to the Web application. The HTTP transmission methods that you can specify include GET, POST, DEBUG, and HEAD. |

# NOTE

If you want to refer to the users or roles on the computer, then you can use the dot (.) to represent the current computer. This is only applicable for Windows user accounts.

# TIP

It is advisable not to use the <deny> element prior to the <allow> element as the access is allowed or denied depending on the order in which elements are specified in the <authorization> element. For example, if you specify the <deny> element as follows:

```
<authorization>
  <deny users=""/>
  <allow users="TestUser"/>
</authorization>
```
