现在，如果 TestUser 登录到计算机并运行 Invoice 应用程序，它运行完全正常，显示的输出与图 36.19 中所示的输出相同。你现在可能想知道这是怎么发生的，TestUser 是如何获得访问 MyLogo 应用程序的权限的？让我们不要焦虑，试着理解 ACL 安全被违反的原因。当 DummyUser 添加引用并编译 Invoice 应用程序时，MyLogo.exe 的本地副本被存储在 Invoice 应用程序的 Invoice\bin\Debug 文件夹中。当 TestUser 登录并执行 Invoice 应用程序时，应用程序使用了 MyLogo.exe 的本地副本。请注意，在这种情况下，MyLogo.exe 是 Invoice 应用程序的私有程序集。你可以在第 33 章 .NET Assemblies 中找到有关私有程序集的更多信息。

正如你之前所学，通过 ACL 提供的<|message|>安全并非万无一失且不一致。这是因为 ACL 安全适用于系统级别；它未存储在文件或应用程序中，因此在不同的用户帐户或计算机上的不同位置之间不可转移。这就需要另一种可以在应用程序级别实现的安全措施——一种嵌入在应用程序内部的安全措施。这就是基于角色的安全性发挥作用的地方。通过基于角色的安全性，你可以在程序集、类或方法级别实现安全性，这样无论应用程序在哪里，只有拥有正确权限的用户才会被授予访问权限。

在本章的 In Depth 部分中，你了解到基于角色的安全性使用主体、身份和角色来允许用户访问。让我们现在尝试使用基于角色的安全性来保护 MyLogo 应用程序。

- 14. 以 DummyUser 登录，并在 MyLogo 应用程序中，在 UserControl1 类的 UserControl1() 方法中添加代码（清单 36.5）：

## Listing 36.5: Using Role-Based Security in the MyLogo Application

```
using System;
using System.Collections.Generic;
using System.Linq;
using System.Text;
using System.Windows;
using System.Windows.Controls;
using System.Windows.Data;
using System.Windows.Documents;
using System.Windows.Input;
using System.Windows.Media;
using System.Windows.Media.Imaging;
using System.Windows.Navigation;
using System.Windows.Shapes;
using System.Threading;
using System.Security.Principal;
namespace MyLogo
{
    /// <summary>
    /// Interaction logic for UserControl1.xaml
    /// </summary>
    public partial class UserControl1 : UserControl {
        public UserControl1() {
            AppDomain.CurrentDomain.SetPrincipalPolicy(PrincipalPolicy.
                WindowsPrincipal);
            WindowsPrincipal winP = (WindowsPrincipal)Thread.CurrentPrincipal;
            WindowsIdentity winI=(WindowsIdentity)winP.Identity;
            if (winI.Name == "Avantika-pc\\TestUser")
                MessageBox.Show("TestUser, you do not have the permissions.The logo will not be visible to you");
            else
                InitializeComponent();
                MessageBox.Show("User Account Details\n\nUser Name: "
                +winI.Name+"\nAuthentication Type: " + winI.AuthenticationType);
        }
    }
```

在清单 36.5 中，为 System.Threading 和 System.Security.Principal 命名空间添加了两个 using 指令。在 UserControl1 类的构造函数中，当前应用程序域的主体策略被设置为 WindowsPrincipal 主体策略。WindowsPrincipal 主体策略会导致 Windows 操作系统中的用户组被映射为 .NET 中的角色。通过 Thread 类的 CurrentPrincipal 属性在当前线程上创建了一个名为 winP 的 Windows 主体对象。接下来，通过 winP 对象的 Identity 属性创建了一个名为 winI 的 Windows 身份对象。现在，在 if 语句中，检查 winI 身份对象的 Name 属性，以查看当前用户是否为 TestUser。如果当前用户是 TestUser，则显示 TestUser, you do not have the permissions.The logo will not be visible to you。

## NOTE

如果你想使用基于角色的安全性允许或拒绝用户组而不是特定用户的权限，那么你可以添加以下代码：

```
AppDomain.CurrentDomain.SetPrincipalPolicy(PrincipalPolicy.WindowsPrincipal);
WindowsPrincipal winP = (WindowsPrincipal)Thread.CurrentPrincipal;
WindowsIdentity winI=(WindowsIdentity)winP.Identity;
if (winP.IsInRole("BUILTIN\\Users"))
    MessageBox.Show("Users, you do not have the permissions.The logo will not be visible to you");
else
    InitializeComponent();
    MessageBox.Show("User Account Details\n\nUser Name: "+winI.Name+"\nAuthentication Type: " + winI.AuthenticationType);
```

这里，使用了 WindowsPrincipal 类的 IsInRole() 方法来检查当前登录的用户是否属于名为 Users 的内置组。如果当前登录的用户属于 Users 组，则会显示 Users, you do not have the permissions.The logo will not be visible to you 消息。

## Performing Role-Based Security Checks

正如你在 In Depth 部分中所学，除了显式使用主体和身份对象来允许或拒绝用户访问之外，你还可以在应用程序上使用命令式或声明式基于角色的检查。你可以在程序集、类或方法级别使用命令式和声明式安全检查。

让我们创建一个名为 Album 的独立 WPF 应用程序（在 CD-ROM 上）并在应用程序中实现命令式和声明式安全检查。在 Album 应用程序中，有两个窗口 – MainWindow 和 Window1。MainWindow 有一个图像列表和两个名为 EditImage 和 Exit 的按钮。当用户单击 EditImage 按钮时，会使用命令式或声明式安全检查来授权用户。如果用户拥有正确的权限，则 Window1 打开，允许用户编辑图像。如果用户没有正确的权限，则 Window1 不会出现；相反，会出现一个消息框，告知用户未被授权。

现在，让我们通过执行以下步骤来设计 Album 应用程序：
