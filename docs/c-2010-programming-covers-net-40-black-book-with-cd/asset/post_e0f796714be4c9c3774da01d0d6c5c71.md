
In case you have provided names for the elements, then the names appear in the parenthesis that immediately follow the element. For instance, name of the Button element is button1, which appears in the parenthesis next to the element (Figure 9.31). Moreover, when you place the mouse over a particular element in the Document Outline window, a thumbnail image of the element appears. Figure 9.31 shows the thumbnail image of the Button element.

Note that if you add or remove any control in the Design or XAML view, then it is reflected in the Document Outline window too. However, you cannot add or remove the controls in the Document Outline window. In addition, you cannot move the controls in the Document Outline window. However, if you select an element in the Document Outline window, it also appears selected in the Design and XAML views.

Now, let’s move on to learn about the role of XAML in WPF.

## Using XAML in WPF 4.0 Applications

As stated earlier, one of the key ingredients in WPF is its base XAML. The support for XAML (pronounced as zammel) in WPF allows you to declaratively specify the UI or appearance of WPF applications. The XAML loader in WPF 4.0 facilitates you to work with XAML content in WPF applications. With XAML integration in WPF, it is easier and more convenient to draw a line between the design or UI and the logic or functionality of WPF applications. This is because you can use XAML to define the UI of WPF applications, while you can add the logic for the UI in the code-behind file of the application. On the other hand, XAML also eases the sharing of XAML content with the code-behind file as it allows the elements defined in the XAML file to be used in the code-behind file.

Visual Studio 2010 supports the XAML IntelliSense feature and allows the debugging and compilation of XAML content. Moreover, Visual Studio 2010 Software Development Kit (SDK) includes an XAML editing tool called XAMLPad to work with XAML elements in real-time. You can access XAMLPad from C:\Program Files\Microsoft SDKs\Windows\v6.0A\bin\XamlPad.exe.

## NOTE

> XAML files have the .xaml extension. XAML files are also supported in Windows Workflow Foundation (WF) and Microsoft Silverlight.

## XAML Elements

XAML, based on XML, makes use of markup tags, elements, and attributes to define the UI of WPF applications. The XAML elements directly correspond to various managed WPF classes, while the XAML attributes correspond to the properties and events of the classes. In addition, the XAML namespaces in which these XAML elements are defined correspond to the CLR namespaces, so that XAML content can make use of the debugging and compiling provided by .NET Framework 4.0.

In WPF, the XAML elements are represented as a logical tree with several element nodes. Each element corresponds to a tree node while the attributes of the elements become the properties of the nodes. When you add an XAML element within an existing element, it becomes the child element of the existing node. This kind of hierarchical tree-like content model makes WPF applications extensible and easy to render. Note that in any XAML file, there is exactly one topmost or root element. In WPF standalone applications, the root element is the Window element, while in XBAPs the root element is the Page element.

Let’s take the example of a new WPF standalone application named SimpleWPFApplication. Listing 9.4 shows the XAML code of the application:

## Listing 9.4: Displaying the XAML code of SimpleWPFApplication

```
<Window x:class="SimpleWPFApplication.MainWindow"
xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
Title="MainWindow" Height="300" Width="300">
<Grid>
<Button Margin="100,25,100,200" Name="button1">Welcome</Button>
<Button Margin="100,100,100,125" Name="button2">WPF</Button>
<Button Margin="50,150,50,10" Name="button3" VerticalAlignment="Bottom">
<Label Margin="5,5,5,5" Name="label1">XAML</Label>
</Button>
</Grid>
</Window>
```

In Listing 9.4, there are four XAML elements, namely Window, Grid, Button, and Label. The Window and Grid elements exist in the WPF application by default, while the Button and Label elements are added by dragging and dropping the respective controls from the Toolbox. These elements can be represented in a hierarchical manner as a tree that is shown in Figure 9.32:

![](img/e073a4882197be4ab61103cbe0bcb394_370_0.png)

## Figure 9.32: Representing the XAML Elements as a Tree

In Figure 9.32, the Window element contains the Grid element, which in turn contains three Button elements named button1, button2, and button3. The button3 element itself contains a Label element named label1. This way as and when you add more controls or elements in the WPF application, this element tree grows.

You may also notice in Listing 9.4 that the Window, Button, and Label elements have several attributes. For instance, the Window element has the xmlns, Title, Height, and Width attributes and the Button and Label elements have the Name and Margin attributes. Note that the Window, Grid, Button, and Label XAML elements correspond to the instances of the Window, Grid, Button, and Label classes, respectively. However, the attributes of the XAML elements correspond to the properties of the respective classes. This implies that whenever you add an XAML element in a WPF application, an instance of the respective class is automatically created and the specified properties are set.

## Namespaces and XAML

Similar to XML, XAML requires certain predefined namespaces to allow you to use the elements and attributes. These namespaces convey about the location of the classes and the structural rules or schemas of the WPF applications to the XAML parser. When you create WPF applications, references to the necessary namespaces are automatically added in the Window element (in standalone WPF applications) and the Page element (in XBAPs). The Application element also contains references to the necessary namespaces.

By default, there are two namespaces that are included in WPF applications. The namespaces are added by using the xmlns declarations, which are provided through the xmlns attribute of the Window or Page element. In Listing 9.4, given earlier, you can see that the xmlns attribute is used in the Window element to include the two namespaces. The xmlns declaration of the first namespace is as follows:

```
xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
```

The preceding xmlns declaration specifies the default namespace for the XAML file and WPF applications. This namespace is provided as a Uniform Resource Indicator (URI) just as any other XML namespace. The namespace includes all the XAML elements and attributes that are required to work with WPF specifically.

The xmlns declaration of the second namespace is as follows:

```
xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
```

The preceding xmlns declaration specifies the namespace that are required to work with XAML in general. This namespace is more exhaustive than the default namespace as it provides all the essential XAML elements and attributes including the elements that do not pertain to WPF. For example, the elements for WF and Silverlight. Note that the xmlns declaration of the XAML namespace specifies x: as an alias for the namespace. This alias (x:) has to be prefixed with every element or attribute that belongs to the XAML namespace. For example, the x:Class attribute in the Window element. The x:Class attribute belongs to the XAML namespace and specifies the partial class (in the code-behind file) that implements the Window XAML element. The following code snippet shows the x:Class attribute:

```
x:Class="SimpleWPFApplication.MainWindow"
```

You may notice the difference between the references to XAML namespaces and CLR namespaces, that is, the XAML namespaces are provided as URIs while the CLR namespaces are provided as dot-separated names (for example, System.Windows.Controls). Due to this dissimilarity, you may wonder how do XAML and CLR namespaces map or correspond to each other. The answer is quite simple, using the assembly level attribute named XmlnsDefinitionAttribute. The XmlnsDefinitionAttribute attribute takes the XAML and CLR namespaces as its arguments to map them. There can be multiple CLR namespaces that are mapped to a single XAML namespace.

## NOTE

> The xmlns declaration of XAML namespaces can be added in any of the XAML elements. However, it is advisable to add the references in the root element of the XAML file, that is, the Window or Page element.

In WPF, you can also create your own namespaces and use it in XAML files by adding an xmlns declaration in the root element of these files. You can create the namespaces by using the namespace keyword in the same or different assembly from that of the current application. You need to include the xmlns declaration with the following syntax to map custom namespaces to XAML code:

```
xmlns:custom_prefix="clr-namespace:namespace_name; assembly=assembly_name"
```

In the preceding code snippet, the following options are used with the xmlns declaration:

- custom_prefix — Refers to the prefix for the custom namespace
- clr-namespace — Refers to the token that allows you to specify the custom namespace
- assembly — Refers to the token that allows you to specify the assembly name

Note that the clr-namespace and assembly tokens are collectively enclosed within the double quotes (") and are separated by a semicolon (;). In addition, value for the clr-namespace token is specified after the colon (:), while that for the assembly token is specified after the equal to operator (=). If the namespace exists in the same assembly as the current application, then there is no need to specify the assembly token.

## XAML Property Syntax

As stated earlier, you can set the properties of WPF classes by setting the appropriate XAML attributes. You may recall from Listing 9.4 that the individual attributes are separated by whitespaces and are specified in name-value pairs. For every attribute, the name of the attribute is followed by the equal to operator, which is then followed by the value to be assigned to the attribute. Note that whether or not the value is a string or number, it is enclosed within double quotes, as shown in the following code snippet:

```
<Button Height="23" Name="button1">Welcome</Button>
```

As you can see in the preceding code snippet, the height and name properties of the Button class are set through attributes, Height and Name, respectively. The value of the Height attribute is 23 and the Name attribute is button1. The string Welcome is the text that appears on the button. This is equivalent to the Text property of Button control in Windows Forms applications.
