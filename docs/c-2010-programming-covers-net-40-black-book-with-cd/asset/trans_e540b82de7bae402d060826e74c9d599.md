在大多数情况下，身份对象具有名称和身份验证类型。对于 Windows 身份，身份验证类型可以是 NT LAN Manager (NTLM) 或 Kerberos。你将在稍后了解更多关于身份验证类型的知识。现在，让我们讨论基于角色的安全检查。

## Role-Based Security Checks

为了将身份验证和授权用于基于角色的安全性，你需要在应用程序中添加必要的代码；即，将基于角色的安全检查添加到授权用户中。你可以通过以下三种方式包含基于角色的安全检查：

- Accessing the Principal directly
- Using the imperative security check
- Using the declarative security check

你可以直接访问当前线程上的 principal 对象，并使用属性和方法来验证和授权用户。你也可以执行命令式或声明式安全检查。现在，让我们学习两种常用的安全检查。

## Imperative Security Check

你知道，使用 .NET Framework 安全系统，你不仅可以在整体应用程序（程序集）级别对用户进行身份验证和授权，还可以在类或方法级别进行。如果你在应用程序的多个方法中实现授权，你可以使用命令式安全检查。如果你希望其他程序集授权用户，你也可以使用命令式安全检查。

在命令式安全检查中，会发出命令式安全需求来授权用户。当应用程序运行时，会检查当前 principal 是否具有授权所需的最小身份和角色。这是通过 principal 权限完成的，principal 权限指的是特定的身份和角色。你可以使用 principal 权限来要求命令式安全检查以验证身份和角色

```
System.Object
System.Attribute
System.Security.Permissions.SecurityAttribute
System.Security.Permissions.CodeAccessSecurityAttribute
System.Security.Permissions.PrincipalPermissionAttribute
```

PrincipalPermissionAttribute 类有几个属性和方法，允许你指定当前 principal 需要匹配以访问类、方法或事件的所需身份和角色。表 36.8 列出了 PrincipalPermissionAttribute 类的重要属性：

### Table 36.8: Noteworthy Properties of the PrincipalPermissionAttribute Class

| Property | Description |
|---|---|
| Name | Sets or retrieves the name of the identity of the current principal. |
| Role | Sets or retrieves the role or membership of the principal. |
| Action | Sets or retrieves the security action (Inherited from SecurityAttribute). |
| Authenticated | Sets or retrieves a value that indicates if the current principal is authenticated or not. |
| TypeId | Retrieves the unique identifier for the current PrincipalPermissionAttribute object (Inherited from Attribute). |
| Unrestricted | Sets or retrieves a value that indicates whether the principal permission provides full access to the requested class or method. If this property is set to true, then the current principal is an authenticated user that can have any identity or role (Inherited from SecurityAttribute). |

表 36.9 列出了 PrincipalPermissionAttribute 类的重要方法：

### Table 36.9: Noteworthy Methods of the PrincipalPermissionAttribute Class

| Method | Description |
|---|---|
| CreatePermission() | Returns a new PrincipalPermission |
| IsDefaultAttribute() | Returns a value that indicates if the PrincipalPermissionAttribute object is the default principal permission for the derived classes (Inherited from Attribute). |
| Match() | Returns a value that indicates if the principal permission is same as a given object (Inherited from Attribute). |

你可以通过 PrincipalPermissionAttribute 类的 Name 和 Role 属性指定所需的身份和角色。在代码中使用 PrincipalPermissionAttribute 对象的语法如下：

```
[SerializableAttribute]
[AttributeUsageAttribute(AttributeTargets.Class|AttributeTargets.Method, AllowMultiple = true,
Inherited = false)]
[ComVisibleAttribute(true)]
public sealed class PrincipalPermissionAttribute : CodeAccessSecurityAttribute
```

关于属性的简要说明如下：

- PrincipalPermissionAttribute — Refers to the PrincipalPermissionAttribute object
- SecurityAction.Demand — Refers to the Demand value of the SecurityAction enumeration
- Name, Role — Refer to the Name and Role properties of the PrincipalPermissionAttribute class
- identityName — Refers to the identity name that is required for the current principal to be authorized
- principalRole — Refers to the role that is required for the current principal to be authorized

与命令式安全检查类似，如果你只想根据当前 principal 的身份或角色执行授权，那么你可以在 PrincipalPermissionAttribute 对象中分别省略 Role 或 Name 属性。

> NOTE
> The PrincipalPermissionAttribute object is a security attribute stored in the metadata, which is used by the CLR to load and run the application. you should also note that the security attributes are used only for declarative security.

你可以使用 SecurityAction 枚举来实现声明式安全检查。该枚举有几个标志，允许你指定要为声明式安全检查执行的操作类型。SecurityAction 枚举的一些常见标志列在表 36.10 中：

### Table 36.10: Flags of the SecurityAction Enumeration

| Flags | Description |
|---|---|
| Assert | Allows the current principal with the specified identity and/or role to access the class or method even when other calling code in the stack does not have the specified permission |
| Demand | Causes the CLR to check if the principal of all the calling code has the identity and/or role specified in the principal permission |
| Deny | Refuses access to the calling code even if the respective principals have the specified permission |
| InheritanceDemand | Causes the CLR to allow access if a derived class or overridden method has the specified permission |
| PermitOnly | Allows the calling code to access only a particular class or method even if the code has permission to access other classes and methods |
| RequestRefuse | Allows you to specify the permissions that you do not want to grant to the code (applicable only for assemblies, not for classes and methods) |
| RequestMinimum | Allows you to specify the minimum permission needed for the code (only applicable for assemblies, not for classes and methods) |
| RequestOptional | Allows you to specify additional permissions for the code (applicable only for assemblies, not for classes and methods) |

除了 RequestRefuse、RequestMinimum 和 RequestOptional 之外，所有其他 SecurityAction 枚举标志都适用于类和方法。

> NOTE
> The level or extent of the declarative security check depends on the location of the security check and the value of the SecurityAction enumeration. If you have specified a declarative security check at the class as well as the method level, then the security check at the method level overrides the security check at the class level.

## Imperative Security Check Versus Declarative Security Check

命令式和声明式安全检查服务于相同的目的，只是方式不同。根据你的需求，你可以选择其中之一。表 36.11 列出了命令式和声明式检查之间的一些主要区别：

### Table 36.11: Difference Between Imperative and Declarative Checks

| Imperative Security Check | Declarative Security Check |
|---|---|
| Allows only Demand, Assert, Deny, and PermitOnly security actions. | Allows all the security actions. |
| Executes at runtime and therefore, there is no way to know about the authorization status at compile time. It is useful when you do not want to disclose the permission requirement information. | Persists in the assembly at compile time; therefore, you can use tools, such as permview (using the /DECL switch), to see the check. This may help you to resolve security issues and configure the security policy while deploying. |
| Imperative checks are performed inside methods and evaluated every time the method is called so they usually provide inferior performance. | Security checks are evaluated once only at the load time, therefore, providing better performance. |
