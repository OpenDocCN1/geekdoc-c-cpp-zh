
The `<allow>` element is rendered ineffective, and no access is given to the TestUser user.

## `<location>` Element

You know how the use of the `<authentication>` and `<authorization>` elements in the web.config file (at root-, application-, or directory-level) assists you in securing the whole ASP.NET Web application(s). Now, consider a situation where you want to secure only a particular range of Web pages in a Web application. In such a case, instead of using the `<authentication>` and `<authorization>` elements, you can use the `<location>` element. The `<location>` element allows you to apply certain configuration settings to a particular Web application or page (or a range of Web pages). You can also use the `<location>` element to secure a particular Web resource, such as a virtual directory or an image.

In the web.config file, the `<location>` element can appear within the `<configuration>` element. The `<location>` element can contain any child element to specify the settings for the given Web application, page, or resource. The syntax of the `<location>` element is as follows:

```xml
<location allowOverride="true|false" path="Path">
  <!-- child elements -->
</location>
```

In the preceding syntax, the `<location>` element has two attributes:

- **path** – Refers to a particular Web application, page, or resource on which you want to secure or apply any other configuration settings. If this attribute is omitted or is set to an empty string, then the security (or configuration) settings apply to the current directory and all its child directories.

- **allowOverride** – Refers to whether the security (or configuration) settings can be overridden in the web.config file of child directories. It can have either `true` or `false` as its value. If `true`, the settings can be overridden in the child directories; if `false`, the settings cannot be overridden. The default value is `true` for this attribute.

## NOTE

You can use `~/` in the path attribute to represent the current application root directory. For example, consider the following code:

```xml
<location path="~/CustomerLists/Customer.xls">
  <system.web>
    <authorization>
      <deny users="TestUser"/>
    </authorization>
  </system.web>
</location>
```

In the preceding code, the TestUser user is denied access to the Customer.xls file in the CustomerList directory that exists in the root directory of the current Web application.

## The `<identity>` Element

The `<identity>` element allows you to specify the identity of the Web application. It is helpful when you want to implement impersonation in Web applications. You can use the `<identity>` element in the web.config file at root-, application-, or directory-level. The `<identity>` element can appear within the `<system.web>` element in the web.config file at the root-, application-, or directory-level. The syntax of the `<identity>` element is as follows:

```xml
<identity impersonate="true|false" userName="domain\userName" password="<secure password>"/>
```

In the preceding syntax, the `<identity>` element has three attributes:

- **impersonate** – Refers to whether client impersonation is used. This attribute can have either `true` or `false` as its value. The default value for this attribute is `false`, which implies that impersonation is not used. If you set the attribute to `true`, then impersonation is used on every request.

- **userName** – Refers to the user name to be used in case you enable impersonation.

- **password** – Refers to the password to be used in case you enable impersonation.

Now, let’s look at some of the common attributes of the `<provider>` element that you need to set while defining the `<provider>` element for ActiveDirectoryMembershipProvider. Table 36.19 lists the attributes of the `<provider>` element:

## Table 36.19: The Attributes of the `<provider>` Element

| Attribute | Description |
|---|---|
| connectionPassword | Specifies the password using which you can access the Active Directory data store. This attribute ensures that the user accessing the Active Directory data store is an authenticated user. |
| connectionStringName | Specifies the name of the connection string created in the `<connectionStrings>` element of the web.config file. This connection string allows you to perform create, update, get, and validate operations on the Active Directory data store. |
| connectionUsername | Specifies the user name using which you can access the Active Directory data store. This attribute ensures that the user accessing the Active Directory data store is an authenticated user. |

> **Note**  
> If you set the `connectionUserName` attribute, make sure that a value for the `connectionPassword` attribute is also specified. Similarly, if you set the `connectionPassword` attribute, make sure that a value for the `connectionUserName` attribute is also specified.

The following code illustrates the configuration of ActiveDirectoryMembershipProvider:

```xml
<membership defaultProvider="ADMembershipProvider">
  <providers>
    <add
      name="ADMembershipProvider"
      type="System.Web.Security.ActiveDirectoryMembershipProvider, System.Web, Version=2.0.0.0, Culture=neutral, PublicKeyToken=b03f5f7f11d50a3a"
      connectionStringName="ActiveDirectoryCS"
      connectionUsername="<domainName>\administrator"
      connectionPassword="pass"/>
  </providers>
</membership>
```

## SqlMembershipProvider

The SqlMembershipProvider is used to store user credentials in an SQL Server data store. You need to first install an SQL Server membership data store and then configure SqlMembershipProvider to use SqlMembershipProvider in an ASP.NET application. An SQL Server membership data store is the one that is used to store user credentials. We will look at the details of installing the SQL Server membership data store and configuring SqlMembershipProvider in the subsequent topics.

## Installing the SQL Server Data Store

Log on to the computer with an account that has the administrative permissions to use the computer, such as an administrative account, to install an SQL Server membership data store on a computer. After logging on to the system, run the aspnet_regsql utility from the Visual Studio 2010 Command Prompt and run it as administrator. The aspnet_regsql utility is used to install data stores for various features of ASP.NET, such as profiles, personalization, and membership. You need to understand its various options, which are as follows, to use the aspnet_regsql utility:

- `-E` — Facilitates authentication using the credentials of the currently logged-on user.
- `-S` — Specifies the name of the computer on which the SQL Server data store is to be installed.
- `-A m` — Generates tables and stored procedures required by SqlMembershipProvider.

For example, you can use the following command to install a SQL Server membership data store on a computer:

```text
aspnet_regsql.exe -E -S server -A m
```

In the preceding line of code, the name of the computer is Server.

## Configuring SqlMembershipProvider

By default, an instance of SqlMembershipProvider, AspNet.SqlMembershipProvider, is defined in the Machine.config file of your ASP.NET application. This instance connects your ASP.NET application to an instance of SQL Server data store running on the local computer. Therefore, if the SQL Server membership data store is installed on a local computer, you do not need to configure SqlMembershipProvider explicitly.

However, if you want to connect your ASP.NET application to an SQL Server data store running on a computer other than the computer on which your ASP.NET application is running, you need to configure SqlMembershipProvider. You can configure SqlMembershipProvider for an ASP.NET application by defining a connection string and an instance of SqlMembershipProvider in the web.config file of the ASP.NET application.

Similar to ActiveDirectoryMembershipProvider, you need to define the `<provider>` element to create an instance of SqlMembershipProvider. Now, let’s look at some of the common attributes of the `<provider>` element that you need to set while defining the `<provider>` element for SqlMembershipProvider in Table 36.20.

## Table 36.20: Attributes of the `<provider>` Element

| Attribute | Description |
|---|---|
| ApplicationName | Specifies information about the users of a single application. You should qualify the user information with the value of the `applicationName` attribute while storing it in the SQL Server data store. This prevents conflicts between similar user names that may arise while storing information for multiple applications in a single SQL Server data store. The default value of the `applicationName` attribute is `/`. |
| EnablePasswordReset | Specifies whether or not a user can modify their password. By default, the `enablePasswordReset` attribute is set to `false`. You can set this attribute to `true` only if the `requiresQuestionAndAnswer` attribute is set to `true`. |
| PasswordFormat | Specifies the format for storing a password in the SQL Server data store. This attribute can take the following values:<br><br>- **Clear** – Stores the passwords in plain text. It is easy to store and retrieve passwords in this format; however, password security is compromised.<br>- **Encrypted** – Stores the passwords in encrypted form. Decryption needs to be done to retrieve the passwords stored in this format. However, the security of passwords stored in encrypted format is high.<br>- **Hashed** – Hashes the password using a one-way hash algorithm while storing it. The security of these passwords is high; however, you cannot retrieve passwords stored in the hashed format. |
| RequiresQuestionAndAnswer | Specifies whether or not a user needs to provide a password question and answer to modify the password. The default value of this attribute is `false`. |
| RequiresUniqueEmail | Indicates whether or not the email address of the user of an ASP.NET application needs to be unique. The default value of this attribute is `false`. |

The following code illustrates the configuration of SqlMembershipProvider using the preceding attributes:

```xml
<configuration>
  <connectionStrings>
    <add name="SqlServices" connectionString="Data Source=localhost;Integrated Security=SSPI;Initial Catalog=aspnetdb;" />
  </connectionStrings>
  <system.web>
    <authentication mode="Forms">
      <forms loginUrl="login.aspx" name=".ASPXFORMSAUTH" />
```
