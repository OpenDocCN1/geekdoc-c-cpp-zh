当你在 IIS 中启用 Windows 身份验证时，默认情况下使用 Negotiate 身份验证协议。Negotiate 协议与 Web 浏览器协商，以确定使用 NTLM 还是 Kerberos 身份验证。如果 Web 服务器和浏览器都支持 Kerberos，则使用 Kerberos 身份验证；否则，使用 NTLM 身份验证。Kerberos 身份验证使用客户端的 Windows 域控制器，因此，如果用户具有 Windows 用户帐户，则 IIS 可能会使用 Kerberos 身份验证。但是，如果用户是非 Windows 用户，或者 Web 服务器与客户端之间没有服务器代理，则 IIS 可能会使用 NTLM 身份验证。

NTLM 身份验证是 Negotiate 身份验证协议默认使用的身份验证方式。你可以在位于 C:\Windows\System32\inetsrv\config 文件夹中的 applicationHost.config 文件中看到此默认设置。在 applicationHost.config 文件中，有一个 <windowsAuthentication> 元素，如以下代码所示：

```
```xml
<configuration>
.
<system.webServer>
.
<security>
.
<authentication>
.
<windowsAuthentication enabled="false">
<providers>
<add value="Negotiate" />
<add value="NTLM" />
</providers>
</windowsAuthentication>
</authentication>
</configuration>
```

## 摘要身份验证

摘要身份验证与基本身份验证相同，只是它的防御能力比基本身份验证更强。与基本身份验证不同，在摘要身份验证中，用户名和密码不以明文形式发送，而是以 MD5 消息摘要（即 Message Digest 5 (MD5) 哈希）的形式发送。这种 MD5 哈希使得未经身份验证或未经授权的用户难以截获。MD5 哈希是一种加密消息，在 HTTP 标头中发送到 Web 服务器。在本章后面，您将了解更多关于 MD5 的内容。Web 浏览器将 MD5 哈希发送到 Web 服务器，以便 IIS 可以对用户进行身份验证。IIS 接着将 MD5 哈希传递给 Windows 域控制器，然后由域控制器确定用户的真实性。

要在 IIS 中实现摘要身份验证，需要确保 Web 服务器和客户端都是同一个域的成员。此外，Windows 域控制器需要启用可逆加密，才能通过摘要身份验证对用户进行身份验证。

> 注意
> 摘要身份验证仅适用于支持 HTTP 1.1 协议的 Web 浏览器。符合 HTTP 1.1 的 Web 浏览器的一些示例包括 Internet Explorer 6、7 和 8。

基本身份验证和摘要身份验证模式都可以在跨代理服务器和防火墙时提供安全性。此外，为了有效实现基本身份验证和摘要身份验证，您需要首先确保在 IIS 中禁用匿名身份验证；否则，将使用匿名身份验证。现在，让我们继续了解 IIS 和 ASP.NET 中的 Forms 身份验证。

## Forms 身份验证

假设有一个 ASP.NET 应用程序，它提供在线买卖（即通过 Internet）的功能。为了进行安全可靠的交易，该应用程序需要唯一标识大量想要买入或卖出的用户。在这种情况下，为每个用户创建 Windows 用户帐户可能不可行。此外，用户可能不知道使用哪些 Windows 凭据来访问该应用程序。在这种情况下，您可能希望允许用户使用自定义凭据进行订阅或注册。您可以将有效凭据存储在后端数据库或应用程序本身中。要对这些拥有非 Windows 凭据的用户进行身份验证，需要允许他们提供凭据以进行身份验证过程，而这在匿名身份验证和 Windows 身份验证模式下是无法实现的。ASP.NET 提供了一种名为 Forms 身份验证的身份验证模式，适用于此类情况。

您可以使用 Forms 身份验证来对独立于 Windows 操作系统的用户进行身份验证。您可以在 ASP.NET 应用程序中编写自己的代码来对用户进行身份验证。在 Forms 身份验证中，如果用户尝试访问网页或资源，您可以将该用户重定向到另一个网页（通常称为登录页）。登录页包含一个 HTML 表单，用户需要在该表单上提供身份验证所需的凭据（用户名和密码）。当登录页提交到 Web 服务器时，将验证凭据。如果用户通过身份验证，则授予该用户访问所请求网页的权限。如果用户未通过身份验证，则再次将用户重定向到登录页以提供正确的凭据。

> 注意
> 使用 Forms 身份验证时，用户的用户名和密码会以明文形式传递给 Web 服务器。因此，在使用 Forms 身份验证时，建议在 Web 服务器和客户端之间使用 SSL 连接。

如果用户通过身份验证，则会向用户发送一个身份验证 Cookie，该 Cookie 包含一个票证，票证中保存着已通过身份验证用户的凭据。当用户随后发出任何请求时，此身份验证票证会被发送到 Web 服务器以重新识别该用户。身份验证 Cookie 的生成取决于 Web 浏览器，因为有些 Web 浏览器不支持 Cookie。在这种情况下，您可以采用无 Cookie 的 Forms 身份验证。在无 Cookie 的身份验证情况下，身份验证票证会被加密，然后通过 URL 本身发送给用户。

当您在 ASP.NET 应用程序中使用 Forms 身份验证时，可以在 IIS 中启用 Forms 身份验证。IIS 中的 Forms 身份验证便于 Windows 用户和非 Windows 用户进行身份验证。IIS 中的 Forms 身份验证甚至可以为非 ASP.NET 内容提供安全性。请注意，如果在 IIS 中单独启用 Forms 身份验证，则会出现错误，因为用户首先需要通过 IIS 进行身份验证，而这只能通过 IIS 中的匿名、Windows（集成）、基本或摘要身份验证模式来实现。在大多数情况下，Forms 身份验证与 IIS 中的匿名身份验证相结合。这意味着 IIS 将该用户视为匿名用户。如果匿名用户在 ASP.NET 应用程序的 web.config 文件中被拒绝访问，并且请求中没有身份验证 Cookie，则会出现登录网页。然后，用户可以在登录页上提供凭据进行身份验证。图 36.12 显示了 Forms 身份验证的过程。

ASP.NET 有一个 FormsAuthenticationModule 类，它有助于实现 Forms 身份验证。FormsAuthenticationModule 对象负责搜索身份验证票证、将用户重定向到登录页以及对用户进行身份验证。该对象允许您将 HttpContext.User 属性设置为用户登录时所用的标识。已通过身份验证的用户的标识由 FormsIdentity 对象表示。您可以将 FormsIdentity 对象与 GenericPrincipal 对象一起使用，以通过 Forms 身份验证实现基于角色的安全性。

FormsAuthenticationModule 类使用另一个类——FormsAuthentication 来管理 Forms 身份验证的过程。此类具有各种属性和方法，您可以使用这些属性和方法指定登录页、将用户重定向到登录页或从登录页重定向出来、对用户进行身份验证以及创建身份验证 Cookie。表 36.14 列出了 FormsAuthentication 类的值得注意的属性：

| Property | Description |
|----------|-------------|
| CookieDomain | 返回身份验证 Cookie 的域名。 |
| CookieMode | 返回一个值，该值指示 ASP.NET 应用程序是否支持 Cookie。 |

## Passport 身份验证

借助 Passport 身份验证，您可以使用 Microsoft 为多个网站提供的单一登录服务。Passport 身份验证为对用户进行身份验证提供了单一的集中中心。用户只需在登录页上提供凭据，如果通过身份验证，就可以使用其他成员站点的服务，而无需在每个站点上重新登录。要在 ASP.NET 应用程序中实现 Passport 身份验证，您需要先从 .NET Passport/Microsoft 网站（www.microsoft.com）下载 .NET Passport SDK。然后需要安装 Passport SDK，之后即可使用允许您实现 Passport 身份验证的类。
