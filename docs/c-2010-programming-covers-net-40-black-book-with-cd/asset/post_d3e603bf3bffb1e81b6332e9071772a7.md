## The Roles Class

Role-based security plays a significant part in securing ASP.NET applications. With the help of principals, identities, and roles, you can easily and effectively protect your applications and other application-specific resources. A role is a group of similar type of users. For example, you can group all the users having administrative rights under the administrative role. Now, let’s move on to the Roles class that allows you to create a role, assign users to a role, and manage a role. Managing role refers to assigning different permissions to the different roles for accessing an ASP.NET application. For example, you may need to restrict the users who are not the members of the Administrator role from accessing the membership data store.

The hierarchy of the Roles class is as follows:

```
System.Object
System.Web.Security.Roles
```

A user can be a member of more than one role and enjoy privileges of multiple roles. For example, if you have created an online discussion forum in ASP.NET, you may need to assign single user to both, member role and moderator role. This user will enjoy privileges of both, member and moderator roles.

The Roles class is available in the System.Web.Security namespace, which resides in the System.Web assembly. The Roles class cannot be inherited.

You can use the members of the Roles class without qualifying them with the instance of the Roles class because Roles class is a static class.

### NOTE

> Roles work with authenticated users only.

## ASP.NET Security Architecture

Securing ASP.NET applications involves an integrated synchronization between the Internet Information Services (IIS), the .NET Framework, and the underlying operating system. As you know, IIS is a part of the Windows operating system, such as Windows 7, and acts as a base for managing and organizing the Web applications on your computer. IIS offers a robust security system for safeguarding the Web applications and their resources. IIS can also make use of the security features of the Windows operating system.

Requests made by clients (Web browsers) for an ASP.NET Web application is first processed by the IIS. If a client is authenticated by IIS, then the request is forwarded to the ASP.NET application, else, the request is denied. The ASP.NET applications may use the security system of the .NET Framework to authenticate and authorize the clients.

The security of ASP.NET applications depends heavily on the security mechanism offered by IIS and .NET Framework. In IIS 6.0, 7.0, and 7.5 (packaged with Windows 7), the ASP.NET worker process (aspnet_wp.exe) runs under the NetworkService account, which is the account under which the IIS worker process (w3wp.exe) also runs. The IIS worker process hosts the IIS Web server, while the ASP.NET worker process hosts the ASP.NET applications. The NetworkService account is a built-in account that has certain limited privileges. This account provides security from malicious attacks by hackers and users who have the intention of damaging the Web server. The NetworkService account is used to run the ASP.NET worker process and not the ASPNET user account as in previous versions of IIS and Windows (Windows XP).

There may be some situations when you want to run the ASP.NET worker process with lesser privileges as compared to the NetworkService account. In such a situation, you can change the user account under which the ASP.NET worker process runs by changing certain relevant attributes in the machine.config file, which exists in the C:\Windows\Microsoft.NET\Framework\v4.0.30319\Config folder on your computer. The machine.config file is an XML file with various tags or elements that define the machine-level configuration settings for .NET applications. You can open the machine.config file in the Notepad or Visual Studio 2010 and locate the <processModel> element in the <system.web> element. In the <processModel> element, you can set the userName and the password attributes. To make the ASP.NET worker process run under the TestUser user account, set the userName and password attributes as follows:

```
<processModel autoConfig="true" userName="TestUser" password="@kogent30"/>
```

The value of the password attribute is the password that you have specified for the TestUser account.

### NOTE

> Apart from the NetworkService account, there are the LocalSystem and LocalService built-in accounts. The LocalSystem account belongs to the Administrators group and has the maximum privileges among the three. Therefore, the LocalSystem account may prove to be unsafe for the Web server as well as the Web applications. The LocalService account has the least privileges and is useful when the application does not use any remote resources.
