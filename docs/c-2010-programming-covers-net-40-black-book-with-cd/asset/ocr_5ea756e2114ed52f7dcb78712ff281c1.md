# Security Changes in the .NET Framework 4

Security is one of the key features of Web applications. The security prevents Web applications from unauthorized access or hacking. The hackers generally manipulate the functionality of the Web application and therefore, makes the Web application irrelevant for the user. Security also provides defense against threats or virus attacks. Without security, a developer cannot think of developing a Web application. Therefore, .NET Framework includes the security feature since its release which is widely used to secure the Web application. There are various types of security mechanism present in .NET related to identify the identity of the user that will be discussed later in this chapter. Now, Microsoft has enhanced the security feature in .NET Framework 4 by making some important changes to make the Web application more secure from unauthorized access. You should note that in .NET Framework 4, there are two major changes with respect to security in comparison in the earlier versions:

+   - The Machine-wide security policy has been eliminated
+   - The security transparency code has become the default enforcement mechanism

Let's discuss the changes and enhancements in the security feature in .NET Framework 4 one by one.

# Security Policy Simplification

The .NET Framework provided Code Access Security (CAS) mechanism. This mechanism is used for controlling and configuring the ability of managed code. The CAS mechanism was powerful but was complicated, as this policy was applicable for native applications and therefore the security guarantee was limited. Therefore, developers look for alternating solutions, such as operating system-level solutions. This problem was solved in .NET Framework 4 by turning off the machine-wide security. The shared and hosted Web applications can now run more securely. The security policy in .NET Framework 4 has been simplified using transparency model. This model allows you to run the Web applications without concerning the CAS policies.

> **NOTE**
> As a result of security policy changes in .NET Framework 4, you may encounter compilation warnings runtime exceptions if your try to use the obsolete CAS policy types and members, either implicitly or explicitly.
> However, you can avoid the warnings and errors by using the <NetFx40_LegacySecurityPolicy> configuration element in the runtime settings schema to opt into the obsolete CAS policy behaviour.

# Security Transparency Level 2

The Security transparency feature was first introduced in .NET Framework 2.0 and was used basically for improving the efficiency of code validation. In .NET Framework 4, this mechanism is basically used to separate the code that executes as a part of the Web application from the code that executes as a part of infrastructure. The Security Transparency acts like an obstacle between the critical code and the transparent code. The critical code can do privileged things, such as modifications in the database, while the transparent code can run command within the limited permissions and cannot call critical code. The main aim of the security transparency is to provide effective mechanism to isolate code on the basis of privileges.

# Obsolete Permission Requests

In .NET Framework 4, the runtime support is omitted that is used to implement the Deny, RequestMinimum, RequestOptional, and RequestRefuse permission requests. These requests are threat to security when they are not properly used. These set of permissions requests can easily be override, cannot be used outside the application, and cannot provide least privilege model. Therefore, .NET Framework 4 removed the runtime calling of these permission requests.
