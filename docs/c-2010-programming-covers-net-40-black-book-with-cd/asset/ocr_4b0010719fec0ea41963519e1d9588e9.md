When you want to disable impersonation in the application, you can use the <identity> element as given in the following code:

```
<identity impersonate="false"/>
```

> NOTE
> You will learn more about the <identity> element later in this chapter.

You can use impersonation in an ASP.NET application through code also. This is specifically useful when you want the ASP.NET application to impersonate a Windows user for temporarily accessing a particular resource and then change to the original account of the application. You can implement programmatic impersonation in ASP.NET by using the Impersonate() method of the WindowsIdentity class. As learned earlier, the WindowsIdentity class represents the identity of a Windows user. Therefore, you can use a WindowsIdentity object for the current Windows user and the Impersonate() method of the object to allow a specific ASP.NET code to impersonate the Windows user. Similar to the web.config file, you can also specify the user name and password of a particular user to cause the code to run under the security context of that user for all the requests.

With impersonation, an ASP.NET application can use the identity of a Windows user and access the resources on the Web server. Now, suppose the ASP.NET application needs to access a resource on some other client (computer) on the network or a remote computer, such as an application requiring access to a network share. In such cases, you can use the identity of the same Windows user and access the resource on the remote computer. This process is known as delegation, which is just an extended form of impersonation. In delegation, the ASP.NET application impersonates as a Windows user and accesses the resources on another computer, that is, the credentials of the impersonated Windows user are delegated to the other computer on which the intended resource exists. Note that delegation is possible only with Basic and Windows (Kerberos) authentication.

> NOTE
> You need to exercise discretion while implementing delegation in ASP.NET applications, as improper user of delegation may compromise the network security.

# Security through the ASP.NET Configuration File

As stated earlier, you can implement security for an ASP.NET application in the application itself by using the configuration file of ASP.NET application. As you know, ASP.NET applications have a configuration file named as web.config. It contains the settings for the directory in which the file exists. The settings applied to one directory apply to its child directories, provided the child directories do not have their own web.config files. Note that apart from the individual web.config file of different ASP.NET applications, there is a root web.config file in the C:\Windows\Microsoft.NET\Framework\v4.0.30319\Config folder on your computer. This root web.config file has the configuration settings that are common to all the ASP.NET applications. Some of the settings in this file are the same as those in the machine.config file.

The web.config file has certain XML elements that you can use to incorporate security for the ASP.NET applications. The XML elements that pertain to the security of the ASP.NET applications include <authentication>, <authorization>, <identity>, and <location>. You may find these elements set in the machine.config file too. Note that the settings of these elements apply only to the ASP.NET resources. Therefore, you learn what these four elements signify and how you can use them to implement security in ASP.NET applications.
