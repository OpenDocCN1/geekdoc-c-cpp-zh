# Using Reflection

To understand how reflection works, you first need to understand two major concepts—assemblies and manifests of an application. We already had a detailed discussion on assemblies and manifests in Chapter 33, that is, .NET Assemblies. However, to recall them, let’s have a recap of the major components.

It has been already defined that an assembly is the basic unit of deployment in a .NET application. An assembly contains the code, the metadata, and the rules (versioning and security) for implementing and running an application within the runtime environment. An assembly file is a self-describing file that contains the Intermediate Language (IL) code loaded by the runtime environment when the application is loaded into the memory. The IL code contains information that describes the types and methods in that assembly, which can be used in a much similar way as you might use the query interface functionality of classic Component Object Model (COM).

From the earlier chapter, you are aware that a manifest contains information about the assembly as a whole. Manifests contain naming and version information that can be used by the runtime environment to ensure that you are loading the proper version of a file when you want it in your application. In addition, because the manifest contains references to other assemblies, the entire package can be loaded into the memory at one time and the runtime can verify that all elements of the application are present before it starts the program. This technique resolves the missing DLL problem so prevalent in the previous versions of Windows programming.

Besides the above mentioned, manifests also contain security information, which details the boundaries that an application is permitted to access when it is run. This concept is incredibly important because of the varied types of applications you can create in C#. For example, a system service having the same level of access as a Web-based application, which must have intense security to avoid people to hack into your system, is not preferred. A system service, on the other hand, needs the freedom to do what it needs to do without the involvement of people in running it.

The final component of the manifest is the list of all the types found in the assembly. Types are important not only because they are the fundamental building blocks of the application, but also because, you cannot use the functionality installed in an assembly without them. Reflection deals primarily with manifest information in the C# runtime environment.

Now that you have recalled about assemblies and manifests, let’s move on and see how to use reflection in an application. C# reflection requires System.Reflection namespace that contains all the reflection-related classes, such as Type, MemberInfo, and so on. These classes are used to retrieve information from any other class under .NET Framework. The System.Type class is the base class for System.Reflection and is the primary way to access metadata. The System.Type class is an abstract class and represents a type in the Common Type System(CLS).

We have mentioned earlier that reflection dynamically creates an instance of any type, binds the type to an existing object, or gets the type from an existing object. The types include the constructors, methods, fields, properties, events, classes, and assemblies. Once an instance is created, appropriate method can be invoked, and the fields and properties can be accessed. This can be done by specifying only the type of object or specifying both assembly and type of the object that needs to be created. In addition, reflection also enables you to find out the various methods associated with newly created object and the way to use these objects in C#. You can use the MemberInfo abstract class to find out the attributes and methods associated with an object.
