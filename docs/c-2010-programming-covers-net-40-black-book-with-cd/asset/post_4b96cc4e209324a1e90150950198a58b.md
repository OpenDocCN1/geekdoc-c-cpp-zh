
## Conditional APTCA

In .NET Framework 4, the AllowPartiallyTrustedCallersAttribute (APTCA) allows the hosts to recognize those assemblies that they want to display to partial trust callers when used conditionally. The candidate assemblies are developed for partial trust, therefore, it must be APTCA or fully transparent. The APTCA uses the PartialTrustVisibilityLevel enumeration to specify the level of visibility for an APTCA assembly.

## Evidence Objects

The object of any type that is identified by the security policy is known as evidence. The security policy consists of code groups. In the previous versions of .NET Framework, almost every object can be used as an evidence object if the hosting code applies it as evidence. At runtime, the evidence objects are not considered as object references and type safety is not applied to them. This raised the problem in the .NET Framework because it applies implicit restrictions on which type can be used as evidence objects. The object which is going to be used as evidence has to be serialized and not null. If it is not so, then the CLR throws the exception.

To avoid the exception, the .NET Framework 4 includes the EvidenceBase class to apply constraints on those objects that may be considered as evidence and to add new requirements and features to the evidence objects. This class ensures that the evidence object should be serializable.

## Evidence Collections

In the previous version of .NET Framework, the full set of evidence objects is generated by the CLR that are used with an assembly when it loads. The evidence objects are stored in the list, which can be used to search the specific object. Therefore, all the evidence objects are displayed whether they were used or not. This behavior was improved in the .NET Framework 4 as the evidence collection now acts like a dictionary. Now, there is no need to search a particular evidence object through iteration rather you can request for particular evidence and the collection returns the evidence. If the requested evidence object is not found then the evidence collection returns null. The dictionary model generates the evidence objects when they are requested.

## Introducing Authentication and Authorization

The very first thing that comes to your mind while distributing your application or resource to the users is how vulnerable or strong it is. Depending on the vulnerability of the application or resource, you may want to limit its access to users. To limit the access and make the application or resource secure, you need to identify and allow access to only a certain set of people or users. Other people or users, who do not have the right access, should not be able to use or access the application or resource. For this, you need to identify the people or users who are recognized by a valid system, such as the operating system on your computer. The process of identifying users of your application or resource is known as authentication. In general, a combination of the user name and the password is used to authenticate users. If the credentials (user name and password) of a user are valid, the user becomes an authenticated user; otherwise, the user is denied access to the requested application or resource.

After a user is authenticated, the next question that comes to the mind is whether or not to provide access to the requested application or resource. The access granted to an authenticated user depends on the operations or actions that the user is allowed or denied to perform on the requested application or resource. Many applications or resources may face a risk of misuse or unintentional manipulation by other users. Therefore, before deciding the actions that you allow an authenticated user to perform, you need to resolve what the user may gain from accessing the resource. After you resolve this matter, you can assign various actions to the authenticated users. This process of deciding whether an authenticated user can access the intended application or resource is known as authorization. ## Role-Based Security

The Web offers a great deal of services and features that can be used in diverse scenarios. Lately, there has been a steep increase in the number of Web applications in use and quality and speed of connectivity. Due to its connected and interactive nature (between server and clients), there is a myriad of threats that afflict the security and reliability of the Web applications. There are many ways in which a third-party user or application may gain access to the Web applications and then manipulate the functioning or data of the Web applications. Therefore, there is a dire need for a robust and impervious security mechanism for Web applications. It is imperative that Web developers have a thorough understanding of the potential security risks to the application and then accordingly incorporate the desired security. Some of the security risks to Web applications include phishing, hacking, and virus attacks.

The Web developer should keep the following things in mind while structuring the security system for a Web application:

- How does the Web application work?
- What is the nature and extent of communication between the server and the clients?
- What are the security threats to the Web application?
- How can these security threats affect the proper running of the Web application?
- What is the level of security that needs to be implemented?

Depending on the mentioned criteria, Web developers can implement the security system for Web applications. Web developers can secure applications in several ways, some of which include configuring firewalls on the Web server and encrypting data exchanged on the Web. Some of these, such as firewalls, may prove useful to only a certain extent. In .NET Framework, there is more than one way in which you can secure the Web applications (ASP.NET Web applications).

The applications that you build, Windows or Web applications, work with large amount of data and resources. Some of the data and resources may be crucial or sensitive in nature and therefore, you would not want such data and resources to be accessible to people who are using your application. As you know, a user can access an application only if the user is authenticated and authorized. In many cases, the authentication is done by the security system of the underlying Windows operating system that checks the identity and the role of the person or user to allow or deny access to an application or resource. .NET Framework and CLR leverages the security system of the Windows operating system by offering role-based security.

Role-based security is based on the notion of users and roles that is implemented in most modern operating systems. Depending on the identity of a user and the roles that the user has, the user is authenticated and authorized. The authorized user can have access to not only the application as a whole but also the classes and methods used in the application. Role-based security has its prime use in situations when the application or resource needs to verify an action based on the role(s) that a user has. Many a times, the intended action requires authorization from multiple people (multiple roles). Now, let’s take a real-life example of an organization where there are people who have distinct roles, such as the managing director, team leaders, software developers, software testers, and human resource manager. People with a particular role have specific privileges and rights that people of another role may or may not have. For instance, the right to sanction leaves rests with the managing director, while the right to approve a software application rests with the team leaders. This concept of roles in real life is inherited by the role-based security of .NET Framework. However, unlike the real-life scenario, the roles or privileges of one user may overlap with those of another user in role-based security. In other words, a single user may have multiple roles. A role is simply a named group of users that has the same set of privileges. Any user belonging to a particular role has all the privileges of that role.

With role-based security, you can easily and efficiently make your applications secure. Role-based security uses a principal, an identity, and a set of roles to authenticate and authorize users to use the applications. You learn about the principal, identity, and the roles in the following section.

## Principal Object

Role-based security revolves around principal. A principal is an encapsulation of the identity of the user and the roles to which the user is affiliated. In .NET framework 4.0, identity of the user is represented through any of the available associated types; and roles of the user are represented by the permissions. The roles and the identity of a principal are taken into consideration by the application for authenticating and authorizing the user. Note that a principal can have only one identity but multiple roles.

Principal (or principal object) represents a user-specific environment in which your applications runs. Depending on the identity and roles of the user, the principal offers less or more security to your application. In .NET framework 4.0, role-based security allows you to work with three types of principals:

- Windows Principals — Refer to the users and roles of the Windows operating system
- Generic Principals — Refer to the users and roles other than the Windows principals
- Custom Principals — Refer to the users and roles that you create in the applications

> NOTE
> With Windows principals, the users and roles have to be linked with the user accounts on the Windows operating system. Therefore, you may need to create new user accounts on the operating system.

You can work with these three types of principals by using different classes available in the System.Security.Principal namespace in the .NET framework 4.0 class library. You can use the WindowsPrincipal class to work with a Windows principal or use the GenericPrincipal class to work with a principal not related to the Windows user accounts. For custom principals, you need to define your own principal class. Note that whether it is the WindowsPrincipal, GenericPrincipal, or a custom principal class, these classes implement the IPrincipal interface of the System.Security.Principal namespace.
