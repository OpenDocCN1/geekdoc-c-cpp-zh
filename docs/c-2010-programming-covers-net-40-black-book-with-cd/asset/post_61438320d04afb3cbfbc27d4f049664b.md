## Web Services Wire Format

The Web service wire format provides an interface to transmit data between a Web service and its users through protocols, such as HTTP-GET and HTTP-POST. A Web service can use any Remote Procedure Call (RPC) protocol, such as DCOM or Common Object Request Broker Architecture (CORBA), to transmit data. However, these types of protocols are not recommended for creating universally available Web services. Therefore, you need to work with frequently used protocols, such as Hypertext Transfer Protocol (HTTP) and SOAP, to transfer data between a Web service and its users.

Table 18.2 lists the common protocols that Web services use to transmit data:

| Table 18.2: Web Service Protocols Used for Data Transmission |
| Protocol Name | Description |
| HTTP-GET | Creates a query string of the name/value pair, such as name=joe, city=Chicago, and appends it to the Uniform Resource Locator (URL) of the requesting script on the server |
| HTTP-POST | Passes the name/value pair in the body of the HTTP request message |
| SOAP | Exchanges information in a decentralized, distributed environment |
| Multipurpose Internet Mail Extensions (MIME) | Defines the standard representation for complex message bodies, such as messages with embedded graphics or audio clips |

The protocols listed in Table 18.2 are used to invoke Web methods of the Web service. The selection of a Web service protocol determines the types of parameters for a method and its return type.

Let's now explore some important protocols in detail.

## HTTP-GET and HTTP-POST

Although you may know about HTTP-GET and HTTP-POST protocols used by the Web services to transmit data over the network, you must be aware of the fact that these methods of transportation of data are not rich enough to represent complex structures or classes. When you work with Web methods, you can use the HTTP-GET and HTTP-POST methods only with the data types listed in Table 18.3:

| Table 18.3: Data Types Supported by HTTP-GET and HTTP-POST Protocols |
| Data Types | Description |
| Enumerations | Supports the transmission of .NET System.Enum types, provided they are represented as a static constant string. |
| Arrays | Creates arrays as a primitive type. |
| Strings | Refers to the string representation of Common Language Runtime (CLR) primitives, such as Int16, Int32, Int64, Boolean, Single, Double, and Decimal. HTTP-Get and HTTP-POST transmit all numerical data as a string token. |

By default, HTTP-GET and HTTP-POST bindings are not enabled for remote Web service invocation. However, HTTP-POST is enabled to allow a machine to invoke a local Web service. These settings are established in the machine.config file using the <protocol> element. Listing 18.3 shows the partial code of the machine.config file:

## Listing 18.3: Partial Code for the machine.config File

```
<!-- In the machine.config file! -->
<webServices>
<protocols>
<add name="HttpSoap1.2"/>
<add name="HttpSoap"/>
<add name="Documentation"/>
<!-- Http GET and POST are disabled! -->
<!--<add name="HttpPost"/>-->
<!--<add name="HttpGet"/>-->
<!--Used by the web service test page-->
<add name="HttpPostLocalhost"/>
</protocols>
</webServices>
```

You can enable the HTTP-GET and HTTP-POST protocols for a Web service, by adding the HttpPost and HttpGet names within the local web.config file, as shown in Listing 18.4:

## Listing 18.4: Adding the HttpPost and HttpGet Names within the Local web.config File

```
<configuration>
  <system.web>
    <webServices>
      <protocols>
        <add name="HttpPost" />
        <add name="HttpGet" />
      </protocols>
    </webServices>
  </system.web>
</configuration>
```

When you use the HTTP-GET and HTTP-POST protocols, you cannot build Web methods that take complex types as parameters or return values, such as ADO.NET DataSet or structure type. For simple Web services, this limitation may be acceptable. However, if you want to build much more elaborate Web services, you can use SOAP bindings.

## Simple Object Access Protocol

SOAP, one of the key elements in a Web service, is a protocol used for messaging. It is completely XML-based.

SOAP specifications are standardized by W3C and are used by most companies that develop Web services.

SOAP provides a complete set of rules for messages, called SOAP envelopes, as well as the rules for issues, such as data encoding, message handling, and message binding, to other protocols, such as HTTP. One of the great advantages of using a SOAP message is that it is not restricted to any particular protocol. However, the HTTP protocol is most commonly used since it is not restricted to any one operating system.

A SOAP message is a simple XML document, which always contains the mandatory envelope and body elements and can contain a few optional elements, such as <Header> and <Fault>. Listing 18.5 shows the syntax of a SOAP message:

## Listing 18.5: Syntax of a SOAP Message

```
<?xml version="1.0"?>
<soap:Envelope
xmlns:soap="http://www.w3.org/2001/12/soap-envelope"
soap:encodingStyle="http://www.w3.org/2001/12/soap-encoding">
  <soap:Header>
    ...
  </soap:Header>
  <soap:Body>
    ...
    <soap:Fault>
      ...
    </soap:Fault>
  </soap:Body>
</soap:Envelope>
```

As already mentioned, the envelope and body elements are always required in any SOAP message. The following is the syntax of both these elements:

```
<?xml version="1.0"?>
<soap:Envelope
xmlns:soap="http://www.w3.org/2001/12/soap-envelope"

...
```

## The Code Model of ASP.NET Web Services

A Web service contains two parts, the entry point for a Web service and the code that is used to implement the functionality of a Web service. In ASP.NET, the entry point for any Web service is a text file with the .asmx extension. This file references the code in precompiled assemblies, in a code-behind file or in the file with the .asmx extension itself.

The WebService directive determines the entry point for the implementation of a Web service, which is at the top of the .asmx file. When you create a Web service through the ASP.NET Web Service template, you will find a code-behind file, such as Service.cs, to write the code for the Web service.

The code model of ASP.NET Web services consists of the following two parts:

- The WebService directive
- The code-behind file

Now, let's discuss these two parts in detail.

## The WebService Directive

The WebService directive defines Web service-specific attributes, such as Namespace and Description attributes, used by the ASP.NET compilers and parsers. The attributes of the WebService directive are as follows:

- **Language** – Notifies the ASP.NET compiler of the programming language in which the class has been written, such as C#, VB, or JS.
- **Class** – Notifies the ASP.NET compiler of the class name to expose as a Web service. A Web service application can contain multiple classes and it is not necessary that all the classes belong to the Web service; therefore, you must inform the ASP.NET compiler of the classes to expose.

For example,

```
<%@ WebService Language="C#" Class="MyFirstWebservice" %>
```

In the preceding example, the class is MyFirstWebservice.

## The Code-Behind File

In the code-behind approach for programming Web services, the WebService directive is separated from the supporting source code. The WebService directive is placed on the file with the .asmx extension, and the supporting source code is placed on the file with the .asmx.cs extension. Before using the Web service, the file with the source code must be compiled into an assembly and placed in the \bin directory of the particular Web service, which is automatically done when your project is built or compiled.

When a request is sent to a Web service for the first time, ASP.NET accesses the .asmx file and reads the WebService directive to get the name of the class file that contains the supporting logic.
