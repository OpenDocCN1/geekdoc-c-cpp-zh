## Routed Events

As you learned earlier, a WPF application has numerous elements. These elements are represented in the form of a tree with one root element (Window or Page) and other elements nested inside the root element. There is no limit for the number of levels of nesting. Except for the root element, all other elements can have more than one nested elements. Most of these elements have certain basic events, for example, the mouse and keyboard events. These events are defined as routed events in WPF. As the name suggests, routed events route or traverse through the element tree of a WPF application. Routed events differ from the traditional CLR events because routed events allow you to raise and handle an event on multiple elements. A routed event originates at one element but can traverse either up or down the element tree from the source element. As the routed event traverses, it is raised on the elements between the root element and the source element and can be handled on each of those elements. You also have the option of handling the routed event at only element and stop the traversal of the routed event at that element.

Routed events belong to the WPF event system and are backed by the RoutedEvent class. Table 9.13 lists some of the noteworthy properties of the RoutedEvent class.

| Table 9.13: Noteworthy Properties of the RoutedEvent Class |
| Property | Description |
| Name | Retrieves the name of the routed event |
| HandlerType | Retrieves the type of handler of the routed event |
| OwnerType | Retrieves the owner with which the routed event is originally registered |
| RoutingStrategy | Retrieves the routing strategy of the routed event |

Since routed events are raised at the elements on the path between the root element and the source element, you can use routed events to pass event information between those elements. The direction in which the routed events (and the event information) traverse depends on the routing strategy employed by the routed event. Now, let's take a look at the routing strategies available for WPF routed events.

## Routing Strategies

In WPF, routed events are used to navigate the elements, up or down, in the elements tree on the basis of their routing strategy. A routing strategy is a way in which an event is raised and traversed in between the elements of the elements tree. These routing strategies are specified with the help of the values of the RoutingStrategy enumeration. These values are given as follows:

- Direct – Represents the events that are raised by the source element. These events have the same behavior as of normal .NET events, but can participate in mechanisms that are specific to routed events, for instance event triggers
- Tunneling – Represents the events that are raised by the root element first. Then, by each element down the elements tree until the source element is reached.
- Bubbling – Represents the events that are raised by the source element first. Then, by each element up the elements tree until the root element is reached.

## Direct Events

Direct events refer to those events that directly apply on the element on which they originated or raised. These events are similar to CLR events that you worked with in Windows Forms applications. This implies that direct events can be raised and handled only on the source element and not routed through other elements in the element tree.

## Tunneling Events

Tunneling events refer to those events that originate on one element but are raised and possibly handled on the root element or parent elements. In other words, tunneling events are raised from the root element in the tree

down to the child element that originally raises the event, that is, from outer element to inner element. Tunneling events are also known as preview events as the names of the events are prefixed with Preview, as shown in Listing 9.6:

## Listing 9.6: Demonstrating the Traversal of a Tunneling Event

```
<Window x:Class="MyWpfApplication.MainWindow"
xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
Title="MainWindow" Height="350" Width="525"
PreviewMouseRightButtonUp="MouseRightHandler">
<Grid Name="grid1" PreviewMouseRightButtonUp="MouseRightHandler">
<Button Name="button1" Height="25" Width="75" Content="button1" Margin="100,10,100,220" PreviewMouseRightButtonUp="MouseRightHandler"/>
<Button Name="button2" Height="150" Width="150" Margin="0" PreviewMouseRightButtonUp="MouseRightHandler">
<Grid Name="grid2" Height="100" Width="100" PreviewMouseRightButtonUp="MouseRightHandler">
<TextBox Name="textBox1" Text="textBox1" Height="25" Margin="0,0,45,60" PreviewMouseRightButtonUp="MouseRightHandler"/>
<TextBox Name="textBox2" Text="textBox2" Height="25" Margin="45,60,0,0" PreviewMouseRightButtonUp="MouseRightHandler"/>
</Grid>
</Button>
<Button Name="button3" Height="25" Content="button3" Margin="100,220,100,10" PreviewMouseRightButtonUp="MouseRightHandler"/>
</Grid>
</Window>
```

In Listing 9.6, you can see that the PreviewMouseRightButtonUp event is associated with its handler, MouseRightHandler, in all the elements. The PreviewMouseRightButtonUp event is a tunneling routed event that is available to all the elements derived from the UIElement class. Whenever you right click any element, the PreviewMouseRightButtonUp event occurs on the root element and tunnels down to the source element. Bubbling events refer to the events that originate on one element but are raised and possibly handled on all the parent elements up to the root element. In other words, bubbling events are raised from the child element to the root element in the order of their hierarchy. For instance, consider the code in Listing 9.7:

## Handlers for Routed Events

As you have learned, routed events traverse through the element tree. They are raised and handled at the level of each element from the source element to the root element or vice versa. There is an entire range of routed events offered by WPF. You can easily and conveniently handle these routed events in the code-behind file. The syntax for event handlers of routed events is as follows:

```
public returnType eventHandlerName(object sender, RoutedEventArgs e)
{
    //event handling logic
}
```

In the preceding syntax:

- public, object, RoutedEventArgs — Represents the C# keywords.
- returnType — Represents the return type of the event handler.
- eventHandlerName — Represents the name of the event handler. It is recommended that the name of the event handler is of the form elementName_eventName, where elementName is the owner of the routed event and eventName is the name of the event.
- sender — Represents the latest sender of the event, that is, the element on which the event is raised most recently.

Note that the RoutedEventArgs class is the base class that provides information related to the raised routed event. For instance, the original source or element that raised the routed event is available through this class. You can also use any of the derived classes of the RoutedEventArgs class for more specific information about the routed event. Table 9.14 lists the noteworthy properties of the RoutedEventArgs class:

| Table 9.14: Noteworthy Properties of the RoutedEventArgs Class |
| Property | Description |
| Handled | Sets or retrieves a value that indicates the current state of handling of a routed event. If this property is set to true, then the event handling stops instantaneously. In case of paired events, if you have set the Handled property to true for a tunneling event, then the bubbling event does not appear. |
| OriginalSource | Retrieves the source or element that originally raised the routed event. The original source is determined by hit testing. |
| Source | Retrieves the source that raised the event. In most cases, OriginalSource and Source refer to the same element; however, the OriginalSource may be a more specific or nested element. |
| RoutedEvent | Sets or retrieves the routed event that is handled by the event handler method. |

> NOTE
> The event handler that you create is passed as an argument to the RoutedEventHandler delegate.

After you have added the event handler of a routed event in the code-behind file, you need to associate the handler with the appropriate event. You can do so by using various event attributes in the XAML file. You should note that the name of the attribute must be same as the name of the event. For example, the Click attribute of the Button element allows you to specify the event handler for the Click event in the XAML file, as shown in the following code snippet:

```
<Button Height="25" Width="75" Name="myButton" VerticalAlignment="Center" Click="myButton_Click">Button1</Button>
```

In the preceding code snippet, a method named myButton_Click() defined in the code-behind file is specified as the event handler for the Click event of myButton button.

Alternatively, you can associate the handler with the routed event in the code-behind file. For instance, the Click event of the myButton button is associated with the myButton_Click() method by using the += operator, as shown in the following code snippet:

```
myButton.Click += new RoutedEventHandler(myButton_Click);
```
