Now, if a TestUser logs in to the computer and runs the Invoice application, it runs absolutely fine showing the same output as the one shown in Figure 36.19. You may now wonder how did that happen and how did the TestUser get access to the MyLogo application? Let’s not be anxious and try to understand the reasons why the ACL security is violated. When the DummyUser added a reference and compiled the Invoice application, a local copy of the MyLogo.exe was stored in the Invoice\bin\Debug folder of the Invoice application. When TestUser logged in and executed the Invoice application, the application used the local copy of MyLogo.exe. Note that in this case, MyLogo.exe is a private assembly for the Invoice application. You can find more information about private assemblies in Chapter 33, .NET Assemblies.

As you learned a while ago, the security provided through ACL is not fool proof and is inconsistent. This is because the ACL security applies on a system level; it is not stored in the file or application and hence is non-transferable between different user accounts or locations on the computer. This calls for another means of security that can be implemented at the application level—a security that is embedded within the application. This is where role-based security comes in the picture. With role-based security, you can implement security at assembly, class, or method level such that irrespective of where the application is, access is granted to only those users who have the right permissions.

In the In Depth section of this chapter, you learned that role-based security uses principals, identities, and roles to allow access to the users. Let’s now try to protect the MyLogo application by using the role-based security.
