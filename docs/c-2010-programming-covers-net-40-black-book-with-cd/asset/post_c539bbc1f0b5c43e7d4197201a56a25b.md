## Understanding the Entity Data Model

A data model is usually designed in the analysis or planning phase of a project. This is done since the relationships among data types, their attributes, and the constraints in the data must be organized conceptually before they can be implemented in the application code. EDM is used to extend models that application designers use to describe data during the development process. These models provide a specification to define data used by an application. An application based on EDM defines the entities and relationships in the domain of the application in the design schema used to generate programmable classes that are further used by the application code.

In EDM, mapping specification connects the design schema and storage schema. The storage structure that contains data for the application is represented in a storage schema. The storage schema is mapped to the design schema so that the mapping specification effectively connects programmable classes to storage structures. ## Data Modeling

Data modeling is a technique to structure and organize data that are needed to support an application. For example, an entity in an application must be represented by data, such as customers, orders, and products, whereas, a relationship specifies the logical connection among the entities. Defining entities and relationships can be a very complex process. It might require unexpected amount of detail, for example, an order might be a telephone order, a catalogue order, or an Internet order, which is quite confusing. To overcome this problem, EDM defines entities and uses data readers to read entities in a serialized form or as materialized objects.

An object model represents the classes that are programmable in Common Language Runtime (CLR) and can be built from the conceptual model defined in the design schema. An EDM conceptual model is a specification for entities and relationships in the domain of an application. Object model and storage metadata, which consist of logical description of database structure, are mapped to the conceptual layer.

Now, let’s discuss about design and implementation of an EDM and its mapping to different platforms.

## Design and Implementation

EDM types are designed in schemas to preserve the logical integrity of data and the constraints of business and technical applications. According to EDM specifications, the following three stages of development are required to implement the data model:

- Entities and relationships in the domain of an application are specified in an XML file
- Metadata that describes the structures of the database is also specified in an XML file
- Mapping of entities and relationships to corresponding databases is specified in the storage metadata file

## EDM Mapping to CLR and Database Management Systems

EDM supports application scenarios across various storage models and maps to both the CLR and the database management system such as SQL Server. With the introduction of EDM, ADO.NET provides a comprehensive platform that connects application code to storage structures. It uses a store-independent view mechanism that takes advantage of the concepts of a Relational Database Management System (RDBMS) to implement mapping among schemas, programming languages, and database tables. The EDM data services are not dependent on any particular storage schema. Applications that require multiple data sources can maintain individual mappings for each data source.

Developing an application by using Entity Framework requires creating and mapping conceptual EDM and storage entity models. Entity Framework has made entity-relationship modeling executable through a combination of XML files such as Conceptual schema definition language (.csdl), Store schema definition language (.ssdl), and Mapping specification language (.msl).

## Conceptual Schema Definition Language

CSDL contains a design schema that provides a design template for an object model. An application uses the object model based on CSDL. A schema is an XML text file that describes entity and relationship types. It also defines a container that contains instances of these types in a logically organized form. CSDL is an XML syntax used to describe both the EDM types, those that are provided when Entity Framework is installed and those that are designed by the developer. The following code snippet shows the overall structure of a CSDL file:

```xml
<?xml version="1.0" encoding="utf-8"?>
<Schema xmlns:cg="http://schemas.microsoft.com/ado/2006/04/codegeneration" xmlns="http://schemas.microsoft.com/ado/2006/04/edm" Namespace="Humanresource.Salaryschema" Alias="Self">
<Documentation>
<Summary>Shows general Syntax of Conceptual schema (csdl) </Summary>
</Documentation>
<EntityType Name="Employee">
<Key>
<PropertyRef Name="EmployeeId" />
</Key>
<Property Name=" EmployeeId " Type="Guid" Nullable="false" />
<!-- Other properties-->
</EntityType>
<Association Name="Monthly_Salary">
<End Role="Employee" Type="Self.Employee" Multiplicity="0..1" />
</Association>
<EntityContainer Name=" Humanresource.SalarySchema ">
<EntitySet Name="Employee" EntityType="Self. Employee" />
<AssociationSet Name="Monthly_Salary" Association="Self.Monthly_Salary">
<End Role="Employee" EntitySet="Employees" />
<!-- Other roles -->
</AssociationSet>
</EntityContainer>
</Schema>
```

Some elements and attributes used in the preceding code snippet are as follows:

- **Schema** — Refers to the root element of every XML schema. It indicates that the elements used in the schema have been extracted from `http://schemas.microsoft.com/ado/2006/04/edm`. This element consists of the following two attributes:
  - **Namespace** — Refers to the top-level node in a schema that assigns a namespace which should be unique. The types defined in a schema are logically organized under the `Humanresource.SalarySchema` namespace.
  - **Alias** — Refers to the attribute that can be used to shorten the name of a namespace in the rest of the schema, such as `Humanresource.SalarySchema`. For example, the Employee table can be shortened by using alias `Self`, which is declared for the namespace such as `Self.Employee`.

- **Using** — Refers to the element that is used to shorten the syntax while referring to types defined in a separate namespace. It consists of the following two attributes:
  - **Namespace** — Specifies the external namespace
  - **Alias** — Provides an alias for the namespace

- **Documentation** — Refers to the element in CSDL file of an EDM that provides information for using entities and associations declared in a schema. It has the following two subelements:
  - **Summary** — Provides a brief description of the type. This attribute is optional.
  - **LongDescription** — Includes a wide range of text information. This attribute is also optional.

> **NOTE**
>
> *An empty Documentation element is also valid in the syntax of a CSDL file.*

- **EntityType** — Refers to the element that is used by EDM in a CSDL schema to specify an object in the domain of the application designed. It consists of the following attributes:
  - **Key** — Specifies one or more properties of the entities as keys. It uniquely identifies instances of an entity for all operations and can be composed of more than one property.
  - **Name** — Identifies the type in the Object Model designed.
  - **NavigationProperty** — Declares a shortcut that is used to navigate to and from entities related by the Association type.
  - **Property element** — Contains most of the information about entities used in an application.
  - **Type** — Refers to the attribute of a property element that is set to `Guid` to specify a unique value for a key.

- **Association** — Refers to the element that specifies a logical relationship between entities in the EDM.

- **EntityContainer** — Refers to the element that is different from a Schema element even though the EntityContainer element is defined in a schema. The EntityContainer elements in a conceptual schema are mapped to the corresponding EntityContainer elements in the storage metadata. It also controls the scope of entities and associations in the object model that is defined.

- **AssociationSet** — Refers to the element that specifies an association in the class that is built from a conceptual schema. The object model, built from a conceptual schema, requires both programmable classes and storage structures to contain data for an application based on it. The attributes of the AssociationSet element are as follows:
  - **AssociationSetMapping** — Connects the AssociationSet element defined in CSDL to the AssociationSet element in SSDL describing the storage structures
  - **Name** — Specifies the name of a class in an object model built from the EDM
  - **Extends** — Provide a means to add entities and associations to an existing schema
