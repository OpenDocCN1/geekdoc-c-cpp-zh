# Security Caveats

In cases where a trusted assembly allows partial trust callers, makes link demands, or asserts permissions, security is likely to be compromised. Any malicious and, in most cases, distrusted code can make use of such assemblies to gain access to protected resources. You should use directives that exempt restrictions only when they are absolutely needed. To prevent such problems, you should enforce alternative checks in the assemblies to ensure detection and prevention.

A strong name identity check for an instance can be used to identify the caller application. In this case, even though your assembly asserts permissions, allows partial trust callers or makes link demands for a certain permission, only the identified caller would be able to make use of your assembly.

Suppose you want that a certain function of your assembly be called by the applications having a certain strong name, you can put a link demand for that strong name identity on that function. For example, in the FileAccessLib assembly you can put a link demand for strong name identity that would identify the immediate caller and allow access to callers only having the company strong name like this:

```
[FileIOPermissionAttribute(SecurityAction.Assert, ViewAndModify ="c:\\file.txt"),StrongNameIdentityPermission(SecurityAction.LinkDemand, PublicKey="0024000004800000940000006020000024000052534131004000001000100938769BF24AB6AEC158CD7EF64E6A5A7C5B00CA273D809307E21E128896C80C735055BDE44C264EEF60B124F8A1ACC36A99305E90E4E33EB1437D875A6A05F21A899B3580A9BD347EEF57DCAC7B060B5FCBBB2C2EEDBE4845047D8E7B11D5070EBE35E7A4B3BE0EA98BE57BE2B0E60E109451CE36AC6EF7E04A24B09B")]
public bool AccessFile(ref string FileText)
{ }
```

As you can see in the highlighted part of the code, the public key of the calling application is used to identify it. You can test this check by making another application and signing it using a new strong name key pair and trying to access the assembly through it.
