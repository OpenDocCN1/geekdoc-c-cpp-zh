general, there is only one UI thread for a single WPF application. However, there can be multiple UI threads that is, you can define UI elements on more than one thread. This kind of multithreaded UI definition results in complicated processing of WPF applications. Therefore, WPF employs the Single-Threaded Apartment (STA) model to make applications single-threaded. With STA, WPF applications are now compatible and interoperable with various browsers, such as Internet Explorer. In the STA model, there can be multiple UI threads but only one of the UI threads would run at a time. Moreover, the UI elements that you create on one UI thread belongs to only that thread and is not available to other UI threads. This phenomenon is known as thread affinity.

The interaction between multiple threads is implemented through a dispatcher, that is, an instance of the Dispatcher class. Every thread has a dispatcher that sends and receives User32 messages to execute the thread. In WPF 4.0, a UI thread has a dispatcher in which its work items are queued. The dispatcher executes the work items based on their priority. A dispatcher can manage the work items of only one thread.

Note that a reference of the dispatcher is stored in an instance of the DispatcherObject class. All classes that inherit the DispatcherObject class have single-thread affinity. This class provides you with certain methods to allow you to check that no thread, other than the one on which an object of the class is created, accesses the object. Moreover, the DispatcherObject class is the base class for most of the classes and UI elements in WPF.

# The System.Windows.DependencyObject Class

The System.Windows.DependencyObject class allows its derived classes to use the dependency property system. Any class that inherits the DependencyObject class can use and implement dependency properties. A dependency property is a CLR property that is backed by the System.Windows.DependencyProperty class and registered with the WPF property system. The values of dependency properties depend on several factors or inputs, such as styles, themes, and animations of WPF objects. Dependency properties allow you to use expressions as property values, bind data, incorporate animations, and apply styles. You learn more about dependency properties later in this chapter.

# The System.Windows.Freezable Class

The System.Windows.Freezable class allows you to work with objects that have editable as well as read-only states. The Freezable class also provides support for change notifications whenever there are changes in the object. The objects called freezable objects (instances of the Freezable class) can have either of the two states— unfrozen (editable) or frozen (read-only). By default, freezable objects are in the unfrozen state and subject to changes and modifications. When an unfrozen object is changed, change notifications are generated to bring the changes into effect.

Change notifications consume ample system resources and sometimes adversely affect the performance of the WPF application. In such a case, the freezable object can be frozen to improve the performance of WPF applications that is, objects are made read-only to prevent any changes in it. Therefore, system resources would not be utilized for change notifications. Moreover, frozen objects can be shared across different threads. Note that a freezable object cannot be frozen under the following conditions:

+   - The object contains any data-bound or animated properties
+   - The object contains any properties that are set by dynamic resources
+   - The object contains any other object that cannot be frozen

After an object is frozen, it cannot be changed or unfrozen. However, you can create editable copies of a frozen object by cloning it. You can then edit or change the cloned editable copies.

> The DispatcherObject, DependencyObject, and Freezable classes exist in the WindowsBase assembly.
