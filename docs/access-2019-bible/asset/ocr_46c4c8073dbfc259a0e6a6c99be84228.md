# Part VII: Advanced Access Programming Techniques

DAO is the default data management library for working with data in Access. It is included in all new projects as part of the Microsoft Office Access database engine Object Library. The DAO object model is a rich and complex hierarchy that is optimized for working with Access data (or more specifically, data in the ACE format). Unless there is something about a project that would benefit from using ADO, most Access developers use DAO to manipulate their data.

ADO is based on Microsoft’s ActiveX technology, which provides the basis for independent objects that perform complex tasks without input from their hosts. Unlike DAO’s rich hierarchy, the ADO object model is flat and sparse. Only a few objects are needed to perform virtually all data access tasks in Access applications. ADO is most commonly used when your project includes external data.

As you learn about and work with DAO and ADO in your VBA code, you might find that DAO feels like you’re manipulating your data directly and that ADO feels like you’re just passing SQL statements. That’s because DAO was built specifically to manipulate JACE data and ADO is meant to be able to work with any compatible database.

Working with DAO and ADO in VBA procedures provides you with much greater flexibility than dealing strictly with forms and reports bound to queries and tables. As you’ll see in the rest of this chapter, relatively few lines of code perform complex operations on data, such as updating or deleting existing records, or adding new records to tables. Using VBA code means that an application can respond to current conditions on a form, such as missing or incorrect values. It’s quite easy to perform ad hoc queries against data that would otherwise require complex queries with many parameters.

Entire books—big books—have been written on the topics covered in this chapter. All we can do in this chapter is provide you with some fundamental examples of using DAO and ADO in Access applications, and, coupled with the material in the other chapters in this book, you should be well prepared to incorporate VBA-based data management in your Access applications.

> **NOTE**
> 
> ADO and DAO are not equivalent in every regard. Both syntaxes enable you to add to or modify the data in tables, build records, work with data in recordsets, and populate forms with data. However, ADO has a distinct edge when it comes to working with external data sources. As you’ll soon see, ADO requires a provider that defines the data source used by the ADO objects in an application. ADO providers are specific to the data source, such as SQL Server or Access. Although Access is not strictly object oriented, it is most certainly object based. The remainder of this chapter describes the object models you use in VBA code to perform data-management tasks in your Access applications. An object model is simply the arrangement of the objects that perform the data-management tasks. A sound understanding of the DAO and ADO object models is an essential requirement when using VBA code to manage Access data.
