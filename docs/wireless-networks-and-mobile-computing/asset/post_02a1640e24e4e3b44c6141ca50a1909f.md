Most commonly used proactive routing protocols include *Destination-Sequenced Distance Vector Routing (DSDV)* [21] and *Optimized Link State Routing (OLSR)* [20].

In reactive routing protocols, routes are not computed in advance. Rather, routes are discovered only when needed. If a source node wants to send a message to some destination node, it first examines its local routing table to see whether a route to the desired destination already exists. If no such route exists, it initiates a *route discovery* process to find a routing path to the destination node. Examples of such reactive routing protocols include *Ad Hoc On-Demand Distance Vector Routing (AODV)* [24], *Dynamic Source Routing (DSR)* [23], and *Temporally-Ordered Routing Algorithm (TORA)* [25].

Reactive routing protocols perform better than the proactive routing protocols due to reduced overhead in route discovery and route maintenance for low to moderate traffic loads in the network. However, if the traffic load is heavy, the signaling overhead in the route discovery of reactive protocols tends to become equal or even surpass that in proactive routing protocols. On the other hand, if the nodes in a MANET have a high mobility or network conditions change very frequently due to addition or removal of nodes or changing transmission conditions, the route maintenance overhead in proactive protocols may rise significantly (being triggered by specific events) and in these situations, reactive protocols may be better choices. Reactive protocols suffer from an additional drawback of a *latency* period of acquiring the route from the instant when the source node needs a route to a given destination. In proactive protocols, there is no such latency as the routes to all destinations are computed in advance at each source node. Due to these advantages and disadvantages of both proactive and reactive protocols, hybrid protocols have been proposed.

## 5.8 Dynamic Source Routing (DSR)

*Dynamic source routing (DSR)* is an example of a reactive routing protocol. This is a source routing protocol, i.e., each packet to be routed from a source node carries in its header the complete ordered list of nodes through which the packet must pass. This protocol has two distinct phases: *route discovery* and *route maintenance*. When a source node *S* wants to send a packet to a destination node *D* and *S* has no information regarding the route to *D*, node *S* has to find a suitable route and this is done in the *route discovery* phase. In the *Route Maintenance* phase, a new route is found if there appears a need for updating an already existing route between a given source and destination pair due to a special situation such as a link failure.

Every node *u* maintains a route cache to store the information regarding all the discovered routes to all other nodes, and also the routes from other nodes to *u*.

**FIGURE 5.35:** Dynamic source routing

Thus, when *S* needs to send a packet to a destination node *D*, and *S* does not find an entry in its route cache for a valid (unexpired) route to *D*, *S* sends a *route request* message *RREQ* to all of its neighbors. The *RREQ* contains the source id *S*, destination id *D* and a unique identification number for the request from *S*. When node *u* receives this *RREQ* message, it looks into its own route cache to see whether it has an entry for a route from *u* to node *D*. If no such entry exists and node *u* is not the destination node *D*, *u* forwards this *RREQ* to all of its neighbors, appending the currently known route from the source *S* to *u*. If an entry for a route from *u* to *D* is found in the route cache of *u* or *u* is the destination node *D*, the accumulated route information from node *u* to *D* is appended to the *RREQ* message to generate a route from *S* to *D* and the route is sent from *u* to *S* (unicast) in the form of a route reply message *RREP*, by traversing the discovered route in the backward direction.

Refer to Figure 5.35(a). The *RREQ* message (*S*) containing the id of the source node *S* reaches nodes *G* and *F*. Node *G* sends the *RREQ* message containing the information (*S, G*) regarding the traversed nodes *S* and *G* to its neighbors *A* and *B*. Similarly, node *F* sends the *RREQ* message to node *E* containing the information (S, F) about the traversed nodes S and F. Node C receives two *RREQ* messages, one containing (S, G, A) from node A and later a message containing (S, G, B) from node B. C ignores the latter message and sends only (S, G, A, C) to the node D. D also receives another *RREQ* message from S with the same identification number containing the information (S, F, E) of the traversed nodes. D sends a *RREP* message to S containing the route information (S, F, E, D), traversing this route backward through the nodes E and F in order, as shown in Figure 5.35(b).

After receiving an *RREQ* message from a source node S, if any node u (including D) receives the *RREQ* message from S with the same identification number once again through some other route, it can store this new path information from S to u in its cache and can also send another *RREP* message back to S if u has route information from u to D (note that in the special case, u can also be D). This allows multiple routes to be known between a source and destination pair which enables multipath routing of packets from a source to a destination and also facilitates easy route maintenance. For example, if an existing route to the destination breaks, the node upstream of the link break, say node w, sends a *route error* message *RERR* to the source node S. If S has an alternative route to D stored in its route cache, this new route can be chosen by S without the need for initiating a fresh *RREQ* message by S. If an intermediate node (in the reverse route from w to S) receiving this *RERR* message also has alternative route information from w to D without involving the broken link, that node can easily perform *route salvaging* by appending this alternative route from w to D to the route from S to w. However, even in this case, the *RERR* message is to be sent back to S to let S know about this error and the corresponding salvaging action taken by w.

This protocol uses a reactive approach which eliminates the need to periodically flood the network with table update messages that are required in a proactive approach like *DSDV*. In contrast, in this protocol, a reactive (on-demand) approach is followed since a route is established only when it is required and hence the need to find routes to all other nodes in the network required by a proactive approach is eliminated. The intermediate nodes also utilize the route cache information efficiently to reduce the control overhead during route discovery and route maintenance. The disadvantage is that the route maintenance mechanism may not allow local repair of a broken link if there is no information for an alternative route to *D* at node *w* (on the upstream side of the broken link). Stale route cache information could also result in inconsistencies during route reconstruction. The latency or connection setup delay is higher than in proactive protocols, particularly in large networks. Even though the protocol performs well in static and low mobility environments, the performance degrades rapidly with increasing mobility.

## 5.9 Ad Hoc On-Demand Distance Vector Routing (AODV)

The *Ad hoc on-demand distance vector (AODV)* routing protocol belongs to the class of reactive routing protocols that blends some of the features from both *DSDV* and *DSR* protocols. The protocol is based on an on-demand route discovery. However, every node also maintains a routing table for storing the information regarding the most recent routing path to a destination node if such a route has already been discovered. Each such route has an associated lifetime. When a source node has data packets to be sent to a destination node, it first checks its routing table to see whether there already exists a valid or unexpired (i.e., within the lifetime) route from this source node to the required destination. If a route already exists, the source node uses it. Otherwise, the route discovery process is initiated.
