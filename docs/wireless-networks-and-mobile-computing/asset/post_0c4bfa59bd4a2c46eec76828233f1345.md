
## 5.36 Request flooding

In essence, the above route discovery action is based on flooding the whole network with the $RREQ$ message to reach the destination node along different source and destination paths in the network. For an illustration of this route discovery process, consider the network shown in Figure 5.36. The destination sequence number is not shown. The fields of the $RREQ$ message forwarded from a node to its neighbors along any possible route as shown in the figure contains the source $id$, destination $id$ and hop count in order. The $RREQ$ message forwarded from every node is shown on the corresponding link. Thus, when node $F$ receives the forwarded message with hop count 2, $F$ ignores this message as it has already received an $RREQ$ message with a hop count of 1. Also, node $C$ receives two $RREQ$ messages from $A$ and $B$, respectively, and only one of them, say the one from $A$, which reaches $C$ first, is processed.

When the $RREQ$ message is received by the destination node $D$, $D$ sends a route reply message $RREP$ back to the source node $S$. The $RREP$ message contains fields for the addresses of the source and the destination nodes, destination sequence number, hop count which is initialized to zero, and the forward route information (from $S$ to $D$). Initially, the forward route information in the $RREP$ message formed by $D$ is empty. The destination sequence number is incremented from the sequence number used by $D$ in the last $RREP$ message it sent. The destination node $D$ then unicasts this $RREP$ message to its neighbor node from which it received the $RREQ$ message (as known from its corresponding entry for the reverse route information). When an $RREP$ message is received by a node $u$ from one of its neighboring nodes,

say *v*, *u* augments the forward route information of the received *RREP* message by concatenating the address of the node *v* to this forward route, and the hop count field is incremented by unity. Thus, referring to Figure 5.37, the destination node *D* sends back the *RREP* message with hop count 3 to the source node *S* backward along the source-destination route (*S*, *F*, *E*, *D*). Every node has the information about the node *id* from which it received the corresponding *RREQ* message, i.e., node *D* knows that the *RREQ* message came from *E* and so it sends the *RREP* message to *E*; *E* knows that it received the *RREQ* message from *F* and so it forwarded the *RREP* message to *F*; and finally *F* sent the *RREP* message to *S*.

If *D* later receives another *RREQ* message originating from *S* with the same request identification number and a smaller hop count value, *D* would initiate sending a fresh *RREP* message back to *S* with the new route information involving smaller path length.

However, as described above in the route discovery process, it is also possible that the *RREQ* message is received by an intermediate node *u* (*u* is not the destination *D*) which has a route information from *u* to *D* with a higher destination sequence number than that in the received *RREQ* message. In that case, *u* sends an *RREP* message (instead of broadcasting the *RREQ* message any further) to its neighbor from which it received the *RREQ* message, by setting the information regarding the route from *u* to *D* already stored at *u* in the forward route information entry of the *RREP* message, and also setting the hop count field in the *RREP* message as that of the route from *u* to *D* stored in its table.

After forming the route, the source node *S* starts sending the data packets to the destination *D* through this route. However, once the route is established, it must be maintained for the duration of sending the packets from *S* to *D*.
