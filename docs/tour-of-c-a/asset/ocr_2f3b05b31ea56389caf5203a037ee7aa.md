```
int main() {
    vector<double> some_vec(1, 2, 3, 4, 5, 6, 7, 8, 9);
    vector<double> vec2(10, 11, 12, 13, 14);
    thread t1(f, some_vec); // Il f(some_vec) executes in a separate thread
    thread t2(F(vec2)); // Il F(vec2) executes in a separate thread
}
```

F(vec2) saves the argument to the vector in F. F can now use and hopefully no other tasks accept vec2 while it is executing. Passing vec2 by value would eliminate that risk.
The initialization with {ref(some_vec)} uses a thread variadic template constructor that can accept an arbitrary sequence of arguments ($8.4). The ref is a type function from <functional> that unfortunately needs to tell the variadic template to treat some_vec as a reference, but not as an object. Without ref(), some_vec would be passed by value. The compiler checks that the first argument is invoked given the following arguments and builds the necessary function object to pass to the thread. Thus, if F::operator() and f perform the same algorithm, the handling of two tasks is equivalent: in both cases, a function object is constructed for the thread to execute.

# 18.2.2 Returning Results

In the example §18.1, I pass the arguments by non-const reference. I only do that if I expect the task to modify the value of data referred to ($1.7). That's a sneaky way, but not uncommon, returning a result.
