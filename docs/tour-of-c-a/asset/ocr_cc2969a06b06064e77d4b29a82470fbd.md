The best approach to program organization is a program as to think of it as a set of modules with well-defined dependencies. Header files represent that modularity through files and exploit modularity through separate compilation.

Acpp file that is compiled by itself (including the h files it #includes) is called a translation unit. A program can consist of thousands of translation units.

The use of header files and #include is a very old way of simulating modularity with significant disadvantages:

+   - Compilation time: You #include header.h in 101 translation units, the text of header.h will be processed by the compiler 101.

+   - Order dependencies: If we #include header1.h before header2.h the declarations and macros ($19.3.2.1) in header1.h might affect the meaning of the code in header2.h. If you #include header2.h before header1.h, it is header2.h that might affect the code header1.h.

+   - Inconsistencies: Defining an entity, such as a type or a function, in one file and defining it slightly differently in another file, can lead to crashes or subtle errors. This happens if we – accidentally or deliberately – declare an entity separately in two source files, rather than putting it in a header, or order dependencies between different header files.

+   - Transitivity: All code that needs to express a declaration in a header file must be present in that header file. This leads to massive code blo at header files #include other headers
