elements are copyable. That is, we must require that Vector's template constrain is not just a typename but an Element "Element" specifies the requirements of a type that can be an element:

```
template<T>
class Vector {
private:
  T* elem; // elem points to an array of sz elements of type T
  int sz;
  // ...
}
```

This template<Element T> predicts C++'s version of mathematical "for all T such that Element(T)\ is, Element checks that T has all the properties that a Vector requires. Such a predicate is called a constrained (§8.2). A template for which a concept is specified is a constrained argument and a template for which an argument is constrained is called a constrained template.

The requirements for the type of a standard-library element are bit complicated (§12.2), but for our simple Vector, Element could be like the standard-library concept copyable (§14.5).

It is a compile-time error to try to use a template that does not meet its requirements. For example:

Click here to view code image

```
Vector<int> v1;// OK: we can copy an int
Vector<thread> v2;// Error: we cannot copy a thread (§18.2)
```

Thus, concepts lets the compiler to do type checking at the point of use, giving better error messages earlier than is possible with unconstrained template arguments. C++ did not officially support concepts before C++20, so older code uses unconstrained template arguments and leaves requirements to documentation. However, the code generated from templates is checked so that even unconstrained template code is as safe as handwritten code. For unconstrained parameters, that type checking cannot done until the types of all entities involved are available, so it can occur unfortunately in the compilation process, at instantiation time (§8.5), and the error messages are often atrocious.

Concept checking is a purely compile-time mechanism and the code generated is as good as that from unconstrained templates.
