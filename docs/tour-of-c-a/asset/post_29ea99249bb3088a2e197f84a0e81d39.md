
- A unordered_map requires an equality function (the default is ==); it does not maintain an order among its elements.

Given a good function, unordered_map is much faster than a map for large containers. However, the worst-case behavior of an unordered_map with a poor hash function is far worse than that of a map.

## 12.7 Allocators

By default, standard-library containers allocate space using new. Operators new and delete provide a free store (also called dynamic memory) that can hold objects of arbitrary size and user-controlled lifetimes. Therefore, the standard-library containers offer the opportunity to install allocators with semantics we need. This has been used to address a wide variety of concerns related to performance (e.g., pool allocators), security (allocators that clean-up memory as part of deletion), per-thread allocation, and non-uniform memory allocators (allocating in specific memories with pointer types to). This is not the place to discuss these important, but very specialized and advanced techniques. However, I will give one example motivated by a real-world problem for which a pool allocator was the

An important, long-running system used an event queue (see §18.4) using as events that were passed as shared_ptrs. That way, the user of an event implicitly deleted it:

Click here to view code image

```
struct Event {
    vector<int> data = vector<int>(52);
};

list<shared_ptr<Event>> q;

void producer() {
    for (int n = 0; n!=nLOT; ++n) {
        lock_guard lock(m);
        q.push_back(make_shared<Event>());
        cv.notify_one();
    }
}
```

From a logical point of view this worked nicely. It is logically so, the code is robust and maintainable. Unfortunately, this led to memory fragmentation. After 100,000 events had been passed among 16 producers and 4 consumers, more than 6GB of memory had been consumed.

The traditional solution to fragmentation problems is to rewrite the code to use a pool allocator. A pool allocator manages objects of a single fixed size and allocates space for many objects at time, rather than using individual allocations. Fortunately, C++ offers direct support for that. The pool allocator is defined in the pmr ("polymorphic memory resource") subnamespace of std.

Click here to view code image

```
pmr::synchronized_pool_resource;
```

I make a pool

```
struct Event {
    vector<int> data = vector<int>(512,&pool);
};
```

```
list<shared_ptr<Event>> q (&pool);
// Il q use the pool
```

```
void producer() {
    for (int n = 0; n<nLOT; ++n) {
        scoped_lock lock(m); // m is a mutex ($18.3)
        q.push_back(allocate_shared<Event,pmr::polymorphic_allocator<Event>>(&pool));
        cv.notify_one();
    }
}
```

Now, 1000 events have been passed by 16 producers and 4 consumers, less than 3MB of memory has been consumed. That's about a 200-fold improvement! Naturally, the amount of memory actually in use (as opposed to memory wasted to fragmentation) is unchanged. After eliminating fragmentation, memory was stable over time so the system could run for months.

Techniques like this have been applied with good effects from the earliest days of C++, but generally required code to be rewritten to specialized containers. Now, the standard containers only require allocators. The default is for the containers to use new and delete. Other polymorphic memory resources include

- unsynchronized_polymorphic_resource; a polymorphic_resource can only be used by one thread.
- monotonic_polymorphic_resource; a fast allocator that releases its memory only upon its destruction and can only be used by one thread.

A polymorphic resource must be derived from memory_resource and define members allocate(), deallocate(), and is_equal(). The idea is for users to build their own resources to tune code.

## 12.8 Container Overview

The standard library provides some of the most useful and general container types to allow the programmer to select a container that best serves the needs of an application:

| Standard Container Summary |
|------|
| vector<T> | A variable-size vector ($12.2) |
| list<T> | A doubly-linked list ($12.3) |
| forward_list<T> | A singly-linked list |
| deque<T> | A double-ended queue |
| map<K,V> | An associative array ($12.5) |
| multimap<K,V> | A map in which a key can order many times |
| unordered_map<K,V> | A map using a hashed lookup ($12.6) |
| unordered_multimap<K,V> | A multimap using a hashed lookup |
| set<T> | A set (a map with just a key and no value) |
| multiset<T> | A set in which value can occur many times |
| unordered_set<T> | A set using a hashed lookup |
| unordered_multiset<T> | A multiset using a hashed lookup |

The unordered containers are optimized for lookup with a value (often a string); in other words, they are hashes.
The containers are defined in namespace std and presented in headers <vector>, <list>, <map>, etc. ($9.3). In addition, the standard library provides container adapters queue<T>, stack<T>, and priority_queue<T>. Look them up if you need them. The standard library also provides specialized container-like types, such as array<T,N> ($15.3) and bitset<N> ($15.2).
The standard containers and their basic operations are designed to be simple from notational point of view. Furthermore, the meanings of operations are equivalent for various kind of container. Basic operations apply to which they make sense and can be implemented:

| Operation | Description |
|---||---|
| p=c.begin() | p points to first element of c; also cbegin() for iterator const |
| p=c.end() | p points to one-past-the-element of c; end() for iterator const |
| k=c.size() | k is the number of elements in c |
| c.empty() | Is c empty? |
| k=c.capacity() | k is the number of elements that c can hold without a new allocation |
| c.reserve(k) | Increase the capacity to k; if k<c.capacity(), reserve(k) does nothing |
| c.resize(k) | Make the number of elements k; added elements have default valuetype() |
| c[k] | The kth element of c; zero-based; no of range, throw out_range |
| c.push_back(x) | Add x to the end of c; increase the size of c by one |
| c.emplace_back(a) | Add value_type(a) at the end of c; increase the size of c by one |
| q.insert(p,x) | Add x before p in c |
| q.erase(p) | Remove element p from c |
| c=c2 | Assignment: copy all elements from c2 to c |
| b=(c==c2) | Equality of elements of c and c2; b==true if equal |
| x=(c<c2) | Lexicographical order of c and c2: x<0 if c is less than c2, x=0 if equal, and 0<x if greater. |
|

This notational and semantic uniformity enables programmers to provide new container types that can be used in very similar manner to the standards. The range-checked vector (§4.3, Chapter 5) is an example of that; the uniformity of container interfaces allows us to specify algorithms independently of container types. However, each has strengths and weaknesses. traversing a vector is cheap and easy. On the other hand, vector elements are moved to different locations when we insert or remove elements; note that a vector is much more efficient than list for short sequences of small elements (even for insert()); I recommend the standardlibrary as the default type for sequences of elements: unless you need a reason to choose another.

Consider the singly-linked forward_list, a container optimized for the empty sequence (§12.3). An empty forward_list occupies only one node, whereas an empty vector occupies three. Empty sequences, and sequences with only one element or two, are surprisingly common and useful.

An emplacement operation, such as place_back(), takes arguments and builds the object in a newly allocated space in the container, rather than copying an object inside. For example, by a vector<pair<int,string>> we could:

Click here to view code image

```
v.push_back(pair(1,"copy or move)); // make a pair and move it into v
v.emplace_back(1,"build in place"); // build a pair in v
```

For simple examples like this, optimizations can result in equivalent performance for both calls.

## 12.9 Advice

- [1] An STL container defines a sequence; §12.2.
- [2] STL containers are resource handlers; §12.2, §12.3, §12.5, §12.6.
- [3] Use vector as your default container; §12.2, §12.8; [CG: SL.con.2.]
- [4] For simple traversals of a container, use a-for loop or a begin/end pair of iterators; §12.2, §12.3.
- [5] Use reserve() to avoid invalidating pointers and iterators to elements; §12.2.
- [6] Don't assume performance benefits without measurement; §12.2.
- [7] Use push_back() or resize() on a container rather than realloc() on an array; §12.2.
- [8] Don't use iterators into a resized vector; §12.2 [CG: ES.65].
- [9] Do not assume [] checks; §12.2;
- [10] Use at() when you need guaranteed ranges; §12.2 [CG: SL.con.3].
- [11] Use range-for and standard-library algorithms for cost-free avoidance of range errors; §12.2.
- [12] Elements are copied into a container; §12.1.
- [13] To preserve memory behavior of elements, store pointers (built-in or user-defined); §12.2.
- [14] Insertion operations, such as insert() and push_back(), are often surprisingly efficient on a vector; §12.3.
- [15] Use forward_list for sequences that are usually empty; §12.8.
- [16] When it comes to performance, don't trust your intuition: measure; §12.2.
