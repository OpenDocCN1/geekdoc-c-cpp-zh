Confusingly, std::move() doesn't move anything. Instead, it casts its argument to an rvalue reference, saying that its argument will not be used again and therefore may be moved (§6.2.2). It should have been called like rvalue_cast. It exists to serve a few essential cases. Consider a simple swap:

Click here to view code image

```
template <typename T>
void swap(T& a, T& b) {
    T tmp (move(a));
    a = move(b);
    b = move(tmp);
}
```

We don't repeatedly copy potentially large objects, but we request moves using std::move().

For other cases, there are tempting, dangerous, uses of std::move(). Consider:

Click here to view code image

```
string s1 = "Hello";
string s2 = "World";
vector<string> v;
v.push_back(s1);
v.push_back(move(s2));
v.emplace_back(s1);
```

Here s1 is copied by (push_back()) whereas s2 is moved. This sometimes (only) makes the push_back() of s2 costly. The problem is that a moved-from object is left behind. If we use s2 again, we have a problem:

Click here to view code image

```
cout << s1[2];
cout << s2[2];
```

I consider this use of std::move() to be error-prone for widespread use. Don't use it unless you can demonstrate significant and necessary performance improvement. Later maintenance may accidentally intend the use of moved-from object.

The compiler knows that a value is not used in a function, so using an explicit std::move(x), is redundant and can inhibit optimizations. All standard-library types leave a moved-from object in a state that is unspecified, but it can be destroyed and assigned to it. It may unwise not to follow that. For a container (e.g., vector or string), the moved-from state will be “empty.” For many types, the default value is a good state: meaningful and cheap to establish.
