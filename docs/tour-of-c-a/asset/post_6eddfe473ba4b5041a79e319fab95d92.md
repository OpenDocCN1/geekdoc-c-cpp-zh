## 3.4.3 Return Deduction

The return type of a function can be deducted from its return value. For example:

Click here to view code image

```cpp
auto mul(int i, double d) { return i*d; }
// here, "auto" means "deduce the return type"
```

This is convenient, for generic functions ($7.3.1) and lambdas ($7.3.3), but should be used carefully because a deduced type does not offer a stable interface: a change the implementation of the function (or lambda) can change its type.

## 3.4.4 Suffix Return Type

Why does the return type come before function's name and arguments? The reason is mostly historical. That's the way Fortran, C, and Simula did it (and still do). However, sometimes we need to look to the arguments to determine the type of the result. Return type deduction is one example of that, but not the only one. Examples beyond the scope of this book, issue creeps up in connection with namespaces ($3.3), lambdas ($7.3), and concepts ($8.2). Consequently, we allow adding the return type after the argument list where we want to be explicit about the return type. That makes auto mean “the return type which will be mentioned later or be deduced”. For example:

Click here to view code image

```cpp
auto mul(int i, double d) -> double { return i*d; } // the return type is "double"
```

As variables ($1.4.2), we can use this to line up names more clearly. Compare with suffix types to use the version in ($1.3):

```cpp
auto next_elem() -> E;
auto exit(int) -> void;
auto sqrt(double) -> double;
```

I find this suffix return type more logical than the traditional prefix one, but since the vast majority of code uses the traditional notation, I have stuck with that in this book.

## 3.4.5 Structured Binding

A function can return only a single value, but that value can be a class object with many members. This allows us to return many values. For example:

Click here to view code image

```cpp
struct Entry {
  string name;
  int value;
};
```

```cpp
Entry read_entry(istream& is) // naive read function (for a better version, see $11.5)
{
  string s;
  int i;
  is >> s >> i;
  return {s,i};
}
auto e = read_entry(cin);
cout << "" << e.name << ", " << e.value << "\n";
```

Here, (s,i) is used to construct the Entry return value. Similarly, we can “unpack” an Entry’s members into locals:

Click here to view code image

```cpp
auto [n,v] = read_entry(is);
cout << "" << n << ", " << v << "\n";
```

The auto [n,v] declares two locals n and v with which they deduced from read_entry()’s return type. This mechanism for giving local names to members of a class object is called structured binding.

Consider another example:

Click here to view code image

```cpp
map<string, int> m;
// ... fill m
for (const auto [key,value] : m)
    cout << "" << key << ": " << value << "\n";
```

As we can, we decorate auto const and &. For example:

Click here to view code image

```cpp
void incr(map<string,int>& m) // increment the value of each element of m
{
    for (auto& [key, value] : m)
        value++;
}
```

When structured binding is used for a class with no private data, it is easy to see how the binding is done: there are the same names defined for the binding as there are data members in the class, and each name introduced in the binding corresponding to member. There will no difference in the code quality compared to explicitly using composite object. In particular, the return of structured binding does not imply copy return types which can be constructed directly in the location where they are needed (§4.2). The use of structured binding is all about classes access through functions. For example:

Click here to view code image

```cpp
complex<double> z = {1,2};
auto [re,im] = z; // re=3
```

complex has two members, but its interface allows access of functions, such as real and imag(). Mapping complex<double> to two local variables, such as re and im is feasible, but the technique for doing so is beyond the scope of this.

## 3.5 Advice

- [1] Distinguish between declarations (used as interfaces) and definitions (used as implementations): §3.1.
- [2] Prefer modules over headers (where modules are supported); §3.2.
- [3] Use headers to represent interfaces and emphasize logical structure; §3.2.
- [4] include a header in the source file that implements its functions; §3.2.
- [5] Avoid non-inline function definitions in headers; §3.2.
- [6] Use namespaces to express logical structure; §3.3.
- [7] Use using-directives for translation, for libraries (such as std), or within a local scope; §3.3.
- [8] Don't put using-directive in a header file; §3.3.
- [9] Pass “small” values by value and “large” values by reference; §3.4.1.
- [10] Prefer pass-by-const-reference over pass-by-reference; §3.4.1.
- [11] Return values as function-return values (rather than out-parameters); §3.4.2.
- [12] Don't overuse return-type deduction; §3.2.
- [13] Don't overuse structured binding; a named return type often gives more readable code; §4.5.

### 4.1 Introduction

Error handling is a large and complex topic with concerns and ramifications that go beyond language facilities using programming techniques and tools. However, C++ provides a few features to help. The major tool is the type system itself. Instead of painstakingly building up applications from claims and statements (e.g., char, int, and double if, while, and for), we build types (e.g., string, map, and thread) and algorithms (e.g., sort(), find_it(), and draw_all()) that are appropriate for our applications. Higher-level constructs simplify our programming, limit opportunities for mistakes (e.g., you are unlikely to try a tree traversal to a dialog box), and increase the compiler's chances of catching errors. The majority of C++ language constructs are dedicated to the design and implementation of efficient and elegant abstractions (e.g., user-defined types and algorithms using them). One effect of using such abstractions is that the point where a run-error can be detected is separated from the point where it can be handled. As programs grow, and especially when libraries are used extensively, standards for handling errors become important. It is a good idea to articulate a strategy for error handling early on in the development of a program.

### 4.2 Exceptions

Consider again the Vector example. What ought to be done when we try to access an element that is out of range for the vector §2.3?

- The writer of Vector doesn't know the user would like to have done in this case (the writer of Vector typically doesn't know which program the vector will be running).
- The user of Vector cannot consistently detect the problem (if the user, the out-of-range access wouldn't happen in the first place).

Assuming that out-of-range access is a risk, the solution is for the Vector implementer to detect the attempted out-of-range access and tell the user about it. The user can take appropriate action. For example, Vector::operator[] can detect the out-of-range access and throw an out_of_range exception:

```cpp
double& Vector::operator[](int i)
{
    if (!(0 <= i && i<size()))
        throw out_of_range("Vector::operator[]");
    return element[i];
}
```

The throw transfers control to a handler for exceptions of type out_of_range in some function that directly or indirectly calls Vector::operator(). To do that, the implementation must unwind the function call as needed to get back to the context of that caller. That is, the exception handling mechanism will exit scopes and functions to get back to a caller that has expressed interest in handling that kind of exception, invoking destructors (§5.2.2) along the way as needed.
