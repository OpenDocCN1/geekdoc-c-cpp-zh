
In many important cases, such as a vector, that representation is only one or more pointers to data stored elsewhere, but that representation is present in each object of the concrete class. That allows implementations to be optimally efficient in time and space. In particular, it allows us to

- Place objects of complex types on the stack, in statically allocated memory, and in other objects ($1.5).
- Refer to objects directly (and not just through pointers or references).
- Initialize objects directly and completely (e.g., using constructors; $2.3).
- Copy and move objects ($6.2).

The representation can be private and accessible only through the member functions (as it is for Vector; $2.3), but it is present. Therefore, if the representation changes in any significant way, a user must remember. This is the price to pay for having complex types behave like built-ins. For types that don't change often, and local variables provide much-needed clarity and efficiency, this is acceptable and ideal. To increase flexibility, a complex type can keep major parts of its representation on the free store (dynamic memory, heap) and access them through the part stored in the class object. That's the way vector and string are implemented; they can be considered resource handles with carefully crafted interfaces.

## 5.2.1 An Arithmetic Type

The "classical user-defined arithmetic type" is complex:

[Click here to view code image]

```cpp
class complex {
    double re, im; // representation: two doubles
public:
    complex(double r, double i) :re(r), im(i) {}
    complex(double r) :re(r), im(0) {}
    complex() :re(0), im(0) {}
    complex(const complex& z) :re(z.re), im(z.im) {}

    double real() const { return re; }
    void real(double d) { re=d; }
    double imag() const { return im; }
    void imag(double d) { im=d; }

    complex&operator+(const complex& z) {
        re+=z.re; // add to re and im
        im+=z.im;
        return *this;
    }

    complex& operator-=(const complex& z) {
        re-=z.re;
        im-=z.im;
        return *this;
    }
};
```

This is a simplified version of the standard-library complex (§17.4). The class definition contains only the operations requiring access to the representation. The representation is simple and conventional. For practical reasons, it has to be compatible with Fortran provided complex and we need a new set of operators. In addition to the logical demands, complex must be efficient or it will remain unchanged. Thus, simple operations (such as constructors, =, imag()) must be implemented without function calls in the generated machine code. Functions defined in a class are inlined by default. An industrial-standard complex is carefully implemented to provide appropriate inlining. In addition, the standard-library complex has functions shown here as `constexpr` so that we can do complex arithmetic at compile time.

A constructor that can be invoked without an argument is a default constructor. Thus, `complex()` is complex's default constructor. By defining a constructor you eliminate the possibility of uninitialized variables of type.

The `const` prefix on functions returning the real and imaginary parts indicates that the functions do not modify the object for which they are called. A const member function can be invoked for const and non-const objects, but a non-const member function can only be invoked for non-const objects. For example:

```cpp
complex x = {1,0};
const complex cz(1,3);
complex z = cz;
// complex z = cz;
double x = z.real();
```

Many users do not require direct access to the representation of complex, so they can be defined separately from the class definition:

```cpp
complex operator+(complex a, complex b) { return a+=b; }
complex operator=(complex a, complex b) { return a=b; }
complex operator-(complex a) { return {-a.real(), -a.imag()};

complex operator/(complex a, complex b) { return a/=b; }
```

Here, I use the fact that an argument passed by value is so that I can modify an argument without affecting the caller and use the result as the return value.


Class complex can be used like this:

```cpp
void f(complex z)
{
    complex a (2.3); // construct {2.3,0} from 2.3
    complex b (1/a);
```

The compiler converts overlapping numbers into appropriate function calls. For example, `c+b` means `operator+(c,b)` and `1/a` means `operator/(complex{1,a})`.
User-defined operators ("overloaded operators") should be used carefully and conventionally (#6.4). The syntax is fixed by the language, so you cannot define a new `/`. Also, it is not possible to change the meaning of an operator for built-in types, so you cannot redefine `+` to subtract ints.

## 5.2.2 A Container

A container is an object holding a collection of elements. We call class Vector a container; objects of type Vector are containers. As defined in #2.3, Vector isnt an unreasonable container of doubles: it is simple to understand, establishes a useful invariant (#4.3), provides range-checked access (#4.2), and provides size to allow us to iterate over its elements. However, it does have a fatal flaw: it allocates new but never deallocates. That's not a good idea; C++ does not offer a garbage collector to manage memory available. In some environments you prefer control over destruction. For example:

[Click here to view image]

```cpp
class Vector {
public:
    Vector(int s):elem(new double[s]), sz(s) // acquire resources
    {
        for (int i=0; i<s; ++i) // initialize elements
            elem[i]=0;
    }
    ~Vector() { delete[] elem; } // destructor: release resources
    double& operator[](int i);
    int size();
private:
    double* elem; // elem points to an array of sz
    int sz;
};
```

The destructor deallocates the elements and initializes the Vector members. The handle-to-data model is very commonly used data that can vary in size during the lifetime of an object. The technique of acquiring resources in a constructor and releasing them in a destructor, known as Resource Acquisition Initialization or RAII. It allows us to eliminate “naked new operations,” that is, to avoid allocations in general code and keep them buried inside the implementation of well-behaved abstractions. Strictly, “naked delete operations” should be avoided. Avoiding naked and naked delete makes code far error-prone and far easier to keep free of resource leaks (§15.2.1).

Vector obeys the rules for naming, scope, allocation, etc. (\$1.5) as a built-in type, such as int and char. This Vector is simplified by leaving out error handling; see §4.4 The constructor/destructor combination is the basis of many elegant techniques. In particular, is the basis for most C++ general resource management techniques (§6.3, §15.2.1). Consider a graphical illustration of Vector:

|---|---|---|---|---|---|---|
| sz: | 0 | 0 | 0 | 0 | 0 | 0 |
