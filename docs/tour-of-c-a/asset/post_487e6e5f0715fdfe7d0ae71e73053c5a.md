When we use "smart pointers" (such as unique_ptr) rather than resource handles with operations designed specifically for the resource (such as vector or thread?) Unsurprisingly, the answer is "when we need pointer semantics."

- When we share an object, we use pointers (or references) to refer to the shared object, so shared_ptr becomes the obvious choice (unless there is an obvious single).
- When we refer to a polymorphic object in classical object-oriented code (§5.5), we need a pointer (or a reference) because we don't know the exact type of object referred to (or its size), a unique_ptr becomes the obvious choice.
- A polymorphic object typically requires shared_ptr.

We do not need to use a pointer to return a collection of objects from a function; a container that is a resource handle will do that simply and efficiently by copy elimination (§3.4.2) and move semantics (§6.2.2).

## 15.2.2 span

Traditionally, range errors have been a major source of serious errors in C and C++ programs, leading to wrong results, crashes, and security problems. The use of containers (Chapter 12), algorithms (Chapter 13) and range-for has significantly reduced this problem, but more can be done. A key source of range errors is people use pointers (raw or smart) and then rely on convention to know the number of elements pointed to [C++22], but without support to assume that at most one object is pointed to is unmanageable. Most programmers need more. The standard-library string_view (§10.3) can help, but for writing into and reading out of buffers in lower-level software, it is notoriously difficult to maintain high performance while still avoiding errors ("buffer overflows"). A span from <span> is basically a (pointer,length) pair denoting a sequence of elements:

```cpp
span<int>: { begin(), size() }
```

| 1 | 2 | 3 | 5 | 8 | 13 | 21 | 34 | 55 |

A span gives access to a contiguous sequence of elements. The elements are stored in many ways, including in vectors and built-in arrays. Like a pointer, a span does not own the characters to which it points. In that, it resembles a string_view (§10.3) and an STL pool of iterators (§13.3). Consider a common interface style:

```cpp
void fpn(int* p, int n)
{
  for (int i = 0; i < n; ++i)
    p[i] = 0;
}
```

We assume that p points to n integers. Unfortunately, this assumption is simply a convention, so we can't use it to write a range-for loop and the compiler cannot implement cheap and effective range checking. Also, our assumption can be wrong:

Click here to view code image

```cpp
void use(int x)
{
    int a[100];
    fpn(a,100);      // OK
    fpn(a,1000);     // oops, my finger slipped! (range error in fpn)
    fpn(a+10,100);  // range error in fpn
    fpn(a:x);        // suspect, but looks innocent
}
```

We can do better using a span:

```cpp
void fs(span<int> p)
{
    for (int &x : p)
        x = 0;
}
```

We can use fs like this:

Click here to view code image

```cpp
void use(int x)
{
    int a[100];
    fs(a);           // implicitly creates a span<int>{a,100}
    fs(a,1000);      // error: span expected
    fs(a+10,100);    // a range error in fs
    fs(a:x);          // obviously suspect
}
```

That is the common case, creating a span directly from an array, is now safe (the compiler computes the element count) and notationally simple. In other cases, the probability of mistakes is lowered and range-detection is easier because the programmer has to explicitly compose a span.

The common case where a span is passed from function to function is simpler than (pointer,count) interfaces and obviously doesn't require extra checking:

```cpp
void f1(span<int> p)
void f2(span<int> p)
```

As for counters, when span is used for subscripting (e.g., r[i]), range checking is not done and an out-of-range access is undefined behavior. Naturally, an implementation can implement undefined behavior as range checking, but few do. The original gsl::span from Core Guidelines [CG] does checking.

## 15.3 Containers

The standard provides containers that don't fit perfectly into the STL (Chapter 12, Chapter 13). Examples are built-in arrays, array, and string. I sometimes refer to those as "almost containers," but that is not quite fair: they hold elements, but each has restrictions that make them awkward in the context of the STL. Describing them separately simplifies the design of the STL.

| | | |
| :--- | :--- |
| T[N] | Built-in array: fixed-size contiguously allocated sequence of elements of type T; implicitly converts to T* |
| array<T,N> | A fixed-size contiguously allocated sequence of elements of type T; like the built-in array, but with most problems solved |
| bitset<N> | A sequence of bits compactly stored in specialization of vector<bool> |
| pair<T,U> | Two elements of T and U |
| tuple...> | A sequence of arbitrary number of elements of arbitrary types |
| basic_string<C> | A sequence of characters of type C; provides string operations |
| valarray<T> | An array of values of type T; provides numeric operations |

Why does standard provide many containers? They serve different (often overlapping) needs. If library didn't provide them, many people would have to design and implement their own. For example:

- pair and tuple are heterogeneous; all other containers are homogeneous (all elements are the same type).
- array and tuple elements are contiguously allocated; list and map are linked structures.
- bitset and vector<bool> hold bits and access through proxy objects; all other containers hold a variety of types and access directly.
- basic_string requires its elements to be character and provide string manipulation.
- valarray requires its elements to be numbers and provide numerical operations.

All of these can be seen as providing specialized services needed by large communities. No single container could serve all of these because needs are contradictory, for example, "ability to grow" vs. "guaranteed to be allocated in a fixed location," vs "elements do not move when added" vs. "contiguously allocated."

## 15.3.1 array

An array, defined in <array>, is a fixed-size sequence of elements of a given type where the number of elements is specified at compile time. Thus, an array can be allocated on the stack, an object, or in static storage. The elements are allocated in the scope where the array is defined. An array is best understood as a built-in array with its size firmly attached, without implicit, potentially surprising conversions to pointer types, and with a few convenience functions provided. There is no overhead (time or space) involved in using an array compared to built-in array. An array does not follow the "handle to elements" model of STL. Instead, an array directly connects its elements. It is nothing more or less than a safer version of-array.

This implies that an array can be initialized by an initializer list:

```cpp
array<int,3> a1 = {1,2,3};
```

The number of elements in the initializer must be equal to or less than the number of elements specified for the array.

The element count is not optional, the element count must be a constant expression, the number of elements must be positive, and the element type must be explicitly stated:

Click here to view code image

```cpp
void f(int n)
{
  array<int> a = {1,2,3};             // error size specified
  array<string,n> a1 = {"Johns","Queens"}; // error size not a constant expression
  array<string,0> a2;                // error size must be positive
  array<int,2> a3 = {"Johns","Queens"}; // error element type not stated
  ...
}
```

If you need the array to be a variable, use vector.
When necessary, an array can be explicitly passed to a C-style function that expects a pointer.
For example:

Click here to view code image

```cpp
void f(int*, int sz);      // C-style interface
void g()
{
  array<int,10> a;
  f(a.data(), a.size());             // error: no conversion
  f(a.data());                        // C-style use
  auto p = find(a, 777);               // C++/STL-style use (a range is passed)
  ...
}
```

Why we would use an array when vector is more flexible? An array is less flexible than it is simpler. Occasionally, there is a significant performance advantage to be had by accessing elements allocated on the stack rather than allocating on the free store, accessing them directly through the vector (a handle), and deallocating them. On the other hand, the stack is a limited resource (especially on some embedded systems), and stack overflow is nasty. Also, there are application areas, such as safety-critical real-time control, where free store allocation is banned. For example, use of delete may lead to fragmentation (§12.7) or memory exhaustion (§4.3).
