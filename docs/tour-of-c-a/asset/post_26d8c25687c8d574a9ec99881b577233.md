
F(vec2) saves the argument to the vector in F. F can now use and hopefully no other tasks accept vec2 while it is executing. Passing vec2 by value would eliminate that risk.

The initialization with {ref(some_vec)} uses a thread variadic template constructor that can accept an arbitrary sequence of arguments ($8.4). The ref is a type function from <functional> that unfortunately needs to tell the variadic template to treat some_vec as a reference, but not as an object. Without ref(), some_vec would be passed by value. The compiler checks that the first argument is invoked given the following arguments and builds the necessary function object to pass to the thread. Thus, if F::operator() and f perform the same algorithm, the handling of two tasks is equivalent: in both cases, a function object is constructed for the thread to execute.

## 18.3 Sharing Data

Sometimes tasks need to share data. In that case, the access has to be synchronized so that most one task at a time has access. Experienced programmers will recognize this as a simplification (e.g., there is no problem with many tasks simultaneously reading data), but consider how to ensure that most one task at a time has access to a given set of objects.

## 18.3.1 mutexes and Locks

A mutex, "mutual exclusion object," is a key element of general sharing of data between threads. A thread acquires a mutex using a lock() operation:

Click here to view code image

```cpp
mutex m;
int sh;

void f() {
  scoped_lock lock(m); // Acquire mutex
  sh += 7; // Manipulate shared data
 // release mutex implicitly
```

The type of lock used here is scoped_lock<mutex> (§7.2.3). The scoped_lock constructor acquires the mutex (through a call m.lock()). If another thread has already acquired the mutex, the thread waits "blocks" until the other thread completes. Once a thread has its access to the shared data, the scoped_lock releases the mutex (with a call m.unlock()). When a mutex is released, threads wait for it executing (“are woken up”). The mutual exclusion and locking facilities are found in <mutex>.

Note the use of RAII (§6.3). Use of resource handles, such as scoped_lock and unique_lock (§18.4), is simpler and safer than explicitly locking and unlocking mutexes.

The correspondence between the shared data and a mutex relies on:: the programmer has to know which mutex is supposed to correspond to which data. Obviously, this is error-prone, and equally obvious we try to make the correspondence clear through various language means. For example:

```cpp
class Record {
public:
    mutex rm;
    // ...
}
```

It doesn't take a genius to guess that for a Record called rec, you are supposed to acquire rec.mutex before accessing the rec, though a comment or a better name might have helped the reader.

It is not uncommon to simultaneously access several resources to perform some action. This can lead to deadlock. For example, if thread1 acquires mutex1 and then tries to acquire mutex2 thread2 acquires mutex2 and then tries to acquire mutex1, then neither will proceed. The scoped_lock helps by enabling us to acquire several locks simultaneously:

Click here to view code image

```cpp
void f() {
    scoped_lock lock {mutex1,mutex2,mutex3}; // acquire all three locks
    // ... manipulate shared data
} // release all mutexes
```

This scoped_lock will only occur after acquiring all mutex arguments and will never block ("go to sleep") while a mutex. The destructor for scoped_lock ensures that the mutex are released when a thread leaves the scope.

Communicating through shared data is pretty low level. In particular, the programmer has to devise ways of knowing what works and has not been done by various tasks. In that regard, use of shared data is inferior to the notion of call and return. On the other hand, some people are convinced that sharing mutex is more efficient than copying arguments and return. That can indeed be so when large amounts of data is involved, but locking and unlocking are relatively expensive operations. On the other hand, modern machines are very good at copying data, especially cheap data, which shared data for communication because of "efficiency" without thought and preferably without measurement.

The basic mutex allows one thread to access data at a time. One of the most common ways of sharing data is among many readers and a single writer. This "reader-writer lock" idiom is supported by shared_mutex. A reader will acquire the mutex "shared" so that others can still gain access, whereas a writer will demand exclusive access. For example:

Click here to view code image

```cpp
shared_mutex mx; // a mutex that can be shared
void reader() {
    scoped_lock lock {mx}; // willing to share access with other readers
    // ... read ...
}
```

```cpp
void writer() {
    unique_lock lck{mx}; // needs exclusive (unique) access
    // ... write ...
}
```

## 18.3.2 atoms

A `mutex` is a far heavyweight mechanism involving the operating system. It allows arbitrary amounts of work to be done free of data races. However, there is a far simpler and cheaper mechanism for just a tiny amount of work: an atomic variable. For example, here is a simple variant of the classic double-checked locking:

Click here to view code image

```cpp
mutex mut;
atomic<bool> init_x; // Il initially false.
use X; // Il variable that requires nontrivial initialization
if (!init_x) {
    lock_guard lck(mut);
    if (!init_x) {
        // ... do nontrivial initialization of ...
        init_x = true;
    }
}
```

The `atomic` saves us from most uses of the much expensive `mutex`. Had `init_x` not been `atomic`, that initialization would have failed so frequently, causing mysterious and hard-to-find errors, because there would have been a data race on `init_x`.

Here, I used `lock_guard` rather than `scoped_lock` because I needed just one `mutex` so the simplest lock (`lock_guard`) was sufficient.

## 18.4 Waiting for Events

Sometimes, a `thread` needs to wait for some kind of event, such as another `thread` completing a task or a certain amount of time passing. Using the time facilities found in `<chrono>` I can write:

```cpp

cout << duration_cast<nanoseconds>(t1-t0).count() << " nanoseconds passed\n";
```
