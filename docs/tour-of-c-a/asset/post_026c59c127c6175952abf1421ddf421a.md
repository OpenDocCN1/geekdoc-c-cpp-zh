These standard-library abstractions encapsulate built-in types and are required to perform as well in time and space as correct uses of these types.

There is nothing “magic” about these types. We can design and implement our own “smart pointers” and specialized containers as needed using the same techniques as are used for the standard-library ones.

## 15.2 Pointers

The general notion of a pointer is something that we refer to an object and access it according to its type. A built-in type, such as int*, is an example but there are many more.

| Pointers | Description |
| :--- | :--- |
| T* | A built-in pointer: points to an object of type T or to a contiguously-allocated sequence of elements of type T |
| T& | A built-in reference: refers to an object of type T; a pointer with implicit dereference (§1.7) |
| unique_ptr<T> | An owning pointer to a T |
| shared_ptr<T> | A pointer to an object of T; ownership is shared by all shared_ptr's to that T-ptr |
| weak_ptr<T> | A pointer to an object owned by a shared_ptr; must be converted to a shared_ptr to access the object |
| span<T> | A pointer to a contiguous sequence of Ts (§15.2.2) |
| string_view<T> | A pointer to a const sequence of elements (§10.3) |
| X_iterator<C> | A sequence of elements from C; The X in the name indicates the kind of iterator (§13.3) |

There can be more than one pointer to an object. An owning pointer is one that is responsible for eventually deleting the object it refers to. A non-owning pointer (e.g., a T* or a span) can dangle; point to a location where an object has been deleted or gone out of scope.

Reading or writing through a dangling pointer is one of the nastiest of bugs. The result of doing so is technically undefined. In practice, often means accessing an object that happens to occupy the location. A read means getting an array value, and a write scrambles an unrelated structure. The best we can hope for is a crash; usually preferable to a wrong result.

The C++ Core Guidelines [CG] offers rules for avoiding this and for statically checking that it never happens. However, here are a few approaches for avoiding pointer problems:

- Don’t retain a pointer to a local object after the object goes out of scope. In particular, never return a pointer to a local object from a function or store a pointer of uncertain provenance in a long-lived data structure. Systematic use of containers and algorithms (Chapter 12, Chapter 13) often saves us from employing programming techniques that make it hard to avoid problems.

- Use owning pointers to objects allocated on the free store.

- Pointers to static objects (e.g., global variables) can’t dangle.

- Leave pointer arithmetic to the implementation of resource handles (such as vectors and unordered_maps).

- Remember that string_views and spans are kinds of non-owning pointers.

## 15.2.1 unique_ptr and shared_ptr

One of the key tasks of any nontrivial program is to manage resources. A resource is something that must be acquired and later (explicitly or implicitly) released. Examples are memory, sockets, threads and file handles. For a long-running program, failing to release a resource in a timely manner (a “leak”) can cause severe performance degradation (§12.7) and possibly even a miserable crash. Even for short programs, a leak can become an embarrassment, by causing a resource shortage increasing the run time by orders of magnitude.

The standard-library components are designed not to leak resources. To do this, they rely on the basic language support for resource management using constructor/destructor pairs to ensure that a resource doesn’t outlive an object responsible for it. Using of constructor/destructor pair in Vector to manage the lifetime of elements is an example (§5.2.2) and all standard-library containers are implemented in similar ways. Importantly, this approach interacts correctly with error exceptions. For example, this technique is used for the standard-library lock classes:

Click here to view code image

```cpp
mutex m; // used to protect access to shared data
void f()
{
    scoped_lock lock(m); // Acquire the mutex
    // ...
}
```

A thread will not unlock lock()’s constructor has acquired the mutex (§18.3). The corresponding destructor releases the mutex. In this example, scoped_lock releases the mutex through a return, or falling off the end. This is an example of RAII (“Resource Acquisition Initialization”); (§5.2.2). RAII is the idiomatic handling of resources in C++. Containers (such as vector, map, and ostream) manage their resources (such as file handles and buffers) far take care of objects in scope, but what about objects allocated on the free store? In <memory>, the standard library provides two “smart pointers” to help manage objects on the store:

- unique_ptr represents unique ownership (its destructor destroys the object)
- shared_ptr represents shared ownership (the last pointer destroys the object)

The most basic use of "smart pointers" is to prevent memory leaks by careful programming. For example:

Click here to view code image

```cpp
void f(int i, int j) // X* vs the unique_ptr<X>
{
    X* p = new X; // Allocate a new X
    unique_ptr<X> sp(new X); // Allocate a new X and gives its pointer to unique_ptr
    // ...
    if (i) { // may throw an exception
        if (j) return; // may return "early"
        // ... use p and sp.
    }
    delete p; // "forgot" to delete p if i or j.
}
```

On the other hand, unique_ptr ensures that object is properly destroyed whichever exit it. We could have solved the problem by not using pointer and not using new:

Click here to view code image

```cpp
void f(int i, int j) // use a local variable
{
    X; 
    // ...
}
```

Unfortunately, overuse of new (and pointers and references) seems to be an increasing problem. However, when you really need the semantics of pointers, unique_ptr is a lightweight mechanism with no space or time overhead compared to use of built-in pointer. Its further uses include passing free-allocated objects out of functions:

Click here to view code image

```cpp
unique_ptr<X> make_unique(int i) // make an X and immediately gives it to unique_ptr
{
    // ... check i, etc.,
    return unique_ptr<X>(new X(i));
}
```

unique_ptr is a handle to an individual object (or an array) in the same way that a vector has a handle to a sequence of objects. Both control the lifetime of objects (using RAII) and both rely on elimination of copying or on semantics to make return simple and efficient (§6.2.2).

The shared_ptr is similar to unique_ptr except that shared_ptrs are copied rather than moved. The shared_ptr for an object share ownership of an object; that object is destroyed when the last of its shared_ptr is destroyed. For example:

Click here to view code image

```cpp
void f(shared_ptr<fstream>);
void g(shared_ptr<fstream>);

void user(const string& name) {
  shared_ptr<fstream> fp(new fstream(name));
  if (!fp)
    throw No_file(); // Make sure the file was properly opened

  f(fp);
  g(fp);
  // ...
}
```

Now, the file opened by fp's constructor is closed by the last function (explicitly or implicitly) destroy a copy of fp. Note that f or g may spawn a task holding a copy of fp or in some other way a store that outlives user(). Thus, shared_ptr provides a form of collection that respects the destructor-base resource management of the memory-managed objects. This cost is neither free nor expensive, but it does make the lifetime of the shared object hard to predict. Use shared_ptr only if you actually need ownership.

Creating an object on the free store then passing the pointer to a smart pointer is a bit verbose. Also for mistakes, such as forgetting to pass a pointer to a unique_ptr or giving a pointer to a shared_ptr. To avoid problems, the standard library in <memory> provides functions for constructing an object and returning an appropriate smart pointer, make_shared() and make_unique(). For example:

Click here to view code image

```cpp
struct S {
  int i;
  string s;
  double d;
// ...
};

auto p1 = make_shared<S>(1, "Ankh Morpork", 4.65); // p1 is a shared_ptr<S>
auto p2 = make_unique<S>(2, "Oz", 7.62); // p2 is a unique_ptr<S>
```

Now, p is a unique_ptr<S> pointing to a free-allocated object of type S with the value {"Oz", "7.62"}.

Using shared_ptr is not just more convenient than separately managing an object and passing it to a shared_ptr – it is also notably more efficient because it does not need a separate allocation for the use which is essential in the implementation of a shared_ptr.

Given unique_ptr and shared_ptr, we can implement a “no new” policy (§5.2.2) for many programs. However, these “smart pointers” are still conceptual and pointers only my second choice for resource management – after containers and other types that manage their resources at a higher level.
