Scalar re, im;

```
public:
    static_assert(is_arithmetic_v<Scalar>, "Sorry, I support only complex of arithmetic types");
    //...
}
```

However, that – like traditional uses – is easier and more elegantly using concepts:

```
template<Arithmetic Scalar>
class complex {
    Scalar re, im;
public:
    // ...
}
```

In many cases, type predicts such as is_arithmetic disappear into the definition of concepts for greater ease of use. For example:

Click here to view code image

```
template<typename T>
concept Arithmetic = is_arithmetic_v<T>;
```

Curiously enough, there is no standard-library type predicates.

Often, we can define concepts that are more general than the standard-library types. Many standard-library type predicates apply only to the built-in types. We can define a concept in terms of the operations required, as specified by the definition of Number (§8.2.4);

Click here to view code image

```
template<typename T, typename U = T>
concept Arithmetic = Number<T,U> && Number<U,T>;
```

Most often, uses the standard-library type predicates are defined in the implementation of fundamental services, often to distinguish cases for optimization. For example, part of the implementation of std::copy(iter, lter, iter2) could optimize the performance of contiguous sequences of simple types, such as:

Click here to view code image

```
template<class T>
void copy(T* first, T* last, T* target)
{
    if constexpr (is_trivially_copyable_v<T>)
        memcpy(first, (last - first) * sizeof(T));
    else
        while (first != last) *target++ = *first++;
}
```

That optimization beat its non-optimized variant by about 50% on some implementations. Do not indulge in cleverness unless you verify that the standard doesn't already get better. Hand-optimized code is typically less maintainable than simpler alternatives.
