
## 6.5.1 Comparisons (Relational Operators)

The meaning of the equality comparisons (== and !=) is closely related to copying. After a copy,
the copies should compare equal:

Click here to view code image

```cpp
X a = something;
X b = a;
assert(a==b); // If a==b here, something is very odd ($4.5)
```

When defining ==, also define != and make sure that a!=b means !(a==b).

Similarly, if you define <, also define <=, >, >= to make sure that usual equivalences hold:

- a<b means (a<b)||(a==b) and !(b<a).
- a>b means b<a.
- a<=b means (a<=b)|(a==b) and !(b<a).

Go identical to treat operands of a binary operator, such as ==, it is best defined as
a free-standing function in the namespace of class. For example:

Click here to view code image

```cpp
namespace NX {
class X {
// ...
};
bool operator==(const X&, const X&);
// ...
};
```

The "spaceship operator," <=> is a law unto itself, its rules differ from those for all other
operators. In particular, by defining the default <= the other relational operators are implicitly
defined:

Click here to view code image

```cpp
class R {
// ...
auto operator<=>(const R& a) const = default;
};
void user(R r1, R r2) {
    bool b1 = (r1<=r2) == 0; // r1==r2
    bool b2 = (r1<=r2) < 0; // r1<r2
    bool b3 = (r1<=r2) > 0; // r1>r2

    bool b4 = (r1==r2);
    bool b5 = (r1<r2);
}
```

Like C's strcmp(), <=> implements a three-way comparison. A return value means less-
an, zero equal, and a positive value means greater-than.

If <=> is defined as non-default, == is not implicitly defined, but < and the other relational
operators are! For example:

Click here to view code image

```cpp
struct R2 {
    int m;
    auto operator<==(const R2& a) const { return a.m == m ? 0 : a.m < m ? -1 : 1; }
};
```

Here, we used the expression form of the if-statement: p?:y is an expression that evaluates the condition p and if it is true, the value of the ?: expression is x otherwise y.

Click here to view code image

```cpp
void user(R2 r1, R2 r2) {
    bool b4 = (r1==r2); // Error: no non-default ==
    bool b5 = (r1<r2); // OK
}
```

This leads to that definition of non-trivial types:

Click here to view code image

```cpp
struct R3 { /* ... */ };
auto operator<=(const R3& a, const R3& b) { /* ... */ };
bool operator==(const R3& a, const R3& b) { /* ... */ };
```

Most standard-library types, such as string and vector, follow pattern. The reason is that if a type has more than one element taking in a comparison, the default <= examines them all yielding a lexicographical order. In case, it is often worthwhile to provide a separate operator == in addition because <=> has to examine all elements to determine all three alternatives. Comparing character strings:

Click here to view code image

```cpp
string s1 = "asdfghjk";
string s2 = "asdfghjk";

bool b1 = s1==s2; // False
bool b2 = (s1<=s2); // False
```

Using a conventional == we find that the strings are not equal by looking at the number of characters. Using <=>, we have to read all the characters of s2 to find that it is less than s1 and therefore not equal.

There are many more details to operator <=, but those are primarily of interest to advanced implementers of library facilities concerned with comparisons and sorting beyond the scope of this book. Older code does not use <=.

## 6.5.2 Container Operations

Unless there is a really good reason not to, design containers in the style of the standard-library containers (Chapter 12). In particular, make the container resource safe by implementing it with a handle with appropriate essential operations (§6.1.1, §6.2).

The standard-library containers all know their number of elements and we can obtain it by calling size(). For example:

Click here to view code image

```cpp
for (size_t i = 0; i<c.size(); ++i) // size_t is the name of the type returned by a standard-library size()
    c[i] = 0;
```

However, rather traversing containers using indices from 0 to size(), the standard algorithms (Chapter 13) rely on the number of sequences delimited by pairs of iterators:

Click here to view code image

```cpp
for (auto p = c.begin(); p!=c.end(); ++p)
    *p = 0;
```

Here, c.begin() is an iterator pointing to the first element of c and c.end() points one-beyond-the-last element of c. Like pointers, iterators support ++ to move to the next element and * to access the value of the pointed-to element.

This begin() and end() are also used by the implementation of the range-for, so we can simplify loops over a range:

```cpp
for (auto& x : c)
    x=0;
```

Iterators are used to pass sequences to standard-library algorithms. For example:

```cpp
sort(v.begin(),v.end());
```

This iterator model (§13.3) allows for great generality and efficiency. For details and more container operations, see Chapter 12 and Chapter 13.

The begin() and end() can also be defined as free-standing functions; §7.2. The versions of begin() and end() for const containers are called cbegin() and cend().

## 6.5.3 Iterators and “smart pointers”

User-defined iterators (§13.3) and “smart pointers” (§15.2.1) implement the operators and aspects of a pointer for their purpose and add offset as needed.

- Access: * (for a class), and [] (for a container)
Iteration/navigation: ++ (forward), -- (backward)

## 6.5.4 Input and Output

For integers, << means left-shift, >> means right-shift. However, for iostreams, << and >> are for input and output.

## 6.5.5 swap()

Many algorithms, notably sort(), use swap(a,b) to exchange values. If you define a custom type, you should provide a non-member swap function for efficiency.

## 6.5.6 hash()

The standard-library unordered_map<K,V> uses hash<K> to compute keys. For custom types, you must provide a specialization of hash<>.

## 6.6 User-Defined Literals

User-defined literals (UDLs) allow you to create custom suffixes for literals. For example, you can define a literal for distance or time.

## 6.7 Advice

- Control construction, copy, and destruction of objects; §6.1.1; [CG: R.1].
- Design constructors, assignment, and destructor as a matched set of operations; §6.1.1; [CG: C22].
- Define all essential operations or none; §6.1.1; [CG: C21].
- If a default constructor, assignment, or destructor is appropriate, let the compiler generate it; §6.1.1; [CG: C20].
- If a class has a pointer member, consider if it needs a user-defined destructor, copy and move; §6.1.1; [CG: C32]; [CG: C33].
- If a class has a user-defined destructor, it properly provides user-defined copy and move; §6.2.1.
 By default, declare single-argument constructors explicit; §6.1.2; [CG: C46].
- If a class has a reasonable default value, provide it as a member initializer; §6.1.3; [CG: A.8]
- Redefine or prohibit copying if the default is not appropriate for a type; §6.1.1; [CG: C61].
- Return containers by value (relying on copy elision and for efficiency); §6.2.2; [CG: F20].
- Avoid explicit use of std::copy(); §16.6; [CG: ES.56].
- For large operands, use const reference argument types; §6.2.2; [CG: F16].
- Provide strong resource safety, so never leaking anything that you think of as a resource; §6.3; [CG: R.1].
