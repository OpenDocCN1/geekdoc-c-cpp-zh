# 3.2 Separate Compilation

C++ supports a notion of separate compilation where user code sees only declarations of the types and functions used. This can be done in two ways:

- *Header files (§3.2.1): Place declarations in separate files, called header files, and textually #include a header file where declarations are needed.
- *Modules (§3.2.2): Define module files, compile them separately, and import them where needed. Only explicitly exported declarations are seen by code importing the module.

Either can be used to organize a program into a set of semi-independent code fragments. Such separation can be used to minimize compilation times and to enforce separation of logically distinct parts of a program (thus minimizing the chance of errors). A library is often a collection of separately compiled code fragments (e.g., functions).
The header-file technique for organizing code goes back to the earliest days of C and is still by far the most common. The use of modules is in C++20 and offers massive advantages in code hygiene and compile time.

# 3.2.1 Header Files

Traditionally, we place declarations that specify the interface to a piece of code we consider a module in a file with a name indicating its intended use. For example:

Click here to view code image

// Vector.h:

```cpp
class Vector {
public:
    Vector(int s);
    double& operator[](int i);
    int size();
private:
    double* elem;
    int sz;
};
```

This declaration would be placed in a file Vector.h. Users then #include that file, called a header file, to access interface. For example:

Click here to view code image

// user.cpp:

```cpp
#include "Vector.h" // get Vector's interface
#include <cmath> // get the standard-library math function interface including sqrt()
double sqrt_sum(const Vector& v) {
    double sum = 0;
    for (int i = 0; i < v.size(); ++i)
        sum += sqrt(v[i]); // sum of roots
    return sum;
}
```

To help the compiler ensure consistency, the .cpp file providing the implementation of Vector also include the .h file providing its interface:

Click here to view code image

// Vector.cpp:

```cpp
#include "Vector.h" // get Vector's interface
Vector::Vector(int s)
    : elem(new double[s]), sz(s) {} // initialize members

double& Vector::operator[](int i)
{
    return elem[i];
}

int Vector::size()
{
    return sz;
}
```

The code in user.cpp and Vector.cpp shares the Vector interface presented in Vector.h, but the two files are otherwise independent and can be separately compiled. Graphically, the program fragments are represented like this:

# Vector.h:
![](img/0bd2e5eba2737c5daca16fad_0.png)

# user.cpp:
```cpp
#include "Vector.h" // use Vector
```

# Vector.cpp:
```cpp
#include "Vector.h" // define Vector
```

The best approach to program organization is to think of it as a set of modules with well-defined dependencies. Header files represent that modularity through files and exploit modularity through separate compilation. A file that is compiled by itself (including headers) is called a translation unit. A program can consist of thousands of translation units.

The use of header files and #include is a very old way of simulating modularity with significant disadvantages:

- Compilation time: You #include header.h in thousands of translation units, the text of header.h will be processed by the compiler.
- Order dependencies: If you #include header1.h before header2.h, the declarations and macros in header1.h might affect the meaning of code in header2.h. If you #include header2.h before header1.h, it is header2.h that might affect the code in header1.h.
- Inconsistencies: Defining an entity, such as a type or a function, in one file and defining it differently in another file, can lead to crashes or subtle errors. This happens if you – accidentally or deliberately – declare an entity separately in two files, rather than putting it in a header.
- Transitivity: All code that needs to access a declaration in a header file must be present in that header file. This results in the user of a header file – accidentally or deliberately – becoming dependent on implementation details.

Obviously this is not ideal, and this technique has been a major source of cost and bugs since it was first introduced in C in the early 1970s. However, use of header files has been viable for decades and old code using #include will “live” for a long time because it can be costly and time consuming to update large programs.

# 3.2.2 Modules

In C++20, we have a natively supported way of directly expressing modularity (§19.2.4). Consider how to express the Vector and sqrt_sum() example from §3.2 using modules:

Click here to view code image

```cpp
export module Vector // defining the module called "Vector"

export class Vector {
public:
    Vector(int s);
    double& operator[](int i);
    size_t size();
private:
    double* elem; // elem points to an array of sz-sized doubles
    int sz;
};
```

```cpp
Vector::Vector(int s)
    : elem(new double[s]), sz(s)
{} // initialize members

double& Vector::operator[](int i) {
    return elem[i];
}

int Vector::size() {
    return sz;
}

export bool operator==(const Vector& v1, const Vector& v2) {
    if (v1.size() != v2.size())
        return false;
    for (int i = 0; i < v1.size(); ++i) {
        if (v1.elem[i] != v2.elem[i])
            return false;
    }
    return true;
}
```

This defines a module called Vector, which exports the class Vector, all its member functions, and the non-member function defining operator ==.

The way we use this module is to import where we need it. For example:

Click here to view code image

// file user.cpp:

```cpp
import Vector;      // get Vector's interface
#include <cmath>     // get the standard-library math function interface including sqrt()

double sqrt_sum(Vector& v)
{
    double sum = 0;
    for (int i = 0; i < v.size(); ++i)
        sum += sqrt(v[i]); // sum of roots
    return sum;
}
```

The differences between headers and modules are compiled only (rather than in each translation unit which it is used):

- A module is compiled only (rather than in each translation unit which it is used).
- Two modules can be imported in either order without changing their meaning.
- If you import or include putting something into a module, users of your module do not implicitly gain access to all: import is not transitive.

The effects on maintainability and compile-time performance can be spectacular. For example, I have measured the "Hello, World!" program using

import std;

to compile 10 times faster than the version using

#include<iostream>

This is achieved despite the fact that module std contains the whole standard library, more than 10 times as much information as the <iostream> header. The reason is that modules only export interfaces whereas a header delivers all that directly or indirectly to the compiler. This allows us to use large modules so that we don't have to worry of a bewildering collection of headers (§3.4) to #include.

Unfortunately, module std is not of C++20. Appendix A explains how to get a module std if a standard-library implementation doesn't yet supply it.

When defining a module, we do not have to separate declarations and definitions into separate files; if we can import our source code organization, but we don't have to. We could define the simple Vector module like this:
