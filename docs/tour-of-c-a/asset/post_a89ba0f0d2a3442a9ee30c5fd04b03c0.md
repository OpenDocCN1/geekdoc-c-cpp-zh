
Consider defining a "smart pointer":

Click here to view code image

```cpp
template<typename T>
class Smart_pointer {
  // ...
  T& operator->() const;
  T* operator->() const; // should work if only if T is a class
};
```

The -> should be defined if and only if T is a class. For example, Smart_pointer<vector<T>> should have ->, Smart_pointer<int> should not.
We cannot use a compile-time if because we are not inside function. Instead, we read

Click here to view code image

```cpp
template<typename T>
class Smart_pointer {
  // ...
  T& operator->() const;
  T* operator->() const requires is_class<T>; // is defined if only if T is a class
};
```

The type predicate directly expresses the constraint on operator->(). We also use concepts for that. There is no-standard concept requiring a type to be a class type (that is a class, struct, or union), but we could define one:

Click here to view code image

```cpp
template<typename T>
concept Class = is_class<T> || is_union<T>; // Illegal unions
```

```cpp
template<typename T>
class Smart_pointer {
  // ...
  T& operator->() const;
  T* operator->() const requires Class<T>; // is defined if and only if T is a class or union
};
```

Often, a concept is more general or simply more appropriate than the direct use of a standard-library predicate.

## 16.4.3 Type Generators

Many type functions return types, new types that they compute. I call such functions generators to distinguish them from the type predicates. The standard offers a few, such as:

| Selected Type Generators | Description |
|---|---|
| R=remove_const_t<T> | R is T with the topmost const (any) removed |
| R=add_const_t<T> | R is const T |
| R=remove_reference_t<T> | if T is a reference U&, R is U otherwise T |

```cpp
R=add_l_reference<T> if T is an lvalue reference, R is T otherwise T&
R=add_r_reference<T> if T is an rvalue reference, R is otherwise T&
R=enable_if_t<b,T,void> if b is false, R is T otherwise R is not defined
R=conditional_t<b,T,U> R if b is true; U other
R=common_type<Ts>... if there is a type that Ts can be implicitly converted to, R is that type; otherwise R is not defined
R=underlying_type<T> if T is an enumeration, R is its underlying type; otherwise error
R=invoke_result<T,A>... if a T can be called with arguments A..., R is its return type; otherwise error
```

These types are properly used in the implementation of utilities, rather than in application code. Of these, enable_if is probably the most common in pre-concepts code. For example, the conditionally enabled -> for a smart pointer is traditionally implemented something like this:

Click here to view code image

```cpp
template<typename T>
class Smart_pointer {
// ...
T& operator->();
enable_if_is_class_v<T>> operator->(); // is defined if and only if T is a class
};
```

I don't find easily to read and more complicated uses are far worse. The definition of enable_if relies on a subtle language featured SFINAE ("Substitution Failure Is Not An Error"). Look up that (only) if you need to.

## 16.5 source_location

When writing out a trace message or an error message, we often want to make a source location part of that message. The library provides source_location for that:

Click here to view image

```cpp
const source_location loc = source_location::current();
```

That current() returns a source_location describing the spot in the source code where it appears. Class source_location has file() and function_name() members returning C-style strings and line() and column() members returning unsigned integers.
Wrap that in function and we have a good cut of a logging message:

Click here to view image

```cpp
void log(const string& msg = {}, const source_location loc = source_location::current())
{
  cout << loc.file_name() << ': '
    << loc.line() << ': ' << loc.column() << " " 
    << loc.function_name() << ": "
    << msg;
}
```

The call of current() is a default argument so we get the location of the caller of log(t) rather than the location of log():

Click here to view image

```cpp
void foo()
{
  log("Hello"); // myfile.cpp (17,4) foo
  ...
}
```

```cpp
int bar(const string& label)
{
  log(label); // myfile.cpp (23,4) bar: the value of label
  ...
}
```

Code written before C++20 or needing to compile on older compilers uses __FILE__ and __LINE__ for this.

## 16.6 move() and forward()

The choice between moving and copying is mostly implicit (§3.4). A compiler will prefer to move when an object is about to be destroyed (as in return) because that's simpler and more efficient operation. However, we must be explicit. For example, unique_ptr is the sole owner of an object. It cannot be copied, so if you want unique_ptr elsewhere, you must move it.

Click here to view image

```cpp
void f()
{
  auto p = make_unique<int>(2);
  auto q = p; // error: can't copy unique_ptr
  auto q = move(p); // p now holds nullptr
  ...
}
```

Confusingly, std::move() doesn't move anything. Instead, it casts its argument to an rvalue reference, saying that its argument will not used again and therefore may be moved (§6.2). It should have been called rvalue_cast. It exists to serve a few cases. Consider a simple swap:

Click here to view image

```cpp
template <typename T>
void swap(T& a, T& b) {
    T tmp(move(a));
    a = move(b);
    b = move(tmp);
}
```

We don't repeatedly copy large objects, but request moves using std::move(). For other cases, it is tempting, dangerous. Consider:

Click here to view image

```cpp
string s1 = "Hello";
string s2 = "World";
vector<string> v;
v.push_back(s1);
v.push_back(move(s2));
v.emplace_back(s1); // s1 is copied whereas s2 is moved. The problem is that a moved-from object is left behind. If we use s2 again, we have a problem:

Click here to view image

```cpp
cout << s1;
cout << s2; // consider this use of std::move() to be error-prone for widespread use. Don't use it unless you can demonstrate significant and necessary performance improvement.
```

Later maintenance may accidentally intend the use of moved-from object. The compiler knows that a value is not used in a function, so using an explicit std::move(x), is redundant and can inhibit optimizations. All standard-library types leave a moved-from object in a state that is unspecified, but it can be destroyed and assigned. It may be unwise to follow that. For a container (e.g., vector or string), the moved-from state will be “empty.” For many types, the default value is a good state: meaningful and cheap to establish.

Forwarding arguments are an important case that requires moves (§8.4.2). We want to transmit a set of arguments on another function without changing anything (to achieve “perfect forwarding”):

Click here to view image

```cpp
template<typename T, typename... Args>
unique_ptr<T>(Args&&... args) {
    return unique_ptr<T>(new T(std::forward<Args>(args)...));
}
```

The standard-library forward() differs by correctly handling std::move() to do with lvalue and rvalue (§6.2.2). Use std::forward() exclusively for forwarding and don't forward() twice; once you have forwarded an object, it's not yours to use anymore.
