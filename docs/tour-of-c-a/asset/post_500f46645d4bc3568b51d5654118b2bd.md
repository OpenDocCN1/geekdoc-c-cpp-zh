## 4.3 Invariants

The use of exceptions to signal out-of-range access is an example of a function checking its argument and refusing to act because a basic assumption, a precondition, didn't hold. We had formally specified Vector's subscript operator, we would have said something like "the index must be in [0:size()) range," and that is what we tested in our operator[](j). The [a:b) notation specifies a half-open range, meaning that a is part of the range, but b is not. Whenever we define a function, we should consider what its preconditions are and consider whether to test them ($4.4). For most applications it is a good idea to test simple invariants; we also $4.5.

However, operator[](j) operates on objects of type Vector and nothing it makes any sense unless the members of Vector have "reasonable" values. In particular, we say "elem points to an array of sz doubles" but we only said that in a comment. A statement of what is assumed to be true for a class is called class invariant, or simply invariant. It is the job of a constructor to establish the invariant for its class (so that the functions can rely on it) and for the members to make sure that the invariant holds when they exit.

Unfortunately, Vector partially did it. It properly initialized the Vector members, but it failed to check that the arguments to it made sense. Consider:

```cpp
Vector v(27);
```

This is likely to cause chaos.

Here is a more appropriate definition:

```cpp
Vector:(int s)
{
    if (s<0)
        throw length_error("Vector constructor: negative size");
    elem = new double[s];
    sz = s;
}
```

I use the standard-library exception length_error to report a number of elements because some standard-library operations use that exception to report problems of this kind. If operator new cannot find memory to allocate, it throws a std::bad_alloc. We can now write:

```cpp
void test(int n) {
  try {
    Vector v(n);
  }
  catch (std::length_error& err) {
    // ... handle negative size ...
  }
  catch (std::bad_alloc& err) {
    // ... handle memory exhaustion ...
  }
}
```

```cpp
void run() {
  test(-27);
  test(1 000 000 000);
  test(10);
}
```

Memory exhaustion occurs if you ask for more memory than the machine offers or if your program already has consumed almost much and your requests pushes over the limit. Note that modern operating systems typically give you more space than will fit in physical memory at once, so asking for too much can cause serious slowdown before triggering bad_alloc.

You can define your own classes to be used as exceptions and carry them as little or as much information as you need from a point where an error is detected to a point where it can be handled ($4.2). It is not necessary to use the standard-library exception hierarchy.

Often, a "handling" an exception meaning does some minimal local cleanup and rethrowing the exception. For example:

```cpp
void test(int n) {
  try {
    Vector v(n);
  }
  catch (std::length_error& err) {
    cerr << "test failed: length error\n";
    throw; // rethrow
  }
  catch (std::bad_alloc&) {
    // or! this program is not designed to handle memory exhaustion
    std::terminate(); // terminate the program
  }
}
```

In well-designed code try-blocks are rare. Avoid overuse by systematically using the RAII technique ($5.2.2, $6.3).

The notion of invariants is central to the design of classes, and preconditions serve a similar role in the design of invariants:

- Formulating invariants helps us to understand precisely what we want.
- Invariants force us to be specific; this gives us a better chance of getting our code correct.

The notion of invariants underpins C++'s notions of resource management supported by constructors (Chapter 5) and destructors ($5.2.2, $15.2.1).
