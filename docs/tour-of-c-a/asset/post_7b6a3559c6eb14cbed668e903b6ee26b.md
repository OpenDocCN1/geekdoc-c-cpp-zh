
(§12.3). Finally, S's iterator type must be at least input_iterator, and the value types of the elements and the iterator must be the same.

The hardest concepts to define are the ones that represent fundamental language concepts. For a useful collection, it is best to use a set from established library. See §14.5. In particular, there is a standard-library concept that allows us to bypass the complexity of the definition of Sequence:

Click here to view code image

```
template<typename S>
concept Sequence = input_range<S>; // Simple to write and general
```

Had restricted my notion of "S's value type to S::value_type, I could have used a simple Value_type:

Click here to view code image

```
template<class S>
using Value_type = typename S::value_type;
```

That's a useful technique for expressing simply concepts and hiding complexity. The definition of the standard value_type_t is fundamentally similar, but a bit more complicated because it handles sequences that don't have a member called value_type (e.g., built-in arrays).

# 8.2.4.1 Definition Checking

The concepts specified for a template are used to check arguments at the point of use of the template. They are not used to check the use of the parameters in the definition of the template. For example:

Click here to view code image

```
template<equality_comparable T>
bool comp(T a, T b)
{
  return a<b;
}
```

Here the concepts guarantee the presence of == but not:

```
bool b0 = comp(cout,cerr); // error: ostream doesn't support ==
bool b1 = comp(2,3); // OK: returns true
bool b2 = comp(2+1,3+4); // error: complex<double> doesn't support <
```

The check catches the attempt to pass ostreams, but accepts the ints because those types support ==. However, int support <= so comp(2,3) compiles, where comp(2+1,3+4) is rejected when the body of comp() is checked and instantiated for complex<double>

Delaying the final check of the template until instantiation gives two benefits:

- We can use incomplete concepts during development. That allows us to gain experience while developing concepts, types, and algorithms, and to gradually improve checking.
- We can insert debug, tracing, telemetry, etc. code into a template without affecting its interface. Changing an interface can cause massive recompilation.

Both are important when developing and maintaining large code bases. The price we pay for that important benefit is some errors, such as using < where only == is guaranteed, as are caught very late in the compilation process (§8.5).

# 8.2.5 Concepts and auto

The keyword auto can be used to indicate that an object should have the type of its initializer (§1.4.2).

Click here to view code image

```
auto x = 1;               // x is an int
auto z = complex<double>(1,2); // z is a complex<double>
```

However, initialization doesn't just take place in the variable definitions:

Click here to view code image

```
auto g(auto i) { return i; }      // g(i) returns int
int f(auto x) { return x; }     // f takes an argument of any type
int x = f(1);                    // f(1) takes an int
int z = f(complex<double>(1,2)); // f takes a complex<double>
```

The keyword auto allows constrained constraint for a value: simply requires that it be some value of type. Using auto parameter makes a function into a function template.
Given contexts, we can strengthen constraints of all initializations by preceding auto by a Concept. For example:

Click here to view code image

```
auto twice(Arithmetic auto x) { return x+x; } // Ill for numbers
auto thrice(auto x) { // Ill for anything with a +

auto x1 = twice(7);      // OK: x=14
string s = "Hello";
auto x2 = twice(s);      // error: a string is not Arithmetic
auto x3 = thrice(s);     // OK: s=="Hello Hello" *
}
```

In addition to this use for constraining function arguments, concepts can constrain the initialization of variables:

Click here to view code image

```
auto ch1 = open_channel("foo");      // Ill works with whatever open_channel(channel) returns
Arithmetic ch2 = open_channel("foo"); // error: a channel is not Arithmetic
Channel auto ch3 = open_channel("foo"); // OK: assuming Channel is an appropriate constraint
```
Ill and that open_channel(channel) returns one.

This comes in very handy to counter overuse of auto and to document requirements in code using generics.

For readability and debugging it is important that a type error is caught as close to the origin as possible. Constraining a return type can help:

Click here to view code image

```
Number auto some_function(int x)
{
    //...
    return fct(x); // an error unless fct(x) returns a Number
    //...
}
```

Naturally, we could have achieved this by introducing a local variable:

Click here to view code image

```
auto some_function(int x)
{
    //...
    Number auto y = fct(x); // An error unless fct(x) returns a Number
    return y;
    //...
}
```

However, that’s a bit verbose and not all types can be cheaply copied.

# 8.2.6 Concepts and Types

A type

- Specifies the set of operations that can be applied to an object, implicitly and explicitly
- Relies on function declarations and language rules
- Specifies how an object is laid out in memory

A single-argument concept

- Specifies the set of operations that can be applied to an object, implicitly and explicitly
- Relies on use patterns reflecting function declarations and language rules
- Says nothing about the layout of the object
- Enables the use of a set of types

Thus, constraining code concepts gives more flexibility than constraining with types. In addition, concepts can define the relationship between several arguments. My ideal is that eventually functions will be defined as template functions with their arguments constrained by concepts. Unfortunately, the support for that is not yet perfect: we have to use a concept as an adjective, rather than a noun. For example:

| void sort(Sortable auto&); | 'auto' required |
| void sort(Sortable&); | // error: 'auto' required after concept name |

# 8.3 Generic Programming

The form of generic programming directly supported by C++ centers around the idea of abstracting from concrete examples with data representations to produce a wide variety of useful software [Stepanov,2009]. The abstractions that represent fundamental operations and data structures are concepts.

# 8.3.1 Use of Concepts

Good, useful concepts are fundamental and are discovered more than they designed. Examples are integer and floating-point number (as defined in Classic C [Kernighan,1978]), sequence, and more mathematical concepts, such as ring and vector space. They represent the fundamental concepts of a field of application. And that is why they are called “concepts”. Identifying and formatting concepts to the degree necessary for generic programming can be a challenge.

For basic use, the concept regular (§14.5). A type is regular when it behaves much like int or a vector. An object of a regular type

- can be default
- can be copied (with the usual semantics of copy, yielding two objects that are independent and compare equal) using a constructor or an assignment.
- can be compared using == and !=.
- doesn't suffer technical problems from overly clever programming tricks.

A string is another example of a regular type. Like int, string is also totally_ordered (§14.5). That is, two strings can be compared using <, >, and <= with the appropriate semantics.
A concept is not a syntactic notation, but it is fundamentally about semantics. For example, don't define + to divide; that would not match the requirements for any reasonable number. Unfortunately, we do not yet have any language support for expressing semantics, so we have to rely on expert knowledge and common sense to get semantically meaningful concepts. Do not define semantically meaningless concepts, such as Addable and Subtractable. Instead, rely on domain knowledge to define concepts that match fundamental concepts in an application domain.

# 8.3.2 Abstraction Using Templates

Good abstractions are carefully grown from concrete examples. It is not a good idea to try “abstract” by trying to prepare for every conceivable need and technique; in that direction leads inelegance and code bloat. Start with one – and preferably more – concrete examples from real use to eliminate unnecessary details. Consider:

Click here to view code image

```
double sum(const vector<int>& v) {
  double res = 0;
  for (auto x : v) {
    res += x;
  }
}
```
