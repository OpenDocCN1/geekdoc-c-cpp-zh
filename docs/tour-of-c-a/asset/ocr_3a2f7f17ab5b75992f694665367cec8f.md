The shared_ptr for an object share ownership of an object; that object is destroyed when the last of its shared_ptr is destroyed. For example:

Now, the file opened by fp's constructor is closed by the last function (explicitly or implicitly) destroy a copy of fp. Note that ft or g may spawn a task holding a copy of fp or in some other way a store that outlives user(). Thus, shared_ptr provides a form of collection that respects the destructor-base resource management of the memory-managed objects. This cost is neither free nor expensive, but it does make the lifetime of the shared object hard to predict. Use shared_ptr only if you actually need ownership.

Creating an object on the free store then passing the pointer to a smart pointer is a bit verbose. Also for mistakes, such as forgetting to pass a pointer to a unique_ptr or giving a pointer to pointing is a shared_ptr. To avoid problems, the standard library in <memory> provides functions for constructing an object and returning an appropriate smart pointer, make_shared() and make_unique(). For example:

```
struct S {
  int i;
  string s;
  double d;
// ...
};
```

```
auto p1 = make_shared<S>(1,"Ankh Morpork",4.65); // p1 is a shared_ptr<S>
auto p2 = make_unique<S>(2,"Oz",7.62); // p2 is a unique_ptr<S>
```

Now, p is a unique_ptr<S> pointing to a free-allocated object of type S with the value {"Oz","7.62"}.

Using shared_ptr is not just more convenient than separately managing an object and passing it to a shared_ptr – it is also notably more efficient because it does not need a separate allocation for the use which is essential in the implementation of a shared_ptr.
