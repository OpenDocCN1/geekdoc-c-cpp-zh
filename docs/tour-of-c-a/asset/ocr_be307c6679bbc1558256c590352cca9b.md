);

The standard-library function forward() (§ 16.6) is used to move the arguments unchained from the InputChannel constructor to the Transport constructor.

The point is that the writer of InputChannel can construct an object of type Transport without knowing what arguments are required to construct a particular Transport. The implementer of InputChannel needs only to know the common user interface for all Transport objects.

Forwarding is very common in functional libraries where generality and low run-time overhead are necessary and very general interfaces are common.

# 8.5 Template Compilation Model

At the point of use, the arguments for a template are checked against its concepts. Errors found here will be reported immediately. What cannot be checked at this point, such as arguments for unconstrained template parameters, is postponed until code is generated for the template with a set of arguments: "template instantiation."

An unfortunate side of instantiation-type checking is that a type error can be detected uncomfortably (§8.2.4.1). Also checking results in spectacularly bad error messages because the compiler does not have type information giving to the programmer's intent and detects problem only after combining information from several places in the program.

The instantiation-type checking for templates checks the use of arguments in the template definition. This provides a compile-time variant of what is often called duck typing ("If it walks like a duck and it quacks like a duck, it's a duck”). Or – using more technical terminology – operate on values, and the presence and meaning of an operation depend solely on its operand values. This differs from the alternative view that "live" in objects. This is the way we determine the presence and meaning of operations. Values (e.g., variables) work in C++, and only values that meet an object's requirements can be put into it. What is done at compile using templates most not involve objects, only values. The exception is locals in a constexpr function (§1.6) that are used as objects inside the compiler.

To use an unconstrained template, its definition (not just its declaration) must be in scope point of use. When using header files and #include, this means that templates are found in header files, rather than .cpp files. For example, the standard <vector> holds the definition of vector.

This changes in the same way for use modules (§3.2.2), the source code can be organized the same way for ordinary functions and template modules. A module is semi-compiled into a representation that makes it fast to import and use. Think of that representation as an easily traversed graph containing all available scope and type information and supported by a symbol allowing quick access to individual entities.
