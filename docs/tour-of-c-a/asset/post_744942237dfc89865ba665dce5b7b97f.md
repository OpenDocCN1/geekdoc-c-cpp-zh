
I didn't even have to launch a thread; by default, this_thread can refer to the one and only thread.
Used duration_cast to adjust the clock's units to the nanoseconds I wanted.

The basic support for communicating external events is provided by condition_variables found in <condition_variable>. A condition_variable is a mechanism allowing one thread to wait for another. In particular, it allows a thread to wait for some condition (if called an event) as the result of work done by other.

Using condition_variables supports many forms of elegant and efficient sharing but can be rather tricky. Consider the classic example of threads communicating by passing messages through a queue. For simplicity, I declare the queue and the mechanism for avoiding race conditions on that queue global to the producer and consumer:

Click here to view code image

```
class Message {
    // Object to be communicated
    //...
};

queue<Message> mqueue;
condition_variable mcond;
mutex mtx;
```

The types queue, condition_variable, and mutex are provided by the standard library.
The consumer() reads and processes Messages:

Click here to view code image

```
void consumer() {
    while(true) {
        unique_lock lock(mtx);
        mcond.wait(lock, [] { return !mqueue.empty(); }); // Acquire mtx
                                            // Release mtx and wait;
                                            // Re-acquire mtx upon wakeup
                                            // Doesn't wake up unless mqueue is non-empty

        auto m = mqueue.front();
        mqueue.pop();
        lock.unlock();
        // Get the message
        // Release mtx

        // ... process m
    }
}
```

Here, I explicitly protect the operations on the queue and the condition_variable with a unique_lock on the mutex. Waiting on a condition_variable releases its lock until the wait is over (or the queue is non-empty) and reacquires it. The explicit check of the condition, here mqueue.empty(), protects against waking up just that some other task has "gotten first" so that the condition no longer holds. For two reasons:

- We need to pass the lock to the condition_variable's wait(). A scoped_lock cannot be moved, but a unique_lock can be.
- We want to unlock the mutex protecting the condition variable before processing the message. A unique_lock offers operations, such as lock() and unlock(), for low-level control of synchronization.

On the other hand, unique_lock can handle only a single mutex.

The corresponding producer looks like this:

Click here to view code image

```
void producer() {
  while(true) {
    Message m;
    // ... fill the message ...
    scoped_lock lck (mutex);
    mqueue.push(m);
    mcond.notify_one();
  }
}
```

# 18.5 Communicating Tasks

The standard library provides few facilities to allow programmers to operate at the conceptual level of tasks (work to potentially be done concurrently) rather than directly at the lower level of tasks and locks:

- future and promise for returning a value from a task spawned on a separate thread
- packaged_task to help launch tasks and connect up the mechanisms for returning a value
- async() for launching of a task in a manner very similar to calling a function

These facilities are found in <future>.

# 18.5.1 future and promise

The important point about future and promise is that they enable a transfer of a value between two tasks without explicit use of lock; "the system" implements the transfer efficiently. The basic idea is simple: when a task wants to pass a value to another, it puts the value into a promise. Somehow, the implementation makes value appearing in the corresponding future, from which it can be read (typically by the launcher of the task) graphically:

![](img/0bd2e25eba2737c3c5daca16fad1b65b_264_0.png)

If we have a future<X> called fx, we can get() a value of type X from it: 

Click here to view code image

```
X = fx.get(); // If necessary, wait for the value to get computed
```

If the value isn't there yet, our thread is blocked until it arrives. If the value couldn't computed, get() might throw an exception from the system or transmitted from the promise.

The main purpose of a promise is to provide "put" operations (called set_value() and set_exception()) to match future's get(). The names "future" and "promise" are historical; please not blame or credit them. They are another fertile source of puns.

If you have a promise and need a result of type X to a future, you can do one of two things: pass a value or an exception. For example:

Click here to view code image

```
void f(promise<X>& px) // a task: place the result in px
{
  // ...
  try {
    X res;
    // ... compute a value for res *
    px.set_value(res);
  } catch (...) {
    // oops: couldn't compute res
    px.set_exception(current_exception()); // pass the exception to the future's thread
  }
}
```

The current_exception() refers to the caught exception.

To deal with an exception transmitted through a future, the caller of get() must be prepared to catch it somewhere.

Click here to view code image

```
void g(future<X>& fx) // a task: get the result from fx
{
  // ...
  try {
    X v = fx.get(); // if necessary, wait for the value to get computed
    // ... use v
  } catch (...) {
    // oops: someone couldn't compute v
    // ... handle error ...
  }
}
```

If the error doesn't need to be handled by g() itself, the code reduces to the minimal:

Click here to view code image

```
void g(future<X>& fx) // a task: get the result from fx
{
  // ...
  X v = fx.get(); // if necessary, wait for the value to get computed
  // ... use v
}
```

Now, an exception from fx's function (f()) is implicitly propagated to g()'s caller, exactly as it would have been if g() called f() directly.

# 18.5.2 packaged_task

How do we get a future that needs a task and the corresponding promise? The packaged_task type is provided to simplify up tasks connected with futures. For example like the code shown in §18.5.1. we can use two tasks to add each of the elements of a vector<double> using the standard-library accumulate():

Click here to view code image

```
double accumulate(vector<double>::iterator end, vector<double>:: double init)
{
    return accumulate("begin", &end, init);
}

double comp2(vector<double>& v)
{
    packaged_task pt0(accum); // Il package the task (i.e., accum)
    packaged_task pt1(accum);

    future<double> f0 (pt0.get_future()); // Il get hold of pt0's future
    future<double> f1 (pt1.get_future()); // Il get hold of pt1's future

    double* first = &v[0];
    thread t1 (move(pt0), first, first+v.size()/2,0); // Il start a thread for pt0
    thread t2 (move(pt1), first+v.size()/2,first+v.size(),0); // Il start a thread for pt1
    // ...

    return f0.get()+f1.get(); // Il get the results
```

The packaged_task takes the type of the task as its constructor argument (here, The move) double(double,double,double) and the task as its constructor argument (here, accum). Operations performed using a packaged_task cannot be copied. The reason that a packaged_task cannot be copied is that it is a resource: it owns its promise and (indirectly) responsible for whatever its task may use.
