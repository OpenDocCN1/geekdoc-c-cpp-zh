The correspondence between the shared data and a mutex relies on:: the programmer has to know which mutex is supposed to correspond to which data. Obviously, this is error-prone, and equally obvious we try to make the correspondence clear through various language means. For example:

```
class Record {
public:
    mutex rm;
    // ...
}
```

It doesn't take a genius to guess that for a Record called rec, you are supposed to acquire rec.mutex before accessing the rec, though a comment or a better name might have helped the reader.

It is not uncommon to simultaneously access several resources to perform some action. This can lead to deadlock. For example, if thread1 acquires mutex1 and then tries to acquire mutex2 thread2 acquires mutex2 and then tries to acquire mutex1, then neither will proceed. The scoped_lock helps by enabling us to acquire several locks simultaneously:

```
void f() {
    scoped_lock lock {mutex1,mutex2,mutex3}; // acquire all three locks
    // ... manipulate shared data
} // release all mutexes
```

This scoped_lock will only occur after acquiring all mutex arguments and will never block ("go to sleep") while a mutex. The destructor for scoped_lock ensures that the mutex are released when a thread leaves the scope.

Communicating through shared data is pretty low level. In particular, the programmer has to devise ways of knowing what works and has not been done by various tasks. In that regard, use of shared data is inferior to the notion of call and return. On the other hand, some people are convinced that sharing mutex is more efficient than copying arguments and return. That can indeed be so when large amounts of data are involved, but locking and unlocking are relatively expensive operations. On the other hand, modern machines are very good at copying data, especially cheap data, which shared data for communication because of "efficiency" without thought and preferably without measurement.

The basic mutex allows one thread to access data at a time. One of the most common ways of sharing data is among many readers and a single writer. This "reader-writer lock" idiom is supported by shared_mutex. A reader will acquire the mutex "shared" so that others can still gain access, whereas a writer will demand exclusive access. For example:

```
shared_mutex mx; // a mutex that can be shared
void reader() {
    scoped_lock lock {mx}; // willing to share access with other readers
    // ... read ...n}
```
