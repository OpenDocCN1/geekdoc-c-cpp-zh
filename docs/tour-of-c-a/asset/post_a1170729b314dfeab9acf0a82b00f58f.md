
template<Sequence Seq, Arithmetic<range_value_t<Seq>> Num
sum(Seq s, Num n);

In cases where we cannot yet use concepts, we have to make do with naming conventions and comments, such as:

Click here to view code image

```
template<typename Sequence, typename Number>
requires Arithmetic<range_value_t<Sequence>,Number>
Number sum(Sequence s, Number n);
```

Whatever we choose, it is important to design a template with semantically meaningful constraints on its arguments (§8.2.4).

## 8.2.2 Concept-based Overloading

Once we have properly specified templates with their interfaces, we can overload based on their properties, such as we do for functions. A slightly simplified standard-library function advance() that advances an iterator (§13.3).

Click here to view code image

```
template<forward_iterator Iter>
void advance(Iter p, int n)    // Il move p elements forward
{
    while (n--)
        ++p;                        // Il a iterator has ++, but not or += =
}
```

```
template<random_access_iterator Iter>
void advance(Iter p, int n)    // Il move p elements forward
{
    p+=n;                        // Il a random-access iterator has += =
}
```

The compiler will select the template with the strongest requirements met by the arguments. In this case, a list provides sufficient iterators, but a vector offers random-access iterators, so we get:

Click here to view code image

```
void user(vector<int>::iterator vip, list<string>::iterator lsp)
{
    advance(vip,10);             // Il uses the fast advance()
    advance(lsp,10);             // Il uses the slow advance()
}
```

Unlike overloading, this is a compile-time mechanism implying no run-time cost, and the compiler does not find a best choice, it gives an ambiguity error. For concept-based overloading are far simpler than for general overloading (§1.3). Consider first single argument for several alternative functions:

- If the argument doesn't match the concept, alternative cannot be chosen.
- If the argument matches the concept for just one alternative, alternative is chosen.
- If arguments from two alternatives match a concept and one is stricter than the other (match all requirements of the other and more), alternative is chosen.
- If arguments from two alternatives are equally good matches for a concept, we have an ambiguity.

For an alternative to be chosen it must be:

- a match for all of its arguments, and
- at least one equally good match for all arguments as other alternatives, and
- a better match for at least one argument.

## 8.2.3 Valid Code

The question of whether a set of template arguments offers what a template requires of its template parameters boils down to whether some expressions are valid.

Using a requires-expression, we can check if a set of expressions is valid. For example, we might try to write advance() without the use of the standard-library concept random_access_iterator:

Click here to view code image

```
template<forward_iterator Iter>
requires(Iter p, int i) { p[i]; p++; } // Iter has subscribing and integer addition
void advance(Iter p, int n) { // Move p n elements forward
 p+=n;
```

No, that requires is not a type. The first requires is the requirements-clause and the second requires is the requires-expression

Click here to view code image

```
requires(Iter p, int i) { p[i]; }
```

A requires-expression is a predicate that is true if the statements in it are valid code and false if not.

I consider requires-expressions the assembly code of generic programming. Like ordinary assembly code, they are extremely flexible and no programming discipline. In some form or other, they are at the bottom of most interesting generic code, just assembly code, should not be seen in order code. By being the implementation of abstractions. If you use requires in your code, it is probably too low level and will become a problem.

The use of requires in advance() is deliberately in and hackish. Note that I "forget" to use += and the required return types for the operations. Some uses of the version of advance() will pass concept checking and not compile. The proper random-access version of advance() is simpler and more readable:

Click here to view code image

```
template<random_access_iterator Iter>
void advance(Iter p, int n) // Move p n elements forward
{
  p+=n; // A random-access iterator has +=
}
```

Prefer use of named concepts with well-specified semantics (§8.2.4) and primarily use requires-expressions in the definition of those.

## 8.2.4 Definition of Concepts

We find useful concepts, such as forward_iterator in libraries, (§14.5). As classes and functions, it is much easier to use a concept from a good library to write a new one, but simple concepts are not hard to define. Names from the standard library, such as random_access_iterator and vector, are in lower case. Here, I use the convention to capitalize the names of concepts I have defined myself, such as Sequence and Vector.

A concept is a compile-time predicate specifying what and the result of those can be used. Consider first one of the following examples:

Click here to view code image

```
template<typename T>
concept Equality_comparable =
requires (T a, T b) {
  { a == b } -> Boolean; // compare Ts with ==
  { a != b } -> Boolean; // compare Ts with !=
};
```

Equality_comparable is the concept we use to ensure that we can compare values of a type equal and non-equal. We say that given two values of the type, they must be comparable using == and != and the result of those operations must be boolean. For example:

Click here to view code image

```
static_assert(Equality_comparable<int>); // succeeds
struct S { int a; };
static_assert(Equality_comparable<S>); // fails because structs do not automatically generate == and !=
```

The definition of the concept Equality_comparable is exactly like the English description and not longer. The value of a concept is always boolean.

The result of { ... } is perceived as a concept. Unfortunately, there isn't a standard-library concept, so I defined one (§14.5). Boolean simply means a type that can be used as a condition.

Defining Equality_comparable to handle heterogeneous comparisons is almost as easy:

Click here to view code image

```
template<typename T, typename T2=T>
concept Equality_comparable =
requires (T a, T b) {
  { a == b } -> Boolean; // compare Ts with ==
  { a != b } -> Boolean; // compare Ts with !=
  { a == b } -> Boolean; // compare Ts with ==
  { a != b } -> Boolean; // compare Ts with !=
};
```

The typename T2 = T says if we don't specify a second argument, T2 will be the same as T. We can test Equality_comparable like this:

Click here to view code image

```
static_assert(Equality_comparable<int>); // succeeds
static_assert(Equality_comparable<int,double>); // succeeds (T2 is defaulted to int)
static_assert(Equality_comparable<int,string>); // fails
```

This Equality_comparable is almost identical with the standard-library concept (§14.5). We can define a concept that arithmetic is valid between numbers. First we need to define:

Click here to view code image

```
template<typename T, typename U = T>
concept Number =
requires(T x, U y) {
  x+=y; x-=y; x*=y; x/=y;
  x+==y; x-==y; x*==y; x/==y;
  x=x;
};
```

This makes assumptions about the result types, but that's adequate for simple uses. Given one argument type, Number<X> checks that X has the desired properties of a Number. Given two arguments, Number<X,Y> checks that the two types can be used together. From that, we can define Arithmetic concept (§8.2.1):

Click here to view code image

```
template<typename T, typename U = T>
concept Arithmetic = Number<T,U> && Number<U,T>;
```

For a more complex example, consider a sequence:

```
template<typename S>
concept Sequence = requires(S a) {
  typename range_value_t<S>; // Il S must have a value type
  typename iterator_t<S>; // Il S must have an iterator
  { a.begin() } -> same_as<iterator<S>>; // Il S must have a begin() that returns an iterator
  { a.end() } -> same_as<iterator<S>>; // Il S must have an end() that returns an iterator
  requires input_iterator<iterator<S>>; // Il S's iterator must be an input_iterator
  requires same_as<typename iterator_traits<iterator<S>>::value_type, range_value_t<S>>;
};
```
