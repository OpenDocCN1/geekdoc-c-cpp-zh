
```cpp
cout << '<<';
```

Similarly for the filter_view:

Click here to view code image

```cpp
for (int x : filter_view{ r, [](int x) { return x % 2; } }, 3 })
cout << '<<';
```

Such views can quickly get a bit crispy, so there is an alternative: pipelines (§14.4). The standard library offers quite many views, also as range adapters:

| Standard-library views (range adapters) <ranges> | v is view; r is range; p is a predicate; n is an integer |
| all_view(r) | v is elements from r |
| filter_view(r,p) | v is elements from r that meets p |
| transform_view(r,f) | v is the results of calling f on each element from r |
| take_view(r,n) | v is at most n elements from r |
| take_while(r,p) | v is elements from r until one doesn't meet the p |
| drop_view(r) | v is elements from r starting with the n+1th element |
| drop_while(r,p) | v is elements from r starting with the first element that meets p |
| join_view(r) | v is a flattened version of r; the elements of r must be ranges |
| split_view(r,d) | v is a range of sub-ranges determined by the delimiter d; must be an element or range |
| common_view(r) | v is described by a (begin, end) pair |
| reverse_view(r) | v is the elements of r in reverse order; r must have bidirectional access |
| views::elements<>(r) | v is the range of the nth elements of the tuple elements of r |
| keys_view(r) | v is the range of the first elements of the pair elements of r |
| values_view(r) | v is the range of the second elements of the pair elements of r |
| ref_view(r) | v is range of elements that are references to the elements of r |

A view offers an interface that's very similar to a range, so in many cases we can use a view wherever in the same way. The key difference is that a view doesn't own its elements; it is not responsible for the elements of its underlying range - that's the range's responsibility. On the other hand, a view must not outlive its range:

Click here to view code image

```cpp
auto bad() {
  vector v = {1, 2, 3, 4};
  return filter_view(v,odd);
}
// v will be destroyed before the view
```

Views are supposed to be cheap to copy, so pass them by value. I have used standard types to keep examples simple, but of course, we can have views of our own user-defined types. For example:

Click here to view code image

```cpp
struct Reading {
    int location();
    int temperature();
    int humidity();
    int air_pressure();
    //...
}
int average_temp(vector<Reading> readings) {
    if (readings.size()==0) throw No_readings();
    double s = 0;
    for (int x : views::elements<1>(readings))
        s += x;
    return s/readings.size();
}
```

## 14.3 Generators

Often, a range needs to be generated on the fly. The standard library provides a few simple generators (aka factories) for that:

| Range factories <ranges> | v is a view; x of the element type T; is an istream |
| v=empty_view<T>() | v is an empty range of type T (if it had any) |
| v=single_view(x) | v is a range of the one element x |
| v=iota_view(x) | v is an infinite range of elements: x, x+1, x+2, ... incrementing is done using ++ |
| v=iota_view(x,y) | v is a range of n elements: x, x+1, ..., y-1 incrementing is done using ++ |
| v=istream_view<T>(is) | v is the range obtained by calling >> to T on is |

Iota views are useful for generating simple sequences. For example:

Click here to view code image

```cpp
for (int x : iota_view<int>(42)) 
  cout << x;
```

The istream_view gives a simple example of using istream in range loops:

Click here to view code image

```cpp
for (auto x : istream_view<double>(cin))
  cout << x;
```

Like other views, an istream_view can be composed with other views:

Click here to view code image

```cpp
auto cpx = istream_view<double>(cin);
for (auto x : transform_view(cpx, [](auto z){ return z; }))
  cout << x;
```

## 14.4 Pipelines

For each standard view, the standard library provides a function that produces a filter; that is, an object that can be used as an argument to filter adaptor. For example, filter_view allows to combine filters in a sequence rather than presenting them as a set of nested calls. The pipeline style (using pipe adaptor) is widely regarded as more readable than nested calls. The pipeline works left to right; that is the result of f is passed to g, so the initial r has to be a range or generator. These filter functions are in namespace views::views:

```cpp
void user(forward_range auto r)
{
  auto odd = [](int x) { return x % 2; };
  for (int x : r | views::filter(odd) | views::take(3))
    cout << x;
}
```

The implementation of views and pipelines involves some hair-raising metaprogramming, if you are concerned about performance make sure to measure whether your implementation delivers what you need. If not, there is always a conventional workaround around

Click here to view code image

```cpp
void user(forward_range auto r)
{
  int count = 0;
  for (int x : r) {
    cout << x;
    if (++count == 3) return;
  }
}
```

However, the logic of what's going on is obscured.

## 14.5 Concepts Overview

The standard library offers many useful concepts:

- Concepts defining properties of types (§14.5.1)
- Concepts defining iterators (§14.5.2)
- Concepts defining ranges (§14.5.3)

### 14.5.1 Type Concepts

The concepts relate to properties of types and the relations among them reflect the variety of types. These concepts help simplify templates.

| Core language concepts <concepts> | T and U are types |
| same_as<T,U> | T is the same as U |
| derived_from<T,U> | T is derived from U |
| convertible_to<T,U> | A T can be converted to a U |
| common_reference_with<T,U> | T and U share a common reference type |
| common_with<T,U> | T and U share a common type |
| integral<T> | T is an integral type |
| signed_integral<T> | T is a signed integral type |
| unsigned_integral<T> | T is an unsigned integral type |
| floating_point<T> | T is a floating point type |
| assignable_from<T,U> | A U can be assigned to a T |
| swappable<T,U> | A T can be swapped with a U |
| swappable_with<T,T> | |

Many algorithms work with combinations of related types, e.g., expressions with a mixture of ints and doubles. We use common_with to say such a mix is mathematically sound. If common_with<X,Y> is true, we use common_type_t<X,Y> to compare a X with a Y by first converting to common_type_t<X,Y>. For example:

Click here to view code image

```cpp
common_type<string, const char> s1 = some_fct();
common_type<string, const char> s2 = some_other_fct();
```

```cpp
if (s1<s2) {
  ...
}
```

To specify a common type for a pair of types, we specialize common_type_t used in the definition of common. For example:

Click here to view code image

```cpp
using common_type_t<Bigint,long> = Bigint; // for a suitable definition of Bigint
```
