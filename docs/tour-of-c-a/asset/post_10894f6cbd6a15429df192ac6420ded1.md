## 6.3 Resource Management

By defining constructors, copy operations, move operations, and a destructor, a programmer can provide complete control of the lifetime of a contained resource (such as the elements of a container). Furthermore, a move constructor can allow an object to move and cheaply from one scope to another. That way, objects that we want or not want to copy out of a scope can be moved and cheaply moved instead. Consider a standard-library thread representing a concurrent activity (§18.2) and a Vector of doubles. We can't copy the former and don't want to copy the latter.

[Click here to view code image](thread>my_threads;)

```
Vector init(int n)
{
    thread t (heartbeat); // heartbeat concurrently (in a separate thread)
    my_threads.push_back(std::move(t)); // Move t into my_threads (§16.6)
    // ... more initialization ...
}

Vector vec(n) 
{
    for (auto &x : vec)
        x = 777;
    return vec; // move out of init()
}
```

auto v = init(100 000); // start heartbeat and initialize v

Resource handles, such as Vector and thread, are superior to direct use of built-in pointers in many cases. In fact, the standard-library "smart pointers," such as unique_ptr, are themselves resource handles (§15.2.1).

I used the standard-library vector to hold the threads because we don't want to parameterize our simple Vector with an element type until §7.2.

In very much the way that new and delete disappear from application code, we can make pointers disappear into resource handles. In both cases, the result is simpler and more maintainable code, without added overhead. In particular, we can achieve strong resource safety; that is, we can eliminate resource leaks for a general notion of a resource. Examples are vectors holding memory, threads holding system threads, and fstreams holding file handles.

In many languages, resource management is primarily delegated to a garbage collector. In C++, you can plug in a garbage collector the last choice after cleaner, more general, and better localized alternatives to resource management have been exhausted. My ideal is not to create any garbage, eliminating the need for a garbage collector: Do not litter!

Garbage collection is fundamentally a global memory management scheme. Clever implementations can compensate, as systems get more distributed (caches, multicores, clusters), locality is less important than ever.

Also, memory is not the only resource. A resource is anything that has to be acquired and (explicitly or implicitly) released after use. Examples are memory, sockets, file handles. Surprisingly, a resource is not just memory as a non-memory resource. A good resource management system handles all kinds of resources. Leaks must be avoided in any long-running system, but excessive resource retention can be as bad as a leak. For example, if a system holds on memory, locks, files, etc. for too long, the system needs to be provisioned with twice as many resources.

Before resorting to garbage collection, systematically use resource handles: let each resource have an owner and be deleted by the end of its owner's scope. In C++, this is known as RAII (Resource Acquisition Initialization) and is integrated with error handling in the face of exceptions. Resources can be moved from scope using moving semantics or "smart pointers," and shared ownership can be represented by "shared pointers" (§15.2.1).

In the C++ standard library, RAII preserves: for example string, vector, map, unordered_map, etc.), fstreams (fstream, ofstream), threads (thread), locks (lock_guard, unique_lock, etc.), and general objects through unique_ptr and shared_ptr. The result is implicit resource management that is invaluable in common use and leads to less contention.
