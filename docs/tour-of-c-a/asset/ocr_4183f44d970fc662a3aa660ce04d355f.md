+   - New kinds of errors can be added in lower-modules of an application so that higher-level modules are not written to cope with such errors. For example, when a previously single-threaded application is modified to use multiple threads or resources are called remotely to be accessed over a network.

+   - No suitable return path for error codes is available. For example, a constructor does not have a return value for a "caller"; In particular, constructors may be invoked for several variables or a partially constructed complex object that clean-up based on error codes would be quite complicated. Similarly, operators not usually have an obvious return path for error codes. For example, `a*b=c/d`.

+   - The return path of a function is more complicated or complex to pass both value and an error indicator back (e.g., a `pair` [$15.3.3]), possibly leading to the use of out-parameters, non-local error-status indicators, or other workloads.

+   - The recovery from errors depends on the results of several function calls, leading to the need to maintain local state between calls and complicated control structures.

+   - The function that found error was a callback (a function argument), so the immediate caller may not even know what function was called.

+   - An error implies that "undo action" is needed [$5.2.2].

We terminate

+   - An error is of a kind from which we cannot recover. For many – but not all – systems there is no reasonable way to recover from memory exhaustion.

+   - The system is one where error-handling is based on returning a thread, process, or computer whenever a non-trivial error is detected.

One way to ensure termination is to add `except` [$4.5.3] to a function so that `throw` from anywhere in the function's implementation will turn into `terminate()`. Note that there are applications that can't accept unconditional conditions, so alternatives must be used. A library for general-purpose use should never unconditionally terminate.

Unfortunately, these conditions are not logically disjoint and easy to apply. The size and complexity of a program grows. When in doubt, prefer exceptions because their use scale better and don't require external tools to check that all errors are handled

Don't believe that all error codes are bad; they are clear for both: slow; it is often faster than correct handling of complex or rare error codes, and repeated tests of error codes.

RAII [$5.2.2, 6.3] is essential for simple and efficient error-handling using exceptions. Code littered with try-blocks simply reflects the worst aspects of error-handling strategies conceived for error codes
