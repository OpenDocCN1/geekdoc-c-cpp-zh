# # 15.3 Containers

The standard provides containers that don't fit perfectly into the STL framework (Chapter 12, Chapter 13). Examples are built-in arrays, array, and string. I sometimes refer to those as "almost containers," but that is not quite fair: they hold elements, so they are containers, but each has restrictions or added facilities that make them awkward in the context of the STL. Describing them separately simplifies the design of the STL.

| | |
|---|---|
| T[N] | Built-in array: fixed-size contiguously allocated sequence of N elements of type T; implicitly converts to T* |
| array<T,N> | A fixed-size contiguously allocated sequence of N elements of type T; like the built-in array, but with most problems solved A fixed-size sequence of N bits |
| bitset<N> | A sequence of bits compactly stored in a specialization of vector<bool> |
| pair<T,U> | Two elements of T and U |
| tuple...> | A sequence of an arbitrary number of elements of arbitrary types |
| basic_string<C> | A sequence of characters of type C; provides string operations |
| valarray<T> | An array of numeric values of type T; provides numeric operations

Why does standard provide many containers? They serve but different (often overlapping) needs. If the library didn't provide them, many people would have to design and implement their own. For example:

+   - pair and tuple are heterogeneous; all other containers are homogeneous (all elements are the same type).
- array, and tuple elements are contiguously allocated; list and map are linked structures.
- bitset and vector<bool> hold bits and access through proxy objects; all other-library containers hold a variety of types and access directly.
- basic_string requires its elements to be some of character and to provide string manipulation, as as concatenation and locale-sensitive operations.
- valarray requires its elements to be numbers and provide numerical operations.

All of these can be seen as providing specialized services needed by large communities of programmers.
