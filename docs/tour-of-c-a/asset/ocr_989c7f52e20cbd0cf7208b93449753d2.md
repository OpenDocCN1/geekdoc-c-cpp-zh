Use of the exception-handling mechanisms can make error handling simpler, and more readable. To achieve that, don't overstay statements. In many programs there are dozens of function calls between a function and a function that can reasonably handle the exception. Thus, most functions should simply allow the exception to be propagated up the call stack. The main technique for making error handling simple and systematic (Resource Acquisition Is Initialization; RAII) idea behind RAII is for a constructor to acquire the resources necessary for a class and for the destructor release all resources, making release guaranteed and implicit.

# # 4.3 Invariants

The use of exceptions to signal out-of-range access is an example of a function checking its argument and refusing to act because a basic assumption, a precondition, didn't hold. We had formally specified Vector's subscript operator, we would have said something like "the index must be in [0:size()) range," and that is what we tested in our operator[](j). The [a:b) notation specifies a half-open range, meaning that a is part of the range, but b is not. Whenever we define a function, we should consider what its preconditions are and consider whether to test them ($4.4). For most applications it is a good idea to test simple invariants; we also $4.5.

However,operator[](j) operates on objects of type Vector and nothing it makes any sense unless the members of Vector have "reasonable" values. In particular, we say "elem points to an array of sz doubles" but we only said that in a comment. A statement of what is assumed to be true for a class is called class invariant, or simply invariant. It is the job of a constructor to establish the invariant for its class (so that the functions can rely on it) and for the members to make sure that the invariant holds when they exit.

Unfortunately, Vector partially did it. It properly initialized the Vector members, but it failed to check that the arguments to it made sense. Consider:
