
The template gives you a few important things.

- **Configuration:** The configuration of WCF is a bear (as you can see in Chapter 3) and making it REST-capable is even worse. The template takes care of the details for you.
- **File formats:** The files for REST aren't any different from WCF, but how you set them up is. The file level templates help a lot.
- **Project setup:** Visual Studio helps you set up the project well for a REST project.

One of the configuration changes that the REST template does for you is the routing. Remember that REST is a URI-based format. The routing needs to be set up with the excellent WebServiceHostFactory to direct incoming requests to the appropriate code in the project. All that needs to be in place is the base service (for a default project), but the global.asax file has it ready if you need to add more.

```
using System;
using System.ServiceModel.Activation;
using System.Web;
using System.Web.Routing;

namespace Chapter4.REST
{
    public class Global : HttpApplication
    {
        void Application_Start(object sender, EventArgs e)
        {
            RouteTable.Routes.Add(new ServiceRoute("",
                new WebServiceHostFactory(), typeof(Service)));
        }
    }
}
```

Another point that the configuration is tuned is in the config file. Remember that while WCF is essentially an IIS add-on, REST projects are extensions of ASP.NET MVC. The web.config is built into the project, and you can use it largely without change. The routing module especially is important — it makes the code in the global.asax work:

```
<system.webServer>
    <modules runAllManagedModulesForAllRequests="true">
        <add name="UrlRoutingModule" type="System.Web.Routing.UrlRoutingModule, System.Web, Version=4.0.0.0, Culture=neutral, PublicKeyToken=b03f5f7f11d50a1a" />
    </modules>
</system.webServer>
```

## Building a service

Making a service isn't much different than working in WCF: First you build an interface and then a method. The contracts look just like what you would expect from Chapter 3 of this minibook. The methods interact with System.ServiceModel.Web and have a slightly different look.

Here's a simple datacontract that grabs the version of the service assembly:

```
namespace Chapter4.REST.Interface
{
    [DataContract]
    public class ServiceVersion
    {
        [DataMember] public String Version;

        public static ServiceVersion Read()
        {
            var asm = Assembly.GetExecutingAssembly();
            var fvi = FileVersionInfo.GetVersionInfo(asm.Location);
            var version =
                String.Format("{0}.{1}", fvi.ProductMajorPart, fvi.ProductMinorPart);
            return new ServiceVersion { Version = version };
        }
    }
}
```

Where things get interesting is the methods. The straight class library of WCF gives way to the controller style classes in REST. Here is the method that interacts with the data contract.

```
[Description("Read the version of this service.")]
[WebGet(UriTemplate = "/version", ResponseFormat = WebMessageFormat.Json)]
public ServiceVersion ReadVersion()
{
    return ServiceVersion.Read();
}
```

There are two bits there above the method code: Description and WebGet. The Description property will change the built-in documentation that is autogenerated by IIS when a user hits the service page. The WebGet is the implementation of all the routing that you saw in the global.asax and web.config file.

Now, all you have to do to get the version is go to http://myurl.com/version, and you get a JSON representation of the information returned from the data contract method. This is what makes the REST restful and makes things a lot easier. And it's all for free from ASP.NET MVC.

## Handling errors

As you may imagine, errors in the REST space are a little different than what you might experience in SOAP. There are predefined ways to handle errors in REST, and they are the same as what you see on the web. It's the same deal, more or less.

That means you should return 404 (file not found) if they misspell the service, and 500 (internal server error) if a server error occurs. This isn't WCF programming at this point; it's a brave new world.

Fortunately, System.ServiceModel.Web has a class called WebFaultException that will help with that. It will take an object and help you morph it into a HTTP status code with little fuss. I recommend adding a method like this to your project:

```
private static WebFaultException<String> InternalError(Exception ex)
{
    var msg = ex.Message;
    if (null != ex.InnerException)
    {
        msg += " - " + ex.InnerException.Message;
    }
    return new WebFaultException<String>(msg,
        HttpStatusCode.InternalServerError);
}
```

## Dealing with the nasty MVC cache

One more thing that you have to handle is the cache. MVC's speed is largely about the caching, which saves often requested data in a buffer that doesn't require database or other resource usage.

Something that tells the HttpContext to ignore the cache will help. Here is a little method that I have found useful for resetting cache settings for REST projects:

```
private static void SetNoCache()
{
    var cache = HttpContext.Current.Response.Cache;
    cache.SetExpires(DateTime.UtcNow.AddMinutes(-1));
    cache.SetCacheability(HttpCacheability.NoCache);
    cache.SetNoStore();
}
```
