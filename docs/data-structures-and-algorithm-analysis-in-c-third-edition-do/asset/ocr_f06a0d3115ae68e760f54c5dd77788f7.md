Typically, there are many more values in the range than there are slots in the hash table. Given a realistic example, suppose that the key can take some value in the range 0 to 65,535 (i.e., the key is a two-byte unsigned integer), and that we expect to store approximately 1000 records at any given time. It is impractical in this situation to use a hash table with 65,536 slots, because most of the slots will be left empty. Instead, we must devise a hash function that allows us to store the records in a much smaller table. Because the possible key range is larger than the size of the table, at least some of the slots must be mapped to multiple key values. Given a hash function $h$ and two keys $k_1$ and $k_2$, if $h(k_1) = eta = h(k_2)$ where $eta$ is a slot in the table, then we say that $k_1$ and $k_2$ have a collision at slot $eta$ under function $h$.

Finding a record with value key $K$ in a database organized by hashing follows a two-step procedure:

+   1. Compute the table location $h(K)$.
2. Starting with $h(K)$, locate the record containing $K$ using (if necessary) **collision resolution policy**.

# 9.4.1 Hash Functions

Hashing generally takes records whose values come from a large range and stores them in records with a relatively small number of slots. Collisions occur when two records hash to the same slot in the table. If we are careful—lucky—selecting a hash function, the actual number of collisions will be nearly unavoidable. For example, consider a classroom of students. What is the probability that some students share the same birthday (i.e., the same day of the year, not necessarily the same year)? If there are 23 students, the odds are about that two will share a birthday. > Exception to this is perfect hashing. Perfect hashing is a system in which records are hashed such that there are no collisions. A hash function is selected for the specific set of records being hashed, which requires the entire collection of records to be available before selecting the hash function. Perfect hashing is efficient because it always finds the record that we are looking for exactly where the hash function computes it, so only one access is required. Selecting a perfect hash function can be expensive, but might be worthwhile when extremely efficient search performance is required. An example is searching for data on a read-only CD. Here the database will never change, the time for each access is expensive, and the database designer can design the hash table before issuing the CD.
