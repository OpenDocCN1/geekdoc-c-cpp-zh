The last policy that we will consider is **garbage collection**. Consider the following series of statements.

```
int* p = new int[5];
int* q = new int[10]
p = q;
```

While Java would be no problem (due to automatic garbage collection), in languages as C++, this would be considered bad form because the original space allocated to **p** is lost as a result of the third assignment. This space cannot be used again by the program. Such loss is referred to as **garbage**, also known as a **memory leak**. When no program variable points to a block of space, no future access to that space is possible. Of course, if another variable had been assigned to **p**'s space, reassigning **p** would not create garbage.

Some programming languages take different views towards garbage. In particular, the LISP programming language uses the multil representation of Figure 12.5, and all storage is in the form of internal nodes with two pointers or atoms. Figure 12.6 shows a typical collection of LISP structures, headed by variables A, B, and C, along with a freelist.

In LISP, list objects are constantly being put together in various ways as temporary variables, and all reference to them is lost when the object is no longer needed. Thus, garbage is normal in LISP, and in fact cannot be avoided during routine program behavior. When LISP runs out of memory, it resorts to a garbage process to recover the space tied up in garbage.
