
# Freelists

The C++ free-store management operators **new** and **delete** are relatively expensive to use. Section 12.3 discusses general-purpose memory managers are implemented. The expense comes from the fact that free-store routines must be capable of handling requests to and from free store with no particular pattern, as well as memory requests of vastly different sizes. This makes them inefficient compared to what might be implemented for more controlled patterns of memory access.

List nodes are created and deleted in a linked list implementation in a way that allows the **Link** class programmer to provide simple efficient management routines. Instead of making calls to **new** and **delete**, the **Link** class holds its own freelist that are not currently being used. When a node is deleted from a linked list, it is placed at the head of the freelist. When a new element is added to a linked list, the freelist is checked to see if a list node is available. If so, the node is taken from the freelist. If the freelist is empty, the standard **new** operator must be called.

Freelists are particularly useful for lists that periodically grow and shrink. The freelist will never grow larger than the largest size reached by the linked list. Requests for new nodes (after the list has shrunk) can be handled by the freelist. Another good opportunity to use a freelist occurs when a program uses multiple lists. So long as they do not all grow and shrink, the free list can link nodes between the lists.

One approach to implement freelists would be to create two operators to use instead of the standard free-store routines **new** and **delete**. This requires the user's code, such as the linked list implementation of Figure 4.8, to be modified to call these freelist operators. A second approach is to use **C++ operator overloading** to replacing the meaning of **new** and **delete** when operating on Link class objects. In this way, the programs that use the **List** class will not be modified by freelists, or rely on the regular free-store mechanism, the **Link** class is implemented with, entirely hidden from the list user. Figure 4.11 shows the implementation for the **Link** class with freelist overloading. Note how simple they are, they only remove and add an element to the front of the freelist, respectively. The freelist versions of **new** and **delete** both operation in $\Theta(1)$ time, except in the case where the freelist is exhausted and the **new** and **delete** operation must be called.

There is an additional efficiency gain to be had from a freelist implementation. The implementation of Figure 4.11 makes a separate call to the system **new** operator for each list node requested whenever the freelist is empty. These link nodes tend to be small — only a few bytes more than the size of the **element** field. If at some point time the program requires thousands of active link nodes, this will have been created by many calls to the system version of new. An alternative is to allocate memory nodes in a single call to the system version of new, anticipating that if the freelist is exhausted, more nodes will be needed. It is faster to make one call to new for 100 link nodes, then load all 100 onto the freelist at once, rather than to make 100 separate calls to new. The following statement will assign ptr to point to an array of 100 link nodes.

```cpp
ptr = ::new Link[100];
```

The implementation for the new operator in the link class could place each of these 100 nodes onto the freelist.

The freelist variable declaration uses the keyword static. This creates a single variable shared among all instances of the Link nodes. We want only a single freelist for all Link nodes of a given type. A program might create multiple lists. If they are all of the same type (that is, their elements are the same), then they can and share the same freelist. This will happen with the implementation of Figure 4.11. If lists are created that have different element types, because this code is implemented with a template, the need for different list implementations will be discovered by the compiler at compile time. Separate versions of the list class will be generated for each element type. Thus, each element type will get its own copy of the Link class and each distinct implementation will generate a separate freelist.

# Sec. 4.1 Lists

```cpp
// Singly linked node with freelist support
template <typename E> class Link {
private:
    static Link<E>* freelist; // Reference to freelist head
public:
    E element; // Value for this node
    Link* next; // Point to next node in list

    Constructors
    Link(E element, Link* next=NULL)
        { element = element; next = next; }
    Link(Link* next=NULL) { next = next; }

    void* operator new(size_t) { // Overloaded new operator
        if (freelist == NULL) return ::operator new(size); // Create space
        Link<E>* temp = freelist; // Can take from freelist
        freelist = freelist->next;
        return temp;
    }

    // Overloaded delete operator
    void operator delete(void* ptr) {
        ((Link<E>*)ptr)->next = freelist; // Put on freelist
        freelist = (Link<E>*)ptr;
    };
```

The head pointer is actually created here template <typename E>
Link<E>::freelist = NULL;

The static declaration for member freelist means that all Link objects share the same freelist pointer instead of each object storing its own copy.

# 4.1.3 Comparison of List Implementations

Now that we have seen two different implementations for lists, it is natural to ask which is better. In particular, if you must implement a list for some task, which implementation should you choose?

Array-based lists have the disadvantage that their size is predetermined before the array is allocated. Array-based lists cannot grow beyond their determined size. Whenever the list contains only a few elements, a substantial amount of space might be tied up in a large array. Linked lists have the advantage that they only need space for the objects on the list. There is no limit to the number of elements on a list, as long as there is free-store memory available. The amount of space required by a linked list is $\Theta(n)$, while the space required by the array-based list implementation is $f(n)$, but can be better.

Array-based lists have the disadvantage that an extra pointer is wasted for every list node. Linked lists require that if the element size is small, then the overhead for lists can be a significant fraction of the total storage. Whenever the array-based list is completely filled, there is no storage overhead. The array-based list will then be more space efficient, by a constant factor, than the linked implementation.

A simple formula can be used to determine whether the array-based list or linked list implementation will be more space efficient in a particular situation. Let $n$ the number of elements currently in the list, $P$ the size of a pointer in storage, $E$ the size of a data element in storage units (this could be, from one for a Boolean variable up to thousands of bytes or more for complex records), and $D$ the maximum number of elements that can be stored in the list. The amount of space required for the array-based list is $DE$, regardless of the number of elements actually stored in the list at any given time. The amount of space required for the linked list is $n(P + E)$. The smaller of these expressions determines the more-efficient implementation for $n$. The linked implementation requires less space than the array-based implementation when relatively few elements are in the list. Conversely, the array-based list becomes more space efficient when the array is close to full. This occurs when $n > DE/(P + E)$

If $P = E$, the break-even point is $D/2$. This would happen if the element field is a four-byte **int** value or a pointer, and the next field is a four-byte pointer. The array-based implementation would be more efficient (if the link field and the element field are the same size) whenever the array is more than half full.

As a rule of thumb, linked lists are more space efficient when implementing lists whose number of elements varies or is unknown. Array-based lists are generally more space efficient when the user knows in advance how large the list will-based lists are faster for random access by position. Positions can be adjusted forwards or backwards by the **next** and **prev** methods. These operations always take $\Theta(1)$ time. In contrast, singly linked lists have no explicit access to the previous element, and access by position requires that we march down the list from the front (the current position) to the specified position. Both of these operations require $\Theta(n)$ time in the average and worst cases, if we assume each position of the list is equally likely to be accessed on call to *prev* or *moveToPos*

Given a pointer to a suitable location in the list, the **insert** and **remove** methods (for linked lists require only $\Theta(1)$ time). Array-based lists must shift the remainder of the list or down within the array. This requires $\Theta(n)$ time in the average and worst cases. For many applications, the time to insert and delete dominates all operations. For this reason, linked lists are often preferred to array-based lists.

When implementing the array-based list, an implementor could allow the size of the array to grow and shrink depending on the number of elements that are actually stored. This data structure is a **dynamic array**. Both the Java and C++/STL Vector classes implement a dynamic array. Dynamic arrays allow the programmer to avoid the limitation on the standard array that its size cannot be changed once the array has been created. This also means that space need not be allocated to the dynamic array until it is used. The disadvantage of this approach is that it takes time to deal with space adjustments. Each time the array grows, its contents must be copied.
