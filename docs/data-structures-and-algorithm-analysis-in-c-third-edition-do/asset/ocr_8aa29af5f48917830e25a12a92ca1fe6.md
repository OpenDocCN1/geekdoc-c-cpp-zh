# 10.5.1 B^+-Trees

The previous section mentioned that B-trees are universally used to implement large-scale database-based systems. Actually, the B-tree as described in the previous section is almost never implemented, nor the 2-3 tree as described in Section 10.4. What is most commonly implemented is a variant of the B-tree, called the B+-tree. When greater efficiency is required, a more complicated variant known as the B+-tree is used.

When data are static, a linear index provides an extremely efficient way to search. The problem is how to handle those inserts and deletes. We could try to keep the core idea of storing a sorted array-based list, but make it more flexible by breaking the list into manageable chunks that are easily updated. How might we do that? First, we need to decide how big the chunks should be. Since data is on disk, it seems reasonable to store a chunk that is the size of a disk block, a small multiple of the disk block size. If the next record is to be inserted into a chunk containing space we can just insert it there. The fact that this might cause other records in the chunk to move a little bit in the array is not important, since this does not cause any extra disk accesses so long as we move data within chunk. But what if the chunk fills up the entire block that it contains? We could just split it in half. What if we want to delete a record? We could take the deleted record out of the chunk, but we might not want a lot of empty-chunks. Or we could adjust chunks if they have a small amount of data between them. The problem would be how to find the desired chunk when processing a record with a given key. Perhaps some sort of tree-like structure could be used to locate the appropriate chunk. These ideas are exactly what the B+-tree does. The B+-tree is essentially a mechanism for managing a sorted array-based list, where the list is broken into chunks.

The most significant difference between the B+-tree and the BST or standard B-tree is that it stores records only at the leaves. Internal nodes store key values, but these are used solely as placeholders to guide the search. This means that internal nodes are significantly different in structure from leaf nodes. Internal nodes store keys to guide the search, associating each key with a pointer to a child B+-tree node. Leaf nodes store actual records, or keys and pointers to actual records in a separate disk file if the B+-tree is being used purely as an index. Depending on the size of a record as compared to the size of a key, a leaf node in a B+-tree of order m might have enough room to store more or less than m records.
