# Small block: External fragmentation

![](bbox=[0.24, 0.205, 0.76, 0.253])

**Figure 12.10** An illustration of internal and external fragmentation. The small white block labeled "External fragmentation" is too small to satisfy typical memory requests. The small gray block labeled "Internal fragmentation" was allocated as part of the gray block to its left, but it does not store information.

When a memory request is received by the memory manager, the freelist must be large enough to serve the request. If no such block is found, then the memory manager must resort to a **failure policy** such as discussed in Section 12.3.

If there is a request for $m$ words, and no blocks exist of exactly size $m$, then one possibility in this case is that the entire request is given away to memory allocation. This might be desirable when the size of the block is only slightly larger than the request. Saving a block that is too small to be useful for a future memory request might not be worthwhile. Alternatively, for a free block of size $k$, with $k > m$, up to $k - m$ space may be returned by the memory manager to form a new free block, while the rest is used to serve the request.

Memory managers can suffer from two types of **fragmentation**, which refers to unused space that is too small to be useful. **External fragmentation** occurs when **Internal fragmentation** occurs when more than $m$ words are allocated to a request for $m$ words, wasting free storage. This is equivalent to the internal fragmentation that occurs when files are allocated in multiples of the cluster size. The difference between internal and external fragmentation is illustrated by Figure 12.10.

Some memory management schemes sacrifice space to internal fragmentation to make memory management easier (and perhaps reduces external fragmentation). For example, external fragmentation does not happen in file management systems that allocate file space in clusters. Another example of sacrificing space to internal fragmentation so as to simplify memory management is the **buddy method** described in this section.

The process of searching the memory pool for a block large enough to serve the request, possibly reserving the remaining space as a free block, is referred to as a **sequential fit** method.
