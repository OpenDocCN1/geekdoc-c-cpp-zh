Looking at this another, the only candidates for second place are losers to the eventual winner. So we need to keep track of the set of elements that have lost in direct comparison to the (eventual) winner. We also observe that we learn from a comparison when both competitors are known to be larger than the same number of other values. So we would like to arrange our comparisons to be against "strong competitors". We can do all of this with a binomial tree. A binomial tree of height $m$ has $2^m$ nodes. Either it is a single node (if $m=0$), or it is two trees of height $m-1$ with one root becoming the other. Figure 15.2 illustrates how a binomial tree with eight nodes is constructed.

The resulting algorithm is simple in principle: Build the binomial tree for all $n$ elements, and then compare the $[n]$ children of the root to find second place. We could store the binomial tree as an explicit tree structure, and easily build it in linear time over the number of comparisons as each comparison requires one link be added. Because the shape of a binomial tree is heavily constrained, we can also store the binomial tree in an array, much as do for a heap. Assume two trees, with $2^k$ nodes, are in the array. The first tree is in positions 1 to $2^k$. The second tree is in positions $2^k$ to $2^{k+1}$. The root of each subtree is in the final array position for that subtree.

To join trees, we simply compare the roots of the subtrees. Swap the subtree so that the larger root becomes the second subtree. This takes space (we only need space for the data values, no pointers) and time (in the worst case, all of the data swapping might cost $O(n \log n)$, though this does not affect the number of comparisons required). Note that for some applications, this is an important observation that the array's swapping requires no comparisons. If a comparison is simply a check between two integers, then of course half the values within the array is too expensive. But if a comparison requires that a competition be held between two sports teams, then the cost of a little bit (or even a lot) of book keeping becomes irrelevant.

Because the binomial tree's root has $\log n$ children, and building the tree requires $n-1$ comparisons, the number of comparisons required by this algorithm is $n+[log n] - 2$. This is clearly better than our previous algorithm. Is it optimal?

## Sec. 15.4 Adversarial Lower Bounds Proofs

We go back to trying to improve the lower proof. To do this, we introduce the concept of an adversary. The adversary's job is to make an algorithm's cost as high as possible. Imagine that the adversary keeps a list of all possible inputs. We view the algorithm as asking the adversary for information about the algorithm's input. The adversary may never lie, in that its answer must be consistent with the previous answers. But it is permitted to "rearrange" the input as it fits in order to drive the total cost for the algorithm as high as possible. In particular, when the adversary asks a question, the adversary must answer in a way that is consistent with at least one remaining input. The adversary then crosses out all remaining inputs inconsistent with that answer. Keep in mind that there is not really an entity within the computer program that is the adversary, and we don't actually modify the program. The adversary operates merely as an analysis device, to help us reason the program.

As an example of the adversarial concept, consider the standard game of Hang. Player A picks a letter and tells Player B how many letters the word has. Player B guesses various letters. If B guesses a letter in the word, then A will indicate which position(s) in the word has the letter. Player B is permitted to make only so many guesses of letters not in the word before.

In the Hangman game example, the adversary is imagined to hold a dictionary of words of some length. Each time the player guesses a letter, the adversary consults the dictionary and decides if more words will be eliminated by accepting the letter (and indicating which positions it holds) or saying that it is not in the word. The adversary can make any decision it chooses, so long as at least one word in the dictionary is consistent with all of the decisions. In this way, the adversary can help to make the player guess as many letters as possible.

Before explaining how the adversary plays a role in our lower bounds proof, first observe that $n-1$ values must lose at least once. This requires at least $n-1$ comparisons. In addition, at least $k$ values must lose to the second largest value. That is, $k$ losers to the winner must be compared. There must be at least $n+k-2$ comparisons. The question is: How can we make $k$?

Call the strength of $A[i]$ the number of elements that $A[i]$ is (known to be) bigger. If $A[i]$ has strength $a$, and $A[j]$ has strength $b$, then the winner has strength $a+b+1$. The algorithm gets to know which two elements are compared next. The adversary decides to win any given comparison. What strategy by adversary would cause the algorithm to learn the least? It can do this by making the element with greater strength win.

To minimize the effects of worst-case behavior, the algorithm's best strategy is to maximize the improvement by balancing the strengths of two competitors. All strengths begin at zero, so the winner must make at least $k$ comparisons when $2^{k-1} < n \le k$. Thus, there must be $n+[log n]-2$ comparisons. Our algorithm is optimal.

## 15.5 State Lower Proof

We now consider the problem of finding both the minimum and maximum from an (unsorted) list of values. This might be useful if we want to know the range of a collection of values to be plotted. We could find them independently in $2n-2$ comparisons. A slight modification is to find the minimum in $n-1$ comparisons, remove it from the list, and then find the maximum in $n-2$ further comparisons for a total of $2n-3$ comparisons. Can we do better than this?

Before continuing, think a moment about how this problem of finding the minimum and maximum compares to the last, that of finding the second best value (and by implication, the maximum). Which of these two problems do you think is harder? It is probably not all obvious to you that one is harder or easier than the other. There is intuition that argues for either case. One intuition might argue that the process of finding the minimum should tell you something about the second best value, more than any comparison tells you which of two can be a candidate for maximum value, and which can be a candidate for minimum value, making progress in both directions.

We will start by considering a simple divide-and-conquer approach to finding the minimum and maximum. Split the list into two parts and find the minimum and maximum elements in each part. Then compare each with other with two comparisons to get the final result. The algorithm is shown in Figure 15.3.

The cost of this algorithm can be modeled by the following recurrence:

```
T(n) = \begin{cases} n & n = 1 \\ n & n = 2 \\ T(\lfloor n/2\rfloor) + T(\lceil n/2\rceil) + 2 & n > 2 \end{cases}
```

This is a rather interesting recurrence, and its solution ranges between $3n/2-2$ (when $n = 2^k$ or $n = 2^k \pm 1$) and $5n/3-2$ (when $n = 3 \times 2^k$). We can infer from this behavior how we divide the list affects the performance of the algorithm.
