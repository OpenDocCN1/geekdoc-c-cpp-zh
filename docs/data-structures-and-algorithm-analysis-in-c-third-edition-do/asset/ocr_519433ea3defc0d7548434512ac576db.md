# Chap. 8 File Processing and External Sorting

How big a file be merged in one pass? Assuming $B$ blocks are allocated to the heap for replacement selection (resulting in runs of average length $2B$ blocks), followed by a $B$-way merge, we can process on average a file of size $2B^2$ blocks in a single multway merge. $2B^{k+1}$ blocks can be processed in $k$ $B$-merges. To gain some appreciation for how this works, assume that we have available 0.5MB of working memory, and that a block is $4KB$, yielding 128 blocks in working memory. The average run size is 1MB (twice the memory size). In one pass, 128 runs can be merged. Thus, a file of size 128MB can, on average, be processed in two passes (to build the runs, do one with 5MB of working memory). Another example, assume blocks are 1KB and working memory is $1MB=1024$ blocks. Then 1024 runs of average length 2MB (which is about 2GB) can be combined in a single merge pass. A larger block size would reduce the size of the file that can be processed in one pass for a fixed-size working merge; a smaller block size or larger working memory would increase the file size that can be processed in one merge pass. Two passes allow much larger files to be processed. With 0.5MB of working memory and 4KB blocks, a file of size 16 gigabytes can be processed in two merge passes, which is big enough for most applications. This, is, a very effective algorithm for single disk external sorting.

Figure 81 shows a comparison of the running time to sort various-sized files for the following implementations: (1) standard Merges with two input runs and (2) two-way Merges with large initial runs (limited by the available memory), and (3) $R$-way Merges performed after generating large inputs. In each case, the file was composed of series of four-byte records (a two-byte key and a two-byte data value), or 256K records per megabyte of file size. We can see from this table that using even a modest memory size to create initial runs results in a tremendous savings in time. Doing 4-way merges for $R$ runs beyond about 4 or 8 runs does not help much because lot of time is spent determining which is the next element among the $R$ runs.

We see from this experiment that building large initial runs reduces the running time to slightly than one third of standard Mergesort, depending on file and memory sizes. Using a multway merge cuts the time nearly in half.

In summary, a good external sorting algorithm will seek to do the following:

+   * Make the initial runs as long as possible.
* At stages, overlap input, processing, and output as much as possible.
* Use as much working memory as possible. Applying more memory usually speeds processing. In fact, more memory will have a greater effect than a faster disk. A faster CPU is unlikely to yield much improvement in running time for external sorting, because disk I/O speed is the limiting factor.
