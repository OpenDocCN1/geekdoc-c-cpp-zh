We could write a separate traversal function for each activity that we intend to perform on the tree. A better approach would be to be a generic traversal function, and pass the action to be performed at each node. This organization constitutes the visitor design pattern. ## 1.3.3 Composite

There are two fundamental approaches to dealing with the relationship between a collection and hierarchy of object types. First consider the typical procedural approach. Say we have a base class for page layout entities, with a subclass hierarchy (e.g., page, columns, row, figures, characters, etc.). And there are actions to be performed on a collection of objects (such as rendering the objects to the screen). The procedural design approach is for each action to be implemented as a method that takes a parameter to the base class type. Each action method will traverse through the collection of objects, visiting each object in turn. Each action method contains something like a switch statement that defines the details of the action for each subclass in the collection (e.g., page, column, character). We can cut the code down by using the visitor design pattern that we only need to traverse the once, and then write a visitor subroutine for each action that might be applied to the collection of objects. But each visitor subroutine must still contain logic for dealing each of the subclasses.

In our page composition, there are only a few activities that we would like to perform on the page representation. We render the objects in full detail. Or if we want a "rough draft" rendering that prints only the bounding of objects. If we come up with a new activity to apply to the collection of objects, we do not need to change any of the code that implements the activities. Adding new activities won't happen often for this application. In contrast, there could be many object types, and we frequently add new object types to implementation. Unfortunately, adding a new object type requires that we modify each activity, and the subroutines implementing the activities get long switch statements to distinguish the behavior of the many subclasses.

An alternative design is to have each subclass object in the hierarchy embody the action for the various activities that might be performed. Each subclass will have code to perform each activity (such as full rendering or bounding box rendering). Then, if we wish to apply the activity to the collection, we simply call the first object in the collection and specify the action (as a method call on that object). In the case of our page layout and its hierarchical collection of objects, those objects that contain other objects (such as a row objects that contains letters) will call the appropriate method for each child.

If we want to add a new activity with this organization, we have to change the code for every subclass. But this is relatively rare for our text composing application. In contrast, adding a new object into the subclass hierarchy (which for this application is far more like adding a new rendering function) is easy. Adding a new subclass does not require changing any of the existing subclasses. It merely requires that we define the behavior of each activity that can be performed on the new subclass.

This second design approach of burying the functional activity in the subclass is called the Composite design pattern. A detailed example for using the Composite design pattern is presented in Section 5.3.1.

## 1.3.4 Strategy

Our final example of a design pattern lets us encapsulate and make interchangeable set of alternative actions that might be performed as part of larger activity. Again continuing our text composing application, each output device that we want to render will use its own function for doing the actual rendering. That is, the objects will be broken down into constituent pixels or strokes, but the actual mechanics of rendering a pixel or stroke will depend on the output device. We don't want to be the subroutine performing the rendering action a method or class that does the appropriate rendering details for that output device. That is, we wish to hand to the appropriate "strategy" for accomplishing the details of the rendering task. Thus, this approach is called the Strategy design pattern.

The Strategy design pattern will be explored further in Chapter 7. There, a sorting function is given a class (called a comparator) that understands how to extract and compare the key values for be sorted. In this way, the sorting function does not need to know any details of how its record type is implemented.

One of the biggest challenges in designing patterns is that times one is quite different from another. For example, you might be confused about the difference between the composite pattern and the visitor pattern. The distinction is that the composite design pattern is about whether to give control of the traversal process to the nodes of the tree or to the tree itself. Both approaches can use of the visitor pattern to allow rewriting the traversal function many times, by encapsulating the activity performed at each node.

But isn't the strategy pattern doing the same thing? The difference between the visitor pattern and the strategy pattern is more subtle. The difference is primarily of intent and focus. In both strategy pattern and visitor pattern, an activity is being passed as a parameter. The strategy pattern is focused on encapsulating an activity that is part of a larger process, so that different ways of performing that activity can be substituted. The visitor pattern is focused on encapsulating an activity that will be performed on members of a collection so that different activities can be substituted.

## 1.4 Problems, Algorithms, and Programs

Programmers commonly deal with problems, algorithms, and programs. These are three distinct concepts.

**Problems:** As your intuition would suggest, a **problem** is a task to be performed. It is best thought of in terms of inputs and outputs. A problem definition should not include any constraints on *how* it is to be solved. The solution should be developed only after the problem is precisely defined and thoroughly understood. However, a problem definition should include constraints on the resources that may be consumed. For any problem to be solved by a computer, there are always such constraints, whether stated or implied. For example, any program may use only the main memory and disk space available, and it must run in a “reasonable” amount of time.

Problems can be viewed as functions. A **function** is a matching between inputs (the **domain**) and outputs (the **range**). An input to a function might be a single value or a collection of information. The values making up an input are called **parameters** of the function. A specific selection of values for the parameters is called an **instance** of the problem. For example, the input to a sorting function might be an array of integers. An array of integers, with a given size and specific values for each position in the array, would be an instance of the sorting problem. Different instances might generate the same output. Any problem instance must always result in the same output every time the function is invoked using that particular input.

This concept of all problems behaving like mathematical functions might not match your intuition for the behavior of computer programs. You might know of programs which can give you the same input value on two separate occasions, and two different outputs will result. For example, if you type “**date**” to a UNIX command prompt, you will get the current date. Naturally the date will be on different days, even though the same command is given. However, there is obviously more to the input for the date program than the command that you type to run. The date program computes a function. In other words, on any particular day there can only be a single answer returned by a properly running date program.
