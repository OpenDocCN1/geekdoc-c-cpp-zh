While selecting the median in this way is guaranteed to eliminate a fraction of the elements (leaving at most $(7n-5)/10$ elements left), we still need to be sure that our recursion yields a linear-time algorithm. We model the algorithm by the following recurrence:

```
$T(n) \le T(\lceil n/5\rceil) + T(\lceil(7n-5)/10\rceil) + 6\lceil n/5\rceil + n - 1.$
```

$T(\lceil n/5\rceil)$ term comes from computing the median of the medians-of-fives, $6\lceil n/5\rceil$ term comes to calculate the cost of median-of-fives (exactly six comparisons for each group of five element), and $T(\lceil(7n-5)/10\rceil)$ term comes from the recursive call of the remaining (up to 70% of the elements that might be left.)

We prove that this recursion is linear by assuming that it is true for constant $r$, and then show $T(n) \le rn$ for all $n$ greater than some bound.

```
$T(n) \le T(\lceil n/5\rceil) + T(\lceil(7n-5)/10\rceil) + 6\lceil n/5\rceil + n - 1$
$\le r(\lceil n/5\rceil+1) + r(\lceil(7n-5)/10\rceil+1) + 6(\lceil n/5\rceil+1) + n - 1$
$\le r(\frac{n}{5}+1) + r(\frac{7n}{10}+\frac{11}{10}) + 6(\frac{n}{5}+1) + n - 1$
$\le r(\frac{9n+22}{10}) + \frac{3n+10}{2}$
```

This is true for $r \ge 23$ and $n \ge 380$. This provides a base case that allows us to use induction to prove that for $n \ge 380$, $T(n) \le 23n$.

In reality, this is not practical because the constant factors are so high. So much work is being done to guarantee linear time performance that it is more efficient to rely on chance to select the pivot, perhaps by picking it at random or picking the middle value out of the current subarray.

We conclude this with an effort to find the sorting algorithm with the fewest possible candidates. It might well be the result will not be practical for a general-purpose sorting algorithm. But we recall our earlier affinity to sports tournaments. In sports, a "comparison" between two teams or individuals means a competition between the two. This is expensive (at least compared to some minor book keeping in a computer), and might be worth paying a fair amount to cut down the number of games that need to be played. What if we want to figure out how to hold a tournament that will give us the exact ordering for all teams in the fewest number of total games? Of course, we are assuming the results of each game will be "accurate" in that we assume not only that the outcome of A playing B would always be the same (at least over the period of the tournament), but that transitivity in the results also holds. In practice these are unrealistic assumptions, such assumptions are implicitly part of many tournament organizations. Most tournament organizers, we can simply accept these assumptions and come up with an algorithm for playing the games that gives us some ranking based on the results we obtain.

Recall Insertion Sort, when we put element $i$ into a sublist of the first $i-1$ elements. What if we modify the Insertion Sort algorithm to use binary search to locate where the $i$-th element goes in the sorted sublist? This algorithm is called binary insert sort. For a general-purpose sorting algorithm, this is not practical because we have to (on average) move $i/2$ elements to make room for the newly inserted element in the sorted sublist. But if we count only comparisons, binary insert sort is pretty good. And we can use some ideas to get closer to an algorithm that uses the absolute number of comparisons to sort.

Consider what when we run insert sort on five elements. How many comparisons do we need? We insert the second with one comparison, the third with two comparisons, and the fourth with two. When we insert the fifth element into the sorted list of four elements, we need three comparisons. Notice exactly what happens when we attempt to do this. We compare the fifth element against the second. If the fifth is bigger, we have to compare it against the third, and if it is bigger we have to compare it against the fourth. In general, is binary search most efficient? When we have $2^k-1$ elements in the list, it is least efficient when we have $2^k$ elements in the list. So can we do a bit better if we arrange our insertions to avoid inserting an element into a list of size?

Figure 15.6 illustrates a different organization for comparisons. First we compare the first and second element, and the third and fourth elements. The two winners are compared, yielding a binary tree. We can view this as a chain of three elements with element A hanging off the root. If we insert element B into the sorted chain of three elements, we will end up with posets on the right side of Figure 15.6 at a cost of 2 comparisons (because we already know it is smaller than either one or two elements). Thus the total number of comparisons needed to sort five elements is at most seven. If we have ten elements to sort, we can first make five pairs (using five comparisons) and then sort the winners using the algorithm described (using five more compares). Now all we need to do is deal with the original losers. We can generalize this process for any number of elements as:

## 15.7 Optimal Sorting

**Figure 15.6** Organizing comparisons for sorting. First we order two pairs of elements and then compare the winners to form a binary tree of four elements. The original loser to the root is labeled A, the remaining three elements form a sorted chain. We then insert element B into the sorted chain to yield a final sorted list.

- Recurse the sort.
- Fold in the losers. We use binary insert to place the losers. However we are free to choose the best ordering for inserting, keeping in mind the fact that binary search has the same cost for $2^k-1$ items. For example, binary search requires three comparisons in the worst case for lists of size 4, 5, or 7. So we pick the order of inserts to optimize the binary searches, which means picking an order that avoids the boundary on list size to require an additional comparison. This sort is called **merge insert**, and also known as Ford-Johnson sort.

For ten elements, the poset shown in Figure 15.7 folds in the last four elements (labeled 1 to 4) in the order Element 3, Element 4, Element 1, and finally Element 2. Element 3 will be inserted into a list of size three, costing two comparisons. Depending on where Element 3 ends up in the list, Element 4 will be inserted into a list of size 2 or 3, costing two comparisons in either case. Depending on where Element 3 and 4 are in the list, Element 1 will be inserted into a list of size 5, 6, or 7, all of which require three comparisons to place in right order. Finally Element 2 will be inserted into a list of size 5, 6, or 7.

Merge insert is pretty good, but is it optimal? Recall from Section 7.9 that **information theoret lower bound** for sorting can be proved to be $\lceil \log_2 n! \rceil$. That is, we can prove a lower bound of exactly $\lceil \log_2 n! \rceil$ comparisons. Merge insert gives us a number of comparisons equal to this information theoret lower bound for all values up to $n=12$. At $n=12$, merge insert requires 30 comparisons while the information theoret lower bound is only 29. However, for such a small number of elements, it is possible to do an exhaustive study of every possible arrangement of comparisons. It turns out there is in fact no possible arrangement of comparisons that make the lower bound less than 30 comparisons when $n=12$. Thus, the information theoret lower bound is an underestimate in this case, because 30 is the best that can be done.

Call the optimal cost for $n$ elements $S(n)$. We know that $S(n+1) \le S(n) + \lceil \log_2(n+1) \rceil$ because we sort elements and use binary insert for the last one. For all $m$, $S(n+m) \le S(n) + M(m,n)$ where $M(m,n)$ is the best time to merge two sorted lists. For $n=47$, it turns out that we can do better by splitting the list into pieces of size 5 and 42, and then merging. Merge sort is not quite optimal. But it is extremely good, and nearly optimal for smaller numbers of elements.
