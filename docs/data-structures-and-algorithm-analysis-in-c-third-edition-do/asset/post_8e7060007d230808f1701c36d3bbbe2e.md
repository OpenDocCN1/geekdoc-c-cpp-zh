Function swap(A, i, j) exchanges $i$ and $j$ in array $A$. To see that this works, notice that each pass through the `for` loop will move at least the integer with $i$ to its correct position in the array, and during this iteration, the value of $A[i]$ must be greater than or equal to $i$. A total of at $n$ swap operations takes place, because an integer cannot be moved out of its correct position once it has been placed, and each swap operation places at least one integer in its correct position. Thus, this code fragment has cost $\Theta(n)$. However, it requires more time than the first fragment. A second principle for the relationship between a program's space and time requires programs that process information stored on disk, as discussed in Chapter 8 and thereafter. Strang enough, the disk-based space/time tradeoff is the reverse of the space/time tradeoff for programs using main memory.

The disk-based space/time tradeoff states that the smaller you can make your storage requirements, the faster your program will run. This is because the time to read information from disk is enormous compared to computation time, so any amount of additional computation to unpack the data is going to be less than the reading time saved by reducing the storage requirements. Naturally this principle does not hold true in all cases, but it is good to keep in mind when designing programs that process information stored on disk.

## 3.10 Speeding Up Your Programs

In practice, there is not such a difference in running time between an algorithm with growth rate $\Theta(n \log n)$ and another with growth rate $\Theta(n)$. There is, however, an enormous difference in running time between algorithms with growths of $\Theta(n \log n)$ and $\Theta(n^2)$. As you will see during the course of your study of common data structures and algorithms, it is not unusual that a problem whose solution requires $\Theta(n^2)$ time also has a solution requiring $\Theta(n \log n)$. Examples include sorting and searching, two of the most important computer problems.

Example 3.18 Following a true story. A few years ago, one of my graduate students had a big problem. His thesis work involved intrications on a large database. He was now working on the final step. "Dr. Shaffer," he said, "I am running this program and it seems to be taking a long time." After examining the algorithm we realized that his running time was $\Theta(n^2)$, and that it would likely take one to two weeks to complete. Even if we could keep the computer running uninterrupted then, he was hoping to complete his thesis and graduate before then. Fortunately, we realized that there was a fairly easy way to convert the algorithm so that its running time was $\Theta(n \log n)$. By the next day he had modified the program. It ran in only a few hours, and he finished his thesis on time.

While not nearly as important as changing an algorithm to reduce its growth rate," "code tuning" can also lead to dramatic improvements in running time. Code tuning is the art of optimizing a program to run faster or require less storage. For many programs, code tuning can reduce running time by a factor of ten, or once tuned a critical function in a program — without changing any basic — to achieve a factor of 200 speed. With this speedy, I did major changes in the representation of the information, converting from a symbolic coding scheme to a numeric coding scheme on which I was able to do direct computation.

Here are some suggestions for ways to speed up your programs by code tuning. The most important thing to realize is that most statements in a program do not have effect on the running time of that program. There are normally just a few subroutines, possibly even key lines of code within the subroutines, that account for most of the running time. There is little point to cutting in half the running time of a subroutine that accounts for only 1% of the total running time. Focus your attention on those parts of the program that have the most impact.

When code tuning, it is important to gather good statistics. Many compilers and operating systems include profilers and other special tools to help gather information on time and use space. These are invaluable when trying to make a program more efficient, because they can tell you where to invest your effort.

A lot of code tuning is based on the principle of avoiding work rather rather than speeding up work. A common situation occurs when we can test for a condition that lets us skip some work. However, such a test is never completely free. Care that the cost of the test does not exceed the amount of work saved. While one test might be cheaper than the work potentially saved, the test must always be made and the work can be avoided only some fraction of the time.

**3.19** A common operation in computer graphics applications is to find which among a set of complex objects contains a given point in space. Many useful data structures and algorithms have been developed to deal with variations of this problem. Most such implementations involve the following tuning step. Directly testing whether a complex object contains the point in question is relatively expensive. Instead, we screen for whether the point is contained within a bounding box for the object. The bounding box is the smallest rectangle (usually defined to have sides perpendicular to the $x$ and $y$ axes) that contains the object. If the point is not in the bounding box, then it cannot be in the object. If the point is in the bounding box, only then we conduct the comparison of the object versus the point. Note that if the point is outside the bounding box, we saved time because the bounding box is cheaper than the comparison of object versus the point. But if the point is inside the bounding box, then that test is redundant because we still have to compare the point against the object. Typically the amount of work avoided by making this test is greater than the cost of making it on every object.

**Example 3.20** Section 7.2.3 presents a sorting algorithm named Selection Sort. The distinguishing characteristic of this algorithm is that it requires few swaps of records stored in the array to be sorted. However, it performs an unnecessary swap operation when it tries to swap a record with itself. This work could be avoided by testing whether the indices being swapped are the same. However, this event does not occur often. Because the cost of the test is high enough compared to the work saved when the test is successful, adding the test will slow down the program faster than speed it up.

Careful not use tricks that make the program unreachable. Most code tuning is simply cleaning a carelessly written program, not taking a clear program and adding tricks. In particular, you should develop an appreciation for the capabilities of modern compilers to make extremely good optimizations of expressions. "Optimization of expressions" here means a rearrangement of arithmetic or logical expressions to run more efficiently. Be careful not to damage the compiler's ability to do such optimizations for you in effort to optimize the expression yourself. Always check that your "optimizations" really improve the expression by running the program before and after the change on a suitable benchmark set of input. Many times I have been wrong about the positive effects of code tuning in my programs. Most often I am wrong when I try to optimize an expression. It is hard to better than the compiler.
