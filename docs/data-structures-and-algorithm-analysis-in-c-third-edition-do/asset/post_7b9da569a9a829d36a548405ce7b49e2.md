```cpp
template <typename E, typename getkey>
void radix(E A[], E B[]) {
    int n, int k, int r, int cnt[] {
    // cnt[i] stores number of records in bin[i]
    int j;

    for (int i=0, rto=1; i<k; i++, rto*=r) { // For k digits
        for (int j=0; j<r; j++) cnt[j] = 0; // Initialize cnt

        // Count the number of records for each bin on this pass
        for (int j=0; j<n; j++) cnt[getkey(A[j])/rto]++;
        // Index B: cnt[j] will be index for last slot of bin j.
        for (int j=1; j<r; j++) cnt[j] = cnt[j-1] + cnt[j];

        // Put records into bins, from bottom of each bin.
        // Since bins fill from bottom, j counts downwards
        for (int j=n-1; j>=0; j--)
            B[--cnt[getkey(A[j])/rto]] = A[j];

        for (int j=0; j<n; j++) A[j] = B[j]; // Copy B back to A
    }
}
```

Figure 17.8 The Radix sort algorithm.

In this example r=10 bins and n=12 keys in the range 0 to $r^2-1$. The total computation is $\Theta(n)$, which we look at each record and bin a constant number of times. This is a great improvement over the simple Bsort where the number of bins must be as large as the key range. Note that the example uses r=100 so as to make the computations easy to visualize: Records were placed into bins based on the value of the rightmost and the leftmost decimal digits. Any number of bins would have worked. This is an example of a Radix Sort, called because the computations are based on the radix or the base of the key in any key range. We assign records to bins based on the keys' values from the rightmost to the leftmost. If there are $k$ digits, this requires that we sort $k$ times.

As Merges, an efficient implementation of Radix Sort is somewhat difficult to achieve. In particular, we would prefer to sort an array of values and avoid processing linked lists. If many values will be in each bin, then an auxiliary array of size $r$ can be used to hold the bins. For example, if the first pass the bin 0 will receive three records and the bin 1 will receive five records, then we could simply reserve the first three positions for 0 and the next five positions for 1. This approach is taken by the C++ implementation of Figure 7.18. At the end of each pass, the records are copied back to the original array.

## 7.7 Binsort and Radix Sort

The first for loop initializes array `cnt`. The second loop counts the number of records to be assigned to each bin. The third loop sets the values in `cnt` to their proper indices within array $B$. Note that the index stored in `cnt[j]` is the last index for bin $j$; bins are filled from high index to low index. The fourth loop assigns the records to the bins (within array $B$). The final loop simply copies the records back to array $A$ for the next pass. Radix sort stores $r^i$ in binary computation over the $i$-th iteration. Figure 7.19 shows how this algorithm processes the input in Figure 7.17.

This algorithm passes over the list of $n$ numbers in base $r$, with $\Theta(n+r)$ work done at each pass. The total work is $\Theta(nk+rk)$. What might be smaller in terms of $n$? One could use base 2 or 10. Base 26 would be appropriate for sorting strings. For now, we will treat $k$ as a constant value and ignore it for the purpose of determining complexity. Variable $k$ is related to the range key: The maximum number of digits that a key may have in base $r$. In some applications we can determine $k$ to be of limited size and so might to consider it a constant. In this case, Radix Sort is $\Omega(n)$ in the best case, making it the best asymptotic complexity that we have studied.

Is it a reasonable assumption to treat $k$ as a constant? Or is there some relationship between $k$ and $n$? If the range is limited and duplicate key values are common, there might be no relationship between $k$ and $n$. To make this distinction clear, use $N$ to denote the number of distinct keys used by the $n$ records. Thus, $N \le n$. Because it takes a minimum of $\log_r N$ digits to represent $N$ distinct keys, we know that $k \le \log_r N$.

Now, consider the situation in which no keys are duplicated. If there are $n$ unique keys ($n=N$), then it requires $n$ distinct code values to represent them. Thus, $k \ge \log_r n$. Because it requires at least $\Omega(\log n)$ digits (with a constant factor) to distinguish between $n$ distinct keys, $k$ is $\Omega(\log n)$. This yields an asymptotic complexity of $\Omega(n \log n)$ for Radix Sort to process $n$ distinct keys.

It is possible that the range is much larger; $\log n$ bits is merely the best case for $n$ distinct values. Thus, the $n$ estimate for $k$ could be overly optimistic. The real of this analysis is that, for the general case of $n$ distinct key values, Radix Sort is at best a $\Omega(\log n)$ sorting algorithm.

Radix Sort can be improved by making base $r$ as large as possible. Consider the case of an integer key value. Set $r = 2^i$ for some $i$. In other words, the value of $r$ is related to the number of bits of the key processed on each pass. Each time the number of bits is doubled, the number of passes is cut in half. When setting $r = 2^{16}$ allows the key to be processed one byte at a time. A 32-bit key requires only four passes. ## 7.8 Empirical Comparison of Sorting Algorithms

Which sorting algorithm is fastest? Asymptotic complexity analysis lets us distinguish between Θ(n²) and Θ(n log n) algorithms, but it does not help distinguish between algorithms with the same asymptotic complexity. Nor does asymptotic analysis anything about which algorithm is best for small lists. For answers to these questions, we can turn to empirical testing.
