
## Sec. 15.5 State Space Lower Bounds Proofs

```
// Return the minimum and maximum values in A
// between positions 1 and r
template <typename E>
void MinMax(E A[], int l, int r, E& Min, E& Max) {
    if (l == r) {
        // n=1
        Min = A[l];
        Max = A[r];
    }
    else if (l+1 == r) { // n=2
        Min = min(A[l], A[r]);
        Max = max(A[l], A[r]);
    }
    else { // n>2
        int Min1, Min2, Max1, Max2;
        int mid = (l + r)/2;
        MinMax(A, l, mid, Min1, Max1);
        MinMax(A, mid+1, r, Min2, Max2);
        Min = min(Min1, Min2);
        Max = max(Max, Max2);
    }
}
```

For example, what if we have six items in the list? If we break the list into two sublists of three elements, the cost would be 8. If we break the list into a sublist of size two and another of size four, the cost would only be 7.

With divide and conquer, the best algorithm is the one that minimizes the work, not necessarily the one that balances the input sizes. One lesson to learn from this example is that it is important to pay attention to what happens for small sizes of n, because any division of the list will eventually produce many small lists.

We can model all divide-and-conquer strategies with this recurrence:

```
T(n) = \begin{cases} 0 & n=1 \\ 1 & n=2 \\ \min_{1\le k\le n-1}(T(k) + T(n-k)) + 2 & n>2 \end{cases}
```

That, we want to find a way to break up the list that will minimize the total work. If we examine various ways of breaking up small lists, we will eventually recognize that breaking the list into a sublist of size 2 and a sublist of size n-2 will always produce results as good as any other division. This strategy yields the following recurrence:

```
T(n) = \begin{cases} 0 & n=1 \\ 1 & n=2 \\ T(n-2) + 3 & n>2 \end{cases}
```

This recurrence (and the corresponding algorithm) yields $T(n) = [3n/2] - 2$ comparisons. Is this optimal? We now introduce another tool to our collection of lower bounds techniques: The state proof.

We will model our algorithm by defining a state that the algorithm must be in any given instant. We can then define the start state, the end state, and the transitions between states that algorithm can support. From this, we will reason about the minimum number of states that the algorithm must go through to get from the start to the end, to reach a state lower bound.

At any given instant, we can track the following categories of elements:

- Untested: Elements that have not been tested.
- Winners: Elements that have won at least once, and never lost.
- Losers: Elements that have lost at least once, and never won.
- Middle: Elements that have both won and lost at once.

We define the current state as a vector of four values, $(U, W, L, M)$ for untested, winners, losers, and middles, respectively. For a set of $n$ elements, the initial state of the algorithm is $(n, 0, 0, 0)$ and the end state is $(0, 1, 1, n-2)$. Thus, every run of the algorithm must go from $(n, 0, 0, 0)$ to state $(0, 1, 1, n-2)$. We also observe that once an element is identified as a middle, it can be ignored because neither is the minimum nor the maximum.

Given that there are four types of elements, there are 10 types of comparison. Comparing with a middle cannot be more efficient than other comparisons, so we should ignore those, leaving six comparisons of interest. We can enumerate the effects of each comparison type as follows. If we are in state $(i, j, k, l)$ and we have a comparison, then the state changes are as follows:

```
$U : U \quad (i-2, j+1, k+1, l)$
$W : W \quad (i, j-1, k, l+1)$
$L : L \quad (i, j, k-1, l+1)$
$L : U \quad (i-1, j+1, k, l) \text{ or } (i-1, j, k, l+1)$
$W : U \quad (i-1, j, k, l+1) \text{ or}$
$W : L \quad (i, j, k, l) \text{ or } (i, j-1, k-1, l+2)$
```

Now, let us consider what the adversary will do for the various comparisons.
The adversary will make sure that each comparison does the least amount of work in taking the algorithm toward the goal state. For example, comparing a winner to a loser is of no value because the worst case result is to learn nothing (the winner remains a winner and the loser remains a loser). ```

Only the last two transition types increase the number of middles, so there must be $n - 2$ of these. The number of untested elements must go to 0, and the first transition is the most efficient way to do this. Thus, $[n/2]$ are required. Our conclusion is that the minimum possible number of transitions (comparisons) is $n + [n/2] - 2$. Thus, our algorithm is optimal.

## 15.6 Finding the ith Best Element

We now tackle the problem of finding the ith best element in a list. As observed earlier, one option is to sort the list and simply find the $i$th position. However, this process provides considerably more information than we need to solve the problem. The minimum amount of information that we actually know can be visualized as shown in Figure 15.4. Thus, all we need to know is the $i - 1$ items less than our desired value, and the $n - i$ items greater. We do not care about the relative order within lower and upper groups. Recall at the lower bound, can we tighten beyond the trivial lower bound of $n$ comparisons? We will focus on the specific question of finding the median element ($i$).

Looking at the Quicksort, we get bad performance if the pivot is first or last element in the array. This would lead to possibly $O(n^2)$ performance. However, if the pivot were to always cut the array in half, then our cost would be modeled by the recurrence $T(n) = T(n/2) + n = 2n$ or $O(n)$.

Finding the average cost requires us to use a recurrence with full history, similar to the one used to model the cost of Quicksort. If we do this, we will find that $T(n)$ is in $O(n)$ in the average case.

Is it possible to modify our algorithm to get worst-case linear time? To do this, we need to pick a pivot that is guaranteed to discard a fixed fraction of the elements. We cannot choose a pivot at random, because doing so will not meet this guarantee. The ideal situation would be if we could pick the median value for the pivot each time. But that is essentially the same problem we are trying to solve.

Notice, however, if we choose any constant $c$, and then we pick the median from a sample of size $n/c$, then we can guarantee that we will discard at least $n/2c$ elements. Actually, we can do better than this by selecting small subsets of a constant size (so we can find the median in each constant time), and then taking the median of these medians. Figure 15.5 illustrates this idea. This observation leads directly to the following algorithm.
