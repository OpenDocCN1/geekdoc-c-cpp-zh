running time for Quicksort can be improved (by a constant factor), and many study have gone into optimizing this algorithm. The most obvious place for improvement is the findpivot function. Quicksort's worst case arises when the pivot does a poor job of splitting the array into equal subarrays. If we are willing to do more work searching for a better pivot, the effects of a bad pivot can be decreased or even eliminated. A good choice is to use the "median of three" algorithm, which uses a random generator to choose the positions is relatively expensive. A common promise is to look at the first, middle, and last positions of the current subarray. However, our simple findpivot function that takes the middle value as pivot has the virtue of being highly unlikely to get a bad input by chance, and is quite cheap to implement. This is in sharp contrast to selecting the first or last element as the pivot, which would yield bad performance for many permutations that are nearly sorted or nearly reversed

This might not seem to be relevant if most of the time we sort large arrays, should not matter how long Quicksort takes in the rare instance when a small array is sorted it will be fast away. But you should notice that Quicksort itself sorts many, many small arrays! This happens as a natural-product of the divide and conquer approach.

simple improvement might then be to replace Quicksort with a faster sort for small numbers, Insertion Sort or Selection Sort. However, there is an even better — optimization. When Quicksort partitions are below a certain size, do nothing! The values within partition will be out of order. However, we know that all values in the array to the left of the partition are smaller than all values in the partition. All values in the array to the right of the partition are greater than all values in the partition. Thus, if Quicksort only gets the values to "nearly" the right locations, the array will be close to sorted. This is an ideal situation in which take advantage of the best-case performance of Insertion Sort. The final step is a simple call to Insertion Sort to process the entire array, putting the elements into sorted order. Empirical testing shows that the subarrays should be left unordered whenever they get down to nine or fewer elements.
