Frequently used records will, over time, move to the front of the list. Records that were once accessed but are no longer used will drift toward the back. It appears to have good properties with respect to changing frequency of access. Unfortunately, there are pathological sequences of access that can transpose poorly. Consider the case where the last record of the list (call it X) is accessed. This is then swapped with the next-to-last record (call it Y), making Y the last. If Y is now accessed, it swaps with X. A repeated series of alternating accesses between X and Y will continually search to the end of the list, because neither record will ever make progress toward the front. However, such pathological cases are unusual in practice. A variation on transpose would be to move the accessed record forward in the list by some fixed number of steps.

**Example 9.4** Assume that we have eight records, with key values A to H, and they are initially placed in alphabetical order. Now, consider the result of applying the following access pattern:

```
D F E G A D F E
```

Assume that when record's frequency count goes up, it moves forward in the list to become the last record with that value for its frequency count. After the first two accesses, F will be the first record and D will be the second. The final list resulting from these accesses will be

```
F G D E A B C H
```

and the total cost for the twelve accesses will be 45 comparisons. If the list is organized by the move-to-front heuristic, then the final list

```
E G F D A B C H
```

and the total number of comparisons required is 54.

Finally, if the list is organized by the transpose heuristic, the final list will be A B F D G E C H, and the total number of comparisons required is 62.

While self-organizing lists do not generally perform as well as search trees or sorted lists, both which require $O(\log n)$ search time, there are many situations in which self-organizing lists provide a valuable tool. Obviously they have an advantage over sorted lists that are not sorted. This means that the cost to insert a new record is low, which could more than make up for the higher search cost when insertions are frequent. Self-organizing lists are simpler to implement than search trees and are more efficient for small lists. Nor do they require additional space. Finally, in the case of an application where sequential search is “almost” fast enough, changing an unsorted list to a self-organizing list might speed the application at a minimum cost in additional code.

An example of applying self-organizing lists, consider an algorithm for compressing and transmitting messages. The list is self-organized by the move-to-front rule. Transmission is in the form of words and numbers, by the following rules:

- 1. If the word has been seen before, transmit the current position of the word in the list. Move the word to the front of the list.
- 2. If the word is seen for the first time, transmit the word. Place the word at the front of the list.

Both the sender and the receiver track the position of words in the list the same way (using the move-to-front rule), so they agree on the meaning of numbers that encode occurrences of words. Consider the following example message to be transmitted (for simplicity, ignore case in letters).

> The car on the left hit the car i.

The first three words have not been seen before, so they must be sent as full words. The fourth word is the second appearance of “the,” which is at this third word. Thus, we only need to transmit the position value “3,” the next two words have not yet been seen, so must be sent as full words. The seventh word is the third appearance of “the,” which coincidentally is again in third position. The eighth word is the second appearance of “car,” which is now in the fifth position of the list. “T” is a new word, and the last word “left” is now in fifth position. Thus the entire transmission would be

The car on 3 left hit 3 5 1 5.

## 9.4 Hashing

This section presents a completely different approach to searching: by direct access based on key value. The process of finding a record using some computation to map its key to a position in the array is called hashing. The function that maps keys to positions is called a hash function and will be denoted by $h$. The array that holds the records is called the hash table. A position in the table is also known as a slot. The number of slots in HT will be denoted by $M$, with slots numbered from 0 to $M-1$. The goal of a hashing system is to arrange things such that, for any key $K$ and some hash function $h$, $i = h(K)$ is a slot such that $0 \le h(K) < M$, and we have the record at $HT[i]$ equal to $K$.

Hashing is not good for applications where multiple records with the same key value are permitted. Hashing is not a good method for answering range searches. In other words, we cannot easily find all records whose key fall within a certain range. Nor can we find the record with the minimum or maximum key value, or the records in key order. Hashing is most appropriate for answering the question, "What record, if any, has key $K$?" For applications where access involves only exact-match queries, hashing is usually the search method of choice because it is extremely efficient when implemented correctly. As you will see in this section, there are many approaches to hashing and it is easy to devise an inefficient implementation. Hashing is suitable for both in-memory and disk-based searching and is one of the two most used methods for organizing large databases stored on disk (the other is B trees).
