
## Chap. 3 Algorithm Analysis

Because the phrase "has an upper bound to its growth rate of $f(n)$" is long and often used when discussing algorithms, we adopt a special notation, called big-Oh notation. If $T(n)$ is the upper bound for an algorithm's growth rate (say, the worst case) is $f(n)$, then we would write that is "in the set $O(f(n))$ in the worst case" (or "in $O(f(n))$ in the worst case"). For example, if $n^2$ grows as fast as $T(n)$ (the running time of our algorithm) for the worst-case input, we would say the algorithm is "in $O(n^2)$ in the worst case",

The following is a precise definition for an upper bound. $T(n)$ represents the true running time of the algorithm. $f(n)$ is some expression for the upper bound.

For $T(n)$ a non-negatively valued function, $T(n)$ is in set $O(f(n))$ if there exist two positive constants $c$ and $n_0$ such that $T(n) \le cf(n)$ for all $n > n_0$.

Constant $n_0$ is the smallest value of $n$ for which the claim of an upper bound holds true. Usually $n_0$ is small, as $c$, but it does not need to be. You must also be able to pick some constant $c$, but it is irrelevant what value $c$ actually is. In other words, the definition says that for all inputs of type in question (such as the worst case for all inputs of size $n$) are large enough (i.e., $n > n_0$), the algorithm executes in less than $cf(n)$ steps for some constant $c$.

**Example 3.4** Consider the sequential search algorithm for finding a specified value in an array of integers. If visiting and examining one value in the array requires $c_a$ steps where $c_a$ is a positive number, and if the value we search for has equal probability of appearing in any position in the array, then in the average case $T(n) = c_an/2$. For all values of $n > 1$, $c_an/2 \le c_an$. Therefore, by the definition, $T(n)$ is in $O(n)$ for $n_0 = 1$ and $c = c_a$.

**Example 3.5** For a particular algorithm, $T(n) = c_1n^2 + c_2n$ in the average case where $c_1$ and $c_2$ are positive numbers. Then, $c_1n^2 + c_2n \le c_1n^2 + c_2n^2$ for all $n > 1$. So, $T(n) \le cn^2$ for $c = c_1 + c_2$, and $n_0 = 1$. Therefore, $T(n)$ is in $O(n^2)$ by the second definition.

**Example 3.6** Assigning the value from the first position of an array to a variable takes constant time regardless of size of the array. Thus, $T(n) = c$ (for the best, worst, and average cases). We could say in this case that $T(n)$ is in $O(c)$. However, it is traditional to say that an algorithm whose running time has a constant upper bound is in $O(1)$.

## Sec. 3.4 Asymptotic Analysis

If someone asked you out of the blue “Who is the best?” natural reaction should be to reply “Best at what?” In the same way, if you are asked “What is the growth rate of this algorithm,” you would need to ask “When? Best case? Average case? Or worst case?” Some algorithms have the same behavior no matter which instance you provide. An example is finding the maximum in an array of integers. For many algorithms, it makes a big difference, such as when searching an unsorted array for a particular value. So any statement about the upper bound of an algorithm must be in the context of some class of inputs $n$. We measure this upper bound nearly on the best-case, average-case, or worst-case inputs. Thus, we cannot say, “this algorithm has an upper bound to its growth rate of $n^2$ in the average case.

Knowing that something is in $O(f(n))$ says only how bad things can be. Perhaps things are not so bad. Because sequential search is $O(n)$ in the worst case, it is also true to say that sequential search is in $O(n^2)$. But sequential search is for large $n$, in a way that is not true for other algorithms in $O(n^2)$. We always seek to define the running time of an algorithm with the tightest (lowest) possible upper bound. Thus, we prefer to say that sequential search is in $O(n)$. This also explains why the phrase “is $O(f(n))$” or the notation “$\in\ O(f(n))$” is used instead of “is $O(f(n))$” or “$= O(f(n))$”. There is no strict equality to the use of big-oh. Big-Omega is in $O(n^2)$, but $O(n^2)$ is not in $O(n)$.

## 3.4.2 Lower Bounds

Big-Omega describes an upper bound. In other words, big-Omega states a claim about the greatest amount of some resource (usually time) that is required by an algorithm for some class of inputs of size $n$ (typically the worst input, the average of all possible inputs, or the best such).

Similar notation is used to describe the least amount of an algorithm needs for some class of input. Like big-Omega notation, this is a measure of the algorithm's growth rate. Like big-Omega, it works for any resource, but we often measure the least amount of time required. And again, like big-Omega, we are measuring the resource required for some particular class of inputs: worst-, average-, or best-case input of size $n$.

The lower bound for an algorithm (or a problem, as explained later) is denoted by the symbol $\Omega$, pronounced “big-Omega” or just “Omega.” The following definition for $\Omega$ is symmetric with the valued function, $T(n)$

For $T(n)$ a non-negatively valued, $T(n)$ is in $\Omega(g(n))$ if there exist two positive constants $c$ and $n_0$ such that $T(n) \ge cg(n)$ for all $n > n_0$.

> An alternate (non-equivalent) definition for $\Omega$ is

### Example 3.7 Assume $T(n) = c_1n^2 + c_2n$ for $c_1$ and $c_2 > 0$. Then,

$c_1n^2 + c_2n \geq c_1n^2$

for all $n > 1$. So, $T(n) \geq cn^2$ for $c = c_1$ and $n_0 = 1$. Therefore, $T(n)$ is in $\Omega(n^2)$ by the definition.

It is also true that the example of Example 3.7 is in $\Omega(n)$. However, with big-O notation, we wish to get the "tightest" for $\Omega$ notation (the largest) bound possible, thus we prefer to say that this running time is in $\Omega(n^2)$.

Recall the sequential search algorithm to find a value $K$ within an array of integers. In the average and worst cases this algorithm is in $\Omega(n)$, because in both the average and worst cases we must examine *least* $cn$ values (where $c$ is $1/2$ in the average case and 1 in the worst case).

## 3.4.3 Notation

The definitions for big-O and $\Omega$ give us ways to describe the upper bound for an algorithm (if we can find an equation for the maximum cost of a particular class of inputs of size $n$) and the lower bound for an algorithm (if we can find an equation for the minimum cost for a particular class of inputs of size $n$). When the upper and lower bounds are the same within a constant factor, we indicate this by using $\Theta$ (big-Theta). If an algorithm is said to be $\Theta(h(n))$ then it is in $O(h(n))$ and $\Omega(h(n))$

This definition says that for an "interesting" number of cases, the algorithm takes least $cg(n)$ time. Note that this definition is not symmetric with the definition of big-O. For $\Omega$ to be a lower bound, this definition does not require $T(n) \geq cg(n)$ for all values of $n$ greater than some constant. It is enough that this happens often enough, in particular that it happens for an infinite number of values. For this alternative definition can be found in the following. Assume an algorithm has the following behavior:

Since $T(n) \geq \frac{n^2}{2}$ for all even $n \geq 2$. So, $T(n) \geq cn^2$ for an infinite number of values of $n$ (i.e, for even $n$) for $c = 1/2$. Therefore, $T(n)$ is in $\Omega(n^2)$ by the definition. For input of size $n$ it takes at least $cn^2$ which is enough to say that the algorithm is in $\Omega(n^2)$. Unfortunately, our first definition will yield a lower bound of $\Omega(n)$ because it is not possible to pick constants $c$ and $n_0$ such that $T(n) \geq cn^2$ for all $n \geq n_0$. The alternative definition results in a lower bound of $\Omega(n^2)$, which fits to common sense more closely. Fortunately, few real algorithms or computer programs display the pathological behavior of this example. Our first definition for $\Omega$ generally yields the expected result.

As you can see from this discussion, asymptotic notation is not a law of nature. It is merely a powerful tool used to describe the behavior of algorithms.
