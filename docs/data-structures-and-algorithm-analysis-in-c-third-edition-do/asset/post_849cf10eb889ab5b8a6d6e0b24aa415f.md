### 8.5.3 Multiway Merging

The second stage of a typical external sorting algorithm merges the runs created by the first stage. Assume that we have *R* runs to merge. If a simple two-way merge is used, then *R* runs (regardless of their sizes) will log *R* passes through the file. While *R* should much less than the total number of records (because the initial runs each contain many records), we would like to reduce still the number of passes required to merge the runs. Note that two-way merging does not make good use of available memory. Because merging is a sequential process over two runs, only one block of records per run need be in memory at a time. Keeping more than one block of a run in memory at any time will not reduce the disk I/O required by the merge (if several blocks are read from a file once, at least they take advantage of sequential access). Thus, most of the space used by the heap for replacement selection (typically many blocks in length) is wasted.

We can use the memory to merge many runs at once. If we have $M$ blocks of memory, we can merge $M-1$ runs at a time. This reduces the number of passes needed. The number of passes required to merge $R$ runs is $\log_{M-1} R$. This is much smaller than $\log_2 R$.

The main cost of the sorting algorithm is the disk I/O. In each pass, we read and write the entire size of the file. If there are $k$ passes, the total I/O is $2k \times (\text{size of file})$. Since $k$ is small for multway merging, this is very efficient.
