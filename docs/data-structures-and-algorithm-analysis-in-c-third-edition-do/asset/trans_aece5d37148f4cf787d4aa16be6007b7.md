class hashdict : public Dictionary<Key,E> {

    int count; // HT 中当前的元素数量
    Key EMPTYKEY; // 用户提供的空槽键值

int p(Key K, int i) const // 使用线性探测进行探测
    { return i; }

h(char* x) const { // 字符键的哈希函数
    int i, sum;
    for (sum=0; x[i] != '\0'; i++) sum += (int) x[i];
    return sum % M;
}

## Sec 9.4 哈希

对记录的失败搜索（回想一下，在插入期间对记录的成功搜索应该产生错误，因为表中不允许存储两个相同键的记录）。

当哈希表为空时，插入的第一条记录总是能找到其主位置是空闲的。因此，它只需要一次记录访问就能找到一个空槽。如果所有记录都存储在它们的主位置，成功搜索也只需要一次记录访问。随着表格开始填充，将记录插入到其主位置的概率就会降低。如果记录哈希到了另一个槽位，则必须通过冲突解决找到另一个槽位进行插入。查找未存储在主位置的记录也需要额外的记录，因为记录是沿着其探测序列进行搜索的。随着推移，越来越多的记录可能位于距离其主位置远的地方。

通过这些讨论，我们看到哈希的期望成本是关于表格满程度的函数。将表的负载因子（load factor）定义为 $\alpha = N/M$，其中 $N$ 是当前表中存储的记录数。

在假设探测序列遵循哈希表中槽位的随机排列的情况下，插入（或失败搜索）的期望成本估计值可以推导为 $\alpha$ 的函数。假设表中的每个槽位都有等概率成为下一条记录的主槽位，那么发现主位置被占用的概率为 $\alpha$。发现主位置和下一个槽位都被占用的概率为：

如果 $N$ 和 $M$ 很大，则这近似于 $(N/M)^i$。期望探测次数是对 $i \ge 1$ 的 $i$ 次冲突概率的求和，即：

```
$$\sum_{i=1}^{\infty}(N/M)^i=1/(1-\alpha).
```

成功搜索（或删除）的成本与最初插入该记录的成本相同。然而，插入成本的期望值并不取决于删除时的 $\alpha$ 值，而是取决于原始插入时的 $\alpha$ 值。我们可以通过从 0 积分到当前的 $\alpha$ 值得到此成本的估计（本质上是所有插入成本的平均值），结果为：

```
$$\int_{0}^{\alpha} \frac{1}{1-x}dx=-\log_{e}\frac{1}{1-\alpha}.$.
```

重要的是意识到，这些代表了在使用探测序列基于哈希表槽位随机排列这一不现实假设时的操作成本（从而避免了聚类带来的昂贵结果）。因此，这些是平均情况下的下界估计。线性探测下的真实平均值对于插入或失败搜索为 $\frac{1}{2}(1+1/(1-\alpha)^2)$，对于删除或成功搜索为 $\frac{1}{2}(1+1/(1-\alpha))$。

这些结果的证明可以在第 9.5 节引用的参考文献中找到。

从图 9.10 中我们可以看到，当表不满时，哈希的成本通常接近一次记录访问。这是极其高效的，优于需要 $\log n$ 次记录访问的二分查找。随着 $\alpha$ 的增加，期望成本随之增加。对于较小的 $\alpha$ 值，期望成本较低。当表几乎为空时，向表中添加新记录不会增加多少成本。然而，这种方法不适用于本节介绍的其他冲突解决策略，因为通过交换某对记录来改进其中一条记录的访问可能会导致另一条记录脱离其探测序列。
