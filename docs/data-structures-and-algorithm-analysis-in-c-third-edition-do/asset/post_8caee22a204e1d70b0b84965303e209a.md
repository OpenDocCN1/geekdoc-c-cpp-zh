```cpp
// Node implementation with the composite design pattern
class VarBinNode { // Node abstract base class
public:
    virtual VarBinNode() // Generic destructor
    virtual bool isLeaf() = 0;
    virtual void traverse() = 0;
};
```

```cpp
class LeafNode : public VarBinNode {
private:
    Operand var; // Operand value
public:
    LeafNode(const Operand& val) { var = val; } // Constructor
    bool isLeaf() { return true; } // isLeaf for LeafNode
    Operand value() { return var; } // Return node value
    void traverse() { cout << "Leaf: " << value() << endl; }
}
```

```cpp
class IntlNode : public VarBinNode // Internal node
private:
    VarBinNode* lc; // Left child
    VarBinNode* rc; // Right child
    Operator opx; // Operator value
public:
    IntlNode(const Operator& op, VarBinNode* l, VarBinNode* r)
        { opx = op; lc = l; rc = r; } // Constructor
    bool isLeaf() { return false; } // isLeaf for IntlNode
    VarBinNode* left() { return lc; } // Left child
    VarBinNode* right() { return rc; } // Right child
    Operator value() { return opx; } // Value

    void traverse() { // Traversal behavior for internal nodes
        cout << "Internal: " << value() << endl;
        if (left() != NULL) left()->traverse();
        if (right() != NULL) right()->traverse();
    }
};
```

```cpp
// Do a preorder traversal
void traverse(VarBinNode *root) {
    if (root != NULL) root->traverse();
}
```

Figure 5.11 A second implementation for separate internal and leaf node representations using C++ inheritance and virtual functions using the composite design pattern. Here, the functionality of traverse is embedded into the node subclasses hidden from users of that tree class. On the other hand, if the nodes are objects that have meaning to users of the tree separate from their existence as nodes in the tree, then the version of Figure 5.11 might be preferred because hiding the internal behavior of the nodes becomes more important.

Another advantage of the composite design is that implementing each node's functionality might be easier. This is because you can focus solely on the information passing and other behavior needed by this node type to do its job. This breaks down the complexity that many programmers feel overwhelmed by when dealing complex information flows related to recursive processing.

## 5.3.2 Space Requirements

This section presents techniques for calculating the amount of overhead required by a binary tree implementation. Recall that overhead is the amount of space necessary to maintain the data structure. In other words, it is any space not used to store data records. The amount of overhead depends on several factors including which NULL nodes store data values (all nodes, or the leaves), whether the leaves store child pointers, and whether the tree is a full binary tree.

In a simple pointer-based implementation for the binary tree such as that of Figure 5.7, every node has pointers to its children (even when the children are NULL). This implementation requires total space up to $n(2P+D)$ for a tree of $n$ nodes. Here, $P$ stands for the amount of space required by a pointer, and $D$ stands for the amount of space required by a data value. The total overhead space will be $2P$ for the entire tree. The overhead fraction will be $2P/(2P+D)$. The actual value for this expression depends on $P=D$, then a full binary tree has two thirds of its space taken up in overhead. Worse yet, Theorem 5.2 tells us that half of the pointers are "wasted" NULL values that serve only to indicate structure, but do not provide access to new data.

A common implementation is not to store any actual data in a node, but rather a pointer to the data record. In this case, each node will typically store three pointers, all of which are overhead, resulting in an overhead fraction of $3P/(3P+D)$.

If only leaves store data values, the fraction of total space devoted to overhead is full. If the tree is not full, conceivably there might be only one leaf node at the end of a series of internal nodes. Thus, the overhead can be an arbitrarily high percentage for non-full binary trees. The overhead fraction drops as the tree gets closer to full, being lowest when the tree is truly full. In this case, about half of the nodes are internal.

Great savings can be made by eliminating the pointers from leaf nodes in full binary trees. Again assume the tree stores a pointer to the data field. Because about half of the nodes are leaves and half internal nodes now have children pointers, the overhead fraction in this case will be approximately

$\frac{\frac{1}{2}(2P)}{\frac{1}{2}(2P) + D} = \frac{P}{P + D}$

If $P = D$, the overhead drops to about one half of the total space. However, if only leaf nodes store useful information, the overhead fraction for this implementation is actually three quarters of the total space, because half of the "data" is unused.

If a binary tree needs to store data only two pointers and no data field the leaf nodes store only a pointer to the data field. This implementation requires $\frac{3}{2}P+(p+d)$ units of space. If $P = D$, the overhead is $3P/(3P+D) = 3/4$.

It might seem counter-intuitive that the overhead ratio has gone up while the total amount of space has gone down. The reason is because have changed our definition of "data" to only refer to what is stored in the leaf nodes, while the overhead fraction is higher, it is from a total storage requirement that is lower.

There is one serious flaw with this analysis. When using internal and leaf nodes, there must be a way to distinguish the node types. When separate node types are implemented via C++ subclasses, the runtime environment stores information with each object to determine, for example, the correct subclass to use when the `isLeaf` virtual function is called. Thus, each node requires an identifier. Only one bit is truly necessary to distinguish the two possibilities. In cases where space is a critical resource, implementors often find a spare bit within the node to store the node type indicator. An alternative is to use a spare bit within a pointer to indicate node type. This is often possible when the compiler requires that structures and objects start on word boundaries, leaving the last bit of a pointer value always zero. Thus, this bit can be used to store the node-type flag and de-referenced.

## 5.3.3 Array Implementation for Complete Trees

The previous section pointed out that a large fraction of space in a typical tree is devoted to overhead, not to data. This section presents a simple implementation for complete trees. Recall that a binary tree is complete if all levels are completely filled except possibly the last, which is filled from left to right. For such trees, we can use an array to store the nodes, as shown in Figure 5.12(a). Figure 5.12(b) lists the indices for the children, parent, and siblings of each node.

We begin by assigning numbers to the nodes in the complete tree, level by level, from left to right as shown in 5.12(a). From 5.12(b), you see a pattern regarding the array positions of a node's relatives. Simple formulas can be derived for calculating the array index of each relative $r$ as follows. The total number of nodes in the tree is $n$. The index of the node in question is $r$, which may fall in the range 0 to $n-1$.

- Parent($r$) = $(r-1)/2$ if $r \neq 0$.
- Left child($r$) = $2r+1$ if $2r+1 < n$.
- Right child($r$) = $2r+2$ if $2r+2 < n$.
- Left sibling($r$) = $r-1$ if $r$ is even.
- Right sibling($r$) = $r+1$ if $r$ is odd and $r+1 < n$.

You might think that a complete tree is such an unusual occurrence that there is no reason to develop a special implementation for it. However, the complete binary tree is the most important being used to implement priority queues (Section 5.5) and for external sorting algorithms (Section 8.5).

Section 4.4 presented the dictionary ADT, along with dictionary implementations based on sorted and unordered lists.
