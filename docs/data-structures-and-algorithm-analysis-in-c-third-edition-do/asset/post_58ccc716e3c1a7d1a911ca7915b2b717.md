
## Sec. 14.3 Amortized Analysis

(charging costs to bits going from right to left)

```
$\sum_{i=0}^{n-1} 2^i < 2^n$.
```

In other words, the average number of bits flipped on each increment is 2, leading to a total cost of only $2 \cdot 2^n$ increments.

A useful concept for amortized analysis is illustrated by a simple variation on the stack data structure, where the `pop` function is slightly modified to take a second parameter $k$ indicating that $k$ operations are to be performed. This revised pop function, called `multipop`, might look as follows:

```
// pop elements from stack
void multipop(int k);
```

The "local" worst-case analysis for multipop is $\Theta(n)$ for $n$ elements in the stack. Thus, if there are $m_1$ calls to pop and $m_2$ calls to multipop, then naive worst-case cost for the series of operations is $m_1 + m_2 \cdot n$. This analysis is unrealistically pessimistic. Clearly it is not possible to pop $m_1$ elements each called **multipop**. Analysis that focuses on single operations cannot deal with this global limit, and so we turn to amortized analysis to model the series of operations.

The key to an amortized analysis of this problem lies in the concept of **potential**. At any time, a certain number of items may be on the stack. The cost for **multipop** can be no more than this number of items. Each call to `push` places another item on the stack, which can be removed by a single **multipop** operation. Thus, each call to `push` raises the potential of the stack by one item. The sum of costs for all calls to **multipop** can never be more than the total potential of the stack (aside each call with **multipop** itself).

The amortized cost for any series of **push** and **multipop** operations is the sum of three costs. First, each **multipop** operation takes constant time in overhead, regardless of the number of items popped on that call. Finally, we count the potentials expended by all **multipop** operations, which is at most $m_1$, the number of **push** operations. This total cost can be expressed as

```
$m_1 + (m_2 + m_1) = \Theta(m_1 + m_2)$.
```

A similar argument was used in our analysis for the partition function in the Quicksort algorithm (Section 7.5). While on any given pass through the loop the left or right pointers might move all the way through the remainder of the partition, doing so would reduce the number of times that the while loop can be further executed.

Our final example uses amortized analysis to prove a relationship between cost of the move-to-front self-organizing list heuristic from Section 9.2 and the cost for the optimal ordering of the list.

Recall that, for a series of searches, the minimum cost for a static list results when the list is sorted by frequency of access to its records. This is the optimal ordering for the records if we never allow the positions of records to change, because the most-frequently accessed record is first (and thus has least cost), because the next most frequently accessed record, and so on.

Theorem 14.2 The total number of comparisons required by any series S of $n$ or more searches on a self-organizing list of length $n$ using the move-to-front heuristic is never more than twice the total number of comparisons required when series S is applied to the list stored in its optimal static ordering.

Proof: Each search with a record in the list is either successful or unsuccessful. For $m$ searches, there must be $m$ successful comparisons for the self-organizing list and the static list. The total of unsuccessful comparisons in the self-organizing list is the sum, over all pairs of distinct keys, the number of unsuccessful comparisons made between that pair.

Consider a pair of keys A and B. For any sequence of searches, $S$, the total of (unsuccessful) comparisons between A and B is identical to the number of comparisons between A and B required for the subsequence of $S$ made up only of searches for A or B. Call this subsequence $S_{AB}$. In other words, including searches for other keys does not affect the relative position of A and B and so not affect the relative contribution to the total cost of the unsuccessful comparisons between A and B.

The number of unsuccessful comparisons between A and B made by the move-to-front on subsequence $S_{AB}$ is at most twice the number of unsuccessful comparisons between A and B required when $S_{AB}$ is applied to the optimal ordering for the list. To show this, assume that $S_{AB}$ contains under the optimal ordering, unsuccessful comparisons are required because B must appear before A in the list (because its access frequency is higher). Move-front will yield an unsuccessful comparison whenever the request sequence changes A to B or from B to A. The total number of changes possible is $2^i$ because each change involves an A and each A can be part of at most two changes.

Because the total number of unsuccessful comparisons required by move-to-front for any pair of keys is at most twice that required by the optimal static ordering, the total number of unsuccessful comparisons required by move-to-front for all pairs of keys is also at most twice as high. Because the number of successful comparisons is the same for both methods, the total number of comparisons required by move-to-front is less than twice the number of comparisons required by the optimal static ordering.
