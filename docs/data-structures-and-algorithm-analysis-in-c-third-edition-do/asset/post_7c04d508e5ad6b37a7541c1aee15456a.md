## 15.1 Lower Bounds

How do I know if I have a good algorithm to solve a problem? If my algorithm runs in $\Theta(n \log n)$ time, is that good? It would be if I were searching the array for the largest element. The value of an algorithm must be determined in relation to the inherent complexity of the problem. In Section 3.6 we defined the upper bound for a problem to be the upper bound of the best algorithm we know for that problem, and lower bound to be the tightest lower bound that we can prove over all algorithms. While we usually recognize the upper bound for a given algorithm, finding the tightest lower bound for all possible algorithms is often difficult, especially if lower bound is more than the "trivial" lower bound by measuring the amount of input that must be processed. We must be careful about how we interpret this statement, however. The world is certainly better off for the invention of Quicksort; Quicksort is not asymptotically faster than Mergesort, yet Mergesort was available at the time. Quicksort is not merely a "tuning" of Mergesort; it is a substantially different approach to sorting. So when even our upper and lower bounds for a problem meet, there are benefits to be gained from a new, clever algorithm.

So now we have an answer to the question "How do I know if I have a good algorithm to solve a problem?" An algorithm is good (asymptotically speaking) if its upper bound matches the problem's lower bound. If they match, we know to stop trying to find an (asymptotically) faster algorithm. What if the (known) upper bound for our algorithm does not match the (known) lower bound for the problem? In this case, we might not know what to do. Our upper bound flawed, and the algorithm is really faster than we can prove? Is our lower bound for greater? Or is our algorithm simply not the best? Our focus in this chapter is discovering and proving lower bounds from first principles.

### 15.1 Introduction to Lower Proofs

The lower bound for the problem is the tightest (highest) lower bound that we can prove for all possible algorithms that solve the problem.¹ This can be a difficult bar, given that we cannot possibly know all algorithms for any problem, because there are theoretically infinite. However, we can recognize a simple lower bound based on the amount of input that must be examined. For example, we can argue that the lower bound for any algorithm to find the maximum-valued element in an unsorted list must be $\Omega(n)$ because any algorithm must examine all the inputs to be sure it actually finds the maximum value.

In the case of maximum finding, the fact that we know of a simple algorithm that runs in $\Omega(n)$ time, combined with the fact that any algorithm needs $\Omega(n)$ time, is significant. Because both upper and lower bounds meet (with a constant factor), we know that we have a "good" algorithm for solving the problem. It is possible that someone can develop an implementation that is a "little" faster than an existing one, or by a constant factor. But we know that it is not possible to develop one that is asymptotically better.

> ¹Throughout this discussion, it should be understood that any mention of bounds must specify what class of inputs are being considered. Do we mean the bound for the worst case input? The average cost over all inputs? Regardless of which class of inputs we consider, all of the issues raised apply equally.
