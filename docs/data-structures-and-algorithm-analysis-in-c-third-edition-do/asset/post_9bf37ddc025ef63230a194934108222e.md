While such a decomposition rule will not necessarily result in a balanced tree (the tree will be unbalanced if the records are not well distributed within the key range), at least the depth of the tree will not depend on the order of key insertion. Furthermore, the depth of the tree will be limited by the resolution of the key range; the depth of the tree can never be greater than the number of bits required to store a key value. For example, if the keys are integers in the range 0 to 1023, the resolution for the key is ten bits. Thus, two keys can be identical only in the tenth bit. In the worst case, two keys will follow the same path in the tree only until the tenth branch. As a result, the BST containing n records could be as much as n levels deep.

Splitting based on predetermined subdivisions of the key range is called **key space decomposition**. In computer graphics, the technique is known as **image decomposition**, and this term is used to describe the process for data structures. A data structure for space decomposition is called a trie. Folklore has that "tree" tries from "retrieval." Unfortunately, that would imply the word is pronounced "tree," which would lead to confusion with regular use of the word. "Trie" is actually pronounced "try."

Like the B+, a trie stores data only in the leaves. Internal nodes serve as placeholders to direct the search process, but since the split points are determined, internal nodes need not "traffic-directing" key values. Figure 13.1 illustrates the concept. Upper and lower bounds must be imposed on the key values so that we can compute the middle of the key range. The largest value inserted in this example is 120, the range from 0 to 127 is assumed, as 128 is the smallest power of two greater than 120. The binary value of the key determines whether to select the left or right branch at any point during the search. The most significant bit determines direction at the root. Figure 13.1 shows a **binary trie**, so called because in this example the tree structure is based on the value of the key as a binary number, which results in a binary trie.

The Huffman coding tree of Section 5.6 is another example of a binary trie. All data values in the Huffman tree are at the leaves, and each branch splits the range of possible letter codes in half. The Huffman codes are actually reconstructed from the positions within the trie.

These are examples of binary tries, but tries can be built with any branching factor. Normally the branching factor is determined by the alphabet used. For binary numbers, the alphabet is {0, 1} and a binary trie results. Other alphabets lead to other branching factors.

One application for tries is to store a dictionary of words. Such a trie will be referred to as an **alphabet trie**. For simplicity, our examples will ignore case in letters. We add a special character ($) to the 26 standard English letters. The $ character is used to represent the end of a string. Thus, the branching factor for each node is (up to) 27.

The binary form of the key value determines the path to the record, assuming that each key is represented as a 7-bit value representing a number in the range 0 to 127.

Once constructed, the alphabet trie is used to determine if a word is in the dictionary. Consider searching for a word in the alphabet trie of Figure 13.2. The first letter of the search word determines which branch from the root, the second letters determine which branch take at the next level, and so on. Only the letters that lead to a word are shown as branches.

In 13.2(b), the leaf nodes of the trie store a copy of the actual words, while in 13.2(a), the word is built up from the letters associated with each branch.

One way to implement an alphabet trie is an array of 27 pointers indexed by letter. Because most nodes branch to only a small fraction of the possible letters in the alphabet, an alternate implementation is to use a linked list of pointers to the child nodes, as in Figure 6.9.

The depth of a leaf node in the alphabet trie of Figure 13.2(b) has little to do with the number of nodes in the trie, or even with the length of the corresponding string. A trie's depth depends on the number of characters required to distinguish this word from any other. For example, if the words "ant" and "ante" are both stored in the trie, it is not until the fifth letter that the words can be distinguished. The limiting factor on the depth of the trie is the length of the words. In general, the trie must be at least as deep as the longest word.

Poor balance in the alphabet trie can result when certain prefixes are heavily used. Any multway trie can be replaced with a binary trie by converting the alphabet to a binary representation.

The trie implementations illustrated by Figures 13.1 and 13.2 are potentially inefficient as certain set keys might lead to a large number of nodes with only a child. A variant on trie implementation is PATRICIA, which stands for “Practical Algorithm To Retrieve Information Alphan.” In the case of a binary alphabet, a PATRICIA trie (referred hereafter as a PAT) is a full binary tree that stores records in the leaf nodes. Internal nodes store only the position within the key’s bit pattern that is used to decide on the next branching point. In this way, internal nodes with single children (equivalently, positions within the key do not distinguish any of the keys in the current subtree) are eliminated.

**Example 13.1** When searching for the value 7 (0000011 in binary) in the PAT trie of Figure 13.3, the root node indicates bit position 0 (the leftmost bit) is checked. The 0th bit for value 7 is 0, take the left branch. At level 1, branch depending on the value of 1, which again is 0. At level 2, branch depending on the value of 2, which again is 0. At level 3, the index stored in the node is 4. This means that bit 4 of the key is checked next. (The value of bit 3 is irrelevant, because all values in that subtree have the same value at bit position 3.)
