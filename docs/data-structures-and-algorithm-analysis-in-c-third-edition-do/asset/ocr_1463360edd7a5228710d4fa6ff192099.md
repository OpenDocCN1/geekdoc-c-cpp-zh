Conceptually, multiway merge assumes that each run is stored in a separate file. However, this is not necessary in practice. We only need to know the position of each run within a single file, and useseekky to move to the appropriate block whenever we need new data from a particular run. Naturally, this approach destroys the ability to do sequential processing on the input file. However, if all runs were stored on a single disk drive, the I/O would be alternating anyway between runs. Thus, multiway merging replaces several (potentially) sequential passes with a single random access. If the processing would not be sequential anyway (as when all processing is on a single disk), no time is lost by doing so.

Multway merge can greatly reduce the number of passes required. If there is room to store one block for each run, then all runs can be merged in a single pass. Thus, replacement selection can build initial runs in one pass, and multiway merge can merge all runs in one pass, yielding a total cost of two passes. For truly large files, there might not be many runs in memory to allocate B blocks for a B-way merge, and the number of runs R is greater than B, then it will be necessary to do multiple merge passes. In other words, the first B runs are merged, then the next B, and so on. These super-runs are then merged by subsequent passes, B super-runs at a time.
