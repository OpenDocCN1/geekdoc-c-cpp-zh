**The growth rate** for an algorithm is the rate at which the algorithm grows as the size of its input grows. Figure 3.1 shows a graph for six equations, each meant to describe the running time for a particular program or algorithm. A variety of growth rates representative of typical algorithms are shown. The two equations labeled 10n and 20n are graphed by straight lines. A growth rate of $cn$ (for $c$ any positive constant) is often referred to as a **linear** growth or running time. This means that for $n$, the running time of the algorithm grows in the same proportion. Doubling the value of $n$ roughly doubles the running time. An algorithm whose equation has a higher-order term containing a factor of $n^2$ is to have a **quadratic** growth. In Figure 3.1, the line labeled $2n$ represents a quadratic growth rate. The line labeled $2^n$ represents an **exponential** growth rate. The line labeled $n$ is also growing exponentially.

As you can see from Figure 3.1, the difference between an algorithm whose running time has $T(n) = 10n$ and another with $T(n) = 2n^2$ becomes tremendous as $n$ grows. For $n > 5$, the algorithm with running time $T(n) = 2n^2$ is already much slower. This is because the fact that 10 has a greater constant factor for one of the equations only shifts the point at which the two curves cross. For $n > 10$, the algorithm with $T(n) = 20n$ is slower than the algorithm with $T(n) = 5n$. $n^2$ grows somewhat quickly than both $T(n) = 10n$ and $T(n) = 20n$, but not nearly quickly as the equation $T(n) = 2n^2$. For constants, $a, b > 1$, $n^a$ grows faster than either $n^b$ or $n^c$. Finally, algorithms with cost $T(n) = cn^2$ or $T(n) = n^n$ are prohibitively expensive for even modest values of $n$. Note that for constants $a, b \geq 1$, $a^n$ grows faster than $b^n$.

## 3.2 Best, Worst, and Average Cases

Consider the problem of finding the factorial of $n$. For this problem, there is only one input of a given "size" (that is, there is only a single instance for each size of $n$). Now consider our largest-value sequential search algorithm of Example 3.1, which always examines every array value. This algorithm works on many inputs of a given size $n$. That is, there are many possible arrays of given size. However, no matter what array of size $n$ the algorithm looks at, its cost will be the same in that it always looks at every element in the array time.

For some algorithms, different inputs of a given size require different amounts of time. For example, consider the problem of searching an array $n$ integers to find a particular value $K$ (assume that $K$ appears exactly in the array). The **sequential search algorithm** begins at the first position in the array and looks at each value until $K$ is found, the algorithm stops. This is different from the largest-value sequential search of Example 3.1, which always examines every array value.

There is a wide range of possible running times for the sequential search algorithm. The first integer in the array could contain value $K$, and so only one integer is examined. In this case the running time is short. This is the **best case** for this algorithm, because it is not possible for sequential search to look to less than one value. Alternatively, if the last position in the array contains $K$, then the running time is relatively long, because the algorithm must examine $n$ values. This is the **worst case** for this algorithm, because sequential search never looks more than $n$ values. If we implement sequential search as a program and run it times on different arrays of size $n$, or search for many values of $K$ within the same array, we expect the algorithm on average to go halfway through the array before finding the value we seek. We call this **average case** for this algorithm.

When analyzing an algorithm, should we study the best, worst, or average case? Normally we are not interested in the best case, because this might happen rarely and is generally too optimistic for a fair characterization of the algorithm's running time. In other words, analysis based on the best case is not likely to be representative of the behavior of the algorithm. However, there are rare instances where a best-case analysis is useful — in particular, when the best case has high probability of occurring. In Chapter 7 you will see some examples where taking advantage of the best-case running time for one sorting algorithm makes a second more efficient.

How about the worst case? The advantage to analyzing the worst case is that you know for certain that the algorithm must perform at least that well. This is especially important for real-time applications, such as for the computers that monitor an air traffic control system. Here, it would not be acceptable to use an algorithm can handle $n$ airplanes quickly enough most of the time, but which fails to perform quickly enough when all $n$ airplanes are coming from the same direction.

For other applications — particularly when we wish to aggregate the worst-case analysis might not be representative of the behavior of the algorithm. Often we prefer to know the average case. Unfortunately, average-case analysis is not always possible. Average-case analysis first requires that we understand how the actual inputs to the program (and their costs) are distributed. See Section 9.2 for further discussion the effects of data distribution on the sequential search. The characteristics of a data distribution have a significant effect on many searches, as those based on hashing (Section 9.4) and search trees (e.g., 5.4). Incorrect assumptions about data distribution can have disastrous consequences on a program's space or time performance. Unusual data distributions can also be used to advantage, as shown in 9.2.

In summary, for real-time applications we are likely to prefer a worst-case analysis. Otherwise, we desire an average-case analysis if we know enough about the distribution of our input to compute the average case. If not, then we must resort to worst-case analysis.

## 3.3 A Faster Computer, or a Faster Algorithm?

Imagine you have a problem to solve, and you know of an algorithm whose running time is proportional to $n^2$. Unfortunately, the program takes so long to run. If you replace your computer with a new one that is ten times faster, does the $n^2$ algorithm become acceptable? If the problem size remains the same, then the faster computer will allow you to get your work done quickly enough with an algorithm having a high growth rate. A funny thing happens to people who get a faster computer. They don't run the same problem. They run a bigger problem! Say that on your old computer you were to sort 10,000 records because that could be done by the computer during your lunch break. On your new computer you might hope to sort 100,000 records in the same time. You won't be back from lunch sooner, so you are better off solving a larger problem.
