For large collections of records that are searched repeatedly, sequential search is unacceptable slow. One way to reduce time is to preprocess the records by sorting them. With a given array, an improvement over linear search is to test if the current element in $L$ is greater than $K$. If it is, then we know that $K$ cannot appear later in the array, and we can quickly search the rest. But this still does not improve the worst-case cost of the algorithm.

We can also observe if we look at position 1 in sorted array $L$ and $K$ is bigger, then it is better, if we look out position 2 in $L$ and find that $K$ is bigger yet? This rules out 0, 1, and 2 with one comparison. What if we carry this to the extreme and look at the last position in $L$ and find that $K$ is not in the list? This is very useful to know, but what is wrong with the conclusion that we should always start looking at the last position? The problem is that, while we learn a lot sometimes (in one comparison we might learn that $K$ is not in the list), usually we learn only a little bit (that the last element is not $K$).

The question then becomes: What is the right amount to jump? This leads us to an algorithm known as **Jump Search**.
