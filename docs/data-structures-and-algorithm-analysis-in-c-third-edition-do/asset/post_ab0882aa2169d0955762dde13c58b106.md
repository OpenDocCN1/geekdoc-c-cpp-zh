Before discussing external sorting techniques, consider the basic model for accessing information from disk. The file to be sorted by the program as a sequential series of fixed-size blocks. Assume (for simplicity) that each block contains the same number of fixed-size data records. Depending on the application, a record may be composed of a few bytes — or hundreds of bytes with a relatively small key field. Records are assumed not to cross block boundaries. These assumptions can be relaxed for special-purpose sorting applications, but ignoring such complications makes the principles clearer.

As explained in Section 8.2, the sector is the basic unit of I/O. In other words, all disk reads and writes are for one or more complete sectors. Sector sizes are typically a power of two, in the range 512 to 16KB, depending on the operating system and the size of the disk drive. The block size used for external sorting algorithms should be equal to a multiple of the sector size.

Under this model, a sorting algorithm reads a block of data into a buffer in memory, processes it, and at some future writes it back to disk. From Section 8.1 we see that reading or writing a block from disk takes the order of one million times longer than a memory access. Based on this fact, we can reasonably expect that the records contained in a single block can be sorted by an internal sorting algorithm such as Quicksort before it is required to read or write the block.

Under good conditions, reading a file in sequential order is more efficient than reading blocks in random order. Given this obvious sequential processing is faster. However, it is important to understand under what circumstances sequential processing is actually faster than random access, it affects our approach to designing an external sorting algorithm.

Efficient sequential access relies on seek time being kept to a minimum. The first requirement is that the blocks making up a file are fact stored on disk in sequential order and close together, preferably laying a small number of contiguous tracks. At the very, the number of extents making up the file should be small. Users typically do not have control over the layout of their file on disk, writing a file all at once in sequential order to a disk drive with a high percentage of free space increases the likelihood of such an arrangement.

The second requirement is that the disk drive's I/O head remains positioned over the file throughout sequential processing. This will not happen if there is competition of any kind for the I/O head. For example, on a multi-user time-shared computer the sorting process may compete for the I/O head with the processes of users. Even when the sorting process has sole control of the I/O head, it is still likely that sequential processing will not be efficient. Imagine the situation where all processing is done on a single disk drive, with the typical arrangement of a single bank of read/write heads that move over a stack of platters. If the sorting process involves reading from an input file, alternated with writing to an output file, the I/O head will continuously seek between the input file and the output file. Similarly, if two input files are being processed simultaneously (such during a merge process), the I/O head will continuously seek between these two files.

The moral is, with a single disk drive, there is no so much as efficient sequential processing of a data file. Thus, a sorting algorithm might be more efficient if it performs a smaller number of non-sequential disk operations than require a large number of seeks in practice.

As mentioned previously, the record size might be quite large compared to the size of the key. For example, payroll entries for a large business might store hundreds of bytes of information including the name, ID, and job title for each employee. The sort key might be the ID number, requiring only a few bytes. The simplest sorting algorithm might be such records as a whole, reading the entire record whenever it is processed. However, this will greatly increase the amount of I/O requested, because only a few records will fit into a single disk block. Another alternative is to use a key sort. Under this method, the keys are all read and stored together in an index file, where each key is stored along with a pointer indicating the position of the corresponding record in the original data file. The key and pointer combination will be substantially smaller than the size of the original record; thus, the index file will be much smaller than the complete data file. The index file then be sorted, requiring much less I/O because the index records are smaller than the complete records.

Once the index file is sorted, it is possible to reorder the records in the original database file. This is typically not done for reasons. First, reading the records in sorted order from the record file requires a random access for each record. This can take a substantial amount of time and is of only value if the complete collection of records needs to be viewed or processed in sorted order (as opposed to a search for selected records). Second, database systems typically allow searches to on multiple keys. For example, today's processing might be done in order of ID numbers. Tomorrow, the business might want information sorted by salary. Thus, there might be no single “sorted” order for the full record. Instead, multiple index files are often maintained, for each sort key. These ideas are explored further in Chapter 10.

### 8.5.1 Simple Approaches to External Sorting

If your operating system supports virtual memory, the simplest “external” sort is to read the entire file into virtual memory and run an internal sorting method such as Quicksort. This approach allows the virtual memory manager to use its normal buffer pool mechanism to control disk accesses. Unfortunately, this might not always be a viable option. One potential drawback is that the size of virtual memory is usually limited to something smaller than the disk space available. Thus, your input file may not fit into virtual memory. Limited virtual memory can be overcome by adapting an internal sorting method to make use of your own buffer pool.

A more general problem with adapting an internal sorting algorithm to external sorting is that it is not likely to be as efficient as designing a new algorithm with the specific goal of minimizing disk I/O. Consider the simple adaptation of Quicksort to use the entire array of records, with the first partition moving inwards from the two ends. This can be implemented efficiently using a buffer pool. However, the next step is to process each of the sub-arrays, followed by processing of sub-sub-arrays, and so on. As the subarrays get smaller, processing quickly random access to the disk drive. Even with maximum use of the buffer pool, Quicksort must still read and write each record log n times on average. We can do better. Finally, even if the virtual memory manager can give good performance using a standard Quicksort, this will mean that the lot of the system cannot use this space for other work. Better methods can save time while using less memory.

Our approach to external sorting is the Mergesort algorithm. The simplest form of external Mergesort performs a series of passes over the records, merging larger and larger subsets on each pass. The first pass merges subsets of size 1 into subsets of size 2; the second pass merges subsets of size 2 into subsets of size 4; and so on. A sorted list is called a run. Thus, each pass is merging pairs of runs to form longer runs. Each pass copies the contents of one file to another. Here is a sketch of the algorithm, as illustrated by Figure 8.6.

1. Split the input into two equal-sized run files.
2. Read one block from each run into input buffers.
3. Take the first record from each input buffer, and write a run of length two to an output buffer in sorted order.
4. Take the next record from each input buffer, and write a run of length two to a second output buffer in sorted order.
5. Repeat until finished, alternating output between the two output runs. Whenever the end of an input buffer is reached, read the next block from the appropriate input file. When an output buffer is full, write it to the appropriate output file.
