Quicksort's best case occurs when findpivot always breaks the array into two halves. Quicksort repeatedly splits the array into smaller partitions, as shown in Figure 7.14. In the best case, the result will be log $n$ levels of partitions, the top level having one array of size $n$, the second two arrays of size $n/2$, the with four arrays of size $n/4$, and so on. Thus, each level, partition steps do do a total of $n$ of work, with an overall cost of $n \log n$ when Quicksort finds perfect pivots.

Quicksort's average-case behavior falls somewhere between the extremes of worst and best case. Average-case analysis considers the cost for all possible ranges of input, summing the costs and dividing by the number of cases. We make one reasonable simplifying assumption: At each step, the pivot is equally likely to end in any position in the (sorted) array. In other words, the pivot is equally likely to break an array into partitions of sizes 0 and $n-1$, or $n-2$, and so on.

Given this assumption, the average-case cost is computed from the following equation:

```
$T(n) = cn + \frac{1}{n} \sum_{k=0}^{n-1} [T(k) + T(n-1-k)], \quad T(0) = e.$
```

This equation is in the form of a recurrence relation. Recurrence relations are discussed in Chapters 2 and 14, and this one is solved in Section 14.2.4. This says that there is one chance in $n$ that the pivot breaks the array into subarrays of size 0 and $n-1$, and so on. The expression "$T(k)+T(n-1-k)$" is the cost for the two recursive calls to Quicksort on two arrays of size $k$ and $n-1-k$. The initial $cn$ is the cost of doing the findpivot and partition steps, some constant $c$. The closed-form solution to this recurrence relation is $\theta(n \log n)$. Thus, Quicksort has average-case cost $\theta(n \log n)$.

This is an unusual situation that the average cost and the worst case have asymptotically growth rates. Consider what "average case" actually means. We consider an average cost for inputs of size $n$ by summing up all possible input of size $n$ the product of the running cost of that input times the probability that input will occur. To simplify things, we assumed that every permutation is equally likely to occur. Thus, finding the average means summing the cost for every permutation and dividing by the number of inputs ($n!$). We know that some of these $n!$ inputs have cost $O(n^2)$. Given the extremely high cost of the worst inputs, there cannot be very few of them. Thus, as $n$ grows, the fraction of inputs with high cost must go towards a limit of zero. We can conclude that Quicksort will have good behavior if we can avoid these bad permutations. Running time for Quicksort can be improved (by a constant factor), and many have gone into optimizing this algorithm. The most obvious place for improvement is the findpivot function. Quicksort's worst case arises when the pivot does a poor job of splitting the array into equal subarrays. If we are willing to do more work searching for a better pivot, the effects of a bad pivot can be decreased or even eliminated. A common choice is to use the "median of three" which looks at the first, middle, and last positions of the current subarray. This is in sharp contrast to selecting the first or last element as the pivot, which would yield bad performance for many permutations that are nearly sorted or nearly reversed. Quicksort is relatively slow when $n$ is small. This might not seem to be relevant if most of the time we sort large arrays. Simple improvement might then be to replace Quicksort with a faster sort for small numbers, Insertion Sort or Selection Sort. However, there is an even better optimization. When Quicksort partitions are below a certain size, do nothing! The final step is a simple call to Insertion Sort to process the entire array, putting the elements into sorted order.

The amount of information that must be stored is small. We need not store copies of an subarray, only the subarray bounds. Furthermore, the stack depth can be kept small if care is taken on the order in which Quicksort's recursive calls are executed. We can also place the code for findpivot and partition inline to eliminate the remaining function calls. Note that by not processing stacks of size near or less as suggested above, about three quarters of the function calls will have been eliminated. Thus, eliminating the remaining function calls will yield a modest speedup.

# 7.6 Heapsort

Discussion of Quicksort began by considering the practicality of a binary search tree for sorting. The BST requires more space than the other sorting methods and will be slower than Quicksort or Mergesort due to the relative expense of inserting values into the tree. There is also the possibility that the BST be unbalanced, leading to a $\Theta(n^2)$ worst-case running time. Balance in the tree is closely related to Quicksort's partition step. Quicksort's pivot secures roughly the same as the pivot (root) value, while the left partition (subtree) stores values less than the pivot (root), while the right partition (subtree) stores values greater or equal to the pivot (root).

Heapsort is based on the heap structure presented in Section 5.5. Heapsort has all of the advantages. The complete binary tree is balanced, its array representation is space efficient, and we can load all values into the tree at once, taking advantage of the efficient buildheap function. The asymptotic performance of Heapsort is $\Theta(n \log n)$ in the best, average and worst cases. It is not as fast as Quicksort in the average case (by a constant factor), but Heapsort has special properties that make it particularly useful when sorting sets too large to fit in main memory, as discussed in Chapter 8.
