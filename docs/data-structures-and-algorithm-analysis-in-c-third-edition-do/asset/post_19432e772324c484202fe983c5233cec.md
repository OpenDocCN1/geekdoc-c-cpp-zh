For large collections of records that are searched repeatedly, sequential search is unacceptable slow. One way to reduce time is to preprocess the records by sorting them. With a given array, an improvement over linear search is to test if the current element in $L$ is greater than $K$. If it is, then we know that $K$ cannot appear later in the array, and we can quickly search the rest. But this still does not improve the worst-case cost of the algorithm.

We can also observe if we look at position 1 in sorted array $L$ and $K$ is bigger, then it is better, if we look out position 2 in $L$ and find that $K$ is bigger yet? This rules out 0, 1, and 2 with one comparison. What if we carry this to the extreme and look at the last position in $L$ and find that $K$ is not in the list? This is very useful to know, but what is wrong with the conclusion that we should always start looking at the last position? The problem is that, while we learn a lot sometimes (in one comparison we might learn that $K$ is not in the list), usually we learn only a little bit (that the last element is not $K$).

The question then becomes: What is the right amount to jump? This leads us to an algorithm known as **Jump Search**. For some value $j$, we check every $j^{th}$ element in **L**, that is, we check elements $L[j]$, $L[2j]$, and so on. So long as $K$ is greater than the values we are checking, we continue. But when we reach a value in **L** greater than $K$, we do a linear search on the piece of length $j - 1$ that we know brackets $K$ at it $i$ if it is in the list.

If we define $m$ such that $mj \leq n < (m+1)j$, then the total cost of this algorithm is at most $m+j-1$ worst-case comparisons. (They are 3-9 because each comparison of $K$ with some $L[i]$ we need to know if $K$ is less than, equal to, or greater than $L[i]$. Therefore, the cost to run the algorithm on $n$ items with a jump of size $j$ is

```
$T(n)
```

What is the best value we can pick for $j$? We want to minimize cost:

```
$$\min_{j\geq 1} f(j) = \left\lceil\frac{n}{j}\right\rceil+j-1.$$
```

Take the derivative and solve for $f'(j)=0$ to find the minimum, which is $j=\sqrt{n}$. In this case, the worst cost will be roughly $2\sqrt{n}$. This invokes a basic principle of algorithm design. We want to balance the work done selecting a sublist with the work done searching it. In general, it is a good strategy to make subproblems of equal effort. This is an example of a **divide and conquer algorithm**.

What if we extend this to three levels? We would first make jumps of size $j$ to find a sublist of size $j-1$ whose ends value bracket $K$. We would then work through this sublist by making jumps of smaller size, say $j_1$, finally, once we find a bracketed sublist of size $j_1-1$, we would do sequential search to complete the process.

This probably evolves into two levels of jumping to be followed by sequential search. While it makes sense to do a two-level algorithm (that is, jump to find a sublist and then sequential search on the sublist), it almost never makes sense to do a three-level algorithm. Instead, when we go beyond two levels, we nearly always generalize by using recursion. This leads us to the most commonly used search algorithm for sorted arrays, binary search described in Section 3.5.

If we know nothing about the distribution of keys, then binary search is the best available for searching a sorted array (Exercise 9.22). However, we know something about the expected key distribution. Consider the typical behavior of a person looking up a word in a large dictionary. Most people certainly not use sequential search! Typically, people use a modified form of binary search, until they get close to the word they are looking for. The search generally does not start at the middle of the dictionary. A person looking for a word starting with 'S' generally assumes that entries beginning with 'S' start about three quarters of the way through the dictionary. He, or she will first open the dictionary about three quarters of the way through and then make a decision on what is found as where to look next. In other words, people typically use some knowledge about expected distribution of key values to “compute” where to look. This form of “computed” binary search is called dictionary search or interpolation search. In dictionary search, we search at a position $p$ that is appropriate to the value of $K$ as follows:

```
$p = \frac{K - L[1]}{L[n] - L[1]}$
```

This equation is computing the position of $K$ as a fraction of the distance between the smallest and largest key. This will be translated into that position which is the fraction of the way through, and this position is checked. With binary search, the actual value of the key found can be used to compute a new position within the remaining range of the array. The next check is made based on the new computation. This proceeds until the desired result is found, or the array is narrowed until no records are left. A variation on dictionary search is known as Quadratic Search (QBS), and its analysis is easier than general search. QBS will first compute $p$ and then examine $L[pm]$. If $K < L[pm]$ then QBS will probe the left by steps of size $\sqrt{n}$, until we reach a value less than or equal to $K$. For $K > L[pm]$ we will step the right by $\sqrt{n}$ until we reach a value in $L$ that is greater than $K$. Assume (for now) that it takes a constant number of comparisons to bracket $K$ within a sublist of size $\sqrt{n}$. We then take this sublist and repeat the process recursively. That is, at the next level we compute an interpolation to start somewhere in the universe. We step to the left or right (as appropriate) by steps of size $\sqrt{n}$. Note that $\sqrt{a^2} = a$, and we will be repeatedly taking square roots of the current sublist until we find the element we are looking for. Because $n=2^{\log n}$ and we can cut $\log n$ in half only $\log \log n$ times, the cost is $\Theta(\log \log n)$ if the number of probes needed is $i$, in which case the cost is $i$ (we have to do $i$ comparisons).
