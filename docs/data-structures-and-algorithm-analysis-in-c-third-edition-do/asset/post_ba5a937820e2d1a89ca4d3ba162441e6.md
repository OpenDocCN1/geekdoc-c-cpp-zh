## 13.2 Balanced Trees

We have noted several times that the BST has a high risk of becoming unbalanced, resulting in excessively expensive search and update operations. One solution to this problem is to adopt another search tree structure as the 2-3 tree or the binary tree. An alternative is to modify the BST access functions in some way to guarantee that the tree performs well. This is an appealing concept, and it works well for heaps, whose access functions maintain the height in the shape of a complete binary tree. Unfortunately, requiring that the BST always be in the shape of a complete binary tree requires excessive modification to the tree during update, as discussed in Section 10.3.

If we are willing to weaken the balance requirements, we can come up with alternative update routes that perform well in terms of cost for the update and for balance the resulting tree structure. The AVL tree works in this way, using insertion and deletion routes altered from the BST to ensure that, for every node, the depth of the left and right subtrees differ by at most one. The AVL tree is described in Section 13.2.

A different approach to improving the performance of the BST is not to require that the tree always be balanced, but rather to spend some effort toward making the BST more balanced every time it is accessed. This is a little like the idea of path compression used by the UNION/FIND algorithm presented in Section 6.2. One example of such a compromise is called the splay tree. The splay tree is described in Section 13.2.2.

### 13.2.1 The AVL Tree

The AVL tree (named for its inventors Adelson-Velski and Landis) should be viewed as a BST with the following property: For every node, the heights of its left and right subtrees differ by 1. As long as the tree maintains its property, if the tree contains $n$ nodes, then it has a depth of at most $O(\log n)$. As a result, for any node will cost $O(\log n)$, and if the updates can be done in time proportional to the depth of the node inserted or deleted, then updates will also cost $O(\log n)$, even in the worst case.

The key to making the AVL tree work is to insert and delete routines to maintain the balance property. For to be practical, we must be able to implement the revised updates in $\Theta(\log n)$ time.

### 13.2.2 The Splay Tree

Like the AVL tree, the splay tree is not actually a distinct data structure, but rather
replements the BST, insert, delete, and search methods to improve the perfor-
a of a BST. The goal of these revised methods is to provide guarantees on the
time required by a series of operations, avoiding the worst-case linear time
behavior of standard BST operations. No single operation in the splay tree is guar-
te to be efficient. The splay tree access rules guarantee that a series
m operations take $O(m \log n)$ time for a tree of $n$ nodes whenever $m \geq n$. Thus, a single insert or search operation could take $O(n)$ time. However, $m$
operations are guaranteed to require $O(m \log n)$ time, for an average cost
of $O(\log n)$ per access operation. This is a desirable performance guarantee for any
search-tree structure.

Unlike the AVL, the splay tree is not guaranteed to be balanced. What is guaranteed that the total cost of the series of accesses will be
cheap. Ultimately, it is the cost of the series of operations, not whether
tree is balanced. Maintaining balance is really done for the sake of reaching
this efficiency goal.

The splay tree access functions in a manner reminiscent of the move-
t-rule for self-organizing lists from Section 9.2, and of the path compres-
sion for managing parent-pointer trees from Section 6.2. These access
function to make the tree more balanced, but an individual access will
necessarily result in a more balanced tree.

of a search), the splay tree performs a process called splaying. Moving nodes $S$
