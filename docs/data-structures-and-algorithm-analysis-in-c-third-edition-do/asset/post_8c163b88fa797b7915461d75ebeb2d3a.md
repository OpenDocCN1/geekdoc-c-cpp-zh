Now that we have defined the dictionary ADT and settled on the design approach of storing key-value pairs for our dictionary entries, we are ready to consider how to implement it. Two possibilities would be to use an array-based or linked list. Figure 4.32 shows an implementation for the dictionary using (unsorted) array-based list.

Examining UArrayList (UAL stands for “unsorted array-based list”), we can easily see that insertion is a constant-time operation, because it simply inserts the new record at the end of the list. However, find and remove both Θ(n) time in the average and worst cases, because we need to do a sequential search. Remove method is much costly to touch every record in the list, because once the desired record is found, the remaining records must be shifted down the list to fill the gap. Method remove implements the last record from the list, so this is a constant-time operation.

As an alternative, we could implement the dictionary using a linked list. The implementation would be quite similar to that shown in Figure 4.32, and the cost of the functions should be asymptotically identical.

Another alternative would be to implement the dictionary with a sorted list. The advantage of this approach would be that we might be able to speed up the find operation using a binary search. To do so, we must first define a variation on the List ADT to support sorted lists. An implementation for the array-based sorted list is shown in Figure 4.33. Class SList (SAL stands for "sorted array-based list") inherits from class AList; however it does so using AList as a protected base class. This means that SAL has available for its use any member functions of AList, but those member functions are not necessarily available to the user of SList. However, many of the AList member functions are useful to the SList user. most of the AList member functions are passed directly to the SALList user without change. For example, the line

```cpp
AList<KVpair, Key, E> > ::remove;
```

provides SList's clients with access to the remove method of AList. However, the original insert method from class AList is replaced, and the append method of AList is kept hidden.

The dictionary ADT can be implemented from class SList, as shown in Figure 4.34. Method insert for the dictionary simply calls the insert method of the sorted list. Method find uses a generalization of the binary search function generally in Section 3.5. The cost for find in a sorted list is Θ(n) for a list of length n. This is a great improvement over the cost of find in an unsorted list. Unfortunately, the cost of insert changes from constant time in the unsorted list to Θ(n). Whether the sorted list implementation for the dictionary is more or less efficient than the unordered list depends on the relative number of insert and find operations performed. Even if we binary search down to find the record prior removal, we would still need to shift the records in the list to fill the gap.

Given keys, we have not properly addressed the issue of how to compare them. One possibility would be to use the basic ==, <=, and >= operators built into C++. This is the approach taken by our implementations for dictionaries shown in 4.32 and 4.34. If the key type is int, for example, this will work. However, if the key is a pointer to a string or any other type of object, this will not give the desired result. When we compare two strings we probably want to know which comes first in alphabetical order, but what we get from the standard comparison operators is simply which appears first in memory. Unfortunately, the C++ will compile, but the answers will probably not be fine.

In a language like C++ that supports operator overloading, we could require the user of the dictionary to overload the ==, <=, and >= operators for the key type. This requirement then becomes an obligation on the user of the dictionary. Unfortunately, this obligation is hidden within the code of the dictionary (and possibly in the user's manual) rather than exposed in the dictionary's interface. As a result, some users of the dictionary might neglect to implement the overloading, with unexpected results. The compiler will not catch this problem.

The most general solution is to have users supply their own definition for comparing keys. The concept of a class that does comparison (called a comparator) is quite important. By making these operations template parameters, the requirement to supply the comparator class becomes part of the interface.
