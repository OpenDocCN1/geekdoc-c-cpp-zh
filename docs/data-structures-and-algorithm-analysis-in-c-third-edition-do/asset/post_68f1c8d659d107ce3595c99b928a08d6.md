
## 9.2 Self-Organizing Lists

It is not always practical to reduce an algorithm's growth rate. There is a "practicality window" for every problem, in that we have a practical limit to how big an input we wish to solve for. If problem size never grows too big, it might not matter if we can reduce the cost by an extra log factor, because the constant factors in the two algorithms might differ by more than the log of the log of the input size.

For our two algorithms, let us look further and check the number of comparisons used. For binary search, we need $\log n - 1$ total comparisons. Quadratic binary search requires $2.4 \log n$. If we incorporate this observation into our table, we get a different picture about the relative differences.

| $n$ | $\log n - 1$ | $2.4 \log n$ | Difference |
|---|---|---|--|
| 16 | 3 | 4.8 | worse |
| 256 | 7 | 7.2 | $\approx$ same |
| $64K$ | 15 | 9.6 | 1.6 |
| $2^{32}$ | 31 | 12 | 2.6 |

But we are not done. This is only a count of raw comparisons. Binary search is isnt simpler than QBS, because binary search only needs to calculate the midpoint of the array before each comparison, while quadratic binary search must calculate an interpolation point which is more expensive. So the constant factors for QBS are even better.

Not only are the factors worse on average, but QBS is far more dependent than binary search on good data distribution to perform well. For example, imagine you are searching a telephone directory for the name "Young." Normally look near the back of the book. If you found a name beginning with 'Z', you might look a little towards the front. The next name also begins with 'Z', you would look a little further towards the front. If this particular telephone directory were unusual in half of the entries begin with 'Z', then you would need to move towards the front many times, time eliminating relatively few records from the search. In the extreme, the performance of interpolation search might not be much better than sequential search if the distribution of key values is badly balanced.

While it turns out that QBS is not a practical algorithm, this is not a typical situation. Furthermore, algorithm growth rates are usually well behaved, so that asymptotic analysis nearly gives us a practical indication for which of two algorithms are better.

While ordering of lists is most commonly done by key value, this is not the only viable option. Another approach to organizing lists to speed search is to the records of frequent access to. While the benefits might not be as great as when organized by key value, the cost to organize (at least approximately) of frequency of access can be much cheaper, and thus can speed up sequential search in some situations.

Assume that we know, for each key $k_i$, the probability $p_i$ that the record with $k_i$ will be requested. Assume also that the list is ordered so that the most frequently requested record is first, then the next frequently requested record, and so on. Search in the list will begin sequentially with the first position. Over the course of many searches, the expected number of comparisons required for one search is:

$$C_n = 1p_0 + 2p_1 + \dots + np_{n-1}$$

In other words, the cost to access the record in **L[0]** is 1 because each key value is looked at, and the probability of this occurring is $p_0$. The cost to access the record in **L[1]** is 2 (because we must look at the first and the second records' key values), with probability $p_1$. For $n$ records, assuming that all searches are for records that actually exists, the probabilities $p_0$ through $p_{n-1}$ must sum to one. Certain probability distributions give computed results.

**Example 9.1** Calculate the expected cost to search a list when each record has equal chance of being accessed (the classic sequential search through unsorted list). Setting $p_i = 1/n$ yields:

$$C_n = \sum_{i=1}^n i/n = (n+1)/2$$

This matches our expectation that half the records will be accessed on on normal sequential search. If the records have equal access probabilities, ordering records by frequency yields no benefit. We in Section 9.1 the more general case where we must consider the probability (labeled $p_n$) that the search key does not match for any record in the ray. In that, in accordance with our general formula, we get:

$$(1-p_n)\frac{n+1}{2} + p_np_n = \frac{n+1-np_n+2np_n^2}{2} = \frac{n+1+p_n(n-1)}{2}$$

Thus, $\frac{n+1}{2} \leq \bar{C}_n \leq n$, depending on the value of $p_0$.

A geometric probability distribution can yield quite different results.

**Example 9.2** Calculate the expected cost for searching a list ordered by frequency when the probabilities are defined as:

$$p_i = \begin{cases} 1/2^i & \text{if } 0 \leq i \leq n-2 \\ 1/2^n & \text{if } i = n-1. \end{cases}$$

Then,

$$\mathcal{C}_n = \sum_{i=0}^{n-1} (i+1)/2^{i+1} = \sum_{i=1}^{n} (i/2^i) \approx 2$$

For this example, the expected number of accesses is a constant. This is because the probability for accessing the first record is high (one half), the second is much lower (one quarter) but much higher than for the third record, and so on. This shows that for some probability distributions, ordering the list by frequency can yield an efficient search technique.

In many searches, real access patterns follow a rule of thumb called the **80/20 rule**. 80/20 rule says that 80% of the record accesses are to 20% of the records. The values of 80 and 20 are only estimates; every data pattern has its own values. However, behavior of this nature occurs surprisingly in practice (which explains the success of caching techniques used by web browsers for searching web pages, and by disk drive and CPU manufacturers for speeding access to data stored in slower memory; see the discussion on buffer pools in Section 8.3). When the 80/20 rule applies, we can expect considerable improvements to search performance from a list ordered by frequency of access over standard sequential search in an unordered list.

**Example 9.3** The 80/20 rule is an example of a *Zipf distribution*. Naturally occurring distributions follow a Zipf distribution. Examples include the observed frequency of use of words in a natural language such as English, and the size of the population for cities (i.e., view the relative proportions for populations as equal to the “frequency of use”). Zipf distributions are related to the Harmonic Series defined in Equation 2.10. Define the Zipf frequency for item $i$ in the distribution for $n$ records as $1/(iH_n)$ (see Exercise 9.4). The expected cost for the series whose members follow this Zipf distribution will be:

$$\mathcal{C}_n = \sum_{i=1}^{n} i/H_n = n/H_n \approx n/\log n$$

When the 80/20 rule applies, we can expect considerable improvements to search performance from a list ordered by frequency of access over standard sequential search in an unordered list.

In most applications, we have no means of knowing in advance access for data. To complicate matters, certain records might be accessed frequently for a period of time, and then rarely thereafter. Thus, the probability of access might change over time. Self-organizing lists seek to solve all of these problems.

Self-organizing lists modify the order of records within the list based on the actual pattern of access. Self-organizing lists use a heuristic for deciding how to reorder the list. These heuristics are similar to the rules for managing buffer pools (see 8.3). In fact, a buffer pool is a form of self-organizing list. Ordering the buffer pool by expected frequency of access is a good strategy, because typically we search the contents of the buffers to determine if the desired information is in main memory. Whenever ordered by frequency of access, the buffer at the end of the list will be the most appropriate for reuse when a new page of information must be read. Below are three traditional heuristics for managing self-organizing lists:

- The most obvious way to keep a list ordered frequently would be to store a count of accesses to each record and always maintain counts in this order. This method will referred to as count. Count is similar to the least used replacement strategy. When a record is accessed, it might move toward the front of the list if its number of accesses becomes greater than a record preceding it. Thus, count will store the records in the order of frequency that has actually occurred so far. Besides requiring space for the access counts, count does not react to changing frequency of access over time.

- Bring a record to the front of the list when it is found, pushing all the other back one position. This is analogous to the least used replacement strategy and is called move-to-front. This heuristic is easy to implement if the records are stored using a linked list. When records are stored in an array, bringing a record forward from near the end of the array will result in a large number of records (slightly) changing position.
