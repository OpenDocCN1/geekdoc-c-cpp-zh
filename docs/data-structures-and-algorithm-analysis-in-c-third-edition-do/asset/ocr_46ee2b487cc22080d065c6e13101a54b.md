The dictionary ADT can be implemented from class SList, as shown in Figure 4.34. Method insert for the dictionary simply calls the insert method of the sorted list. Method find uses a generalization of the binary search function generally in Section 3.5. The cost for find in a sorted list is Θ(n) for a list of length n. This is a great improvement over the cost of find in an unsorted list. Unfortunately, the cost of insert changes from constant time in the unsorted list to Θ(n) in the sorted list. Whether the sorted list implementation for the dictionary ADT is more or less efficient than the unordered list depends on the relative number of insert and find operations to be performed. If more find insert operations are used, remove requires Θ(n) time in the worst and average cases. Even if we binary search down to find the record prior removal, we would still need to shift the records in the list to fill the gap left by remove operation.

Given keys, we have not properly addressed the issue of how to compare them. One possibility would be to use the basic ==, <=, and >= operators built into C++. This is the approach taken by our implementations for dictionaries shown in Figures 4.32 and 4.34. If the key type is int, for example, this will work not fine. However, if the key is a pointer to a string or any other type of object, this will not give the desired result. When we compare two strings we probably want to know which comes first in alphabetical order, but what we get from the standard comparison operators is simply which appears first in memory. Unfortunately, the C++ will compile, but the answers will probably not be fine.

In a language like C++ that supports operator overloading, we could require the user of the dictionary to overload the ==, <=, and >= operators for the key type. This requirement then becomes an obligation on the user of the dictionary. Unfortunately, this obligation is hidden within the code of the dictionary (and possibly in the user's manual) rather than exposed in the dictionary's interface. As a result, some users of the dictionary might neglect to implement the overloading, with unexpected results. The compiler will not catch this problem.

The most general solution is to have users supply their own definition for comparing keys. The concept of a class that does comparison (called a comparator) is quite important. By making these operations template parameters, the requirement to supply the comparator class becomes part of the interface.
