
## Protocols and Delegation

A protocol is a list of methods that is shared among classes. The methods listed in the protocol do not have corresponding implementations; they're meant to be implemented by someone else (like you!). A protocol provides a way to define a set of methods that are somehow related with a named name. The methods are typically documented so that you know how to perform and so that you can implement them in your own class definitions, if desired.

A protocol is a list of methods, some of which you can optionally implement, and others that you are required to implement. If you decide to implement all of the required methods for a particular protocol, you are allowed to conform or adopt that protocol. You are allowed to define a protocol where all methods are optional, or where all are required.

Defining a protocol is easy: simply use the `@protocol` directive followed by the name of the protocol, which is up to you. After that, you declare methods just as you did with your interface section. All the method declarations, up to the `@end` directive, become part of the protocol.

When you work with the Foundation framework, you'll find that several protocols are defined. One of them declares a method that you need to implement if your class is to support copying of objects through the `copy` (or `copyWithZone:`) method. ("Copying Objects" covers the topic of copying objects in detail.)

Here's how `NSCopying` protocol is defined in the standard Foundation header file `NSObject.h`:

```objc
@protocol NSCopy
- (id)copyWithZone:(NSZone);
@end
```

If you adopt the NSCopy protocol in your class, you must implement a method called `copyWithZone:`. Tell the compiler that you are adopting a protocol by listing the protocol name inside a pair of angular brackets `<..>` on the `@interface` line. The protocol name comes after the name of the class and its parent class, as in the following:

```objc
@interface AddressBook: NSObject <NSCopying>
```

This says that `AddressBook` is one whose parent is `NSObject` and states that it conforms to the `NSCopying` protocol. The system already knows the method(s) defined for the protocol (for example, it knows from the header file `NSObject.h`), you don't need to declare the methods in the interface section. However, you need to define them in your implementation section.

In this example, the implementation section for `AddressBook`, the compiler expects to see the `copyWithZone:` method defined.

If your class adopts more than one protocol, just list them inside the angular brackets, separated by commas:

```objc
@interface AddressBook: NSObject <NSCopying, NSCoding>
```

## Delegation

You can also think of a protocol as an interface definition between two classes. The class that defines the protocol can be thought of delegating the work defined by the methods to the class that implements them. In that way, the class can be more general, with specific actions. Cocoa and iOS rely heavily on this concept of delegation. For example, when you set up a table on the iPhone's display, you'll use `UITableView`. But that class does not know the title of the table, how many sections or rows it contains, or what to put in each row (cell). So it delegates responsibility to you by defining a protocol called `UITableViewDataSource`. When it needs information, for example, how many rows are in the table, it will call the appropriate method that you've defined in your class.
