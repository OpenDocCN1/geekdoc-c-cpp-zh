
## Overriding Methods

We noted earlier in this chapter that you can't remove methods through inheritance. However, you can change the definition of an inherited method by overriding.

Returning to your two classes, ClassA and ClassB, assume that you want to write your own initVar method for ClassB. You already know that ClassB will inherit initVar from ClassA, but can you make a new method with the same name to replace the inherited method? The answer is yes, and you do so by simply defining a new method with the same name. A method defined with the same name as the parent class replaces, or overrides, the inherited definition. Your new method must have the same return type and arguments as the method you are overriding. Program 8.6 shows a simple example to illustrate this.

### Program 8.6

```objc
// Overriding Methods

#import <Foundation.h>

// ClassA declaration and definition

@interface ClassA: NSObject
{
  int x;
}

-(void)initVar;
@end

@implementation ClassA
-(void)initVar
{
    x = 100;
}
@end
```

```objc
// ClassB declaration and definition

@interface ClassB: ClassA
-(void)initVar;
-(void)printVar;
@end

@implementation ClassB
-(void)initVar // added method
{
    x = 200;
}

-(void)printVar
{
    NSLog("%d", x);
}
@end

int main (int argc, char *argv[]) {
    NSAutleasePool *pool = [[NSAutleasePool alloc] init];
    ClassB *b = [[ClassB alloc] init];

    [b initVar]; // uses overriding method in B

    [b printVar]; // reveal value of x;
    [b release];

    [pool drain];
    return 0;
}
```

#### Program 8.6 Output
200

Clearly, the message [b initVar]; causes the initVar method defined in ClassB to be used, and not the one in ClassA, as was the case with the previous example. Figure 8.9 illustrates this.

| :--- | :--- | :--- |
| Object | | |
| ClassA | x | initVar |
| ClassB | x | initVar, printVar |

## Which Method Is Selected?

We covered how the system searches up the hierarchy for a method to apply to an object. If you have methods in different classes with the same name, the correct method is chosen based on the class of the receiver of the message. Program 8.7 uses the same class definition for ClassA and ClassB as before.

### Program 8.7

```objc
#import <Foundation.h>

// insert definitions for ClassA and ClassB here

int main (int argc, char *argv[]) {
    NSAutleasePool * pool = [[NSAutleasePool alloc] init];
    ClassA *a = [[ClassA alloc] init];
    ClassB *b = [[ClassB alloc] init];

    [a initVar]; // uses ClassA method
    [a printVar]; // reveal value of x;

    [b initVar]; // use overriding ClassB method
    [b printVar]; // reveal value of x;
    [a release];
    [b release];

    [pool drain];
    return 0;
}
```

You'll get this warning message when you build this program:
`warning: 'ClassA' may not respond to selector '-printVar'`

What happened here? We talked about this in an earlier section. Take a look at the declaration for ClassA:

```objc
// ClassA declaration and definition

@interface ClassA: NSObject
{
    int x;
}

-(void)initVar;
@end
```

Notice that no printVar method is declared. Because no printVar method is declared, the system cannot find it in the hierarchy, leading to the warning.

## Chapter 8 Inheritance

By default, the action of a setter is to copy the object pointer, not the object itself. You can synthesize a different type of setter that instead makes a copy of the object. However, to do that, you need to learn how to write a copying method. We revisit this topic in Chapter 17, "Memory Management."

Before learning this section, let's think about the getter side of Rectangle class. Suppose in your test program from 8.4 you inserted the following lines after setting Rectangle's values:

```
Point *tOrigin = myRect.origin;
tOrigin.x = 200;
tOrigin.y = 300;
```

What would happen to myRect's origin after this code was executed? Right, its origin would be changed. The object that the getter returns is "vulnerable": anyone changing its x or y would change the rectangle's x or y value accordingly. For this reason, the safest way to write a getter is to actually make a copy of the object and return that copy. In that way, you are protecting the instance variable from getting changed. We won't make that change here, but leave that as exercise. Note that you face a performance penalty if you copy objects before returning them. You will have to judge if tradeoff is worth it when designing your class.

## Overriding the dealloc Method

If you decide to override dealloc, you also have to be sure to release the memory taken not only by your own variables, but by any inherited ones as well. To do this, you need to take advantage of the special keyword super, which refers to the parent class of the message. This is the most common use for super:

```objc
[super dealloc];
```

when used inside a method it invokes the dealloc method of the parent class. So, the strategy for overriding the dealloc method for your class is to first release the memory taken up by your origin and then invoke the dealloc method from the parent class to complete the job. Here is the new method:

```objc
-(void)dealloc
{
  if (origin)
    [origin release];
  [super dealloc];
}
```

The dealloc method is defined to not return a value. A test is made to see if origin is nonzero before releasing it. The origin of the rectangle was never set; in this case, it has its default value of zero. Then we invoke the dealloc method from the parent class, which is the same method the Rectangle class would have inherited if it had not been overridden. You can also write the dealloc method more simply as

```objc
-(void)dealloc
{
  [origin release];
  [super dealloc];
}
```

because it’s okay to send a message to a nil (zero) object. Also, you’re careful to release origin and not dealloc here. If no one else is using the origin, that release message will end up invoking the dealloc method on the origin anyway to free up its space.

With your new method, you have to release the rectangles that you allocate, without worrying about the XYPoint objects they contain. The two release messages shown in Program 8.5 will now suffice to release all the objects in the program, including the XYPoint object that setOrigin: creates:

```
[myRect release];
[myPoint release];
```
