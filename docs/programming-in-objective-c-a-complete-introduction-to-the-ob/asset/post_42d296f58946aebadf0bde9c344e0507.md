You retrieved the first element of dataArray with the following statement:

```
mStr = [dataArray objectAtIndexIndex: 0];
```

Then you appended the string "ONE" to it with this statement:

```
[mStr appendString: "ONE"]
```

Notice the value of the first element of the original array and its copy: Both were modified. Perhaps you can understand why the first element of dataArray was changed but not its copy was as well. When you get an element from a collection, you get a reference to that element, but not a copy. So when the method is invoked on dataArray, the returned object points to the same object in memory as the first element in dataArray. Subsequently modifying the string mstr has the side effect of affecting the first element of dataArray, as you can see from the output.

But what about the copy you made? Why is its first element changed as well? This has to do with the fact that copies, by default, are shallow copies. Thus when the array was copied with the mutableCopy method, space was allocated for a new array in memory and the individual elements were copied into the new array. But copying each element in the original to a new location meant just copying the reference from one element of the array to another. The net result was that the elements of both arrays referenced the same strings in memory. This is no different from assigning one object to another, which we covered at the beginning of this chapter.

To make distinct copies of each element of the array, you must perform a deep copy. This means making copies of the contents of each object in the array, not just copies of the references to the objects (and think about what implies if an element of an array is itself an array). But deep copies are not performed by default when you use the copy or mutableCopy methods with the Foundation classes. In Chapter 19, "Archiving," we show you how to use the Foundation's archiving capabilities to create a deep copy of an object.

When you copy an array, a dictionary, or a set, for example, you get a new copy of those collections. However, you might need to make your own copies of individual elements if you want to make changes to one collection but not to its copy. For example, if you wanted to change the first element of dataArray2 but not dataArray1.2, you could make a new string using a method such as stringWithString: and store it into the first location of dataArray2, as follows:

```
mstr = [[NSMutableString stringWithString:dataArray2 objectAtIndexIndex:0]];
```

Then you could make a copy of mstr and add the index to the array using the replaceObject:atIndex:withObject: method, as follows:

```
[dataArray2 replaceObject:mstr atIndex:0 with:mstr];
```

Hopefully you realize that even after replacing the object in the array, mstr and the first element of dataArray2 refer to the same object in memory. Therefore, subsequent changes to mstr in your program will also change the first element of the array. If that's not what you want, you can release mstr and allocate a new instance, because the replaceObject:atIndex:withObject: method automatically retains the object that's added to the array.

# Implementing the <NSCopying> Protocol

If you try to use the copy method on one of your classes—for example, on your address book, as follows

```
[NewBook copy mutableCopy];
```

you'll get an error message that looks like this:

> *** -[AddressCopy copyWithZone:] selector not recognized
*** Uncaught exception:
*** -[AddressCopy copyWithZone:] selector not recognized

As noted, to implement copying with your classes you have to implement one or two methods according to the <NSCopying> protocol.

We now show how to get a copy of your Fraction class, which is used extensively in Part I, "The Objective-C 2.0 Language." Note that the techniques we describe here for copying strategies will work fine for your own classes. If those classes are subclasses of the Foundation classes, you'll need to implement a more sophisticated copying strategy to account for the fact that the superclass might have already implemented its own copying strategy.

Recall that Fraction contains two integer variables, numerator and denominator. To make a copy of one of these objects, you must allocate space for a new fraction and then copy the values of the two integers into the new fraction.

When you implement the <NSCopying> protocol, your class must implement the copyWithZone: method to respond to a copy message. (The copy message sends a copyWithZone: message to your class with an argument of nil). If you want to make a distinction between mutable and immutable copies:

Here's what the @interface directive should look like:

```
@interface Fraction : NSObject <NSCopying>
```

Fraction is a subclass of NSObject and conforms to the NSCopying protocol.
In the implementation file Fraction.m, add the following definition for your new method:

```objc
- (id) copyWithZone:(NSObject *)zone {
    Fraction *newFract = [[Fraction alloc] initWithZone:zone];

    [newFract setTo:numerator denominator:denominator];
    return newFract;
}
```

The zone argument has to do with different memory zones that you can allocate and work in your program. You need to deal with these only if you are writing applications that allocate memory by grouping them into zones.

int main (int argc, char *argv[]) {
    NSAutleasePool *pool = [[NSAutleasePool alloc] init];
    
    Fraction *f1 = [[Fraction alloc] init];
    [f1 setTo:1 denominator:2];
    Fraction *f2 = [f1 copyWithZone:nil];
    [f1 setTo:3 denominator:4];
    
    [f1 print];
    [f2 print];
    
    [f1 release];
    [f2 release];
    [pool drain]; 
    return 0;
}

# Copying Objects in Setter and Getter Methods

Whenever you implement a setter or getter method, you should think about what you're storing in the instance variables, what you're retrieving, and whether you need to protect these values. For example, consider this when you set the name of your AddressCard using the corresponding setter method:

```
newCard.name = newName;
```

Assume that newName is a string containing the name for your new card. Assume that the setter routine you simply assigned the parameter to the instance variable:

```objc
(void) setName:(NSString *)newName
    name = newName;
```

Now, what do you think would happen if the program changed some of the characters contained in newName in the program (this could happen if newName were a mutable string object; such an object can be used in places where an NSString object is specified, as the former is a subclass of the latter)? Would it unintentionally change the corresponding field in your address card because both would reference the same string object.

As you have already seen, a safer approach is to make a copy of the object in the setter routine, to prevent this effect. We did this by using the alloc method to create a new string object and then using initWithString to set it to the value of the parameter provided to the method.

You can also write a version of the setName: method to use copy, like this:

```objc
(void) setName:(NSString *)newName
{
    name = [newName copy];
}
```

Of course, to make this setter memory management friendly, you should autorelease the old value, like this:

```objc
(void) setName:(NSString *)newName
{
    [name autorelease];
    name = [newName copy];
}
```
