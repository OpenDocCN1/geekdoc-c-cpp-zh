# Entering Your Code

Now we're ready to modify some of your project files. Notice that a class called projectnameAppDelegate.h and projectnameAppDelegate.m were created for you, where in this example project-name is iPhone_1. An application delegate subclass is created for every new iOS application you create. In general, this class are methods that control the application's execution. This includes things like what to do when the application starts, when it enters and leaves the background, when the system tells it's using too much memory, and when it terminates. We're also going to make it responsible for handling the event of pressing the button labeled “1.” Here we'll define a method to respond to that action when it occurs in your iPhone's window, in our example, the that to the execution of a specific method.

Your objects can have instance variables whose values correspond to control in your iPhone's window, such as the name on a label or the text displayed in an editable text box. These variables are known as outlets, and you will see how you connect an instance variable to an actual control in the iPhone's window.

For our first application, we need a method that responds to the pressing of the button 1. We also need an outlet variable that contains (among other information) to be displayed in the label that we create at the top of the iPhone's window.

Edit the file iPhone_AppDelegate.h to add a new UILabel property called display and declare an action method called click1 to respond to the pressing of the button. Your window interface file should appear as shown in Program 21.1. (The comment lines automatically inserted at the head of the file are not shown here.)

# Program 21.1 iPhoneAppDelegate

```
@import <UIKit/UIKit.h>

@interface iPhone_1AppDelegate : NSObject <UIApplicationDelegate>
@private
}

@property (nonatomic, retain) IBOutlet window;
@property (nonatomic, retain) IBOutlet UILabel label;

-(IBAction) click;

@end
```

Notice that iPhone applications import the header file <UIKit/UIKit.h>. This header file, in turn, imports other header files, in a similar way that the Foundation.h header file imported other header files you needed, as NSString and NObject. The iPhone_1AppDelegate class has two properties. First is a window object called window. That property is automatically when you create the project, and it references the iPhone's main window.

> Note
> Xcode does not list instance variables inside the curly braces, as we have done throughout this text. In fact, you'll see from the implementation section that this property is associated with an instance variable _window. Your app delegate class will have an instance variable _window with an associated property called window. The @private directive ensures that instance variable cannot be accessed directly by my methods defined in other classes, including subclasses. The preferred way to access your instance variables is through its accessors. Xcode generates template code to encourage that.

You added another property belonging to the UILabel class called display. When you set your property's text, it updates the content for the label. Other methods defined by the class allow you to set and retrieve other attributes of a label, such as its color, the number of lines, and the size of the font.

You'll want to use classes as you learn more about iPhone programming that we are writing. The names of some of these will give you a clue as to their purpose: UITextField, UILabel, UIView, UITableView, UIImageView, UISl, and UIButton.

Both the window and display properties are outlets, and in the property declarations, the use of IBOutlet identifier is really defined as nothing in the UIKit header file UIButtonDeclarations.h. (That is, it is literally replaced by nothing in the source file by the preprocessor.) However, it's needed because Xcode looks for IBOutlets when it reads your header file to determine which of your variables can be used as outlets and can be connected to the appropriate UI elements in the subclass.

The click1 method is defined to return a value of IBAction. (This is defined as void in the UIViewDeclarations.h file.) Like IBOutlet, Xcode uses this identifier when it examines your header file to identify methods that can be used as actions.

Now it is time to modify the corresponding iPhone_AppDelegate implementation for your class. Here you synthesize the accessor methods for your display property (the window accessor methods are already synthesized for you) and add the definition for your click1 method.

# Note

> Before you make any changes, take a look at the @synthesize directive that XCode has inserted: @synthesize window __; As mentioned in an earlier note, this associates the instance variable _window with the property window, defined in the interface section. The reason this is to ensure direct access through the synthesized accessor methods as opposed to direct access through the instance variable.

Now edit your implementation file so that it resembles the one shown in Program 21.1.

The applicationDidFinishLaunchingWithOptions: method is automatically called by the iPhone runtime system once, as its name implies, your application has finished launching. This is the place where you initialize your instance variables, draw things on the screen, and make your window visible to display its contents. This last action is done by sending the makeKeyAndView message to your window at the end of the method.
