# More on the Event Loop and Memory Allocation

+   - autorelease pool provides for the automatic release of objects when the pool is drained. The system does this by sending a release message to each object in the pool for each time it was autoreleased. Each object in the autorelease pool whose reference count goes to 0 is sent a dealloc message to destroy it.
- If you no longer need an object from within a method but need to return it, send it an autorelease message to mark it for later release. The autorelease message does not affect the reference count of the object.
- When your application terminates, all the memory your objects take up is released, regardless of whether they were in the autorelease pool.
- When you develop Cocoa or iOS applications, autorelease pools will be created and drained throughout execution of the program (this will happen every time an event occurs). In such cases, if you want to ensure that your survives automatic deallocation when the autorelease pool is drained, you need to retain it. All objects that have a reference count greater than the number of autorelease messages they have sent will survive the release of the pool.

As noted in the previous section, Cocoa and iOS applications run inside what's called a run or event loop. Think of an event as something that initiated by your performing some action (e.g., you press on the iPhone) or an implicit action (e.g., something arrives over the network). To process the event, the system will create a new autorelease pool and may call some method in your application to handle it. When you're done handling the event, you'll return from your method and the system will wait for the next event to occur. Before doing so, however, the system will drain the autorelease pool. That means that any autoreleased objects you have created in processing that event will be destroyed, unless you have retained those objects so they will survive the draining of the pool.
