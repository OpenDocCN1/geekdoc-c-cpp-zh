The third reason applies to if you plan on writing runtime libraries, plugins, or shared code. Since that code might be loaded into a garbage-collected or non garbage-collected process, it has to work in both environments. That means you need to write your code using the memory management techniques described throughout this book. It also means you have to test your code with garbage-collection disabled and enabled.

If you decide to use garbage collection, you must turn it on when building programs with Xcode. You can do this through the Project, Edit Project Settings. Under the "GCC 4.x—Code Generation" settings, you will see a setting Objective-C Garbage Collection. Changing that from its default value to Unsupported requires that your program will be built with automatic garbage collection enabled (see Figure 17.1).

When garbage collection is enabled, your program can still make its retain, autorelease, release, and dealloc method calls. However, they'll be ignored. In that way, you can develop a program that can run in both memory-managed and garbage-collected environments. This also implies that if your code is to run in both environments, you can't do any work in a dealloc method that you provide. That's because, as stated, dealloc calls are ignored when garbage-collection is enabled.

> Note
The memory-management techniques described in this chapter will suffice for most applications. However, in more advanced cases, such as when writing multithreaded applications, you might need to do more.
