In fact, at runtime, the CLR has no idea what programming language developer used for the source code. This means you should choose whatever programming language allows you to express your intentions most easily. You can develop your code in any programming language you desire as long as your compiler allows you to compile your code targets the CLR.

So, if I say that here is true, what is the advantage of using one programming language over another? Well, think of compilers as syntax checkers and "correct code" analyzers. They examine your source code, ensure that whatever you've written makes some sense, and then output code that describes your intention. Different programming languages allow you to develop using different syntax. Do not underestimate the value of this choice. For mathematical or financial applications, expressing your intentions by APL syntax can save many days of development time when compared to expressing the same intention by using Perl, for example,

Microsoft has created several language compilers that target the runtime: C++/CLI, C# (pronounced "C sharp"), Visual Basic, F# (pronounced "F sharp"), Iron Python, Iron Ruby, and Intermediate Language (IL) Assembler. In addition to Microsoft, several other companies, colleges, and universities have created compilers that produce code to target the CLR. I am aware of compilers for Ada, APL, Camel, Cobol, Eiffel, Fort, Fortran, Haskell, Lexico, LSP, LGO, Lua, Mercury, ML, Mondrian, Oberon, Pascal, Perl, PHP, Prolog, RPG, Scheme, Smalltalk, and T/Tk.

Native code producers produce code targeted to a specific CPU architecture, such as x86, x64, or ARM. All CLR-compliant compilers produce IL code instead (I'll go into more detail about IL later in this chapter). IL code is referred to as *managed code* when the CLR manages its execution.

In addition to emitting IL, every compiler the CLR is required to emit **metadata** into every managed module. In brief, metadata is a set of data tables that describe what is defined in the module, such as types and their members. In addition, metadata also has tables indicating the managed module references, such as imported types and members. Metadata is a subset of older technologies like COM's Type Libraries and Interface Definition Language (IDL) files. The important thing to note is that CLR metadata is far more complete. And, unlike Type Libraries and IDL, metadata is always associated with the file that contains the IL code. In fact, the metadata is embedded in the same EXE/DLL, making it impossible to separate the two. The compiler produces the metadata and the code at the same time and binds them into the resulting managed module, the metadata and the IL code are out of sync with one another.

Metadata has many uses. Here are some of them:

- Metadata removes the need for native C/C++ header and library files when compiling because the information about the referenced types/members is contained in the file that has the IL that implements the type/members. Compilers can read metadata directly from managed modules.
- Metadata allows Microsoft Visual Studio to tell you what methods, properties, events a type offers.
- The CLR's code process uses metadata to ensure your code performs only “type-safe” operations.
- Metadata allows the garbage collector to track the lifetime of objects.
- Metadata allows the garbage collector to know which fields refer to other objects.

All of the Microsoft compilers mentioned, C++ is unique in that it is the only compiler that allows the developer to write both managed and unmanaged code and have it emitted into a single module.  Combining Managed Modules into Assemblies

The CLR doesn’t actually work with modules, it with assemblies. An assembly is an abstract concept that can be difficult to grasp initially. First, an assembly is a logical grouping of one or more modules or resources. Second, an assembly is the smallest unit of release, security, and versioning. Depending on the choices you make with your compilers or tools, you can produce a single-file or multifile assembly. In the CLR world, an assembly is what we would call a component.

In Chapter 2, I’ll go over assemblies in great detail, so I don’t want to spend a lot of time on them here. All I want to do make sure you are aware that there is this conceptual notion that offers a way to treat a group of assemblies as a single file.
