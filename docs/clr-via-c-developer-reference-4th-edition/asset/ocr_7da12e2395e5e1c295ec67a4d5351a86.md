Ultimately, the hardware device will complete the I/O operation, and then Windows will wake up your thread, schedule it to a CPU, and let return from kernel mode to user mode, and then back to managed code (#7, #8, and #9). FileStream's Read method now returns an Int32, indicating the actual number of bytes read from the file so that you know how many bytes you can examine in the Buffer[] you passed to Read.

Let's imagine that you are implementing a web application and each client request comes in to your server, you need to make a database request. When a client request comes in, a thread pool will block for an indefinite amount of time waiting for the database to respond with. If during this time another client request comes in, the thread pool will create another thread and again this thread will block when it makes another database request. As more and more client requests come in, more and more threads are created, and all these threads block waiting for the database to respond. The result is that your web server is allocating lots of system resources (threads and their memory) that are barely used!

And to make matters worse, when the database does reply with the various results, threads become unblocked and because you have lots of threads running and few CPU cores, Windows has to perform frequent context switches, which hurts performance. This is no way to implement a scalable application.

Now, let's explain how Windows performs asynchronous I/O operations. In Figure 2-8, we have removed all the hardware devices except the hard disk from the picture, I introduce the common language runtime's (CLR) thread pool, and I modified the code slightly. I will then open the file by constructing a FileStream object, but now I pass in the FileStreamOptions.Asynchronous flag. This flag tells Windows that I want to read and write operations on the file to be performed asynchronously.


To read data from the file, I call ReadAsync instead of Read. ReadAsync internally allocates a Task<Int32> object to represent the pending completion of the read operation. Then, ReadAsync calls Win32's ReadFile (#1). ReadFile allocates its ISR, initializes it just like it did in the synchronous scenario (#2), and passes it down to the Windows kernel (#3). Windows adds the IRP to the disk driver's IRP queue (#4), but not, instead of blocking your thread, your thread is allowed to return to your code; that immediately returns from its call to ReadAsync (#5, #6, and #7). Now you might ask, and how do you process the data that will be returned? Well, when you call ReadAsync, it returns to you a Task<Int32> object. Using this object, you can ContinueWith to register a callback method that should execute when the task completes and then process the data in this callback method. Or, alternatively, you can use C# asynchronous function feature to simplify your code by allowing you to write it sequentially (as you would if you were performing synchronous I/O).
