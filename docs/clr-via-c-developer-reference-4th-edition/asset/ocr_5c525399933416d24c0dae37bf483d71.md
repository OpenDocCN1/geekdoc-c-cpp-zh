Now let's talk about Task objects scheduled using the default TaskScheduler (obtained by querying TaskScheduler's static Default property). When a non-worker thread schedules a Task, the Task is added to the global queue, when each worker thread has its local queue, and when a worker thread schedules a Task, the Task is added to calling the thread's local queue.

When a worker thread is ready to process an item, it always checks its local queue for a Task first. If a Task exists, the worker thread removes the Task from its local queue and Note that a worker thread pulls tasks from its local queue using a last-in-first-out (LIFO) algorithm. Because a worker thread is the only thread allowed to access the head of its local queue, no thread synchronization lock is required and adding and removing Tasks from the queue is very fast. A side effect of this behavior is that Tasks are executed in the reverse order that they queued.

> Important threads never guarantee the order in which queued items are processed, especially multiple threads could be processing items simultaneously. However, this side effect exacerbates the problem. You must make sure that your application has no expectations about the order in which queued work items or tasks execute.

When a worker thread sees that its local queue is empty, the worker thread will attempt to steal a Task from another worker's local queue. Tasks are stolen from the tail of a local queue and require a thread synchronization lock be taken, which hurts a little bit. Of course, the hope is that stealing rarely occurs, so lock is taken rarely. If all the local queues are empty, then the worker thread will extract an item from the global queue (taking its lock) using the FIFO algorithm. If the global queue is empty, the worker thread puts itself to sleep waiting for something to show up. If it sleeps for a long time, it will wake up and destroy itself, allowing the system to reclaim the resources (kernel object, stacks, TEB) that were used by the thread.
