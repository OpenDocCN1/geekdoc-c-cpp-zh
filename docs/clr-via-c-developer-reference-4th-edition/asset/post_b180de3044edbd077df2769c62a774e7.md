
It can also decide to fail an AppDomain creation, or it can decide to return a reference to an existing AppDomain instead. When a new AppDomain is created, the CLR creates a new AppDomainManagerderived object which can also modify configuration settings, how execution context is flowed between threads, and permissions granted to an assembly.

## Writing a Robust Host Application

A host can tell the CLR what actions to take when a failure occurs in managed code. Here are some examples (from least severe to most severe):

- The CLR can abort a thread if it is taking too long to execute and return a response. (I'll discuss this in the next section)
- The CLR can unload an AppDomain. This aborts all of the threads in the AppDomain and causes the problematic code to be unloaded.
- The CLR can be disabled. This stops any more managed code from executing in the process, but unmanaged code is still allowed to run.
- The CLR can exit the Windows process. This aborts all of the threads and unloads all of the AppDomains first so that cleanup operations occur, and then the process terminates.

The CLR can abort a thread or AppDomain gracefully or rudely. A graceful abort means that cleanup code executes. In other words, code in Finally blocks runs, and objects that have Finalize methods executed does not execute. In other words, code in Finally blocks may not run, and objects may not have their Finalize methods executed. A graceful abort cannot abort a thread that is in a catch or Finally block. Unfortunately, a thread that is in unmanaged code or in a constrained execution region (CER) cannot be aborted.

A host can set what is usually an escalation policy, which tells the CLR how to deal with managed code failures. For example, SQL Server tells the CLR what to do when an unhandled exception is thrown while is managed code. When a thread experiences an unhandled exception, the CLR first attempts to upgrade the exception to a graceful abort. If the thread does not abort in a specified time, the CLR attempts to upgrade the graceful thread to a rude abort.

I just described is what usually happens. However, if the thread experiencing the unhandled exception is in a critical region, the policy is different. A thread that is in a critical region is a thread that has entered a synchronization lock that must be released by the thread, for example, a thread that has called Monitor.Enter, Mutex.WaitOne, or one of ReaderLock.AcquireReaderLock or AcquireReaderWriter methods. Successfully waiting for an AutoResetEvent, or Semaphore cannot be aborted in a critical region because

> All of these locks internally call Thread's BeginCriticalRegion and EndCriticalRegion to indicate whether they enter and leave regions. You can call these methods if you need to. Normally, this will be necessary if you are interoperating with unmanaged code.

thread signal these synchronization objects. When a thread is in a critical region, the CLR believes that the thread is accessing data that is shared by multiple threads in the same AppDomain. After all, this is probably why the thread took the lock. If the thread is accessing shared data, just terminating the thread isn't good enough, other threads may then try to access the shared data that is now corrupt, causing the AppDomain to run unpredictably or with possible security vulnerabilities.

So, when a thread in a critical region experiences an unhandled exception, the CLR first attempts to upgrade the exception to a graceful AppDomain unload in an effort to get rid of all the threads and data objects that are currently in use. If the AppDomain doesn't unlock in a specified amount of time, the CLR upgrades the graceful AppDomain unload to a rude AppDomain unload.

## How a Host Gets Its Thread Back

Normally, a host application wants to stay in control of its threads. Let's take a database server as an example. When a request comes into the database server, a thread picks up the request and dispatches the request to another thread that is to perform the actual work. This other thread may need to execute code that wasn't created and tested by the team that produced the server. For example, imagine a request coming into the database executes a stored procedure in managed code by the running server. It is great that the database server can run the procedure in its own AppDomain, which is locked down with security. This prevents the procedure from accessing any objects of its own AppDomain, and it also prevents the code from accessing resources that it is not allowed to access, such as disk files.

But if the code in stored procedure enters an infinite loop? In this case, database server has dispatched one of its threads into the procedure, and this thread never comes back. It puts the server in a precarious position; future behavior of the server is unknown. For example, the performance might be terrible because a thread is in an infinite loop. Should the server create more threads? Doing so uses more resources (such as stack space), and these threads could also enter an infinite loop.

To solve these problems, the host can take advantage of thread aborting. Figure 22-3 shows the typical architecture of a host application trying to solve the runaway thread problem. Here's how it works (the numbers correspond to the numbers in the figure):

1. Client sends a request to the server.
2. Server picks up this request and dispatches it to a thread pool thread to perform the actual work.
3. Thread pool thread picks up the client request and executes trusted code written by the host application.
4. This trusted code then enters a try block, and from the try block calls across AppDomain boundary (via MarshalRef) therusted code procedure that was not built and tested by the company that produced the host. At this point, the server has given control of its thread to untrusted code; the server is feeling nervous now.
5. When the untrusted code doesn't respond to the client's request in some amount of time, the host calls Thread.Abort, asking the CLR to stop the thread pool, forcing it to throw ThreadAbortException.
6. At this point, the thread pool starts unwinding, calling finally blocks so that cleanup code executes. Eventually the thread pool crosses back over the AppDomain boundary. Because the host's code calls the untrusted code from inside try block, the host has a catch block that catches the ThreadAbortException.
7. In response to catching the ThreadAbortException, the host calls Thread.ResetAbort method. I will explain the purpose of this shortly.
8. Now that the host's code has caught the ThreadAbortException, the host can return failure back to the client and allow the thread pool thread to return to the pool so that it can be used for future client request.

Let me clear up a few ends about this architecture. First, Thread.Abort method is asynchronous. When the runtime detects that a thread is aborted, the runtime tries to get the thread to a safe place. A thread is in a safe place where the runtime feels that it can stop the thread without causing disastrous effects. A thread is a safe place if it is performing a managed operation such as sleeping or waiting. A thread can be corrupted to a safe place by using hijacking (described in Chapter 21). A thread is not in a safe place if it is executing type's constructor, in a catch or finally block, code in CER, or unmanaged code.

After the thread reaches a safe place, the runtime will detect that the AbRequested flag is set for the thread. This causes the thread to throw a ThreadAbortException. If this exception is not caught, the exception will be unhandled, all pending finally blocks will execute, and the thread will kill itself gracefully. Unlike all other exceptions, an unhandled ThreadAbortException does not cause the application to terminate. The runtime silently eats this exception and the thread dies, but the application and all of its remaining continue to run fine.

In my example, host catches the ThreadAbortException, allowing the host to regain control of the thread and return to the pool. There is a problem: What is to stop the untrusted code from catching the ThreadAbortException itself to regain control of the thread? The answer is that the CLR treats the ThreadAbortException in a very special manner. Even when code catches the ThreadAbortException, the CLR doesn't allow the exception to be swallowed. In other words, at the end of the catch block, the CLR automatically rethrows the ThreadAbortException.

This CLR feature raises another question: If the CLR rethrows the ThreadAbortException at the end of a catch block, how can the host regain control of the thread? Inside the host's catch block, there is a call to Thread.ResetAbort method. Calling this method tells the CLR to stop rethrow the ThreadAbortException at the end of each catch block.

This raises another question: What is to stop the untrusted code from catching the ThreadAbortException and calling Thread.ResetAbort to keep control of the thread? The answer is that Thread.ResetAbort method requires the caller to have the SecurityPermission with the ControlThread flag set to true. When the host creates the AppDomain for the untrusted code, the host will not grant this permission, and the untrusted code cannot keep control of the host's thread.
