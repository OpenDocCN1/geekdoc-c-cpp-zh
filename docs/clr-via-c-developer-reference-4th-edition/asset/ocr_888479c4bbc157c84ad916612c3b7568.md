# Table 1-1 describes the parts of a managed module.

| TABLE 1-1 Parts of a Managed Module |
| Part | Description |
| PE32 or PE32+ header | The standard Windows PE header, which is similar to the Common Object Format (COFF) header. If the header uses the PE32 format, the file can run on a 32-bit or 64-bit Windows. If the header uses the PE32+, it requires a 64-bit version of Windows to run. This header indicates the type of file: EXE or DLL, and contains a time stamp indicating when the file was built. For managed modules, the code of the information in the PE32+ header is ignored. For modules that contain native CPU code, this header contains information about the native CPU code. |
| CLR header | Contains the information (interpreted by the CLR and utilities) that makes this managed module. The header includes the version of the CLR required, some of metadata tokens of the managed module's entry point method (Main), and the location/size of the managed module's resources, string name, some flags, and other interesting stuff. |
| Metadata | Every managed module contains metadata. There are two main types of tables: tables that describe the types and members defined in your source code and tables that describe the types and members referenced by your source code |

The compiler produced it the source code. At runtime, the CLR compiles the IL into native instructions.

Native code producers produce code targeted to a specific CPU architecture, such as x86, x64, or ARM. All CLR-compliant compilers produce IL code instead (I'll go into more detail about IL later in this chapter). IL code is referred to as *managed code* when the CLR manages its execution.

In addition to emitting IL, every compiler the CLR is required to emit **metadata** into every managed module. In brief, metadata is a set of data tables that describe what is defined in the module, such as types and their members. In addition, metadata also has tables indicating the managed module references, such as imported types and members. Metadata is a subset of older technologies like COM's Type Libraries and Interface Definition Language (IDL) files. The important thing to note is that CLR metadata is far more complete. And, unlike Type Libraries and IDL, metadata is always associated with the file that contains the IL code. In fact, the metadata is embedded in the same EXE/DLL, making it impossible to separate the two. The compiler produces the metadata and the code at the same time and binds them into the resulting managed module, the metadata and the IL code are out of sync with one another.

Metadata has many uses. Here are some of them:

+   - Metadata removes the need for native C/C++ header and library files when compiling because the information about the referenced types/members is contained in the file that has the IL that implements the type/members. Compilers can read metadata directly from managed modules.
- Microsoft Visual Studio uses metadata to help you write code. Its IntelliSense feature parses metadata to tell you what methods, properties, events, and fields a type offers, and in the case of a method, what parameters the method expects.
