However, constructing the EventHandler delegate object is required for the CLR this object provides a wrapper that ensures the method can be called only in a type-safe fashion. The wrapper also allows the calling of instance methods and chaining. Unfortunately, most programmers don't want to think about these details. Programmers prefer to write the preceding code as follows.

```
button1.Click += button1Click;
```

Fortunately, Microsoft's C# compiler offers programmers some syntax shortcuts when working with delegates. I'll explain all of these shortcuts in this section. Last one point before we begin: I'm about to describe really boils down to C# syntactic sugar; these new syntax shortcuts are really just giving programmers an easier way to produce the IL that is generated so that the CLR and other programming languages can work with delegates. This also means that I'm about to describe specific to C#; other compilers might not offer the additional delegate syntax shortcuts.

# Syntactical Shortcut #1: No Need to Construct a Delegate Object

As demonstrated already, C# allows you to specify the name of a callback method without having to construct a delegate object wrapper. Here is another example.

```
internal sealed class ACClass {
    public static void CallbackWithoutNewingADlegateObject() {
        ThreadPool.QueueUserWorkItem(SomeAsyncTask, S);
    }

    private static void SomeAsyncTask(Object o) {
        Console.WriteLine(o);
    }
}
```

Here, the ThreadPool class's static QueueUserWorkItem method expects a reference to a WaitCallback delegate object that contains a reference to the SomeAsyncTask method. Because the C# compiler is capable of inferring this on its own, it allows me to code that constructs the Wait-Callback delegate object, making the code much more readable and understandable. Of course, when the code is compiled, the C# compiler does produce IL that, in fact, new up the Wait-Callback delegate object—we just got a syntactical shortcut.
