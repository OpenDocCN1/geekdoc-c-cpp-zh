# Generic Infrastructure

Generics were added to version 2.0 of the CLR, and it was a major task that required many people working for quite some time. Specifically, to make generics work, Microsoft had to do the following:

- Create new Intermediate Language (IL) instructions that are aware of type arguments.
- Modify the format of exporting metadata tables so that type names and methods with generic parameters could be expressed.
- Modify the various programming languages (C#, Microsoft Visual Basic .NET, etc.) to support the new syntax, allowing developers to define and reference generic types and methods.
- Modify the compilers to emit the new IL instructions and the modified metadata format.
- Modify the just-in-time (JIT) compiler to process the new type-argument-aware IL instructions that produce correct native code.
- Create new reflection members so that developers can query types and determine if they have generic parameters. Also, new reflection members had to be defined so that developers could create generic type and method definitions at runtime.
- Modify the debugger to show and manipulate generic types, members, fields, and local variables.
- Modify the Microsoft Visual Studio IntelliSense to show specific member prototypes when using a generic type or a method with a specific data type.

Now let's spend some time discussing how the CLR handles generics internally. This information could impact how you architect and design a generic algorithm. It could also impact your decision to use an existing generic algorithm or not.

# Open and Closed Types

In various chapters throughout this book

When code references a generic type, it can specify a set of generic type arguments. If actual data types are passed in for all of the arguments, the type is called a closed type, and the CLR allows instances of a closed type to be constructed. However, it is possible for code referencing a generic type to leave some generic arguments unspecified. This creates a new open type object in the CLR, and instances of this type cannot be created. The following code should make this clear.

```cs
using System;
using System.Collections.Generic;
```

```cs
// A partially specified open type
internal sealed class DictionaryKey<TValue> {
    Dictionary<String, TValue> dict;
}
```

```cs
public static class Program {
    public static void Main() {
        Object o = null;
        // Dictionary<,> is an open type having 2 type parameters
        Type t = typeof(Dictionary<,>);

        // Try to create an instance of this type (fails)
        try {
            o = Activator.CreateInstance(t);
        } catch (ArgumentException e) {
            Console.WriteLine(e.Message);
        }

        // DictionaryKey<> is an open type having 1 type parameter
        Type t2 = typeof(DictionaryKey<>);

        // Try to create an instance of this type (fails)
        try {
            o = Activator.CreateInstance(t2);
        } catch (ArgumentException e) {
            Console.WriteLine(e.Message);
        }

        // DictionaryKey<Guid> is a closed type
        Type t3 = typeof(DictionaryKey<Guid>);

        // Try to create an instance of this type (succeeds)
        o = Activator.CreateInstance(t3);
        // Prove it actually worked
        Console.WriteLine("Object type=" + o.GetType());
    }

    private static Object CreateInstance(Type t) {
        Object o = null;
        try {
            o = Activator.CreateInstance(t);
            Console.Write("Created instance of " + t.ToString());
        } catch (ArgumentException e) {
            Console.WriteLine(e.Message);
        }
        return o;
    }
}
```

When I compile the preceding code and run it, I get the following output:

Cannot create an instance of System.Collections.Generic.Dictionary`2[,,] because GenericParameters is true.
Cannot create an instance of DictionaryKey<TValue> because GenericParameters is true.
Created instance of DictionaryKey<Guid>.

As you see, Activator.CreateInstance throws an ArgumentException when you ask to construct an instance of a type. In fact, the exception's message indicates that the type contains some generic parameters. In the output, you'll notice the type names end with a backtick (`) followed by a number. The number indicates the type's arity, which indicates the number of type parameters required by the type. For example, Dictionary<,> has an arity of 2 because it requires types to be specified for TKey and TValue. DictionaryKey<> has an arity of 1 which requires just one type to be specified for TValue.

I should also point out that the CLR allocates fields inside the type object (discussed in Chapter 4, "Type Fundamentals"). So each closed type has its own fields. In other words, if List<T> defines fields, these fields are not shared between List<DateTime> and List<String>; each closed type has its own fields. Also, if a generic type defines a constructor (discussed in Chapter 8, "Methods"), that constructor will execute once per closed type. Sometimes people define a constructor in a generic type to ensure that the arguments meet certain criteria. For example, if you wanted to define a generic type that can be used only with enumerated types, you could do the following:

```cs
internal sealed class GenericTypeRequiresEnum<T> {
    static GenericTypeRequiresEnum() {
        if (!typeof(T).IsEnum)
            throw new ArgumentException("T must be an enumerated type");
    }
}
```

The CLR has a feature called constraints that offers a better way to define a generic type indicating what type arguments are valid for. I'll discuss constraints later in this chapter. Unfortunately, constraints do not support the ability to limit a type argument to enumerated types only, which is why the previous example requires a constructor to ensure that the type is an enumerated type.

# Generic Types and Inheritance

A generic type is, like that, can be derived from any other type. When you use a generic type and specify type arguments, you are defining a new type object in the CLR, and the new type object is derived from whatever the generic type was derived from. In other words, because List<T> is derived from Object, List<String> and List<Guid> are also derived from Object. Similarly, Dictionary<StringKey,Value> is derived from Dictionary<String, Value>, Dictionary<StringKey,Guid> is also derived from Dictionary<String, Guid>. Understanding that specifying type arguments has nothing to do with inheritance hierarchies will help you to recognize what kind of class you can and can't

For example, if a linked-list class is defined like this:

```cs
internal sealed class Node<T> {
    public T m_data;
    public Node<T> m_next;

    public Node(T data) : this(data, null) {
    }

    public Node(T data, Node<T> next) {
        m_data = data; m_next = next;
    }

    public override String ToString() {
        return m_data.ToString() + ((m_next != null) ? m_next.ToString() : String.Empty);
    }
}
```

then I can write code to build up a linked list that would look something like the following:

```cs
private static void SameDataLinkedList() {
    Node<Char> head = new Node<Char>('C');
    head = new Node<Char>('B', head);
    head = new Node<Char>('A', head);
    Console.WriteLine(head.ToString()); // Displays "ABC"
}
```

In the Node class shown, the m_next field must refer to another node that has the same kind of type in its m_data field. This means the linked list must contain nodes in which all data items are of the same type (or derived type). For example, I can't use the Node class to create a linked list in which one element contains Char, another element contains DateTime, and another contains String. Well, I could use Node<Object> everywhere, but then I would lose compile-time safety, and value types would get boxed.

So a better way to go would be to define a non-generic base class and then define a generic TypedNode (using Node as a base). Now, I can have a linked list in which each node is of a specific type (not Object), avoid the boxing of value types. Here are the new class definitions:

```cs
internal class Node {
    protected Node m_next;

    public Node(Node next) {
        m_next = next;
    }
}

internal sealed class TypedNode<T> : Node {
    public T m_data;

    public TypedNode(T data) : this(data, null) {
    }

    public TypedNode(T data, Node next) : base(next) {
        m_data = data;
    }

    public override String ToString() {
        return m_data.ToString() +
        (m_next != null) ? m_next.ToString() : String.Empty;
    }
}
```
