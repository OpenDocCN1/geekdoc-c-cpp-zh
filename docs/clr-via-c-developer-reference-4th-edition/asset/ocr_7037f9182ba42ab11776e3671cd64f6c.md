# The Barrier.Threading Class

The System.Barrier construct is designed to solve a very rare problem, so it is unlikely that you will have a use for it. Barrier is used to control a set of threads that are working in parallel so that they can step through phases of an algorithm together. Perhaps an example in order: when the CLR is using the server version of its garbage collector (GC), the GC algorithm creates one per core. Threads walk up different application stacks, concurrently marking objects in the heap. As each thread completes its portion of the work, it must stop waiting for the other threads to complete their portion of the work. After all have marked the objects, then the threads can compact different portions of the heap concurrently. As each thread finishes compacting the portion of the heap, the thread must block waiting for the other threads. After all the threads have finished compacting the portion of the heap, then all the threads walk up the application's threads, fixing up roots to the root of the newly compacted object. Only after all the threads have completed this work is the garbage collector considered and the application's threads can be resumed.

This scenario is easily solved using the Barrier class, which looks like this (method shown below):

```
public class Barrier {
    public Barrier(Int32 participantCount, Action<Barrier> postPhaseAction);
    public void Dispose();
    public Int64 AddParticipants(Int32 participantCount); // Adds participants
    public void RemoveParticipants(Int32 participantCount); // Subtracts participants
    public bool SignalAndWait(Int32 milliseconds, CancellationToken cancellation);

    public Int64 CurrentPhase { get; } // Indicates phase in process (starts at 0)
    public Int32 ParticipantCount { get; } // Number of participants
    public Int32 ParticipantsRemaining { get; } // # of threads needing to call SignalAndWait();
}
```

When you create a Barrier, you tell it how many threads are participating in the work, and you can also pass an Action<Barrier> delegate referring to code that will be invoked whenever all participants complete a phase of the work. You can dynamically add and remove participating threads from the Barrier by calling AddParticipant and RemoveParticipant methods, but in practice, this is rarely done. As each thread completes its portion of the work, it calls Signal-AndWait, which tells the Barrier the thread is done and the Barrier blocks the thread (using a ManualResetEventSlim). After all participants call SignalAndWait, the Barrier invokes a delegate (the last thread that called SignalAndWait) and unblocks the waiting threads so they can get the next phase.
