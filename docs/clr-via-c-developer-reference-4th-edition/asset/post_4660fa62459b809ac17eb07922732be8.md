
```csharp
public void EventRaised(Object sender, EventArgs eventArgs) {
    m_events.Enqueue(eventArgs); // Save EventArgs to return it from GetResult/await

    // If there is a pending continuation, this thread takes it
    Action continuation = Interlocked.Exchange(ref m_continuation, null);
    if (continuation != null) continuation(); // Resume the state machine
}
```

# Async Functions and Event Handlers

Async functions usually have a return type of either Task or Task<TResult> to represent the completion of the function's state machine. However, it is also possible to define an async function with a void type. This is a special case that the C# compiler allows to simplify the common scenario where you want to implement an asynchronous event handler.

Almost all event handler methods adhere to a method signature similar to this.

```csharp
void EventHandlerCallback(Object sender, EventArgs e);
```

But, it is common to perform I/O operations inside an event handler, when a user clicks to open a file and read from it. To keep the UI responsive, this I/O should be done asynchronously. Allowing you to write this code in an event handler method that has a void return type requires that the C# allows async functions to have a void return type so you can use await to perform non-blocking I/O operations. When an async function has void return type, the compiler generates code to create the state machine but it does not create a Task object because there is no way that could be used. Because of this, there is no way to know when the state machine of a void-returning async function has run to completion.⁵

# Async Functions in the Framework Class Library

Personally, I love async functions because they are easy to learn, simple to use, and they are supported by many types in the FCL. It is easy to identify async functions because, by convention, Async is suffixed to the method's name. In the Framework Class Library (FCL), many of the types offer I/O operations over xxxAsync methods.⁶ Here are some examples.

- All the System.IO.Stream-derived classes offer ReadAsync, WriteAsync, FlushAsync, and CopyToAsync methods.
- All the System.IO.Text-derived classes offer ReadAsync, ReadAsync, ReadToEndAsync, and ReadTextBlock methods. And the System.IO.Text-derived classes offer WriteAsync, LineAsync, and FlushAsync methods.
- The System.Net.Http.HttpClient class offers GetAsync, GetStreamAsync, GetByteArrayAsync, PutAsync, DeleteAsync, and more.
- The System.Net.WebRequest-derived classes (including FileWebRequest, FWebRequest, and HttpWebRequest) offer GetStreamAsync and GetResponseAsync.
- Tools (as SvcUtil.exe) that produce web proxies also offer xxxAsync methods.

> ⁵For this reason, if you try to mark your entry point method (Main) as async, the C# compiler issues the following error: an entry point cannot be marked with 'async'. If you put any await operators in your Main method then your process would return from Main as soon as the first await executes. But because code that calls Main can't get the task, it cannot monitor and wait for it to complete, the process will just terminate (because you're returning from Main), and the rest of the code in Main would never execute at all. Fortunately, the C# compiler includes this error to prevent you from returning an async.

> ⁶WinRT methods follow the same naming convention and returning IAsyncInfo interface. The .NET Framework provides extension methods that effectively cast IAsync to a Task. For more information about using asynchronous WinRT APIs with async functions, see Chapter 25, "Interoperating with WinRT Components."

For anyone has been working with earlier versions of the .NET Framework, you may be familiar with some other asynchronous programming models that it offered. There is the programming model that used BeginXx and EndXx methods along with an IAsyncResult interface. There is the event-based programming model that also had XxxAsync methods (that did not return Task objects) and invoked event handler methods when an asynchronous operation completed. These two asynchronous programming models are now considered obsolete and the new model using Task is the preferred model.

While looking through the FCL, you might notice some classes that are lacking XxxAsync methods and instead offer BeginXx and EndXx methods. This is mostly due to Microsoft not having the time to update these classes with the new methods. In the future, Microsoft will be enhancing these classes so that they fully support the new model. However, until then, there is a helper method that you can use to adapt the BeginXx and EndXx model to the new Task-based model.

Earlier I showed the code for a client that makes a request over a named pipe. Let me show the server side of this code now.

```csharp
private async void StartServer() {
    while (true) {
        var pipe = new NamedPipeServerStream(pipeName, PipeDirection.InOut, -1,
        PipeTransmissionMode.Message, PipeOptions.Asynchronous | PipeOptions.WriteThrough);
        // asynchronously connect a client connection
        // NOTE: NamedPipeServerStream uses the old Asynchronous Programming Model (APM)
        // I convert the old APM to the new model via TaskFactory's FromAsync method
        await Task.Factory.FromAsync(pipe.BeginWaitForConnection, pipe.WaitForConnection, null);
        // Start serving the client, which returns immediately because it is asynchronous
        ServiceClientRequestAsync(pipe);
    }
}
```

The NamedPipeServer class has BeginWaitForConnection and EndWaitConnection methods defined, but it does not have a WaitForConnection method. Hopefully this method will be added in a future version of the FCL. However, all is not lost, because as you see in the preceding code, I call TaskScheduler.FromAsync method, passing it into the names of the BeginXx and EndXx methods, and then FromAsync internally creates a Task object that wraps these methods. Now I can use the Task object with the await operator.

For the old event-based programming model, the FCL does not include any helper methods to adapt this model to the new Task-based model. So you have to hand-code how to wrap a WebClient with a Task-CompletionSource so it can be awaited.

```csharp
private static async Task<String> AwaitWebClient(Uri uri) {
    // The System.WebClient supports the Event-based Asynchronous Pattern
    var wc = new System.WebClient();

    // Create the TaskCompletionSource and its underlying Task
    var tcs = new TaskCompletionSource<String>();

    // When a string is downloading, the WebClient raises the
    // DownloadCompleted event, which completes the TaskCompletion
    wc.DownloadStringCompleted += (s, e) => {
        if (e.Cancelled) tcs.SetCancelled();
        else if (e.Error != null) tcs.SetException(e.Error);
        else tcs.SetResult(e.Result);
    };

    // Start the asynchronous operation
    wc.DownloadStringAsync(uri);

    // Now, we can use the TaskCompletionSource's Task and the result as usual
    String result = await tcs.Task;
    // Process the result (if desired)

    return result;
}
```

# Async Functions and Exception Handling

When a Windows device driver is processing an asynchronous I/O request, it is possible for something to go wrong, and Windows will need to inform your application of this. For example, while sending or waiting for bytes to come over the network, a timeout could expire. If the data does not come in time, the device driver will tell you that the asynchronous operation completed with an error. To accomplish this, the device driver posts the completed IRP to the CLR's thread pool and a thread pool completes the Task object with an exception. When your state machine is resumed, the await operator sees that the operation failed and throws this exception.

In Chapter 27, I discussed how Task objects normally throw an AggregateException, and then you would query that exception's InnerExceptions to see the real exception(s) that occurred. However, when using await with a Task, the first inner exception is thrown instead of an AggregateException. This gives you the programming experience you expect. Also, without this, you would have to catch AggregateException through your code, check the inner exception and either handle or re-throw it. It would be very cumbersome.

> For the curious, it is TaskAwaiter's GetResult method that throws the first exception instead of an AggregateException.
