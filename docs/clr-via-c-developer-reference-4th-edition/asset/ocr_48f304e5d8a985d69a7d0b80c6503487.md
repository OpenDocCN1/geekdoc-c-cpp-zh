In the early days of Windows, many processes had maybe 5 or 6 DLLs loaded into them, today, some processes have several hundred DLLs loaded into them. Right now, on my machine, Microsoft Visual Studio has about 470 DLLs loaded into its process space! This means that whenever a new thread is created in Visual Studio, 470 DLL functions must get called before the thread is allowed to do what it was created to. And these 470 functions must be called whenever a thread in Visual Studio dies. Wow—this can seriously affect the performance of creating and destroying threads within a process.¹

Now, we see all the space and overhead that is associated with creating a thread, letting it sit around in the system, and destroying the situation gets worse—now we're going to start talking about context switching. A computer with only one CPU in the band can do only one thing at a time. Therefore, Windows has to share the actual CPU hardware among all the logical (CPUs) that are sitting around in the system.

At any moment in time, Windows assigns one thread to a CPU. That thread is allowed to run for a time-slice(sometimes referred to as a quantum). When the time-slice expires, Windows context switches to another thread. Every context switch requires that Windows performs the following actions:

+   1. Save the values in the CPU's registers to the currently running thread's context structure inside the thread's kernel object.
2. Select one thread from the set of existing threads to schedule next. If this thread is owned by another process, then Windows must also switch the virtual address space seen by the CPU before it starts executing any code or touching any data.
3. Load the values in the selected thread's context structure into the CPU's registers.

After the context switch, Windows executes the thread until its time-slice expires, and then another context switch happens every 30 ms. Context switches are overhead; that is there is no memory or performance benefit that comes from context switches. Windows performs context switching to provide end users with a robust and responsive operating system.

Now, if an application enters into an infinite loop, Windows will periodically preempt that thread, assign a different thread to an actual CPU, and let this thread run for a while. This other thread could be Task Manager's thread and now, the user can use Task Manager to kill the process containing the thread that is in an infinite loop. When doing this, the process dies and all the data it was working on loses their data. Of course, the user doesn't need to reset the machine and reboot, so context switches are provide end users with a much better overall experience at the cost of performance.

> ¹ DLLs produced by C# and most other programming languages do not have a Main in them at all and so managed DLLs will not receive the DLL_THREAD_ATTACH and DLL_THREAD_DETACH notifications improving performance. In addition, unmanaged DLLs can opt out of these by calling the Win32 DisableThreadLibraryCalls function. Unfortunately, many unmanaged developers are not aware of this, so they don't.
