# C#'s Null-Coalescing Operator

C# has an operator called the null-coalescing operator (??), which takes two operands. If the operand on the left is not null, the operand's value is returned. The null-coalescing operator offers a very convenient way to set a variable's default value.

A cool feature of the null-coalescing operator is that it can be used with reference types as well as nullable value types. Here is some code that demonstrates the use of the null-coalescing operator.

```c
private static void NullCoalescingOperator() {
Int32? b = null;

// The following line is equivalent to:
// x = (b.HasValue) ? b.Value : 123;
Int32 x = b ?? "123";
Console.WriteLine(x); // "123"

// The following line is equivalent to:
// String temp = GetFileName();
// filename = (temp == null) ? "Untitled" : temp;
String filename = GetFileName() ?? "Untitled";
}
```

Some people argue that the null-coalescing operator is simply syntactic sugar for the ? : operator, and the C# compiler team should not have added this operator to the language. However, the null-coalescing operator offers two significant syntactic improvements. The first is that the ?? operator works better with expressions.

```csharp
Func<String> f = () => SomeMethod() ?? "Untitled";
```

This code is much easier to read and understand the following line, which requires variable assignments and multiple statements.

```csharp
Func<String> f = () => { var temp = SomeMethod();
return temp != null ? temp : "Untitled";};
```

The second improvement is that ?? works better in composition scenarios. For example, the following single line:

```csharp
String s = SomeMethod1() ?? SomeMethod2() ?? "Untitled";
```

is far easier to read and understand this chunk of code.

```csharp
String s;
var sm1 = SomeMethod1();
if (sm1 != null) s = sm1;
else {
    var sm2 = SomeMethod2();
    if (sm2 != null) s = sm2;
    else s = "Untitled";
}
```

# The CLR Has Special Support for Nullable Value Types

The CLR has built-in support for nullable value types. This special support is provided for boxing, unboxing, calling GetType(), calling interface methods, and is given to nullable types to make them fit seamlessly into the CLR. This also makes them behave more naturally and as most developers expect. Let's take a closer look at the CLR's special support for nullable types.

# Boxing Nullable Value Types

Imagine a Nullable<Int32> variable that is logically set to null. If this variable is passed to an expecting Object, the variable must be boxed, and a reference to the Nullable<Int32> is passed to the method. This is not ideal because the method is now passing a non-null value even when the Nullable<Int32> variable logically contains the value of null. To fix this, the CLR executes some special code when boxing a nullable value to keep the illusion that nullable types are first-class citizens in the environment.

Specifically, when the CLR is boxing a Nullable<T> instance, it checks to see if it is null, and so, the CLR doesn't box anything, and null is returned. If the nullable instance is not null, the CLR takes the value out of the nullable instance and boxes it. In other words, a Nullable<Int32> with a value of 5 is boxed into a boxed-Int32 with a value of 5. Here is some code that demonstrates this behavior.

```csharp
// Nullable<T> is null or boxed T
Int32? n = null;
Object o = n; // o is null
Console.WriteLine("o={0}", o == null); // "True"

n = 5;
o = n; // o refers to a boxed Int32
Console.WriteLine("o's type={0}", o.GetType()); // "System.Int32"
```

# Unboxing Nullable Types

The CLR allows a boxed value type T to be unboxed into a T or Nullable<T>. If the reference to the boxed value type is null, and you are unboxing to a Nullable<T>, the CLR sets Nullable<T>'s value to null. Here is some code to demonstrate this behavior.

```csharp
// Create a boxed Int32
Object o = 5;

// Unbox it into a Nullable<Int32> and into Int32
Int32 a = (Int32)o; // a = 5
Int32 b = (Int32)o; // b = 5

// Create a reference initialized to null
o = null;

// "Unbox" it into a Nullable<Int32> and into Int32
a = (Int32)o; // a = null
b = (Int32)o; // NullReferenceException
```

# Calling GetType via a Nullable<T>

When calling GetType on a Nullable<T> object, the CLR actually lies and returns the type T instead of the type Nullable<T>. Here is some code that demonstrates this behavior.

```csharp
Int32? x = 5;

// The following line displays "System.Int32", not "System.Nullable<Int32>"
Console.WriteLine(x.GetType());
```

# Calling Interface Methods via a Nullable Type

In the following code, I'm casting n, a Nullable<Int32>, to IComparable<Int32>, an interface type. However, the Nullable<T> type does not implement the IComparable<Int32> interface as Int32 does. The C# compiler allows this code to compile anyway, and the CLR's verifier considers this code valid to allow you a more convenient syntax.

```csharp
Int32? n = 5;
Int32 result = ((IComparable)n).CompareTo(5); // Compiles & runs OK
Console.WriteLine(result);
// 0
```

If the CLR didn't provide this support, it would be cumbersome to call an interface method on a nullable value type. You'd have to cast the unboxed value type first before casting it to the interface to make the call.

```csharp
Int32 result = ((IComparable)(Int32)n).CompareTo(5); // Cumbersome
```
