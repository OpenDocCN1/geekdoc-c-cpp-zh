> If you attempt to remove a method that was never added, then Delegate's Remove method internally does nothing. That is, you get no exception or warning of any type; the event's collection of methods remains unchanged.

> The add and remove methods use a well-known pattern to update a value in a thread-safe way. This pattern is discussed in the “The Interlocked Anything Pattern” of Chapter 29.

In this example, the add and remove methods are public. The reason they are public is that the original line of source code declared the event to be public. If the event had been declared protected, the add and remove methods generated by the compiler would also have been declared protected. So, when you define an event in a type, the accessibility determines what code can register and unregister in the event, but only the type itself can access the delegate field. Event members can also be declared static or virtual, in which case the add and remove methods generated by the compiler would be either static or virtual.

In addition to emitting the aforementioned three constructors, compilers emit an event definition into the managed assembly's metadata. This entry contains some flags and the delegate type, and refers to the add and remove access methods. This information exists simply to draw an association between the abstract concept of an “event” and its access methods. Compilers and other tools can use this metadata, and this information can also be obtained by the System.Reflection.EventInfo class. However the CLR doesn't use this metadata and requires only the access methods at run time.
