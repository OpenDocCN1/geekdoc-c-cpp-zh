
# Implementing a Simple Spin Lock

The Interlocked methods are great, but they mostly operate on Int32 values. If you need to manipulate a bunch of fields in a class object atomically? In this case, we need a way to stop all threads but not one entering the region of code that manipulates the fields. Using Interlocked methods, we can build a thread synchronization lock.

```
internal struct SimpleSpinLock {
    private Int32 m_ResourceInUse; // 0=false (default), 1=true

    public void Enter() {
        while (true) {
            // Always set resource to in-use
            // When this thread changes it from not in-use
            if (Interlocked.Exchange(ref m_ResourceInUse, 1) == 0) return;
            // Black magic goes here...
        }
    }

    public void Leave() {
        // Set resource to not in-use
        Volatile.Write(ref m_ResourceInUse, 0);
    }
}
```

Here is a class that shows how to use the SimpleSpinLock.

```
public sealed SomeResource {
    private SimpleSpinLock m_sl = new SimpleSpinLock();

    public void AccessResource() {
        m_sl.Enter();
        // Only one thread at a time can get here to access the resource...
        m_sl.Leave();
    }
}
```

The SimpleSpinLock implementation is very simple. If two threads call Enter at the same time, Interlocked.Exchange ensures one thread changes m_resourceInUse from 0 to 1 and sees m_resourceInUse was 0. This thread returns from Enter so that can continue executing the code in the AccessResource method. The other thread will change m_resourceInUse from 1 to 1. This thread will see that it did not change m_resourceInUse from a 0, and this thread will start spinning continuously, calling Exchange until the first thread calls Leave.

When the first thread is done manipulating the fields of the SomeResource object, it calls Leave, the spinning thread then Volatile.Write and changes m_resourceInUse back to 0. This causes the spinning thread to then change m_resourceInUse from 0 to 1, and this thread now gets to return from Enter so it can access SomeResource object's fields.

You have it. This is a simple implementation of a thread synchronization lock. The big potential problem with this lock is that it spins when there is contention for the lock.

This spinning locks precious CPU time, preventing the CPU from doing other, more useful work. As a result, it should only be used to guard regions of code that execute very quickly.

Spin locks should not typically be used on single-CPU machines, because the thread that holds the lock can't quickly release it if the thread that wants it is spinning. The situation becomes worse if the thread holding the lock is at a lower priority than the thread wanting to get the lock, because now the thread holding the lock may not get a chance to run at all, in a deadlock situation. Windows sometimes boosts a thread's priority dynamically for short periods of time. Therefore, boosting should be disabled for threads that use spin locks; see the PriorityEnabled property of System.Diagnostics.Process and System.Diagnostics.Thread. There are issues related to using spin locks on hyperthreaded machines, too. In an attempt to circumvent these kinds of problems, many spin locks have some additional logic in them; I refer to the additional logic as Black Magic. I'd rather not go into the details of Black Magic because it changes over time as more people study locks and their performance. However, I will say this FCL has a structure, Thread.SpinWait, which encapsulates the state-of-the-art thinking around this Black Magic.

# Putting a Delay in the Thread's Processing

The Black Magic is all about having a thread that wants to pause its execution temporarily so that the thread currently has the resource can execute its code and relinquish the resource. To do this, the SpinWait struct internally calls Thread's static Sleep, Yield, and SpinWait methods. I'll briefly describe these methods in this sidebar.

A thread can tell the system that it does not want to be scheduled for a certain amount of time. This is accomplished by calling Thread's static Sleep method.

```c
public static void Sleep(Int32 milliseconds);
public static void Sleep(TimeSpan timeout);
```

This method causes the thread to suspend itself until the specified amount of time has elapsed. Calling Sleep allows the thread to voluntarily give up the remainder of its time-slice. The system makes the thread not schedulable for approximately the amount of time specified. That's right—if you tell the system to sleep for 100 milliseconds, the thread will sleep approximately that long, but several seconds or minutes more. Remember that Windows is not a real-time operating system. Thread will probably wake you up at the right time, but whether it depends on what is going on in the system.

You can call Sleep and pass the value in System.Threading.Infinite (defined as -1) for the milliseconds parameter. This tells the system not to schedule the thread, and it is not a useful thing to do. It is better to have the thread exit and recover its stack and kernel object. You can pass 0 to Sleep. This tells the system that the calling thread relinquishes the remainder of its current time-slice, and for the system to schedule another thread. However, the system can reschedule the thread that just called Sleep. This will happen if there are no more schedulable threads at the same priority or higher.

A thread can ask Windows to schedule another thread on the current CPU by calling Thread's Yield method.

```csharp
public static Boolean Yield();
```

If Windows has another thread ready to run on the current processor, Yield returns true and the thread that called ended its time-slice, the selected thread gets to run for one time-slice, and then the thread that called Yield is scheduled again and starts with a fresh new time-slice. If Windows does not have another thread to run, then Yield returns false and the thread continues its time-slice.

The Yield method exists in order to give a thread of equal or lower priority that is starving for CPU time a chance to run. A thread calls this method if it wants a resource that is currently owned by another thread. The hope is that Windows will schedule the thread that currently owns the resource and this thread will relinquish the resource. When the thread called Yield runs again, this thread can have the resource.

Yield is a cross between calling Thread.Sleep(0) and Thread.Sleep(1). Thread.Sleep(0) will not let a lower-priority thread run, whereas Thread.Sleep(1) will always force a context switch and Windows will force the thread to sleep longer than one millisecond due to the resolution of the system timer.

Hyperthreaded CPUs rely only one thread at a time. So, when executing sleep loops on these CPUs, you must force the current thread to pause so the CPU switches to the other thread, allowing it to run. A thread can force itself to pause, allowing a hyperthreaded CPU to switch to other by calling Thread's SpinWait method.

```csharp
public static void SpinWait(Int32 iterations);
```

Calling this method actually executes a special CPU instruction; it does not tell Windows to do anything (because Windows already thinks that it has scheduled threads on the CPU). On a non-hyperthreaded CPU, this special instruction is simply ignored.

> For more information about these methods, see their Win32 equivalents: SwitchToThread, and YieldProcessor. You can also learn more about adjusting the resolution of the system timer by looking up the Win32 timeBeginPeriod and timeEndFunctions.
