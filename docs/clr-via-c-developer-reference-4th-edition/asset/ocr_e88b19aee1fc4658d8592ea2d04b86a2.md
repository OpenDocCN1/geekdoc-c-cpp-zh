executes, the best way for you to load an assembly is to use Assembly's ReflectionOnlyFrom
method, or in some rarer cases, Assembly's ReflectionOnlyLoad method. Here are the prototypes
of both methods.

```
public class Assembly {
    public static Assembly ReflectionOnlyLoad(String assemblyFile);
    public static Assembly ReflectionOnlyLoad(String assemblyString);
    // commonly used overload of ReflectionOnlyLoad is not shown
}
```

The ReflectionOnlyLoad method will load the file by the path; the strong-
ame of the identity is not obtained, and the file is not searched in the GAC or elsewhere.
The ReflectionOnlyLoad method will search for the specified assembly in the GAC,
application base directory, private paths, and codebases. However, unlike the Load method,
ReflectionOnlyLoad method does not apply versioning policies, so you will get the exact
that you specify. If you want to apply versioning yourself to an assembly identity, you can pass
t string into AppDomain's ApplyPolicy method.

When an assembly is loaded with ReflectionOnlyFrom or ReflectionOnly, the CLR
forbids any code from executing; any attempt to execute code in an loaded assembly
ither of these methods causes the CLR to throw an InvalidOperation. These
methods allow to load an assembly that was delay-signed, would normally require security
permissions to prevent it from loading, or were created for a different CPU architecture.

Frequently, using reflection to analyze an assembly loaded with one of these two methods,
t code will have to register a callback method with AppDomain's ReflectionOnlyAssembly-
Resolve event to manually load any referenced assemblies (calling AppDomain's ApplyPolicy
method, if desired); the CLR doesn't do it automatically for you. When the callback is invoked,
it must call Assembly's ReflectionOnlyLoadFrom or ReflectionOnlyLoad method to explicitly
load referenced assembly and return a reference to this.

> Note people often ask about assembly unloading. Unfortunately, the CLR doesn't support
t ability to unload individual assemblies. If the CLR allowed it, your application would
cash if a thread returned from a method code to the unloaded assembly. The CLR
is all about robustness, security, and allowing an application to crash in this way would be
counterproductive to its goals. If you want to unload an assembly, you must unload the
entire AppDomain that contains. This was discussed in great detail in Chapter 22.

It would seem that assemblies loaded with either ReflectionOnlyLoadFrom or
ReflectionOnlyLoad method could be unloaded. After all, in these assemblies is not
al to execute. However, the CLR also doesn't allow assemblies loaded via either
these two methods to be unloaded. The reason is that after an assembly is loaded this way,
you still use reflection to create objects that refer to the metadata defined inside these
assemblies. Unloading the assembly would require the objects to be invalidated somewhat.
Keeping this track would be too expensive in terms of implementation and execution
speed.
