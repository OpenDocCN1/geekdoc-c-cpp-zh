
The System.TypeInfo offers the following instance members: DeclaredNestedTypes and GetDeclaredNestedType.

The System.Reflection.Assembly offers the following instance members: GetType, DefinedTypes, and ExportTypes.

> Note Microsoft has defined Backus-Naur Form grammar for type names and assembly-qualified types that are used for constructing strings that will be passed to reflection methods. Knowledge of the grammar can come in quite handy when you are using reflection, specifically if you are working with nested types, generic types, generic methods, reference parameters, or arrays. For the complete grammar, see the FCL documentation or do a web search for "Backus-Naur Grammar for Type Names." You can also look at Type’s and TypeInfo’s MakeArrayType, MakeByRefType, MakeGenericType, and PointerType methods.

Many programming languages allow an operator that allows you to obtain an Object by a type name that is known at compile time. When possible, you should use this operator to obtain a reference to a Type instead of using any of the methods in the list, because the operator generates faster code. In C#, the operator is called typeof, and you use this operator typically to compare late-bound type information with early-bound (known at compile time) type information. The following code demonstrates an example of its use.

```
private static void someMethod(object o) {
// typeof returns the type of the object at runtime (late-bound)
// typeof returns the type of the specified class (early-bound)
if (o.GetType() == typeof(FileInfo)) { ... }
if (o.GetType() == typeof(DirectoryInfo)) { ... }
}
```

> Note The first statement in the code checks whether the variable o refers to an object of the FileInfo type; it does not check o refers to an object that is derived from the FileInfo type. In other words, the preceding code tests for an exact match, not a compatible match, which is what you would get if you use a cast or C#'s as operators.

As mentioned earlier, a Type object represents a type reference that is a lightweight object. If you want to learn more about the type itself, then you must acquire a TypeInfo object, which represents a type definition. You can convert a Type object to a TypeInfo object by calling System.Reflection.IntrospectionExtensions GetType extension method.

```
Type typeReference = ...; // For example: o.GetType() or typeof(Object)
TypeInfo typeDefinition = typeReference.GetTypeInfo();
```

And, although less useful, you can convert a TypeInfo object to a Type object by calling TypeInfo's AsType method.

```
TypeInfo typeDefinition = ...;
Type typeReference = typeDefinition.AsType();
```

Obtaining a TypeInfo object forces the CLR to resolve the type ensuring that the assembly defines the type is loaded. This can be an expensive operation that can be avoided if you all need references (Type objects). However, after you have a TypeInfo object, you can query any of the type's properties to learn more about it. Most of the properties, such as IsPublic, IsSealed, IsAbstract, IsClass, IsValueType, and so on, indicate flags associated with the type. properties such as AssemblyQualifiedName, FullName, Module, and so, return the name of the type's defining assembly or module and the full name of the type. You can also query the BaseType property to obtain a reference to the type's base type, and a few of members will give you even more information about the type. The FCL documentation describes all of the methods and properties that Type exposes.

# Building a Hierarchy of Exception-Derived Types

The following code uses many of the concepts discussed already in this chapter to load a bunch of assemblies into the AppDomain and display all of the classes that are ultimately derived from System. By the way, this program I wrote to build the exception hierarchy displayed in the "FCL-Derived Exception Classes" section in Chapter 20, "Exceptions and State Management."

```
public static void Go() {
    // Explicitly load the assemblies that we want to reflect over
    LoadAssemblies();

    // Filter & sort all the types
    var allTypes = 
        (from a in AppDomain.CurrentDomain.GetAssemblies()
        from t in a.ExportedTypes
        where typeof(Exception).GetType().IsAssignableFromFrom(t.GetType())
        order by t.Name
        select t).ToArray();

    // Build the inheritance hierarchy tree and show it
    WalkInheritanceHierarchy(new StringBuilder); // Build the inheritance hierarchy tree and show it
    Console.WriteLine(WalkInheritanceHierarchy(new StringBuilder(), 0, typeof(Exception),
    allTypes));
}

private static void WalkInheritanceHierarchy(StringBuilder sb, Int32 indent, Type baseType, IEnumerable<Type> allTypes) {
    String spaces = new string(' ', indent * 3);
    sb.Append(spaces + baseType.FullName);
    foreach (var t in allTypes) {
        if (t.GetType().BaseType != baseType) continue;
        WalkInheritanceHierarchy(sb, indent + 1, t, allTypes);
    }
}
return sb;
```

# Constructing an Instance of a Type

When you have a reference to a Type object, you might want to construct an instance of this. The FCL offers several mechanisms:

- **System.Activator.CreateInstance methods** The Activator class offers several overloads of its static CreateInstance method. When you call this method, you can pass either a reference to a Type or a string that identifies the type. The versions that take a string are a bit more complex. First, you must specify the type and its assembly via parameters. Second, all of these methods return a System.Runtime.Remoting.ObjectHandle.

 ObjectHandle is a type that allows an object created in one AppDomain to be passed to other AppDomains without forcing the object to materialize. When you're ready to materialize the object, you call ObjectHandle's Unwrap method. This method loads the assembly that defines the type being materialized in the AppDomain where it is created. If the object is marshaled by reference, the proxy type and object are created.

- **System.Activator.CreateInstance methods** The Activator class also offers static CreateInstance methods. These methods behave just as the CreateInstance method, except that you must always specify the type and its assembly. The of the CreateFrom methods return an ObjectHandle, which must be unwrapped.

- **System.AppDomain.methods** The AppDomain offers four instance methods (each with several overloads) that construct an instance of a type: CreateInstance, CreateInstanceAndUnwrap, CreateInstanceFrom, and CreateInstanceFromUnwrap. These work just as Activator's methods except that these methods are instance methods, allowing you to specify which AppDomain the object should be constructed in. The methods that end with Unwrap for convenience so that you don't have to make an additional method call.

- **System.Reflection.ConstructorInfo Invoke method** Using a reference to a Type object, you can bind to a particular constructor and obtain a reference to the constructor's ConstructorInfo object. Then you can use the reference to the ConstructorInfo to call its Invoke method. The type is always created in the calling AppDomain, and a reference to the new object is returned. I'll also discuss this method in more detail later in this chapter.

> Note The CLR doesn't require value types define any constructors. However, this is a problem because all of the mechanisms in the preceding list construct an object by calling its constructor. However, Activator's CreateInstance methods will allow to create an instance of a value type without calling a constructor. If you want to create an instance of a value type without calling a constructor, you must call the version of the CreateInstance method that takes a single Type parameter or the version that takes and Boolean parameters.
