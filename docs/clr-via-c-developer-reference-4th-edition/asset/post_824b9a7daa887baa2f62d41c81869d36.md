## Designing Your Exception Class

Unfortunately, designing your own exception is tedious and error prone. The main reason for this is because all Exception-derived types should be serializable so that they can cross an App boundary or to a log or database. There are many issues related to serialization and they are discussed in Chapter 24, "Runtime Serialization." So, in order to simplify things, I made my own generic TExceptionArgs class, which is defined as follows.

```csharp
[Serializable]
public sealed class TExceptionArgs : Exception, ISerializable
    where TExceptionArgs : ExceptionArgs {

    private const string c_args = "Args"; // For (de)serialization
    private readonly TExceptionArgs m_args;

    public TExceptionArgs Args { get; return m_args; }

    public TException(String message = null, Exception innerException = null)
        : this(null, message, innerException) {}

    public TException(TExceptionArgs args, String message = null,
        Exception innerException = null) : base(message, innerException) { args = args; }

    // This constructor is for deserialization; since the class is sealed, the constructor is
    // If this class was not sealed, this constructor must be protected
    [SecurityPermission(SecurityAction.LinkDemanding,
    Flags=SecurityPermissionFlag.SerializationFormatter)]
    private TException(SerializationInfo info, StreamingContext context)
        : base(info, context)
    {
        m_args = (TExceptionArgs)info.GetValue(c_args, typeof(TExceptionArgs));
    }

}
```

```csharp
// This method is for serialization; it's because of the ISerializable interface
[SecurityPermission(SecurityAction.LinkDemanding,
    Flags=SecurityPermissionFlag.SerializationFormatter)]
public override void GetObjectData(SerializationInfo info, StreamingContext context) {
    info.AddValue(c_args, m_args);
    base.GetObjectData(info, context);
}
```

```csharp
public override String Message {
    String baseMsg = base.Message;
    return (m_args == null) ? baseMsg : "(" + m_args.Message + ")";
}
```

```csharp
public override Boolean Equals(Object obj) {
    Exception<TExceptionArgs> other = obj as Exception<TExceptionArgs>;
    if (other == null) return false;
    return Object.Equals(m_args, other.m_args) && base.Equals(obj);
}
public override int GetHashCode() { return base.HashCode(); }
```

And the ExceptionArgs class that TExceptionArgs is constrained to is very simple and looks like this.

```csharp
[Serializable]
public abstract class ExceptionArgs {
    public virtual String DiskPath { return String.Empty; }
}
```

Now, with these classes defined, I can trivially define more exception classes when I need to. To define an exception type indicating the disk is full, I simply do the following.

```csharp
[Serializable]
public sealed class DiskFullExceptionArgs : ExceptionArgs {
    private readonly String m_diskpath; // private field set at construction

    public DiskFullExceptionArgs(String diskpath) { m_diskpath = diskpath; }

    // Read-only property that returns the field
    public String DiskPath { return m_diskpath; }

    // Override the Message property to include my field (if set)
    public override String Message {
        return (m_diskpath == null) ? base.Message : "DiskPath=" + m_diskpath;
    }
}
```

And, if I have no additional data that I want to put inside the class, it gets as simple as the following.

```csharp
[Serializable]
public sealed class DiskFullExceptionArgs : ExceptionArgs { }
```

And now I can write code like this, which throws and catches one of these.

```csharp
public static void TestException() {
  try {
    throw new Exception<DiskFullException>(
      new DiskFullException(@"C:\", "The disk is full")
    );
  } catch (Exception<DiskFullException> e) {
    Console.WriteLine(e.Message);
  }
}
```

> There are two issues to note about my Exception<TException> class. The first issue is that any exception type you define with is always derived from System Exception. In many scenarios, this is not a problem at all and, in fact, having a shallow and wide exception type hierarchy is preferred. ## Trading Reliability for Productivity

I started writing software in 1975. I did a fair amount of BASIC programming, and as I got more interested in hardware, I switched to assembly language. Over time, I switched to C programming language because it allowed me access to hardware with a much higher level of abstraction.

Object-oriented programming allows developers to be very productive. A big part of this is composability which makes it easy to write, read and maintain code. This line of code, for example:

```csharp
Boolean f = "Jeff".Substring(1
```

There is a assumption being made with the preceding code: no errors occur. But, of course, errors are always possible, and so we need a way to handle these errors. This is what the exception handling constructs and mechanisms are all about and why we need them as opposed to having methods that return true/false or an HRESULT to indicate success/failure the way that Win32 COM functions do.

In addition to composability, we are productive for all kinds of great features provided by our compilers. For the compiler implicitly:

-   Inserts optional parameters when calling a method.
-   Boxes value type instances.
-   Constructs/initializes parameter arrays.
-   Binds to members of dynamic variables and expressions.
-   Binds to extension methods.
-   Binds/invokes overloaded operators.
-   Constructs delegate objects.

For some reason that I can't explain, this attention to detail is not done when writing code for the .NET Framework. When allocating memory (using C++'s new operator or calling Heap, VirtualAlloc, etc.), I would always check the return value to ensure that the memory requested was came to me. And, if the memory request failed, I always had an alternate code path ensuring that the rest of the program's state was unaffected and let any of callers know that I failed so they can take corrective measures.

In this section, I'd like to point out some of the potential failures and why it has become culturally acceptable to ignore them. I'd also like to point out some of the significant problems that can occur when ignoring these failures and suggest some ways to help mitigate these problems.
