The SemaphoreSlim class implements this idea via its WaitAsync method. Here is the signature for the most complicated overload of this method.

```
public Task<Boolean> WaitAsync(Int32 millisecondsTimeout, CancellationToken cancellationToken);
```

With this, you can synchronize access to a resource asynchronously (without blocking any thread).

```
private static async Task AccessResource()WithAsyncSynchronization(SemaphoreSlim asyncLock) {
    // TODO: Execute whatever you want here.

    await asyncLock.WaitAsync(); // Request exclusive access to a resource via its lock
    // When we get here, we know that no other thread is accessing the resource
    // TODO: Execute the resource (exclusively).

    // When done accessing resource, relinquish lock so other code can access the resource
    asyncLock.Release();

    // TODO: Execute whatever you want here.
}
```

SemaphoreSlim's WaitAsync method is very useful, but of course, it gives you semaphore semantics. Usually, you'll create the SemaphoreSlim with a maximum count of 1, which gives you mutual-exclusive access to the resource that the SemaphoreSlim protects. This is similar to the behavior you get when using Monitor, except that SemaphoreSlim does not offer ownership and recursion (semantics which it does).

But, what about reader-writer semantics? Well, .NET Framework has a class ConcurrentExclusiveSchedulerPair, which looks like this.

```

    public ConcurrentExclusiveSchedulerPair();
```

An instance of this class comes with two TaskScheduler objects that work together to provide reader/writer semantics when scheduling tasks. Any tasks scheduled using ExclusiveScheduler will execute one at a time, as long as no tasks are running that are using the ConcurrentScheduler. And, any tasks scheduled by the ConcurrentScheduler can all run simultaneously, as long as no tasks are running that scheduled by the ExclusiveScheduler.
