# Setting Thread Limits

The CL allows developers to set a maximum number of threads that the thread pool will create. However, it turns out that thread pools should never place an upper limit on the number of threads in the pool because starvation or deadlock might occur. Imagine queueing 1,000 work items that block on an event that is signaled by the 1,001st item. If you've set a maximum of 1,000 threads, the 1,001st work item will not be executed, and all 1,000 threads will be blocked, forcing users to terminate the application and lose all their work. Also, it is very unusual for developers to artificially limit the resources they have available to their application. For example, if you would start your application and let the system you de restrict the amount of memory that your application can use or limit the amount of network bandwidth that your application can use? Yet, for some reason, developers felt compelled to limit the number of threads that the thread pool can create.

Because customers have starvation and deadlock issues, the CLR team has steadily increased the default maximum of threads that the thread pool can create. The default maximum is now about 1,000 threads, which is effectively limitless a 32-bit process has at most 2 GB of usable address space within. After a bunch of Win32 DLLs load, the CLR DLLs load, the native and managed heap allocated, there is approximately 1.5 GB of address space left over. Each thread requires more than 1 MB of memory for its user-mode stack and environment block (TEB), the most threads you can create in a 32-bit process is about 1,360. Attempting to create more threads than this will result in an OutMemoryException being thrown. Of a 64-bit process offers 8 terabytes of address space, so you could theoretically create hundreds of threads. But allocating anywhere near this number of threads is really just a waste of resources, especially when the ideal number of threads to have is really the number of CPUs in the machine. What the CLR team should do is remove the limits entirely, but they can't do this now because might break some applications that expect thread pool limits to exist.

The System.ThreadPool offers several methods that you can call to manipulate the threads in the thread pool: GetMaxThreads, SetMaxThreads, GetMinThreads, SetMinThreads, and GetAvailableThreads. I highly recommend that you do not call any of these methods. Playing with thread limits usually results in making an application performance worse, not better. If you think your application needs hundreds or thousands of threads, there is something wrong with the architecture of your application and the way that it's using threads. This chapter and Chapter 28 demonstrate the proper way to use threads.

# Worker Threads Are Managed

Figure 27-1 shows the data structures that make up the worker threads' part of the thread pool. The ThreadPool.QueueUserItem method and the Timer class always work items to the global queue. Worker threads pull items from this queue using a first-in-first-out (FIFO) algorithm and process them. Because multiple worker threads can be removing items from the global queue simultaneously, all workers contend on a thread synchronization lock to ensure that two or more threads don't take the same work item. This thread synchronization lock can become a bottleneck in some applications, thereby limiting scalability and performance to some degree.
