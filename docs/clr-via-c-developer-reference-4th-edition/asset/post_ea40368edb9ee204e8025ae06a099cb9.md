
# CLR Threads and Windows Threads

Today, the CLR uses the threading capabilities of Windows, Part V of this book is really focusing on how the threading capabilities of Windows are exposed to developers who write code by using the CLR. I will explain about how threads in Windows work and how the CLR alters the behavior (if it does). Sleep, if you'd like more information about threads, I recommend reading some of my early-writings on the topic, such as *Windows via C/C++, Fifth Edition*, by myself and Christophe Nasarre (Microsoft Press, 2007).

**Note:** Back in the days of the .NET Framework, the CLR team felt that they would someday have logical threads, which did not necessarily map to Windows threads. However, around 2005, this was attempted unsuccessfully, causing the CLR team to give up on the idea. So, a CLR thread is identical to a Windows thread. However, in the .NET Framework, you see the CurrentManagedThread property, which returns the CLR's ID for a thread, although the System.Diagnostics.Thread class exposes an Id property and BeginThreadAffinity and EndThreadAffinity methods were also introduced to deal with the notion that a CLR thread might not map to a Windows thread.

**Note:** For Windows Store apps, Microsoft has removed some APIs related to threading, because the APIs encouraged bad programming practices (discussed in the "Stop the Madness" section of this chapter), or because the APIs did not achieve the goals that Microsoft has set out for Windows Store apps. For example, the whole Thread class is not available in Windows Store apps because it has many bad APIs (as Start, IsBackground, Sleep, Suspend, Join, Interrupt, Alert, BeginThreadAffinity, and EndThreadAffinity). Personally, I think this is great, and I wish it had happened a long time ago. So, in Chapters 26 to 30, I discuss some APIs and features that are available for desktop apps but are not available for Windows Store apps. As you read these chapters, you should be able to easily discern certain APIs are unavailable for Windows Store apps.

# Using a Dedicated Thread to Perform an Asynchronous Compute-Bound Operation

In this section, I will show you how to create a thread and perform it an asynchronous compute-bound operation. Although I am going to walk through this, I highly recommend that you use the technique I show you here. And, in fact, this technique is not even possible if you are building a Windows Store app because the Thread class is not available. Instead, you should use the thread pool to execute asynchronous compute-bound operations whenever possible. I go into the details doing this in Chapter 27, "Compute-Bound Asynchronous Operations."

However, there are some unusual occasions when you might want to explicitly create a thread dedicated to executing a particular compute-bound operation. Typically, you'd want to create a dedicated thread if you're going to execute code that requires the thread to be in a particular state that is not normal for a thread pool thread. For example, explicitly create your thread if any of the following is:

- You need the thread to run with a non-normal thread priority. All thread pools run at normal priority. Although you can change this, it is not recommended, and the priority change does not persist across thread pools.
- You need the thread to behave as a foreground thread, thereby preventing the application from dying until the thread has completed its task. For more information, see the "Foreground Threads vs. Background Threads" section later in this chapter. Thread pools are always background threads, and they may not complete their task if the CLR winds to terminate the process.
- The compute-bound task is extremely long-running. This way, I would not be taxing the thread pool's logic as it tries to figure out where to create an additional thread.
- You want to start a thread and possibly abort it prematurely by calling Thread.Abort (discussed in Chapter 22, "CLR Hosting and AppDomains").

To create a thread, you use an instance of the System.Threading class, passing the name of a method into its constructor. Here is the prototype of Thread's constructor.

```csharp
public sealed class Thread : CriticalFinalizerObject, ... {
    public Thread(ParameterizedThreadStart start);
    // Less commonly constructors are not shown here
}
```

The start parameter identifies the method that the dedicated thread will execute, and this method must match the signature of the ParameterizedThreadStart delegate.

```csharp
delegate void ParameterizedThreadStart(Object obj);
```

Constructing a thread is a relatively lightweight operation because it does not actually create a physical operating system thread. To actually create the operating system thread and have it start executing the callback method, you must call Thread's Start method, passing it into the (state) that you passed as the callback method's argument.

> ^ 4 For the record, the Thread also offers a constructor that takes a ThreadStart delegate that accepts no arguments and returns void. Personally, I recommend using this constructor and delegate because they are more limiting. If your method takes an Object and returns void, then you can invoke it by using a dedicated thread or invoke it using the thread pool (as shown in Chapter 27).

The following code demonstrates how to create a dedicated thread and have it call a method asynchronously.

```csharp
using System;
using System.Threading;

public static class Program {
    public static void Main() {
        Console.WriteLine("Main thread: starting a dedicated thread " +
        "to do an asynchronous operation");
        Thread dedicatedThread = new Thread(ComputeBoundOp);
        dedicatedThread.Start(0);

        Console.WriteLine("Main thread: Doing other work here...");
        Thread.Sleep(10000);

        // Note: Main method calls Join, which causes dedicatedThread to stop
        dedicatedThread.Join();
    }

}

// This method's signature must match the ParameterizedThreadStart delegate
private static void ComputeBoundOp(object state) {
    // This method is executed by a dedicated thread
    Console.WriteLine("ComputeBoundOp: starting work... ");
    // Simulating some work
    Thread.Sleep(2000);
    Console.WriteLine("ComputeBoundOp: finished");
}
```

When I compile and run this code, I get the following output:

```
Main thread: starting a dedicated thread to do an asynchronous operation
Main thread: Doing other work here...
ComputeBoundOp: starting work...
ComputeBoundOp: finished
```

# Reasons to Use Threads

There are two reasons to use threads:

- **Responsiveness (typically for client-side GUI applications):** Windows gives each process its own thread so one application running an infinite loop doesn't prevent the user from working. Similarly within your client-side application, you could spawn some work off to a thread so your GUI remains responsive. In example, you are possibly creating more threads than available, so you are wasting system resources and hurting performance. However, the user is gaining a responsive user interface.
- **Performance (for server side applications):** Because Windows can schedule one thread per CPU and because the CPUs can execute these concurrently, your application can improve its performance by having multiple elements at the same time. Of course, you only get the improved performance if and only your application is running on a machine with multiple CPUs. Today, machines with multiple CPUs are quite common, so designing your application to use multiple cores makes sense.

Now, I like to share with you a theory of mine. Every computer has an incredibly powerful resource inside it: the CPU. If someone spends money on a computer, then that computer should be working all the time. In other words, I believe all the CPUs in a computer should be running at one hundred percent utilization. I will qualify this statement with two caveats. First, you may not want the CPUs running at 100 percent utilization if the computer is on battery power, because that may drain the battery too quickly. Second, some data centers would prefer to have 10 machines running at 50 percent CPU utilization than 5 machines running at 100 percent utilization, because running CPUs at full power to generate heat, which requires systems, and powering an HVAC cooling system can be more expensive than powering more computers running at reduced capacity.

Although data centers find it increasingly expensive to maintain multiple machines, because each has periodic hardware and software upgrades and monitoring, this has to be weighed against the expense of running a cooling system.

Now, if you agree with my theory, the next step is to figure out what the CPUs should be doing. Before I give you my ideas here, let me say something else first. In the past, developers and end users always felt that the computer was not powerful enough. Therefore, developers would never just execute code unless the end users give us permission to do so and indicate that it is OK for the application to consume CPU resources via UI elements, such as menu items, buttons, and check boxes.
