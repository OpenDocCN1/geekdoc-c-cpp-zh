
# Serialization/Deserialization Quick Start

Let's start off by looking at some code.

```csharp
using System;
using System.Collections.Generic;
using System.IO;
using System.Runtime.Serialization.Formatters.Binary;

internal static class QuickStart {
    public static void Main() {
        // Create a graph of objects to serialize to the stream
        var objectGraph = new List<String> { "Jeff", "Kristin", "Aidan", "Grant" };
        Stream stream = SerializeToMemory(objectGraph);

        // Reset everything for this demo
        stream.Position = 0;
        objectGraph = null;

        // Deserialize the objects and prove it worked
        objectGraph = (List<String>)DeserializeFromMemory(stream);
        foreach (var s in objectGraph) Console.WriteLine(s);
    }

    private static MemoryStream SerializeToMemory(Object objectGraph) {
        // Construct a stream that is to hold the serialized objects
        MemoryStream stream = new MemoryStream();

        // Construct a serialization formatter that does all the hard work
        BinaryFormatter formatter = new BinaryFormatter();

        // Tell the formatter to serialize the objects into the stream
        formatter.Serialize(stream, objectGraph);

        // Return the stream of serialized objects back to the caller
        return stream;
    }

    private static Object DeserialFromMemory(Stream stream) {
        // Construct a serialization formatter that does all the hard work
        BinaryFormatter formatter = new BinaryFormatter();

        // Tell the formatter to deserialize the objects from the stream
        return formatter.Deserialize(stream);
    }
}
```

Wow, look how simple this is! The SerializeToMemory method constructs a System.MemoryStream object identifies which serialized blocks of bytes is to be. Then the method constructs a BinaryFormatter object (which can be found in the System.Runtime.Serialization.Binary namespace). A formatter is a type that knows how to serialize and deserialize an object. The Framework Class Library (FCL) provides System.Runtime.Serialization.Formatter interface with two formatters: the BinaryFormatter (used in this code example) and a SoapFormatter (which can be found in the System.Runtime.Serialization.Formatters.Soap namespace and is implemented in the System.Runtime.Serialization.Formatters.Soap.dll assembly).

> As of version 3.5 of the .NET Framework, the SoapFormatter class is obsolete and should not be used in production code. However, it can be useful for debugging-serialization code it produces XML text that you can read. To use XML serialization and deserialization in production code, see the XmlSerializer and DataContractSerializer classes.

To serialize a graph of objects, just call the formatter's Serialize method and pass two things: a reference to a stream object and a reference to the object graph that you want to serialize. The stream identifies where the serialized bytes should be placed and can be an object of any type derived from the System.IO.Stream abstract class. This means that you can serialize an object graph to MemoryStream, a FileStream, a NetworkStream, and so on.

The second parameter to Serialize is a reference to an object. This object could be anything: an Int32, a String, a DateTime, an Exception, a List<String>, a Dictionary<Int32, DateTime>, and so on. The object referred to by the objectGraph parameter may refer to other objects. For example, objectGraph may refer to a collection that refers to a set of objects. These objects may refer to other objects. When the formatter's Serialize method is called, all objects in the graph are serialized to the stream.

Formatters know how to serialize the complete graph by referring to the metadata that describes each object's type. The Serialize method uses reflection to see what instance fields in each object's type are serialized. If any of these fields refer to other objects, then the formatter's Serialize method knows how to serialize these objects, too.

Formatters have very intelligent algorithms. They know to serialize each object in the graph no more than once to the stream. That is, if two objects in the graph refer to each other, then the formatter detects this, serializes each object once, and avoids entering an infinite loop.

In my SerializeToMemory method, when the formatter's Serialize method returns, the MemoryStream is simply returned to the caller. The application uses this flat byte array it wants. For example, it could save it in a file, copy it to the clipboard, send it over a wire, or whatever.

The DeserializeFromStream method deserializes a stream back into an object graph. In this code, BinaryFormatter is constructed and then its Deserialize method is called. This method takes the stream as a parameter and returns a reference to the root object within the deserialized object graph.

Internally, the formatter's Deserialize method examines the contents of the stream, constructs instances of all the objects that are in the stream, and initializes the fields in these objects so that they have the same values as they had when the object graph was serialized. Typically, you will have the object reference returned from the Deserialize method into the type that your application is expecting.

> **Note** Here's a useful method that uses serialization to make a deep copy, or clone, of an object.

```csharp
private static object DeepClone(Object original) {
    // Construct a temporary memory stream
    using (MemoryStream stream = new MemoryStream()) {
        // Construct a serialization formatter that does all the hard work
        BinaryFormatter formatter = new BinaryFormatter();

        // This line is explained in this chapter
        // Serialize the object graph into the stream
        formatter.Serialize(stream, original);

        // Seek back to the start of the memory stream
        stream.Position = 0;

        // Deserialize the graph (deep copy) to the caller
        return formatter.Deserialize(stream);
    }
}
```

At this point, I'd like to add a few notes to our discussion. First, it is up to you to ensure that your code uses the same formatter for serialization and deserialization. For example, let's say that we have the following class definitions.

```csharp
[Serializable] internal class Customer { /* ... }
[Serializable] internal class Order { /* ... }
```

And then, in the main class of our application, we define the static fields.

```csharp
private static List<Customer> s_customers = new List<Customer>();
private static List<Order> s_pendingOrders = new List<Order>();
private static List<Order> s_processedOrders = new List<Order>();
```

We can now serialize our application state to a single stream with a method that looks like this.

```csharp
private static void SaveApplicationState(Stream stream) {
    // Construct a serialization formatter that does all the hard work
    BinaryFormatter formatter = new BinaryFormatter();

    // Serialize our application's entire state
    formatter.Serialize(stream, s_customers);
    formatter.Serialize(stream, s_pendingOrders);
    formatter.Serialize(stream, s_processedOrders);
}
```

To reconstruct our application state, we would deserialize the state with a method that looks like this

```csharp
private static void RestoreApplicationState(Stream stream) {
    // Construct a serialization formatter that does all the hard work
    BinaryFormatter formatter = new BinaryFormatter();

    // Deserialize our application's entire state (same order as deserialized)
    s_customers = (List<Customer>)formatter.Deserialize(stream);
    s_pendingOrders = (List<Order>)formatter.Deserialize(stream);
    s_processedOrders = (List<Order>)formatter.Deserialize(stream);
}
```

The third and last I'd like to point out how to deal with assemblies. When serializing an object, the full name of the type and the name of the type's defining assembly are written to the stream. BinaryFormatter outputs the assembly's full identity, which includes the assembly's file name (without extension), version number, culture, and public key information. When deserializing an object, the formatter first grabs the assembly identity and ensures that the assembly is loaded into the executing App.Reflection.Assembly.Load method (discussed in Chapter 23, "Assembly Loading and Reflection")

After an assembly has been loaded, the formatter looks in the assembly for a type matching or an exception is thrown if the assembly doesn't contain a matching type, and no more objects can be deserialized. If a matching type is found, an instance of the type is created and its fields are initialized from the values contained in the stream. If the type's fields exactly match the names of the fields as read from the stream, a SerializationException is thrown and no more objects can be deserialized. Later in this chapter, I will discuss some sophisticated mechanisms that allow you to override some of this behavior.
