
Here is some code that shows this.

```cs
private static void Method() {
    // Construct a List that operates on DateTime objects
    List<DateTime> dtList = new List<DateTime>();

    // Add a DateTime object to the list
    dtList.Add(DateTime.Now);    // No boxing

    // Add another DateTime to the list
    dtList.Add(DateTime.MinValue); // No boxing

    // Attempt to add a String object to the list
    dtList.Add("1/2004");    // Compile-time error

    // Extract a DateTime object out of the list
    DateTime dt = dtList[0];
}
```

Generics provide the following big benefits to developers as exhibited by the code just shown:

- **Source code protection** Using a generic algorithm doesn't have to access to the algorithm's source code. With C++ templates, however, the algorithm's source code must be available to the developer who is using the algorithm.

- **Type safety** When a generic is used with a specific type, the compiler and the CLR understand and ensure that only objects compatible with the specified data type are used with the algorithm. Attempting to use an object of an incompatible type will result in either a compiler error or a run-time exception being thrown. In the example, attempting to pass a String object to the Add method results in the compiler issuing an error.

- **Cleaner code** Because the compiler enforces type safety, fewer casts are required in source code, meaning your code is easier to write and maintain. In the last line of Method, a developer doesn't need to use a (DateTime) cast to put the result of the indexer (querying element at index 0) into the dt variable.

## Generics in the Framework Class Library

Certainly, the most obvious use of generics is with collection classes, and the FCL defines several generic classes available for your use. Most of these classes can be found in the System.Collections.Generic namespace and System.Collections.ObjectModel namespace. There are also thread-safe generic classes available in the System.Collections.Concurrent namespace. Microsoft recommends that programmers use the generic collection classes and now discourages use of the non-generic classes for several reasons. First, the non-generic classes are not generic and you don't get the type safety, cleaner code, and better performance that you get when you use generic collections. Second, the generic classes have better object model than the non-generic classes. For example, fewer methods are virtual, resulting in better performance, and new members have been added to the generic collections to provide functionality.

The collection classes implement many interfaces, and the objects that you place into the collections implement these interfaces for operations such as sorting and searching. The FCL ships with many generic interface definitions so that the benefits of generics can be realized when working with interfaces. The commonly used interfaces are contained in the System.Collections.Generic namespace.

The new generic interfaces are not a replacement for the old non-generic interfaces; in many scenarios, you will have to use both. The reason is backward compatibility. For example, if the List<T> class implemented only the IList interface, no code could create a List<DateTime> object implemented IList.

I should also point out that the System.Array class base of all types, offers many static generic methods, such as AsReadOnly, BinarySearch, ConvertAll, Exists, Find, FindAll, IndexOf, FindLast, LastIndexOf, ForEach, Resize, Sort, and TrueForAll.
