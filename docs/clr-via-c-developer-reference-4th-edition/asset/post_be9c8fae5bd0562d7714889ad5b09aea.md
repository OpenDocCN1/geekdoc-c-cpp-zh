The RUT.netmodule file contains the IL code generated by compiling RUT.cs. This file also contains metadata tables that describe the types, methods, fields, properties, events, and so on that are defined by RUT.cs. The metadata tables also describe the types, methods, and so on that are referenced by RUT.cs. The MultiFileLibrary.dll is a separate file. Like RUT.netmodule, this file includes the IL code generated by compiling FUT.cs and includes similar definition and reference metadata tables. However, MultiFileLibrary.dll contains the additional manifest metadata tables, making MultiFileLibrary.dll an assembly. The additional manifest metadata tables describe all of the files that make up the assembly (the MultiFileLibrary.dll file itself and the RUT.netmodule file). The manifest metadata tables include all of the types exported from MultiFileLibrary.dll and RUT.netmodule.

> In reality, the manifest metadata tables don't actually include the types that are exported from the PE file that contains the manifest. The purpose of this optimization is to reduce the number of bytes required by the manifest information in the PE file. Some statements like "The manifest metadata tables also include all the public types exported from MultiFileLibrary.dll and RUT.netmodule" aren't 100 percent accurate. However, this statement reflects what the manifest is logically exposing.

After the MultiFileLibrary.dll assembly is built, you can use ILasm.exe to examine the metadata manifest tables to verify that the assembly file in fact has references to the RUT.netmodule's types. Here is what the FileDef and ExportedTypes metadata tables look like:

```
File #1 (06000001)
Token: 0x26000001
Name : RUT.netmodule
HashValue : e6 62 2c 1a 2c 97 65 21 44 10 15 96 f2 db22
Flags : [ContainsMetadata] (00000000)

ExportedType #1 (07000001)
Token: 0x27000001
Name: Referenced
Implementation token: 0x26000001
TypeDef token: 0x02000002
Flags : [Public][AutoLayout][Sealed][AnsiClass][BeforeFieldInit] (001)
```

From this, you can see that RUT.netmodule is a file that is part of the assembly with token 0x26000001. From the ExportedTypes table, you can see a publicly exported type, Referenced. The implementation token for this type is 0x26000001, which indicates that the type's code is contained in the RUT.netmodule file.

Note For the curious, metadata tokens are 4-byte. The high byte indicates the type: (0x01=Ref, 0x02=AssemblyRef, 0x26=File (file definition), 0x27=ExportedType). For the complete list, see the file included with the .NET Framework SDK. The higher bytes of the token simply identify the row in the corresponding metadata table. For example, implementation token 0x26000001 refers to the first row of File table. For the TypeDef table, rows are numbered starting with 1, not 0.

Any client code that uses the MultiFileLibrary.dll assembly must be built using the /reference switch. This switches the compiler to MultiFileLibrary.dll and all of the files listed in its File table when searching for a type. The compiler requires all of the assemblies to be installed and accessible. If you were to delete the RUT.netmodule file, the C# compiler would produce the following fatal error: CS0009: Metadata file 'C:\MultiFileLibrary.dll' could not be opened - Error importing module 'RUT.netmodule' of assembly 'C:\MultiFileLibrary.dll': The system cannot find the file specified. This means that to build a new assembly, all of the files from the referenced assembly must be present.

As the client code executes, it calls methods. When a method is called for the first time, the CL detects the type references as a parameter, a return type, or as a local variable. The CL then attempts to load the referenced assembly's file that contains the manifest. If the type being accessed is in this file, the CL performs its internal bookkeeping, allowing the type to be used. If the manifest indicates that the referenced type is in a different file, the CL attempts to load the necessary file and allows the type to be accessed. CL loads assemblies only when a method referencing a type in an unloaded assembly is called. This means that to run an application, all of the files from a referenced assembly do not need to be present.

# Adding Assemblies to a Project Using the Visual Studio IDE

If you're using the Visual Studio IDE to build your project, you'll have to add any assemblies you want to reference to your project. To do so, open Solution Explorer, right-click the project you want to add a reference to, and then select the Add Reference menu item. This causes the Reference Manager dialog box, see in Figure 2-2, to appear.

To have your project reference, select the assembly from the list. If the assembly you want is not in the list, click the Browse button to navigate to the desired assembly (file containing a manifest) to add the assembly reference. The Solution option allows the current project to reference another project in the same solution. The COM option in the Reference Manager dialog box allows an unmanaged COM server to be accessed from managed proxy source code automatically generated by Visual Studio. The Browse option allows you to select an assembly that you recently added to another project.

To make your own assemblies appear in the Reference Manager's dialog box, follow the instructions at http://msdn.microsoft.com/en-us/library/ze6zky(v=110).aspx.

# Using the Assembly Linker

Instead of the C# compiler, you might want to create assemblies using the Assembly Linker utility,.exe. The Assembly Linker is useful if you want to create an assembly consisting of modules built from different compilers (if your compiler does not support the equivalent of C# /addmodule switch) or if you don't know your assembly packing requirements at build time. You can also use ALexe to build resource-only assemblies, called satellite assemblies, which are typically used for localization purposes. I'll talk about satellite assemblies later.

To understand how ALexe works, let's change the MultiFileLibrary.dll. The following is an example of how to call the Assembly Linker, ALexe, by using the /main switch.

```
csc /t:module RUT.cs
al /out:MultiFileLibrary.dll /main:FUT.cs
```

Figure 2-3 shows the result of these statements.

In this example, two modules, RUT.netmodule and FUT.module, are created. Neither module is an assembly because they don't contain metadata tables. Then a third is produced: MultiFileLibrary.dll, which is a small file (because of the /library switch) that contains no IL code but has metadata tables. RUT.netmodule and FUT.module are part of the assembly.

The ALexe utility can also produce EXE files by using the /exe switch. But this is very unusual unless you've ever created an assembly for an application that doesn't have its entry in the PE file that contains metadata tables. The resulting assembly consists of three files: MultiFileLibrary.dll, RUT.netmodule and FUT.module.
