Here is an example.

```
public static class SomeType {
    private static void Test(){
        Int32 x = S;
        Guid g = new Guid();

    // This call to M compiles fine because
    // Int32 implements IComparable AND IConvertible
    M(x);

    // This call to M causes a compiler error because
    // Guid implements IComparable but it does not implement IConvertible
    M(g);
}

// M's parameter, T, is constrained to work only with types that
// implement both the IComparable AND IConvertible interfaces
private static Int32 M<T>(T t) where T : IComparable, IConvertible {
    ...
}
```

This is actually cool! When you define a method's parameters, each parameter's type indicates that the argument passed must be of the method's type or derived from it. If the parameter type is an interface, this indicates that the argument can be of any class as long as the class implements the interface. Using multiple interface constraints lets the method indicate that the passed argument must implement multiple interfaces.

In fact, if we constrained T to class and interfaces, we are saying that the type of argument passed must be of the specific base class (or derived from it), and it must also implement the interfaces. This flexibility allows the method to dictate what can pass, and compiler errors will be generated if callers do not meet these constraints.

The second benefit of interface constraints is reducing boxing when passing instances of values. In the previous code fragment, the M was passed to x (an instance of an Int32, which is a value type). No boxing will occur when x is passed to M. If code inside M does call t.CompareTo(...), still no boxing occurs to make the call (boxing may still happen for arguments passed to CompareTo).

On the other hand, if M had declared this:

```
private static Int32 M(IComparable t) {
    ...
}
```

then in order to pass x to M, x would have to be boxed.

For interface constraints, the C# compiler emits Intermediate Language (IL) instructions that result in calling the interface method on the value type directly without boxing. Aside from using interface constraints, there is no other way to get the C# compiler to emit these IL instructions, and therefore, calling an interface method on a value type always causes boxing.
