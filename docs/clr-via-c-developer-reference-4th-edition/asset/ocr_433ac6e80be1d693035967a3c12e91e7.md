Let me clear up a few ends about this architecture. First, Thread.Abort method is asynchronous. When the runtime detects that a thread is aborted, the runtime tries to get the thread to a safe place. A thread is in a safe place where the runtime feels that it can stop the thread without causing disastrous effects. A thread is a safe place if it is performing a managed operation such as sleeping or waiting. A thread can be corrupted to a safe place by using hijacking (described in Chapter 21). A thread is not in a safe place if it is executing a type's constructor, in a catch or a finally block, code in CER, or unmanaged code.

After the thread reaches a safe place, the runtime will detect that the AbRequested flag is set for the thread. This causes the thread to throw a ThreadAbortException. If this exception is not caught, the exception will be unhandled, all pending finally blocks will execute, and the thread will kill itself gracefully. Unlike all other exceptions, an unhandled ThreadAbortException does not cause the application to terminate. The runtime silently eats this exception and the thread dies, but the application and all of its remaining continue to run fine.

In my example, the host catches the ThreadAbortException, allowing the host to regain control of the thread and return to the pool. There is a problem: What is to stop the untrusted code from catching the ThreadAbortException itself to regain control of the thread? The answer is that the CLR treats the ThreadAbortException in a very special manner. Even when code catches the ThreadAbortException, the CLR doesn't allow the exception to be swallowed. In other words, at the end of the catch block, the CLR automatically rethrows the ThreadAbortException.

This CLR feature raises another question: If the CLR rethrows the ThreadAbortException at the end of a catch block, how can the host it regain control of the thread? Inside the host's catch block, there is a call to Thread.ResetAbort method. Calling this method tells the CLR to stop rethrow the ThreadAbortException at the end of each catch block.

This raises another question: What is to stop the untrusted code from catching the ThreadAbortException and calling Thread.ResetAbort to keep control of the thread? The answer is that Thread's ResetAbort method requires the caller to have the SecurityPermission with the Control1Thread flag set to true. When the host creates the AppDomain for the untrusted code, the host will not grant this permission, and the untrusted code cannot keep control of the host's thread.

I should point out that there is still a potential hole in this story: the thread is unwinding from its ThreadAbortException, the untrusted code could execute catch and finally blocks. Inside these blocks, the host could remain. A host application prevents this by setting an escalation policy (described earlier). If an aborting thread doesn't finish in a reasonable amount of time, the CLR can upgrade the thread abort to a rude abort, a AppDomain unload, or killing of the process. I should also note that the untrusted code could catch the ThreadAbortException and, inside the catch block, throw some other kind of exception. If this other exception is caught, at the end of the catch block, the CLR automatically rethrows the ThreadAbortException.
