
features, there is some cost to tasks because memory must be allocated for all this state. If you don't
need additional features offered by tasks, your program will use resources more efficiently if
you use ThreadPool.QueueUserWorkItem.

The Task and <TResult> classes implement the Disposable interface, allowing you to
call Dispose when using the Task object. Today, all the Dispose method does close the
ManualResetEvent object. However, it is possible to define classes from Task and
<TResult>, and these classes could allocate their own resources, which would be freed in
override of the Dispose method. I recommend that developers not explicitly call Dispose on a Task
object in their code; instead, just let the garbage collector clean up any resources when it determines
they are no longer in use.

You'll notice that Task object contains an Int32 representing a Task's unique ID. When
you first time you query the Task's read-only id the property assigns a unique Int32 value to this and returns it from the property.
Task IDs start at 1 and increment by 1 as each ID is assigned. Looking at a Task object in the
Microsoft Visual Studio debugger will cause the debugger to debug the Task's ID, forcing the Task
to assigned.

The idea behind the ID is that each Task can be identified by a unique value. In fact, Visual Studio
shows you this IDs in its Tasks and Parallel Stacks windows. But because you don't as-
sign the IDs in your code, it is practically impossible to correct an ID with number that your
are doing. When running a task code, you can query Task's static CurrentId property, which
returns a null Int32 (Int32). You can also call this from Visual Studio's Watch or Im-
mediate window while debugging to get the ID for the code that you currently stepping through.
You then find it in the Parallel Tasks/Stacks windows. If you query the CurrentId property a task is not executing, it returns null.

During a Task's existence, you can learn it in its lifecycle by querying the Read-
only status. This property returns a TaskStatus value that is defined as.

```c
public enum TaskStatus {
    // Flags indicate the state of a Task in its lifetime:
    Created,
    // Task created explicitly; you can manually Start() this task
    WaitingForActivation,// // Task created implicitly; it starts automatically

    WaitingToRun,
    // The task was scheduled but it's not running
    Running,
    // The task is actually running
```

```csharp
// The task is waiting for children to complete before it considers itself complete
WaitingForChildrenToComplete.
```

```csharp
// A task's final state is one of these:
RanToCompletion,
Canceled,
Faulted
```

```csharp
}
```

When you construct a Task object, its status is Created. Later, when the task is started, its
status changes to WaitingToRun. When the task is actually running on a thread, its status changes
to Running. When the task stops and is waiting for any task state, the status changes to WaitingForChildrenToComplete. When a task is completely finished, it enters one of three final states: RanToCompletion, Canceled, or Faulted. When a Task<TResult> runs to completion, you can query the task's result via Task<TResult>.Result property. When a Task or Task<TResult> fails, you can obtain the unhandled exception that throws by querying Task's Exception property; which always returns an AggregateException object which contains the set of unhandled exceptions.

For convenience, Task offers several read-only, Boolean properties: IsC, IsFaulted, and IsCompleted. Note that IsCompleted returns true when the Task is in the RanToCompletion, Canceled, or Faulted state. The easiest way to determine if a Task is successfully completed is to use code like the following:

```csharp
if (task.Status === TaskStatus.RanToCompletion) ...
```

A Task object is in the WaitingForActivation state if a Task is created by calling one of these functions: ContinueWith, ContinueWhenAll, ContinueWhenAny, or FromAsync. Task created by constructing a TaskCompletionSource is also created in the WaitingForActivation state. This means that the Task's scheduling is controlled by the task infrastructure. For example, you cannot explicitly start a Task object that was created by calling ContinueWith. This Task will start automatically when its antecedent task has finished executing.

# Task Factories

Occasionally, you might want to create a bunch of Task objects that share the same configuration. To keep you from having to pass the same parameters to each Task's constructor over and again, you can create a task factory that encapsulates the common configuration. The System.Threading namespaces defines TaskFactory type as well as a TaskFactory<TResult>. Both of these types are derived from System.Object; that is, they are peers of each other.

If you want to create a bunch of tasks that return void, then you will construct a TaskFactory. If you want to create a bunch of tasks that have a specific return type, then you will construct a TaskFactory<TResult> where you pass the desired return type for the generic TResult argument. When you create one of the task factory classes, you pass to your constructor the defaults that you want the tasks to create. Specifically, you pass to the task factory the CancellationToken, TaskScheduler, TaskCreationOptions, and TaskContinuationOptions that you want factory-created tasks to have.

Here is some sample code demonstrating the use of a TaskFactory.

```csharp
Task parent = new Task(() => {
var cts = new CancellationTokenSource();
var tf = new TaskFactory<int32>(cts.Token, TaskCreationOptions.AttachedToParent, TaskScheduler.Default).ExecuteSynchronously;

// This creates 3 child tasks
var childTasks = new Task[] {
tf.StartNew(() => Sum(cts.Token, 10000)),
tf.StartNew(() => Sum(cts.Token, 20000)),
tf.StartNew(() => Sum(cts.Token, Int32.MaxValue)) // Too big, throws OverflowException
});

// If any of the child tasks, cancel the rest of them
for (Int32 task = 0; task < childTasks.Length; task++)
childTasks[task].ContinueWith(t => cts.Cancel(), TaskContinuationOptions.OnlyFaulted);

// When all children done, get the maximum value from the non-faulting tasks
tf.ContinueWhenAll(childTasks.Where(t => t.Status == TaskStatus.RanToCompletion).Max(t => t.Result), CancellationToken.None).ContinueWith(t => "The maximum is " + t.Result, TaskContinuationOptions.ExecuteSynchronously);

// When the children done, show anyhandled exceptions too
parent.ContinueWith(p => {
// I put all this text in a StringBuilder and call Console.WriteLine once
// because this task could execute concurrently with the task above and I don't
// want the task's output interpersed
StringBuilder sb = new StringBuilder("The exception occurred:" + Environment.NewLine);
foreach (var e in p.Exception.Flatten().InnerExceptions)
sb.Append("  " + e.GetType().ToString());
Console.WriteLine(sb.ToString());
}, TaskContinuationOptions.OnlyFaulted);

// Start the parent task so it can start its children
parent.Start();
```
