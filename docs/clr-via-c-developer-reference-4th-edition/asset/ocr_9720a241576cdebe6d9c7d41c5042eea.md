This method is safe even though it doesn't take any lock. Because Int32 is a value type, the two Int32 values passed to Max are copied into it, so multiple threads could be calling Max simultaneously, each thread working on its own data, isolated from any other thread.

On the other hand, the FCL does not guarantee that instance methods are safe because adding all the locking code would hurt performance too much. And in fact, if every instance method acquires a lock, you ultimately end up having one thread running in your application at any time, which hurts performance even more. As mentioned earlier, when a thread constructs an object, this thread has a reference to the object, no other thread can access that object, and no thread synchronization is required when invoking instance methods. However, if the thread then expands the reference to the object—by placing it in a static field, as the argument to ThreadPool.QueueWorkItem or a Task, and on—then thread synchronization is required if the thread could attempt non-read-only access.

It is recommended that you make your class libraries thread safe and make all your instance methods thread safe. There is one caveat to this pattern: if the purpose of the instance method is to coordinate threads, then the instance method should be safe. For example, one thread can cancel an operation by calling CancellationSource's Cancel method, and another thread detects it should stop what it's doing by querying the CancellationToken's IsRequested property. These two instance members have special synchronization code inside to ensure that the coordination of the two threads goes as expected.

# Primitive User-Mode and Kernel-Mode Constructs

In this chapter, I explain the thread synchronization constructs. By primitive, I mean the simplest constructs that are available to you in your code. There are two kinds of primitive constructs: user-mode and kernel-mode. Whenever possible, you should use the primitive user-mode constructs, because they are significantly faster than the kernel-mode constructs because they use CPU instructions to coordinate threads. This means that the coordination is occurring in hardware (which makes it fast). This also means that the Windows operating system detects that a thread is blocked on a primitive user-mode construct. Because a thread pool blocked on a user-mode construct is never considered blocked, the thread pool will not create a new thread to replace the temporarily blocked thread. In addition, these CPU instructions block the thread for an incredibly short period of time.

However, there is a downside—only the Windows operating system kernel can stop a thread from running so that it is not wasting CPU time.
