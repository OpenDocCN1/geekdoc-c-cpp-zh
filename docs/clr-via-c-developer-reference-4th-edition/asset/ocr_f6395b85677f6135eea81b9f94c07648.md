+   The CLR's code verification process uses metadata to ensure your code performs only “type-safe” operations. (I’ll discuss verification shortly.)

+   Metadata allows objects' fields to be serialized into a metadata block, sent to another machine, and deserialized, re-creating the object's state on the remote machine.

+   Metadata allows the garbage collector to track the lifetime of objects. For any object, the garbage collector can determine the type of the object and, from the metadata, know which fields within that object refer to other objects.

In Chapter 2, “Building, Packaging, Deploying, and Administering Applications and Types,” the IL Assembler always produces modules that contain managed code (IL) and managed data (garbage-collected data types).

Microsoft’s C#, Visual Basic, F#, and the IL Assembler always produce modules that contain unmanaged code. End users must have the CLR (presenting as part of the .NET Framework) installed on their machine in order to execute modules that can manage managed code and/ managed data in the same way that they have the Microsoft Foundation Class (MFC) library or Visual Basic DLLs installed to run MFC or Visual Basic 6.0 applications.

By default, Microsoft’s C++ compiler builds EXE/DLL modules that contain unmanaged (native) code and manipulate unmanaged (native memory) at runtime. These modules don’t require the CLR to execute. However, by specifying /CLR command-line switch, the C++ compiler produces modules that manage managed code, and of code, the CLR must be installed to execute this code. All of the Microsoft compilers mentioned, C++ is unique in that it is the only compiler that allows the developer to write both managed and unmanaged code and have it emitted into a single module. It is also the only compiler that allows developers to define both managed and unmanaged data types in their source code. The flexibility provided by Microsoft’s C++ compiler is unparalleled by other compilers because it allows developers to use their existing native/C++ code from managed code and start integrating the use of unmanaged types as they see fit.

# Combining Managed Modules into Assemblies

The CLR doesn’t actually work with modules, it with assemblies. An assembly is an abstract concept that can be difficult to grasp initially. First, an assembly is a logical grouping of one or more modules or resources. Second, an assembly is the smallest unit of release, security, and versioning. Depending on the choices you make with your compilers or tools, you can produce a single-file or multifile assembly. In the CLR world, an assembly is what we would call a component.

In Chapter 2, I’ll go over assemblies in great detail, so I don’t want to spend a lot of time on them here. All I want to do make sure you are aware that there is this conceptual notion that offers a way to treat a group of assemblies as a single file.
