

# 计时器这么多，时间有限

遗憾的是，FCL（框架类库）实际上带了好种计时器，而大多数程序员并不清楚每个计时器的独特之处何在。让我来尝试解释一下：

- **System.Threading.Timer 类**是上一节讨论的计时器，当你想要在线程池上执行周期性后台任务时，它是最好的计时器。

- **System.Windows.Forms.Timer 类**构造此类的实例会告诉 Windows 将计时器与调用线程关联（参见 SetTimer 函数）。当此计时器触发时，Windows 会向线程的消息队列中插入一个计时器消息（WM_TIMER）。该线程必须执行消息循环，以提取这些消息并将其分发到指定的回调方法。请注意，所有的工作都由一个线程完成——即那个保证是执行回调方法的线程。这同时也意味着计时器将不会被多个线程并发执行。

- **System.Windows.Threading.DispatcherTimer 类**该类是 Silverlight 和 WPF 应用中 System.Forms.Timer类的等效物。

- **System.UI.Xaml.DispatcherTimer 类**该类是 Windows Store 应用中 System.Windows.Forms.Timer类的等效物。

- **System.Timers.Timer 类**这种计时器是对 System.Threading 类的简单封装，允许 CLR 在计时器到同时将事件队列到线程池中。System.Timers.Timer 类派自 System.ComponentModel.Component，允许这些计时器对象被放置在 Visual Studio 的设计面上。它暴露了属性和事件，使其能够更容易地从 Visual Studio 设计器中使用。该类在多年前微软仍在处理线程等问题时被添加到 FCL 中。这个类可能本应该是被移除的，这样大家就会一直使用 System.Threading.Timer 了。事实上，我从不使用 System.Timers.Timer 类，除非你真的想在设计面上使用计时器，否则我也建议不要使用它。

# 线程池如何管理线程

现在我想谈谈线程池如何管理工作线程和 I/O 线程。然而，我不想进入过多细节，因为内部实现随着 CLR 每一个版本的更新而发生了变化，并在未来的版本中将继续变化。最好的方法是将线程池视为一个黑盒。这个黑盒对于任何应用程序来说都不是完美的，因为它是一种通用的线程调度技术，旨在与各种应用程序配合；它对某些应用程序的效果会比其他应用程序好。它在今天运行良好，我强烈建议你信任它，因为你很难生产出一个比 CLR 自带的运行得更好的线程池。而且，随着时间的推移，由于线程池代码内部管理线程，大多数应用程序都应该改进。

# 设置线程限制

CL 允许开发者设置线程池创建的最大线程数。然而，事实证明，线程池永远不应对池中的线程数量设置上限，因为可能会发生饥饿或死锁。想象队列了 1,000 个工作项目，这些项目阻塞在一个由第 1,001 个项目触发的事件上。如果你设置了最大 1,000 个线程，第 1,001 个工作项目将无法执行，且所有 1,000 个线程都将被阻塞，迫使用户终止应用程序并丢失所有工作。此外，开发者人为限制其应用程序可用资源是非常不寻常的。例如，你会启动应用程序，并让系统限制应用程序可以使用的内存量，或限制应用程序可以使用的网络带宽吗？然而，出于某种原因，开发者们觉得必须限制线程池可以创建的线程数。

由于客户遇到了饥饿和死锁问题，CLR 团队稳步增加了线程池可以创建的默认最大线程数。现在的默认最大约为 1,000 个线程，这对于 32 位进程（最多有 2 GB 可用地址空间）来说实际上是无限的。在加载了一堆 Win32 DLL、加载 CLR DLL、分配了原生和托管堆后，大约剩余 1.5 GB 的地址空间。每个线程需要超过 1 MB 的内存作为其用户模式栈和环境块（TEB），在 32 位进程中能创建的最线程约为 1,360 个。尝试创建比此更多的线程将导致抛出 OutMemoryException。64 位进程提供 8 TB 的地址空间，因此从理论上讲你可以创建数百个线程。但分配接近这个数量的线程真的是在浪费资源，特别是当理想的线程数实际上是机器上的 CPU 数量时。CLR 团队应该做的是完全移除限制，但他们现在无法这样做，因为可能会破坏某些预期线程池限制存在的应用程序。

System.ThreadPool 提供了几个可以调用的方法来操作线程池中的线程：GetMaxThreads, SetMaxThreads, GetMinThreads, SetMinThreads 和 GetAvailableThreads。我强烈建议你不要调用这些任何一个方法。玩弄线程限制通常会导致应用程序性能变差而不是更好。如果你认为你的应用程序需要数百或数千个线程，那么你的应用程序架构以及使用线程的方式有问题。本章和第 28 节演示了使用线程的正确方法。

# 工作线程是被管理的

图 27-1 显示了组成工作线程的数据结构。ThreadPool.QueueUserItem 方法和 Timer 类始终将项目置于全局队列。工作线程使用先进先出（FIFO）算法从该队列中提取项目。由于多个线程可以从全局队列中移除项目，所有工作线程都在一个线程同步锁上竞争。这个线程同步锁在某些应用程序中可能成为瓶颈，从而在某种程度上限制扩展性和性能。

现在谈谈使用默认 TaskScheduler（通过查询 TaskScheduler.Default 属性获取）调度 Task 对象。当非工作线程调度 Task 时，Task 被添加到全局队列；每个工作线程都有自己的本地队列，而当工作线程调度 Task 时，Task 被添加到调用线程的本地队列中。

当工作线程准备好处理某个项目时，它总是首先检查其本地队列是否有 Task。如果存在，工作线程将从其本地队列中移除 Task。注意，工作线程使用后进先出（LIFO）算法从其本地队列中提取任务。由于工作线程是唯一允许访问其本地队列头的线程，因此不需要线程同步锁，从队列中添加和移除 Task 是非常快的。这种行为的副作用是 Task 的执行顺序与它们入队的顺序相反。

> 重要：线程池从不保证队列项目处理的顺序，特别是多个线程可能同时处理项目时。你必须确保你的应用程序对队列工作项目或任务的执行顺序没有预期。

当工作线程看到其本地队列为空时，它将尝试从另一个工作线程的本地队列中“偷”一个 Task。Task 从本地队列的尾部被偷取的，需要获取线程同步锁，这会有轻微影响。当然，希望是偷取很少发生，因此获取锁的情况也很少。如果所有本地队列都为空，工作线程将使用 FIFO 算法从全局队列中提取一个项目（获取锁）。如果全局队列为空，工作线程将进入睡眠状态等待事情出现。如果它睡眠很长时间，它将醒来并销毁自己，允许系统回收该线程使用的资源（内核对象、栈、TEB）。
