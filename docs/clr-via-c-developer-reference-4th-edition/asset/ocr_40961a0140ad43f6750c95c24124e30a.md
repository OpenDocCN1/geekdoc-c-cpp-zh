any corrupted state that lives within an AppDomain by unloading the entire AppDomain by calling
AppDomain's Unload method (Chapter 22 for details).

And, if you feel that your state is so bad that the whole process should be terminated, then you
call Environment's static FailFast method.

```
public static void FailFast(String message);
public static void FailFast(String message, Exception exception);
```

This method terminates the process without running any active try/finally blocks or Final-
ize methods. This is good because executing more code while state is corrupted could easily make
ters worse. However, FailFast will allow any CriticalFinalizer-derived objects,
discussed in Chapter 21, "The Managed Heap and Garbage Collection," a chance to clean up. This is
 OK because they tend to close native resources, and Windows state is probably fine even
the CLR's state or your application's state is corrupted. The FailFast writes the message
string and any optional exception (usually the exception captured in a catch block) to the Windows-
plication event log, produces a Windows error report, creates a memory dump of your application,
and terminates the current process.

> Important Most of the FCL code does not ensure that state remains in the case of an
ununexpected exception. If your code catches an exception that passes through FCL code and
continues to use FCL objects, there is a chance that these objects will behave unprepre-
dictably. It's a shame that more FCL objects don't maintain their state better in the face of
ununexpected exceptions or call FailFast if their state cannot be restored.

The point of this discussion is to make aware of the potential problems related to using the
CLR's exception-handling mechanism. Most applications cannot tolerate running with a corrupted
state it leads to incorrect data and security holes. If you are writing an application
that cannot tolerate (like an operating system or database engine), then managed code is
ot a good technology to use. And although Microsoft Exchange Server is largely written in managed
code, it uses a native database to store email messages. The native database is called the Extensible
Storage Engine; it ships with Windows, and can be found at C:\Windows\System32\Esent.dll.
Your applications can also use this engine if you'd like: search for "Extensible Storage Engine" on the
Microsoft website.

Managed code is a good choice for applications that can tolerate an application terminating when
state corruption has possibly occurred. There are many applications that fall into this category. Also,
it takes significantly more resources and skills to write a robust native class library or application;
for many applications, managed code is the better choice because it greatly enhances programmer
productivity.
