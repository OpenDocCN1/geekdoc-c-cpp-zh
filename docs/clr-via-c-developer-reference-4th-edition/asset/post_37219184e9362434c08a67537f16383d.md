
If you were to compile this code and examine the resulting assembly with ILasm.exe, you'd see that the C# compiler did, in fact, emitted a protected override method Finalize into the module's metadata. If you examined the Finalize method's IL code, you'd also see that the code inside the method's body is emitted into a try block, and that call to base.Finalize is emitted into a finally block.

If you are familiar with C++, you'll notice that the special C# syntax for defining a Finalize method looks just like the syntax you'd use to define a C++ destructor. In fact, the C# Programming Language Specification calls this method a destructor. However, a Finalize method doesn't work like a C++ destructor at all, and this has caused a great deal of confusion for developers migrating from one to another.

The problem is that developers mistakenly believe that the C# destructor means that the type's objects will be deterministically destroyed when they go out of lexical scope, just as they would be in C++. However, the CLR does not support deterministic destruction, preventing C# from providing this mechanism.

Finalize methods are called at the collection of a garbage collection on which the GC has determined that the memory for these objects cannot be reclaimed right away. The Finalize method might execute access. A final object must survive the collection, gets promoted to another generation, forcing the object to live much longer than it does. This is not ideal in terms of memory consumption and is why you should avoid finalization when possible. To make worse, when finalizable objects get promoted, any object referred to by its fields get promoted because they must continue to live too. So, try to avoid finalizing objects with reference type fields.

Furthermore, be aware of the fact that you have no control over when the Finalize method will execute. It runs when a garbage collection occurs, which may happen when your application requests memory. Also, the CLR doesn't make any guarantees as to the order in which Finalize methods are called. So, you should avoid writing a Finalize method that accesses other objects whose type defines a Finalize method or reference type objects that do not define a Finalize method already finalized. You also need to be careful when calling static methods because these methods can internally access objects that have been finalized, causing the behavior of the static method to become unpredictable.

The CLR uses a special, high-priority dedicated thread to call Finalize methods to avoid deadlock scenarios that could occur otherwise. If a Finalize method blocks (for example, enters an infinite loop or waits for an object that is never signaled), this special thread can call any more Finalize methods. This is a very bad situation because the application will never be able to reclaim the memory occupied by the finalized objects—the application will leak memory as it runs.

⁵ A future of the CLR might use multiple finalizer threads to improve performance.

If a Finalize method throws an unhandled exception, then the process terminates; there is no way to catch this exception.

As, as you can see, there is a lot of cases related to Finalize methods and they must be used with caution. Specifically, they are designed for releasing native resources. It is highly recommended that developers avoid overiding Object's Finalize method; instead, use helper classes that Microsoft now provides in the Framework Class Library (FCL). The helper classes override Finalize and some special CLR magic I'll talk about as we go. You will derive your own classes from the helper classes and inherit the CLR magic.

The first thing to notice is the SafeHandle class that is derived from CriticalFinalizer-Object, which is defined in the System.Runtime.ConstrainedExecution. The CLR treats this class and classes derived from it in a very special manner. In particular, the CLR enhances this class with three core features:

- The first time an object of any CriticalFinalObject-derived type is constructed, the CLR immediately-compiles all of the JIT methods in the inheritance hierarchy. Compiling these methods upon object construction guarantees that the native resource will be released when the object is determined to be garbage. Without this compiling of the Finalize method, it would be possible to allocate the native resource and use it, but not to get rid of it. Under low memory conditions, the CL might not be able to find enough memory to compile the Finalize method, which would prevent it from executing, causing the native resource leak. The resource might not be freed if the Finalize method contained code that referred to it in another assembly, and the CLR failed to locate this other.

- The CLR calls the Finalize method of CriticalFinalizerObject-derived types after calling the Finalize methods of non-CriticalFinalizerObject-derived types. This ensures that managed resource classes have a Finalize method can access Critical-FinalizerObject-derived objects within their Finalize methods successfully. For example, the FileStream class's Finalize method can flush data from a memory buffer to an under-lying disk if the file has not been closed.

- The CLR calls the Finalize method of CriticalFinalizerObject-derived types if an AppDomain is rudely aborted by a host application (such as SQL Server or ASP.NET). This is also part of ensuring that the native resource is released even in a case where a host application no longer trusts the managed code running inside of it.
