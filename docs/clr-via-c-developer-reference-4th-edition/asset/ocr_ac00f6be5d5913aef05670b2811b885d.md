And now I can write code like this, which throws and catches one of these.
public static void TestException() {
  try {
    throw new Exception<DiskFullException>((
      new DiskFullException(@"C:\", "The disk is full");
    );
  } catch (Exception<DiskFullException> e) {
    Console.WriteLine(e.Message);
  }
}

In many scenarios, this is not a problem at all and, in fact, having a shallow and wide exception type hierarchy is preferred. # Trading Reliability for Productivity

I started writing software in 1975. I did a fair amount of BASIC programming, and as I got more interested in hardware, I switched to assembly language. Over time, I switched to the C programming language because it allowed me access to hardware with a much higher level of abstraction, making my programming easier. My background is in writing operating systems' code and platform/library code, so I always worked to make my code as small and fast as possible, because applications can only be as good as the operating system and the libraries they consume.

In addition to creating small and fast code, I always focused on error recovery. When allocating memory (by using C++'s new operator or calling malloc, HeapAlloc, VirtualAlloc, etc.), I would always check the return value to ensure that the memory requested was actually came to me. And, if the memory request failed, I always had an alternate code path ensuring that the rest of the program's state was unaffected and let any of my callers know that I failed so that they can take corrective measures too.
