FIGURE 28-1 How Windows performs a synchronous I/O operation.

In your program, you open a disk file by constructing a FileStream object. Then you call the Read method to read data from the file. When you call FileStream's Read method, your thread transitions from manage to native/user-mode code and internally calls the Win32 Read-File function (#1), ReadFile then allocates a small data structure called an I/O Request Packet (IRP) (#2). The structure is initialized to handle the file, an offset in the file where bytes will start to read from, the address of a Byte[] that be filled with the bytes being read, the number of bytes to transfer, and some other interesting stuff.

ReadFile then calls into the Kernel by having your thread from native/user-mode code to native/kernel-mode code, passing the IRP data structure to the kernel (#3). From the hardware device, the IRP is destined for, and Windows delivers the IRP to the appropriate driver's IRP queue (#4). Each device driver maintains its own IRP queue that contains IRP requests from all processes running on the machine. As IRP packets show up, the device driver passes the IRP information to the circuit board associated with the actual hardware device. The hardware device now performs the requested I/O operation (#5).

But here is the important part: While the hardware is performing the I/O operation, your thread that issued the I/O request has nothing to do, so Windows puts your thread to sleep so that it is not wasting CPU time (#6), but although your thread is not wasting time, it is wasting-space (memory), as its user-mode stack, kernel-mode stack, thread environment block (TEB), and other data structures are sitting in memory but not being accessed at all. In addition, for GUI applications, the UI cannot respond to user input while the thread is blocked. All of this is bad.
