```
// Process the data in the file...
catch (IOException) {
    // Put that code recovers from an IOException
}
finally {
    // Make sure that the file gets closed.
    if (fs != null) fs.close();
}
```

If the code in the try block executes without throwing an exception, the file is guaranteed to be closed. If the code in the try block throws an exception, the finally block still executes, the file is guaranteed to be closed, regardless of whether the exception is caught. Improper to put the statement to close the file after the finally block; the statement wouldn't execute if an exception was thrown and not caught, which would result in the file being open (until the next garbage collection).

A try block doesn't require a finally block associated with it; sometimes the code in a try block doesn't require any cleanup code. If you have a finally block, it must appear after any and all catch blocks. A try block can have no more than one finally block associated with it.

When a thread reaches the end of the code contained in a finally block, the thread simply starts executing the statements immediately following the finally block. Remember that the finally block is cleanup code. This code should execute only what is necessary to clean up initiated in the try block. The inside catch and finally blocks should be short and have a high likelihood of succeeding without throwing an exception. Usually the code in these blocks is one or two lines of code.

It is always possible that exception-recovery or cleanup code could fail and throw an exception. Although, it is unlikely and if it happens it usually means that there is something very wrong somewhere. Most likely some state has corrupted somewhere. If an exception is inadvertently thrown within a catch or finally block, the world will not come to an end—theCLR's exception mechanism will execute as the exception was thrown from the finally block. However, the CLR does not keep track of the first exception that was thrown in the corresponding try block (if any), and will lose any and all information (as the stack trace) available about the first exception. Probably (and hopefully), this new exception will be handled by your code and the exception will turn into an unhandled exception. The CLR will terminate your process, which is good because the corrupted state will now be destroyed. This is much better than having your application continue to run with unpredictable results and security holes.

Personally, I C# team should have chosen different language keywords for the exception-handling mechanism. What programmers want to do is try to execute some piece of code. And then, if something fails, either recover from the failure and move on or compensate to undo some state change and continue to report the failure to a caller. Programmers also want to guarantee cleanup no matter what happens.
