# Important In regard to inheritance, a derived type cannot override and change the pre-conditions of a virtual member defined in a base type. Similarly, a type implementing an interface member cannot change the preconditions defined by that interface. If a member does not have an explicit contract defined for it, then the member has an implicit contract that logically looks like this.

```
Contract.Requires(true);
```

And because a contract cannot be stricter with new versions (without compatibility), you should carefully consider preconditions when introducing a virtual, abstract, or interface member. For postconditions and object invariants, contracts can be added and removed at will with the conditions expressed in the virtual/abstract/interface member and the conditions expressed in the overiding member are just logically AND-ed together.

Now that you see how to declare contracts. Let's now talk about how they function at run time. You get to declare all your precondition and postcondition contracts at the top of your methods where they are easy to find. Of course the precondition contracts will validate your tests when the method is invoked. However, we don't wait the postcondition contracts to validate your tests until the method returns. In order to get the desired behavior, the assembly produced by the C# compiler must be processed by the Code Rewriter CCWrite.exe, located in C:\Program Files (x86)\Microsoft\Contracts\Bin, which produces a modified version of the assembly. After you select the Perform Contract Checking box for your project, Visual Studio will invoke this tool for automatically when you build the project. This tool analyzes the IL in all of methods and rewrites the IL so that any postcondition contracts are executed at the end of each method. If your method has multiple return points inside it, the CCWrite.exe tool modifies the method's IL code so that all return points execute the postcondition code prior to the method returning.

The CCWrite.exe tool looks the type for any method marked with the [ContractInvariant-Method] attribute. This method can have any name, by convention, people usually use the name ObjectInvariant and mark the method as private (if you just). The method must accept no arguments and have a void return type. The CCWrite.exe sees a method marked with this, it inserts IL code at the end of every public interface method to call the ObjectInvariant method. This way, the object's state is checked as each method returns to ensure that no method has violated the contract. Note that the CCWrite.exe tool does not modify a Finalize method or IDisposable method to call the ObjectInvariant method because it is OK for an object's state to be altered if it is desired to be destroyed or disposed. Also note that a single type can define multiple methods with the [ContractInvariantMethod] attribute; this is useful when working with partial types. The CCWrite.exe tool will modify the IL to all of these methods (in an undefined order) at the end of each public method.
