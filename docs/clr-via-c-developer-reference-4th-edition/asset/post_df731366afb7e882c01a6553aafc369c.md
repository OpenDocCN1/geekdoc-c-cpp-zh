Now, I will discuss what this code does and the CLR doing.

Inside the Marshalling method, I get a reference to an AppDomain object that identifies the
Domain calling thread is currently executing in. Windows, a thread is always created in the
context of one process, and the thread lives its entire lifetime in that. However, a one-to-one
correspondence does not exist between threads and AppDomains. AppDomains are a CLR feature;
Windows knows how multiple AppDomains can be in a single
Windows process, a thread can execute code in one AppDomain and then execute code in another
AppDomain. From the CLR's perspective, a thread is executing code in one AppDomain at a time. A
thread can ask the CLR what AppDomain it is currently executing in calling Thread.CurrentDomain.Thread's static GetDomain method. The thread could also query System.AppDomain's static, read-
only CurrentDomain property to get the same information.

When an AppDomain is created, it can be assigned a friendly name. A friendly name is just a String that you can use to identify an AppDomain. This is typically useful in debugging scenarios. Because the CLR creates the default AppDomain before any of your code can run, the CLR uses the executable file name as the default AppDomain's friendly name. My Marshalling method queries the AppDomain's name using System.AppDomain's read-only friendlyName property.

Next, my Marshalling method queries the strong-name identity of the assembly that defines the entry point method Main that calls Marshalling. This assembly defines several types: Program, MarshallByRefType, MarshallByType, and NonMarshalableType. At this point, we're ready to look at the three demos that are all similar to each other.

# Demo #1: Cross-AppDomain Communication Using Marshal-by-Value

In Demo #1, System.AppDomain.static CreateDomain method is called, instructing the CLR to create a new AppDomain in the windows process. The AppDomain type actually offers several loads of the CreateDomain method; I encourage you to study and select the version that is most appropriate when you are writing code to create a new AppDomain. The version of CreateDomain I call accepts three arguments:

- A identifying the friendly name I assigned to the new AppDomain I'm passing in "AD #2" here.
- A System.Security.Policy.Evidence identifying the evidence that the CLR should use to calculate the permission set I'm passing null here that the new AppDomain will inherit the permission set as the AppDomain creating it (Wait, the text says "as well as the AppDomain creating it"). Usually, if you want to create a security boundary around code in an AppDomain, you would construct a System.Security.PermissionSet object, add the desired permission objects to it (instances of types that implement the IPermission interface), and then pass the resulting PermissionSet reference to the overloaded version of the CreateDomain method that accepts a PermissionSet.
- A AppDomainSetup identifying the configuration settings the CLR should use for the new AppDomain Again. I'm passing null here so that the new AppDomain will inherit the same configuration settings as the AppDomain creating it. If you want the AppDomain to have a specific configuration, construct an AppDomainSetup object, set its properties to whatever you want, as the name of the configuration file, and pass the resulting AppDomainSetup object reference to the CreateDomain method.

Internally, the CreateDomain method creates a new AppDomain in the process. This AppDomain will be assigned the specified friendly name, security, and configuration settings. The new AppDomain will have its own loader heap, which will be empty because there are currently no assemblies loading into the AppDomain. When you create an AppDomain, the CLR does not create any threads in this AppDomain; no code runs in the AppDomain unless you explicitly have a thread call in the AppDomain.
