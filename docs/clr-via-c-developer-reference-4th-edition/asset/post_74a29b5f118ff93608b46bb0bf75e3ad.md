
File versioning is a very difficult problem to solve. If I assert that you used it by other code files and change one bit in the file—change a 0 to a 1 or a 1 to a 0—there's absolutely no way to guarantee that code that used the file before it changed will now work as well if you use the new version of the file. One of the reasons why this statement is true is that lot of applications exploit bugs, either knowingly or unknowingly. If a later version of the file fixes a bug, the application no longer runs

So here the problem: How do you fix bugs and add features to a file and also guarantee that you don't break some? I gave this question a lot of thought and have come to one conclusion: It's not possible. But, obviously, this isn't good enough. Files will ship with bugs, and companies will always want to provide new features. But there is a way to distribute new files with the hope that the applications will work just fine. If the application doesn't work, there is an easy way to restore the application to its last-known good state.

In this chapter, I'll explain the infrastructure that .NET Framework has in place to deal with versioning problems. Let me warn: What I'm about to describe is complicated. I'm going to talk about lot of algorithms, rules, and policies that are built into the common language runtime (CLR). I'm also mentioning a lot of tools and utilities that the application developer must use. This is complicated because, as I've mentioned, the versioning problem is difficult to address and solve.

## Two Kinds of Assemblies, Two Kinds of Deployment

The CLR supports two kinds of assemblies: weakly named assemblies and strongly named assemblies.

> **Important** By the way, you won't find the term weakly named in any of the .NET Framework documentation. Why? Because I made it up. In fact, the documentation has no term to identify a weakly named assembly. I decided to coin the term so that I can talk about assemblies without any ambiguity to what kind of assembly I'm referring to.

Weakly named assemblies and strongly named assemblies are structurally identical—that is, they use the same portable executable (PE) file format, PE32(+) header, CLR header, metadata, tables, and Intermediate Language (IL) that we examine in Chapter 1, "The CLR's Execution Model," and Chapter 2. And you use the tools, such as the C# compiler andxexe, to build both kinds of assemblies. The real difference between weakly and strongly named assemblies is that a strongly named assembly is signed with a publisher's public/private key which identifies the assembly's publisher. This key pair allows the assembly to be uniquely identified, secured, and versioned, and it allows the assembly to be deployed anywhere on the user's machine or even on the Internet. This ability to uniquely identify an assembly allows the CLR to enforce certain known-to-be safe policies when an application tries to bind to a strongly named assembly. This chapter is dedicated to explaining what strongly named assemblies are and what policies the CLR applies to them.

An assembly is deployed in two ways: privately or globally. A privately deployed assembly is an assembly that is deployed in the application's base directory or one of its subdirectories. A weakly named assembly can be deployed only privately. I talked about privately deployed assemblies in Chapter 2. A globally deployed assembly is an assembly that is deployed into some well-known location that the CLR looks in when it's searching for the assembly. A strongly named assembly can be deployed privately or globally. I'll explain how to create and deploy strongly named assemblies in this chapter. Table 3-1 summarizes the kinds of assemblies and how they can be deployed.

## TABLE 3-1 How Weekly and Strongly Named Can Be Deployed

| Kind of Assembly | Can Be Privately Deployed | Can Be Globally Deployed |
| --- | --- | --- |
| Weakly named | Yes | No |
| Strongly named | Yes | Yes |

## Giving an Assembly a Strong Name

If multiple applications are going to access this directory automatically the assembly must be placed in a well-known directory

Obviously, differentiating assemblies simply by a file name is not enough. The CLR needs to support some mechanism that allows assemblies to be uniquely identified. This is the term we strongly named assembly refers to. A strongly named assembly consists of four attributes that uniquely identify the assembly: a file name (without an extension), a version number, a culture and a public key. Because public keys are very large numbers, we frequently use a small hash value derived from a public key. This hash value is called a public token. The following assembly identity strings identify four different assembly files.

```
"MyTypes,Version=1.0.8123.0,Culture=neutral,PublicKeyToken=b77a5c561934e089"
"MyTypes,Version=1.0.8123.0,Culture=en-US,PublicKeyToken=b77a5c561934e089"
"MyTypes,Version=2.0.1234.0,Culture=neutral,PublicKeyToken=b77a5c561934e089"
"MyTypes,Version=1.0.8123.0,Culture=neutral,PublicKeyToken=b035f7f7d15d50a3"
```

The first identity string identifies an assembly file named MyTypes.dll (you can't determine the file extension from an assembly string). The company producing the assembly is creating version 1.0.8123.0 of this, and nothing in the assembly is sensitive to any culture Culture is set to neutral. Of course, any company could produce a MyTypes.dll (or MyTypes.exe) file that is marked with a version number of 1.0.8123 and a neutral culture.

There must be a way to distinguish this company's assembly from another company's assembly that happens to have the same attributes. For several reasons, Microsoft chose to use standard/private key cryptographic technologies instead of any other unique identification technique such as GUIDs, URLs, or.. cryptographic techniques provide a way to check the integrity of the assemblies as they are installed on a machine, and they also allow permissions to be granted on a per-publisher basis. I'll discuss these techniques later in this chapter. So a company that uniquely marks its assemblies must create a public/private key pair. Then the public key can be associated with the assembly. No two companies have the same public/private key pair, and this distinction is what allows companies to create assemblies that have the same name, version, and culture without any conflict.

> **Note** The System.Reflection.AssemblyName class is a helper class that makes it easy for you to build an assembly name and obtain the various attributes of an assembly's name. The class offers several public instance properties, such as Culture, FullName, KeyPair, Name, and Version. In Chapter 2 I showed you how to make an assembly file and how to apply an assembly version number and a culture. A weakly named assembly can have assembly version and culture attributes embedded in the manifest metadata; however, the CLR ignores the version number and uses only the culture information when it is probing subdirectories looking for the satellite assembly. Because weakly named assemblies are always privately deployed, the CLR simply uses the name of the assembly (tacking on a .dll or an .exe extension) when searching for the assembly's file in the application's base directory or in any of the application's subdirectories specified by the Extensible Markup Language (XML) configuration file probing its privatePath attribute.

A strongly named assembly has a file name, an assembly version, and a culture. In addition, a strongly named assembly is signed by the publisher's private key.

The first step in creating a strongly named assembly is to obtain a key using the Strong Name utility, SN.exe, that ships with the .NET Framework SDK and Microsoft Studio. This utility offers a whole slew of features depending on the command-line switch. Note that all SN.exe's command-line switches are case-sensitive. To generate a public/private key, run SN.exe as follows.

```
$ -k MyCompany.snk
```

This line tells SN.exe to create a file called MyCompany.snk. This file will contain the public and private keys persisted in a binary format.
