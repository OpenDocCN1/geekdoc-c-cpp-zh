
# So Many Timers, So Little Time

Unfortunately, the FCL actually ships with several timers, and it is not clear to most programmers what makes each timer unique. Let me attempt to explain:

- **System.Threading.Timer class** is the timer discussed in the previous section, and it is the best timer to use when you want to perform periodic background tasks on a thread pool.

- **System.Windows.Forms.Timer class** Constructing an instance of this class tells Windows to associate a timer with the calling thread (see SetTimer function). When this timer goes off, Windows inserts a timer message (WM_TIMER) into the thread's message queue. The thread must execute a message pump that extracts these messages and dispatches them to the desired callback method. Notice that all of the work is done by just one—the thread that is guaranteed to be the thread that executes the callback method. This also means that your timer will not be executed by multiple threads concurrently.

- **System.Windows.Threading.DispatcherTimer class** This class is the equivalent of the System.Forms' Timer class for Silverlight and WPF applications.

- **System.UI.Xaml.DispatcherTimer class** This class is the equivalent of the System.Windows.Forms' Timer class for Windows Store apps.

- **System.Timers.Timer class** This timer is a basic wrapper around System.Threading class that allows CLR to queue events into the thread pool when the timer comes due. The System.Timers.Timer class is derived from System.ComponentModel.Component which allows these timer objects to be placed on a design surface in Visual Studio. It, exposes properties and events, allowing it to be used more easily from Visual Studio's designer. This class was added to the FCL years ago while Microsoft was still sorting out the threading and stuff. This class probably should have been removed so that everyone would be using the System.Threading.Timer instead. In fact, I never use the System.Timers.Timer class, and I'd discourage you from using it, too, unless you really want a timer on a design surface.

# How the Thread Pool Manages Its Threads

Now I'd like to talk about how the thread pool manages workers and I/O threads. However, I don't want to go into a lot of detail, because the internal implementation has changed over the years with each version of the CLR, and it will continue changing with future versions. It is best to think of the thread pool as a black box. The black box is not perfect for any application, because it is a general purpose thread-scheduling technology designed to work with a large myriad of applications; it will work better for some applications than others. It works well today, and I highly recommend that you trust it, because it would be very hard for you to produce a thread pool that works better than the one shipping in the CLR. And, over time, most applications should improve as the thread pool code internally manages threads.

# Setting Thread Limits

The CL allows developers to set a maximum number of threads that the thread pool will create. However, it turns out that thread pools should never place an upper limit on the number of threads in the pool because starvation or deadlock might occur. Imagine queueing 1,000 work items that block on an event that is signaled by the 1,001st item. If you've set a maximum of 1,000 threads, the 1,001st work item will not be executed, and all 1,000 threads will be blocked, forcing users to terminate the application and lose all their work. Also, it is very unusual for developers to artificially limit the resources they have available to their application. For example, if you would start your application and let the system restrict the amount of memory that your application can use or limit the amount of network bandwidth that your application can use? Yet, for some reason, developers felt compelled to limit the number of threads that the thread pool can create.

Because customers have starvation and deadlock issues, the CLR team has steadily increased the default maximum of threads that the thread pool can create. The default maximum is now about 1,000 threads, which is effectively limitless a 32-bit process has at most 2 GB of usable address space within. After a bunch of Win32 DLLs load, the CLR DLLs load, the native and managed heap allocated, there is approximately 1.5 GB of address space left over. Each thread requires more than 1 MB of memory for its user-mode stack and environment block (TEB), the most threads you can create in a 32-bit process is about 1,360. Attempting to create more threads than this will result in an OutMemoryException being thrown. Of a 64-bit process offers 8 terabytes of address space, so you could theoretically create hundreds of threads. But allocating anywhere near this number of threads is really just a waste of resources, especially when the ideal number of threads to have is really the number of CPUs in the machine. What the CLR team should do is remove the limits entirely, but they can't do this now because might break some applications that expect thread pool limits to exist.

The System.ThreadPool offers several methods that you can call to manipulate the threads in the thread pool: GetMaxThreads, SetMaxThreads, GetMinThreads, SetMinThreads, and GetAvailableThreads. I highly recommend that you do not call any of these methods. Playing with thread limits usually results in making an application performance worse, not better. If you think your application needs hundreds or thousands of threads, there is something wrong with the architecture of your application and the way that it's using threads. This chapter and Chapter 28 demonstrate the proper way to use threads.

# Worker Threads Are Managed

Figure 27-1 shows the data structures that make up the worker threads. The ThreadPool.QueueUserItem method and the Timer class always work items to the global queue. Worker threads pull items from this queue using a first-in-out (FIFO) algorithm. Because multiple threads can be removing items from the global queue, all workers contend on a thread synchronization lock. This thread synchronization lock can become a bottleneck in some applications, thereby limiting scalability and performance to some degree.

Now let's talk about Task objects scheduled using the default TaskScheduler (obtained by querying TaskScheduler.Default property). When a non-worker thread schedules a Task, the Task is added to the global queue, when each worker thread has its local queue, and when a worker thread schedules a Task, the Task is added to calling thread's local queue.

When a worker thread is ready to process an item, it always checks its local queue for a Task first. If a Task exists, the worker thread removes the Task from its local queue Note that a worker thread pulls tasks from its local queue using a last-in-first-out (LIFO) algorithm. Because a worker thread is the only thread allowed to access the head of its local queue, no thread synchronization lock is required and adding and removing Tasks from the queue is very fast. A side effect of this behavior is that Tasks are executed in the reverse order that they queued.

> Important threads never guarantee the order in which queued items are processed, especially multiple threads could be processing items simultaneously. You must make sure that your application has no expectations about the order in which queued work items or tasks execute.

When a worker thread sees that its local queue is empty, the worker thread will attempt to steal a Task from another worker's local queue. Tasks are stolen from the tail of a local queue and require a thread synchronization lock be taken, which hurts a little bit. Of course, the hope is that stealing rarely occurs, so lock is taken rarely. If all the local queues are empty, then the worker thread will extract an item from the global queue (taking its lock) using the FIFO algorithm. If the global queue is empty, the worker thread puts itself to sleep waiting for something to show up. If it sleeps for a long time, it will wake up and destroy itself, allowing the system to reclaim the resources (kernel object, stacks, TEB) that were used by the thread.
