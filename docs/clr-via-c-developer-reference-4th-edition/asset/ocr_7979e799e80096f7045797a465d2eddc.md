+   4. This trusted code then enters a try block, and from the try block, calls across an AppDomain (via a type derived from MarshalByRefObject). This AppDomain contains the untrusted code (perhaps a stored procedure) that was not built and tested by the company that produced the host application. At this point, the server has given control of its thread to some untrusted code; the server is feeling nervous right now.

+   5. When the untrusted code doesn't respond to the client's request, it recorded the time. In some administrator-set amount of time, the host calls Thread's Abstract, asking the CLR to stop the thread pool, forcing it to throw a ThreadAbortException.

+   6. At this point, the thread pool starts unwinding, calling finally blocks so that cleanup code executes. Eventually, the thread pool crosses back over the AppDomain boundary. Because the host's stub code calls the untrusted code from inside a try block, the host's stub code has a catch block that catches the ThreadAbortException.

+   7. In response to catching the ThreadAbortException, the host calls Thread's ResetAbort method. I will explain the purpose of this call shortly.

+   8. Now that the host's code has caught the ThreadAbortException, the host can return sort of failure back to the client and allow the thread pool thread to return to the pool so that it can be used for a future client request.
