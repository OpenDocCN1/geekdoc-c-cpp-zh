in using a Synchronization object. In addition, class library developers should do everything in their power to help application developers avoid deadlock situations. To solve both of these problems, the Task and TResult classes offer a method called ConfigureAwait whose signature looks like this.

```
// Task defines this method:
public ConfigureTaskAwait(Boolean continueOnCaptured);
```

```
// TResult defines this method:
public ConfigureTaskAwait<TResult> ConfigureAwait(Boolean continueOnCaptured);
```

Passing true to this method gives you the same behavior as not calling the method at all. But, if you pass false, the await operator does not query the thread's SynchronizationContext and, when a thread pool completes the Task, it simply completes it and the code after the await operator executes via the thread pool.

Even though GetMethod is not class library, the deadlock problem goes away if you add to ConfigureAwait. Here is the modified version of your GetMethod.

```
private async Task<String> GetHttp() {
// The HTTP request and let the thread return from GetHttp
HttpResponseMessage msg = await new HttpClient().GetAsync("http://intellect.com/");
.ConfigureAwait(false);
// WE DO get here now because a thread pool can execute this code
// as opposed to forcing the GUI thread to execute it.

return await msg.Content.ReadAsString().ConfigureAwait(false);
}
```

As the preceding code shows, ConfigureAwait(false) must be applied to every Task object you await. This is because asynchronous operations may complete synchronously and, when this happens, the calling thread simply continues without returning to its caller; you never know which operation requires ignoring the SynchronizationContext object, so you have to tell all of them to ignore it. This also means that your library code should be application model agnostic.

Alternatively, I could re-write my GetHttp method so far that the thread executes via a thread pool.

```
private Task<String> GetHttp() {
return Task.Run(async () => {
// We run on a thread pool now that has no SynchronizationContext on it
HttpResponseMessage msg = await new HttpClient().GetAsync("http://intellect.com/");
// WE DO get here because some thread pool can execute this code

return await msg.Content.ReadAsString();
});
```

In this version of the code, notice that your GetHttp method is not an async function; I removed the async keyword from the method signature, because the method no longer has an await operator in it. On the other hand, the lambda expression I pass to Task.Run is an async function.
