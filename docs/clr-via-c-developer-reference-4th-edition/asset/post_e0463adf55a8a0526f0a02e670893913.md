
# Implementing a Server Asynchronously

From talking to many developers over the years, I have discovered that very few of them are aware that the .NET Framework has built-in support you to build asynchronous servers that scale really well. In this book, I can't explain how to do this for every kind of server, but I can list what you should look for in MSDN documentation.

- To build an asynchronous ASP.NET Web Forms: your .aspx file, add "Async=true" to your page directive and look up the System.Web.UI.Page RegisterAsyncTask method.
- To build an asynchronous ASP.NET MVC controller: derive your controller class from System.Web.Mvc.Controller and simply have your action method return a Task<ActionResult>.
- To build an asynchronous ASP.NET handler: derive your class from System.Web.HttpAsyncTaskHandler and then override its abstract ProcessRequestAsync method.
- To build an asynchronous WCF service: implement your service as an async function and return Task or Task<TResult>.

# Canceling I/O Operations

In general, Windows doesn't give you a way to cancel an outstanding I/O operation. This is a feature that many developers would like, but it is quite hard to implement. After all, if you make a request from a server and then decide you don't want the response anymore, there is no way to tell the server to abandon your original request. The way to deal with this is just to let the bytes come back to the client machine and then throw them away. In addition, there is a race condition here—your request to cancel the could come while the server is sending the response. Now how should your application do? You'd need to handle this race condition in your own code and decide how to throw the data or act on it.

To assist with this, I recommend you implement a WithCancellation method that extends Task<TResult> (using a similar overload that extends Task) as follows.

```c
private async Task<TResult> WithCancellation<TResult>(this Task<TResult> originalTask, CancellationToken ct) {
    // Create a task that completes when the CancellationToken is canceled
    var cancelTask = new TaskCompletionSource<Void>();

    // When the CancellationToken is canceled, complete the task
    using (ct.Register(t => ((TaskCompletionSource<Void>)t).SetResult(new Void())), cancelTask)) {
    }

    // Create a task that completes either the original or
    // CancellationToken Token completes
    Task any = await Task.WhenAny(originalTask, cancelTask.Task);

    // If any Task completes by CancellationToken, throw OperationCanceledException
    if (any == cancelTask.Task) ct.ThrowIfCancellationRequested();

    // await originalTask (synchronously); if it failed, awaiting
    // throws 1 inner exception instead of AggregateException
    return originalTask;
}
```

Now, you can call this extension method as follows.

```csharp
public static async Task Go() {
    // Create a CancellationTokenSource that cancels itself after # milliseconds
    var cts = new CancellationTokenSource(5000); // To cancel sooner, call cts.Cancel()
    var ct = cts.Token;

    try {
        // I used Task.Delay for testing; replace this with another method that returns a Task
        await Task.Delay(10000).WithCancellation(ct);
        Console.WriteLine("Task completed");
    }
    catch (OperationCanceledException) {
        Console.WriteLine("Task cancelled");
    }
}
```

# Some I/O Operations Must Be Done Synchronously

The Win32 API offers many functions that execute I/O operations. Unfortunately, some of these methods do not let you perform the I/O asynchronously. For example, the Win32File method (called by FileStream's constructor) always executes synchronously. If you are trying to create or open a file on a network server, it could take seconds before CreateFile returns the calling thread is idle all the time. An application designed for responsiveness and scalability would ideally call a Win32 function that lets you create or open a file so that your thread is not sitting and waiting for the server to reply. Unfortunately, Win32 has no CreateFile-like function to let you do this, and therefore the FCL cannot offer an efficient way to open a file asynchronously. Windows also does not offer functions to asynchronously access the registry, access the event log, or get a directory's/directories, or change a file's/directory's attributes, to just a few.

Here is an example where this is a real problem. Imagine writing a simple UI that allows the user to type a file path and provides automatic completion (to the common File dialog box). The control must use separate threads to enumerate directories looking for files because Windows does not offer functions to enumerate files asynchronously. As the user continues to type in the UI, you have to use more threads and ignore the results from any previously spawned threads. With Windows Vista, Microsoft introduced a new Win32 function called Cancel-SynchronousIO. This function allows one to cancel a synchronous I/O operation that is performed by another thread. This function is not exposed by the FCL, but you can also P/Invoke to if you want to take advantage of it from a desktop application implemented with managed code. show the P/Invoke signature near the end of this chapter.

The Point I want to take away though is that many people think synchronous APIs are easier to work with, and in many cases this is true. In some cases, synchronous APIs make things harder.

Due to the problems that exist when executing I/O operations, when designing the Windows Runtime, the Windows team decide to expose all methods that perform I/O asynchronously. see Windows.Storage.StorageFile's OpenAsync method. In fact, the Windows Runtime does not offer any APIs allowing you to perform an I/O operation. Fortunately, you can use the C#s async function to simplify your code when calling these APIs.

# FileStream-Specific Issues

When you create a FileStream object, you specify whether you want to communicate with synchronous or asynchronous operations via the FileOptions.Asynchronous flag (which is equivalent to calling the Win32 CreateFile function and passing it FILE_FLAG_OVERLAPPED flag). If you do not specify this flag, Windows performs all operations against the file. Of course, you can still call FileStream's ReadAsync, and to your application, it looks as if the operation is performed asynchronously, but internally, the FileStream class uses others to emulate asynchronous behavior, and this is wasteful and hurts performance.

On the other hand, you can create a FileStream by specifying the FileOptions.Asynchronous flag. Then you can call FileStream's Read method to perform a synchronous operation. Internally, the FileStream class emulates this behavior by starting an asynchronous operation and immediately puts the calling thread to sleep until the operation is complete. This is also inefficient, but it is not as efficient as calling ReadAsync using a FileStream constructed without the FileOptions.Asynchronous flag.

So, to summarize, when working with a FileStream, you must decide whether you intend to perform synchronous or asynchronous I/O against the file and indicate which choice by specifying the FileOptions.Asynchronous flag (or not). If you specify this flag, always call ReadAsync. If you do not specify this flag, and to make some synchronous and asynchronous operations against the FileStream, it is more efficient to construct it using the FileOptions.Asynchronous flag. Alternatively, you can create two FileStream objects over the same file; open one FileStream for asynchronous I/O and open the other FileStream for synchronous I/O. The System.IO.File class offers helper methods (Create, Open, and OpenWrite) that return FileStream objects. Internally, none of these methods specify the FileOptions.Asynchronous flag, so you should avoid using these methods if you want to create a responsive or scalable application.

You should also be aware that the NTFS file system driver performs some operations synchronously no matter how you output the file. For more information about this, https://support.microsoft.com/default.aspx?scid=kb38%38-en-us%3816932.
