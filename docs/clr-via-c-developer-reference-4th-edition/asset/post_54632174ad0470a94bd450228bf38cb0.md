
Internally, the CLR can take an IBuffer object, query for its IBufferByte interface, and then query the Buffer property to get an unsafe pointer to the bytes contained within the buffer. With the pointer, the bytes can be accessed directly.

To avoid developers write unsafe code that manipulates pointers, the Framework Class Library includes a RuntimeExtensions class that defines a bunch of extension methods, which .NET developers explicitly invoke to help pass blocks from CLR byte arrays and streams to WinRT objects. To call these extension methods, make sure you are using System.Runtime.InteropServices.WindowsRuntime; directive to your source code.

```c
namespace System.Runtime.InteropServices.WindowsRuntime {
    public static class WindowsBufferExtensions {
        public static IBuffer AsBuffer(this Byte[] source);
        public static IBuffer AsBuffer(this Byte[] source, Int32 offset, Int32 length);
        public static IBuffer AsBuffer(this Byte[] source, Int32 offset, Int32 length, Int32 capacity);
    }
}
```

```c
public static IBuffer GetWindowsRuntimeBuffer(MemoryStream stream);
public static IBuffer GetWindowsRuntimeBuffer(MemoryStream stream);
```

So, if you have a Byte[] and you want to pass it to a WinRT API using an IBuffer, you simply call AsBuffer on the Byte[]. This effectively wraps the reference to the Byte[] inside an object that implements the IBuffer interface; the contents of the Byte[] are not copied, so this is very efficient. Similarly, if you have a MemoryStream object wrapping a visible Byte[] array that is not copied, you can call GetWindowsRuntimeBuffer on it to wrap the reference to the MemoryStream's buffer inside an object that implements the IBuffer interface. The buffer's content is not copied, so this is very efficient. The following method demonstrates scenarios.

```csharp

    Int32 sum = bytes.Sum(b => b); // Access the bytes read via the Byte[]
```

```csharp
    using (var sw = new StreamWriter(ms)) {
        sw.Write("This string represents data in a stream");
```

IRandomAccessStream interface implements WinRT's IInputStream interface as follows.

```csharp
namespace Windows.Storage.Streams {

        IAAsyncOperationWithProgress<UInt32, UInt32> WriteAsync(IBuffer buffer);

```

When you call the AsBuffer or GetWindowsRuntime methods in your code, these methods wrap the source object inside an object which implements the IBuffer interface. The CLR creates a CCW for it and passes it to the WinRT API. The WinRT API queries the IBufferAccess interface's Buffer to obtain a pointer to the underlying byte array, the array is pinned, and the address is returned to the WinRT API so it can access the data. The data is unpinned when the WinRT API internally calls COM's Release method on the IBufferAccess interface.

If you call a WinRT API that returns an IBuffer to you, the data itself is probably in native memory, and you'll need a access to this data from managed code. For this, we'll turn to some other extension methods defined by the WindowsRuntimeBufferClasses.

```csharp
namespace System.Interop.WindowsRuntime {
    public static class WindowsRuntimeExtensions {
        public static Stream AsStream(IBuffer source);
        public static Byte[] ToArray(IBuffer source);
        public static Byte[] ToArray(IBuffer source, UInt32 sourceIndex, Int32 count);

        // Not shown: CopyTo method to transfer bytes between IBuffer and a Byte[]
        // Not shown: GetByte, IsSameData methods
    }
}
```

The AsStream method creates a Stream-driven object that wraps the source IBuffer. With this object, you can access the data in the IBuffer by calling Stream.Read, and similar methods. The ToArray method internally allocates all the bytes from the source IBuffer into the Byte[]; be aware that this extension method is potentially expensive in terms of memory consumption and CPU time.

The WindowsRuntimeBufferExtensions class also has several overloads of a CopyTo method that can copy bytes between an IBuffer and a Byte[]; It also has a GetByte method that retrieves a single byte at a time from an IBuffer and an IsSameData method that compares the contents of two IBuffer objects to see if their contents are identical. For most applications, it is unlikely that you will need to call all of these.

I'd like to point out that the .NET Framework defines a System.Interop.Runtime.WindowsRuntimeBuffer class that allows you to create an IBuffer whose bytes are in the managed heap. Similarly, there is a WinRT component called Windows.Storage.Streams.Buffer that allows you to create an IBuffer whose bytes are in the native heap. For most .NET developers, there should be no need to use either of these classes explicitly in your code.

# Defining WinRT Components in C#

So far in this chapter, I've been focusing on how to consume WinRT components from C#. and then these components can be used by C/C++, C#/Visual Basic, JavaScript, and potentially other languages too. Although this is possible to, we need to think about the scenarios where this actually makes sense. For example, it makes no sense at all to define a WinRT component in C# as if the only consumers of the component are other managed languages that run on top of the CLR. This is because the WinRT type has far fewer features, which makes it much more restrictive than the CLR's type system.

I do not think it makes lot of sense to implement a WinRT component with C# that could be consumed by native C/C++ code. Developers using native C/C++ to implement their application are probably doing so because they are very concerned about performance/or memory consumption. They are unlikely to want to take advantage of a WinRT component implemented with managed code, because this forces the CLR to load into their process and increases their memory requirements and performance due to the garbage collections and just-in-time compilation of code. For reason, most WinRT components (like those with Windows itself) are implemented in native code. Of course, there may be some parts of a native C++ app where performance is not so sensitive and, at these times, it may make sense to leverage .NET Framework functionality in order to improve productivity. For example, Bing Maps uses native C++ to draw its UI using DirectX, but it also uses C# for its business logic.

So, it seems to me the sweet spot for C#-implemented components is for Windows Store app developers who want to build their user interface with HTML and then use JavaScript as the glue code to tie the UI with business logic that is implemented in a C# WinRT component. Another scenario would be leveraging Framework Class Library functionality (like Windows Communication) from an HTML/JavaScript app. Developers working with HTML and JavaScript are already willing to accept the kind of performance and memory consumption that comes with a browser engine and may be willing to even further additional performance and memory consumption that comes along also the CLR.

To build a WinRT component with C#, you must first create a Microsoft Visual Studio "Windows Runtime" project. What you do is create a normal class library project; however, the C# compiler will be spawned with the /t:winmdb command line switch in order to produce a file with .winmdb extension. With this switch enabled, the compiler emits only IL code differently than it would normally. For example, WinRT components add and remove delegates differently than how the CLR does, so the compiler emits different code for an event's add and remove moves when this compiler switch is switched. I will show how to explicitly implement an event's add and remove methods later in this chapter.

After the compiler produces the .winmdb file, the WinMD export (WinMDE.exe) is spawned passing to it the .winmdb, .pdb, and .xml docs produced by the compiler. The WinMDExp utility examines your file's metadata, ensuring that your types adhere to the WinRT type system rules, as discussed at the beginning of this chapter. This also modifies the metadata contained in the .winmd file; it does not alter the CLR at all. Specifically, the utility maps any CLR types to the equivalent WinRT types. For example, references to the .NET Framework's IList<String> are changed to WinRTVector<String>; the output of the WinMD-Exp utility is a .winmd file that other programming languages can consume.
