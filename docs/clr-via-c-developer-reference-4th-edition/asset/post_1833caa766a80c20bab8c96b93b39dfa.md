
In this code, many of the fields are initialized inline. C# allows you to use this convenient inline initialization syntax, as you'll see in Chapter 8, "Methods," C# treats initializing a field inline as shorthand for initializing the field in a constructor. Also, in C#, there are some performance issues to consider when initializing fields by using inline syntax versus assignment syntax in a constructor. These performance issues are discussed in Chapter 8 as well.

> **Important** When a field is a reference type and the field is marked as readonly, it is the reference that is immutable, not the object that the field refers to. The following code demonstrates:

```csharp
public sealed class AType {
    // InvalidChars must always refer to the same array object
    public static readonly Char[] InvalidChars = new Char[] { 'A', 'B', 'C' };
}

public sealed class AnotherType {
    public static void M() {
        // The lines below are legal, compile, and successfully
        // change the characters in the InvalidChars array
        AType.InvalidChars[0] = 'X';
        AType.InvalidChars[1] = 'Y';
        AType.InvalidChars[2] = 'Z';

        // The line below is illegal and will not compile because
        // what InvalidChars refers to cannot be changed
        AType.InvalidChars = new Char[] { 'X', 'Y', 'Z' };
    }
}
```

# Instance Constructors and Classes (Reference Types)

Constructors are special methods that allow an instance of a type to be initialized to a good state. Constructor methods are always called .ctor (for constructor) in a method definition metadata table. When creating an instance of a reference type, memory is allocated for the instance's data fields, the object's overhead fields (type object pointer and sync block index) are initialized, and then the type's constructor is called to set the initial state of the object.

When constructing a reference type object, the memory allocated for the object is always zeroed before the type's constructor is called. Any fields that the constructor doesn't explicitly overwrite are guaranteed to have a value of 0 or null.

Unlike other methods, instance constructors are never inherited. That is, a class has only the instance constructors it defines. Because instance constructors are not inherited, you cannot apply the following modifiers to an instance constructor: virtual, new, override, sealed, or abstract. If you define a class that does not explicitly define any constructors, the C# compiler defines a default (parameterless) constructor for you whose implementation simply calls the base class's parameterless constructor.

For example, if you define the following class.

```
public class SomeType {
}
```

it is as though you wrote the code as follows.

```
public class SomeType {
    public SomeType() : base() { }
}
```

If the class is abstract, the compiler-produced default constructor has protected accessibility; otherwise, the constructor is given public accessibility. If the base class doesn't have a parameterless constructor, the derived class must explicitly call a base constructor or the compiler will issue an error. If the class is static (sealed and abstract), the compiler will not emit a default constructor at all into the class definition.

A class can define several instance constructors. Each constructor must have a different signature, and each can have different accessibility. For verifiable code, a class's constructor must call its base class's constructor before accessing any of the inherited fields of the base class. The C# compiler will generate a call to the base class's constructor automatically if the derived class does not explicitly invoke one of the base class's constructors. Ultimately, System.Object's public, parameterless constructor gets called. This constructor does nothing—it simply returns. This is because System.Object defines no instance fields, and therefore its constructor has nothing to do.

In a few situations, an instance of a type can be created without an instance constructor being called. In particular, calling Object.MemberwiseClone method allocates memory, initializes the object's fields, and then copies the source object's bytes to the new object. Also, a constructor is usually not called when deserializing an object with the runtime serializer. The deserialization code allocates memory for the object without calling a constructor by using the System.Runtime.Serialization.Formatter's type GetUninitializedObject or GetSafeUninitializedObject (see Chapter 24, "Serialization").

> **Important** You should not call any virtual methods within a constructor that can affect the object being constructed. The reason is if the virtual method is overridden in the type being instantiated, the derived type's implementation of the overridden method will execute, but all of the fields in the hierarchy have not been fully initialized. Calling a virtual method would therefore result in unpredictable behavior.

```csharp
internal sealed class SomeType {
    private Int32 m_x = 5;
}
```

When SomeType object is constructed, its m_x field will be initialized to 5. How does this happen? If you examine the Intermediate Language (IL) for SomeType's constructor method (also called .ctor), you'll see the code shown here.

```il
.method public hidebys specialname rtspecialname
Instance .ctor() cil managed
{
    // Code size 14 (0xe)
maxstack 8
IL_0000: ldarg.0
IL_0001: ldc.i4.5
IL_0002: stfld      int32 SomeType::m_x
IL_0007: ldarg.0
IL_0008: call void [mscorlib]System.Object::ctor()
IL_000d: ret
} // end of method SomeType::ctor
```

In this code, you see that SomeType's constructor contains code to store 5 into m_x and then calls the base class constructor. In other words, the C# compiler uses the convenient syntax that lets you initialize fields inline and translates this to the constructor method to perform the initialization. What you should be aware of is code explosion, as illustrated by the following class.

```
internal sealed class SomeType {
    private Int32 m_x = 5;
    private String m_s = "Hi there";
    private Double m_d = 3.14159;
    private Byte m_b;

    // Here are some constructors.
    public SomeType() { }
    public SomeType(Int32 x) { ... }
    public SomeType(String s) { ...; m_d = 10; }
}
```

When the compiler generates code for these methods, the beginning of each method includes the code to initialize m_x, m_s, and m_d. After this initialization, the compiler inserts a call to the base class constructor, and then appends the code to the method. For example, the code generated for the constructor that takes a String parameter includes the code to initialize m_x, m_s, and m_d, call the base class (Object)'s constructor, and then overwrite m_d with the value 10. Note that m_b is guaranteed to be initialized to 0 even though no code exists to explicitly initialize it.

> **Note** The compiler initializes any fields by using the convenient syntax before calling a base class constructor to maintain the impression that these fields always have a value as the source code appearance dictates. The potential problem occurs when a base class's constructor invokes a virtual method that calls back into a method defined by the derived class.
