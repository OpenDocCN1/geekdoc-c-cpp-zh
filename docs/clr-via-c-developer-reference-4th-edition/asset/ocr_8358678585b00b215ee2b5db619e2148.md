+   - The CLR projects the WinRT Windows.Foundation.Uri type as the .NET Framework's System.Uri type. When passing a .NET WinRT Uri to a WinRT API, the CLR throws an ArgumentException if the URI is a relative; WinRT supports absolute URIs only. URIs are always copied across the interop boundary.

+   - The CLR projects the WinRT Windows.Foundation.IClosable interface (which has only a Close method) as the .NET Framework's System.IDisposable interface (with a Dispose method). One thing to really note here is that not all WinRT APIs that perform I/O operations are implemented asynchronously. Because IClosable's method is Close and is not CloseAsync, the Close method must not perform any I/O operations. This is semantically different from how Dispose usually works in the .NET Framework. For Framework-implemented types, calling Dispose caches buffered data to be written before closing a device. When C# code calls Close on a WinRT type however I/O (like writing buffered data) will not be performed and loss of data is possible. You must be aware of this, for WinRT components that wrap output streams, you will have to explicitly call methods to prevent loss. For example, when using a DataWriter, you should always call its StoreAsync method.

+   - Arrays support single-dimension, zero-based arrays. WinRT can marshal an array's elements in or out of it; never in out. Because of this, you cannot pass an array into a WinRT API, have the API modify the array's elements and then access the modified elements after the API returns. I have described the contract that should be adhered to. However, this is not actively enforced, so it is possible that some projections might marshal array contents both in and out. This happens naturally to improving performance. For example, if the array contains structures, the CLR will pin the array, pass it to the WinRT API and unpin upon return. In effect, the array's contents are passed in, the WinRT API can modify the contents and, the modified contents are returned. However, in this example, the WinRT API is violating the contract and this behavior is not guaranteed to work. And, in fact, it will not work if the API is invoked on a WinRT component that is running out-of-process.

+   - When passing a collection to a WinRT API, the CLR wraps the object with a CCW and a reference to the CCW to the WinRT API. When WinRT invokes a member on the CCW, the calling thread crosses the interop boundary, incurring a performance hit. Unlike arrays, this means that passing a collection to a WinRT API allows the API to manipulate the collection in place, and copies of the collection's elements are not created.
