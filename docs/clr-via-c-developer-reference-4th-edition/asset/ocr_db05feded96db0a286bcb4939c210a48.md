A special-priority CLR thread is dedicated to calling Finalize methods. A dedicated thread is used to avoid thread synchronization situations that could arise if one of the application's normal-priority threads were used instead. When the finalizable queue is empty (the usual case), the thread sleeps. When entries appear, this thread wakes, removes each entry from the queue, and calls each object's Finalize method. Because of this thread works, you shouldn't execute any code in a Finalize method that makes any assumptions about the thread that's executing the code. For example, accessing thread-local storage in the Finalize method.

In the future, the CLR may use multiple threads. You should avoid writing any code that assumes Finalize methods will be called serially. With just one finalizer thread, there could be performance and scalability issues in the scenario in which multiple CPUs finalizing objects but only one thread executing Finalize methods—the one thread might not be able to keep up with the allocations.

The interaction between the finalization list and the finalizable queue is fascinating. First, I'll tell you how the finalizable queue gets its name. The "F" is obvious and stands for *finalization*; every entry in the finalizable queue is a reference to an object in the managed heap that has its Finalize method called. But the *reachable* part of the name means that the objects are reachable. To put it another way, the finalizable queue is considered a root, just as static fields are roots. So a reference in the finalizable queue keeps the object reachable and is not garbage.

In short, when an object is unreachable, the garbage collector collects the object to be garbage. When the garbage collector moves an object's reference from the finalization list to the final-able queue, the object is no longer considered garbage and its memory can't be reclaimed. When an object is garbage and not garbage, we say that the object has been *resurrected*.

As finalizable objects are marked, objects referred to by their reference fields are also marked recursively; all these objects must get resurrected in order to survive the collection. At this point, the garbage collector has finished identifying garbage. Some of the objects as garbage have been resurrected. The garbage collector collects the reclaimable memory, which promotes the resurrected object to an older generation (not ideal). And now, the special finalization thread enters the finalizable queue, executing each object's Finalize method.

The next time the garbage collector is invoked on the older generation, it will see that the finalized objects are truly garbage because the application's roots don't point to it and the finalizable queue no longer points to either. The memory for the object is simply reclaimed. The important point to get from all of this is two garbage collections are required to reclaim memory used by objects that require finalization.
