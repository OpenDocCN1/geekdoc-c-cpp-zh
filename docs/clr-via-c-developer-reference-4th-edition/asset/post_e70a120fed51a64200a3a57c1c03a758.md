Here is some code that demonstrates the use of this construct.

```cs
internal sealed class Transaction : IDisposable {
    private readonly ReaderWriterSlim m_lock =
        new ReaderWriterSlim(LockRecursionPolicy.NoRecursion);
    private DateTime m_timeOfLastTransaction;

    public void PerformTransaction() {
        m_lock.EnterWriteLock();
        // This code has exclusive access to the data...
        m_timeOfLastTransaction = DateTime.Now;
        m_lock.ExitWriteLock();
    }

    public DateTime LastTransaction {
        get {
            m_lock.EnterReadLock();
            // This code has shared access to the data...
            DateTime temp = m_timeOfLastTransaction;
            m_lock.ExitReadLock();
            return temp;
        }
    }

    public void Dispose() { m_lock.Dispose(); }
}
```

There are few concepts related to this construct that deserve special mention. Reader-ReaderWriterLockSlim's constructor allows you to pass in a LockRecursionPolicy flag, which is defined as follows.

```cs
public enum LockRecursionPolicy { NoRecursion, SupportsRecursion }
```

If you pass the SupportsRecursion flag, the lock will add thread ownership and recursion behaviors to the lock. As discussed earlier in this chapter, these behaviors negatively affect the lock's performance, so I recommend you always pass LockRecursionPolicy.NoRecursion to the constructor (as I've done). For a reader-writer lock, supporting ownership and recursion is notoriously expensive, because the lock must keep track of all the reader threads that it has let into the lock and keep a separate recursion count for each reader thread. To maintain this information in a thread-safe way, the ReaderWriterLockSlim internally uses a mutually exclusive spinlock! No, not kidding.

The ReaderWriterLockSlim class offers additional methods (not shown here) that allow a reading thread to upgrade itself to a writer thread. Later, the thread can downgrade itself to a reader thread. The thinking here is that a thread could start reading the data and based on the data's contents, the thread might want to modify it. To do this, the thread would upgrade itself from a reader to writer. Having the lock support deteriorates the lock's performance, and I don't think this is a useful feature at all. Here's a why: you can't just turn itself from a reader into a writer. Other threads may be reading, and these threads will exit the lock-completely before the thread trying to upgrade to a writer. This is the same as having the reader thread exit the lock and immediately acquire it for writing.

> The FCL also ships a ReaderWriterLock construct, which was introduced in the Microsoft .NET Framework 1.0. This construct had so many problems that Microsoft introduced the ReaderWriterLock construct in .NET Framework 3.5. The team didn't improve the ReaderWriterLock construct for fear of losing compatibility with applications that they were using. Here are the problems with the ReaderWriterLock. Even without thread contention, and recursion behaviors, making the lock even slower. It favors readers over writer threads, and therefore, writer threads can get queued and are rarely serviced, resulting in denial of service problems.

# OneManyLock Class

I have created my own-writer construct that is faster than the FCL's ReaderWriterLockSlim class. My class is class OneManyLock because it allows access to one writer thread or many reader threads. The class basically looks like this:

```cs
public sealed class OneManyLock : IDisposable {
    public OneManyLock();
    public void Dispose();

    public void Enter(Boolean exclusive)
    public void Leave();
}
```

Now I'd like to give a sense of how it works. Internally, the class has an Int32 for the state of the lock, a Semaphore object that readers block on, and an AutoResetEvent object that writers block on. The Int64 state is divided into five fields as:

- Four bits represent the state of the lock itself. The possibilities are 0=Free, 1=OwnedByWriter, 2=OwnedByReadersAndWriterPending, and 4=ReservedForWriter. The other values are not used.
- Twenty bits (a number from 0 to 1,048,575) represent the number of reader threads reading (RR) that the lock has currently allowed in.
- Twenty bits represent the number of reader threads waiting (RW) to get into the lock. These threads block on the auto-reset event object.
- Twenty bits represent the number of writer threads waiting (WW) to get into the lock. These threads block on the other semaphore object.

The code is inside the Ch30-1-HybridThreadSync.cs file is part of the code that accompanies this book. Download this code. Now, because all the information the lock fits in a single Int64 field, I can manipulate this field by using the methods of the Interlocked class as the lock is incredibly fast and causes a thread block only when there is contention.

Here's what happens when a thread enters the lock for shared access.

- If the lock is Free: Set state to OwnedByReaders, RR=1, Return.
- If the lock is OwnedByReaders: RR++, Return.
- Else: RW++, Block reader thread. When the thread wakes, loop around and try again.

Here's what happens when a thread that has shared access leaves the lock.

- RR--
- RR > 0: Set state to ReservedForWriter, WW--, Release 1 blocked writer thread, Return
- If RW == 0: Set state to Free & WW == 0: Set state to Free, Return

Here's what happens when a thread enters the lock for the exclusive access:

- If the lock is Free: Set state to OwnedByWriter, Return.
- If the lock is ReservedForWriter: Set state to OwnedByWriter, Return.
- If the lock is OwnedByWriter: WW++, Block writer thread. When thread wakes, loop around and try again.
- Else: Set state to OwnedByReadersAndWriterPending, WW++, Block writer thread. When thread wakes, loop around and try again.

Here's what happens when a thread that has exclusive access leaves the lock:

- If WW == 0 && RW == 0: Set state to Free, Return
- If RW > 0: Set state to ReservedForWriter, WW--, Release 1 blocked writer thread, Return
- If WW == 0 && RW > 0: Set state to Free, Wake all readers

Let's say there is currently one thread reading and another wants to lock. After a CountdownEvent's CurrentCount reaches 0, it cannot be changed. The AddCount method throws InvalidOperationException when CurrentCount is 0, whereas the TryAdd method simply returns false if CurrentCount is 0.

To solve this, all reader-writer locks perform more logic than Interlocked. When I perform tests comparing my OneManyLock against FCL, I get the following results:

| :--- | :--- |
| Incrementing x in OneManyLock | Fastest |
| Incrementing x in ReaderWriterSlim | ~1.7x slower |
| Incrementing x in ReaderLock | ~3x slower |
