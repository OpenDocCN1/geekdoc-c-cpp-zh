
To load an assembly specifying a path name, you call Assembly.LoadFrom method.

```c
public class Assembly {
    public static Assembly LoadFrom(String path);
    // Less used overloads of LoadFrom are not shown
}
```

Internally, LoadFrom calls System.Reflection.AssemblyName's static GetAssemblyName method which opens the specified file, finds AssemblyDef metadata table's entry, and extracts the assembly identity information and returns it in a System.Reflection.AssemblyName (the file is also closed). Then, LoadFrom internally calls Assembly's Load method, passing the AssemblyName object. At this point, the CLR performs a version-binding redirection policy and searches the various locations looking for a matching assembly. If Load finds the assembly, it will load it, and an Assembly object that represents the loaded assembly will be returned; Load returns its value. If Load fails to find an assembly, LoadFrom loads the assembly at the path name specified in LoadFrom's argument. Or, if an assembly with the same identity is already loaded, LoadFrom simply returns an assembly object that represents the already loaded assembly.

By the way, the LoadFrom allows you to pass a URL as an argument. Here is an example:

```csharp
Assembly a = Assembly.LoadFrom("http://Wintellect.com/SomeAssembly.dll");
```

When you pass an Internet location, the CLR downloads the file, installs it into the user's cache, and loads the file data. Note that you may be online or an exception will be thrown. If the file has been downloaded previously, and if Windows Internet Explorer has been set to work offline (see Internet Explorer's Work Offline menu in its File menu), the previously downloaded file will be used, and no exception will be thrown. You can also call UnsafeLoadFrom, which can load a web-downloaded assembly, bypassing security checks.

> **Important**: It is possible to have different assemblies on a single machine with all the same identity. Because LoadFrom calls internally, it is possible that the CLR will not load the specified file and will load a different file, giving you unexpected behavior. It is highly recommended that you build of your assembly the version number; this ensures that each version has its own identity, and because of this, LoadFrom will work as expected.

Visual Studio's UI designers and other tools typically use Assembly's LoadFile method. This method can load an assembly from any path and can be used to load an assembly with the same identity multiple times into a single AppDomain. This can happen as changes to an application's UI are made in the designer/tool and the user reloads the assembly. When loading an assembly via LoadFile, the CLR will not resolve any dependencies automatically; your code must register with AppDomain's AssemblyResolve event and have your callback explicitly load any dependent assemblies.

If you are building a tool that simply analyzes an assembly's metadata by reflection (as discussed later in this chapter), and you want to ensure that none of the code contained inside the assembly executes, the best way for you to load an assembly is to use Assembly's ReflectionOnlyFrom method, or in some rarer cases, Assembly's ReflectionOnlyLoad method. Here are the prototypes of both methods.

```csharp
public class Assembly {
    public static Assembly ReflectionOnlyLoad(String assemblyFile);
    public static Assembly ReflectionOnlyLoad(String assemblyString);
    // commonly used overload of ReflectionOnlyLoad is not shown
}
```

The ReflectionOnlyLoad method will load the file by the path; the strong name of the identity is not obtained, and the file is not searched in the GAC or elsewhere. The ReflectionOnlyLoad method will search for the specified assembly in the GAC, application base directory, private paths, and codebases. However, unlike the Load method, ReflectionOnlyLoad method does not apply versioning policies, so you will get the exact that you specify. If you want to apply versioning yourself to an assembly identity, you can pass a string into AppDomain's ApplyPolicy method.

When an assembly is loaded with ReflectionOnlyFrom or ReflectionOnlyLoad, the CLR forbids any code from executing; any attempt to execute code in a loaded assembly using either of these methods causes the CLR to throw an InvalidOperation. These methods allow to load an assembly that was delay-signed, would normally require security permissions to prevent it from loading, or were created for a different CPU architecture.

Frequently, using reflection to analyze an assembly loaded with one of these two methods, the code will have to register a callback method with AppDomain's ReflectionOnlyAssembly-Resolve event to manually load any referenced assemblies (calling AppDomain's ApplyPolicy method, if desired); the CLR doesn't do it automatically for you. When the callback is invoked, it must call Assembly's ReflectionOnlyLoadFrom or ReflectionOnlyLoad method to explicitly load referenced assembly and return a reference to this.

> **Note**: people often ask about assembly unloading. Unfortunately, the CLR doesn't support the ability to unload individual assemblies. If the CLR allowed it, your application would crash if a thread returned from a method code to the unloaded assembly. The CLR is all about robustness, security, and allowing an application to crash in this way would be counterproductive to its goals. If you want to unload an assembly, you must unload the entire AppDomain that contains. This was discussed in great detail in Chapter 22.

It would seem that assemblies loaded with either ReflectionOnlyLoadFrom or ReflectionOnlyLoad method could be unloaded. After all, in these assemblies it is not allowed to execute. However, the CLR also doesn't allow assemblies loaded via either these two methods to be unloaded. The reason is that after an assembly is loaded this way, you still use reflection to create objects that refer to the metadata defined inside these assemblies. Keeping track would be expensive in terms of execution speed.

Many applications use an EXE file that depends on many DLL files. When deploying this application, however, there is a technique that you can use to deploy a single file. First, add these DLLs to Visual Studio project. For each DLL, select its properties and change the Build Action to Embedded Resource. This causes the C# compiler to embed the DLL(s) into your EXE, and you can initialize a callback method with the AssemblyResolve event. The code should look something like this:

```csharp
private static ResolveEventHandler(Object sender, ResolveEventArgs args) {
  String dllName = new Assembly(args.Name) + ".dll";

  var assemble = Assembly.ExecutingAssembly();
  String resourceName = assemble.GetResourceNames().FirstOrDefault(name => name.EndsWith(dllName));
  if (resourceName == null) return null; // Found, maybe another handler will find it
  using (var stream = assemble.GetResourceStream(resourceName)) {
    Byte[] assemblyData = new Byte[stream.Length];
    stream.Read(assemblyData, 0, stream.Length);
    return Assembly.Load(assemblyData);
  }
}
```
Now, the first time a method calls that references a type in a dependent DLL, the AssemblyResolve event will be raised and the preceding callback code will find the embedded resource and load it.

# Using Reflection to Build a Dynamically Extensible Application

As you know, metadata is stored in a bunch of tables. When you build an assembly or a module, the compiler that you're using creates a type definition table, a field definition table, a method table, and so on. The System.Reflection namespace contains several types of tables that allow you to write code that reflects over (or parses) these tables. In effect, the types in this namespace offer an object model over the metadata contained in an assembly or module.

Using these object model, you can easily enumerate all of the types in a type metadata table. For each type, you can obtain its base type, the interfaces it implements, and the flags that are associated with that type. Additional types in the System.Reflection namespace allow you to query the type's fields, methods, and events. You can also discover any custom attributes (covered in Chapter 18, "Custom Attributes") that have been applied to any of the metadata entities. There are even classes that let you determine referenced assemblies and methods for a method. With all of this information, you could easily build a tool very similar to Microsoft's ILasm.exe.
