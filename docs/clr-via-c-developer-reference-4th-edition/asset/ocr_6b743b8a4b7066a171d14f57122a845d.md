You'll notice that these methods return Boolean that indicates the String passed in contains characters that can be parsed into an Int32. These methods also return an output parameter result. If the methods return true, result will contain the result of parsing the string into a 32-bit integer. If the methods return false, result will contain 0, but you really shouldn't execute any code that looks at it anyway.

One thing I want to make absolutely clear: A Tryxxx's Boolean return values false to indicate one and only type of failure. The method should still throw exceptions for any other type of failure. For example, Int32's TryParse throws ArgumentException if the style is not valid, and it is certainly possible to have an OutOfMemoryException thrown when calling TryParse.

I also want to make clear that the thread object-oriented programming allows programmers to be productive. One way that it does is by not exposing error codes in a type's. In other words, constructors, methods, properties, etc. are all defined with the idea that calling wont fail. And, if defined correctly, for most of a member, it will not fail, and there will be no performance hit because an exception will not thrown.

When defining types and members, you should define the members so that it is unlikely they will fail for the common scenarios in which you expect your types to be used. If you later find from users who are dissatisfied with the performance due to exceptions being thrown, and then should you consider adding Tryxxx methods. In other words, you should produce the best object model first, and, if users push back, add some Tryxxx to your type so that the users experience performance trouble can benefit. Users who are not experiencing performance trouble should continue to use the non-Tryxxx versions of the methods because this is the better object model.

# Constrained Execution Regions (CERs)

Many applications don't need to be robust and recover from any and all kinds of failures. This is true of many client applications like Notepad.exe and Cal.exe. And, of course, many of us have seen Microsoft Office applications like Word.exe, Excel.exe, and Outlook.exe terminate due to unhandled exceptions. Also, many-side applications, like web servers, are stateless and automatically restarted if they fail due to an unhandled exception. Of course some servers, like SQL Server, are all about state management and having data loss due to an unhandled exception is potentially much disastrous.

In the CLR, we have AppDomains (discussed in Chapter 22), which contain state. When an AppDomain is unloaded, all its state is unloaded. And if a thread in an AppDomain experiences an unhandled exception, it is OK to unload the AppDomain (which destroys all its state) without terminating the whole process.

> 8 This is definitely true if the thread lives its life inside a single AppDomain (like the ASP.NET and managed SQL Server stored procedures). But you might have to terminate the whole process if a thread crosses AppDomain boundaries during its lifetime.
