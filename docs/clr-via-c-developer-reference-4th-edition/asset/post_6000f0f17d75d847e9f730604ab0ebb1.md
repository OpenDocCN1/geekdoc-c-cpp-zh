The size of public keys makes them difficult to work with. To make things easier for the developer (and for end users), public tokens are created. A public token is a 64-bit hash of the public key. SN.exe's -tp switch shows the public key token that corresponds to the complete public key at the end of its output.

Now how to create a public/private key pair, creating a strongly named assembly is simple. When you compile your assembly, use the /keyfile:<file> compiler switch.

```
csc /keyfile:MyCompany.snk Program.cs
```

When the C# compiler sees this, the compiler opens the specified file (MyCompany.snk), signs the assembly with the private key, and embeds the public key in the manifest. Note that you sign only the assembly file that contains the manifest; the other's files cannot be signed.

If you are using Visual Studio, you can create a public/private key pair by displaying the properties for your project, clicking the Signing tab, selecting the Sign Assembly check box, and then choosing the <New.../> option from the Strong Name Key box.

> In this example, I am using Enhanced Signing, which was introduced in .NET Framework 4.5. If you need to produce an assembly that is compatible with previous versions of the .NET Framework, you will also have to create a counter-signature by using the AssemblyKeyAttribute. For details about this, see: mdn.microsoft.com/en-us/library/hh451055(v=10).assembly.

Here's what it means to sign a file: When you build a strongly assembled, the assembly's FileDef manifest metadata table includes the list of all the files that make up the assembly. As each file's name is added to the manifest, the file contents are hashed, and this hash value is stored along with the file's name in the FileDef table. You can override the default hash algorithm used with /EXalgid switch or apply the assembly-level System.Reflection.AssemblyAlgorithmID custom attribute in the assembly's source code files. By default, a SHA-1 algorithm is used.

After the PE file containing the manifest is built, the PE file's contents (except for any Authenticode Signature, the assembly's strong name data, and the PE header checksums) are hashed, as shown in Figure 3-1. This hash value is signed with the publisher's private key, and the resulting RSA digital signature is stored in a reserved section (not included in the hash) within the PE file. The CLR header of the PE file is updated to reflect where the digital signature is embedded within the file.

At this point, the assembly and all of its files are ready to be packaged and distributed.

As described in Chapter 2, when you compile your source code, the compiler detects the types and members that your code references. You must specify the referenced assemblies to the compiler. For the C# compiler, you use the /reference compiler switch. Part of the compiler's job is to emit an AssemblyRef metadata table inside the resulting managed module. AssemblyRef metadata table indicates the referenced assembly name (without path and extension), version number, culture, and public key information.

# Important
Because public keys are such large numbers, and a single assembly might reference many assemblies, a large percentage of the resulting file's total size would be occupied with public key information. To conserve storage space, Microsoft hashes the public key and takes the last 8 bytes of the hashed value. These reduced public key values—known as public tokens—are actually stored in an AssemblyRef table. In general, developers and end users will use public key tokens much more frequently than full public keys.

Note, however, that the CLR never uses public tokens when making security or trust decisions because it is possible that several public keys could hash to a single public token.

# The Global Assembly Cache
Now that you know how to create a strongly named assembly, it's time to learn how to deploy this assembly and how the CLR uses the information to locate and load.

If an assembly is to be accessed by multiple applications, the assembly must be placed into a well-known directory, and the CLR must know to this directory automatically with a reference to the assembly is detected. This well-known location is called the global assembly cache (GAC). The exact location of the GAC is an implementation detail that is subject to change with different versions of the .NET Framework. However, you can typically find it in the following directory:

```
%SystemRoot%\Microsoft.NET\Assembly
```

The GAC directory is structured. It contains many subdirectories, and an algorithm is used to generate the names of these subdirectories. You should never manually copy assembly files into the GAC; instead, you use tools to accomplish this task. These tools know the GAC's internal structure and how to generate the proper subdirectory names.
