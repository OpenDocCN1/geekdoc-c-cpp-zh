
...out; never in and out. This means you can't refer to a method again, but `out` is OK. For more information about this, see the "Arrays" bullet point in the next

- Properties: WinRT properties must specify only WinRT-compatible types for that data type. WinRT does not support parameterful properties or write-only properties.

- Delegates: WinRT delegate must specify only WinRT components for parameter types and return types. When passing a delegate to a WinRT component, the delegate object is wrapped with a CCW and will not get garbage collected until the CCW is released by the WinRT component consuming it. WinRT delegates do not have `BeginInvoke` and `EndInvoke` methods.

- Events: WinRT components can expose events using a WinRT delegate type. Because most WinRT components are sealed (no inheritance), WinRT defines a TypedEventHandler delegate where the sender is a generic type (as opposed to System.Object).

```cs
public void EventHandler<T>(TSender sender, TResult args);
```

There is also a `Windows.Foundation.EventHandler<T>` WinRT delegate type that allows the CLR projects as .NET Framework's `System.EventHandler<T>` delegate type.

- Exceptions: Under covers, WinRT components, like COM components, indicate their status via HRESULT values (32-bit integer with special semantics). The CLR projects WinRT values of type `Windows.Foundation.HResult` as exception. When a WinRT API returns a well-known failure HRESULT value, the CLR throws an instance of a corresponding Exception-derived class. For instance, the HRESULT 0x800700EE (EOFMEMORY) is mapped to a `System.OutOfMemoryException`. Other HRESULT values allow the CLR to throw a `System.Exception` object property contains the HRESULT value. A WinRT component implemented in C# can throw an exception of a desired type and the CLR will convert it to an appropriate HRESULT value, assign a specific HRESULT value in the HResult property, and then throw the object.

- Strings: Of course, you can pass immutable strings between the WinRT and CLR types. However, the WinRT type system doesn't allow a string to have value null. If you pass `null` to a string parameter of a WinRT API, the CLR detects this and throws an `Argument-NullException`; instead, use `String` to pass an empty string into a WinRT API. Strings are passed by reference to a WinRT API; they are pinned on the way and unpinned return. Strings are always copied when returned from a WinRT API. When passing a CLR string array (`String[]`) to or from a WinRT API, a copy is made with all its elements and the copy is passed or returned to the other side.

- Dates and Times: The WinRT `Windows.Foundation.DateTime` structure represents a UTC date/time. The CLR projects the WinRT `DateTime` structure as the .NET Framework's `System.DateTimeOffset` structure, because `DateTimeOffset` is preferred over the .NET Framework's `System.DateTime` structure. The CLR converts the UTC date/time returned from a WinRT to the local resulting `DateTimeOffset` instance. The CLR passes a `DateTimeOffset` to a WinRT API at a UTC time.

- Uri: The CLR projects the WinRT `Windows.Foundation.Uri` type as the .NET Framework's `System.Uri` type. When passing a .NET WinRT `Uri` to a WinRT API, the CLR throws an `ArgumentException` if the URI is a relative; WinRT supports absolute URIs only. URIs are always copied across the interop boundary.

- Iable: The CLR projects the WinRT `Windows.Foundation.IClosable` interface (which has only a `Close` method) as the .NET Framework's `System.IDisposable` interface (with a `Dispose` method). One thing to really note here is that not all WinRT APIs that perform I/O operations are implemented asynchronously. Because `IClosable`'s method is `Close` and is not `CloseAsync`, the `Close` method must not perform any I/O operations. This is semantically different from how `Dispose` usually works in the .NET Framework. For Framework-implemented types, calling `Dispose` caches buffered data to be written before closing a device. When C# code calls `Close` on a WinRT type however I/O (like writing buffered data) will not be performed and loss of data is possible. You must be aware of this, for WinRT components that wrap output streams, you will have to explicitly call methods to prevent loss. For example, when using a `DataWriter`, you should always call its `StoreAsync` method.

- Arrays: support single-dimension, zero-based arrays. WinRT can marshal an array's elements in or out of it; never in out. Because of this, you cannot pass an array into a WinRT API, have the API modify the array's elements and then access the modified elements after the API returns. I have described the contract that should be adhered to. However, this is not actively enforced, so it is possible that some projections might marshal array contents both in and out. This happens naturally to improving performance. For example, if the array contains structures, the CLR will pin the array, pass it to the WinRT API and unpin upon return. In effect, the array's contents are passed in, the WinRT API can modify the contents and, the modified contents are returned. However, in this example, the WinRT API is violating the contract and this behavior is not guaranteed to work. And, in fact, it will not work if the API is invoked on a WinRT component that is running out-of-process.

- When passing a collection to a WinRT API, the CLR wraps the object with a CCW and a reference to the CCW to the WinRT API. When WinRT invokes a member on the CCW, the calling thread crosses the interop boundary. Unlike arrays, this means that passing a collection to a WinRT API allows the API to manipulate the collection in place, and copies of the collection are not created. Table 25-1 shows the WinRT collection interfaces and how the CLR projects them to .NET code. This means you can't have an API like `Array.Sort`. Interestingly, all the languages (C++, Visual Basic, and JavaScript) support passing array elements in and out, but the WinRT type system does not.

## Framework Projections

When the CLR can't implicitly project a WinRT type to the .NET Framework, the developer must resort to explicitly using framework projections. There are three main technologies where framework projections are required: asynchronous programming, interoperating between WinRT streams and .NET Framework streams, and when passing blocks of data between the CLR and WinRT APIs. Because many applications require the use of these technologies, it is important that you understand them and use them effectively.

### Calling Asynchronous WinRT APIs from .NET Code

When a thread performs an I/O operation asynchronously, the thread can block for an indefinite amount of time. When a GUI thread waits for a synchronous I/O operation to complete, the application's user interface stops responding to user input, such as touch, mouse, and stylus events, causing the user to get frustrated with the application. To prevent non-responsive applications, WinRT components that perform I/O operations expose the functionality via asynchronous APIs. In fact, WinRT components that perform compute operations also expose this functionality via asynchronous APIs if the CPU operation could take greater than 50 milliseconds. For more information about building responsive applications, see Part V, “Threading” of this book.
