# How Hosts Use AppDomains

So far, I've talked about hosts and how they load the CLR. I've also talked about how the hosts tell the CLR to create and unload AppDomains. To make the discussion more concrete, I'll describe some common hosting and AppDomain scenarios. In particular, I'll explain how different application types host the CLR and how they manage AppDomains.

# Executable Applications

Console UI applications, NT Service applications, Windows Forms applications, and Windows Presentation Foundation (WPF) applications are all examples of self-hosted applications that have managed EXE files. When Windows initializes a process by using a managed EXE file, Windows loads the shim, and the shim examines the CLR header information contained in the assembly (the EXE file). The header information indicates the version of the CLR that was used to build and test the application. The shim uses this information to determine which version of the CLR to load into the process. After the CLR loads and initializes, it examines the assembly's CLR header to determine which method is the application's entry point (Main). The CLR invokes this method, and the application is now up and running.

As the code runs, it accesses other types. When referencing a type contained in another assembly, the CLR locates the necessary assembly and loads it into the same AppDomain. Any additionally referenced assemblies also load into the same AppDomain. When the Main method returns, the Windows process terminates (destroying the default AppDomain and all other AppDomains).

> Note By the way, you can call System.Environment static Exit method if you want to shut down the Windows process including all of its AppDomains. Exit is the most graceful way of terminating a process because it calls the Finalize methods of all the objects on the managed heap and releases all of the unmanaged COM objects held by the CLR. Finally, Exit calls the Win32 Exit function.

It is possible for the application to tell the CLR to create additional AppDomains in the process's address space. In fact, this is what my CH22-1-AppDomains application did.

# Microsoft Silverlight Rich Internet Applications

Microsoft Silveright runtime technology uses a special CLR that is different from the normal desktop version of the .NET Framework. After the Silverlight runtime is installed, navigating to a website that uses Silveright calls the CLR (ClrDll) to load in your browser (which may or not be Windows Internet Explorer—you may not be using a Windows machine). Each Silverlight control on the page runs in its own AppDomain. When the user closes tabs or navigates to another website, Silveright controls no longer in use have their AppDomains unloaded. The Silverlight code runs in a limited-security sandbox so that it cannot harm the user or the machine in any way.
