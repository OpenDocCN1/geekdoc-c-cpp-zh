
```cs
namespace CompanyB
public class BetterPhone : CompanyA.Phone {
    // Delete the Dial method (inherit Dial from base).

    // Remove 'new' and change 'virtual' to 'override' to
    // mark this method as having a relationship to the base
    // type's EstablishConnection method.
    protected override void EstablishConnection() {
        Console.WriteLine("BetterPhone.EstablishConnection");
        // Do not work to establish the connection.
    }
}
```

Now when the same application code (in the Main method) executes, the output is as follows.

Phone.Dial

This output shows that Main's call to Dial calls the Dial method defined by Phone and inherited by BetterPhone. Then when Phone's Dial method calls the virtual EstablishConnection method, BetterPhone's EstablishConnection method is called because it overrides the virtual EstablishConnection method defined by Phone.

In this chapter, I'll show you how to add data members to a type. Specifically, we'll look at constants and fields.

## Constants

A constant is a symbol that has a never-changing value. When defining a constant symbol, the compiler then saves the constant's value in the assembly metadata. This means that you can define a constant only for types that your compiler considers primitive types. In C#, the following types are primitives and can be used to define constants: Boolean, Char, Byte, SByte, Int16, UInt16, Int32, UInt32, Int64, UInt64, Single, Double, Decimal, and String. However, C# also allows you to define a constant variable of a non-primitive type if you set the value to null.

using System;

```cs
public sealed class SomeType {
    // SomeType is not a primitive type but C# does allow
    // a constant variable of this type to be set to 'null'
    public const SomeType Empty = null;
}
```

Because a constant value never changes, constants are always considered to be part of the definition. In other words, constants are always considered to be static members, not instance members. Defining a constant causes the creation of metadata.

When code refers to a constant symbol, compilers look up the symbol in the metadata of the assembly that defines the constant, extract the constant's value, and embed the value in the emitted Intermediate Language (IL) code. Because a constant's value is embedded directly in code, constants don't require any memory to be allocated for them at runtime. In addition, you can't get the address of a constant and can't pass a constant by reference. These constraints also mean that constants don't have a good cross-assembly versioning story, so you should use them when you know that the value of a symbol will never change. (Defining MaxInt16 as 32767 is a good example.) Let me demonstrate exactly I mean. First, take the following code and compile it into a DLL assembly.

using System;

```cs
public sealed class SomeLibrary {
    // NOTE: C# doesn't allow you to specify static for constants
    // because constants are always implicitly static.
    public const Int32 MaxEntriesInList = 50;
}
```

Then use the following code to build an application assembly.

using System;

```cs
public sealed class Program {
    public static void Main() {
        Console.WriteLine("Max entries supported in list: " + \n + SomeLibrary.MaxEntriesInList);
    }
}
```

You'll notice that this code reference uses the MaxEntriesInList constant in the SomeLibrary class. When the compiler builds the application code, it sees that MaxEntriesInList is a constant with a value of 50 and embeds the Int32 value of 50 inside the application's IL, as you can see in the following IL code. In fact, after building the assembly, the DLL assembly isn't even loaded at runtime and can be deleted from the disk because the compiler does not add a reference to the DLL assembly in the application's metadata.

```il
.method public hidevisibility static void Main() cil managed {
    .entrypoint
    // Code size 25 (0x19)

.maxstack 8
IL0000: nop
IL0001: ldstr "Max entries supported in list: "
IL0006: ldc.i4 50
IL000b: box [mscorlib]System.Int32
IL000d: call [mscorlib]System.String::Concat(object,object)
IL0012: call void [mscorlib]System.Console::WriteLine(string)
IL0017: nop
IL0018: ret
} // end of method Program::Main
```

This example should make the version problem obvious to you. If the developer changes MaxEntriesList constant to 1000 and only rebuilds the DLL assembly, the application assembly is not affected. For the application to pick up the new value, it will have to be recompiled as well. You can't use constants if you need to have a value in one assembly picked up by another at runtime (instead of compile time). Instead, you can use readonly fields, which I'll discuss next.

## Fields

A field is a data member that holds an instance of a value type or a reference type. Table 7-1 shows the modifiers that can be applied to a field.

| CLR Term | C# Term | Description |
| :--- | :--- | :--- |
| Static | static | The field is part of the type's state, opposed to being part of object's state. |
| Instance | (default) | The field is associated with an instance of the type, not the type itself. |
| InitOnly | readonly | The field can be written only within a constructor method. |
| Volatile | volatile | Code that accesses the field is not subject to thread-unsafe optimizations that may be performed by the compiler, the CLR or by hardware. |

As Table 7-1 shows, the common language runtime (CLR) supports both (static) and instance (non-static) fields. For instance fields, only the following types can be marked as volatile: all reference types, Boolean, Byte, UInt16, Int32, Char, Int16, and all enumerated types with an underlying type of Byte, UInt16, or Int32. Volatile fields are discussed in Chapter 29, "Primitive Synchronization". The dynamic memory required to hold the field is allocated inside the type object, which is created when the type is loaded into an AppDomain (see Chapter 22, "CLR Hosting and AppDomains"), which typically happens the first time any method that references it is just-in-time (JIT)-compiled. Because fields are stored in dynamic memory, their value can be obtained at runtime. Fields also solve the versioning problem that exists with constants. The CLR supports read/write fields. Most fields are read/write fields, meaning the field's value might change multiple times as the code executes. However, readonly fields can be written only within a constructor method (which is called only once, when an object is first created). Compilers and verification ensure that readonly fields are not written by any method other than a constructor. Note that reflection can be used to modify a readonly field.

Let's take the example from the "Constants" section and fix the versioning problem by using a static readonly field. Here is the new version of the DLL assembly's code.

```cs
using System;
public sealed class SomeLibraryType {
// The static is required to associate the field with the type.
public static readonly Int32 MaxEntriesInList = 50;
}
```

This is the only rebuild you have to make; the application code doesn't have to change at all, although you must rebuild to see the new behavior. Now when the application's Main method runs, the CLR will load the DLL assembly (this assembly is now required at runtime) and grab the value of the MaxEntriesList field out of the dynamic memory allocated for. Of course, the value will be 50.

Let's say that the developer of the DLL assembly changes the 50 to 1000 and rebuilds assembly. When the application code is re-executed, it will automatically pick up the new value: 1000. In this case, the application code doesn't have to be rebuilt—it just works (although its performance is adversely affected). A caveat: this scenario assumes that the new version of the DLL assembly is not strongly named and the versioning policy of application is that this new version be 50.

The following example shows how to define a readonly static field that is associated with the type itself, as well as read/write static fields and readonly/read/write instance fields, as shown here.

```cs
public sealed class SomeType {
// This is a static read-only field; its value is calculated and
// stored in memory when this class is initialized at run time.
    public static readonly Random s_random = new Random();

    // This is a static read/write field.
    private static Int32 s_numberOfWrites = 0;

    // This is an instance read-only field.
    public readonly String Pathname = "Untitled";

    // This is an instance read/write field.
    private System.IO.FileStream m_fs;

    public SomeType(String pathname) {
    // This line changes a read-only field.
    // This is OK because the code is in a constructor.
    this.Pathname = pathname;
}

    public String DoSomething() {
    // This line reads and writes to the static read/write field.
    s_numberOfWrites = s_numberOfWrites + 1;

    // This line reads the read-only instance field.
    return Pathname;
}
}
```
