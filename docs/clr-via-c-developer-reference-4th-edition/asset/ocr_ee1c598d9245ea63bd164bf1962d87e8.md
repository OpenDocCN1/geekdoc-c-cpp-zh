**Under most circumstances, you should avoid calling any of the Collect methods;** it's best just to let the garbage collector run on its own account and fine-tune its generations based on actual application behavior. However, if you are writing a user interface (UI) or GUI application, your application codes the process and GC in that process. For these application types, *you might* suggest a garbage collection to occur at certain times using a GCCollectionMode of Optimized. Normal modes of Default and Forced are used for debugging, and looking for memory leaks.

For example, you might consider calling the Collect method if some non-recurring event has occurred that has caused a lot of objects to die. The reason that calling Collect in a circumstance may not be so bad is the GC's predictions of the future based on the past are not likely to be accurate for non-recurring events. For example, it might make sense for your application to force a full GC of all generations after your initializes or after the user saves a data file. Because *Collect* causes the generation budgets to adjust, do not call Collect to try to improve your application's response time; call to reduce your working set.

For some applications (especially servers that tend to keep a lot of objects in memory), the time required for the GC to do a full collection that includes generation 2 can be excessive. If, the collection takes a very long time, clients request more time out. To help these kinds of applications, the GC class offers a RegisterFullGCNotification method. Using this method and another helper methods (WaitForFullGCApproach, WaitForFullGCComplete, and CancelFullGCNotification), an application can be notified when the garbage collector is getting close to performing a full collection. The application can then call.Collect to force a collection at a more opportune time, or the application could communicate with another server to better load the client requests. For more information, examine these methods and the "Garbage Collection Notifications" in the Microsoft .NET SDK documentation. Note that you should always call the WaitForFullGCApproach and WaitForFullGCComplete methods in pairs because the CLR handles them as pairs internally.
