
# Properties and the Visual Studio Debugger

Microsoft Visual Studio allows you to inspect an object's property in the debugger's window. When you do this, every time you hit a breakpoint, the debugger calls the property's getter method and displays the returned value. This can be quite helpful in tracking down bugs, but it can also cause bugs to hurt your debugger performance. For example, let's say you have created a FileStream for a file on a network share and then you add FileStream's Length to the debugger's watch window. Now every time you hit a breakpoint, the debugger will call Length's getter method, which internally makes a network request to the server to get the current length of the file!

Similarly, if your property gets a side effect, this side effect will execute every time you hit a breakpoint. For example, let's say your property's getter method increments a counter every time you hit a breakpoint. Because of these potential problems, Visual Studio allows you to turn off evaluation for properties in watch windows. To turn property evaluation off in Visual Studio, select Tools, Options, Debugging, and the list in Figure 10-1, and clear the Enable Property Evaluation And Other Implicit Function calls box. Note that with this item cleared, you can add the property to the watch window and manually force Visual Studio to evaluate it by clicking the force evaluation circle in the watch window's Value column.

# Object and Collection Initializers

It is very common to construct an object and then set some of the object's public properties (or fields). To simplify this common programming pattern, the C# language supports a special object initialization syntax. The following is an example.

```cs
Employee e = new Employee { Name = "Jeff", Age = 45 };
```

With this statement, I am constructing an Employee object, calling its parameterless constructor, and then setting its Name property to "Jeff" and its Age to 45. The preceding code is identical to the following, which you could verify by examining the Intermediate Language (IL) for both of these code fragments

```cs
Employee tempVar = new Employee();
tempVar.Name = "Jeff";
tempVar.Age = 45;

// Only assign to e if the assignments don't throw an exception.
// This prevents e from referring to a partially initialized object.
Employee e = tempVar;
```

The real benefit of the object initializer syntax is that it allows you to code in an expression (as opposed to a statement context), permitting composability of functions, which then, using the resulting expression, increases code readability. I can write the following:

```cs
String s = new Employee { Name = "Jeff", Age = 45 }.ToString().ToUpper();
```

So now, in one statement, I have constructed an Employee object, calling its constructor, initialized two public properties, and then, using the resulting expression, to ToString on it followed by calling ToUpper. For more composability of functions, see the "Extension Methods" section in Chapter 8, "Methods".

As a small note, C# also lets you omit the parentheses before you want to call a parameterless constructor. The following line produces the same result as the preceding line.

```cs
String s = new Employee { Name = "Jeff", Age = 45 }.ToString().ToUpper();
```

If a type implements the IEnumerable or IEnumerable<T> interface, then the property is considered to be a collection, and initializing a collection is an additive operation as opposed to a replacement operation. For example, suppose I have the following class definition:

```cs
public sealed class Classroom {
    private List<String> m_students = new List<String>();
    public List<String> Students { get { return m_students; } }

    public Classroom() {}
}
```

I can now have code that constructs a Classroom object and initializes the Students collection as follows.

```cs
public static void M() {
    Classroom classroom = new Classroom {
    Students = { "Jeff", "Kristin", "Aidan", "Grant" };
    };
}
```

```cs
// Show the 4 students in the classroom
foreach (var student in classroom.Students)
    Console.WriteLine(student);
```

When compiling this code, the compiler sees that the Students property is of type List<String> and that this type implements the IEnumerable<String> interface. Now, the compiler assumes that the List<String> type offers a method Add (because collection classes actually offer an Add method that adds items to the collection). The compiler generates code to call the collection's Add method. So, the preceding code is converted by the compiler into the:

```cs
public static void M() {
    Classroom classroom = new Classroom();
    classroom.Students.Add("Jeff");
    classroom.Students.Add("Kristin");
    classroom.Students.Add("Aidan");
    classroom.Students.Add("Grant");
}
```

```cs
// Show the 4 students in the classroom
foreach (var student in classroom.Students)
    Console.WriteLine(student);
```

If the property's type implements IEnumerable or IEnumerable<T> but the type doesn't offer an Add method, then the compiler does not let you use the collection syntax to add items to the collection; instead, the compiler issues the following message: error CS0117: 'System.Collections.Generic.IEnumerable<string>' does not contain a definition for 'Add'.

Some Add methods take multiple arguments—for example, Dictionary's Add method.

```cs
public void Add(TKey key, TValue value);
```

You can pass multiple arguments to an Add method by using nested braces in a collection initializer.

```cs
var table = new Dictionary<String, Int32> {
    { "Jeffrey", 1 }, { "Kristin", 2 }, { "Aidan", 3 }, { "Grant", 4 } };
```

The pre-ceding line is identical to the following.

```cs
var table = new Dictionary<String, Int32>();
table.Add("Jeffrey", 1);
table.Add("Kristin", 2);
table.Add("Aidan", 3);
table.Add("Grant", 4);
```

# Anonymous Types

C#'s anonymous type feature allows you to automatically declare an immutable tuple type by using a very simple and succinct syntax. A tuple type is a type that contains a collection of properties that are usually related to each other in some way. In the top line of the code, I am defining a class with two properties (Name of String, and Year of type Int32), constructing an instance of this type, and setting its Name to "Jeff" and its Year to 1964.

```cs
// Define a type, construct an instance of it, initialize its properties
var ol = new { Name = "Jeff", Year = 1964 };
```

```cs
// Display the properties on the console:
Console.WriteLine("Name={0}, Year={1}", ol.Name,ol.Year);// Displays: Name=Jeff, Year=1964
```

This line of code creates an anonymous type because I did not specify a name after the new keyword; the compiler will create a type name for me and not tell me what it is (which is why it is called an anonymous type). The line of code uses object initializer syntax discussed in the previous section to declare the properties and also to initialize them. Also, because I (the developer) do not know the name of the type at compile time, I do not know what type to declare the variable as. However, this is not a problem, I can use C#'s typed variable feature (var), as discussed in Chapter 9, "Parameters", to have the compiler infer the type from the expression on the right of the operator (=).

, let's focus on what the compiler is actually doing. When you write a line of code like:

```cs
var o = new { property1 = expression1, ..., propertyN = expressionN };
```

the compiler infers the type of each expression, creates private fields of these inferred types, creates public read-only properties for each of the fields, and creates a constructor that accepts all these expressions. The constructor's code initializes the read-only fields from the expression results passed in to it. In addition, the compiler overrides Object's Equals, GetHashCode, and ToString methods and generates code inside all these methods. In effect, the class that the compiler generates looks like this:

```cs
[CompilerGenerated]
internal sealed class <f_AnonymousType0<...>: Object {
    private readonly T f1;
    public T p1 { get { return f1; }
}
```

> The term originated as an abstraction of the sequence: single, double, triple, quadruple, quintuple, n-tuple.
