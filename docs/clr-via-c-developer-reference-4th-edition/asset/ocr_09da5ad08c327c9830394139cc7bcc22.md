```
// If the Singleton was already created, return it (this is fast)
if (s_value != null) return s_value;

Monitor.Enter(s_lock); // Not created, let 1 create it
if (s_value == null) {
    // Still not created, create it
    Singleton temp = new Singleton();

    // Save the reference in s_value (see discussion for details)
    Volatile.Write(ref s_value, temp);
}
Monitor.Exit(s_lock);

// Return a reference to the one Singleton object
return s_value;
```

The idea behind the double-checking locking technique is that a call to the GetSingleton method quickly checks the s_value field to see if the object has already been created, and if it has, the method returns a reference to it. The beautiful thing here is that no synchronization is required after the object has been constructed; the application will run very fast. On the other hand, if the first thread calls the GetSingleton sees that the object hasn't been created, it takes a synchronization lock to ensure that only one thread constructs the object. This means that a performance hit occurs only the first time a thread queries the singleton object.

Now, let me explain why this pattern didn't work in Java. The Java Virtual Machine read the value of s_value into a CPU register at the beginning of the GetSingleton method and then queried the register when evaluating the second if statement, causing the second statement to evaluate to true, and multiple threads creating Singleton objects. Of course, this happened only if multiple threads called GetSingleton at exactly the same time, which in most applications is very likely. This is why it didn't work in Java for so long.

In the CLR, calling any lock method is a full memory fence, and any variable writes before the fence must start after it. For the GetSingleton method, this means that the s_value must be reread after the call to Monitor.Enter; it cannot be cached in a register across this method.

Inside Singleton, you see the call to Volatile.Write. Here is the problem that this solves: Let's say what you had inside the second if statement was the following line of code.

```
s_value = new Singleton(); // This is what you'd ideally like to write
```

You would expect the compiler to produce code that allocates the memory for a Singleton, calls the constructor, and then assigns the reference into the s_value field. Making a value visible to others is called publishing. But the compiler could do this: allocate memory for the Singleton, publish (the reference into s_value, and then call the constructor. From a single thread's perspective, changing the order like this has no impact. But if, after publishing the reference into s_value and before calling the constructor, another thread calls the GetSingleton method? This thread will see that s_value is not null and start to use the Singleton
