In the preceding code, you can tell that an async function, as I specified async on the first line after static. When you mark a method async, the compiler transforms your method's code into a task that implements a state machine (the details of which are discussed in the next section). This allows to execute some code in the state machine and then return without having the method execute all the way to completion. So, when a thread calls ClientRequestAsync, the thread constructs a NamedPipeClientStream, calls Connect, sets its ReadMode property, converts the passed-in message to a Byte[] and then calls WriteAsync. WriteAsync internally allocates a Task and returns it back to ClientRequestAsync. At this point, the await operator continues with the Task passing in the method that resumes the state machine, and then returns from ClientRequestAsync.

Sometimes in the future, the network device driver will write the data to the pipe and then, a thread pool will notify the Task object, which will activate the WithCallback method, causing a thread to resume the state machine. More specifically, a thread will reenter the ClientRequestAsync method but at the point of the await operator. It executes compiler-generated code that queries the status of the Task object. If the operation failed, an exception representing the failure is thrown. If the operation completes successfully, the await operator returns the result. In this case, WriteAsync returns a Task instead of a Task<Result>.

Now, our method continues by allocating a Byte[] and then calls NamedPipeClientStream's asynchronous ReadAsync method. Internally, ReadAsync creates a Task<Int32> object and returns it. Again, the await operator continues with the Task<Int32> object and resumes the state machine. And then returns from ClientRequestAsync.

Sometimes in the future, the server will send a response back to the client manager, the network device driver gets this response, and a thread pool notifies the Task<Int32> object, which will resume the state machine. The await operator calls the compiler to generate code that queries the Task object's Result property (an Int32) and assigns the result to the bytesRead local variable or others if an exception was failed. Then, the rest of the code in ClientRequestAsync executes, returning the result string and closing the pipe. At this point, the state machine has run to completion and the garbage collector will reclaim any memory it needed.

Because async functions return before the state machine has all the way to completion, the method calling ClientRequestAsync will continue its execution right after ClientRequestAsync executes its first await operator. But, how can the caller know when ClientRequestAsync has completed its state machine in its entirety? Well, when you mark a method as async, the compiler automatically generates code that creates a Task object when the state machine begins its execution; this Task object is created automatically when the state machine runs to completion. You will notice that the IssueClientAsync method's return type is a Task<String>. It actually returns the Task<String> object that the compiler-generated code creates for its caller, and the Task's Result property is of type string in this case. Near the bottom of IssueClientAsync, I return a string. This causes the compiler-generated code to complete the Task-it created and set its Result property to the returned string.

You should be aware of the following restrictions related to async functions:

- You cannot turn your application's Main method into an async function. In addition, constructors, property accessor methods and event accessor methods cannot be turned into async functions.
- You cannot have any out or ref parameters on an async function.
- You cannot use the await operator inside a catch, finally, or unsafe block.
- You cannot take a lock that supports thread ownership or recursion before an await operator and release it after the await operator. The reason is because one thread might execute the code before the await and a different thread might execute the code after the await. If you use await within a C# lock statement, the compiler issues an error. If you explicitly use Monitor.Enter and Exit methods instead, then the compiler will compile while Monitor.Exit will throw a SynchronizationException at runtime.
- Within a query expression, the await operator may only be used within the first collection expression of the initial from clause or within the collection expression of a join clause.

These restrictions are pretty minor. If you violate one, the compiler will let you know, and you can usually work around the problem with some small code modifications.

//AsyncStateMachine attribute indicates an async method (for tools using reflection);
// the type indicates which structure element implements the state machine
[DebuggerStep, AsyncStateMachine(typeof(StateMachine))]
private static Task<String> MyMethodAsync(Int32 argument) {
    // Create state machine instance and initialize it
    StateMachine stateMachine = new StateMachine() {
        // Create builder returning Task from this stub method
        // State machine accesses builder to set Task completion/exception
        m_builder = AsyncTaskBuilder<String>.Create();

        m_state = -1; // Initialize state machine location
        m_argument = argument; // Copy arguments to state fields
    };

    // Start executing the state machine
    stateMachine.m_builder.Start(ref stateMachine);
    return stateMachine.m_builder.Task; // Return state machine's Task
}
