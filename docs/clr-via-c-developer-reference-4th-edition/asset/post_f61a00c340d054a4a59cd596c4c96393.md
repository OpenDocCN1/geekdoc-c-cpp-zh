
GroupJoin, and ToLookup. If you want to enforce ordering again after one of these operators, call the AsOrdered method.

The following operators produce ordered operations: OrderBy, OrderByDescending, ThenBy, and ThenByDescending. If you want to go back to unordered processing again to improve performance after one of these, call the AsUnordered method.

Parallel LINQ offers some additional Parallel methods that you can use to control how the query is processed.

```csharp
public static ParallelQuery<TSource> WithCancellation<TSource>(ParallelQuery<TSource> source, CancellationToken cancellationToken)
```

```csharp
public static ParallelQuery<TSource> WithDegreeOfParallelism<TSource>(ParallelQuery<TSource> source, int degreeOfParallelism)
```

```csharp
public static ParallelQuery<TSource> WithExecutionMode<TSource>(ParallelQuery<TSource> source, ExecutionMode executionMode)
```

```csharp
public static ParallelQuery<TSource> WithMergeOptions<TSource>(ParallelQuery<TSource> source, MergeOptions mergeOptions)
```

Obviously, the WithCancellation method allows you to pass a CancellationToken to the query processing can be stopped prematurely. However, you could call WithDegreeOfParallelism method to specify the maximum number of threads allowed to process the query; it does not force the threads to be created if not all of them are necessary. Usually you would not call this method, and by default, the query will execute using one thread per core. However, you could call DegreeOfParallelism, passing a number that is smaller than the number of available cores if you want to keep some cores available for doing other work. You could also pass a number that is greater than the number of cores if the query performs synchronous I/O operations because these will be blocking during these operations. This wastes more resources but can produce the final result in less time. You might consider doing this in a client application, but I'd highly recommend performing synchronous I/O operations in a server application.

Parallel LINQ analyzes a query and decides how to process it. Sometimes a query sequentially yields better performance. This is usually true when any of the following operations: Concat, ElementAt(OrDefault), First(orDefault), Last(orDefault), Skip(While), or Zip. It is also true when using overloads of Select(Many) or where that pass passes a position index into your selector or predicate delegate. However, you can force a query to be processed in parallel by calling WithExecutionMode, passing one of the ParallelExecutionMode flags.

```csharp
public enum ParallelExecutionMode {
    Default = 0, // Let Parallel LINQ decide to best process the query
    ForceParallelism = 1 // Force the query to be processed in parallel
}
```

As mentioned before, Parallel LINQ has multiple threads processing items, and then the results must be merged back together. You can control how the items are buffered and merged by calling WithMergeOptions, passing one of the ParallelMergeOptions flags.

```csharp
public enum ParallelMergeOptions {
    Default = 0, // As AutoBuffered today (could change in the future)
    NotBuffered = 1, // Results are processed as ready
    AutoBuffered = 2, // Each thread buffers some results before processed
    FullyBuffered = 3 // Each thread buffers all results before processed
}
```

These options basically give you some control over memory consumption. FullyBuffered saves memory but consumes more while running. AutoBuffered is the compromise between NotBuffered and FullyBuffered. Really, the best way to know which of these to choose for any given query is to try them all and compare their performance, or just accept the default, which works quite well for many queries. ## Performing Compute-Bound Operation

The System.Threading namespace defines a Timer class, which you can use to have a thread pool call periodically. When you construct an instance of Timer, you are telling the thread pool that you want a method called at a future time. The Timer class offers several constructors, all similar to each other.

```csharp
public sealed class Timer : MarshalObject, IDisposable {
    public Timer(TimerCallback callback, Object state, TimeSpan dueTime, TimeSpan period);
    public Timer(TimerCallback callback, Object state, int dueTime, int period);
    public Timer(TimerCallback callback, Object state, long dueTime, long period);
    public Timer(TimerCallback callback, Object state, TimeSpan dueDate, TimeSpan period);
}
```

All four constructors construct Timer object identically. The callback parameter identifies the method that you want called back by a thread pool. Of course, the callback method you write must match the System.Threading.TimerCallback delegate, which is defined as follows:

```csharp
delegate void TimerCallback(Object state);
```

The constructor's state parameter allows you to pass state to the callback method each time it is invoked; you can pass null if you have no state to pass. You use the dueDate parameter to tell the CLR how many milliseconds to wait before calling your callback for the first time. You can specify the number of milliseconds using a signed or unsigned value, or a TimeSpan value. The last parameter, period, allows you to specify how long to wait between successive calls to the callback method. If you set Timeout.Infinite for this parameter, the thread pool will call the method just once. Internally, the thread pool has one thread that knows when the next Timer object is due. When the Timer object is due, the thread wakes up and internally calls ThreadPool.QueueWorkItem to enter the thread pool's queue, causing your callback method to get called. If your callback method takes a long time to execute, this could cause multiple threads to execute simultaneously. To avoid this problem, I recommend the following: construct the Timer specifying Timeout.Infinite for period parameter. Now the timer will fire only once. Then, in your callback method, call Change method and again specify Timeout.Infinite for period parameter.

```csharp
public sealed class Timer : MarshalObject, IDisposable {
    public void Change(int dueTime, int period);
    public void Change(uint dueTime, uint period);
    public void Change(long dueTime, long period);
    public void Change(TimeSpan dueDate, TimeSpan period);
}
```

The Timer class also offers a Dispose method that allows you to cancel the timer and optionally signal the kernel object identified by the notifyObject parameter when all callbacks have completed. Here is what the Dispose method overloads like:

```csharp
public void Dispose();
public void Dispose(WaitHandle notifyObject);
```

> **Important**: When a Timer object is garbage collected, its finalization code calls the thread pool to cancel the timer so that it no longer goes off. When using a Timer object, make sure that a variable is keeping the Timer object alive or your callback method will stop getting called. This is discussed and demonstrated in the "Garbage Collection and Debugging" section in Chapter 21, "The Managed Heap and Garbage Collection."

The following code demonstrates how to have a thread pool call a method immediately and every two seconds thereafter.

```csharp
internal static class TimerDemo {
    private static Timer s_timer;

    public static void Main() {
        Console.WriteLine("Checking status every 2 seconds");
        // Now that s_timer is assigned to, we can let the timer fire knowing
        // calling Change in Status will not throw a NullReferenceException
        s_timer.Change(0, Timeout.Infinite);
        Console.ReadLine(); // Prevent the process from terminating
    }

    // This method's signature must match the TimerCallback delegate
    private static void Status(object state) {
        // This method is executed by a thread pool
        Console.WriteLine("In status {0}", DateTime.Now);
        Thread.Sleep(1000); // Simulates other work (1 second)
        // Just before returning, have the Timer fire again in 2 seconds
        s_timer.Change(2000, Timeout.Infinite);
        // When this method returns, the thread goes back
        // to the pool and waits for another work item
    }
}
```

If you have an operation you performed periodically, there is another way to structure your code by taking advantage of Task's static Delay method with C#'s async and await key-words (discussed extensively in Chapter 28). Here is a rewrite of the preceding code demonstrating this.

```csharp
internal static class DelayDemo {
    public static void Main() {
        Console.WriteLine("Checking status every 2 seconds");
        Status();
        Console.ReadLine(); // Prevent the process from terminating
    }

    // This method can take whatever parameters you desire
    private static async void Status() {
        while (true) {
            Console.WriteLine("Checking status {0}", DateTime.Now);
            // Put code to check here...
            // At end of loop, delay 2 seconds without blocking a thread
            await Task.Delay(2000); // await allows thread to return
            // After 2 seconds, some thread will continue after wait to loop again
        }
    }
}
```
