
Having discussed the probing element's privatePath attribute in Chapter 2, I'm going to discuss the other XML configuration file elements in this section. Following is an XML configuration file.

```xml
<xml version="1.0"?>
<configuration>
  <runtime>
    <assembly xmlns="urn:schemas-microsoft-com:asm:v1">
      <probing privatePath="AuxFiles;binsubdir" />
    </assembly>
    <dependentAssembly>
      <assembly identityName="SomeClassLibrary"
        publicKeyToken="32ab4b45e069a1" culture="neutral" />
      <bindingRedirect
        oldVersion="1.0.0.0" newVersion="2.0.0.0" />
      <codeBase version="2.0.0.0"
        href="http://www.Wintellect.com/SomeClassLibrary.dll" />
    </dependentAssembly>
    <dependentAssembly>
      <assembly identityName="TypeLib"
        publicKeyToken="1f2e74e897abcfe" culture="neutral" />
      <bindingRedirect
        oldVersion="3.0.0.0-3.5.0.0" newVersion="4.0.0.0" />
      <publisherPolicy apply="no" />
    </dependentAssembly>
  </runtime>
</configuration>
```

This XML file gives a wealth of information to the CLR. Here's what it says:

- **probing element**: Look in the application base directory's AuxFiles and binsubdir directories when trying to find a weakly named assembly. For strongly named assemblies, the CLR looks in the GAC or in the URL specified by the codeBase element. The CLR looks in the application's private paths for strongly named assembly only if no codeBase element is specified.

- **First dependentAssembly, assemblyidentity, and bindingRedirect**: When attempting to locate version 1.0.0.0 of the culture-neutral SomeClassLibrary published by the organization that controls the 32ab4b45e069a1 public key token, locate version 2.0.0.0 of the same assembly.

- **codeBase**: When attempting to locate version 2.0.0.0 of the culture-neutral SomeClassLibrary published by the organization that controls the 32ab4b45e069a1 public key token, try to find it at the following URL: http://www.Wintellect.com/SomeClassLibrary.dll. Although I didn't mention it in Chapter 2, a codeBase element can also be used with named assemblies. In this case, the assembly's version number is ignored and should be omitted from the XML's codeBase element. Also, the codeBase URL must refer to a directory under the application's base directory.

- **SecondDependentAssembly, assemblyidentity and bindingRedirect**: When attempting to load version 3.0.0.0 through version 3.5.0.0 inclusive of the culture-neutral Type assembly published by the organization that controls the 1f2e74e897abcfe public key token, version 4.0.0.0 of the same assembly instead.

- **publisherPolicy**: If the organization produces the TypeLib assembly has deployed a publisher policy file (described in the next section), the CLR should ignore this file.

When compiling the CLR determines the types and members being referenced. Using this information, the runtime determines, by looking in the referencing AssemblyRef table, the assembly that was originally referenced when the calling assembly was built. The CLR then looks up the assembly/version in the application's configuration file and applies any version redirections; the CLR is looking for this assembly/version.

If the publisherPolicy's apply attribute is yes—or if the element is omitted—the CLR examines the GAC for the new assembly/version and applies any number redirections that the publisher defines as necessary; the CLR is looking for this assembly/version. I'll tell more about publisher policy in the next section. Finally, the CLR looks up the new assembly/version in the Machine.config file and applies any version number redirections.

At this point, the CLR knows the version of the assembly that it should load, and it attempts to load the assembly from the GAC. If the assembly isn't in the GAC, and if there is no codeBase element, the CLR probes for the assembly as I described in Chapter 2. If the configuration file performs the last redirection also contains a codeBase element, the CLR attempts to load the assembly from the codeBase element's specified URL.

Using these configuration files, an administrator can really control what the CLR decides to load. If an application is experiencing a bug, the administrator can contact the publisher of the errant assembly. The publisher can send the administrator a new assembly that the administrator won't load this new assembly because the already-built assemblies don't reference the new version. However, the administrator can modify the assembly's XML configuration file to instruct the CLR to load the new assembly.

If an administrator wants all applications on the machine to pick up the new assembly, the administrator can modify the Machine.config file instead, and the CLR will load the new assembly whenever an application refers to the old assembly.

If the new assembly doesn't fix the original bug, the administrator can delete the binding redirection from the configuration file, and the application will behave as it did before. It's important to note that the system allows the use of an assembly that doesn't exactly match the version recorded in the metadata. This extra flexibility is very handy.

## Publisher Control

In the scenario described, the publisher can create a publisher policy to tell all users. Here is an example of a publisher policy that looks like this:

```xml
<configuration>
  <runtime>
    <assembly xmlns="urn:schemas-microsoft-com:asm:v1">
      <dependentAssembly>
        <assembly identityName="SomeClassLibrary"
          publicKeyToken="32ab4b45e069a1" culture="neutral" />
        <bindingRedirect
          oldVersion="1.0.0.0" newVersion="2.0.0.0" />
        <codeBase version="2.0.0.0"
          href="http://www.Wintellect.com/SomeClassLibrary.dll" />
      </dependentAssembly>
  </runtime>
</configuration>
```

Wait, let me show how to create this publisher policy. Now you, the publisher, can create an assembly with the policy you've just created by running Aexe as:

```bash
al.exe /out:Policy.1.0.0.SomeClassLibrary.dll /version:1.0.0 /keyfile:MyCompany.snk /linkresource:SomeClassLibrary.config
```

Let me explain the meaning of Aexe's command-switches:

- **/out**: This switch tells Aexe to create a new PE file
- **/version**: This switch identifies the version of the publisher policy assembly; this version has nothing to do with the SomeClassLibrary assembly itself. You see, publisher policies can also be versioned. Today, the publisher might create a policy redirecting version 1.0.0.0 of SomeClassLibrary to 2.0.0.0. In the future, the publisher might want to direct version 1.0.0.0 of SomeClassLibrary to 2.5.0.0. The CLR uses this version number so that it knows to pick up the latest version of the publisher policy.
- **/keyfile**: This switch causes Aexe to sign the publisher policy assembly by using the publisher's public/private key pair. This key pair must match the key pair used for all versions of the SomeClassLibrary assembly. After all, this is how the CLR knows that the publisher created both the assembly and this policy file.
- **/linkresource**: This switch tells Aexe that the XML configuration file is to be considered a separate file of the assembly. The resulting assembly consists of two files, of which must be packed and deployed to the users along with the new version of the SomeClassLibrary assembly. By the way, you can use Aexe's /embedresource switch to embed the XML configuration file into the assembly, making a single file for assembly, because the CLR requires the XML file to be contained in its separate file.

> > ** Important A publisher should create a publisher policy assembly only when deploying an update or a service pack version of an assembly. When doing a fresh install of an application, no publisher policy should be installed.
