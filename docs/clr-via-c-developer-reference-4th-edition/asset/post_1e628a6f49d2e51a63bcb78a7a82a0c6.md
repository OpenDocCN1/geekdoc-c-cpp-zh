## 25-1 The kinds of features exposed by Windows's WinRT components and the various languages that Microsoft supports to access them.

WinRT components are internally implemented as Component Object Model (COM) components, which is a technology that Microsoft introduced in 1999. At the time, COM was considered a complicated model with a lot of arcane rules and a tedious programming model. However, there are lot of good ideas in COM, and over the years, Microsoft has tweaked it in to greatly simplify it. For WinRT, Microsoft made a significant tweak: instead of using type libraries to describe a COM component's API, they now use metadata. That's right, WinRT components describe their API using the .NET metadata format (ECMA-335) as standardized by the ECMA-committee. This is the same metadata format I've been describing throughout this whole book.

Metadata is much richer than type libraries and the CLR already has a complete understanding of metadata. In addition, the CLR has supported interoperating with COM components Runtime Callable Wrappers (RCWs) and COM Callable Wrappers (CCWs) since its inception. For the most part, this allows (like C#) running on the CLR to seamlessly operate with WinRT types and components.

In C#, when you have a reference to a WinRT object, you really have a reference to an RCW that internally refers to the WinRT object. Similarly, if you pass a CLR object to a WinRT API, you are really passing a reference to a CCW to the WinRT API and the CCW holds a reference to your CLR object.

WinRT components have their metadata embedded in files with .winmd extension. The WinRT components that ship with Windows have their metadata in the various Windows.*winmd files, which can be found in the %WindowsDir%\System32\Metadata directory. When building an app, you would reference the winmd file that the Windows SDK installs here.

%ProgramFiles(x86)%\Windows Kits\8.0\CommonConfiguration\Neutral\Windows.winmd

A major design goal of the Windows Runtime system is to enable developers to be successful in writing apps using the technologies, tools, practices, and conventions that are already familiar and well-known to them. In order to achieve this, some WinRT features are projected to the respective technologies. For .NET Framework developers, there are two kinds of projections:

- **CLR projections** CLR projections are mappings performed implicitly by the CLR, usually related to reinterpreting metadata. The next section focuses on the WinRT Component Type System Rules and how the CLR projects these rules to the .NET Framework.

- **Framework projections** Framework projections are mappings performed explicitly in your code by leveraging APIs introduced into the Framework Class Library. Framework projections are required when the impedance mismatch between the WinRT type system and the CLR's type system is too great for the CLR to do it implicitly. Framework projections are discussed later in this chapter.

## CLR Projections and WinRT Component Type System Rules

WinRT components conform to a type system similar to how the CLR enforces a type system. When the CLR sees a WinRT type, it usually allows that type to be used via the CLR's normal COM interop technologies. But, in some cases, the CLR hides the WinRT type (by dynamically setting it to private) and then the CLR exposes the type via a different type. Internally, the CLR is looking for certain types (via metadata) and mapping these types to the Framework Class Library. For the complete list of WinRT types that the CLR implicitly projects to Framework Class Library types, see http://msdn.microsoft.com/en-us/library/windows/hh995050.aspx.

## WinRT Type System Concepts

The WinRT type system is not as rich as the CLR's type system. This bulleted list describes the WinRT type system's core concepts and how the CLR projects them:

- **File names and namespaces** The name of the .winmd file must match the name of the namespace containing the WinRT components. For example, a file named WindowsStore.winmd must have WinRT components defined in a Intel.Windows-Store namespace or in a sub-namespace of Intel.WindowsStore. Because the Windows file system is insensitive, namespaces that differ by case are not allowed. Also, a WinRT component cannot have the same name as a namespace.

- **Common base type** WinRT components do not share a common base class. When the CLR projects a WinRT type, it appears as if the WinRT type is derived from System.Object and therefore all WinRT types inherit public methods like ToString, GetHashCode, Equals, and GetType. So, when using a WinRT object via C#, the object will look like it is derived from System.Object, and you can call the "inherited" methods such as ToString.

- **Core data types** The WinRT system type supports the core data types as Boolean, unsigned-16-bit, 32-bit, and 64-bit signed and unsigned integers, single-precision and double-precision floating-point numbers, 16-bit character, and void.1 Like in the CLR, all other data types are composed from these core data types.

- **Classes** WinRT is an object-oriented system type, making that WinRT components support abstraction, inheritance, and polymorphism.2 However, some languages (like JavaScript) do not support inheritance and in order to cater to these languages, almost no WinRT components take advantage of inheritance. This means they do not take advantage of polymorphism. In fact, only WinRT components consumable from non-JavaScript languages leverage inheritance and polymorphism. For the WinRT components that ship with Windows, only the XML components (for building user interfaces) take advantage of inheritance and polymorphism. Applications written in JavaScript use HTML and CSS to produce their user interface.

- **Structures** WinRT supports structures (value types), and instances of these are marshaled by value across the COM interoperability boundary. Unlike CLR value types, WinRT structures can have only public faces of the core data types or of other WinRT structure.3 In addition, WinRT structures cannot have any constructors or helper methods. For convenience, the CLR projects may use operating system WinRT structures as some native CLR types, which offer constructors and helper methods. These projected types feel more natural to the CLR developer. Examples include the Point, Rect, Size, and TimeSpan structures defined in the Windows .namespace.

- **Nullable Structures** WinRT APIs expose nullable structures (value types). The CLR projects the WinRT’s .Foundation.IReference<T> interface as the CLR’s System.Nullable<T>.

- **Enumerations** An enumeration is simply defined as a signed or unsigned 32-bit integer. If you define an enumeration type in C#, the underlying type must be either int or uint. Also, signed 32-bit integer enums are considered to be discrete values, unless unsigned 32-bit units are considered as flags capable of being ORed together.

- **Interfaces** WinRT interface’s members must specify only WinRT-compatible types for parameters and return types.

- **Methods** WinRT has limited support for method overloading. Specifically, because JavaScript has dynamic typing, it can’t distinguish between methods that differ by the types of their parameters. For example, JavaScript will happily pass a number to a method expecting a string. However, JavaScript can distinguish between a method that takes one parameter and a method that takes two parameters.
