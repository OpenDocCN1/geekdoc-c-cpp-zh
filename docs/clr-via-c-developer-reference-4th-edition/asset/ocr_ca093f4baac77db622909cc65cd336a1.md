It would be nice if .NET Framework included additional classes that wrap native resources. For example, one could imagine classes as SafeProcessHandle, SafeThreadHandle, SafeTokenHandle, SafeLibraryHandle(it ReleaseHandle would call the Win32 Free function), SafeLocalAlloc(it ReleaseHandle would call the Win32 LocalFree function), and so on.

All of the classes used (just mentioned) interact with the Framework Class Library (FCL). However, these classes are not publicly exposed; they are internal to the assemblies that define them. Microsoft didn't expose these classes publicly because they didn't want to document them and do full testing of them. If you need any of these classes for your work, I recommend you use a tool such as ILDisasm or some IL decompiler to extract the code for these classes and integrate them into your project's source code. All of these classes are trivial to implement, and writing them from scratch would be quite deite.

The SafeHandle-derived classes are extremely useful because they ensure that the native resource is freed when a GC occurs. In addition to what we've already discussed, SafeHandle offers two capabilities. First, the CLR gives SafeHandle-derived types special treatment when used in scenarios in which you are operating with native code. For example, let's examine the following code:

```
using System;
using System.Runtime;
using Microsoft.Win32.SafeHandles;

internal static class SomeType {
[DllImport("kernel32", CharSet=CharSet.Unicode, EntryPoint="CreateEvent")
// This prototype is not robust
private static extern IntPtr CreateEventBad(
IntPtr pSecurityAttributes, Boolean initialState, String name);

// This prototype is robust
[DllImport("kernel32", CharSet=CharSet.Unicode, EntryPoint="CreateEvent")
private static extern SafeWaitHandle CreateEventGood(
IntPtr pSecurityAttributes, Boolean initialState, String name);

public static void SomeMethod() {
IntPtr handle = CreateEventBad(IntPtr.Zero, false, false, null);
SafeWaitHandle swh = CreateEventGood(IntPtr.Zero, false, false, null);
}
```

You'll notice that the CreateEvent method is prototyped returning an IntPtr, which will return the handle back to managed code; however, interoperating with native code is not robust. You see, after CreateEventBad is called (which creates the native resource), it is possible that a ThreadAbortException could be thrown to the handle being assigned to the handle variable. In the rare case this happens, the managed code would leak the native resource. The only way to get the event closed is to terminate the process.
