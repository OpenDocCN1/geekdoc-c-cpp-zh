
If your state method experiences an unhandled exception, the Task object representing your async function completes due to the unhandled exception. Any code waiting for this Task object to complete will see the exception. However, it is also possible for an async function to have a void return type. In this case, there is no way for a caller to discover the unhandled exception. So, when a void-returning async function throws an unhandled exception, the compiler-generated code catches it and rethrows it using the caller's synchronization context (discussed later). If the caller executed via a GUI thread, the GUI thread will eventually rethrow the exception. If the caller executed via a non-GUI thread, a thread pool thread will eventually rethrow the exception. Usually, rethrowing these exceptions causes the whole process to terminate.

## Other Async Function Features

In this section, I'd like to share with you some additional features related to async functions. Microsoft Visual Studio has great support for debugging async functions. When the debugger is stopped on an await iterator, stepping over (F10) will actually break into the debugger when the next statement is reached after the operation completes. This is incredibly useful and simplifies debugging.

Also, if you accidentally step into (F11) an async function, you can step out (Shift+F11) to get back to the caller; you must do this on the opening brace of the async function. After you pass the open brace, step out (Shift+F11) won't break until the async function runs all the way to completion. If you need to debug the calling method before the state machine runs to completion, put a breakpoint in the calling method and just run (F5) to it.

Some asynchronous operations execute quickly and complete almost instantaneously. When this happens, it is inefficient to suspend the state machine and then another thread immediately resumes the state machine; it is much more efficient to have the state machine continue its execution. Frankly, the await operator's compiler-generated code checks for this. If an asynchronous operation completes just before the thread would return, the thread does not return and just executes the next line of code.

This is all fine and good but occasionally you have a function that performs an intensive amount of processing before initiating an asynchronous operation. If you invoke the function via your GUI thread, your user interface will become non-responsive to the user. And, if the asynchronous operation completes synchronously, then your user-interface will be non-responsive longer. So, if you want to initiate an async function from a thread other than the one that calls it, you can use Task's static run methods.

```
// Task.Run is called on the GUI thread
Task.Run(async () => {
    // This code runs on a thread pool
    // TODO: Do intensive compute-bound processing here...

    await XxxAsync(); // Initiate asynchronous operation
    // Do more processing...
});
```

This code demonstrates another C# feature: async lambda expressions. You see, you can't just put an await operator inside the body of a regular lambda expression, because the compiler will know how to turn the method into a state machine. By placing async just before the lambda expression causes the state machine that returns a Task or Task<TResult>, which can then be assigned to any Func delegate whose return type is Task or Task<TResult>.

When writing code, it is very easy to invoke an async function, forgetting to use the await operator; the following code demonstrates:

```
static async Task OuterAsyncFunction() {
    // Oops, forgot to put the await operator on this line!

    // Code continues to execute while InnerAsyncFunction also continues to execute...
}
```

```
static async Task InnerAsyncFunction() { /* Code here is not important */ }
```

Fortunately, when you do this, the C# compiler gives the following warning: Because this call is not awaited, execution of the current method continues before the call is completed. Consider applying the 'await' operator to the result of the call. This is nice on rare occasions, when you don't actually care when InnerAsyncFunction completes, and you want to avoid writing the code and not have the compiler issue a warning.

To quiet the warning, you can simply assign the Task returned from InnerAsyncFunction to a variable and then ignore it.

```
static async Task OuterAsyncFunction() {
    var noWarning = InnerAsyncFunction(); // I intend not to put the await operator on this line.

    // Code continues to execute while InnerAsyncFunction also continues to execute...
}
```

Or, I prefer to define an extension method that looks like this.

```
[MethodImpl](MethodOptions.AggressiveInlining)] // Causes compiler to optimize the call away
public static void NoWarning(this Task task) { /* No code goes in here */ }
```

And then can use it like this.

```
static async Task OuterAsyncFunction() {
    InnerAsyncFunction().NoWarning(); // I intend not to put the await operator on this line.

    // Code continues to execute while InnerAsyncFunction also continues to execute...
}
```

One of the truly great features of performing asynchronous I/O operations is that you can initiate many of them concurrently so that they are all executing in parallel. This can give your application

a phenomenal boost. I never showed you code that started my piped server and then made a bunch of client requests to. Let me show you that code now.

```
public static async Task Go() {
    // Start the server, which returns immediately because
    // it asynchronously waits for client requests
    StartServer(); // This returns void, compiler warning to deal with

    // Make lots of async requests; save each client's Task<String>
    List<String> requests = new List<String>(10000);
    for (Int32 n = 0; n < requests.Capacity; n++) {
        requests.Add(IssueClientRequestAsync("localhost", "Request " + n));
    }

    // Asynchronously wait until all client requests have completed
    // NOTE: If 1+ tasks throws, WhenAll rethrows the last exception
    String[] responses = await Task.All(requests);

    // Process all responses
    for (Int32 n = 0; n < responses.Length; n++) {
        Console.WriteLine(responses[n]);
    }
}
```

This code starts the main pipe server that is listening and for op, it initializes 10,000 client requests as fast as possibly can. Each ClientRequestAsync returns a Task<String> object, which I add to a collection. Now, the pipe server is processing these client requests as fast as possible using thread pools that will try to keep all the CPUs on the machine busy.¹⁰ Each request's Task<String> object completes with the string response returned from the server.

In the preceding code, I want to wait until all the client requests have their response before processing their results. I accomplish this by calling Task's WhenAll method. Internally, method creates a Task<String[]> object that completes after all of the List's objects have completed. I await the Task[] object so that the state machine executes after all of the tasks have completed. I loop through all the responses at once and process them (call Console.WriteLine).

Perhaps you'd prefer to process each response as it happens rather than waiting for all of them to complete. Accomplishing this is as easy as using Task's WhenAny. The revised code looks like this:

```
public static async Task Go() {
    // Start the server, which returns immediately because
    // it asynchronously waits for client requests
    StartServer();

    // Make lots of async requests; save each client's Task<String>
    List<String> requests = new List<String>(10000);
```
