The third problem with thread synchronization locks is that they allow only one access to the resource at a time. This is the lock's whole reason for existing, but it is also a problem, blocking a thread causes more threads to be created. So, for example, if a thread pool attempts to acquire a lock that it cannot have, it is likely that the thread pool will create a new thread to keep the CPUs saturated with work. As discussed in Chapter 26, "Thread Basics," creating a thread is very expensive in terms of memory and performance. And to make matters worse, when the blocked thread gets to run again, it will run with this new thread pool; Windows now scheduling threads than there are CPUs increases this context switching, which also hurts performance.

The summary of all of this is that thread synchronization is bad, so you should try to design your applications to avoid as much of it as possible. To that end, you should avoid shared data as static fields. When a thread uses the operator to construct an object, the new operator returns a reference to the new object. At this point in time, only the thread that constructs the object has a reference to it; no other thread can access that. If you avoid passing this reference to another thread that might use the object at the same time as the creating thread, there is no need to synchronize access to the object.

Try use value types because they are always copied, so each thread operates on its own copy. Finally, it is OK to have multiple threads sharing data simultaneously if access is readonly. For example, many applications create data structures during their initialization. Once initialized, the application can create as many threads as it wants; if all these threads query the data, then the threads can do this simultaneously without acquiring or releasing any locks. The String type is an example of this: a String object is created, it is immutable; so many threads can access a single String object at the same time without any chance of the String object corrupted.

# Class Libraries and Thread Safety

Now, I'd like to say a quick about class libraries and thread synchronization. Microsoft's Framework Library (FCL) guarantees that all static methods are safe. This means that if two threads call a static method at the same time, no data will get corrupted. The FCL had to do this internally because there is no way that companies producing different assemblies could coordinate on a single lock for accessing the resource. The Console class contains a static field, which many of its methods acquire and release to ensure that only one thread at a time is accessing the console.

For the record, making a thread safe does not mean that internally it takes a synchronization lock. A thread-safe method means that data doesn't get corrupted if two threads attempt to access the data at the same time. The System.Math class has a static method implemented as follows.

```
public static Int32 Max(Int32 val1, Int32 val2) {
    return (val1 < val2) ? val2 : val1;
}
```
