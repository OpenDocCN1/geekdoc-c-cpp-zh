
# The Barrier.Threading Class

The System.Barrier construct is designed to solve a very rare problem, so it is unlikely that you will have a use for it. Barrier is used to control a set of threads that are working in parallel so that they can step through phases of an algorithm together. Perhaps an example in order: when the CLR is using the server version of its garbage collector (GC), the GC algorithm creates one per core. Threads walk up different application stacks, concurrently marking objects in the heap. As each thread completes its portion of the work, it must stop waiting for the other threads to complete their portion of the work. After all have marked the objects, then the threads can compact different portions of the heap concurrently. As each thread finishes compacting the portion of the heap, the thread must block waiting for the other threads. After all the threads have finished compacting the portion of the heap, then all the threads walk up the application's threads, fixing up roots to the root of the newly compacted object. Only after all the threads have completed this work is the garbage collector considered and the application's threads can be resumed.

This scenario is easily solved using the Barrier class, which looks like this (method shown below):

```
public class Barrier {
    public Barrier(Int32 participantCount, Action<Barrier> postPhaseAction);
    public void Dispose();
    public Int64 AddParticipants(Int32 participantCount); // Adds participants
    public void RemoveParticipants(Int32 participantCount); // Subtracts participants
    public bool SignalAndWait(Int32 milliseconds, CancellationToken cancellation);

    public Int64 CurrentPhase { get; } // Indicates phase in process (starts at 0)
    public Int32 ParticipantCount { get; } // Number of participants
    public Int32 ParticipantsRemaining { get; } // # of threads needing to call SignalAndWait();
}
```

When you create a Barrier, you tell it how many threads are participating in the work, and you can also pass an Action<Barrier> delegate referring to code that will be invoked whenever all participants complete a phase of the work. You can dynamically add and remove participating threads from the Barrier by calling AddParticipant and RemoveParticipant methods, but in practice, this is rarely done. As each thread completes its portion of the work, it calls SignalAndWait, which tells the Barrier the thread is done and the Barrier blocks the thread (using a ManualResetEventSlim). After all participants call SignalAndWait, the Barrier invokes a delegate (the last thread that called SignalAndWait) and unblocks the waiting threads so they can get the next phase.

# Thread Synchronization Construct Summary

My recommendation is always to avoid writing code that blocks any threads. When performing asynchronous compute or I/O operations, the data hand off from thread to thread in a way to avoid the chance that multiple threads access the data simultaneously. If you are unable to accomplish this, then try to use the Volatile and Interlocked methods because they are fast and they never block a thread. Unfortunately, these methods manipulate only simple types, but you can perform rich operations on these types as described in "The Interlocked Anything Pattern" in Chapter 29.

There are two main reasons why you would consider blocking threads:

- **The programming model is simplified** By blocking a thread, you are sacrificing some resources and performance so that you can write your application code sequentially without using callback methods. C# async methods features give you a simplified programming model without blocking threads.

- **A thread has a dedicated purpose** Some threads must be used for specific tasks. The best example is an application's primary thread. If an application's primary thread doesn't block, it will eventually return and the whole process will terminate. Another example is an application's GUI thread or threads. Windows requires that a window or control always be manipulated by the thread that created it, so sometimes we write code that blocks a GUI thread until some other operation is done, and then the GUI thread updates any windows and controls as needed. Of course, blocking the GUI thread hangs the application and provides a bad user experience.

To avoid blocking threads, don't mentally assign a label to your threads. For example, don't create a spell-checking thread, a grammar-checking thread, a thread that handles this particular client request, and so on. The moment you assign a label to a thread, you have also said to yourself that thread can't do anything. But threads are too expensive to have them dedicated to a particular purpose. Instead, you use the thread pool to rent threads for short periods of time. So a pool thread starts out checking, then it changes to grammar checking, and then it changes to perform on behalf of a client request, and so on.

If, in spite of this discussion, you decide to block threads, then use the kernel objects to synchronize threads that are running in different AppDomains or Processes. To manipulate state via set of operations, use the Monitor class with a private field. Alternatively, you could use a reader-writer lock inside Monitor. Reader-writer locks are generally slower than Monitor, but they allow multiple readers to execute concurrently, improves overall performance and minimizes the cost of blocking threads.

In addition, using recursive locks (especially recursive reader-writer locks) because they hurt performance. However, Monitor is recursive and its performance is very good. Also, avoiding a lock in a finally block because entering and leaving exception-handling incurs a performance, and if an exception is thrown while mutating state, the state is corrupted, and other threads that manipulate it will experience unpredictable behavior and security bugs.

> Could use a SpinLock instead of Monitor because SpinLocks are slightly faster. But a SpinLock is potentially dangerous because it consume CPU time, and in opinion, it is not sufficiently faster than Monitor to justify its use.
This is partially because Monitor is actually implemented in native code, not managed code.

Of course, if you write code that holds a lock, your code should not hold the lock for a long time, because this increases the likelihood of threads blocking. In the “Asynchronous Synchronization” section later in this chapter, I will show a technique that uses collection classes as a way to avoid holding a lock for a long time.

Finally, for compute-bound work, you can use tasks (discussed in Chapter 27) to avoid a lot of the thread synchronization constructs. In particular, I love that each task can have one or more continu-tasks associated with it that execute via some thread pool when some operation completes. This is much better than having a thread block waiting for I/O-bound work, call the various XxxAsync methods that cause your code to continue running after the I/O operation completes; this is similar to a task’s-continue.

# The Famous Double-Check Locking Technique

There is a famous technique called double-check locking, which is used by developers who want to defer constructing a singleton object until an application requests (sometimes called lazy initialization). If the application never requests the object, never gets constructed, saving time and memory. A potential problem occurs when multiple threads request the singleton object simultaneously. In this case, some form of thread synchronization must be used to ensure that the singleton gets constructed just once.

This technique is not famous because it is particularly interesting or useful. It is famous because there has been much written about it. This technique was used in Java, and later that we discovered that Java couldn’t guarantee that it would work everywhere. The famous document that describes the problem can be found on this webpage: www.cs.umd.edu/~pugh/java/memoryModel/DoubleCheckedLocking.html.
