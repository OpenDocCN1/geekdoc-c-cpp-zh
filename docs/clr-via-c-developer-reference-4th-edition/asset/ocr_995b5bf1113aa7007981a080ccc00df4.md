# CLR Threads and Windows Threads

Today, the CLR uses the threading capabilities of Windows, Part V of this book is really focusing on how the threading capabilities of Windows are exposed to developers who write code by using the CLR. I will explain about how threads in Windows work and how the CLR alters the behavior (if it does). Sleep, if you'd like more information about threads, I recommend reading some of my early-writings on the topic, such as Windows via C/C++, Fifth Edition, by myself and Christophe Nasarre (Microsoft Press, 2007).

Note Back in the days of the .NET Framework, the CLR team felt that they would someday have logical threads, which did not necessarily map to Windows threads. However, around 2005, this was attempted unsuccessfully, causing the CLR team to give up on the idea. So, a CLR thread is identical to a Windows thread. However, in the .NET Framework, you see the CurrentManagedThread property, which returns the CLR's ID for a thread, although the System.Diagnostics.Thread class exposes an Id property and BeginThreadAffinity and EndThreadAffinity methods were also introduced to deal with the notion that a CLR thread might not map to a Windows thread.

Note For Windows Store apps, Microsoft has removed some APIs related to threading, because the APIs encouraged bad programming practices (discussed in the "Stop the Madness" section of this chapter), or because the APIs did not achieve the goals that Microsoft has set out for Windows Store apps. For example, the whole Thread class is not available in Windows Store apps because it has many bad APIs (as Start, IsBackground, Sleep, Suspend, Join, Interrupt, Alert, BeginThreadAffinity, and EndThreadAffinity). Personally, I think this is great, and I wish it had happened a long time ago. So, in Chapters 26 to 30, I discuss some APIs and features that are available for desktop apps but are not available for Windows Store apps. As you read these chapters, you should be able to easily discern certain APIs are unavailable for Windows Store apps.
