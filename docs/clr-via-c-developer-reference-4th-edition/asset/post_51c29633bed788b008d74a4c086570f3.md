
# Using Delegates to Call Back Static Methods

Now that you understand how the Counter method is designed and how it works, let's see how to use delegates to call static methods. The StaticDelegatedDemo method that appears in the previous code sample is the focus of this section.

The StaticDelegatedDemo method calls the Counter method, passing null in the third parameter, which corresponds to Counter's fb parameter. Because Counter's `fb` parameter receives null, each item is produced without calling any callback.

Next, the StaticDelegatedDemo method calls Counter twice, passing a newly constructed Feedback delegate object in the third parameter of the method call. This delegate object is a wrapper around a method, allowing the method to be called indirectly via the wrapper. In this example, the name of the static method, Program.FeedbackToConsole, is passed to the Feedback delegate constructor, indicating that it is the method to be wrapped. The reference returned from the new operator is passed to Counter as its third parameter. Now when Counter executes, it will call the Program type's static FeedbackToConsole method for each item in the series. FeedbackToConsole simply writes a string to the console indicating the item being processed.

> Note: The FeedbackToConsole method is defined as private inside the Program type, but the Counter method is able to call Program's private method. In this case, you might not expect a problem because both Counter and FeedbackToConsole are defined in the same type. However, this code would work fine even if the Counter method was defined in another type. In short, it is not a security or accessibility violation for one type to have code that calls another type's private member via a delegate as long as the delegate object is created by that class has ample security/accessibility.

The third call to Counter in the StaticDelegatedDemo method is almost identical to the second call. The only difference is that the Feedback delegate object wraps the static Program, FeedbackToMsgBox builds a string indicating the item being processed. This string is displayed in a message box.

Everything in this example is type-safe. For instance, when constructing a Feedback delegate object, the compiler ensures the signatures of Program's FeedbackToConsole and FeedbackToMsgBox methods are compatible with the signature defined by the Feedback delegate. Specifically, both methods must have one argument (Int32), and both methods must have the same return type (void). If FeedbackToConsole had been defined like this:

```csharp
private static Boolean FeedbackToConsole(String value) {
    ...
}
```

the C# compiler will not compile the code and issue the following error: error CS0123: No overload for 'FeedbackToConsole' matches delegate 'Feedback'.

Both C# and the CLR allow for covariance and contra-variance of reference types when binding a method to a delegate. Covariance means that a method can return a type that is derived from the delegate's return type. Contra-variance means that a method can take a parameter that is a base of the delegate's return type. For example, given a delegate defined like this:

```csharp
delegate Object Callback(FileStream s);
```

it is possible to construct an instance of this delegate type bound to a method that is prototyped like this.

```csharp
String SomeMethod(Stream s);
```

Here, SomeMethod's return type (String) is a type that is derived from the delegate's return type (Object); this covariance is allowed. SomeMethod's parameter type (Stream) is a type that is a base class of the delegate's parameter type (FileStream); this contraariance is allowed.

Note that covariance and contra-variance are supported only for reference types, not for values or for void. So, for example, I cannot bind the following method to the MyCallback delegate.

```csharp
Int32 SomeMethod(Stream s);
```

Even though SomeMethod's return type (Int32) is derived from MyCallback's return type (Object), this form of covariance is not allowed because Int32 is a value. The reason why value types and void cannot be used for covariance or contra-variance is the memory structure for these things, whereas the memory structure for reference types is always a pointer. Fortunately, the C# compiler will produce an error if you attempt to do so not supported.

# Using Delegates to Call Back Instance Methods

I explained how delegates can be used to call static methods, but they can also be used to call instance methods for a specific object. To understand how calling an instance method works, look at the InstanceDelegateMethod that appears in the code shown at the beginning of this chapter.

Notice that a Program object `p` is constructed in the InstanceDelegateMethod. This Program object doesn't have any instance fields or properties with it; I created it merely for demonstration purposes. When the new delegate object is constructed in the call to the Counter method, its constructor is passed `p.FeedbackToFile`. This causes the delegate to wrap a reference to the FeedbackToFile method, which is an instance method (not a static method). When Counter calls the callback method identified by its `fb` argument, the FeedbackToFile instance method is called, and the address of the recently constructed object `p` will be passed as the implicit `this` argument to the instance method.

The FeedbackToFile method works as the FeedbackToConsole and FeedbackToMsg methods, which it opens a file and appends the string to the end of the file. (The Status file that the method creates can be found in the application's AppBase directory.)

Again, the purpose of this example is to demonstrate that delegates can wrap instance methods as static methods. For instance methods, the delegate needs to know the instance of the object it is going to operate on. Wrapping an instance method is useful because code inside the object can access the instance members. Members that the object can have a state that can be used when the callback method is doing its processing.

# Demystifying Delegates

On the surface, delegates seem easy to use: you define them using the delegate keyword, construct instances of them using the new operator, and invoke them using the familiar method syntax. However, what's really going on is a bit more complex than the earlier examples illustrate. The compilers and the CLR do a lot of behind-the-scenes. In this section, I'll focus on how the compiler and the CLR work together. Having this knowledge will improve your understanding of delegates. Let's reexamine this line of code:

```csharp
internal delegate void Feedback(Int32 value);
```

When the compiler sees this, it actually defines a class that looks something like:

```csharp
internal class Feedback : System.MulticastDelegate {
  // Constructor
  public Feedback(Object object, IntPtr method);

  // Method with same prototype as specified by the code
  public virtual void Invoke(Int32 value);

  // Methods allowing callback to be called asynchronously
  public virtual AsyncResult BeginInvoke(Int32 value, AsyncCallback callback, Object object);
  public virtual void EndInvoke(IAsyncResult result);
}
```

In this example, the compiler has defined a class Feedback that is derived from the System.MulticastDelegate type defined in the Class Library (FCL).

> Important: The System.MulticastDelegate class is derived from System.Delegate, which is itself derived from System.Object. The reason why there are two delegate classes is historical and unfortunate: there should be one delegate class in the FCL. Sadly, we need to be aware of both of these classes because even though delegate types you create have Delegate as base class, you'll occasionally manipulate your delegate by using methods defined by the Delegate class instead of the MulticastDelegate class. For example, the Delegate class has static methods Combine and Remove. (I explain what these methods do later.) The signatures for both of these methods indicate that they take Delegate parameters. Because your delegate type is derived from MulticastDelegate, which is derived from Delegate, instances of your delegate type can be passed to these methods.
