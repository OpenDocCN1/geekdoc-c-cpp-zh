
This data corruption problem occurs because one of the Encoding-derived classes maintains a state between calls to them. If you're encoding or decoding characters/bytes in chunks, you must do some additional work to maintain state between calls, preventing any loss of data.

To decode chunks of bytes, you should obtain a reference to an Encoding-derived object (as described in the previous section) and call its Decoder method. This method returns a reference to a newly constructed object whose type is derived from the System.Text.Decoder. Like the Encoding class, the Decoder class is an abstract base class. If you look in the .NET Framework documentation, you will find that the FCL defines a few classes of Decoder-derived classes. These classes are all internal to the FCL, but the Decoder method can construct instances of these classes and return them to your application code.

All Decoder-derived classes offer two important methods: GetChars and CharCount. Obviously, these methods are used for decoding an array of bytes and work similarly to Encoding's GetChars and CharCount methods, discussed earlier. When you call one of these methods, it decodes the array as much as possible. If the array doesn't contain enough bytes to complete a character, the leftover bytes are inside the decoder object. The next time you call one of these methods, the decoder uses the leftover bytes by the new array added to it—this ensures that the chunks of data are properly decoded. Decoder objects are very useful when reading bytes from a stream.

An Encoding-derived type can be used for stateless encoding and decoding. However, a Decoder-derived type can be used only for decoding. If you want to encode strings in chunks, call GetEncoder instead of calling the Encoding's GetDecoder method. GetEncoder returns a newly constructed object whose type is derived from the abstract base class System.Text.. Again, the .NET Framework documentation doesn't contain any classes representing concrete implementations of the Encoder class. However, the FCL defines some Encoder-derived classes. As with Decoder-derived classes, these are all internal to the FCL, but the GetEncoder method can construct instances of these classes and return them to your application code.

All Encoder-derived classes offer two important methods: GetBytes and GetCount. On each call, the Encoder-derived object maintains any leftover state information so that you can encode data in chunks.

## Base-64 String Encoding and Decoding

As of writing, the UTF-16 and UTF-8 encoding are popular. It is also popular to encode a sequence of bytes to a base-64 string. The FCL offers methods to do base-64 encoding and decoding, and you might expect that this would be accomplished via an Encoding-derived type. However, for some reason, base-64 encoding and decoding is done using some static methods offered by the System.Convert type.

To encode a base-64 string as an array of bytes, you call Convert's FromBase64String or FromBase64CharArray method. Likewise, to decode an array of bytes as a base-64 string, you call Convert's static Base64String toToBase64CharArray method. The following code demonstrates how to use some of these methods.

```csharp
using System;

public static class Program {
    public static void Main() {
        // Get a set of 10 randomly generated bytes
        Byte[] bytes = new Byte[10];
        new Random().NextBytes(bytes);

        // Display the bytes
        Console.WriteLine(BitConverter.ToString(bytes));

        // Decode the bytes into a base-64 string and show the string
        String s = Convert.ToBase64string(bytes);
        Console.WriteLine(s);

        // Encode the base-64 string back to show the bytes
        bytes = Convert.FromBase64string(s);
        Console.WriteLine(BitConverter.ToString(bytes));
    }
}
```

## Secure Strings

String objects are used to contain sensitive data such as a user's password or credit-card information. Unfortunately, String objects contain an array of characters in memory, and if some unmanaged code is used to execute, the unsafe/unmanaged code can sniff around the process's address space, locate the string containing the sensitive information, and use this data in an unauthorized way. Even if the String object is used for just a short time and then garbage collected, the CLR might not immediately release the String object's memory (especially if the String object was in an older generation), leaving the String's characters in the process's memory, where the information could be compromised. In addition, because strings are immutable, as you manipulate them, the old copies linger in memory and you end up with different versions of the string scattered over memory.

Some government departments have stringent security requirements that require specific security guarantees. To meet these requirements, Microsoft added a more secure string class to the FCL: System.Security.SecureString. When you construct a SecureString, it internally allocates a block of unmanaged memory that contains an array of characters. Unmanaged memory is used so that the garbage collector is not aware of it.

These string characters are encrypted, protecting the sensitive information from malicious unsafe/unmanaged code. You can insert, remove, or set a character in the secure string by any of these methods: AppendChar, InsertAt, RemoveAt, and SetAt. Whenever you call any of these methods, internally the method decrypts the characters, performs the operation in place, and re-encrypts the characters. This means that the characters are in an unencrypted state for short period of time. This also means that the performance of each operation is less than stellar, so you should perform as few of these operations as possible.

The SecureString class implements the IDisposable interface to provide an easy way to deterministically destroy the secure contents. When your application longer needs the sensitive information, you simply call SecureString.Dispose method or a SecureString in a using constructor. Internally, Dispose zeroes out the contents of the memory buffer to make sure the sensitive information is not accessible to malicious code, and then the buffer is freed. Internally, a SecureString object has a field to a SafeBuffer-derived object, which retains the actual string. Because the SafeBuffer class is ultimately derived from Critical-FinalObject, discussed in Chapter 21, "The Managed Heap and Garbage Collection," the string characters are guaranteed to be zero out and have its buffer free when it is finalized. Unlike a String object, when a SecureString object is finalized, the encrypted string characters will no longer in memory.

Now that you know how to create and modify a SecureString, let's talk about how to use one. Unfortunately, the most recent F has limited support for the SecureString class. In other words, there are only a few methods that accept a SecureString argument. In .NET Framework 4, you can pass a SecureString as a password when:

- Working with a cryptographic service provider (CSP). See the System.Security.Cryptography.CspParameters classes.
- Creating, importing, or exporting an X.509 certificate. See the System.Security.Cryptography.X509Certificate.X509Certificate and System.Security.Cryptography.X509Certificate2 classes.
- Starting a new process under a specific user account. See the System.Diagnostics.Process and System.Diagnostics.ProcessStart classes.
- Constructing an event log session. See the System.Diagnostics.EventLog.EventLogSession class.
- Using the System.Windows.Controls.PasswordBox control. This class's SecurePassword property.

Finally, you can create your methods that can accept a SecureString object parameter. Inside your method, you must have the SecureString object create an unmanaged memory buffer contains the decrypted characters before you use the buffer. To keep the window of opportunity for malicious code to access the sensitive data as small as possible, your code should require access to the decrypted string for as short a period of time as possible.
