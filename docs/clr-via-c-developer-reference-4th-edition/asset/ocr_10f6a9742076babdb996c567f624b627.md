To solve the problem, all of these manipulations are performed using the technique I showed in the "The Interlocked Anything Pattern" section from Chapter 29. If you recall, this lets you turn any operation into a thread-safe atomic operation. This is what allows this lock to be so fast and have less state in other reader-writer locks. When I perform tests comparing my OneManyLock against FCL's ReaderWriterLock and ReaderWriterLock classes, I get the following results.

| Incrementing x in OneManyLock: 330 | Fastest |
| Incrementing x in ReaderWriterSlim: 554 | ~1.7x slower |
| Incrementing x in ReaderWriterLock: 984 | ~3x slower |

Of course, all reader-writer locks perform more logic than a mutually exclusive lock, the performance can be slightly slower. However, you have to weigh this fact that a reader-writer lock allows multiple readers into the lock simultaneously.

Before leaving this section, I also mention that my Power Threading library (downloadable for free from http://Winintel.com/Threading.aspx) offers a slightly different version of this lock, called OneManyResourceLock. This lock and others in the library offer many additional features, such as deadlock detection, the ability to turn lock ownership and recursion (albeit at a performance cost), a unified programming model for all locks, and the ability to observe the run-time behavior of the locks. For observing behavior, you can see the maximum amount of time that a thread ever waited to acquire a lock, and you can see the minimum and maximum amount of time that a lock was.

# The CountdownEvent Class

The next construct is System.Threading.CountdownEvent. Internally, this construct uses a ManualResetEventSlim object. This construct blocks a thread until its internal counter reaches 0. In a way, this construct's behavior is the opposite of a Semaphore (which blocks threads while its count is 0). Here is how this lock works (like some methods are not shown).

```
public class CountdownEvent : IDDisposable {
    public CountdownEvent(Int32 initialCount);
    public void Dispose();
    public void Reset(Int32 count); // SetCurrentCount to count
    public void AddCount(Int32 signalCount); // Increments CurrentCount by signalCount
    public bool TryAddCount(Int32 signalCount); // Increments CurrentCount by signalCount
    public bool Signal(Int32 signalCount); // Decrements CurrentCount by signameCount
    public bool Wait(int millisecondsTimeout, CancellationToken cancellationToken);

    public Int32 CurrentCount { get; }
    public bool IsSet { get; } // true if CurrentCount is 0
    public WaitHandle WaitHandle { get; }
}
```

After a CountdownEvent's CurrentCount reaches 0, it cannot be changed. The AddCount method throws InvalidOperationException when CurrentCount is 0, whereas the TryAdd method simply returns false if CurrentCount is 0.
