However, if any of these threads voluntarily block (by invoking a synchronous I/O operation, calling Thread::sleep or waiting to acquire a thread synchronization lock), Windows notifies the thread pool that one of its threads has stopped. The thread pool now realizes that the CPUs are undersaturated and creates a new thread to replace the blocked thread. Of course, this is not ideal because creating a new thread is very expensive in terms of time and memory.

What's worse that the blocked thread might wake up and now the CPUs are oversaturated again and context switching occurs, decreasing performance. However, the thread pool is smart here. As threads complete their processing and return to the pool, the thread pool won't let new work items units until the CPUs exactly saturated, thereby reducing context switches and improving performance. And if the thread pool later determines that it has more threads than it needs, it lets the extras kill themselves, reclaiming the resources that they were using.

Internally, the CLR's thread pool uses a Windows resource called an I/O Completion Port to permit the behavior that I've described. The CLR creates an I/O Completion Port when it initializes, as you open hardware devices, these devices can be bound to the I/O Completion Port so that drivers know where to queue the completed IRPs. If you want to understand more about this mechanism, I recommend the book, Windows via C/C++, Fifth Edition, by Michel and Christophe Nasser (Microsoft Press, 2007).

In addition to minimal usage and reduced context switches, we get many benefits when performing I/O operations asynchronously. Whenever a garbage collection starts, the CLR must suspend all the threads in the process. The further the threads are, the faster the garbage collector runs. In addition, when a garbage collection occurs, the CLR must wait all the threads' stacks looking for roots. And, the further threads there are, the fewer stacks there are, and this also makes the garbage collection faster. But, in addition, if our threads do not block while processing work items, the threads tend to spend more of their waiting in the thread pool. When a garbage collection occurs, the threads are at the top of their stack, and walking each thread's stack for roots takes very little.

Also, when you debug an application, Windows suspends all threads in the debugger when you hit a breakpoint. Then, when you continue executing the debugger, Windows has to resume all its threads, so if you have a lot of threads in an application, single-stepping through the code in a debugger can be excruciating. Using asynchronous I/O allows you to have a few threads, improving your debugging.
