your code might try to catch it and recover from it but you didn't even know you were invoking the type constructor. So the CL converts the DivideByZeroException into a TypeInitializationException so you know clearly that the exception occurred due to a type constructor failing; the problem was not with your code.

On the other hand, here is a bad use of this technique: when you invoke a method reflection, the CL internally catches any exception thrown by the method and converts it to a TargetInvocationException. This is incredibly annoying because you must now catch the TargetInvocationException object and look at its InnerException to discern the real reason for the failure. In fact, when using, it is common to see code like this.

```
private static void Reflection(Object o) {
    // Invoke a DoSomething method on this object
    var mi = o.GetType().GetMethod("DoSomething");
    mi.Invoke(o, null); // The DoSomething method might throw an exception
} catch (Reflection.TargetInvocationException e) {
    // The CL converts reflection-produced exceptions to TargetInvocationException
    throw e.InnerException; // Re-throw what was originally thrown
}
```

I have good news then: if you use C#'s dynamic type (discussed in Chapter 5, "Primitive, Reference, and Value Types") to invoke a member, the compiler-generated code does not catch any and exceptions and throw a TargetInvocationException object; the thrown exception object simply walks up the stack. For many developers, this is a good reason to prefer C#'s dynamic primitive type over reflection.

# Unhandled Exceptions

When an exception is thrown, the CL climbs the call stack looking for catch blocks that match the type of the exception object being thrown. If no catch block matches the thrown exception, an unhandled exception occurs. When the CL detects any thread in the process has an unhandled exception, the CL terminates the process. An unhandled exception identifies a situation that the application did not anticipate and is considered to be a true bug in the application. At this point, the bug should be reported back to the company that publishes the application. Hopefully, the publisher will fix it and distribute a new version of the application.

Class library developers should not even think about unhandled exceptions. Only application developers need to concern themselves with unhandled exceptions, and the application should have a policy in place dealing with unhandled exceptions. Microsoft actually recommends that developers just accept the CL's default policy. That is, when an application gets an unhandled exception, Windows writes an entry to the system's event log.
