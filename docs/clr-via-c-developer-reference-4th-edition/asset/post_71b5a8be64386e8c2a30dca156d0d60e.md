
From this discussion, you should conclude that you must avoid threads as much as possible because they consume a lot of memory and require time to create, destroy, and manage. Time is also wasted when Windows context switches between threads and garbage collections occur. However, this discussion should also help you realize that threads must be used sometimes because they allow Windows to be robust and responsive.

I should also point out that a computer with multiple CPUs in it can actually run multiple threads simultaneously, increasing scalability (the ability to do more work in less time). Windows will assign one thread to each CPU core, and each core will perform its own context switching to other threads. Windows makes sure that a single thread is not scheduled on multiple cores or would wreak havoc. Today, computers that contain multiple CPUs, hyperthreaded CPUs, or multi-core CPUs are commonplace. When Windows was originally designed, single-core CPUs were commonplace, and Windows added threads to improve system responsiveness and reliability. Today, threads are also used to improve scalability, which can happen only on computers that have multiple cores.

The remaining chapters in this book discuss the various Windows and CLR mechanisms that exist so that you can effectively wrestle with the tension of creating as few threads as possible, while keeping your code responsive and to scale if your code is running on a machine with multiple cores.

## Stop the Madness

If we cared about was raw performance, then the optimum number of threads to have on any machine is identical to the number of CPUs on that machine. So a machine with one CPU would have only one thread, a machine with two CPUs would have two threads, and so on. The reason is obvious: if you have more threads than CPUs, context switching is introduced and performance deteriorates. If each CPU has one thread, then no context switching exists and the threads run at full speed.

However, Microsoft designed Windows to favor reliability and responsiveness as opposed to raw performance and speed. And I recommend this: I do not think you would be using Windows or the .NET Framework today if applications could still stop the operating system and other applications. Therefore, Windows gives each process its own thread for improved system reliability and responsiveness. On my machine, for example, when I run Task Manager and select the Performance tab, I see the image in Figure 26-1.

It shows that my machine has 55 processes running on it, and so we'd expect that there were at least 55 threads on my machine, because each process gets at least one thread. Task Manager also shows that my machine currently has 864 threads in it! These threads end up allocating many megabytes of memory on my machine, which has only 4 GB of RAM in it. This also means that there is an average of approximately 15.7 threads per process, when I should ideally have 2 threads per process on my dual core machine!
