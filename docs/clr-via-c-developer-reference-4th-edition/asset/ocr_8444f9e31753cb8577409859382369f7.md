+   The array you pass to the WaitAny and WaitAll methods must contain no more than 64 elements or the methods will throw a System.NotSupportedException.

+   You call WaitHandle's Dispose method to close the underlying kernel object handle. Internally, these methods call the Win32 CloseHandle function. You can only call Dispose explicitly in your code if you know for a fact that no threads are using the kernel object. It puts a lot of burden on you if you write your code and set it. So, I would strongly discourage you from calling Dispose; instead, let the garbage collector (GC) do the cleanup. The GC knows when no threads are using the object anymore, and it will get rid of it. In a way, GC is doing thread synchronization for you automatically!

> In some cases, when a COM single-threaded apartment thread blocks, the thread can wake up to internally pump messages. For example, the blocked thread will process a Windows message sent from another thread. This is done to support COM interoperability. For most applications, this is not a problem—in fact, it is a good thing. However, if your code takes another synchronization lock during the processing of the message, then deadlock could occur. As you'll see in Chapter 30, all the hybrid locks call these methods internally, so the same benefit or problem exists when using the hybrid locks as well.

The versions of WaitOne and WaitAll do not accept a timeout parameter by void return type, not Boolean. The reason is because these methods return only true because the implied timeout is infinite (System.Threading.Timeout.Infinite). When you call any of these methods, you do not need to check their return value.

As already mentioned, the AutoResetEvent, ManualResetEvent, Semaphore, and Mutex classes are all derived from WaitHandle, so they inherit WaitHandle's methods and behavior. However, these classes introduce additional methods of their own, and I will address those now.

First, the constructors for all of these call the Win32 CreateEvent (passing FALSE for the bManualReset parameter) or CreateEvent(passing TRUE for the bManualReset parameter), CreateSemaphore, or CreateMutex. The handle value returned from all of these is saved in a SafeWaitHandle field defined inside the WaitHandle base class.

Second, the EventWaitHandle, Semaphore, and Mutex classes all offer static OpenExisting methods, which internally call the Win32 OpenEvent, OpenSemaphore, or OpenMutex, passing a String that identifies an existing kernel object. The handle value returned from all of these functions is saved in a newly constructed object that is returned from the OpenExisting method. If no kernel object exists with the specified name, a WaitHandleOpenException is thrown.
