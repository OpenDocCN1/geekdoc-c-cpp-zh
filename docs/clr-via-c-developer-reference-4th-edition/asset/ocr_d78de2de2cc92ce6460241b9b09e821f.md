Many applications use an EXE file that depends on many DLL files. When deploying this application, however, there is a technique that you can use to deploy a single EXE file. First, identify all the DLL files that your EXE file depends on that do not ship part of the Microsoft .NET Framework itself. Then add these DLLs to Visual Studio project. For each DLL you add, select its properties and change the Build Action to Embedded Resource. This causes the C# compiler to embed the DLL file(s) into your EXE, and you can deploy this one file.

At runtime, the CLR will be able to find the DLL assemblies, which is a problem. To fix this, use another assembly, initialize a callback method with the AppDomain's Resolve-Assembly event. The callback method's code should look something like this:

```
private static ResolveEventHandler(Object sender, ResolveEventArgs args) {
  String dllName = new Assembly(args.Name) + ".dll";

  var assemble = Assembly.ExecutingAssembly();
  String resourceName = assemble.GetManifestResourceNames().FirstOrDefault(name =>
    name.EndsWith(dllName));
  if (resourceName == null) return null; // Found, maybe another handler will find it
  using (var stream = assemble.GetManifestResourceStream(resourceName))
    Byte[] assemblyData = new Byte[stream.Length];
    stream.Read(assemblyData,0,stream.Length);
    return Assembly.Load(assemblyData);
  }
}
```

Now, the first time a method calls that references a type in a dependent DLL file, the AssemblyResolve event will be raised and the preceding callback code will find the embedded DLL resource and load it by calling an overload of Assembly's Load method that takes a Byte[] as an argument. Although I love the technique of embedding DLLs inside another assembly, you should be aware that this increases the memory used by your application at runtime.

# Using Reflection to Build a Dynamically Extensible Application

As you know, metadata is stored in a bunch of tables. When you build an assembly or a module, the compiler that you're using creates a type definition table, a field definition table, a method table, and so on. The System.Reflection namespace contains several types of tables that allow you to write code that reflects over (or parses) these metadata tables. In effect, the types in this namespace offer an object model over the metadata contained in an assembly or module.

Using these object model, you can easily enumerate all of the types in a type metadata table. For each type, you can obtain its base type, the interfaces it implements, and the flags that are associated with that type. Additional types in the System.Reflection namespace allow you to query the type's fields, methods, and events, by parsing the corresponding metadata tables. You can also discover any custom attributes (covered in Chapter 18, "Custom Attributes") that have been applied to any of the metadata entities. There are even classes that let you determine referenced assemblies and methods for a method. With all of this information, you could easily build a tool very similar to Microsoft's ILasm.exe.
