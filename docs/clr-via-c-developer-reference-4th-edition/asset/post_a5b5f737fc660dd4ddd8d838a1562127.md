
By the way, if T had constrained to a struct, the C# compiler would issue an error because you shouldn't be writing code that compares a value type variable with null because the result is always the same.

## Comparing Two Generic Type Variables with Each Other

Comparing two variables of the same generic type is illegal if the generic type parameter is not known to be a reference type.

```sharp
private static void ComparingTwoGenericTypeVariables<T>(T o1, T o2) {
    if (o1 == o2) { // Error
}
```

In this example, T is unconstrained, and here it is illegal to compare two reference variables with one another, unless the type overloaded the == operator. If T were constrained to class, this would compile, and the == operator would return true if the variables referred to the same object, checking for exact identity. Note that if I were constrained to a reference type that overloaded the operator == method, the compiler would emit calls to it when it sees the == operator. Obviously, this whole discussion applies to the use of != operator.

When you write code to compare the primitive value types—Byte, Int32, Decimal, etc., the C# compiler knows how to emit the right code. However, for non-primitive value types, the C# compiler doesn't know how to emit the code to comparisons. So if ComparingTwoGenericTypeMethods<T> were constrained to struct, the compiler would issue an error. And you're not allowed to constrain a type parameter to a specific value type because it is implicitly sealed, and no types exist that are derived from the value type. Allowing this would make the generic constrained to a specific type, and the C# compiler doesn't allow this because it is more efficient to just make a non-generic method.

## Using Generic Type Variables as Operands

Finally, it should be noted that there are a lot of issues about using operators with generic type operators. In Chapter 5, I talked about C# and how it handles its primitives: Byte, Int16, Int32, Int64, Decimal, and so on. In particular, I mentioned that C# knows how to interpret operators such as +, *, and / applied to the primitive types. Well, these operators can't be applied to variables of a generic type because the compiler doesn't know the type at compile time. This means you can't use any of these operators with variables of a generic type. So it is impossible to write a mathematical algorithm that works on any arbitrary numeric data type. Here is an example of a generic method that I'd like to:

```sharp
private static T Sum<T>(T num) where T : struct {
    T sum = default(T);
    for (T n = default(T); n < num; n++) {
        sum += n;
    }
    return sum;
}
```

I've done everything possible to try to get this method to compile. I've constrained T to struct, and I'm using default(T) to initialize sum and n to 0. When I compile this code, I get the following-three errors.

- error CS0019: Operator '<' cannot be applied to operands of type 'T' and 'T'
- error CS0023: Operator '++' cannot be applied to operand of type 'T'
- error CS0019: Operator '+=' cannot be applied to operands of type 'T' and 'T'

This is a severe limitation on the CLR's generic support, and many developers (especially in the scientific, financial, and mathematical world) are very disappointed by this limitation. Many people have tried to come up with techniques to work around this limitation by reflection (see Chapter 23, "Assembly Loading and Reflection"), the dynamic primitive type (see Chapter 5), operator overloading, and so on. But all of these cause a severe performance penalty or hurt readability of the code substantially. Hopefully, this is an area that Microsoft will address in a future version of the CLR and the compilers.

Many programmers are familiar with the concept of multiple inheritance: the ability to define a class that is derived from two or more base classes. For example, imagine a class named TransmitData, whose function is to transmit data, and another class named ReceiveData, whose function is to receive data. imagine that you want to create a class named SocketPort, whose function is to transmit and receive data. In order to accomplish this, you would want to derive SocketPort from both TransmitData and ReceiveData.

Some programming languages allow multiple inheritance, making it possible for the SocketPort class to be derived from the two base classes, TransmitData and ReceiveData. However, the language runtime (CLR)—and therefore managed programming languages—does not support multiple inheritance. Rather than offer any inheritance at all, the CLR does multiple inheritance via interfaces. This chapter will discuss how to define and use interfaces as well as provide guidelines to help you determine when to use an interface rather than a base class.

## Class and Interface Inheritance

In the .NET Framework, there is a class called Object that defines public instance methods: ToString, Equals, GetHashCode, and GetType. Because Microsoft has implemented Object's methods, any class derived from Object is actually inheriting these. This also means code written to operate on an instance of Object can actually perform operations on any class.

Object actually provides the following:

- The method signatures This allows code to think that it is operating on an instance of Object, when in fact, it could be operating on some class.
- The implementation of these methods This allows the developer defining a derived class not to be required to manually implement Object's methods.

In the CLR, a class is always derived from one and only class (that ultimately be derived from Object). This base class provides a set of method signatures and implementations for these methods. A cool thing about defining a new class is that it can become the base class for other class defined in the future—all of the method signatures and their implementations will be inherited by the new class.

The CL also allows developers to define an interface, which is really just to give a name to a set of method signatures. These methods do not come with any implementation at all. A class inherits an interface by specifying the interface's name, and the class must explicitly implement the interface's methods before the CLR will consider the referred type to be valid. Of course, implementing interface methods can be tedious, which is why I referred to inheritance as a scaled-down mechanism to achieve multiple inheritance. The C# compiler and the CLR actually allow a class to inherit several interfaces, and of course, the class must provide implementations for all of the inherited interface methods.

## Defining an Interface

As mentioned in the previous section, an interface is a named set of method signatures. Note that interfaces can also define events, parameterless properties, and parameterized properties (indexers in C#) because all of these are just syntax shortcuts that map to methods away, shown in previous chapters. However, an interface cannot define any constructor methods. In addition, an interface is not allowed to define any instance fields.
