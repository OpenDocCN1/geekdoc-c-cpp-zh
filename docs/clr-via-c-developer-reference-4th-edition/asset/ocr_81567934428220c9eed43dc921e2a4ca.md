+   - A property method can take a long time to execute: field access always completes immediately. A common reason to use properties is to perform thread synchronization, which can stop the thread forever, and therefore, a property should not be used if thread synchronization is required. In that situation, a method is preferred. Also, if your class can be accessed remotely (for example, your class is derived from System.MarshalByRefObject), calling the property method will be very slow, and therefore, a method is preferred to a property. classes derived from MarshalByRefObject should never use properties.

+   - If called times in a row, a property method may return a different value each time; a field returns the same value time. System.DateTime class has a read-only property that returns the current date and time. If you query this property, it will return a different value. This is a mistake, and Microsoft says you could fix this by making a method instead of a property. Environment's TickCount is another example of this mistake.

+   - A property method may cause observable side effects; field access never does. In other words, a user of a type should be able to set various properties defined by a type in any order or he chooses without noticing any difference in the behavior.

+   - A property method may require additional memory or return a reference to something that is not actually part of the object's state; querying a field always returns a reference to an object that is guaranteed to be part of the object's state. Working with a property that returns a copy can be very confusing to developers, and this characteristic is frequently documented.

It comes to my attention that people use properties more often than they should. If you examine this list of differences between properties and fields, you'll see there are very few circumstances in defining a property is actually useful and will cause confusion for developers. The only things property buy you some some syntax; there is no performance benefit compared to a non-property method, and understandability of the code is reduced. If I had been involved in the design, the .NET Framework and compilers, would have not offered properties at all; instead, would programmers actually implement GetXxx and SetXxx methods as desired. Then, if compilers want to offer some special, simplified syntax for calling these methods, so be it. But I'd want the compiler to use some syntax that is different from field access syntax so that programmers really understand what they are doing—a method call.
