By default, compilers actually do the work of turning the emitted managed module into an assembly; that is, the C# compiler emits a managed module that contains a manifest. The manifest indicates that the assembly consists of just the one file. So, for projects that have just one managed module and no resource (or data) files, the assembly will be the managed module, and you won't have any additional steps to perform during your build process. If you want to grow a set of files into an assembly, you'll have to be aware of more tools (such as the assembly linker, AL.exe) and command-line options. I'll explain these tools and options in Chapter 2.

An assembly allows you to decouple the logical and physical notions of a reusable, securable, versionable component. How you partition your code and resources into different files is completely up to you. For example, you could rarely use types or resources in separate files that are part of an assembly. The separate files could be downloaded on the web as they are needed at runtime. If the files are never needed, they're never downloaded, saving disk space and reducing installation time. Assemblies allow you to break up the deployment of files while still treating all of them as a single collection.

An assembly's modules also include information about referenced assemblies (including their version numbers). This information makes an assembly self-describing. In other words, the CLR determine the assembly's immediate dependencies in order for the assembly to execute. No additional information is required in the registry or in Active Directory Services (AD DS). Because no additional information is needed, deploying assemblies is much easier than deploying unmanaged components.
