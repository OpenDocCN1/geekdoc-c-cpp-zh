The C# language specification states, "As a matter of style, the keyword is favored over use of the complete system type name." I disagree with the language specification; I prefer to use FCL type names and completely avoid the primitive type names. In fact, I wish that compilers didn't offer the primitive types and forced developers to use the FCL type names instead. Here are my reasons:

- I've seen a number of developers confused, not knowing whether to use string or String in their code. Because C# string (a keyword) maps exactly to System.String (an FCL type), there is no difference and either can be used. Similarly, I've heard developers that int represents a 32-bit integer when the application is running on a 32-bit operating system and that it represents 64-bit integer false when the application is running on a 64-bit operating system. This statement is absolutely false in C#, int always maps to System.Int32, and therefore it represents a 32-bit integer regardless of the operating system code is running on. If programmers use Int32 in their code, then this confusion is eliminated.

- In C#, long maps to System.Int64, but in a different programming language, long could map to an Int16 or Int32. In fact, C++/CLI treats long as an Int32. Someone reading source code in one language could misinterpret the intent if he or she were used to programming in a different programming language. In fact, most languages won't even treat long as a keyword and won't compile that code they uses.

- The FCL has many methods that have type names as part of their method names. For example, the BinaryReader offers methods such as ReadBoolean, ReadInt32, ReadSingle, and so on. System.Convert offers methods such as ToBoolean, ToInt32, ToSingle, and so on. It is legal to write the following code, with the line feels very unnatural to me, and yet this is not the correct line.

```
BinaryReader br = new BinaryReader(...);
float val = br.ReadSingle(); // OK, but feels unnatural
single val = br.ReadSingle(); // OK and feels good
```

- Many programmers use C# exclusively to denote type names that can be used against the CLR, and because of this, C#-seems creep into the class library code. For example, Microsoft's FCL is almost exclusively written in C# and developers on the FCL team have now introduced methods into the library such as Array.GetLength, which returns an Int64 value that is a long but not in other languages (like C++/CLI). Another example is System.Linq.Enumerable.Count

For all of these reasons, I'll use the FCL type names throughout this book.

In programming languages, you would expect the following code to compile and execute correctly.

```
Int32 i = S; // A 32-bit value
Int64 l = i; // Implicit cast to a 64-bit value
```

However, based on the casting demonstrated presented in Chapter 4, you would not expect this to compile. After all, System.Int32 and System.Int64 are different types, and neither is derived from the other. You'll be happy to know that the C# compiler does this code correctly, and it runs as expected. Why? The reason is that the C# compiler has intimate knowledge of primitive types and applies its own special rules when compiling the code. In other words, the compiler recognizes common programming patterns and produces the necessary IL to make the code work as expected. Specifically, the C# compiler supports patterns related to casting, literals, and operators, as shown in the following examples.

First, the compiler is able to perform implicit or explicit cast between primitive types such as the following.

```
Int32 i = S; // Implicit cast from Int32 to Int32
Int64 l = i; // Implicit cast from Int32 to Int64
Single s = i; // Implicit cast from Int32 to Single
Byte b = (Byte) i; // Explicit cast from Int32 to Byte
Int16 v = (Int16) s; // Explicit cast from Int32 to Int16
```

C# allows implicit casts if the conversion is "safe", if no loss of data is possible, such as converting Int32 to Int64. But C# requires explicit casts if the conversion is potentially unsafe. For numeric types, "unsafe" means you could lose precision or magnitude as a result of the conversion. For example, converting from Int32 to Byte requires an explicit cast because precision might be lost from Int32 numbers; converting from Single to Int16 requires a cast because Single can represent numbers much larger than Int16.

Be aware that different compilers can generate different code to handle these cast operations. For example, when casting a Single with a value of 6.8 to Int32, some compilers could generate code to put a 6 in the Int32, and others could perform the cast by rounding the result up to 7. The way C# truncates the result. For the exact rules that C# follows for casting primitive types, see the "Conversions" section in the C# language specification.

In addition to casting, primitive types can be written as literals. A literal is considered to be an instance of the type itself, and therefore, you can call instance methods using the instance shown here.

```
Console.WriteLine(123.ToString() + 456.ToString()); // "123456"
```

Also, if you have an expression consisting of literals, the compiler is able to evaluate at compile time, improving the application's performance.

```
Boolean found = false; // Generated code sets found to 0
Int32 x = 100 + 20 + 3; // Generated code sets x to 123
String s = "a" + "bc"; // Generated code sets s to "abc"
```
