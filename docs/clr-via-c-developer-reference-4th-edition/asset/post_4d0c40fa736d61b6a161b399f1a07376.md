
You'll notice that these methods return Boolean that indicates the String passed in contains characters that can be parsed into an Int32. These methods also return an output parameter result. If the methods return true, result will contain the result of parsing the string into a 32-bit integer. If the methods return false, result will contain 0, but you really shouldn't execute any code that looks at it anyway.

One thing I want to make absolutely clear: A Tryxxx's Boolean return values false to indicate one and only type of failure. The method should still throw exceptions for any other type of failure. For example, Int32's TryParse throws ArgumentException if the style is not valid, and it is certainly possible to have an OutOfMemoryException thrown when calling TryParse.

I also want to make clear that the thread object-oriented programming allows programmers to be productive. One way that it does is by not exposing error codes in a type's. In other words, constructors, methods, properties, etc. are all defined with the idea that calling won't fail. And, if defined correctly, for most of a member, it will not fail, and there will be no performance hit because an exception will not be thrown.

When defining types and members, you should define the members so that it is unlikely they will fail for the common scenarios in which you expect your types to be used. If you later find from users who are dissatisfied with the performance due to exceptions being thrown, and then should you consider adding Tryxxx methods. In other words, you should produce the best object model first, and, if users push back, add some Tryxxx to your type so that the users experience performance trouble can benefit. Users who are not experiencing performance trouble should continue to use the non-Tryxxx versions of the methods because this is the better object model.

## Constrained Execution Regions (CERs)

Many applications don't need to be robust and recover from any and all kinds of failures. This is true of many client applications like Notepad.exe and Cal.exe. And, of course, many of us have seen Microsoft Office applications like Word.exe, Excel.exe, and Outlook.exe terminate due to unhandled exceptions. Also, many-side applications, like web servers, are stateless and automatically restarted if they fail due to an unhandled exception. Of course some servers, like SQL Server, are all about state management and having data loss due to an unhandled exception is potentially much disastrous.

In the CLR, we have AppDomains (discussed in Chapter 22), which contain state. When an AppDomain is unloaded, all its state is unloaded. And if a thread in an AppDomain experiences an unhandled exception, it is OK to unload the AppDomain (which destroys all its state) without terminating the whole process.

> 8 This is definitely true if the thread lives its life inside a single AppDomain (like the ASP.NET and managed SQL Server stored procedures). But you might have to terminate the whole process if a thread crosses AppDomain boundaries during its lifetime.

By definition, a CER is a block of code that must be resilient to failure. Because AppDomains can be unloaded, destroying their state, CERs are typically used to manipulate any state that is shared by multiple AppDomains or processes. CERs are useful when trying to maintain state in the face of exceptions that get thrown unexpectedly. Sometimes we refer to these kinds of exceptions as asynchronous exceptions. For example, when calling a method, the CLR calls to load an assembly, create a type object in the AppDomain's loader, call the type's static constructor, JIT IL into native code, and so on. Any of these operations could fail, and the CLR reports the failure by throwing an exception.

If any of these operations fail within a catch or finally block, then your error recovery clean-up code won't execute in its entirety. Here is an example of code that exhibits the potential problem.

```cs
private static void Demo1() {
  try {
    Console.WriteLine("In try");
  }
  finally {
    //Type1's static constructor is implicitly called in here
    Type1.M();
  }
}
```

```cs
private sealed class Type1 {
  static Type1() {
    // if this throws an exception, M won't get called
    Console.WriteLine("Type1's static ctor called");
  }
}
```

When I run the preceding code, I get the following output.

In try
Type1's static ctor called

What we want is to not even start executing the code in the try block unless we know that the code in the associated catch and finally blocks is guaranteed (or as close as we can get) to execute. We accomplish this by modifying the code as follows.

```cs
private static void Demo2() {
  // Force the code in the finally to be eagerly prepared
  RuntimeHelpers.PrepareConstrainedRegions(); // System.Runtime.CompilerServices namespace
  try {
    Console.WriteLine("In try");
  }
  finally {
    // Type2's static constructor is implicitly called in here
    Type2.M();
  }
}
```

```cs
public class Type2 {
  static Type2() {
    Console.WriteLine("Type2's static ctor called");
  }
}
```

```cs
// Use this attribute defined in the System.Runtime.ConstrainedExecution namespace
[ReliabilityContract(Consistency.WillNotCorruptState, Cer.Success)]
public static void MC() {
}
```

Now, when I run this version of the code, I get the following output.

Type2's static ctor called

In try

When the JIT compiler eagerly prepares methods, it also walks the entire call graph eagerly preparing methods. The JIT compiler only prepares methods that have the ReliabilityContractAttribute applied with Consistency.WillNotCorruptState or Consistency.MayCorruptInstance. However, the compiler and CER do not knowing that you've written your method to live up to the guarantees you document via the ReliabilityContractAttribute. If you result in something wrong, state corruption is possible.

The ReliabilityContractAttribute looks like this.

```cs
public sealed class ReliabilityContractAttribute : Attribute {
    public ReliabilityContract(Consistency consistencyGuarantee, Cer cer);
    public Cer Cer { get; }
    public Consistency ConsistencyGuarantee { get; }
}
```

```cs
enum Consistency {
    MayCorruptProcess,
    MayCorruptDomain,
    MayCorruptInstance,
    WillNotCorruptState
}
```

```cs
enum Cer {
    None,
    MayFail,
    Success
}
```

When you want to write a reliable method, make it small and constrain what it does. Make sure it doesn't allocate any objects (no boxing for example), don't call any virtual methods or interface methods, use any delegates, or reflection which the JIT compiler can tell you. You can manually prepare these methods by calling one of these methods defined by the RuntimeHelper.

```cs
public static void PrepareMethod(RuntimeMethodHandle method);
public static void PrepareMethod(RuntimeMethodHandle method, RuntimeTypeHandle[] instantiation);
public static void PrepareDelegate(Delegate d);
public static void PrepareConstrainedDelegate(Delegate d);
```

You should also look at RuntimeHelper.ExecuteCodeWithGuaranteedCleanup method, which is another way to execute code with guaranteed cleanup.

```cs
public static void ExecuteCodeWithGuaranteedCleanup(TypeCode code, CleanupCode backup, Object userData);
```

When calling this method, you pass the body of the try and finally block as callback methods whose prototypes call these two delegates respectively.

```cs
public delegate void TryCode(Object userData);
public delegate void CleanupCode(Object userData, Boolean exceptionThrown);
```
