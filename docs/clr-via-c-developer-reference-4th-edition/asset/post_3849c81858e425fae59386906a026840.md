
In fact, you should test your application on a machine that has as many CPUs as possible because the more CPUs you have, the better chance that two or more threads will attempt to access the resource at the same time, making it more likely you will detect a problem.

The second problem with locks is that they hurt performance. It takes time to acquire and release a lock because there are additional method calls, and the CPUs must coordinate with each other to determine which thread will acquire the lock. Having the CPUs in the machine communicate with each other what hurts performance. For example, let's say that you have code that adds a node to the head of a linked list.

```csharp
// This class is used by the LinkedList class
public class Node {
    internal Node m_next;
    // Other members not shown
}
```

```csharp
public sealed class LinkedList {
    private Node m_head;
```

```csharp
public void Add(Node newNode) {
    // The following two lines perform very fast reference assignments
    newNode.m_next = m_head;
    m_head = newNode;
}
```

This Add method simply performs two reference assignments that can execute extremely fast. Now, if we want to make Add safe so that multiple threads can call it simultaneously without corrupting the linked list, then we need to have the Add acquire and release a lock.

```csharp
public sealed class LinkedList {
    private SomeKindOfLock m_lock = new SomeKindOfLock();
    private Node m_head;
```

```csharp
public void Add(Node newNode) {
    m_lock.Enter();
    // The following two lines perform very fast reference assignments
    newNode.m_next = m_head;
    m_head = newNode;
    m_lock.Leave();
}
```

Although Add is now thread safe, it has also become substantially slower. How much slower depends on the kind of lock chosen; I will compare the performance of various locks in this chapter and in Chapter 30, "Hybrid Thread Synchronization Constructs." But even the fastest could make the Add method several times slower than the version that didn't have any lock code in it all. Of course, the performance becomes significantly worse if the code calls Add in a loop to insert several nodes into the linked list.

The third problem with thread synchronization locks is that they allow only one access to the resource at a time. This is the lock's whole reason for existing, but it is also a problem, blocking a thread causes more threads to be created. So, for example, if a thread pool attempts to acquire a lock that it cannot have, it is likely that the thread pool will create a new thread to keep the CPUs saturated with work. As discussed in Chapter 26, "Thread Basics," creating a thread is very expensive in terms of memory and performance. And to make matters worse, when the blocked thread gets to run again, it will run with this new thread pool; Windows now scheduling threads than there are CPUs increases this context switching, which also hurts performance.

The summary of all of this is that thread synchronization is bad, so you should try to design your applications to avoid as much of it as possible. To that end, you should avoid shared data as static fields. When a thread uses the operator to construct an object, the new operator returns a reference to the new object. At this point in time, only the thread that constructs the object has a reference to it; no other thread can access that. If you avoid passing this reference to another thread that might use the object at the same time as the creating thread, there is no need to synchronize access to the object.

Try use value types because they are always copied, so each thread operates on its own copy. Finally, it is OK to have multiple threads sharing data simultaneously if access is readonly. For example, many applications create data structures during their initialization. Once initialized, the application can create as many threads as it wants; if all these threads query the data, then the threads can do this simultaneously without acquiring or releasing any locks. The String type is an example of this: a String object is created, it is immutable; so many threads can access a single String object at the same time without any chance of the String object corrupted.

# Class Libraries and Thread Safety

Now, I'd like to say a quick about class libraries and thread synchronization. Microsoft's Framework Library (FCL) guarantees that all static methods are safe. This means that if two threads call a static method at the same time, no data will get corrupted. The FCL had to do this internally because there is no way that companies producing different assemblies could coordinate on a single lock for accessing the resource. The Console class contains a static field, which many of its methods acquire and release to ensure that only one thread at a time is accessing the console.

For the record, making a thread safe does not mean that internally it takes a synchronization lock. A thread-safe method means that data doesn't get corrupted if two threads attempt to access the data at the same time. The System.Math class has a static method implemented as follows.

```csharp
public static Int32 Max(Int32 val1, Int32 val2) {
    return (val1 < val2) ? val2 : val1;
}
```

This method is safe even though it doesn't take any lock. Because Int32 is a value type, the two Int32 values passed to Max are copied into it, so multiple threads could be calling Max simultaneously, each thread working on its own data, isolated from any other thread.

On the other hand, the FCL does not guarantee that instance methods are safe because adding all the locking code would hurt performance too much. And in fact, if every instance method acquires a lock, you ultimately end up having one thread running in your application at any time, which hurts performance even more. As mentioned earlier, when a thread constructs an object, this thread has a reference to the object, no other thread can access that object, and no thread synchronization is required when invoking instance methods. However, if the thread then expands the reference to the object—by placing it in a static field, as the argument to ThreadPool.QueueWorkItem or a Task, and on—then thread synchronization is required if the thread could attempt non-read-only access.

It is recommended that you make your class libraries thread safe and make all your instance methods thread safe. There is one caveat to this pattern: if the purpose of the instance method is to coordinate threads, then the instance method should be safe. For example, one thread can cancel an operation by calling CancellationSource's Cancel method, and another thread detects it should stop what it's doing by querying the CancellationToken's IsRequested property. These two instance members have special synchronization code inside to ensure that the coordination of the two threads goes as expected.

# Primitive User-Mode and Kernel-Mode Constructs

In this chapter, I explain the thread synchronization constructs. By primitive, I mean the simplest constructs that are available to you in your code. There are two kinds of primitive constructs: user-mode and kernel-mode. Whenever possible, you should use the primitive user-mode constructs, because they are significantly faster than the kernel-mode constructs because they use CPU instructions to coordinate threads. This means that the coordination is occurring in hardware (which makes it fast). This also means that the Windows operating system detects that a thread is blocked on a primitive user-mode construct. Because a thread pool blocked on a user-mode construct is never considered blocked, the thread pool will not create a new thread to replace the temporarily blocked thread. Wow! All this sounds great, doesn't it? And it is great, why not I recommend using these constructs as much as possible.
