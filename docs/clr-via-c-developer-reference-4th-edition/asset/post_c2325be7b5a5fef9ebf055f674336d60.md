By default, compilers actually do the work of turning the emitted managed module into an assembly; that is, the C# compiler emits a managed module that contains a manifest. The manifest indicates that the assembly consists of just the one file. So, for projects that have just one managed module and no resource (or data) files, the assembly will be the managed module, and you won't have any additional steps to perform during your build process. If you want to grow a set of files into an assembly, you'll have to be aware of more tools (such as the assembly linker, AL.exe) and command-line options. I'll explain these tools and options in Chapter 2.

An assembly allows you to decouple the logical and physical notions of a reusable, securable, versionable component. How you partition your code and resources into different files is completely up to you. For example, you could rarely use types or resources in separate files that are part of an assembly. The separate files could be downloaded on the web as they are needed at runtime. If the files are never needed, they're never downloaded, saving disk space and reducing installation time. Assemblies allow you to break up the deployment of files while still treating all of them as a single collection.

An assembly's modules also include information about referenced assemblies (including their version numbers). This information makes an assembly self-describing. In other words, the CLR determine the assembly's immediate dependencies in order for the assembly to execute. No additional information is required in the registry or in Active Directory Services (AD DS). Because no additional information is needed, deploying assemblies is much easier than deploying unmanaged components.

# Loading the Common Language Runtime

Each assembly you build can be either an executable application or a DLL containing a set of types for use by an executable application. Of course, the CLR is responsible for managing the execution of code contained within these assemblies. This means that the .NET Framework must be installed on the host machine. Microsoft has created a distribution package that you can freely ship to install the .NET Framework on your customers' machines. Some versions of Windows ship with .NET Framework already installed.

You can tell if the .NET Framework has been installed by looking for the MSCore.dll file in the %SystemRoot%\System32 directory. The existence of this file tells you that the .NET Framework is installed. however, several versions of the .NET Framework can be installed on a single machine simultaneously. If you want to determine which versions of the .NET Framework are installed, examine the subdirectories under the following directories:

```
%SystemRoot%\Microsoft\.Framework
%SystemRoot%\Microsoft\.Framework\64
```

The .NET Framework SDK contains a command-line utility called CLRx.exe that shows all of the CLR versions installed on a machine. This utility can also show which version of the CLR is being used by processes currently running on the machine using the -all switch or passing the ID of the process you are interested in.

Before we start looking at how the CLR loads, we need to spend a moment considering 32-bit and 64-bit versions of Windows. If your assembly files contain only type-safe managed code, you are writing code that should run on both 32-bit and 64-bit versions of Windows. Source code changes are required for your code to run on either version of Windows. The resulting EXE/DLL produced by the compiler should work when running on x86 and x64 versions of Windows. In addition, Windows Store applications or class libraries will run on Windows RT machines (which use an ARM CPU). In other words, the one file will run on any machine that has the corresponding version of the .NET Framework installed on it.

Depending on the platform switch, the C# compiler will also emit the desired CPU architecture (or agnostic) into the header as well. Microsoft shifts two SDK PE32/2+ command-line utilities, DumpBin.exe and CorFlags.exe, that you can use to examine the header information in a managed module by the compiler.

When running an executable file, Windows examines this EXE file's header to determine whether the application requires a 32-bit or 64-bit address space. A file with a PE32 header can run with a 32-bit or 64-bit address space, and a file with a PE32+ header has a 64-bit address space. Windows also checks the CPU architecture information embedded inside the header to ensure that it matches the CPU type in the computer. Lastly, 64-bit versions of Windows offer a technology that allows 32-bit Windows applications to run. This technology is called WoW64 (for Windows 64).

After Windows has examined the EXE file header to determine whether to create 32-bit or 64-bit, Windows loads the x86, x64, or ARM version of MSCore.dll into the process space. On an x86 or ARM version of Windows, the 32-bit version of MSCore.dll can be found in the %SystemRoot%\System32 directory. On an x64 version of Windows, MSCore.dll can be found in the %SystemRoot%\SysWo64 directory, where the 64-bit version can be found in the %SystemRoot%\System32 (for backward compatibility reasons). Then, the process's primary thread calls a method inside MSCore.dll. This method initializes the CLR, loads the EXE assembly, and calls its entry point (Main). At this point, the managed application is up and running.

> Note Assemblies built by using version 1.0 or 1 of Microsoft's C# compiler can PE32 header and are CPU-architecture agnostic. However, at load time, the CLR considers these to be x86 only. For executable files, this improves the likelihood of the application actually running on a 64-bit system because the executable file will load in WoW64, giving the process environment very similar to what it would have on a 32-bit x86 version of Windows.

If an unmanaged application calls the Win32 LoadLibrary function to load a managed assembly, Windows knows to load and initialize the CLR (if not already loaded) in order to process the code contained within the assembly. Of course, in this scenario, the process is already up and running, and this may limit the usability of the assembly. For example, a managed assembly compiled with the /platform:x86 switch will not be able to load into a 64-bit process at all, whereas an executable file compiled with this switch would have loaded in WoW64 on a computer running a 64-bit version of Windows.
