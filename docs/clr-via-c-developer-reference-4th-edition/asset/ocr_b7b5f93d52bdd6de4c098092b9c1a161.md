# So Many Timers, So Little Time

Unfortunately, the FCL actually ships with several timers, and it is not clear to most programmers what makes each timer unique. Let me attempt to explain:

+   **System.Threading.Timer class** is the timer discussed in the previous section, and it is the best timer to use when you want to perform periodic background tasks on a thread pool.

+   **System.Windows.Forms.Timer class** Constructing an instance of this class tells Windows to associate a timer with the calling thread (see SetTimer function). When this timer goes off, Windows inserts a timer message (WM_TIMER) into the thread's message queue. The thread must execute a message pump that extracts these messages and dispatches them to the desired callback method. Notice that all of the work is done by just one—the thread that is guaranteed to be the thread that executes the callback method. This also means that your timer will not be executed by multiple threads concurrently.

+   **System.Windows.Threading.DispatcherTimer class** This class is the equivalent of the System.Forms' Timer class for Silverlight and WPF applications.

+   **System.UI.Xaml.DispatcherTimer class** This class is the equivalent of the System.Windows.Forms' Timer class for Windows Store apps.

+   **System.Timers.Timer class** This timer is a basic wrapper around System.Threading class that allows CLR to queue events into the thread pool when the timer comes due. The System.Timers.Timer class is derived from System.ComponentModel.Component which allows these timer objects to be placed on a design surface in Visual Studio. It, exposes properties and events, allowing it to be used more easily from Visual Studio's designer. This class was added to the FCL years ago while Microsoft was still sorting out the threading and stuff. This class probably should have been removed so that everyone would be using the System.Threading.Timer instead. In fact, I never use the System.Timers.Timer class, and I'd discourage you from using it, too, unless you really want a timer on a design surface.

# How the Thread Pool Manages Its Threads

Now I'd like to talk about how the thread pool manages workers and I/O threads. However, I don't want to go into a lot of detail, because the internal implementation has changed over the years with each version of the CLR, and it will continue changing with future versions. It is best to think of the thread pool as a black box. The black box is not perfect for any application, because it is a general purpose thread-scheduling technology designed to work with a large myriad of applications; it will work better for some applications than others. It works well today, and I highly recommend that you trust it, because it would be very hard for you to produce a thread pool that works better than the one shipping in the CLR. And, over time, most applications should improve as the thread pool code internally manages threads.
