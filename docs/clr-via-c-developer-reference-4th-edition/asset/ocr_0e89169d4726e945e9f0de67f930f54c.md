Here's the way to Host SDK assembly:

+   - Create a SDK assembly that defines an interface whose methods are used as the communication mechanism between the host application and the add-in components. When defining the parameters and return types for the interface methods, try to use other interfaces or types defined in MSCorLib.dll. If you want to pass and return your own data types, define them in this Host SDK assembly. After you settle on your interface definitions, give this assembly a strong name (described in Chapter 3), and then package and deploy it to your partners and users. Once, you should really avoid making any kind of changes to the types in this assembly. For example, do not change the interface in any way. However, if you define any data types, it is OK to add new members. If you make modifications to the assembly, you'll probably want to deploy it with a publisher policy (also described in Chapter 3).

> Note You can use types defined in MSCorLib because the CLR always loads the version of MSCorLib.dll that matches the version of the CLR itself. Also, only one version, different versions of MSCorLib never load by side (as described in Chapter 3). As a result, you won't have any version mismatches, and your application will require less memory.

+   - The add-in developers will, of course, define their own types in your Host Add-In assembly. Their Add-In assembly will reference the types in your Host SDK assembly. The add-in developers are able to put out a new version of your assembly as they'd like, and the host application will be able to compose the add-in types without any problem whatsoever.

+   - Create a separate Host Application assembly containing your types. This will obviously reference the Host SDK assembly and use the types defined in it. Feel free to modify the code in the Host Application assembly to your heart's desire. Because the add-in developers don't reference the Host Application assembly, you can put out a new version of it every hour if you want and not affect any of the add-in developers.

This section contains very important information. When using types across assemblies, you need to be concerned about assembly-versioning issues. Take your time to architect this by isolating the types that you use for communication across boundaries into your own assembly. Avoid mutating or changing these type definitions. However, if you really need to modify the type definitions, make sure that you change your assembly version and create a publisher policy for the new version.

```
namespace Wisintellect.HostSDK {
public interface IAddIn {
    String DoSomething(Int32 x);
}}
```
