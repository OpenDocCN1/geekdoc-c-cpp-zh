A performance hit is incurred only the first time a method is called. All subsequent calls to the method execute at the full speed of the native code because verification and compilation to native code don't need to be performed again.

The JIT compiler stores the native CPU instructions in dynamic memory. This means that the compiled code is discarded when the application terminates. If you run the application in the future or you run two instances of the application simultaneously (in two different operating system processes), the JIT compiler will have to compile the IL to native instructions again. Depending on the application, this can increase memory consumption significantly compared to a native application whose read-only code pages can be shared by all instances of the running application.

For most applications, the performance hit of JIT compiling isn't significant. Most applications tend to call the same methods over and over again. These methods will take the performance only once while the application executes. It is also likely that more time is spent inside the method calling them.

You should also be aware that the CLR's C++ compiler optimizes the native code as the back end of unmanaged code. Again, it may take more time to produce the optimized code, but the code will execute with much better performance than it hadn't been optimized.

There are two C# compiler switches that impact code optimization: /optimize and /debug. The following table shows what these switches have on the quality of the IL generated by the C# compiler and the quality of the native code generated by the JIT compiler.

| Compiler Switch Settings | C# IL Code Quality | JIT Native Code Quality |
|---|---|---|n| /optimize- /debug- (this is the default) | Unoptimized | Optimized |
| /optimize- /debug(+/full/pdbonly) | Unoptimized | Unoptimized |
| /optimize+ /debug(-+/full/pdbonly) | Optimized | Unoptimized |

With /optimize-, the unoptimized IL code produced by the C# compiler contains many operation (NOP) instructions and branches that jump to the next line of code. These instructions are emitted to the edit-and-continue feature of Visual Studio while debugging and the extra instructions also make code easier to debug allowing breakpoints to be set on control instructions such as for, while, do, if, else, try, catch, and finally statements. When producing optimized IL code, the C# compiler will remove these extraneous NOP and branch instructions, making the code harder to single-step through a debugger because control flow will be optimized. Also, some function evaluations may not work when performed inside the debugger. However, the IL code is smaller, making the resulting EXE/DLL file smaller, and the IL tends to be easier to read for those of you (like me) who enjoying the IL to understand what the compiler is producing.
