# Applications and Their Threading Models

The .NET Framework supports several kinds of application models, and Windows Services which can impose its own threading model. Console applications and Windows Services (which are really console applications; you just don't see the console) do not impose any kind of threading model; that is, you can do whatever it wants when it wants.

However, GUI applications, including Windows Forms, Windows Presentation Foundation (WPF), Silverlight, and Windows Apps impose a threading model where the thread created a UI element is the only thread to update that UI element. It is common for the GUI thread to spawn an asynchronous operation so that the GUI thread doesn't block and stop responding to user input like mouse, keystroke, pen and touch events. However, when the asynchronous operation completes, a thread pool thread completes the Task resulting state machine.

For some application models, this is OK and even desired because its efficient. For some other application models, like GUI applications, this is a problem, because your code will throw an exception if it tries to update UI elements via a thread pool. Somewhat, the thread pool must have the GUI thread update the UI elements.

ASP.NET applications allow any thread to do whatever it wants. When a thread pool starts to process a client's request, it can assume the client's culture (System.Globalization.CultureInfo), allowing the web server to return culture-specific formatting for numbers, dates, and times.¹¹ In addition, the web server can assume the client's identity (System.Security.Principal.IPPrincipal), so the server can access only the resources that it is allowed to access. When a thread pool spawns an asynchronous operation, it may be completed by another thread pool, which will be the result of an asynchronous operation. While this

Fortunately, the FCL defines a base class, called System.Threading.SynchronizationContext, which solves all these problems. Simply stated, a SynchronizationContext-derived object connects an application model to its threading model. The FCL defines several classes derived from SynchronizationContext, but usually you will not directly with these classes; in fact, many of them are not publicly exposed or documented.

For the most part, application developers do not need to know anything about the SynchronizationContext class. When you await a Task, the calling thread’s SynchronizationContext object is obtained. When a thread pool completes the Task, the SynchronizationContext object is used, using the right threading model for your application model. So, when a GUI awaits a Task, the code following the await operator is guaranteed to execute on the GUI thread well, allowing that code to update UI elements.¹12 For an ASP.NET application, the code following the await operator is guaranteed to execute on a thread pool that has the client’s culture and principal information associated with it.

Most of the time, having a state machine using the application model’s threading model is phenomenally useful and convenient. But on some occasions, this can get you into trouble. Here is an example that causes a WPF application to deadlock.

```csharp
private sealed class MyWpfWindow : Window {
    public MyWpfWindow() { Title = "WPF Window"; }

    protected override void OnActivated(EventArgs e) {
        // Querying the Result property prevents the GUI thread from returning;
        // the thread blocks waiting for the result
        string http = GetHttp().Result; // Get the string synchronously!

        base.OnActivated(e);
    }

    private async Task<string> GetHttp() {
        // The HTTP request and let the thread return from GetHttp
        HttpResponseMessage msg = await new HttpClient().GetAsync("http://Intellect.com/");
        // We never get the result: The GUI thread is waiting for this method to finish but this method
        // can't finish because the GUI thread is waiting for it to finish -- DEADLOCK!

        return await msg.Content.ReadAsStringAsync();
    }
}
```

Developers creating class libraries need to be aware of the SynchronizationContext class so they can write high-performance code that works with all application models. A lot of class library code is application agnostic, want to avoid any additional overhead involved

in a Synchronization object. In addition, class library developers should do everything in their power to help application developers avoid situations. To solve both of these problems, the Task and TResult classes offer a method called ConfigureAwait whose signature looks like this.

```csharp
// Task defines this method:
```

```csharp
public ConfigureTaskAwait<TResult> ConfigureAwait(Boolean onCaptured);
```

Passing true to this method gives you the same behavior as not calling the method. But, if you pass false, the await operator does not query the SynchronizationContext and, when a thread pool completes the Task, it simply completes it and the code after the await operator executes via the thread pool.

Even though GetMethod is not class library, the deadlock problem goes away if you add to ConfigureAwait. Here is the modified version of your GetMethod.

```csharp
private async Task<string> GetHttp() {
// The HTTP request and let the thread return from GetHttp
HttpResponseMessage msg = await new HttpClient().GetAsync("http://intellect.com/").ConfigureAwait(false);
// WE DO get here now because a thread pool can execute this code
// as opposed to forcing the GUI thread to execute it.

return await msg.Content.ReadAsStringAsync().ConfigureAwait(false);
}
```

As the preceding code shows, ConfigureAwait(false) must be applied to every Task object you await. This is because asynchronous operations may complete synchronously and, when this happens, the calling thread simply continues without returning to its caller; you never know which operation requires ignoring the SynchronizationContext, so you have to tell all of them to ignore it. This also means that your library code should be application model agnostic.

Alternatively, I could re-write my GetHttp method so far that the thread executes via a thread pool.

```csharp
private Task<string> GetHttp() {
return Task.Run(async () => {
// We run on a thread pool now that has no SynchronizationContext on it
HttpResponseMessage msg = await new HttpClient().GetAsync("http://intellect.com/");
// WE DO get here because some thread pool can execute this code

return await msg.Content.ReadAsStringAsync();
});
}
```

In this version of the code, notice that your GetHttp method is not an async function; I removed the async keyword from the method signature, because the method no longer has an await operator in it. On the other hand, the lambda expression I pass to Task.Run is an async function.
