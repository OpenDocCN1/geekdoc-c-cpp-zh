
# Parsing a String to Obtain an Object: Parse

In the preceding section, I explained how to take an object and obtain a string representation of that object. In this section, I'll talk about the opposite: how to take a string and obtain an object representation of it. Obtaining an object from a string isn't a very common operation, but it does occasionally come in handy. Microsoft felt it necessary to formalize a mechanism by which strings can be parsed into objects.

Any type that can parse a string offers a public, static method called Parse. This method takes a String and returns an instance of the type; in a way, Parse acts as a factory. In the CLR, a Parse method exists on all of the numeric types as well as for DateTime, and few other types (such as the SQL data types).

Let's look at how to parse a string into a number type. Almost all of the numeric types (Byte, SByte, Int16/UInt16, Int32/UInt32, Int64/UInt64, Double, Decimal, and BigInteger) offer at least one Parse method. Here I'll show you just the Parse method defined by the Int32 type (The Parse methods for other numeric types work similarly to Int32's)

```c
public static Int32 Parse(String s, NumberStyles style, IFormatProvider provider);
```

Just from looking at the prototype, you should be able to guess exactly how this method works. The String parameter identifies a string representation of a number you want parsed into an Int32 object. The System.Globalization.NumberStyles parameter is a set of flags that identifies characters Parse should expect to find in the string. And the IFormatProvider parameter identifies an object that the Parse method can use to obtain culture-specific information, as discussed earlier in this chapter.

For example, the following code causes Parse to throw a System.FormatException because the string being parsed contains a leading space.

```c
Int32 x = Int32.Parse(" 123", NumberStyles.None, null);
```

To allow Parse to skip the leading space, change the style parameter to AllowLeadingWhite.

```c
Int32 x = Int32.Parse(" 123", NumberStyles.AllowLeadingWhite, null);
```

See the .NET Framework documentation for a complete description of the bit symbols and common combinations that the NumberStyles enumeration defines.

Here's a code fragment showing how to parse a hexadecimal number.

```c
Int32 x = Int32.Parse("1A", NumberStyles.HexNumber, null);
Console.WriteLine(x); // Displays "26"
```

This Parse method accepts three parameters. For convenience, many types offer additional overloads of Parse so you don't have to pass as many arguments. For example, Int32 offers four overloads of the Parse method.

```csharp
// Parse NumberStyles.Integer for style
// and thread's culture's provider information.
public static Int32 Parse(String s);
```

```csharp
// Parses thread's culture provider information.
public static Int32 Parse(String s, NumberStyles styles);
```

```csharp
// Parse NumberStyles.Integer for the style parameter.
public static Int32 Parse(String s, IFormatProvider provider);
```

```csharp
// This is the method I've been talking about in this section.
public static Int32 Parse(String s, NumberStyles styles, IFormatProvider provider);
```

The DateTime type also offers a Parse method.

```csharp
public static DateTime Parse(String s, IFormatProvider provider, DateTime styles);
```

This method works just as the Parse method defined on the number types except that DateTime's Parse takes a set of bit flags defined by the System.Globalization.DateTimeStyles enumerated instead of the NumberStyles enumerated type. The .NET Framework SDK documentation for a complete description of the bit symbols and common the DateTimeStyles types.

For convenience, the DateTime type offers three overloads of the Parse method.

```csharp
// Parses thread's culture's provider information
// and DateTimeStyles.None for the style
public static Int32 Parse(String s);
```

```csharp
// Parses DateTimeStyles.None for the style
public static DateTime Parse(String s, IFormatProvider provider);
```

```csharp
// This is the method I've been talking about in this section.
public static DateTime Parse(String s, IFormatProvider provider, DateTimeStyles styles);
```

Parsing dates and times is complex. Many developers have found the Parse method of the DateTime too forgiving that it sometimes parses strings that don't contain dates or times. For this reason, the DateTime type offers a ParseExact method that accepts exactly how the date/time string should be formatted and how it should be parsed. For more information about format, see the DateTimeFormat class in .NET SDK.

Some developers have reported that when their application calls Parse frequently, and throws exceptions (due to invalid input), performance suffers. For these performance-sensitive users, added TryParse methods to handle all of the numeric types, DateTime, DateTimeOffset, and IPAddress like:

```csharp
public static boolean TryParse(string s, NumberStyles style, IFormatProvider provider, out Int32 result);
```

As you can see, this method returns true or false indicating whether the string can be parsed into Int32. The variable passed by reference will contain the parsed value. As discussed in Chapter 2, "Exceptions and State Management."

# Encodings: Converting Between Characters and Bytes

In Windows, programmers frequently have to convert Multi-Byte Character Set (MBC) characters and strings, and it's very tedious and error-prone to use. In the CLR, all characters are represented as 16-bit Unicode values, which makes working with characters and strings easy. At times, however, you want to save strings to a file or transmit them over a network. Encodings also allow managed applications. For example, if you want to produce a file readable by an application running on Windows 95, you have to use Shift-JIS (code page 932) encoding. Encoding is typical when you want to send a string to a file or network using System.IO.BinaryWriter or System.IO.StreamWriter. Decoding is typical when you want to read a string from a file or network using System.IO.BinaryReader or System.IO.StreamReader. If you don't explicitly specify an encoding, all of these types default to UTF-8 (UTF stands for Unicode Transformation Format). However, at times you might want to explicitly encode or decode a string. This section will give you more insight into the encodings.

Fortunately, the FCL offers some types to make character encoding and decoding easy. The most frequently used encodings are UTF-16 and UTF-8:

- UTF-16 encodes 16-bit character as 2 bytes. It doesn't affect the characters at all, and no compression occurs—its performance is excellent. UTF-16 is also referred to as Unicode-encoding. Note that UTF-16 can be converted from little-endian to big-endian and vice versa.
- UTF-8 encodes some characters as 1 byte, characters as 2 bytes, some as 3 bytes, and some as 4 bytes. Characters with a value below 0x080 are compressed to 1 byte, which works very well for characters used in the United States. Characters between 0x080 and 0x7FF are converted to 2 bytes, which works well for European and Middle-Eastern languages. Characters of 0x0800 and above are converted to 3 bytes, which works well for East Asian languages. Finally, surrogate pairs are written out 4 bytes. UTF-8 is an extremely popular encoding, but it's less efficient than UTF-16 if you encode many characters with values of 0x0800 or above.

Although UTF-16 and UTF-8 encodings are by far the most common, the FCL supports some encodings that are used less frequently:

- UTF-32 encodes all characters as 4 bytes. This encoding is useful when you don't want to deal with characters taking a variable number of bytes. For example, with UTF-32, you do not need to think about surrogates because character is 4 bytes. Obviously, UTF-32 is not an efficient encoding in terms of memory usage and is therefore rarely used for saving or transmitting strings to a file or network. This encoding is typically used inside the program itself. Also UTF-32 can be converted from little-endian to big-endian and vice versa.
- UTF-7 encoding is typically used with older systems that work with characters that can be expressed using 7-bit values. You should avoid this encoding because it usually ends expanding the data rather than compressing it. The Unicode Consortium has deprecated this encoding.
- ASCII encodes the 16-bit characters into ASCII characters; that is, any 16-bit character with a value less than 0x080 is converted to a single byte. Any character with a value greater than 0x7F can't be converted, so that character's value is lost. For strings consisting of characters in the ASCII range (0x00 to 0x7F), this encoding compresses the data in half and is very fast (because the high is just cut off). This encoding is not appropriate if you have characters outside of the ASCII range whose characters will be lost.
