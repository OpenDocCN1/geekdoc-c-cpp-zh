The simple host/add-in scenario just doesn't use AppDomains. However, in a real-life scenario, you likely create each add-in in its own AppDomain with its own security and configuration settings. And of course, each AppDomain could be unloaded if you want to remove an add-in from memory. To communicate with the AppDomain, you'd either tell the add-in developers to derive their add-ins from MarshallByRefObject, or have the application definition's own internal type that is derived from MarshallByRefObject. The host would create an instance of its MarshallByRefObject-derived type in the new AppDomain. The host's code (the default AppDomain) would communicate with its own (in the other AppDomains) to have load add-in assemblies and create and use instances of the add-types.

# Reflection to Discover a Type’s Members

So far, this chapter has focused on the parts of reflection—assembly loading, type discovery, and object construction—necessary to build a dynamically extensible application. In order to have good performance and compile-time type safety, you want to avoid using reflection as much as possible. In dynamically extensible application scenario, the host code typically calls the object to an interface type or a base class that is known at compile time; this allows the object's members to be accessed in a high-performance and compile-time type-safe way.

In the remainder of this chapter, I am going to focus on other aspects of reflection that you can use to discover and invoke a type's members. The ability to discover and invoke a type's members is typically used to create tools and utilities that analyze an assembly by looking for certain programming patterns or use of certain members. Examples of tools/utilities that this are ILasm.exe, FxCopCmd.exe, and Visual Studio's Windows Forms, Web Presentation. In addition, some class libraries use the ability to discover and invoke a type’s members in order to offer rich functionality as a convenience to developers. Examples of class libraries that do so serialization/deserialization/simple data binding.
