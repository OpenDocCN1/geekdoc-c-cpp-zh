
# Code Contracts

Code contracts provide a way to declaratively document design decisions that you've made about your code within the code itself. The contracts take the form of the following:

- **Preconditions** Typically used to validate arguments
- **Postconditions** Used to validate state when a method terminates either due to a normal return or to throwing an exception
- **Object Invariants** Used to ensure an object's fields remain in a good state throughout an object's lifetime

Code contracts facilitate code usage, understanding, evolution, testing, documentation, and early error detection.¹¹⁰ You can think of preconditions, postconditions, and object invariants as parts of method's signature. As such, you can loosen a contract with a new version of your code, you can make a contract stricter with a new version without breaking compatibility.

At the heart of the code contracts is the static System.Diagnostics.Contracts.Contract class.

```cs
public static class Contract {
    public Precondition methods: [Conditional("CONTRACTS_FULL")];
    public static void Requires(Boolean condition);
    public static void EndContractBlock();

    // Postconditions: Always
    public static void Requires<TException>(Boolean condition) where TException : Exception;

    // Postcondition methods: [Conditional("CONTRACTS_FULL")];
    public static void Ensures(Boolean condition);
    public static void EnsuresOnThrow<TException>(Boolean condition)
    where TException : Exception;

    // Special Postmethods: Always
    public static T Result<T>();
    public static T 0OldValue<T>(out T value);
    public static T ValueAtReturn<T>(out T value);

    // Object Invariant methods: [Conditional("CONTRACTS_FULL")];
    public static void Invariant(Boolean condition);

    // Quantifier methods: Always
    public static bool Exists<T>(IEnumerable<T> collection, Predicate<T> predicate);
    public static bool Exists(Int32 inclusive, Int32 toExclusive,
    Predicate<Int32> predicate);
    public static bool ForAll<T>(IEnumerable<T> collection, Predicate<T> predicate);
    public static bool ForAll(Int32 inclusive, Int32 toExclusive,
    Predicate<Int32> predicate);
    // Helper methods: [Conditional("CONTRACTS_FULL")] or [Conditional("DEBUG")];
    public static void Assert(Boolean condition);
```

As previously indicated, many of these static methods have the [Conditional(CONTRACTS FULL)] attribute applied to them. Some of the other methods also have the [Conditional-DEBUG] attribute applied to them. This means the compiler will ignore any code you write that calls these methods unless the appropriate symbol is defined when compiling your code. Any methods marked with "Always" mean the compiler always emits them to call the method. Any methods marked with Requires, Requires-Exception, Ensures, EnsuresOnThrow, Invariant, Assert, and Assume methods have an overload (not) that takes a String argument so you can explicitly specify a string message when the contract is violated.

To turn on code contract features, select the Perform Runtime Checking check box and select From from the combo box next to it. This defines the CONTRACTS_FULL symbol when you build your project and invokes the appropriate tools (described shortly) after building your project. Now, at run time, when a contract is violated, Contract.Failed event is raised. Usually, developers do not register any methods with this event, but if you do, then any methods you register receive a ContractFailedEventArgs object that looks like this.

```cs
public sealed class ContractFailedEventArgs : EventArgs {
    public ContractFailedEventArgs(ContractFailureKind kind,
                                    String message, String condition, Exception originalException) {

    public ContractFailureKind Kind { get; }
    public String Message { get; }
    public String Condition { get; }
    public Exception OriginalException { get; }

    public bool SetHandled { get; set; } // true if any handler called SetHandled
    public void SetHandled(); // Call to ignore the violation; sets Handled to true

    public bool Unwind { get; set; } // true if any handler called SetUnwind
    public void SetUnwind(); // Call to force Contractexception; sets Unwind to true
}
```

Multiple handlers can be registered with this event. Each method can process the contract violation any way it chooses. For example, a handler can ignore the violation (by calling SetHandled), or terminate the process. If any method calls SetHandled, then the violation will be considered handled, and after all the handlers return, the application code is allowed to continue running unless any handler calls SetUnwind. If a handler calls SetUnwind, then, after all the handlers have completed running, a System.Diagnostics.Contracts.ContractException is thrown. This type is internal to MSCorLib.dll and therefore you cannot write a catch block to catch it explicitly. Also note that if any handler throws an unhandled exception, then the remaining handler methods are invoked and then a ContractException is thrown.

If there are no event handlers or none of them call SetHandled, SetUnwind, or throw an unhandled exception, then default processing of the contract violation happens next. If the CLR is running an application on a non-interactive window station (which would be the case for a Windows service application), then Environment.FailFast is called to instantly terminate the process. If you compile with the Assert On Contract Failure check box selected, then an alert dialog will appear allowing you to connect a debugger to your application. If this option is not selected, then a ContractException is thrown.

Let's look at a sample class that uses code contracts.

```cs
public sealed class Item { /* ... */ }
```

```cs
public sealed class ShoppingCart {
    private List<Item> m_cart = new List<Item>();
    private Decimal m_totalCost = 0;
}
```

```cs
public ShoppingCart() {
}
```

```cs
public void AddItem(Item item) {
    AddItemHelper(m_cart, item, ref m_totalCost);
}
```

```cs
private static void AddItemHelper(List<Item> m_cart, Item newItem,
    ref Decimal totalCost) {

// // Preconditions:
Contract.Requires(newItem != null);
Contract.Requires(Contract.ForAll(m_cart, s => s != newItem));

// // Postconditions:
Contract.Ensures(Contract.Exists(m_cart, s => s == newItem));
Contract.Ensures(totalCost == Contract.OldValue(totalCost));
Contract.EnsuresOnThrow(totalCost == Contract.OldValue(totalCost));

// Do some stuff (which could throw an IOException)
m_cart.Add(newItem);
totalCost += 1.0M;
}
```

```cs
// ObjectInvariantMethod
private void ObjectInvariant() {
    Contract.Invariant(m_totalCost >= 0);
}
```

The AddItem method defines a bunch of contracts. It indicates that the item being added to the cart is not already in the cart. newItem must not be null and the postconditions indicate that the new item must be in the cart and that the total cost must be at least much as it was before the item was added to the cart. The preconditions also indicate that if AddItemHelper to throw an IOException for some reason, then totalCost is unchanged from what it was when the method started to execute. The ObjectInvariant method is a private method that, when called, makes sure that the object's m_totalCost field never contains a negative value.

> Important members referenced in a precondition, postcondition, or invariant test must be side-effect free. This required testing conditions should not change the state of the object itself. In addition, members referenced in a precondition test must be least as accessible as the method defining the precondition. This is required callers of the method should be able to verify that they have met all the preconditions prior to invoking the method. On the other hand, members referenced in a postcondition or invariant test have any accessibility as long as the code can compile. The reason accessibility is not important is because postcondition and invariant tests do not affect the callers' ability to invoke the method correctly.
