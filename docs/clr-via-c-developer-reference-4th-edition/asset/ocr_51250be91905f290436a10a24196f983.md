# CLS and Non-CLS Exceptions

All programming languages for the CLR must support the throwing of Exception-derived objects because the Common Language Specification (CLS) mandates. However, the CLR allows an instance of any type to be thrown, and some programming languages allow code to throw non–CLS-compliant exception objects as a String, Int32, or DateTime. The C# compiler allows code to throw only Exception-derived objects, whereas code written in other languages allow code to throw Exception-derived objects in addition to objects that are not derived from Exception.

Many programmers are not aware that the CLR allows any object to be thrown to report an exception. Most developers believe that Exception-derived objects can be thrown. Prior to CLR 2.0, when programmers wrote catch blocks to catch exceptions, they were CLS-compliant exceptions only. If a C# method called a method written in another language, and that method threw a non–CLS-compliant exception, the C# code would not catch this exception at all, leading to security vulnerabilities.

In CLR 2.0, Microsoft introduced a new RuntimeWrappedException class. This is derived from Exception, so it is a CLS-compliant exception. The RuntimeWrappedException class contains a private field of type Object (which can be accessed by using RuntimeWrappedException.Exception read-only property). In CLR 2.0, when a non–CLS-compliant exception is thrown, the CLR automatically constructs an instance of the RuntimeWrappedException class and initializes its field to refer to the object that was actually thrown. In effect, the CLR now turns all non–CLS-compliant exceptions into CLS-compliant exceptions. Any code that catches an Exception type will catch non–CLS-compliant exceptions, which fixes the potential security vulnerability problem.
