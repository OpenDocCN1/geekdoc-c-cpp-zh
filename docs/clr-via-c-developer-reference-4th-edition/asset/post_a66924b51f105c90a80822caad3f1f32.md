
I mentioned earlier that unboxing operation is frequently followed immediately by a field copy. Let's take a look at C# code demonstrating unbox and copy operations work together.

```csharp
public static void Main() {
    Point p;
    p.x = p.y = 1;
    Object o = p; // Boxes p; o refers to the boxed instance

    p = (Point)o; // Unboxes AND copies fields from boxed
                   // Instance to stack variable
}
```

On the last line, the C# compiler emits an IL instruction to unbox o (get the address of the fields in the boxed instance) and another IL instruction to copy the fields from the heap to the stack-based variable p.

Now look at this code.

```csharp
public static void Main() {
    Point p;
    p.x = p.y = 1;
    Object o = p; // Boxes p; o refers to the boxed instance

    // Change Point's field to 2
    p = (Point)o; // Unboxes AND copies fields from boxed
                   // Instance to stack variable
    p.x = 2; // Changes the state of the stack variable
    o = p; // Boxes p or refers to a new boxed instance
}
```

The code at the bottom of this fragment is intended to change Point's field from 1 to 2. To do this, unboxing operation must be performed, followed by a field copy, followed by changing the field (on the stack), by a boxing operation (which creates a new boxed instance in the managed heap). Hopefully, you see the impact that boxing and unboxing/copy operations have on your application's performance.

Some languages, as C++/CLI, allow you to unbox a boxed value without copying the fields. Unboxing returns the address of the object (ignoring the object's type pointer and sync block overhead). You can now use this to manipulate the unboxed instance's fields (which happen to be in a boxed object on the heap). For example, the previous code would be much more efficient if written in C++/CLI, because you could change the value of Point's field within the well boxed Point instance. This would avoid both allocating a new object on the heap and copying all of the fields twice!

> **Important**: If you're the least concerned about your application's performance, you must be aware of when the compiler produces these operations. Unfortunately, many compilers implicitly emit code to box objects, so it is not obvious when you write code that boxing is occurring. If I am concerned about the performance of a particular algorithm, I always use a tool such as ILasm.exe to view the IL code for my methods and see where the box IL instructions are.

Let's look at a few examples that demonstrate boxing and unboxing.

```csharp
public static void Main() {
    Int32 v = 5; // Create an unboxed value type variable.
    Object o = v; // o refers to a boxed Int32 containing 5.
    v = 123; // Changes the boxed value to 123

    Console.WriteLine("" + (Int32)o + " , " + v); // Displays "123, s"
}
```

In this code, can you guess how boxing operations occur? You might be surprised to find that the answer is three! Let's analyze the code carefully to really understand what's going on. To help you understand, I've commented the IL code generated for the Main method shown in the preceding code. I've commented the code so that you can easily see the underlying operations.

```il
.method public static void Main() {
    .entrypoint
    // Code size 45 (0x2d)
    .maxstack 3
    .locals init [0]int32 v, [1]object o
    // Load 5 into v.
    IL_0000: ldc.i4.5
    IL_0001: stloc.0
    // Box v and store the reference pointer in o.
    IL_0002: ldc.i4.0
    IL_0003: box [mscorlib]System.Int32
    IL_0008: stloc.1

    // Load 123 into v.
    IL_0009: ldc.i4.s 123
    IL_000b: stloc.0

    // Box v and leave the pointer on the stack for Concat.
    IL_000c: ldc.i4.0
    IL_000d: box [mscorlib]System.Int32

    // Load the string on the stack for Concat.
    IL_0012: ldstr ","
    // The string returned from Concat is passed to WriteLine.
    IL_0027: call void [mscorlib]System.Console:WriteLine(string)

    // Return from Main terminating this application.
    IL_002c: ret
} // end of method App::Main
```

First, an Int32 boxed value type (v) is created on the stack and initialized to 5. Then a variable (o) typed as Object is created, and initialized to v. But because reference type variables must always be boxed to objects in the heap, C# generated the proper IL to box and store the address of the boxed copy of v in o. Now the value 123 is placed into the boxed value type instance v; this has no effect on the Int32 value, which keeps its value of 5.

Next is the call to the WriteLine method. WriteLine wants a String object passed to it, but there is no string object. Instead, these three items are available: an unboxed Int32 value type instance (v), a String (a reference type), and a reference to a boxed Int32 value type instance (o) that is being cast to an unboxed Int32. These must be combined to create a String.

To create a String, the C# compiler generates code that calls String's static Concat method. There are several overloaded versions of the Concat method, all of which perform identically—the difference is in the number of parameters. Because a string is being created from the concatenation of three items, the compiler chooses the following version of the Concat method.

```csharp
public static String Concat(object arg0, object arg1, object arg2)
```

For the first parameter, arg0, v is passed. But v is an unboxed value parameter and arg0 is an Object, so v must be boxed and the address of v is passed for arg0. For the arg1 parameter, " " is passed as a reference to a String object. Finally, for the arg2 parameter, o (a reference to a boxed Int32) is cast to an unboxed Int32. This requires an unboxing operation (but no copy), which retrieves the Int32 contained inside the boxed instance address passed to Concat's arg2 parameter. This is identical to the earlier version except that I've removed the (Int32) cast to show savings.
