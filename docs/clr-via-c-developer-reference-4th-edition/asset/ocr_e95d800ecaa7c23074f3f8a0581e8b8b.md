One of the nice things about exceptions is that an unhandled exception causes your application to terminate. This is nice during testing, you will discover problems quickly and the information you get with an unhandled exception (error message and stack trace) are usually enough to allow you to fix your code. Of course, a lot of companies don't want their application to terminate after it has been tested and deployed, so many of developers insert code to catch System.Exception. The base class of all exception types. However, the problem with catching System.Exception and allowing the application to continue running is that state may be corrupted.

Earlier in this chapter, I showed an Account class that defines a Transfer method whose job is to transfer money from one account to another. What if, this Transfer method is called, it successfully subtracts money from the account and then inserts an exception before it moves money to the account? If calling catches System.Exception and continues running, the state of the account is corrupted; both the from and accounts have less money in them they should. Because we are talking about money here, this state corruption wouldn't be considered a simple bug, but would definitely be a security bug. If the application continues running, it will attempt to perform more transfers to from various accounts and now state corruption remains within the application.

One could say that the Transfer method itself should catch System.Exception and restore money back into account. This might actually work out if the Transfer method is simple enough. But if the Transfer method produces an audit record of the withdrawn money or if others are manipulating the same account at the same time, then attempting to undo the operation could fail as well, producing yet another thrown exception. And now, state corruption is getting worse, not better.

> Note One could argue that knowing something went wrong is more useful than knowing what error occurred. For example, it might be more useful to know that transferring money out of an account failed instead of knowing that Transfer failed due to a SecurityException or OutOfMemoryException. In fact, the Win32 error model works this way: methods return true/false to indicate success/failure so you know which method failed. If your program cares about why it failed, it calls the Win32 GetLastError method. System.Exception has a Source property that tells you the method that failed. But this property is a String that you'd have to parse, and if two methods call the same method, you can't tell from the Source property alone which your code failed. Instead, you'd have to parse the String returned from Exception's StackTrace property to get this information. Because this is so difficult, I've never seen anyone actually write code to do it.
