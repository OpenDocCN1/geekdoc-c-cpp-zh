
Now to create an instance of an object in the new AppDomain, we must first load an assembly into the new AppDomain and construct an instance of a type defined in this assembly. This is precisely what the call to AppDomain's public, CreateInstanceAndUnwrap method does. When calling CreateInstanceAndUnwrap, I pass two arguments: a String identifying the assembly I want loaded into the new AppDomain (referenced by the ad2 variable) and String identifying the name of the type that I want to construct an instance of. Internally, CreateInstanceAndUnwrap causes the thread to transition from the current AppDomain to the new AppDomain. Now, the thread (which is inside the call to CreateInstanceAndUnwrap) loads the specified assembly into the new AppDomain and scans the assembly's type metadata, looking for the specified type (`MarshalByRefType`). After the type is found, the thread calls the MarshalByRefType's parameterless constructor. Now the thread transitions back to the default AppDomain so that CreateInstanceAndUnwrap can return a reference to the new MarshalByRefType object.

> There are overloaded versions of CreateInstanceAndUnwrap that allow you to call a type's constructor passing in arguments.

Although this sounds all fine, and there is a problem: the CLR cannot allow a variable (root) living in one AppDomain to reference an object created in another AppDomain. If CreateInstanceAndUnwrap simply returned the object, isolation would be broken, and isolation is the whole purpose of AppDomains! So, if CreateInstanceAndUnwrap returns the object, it performs some additional logic.

You'll notice that the MarshalByRefType type is derived from a very special base class: System.MarshalByRefObject. When CreateInstanceAndUnwrap sees that it is marshalling an object whose type is derived from MarshalByRefObject, the CLR will marshal the object by reference across the AppDomain boundaries. Here is what it means to marshal an object by reference from one AppDomain (the source AppDomain where the object is created) to another AppDomain (the destination AppDomain from where CreateInstanceAndUnwrap is called).

When a source AppDomain wants to send or return the reference of an object to a destination AppDomain, the CLR defines a proxy type in the destination AppDomain's loader. This proxy is defined using the original type's metadata, and therefore, it looks exactly like the original type; it has all of the same instance members (properties, events, and methods). The instance fields are not part of the type, but I'll talk about this in a moment. This new type does have some fields defined inside of it, but these are not identical to that of the original data type. Instead, these fields indicate which AppDomain "owns" the real object and how to find the real object in the owning AppDomain. (Internally, the proxy object uses a GHandle that refers to the real object. The GHandle is discussed in Chapter 21, "Managed Heap and Garbage Collection.")

After this type is defined in the destination AppDomain, CreateInstanceAndUnwrap creates an instance of this proxy type, initializes its fields to identify the source AppDomain and the real object, and returns a reference to this proxy object to the destination AppDomain. In My Ch22-1-AppDomains application, the mnt variable will be set to this proxy. Notice that the object returned from CreateInstanceAndUnwrap is actually not an instance of the MarshalByRefType. The CLR usually does not allow you to cast an object of one type to an incompatible type. However, in this situation, the CLR allows the cast, this new type has the same instance members as defined on the original type. If you use the proxy object to call GetType(), it lies and says it is a MarshalByRefType.

It is possible to prove that the object returned from CreateInstanceAndUnwrap is actually a reference to a proxy object. To do this, my Ch22-1-AppDomains calls System.Runtime.Remoting.RemotingService's public, static IsTransparentProxy method passing the reference returned from CreateInstanceAndUnwrap. As you can see from the output, IsTransparentProxy returns true, indicating that the object is a proxy.

Now, my Ch22-1-AppDomains uses the proxy to call the SomeMethod. Because the mbr variable refers to a proxy object, the proxy's implementation of this method is called. The proxy's implementation uses the information fields inside the proxy object to transition the calling thread from the AppDomain to the new AppDomain. Any actions now performed by this thread run under the new AppDomain's security and configuration settings. The thread uses the proxy object's GHandle to find the object in the new AppDomain, and then it uses the real object to call the real SomeMethod.

There are two ways to prove that the calling thread has transitioned from the AppDomain to the new AppDomain. First, inside the SomeMethod method, I call Thread.GetDomain().Friendly-Name. This will return "AD #2" (as evidenced by the output) the thread is now running in the new AppDomain created by using AppDomain.CreateDomain with "AD #2" as the friendly name parameter. Second, if you step through the code in a debugger and display the Call Stack, the [AppDomain Transition] line marks where a thread has transitioned across an AppDomain. When the real SomeMethod returns, it returns to the proxy's SomeMethod, which transitions the thread back to the default AppDomain, and then the thread continues executing in the default AppDomain. When a thread in one AppDomain calls a method in another AppDomain, the thread transitions between the AppDomain boundaries are executed synchronously. However, at any given time, a thread is considered to be in one AppDomain, and it executes code using AppDomain's security and configuration settings. If you want to execute code in multiple AppDomains, you should create additional threads and execute them whatever AppDomains you want.

The next thing that Ch22-1-AppDomains application does is call AppDomain's public, static Unload method to unload the specified AppDomain, including all of the assemblies loaded into it. A garbage collection is forced to free any objects that were created by the unloading AppDomain. At this point, the default AppDomain mbr variable still refers to a valid proxy object; however, the proxy object no longer refers to a valid AppDomain (because it has unloaded).

When the default AppDomain attempts to use the proxy object to call the SomeMethod, the proxy's implementation of this method determines that the AppDomain that contains the real object has unloaded, and the proxy's SomeMethod throws an AppDomainloadedException to let the caller know that the operation cannot complete.

The CLR team at Microsoft had to do a lot of work to ensure AppDomain isolation, but it is important work because these features are used heavily and are being more and more by developers every day. Obviously, accessing objects across AppDomain boundaries by marshall-reference semantics has performance costs associated with it, so you would typically want to use this feature to manage I promised that I'd talk a little about instance fields. A type derived from MarshalRef can define instance fields. However, these fields are not defined as part of the proxy and are not contained inside a proxy object. When you write code that reads or writes to an instance of a type derived from MarshalRefObject, the JIT compiler embeds code that uses the proxy object (to find the real AppDomain/object) by calling System.Object's FieldGetter and FieldSetter methods, respectively. These methods are private and undocumented; they are basically methods that use reflection to get and set the value in a field. So although you can access fields of a type derived from MarshalRef, the performance is particularly bad because the CLR really ends calling methods to perform the field access.³ If the CLR required that all fields be present (which is recommended for good data encapsulation), then the FieldGetter and FieldSetter methods wouldn't have to exist and access fields from methods could always have been direct, avoiding any penalty penalty.
