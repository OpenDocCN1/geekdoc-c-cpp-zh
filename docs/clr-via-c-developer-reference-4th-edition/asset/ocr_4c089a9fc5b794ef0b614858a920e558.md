Well, without a doubt, we can say sure that all of the applications we've just discussed are using threads independently. There is just no way that all of these threads need to exist in the system. It is one to allocate resources inside an application; it's quite another to allocate and then not use them. This is wasteful, and allocating all the memory for threads stacks means that there is less for more important data, such as a user's document.³

To make matters worse, what if these processes were running in a single user's Remote Desktop Services session—and what if there were actually 100 users on this machine? Then there would be 100 instances of Outlook, all creating 24 threads only to do nothing with them. That's 2,400 threads each with its own kernel object, TEB, user-mode stack, kernel-mode stack, etc. There is a lot of wasted resources. This madness has to stop, especially if Microsoft wants to give users a good experience when running Windows on notebook computers, many of which have only 1 GB of RAM. Again, the chapters in this part of the book will describe how to properly design an application to use very few threads in an efficient manner.

> ³ I cannot resist sharing with you another demonstration of how bad this situation is. Try this: open Notepad.exe and use Task Manager to see how many threads are in (you should see 1). Then select Notepad's File menu item to display the common File Open box. After the dialog opens, look at Task Manager to see how many threads you just created. On my machine, 31 additional threads were created by displaying this dialog box! In fact, every application that uses the common File or Save dialog box will get many additional threads created inside it idle side of the time. A lot of these threads aren't even destroyed when the dialog box is closed!
