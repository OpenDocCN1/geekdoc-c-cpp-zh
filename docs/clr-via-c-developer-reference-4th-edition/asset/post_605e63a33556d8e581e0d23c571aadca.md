
Using C# fixed statement more efficient than allocating a pinned GC pool. What happens is that the C# compiler emits a special "pinned" flag on the bytes local variable. During a garbage collection, the GC examines the contents of this root, and if the root is not null, it knows not to move the object referred to by variable during the compaction phase. The C# compiler emits IL to initialize an IL instruction to set the bytes local variable back to null at the address of the object of a fixed block, the compiler emits IL until the end of the fixed block that the variable doesn't refer to any object, allowing the object to move when the next garbage collection occurs.

Now, let's talk about the next two flags, Weak and WeakTrackResurrection. These flags can be used in scenarios when interoperating with native code, but they can also be used in scenarios that use only managed code. The Weak flag lets you know when an object has been determined to garbage; the object's memory is not guaranteed to be reclaimed. The WeakTrackResurrection flag lets you know when an object's memory has been reclaimed. Of the two, the Weak flag is much more commonly used than the WeakTrackResurrection flag. I've never seen such the WeakTrackResurrection flag in a real application.

Let's say Object-A periodically calls a method on Object-B. However, the fact that Object-A has a reference to Object-B forbids Object-B from being garbage, and in some scenarios, this may not be desired; we want Object-A to call Object-B's method if Object-B is still alive in the managed heap. To accomplish this scenario, use GCHandle.Alloc passing the reference to Object-B and the Weak flag. Object-A would now just have the returned GCHandle instance instead of the Object-B.

At this point, Object-B can be garbage collected if no roots are keeping it. When Object-A wants to call Object-B's method, it would query GCHandle's read-only Target property. If this property returns a non-null value, then Object-B is still alive. Object-A would then cast the returned to Object-B's type and call the method. If the Target property returns null, then Object-B has been collected (but not finalized) and Object-A would not attempt to call the method. At this point, Object-A's code would probably call GCHandle.Free to relinquish the GCHandle instance.

Because working with the GCHandle type can be a bit cumbersome because it requires elevated to keep or pin an object in memory, the System namespace includes a WeakReference<T> class to help you.

```c
public sealed class WeakReference<T> : ISerializable where T : class {
    public WeakReference(T target);
    public WeakReference(T target, bool trackResurrection);
    public void SetTarget(T target);
    public bool GetTarget(out T target);
}
```

This class is really just an object-oriented wrapper around a GCHandle instance: logically, its constructor calls GCHandle.Alloc, its GetTarget method queries GCHandle's Target property, its SetTarget method sets GCHandle's Target property, and its Finalize method protects it. In addition, no special options are required to use the WeakReference<T> class because the class supports only weak references; it doesn't support the behavior provided by GCHandle instances allocated with a GCHandleType.Normal or Pinned. The downside of the WeakReference<T> class is that an instance it must be allocated on the heap. The WeakReference<T> class is a heavier-weight object than a GCHandle instance.

**Important** When developers start learning about weak references, they immediately start thinking that they are in caching scenarios. For example, they would think it would be cool to construct a bunch of objects that contain a lot of data and to create weak references to these objects. When the program needs data, the program checks the weak reference to see if the object contains the data is still around, and if it is, the program uses it; the program experiences high performance. However, if a garbage collection occurred, the objects that contained the data would be destroyed, and the program has to re-create the data, the program experiences lower performance.

The problem with this is following: garbage collections do not only occur when memory is full or close to full. Instead, garbage collections occur whenever generation is full. So objects are tossed out of memory more frequently than desired, and your application's performance suffers greatly.

Weak references can be used effectively in caching scenarios, but building a good cache algorithm that finds the right balance between memory consumption and speed is very complex. Basically, you want cache to keep strong references to all of your objects and then, when you see that memory is getting tight, turning strong references into weak references. The CLR offers no mechanism to notify an application that memory is getting tight. But some people have had success by calling the Win32 GlobalMemoryStatus function and returning the MEMORYSTATUS structure dwMemoryLoad member. If this member reports a value above 80, memory is getting tight, and you can start converting strings to weak references based on whether you use a least-recently used algorithm, a most-frequently used algorithm, or whatever.

Developers frequently want to associate a piece of data with another entity. For example, you can associate data with a thread or with an AppDomain. It is also possible to associate data with an individual object using the System.Runtime.CompilerServices.ConditionalWeakTable<TKey, TValue> class, which looks like this:

```csharp
public sealed class ConditionalWeakTable<TKey, TValue>
    where TKey : class where TValue : class {
        public ConditionalWeakTable();
        public void Add(TKey key, TValue value);
        public TValue GetValue(TKey key, CreateValueCallback<TKey, TValue> createValueCallback);
        public bool TryGetValue(TKey key, out TValue value);
        public TValue GetGetValue(TKey key);
        public TValue GetOrCreate(TKey key);
        public bool Remove(TKey key);

        public delegate TValue CreateValueCallback(TKey key); // Nested delegate definition
    }
```

If you want to associate arbitrary data with one or more objects, you would create an instance of this class. Then, call the Add method, passing in a reference to some object for the key parameter and the data you want to associate with the object in the value parameter. If you attempt to add a reference to the same object than once, the Add method throws an ArgumentException; to change the value associated with the object, you must remove the key and add it back in the new value. Note that this class is thread-safe so multiple threads can use it concurrently, although this means the performance of the class is not stellar; you should test the performance of this to see how it works for your scenario.

Of course, a table object internally stores a WeakReference to the object passed in as the key; this ensures that the table does not forcibly keep the object alive. But what makes the Conditional-WeakTable class so special is that it guarantees the value remains in memory as long as the object identified by the key is in memory. So this is more than a normal WeakReference because if were, the value could be garbage collected even though the key object continued to live. The ConditionalWeakTable class could be used to implement the dependency property mechanism by XAML. It can also be used internally by dynamic languages to dynamically associate data with objects.
