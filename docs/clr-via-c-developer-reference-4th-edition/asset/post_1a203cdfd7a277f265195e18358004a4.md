
Whenever you obtain a stack trace, you might find that methods in the actual stack don't appear in the stack trace. There are two reasons for this. First, the stack is really a record of where the thread should return to, not where the thread has come from. Second, the just-in-time (JIT) compiler can inline methods to avoid the overhead of calling and returning from a separate method. Many compilers (including the C# compiler) offer a /debug command-line switch. When this switch is used, compilers embed information into the resulting assembly to tell the JIT compiler not to inline any of the assembly's methods, making stack traces complete and meaningful to the developer debugging.

![](img/0ce3b788d061e3d3095fa554b1a34adf_488_0.png)

Note The JIT compiler examines the System.Diagnostics.DebuggableAttribute attribute applied to the assembly. The C# compiler applies this attribute automatically. If this attribute has the DisableOptimization flag set, the JIT compiler won't inline the assembly's methods. Using the C# compiler's /debug switch sets this flag. By applying the System.Runtime.CompilerServices.MethodImplAttribute custom attribute to a method, you can forbid the JIT compiler from inlining the method for both debug and release builds. The following method definition shows how to forbid the method from being inline.

```
using System;
using System.Runtime.CompilerServices;

internal sealed class SomeType {
    [MethodImpl(MethodImplOptions.NoInlining)]
    public void SomeMethod() {
        ...
    }
}
```

The original idea was that Exception, would be the base for all exceptions and for two other types, System.Exception and System.ApplicationException, would be the only types immediately derived from Exception. Furthermore, exceptions from the CLR would be derived from SystemException, and all application-exceptions would be derived from ApplicationException. This way, developers could write a catch block that catches all CLR-exceptions or all application-exceptions.

However, as we can see, this rule was not followed well; some exceptions are immediately derived from Exception (IsolatedStorageException), some CLR-exceptions are derived from ApplicationException (TargetInvocationException), and some application-exceptions are derived from SystemException (FormatException). So it is all a big mess, and the result is that SystemException and ApplicationException have no special meaning at all. At this point, Microsoft would like to remove them from the class hierarchy, but they can't because it would break any code that already references these two types.

## Throwing an Exception

When implementing your own methods, you should throw an exception when the method cannot complete its task as indicated by its name. When you want to throw an exception, there are two issues that you really need to think about and consider.

The first issue is about Exception-derived type you are going to throw. You really want to select a type that is meaningful here. Consider the code that is higher up the stack call and what code might want to determine that a method failed to execute some graceful recovery code. You can use a type that is already defined in the FCL but there may not be one in the FCL that matches your exact. You'll probably need to define your own, ultimately derived from System.Exception.

If you want to define an exception hierarchy, it is highly recommended that the hierarchy be shallow and wide in order to create base classes as possible. The reason is that base classes act as a way of treating lots of errors as one, and this is usually dangerous. Along these lines, you should never throw a System.Exception object, and you should use extreme caution if you throw any other base exception type.³

> **Important** There are versioning ramifications here, too. If you define a new exception type derived from an existing exception type, then all code that catches the base type will now catch your new type as well. In some scenarios, this may be desired and in some scenarios, it may not be desired. The problem is that it really depends on how code catches the base class responds to the exception type and types derived from. Code that never anticipated the new exception may behave unpredictably and open security holes. The person defining the new exception type can't know about all the places where the base exception is caught and how it is handled. And so, in practice, it is impossible to make a good intelligent decision here.

The second issue is about deciding what string message you are going to pass to the exception's constructor. When you throw an exception, you should include a string message with detailed information indicating why the method could not complete its task. If the exception is caught and handled, this string message is not set. However, if the exception becomes an unexpected exception, this message is usually logged.
