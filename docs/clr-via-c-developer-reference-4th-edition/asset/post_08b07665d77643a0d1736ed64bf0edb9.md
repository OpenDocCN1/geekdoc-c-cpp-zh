## Introducing the CLR's Thread Pool

As stated in the previous chapter, creating and destroying a thread is an expensive operation in time. In addition, having lots of threads wastes memory resources and also hurts performance due to the operating system having to schedule and context switch between the runnable threads. To improve this, the CLR contains code to manage its own thread pool. You can think of a thread pool as being a set of threads that are available for your application's use. There is one thread pool per CLR; this thread pool is shared by all AppDomains controlled by that CLR. If multiple CLRs load within a single process, each CLR has its own thread pool.

When the CLR initializes, the thread pool has no threads in. Internally, the thread pool maintains a queue of operation requests. When your application wants to perform an asynchronous operation, you can call some method that adds an entry into the thread pool's queue. The thread pool will extract from this queue and dispatch the entry to a thread pool. If there are no threads in the thread pool, a new thread will be created. Creating a thread has a performance hit associated with it (it as already discussed). However, when a thread pool has completed its task, the thread is not destroyed; instead, the thread is returned to the thread pool, where it sits idle waiting to respond to another request. Because the thread doesn't destroy itself, there is no added performance hit.

If your application makes many requests of the thread pool, the pool may have to serve all of the requests by using just this one. However, if your application is queuing several requests faster than the thread pool can handle them, additional threads will be created. Your application will eventually get to a point at which all of its requests can be handled by a small number of threads, so the thread pool should have no need to create a lot of threads.

If your application stops making requests of the thread pool, the pool may have a lot of threads in it that are doing nothing. This is wasteful of memory resources. When a thread pool has been idle with nothing to do for some period of time (subject to change with different versions of the CLR), the thread wakes itself up and kills itself to free up resources. As the killing is there is a performance hit. However, this probably doesn't matter, because the thread is killing itself because it has been idle, which means that your application isn't performing a lot of work.

The great thing about the thread pool is that it manages the tension between having a few threads, to keep from wasting resources, and taking advantage of multiprocessors, hyperthreaded processors, and multi-core processors. And the thread pool is heuristic. If your application needs to perform many tasks and CPUs are available, the thread pool creates threads. If your application's workload decreases, the thread pool kill themselves.

## Performing a Simple Compute-Bound Operation

To queue an asynchronous compute-bound operation to the thread pool, you typically call one of the methods defined by the ThreadPool class.

```csharp
static Boolean QueueUserWorkItem(WaitCallback callback);
static Boolean QueueUserWorkItem(WaitCallback callback, Object state);
```

These methods queue a "work item" and optional state to the thread pool's queue, and then all of these methods return immediately. A work item is a simple method identified by the callback parameter that will be called by a thread pool. The method can be passed a single parameter specified via the state (the state data) argument. The version of QueueUserWorkItem without the state parameter passes null to the callback method. Eventually, some in the pool will execute your item, calling your method to be called. The callback method you write must match the System.Threading.WaitCallback delegate type,

```csharp
delegate void WaitCallback(Object state);
```

> **Note:** The signatures of the WaitCallback delegate, the TimerCallback delegate (discussed in this chapter "Performing a Periodic Compute-Bound Operation" section), and the ParameterizedThreadStart delegate (discussed in Chapter 26, "Thread Basics") are all identical. If you define a method with this signature, it can be invoked by using ThreadPool.QueueUserWorkItem, by using a System.Threading.Timer object, or by using a System.Threading.Thread object.

The following code demonstrates how to have a thread pool call a method asynchronously:

```csharp
using System;
using System.Threading;
public static class Program {
    public static void Main() {
        Console.WriteLine("Main thread: queuing an asynchronous operation");
        ThreadPool.QueueUserWorkItem(ComputeBoundOp, S);
        Console.WriteLine("Main thread: Doing other work...");
        Thread.Sleep(1000); // Simulating other work (10 seconds)
        Console.WriteLine("Hit <Enter> to end this program...");
        Console.ReadLine();
    }
}
```

```csharp
// This method's signature must match the WaitCallback delegate
private static void ComputeBoundOp(Object state) {
    // This method is executed by a thread pool
    Console.WriteLine("ComputeBoundOp: state={0}", state);
    Thread.Sleep(1000); // Simulates other work (1 second)
    // When this method returns, the thread goes back
    // to the pool
}
```

## Execution Contexts

Every thread has an execution context associated with it. The execution context includes things as security settings. By default, the CLR automatically causes the initiating thread's execution context to flow to helper threads. This takes a fair amount of time because helper threads, more execution context structures have to be created and initialized.

In the System.Threading namespace, there is an ExecutionContext class that allows you to control how a thread's execution context flows from one to another. Here is what the class looks like:

```csharp
public sealed class ExecutionContext : IDisposable, ISerializable {
    [SecurityCritical] static AsyncControl SuppressFlow();
    public static void RestoreFlow();
    public static bool IsSuppressed();
}
```

You can use this to suppress the flowing of execution context, improving your application's performance. The performance gains can be quite substantial for a server application. There is not much benefit for a client application, and the SuppressFlow method is marked with the [SecurityCritical] attribute, making it impossible to call in some client applications (like Silverlight). Of course, you should suppress the flowing of execution context only if the helper thread does not need to access the context information. If the initiating execution context does not flow to a helper thread, the helper thread will use whatever execution context it last with. Therefore, the helper thread shouldn't execute any code that relies on the execution context state (such as a user's identity).

Here is an example of how suppressing the flow of execution context affects data in a thread's logical call context when queuing work item to the CLR's thread pool.

```csharp
public static void Main() {
    // Put some data into the Main thread's logical call context
    CallContext.LogicalGetData("Name", "Jeffrey");

    // Initiate some work to be done by a thread pool thread
    // The thread pool can access the logical call context
    ThreadPool.QueueUserWorkItem(state => {
        state = "0";Console.WriteLine("Name={0}", CallContext.LogicalGetData("Name"));
    });

    // Now, suppress the flowing of the Main thread's execution context
    ExecutionContext.SuppressFlow();
}
```

The items that you add to the logical call context must be serializable, as discussed in Chapter 24, Runtime Serialization." Flowing an execution context that contains logical call data items can hurt performance dramatically, because capturing the execution context requires serializing and deserializing the data items.
