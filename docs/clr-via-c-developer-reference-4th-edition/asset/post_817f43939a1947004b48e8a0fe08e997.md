
Although the C# compiler allows developers to throw Exception-derived objects only, prior to C# 2.0, the C# compiler did allow developers to catch non-CLS-compliant exceptions by using like code this:

```csharp
private void SomeMethod() {
  try {
    // Put code requiring graceful recovery and cleanup operations here...
  } catch (Exception e) {
    // Before C# 2.0, this block catches CLS-compliant exceptions only
    // Now, this block catches CLS-compliant & non-CLS-compliant exceptions
    throw; // Re-throws whatever got caught
  }
  catch {
    // In all versions of C#, this block catches CLS-compliant
    // & non-CLS-compliant exceptions
    throw; // Re-throws whatever got caught
  }
}
```

Now, some developers were aware that the CLR supports CLS-compliant and non-CLS-compliant exceptions, and these developers might have written the preceding two catch blocks in order to catch both kinds of exceptions. If the preceding code is recompiled for CLR 2.0 or later, the second catch block will never execute, and the C# compiler will indicate this by issuing a warning: CS1058: A previous catch clause already catches all exceptions. All non-exceptions thrown will be wrapped in a System.Runtime.Exception.

There are two ways for developers to merge code version from a .NET Framework prior to version 2.0. First, you can merge the code from the two catch blocks into a single catch block and delete one of the catch blocks. This is the recommended approach. Alternatively, you can tell the CLR that the code in your assembly wants to play by the old rules. That is, tell the CLR that {Exception} blocks should not catch an instance of the new RuntimeWrappedException. And instead, the CLR should wrap the non-CLS object and call you only if you have a catch block that doesn't specify any type at all. You tell the CLR that you want the old behavior by applying an instance of the RuntimeCompatibilityAttribute to your assembly like:

```csharp
using System.Runtime.CompilerServices;
[assembly:RuntimeCompatibility(WrapNonExceptionThrows) = false]
```

> Note: This attribute has an assembly-wide impact. There is no way to mix wrapped and unwrapped exceptions in the same assembly. Be careful when adding new code (that expects the CLR to wrap exceptions) to an assembly containing old code (which the CLR didn't wrap exceptions).

# The System.Exception Class

The CLR allows an instance of any type to be thrown for an exception—from an Int32 to a String and beyond. However, Microsoft decided after forcing all programming languages to throw and catch exceptions of any type, they defined the System.Exception type and decreed that all CLS-compliant programming languages must be able to throw and catch exceptions whose type is derived from this type. Exception types that are derived from System.Exception are expected to be CLS-compliant. C# and many other compilers allow your code to throw only CLS-compliant exceptions.

The System.Exception type is a very simple type that contains the properties described in Table 20-1. Usually, you will not write any code to query or access these properties in any way. When your application terminates with an unhandled exception, you will look at these properties in the debugger or in a report that generated and written out to the Windows Event log or crash dump.

TABLE 20-1 Public Properties of the System.Exception Type

| Property | Access | Type | Description |
|---|---|---|---|
| Message | Read-only | String | Contains helpful text indicating why the exception was thrown. It is typically written to a log when an exception is unhandled. Because we cannot see this message, the message should be as technical as possible so that developers viewing the log can use the information to fix the code producing a new version |
| Data | Read-only | IDictionary | A reference to key-value pairs. Usually, the code throwing the exception adds entries to this collection prior to throwing. The catch block can query the entries and uses the information in exception-recovery processing |
| Source | Read/write | String | Contains the name of the assembly that generated the exception |
| StackTrace | Read-only | String | Contains the names of methods called led to the exception being thrown. This property is invaluable for debugging |
| TargetSite | Read-only | MethodBase | Contains the method that threw the exception |
| HelpLink | Read-only | String | Contains a URL (such as file:///C:\MyApp.help#Exception) to help a user understand the exception. Keep in mind that programming and security practices prevent users from ever being able to see raw unhandled exceptions, unless you are trying to convey information to other programmers, this property is seldom used |
| InnerException | Read-only | Exception | Indicates the previous exception if the current exception was raised while handling an exception. This read-only property is usually null. The Exception type also offers a public GetBaseException method that traverses the linked list of inner exceptions and returns the originally exception. |
| HResult | Read/write | Int32 | A 32-bit value that is used when crossing managed and native boundaries. For example, when COM APIs return HRESULT values, the CLR throws an Exception-derived object and maintains the HRESULT value in this property. |

I'd like to say a few words about System.Exception's read-only StackTrace property. A catch block read this property to obtain the stack trace indicating what methods were called up to the exception. This information can be extremely valuable when you're trying to detect the cause of an exception so that you can correct it. Actually calling it in the CLR; the property doesn't return a string. When you construct a new object of an Exception-derived type, the StackTrace property is initialized to null. If you were to read the property, you wouldn't get a stack trace, you would get null.

When an exception is thrown, the CLR internally records where the throw instruction occurred. When a catch block accepts the exception, the CLR records where the exception was caught. If, inside a catch block, you now access the exception object's StackTrace property, the code that implements property calls into the CLR, which builds a string identifying all of the methods between the place where the exception was thrown and the filter that caught the exception.

> **Important** When you throw an exception, the CLR resets the starting point for the exception; that is, the CLR remembers only the location where the most recent exception object was thrown.

The following code throws the same exception that it caught and causes the CLR to reset its starting point for the exception.

```csharp
private void SomeMethod() {
    try { ... }
    catch (Exception e) {
        throw e; // CLR thinks this is where exception originated.
        // Fxcop reports this as an error
    }
}
```

In contrast, if you re-throw an exception object using the throw keyword itself, the CLR doesn't reset its starting point.

```csharp
private void SomeMethod() {
  try { ... }
  catch (Exception e) {
    throw; // This has no effect on where the CLR thinks is
    // original. Fxcop NOT report this as an error
  }
}
```

In fact, the only difference between these two fragments is what the CLR thinks is the original location where the exception was thrown. Unfortunately, when you throw or re-throw an exception, Windows resets the stack's starting point. If so the exception unhandled, the stack location that reports to Windows Error Reporting is the location of the last throw or re-throw. This is unfortunate because it makes debugging applications that failed in the field much more difficult. Some developers have found this so intolerable that they have chosen a different way to implement their code to ensure that the stack trace reflects the location where an exception was thrown.

```csharp
private void SomeMethod() {
  Boolean trySucceeds = false;
  try {
    ...
    trySucceeds = true;
  }
  finally {
    if (trySucceeds) { /* catch code goes in here */ }
  }
}
```

The string returned from the StackTrace property doesn't include any of the methods in the call stack that are above the point where the catch block accepted the exception object. If you want the complete stack trace from the start of the thread up to the exception handler, you can use the System.Diagnostics.StackTrace. This type defines some properties and methods that allow a developer to programmatically manipulate a stack trace and the frames that make up the stack trace.

You can construct a StackTrace object using several different constructors. Some constructors build the frames from the start of the thread to the point where the StackTrace object is constructed. Other constructors initialize the frames of the StackTrace object by using an Exception-derived object as an argument.

If the CLR can find debug symbols (located in the .pdb files) for your assemblies, the string returned by System.Exception's StackTrace property or System.Diagnostics.StackTrace's ToString method will include source code file and line numbers. This information is incredibly useful for debugging.
