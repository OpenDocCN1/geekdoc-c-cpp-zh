
# How Windows does Asynchronous I/O

**FIGURE 28-2** How Windows performs an asynchronous I/O operation.

When the hardware device completes processing the IRP (a), it will queue the completed IRP into the CLR's thread pool (b). In the future, a thread pool will extract the completed IRP and execute code that completes the task by setting an exception (if an error occurred) or the result (in this case, an Int32 indicating the number of bytes successfully read) (c).¹ So the Task object knows when the operation completes and, in turn, lets your code run so it can safely access the data inside the Byte[].

Now that you understand the basics, let's put it all into perspective. Let's say a client request comes in, and our server makes an asynchronous database request. As a result, our thread won't block, and it will be allowed to return to the thread pool so that it can handle more incoming requests. So we have one thread handling all incoming requests. When the database server responds, it is queued into the thread pool and our thread will just process it at some point and ultimately send the necessary data back to the client. At this point, we have just one thread processing all client requests and all database responses. Our server is using very few system resources and it is still running as fast as it can, especially because there are no context switches!

If items appear in the thread pool quicker than our thread can process them all, then the thread pool might create additional threads. The thread pool will quickly create one thread per CPU on the machine.

> ¹ Completed IRPs are extracted from the thread pool using a first-in-first-out (FIFO) algorithm.

So, on a quad-processor machine, four client requests/database responses (in any combination) are running on four threads without context switching.

However, if any of these threads voluntarily block (by invoking a synchronous I/O operation, calling Thread.sleep or waiting to acquire a thread synchronization lock), Windows notifies the thread pool that one of its threads has stopped. The thread pool now realizes that the CPUs are undersaturated and creates a new thread to replace the blocked thread. Of course, this is not ideal because creating a new thread is very expensive in terms of time and memory.

What's worse that the blocked thread might wake up and now the CPUs are oversaturated again and context switching occurs, decreasing performance. However, the thread pool is smart here. As threads complete their processing and return to the pool, the thread pool won't let new work items units until the CPUs exactly saturated, thereby reducing context switches and improving performance. And if the thread pool later determines that it has more threads than it needs, it lets the extras kill themselves, reclaiming the resources that they were using.

Internally, the CLR's thread pool uses a Windows resource called an I/O Completion Port to permit the behavior that I've described. The CLR creates an I/O Completion Port when it initializes, as you open hardware devices, these devices can be bound to the I/O Completion Port so that drivers know where to queue the completed IRPs. If you want to understand more about this mechanism, I recommend the book, Windows via C/C++, Fifth Edition, by Michel and Christophe Nasser (Microsoft Press, 2007).

In addition to minimal usage and reduced context switches, we get many benefits when performing I/O operations asynchronously. Whenever a garbage collection starts, the CLR must suspend all the threads in the process. The further the threads are, the faster the garbage collector runs. In addition, when a garbage collection occurs, the CLR must wait all the threads' stacks looking for roots. And, the further threads there are, the fewer stacks there are, and this also makes the garbage collection faster. But, in addition, if our threads do not block while processing work items, the threads tend to spend more of their waiting in the thread pool. When a garbage collection occurs, the threads are at the top of their stack, and walking each thread's stack for roots takes very little.

Also, when you debug an application, Windows suspends all threads in the debugger when you hit a breakpoint. Then, when you continue executing the debugger, Windows has to resume all its threads, so if you have a lot of threads in an application, single-stepping through the code in a debugger can be excruciating. Using asynchronous I/O allows you to have a few threads, improving your debugging.

And, if CPU usage is at 100 percent due to threads lower than priority 8, your application will not have its responsiveness and performance impacted by your application's thread will pre-empt the priority threads. And, here's another benefit: let's say your application waits to download 10 images from various websites, and it takes 5 seconds to download each image. If you perform this work synchronously (downloading one image after another), then it takes 50 seconds to get the 10 images. However, if you use just one thread to initiate 10 asynchronous operations, then all 10 are performed concurrently and all 10 images will come back in 5 seconds! That is, when performing synchronous I/O operations, the time it takes to get all the results is the sum of the times required for each result. However, when performing multiple asynchronous I/O operations, the time it takes to get all the results is the time required to get the slowest-performing operation.

For GUI applications, asynchronous operations offer another advantage: the user interface doesn remains responsive to the end user. In fact, if you are building a Microsoft Silverlight or Windows Store application, you must perform all I/O operations asynchronously, because the class libraries available for performing I/O operations only expose these operations asynchronously; the equivalent synchronous methods do not exist in the library. This was done purposely ensuring that these applications can never issue a synchronous I/O operation, thereby blocking the GUI while making the application unresponsive to the end user. This forces developers to build responsive applications providing users a better experience.

# C#'s Asynchronous Functions

Performing asynchronous operations is the key to building scalable and responsive applications that allow you to use very few threads to execute lots of operations. And when coupled with the thread pool, asynchronous operations allow you to take advantage of all the CPUs that are in the machine. Realizing the potential here, Microsoft designed a programming model that would make it easy for developers to take advantage of this capability. This pattern leverages Tasks (as discussed in Chapter 27, "Compute-Bound Asynchronous Operations") and a C# language feature called async-functions (or async functions, for short). Here is an example of code that uses an async function to issue two asynchronous I/O operations.

```csharp
private static async Task<String> IssueClientRequestAsync(String serverName, String message) {
    using (var pipe = new NamedPipeStream(serverName, "PipeName", PipeDirection.InOut, PipeOptions.Asynchronous) | Options.WriteThrough()) {

        pipe.Connect(); // Connect before setting ReadMode
        pipe.ReadMode = PipeTransmissionMode.Message;

        // Asynchronously send data to the server
        Byte[] request = Encoding.UTF8.GetBytes(message);
        await pipe.WriteAsync(request, 0, request.Length);
    }
}
```
