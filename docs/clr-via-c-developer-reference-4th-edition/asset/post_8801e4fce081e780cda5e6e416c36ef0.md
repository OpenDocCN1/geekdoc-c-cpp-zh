
The second thing to notice about SafeHandle is that the class is abstract; it is expected that another class will be derived from SafeHandle, and this class will provide a constructor that invokes the protected constructor, the abstract method ReleaseHandle, and the abstract IsInvalid property accessor method.

Most resources are manipulated with handles (32-bit values on a 32-bit system and 64-bit values on a 64-bit system). So the SafeHandle class defines a IntPtr called handle. In Windows, most handles are invalid if they have a value of 0 or -1. The Microsoft.Win32.Handle namespace contains another helper class SafeHandleZeroOrMinusOneInvalid, which looks like this.

```csharp
public abstract SafeHandleZeroOrMinusOneInvalid : SafeHandle {
    protected SafeHandleZeroOrMinusOneInvalid(Boolean ownsHandle)
        : base(IntPtr.Zero, ownsHandle) {
```

```csharp
public override bool IsInvalid {
    get {
        if (base.handle == IntPtr.Zero) return true;
        if (base.handle == (IntPtr)(-1)) return true;
        return false;
    }
}
```

Again, you'll notice that the SafeHandleZeroOrMinusOneInvalid class is abstract, and therefore, another class must be derived from this to override the protected constructor and the abstract method ReleaseHandle. The .NET Framework provides a few public classes derived from SafeHandleZeroOrMinusOneInvalid, including SafeFileHandle, SafeRegistryHandle, SafeWaitHandle, and SafeMemoryMappedViewHandle. Here is what the SafeFile class looks like.

```csharp
public class SafeFileHandle : SafeHandleZeroOrMinusOneInvalid {
    public SafeFileHandle(IntPtr preexistingHandle, Boolean ownsHandle)
        : base(ownsHandle) {
        base.SetHandle(preexistingHandle);
    }
}
```

```csharp
protected override bool ReleaseHandle() {
    // Tell Windows that we want the native resource closed.
    return Win32Native.CloseHandle(base.handle);
}
```

The SafeWaitHandle class is implemented similarly to the SafeFile class just shown. The only reason why there are different classes with similar implementations is to achieve type safety; the compiler won't let you use a file handle as an argument to a method that expects a wait handle, and vice versa. The SafeRegistryHandle class's ReleaseHandle method calls the Win32 RegCloseKey function.

It would be nice if .NET Framework included additional classes that wrap native resources. For example, one could imagine classes as SafeProcessHandle, SafeThreadHandle, SafeTokenHandle, SafeLibraryHandle(it ReleaseHandle would call the Win32 Free function), SafeLocalAlloc(it ReleaseHandle would call the Win32 LocalFree function), and so on.

All of the classes used (just mentioned) interact with the Framework Class Library (FCL). However, these classes are not publicly exposed; they are internal to the assemblies that define them. Microsoft didn't expose these classes publicly because they didn't want to document them and do full testing of them. If you need any of these classes for your work, I recommend you use a tool such as ILDisasm or some IL decompiler to extract the code for these classes and integrate them into your project's source code. All of these classes are trivial to implement, and writing them from scratch would be quite easy.

The SafeHandle-derived classes are extremely useful because they ensure that the native resource is freed when a GC occurs. In addition to what we've already discussed, SafeHandle offers two capabilities. First, the CLR gives SafeHandle-derived types special treatment when used in scenarios in which you are operating with native code. For example, let's examine the following code:

```csharp
using System;
using System.Runtime;
using Microsoft.Win32.SafeHandles;

internal static class SomeType {
    [DllImport("kernel32", CharSet=CharSet.Unicode, EntryPoint="CreateEvent")]
    // This prototype is not robust
    private static extern IntPtr CreateEventBad(
    IntPtr pSecurityAttributes, Boolean initialState, String name);

    // This prototype is robust
    [DllImport("kernel32", CharSet=CharSet.Unicode, EntryPoint="CreateEvent")]
    private static extern SafeWaitHandle CreateEventGood(
    IntPtr pSecurityAttributes, Boolean initialState, String name);

    public static void SomeMethod() {
        IntPtr handle = CreateEventBad(IntPtr.Zero, false, null);
        SafeWaitHandle swh = CreateEventGood(IntPtr.Zero, false, null);
    }
}
```

You'll notice that the CreateEvent method is prototyped returning an IntPtr, which will return the handle back to managed code; however, interoperating with native code is not robust. You see, after CreateEventBad is called (which creates the native resource), it is possible that a ThreadAbortException could be thrown to the handle being assigned to the handle variable. In the rare case this happens, the managed code would leak the native resource. The only way to get the event closed is to terminate the process.

The SafeHandle class fixes this potential resource leak. Notice that the CreateEventGood method is prototyped as a SafeHandle(of an IntPtr). When CreateEventGood is called, the CLR calls the Win32 CreateEvent function. When the CreateEvent returns to managed code, the CLR knows that SafeHandle is derived from SafeHandle, the CLR to automatically construct an instance of the SafeHandle class on the managed heap, passing the value returned from CreateEvent. The constructing of the SafeHandle object and the management of the handle in native code, which cannot be interrupted by a ThreadAbortException. Now, it is impossible for managed code to leak this resource. Eventually, the SafeHandle object will be garbage collected and its Finalizer method will be called, ensuring that the resource is released.

One feature of SafeHandle-derived classes is that they prevent someone from trying to exploit a potential security hole. The problem is that one thread could be using a native resource while another thread tries to free it. This could manifest itself as a handle-recycling error. The SafeHandle class prevents this vulnerability by using reference counting. The SafeHandle class defines a field that maintains a counter. When SafeHandle is set to a valid handle, the counter is set to 1. Whenever a SafeHandle-derived object is passed as an argument to a native method, the CLR automatically increments the counter. Likewise, as the native method returns to managed code, the CLR decrements the counter. For example, you would prototype the Win32 SetEvent function as

```csharp
[DllImport("Kernel32", Exactelling=true)]
private static extern Boolean SetEvent(SafeHandle handle);
```

Now when you call this method passing in a reference to a SafeHandle object, the CLR increment the counter just before call and decrement the counter just after call. Of course, the manipulation of the counter is performed in a thread-safe fashion. Does this improve security? Well, if another thread tries to release the native resource by the SafeHandle object, the CLR knows it cannot actually release it because the resource is being used by a native function. When the native function returns, the counter is decremented to 0, and the resource is released.

If you are writing or calling code to manipulate a handle as an IntPtr, you can access it out of SafeHandle, but you should manipulate the reference counting explicitly. You accomplish this via SafeHandle's DangerousAddRef and DangerousRelease methods. You gain access to the handle via the DangerousGetHandle method.

I would remember if I didn't mention that the System.Runtime.Interop namespace also defines a CriticalHandle class. This class works exactly as the SafeHandle class in all ways except that it does not offer the reference-counting feature. The CriticalHandle class and the classes derived from its service class for better performance when you use it (because counters don't get managed). As SafeHandle, the CriticalHandle class has two types derived from: CriticalHandleMinusOneIsInvalid and CriticalHandleZeroMinusOneIsInvalid. Microsoft forms a more secure system over a faster system, the class library contains no types derived from either of these two classes. For your work, I would recommend that you use CriticalHandle-derived types only if performance is an issue. If you justify reducing security, you can switch to a CriticalHandle-derived type.
