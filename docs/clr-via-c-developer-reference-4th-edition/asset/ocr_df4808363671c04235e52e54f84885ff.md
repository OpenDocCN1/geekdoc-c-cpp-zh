And, the CLR itself does all kinds of great things for developers to make our lives even easier. For example, the CLR implicitly:

+   - Invokes virtual methods and interface methods.

+   - Loads assemblies and JIT-compiles methods that can potentially throw FileLoadException, BadImageFormatException, InvalidProgramException, FieldAccessException, MethodAccessException, MissingFieldException, MissingMethodException, and VerificationException.

+   - Transitions across AppDomain boundaries when accessing an object of a MarshalByObject-derived type which can potentially throw AppDomainUnloadedException.

+   - Serializes and deserializes objects when crossing an AppDomain boundary.

+   - Causes thread(s) to throw a ThreadAbortException when Thread.AppDomain.Unload is called.

+   - Invokes Finalize after a garbage collection before objects that have their memory reclaimed.

+   - Creates type objects in the loader heap when using generic types.

+   - Invokes a type's static constructor throwing of TypeInitializationException.

+   - Throws various exceptions, including OutOfMemoryException, DivideByZeroException, NullReferenceException, RuntimeWrappedException, TargetInvocationException, OverflowException, NotFiniteNumberException, ArrayTypeMismatchException, DataMisalignedException, IndexOutOfRangeException, InvalidCastException, RankException, SecurityException, and more.

And, the .NET Framework ships with a massive class library that contains tens of types, each encapsulating common, reusable functionality. There are types for building web applications, web services, ri GUI applications, working with security, manipulation of images, search recognition, and the list goes on. Any of this code could throw an exception, indicating failure. Future versions could introduce new exception types derived from existing exception types and your catch blocks catch exceptions that never existed before.

All of this stuff—object-oriented programming, compiler features, CLR features, and the enormous class library—what makes the .NET Framework such a compelling software platform.4 My point is that all of this stuff introduces failure into your code, which you have little control. As long as everything is working, great is all; we write easily, the code is easy to read and maintain. But, when something goes wrong, it is nearly impossible to fully understand what went wrong and why.
