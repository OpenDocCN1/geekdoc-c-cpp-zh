**Under most circumstances, you should avoid calling any of the Collect methods;** it's best just to let the garbage collector run on its own account and fine-tune its generations based on actual application behavior. However, if you are writing a user interface (UI) or GUI application, your application codes the process and GC in that process. For these application types, *you might* suggest a garbage collection to occur at certain times using a GCCollectionMode of Optimized. Normal modes of Default and Forced are used for debugging, and looking for memory leaks.

For example, you might consider calling the Collect method if some non-recurring event has occurred that has caused a lot of objects to die. The reason that calling Collect in a circumstance may not be so bad is the GC's predictions of the future based on the past are not likely to be accurate for non-recurring events. For example, it might make sense for your application to force a full GC of all generations after you initializes or after the user saves a data file. Because *Collect* causes the generation budgets to adjust, do not call Collect to try to improve your application's response time; call to reduce your working set.

For some applications (especially servers that tend to keep a lot of objects in memory), the time required for the GC to do a full collection that includes generation 2 can be excessive. If, the collection takes a very long time, clients request more time out. To help these kinds of applications, the GC class offers a RegisterFullGCNotification method. Using this method and another helper methods (WaitForFullGCApproach, WaitForFullGCComplete, and CancelFullGCNotification), an application can be notified when the garbage collector is getting close to performing a full collection. The application can then call.Collect to force a collection at a more opportune time, or the application could communicate with another server to better load the client requests. For more information, examine these methods and the "Garbage Collection Notifications" in the Microsoft .NET SDK documentation. Note that you should always call the WaitForFullGCApproach and WaitForFullGCComplete methods in pairs because the CLR handles them as pairs internally.

# Monitoring Your Application's Memory Usage

Within a process, there are a few methods that you can call to monitor the garbage collector. Specifically, the GC class offers the static methods, which you can call to see how many collections have occurred of a specific generation or how much memory is currently being used by objects in the managed heap.

```
Int32 CollectionCount(Int32 generation);
Int64 GetTotalMemory(Boolean forceFullCollection);
```

At this point, you should have a basic understanding of garbage collection and the managed heap, including how the collector reclaims an object’s memory. Fortunately for us, most types need only memory. However, some types require more than just memory to be useful; some types require the use of a native resource.

The System.IO.FileStream type, for example, needs to open a file (a native resource) and store its handle. The Read and Write methods use this to manipulate the file. Similarly, the System.Threading.Mutex type opens a Windows kernel object (a native resource) and stores it, using it when the Mutex’s methods are called.

# Working with Types Requiring Special Cleanup

This is called finalization. All types that wrap a native resource—such as a file, network connection, socket, or mutex—support finalization. When the CLR determines that one of these is no longer reachable, the GC gets itself finalized, releasing the native resource it wraps, and then, the GC will reclaim the object from the managed heap.

System.Object, the base of everything, defines a protected and virtual method Finalize. When the garbage collector determines that an object is garbage, it calls the object’s Finalize (if it is overridden). Microsoft’s C# team felt Finalize methods were a special kind of method requiring special syntax in the programming language (similar to how C# requires special syntax to define a constructor). So, in C#, you must define a Finalize method by placing a tilde~) in front of the class name, as shown in the following code sample.

```
internal sealed class SomeType {
  ~SomeType() {
    // The code is inside the Finalize method
  }
}
```
