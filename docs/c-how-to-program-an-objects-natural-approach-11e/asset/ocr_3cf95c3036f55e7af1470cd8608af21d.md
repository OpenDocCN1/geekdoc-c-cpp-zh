# 18.5 Launching Tasks with concurrencpp

Before we use **concurrencpp** to implement a coroutine, let’s use it to schedule tasks that execute in separate threads. As with standard library threads, each task executes a function, a lambda or a function object. Figure 18.2 uses four **concurrencpp** components:

+   - A **concurrencpp::runtime** manages your **concurrencpp** interactions. It provides access to various executors for scheduling tasks. It also ensures that the executors shut down scheduled tasks properly when the **runtime** is destroyed. You must create a local **runtime** object, typically at the beginning of `main` (line 35). When `main` ends, the local **runtime** object goes out of scope. Its destructor shuts down the executors and any remaining scheduled tasks that have not finished executing.
+   - A **concurrencpp::thread_pool_executor** (one of several executor types) schedules tasks to execute. It creates and manages a group of threads called a **thread pool** and assigns tasks to the pool’s threads to execute. This executor can reuse existing threads in the pool to eliminate the overhead of creating a new thread for each task. It also can optimize the number of threads to ensure the processor stays busy without creating so many threads that the application runs out of resources. Standard executors are expected in C++23 or C++26, but libraries like **concurrencpp**, **libunifex** and **folly::coro** offer them now.
+   - A **concurrencpp::task** represents a task to execute. **concurrencpp** executors create these when you schedule tasks.
+   - A **concurrencpp::result** enables you to access a concurrent task’s result or simply wait for the task to complete execution if it does not return a value. When you schedule a **concurrencpp::task**, you receive a **concurrencpp::result**.
