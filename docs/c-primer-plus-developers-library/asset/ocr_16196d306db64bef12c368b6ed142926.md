```
Stonewt jennySt(9, 12);
Stonewt bennySt(12, 8);
Stonewt total;
total = jennySt + bennySt;
```

Also given the Stonewt (double) constructor, each form lets you do the following:

```
Stonewt jennySt(9, 12);
double bennyD = 176.0;
Stonewt total;
total = jennySt + bennyD;
```

But only the friend function lets you do this:

```
Stonewt jennySt(9, 12);
double bennyD = 146.0;
Stonewt total;
total = pennyD + jennySt;
```

To see why, you can translate each addition into the corresponding function calls. First,

```
total = jennySt + bennySt;
```

becomes

```
total = jennySt.operator+(bennySt);   // member function
```

or else

```
total = operator+(jennySt, bennySt);  // friend function
```

In either case, the actual argument types match the formal arguments. Also the member function is invoked, as required, by a Stonewt object.

Next,

```
total = jennySt + bennyD;
```

becomes

```
total = jennySt.operator+(bennyD);   // member function
```

or else

```
total = operator+(jennySt, bennyD);  // friend function
```

Again, the member function is invoked, as required, by a Stonewt object. This time, in each case, one argument (bennyD) is type double, which invokes the Stonewt (double) constructor to convert the argument to a Stonewt object.

By the way, having an operator double() member function defined would create confusion at this point because that would create another option for interpretation. Instead of converting bennyD to double and performing Stonewt addition, the compiler could convert jennySt to double and perform double addition. Having too many conversion functions creates ambiguities.
