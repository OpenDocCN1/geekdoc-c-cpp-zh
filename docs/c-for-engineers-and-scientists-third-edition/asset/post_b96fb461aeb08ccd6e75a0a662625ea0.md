# Phase I: Development and Design

Phase 1 begins with a statement of a problem or a specific request for a program, which is referred to as a program requirement. After a problem has been stated or a specific request for a program solution has been made, the development and design phase begins. This phase consists of four well-defined steps, as illustrated in Figure 1.2.

# Preliminaries

## Step 1 Analyze the Problem

The analysis of a problem can consist of up to two parts. The first part is a basic analysis that must be performed on all problems; it consists of extracting the complete input and output supplied by the problems. For this analysis, you must:

- Determine and understand the output items the program must produce.
- Determine the input items.

Together, these two items are referred to as the problem's input/output (I/O). Only after determining a problem's I/O can you select specific methods for transforming inputs into outputs. By doing a hand calculation to verify that the output(s) can be obtained from the inputs is sometimes necessary and/or useful. Clearly, if you have a formula that relates to inputs, you can omit this step. If the required inputs are available and the desired outputs can be produced, the problem is to be clearly defined and solved.

For a variety of reasons, completing a basic analysis might not be possible. If so, an extended analysis might be necessary. An extended analysis simply means you gather more information about the problem so that you thoroughly understand what is being asked for and how to achieve the result. In this book, any additional information required to understand the problem is supplied along with the problem.

## Step 2 Develop a Solution

In this step, you select the exact set of steps, called an "algorithm," to solve the problem. Typically, you find the solution by a series of refinements, starting with the initial solution you find in the analysis step, until you have an acceptable and complete solution. This solution must be checked, if it's not done in the analysis step, to make sure it produces the required outputs correctly. The check is usually carried out by doing one or more calculations that haven't been done.

For small programs, the selected solution might be extremely simple and consist of one or more calculations. Typically, you need to refine the initial solution and organize it into smaller subsystems, with specifications for the subsystems interface each other. To achieve this, the goal's description starts from the highest level (top) requirement and proceeds towards the parts that must be constructed to meet this requirement. To make this explanation more meaningful, a comprehensive program must track the number of items in inventory. The required output for a program is a description of all parts in inventory and the inventory of each item in stock; the given inputs are the initial quantity of each part, the number of items sold, the number of items returned, and the number of items purchased.

For these specifications, a designer could initially organize the program's requirements into the three sections illustrated in Figure 1.3. This figure is referred to as both a top-level structure diagram and a first-level decomposition because it represents the overall structure of the program the designer has selected.

After an initial structure is developed, it is refined until the tasks in the boxes are completely defined. For example, the data entry and report modules shown in Figure 1.3 would be refined further. Because planning for contingencies and human error is the system designer's responsibility, provisions must also be made for changing incorrect data after an entry is made and for deleting previous entries. ## Step 3 Code the Solution (Write the Program)

This step consists of actually writing a C++ program that corresponds to the solution developed in Step 2. If the analysis and solution steps have been performed correctly, the coding step becomes mechanical in nature. In a well-defined program, the statements making up the program, however, conform to certain well-defined patterns or structures that have been defined in the solution step. These structures control how the program executes and consist of the following types:

- Sequence
- Selection
- Iteration
- Invocation

# Preliminaries

Sequence defines the order in which the program executes instructions. Specifying which instruction comes first, and which second, is essential if the program is to achieve a well-defined purpose.

Selection provides the capability to make a choice between different operations, depending on the result of some condition. For example, the value of a number can be checked before a division is performed: if the number is not zero, it can be used as the denominator of a division; otherwise, the division isn't performed and the user is given a warning message.

Iteration, also referred to as "looping" and "repetition", for example, grades may be entered and added repeatedly based on a value of a condition. If a negative grade is entered, the entry of a negative grade is the condition that significant addition will stop and addition of grades. At that point, an average for all grades could be calculated.

Invocation involves invoking, or summoning, a set of statements as executed. For example, computing a person's net pay involves the tasks of obtaining pay and hours worked, calculating the net pay, and providing a report. Each task is typically coded as a separate unit that is called, or invoked, as needed.

## Step 4 Test and Correct the Program

The purpose of testing is to verify that a program works correctly and fulfills its requirements. In computer terminology, a program error is called a bug. In practice, finding all errors would require checking all possible combinations of statement execution. The time and effort required, this is usually impossible, except for extremely simple programs (Section 4.8 explains why this is generally considered impossible).

Exhaustive testing isn't feasible for most programs, different philosophies and methods of testing have evolved, however requires conscious effort to make sure a program works correctly and produces meaningful results. This effort means giving thought to what the test is to achieve and the data used in it. If testing reveals an error (bug), the process of debugging, which includes locating, correcting, and verifying the correction, can be initiated. Although the fact that a test failed might reveal the presence of an error, it doesn't necessarily indicate the absence of one, for that a test revealed does not indicate that one isn't elsewhere in the program.

To catch and correct errors in a program, developing a set of test for determining whether the program gives correct results is important. In fact, often an accepted step in formal software development is to plan test procedures and create meaningful test before writing the code. This doing step helps you be more objective about what the program must do because of the subconscious temptation after coding to avoid test that would reveal a problem with your program. The procedures for testing a program should examine every possible situation in which the program will be used.
