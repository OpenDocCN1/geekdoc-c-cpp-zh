# Correctness of graph-based Slicing

Horwitz et al. [HPR88] showed that PDGs (for a language including arrays) are adequate for representing a program's execution behavior: if the PDGs of two programs are isomorphic, then for a given input either both programs diverge, or terminate with the same values for all variables. Backward intraprocedural slicing based on the PDG for a simple while language has been proved correct in [RY88]. Their Slice Theorem proves that for any initial state on which the program terminates, the program and its slice compute the same sequence of values for each element of the slice. This result was extended to the SDG by Brinkley et al. [BHR89] and to programs with heap-allocated storage (based on a LISP-style control operator) and pointers [PS91], in the spirit of [HPR89]. It is well-known that such an operator is sufficient to model complex heaps and even Java-like objects. Our extension of SDGs in section 2.5 is presented together with a correctness argument for interprocedural data dependencies parameter passing. Syntax-preserving slicing in the presence of unstructured control flow has been solved independently by Ball and Horwitz [BH93] and Choi and Ferrate [CF94]. Both solutions include a correctness proof. Harman and Danihani [HD98] extend the solution of Agrawal [Agr94] and present a correctness proof.

## 2.3 Points-to-Analysis

Points-to analysis is a major prerequisite for analyzing heap-manipulating programming languages. For an object-oriented language, it answers the question which objects a given pointer or reference may point to at runtime.

| 1 Object o1; | |
| :--- | :--- |
| 2 String o2; | |
| 3 o1 = new Object(); | o2 → new Object() |
| 4 o2 = new String(); | |
| 5 if (...) | | |
| 6 o1 = o2; | new String() → new Object() |

Figure 2.7: Code fragment and possible points-to-graphs

Based on this analysis one can derive related relations, like may-using, i.e. whether two variables refer to the same location in memory – thus the same object, and under certain conditions also must-using, i.e. if two variables always point to the same object.

Since the base techniques were presented by Andersen [And94] and Steensgaard [Ste96], hundreds of papers have targeted this issue (e.g. [SS00b, RMR01, LLS01, MRG02, NRO03, LL03, WL04, LH08]) and thereby refined the technique such that today, points-to analysis scales well for realistic programming languages and programs. However, even though points-to analysis seen around [Hin01] years ago, there are still papers at major conferences on that topic improve precision and scalability issues.

Points-to analysis is usually solved by constraint based program analysis: From the control flow graph a number of constraints is extracted that must hold due to the program semantics. These constraints can be solved and yield a conservative solution for the points-to relation. The constraint system is traditionally represented as a graph, where- there is one node for each pointer own- one node for each allocation site
- an edge p → q exists if p may point to q
- an edge p → q exists if p must point to q

As an example, consider Figure 2.7, where program fragment is depicted together with points-to graphs. There are nodes for each variable o1 and o2. The assignment in line 3 and 4 yield edges between the variables. The assignment in line 6 creates another edge.

## 2.3.1 Inclusion-Based vs. Unification-Based Analysis

Two fundamental approaches in determining points-to have been presented: Stegaard [Ste96] proposed a unification-based approach, pointers are either aliased or point to the same set of objects. Its advantage is the near-linear complexity of $O(n\alpha(n))$ where $\alpha$ is inverse Ackermann function, based on the Leis-Tarjan algorithm [LT79]. In the example of Figure 2.7, the rightmost graph corresponds to Steards. Since unification means that the points-to of o1 equals one of o2, the edge connecting nodes in both directions. Unfortunately, applying this to Java yields several undesirable properties. Streckbench [SS00b] has found that strangely typed languages like Java lose type safety with unification-based approaches, which can be seen in Figure 2.8, where a reference of type String is determined to possibly point to a declared type Object. This dramatic implications on the approximation of dynamic binding, where the called method depends on the target object: When char() is called on o2 the analysis cannot determine which method in java.lang.Object the of. Because it lacks typing information, it is now unclear, the analysis contains a bug, or is simply due to over-approximation. This led to years of research for scalability in the inclusion-based approach.

Andersen's points-to inclusion-based inserts only uni-directed edges between pointers of an assignment. This approach will only generate constraints that obey type-safety, which corresponds more thinly to an assignment's semantics, as be in Figure 2.7. Here, only o1 might point to o2 but not versa. The points-to relations become more precise than the unification-based approach (see left graph in Figure 2.8). However, the cost of solving the constraint system is in $O(n^3)$ where $n$ is the number of statements in the program. Despite this inclusion-based analyses have become predominant in the last years, due to advances in runtime BDDs from recent research e.g. by using better data structures [WL04, LH08].
