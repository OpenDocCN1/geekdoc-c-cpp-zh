For determining interference, it is crucial to know if more than one instance of a given thread may execute in parallel, as in this case different instances of this thread class could collide. If only a single instance of a given thread class will be created or executed, no interference between two instances of this thread and another class is possible. For a specific case this can be easily determined: The thread executing the main method is a singleton, its class does not extend or implement Runnable; however, in general determining that may only be created once in a program's execution is undecidable. Similar to must-aliasing described in section 2.3.3, if a Thread allocation statement is not contained in a cycle of the interprocedural control flow graph, then we know that a's equivalence class represents a singleton set, if there is no other allocation site of a' type, we know that there cannot be interference from a to another instance of a. A similar idea was presented in [RI04], where the different sets of thread allocations are determined not to have thread-local data escaping.

To get a graph which is most similar to the sequential SDG-variances, many approaches [KR03b, Za99, XR06] propose to build one dependence graph for each execution and connect those with inter-dependencies. This may reduce the number of spurious interference dependence edges, in a highly dynamic language, where (at theoretically) an unbounded number of threads can be started during program execution, this approach is no longer feasible. Another reason against this approach is that class libraries like Java's are so large that one needs to share their dependence graphs.
