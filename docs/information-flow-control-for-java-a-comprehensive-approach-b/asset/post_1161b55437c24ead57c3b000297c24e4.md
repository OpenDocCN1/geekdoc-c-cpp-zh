
## 2.3. POINTS-TO-ANALYSIS

### 2.3.2 Inter-procedural Analysis and Dynamic Dispatch

For inter-procedural analysis, the predominant implementation technique is graph cloning, i.e. one adds a points-to-graph for each procedure in each context. A method is the traditional calling context as [WL04]. Alternatively, for object-oriented languages the target of virtual method calls has been found effective as context [MRR02], which has been termed object-sensitive pointer analysis. Using calling for contexts is problematic in that it requires conservative approximations in recursion and often a computed call graph is needed, which hinders the fly computation. Therefore, using target objects as contexts is while more conservative for some cases practical, as no call graph is needed for computation and contexts not constructed in a complicated manner. Still, it has been efficient for many typical problems, like factory methods or containers, which context-insensitive analysis remains in too conservative way.

Object-oriented languages like Java need points-to analysis, with the drawbacks that an additional analysis needs to be done in advance and that generated call graphs are typically relatively impressive. Alternatively, the call graph may be computed on the fly during points-to analysis. While this makes points-to considerably more complex, the generated call graph is accurate as the analysis itself, typically much precise than simple algorithms like class hierarchy (CHA) [DGC95] or more refined analyses like 0-CFA [GDC97], VTA [SHR00], Rapid Type Analysis (RTA) [BS96] and the CFA algorithm [TPU0].

The algorithm to conservatively approximate dynamic binding on-the-fly during points-to analysis consists of [HBCC99, SS0b]:

- Construct the initial points-to relations from assignments and statically dispatched method calls.
- Propagate the points-to relations along the graph edges.
- For each virtual call o(x1, ..., xn), determine the points-to(o) = {o1, ..., ok} in the current graph.
- Use static lookup to determine the call target $f_i$ of method $f_i(x1, ..., xn)$ and insert an edge from the call to its target $f_i$ in the call graph.
- Connect the parameters and return value of the call to those of $f_i$ in the points-to graph, but only add an edge between the this-pointer of $f_i$ and $o_i$, instead of $o$. This last restriction guarantees points-to-relation is reached.
- Iterate until a fixed point of the points-to-relation is reached.

The high technical complexity of this algorithm – adaption of Lhoták [LH03] – when propagating points-to relations with a working algorithm, stems from the fact that the call targets $f_i$ usually have not yet been analyzed and need to be added to the points-to graph. This is even more true for call targets in $f_i$, which often need to be analyzed and added as well, those methods may turn in contain calls to new methods. But even after analyzing and adding all new methods, the complexity remains that worklist algorithm must know node propagation. When analyzing new code it is sufficient to add all parameters of the call to f into the worklist, but the targets of all edges from newly analyzed code to elder nodes, that have already been propagated, may also require propagation. However, it is difficult to keep track of which nodes are old and not. As a result, on conservatively propagate all point-assignment edges after adding new methods.

As expected, processing the new virtual target is most challenging. This procedure directly reflects all elements described in the list.

### 2.3.3 Aliasing

For our application program slicing points-to-relations is mainly required for aliasing. Two references are said to be aliased [HLW+91] if they point to the same memory cell. We distinguish two flavors of aliasing:

Definition 2.15 (Aliasing). Two references are must-aliased, if they point to the same memory cell in every execution of the program; they may-be-aliased, if they point to the same memory cell in some executions of the program.

May-aliasing is needed when computing data dependences, where a dependence must be inserted if the two statements access the same memory cell. May-aliasing allows strong updates (i.e. insertion into the kill-set of an update) and thus reduces the number of spurious dependencies. However, aliasing is known to be statically undecidable [Ram94], so conservative approximations must be applied. In practice this means a subset of the must-aliases and these strong updates can be determined, some spurious dependencies remain in the dependency graph. And for-aliasing, one must find a superset of all definitive may-aliases, in order to get all possible data dependences.

May-aliasing based on points-to-relations is easily determined, even that points-to and aliasing are sometimes used interchangeably.

Definition 2.16 (May-aliasing). For two references [pointers] of p and q,
may-alias(p,q) := (points-to(p) ∩ points-to(q) ≠ ∅)

Little work can be found on must-aliasing, probably because points-to is already hard for realistic languages and often local reasoning is sufficient. Must-aliasing is hard to determine, as the points-to relation is already a conservative approximation (specifically due to flow-sensitivity). One problem lies in the fact that each allocation site in points-to stands for an equivalence class of dynamic allocations that are possible at runtime. For example, an allocation in a loop can create an unbounded number of objects, none of which is must-aliased. The same goes to allocations in recursive cycles of the call graph. Still, provided an allocation not in cycle in the interprocedural control flow graph, accesses x, y where points-to(x)=points-to(y) are known to be must-aliased. This is trivial for the case where both references may never null, but also straightforward, if one reference might be the corresponding use or definition will not take place the program will branch to handling code. Such a dependency is impossible and redundant, so must-aliasing may induce definitions here.

As references in Java are immutable, must-aliasing becomes a simple form of Global Variable Numbering [RWZ58]. Therefore, another analysis is possible with intermediate representation in SSA-form: If two statements in the same method access the same SSA-variable, they are must-aliases, no matter how many elements their points-to use. Usually the employed SSA-form is not minimal, so remains of the form x2=Φ(x1,...,x1) can be detected as must-aliases.

## 2.4 Slicing Object-Oriented Languages

The slicing techniques presented in the previous sections and other research in program slicing produced systems like CodeSurfer [AT01] or VALSOFT [Kri03a,RS02], which can slice realistic programs in the full C language with precision and performance.

### 2.4.1 Dynamic Dispatch

Special extensions of the SDG to object-oriented features have been proposed, all of them are capable of handling dynamic dispatch and inheritance [LH96, KMG96, Zha00, LH98, WRW03, MMKM94, HDZ000]. Usually, dynamic dispatch is treated similar to functions in C [GH96]. Today, approximation of dynamic dispatch in slicers for object-oriented languages is reasonable precision and efficient, enough to support call-graph and points-to analysis algorithms supporting the SDG construction. For every method to the call graph (see Definition 2.14) might be called at runtime, adds an edge to the entry of this method [TAFM97]. Each c→m in Gc induces a edge c→Entry_m in the SDG. As the number and type of parameters must be identified for redefined methods, the parameter nodes at t site can be taken from any appropriate method definition. However, global variables and fields of parameters that are used or modified may differ for redefinitions. This problem will be discussed in section 2.5.
