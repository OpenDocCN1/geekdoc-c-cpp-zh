## 4.5 Analyzing Information Flow

The noninterference criterion prevents illegal flow, but in practice one wants more detailed information about security levels of individuals status. Thus theoretical models for IFC such as Bell-LaPadula [BL96] or Noninterference [GMS84] utilize a lattice $\mathcal{L} = (\mathcal{L}, \le, \sqcup, \sqcap, T)$ of security levels, the simplest consisting of just two security levels *High* and *Low*. The programmer needs to specify a lattice, as well as Annotations defining the security level for some (or all) annotations. In practice, only input and output channels need such annotations.

Arguing about security also requires an explicit attacker model. For our approach, we assume:

### 4.5.1 Fundamental Flow equations

For a correct IFC, the actual security level of every statement must be computed, and this computation must respect the programmer-specified levels as well as propagation rules along program constructs. The huge advantage of PDG-base IFC is that the PDG already defines the edges between statements and expressions, where a flow can happen; as explained, explicit and implicit flow between PDG nodes is impossible. Thus it suffices to provide propagation rules along PDG edges. We begin with the intraprocedural analysis.

The security level of a statement resp., where the PDG node is S(x), where $S : N \rightarrow L^5$ Confidentiality requires that an information receiver $x$ must have at least the security level of every sender $y$ [31.96]. In a PDG, where $pred$ and $succ$ are the predecessor and successor functions induced by →, resp., the fundamental property is easily stated as

```
$$y \rightarrow x \in G \Rightarrow S(x) \geq S(y) \quad (4.4)$
```

and by the definition of a supremum

```
$S(x) \geq \bigsqcup_{y \in pred(x)} S(y) \quad (4.5)$
```

> $^5$Remember that $N$ is the set of PDG nodes. Note that our $S$ is called *dom* in the original Goguen/Meseguer noninterference definition, but we need *dom* for partial functions.

This fundamental constraint ensures $S(y) \rightarrow S(x).^6 Remember that confidentiality and integrity are dual to each other [Bib77], hence the dual condition for integrity is

```
$S(x) \leq \prod_{y \in prod(x)} S(y) \quad (4.6)$
```

In the following, we concentrate on confidentiality, as all equations for integrity are obtained by duality.

Equation (4.5) assumes that every statement, node has a security level specified, which is not realistic. In practical applications, one wants to specify security levels not for all, but for certain selected statements.^7 The provided security level specifies that a statement sends information with the provided security level, i.e. represents an input channel. The required security level requires only that input with a smaller or equal security level may reach that statement,8 it represents an output channel of the specified security level. From these values the actual security levels can be computed.

Provided security levels are defined by a partial function $P : N \rightarrow L$. The required security levels are defined similarly as a partial function $R : N \rightarrow L$. Thus, $P(s)$ specifies the security level of the information at $s$ (also called 'the security level of $s$), and $R(s)$ specifies the maximum allowed security level of the information.

The actual security level $S(x)$ for a node $x$ must not be greater than the level of its predecessors, but greater than its own provided security level. This equation (4.5) refines to

```
$S(x) \geq \begin{cases} P(x) \cup \bigcup_{y \in dom(P)} S(y), & \text{if } x \in dom(P) \ \bigcup_{y \in prod(x)} S(y), & \text{otherwise} \end{cases} \quad (4.7)$
```

Note that $R$ does not occur in this for $S$. We need an additional constraint to specify that incoming nodes must not exceed a node's required level:

```
$$\forall x \in dom(R) : R(x) \geq S(x) \quad (4.8)$
```

We can now formally define confidentiality:

**Definition 4.1.** *Let a program's PDG be given. The program maintains confidentiality, if for all PD nodes equations (4.7) and (4.8) are satisfied.*

As mentioned earlier, we are preparing a machine-checked program [qui Definition 4.1 defines noninterference. For the time being, Definition 4.1 is treated as an axiom, however, as discussed above, is well-founded in correctness properties of PDGs and classical definitions of confidentiality.

```

Now equation (4.7) simplifies to

```
$S(x) \geq P'(x) \sqcup_{y \in pred(x)} S(y) \quad (4.11)$
```

```
$R'(x) \geq S(x) \quad (4.12)$

### 4.5.2 Solving Flow equations

Equation (4.11) is satisfied in the most precise way, and hence the risk that
equation (4.8) is violated is minimized, if the inequality for $S$ turns into equality:

```
$S(x) = P'(x) \sqcup_{y \in pred(x)} S(y) \quad (4.13)$
```

Of course (4.13) also satisfies (4.11), and can be read as an algorithm which
computes $S(x)$ from $P(x)$ and $x$'s preds $S$ values. Thus equation (4.13)
defines a *forward propagation*: what happens if all the $P$ values are
propagated through the PDG (while ignoring $R$).

We now show that equation (4.13) corresponds to a well-known concept
in program analysis, a monotone dataflow framework [KU77]
presented in section 2.1, which allows efficient computation. Flows start with a lattice of attributes, which is in our case. L is for
every $x \in N$, a so-called function $f_x : L \rightarrow L$ must be defined, which
typically has the form $f_x(l) = g_x \sqcup in(k_x)$. In our case, $g_x = P'(x)$ and $k_x = \perp$,
so $f_x(l) = P'(x) \sqcup l$. Furthermore, for every $x \in N$, the framework defines
out(x) = f_x(in(x))$ and $in(x) = \sqcup_{y \in pred(x)} out(y)$. In our case, we

```
$out(x) = f_x(in(x)) = P'(x) \sqcup_{y \in pred(x)} S(y) = S(x)$
```
