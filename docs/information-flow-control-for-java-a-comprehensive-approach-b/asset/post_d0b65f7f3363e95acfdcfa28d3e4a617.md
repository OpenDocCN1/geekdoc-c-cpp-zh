## Third Party Code

A problem known in static program analysis arises for dynamic analyses as well: Libraries (especially provided by a third party) usually do not provide source code nor the debugging information needed to collect tracing data. I.e. any side-effect produced by a library call does not generate the tracing information to produce correct dependencies. When the debugging information is extracted from the SDG that problem arises already during construction of the SDG. But even if one did not depend on a static dependence graph would face the same problem.

A possible solution has been employed by static analysis designers for some years now: One writes stubs for those library methods and conservatively adds the summary dependencies at the invocation point.

## Incomplete Traces

Besides the problem of third party code, other reasons exist, why a trace could be incomplete: Either the tracer loses information, maybe by purpose or because of limitations of the tracing approach. But it depends on the whether of the traced data suffices to gain sound results. As mentioned at the beginning of this section, our goals are dynamic slicing re: chopping (cf. Section 5.4.2) and the refinement of conditions with dynamic variable data (cf. Section 5.4.3).

Dynamic slicing does not depend on the actual values of variables but the def-use relations will most probably lead to false dependencies and incorrect dynamic slices. As an example consider Figure 5.8. In the left protocol line 10 depends on the definition in line 8, this entry has been missed in the protocol on the right. The dynamic slice will determine a dependence to line 3 then, which is incorrect.

## 5.4.2 Dynamic Slicing

Dynamic slicing was introduced by Koret and Laski [KL88]. Dynamic slicing builds a dynamic dependence graph (DDG) from the real dependencies arising during program execution. Therefore, a dependence graph is usually considerably smaller than a static dependence graph, which has to rely on conservative approximations not to relinquish soundness.

For illustration Figure 5.1 again. If the execution trace is 1,2,3,4,7,9 then the static slice of node 9 is the whole graph. The dynamic slice of 9 does, not contain the statements 1 and 5 as those did not contribute to the value of z in the given graph.

Once a program trace has collected, dynamic slicing falls to two tasks: the preprocessing phase a dynamic dependence graph is generated by processing the collected data. In the slicing phase this graph is traversed to build the dynamic slice for the given slicing criterion.

A naive approach to dynamic slicing would mark all statements encountered during program execution, reduce the static dependence graph to the corresponding nodes, and do static slicing on that graph. This approach is, however, imprecise which be illustrated on Figure 5.1: With the execution trace 1,2,3,4,7,9, the naive algorithm yields a dynamic slice that contains the whole graph. Node 5 had no effect on node 7, though, as the definition of b took place the use. So, nodes 1 and 5 should not be in the dynamic slice.

As a remedy, [AI90] proposed not to work on the static dependence graph but on the tracing protocol, which shows a linear program with all loops unrolled. From that the dynamic dependence graph needs to be computed. Its nodes usually represent basic blocks rather than single statements, which build the static variant. Dependencies point from a variable use to its last definition. It may be a bit confusing that dynamic edges are reversed compared to static edges. Dynamic (backward) slicing follows all edges starting from the slicing criterion:

```
dB(y) = {x | y \to* x}
```

Since the length of the runtime protocol is in principle unbounded, the space requirement of the context-sensitive dependence graph for long program runs explodes. Therefore several ways to compact this graph were proposed.

Agrawal [AI90] noted that the number of statements in a program is bounded and hence, the number of different slices must bounded, too. He found that with the same transitive dependences could be merged. This graph was *dynamic dependence graph/reduced (RDDG)* While this representation is compact and gives a program slice in $O(1)$ (the transitive dependences are stored in memory), different instances of the same node (e.g. in a loop) cannot be distinguished. So the reduced size of the graph results in a loss of precision.

Context-sensitivity is a property that is not granted with such an approach.
A consequence of the linearity of the trace, however, dynamic slicing being added to the edges [ZG03, ZG05]. The labels contain additional information to disambiguate the execution instances of the statements the edge links. Zhang et al. can call this dynamic *data dependence graph*. As an example consider Figure 5.2 with the execution code 1,2,3,4,5,6. The graph edges capture the execution time of the involved statements. The check whether $x$ on line 2 is executed at time 2 and depends on the value of $x$ computed in line 1 at time 1. Thus the edge contains the timestamps: (2, 1). The node corresponding to line 3 (we will use the terms node/statement interchangeably for this example) depends on execution of statement 1 in the first instance of the while-loop, represented by an edge marked (3,1); in the second it is dependent on the last instance of itself: the loop edge is marked with the execution (6,3).

The dynamic program slice is computed in the dynamic data dependence graph using the formula $x 	o_i y$ to denote the edge from $x$ to $y$ with the timestamp $l = (t_1, t_2)$:

```
$dBS_{cs}(y,t) \quad \{x \mid \text{Path } p : (y = x_0 \to l_0 \cdots \to l_{n-1} \to x_n = x) :\n l_0 = (t, t_0) \wedge\n\forall 0 < i < n-1 : l_i = (t_{i-1}, t_i) \wedge l_{i+1} = (t_i, t_{i+1})\}$
```

In our example, the dynamic slice of the execution of line 2 (with timestamp 2) is itself and line 1. Line 3 is not included, as the edge with timestamp 5 is not followed. Starting from line 2 with timestamp 5, however, we will have to include line 3 and come back to line 1. This small example already illustrates the power of edge labels.

Similar to the dynamic program slice, it is possible to define a dynamic program in the dynamic data dependence graph:

```
$dCH_{cs}(x,y,t_x,t_y) = \{x \mid \exists \text{Path } p : (y = x_0 \to \cdots \to l_{n-1} \to x_n = x) :\n l_0 = (y, t_0) \wedge l_{n-1} = (t_{n-2}, t_y) \wedge\n\forall 0 < i < n-1 : l_i = (t_{i-1}, t_i) \wedge l_{i+1} = (t_i, t_{i+1})$
```

A dynamic chop contains all nodes that are part of a path from $x$ to $y$ in the dynamic data dependence graph that starts at $y$ with timestamp $y$ and ends at $x$ with timestamp $x$.

The dynamic dependence graph is not respected in space, and the graph can only be built if the runtime is entirely processed which may take too time for long-running applications. Zhang et al. [ZGZ03, ZGZ05] proposed—apart from this preprocessing algorithm (FP)—two variants that do not need the graph beforehand. no preprocessing (NP) and limited preprocessing (LP). The algorithm entirely forebears from constructing the dependence graph and, when slicing, runs back linearly to find the most recent definition of the graph variable. NP has a worst case complexity of $O(N^2)$ which is unacceptable for larger slices or for many slicing. Even with the use of marking statements in the slice not to followed again, this complexity cannot be lowered. The best compromise between the FP and NP algorithms, is to the authors, the LP algorithm, which introduces some information at a offset between two entries in the tracing protocol. Still, the complexity cannot be reduced by an order of magnitude but by a constant factor.

We implemented all the mentioned algorithms for dynamic slicing and evaluated them on our suite cf. Section 7.4.2). Our experiments approve the results of Zhang et al. [ZGZ03, ZGZ05]. On average over 100 slicing criteria for **agrep**, the cached LP algorithm was, with about 20 sec and 4.7 MB memory, faster than NP with 21 sec and FP with 26 sec, consuming significantly more memory than the NP algorithm, which used 4.4 MB ram, and better than FP needing 6.4 MB.
