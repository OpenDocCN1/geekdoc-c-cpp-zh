## 7.3 Information Flow Control

This section presents empirical studies about precision, scalability, and pract-
icability of our new information flow analysis developed in chapter 4. It starts
an elaboration on the current state of the art in language-based informa-
tion flow control. The language Jif is the only implementation of a Java-like
language with built-in information flow control. We will show that the applic-
ability diminishes significantly, as the language design is centered around the
information flow type system. Traditional Java programs need sign-
ificant refactoring for complying with Jit's constraints (see e.g. [AS05]).
The later parts of this section connect on empirical evaluations of accuracy
and scalability.

## CHAPTER 7 EVALUATION

### 7.3.1 JIF

The only implementation of a type system for a non-trivial imperative language is JIF [MCN+], originally called JFlow. It provides a Java-like language extended by labeled types, comprising an ordinary Java type like String, and a security label which is part of the program's security policy. Each security label restricts the information that may flow the annotated variable. The variables implicitly form a complete lattice in the decentralized label model [ML00]. This model allows multiple principals that form some sort of access control on the information they own. They can allow other principals to read data, classify and transfer authority to principals and code. In version 3, Jif's decentralized label model was augmented with integrity checking.

The major advantages of security type systems can be found in Jif as well: Type checking is both efficient and compositional. It is therefore possible to check each class in isolation and compose an application of the pieces later to analyze the program as a whole. In principle, composition applies to libraries as well. However, due to the sheer size of Java's standard classes and the lack of publicly available source code, Jif does not provide security annotation for free. And even for these, there is no semantic guarantee (see the paragraph on libraries below).

But first, we evaluate the dimensions of analysis precision of Jif's systems.

### Flow-insensitivity

Like most type-based approaches, Jif partitions the set of variables and fields into disjoint sets (such as secure and public data). If illicit information flows e.g. from the public partition, Jif already considers program insecure, even if the program variable is no longer active after flow. This can be seen in the program fragment in Figure 4.2 on page 90, which is intuitively correct, the assignments from the if-block are killed by the subsequent definition. Type systems like Jif will spuriously reject code because confidential information has an influence on the value in a public variable.

Based on the original definition of noninterference [GM82, GM84] (see section 4.3), however, this program fragment states that the two streams of (public) output of the program should be indistinguishable if they differ on (secret) input. In other words, secret input is not allowed to flow to public output channels. This definition is reflected in our slicing-based approach, which only checks for secret data that might flow to public output. But type systems cannot guarantee that property since like slicing.

### Context-Insensitivity

Partitioning variables and fields into disjoint sets has the additional advantage that the analysis becomes context-insensitive: As a result, data structures or even simple utility methods cannot be reused for different security levels. One would need to write one Vector class or cosine-method for each security

level, and would be even worse for multi-parameter methods. As a remedy, Jif supports various kinds of polymorphism to allow reusable code, similar to Java 5's generics for collections. But like these, the programmer needs to annotate all data structures with type parameters when they are to be used in different security policies. A recent case for Jif [AS05] found that a Java library wrapper had insufficient annotation, which may result in undetected security violations. Apart from that, polymorphic classes are subject to certain restrictions (see type discriminants on page 167) which limits their applicability.

### Object-Insensitivity

Similar to contexts, different objects might want to store data with different security labels. However, type systems label each field statically with a single security label. Again, some remedy can be achieved by polymorphism, with the same problems as before. Another way to achieve object-sensitivity is runtime-labels, but these require program instrumentation, which induces an additional execution time and space overhead.

### Differences to Java

Even though Jif compiles down to standard Java (but requires an additional runtime system provided as a jar library), there are differences between Jif and Java. Some of these limitations are standard in any kind of language-based interfaces:

Threads Like most, Jif does not prevent threads from communicating via the timing of modification of shared variables and synchronization. Such channels can only be controlled by possibilistic [SV98] and probabilistic [SS01,Smi6] IFC. An implementation of a type system for these security policies has been reported. However, our slicing-based IFC can be extended to probabilistic noninterference [GL]. We are currently integrating a checker for this security policy in our system.

Finalizers run in a separate thread in Java and can exploit the shared covert channel. Therefore, Jif does not support finalizers. Most analyses ignore them, as they are rarely used in Java and their execution time is unknown. Java guarantees that execution happens when the garbage collector finds an object not reachable from the active state. There is no guarantee that a finalizer will run at all however, e.g. [LIF03].

Timing channels are extremely hard to counter if an adversary has access to a clock independent from the system. These physical side channels are not covered by language-based information flow control except for Agat's type system [Aga0] and Sabelfeld and Sand's strong security [SS01].
