# 2.3.1 Inclusion-Based vs. Unification-Based Analysis

Two fundamental approaches in determining points-to-relations have been presented:
Steengaard [Ste96] proposed a unification-based approach, where pointers are either aliased or point to the same set of objects. Its advantage is the near-linear complexity of $O(n\alpha(n))$ where $\alpha$ is inverse Ackermann function), based on the Leis-Tarjan algorithm [LT79]. In the example of Figure 2.7, the rightmost graph corresponds to Steengaards algorithm. Since unification means that the points-to of o1 equals one of o2, the edge between connecting nodes points in both directions. Unfortunately, applying this to Java yields several undesirable properties. Streckbench [SS00b] has found that strangely typed languages like Java lose type safety with unification-based approaches, which can be seen in Figure 2.8, where a reference of type String is determined to possibly point to a declared type Object. This dramatic implications on the approximation of dynamic binding, where the called method depends on the target object: When char() is called on o2 the analysis cannot determine which method in java.lang.Object the of the first allocation. Because it lacks typing information, it is now unclear, the analysis contains a bug, or is simply due to over-approximation. This led to years of research for scalability in the inclusion-based approach.
Andersen's points-to inclusion-based inserts only uni-directed edges between pointers of an assignment. This approach will only generate constraints that obey type-safety, which corresponds more thinly (middle) to an assignment's semantics, as be seen in Figure 2.7. Here, only o1 might point to o2 but not versa. The points-to relations become more precise than the unification-based approach (see left graph in Figure 2.8). However, the cost of solving the constraint system is in $O(n^3)$ where $n$ is the number of statements in the program. Despite this inclusion-based analyses have become predominant in the last years, due to advances in runtime BDDs from recent research e.g. by using better data structures [WL04, LH08].
