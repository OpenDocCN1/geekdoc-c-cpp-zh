# 4.2. INFORMATION FLOW CONTROL

**Explicit Flow** from $x$ to $y$ occurs, when $y$ is assigned a value which contains a reference to $x$. $y = \mathbf{f}(x)$ is an example of explicit flow.

**Implicit Flow** from $x$ to $y$ emerges from control flow, where the execution depends on the value of $x$. For example the if $(x=0)$ $y=0$ else $y=1$; contains implicit flow from $x$ to $y$. Historically, some authors regarded implicit flow as a covert channel, however, today, this classification is no longer found, as implicit flow can easily be checked with language-based techniques.

# 4.2 Information Flow Control

A means to control how information flows through the channels of a program is called information flow control (IFC). Of the three dimension described in the CIA-triad, information flow controls confidentiality/or integrity. Often integrity is limited to duality (on an observation of [Bib77]), one generally describes only how to assert confidentiality. control can be done online (during program execution) or offline (often compile time). Both approaches have different advantages and disadvantages.

The major advantage of online (dynamic) IFC is that it does not spuriously secure program execution, so it is precise. Its classification may be static (each variable has a fixed security level for the whole execution) or dynamic (the security level is determined at each assignment). But like dynamic program analyses, it cannot show the general security of the program, and it slows down program execution with runtime tests. Also, dynamic checking can best prevent illicit flow that is about to happen, but malicious adversary might gain the information that the program was terminated due to a violation of the security policy, so the program leaks at least boolean information. Some systems like Fenton's Data Mark Machine [Fen74] employ special techniques to avoid this leak, but these may not be effective in the presence of side-effects. The most limiting property of runtime IFC is control structures, a synthetic variable, called *program* (or called *sensitivity label* in [Ara83]) keeps track of the data in control flow. However, the security label of a control predicate $p$ does not restrict the security level of controls that are controlled by the predicate in a given program execution, but also values of variables that might change as a consequence of the predicate $p$ in another execution. But dynamic analysis is characterized by only one path of execution, not all possible paths. One approach to detect all possible implicit flows is to keep the PC (program counter) at the security level of $p$ for the rest of the program (and increase with subsequent control structures, an effect which is called *label creep* in [SM03]), making dynamic analysis only restrictive in practice.
