For non-executable slices, the latter are not necessary as they do not increase the precision of the slice. Thus in our SDG membership and inheritance dependences are omitted.

Nanda's approach [NR03] models fields of objects as extra parameter nodes escape nodes. The concept is similar to our approach but they build no nodes which makes it harder to find the dependence between a field and the containing object.

CoderSurfer [AT01, ART03] contains a beta version slice for C++. A Java version is planned. As of today, nothing is known about the precision of CoderSurfer for....

The Bandera [HDZ00] uses the Indus⁴ Java slice to automatically reduce the size of the transition system for model checking of Java source code [DHH+06]. The Bandera slic is designed as a model checker frontend, not as a tool for program analysis. In the contrast, Kaveri Eclipse plugin [JRH05] offers a slice for Java in a popular development environment. To our knowledge the Indus slice—besides ours—fully implemented and can handle Java bytecode. Indus is customizable, embedded in Eclipse, and has a very nice GUI, but is less precise than our slic in terms of procedural data dependences of object fields. Many implementations of slic for Java like [JRH05] provide a relaxed notion of dependence graph¹⁵ where dependences are allowed to cross boundaries. While this allows a more efficient implementation, one loses context-sensitivity for contexts for precise slicing, while SDG slicing is precise even for recursive methods. Furthermore, applications like an example, Kaveri only offers k-limiting of contexts for precise information flow control algorithm (see section 4.6.1) require context-slicing and are thus not applicable to relaxed graphs. Only the basic IFC algorithm can be leveraged in such a setting.
