# 7.3.1 JIF

The only implementation of a type system for a non-trivial imperative language is JIF [MCN+], originally called JFlow. It provides a Java-like language extended by labeled types, comprising an ordinary Java type like String, and a security label which is part of the program's security policy. Each security label restricts the information that may flow the annotated variable. The variables implicitly form a complete lattice in the decentralized label model [ML00]. This model allows multiple principals that form some sort of access control on the information they own. They can allow other principals to read data, classify and transfer authority to principals and code. In version 3, Jif's decentralized label model was augmented with integrity checking.

The major advantages of security type systems can be found in Jif as well: Type checking is both efficient and compositional. It is therefore possible to check each class in isolation and compose an application of the pieces later to analyze the program as a whole. In principle, composition applies to libraries as well. However, due to the sheer size of Java's standard classes and the lack of publicly available source code, Jif does not provide security annotation for free. And even for these, there is no semantic guarantee (see the paragraph on libraries below).

But first, we evaluate the dimensions of analysis precision of Jif's systems.

# Flow-insensitivity

Like most type-based approaches, Jif partitions the set of variables and fields into disjoint sets (such as secure and public data). If illicit information flows e.g. from the public partition, Jif already considers program insecure, even if the program variable is no longer active after flow. This can be seen in the program fragment in Figure 4.2 on page 90, which is intuitively correct, the assignments from the if-block are killed by the subsequent definition. Type systems like Jif will spuriously reject code because confidential information has an influence on the value in a public variable.

Based on the original definition of noninterference [GM82, GM84] (see section 4.3), however, this program fragment states that the two streams of (public) output of the program should be indistinguishable if they differ on (secret) input. In other words, secret input is not allowed to flow to public output channels. This definition is reflected in our slicing-based approach, which only checks for secret data that might flow to public output. But type systems cannot guarantee that property since like slicing.
