If the criterion is not satisfied, then the outputs for the final statement $a$ differ between the actual $a$ and $\alpha$ with all supposedly non-influential statements removed — thus there is influence from a statement $s$ in $\alpha$ to $a$ even though this is forbidden by $dom(s) \not\subseteq dom(a)$. We see that the notion of security is based on observational behavior and not on the source code.

Type-based approaches for the definition of noninterference have been defined in a more compact format. In its simplest variant $c_{Low}$ which assumes only security levels $Low - High$ — it reads

```
$s_{Low} s' \implies [c]_s_{Low} [c]_{s'}$ (4.2)
```

where $c$ is a statement or program, $s, s'$ are two initial program states, $[c]_s, [c]_{s'}$ are the final states after executing $c$. $s_{Low} s'$ means that $s$ and $s'$ are equivalent: they might coincide on variables which have $Low$ security. This variation in the high input variables does not affect output, and hence confidentiality is assured. Note that various extensions of elementary noninterference, such as possible or probabilistic noninterference; some of them based on PER relations [SS01]. Pistoa et al. [PCFY07] already noted that Goguen/Mesueger noninterference is more than the criterion of security flow of equation 4.2 and its descendants, because the former considers only observational behavior and does not contain implicit and explicit flow at each statement. The approach presented in the sequel only considers behavior, and thus adheres to the original Goguen-Mesueger definition.

The following theorem connects PDGs to the original Goguen-Mesueger definition and can be used to check for noninterference.

## Theorem 4.1. If

```
$s \in BS(a) \implies dom(s) \not\subseteq dom(a)$ (4.3)
```

then the noninterference criterion is satisfied for $a$.

Proof. See [SRK06].
If $dom(s) \not\subseteq dom(a)$ ($s$ and $a$ have noninterference security levels), there must be no PDG path $s \to a$, otherwise a security leak has been discovered.
The generality of the theorem stems from the fact that it is independent of specific languages or slicing algorithms; it just exploits a fundamental property of any correct slice. The theorem is valid even for imprecise PDGs and slices, as long as they are correct. Applying the theorem results in a linear-time test for all $s$. More precise slices result in fewer false alarms. However, as we will see later, it is not possible to use declassification in a purely slicing based approach, thus later we will present extended versions of Theorem 4.1.

## 4.4 Examples for Slicing-based IFC

In the following, we assume some familiarity with slicing technology, as presented in chapter 2. Our Java PDG is based on bytecode rather than source text for the following reasons:

```java
class PasswordFile {
    private String[] names;
    /**P: confidential*/
    private String[] passwords;
    /**P: secret*/
    // Pre: all strings are interned
    public boolean check(String user,
        String password /**P: confidential*/) {
        boolean match = false;
        try {
            for (int i = 0; i<names.length; i++) {
                if (names[i]==user
                && passwords[i]==password) {
                    match = true;
                    break;
                }
            }
        } catch (NullPointerException e) {
        } catch (IndexOutOfBoundsException e) {
            return match; /*R: public*/
        }
    }
}
```
