
## 5.4. DYNAMIC PATH CONDITIONS IN DEPENDENCE GRAPHS

Venkatesh [Ven95] implemented a low level approach for tracing C programs. His prototype implementation called SLICE instruments the source code to write a program trace during execution. With this experience, the authors recommend object-code instrumentation for future implementations together with several reasons. Nonetheless, this implementation is faster than tracing with a traditional debugger.

Zhang et al. [ZGZ03] follow a different low-level approach to create a program trace: the program is compiled with the Trimaran system, a compiler for the Explicitly Parallel Instrumentation Computing (EPIC). An interpreter takes the generated object-code and creates the program trace during execution. Since C programs are not properly instrumented, this approach is valid mostly for theoretical evaluations.

All low-level approaches generally not slow down program execution as much as a debugger does. However, as our work is on the static dependence graph which must be mappable to source, these approaches do not suit our needs.

Dynamic program slicing has been in active research for several years. Various approaches, either for dynamic slicing on their own, or with static elements have been proposed. To mention all of them would be out of scope of this work:

Chen et al. [CX01b] describe a dynamic slicing algorithm that is based on a static SDG providing the information to set break points for the debugger. The static dependence graph is confined to the nodes and edges that have been visited to build the dynamic dependence graph. Slicing is done following all edges in graph.

> Tip95 embarks on a different strategy: He uses the abstract syntax tree (AST) instead of a dependence graph and interprets the program. The approach is language independent but only available for the custom-built language 'L'.

Zhang et al. proposed another way to reduce the amount of data that is stored in the program trace. They compute the dynamic slices during execution and store them in binary decision graphs (BDDs) [ZGZ04].

Wang et al. [WRO04] propose a dynamic slicing technique for Java that compresses the trace on-the-fly and obtains two to three orders of magnitude compression algorithm. A lossless compression finds a high repetition pattern in the sequence of (memory and control) edges captured by the tracer. They also propose a dynamic slicing algorithm which operates directly on the compressed data and can save the uncompressing time. Such an algorithm may not only be suitable for languages with extensive pointer usage. We expect the repetition pattern for our variable trace to yield a similar compression rate. Since the slicing algorithm runs on the compressed data with no dynamic dependence graph used, multiple slicing requests requiring the trace multiple times at a significant time overhead.

### 6.1 Frontends

Currently, SDGs are constructed for both C and Java code. We extended the commercial slicer system CodeSurfer [ART03] with a plugin that creates files compatible with our graph format. This approach complements the Valsoft SDG generator created previously in our group [Kri03a]. Adding a commercial product to our tool suite naturally makes it more mature, however, CodeSurfer is deemed unsound for very large programs [And08]. The challenge in extending CodeSurfer dependencies arises as slicing forms a basis for path conditions. Path conditions require a fine-grained SDG structure similar to an abstract syntax tree, but CodeSurfer supports only coarse-grained SDGs. ### 6.1.1 Stubs

The Harpoon frontend full bytecode for Java up to version 1.4. We found that the changes in executable bytecode for Java 1.5 were marginal, that a small patch to that library now allows parse bytecode to version 1.6. However, the library is another issue. It is well known that of JDK 1.4.2, even the simplest "Hello world" program loads 248 classes! And for versions the library is even bigger and more classes are loaded. Yet, many of these do not contribute to the transitive dependencies of the analyzed program. For example, it does matter how a special locale determines the upper and lower case versions for a given character. What matters is the resulting depend can be modeled via method stubs. A stub is a placeholder method that models the necessary semantics of the original method that all possible dependencies are included into the dependency graph. Type systems use a simple technique to represent the effects of library calls, e.g. in Jif, library methods need to be annotated in semantics. Providing these annotations is equally error-prone as writing stubs for libraries (e.g. Askarov [AS05] reports a false annotation included in experiments) analyses need to model library methods to avoid excessive analysis cost.

For our analyses, we created stubs for native methods and important library methods for two versions of Java:

- First, we created stubs for all native methods of JavaCard 2.2. Card is an implementation for very restrictive environments like smartcards. Therefore, JavaCard contains only the sequential parts of Java and the library has been pruned. With the stubs for native methods and the ability to analyze the bytecode of the library, our experiments in chapter 7 include all effects of user and library code.
- Second, we developed stubs for the essential parts of the standard library. In particular, the effects of lang are included in our stubs except for very problematic constructs like dynamic class loading. Such constructs are well beyond the scope of this thesis, solutions can be found e.g. in Livshits et al. [LWL05]. At certain points we cut parts of the call graph, when dependencies can be included without loading a myriad of other library classes (see the Locale example above). Still, these stubs induce conservative approximations of the original dependencies and remove excessive burden.

> A second reason for the need of Jif's annotation mechanism is that it lacks the ability to analyze bytecode, therefore the standard library cannot be analyzed.

### 6.2 Analyses based on SDGs

The generated dependence graphs are stored on disk, from where they are parsed with an ANTLR² grammar, and stored in the open source graph library JGraphT.¹ When we decided to use that library, the author first contributed Java 5's generics to that library, resulting in type-safe graphs (specifically no explicit casts for node and edge types) for our custom algorithms. The Joana library based on JGraphT provides a long list of algorithms for slicing, chopping, and related analyses. In particular, all presented and implemented in the original Valsoft [Kri03a] have been integrated. This core library forms the basis for nearly all other libraries and Eclipse plugins in the sequel.
