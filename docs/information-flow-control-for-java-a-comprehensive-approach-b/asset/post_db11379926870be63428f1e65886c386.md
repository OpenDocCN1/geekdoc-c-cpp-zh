Building PDGs without explicit exception handling renders it incomplete for the full Java semantics. In Java, bytecode instruction may throw an implicit exception (subtypes of RuntimeException) in case operands are operands. For example, every bytecode that manipulates objects may throw a NullPointer, those for arrays ArrayOutOfBoundsException. To get a sound analysis, control flow must be taken into account. In each case, each bytecode that throws an implicit exception is preceded by a predicate that checks code's precondition for normal execution, and if it is not satisfied, control flow branches to exception handling code or to code for abnormal termination [CPS99].

An exception without appropriate exception handler is passed to the caller of the causative method. If this caller has an appropriate handler installed at the invocation bytecode, this handler is branched in order to handle the exception; if not, then the caller method terminates abruptly as, "rethrowing" the causing exception. This schema is employed until an appropriate handler is found somewhere in the stack, or else this thread of execution terminates and the causing exception is printed to the user. Again, this is incorporated into the control flow graph by introducing an extra predicate with two successors for each possibly executing call instruction: one-successor models normal termination and one is for abrupt termination of the called method.

Slicing in the presence of objects and fields is not so different from slicing data types in traditional languages. Horwitz et al. [HPR89] already noticed to extend the concept of data dependence for languages that manipulate heap-allocated storage, it is necessary to phrase its definition in terms of locations rather than variables:

**Definition 2.17** (Data Dependence for Composite Data Structures). Point q has a data dependence on program point p if p writes into a memory location q reads, and there is no intervening write into loc along the execution path by which q is reached from p.

Even Horwitz et al. only considered a List-like operator, it can model more complex data structures. However, with objects and fields, it is not always decide if two program points access the same memory location. Agrawal et al. [ADS93] give a classification of memory accesses into complete, maybe and partial intersection of memory locations: *Complete intersection*, if the objects of both are must-aliases and they access the same field. Intersection for field access is possible due to aliasing; if two references access the same field they are only maybe-aliases, this is called *maybe intersection*. Another case maybe intersection arises with arrays, where the field index is generally unknown at compile time. Arrays combine this maybe intersection with *partial intersection*, as only one element of the array is accessed. Most work on arrays treats arrays as a single location in memory, ignoring the index which is only known at runtime. We follow this conservative convention by modeling arrays as a field with reserved name. Lyle [L84] proposed that array updates should be handled as a reference to and subsequent update of the whole array. This results in data dependences between array updates $a[i] -> a[j]$ when the first statement reaches the code, even if $i$ may not equal $j$.

## Field sensitive analysis

Several approaches for determining the type of intersection have been proposed in literature. Each approach has its strengths and weaknesses. A straightforward intersection computation by scalar replacement [Kri03], where any access to a variable is (recursively) replaced by contained fields, does not necessarily give the most precise data dependencies. Consider the program in Figure 10 where z is only dependent on the definition in line 6. Framework of ValSoft [Kri03] uses slicing of line 4 due to loss of precision of its scalar replacement. CodeSurfer [AT01] employs a non-virtual scalar replacement strategy that blows up by replacing the assignment a = b with strategy that allows the computation of the slice. Such replacement may be appropriate for procedural languages like C, where nesting of structures is not too common, for object-oriented languages like Java with deeply nested objects would require a large overhead, which can be avoided by using definition of data dependence without explicit scalar replacement. The definition of data dependences can be refined for the case of access to a field f, which is referenced by its fully qualified name:

**Definition 2.18** (Data Dependence for Field Access), A PDG has a data edge from node n1 to node n2 due to field access iff all the following conditions hold:

- n1 is a node that defines the field f of variable x
- n2 is a node that uses the field f of variable y
- x and y are potential aliases (may-aliases)
- control flow can reach $n2$ after $n1$ via a path in the CFG along which is no intervening definition of f

With this definition, we get the precise slice in Figure 10 without expensive replacement strategies just by inspecting the reaching definitions of the last line, which contains both assignments to the y field. With the flow-sensitivity in pointer analysis gained by SSA form, the criterion will be determined dependence only on the definition in line 6. While this last definition of dependence is always field-sensitive, its precision relies heavily on the precision of the underlying alias analysis.

## 2.5 Interprocedural Dataflow Analysis

For interprocedural analysis, a conservative approximation is required for how a program manipulates its data at the call graph level. For program slicing, this mainly covers what side-effects a method may impose on its parameters. Side-effects of called methods produce new definitions that may reach a use and thus require data dependencies. Algorithms to compute such side-effects are known in the literature [Ban79, Muc97], but they are presented for procedural languages only, without covering extensive use of objects and their fields. Side-effect analysis for multi-level pointers [LLS01] is, however, too infiltrate for representing objects slicing [L496, L498]; their approaches either have flaws or do not handle nested objects conservatively. [TAFM97] already noted that points-to information is a prerequisite for precise side-effect analysis of oriented languages. The following section will present a new approach for putting a conservative approximation of the side-effects of methods and their invoked methods that allow context-sensitive slicing of objects. It allows field-sensitive slicing and takes aliasing into account.

To field-sensitive analysis also in the interprocedural case, we need to explicitly represent all the fields of parameter objects and accessed values at the method entry nodes and call sites [FS91]. This corresponds to the non-virtual scalar replacement strategy in the intra-procedural case (see section 2.4.3).

In analogy to previous work [Ban79, Muc97] we characterize side-effects as set of locations they may access. A memory location is an abstract of a cell in the heap and is represented as a sequence of fields rooted at a pointer of the given method, such that dereferencing the fields in the lists yields a pointer to the abstract location. For example, if an object may be accessed with the expression $a.f$ from the parameter $a$, then $a.f$ is an abstract location for the memory storing that object. While this representation is not necessarily unique, it is sufficient for our algorithm.
