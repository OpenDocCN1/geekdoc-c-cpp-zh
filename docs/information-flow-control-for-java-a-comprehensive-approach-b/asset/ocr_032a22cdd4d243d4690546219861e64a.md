# 4.3 Dependence Graphs and Noninterference

The soundness of PDG construction guarantees that a matching path from a to b in a PD implies there is no influence from a to b. This asserts that information flow is not caused by hidden physical side channels such as timing or termination leaves is impossible. It is therefore not surprising that technical details for secure information flow as noninterference is related to PDGs.

Noninterference as defined by Goguen and Mesueger [GM82, GM84] is defined with respect to an abstract automaton M=(S, A, O, step, out) representing state transitions of a program. The generali contains an initial state s₀ S, the set of actions A can be thought of as the program's constructs, and the outputs O represent all possible outputs. step: S × A → S is the transition function, which in our case is induced by the program semantics, and out: S × A → O is the output function. We define the function run: S × A* as the natural extension of sequence of actions in A* in the standard manner: run(s,e)=s; run(s,a)=run(s,a),

The security level of action a ∈ dom(d) ∈ L. Given a state domain d, the function purge: A* × L → A* merges sequence α from all statements which will not influence security level d: purge(α,d)=(a ∈ α dom(d)→).

A system is considered safe according to the Goguen/Mesueger noninterference-criterion if, for all statement a that are possible according to the control flow graph and all final statements (executed after a has been processed),

```
output(run(s₀,a)) = output(run(s₀,purge(α,dom(s₀)))), a)) (4.1)
```

Thus noninterference requires that the final program output be unchanged if every statement is deleted – according to its security level – must not influence the final program state.
