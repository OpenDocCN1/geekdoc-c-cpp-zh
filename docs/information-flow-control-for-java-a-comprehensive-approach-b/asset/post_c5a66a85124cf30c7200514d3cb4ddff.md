# Evaluation

The previous chapters defined several precise analyses which can be leveraged for security purposes. This chapter now presents empirical evidence of their practicability, scalability, and precision. First, we will evaluate the precision of our new side-effect analysis for program slicing (see chapter 2). Second, we assess the effectiveness of our improved algorithm that determines interference dependence (see chapter 3), and contrast it to previous definitions, which did not take points-to information into account.

Next, we evaluate our slicing-based definition of information flow control (see chapter 4). To thoroughly analyze practicability, we present Jif, the only implementation of an information flow type system, and compare it to our system. The gain in precision is examined by a case study with an Jif program, which we converted back to standard Java. A detailed evaluation of our IFC algorithm on a set of benchmark programs illustrates its scalability.

Finally, we present path conditions (see chapter 5). Both static path conditions for Java with its object-oriented language constructs, and dynamic path conditions for C are presented. These studies illustrate that extensions provide precise results for realistic programs.

## 7.1 Slicing Java Programs

Our initial presentation of the Java slic [HS04] aimed at an evaluation of the imprecise between an approximate modeling of parameter objects and our object trees. However, we could not learn from Liang and Harro [LH98] how k-limiting works. So we fell back to comparing our sound model without k-limiting, i. we measured the effect of omitting the dependences induced by deeper levels all-together. As a matter of fact, we found that unsound k-limiting may miss up to 90% of the correct slice. While this evaluation showed that deeper levels have great impact on slicing of Java programs, this comparison was not what we originally had in mind. But after several years we could not find a sound approximation for the missed dependences of k-limiting.

However, the Indus/Kaveri slic [JRH05] propagates an alternative approach to data dependence computation. They essentially add data dependences

between all definition statements to all matching uses of a given field and ignore method boundaries for that purpose. It should be straightforward to prove such a model for context-insensitive slicing. However, this thesis shows the effectiveness of our object trees in comparison to method-spanning dependencies.

Note that data that cross method boundaries violate a precaution for two-phase slicing, for context-sensitive slicing in such a model needs extra recovery at method boundaries each time slice is computed. We did not include such complex' analysis. Instead, we compare our context-sensitive slicer to the context-insensitive slicer using SDG and to the relaxed notion of graphs described above.

## 7.2 Evaluating Interference Dependence

Apart from usual data dependencies our SDG contains interference dependence caused by memory access in threads. To compare the effectiveness of our algorithm of chapter 3, which computes a safe approximation of interference dependence, we measured the number of interference edges and compared this number with the one reported in Ranganathan and Hatcliff [RH04] and type-based approaches as used in [HCD7:99]. Table 7.2 shows the result of our analysis: We examined the same programs as in [RH04], i.e. a suite of benchmarks from

JavaGrande Forum.³ These programs consist of a range of programs, from very small to medium-sized. Especially the smaller programs allow manual inspection to verify which interferences are spurious and real. This does not allow relative comparisons but also how far we are from the (undecidable) minimum. The left hand of the table shows the result from [RH04], the columns, from left to right, the number of interference edges when only taking information into account, when using the specialized analysis developed in that paper, and when using entity information, respectively. They display the number of interference dependences, from left to right, using type information, presented in chapter 3, and after pruning spurious dependences with a simple happens-before-analysis [GH09]. The last column shows the number of interference dependences determined by manual inspection (where possible).

The first benchmarks in Table 7.2 are micro-benchmarks with the two operations to test and evaluate a virtual machine implementation's synchronization constructs. The absolute number of interference dependences in these constructs is relatively low, one benchmark ForkJoin does not expose a single one. Nevertheless, Ranganath and our analysis report a considerable number of dependences. Manual inspection due cases where a field is defined in a constructor of a thread object that is subsequently used. When two operations are embedded in a loop, our happens-before analysis, developed for precise slicing of concurrent programs [GH09], will merge constructor statements for being in the same strongly connected component. This constructor appears to happen in parallel to the stated thread. However, the constructor only handles data that is local to its object. Therefore, these dependences are already modeled as fork-ins (which are equivalent to parameter dependences) modeled at the statement starting the thread that adding interference dependence here is redundant. Currently, our analysis does not perform a thread-locality analysis that detects false positives.
