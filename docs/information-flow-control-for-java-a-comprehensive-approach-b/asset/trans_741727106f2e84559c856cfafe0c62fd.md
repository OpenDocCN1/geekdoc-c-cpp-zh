

## 5.4. 依赖图中的动态路径条件

Venkatesh [Ven95] 实现了一种用于跟踪 C 程序的低级方法。他的原型实现 SLICE 对源代码进行仪器化以在执行期间写入程序跟踪。凭借这一经验，作者建议未来实现采用对象代码仪器化，并提出了若干理由。尽管如此，该实现比使用传统调试器进行跟踪更快。

Zhang 等人 [ZGZ03] 采用了另一种低级方法来创建程序跟踪：程序使用 Trimaran 系统编译，该系统是显式并行仪器化计算（EPIC）的编译器。解释器接收生成的对象代码并在执行期间创建程序跟踪。由于 C 程序未得到适当仪器化，因此该方法主要适用于理论评估。

所有低级方法通常不会像调试器那样大幅减慢程序执行。然而，由于我们的工作基于静态依赖图，该图必须能够映射到源代码，因此这些方法不适合我们的需求。

动态程序切片已活跃研究多年。提出了各种方法，无论是仅用于动态切片，还是结合静态元素。要全部提及已超出本工作的范围：

Chen 等人 [CX01b] 描述了一种基于静态 SDG 的动态切片算法，该算法提供设置调试器断点所需的信息。静态依赖图被限制为已访问的节点和边，以构建动态依赖图。切片沿图中的所有边进行。

> Tip95 采用了不同的策略：他使用抽象语法树（AST）而不是依赖图并解释程序。该方法与语言无关，但仅适用于自定义构建的语言 'L'。

Zhang 等人提出了一种减少程序跟踪中存储的数据量的另一种方法。他们在执行期间计算动态切片并将其存储在二进制决策图（BDDs）中 [ZGZ04]。

Wang 等人 [WRO04] 提出了一种用于 Java 的动态切片技术，该技术在飞行中压缩跟踪并获得两个到三个数量级的压缩算法。无损压缩在跟踪器捕获的（内存和控制）边序列中寻找高重复模式。他们还提出了一种直接在压缩数据上运行的动态切片算法，可以节省解压缩时间。这样的算法可能不仅适用于指针使用广泛的语言。我们预计我们的变量跟踪的重复模式会产生类似的压缩率。由于切片算法在压缩数据上运行且未使用动态依赖图，因此多次切片请求需要多次使用跟踪，会产生显著的时间开销。

### 6.1 Frontends

目前，SDG 是为 C 和 Java 代码构建的。我们扩展了商业切片系统 CodeSurfer [ART03]，并添加了一个插件来创建与我们图格式兼容的文件。这种方法补充了我们组内之前创建的 Valsoft SDG 生成器 [Kri03a]。将商业产品添加到我们的工具套件中自然使其更加成熟，然而，CodeSurfer 对于非常大的程序被认为是不健全的 [And08]。扩展 CodeSurfer 依赖关系的挑战在于切片构成了路径条件的基础。路径条件需要类似于抽象语法树的细粒度 SDG 结构，但 CodeSurfer 仅支持粗粒度 SDG。然而，CodeSurfer 提供了对控制流图的访问，经过其依赖图的后处理，与 CFG 结合后可得到。

对于 Java，本论文定义了字节码程序的精确表示（第 2 章），我们的生成器反映了这一点。它基于字节码的 Horizon 中间表示，来自 MIT 的 Fx 编译器。该框架在基于 SSA 的表示上运行，并在可能抛出异常的所有指令处插入显式检查，从而保守地建模了由于隐式和显式异常导致控制流。从那里，我们的工具生成细粒度（用于路径条件）和粗粒度（用于所有其他分析）的依赖图。首先，指针分析确定调用图和指向关系，之后为每个方法创建依赖图并合并过程间副作用。最后插入由于这些副作用引起的数据依赖，并可选择计算摘要边。根据请求添加推理依赖（见第 3 章）。

### 6.1.1 Stubs

Harpoon 前端完全支持 Java 1.4 的字节码。我们发现 Java 1.5 可执行字节码的变化很小，对该库的一个小补丁现在允许解析到 1.6 版本的字节码。然而，库是另一个问题。众所周知，对于 JDK 1.4.2，即使是最简单的“Hello world”程序也会加载 248 个类！对于更高版本，库甚至更大，加载的类更多。然而，其中许多类并不会对分析程序的传递依赖产生贡献。例如，特殊区域设置如何确定给定字符的大小写版本并不重要。重要的是 resulting depend 可以通过方法存根建模。存根是占位方法，它模拟原始方法的必要语义，使得所有可能的依赖都被包含到依赖图中。类型系统使用一种简单技术来表示库调用的效果，例如在 Jif 中，库方法需要在语义中进行注释。提供这些注释与为库编写存根一样容易出错（例如 Askarov [AS05] 报告了实验中包含的错误注释）分析需要对库方法进行建模以避免过度的分析成本。

对于我们的分析，我们为 Java 的两个版本创建了原生方法和重要库方法的存根：

- 首先，我们为 JavaCard 2.2 的所有原生方法创建了存根。Card 是针对智能卡等非常受限环境的实现。因此，JavaCard 仅包含 Java 的顺序部分，库已被精简。凭借原生方法的存根以及分析库字节码的能力，我们在第 7 章的实验中包含了用户代码和库代码的所有效果。
- 其次，我们为标准库的核心部分开发了存根。特别是，lang 的效果已包含在我们的存根中，除了动态类加载等非常有问题的构造。此类构造已远远超出本论文的范围，解决方案可参见例如 Livshits 等人 [LWL05]。在某些点我们剪切了调用图的部分，当可以在不加载大量其他库类的情况下包含依赖关系时（见上面的 Locale 示例）。尽管如此，这些存根对原始依赖关系引入了保守的近似，并消除了过度的负担。

> Jif 注释机制需要的第二个原因是它缺乏分析字节码的能力，因此标准库无法被分析。

### 6.2 Analyses based on SDGs

生成的依赖图存储在磁盘上，从那里使用 ANTLR² 语法进行解析，并存储在开源图库 JGraphT 中。¹ 当我们决定使用该库时，作者首先为该库贡献了 Java 5 的泛型，从而为我们的自定义算法提供了类型安全的图（具体来说，节点和边类型无需显式转换）。基于 JGraphT 的 Joana 库提供了切片、切块以及相关分析的长列表算法。特别是，原 Valsoft [Kri03a] 中提出并实现的所有内容都已集成。该核心库构成了随后几乎所有其他库和 Eclipse 插件的基础。
