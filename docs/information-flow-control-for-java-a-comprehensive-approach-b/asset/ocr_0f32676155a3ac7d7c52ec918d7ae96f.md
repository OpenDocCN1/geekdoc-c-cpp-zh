Slicing in the presence of objects and fields is not so different from slicing data types in traditional languages. Horwitz et al. [HPR89] already noticed to extend the concept of data dependence for languages that manipulate heap-allocated storage, it is necessary to phrase its definition in terms of locations rather than variables:

**Definition 2.17** (Data Dependence for Composite Data Structures). Point q has a data dependence on program point p if p writes into a memory location q reads, and there is no intervening write into loc along the execution path by which q is reached from p.

Even Horwitz et al. only considered a List-like operator, it can model more complex data structures. However, with objects and fields, it is not always decide if two program points access the same memory location. Agrawal et al. [ADS93] give a classification of memory accesses into complete, maybe and partial intersection of memory locations: *Complete intersection*, if the objects of both are must-aliases and they access the same field. Intersection for field access is possible due to aliasing; if two references access the same field they are only maybe-aliases, this is called *maybe intersection*. Another case maybe intersection arises with arrays, where the field index is generally unknown at compile time. Arrays combine this maybe intersection with *partial intersection*, as only one element of the array is accessed. Most work on arrays treats arrays as a single location in memory, ignoring the index which is, only known at runtime. We follow this conservative convention by modeling arrays as a field with the reserved name []. Lyle [Lyl84] proposed that array updates should be handled as a reference to and subsequent update of the whole array (modifying decorations). This results in data dependences between array updates a[i] -> a[j] when the first statement reaches the code, even if i may not equal j.
