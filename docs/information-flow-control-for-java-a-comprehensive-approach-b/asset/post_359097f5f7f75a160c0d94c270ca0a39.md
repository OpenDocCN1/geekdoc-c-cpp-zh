**Definition 2.10** (Intraprocedural Backward Slice). The (backward) slice BS(v) of v is defined as the reflexive, transitive closure of v under the predecessor relation in the PDG, denoted as $\to^*$, where the predecessor relation subsumes both kinds of dependence:

```
$BS(v) = \{x \in PDG \mid x \to^* v\}$ (2.1)
```

So slicing the program becomes a simple graph reachability problem, which stems from the tenacity of data and control dependence.

A common variation of slicing is the forward slice, which computes statements that may be influenced by the slicing criterion, as opposed to backward slicing, which determines those statements can influence the criterion:

**Definition 2.11** (Intraprocedural Forward Slice). The forward slice FS(v) of v is defined as the reflexive, transitive closure of v under the successor relation in the PDG, aggregating both kinds of dependence edges:

```
$FS(v) = \{x \in PDG \mid v \to^* x\}$ (2.2)
```

### 2.2.2 Interprocedural Analysis

When analyzing procedural languages, the calling structure of the program must be taken into account. A standard data structure for that purpose is the call graph [Ryd79, CCHIK90, GDDC97], which can be derived from the interprocedural control flow graph.

**Definition 2.12** (interprocedural control flow graph). An interprocedural control flow graph (ICFG) $G = (G_p)_{p \in P}, main, Ret$ for a program P consists of a family $(G_p)_{p \in P}$ of CFGs $G_p = (N_p, Entry_p, Exit_p)$ for procedures $p \in P$, an entry procedure map, and sets of call and return edges $Call$ and $Ret$ that:

1. $(N_p)_{p \in P}$ and $(Edge_p)_{p \in P}$ are pairwise disjoint.
2. If $(u, v) \in Call$, then $u \in N_p \setminus \{Entry_p\}$ and $v = Entry_{p'}$ for some $p, p'$, and there is a matching return edge $(Exit_{p'}, u') \in Ret$ such that $u' \in N_p$ is the only successor to $u$ in $G_p$, $p$ is the caller and $p'$ the callee for that call we say $u$ and $u'$ match each other and call $(u, u')$ a call-return edge.
3. Conversely, every return edge in $Ret$ has a matching call edge in $Call$.

Nodes with calling edges (returning return edges) are called call nodes (return nodes).

In an ICFG, label each edge $(u, Entry_{u'})$ with $\ell_u$ and each return edge $(Exit_{u'}, v)$ with $\ell_v$ where $u'$ is the matching call node for $u'$ and label all-edges with $\perp$. All other edges are labeled according to Definition 2.1.

**Definition 2.13** (interprocedural path [RHISR94, Kri103]). For a path $\pi$ in ICFG, let $EL(\pi)$ denote the concatenation of labels of edges in $\pi$. $\pi$ is balanced iff $EL(\pi)$ is in the language of balanced parentheses generated from nonterminal $M$ by the context-free grammar with these productions $\{M := M ( \ell_u M \ell_v ) \mid \text{true} \mid \mid i MM \mid (u, Entry_{u'}) \in Call \wedge Z\}$

$\pi$ is left balanced iff there paths $\pi_1, \pi_2$ in G such that $\pi = \pi_1\pi_2$ is the concatenation of $\pi_1$ and $EL(\pi_2)$ contains no labels of the form $\ell_v$ and $\perp$. $\pi$ is right balanced iff there are paths $\pi_1, \pi_2$ in G that $\pi = \pi_1\pi_2$ such that $\pi_1$ is left balanced and $EL(\pi_2)$ contains no labels of the form $\ell_u$ and $\perp$ or right balanced.

Note that reliable paths in the ICFG are not closed under concatenation. A common abstraction of the ICFG is the call graph, which models the invocation structure of the program:

**Definition 2.14** (Call Graph). A call graph in our setting is a directed bipartite graph $G = (N_p, N_c)$ consisting of the procedure entry nodes of the program $(N_p = \{v \in N_p \mid v = Entry_p \text{ for some } p \in P\})$ and the call sites of the program $(N_c = \{u \in N_c \mid (u, v) \in E\})$, where the edges $E$ represent:

1. Constraint: An edge $e = Entry_p \to c$ is included in $E$ for each call site $c \in N_c$ that appears in $p \in N_p$.
2. Invocation: An edge $e = c \to Entry_p$ is contained in $E$ for each call site $c \in N_c$ may invoke $p \in N_p$.

This graph effectively represents the interprocedural control flow of the program. It is a static property, each call site has degree of 1. But function pointers or dynamic dispatch make ICFG and graph construction more difficult. We will see later how pointer analysis be leveraged for constructing precise call graphs in the presence of dynamic.

### Slicing Procedure Programs

To slice programs that consist of a set of procedures, Horwitz et al. [HRB90] extended the PDG: The *Dependence Graph* (SDG) models multi-procedure programs using call-by-value parameter semantics. Each procedure is represented by a dependence graph similar to PDG, the *Procedure Dependence Graph*, which is also abbreviated as PDG. It is clear from the context, if PDG represents only a procedure or a whole program. At each call site, the PDG contains an actual-node per parameter of invoked procedure, modeling the assignments of the parameters to temporary variables (this assignment is supposed to take place before the actual call). The called procedure's PDG holds, in analogy, a formal-node for each formal parameter, representing the assignment of the temporary variable to the formal parameter. The edge of the procedure operates this schema is applied: the return parameters are copied to temporary variables in formal-out nodes, and after returning to the caller, those are copied back to variables receiving the values in actual-out nodes. Globally visible variables (e.g. static variables in Java) receive special treatment: they are handled like additional read-write parameters of that procedure and are ignored in the subsequent discussions.

```
main() {
  a=3;
  b=4;
  v=add(a,b);
  w=add(v,b);
}
add(x,y) {
  return x+y;
}
```

The SDG consists of all the PDGs involved in the program connected by interprocedural edges, which are inserted in accordance to the invocation edges of the call graph. An actual parameter node is connected to its corresponding formal-node with an parameter-in edge (pi), formal-out nodes to their actual-out nodes with a parameter-out edge (po). Finally, the node representing a call-site is connected to the entry node of the callee with a call edge (cl).

As an example, consider Figure 2.5, which shows an example program and the corresponding SDG. The straight edges in blue represent dependence, the curved edges in green data dependence. Interprocedural edges are shown as dashed edges. The call edges from nodes 4 and 5 to the entry of procedure add, parameter-in edges from variables a and v to x, parameter-out edges from the return statement in node 8 to the variables v and w.

While this representation does allow program slicing, the slice according to equation 2.1 is correct but not context-sensitive due to the calling-context problem: a slice may enter a callee by a parameter-out edge but leave it towards different procedure using a parameter-in edge towards a different call-site, so this kind of slicing is called context-insensitive.

When slicing the example program in Figure 2.5, the context-insensitive backward slice of node v from call site 4 is shown in Figure 2.5 as shaded nodes. However, a dataflow from in-parameters of statement 5 to the slicing criterion is infeasible in any program execution, because statement executes no other statement 4.

The SDG makes all side-effects visible, the actual parameters of any call-site can be (transitively) dependent on actual-in parameters of the same call-site. This inspiration of so-called summary edges [HRB90] enrich the SDG. Summary edges are inserted between actual-in and actual-out nodes of the call-site, if there exists a path in the callee between corresponding formal parameters. These edges represent interprocedural summary information of dependences between procedure parameters and thus allow preservation of the calling context.

In our example in Figure 2.5, there are four summary edges in red and dashed: from a and b of call site 4 to v, and from v and b of call site 5 to v. These correspond to the transitive dependences between the formal parameters x y and the statement in node 8.

With summary edges, context-sensitive slicing becomes a two-phase algorithm which is still in O(SDG). The first phase traverses all edges (including summary edges) except for formal-out edges. Thus all dependences of slicing's procedure and its transitive closures are included. The second phase starts at all formal-out nodes and traverses all edges but call and parameter-in edges, thus omitting all callers (whose effects have already been included because of the summary edges). The context-sensitive slice is the union of nodes encountered in both phases.

The result of the context-sensitive two-phase algorithm for the program in Figure 2.5 is shown in Figure 2.6. It traverses the summary edges to a and b from there the nodes 2, 3, and 4 (gray nodes). The second phase starts with node 8 which has been omitted from the formal-out edge to v and includes the nodes y and the entry of add (depicted in light gray). Note that the nodes at call site 5 are not correctly included in the context-sensitive slice (Figure 2.5).

### Computing Summary Information

Summary edges have been proposed by Horwitz et al. [HRB90] as a means to allow context-sensitive slicing in linear time in the size of the dependence graph. Their algorithm to compute these edges based on attribute graphs, however, is asymptotically slower than an alternative algorithm presented by Reps et al. [HRSR94]. An optimization of this latter algorithm, which trades space for time in the map fragmentPath, is presented in Algorithm 2. Its worst case complexity is in O(n⁵) where n is the size of the dependence graph. After summary edges have been computed, each slice can be determined in linear time.
