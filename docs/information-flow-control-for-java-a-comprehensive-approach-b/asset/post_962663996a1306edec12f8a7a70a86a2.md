## 3.2 Slicing Concurrent Java

The JMM defines the inter-thread semantics for accessing shared variables and therefore forms the basis for intra-thread slicing. The program order rule's intra-thread semantics effectively requires that program transformations adhere to the topological ordering imposed by data and control dependencies (see definitions in this chapter). Statements that are not ordered by these dependencies can safely be reordered⁵. Therefore, a more precise and control dependence analysis may enable more aggressive compiler optimizations. Additionally, the memory model requires that values written to shared variables in other threads are ordered by happens-before. The SDG needs to be extended to a concurrent system dependence graph (cSDG), a representation of concurrent programs where threads communicate via shared variables. These communications are represented as a special kind of dependence for shared variables that is traditionally called interference-dependence. The most basic form requires that the involved accesses are conflicting:

**Definition 3.1 (Interference Dependence).** A node $m$ is interference dependent [Kri98, HCD+99] on node $n$ ($n \to m$), if

- 1. there is a variable $v$, such that $v \in Def(n)$ and $v \in Ref(m)$,
- 2. $n$ and $m$ must execute in different threads at runtime $\theta(n) \neq \theta(m)$, where a map $\theta$ maps a CFG node $n$ to a thread identifier to which $n$ belongs.

This definition is very conservative and will be shown in the subsequent sections, how to refine this to prune many of the spurious cases that previous approaches [HCD+99, Za99, RH04] suffer from.

Thread violation is traditionally modeled in analogy to procedure calls, if fork sites are connected via fork edges to the corresponding run() methods. As Java only supports thread invocation via calling Thread.start(), spawning a new thread executing its run() method and do not have explicit parameters, a fork site can only have one parameter for this pointer, as well as symmetric parameters for static variables. This parameter passing is modeled as for edges, in analogy to parameter-in-edges of method invocations. Changes in parameters are already modeled with interference⁷, so parameter-out edges are not ordered.

As an example, consider Figure 3.1, where a program fragment is depicted alongside its cSDG. The variables $x$ and $y$ are global, and thus as extra parameters at the thread's fork point. Note the fork edge between nodes 4 and 10 and the fork-edges between nodes 5 and 11, and 6 and 12. Node 15 defines the shared variable $x$, which is used at node 7 in the main thread, therefore an interference dependence is included from 15 to 7. The same goes for nodes 9 and 13, where the shared variable is redefined.

### 3.2.1 Undecidability of Slicing

Precise slicing is undecidable in general. Several undecidability results have impact on the slicing technique for concurrent programs:

- 1. Whether a condition becomes true or false in the run of a program cannot be statically decided. To circumvent this, one generally assumes non-deterministic choice at conditionals during static analysis, the consequence that every path in the interprocedural CFG is assumed to be feasible (see chapter 2, page 23).
- 2. Precise slicing of languages with respect to synchronization and recursion is undecidable [Ram00].
- 3. In combination with interference dependence, data dependence is no longer transitive [MOS01], rendering parallel interprocedural slicing undecidable altogether.

In the following, we will present another source of undecidability: Precise interprocedural slicing [Kri98] in combination with dynamic thread creation is undecidable.

To illustrate the results (2) and (3), consider Figure 3.2, which shows small example programs. The program on the left demonstrates how synchronization can induce an order on the execution sequence: first a is set to 1, after the other thread can proceed and will kill the first definition assigning to 0. So the difference between a:=1 and write(a) could be removed.

In the example right (taken from [MOS01]), the value of write(c) will not have influence on any possible execution sequence. The statement in the right might either be scheduled before b:=0 or after. If it executes, then c will be redefined in the first thread before the join. If not, b will already be redefined to 0, and thus independent from the value of a.

### 3.2.2 Dynamic Thread Creation

Threads in Java are in contrast to previous languages like Ada totally dynamic. In static detection of the number of threads running in a program's execution is undecidable. A thread can be created by any other object calling java.lang.Thread constructors, and a subsequent invocation of its start() method will create a new thread of execution in the operating system executing its run() method. All this may happen in loops or recursion, so there is no static bound on the number of threads.

When a language offers threads that can be created and destroyed dynamically, and when thread creation may occur in a control flow cycle gets another source of undecidability even if the language offers no precisely. In this case, the undecidability result from intraprocedural slicing causes another undecidability. One cannot determine, or how. One cannot determine, or how many threads will be created.
