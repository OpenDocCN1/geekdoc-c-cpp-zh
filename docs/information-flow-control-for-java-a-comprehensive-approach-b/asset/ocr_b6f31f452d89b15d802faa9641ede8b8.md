# 6.1.1 Stubs

The Harpoon frontend full bytecode for Java up to version 1.4. We found that the changes in executable bytecode for Java 1.5 were marginal, that a small patch to that library now allows parse bytecode to version 1.6. However, the library is another issue. It is well known that of JDK 1.4.2, even the simplest "Hello world" program loads 248 classes! And for versions the library is even bigger and more classes are loaded. Yet, many of these do not contribute to the transitive dependencies of the analyzed program. For example, it does matter how a special locale determines the upper and lower case versions for a given character. What matters is the resulting depend can be modeled via method stubs. A stub is a placeholder method that models the necessary semantics of the original method that all possible dependencies are included into the dependency graph. Type systems use a simple technique to represent the effects of library calls, e.g. in Jif, library methods need to be annotated in semantics. Providing these annotations is equally error-prone as writing stubs for libraries (e.g. Askarov [AS05] reports a false annotation included in experiments) analyses need to model library methods to avoid excessive analysis cost.

For our analyses, we created stubs for native methods and important library methods for two versions of Java:

+   - First, we created stubs for all native methods of JavaCard 2.2. Card is an implementation for very restrictive environments like smartcards. Therefore, JavaCard contains only the sequential parts of Java and the library has been pruned. With the stubs for native methods and the ability to analyze the bytecode of the library, our experiments in chapter 7 include all effects of user and library code.
- Second, we developed stubs for the essential parts of the standard library. In particular, the effects of lang are included in our stubs except for very problematic constructs like dynamic class loading. Such constructs are well beyond the scope of this thesis, solutions can be found e.g. in Livshits et al. [LWL05]. At certain points we cut parts of the call graph, when dependencies can be included without loading a myriad of other library classes (see the Locale example above). Still, these stubs induce conservative approximations of the original dependencies and remove excessive burden.

> A second reason for the need of Jif's annotation mechanism is that it lacks the ability to analyze bytecode, therefore the standard library cannot be analyzed.
