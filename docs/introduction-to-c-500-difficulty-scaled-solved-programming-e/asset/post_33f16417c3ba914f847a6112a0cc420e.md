C++ also introduces the =default syntax. This syntax is used when we want to explicitly state that a default function will be used. For example:

```cpp
class T
{
    T() = default;
    T(const T&) = default;
};
```

Some may prefer this syntax to make it clear which default functions will be used. Note that if you want not to delete, because their absence implies that they are going away, an empty default constructor it is better to prefer the =default syntax over the empty {} (e.g., T{}) for technical reasons, which are beyond the scope of our discussion to analyze.
The =default syntax may be useful when we want to use a default function which due to other conditions is not automatically created. For, if we declare a move constructor, then the default constructor, the copy constructor, and the copy function are not provided. In that case, we can use this syntax to explicitly declare the default functions we need:

```cpp
class T
{
    T(T&&);
    T() = default;
    T(const T&) = default;
    T& operator=(const T&) = default;
};
```

If we do not declare the corresponding default functions, each of the following declarations causes a compilation error:

```cpp
T t1;
T t2(t1);
t1 = t2;
```

With the =default syntax, the compiler provides the corresponding default functions and the declarations are compiled successfully.

# FRIEND CLASSES

As a function can be friend to a class, a class can be friend to another class. The functions of the friend class may access all the members of the class. An example of using a friend class is when we have two classes and we want one to control the operation of the other. For example, I once had to implement an IP network management application. I decided to develop a centralized management system, where the Net_Mgt class represents the network administrator, while the System class represents each system (e.g., computer). Because I wanted the Net_Mgt class to have access to the private members of System, I declared Net_Mgt as friend to System. In the following example, the Net_Mgt provides two functions that set the type and the IP address of the managed system.

```cpp
#include <iostream> // Example 19.9
#include <string>
using std::cout;
using std::string;

class System {
private:
    int type;
    string ip_addr;
public:
    friend class Net_Mgt; /* The Net_Mgt class is declared as friend to System */
    enum {PC, Switch, Router};
    void show() const { cout << "T:" << "IP:" << ip_addr << '\n'; }
};
```

```cpp
class Net_Mgt {
    void set_type(System& s, int type);
    void set_IP(System& s, const string& addr) {s.ip_addr = addr};
    void show(System& s) const;
};
```

```cpp
void Net_Mgt::set_type(System& s, int type)
{
    s.type = type; /* The Net_Mgt class can access the private members of the System class. */
}
```

```cpp
void Net_Mgt::show(System& s) const
{
    s.show();
}
```

```cpp
int main()
{
    System s;
    Net_Mgt mgt;

    mgt.set_type(s, System::PC);
    mgt.set_IP(s, "192.168.1.2");
    mgt.show();
    return 0;
}
```

Because the functions of the Net_Mgt class refer to members of the System class, I first declare System so that the compiler has the information it needs to process the program. In order for a class to become friend to another, we must declare it with the prefix friend. The position does not matter, it can be declared in the private, protected or public section. Because Net_Mgt has been declared friend of System, it may access its private members. That is, if we omit the friend in the declaration of Net_Mgt the compiler will not compile with s.type = type; s.IP_addr = addr; Also, do not forget, although Net_Mgt is declared within System, it is not in his case. When you make set_IP() inline and the others, I could make all inline. I'll tell you why I did that in the next section. The program displays T:0 and IP:192.168.1.2.

The purpose of this example is not to show how to use a friend class, but also to show an example where it uses flexibility in design. One could say, make System public so we don't need to use a friend class. Yes, we could lose the safety of data all the members would be accessible from the outside world. Another could, add a Net_Mgt object in System, which manages that particular system. In this case, we'd have one-to-one relationship, that is, one Net_Mgt object for each System object. By declaring Net_Mgt as friend and passing a System object as argument to its functions, a single Net_Mgt object can manage all systems, and then we can implement a centralized management model. As you see, in a real application, a network administrator can configure more than just an IP.

Two classes must become mutually friend. If example:

```cpp
class Net_Mgt
{
    friend class System;
};
```

The System class becomes friend of Net_Mgt. Note that the friendship is not transitive. That is, if the System class has its own functions, these functions don't have special access to Net_Mgt. In general, friend classes should associate independent entities that are closely related. In our example, Net_Mgt entity is not a System entity and vice versa, so the model does not apply. Similarly, may not be declared as part of the other, so it wouldn't fit to declare either side. The fact that Net_Mgt controls the state of the System leads to the right choice, to make Net_Mgt friend to the System class. When you choose a class to become friend to another you need to be careful as all the functions of the friend class will have access to its data. Someone might ask, can we declare some of the functions of a class and not the entire class? Yes as we'll see in the next section.

# Friend Member Functions

If we do not want to make the entire class, we can select which functions to make friend. For example, let's make only the set_IP() friend:

```cpp
class System
{
    friend void Net_Mgt::set_IP(System& s, const string& addr); /* Only set_IP() is declared as a friend function */
};
```

As shown, to declare the friend function we need to specify the class in which it belongs. However, this declaration requires a restructuring of the code. Let's see why. In order for the compiler to process this declaration, it must meet the declaration of Net_Mgt to be aware of its existence and presence of set_IP(). So, we need to include Net_Mgt before System. But if we do, the compiler won't have the declaration of System and won't be able to process the Net_Mgt functions that take a System object as argument. Fine, and how do we overcome this circular dependency? As in example C13.6, by adding a forward declaration of System. The code is restructured as follows:

```cpp
class System; // Forward declaration (incomplete declaration)
class Net_Mgt { ... };
class System { ... };
```

There is one problem: When the compiler encounters the inline definition of set_IP() in Net_Mgt it will display an error message because it does not know anything about the System class and the members it contains, it cannot compile. This is why I chose to make set_IP() inline. So, if something happens to you, show how to solve this problem. The solution is to place the declarations in the Net_Mgt class and their definitions after the declaration of System. And if you want to make inline just add the word inline in their definition. Thus, the code is restructured as follows:

```cpp
class System; // Forward declaration
class Net_Mgt { ... }; // Function declarations.
class System { ... };
// Definitions of Net_Mgt functions.
```

Now, when the compiler encounters the function declarations in Net_Mgt it won't complain, because it is informed from the forward declaration that the System is a class. Then, when it encounters their definitions it can compile them, because the System has already been declared. Note that even after these changes the program won't compile, because set_type() is no longer friend. Therefore, because the type is a private member, the statement s.type = type; is not acceptable.

# NESTED CLASSES

A class can be declared within another class. Such a class is called nested. The typical reason to use nested classes is to group together classes that are only used in one place and describe the entity in a more compact form. For example, in an application that manages a company we could declare the Company class and within nested classes for each department of the company. Consider the following program, where the Mgt_Dpt class is declared inside the Company class:

```cpp
#include <iostream> // Example 19.10
class Company {
public:
    class Mgt_Dpt {
        private:
            int code;
        public:
            Mgt_Dpt(int c, int e) : code(c), empl(e) {}
            int empl;
        void show() const;
    };
}
```
