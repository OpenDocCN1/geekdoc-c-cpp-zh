Now that we've discussed classes we can more easily understand the difference between the object-oriented philosophy and the procedural programming. Let's look at the difference with C. C does not support the concept of the class, the closest concept is the structure. However, a struct is not allowed to contain functions. Therefore, the programmer must define external functions, in order to manipulate its data. Thus, the functions are scattered in the program and do not form a single unit that we can easily understand and control. Also, the user of the structure has access to all of its data, since C does not support the concept of data hiding. In contrast, C++ encapsulates data and functions that handle this data in the same type. Thus, a class unifies the description of an abstract entity and represents it.

To understand the difference between the two approaches, consider the C-list implementation. As you will see, several variables and functions that anyone may define to represent the functionality of the list. This is also an example of procedural programming. The emphasis is on the definition of functions to process the data. In the object-oriented approach, the emphasis is on the definition of a class type to process the data. For example, we may define the List type to represent the list and put inside there all variables and functions to manage it. Now, the code becomes more representative, as easy to read, write, and be maintained.

```
class List {
    Node *head;
    Node *tail;
n    void add_list(const Node *p);
    void add_list(const Node *p, int code);
    void show_list();
};
```

The list data are encapsulated inside the List type and it is the programmer's responsibility to access the data.

To up, in the public section we place the functions that the user of the class can use in order to communicate with the class, while in the private/protected section we place the functions that implement the functionality of the class. In other words, to use a class, you need to know its public interface; not its private interface. As we'll see in Chapter 20, the decision to make a protected member depends on whether we want to allow direct access to it from within a derived class. If we do, we protect it; otherwise we make it private. We'll see some simple examples of class design in this book's exercises.
