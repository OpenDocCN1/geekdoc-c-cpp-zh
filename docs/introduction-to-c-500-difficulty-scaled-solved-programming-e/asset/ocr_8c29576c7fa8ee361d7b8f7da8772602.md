As with new and new[], the use of delete and delete[] causes the operator functions to be called. For example, let's look at their simple versions:

```
void operator delete (*ptr);
void operator delete(void *ptr);
```

For example, the statement delete p causes the call of delete(p). As we'll see in Chapter 17, if p points to memory that is allocated with new for an object (Student) the destructor of that object is called, if it points to memory that is allocated with new[] for many objects, delete[] p causes the destructor of each element object starting from the last. That is, the last element is destroyed, then the last one, until the first one.

Note that memory can be dynamically allocated in one function and returned in another, provided that the second function has access to that (e.g., through a returned pointer). However, as we will next, allocating memory in one place, moving around the pointer, and release the memory in another place complicates the management of memory and also is a potential source of a memory leak or bug since we can forget to release the memory or release it more than once. We should try to allocate and release memory in the same function.

As mentioned, in large programs where the same pointer can be used in different parts of the program, my advice for more safety and control of the program is to assign nullptr value when you release the memory. Here is an example, of what happened to me once.

One time, I used an array of some pointers to classes. I initialized it with nullptr and memory was allocated for some of their during program execution. So, far so good. In a while, memory was released in random order. That, the program was crashing. And the worst part, the program was crashing occasionally, not always. That's the programmer's nightmare, random failures. After days of stress and debugging, I concluded that the crash was due to some pointer misuse... what? Here is the buggy code:

```
if(arr[i] != nullptr)
 x = arr[i]->field;
```

The if condition didn't let a pointer to access the member field of the class. That's fine, but what about a pointer wanted to use a pointer to memory and memory is later released? Such a pointer is usually calling a dangling pointer in the sense that it once pointed to a memory that has now been released. For example, suppose that the memory pointed to by arr[i] is released does not mean that arr[i] becomes null pointer; it is still true, because the fact that the memory is released does not. When using arr[i] to access the member field, the if condition was true and the program was crashing. By setting arr[i] = nullptr, after releasing the memory, the problem was solved and we went for free. Cheers!

Of course, things could be worse. For example, besides arr[i] use another pointer (e.g., q[j]) pointing to the same object. That is, another point in the program to have:

```
if(q[j] != nullptr)
 x = q[j]->field;
```

Making arr[i] equal to nullptr has no effect on q[j]. Thus, I'd have to search in the code to find the right matches of arr[i] and q[j] pairs and make q[j] equal to nullptr as well. Nightmare, I do not want to think about it. If I had smart pointers of C++11 at my disposal, I would have used them and avoid such many dangerous situations.
