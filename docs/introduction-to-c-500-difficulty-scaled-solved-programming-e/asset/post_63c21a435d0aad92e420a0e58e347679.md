## One Header File

A simple way to organize a program consisting of many files is to place the definitions (e.g., functions, classes, ...) in the code files where they are used and all the declarations in a single header file. This header file is included in each code file. By convention, the extension of the header file is .h. Yes, for a small-size program, this approach might be convenient, since we've have only one place to search for declarations and edit. However, it is not an efficient approach for large programs. One reason is that every time contents change all the code files have to be re-compiled, which is time consuming for a large application. Also, changes in this file by many programmers are a source of risk for potential errors. And of course, its large size makes such difficult tasks as to read it, use it, understand, and maintain.

## Many Header Files

An alternative approach is each code file to have its own header file. The header file facilitates one who reads to get quickly what part of the code file implements and the services it provides. In large programs where organizing files is the best way, it is very helpful for the control, understanding, and maintenance of the program services that the code file provides to be split into many one header files. If there is a change in one header file, only the code that include it are compiled again.

The declarations are placed in the header file and the definitions in the respective code files. Common information used in more than one code file having a common header is what we need to make when we do not need to change in different files to make change, we do it in one place. For example, the declaration of a class used in many code files is placed in a header file, which is included in any code file that uses it. The functions of the class can be defined in the code files that use them in the same way as we have a single code file, that is, with the class name and the :: operator.

## APPLICATION EXAMPLE

Because in my experience I was deeply involved with the development of network protocols, I decided to implement a simple protocol to show you an example of a large application. The purpose of the program is not to understand the details of the implementation, but to get an idea of the object-oriented design approach and how the different programs communicate. Also, if you ever need to get involved with the area of communication protocols, this example might help you start.

At first, what is a network protocol? Simply put, it is a set of rules that enables system communication. A protocol may be implemented in hardware, software, or both. Typically, its operation is based on the standard defined by an international organization. A protocol example is the famous Internet Protocol (IP). It is specified by the IETF organization in RFC 791. A protocol standard specifies, among others, the information exchanged between systems, the format of the exchanging messages, significance, and the message handling protocols. Typically, the guideline for the implementation of a protocol is a finite-state machine that models the protocol operation in states and events.

Let's describe the protocol we are going to implement. It is an oversimplified version of the ITU-T Q.91 protocol designed for the establishment, maintenance, and release of calls in an ISDN network. When the calling user dials the number of the called user a message SETUP. The SETUP message is routed through the ISDN network to reach the called user. If the called accepts the call (e.g., picks up the phone) a message CONNECT is transmitted back to the calling user. The called user responds with CONNECT_ACK and the call establishment procedure ends. A circuit is reserved along the path between the two parties to serve the data transfer. Now, the two parties can communicate. If either party closes the connection (e.g., hangs up), a message named RELEASE is transmitted to the other party and the circuit is released.

The application provides a menu of choices and simulates the message exchange between the two parties to establish and release calls. Each message is identified by a unique code and specific information. For example, the code of the SETUP message is 5 and it contains several information elements, such as the phone number of the calling user. Having the object-oriented philosophy in mind, we represent each call by an object. Each call is identified by a unique number, which is named CRV (Reference Value). For simplicity, let's assume that each message contains only its code and the CRV.

The usual choice for the file that contains main() is the name of the application, example, prctl.cpp. We split the functionality of the program into several modules. Each of the following source files represents a module:

- prctl.cpp: It contains functions which interfaces the interface with the upper and lower layer. It parses and forwards the messages it receives to the fsm.cpp. The concept of layers is described in Open Systems Interconnection (OSI) model, a reference model which describes how an application that runs in system A can communicate, through a network, with another application than runs in system B. A layer may be implemented in software or hardware. For example, the lower layer might be the driver of the network card or the card itself, the upper layer might be an application which provides the means to communicate with another system (e.g., web browser). In our program, the upper layer is a simple console application which provides a menu of choices to the user.

- fsm.cpp: It contains the function which implements the protocol finite state machine. Each call is in a state. For example, when the SETUP message is sent (i.e., to establish the call), the call goes to the INIT state. In this state, the CONNECT message (sent by the user) is received, the call goes to the ACTIVE state, which means that the call is established. When the RELEASE message is sent, the call is released.
