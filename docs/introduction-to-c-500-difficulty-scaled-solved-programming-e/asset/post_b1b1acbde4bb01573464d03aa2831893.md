Now that we've discussed classes we can more easily understand the difference between the object-oriented philosophy and the procedural programming. Let's look at the difference with C. C does not support the concept of the class, the closest concept is the structure. However, a struct is not allowed to contain functions. Therefore, the programmer must define external functions, in order to manipulate its data. Thus, the functions are scattered in the program and do not form a single unit that we can easily understand and control. Also, the user of the structure has access to all of its data, since C does not support the concept of data hiding. In contrast, C++ encapsulates data and functions that handle this data in the same type. Thus, a class unifies the description of an abstract entity and represents it.

To understand the difference between the two approaches, consider the C-list implementation. As you will see, several variables and functions that anyone may define to represent the functionality of the list. This is also an example of procedural programming. The emphasis is on the definition of functions to process the data. In the object-oriented approach, the emphasis is on the definition of a class type to process the data. For example, we may define the List type to represent the list and put inside there all variables and functions to manage it. Now, the code becomes more representative, as easy to read, write, and be maintained.

```cpp
class List {
    Node *head;
    Node *tail;
    void add_list(const Node *p);
    void add_list(const Node *p, int code);
    void show_list();
};
```

The list data are encapsulated inside the List type and it is the programmer's responsibility to access the data.

To up, in the public section we place the functions that the user of the class can use in order to communicate with the class, while in the private/protected section we place the functions that implement the functionality of the class. In other words, to use a class, you need to know its public interface; not its private interface. As we'll see in Chapter 20, the decision to make a protected member depends on whether we want to allow direct access to it from within a derived class. If we do, we protect it; otherwise we make it private. We'll see some simple examples of class design in this book's exercises. I really think that the ability of data encapsulation and data hiding in the same type was a great idea, a very important feature of C++ and object-oriented programming in general.

Wait a minute; we're not done yet. I do not want to create the false impression that the class design is a quick easy task, just decide about the operations you want to support, choose the private, protected and public members and you are done. Even this is a difficult decision. For example, wouldn't be safer and easier in order to control the class to have no public members at all and to have set()/get() public functions to access the class data? Much worse, think about creators. When providing a class to the outside world (e.g., string) you must ensure that the protection of the class, as well as protected in the case of a derived class, is functional and won't change or over. Any changes the developer of the class makes to the design should be related to the implementation code, not the public interface. Imagine that the programmers who already use the class be forced to change their code often because of a new version of the class that the public functions changed or some public members were removed.

Also, when designing a class, besides its operations, you have to decide on many of its features, such as what would be the valid values of its (e.g., in a Time class, the valid range for the hour member is 0-24), if the class would overload operators, if it'd be used as a base class, if it would contain virtual functions, if you use the default functions or others you specify, if it'd allow conversion from/to another, and many more "ifs". Who said the design is an easy job?

## Structures/Unions and Classes

The concept of structure and how to use variables is very similar to the class and objects. Indeed, the difference is that the members of a class are private by default, while the members of a structure are public by default. A similar difference, as we will see in Chapter 19, is that a derived class inherits a base class with private access, while a derived structure has public access. Since there is no fundamental difference between them, someone might ask, couldn't we have one type, struct and class, and just change the default access if needed? Why not? Reasonable to wonder, I'm not sure about the answer. I imagine that in the beginning, the struct type was pre-existing in C and because object-oriented features were new programming concepts that had not yet spread, Stroustrup would like to introduce a new type in C++ with focus on object-oriented operations. Then, it was decided that the struct type would also support object-oriented operations.

The common practice is to use a class when both variables and functions are needed to represent an entity, while the structure is used when only variables are required. Also, if the members are public only, the structure is usually chosen, while if there are private members all, the class is chosen.

Regarding unions, we know from Chapter 13, only one of its members has a valid value. As with structure, the members of a union are public by default. A union supports the properties of the class, but not all. For example, a union may contain public, private, and protected sections. It can also contain member functions including constructors and destructors. However, a union cannot be used as a base class, nor can it inherit another class. Therefore, it cannot contain virtual functions.

## const Member Functions

In our first example C.17.1, the show() function can change the values of the object that it calls. For

```cpp
void Student::show()
{
    grd = 2;
}
```

and write s.show(); the value of grd of the s object becomes 2. If we don't want a function to be able change the values of invoking object we add the const keyword at the end of its declaration. The const keyword must also be added in its definition. For example, the declaration of the show() comes

void show() const; and its definition:

```cpp
void Student::show() const
{
    grd = 2; // Wrong.
}
```

If show() attempts to change the value of a member, such as grd, the compiler will display an error message for illegal action.

> For better control of the class operation, it'd be better to declare functions that do not change the values of its members as const.

Inside a const function we can call const member function, but it is an error to call non-const function. This makes sense because the non-const function may modify the object, which removes the const protection. For example:

```cpp
void Student::show() const
{
    set(5); // Wrong.
}
```

Now, suppose that we add the following member function:

```cpp
float& Student::get() const {return grd;} // Wrong.
```

Is it correct? No, the compiler will not let you do. You cannot return a reference or pointer to a class member. Within a const function, every data becomes const so that it cannot be modified. The reference must be const:

```cpp
const float& Student::get() const {return grd;} // Fine.
```

For example, if you were allowed to return a non-const reference, then you could violate the constness of a const object, then to alter an object that must not be modified. For example, to write such like this:

```cpp
const Student s;
s.get() = 10; // The value of s.grd becomes 10.
```

Therefore, the compiler in order to preserve the constness does not allow us to return non-const references to member variables from const functions.
