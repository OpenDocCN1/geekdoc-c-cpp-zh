When the function is called, the common memory pointed to s and t.s will be released, so it'd be wrong to use t.s to re-allocate new memory and copy something that no longer exists. How can we fix this problem? Before answering, someone might ask, what is the point of making an assignment in the first place? Yes you right, this self-assignment does not make sense, but in their copy could be two pointers (e.g., *p1 = *p2) that you have no clue if they point to the same object. The traditional way is to check for self-assignment before releasing the memory:

```
T&::operator=(const T& t)
{
  if(this == &t) // We check for self-assignment (e.g., t1 = t1).
    return *this;
}
```

> Don't forget to test for self-assignment when overloading the copy assignment operator. If you forget to that, fatal errors may occur if an object is accidentally assigned to itself.

The if condition compares the address of the invoking object to check if the referenced object is itself. If the addresses are the same, could it not be just void? Yes, it could, but then, why could we not use += in expressions, as t1 = t2; is translated to t1.operator=(t2); Because = operator has right-to-left associativity, this statement is translated to: t1.operator(operator=(t3)); When t2.operator=(t3) is called, the memory pointed to t2.s is first released, new memory is reserved for t2.s and the string pointed by t3.s is copied to it. The function returns the reference to t2, which becomes the next argument. Thus, t1.operator=(t2) is now called. Similarly, t2.s is copied to t1.s. Okay, you might find difficult to understand the above now, we'll analyze a similar expression in the next (e.g. count r1 = r2); and you will get it. If you do not want to support chained assignments, you declare void and you are done. The usual practice is to return a reference in order to support them.
