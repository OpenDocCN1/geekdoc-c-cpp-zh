### 3.2.5 Loop interchange

Loop interchange is the next compiler optimization, and matrix multiplication is the example we use to bring it out. In our discussion of matrix multiplication and loop interchanging, the following points emerge:

- One should use restrict pointers as far as possible. The restrict pointers can speed up a program by more than a factor of 2.
- It is best to present loops to compilers in a simple and transparent form.
- Although AVX2-capable machines are faster than SSE2-capable machines, AVX2 code is a bigger struggle for a compiler.
- Therefore, much of the advertised advantage of AVX2 over SSE2 machine may not be realized.
- Compilers are capricious, and no assumptions about the generated assembly code can be made without inspecting it.
- Optimizing for the instruction pipeline can yield far greater speedups on recent processors than on earlier ones.

Some of these points have come lately. Many of these points are much broader in scope than any particular optimization. Before we begin, we make some remarks about the peak capabilities of SSE2 and AVX2-capable machines. As shown in table 3.1, SSE2 provides XMM registers enough to hold two doubles.

| dim=1000 | dim=2000 | dim=1000 | dim=2000 |
| :--- | :--- | :--- | :--- |
| (SSE2) | (SSE2) | (AVX2) | (AVX2) |
| multijk() | 0.37 | 0.22 | 0.62 | 0.46 |

| multIJKX() | 1.72 | 1.62 | 1.31 | 1.21 |
| MKL BLAS | 3.81 | 3.84 | 14.0 | 14.6 |

Table 3.3: Floating point operations per cycle in the multiplication of square matrices.

The mulpd (or vmulpd) instruction applied to XMM registers carries out two multiplications in a single cycle. Similarly, the addp (or vaddpd) instruction carries out two additions in a single cycle. Typical SSE2 processors can simultaneously issue an addp and mulpd to separate execution units in the same cycle. Therefore, the peak capability of a single SSE2 processor is 4 flops (floating point operations) per cycle. The AVX2 processor has YMM registers, which are twice as wide as XMM. In addition, it has the faddpd instruction, which does a fused multiply-add of the type c = a+b on the entire width of YMM registers. A single faddpd instruction is equal to 8 flops. The AVX2 processor can issue two of these instructions to separate execution units in the same cycle. Therefore, the peak capability of a single AVX2 processor is 16 flops per cycle. Some Intel processors accelerate the clock. For such machines, the actual theoretical limit can be slightly greater the bounds derived above. Neither the 2.6 GHz SSE2 machine nor the 3.6 GHz AVX2 machine features core acceleration.

All the points we wish to make in this section emerge from table 3.3. One of the points is so glaring that we will begin by commenting on it. The point is that matrix multiplication is much faster using Intel's MKL library. On SSE2, MKL is more than twice as fast as functions such as multijk() and multIJK() that we write in C++. The programs that we write are in C++ and are not optimized for the instruction pipeline. MKL's optimization for the instruction pipeline, which must be coded in assembly, yields a far greater speedup of more than a factor of 10 on AVX2 machines. In both cases, MKL comes close to the peak point throughput, while the C/C++ programs fall short. In fact, the C/C++ programs do better in SSE2 than AVX2, although the peak capability of the recent AVX2 architecture is four times as high.

We step through four simple implementations of matrix multiplications. These are the sort of C/C++ programs one may be expected to write. For each implementation, we explain how the compiler views the program and what it does with it. The sort of optimizations that yield the amazing speed of MKL BLAS is discussed in section 3.3.

(i,j)th entry of the square matrix a is a[i+j*dim] (we assume that the leading dimension is equal to dim). Here is a double * and points to the first location of the contiguous segment of memory where the dim*dim entries of the matrix are stored. we assume that matrices are stored columnwise.

The function multijk() defined below multiplies a and b and adds their product to the matrix c.

```c
void multijk(double *a, double *b, double *c, int dim) {
  for(int i=0; i < dim; i++)
    for(int j=0; j < dim; j++)
      for(int k=0; k < dim; k++)
        c[i+j*dim] += a[i+j*dim]*b[k+j*dim];
}
```

None of the pointers is marked as restrict. Thus, the arrays a, b, and c could be indexed to point to the same location, and the compiler has to preserve semantics in the event of such aliasing. There is no room for the compiler to apply loop transformations.

On both SSE2 and AVX2, the compiler-generated assembly code (not shown) closely follows the C code of multijk(). There is no dramatic code transformation. From table 3.3, we see that AVX2 is nearly twice as fast as multijk(). That speedup is easily explained. On both SSE2 and AVX2, the compiler generates only single double instructions, and nothing more can be expected. On SSE, the single double instructions are vaddsd vmulsd. On AVX2, they are fmaddpd. The speedup of two results because the fused-multiply-add combines addition and multiplication into a single instruction.

Next we make a slight change to the matrix multiplication program.

```c
void multijkx(double *a, double *b, double *c, int dim) {
  for(int i=0; i < dim; i++)
    for(int j=0; j < dim; j++) {
      double x = c[i*dim];
      for(int k=0; k < dim; k++)
        x += a[i+j*dim]*b[k+j*dim];
      c[i+j*dim] = x;
    }
}
```

This program does not use restrict. However, the innermost loop makes it accumulate its computation in a variable x. From table 3.3, we see that the optimization is better on SSE2 and AVX2 for dimension 1000 and 2000, although the improvement is minor.

The programs below are exactly the same except all pointers are restrict qualified.

```c
void multJK(double *restrict a, double *restrict b, double *restrict c, int dim) {
  for(int i=0; i < dim; i++)
    for(int j=0; j < dim; j++) {
      double x = c[i*dim];
      for(int k=0; k < dim; k++)
        x += a[i+j*dim]*b[k+j*dim];
      c[i*dim] = x;
    }
}
```

```c
void multJKX(double *restrict a, double *restrict b, double *restrict c, int dim) {
  for(int i=0; i < dim; i++)
    for(int j=0; j < dim; j++) {
      double x = c[i*dim];
      for(int k=0; k < dim; k++)
        x += a[i+k*dim]*b[k+j*dim];
      c[i*dim] = x;
    }
}
```

These programs are nearly four times faster on SSE2 and twice as fast on AVX2 (see table 3.3). We may wonder why they are four times faster on SSE2 than AVX2. Inspection of the assembly code will bring out the explanations. In fact, overall, the program is faster on SSE2 than AVX2. On very rare occasions, the compiler exploits the assumption that arithmetic is commutative and associative may become problematic.
