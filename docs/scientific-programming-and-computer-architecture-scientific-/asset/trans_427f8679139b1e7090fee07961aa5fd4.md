
与之前一样，`for` 循环的缺失使得这些函数更加透明。

成员函数 `wait()` 等待发送完成，但不会等待接收完成。

```
void FastTrans::wait(){
    MPI_Waitall(P, sreqlist, MPI_STATUSES_IGNORE);
}
```

MPI 函数 `MPI_Waitall()` 用于等待 `sreqlist` 中的所有 `P` 请求完成。我们并没有以相同的方式等待接收完成。等待接收完成被折叠在 `transpose()` 的结构中，并作为将网络活动与缓冲区之间的数据拷贝进行重叠的策略的一部分。

成员函数 `transpose()`（我们现在定义它以进行转置）是 `Transpose` 类的核心。它比 `Transpose` 类中对应的成员函数要复杂得多。在深入细节之前，我们先问自己想要做什么。当然，在某个层上，答案是简单的：我们想让网络活动与缓冲区之间的数据拷贝进行重叠。其他成员函数的定义是为了促进这种重叠，即通过一次处理一个块的方式在缓冲区之间进行拷贝，或者完全不进行拷贝。同样地，发送和接收也是一次处理一个进程的，而不是一次性完成。

真正的答案要复杂得多。为了让网络活动与处理器活动实现重叠，我们必须确切理解 Open MPI 库何时发出了 RDMA 读取请求。当 RDMA 请求被发出时，网络活动就与处理器活动解耦了。

为了直观感受 RDMA 请求是如何发出的，我们回到了原始的 `Transpose` 类。我们通过在许多位置插入打印语句修改了 Open MPI 库的 1.6 版本。原始类通过将数据拷贝到发送缓冲区来影响矩阵转置，启动一系列非阻塞的发送和接收，等待它们完成，最后从接收缓冲区中拷贝出数据。该程序在 `P=20`（或 `nprocs=20`）时运行。以下是记录的进程  0 记录的输出：

```
DV MESG:: MPI_Isend() entry
DV MESG:: MPI_Isend() exit
[Isend message repeats total of 20 times]
...
```

```
DV MESG:: MPI_Irecv() entry
DV MESG:: MPI_Irecv() exit
```

## 6.3. MPI 示例

```
[Irecv message repeats total of 20 times]
...
DV MESG:: MPI_Wait() entry
DV MESG:: MPI_Wait() exit
DV MESG:: MPI_Wait() entry
DV MESG:: issuing RDMA read
[RDMA read message repeats total of 19 times]
```

```
DV MESG:: MPI_Wait() exit
DV MESG:: MPI_Wait() entry
[Wait message repeats 38 times after RDMA]
```

RDMA 请求是在在前 20 次发送期间以及随后的前 20 次接收期间发出的。在第一次 `MPI_Wait()` 期间也没有发出 RDMA 请求。秩 0 进程的第一次等待是等待从秩 0 发给自己自身的发送完成。所有的 RDMA 请求都在第二次等待期间发出的，这次等待不涉及网络活动。这是秩 1 进程的等待。随后是对其他 38 次接收的等待。其中没有一个等待导致了 RDMA 请求。在单次多进程过程中，来自进程 0 的全部 19 个 RDMA 请求都是在第二次等待后生成的。

如果我们尝试通过让网络活动与缓冲区之间的拷贝重叠，并认为 RDMA 请求可能会在发送或接收期间发出，那么我们将无法取得进展。如下所示，Open MPI 不愿意在发送或接收期间发出 RDMA 请求。它只极少数情况下这样做。然而，当我们等待一个特定的发送请求时，Open MPI 库发出了对应于所有处理器节点的 RDMA 请求，尽管其中某些节点并不是我们正在等待的请求对象。

库函数 `MPI_Wait()` 是一个阻塞调用，因此不适用于将网络活动与处理器活动重叠。其他函数如 `MPI_Test()` 和 `MPI_Testany()` 则具有此目的。`MPI_Test()` 会立即返回有关完成的信息。
