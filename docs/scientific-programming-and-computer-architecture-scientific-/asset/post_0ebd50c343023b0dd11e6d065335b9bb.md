As we step through the design, it is helpful to keep a few numbers in mind. The L1 cache is 32 KB and big enough to hold 4,000 double-precision numbers. The L3 cache is 12 MB and big enough to hold 1.5 million double-precision numbers. The second-level TLB has 512 entries (see tables 4.1 and 4.2). To keep the design simple, we ignore the L2 cache and the first TLB.

In section 4.2.1, we found that it takes about two cycles to load a single double into memory at peak bandwidth. The changes in storage formats that occur, when we begin with the microkernel and increase the dimensions of the matrices that are multiplied, are too complicated to permit access to memory at peak bandwidth. It is perhaps reasonable to take the cost of accessing a double from DRAM memory as 10 cycles. At floating point bandwidth, the cost of a single arithmetic operation is 1/4 cycle on an SSE machine. To approach peak floating point bandwidth, we should expect to perform a few hundred arithmetic operations for every double loaded from DRAM memory.

4 × 200 × 12

The microkernel of section 3.3.4 performs a 4 × 200 × 4 multiplication and reaches 34 flops per cycle, assuming all matrices to be in L1. The 4 × 200 × 12 multiplication function that is written under the assumption that a[] will be loaded from L3 cache. To pay for the cost of loading a[], it returns a[] three times.

```c
void mult4200x12(double *a, double *b, double *c){
    asm4200x4(a, b, c);
    asm4200x4(a, b+800, c+16);
    asm4200x4(a, b+1600, c+32);
}
```

In the mult4200x12() function, the arrays a[], b[] and c[] are lengths of 800, 2,400, and 48, respectively. The L1 cache is big enough to hold all three of them. In the next step, this function is called repeatedly with the same b[] but with a[] and c[], which change with iteration. Therefore, we assume that b[] is in L1 cache.

The function mult4200x12() assumes a[] to be in column-major format with leading dimension equal to 4—the same as in the microkernel. But b[] has a pretty strange format. The first four columns of the 200×12 matrix are stored in b[0..799] in row-major order, the next four columns are similarly stored in b[800..1599], and the final four columns are in b[1600..2399]. The array c[] is in column-major format (except for skewing, which we are ignoring).

The arrays a[], b[], and c[] defined on lines 2, 3, and 4, respectively, are 16-byte aligned. The 4 × 200 × 4 microkernel ensures that its arguments are 16-byte aligned, and we must be careful to respect that requirement.

The array a[] is too large to fit into L1 or L2 cache but fits comfortably into L3 cache. It is big enough to hold 150 matrices of size 4 × 200. The array c[], which holds 150 matrices of size 4 × 4, fits into L2 cache but not L1.

On lines 8 and 12, the arrays b[] and a[] are initialized with random numbers. Initializing with simple numbers as 0 gives timing numbers that are reproducible. The mult4x20012() function is called $10^7$ times on line 15 so that the function has to load a[] and c[] from L2 or L3 cache after each call. This pattern of function calls imitates the manner in which the function is called in the next stage $600 \times 200 \times 12$. The mult600x0012() function requires scratch space of $600 \times 12$ to store c[], which is unpacked to the array C[] in column-major format with the right leading dimension.

```c
void mult600x0012(double *a, double *b,
               double *C, int ldC,
               double *scratch){
    double *c = scratch;
    for(int i=0; i < 7200; i++)
        c[i] = 0;
    for(int i=0; i < 150; i++)
        mult4200x12(a*i*800, b, c+i*48);
    unpackC(c, ldC);
}
```

The array a[] stores a $600 \times 200$ matrix. The $600 \times 200$ matrix is thought of as 150 matrices of dimension $4 \times 12$ below the other, and these 150 submatrices must be lined up in c[], with each submatrix stored in the column-major format required by mult200x12(). The function mult600x12() makes 150 calls to mult200x12(). At the end it unpacks c[]. The function unpackC() listed below converts c[] to the column-major format of C.

```c
void unpackC(double *c, double *C, int ldC){
    for(int i=0; i < 600; i++)
        for(int ii=0; ii < 12; ii++)
            for(int iii=0; iii<4; iii++)
                C[i+iii+ii*ldC] += c[12*i+4*ii+iii];
}
```

Deciphering this triply nested loop is an exercise. The main point is the cost of unpacking, whatever it may be, is far less the savings obtained in calling mult200x12() 150 times with c[] in a format that permits sequential access.

## 600 × 200 × 3000

The earlier function for $600 \times 200 \times 12$ assumes a[] to be packed format. The $600 \times 200$ entries of a[] store 150 submatrices of dimension $4 \times 200$. Each submatrix occupies 800 contiguous entries and is in column-major order. The function packA() packs a[] into this format.

```c
void packA(double *A, int ldA, double *a)
    for(int j=0; j < 200; j++)
        for(int i=0; i < 150; i++)
            for(int ii=0; ii < 4; ii++)
                a[i*800+ii+j*4] = A[4*i+ii+j*ldA];
```

Deciphering this triply nested loop is another exercise we commit. The function mult600x200x300() reuses a[] as soon as it is packed by making 250 calls to the function in the previous stage of our design, then makes up for the cost of packing. It claims $600 \times 200$ entries of scratch[] to store the packed array.

```c
void mult600x200x3000(double *A, int ldA,
  double *b,
  double *C, int ldC,
  double *scratch){
  double *a = scratch;
  scratch += 600*200;
  packA(A, ldA, a);
  for(int i=0; i < 250; i++)
    mult200x12(a, b*i*2400, C*i*12*ldC, ldC,
    scratch);
}
```

For every double entry in the packed array[] of size $600 \times 200$, the $600 \times 200 \times 3000$ multiplication functions perform 6,000 arithmetic operations. We expect the cost of the arithmetic to greatly outweigh the cost of packing(). The multiplication function has floating point performance of 3.21 flops per cycle (see table 4.7). As expected, the decline from 3.22 flops per cycle yielded by the previous stage is marginal.
