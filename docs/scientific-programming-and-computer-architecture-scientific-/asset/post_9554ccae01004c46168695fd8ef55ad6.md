## Memory error without segmentation fault

In fact, we can modify run2() slightly so that there is no segmentation fault, although the program is erroneous.

```c
void run3() {
    long *list = new long[2000];
    for(int i=0; i < 2000; i++)
        list[i] = i+100000;
    f1(list, 2000);
    delete [] list;
}
```

The stacking of functions with run3() is identical to that with run2(). The difference is in the way the 2,000 entries of list have been set. The for-loop on lines 4 and 5 of f0() executes the statement a0[j]=j*j for j = 10^3, ..., 10^4 + 1,999. So it skips over the first 1,000 entries of a0 as f1—the address that f0() must return to and modifies certain entries of a1(). The program prints the following:

```
in f0: sum = 0
f1: sum = 242644667000
```

We may verify that $\sum_{i=0}^{1999} (i+1000)^2 = 242,644,667,000$. In run1(), run2(), and run3(), all the entries of list[] $\ge 0$. We fill list [] with negative entries to examine scenarios that break the stack in the opposite direction, which is the direction the stack grows. If the entries of list [] are all negative and $\le -1,000$, for example, the local variables of f0() and the return addresses are not overwritten. The program will run to completion if the maximum limit on the size of the stack is not exceeded. In a more complex program, the point where the program fails can be far away from the error.

The kernel does not shrink the stack, even when a function uses a lot of memory on the stack returns. Once the kernel adopts the policy that it will let the stack expand up to its maximum limit, whenever the program generates memory references in the stack area, there is no reasonable way for the kernel to shrink the stack.

## 5.4. Program memory

Functions return using the RET instruction. No kernel function is called every function return—it would be a huge waste to do so. The kernel has no way of knowing when a process scales its use of the stack.

Many computing clusters set the maximum stack size to be as large as 8 GB. Such a large limit on the stack size is not a good thing, although it might be helpful to inexperienced programmers. Memory acquired on the stack is never released and the performance of programs that abuse the stack may degrade.

## Corruption of dynamically allocated memory

Dynamic memory allocation using malloc(), _mm_alloc(), or new[] can invoke algorithms of considerable complexity. Functions such as malloc() and free() invoked by user programs are defined in runtime libraries in user space. Our discussion of memory errors is corrected by the following simple function:

```c
void mreg(long *a, long n){
    for(long i=0; i < 5; i++)
        a[i] = i;
    a[n] = n;
}
```

This function initializes the first five entries of the array a[]. Each entry is a long. Finally, mreg() stores n in the n+1 entry a[n]. We will attempt to cause memory corruption by passing invalid values of n and understand how the system responds. The function mreg() is called by run(), whose definition follows:

```c
void run(long n){
    long *a = (long *) malloc(5*sizeof(long));
    mreg(a, n);
    free(a);
}
```

It is evident that run() allocates a[] to point to 5 entries of type long. It then calls mreg() to assign to a[n].

The point to be noted is the vm area where the array a[] is allocated typically has a lot of padding in either direction.

If we make the call run(5), we may expect that there is no segmentation fault because the vm area is probably larger than 5 entries of the type long. There is in fact no segmentation fault, but the runtime library detects an error when we try to free the pointer. How could that be? It turns out that the runtime library is storing a magic number in a location [5]. When freeing the pointer, it checks whether that magic number has been overwritten. The runtime glibc catches this error and produces a lengthy error report, which includes the memory map of the process—as if that were the tonic to catch up the programmer. In a more complex program, the point where the error is caught can be far away from where it occurs.

Let us run(6) or run(10000). None of these function produces an error message. All of them catch illegal locations, but it turns out the kernel has created a large vm area expecting more than to be allocated dynamically. The runtime glibc fails to catch the error. The magic number is stuffed into the first entry past the legal boundary but not ones after that. Stuffing a magic number in the entries just after the legal boundaries is a low overhead way to catch memory errors. Unfortunately, the point where the error can be far away from the place where the error is committed, and in some cases, the error may not be caught.

There is one last point we make about dynamic memory. Freeing a pointer can be a high overhead activity. When a pointer is freed, the runtime library may decide to give up a vm area. When the vm area of a running process is deleted, the kernel must change the pages tables. When the pages tables are cached, the entire TLB must be flushed to the process from accessing memory illegally.

After our discussion of stack and dynamic memory, the very idea of what is a legal memory access may seem fuzzy. In fact, the notion is fuzzy. There may be a notion of what is a legal memory reference respect to program semantics. Neither the runtime library nor the Linux kernel enforce that notion stringently. As a result, memory errors can be quite hard to catch, especially in multithreaded programs. The point where the program crashes can be far away from the point the error is committed. The programmer’s best defense is to know what is going on.

Dynamic memory is sometimes referred to as heap. For example, malloc() is said to allocate memory on the heap. In this usage, “heap” is a reference to the data structure that was used to keep track of dynamically allocated memory at some point in history. It may well that glibc uses the heap. But Linux does not use the heap to organize vm areas. It uses linked lists and red-black trees.
