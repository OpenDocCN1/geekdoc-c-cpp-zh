# 4.1. DRAM cache memory

The function time_unitstride() defines a[] statically, initializes every entry of a[] to 0, and makes a single call to unitstride on line 7. The function call is timed, and the number of cycles is divided by 10^9 to derive the cycles consumed per access. Each array dereferencing a[i] in unitstride() is counted as a memory access.

The two unitstride() and time_unitstride() are defined in separate files and compiled separately. As usual, we use the -ipo option for procedural optimization during compilation, and we use -fno-inline-functions to eliminate inlining. If the two functions are in the same file or ifprocedural optimization is turned on, the compiler will figure out that the call to unitstride() is doing nothing meaningful and simply eliminate the call.

Initializing the array to zero on line 4 ensures that page frames in physical memory have been allocated to the entire array before the function unitstride() is called.
The program reports 0.92 cycles per access. Cycle counts are similar to SSE2, AVX, and AVX2 machines (for the full name of the memory, see table A.1). The 0.92 cycles per access in unitstride() is a woful underestimate of the latency to DRAM memory. The single-for is loop-carried RAW dependency. The excellent ipc compiler has difficulty recognizing that a list of numbers can be grouped before it is submitted to introduce parallelism into the loop body. The generated code uses the XMM (or YMM) registers, which are large enough to pack four (or eight) ints, to decrease the number of instructions used to load entries of a[] into the registers. One reason is that a cache line here is so much smaller than the latency to DRAM: a cache line is large enough to hold 16 ints, and only one of 16 accesses of the array is fetching data from outside the cache.
