## 3.2.3 Loop fusion

Because the speed of modern x86 computers relies on instruction-level parallelism and vector registers, it is often a good idea to have a lot of parallelism in the innermost loops. If sets of instructions in the body of the innermost loop are independent of each other, the processor is likely to execute them in parallel.

Loop fusion addresses the situation where we have dependencies that make loop unrolling ineffective. In such a scenario, merging the two loops may be the best way to produce a loop body that is amenable to instruction-level parallelism. The transformation where distinct loops are merged is called loop fusion.

For an example, we consider the power series for sine and cosine.$^{14}$

```
$$\sin x = \frac{x^3}{3!} - \frac{x^5}{5!} - \dots$$
$$\cos x = 1 - \frac{x^2}{2!} + \frac{x^4}{4!} - \dots$$
```

The following program computes the sine and cosine of x and returns them in the reference variables c and s. The number of terms of the series used to be input to the function as n:

```
void sincos(double x, int n, double& c, double& s) {
    c = s = 0;
    double ci = 1;
    for(int i=0; i<n; i++){
        c += ci;
        ci *= -x*x/(2.0*i+2)/(2.0*i+1);
    }
    double si = x;
    for(int i=0; i<n; i++){
        s += si;
    }
```

> $^{14}$These series were discovered by Madhava around 1400 AD according to Sarma (1992).

```
si *= -x*x/(2.0*i+3)/(2.0*i+2);
}
```

The cosine loop accumulates the term in c and stores the term in ci. Each iteration updates the current term ci. When we look at the terms of the series cos x, we see a lot of parallelism because the terms are grouped and summed in many ways. However, when the loop posted to the compiler generates each iteration by updating the previous term, it is quite difficult for a compilation algorithm to automatically detect such parallelism. Similar comments apply to the sine loop.

Thus, simply unrolling the loops will not introduce much parallelism into the instruction stream and will not enable the compiler to generate packed double-instructions.

A better idea may be to fuse the two loops. To a human observer, it is obvious that the two loop bodies can be merged, assuming ci and si are appropriately initialized. Even if the loops are fused, it will be hard for the compiler to generate packed double instructions. It is true that when the terms are updated, we will need an XMM register that saves -x² in both its halves, and perhaps problematically, another XMM register that stores (2i+2)(2i+1) and (2i+2)(2i+3) in its two halves. A human programmer can easily see how to get around the problem. One XMM register can hold 2i in both halves, and a second XMM register can hold 2i+1 and 2i in both halves. The two XMM registers can be multiplied to get (2i+2)(2i+1) and (2i+2)(2i+3) and updated by adding (2,2) saved in each XMM register or cached location. All this proves to be too much for the compiler, however, some of the instructions in the body of the inner loop for SSE2-capable machine (see table 3.1):

```
addsd %xmm6, %xmm5
subsd %xmm1, %xmm8
subsd %xmm6, %xmm7
addsd %xmm6, %xmm5
addsd %xmm6, %xmm7
divsd %xmm5, %xmm8
divsd %xmm7, %xmm8
%xmm8, %xmm2
```

There is no need to decipher the assembly code. All that matters is that the cosine and sine loops are not fused, and both loops use single double instructions in the loop body (notice the sd mnemonics). On AVX2 machine, the compiler does generate fused-multiply-add instructions, but the instructions are still single double, and loops are not fused.

## 3.2.4 Unroll and jam

In this section, we will study a compiler optimization that applies to nested loops. So far we have considered loop unrolling and loop fusion. In nested loops, it is desirable to unroll the outer loop and fuse several copies of the inner loop result. That is the unroll and jam transformation. The following C++ program computes a sine table:

```
// sine table for x = pi/(2*n)
// with i=0,...,n.
// therefore stab must be of size n+1.
void sinetable(int n, double *restrict stab)
    double dx = 3.141592653589723846/(2*n);
    for(int i=0; i<= n; i++){
        double x = i*dx;
        stab[i] = 0;
        for(int j=0; j < 20; j++){
            stab[i] += si;
            si *= -x*x/(2*j+3)*(2*j+2);
        }
    }
```

This program computes sin x for $x=0,\pi/(2n),\dots,(n-1)\pi/(2n),\pi/2$ and leaves the $n+1$ computed values in the array stab. If we choose $n=360$, the resulting table corresponds to chord table presented by Ptolemy in his treatise on mathematical astronomy, which became known as the *Almagest*.¹ Ptolemy did not use power series, however. One of his tools was a generalization of the Pythagoras theorem to quadrilaterals.

This program gives the type of *stab* as double *restrict*. The *restrict* qualifier tells the compiler that any location addressed using the pointer will not be addressed using other pointer. Its use is not significant because only one pointer is in sight. However, in general, judicious use of *restrict* qualifier can help the compiler generate good code. We will discuss this in greater detail.

In this program, the outer loop variable *i* generates different values for *x* in the range $[0, \pi/2]$. The inner loop variable *j* generates terms of the power series of sin x. We fixed the number of terms to 20. So the numerical bounds of the inner loop *j* are known to the compiler.

If the compiler chooses to, it can unroll the inner loop completely. However, much can be gained by unrolling the inner loop. The new value of *si*, which holds a term of the power series, is obtained using its previous value. If the loop is unrolled, this chain, which each iteration of the inner loop depends on the previous iteration, remains intact, making it quite hard for the compiler to generate packed double instructions. The assembled generated by the compiler does not unroll the inner loop nor does it unroll on SSE2-capable machine. Some of the instructions in the body of the inner loop are shown below.

```
pxor %xmm5, %mm5
subsd %xmm1, %xmm5
addsd %xmm2, %xmm3
cvtsi2sd %r8d, %mm4
divsd %xmm4, %xmm5
mulsd %xmm5, %mm5
```

> ¹¹Chord tables are equivalent to sine tables, and one of the earliest chord tables was computed by Hipparchus around 150 BC. The first book of the *Almagest*, a textbook of mathematical astronomy written by Claudius Ptolemy of Alexandria around 150 AD, has a table of chords in sexagesimal. Toomre (1998).

On an AVX2-capable machine, the compiler unrolls the inner loop, but the instructions are all single double, as they are here. So there is no real gain from the compiler's code transformation.

Our experience with unroll and jam, so far, is similar to that with loop fusion. We wrote a program expecting the compiler to make a certain loop transformation, and it did not. This time we will persist and alter the program to get the compiler to generate code.

```
void sinetable(int n, double *restrict xlist,
double *restrict stab){
  for(int i=0; i < n; i++){
  stab[i] = 0;
  double si = xlist[i];
  for(int j=0; j < 20; j++){
    stab[i] += si;
    si *= -xlist[i]*xlist[j]/((2*j+3)*(2*j+2));
  }
}
```

The values for which the sine function must be computed in the array xlist[0...n], which is of length n+1. The use of the restrict qualifier is crucial. It tells the compiler that the arrays xlist and stab do not overlap in memory. Without qualifier, the compiler has to allow for the case in which xlist and stab are indexed to address the same location in memory. Having to preserve the semantics of the program when the two are aliased would preclude loop transformations. The assembly of the inner most loop follows.

```
.B3.4:
pxor    %xmm3, %xmm3
lea     2(%rdi,%rdi), %r8d
pxor    %xmm4, %xmm4
lea     3(%rdi,%rdi), %r9d
subpd   %xmm0, %xmm4
addpd   %xmm1, %xmm2
imull   %r8d, %r9d
mulpd   %xmm0, %xmm4
```
