# 3.2. Compiler optimizations

```
si *= -x*x/(2.0*i+3)/(2.0*i+2);
}
```

The cosine loop accumulates the term in c and stores the term in ci. Each iteration updates the current term ci. When we look at the terms of the series cos x, we see a lot of parallelism because the terms are grouped and summed in many ways. However, when the loop posted to the compiler generates each iteration by updating the previous term, it is quite difficult for a compilation algorithm to automatically detect such parallelism. Similar comments apply to the sine loop.

Thus, simply unrolling the loops will not introduce much parallelism into the instruction stream and will not enable the compiler to generate packed double-instructions.

A better idea may to fuse the two loops. To a human observer, it is obvious that the two loop bodies can be merged, assuming ci and si are appropriately initialized. Even if the loops are fused, it will be hard for the compiler to generate packed double instructions. It is true that when the terms are updated, we will need an XMM register that saves -x² in both its halves, and perhaps problematically, another XMM register that stores (2i+2)(2i+1) and (2i+2)(2i+3) in its two halves. A human programmer can easily see how to get around the problem. One XMM register can hold 2i in both halves, and a second XMM register can hold 2i+1 and 2i in both halves. The two XMM registers can be multiplied to get (2i+2)(2i+1) and (2i+2)(2i+3) and updated by adding (2,2) saved in each XMM register or a cached location.

All this proves to be too much for the icpc compiler, however are some of the instructions in the body of the cosine inner loop for SSE2-capable machine (see table 3.1):

```
addsd %xmm6, %xmm5
subsd %xmm1, %xmm8
subsd %xmm6, %xmm7
addsd %xmm6, %xmm5
addsd %xmm6, %xmm7
divsd %xmm5, %xmm8
divsd %xmm7, %xmm8
```
