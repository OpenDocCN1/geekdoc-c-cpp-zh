Why is the C++ interface more than 100 times slower? There are three reasons.

First, while the C library functions read() and write() can read and write objects of any type or class, they do not waste a single byte of storage. Each double is 64 bits and gets stored exactly as 8 bytes. If file streams are used and each double is stored in ascii, as in the earlier program, each double uses 23 bytes (+1 if the number is negative).

Second, the C++ interface incurs an overhead in converting every double from binary to ascii.

Third, the C++ interface gets the entire reading and writing using a single call to the C library. In contrast, the C++ interface reads or writes item, with the C++ fstream library being invoked for every item. The overhead of calling the library frequently can build up. What is, the fstream library probably invokes the file system inside the operating system kernel frequently, although it does some buffering. Every system call is like another function call, which can lead to many more function calls inside the file system. This overhead can build up.

# 4.3.2 Latency to disk

The measurement of latency to hard disk brings issues unlike the ones encountered in DRAM memory. Hard disk is so slow relative to memory that the operating system kernel gets to lengths to cache file data in DRAM memory. The hard disk maintains a cache and attempts to predict future accesses. The true latency to hard disk is not easily visible to simple computer programs.

The plan for measuring latency is to create a number of files and access several different positions in different files to gather latency statistics. The plan does not work easily. If 100 files of 100 MB are used in the measurement, the latencies for a 1 TB hard disk come quite low and of microseconds, not milliseconds. That is because all of 10 GB can fit comfortably inside the page cache of a system with 16 GB of memory.
