In sections 4.3.2 and 4.3.3, we investigate latency and bandwidth of DRAM memory. In both of these sections, the page cache maintained by the Linux kernel plays a big role. The page cache is a cache of the hard disk maintained in main memory. DRAM memory can be TB of size, and the page cache can occupy a considerable portion of that memory. A lot of file input/output is serviced by the operating system kernel using the page cache. To get a real picture of latency and bandwidth to hard disk, one needs to get beyond the page cache, and imply file sizes that are in the hundreds of GB.

Latency to hard disk is of the order of milliseconds and can therefore be 10⁶ times the latency to DRAM memory. Bandwidth to hard disk is of the order of hundreds of MB/s, which is a thousand times the bandwidth of DRAM on typical computers. However, hard disk capacity can be 100 or even 1,000 times DRAM capacity on typical computers. With respect to hard disk capacity, many supercomputing systems (and high-end workstations) are not well balanced. The need to provide a common file system across many computers for many users implies that the hard disk capacity is not as high as it should be.

## 4.3.1 C versus C++

With regard to the programming technique for reading and writing files, the simplest lesson is also the most valuable. The C interface can be much faster than the C++ interface as we show and for reasons we explain.

The following functions use C++ ofstream to read and write a double array v[] from or to a file of name filename.

```cpp
void write_easy(double *, long len, const char *fname){
    ofstream ofile(fname);
    ofile<<scientific;
    ofile.precision(16);
    for(long i=0; i < len; i++)
        ofile<<v[i] << endl;
    ofile.close();
}
```

## 4.3 Reading from and writing to disk

```cpp
void read_easy(double *v, long len, const char *fname){
    ifstream infile(fname);
    for(long i=0; i < len; i++)
        infile >> v[i];
}
```

The C interface below can be more than 100 times faster.

```cpp
#include <cstdio>
void write_direct(double *v, long len, const char *fname){
    FILE *fptr;
    fptr = fopen(fname, "w");
    fwrite((void *)v, len, sizeof(double), fptr);
    fclose(fptr);
}

void read_direct(double *v, long len, const char *fname){
    FILE *fptr;
    fptr = fopen(fname, "r");
    fread((void *)v, len, sizeof(double), fptr);
    fclose(fptr);
}
```

The FILE type as well as the functions fopen(), fwrite(), fread() are declared in stdio.h header file included on line 1. On line 5, a file is opened for writing and on line 13 for reading.

The library function fwrite() (line 6) has a quite simple interface. Its first argument is a pointer to a location in memory. The second argument is the number of items to be written, and the third argument is the size of each item in bytes. The final argument is a pointer to a file.

The library function fread() (line 14) has an identical interface. It returns the number of items read, which may be less than the number requested if there is an error. Following our usual practice, we do not check for error conditions. Open files are closed using fclose() (lines 7 and 15).

Why is the C++ interface more than 100 times slower? There are three reasons.

First, while the C library functions read() and write() can read and write objects of any type or class, they do not waste a single byte of storage. Each double is 64 bits and gets stored exactly as 8 bytes. If file streams are used and each double is stored in ascii, as in the earlier program, each double uses 23 bytes (+1 if the number is negative).

Second, the C++ interface incurs an overhead in converting every double from binary to ascii.

Third, the C++ interface gets the entire reading and writing using a single call. In contrast, the C++ interface reads or writes item, with fstream library being invoked for every item. The overhead of calling library can build up. fstream library probably invokes the file system inside the operating system frequently, although it does some buffering. Every system call is like another function call, which can lead to many function calls. This overhead can build up.

## 4.3.2 Latency to disk

Hard disk is so slow relative to memory that the operating system kernel caches file data and attempts to predict future accesses. The true latency to hard disk is not easily visible to simple programs. The plan for measuring latency is to create a number of files and access different positions in different files to gather statistics. If 100 files of 100 MB are used in the measurement, the latencies come quite low, not milliseconds. The idea is to use 100 files each of 1 GB to make the total file size in the order of several TB. As result, the actual measurement of latencies makes a large number of calls to latencydisk() and the code for which is now

```cpp
struct disk_latency {
    double fopen_cycles;
    double fseek_cycles;
    double fread_cycles;
    double fclose_cycles;
};

double latencydisk(const char *dir, int filenum, long pos, disk_latency &lat){
    char fname[200];
    sprintf(fname, "%s/file%d.dat", dir, filenum);
    Timestamp clk;
    FILE *fptr;
    clk.tick();
    fptr = fopen(fname, "r");
    lat.fopen_cycles = clk.toc();
    clk.tick();
    fseek(fptr, pos, SEEK_SET);
    lat.fseek_cycles = clk.toc();
    double x;
    clk.tick();
    fread(&x, sizeof(double), 1, fptr);
    lat.read_cycles = clk.toc();
    clk.tick();
    fclose(fptr);
    lat.fclose_cycles = clk.toc();
    return x;
}
```

¹On some computer systems, there is so much memory that 100 GB may fit comfortably inside a page cache and be too small for latency measurement. Thus, the file count as well as the file size may need to be changed.
