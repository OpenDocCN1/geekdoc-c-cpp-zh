```cpp
#include <offload.h>
#include <omp.h>

int gl_host_nththreads = -1;
int gl_mic_nththreads = -1;

void mic_init(int &nmic){
    char *s = getenv("OMP_NUM_THREADS");
    assert(s != NULL);
    gl_host_nththreads = atoi(s);
    omp_set_num_threads(gl_host_nththreads);

    nmic = _Offload_number_of_devices();
    s = getenv("MIC_OMP_NUM_THREADS");
    assert(s != NULL);
    gl_mic_nththreads = atoi(s);
    for(int i=0; i < nmic; i++)
        #pragma target(mic, i)
        omp_set_num_threads_target(gl_mic_nththreads);
}
```

On line 8, this program runs OMP_NUM_THREADS. On line 11, the default number of OpenMP threads on the host is set to the value of this environment variable. The default number of threads on the host is globally visible to the definition on line 4.

The function used on line 13 to find out the number of MIC devices is declared in offload.h (which is included on line 1). The environment variable prefixed with MIC is read on line 14, and for the for-loop on lines 17 to 19 sets the default of OpenMP on every MIC device to the value of that environment variable.

Defining OMP_NUM_THREADS and the same environment variable with the prefix MIC is enough to set the default number of threads correctly. The function mic_init() makes setting explicit within the structure of the program.

## 7.2. Offload

### 7.2.2 The target(mic) declaration specification

The icpc compiler has the ability to compile a function written in C/C++ to produce assembly for both the host computer and MIC device.

The function definition below is prefixed with `__declspec(target(mic))`. It is defined in the compilation unit leibnitz_init.cpp.

```cpp
__declspec(target(mic))
double hostmic_sum(double *v, long len) {
    printf("sum:mic/pointer v = %p \n", v);
    double sum = 0;
    #pragma omp parallel for
    reduction(:sum)
    for(long i=0; i < len; i++)
        sum += v[i];
    return sum;
}
```

This function simply sums the array v[]. When compiled (without the -mic flag), two object files are produced from the same source. The object file leibnitz_init.o has function definitions using the instruction set of the host computer. The object file leibnitz_initMIC.o has function definitions using the instruction set of the MIC device.

Compiling with the -S flag and inspecting the assembly shows that code for the MIC device uses ZMM registers and vaddpd instructions. On the AVX host, the assembly uses XMM registers but not the wider YMM registers. That is either a sign that compiler technology is yet to catch up with AVX or an indication that the compiler has figured out that using YMM registers brings no benefit in this program, which is limited by bandwidth to memory.

The rest of leibnitz_init.cpp has the following definition:

```cpp
/*
* gl_scl = 4.0^(1.0/3.0)
*/
__declspec(target(mic)) const double gl_scl = 1.5874010519681994;

__declspec(target(mic))
void hostmic_scale(double *v, long len) {
    printf("scale:host/mic pointer v = %p \n", v);
    #pragma omp parallel
    for(long i=0; i < len; i++)
        v[i] *= gl_scl;
}

#pragma omp parallel
#pragma omp master
    printf("num of threads = %d\n", omp_get_num_threads());

void leibnitz_init(double *v, long len) {
    #pragma omp parallel
    for(long i=0; i < len; i+=2){
        v[i] = 1.0/(2*i+1);
        v[i+1] = -1.0/(2*i+3);
    }
}
```

The global variable gl_scl is initialized to $4^{1/3}$. Thanks to the target(mic) qualifier, it is defined on both the MIC device and the host. The function hostmic_scale() multiplies every entry of the array v[] by $4^{1/3}$. However, the function leibnitz_init() initializes the array v[] to terms of the Leibniz series $1-1/3+1/5-\dots$. This function is not qualified using target(mic), and it is compiled only for the host. Although compilation of leibnitz_init.cpp using icpc generates an object file leibnitz_init.o compiled for the host and object file leibnitzMIC.o compiled for the MIC device, only the first of these needs to be linked. The icpc linker appears to automatically look for and find the other object file.

### 7.2.3 Summing the Leibniz series

We will discuss four different programs to sum. All four programs initialize the array v[] to terms of the series $1-1/3+1/5-\dots$ and then scale each term by $4^{1/3}$ before summing the series. Together the programs explore nearly all needs. Work is offloaded using the offload directive. Communication between the host and the MIC device is controlled using in, out, inout clauses. Each program works as follows. To begin, the array v[] is initialized with entries of the series $1-1/3+1/5-\dots$ on the host using leibnitz_init(). Subsequently, three calls are made to hostmic_scale(), and a single call to hostmic_sum(), which was defined above. The three calls to hostmic_scale() and the one to hostmic_sum() may be on either the host or MIC device. Each call to hostmic_scale() multiplies the terms of the series by $4^{1/3}$. In leibnitz1(), the three calls to hostmic_scale() and the call to hostmic_sum() are all offloaded to the MIC device. The syntax in this case is the simplest.

The function leibnitz2() is similar, except for one difference. When the master encounters a typical offload region, such as the offload region leibnitz1(), it blocks until the MIC device exits the offload region. In leibnitz2(), the syntax allows the master to offload without blocking and then wait for the offload region to complete. That type of syntax is essential to make the MIC coprocessor and the host in parallel.

The function leibnitz3() exhibits facilities for communication between the host and the MIC coprocessor in considerable detail. The first two scalings are done on the MIC device and the third scaling on the host. The sum is computed on the MIC device.

Finally, the function leibnitz4() shows how multiple MIC devices may be used in parallel. In offload directives, syntax such as `length(n)` is used to offload v[0,...,len-1] to the coprocessor. Parallelism between MIC devices is facilitated by the syntax `v[offset,...,offset+len-1]` which offloads to the coprocessor.

#### Offloading from the processor to the MIC

The first of the four functions, leibnitz1(), is the simplest.

```cpp
void leibnitz1(){
  int nmic;
  mic_init(nmic);
  long n = 1000*1000*8;
  long nbytes = n*8;
  double* v = (double *)mm_malloc(nbytes, 64);
  leibnitz_init(v, n);
  double sum;
  #pragma offload target(mic:0) mandatory(in(v:length(n))) align(64)
  {
    hostmic_scale(v, n);
    hostmic_scale(v, n);
    hostmic_scale(v, n);
    sum = hostmic_sum(v, n);
  }
  printf("%f\n", sum);
  _mm_free(v);
  mic_exit();
}
```

The number of MIC devices nmic is initialized on line 3. The initialization function mic_init() also sets the default number of threads for MIC as the host, as described. The 6.4 GB array v[] is initialized to entries of the Leibniz series $1-1/3+1/5-\dots$ on line 7.

The #pragma offload construct begins on line 10. The first clause, which is on line 10, is target(mic:0). This clause says that the computation in the ensuing block (lines 13 through 18) must be offloaded to the MIC device numbered 0. If there are nmic devices, the devices are numbered from 0 to nmic-1.

If there is in fact no MIC device on the system, the program by default ignores the offload directive and executes the ensuing block on the host itself. The mandatory clause on line 11 forces the program to abort if no MIC device is found.

The offload statement block (lines 13 through 18) refers to the array v[] and the variables sum and n. Before an offload region is entered, all the variables input to the offload region are automatically gathered and sent to the MIC device. During exit, the MIC device gathers all the variables to output and sends them back to the host. Therefore, we do not need to do anything to propagate the variables sum and n to the MIC device and back.

However, the 6.4 GB array v[] needs special handling. The clause on line 12 tells the compiler that v[] is an input to an offload region. The modifier length(n) tells the compiler that this is an array of length n. By default, the compiler will allocate a 6.4 GB array on the MIC device named v. An `in` clause always has the effect of copying v[] on the host to the corresponding array v[] on the MIC device. By default, the array v[] that resides on the MIC device is deallocated at exit from the offload region.
