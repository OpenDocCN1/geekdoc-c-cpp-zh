First, we will understand why unoptimized code is nearly always slow. The first few lines of the unoptimized assembly of leibniz() are as follows:

```
pushq %rbp
movq %rsp, %rbp
subq $32, %rbp
movq %rdi, -32(%rbp)
movq $0, -24(%rbp)
movq -24(%rbp), %rax
movq -32(%rbp), %rdx
cmpq %rdx, %rax
jle ..B1.4
jmp ..B1.9
```

The function leibniz() receives its argument n in the register rdi. This code fragment is checking whether o is less than n. If n > 0, the program jumps to the address ..B1.4. If not, it jumps to the address ..B1.9, where it terminates quickly by returning 0 as the answer. Deciphering this code fragment is left to the reader. It is a roundabout way to check whether n > 0 or not.

The optimized code performs the same action as follows:

```
testq %rdi, %rdi
jle ..B2.9
```

The test instruction uses the rdi register, which contains the argument n, with itself and sets flags. The instruction discards the result of and and does not alter the contents of rdi. If n is negative, the result will be negative as well, and the sign flag is set. The next instruction jle jumps to a location where the program terminates with a ret statement if either the sign or zero flag is set, in other words, if n ≤ 0. The optimized code is checking whether n ≤ 0 or n > 0 using a single instruction, while the unoptimized code takes more than half dozen to do the same thing.

We get a sense here of why unoptimized assembly is nearly always slow. Unoptimized assembly is characterized by a certain listlessness. The compiler takes a local view of the program.
