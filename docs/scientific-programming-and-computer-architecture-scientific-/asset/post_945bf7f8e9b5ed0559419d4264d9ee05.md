## Block multiplication

The function `blockmult()` listed below carries out an l × m × n multiplication if l, m, and n are multiples of 3,000, 200, and 3,000, respectively.

```c
void blockmult(double *A, double *B, double *C,
int l, int m, int n,
double *scratch){
    assert(l%3000==0);
    assert(m%200==0);
    assert(n%3000==0);
    int dA = 1;
    int dB = m;
    int dC = 1;
    l = 1/3000;
    m = m/3000;
    n = n/3000;
    for(int i=0; i < l; i++)
        for(int j=0; j < m; j++)
            for(int k=0; k < n; k++){
                double *AA = A + (i*3000)+(j*200)*dA;
                double *BB = B + (j*200)+(k*3000)*dB;
                double *CC = C + (i*3000)+(k*3000)*dC;
                mult3000x200x3000(dA, BB, dB, CC, dC, scratch);
```

## 4.2. Optimizing memory access

This function implicitly partitions $A$ into $3000 \times 200$ blocks, $B$ into $200 \times 3000$ blocks, and $C$ into $3000 \times 3000$ blocks. The function `mult_3000x200x3000()`, defined at the previous stage, is used to multiply a single block of $A$ into a single block of $B$ to get a single block of $C$.

The floating point bandwidth realized is 3.19 flops per cycle for the multiplication of square matrices of dimension 9000 on a 2.6 GHz SSE2 machine. For the same problem, the MKL library realizes more than 3.8 flops per cycle. Why is our design worse? The bulk of blame falls on the microkernel. To begin, the microkernel yields only 3.48 flops per cycle, assuming all its arguments are in L1 cache. On a 3.6 GHz AVX2 machine, which the microkernel yields 3.98 flops per cycle, the bandwidth realized for the multiplication of square matrices is 3.75 flops per cycle.

## 4.3. Reading and writing to disk

The data in registers disappears when the computer is powered off. In contrast, hard storage is permanent. Bits on platters are turned on and off using a magnetic field. More than 100 billion bits can be packed into a single inch of a platter.

File systems, implemented inside the operating kernel, impose a logical structure on hard disk and facilitate it. Files and directories are stored on hard disk. In everyday usage, files are read and written with the understanding that the data is on hard disk.

The Linux kernel implements a number of optimizations to speed access to the disk. The most most optimization is to use a page cache. The page cache is a list of page frames that corresponds to data in the disk. When a file is read, Linux will service the read using the page cache if possible. A read or write file operation has to fall through a number of software layers before it reaches the disk. The `read()` and `write()` calls are issued by the C library functions `fread()` and `fwrite()`. The C library may do some buffering of its own. The kernel will service the calls using a page cache if possible. If not, it invokes the file system to which the file belongs. There are software layers for combining, queuing, and scheduling requests to read or write to the hard disk. The request is finally issued using a device driver.

The command `lspci -v` may be used to find out the type of hard disk as well as the driver that is in. The C versus C++ discussion in section 4.3.1 is on programming technique. The C++ language provides a convenient interface to file input/output using `ifstream`

> When the file accesses through the driver, the driver issues a DMA request and puts the calling process to sleep. The process is woken up by an interrupt handler when the request is complete. The Linux kernel will cache the data before returning control to the user program.
