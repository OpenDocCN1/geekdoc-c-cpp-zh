# One MPI process per core is a bad idea

Assigning one MPI process for each core remains quite popular. It saves the trouble of learning about threads. Table 6.8 gives part of the reason it is a bad idea. To generate the nodes of this table, the same MPI process used for table 6.7 was used. The program was compiled with the same C/C++ compiler with the flags and linked against the same MPI library. The difference was that NTHREADS (a #define macro variable) was set to 1 to turn off threading and an MPI process was assigned to every core.

Table 6.8 shows the bandwidth of data transfer across the network drops precipitously. With 10 nodes it is less than 50% of the peak, and with 100 nodes it is not even 20%.

Having a process on every core increases contention for the host channel adapter. Even if the loss in performance were not so severe, it is a bad idea. Assigning a process to every core increases the modularity of hardware design. The processor node is a hardware module with multiple cores, and there is one network card on every node most of the time. There is modularity in hardware design from the register level up. There is a single memory system to manage all the cores. It is difficult to sustain good design practices if users at one level ignore the modularity of software or hardware they rely on.

## 6.3.4 Collective communication

The MPI programs we have written so far transfer data using versions of $MPI\_Send()$ and MPI\_Recv()$. Such calls are made autonomously by individual processes, but their completion is subject to matching calls by other processes. The MPI library provides several function calls for collective communication. A collective function must be made by all processes in a group. The result of collective calls as Bcast, Scatter, Gather, and Alltoall is data transfer involving all the processes.

The only collective we have encountered so far is $MPI\_Barrier() in the function unsafe(). The barrier was inserted with the purpose of exhibiting MPI syntax. It had no effect on the function unsafe().

In this section, we look at $MPI\_Bcast()$, $MPI\_Scatter()$, $MPI\_Alltoall()$, and $MPI\_Reduce()$. All these collective functions transfer data between participating processes and, in principle, can be implemented using send and receive operations between processes. For broadcast, the send/receive implementation is too slow.

The all-to-all transfer of data effected by $MPI\_Alltoall()` can be implemented using send/receive. However, if we restrict ourselves to send/receive syntax so far, the resulting implementation is not as fast as the library function. In deriving an effective send/receive implementation, we encounter an aspect of send/receive syntax of much value. Not surprisingly, this new syntax is of value because it could be related to a facility provided by the Infiniband hardware.

In typical MPI programs, the problem to be solved is split between several processes. However, reduction operations such as finding the minimum, maximum, or sum of data scattered across several computers and processes. The $MPI\_Reduce()$ function may be implemented using send/receive operations, but an effective send/receive implementation requires a tree-like or recursive pattern of communication. Like matrix transpose, reduction provides opportunities for overlapping network activity with processor activity. In the case of the matrix transpose, the processor activity involves copying to and from buffers. In reduction, the processors must also minimize, maximize, or sum.

# Broadcast

In a broadcast operation, the root process sends out data to every other process. The following function was used to time $MPI\_Bcast()$:

```c
double bcast(int rank, int nprocs, double *buffer,
    int bufsize){
    TimeStamp clk;
    int root = 0;
    clk.tick();
    MPI_Bcast(buffer, bufsize, MPI_DOUBLE, root,
    MPI_COMM_WORLD);
    double cycles = clk.toc();
    return cycles;
}
```

This bcast() function must be called by every MPI process with exactly the same value for bufsize. The bcast() function calls $MPI\_Bcast()$, which is a collective operation. Infiniband, like many other network architectures, supports broadcast in hardware. The MPI library $MPI\_Broadcast()$ uses the hardware-level architectural facility for broadcasting. The advantages of supporting broadcasting in hardware are obvious. In the fat-tree, a single Infinand switch may be connected to many other switches. The hardware can move the broadcast data to a switch just once and route it to all the host computers that may be reached from that switch. The send/receive implementation is forced to send data through the switch multiple times, for each host computer that may be reached from that switch. The Internet supports a broadcast protocol for radio broadcasts, sporting events, and the like.

The MPI standard states that all collective function calls are blocking. Therefore, a broadcast initiated at the root must wait until every process has a matching call to $MPI\_Broadcast()$.
