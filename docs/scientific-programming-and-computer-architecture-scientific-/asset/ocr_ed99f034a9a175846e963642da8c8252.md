When the cycles consumed by the entropy function were divided by 6,000, we got 270 cycles. So is the latency to DRAM memory about 270 cycles? Not really. We were careful to break instruction-level parallelism. We flushed the entire array out of cache (not shown here) before calling the function and respect cache boundaries. However, we forgot to think about a third element. Memory management is done using pages, page frames, page directories, and page tables. Because the array is large, every memory reference is likely to hit a new page. The page table for that page is unlikely to be in TLB and may have to be brought in from DRAM memory. What we thought was one memory access is likely to be two or more.

This little example may give us a sense of the complex in which parts of the memory system interact. Cache line size, parallelism in memory access, and the cost of TLB misses are all of no significance to program optimization.

# 4.1.5 Latency to DRAM

Our earlier attempts to measure latency to DRAM memory failed because we did not account for the overhead of creating and accessing page table entries. The more careful program in this section breaks instruction-level parallelism, ensures that the cache lines is accessed from L1, L2, or L3 caches, and accesses all of the 256 cache lines within four pages of memory (so that TLB misses are not a factor).

To begin with, we look at the function randomop(), which initializes the n entries of the array[] to be a permutation of the numbers 0, 1, . . . , n - 1.

```
void randomop(int *List, int n) {
for (int i=0; i < n; i++) {
  List[i] = i;
  for (int i=0; i < n; i++) {
    int j = rand()%(n-i)+i;
    int temp = List[j];
    List[j] = List[i];
    List[i] = temp;
  }
}
```
