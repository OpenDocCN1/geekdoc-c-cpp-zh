The typical cost of creating and destroying Pthreads appears to be somewhat less $than$ $10^6$ cycles. The number is not unreasonable given that each process descriptor used by the kernel is nearly 6 KB. A thread is more likely to wait for the time quantum of some other process to expire on a quad-core computer than on a computer with 12 cores.

## 5.3.3 Parallel regions using Pthreads

This section begins with a simple OpenMP program. The OpenMP program alternates between two parallel regions. In the first parallel region, every thread runs a function called `addone()`. In the second parallel region, every thread runs a function called `addtwwo()`.

Later in the section, the parallel regions are implemented in plain C, except for creating and launching Pthreads. The second and third implementations use spinlocks and mutexes, respectively. The final implementation uses conditional variables.

The basic idea in all four implementations is as follows. If the number of threads is $n$, including the master thread, the master begins by creating $n-1$ workers. The worker threads do not exit when their job is done but waiting for the master to send them more work. The threads exit only when the master tells them to.

Corresponding to the parallel regions of the OpenMP program, the master tells the workers to alternately execute `addone()` and `addtwwo()`. The master thread itself alternately executes those two functions.

If the threads were executing a complex function inside the parallel region, the two implementations would look different.

The C and the spinlock implementation do not yield the processor core voluntarily. In our setting, it is true for mutexes as well. As a result, all three implementations are highly wasteful when the number of threads is greater than the number of cores.

In the conditional variable implementation, the threads yield gracefully. As a result, it is the most efficient when the number of threads is greater than the number of cores.

Strangely, the conditional variable implementation is faster with four or eight threads than two threads, which is faster than one thread (see table 5.6). The explanation of this conundrum is important to understand, as it can happen in almost any program. The explanation (TLB flushes) is given later.

The gcc++ implementation of OpenMP also creates threads only at the point of entry into the parallel regions. Overall, it looks better than all our implementations. The first OpenMP parallel region that is entered is expensive because threads are created. If the number of threads changes from parallel region to parallel region, the parallel regions will be constantly hit by the same overhead.

The C implementation highlights the role of cache coherence, which is essential and fundamental to multithreaded programming. Propagating writes from cache can cause significant overhead. The C implementation also introduces memory fences.

## A simple OpenMP program

The two OpenMP parallel regions, in the program that will be listed shortly, alternately call the following functions:

```c
void addone(void *arg){
  long *p = (long *)(arg);
  *p += 1;
}

void addtwo(void *arg){
  long *p = (long *)(arg);
  *p += 2;
}
```

The functions receive a pointer to a long cast to void *, dereference it, and then add 1 or 2 to the long location. It would be simpler to add 1 and 2 directly without having to call functions that work through pointers. The OpenMP parallel regions invoke these functions to preserve a close analogy to the Pthread implementations. The Pthread implementations also use these two functions.

Here is the OpenMP program with two parallel regions.

```c
void ompmaster(long *list, int nthreads, int count){
  for(int i=0; i < count/2; i++){
    #pragma omp parallel
      num_threads(nthreads)
      default(list)
      {
        int j = omp_get_thread_num();
        addone((long *)(list+j));
      }
    #pragma omp parallel
      num_threads(nthreads)
      default(none)
      shared(list)
      {
        int j = omp_get_thread_num();
        addtwo((void *)list+j);
      }
  }
}
```

This program has two parallel regions, one of which calls add 1 to an entry of list[]. Each adds to the entry whose index is the same as its thread id. The thread id is returned by omp_get_thread_num(). The other parallel region adds 2 to the same entry using addtwo(). Because the regions are in a for-loop that is iterated count/2 times, the effect of a single call to ompmaster is to add 3 to as many entries as there threads.

## 5.3. Introduction to Threads

### Parallel regions in C

The first implementation makes minimal use of Pthreads. The following definitions are the basis of:

```c
typedef void (*fnlist_t[threads])(void *);
typedef void *arglist_t[threads];
volatile fnlist_t fnlist;
volatile arglist_t arglist;
volatile long work_count[threads];
volatile long done_count[threads];
```

This code defines two types, fnlist and arglist, and four variables. Here threads, whose definition is not shown, is equal to the number of threads. The type fnlist_t is an array (of threads) of functions with a single argument of void *. The type arglist_t is an array of (size threads) pointers to void.

### The worker function

These four volatile variables are used by the worker threads to communicate with the manager. The manager thread sets fnlist[tid] and arglist[tid] to tell the thread of identifier tid which function it should execute and what argument be passed to it. For example, fnlist[tid] is set to addone to ask the worker thread with identifier tid to execute the addone() function earlier in this section.

The manager thread uses the array entry work_count[tid] to tell the worker thread of identifier tid how many units of work have been assigned to it. The worker thread uses done_count[tid] to tell the manager how many units of work it has completed.

Making the four arrays used for communication between the manager thread and the workers ensures that every single reference generates a load or store instruction. In particular, the compiler will not assign any of these items to a register, which would get in the way of communication between the manager and the workers.

Every thread created using pthread_create() begins execution with a function that takes a pointer as its argument and returns a pointer. The worker thread begin with the following function:

```c
void *worker(void *arg){
    int tid = *((int *)arg;
    while(1){
        while(work_count[tid] == done_count[tid]);
        if(work_count[tid]==done_count[tid]+1){
            (*fnlist[tid])(arglist[tid]);
            asm volatile("mfence");
            done_count[tid] += 1;
        }
    }
}
```
