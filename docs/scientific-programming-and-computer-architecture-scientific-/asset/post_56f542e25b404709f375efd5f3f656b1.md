### 2.3.6 Recursive make and .d files

The make utility, as we have discussed so far, applies to all of whose source files are in a single directory. This assumption fails for even moderately large programs. When the source and object files required to build a single executable reside in several subdirectories, recursive make may be needed to complete the build.

Recursive make is a straightforward concept. It consists of calling make within a recipe for a phony target. The linking/linalg module defines interfaces to LAPACK's LU factorization routines as discussed in a previous section. These interfaces reside in the source file lusolve.cpp. The source test_lusolve.cpp tests the interface. It uses a few utilities such as verify_dir() defined in utils/utils.cpp. Building the executable test_lusolve.exe offers a simple example of recursive make.

```
1 include ../../makevars.mk
2 CFLAGS := $(CFLAGS) $(MKLINC)
3 LIBS := $(LIBS) $(MKLIBS)
4 ######
5 .PHONY: ../utils obj
```

### 2.3 Building programs using GNU Make

```
6 ../../utils:
7   make --directory=$@ objl
8 #####
9 objl: lusolve.o
10 lusolve.o: lusolve.cpp
11  -include lusolve.d
12 test_lusolve.o: test_lusolve.cpp
13  -include test_lusolve.d
14 #####
15 test_lusolve.exe: test_lusolve.o lusolve.o \
16     ../../utils ../../../utils/utils
```

This Makefile is used as the base for three somewhat distinct builds:

- The first of these, which is ../../utils, enables recursive build using on line 5. The first of these, ../../utils enables recursive build using the Makefile in ../../utils. The other phony objl is the target in the Makefile that builds all object files and libraries that may be useful externally. Indeed, we use objl generally in Makefiles as the name of the target that builds all object files and libraries in the same directory as the Makefile that may be useful externally.

Thus, the recipe for the phony target ../../utils (lines 6 and 7) is

```
make --directory=$@ objl
```

--directory option implies that a new shell process is forked

```
../../../utils
```

as the current directory and make objl is invoked within that directory (see table 2.2 for the meaning of $$). The Makefile in ../utils defines objl as a phony target. Its recipe updates all object files and libraries that may be used externally, including utils.o, which will be used in this Makefile.

The rule with the phony target objl (line 9) updates lusolve.o, which is the one object file in the linking/linalg/ folder that may be linked externally. Therefore, when other modules recursively call the Makefile in linking/linalg with objl as the target, the only object file that will be built is lusolve.o.

Recursive invocation of make is a consequence of the dependency on lines 15 and 16. The executable test_lusolve.exe is built using three object files (lines 15 and 16). Two of these object files, test_lusolve.o and lusolve.o, are built in the current directory. The object file utils.o, however, resides in ../utils. To build that object file correctly, the phony target ../utils is listed as a prerequisite. Updating ../utils will lead to a recursive invocation of make, which builds utils.o (lines 6 and 7). The linking recipe defined in makevars.mk filters out the phony target.

The second discussion is of .d files and the ways dependencies on header files are: Line 10 gives the dependency of lusolve.o on the source lusolve.cpp. It is typical for each object file to depend primarily on one source file. However, the source lusolve.cpp typically includes several header files that in turn include other files:

```
#include <math>
#include <iostream>
#include <mkl.h>
#include "../utils/utils.hh"
#include "lusolve.hh"
```

yet, the command

```
icpc -O3 -M -c lusolve.cpp
```

shows all the included files, which in number. This command uses the option supported by icpc to find the MKL header files. The -M option tells the compiler to give a list of all the included files. If any of these headers are altered, the object file lusolve.o must be rebuilt, although lusolve.cpp is unchanged.

Lines 11 and 13 are responsible for tracking the dependence of lusolve.o and test_lusolve.o, respectively, on header files. To understand how these lines work, go back to line 4 of makevars.mk, which included the -MMD and -MP options in CFLAGS. When icpc is invoked with -MMD -MP, it creates a .d file along with the object file. The .d file contains dependencies on header files. For example, generated lusolve.d contains the following:

```
lusolve.o: lusolve.cpp ../utils/utils.hh lusolve.hh \
/opt/intel/mkl/include/mkl.h \
[...]
```

```
/opt/intel/mkl/include/mkl_types.h
```

```
../utils/utils.hh: lusolve.hh
```

The first rule here, with lusolve.o as target, has generated the dependencies on all MKL header files as well as lusolve.hh and ../utils/utils.hh. Dependencies on system header files as iostream are omitted if the flag is -MMD but included with -MD. Line 11 of the Makefile reads

```
-include lusolve.d
```

The directive is -include and not include. When the directive include (as on line 1), make signals an error if the file to be included is not found (or cannot be built). In contrast, -include moves forward silently if the file to be included is found. If lusolve.o has been built, make will definitely use its first pass because the .d file is missing, the object file must also be missing, and there is no need to track dependencies on header files.

There can be a subtle problem with generating the .d files that list dependencies on header files during every compilation. Suppose lusolve.o is built correctly by the compiler, it also outputs a .d file as above, and then the implementation is changed. Suppose the header file ../utils/utils.hh is deleted during the new implementation. If we try to rebuild lusolve.o, GNU make looks at the old .d file and tries to resolve a dependency of lusolve.o on ../utils/utils.hh. There will be an error as the header file has been removed. To handle this problem, the compiler generated include rules such as

```
../utils/utils.hh:
```

If the header is not found, it is assumed to be built correctly by doing nothing. Although the -MM and related options supported by icpc/gcc/g++ make it relatively painless to handle dependencies of C/C++ sources on header files, it must

The third and final reiterates points that may have arisen. The include directive on line 1 splices in all makevars.mk at this point. This Makefile resides in linking/linalg, while makevars.mk is at the root of the source tree (see figure 2.2). Therefore, line 1 refers to the file to be included as ../../makevars.mk. Once this file is included, all the variables and pattern rules defined in it become available.

We want the compilation command to look for MKL header files at the right places. CFLAGS variable is modified to do that on line 2. It will be evaluated during the first pass and used when the recipe for generating % targets depend on %.cpp sources is invoked during the second pass. That recipe of course is in makevars.mk, which is above the definition of CFLAGS. Similarly, line 3 sets the LIBS so the MKL libraries are linked when the %.exe target that depends on %.o object is built using the recipe in makevars.mk.

The dependencies on lines 10 and 12 will be omitted. GNU make will use the pattern rule for %.o depending on %.cpp sources to generate those rules automatically—if the corresponding source files lusolve.cpp and test_lusolve.cpp are in the directory.

Makefiles capture the dependency of object files on source files and headers perfectly. A perfect capture is possible because typically an object file depends only on the source file (of the same name but with a different extension) and the header files included from inside the source file. In contrast, no attempt is made to capture the dependencies between object files. Each object file is a collection of functions. Because functions may call one another, the dependency graph between object files is typically more complicated. Circular dependencies between object files are common. Resolving these dependencies is left to the linker.

If suitable pattern rules have been defined, the dependencies of object files are deduced automatically by make. In contrast, we almost always need to indicate which object files are used to build an executable. We usually include rules as lines 10 and 12, which indicate the dependence of object files on sources, to make the structure of the program more explicit within the Makefiles.
