# Memory error without segmentation fault

In fact, we can modify run2() slightly so that there is no segmentation fault, although the program is erroneous.

```
void run3() {
    long *list = new long long[2000];
    for(int i=0; i < 2000; i++)
        list[i] = i+100000;
    f1(list, 2000);
    delete [] list;
}}
```

The stacking of functions with run3() is identical to that with run2(). The difference is in the way the 2,000 entries of list have been set. The for-loop on lines 4 and 5 of f0() executes the statement a0[j]=j*j for j = 10^3, ..., 10^4 + 1,999. So it skips over the first 1,000 entries of a0 as f1—the address that f0() must return to and modifies certain entries of a1(). The program prints the following:

```
in f0: sum = 0
f1: sum = 242644667000
```

We may verify that $\sum_{i=0}^{1999} (i+1000)^2 = 242,644,667,000$. In run1(), run2(), and run3(), all the entries of list[] $\ge 0$. We fill list [] with negative entries to examine scenarios that break the stack in the opposite direction, which is the direction the stack grows. If the entries of list [] are all negative and $\le -1,000$, for example, the local variables of f0() and the return addresses are not overwritten. The program will run to completion if the maximum limit on the size of the stack is not exceeded. In a more complex program, the point where the program fails can be far away from the error.

The kernel does not shrink the stack, even when a function uses a lot of memory on the stack returns.
