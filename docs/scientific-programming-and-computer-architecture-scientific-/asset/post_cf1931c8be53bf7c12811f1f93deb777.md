There are 32 ZMM registers, each of them 64 bytes or 512 bits wide. The Phi supports all the general-purpose registers such as %rdi, %rdx, and %rax. The thread register file is replicated for each of the four threads on any coprocessor core.

Figure 7.4 is a more detailed depiction of the Xeon Phi pipeline. The thread picker picks one of four threads every cycle. The next stage in the pipeline executes instructions. Instructions that use general-purpose registers are sent to either the U- or V-pipe. Both these pipes are part of the Vector Processing Unit (VPU) extension of the coprocessor core. The U-pipe can execute all instructions except a few. Notice that the Add/Mul unit of the U-pipe has four cycle latency, which is the same as the number of threads. So if each issues an Add/Mul instruction every cycle in round-robin scheduling, that one can be kept busy. Because the V-pipe is separate from the U-pipe, the coprocessor core can issue two vector instructions in the same cycle.

The next instruction we look at is FMADD231PD. FMADD refers to fast multiply and add. As before, V and PD refer to "vector" and "packed double." The effect of

```
vfadd231pd %zmm3, %zmm2, %zmm1
```

is equivalent to ZMM1 = ZMM1 + ZMM2 × ZMM3. Each ZMM register holds eight double-precision numbers. Each set of eight is subject to the multiply-add operation. This single instruction is responsible for 16 flops.

The first source of FMADD231PD can be swizzled in two different ways.

```
vfadd231pd %zmm3{cdab}, %zmm2, %zmm1
vadd231pd %zmm3{badc}, %zmm2, %zmm1
```

The effect of the swizzles is to permit the eight double-precision numbers stored in ZMM3 before subjecting it to the multiply-add operation. The permutations that the two swizzles {cdab} and {badc} correspond to be shown in figure 7.5. The 64-byte register is divided into halves, with each half holding four double-precision numbers, and both halves are subject to the same permutation.

The final instruction we consider is vpermmf32x4 shown in figure 7.6. The instru-

vpermmf32x4 $78, %zmm0, %zmm0

treats the ZMM0 register as divided into four blocks of 128 bits. In figure 7.6, these blocks d0-d1, c0-c1, b0-b1, and a0-a1. The number 78 determines the permutation that is effected. In binary, 78 is 01[00]11|10 or 4^5+1+4^2+0+3+4^9*2. Therefore, the permutation takes effect, the block in second position moves to the zeroth block in third position to the first position, and vice versa. Thus, we have the permutation shown in figure 7.6, which swaps the lower half of the ZMM register with the upper half. This instruction cannot be executed on the V-pipe.

# A microkernel for matrix multiplication

The assembly code shown in figure 7.7 implements a function with the following declaration:

```
asm8x1x8(double *A, double *B, double *C);
```

All pointers must be 64-bit aligned. An 8 x 1 column is stored in A[], and a 1 x 8 row is stored in B[]. The function computes their outer product AB adds the 8 x 8 matrix stored in C[]. To simplify implementation, the storage format of C is a little odd.

Figure 7.8 shows the diagonals of an 8 x 8 matrix. It is assumed that C is stored diagonal by diagonal, with the eight entries of diagonal 1 preceding of diagonal 2 and so on. This is not an restrictive assumption. If each 8 x 8 submatrix of a large 8n x 8n matrix is stored in this skewed manner, passing back and between the skewed and skewed formats needs to be done once and is much cheaper than the cost of multiplying such matrices.

In figure 7.7, the function name asm8x1x8(C) is mangled according to C++/Linux (but not a C program) can call the function as simply asmx1x8(). The first three arguments, which are pointers to the matrices, B, and C, are passed in the registers %rdi, %rsi, and %rdx (4, 5, 6), conforming with GNU/Linux convention. On lines 7 and 8, the matrices A and B are loaded into the registers ZMM0 and ZMM1. On line 9, the first diagonal of C is loaded into ZMM2. On line 11, the first diagonal of C is updated using vfadd231pd instruction.

```
.align 16,0
```

On line 12, the second diagonal is loaded into the register ZMM3. When it is updated on line 13, notice that the ZMM1 register storing the matrix $B$ is swizzled with {cdab}. The {badc} swizzle is used on line 16 to update the third diagonal. Both the swizzles are used (lines 19 and 20) to update the fourth diagonal.

On line 22, the upper and lower halves of the ZMM1 register, which stores the matrix $B$, are swapped. The other four diagonals are updated and stored back in $C$ (lines 37 through 44).

This program may be modified to compute the product of an $8 \times n$ matrix $A$, stored in column-major order, with an $n \times 8$ matrix $B$, stored in row-major order. The product of these two matrices may be computed as the sum of $n$ outer products of $8 \times 1$ matrices (any of $n$ columns of $A$) with $1 \times 8$ matrices (the corresponding row of $B$). Each product is added to the matrix $C$. To modify the program, one simply has to step through the columns of $A$ and the rows of $B$ while reproducing the logic of figure 7.7. The choice of $n$ should be large enough to result in many arithmetic operations for every load/store instruction but not so as to overflow the instruction cache. With $n=48$, this microkernel, running on 244 threads, reaches 473 GFLOPS/sec on a single Phi coprocessor. The theoretical peak is slightly more than twice as fast. Even getting to 50% of peak bandwidth is not bad. We have seen that MKL's optimized FFT reaches only 15% of the peak.
