The code is written to hold inLock to read and update list in; the list is reversed after the lock is released, so that calls to put can take place concurrently with this reversal. You also want to avoid any initial isEmpty test, because it would require locking both lists. Between occasional reversals, multiple calls to put and take can proceed fully in parallel, without lock contention.⁴

In this implementation of ConcurrentQueue, the locks are private and not exported. Client-side locking is not available, but you can implement addAll and drain as part of the class if needed:

```
// inside ConcurrentQueue
def putAll(values: A*): Unit = inLock.synchronized {
  for value <- values do in ::= value
}

def drain(): List[A] =
  val (in, out) =
    outLock.synchronized {
      inLock.synchronized {
        val i = this.in
        val o = this.out
        this.out = List.empty
        this.in = List.empty
        (i, o)
      }
    }
  out ++ in.reverseIterator
```
