## 33.2 Requirements [thread.req.paramname]

### 33.2.1 Template parameter names

Throughout this Clause, the name of templates are used to express type requirements. If a template is named Predicate, operator() of the template argument should return a value that is convertible to bool.

### 33.2.2 Exceptions [thread.req.exception]

Some functions in this Clause are specified to throw exceptions of type system_error (22.5.7). Such exceptions shall be thrown if any of the function's error conditions is detected or a call to an operating system or other underlying API returns an error that prevents the function from meeting its specifications. Failure to allocate storage should be reported in 20.5.5.12.

> Example: Consider a function in this clause that is specified to throw exceptions of operation_not_permitted that does not have the privilege to perform the operation. That, during the execution of this function, an errno of EPERM is reported by a POSIX API call. Since POSIX specifies an errno of EPERM when the "caller does not have the privilege to perform the operation," the implementation maps errno to operation_not_permitted (22.5) and an exception of type system_error is thrown. The error code reported by an exception's code() function shall have value equal to one of the conditions specified in the function's element.

### 33.2.3 Native names [thread.req.native]

Several classes described in this Clause have members native_handle and native_type. The presence of these members and their semantics is implementation-defined. [Note: These members allow implementations to provide access to implementation details. Their names are specified to facilitate portable code. Actual use of these members is inherently non-portable.]

## 33.2.4 Timing specifications

1 Several functions described in this Clause take an argument to specify a timeout. These timeouts are specified either as a duration or a time_point type.

2 Implementations have some delay in returning from a timeout. Overhead in interrupt response, function return, and scheduling includes “quality of implementation” delay, expressed as duration $D_i$. [330] Ideally, this delay would be zero. Further, contention for processor and memory resources reduces “quality of management” delay, expressed as duration $D_m$. The delays may vary from timeout, but in all cases it is shorter.

3 The member functions use end_in take an argument to specify a duration. These functions produce relative times. Implementations should use steady clock to measure time for these functions. Given a duration $D_t$, the real-time of that duration is $D_t + D_i + D_m$.

4 The member functions use end_until take an argument to specify a timeout. These functions produce absolute times. Implementations should use steady clock to measure time for these functions. The clock point of the return from them should be $C_t + D_i + D_m$ during the execution. If the clock is adjusted to $C_n$ during the timeout, the behavior should be as follows:
- (4.1) If $C_n < C_t$, the waiting function should return as soon as possible, i.e. at $C_n + D_i + D_m$, since the timeout is specified already.
- (4.2) If $C_n > C_t$, the waiting function should not time out until the time specified above.

5 If the clock is not synchronized with a steady clock, e.g., a CPU clock, these timeouts might not provide usefulness.

6 The resolution of timing provided by an implementation depends on both operating system and hardware. The finest resolution provided by an implementation is called the native resolution.

7 Implementation-provided clocks that are used for these functions must meet a timeout if, during its execution, a clock point or duration throws an exception. Such exceptions are referred to as timeout-related. [Note: Instances of clock, time point and duration types supplied by the implementation as specified in 23.1.7 do not throw exceptions.]

8 A function that takes an argument will timeout if, during its execution, a clock point or duration throws an exception.

## 33.2.5 Requirements for Lockable types

### 33.2.5.1 In general

1 An agent is an entity such as a thread that may perform in parallel with other execution agents. Note: Implementations or users may introduce other kinds of agents as processes or thread-pool tasks. All implementations for which standard time units are meaningful must necessarily have a steady clock within their hardware implementation. The calling agent is determined by context, e.g., the calling thread that contains the call, and so on. [Note: Lockable objects are "agent oblivious" in that for any execution agent model they do not determine or store the agent's ID (e.g., an ordinary spin lock).]

The standard library templates unique_lock (33.4.4.3), shared_lock (33.4.4.4), scoped_lock (33.4.4.2), lock_guard (33.4.4.1), try_lock (33.4.5), and condition_variable (33.5.4) all operate on user-supplied lockable objects. The BasicLockable requirements, and the TimedLockable requirements, are listed by these library types in order to acquire or release ownership of a lock by a given execution agent. [Note: The nature of any lock ownership and synchronization is not part of these requirements.]

### 33.2.5.2 BasicLockable [thread.req.lockable.basic]

- A type meets the BasicLockable requirements if the following requirements are well-formed and have the specific semantics (m denotes a value of type L).

```
m.lock()
```
- Effects: Blocks until a lock can be acquired for the current execution agent. If an exception is thrown then a lock shall not have been acquired for the current execution agent.

```
m.unlock()
```
- Requires: The current execution agent shall hold a lock on m.
- Effects: Releases a lock on m held by the current execution agent.
- Throws: None.

### 33.2.5.3 Lockable requirements [thread.req.lockable.req]

- A type meets the Lockable requirements if it meets the BasicLockable requirements and the following requirements are well-formed and have the semantics (m denotes a value of type L).

```
m.try_lock()
```
- Effects: Attempts to acquire a lock for the current execution agent without blocking. If an exception is thrown then a lock shall not have been acquired for the current execution agent.
- Return: bool.
- Returns: true if the lock was acquired, false otherwise.

### 33.2.5.4 TimedLockable requirements [thread.req.lockable.timed]

- A type meets the TimedLockable requirements if it meets the Lockable requirements and the following requirements are well-formed and have the semantics (m denotes a value of type L, rel_time denotes a value of duration (23.17.5), and abs_time denotes a value of an instantiation of time_point (23.17.6)).

```
m.try_lock_for(rel_time)
```
- Effects: Attempts to acquire a lock for the current execution agent within the relative timeout (33.2.4) specified by rel_time. The function shall not return within the timeout specified by rel_time unless it has obtained a lock on m for the current execution agent. If an exception is thrown then a lock shall not have been acquired for the current execution agent.
- Return: bool.
- Returns: true if the lock was acquired, false otherwise.
