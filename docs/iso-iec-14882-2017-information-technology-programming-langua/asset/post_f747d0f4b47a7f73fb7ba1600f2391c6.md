# 33.6 Futures

## 33.6.1 Overview

[futures.overview]

future describes how a C++ program can use future to retrieve a result (value or exception) from a function that has run in the same thread or another thread. [Note: These components are not restricted to multi-threaded programs but can be useful in single-threaded programs as well. — end note]

## 33.6.2 Header <future> synopsis

2. The enum values are distinct and not zero.

## 33.6.5 Shared state

+ Many of the classes introduced in this subclause use some state to communicate results. This shared state consists of some information and (possibly not yet evaluated) result, which can be a (possibly) value or an exception. [Note: Futures, promises, and tasks defined in this clause require shared state. — end note]

+ [Note: The result can be any kind of object including a function to compute the result, as by using async policy launch::deferred. — end note]

+ An asynchronous return object is an object that returns from a shared state. A waiting for an asynchronous return object is one that potentially blocks until the shared state is made ready. If a waiting return before the state is made ready because of a timeout (33.2.5), then it is a timed waiting, otherwise it is a non-timed waiting.

+ An asynchronous provider is an object that provides a shared state. The result of a state is set by the asynchronous provider. [Note: As promises or tasks. — end note] The means of setting the result of a state is specified in the description of these classes and functions that create such an object.

+ When an asynchronous return object or an asynchronous provider is said to release its shared state, it means:

- (5.1) the return object or provider holds the last reference to the shared state, the shared state is destroyed; and
- (5.3) these actions will not block for the shared state to become ready, except that may block if all of the following are true: the shared state was created by a call to async; the shared state is not yet ready, and this was the last reference to the shared state.

+ When an asynchronous provider is said to make its shared state ready, it means:

- (6.1) first, the provider makes its shared state ready; and
- (6.2) second, the provider unblocks any execution agents waiting for its shared state to become ready.

+ When an asynchronous provider is said to abandon its shared state, it means:

- (7.1) first, if state is not ready, the provider stores an object of type future_error with an error condition of broken_promise within its shared state; and then
- (7.2) makes its shared state; releases its shared state.

+ A shared state is ready only if it holds a value or an exception for retrieval. Waiting for a shared state to become ready may invoke code to compute the result on the shared state, synchronize with (4.7) calls to functions successfully the ready state returning from storage. The result of (whether normal or exceptional) the shared state synchronizes with (4.7) the successful result from a call to waiting on the shared state.

+ Some functions (e.g., promise::set_value_at_thread_exit) delay making the shared state ready until the calling thread exits. The destruction of each thread's objects with thread storage (6.7.2) is sequenced before making that shared state.

+ Access to the result of the same shared state may conflict (4.7). [Note: This specifies that the shared state is visible in the objects that reference this state in the sense of data race avoidance (20.5.9).]
