
# ISO/IEC 14882:2017(E)

## 32.6 Class template atomic

```cpp
namespace std {
template <class T> struct atomic {
    using value_type = T;
    static constexpr bool is_always_lock_free = implementation-defined;
    bool is_lock_free() const noexcept;
    void store(T val, memory_order = memory_order_seq_cst) volatile noexcept;
    void store(T val, memory_order = memory_order_seq_cst) noexcept;
    T load(memory_order = memory_order_seq_cst) const noexcept;
    T load(memory_order = memory_order_seq_cst) const noexcept;
    operator T() const noexcept;
    T exchange(T desired, memory_order = memory_order_seq_cst) volatile noexcept;
    T exchange(T desired, memory_order = memory_order_seq_cst) noexcept;
    bool compare_exchange(T& expected, T desired, memory_order = memory_order_seq_cst) volatile noexcept;
    bool compare_exchange(T& expected, T desired, memory_order = memory_order_seq_cst) noexcept;
    bool compare_exchange_weak(T& expected, T desired, memory_order = memory_order_seq_cst) volatile noexcept;
    bool compare_exchange_weak(T& expected, T desired, memory_order = memory_order_seq_cst) noexcept;

    atomic() = default;
    constexpr atomic(T) noexcept;
    atomic(const atomic&) = delete;
    atomic& operator=(const atomic&) = delete;
    operator T() volatile noexcept;
    operator T(T) volatile noexcept;
};
```

- 1 The template argument for T shall be trivially copyable (6.9). [Note: Type arguments that are not statically initialized may be difficult to use. — end note]

- 2 The specialization

- 3 The representation of an atomic specialization need not have the same size as its corresponding argument type. Specializations should have the same size whenever possible, as this reduces the effort to port existing code. — end note

## 32.6.1 Operations on atomic type

- 1 Many operations are volatile-qualified. The "volatile device register" semantics have not been changed in the standard. This qualification means that volatility is preserved when applying these operations to volatile objects. It does not mean that operations on non-volatile objects become volatile. — end note

```cpp
atomic() = default;
```

- 2 Effects: Initializes the atomic in an uninitialized state. [Note: These semantics ensure compatibility with C. — end note]

```cpp
constexpr atomic(T desired) noexcept;
```

- 3 Effects: Initializes the object with the desired value. Initialization is not an atomic operation (4.7). [Note: It is possible to have access to an atomic A race with its construction, for example by communicating the address of the just-constructed object Λ to thread via memory_order_relaxed operations on an atomic pointer variable, and then immediately accessing Λ in the receiving thread. This results in undefined behavior. — end note]

```cpp
#define ATOMIC_VAR_INIT(value) see below
```

The macro expands to a token sequence for constant initialization of an atomic variable of static storage of a type that is initialization-compatible with value. [Note: This operation may not initialize. — end note] Concurrent access to the variable being initialized, even by an atomic operation, constitutes a data race. [Example:

```cpp
atomic<int> y = ATOMIC_VAR_INIT(5);
// end example
```

```cpp
static const bool is_lock_free = implementation-defined;
```

The static data member `is_always_lock_free` is true if the atomic type's operations are all lock-free, and false otherwise. [Note: The value of `is_always_lock_free` is consistent with the value of the corresponding atomic.... LOCK_FREE macro, if defined. — end note]

```cpp
bool is_lock_free() const noexcept;
```

Returns true if the atomic operations are lock-free, false otherwise. [Note: The return value of the `is_lock_free` function is consistent with the value of `is_always_lock_free` for the same order. — end note]

```cpp
void store(T desired, memory_order order = memory_order_seq_cst) noexcept;
```

Requires: The order shall not be `memory_order_consume`, `memory_order_acquire`, nor `memory_order_acq_rel`.

Atomically replaces the value pointed to by this with the value of desired. Memory is affected according to the value of order.

```cpp
T operator=(T desired) noexcept;
T operator=(T desired) noexcept;
```

Equivalent: to `store(desired)`.

Returns: desired.

```cpp
T load(memory_order order = memory_order_seq_cst) const noexcept;
```

Requires: The order shall not be `memory_order_release` nor `memory_order_acq_rel`.

Memory is affected according to the value of order.

Atomically returns the value pointed to by this.

```cpp
operator T() const noexcept;
```

Equivalent to: `load()`.

```cpp
T exchange(T desired, memory_order order = memory_order_seq_cst) noexcept;
```

Atomically replaces the value pointed to by this with this desired. Memory is affected according to the value of order. These operations are atomic read-modify-write operations (4.7).

- 16 Returns: Atomically returns the value pointed to by this immediately before the effects.

```cpp
bool compare_exchange_weak(T& expected, T desired,
                    memory_order success, memory_order failure) volatile noexcept;
bool compare_exchange_weak(T& expected, T desired,
                    memory_order success, memory_order failure) noexcept;
bool compare_exchange_strong(T& expected, T desired,
                    memory_order success, memory_order failure) volatile noexcept;
bool compare_exchange_strong(T& expected, T desired,
                    memory_order success, memory_order failure) noexcept;
bool compare_exchange_weak(T& expected, T desired,
                    memory_order order = memory_order_seq_cst) volatile noexcept;
bool compare_exchange_strong(T& expected, T desired,
                    memory_order order = memory_order_seq_cst) noexcept;
```

- 17 Requires: The failure argument must not be `memory_order_release` or `memory_order_acq_rel`.

- 18 Effects: The value in expected is replaced. It then atomically compares the contents of the memory pointed to this by that replaced from expected, and if it returns true, the contents of the memory pointed to this is as desired. And if the comparison is false, the memory is affected by the value of success. When only one memory_order argument is supplied, the value of success is order, and the value of failure is except that a value of `memory_order_acq_rel` shall be replaced by the value `memory_order_acquire` or a value of `memory_order_release` shall succeed if the comparison succeeds the contents of the memory are replaced by the value read from the atomic operation. Otherwise, these operations are atomic load operations on that memory.

- 19 Returns: The value of the comparison.

- 20 [Note: For example, the effect of compare_exchange_strong is

```cpp
if (memcmp(this, &expected, sizeof(*this)) == 0)
    memcpy(this, &desired, sizeof(*this));
else
    memcpy(expected, sizeof(*this));

// example: The expected value of the compare-and-exchange operations is as follows.
The compare-and-exchange operations will update expected when another iteration of the loop is needed.
expected = current.load();
do {
    desired = function(expected);
} while (!current.compare_exchange_weak(expected, desired));

// example: Because the expected value is updated only on failure operation, releasing the memory containing the expected value on success will work. E.g. list insertion will act atomically and not introduce a data race in the following:
do {
    p->next = head; // make new list node point to the current head
} while (!head.compare_exchange_weak(head, p)); // try to insert
```
