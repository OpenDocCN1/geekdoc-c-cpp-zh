Referring to any non-static member or base class of an object in the handler for a function-try-block of a constructor or destructor for that object results in undefined behavior.

The scope and lifetime of parameters of a function or constructor extend into the handlers of a function-try-block.

The variable declared by the exception-declaration, of type ct or T, is initialized from the exception object, of type E, as:

- if T is a base class of E, the variable is copy-initialized (11.6) from the corresponding base subclass of the exception object;
- otherwise, the variable is copy-initialized (11.6) from the exception object.

The lifetime of the exception ends when the handler exits, with the destruction of any automatic objects initialized within the handler.

When the handler deletes an object, changes to that object will not affect the exception object. When the handler refers to an exception, any changes to the rethrown exception are changes to the exception object and will effect that object be rethrown.

# 18.4 Exception specifications [except.spec]

The predicate indicates whether a function cannot throw except it is called the exception specification of the function. If the predicate is false, the function has a potentially-throwing exception specification, or explicitly by using a noexcept exception specification. The exception specification is either implicitly, or explicitly by using a noexcept-specifier as a suffix of a function declarator (11.3.5).

```
noexcept-specifier:
except { constant-expression }
```

In noexcept-specifier, the constant-expression, if supplied, shall be a contextually evaluated constant expression of type bool (8.20); constant expression is the exception specification of the type in which the noexcept-specifier appears. A (token) that follows noexcept is not part of the noexcept-specifier and does not commence an initializer (11.6). The noexcept-specifier without a constant-expression is deprecated (D.3), and equivalent to the noexcept-specifier(throw()).

If a declaration of a function does not have a noexcept-specifier, the declaration has a potentially throwing exception specification unless it is a destructor or a declaration function or is executed on its first declaration, in which cases it has a noexcept specification as specified below and no other declaration for that function shall have a noexcept-specifier. (17.7.2) a noexcept-specifier may be specified, but is not required. If a noexcept-specifier is specified in an explicit instantiation directive, the exception specification shall be the same as the exception specification of all other declarations of that function.

diagnostic is required only if the exception specifications are not within the translation unit.

If a virtual function has a non-throwing exception specification, all declarations, including the definition of, any function that overloads that virtual function in a derived class has a non-throwing exception specification, unless the overriding function is defined as deleted.; | Example:

```
struct B {
    virtual void f() noexcept;
    virtual void g();
    virtual void h() noexcept = delete;

```

```
struct D : B {
    void f(); // ill-formed
    void g() noexcept; // OK
    void h() = delete; // OK
}
```

The declaration of D:f is ill-formed because it has a potentially-throwing exception specification, whereas B:f has a non-throwing exception specification. — end example

An expression is potentially-throwing if

- (6.1) e is a function (8.2.2) whose postfix-expression has a function type, a pointer-to-function type, with a potentially-throwing exception specification,
- (6.2) e implicitly invokes a function (such as an overloaded operator, an allocation in a new-expression, a constructor for a function argument, or a destructor if e is a full-expression (4.6) that is potentially-throwing,
- (6.3) e is a throw-expression cast that refers to a reference type and requires a runtime cast (8.2.7), or
- (6.4) e is a dynamic-cast expression that casts to a pointer
- (6.5) e is a type expression applied to a (possibly evaluated) built-in unary * operator applied to a pointer to a polymorphic class
- any of the initializer-list (4.6) of e is potentially-throwing.

An implicitly-declared constructor for a class X, or a constructor with a noexcept-specifier that is defaulted on its first declaration, has potentially-throwing exception specification if and only if any of the following constructs is potentially-throwing:

- (7.1) a constructor selected by overload resolution in the implicit definition of the constructor for class X to initialize a properly constructed subobject, or as a default argument expression, or,
- (7.2) a subexpression of such an initialization, or,
- (7.3) for a default constructor, a default member initializer.

*Note: Even destructors for fully-constructed objects are invoked when an exception is thrown during the execution of a constructor (18.2), their exception specifications do not contribute to the exception specification of a constructor, because an exception thrown from a destructor would call std::terminate rather than escape the constructor (18.1, 18.5.1). — end note*

The exception specification for an implicitly-declared constructor, or a destructor with a noexcept-specifier, is potentially-throwing if and only if any of the destructors of its potentially constructed subobjects is potentially-throwing.

The exception specification for an implicitly-declared assignment operator, or an assignment-operator without a noexcept-specifier that is defined on its first declaration, is potentially-throwing if and only if the invocation of any assignment operator in the implicit definition is potentially-throwing.

A allocation function (6.7.4.2) with explicit noexcept-specifier has a non-throwing exception specification.

- Example:

```
struct A {
A(int = (A(5)), 0) noexcept;
A(const A&) noexcept;
A(A&) noexcept;
~A();
};

struct B {
B();
B(const B&) = default; // implicit exception specification is noexcept(true)
B(B&, int) noexcept; // throw
-(B&) noexcept(false);
};

struct D {
int n = 7;
int* p = new int[n];
// /D:D() potentially-throwing, as the new operator may throw_bad_alloc or array_bad_length
// /D:D(const D&) non-throwing
// /D:D(D&) potentially-throwing
};
```

Furthermore, if A::~() is virtual, the program would be ill-formed since a virtual function from a base class cannot have a potentially-throwing exception specification if the base class has a non-throwing exception specification. — end example
