
# ISO/IEC 14882:2017(E)

The element of element access functions in parallel algorithms invoked with an execution of type execution::parallel_unsequenced_policy, are permitted to be executed in an unspecified fashion in threads, and with respect to one another within each thread of execution. Threads of execution are either the invoking of execution or threads implicitly created by the library; the latter will provide weakly parallel progress guarantees. [Note: This means that multiple object functions may interleave with one another. — end note] Since from execution::parallel_unsequenced_policy, an element access function may be interleaved on a single thread of execution, blocking synchronization, or the use of mutexes, leading deadlock. Thus, with the synchronization: execution::parallel_unsequenced_policy is restricted to synchronize with another function invocation, or it is specified to synchronize with it, and if it is not a memory allocation or deallocation function. Vectorization-standard library functions may not be invoked by the user from execution::parallel_unsequenced_policy. [Note: Implementations must ensure that internal synchronization standard library functions do not prevent progress when these functions are executed by threads of weakly forward progress guarantees. — end note]

```
int x = 0;
std::mutex m;
int a[] = {1, 2};
std::for_each(execution::parallel_unseq, std::begin(a), std::end(a), [&](int &i) {
  std::lock_guard<std::mutex> lock(m); // incorrect: lock_guard constructor calls m.lock()
  x += i;
});
```

The above program may result in two costly cases as the function invocation is not guaranteed to run on all threads of execution. [See example] [Note: The semantics of the execution::parallel_policy or the execution::parallel_unsequenced_policy allow the implementation to fall back to sequential execution if the system cannot parallelize an algorithm invocation due to lack of resources. — end note]

If an invocation of a parallel algorithm uses threads of execution implicitly created by the library, then the invoking of execution will

- (6.1) temporarily block with forward progress guarantee (4.7.2) on the completion of the library-managed threads of execution, or
- (6.2) eventually execute an element access function;

the thread of execution will continue to do until the algorithm is finished. [Note: In blocking with forward progress guarantee in this context, a thread of execution created by the library is considered to have finished execution as it has finished the particular element access function that the invoking of execution largely depends on. — end note]

The semantics of parallel algorithms invoked with an execution policy of implementation-defined type are implementation-defined.

## 28.4.4 Parallel algorithm exceptions [algorithms.parallel.Exceptions]

During the execution of a parallel algorithm, if temporary memory resources are required for parallelization and not available, the algorithm throws a bad_alloc exception.

During the execution of a parallel algorithm, if the invocation of an element access function exits via an uncaught exception, the behavior is determined by the ExecutionPolicy.

Parallel algorithms are algorithm overloads. Each parallel algorithm overload has an additional template type named ExecutionPolicy, which is the first template parameter. Additionally, each parallel algorithm overload has an additional function parameter of ExecutionPolicy&, which is the first function parameter. [Note: Not all algorithms have parallel algorithm overloads. — end]

Unless otherwise specified, the semantics of ExecutionPolicy algorithm overloads are identical to those without overload.

Unless otherwise specified, the requirements of ExecutionPolicy algorithm overloads are relaxed from the complexity requirements of the overload as follows: when the guarantee says “most expr” or “exactly expr” and does not specify the number of assignments or swap, and expr is not expressed with (O(expr)) notation, the complexity of the algorithm is O(expr).

Parallel algorithms shall not participate in overload resolution unless is_execution_policy_v<tExecutionPolicy> is true.

## 28.5 Non-modifying sequence operations [alg.nonmodifying]

### 28.5.1 All of [alg.all_of]

```
template<class InputIterator, class Predicate>
bool all_of(InputIterator first, InputIterator last, Predicate pred);
template<class ExecutionPolicy, class ForwardIterator, class Predicate>
bool all_of(ExecutionPolicy&& exec, ForwardIterator first, ForwardIterator last, Predicate pred);
```

> Returns: true if [first, last) is empty or pred(*i) is true for every iterator i in the range [first, last), and false otherwise.

> Complexity: At most – first applications of the predicate.

### 28.5.2 Any of [alg.any_of]

```
template<class InputIterator, class Predicate>
bool any_of(InputIterator first, InputIterator last, Predicate pred);
template<class ExecutionPolicy, class ForwardIterator, class Predicate>
bool any_of(ExecutionPolicy&& exec, ForwardIterator first, ForwardIterator last, Predicate pred);
```

> Returns: false if [first, last) is empty or if there is no iterator i in the range [first, last) such that pred(*i) is true, and true otherwise.

> Complexity: At most – first applications of the predicate.

### 28.5.3 None of [alg.none_of]

```
template<class InputIterator, class Predicate>
bool none_of(InputIterator first, InputIterator last, Predicate pred);
template<class ExecutionPolicy, class ForwardIterator, class Predicate>
bool none_of(ExecutionPolicy&& exec, ForwardIterator first, ForwardIterator last, Predicate pred);
```

> Returns: true if [first, last) is empty or pred(*i) is true for every iterator i in the range [first, last), and false otherwise.

> Complexity: At most – first applications of the predicate.

### 28.5.4 For each [alg.foreach]

```
template<class InputIterator, class Function>
for_each(InputIterator first, InputIterator last, Function f);
```

> Returns: void.

> Complexity: O(N).

```
template<class ExecutionPolicy, class ForwardIterator, class Function>
for_each(ExecutionPolicy&& exec, ForwardIterator first, ForwardIterator last, Function f);
```

> Returns: void.

> Complexity: O(N).

```
template<class InputIterator, class Size, class Function>
for_each_n(InputIterator first, Size n, Function f);
```

> Returns: void.

> Complexity: O(n).

```
template<class ExecutionPolicy, class ForwardIterator, class Size, class Function>
for_each_n(ExecutionPolicy&& exec, ForwardIterator first, Size n, Function f);
```

> Returns: void.

> Complexity: O(n).
