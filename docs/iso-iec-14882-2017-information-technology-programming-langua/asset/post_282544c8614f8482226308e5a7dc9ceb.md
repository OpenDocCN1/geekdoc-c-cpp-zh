## 20.5.4.2.2 Namespace posix [namespace.posix]

1 The behavior of a C++ program is undefined if it adds declarations or definitions to namespace posix unless otherwise specified. The namespace posix is reserved for use by ISO/IEC 9945 and other POSIX standards.

## 20.5.4.2.3 Names for future standardization [namespace.future]

1 Top level namespaces with a name starting with std followed by a non-empty sequence of digits are reserved for future standardization. The behavior of a C++ program is undefined if it adds declarations or definitions to such a namespace. Example: The top level namespace std2 is reserved for use in revisions of this International Standard.—end example

## 20.5.4.3 Reserved names [reserved.names]

1 The C+++ standard library reserves the following kinds of names:

- macros
- global names
- names with external linkage

2 If a program declares or defines a name in a context where it is used, other than as explicitly allowed by this Clause, its behavior is undefined.

## 20.5.4.2 Macro names [macro_names]

1. A translation unit that includes a standard header shall #define or #undef declared in any standard header.
2. A translation unit shall not #define or #undef lexically linked to keywords, to the identifiers listed in Table 4, or to the attribute-tokens described in 10.6.

## 20.5.4.3 External linkage [extern_names]

1. Each name declared as an external linkage is reserved to the implementation to designate that object with external linkage, both in namespace std and in the global namespace.
2. Each global function declared with external linkage is reserved to the implementation to designate that function signature with external linkage.
3. Each name from the C standard library declared with external linkage is reserved to the implementation for use as a name with extern "C" linkage, both in namespace std.
4. Each function signature from the C standard declared with external linkage is reserved to the implementation for use as a function signature with both "C" and "C++" linkage, or as a name of scope in the global namespace.

## 20.5.4.4 Types [extern_types]

1. For each type T from the C library, 180 types :T and std::T are reserved to the implementation and, when defined, ::T shall be declared to std::.

## 20.5.4.5 User-defined literal suffixes [illit_suffix]

1. Literal identifiers equivalent to the file name of the C++ standard library starting with an underscore are reserved for future standardization.

## 20.5.4.6 Headers [alt_headers]

1. If a file name equivalent to the derived file name for one of the C++ standard library headers is provided as part of the implementation, and a file name placed in any of the places for a source to be defined (13.2), it is undefined.

## 20.5.4.7 Derived classes [derived_classes]

1. Virtual function signatures defined for a base class in the C++ standard library may be overridden in a derived class in the implementation (13.3).

> 177. The list of such names includes errno, declared or defined in <cerrno.
> 178. The list of such function signatures with external linkage includes setjmp(jmp_buf), declared or defined in <setjmp>, and va() in <stdarg>.
> 179. The function signatures declared in <cuchar>, <cwchar>, and <cctype> are always reserved, notwithstanding the restrictions imposed in subclause 4.5.1 of Amendment I to the C Standard for these headers.
> 180. These types are clock_t, div_t, fpos_t, lconv, long_t, dbstate_t, ptrdiff_t, atomic_t, size_t, time_t, va_list, wctrain_t, wctype_t, and wint_t.

## 20.5.4.7 Handler functions [handler.functions]

1 The C++ standard library provides a definition of the following handler function (Clause 21):

(1.1) terminate_handler

2 A C++ program may install different handler functions during execution, supplying a pointer to a function defined in the program or the library as argument (to respectively):

(2.1) set_new_handler
(2.2) set_terminate

See also 21.6.3, Storage allocation errors, and 21.8, Exception handling.

3 A C++ program can get to the current handler function by calling the following functions:

(3.1) get_new_handler
(3.2) get_terminate

4 Calling the set_* and get_* functions shall not incur a data race. A call to any of the set_* functions shall synchronize with subsequent calls to the same set_* and to the corresponding get_* function.

## 20.5.4.11 Requires paragraph [res.on.required]

Violation of the preconditions specified in a function's Requires: paragraph results in undefined behavior unless the function's Throws: paragraph throwing an exception when the precondition is violated.
