
# ISO/IEC 14882:2017(E)

In this document, the notation *cv* (or *cv1*, *cv2*, etc.), used in the description of types, represents an arbitrary set of cv-qualifiers, i.e., of {const}, {volatile}, {const, volatile}, or the empty set. For a type cv T, the *top-level* cv-qualifiers of that type are denoted by *cv*: [Example: The type corresponding to the *type-id* const int has no top-level cv-qualifiers. The type corresponding to the *type-id* volatile int has the top-level cv-qualifier. — end example]

CV-qualifiers applied to an array type attach to the notation "cv T", where T is an array type, refers to an array type whose elements are so-qualified. An array type whose elements are considered to have the same cv-qualifications as its elements. [Example:

## 6.11 [basic.align]

Object types have alignment which place restrictions on the addresses at which an object may be allocated. An alignment is an implementation-defined integer value representing the number of bytes between successive addresses at which an object can be allocated. An object imposes an alignment requirement on every object of that type; stricter alignment can be requested using the alignment specifier (10.6). The intent of this list is to specify these circumstances in which an object may be aligned.

- 2 A fundamental alignment is represented by an alignment less than or equal to the alignment supported by the implementation in all contexts, which is equal to alignof(std::max_align_t) (21.2). The alignment required for a type is better defined when it is used as a subtype of a complete object and when it is used as a subject of. [Example]:
```
struct B { long double d; };
struct D : B { char c; };
```
When D is a type of a complete object, it will have a subtype of B, it must be aligned appropriately for a long double. If D appears as a subtype of another object that has B as a base class, the B subject might be part of a different subtype, reducing the requirements on the D subject.—example—The result of the alignof operator reflects the alignment requirements of the type in the case.

- 3 An extended alignment is greater alignof(std::max_align_t). is implementation-defined whether extended alignments are supported and the contexts in which they apply (10.6). A type having an extended alignment is an over-aligned type. [Note: Every over-aligned type is one or a class type to which extended alignment applies (possibly through a non-static data member).—end note — A new-extended alignment is represented by a greater alignment—STUFF_DEFAULT_NEW_ALIGNMENT—(19.8).

- 4 Alignments are represented as values of the type std::size_t. Valid alignments include only those values returned by alignof for the fundamental types plus an additional implementation-defined set of values, which may be empty. Every alignment value should be a non-negative integer power of two. Alignments have an order from weaker to stronger alignments. Stricter alignments have larger alignment values. An address that satisfies an alignment requirement also satisfies any weaker requirement.

- 6 The alignment requirement of a complete type can be queried and provides the obvious results: Comparing alignments is meaningful and provides the character types (6.9.1) shall have the weakest alignment. [Note: This enables the character types to be used as the underlying type for an aligned memory area (10.6).—end note]

- (7.1) Two alignments are equal when their numeric values are equal.
- (7.2) Two alignments are different when their numeric value represents a stricter align.
- (7.3) When an alignment is larger than another it represents a stricter alignment.

- 8 [Note: The runtime pointer alignment function (23.10.5) can be used to obtain a pointer within a buffer; the aligned-storage templates in the library (23.15.7) can be used to obtain aligned storage.—end note]

- 9 If a request for a specific alignment in a specific context is not supported by an implementation, the program is ill-formed.
