## 2.6.2

Change: Requirements change; default constructible.
Rationale: Clarification of container requirements.
Effect on original feature: C++ 2003 code that attempts to explicitly instantiate a container using a user-defined type with no default may fail to compile.

## 2.6.2.5, 2.6.2.6

Change: Signature changes; from return types.
Rationale: Old signature threw away useful information that may be expensive to recalculate.
Effect on original feature: The following member functions have changed:
- erase(iter) for set, multiset, map, multimap
- erase(begin, end) for set, multiset, map, multimap
- insert(pos, num, val) for vector, deque, list, forward_list
- insert(pos, beg, end) for vector, deque, list, forward_list

C++ 2003 code that relies on these functions returning void (e.g., code that connects to a member function that points to one of these functions) may fail to compile with this International Standard.

## 2.6.2.7, 2.6.2.8

Change: Signature changes; from iterator to const iterator parameters.
Rationale: Overspecification.
Effect on original feature: The signatures of the member functions changed from taking an iterator to taking a const_iterator.
- insert(iter, val) for deque, list, set, multiset, map, multimap
- insert(pos, beg, end) for vector, deque, list, forward_list
- erase(begin, end) for set, multiset, map, multimap
- forms of list::splice
- all forms of list::merge

C++ 2003 code that uses these functions may fail to compile with this International Standard.

## 2.6.2.9, 2.6.2.10

Change: Signature changes; resize.
Rationale: Performance, compatibility with move semantics.
Effect on original feature: For vector, deque, and list the fill value passed to resize is now passed instead of value, and an additional overload of resize has been added. C++ 2003 code that uses this function may fail to compile with this International Standard.

## C.2.14 Clause 28: algorithms library [diff.cpp03.algorithms]

## 28.1

Change: Result of inputs after application of some algorithms.
Rationale: Required by new feature.
Effect on original feature: A C++ 2003 program may detect that an object with a valid but unspecified state has a different valid but unspecified state with this International Standard. For example, std::remove and std::remove_if may leave the tail of the input sequence with a different set of values previously.

## C.2.15 Clause 29: numerics library [diff.cpp03.numerics]

### 29.5

Change: Specified representation of complex numbers.
Rationale: Compatibility with C99.
Effect on original feature: Valid C++ 2003 code that uses implementation-specific knowledge about the binary representation of the required template specializations of std::complex may not be compatible with this International Standard.

## C.2.16 Clause 30: input/output library [diff.cpp03.input.output]

### 30.7.4.1,30.5.5.1,30.5.5.4,

Change: Specify use of explicit in existing boolean conversion functions.
Rationale: Clarify intentions.
Effect on original feature: Valid C++ 2003 code that relies on implicit boolean conversions will fail to comply with this International Standard. Such conversions occur in the following conditions:

- passing a value to a function that takes an argument of type bool;
- using operator== to false or true;
- returning a value from a function with return type bool;
- initializing members of type bool via aggregate initialization;
- initializing a const bool would bind to a temporary.

### 30.5.3.1

Change: Base class of std::ios_base::failure.
Rationale: More detailed error messages.
Effect on original feature: std::ios_base::failure is no longer derived from std::exception, but is now derived from std::runtime_error. Valid C++ 2003 code assumes that std::ios_base::failure is derived directly from std::exception may except efficiently in this International Standard.

### 30.5.2

Change: Flag types in std::ios_base are now bitmasks with values defined as constexpr static members.
Rationale: For new features.
Effect on original feature: Valid C++ 2003 code that relies on std::ios_base flag types being represented as std::bitset or as an integer type may fail to comply with this International Standard. For example:

```cpp
#include <iostream>

int main() {
  int flag = std::ios_base::hex;
  std::cout.setf(flag); // setf does not take argument of type int
```

## C.3 C++ and ISO C++ 2011 [diff.cpp111]

This subclause lists the differences between C++ and ISO C++ 2011 (ISO/IEC 14882:2011, Programming Languages - C++), by the characters of this document.

## C.3.1 Lexical conventions [diff.cpp11.lex]

Change: pp-number can contain one or more quotes.
Rationale: Necessary to enable quotes as digit separators.
Effect on original feature: Valid C++ 2011 code may fail to comply or change meaning in this International Standard. For example, the following code is both in C++ 2011 and in this Standard, the macro invocation produces different outcomes because the single quotes delimit a character literal in C++ 2011, whereas they are digit separators in this Standard:

```cpp
#define M(x, ...) __VAR_ARGS__
int x[] = {M(1,2,3, 4), 5};
// int x[] = { 5 }; // C++ 2011
// int x[] = { 3, 4, 5 };
```

## C.3.2 Basic concepts

### 6.7.4

Change: New placement deallocator.
Rationale: Required for sized deallocation.
Effect on original feature: Valid C++ 2011 code could declare a global placement allocation and deallocation functions follows:

```cpp
void operator delete(void*, size_t);
void operator delete(void*, size_t) noexcept;
```

In this International Standard, however, the declaration of operator delete might match a predefined (non-placement) operator delete (6.7.4). If so, the program is ill-formed, as it was for class member allocation and deallocation functions (8.3.4).

Change: A conditional expression with throw expression as its second or third operand keeps the type and value of the other operand.
Rationale: Formally mandated conversions (value-to-reference (7.1), array-to-pointer may behave differently in this International Standard.

## C.3.4 Loop declarations

### 10.1.5

Change: constexpr non-static member functions are not implicitly const functions.
Rationale: Necessary to allow member functions to mutate the object.
Effect on original feature: Valid C++ 2011 code may fail to compile in this International Standard. For example, the following code is valid in C++ 2011 but invalid in this International Standard because it declares the same member function with different return types:

```cpp
struct S {
  constexpr const int &kf();
  int &kf();
};
```

## C.3.5 Clause 11: declarators [diff.cpp11.dcl.decl]

### 11.6.1

Change: Classes with default initializers can be aggregates.
Rationale: Necessary to allow default member initializers to be used by aggregate initialization.
Effect on original feature: Valid C++ 2011 code may fail to compile or change this meaning in this International Standard.

```cpp
struct S { // Aggregate in C++ 2014
  int m = 1;
};
struct X {
  operator int();
  operator S();
};
S b(a); // uses copy constructor in C++ 2011,
// performs aggregate initialization in this International Standard
```

## C.3.6 Clause 20: library introduction [diff.cpp11.library]

### 20.5.1.2

Change: New header.
Rationale: New functionality.
Effect on original feature: The C++ header <shared_mutex> is new. Valid C++ 2011 code that #includes a header with that name may be invalid in this International Standard.

## C.3.7 Clause 30: input/output library [diff.cpp11.input.output]

### 30.11

Change: gets is not defined.
Rationale: Use of gets is considered dangerous.
Effect on original feature: Valid C++ 2011 code that uses the gets function may fail to compile in this International Standard.

## C.4 C++ and ISO C++ 2014 [diff.cpp14]

> This subsection lists the differences between C++ and ISO C++ 2014 (ISO/IEC 14882:2014, Programming Languages - C++), by the chapters of this document.

## C.4.1 Clause 5: lexical conventions [diff.cpp14.lex]

### 5.2

Change: Removal of trigraph support as a required feature.
Rationale: Prevents accidental use of trigraphs in raw string literals and comments.
Effect on original feature: Valid C++ 2011 code that uses trigraphs may not be valid or have different semantics in this International Standard. Implementations may translate trigraphs as specified in C++ 2014 if they appear outside of a raw string literal, as part of the implementation-defined mapping from physical source file characters to the basic character set.

### 5.9

Change: pp-number can contain p sign and P sign.
