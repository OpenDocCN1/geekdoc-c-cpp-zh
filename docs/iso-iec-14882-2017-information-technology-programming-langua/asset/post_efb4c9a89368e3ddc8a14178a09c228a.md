
# ISO/IEC 14882:2017(E)

A return statement in main has the effect of leaving the function (destroying any objects with automatic storage) and calling std::exit with the return value as the argument. If control flows off the end of the compound-statement of main, the effect is equivalent to a return with order (see also 18.3).

## 6.6.2 Static initialization [basic.start.static]

+ 1 Variables with static storage duration are initialized as a consequence of program initialization. Variables with thread storage duration are initialized as a consequence of execution. Within each of these phases initialization occurs as follows:

+ 2 A constant initializer for a variable or temporary object is one whose expression is a constant expression, except if it is an object which may also invoke constructors for it and its subobjects if they are of non-literal types.[Note: Such a class may have a non-trivial destructor.—end note] Initialization is performed if a variable or temporary object with static or thread storage duration is initialized by a constant for the entity. If initialization is not performed, a variable with static storage duration (6.7.1) or thread storage (6.7.2) is zero-initialized (6.11). Then, zero-initialization and constant initialization are called static initialization; all dynamic initialization of variables and static initialization happens before dynamic initialization.[Note: The dynamic initialization of non-literal variables happens before (4.7.1) and that initialization of local variables is defined in 9.7.—end note]

+ 3 An implementation is permitted to initialize a variable with static or thread storage duration as static initialization even if initialization is not required to be done, provided that

+ (3.1) the dynamic initialization of the initialization does not change the value of any other object of static or thread storage duration prior to its initialization, and

+ (3.2) the static initialization of the initialization produces the same value in the initialized variable as would be produced by the dynamic initialization if all variables not required to be statically initialized dynamically.

> Note: As a consequence, if the initialization of an object obj1 refers to an object obj2 of namespace scope it is unspecified whether the value of obj2 will be the value of the fully initialized obj2 (because obj2 was statically initialized) or be the value of obj2 merely zero-initialized. For example,

```
inline double fd() { return 1; }
extern double d1;
double d2 = d1;
// may be statically initialized to 0.0 or
// dynamically initialized to 0 if d1 is
// dynamically initialized, or 1 or otherwise

double d3 = fd();
// may be statically initialized or dynamically to 1
```

## 6.6.3 Dynamic initialization of non-local variables [basic.start.dynamic]

+ 1 Dynamic initialization of a non-local variable with static storage duration is ordered if the variable is implicitly or explicitly instantiated, partially-ordered if an inline variable that is not an implicitly or explicitly specialized instantiation, and otherwise is ordered.[Note: An explicitly specialized non-inline static data member or variable template specialization has ordered initialization.—end note]

+ 2 Dynamic initialization of non-local variables V and W with static storage duration are ordered as follows:

+ (2.1) If V and W have ordered initialization and V is defined before W within a single translation unit, the initialization of V is sequenced before the initialization of W.

+ (2.2) — If V has partially-ordered initialization, W does not have over unordered initialization, and V is defined before W in every translation unit where W is defined, then

+ (2.2.1) — if the program starts a thread (4.7) other than the main thread (6.6.1), the initialization of V strongly happens before the initialization of W;

+ (2.2.2) — otherwise, the initialization of V is sequenced before the initialization of W.

+ (2.3) — Otherwise, if the program starts a thread other than the main thread either V or W is initialized, it is unspecified in which threads the initializations of V and W occur; the initializations are unsequenced they occur in the same thread.

+ (2.4) — Otherwise, the initializations of V and W are indeterminately sequenced.

> [Note: This definition permits initialization of a sequence of ordered values concurrently with another sequence. — end note]

+ 3 A non-local od-use is an od-use (6.2) not caused directly or indirectly by the initialization of a non-local static or storage duration variable.

+4 It is implementation-defined, whether the dynamic initialization of a non-local inline variable with static storage duration is sequenced before the first statement of main or deferred. If it is deferred, it strongly happens before any non-local od-use of any non-inline function defined in the same translation unit as the variable. It is implementation-defined in which threads and at points in the program dynamic initialization occurs. [Note: Such points should be chosen in a way that allows the programmer to avoid deadlocks.— end note] Example:

```
// File 1
#include "a.h"
#include "b.h"
B::Use();

// File 2 -
#include "a.h"
A b;

// File 3 -
#include "a.h"
#include "b.h"
extern A a;
extern B b;

int main() {
a.Use();
b.Use();
}
```
It is implementation-defined whether either a or b is initialized before main is entered or whether the initializations are delayed until a is first od-used in main. In particular, if a is initialized before main, it is not guaranteed that b will be initialized before it is od-used by the initialization of a, that is, before A::A is called. If, however, a is initialized at some point after the first statement of main, b will be initialized prior to its use in A::A. — end example

A non-local variable with static storage duration having initialization with side effects is initialized in this case, even if not itself od-used (6.2, 6.7.1).

+5 It is implementation-defined whether the dynamic initialization of a non-local variable with static storage duration is sequenced before the first statement of main or deferred. If it is deferred, it strongly happens before any non-local od-use of that variable. It is implementation-defined in which threads and at which points the dynamic initialization occurs.

+6 It is implementation-defined whether the dynamic initialization of a non-local variable with static storage duration is sequenced before the first statement of the initial function of thread or is deferred. If it is deferred, the initialization associated with the entity for thread is sequenced before the first non-local od-use of any non-local variable with thread storage duration in the same translation unit as the variable to be initialized. It is implementation-defined in which threads and at which points the initialization occurs.

If the initialization of a non-local variable with static or thread duration exits with an exception, std::terminate is called (18.5.1).

## 6.6.4 Termination [basic.terminate]

+ 1 Destructors (15) for initialized objects (that objects whose lifetime (6.8) has begun) with static storage duration, and functions are registered as part of a call to std::exit (21.5). The call to std::exit is sequenced before the initialization of the destructors and the registered functions. [Note: Returning from main invokes std::exit (6.6.1)—end note]

+ 2 Destructors for initialized objects with thread storage duration within a given thread are called as a result of returning from the initial function of that thread and as a result of calling std::exit. The completions of the destructors for all initialized objects with thread storage duration within that thread will strongly happen before the initialization of the destructors of any object with static storage duration.

+3 If the constructor or dynamic initialization of an object with static storage duration happens before the initialization of the first, the completion of the second is sequenced before the call to the destructor. If the completion of the constructor or dynamic initialization of an object with thread storage duration happens before that of another, the completion of the second is sequenced before the call to the destructor. If an object is destroyed before it was initialized, its destructor is not called. For an array or class type, all destructors that are destroyed before any block-scope object with static storage duration initialized during the construction of the subobjects are. If the destruction of an object with static or thread storage duration exits with an exception, std::terminate is called (18.5.1).

+4 If a function calls a block-scope object of an object with static or thread storage duration that has been destroyed and the program has undefined if the flow of control passes through the definition of the previously destroyed block-scope object; however, the behavior is undefined if the object is used indirectly (i.e., through a pointer) after its destruction.

+5 If the initialization of an object with static storage duration happens before a call to std::exit (see <cstdlib>, 21.5), the call to the function passed to std::exit is sequenced before the call to the destructor. If a call to std::exit strongly happens before the initialization of an object with static storage duration, the call to the destructor for the object is sequenced before the call to the function passed to std::exit. If a call to std::exit strongly happens before the second call to std::exit is sequenced before the call to the first call to std::exit.

+6 If there is a use of a standard library object or function not permitted within signal handlers (21.10) that does not happen before (4.7) completion of the destructors with static storage duration and execution of std::exit registered functions (21.5), the program has undefined behavior.
