## 6.7.4.3 Safe-derived pointers

1 A traceable pointer object
- (1.1) an object of pointer type (6.9.2),
- (1.2) an object of an integer type that is at least as large as std::intptr_t, or
- (1.3) a sequence of elements in an array of narrow type (6.9.1), where the size and alignment of the sequence matches those of some pointer object.

2 A pointer is a safe-derived pointer only if it has an object pointer type and it is one of the following:
- (2.1) the value returned by a C++ standard library implementation of ::operator new(std::size_t) or ::operator new(std::size_t, std::align_val_t);
- (2.2) the result of the address of an object (or one of its subobjects) designated by an lvalue resulting from a traceable object;
- (2.3) the result of well-defined pointer arithmetic (8.7) using a safe-derived pointer value;
- (2.4) the result of a well-defined conversion (7.11, 8.4) of a safe-derived pointer value;
- (2.5) the result of a reinterpret_cast of a safe-derived pointer value;
- (2.6) the result of a reinterpret_cast of an integer representation of a safe-derived pointer;
- (2.7) the value of an object whose was copied from a traceable pointer object, at the time of the source object contained a copy of a safe-derived pointer value.

3 An value is an integer representation of a safe-derived pointer only if its type is at least large as std::intptr_t and it is one of the following:
- (3.1) the result of a valid conversion of an integer representation of a safe-derived pointer value;
- (3.2) the result of a valid conversion from a traceable pointer object, at the time of the source object contained an integer representation of a safe-derived pointer value;
- (3.3) the value of an object whose value was copied from a traceable pointer object, at the time of the source object contained an integer representation of a safe-derived pointer value;
- (3.4) the result of an additive or bitwise operation, one of whose is an integer representation of a safe-derived pointer P, if that result converted by reinterpret_cast<void>() would compare P.

4 An implementation may have relaxed pointer, in which case the value of a pointer value does not depend on whether it is a safe-derived pointer. Alternatively, an implementation may have a safe-derived pointer value referring to dynamic storage which is not a safe-derived pointer value unless the referenced complete object has previously been deallocated (5.11.1). Note that any pointer value (including null value passed to a deallocation function) is undefined; 6.7. This is even true if the unsafe-derived pointer value might compare equal to some-derived pointer value. [Note: This section does not impose restrictions on indirect pointers to memory not allocated by ::operator new. This maintains the ability of many C++ implementations to use binary libraries and components written in other languages. In particular, this applies to C binaries, indirect pointer to memory allocated by std::malloc is not prohibited.] It is implementation-defined whether an implementation has relaxed or strict pointer safety.

## 6.8 Object lifetime

1 The lifetime of an object or reference is a property of the object or reference. An object is said to have non-trivial initialization if it is of class or aggregate type and it one of its subobjects is initialized by a constructor other than a default constructor. [Note: Initialization by a trivial copy/move constructor is non-virtual.] The lifetime of an object T begins when
- (1.1) with the proper alignment and size T is stored, and
- (1.2) if the object has non-virtual initialization, its initialization is complete except that if it is a union member or subobject thereof, its lifetime only begins if
- (1.3) if T is a class with non-trivial destructor (15.4), the destructor calls, or
- (1.4) the storage which the object occupies is released, or reused by an object that is not nested within (4.5).

2 The lifetime of a reference begins when its initialization is complete. The lifetime of a reference ends as if it were a scalar object [Note: 15.6.2 describes the lifetime of member objects.]

3 properties assigned to objects and references throughout this document apply for a given object or reference during its lifetime. Note: In particular, before an object starts and its lifetime ends there are significant restrictions on the object, as described in 15.6.2 and in 15.7. The behavior of an object under construction and destruction is not the same as behavior of an object whose lifetime has started and not ended.

A program may end the lifetime of any object by destroying the storage it occupies or by explicitly calling the destructor for an object of class type with a non-trivial destructor, the program is not required to call the destructor before the storage which the object occupies is reused or released; however, if there is no explicit call to the destructor or if a delete-expression (8.3.5) is used to release the storage then has undefined behavior on the side effects produced by the destructor. Before the lifetime of an object has started but the storage which the object will be allocated, or after the lifetime of an object has ended and the storage which the object occupied was released or reused, any pointer that points the address of the storage location the object will be used for is undefined. Otherwise, if such pointer refers to allocated storage (6.4.2), then as the result of type* is valid but may only be used in limited ways, as described below. A program has undefined behavior if:
- (6.1) the object is a class type with a non-trivial destructor and the pointer is used operand of a delete-expression,
- (6.2) the pointer is used to access a non-static data member or a non-static member function of the object, or
- (6.3) the pointer is implicitly converted (7.11) to a virtual base class, or
- (6.4) the pointer is used as the operand of a static_cast (8.2.9), except when the conversion is to pointer to const void, or to pointer to void and subsequently to pointer to const char, unsigned char, or const std::byte(21.1), or
- (6.5) the pointer is used as the operand of a dynamic_cast (8.2.7).

Example:
```
#include <cstdlib>

struct B {
    virtual void f();
    void mutate();
    virtual ~B();
};

struct D1 : B { void f(); };
struct D2 : B { void f(); };

void B::mutate() {
    new (D2) // allocates storage ends the lifetime of *this
    f(); // undefined behavior
    = ...; // OK, this points to valid memory
}

void g() {
    void* p = std::malloc(sizeof(D1) + sizeof(D2));
    B* pb = new (p) D;
    pb->mutate();
    *pb;
    void* q = pb; // OK pb points to valid memory
    pb->f(); // undefined behavior, lifetime of *pb has ended
}
```

Similarly, before the lifetime of an object has started but after the storage which the object will occupy has been reused or released, or after the lifetime of an object has ended and before the storage which the object is occupied by reused, any gvalue that refers to the original object may be used only in limited ways. For an object under construction or destruction, see 15.7. Otherwise, a gvalue refers to allocated storage (6.4.5), and using the properties of the gvalue that do not depend on its value is well-defined. The program has undefined behavior:
- (7.1) the gvalue is used to access the object, or
- (7.2) the gvalue is used to call a non-static member function of the object, or
- (7.3) the gvalue is used to bind a reference to a virtual base class (11.6.3), or
- (7.4) the gvalue is used as the operand of a dynamic_cast (8.2.7) or as the operand of typeid.

If, after the lifetime of an object has ended and before the storage which the object is occupied or released, a new object is created at the storage location which the original object occupied, a pointer that pointed to the original object, a reference to the original object, or the name of the original object will automatically refer to the new object and, once the lifetime of the new object has started, can be used to manipulate the new object.
