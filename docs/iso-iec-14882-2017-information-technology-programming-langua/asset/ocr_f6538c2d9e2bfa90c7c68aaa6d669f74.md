# 28.4.3 Effect of execution policies on algorithmPolicy algorithms.parallel.exec

+   1 Parallel algorithms have template parameters named ExecutionPolicy (23.19) which describe the manner in which the execution of these algorithms may be parallelized and the manner in which they apply the access functions.

+   2 Unless otherwise stated, implementations may make copies of objects (with type T) from where is_trivially_copyconstructible_v<T> and is_trivial_destructible_v<T> are true. [Note: The invocations that use user-supplied functions should not rely on object identity of the arguments for such input is important consider using a wrapper that returns a non-copying implementation such as `reference_wrapper<T>` (23.14) or some equivalent. — end note]

+   3 The invocations of element access in parallel algorithms with an execution policy object of type execution::sequenced_policy all occurring in the calling thread of execution. [Note: The invocations are not interleaved; 4.6 — end note]

+   4 The invocations of element access in parallel algorithms with an execution policy object of type execution::parallel are permitted to execute in either the invoking thread of execution or concurrently. If the threads of execution created by thread (23.3.2) provide concurrent forward progress guarantees (7.2), then the provided forward progress guarantee is implementation-defined. Any such executions in the same thread of execution are indeterminate with respect to each other. [Note: The caller's responsibility is to ensure that the invocation does not introduce data races or deadlocks. — end note]

std::atomic<int> x(0);
std::vector<int> v;
std::for_each(std::execution::par, std::begin(a), std::end(a), [&](int i) {
    v.push_back(i*2); // incorrect: data race
});
