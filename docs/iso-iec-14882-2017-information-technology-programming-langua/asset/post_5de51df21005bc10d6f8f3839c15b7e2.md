# Lexical conventions

## 5.1 Separate translation

The text of the program is kept in units called source files in this document. A source file together with all the headers (20.5.1.2) and source files included (19.2) via the preprocessing directive #include, any source lines skipped by any of the conditional inclusion (19.1) preprocessing directives, is a translation unit. [Note: A C++ program may not be translated at the same time. — end note]

(6.5) — end note]

## 5.2 Phases of translation

- 1. Physical source characters are mapped, in an implementation-defined manner, to the basic source character set (5.3) by introducing new-line characters or end-of-line identifiers if necessary. The set of physical source characters accepted is implementation-defined. If any physical character not in the basic source character set is replaced by the universal-character name that designates it. An implementation may use any internal encoding, so long as an external character encountered in the source, and the same character expressed in the source as a universal-character-name (e.g., using the \uXXXX notation), are handled equivalently when that replacement is reverted (5.4) in a raw string literal.

- 2. Each instance of a backslash (\ immediately followed by a new-line character is deleted, splicing characters to form logical spaces. Only the backslash on any physical source line shall be eligible for part of such a splice. For splices replaced in a raw string literal, if splicing occurs in a character sequence that matches the syntax of a universal-character-name, the behavior is undefined. A source file that is not empty and does not end in a new-line character, or ends in a new-line character preceded by a backslash before any such splicing takes place, shall be processed as if an additional new-line character were appended to the file.

- 3. The source file is decomposed into preprocessing (5.4) and sequences of white-space characters (including comments). A source file must not end in a preprocessing token or in a comment. Each comment is replaced by one space character. New-line characters are retained. Each unwanted sequence of white-space characters other than new-line is retained or replaced by one space character. The process of dividing source files into preprocessing tokens is context-dependent. [Example: The handling of within a preprocessing directive, — end example]

## 5.4 Preprocessing tokens

```
preprocessing-token:
header-name
identifier
pp-number
character-literal
user-defined-character-literal
string-literal
user-defined-string-literal
preprocessing-op-or-unc
```

[lex.pptoken]

- 1. Each preprocessing token that is converted to a token (5.6) shall have the lexical form of a keyword, an identifier, a literal, or an operator.
2. A preprocessing token is the minimal lexical element of the language in translation phases 3 through 6. The categories of preprocessing include header names, identifiers, preprocessing numbers, character literals (including user-defined character literals), string literals (including user-defined string literals), operators and punctuators. If a ' ' or a '+' character matches the last category, the behavior is undefined. Preprocessing tokens can be separated by white space; this consists of (5.7), or white-space categories (space, tab, new-line, vertical tab, and form-feed). As described in Clause 19, in certain circumstances during translation phase 4, white serves as more than preprocessing token. White space can appear within a preprocessing token only as part of a header name or between characters in a character or string literal.
3 If the stream has been parsed into preprocessing tokens to give a given character

If the next character is a sequence of characters that would be the prefix and initial double quote of a raw string literal, the next preprocessing token shall be a raw string literal. Between the initial and final double quote characters of the raw string, any transformations performed in phases 1 and 2 (universal-character-names and line splicing) are reverted; d-char, r-char, or delimiting-names are also reverted; The raw string is defined as the shortest sequence of characters that matches the string-pattern

```
encoding-fix-utf R-string
```
