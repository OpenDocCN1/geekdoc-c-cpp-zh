# 4.7.2 Forward progress [intro.progress]

The implementation may assume that any thread will eventually do one of the following:

+   - terminate,
- make a call to a library I/O function,
- perform an access to a volatile glance, or
- perform a synchronization operation or an atomic operation.

> [Note: This is intended to allow compiler transformations such as removal of empty loops, when termination cannot be proved.]

2 Executions of atomic functions that are either defined to lock-free (32.8) or indicated as lock-free (32.5) are lock-free.

+   - If there is only one thread that is not blocked (3.6) in a standard library function, a lock-free execution on that thread shall complete. [Note: Such situation can occur with load-store-conditional implementations. This execution is sometimes over-threaded.]

+   - When one or more lock-free executions run concurrently, at least one must complete. [Note: It is difficult for some implementations to provide guarantees about this effect, especially when particularly important that other threads may prevent forward progress, e.g., by repeatedly stealing a line for unrelated purpose-load and store-conditional instructions. Instructions should ensure that such anomalies cannot indefinitely delay progress under expected operating conditions, and that those anomalies can safely be ignored by programmers. Outside this document, the execution of a thread is sometimes termed.]

3 During the execution of a thread, each of the following is termed an execution step.

+   - termination of the execution,
- performing an access to a volatile glance,
- completion of a call to a library I/O function, a synchronization operation, or an atomic operation.

4 An invocation of a standard library function that blocks (3.6) is considered to continuously execute execution steps while waiting for the condition that it blocks be satisfied. [Example: A library I/O function that blocks the I/O operation is capable to continuously check whether the execution is complete. Each such check might consist of one or more execution steps, for example using behavior of the abstract machine.]

5 Because of this and the preceding requirement regarding what of execution is to perform eventually, it follows that no thread of execution can exist without an execution step.

A thread of execution makes progress when an execution step or a lock-free execution does not complete because there are other concurrent threads that are not blocked in a standard library function (see above).

7 For a thread of execution providing concurrent forward progress guarantees, the implementation ensures that the thread will eventually make progress as long as it has not terminated. [Note: This is required regardless of whether or not other threads of executions (if any) are being or making progress. Eventually this requirement means that this will happen in an unspecified but finite amount of time.]
