
# ISO/IEC 14882:2017(E)

## 20.5.5 Conforming implementations

### 20.5.5.1 Overview

This section describes the constraints on, and latitude of, implementations discussed in 20.5.2; its use of macros in 20.5.3, non-member functions in 20.5.4, member functions in 20.5.5.5, data race avoidance in 20.5.5.9, class specifiers in 20.5.5.10, class derivation in 20.5.5.11, and exceptions in 20.5.5.12.

- A C++ header may include other C++ headers. A C++ header shall include only its corresponding declarations and definitions that appear in its syntax. A C++ header shown in its includes, including any other C++ headers shall provide the declarations and definitions that appear in those of other headers.

- Certain types and macros are defined in more than one header. Every entity shall be defined such that any header that defines it may be included after any other header that defines it (6.2).

- The C standard library headers (D.5) shall define C++ standard library header, as described in 20.5.1.2.

### 20.5.5.3 Restrictions on macro functions

- The names and global functions defined in 20.5.1.1 shall be reserved to the implementation.

- All object-like macros defined by the C standard library and described in this class as expanding to include constant expressions are also suitable for #if directives, unless explicitly stated otherwise.

### 20.5.5.4 Non-member functions

It is specified whether any non-member functions in the C++ standard library are defined as inline [10.1.6).

A call to a non-member function signature declared in Clauses 21 through 33 and Annex D shall be allowed if the implementation declared no additional non-member function signatures. [18].

An implementation shall not declare a non-member function signature with default arguments. Unless otherwise specified, calls made by functions in the standard library to non-operator, non-member functions do use functions from another namespace which are found through argument-dependent lookup (20.5.3.2). The exception for argument-dependent lookup allows cases such as the swappable with requirements (20.5.3.2); operator:: (27.6.2.2) in cases where out_iterator_.

### 20.5.5.5 Member functions

It is specified whether any member functions in the C++ standard library are defined as inline [10.1.6).

For a non-virtual member function signature described in the C++ standard, an implementation may declare a different set of member function signatures, provided that any call to the member function that would select an overload from the set of declarations in this document behaves as if overload were selected. [4 Note: For instance, an implementation may add parameters with default values, or replace a member function with default arguments with two or more member functions with equivalent behavior]

- 1) A valid C++ program always calls the expected non-member function. An implementation may also add additional non-member functions that would otherwise not be called by a valid C++ program.

### 20.5.5.6 Constexpr functions and constructors [constpr.functions]

1 This document explicitly requires that certain standard library functions are constexpr (10.1.5). An implementation shall not declare any standard library function as constexpr except for where it is explicitly required. Any header that provides non-declaring declarations of constexpr functions or constructors shall provide corresponding definitions.

### 20.5.5.7 Requirements for stable algorithms [algorithm.stable]

- 1 When for an algorithm to state that it is “stable” without further elaboration, it:
  (1.1) For the sort algorithms relative order of elements is preserved.
  (1.2) For the remove and copy algorithms relative order of the elements that are not removed is preserved.
  (1.3) For the merge algorithms, for equivalent elements in the original two ranges, the elements from the first range (preserving their original order) precede the elements from the second range (preserving their original order).

### 20.5.5.9 Data race avoidance [res.on.data.race]

1 This section specifies requirements that implementations shall meet to prevent data races (4.7). Any standard library function shall meet each requirement unless otherwise specified. Implementations may prevent data races in cases other than those specified below.

2 A C++ standard library function shall not directly or indirectly modify objects accessible by threads other than the current thread unless the objects are accessed directly or indirectly by the function’s arguments, including this.

3 A C++ standard library function shall not directly or indirectly modify objects (4.7) accessible by threads other than the current thread unless the objects are accessed directly or indirectly by the function’s non-const arguments, including this.

> 4 [Note: This means, that implementations cannot use a static object for internal purposes without synchronization because it could cause a data race even in programs that do not explicitly share objects between. — end note]

5 A C++ standard library function shall not access objects indirectly via its arguments or elements of its container by invoking functions required by its specification on those container elements.

Operations on iterators obtained by calling a library container or string member function may access the underlying container, but not modify it. [Note: In particular, container operations that invalidate iterators affect operations performed on iterators with that container. — end note]

7 Implementations share their own internal objects between threads if the objects are not visible to users and are protected against data races

8 Unless otherwise specified, C++ standard library functions shall perform all operations solely within the current thread if those operations have effects that are visible (4.7) to users.

> 9 [Note: This allows implementations to parallelize operations if there are no side effects. — end note]

### 20.5.5.10 Protection within classes [protection.within.classes]

1 It is unspecified whether any function signature or class described in Clauses 21 through 33 and Annex D is a friend of any class in the C++ standard library.

### 20.5.5.11 Derived classes [derivation]

1 An implementation may derive any class in the C++ standard library from a class with a name reserved to the implementation.

2 Classes in the C++ standard library are required to derive from base directly or indirectly through a hierarchy of base classes.

3 In any case:
   - (3.1) Every class described as virtual shall be virtual;
   - (3.2) Every class not described as virtual shall not be virtual;
   - (3.3) Unless explicitly stated, every type with distinct names shall be distinct.

4 All types in the C++ standard library shall be non-final unless otherwise specified.

### 20.5.5.12 Restrictions on exception handling [res.exception.handling]

1 Any of the functions in the C++ standard library can report a failure by throwing an exception of their type; or by throwing an exception that would be caught by an handler.

2 Functions from the C++ standard library shall not throw exceptions except when such function calls a program-specified function that throws.

3 Destructor operations in the C++ standard library shall not throw exceptions. Every destructor in the C++ standard library shall have a non-throwing exception specification.

4 Functions in the C++ library that do not have a Paragraph but have a potentially-throwing exception specification may throw implementation-defined exceptions.

5 An implementation may strengthen the exception specification for a non-virtual function by adding a non-throwing exception specification.

### 20.5.5.13 Restrictions on storage of pointers [res.pointer.storage]

1 Objects constructed by the standard library that may hold a smart-pointer value or an integer of type::intptr_t shall store values in a traceable pointer location (6.7.4.3). [Note: Others are strongly encouraged to use the same, since doing so may result in accidental use of pointers that are not safely defined. Libraries that store pointers outside the user's address space should make it apparent that they are stored and returned from a traceable pointer location. — end note]

### 20.5.5.14 Value of error codes [value.error_codes]

1 Certain functions in the C++ standard library report errors as type::error_code (22.5.3.1) object. That object's category() method return type::system_category() for errors originating from the system.

2 There is an implicit exception to this rule for types that are synonyms for basic integral types, such as size_t (21.2) and streambuf (30.5.2).

3 That is, the C++ library functions can be treated as if they are marked noexcept. This allows implementations to make performance optimizations based on the absence of exceptions at runtime.

4 The functions quant() and search() (28.8) meet this condition.
