+   (9.3) — for some event X A synchronizes with X and is sequenced before B, or if:

+   (9.3.1) — A is sequenced before X and X inter-thread happens before $B$, or

+   (9.3.2) — A inter-thread happens before X and X inter-thread happens before $B$.

[Note: The “inter-thread happens before” describes arbitrary concatenations of “sequenced before”, “synchronizes” and “dependency-ordered before”, with two exceptions. The first exception is that a concatenation is not permitted to end with “dependency-ordered before” followed by “sequenced before”. The reason for this limitation is that a consumption operation participating in a “dependency-ordered before” provides no relation to which this consumption operation actually carries a dependency. The reason is that this limitation applies only to the end of such a concatenation if any subsequent release operation will provide the required ordering for a consumer operation. The second exception is that a concatenation is not permitted to consist entirely of “sequenced before”. The reasons for this limitation are (1) to permit “inter-thread happens before” to be transitively closed and (2) the “happens before” relation, defined below, provides for relationships consisting of “sequenced before”. — end note]

+   10 Event A happens before an event B (or, equivalently, $B$ happens after $A$) if

+   (10.1) — A is sequenced before $B$, or

+   (10.2) — A inter-thread happens before $B$.

The implementation shall ensure no program execution executes a cycle in the “happens before” relation. [Note: This would otherwise be possible only through the use of consumer operations. — end note]

+   11 Event A happens before an event B if either

+   (11.1) — A is sequenced before $B$, or

+   (11.2) — A synchronizes with $B$, or

+   (11.3) — A strongly happens before $X$ and $X$ strongly happens before $B$.

[Note: In the absence of consumer operations, the happens before and strongly happens before relations are identical. Strongly happens before essentially consumes consumer operations. — end note]

12 A visible side effect $X$ on a scalar object or bit-field $M$ such that $A$ happens before $X$ and $X$ happens before $B$ satisfies the conditions:

+   (12.1) — A happens before $X$ to $M$ such that $A$ happens before $X$ and $X$ happens before $B$.

+   (12.2) — there is no non-atomic scalar effect $X$ or bit-field $M$, as determined by evaluation $B$, shall be the value stored by the side effect $A$.

[Note: If there is any ambiguity about side effect, the behavior is either unspecified or undefined. — end note] [Note: This states that operations on objects are not visibly detectable data races, but it is necessary to ensure that data races, as defined below, and with restrictions on the use of atoms, occur to data in a simple uninterrupted (sequentially consistent) execution. — end note]

13 The value of an object $M$, as determined by evaluation $B$, shall be the value stored by some side effect $A$ that modifies $M$, where $B$ happens after $A$. [Note: The set of such side effects is also modified by the rest of the rules defined here and in particular. — end note]

14 If an operation that modifies an object $M$ happens before an operation $B$ that modifies $M$, then $A$ shall be earlier than $B$ in the modification order of $M$. [Note: This requirement is known as write-write coherence. — end note]
