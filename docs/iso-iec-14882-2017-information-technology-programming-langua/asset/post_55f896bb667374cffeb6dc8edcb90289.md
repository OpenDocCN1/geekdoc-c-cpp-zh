## 16.2 Declaration matching

¹ Function declarations of the same name refer to the same function if they are in the same scope and have equivalent parameter declarations (6.1). A function member of a derived class is not in the same scope as a function member of the base class. [Example:
```cpp
struct B {
    int f();
};
struct D : B {
    int f(const char);
};
```

² When a parameter type has a function type, such as in the case of a parameter type that is a pointer to function, the const and volatile type-specifiers at the outermost level of the type specification for the inner function are also ignored.

```cpp
D::f(const char*) hides B::f(int) rather than overloading.
void h(D* pd) {
    pd->f(int);             // error:
    pd->f(const char);      // OK
    pd->D::f("asdf");          // OK, calls D::f
}
```

³ A locally declared function is not in the same scope as a function in a containing scope. [Example:
void f(const char*);
void g() {
    extern void f(int);
    f("asdf");               // error: f(int) hides f(char*)
} // so there is no f(char*) in this scope
void caller() {
    extern void callee(int, int);
    extern void callee(int);
    callee(int, int);        // hides callee(int, int)
    callee(int);             // error: only callee(int) in scope
}

⁴ Different versions of an overloaded function can give different access rules. [Example:
```cpp
class buffer {
private:
    char* p;
    int size;
protected:
public:
    buffer(int s, char*) { size = s; p = new char[size]; };
    buffer(int s) { p = new char[s]; };
};
```

## 16.3 Overload resolution

Overload resolution is a mechanism for selecting the best function to call from a list of expressions that are the arguments of the call and candidate functions that can be based on the context of the call. The selection criteria for the best function are the number of arguments, how well the arguments match the parameter-type-list of the candidate function, how well (for non-static member functions) the object matches the implicit parameter, and other properties of the candidate function [Note: The function selected by overload resolution is not guaranteed to be appropriate for the context. Other restrictions, such as the accessibility of the function, can make its use in the calling context ill-formed — note].

² Overload resolution selects the function to call in seven distinct contexts within the language:
(2.1) invocation of a function named in the function syntax (16.3.1.1);
(2.2) invocation of a function call operator, a pointer-to-pointer conversion function, a reference-to-pointer-function conversion function, or a reference-to-function conversion function on a class object named in the function syntax (16.3.1.2);
(2.3) invocation of the operator referenced in an expression (16.3.1.2);
(2.4) invocation of a constructor for default- or de-initialization (11.6) of class objects (16.3.1.3);
(2.5) invocation of a user-defined constructor for copy-initialization (11.6) of a class object (16.3.1.4);
(2.6) invocation of a conversion function for initialization of an object of a non-class type by an expression of class type (16.3.1.5); and
(2.7) invocation of a conversion function to a guise or class value to which (11.6.3) will be directly accessed (16.3.1.6).

Each of these contexts defines the set of candidates and the list of arguments in its unique way. But, once the candidate functions and lists have been identified, the selection of the best function is the same in all cases:

(2.8) First, a subset of the candidate functions (that have the proper number of arguments and meet other conditions) is selected to form a set of viable functions (16.3.2).

Then the best viable function is selected based on implicit conversion sequences (16.3.3.1) to match each argument to the parameter of each viable function,

³ If a best viable function exists and is unique, overload resolution succeeds and produces the result. Overload resolution fails and the overload is ill-formed. When overload resolution succeeds, and the best function is not ambiguous (Clause 14) in the context in which it is used, the program is ill-formed.

### 16.3.1 Candidate functions and argument lists [over.match.funcs]

¹ The subclause of 16.3.1 describe the set of candidate functions and the argument list submitted to overload in each context where overload resolution is. The source transformations and constructions defined in these subclause are only for the purpose of describing the overload process. Implementation is not required to use such transformations and constructions.

² The set of functions can contain both member and non-member functions to be resolved within the same argument list. For an object context, a member function is considered to have an extra parameter, the implicit object parameter, and static and non-static member functions have an implicit object parameter, but constructors do not.

³ Similarly, when appropriate, the context can construct an argument list that contains an implicit object parameter to match the object to which the function is called. The parameters are associated by position within their respective lists, and the implicit object parameter, if present, is always the first argument.
