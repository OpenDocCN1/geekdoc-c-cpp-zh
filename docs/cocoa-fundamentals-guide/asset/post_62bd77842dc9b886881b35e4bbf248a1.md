## Iterator

The Iterator design pattern provides a way to access the elements of an aggregate object (that is, a collection) sequentially without exposing its underlying representation. The Iterator pattern transfers the responsibility for accessing and traversing the elements of a collection from the collection itself to an iterator object. The Iterator defines an interface for accessing collection elements and keeps track of the current element. Different iterators can carry different traversal policies.

## Enumerators

The NSEnumerator class in the Foundation framework implements the Iterator pattern. The private subclass of the abstract NSEnumerator returns enumerator objects that sequentially traverse various types—arrays, sets, dictionaries (values and keys)—returning objects in the collection clients.

NSDirectoryEnumerator is a distantly related class. This class recursively enumerate the contents of the file system.

## Uses and Limitations

The collection classes use NSArray, NSSet, and NSDictionary include methods that return an enumerator appropriate to the type of collection. All workers work in the same manner. You send next message to the enumerator object in a loop that exits when nil is returned instead of the next object in the collection.

You can use fast enumeration to access the elements of a collection; this language is described in [Fast Enumeration](page 63).

## Mediator

The Mediator pattern defines an object that encapsulates a set of objects interact. Mediator promotes loose coupling by keeping objects from referring to each other explicitly, and it lets you vary their interaction independently. These objects can thus remain reusable.

A "mediator object" in this pattern centralizes complex communication and control logic between objects in a system. These objects tell the mediator object when their state change and, in turn, respond to requests from the mediator.

## Cocoa Classes in the AppKit Framework

The Model-View-Controller design pattern assigns roles to objects in an object-oriented system such as an application. They can be model objects, which contain the data of the application and manipulate data; they can be view objects, which present the data and respond to user actions; or they can be controllers objects, which mediate between the model and view objects. Controllers fit the Mediator pattern.

In Cocoa, controllers can be of two general types: mediating controllers or coordinating controllers. Mediating controllers manage the flow of data between view objects and model objects in an application. Coordinating controllers implement the centralized communication and control logic for an application, acting as delegates for framework objects and as action messages. They are typically NSController objects or instances of NSObject subclasses. They are highly specialized for a particular program, coordinating controllers not to be reusable.

The abstract NSController and its concrete subclasses in the AppKit framework are part of the Cocoa technology of bindings, which automatically synchronizes data contained in model objects and displayed and edited in views. For example, if a user edits a string in a text field, the technology changes—through a mediating controller—to the appropriate property of the bound model object. All programmers need to design their model and, using Interface Builder, establish bindings between the view, controller, and model objects of a program.

Instances of particular controller classes are available from the Interface Builder library and are highly reusable. They provide services such as the management of selections and placeholder values. These objects perform the following functions:

- NSController manages a single model object.
- NSArrayController manages an array of model objects and maintains a selection; it also allows you to add objects to remove objects from the array.
- NSTController enables you to add, remove, and manage model objects in a hierarchical structure.
- NSUserDefaultsController provides a convenient interface to the preferences (defaults) system.

## Uses and Limitations

Generally you use NSController objects as mediating controllers because these objects are designed to communicate data between the view objects and model objects of an application. To use a mediating controller, you typically drag the object from the Interface Builder library, select the model-property keys, and establish the bindings between view and model objects using the Bindings pane of the Interface Builder window. You can also subclass NSController or one of its subclasses to get more specialized behavior.

You can potentially make bindings between almost any pair of objects as long as those objects comply with the NSKeyValue and NSValueObserving informal protocols. But to get all the benefits the NSController and its subclasses give you, it is to make better bindings through mediating controllers.

Coordinating controllers central communication and control logic in an application by:

- Maintaining outlets to model and view objects (outlets are instance variables that hold connections or references to other objects)
- Responding to user manipulations of view objects through target-action (see "The Target-Action Mechanism" (page 143))
- Acting as a delegate for messages sent by framework objects (see "Delegation" (page 145))

You usually make all of the above connections—outlets, target-action, and delegates—in Interface Builder, which archives them in the application's nib file.

> Further Reading: "The Model-View-Controller Design Pattern" (page 160) for a discussion of mediating coordinators, coordinating controllers, and design decisions related to controllers. Cocoa Bindings Programming describes the mediating controller classes in detail.

## View Controllers in UIKit

Applications running in iOS frequently use a modal and navigation user-interface design for presenting screen-size chunks of the application's data model. An application may have a navigation bar and toolbar, and between these objects is the current view of application data. Users can tap buttons on the toolbar to select a (data) objects; at each level the current view presents more detail. At the end of this hierarchy is often it that the user can inspect or edit. In application, of course, is free to use a navigation bar or just a toolbar.

View controllers—that inherit from ViewController—are central to this design. ViewController is an abstract class that you can subclass to manage a particular view. The UIKit framework also provides ViewController subclasses for managing navigation bar and toolbar objects: UINavigationController and UITabBarController. As depicted in Figure 4-4, a tab-bar controller can manage a number of navigation controllers, which in turn can manage one or more view controllers, each with its associated view object. In addition to managing views (including overlay views), a view controller specifies the buttons and titles that are displayed in the navigation bar.

To learn more about view controllers, see ViewController Programming Guide for iOS.
