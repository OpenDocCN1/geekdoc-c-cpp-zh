## Adding Behavior to a Cocoa Program

When you develop a Cocoa program in Objective-C, you won't be on one design you want. You'll be drawing the work done by Apple and others, on the classes they've developed and packaged in Objective-C frameworks. These frameworks give you a set of interdependent classes that work together to structure a part—often a substantial part—of your program.

This chapter describes what it's like to write an Objective-C program using a Cocoa framework. It also gives you the basic information you need to know to make a subclass of a framework class.

### Starting Up

Using a framework of Objective-C classes and their methods differs from using a library of C functions. With a library of C functions, you can pretty pick which functions to use and when to use them, depending on the program you're trying to write. On the other hand, it imposes a design on your program, or at least a certain problem space you are trying to address. With a procedural program, you call library functions as necessary to get the work of the program done. Using an object-oriented framework is similar in that you must invoke methods of the framework to do the work of the program. However, you'll also need to customize the framework and adapt it to your needs by implementing methods that the framework will call. These methods are hooks that introduce your code into the structure imposed by the framework, augmenting it with the behavior that characterizes your program. In a sense, the usual roles of program and library are reversed. Instead of Incorporating library code into your program, you incorporate your code into the framework.

You can gain some insight into the relationship between custom code and framework by considering what takes place when a Cocoa program begins.

### What Happens in the main Function

Objective-C programs begin executing where Cocoa programs do, in the main function. In a complex Objective-C program, the job of main is fairly simple. It consists of two steps:

- Set up a core group of objects.
- Turn program control over those objects.

Objects in the core group create other objects as the program runs, and those objects might create other objects. From time to time, the program might also load classes, archive instances, connect to remote methods, and find other resources as they need. However, all that's required at the outset is enough structure—enough of the object network—to handle the program's initial tasks. The main function puts this initial structure in place and gets it ready for the task ahead.

Typically, one of the core objects has the responsibility for overseeing the program or controlling its input. When the code structure is ready, main sets this overseer to work. If the program is a command-line tool or a background server, what this entails might be as simple as command-line parameters or opening a remote connection. For the most common type of Cocoa program, what happens is a bit more involved.

For an application, the core group of objects that must include such objects that draw the user interface, or at least part of it (such as an application's menu), must appear on the screen when the user launches the application. If the visual user interface is on screen, the application is driven by external events, the most important of which are initiated by users: clicking a button, choosing a menu item, drawing an icon, typing something in a field, and so on. Each such event action—reported to the application with a good deal of information about the circumstances of the action—for example, which key was pressed, whether the mouse button was pressed or released, where the cursor was located, and window was accessed.

An application gets an event, it looks at it, and responds to it—often by drawing a part of the user interface—then waits for the next event. It keeps events, one after another, as long as the user or some source (such as a timer) launches them. From the time it is launched until the time it terminates, almost everything the application is driven by user actions in the form of events.

The mechanism for getting and responding to events is the main loop (called main because an application can set up subordinate loops for brief periods). An event loop is essentially a run loop with one or more input sources attached to it. The object in the core group is responsible for running the main loop—getting an event, dispatching the event to the object or objects that can handle it, and then getting the next. In a Cocoa application, this coordinating object is the global application object. In Mac OS X, this is an instance of NSApplication, and in iOS, it is an instance of UIApplication.

### Using Cocoa Framework

Library functions impose few restrictions on the programs that use; you can call them whenever you need to. The methods in an object-oriented library or framework, on the other hand, are tied to class definitions and can't be invoked unless you create or obtain an object that has access to those definitions. Moreover, in most programs the object must be connected to at least one object so that it can operate in the program network. A framework defines a component; to access its services, you need craft it into the structure of your application.

That said, classes generate instances that behave like a set of library functions. You simply create an instance, initialize it, and either send it a message to accomplish a task or insert it into a waiting slot in your program. For example, you can use the NSFileManager class to perform various file-system operations, such as copying, and deleting files. If you need to display an alert dialog, you would create an instance of the NSAlert class—or, with UIKit, an instance of the UIAlert class—and send it the.

### Kinds of Framework Classes

The classes in a Cocoa framework deliver their services in four:

- **Off the shelf. Some classes define off-the objects, ready to be used. You simply create instances of class and initialize them as needed. For the AppKit framework, subclasses of NSControl, such as NSTextField, NSButton, and NSTableView, fall into this category. The corresponding UIKit classes are UILabel, UITextField, UIButton, and UIView. You typically create and initialize off-the objects using Interface Builder, you can create and initialize them programmatically.**
- **Behind the scenes. As a program runs, Cocoa creates some framework objects for behind the scenes. You don't need to explicitly allocate and initialize these objects; they are done for you. For the classes that are private, they are necessary to implement the desired behavior.**
