
# Cocoa Objects

## A Composite Object: An Example

To illustrate the use of a composite object, imagine you have a mutable array object that tests changes against some validation criteria before allowing any modification to the array's contents. The example follows a class called ValidatingArray, which contains a standard mutable array object. ValidatingArray overrides all of the primitive methods declared in its superclasses, NSArray and NSMutableArray. It also delays the array, validatingArray, and init methods, which can be used to create and initialize an instance.

```objc
#import <foundation/foundation.h>

interface ValidatingArray : NSMutableArray

    NSMutableArray *embeddedArray;

+validatingArray;
-init;
-(unsigned)count;
-(object) objectAtIndex:(unsigned)index;
-(void)addObject:(object)at:(unsigned)index;
-(void)replaceObject:(object)at:(unsigned)index;
-(void)removeLastObject;
-(void)insertObject:(object)at:(unsigned)index;
-(void)removeAtIndex:(unsigned)index;

@end
```

The implementation file shows how in an init method of the ValidatingArray class, the embedded object is created and assigned to the embeddedArray variable. Messages that access the array don't modify its contents are relayed to the embedded object. Messages that could change the contents are scrutinized (in pseudocode) and relayed only if they pass the hypothetical validation test.

```objc
#import "ValidatingArray.h"

@implementation ValidatingArray

-init {
    self = [super init];
    if (self) {
        embeddedArray = [[NSMutableArray allocWithZone:zone] init];
    }
    return self;
}

+validatingArray {
    return [[self alloc] autorelease];
}

-(unsigned)count {
    return [embeddedArray count];
}

-objectIndex:(unsigned)index {
    return [embeddedArray objectAtIndexAt:index];
}

(void)addObject:object {
    /* modification is valid */
    [embeddedArray addObject:object];
}

(void)replaceObjectAtIndex:(unsigned)index withObject:object {
    if (* modification is valid *) {
        [embeddedArray replaceObjectAtIndex:index withObject:object];
    }
}

(void)removeLastObject {
    if (* modification is valid *) {
        [embeddedArray removeLastObject];
    }
}

(void)insertObject:object objectAtIndex:(unsigned)index {
    if (* modification is valid *) {
        [embeddedArray insertObject:object objectAtIndex:index];
    }
}

(void)removeObjectAtIndex:(unsigned)index {
    if (* modification is valid *) {
        [embeddedArray removeObjectAtIndex:index];
    }
}
@end
```

## Toll-Free Bridging

There are a number of data types in the Core Foundation framework and the Foundation framework that can be used interchangeably. This capability, called toll-free bridging, means that you can use the same data type as the parameter to a Core Foundation call or as the receiver of an Objective-C message. For example, NSLocale (NSLocale Class Reference) is interchangeable with its Core Foundation counterpart, CFLocale (CFLocale Reference). Therefore, in a method where you use an NSLocale * parameter, you can pass a CFLocaleRef, and in a function where you see a CFLocaleRef, you can cast one to the other to suppress warnings, as illustrated in the following.

```objc
NSLocale *locale = [NSLocale alloc] initWithIdentifier:@"en_GB"];
CFLocaleRef gbLocale = (CFLocaleRef)locale;
NSString *cfidentifier = [CFLocaleGetIdentifier(gbLocale)];
NSLog("identifier=%@", (NSString *)cfidentifier);
// cast identifier to en="GB"
CFRelease((CFLocaleRef)locale);
```

```objc
CFLocaleRef myLocale = CFLocaleCopyCurrent();
NSLocale * myNSLocale = (NSLocale *)myLocale;
[myNSLocale autorelease];
NSString *identifier = [myNSLocale localeIdentifier];
CFShow((CFString*)@identifier stringByAppendingString:identifier);
// logs identifier for current locale
```

Note from the example that the memory management functions and methods are also interchangeable—you can use CFRelease with a Cocoa object and release with a Foundation object.

> Note: When using garbage collection, there are important differences to how memory works for Cocoa objects and Foundation objects. See "Using Foundation with Garbage Collection" for details.

## Creating a Singleton Instance

Some classes of the Foundation and AppKit create singleton objects. In a strict implementation, a singleton is the sole instance of a class in the current process. You can have a more flexible singleton implementation in which a factory method returns the same instance, but you can allocate and initialize additional instances. The FileManager class fits this latter pattern, whereas the UIApplication fits the former. When you ask for an instance of UIApplication, it passes you reference to the sole instance, allocating and initializing it if it does not.

A singleton object acts as a class of control, directing or coordinating the services of the class. Your class should define a singleton instance rather than multiple instances when there is conceptually only one instance (with example, NSString). You use instances rather than factory methods or functions when it is conceivable that there might be multiple instances.

To create a singleton as the sole instance of a class in the current process, you need to have an implementation similar to Listing 2-15. This code does the following:

- It creates a static instance of your singleton object and initializes it to nil.
- In your factory method for the class (named something like "sharedInstance" or "sharedManager"), it generates an instance of the class but if the static instance is nil.
- It overrides the allocWithZone method to ensure that an instance is not allocated if someone tries to allocate and initialize your class instead of using the class factory method. Instead, it returns the shared object.
