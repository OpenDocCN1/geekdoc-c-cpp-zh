# Cocoa Design Patterns

In your framework classes and in its languages and runtime, Cocoa has already implemented many of the cataloged patterns for you. These implementations are described in [How Cocoa Adapts Design Patterns](page 139). You can satisfy many of your development requirements by using one of the "off-the-shelf" adaptations of design pattern. You may decide your problem and context demands a brand new pattern-design of your own. The important thing is to be aware of patterns when you are developing software and to use them in designs when appropriate.

# How Cocoa Adapts Design Patterns

You can find adaptations of design patterns throughout Cocoa, in both its OS X and iOS versions. Mechanisms and architectures based on patterns are common in Cocoa frameworks and in the Objective-C runtime and language. Cocoa often puts its distinctive spin on a pattern because its designs are influenced by such language capabilities or existing architectures.

This section contains summaries of the design patterns cataloged in Design Patterns: Elements of Reusable Object-Oriented Software. Each section not only summarizes the pattern but also discusses the Cocoa implementations of it. Only patterns that are implemented are listed, and each description of a pattern in the following sections pertains to a particular Cocoa context.

Implementation of design patterns in Cocoa come in various forms. Some of the designs described in the following sections—such as protocols and categories—are features of the Objective-C language. In some cases, the "instance of a pattern" is implemented in one class or a group of related classes (for example, class clusters and singleton classes). And in others the pattern adaptation is a major framework architecture, which the responder chain. Some of the pattern-based mechanisms get almost "free" while others require some work on your part. Even if Cocoa does not implement a pattern, you are encouraged to do so when situations warrant it; for example, object composition (Decorator) is a better technique than subclassing for extending class behavior.

Two design patterns are reserved for later sections, Model-View-Controller (MVC) and object modeling. MVC is a compound, or aggregate pattern, meaning that it is based on several catalog patterns. Object modeling has no counterpart in the Gang of Four, originating from the domain of relational databases. MVC and object modeling are the most pervasive and design patterns in Cocoa, and to a large extent they are interrelated. They play a crucial role in the design of several technologies, including bindings, undo management, scripting, and the document architecture. To learn more about patterns, see [The Model-View-Controller Design Pattern](page 166) and [Object Modeling](page 167).

# Abstract Factory

The Abstract Factory pattern provides an interface for creating families of related or dependent objects without specifying their concrete classes. The client is decoupled from any of the specifics of the object obtained from the factory.

# Class Cluster

A class cluster is an architecture that groups a number of private concrete subclasses under a public abstract superclass. The abstract superclass declares methods for creating instances of its private subclasses. The superclass returns an object of the proper concrete subclass based on the creation method invoked. Each object may belong to a different private subclass.
