# CHAPTER 5

Communicating with Objects

Because it is an instance variable, an outlet becomes part of an object's encapsulated data. An outlet is more than a simple instance variable. The connection between an object and its outlets is always available in a nib whenever the file is loaded, each connection is unconnected and reestablished, and whenever it becomes necessary to send messages to the other object. The type qualifier `IBOutlet` is a tag applied to an instance-variable declaration that the Interface Builder application can recognize the instance variable as an outlet and synchronize the connection and interface of Xcode.

You connect an outlet in Interface Builder, you must first declare an outlet in the header file of your custom class by tagging the variable with the `IBOutlet`.

An application typically sets outlets between its controller objects and objects on the user interface, but they can be made between any objects that be represented as instances in Interface Builder, even between two custom objects. With any instance variable, you should be able to justify its inclusion in a class; the more instance variables an object has, the more memory it takes. If there are other ways to obtain a reference to an object, such as finding it through its index position in a matrix, or through its inclusion as a function parameter, or using a tag (assigned unique identifier), you should do that instead.

Outlets are a form of object composition, which is a dynamic pattern that requires an outlet to somehow acquire references to its constituent objects so that it can send messages to them. It typically holds these other objects as instance variables. These variables must be initialized with the appropriate references at some point during the execution of the program.

# Delegates and Data Sources

A delegate is an object that acts on behalf of, or in coordination with, another object when that object encounters an event in a program. The delegating object is often a responder—that is, an object inheriting from `Responder` in AppKit or `Responder` in UIKit—that is responding to a user event. The delegate is an object delegated control of the user interface for that event, or is at least to interpret the event in an application-specific manner.

To better appreciate the value of delegation, it helps to consider an off-shelf control such as a text field (instance of `NSTextField` or `UITextField`) or a view (instance of `NSView` or `UIView`). These objects are designed to fulfill a specific role in a generic fashion; however the AppKit framework allows for manipulation of controls and handles such as closing, resizing, and moving the physical view. This restricted and generic behavior necessarily limits what the object can know about how an event (or will affect) something in the application, especially when the affected behavior is specific to your application. Delegation provides a way for your custom to communicate application-specific behavior to the off-the-shelf.

The programming mechanism of delegation gives objects a chance to coordinate their appearance and state with changes elsewhere usually by user actions. More importantly, delegation makes it possible for one object to alter the behavior of another object without the need to inherit from it. The delegate is almost always one of your custom objects, and by definition it incorporates application-specific logic that the generic and delegating object cannot possibly know.
