# The Cocoa Frameworks

What makes a Cocoa program? It's not really the language, because you can use a variety of languages in Cocoa development. It's not the development tools, because you could create a Cocoa application from the command line (although that would be a complex, time-consuming task). No, what all Cocoa frameworks have in—what makes them distinct—is they are composed of objects that inherit largely from the root class, and that are ultimately based on the Objective-C runtime. This statement is also true of all Cocoa frameworks.

> **Note:** The statement about the root class needs to be first. The Foundation framework supplies another root, `NSProxy`; however, `NSProxy` is rarely used in Cocoa programming. Second, you could create your own root class, but that would be a lot of work (entailing the writing of code that interacts with the Objective-C runtime) and probably not worth your time.

On any system there are many Cocoa frameworks, and Apple and third-party vendors are releasing more frameworks all the time. Despite this abundance of Cocoa frameworks, two of them stand out on each platform as core frameworks:

- In OS X: Foundation and AppKit
- In iOS: Foundation and UIKit

The Foundation, AppKit, and UIKit frameworks are essential to Cocoa application development for Mac OS X unless you link against them. If you link against (and use the classes of) the AppKit, you cannot develop a Cocoa application for iOS unless you link against (and use the classes of) UIKit. Moreover, you cannot develop Cocoa software of any kind unless you link against (and use the classes of) the Foundation framework. (Linking against the right frameworks in Mac OS X happens automatically when you link against the Cocoa umbrella framework.) Classes, functions, data types, and constants in Foundation and the AppKit have a prefix of "NS"; classes, functions, data types, and constants in UIKit have a prefix of "UI".

> **Note:** In Mac OS X version 10.5 the Cocoa frameworks were ported to support 64-bit addressing. iOS also supports 64-bit addressing. As part of this effort, various general changes have been made to the Cocoa API, most significantly the introduction of the NSInteger and NSUInt types (replacing int and unsigned where appropriate) and the CGFloat type (replacing most instances of float). Most applications have no immediate need to make the transition to 64-bit, but for those that, porto tools and guidelines are available. 64-Bit Transition Guide for Cocoa covers these matters in detail.

The Cocoa frameworks handle many low-level tasks for you. For example, classes that store and manipulate integer and floating-point values automatically handle the endianness of these values for you.

The following sections survey the features and classes of the three core Cocoa frameworks and describe some of the secondary frameworks. Because each of these core frameworks has dozens of classes, the descriptions of the core frameworks categorize classes by their function. Although these categorizations have a strong logic basis, one can plausibly group classes in other ways.

# Foundation

The Foundation framework defines a base layer of classes that can be used for any type of Cocoa program. The criterion selecting classes in Foundation from those in the AppKit is the user interface. If an object doesn't either appear in a user interface or isn't exclusively used to support a user interface, its class belongs in Foundation. You can create Cocoa programs that use Foundation and no other framework; examples of these are command-line tools and Internet services.

The Foundation framework was designed with certain goals in mind:

- Define basic behavior and introduce consistent conventions for such things as memory management, object mutability, and notifications.
- Support internationalization and localization with (among other things) bundle technology and Unicode strings.
- Support object persistence.
- Provide some measure of operating-system independence to support portability.
- Provide object wrappers or equivalents for programmatic primitives, such as numeric values, strings, and collections. It also provides classes for accessing underlying system services and entities, such as ports, threads, and file systems.

Cocoa applications, by definition link either against the AppKit framework or UIKit framework, invariably must link against the Foundation framework as share the root class, NSObject, and many if most of the AppKit and UIKit methods and functions have Foundation objects as parameters or return values. Some Foundation classes may seem designed for applications—NSManager and NSUserDefaults, to name two—but they are included in Foundation because they can be used for them that do not need a user interface.

# Foundation Paradigms and Policies

Foundation introduces several paradigms and policies to Cocoa programming to ensure consistent behavior and expectations among the objects of a project in certain situations:

- **Object retention and disposal.** The Objective-C runtime and Foundation give Cocoa programs two ways to ensure objects persist when they are needed and free them when they are longer needed. Garbage collection, which was introduced in Objective-C 2.0, automatically tracks and decomposes objects that you no longer needs, freeing up memory. Foundation still offers the traditional approach of memory management. It institutes a policy of object ownership where that are responsible for releasing objects they have created, copied, or explicitly retained. `NSObject` class and methods `NSAutleasepool` implement a delayed release mechanism and Cocoa programs have a consistent convention for retaining objects for the caller responsible. For more about garbage collection and explicit memory management, see [Object Retention and Disposal].

iOS Garbage collection is not available to applications running iOS.

- **Mutable classes.** Various value and container classes in Foundation have a mutable variant of an immutable class, with the mutable class being a subclass of the immutable one. If you need to dynamically change the value or membership of such an object, you create an instance of the mutable class. Because it inherits from the immutable, you can pass the mutable instance in methods that take the immutable type. For more on object mutability, see "Object Mutability" (page 90).

- **Class clusters.** a class cluster is an set of private subclasses for which the abstract class acts as an interface. Depending on the context (particularly the method you use to create an object), an instance of the optimized class is returned to you. `NSString` and `NSMutableString`, for example, act as brokers for instances of private subclasses optimized for different kinds of storage. Over the years the set of concrete classes has changed several times without breaking applications. For more on class clusters, see "Class Clusters" (page 95).

- **Notifications.** Notification is a major design pattern in Cocoa. It is based on a broadcast mechanism that allows objects (called observers) to be informed of what another object is doing or encountering in the world of user or system events. The object notifying can be unaware of the existence or identity of the observers. There are several types of notifications: synchronous, asynchronous, and distributed. The Foundation notification mechanism is implemented by `NSNotificationCenter`, `NSNotificationQueue`, and `NSDistributedNotificationCenter` classes. For more on, see "Notifications" (page 190).
