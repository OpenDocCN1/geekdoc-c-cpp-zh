Objective-C classes use the protocols they conform to as well as the classes they inherit from. You can check whether a class conforms to a protocol by sending a conformsToProtocol: message:

```objc
if ([anObject conformsToProtocol:@protocol(NSCoding)]) {
    // do something appropriate
}
```

In a declaration of a type—a method, instance variable, or function—you can specify protocol conformance as part of the type. This gives you another level of type checking by the compiler, one that more abstract because it's not tied to particular implementations. You use the same syntactic convention as protocol adopt: Put the protocol name between angle brackets to specify protocol conformance in the type. You can see the dynamic type, used in these declarations—examples:

```objc
- (void)draggingEnded:(id<NSDraggingInfo>)sender;
```

Here the object in the parameter can be any class type, but it must conform to the NSDraggingInfo protocol. Cocoa provides several examples of other protocols besides the ones shown so far. An interesting one is the NSObject protocol—not surprisingly, the NSObject class adopts it, but also does the root class, NSObjectProxy. Through the protocol, NSObjectProxy can interact with the properties of the Objective-C runtime to enable reference counting, introspection, and other aspects of object behavior.

# Declared Properties

In the object modeling design pattern (the ‘Object Modeling’ (page 167)) objects have properties. Properties consist of attributes, such as title and color, and an object's relationships with other objects. In traditional Objective-C, you define properties by declaring instance variables, and enforce encapsulation by implementing accessor methods to get and set the values of those. This is a tedious and error-prone task, especially when memory-management is a concern (see “Storing and Accessing Properties” (page 123)).

Objective-C 2.0, which was introduced in Mac OS X 1.0, offers a syntax for declaring properties and specifying how they are accessed. Declaring a property is a kind of shortcut for declaring a setter and getter method for the property. With properties, you no longer have to implement accessor methods. Direct access to values is also available through a new dot-notation syntax. There are three aspects to properties: declaration, implementation, and access.

You can declare properties however they may be declared in a class, category, or property declaration. The syntax for declaring properties is:

```objc
@property(attributes..) type propertyName
```

where attributes are one or more optional attributes (comma-separated if multiple) that affect how the compiler stores instances and synthesizes accessor methods. The type element specifies an object type, declared type, or scalar type, such as id, NSString *, or float. The property must be backed by an instance variable of the same type and name.

The possible attributes in a property declaration are listed in Table 2-1.

# Object-Oriented Programming in Objective-C

**Table 2-1** Attributes for declared properties

| Attribute | Effect |
|---|---|
| getter=setName | Specifies the names of getter and setter accessor methods (see "Storing and Accessing Properties" (page 123)). You specify these when you are implementing your own accessor methods and want to control their names. |
| readonly | Indicates that the property can only be read, not written to. The compiler does not synthesize a setter accessor or allow unsynthesized one to be called. |
| readwrite | Indicates that the property can be read and written to. This is the default if `readonly` is not specified. |
| assign | Specifies that simple assignment should be used in the implementation of the setter; this is the default. If properties are declared in a non-garbage-collected program, you must specify `retain` or `copy` for properties that are objects. |
| retain | Specifies that `retain` should be sent to the property (which must be an object type) upon assignment. Note that `retain` is not in a garbage-collected environment. |
| copy | Specifies that `copy` should be sent to the property (which must be an object type) upon assignment. |
| atomic | Specifies that the property is thread-safe. This is the default if atomic is not specified. |
| nonatomic | Indicates that the property is not thread-safe. This is faster but requires the programmer to ensure synchronization if needed. Use this when the property is only accessed from a single thread or in a single-threaded environment. |
