To make each property of a subclass compliant with the requirements of key-value coding, do one of the following:

- For an attribute or a-to-one relationship named key, implement accessor methods named key (getter) and setKey: (setter). For example, if you have a property named salary, you would have accessor methods salary and setSalary: (if the compiler synthesizes a declared property, it follows this pattern, unless otherwise).
- For a to-many relationship, if the property is based on an instance variable that is a collection (for example, an NSArray object) or an instance method that returns a collection, give the getter method the same name as the property (for example, employees). If the property is mutable, the getter method does not return a mutable collection (as as NSMutableArray); you must insertObject:forKeyAtIndex: and removeObjectForKeyIndex:. If the instance is not a collection and the getter method does not return a collection, you must implement other NSObjectCoding methods.

To make your object KVO compliant, ensure your object is KVC compliant if you are satisfied with automatic notification, you may choose to implement manual key-value observing, which requires additional work.

# Error Handling

It is axiomatic for any programming discipline that the programmer properly handle errors. However, what is proper often varies by programming language, application environment, and other factors. Cocoa has its own set of conventions and prescriptions for handling errors in subclass code.

- If the error encountered in a method implementation is a system-level or Objective-C runtime error, create and raise an exception, if necessary, and handle it, if possible.

In Cocoa, exceptions are typically reserved for programming or unexpected runtime errors such as out-of-bounds collection access, attempts to mutate objects, sending invalid message, and losing the connection to the window server. You usually take care of these errors when an application is being created rather than runtime. Cocoa defines predefined sets of errors that you can catch with an error handler. For information on predefined codes and the procedure and API for raising exceptions, Exception Programming Topics.

- For other sorts of errors, including expected runtime errors, return nil, NO, NULL, or some type-safe object from zero to the caller. Examples include a failure to initialize an object, the inability to establish a network connection, or a failure to locate an object in a collection. Use an NSError object if you feel necessary to return supplemental information about the error to the sender.

An NSError object encapsulates information about an error, including an error code (which can be specific to Mac, POSIX, or OS domains) and a dictionary of program-specific information. The negative value that is returned (nil, NO, and so) should be the principal indicator of error; if you communicate more specific error information, return an NSError object directly in parameter of the method.

- If the error requires a decision or action from the user, use an UIAlert class (and related facilities) for displaying an alert dialog and handling the user's response. For iOS, you use the facilities of the UIAlertSheet or UIView classes. See Dialogs and Special Panels for information.

For further information about NSError objects, handling errors, and displaying error alerts, see Error Handling Programming Guide.

# Resource Management and Other Efficiencies

There are all sorts of things you can do to enhance the performance of your objects and, of course, the application manages these. These procedures range from multithreading to drawing optimizations. You can learn about these by reading Cocoa Performance Guidelines.

Yet you can, before adopting more advanced performance technique, improve the performance of your objects significantly by following three simple, common-sense guidelines:

- Don't load a resource or allocate memory until you need it.

If you load a resource of the program, as a nil file or an image, and don't use it until much later, or don't use it at all, that is a inefficiency. Your program's memory footprint is bloated for reason. You should load or allocate memory only when there is immediate need.

For example, if your application's preferences are in a separate file, don't load that file until the user chooses Preferences from the menu. The same caution goes for allocating memory for some task; hold off on allocation until the need appears. This technique of lazy-loading or lazy-allocation is easily implemented. For example, if your application has an image that loads, upon the first user request, for displaying in the user interface. Listing 3-9 shows one approach: loading the image in the getter for the image.

# Listing 3-9 Lazy-loading of a resource

```objc
(NSImage*)image {
    if (!image) { // image is an instance variable
        NSString *imagePath = [[NSBundle mainBundle] pathResource:@"Foo" ofType:@"jpg"];
        if (!imagePath) return nil;
        image = [[NSImage alloc] initWithContentsOfFile:imagePath];
    }
    return image;
}
```

- Use the Cocoa API; don't dig down into lower-level programming interfaces.

Much effort goes into making the implementations of the Cocoa frameworks as robust, secure, and efficient as possible. These implementations introduce many interdependencies that you might not be aware of. If, instead of using the Cocoa API for a certain task, you decide to "roll your solution" using lower-level interfaces, you'll probably end up writing code, which introduces a greater risk of error or inefficiency. Also, by leveraging Cocoa, you are better prepared to take advantage of future enhancements at the same time you are insulated from changes in the underlying implementations. So use the Cocoa for programming if one exists and its capabilities answer your needs.

- Practice good memory-management techniques.

If you do not enable garbage collection (which is disabled by default in iOS), perhaps the most important thing you can do to improve the efficiency and robustness of your custom objects is to practice good memory-management techniques. Make sure every object allocation, copy message is matched with a corresponding release message or retain message. Become familiar with the policies and techniques for proper memory management and practice, practice, practice. See Memory Management Programming guide for complete details.
