## Basic Subclass Design

All subclasses, regardless of subclass share certain characteristics when they are well designed. A poorly designed subclass is susceptible to error, hard to use, difficult to extend, and a drag on performance. A well-designed subclass is quite the opposite. This section offers suggestions for designing subclasses that are efficient, robust, and both useful and reusable.

Although this document describes some of the mechanics of crafting a subclass, it focuses primarily on design. It does not describe how you can use the developments Xcode and Interface Builder to automate part of class definition. To learn about these applications, read A Tour of Xcode. The information presented in this section is particularly applicable to model objects. Model Object Implementation Guide discusses the proper design and implementation of model objects at length.

## The Form of a Subclass Definition

Objective-C class consists of an interface and an implementation. By convention, two parts of a class definition go in separate files. The name of the interface file (as ANSI C header files) has an extension of .h; the name of the implementation file has an extension of .m. The name of the file up to the extension is typically the name of the class. For a class named Controller, the files would be:

```
Controller.h
Controller.m
```

The interface file contains a list of property, method, and function declarations that establish the public interface of the class. It also holds declarations of instance variables, constants, string globals, and other data types. The @interface directive introduces the essential declarations of the interface, and the @end directive terminates the class. The @interface directive is particularly important because it identifies the name of the class and the class directly inherited from, using the form:

```
@interface own : Superclass
```

Listing 3-2 gives an example of the interface file for the hypothetical Controller class, before any declarations are made.

> Listing 3-2 The basic structure of an interface file
#import <Foundation/Foundation.h>

```
@interface Controller : NSObject {
}
@end
```

To complete the class interface, you must make the necessary declarations in the appropriate places in this interface structure, as shown in Figure 3-4.

```
#import <Framework/File.h>
```

The framework must be in one of the standard system locations for frameworks. In the example in Listing 3-2 (page 117), the class interface files the file Foundation.h from the Foundation framework. As in this case, the Cocoa convention is that the header having the same name as the framework contains a list of #import commands that define all public interfaces (and other headers) of the framework. Incidentally, if you're defining part of an application, all you need to do is import the Cocoa.h file of the umbrella framework.

If you must import a header file that is for your project, use question marks rather than angle brackets as delimiters; for example:

```
#import "MyDataTypes.h"
```

You must write all method and property implementations between the @implementation and @end directives. The implementations of functions related to the class can go anywhere in the file, although they are also put between the two directives. Declarations of private types (functions, structures, and so on) typically go between the #import commands and the @implementation directive.

## Overriding Superclass Methods

Custom classes, by definition, modify the behavior of their superclass in some program-specific way. Overriding superclass methods is usually the way to effect this change. When you design a subclass, an essential step is identifying what you are going to override and thinking about how you are going to implement them.

Although "When to Override a Method" (page 113) offers some general guidelines, identifying which superclass methods to override you must investigate the class. Peruse the header files and documentation of the class. Also locate the designated initializer of the subclass, for initialization, you must invoke the superclass version of this method.

Once you identified the methods, you can start—from a practical standpoint—by copying the declarations of the methods to be overridden into your interface file. Then copy those declarations into your .m file as skeleton implementations by replacing the terminating semicolon.

Remember, as discussed in "When to Override a Method" (page 113), a Cocoa framework (not your) code usually invokes the methods that you override. In some situations, you need to let the framework know that you have overridden and not the original. Cocoa gives you various ways to accomplish this. The Interface Builder, for example, allows you to substitute your subclass for a (compatible) framework class in the Inspector window. If you create a custom NSCell class, you can associate it with a particular control using the setCell method of the NSControl.

## Instance Variables

The reason for creating a custom class, aside from modifying the behavior of the superclass, is to add properties to it (The word properties are here in a general sense, identifying both the attributes of an instance of the subclass and the relationships that this instance has to objects.)Given a hypothetical Circle class, if you are going to make a subclass that adds color to the shape, the subclass must carry the attribute of color. To accomplish this, you might add a color instance (most likely backed by an NSColor object for a Mac OS application, or a UIColor object for an iOS application) to the class interface. Instances of your custom class encapsulate this new attribute, holding it as a persistent, characterizing piece of data.

Instance variables in Objective-C are declarations of objects, and data types that are part of the class definition. If they are objects, the declaration can either dynamically type (using id) or statically type the object. The following example shows styles:

```
id delegate;
NSColor *color;
```

Generally, you type an object instance variable when the class membership of the object is indeterminate or unimportant. Objects held as instance variables are created, copied, or explicitly retained—unless they are already retained by a parent. If an instance is archived, it should retain its object unless it decodes and assigns them in initCoder:(For more object archiving and archiving, see "Entry and Exit Points" (page 121)).
