# Model-View-Controller in Cocoa (Mac OS X)

The Model-View-Controller design pattern is fundamental to many mechanisms and technologies. As a consequence, the importance of using MVC in object-oriented design goes beyond attaining greater usability and extensibility for your applications. If you are to incorporate a Cocoa technology that is MVC-based, your application will work well. If its design also follows the MVC pattern, it will be relatively painless to use these technologies if your application has a good MVC separation, but it will take more effort to use such technology if you don't have a good separation.

Cocoa in Mac OS X includes the following architectures, mechanisms, and technologies that are based on Model-View-Controller:

+   - Document architecture. In this architecture, a document-based application consists of a controller object for the entire application (NSDocumentController), a controller object for each document (NSViewController), and an object that combines controller and model roles for each document (NSDocument).

+   - Bindings. MVC is central to the bindings of Cocoa. The concrete subclasses of abstract ViewController provide ready-made controller objects that you can configure to establish bindings between view objects and properly designed models.

+   - Application scripting. When designing an application to make it scriptable, it is essential not only to follow the MVC design pattern but that your application's models are properly designed. Scripting commands that access state and request application behavior should be sent to model objects or controllers.

+   - Core Data. The Core Data framework manages graphs of model objects and ensures the persistence of those by saving them (and retrieving them) a persistent store. Core Data is tightly integrated with the Cocoa bindings technology. The MVC and object design patterns are essential determinants of the Core Data architecture.

+   - Undo. In the architecture, model objects play a central role. The primitive methods of model objects (which are usually their accessor methods) are often where you implement undo and redo operations. For example, you might have such objects specific titles to the undo and redo menu items, or you might have them undo selections in a text view.
