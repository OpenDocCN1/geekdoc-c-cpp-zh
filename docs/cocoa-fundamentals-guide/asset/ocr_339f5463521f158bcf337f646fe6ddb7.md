# Overriding Superclass Methods

Custom classes, by definition, modify the behavior of theirsuperclass in some program-specific way. Overriding superclass methods is usually the way to effect this change. When you design a subclass, an essential step is identifying what you are going to override and thinking about how you are going to implement them.

Although "When to Override a Method" (page 113) offers some general guidelines, identifying which superclass methods to override you must investigate the class. Peruse the header files and documentation of the class. Also locate the designated initializer of the subclass, for initialization, you must invoke the superclass version of this method in your class's designated initializer ("Object Creation" (page 77) for details).

Once you have identified the methods, you can start—from a practical standpoint—by copying the declarations of the methods to be overridden into your interface file. Then copy those declarations into your .m file as skeleton implementations by replacing the terminating semicolon enclosing braces.

Remember, as discussed in "When to Override a Method" (page 113), a Cocoa framework (not your own) code usually invokes the methods that you override. In some situations, you need to let the framework know that you have overridden your version and not the original. Cocoa gives you various ways to accomplish this. The Interface Builder, for example, allows you to substitute your subclass for a (compatible) framework class in the Inspector) window. If you create a custom NSCell class, you can associate it with a particular control using the setCell method of the NSControl.

# Instance Variables

The reason for creating a custom class, aside from modifying the behavior of the superclass, is to add properties to it (The word properties are here in a general sense, identifying both the attributes of an instance of the subclass and the relationships that this instance has to objects.)Given a hypothetical Circle class, if you are going to make a subclass that adds color to the shape, the subclass must carry the attribute of color. To accomplish this, you might add a color instance (most likely backed by an NSColor object for a Mac OS application, or a UIColor object for an iOS application) to the class interface. Instances of your custom class encapsulate this new attribute, holding it as a persistent, characterizing piece of data.

Instance variables in Objective-C are declarations of objects, and data types that are part of the class definition. If they are objects, the declaration can either dynamically type (using id) or statically type the object. The following example shows styles:

```
id delegate;
NSColor *color;
```

Generally, you type an object instance variable when the class membership of the object is indeterminate or unimportant. Objects held as instance variables are created, copied, or explicitly retained—unless they are already retained by a parent. If an instance is archived, it should retain its object unless it decodes and assigns them in initCoder:(For more object archiving and archiving, see "Entry and Exit Points" (page 121)).
