Other clusters of this type also exist, but these clearly illustrate how two abstract nodes cooperate in declaring the programmatic interface to a class cluster. In each of these clusters, one public node declares methods that all clusters can respond to, and the other node declares methods that are only appropriate for cluster objects that allow their contents to be modified.

This factoring of the cluster's interface makes an object-oriented framework's programmatic interface more expressive. For example, imagine an object representing a book that declares this method:

`+ - (NSString *)title: `

The book object could return its own instance variable or create a new string object and return that—it doesn't matter. It's clear from this declaration that the returned string can't be modified. Any attempt to modify the returned object will elicit a compiler warning.

## Creating Subclasses Within a Class Cluster

The class cluster architecture involves a trade-off between simplicity and extensibility. Having a few public clusters stand for a multitude of ones makes it easier to learn and use the classes in a framework subclass, but however it's rarely necessary to create a subclass within any of the clusters. However, the cluster architecture is clearly beneficial. Clusters are used in the Foundation framework in just these situations.

If you find a cluster doesn't provide the functionality you need, then a subclass may be in order. For example, imagine you want to create an array object whose storage is file-based rather than memory-based, as in the `NSArray` class cluster. Because you are using the underlying storage mechanism of the class, you'd have to create a subclass.

On the other hand, in some cases it might be better (and easier) to define a class that embeds within an object from the cluster. In this case, let's say that your program needs to be alerted whenever some data is modified. Creating a simple class that wraps a data object that the Foundation framework defines may be the best approach. An object of this class could intervene in methods that modify the data, intercepting the messages, acting on them, and then forwarding them to the embedded data object.

In summary, if you need to manage your object's storage, create a true subclass. Otherwise, create a composite object, one that embeds a Foundation framework object in an object of your own design. The following sections give more detail on these two approaches.

## A True Subclass

A new class that you create within a class cluster:

- - Be a subclass of the cluster's abstract subclass
- - Declare its own storage
- - Override all initializer methods of the superclass
- - Override the superclass's primitive methods (described below)

Because the cluster's abstract superclass is the publicly visible node in the cluster's hierarchy, the first point is obvious. This implies that the new subclass will inherit the cluster's interface but no instance variables, because the abstract subclass declares none. The second point: The subclass must declare any instance variables it needs. Finally, the subclass must override any method that directly accesses an object's instance variables. Such methods are called `primitive methods`.

A class's primitive methods form the basis for interface. For example, the `NSArray` class, which declares the interface to manage arrays of data, each of which is accessed by index; `NSArray` expresses this abstract notion through its primitive methods, `count` and `objectAtIndex:`. With these as a base, other methods—derived methods—can be implemented. Table 2-4 shows examples of derived methods.

## Table 2-4 Derived methods and their implementations

| Derived Method | Possible Implementation |
| --- | --- |
| `lastObject` | Find the last by sending the array object message: `[self objectAtIndex:(self count-1)]` |
| `containsObject:` | Find an object by repeatedly sending the array object `objectAtIndex:`, message, each time incrementing the index until all objects in the array have been found. |

The division of an interface between primitive and derived methods makes subclasses easier. Your subclass must override inherited primitives, but by doing so all derived methods that it inherits operate properly.

The primitive-derived interface applies to the interface of a fully initialized object. The question of how `init...` methods should be handled in a subclass also needs to be addressed.

In general, a cluster's abstract subclass declares a number of `init...` and `+className` methods. As described in `Creating Instances` (page 96), the abstract class decides which concrete subclass to instantiate your choice of `init...` or `+className` method. You can consider that for the convenience of the subclass. The abstract class has no instance variables, it has no initialization methods.

Your subclass declare its own init... (if it needs to initialize its instance variables) and possibly className. It should not rely on any of those that it inherits. To maintain its link in the initialization, it should invoke its superclass's designated initializer within its own designated initializer. It should also override all other inherited methods and implement them in a reasonable manner. (See "Runtime System" in The Objective-C Programming abstract for a discussion of designated initializers). With a class cluster, the designated initializer of the superclass is always init.

## True Subclasses: An Example

Let's say you want to create a subclass of NSArray, named MonthArray, that returns the name of a month with its index position. However, a MonthArray object won't store the array of months as an instance variable. Instead, the method returns a value given an index position (objectAtIndex:) will return constant strings. Thus, only twelve strings will be allocated, no matter how many MonthArray objects exist in an application.

The MonthArray class is declared as:

```objc
@import <foundation/foundation.h>
interface MonthArray : NSArray

+monthArray;
-(unsigned)count;
-(id)objectAtIndex:(unsigned)index;

@end
```

Note that the MonthArray class does not declare an init... method because it has no instance variables to initialize. The count and objectAtIndex: methods simply cover the inherited primitive methods, as described above.

The implementation of the MonthArray class looks like this:

```objc
@import "MonthArray.h"
@implementation MonthArray
static MonthArray *sharedMonthArray = nil;
static NSString *months[] = {"@January","@February","@March",
@April","@May","@June","@July","@August","@September",
@October","@November","@December"};

+monthArray
if (!sharedMonthArray) {
    sharedMonthArray = [[MonthArray alloc] init];
}
return sharedMonthArray;

-(unsigned)count
return 12;

-(id)objectAtIndex:(unsigned)index
{
    if (index >= [self count]) raise [NSOutOfRangeException:@"%s:%d] beyond bounds:self, @"objectAtIndex:", index];
    return [self count] - 1;
} else
return months[index];
}

@end
```

Because NSMutableArray inherited the primitive methods, the derived methods that it inherits work properly without being overridden. NSArray's lastObject, containsObject:, sortedArrayUsingSelector:objectEnumerator, and other methods work without problems for MonthArray objects.

## A Composite Object

By embedding a private cluster object in an array of your own, you create a composite object. This composite object can rely on the cluster object for its basic functionality, intercepting messages that the composite object wants to handle in such particular way. This architecture reduces the amount of code you must write and lets you take advantage of the test code provided by the Foundation Framework. Figure 2-13 depicts this architecture.

![](img/0c5ea7638a6e08e6bdc6bc222975f6ee_99_0.png)

The composite object must declare itself to be a subclass of the cluster's abstract superclass. As a subclass, it must override the superclass's primitive methods. It can also override derived methods, but this isn't necessary because the derived methods work through the primitive ones.

The count method of the NSArray class is an example; the intervening object's implementation of a method it overrides can be simple as:

```objc
(unsigned)count {
    return [embeddedObject count];
}
```

However, your object could put code for its own purposes in the implementation of any method it overrides.
