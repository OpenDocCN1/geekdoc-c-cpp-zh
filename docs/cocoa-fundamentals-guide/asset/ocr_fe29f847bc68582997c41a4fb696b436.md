# View Objects Present Information to the User

A view knows how to display, and might allow users to edit, the data from the application's model. The view should not be responsible for storing the data it is displaying (This does not mean the view ever actually stores data's displaying, of course. You can cache data or similar tricks for performance reasons). A view can be in charge of displaying just one part of a model object, or a whole model object, or even many different model objects. Views come in many variants.

View objects tend to be reusable and configurable, and they provide consistency across applications. In Cocoa, the AppKit framework defines a large number of view objects and provides many of them in the Interface Builder library. By using the AppKit's view objects, such as NSButton objects, you guarantee that your buttons in application behave just like buttons in any other Cocoa application, assuring a high level of consistency in appearance and behavior across applications.

A view should ensure is displaying the model correctly. Consequently, it needs to know about changes to the model. Because model objects should not be tied to specific views, they need a generic way of identifying that they have changed.

# Controller Objects Tie the Model to the View

A controller object acts as the intermediary between the application's view objects and its model objects. Controllers are often in charge of making sure the views access the model objects they need to display and act as the control through which views learn about changes to the model. Controller objects can also perform-set and coordinating tasks for an application and manage the life cycle of other objects.

In a typical MVC design, users enter a value or indicate choice through a view object, that value or choice is communicated to a controller object. The controller object might interpret the user input in some application-specific way and then tell the model what to do with this input—or it may have the model object reflect a changed value in one of its properties. Based on this user input, controller might also tell a view object to change its appearance or behavior, such as a button to disable itself. When a model object changes—say, a new data source is accessed—the model object communicates change to a controller object, which requests one or more view objects to update accordingly.

Controller objects can be either reusable or nonreuses, depending on their general type. "Types of Cocoa Controller Objects" (page 162) describes the different types of controller objects in Cocoa.

# Combining Roles

One can make the MVC roles played by an object, making an object, for example, fulfill the controller and view roles—in which case, it would be called a view controller. In the same way, you can also have model-controller objects. For some applications, combining roles like this is an acceptable design.
