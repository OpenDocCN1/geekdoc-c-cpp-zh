```
NSAutoreleasePool *arp =\ [[NSAutoreleasePool alloc] init];

int count = 2;
while (count--) {
    NSFoo *obj1 = [[NSFoo alloc] 
[init] autorelease];
    NSFoo *obj2 = [[NSFoo alloc] 
[init] autorelease];
}

[arp release];
```

> iOS Note: Because iOS an application executes in a more memory-constrained environment, the use of autorelease pools is discouraged in methods or blocks of code (for example, loops) where an application creates many objects. Instead, you should explicitly release objects whenever possible.

So far the discussion of the object life cycle has focused on the mechanics of managing objects through cycle. A policy of object ownership guides the use of these mechanisms. This policy can be summarized as follows:

+   * If you create an object by allocating and initializing it (for example, [MyClass alloc init]), you own the object and are responsible for releasing it. This rule also applies if you use the NSObject convenience method new.
* If you copy an object, the copied object and are responsible for releasing it.
* If you retain an object, you have partial ownership of the object and release it when you no longer need it.

Conversely, if you receive an object from some other object, you do not own the object and should not release it. (There are a few exceptions to this rule, which are explicitly noted in the reference documentation).
As with any set of rules, there are exceptions and "gotchas":

+   * If you create an object using a class method (such as the NSMutableArray arrayWithCapacity:), ensure the object you receive has been autoreleased. You should not release the object yourself and retain it if you want to keep it around.
* To avoid cyclic, a child object should never retain its parent. (Parent is the creator of the child or is an object holding the child as an instance variable.)
