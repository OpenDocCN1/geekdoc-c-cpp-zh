
## Class Factory Methods

Further Reading: To learn about approaches to implementing the finalize method, read "Implementing a finalize Method" in Garbage Collection Programming Guide.

Class factory methods are implemented by a class as a convenience. They combine allocation and initialization in one step and return the created object. However, the client receiving this object does not own it and thus (the object-ownership policy) is not responsible for releasing it. These methods are of the form + (type*)className ... (where className excludes any prefix).

Cocoa provides plenty of examples, especially among "value" classes. NSDate includes the following factory methods:

- + (dateWithIntervalNow:(NSTimeInterval)secs);
- (dateWithIntervalReference:(NSTimeInterval)secs);
- (dateWithIntervalSince1970:(NSTimeInterval)secs);

And NSData includes the following factory methods:

```
+ (dataWithBytes:(const void*)bytes length:(unsigned)length);
+ (dataWithNoCopy:(void*)bytes length:(unsigned)length);
+ (dataWithNoCopy:(void*)bytes length:(unsigned)length
  freeDone:(BOOL)done);
+ (dataWithContentsOf:(NSString*)path);
+ (dataWithContentsOf:(URL*)url);
+ (dataWithContentsMappedFile:(NSString*)path);
```

Factory methods can be more than a simple convenience. They can not combine allocation and initialization, but the allocation can inform the initialization. As an example, let's say you might initialize a collection from a property-list that encodes any-number of elements for the collection (NSString objects, NSData objects, NSNumber objects, and so on). Before the factory method can know how much memory to allocate for the collection, it must read and parse the list to determine how many elements there are and what object type these elements are.

Another purpose for a class factory method is to ensure that a class (NSWorkspace, for example) lends a singleton instance. Although an init... method could verify that only one instance exists at any time in a program, it would require the prior allocation of a "raw" instance and, in memory-managed code, would have to release that instance. A factory method, on the other hand, gives you a way to avoid blindly allocating an object that you might not use (see Listing 2-6).

Listing 2-6 A factory method for a singleton instance

```
static AccountManager *defaultManager = nil;

+ (AccountManager*)defaultManager (
  if (!defaultManager) defaultManager = [[alloc allocWithZone:NULL] init];
  return defaultManager;
)
```

## Evaluating Inheritance Relationships

Once you know the class an object belongs to, you probably know a bit about the object. You know its capabilities, and what kinds of messages it can respond to. Even after introspection you are unfamiliar with the class to which an object belongs, you now know enough to send it messages.

The NSObject declares methods for determining an object's position in the class hierarchy. These methods operate at different granularities. The class and superclass instance methods, for example, return the Class objects representing the class and superclass, respectively, of the receiver. These methods require you to compare one Class object with another. Listing 2-7 gives a simple (one might say trivial) example of their use.

- Listing 2-7 Using the class and superclass methods

```
while (id anObject = [objectEnumerator nextObject]) {
  if ([self class] == [anObject superclass]) {
    // do something appropriate...
  }
}
```

> Note: Sometimes you use the class or superclass methods to obtain an appropriate receiver for a class message.

More commonly, to check an object's class affiliation, you would send it an isKindOfClass: or isMemberOfClass: The message returns whether the receiver inherits from an instance of a class or an instance of any class that inherits from that class. A isMemberOfClass: message, on the other hand, tells you if the receiver is an instance of the specified class. The isKindOfClass: method is generally more useful because it you can know at once the complete range of messages you can send to an object. Consider the snippet in Listing 2-8

## Listing 2-8 Using isKindOfClass:[NSData class]

```
if ([item isKindOfClass:[NSData class]]) {
    const unsigned char *bytes = [item bytes];
    unsigned int length = [item length];
}
//
```

By learning that the item inherits from the NSData class, this code knows it can send it the NSData bytes and length messages. The difference becomes apparent if item is an instance of NSMutableData. If you use isMemberOf instead of isKindOfClass; the code in the conditional block is never executed because item is not an instance of NSData but a subclass of NSData.

## Method Implementation and Protocol Conformance

Two of the more powerful introspection methods of NSObject are respondsSelector: and conformsProtocol:. These methods tell you, respectively, whether an object implements a certain method and whether an object conforms to a formal protocol (that, adopts, the protocol, if necessary, and all the methods of the protocol).

You use these in a similar situation to yours. They enable you to discover whether potentially anonymous object can respond appropriately to a particular message or set of messages before you send any of them. By making this check you can avoid the risk of runtime exceptions from unrecognized selectors. The AppKit framework implements protocols—the basis of delegation—by checking delegates implement a delegation method using respondsSelector:prior to invoking that method.

Listing 2-9 shows how you might use respondsSelector: in your code.

- Listing 2-9 Using respondsSelector:

```
(void)doCommandBySelector:(SEL)selector {
    if ([self respondsSelector:selector]) {
        [self performSelector:selector];
    } else {
        // handle not responding to the selector
    }
}
```

Listing 2-10 shows how you might use conformsProtocol: in your code.

- Listing 2-10 Using conformsProtocol:

```
if ([testObject conformsToProtocol:NSMenuItem]) {
    NSLog("Custom Item must conform to MenuItem protocol.", [testObject class]);
    [testObject release];
}
```

## Object Comparison

Although they are not strictly introspection methods, the hash and isEqual methods fulfill a similar role. They are indispensable for identifying and comparing objects. But instead of querying the runtime for information about an object, they rely on class-specific comparison.

The hash and isEqual methods, both declared by the NSObject protocol, are closely related. The hash method must be implemented to return an integer that can be used as address in a hash table. If two objects are equal (determined by isEqual: method), they must have the same hash value. If your object could be included in collections as NSObject objects, you need to define hash and verify the invariant that if two objects are equal, they return the same hash value. The default NSObject implementation of isEqual: simply checks for pointer equality.

Using the isEqual: method is straightforward; it captures the receiver against the object supplied as parameter. Object comparison frequently informs decisions about what should be done with an object. As Listing 2-11 illustrates, you can use isEqual: decide whether perform an action, in this case to save preferences that have been modified.

- Listing 2-11 Using isEqual:

```
(void)saveDefaults {
  NSDictionary *prefs = [self preferences];
  if (!origValues isEqual:prefs]) {
    [Preferences saveDefaults:prefs];
  }
}
```

If you are creating a subclass, you might need to override isEqual to add checks for equality. The subclass must define an attribute that has to be the same value in two instances for them to be considered equal. For example, if you create a subclass of NSObject called MyWidget that contains two variables, name and data, both of these must be the same value for instances of MyWidget to be considered equal. Listing 2-12 illustrates how you might implement isEqual: for the MyWidget class.

- Listing 2-12 Overriding isEqual:

```
(BOOL)isEqual:(id)other {
  if (self == other)
    return YES;
  if (![other isKindOfClass:[self class]])
    return NO;
  return [self isEqual:other];
}
(BOOL)isEqualToWidget:(MyWidget*)widget {
  if (self == widget)
    return YES;
  if ([self name isEqual:[widget name]])
    return NO;
  if ([self data isEqualData:[widget data]])
    return NO;
  return YES;
}
```
