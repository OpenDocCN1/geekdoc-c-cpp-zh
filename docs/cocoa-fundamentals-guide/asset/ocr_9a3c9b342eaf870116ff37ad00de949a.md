# Using Cocoa Framework

Library functions impose few restrictions on the programs that use; you can call them whenever you need to. The methods in an object-oriented library or framework, on the other hand, are tied to class definitions and can't be invoked unless you create or obtain an object that has access to those definitions. Moreover, in most programs the object must be connected to at least one object so that it can operate in the program network. A framework defines a component; to access its services, you need craft it into the structure of your application.

That said, classes generate instances that behave like a set of library functions. You simply create an instance, initialize it, and either send it a message to accomplish a task or insert it into a waiting slot in your program. For example, you can use the NSFileManager class to perform various file-system operations, such as copying, and deleting files. If you need to display an alert dialog, you would create an instance of the NSAlert class—or, with UIKit, an instance of the UIAlert class—and send it the instance.

In general, environments like Cocoa are more than a bag of individual classes that offer their services. They consist of object-oriented frameworks, collections of classes that span space and present an integrated solution to that you can use as needed (with function libraries), a framework maps out and implements an entire structure—or—that you must adapt. Because that model is generic, you can specialize it to meet the requirements of your particular program. Rather than design a program that you plug library into, you your code into the design provided by the framework.

To use a framework, you must accept the model that it defines and employ as many of its classes as necessary to model your program to that model. The classes are mutually defined and come as a group, not individually. At first, the need to adapt your code to a framework model might seem restrictive. But the framework offers many ways in which you can alter and extend its generic behavior. It simply requires you to ensure that Cocoa programs behave the same fundamental ways because they are all based on the same program model.

# Kinds of Framework Classes

The classes in a Cocoa framework deliver their services in four:

+   - **Off the shelf.** Some classes define off-the objects, ready to be used. You simply create instances of class and initialize them as needed. For the AppKit framework, subclasses of NSControl, such as NSTextField, NSButton, and NSTableView, fall into this category. The corresponding UIKit classes are UILabel, UITextField, UIButton, and UIView. You typically create and initialize off-the objects using Interface Builder, you can create and initialize them programmatically.
- **Behind the scenes.** As a program runs, Cocoa creates some framework objects for behind the scenes. You don't need to explicitly allocate and initialize these objects; they are done for you. For the classes that are private, they are necessary to implement the desired behavior.
