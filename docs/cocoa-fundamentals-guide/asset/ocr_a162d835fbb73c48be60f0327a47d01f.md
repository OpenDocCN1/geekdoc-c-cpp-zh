+   * Generically. Some framework classes are generic. A framework might provide some concrete subclasses of the generic class that you can use unchanged. You can—and must in some circumstances—define your own subclasses and override the implementations of certain methods. * Through delegation and notification. Many framework objects keep track of other objects of their actions and delegate. The mechanisms for delivering this information are delegation and notification. A delegating object publishes an interface as a protocol—see “Protocols” (page 59) for details. Clients objects must first register as delegates and implement one or more of this interface. A notifying object publishes the list of notifications, and is free to observe one or more of them. Many framework classes broadcast notifications.

Some classes provide more than one of the kinds of services. For example, you can draw a ready-made NSWindow object from the Interface Library and with only minimal initializations. The NSWindow class provides off-the-shelf interfaces. An NSWindow object also sends messages to its delegates and ports of notifications. You can subclass NSWindow if, for example, you want to have rounds.

It is Cocoa classes in all the last categories—generic and delegation/notification—that offer the most possibilities for integrating your program-specific code into the structure provided by the frameworks. “Inheriting from a Cocoa Class” (page 112) describes in general terms how you use subclasses of framework classes, particularly generic classes. See “Communicating with Objects” (page 175) for information on delegation, notification, and other mechanisms for communicating between objects in a program network.

# Cocoa API Conventions

When you start the classes, methods, and other symbols declared by the Cocoa frameworks, you should be aware of a few conventions that are intended to ensure efficiency and consistency in usage.

+   * Methods that return objects typically return nil to indicate that there was a failure to create an object or that, for any reason, no object was returned. They do not return a status code.

The convention of returning nil is often used to indicate a runtime error or other nonexceptional condition. The Cocoa frameworks handle errors such as an array index out of bounds or an unrecognized selector by raising an exception (which is handled by a top-level handler) and, if the method requires, returning nil.

+   * Some of these methods that return nil may include a parameter for returning error information by reference.

This final parameter takes a pointer to an NSError object. Upon return from a method call that fails (that is, returns nil), you can inspect the error object to determine the cause of the error or you can display the error to a user.

As an example, a method from the NSDocument class:

```
- (initWith:(NSString*)name error:(NSError **)outError);
```

+   * In a similar fashion, methods that perform some system operation (such as reading or writing a file) often return a Boolean value to indicate success or failure.
