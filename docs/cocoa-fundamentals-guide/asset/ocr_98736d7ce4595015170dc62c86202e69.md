# Table 2-2 Important Objective-C defined types and literals

| Type | Description and literal |
| --- | --- |
| id | The dynamic object. Its negative literal is nil. |
| Class | The dynamic class type. Its negative literal is NIL. |
| SEL | The data type (typedef) of a selector. The negative literal of this type is NULL. |
| BOOL | A Boolean type. The literal values are YES and NO. |

In your program control-flow sentences, you can test for the presence (or absence) of the appropriate negative literal to determine how to proceed. For example, the while statement in the SimpleCocoaTool could implement using the word object variable for the presence of a returned object (or, in another sense, the absence of nil):

```
while (word ~ [nextObject]) {
    printf("%s", [word UTF8String]);
}
```

In Objective-C, you can send a message to nil with no ill effects. Return values from messages sent to nil are guaranteed as long as what is returned is an object. See "Messages to nil" in the Objective-C Programming Language for details.

One final thing to note about the SimpleCocoaTool is something that is not readily apparent if you're new to Objective-C. Compare this:

```
Enumerator *enum = [sorted_args enumerator];
```

with this one:

```
AutoreleasePool *pool = [[AutoreleasePool alloc] init];
```

On the surface, they do identify things; both return a reference to an object. However, there is an important semantic difference (for memory-managed code) that has to do with the ownership of the returned object, and the responsibility for freeing it. In the first statement, the SimpleCocoaTool program does not return the object. In the second statement, the program creates the object and owns it. The last thing the program does is to send the release message to the created object, thus freeing it. The only other explicitly created object (the NSCounted instance) is explicitly released at the end of the program. For a summary of the memory-management policy for object ownership and disposal, and the methods to enforce this policy, "How Memory Management Works" (page 73).

# The Root Class

By themselves, the Objective-C language and runtime are not enough to construct the simplest object-oriented program, at least not. Something is missing: a definition of the fundamental behavior and interface to all objects. A root class supplies that definition.
