Adding Behavior to a Cocoa Program

Overriding a method does not have to be a formidable task. You can often make significant change in superclass behavior by a careful reimplementation of the method that entails no more than one or two lines of code. You are not entirely on your own when you implement your own version of a method. You can draw on the classes, methods, functions, and types always provided by the Cocoa frameworks.

# When to Make a Subclass

Just as important as knowing methods of a class to override—and indeed predicting which decision—is identifying those classes to inherit from. Sometimes these decisions can be obvious, and sometimes they can be far from simple. A few design considerations can guide your choice.

First, know the framework. You should become familiar with the purpose and behavior of each class in the framework. Maybe there is a class that already does what you want to do. And if you find a class that does almost what you want, you're in luck. That is a superclass for your subclass. Subclassing is a process of reusing an existing class and specializing it for what you need. Sometimes a subclass needs to override a simple inherited method and have it something slightly different from the original behavior. Subclasses might add one or two attributes to their superclass (instance variables), and then define the methods that access and operate these attributes, integrating them into the subclass behavior.

There are other considerations that can help you decide where your subclass fits into this hierarchy. What is the nature of the application, or which part of the application you are trying to create? Some Cocoa architectures use model-view the document-based architecture defined by AppKit requires you to subclass NSDocument and other classes. To make your Mac OS X application scriptable, you have to subclass one of the scripting classes of AppKit, such as NSScriptCommand.

Another factor is the role that instances of your subclass will play in the application. The Model-View-Controller design pattern, where view objects appear on the user interface; model objects handle application data (and the algorithms that act on data); and controllers mediate between view and model objects. For details, see "Model-View-Controller Design Pattern". Knowing the role each class plays simplifies the decision for which superclass to use. If instances of your class are view objects that do their own drawing and event-handling work, you should probably inherit from NSView (if you are using AppKit) or UIView (if you are using UIKit). If your application needs a controller, you can use either one of the off-the-shelf controllers of AppKit (such as NSViewController), or if you want a different behavior, subclass ViewController or NSObject. If your class is a model class—say, one which represents rows of data in a spreadsheet—you should subclass NSObject or use the Core framework.

iOS Note: The controller classes of the AppKit framework, including ViewController, have no counterparts in UIKit. There are controllers in UIKit—UITViewController, UINavigationController, and UITabBarController—but these are based on a different purpose—navigation and selection (see "Controllers in UIKit" (page 150 for a summary).
