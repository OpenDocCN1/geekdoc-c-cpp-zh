
# How Delegation Works

The design of the delegation mechanism is simple (Figure 5-1). The delegating class has an outlet or property, usually one that is named delegate; if it is an outlet, it includes methods for setting and accessing the value of the outlet. It also declares, without implementing, one or more methods that constitute a formal protocol or an informal protocol. A formal protocol uses optional methods—a feature of Objective-C 2.0—is the preferred approach, but both kinds of protocols are used by the Cocoa frameworks for delegation.

In the informal protocol approach, the delegating class declares methods on a category of NSObject, and the delegate implements only those methods in which it has an interest in coordinating with the delegating object or affecting that object's default behavior. If the delegating class declares a formal protocol, the delegate may choose to implement those methods marked optional, but it must implement the required ones.

The methods of the protocol match significant events handled or anticipated by the delegating object. This object wants either to communicate these events to the delegate or, for pending events, to request input or approval from the delegate. For example, when a user clicks the close button of a window in Mac OS X, the window sends the windowShouldClose message to its delegate; this gives the delegate the opportunity to veto or defer the closing of the window if, for example, the window has associated data that must be saved (see Figure 5-2).

# The Form of Delegation Messages

Delegation methods have a conventional form. They begin with the name of the AppKit or UIKit object delegating—application, window, control, and so on; this name is in lower-case and without “NS” or “UI” prefix. Usually (but not) this object is followed by an auxiliary verb indicating the temporal status of the reported event. This verb, in other words, indicates whether the event is about to occur (“Should” or “Will”) or it has just occurred (“Did” or “Has”). This temporal distinction helps to categorize messages that expect a return value and that don't. Listing 5-1 includes a few AppKit delegation methods that expect a return value.

# Listing 5-1 Sample delegation methods return values

```
(BOOL)application:(NSApplication *)sender
openFile:(NSString *)filename; // NSApplication
(BOOL)application:(UIApplication *)application
handleOpenDocument:(id)sender; // UIApplicationDelegate
(void)tableView:(UITableView *)tableViewRowRowSet
willSelectRows:(IndexSet *)selection; // UITableView
(NSRect)windowWillUseStandardFrame:(NSWindow *)window
defaultFrame:(NSRect *)newFrame; // NSWindow
```

The delegate that implements these methods can block the impending event (by returning NO in the first two methods) or return a suggested value (the index set and the frame rectangle in the last two methods). It can even defer an impending event, for example, the delegate implementing the applicationShouldTerminate:method can delay application termination by returning NSStateTerminateLater.

Other delegation methods are invoked by messages that don't expect a return value and are typed to return void. These messages are purely informational, and the method names often contain "Did"; "Will"; or some other indication of a transpired or impending event. Listing 5-2 shows a few examples of these kinds of delegation method.

# Listing 5-2 delegation methods returning void

```
(void)tableView:(NSTableView*)tableView
    mouseDownInHeaderOfTableColumn:(NSTableColumn*)tableColumn // NSTableView
(void)windowDidMove:(NSNotification*)notification // NSWindow
(void)application:(UIApplication*)application
    willChangeStatusBarFrame:(CGRect)statusBarFrame // UIApplication
(void)applicationWillBecomeActive:(NSNotification*)notification // NSApplication
```

There are couple of things to note about this last group of methods. The first is that an auxiliary view of "Will" (in the third method) does not necessarily mean that a return value is expected. In this case, the event is imminent and cannot be blocked, but the message gives the delegate an opportunity to prepare the program for the event.

The other point of interest concerns the second and last method declarations in Listing 5-2. The sole parameter of these methods is an NSNotification object, which means that these methods are invoked as the result of a particular notification. For example, the windowDidMoveNotification. The section "Notifications" (page 190) discusses notifications in AppKit, but it's important to understand the relationship of notifications to delegation methods. The delegating object automatically makes its delegate an observer of all notifications it posts. All the delegate needs to implement the associated method to get the notification.

To make an instance of your custom class of an AppKit object, simply connect the instance to the delegate outlet or property in Interface Builder. Or you can set it programmatically through the delegate object's setDelegate method or delegate property, preferably early on, such as in the awakeFromNib or applicationDidFinishLaunching method.

# Delegation and the Cocoa Application Frameworks

The delegating object in Cocoa is often a responder—such as application, window, or control. The delegate is typically an object that coordinates some part of the application. The following AppKit classes define a delegate:

- NSApplication
- NSBrowser
- NSControl
- NSDraw
- NSFontManager
- NSFontPanel
- NSMatrix
- NSOutlineView
- NSplitView
- NSTableView
- NSTabView
- NSTextField
- NSTextView
- NSWindow

The UIKit framework uses delegation extensively and always implements it using formal protocols. The application delegate is extremely important in an application running in iOS because it must respond to application-launch, application-quit, low-memory, and other messages from the application. The application delegate must manage the UIApplication protocol.

Delegating objects do not (and should) retain their delegates. However, clients of delegating objects (applications) are responsible for ensuring that their delegates are around to receive messages. To do this, they may need to retain the delegate in memory-managed code. This precaution applies to data sources, notification observers, and targets of action.

Some AppKit classes have a restricted type of delegate called a modal delegate. Objects of these classes (NSOpenPanel, for example) run modal delegates that invoke a handler method in the designated delegate when the user clicks the OK button. Modal delegates are limited in scope to the operation of the modal dialog.

The existence of delegates has other pragmatic uses. For example, with delegates it is easy for two coordinators in the same program to find and communicate with each other. For example, the object controlling the application can easily find the controller of the application's inspector window (assuming it's the current keyWindow) using code to simulate the following:

```
id winWindow = [[NSApp delegate];
```

And you can find the application-controller object—by definition, the delegate of the global application instance—by doing something to the following:

```
id appController = [[NSApp delegate];
```

# Data Sources

A data source is a delegate except that, instead of being delegated control of the user interface, it is delegated control of data. A data source is an outlet held by NSView and UIView objects such as tables and outline views that require a source to populate their rows of visible data. The data source for a view is usually the same object that acts as its delegate, but it can be any object. As the delegate, the data source must implement one or more methods of an informal protocol to supply with the data it needs, and in more advanced implementations, to handle data users directly edit in views.
