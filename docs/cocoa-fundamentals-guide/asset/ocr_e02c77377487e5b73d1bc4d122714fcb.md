The NSControl and NSCell classes, and their subclasses, define a common set of user-interface objects such as buttons, sliders, and browsers that your user can manipulate graphically to control some of your application. Most control objects are with one or more cell objects that implement the details of drawing and handling events. For example, a button comprises an NSObject and an NSButton object.

Controls and cells implement a mechanism that is based on an important design pattern of the AppKit: target-action. A cell can hold information that identifies the message to be sent to a particular object when the cell clicks (or otherwise acts upon it). When a user controls a control (for example, by clicking it), the control extracts the required information from its cell and sends a message to the target. Target action allows giving meaning to a user action by specifying what the target and invoked method should. You would typically use Interface Builder to set these targets and actions by Control-drawing from the control to any other object. or You can also set targets and actions proactively.

Another design pattern-based mechanism of AppKit (and also UIKit) is delegation. In a user interface, such as cells and table views, a delegate is an object that handles of, or in conjunction, the delegating object. It lets to import application-specific logic to the operation of the user interface. For delegation, target-action, and other patterns and mechanisms of AppKit, "Communicating with Objects" (page 175). For discussion of the designs on which these paradigms and mechanisms are based, "Cocoa Design Patterns" (page 137).

The system automatically scales content for rendering on the screen. The AppKit classes support resolution independence in their user-interface objects. # General-User Interface Classes

For the overall functioning of a user interface, the AppKit provides the following classes:

+   **The global application object.** Every application uses a singleton of NSApplication to control the main event loop, keep track of the application's windows and menus, distribute events to the appropriate objects (that is, itself or one of its windows), set up top-level autorelease pools, and receive notification of application-level events. An NSApplication has a delegate (an object that you assign) that notifies when the application starts or terminates, is hidden or activated, should be selected by the user, and so forth. By setting the NSApplication's delegate and implementing the delegate methods, you customize the behavior of your application without having to subclass NSApplication.

+   **Windows and views.** The window and view classes, NSWindow and NSView, also inherit from Responder, and are designed to respond to user actions. An NSApplication maintains a list of NSWindows—for each belonging to the application—and each NSWindow object maintains a hierarchy of NSView objects. The view hierarchy is used for drawing and handling events within a window. An NSWindow object handles window-level events, distributes other events to its views, and provides a drawing area for its views. An NSWindow object also has a delegate allowing you to customize its behavior.
