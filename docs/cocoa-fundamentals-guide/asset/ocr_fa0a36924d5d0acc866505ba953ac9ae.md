# CHAPTER 5

Communicating Objects

# The Target-Action Mechanism

Although delegation, bindings, and notification are useful for handling certain forms of communication between objects in a program, they are not particularly suitable for the most visible sort of communication. A typical application's user interface consists of a number of graphical objects, and perhaps the most common of these objects are controls. A control is a graphical analog of a real-world or logical device (button, slider, checkboxes, and so on); as a real-world control, such as a radio tuner, you use it to convey your intent to some system of which it is a part—that is, an application.

The role of a control is simple: to interpret the intent of the user and some other object to carry out that request. When a user acts on the control, by clicking it or pressing the Return key, the hardware generates an event. The control accepts the event (appropriately packaged for Cocoa) and sends it to an instruction specific to the application. However, events themselves do not give much information about the user's intent; they merely tell you that the user clicked a mouse button or pressed a key. Some mechanism must be called upon to provide the translation between event and instruction. This mechanism is *target-action*.

Cocoa uses the target-action mechanism for communication between a control and another object. This mechanism allows the control and, in Mac OS X itself, to encapsulate the information necessary to send an application-specific instruction to the receiving object—typically an instance of a custom class—is called the *target*. The action is the message that the control sends to the target. The object that is identified in the user event—that is the one that imparts significance to it, and this significance is usually reflected in the name it gives to the action.

# The Target

A target is a receiver of an action message. A control, or more frequently, holds the target of its action message as an outlet (see "Outlets" (page 175)). The target usually is an instance of one of your custom classes, although it can be any Cocoa object class implements the appropriate action method.

You can set the control's target to *nil* and let the target object be determined at runtime. When the target is *nil*, the action object `UIApplication` or `Responder` searches for an appropriate receiver in a prescribed order:

+   1. A key window in Mac OS X responds to key presses for an application and is the receiver of messages from menus and dialogs. An application's main window is the primary focus of user actions and often has key status as well.
2. It tries the object and then the window object's delegate.
3. If the main window is different from the key window, it starts over with the first responder in the main window and works its way up the main window's responder chain to the window object and its delegate.
4. Next, the application object tries to respond. If it can't, it tries its delegate. The application object and its delegate are the receivers of last resort.

> Note: A key window in Mac OS X responds to key presses for an application and is the receiver of messages from menus and dialogs. An application's main window is the primary focus of user actions and often has key status as well.
