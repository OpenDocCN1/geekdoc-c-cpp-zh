## Cocoa API Conventions

When you start the classes, methods, and other symbols declared by the Cocoa frameworks, you should be aware of a few conventions that are intended to ensure efficiency and consistency in usage.

- * Methods that return objects typically return nil to indicate that there was a failure to create an object or that, for any reason, no object was returned. They do not return a status code.

The convention of returning nil is often used to indicate a runtime error or other nonexceptional condition. The Cocoa frameworks handle errors such as an array index out of bounds or an unrecognized selector by raising an exception (which is handled by a top-level handler) and, if the method requires, returning nil.

- * Some of these methods that return nil may include a parameter for returning error information by reference.

This final parameter takes a pointer to an NSError object. Upon return from a method call that fails (that is, returns nil), you can inspect the error object to determine the cause of the error or you can display the error to a user.

As an example, a method from the NSDocument class:

```
- (initWith:(NSString*)name error:(NSError **)outError);
```

- * In a similar fashion, methods that perform some system operation (such as reading or writing a file) often return a Boolean value to indicate success or failure.

These methods might also include a pointer to an NSError object as a final by-reference parameter. For example, this is from the NSData class:

```
- (BOOL)writeToFile:(NSString*)path options:(unsigned)writeOptionsMask error:(NSError **)errorPtr;
```

- * Empty containers are used to indicate a default value or no value—nil is usually not a valid object parameter.

Many examples encapsulate values or collections of objects—for example, instances of NSString, NSDate, NSArray, and NSDictionary. Methods that these objects may accept as any object (for example, @*) to indicate that there is no value or that the default value is used. For an empty string, the following message shows the represented filename for a window to "no value" by specifying an empty string:

```
[Window setRepresentedFilename:@];
```

> Note: The Objective-C construct "characters" creates an NSString object containing the literal characters. Thus, @* would create a string object with no characters—or, an empty string. For more information, see String Programming Guide.

- * The Cocoa frameworks use global constants rather than string literals for dictionary keys, notification and exception, and some methods that take strings.

You should always prefer constants over string literals when you have a choice. By using string constants, you let the compiler to check your spelling and avoid runtime errors.

- * The Cocoa frameworks use Float for coordinate values, CFloat for both coordinate and gradient values, NSPoint (AppKit) or CGPoint (UIKit) for a location in a coordinate system, NSString objects for string values, NSRange for ranges, NSInteger and NSInteger for respectively, signed and unsigned integers. When you design your own API, you should use for similar type consistency.

- * Unless otherwise stated in the documentation or header files, sizes that are returned in methods as frame and bounds (UIView) are in points.

A substantial subset of Cocoa API conventions the naming of classes, methods, functions, constants, and other symbols. You should be aware of these conventions when designing your programmatic interfaces. Some of the important of these naming conventions are the following:

- * Use prefixes for class names and symbols associated with the class, such as functions and type definitions (typedef).

A prefix protects against collisions and helps to differentiate functional areas. The prefix convention is two or three unique uppercase letters, for example, the "AC" in ACCClass.

- * With API names, it's better to be clear than brief.

For example, it's easy to understand what removeObjectAtIndex: does but remove: is ambiguous.

- * Avoid ambiguous names.

A general, overarching API convention pertains to object ownership with memory-managed applications (versus garbage-collected collections). Briefly stated, the convention is that a client owns an object if it creates it (by allocation initialization), copies or retains it (by sending it retain). An owner of an object is responsible for its disposal using release or autorelease to the object when it longer needs it. For more on this subject, see "How Memory Management Works" (page 73) and Memory Management Programming Guide.

## Inheriting from a Cocoa Class

A framework such as AppKit or UIKit defines a program model, because it is generic, many different types of applications can scale. Because the model is generic, it is not surprising that some framework classes are abstract or intentionally incomplete. A class often does much but leaves significant portions of the work unfinished or in a safe "default" fashion.

An application often needs to create a subclass that fills these gaps in its super, supplying the pieces the framework class missing. A subclass is the primary way to add application-specific behavior to a framework. It inherits the ability to work with other objects from the framework. For example, if you create a subclass of NSObject (AppKit), instances of this class will appear to appear in an NSString object, just as NSButton, UITextField, and other framework-defined class objects can.

When you make a subclass, one of your priorities is to implement a specific set of methods declared by a superclass (or in a protocol adopted by a subclass). Reimplementing an inherited method is known as overriding that method.
