The Cocoa version of MVC as a compound pattern has some similarities to the traditional version, and in fact it is quite to construct a working application based on the diagram in Figure 4-6. Using the bindings technology, you can easily create a Cocoa MVC application where views directly observe model objects to receive notifications of state changes. However, there is a theoretical problem with this design. View objects and model objects should be the most reusable objects in an application. View objects represent the "look and feel" of an operation and supports consistency in appearance and behavior is essential, and that requires highly reusable objects. Model objects by definition encapsulate the data associated with a problem domain and perform operations on that data. Design-wise, it's best to keep model and view objects separate from each other, because that enhances their reusability.

In Cocoa applications, notifications of state changes in model objects are communicated to view objects through controller objects. Figure 4-7 shows this different configuration, which appears much cleaner despite the involvement of two more design patterns.

Figure 4-7 Cocoa version of MVC as a compound design pattern

![](bbox=[0.181, 0.638, 0.746, 0.783])

The controller object in this compound design pattern incorporates the Mediator pattern as well as the Strategy pattern; it mediates the flow of data between model and view objects in both directions. Changes in model state are communicated to view objects through controller objects of an application. In addition, view objects observe the Command pattern through their implementation of the target-action mechanism.
