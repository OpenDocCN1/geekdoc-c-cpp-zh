There are some limitations to categories. You cannot use a category to add new instance variables to the class. A category method can override an existing method, it is not recommended that you do so, especially if you want to augment the current behavior. Reason for this is that the category method is part of the class interface, and so there is no way to send a message to super to get the behavior already defined by the class. If you need to change an existing method of a class, it is better to make a subclass of the class.

You can define categories that add to the root class, NSObject.Such methods are available to all class objects that are linked into your code. Informal protocols—the basis for Cocoa delegation mechanism—are declared as categories on NSObject. This wide exposure, however, has its dangers as well as its. The behavior you add to every object through a category on NSObject could have consequences that you might not be able to anticipate, leading to crashes, corruption, or worse.

# Protocols

The Objective-C extension called a protocol is very much like an interface in Java. Both are simply a list of method declarations publishing an interface that any class can choose to implement. The methods in the protocol are invoked by messages sent by an instance of some other class.

The main value of protocols is that, like categories, can be an alternative to subclassing. They yield some of the advantages of multiple inheritance in C++, allowing sharing of interfaces. A protocol is a way to declare an interface while conforming to identity. This interface may expose all or (as is the case) only services the class has to offer. Other classes throughout the class hierarchy, and not necessarily in an inheritance relationship (not to the root class), can implement the methods of protocol and access the published services. With a protocol, classes that have no knowledge of another's identity (that is, class type) can communicate for the specific purpose established by the protocol.

There are two types of protocols: formal and informal. Informal protocols are briefly introduced in "Categories" (page 58). These are categories on NSObject as a consequence, every object with NSObject its root object (as well as class object) implicitly adopts the interface published in the category. To use an informal protocol, a class does not have to implement every method in it, just those it's interested in. For an informal protocol to work, the class declaring the informal protocol must get a positive response to a respondsToSelector: from a target object before sending the object protocol message. (If the target did not implement the method, there would be a runtime exception.)
