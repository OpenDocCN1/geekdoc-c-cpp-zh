## Cocoa Objects

The runtime's message-dispatch machinery enables dynamic binding. When you send a message to a dynamically typed object, the runtime uses the receiver's pointer to locate the object's class, and from there the implementation to invoke. The method is dynamically bound to the message. You don't have to do anything special in your Objective-C code to reap the benefits of dynamic binding. It happens routinely and transparently every time you send a message, to a dynamically typed object.

Dynamic loading, the final type of dynamism, is a feature of Cocoa that depends on Objective-C for runtime. With dynamic support, a Cocoa program can load executable code and resources as they're needed instead of having to load all program components at launch time. The executable code (which is linked to) often contains new classes that become integrated into the runtime image of the program. Both code and resources (including nib files) are packaged in bundles and are explicitly loaded with methods defined in NSBundle class.

This "lazy-loading" of program code and resources improves performance by placing lower memory demands on the system. Even more importantly, loading makes applications extensible. You can devise a plug-in architecture for your application that you and other developers to customize with additional modules that the application can dynamically load months or years after the application is released. If the design is right, the classes in modules will not clash with the classes already in place because each encapsulates its implementation and has its own name.

## Extensions to the Objective-C Language

Objective-C features four types of extensions that are powerful tools in software development: categories, protocols, declared properties, and fact enumeration. Some extensions introduce different techniques for declaring methods and associating them with a class. Others offer convenient ways to declare and access object properties, quickly over collections, handle exceptions, and perform other tasks.

## Categories

Categories give you a way to add methods to a class without having to make a subclass. The methods in the category become part of the class type (within the scope of your program) and are inherited by all the class subclasses. There is no difference between the original methods and the added methods. You can send a message to any instance of the class (or its) to invoke a method defined in the category.

Categories are more than a convenient way to add behavior to a class. You can also use categories to compartmentalize methods, grouping related methods in different categories. Categories can be particularly helpful for organizing large classes; you can put different categories in different source files, for instance, several developers working on the class.

You declare and implement a category just as you do a subclass. Syntactically, the only difference is the name of the category, which follows the @interface or @implementation directive and is in parentheses. For example, say you want to add a method to the NSArray class that prints the description of a collection in a more structured way. In the header file for the category, you would write:

```
#import <Foundation/NSArray> // if Foundation not already imported

@interface NSArray (PrettyPrintElements)
-(NSString*)prettyPrintDescription;
@end
```

Then in the implementation you will write code as:

```objc
#import "PrettyPrintCategory.h"

@implementation NSArray (PrettyPrintElements)
-(NSString*)prettyPrintDescription {
// implementation code...
}
@end
```

There are some limitations to categories. You cannot use a category to add new instance variables to the class. A category method can override an existing method, it is not recommended that you do so, especially if you want to augment the current behavior. Reason for this is that the category method is part of the class interface, and so there is no way to send a message to super to get the behavior already defined by the class. If you need to change an existing method of a class, it is better to make a subclass of the class.

You can define categories that add to the root class, NSObject. Such methods are available to all class objects that are linked into your code. Informal protocols—the basis for Cocoa delegation mechanism—are declared as categories on NSObject. This wide exposure, however, has its dangers as well as its. The behavior you add to every object through a category on NSObject—every object with NSObject its root object (as well as class object) implicitly adopts the interface published in the category—could have consequences that you might not be able to anticipate, leading to crashes, corruption, or worse.

## Protocols

The Objective-C extension called a protocol is very much like an interface in Java. Both are simply a list of method declarations publishing an interface that any class can choose to implement. The methods in the protocol are invoked by messages sent by an instance of some other class.

The main value of protocols is that, like categories, can be an alternative to subclassing. They yield some of the advantages of multiple inheritance in C++, allowing sharing of interfaces. A protocol is a way to declare an interface while conforming to identity. This interface may expose all or (as is the case) only services the class has to offer. Other classes throughout the class hierarchy, and not necessarily in an inheritance relationship (not to the root class), can implement the methods of protocol and access the published services. With a protocol, classes that have no knowledge of another's identity (that is, class type) can communicate for the specific purpose established by the protocol.

There are two types of protocols: formal and informal. Informal protocols are briefly introduced in "Categories" (page 58). These are categories on NSObject as a consequence, every object with NSObject its root object (as well as class object) implicitly adopts the interface published in the category. To use an informal protocol, a class does not have to implement every method in it, just those it's interested in. For an informal protocol to work, the class declaring the informal protocol must get a positive response to a respondsToSelector: from a target object before sending the object protocol message. (If the target did not implement the method, there would be a runtime exception.)

A formal protocol is usually what is designated by the term protocol in Cocoa. It allows a class to formally declare a list of methods that are an interface to a vended service. The Objective-C language and runtime system support formal protocols; the compiler can check for types based on protocols, and objects can introspect at runtime to verify conformance to a protocol. Formal protocols have their own terminology and syntax. The syntax is different for provider and client:

- A provider (which is usually a class) declares the formal protocol.
- A client adopts a formal protocol, and by doing so agrees to implement all required methods of the protocol.
- A class is said to conform to a formal protocol if it adopts the protocol or inherits from a class that adopts it. (Protocols are inherited by subclasses.)

Both the declaration and adoption of a protocol have their syntactic forms in Objective-C. To declare a protocol you must use the @protocol compiler directive. The following example shows the declaration of the NSCCoding protocol (in the Foundation framework's header file NSObject.h).

```objc
@protocol NSCCoding
-(void)encodeWithCoder:(NSCoder *)coder;
-(id)initWithCoder:(NSCoder *)coder;
@end
```

Objective-C 2.0 adds a freedom to formal protocols by giving you the option of declaring optional methods as well as required. In Objective-C 1.0, the adopter of a protocol had to implement all methods of the protocol. In Objective-C 2.0, protocol methods are implicitly required and can be specifically marked as using the @required directive. You can also mark blocks of methods for optional implementation using the @optional directive; all methods declared after this directive, unless there is an @intervening, which can be implemented. Consider these declarations:

```objc
@protocol MyProtocol
// implementation of this method is required implicitly
-(void)requiredMethod;

@optional
// implementation of these methods is optional
-(void)someOptionalMethod;
-(void)anotherOptionalMethod;

@required
// implementation of this method is required
-(void)anotherRequiredMethod;
@end
```

The class that declares the protocol typically does not implement these methods; however, it should invoke them in instances of the class that conforms to the protocol. Before invoking optional methods, it should verify that they are implemented using the respondsToSelector method.

A class adopts a protocol by specifying the protocol, enclosed by angle brackets, at the end of its interface declaration. A class can adopt multiple protocols by delimiting them with commas. This is how the Foundation NSData class adopts three protocols:

```objc
@interface NSData :Object <NSCopying, NSMutableCopying, NSCoding>
```
