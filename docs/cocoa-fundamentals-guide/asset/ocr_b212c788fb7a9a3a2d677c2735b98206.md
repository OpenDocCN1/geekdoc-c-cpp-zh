# When to Override a Method

Most methods defined in a framework class are generally fully implemented; they exist so you can invoke them
to obtain the services they provide. You rarely need to override these methods and shouldn't attempt to
the framework depends on what they are doing—nothing more and nothing less. In other cases,
y can override a method, but there's no real reason to do so. The framework's version of the method does
an adequate job. But just as you might implement your own version of a string-comparison function rather
t use `strcmp`, you can choose to override the framework method.

Some framework methods, however, are intended to be overridden; they exist to let you add program-specific
behavior to the framework. Often the method, as implemented by the framework, does little or nothing
th of value to your purpose, is invoked in messages initiated by other framework methods. To give
to content to these methods, an application must implement its own version.

# Invoke or Override?

The methods you override in a subclass generally won't be the ones that you'll invoke yourself, at
least. Simply reimplement the method and leave the rest to the framework. In fact, the more
y you are to write an application-specific version of a method, the less likely you are to invoke it in
yown code. There's a good reason for this. In a general sense, the framework declares public methods so
t you, the developer, can do one of two things:

+   - Invoke to yourself the services the class provides

+   - Override to introduce your own code into the program model defined by the framework

Sometimes a method falls into both categories; it renders a valuable service upon invocation, and it
can be strategically overridden. But generally, if a method is one that you can invoke, it's fully defined by the
framework and doesn't need to be redefined in yours. If the method is the one that you need to reimplement
a a subclass, the framework has a particular job for it to do and so will override the method itself at the
