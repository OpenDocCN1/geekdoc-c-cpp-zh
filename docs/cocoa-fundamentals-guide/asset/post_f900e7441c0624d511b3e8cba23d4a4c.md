
# Functions, Constants, and Other C Types

Because Objective-C is a superset of ANSI C, it permits any C type in your code, including typedef structures, enum constants, and macros. The important design issue is when and how to use these types in the interface and implementation of custom classes.

The following list offers some guidance on using C types in the definition of a custom class:

- Define a method rather than a function for functionality that is often requested but doesn't need to be overridden by subclasses. The reason for this is performance. In cases, it's best for the class to be private rather than being part of the API. You can also implement functions for behavior that is not associated with any class (it is global) or for operations on simple types (C primitives or structures). For global functionality it might be better—for reasons of extensibility—create a class from which a singleton instance is generated.
- Define a type rather than a simple class when the following conditions apply:
  - You don't expect to augment the list of fields.
  - All the fields are public (for performance reasons).
  - None of the fields is dynamic (dynamic fields might require special handling, such as retaining or releasing).
  - You don't intend to use of object-oriented techniques, such as subclassing.

Even when all these conditions apply, the primary justification for structures in Objective-C code is performance. In other words, if there is no compelling reason, a simple class is preferable.

- Declare enum constants than #define. The former are more suitable for typing, and you can discover their values in the debugger.

# When the Class Is Public (Mac OS X)

When you are defining a class for your own use, such as a controller class for an application, you have great flexibility because you know the class well and can always redesign it if you have to. However, if your custom class will likely be a superclass for other developers—in other words, if it's a public class, the expectations others of you mean you have to be more careful of your design.

Here are few guidelines for developers of public Cocoa classes:

- Make those instance variables that subclasses need to access scoped as @protected.
- Add one or two instance variables to help binary compatibility with future versions of your class ("Instance Variables" (page 19)).
- In-memory managed code, implement your accessor to properly handle memory management of vested objects ("Storing and Accessing Properties" (page 123)). Clients of your class will get back autoreleased objects from your getter access.
- Observe the naming guidelines for public Cocoa interfaces as recommended in Coding Guidelines for Cocoa.

# Multithreaded Cocoa Programs

It has long been a standard programming technique to optimize program performance through multithreading. By having data processing and I/O operations run on their own secondary threads and dedicating the main thread to user-interface management, you can enhance the responsiveness of your applications. In recent years, multithreading has assumed even greater importance with the emergence of multicore processors and symmetric multiprocessing (SMP). Concurrent processing on such systems synchronizing the execution of only one thread on the same processor but multiple threads on multiple processors.

But making your program multithreaded is not without risk or costs. Although threads share the virtual address space of process, they add to the memory footprint; each thread requires an additional data structure, associated attributes and its own stack. Multithreading also requires greater complexity of program design to synchronize access to shared memory among multiple threads. Such designs make a program harder to maintain and debug. Moreover, multithreaded designs that use locks can actually degrade performance (relative to a single-threaded program) for shared resources. Designing a program for multithreading often involves tradeoffs between performance and protection which require careful consideration of your data structures and the intended usage pattern for extra threads. Indeed, in some situations the best approach is to avoid multithreading altogether and keep all program execution on the main thread.

> **Further Reading:** To get a solid understanding of issues and guidelines related to multithreading, read Multithreading Programming Guide.
