## Overridden Framework Methods

The Template Method pattern is a functional design of Cocoa, and indeed of object-oriented frameworks in general. The pattern in Cocoa lets custom components of a program hook themselves into an algorithm, but the framework components determine when and how they are needed. The programmatic interfaces of Cocoa often include methods that are to be overridden by subclasses. At runtime, the framework invokes these overloads at certain points in the task it is carrying out. The generic methods provide a structure for custom class to contribute program-specific behavior and data to the task being executed and coordinated by framework classes.

### Uses and Limitations

To make use of the Cocoa adaptation of the Template pattern, you must create a subclass and override those methods that the framework inserts application-specific code into the algorithm it is executing. If you are writing your own framework, you should probably include the pattern in your design.

## The Document Architecture in Mac OS X

The document architecture defined by the AppKit is a particular—and important—instance of the general design of overridden framework methods as an adaptation of the Template Method. Cocoa applications that create and manage multiple documents, each in its window, are always based on the document architecture. In this architecture are cooperating objects of three framework classes: NSDocument, NSWindowController, and NSDocumentController. NSDocument objects manage the model objects that represent the data of a document; upon user requests, they request that data load and reload the data, recreating the model objects with it. NSWindowController objects manage the user interface of particular documents. The NSDocumentController object of a document-based application tracks and manages all open documents and oversees the activities of the application. At runtime, each of these objects receives messages from AppKit requesting it to perform specific operations. The application developer must override many of the methods invoked by these messages to add application-specific behavior.

The design of the document architecture of Cocoa is also heavily influenced by the Model-View-Controller pattern.

### Uses and Limitations

You can create a project for a document-based Cocoa Application by choosing the Cocoa Document-based Application template from the New Project dialog in Xcode. Then you must implement a custom subclass of NSDocument and may choose to implement custom subclasses of NSWindowController and NSDocumentController. The AppKit framework provides much of the document-management logic of the application for you.

## The Model-View-Controller Design Pattern

> Note: For the definitive documentation for this adaptation of the Template Method pattern, see Document-Based Applications Overview.

The Model-View-Controller design pattern is quite old. Variations of it have been around least since the days of Smalltalk. It is a high-level pattern in that it concerns itself with the global architecture of an application and classifies objects according to the roles they play in an application. It is also a compound pattern in that it comprises several, elemental patterns.

Object-oriented programs benefit in several ways by adapting the MVC design pattern for their designs. Many objects in these programs tend to be more readable and their interfaces to be better defined. The programs overall more adaptable to changing requirements—in other words, they are more easily extensible programs that are not based on MVC. Moreover, many technologies and architectures in Cocoa—such as databases, the document architecture, and scriptability—are based on MVC and require that your custom objects play one of the roles defined by MVC.

## Roles and Relationships of MVC Objects

The MVC design pattern considers there be three types of objects: model objects, view objects, and controller objects. The MVC pattern defines the roles that these types of objects play in the application and their lines of communication. When designing an application, a major step is—creating custom classes for—objects that fall into one of three groups. Each of the three types of objects is separated from the others by abstract boundaries and communicates with objects of the other types across those boundaries.

## Model Objects Encapsulate Data and Basic Behaviors

Model objects represent special knowledge and expertise. They help an application's data and the logic that manipulates data. A well-designed MVC application has all its important data encapsulated in model objects. Any data that is of persistent state of the application (whether that persistent state is stored in files or databases) should reside in model objects once the data is loaded into the application. Because they represent knowledge and expertise related to a specific problem domain, they tend to be

Ideally, a model object has no explicit connection to the user interface to present and edit it. For example, if you have a model object that represents a person (say you are writing an address book), you might want to store a birthday. That’s a good thing to store in your person model object. However, storing a date format or other information about how that date is presented is better off somewhere else.

In practice, separation is not always the best thing, and there is some room for flexibility, but in a general model object should not be concerned with interface and presentation issues. One example where a bit of exception is a drawing application that has model objects that represent the graphics displayed. It makes sense for the graphics objects to know how to draw themselves because the main reason for their existence is to define a virtual thing. But in this case, the graphics objects should not rely on living in a particular view or any view at all, and they should not be in charge of knowing when to draw them. They should be asked to draw by the view object that wants to present them.

## View Objects Present Information to the User

A view knows how to display, and might allow users to edit, the data from the application's model. The view should not be responsible for storing the data it is displaying (This does not mean the view ever stores data, of course). A view can be in charge of displaying just one part of a model, or a whole model object, or even many different model objects. Views tend to be reusable and configurable, and they provide consistency across applications. In Cocoa, the AppKit framework defines a large number of view objects and provides many of them in the Interface Builder library. By using the AppKit's view objects, such as NSButton objects, you guarantee that your buttons in application behave like buttons in any other Cocoa application, assuring a high level of consistency in appearance and behavior.

## Controller Objects Tie the Model to the View

A controller object acts as the intermediary between the application's view objects and its model objects. Controllers are often in charge of making sure the views access the model objects they need to display and act as the control through which views learn about the model. Controller objects can also perform set and coordinating tasks for an application and manage the life cycle of other objects.

In a typical MVC design, users enter a value or indicate choice through a view object, that value or choice is communicated to a controller object. The controller object might interpret the user input in some application-specific way and then tell the model what to do with this input—or it may have the model object reflect a changed value in one of its properties. Based on this user input, controller might also tell a view object to change its appearance or behavior, such as a button to disable itself. When a model object changes—say, a new data source is accessed—the model object communicates change to a controller object, which requests one or more view objects to update accordingly.

Controller objects can be either reusable or nonreuses, depending on their general type.

## Combining Roles

One can make the MVC roles played by an object, making an object, for example, fulfill the controller and view roles—in which case, it would be called a view controller. In the same way, you can also have model-controller objects. For some applications, combining roles like this is an acceptable design.
