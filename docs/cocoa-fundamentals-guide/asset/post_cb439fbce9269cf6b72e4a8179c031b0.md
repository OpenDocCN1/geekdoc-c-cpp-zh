As delegates, data sources are objects that must be present to receive messages from the objects requesting data. The application that uses them must ensure their persistence, retaining them if necessary in memory-managed code.

Data sources are responsible for the persistence of the objects they hand out to user-interface objects. In other words, they are responsible for the memory management of those objects. However, whenever a viewer object such as an outline view or table view accesses the data from a data source, it retains the object as long as it uses the data. But it does not use the data for very long. Typically it holds on the data only enough to display it.

# Implementing a Delegate for a Custom Class

To implement a delegate for your custom class, complete the following steps:

- Declare the delegate accessor methods in your class header file.
  - (id)delegate;
  - (void)setDelegate:(id)newDelegate;

- Implement the accessor methods. In a memory-managed program, to avoid retain cycles, the setter method should not retain or copy your delegate.
  - (id)delegate {
    return delegate;
  }
  - (void)setDelegate:(id)newDelegate {
    delegate = newDelegate;
  }

- Declare a formal or informal protocol for the programmatic interface for the delegate. Informal protocols are on the NSObject class. If you define a formal protocol for your delegate, make sure you mark all of optional methods with the @optional directive.
  - "The Form of Delegation Messages" (page 178) gives freedom for naming your own delegate methods.

- Before invoking a delegate method, make sure the delegate implements it by sending it to a respondsToSelector:message.
  - (void)someMethod {
    if ([delegate respondsToSelector:@selector(operationShouldProceed)]) {
      if ([delegate operationShouldProceed]) {
        // do something appropriate
      }
    }
  }

The precaution is necessary only for optional methods in a formal protocol or methods of an informal protocol.

# The Target-Action Mechanism

Although delegation, bindings, and notification are useful for handling certain forms of communication between objects in a program, they are not particularly suitable for the most visible sort of communication. A typical application's user interface consists of a number of graphical objects, and perhaps the most common of these objects are controls. A control is a graphical analog of a real-world or logical device (button, slider, checkboxes, and so on); as a real-world control, such as a radio tuner, you use it to convey your intent to some system of which it is a part—that is, an application.

The role of a control is simple: to interpret the intent of the user and some other object to carry out that request. When a user acts on the control, by clicking it or pressing the Return key, the hardware generates an event. The control accepts the event (appropriately packaged for Cocoa) and sends it to an instruction specific to the application. However, events themselves do not give much information about the user's intent; they merely tell you that the user clicked a mouse button or pressed a key. Some mechanism must be called upon to provide the translation between event and instruction. This mechanism is *target-action*.

Cocoa uses the target-action mechanism for communication between a control and another object. This mechanism allows the control and, in Mac OS X itself, to encapsulate the information necessary to send an application-specific instruction to the receiving object—typically an instance of a custom class—is called the *target*. The action is the message that the control sends to the target. The object that is identified in the user event—that is the one that imparts significance to it, and this significance is usually reflected in the name it gives to the action.

# The Target

A target is a receiver of an action message. A control, or more frequently, holds the target of its action message as an outlet (see "Outlets" (page 175)). The target usually is an instance of one of your custom classes, although it can be any Cocoa object class implements the appropriate action method.

You can set the control's target to *nil* and let the target object be determined at runtime. When the target is *nil*, the action object `UIApplication` or `Responder` searches for an appropriate receiver in a prescribed order:

- 1. A key window in Mac OS X responds to key presses for an application and is the receiver of messages from menus and dialogs. An application's main window is the primary focus of user actions and often has key status as well.
- 2. It tries the object and then the window object's delegate.
- 3. If the main window is different from the key window, it starts over with the first responder in the main window and works its way up the main window's responder chain to the window object and its delegate.
- 4. Next, the application object tries to respond. If it can't, it tries its delegate. The application object and its delegate are the receivers of last resort.

> Note: A key window in Mac OS X responds to key presses for an application and is the receiver of messages from menus and dialogs. An application's main window is the primary focus of user actions and often has key status as well.

Control objects do not (and should not) retain their targets. However, clients of controls sending action messages (applications), are responsible for ensuring that their targets are able to receive action messages. To do this, they may have to retain their targets in memory-managed environments. This precaution applies equally to delegates and data sources.

# The Action

An action is a message control sends to the target, or from the perspective of the target, the method implements to respond to the action message. A control or sel is frequently the case in AppKit—a control's own action is an instance variable of SEL An Objective-C type used to specify the signature of a message. An action message must have a simple, distinct signature. The method it invokes nothing and has also some parameter of type id. By convention, it is named sender. Here is an example of NSResponder class, which defines a number of action methods:

```
(void)capitalize:(id)sender;
```

Action methods declared by Cocoa classes can also have the following signature:

```
(IBAction)delete:(id)sender;
```

In this case, IBAction does not designate a type for a return value; no is returned. IBAction is a type qualifier that Interface Builder notices during application development to synchronize actions added programmatically with one of action methods defined for a control.

> iOS Note: In UIKit, action selectors can also take other forms. See "Target-Action in UIKit" (page 186) for details.

The sender parameter identifies the control sending the action message (although it can be another object substituted by the actual sender). The idea behind this is similar to a return address on a postcard. The target can query for more information if it needs to. If the actual sender substitutes another object, you should treat that as the own. For example, if you have a text field and when the user enters, the action method nameEntered is invoked in the target:

```
(void)nameEntered:(id)sender
NSString *name = [sender stringValue];
if ([name isEqualToString:@"*"]) {
MutMutableArray *names = [sender nameList];
[names addObject:name];
[sender setNSString:@"*"];
}
```

Here the method extracts the contents of the text field, adding the string to an array cached as an instance variable, and clears the field. Other queries to the sender would be asking an NSMatrix object for its selected row ([sender selectedRow]), asking an NSButton for its state ([sender state]), and asking any cell associated with a control for its tag ([sender cell tag]), a tag being a numeric identifier.
