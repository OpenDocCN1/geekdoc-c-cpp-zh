
# When to Override a Method

Most methods defined in a framework class are generally fully implemented; they exist so you can invoke them to obtain the services they provide. You rarely need to override these methods and shouldn't attempt to the framework depends on what they are doing—nothing more and nothing less. In other cases, you can override a method, but there's no real reason to do so. The framework's version of the method does an adequate job. But just as you might implement your own version of a string-comparison function rather than use `strcmp`, you can choose to override the framework method.

Some framework methods, however, are intended to be overridden; they exist to let you add program-specific behavior to the framework. Often the method, as implemented by the framework, does little or nothing of value to your purpose, and is invoked in messages initiated by other framework methods. To give content to these methods, an application must implement its own version.

# Invoke or Override?

The methods you override in a subclass generally won't be the ones that you'll invoke yourself, at least. Simply reimplement the method and leave the rest to the framework. In fact, the more you are are to write an application-specific version of a method, the less likely you are to invoke it in your own code. There's a good reason for this. In a general sense, the framework declares public methods so that you, the developer, can do one of two things:

- Invoke to yourself the services the class provides
- Override to introduce your own code into the program model defined by the framework

Sometimes a method falls into both categories; it renders a valuable service upon invocation, and it can be strategically overridden. But generally, if a method is one that you can invoke, it's fully defined by the framework and doesn't need to be redefined in yours. If the method is the one that you need to reimplement in a subclass, the framework has a particular job for it to do and so will override the method itself at the appropriate times. # Types of Overridden Methods

You may choose to define several types of methods in a subclass:

- Some framework methods are fully implemented and are meant to be invoked by other framework methods. In words, even though you might reimplement them, you don't invoke them elsewhere in your code. They provide some service—data or behavior—required by some other code at some point during program execution. These methods exist in the public interface for just one reason—so that you can override them if you want. They give you an opportunity to substitute your own algorithm for the one used by the framework or to modify or extend the framework algorithm.

An example of this type is `trackWithEvent:` in the `NSView` class of the AppKit. `NSView` implements this method to satisfy the requirement—handling method tracking and selection—but you may override it if you want different behavior.

- Another type of method is one that makes an object-specific decision, such as whether an attribute is turned on or whether a policy is in effect. The framework implements a default version of this method that makes the decision you, and you might implement your own version and then add a different decision. In many cases, implementation is simply a matter of returning `YES` or `NO`, or a value larger than the default.

The `acceptFirstResponder` method of `Responder` is typical of this sort of method. Views accept `acceptFirstResponder` messages, among other things, if they respond to keystrokes or mouse clicks. By default, `view` returns `NO` for this method—most views don't accept input. But some, should override `acceptFirstResponder` to return `YES`. A UIKit view is the `layer` class method of `UIView`: if you do not know the default class for the view, you can override the method and substitute your own.

- Some methods might be overridden, but to add something, not to replace the framework implementation of the method does. The subclass version of the method augments the behavior of the superclass. When the framework performs one of these methods, it's important to incorporate the very method it overrides. It does this by sending a message to `super` (the superclass), invoking the framework-defined version of the method.

This kind of method is one that every class in inheritance is expected to contribute to. For example, objects that archive themselves must conform to the `NSCoding` protocol and the `initWithCoder:` and `encodeCoder:` methods. Before a class performs the encoding or decoding to set its instance variables, it must invoke the superclass version of the method.

Sometimes a subclass version of a method wants to reuse the superclass and then add something, the final result. In the `UIView` method `drawRect:`, for example, a subclass of a class that performs complicated drawing wants to draw a border around the drawing, so it would invoke `super` first.

- Some framework methods do not have at all return some default value (such as `self`) to prevent runtime or compile-time errors. These methods are overridden. The framework cannot define these methods in rudimentary form because they carry out tasks that are entirely program-specific. There's no need to incorporate the framework implementation of the method with a message to `super`.

# When to Make a Subclass

There are other considerations that can help you decide where your subclass fits into. What is the nature of the application, or which part of the application you are trying to create? Some Cocoa architectures use the document-based architecture defined by AppKit requires you to subclass NSDocument and other classes. To make your Mac OS X application scriptable, you have to subclass one of the scripting classes of AppKit, such as NSScriptCommand.

Another factor is the role that instances of your subclass will play in the application. The Model-View-Controller design pattern, where view objects appear on the user interface; model objects handle application data (and the algorithms that act on data); and controllers mediate between view and model. For details, see "Model-View-Controller Design Pattern". Knowing the role each class plays simplifies the decision for which superclass to use. If instances of your class are view objects that do their own drawing and event-handling work, you should probably inherit from NSView (if you are using AppKit) or UIView (if you are using UIKit). If your application needs a controller, you can use either one of the off-the-shelf controllers of AppKit (such as NSViewController), or if you want a different behavior, subclass ViewController or NSObject. If your class is a model class—say, one which represents rows of data in a spreadsheet—you should subclass NSObject or use the Core framework.

iOS Note: The controller classes of the AppKit framework, including ViewController, have no counterparts in UIKit. There are controllers in UIKit—UITViewController, UINavigationController, and UITabBarController—but these are based on a different purpose—navigation and selection (see "Controllers in UIKit" (page 150 for a summary)).
