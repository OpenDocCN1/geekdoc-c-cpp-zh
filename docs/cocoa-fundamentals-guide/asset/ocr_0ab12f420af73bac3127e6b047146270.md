# CHAPTER 5
Communicating with Objects

But there are differences between notification and delegation, and these differences dictate these mechanisms should be used for. As noted earlier, the main difference between the notification model and the delegation model is that the former is a broadcast mechanism whereas delegation is a one-to-one relationship. Each model has its advantages; notifications they enable the following:

+   * The posting object does not have to know the identity of the observing objects.
* An application is not limited to notifications by the Cocoa framework; any class can declare notifications for its instances to post.
* Notifications are not limited to intra-application communication; with distributed notifications, one process can notify another process about events that occur.

> iOS Note: Distributed notifications are not available in iOS.

But the one-one model of delegation has its advantages too. A delegate gives the opportunity to affect an event by returning a value to the delegating object. A notification observer, on the other hand, must play a more passive role; it can affect itself and its environment in response to the event. Notification methods have the following signature:

```
- (void)notificationHandlerName:(NSNotification *)
```

This requirement prevents the observing object from affecting the original event in any way. A delegate, can often affect how the delegating object will handle an event. An AppKit object is automatically registered as an observer of its notifications. All it need to implement is the notification methods defined by the framework class for notifications.
The notification mechanism is not the only Cocoa for affecting changes in object state, and for many situations should not be preferred. The Cocoa bindings technology, and specifically its enabling key-value observing (KVO) and key-value binding (KVB) protocols, allow objects in application to observe changes in the properties of other objects. The bindings accomplishes this function more efficiently than notifications. In bindings, the communication between observed and observing object is direct, and does not require an intermediary object as the notification center. Moreover, the bindings impose no performance penalty for unchanged objects, as regular notifications.

However, there can be situations where it makes sense to prefer notifications over delegations. You may want to observe other events than a change in object properties or it might be impractical to implement KVO and KVB combinations, especially when the notifications to be posted and observed are free.
If the situation warrants the use of notifications, you should be aware of the performance implications. When you post a notification, it is eventually dispatched to observing objects synchronously by the local notification center. This occurs regardless of whether the posting was done synchronously or asynchronously. If there are many observers each does a lot of work while handling the notification, your program could experience a significant delay. should be careful about overusing notifications or using them inefficiently. The following guidelines for notification usage should help towards this end:

+   * Be selective about which notifications your application should observe.
* Be specific about notification naming and posting objects when you register for notifications.
* Implement the methods that handle notifications to do so as efficiently as possible.
