
# Calling Conventions

```
ST1 := ST1 + ST0
FPU POP ST0
```

Multiplies ST(1) and ST(0) and stores the result in ST(1). Then, ST(0) is marked empty and stack pointer is incremented. Thus, contents of ST(1) are on the top of the stack. So the top 2 values are multiplied together, and the result is stored on top of the stack. Therefore, in our instruction above, `fmul ST(1), ST(0)*`, which is also the last instruction of the function, we can see that the last result is stored in ST0. Therefore, floating point parameters are passed on the regular stack, but floating point results are passed on the FPU stack.

One final note is that MyFunction cleans its own stack, as referenced by the **ret 20** command at the end. Because none of the parameters were passed in registers, this function appears to be exactly what we would expect a STDCALL function would look like: parameters passed on stack from right-to-left, and the function cleans its own stack. We will see below that this is actually a certain assumption.

For comparison, here is the GCC list:

```
LC1:
  .long
  .long
  .align 8 0 1073741824

LC2:
  .long
  .long 0 1074266112
.global MyFunction
  .def MyFunction;    .scl 2;    .type 32;    .endf
  MyFunction:
    push
    movl %esp,%eb
    subl $16,,(eb)
    fld
    -8(%eb)
    fstpl
    fld
    -16(%eb)
    fstpl
    -8(%eb)
    fld
    fadd
    %st, xst(1)
    fld
    -16(%eb)
    LC1
    fadd
    %st, xst(1)
    %st, xst(1)
    fmul
    24(%eb)
    fld
    LC2
    fadd
    %st, xst(1)
    fmul
    %st, xst(1)
    leave

```

This is a very difficult listing, so we will step through it (albeit quickly). 16 bytes of extra space is allocated on the stack. Then, using a combination of fld and fstpl instructions, the first 2 parameters are moved from offsets +8 and +16, to offsets -8 and -16 from ebp. Seems like a waste of time, but remember, optimizations are off. **fld1** loads the floating point value 1.0 onto the FPU stack. fadd adds the top of the stack (1.0), to the value in ST1 [ebp - 8], originally [ebp + 8].


We can see that this function takes 20 bytes worth, because the @20 decoration at the end of the name. This makes sense, because the function is taking **double** parameters (8 bytes each), and one **float** parameter (4 bytes). This is a grand total of 20 bytes. We can notice at a glance, without having to actually analyze any of the code, that there is one register being accessed: ebp. This seems strange, considering that FASTCALL passes its arguments in registers. However, that is not the case: all the floating-point parameters (even z, which is a 32-bit float) are passed on the stack. We know this because by looking at the code there is no other place where parameters could coming from.

# Calling Conventions

Notice that fmul is the last instruction performed, as in the CDECL example. We can infer then, without investigating too deeply, that the result is passed to the top of the floating point stack. Notice also that x (offset [ebp + 8]), y (offset [ebp + 16]) and z (offset [ebp + 24]) are pushed in reverse order: this means floating point parameters are passed right-to-left. This is exactly the same as CDECL code, although we are using floating point values. Here is the GCC assembly for MyFunction2:

```
.align 8
LC5:
  .long 0
  .long 1073741824
  .align 8
LC6:
  .long 0
  .long 10742666112
  .glob @MyFunction2020
  .def _2; .type 32; .endf
@MyFunction2020:
  pushl %ebp
  movl %esp, %ebp
  subl $16, %esp
  fstpl -8(%ebp)
  fld 16(%ebp)
  fstpl -10(%ebp)
  fld
  faddp %st, xst(1)
  fld -6(%ebp)
LC5:
  faddp %st, xst(1)
  fmul
  fld 24(%ebp)
LC6:
  faddp %st, xst(1)
  fmul
  leave
  ret $20
```

This is a tricky piece of code, but luckily we don't need to read it very close to find what we are looking for. First off, notice that no other registers are accessed besides ebp. Again, GCC passes all floating point values (the 32-bit float, z) on the stack. Also, the floating point value is passed on the top of the floating point stack.

We can see that GCC is something strange at the beginning, taking the values from the stack [ebp + 8] and [ebp + 16], and moving them to locations [ebp - 8] and [ebp - 16]. Immediately after being moved, these values are loaded onto the floating point stack and arithmetic is performed. z isn't loaded till later, and isn't ever moved to [ebp - 24], despite the pattern.

LC5 and LC6 are constant values that most likely represent floating point values (because the numbers themselves, 1073741824 and 10742666112 do not make any sense in the context of our example functions). Notice that both LC5 and LC6 contain two .long data items, for a total of 8 bytes of storage. They are therefore most definitely double values.

```

                                ENDS

                                ENDS
TEXT            _
x$ = 8                                     ; size = 8
y$ = 16                                     ; size = 8
z$ = 24                                     ; size = 4
@MyFunction2020 PROC NEAR
; Line 7
    mov             ebp, ebp
; Line 8
    fld             QWORD PTR y$[ebp]
    fadd            QWORD PTR [__real83ff000000000000]
    fld             QWORD PTR [__real8400000000000000]
    fmul            QWORD PTR ST(1)
    fld             QWORD PTR [ebp]
    fadd            QWORD PTR [__real8480000000000000]
    fmul            ST(1), ST(0); Line 9
    pop             ebp
    set             20                              ; 0000014H
@MyFunction20 END
TEXT            ENDS
```

x is the highest on the stack, and z is the lowest, therefore these parameters are passed from right-to-left. We can tell that x is the smallest offset (offset + 8), while z is the largest offset (offset + 24). We also see as the final fmul instruction that the return value is on the FPU stack. This function also cleans the stack as needed, by the call ret. It cleans 20 bytes off the stack which is, incidentally, the total amount that we passed to begin with.

We can also notice that the implementation of this function works exactly like the FASTCALL version of this function. This is true because FASTCALL only passes DWORD-sized parameters in registers, and floating point numbers do not qualify. This means that our assumption above was correct.
