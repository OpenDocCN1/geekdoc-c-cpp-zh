
## 5.7 Imports and Exports - Linking to other modules

### 5.7.1 What is linking?

Whenever a developer writes a program, there are expected to be implemented already a number of subroutines and functions which are saving the writer hassle of having to write more code or work with complex data structures. Instead, the coder only need to declare one call to the subroutine, and the linker will decide what happens next.

There are two types of linking that can be used: static and dynamic. This precompiled code can be inserted into the final executable to implement a function, saving the programmer lot of time. In contrast, dynamic linking allows subroutine to reside in a different file (or module), which is loaded at runtime by the operating system. This is also known as a "Dynamically linked library", or DLL library which is a module containing a set of functions or values that can be exported. This is different from the executable, which imports from libraries to do what it wants. From here on, "module" means any of PE format, and a "Library" is any module which exports and imports functions and values.

- Dynamically linking has the following benefits:
- It saves space, if more than one executable links to the library module
- Allows instant updating of routines, without providing new executables for all applications
- Can save space in memory by mapping the code of the library into more than one process
- Increases abstraction of implementation. The method by which an action is achieved can be modified without reprogramming of applications. This is extremely useful for backward compatibility with operating systems.

This section discusses how this is achieved using the PE file format. An important point to note at this point is that anything can be imported or exported between modules, including variables as well as subroutines.

### 5.7.2 Loading

The downside of dynamically linking modules together is that, at runtime, the software which is initialising an executable must link these modules together. For various reasons here you cannot declare that "The function in this dynamic library will always exist in memory". If memory address is unavailable or the library is updated, the function will no longer exist there, and the application trying to use it will break. Instead, each module (library or executable) must declare what functions or values it exports to other modules, and what it wishes to import from other modules.

As said above, a module cannot declare where in memory it expects a function or value to be. Instead, it declared where in its own memory it expects to find a pointer to the value it wishes to import. This permits the module to address any imported value, wherever it turns up in memory.

## 5.8 Exports

Exports are functions and values in one module to be shared with other modules. This is done through the use of the "Export Directory", which is used to translate the name of an export (or "Ordinal", see below), and a location in memory where the code or data can be found. The start of the export directory is identified by the IMAGE_DIRECTORY_ENTRY entry of the resource directory. All export data must exist in the same section. The directory is headed by the following structure:

```struct
struct IMAGE_EXPORT_DIRECTORY {
    long Characteristics;
    long TimeStamp;
    short MajorVersion;
    short MinorVersion;
    long Name;
    long Base;
    long NumberOfFunctions;
    long *AddressOfFunctions;
    long *AddressOfNames;
    long *AddressOfOrdinals;
}
```

The 'Characteristics' value is generally unused, TimeStamp describes the time the export was generated, MajorVersion and MinorVersion describe the version details of the directory, but their nature is undefined. These values have little or no impact on the actual exports themselves. The 'Name' value is an RVA to a zero terminated ASCII string, the name of this library name, or module.

### 5.9.2 Imports at runtime

Using the above import directory at runtime, the loader finds the appropriate modules, loads them into memory, seeks the correct export. However, to use the export, a pointer to it must be stored somewhere in the importing module. This is why there are two parallel arrays, OriginalThunk and FirstThunk, identifying IMAGE_BY_NAME structures. Once an imported value has been resolved, the pointer to it is stored in the FirstThunk array. It can then be used at runtime to address values.

### 5.9.3 Bound imports

The PE format also supports a peculiar feature known as 'binding'. In the process of loading and resolving import addresses can be time consuming, and in situations this is to be avoided. If a developer is fairly certain that a library is not going to be updated or changed, the addresses in memory of imported values will not change each time the application is loaded. So, the import can be computed and stored in the FirstThunk array before runtime, allowing the loader to skip resolving the imports - the imports are 'bound' to a particular memory location. However, if the versions numbers between modules do out of date, or the imported library needs to be relocated, the loader will assume the bound addresses are invalid, and resolve the imports.

The Timestamp member of the import directory entry for a module controls binding; if it is set to zero, the import is not bound. If it is non-zero, then it is bound to another module. However, the Timestamp in the import table must match the Timestamp in the module's Header, otherwise the bound values will be discarded by the loader.
