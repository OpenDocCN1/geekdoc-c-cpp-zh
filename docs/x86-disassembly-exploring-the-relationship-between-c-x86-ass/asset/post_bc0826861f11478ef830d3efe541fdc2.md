
## 24 Optimization Examples

### 24.1 Example: Optimized vs Non-Optimized Code

The following example is adapted from an algorithm presented in Knuth(vol 1, chap 1) used to find the greatest common denominator of 2 integers. Compare the listing file of this function when compiler optimizations are turned on and off.

```
/line i=/
int EuclidGCD(int m
```

Compiling with the Microsoft C compiler, we generate a listing file using no optimization:

```
PUBLIC _EuclidsGCD
_TEXT SEGMENT
_r = -8; size = 4
_q = -4; size = 4
_m = 12; size = 4
_EuclidGCD PROC NEAR
: Line 2
push ebp
mov ebp, esp
sub ebp, 8
$L477:
```

```
; Line 4
mov eax, 1
test eax, eax
je SHORT $L473
; Line 6
mov eax, DWORD PTR _m$[ebp]
cdq
idiv DWORD PTR _q$[ebp], eax
; Line 7
mov eax, DWORD PTR _m$[ebp]
cdq
idiv DWORD PTR _n$[ebp], eax
mov DWORD PTR _r$[ebp], edx
; Line 8
cmp DWORD PTR _r$[ebp], 0
jne SHORT $L479
; Line 10
mov eax, DWORD PTR _n$[ebp]
jmp SHORT $L473
$L479:
; Line 12
mov ecx, DWORD PTR _n$[ebp]
mov DWORD PTR _m$[ebp], ecx
; Line 13
mov edx, DWORD PTR _r$[ebp]
mov DWORD PTR _n$[ebp], edx
; Line 14
jmp SHORT $L473
$L473:
; Line 15
mov esp, ebp
pop ebp
ret 0
_EuclideanGCD ENDP
_TEXT ENDS
END
```

Notice how there is a very clear correspondence between the lines of C code, and the lines of the ASM code; the addition of the '; line x' directives is very helpful in that respect.

Next, we compile the same function using a series of optimizations to stress speed over size:

```
cl.exe /Teuclids.c /Fa /Ogt2
```

and we produce the following:

```
PUBLIC _EuclidsGCD
_TEXT SEGMENT
_r = 8 ; size = 4
_q = 12
_EuclidsGCD PROC NEAR
; Line 7
mov eax, DWORD PTR n#[esp-4]
push esi
mov esi, DWORD PTR n#[esp]
cdq
idiv esi
mov eax, edx
; Line 8
test ecx, ecx
je SHORT $L563
$L547:
; Line 12
mov eax, esi
cdq
idiv ecx, ecx
; Line 13
mov esi, ecx
mov eax, edx
test ecx, ecx
jne SHORT $L547
$L563:
; Line 10
mov eax, esi
pop esi
; Line 15
ret 0
_EuclidGCD ENDP
_TEXT ENDS
```

As you can see, the optimized version is significantly shorter then the non-optimized version. Some of the key differences include:

- The optimized version does not prepare a standard stack frame. This is important to note, because many times new revers assume that functions always start and end with proper stack frames, and this is clearly not the case. EBP isnt't being used, ESP isnt't being altered (because the local variables are kept in registers, and not put on the stack), and no subfunctions are called. 5 instructions are cut by this.

- The test 'EAX, EAX' series of instructions in the non-optimized output, 'line 4' is unnecessary. The while-loop is defined by 'while(1)' and therefore the loop always continues. This extra code is easily cut out. Notice also that there is no unconditional jump in the loop would look like: 'if(r == 0) return*' instruction have become the new loop condition.

- The structure of the function is altered; the division of m and n to produce r is performed in this function twice: once at the beginning of the function to initialize, and once at the end of the loop. the value of r is tested twice, in the same places. The compiler is very liberal with how it assigns storage in the function, and readily discards values that are not needed.

## 24.2 Example: Manual Optimization

The following lines of assembly code are not optimized, but they can be optimized very easily. You can find a way to optimize these lines?

```
mov eax, 1
test eax, eax
je SHORT $L473
```

The code in this line is the code generated for the 'while( 1 )' C code, to be exact, it represents the loop break condition. Because this is an infinite loop, we can assume that these lines are unnecessary.

*mov eax, 1* initializes eax.
the immediately afterwards tests the value of eax to ensure that it is a nonzero. because eax will always be nonzero (eax = 1) at this point, the conditional jump can be removed along with the 'mov' and the 'test'.

The assembly is actually checking whether 1 equals 1. Another fact is, that the C code for an infinite FOR loop:

## 24.3 Example: Trace Variables

Here are the C code and the optimized assembly listing from the EuclidGCD function, from the example above. Can you determine which registers contain the variables **r** and **q**?

```c
/* line 1/
int EuclidGCD(int m, int n) /*we want to find the GCD of m and n*/
{
    int q, r; /*q is the quotient, r is the remainder*/
    while(1)
    {
        q = m / n; /*find q and r*/
        r = m % n;
        if(r == 0) /*if r is 0, return our n value*/
            return n;
        m = n; /*set m to the current n value*/
        n = r; /*set n to our current remainder value*/
    }
} /*repeat*/
```

```asm
PUBLIC _EuclidGCD
_TEXT SEGMENT
_m = 8; size = 4
_n = 12;      size = 4
_EuclidGCD PROC NEAR
; Line 7
mov eax, DWORD PTR _m$[esp-4]
push esi
mov esi, DWORD PTR _n$[esp]
cdq
idiv esi
mov ecx, edx
; Line 8
test ecx, ecx
je SHORT $L563
$L547:
```

```asm
; Line 12
mov eax, esi
cdq
iv ecx
; Line 13
mov esi, ecx
mov ecx, edx
test ecx, ecx
je SHORT $L547
$L563:
; Line 10
mov eax, esi
pop esi
; Line 15
ret 0
_EuclidGCD ENDP
_TEXT ENDS
END
```

At the beginning of the function, eax contains m, and esi contains n. When the instruction "idiv esi" is executed, eax contains the quotient (q), and edx contains the remainder (r). The instruction "mov ecx, edx" moves r into ecx, while q is not used, and therefore discarded.

## 24.4 Example: Decompile Optimized Code

Below is the optimized listing of the EuclidGCD function, presented in the examples above. Can you decompile this assembly into equivalent C code? How is the optimized version different from the non-optimized version?

```asm
PUBLIC _EuclidGCD
_TEXT SEGMENT
_m = 8 ; size = 4
_n = 12 ; size = 4
_EuclidGCD PROC NEAR
; Line 7
mov eax, DWORD PTR _m$[esp-4]
push esi
mov esi, DWORD PTR _n$[esp]
cdq
idiv esi
mov ecx, edx
```

```asm
; Line 8
test ecx, ecx
je SHORT $L563
$L547:
; Line 12
mov eax, esi
cdq
idiv ecx
; Line 13
mov esi, ecx
mov eax, edx
test ecx, ecx
jne SHORT $L547
$L563:
; Line 10
mov eax, esi
pop esi
; Line 15
ret 0
_EuclidGCD ENDP
_TEXT ENDS
```

Altering the conditions to maintain the same structure gives us:

```c
int EuclidGCD(int m, int n)
{
    int q, r;
    while(1)
    {
        r = m % n;
        if(r != 0)
            do {
                m = n;
                r = m % r;
                n = r;
            }while(r != 0);
    }
    return n;
}
```

It is up to the reader to compile this new 'optimized' code, and determine if there is any performance increase. Try compiling this new code without optimizations first, and then compare the assembly listings to the previous ones.

## 24.5 Example: Instruction Pairings

Q
Why does the dec/jne move faster than the equivalent looppnz?

A
The dec/jnz pair up in the different modules of the netburst pipeline, so they can be executed simultaneously. With that off the fact that the dec and jnz both require few cycles to execute, while the looppnz (and all the loop instructions, for that matter) instruction takes more cycles to complete. loop instructions are rarely seen out by good compilers.

## 24.6 Example: Avoiding Branches

Below is an assembly version of the expression ? d : 0. There is no branching in the code, how does it work?

```asm
; ecx = c and eds = d
; eax will contain c ? d : 0 (eax = d if c is not zero, otherwise eax
; = 0)
neg ecx
sbb eax, eax
and eax, edx
ret
```

This is an example of using various arithmetic instructions to avoid branching. The neg instruction sets the carry flag if c is not zero; otherwise, it clears the carry flag. The next line depends on this. If the carry flag is set, sbb results in eax = eax - eax - 1 = 0xffffffff. Otherwise, eax = 0. Finally, performing and on this result ensures that if ecx was not zero in the first place, eax will contain edx, and zero otherwise.
