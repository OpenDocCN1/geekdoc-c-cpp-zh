## 7 Linux Executable Files

### 7.1 a.out Files

a.out is a very simple format consisting of a header (at offset 0) which contains the size of 3 executable sections (code, data, bss), plus pointers to additional information such as relocations (for .o files), symbols and symbols' strings. The actual sections contents follows the header. Offsets of different sections are computed from the size of the previous section.

## 7.2 ELF Files

Executable and Linkable Format$^1$

The **ELF file format** (short for Executable and Linking Format) was developed by Unix System Laboratories to be a successor to previous file formats such as COFF and a.out. In many respects, the ELF format is more powerful and versatile than previous formats, and has widely become the standard on Linux, Solaris, IRIX, and FreeBSD (although the FreeBSD-derived Mac OS X uses the Mach-O format instead). ELF has also been adopted by OpenVMS for Titanium and BeOs for x86.

Historically, Linux has not always used ELF; Red Hat Linux 4 was the first time that distribution used ELF; previous versions used the a.out format.

ELF Objects are broken down into different segments and/or sections. These can be located using the ELF header found at the first byte of. The ELF header provides the location for both the program header and the section header. Using these data structures the rest of ELF objects contents can be found, this includes .text and .data segments which contain code and data respectively.

The GNU readelf utility, from the binutils package, is a common tool for parsing ELF objects.

**Figure 6** An ELF file has two views: the program header shows the segments used at run-time, while the section header lists the set of sections of the binary.

Each ELF file is made up of one ELF header, followed by file data. The file data can include:

- Program header table, describing zero or more sections
- Section header table, describing zero or more sections
- Data referred to entries in the program or section header table

The segments contain information that is necessary for runtime execution of the file, while sections contain important data for linking and relocation. Each byte in the file is taken by no more than one section at a time, but there can be orphan bytes, which are not covered by a section. In the normal case of a Unix executable one or more sections are enclosed in one segment.

## 8 The Stack

## 8.1 The Stack

![](img/9b6491f497eec80c9bc014658123790_68_png)

Generally speaking, a stack is a data structure that stores data contiguously in memory. Unlike an array, however, you access (read or write) data only at the 'top' of the stack. To read from the stack is said 'pop' and to write to the stack is said 'push'. A stack is also known as a LIFO queue (Last In Out) since values are popped from the stack in the reverse order they are pushed onto (think of how you pile up plates). All x86 architectures use a stack as a temporary storage area in RAM that allows the processor to quickly store and retrieve data in memory. The current top of the stack is pointed to by the esp register. The stack 'grows' downward, from high to low addresses, so values recently pushed onto the stack are located in memory addresses above the esp pointer. Modern operating systems monitor the stack bounds to detect both 'underflow' (popping an empty stack) and 'overflow' (pushing too much information on the stack). When a value is popped off the stack, it remains sitting in memory until overwritten. However you should never rely on the content because other functions may overwrite these values without your knowledge. Users of Windows ME, 98, 3.1 (and earlier) may fondly remember the infamous 'Blue Screen of Death' -- that was sometimes caused by stack overflow exception. This occurs when too much data is written to the stack, and the stack 'grows' beyond its limits. Modern operating systems use better bounds checking and error recovery to maintain system stability after one has occurred.

## 8.2 Push and Pop

The following lines of ASM code are basically equivalent:

```
mov DWORD PTR:[esp], eax
add esp, 4
```

but the single command actually performs much faster than the alternative. It can be visualized that the stack grows from right to left, and esp decreases as the stack grows in size.

## 8.3 ESP In Action

![](img/9b6491f497eec80c9bc014658123790_70_png)

This code example uses MASM Syntax. Let's say we want to discard 3 items we pushed onto the stack, without saving the values (in other words 'clean' the stack). The following works:

```
pop eax
pop eax
pop eax
xor eax, eax because we don't need the values
```

However there is a faster method. We can simply perform some basic arithmetic on esp to make the pointer go "above" the data items, so they cannot be read anymore, and can be overwritten with the next push commands.

```
add esp, 12 ; 12 is 3 DWORDs (4 bytes * 3)
```

Likewise, if we want to reserve room on the stack for an item bigger than a DWORD, we can use a subtraction to move esp forward. We can then access our reserved memory directly as a memory pointer, or we can access it indirectly as an offset from esp. Say we wanted to create an array of bytes values on the stack, 100 items long. We want to store the pointer to the base of this array in edi. How do we do it? Here is an example:

```
sub esp, 100    ; num of bytes in our array
mov edi, esp     ; copy address of 100 bytes area to edi
```

To destroy it, we simply write the instruction:

```
add esp, 100
```

## 8.4 Reading Without Popping

To read values on the stack without popping them off the stack, esp can be used with an offset. For instance, to read the 3 DWORD values from the top of the stack into eax (but without using a pop instruction), we use the instructions:

```
mov eax, DWORD PTR: [esp]
mov eax, DWORD PTR: [esp + 4]
mov eax, DWORD PTR: [esp + 8]
```

Remember, since esp moves downward as the stack grows, the data on the stack can be accessed with a positive offset. A negative offset should never be used because data 'above' the stack cannot be counted on to stay where you left it. The operation of reading from the stack without popping is often referred to as 'peeking', but since this isn't the official term for this wikibook won't use it.

## 8.5 Data Allocation

There are two areas in the computer where a program can store data. The first, the one we have been talking about, is the stack. It is a linear LIFO buffer that allows allocations and deallocations, but has a limited size. The heap is typically a non-linear data storage area, typically implemented using linked lists, binary trees, or other more exotic methods. Heaps are slightly more difficult to interface with and to maintain than a stack, and allocations/deallocations are performed more slowly. However, heaps grow as the data grows, and new heaps can be allocated when data quantities become too large.

As we will see, explicitly declared variables are allocated on the stack. Stack variables are finite in number, and have a definite size. Heap variables can be variable in number and in size. We will discuss these topics in more detail later.
