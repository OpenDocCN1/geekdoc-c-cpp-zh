
During OOA, you express the problem and the requirements of a solution in relevant objects. These objects may represent real-world objects, software systems, or ideas. Using OOA, you describe these objects and their interactions among one another. Analysis work involves the discovery associated with understanding the problem. It does not involve thinking about a solution to the problem, and instead focuses on thinking about the problem itself.

The results of analysis act as input to the process of design. During object-oriented design (OOD), you describe a solution to the problem, fulfilling the requirements you discovered during analysis. You express the solution in terms of software objects, and you note how objects collaborate. Objects collaborate when they send each other messages; that is, objects call on another to perform operations. The interactions are as important as the objects themselves and require careful planning. To solve the problem efficiently, the collaborations among objects should be minimal and meaningful.

During OOD, you typically create one or more models for the solution. Some of the models emphasize the interactions among objects; others show the relationships among objects. Taken together, they create a design that can be implemented in C++ or any other object-oriented language.

## 1.1.2 Aspects of an Object-Oriented Solution

Unless otherwise, a solution to a problem in this book is a computer program. A program comprises working modules. A module is a self-contained unit of code and could be a single-alone function, a class, a method itself, a group of functions or classes that work closely together, or other blocks of code. Exactly how a module depends depends on the type and size of the application. Functions and methods implement algorithms, which are step-by-step recipes for performing a task within a finite period of time. One action that an algorithm performs is operating on a class.

When designing a solution, your challenge is to create a good set of modules. These modules must store, move, and alter data. They also use methods to communicate with one another. When constructing a solution, you organize your data collection so that you can operate on the data in the manner an algorithm requires. In fact, most of this book describes ways of organizing data.

Object-oriented programming languages allow you to build classes of objects. A class combines the attributes—characters of a type with the objects' behaviors—into a single unit. The individual items specified in a class are called data members. Operations are typically data, and methods are functions that often operate on data. In programming languages such as C++ and Java, classes specify the attributes and operations for the objects.

Encapsulation is a technique that hides inner details. Whereas functions encapsulate behavior, objects encapsulate data as well as behavior. For example, a class encapsulates the time—an attribute—along certain operations, such as setting or displaying the time. You can request that a class perform operations but you cannot see how they are done (unless you have a mechanical class with see-through sides).

Classes can inherit properties and operations from other classes. For example, once you define a base class of objects, you can design a subclass that inherits the properties of it but adds attributes that provide the functionality of an ally. You can produce an alarm clock quickly because the clock portion is done. Thus, inheritance—another object-oriented concept—allows you to reuse classes you defined earlier for a related purpose by extending that implementation with modifications.

Inheritance may make it impossible for the compiler to determine which operation you require in a particular situation. However, polymorphism—which literally means many forms—allows the determination to be made at execution time. That is, the outcome of a particular operation depends upon the object that performs the operation. For example, you can create a pointer to a clock object, myClock, in your program in such a way that it could reference either a clock object or an alarm clock. When myClock is called to display the time, the compiler cannot determine whether it should use the clock implementation to display the time or the alarm clock implementation, since it does not know which class of clocks the object referenced by myClock belongs. Polymorphism allows the compiler to simply note that the meaning of an operation is unknown until execution time.

Note: Three principles of object-oriented programming
1. Encapsulation: Objects combine data and operations.
2. Inheritance: Classes can inherit properties from other classes.
3. Polymorphism: Objects can determine appropriate operations at execution time.

## 1.2 Achieving a Better Solution

The last program you wrote likely solved the given problem correctly. However, was it the best possible solution? If you spent little—any—time on analysis and design, the solution probably left something to be improved. If you were to code the same program again, you would undoubtedly produce a better solution than your first attempt. If you spent some time analyzing the problem and designing a solution, you would probably get your best solution.

Suppose you generated three correct but different solutions. How could you identify if each solution makes it better than the others? What are the aspects? What would you focus on to create better solutions?

Creating a set of modules for a moderate-sized project is more art than science. It requires experience on part of the programmer. A given problem likely has no “best” set of modules. Some sets of modules and their interactions—might be better than others in light of certain measures. Moreover, for a sufficiently large project, several different sets of modules could be considered “best,” depending upon the pressure used. The “best” designs, however, do adhere to certain principles, which we must examine.

### 1.2.1 Cohesion

Each module should perform one well-defined task; high cohesion is a goal of good module design. High cohesion makes a module easier to understand, maintain, and reuse. Low cohesion means a module is doing too many unrelated things, which makes it difficult to manage.

First, high cohesion makes a module easier to understand. When a module has one clear purpose, its code is straightforward to follow. If a module has many unrelated tasks, it becomes complex and hard to reason about.

Second, high cohesion makes a module easier to maintain. When a module has a single responsibility, changes to that responsibility are unlikely to affect other parts of the program. This reduces the risk of introducing bugs.

Third, high cohesion makes a module easier to reuse. A module with a focused purpose can be used in many different contexts or projects. If a module has many unrelated responsibilities, it is difficult to extract and use elsewhere.

Fourth, high cohesion makes a module more robust. A module that does one thing is less likely to be affected by changes in other areas. This makes the system more stable and reliable.

Note: A guiding principle of OOD is that each class should have a single responsibility. The methods of a class should be functionally equivalent. If a class has too many responsibilities, it should be split into multiple classes, each with one.

### 1.2.2 Coupling

Coupling is a measure of the dependence among modules. This dependence, for example, could involve sharing data structures or calling each other' methods. Ideally, modules should be independent of one another. However, some degree of coupling is necessary to get work done. That is, modules should be loosely coupled, and highly coupled should be avoided.

Loose coupling benefits a system in several ways:
- It creates a system that is more easily adaptable. If class A depends on—that is, highly coupled to—class B and B is changed, it is very likely that these changes will affect class A and break it.
- It makes the system easier to understand. If class A depends on B, understanding how A works requires an understanding of B. Thus, class A is difficult to understand in isolation.
- It increases the reusability. If class A depends on B, reusing class A in another program is complicated by the need to include class B as well. Reusing coupled modules requires all of the modules as a unit. This is often not ideal, or possible.
- It makes the system more robust. A module that is loosely coupled is less likely to be affected by changes. This makes the system more stable and reliable.

Again, realize that coupling is required; coupling cannot and not be eliminated from objects to one another. Tasks that an object has delegated to other objects create coupling between these objects. This coupling is necessary, but it should be kept to a minimum. However, other factors may influence a design. Thus, some designs with more coupling are better than other designs with less coupling because of these factors.

Note: If, in the past, you have spent little or no time on analysis and design for your programs, you must change this habit! The result of OOD should be a modular solution that is easy to translate into the constructs of a particular programming language. By spending adequate time with analysis and design, you will spend less time writing and debugging your program.
