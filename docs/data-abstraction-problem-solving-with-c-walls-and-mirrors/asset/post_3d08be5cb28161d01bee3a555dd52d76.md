Unlike variables on the run-time stack, which have their memory allocated and deallocated automatically, variables in the free store persist in memory even when the function or method that created them ends. This means that when a programmer allocates memory from the free store for a variable, the programmer has the responsibility to deallocate that memory when the variable is no longer needed. Failure to do so results in a memory leak. A memory leak is memory that is allocated but no longer needed and cannot be accessed or deallocated.

Pointer variables are simply another type of variable and follow the same rules as other variable types. For example, if you declare a pointer variable that points to a ToyBox<string> object, you can have point only to ToyBox<string> objects, not MagicBox<string> objects or ToyBox<double> objects, as the following statements illustrate:

```
ToyBox<string>* toyPtr = new ToyBox<string>(); // OK
ToyBox<string>* boxPtr = new MagicBox<string>(); // Error!
ToyBox<string>* somePtr = new ToyBox<double>(); // Error!
```

If you have two pointer variables that can point to the same type of object, you can make them point to the same object by using the assignment operator =. For example, the statement
somePtr = toyPtr;

makes the variable somePtr to point to the same ToyBox object which toyPtr points. In such cases, it is helpful to think of assignment operation as copying the value stored within the pointer variable on the right into the pointer variable on its left. Since pointers store addresses of objects, the value copied is the location of the object in the free store. The object itself is not copied. The result is that both pointer variables point to the same object, as shown in Figure C2-5.

If you declare a pointer variable but not immediately create an object for it to reference, you should set the pointer to nullptr. An assignment like the following one is necessary because C++ does not initialize the pointer for you:

```
ToyBox<int>* myToyPtr = nullptr;
```

### C2.3.1 Deallocating Memory

When the memory to which a pointer points is no longer needed, you allocate it by using the delete operator. You should then set the pointer variable to nullptr as a signal that it no longer references or points to an object:

```
delete somePtr;
somePtr = nullptr;
```

## Pointers and the Program's Free Store 123

If we did not set somePtr to nullptr in this example, somePtr would be an example of a **dangling pointer**, because it would still contain the address of an object that was deallocated. Dangling pointers can be the source of serious errors.

Always remember that if a class uses new to create an object, some method of the class must delete the object's memory. It is a characteristic of safe and secure programming that any allocating memory from the free store also carries responsibility to deallocate memory when it is no longer needed.

Pointers give a great amount of control over how memory is used and when binding occurs, as we will discuss shortly. They can also create severe problems and hard-to-find bugs if not used properly. The most common errors involving pointers are the memory leak and the dangling pointer, as presented in this section. ## C.3.2 Avoiding Memory Leaks

Memory leak occurs when an object has been created in the free store, but the program no longer has a way to access it. Because the object cannot be accessed, it cannot be deleted and takes up memory, even though it cannot be used. A program can run out of memory and crash if it has several memory leaks.

Consider the following statements:

```
MagicString* myBoxPtr = new MagicBox<string>();
MagicString* yourBoxPtr = new MagicBox<string>();
yourBoxPtr = myBoxPtr; // Results in inaccessible object
```

Figure 2-6 traces the execution of these statements. Eventually, yourBoxPtr points to the same object as myBoxPtr, and the object to which yourBoxPtr originally pointed is no longer accessible, resulting in the memory leak shown in part of the figure.

To prevent this, we should not create the second object. Instead, either initialize yourBoxPtr to nullptr or set it to myBoxPtr:

```
MagicString* myBoxPtr = new MagicBox<string>();
MagicString* yourBoxPtr = myBoxPtr;
```

A subtle memory leak occurs when a function or method creates an object in the free store and loses the pointer to it by not returning that pointer to the caller or not storing it in a class data member. That is what happens in the function in Listing C2-1.

LISTING C2-1 Poorly written function allocates memory in the free store

```
void leakyFunction(const double& someItem)
{
    ToyBox<double>* someBoxPtr = new ToyBox<double>();
    someBoxPtr->setItem(someItem);
```

The parameter someItem and the pointer someBoxPtr are both stored in an activation record on the run-stack time and are automatically destroyed after the function ends. We have several options to fix this function. The first is to delete the object before the function terminates. We can do this by adding the lines

```
delete someBoxPtr;
someBoxPtr = nullptr;
```

at the end of the function. If the Box object pointed to by someBoxPtr is needed only by this function, a better implementation would have been not to allocate memory from the free store, but to use a local variable as is done in the following statements:

```
ToyBox<double> someBox(); // someBox is not a pointer variable
someBox.setItem(someItem);
```

If the object created is outside the function, the function can return a pointer to it that the caller can access the object. To implement this, we would change the function's return type from void to ToyBox<double>* and return someBoxPtr, which is a pointer to the ToyBox<double> object. The resulting definition is

```
ToyBox<double>* leakyFunction(const double& someItem)
{
    ToyBox<double>* someBoxPtr = new ToyBox<double>();
    someBoxPtr->setItem(someItem);
    return someBoxPtr;
} // end leakyFunction
```
