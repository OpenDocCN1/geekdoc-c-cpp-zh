**Removal from a B-tree.** To remove a record with a search key from a B-tree, you take the following steps:

- 1. **Locate the index record in the index file.** You use the search algorithm to locate the index record with the desired key value. If this record is not already in a leaf, you swap it with its inorder successor. Suppose that the leaf L shown in Figure 21-15 contains the index record with the desired key value, 73. After noting the value $p$ of the pointer in this index record (you will need $p$ in step 2 to remove the data record), you remove the index record from L (Figure 21-15b). Because L contains only one value (recall that a node must contain at least two values), and L's siblings cannot share a record, you merge L with one of the siblings and bring a record from the parent P (Figure 21-15c). Notice this is analogous to the merge step for a 2-3 tree. However, P now has only one value and two children, and its siblings cannot share a record and you must merge P with its sibling P', and bring a record down from P's parent, Q. Because P is an internal node, its children must be adopted by P'. (See Figure 21-15d).

After this merge, parent Q is left with only two children and one record. In this case, however, Q's sibling Q' can share a record and so you redistribute children and records among Q', and the parent S completes the remove. (See Figure 21-15e). If a removal propagates all the way to the root, leaving it with only one record and two children, you are finished because the definition of B-tree allows this situation. If a removal causes the root to have a single child and no records, you remove the root so that the tree's height decreases by 1, as in Figure 21-15f. The removal of the index record is complete, and you must remove the data record.

## 21.3.4 Traversals

Now consider the traverse in sorted order, which is one of the operations hashing does not support at all. Often an application requires only the traversal display the search keys of the records. If such is the case, the B-tree implementation can efficiently support the operation, you do not have to access the data file. You can visit the search keys in sorted order by using an inorder traversal of the B-tree, as follows:

Accessing the search key of each record, but not the data file

```

// blockNum is the block number of the root of the B-tree in the index file.
```

This traversal accomplishes the task with the minimum possible number of block accesses because each index of the file is read only once. This algorithm, assumes that internal memory is available for a recursive stack of h blocks, where h is the height of the tree. In many situations this assumption is reasonable—for example, a 256-degree B-tree indexes a file of 16 million data records with a height of no more than 3. When internal memory cannot accommodate h blocks, you must use a different algorithm.

If the traversal must retrieve the entire data record (and not just the search key), the B-tree implementation is less attractive. In this case, as you traverse the B-tree, you must access the appropriate data record of the file. The traversal becomes

## 21.35 Multiple Indexing

Before concluding the discussion of external implementations, let's consider the multiple indexing of a data file. Programming Problem 8 in Chapter 18 asked you to support multiple organizations for data stored in internal memory. Such a problem is also common for data stored externally. For example, suppose that a data file contains a collection of employee records on which you need to perform two types of retrievals:

```
// Retrieves the item whose search key contains the aName.
retrieved(aName: NameType): ItemType

// Retrieves the item whose search key contains the ssn.
retrieved(ssn: SSNType): ItemType
```

Multiple index files allow multiple organizations

One solution to this problem is to maintain two independent index files to the data file. For example, you could have one index file that contains records of the form <name, pointer> and another index file that contains records of the form <socSec, pointer>. These index files could be hashed, both be B-trees, or be one of each, as Figure 21-16 indicates. The choices would depend on the operations you wanted to perform with each search key. Similarly, if an application required extremely fast retrievals on socSec and also required operations such as traverse in sorted socSec order and range queries over socSec, it might be reasonable to have two socSec index files—one hashed, the other a B-tree.
