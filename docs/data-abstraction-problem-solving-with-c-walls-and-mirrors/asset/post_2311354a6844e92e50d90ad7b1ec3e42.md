Another way in which you should make a program fail-safe is to each function check its precondition. For example, consider the following function, factorial, which returns the factorial of an integer:

```cpp
/** Computes the factorial of an integer.
 * @param n Given integer.
 * @pre n > 0.
 * @post None.
 */
int factorial(int n) {
    int fact = 1;
    for (int i = n; i > 1; i--) {
        fact *= i;
    }
    return fact;
} // factorial
```

The initial comments in this function contain a precondition—information about what assumptions are made—as always be the case. The value that this function returns is only if the precondition is met. If n is less than zero, the function will return the incorrect value of I. In the context of the precondition for which this function was written, it may be reasonable to make the assumption that n will never be negative. That, if the rest of the program is working correctly, it will call factorial only with correct values of n. Ironically, this observation gives a good reason for factorial to check the value of n: If n is less than zero, the warning that results from the check indicates that something might be elsewhere in the program.

Another reason the function factorial should check whether n is less than zero is that the function should be correct outside the context of its program. If, if you borrow the function for use in another program, the function should warn you if you use it incorrectly by passing it an n that is negative. A stronger check than the statement of the precondition in a comment is desirable.

> Note: A function should state its assumptions and, when possible, check whether its arguments conform to these assumptions.

In this example, factorial could check the value of n and, if it is negative, return zero, because factors are never zero. The program that uses C++ could check for this unusual value. Alternatively, factorial could abort execution if it is negative. Many programming languages, including C++, provide a mechanism for handling every exception. A module indicates that an error has occurred by throwing an exception. A module reacts to an exception by catching the exception and executing code to deal with the error condition. C++ Interlude provides more information about exceptions.

C++ also provides a convenient function assert(expression) that displays an informative message and aborts a program if expression is zero. You can use assert to check for both error conditions and the validity of preconditions within your program. C++ Interlude 3 provides more information about assert.

## B.6 Debugging

No matter how care you take in writing a program, it will contain errors that you need to track. Fortunately, programs that are modular, clear, and well documented are generally amenable to debugging. Fail-safe techniques, which guard against certain errors and report them when they are encountered, also provide a great aid in debugging.

Without a systematic approach, finding a small mistake in a program can be a difficult task. Many people have difficulty in debugging, perhaps because they believe their program is really doing what it is supposed to. For example, on an execution-time error message at line 1098, a person might say, “That’s the statement at line 1098 not executed, because it is in the else clause and I am positive that it was not.” However, the proper approach is to trace the program's execution by using available debugging features or to add count statements to show which part of the statement was executed. By doing so, you verify the value of the expression in the if statement. If the expression is 0, for example, then your next step is to find out why how.

How can you find the point in a program where something other than what it should be? A typical Integrated Development Environment, IDE, allows you to trace the program's execution by single-stepping through the statements in the program or by breakpoints at which error occurs. You can also examine the contents of particular variables by establishing watches or inserting temporary count statements. The key to debugging is to use these techniques to find what you are going on. This may sound pretty mundane, but the real trick is to use these debugging aids in an effective manner. After all, do not simply put breakpoints, watches, and count statements at random points in the program and have them report random information.

The main idea is to systematically locate the points that cause the problem. A program's logic implies that certain conditions should be true at various points of the program. If the program's results differ from your expectations, an error occurs. To correct the error, you must find the first point in the program at which this difference exists. By inserting breakpoints and watches or loops and functions—such as at the entry and departure points of loops—you can systematically isolate the error.

These diagnostic techniques should inform you whether things start going wrong or after a given point in the program. Thus, after you run the program with an initial set of diagnostics, you should be able to trap the error between two points. For example, if things are fine before you call method $M_1$, but something is wrong by the time you call $M_2$, this information allows you to focus your attention between these two points. You continue the process until eventually the search is limited to only a few statements. There is no place in a program for an error to hide.

> Programming Tip: A statement of truth about some aspect of your program's logic is known as an assertion. You can express an assertion as a comment or by using the assert macro. By including assertions in your program, you facilitate the debugging process.

The ability to place breakpoints, watches, and count statements in appropriate locations and to have them report appropriate information comes from thinking logically about the problem and in part experience. Here are a few general guidelines.

### B.6.1 Debugging Functions and Methods

You should examine the values of the arguments passed to a function or method as at its beginning and end by using either watches or cout statements. Ideally, you should debug each major function or method separately using it in your program.

### B.6.2 Debugging Loops

You should examine the values of variables at the beginnings and ends of loops, as the comments in this example indicate:

```cpp
// Check values of start before entering loop
for (index = start; index <= stop; index++)
{
    // Check values of index and key variables
    // at the beginning of iteration
    ...
    // Check values of index and key variables
    // at the end of iteration
} // end for
// Check values of start and stop after exiting loop
```

### B.6.3 Debugging if Statements

Just before an if statement, you should examine the values of the variables within its expression. You can use breakpoints or cout statements to determine which branch the if statement takes, as this example indicates:

```cpp
// Check variables within expression before executing if
if (expression)
{
    cout << "Condition is true (value of expression 1).";
    ...
}
else
{
    cout << "Condition is false (value of expression 0).";
    ...
} // end if
```

### B.6.4 Using cout Statements

Sometimes cout statements can be more convenient than watches. Such cout statements should report both values of key variables and the location in the program at the variables have those values. You can use a comment to label the location, as follows:

```cpp
// This is point A
cout << "At point A in the computerResults:\n"
    << "x = " << x << ", y = " << y << endl;
```

Remember to disable or remove these statements when your program finally finishes.
