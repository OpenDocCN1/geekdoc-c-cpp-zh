Each call to mergesort recruits twice. As Figure 11-8 illustrates, if each call to mergesort is at level 0, two calls to mergesort occur at level 1 of recursion. Each of these calls then merges twice, so four calls to merge occur at level 2 of the recursion, and on how many levels of recursion are there? We can count them, as:

Each call to mergesort halves the array. Halving the first array produces two pieces. The next recursive calls to mergesort halve each of the first two to produce four pieces of the original array; the next calls have each of these four pieces to produce eight pieces—that is, until there are *n* pieces, the recursive calls continue until the array contains only one item. If *n* is a power of $2^k$, the recursion depth $k = \log_2 n$ levels deep. For example, in Figure 11-8, there are two levels of recursive calls to mergesort because the original array contains eight items and $2^3$. If not a power of 2, there are $1 + \log_2 n$ (rounded up) levels of recursive calls to mergesort. 

The original call to mergesort (at level 0) merges nothing. Then each merges and requires $3 \times n - 1$ operations, as shown before. At level 1 of recursion, two calls to mergesort, hence merge occur. Each of these two calls merge $n/2$ items and requires $3 \times (n/2 - 1)$ operations. At level $m$ of recursion, $2^m$ calls to merge each have $n/2^m$ items and so require $3 \times (n/2^m - 1)$ operations. Together the $2^m$ merges require $O(n)$ operations. Since there are either $O(\log n)$ or $O(\log n)$ levels, the merge sort is $O(n \times \log n)$ in both the worst and average cases. You should look at Figure 10-3 in the previous chapter to convince yourself that $O(n \times \log n)$ is significantly faster than $O(n^2)$.

Although it is an extremely efficient algorithm with respect to time, it does have one drawback: the merge sort requires an auxiliary array. This extra storage and the necessary copying of entries is disadvantageous.
