The class diagram represents a conceptual model of a class of objects in a language-independent way. That, the diagram does not dictate how the class is implemented. It just gives you a design to work from. However, you can specify many qualities associated with the attributes and operations of the class as an option. These qualities are easily implemented in C++, and they increase the amount of information given in a design.

The UML syntax for the attributes of a class is
`[visibility] name [type]=defaultValue[{property}]`

where

-   * All elements within brackets are optional.
- visibility can be + for public accessibility, - for private accessibility, or # for protected accessibility. (C++ Interleave 4 covers protected accessibility.) If omitted, the visibility defaults to private accessibility.
- name is the name of the attribute.
- type is the data type of the attribute.
- defaultValue is the default value of the attribute.
- property indicates some property that applies to this attribute.

At a minimum, an attribute should be defined. The defaultValue is given only in situations where the design dictates that a default value is appropriate for that attribute. In certain cases it might be appropriate to omit the type of attribute, leaving this decision until the implementation phase.

The UML specifies that programming-language-independent names be used for the type of an attribute. This text will follow the UML recommendations by using integer for integral storage, float for floating-point storage, bool for boolean storage, and string for string strings.
The property of an attribute can have one of the following values:

-   * changeable indicates a normal, modifiable attribute and is usually omitted.
- frozen indicates a constant or write-once attribute.

The attributes for the Bank class in Figure C-3b could be written as
-name: string
-routingNum: integer

The visibility of these attributes praise adheres to the object-oriented programming principle of information hiding.

The UML syntax for a class’s operations is more involved:
`[visibility] name ([parameterList]) [type]{[property}]`

where

-   - All elements within square brackets are optional.
- visibility is the same as specified for attributes, except if omitted operations default to public accessibility.
- name is the name of the operation.
- type is the data type of the result returned from the operation. If the operation returns nothing, type can be omitted or specified as void. The same language-independent types apply here as for attribute types.
- property indicates some property that applies to this operation. The only property relevant to it is ry, which indicates that the operation will not modify any of the data members in the calling object.
- parameterList is either empty—in which the parameters are still required—or contains a comma-delimited list of parameters to the operation. The syntax for each parameter looks like this:

```
[direction]name:type[=defaultValue]
```

where

-   - All elements within square brackets are optional.
- direction shows whether the parameter is used for input (in), output (out), or both input and output (out).
- name is the name of the parameter.
- type is the data type of the parameter. The same language-independent types apply here as for attribute types.
- defaultValue is the value of this parameter if no actual argument is provided when this operation is called.

In Figure C-3b, the Bank operations could be written as
+authorize(in name: string, in identifier: string): void {query-createAccount()}

The authorize operation has public accessibility, and the createAccount operation is private. Because the design of the authorize operation has the query property specified, this operation will not change any of the data in the calling object.

The UML provides for several types of relationships between the classes in a class diagram. For example, Figure C-4 shows a static (class) diagram for a banking system. Because the bank has checking accounts and savings for customers, the diagram shows five classes of objects: a Bank class, a Customer class, an Account class, a Checking class, and a Savings class. These classes are related by sending message through each other. These collaborations, the classes are related to one another in various ways.

For example, the Bank and Customer have an association relationship indicated by the solid line with no arrows. The numbers at the ends of the association—and relationships are multiplicities. Each bank is associated with two or more customers, but each customer is associated with one account. Each customer can have multiple types of account, and each account can belong to only one customer.

The Bank Account relationship is in one kind of part/whole relationship called an aggregation, or containment, relationship that is denoted by the diamond arrow head near the containing class. In an aggregation relationship, the lifetime of the object contained and the object contained are not necessarily the same. Banks “live” longer than the accounts that they contain.
