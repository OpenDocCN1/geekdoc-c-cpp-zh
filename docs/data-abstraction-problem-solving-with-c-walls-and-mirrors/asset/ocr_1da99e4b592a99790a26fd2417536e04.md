Thus, two facts emerge from the recursive version of inorder when a return is made from a recursive call:

+   * The recursive stack of nodes is used to find the node $p$ that the traversal must go back to.

+   * Once the stack backs up to node $p$, it visits $p$ (for example, displays its data) or backs further up. The tree $p$’s left subtree has been traversed; it backs up if its right subtree has been traversed. The appropriate action is taken as a consequence of the point—1 or 2—to which control is returned.

You could directly mimic this using an iterative method and an explicit stack, as some bookkeeping device kept track of which subtree of a node had just been. However, you can use the following observation to eliminate the need for bookkeeping and speed up the traversal. Consider the tree in Figure 16-6. After you have finished traversing the subtree rooted at $R$, there is no need to return to nodes $C$ and $B$, because the right subtrees of these nodes have already been traversed. You can instead return to node $A$, which is the nearest ancestor of $R$ whose right subtree has not yet been traversed.

This strategy of returning to a node after its right subtree has been traversed is simple to: place a node to the stack before the node’s left subtree is traversed, but before its right subtree is traversed. In Figure 16-6, when you are at node $R$, the stack contains $A$ and $R$, with $B$ and $C$ not in the stack, because you have them already are currently traversing their right subtrees. On the other hand, $A$ is in the stack because you are currently traversing its left subtree. When you return from node $R$, nodes $B$ and $C$ are thus bypassed because you have finished with their right subtrees and do not need to return to these nodes. Thus, you $R$’s pointer from the stack goes directly to node $A$, whose left subtree has just been traversed. Then you visit $A$, its pointer from the stack, and traverse $A$’s right subtree.
