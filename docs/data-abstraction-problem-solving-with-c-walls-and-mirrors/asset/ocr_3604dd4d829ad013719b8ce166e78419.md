What are the specific characteristics of good solutions? How can you construct good solutions?
This appendix provides some answers to these very difficult questions. However, the novice programmer usually does not truly appreciate their importance. After the first course in programming, many students will simply want to "get the thing done." The discussion that follows should help you realize how important these themes really are.

One of the most widespread misconceptions held novice programmers is that a computer program is "read" only by a computer. As a consequence, they consider only whether the computer is able to "understand" the program—that is, the program complete, execute, and produce the correct output? The truth is, of course, that other people often read and modify programs. A typical programming environment involves reading programs written by others, and a year later, a different person may modify the program. It is essential that you take great care to design a program that is easy to read and run.

You should always keep in mind the following seven themes of programming: modularity, style, modifiability, ease of use, fail-safe programming, debugging, and testing.

# B.1 Modularity

As this book thoroughly emphasizes, you should strive for modularity in all phases of the problemsolving process, beginning with the initial design of a solution. Many programming tasks become more difficult as the size and complexity of a program grows. Modularity slows the rate at which the level of difficulty grows. More specifically, modularity has a favorable impact on the following aspects of programming:

+   **Constructing the program.** The difference between a small modular program and a large modular program is simply the number of modules each contains. Because the modules are independent, writing one large module is not different from writing many small, independent programs, although the interrelationships among modules make the design much more complicated. On the other hand, working on a large modular program is much like working on many unrelated programs simultaneously. Modularity also permits team programming, where several programmers debug their own modules before combining them into one program.
**Debugging the program.** Debugging a large program can be a monstrous task. Imagine you have a 9,000-line program and need to get it to run. Neither of these tasks would be easy. Now imagine you write your program, and after a few hundred lines of output, you encounter an incorrect number. You should anticipate spending the day or tracing to find the intricacies of your program before discovering a problem such as an index that of.
A great advantage of modularity is that the task of debugging a large program is reduced to one of debugging small programs. When you begin to code a module, you should be almost certain that all other modules coded so far are correct. That is, before you consider a module finished, you should test it extensively, both separately and in context with the other modules, by calling with actual arguments carefully chosen to induce all possible behaviors of the modules. If this testing is done thoroughly, you can fairly sure that any problem is a result of an error in the last module added. *Modularity isolates errors.*
