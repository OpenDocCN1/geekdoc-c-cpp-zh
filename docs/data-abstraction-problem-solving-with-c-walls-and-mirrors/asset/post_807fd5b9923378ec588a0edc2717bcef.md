### 5.1.2 Two Simple Languages

Now consider two simpler examples of languages, their grammars, and, recognition algorithms.

**Palindromes.** A palindrome is a string that reads from left to right as it does from right to left. For example, "radar" and "deed" are both palindromes. You can define the language of palindromes as:

> Palindromes = { s : s reads the left to right as right to left }

How can you use a grammar to define the language Palindromes? You need to decide a rule that allows you to determine whether a given string s is a palindrome. In the spirit of recursive definitions, you should state this in terms of determining a smaller string is a palindrome. Your first instinct might be to choose s minus its last (or first) character for the smaller string. However, this approach does not work, because there is no relationship between the statements

- s is a palindrome
- s minus its last character is a palindrome

That is, s might be a palindrome, although s minus its last character is not, as is the case for "deed." Similarly, s minus its last character might be a palindrome, although s is not, as is the case for "deeds."

A little thought reveals that you must consider characters in pairs: there is a relationship between the statements

- *s is a palindrome*
- s minus its first and last characters is a palindrome

Specifically, *s* is a palindrome if and only if

- The first and last characters of *s* are the same
- s minus its first and last characters is a palindrome

You need a base case that you will reach after stripping away enough pairs of characters. If *s* has an even number of characters, you will eventually be left with two characters, and then, if you strip another pair, you will be left with zeros. A string of length 0 is the **empty string** and is a palindrome. If s has an odd number of characters, you will eventually be left with one character, after which you can strip another pair. Hence, you must have a base case: A string of length 1 is a palindrome.

This discussion leads to the following grammar for the language of palindromes:

```
<pal> = empty string | <ch> | a <pal> | b <pal> | .. | Z <pal> | Z
<ch> = a | b | .. | Z | A | .. |
```

Based on this, you can construct a recursive valued function for recognizing palindromes. The pseudocode for such function cases:

```js
// Returns true if the string s is of a palindrome; otherwise returns false.
isPalindrome(s: string): boolean
if (s is the empty string or s is length 1)
    return true
else if (s's first and last characters are the same)
    return isPalindrome(s minus its first and last characters)
else
    return false
```

**Strings of the form AⁿB*.** The notation 'AⁿB*' represents the string that consists of *n* consecutive A's followed by *n* consecutive B's. Another simple function for this language of strings consists:

AnBn = {string s : s is of the form AⁿB* for some n ≥0}

The grammar for this language is actually very similar to the grammar for palindromes. You strip away both the first and last characters to confirm that the first character is an A and the last is a B. Thus, the grammar for the language AnBn is

```
<legal_word> = empty string | A <legal_word> B
```

The pseudocode for recognizing this language of strings follows:

```js
// Returns true if the string s is of the form AⁿB*; otherwise returns false.
isBn(s: string): boolean
if (s is the empty string or s is length 1)
    return true
else if (s starts with 'A' and ends with 'B')
    return isBn(s minus its first and last characters)
else
    return false
```

### 5.2 Algebraic Expressions

Recursion as a Problem-Solving Technique

Even with precedence rules, an expression like a+b*c is ambiguous. Typically, / and * have equal precedence, so you could interpret the expression either as (a/b)*c or as a/(b*c). The common practice is to associate from left to right, thus yielding the first interpretation.

Two alternatives to the infix convention are prefix and postfix expressions. Under these conventions, an operator appears before its operands (prefix) or after its operands (postfix). Thus, the infix expression a+b is called infix.

To illustrate the conventions, consider the infix expression a+b*c just considered. You write the expression a*(b*c) in prefix form as +*bc. The + appears before its operands a and (* c), and the * appears before its operands b and c. The same expression is written in postfix form as abc*+. The * appears after its operands b and c, and the + appears after its operands a and (b c*). Similarly, you write the expression (a+b)*c in prefix form as *abc. The * appears before its operands (+ a b) and c, and the + appears before its operands a and b. The same expression is written in postfix form as ab+*. The + appears after its operands a and b, and the * appears after its operands (a b+) and c.

In the infix notation, parentheses are used to specify the order of operations. For example, (a+b)*c removes the ambiguity. If you use parentheses, you specify that + is the first operation to be performed.

In prefix notation, the operator precedes the operands. For example, +*bc means b and c are multiplied, and then the result is added to a. In postfix notation, the operator follows the operands. For example, ab+* means a and b are added, and then the result is multiplied by c.

All three notations—infix, prefix, and postfix—are ways of representing the same mathematical expression. The infix notation is the most common in mathematics, while prefix and postfix are often used in computer science because they are easier for compilers to parse.
