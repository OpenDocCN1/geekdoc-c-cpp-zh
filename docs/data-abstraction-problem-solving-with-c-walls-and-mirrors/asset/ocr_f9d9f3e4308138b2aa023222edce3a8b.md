```
// Else search appropriate half of index file
else if (searchKey < (buf.get(0)).getKey())
    return getItem(first half of indexFile, dataFile,
        searchKey)
else
    return getItem(second half of indexFile, dataFile,
        searchKey)
```

Because the index records are far smaller than the data records, the index file can contain fewer blocks than the data file. For example, if the index records are one-tenth the size of the data records and the data file contains 1000, the index file will require only 100 blocks. As a result, the use of an index cuts the block count in getItem down from log,1000 ≈ 10 to about 1 + log,100 ≈ 8. The one additional block is access to the data file once you have located the appropriate record.

The reduction in blocks is far more dramatic for the add and remove operations. In the implementation, if you insert a record or remove a record from the first block of the data file, you have to shift records in every block, requiring you to shift all 1000 blocks of the data file (See Figure 21-5).

However, when you perform an insertion or removal using the index scheme, you only shift index records. When you use an index, you do not keep the data file in any particular order, so you can simply insert a new record into any convenient location in the data file. This flexibility means that you can easily insert a new record at the end of the data file or at a position vacant by a previous removal. However, you do need to shift records in the index file to create an opening for a corresponding entry. Because the index file contains many fewer blocks than the data file (100 versus 1000 in the previous example), the maximum number of accesses required is greatly reduced. A secondary benefit of shifting index records rather than data records is a reduction in the time required for a single shift. Because the index records are smaller, the time required for the statement buf.set(i+1, buf.get(i)) is decreased.

Removals under the index scheme reap similar benefits. If you have searched the index and located the data to be removed, you can simply leave its location in the data file, and you do not need to shift any data records. You can keep track of the vacancies in the data file, so you can insert new records into the vacancies, as needed. The only shifting is required in the index file to fill the gap created when you remove the record that corresponds to the deleted data file.

Even this scheme is an improvement over maintaining a sorted data file, in many applications it is far from satisfactory. The 100 blocks that would be required to insert or remove an index record would be prohibitive. Far better implementations are possible when you use either hashing or search to organize the index file.
