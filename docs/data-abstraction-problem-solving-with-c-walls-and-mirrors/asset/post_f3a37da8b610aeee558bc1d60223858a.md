
Since a bag is an abstract data type, we only describe its data and specify its operations. We don't indicate how to store the data or how to implement its operations. Don't think about arrays, for example. You need to clearly know what the bag operations do: Focus on what the operations do, not on how they do. That is, you need a detailed set of specifications before you use a bag in a program. In fact, you should specify the bag operations before you decide on a programming language.

## 1.5.2 Specifying Data and Operations

Before we can implement a bag in C++, we need to describe its data and specify in detail the methods that correspond to the bag's behaviors. We will name the methods, choose their parameters, decide their return types, and will fully describe each effect on the bag's data. Our goal, of course, is to write a C++ header file and comments for each method. However, we will first express the methods in pseudocode and in UML notation.

The first behavior over CRC code gives rise to a method that returns a count of the number of entries in the bag. The corresponding method has no parameters and returns an integer. In pseudocode, we have the following specification, again using UML notation:

```
// Returns the current number of entries in the bag
+getCurrentSize(): integer
```

We can test whether the bag is empty by a boolean-valued method, again without parameters. Its specification in pseudocode is

```
// Returns true if the bag is empty.
+isEmpty(): boolean
```

We now want to add an object to the bag. We need add the method and give it a parameter to represent the new entry. We will write the following pseudocode:

```
// Adds a new entry to the bag
add(newEntry)
```

We might be tempted to add a void method, if the bag is full, we cannot add a new entry to it. What should we do in this case?

Here are two options that we can take when add cannot complete its task:

- Do nothing. We cannot add another item, so we ignore it and leave the bag unchanged.
- Leave the bag unchanged, but signal the client that the addition is possible.

The first option is easy, but it leaves the client wondering what happened. Of course, we could state as a precondition that the bag must not be full. Then the client has the responsibility to adding a new entry to a full bag.

The second option is the better one, and it is not too late to specify or implement. How we could throw an exception if the addition is not successful. Displaying an error message is not a good choice, as you should let the client dictate output. Since the addition is either successful or not, we can simply have the method return a value. Thus, we can specify the method more completely as

```
+add(newEntry: ItemType): boolean
```

where newEntry’s data is ItemType. In C++, we will discuss the implementation details of templates and typedef statements to give us flexibility in the type of data our ADT can hold.

Two behaviors involve removing entries from a bag: remove a particular entry and remove all entries. Suppose we name the methods and parameters and begin to specify them in pseudocode as:

```
// Removes one occurrence of a particular entry, if possible.
remove(anEntry)
```

```
// Removes all entries from the bag.
clear()
```

What return types are these methods? The method won't be able to remove a given entry if it't in the bag. We will have the method return a boolean value, much as add does, so it can indicate success or not. The UML specification for the method is

```
+remove(anEntry: ItemType): boolean
```

The method clear is a void method: we just want to empty the bag, not change any of its contents. Thus we refine its specification as follows:

```
+clear(): void
```

The remaining behaviors do not change the bag. One of these behaviors counts the number of times a given object occurs within the bag. Its specification in pseudocode is

```
// Counts the number of times an entry appears in the bag.
+getFrequencyOf(anEntry: ItemType): integer
```

Another method tests whether the bag contains a given object. We specify it in pseudocode as:

```
// Tests whether the bag contains an entry.
+contains(anEntry: ItemType): boolean
```

Finally, we want to look at the contents of the bag. Rather than providing a method that displays the entries in the bag, we will define one that places these entries into a vector in any way desired. Here is the specification for our last method:

```
// Gets all entries in the bag.
+toVector(): vector
```

> **Note: Dealing with unusual conditions**
As mentioned earlier, you must make decisions about how to treat unusual conditions. The documentation for the ADT bag should reflect both these decisions and the details in the previous discussion. For example, our specification of the method indicates that it will return false if a client tries to remove an entry from an empty bag. Instead, we could have given the precondition that the bag is not empty. It is up to the client that the precondition is satisfied before invoking the method. Notice that the client can use other methods of the ADT bag, such as isEmpty and getCurrentSize, to help with this task.

A first draft of an ADT's specifications often overlooks or ignores situations that you really to consider. You might intentionally make these omissions to simplify this first draft. If you have written the major portions of the specifications, you can concentrate on the details that the specifications complete.
