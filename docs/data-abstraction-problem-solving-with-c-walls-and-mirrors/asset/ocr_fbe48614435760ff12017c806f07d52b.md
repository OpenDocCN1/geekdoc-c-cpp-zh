**Entries equal to the pivot.** Note that both of the subarrays $S_i$ and $S_j$ can contain entries equal
t pivot. This might seem a strange to you. Why not always place entries that equal the pivot
to the same subarray? Such a strategy would make one subarray larger than the other.
However, to enhance the quick sort's performance, we want the subarrays to be nearly equal as in
as possible.

Notice that both search from the left and the search from the right stop when they encounter
an entry that equals the pivot. This means that when leaving entries in subarrays, they are
swapped. It also means that each search has an entry of landing in each of the subarrays.

**Selecting a pivot.** Ideally, the pivot should be the median value in the array, so that the subarrays $S_i
of $S_j$, each have the same—or nearly the same—number of entries. One way to find the median value
to sort the array and then get the value in the middle. But sorting this logic is doomed. Instead of getting the best pivot by finding the median of all values
in the array, we will all try to avoid a bad pivot.

We will pick the median of three entries in the array: the first entry, the middle entry,
 the last entry. One way to accomplish this is to sort only these three entries and use the mid-
dle of the three as the pivot. Figure 11-11 shows an array before and after its first, middle,
and last entries are sorted. The pivot is 5. This pivot selection strategy is called **median-of-three
pivot selection.**

This pivot selection ensures that the array has three entries. If you have only
tree entries, the pivot selection sorts them, so there is no need for the partition method or for a quick
sort. we now assume that the array contains at least four entries.
