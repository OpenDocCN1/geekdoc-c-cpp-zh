## Approach 2: Restructuring the hash table. Another way to resolve collisions is to change the structure of the array—the hash table—so that it can accommodate more than one item in the same location. We describe two ways to alter the hash table.

A bucket is an element of a hash table that is itself an array

**Buckets.** If you define the hash table so that each table[i] is an array—called a bucket—you store the items in hash table[i] in this array. The problem with this approach, of course, is choosing the size $b$ of each bucket. If $b$ is too small, you will only have the problem of collisions until $b$ items map into some array location. If you attempt to map $b$ large so that each array location can accommodate the largest number of items that map into it, you will likely waste a good deal of storage.

Each hash-dictionary location is a linked chain

**Separate chaining.** A better approach than using buckets is to design the hash table as an array of linked chains. In this resolution-technique, known as separate chaining, each table[i] is a pointer to a chain of nodes containing the items that the hash function has mapped into location $i$, as shown in Figure 18-4. Separate chaining provides a successful approach to resolving collisions. With separate chaining, size of the dictionary is dynamic and can exceed the size of the hash table, because each linked chain can be as long. As you will see in the next section, the length of these chains affects the efficiency of retrievals and removals. Even so separate chaining is the most time-efficient collision-resolution scheme.

We will discuss an implementation of the AD dictionary using hashing and separate chaining in Section 18.4.6 of chapter.

# 18.4.3 The Efficiency of Hashing

An analysis of the average-case efficiency of hashing involves the load factor ($\alpha$), which is the ratio of the current number of items in the dictionary to the maximum size of the array dictionary. That is,

```
α = \frac{Current number of items}{tableSize}
```

The load factor measures how full a hash table is

$\alpha$ is a measure of how full the hash table is. As the table fills, $\alpha$ increases and the chance of collision increases, search times increase. Thus, hashing efficiency decreases as $\alpha$ increases.

Unlike the efficiency of earlier dictionary implementations, the efficiency of hashing does not depend solely on the number $n$ of items in the dictionary. While it is true for a fixed $tableSize$ efficiency decreases as $n$ increases, for a given $n$ you can choose $tableSize$ to increase efficiency. Thus, when determining the size of the hash table, you should estimate the largest $n$ and select $tableSize$ so that it is small as you will shortly, should not exceed 2/3.

Hashing efficiency for a particular search also depends on whether the search is successful. An unsuccessful search requires more time in a successful search. The following analyses$^3$ enable a comparison of collision-resolution techniques.

**Linear probing.** For linear probing, the approximate average number of comparisons to a search requires is

```
$$\left[ 1 + \frac{1}{\alpha}\right]$ for a successful search, and
```

```
$$\left[ 1 + \frac{1}{(1 - \alpha)^2} \right]$ for an unsuccessful search
```

As collisions increase, the probe sequence increases in length, causing unsuccessful search times. For example, for a dictionary that is two-thirds full ($\alpha = 2/3$), an unsuccessful search might require at most five comparisons, or a successful search might require at most two comparisons. To maintain efficiency, it is important to prevent the hash table from filling up.

**Quadratic probing and double hashing.** The efficiency of quadratic probing and double hashing is given by

```
$$- \frac{\log(1 - \alpha)}{\alpha}$ for a successful search, and
```

```
$- \frac{1}{1 - \alpha}$ for an unsuccessful search
```

On average, both techniques require fewer comparisons than linear probing. For example, for a dictionary that is two-thirds full, an unsuccessful search might require at most three comparisons, or a successful search might require at most two comparisons. You can use a smaller hash table for quadratic probing and double hashing than you can for linear probing. However, because they are open-addressing schemes, all three suffer when you are unable to predict the number of insertions and removals that will occur. If your hash table is too small, it will suffer efficiency.

**Separate chaining.** The table, $tableSize$ places the new item at the beginning of a linked chain within the table, as is $O(1)$. The get and remove operations, however, are not as fast. Each search of the linked chain, ideally you would like for these to be short. For separate chaining, $tableSize$ is the number of chains, not the maximum number of dictionary items. Thus, it is entirely possible, even when the current number of items exceeds $tableSize$. That is, $n/tableSize$, the factor $\alpha$, is the average length of each linked chain.

> Note: Maintaining the performance of hashing
Collisions and their resolution usually cause the load factor to increase and the efficiency of the dictionary operations to decrease. To maintain efficiency, you should restrict the size of $\alpha$:
* $\alpha < 0.5$ for open addressing
* $\alpha < 1.0$ for separate chaining
Should the load factor exceed these bounds, you must increase the size of the hash table using hashing.

# 18.44 What constitutes a Good Hash Function?

Before we conclude this introduction to hashing, consider in detail the issue of choosing a hash function to perform the address calculations for a given application. A great deal has been written on this subject, which is beyond the mathematical level of this book. This section will present a brief summary of the major concerns.

- Is the hash function fast and easy to construct? If a hashing scheme is to perform dictionary operations almost instantaneously and in constant time, you must be able to calculate the hash function rapidly. Most common hash functions require only a single division (like the modulo operation), a multiplication, or some kind of “bit-level” operation on the internal representation of the search. In all cases, the requirement that the hash function be fast and easy to compute is satisfied.
- Does hashing scatter even throughout the hash table? Unless you use a perfect hash function—which is impractical to construct—you typically avoid collisions. For example, to achieve the best performance from a separate-chaining scheme, each table should point to a chain containing approximately the same number of items, and each chain should contain approximately $n/tableSize$ items (and thus not contain significantly more than $n/tableSize$ items). To accomplish this goal, your hash function should scatter the search keys evenly throughout the hash table.
- Does the hash function scatter random data? If every search-key value is equally likely, will the hash function scatter the search keys evenly? For example, consider nine-digit employee IDs as the search keys, a hash table[0..39], and a hash function h(x)=(first two digits of x) mod 40.
