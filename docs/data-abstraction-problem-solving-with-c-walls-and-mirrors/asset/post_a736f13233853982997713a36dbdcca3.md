The Unified Modeling Language, or UML, is a modeling language used to express object-oriented designs. The UML provides specifications for many types of diagrams and text-based descriptions of various aspects of a design. The diagrams are particularly useful in showing specific, interesting aspects of the elements in the domain of the problem.

A use case is a textual story; a scenario describes the system's behavior under certain circumstances from the perspective of the user.

# C.1 The Use Case

A use case is a set of scenarios that describe the proposed solution. A use case is not object-oriented, but it is an important part of the analysis of the problem. A single use case has several scenarios. The main success scenario (or "happy path") describes how the system satisfies the goals of the user when everything goes smoothly. Alternate scenarios describe the interaction between the user and the system when things do not go well or when exceptional conditions occur.

For example, suppose a customer wants to withdraw money from his or her checking account. A main success scenario might look like this:

An example of a main success scenario

Customer makes a request to withdraw money from a bank account. Bank identifies and authenticates the customer. Bank gets from the customer the type of account (savings or checking), the account number, and the amount of the withdrawal. Bank verifies that the account balance is greater than the amount of money. Bank generates a receipt for the transaction. Bank counts out the amount for the customer. Bank gives the customer the receipt and money. Customer leaves the bank.

A scenario is written from the perspective of the user of the system. In this way, the analysis will focus on the responsibilities of the system to meet a user's goals. That is, the analysis will focus on what the scenario needs to accomplish the goals of its users.

Notice that the scenario does not describe how the system works. For example, "Bank identifies and authenticates the customer" does not indicate how this occurs. The focus should be on the interactions between the user and the system but not on the user interface, which will be explored during design.

Alternate scenarios should be written only for stories that are interesting or tricky. For example, one scenario describes what happens when the customer authenticates:

An example of an alternate scenario

Customer makes request to withdraw money from a bank account. Bank identifies but fails to authenticate the customer. Bank refuses to process the request. Customer leaves the bank.

Other alternate scenarios could include the denial of a withdrawal request because insufficient funds are in the account or the bank does not have sufficient cash on.

From the scenarios in this case, you generate a list of objects by listing the nouns in the case. (This is where the analysis becomes object oriented.) For example, bank, money, customer, account, type, number, transaction amount, and receipt are all in the main scenario. The final million might not use all of the objects discovered.

# C.2 UML Sequence Diagrams

A UML sequence diagram shows the interactions among objects over time

After you create a use case and list objects, you need to explore how these objects will interact with one another. You accomplish this by UML sequence diagrams that model the use case scenario. A UML sequence diagram, or interaction diagram, shows how two or more objects interact with one another over time within a single scenario. This diagram allows you to visualize the messages sent between objects in the scenario and where those messages are handled. In giving a sense of the flow of the logic, the diagram is important when defining the responsibilities of the objects: What must the object "remember," or keep track of, and what must the object do for other objects? The responsibilities of the objects are described in the use case. Figure-1 shows a UML sequence diagram for the main scenario given previously.

Although the development of the use case is part of object-oriented design (OAD), the creation of sequence diagrams shows the scenario's objects from left to right and their actions in order of occurrence. UML represents an object as a square box containing the name of the object—if it has one—followed by a line and the type of the object. In Figure-1, the type of Bank is named Bank, and the objects of type Customer and Account are nameless.

Each object in a sequence diagram has a lifeline denoted by a dashed line below the object box extending forward in time. Each lifeline can have one or more activation bars, represented by an open box on the lifeline. An activation indicator shows when an object is active—and represents a responsibility of the object's class. A class needs a method to handle responsibility. Such arrows are labeled with a message expression indicating what task object needs to perform. The message expression corresponds to the name of a method for handling task. The message expression may also include parameters necessary for performing the task. Ultimately, these parameters will correspond to method arguments. When an object finishes a task, the activation associated with that task ends. If the task returns something of interest to the calling object, a dashed arrow may be pointing back to the calling object's activation bar. You can label this arrow with the name of the variable received.

In C-1, the customer asks the bank for authorization by giving its name and identifier passed as arguments. The bank processes this message—activated by the activation bar with the bank object's lifeline—and then signals whether or not the customer has been authenticated by returning a value to the variable OK within the Customer object. Note that you should write the messages in a general, language-independent fashion. A bank class could declare the authorize message as follows:

```
class Bank {
public:
    bool authorize(string name, string identifier);
}; // end Bank
```

An object may also send messages to itself, as is done in the generateReceipt and count messages in Figure C-1. Notice the piggybacked activation bars, which indicate that the Bank class is calling its own member methods.

A sequence diagram can also show the creation of a new object. In Figure C-2, a new account is created. This diagram can represent a part of an alternate scenario in a use case, in which a customer comes into the bank but not yet have an account. In the UML, the notation <<create>> is what is known as a stereotype. Stereotypes use left and right guillemets << and >> when drawing a sequence diagram you can simply label the message arrow with create. A stereotype is used to identify a unique characteristic of an element in a UML diagram.

The UML sequence diagram is a design document that gives guidance on several levels to the programmer implementing a solution. It gives a view of how the objects will dynamically interact (collaborate) to solve a use scenario. In particular, a sequence diagram shows

* Which objects collaborate to solve a particular use-case scenario
* The synchronous nature of the messages that are passed between objects, providing the order in which tasks are accomplished
* Which object is responsible for what task or tasks by handling a particular message

# C.3 UML Class Diagrams

The last element we will introduce is the UML class diagram, or static diagram. The class diagram shows the attributes and operations of an individual class and how multiple classes are related to one another. These elements do not change after they have been created within a solution—that is, they are static, or unchanging.

The class diagram shown in Figure C-3 represents a class of banks. Each diagram consists of a square-rectangle box containing the name of the class within its borders. Figure C-3a shows the simplest of class diagrams: a class with a name but no attributes or operations. Figure C-3b shows the bank's attributes in the middle section and operations in the bottom section. If a class has no attributes, in Figure C-3c, an empty middle section must be present.
