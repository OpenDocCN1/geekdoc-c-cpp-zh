# Specifications

You can view these specifications as the terms of a contract between your function and the module
calls it.

Specifications are
them of a
contract

This contract helps programmers understand what responsibilities the module will have to
other modules in the module. Whoever the sort function must live up to this contract. After the
sort function has been written and tested, the contract tells the rest of the program how to call the sort
function properly, as well as the result of doing so.

An operation
contract should not
describe how a
module will perform its task

Notice, that a module's contract does not commit the module to a particular way of
performing its task. If another part of the program assumes anything about the algorithm, it
to its own risk. Thus, for example, if at some later date you rewrite your function to a differ-
sorting algorithm, you do not need to change the contract of the algorithm. As long as the
new function honors the terms of the original contract, the rest of the program should be oblivious
to the change.

Operation contracts
should include
precise
preconditions and
postconditions

This should not be news to you. Although you might not explicitly used the term con-
tract, the concept should be familiar. You write a contract when you write a function's pre-
condition, which is a statement of the conditions that must exist at the beginning of a function,
well as when you write its postcondition, which is a statement of the conditions at the end of a
function. For example, the sort function that adheres to the previous contract could appear in
pseudocode as:

```
// Sort an ascending order.
// Precondition: array is an array of integers; num > 0.
// Postcondition: the integers in array are sorted.
sort(array, num)
```

First-draft
specifications

These pair- and postconditions are abstract, as can be the case in a first-draft
contract. For example, does sorted means ascending or descending order? How large can we
be? While implementing this function, you might assume that sort/means ascending and that
num will not exceed 100. The difficulties that can arise when another person tries to use
sort an array of 500 integers the user will not know your assumptions\unless you documented them by revising the contract as follows:

Revised
specifications

```
// Sort into ascending order.
// Precondition: array is an array of integers and j <= num <= MAX_ARRAY,
// WHERE MAX_ARRAY is a global constant that specifies the maximum size of array.
// Postcondition: anArray[0]<= anArray[1]... <= anArray[num - 1].
// num is unchanged.
sort(array, num)
```

When you write a procedure, begin by describing the behavior of your function's inputs,
ment any global constants that it uses, and finally list all annotations that it makes. Note that in the case of
you write a postcondition, describe what the module has. Note that if a module
or returns a value—which is a critical part of the postcondition—the value
be described.

Precise
documentation is
essential

Novice programmers tend to diminish the importance of documentation, particularly when
they are less experienced designer, programmer, and user of a small program. If you sort
but not write the terms of the contract, you will remember them when you later implement
the function? Will you remember to sort weeks after you have written it? To refresh your
memory, would you examine your program code or read a simple set of pre- and postcond-
tions? As the size of the program increases, good documentation becomes more important, regard-
less of whether you are sole author or part of a team.
