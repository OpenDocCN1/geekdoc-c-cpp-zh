## Dictionaries and Their Implementations

Each of the methods remove, getItem, and contains is passed a search key as its only argument. Each method must search the binary search tree for an Entry object that has a particular search key. How will Dictionary's remove method, for example, call BinarySearchTree's remove method? After all, it requires an Entry object as an argument.

The methods of BinarySearchTree compare Entry objects using either of the operators == or >. These operators are the same ones as Entry overloads. Then we can control how BinarySearchTree will make these comparisons. Because we are searching for a specific search key, which overload == to examine only the search-key portion of the Entry object, the definition of the overloaded operator is

```cpp
template <class KeyType, class ItemType>
bool Entry<KeyType, ItemType>::operator==(const Entry<KeyType, ItemType>&rightHandItem) const {
    return (searchKey == rightHandItem.GetKey());
} // end operator==
```

Now BinarySearchTree can compare Entry objects based only on their search keys. How does Dictionary's remove method call BinarySearchTree's remove method? Because BinarySearchTree's remove expects an Entry object as an argument, Dictionary creates an Entry object that has a specific search key and item type, and passes it to the invoked method. To create this entry, you can write the following expression:

```cpp
Entry<KeyType, ItemType>(ItemType(), searchKey)
```

```cpp
template <class KeyType, class ItemType>
bool Dictionary<KeyType, ItemType>::remove(const KeyType& searchKey)
{
    return tree.remove(Entry<KeyType, ItemType>(ItemType(), searchKey));
} // end remove
```

We leave the rest of the implementation for you to complete as an exercise.

> Note: Usually a binary search tree can support the ADT dictionary operations efficiently. In the worst case, when the tree approaches a linear shape, the performance of the dictionary operations is comparable to that of a linear link-based implementation. If a given application cannot tolerate poor performance, you should use the dictionary implementations presented in either Section 18.4 of this chapter or in Chapter 19.

## 18.3 Selecting an Implementation

A major goal of this chapter is to indicate how the requirements of a particular application influence the selection of an implementation. This discussion generates comments made in Section 10.2.4 of Chapter 10. Some applications require all of the ADT dictionary operations given earlier; others require a subset of them or additional operations. Before choosing an implementation of the ADT dictionary, the problem solver should carefully analyze which operations perspective, efficiency, and motivation are reasons for studying the linear implementations you really need the application at hand. It is tempting to want all possible operations, but this strategy is a poor one, because often one implementation supports some of the operations more efficiently than another implementation. Therefore, if you include an operation that you do not need, you might end up with an implementation of the ADT that does not suit your purpose.

In addition to knowing what operations are needed for a given application, the ADT implementer should know how often the application will perform each operation. Although some applications may require many of every operation, other applications may not. For example, if you invented a dictionary of cities—such as those in Figure 18–1—you would expect to perform many more retrieval operations than additions or removals. If you seldom add items to a dictionary, you could insert an implementation that results in an inefficient add operation, as frequently used operations are efficient. Course, as Chapter 10 mentioned, if an ADT operation is to be used in a life-or-death situation, operation must be efficient even if you rarely need it. The necessary operations, their expected frequency of occurrence, and their required response times are some factors that influence implementation of an ADT you select for a particular application. You should, however, remain conscious of factors other than efficiency, as discussed in Chapter 10.

## 18.3 Three Scenarios

Consider now several application scenarios, each of which requires a particular mix of the dictionary operations. The analysis of various implementations of the ADT will illustrate some of the basic concerns of algorithms. You will see, given an application, how to select an implementation that supports in a reasonably efficient manner the required mix of dictionary operations.

**Scenario A: Insertion and traversal in no particular order.** Mary plans to raise money for a local charity. Tired of previous fund-raisers, Mary suggests a brainstorming session to cover a new money-making strategy. As members voice their ideas, Mary records them by adding each new word to the dictionary. Later, she will insert each of the ideas in the dictionary. Also assume that the organization of the order is relevant—the items can be sorted or unordered. Also assume that operations such as retrieval, removal, or traversal in the linked array do not occur or so infrequently that they do not influence your choice of an implementation.

**An unordered order is efficient**

For this application, maintaining the items in a sorted order has no advantage. In fact, by not maintaining a sorted order, the add operation can be efficient. For unordered linear implementation, you can easily insert a new item in any convenient location. For an unordered array-based implementation, you can easily insert the new item at the itemCount. Figure 18–6 shows the result of this insertion after each itemCount has been updated. For a linked-based implementation, you can simply insert a new item at the beginning of the linked chain. As Figure 18–6 illustrates, the head pointer points to the new item, and the new item points to the item that was first in the chain. Thus, you can insert a new item quickly into either unordered implementation of a dictionary; in fact, the add operation is O(1).

**Array-based versus pointer-based**

Should you choose the array-based or link-based implementation? As you see with other ADTs, an implementation that dynamically uses memory is appropriate if you do not have a good estimate of the maximum size. This brainstorming session likely falls into this category. On the other hand, if you know that the dictionary’s maximum size is not drastically larger than its expected size, the choice is mostly a matter of style. Section 4.5 of Chapter 4 discussed how the expected and maximum number of items in an ADT affect array-based implementation requires less space than link-based implementation, because no explicit pointer is stored. The extra cost of this pointer relative to the size of the data items, however, is insignificant in most situations.

Should you use a binary search in the dictionary implementation for this application? Because such an implementation orders the dictionary items, it does more work than the application. In fact, as you see in Chapter 15, insertion into a binary search tree is O(log n) in the average case; it is slower than the O(1) linear implementations.

**Scenario B: Retrieval.** When you use a processor's thesaurus to look up synonyms for a word you use a retrieval operation. If an ADT dictionary represents the thesaurus, each dictionary item is a record that contains both the word—which is the search key—and the word's synonyms. Frequent retrieval operations require a dictionary that allows you to search efficiently for any item, given its search key. Typically, you cannot alter the thesaurus, so no insertion or removal operations are necessary.

**A sorted array-based implementation can use a binary search**

For an array-based implementation, you can use a binary search to retrieve a particular word's synonyms, if the array is sorted. On the other hand, for a link-based implementation, you must traverse the linked chain from its beginning until you encounter the word.
