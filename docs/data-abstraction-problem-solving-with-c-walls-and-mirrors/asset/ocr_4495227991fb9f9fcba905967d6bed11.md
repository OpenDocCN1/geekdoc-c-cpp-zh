# 1.3.2 Unusual Conditions

As a class designer need to make decisions about how to treat unusual conditions and include these decisions in your specifications. The documentation for methods and functions should reflect these decisions.

In general, you can address unusual situations in several ways. You can

+   * Assume that the invalidations will not occur. This assumption is not as naive as it might sound. A method could state as an assumption—that is, a precondition—restrictions to what a client must adhere. It is then up to the client to check that the precondition is satisfied before invoking the method. As long as the client obeys the restriction, the invalid situation will not occur.
* Ignore the invalid situations. A method could simply do nothing when given data. Doing absolutely nothing, leaves the client without knowledge of what happened.
* Guess at the client's intention. Like the previous option, this choice can cause problems for the client.
* Return a value that signals a problem. For example, a method can return a value that indicates success or failure.
* Throw an exception. Throwing an exception is desirable for a C++ method to react to unusual events. The method can report problem without deciding what to do about it. The exception enables each client to act as needed in its particular situation. For simplicity right now, we will adopt the policy that methods should throw exceptions only in truly unusual circumstances, when no reasonable solution exists. You can learn about exceptions in C++ Interlude 3.

> Note: A first draft of a module's specifications often overlooks or ignores situations that you really need to consider. You might intentionally make omissions to simplify this draft. Once you have written the major portions of the specifications, you can concentrate on the details that make the specifications complete.

# 1.3.3 Abstraction

Abstraction separates the purpose of a module from its implementation. Modularity breaks a solution into modules; abstraction specifies each module clearly before you implement it in a programming language. For example, what does the module assume, and what action does it take? What is this module responsible for when called? Such clarifications help you focus on its high-level functionality without the distraction of implementation details. In addition, they help you modify one part of a solution without significantly affecting the other parts. For example, you should be able to change the sorting algorithm in the previous example without affecting the rest of the solution.
