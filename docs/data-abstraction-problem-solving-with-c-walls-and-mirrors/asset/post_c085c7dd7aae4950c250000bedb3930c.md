The details of the operations, of course, vary from application to application; the overall theme is the management of data. Realize, however, not every problem uses or requires all of these operations.

Most of this is about abstract ADTs. To enable you to think absolutely about data, you should define an **abstract data type**, or **ADT**. An ADT is a collection of data and a set of operations on the data. You can use an ADT's operations, if you know their specifications, without knowing how the operations are implemented or how the data is stored.

Ultimately—perhaps you will implement the ADT by using a **data structure**, which is a construct that you define using a programming language to store the data. For example, you might store the data in a C++ array of strings or in an array of objects or in an array of arrays.

For instance, you might need a collection of items in a manner that allows you to search rapidly for a given name. A collection of *name items providing rapid searches* is the description of a simple ADT. The description of an ADT's operations must be rigorous enough to completely complete their effect on the data, for the operations should not specify how to store the data in consecutive memory locations or in disjoint memory locations. You choose a data structure when you **implement an ADT**.

When a program performs operations that are not directly supported by the language, you should first design an ADT and carefully specify what the ADT operations are to do (the contract)—then implement the operations with a data structure. If you implement the operations properly, the rest of the program will be able to assume the operations as specified—that is, the terms of the contract are honored. The program must not depend on a particular technique for supporting the operations.

> Note: ADTs vs. data structures
> * An abstract data type is a specification for a group of values and the operations on those values.
> * A data structure is an implementation of an ADT within a programming language.
>
> Carefully specify an ADT's operations before you implement them.

When you get a better idea of the conceptual difference between an ADT and a data structure, consider a refrigerator dispenser, which has water and produces as output either chilled water or ice cubes, according to which buttons you push.

Figure 1-4 A dispenser of chilled water, or ice cubes. (img/d0cb862f182db5699ad7c43510e_38.png)

It also has an indicator when ice is available. The water is analogous to data; the operations are chill, cube, and isNotEmpty(or). At this level of design, the dispenser is analogous to an ADT; you are not concerned with how the dispenser performs its operations, only that it performs them. If you want chilled water, do you care how the dispenser accomplishes its task, as long as it does correctly? Thus, after you have specified the dispenser's operations, you can design many uses for it without knowing how the dispenser accomplishes its task and without the distraction of engineering details.

Eventually, someone must build the dispenser. How will it produce ice, for example? It could first smash them into small pieces. Many other techniques are possible. The internal structure of the dispenser corresponds to the implementation of the ADT in a programming language, that is, a data structure.

Although the owner of the dispenser does not care about its inner workings, he or she wants a design that is efficient in operation. Similarly, the manufacturer wants a design that is cheap and inexpensive to build. You should have these same concerns when choosing a data structure to implement an ADT. Even if you do not implement the ADT yourself, but instead use an already implemented one—like the person who buys a refrigerator—you care about the ADT's efficiency.

Notice the walls surround the input (machine) and its output (chilled water or ice cubes). Thus, the interior mechanisms are hidden from the user, but also accessible. In addition, the mechanism of one operation is hidden and accessible to another. This modular design has benefits. For example, you can improve an operation by modifying its implementation without affecting the others. Thus, abstraction and information hiding are at work here.

To summarize, data abstraction results in a wall between ADT operations and the program that accesses the data structures, as Figure 1-5 illustrates. A program should not depend on the details of the ADT's implementation.

On the side of the wall, you will see an interface that enables you to communicate with the data structure. That is, you use the ADT operations to manipulate the data in the data structure and pass the results of these manipulations back to you.

Using ADT is like using a vending machine. This process is analogous to using a vending machine: you press buttons to communicate with the machine and obtain something in return. As the ADT's specifications dictate what its operations are and what they do, as long as you use the vending machine according to its design, you can ignore its inner technology. As long as you access data only by ADT operations, your program will be oblivious to any change in the data structures that implement the ADT.

## 1.4.1 Designing an ADT

The design of an abstract data type should evolve naturally during the problem-solving process. As an example of how this might occur, suppose that you want to determine the dates of all holidays in a year. One way to do this is to examine a calendar. That is, you could consider each day in the year and ascertain whether day is a holiday. The following pseudocode is a possible solution:

```
// Displays the dates of all holidays in a given year.
listHolidays(year)
  date = first day of year
  while (date is before the first day of year + 1)
  {
    if (date is a holiday)
      write(date, "is a holiday")
    date = date of next day
  }
```

What is involved here? Clearly, this problem operates on dates, where a date consists of a month, day, and year. What operations will you need to solve the holiday problem? Your ADT specify and restrict the legal operations on the dates, as the fundamental data type int restricts to operations as addition and comparison. // Returns the date of the first day of a given year.

// Returns true if this date is before the given date; otherwise returns false.
