
For now, the items in the bag will be objects of the same class. To accommodate entries of any single class, the bag methods use a generic type ItemType for each entry. For give meaning to the identifier ItemType, we must write template<class ItemType> on the line before the class header. The actual type is chosen by a client, the compiler will use that data type wherever ItemType appears.

The class BagInterface is a C++ abstract class. An abstract base class, or simply an abstract class, in C++ contains at least one method that is defined as virtual and has no implementation. An abstract class cannot be instantiated; it can only be used as a base class. The subclass must implement the methods specified but not defined in the abstract class.

The specifications of these operations are the sole terms of the contract for the ADT. If you request that these operations are performed, this is what will happen. The specifications contain no mention of how to store the bag or how to perform the operations; they tell you only what to do with the bag. It is of fundamental importance that the specification of an ADT does not limit implementation issues. This restriction on the specification of an ADT allows you to build a wall between an implementation of an ADT and the program that uses it—that is, it, the client. The behavior of the operations is the only thing on which a program should depend.

> Note: Although writing an interface is certainly not required, doing enables you to document your specifications in a concise way. Then you can use the code in the interface as an outline for the actual class. Having an interface also provides a data type for an ADT that is independent of a particular class definition. Chapters 3 and 4 will develop different implementations of a class of bags. Code written with respect to an interface allows you to more easily replace one implementation of a bag with another.

# 1.5.4 Using the ADT Bag

Imagine we have a programmer to implement the ADT bag in C++, given the interface and specifications that we have developed so far. If we assume that these specifications are enough for the programmer to complete the implementation, we can use the bag's operations in a program without knowing the details of the implementation. We do not need to know how the programmer implemented the bag to be able to use it. We need to know only what the ADT bag does.

The following example demonstrates how we can use a bag and assumes that we are using a C++ class bag, that implements the C++ abstract class BagInterface given in Listing 1.

Example. Suppose you invite three friends to your home to watch your favorite soccer team on election. To make the breaks more interesting, you make up the following game. From a deck of cards, you remove the entire suit of clubs: Ace, Two, Three... Jack, Queen, and King of clubs. You randomly select six of these cards and place them into a bag. Your friends guess which cards are in the bag. Each time they correctly guess a card, it is removed from the bag.

When the bag is empty, the friend with the most cards wins. Listing 1-2 shows a simple program that plays this game.

# LISTING 1-2 A program for card game

```cpp
#include <iostream>
#include <string>
#include "Bag.h" // For Bag
using namespace std;

int main() {
    string clubs[] = {"Ace", "Two", "Three", "Four", "Five", "Six", "Seven", "Eight", "Nine", "Ten", "Jack", "Queen", "King", "Joker"};
    Bag<string> grabBag; // Create our bag

    // Place six cards in it.
    for (int i = 0; i < 6; i++) {
        grabBag.add(clubs[i]);
    }

    int guess = 0;
    // Get friend's guess and check it.
    while (!grabBag.isEmpty()) {
        cout << "What is your guess?";
        cin >> guess;

        // Is card in the bag?
        if (grabBag.contains(guess)) {
            // Good guess - remove card from the bag.
            cout << "You get the card!" << endl;
            grabBag.remove(guess);
        } else {
            cout << "Sorry, card not in the bag." << endl;
        }
    }

    cout << "No more cards in the bag. Game over!" << endl;
    return 0;
}
```

# SUMMARY

1. Object-oriented analysis (OOA) is used during the initial stage of problem solving to understand what the problem is and what are the requirements of a solution.
2. During object-oriented design (OOD), you describe a solution to a problem whose requirements are discovered during OOA. You express the solution in terms of software objects.
3. Encapsulation is a principle of object-oriented programming where you hide the inner details of functions and objects. Functions encapsulate behavior, and objects—that is, instances of a class—encapsulate data as well as behavior.
4. Inheritance is another concept related to object-oriented programming, allowing you to reuse already defined classes by extending their definitions or making slight modifications.
5. Polymorphism is the third principle of object-oriented programming, whereby objects determine appropriate operations at execution time.
6. Each module should be highly cohesive; that is, it should perform one well-defined task.
7. Coupling is a measure of the dependence among modules. Module should be loosely coupled.
8. UML is a modeling language used to express object-oriented designs. It provides a notation to specify the data and uses diagrams to show relationships among classes.
9. An operation contract documents how a module can be used and what limitations it has.
10. A function or method should always include an initial comment that states its purpose, its precondition—that is, the conditions that must exist at the beginning of a module—and its postcondition—the conditions at the end of a module's execution.
11. For problems that primarily involve data management, encapsulate operations on data by designing classes. Practice abstraction—that is, focus on what a module does instead of how it does it.
12. Data abstraction is a technique for controlling the interaction between a program and its data structures. It builds walls around a program's data structures, just as other aspects of modularity build walls around a program's algorithms. Such walls make programs easier to design, implement, read, and modify.
