# CHAPTER 3 Array-Based Implementations

# 3.1 The Approach

An ADT is a collection of data and a set of operations on that data

We have said that a collection of data, together with a set of operations on that, are called an abstract data type, or ADT. For example, suppose that you want to store a collection of names that you can search rapidly. The collection of names, together with operations that add a name, remove a name, and search for a name, can form an ADT that solves this problem.

Specifications indicate what ADTs do, not how to implement them

Previously, we emphasized the specification of an abstract data type. When you design an ADT, you concentrate on what its operations do, not how well you will implement them. That is, the description of the ADT's operations must be rigorous enough to completely specify their effect on the data, and you must not specify how to store the data or how to carry out the operations. For example, the operations of an ADT should not specify whether to store the data in memory locations or in disjoint memory locations. The result should be a set of clearly specified operations.

How do we implement an ADT when operations are clearly specified? If, how do we store the ADT's data and carry out its operations? By choosing particular data structures to store the data. A data structure is a construct that you define within a programming language to store a collection of data. For example, C++ arrays are data structures.

Your first reaction to the implementation question might be to choose a data structure and to write functions that act in accordance with the ADT's operations. Although this point of view is not incorrect, hopefully you have learned not to jump right into code. You should refine an ADT through successive levels of abstraction yielding successively concrete descriptions of the ADT.

The choices you make during the implementation process can affect the execution time of your code. For now, our analyses will be intuitive, but Chapter 10 will introduce you to quantitative techniques that you can use to weigh the trade-offs.

Recall that the client—that is, the program that uses the ADT—should see only a wall of available operations that act on the data, as Figure 1-5 in Chapter 1 illustrates. The data structure are hidden behind the wall. By now, you should realize the advantage of this wall and take steps to prevent a client's direct access—either intentional or accidental—to the data structure, as shown in Figure 3-1. Why is such access inaccessible? Public data allows the client to go around the wall of abstraction and access the ADT's data. For example, suppose that you use an array items to store an ADT's data. In a program that uses the ADT, you might, for example, accidentally access the first element in the array by writing

```
firstItem = items[0];
```

instead of invoking an ADT. If you changed the implementation of the ADT, your program would be incorrect. To correct your program, you would need to locate and correct all occurrences of items—but first you would have to realize that items[0] is in error! Moreover, by violating the wall, a client could damage the ADT's data. If the data were ordered in a certain way, for example, the ADT's operations would ensure that the order was maintained, but if a client could alter the data directly, that order could be destroyed.

> Implementing an ADT as a C++ class provides a way for you to enforce the wall of an ADT, thereby preventing access to the data structure in any other way than using the ADT's operations. A client then cannot damage the ADT's data. Moreover, the client is independent of the details of the ADT's implementation, because it adheres only to the ADT's specifications.
