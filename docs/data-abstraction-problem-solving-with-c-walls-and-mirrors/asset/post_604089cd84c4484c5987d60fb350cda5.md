## 21.3 Indexing an External File

Two of the external dictionary implementations are variations of the internal hashing and search trees. The biggest difference between the internal and external versions of these implementations is that in the external versions, it is often advantageous to organize an index to the data file rather than organize the data file itself. An index to data is conceptually similar to indexes with you are familiar. For example, consider a library catalog. Rather than looking over the library for a particular title, you can simply search the catalog. The catalog is typically organized alphabetically by title (or by author), so it is a-simple matter to locate the appropriate entry. The entry for each book contains an indication (for example, a Library of Congress number) of where you can find the book.

Using a catalog to index books in a library has at least three benefits:

**Advantages of a library catalog**

- Because each catalog entry is much smaller than the book it represents, a patron can locate a particular book quickly.
- The library organizes the books on the shelves in any way, without regard to how easy it will be for a patron to scan the shelves for a particular book. To locate a particular, the patron searches the catalog for the appropriate entry.
- The library can have different types of catalogs to facilitate different types of searches. For example, it can have one catalog organized by title and another organized by author.

Now consider how you can use an index to a data file to get the same advantage as the library catalog. As Figure 21-6 illustrates, you leave the data file in a disorganized state and maintain an organized index to it. When you need to locate a particular record in the data file, search the index for the corresponding entry, which will tell you where to find the desired record in the data file.

An index to the data file is simply another file, which called the **indexed file**, that contains an **index record** for each record in the data file, just as a library catalog contains an entry for each book in the library. An index record has two parts: a key, which contains the same value as the search key and a "pointer", which shows the number of the block in the data file that contains this record. Despite its name, an index record's pointer contains an integer, not a C++ pointer. You can then determine which block of the data file contains the record whose search key equals search for the index file whose record equals searchkey.

Maintaining an index for data file has benefits advantages to those provided by the library's catalog.

**Advantages of an index file**

- In general, an index record will be much smaller than a data record. The data record may contain many components, an index record contains only two: a key and a single integer, which is the block number. Thus, just as a library occupies only a small fraction of the space occupied by the books it indexes, an index file is only a fraction of the size of the data file. As you will see, the small size of the index often allows you to manipulate it with fewer blocks than you would need to manipulate the data file.
- Because you do not need to maintain the data file in any particular order, you can insert new records in any convenient location, such as at the end of the file. As you will see, this flexibility eliminates the need to shift the records during insertions and removals.
- You can maintain several indexes simultaneously. Just as a library can have one catalog organized by title and another by author, you can have one index that indexes the data file by search key (for example, an index that consists of <name, pointer>), and a second index file that indexes the data file by another search key (for example, an index file that consists of <sec, pointer>). **Multiple indexing** is discussed briefly at the end of this chapter.

Because the index records are far smaller than the data records, the index file can contain fewer blocks than the data file. For example, if the index records are one-tenth the size of the data records and the data file contains 1000, the index file will require only 100 blocks. As a result, the use of an index cuts the block count in getItem down from log1,1000 ≈ 10 to about 1 + log1,100 ≈ 8. The one additional block is access to the data file once you have located the appropriate record.

The reduction in blocks is far more dramatic for the add and remove operations. In the implementation, if you insert a record or remove a record from the first block of the data file, you have to shift records in every block, requiring you to shift all 1000 blocks of the data file (See Figure 21-5).

However, when you perform an insertion or removal using the index scheme, you only shift index records. When you use an index, you do not keep the data file in any particular order, so you can simply insert a new record into any convenient location. This flexibility means that you can easily insert a new record at the end of the file or at a position vacant by a previous removal. However, you do need to shift records in the index file to create an opening for a corresponding entry. Because the index file contains fewer blocks than the data file (100 versus 1000 in the previous example), the maximum number of accesses required is greatly reduced. A secondary benefit of shifting index records rather than data records is a reduction in the time required for a single shift. Because the index records are smaller, the time required for the statement buf.set(i+1, buf.get(i)) is decreased.

Removals under the index scheme reap similar benefits. If you have searched the index and located the data to be removed, you can simply leave its location in the data file, and you do not need to shift any data records. You can keep track of the vacancies in the data file, so you can insert new records into the vacancies, as needed. The only shifting is required in the index file to fill the gap created when you remove the record that corresponds to the data file.

Even this scheme is an improvement over maintaining a sorted data file, in many applications it is far from satisfactory. The 100 blocks that would be required to insert or remove an index record would be prohibitive. Far better implementations are possible when you use either hashing or search to organize the index file.
