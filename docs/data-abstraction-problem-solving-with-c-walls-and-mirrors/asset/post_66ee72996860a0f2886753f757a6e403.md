
# 10.2 Measuring the Efficiency of Algorithms

Well-designed algorithms reduce the human costs of implementing the algorithm with a program, of maintaining the program, and of modifying the program. Developing good problem-solving skills and programming style has been and continues to be important. However, efficiency of algorithms is also important. Efficiency is a criterion that you should consider when selecting an algorithm and its implementation.

The comparison of algorithms is a topic central to computer science. Measuring an algorithm's efficiency is important because your choice of algorithm for a given application has a great impact. Responsive word processors, grocery checkout systems, automatic teller machines, video games, and life support systems all depend on efficient algorithms.

The analysis of algorithms is the area of computer science that provides tools for controlling the efficiency of algorithms. Note the use of the term "algorithm" rather than "program," it is important to emphasize that analysis concerns itself primarily with significant differences in efficiency—differences that you can obtain only through superior algorithms and rarely through clever tricks. Reductions in cost due to clever tricks are often more offset by reduced program readability, which increases human costs. An analysis should focus on gross differences in the efficiency of algorithms that are likely to dominate the overall cost of a solution. To otherwise select an algorithm that runs a small fraction of a second faster than another yet requires many hours of your time to implement and maintain.

The efficient use of time and memory is important. Computer scientists use similar techniques to analyze an algorithm with time and space. None of the algorithms covered in this text have significant space requirements, our focus is primarily on efficiency.

How do you compare the efficiency of two algorithms that solve the same problem? One possible approach is to implement the two algorithms and run the programs. This approach has at least three fundamental problems:

- How the algorithms were chosen? If $A_1$ runs faster than $A_2$, it could be the result of better programming. Though, if you compare the running times of the programs, you are comparing implementations of the algorithms rather than the algorithms themselves. You should not compare implementations, because they are sensitive to factors such as programming style that tends to cloud the image of which algorithm is inherently more efficient.

- What should you use? The operations that algorithms run can cause $A_1$ to run faster on one computer, while the opposite is true on another computer. You should compare the efficiency of algorithms independently of a particular computer.

- What data do programs use? Perhaps the most important difficulty in this is the selection of the data for the programs to use. There is always the danger that you could select instances of the problem where one algorithm runs characteristically. For example, when comparing a sequential search and binary search of a sorted array, you might search for an item that happens to be the smallest item in an array. In such a case, the sequential search finds the item more quickly than the binary search because the item is first in the array and thus the first item that the search examines. Any analysis of efficiency must be independent of specific data.

To overcome these difficulties, computer scientists employ mathematical techniques that analyze algorithms independently of specific implementations, computers, or data. Or doing this analysis by counting the number of significant operations in a particular solution, as the next section describes.

## 10.2.1 The Execution Time of Algorithms

Previous chapters have informally compared different solutions to a problem by looking at the number of operations that each solution required. For example, Chapter 4 compared array-based and link-based implementations of the ADT bag. An array-based bag can access its $i^{th}$ element directly in one step, because the element is stored in $[i-1]$. A link-based bag, however, must traverse a chain of linked nodes until the $i^{th}$ node is reached and therefore require $i$ steps.

An algorithm's efficiency is related to the number of operations it requires. It is usually expressed in terms of the number, $n$, of items the algorithm must process. Counting an algorithm's operations—if possible—is a way to assess its efficiency. Let us consider a few examples:

**Traversal of linked nodes.** As an example of traversing a chain of linked nodes, displaying the data in such a chain. If headPtr points to the first node in the chain, the following C++ code displays:

```cpp
Node<ItemType>* curPtr = headPtr;
while (curPtr != nullptr) {
    cout << curPtr->getItem() << endl;
    n++;
    comparisons++;
    curPtr = curPtr->getNext();
}
```

Displaying the data in a linked chain of $n$ nodes requires proportional to $n$

If we have $n$ nodes, these statements require $n+1$ comparisons, and $n$ write operations. If each assignment, comparison, and write operation, respectively, $a$, $c$, and $w$ time units, the time $(n+1) \times (a+c) + n \times w$ time units. Thus, the time to write $n$ nodes is proportional to $n$. This conclusion makes sense intuitively: It takes longer to display, or traverse, a chain of 100 nodes than it does a chain of 10 nodes.

> Note: You must traverse a linked chain to access its $i^{th}$ node. The access time is, directly proportional to $i$. On the other hand, you can access items directly, with equal access time for each item.

**The Towers of Hanoi.** Chapter 2 proved recursively the solution to the Towers of Hanoi with $n$ disks requires $2^n-1$ moves. If each move requires the same time $m$, the number of moves grows exponentially. You will soon see, this time requirement increases rapidly as the number of disks increases.

Nested loops. Consider an algorithm that contains nested loops of the following form:

```cpp
for (i = 1; i <= n; i++) {
    for (j = 1; j <= i; j++) {
        for (k = 1; k <= 5; k++) {
            task;
        }
    }
}
```

$$\sum_{i=1}^{n} (5 \times t \times i) = 5 \times t \times (1 + 2 + \cdots + n) = 5 \times t \times n \times (n + 1)/2$$

## 10.2 Algorithm Growth Rates

As you can see, the previous examples derive an algorithm's time requirement as a function of the problem size. To measure a problem's size depends on the application—typical examples are the number of nodes in a linked chain, the number of disks in the Towers of Hanoi, the size of array, or the number of items in a stack. Thus reached conclusions such as

Measure the algorithm's time requirement as a function of the problem size

+   - Algorithm A time proportional to n²
- Algorithm B time proportional to n

The time units in the previous two statements must be the same before you compare the efficiency of the two algorithms. If we had written

Algorithm A requires n² / 5 seconds to solve a problem of size n

our earlier discussion indicates the difficulties with such a statement: On what computer does the algorithm require n² / 5 seconds? What caused the algorithm to require n² / 5 seconds?

What specifically do you want to know about the time requirement of an algorithm? The most important thing to learn is how quickly the algorithm's time grows as a function of the problem size. Statements such as

+   - Algorithm A time proportional to n²
- Algorithm B time proportional to n

each an algorithm's proportional time requirement, or growth rate, and enable you to compare algorithm A with another algorithm B. Although from these statements you can determine the exact time requirement for either algorithm A or B for large problems, B requires significantly less time than A. That is, B's time requirement—as a function of the problem size n—increases at a slower rate than A's time requirement, because n increases at a slower rate. Even if B actually requires 5 × n seconds and A actually n² / 5 seconds, B usually requires significantly less than A, as n increases. Figure 10-1 illustrates this.
