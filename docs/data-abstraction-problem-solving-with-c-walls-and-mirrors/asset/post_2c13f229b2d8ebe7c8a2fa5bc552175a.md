## B.2.2 Proper Use of Reference Arguments

A method, in a controlled fashion, with the rest of the program when you do not write '&' after the program's data type, pass parameters, which are the default in C++ when you copy values into the method. The value of each argument corresponding to a value parameter is copied into the parameter, which is local to the method. Any change that the method makes to these parameters is not reflected in the actual arguments in the calling program. This communication between the calling program and the method is one-way and supports the notion of an isolated module. Thus, you should use value arguments when possible. However, passing large objects by value is not very efficient because of the copying.

How and when is it appropriate to use reference parameters? Since a reference parameter alias (another name for the corresponding argument), changes to the parameter within the method also occur in the calling module. The obvious situation requiring references is when you use a parameter to pass a value out of a method; the parameter must be a reference parameter.

Suppose that you are using a method that requires a large object x, whose value should not be altered. You consider passing by value; however, to increase the efficiency of your program, you would like to avoid the computer- and storage requirements of making a copy of x. So about passing x by reference? The problem with passing x by reference is that it conveys information about the method's relation to the rest of the program. Since a reference parameter is used to communicate with the method back to its calling module, the program is more difficult to read if the parameter's value remains unchanged. The program also is prone to errors if modifications are required. The solution is to proceed the method's declaration with `const`, thus we have the efficiency of pass-by-reference (no copy made) with the protection of pass-by-value (the argument is input only). This is called pass-by-constant-reference. If objects are large and complex, use pass-by-reference; otherwise pass-by-value works fine.

## B.2.3 Proper Use of Methods

To reduce coupling among modules, you should restrict the calls that a method can make. A method should only call other methods:

- Defined within the same class
- Of argument objects
- Of objects created within the method
- Of objects contained within the same class as data members

For example, we have the following code for three classes that are building, an appliance, and a lamp, respectively:

```cpp
// Original Solution
class Building
{
  private:
    Appliance appliance;

  public:
    void turnOnChange()
    {
      appliance.getLamp().turnOn(); // Improper method use
    } // end turnOnChange
}; // end Building
```

```cpp
class Appliance
{
private:
    Lamp light;
public:
    Lamp getLamp()
    {
        return light;
    } // end getLamp
}; // end Appliance
```

```cpp
class Lamp
public:
    void turnOn();
}; // end Lamp
```

Here, Building's method `turnOn` fails to follow these rules. It calls the method `turnOn` from the Lamp class, although a Lamp object is not part of the Building class and has not been passed to the `turnOn` method as an argument. This code has coupled the Building class to the Lamp class. A much better design would decouple the Building and Lamp classes, as:

```cpp
// Revised Solution
class Building
private:
    Appliance appliance;
public:
    void turnOnLight()
    {
        appliance.turnOnLamp();
    } // end turnOnLight
}; // end Building
```

```cpp
class Appliance // Improved Appliance class
private:
    Lamp light;
public:
    void turnOnLamp()
    {
        light.turnOn();
    } // end turnOnLamp
}; // end Appliance
```

```cpp
class Lamp
public:
    void turnOn();
}; // end Lamp
```

Now the building asks the appliance to turn on, and the appliance turns on its lights.
Suppose that the Lamp's switch is replaced with a dimmer-type switch. We would need to give the `turnOn` method in the Lamp class an indication of how to dim the light. Finding the call to `turnOn` in the original code segment might be difficult, because the Building class does not have explicit access to a Lamp object. You could search the Building class for instances of Lamp, and not find any. This type of dependency makes a solution more difficult to modify.

## B.2.4 Avoidance of Global Variables in Modules

One of the many advantages of the concepts of encapsulation and information hiding is the creation of isolated modules. This isolation is sacrificed when a module accesses a global variable, because the effects of a module are no longer self-contained or limited to output arguments. That is, a module has a side effect. Hence, the isolation of errors and limitations is greatly compromised when global variables appear in modules.

Do not use global variables

## B.2.5 Error Handling

A program should check for errors in both its input and its logic and attempt to behave gracefully and consistently when it encounters them. A method should check for certain types of errors, such as invalid argument or null values. What should a method take when it encounters an error? Depending on context, the appropriate action in the face of an error ranges from ignoring the error and continuing to terminate the program. A common technique is for method to return a boolean value to the calling method to indicate that it has encountered an error. Thus, the method leaves error handling to the calling method. In general, methods should either return a value or throw an exception instead of displaying a message when an error occurs.

In case of an error, methods should return a value or throw an exception, but not display a message
