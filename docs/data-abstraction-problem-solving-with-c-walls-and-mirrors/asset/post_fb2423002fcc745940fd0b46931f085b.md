## 1.3 Specifications

When you design a modular solution to a problem, each module simply states what it does but not how it does it. No module may “know” how any other module performs its task—it may know only what that task is. For example, if one part of a solution is to sort some data, one of the modules may be a sorting algorithm, as Figure 1-1 illustrates. The other modules that know the module sorts, but do not know how it sorts. In this way, the components of a solution are kept isolated from one another.

Using this, we can write the modules in relation to one another, knowing what each will do but not necessarily how each will eventually do it. It is essential that a module's specifications be written and understood.

> before implementing

### 1.3.1 Operation Contracts

An operation contract describes how a method can be used and what limitations it has. You should begin this contract during analysis, finish the specification during design, and then document the contract in query, particularly within the header files. In this way, programmers who use your code can indicate what they need from the method to generate correct results.

There is certain information you need to provide for each method. An interface specifies how to call the method and the number, and types of arguments it expects—already discussed. You may need to specify what should be true before the method is called and what will be true after the method finishes execution.

> A module contract specifies
> the module's purpose,
> assumptions, input,
> output

During design, it is important that you clearly specify not only the purpose of each module, but also the data flow among modules. For example, you should provide answers to these questions for each module: What data is available to the module before its execution? What does the module assume? What actions have taken place, and what does the data look like, after the module executes? Thus, you should specify in detail the assumptions, input, and output for each module.

> Specify the data flow
 among
> modules

For example, if you program designer needed to sort an array of integers, you might write the following specifications for a sort function:

- The function will receive an array of num integers, where num > 0.
- The function will return the array with its integers sorted.

## Specifications

You can view these specifications as the terms of a contract between your function and the module calls it.

> Specifications are
> them of a
> contract

This contract helps programmers understand what responsibilities the module will have to other modules in the module. Whoever the sort function must live up to this contract. After the sort function has been written and tested, the contract tells the rest of the program how to call the sort function properly, as well as the result of doing so.

> An operation contract should not
> describe how a
> module will perform its task

Notice that a module's contract does not commit the module to a particular way of performing its task. If another part of the program assumes anything about the algorithm, it is to its own risk. Thus, for example, if at some later date you rewrite your function to a different sorting algorithm, you do not need to change the contract of the algorithm. As long as the new function honors the terms of the original contract, the rest of the program should be oblivious to the change.

> Operation contracts should include
> precise
> preconditions and
> postconditions

This should not be news to you. Although you might not explicitly used the term contract, the concept should be familiar. You write a contract when you write a function's precondition, which is a statement of the conditions that must exist at the beginning of a function, as well as when you write its postcondition, which is a statement of the conditions at the end of a function. For example, the sort function that adheres to the previous contract could appear in pseudocode as:

```
// Sort an ascending order.
// Precondition: array is an array of integers; num > 0.
// Postcondition: the integers in array are sorted.
sort(array, num)
```

> First-draft specifications

These pair- and postconditions are abstract, as can be the case in a first-draft contract. For example, does sorted means ascending or descending order? How large can we be? While implementing this function, you might assume that sort means ascending and that num will not exceed 100. The difficulties that can arise when another person tries to sort an array of 500 integers the user will not know your assumptions unless you documented them by revising the contract as follows:

> Revised specifications

```
// Sort into ascending order.
// Precondition: array is an array of integers and j <= num <= MAX_ARRAY,
// WHERE MAX_ARRAY is a global constant that specifies the maximum size of array.
// Postcondition: anArray[0]<= anArray[1]... <= anArray[num - 1].
// num is unchanged.
sort(array, num)
```

When you write a procedure, begin by describing the behavior of your function's inputs, mention any global constants that it uses, and finally list all annotations that it makes. Note that in the case of you write a postcondition, describe what the module has. Note that if a module returns a value—which is a critical part of the postcondition—the value must be described.

> Precise documentation is
> essential

Novice programmers tend to diminish the importance of documentation, particularly when they are less experienced designer, programmer, and user of program. If the size of the program increases, documentation becomes more important, regardless of whether you are sole author or part of a team. If you do not write the terms of the contract, will you remember them when you later implement it?

## 1.3.2 Unusual Conditions

As a class designer need to make decisions about how to treat unusual conditions and include these decisions in your specifications. In general, you can address unusual situations in several ways. You can

- Assume that the invalid will not occur. This assumption is not as naive as it might sound. A method could state as an assumption—that is, a precondition—restrictions to what a client must adhere. It is then up to the client to check that the precondition is satisfied before invoking the method. As long as the client obeys the restriction, the invalid situation will not occur.
- Ignore the invalid situations. A method could simply do nothing when given data. Doing absolutely nothing leaves the client without knowledge of what happened.
- Guess at the client's intention. Like the previous option, this choice can cause problems for the client.
- Return a value that signals a problem. For example, a method can return a value that indicates success or failure.
- Throw an exception. Throwing an exception is desirable for a C++ method to react to unusual events. The method can report problem without deciding what to do about it. The exception enables each client to act as needed in its particular situation. For simplicity right now, we will adopt the policy that methods should throw exceptions only in truly unusual circumstances, when no reasonable solution exists. You can learn about exceptions in C++ Interlude 3.

> A first draft of a module's specifications often overlooks or ignores situations that you really need to consider. You might intentionally make omissions to simplify this draft. Once you have written the major portions of the specifications, you can concentrate on the details that make the specifications complete.

## 1.3.3 Abstraction

Abstraction separates the purpose of a module from its implementation. Modularity breaks a solution into modules; abstraction specifies each module clearly before you implement it in a programming language. For example, what does the module assume, and what action does it take? What is this module responsible for when called? Such clarifications help you focus on high-level functionality without the distraction of implementation details. In addition, they help you modify one part of a solution without significantly affecting the other parts. For example, you should be able to change the sorting algorithm in the previous example without affecting the rest of the solution.
