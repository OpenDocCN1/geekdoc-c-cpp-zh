There is no way to guarantee that a hash function will scatter all data evenly, you can greatly increase the likelihood of this behavior.

As an example, consider a table[0..39] and a hash function h(x) = two digits of x. If every ID number is equally likely, h will scatter the search keys ever throughout. But what if every ID number is not equally likely? For instance, a company might assign employee IDs to department, as follows:

| ID | Department |
|---|---|
| 10xxxx | Sales |
| 20xxxx | Customer Relations |

Under this assignment, only 9 out of the 100 array locations would contain any items at all. Further, those locations corresponding to the largest departments (Sales, for example, corresponds to table[10]) would contain more items than those locations corresponding to the smallest departments. This scheme does not scatter the data evenly.

Much research has been done into the types of hash functions you should use to guard against various patterns in the data. The results of this research are relevant in providing advanced courses, but two general principles can be noted here:

- The calculation of the hash function should involve the entire search key. For example, computing a modulo of the entire ID number is much safer than using only its first digits.
- If a hash function uses arithmetic, the base should be prime; that is, if h is of the form

```
h(x) = x mod tableSize
```

then tableSize should be a prime number. This selection can safeguard against many subtle patterns in the data (for example, search keys are likely to be multiples of one another). Although each application can have its own kind of patterns and should be analyzed on an individual basis, choosing a prime number for tableSize is an easy way to safeguard against some types of patterns in the data.

## 18.4 Dictionary Traversal: An Inefficient Operation Under Hashing

For many applications, hashing provides the most efficient implementation of the ADT dictionary. One important dictionary operation—traversal in sorted order—performs poorly when hashing implements the dictionary. As mentioned previously, a good hash function scatters items as randomly as possible throughout the array, so that no ordering exists between a search key that hashes into table[i] and one that hashes into table[i+1]. As a consequence, if you must traverse the dictionary in sorted order, you have to sort the items. If ordering were required, hashing would be a far less efficient implementation than a search tree.

Traversing in sorted order is just one example of a whole class of operations that hashing does not support well. Many similar operations that you often wish to perform on a dictionary require that the items be ordered. For example, consider an operation that finds the dictionary item whose search key is the smallest or largest. If you use a search-tree implementation, these are in the leftmost and rightmost nodes of the tree. If you use a hashing implementation, you do not know where these items are—you would have to search the entire dictionary. A similar type of operation is a range query, which requires you to retrieve all items whose keys fall in a range of values. For example, you might want to retrieve all items whose search keys are in the range 129 to 755. This task is relatively easy to perform by using a search tree (see Exercise 3 in the next chapter), but by using hashing, there is no efficient way to answer the query.

In general, if application requires these ordered operations, you probably use a search tree. The getItem, add, and remove operations are somewhat more efficient when you use hashing the dictionary implementation of a balanced search tree, the search tree supports these operations so effectively that, in most cases, the difference in speed for these operations is negligible (whereas the advantage of the search tree over hashing is significant).

In the context of external storage, the story is different. For data that is external, the difference in speed between hashing's implementation of getItem and a search tree implementation may be significant, as you will see in Chapter 21. In an external setting, it is not uncommon to use a hashing implementation of the getItem operation and a search-tree implementation of the ordered operations used simultaneously.
