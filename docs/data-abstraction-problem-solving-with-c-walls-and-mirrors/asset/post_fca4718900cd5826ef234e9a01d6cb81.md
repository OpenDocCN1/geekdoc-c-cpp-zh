## 15.3.3 Creating a Binary Search Tree

Suppose that you want to insert a record for Frank in the binary search tree of Figure 15-13. As a first step, imagine you want to search for the string “Frank”. The search algorithm searches the tree rooted at Jane, then the tree at Bob, and the tree at Elisa. It searches the tree at the right child of Elisa. Because this is empty, as Figure 15-16 illustrates, the search algorithm has reached a base case and will terminate with a report that Frank is not present. What does it mean if search looked for Frank in the right subtree of Elisa? For one thing, it means that if Frank was the right child of Elisa, search would have found Frank.

> This observation indicates a good place to insert Frank as the right child of Elisa. Because Elisa has no right child, the insertion is simple, requiring only the addition of a new leaf node. More important, Frank belongs in this location—search will look for Frank. Specifically, inserting Frank as the right child of Elisa will preserve the tree’s binary search property. Because search, when searching for Frank, would follow a path that leads to the right child of Elisa, you are assured that Frank is in the proper relation to the names above it in the tree.

Use search to determine the insertion point

> Note: Using search to determine where in the tree to insert a new name always leads to an easy insertion. No matter what item you insert into the tree, search will always terminate at an empty subtree. Thus, search always tells you to insert the item as a new leaf.

**Example.** Let's create the binary search tree shown in Figure 15-13. The following pseudocode begins with an empty binary search tree and adds entries one at a time until we get the desired tree:


Once we insert Jane into the empty tree, Jane becomes the root. Inserting Bob into the tree leaves the root untouched, and so the search tree places Bob as the left child of the root. Because Bob is less than "Jane", when we insert the next name, Alan, it becomes the left child of Bob. Note that each insertion creates a new leaf of the tree at that point in time. It might not remain a leaf in the final tree.

## 15.3.4 Traversals of a Binary Search Tree

The traversals of a binary search tree are the same as traversals of a binary tree. The inorder traversal of a binary search tree is of special note. Recall its algorithm from earlier:

```
// Traverses the given tree in inorder.
// Assumes that "visit a node" means to process the node's data.
void inorder(BinaryTree tree) {
  if (tree is not empty)
    inorder(Left subtree of tree.root);
    visit the root of tree;
    inorder(Right subtree of tree.root);
}
```

> Note: The inorder traversal of a binary tree visits the nodes in sorted-key order.

## 15.3.5 The Efficiency of Binary Search Tree Operations

You have seen binary trees in many shapes. For example, even though the binary trees in Figures 13-15 have seven nodes each, they have different shapes and heights. To locate Wendy in Figure 15-14b you would have to inspect all nodes, but you can locate Wendy in Figure 15-13 by inspecting only three nodes (Jane, Tom, and Wendy). Now consider the relationship between the height of a binary search tree and the efficiency of the insertion, retrieval, and removal.

Each of these operations performs a compared value $v$ in the nodes along a path through the tree. This path starts at the root of the tree, and at each node $n$, follows the left or right branch, depending on the comparison of $v$ to the value in $n$. The path terminates at the node that contains $v$, or at an empty subtree. Thus, each retrieval, insertion or removal requires a number of comparisons equal to the number of nodes along this path. This means that the maximum number of comparisons that each operation requires is the longest path through the tree. In other words, the maximum number of comparisons that these operations can require is equal to the height of the binary search tree.

The number of comparisons for a retrieval, insertion, or removal is the height of the tree.

> Note: The height of a binary tree: Recall that the height of an $n$-node binary tree ranges from $\log_2(n+1)$ to $n$. (Wait, usually it is $\log_2(n+1)$).

# Summary

If the height of the binary search tree is $\log(n+1)$, the efficiency of its operations is $O(\log n)$. However, what will the height of a binary search tree actually be? The factor that determines the height of a binary search tree is the order in which you perform insertion and removal operations on the tree. Recall that starting with an empty tree, if you insert names in sorted order Alan, Bob, Elisa, Nancy, Tom, Wendy, you would obtain a tree of maximum height. On the other hand, if you insert names in random order, you would expect a tree of minimum height. In many applications you can expect the binary search tree to be excellent, you should be wary of the possibility of poor performance due to some characteristics of a given application. Are you worried that operations might not occur in a random order? Similarly, is there anything if you have an enormous number of items and need to ensure that the height of the tree is close to $log n$? Chapter 19 presents variations of the binary search tree that are guaranteed to remain balanced and therefore of minimum height.
