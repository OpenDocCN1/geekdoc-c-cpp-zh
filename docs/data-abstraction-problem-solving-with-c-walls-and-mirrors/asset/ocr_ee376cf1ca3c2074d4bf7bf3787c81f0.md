Always remember that if a class uses new to create an object, some method of the class must delete the object's memory. It is a characteristic of safe and secure programming that any allocating memory from the free store also carries responsibility to deallocate memory when it is no longer needed.

Pointers give a great amount of control over how memory is used and when binding occurs, as we will discuss shortly. They can also create severe problems and hard-to-find bugs if not used properly. # ## C.3.2 Avoiding Memory Leaks

Memory leak occurs when an object has been created in the free store, but the program no longer has a way to access it. Because the object cannot be accessed, it cannot be deleted and takes up memory, even though it cannot be used. A program can run out of memory and crash if it has several memory leaks.

Consider the following statements:

```
MagicString* myBoxPtr = new MagicBox<string>();
MagicString* yourBoxPtr = new MagicBox<string>();nyourBoxPtr = myBoxPtr; // Results in inaccessible object
```

Figure 2-6 traces the execution of these statements. Eventually, yourBoxPtr points to the same object as myBoxPtr, and the object to which yourBoxPtr originally pointed is no longer accessible, resulting in the memory leak shown in part of the figure.

To prevent this, we should not create the second object. Instead, either initialize yourBoxPtr to nullPtr or set it to myBoxPtr:

```
MagicString* myBoxPtr = new MagicBox<string>();
MagicString* yourBoxPtr = myBoxPtr;
```

A subtle memory leak occurs when a function or method creates an object in the free store and loses the pointer to it by not returning that pointer to the caller or not storing it in a class data member. That is what happens in the function in Listing C2-1.
