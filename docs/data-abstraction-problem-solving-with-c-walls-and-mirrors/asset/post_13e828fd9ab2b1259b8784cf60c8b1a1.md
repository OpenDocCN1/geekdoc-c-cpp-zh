
## APPENDIX C The Unified Modeling Language

### C.4 Keeping The UML In Its Perspective

UML diagrams are not documentation

Although the UML can be thought of as a tool for documenting a solution to a problem, this is not how it should be used. Rather, you should use the UML to quickly draw various aspects of the current problem to better understand it during OOA and to create a set of objects OOD that can collaborate to solve this problem. Often small teams of programmers will draw several UML diagrams on a whiteboard, and after working out the kinks in the diagrams, take digital pictures of them for future reference. These design diagrams are considered an artifact, or document, associated with the analysis and design. However, the ultimate implementation—that is, the solution—might not exactly match the original design. Thus, design designs might not document the solution.

### The UML is a tool for exploration and communication

The UML is a useful tool for creating a design for solution. It enables programmers to explore and understand the problem domain and to develop a design that is close to the required solution. Although the UML will not necessarily make better designs than other techniques, it can model a problem in terms of software objects, independently of a programming language. Because the UML gives a visual representation of proposed systems, humans—visual creatures—can benefit from using it. After all, a picture is worth a thousand words. The UML enables the members of a programming team to communicate visually with one another, thereby gaining a common understanding of the system that is being built.

## Prerequisites

A general knowledge of software

The software life cycle describes the phases of software development

> This appendix examines what major piece of software “experiences” during its lifetime. The life cycle of software describes the phases through which software will progress from conception to replacement or deletion from a hard disk ever. We will look at the development phases, from project conception to deployment to end users. Beyond this development process, software will need maintenance to correct errors and extend it to new tasks. Eventually the software will be retired.

The development of good software is a complex affair. Over the last decades techniques have been developed to control and manage complexity. Some of these techniques have been more successful than others.

Iterative development forms a solution after many iterations; each iteration builds on the previous iteration until a complete solution is achieved.

## D.1 Iterative and Evolutionary Development

An Iterative development of a solution progresses through many stages, fixed-length iterations, each iteration cycles through the analysis, design, implementation, and integration of a small portion of the problem domain. Early iterations build the core of the system. Subsequent iterations build on that core. After many iterations, the entire solution is developed.

To manage the time spent on an iteration, each one is assigned a predetermined duration—called a timebox—at the beginning of the project. Typical timeboxes are two to four weeks in length. The portion of the system that can be developed in less than two weeks is typically small to be meaningful. In more than four weeks, the partial system becomes too large. At the end of each iteration, the partial system should be functional and completely tested. Each iteration makes relatively few changes to the partial system by the previous iteration, so it can occur quickly. Thus, you do not spend too much on something that you have misunderstood about the system requirements.

### A critique of each iteration influences the next iteration

This process creates solution incrementally. There are many places for end users and developers to check that it solves the problem. Because each iteration produces a functional but partial system, developers can engage end users for feedback. This feedback influences the next iteration and can change the direction of development so a more correct solution is reached. Figure D-1 illustrates the progress of the solution. In early iterations, the requirements are not stable. In later iterations, the requirements become stable.

### Iterative development enables you to adapt to a changing environment

Iterative, incremental development allows the team to adapt the solution to the environment as it becomes understood. Thus, the process is sometimes called evolutionary development.

> Note: Iterative and Evolutionary Development
> - Determines timeline lengths at the start of the project
> - Keeps timeline lengths short (two to four weeks)
> - Gets end-user feedback

## D.2 Rational Unified Process Development

The RUP gives structure to the development process

This section introduces the widely used Rational Unified Process (RUP) as a basis for examining the phases of development. As the RUP is a large and complex process, most of its workings are beyond the scope of this text. Thus, we will simply introduce it.

The RUP organizes development into four phases:

- Inception: feasibility study, project vision, rough estimates of time and cost
- Elaboration: refined project vision, iterative development of core system, more accurate time and cost estimates
- Construction: iterative development of remaining system
- Transition: testing and deployment

We will look at the characteristics of each phase. Figure D-2 shows how RUP development phases relate to iterations.

### D.2.1 Inception Phase

During the inception phase, we define the scope of the project and decide whether the project is feasible. If a team has already implemented solutions for similar problems, and the solution is clearly feasible, the inception phase may be very brief.

At a minimum, the inception phase must define an initial set of system requirements and choose the length of the iteration. While defining the initial requirements, we generate a core set of use scenarios and determine which elements of solution outline the greatest risk. This set of scenarios and the highest-risk aspects of the solution are the focus of the first iterations in the elaboration phase. Note that the inception phase is not an iteration. You should not try to develop all—or most—of the use cases during inception.

### D.2.2 Elaboration Phase

During the elaboration phase, the system’s core architecture is iteratively developed, high-risk elements of the system are addressed, and most of the system requirements are defined. The core architecture is composed of software components that are central to the system.

The elaboration phase extends over two or more iterations. If the elaboration phase has only one iteration, no feedback can come into play. Multiple iterations are necessary when developing the correct solution incrementally and adaptively.
