What are the specific characteristics of good solutions? How can you construct good solutions?
This appendix provides some answers to these very difficult questions. However, the novice programmer usually does not truly appreciate their importance. After the first course in programming, many students will simply want to "get the thing done." The discussion that follows should help you realize how important these themes really are.

One of the most widespread misconceptions held novice programmers is that a computer program is "read" only by a computer. As a consequence, they consider only whether the computer is able to "understand" the program—that is, the program complete, execute, and produce the correct output? The truth is, of course, that other people often read and modify programs. A typical programming environment involves reading programs written by others, and a year later, a different person may modify the program. It is essential that you take great care to design a program that is easy to read and run.

You should always keep in mind the following seven themes of programming: modularity, style, modifiability, ease of use, fail-safe programming, debugging, and testing.

## B.1 Modularity

As this book thoroughly emphasizes, you should strive for modularity in all phases of the problem-solving process, beginning with the initial design of a solution. Many programming tasks become more difficult as the size and complexity of a program grows. Modularity slows the rate at which the level of difficulty grows. More specifically, modularity has a favorable impact on the following aspects of programming:

- **Constructing the program.** The difference between a small modular program and a large modular program is simply the number of modules each contains. Because the modules are independent, writing one large module is not different from writing many small, independent programs, although the interrelationships among modules make the design much more complicated. On the other hand, working on a large modular program is much like working on many unrelated programs simultaneously. Modularity also permits team programming, where several programmers debug their own modules before combining them into one program.
- **Debugging the program.** Debugging a large program can be a monstrous task. Imagine you have a 9,000-line program and need to get it to run. Neither of these tasks would be easy. Now imagine you write your program, and after a few hundred lines of output, you encounter an incorrect number. You should anticipate spending the day or tracing to find the intricacies of your program before discovering a problem such as an index out of range.

A great advantage of modularity is that the task of debugging a large program is reduced to one of debugging small programs. When you begin to code a module, you should be almost certain that all other modules coded so far are correct. That is, before you consider a module finished, you should test it extensively, both separately and in context with the other modules, by calling with actual arguments carefully chosen to induce all possible behaviors of the modules. If this testing is done thoroughly, you can be fairly sure that any problem is a result of an error in the last module added. *Modularity isolates errors.*

## Style 723

Formal theoretical techniques are available to verify the correctness of a program. Modular programs are amenable to this verification process.

- **Reading the program.** A person reading a large program may get lost in its details. Just as a modular design helps the programmer cope with the complexities of solving a problem, so too a modular program is easy to follow—the reader can get a good idea of what is going without reading any of the code. A well-written function can be understood early on from its name, initial comments, and the names of the functions that it calls. Readers of a program need to study actual code if they require a detailed understanding of how the program operates. Program readability is discussed further in the next section on style.
- **Modifying the program.** Modularity is discussed in greater detail in Section B.3 of this appendix, as the modularity of a program has a direct bearing on its maintainability, a brief mention is appropriate here. A small change in the requirements of a program should require only a small change in the code. If this is not the case, it is likely that the program is poorly written and, it is not modular. To accommodate a small change in the requirements, a modular program usually requires a change in only a few of its modules, particularly when the modules are independent (referred to as loosely coupled) and each module performs a single well-defined task (referred to as highly cohesive). This point is of particular importance with iterative development techniques, which changes in program requirements at every iteration, as Appendix D will discuss.
- **Eliminating redundant code.** Another advantage of modular design is that you can identify a computation that occurs in different parts of the program and implement it as a function or class method. Thus, the code for the computation appears only once, resulting in an increase in both modularity and modifiability.

When making changes to a program, it is best to make a change at a time. By maintaining a modular design, you can reduce a large modification to a set of small and relatively simple modifications to isolated parts of the program. Modularity isolates modifications.

## B.2 Style

We consider the following seven issues of programming: the use of private data members, the use of reference arguments, the use of methods, avoidance of global variables in modules, error handling, readability, and documentation. Admittedly, much of the following discussion reflects the personal taste of the authors; otherwise good programming styles are possible. Most organizations that hire programmers use specific styles, so that programmers can produce code that is easily read and maintained by other teams.

## B.2.1 Use of Private Data Members

Each object has a set of methods that represents the operations that the object can perform. The object also contains data members for storing information. You should hide the exact representation of these data members by making all the data members private. Doing so follows the principle of information hiding. The details of the object's implementation are hidden from view, with methods providing the only mechanism for getting information to and from the object. When the only operations involved with a particular data member are retrieve and modify, the object should provide a simple method—called an *accessor*—that returns the value of the data member and another method—called a *mutator*—that sets the value of the data member. For example, a Person object could provide access to the data member through the `getName` to return the person's name and `setName` to change the person's name.
