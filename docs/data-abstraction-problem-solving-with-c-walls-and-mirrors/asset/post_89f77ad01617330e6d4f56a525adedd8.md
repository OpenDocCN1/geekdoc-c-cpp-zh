You must write a destructor if your class allocates memory dynamically

Each class has only one destructor. The destructor destroys an instance of the class, which is an object, when the object's lifetime ends. Typically, the destructor is invoked at the end of the block in which the object was created.

Classes that use statically allocated memory depend on the compiler-generated destructor, as was the case with ArrayBag in Chapter 3. However, when a class uses dynamically allocated memory, you need to write a destructor that deallocates this memory by using `delete`. The destructor for LinkedBag can simply call the method to delete each node in the link containing the bag's entries. The destructor's definition follows:

```cpp
template <class ItemType>
LinkedBag<ItemType>::~LinkedBag()
{
    clear();
} // end destructor
```

A destructor's name is a tilde (`~`) followed by the class name. A destructor cannot have arguments, and has no return type—even `void`—and cannot return a value.

```cpp
template <class ItemType>
LinkedBag<ItemType>::LinkedBag(const LinkedBag<ItemType>& a_bag)
{
    itemCount = a_bag.itemCount;
    Node<ItemType>* origChainPtr = a_bag.headPtr;
    if (origChainPtr == nullptr)
        headPtr = nullptr; // Original bag is empty, so we copy
    else {
        // Copy first node
        headPtr = new Node<ItemType>();
        headPtr->setItem(origChainPtr->getItem());
        // Copy remaining nodes
        Node<ItemType>* newChainPtr = headPtr;
        origChainPtr = origChainPtr->getNext();
        while (origChainPtr != nullptr) // Advance pointer
        {
            // Get next item from original chain
            ItemType nextItem = origChainPtr->getItem();
            // Create a new node containing the next item
            Node<ItemType>* newNodePtr = new Node<ItemType>(nextItem);
            // Link node to end of chain
            newChainPtr->setNext(newNodePtr);
            // Advance pointer to last node
            newChainPtr = newNodePtr;
        }
        newChainPtr->setNext(nullptr); // end of chain
    } // end if
} // end copy constructor
```

As you can see, the constructor is an expensive operation. It requires traversing the original linked chain and duplicating each node.

## 4.3 Using Recursion in Link-Based Implementations

It is possible, and sometimes desirable, to process linked chains recursively. This section examines how to write the iterative methods previously as recursive ones. Such recursive methods require the head pointer as an argument. Therefore, they should not be public because the head pointer is a private data member of the class and the client does not have access to it. Otherwise, clients could access the linked nodes directly, violating the ADT's safety.

### 4.3.1 Recursive Definitions of Methods in LinkBag

An introduction to this topic, we will review two methods in the class LinkBag to use recursion. These methods simply traverse a chain of linked without making any changes to it.

The method `toVector` has a straightforward recursive implementation. This operation requires us to traverse the linked chain of nodes as we copy data from the nodes into the vector. Traversal of a linked chain is an operation that occurs in many situations. We have established that the method performing the recursion must be private and must have the head pointer as a parameter. Since the method will copy data into the vector as it traverses the linked chain, the vector must also be a parameter. We declare this method in the private section of the class, as follows:

```cpp
// fills the vector contents with the data in the nodes of
// linked chain to which curPtr points.
void fillVector(vector<ItemType>& bagContents, Node<ItemType>* curPtr) const;
```

Given this definition, we would implement it as follows: After creating a vector, `toVector` fills it—by calling `fillVector`—with the data in the chain of nodes whose head pointer is `headPtr`. Finally, `toVector` returns the vector to the client. To define `fillVector`, we need to recurse. If the chain is empty—that is, if `curPtr` is `nullptr`—nothing is to do. In the recursive step, we add the data `curPtr->getItem()` to the vector and recursively fill the chain that begins at `curPtr->next()`. The method then has the following definition:

```cpp
template <class ItemType>
void fillVector(vector<ItemType>& bagContents, Node<ItemType>* curPtr) const
{
  if (curPtr != nullptr) {
    bagContents.push_back(curPtr->getItem());
    fillVector(bagContents, curPtr->getNext());
  } // end if
} // end fillVector


Even though `fillVector` has a reference parameter, the method is safe because it is private. A similar situation occurs in Chapter 16 and is discussed further in a Note in Section 16.3.1.

**The private method** `getPointerTo`. The method `getPointerTo` calls a given entry within the linked chain. Unlike `fillVector`’s traversal, this stops if it locates the node that contains the given entry. The iterative version of `getPointerTo` has one parameter, which is the given entry. We could define a private method to perform the recursion—as we did for traverse—with two parameters: the given entry and a head pointer. Then `getPointerTo` would call this new method. However, since `getPointerTo` is itself a private method, we can revise it to have the necessary parameters. This is the approach we take. Of course, we would have to revise the calls to the method that appears in the rest of the class.

By replacing the declaration of `getPointerTo` in the header file for class `LinkedBag` with the following:

```cpp
// Locates a given entry within this bag
// Returns either a pointer to the node containing a given entry or
// the null pointer if the entry is not in the bag.
NodeType* getPointerTo(const ItemType& target, Node* curPtr) const;
```

Before we go do so, we revise the calls to this method in the class that remove and contains items. The original calls are `getPointerTo(aEntry)`, but now each needs to be `getPointerTo(aEntry, headPtr)`.

The recursive definition of this method has two base cases. One case occurs when the chain is empty, causing the method to return `nullptr`. The other base case occurs when we locate the desired entry at `curPtr->getItem()`. In this case, the method returns `curPtr`. The recursive search continues the chain beginning at `curPtr->getNext()`. Thus, the method returns the following:

```cpp
template <class ItemType>
NodeType* getPointerTo(const ItemType& target, Node* curPtr) const
{
  NodeType* result = nullptr;
  if (target == curPtr->getItem()) {
    result = curPtr;
  } else {
    result = getPointerTo(target, curPtr->getNext());
  } // end if
  return result;
} // end getPointerTo
```
