Thus, you can define an ADT by identifying data and choosing operations that are suitable to your problem. After specifying the operations, you use them to solve your problem independently of the implementation details of the ADT.

An appointment book. As another example of an ADT design, imagine that you want to create a computerized appointment book that spans a one-year period. Suppose that you make appointments only on the hour or half hour between 8 am and 5 pm. Your system must store a brief notation about the nature of each appointment along with the date and time.

To solve this problem, you can define an ADT appointment book. The data it consists of a date, time, and purpose. What are the operations? Two obvious operations are

- Make an appointment for a certain date and time. (You will want to be careful that you do not make an appointment at an already occupied time.)
- Cancel the appointment for a certain date and time.

In addition to these operations, it is likely that you will want to

- Ask whether you have an appointment at a given time.
- Get the purpose of your appointment at a given time.

Finally, ADTs have initialization and destruction operations that we assume but do not specify at this stage.

Thus, the appointment book can have the following operations:

```
// Returns true if an appointment exists for the date and time specified.
// false otherwise.
+hasAppointment(appDate: Date, appTime: Time): boolean

// Inserts the appointment for the date, time, and purpose as long as
// it does not conflict with an existing appointment.
// Returns true if successful, false otherwise.
+makeAppointment(appDate: Date, appTime: Time, appPurpose: string): boolean

// Deletes the appointment for the date and time specified.
// Returns true if successful, false otherwise.
+cancelAppointment(appDate: Date, appTime: Time): boolean

// Gets the purpose of the appointment at the given date and time, if one exists.
// Otherwise returns an empty string.
+getAppointmentPurpose(appDate: Date, appTime: Time): string
```

You can use these ADT operations to design other operations on the appointments. For example, suppose you want to change the date or time of a particular appointment within the existing appointment book app.

## 1.4.2 ADTs That Suggest Other ADTs

Both of the previous examples you require to represent a date, the appointment book example requires you to represent the time. C++ has date-time objects specified in ctypes that you use to represent the date and time. You can also design ADTs to represent these items in an object-oriented way. It is not unusual for the design of one ADT to suggest other ADTs. In fact, you can use one ADT to implement another.

You can use an ADT to implement another ADT

This final example describes an ADT that suggests other ADTs for its implementation. Suppose you want to design a database of recipes. You can think of this as an ADT. The recipes are the data items, and some typical operations on the recipes could include:

```
// Inserts a recipe into the database.
+insertRecipe(aRecipe): boolean
// Deletes a recipe from the database.
+deleteRecipe(aRecipe): boolean
// Gets the named recipe from the database.
+getRecipe(aName): string
```

This level of design does not include such details as where insertRecipe will place a recipe into the database. Now imagine that you want to design an operation that scales a recipe retrieved from the database: if the recipe is for n people, you want to revise it so that it will serve m people. Suppose that measurements as ½ cups, 1 tablespoon, and 1/4 teaspoon. The quantities are given as mixed numbers—integers and fractions—in units of cups, tablespoons, and teaspoons. This suggests another ADT—measurement—with the following operations:

```
// Returns this measure.
+getMeasure()

// Sets this measure to another one.
+setMeasure(m: Measurement)

// Returns this measure multiplied by a scale factor, which has no units.
+scaleMeasure(scaleFactor: float)

// Returns this measure converted from old units to new units.
+convertMeasure(oldUnits: MeasureUnit, newUnits: MeasureUnit)
```

Suppose that you want to implement exact arithmetic in C++. Because our planned language does not have a data type for fractions, and floating-point arithmetic is not exact, another ADT called fraction is needed. Its operations could include addition, subtraction, and division of fractions. For example, you could specify addition as

// Returns the sum, reduced to lowest terms, of this fraction and the given fraction
+add(other: Fraction): Fraction

Moreover, you could include operations to convert a mixed number to a fraction and vice versa. When you finally implement the ADT measurement, you can use the ADT fraction. That is, you use one ADT to implement another.

## 1.5 The ADT Bag

Imagine a paper bag, a cloth bag, or a plastic bag. People use bags when they shop, pack a lunch, or carry potato chips. A bag contains things; it is a container of a collection of objects. We could consider the bag to be an abstract data type.

A bag is a container

Let's specify and use the ADT bag. Knowing its interface, you use a bag in a program. You do not need to know how the entries in the bag are represented or how the bag operations are implemented. These specifics are hidden behind the bag's wall of abstraction, and your program will not depend on them. As you will see, this important characteristic is what abstraction is all about.

When distinguishing a bag from other ADTs a bag doesn't do more than its contents. It doesn't order in a particular way, nor does it prevent duplicates. While describing the behaviors of the ADT bag that we will design in this chapter, let's keep in mind that we are specifying an abstraction by an actual bag. For example, a paper bag holds things of various dimensions and shapes in no particular order and without regard for duplicates. Our abstract bag will hold unordered and possibly duplicate objects, but let's say these objects have the same types.

> Note: A bag is a container of finite objects having the same data type and in no order. A bag can contain duplicate items.

### 1.5.1 Identifying Behaviors

As a bag contains a finite number of objects, reporting how many objects it contains could be one of a bag's behaviors:

- Get the number of items currently in the bag.

A related behavior detects if a bag is empty:
- See whether the bag is empty.

We should be able to add and remove objects:

- Add a given object to the bag.
- Remove an occurrence of a specific object from the bag, if possible.
- Remove all objects from the bag.

Note that the add operation does not indicate where in the bag the object should go. Remember that a bag does not order its contents. The remove operation looks for a particular item in the bag. If it finds it, it takes it out. If the bag contains several objects equal to the one, they remain in the bag. If the operation cannot find the specific object in the bag, it can't remove it, and just says so. Finally, the second remove operation empties the bag of all objects.

What is in a particular bag? The answer to this question can be answered by the following operations:

- Count the number of times a certain object occurs in the bag.
- Test whether the bag contains a particular object.
- Look at all objects that are in the bag.

We have enough behaviors for now. At this point, we would have written all the behaviors on a piece of paper or, as Appendix C suggests, on the **class-responsibility-collaboration (CRC) card** pictured in Figure 1-6.
