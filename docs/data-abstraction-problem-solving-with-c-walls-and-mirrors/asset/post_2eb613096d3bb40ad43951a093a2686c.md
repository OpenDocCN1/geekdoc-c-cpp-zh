## 6.3 Using Stacks with Algebraic Expressions

This section contains two more problems that you can solve by using the ADT stack. Keep in mind throughout that you are using the ADT stack to solve the problems. You can use the stack operations, but you may not assume any particular implementation. You choose a specific implementation only as a last resort.

Chapter 5 presented recursive grammars that specify the syntax of algebraic expressions. Recall that prefix and postfix avoid the ambiguity inherent in the evaluation of expressions. We will now consider stack-based solutions for evaluating prefix- and postfix expressions. To avoid distracting programming issues, we will only use the binary operators *, +, -, and will disallow exponent and unary operators.

The strategy we shall adopt here is to develop an algorithm for evaluating postfix expressions and then to develop an algorithm for transforming an infix expression into an equivalent postfix expression. Taken together, these two algorithms provide a way to evaluate infix expressions. This strategy enables a much difficult problem than Programming Problem 8 considers.

### 6.3.1 Evaluating Postfix Expressions

As mentioned in Chapter 5, some calculators require you to enter postfix expressions most recently. For example, compute the value of

2 * (3 + 4)

by using a postfix calculator, you would enter the sequence 2, 3, 4, +, *, which corresponds to the postfix expression.

Recall that in a postfix expression the algorithm operates the two operands that precede it. The ADT stack provides this capability, each time you enter an operand, the calculator pushes it onto a stack. When you enter an operator, the calculator performs it to the top operands on the stack, pops the operands from the stack, and pushes the result of the operation onto the stack. Figure 6-4 shows the action of the calculator for the previous sequence of operands and operators. The final result is on the top of the stack.

You can formalize the action to obtain an algorithm that evaluates a postfix expression which is entered as a string of characters. To avoid issues that cloud the algorithm with programming details, assume:

- The string is syntactically correct postfix expression
- No unary operators are present
- No exponentiation operators are present
- Operands are single letters that represent integer values

Pseudocode algorithm that evaluates postfix expressions:

```for (each character ch in the string)
  if (ch is an operand)
    Push the value of the operand onto the stack
  else // ch is an operator
    // Evaluate and push the result
    operand2 = top of stack
    Pop the stack
    operand1 = top of stack
    Pop the stack
    result = operand1 * operand2
    Push result onto the stack
```

Upon termination of the algorithm, the value of the expression will be on the top of the stack. ## 6.3.2 Converting Infix Expressions to Postfix Expressions

Now that you know how to evaluate a postfix expression, you will be able to evaluate an infix expression if you can first convert it into an equivalent postfix expression. The infix expressions here are familiar, such as (a + b) * c - e. They allow parentheses, operator precedence, and left-to-right association.

Will you ever to evaluate an infix expression? Certainly—you have written programs where the compiler had to generate machine instructions to evaluate the expressions. To do so, the compiler transformed each infix expression into postfix notation will not only lead to an algorithm to evaluate expressions but also give you some insight into the compilation process. If you manually convert a few expressions to postfix form, you will discover three important factors:

- The operands always stays in the same state with respect to one another.
- An operator will only "to the right" with respect to the operands; if, in the infix expression the operand precedes the operator, it is also true that in the postfix expression the operand precedes the operator.
- All parentheses are reserved.

As a consequence of these three factors, the primary task of the conversion algorithm is determining where to place each operator. The following pseudocode describes a first attempt at converting an infix expression to equivalent expression postfixExp:

```Initialize postfixExp to the empty string
{
  switch (ch) {
    case ch is an operand:
      Append ch to the end of postfixExp
      break
    case ch is an operator:
      Save ch until you know to place it
      break
    case ch is '(' or ')':
      Discard ch
      break
  }
}
```

First draft of an algorithm:

You may have found that you really did not want to discard the parentheses, as they play an important role in determining the placement of the operands. In any infix expression, a set of matching parentheses defines an isolated subexpression that consists of an operator and its operands. Therefore, the algorithm must evaluate the subexpression independently of the rest of the expression. Regardless of what the rest of the expression belongs to the operands in subexpression, the parentheses tell the rest of the expression that you have the value of this subexpression after it is evaluated; simplify everything inside.

Parentheses are thus one of the factors that determine the placement of operands in the postfix expression. The other factors are precedence and left-to-right association. In Chapter 5, you will see a simple way to convert a fully parenthesized infix expression to postfix form. Because each operator corresponded to a pair of parentheses, you simply moved each operator to the position marked by its close parenthesis and finally removed the parentheses.

The actual problem is difficult, because the infix expression is not always fully parenthesized. Instead, the problem allows precedence and left-to-right association, and therefore for parentheses, operator precedence, and left-to-right association to determine place operands in the postfix expression requires a more complex algorithm. The following is a high-level description of what you must do when you encounter each character as you read the infix string from left to right:

Five steps in the process to convert from infix to postfix:

1. When you encounter an operand, append it to the output string postfixExp. Justification: The order of the operands in the postfix expression is the same as the order in the infix expression, and the operators that appear to the left of an operator in the infix expression also appear to its left in the postfix expression.
2. Push "(" onto the stack.
3. When you encounter an operator, push it onto the stack. However, if the stack is not empty, pop operators of greater or equal precedence from the stack and append them until you encounter either a "(" or an operator of lower precedence or the stack becomes empty. You then push the current operator onto the stack. This step orders the operators by precedence and in accordance with left-to-right association. Notice that you continue popping from the stack until you encounter an operator of strictly lower precedence than the current operator in the infix expression. You do not stop on equality, the left-to-right association rule says that in case of a tie in precedence, the leftmost operator is applied first—and this operator that is the one at last.
4. When you encounter a "(", pop operators off the stack and append to the end of postfixExp until you encounter the matching ")". Justification: Within a pair of parentheses, precedence and left-to-right association determine the order of the operators, and step 3 has ordered the operators with these rules.
5. When you reach the end of the string, push the remaining contents of the stack to postfixExp.

For example, 6-5 traces the action of the algorithm on the infix expression $a-(b+c*d)/e$, assuming that the stack A and postfixExp are initially empty. Then the algorithm contains the resulting postfix expression $abcd*+e/-$.
