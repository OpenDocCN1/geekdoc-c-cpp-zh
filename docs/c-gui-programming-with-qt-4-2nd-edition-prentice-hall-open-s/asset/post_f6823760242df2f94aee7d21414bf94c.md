
# Making Applications Translation-Aware

If we want to make our applications available in multiple languages, we must do two things:

- Make sure that every user-visible string goes through `tr()`.
- Load a translation (.qm) file at startup.

Neither of these is necessary for applications that will never be translated. However, using `tr()` requires no effort and leaves the door open for doing translations at a later date.

The `tr()` is a static function defined in `QObject` and overridden in every subclass defined with the `Q_OBJECT` macro. When writing code inside a QObject subclass, we can call `tr()` without formality. A `tr()` function returns a translation if one is available; otherwise, the original text is returned. Inside a non-`QObject` class, we can write `QObject::tr()` with the class prefix or use `Q_DECLARE_TR_FUNCTIONS()` macro to add `tr()` to the class, as we did in Chapter 8 (p. 200).

To prepare translation files, we must run Qt's `update` tool. This tool extracts all string literals that appear in `tr()` and produces translation files that contain all of these strings to be translated. The files can then be sent to a translator to have translations added. Process this is explained in the "Translating Applications" section later in this chapter.

A `tr()` call has the following general syntax:

```
Context::tr(sourceText, comment)
```

The `Context` is the name of a `QObject` subclass defined with the `Q_OBJECT` macro. We do not need to specify it if we call `tr()` from a member function of the class in question. The `sourceText` part is the string literal that needs to be translated. The `comment` part is optional; it can be used to provide additional information to the translator.

Here are a few examples:

```
RockyWidget::RockyWidget(QWidget *parent)
    : QWidget(parent)
{
    QString str1 = tr("Letter");
    QString str2 = RockyWidget::tr("Letter");
    QString str3 = SnazzyDialog::tr("Letter");
    QString str4 = SnazzyDialog::tr("Letter", "US paper size");
}
```

The first two calls to tr() have "RockyWidget" as their context, and the last two calls have "SnazzyDialog". All four have "Letter" as their source text. The last call also has a comment to help the translator understand the meaning of the source text.

Strings in different contexts (classes) are translated independently of each other. Translators typically work on one context at a time, often with the application running and showing the widget or dialog being translated.

When we call tr() from a global function, we must specify the context explicitly. If none is QObject subclass in the application can be used as the context. If none is appropriate, we can always use QObject itself. For example:

```
int main(int argc, char *argv[]) {
    QApplication app(argc, argv);
    QPushButton button(QObject::tr("Hello Qt!"));
    button.show();
    return app.exec();
}
```

In every example so far, the context has been a class name. This is convenient, because we can almost always omit it, but this doesn't have to be the case. The most general way of translating a string in Qt is to use the QCoreApplication::translate() function, which accepts up to three arguments: the context, the source text, and the optional comment. For example, here's another way to translate "Hello Qt":

```
QCoreApplication::translate("Global Stuff", "Hello Qt!")
```

This time, we put the text in the "Global Stuff" context. tr() and translate() functions serve a dual purpose: They are markers that update to find user-visible strings, and at the same time they are C++ functions that translate text. This has an impact on how we write code. For example, the following will not work:

```
// WRONG
const char *appName = "OpenDrawer 2D";
QString translated = tr(appName);
```

The problem here is that update will not be able to extract the "OpenDrawer 2D" string literal, as it doesn't appear inside a tr() call. This means that the translator will not have the opportunity to translate the string. This issue often arises in conjunction with dynamic strings:

```
// WRONG
statusBar->showMessage(tr("Host " + hostName + " found"));
```

Here, the string we pass to tr() varies depending the value of hostName, so we can't reasonably expect tr() to translate it. The solution is to use QString::arg():

```
statusBar->showMessage(tr("Host %1 found").arg(hostName));
```

Notice how it works: The string literal "Host %1" is passed to tr(). Assuming that a French translation is loaded, tr() would return something like "Host trouvé". Then the "%1" parameter is replaced with the contents of hostName.

Although it is generally not to call tr() on a variable, it can be made to work. We must use QT_TR_NOOP() macro to mark the string literals for translation before we assign them to a variable. This is mostly useful for static arrays of strings. For example:

```
void OrderForm::init() {
    static const char * flowers[] = {
        QT_TR_NOOP("Medium Pink Roses"),
        QT_TR_NOOP("One Dozen Boxed Roses"),
        QT_TR_NOOP("Calypso Orchid"),
        QT_TR_NOOP("Dried Rose Bouquet"),
        QT_TR_NOOP("Mixed Peonies Bouquet")
    };

    for (int i = 0; i < 5; ++i) {
        comboBox->addItem(tr(flowers[i]));
    }
}
```

QT_TR_NOOP() macro simply returns its argument. lupdate strings wrapped in QT_TR_NOOP() so they can be translated. When using the variable later, we call tr() to perform the translation. Even though we have passed tr(), translation will still work.

There is also a QT_TRANSLATE_NOOP() macro that works like QT_TR_NOOP() but takes context. This context is useful when initializing variables of a class:

```
static const char * flowers[] = {
    QT_TRANSLATE_NOOP("OrderForm", "Medium Pink Roses"),
    QT_TRANSLATE_NOOP("OrderForm", "One Dozen Boxed Roses"),
    QT_TRANSLATE_NOOP("OrderForm", "Calypso Orchid"),
    QT_TRANSLATE_NOOP("OrderForm", "Dried Rose Bouquet"),
    QT_TRANSLATE_NOOP("OrderForm", "Mixed Peonies Bouquet")
};
```

The context argument must be the same as context given to tr() or translate() later on.

When we start tr() in an application, it's easy to forget to surround some user-visible strings with a tr() call, especially when we are just beginning to use it. Its missing tr() calls are eventually discovered by the translator, or by users of the translated application, when strings appear in the original language. To avoid this problem, we can tell Qt to forbid implicit conversions from const char * to QString. We do this by defining the QT_NO_CAST_FROM_ASCII preprocessor symbol before including any header. The easiest way to ensure that symbol is set is by adding the following line to the application's .pro

```
DEFINES += QT_NO_CAST_FROM_ASCII
```

This will force every string literal to require wrapping by tr() or by QLatinString(), depending on whether it should be translated. Strings that are not suitably wrapped will produce a compile-time error, compelling us to add the missing tr() or QLatinString() wrapper.

Once we have wrapped every user-visible string by a tr() call, the only thing left to do to enable translation is to load a translation file. Typically, we would do this in the application's main() function. For example, here's how we would try to load a translation file depending on the user's locale:

```
int main(int argc, char *argv[])
{
    QApplication app(argc, argv);
    ...
    QtTranslator appTranslator;
    appTranslator.load("myapp" + QLocale::system().name(), qPath);
    app.installTranslator(&appTranslator);

    return app.exec();
}
```

The QLocale::system() function returns a QLocale object that provides the locale name about the user's locale. Conventionally, we use the locale name as part of the .qm file. Names can be more or less precise; for example, fr specifies a French-language locale, fr_CA specifies a French Canadian locale, and fr_CA.ISO8859-15 specifies a French Canadian locale with ISO 8859-15 (an encoding that supports ‘€’, ‘Œ’, ‘æ’ and ‘Ÿ’).

Assuming that the locale is fr_CA.ISO8859-15, the QtTranslator::load() first tries to load the file myapp_fr_CA.ISO8859-15. If this file does not exist, load() next myapp_fr_CA.qm at a time, then myapp_fr.qm and finally myapp.qm, before giving up. Normally, we would only provide myapp_fr.qm, containing a standard French translation, but if we need a different file for French-speaking Canada, we can also provide myapp_fr_CA.qm and it will be for fr locales.

The second argument to QtTranslator::load() is the directory where we want load() for the translation file. In this case, we assume that the translation files are located in the directory given in qPath variable.

The Qt libraries contain a few strings that need to be translated. Trolltech provides French, German, and Simplified Chinese translations in Qt's translations directory. A few other languages are provided as well, but these are contributed by Qt users and are not officially supported. The Qt libraries' translation file should also be loaded:

```
QtTranslator qtTranslator;
qtTranslator.load("qt" + QLocale::system().name(), qPath);
app.installTranslator(&qtTranslator);
```

A Translator object can hold only one translation file at a time, so we use a separate QtTranslator for Qt's translation. Having just one file per translator is not a problem because we can install as many translators as we need. QApplication will use all of them when searching for a translation.
