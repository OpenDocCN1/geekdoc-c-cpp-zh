
```cpp
if (event->timerId == myTimerId) {
    ++offset;
    if (offset >= fontMetrics().width(text)) {
        offset = 0;
        scroll(-1, 0);
    }
} else {
    QWidget::timerEvent(event);
}
```

The system calls the timerEvent() function at intervals. It increments offset by 1 to simulate movement, wrapping at the width of the text. Then it scrolls the contents of the widget one pixel to the left using QWidget::scroll(). It would have been sufficient to call update() instead of scroll(), but scroll() is more efficient because it simply moves the existing pixels on-screen and generates a paint event only for the widget's newly revealed area (a 1-pixel-wide strip in this case).

If the the timer event isn't for the timer we are interested in, we pass it on to the base class.

```cpp
void Ticker::hideEvent(QHideEvent / /* event */)
{
    killTimer(myTimerId);
    myTimerId = 0;
}
```

The hideEvent() function calls QObject::killTimer() to stop the timer.
Timers are low-level, and if we need multiple timers, it can become cumbersome to keep track of all the timer IDs. In such situations, it is usually easier to create a QTimer object for each timer. QTimer emits the timeout() signal at each time interval. QTimer also provides a convenient interface for single-shot timers (timers that time out just once), as we saw in Chapter 6 (p. 158).

## Installing Event Filters

One really powerful feature of Qt's event model is that a QObject instance can be set to monitor the events of another QObject instance before the latter even sees them.

Let's suppose that we have a CustomerInputDialog widget composed of several QEdits and that we want to use the Space key to move the focus to the next QEdit. This non-standard behavior might be appropriate for an in-house application where users are trained to use it. A straightforward solution is to subclass QEdit and reimplement keyPressEvent() to call focusNextChild(), like this:

```cpp
void MyLineEdit::keyPressEvent(QKeyEvent *event)
{
    if (event->key() == Qt::Key_Space) {
        focusNextChild();
    } else {
        QLineEdit::keyPressEvent(event);
    }
}
```

This approach has one main disadvantage: If we use several different kinds of widgets in the form (e.g., ComboBox and SpinBoxes), we must also subclass them to make them exhibit the same behavior. A better solution is to make CustomerInputDialog monitor its child widgets' key press events and implement the required behavior in the monitoring code. This can be achieved using event filters. Setting up an event filter involves two steps:

- Register the monitoring object with the target object by calling installEventFilter() on the target.

- Handle the target object's events in the monitor's eventFilter() function.

A good place to register the monitoring object is in the constructor:

```cpp
CustomerInputDialog::CustomerInputDialog(QWidget *parent)
    : QDialog(parent)
{
    ...
    firstNameEdit->installEventFilter(this);
    lastNameEdit->installEventFilter(this);
    cityEdit->installEventFilter(this);
    phoneNumberEdit->installEventFilter(this);
}
```

Once the first filter is registered, the events that are sent to the firstNameEdit, lastNameEdit, phoneNumberEdit widgets are first sent to the CustomerInfoDialog::eventFilter() function before they are sent on their intended destination.

Here's the eventFilter() function that receives the events:

```cpp
bool CustomerInfoDialog::eventFilter(QObject target, QEvent event) {
    if (target == firstNameEdit || target == lastNameEdit
        || target == cityEdit || target == phoneNumberEdit) {
        if (event->type() == QEvent::KeyPress) {
            QKeyEvent *key = static_cast<QKeyEvent>(event);
            if (key->key() == Qt::Key_Space) {
                focusNextChild();
                return true;
            }
        }
    }
    return QDialog::eventFilter(target, event);
}
```

First, we check to whether the target widget is one of the QLineEdits. If the event was a key press, we cast it to QKeyEvent and check which key was pressed.

If the pressed key was Space, we call focusNextChild() to pass focus on to the next widget in the focus chain, and return true to tell Qt that we have handled the event. If we returned false, Qt would send the event to its intended target, resulting in a spurious space being inserted into the QLineEdit.

If the target widget isn't a QLineEdit or if the event isn't a Space key press, we pass control to the base class implementation of eventFilter(). The target widget could also be some widget that the base class, QDialog, is monitoring. (In Qt 4.3, this is not the case for QDialog. However, other widget classes, such as QScrollArea, do monitor some of their child widgets for various reasons.)

Qt offers five levels at which events can be processed and filtered:

## 1. We can reimplement a specific event handler.

Reimplementing handlers as mousePressEvent(), and paintEvent() is by far the most common way to process events. We have already seen many examples of this.

## 2. We can reimplement QObject::event().

By reimplementing the event(), we can intercept events before they reach the handlers. This is useful for events that don't have a specific handler, or for custom events.

## 3. We can use event filters.

As discussed, event filters are a powerful way to intercept events without subclassing the widget.

## 4. We can use QTimer.

QTimer provides a convenient way to handle time-based events.

## 5. We can subclass and reimplement virtual methods.

By subclassing a class, you can override its default behavior and provide your own implementation of virtual methods.
