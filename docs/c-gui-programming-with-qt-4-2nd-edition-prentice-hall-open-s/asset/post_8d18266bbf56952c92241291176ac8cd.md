
insert(). The iterator is then advanced to point between the new item and the following item.

In addition to the Java-style iterators, every sequential container class C<T> has STL-style types: C<T>::iterator and C<T>::const_iterator. The difference between the two is that const_iterator doesn't modify the data.

A container's begin() returns an STL-style iterator that refers to the first item in the container (e.g., list[0]), whereas end() returns to the "one past the last" item (e.g., list[5] for a list of size 5). Figure 11.5 shows the valid positions for STL-style iterators. If a container is empty, begin() equals end() can be used to see whether the container has any items, although it is usually more convenient to call isEmpty() for this purpose.

The STL-style iterator syntax ++ and -- is modeled after that of C++ pointers into an array. We can use the ++ and -- operators to move to the next or previous item, and the unary * operator to retrieve the current item. For QVector<T>, the iterator and const_iterator are merely typedefs for T* and const T*. (This is possible because QVector<T> stores its items in consecutive locations.)

The following example returns each value in QList<double> with its absolute value:

```cpp
QList<double>::iterator i = list.begin();
while (i != list.end()) {
    *i++;
}
```

A few functions return a container. If we want to iterate over the return value of a function using STL-style iterator, we must take a copy of the container and iterate over it. For example, the following code is the correct way to iterate over the QList<int> returned by sizes():

```cpp
QList<int> list = sizes();
QList<int>::const_iterator i = list.begin();
while (i != list.end()) {
    do_something(*i);
}
```

The following code is wrong:

```cpp
// WRONG
QList<int>::const_iterator i = sizes().begin();
while (i != sizes().end()) {
    do_something(*i);
}
```

This is because sizes() returns a new QList<int> every time it is called. If we don't store the return value, Qt destroys it before we have started iterating, leaving us with a dangling iterator. This makes worse, each time the loop runs, sizes() must generate a new copy of the list. In summary: When using STL-style iterators, always iterate on a copy of a container returned by value. For read-only Java-style iterators, we don't need to take a copy. The iterator takes a copy for us behind the scenes, ensuring that we iterate over the data that the function returned. For example:

```cpp
QListIterator<int> i(sizes());
while (i.hasNext()) {
    do_something(i.next());
}
```

Copying a container like this sounds expensive, but it isn't, thanks to an optimization called implicit sharing. This means that copying a Qt container is as fast as copying a single pointer. Only if one of the copies is changed is data actually copied—and this is handled automatically behind the scenes. For this reason, implicit sharing is sometimes called "copy on write".

The beauty of implicit sharing is that it is an optimization we don't need to think about; it works without requiring any programmer intervention. At the same time, implicit sharing encourages a clean programming style where objects are returned by value. Consider the following function:

```cpp
QVector<double> sineTable() {
    QVector<double> vect(360);
    for (int i = 0; i < 360; ++i)
        vect[i] = std::sin(i / (2 * M_PI));
    return vect;
}
```

The call to the function looks like this:

```cpp
QVector<double> table = sineTable();
```

STL, in comparison, encourages us to pass the vector as a non-const reference to avoid the copy that takes place when the function's return value is stored in a variable:

```cpp
void sineTable(std::vector<double> &vec) {
  vec.resize(360);
  for (int i = 0; i < 360; ++i)
    vec[i] = std::sin(i / (2 * M_PI));
}
```

The call then becomes more tedious and less clear to read:

```cpp
std::vector<double> table;
sineTable(table);
```

Qt uses implicit sharing for all its containers and for many other classes, including ByteArray, QBrush, QFont, QImage, QPixmap, QString. This makes these classes very easy to pass by value, both as function parameters and as return values.

Implicit sharing is a guarantee from Qt that the data won't be copied if we don't modify it. To get the best out of implicit sharing, we can adopt a couple of new programming habits. One habit is to use the at() function rather than the [] operator for read-only access on a (non-const) vector or list. Since Qt's containers cannot tell whether [] appears on the left side of an assignment, it assumes the worst and forces a deep copy to occur—whereas at() isn't allowed on the left side of an assignment.

A similar issue arises when we iterate over a container with STL-style iterators. We call begin() and end() on a non-const container, Qt forces a deep copy to occur if the data is shared. To prevent this inefficiency, the solution is to use const_iterator, constBegin(), and constEnd() whenever possible.

Qt provides one last method for iterating over items in a sequential container: the foreach loop. It looks like this:

```cpp
QList<Movie> list;
...
foreach (Movie movie, list) {
    if (movie.title() == "Citizen Kane") {
        std::cout << "Found Citizen Kane" << std::endl;
        break;
    }
}
```

The foreach pseudo-keyword is implemented in terms of the standard for loop. At each iteration of the loop, the iteration variable (movie) is set to a new item, starting at the first item in the container and progressing forward. The foreach loop automatically takes a copy of the container when the loop is entered, and for this reason the loop is not affected if the container is modified during iteration.

Implicit sharing works automatically behind the scenes, so we don't need to do anything. But since it's nice to know how things work, we will study an example. The example uses QString, one of many implicitly shared classes.

```cpp
QString str1 = "Humpty";
QString str2 = str1;
```

We set str1 to "Humpty" and str2 to be equal to str1. At this point, QString objects point to the same data structure. The data structure holds a reference count that indicates how many QStrings point to the data. The reference count is 2.

```cpp
str2[0] = 'D';
```

When we modify str2, it first makes a deep copy of the data, to ensure str1 and str2 point to different data, and then it applies the change to its own copy. The reference count of str1's data ("Humpty") becomes 1, and the reference count of str2's data ("Dumpty") is set to 1.

```cpp
str2.truncate(4);
```

If we modify str2 again, no copying takes place because the reference count of str2's data is 1. The truncate() function operates directly on str2's data, resulting in the string "Dumpty". The reference count stays at 1.

```cpp
str1 = str2;
```

When we assign str2 to str1, the reference count for str1's data goes down to 0, which means that no QString is using the "Humpty" data anymore. The data is then freed from memory. Both QString point to "Dumpty", which now has a reference count of 2.

Data sharing is often disregarded as an option in multithreaded programs, because of race conditions in the reference counting. With Qt, this is not an issue. Internally, the container classes use assembly language instructions to perform atomic counting. This technology is available in Qt through the QSharedData and QSharedDataPointer classes.
