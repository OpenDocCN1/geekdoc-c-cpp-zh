typesObject, we can use querySubObject() instead:

```
QAObject session = outlook.querySubObject("Session");
QAObject defaultContacts =
session->querySubObject("GetDefaultFolder(OlDefaultFolders)");
```

If we want to handle unsupported data types in their parameter list, we can use QABase::queryInterface() to retrieve the COM interface and call the method directly. As usual with COM, we must call Release() when we have finished using the interface. If we often need to call such methods, we subclass QAObject or QAWidget and provide member functions that encapsulate the COM interface calls. Be aware that QAObject and QAWidget subclasses cannot define their own properties, signals, or slots.

We will now review the QAServer module. This module enables us to turn a standard Qt program into an ActiveX server. The server can be either a shared library or a stand-alone application. Servers built as shared libraries are often called in-process servers; stand-alone applications are called out-of-process servers.

Our first QAServer example is an in-process server that provides a widget that shows a ball bouncing left and right. We will also see how to embed the widget in Internet Explorer.

Here's the beginning of the class definition of the AxBouncer widget:

```
class AxBouncer : public QWidget, public QABindable
{
    Q_OBJECT
    Q_ENUMs(SpeedValue)
    Q_PROPERTY(QColor color READ color WRITE setColor)
    Q_PROPERTY(SpeedValue speed READ speed WRITE setSpeed)
    Q_PROPERTY(int radius READ radius WRITE setRadius)
    Q_PROPERTY(bool running READ isRunning)
```

AxBouncer, shown in Figure 23.6, is derived from both QWidget and QABindable.
The QABindable class provides an interface between the widget and an ActiveX client. Any QWidget can be exported as an ActiveX control, by subclassing QABindable we can notify the client when a property's value changes, and we can implement COM interfaces to supplement those already implemented by QAServer.
