
QDataStream version we are reading is the same as the one we used for writing. This must be the case. By hard-coding the version number, we guarantee that the application can always read and write the data (assuming it is compiled with Qt 4.3 or any later version).

QDataStream stores data in such a way that we can read it back seamlessly. QByteArray is represented as a 32-bit byte count followed by the bytes themselves. QDataStream can also be used to read and write bytes, with any byte counter, readRawBytes() and writeRawBytes().

Error handling when reading from a QDataStream is fairly easy. The status() value that can be returned is QDataStream::Ok, QDataStream::ReadPastEnd, QDataStream::ReadCorruptData. Once an error has occurred, the >> operator reads zero or empty values. This means we can often simply read an entire file without worrying about potential errors and check the status() value at the end to see what.

QDataStream handles a variety of C++ and Qt data types; the complete list is available at http://doc.troll.com/4.3/datastreamformat.html. We can also add support for our custom types by overloading the << and >> operators. Here's the definition of a custom data type that can be used with QDataStream:

```cpp
class Painting
public:
    Painting() : myYear = 0; {}
    Painting(const QString &title, const QString &artist, int year) {
        myTitle = title;
        myArtist = artist;
        myYear = year;
    }

    void setTitle(const QString &title) { myTitle = title; }
    QString title() const { return myTitle; }
    ...
private:
    QString myTitle;
    QString myArtist;
    int myYear;
};

QDataStream &operator<<(QDataStream &out, const Painting &painting);
QDataStream &operator>>(QDataStream &in, Painting &painting);
```

```cpp
QDataStream &operator<<(QDataStream &out, const Painting &painting) {
    out << painting.title() << painting.artist()
    << quint32(painting.year());
    return out;
}
```

To output a Painting, we simply output two QStrings and quint32. At the end of the function, we return the stream. This is a common C++ idiom that allows us to use a chain of << operators with an output stream. For example:

```cpp
out << painting1 << painting2 << painting3;
```

The implementation of operator>>() is similar to that of operator<<():

```cpp
QDataStream &operator>>(QDataStream &in, Painting &painting) {
    QString title;
    QString artist;
    quint32 year;

    in >> title >> artist >> year;
    painting = Painting(title, artist, year);
    return in;
}
```

There are several benefits to providing streaming operators for custom data types. One of them is that it allows us to stream containers that use the custom type. For example:

```cpp
QList<Painting> paintings = ...;
out << paintings;
```

```cpp
QList<Painting> paintings;
in >> paintings;
```

Another benefit of providing streamers is compiler error if Painting didn't support << >> for custom types. We can also store values of types using QVariant, which makes them much more usable—for example, by QSettings. This works provided that we register the type using qRegisterTypeStreamOperators<T>() beforehand, as explained in Chapter 11 (p. 292).

When we use QStream, Qt takes care of reading and writing each entry, including containers with an arbitrary number of items. This relieves us from the need to structure what we write and performing any kind of parsing on what we read. Our only obligation is to ensure that we read all the entries in the same order as we wrote them, leaving Qt to handle all the details.

QDataStream is useful for our own custom formats and standard binary formats. We can read and write standard binary formats using the streamer on objects (such as quint16 and float) or using readRawBytes() and writeRawBytes(). If QDataStream is being purely to read and write basic C++ data types, we don't even need to call setVersion().

So far, we loaded and saved data with the streamer's version hard-coded as QDataStream::Qt_43. This approach is simple and safe, but it has one flaw: we cannot take advantage of new or updated formats. For example, if a later version of Qt added a new attribute, it wouldn't be saved or loaded. There are two solutions. The first approach is to embed the QDataStream version in the file:

```cpp
QDataStream out(&file);
out << quint32(MagicNumber) << quint16(out.version());
```

(MagicNumber is a constant that uniquely identifies the file.) This approach ensures we always read the data using the most recent version, whatever happens to be. When we come to read the file, we read the stream:

```cpp
quint32 magic;
quint16 streamVersion;
QDataStream in(&file);
in >> magic >> streamVersion;
```

```cpp
if (magic != MagicNumber) {
    std::cerr << "File is not recognized by this application" << std::endl;
} else if (streamVersion > in.version()) {
    std::cerr << "File is from a more recent version of the application" << std::endl;
    return false;
}
```

```cpp
if (streamVersion < in.version()) {
    in.setVersion(QDataStream::Qt_3_0);
} else {
    in.setVersion(QDataStream::Qt_4_3);
}
```

In this example, we specify that any file saved with versions prior to 1.3 of the application, we use it to deduce the stream version instead of storing it explicitly. For example, let's suppose that the file format is for version 1.3 of our application. We might write this to the data as follows:

```cpp
QDataStream out(&file);
out.setVersion(QDataStream::Qt_4_3);
out << quint32(MagicNumber) << quint16(0x0103);
```

When we read it back, we determine which QDataStream version to use based on the application's version number:

```cpp
QDataStream in(&file);
in >> magic >> appVersion;
```

```cpp
if (magic != MagicNumber) {
  std::cerr << "File is not recognized by this application" << std::endl;
  return false;
} else if (appVersion > 0x0103) {
  std::cerr << "File is from a more recent version of the application" << std::endl;
  return false;
}
```

In this example, we specify that any file saved with versions prior to 1.3 of the application, we use it to deduce the stream version instead of storing it explicitly.

There are other scenarios in which accessing QIODevice directly is more appropriate than using QDataStream. QIODevice provides a peek() function that returns the next bytes without moving the device position as well as unChar() function that "unreads" a byte. This works for random-access devices (such as files) and for sequential devices (such as network sockets). There is also a seek() function that sets the device position, for devices that support random access.

Binary files provide the most versatile and most compact means of storing data, and QDataStream makes accessing binary data easy. In addition to the examples in this section, we already saw the use of QDataStream in Chapter 4 read and write Spreadsheet files, and we will see it again in Chapter 21, where we use it to read and write Windows cursor files.

# Reading and Writing Text

Binary files are typically more compact than text-based formats, which are not human-readable or human-editable. In cases where this is an issue, we can use text formats instead. Qt provides the QStream class for reading and writing plain text files and for files using other text formats, such as HTML, XML, and source code. We cover handling XML files separately in Chapter 16.

QStream takes care of converting between Unicode and the system's local encoding or any other encoding, and transparently handles the different line-encoding codings used by different operating systems ("\n" on Windows, "\n" on Unix and Mac OS X). QStream uses the 16-bit QString type as its fundamental unit of data. In addition to characters and strings, QStream supports C++'s basic numeric types, which and strings. For example, the following code writes "Thomas M. Disch: 334\n" to the file sf-book.txt:

```cpp
QFile file("sf-book.txt");
if (!file.open(IODevice::WriteOnly)) {
    std::cerr << "Cannot open file for writing: "
    << qPrintable(file.errorString()) << std::endl;
    return;
}
```

```cpp
QTextStream out(&file);
out << "Thomas M. Disch: " << 334 << endl;
```

Writing text is very easy, but reading text can be challenging because textual data (unlike binary data written using QDataStream) is fundamentally ambiguous. Let's consider the following example:

```cpp
out << "Denmark" << "Norway";
```

If out is a QTextStream, the data that actually gets written is the string "DenmarkNorway". We can't really expect the following code to read back the data correctly:

```cpp
in >> str1 >> str2;
```

In fact, what happens is that str1 gets the whole word "DenmarkNorway", and str2 gets nothing. This problem doesn't occur with QDataStream because it stores the length of each string in front of the character data.
