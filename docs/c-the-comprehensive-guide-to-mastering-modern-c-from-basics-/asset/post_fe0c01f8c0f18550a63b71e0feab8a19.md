#include <thread>
#include <barrier>
#include <iostream>
#include <vector>
long fib(long n) { return n<=1 ? n : fib(n-1)+fib(n-2); };
constexpr int anz = 8;           // 8 workers
constexpr int max = 32;         // calculate up to 32
std::vector<long> results(anz); // Buffer: space for 8 results

void output() {
    // Signaling function points buffer
    for (auto &n : results) std::cout << n << ' ';
    std::cout << '\n';
}

std::barrier ba(anz, output); // always output after 8

void worker(std::stop_token st, int idx) {
    // n = 0, 9, 17, 25, ... 1, 10, 18, 26, ...
    for(int n=idx; n<max; n+=anz) {
        if(st.stop_requested()) return;
        results[idx] = fib(n); // write result to buffer
        ba.arrive_and_wait(); // wait until 8 threads are here
    }
}

int main() {
    std::vector<std::thread> threads; // 8 Threads
    for (int idx=0; idx<anz; ++idx) {
        threads.emplace_back(worker, idx); // create thread with index
    }
    for (auto &t : threads) t.join(); // wait until all are done
}
```

**Listing 29.16** A barrier waits for a specific number of threads.

Each worker function calculates the Fibonacci numbers in steps of eight and writes the result to its position—so the threads do not interfere with each other. The function output outputs all results. And this happens exactly when eight threads in worker reach the call arrive_and_wait().

29.2.4 Mutex stands for mutual exclusive. You use a mutex on a resource that you want to protect from concurrent access: one resource thus has one mutex, no matter how many threads you use. If you have two instances of the resource, you need two mutexes.. [ 83 ]

In each thread, you lock the mutex associated with the resource before using the resource. If another thread then wants to use the same resource, it also tries to lock this mutex. This fails, and the second thread can either wait or forgo using the resource.

Once the first thread is done with its transactions, it unlocks the mutex. If another thread was waiting to lock the same mutex, it will acquire the lock at the next opportunity and then perform its actions.

In this way, the threads work cooperatively, mutually excluding each other from the critical resource, coordinated via a mutex.

# A Mutex is a Special Case of a Semaphore

A semaphore allows a fixed number of threads to simultaneously use a resource. A mutex is a semaphore with a limit of one: at most one thread can use the resource at the same time.

In C++20, the counting_semaphore and binary_semaphore classes have been newly added. They are, in a way, lighter alternatives to mutex. You do not use them with a lock (i.e., without RAII), but instead call acquire and release manually. The other difference is that it does not matter which thread releases the semaphore, whereas with mutex it must always be the original thread.

What does this look like in C++ practice? You use an instance of the mutex class belonging to the resource and a lock_guard on the mutex in one thread to lock and unlock it.

With the lock_guard class, you cannot forget to unlock the mutex again, because the destructor takes care of that, following the RAII principle. Thus, the range between initializing the lock_guard instance and its scope is protected.

For special tasks, there are suitable alternatives to both mutex and lock_guard, which I will discuss later.

The following listing shows first a typical, albeit simple, use of the basic tools.

```cpp
// https://godbolt.org/z/3fz5a4vYv
#include <mutex> // mutex
#include <list>
#include <algorithm>
using std::mutex;
using std::lock_guard;

class MxList {
    std::list<int> data;
    mutable mutex mx;
public:
    void add(int value) {
        std::lock_guard<mutex> lock(mx);
        data.push_back(value);
    }
    bool contains(int searchVal) const {
        std::lock_guard<mutex> lock(mx);
        return std::find(data.begin(), data.end(), searchVal) != data.end();
    }
};
```

**Listing 29.17** A mutex used to protect a list.

Because the resource is shared among threads, it must be protected. In the example above, the `lock_guard` ensures that only one thread can access the `data` list at a time.

# Critical Section

A critical section is a part of code that accesses a shared resource that should be accessed by multiple threads. To prevent race conditions, these sections must be protected by a mutex.

```cpp
// Critical section example
{
    std::lock_guard<mutex> lock(mtx);
    // access shared resource
}
```

The code block protected by a mutex is called a critical section. This ensures that only one thread can execute the block at a time, preventing data corruption.

# Mutable Mutex?

A method marked `const` should not modify the state of the object. However, a mutex must be modified when locked. To allow this in `const` methods, the mutex is declared `mutable`.

```cpp
class MyClass {
    int data;
    mutable mutex mx;
public:
    int getValue() const {
        std::lock_guard<mutex> lock(mx);
        return data;
    }
};
```
