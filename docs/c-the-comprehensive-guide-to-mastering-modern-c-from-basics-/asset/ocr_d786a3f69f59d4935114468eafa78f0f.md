# 29.2.7 More Flexible Locking with "unique_lock"

While lock_guard offers the simplest interface to use, we can alternatively use the more flexible unique_lock:

+   - unique_lock{..., adopt_lock};
The mutex is already locked; just take care of unlocking.

+   - unique_lock{..., defer_lock}
Do not lock the mutex immediately. Handle later with lk..(not on the mutex!) or with the std::lock(lk) function call.

+   - unique_lock{..., try_to_lock}
Try to lock, and if that doesn't work, proceed anyway.

Using unique_lock instead of lock_guard, the functionality would be identical. The big difference is that it can temporarily not own the mutex associated with it. Similar to how a unique_ptr can transfer its content as a return value or parameter to another unique_ptr, the unique_lock can do the same with the mutex associated with it. You can transfer the lock of a mutex out of or into a method or function.
