
## 24.8.5 "unordered_map"

The unordered_map shares large parts of its interface with (Section 24.7.4) and often exhibits similar behavior to unordered_set (Section 24.8.4).

This implies that it is possible to link target values to keys and retrieve them rapidly. In particular note is that this is usually achieved in O(1) time, which is optimal. Regrettably, this may not always be guaranteed, and in extreme cases the process could take O(n) time.

As with map, you have operator[], and at, insert_assign available. Otherwise, you search with forward iterators.

The examples in this section for unordered_map should be considered embedded in the code of Listing 24.83. However, note my comment on << in the box that followed Listing 24.12.

```cpp
// https://cppbolt.org/z5KKw4z4
#include <unordered_map>
#include <iostream>
using std::unordered_map; using std::cout;
template<typename K, typename T>
std::ostream& operator<<(std::ostream& os, const unordered_map<K,T>& data) {
    for (const auto& first : data)
        os << first.first << " ": << << first.second << "\n";
    return os << '\n'; // with operator followed by a newline
}
```

### The Elements and Their Properties

The elements of an unordered_map are pair<const Key, Target>. For key, you need two things:

- You need a hash function, which is either std::hash<Key> or specified by you as a template argument.
- Key must be comparable with ==, meaning it must be defined, or you must provide a functor for this.

For custom data types, the easiest is to define operator== as friend or operator== = default and also provide a custom hash function. A short example is shown in Listing 24.84.

```cpp
// https://cppbolt.org/cdeGW5a3p
#include <unordered_map>
#include <string>
using std::string; using std::unordered_map; using std::cout;
struct City {
    string name;
    explicit City(const string& name) : name(name) {}
    auto operator==(const City& b) const = default;
};
struct CityHash {
    std::hash<string> hash;
    size_t operator()(const City& a) const {
        return hash(a.name);
    }
};
int main() {
    unordered_map<City, CityHash> cty{
        {City("San Francisco"), "CA"},
        {City("Austin"), "TX"},
        {City("Miami"), "FL"}
    };
    cout << cty[City("San Francisco")] << "\n"; // Output: CA
}
```

**Listing 24.84** A custom data type as a key in an "unordered_map".

The spaceship operator == with default ensures that the compiler can use for == and thus it can be used by the unordered_map() method.

The CityHash functor requires a size_t operator(const City& const) const method. In it, I use the hash function provided by the standard library for string.

### Initialize

When defining an unordered_map, you need at least the template arguments for Key and Target.

You can only omit them if you use pair for initialization; unfortunately, the compiler cannot handle them with nested initialization lists.

The rest is optional:

- Key—the type to which the keys should refer
- Target—the type to which the values refer
- Optional Hash—the hash function for Key, default is std::hash<Key>
- Optional KeyEqual—the comparison operator for Key; by default std::equal_to<Key> and thus operator==
- Optional Allocator—memory allocator for the elements

Besides the types, you can use various overloads. Most of the following options also have the possibility to provide a hash function, a comparison operator, or an allocator:

- The default constructor without arguments to create an empty container
- An iterator pair for copying from another container or stream
- An initializer list with initial values
- From C++23, from_range with a range
- Another unordered_map for a complete copy or move

A peculiarity of all associative containers is that in the first variants, an optional size_t count can still be passed, which sets the minimum size of hash table.

### Assignment

Like all containers, you can use operator= for both copying and moving to the container. With swap, you have a tool for quickly exchanging all data with unordered_map.

### Insert

When inserting, there is no difference in interface compared to map. Only the runtime guarantees are different as they are constant and linear per element:

- Inserting a single element with automatic positioning
Use insert(pair<Key,Target>) or insert(Key,Target) to insert a new element. Be careful as well; the container will not overwrite if the key exists.
- Automatic insertion and overwriting
Alternatively, you can use operator[] for insertion, but this will first create an empty value. If you use this on the left side of assignment, you will get a reference to the target back, which you then reassign.
- Inserting a single element with position
There are also insert_hint with an additional parameter in unordered_map.
- Inserting multiple elements
You can copy multiple elements with an iterator pair or initializer list using insert, or use insert_range starting from C++23.

With merge, you can extract elements from another unordered_map that do not yet exist. Iterators in unordered_map retain their validity like in unordered_set as long as the number of buckets does not need to be adjusted. If you want to have control over this, use reserve() beforehand, for example.

### Access

When accessing elements with the forward iterators of unordered_map, they refer to pair<const Key, Target>. This means you cannot change it->first but can change the target value it->second. Otherwise, the interface is roughly equivalent to that of a normal map. Only with search functions do you need limit yourself to what associative containers offer:

- Access via iterators
With begin() and end() as cbegin() and cend(), you get forward iterators that you can use, for example, in range-based loop.
- Access via search
find, count, and equal_range available for searching. Because unordered_map only knows unique keys, find() probably makes the most sense here. Without search without creating a complete key.
- Index-like access
The special features of unordered_map are, as with map, the operator[] method. With this, you get a reference to the target value of an existing entry back. The difference between the two is that operator[] inserts a new element if one exists, while at throws an exception of type std::out_range if the key does not exist.

### Deleting

- Deleting all elements
Clear the unordered_map with clear().
- Deleting or transferring a single element
As with map, erase from unordered_map either by key or by iterator. With erase, you delete an element to immediately insert it elsewhere. own- Deleting multiple elements
With a pair of iterators, erase deletes multiple elements. Iterators to nondeleted elements remain valid through operations. Moreover, the relative order of the remaining elements in the container does not change, allowing you to delete elements within a loop without disrupting the loop.

### Specialty: “operator[]”

Like map, the unordered_map offers the operator[] for easy reading and writing. No other associative container has this access capability.

### Specialty: The Bucketful

The unordered_map also has an interface that allows you to gain precise insights into its internal workings. You can use bucket_count() to get the number of buckets and begin/end(int) iterators to access the contents of buckets. In addition, bucket_size(int) and int bucket(Key) are available to you.

### Specialty: Reserve Space

To maintain control over when a reordering of elements occurs during insertion, you can influence this mechanism with several methods, similar to unordered_set.load_factor and max_load_factor the interfaces for load factor, and with rehash and reserve you can directly influence the size of the hash table.

The unordered_multiset inherits its properties from unordered_set (Section 24.7.3) and from multiset (Section 24.7.5). It usually finds its keys optimally in O(1), but unfortunately guarantee this and then needs O(n) time in the worst case, which is why the ordered multiset might be the better choice if you want to avoid nasty surprises.

As with multiset, each key can be stored multiple times. One of the typical use cases is that only a part of the stored objects actually serves as keys. There is an example in Listing 24.85.
