# Casting inside a Generic Method

Sometimes you should be wary of generics—for instance, when using them specifically to bury a cast operation. Consider the following method, which converts a stream into an object of a given type:

```
public static T Deserialize<T>(
stream, IFormatter formatter)
{
return (T)formatter.Deserialize(stream);
}
```

The formatter is responsible for removing data from the stream and converting it to an object. The Deserialize() call on the formatter returns data of type object. A call to use the generic version of Deserialize() looks something like this:

```
string greeting =
Deserialization.Deserialize<string>(stream, formatter);
```

The problem with this code is that to the caller of the method, Deserialize<T>() appears to be type-safe. However, a cast operation is still performed on behalf of the caller, as in the case of the nongener equivalent:

```
string greeting =
(string)Deserialization.Deserialize(stream, formatter);
```

The cast could fail at runtime, the method might not be as type-safe as it appears. The Deserialize<T> method is generic solely so that it can hide the existence of the cast from the caller, which seems dangerously deceptive. It might be better for the method to be generic and return object, making the caller aware that it is not type-safe. Developers should use care when casting in generic methods if there are no constraints to verify cast validity.

> Guidelines\AVOID misleading the caller with generic methods that are not type-safe as they appear.
