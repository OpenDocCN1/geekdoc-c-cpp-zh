```
    Apple apple1 = new();

    Orange orange = new();

    // A fruit comparer can compare apples and oranges:
    bool b1 = fc.FirstIsBetter(apple1, orange);
    // or apples and apples:
    bool b2 = fc.FirstIsBetter(apple1, apple2);
    // This is legal because the interface is
    // contravariant.
    IComparable<Apple> ac = fc;
    // This is really a fruit comparer, so it can
    // still compare two apples
    bool b3 = ac.FirstIsBetter(apple1, apple2);
}
```

Like covariance support, contariance uses a type parameter modifier: in, which appears in the interface's type parameter declaration. This instructs the compiler to check that T never appears on a property getter or as the return type of a method, thereby enabling contravariant conversions for this interface.

Contravariant conversions have all the analogous restrictions described earlier for covariant conversions: They are valid only for generic interface and delegate types, the varying type arguments are reference types, and the compiler must verify that the interface is safe for the contravariant conversions.

An interface can be covariant in one parameter and contravariant in, although this case seldom arises in practice except with delegates. The Func<A1, A2, ..., R> family of delegates, for example, is covariant in the return type, R, and contravariant in all the argument types.

Lastly, note that the compiler will check the validity of the covariance and contravariance type parameter modifiers throughout the source. Consider the IPairInitializer<in T> interface in Listing 12.45.
