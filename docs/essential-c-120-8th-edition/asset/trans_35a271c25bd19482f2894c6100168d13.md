列表 22.1 中的问题是竞态条件，即多个线程同时访问相同的数据元素。此执行示例表明，允许多个线程访问相同的数据元素可能会破坏数据完整性，即使在单处理器计算机上也是如此。为了解决这一潜在问题，需要对数据进行同步。为了多线程同时访问而进行同步的代码或数据是**线程安全的**。

关于变量读取和写入的原子性，有一点重要的需要注意。运行时保证了大小不大于原生（指针大小）整数的变量不会被不恰当地读取或写入。在 64 位操作系统上，原子操作是原子的。然而，对 `long`（64 位）原子变量进行十进制读取和写入可能不是原子的。因此，对十进制变量的写入操作可能会在仅复制 32 位后被中断，导致读取到错误的值，这被称为**撕裂读（torn read）**。

## 多线程与局部变量

注意，没有必要对局部变量进行同步。局部变量被加载到栈上，每个线程都有自己的逻辑栈。因此，每个局部变量对于每个方法调用都有自己的实例。默认情况下，局部变量不会在方法调用之间共享；同样，它们也不会在多个线程之间共享。

这并不意味着局部变量完全没有并发问题——毕竟，代码很容易将局部变量暴露给多个线程。² 例如，一个在迭代之间共享局部变量的并行 for 循环会将该变量暴露在并发访问和竞态条件之下（参见列表 22.2）。

> ² 虽然在 C# 级别它是局部变量，但在公共中间语言（CIL）级别它是一个字段——字段可以从多个线程访问。

# 使用 Monitor 进行同步

为了同步多个线程以便它们无法同时执行特定的代码段，你可以使用 monitor 来阻塞第二个线程在第一个线程退出该段之前进入保护的代码段。monitor 功能是名为 `System.Threading.Monitor` 类的一部分，受保护代码段的开始和结束分别用静态方法 `Monitor.Enter()` 和 `Monitor.Exit()` 进行标记。

列表 22.3（结果如输出 22.2 显示）演示了显式使用 Monitor 类进行同步。如此列表所示，重要的是 `Monitor.Enter()` 和 `Monitor.Exit()` 调用之间的所有代码都必须包含在 `try/finally` 块中。如果没有此块，保护段内可能会发生异常且 `Monitor.Exit()` 可能永远不会被调用，从而无限地阻塞其他线程。

列表 22.3：显式使用 Monitor 同步

```csharp
using System;
using System.Threading;
using System.Threading.Tasks;

public class Program
{
    readonly static object _Sync = new();
    static int _Total = int.MaxValue;
    static int _Count = 0;

    public static int Main(string[] args)
    {
        if (args?.Length > 0) { _Total = int.TryParse(args[0], out _Total); }
        Console.WriteLine("increment and decrementing " + _Total + " times...");

        // Task.Factory.StartNew 用于 .NET 4.0
        Task task = Task.Run(() => Decrement());

        // 增加
        for(int i = 0; i < _Total; i++)
        {
            bool lockTaken = false;
            try
            {
                Monitor.Enter(_Sync, ref lockTaken);
                _Count++;
            }
            finally
            {
                if(lockTaken)
                {
                    Monitor.Exit(_Sync);
                }
            }
        }

        task.Wait();
        Console.WriteLine($"Count = {_Count}");
        return _Count;
    }

    public static void Decrement() 
    {
        for(int i = 0; i < _Total; i++) 
        {
            bool lockTaken = false;
            try {
                Monitor.Enter(_Sync, ref lockTaken);
                _Count--;
            }
            finally {
                if(lockTaken) {
                    Monitor.Exit(_Sync);
                }
            }
        }
    }
}
```

注意，`Monitor.Enter()` 和 `Monitor.Exit()` 的调用通过共享作为参数的相同对象引用（在本例中为 `_Sync`）相关联。接受 `lockTaken` 参数的 `Monitor.Enter()` 载载方法仅在 .NET 4.0 中才添加到框架中。在此之前，没有这种 `lockTaken` 参数，也没有办法可靠地捕获 `Monitor.Enter()` 和 `try` 块之间发生的异常。将 `try` 块紧跟在 `Monitor.Enter()` 调用之后在发布代码中是可靠的，因为即时编译器（JIT）阻止了异步异常的发生。然而，在 `Monitor.Enter()` 之后除了 `try` 块以外的任何内容（包括编译器在调试代码中注入的任何指令）都可能阻止 JIT 可靠地返回。因此，如果发生了异常，会导致锁泄漏（锁保持锁定状态），而不是执行 `finally` 块并释放它——导致其他线程尝试获取锁时死锁。总结，在 .NET 4.0 之前的框架版本中，你应该始终在 `Monitor.Enter()` 之后跟随 `try/finally {Monitor.Exit(_Sync)}` 块。

Monitor 还支持 `Pulse()` 方法允许线程进入就队列，表示它是下一个执行。这是同步生产者-消费者模式的常用方法，确保在没有“生产”的情况下不会“消费”。拥有 monitor 的生产者（通过调用 `Monitor.Enter()`）调用 `Monitor.Pulse()` 来通知消费者线程（它可能已经调用了 `Monitor.Enter()`）有可消费的项目，并且应该准备就绪。对于单个 `Pulse()` 调用，只有一个线程（在本例中为消费者线程）可以进入就绪队列。当生产者调用 `Monitor.Exit()` 时，消费者获取锁（`Monitor.Enter()` 完成）并进入区域开始消费。一旦消费者处理了等待的项目，它就会调用 `Exit()`，从而允许生产者（当前被 `Monitor.Enter()` 阻塞）再次生产。在此示例中，一次只有一个线程可以进入就绪队列，确保没有生产就没有消费，反之亦然。
