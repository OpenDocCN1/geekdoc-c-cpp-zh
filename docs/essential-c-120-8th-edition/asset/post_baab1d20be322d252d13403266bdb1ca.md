## Delegates Do Not Have Structural Equality

Delegate types in .NET do not exhibit structural equality. That is, you cannot convert a reference to an object of one delegate type to an unrelated delegate type, even if the formal parameters and return types of both delegates are identical. For example, you cannot assign a reference to a Comparator to a variable of type Func<int, int, bool>, even though delegate types represent methods that take two parameters and return a bool. Unfortunately, the only way to use a delegate of a given type is when a delegate of a structurally identical but unrelated delegate type is needed to create a new delegate that refers to the Invoke method of the old delegate. For example, if you have a variable c of type Comparator, and you need to assign its value to a variable f of type Func<int, int, bool>, you can say f = c.Invoke;

However, thanks to variance support,¹¹ it is possible to make reference conversions between some delegate types. Consider the following contravariant example: Because void Action<T>(T arg) has the type parameter modifier, it is possible to assign a reference to a delegate of type Action<object> to a variable of type Action<string>.

Many people find delegate contravariance confusing. It may help to remember that an action can act on every object can be an action that acts on any string. The opposite is not true: An action that act only on strings cannot act on every object. Similarly, every type in the Func family of delegates is covariant in its return type, as indicated by the out parameter modifier on TResult. Therefore, it is possible to assign a reference to a delegate of type Func<string> to a variable of type Func<object>.

## Outer Variables

Local variables declared outside a lambda expression (including parameters of the containing method) are called the outer variables of that lambda. (This reference, though technically not a variable, is also considered to be an outer variable.) When a lambda body uses an outer variable, the variable is said to be captured (or, equivalently, closed over) by the lambda. In Listing 13.20, we use an outer variable to count how many times BubbleSort() performs a comparison. Output 13.2 shows the results of this listing.

## Listing 13.20: Using an Outer Variable in a Lambda Expression

```csharp
public class Program
{
    public static void Main()
    {
        int[] items = new int[5];
        int comparisonCount = 0;

        for (int i = 0; i < items.Length; i++)
        {
            Console.Write("Enter an integer:");
            string text = Console.ReadLine();
            if (!int.TryParse(text, out items[i]))
            {
                Console.WriteLine($"{text} is not a valid integer.");
                return;
            }
        }

        DelegateSample.BubbleSort(items,
            (int first, int second) =>
            {
                comparisonCount++;
                return first < second;
            });

        for (int i = 0; i < items.Length; i++)
        {
            Console.WriteLine(items[i]);
        }
        Console.WriteLine("Items were compared {0}",
            comparisonCount);
    }
}
```

Note that comparisonCount appears outside the lambda expression and is incremented inside it. After calling the BubbleSort() method, comparisonCount is printed out to the console. Normally, the lifetime of a local variable is tied to its scope; when control leaves the scope, the storage location associated with the variable is no longer valid. But a delegate created from a lambda that captures an outer variable might have a longer (or shorter) lifetime than the local variable, and the delegate must be able to access the outer variable every time the delegate is invoked. Therefore, the lifetime of a captured variable is extended: It is guaranteed to live at least as long as the longest-lived delegate capturing it. (And it may live even longer than that—precisely how the compiler generates the code that ensures outer variable are extended is an implementation detail and subject to change.)
