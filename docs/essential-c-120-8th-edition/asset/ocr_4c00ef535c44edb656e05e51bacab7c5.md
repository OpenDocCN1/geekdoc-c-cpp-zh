2. We can surround each delegate body with a try/catch block so that no exceptions go unhandled from the task. Unfortunately, this approach is also less ideal. First, some exceptions (those triggered when calling antecedent.Result) will throw an AggregateException, from which we will need to unwrap the InnerException(s) to handle them individually. Upon unwrapping, we either rethrow them to catch a specific type or conditionally check for the type of the exception separately from any other blocks (even catch blocks for the same type). Second, each delegate body requires its own separate try/catch handler, even if some of the exception types between blocks are the same. Third, Main's call to Wait.Wait() could still throw an exception because HttpClient.GetByteArrayAsync() and CountOccurrencesAsync could throw an exception, and there is no way to surround the latter with a try/catch block. There is no way to eliminate the catch block in Main that surrounds task.Wait().

3. In Listing 20.2, we don't catch exceptions thrown from GetByteArrayAsync() but instead rely solely on the try/catch block that surrounds Main.Wait(). Given that we know the exception will be an AggregateException, there is a catch for that exception. Within the catch block, we handle the exception by calling AggregateException.Handle() and throwing each exception using the ExceptionDispatchInfo object so not to lose the original stack trace. These exceptions are then caught by the expected exception handlers and addressed accordingly. Notice, however, before handling the AggregateException.InnerExceptions, we first call AggregateException.Flatten(). This step addresses the issue of AggregateException wrapping inner exceptions that are also of type AggregateException. By calling Flatten(), we ensure that all exceptions are moved to the first level and all contained AggregateExceptions are removed.

As shown in Listing 20.2, option 3 is probably the preferred approach because it keeps the exception handling outside the control flow for the most. This doesn't eliminate the error-handling complexity entirely; rather, it simply minimizes the occasions on which it is interspersed within the regular control flow.
