## Exception Class Inheritance

All objects thrown as exceptions derive from System.Exception. (Objects thrown from other languages that do not derive from System.Exception are automatically "wrapped" by an object that derives.) Therefore, they can be handled by the catch(System.Exception exception) block. It is preferable, however, to include a block that is specific to the most derived type (e.g., System.FormatException), because then it is possible to get the most information about an exception and handle it generically. In so doing, the catch statement that uses the most derived type can handle the exception type specifically, accessing data related to the exception and avoiding conditional logic to determine what type of exception occurred.

Therefore, C# enforces the rule that catch blocks appear from most derived to least derived. For example, a catch statement that catches System.Exception cannot appear before a statement catches System.FormatException because System.FormatException derives from System.Exception.

A method could throw many exception types. Table 5.2 lists some of the common ones within the framework.

TABLE 5.2: Common Exception Types

| Exception Type | Description |
| --- | --- |
| System.Exception | The "base" exception from which all other exceptions derive. |
| System.ArgumentException | Indicates that one of the arguments passed into the method is invalid. |
| System.ArgumentNullException | Indicates that a particular argument is null and that this is not a valid value for that parameter. |
| System.Application | To be avoided. The original idea was that you might want to have one kind of handling for system exceptions and another for application exceptions, although plausible, doesn't actually work well in the real world. |

## General Catch

It is possible to specify a catch block that takes no parameters, as shown in Listing 5.29.

LISTING 5.29: General Catch Blocks

```cs
// A previous catch clause already catches all exceptions
#pragma warning disable CS1058
// ...
    try
```

```cs
{
  age = int.Parse(ageText);
  Console.WriteLine($"Hi {firstName}! You are {age * 12} months old.");
}
catch(FormatException exception) {
  Console.WriteLine($"The age entered {ageText}, is not valid.");
  result = 1;
}
catch(Exception exception) {
  Console.WriteLine($"Unexpected error: {exception.Message}");
  result = 1;
}
catch {
  Console.WriteLine("Unexpected error!");
  result = 1;
}
finally {
  Console.WriteLine($"Goodbye {firstName}");
}
```

A catch block with no data type, called a general catch block, is equivalent to specifying a catch block that takes an object data type—for instance, catch(object exception){...}. For this reason, a warning is triggered stating that the catch block already exists; hence the #pragma warning disable directive.

Because all classes derive from object, a catch block with no data type must appear last.
General catch blocks are rarely used because there is no to capture any information about the exception. In addition, C# doesn't support the ability to throw an exception of type object. (Only written in languages such as C++ allow exceptions of any type.)

## Basic Error Handling with Exceptions

## Guidelines

- **AVOID** general catch blocks and replace them with a catch of **System.Exception**.
- **AVOID** catching exceptions for which the appropriate action is unknown. It is better to let an exception go unhandled than to handle incorrectly.

## Reporting Errors Using a throw Statement

C# allows developers to throw exceptions from their code, as demonstrated in Listing 5.30 and Output 5.14.

Listing 5.30: Throwing an Exception

```cs
public static void Main()
{
    try
    {
        Console.WriteLine("Begin executing");
        Console.WriteLine("Throw exception");
        throw new Exception("Arbitrary exception");
        // Catch 1
        Console.WriteLine("End executing");
    }
    catch(FormatException exception)
    {
        Console.WriteLine(
            "FormatException was thrown");
    }
    // Catch 1
    catch(Exception exception)
    {
        Console.WriteLine(
            $"Unexpected error: {exception.Message}");
        result = 1;
    }

    // Post Catch
    Console.WriteLine(
        "Shutting down...");
}
```

OUTPUT 5.14

```
Begin executing
Throw exception
Unexpected error: Arbitrary exception
Shutting down...
```

As the comments in 5.30 depict, throwing an exception causes execution to jump from where it is thrown into the first compatible catch block.¹⁰ In this case, To throw an exception, it is necessary to have an instance. Listing 5.30 creates an instance using the keyword followed by the type. Sometimes a catch block will trap an exception but be unable to handle it. In these circumstances, a catch block can rethrow the exception, as shown in 5.31.

```cs
// ...
catch (Exception exception)
{
    Console.WriteLine("Rethrowing unexpected error: " + exception.Message);

    throw;
}
// ...
```

In Listing 5.31, the throw statement is “empty” rather than specifying that the exception referred to by the exception variable is be thrown. This illustrates a subtle difference: throw preserves the stack information, whereas throw exception; replaces that information with the current stack. For debugging purposes, it is usually better to know the original call stack. Of course, this is allowed only in a catch statement where the caught exception can be determined.

- DO prefer using an empty throw when rethrowing an exception, to preserve the call stack.
- DO report exception failures by throwing exceptions rather than returning error codes.
- DO NOT use public members that return exceptions as return values or an out parameter. Throw exceptions to indicate errors; do not use them as return values to indicate errors.
- AVOID catching and logging an exception before rethrowing. Instead, allow the exception to escape until it can be handled appropriately.

## Reporting Null Argument Exceptions

When nullability reference types are enabled, the compiler will make a best effort to identify when there is the possibility of a nullable argument passed as a non-nullable argument. If you assign a possible null value to a non-nullable argument, the compiler will issue a warning stating that you are attempting to convert a possible null value to a non-nullable argument. Assuming you address all warnings appropriately, the compiler will catch most of the cases. However, if the caller is outside of your control (such as from a library you didn’t write), doesn’t turn on nullable reference types, ignores the warnings, or invokes the method from C# 7.0 or earlier, there is nothing preventing a null argument even though the parameter is declared as non-nullable.
