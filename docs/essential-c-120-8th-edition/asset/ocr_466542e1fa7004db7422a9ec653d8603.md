# Chapter 22: Thread Synchronization

+   * **Hold and wait**: One thread (Thread A) with a mutual exclusion is waiting to acquire a resource held by another thread (Thread B).
* **No preemption**: The resource held by a thread (Thread A) cannot be forcibly removed (Thread A needs to release its owned resource).
* **Circular wait condition**: Two or more threads form a circular chain that they lock on the same or more resources, and each waits on the resource held by the next thread in the chain.

Removing any one of these conditions prevents the deadlock.
One scenario likely to cause a deadlock when two or more threads request exclusive ownership on the same or more synchronization targets (resources) and the locks are requested in different orders. This situation can be avoided when developers are careful to ensure that multiple lock acquisitions always occur in the same order. Another potential cause of a deadlock is locks that are not reentrant. When a lock from one thread can block the same thread—that is, when it re-requests the same lock—is blocked because the lock is already owned (by itself), it is not reentrant and the additional request will result in deadlock.

The code generated by the lock keyword (with the underlying Monitor class) is reentrant. However, as we shall see in the "More Synchronization Types" section, some lock types are not reentrant.

# When to Provide Synchronization

As we discussed earlier, all static data should be thread safe. Therefore, synchronization needs to surround static data that is mutable. Generally, programmers should declare private variables and provide public methods for modifying the data. Such methods should internally handle the synchronization if multithreaded access is possible.

In contrast, instance state is not expected to include synchronization. Synchronization may significantly decrease performance and increase the chance of a lock contention or deadlock. With the exception of classes that are explicitly designed for multithreaded access, programmers sharing objects across multiple threads are expected to handle their own synchronization of the data being shared.
