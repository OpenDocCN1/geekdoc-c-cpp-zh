
Threads are expensive resources, thread context switching is not free, and running two jobs in simulated parallelism via time slicing can be significantly slower than running one after the other. And while the thread pool does its job well, it does not provide services to deal with long-running jobs or jobs that need to be synchronized with the main thread or with one another. What we really need is to build a higher-level abstraction that can use threads and thread pools as an implementation detail. TPL provides precisely that abstraction, ThreadPool can essentially be deprecated in favor of the TPL-based APIs.

For more details on other techniques for managing threads that were commonly used prior to .NET 4, see the Essential C# 3.0 multithreading chapters at https://intellitextect.com/EssentialCSharp

# Guidelines

- AVOID calling Thread.Sleep() in production code.
- DO use tasks and related APIs in favor of System.Threading classes as Thread and ThreadPool.

For more information on System.Threading.ThreadPool’s and System.Threading.Thread’s Sleep() methods, see https://intellitextect.com/legacy-system-threading.

The logic in Listing 20.1 is relatively straightforward—common C# idioms. After determining the url and findText values, Main(), using an existing HttpClient instance, it invokes the asynchronous method GetByteArrayAsync() to download the content. It calls .Result to force the asynchronous method to execute synchronously and return the result. This approach to making asynchronous methods runs synchronously is not recommend as it can cause deadlocks. Given the downloaded data, it passes this to CountOccurrences(), which loads it into a stream and search for the findText value. (We use the GetByteArrayAsync() method rather than the simpler GetStringAsync() in Listing 20.2 and 20.3.)

The problem with this approach is, of course, that the calling thread is blocked until the I/O operation completes; this is wasting a thread that could be doing work. For this reason, we cannot execute other code, such as code that asynchronously indicates progress. In other words, “Download...” and “Searching...” are invoked *before* their corresponding operations, not *during* the operation. While doing so would be irrelevant here, imagine that we wanted to concurrently execute additional work or, at a minimum, provide an animated busy indicator.
