
## Language Contrast: Java—Generics

The implementation of generics in Java occurs entirely within the compiler, not within the Java Virtual Machine. Sun Microsystems, which originally developed Java (long before Oracle took it over), adopted this approach to ensure that no updated Java Virtual Machine would need to be distributed with generics.

The Java implementation uses syntax like the templates in C++ and the generics in C#, using type parameters and constraints. It does not treat value types differently from reference types, however. As such, generics in Java do not offer the same gains in execution efficiency as they do in C#. Indeed, whenever the Java compiler returns data, it injects automatic downcasts from the specified constraint to the base Object. The Java compiler generates a single specialized type at compile time, which it uses to instantiate any generic type. Finally, because the Java Virtual Machine does not support generics natively, there is no way to ascertain the type of an instance at execution time, and other uses of reflection are severely limited.

# Summary

In C# programs, using object (particularly in the context of collections) should make you consider whether the problem would be better solved with generics. The increased type safety enabled by the elimination of casts, the elimination of boxing performance penalty, and the reduction of repeated code are all significant improvements.

Chapter 15 looks more at the pervasive Collections.Generic namespaces. As its name implies, this namespace is composed almost exclusively of generic types. It provides clear examples of how some types were originally converted to use generics. However, before we tackle these topics, we will investigate expressions, which provide significant improvement for working with collections in C# 3.0.

# Delegates and Lambda Expressions

Previous chapters discussed extensively how to create classes to encapsulate data and operations. As you create more classes, you will see common patterns among them. One common pattern is to pass an object to a method so that the method can, in turn, call a method on the object. For example, if you pass an IComparer<int> reference to a method, odds are good that the called method will itself call compare() on the object provided. In this case, the interface is nothing more than a way to pass a reference to a single method that can be invoked. Consider a second example in which you invoke a new process. Rather than blocking or repeatedly checking (polling) when the process has completed, ideally you would like to have the method run asynchronously and then invoke a callback function, which the called method will invoke to notify the caller when the invocation completes.

It seems unnecessary to define a new interface every time you want to pass a method around. In this chapter, we describe how to create and use a special kind of class called a delegate that enables you to treat methods as any other data. We then show how to create custom delegate instances easily with lambda expressions.
