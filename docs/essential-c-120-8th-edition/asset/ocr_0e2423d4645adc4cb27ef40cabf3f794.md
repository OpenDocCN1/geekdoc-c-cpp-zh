A list, by contrast, stores values in a specific order and accesses them by their position. In a sense, lists are the special case of dictionaries where the “Key” is always an integer and the key set is always a contiguous set of non-negative integers starting with zero. Nevertheless, this is a strong enough difference that it is worth having an entirely different type to represent it.

Thus, when selecting a collection to solve some data storage or retrieval problem, the first two interfaces to look for are IList<T> and IDictionary<TKey, TValue>. These interfaces indicate the collection type is forced by retrieval of a value given its positional index or retrieval of a value given its associated key.

Both of these interfaces require that a class that them implement an indexer. In case of IList<T>, the operand corresponds to the position of the element being retrieved: The indexer takes an integer and gives you access to the nth element in the list. In the case of the IDictionary<TKey, TValue> the operand corresponds to the key associated with a value and gives you access to that value.

# ICollection<T>

Both IList<T> and IDictionary<TKey, TValue> implement ICollection<T>. A collection that does not implement IList<T> or IDictionary<TKey, TValue> will more than likely implement ICollection<T> (although not necessarily, because collections implement the lesser requirement of IEnumerable<T> or IEnumerable<T>). ICollection<T> is derived from IEnumerable<T> and includes two members: Count and CountTo().

+   * The Count property returns the total number of elements in the collection. Initially, it might appear that this would be sufficient to iterate through each element in the collection using a for loop, but in fact, the collection would also need to support retrieval by index, which the ICollection<T> interface does not include (although IList<T> does include it).
