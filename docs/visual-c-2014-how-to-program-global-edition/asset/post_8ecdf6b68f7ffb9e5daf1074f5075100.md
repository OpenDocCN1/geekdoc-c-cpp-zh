## Summary

## Section 13.1 Introduction

- An exception is an indication of a problem that occurs during a program's execution.
- Exception handling enables you to create apps that can resolve (or handle) exceptions.

## Section 13.2 Example: Divide by Zero Without Exception Handling

- An exception is thrown when a method or the CLR detects a problem and is unable to handle it.

### Section 13.2.1 Dividing By Zero

- A stack trace includes the name of the exception in a descriptive message that indicates the problem that occurred and the complete method-call stack at the time the exception occurred.
- Division by zero is not allowed in integer arithmetic.
- Division by zero is allowed with floating-point values. Such a calculation results in the value infinity, which is represented by Double.PositiveInfinity or Double.NegativeInfinity, depending on whether the numerator is positive or negative. If both the numerator and denominator are zero, the result of the calculation is Double.NaN.
- When division by zero occurs in integer arithmetic, a DivideByZeroException is thrown.

### Section 13.2.2 Enter a Non-Numeric Denominator

- A FormatException occurs when int.Parse receives a string that does not contain a valid integer.

### Section 13.3.1 Enclosing Code in a try Block

- A try block excludes the code that might throw exceptions, as well as the code that should not execute if an exception occurs.

### Section 13.3.2 Catching Exceptions

- A catch block can specify an identifier representing the exception that the catch block can handle. A general catch clause catches all exceptions, without access exception information.
- At least one catch block and/or a finally block must immediately follow the try block.

### Section 13.3.3 Uncaught Exceptions

- An uncaught exception is an exception that occurs for which there's no catch block.

### Section 13.3.4 Termination Model of Exception Handling

- After an exception is handled, program control does not return to the throw point, because the try block has exited. Instead, control resumes the try statement's last catch block. This is known as the termination model of exception handling.

### Section 13.3.5 Flow of Control When Exceptions Occur

- When a method block in a program detects an exception, or when the CLR detects a problem, the method or the CLR throws an exception.
- The point in the block at which an exception occurs is called the throw point.
- If an exception occurs in a try block, the try block terminates, and program control transfers to the first of the following catch blocks in which the exception parameter matches the type of exception.
- The try block and its corresponding catch and finally blocks form a try statement.
- The CLR locates the matching catch by comparing the thrown exception's type to each catch's exception parameter. A match occurs if the types are identical or if the thrown exception's type is a derived class of the exception-type.
- Once an exception is matched to a catch block, the other catch blocks are ignored.

## Section 13.4 .NET Exception Hierarchy

- The C# exception handling mechanism allows only of class Exception and its derived classes to be thrown and caught.
- Class Exception of namespace System is the base class of the .NET Framework Class Library exception class hierarchy.

### Section 13.4.1 SystemException

- The CLR generates SystemExceptions, which can occur at any point.
- A benefit of using exception hierarchy is that a catch block can catch exceptions of a particular type—or because of inheritance—a base class of exception.

## Chapter 13 Exception Handling: A Deeper Look

## Section 13.5 finally

- The most common type of resource leak is a memory leak.
- A memory leak occurs when a program allocates memory but does not deallocate it when no longer needed. Normally, this is not an issue in C#, because the CLR performs garbage collection of memory that is longer needed.

### Section 13.5.1 Moving-Release Code to finally

- The using statement simplifies writing code in which you obtain an IDisposable resource, the resource in a block and release the resource in a corresponding finally block.
- The finally block executes regardless of whether the try block executes. This makes the finally block an ideal location to place resource-release code for resources acquired and manipulated in the try block.
- If a try block executes, the finally block executes immediately after the try block. If an exception occurs in the try block, the finally block executes immediately after matching catch block (if any) completes.
- If the exception is not associated with a catch block by the try block, or if a catch block associated with the try block throws an exception, the finally block executes before the exception is processed by the next try block (if there is).
- A throw statement can rethink an exception, indicating that a catch block performed partial processing of the exception and now is throwing the exception again for further processing.

## Section 13.6 Using Statement

- The using statement simplifies writing code in which you obtain an IDDisposable resource, the resource in a block and release the resource in a corresponding finally block.

## Section 13.7 Exception Properties

- Property Message of class Exception stores the error message with an Exception object.
- Property StackTrace of class Exception contains a string that represents the method-call stack.

### Section 13.7.1 InnerException

- Another Exception property used frequently by class library programmers is InnerException. Typically, you use this property to "wrap" exception objects caught in your code, so that you can throw new exception types specific to your libraries.

### Section 13.7.3 Demonstrating Exception Properties and Stack Unwinding

- When an exception is thrown but not caught in a particular scope, stack unwinding occurs and an attempt is made to catch the exception in the next outer try block.

## Section 13.8 User-Defined Exception Classes

- User-defined exception classes derive directly or indirectly from class Exception.
- User-defined exceptions should typically extend Exception, have a class name that ends with "Exception" and define a parameterless constructor, a constructor that receives a string argument (the error message), and a constructor that receives a string argument and an Exception argument (the error message and the inner-exception object).
