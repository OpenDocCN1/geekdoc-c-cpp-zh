# 23.5.3 Modifying a GUI from a Separate Thread

Lines 55, 60 and 63 in StartFibonacci call AppendText (lines 82–92) to append to the output TextBox. GUI controls are designed to be manipulated only by the GUI thread—all GUI handlers are invoked in the GUI thread automatically. Modifying controls from a non-GUI thread can corrupt the GUI, making it unreliable or unusable. When updating from a non-GUI thread, you must schedule that to be performed by the GUI. To do so in Windows Forms, check the inherited property InvokerRequired (line 84). If this property is true, the code executing in a non-GUI thread must not update the GUI. Instead, call the inherited Method Invoke (line 86), which receives as an argument a Delegate representing the update to the GUI thread. In this example, we pass a Delegate (namespace System.Windows.Forms)—a Delegate that invokes a method with no arguments and a void return type. We initialize the MethodInvoke with a lambda expression that calls AppendText. Line 86 schedules this MethodInvoke to execute in the GUI thread. When the method is called from the GUI thread, line 90 updates the TextBox. Similar concepts also apply to WPF and Universal Windows GUIs.

# 23.5.4 Waiting One of Several Tasks with Task Method WhenAny

Similar to WhenAll, task class also provides static method WhenAny, which enables you to wait for any one of several Tasks specified as to complete. WhenAny returns the Task that completes first. One use of WhenAny might be to initiate several Tasks that perform the same complex calculation on computers over the Internet, then wait for any one of them to send results. This would allow you take advantage of computing power to get the result as fast as possible. In this case, it's up to you to decide whether to cancel the remaining Tasks or allow them to continue executing. For details on how to do this,
