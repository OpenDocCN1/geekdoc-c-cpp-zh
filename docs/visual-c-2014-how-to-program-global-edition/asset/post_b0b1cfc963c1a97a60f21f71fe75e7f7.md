
# Error-Prevention Tip 13.4

When placing code that can throw an exception in a Finally block, enclose the code in a try statement that catches the exception types. This prevents the loss of any uncaught and rethrown exceptions that occur before the Finally block executes.

# Software Engineering Observation 13.3

Do not place try blocks around every statement that might throw an exception—this can make programs difficult to read. Instead, place one try block around a significant portion of code, and follow this try block with catch blocks that handle each possible exception. Then follow the catch blocks with a single Finally block. Use separate try blocks to distinguish between multiple statements that can throw the same exception type.

# 13.6 The using Statement

Typically resource-release code should be placed in a finally block to ensure that a resource is released, regardless of whether there were exceptions when the resource was used in the corresponding try. An alternative notation—the using statement (not to be confused with the using directive for namespaces)—simplifies writing code when you obtain a resource, use the resource in a try block and the resource in the corresponding finally block. For example, a file-processing app (Chapter 17) could produce a file needed. The resource must be an object that implements the IDisposable interface and therefore closed properly when it's longer needed and therefore has a Dispose method. The general form of a using statement is

```cs
using (var exampleObject = new ExampleClass())
{
    exampleObject.SomeMethod(); // do something with exampleObject
}
```

Where ExampleClass is a class that implements the IDisposable interface. This code creates an object of type ExampleClass and uses it in a statement, calls its Dispose method to release any resources used by the object. The using statement implicitly places the code in its body of a try block with a corresponding finally block that calls the object's Dispose method. For instance, the preceding code segment is equivalent to

```cs
var exampleObject = new ExampleClass();
try
{
    exampleObject.SomeMethod();
}
finally
{
    if (exampleObject != null)
    {
        exampleObject.Dispose();
    }
}
```

# 13.7 Exception Properties

The if statement in finally block ensures that exampleObject is not null—that is, it references an object—otherwise, a NullReferenceException would occur when attempting to call Dispose. Section 13.9 introduces C# 6 new ? operator, which is used to express the above if statement more elegantly as a single line of code.

As we discussed in 13.4, exceptions derive from class Exception, which has several properties. These are frequently used to formulate error messages indicating a caught exception. Two important properties are Message and StackTrace. Message stores the string error associated with an Exception object. This message can be a default message defined in the exception type or a customized message passed to an Exception object's constructor when the exception is thrown. StackTrace contains a string representing the method-call stack. Recall that the runtime keeps a list of open method calls that have been made but not yet returned. The StackTrace represents the series of methods that have not finished processing at all times the exception occurs. # 13.7.1 Property InnerException

Another queried property is InnerException. When an exception occurs in a class library, it's common for the library to catch that exception, then throw a new one containing information that helps the client code determine the exception's cause. Class programmers typically "wrap" the original exception object in the new exception object—this gives the client code complete details of what led to the exception.

For example, implementing libraries in an accounting system might have account-number processing code in which account numbers are input as strings but represented as ints in the code. Parse, which allows a program to convert strings to int values with int.Parse, can throw FormatException if it encounters an invalid number format. When this happens, the library programmer might wish to display a default error message supplied by FormatException or might wish to indicate a new exception type, such as InvalidAccountNumberException.

In such cases, the library would provide an InvalidAccountNumberException object to catch the FormatException, then create in the catch block, passing the original exception object to be the InvalidAccountNumberException object's InnerException. Section 13.8 shows how to create a custom exception class.

When an InvalidAccountNumberException occurs in code that uses the accounting-system library, the catch handler can reference the original exception via property InnerException. So the InvalidAccountNumberException indicates both that the user specified an invalid account number and that the number format was invalid. If the InnerException property is null, this indicates that the exception was not caused by another exception.

# 13.7.2 Other Exception Properties

Class Exception provides other properties, including HelpLink, Source and TargetSite:

- Property HelpLink specifies a link to the help file that describes the problem that occurred. Property is null if no such file exists.
- Property Source specifies the method of the assembly (i.e., app or library) that caused the exception.
- Property TargetSite specifies the method that the exception originated.
