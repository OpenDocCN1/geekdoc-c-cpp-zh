// perform a linear search on the data
public static int LinearSearch(int[] values, int searchKey)
{
    for (var index = 0; index < values.Length; ++index)
    {
        if (values[index] == searchKey)
        {
            return index; // return the element's index
        }
    }
}

**Efficiency of Linear Search**
Searching algorithms all accomplish the same goal—finding an element that matches a given key, if such an element exists. Many, however, differentiate algorithms from one another. The major difference is the amount of effort required to complete the search. One way to describe this effort is Big O notation, which is a measure of the worst-case runtime for an algorithm—that is, how an algorithm might have to solve a problem. For searching and sorting algorithms, this is particularly dependent on how many elements are in the data and which algorithm used.

**Constant Runtime**
Suppose an algorithm is designed to test whether the first element of an array is equal to the second. If the array has 10 elements, this algorithm requires one comparison. If the array has 1,000 elements, this algorithm still requires one comparison. In fact, this algorithm is completely independent of the number of elements in the array, and is thus said to have a constant runtime, which is represented as O(1). It does not necessarily require only one comparison. O(1) just means that the number of comparisons is constant—it does not grow as the size of the array increases. An algorithm that tests whether the first element of an array is equal to any of the three elements is still O(1), even though it requires three comparisons.

**Linear Runtime**
An algorithm that tests whether the first element of an array is equal to any of the other elements of the array will require most $n-1$ comparisons, where $n$ is the number of elements in the array. If the array has 10 elements, this algorithm requires up to nine comparisons. If the array has 1,000 elements, this algorithm requires up to 999 comparisons. As $n$ grows, the $n$ part of the expression *dominates*, and subtracting one becomes inconsequential. Big O is designed to highlight these dominates and ignore terms that become unimportant as $n$ grows. For an algorithm that requires up to $n-1$ comparisons (such as the one we described earlier) is said to be $O(n)$. An $O(n)$ algorithm is referred to as having a linear runtime. $O(n)$ is often pronounced "on the order of $n$" or more simply "order of $n$."

# Quadratic Runtime

Suppose you have an algorithm that tests whether any element of an array is duplicated elsewhere in the array. The first element must be compared with every other element in the array. The second element must be compared with every other element except the first (it was already compared to the first). The third element must be compared with every other element except the first two. In this end, algorithm will be making $(n-1) + (n-2) + \dots + 2$ or $n^2/2$ comparisons. As $n$ increases, the $n^2$ term dominates and $n$ term becomes inconsequential. Big O highlights the $n^2$ term, leaving $n^2/2$ but we see.

Big O is concerned with how an algorithm's runtime grows in relation to the number of elements. Suppose with four elements the algorithm requires 16 comparisons; with eight elements, the algorithm will require 64 comparisons. With this algorithm, doubling the number of elements quadruples the number of comparisons. With four elements, doubling doubles the number of comparisons. Both of these algorithms grow as the square of n, so Big O ignores the constant, and both algorithms are considered to be $O(n^2)$, referred to as quadratic runtime and pronounced "on the order of $n$-squared" or more "order $n$-squared."

When $n$ is small, $O(n^2)$ algorithms (running on billions of operations-per-second personal computers) will not noticeably affect performance. As $n$ grows, you will start to notice the performance degradation. An $O(n^2)$ algorithm running on a million-element array would require a trillion operations (where each could require several machine instructions to execute). This could require many minutes to execute. A billion-element array would require a trillion operations, so $n$ large that the algorithm could take decades. $O(n^2)$ algorithms are easy to write, you will see shortly. You'll also see algorithms with more favorable Big O measures. These efficient algorithms often take more cleverness and effort to create, but their superior performance can be well worth the effort, especially as $n$ gets.

# Linear Search Runtime
The linear search runs in $O(n)$ time. The worst case in this algorithm is every element must be checked to determine whether the search item exists in the array. If the size of the array is doubled, the number of comparisons that the algorithm must perform is also doubled. Linear search can provide outstanding performance if the matching the search key happens to be near the front of the array. But where the search key is near the end of the array.

Linear search is the easiest algorithm to program, but it can be slow compared to other algorithms. If an app needs to perform searches on large arrays, it may be better to implement a different, more efficient algorithm, such as binary search.

### 18.2.2 Binary Search
The binary search algorithm is more efficient than the linear search, but it requires that the array be sorted. The first iteration of this tests the middle element. Assuming the array is sorted, if the key is less than the middle element, the search key cannot match any element in the second half of the array and the algorithm continues with only the first half of the array (i.e., the element up to, not including, the middle element). If the key is greater than the middle element, the search key cannot match any element in the first half of the array and the algorithm continues with only the second half of the array (i.e., the element after the middle element through the last element). Each iteration tests the middle value of the remaining portion of the array, called subarray. A subarray has no elements, or it can encompass the entire array. If the search does not match the element, the algorithm eliminates half of the remaining elements.

As an example, consider the sorted 15-element array

2 3 5 10 27 30 34 51 56 77 81 82 93 99

and a search for 65. The binary search algorithm would first check whether 51 is the search key, because 51 is the array's middle element. The search key 65 is larger than 51, so 51 is “discarded” (i.e., eliminated from consideration) along with the first half of the array (all elements smaller than 51), leaving the following subarray to be searched:

56 65 77 81 82 93 99

Next, the algorithm checks the subarray's middle element (81) matches the search key—65 is smaller than 81, so 81 is discarded along with the elements larger than 81, leaving the following subarray to be searched:

65 77

After just checks, the algorithm has narrowed the search from 15 elements to three. The algorithm then indeed matches the search key and returns array's index. This algorithm required three comparisons to determine whether the search key matched an element in the array. Using a linear search algorithm would have required 10 comparisons. [Note: In this example, we have chosen to use an array with 15 elements so that there will always be an obvious middle element in the array. With an even number of elements, the middle of the array lies between two elements. We implement the algorithm to choose the higher of the two elements]
