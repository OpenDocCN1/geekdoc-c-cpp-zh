# 10.8 Garbage Collection and Destructors

Every object you create various system resources, such as memory. In many programming languages, these system resources are reserved for the object's use until released by the programmer. If all references to the object that manages a resource are lost before the resource is explicitly released, the program can no longer access the resource to release it. This is known as a resource leak.

To avoid leaks, we needed a discipline to give resources back to the system when they're no longer using. The Common Language Runtime (CLR) automatically manages by using a garbage collector which reclaims the memory occupied by objects no longer use, so the memory can be used for other objects. When there are no more references to an object, the object becomes eligible for destruction, that invoked by the garbage collector to perform termination housekeeping on an object before the garbage collector reclaims the object's memory. A destructor is declared like a parameterless constructor, except that it operates. Its name is the same, preceded by a tilde (~), and it has no access modifier in its header. After the garbage collector calls the object's destructor, the object becomes eligible for garbage collection. The memory for such an object can be reclaimed by the collector. Memory leaks, which are common in other languages as C and C++ because memory is not automatically reclaimed in those languages, but less likely in C#, but can still happen in subtle ways. Other types of resource leaks can occur. For example, an app could open a file to modify its contents. If the file does not close, the other app can modify (or possibly even use) the file until the app it opened terminates.

A problem with the garbage collector is it doesn't guarantee that it will perform its tasks at a specified time. Therefore, the garbage collector may reclaim the memory any time after the destructor executes. In fact, it is possible that neither will happen before the app terminates. Thus, it's unclear whether or when, the destructor will be called. For this reason, destructors are rarely used.

> Software Engineering Observation 10.9 class that uses resources, such as files on disk, should provide a method to eventually release the resources. Many Framework Library classes provide Close or Dispose methods for this purpose. Section 13.6 introduces the Dispose method, which is used in many later examples. Classes are typically used with objects that are associated with files (Chapter 17) and other types of so-called streams of data.

# 10.9 static Class Members

Every object has its own copy of its class's instance variables. In certain cases, only one copy of a particular variable should be shared by all objects of a class. A static variable (or property) is used in such cases. A static variable or property represents classwide information—all objects of the class share the same piece of data. The declaration of a static variable or property begins with the keyword static.

Let's motivate data with an example. Suppose that we have a video game with Martians and other space creatures. Each Martian tends to be brave and to attack other space creatures when it's aware that there are at least four Martians present. If fewer than five Martians are present, each Martian becomes cowardly. Each Martian needs to know the MartianCount. We could count class Martian with MartianCount as an instance variable (as a property, but we'll use an instance variable for discussion purposes here). If we do this, every Martian will have a separate copy of the instance variable, and every time we create a new Martian, we'll have to update the instance variable MartianCount every Martian. This wastes space on redundant copies, updating the separate copies and is prone error. Instead, we declare MartianCount to be static, making the MartianCount, but only one copy of the static MartianCount is maintained. We save space by having the Martian constructor implement the static oldCount—there's only one copy, so we do not have to implement separate copies of martCount for each Martian object.

# static Variable Scope

The scope of a static variable is the body of its class. A class's public static members can be accessed by qualifying the member name with the class name and the member access (.) operator, as in Math.Pt. A class's private static class members can be accessed only through the class methods and properties. To access a private static member from outside its class, a public static method or property can be provided.

# Class Employee

Our next app contains classes Employee (Fig. 10.10) and EmployeeTest (Fig. 10.11). Class Employee declares static auto-implemented property Count to maintain a count of the number of Employee objects that have been created.

```cs
// Fig. 10: Employee.cs
// static property used to maintain a count of the number
// Employee objects that have been created.
using System;
public class Employee {
    public static int Count { get; private set; }
    public string FirstName { get; }
    public string LastName { get; }

    // initialize name, add 1 to static Count and
    // output string indicating constructor was called
    public Employee(string firstName, string lastName)
    {
        FirstName = firstName;
        LastName = lastName;
        Count++; // increment static count of employees
        Console.WriteLine($"Employee constructor: {FirstName}{LastName} = {Count}");
    }
}
```

# Software Engineering Observation 10.12

Actually, strings in C# are immutable—they cannot be modified after they are created. Therefore, it is safe to have many references to one string. This is not normally the case for most other classes. If strings are immutable, you might wonder why we use operators and += to concatenate strings. String-concatenation operations actually result in a new string containing the concatenated values. The original string objects are not modified.
