## 11.3 protected Members

Not every class relationship is an inheritance relationship. In Chapter 10 we discussed the has-a relationship, in which classes have members that are references to other classes. Such relationships create classes by composition of existing classes. For example, given the classes Employee, BirthDate and Telephone, it’s improper to say that an Employee is a BirthDate or that an Employee is a TelephoneNumber. However, an Employee has a BirthDate, and an Employee has a TelephoneNumber.

It is possible to test base class and derived-class objects—their commonalities are expressed in the base class’s members. Objects of classes that extend a common base class can be treated as objects of that base class—such objects have an is-relationship with the base class. For example, base-class objects cannot be treated as objects of their derived classes. For example, all cars are vehicles, but not all vehicles are cars (other vehicles could be trucks, planes, bicycles, etc.). This chapter and Chapter 12 consider examples of is-relationships.

A derived class can customize methods it inherits from its base class. In such cases, the derived class can override (redefine) the base-class method with an appropriate implementation, as we will see often in the chapter’s code examples.

Chapter 10 discussed access public and private. A class’s public members are accessible whenever the app has a reference to that class or one of its derived classes. A class’s private members are accessible only within the class itself. A base class’s private members are inherited by its derived classes, but are not directly accessible by derived-class methods and properties. In this section, we introduce access modifier. Using protected access offers an intermediate level of access between public and private. A base class’s protected members can be accessed by members of base class and by members of its derived classes, but not by clients of the class.

All non-base-class members retain their own access modifier when they become members of the derived class—public members of the base class become public members of the derived class, and protected members of the base class become protected members of the derived class.

Derived-classes can refer to public and protected members inherited from the base class by using their name. When a derived-class overrides the base class version can be accessed from the derived class by preceding the base-class method name with the keyword and the member access (base.). We discuss accessing overridden methods of the base class in Section 11.4.

| :--- |

## 11.4 Relationship between Base Classes and Derived Classes

In this section, we use an inheritance hierarchy containing types of employees in a company's payroll app to discuss the relationship between a base class and a derived class. In this company:

- commission employees—who will be represented as objects of a base class—are paid a percentage of their sales,
- base-salary commission employees—who will be represented as objects of a derived class—receive a base salary plus a percentage of their sales.

We divide our discussion of the relationship between these employee types into an evolutionary set of five examples that were carefully designed to teach key capabilities for good software engineering with inheritance:

- 1. The first example represents class CommissionEmployee, which directly inherits from object.
- 2. The second example declares class BaseCommissionEmployee, which directly inherits from object.
- 3. The third example declares class BasePlusCommissionEmployee, which directly inherits from object.
- 4. The fourth example shows that BasePlusCommissionEmployee inherits from CommissionEmployee.
- 5. The fifth and final example demonstrates best practice by making variables private in class.

In the first four examples, we will directly access variables in several cases where properties should be used. In the fifth example, we will effectively use software engineering techniques we've presented up to this point to create classes that are easy to maintain, modify and debug.

The colon (:) followed by class name object in line 5 identifies that class CommissionEmployee extends (i.e., inherits from) class object (alias for Object in System).
