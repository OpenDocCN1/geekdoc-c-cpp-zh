In such a case, the software is said to be fragile or brittle, because a small change in the base-class can "break" derived-class implementation. You should be able to change the base-class implementation while still providing the same services to the derived classes. Of course, if the base-class services change, we must rethink our classes.

# Software Engineering Observation 11.4

Declaring base-class instance variables private (as opposed to protected) enables the base-class implementation of these instance variables to change without affecting derived-class implementations.

# 11.4.5 CommissionEmployee-BasePlusCommissionEmployee Hierarchy Using private Instance Variables

We reexamine our hierarchy, this using the best software engineering practices.

Base CommissionEmployee
CommissionEmployee (Fig. 11.10) once again declare instance variables grossSales and commissionRate as private (lines 10–11). Earnings (65) and ToString (lines 68–72) do longer directly access these instances—rather they use properties grossSales and commissionRate to access the data. If we decide to change the instance-variables, the Earnings and ToString declarations will not require modification—only the bodies of the properties grossSales and commissionRate that manipulate the instance variables will need to change. These changes occur solely within the base class—no changes to the derived class are required. Localizing the effects of changes like this is a good software engineering practice. Derived class BasePlusCommissionEmployee (Fig. 11.11) inherits from CommissionEmployee and can access the private base members via the inherited properties.
