# public vs. protected Data

We have derived base class CommissionEmployee with instance variables grossSales and commissionRate as public to enable derived BasePlusCommissionEmployee to access the base-class variables. However, declaring public variables is poor software engineering, because it allows unrestricted access to the instance variables by any of the classes, increasing the chance of errors and inconsistencies. With protected instance variables, the derived class cannot access the instance variables directly.

# Problems with protected Instance Variables

In this example, we have derived class instance variables as protected so that derived classes could access them. Inheriting protected instance variables enables us to directly access the variables in the derived class without invoking the setter or getter of the corresponding property, violating encapsulation. In many cases, it's better to use protected instance variables and access them through properties to ensure proper software engineering. Your code will be easier to maintain, modify and debug.

Using protected variables creates several potential problems. First, since the derived-class object can set an inherited value without using a property's setter accessor, for example, if we declare CommissionEmployee's instance grossSales as protected, a derived-class object (e.g., BasePlusCommissionEmployee) could then assign a negative value to grossSales, making it invalid.

The second problem with protected instance variables is that derived-class methods are more likely to depend on the base-class data implementation. In practice, derived classes should depend only on the base-class (i.e., non-private methods and properties) and not on the base-class implementation. With protected instance variables in the base class, we may need to modify all the derived classes of the base class if the base-class implementation changes.
