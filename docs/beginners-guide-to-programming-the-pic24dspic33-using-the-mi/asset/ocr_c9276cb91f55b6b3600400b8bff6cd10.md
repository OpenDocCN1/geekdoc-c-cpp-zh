An embedded design cycle starts first with designing and entering source code for the target application, and then working through the any source code syntax errors associated with target code's software language to achieve an executable form of this source code. This executable form of source code is designated as object code. The next critical step, in this cycle, is to program the object code into your microcontroller prototype in order to test and validation the original code design. At this point in the cycle an external tool device is required to program the microcontroller. This tool type, like the Microchip's Microstick II, allows "In Circuit Programming" to enable you to program the microcontroller while it is in the prototype without having to remove it.

Ok, let's assume we are far enough along in the embedded design cycle where we now have executable object code programmed in the prototype. We now begin the next step of testing our source code design. Nine times out of ten all code as initially designed will have latent logic errors that need to be identified and fixed. As designers, all of us are "only too human", and, as such, are infallible in making mistakes. The mistakes at this point in the cycle are not syntax source code errors but are logic errors in that are in implicit in the original source code design. These logic errors are always, in the end, ultimately linked with any assumptions you as the designer may have made about the application or the microcontroller hardware. This is where debug comes "to the rescue".

In debug we need to test and exercise those original assumptions and discover if they are correct or not. The IDE helps us here, and with support an external debugger, allows operational test and control of the microcontroller "in Circuit" with the ability to view its operation in an investigative way. For example you should be able, in real time, to examine memory, single step the microcontroller operations, or halt operation at a designated point in the code. As you apply these tools, with your own careful thinking you begin to uncover the latent errors or "bugs" in the design.

Now the real chore becomes reworking the source code, making changes to the source code to fix the problem, and then verifying the fix by running through the entire cycle once again. The process, in fact, relies on multiple iterations through the embedded design cycle. For each of these iterations you will continue to discover the bugs, and fix those, eventually converging on a baseline solution that is hopefully bug free. There are some experts that believe that all designs reach product maturity with some measure of latent bugs still present (I tend to believe them). The amount of time you spend in iteration is dependent on a number of factors, like the total complexity of the design, your complete understanding of the application that you designed to, your skills with the tools, your knowledge of the microcontroller, and finally, and most importantly, the numbers of assumptions you have made on all the above. A lot of these factors will definitely tend to diminish with experience, as both your skills with the tools and knowledge of the technology grows.
