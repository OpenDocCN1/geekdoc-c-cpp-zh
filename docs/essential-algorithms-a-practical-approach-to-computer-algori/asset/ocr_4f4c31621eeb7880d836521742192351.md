Now suppose you store the same 1 million records in a B+tree using nodes of the same size in kilobytes. Because the B+tree stores only key values in the nodes, nodes may be able to hold far keys.

Suppose this B+tree can store up to 20 employee IDs in the same node space. (The actual value may be much larger, depending on the size of the employee records.) In that case, each node in the tree would have between 11 and 21 children, so log2(1,000,000) and log21(1,000,000), or between 5 and 6. To find an item, the program would need to search only six nodes at most and perform disk accesses at most, cutting the time roughly in half.

> Because B-trees provide fast times with few disk accesses, relational databases use them to implement indices.

# Summary

Like other sorted trees, balanced trees let a program store and find values quickly. By keeping themselves balanced, trees such as AVL trees, 2-3 trees, B-trees, and B+trees ensure they don't grow too tall and thin, which would ruin their performance.

Adding and removing values in a balanced tree takes longer than it does in an ordinary (nonbalanced) sorted tree. Those operations still take O(log N) time, however, the theoretical run time is the same even if the actual time is slightly longer. Spending that time lets the algorithm guarantee that those operations do not grow to linear time.

Chapter 8 describes hash tables, which store and retrieve values even more quickly than balanced trees do. However, hash tables do not allow some of the features, such as quickly displaying all the values in the data structure in sorted order.

This chapter and the preceding one describe generic trees that you build and traverse trees and balanced trees. The next chapter describes decision trees, which you can use to solve a wide variety of problems.
