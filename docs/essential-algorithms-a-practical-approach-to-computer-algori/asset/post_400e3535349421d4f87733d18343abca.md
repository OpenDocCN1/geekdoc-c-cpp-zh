## Branch and Bound

Branch and bound is a technique for searching trees more effectively than an exhaustive search. After it moves down a branch in the tree, the algorithm calculates the best possible outcome it can achieve in that branch. If the best possible outcome won't be an improvement over the best solution that has already been found, the algorithm abandons branch and doesn't continue its subtree. Depending on the specific data values, this can save a huge amount of time.

For example, suppose a partition problem algorithm keeps track of the current total weight in each of the two groups it is building and the total weight of the items that have not yet been assigned to a group. Now suppose the algorithm has reached a point where group 0 has a weight of 100, group 1 has a total weight of 50, and the unassigned items have a total weight of 20. Suppose also that the algorithm has already found a solution in which the two groups have weights differing by 20.

If we were to assign all the remaining items to group 1, group 0 would have a total of 100, and group 1 would have a total weight of 70, a difference of 30. But the algorithm has already found a solution in which the difference is only 20. The current test solution cannot be improved to make it better than the current best solution. In that case, the algorithm can stop working on its current solution without assigning the rest of the items.

The following pseudocode shows a high-level branch and bound algorithm for the optimization of the partition problem:

```
StartBranchAndBound() <Initialize best solution so it is replaced by the first test solution>
  BranchAndBound(0)
End StartBranchAndBound()

BranchAndBound(Integer: next_index)
  // See if <next_index > max_index>
  // We have assigned all items, so we are at a leaf node.
    <If the test solution is better than the best solution, save it>
  Else
    // We have not assigned all items, so we are not at a leaf node.

  If <test solution cannot be improved enough
    to beat the current best solution>
    Then Return

  <Assign item next_index to group 0>
  BranchAndBound(next_index + 1)
  <Unassign item next_index to group 0>

  <Assign item next_index to group 1>
  BranchAndBound(next_index + 1)
  <Unassign item next_index to group 1>
End If
BranchAndBound
```

This algorithm is similar to the exhaustive search algorithm, except that it determines if the test solution can be improved to beat the best solution, and it returns if it can't.

Branch and bound often trims branches and subtrees from the tree, so it can be much faster than exhaustive search. For example, in one test, while trying to divide 20 items exhaustive search visited 1097150 nodes, but branch and bound visited 74650 nodes. When both algorithms were allowed to use the “short circuit” to stop early, exhaustive search visited 4082 nodes, but branch and bound visited 98 nodes.

Branch and bound is a very useful technique, but I want to mention two important factors before moving on to heuristics. First, branch and bound avoids any path through the tree that might lead to a worse solution found so far. That means, unlike exhaustive search, it always finds the optimal solution.

The second important fact is that, although branch and bound avoids searching large parts of the tree, trees can be enormous, so branch and bound can still be slow. In one test, exhaustive search could search a tree for a 25-item problem in 6 seconds. Branch and bound could search the same tree in 2 seconds. That’s a big improvement, but adding one more item to the tree’s size makes branch and bound take about 4 seconds, and adding a second item made it 9 seconds. Branch and bound is much faster than exhaustive search, but it still isn't fast enough to search a tree like 40 items.

## Decision Heuristics

Exhaustive search and branch and bound find the best solution. Unfortunately, trees are so large that those algorithms work only for relatively small problems. To search larger trees, you need to use heuristics. A heuristic won’t necessarily find the best solution, but it might find a good solution—at least for optimization version where approximate solutions make sense.

The following sections describe heuristics for use with partition problem.

### Random Search

One of the simplest heuristics for searching a tree is to follow random paths through it. At each node, simply pick a branch to follow randomly. If you have enough random paths, you may stumble across a reasonably good solution. The following pseudocode shows how you might search a tree randomly:

```
RandomSearch()
  <Initialize best solution so it is replaced by the test solution>
  For i = 1 To num_trials
    For index = 0 To max_index
      <Randomly assign item number index to group 0 or 1>
    Next index
    // See if this solution is an improvement.
    //If the test solution is better than the best solution, save it>
  Next i
End RandomSearch
```

The algorithm starts by initializing the best solution as usual. It enters a loop that executes for some number of trials. For each trial, the algorithm loops over the indices of the items to be partitioned and randomly assigns each item to group 0 or 1. After it has randomly assigned every item to a group, the algorithm checks the solution to see if it is better than the best solution so far and, if it is, saves the new solution. If you are trying to partition N weights, each takes only N steps; this heuristic is extremely fast. That's good, because in a large tree, the odds of finding a good solution may be small, so you need to run a lot of trials. There are several ways to pick the number of trials—say, 1,000. That will work for small trees, but it might be better to pick a number that depends on the tree's size. Another strategy is to make the number of trials a polynomial function of the weights being partitioned. For example, if you are partitioning N weights, you could use num_trials = 3 × N³. The function 3 × N³ grows quickly as N increases, but not nearly as quickly as 2N, so this searches only a fraction of the tree.

Another approach is to continue running random paths until a certain number of random paths in a row fail to find an improvement. Then the algorithm won't stop as long as it's fairly easy to find improvements. Perhaps the ideal approach is to let the algorithm run continuously, updating its best solution when it finds improvements, until you stop it. If you don't need a solution in a hurry, you can let the algorithm run for hours or possibly even days.

### Improving Paths

You can make random path selection more effective if you pick a random path and then try to improve it. Start with a random path. Then randomly pick an item, and switch it from the group it is to the other group. If that improves the partitioning, keep that change. If the change doesn't help, undo it and try again. Repeat this many times until you can't improve the path anymore. This technique has many variations. For example, instead of swapping random items, try swapping each item at a time. You might want to repeat that several times, because swapping one item may change the weights of the two groups so that it is now possible to swap some other item that you could not swap before.

The following pseudocode shows this algorithm:

```
MakeImprovements()
  Initialize best solution so it is replaced by the test solution
  For i = 1 To num_trials
    // Make a random initial solution.
    For index = 0 To max_index
      <Randomly assign item number index to group 0 or 1>
    Next index

    // Try to improve the solution.
    Boolean: had_improvement = True
    While (had_improvement)
      // Assume this time we won't have any improvement.
      had_improvement = False

      // Try swapping items.
      For index = 0 To max_index
        <Swap item number into the other group>

        // See if this improves the test solution.
        If <this swap improves the test solution> Then
          had_improvement = True
        Else
          <Swap the item back>
        End If
      Next index
    End While
  Next i
```
