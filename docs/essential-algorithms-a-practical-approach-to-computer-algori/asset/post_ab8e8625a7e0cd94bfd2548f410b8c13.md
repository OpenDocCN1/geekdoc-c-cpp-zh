
## Chapter 18 Distributed Algorithms

For a concrete example, suppose processes A and B store the bank balances for customers A and B. Now suppose customer A wants to transfer $100 to customer B. Process A subtracts the money and sends a message to process B, while the message is in transit, you take a snapshot of the system. If you later restore the system from the snapshot, customer A has already sent the $100, but customer B has not received it, so the $100 is lost.(This would be a terrible way to manage bank accounts. If a network failure makes a message disappear, the money will also be lost. You need to use a more secure consensus protocol to make sure both processes agree that the message has been transferred.)

So to take a good snapshot of the system, you need to save not only each process's state, but also any messages that are traveling among the processes. The following steps describe a snapshot algorithm developed by K. Mani Chandy and Leslie Lamport:

- 1. Any process (called the observer) can start the snapshot process. To start a:
    a. The observer saves its own state.
    b. The observer sends a snapshot message to all other processes. The message contains the observer's address and a snapshot token that indicates which this is.
- 2. If a process receives a particular snapshot token for the first time:
    a. It sends the observer's saved state.
    b. It attaches a snapshot token to all subsequent messages that it sends to any other process.
- 3. Suppose process B receives the snapshot token and then later receives a message from process A that does not have the snapshot token attached. In that case, the message was in transit. It was sent before process A received the snapshot token, so it is not taken into account by process A's saved state. To make sure this information is not lost, process B receives a copy of the message to the observer.

After all the messages have finished flowing through the system, the observer has a record of every process's state and of any messages that were in transit when the snapshot was taken.

## Clock Synchronization

Exact clock synchronization can be tricky due to inconsistent message transmission times that occur in a shared network. The problem becomes much easier if processes communicate directly without using a network. For example, if computers are in the same room and you connect them with a wire, you can measure the wire's length, calculate the time it takes for a signal to travel across the wire, and you can use it to synchronize the computers' clocks.

This works, but it is cumbersome and may not be possible between computers that are far apart. Fortunately, you can synchronize two processes fairly by using a network if you assume that a network's message transmission time doesn't vary much over a short period of time.

Suppose you want process B to synchronize its clock to the clock used by process A. Call the time according to process A "true time". The following steps describe the messages processes should exchange:

- 1. A sends process B a message containing $T_{AI}$ (the current time according to process A).
- 2. B receives the message and sends process A a reply containing $T_{A1}$ and $T_{BI}$ (the current time according to process B).
- 3. A receives the reply and sends process B a new message containing $T_{A'}$, $T_{BI'}$ and $T_{A2}$ (the new current time according to process A).

Now B can perform some calculations to synchronize its clock with process A.
Suppose E is the error between the two clocks, $T_B = T_A + E$ at any given time. Also suppose D is the delay to send a message between the two processes.

When B records time $T_{BI'}$ the initial message time D to get from process A to process B, so:

```
$T_{B1} = (T_{AI} + E) + D
```

Similarly, when A records time $T_{A2}$ the reply time D to get from process B to process A,

```
$T_{A2} = (T_{BI} - E) + D
```

If you subtract the second equation from the first, you get:

```
$T_{BI} - T_{A2} = (T_{AI} + E + D) - (T_{BI} - E - D)$
$= T_{A1} - T_{BI} + 2 \times E$
```

Solving this equation for E gives:

```
$E = (2 \times T_{BI} - T_{A2} - T_{AI}) / 2
```

Now process B has an estimate of E, so it can adjust its clock accordingly. This algorithm assumes that the delay roughly constant during the time it takes to pass the messages back and forth. It also assumes that a message from A to B takes about the same amount of time as a message from B to A.

## Summary

This chapter has discussed issues that involve parallel processing. It explained some of the different models of parallel computation and described several algorithms that run in distributed systems. You may not need to use some of the esoteric algorithms, such as the zero-sort on a systolic array or the solution to the dining philosophers problem, but all these algorithms highlight some of the problems that can arise in distributed systems. These problems include such issues as race conditions, deadlock, consistency, and synchronization.

Distributed environments range from desktop and laptop computers with multiple cores that use hundreds of thousands of computers to attack a single problem. Even if Moore's Law holds for another decade or two, so much unused processing power is available that it makes sense to take advantage of it with distributed computing. To get the most out of today, you must be aware of these issues and how to solve them.
