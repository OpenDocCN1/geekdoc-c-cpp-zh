# Using Quicksort

If you divide the items in place instead of using stacks, quicksort doesn't use any extra storage (beyond a few variables).

Like heapsort, quicksort has O(N log N) expected performance, although quicksort can have O(N) performance in the worst case. Heapsort has O(N log N) performance in all cases, so it is in safer sense and more elegant. But in practice quicksort is usually faster than heapsort, so it is the algorithm for most programmers. It is also the algorithm that is used in most libraries. (The Java library uses mergesort, at least sometimes. The following section provides more information about mergesort, and the “Stable Sorting” sidebar in that has information about why Java uses mergesort.)

In addition to greater speed, quicksort has advantage over heapsort: it is parallelizable. Suppose a computer has more than one processor, which is increasingly the case these days. Each time the algorithm splits a section of the array into two pieces, it can make different processors sort the two pieces. Theoretically a highly parallel computer could use O(N) processors to sort the list in log(N) time. In practice, most computers have a fairly limited number of processors (for example, two or four), so the run time would be divided by the number of processors, plus some additional overhead to manage the different threads of execution. That won't change the Big O run time, but it should improve performance in practice.

Because it has O(N²) performance in the worst case, the implementation of quicksort provided by a library may be cryptographically insecure. If the algorithm uses a simple item selection strategy, such as picking the first item, an attacker might be able to create an array holding items in an order that gives worst-case performance. The attacker might be to launch a denial-of-service (DOS) attack by passing your program that array and ruining your performance. Most programmers don't worry about this possibility, but if this is a concern, you can use a randomized item selection strategy.

# Mergesort

Like quicksort, mergesort uses a divide-and-conquer strategy. Instead of picking a dividing item and splitting the items into two groups holding items that are larger and smaller than the dividing item, mergesort splits the items into two halves of equal size. It then recursively calls itself to sort the halves. The algorithm merges the two sorted halves into a combined sorted list.

The following pseudocode shows the algorithm:

```
Mergesort(Data: values[], Data: scratch[], Integer: start, Integer: end)
// If the array contains only one item, it is already sorted.
If (start == end) Then Return
```

```
// Break the array into left and right halves.
midpoint = (start + end) / 2
```

```
// Call Mergesort to sort the two halves.
Mergesort(values, scratch, midpoint)
Mergesort(values, scratch, midpoint + 1, end)
```

```
// Merge the two sorted halves.
Integer: left_index = start
right_index = midpoint + 1
Integer: scratch_index = left_index
While ((left_index < midpoint) and (right_index <= end)) Then
If (values[left_index] < values[right_index]) Then
scratch[scratch_index] = values[left_index]
left_index = left_index + 1
```

```
Else
scratch[scratch_index] = values[right_index]
right_index = right_index + 1
```

```
End If
scratch_index = scratch_index + 1
End While
```

```
// Finish copying whichever half is not empty.
For i = left_index to midpoint
scratch[scratch_index] = values[i]
scratch_index = scratch_index + 1
```

Next i
For i = right_index to end
scratch[scratch_index] = values[i]
scratch_index = scratch_index + 1
```

Next i
```

```
// Copy the values back into the original values array.
For i = start to end
```

values[i] = scratch[i]
Next i
End Mergesort
```

In addition to the array to sort the start and end indices to sort, the algorithm also takes as a parameter scratch array that it uses to merge the sorted halves.

This algorithm starts checking whether the section of the array contains one or fewer items. If it does, it is trivially sorted, the algorithm returns.

If the section of the array contains at least two items, the algorithm calculates the index of the item in the middle of the section of the array and recursively calls itself to sort the two halves.

Next the algorithm merges the sorted halves. It loops through the halves, copying the smaller item from whichever half holds it into the scratch array. When one half is empty, the algorithm copies the remaining items from the other half.

Finally, the algorithm copies the merged items from the scratch array back into the original array.

> NOTE It is possible to merge sorted halves without using a scratch array, but it's more complicated and slower, so most programmers use a scratch array.

The “call tree” shown in Figure 6-11 shows to quicksort when the array are perfectly balanced, so the algorithm divides the items into equal halves at every step. The mergesort algorithm does divide the items into equal halves at every step, so Figure 6-11 applies more to the mergesort algorithm than it does to quicksort.

The run time analysis shown earlier for quicksort also works for mergesort, so this algorithm has O(N log N) run time. Like heapsort, mergesort’s run time does not depend on the initial arrangement of the items, so it always has O(N log N) run time and doesn't have a disastrous worst case like quicksort.

Like quicksort, mergesort is parallelizable. When a call to mergesort calls itself recursively, one can make one of calls on another processor. This requires some coordination, however, because the original call must wait until recursive calls finish before it can merge their results. In contrast, quicksort can simply tell its recursive calls to sort a particular part.

Mergesort is particularly useful when data isn't in memory. For example, a customer record might occupy 1 MB, but the customer's name might occupy only 100 bytes. Then, if you have 1 million customers, sorting them requires only 100 MB of memory, and an amount that could reasonably hold.

The mergesort algorithm, however, doesn't need to look at any of the items in the array. Mergesort was more useful in the days when large data sets were stored on tape drives. Specialized versions of mergesort were even more efficient for tape drives. They're interesting but not commonly used, so they aren't described here.

> Sorting

A stable sorting algorithm is one that maintains the original positioning of equivalent values. For example, suppose a program is sorting Car objects by their Cost and Car objects A and B have the same Cost values. If object A initially comes before B in the array, then in a stable sorting algorithm, A still stays before B in the sorted array.

If the items are sorting value types such as integers, dates, or strings, then two entries with the same values are equivalent, so it doesn't matter if the sort is stable. For example, if the array contains two entries have value 47, it doesn't match 47 comes first in the sorted array.

In contrast, if Car objects are rearranged unnecessarily, a stable sort lets you sort the array times to get a result that is sorted on multiple keys (such as Maker and Cost for the Car example).

Mergesort is easy to implement as a stable sort (the algorithm described earlier-is stable), so it is used by Java's Arrays.sort library method.

Mergesort is also easy to parallelize, so may be useful on computers that have more than one CPU. See Chapter 18 for information on implementing merge-sort on multiple CPUs.

Quicksort may be faster, but mergesort still has some advantages.
