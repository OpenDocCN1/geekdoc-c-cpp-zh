### KnightsTour

This algorithm takes as parameters the row and column where the knight should move next, an array named move_number which gives the number of the move when the knight visited each square, and the number of moves made so far.

The algorithm starts by recording the knight's move to the current square and incrementing the number of moves made. If the number of moves made is 64, the knight has finished a tour of the board, the algorithm returns true to indicate success.

If the tour is not finished, the algorithm initializes two arrays to represent the moves that are from the current square. For example, the first entries in the arrays are -2 and -1, indicating that the knight can move from square (row, col) to row-2, col-1 if that square is on the board.

The next algorithm loops through all the possible moves from the position (row, col). If a move is on the board and has not already been visited in the test tour, the algorithm makes the move and recursively calls itself to see if it leads to a full solution.

If none of the possible moves from the current position leads to a solution, the algorithm sets move_number[row, col] = 0 to undo the current move and returns false to indicate that the knight can move to the square (row, col) does not lead to a solution.

Unfortunately, the knight's problem isn't easy to constrain as the queens problem. With the queens under attack by another queen it's fairly easy to tell whether a new position is and therefore unavailable for a new queen. In that case you can eliminate position from consideration.

In the knight's tour, any position the knight can reach that has not yet been visited gives new test solution. There may be some cases where you can easily conclude that a test won't work, such as if the board has an unvisited square that is not one move away from any other unvisited square, and recognizing that situation is difficult.

The fact that it's hard to eliminate solutions early on the algorithm often follows a test solution for a while before discovering that the solution is infeasible. A knight can have up to eight legal moves, so an upper bound on the number of potential tours is $8^{64}$, or roughly $6.3 \times 10^{57}$. You can study the positions on the board to get a better estimate of the potential number of tours (for example, a knight in a corner has only two possible moves), but the total number of potential tours it's an enormous number in any case.

All this means it's difficult to solve the knight's tour for a normal $8 \times 8$ chessboard. In one set of tests, a program solved the problem on a $6 \times 6$ board almost instantly and on a $7 \times 7$ board in about 2 seconds. It still hadn't found a solution on a $7 \times 7$ board after an hour.

Although solving the knight's tour using only backtracking is difficult, a heuristic solves the problem quite well. A *heuristic* is an algorithm that produces a good result but that is not guaranteed to produce the best possible result. For example, a driving heuristic might add to 10 percent more than expected travel time to allow for traffic delays. Doing so doesn't guarantee you'll be on time, but it increases the chances.

In 1823 C. C. von Warnsdorf suggested a knight's tour in which at each step the algorithm should select the next possible move that has the lowest number of possible moves out of it.

For example, suppose the knight is in a position where it has only two possible moves for its next move. If the knight makes the first move, it has only one possible move for its next move. In that case, the heuristic says the algorithm should try the second move first.

This heuristic is so good that it completes a tour with no backtracking for boards of size up to $75 \times 75$. (In my test, the program found a solution on a $57 \times 58$ board almost instantly and then crashed with a stack overflow on a $58 \times 58$ board.).

### Selections or combination and Permutations

A selection or combination is a subset of a set of objects. For example, in the set $[A, B, C]$, the subset $[A, B]$ is a selection. All the selections for the set $[A, B, C]$ are $[A, B]$, $[A]$, and $[B, C]$. In a selection, the order of the items doesn't matter so $[A, B]$ is considered the same as $[B, A]$. You can think of this as being similar to menu selection at a restaurant. Selecting a cheese sandwich and milk is similar to selecting milk and cheese sandwich.

A permutation is an ordered arrangement of subset taken from a set. This is similar to selection except that the ordering matters. For example, $(A, B)$ and $(B, A)$ are permutations of two items taken from the set $[A, B]$. All the permutations of two items taken from set $[A, B, C]$ are $(A, B)$, $(A, C)$, $(B, A)$, $(B, C)$, $(C, A)$, and $(C, B)$. (Notice the notation uses brackets $[]$ for selections and parentheses $)$ for permutations.)

One other factor determines which groups of items are included in a particular selection or permutation: whether duplicates are allowed. For example, two-item selections for the set $[A, B, C]$ allowing duplicates are $[A, A]$, $[B, B]$, and $[C, C]$, in addition to the other selections listed earlier. The special case of permutation takes all the items in the set and doesn't allow duplicates: all arrangements of the set $[A, B, C]$ are $(A, B)$, $(A, C)$, $(B, A)$, $(B, C)$, $(C, A)$, and $(C, B)$. Many people think of the permutations of a set to be this collection of arrangements rather than the more general case in which you may not take all the items from the set and may allow duplicates. The following sections describe algorithms you can use to generate selections and permutations without duplicates:

### Selections with Loops

If you know how many items you want to select from a set when you are writing a program, you can use a series of Loops to easily generate combinations. For example, the following pseudocode generates all selections of three items from a set of five items allowing duplicates:

```
// Generate selections of 3 items allowing duplicates.
List<string>: SelectWithDuplicates(List<string> items)
List<string>: results = New List<string>
For i = 0 To <Maximum index in items>
  For j = i To <Maximum index in items>
    For k = j To <Maximum index in items>
      results.Add(items[i] + items[j] + items[k])
    Next k
  Next j
Next i
Return results
```

This algorithm takes a list of Strings. It then uses For loops to select the letters that make each selection. Each loop starts with the current value of the previous loop's counter. For example, the second loop starts with $j$ equal to $i$. That means the second letter chosen for the selection will come before the first letter in the items. For example, if the items are the letters A, B, C, D, and E, and the first letter in the selection is C, the second letter will be A or B. That keeps the letters in the selection in alphabetical order and prevents the algorithm from selecting both $[A, B, C]$ and $[A, C, B]$, which are the same set. Within the innermost loop, the algorithm combines the items selected by each loop variable to produce an output that includes all selections.

Modifying this algorithm to prevent duplicates is simple. Just start each loop at the value 1 greater than the current value in the next loop. The following pseudocode shows this modification:

```
// Generate selections of 3 items without allowing duplicates.
List<string>: Select3WithoutDuplicates(List<string> items)
List<string> results = new List<string>()
For i = 0 To <Maximum index in items>
  For j = i + 1 To <Maximum index in items>
    For k = j + 1 To <Maximum index in items>
      results.Add(items[i] + items[j] + items[k])
  Next k
Next j
Next i
Return results
```

This time each loop starts at 1 greater than the previous loop's current value, so a loop cannot select the same item as a previous loop, and that prevents duplicates. The sidebar "Counting Combinations" earlier in this chapter explains how you can calculate the number of possible selections for a given set and number of items to select.

### Selections with Duplicates

The problem with the algorithms described in the preceding section is that they require you to know how many items you select when you write the code, and sometimes that may not be the case. If you don't know how many items are in the original set of items, the program can figure that out. However, if you don't know how many items to select, you cannot program the right number of loops.

You can solve this problem recursively. Each recursive call to the algorithm is responsible for adding a single selection to the result. If the result doesn't include enough selections, the algorithm calls itself recursively to make more. When the selection is complete, the algorithm does something with it, such as printing the list of items selected.
