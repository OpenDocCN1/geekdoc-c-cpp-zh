For this example, where processes are performing Hamiltonian path heuristics, a process shouldn't compare every test it finds with the shared best solution. Instead, it should keep track of the best solution it has found and compare it to the shared solution only when it finds an improvement on its best solution.

When it acquire the mutex, a process can also update its private best route length, so it has a shorter total length to use for comparison. For example, suppose process A finds a new best route with a length of 90. It acquires the mutex and finds that the best route length is 80 (because process B found a route with length). At this point process A should update its private route length to 80. It doesn't need to know what the best route is; it needs to know that only routes with lengths of less than 80 are interesting.

You can acquire a mutex incorrectly in several ways:

- Acquiring a mutex and not releasing
- Releasing a mutex that was never acquired
- Holding a mutex for a long time
- Using a resource without acquiring the mutex

Other problems can arise if you use mutexes correctly:

- Priority inversion—A high-priority process is stuck waiting for a low-priority process that has the mutex. In this case, it might be nice to remove the mutex from the lower-priority process and give it to the higher-priority process. That would mean the lower-priority process would need to be able to somehow undo any unfinished changes it was making and then later acquire the mutex again. An alternative strategy is to make each process the mutex for the smallest time possible so that the higher-priority process isn't blocked for very long.
- Starvation—A process cannot get the resources it needs to finish. Sometimes this occurs when the operating system tries to solve the priority inversion problem. If a high-priority process keeps the CPU busy, a lower-priority process might never get a chance to run, so it will never finish.
- Deadlock—Two processes are stuck waiting for each other.

The next section discusses deadlocks in greater detail.

## Deadlock

In a deadlock, two processes block each other while each waits for a mutex held by the other.

For example, suppose processes A and B both need two resources that are controlled by mutex 1 and mutex 2. Then process A acquires mutex 1, and process B acquires mutex 2. Now process A waits for mutex 2. Both processes are blocked, so neither can release the mutex it already holds to release the other process.

One way to prevent deadlocks is to agree that every process will acquire mutexes in order (assuming the mutexes are numbered). In the previous example, both processes A and B try to acquire mutex 1. One of the processes succeeds, the other is blocked. Whichever process successfully acquired mutex 1 when it finishes, it releases it, and then the other process can acquire it.

The problem is more difficult in a complex environment such as an operating system, where dozens or hundreds of processes are competing for shared resources, and no clear order for requesting mutexes has been defined. The ‘dining philosophers’ problem described later in this chapter is a special instance of a deadlock problem.

## Quantum Computing

A quantum computer uses quantum effects such as entanglement (multiple particles remain in the same state if they are separated) and superposition (a particle exists in multiple states simultaneously) to manipulate data.

Currently quantum computing is in its infancy. Very few laboratories can build and run a small quantum computer with only a few qubits (qubits, the basic unit of information in a quantum computer). So far quantum computers have been able to use Shor’s algorithm to find the number 15 and the number 21. With such results, it’s probably a bit early to start planning quantum algorithms in your programs.

All advanced technology starts with these sorts of proof-of-concept demonstrations, and there’s a chance that quantum computers may eventually become commonplace. In that case, manufacturers may someday be able to build truly nondeterministic and probabilistic computers that can solve problems in NP exactly.

For example, Shor’s algorithm can factor numbers in O(log N³) time, where N is the size of the input number. This is much faster than the fastest-known algorithm, the general number sieve, which runs in subexponential time. (It’s slower than any polynomial time but faster than exponential.)

Quantum computing is very confusing, so this book doesn’t cover it further. Fortunately, it will be several years before you will need to write your own algorithms for quantum computers.

## Distributed Algorithms

Some of the parallelism described in the previous sections are somewhat scarce. Very few home or business computers contain syntactic arrays (although I could see a case for building a chip to perform zero-time sorting). It may be decades before quantum computers appear in computer stores—if they ever.

However, distributed computing is widely available. Large grid projects use tens or hundreds of thousands of computers to apply massive computing to complex problems. Smaller networked clusters let dozens of computers work together. Most desktop and laptop systems today contain multiple cores.

Some of these rely on fast communication between cores on a single chip, and others anticipate slow, unreliable network connections, but all these cases use distributed algorithms.

The next two sections discuss general issues that face distributed algorithms: debugging and identifying embarrassing parallel problems.

The sections after describe some of the most interesting classical distributed algorithms. Some of these seem more like IQ tests or riddles than practical algorithms, but they are useful for a couple of reasons. First, they highlight some the issues that affect distributed systems. They demonstrate ways to build about problems that encourage you to look for potential trouble spots in distributed algorithms.

Second, these algorithms are actually implemented in real-world scenarios. In many applications, it doesn't matter much if one of set of processes fails. If a grid computing process doesn't return a value, you can simply assign it to another computer and carry on. However, if a set of processors is controlling a patient's life-support systems, a large passenger plane, or a billion-dollar spacecraft, it may need the extra effort to ensure that the processes reach the correct decision, even if one of them produce incorrect results.

## Debugging Distributed Algorithms

Because events in different CPUs can occur in any order, debugging distributed algorithms can be very difficult. For example, consider the Hamiltonian path example described earlier. A race condition occurs only if the events in processes A and B happen in the exact right sequence. If the two processes don't update the shared best solution too frequently, the chance of they updating the solution at the same time is small.

Even if you have good logs, each process could perform millions of steps over hours before a problem arises. Even if a problem does occur, you may not notice it. Some debuggers let you examine variables use by multiple processes at the same time. Unfortunately, by pausing the processes to examine variables, you interrupt the timing that might cause an error.

Another approach is to make the processes write information about what they are doing in a file or terminal so that you can examine it later. If the processes needs to write into the file frequently, they probably use separate files so that they do not fight over access to the file. In that case, they should also write timestamps into the file so you can figure out the order.

Possibly best for debugging distributed algorithms is to avoid bugs in the first place. Think carefully about the critical sections of code where multiple processes interfere with each other, and then use mutexes to prevent trouble.

When you write an application, you add code to frequently check any shared variables to see if they contain correct values. After you've tested the code and run it reliably, you can comment out the value-checking code to get better performance.

## Embaringly Parallel Algorithms

An embarrassingly parallel algorithm is one that naturally breaks into pieces that can be easily solved by separate processes. They require little communication among processes and ideally work to combine results from different processes. Here are some embarrassingly parallel problems:

- Ray tracing is a computer graphics technique that traces a ray from a point of view into a scene to see which objects it strikes. A ray can travel through transparent objects and bounce off reflective objects. The reason is that each is an embarrassingly parallel problem is that the calculations needed for each are independent, so you can easily divide them among multiple processors. If you have 10 processors, you can split up the image and make each processor generate one-tenth of the image. Each processor needs to know the scene's geometry, but it doesn't need to know what calculations the other processors are performing. Each process writes its results into different parts of the image, so they may not need mutexes to access shared memory.
- Fractals—Many fractals, such as the Mandelbrot set, require a program to perform a long series of calculations for each pixel in the resulting image. In ray tracing, the calculations for each pixel are completely separate, so it is easy to divide the problem among as many processors.
