If it cannot be emulated, then the emulator must pass it on to the original handler using the vector that was stored when the emulator was installed. When a chain of emulators is exhausted, no further processing of the instruction can take place and the undefined instruction handler should report an error and quit.

### Prefetch Abort Handler

When the system does not contain any MMU, Prefetch Abort handlers are used. These handlers simply report the error and quit. Otherwise, the address that caused the Prefetch Abort must be restored into the physical memory. The virtual memory fault for that address can be dealt with the instruction fetch retried. The handler should therefore be returned to the same instruction rather than the following one.

### Data Abort Handler

In case there is no MMU in the system, the data abort handler should report the error and return. If there is an MMU in the system, then the handler should deal with the virtual memory fault. Three types of instructions cause an abort: Single Register Load or Store, Swap, and Load/Store Multiple.

For the Single Register Load or Store instruction, the response can depend on the type of the ARM processor. If it is an ARM6 processor, then an abort can take place. If the processor is in early abort mode and write-back was requested, then the address register will not be updated. Abort can also happen if the processor is in late abort mode and write-back was requested. In that case, the address register will be updated and the changes must be undone. For an ARM7-based processor, if the abort takes place, then the address register will be updated and the changes must be undone. For processors, such as ARM9TDMI, the address is restored by the processor to the value it had before the instruction started.

For the Swap instruction, no address register update is involved.

For the Load/Store Multiple instruction, the response depends on the processor type. If the processor type is ARM6 or ARM7 and write-back was enabled, then the base register will be updated as if the whole transfer had taken place. For processors, such as ARM9TDMI, the base register will be restored to the value it had before the instruction started.

In each of the three instructions, the MMU can load the required virtual memory into physical memory. The MMU Fault Address Register (FAR) contains the address that caused the abort. When this is done, the handler can return and try to execute the instruction again.

## Chapter 7

A preprocessor is a program that processes its input data to produce an output. Other programs, such as compilers, use this output as their input. In the C language, a preprocessor processes a source code before it is passed to the compiler. The kind of processing done depends on the nature of the source processor. Some preprocessors are capable of performing relatively simple textual substitutions and macro expansions; whereas, some preprocessors have the power of full-fledged programming languages.

In this chapter, we first learn about the role of preprocessor while compiling a source code in C. After that, the chapter discusses various preprocessor directives in C, such as #define, #ifdef, #endif, #pragma, #error, and #line.

Several stages are involved from writing a native C code and executing it on a platform; therefore, let's get a brief overview about them in the next section.

## Stages of Compilation

In C, a source code passes through various stages before it becomes ready for the execution. Generally, a source code is written in a file with the ".c" extension. When the source code is passed to a C preprocessor, it converts the code into an expanded source code, which gets stored in a file with the ".i" extension. Then, the expanded source code is compiled and an object code is generated. The object code is stored in a file with the ".obj" extension. This object code is linked with the object code of the library functions that are used in the source code. The result of this linking is the executable code that gets stored in a file with the ".exe" extension. Figure 7.1 shows the stages of compilation:

## Preprocessor Directives

In the C language, a preprocessor consists of several directives that are considered as another set of language within C. Each preprocessor directive begins with the # symbol. Preprocessor directives can be placed anywhere in the C code; however, they are preferably placed at the beginning of the code.

In C, preprocessor directives can be categorized as follows:

- Macro definition
- File inclusion
- Conditional compilation
- Miscellaneous directives

Let's discuss them in detail, one by one.

### Macro Definition

A macro definition replaces all the macros in a source code with the specified macro expansion. Consider the following statement:

```c
#define LENGTH 50
```

In the preceding statement, LENGTH is the macro. Before the compilation of the source code begins, the source code is passed to the preprocessor, which checks for any macro within it. Wherever a macro (in our case, LENGTH) is found in the source code, the preprocessor replaces the macro with the appropriate macro expansion (in our case, 50). Macro expansion means replacing a macro with the specified chunk of code. After all the macros are replaced, the source code is compiled. Listing 7.1 describes the basic working principle of a macro in C:

**Listing 7.1: Showing the Basic Working Principle of a Macro**

```c
#include<stdio.h>
#define LENGTH 50
int main()
{
        int temp = 10;
        printf("\n Sum of the variables is %d ",temp + LENGTH);
        getch();
        return 0;
}
```

In Listing 7.1, the preprocessor checks the source code for the #define directive, which defines constants and macro substitutions. As a standard programming practice, all the macros should be written in capital letters. A macro and its expansion are always separated by a blank space. Note that a macro definition is never terminated by a semicolon.

The output of the preceding program is given as follows:

```text
    Sum of the variables is 60
```
