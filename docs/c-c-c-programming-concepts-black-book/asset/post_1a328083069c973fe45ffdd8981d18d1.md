
The preceding program shows that in case a thread tries to lock a mutex variable, which is already locked, it continuously loops checking whether the lock is released or not. This results in huge CPU cycles wasted, which could have been avoided using conditional variables.

Now, let’s learn about conditional variables.

## Conditional Variables

A conditional variable is a thread synchronization mechanism. Typically, a conditional variable is used in scenarios where a thread remains blocked until a condition is satisfied. The value of the condition is usually set by another thread. A thread may wait on a conditional variable. If thread A waits on a conditional variable, it is blocked until some other thread, say thread B, signals the same conditional variable. Thread A must wait on the conditional variable prior to thread B signaling it. If thread B signals the conditional variable before thread A waits on it, the signal is lost. Note that conditional variable is not a counter.

A conditional variable is represented by an instance of `pthread_cond_t`. The following statement defines a conditional variable:

```c
pthread_cond_t cv;
```

Each conditional variable should be accompanied by a mutex. We can initialize a conditional variable by using the following API:

```c
pthread_cond_init(&cv, NULL);
```

The basic usage of the conditional variables is as follows:

- To signal a conditional variable, the following APIs can be used:
  1. **pthread_cond_signal(&cv)**—If one or more threads are waiting on the conditional variable, then one of the threads will be unlocked. If no thread is waiting on the conditional variable at that moment, then the signal will be ignored.
  2. **pthread_cond_broadcast(&cv)**—It unblocks all the threads that are waiting on the conditional variable.

- To wait on a conditional variable, the `pthread_cond_wait(&cv, &mutex)` API can be used. The API blocks the calling thread until the conditional variable is signaled. When the `pthread_cond_wait()` API is called, the mutex must already be locked. The call unlocks the mutex and blocks on the conditional variable in a single atomic operation. When the conditional variable is signaled, the calling thread unblocks and a lock on the mutex is atomically acquired.

- To destroy a conditional variable, the `pthread_cond_destroy(&cv)` API can be used.

Perform the following steps in case the code is changing the sense of the condition protected by a conditional variable:

1. Lock the mutex accompanying the conditional variable.
2. Take the action that may change the sense of the condition (for example, set the flag).
3. Signal or broadcast the conditional variable, depending on the desired behavior.
4. Unlock the mutex accompanying the conditional variable.

The following program illustrates the concept of conditional variables:

```c
#include <stdio.h>
#include <stdlib.h>
#include <pthread.h>
int continue_flag;
pthread_mutex_t continue_flag_mutex;
pthread_cond_t continue_flag_cv;
void do_work ()
{
    fprintf(stdout, "\nworker thread: working..."); fflush(stdout);
}
void* worker_thread_function(void *arg)
{
    while (1) {
        pthread_mutex_lock(&continue_flag_mutex);
        while (!continue_flag) {
            pthread_cond_wait(&continue_flag_cv, &continue_flag_mutex);
        }
        do_work();
        pthread_mutex_unlock(&continue_flag_mutex);
    }
}
int
main()
{
    pthread_t               worker_thread;
    int                     res = 0;

    continue_flag = 0;
    pthread_mutex_init(&continue_flag_mutex, NULL);
    pthread_cond_init(&continue_flag_cv, NULL);

    res = pthread_create(&worker_thread, NULL, worker_thread_function, NULL);
    if (res != 0) {
        fprintf(stderr, "\nthread creation failed\n");
        return 1;
    }
    while (1) {
        pthread_mutex_lock(&continue_flag_mutex);
        continue_flag = 1;
        pthread_cond_signal(&continue_flag_cv);
        pthread_mutex_unlock(&continue_flag_mutex);
        fprintf(stdout, "\nmain thread: Start work\n"); fflush(stdout);
        sleep(2);
        pthread_mutex_lock(&continue_flag_mutex);
        continue_flag = 0;
        pthread_mutex_unlock(&continue_flag_mutex);
        fprintf(stdout, "\nmain thread: Stop work\n"); fflush(stdout);
        sleep(3);
    }
    fprintf(stdout, "\nwaiting for thread to finish...\n");
    res = pthread_join(worker_thread, NULL);
    if (res != 0) {
        fprintf(stderr, "\nthread join failed\n");
        return 0;
    }
    fprintf(stdout, "\nthread joined. \n");
    pthread_mutex_destroy(&continue_flag_mutex);
    return 0;
}
```

In the preceding program, instead of using a mutex, we have used the conditional variables to avoid the wastage of CPU cycles.

## Deadlocks

Deadlocks can arise if two or more threads share a common set of resources and try to lock the resources in some order and wait for them indefinitely. This kind of deadlock situation happens when two or more competing threads are waiting for each other to finish; and therefore, they keep on waiting for each other indefinitely. Deadlocks are very common in multithreading systems, where both the software and hardware locks are used to handle shared resources and implement synchronization. Consider the following example, which will lead to a deadlock:

| Thread 1 | Thread 2 |
| --- | --- |
| Lock (A) | Lock(B) |
| Lock (B) | Lock(A) |
| ... | ... |

In the preceding example, we have defined two threads – Thread 1 and Thread 2. Note that both the threads are sharing the same data space. Now, we have two variables, A and B, which are common to both the threads. In the execution path, Thread 1 locks the variable A and waits to lock the variable B. On the other hand, Thread 2 executing in parallel, locks the variable B first and then intends to lock the variable A, which is currently locked by Thread 1. This implies that both Thread 1 and Thread 2 wait for the resources A and B, which are currently locked by the other thread; therefore, both the threads are in a deadlock situation. In other words, both Thread 1 and Thread 2 wait for an event, `unlock()`, which is never going to happen.

Therefore, while writing the codes for multithreading-enabled programs, we should ensure that all the threads acquire the locks in the same order. That is, if Thread 1 locks A first and then locks B, then all the other threads performing the similar operation should also lock A before locking B.
