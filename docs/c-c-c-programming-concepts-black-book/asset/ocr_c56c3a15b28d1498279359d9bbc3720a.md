# # Interrupt Handlers

Two types of communication can occur between a CPU and the rest of the hardware. In the first type, the CPU can make a request to the hardware. In the second type, the hardware sends a request to the CPU for immediate processing. The second type of communication is known as interrupts. In Linux, hardware interrupts are called Interrupt Requests (IRQs). The two types of IRQs are as follows:

+   - **Short IRQ**—Takes shorter time to service the request. During this phase, the machine will be in the blocked state with no other interrupts being handled.
+   - **Long IRQ**—Takes longer time to service the request, but other interrupts may occur. It is always recommended to define a long IRQ.

If the CPU receives an interrupt, it stops its current task, saves the runtime parameters, registers the variables on the stack, and calls the interrupt handler. If the CPU is processing some important task, which cannot be aborted or stopped, then the similar set of activities is done once the current task completes its execution. This implies that the interrupt handler does not even allow certain things while the system receives the interrupt request because it is in the unknown state. The only available solution to this problem is to complete the current task execution, schedule the handling of the new interrupt request later (this is called the bottom half), and then return. The kernel then call the bottom half as soon as possible to process the pending interrupt request. To implement this, we need to call `request_irq()` to get the interrupt handler called when the relevant IRQ is received. This function generally receives the IRQ number, the name of the function, flags, a name for `/proc/interrupts`, and a parameter to pass to the interrupt handler. The flags can include `SA_SHIRQ`, which shares the IRQ with other interrupt handlers, or `SA_INTERRUPT`, which is a fast interrupt. The function will succeed if and only if a handler does not already exist on the IRQ. We can start processing the request by communicating with the hardware and use `queue_work()` and `mark_bh(BH_IMMEDIATE)` to schedule the bottom half from the interrupt handler.
