
Figure 16.5 shows the hierarchical tree view of the types in .NET Framework:

**Figure 16.5: Showing the Hierarchical Tree View of Types**

CTS also states the rules for the visibility and scope of the members of a type. Following is a list of access restrictions that can be applied to a type:

- **Public** → A type with the public access can be used in any code in any assembly.
- **Private** → A type with the private access can be used in the method where it is defined.
- **Family or Protected** → A type with the protected access can be called by any inherited types, regardless of the fact that whether they are within the same assembly or not.
- **Assembly or Internal** → A type with the internal access can be called by any types defined within the assembly it belongs to.
- **Family or Assembly/Protected Internal** → A type with the protected internal access can be called by derived types in any assembly and any types in the same assembly.

CTS specifies one more rule, which states that a type must be inherited from a predefined type known as System.Object. Object is the name of the type defined in the System namespace. Therefore, it is the root of all the other types; and thereby, holds the minimum set of behavior. All other types, such as integer, character, or class, are derived from the Object class. The System.Object type allows us to do the following:

- Compare two instances to check equality
- Enquire the true type of the instance
- Perform a shallow copy of the instance
- Contain the hash code of the instance
- Obtain the current state of the object in a string

Next, we learn about CLS that has been defined based on the CTS.

## CLS

CLS allows different languages to be implemented in a single application in .NET environment. This is done with the help of the CLR. However, different languages have their own set of rules. For example, one language implements case sensitivity, while the other language does not impose case sensitivity. On the other hand, one language supported by .NET platform supports operator overloading, while some other language supported by .NET platform does not support operator overloading. These dissimilarities among the languages forced the Microsoft developers to define a minimum set of specifications that must be supported by the compiler. These specifications are known as CLS. Therefore, CLS represents a minimum set of features that a language commonly supports. Figure 16.6 shows the relationship between CLS and CLR/CTS:

![](img/43c5f409f9b17790a628c4b4df854b61_512_0.png)

In Figure 16.6, we can observe that CLS is a subset of CLR and CLR/CTS contains a larger set of features than CLS. In addition, CLS consists of the common features of the Fortran, VB, and C# languages (there are a lot of other languages also). Most of the languages, such as VB, Fortran, and C#, contain the CLR features. However, those who are not interested about language interoperability can directly utilize the features of the CLR/CTS. In case we want to use the language interoperability, we can define a very rich set of functions, which is specific to the language itself. Therefore, to provide the language interoperability, CTS has been delivered to the vendor to develop the compiler that should at least support the features mentioned in the CLS. Consider an example of Java and VB.NET languages. After writing a piece of code for adding two integers in Java and VB.NET, Integer in VB.NET and int in Java are both converted to Int32 by following the CLS, as shown in Figure 16.7:

![](img/43c5f409f9b17790a628c4b4df854b61_512_1.png)

According to CLS, following are some of the rules that the languages should at least follow to generate MSIL or CIL:

- Data type size should be fixed; for example, int should be of 32 bit and character should be of 8 bit
- Common data types should be used

## Assemblies in C#

The term assembly has been around for a decade, but the definition of assembly in the context of .NET architecture is somewhat different. An assembly represents an executable file (.exe or .dll) that is executed at the end of the compilation. It can also be defined as the building block of the .NET architecture; the fundamental unit that provides deployment, version control, reuse, and security permissions; or a collection of types and resources that are built to work together and form a logical unit of functionality.

Figure 16.8 shows the assembly and its various components:

![](img/43c5f409f9b17790a628c4b4df854b61_513_0.png)

**Figure 16.8: Displaying the Overview of Assembly**

CLR first converts the C# code into the Intermediate Language (IL). This IL contains the managed IL code as well as the metadata. The metadata helps in the execution of the managed IL code. Assembly contains this managed IL code and passes the code for the execution to the CPU.

As shown in Figure 16.8, an assembly contains the following components:

- Assembly manifest
- Type metadata
- CIL/MSIL code
- Resource files

Let's first learn about the assembly manifest and its significance in assembly.

### Assembly Manifest

To execute a file, every assembly should keep a record of how the elements in the assembly are related to each other. This can be known from the metadata. Assembly manifest contains the metadata that specifies the versioning of the assembly and the security identity. Other than this, metadata contains the information related to the scope of the assembly as well as the reference to the classes and resource files. The assembly manifest is stored either in an .exe or .dll file (commonly known as PE file) along with the MSIL/CIL code or in a separate standalone file that contains only the assembly metadata.

Now let's learn how to view the assembly manifest and its components. For this, consider a small C# code that adds two constants and displays the value in the console, as shown in Listing 16.1:

**Listing 16.1: Showing the C# Code of Example.exe**

```
    using System;
    class Program
    {
        public const int a = 10;
        public const int b = 20;
        public static void Main()
        {
            Console.WriteLine("The result is : {0}", a + b);
        }
    }
```

To view the assembly manifest content, we need to type the ildasm <exe file name> command in the Visual Studio 2008 console. In our case, we have typed ildasm Example.exe, as shown in Figure 16.9:

![](img/43c5f409f9b17790a628c4b4df854b61_514_0.png)

**Figure 16.9: Displaying the Command to View the Assembly**

The command executes the MSIL Disassembler (ildasm.exe) that results in a new window where we can view the IL information in a file. Figure 16.10 shows the new window that appears after the execution of the command:

![](img/43c5f409f9b17790a628c4b4df854b61_514_1.png)

**Figure 16.10: Displaying the IL Information Window**

We can click the MANIFEST label to open the Notepad that contains the following information:

- **Name of the assembly**—Holds the name of a file containing the manifest. This name is set automatically when an assembly is created.
- **Version**—Contains a four part version number: Major, Minor, Build, and Revision.
- **Culture**—Targets the language or culture of the assembly. It has been set using the AssemblyCulture attribute. This component is optional.
- **Public Key Token**—Gives a strong name to the assembly.
- **List of files in the assembly**—Contains the list of files as a hash file.
- Type reference information—Contains the information that will be used in runtime to map the type references used in the code.
- Reference assembly information—Contains the reference of other assemblies that can be called in runtime.

The first four attributes form the name of the assembly and are required when referencing the assembly in code.
