Next, let’s learn about the module_init() and module_exit() macros.

## The module_init() and module_exit() Macros

If we are writing a kernel module in Linux 2.4 and later, then we can rename the start and cleanup functions in the module, as these functions always need not be called init_module() and cleanup_module(), respectively. This functionality can also be achieved by using the module_init() and module_exit() macros, which are defined in linux/init.h. The only restriction is that the start and cleanup functions must be defined before calling the macros; otherwise, we will get compilation errors. Following is the kernel module with the module_init() and module_exit() macros:

```c
/*
 * hello-2.c - Demonstrating module_init() and module_exit() macros.
 */

#include <linux/module.h> /* Required by all modules */
#include <linux/kernel.h> /* Required for KERN_INFO */
#include <linux/init.h>   /* Required for the macros */

static int __init hello_world_init(void)
{
    printk(KERN_INFO "Hello world -- once again\n");
    return 0;
}

static void __exit goodBye_world_exit(void)
{
    printk(KERN_INFO "Goodbye world -- once again\n");
}

module_init(hello_world_init);
module_exit(goodBye_world_exit);
```

Makefile for this kernel module is same as the one for hello-1.c; we have only changed the program name.

Let’s now learn about the __init and __exit macros.

## The __init and __exit Macros

The __init macro results in discarding the start function and freeing up its memory after the first call. This is done for built-in-drivers, but not for loadable modules. Another macro called __initdata works similar to the __init macro; it cleans up the startup variables just after they are used. When the module is built into the kernel, the __exit macro results in omitting the function, which is followed by the __exit keyword.

Let's consider the following program:

```c
/*
 * hello-3.c -- Illustrating the __init, __initdata and __exit macros.
 */
#include <linux/module.h> /* Required by all modules */
#include <linux/kernel.h> /* Required for KERN_INFO */
#include <linux/init.h>   /* Required for the macros */

static int hello_world_data __initdata = 3;

static int __init hello_world_init(void)
{
    printk(KERN_INFO "Hello, world Data = %d\n", hello_world_data);
    return 0;
}

static void __exit goodBye_world_exit(void)
{
    printk(KERN_INFO "Goodbye, world once again\n");
}

module_init(hello_world_init);
module_exit(goodBye_world_exit);
```

In the preceding program, we have defined a static variable hello_world_data in the global scope followed by the __initdata macro. We have used the hello_world_data variable in the startup function and __initdata ensures that the variable will be cleaned up once it is used for the first time in the startup function, hello_world_init(). As a coding convention, we define the variables with __initdata macro, which are to be used only in the startup function. We do not need to keep those variables alive for the entire program execution, as they are not used anywhere else. Similarly, the usage of __init and __exit macros before the startup and cleanup functions ensures that the memory occupied by the functions is freed up, once they are used. This is done as both the functions are of special type, as they are called only while loading and unloading the kernel modules. These keywords or macros are not used for other functions in the module, as we might require calling those functions more than once during the program’s lifetime.

The function followed by the __exit macro is goodBye_world_exit(). It will have no effect for loadable modules. In addition, this function will never be called if the module is compiled statically.

## Licensing and Documentation for Kernel Modules

Whenever we try to run a kernel module in Linux 2.4 or later, although it gets loaded into the kernel, we still get some warning on the console at the time of invoking the insmod command. Let’s run the hello-1.ko module using the insmod command to see the warning, as follows:

```text
# insmod hello-1.ko
Warning: loading hello-1.ko will taint the kernel: no license
See http://www.tux.org/lkml/#export-tainted for information about tainted modules
Module hello-1 loaded, with warnings
```

In Linux 2.4 or later, there is a mechanism to identify the code licensed under the GPL, so that the programmers can be warned that this code is a non-open source. This functionality is performed by the MODULE_LICENSE() macro. To overcome the warning, we need to set the license to GPL. The license mechanism is defined and documented in linux/module.h. To understand the concept of GPL license for Linux kernel modules, let's consider the following program:

```c
/*
 * hello-4.c - Demonstrates module documentation to eliminate warning during module
 *             loading time
 */
#include <linux/module.h> /* Required by all modules */
#include <linux/kernel.h> /* Required for KERN_INFO */
#include <linux/init.h>   /* Required for the macros */

#define DRIVER_AUTHOR "Soumitra Banerjee"
#define DRIVER_DESC "A sample driver"

static int __init init_hello_world(void)
{
    printk(KERN_INFO "Hello, world for license example.\n");
    return 0;
}

static void __exit cleanup_goodbye_world(void)
{
    printk(KERN_INFO "Goodbye, world  once again.\n");
}

module_init(init_hello_world);
module_exit(cleanup_goodbye_world);

/* To get rid of taint message by declaring code as GPL. */

MODULE_LICENSE("GPL");

MODULE_AUTHOR(DRIVER_AUTHOR); /* who wrote this module. */
MODULE_DESCRIPTION(DRIVER_DESC); /* what does this module do */

/* This module uses /dev/testdevice. The MODULE_SUPPORTED_DEVICE
 * macro might be used in the future to help automatic configuration
 * of modules, but is currently unused other than for documentation
 * purposes. */
MODULE_SUPPORTED_DEVICE("testdevice");
```

In the preceding program, we have used the MODULE_LICENSE() macro to eliminate the warnings given during the module loading time.

Next, let's learn how to compile a module spanning multiple files.

### Compilation of a Module Spanning Multiple Files

Sometimes, we need to divide a kernel module into several source files. Splitting a single kernel module file into more than one file increases the modularity of the code and makes the entire module simple. Let's write a kernel module that spans over two source files. Following is the code for start.c:

```c
/* start.c - Illustration of multi-file modules */
#include <linux/kernel.h> /* we're doing kernel work */
#include <linux/module.h> /* Specifically, a module */

int init_module(void)
{
    printk(KERN_INFO "Hello, world - in start\n");
    return 0;
}
```

Following is the code for stop.c:

```c
/* stop.c - Illustration of multi-file modules */

#include <linux/kernel.h> /* we're doing kernel work */
#include <linux/module.h> /* Specifically, a module */

void cleanup_module(void)
{
    printk(KERN_INFO "Good Bye - in stop.\n");
}
```

The start.c file contains the definition of the init_module() function; whereas, the stop.c file contains the definition of the cleanup_module() function.

Now, we need to compile both the files and generate the .ko file to load the kernel module. Till now, we have learned to generate the .ko file by compiling a single source file by using the make command. Therefore, a question arises that will there be two different kernel modules for this example; one for start.c and the other for stop.c. The answer to this question is no, as a single kernel module will be generated after compiling the start.c and stop.c files. The Makefile for this example will contain the name for both the programs, as shown as follows:

```makefile
obj-m += startstop.o
startstop-objs := start.o stop.o
all:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules
clean:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean
```

Executing the Makefile by using the make command generates a kernel module called startstop.ko, which can be loaded and unloaded from the kernel using the insmod and rmmod commands, respectively.

After having an idea on how kernel modules are written, let's discuss the primary differences between a kernel module and a C user-space program.

### Kernel Modules vs. C User-Space Programs

A C user-space program begins with a main() function, executes a set of instructions, and terminates the execution upon completion of those instructions. On the other hand, a kernel module always begins with the startup function, which is either init_module or the function that is specified within the module_init macro. The startup function, once invoked as the kernel module loads, sets up the environment in the kernel to run the module's functions whenever they are required.

To end the execution of a C user-space program, nothing special needs to be done; however, to unload a kernel module, we should always call the cleanup function, which is either cleanup_module or the function that is specified with the module_exit call. The cleanup function is the exit point for every kernel module, where it unregisters all the functionalities that the entry function had once registered. Every Linux kernel module must have an entry function and an exit function.
