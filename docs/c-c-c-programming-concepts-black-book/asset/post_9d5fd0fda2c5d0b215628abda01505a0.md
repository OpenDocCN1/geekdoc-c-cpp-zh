
```c
if (bind(parentfd, (struct sockaddr *) &serveraddr,
          sizeof(serveraddr)) < 0)
    error("ERROR on bind");

/*
 * listen: make this socket ready to accept connection requests
 */
if (listen(parentfd, 5) < 0) /* allow 5 requests to queue up */
    error("ERROR on listen");

/*
 * main loop: wait for a connection request, echo input line,
 * then close connection.
 */
clientlen = sizeof(clientaddr);
while (1) {

    /*
     * accept: wait for a connection request
     */
    childfd = accept(parentfd, (struct sockaddr *) &clientaddr, &clientlen);
    if (childfd < 0)
        error("ERROR on accept");

    /*
     * gethostbyaddr: determine who sent the message
     */
    hostp = gethostbyaddr((const char *)&clientaddr.sin_addr.s_addr,
                          sizeof(clientaddr.sin_addr.s_addr), AF_INET);
    if (hostp == NULL)
        error("ERROR on gethostbyaddr");
    hostaddrp = inet_ntoa(clientaddr.sin_addr);
    if (hostaddrp == NULL)
        error("ERROR on inet_ntoa\n");
    printf("server established connection with %s (%s)\n",
           hostp->h_name, hostaddrp);

    /*
     * read: read input string from the client
     */
    bzero(buf, BUFSIZE);
    n = read(childfd, buf, BUFSIZE);
    if (n < 0)
        error("ERROR reading from socket");
    printf("server received %d bytes: %s\n", n, buf);

    /*
     * write: echo the input string back to the client
     */
    n = write(childfd, buf, strlen(buf));
    if (n < 0)
        error("ERROR writing to socket");

    close(childfd);
}
}
```

In the preceding listing, we have a simple TCP echo server; let us have a look at how the server works:

- The server first binds to a predefined port number
- After executing a successful bind, the server then starts listening on that very port to ensure that the incoming connections are made on that port
- It loops infinitely and receives any incoming connection that comes its way in that port
- Upon successfully accepting the connection, the server performs a read call to check if some information has arrived at the socket or not
- If the server finds any information at the socket, then it immediately writes the same information back to the client as well

At the server's end, we have used the same port as of the client so that the TCP connection is successfully established. We have used "INADDR_ANY" to let the kernel assign the IP to the server and the function "htons" to properly convert the port to the network byte order. Then we perform a bind call on the predefined IP and port. After the bind is successful, the server starts listening on that IP and port for incoming connections. The server accepts the incoming connection with the help of an accept call. After successfully accepting the connection, it figures out the host name and the address of the client by using the function "gethostbyaddr." This function takes as input the IP address of the host and returns the host name that is associated with that IP address. After gathering the relevant information, the server performs a read operation to check whether some information has arrived at its end or not. Unlike the client, at the server side, we have used the "read" and "write" function calls. If the server receives some information, then it immediately writes the same information back to the client. In this way, the echo server works. Similar to the client, the server also performs blocking read and write calls; by any chance if the client fails to write data in the socket, the server process will sleep forever.

**NOTE**

INADDR_ANY is a special IP address which allows a socket to bind with the lowest numbered interface attached with that socket.

## I/O Multiplexing

If we take a closer look at the client-server example that has been stated in the earlier section, then we will notice that the TCP client program is actually handling two inputs at the same time. It is reading information from the standard input with the help of a gets() call and again it is receiving information from the TCP socket as well. Imagine a scenario where the TCP client process gets blocked on a gets() call made on the standard input path. In the meantime, the server process gets killed and it sends a FIN to the client. The server closes its end of the connection after sending the FIN. However, the client will never observe this as it is blocked on the call made on the standard input. One of the solutions to this problem is that the kernel would be notifying the process about one or more I/O conditions that are ready. This is known as I/O multiplexing. This is achieved with the help of the select and poll functions. I/O multiplexing is used in the following cases:

- When the client is using multiple descriptors, such as reading information from a standard input and maintaining a network socket as well
- When the client wants to use multiple sockets it can use the select function
- A TCP server can use I/O multiplexing when it needs to handle both listening and connected sockets at the same time
- I/O multiplexing can be needed if the server uses both TCP and UDP

Before discussing the select and poll options for the I/O multiplexing, we need to understand the different models that we have for I/O handling.

### Blocking I/O Model

The most basic I/O model used in networking is called blocking I/O model. All the sockets are blocking by default. Let us take an example of a UDP message exchange which becomes easier to discuss, as in case of UDP, we can easily conclude whether a datagram has been received or not. Let us take an example of a system call "recvfrom," which expects data from a UDP socket and tries to read it. Figure 22.6 shows a blocking I/O model:

![](img/43c5f409f9b17790a628c4b4df854b61_780_0.png)

The preceding figure shows that a system call made to "recvfrom" gets blocked until the kernel finds that information has arrived on that socket. The moment information arrives on the socket, the function call is returned to the process.

### Non-Blocking I/O Model

We can set a socket to a non-blocking I/O model. Setting the socket to non-blocking means that we are signaling the kernel when an I/O operation requested by the process that fails to complete the process should not be put to sleep, but an error should be returned in return. Figure 22.7 explains the working of a non-blocking socket:

The timeval structure mentioned in the signature is used to let the users configure how long they want to make the select call wait before it goes through a timeout. A timeout structure is used in Listing 22.13 to specify the time in seconds and microseconds:

```c
    long tv_sec;
    long tv_usec;

```

We can have the following three outcomes by using the timeout structure:

- We can wait forever and return only when one of the specified descriptors is ready for I/O.
- We can wait up to a fixed amount of time and return when one of the descriptors is ready for I/O, but we should not wait beyond the time mentioned in the timeout argument.
- We should not wait at all and return immediately after checking the descriptors. This is known as polling.

The three arguments other than the timeout structure, i.e., readfds, writefds, and exceptfds, specify the descriptors that would be used by the kernel to test reading, writing, and exception conditions. Some major exception conditions that are supported by the select function are as follows:

- The arrival of out-of-band-data in the socket
- The control status information that needs to be read from the master side of the pseudo terminal

The select function uses descriptor sets which enable the usage of multiple descriptor values for each of the arguments. These descriptor sets are an array of integers where each bit of each integer corresponds to a descriptor. The descriptors are further manipulated with the help of the following four macros:

```c
void FD_ZERO(fd_set *fdset);       /* clear all bits in fdset */
void FD_SET(int fd, fd_set *fdset); /* turn on the bit for fd in fdset */
void FD_CLR(int fd, fd_set *fdset); /* turn off the bit for fd in fdset */
int FD_ISSET(int fd, fd_set *fdset); /* is the bit for the fd set ? */
```

If we take up an example, then for descriptors 3, 7, and 9 we can use the macros as follows:

```c
fd_set readset;
FD_ZERO(&readset);              /* initialize the set */
FD_SET(3, &readset);            /* turn on bit for fd 3 */
FD_SET(7, &readset);            /* turn on bit for fd 7 */
FD_SET(9, &readset);            /* turn on bit for fd 9 */
```

If we do not want to use any of the three arguments (readfds, writefds, or exceptfds), then we can use NULL in place of that fdset. The maxfd1 argument specifies the number of descriptors to be tested. The value should be set to the number of descriptors to be tested plus one. The FD_ISSET macro is used to test a specific descriptor in an fd_set structure. The value returned by the function indicates the total number of bits that are ready across all descriptor sets each time we call the select function. The socket descriptors become ready for reading when one of the following conditions holds:

- The bytes of data in the socket receive buffer are greater than or equal to the current size of the low water mark for the socket receive buffer.
- The read-half of the connection is closed; it signifies that the TCP connection has received a FIN. The read operation on the socket will not block and will return 0.
- The socket happens to be a listening socket and the number of completed connections is non-zero. An accept call will not block.
- A socket error is pending. The read operation on the socket will not block and will return an error (-1) with errno set to the specific error condition.
