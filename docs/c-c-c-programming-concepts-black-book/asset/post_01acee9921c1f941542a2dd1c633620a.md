
## Exception Handling

Before the advent of different error handling mechanisms, every function that is called would return any value indicating how properly the execution went. Program code that called the function would then check the particular return code and deal with it accordingly. The resulting code could be littered with extra if-statements as well as the error handling code. Further, the return value of the function could not return anything but one code.

The generic concept of exception handling is very lucid. The motive is to raise some error flag every time something goes wrong. Next, a system always acts as a watcher for this error flag. Further, the system calls the error handling code if the error flag has been spotted.

If noticed, we have mentioned two synonymous words, but these are not same. These two words are error and exception.

An error typically refers to a problem that exists in a program when it is written and compiled. It could be a logical error that will result in incorrect results. In other words, the code is correct, but the algorithm is wrong. Exceptions are errors or anomalies that occur during the execution of a program. They can be the result of unavailability of system resources, such as memory, file space, and channels, or data-dependent conditions, such as a divide-by-zero or numerical overflow. Such runtime errors can cause the applications to behave unpredictably or to crash. Exceptions tend to be rare events, but are predictable.

Given that exceptions are somewhat predictable, how should our programs handle them? Three types of actions can be performed, which are given as follows:

- We do not handle the exception and allow the program to die or core dump
- We can issue a warning; for example, print some error messages, probably at the point in the code where the exception occurred and then exit
- We can handle the exception gracefully and continue executing

Can the same piece of code raise an exception and handle it? Let's consider that an exception arises while allocating memory. Can the same function or method that attempts to allocate memory itself handle the exception raised? Probably some other section of code would handle the exception. This implies a separation between the creation of an exception and its handling. The method in which an exception occurs could just alert its caller. This allows the code that raises the exception to be developed separately from the code that handles it. If we pass exceptions up to the calling routines, it is necessary to have a way to bundle information.

> **NOTE**
>
> Exceptions are errors that occur at runtime. When such exceptions occur, a programmer has to decide a strategy according to which he/she would handle them. This systematic handling of runtime errors is called exception handling.

Next, let's discuss error handling in C and C++.

## Error Handling in C and C++

Function calls may be followed with error assessments as return values to understand whether the function executed or not. In the C programs, a function usually returns one value if any problem occurs during the execution of the function. For example, file opening functions return a NULL indicating their lack of ability to open a file successfully. Therefore, each time we call a function, we can check for the return value. In C, the setjmp() and longjmp() functions are used as error handlers. This approach is intended to handle the conditions that do not require immediate system termination. In case a recursive descent parser detects an exception, it should report the exception and continue with further processing. The setjmp() operates when called from main() and saves the state of context of the function in the jmp_buf structure, which is defined inside the setjmp.h header file. When an error occurs, the longjmp() function uses the saved context to revert to a previous point in the system.

Every time a function is called, we must check its return value through a pair of if-else statements. Surrounding every function call with a pair of if-else results in an increase in code size and decreases readability. This approach cannot be used to report errors in the constructor of a class, as the constructor cannot return a value.

The jmp_buf structure is system dependent because different systems might require different amounts of information to capture the context of a process. The setjmp() or longjmp() functions do not call destructors; therefore, objects are not properly cleaned up. Destructor calls are essential; therefore, this approach is not feasible in C++.

The C++ language provides built-in functionality for handling exceptions, which may occur throughout the execution of a system. With C++ exception handling, a program can communicate unexpected events with a higher execution context, which is better to recover from such abnormal events. These exceptions are handled by code, which is outside the normal flow of control.

The C++ exception mechanism handles the following features:

- Exceptions may be raised and handled in different sections of code.
- Any object, including class objects, may be passed back to the handler of an exception. These objects can contain data and methods to assist in handling the exception.

The portion of code that leads to or detects the runtime abnormality (for example, divide by zero or out of memory) may throw an exception, which is caught by another portion of code. The exception may be the object that is actually thrown. The exception object can be used to convey information in the section of code that throws the object to the portion of code that catches the object. This separation associated with exception creation as well as exception handling is extremely significant.

C++ uses two classes to represent and encapsulate exceptions:

- **Skeleton classes** — These classes have no members because their names are sufficient to refer to and handle the exceptions.
- **Classes with data members** — These classes declare data members that allow them to describe the exception better.

In some instances, the appropriate response may be to terminate a program. In other instances, the appropriate response is to give some warning information. In others, maybe the exception could be caught and ignored.

Sections of code that may throw exceptions tend to be surrounded by try blocks. Exceptions that are thrown from the try blocks are caught by a catch clause. The format of the try-catch block is shown as follows:

```cpp
try
{
    // try block
}

catch (type 1 arg)
{
    // catch block
}
```

Consider the following piece of code:

```cpp
#include <iostream>
using namespace std;
int main()
{
    int a = 6;
    int b = 0;
    int result;
    int exceptionCode = 36;
    try
    {
        if (b == 0)
        {
            throw exceptionCode;
        }
        result = a/b;
    }
    catch (int e)
    {
        if (e == 25)
        {
            cout << "Divide by zero exception has occurred" << endl;
            cout << "Hence terminating..." << endl;
        }
        else
        {
            cout << "Exception of unknown type has been found" << endl;
            cout << "Hence terminating..." << endl;
        }
    }
    cout << "Exiting the program..." << endl;
    return 0;
}
```

The exception thrown in the preceding program is of type int. The catch block consists of logic to decode this particular value and print a suitable error message. This is bad design since it requires the catch block. Moreover, a programmer needs to understand the possible exception rules and put into action the possibly complex logic. It is noteworthy that an exception can be any kind of object. As we can throw any kind of object, let's try throwing an error message string, rather than an exception. Consider the following code:

```cpp
#include <iostream>
using namespace std;
int main()
{
    int a = 6;
    int b = 0;
    int result;
    try {
        if (b == 0) {
            throw "Divide by zero";
        }
        result = a/b;
    } // try block ends here
    catch (char *x) {
        cout << x << endl;
    }
    cout << "Exiting the program..." << endl;
    return 0;
}
```

The preceding code is a better design. The catch block no longer needs the detailed understanding of the exception. The code that throws the exception is passing information about the exception, which, in this case, is an error message.
