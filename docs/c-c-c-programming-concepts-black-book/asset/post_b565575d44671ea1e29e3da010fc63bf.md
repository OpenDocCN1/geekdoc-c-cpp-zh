Before going further, let's understand the differences between composition and aggregation.

Composition is a stronger form of aggregation. It shows an exclusive ownership of the part of classes by the whole class. This implies that parts may be created after a composite is created, but such parts will be explicitly removed before the destruction of the composite. However, aggregation differs from composition in that it does not imply ownership. In composition, when the owning object is destroyed, the contained objects are also destroyed. However, in aggregation, this is not necessarily true. Let's take an example to understand this concept. A company owns numerous departments and each department has numerous employees. If the company closes someday, then the departments will not exist, but the employees within those departments will persist. Therefore, the company can be cited as an example of a composition associated with departments; whereas, departments continue as an aggregation of employees.

In aggregation, an object may only contain a reference or pointer to the object and may not have lifetime responsibility for it. Sometimes, aggregation is referred to as composition when the distinction between composition and aggregation is unimportant.

Composition may be used to store numerous instances of the composite data types. This is sometimes referred to as containment, which includes linked lists, associative arrays, and binary trees.

## Data Abstraction and Information Hiding

Information hiding is a very important term used in OOP, where a class tries to hide its implementation details from its users. For example, we can implement a stack using the concept of arrays or linked lists. This, however, does not affect the functionality of the stack. A user bothers only about how the stack performs and what functionality it provides, but not about how it is implemented. This concept is called data abstraction.

Consider the EmployeeSal class to calculate the salary of an employee. Listing 13.22 shows the code of the EmployeeSal class:

### Listing 13.22: Showing the Code to illustrate Information Hiding

```cpp
class EmployeeSal
{
    public:
        void setSalary(double sal)
        {
            salary = sal;
        }
    private:
        double salary;
};
```

People may confuse encapsulation with information hiding. Encapsulation enables us to draw a boundary around something that we want to encapsulate. It enables us to communicate about the inner and outer worlds of that boundary. Information hiding, on the other hand, is a design, which limits the direct exposure of data and implementation flow to prevent unwanted coupling. Information hiding is a design principle; whereas, encapsulation is merely a feature of programming languages.

> According to John Wilkinson, “Information hiding or the opposite, information leakage may span multiple objects, or it may involve other forms of coupling between client code and implementation code. For example, call order dependency will expose some information that normally should be hidden. Another example might be default values that are used by the client code. There are examples of perfectly encapsulated code that still exhibits information hiding problems.”

Therefore, encapsulation is not synonymous to information hiding, but in some ways, it requires some degree of information hiding.

Abstraction, encapsulation, and information hiding can be implemented using Abstract Data Types (ADTs). An ADT is a class that is designed to be served as an interface for derived classes.
