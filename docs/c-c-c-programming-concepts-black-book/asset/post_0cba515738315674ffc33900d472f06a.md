
## Chapter 9: *Library Functions for Modules*

While writing C user-space programs, we can use different library functions that we do not want to define all the time. The most common example is the printf() function. Similar library functions are also available for kernel modules, such as printk().

In the hello.c program, discussed earlier in this chapter, note that we have used the printk() function without including any standard I/O library. This is because kernel modules are object files, whose symbols are resolved during insmod'ing. The definitions for the symbols generally come from the kernel itself. The /proc/kallsyms file provides the list of all the symbols that are exported by the kernel.

Before going further, let's understand the difference between library functions and system calls. Library functions are higher-level Application Programming Interfaces (APIs) that run completely in a user space and provide a more convenient interface to the functions. On the other hand, system calls run in a kernel mode on the user's behalf. For example, to format the data passed as an argument to printf(), the system call write() is used that sends the data to the standard output.

Consider the following program:

```c
#include <stdio.h>
int main(void)
{
    printf("hello");
    return 0;
}
```

Now, compile the preceding program with gcc -Wall -o hello hello.c and run the executable with strace ./hello. The strace tool gives every detail about the system calls a program is using, including which call is made, what its arguments are, and what it returns. The output of running the executable with strace ./hello shows that the actual operation behind the printf() function is write(1, "hello", 5).

Next, let's discuss character device files.

### Character Device Files

The file_operations structure in the linux/fs.h header file holds the pointers to the functions that the driver registers with the kernel to perform various operations on a device. Every field of the structure corresponds to a function that handles a requested operation; however, not all the entries are mandatory in the structure. An instance of file_operations is commonly known as fops or file ops. The structure assignment is given as follows:

```c
struct file_operations file_ops = {
    read: read_my_device,
    write: write_my_device,
    open: open_my_device,
    release: release_my_device
};
```

Note that any member of the structure that is not explicitly assigned will be automatically initialized as NULL by the gcc compiler.

### Exploring the File Structure

In Linux, a file is a kernel-level structure and should not be confused with user-space files. It is not the same file as defined by glibc and it would never appear in the kernel-space function. Moreover, the file in context is a Linux open file and not the file on disk; therefore, it should not be confused with an inode, which is used to store the entire information specific to a file in Linux systems.

### Registering a Device

Character devices are accessed through the device files, which are located in /dev. Each character device file has two numbers: a major number and a minor number. The major number helps in locating the driver that handles the device. On the other hand, the minor number is used by the driver to differentiate between the devices it is working on, in case the driver handles more than one device. Whenever we add a device to the system, we need to first register it with the kernel. The major number of a device is generated during the initialization of a module. The function called to register a device with the kernel is register_chrdev(), which is defined in the linux/fs.h header file. The signature of register_chrdev() is given as follows:

```
int register_chrdev(unsigned int major, const char *name, struct file_operations *fops);
```

In the preceding signature, the first argument is the major number that we want to request; the second argument is the name of the device as it appears in /proc/devices; and the third argument is a pointer to the file_operations table for the driver. If the major number is passed as 0, then register_chrdev() tries to dynamically allocate a major number and returns its value. If the major number is passed as some positive non-zero value, then register_chrdev() attempts to register the device with the given major number and returns 0 on success. The register_chrdev() function returns a negative value on failure.

While registering character devices, we mostly pass the major number as 0 to the register_chrdev() function. This ensures that there is no conflict with the major number of the existing registered devices. However, this approach has one disadvantage that we cannot make a device file in advance, as we do not know which major number it is going to take. There are a couple of methods to make a device file. First, the driver can print its own newly assigned major number and using this, we can make the device file. Second, the newly registered device can make an entry in /proc/devices, and from there, we can generate the device file easily. Third, we can make the driver create the device file using the mknod system call after a successful registration and rm during the call to cleanup_module.

Note that we do not pass the minor number of a device explicitly to the kernel during a registration, as only the device uses it. This implies that the Linux kernel has nothing to do with the minor number of a device.

### Unregistering a Device

After a character device serves its purpose, we need to unregister it from the kernel. The following function can be used to unregister a character device file from the kernel:

```
int unregister_chrdev(unsigned int major, const char *name);
```

In the preceding function, the first argument is the device major number and the second argument is the device name. The unregister_chrdev() function is called during cleanup_module to remove the driver from the kernel. It returns 0 on success and -EINVAL if the major number is not registered with the matching name.

Next, let’s learn about device drivers.

### Device Drivers

Whenever we plug in a new device into a system, a special program is loaded into it during its startup. This special program is known as the device driver routine. Without a device driver, the system would not be able to use the device. For example, when we plug in a TV tuner card or a graphics card into a system, we need to install the driver into the system to make it recognize the new hardware and support its execution and operation. In UNIX, each piece of hardware is represented by a file located in /dev, which provides the communication with the underlying hardware.

As most of the devices are used in both the input mode and the output mode, a mechanism should be there for a driver to receive an input and send an output to the device. To send an output to the device, we need to open the device file in the input mode and write the required data to it. A user process accesses the device files and performs the I/O operations on them by using a special function called Input Output Control (ioctl). To communicate with the driver, every device takes the help of the ioctl command. Every device has its own ioctl command, which can be read ioctls (for sending information from a device to a process), write ioctls (for sending information from a process to a device), both, or neither. The ioctl function is called with three parameters: the file descriptor of the device file, the ioctl number, and a parameter. The ioctl number encodes the major device number along with the type of the ioctl, the command, and the type of the parameter. To create the ioctl number, a macro call, such as _IOR, _IOW, or _IOWR, is used depending on the type. To implement an ioctl, it is always recommended to receive an official ioctl assignment to avoid any conflict with the existing ioctls.

Let’s now learn about system calls, in detail.

### System Calls

System calls are very important for all the user processes, as they are the only mechanism for them to get any service from the kernel, while running in the user mode. Any process running in the user mode is not allowed to access the kernel or the functions in the kernel due to hardware protection. A process needs to invoke the system calls to get the services (such as opening a file, forking to a new process, or requesting more memory) from the kernel. Whenever a process invokes a system call, the process fills the registers with the appropriate values and then calls for a special instruction, which transfers the control to a previously defined location in the kernel. Although the process does not have any write access to that location, it can definitely read from that location. In the Intel CPU architecture, this is done by using the interrupt 0x80. The hardware knows that once a process jumps to this location, it would no longer run in the restricted user mode, but as the operating system kernel. The location in the kernel a process can jump to is called a system call. Without a proper context, changing the definition of a system call can be fatal for the system. The strace command is used to know all the system calls that a program uses during the runtime.

The entire process of system call execution is simple and straightforward. When a system call is invoked by a user process, the procedure at that location checks the system call number and informs the kernel about the service for which the user process has requested. Then, it looks at the table of system calls (sys_call_table) to see the address of the kernel function to call. Further, it calls the function, executes it, and then returns to the invoking process.

In case we want to add a new functionality in the kernel or change the way any system call used to work before, we need to implement our own code in the kernel and then change the pointer at sys_call_table to point to our function. Note that we should not leave the system in an unstable state; whatever module we load using insmod, it is very important to restore sys_call_table to its original state from the cleanup_module function.

### Task Scheduling

If a task needs to be done by a process, then we need to put it in the system's crontab file. As the task will be done by a kernel module, we have two different types of possibilities. One is to put a process in the crontab, which will wake up the module by a system call when necessary. This approach is very inefficient because to perform a task at regular intervals, we need to wake up a kernel module, which is already in the memory. The second approach is to create a function that can be called once for every timer interrupt. This can be done by creating a task, which will hold a pointer to the function. Next, we use queue_delayed_work to put the task on a task list for execution on the next timer interrupt. If we want to keep the function being executed, we need to put it back onto the task list, whenever it is called, for the next timer interrupt. When a module is removed by rmmod, its reference count is checked. However, if it is zero, then cleanup_module is called. Further, the module is removed from the memory with all its functions.
