## Chapter 23 Behavioral Diagrams

Behavioral diagrams visualize, specify, construct, and document the dynamic aspects of a system. In these diagrams, we basically emphasize on the interaction between objects and the flow of control among them. This flow of control may be simple or complex and may involve branching, looping, recursion, and concurrency. There are four types of behavioural diagrams, which are discussed in the following subsections.

### Use-Case Diagram

A use-case diagram shows a set of use cases, actors, and their relationships. It is used to model the requirement of a system. It comprises use cases, actors, dependency, generalization, association, relationship, roles, subsystems, and classes. Figure 23.23 shows a use-case diagram:

### Interaction Diagram

Interaction diagrams describe the flow of messages between objects.

### Sequence Diagram

Sequence diagram is a type of interaction diagram that focuses on the order in which the messages are sent. It is very useful for describing the procedural flow through many objects and for finding race conditions in concurrent systems. In UML, it is shown as a table that shows objects arranged along the X-axis and messages ordered in increasing time along the Y-axis.

### MVC Architecture

The MVC pattern separates the modeling of the domain, the presentation, and the actions based on user input into three separate set of classes, which are as follows:

- **Model**—This manages your behavior and data in the application domain, responds to requests for specifics of its state (usually through the view), and responds to instructions to switch state (usually through the controller).
- **View**—The view manages the display of information.
- **Controller**—The controller interprets inputs from the user, informing the model and/or the view to change as appropriate.

### Case Study – Hotel Management Systems

ABC is a reputed hotel that desires to automate its room management and room booking services for providing efficient service to its customers. The hotel management system can perform the following tasks:

- Room can be booked depending on its type ("D," "L," and "O"), where the room rent is dependent on its type. Hotel manager can confirm the request.
- Customer can cancel the booking before his/her date of booking. Even the hotel manager can also cancel the booking, depending on the hotel strength.
- Customer can search room availability before he/she books any room.
- Members will get special discount on the room rent.
- Hotel manager can change the status of the rooms depending on the room occupancy.
- Management can add rooms to the system.

First, we need to recognize the actors and stakeholders in the system and then go for the process identification. Along with the use case diagram, a use case template is also required for better understanding. Further, we draw the diagram and then prepare the use-case template.

### Use-Case Template for Case Study

In this section, we describe the use-case template for the “Request for Booking” use case as follows:

- Use case UC1 – Request for Booking.
- Overview – UC1-Request for Booking: Use case has been initiated by the customer to book a hotel room online.
- Actors – Customer.
- Stakeholders – Hotel.
- **Pre-condition** –
  - 1. Assume that any people can visit this site and book the room.
  - 2. In case of a member of the hotel, a verification process will be done where the member has to give his/her member ID.
- **Post-condition** – After successfully booking a room, the database should be updated with the booking details.
- **Normal flow** – Customers can book any room after searching. Rooms can be booked depending on their type and rent. To book a room, a customer needs to provide booking details and self-details. After accumulating information and getting confirmation from the customer, a new booking object has been created, which stores the booking information along with the customer data.
- **Alternate flows** – If the customer is a member, he/she will be asked to provide membership details (such as member ID) to avail the facility of the membership.
- **Exceptions** – We assume that no exception will occur during the execution of the use case.
- **Extend** – There are three use cases that are used as extended use cases. “Member of hotel” and “General Customer” are two extensions of the room rent since they will avail different rents for the same room. Thus, the use case “Room Rent” is extended into these two use cases. Another use case we have used as an extension as “New Booking” of the use case “Request Room Booking” is “Booking Details.”
- **Uses** – This use case will be used by the customers whenever there is a need to book a hotel room of their choice through online.
- **Unresolved issues** – No issues are found.
- **Non-functional requirement** – The use case must meet the following non-functional requirements:
  - 1. The performance of the use case should be good enough so that in any environment, it can run safely and efficiently
  - 2. Reliability is an issue where the use case should be reliable in any platform so that the users do not have any problem accessing the program
  - 3. It should be user friendly
- **Future requirement** – Every user should be given a user ID and password before accessing the room details.
