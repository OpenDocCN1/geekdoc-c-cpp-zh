
We need to include the header `<sys/socket.h>` in order to use the recvmsg and sendmsg functions. The `recvmsg()` function is used to receive a message from a connection-mode or connectionless-mode socket. It is normally used with the connectionless-mode sockets because it permits the application to retrieve the source address of the received data. The `sendmsg()` function is used to send a message through a connection-mode or connectionless-mode socket. Both functions take the following variables as arguments:

- **socket**—The socket variable specifies the socket file descriptor.
- **message**—The "message" variable points to the `msghdr` structure. For the sendmsg function, the message pointer is used to store both the destination address and the buffers for the outgoing message. The length and format of the address depend on the address family of the socket. For the recvmsg function, the message pointer is used to store the source address and the buffers for the incoming message. The length and format of the address depend on the address family of the socket.
- **flags**—These flags are used to specify the type of message transmission. We will learn details about these flags in successive topics.

Let us take a look at the `msghdr` structure which is used to contain most of the information both for recvmsg and sendmsg functions. The structure is as follows:

```c
struct msghdr {
    void          *msg_name;            /* protocol address */
    socklen_t     msg_namelen;          /* size of protocol address */
    struct iovec  *msg_iov;             /* scatter/gather array */
    size_t        msg_iovlen;           /* # elements in message iov */
    void          *msg_control;         /* ancillary data */
    socklen_t     msg_controllen;       /* length of ancillary data */
    int           msg_flags;            /* flags returned */
};
```

The `msg_name` and `msg_namelen` members are used when the socket is in unconnected state, i.e., when it is used for UDP. The `msg_iov` and `msg_iovlen` members specify the array of input or output buffers. The `msg_control` and `msg_controllen` members specify the location and size of the optional ancillary data. The `msg_controllen` is a value-result argument for the recvmsg function.

There are various definitions of OOP. Grady Booch defined object-oriented programming as:

> Object-oriented programming is a method of implementation in which programs are organized as cooperative collections of objects, each of which represents an instance of some class, and whose classes are all members of a hierarchy of classes united via inheritance relationships.

> Stroustrup suggests that: "If the term 'object-oriented language' means anything, it must mean a language that has mechanisms that support the object-oriented style of programming well.... A language supports a programming style well if it provides facilities that make it convenient to use that style. A language does not support a technique if it takes exceptional effort or skill to write such programs; in that case, the language merely enables programmers to use the techniques."

Cardelli and Wegner said that a language is object oriented if and only if it satisfies the following requirements:

- It supports objects that are data abstractions with an interface of named operations and a hidden local state
- Objects have an associated type [class]
- Types [classes] may inherit attributes from supertypes [super classes]

For any language to support inheritance, you must be able to express "is a" associations among types; for instance, an apple is a type of fruit and a fruit is a type of plant. If a language does not provide direct support with regard to inheritance, then it is not object oriented.

### Object-Oriented Design

The emphasis in programming methods is primarily on proper and effective use of particular language mechanisms. Grady Booch defined Object-Oriented Design (OOD) as:

> Object-oriented design is a method of design encompassing the process of object-oriented decomposition and a notation for depicting both logical and physical as well as static and dynamic models of the system under design.

You can find two important parts in the definition, that is, object-oriented design (1) contributes to an object-oriented decomposition and (2) uses different notations to state different models of the particular logical (class and also object structure) and physical (module and also process architecture) designs of your system, in addition to the static and dynamic areas of the system.

### Unified Modeling Language

Unified Modeling Language (UML) is a family of graphical representations that are used in visualizing, specifying, constructing, and documenting business processes. It can be used with any processes throughout the software development life cycle. UML is a standard controlled by the Object Management Group (OMG), and is accepted as a standard in many business organizations to view their business models in the form of UML. UML is also used in many diverse business environments due to its extremely flexible nature. However, due to the vastness of UML, a significant amount of effort is required to understand and apply it. The major features of UML are as follows:

- Defines system structure for object modeling
- Provides support for different model organization
- Provides strong modeling for structure and behavior of objects and classes
- Provides clear representation of concurrent activities
- Provides support for object-oriented patterns for design reuse

The model for the object-oriented development may be classified as static/dynamic and logical/physical models.

**Logical view** of a system describes the existence and meaning of the key abstractions and the mechanism that forms the problem space or defines the system architecture.

The **physical model** describes the concrete software and hardware components of the system’s context or implementation.

UML has the following three parts:

- **View**—Shows different aspects of a system
- **Diagrams**—Implement different notations to visualize the content in view
- **Model elements**—Include elements required to model an object-oriented system

In UML, five types of views are available, which are explained as follows:

- **User view**—Illustrates how an end user views a system
- **Structural view**—Illustrates the static feature of a model, which includes classes, attributes, behaviors, and relationships between classes
- **Behavioral view**—Illustrates the interaction between the objects and the way a group of objects collaborates in the same behavior
- **Component view**—Illustrates the organizations and dependencies among software components, including source code component, run-time component, or an executable component
- **Deployment view**—Displays a system’s physical layers elaborately and helps in revealing software-hardware dependencies, meaning which piece of software is operated on which piece of hardware.

### Object Modeling Notations and Basic Concepts

In the world of computer, all the real-world entities are referred to as objects. Objects are generally associated with various properties and operations they perform. They are an integral part in database design as they provide you a better understanding of the real-world problem. In addition, it is easy for a developer to code the application program implementing objects. In this section, we will get familiar with the different object modeling notations and their basic concepts, which are explained as follows:

- **Class**—Refers to a description of a set of objects that share the same attributes, operations, relationships, and semantics. In UML, it is denoted by a rectangle.
- **Attribute**—Refers to a named property of a class that describes a range of values that instances of the property may hold. In UML, attributes are listed in the compartment just below the class name.
- **Operation**—Specifies the implementation of a service that can be requested from any object of the class to affect behavior of itself. In UML, operations are listed in the compartment just below the class attribute.
