Every device has its own ioctl command, which can be read ioctl's (for sending information from a device to a process), write ioctl's (for sending information from a process to a device), both, or neither. The ioctl function is called with the three parameters: the file descriptor of the device file, the ioctl number, and a parameter. The ioctl number encodes the major device number along with the type of the ioctl, the command, and the type of the parameter. To create the ioctl number, a macro call, such as IO_IOR, IOW, or IOWR, is used depending on the type. To implement an ioctl, it is always recommended to receive an official ioctl assignment to avoid any conflict with the existing ioctls.

# ## System Calls

System calls are very important for all the user processes, as they are the only mechanism for them to get any service from the kernel, while running in the user mode. Any process running in the user mode is not allowed to access the kernel or the functions in the kernel due to hardware protection. A process needs to invoke the system calls to get the services (such as opening a file, forking to a new process, or requesting more memory) from the kernel. Whenever a process invokes a system call, the process fills the register with the appropriate values and then calls for a special instruction, which transfers the control to a previously defined location in the kernel. Although the process does not have any write access to that location, it can definitely read from that location. In the Intel CPU architecture, this is done by using the interrupt 0x80. The hardware knows that once a process jumps to this location, it would no longer run in the restricted user mode, but as the operating system kernel. The location in the kernel a process can jump to is called a system call. Without a proper context, changing the definition of a system call can be fatal for the system. The strace command is used to know all the system calls that a program uses during the runtime.

The entire process of system call execution is simple and straightforward. When a system call is invoked by a user process, the procedure at that location checks the system call number and informs the kernel about the service for which the user process has requested. Then, it looks at the table of system calls (sys_call_table) to see the address of the kernel function to call. Further, it calls the function, executes it, and then returns to the invoking process.

In case we want to add a new functionality in the kernel or change the way any system call used to work before, we need to implement our own code in the kernel and then change the pointer at sys_call_table to point to our function. Note that we should not leave the system in an unstable state; whatever module we load using insmod, it is very important to restore sys_call_table to its original state from the cleanup module function.

# ## Task Scheduling

If a task needs to be done by a process, then we need to put it in the system's crontab file. As the task will be done by a kernel module, we have two different types of possibilities. One is to put a process in the crontab, which will wake up the module by a system call when necessary. This approach is very inefficient because to perform a task at regular intervals, we need to wake up a kernel module, which is already in the memory. The second approach is to create a function that can be called once for every timer interrupt. This can be done by creating a task, which will hold a pointer to the function. Next, we use queue_delayed_work to put the task on a task list for execution on the next timer interrupt. If we want to keep the function being executed, we need to put it back onto the task list, whenever it is called, for the next timer interrupt. When a module is removed by rmmod, its reference count is checked. However, if it is zero, then module_cleanup is called. Further, the module is removed from the memory with all its functions.
