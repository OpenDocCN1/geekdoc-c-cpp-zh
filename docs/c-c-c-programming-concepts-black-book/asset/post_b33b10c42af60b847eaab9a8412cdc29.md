
As a successor of UNIX, Linus Torvalds developed the Linux operating system in the year 1991 for the computers using the Intel 80386 microprocessor. Although Linux is designed over the foundations of UNIX, it has applied its own intelligence and optimization to deviate from the path shown by UNIX. However, Linux has neither broken the application interfaces of UNIX nor compromised with the general design goals of UNIX.

One of the most fascinating features of the Linux operating system is that it is not a commercial product; instead, it is an open source project, developed collaboratively over the Internet. Although Linus Torvalds remains the creator and maintainer of the Linux, progress continues as programmers across the world are contributing to make it richer in features. As the Linux kernel, along with much of its system, is free and open source software; therefore, anyone willing to contribute can take part in this project. The Linux kernel is licensed under the GNU General Public License (GPL). Therefore, anyone willing to make modifications can download the source code over the Internet and work on it.

Let's start the chapter by discussing Linux operating system.

## Overview of the Linux Operating System

Linux operating system comprises the kernel, device drivers, boot loader, command shells, and other user interfaces along with the basic files and system utilities. Kernel is the innermost and important part of the Linux operating system. It can be defined as system software that provides basic services to all the other parts of the system, manages hardware, and distributes system resources. Typical components of a kernel include interrupt handlers for servicing the interrupt requests, a scheduler to share the processor time among competing processes, a memory management unit managing the process address space, and a set of system services, such as inter-process communication and networking.

Nowadays, with the protected memory management units, kernel resides in a higher level of system state as compared to the normal user applications. This includes protected memory space and a full access to hardware. The system state and memory space are collectively referred to as *kernel space*. On the other hand, user applications execute in *user space*. Unlike the kernel space, applications in the user space view only a subset of system's available resources and are unable to perform certain functions, such as directly accessing or communicating with hardware. Applications running in the user space use the *system calls* to communicate with the kernel. A system call is a program that requests a service from the kernel. Generally, system calls are invoked by the processes, which are running in a user space.

As shown in Figure 9.1, the architecture is broken down into three levels - user space, System Call Interface (SCI), and kernel. On the top level, user applications are running and at the bottom level, kernel is running. The intermediate level is SCI, which connects various user applications to get the services from the kernel. This layer is important as both the kernel space and the user space reside in two different protected address spaces. In other words, the SCI layer serves as the only communication medium between them. Communication between the applications in user space and the kernel space is done mainly through the calls to the library functions, which in turn issue a system call to perform the job. To understand the communication between the user space and the kernel space, let’s take an example of the printf() function in the C language that helps in the formatting and buffering of data. Issuing a call to printf() eventually calls the write() system call, which instructs the kernel to write the data on the console. It is interesting to note that when an application executes a system call, the kernel executes on behalf of the application and runs in a process context.

The kernel also manages hardware resources by means of interrupts. When any hardware wants to communicate with the system, it issues an interrupt that asynchronously interrupts the kernel. Generally, interrupts are identified by a number. The kernel uses this number to execute a specific interrupt handler to process and respond to the interrupt. For example, as you type, the keyboard controller issues an interrupt to let the system know that there is a new data in the keyboard buffer. Kernel handles this by enabling and disabling the interrupts to interact with the outside environment. In the Linux kernel, interrupts do not execute in process context; instead, they run in a special context called the interrupt context.

After getting an idea about Linux operating system, let’s now discuss kernel design.

## Monolithic or Microkernels – What Linux Chooses?

Kernels can be classified into two main design patterns: monolithic kernel and microkernel. Monolithic kernel is an operating system architecture that is implemented as a single large process running as a supervisor, entirely in the kernel mode. Communication within the monolithic kernel is comparatively simple as everything runs in the kernel mode in the same address space. On the other hand, microkernels are not implemented as a single large process. For designing microkernels, the entire functionality of the kernel is broken down into the smaller kernel modules that can be configured easily and flexibly.

Similar to UNIX, Linux has a monolithic kernel. This implies that Linux is implemented as a single process running entirely in the kernel space. However, Linux also borrows some of the features from microkernels. Linux adds to itself the capability of loading small kernel modules dynamically that enhances its functionality at runtime without restarting the operating system. Let’s consolidate the characteristics of Linux kernel that make it different from UNIX variants:

- 1. Linux supports dynamic loading of kernel modules. Although the Linux kernel is monolithic, it is capable of dynamically loading and unloading the kernel code on demand.
- 2. Linux has Symmetric Multiprocessor support. Symmetric multiprocessing is a computer architecture where two or more processors are connected by a single shared memory and the entire system is controlled by a single operating system instance.
- 3. The Linux kernel is preemptive, that is, it can be interrupted to perform another task. Unlike traditional UNIX variants, the Linux kernel is capable of preempting a task even if it is running in the kernel. UNIX implementations, such as SOLARIS and IRIX, have preemptive kernels, but most traditional UNIX kernels are non-preemptive.
- 4. Linux takes an interesting approach towards thread support, that is, it does not differentiate between normal threads and processes. This implies that they are all the same to the kernel.
- 5. Linux provides an object-oriented device model with device classes, hot pluggable events, and a user-space device filesystem (sysfs).
- 6. Linux ignores some common UNIX features that are thought to be poorly designed, such as STREAMS.
- 7. Linux is free in every sense of the word, that is, its source code is freely distributable and can be modified and enhanced by anyone.

## Linux Kernel Modules

Linux kernel modules are smaller modules having a specific functionality that can be loaded and unloaded into the kernel dynamically. Similar to microkernels, kernel modules extend the functionality of the kernel without the need to reboot the system. However, we should be careful while running the kernel modules from the systems, as even a small mistake in the code can wipe out the entire file system or may result in a core dump followed by a reboot. Examples of Linux kernel modules are device drivers that allow the kernel to access hardware connected to the system. Without kernel modules, we would have to build monolithic kernels and add the new module directly into the kernel image to add a small functionality or utility into the Linux kernel. Moreover, one of the biggest disadvantages of having larger kernels is that it requires us to rebuild the entire kernel and reboot it every time to add a new functionality.

To see the kernel modules that are already loaded into the kernel, we need to run the lsmod command and view its output. The lsmod command displays this information by reading the /proc/modules file. A kernel module has its extension as ko.
