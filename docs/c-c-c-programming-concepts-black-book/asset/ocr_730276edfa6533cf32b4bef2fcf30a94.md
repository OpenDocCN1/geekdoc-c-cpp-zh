In the preceding listing, we have a simple TCP echo server; let us have a look at how the server works:

+   - The server first binds to a predefined port number
+   - After executing a successful bind, the server then starts listening on that very port to ensure that the incoming connections are made on that port
+   - It loops infinitely and receives any incoming that comes its way in that port
+   - Upon successfully accepting the connection, the server performs a read call to check if some information has arrived at the socket or not
+   - If the server finds any information at the socket, then it immediately writes the same information back to the client as well

At the server's end, we have used the same port as of the client so that the TCP connection is successfully established. We have used "INADDR_ANY" to let the kernel assign the IP to the server and the function "htons" to properly convert the port to the network byte order. Then we perform a bind call on the predefined IP and port. After the bind is successful, the server starts listening on that IP and port for incoming connections. The server accepts the incoming connection with the help of an accept call. After successfully accepting the connection, it figures out the host name and the address of the client by using the function "gethostbyaddr." This function takes as input the IP address of the host and returns the host name that is associated with that IP address. After gathering the relevant information, the server performs a read operation to check whether some information has arrived at its end or not. Unlike the client, at the server side, we have used the "read" and "write" function calls. If the server receives some information, then it immediately writes the same information back to the client. In this way, the echo server works. Similar to the client, the server also performs blocking read and write calls; by any chance if the client fails to write data in the socket, the server process will snoop forever.

**NOTE**
INADDR_ANY is a special IP address which allows a socket to bind with the lowest numbered interface attached with that socket.

# ## I/O Multiplexing

If we take a closer look at the client-server example that has been stated in the earlier section, then we will notice that the TCP client program is actually handling two inputs at the same time. Its reading information from the standard input with the help of a gets() call and again its receiving information from the TCP socket as well. Imagine a scenario where the TCP client process gets blocked on a gets() call made on the standard input path. In the meantime, the server process gets killed and it sends to FIN to the client. The server closes its end of the connection after sending the FIN. However, the client will never observe this as it is blocked on the call made on the standard input. One of the solutions to this problem is that the kernel would be notifying the process about one or more I/O conditions that are ready. This is known as I/O multiplexing. This is achieved with the help of the select and poll functions. I/O multiplexing is used in the following cases:

+   - When the client is using multiple descriptors, such as reading information from a standard input and maintaining a network socket as well
+   - When the client wants to use multiple sockets it can use the select function
+   - A TCP server can use I/O multiplexing when it needs to handle both listening and connected sockets at the same time
+   - I/O multiplexing can be needed if the server uses both TCP and UDP
