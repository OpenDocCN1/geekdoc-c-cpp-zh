# ## Exception Handling

Before the advent of different error handling mechanisms, every function that is called would return any value indicating how properly the execution went. Program code that called the control would then check the particular return code and deal with it accordingly. The resulting code could be littered with extra if-statements as well as the error handling code. Further, the return value of the function could not return anything but one code.

The generic concept of exception handling is very lucid. The motive is to raise some error flag every time something goes wrong. Next, a system always acts as a watcher for this error flag. Further, the system calls the error handling code if the error flag has been spotted.

If noticed, we have mentioned two synonymous words, but these are not same. These two words are error and exception.

An error typically refers to a problem that exists in a program when it is written and compiled. It could be a logical error that will result in incorrect results. In other words, the code is correct, but the algorithm is wrong. Exceptions are errors or anomalies that occur during the execution of a program. They can be the result of unavailability of system resources, such as memory, file space, and channels, or data dependent conditions, such as a divide-by-zero or numerical overflow. Such runtime errors can cause the applications to behave unpredictably or to crash. Exceptions tend to be rare events, but are predictable.

Given that exceptions are somewhat predictable, how should our programs handle them? Three types of actions can be performed, which are given as follows:

+   - We do not handle the exception and allow the program to die or core dump
+   - We can issue a warning; for example, print some error messages, probably at the point in the code where the exception occurred and then exit
+   - We can handle the exception gracefully and continue executing

Can a same piece of code raise an exception and handle it? Let's consider that an exception arises while allocating a memory. Is the same function or method that attempts to allocate a memory can itself handle the exception raised? Probably some other section of code would handle the exception. This implies a separation between the creation of an exception and its handling. The method in which an exception occurs could just alert its caller. This allows the code that raises the exception to be developed separately from the code that handles it. If we pass exceptions up to the calling routines, it is necessary to have a way to bundle information.

> **NOTE**  
> Exceptions are errors that occur at runtime. When such exceptions occur, a programmer has to decide a strategy according to which he/she would handle them. This systematic handling of runtime errors is called exception handling.
