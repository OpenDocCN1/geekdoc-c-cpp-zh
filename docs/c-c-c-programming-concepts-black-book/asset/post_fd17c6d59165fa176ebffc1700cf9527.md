### socket Function

For any Input/Output (I/O) operation taking place over network, a process must call a socket function with proper type of protocol. A typical socket API has its signature as shown in Listing 22.8:

**Listing 22.8: Showing signature of a socket API**

```c
int socket (int family, int type, int protocol);
```

The header file used for the socket API is `<sys/socket.h>`. The parameter `family` signifies the protocol family, as shown in Figure 22.3:

| family | Description |
|---|---|
| AF_INET | IPv4 Protocols. |
| AF_INET6 | IPv6 Protocols. |
| AF_LOCAL | Unix domain protocols. |
| AF_ROUTE | Routing Sockets. |
| AF_KEY | Key Sockets. |

**Figure 22.3: Displaying Protocols Family Constants for Socket Function**

Another parameter `type` is a constant, which can have any value from the list shown in Figure 22.4:

| type | Description |
|---|---|
| SOCK_STREAM | stream socket |
| SOCK_DGRAM | datagram socket |
| SOCK_RAW | raw socket |

**Figure 22.4: Showing Protocol Type Constants**

The protocol argument in the socket is generally kept to 0, except for raw sockets (raw sockets are out of scope in this chapter). Figure 22.5 illustrates the different families and type combinations which are valid for sockets:

| | AF_INET | AF_INET6 | AF_LOCAL | AF_ROUTE | AF_KEY | Socket type |
|---|---|---|---|---|---|---|
| | TCP | TCP | Yes | | | SOCK_STREAM |
| | UDP | UDP | Yes | | | SOCK_DGRAM |
| | IPv4 | IPv6 | | Yes | Yes | SOCK_RAW |

**Figure 22.5: Illustrating Combination of Families and Type**

Not all combination of family and type are supported. Those which are directly identified by a protocol have a protocol name at the corresponding box and those which are a valid combination but do not have an acronym have “yes” at the corresponding box.

The socket function returns a non-negative integer on success; this integer can be associated with a file descriptor as well. This integer is often called socket descriptor or sockfd. To get a valid sockfd, we need to specify a valid protocol family and a valid type. The AF_ prefix stands for “address family” and the PF_ prefix stands for the protocol family. Previously, it was envisioned that multiple address families will be supported by a single protocol family and the PF_ values would be used to create sockets, whereas the AF_ values would be used for socket structures. But it has never happened that a protocol family is supporting multiple address families. In the <sys/socket.h> header, it is defined that the PF_ values for a given protocol are equal to the AF_ values for that protocol.

### connect Function

The connect function is used by the TCP client to establish a TCP connection with the server. The signature of the connect function is defined in Listing 22.9 as follows:

**Listing 22.9: Defining the signature of the connect function**

```c
int connect(int sockfd, const struct sockaddr *servaddr, socklen_t addrlen);
```

The connect function is defined inside the <sys/socket.h> header. The parameter sockfd mentioned in Listing 22.9 is the socket descriptor that was returned by the socket function call. The second argument is a pointer to the socket address structure and the third one denotes the size of the socket address structure. The socket address structure should contain a valid IP address and a port number of the server. For a TCP socket, the connect call initiates a three-way handshake and establishes the connection. The function returns only when the connection is established or an error has occurred. The following error scenarios occur in a connect call:

- It might happen that the client is not getting any response from the SYN that it has sent to the server. ETIMEDOUT is returned in such scenario.
- It can happen that the server sends a RST in response to the SYN sent from the client. This response indicates that no process is waiting for that host on the server side. The server process is not running on the port that is mentioned in the SYN sent from the client. These sorts of errors are known as hard errors, and ECONNREFUSED is returned to the client when the RST is received. A RST is also known as a reset; this sort of segment is sent by TCP when something goes wrong. Generally, there are three conditions that can give rise to a RST. Firstly, when a SYN arrives on the port at the server side and no process is listening on that port. Secondly, when the TCP wants to abort an existing connection, and lastly, when the TCP receives a segment for a connection which does not exist.
- A connect error can occur when a SYN sent from a client meets an ICMP destination unreachable error from some intermediate router. These sorts of error are also called soft errors.

We would be discussing about all types of TCP connect errors later in this chapter.

### bind Function

The bind function is used for assigning a local protocol address to a socket. The IP address is a combination of a 32-bit IPv4 or 128-bit IPv6 address along with a 16-bit TCP or User Datagram Protocol (UDP) port. Listing 22.10 shows the signature of a bind function call:

**Listing 22.10: Showing the signature of a bind function call**

```c
int bind(int sockfd, const struct sockaddr *ipaddr, socklen_t addrlen);
```

The signature mentioned in Listing 22.10 is defined inside the <sys/socket.h> header. The first argument is the socket descriptor which is returned by the socket call. The second argument is the pointer to the protocol-specific address and the third argument is the size of this structure. Some characteristics of the bind call are as follows:

- A server generally binds to their well-known ports when they start. A TCP client or server is assigned ephemeral ports by kernel if it chooses not to use well-known ports. It is normal for a TCP client to let the kernel choose an ephemeral port for it to use. But a server must bind to a well-known port as servers are generally known for their well-known ports.
- A process can also bind a specific IP address to its socket. The IP address should belong to an interface on the host. For TCP clients, it assigns the source address that will be used by the IP datagrams sent on the socket. A TCP client doesn't bind an IP address to its socket. The kernel chooses an IP for the socket whenever the socket is connected. The selection of the IP address is based on the route required to reach to the server. If a TCP server doesn't bind an IP address to its socket, the kernel checks the SYN packet that has reached the server from the client. The kernel uses the destination IP address of the SYN as the server's source IP address.

We have discussed earlier that with the help of bind call, users are able to specify the IP address and port. Table 22.2 presents the different IP addresses and port combinations:

**Table 22.2: Presenting the different IP addresses and port combination**

| IP Address | Port | Result |
|---|---|---|
| Wild card | 0 | Kernel chooses the IP address and port |
| Wild card | non zero | Kernel chooses IP and process specifies port |
| Local IP address | 0 | Process specifies IP address and kernel chooses port |
| Local IP address | non zero | Process specifies the IP address and port |

For a value of zero as port number, the kernel selects an ephemeral port number while bind is called. If any wild card IP address is mentioned, then the kernel doesn’t assign an IP address to the socket until the socket is connected. For IPv4 addresses, a wild card entry is mentioned by INADDR_ANY, which has a value 0. The following example shows the usage of wild card IPv4 address:

```c
struct sockaddr_in server_address;

server_address.sin_addr.s_addr = htonl (INADDR_ANY);
```

The preceding example can also be used for an IPv4 address, but the same technique cannot be used while dealing with IPv6 addresses. The main reason being that IPv6 is a 128-bit value, which cannot be represented with the help of constants. An IPv6 address needs to be stored inside a structure. The solution to this problem is as follows:

```c
struct sockaddr_in server_address;

server_address.sin6_addr.s_addr = in6addr_any;
```

The system allocates the variable in6addr_any and also initializes it to a constant IN6ADDR_ANY_INIT. The <netinet/in.h> header contains the extern declaration for the variable in6addr_any.

Although it is not mandatory to use htonl for INADDR_ANY as the value will be same for both host and network, still it is a good practice since all INADDR_ constants inside the header <netinet/in.h> are in host-order bytes.

### listen Function

The signature of the listen function is as follows:

```c
int listen(int sockfd, int max_backlog);
```

The listen function call is being made by the server and it performs the following two major operations:

- When a socket gets created by a socket function, the socket is assumed to be active. Active socket signifies that it’s a client socket that will issue a connect call. The listen function converts an unconnected socket into a passive socket which indicates that the kernel will accept incoming connection requests directed to the socket.
- The second argument to the listen function specifies what will be the maximum number of connections that the kernel should queue for this socket.

A listen function is called after the socket and bind call are being made. Let us now have a look into the max_backlog variable and understand its working.

For any given listening socket we come across, kernel maintains the following two queues:

- One is called the incomplete connection queue, which contains an entry for each SYN that has arrived from the client side and the server is awaiting a three-way handshake for the incoming SYNs.
