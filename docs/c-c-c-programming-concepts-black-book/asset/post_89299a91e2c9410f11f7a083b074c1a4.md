When the access specifier for a base class is public, all the public members of the base class become the public members of the derived class, and all the protected members of the base class become the protected members of the derived class. For example, in the preceding program, the object of the derived class can directly access the public members of the base class, that is the set() and showBase() functions. In all the cases, the private members of the base class remain private to the base class and are not accessible by any member of the derived class.

When the base class is inherited by using the private access specifier, all the public and protected members of the base class become private members of the derived class. It implies that they are still accessible by the members of the derived class but cannot be accessed by parts of the program that are not the members of either the base class or the derived class. Therefore, to generalize the access specifier related problems as to which one to use and when, one thing can be done is to make every member's scope public rather than putting some of the members in public definition and others in private. However, in that case, if all the members of the class are made public, the data is going to be exposed to the outside world and security will be breached. Moreover, it is also not aligned with object-oriented programming principles of encapsulation. Therefore, C++ provides the solution for this problem in the form of **protected** access specifier. ### Protected Access Specifier

Class members can always be accessed by functions of the same class, irrespective of the members being public or private. However, objects of a class defined outside of the class, such as in the main() function, can only access the public members of the class. The following program illustrates this concept:

```cpp
class Base {
    int a;
public:
    int b;
    void set() {
        a = b = 5;
    }
};

......

int main()
{
    Base object;
    object.set(); /* Valid Access - as set() is public member */
    object.a = 10; /* Error - 'a' is not a public member of Base */
    object.b = 9; /* Valid Access - as 'b' is a public member */
    ......
    return 0;
}
```

In the preceding program, the Base class has two member variables: ‘a’ with private access specifier and ‘b’ with public access specifier. The Base class also defines a member function set() as public. In the main() function, we define an object of the Base class. The object.set() statement in the main() function gets executed smoothly and the values of the member variables are set to 5 for both ‘a’ and ‘b’. The compiler does not generate any error for this statement because we are calling a public member of the class, which in turn sets the value for the member variables of the class. Now, consider the following statement:

```cpp
object.a = 10;
```

While compiling the preceding statement, the compiler generates an error, as we do not have permissions to access the private member of the class from outside it. Private members of the classes can only be accessed through the member functions. Therefore, if we try to access them directly from outside the class, the compiler will generate a compilation error. Again, the access is fine for the following statement:

```cpp
object.b = 9;
```

The compiler does not generate any error, as the member variable ‘b’ is within the public scope of the class and is visible from outside the class. However, at the same time, it is also vulnerable to different types of threats, as it is not protected from the outside world using the private specifier.

The question that comes to our mind is that in case of private members of a base class, if the private members cannot be accessed from outside the class, then how we should access them from within the member functions of a derived class. This is going to stop us from code reusability as well. The answer to this question is that derived class member functions can access the base class’s member variables, if they are defined public or protected in the base class. However, we do not want to make the member variables public, as that would make them vulnerable to the outside world. Therefore, the option we are left with is to define the variables using protected access specifier. A protected member, on the other hand, can be accessed by the member functions in its own class and is accessible to the member functions of the derived class, unlike private. However, at the same time, it cannot be accessed from functions outside the class, making it private to the outside world.

Table 14.1 summarizes the inheritance and accessibility of access specifiers:

**Table 14.1: Inheritance and Accessibility**

| Access Specifier | Accessible from Own Class | Accessible from Derived Class | Accessible from Objects Outside Class |
|---|---|---|---|
| public | Yes | Yes | Yes |
| protected | Yes | Yes | No |
| private | Yes | No | No |

Let’s now discuss some of the disadvantages of protected access specifier.

### Disadvantages of Protected Access Specifier

Although we have seen the advantages of using protected access specifier in case of inheritance, it also comes with some disadvantages. Suppose we are writing a base class that any class can inherit and making it a part of a distributable library available to the public. Any programmer, who buys this library, can access the protected member of the base class by simply deriving it. This makes protected member a little more insecure than private members. To avoid corrupted data, we can force the derived class to access the member data of a base class using only the member functions of the base class. This way we can ensure a certain amount of security to the member data of a base class, but even then guaranteeing restricted access to base class members is difficult. Using the protected specifier leads to simpler programming, but we need to handle this tradeoff between reusability and security of base class members.
