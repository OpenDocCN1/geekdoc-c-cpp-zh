
- Another one being the complete connection queue. It contains an entry for each of the clients for whom the three-way handshake has already been performed.

When a SYN sent from the client side arrives at the server’s end, TCP creates a new entry on the incomplete queue and responds to the SYN sent from the client by sending a SYN from the server side and an ACK for the SYN of the client. The entry will remain in the incomplete queue until the last and final phase of the three-way handshake takes place or the entry itself times out. The final phase of the handshake is identified by the client ACK toward the server’s SYN. When the TCP handshake completes successfully, the entry is moved out of the incomplete queue and pushed into the end of the complete connection queue. The second argument in the listen function specifies the maximum value of the sum for both the queues.

Some points regarding queue management for the queue mentioned earlier are as follows:

- There are some implementations such as Berkeley which take another factor into account while calculating backlog for the socket. This implementation multiplies the backlog value with 1.5 and considers the result.
- A backlog value of 0 should be avoided while using the listen call. The value has different interpretations by different implementations. Some implementations allow one queued connection, while some do not allow any queued connection.
- At the server end, when the TCP SYN arrives, if the queues happen to be full, the SYN is simply ignored. The server doesn’t send any RST. This happens because the client TCP will retransmit the SYN if the server ignores it. If the server had sent RST, then the client’s connect call would have returned with an error and the connection would have been closed.
- If any data arrives at the server’s TCP socket after the completion of the three-way handshake but before the accept call from the server, the data should be queued by the server.

## accept Function

The accept function is called by the TCP server to return the next completed connection from the front of the completed connection queue. If the completed connection queue happens to be empty, then the process is put to sleep. The signature of the accept function is as follows:

```c
int accept(int sockfd, struct sockaddr_in *cliaddr, socklen_t *addrlen);
```

The accept function is defined within the `<sys/socket.h>` header. The `cliaddr` and `addrlen` arguments are used to return the address of the connected process which happens to be the client. The `addrlen` argument happens to be a value-result argument; before the accept call the value pointed by `*addrlen` is set to the size of the socket address structure being pointed by `cliaddr`. On return from the function, this integer value contains the actual number of bytes stored by the kernel in the socket address structure. If the accept call becomes successful, then the return value happens to be a new descriptor that got automatically created by the kernel. The new socket descriptor refers to the TCP connection with the client. The accept function is called with the listening socket that got created with the socket call and used in both bind and listen. The value returned by the accept call is often referred to as the connected socket. The server normally creates one listening socket which remains till the server is up and running. The kernel creates sockets for each client connection that is accepted by the server. The function returns three values: the first one is an integer return code which denotes whether the function was successful or not. Then the protocol address of the client process is returned through the `cliaddr` parameter and the size of the address is returned by the `addrlen` pointer.
