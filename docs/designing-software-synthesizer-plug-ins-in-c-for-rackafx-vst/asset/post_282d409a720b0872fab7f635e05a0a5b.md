All oscillators are derived from an abstract base class called COscillator. The base class object will also handle updating and calculating all variables, as well as modulating the oscillator's frequency (both linear and exponential), phase shift(for modulation), pulse width, and anything else we decide to add at a later time. Since all oscillators are derived from it, this needs to have attributes and member functions that are common to most of the derived classes. As is typical in C++, if we need some functionality that is not common to the other oscillators, we will subclass an existing object and add the functionality. We do this in Chapter 11.

## 5.28 The COscillator Base Class

The COscillator base class will expose the oscillator interface. It will store all variables that are common to all models

two lines of code:

```cpp
double dAmplitude = Oscillator.m_dAmplitude;
```

use direct access to the variable, it must be declared as public. Using the "declare all variables as private/protected" paradigm, you would write them:

```cpp
double dAmplitude = Oscillator.getAmplitude()
```

```cpp
m_Oscillator.setAmplitude(0.707);
```

This kind of coding fish allows the programmer to read/write access to the variable. However, for variables that both read and write access all the time, deleting the extra get() and set() functions can add code (please don't flood my inbox with every...). Our objects are created with the following convention that makes it easy to remember when to use direct access or functions:

- member variables that control inputs are read/write and declared public; use the dot operator to access them
- member variables that are modulation inputs are write-only and declared protected; use the set() function to control them
- member variables that are used internally and are not read or write will be declared as protected to allow classes to access their property
- variables that specifically connect to a GUI control have the word "control" in them, as m_dpWidthControl
- variables which specifically connect to a MIDI variable or control the word "MIDI" in them
- variables named using Hungarian Notation
- member functions that are called during runtime-rendering are declared as implemented in the .h file of the class definition

When we use the objects together, this paradigm will make more sense. Once we use the modulation matrix and global parameters in there, we won't need to worry about the dot operator on public variables. The synths will always use function calls instead.

## Limits

Modulating parameters requires knowing the limits of the modulated variable. In each of our synth objects, the modulate limits are defined at the top of the .h file. For the oscillator objects these are:

| --- | --- | --- |
| double | m_dOscFo | the oscillator frequency; for pitched oscillators it is the MIDI note frequency; for LFOs it is the control on the GUI |
| double | m_dFoRatio | oscillator frequency (FM/PM synth only) |
| double | m_dAmplitude | the output amplitude (-) |
| double | m_dPulseWidthControl | the pulse width (n % controlled by the GUI) |
| double | m_dModulo | modulo counter value |
| double | m_dinc | phase increment value |
| int | m_nOctave | octave offset |
| int | m_nSitemones | semitone offset |
| int | m_nCounts | pitch offset |
