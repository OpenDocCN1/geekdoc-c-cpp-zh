A fundamental problem is that the data declared a function cannot persist from one call to the next. One solution involves using global variables, which is generally frowned upon. Another is for the DLL to dynamically declare a data structure that will hold all persistent variables and then pass a pointer to this data back to the client. This is very similar to the way callback functions work. During subsequent calls to the DLL, the client passes the pointer back to the DLL so that it may operate on the persistent data. When the DLL is no longer needed, it clears the memory by deleting the structure.

In the C++ programming language, the class-type defines an object that is a collection of member variables and member functions that can operate on those variables or. By packing a plugin-in as a C++ class, you get several advantages: first, all of the C++ (inheritance, encapsulation, polymorphism, etc.) are available during the coding process. Second, rather than allocating a data structure and returning a pointer to the DLL, the client can create a new instance of the plugin-object and pass a pointer to the client. The function that calls is the creation. With a plug-pointer, the client can simply call functions on the object—it does not have to communicate with the DLL until it is time to unload the DLL, or create another instance of the plugin-object. This leads to a third advantage over the C-based DLL: the client can create multiple instances easily. The DLL can serve-multiple instances of the object. Sometimes, the plugin-in is referred to as a server and this becomes another kind of client-server.

# 2.3 The Application Programming Interface (API)

In order for the client-server scheme to work, both the client and DLL/plugin-in must agree on the naming of the functions. This includes the creation function and all of the functions that will be called on the plugin-in. The plugin-object must implement other functions that the client doesn't know about, but they must agree on a basic set of them. Rules must be set up to define the sequence of function calls; the plugin-in's author (that's you) will need to understand how the client uses the object. The client must make sure that it establishes these rules, adheres to them in future versions to avoid breaking the plugin-in. On the other hand, the plugin-in may promise to implement the basic required functions properly to make the plugin-in work and not crash the client. So, you can see that there is an implicit contract between the client and DLL server. This contract is the Application Programming Interface or API. It is a definition of the functions an object must implement to be considered a proper plugin-in, as well as any additional functions that may be called or overridden. It defines the function prototypes and describes how the functions will be called and used. The client manages the API and makes it available for programmers to create plugin-ins for target client.

C++ is especially useful. Since the plugin-in is an instance of a C++ object, the client can specify that the plugin-in is derived of a special base class that the manager defines. The base class is to be abstract, containing virtual functions that the client declares. These virtual functions provide the common functionality of the plugin-in. There are two options here:

+   • the manager defines the base class as abstract as there provides default implementations of the functions. Typically, the implementations do nothing but return a success code. The plugin-in authors then override methods they need. For example, the plugin-in might not care about reporting to MIDI messages, so the default implementation of the MIDI will suffice.

+   • the manager defines the base class as pure abstract class by making one or more of the virtual functions pure virtual functions. A pure abstract class cannot be instantiated; only derived classes that implement all the pure virtual functions may be instantiated. This forms a binding between the plugin-in developer and the client manager since the derived class won't work properly unless it implements the plugin-in functions that the client requires.
