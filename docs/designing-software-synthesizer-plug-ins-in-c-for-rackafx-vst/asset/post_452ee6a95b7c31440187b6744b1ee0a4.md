## 2.38 AU Conversions

### Function Return Types:

Most of the AU functions return an error code of OSStatus or ComponentResult. These are essentially the same thing (both are unsigned integers). The return code for success is noErr for both types. There are many error codes but most are common are:

```
kAudioUnitErr_InvalidProperty
kAudioUnitErr_InvalidParameter
```

### Redeclaration of Datatypes

Like VST3, AU redeclares datatypes such as Int32, UInt32, Float32 etc., so be aware of this. You can always use your familiar datatypes, int, float, double, etc.; however, on occasion you can get burned if you try to override a base class function that uses the redeclared type but you substitute a standard type. The compiler will not recognize your function as an override.

### Scopes and Elements

You will see the argument datatypes AudioUnitScope and AudioUnitElement in several of the AU functions we override. Scopes are used to identify a "major attribute" of an audio unit. Typically you will see input, output and global (both input and output). For example, output bus #2 would use Scope = output and Element = 2 while input bus #1 would use Scope = input and Element = 1.

## 2.39 AUSynth and the AUInstrumentBase

The base for AU synth plug-ins is named AUInstrument. It is derived from another object called MusicDevice, which is derived from AUBase and AUMIDBase. In the application document, you may run across AUMonitimbralInstrumentBase and AUMultimbralInstrumentBase, which are also derived from AUInstrument. These objects were added later in the development of the Audio Units API and are supposed to make your life easier; we do not find this to the case and were quite perplexed that the definition for AUMultimbralInstrumentBase in AUInstrument.h says "this is a work in progress." We decided to bypass these objects and design a straight-up synth plug-in template that you can easily modify. As a bonus, the operation of synth very much parallels the way that RackAFX and VST3 operate, making it easy to move from one API to the next. Additionally, you can easily modify your voice while using AUXXimbralInstrumentBase classes.

The AUInstrumentBase functions need to override and implement can be loosely categorized as follows:

- standard plug-ins initialization and destruction
- function for rendering/processing
- functions to declare user interface ("Parameters")
- functions to handle presets and saved states
- functions to declare custom GUI and MIDI capabilities
- functions to handle MIDI events

We implement all of these on one single synth object; remember, all projects use the same AUInstrumentBase base class handles the rest (and there is a lot of it). You don't have to worry about the implementation details, but it wouldn't hurt for you to examine the AUInstrumentBase object in CoreAudio. Download the MiniSynth project, open the AUSynth.h file and look at the functions.

### Standard Plug-in Functions:

Here the constructor and destructor, which we use to initialize variables and destroy objects.

```c
AUSynth (AudioUnitInstanceComponent);
virtual ~AUSynth();
```

- the constructor's argument is the instance of Audio Unit
- you will allocate memory in the constructor and destroy these objects in the destructor
- you will declare the parameters for the first time here

```
virtual OSStatus Initialize();
```

- this is where you declare your user interface and initialize our synth object- you also initialize your base class by calling its function

```
virtual void Cleanup();
```

- called after user has unloaded the plug-in before the destructor

```
virtual OSStatus Reset();
```

- similar to prepareForPlay() in RackAFX, when the plug-in is first opened and again if the user makes changes to the global settings, such as sample rate or bit depth

### Audio Rendering:

```
virtual OSStatus Render(AudioUnitRenderFlags& ioFlags, const AudioTime& inTimeStamp, UInt32 inNumberFrames);
```

You can ignore the flags and time stamp for now. In inNumberFrames argument is the number of audio frames to process, where frame represents a a sample for mono and a left/right pair for stereo. Since our left and right channels each have, inNumberFrames represents the length of these buffers.

### Functions to Declare User Controls:

In the constructor we will declare the interface controls by first defining the number of controls, then calling SetParameter() once for each control to set the initial value, but the parameter is not completely initialized. This happens in another pair of functions:

```
virtual OSStatus GetParameterInfo();
```

```
virtual OSStatus GetParameterStrings();
```

For each parameter we declare in the constructor, the AU framework will subsequently call GetParameterInfo() and pass the index of the parameter in construction. This happens in a loop after construction occurs. In GetParameterInfo() you decode the index and set the control by declaring:

- control name
- control units
- minimum control value
- maximum control value
- default control value
- if your control is an indexed list of strings (as in Filter Type from Table 2.9)

When you are working on a synth project from this book, use the GUI table to help with the setup—it contains all this information (remember you can ignore the variable declarations).

After AU loops through your parameter setup, for each parameter declared as a list of strings in GetParameterInfo(), the framework will call GetValueStrings(), passing the zero-based index of the string-parameter list. You decode this value and pass back a string of substrings separated by commas, for example "LPF,HPF,BPF" from Table 2.9. When you declared that your parameter was indexed, you set a minimum (0), (maximum string-count) and default value. If your string count does not match the number of substrings in the comma-separated string, you will get a validation error. So, you need to be careful with parameter setup.

### Functions to Handle Presets and Saved States:

Fortunately, presets are fairly to deal with in AU and RackAFX, unlike VST3 where you must serialize yourself. The ones you need to implement are:

```
virtual ComponentResult GetPresets()
```

```
virtual OSStatus NewFactoryPreset()
```

```
OSStatus RestoreState()
```

The AU framework will query your plug-in for a list of names of presets you have compiled into the instrument by calling GetPresets(). You pass it an array of strings that are your preset names. It is OK if you have no presets; our synths have one preset as an example, and you are urged to do more of your own.

The framework calls NewFactoryPreset() when the user recalls one of your factory presets. It gives you a zero-based index value for the preset and you respond by decoding the value and updating your synth parameters using the preset values. One of handling presets is with a simple array that is the same length as the number of parameters in your cloud. This is declared in the .h file:

```c
double factoryPreset[NUMBER_OF_SYNTH_PARAMETERS]
```

The array is declared as a double because all of our non-integer synth parameters are doubles. You could also declare this as a float or Float32 array.

RestoreState() is an optional function that called to restore the plug-ins internal state. If you need to do processing after a preset is loaded, you can implement that here. None of the book projects uses this function, you simply forward it to the base class.
