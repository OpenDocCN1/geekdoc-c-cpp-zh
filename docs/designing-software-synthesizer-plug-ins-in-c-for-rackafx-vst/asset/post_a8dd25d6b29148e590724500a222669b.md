
VST3 is developed using the Common Model or COM programming is a Microsoft invention. Simply stated, COM programming is a way of writing soft components. It is neither a separate language nor an extension to a language. In fact, it is language independent, though course here we will be C+. COM programming is a paradigm that originated from a Microsoft technology of the 1980s called Object Linking and Embedding (OLE), where the idea was to allow you to edit multiple things in one document. It effectively allowed one piece of software—or at least another—as you can see a relationship to plugins, where the DLL "runs" inside the client). OLE was often buggy and sometimes crashed. COM helped fix some of the issues there. Microsoft then used COM in the Direct-X plug-in in the 1990s, parts of which still survive today.

The good news is you won't need to do COM programming if you are using the projects in this book that the code is already written for you. In fact, most of the low-level COM stuff is buried deep inside base classes, and we won't need to go there. However, you will see COM paradigms in the VST3 documentation and in our code. If you want to go deeper into and implement things like Steinberg's expression or give your plug-in ability to load and store banks of presets or other extended functionality, you will have to do COM programming work.

One of the most important things that COM does is that it completely separates the components and plug-in from one another in a safe way. It does this by using the concepts of components and interfaces. A long time ago, soft was written in a monolithic way with a set of variable declarations and a run-loop all packed inside of one executable. As the allocations got larger, software meant that teams of programmers could work on separate components. A special problem with this approach involves making sure that the components fit together and communicate properly, and most importantly that they do not ultimately break the application—also known as a crash. This is where the interface concepts come into play.

Suppose that for some reason, you are determined to pull a big-Chevy V8 engine in your Honda automobile. You will rip out the Honda motor and drag in the V8. The V8 needs to be connected to a Chevy transmission. The Honda transmission mounting plate is the right size and the housing are all metric! What you need is an interface that lets you connect in a robust and safe way. With this Chevy-interface in place, the Honda transmission doesn't know it's connected to a Chevy—as far as it is concerned, it's connected to a Honda engine. Likewise, the V8 thinks it's connected to a Chevy transmission. Interfaces are portable, so you could take the Chevy-interface and connect it to the side of your house so that now a Chevy motor can be attached to it one side and Honda transmission on the other. With the interface established, the two do not need to know about each other, nor do they care about each other's implementation details. They also don't care about the language used to design the other.

This makes a lot of sense for our client-plug design reality. The software doesn't need to know about the implementation of the plug and vice-versa. And, as long as the plug implements the required set of functions, it is guaranteed to be a proper plug-in and loaded into the client's address space. If you've used RackAFX to make a VST2/3 compatible DLL, then you have already seen this. The single RackAFX file works as both RackAFX plug-in, VST2 plug-in, and a VST3 plug-in. This is because it implements three sets of interfaces—it can "dock" to either platform.

Broadly speaking, COM interface is a set of functions whose pointers are laid out in memory a specific way. Writing in C++, a COM interface will consist of member functions on a C++ base class object. Interestingly, this COM base class is also known as an interface. Two C++ classes (interfaces) are pure abstract. When we implement a COM interface in one of our plug-objects, we will derive our plug-object from that interface. In other words, we will inherit from the abstract base class and implement the functions. By making the class pure abstract, it forces the derived class to implement specific functions. This forms a kind of contract between the two.

Once the derived class has properly implemented the required functions, it is now considered to possess the interface and the client can safely use it. If we implement another COM interface that lets us add some new functionality we will add the COM interface to our class declaration and inherit from it—though multiple inheritance is key for implementing multiple COM interfaces on objects. In particular, when you derive from a COM base class (interface), and you implement the base functions, you are “exposing the interface.” The fundamental COM interfaces are in a COM Library. The 32-bit version of COM is packed in OLE32.LIB. VST uses its own version of COM, and these functions are compiled directly into your VST-plugin. The names of the interfaces and functions are nearly identical to the Microsoft version. Remember that COM is a way of programming, so manufacturer variations can exist.

COM objects connect and communicate with the interfaces. If you have any serious C++ programming, you have already used a similar concept perhaps times. Suppose object A needs to call a function on object B—they need to be connected and connection needs to occur. One way to handle this is to give object A a pointer to B (let’s name the pointer pObjectB). Object A then needs that pointer to call object B method:

```cpp
float fCoefficient = pObjectB->calculateCoefficient();
```

There is a safety issue here. Suppose this is part of a large project where one team is working on this component. A junior engineer, cleaning up project, then writes:

```cpp
float fCoefficient = pObjectB->calculateCoefficient();
delete pObjectB;
```

Boom! Object B is destroyed. Object B is used later in another module that another team is designing. Because the project is large, this bug may not appear until months later when a senior engineer connects components. Someone is going to have some explaining to do. COM gets around this problem. The client can only get a pointer to an interface-derived object. With this interface, the client can use the object by calling its methods to query the object. But how can the client get an interface pointer without having a pointer to the object? The answer is when the client creates an object, it does not use the new operator. Instead, it uses a COM function—in VST it is called CreateWindow(); Microsoft’s version is called CreateInstance(). This function creates the object (with the new operator) but does not return a pointer to the derived class. Instead, it returns a pointer to the base interface. But if the client calls the CreateWindow() method, it must have some way of specifying which component it wants to instantiate. We will see how this is handled and don’t worry—most of COM stuff. All objects must expose a common interface that the client uses to connect to. All communication from the client to the plug-in is done via interfaces. If you use Hungarian notation like we do, have become accustomed to naming your C++ classes with a capital "C", for example CProcessor. The capital "I" indicates that it is an interface. Your VST Processor object inherits from IProcessor, and your Controller object inherits from IController. Since all objects must expose a common interface that the client will use to connect to, what should that interface be? Microsoft chooses to call it IUnknown. Steinberg's version is called IUnknown. Either way, the name of "unknown" interface is something that has turned off more a few programmers; it seems confusing. We do not have a better name for it.

Let's wrap this section on COM by learning how the creation function knows what kind of COM object to instantiate. This is done by uniquely identifying each COM object. Your Processor and your Controller objects. When the client creates a VST plug-in, it will use one of these unique identifiers to specify which plugin it wants. It is important that every VST component has a unique identifier. Two developers might accidentally name their plugin the same—GoldenFlanger. As long as you have unique identifiers, the VST host can instantiate both GoldenFlangers without conflicts. If you create a new VST plug-in that has the same identifier as one already loaded in the client, the client will ignore its existence or return an error when asked. Microsoft calls these Globally Identifiers or GUIDs (pronounced "guide-idz”). Steinberg's version names them FUIDs—“foo-idz”. A FUID or GUID is a 128-bit value. The easiest way to generate one is with Microsoft's COM generator, which is called uuidgen.exe. You can find it in your Visual Studio project folder. Launch this executable, and a window will pop up with a button that says "GUID"—you hit the button to copy it to the clipboard. Then, you can paste it into your VST code with a bit of manual formatting. The uuidgen program generates a GUID from a unique timestamp based on the number of 100 nanosecond intervals that has elapsed since midnight of October 1582. This guarantees that no duplicate GUIDs will be generated until year 3400AD. Microsoft calls GUIDs here:

```cpp
GUID({846EB93F-3247-4B8F-A901-10E8EDACC34})
```

Steinberg FUIDs are declared like this (here is the FUID for a Controller object):

```cpp
FUID Controller::cid(0xB561D747, 0xBA004597, 0xA3BF911A, 0x5DA2AFA4)
```

Both Microsoft and Steinberg's IDs are 128-bit, so you just have to format the numbers. For example, to use the above Microsoft GUID as a VST FUID for this Controller you would duplicate the digits as follows, removing the dashes and consolidating:

```
GUID({846EB93F-3247-4B8F-A901-10E8EDACC34})
```

becomes:

```cpp
FUID Controller::cid(0x846EB93F, 0x32474B8F, 0xA90110E8, 0xED4ACC34)
```
