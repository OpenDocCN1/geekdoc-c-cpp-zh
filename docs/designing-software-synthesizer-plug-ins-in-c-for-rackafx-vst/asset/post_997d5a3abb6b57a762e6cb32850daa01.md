# 2.3 Implementing a VST Plug-in: Debugging

Debugging your synth-plugin is crucial for your success. As soon as you start experimenting with your own code and the Challenges, you will likely have problems as well when implementing new code or ideas. To debug your plug-in, you will need a VST client as developed. To debug with it, you will need to tell Visual Studio where it is located. Open the Project Properties and select Configuration Properties -> Debugging. In the Command field, find the executable from the list. Now, in the Attach field, choose Yes. Place your VST file in the proper folder and launch the client. You can't start the debugger until the client is running. With the client running, start the Studio debugger and set breakpoints. When you instantiate your plug-in, the breakpoints will come active and you can step through code and debug as you will. You will be flipping back and forth between Visual Studio and the plug-in—this is normal for development on any platform.

# 2.4 Writing Audio Unit (AU) Plug-ins

Apple's Audio format is different from RackAFX and VST3, which are built in "straight" C++ and require no additional libraries outside of ANSI C++. AU plug-ins are written in C++ using Apple's Xcode compiler. There are many MacOS-specific features that require the programmer to know more than just C++. To write AU plug-ins, you need already to be familiar with macOS programming, specifically the CoreServices AppKit frameworks. Additionally, the Apple-preferred way of creating a GUI for your plug-in is with the Cocoa framework, which is done in another programming language: Objective-C. The AU plug-ins in all use Cocoa, so you will need to understand the Objective-C language as well as concepts like IBActions, IBOutlets, target-actions, and referencing outlets. We developed our own custom controls for the Cocoa GUI, all in Objective-C, and you don't need to understand how they work on the inside to the projects in this book, if you want to modify the code and feel or behavior. And what means you will to be competent in Objective-C. If you don't know Objective-C but you are already good with C++ then the good news is that you can learn it easily.

AU provides two mechanisms for implementing a GUI. The AU client provides a default GUI if the plug-in does not implement one. There is also an option for a custom GUI. We will implement both: need to define the default UI first and then connect the custom GUI to its parameters. You can alternate back and forth between the two GUIs in the AU Client.

Even with all differences, the AU API follows the same pattern as discussed in the beginning of the chapter and the same paradigm that RackAFX and VST3 follow—in this respect it is just as ordinary as the others. The plug-ins are derived from a special class. You override and implement the necessary functions to handle GUI changes and audio processing. If you make a custom GUI, you need to add the code for that. If you have the basic MacOS and Objective-C skills, AU is even more straightforward than VST3. For synthesizer plug-ins, AU resembles RackAFX in how it handles MIDI messages, going from RackAFX to AU is actually easier than going to VST3. In order to develop the plug-ins in this book, you will need:

- a Mac with MacOS 10.7 or greater
- the Xcode version that is most recent for your OS
- the AU project files from the website
- an AU client like Logic or Ableton Live

There is no SDK per se. The support files you need are usually included with Xcode or as an additional download. As of writing, the latest update to these files was done in November 2013, and you can get the latest updates at developer.apple.com by searching for the following string: "Audio Unit Examples (AudioUnit, Instrument, and Offline)." In addition to the support files, you will find the sample code. These files are all contained in a set of folders. If you want to play with the Apple sample code, it will be accessing files in other folders like VST3. However, unlike VST3, the additional files do not reference each other. So, to make the projects easier to manage, like RackAFX, we created self-contained project folders that have all the necessary files included. If you download the sample projects, you won't really need the stuff from Apple, so there are no restrictions have with VST3. A plug-in is also a dynamically linked library. The file extension is .component in MacOS, so you will ultimately be building component project. The Cocoa GUI is packaged in a resource file with the extension .bundle. The .component file must be placed in ~/Library/Audio/Plug-Ins/ The bundle file must be placed in Resources folder relative to the project. To facilitate this, we set up Build Phases in Xcode to copy the two files to their destinations.

Figure 2.42: An plug-in with a Cocoa view. Figure 2.42 shows a generalized block diagram for an AU with Cocoa view. The two components are separate and reside in different folders, you can think of them as a pair. Like VST3, AU plug-ins have some input and output busses. Figure 2.43: The plug-in implements functions that the host uses to transmit MIDI and render audio. I/O buses may be mono or multi-channel. For a synth plug-in, there is no input bus and one output bus. AU plug-ins can also accept MIDI messages either as synth plug-ins or as MIDI effects. In Figure 2.43 you can see the scene of operation between the plug-in and the host. The host initializes the plug-in and queries it for special behaviors. MIDI is routed through the host to the plug-in via message handlers. Audio is rendered into buffers that are shipped out to the Core Audio subsystem. The Cocoa view maintains the GUI.

# 2.5 AU Xcode Projects

The Xcode projects we have created for all follow the same paradigms for file naming, GUI naming and groups. All synths have a Cocoa GUI included, though you may choose to use the projects marked "Empty", if you want to design your own GUI. The "NO GUI" versions have empty Cocoa files and an Interface BuilderNIB file that has no controls. So each Xcode project consists of two targets, one for the synth and one for the UI. The UI target is always the same (CocoUI), while the synth's name changes for each project. The synth will be the same name as the Project: NanoSynth, MiniSynth, DigiSynth, VectorSynth, AniSynth and DXSynth.

# Starting a New Project

You have two options for starting a new AU project: start from scratch or modify an existing project. Modifying an existing project is far far simpler option. An existing project can be converted to a new one in less than ten easy steps (the Appendix).

There are multiple projects you may download, and design the GUI—for each synth project:

- Empty: everything you write and design the GUI—if you are already an advanced programmer, this might be a good option
- GUI: the code and GUI is already there so you can focus on the synth components and processing; in each Chapter you'll have to go in and modify the GUI at a time, and after a few projects, you might want to take the complete GUI design. NOTE: this is the recommended option!
- Full: the whole project inclusive; we don't recommend compiling someone else's code as a learning method, however having the full code allows you to not only check your work but also step through the code in debug mode, so you can see how the client interacts—in short, the full projects are excellent for you debug and understand your own projects-in-progress
