# 2.4 API Function Comparisons

Although the various plug-in APIs differ in their implementations, they share a common set of operations for making a synthesizer plug-in. Table 2.1 lists the common functionality while Tables 2.2–2.4 detail the responsibility for each function.

You can see that each platform is different in implementation and complexity, VST3 certainly wins the prize for most number of supporting files, but you can see that only two functions (setActive() and process()) handle the most of the core functionality. In RackAFX and VST3, the process() function becomes so large that we split it into three functions. In RackAFX there is no GUI to write since we can use drag-and-drop editors, but you will have to write your own in AU (and it's in the Objective-C programming language). The MIDI message handling is simple in RackAFX and AU but complicated in VST3.

Table 2.1: The typical operations of all plug-in APIs.

| Function | Description |
| Construction/Dynamic Memory Allocation | called once the plug-in is instantiated, this function implements any one-time initialization, usually consisting of initializing the plug-in variables, GUI and allocating memory buffers dynamically |
| Destruction | called when the plug-in is to be destroyed, this function deallocates any memory in the One-Time-Initialization/ and in other functions that allocate memory; if there are any child-windows, the plug-in destroys them |
| Per-run initialization | called before an audio session starts; this function is used to flush buffers containing old data or initialize any variables as counters that operate on a per-play basis |
| Render Audio | the function synthesizes the audio and delivers it to the client |
| MIDI Event Handling | functions that handle MIDI messages including on and off, pitch bend, continuous controllers and sustain pedal |
| GUI Control Changes | functions to deal with changes to the GUI controls |
| GUI Setup/Instantiation | functions to deal with the lifecycle of the GUI |

|---|---|---||}{
