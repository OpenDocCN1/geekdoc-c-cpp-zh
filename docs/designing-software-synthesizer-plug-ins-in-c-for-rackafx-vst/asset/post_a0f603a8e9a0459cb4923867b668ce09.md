# Starting a New Project

Starting a new VST3 project from scratch is arduous at best and frustrating at worst. Our strongest advice is to download the sample projects and use them as a basis. We have multiple versions you can download, set for each synth project:

- empty—write everything and design the GUI—if you are already an advanced VST3 programmer, this might be a good option
- GUI—only the code and UI are already done so you can focus on the synth components and processing; in each chapter you'll have the chance to go in and modify the GUI bit at a time, and after a few projects, you might want to take into account the GUI design: this is the recommended option!
- full—the project includes; we don't recommend simply compiling else's code as a learning method, however having the full code allows you to not check your own work but also step through the code in debug mode so you can see how the client interacts—in short, the full projects are excellent for helping you and understand your projects-in-progress

Another method is to start with one of the sample projects, copy the project folder to a project name, then modify the Files and Visual as described in Appendix A. It shows step-by-step how to modify the project to convert anis. It is especially useful using the progression of MiniSynth, DigiSynth, VectorSynth, AnySynth will build up one another. If you really want to start a project from scratch, you can get that information from the website too, but beware; it is not for the faint of heart.

Once you have the SDK installed and a supported version of Visual Studio running, you are ready to develop VST3 plug-ins. However, you will need a way to test your plug-functionality. Remember that a DLL is an entity and requires a client to load it, instances its objects and use it. You will need to install a Visual VST3 host; we prefer C# as it is a Steinberg product, and we need the tightest and most robust integration. Remember to make sure your client specifically supports VST3. The synths will often refer back to this chapter bookmark it for later. Let's get started.

# Project Details

Each VST3 is packaged in a Visual Studio Solution. Its name will depending on your Visual Studio version. VS2008 users need to open projects using the solution (.sln) file while VS2010 and later users will open the .vcn projects; the first is a library project. The second project is your actual synth. The base project differs according to Visual Studio version while the synth project is identical for both. Solution the MiniSynth project is shown in Figure 2.19. We use Visual Filters to group the sets of files accordingly. The SynthCore filter contains all the files for the synth—this will be different for each project. The plug-in files are located in the VSTource

When you compile the solution, it compiles the base project into a static library. Then, it compiles your synth project and statically links to the previously built base. The resulting file is a DLL with suffix changed to .vst3. The only real major issue is that all these files (127 in total) can be difficult to maintain. The sheer of files making these projects from scratch quite tedious. In any event, one thing you must do is decide where the output folder is going to be. This is the folder that will receive the final vst plug-in file. You then copy your file into your VST3 folder and let the client re-scan to pick up the changes. It may be tempting to set the file destination to the client's VST3 folder, saving you the hassle of copying the file. However, this is at your own risk. An issue that is also the output destination for the static library that you compile. The compiler creates and writes a slew of intermediates to this folder that are not deleted upon successful compilation.

To set up your output folders, open the project properties for both the base library and synth. In the Configuration Properties -> General, browse and find your output destination folder. Make this the intermediate directory (also if it is not by default). Make sure to set these folders in both the release and debug configurations (easy to find).

# Additional Files

We have set the VST projects to be as similar as possible. The main difference will be in the SynthCore—the set of C++ objects that make each individual synth. You will get a list of these files for each project, however there are three files that are necessary for each one and are identical:

- synthfunctions.h: a collection of the structures and functions that are used throughout the synth objects; you can add more of your own here
- pluginconstants.h: another collection of structures, functions and objects that are used in the synth projects
- pluginobjects.cpp: the implementations of objects declared in pluginconstants.h

# 2.16 VST3: Processor and Controller

You learned how plug-ins are packaged inside dynamic libraries or DLLs in the beginning of this chapter and how C++ is useful because we can define an abstract base class that the plug-developer uses in his or her derived classes. In RackAFX the base class is called CPlugin, and it implements methods for handling the processing and user interaction with the GUI.

VST2 is similar in that it defines a single base class that handles both the audio processing and the user interaction with the GUI controls. The base class is called AudioEffect, and it inherits from an earlier class named AudioEffect. One of the ways that VST3 is different (that make very different) is that it uses two C++ and Controller objects. You will be spending most of your coding time inside these two objects.

Figure 2.20 shows a simple block diagram—the Processor handles audio input/output while the Controller maintains the user interface. VST3 plug-ins may have any number of audio inputs and outputs and may be side-chained.

Your Processor object will inherit from a base class called AudioEffect (no relation to VST2's base of the same name), and it will handle the audio processing or interaction, in our case, also called rendering. It will receive control change information when the user adjusts a control, and it will modify the processing as needed.

Processor will also receive queries from the client regarding the audio bussing capabilities and audio format capabilities. The Processor also implements the task of serialization, which means the loading and storing of the plug-in at any given time to a serialized binary file. The term serialize is used because the parameters will be stored in series, one after another in the file. This allows the client to initialize the plug-in as it was left when the project was last saved/ closed, as well as providing basic user-preset loading and storing capabilities.

Your Controller will inherit from a base class called EditController. In VST parlance, the terms "edit" and "editor" refer to the GUI or its associated objects and not a text or audio editor. The answer is that your Controller object will receive change information, why do you need a separate Controller object? If the Processor is already controlling change information your Controller object will handle initialization and setup of the GUI controllers and implement the communication mechanism that sends information to and from the GUI. This is a separate job for dealing with the control change messages that alter the rendering of the audio. The Controller also handles the automation of the controls if the users wishes to remember and playback control memories. The Controller must also handle serialization (again) but only on the read-side. Finally, your Controller object will also deal with the setup of MIDI controllers.

To recap, the main VST3 objects implement the following:

# Processor:

- initialization and queries from channel count and audio formats
- handling GUI changes
- responding to MIDI note and off messages
- processing (rendering) the audio stream
- serialization of the plug-in's parameters to and from a file (read/write)

# Controller:

- declaration and initialization of the GUI controls
- implementation of sending and receiving parameter changes
- MIDI controller setup
- read-side serialization
- creation and maintenance of a custom GUI (optional)

Figure 2.20: A VST3 plug-in consists of Processor and Controller sub-components.

There are a few details of the Processor/Controller model to consider. First, the Processor should be able to run completely on its own without the Controller and not need to know about the Controller's existence. You can see that it is already set up for this with control information, processing and serialization—all the basic operations of the plug-in. The desirable configuration is to implement two separate objects, which could not run without knowledge of each, but also run on different processors or separate computers in different locations. Our synth will be implemented in this configuration, as the documentation points out, some plug-ins require more resources that do not allow the Processor and Controller to run on separate processors or in different contexts. Lastly, it is possible to combine the two objects into one, but Steinberg highly encourages this
