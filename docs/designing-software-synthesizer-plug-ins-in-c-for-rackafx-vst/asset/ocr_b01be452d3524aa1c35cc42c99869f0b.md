Broadly speaking, COM interface is a set of functions whose pointer are laid out in memory a specific way. We are writing in C++, a COM interface will consist of member functions on a C++ base class object. Interestingly, this COM base class is also known as an interface. Two C++ classes (interfaces) are pure abstract. When we implement a COM interface in one of our plug-objects, we will derive our plug-object from that interface. In other words, we will inherit from the abstract base class and implement the functions. By making the class pure abstract, it forces the derived class to implement specific functions. This forms a kind of contract between the two.

Once the derived class has properly implemented the required functions, it is now considered to possess the interface and the client can safely use it. If we implement another COM interface that lets us add some new functionality we will add COM interface to our class declaration and inherit from it—though multiple inheritance is key for implementing multiple COM interfaces on objects. In particular, when you derive from a COM base class (interface), and you implement the base functions, you are “exposing the interface.” Packages the fundamental COM interfaces in a COM Library. The 32-bit version of COM is packed in OLE32.LIB. VST uses its own version of COM, and these functions are compiled directly into your VST-plugin. The names of the interfaces and functions are nearly identical to the Microsoft version. Remember that COM is a way of programming, so manufacturers variations can exist.

COM objects connect and communicate with the interfaces. If you have any serious C++ programming, you have already used a similar concept perhaps times. Suppose object A needs to call a function on object B—they need to be connected and connection needs occur. One way to handle this is to give object A a pointer to object B (let’s name the pointer pObjectB). Object A then needs that pointer to call an object B method:

```
float fCoefficient = pObjectB-
>calculateCoefficient();
```

There is a safety issue here. Suppose this is part of a large project where one team is working on this component. A junior engineer, is cleaning up project, then writes:

```
float fCoefficient = pObjectB-
>calculateCoefficient();

delete
pObjectB;
```

Poof! Object B is destroyed. Object B is used later in another module that another team is designing. Because the project is component-sized, this bug may not appear until months later when a senior software engineer connects the components. Someone is going to have some explaining to do.

COM gets around this problem. The client can’t get a pointer to a COM-derived object. It can only get a pointer to an interface on that. With this interface, the client can use the object by calling its methods to do Even use this interface pointer to query the object and ask it it other interfaces. But how can the client get an interface pointer from an object without having a pointer to the object—doesn’t the object need to be created before the client asks it for an interface? The answer is when the client creates the COM object, it does not use the new operator. Instead, it uses a COM function—in VST it is called CreateWindow(); Microsoft’s version is called CreateInstance(). This function creates the object (with the new operator) but does not return a pointer to the derived class. It returns a pointer to the base COM interface instead. But if the client calls the CreateWindow() method, it must have some way of specifying the component it wants to instantiate as the Will Pink MiniSynth object.
