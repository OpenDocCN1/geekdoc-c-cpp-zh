Your constructor is where all your variables are initialized. The very first line of the constructor has been written for you; it calls initUI() which is a method that handles the control and setup of your GUI controls. You never modify the initUI() method; RackAFX maintains this code for you.

# Destruction

When users use the DLL either manually or by loading another plug-in, the client first deletes the plug-in from memory, which calls the destructor. Any dynamically declared variables or buffers need to be deleted here. After destruction, the client deletes the DLL from the process space.

# The GUI

RackAFX uses a two-phase approach to GUI design. The first phase is prototyping—here, you create a set of controls using the main interface consisting of slider controls, buttons and a low LCD control (more than one in a moment). You don't need to be careful about the ordering of the controls. The user-interface is not flashy; it's a set of rows and buttons, but it allows you to rapidly prototype your plug-in. When you set up elements on the Prototype Panel, RackAFX adds members to the .h file of your derived plug-in. Each slider or button-group controls one variable in you. You setup each control with minimum, maximum and initial values as well as the name and data type. RackAFX calculates the variable's value and delivers it to your plug-in, automatically updating it in real-time. In some cases, this is all you will need and there is nothing left to write. In other cases, you will need to perform more calculations or logic processing in order to changing the control.

After your plug-in is completed and tested, you move to the second phase by switching to the GUI Designer Panel. Here, you drag and drop controls onto a blank surface, and you link them to the variables you set up in the prototyping phase. You can also customize the controls to a reasonable extent, changing the sizes, bitmaps, colors, fonts and other attributes. You can re-arrange the controls however you wish. It is not uncommon to provide the user with a more limited final GUI than you implemented in the prototyping phase—you decide you do not want the user to have control over some voicing aspects of your plug-in. Many companies go out of their way to prevent the user from making really horrible sounds by limiting the controls and the ranges on them.
