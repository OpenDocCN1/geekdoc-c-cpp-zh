This kind of coding-fishes allows the programmer to read/write access to the variable. However, for variables that both read and write access all the time, deleting the extra get() and set() functions can add code (please don't flood my inbox with every...). Our objects are created with the following convention that makes it easy to remember when to use direct access or functions:

+   - member variables that control inputs are read/write and declared public; use the dot operator to access them
- member variables that are modulation inputs are write-only and declared protected; use the set() function to control them
- member variables that are used internally and are not read or write will be declared as protected to allow classes to access their property
- variables that specifically connect to a GUI control have the word "control" in them, as m_dpWidthControl
- variables which specifically connect to a MIDI variable or control the word "MIDI" in them
- variables named using Hungarian Notation
- member functions that are called during runtime-rendering are declared as implemented in the .h file of the class definition

When we we the objects together, this paradigm will make more sense. Once we the modulation matrix and global parameters in there, we won't need to worry about the dot operator on public variables. The synths will always use function calls instead.
