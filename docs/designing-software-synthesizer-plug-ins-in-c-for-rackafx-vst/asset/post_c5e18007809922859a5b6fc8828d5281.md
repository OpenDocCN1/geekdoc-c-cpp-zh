# MIDI Note On and Off

These are the two most important MIDI messages we will deal with. We will get into the exact details of these methods in Chapter 8; however, you need to know how RackAFX simplifies some of the work for you, depending on the MIDI message. For the note on messages, RackAFX converts the MIDI byte data into manageable UINT types. The three arguments are:

- UINT uChannel: 0–15 for 16 total channels
- UINT uMIDINote: the MIDI note number 0->127 for the note event
- UINT uMIDIVelocity: the note ON velocity 0->127 for the note event

The first step is to check midiNote and bail out if it is not a channel we are playing or supporting. More details will show up in the next chapter when we look more closely at the MIDI messages. After, we do the necessary event stuff.

# MIDI Mod Wheel

The mod wheel is the standard on most MIDI controllers. It is typically managed separately from continuous controller (CC) messages unlike VST3 and AU, RackAFX decodes and sends this message simply because it is common on such products. The mod wheel value is 0 to 127. With note on and off, RackAFX converts the bytes into UINTs for you.

- UINT uChannel: 0–15 for 16 total channels
- UINT uModValue: the wheel position from 0->127

# MIDI Pitch Bend

Pitch Bend is a special MIDI message because it uses 14-bit value to indicate the pitch bend amount. With a range of 0 to 127 only (seven bits), you would hear pitch transitions that would not sound. For this message RackAFX sends two versions of the pitch bend, once as a signed integer (-8192 to +8191) and as a floating point value (-1.0 to +1.0). 0 represents the center position or no bend.


# 2.15 Writing VST Plugins

Steinberg originally developed the VST-plugin API in 1996 to provide a simple cross-platform compatibility solution. The API for versions 1 and 2 was very basic in comparison to Microsoft's DirectX, a competing format at the time, and VST met with success: nearly every recording and editing software package eventually adhered to the VST client specification. VST2 represents the most mature version of the VST tree. It is likely that there are more plugins available, both commercial and free, in the VST format than any other-in format to date. VST2 plug-ins are packaged in a Dynamic-Link Library with the .dll file extension.

![](img/b42d0dca53f4a889d8162d55f7c8c05d_65_0.png)

VST3 was introduced in 2008, not as an update but rather a complete overhaul and redo from scratch, so VST3 are not directly compatible. Unlike VST2, the plug-in is packed in a dynamic-link library, the extension is renamed from .dll to .vist. In September 2013, Steinberg officially stopped support for VST2 and removed the VST Software Developer's Kit (SDK) from its website. Steinberg's removal and obsoletion of the API means that only all major clients will support VST3. Due to the large number of VST2 plug-ins available, clients will still support VST2 for some time. VST3 provides a wrapper mechanism, similar to the one in Designing Audio Effects Plug-Ins in C++, to wrap VST3 plug-in so that it appears a VST2.

VST2 and VST3 provide two mechanisms for implementing a GUI. The VST client provides a default GUI if the plug-in does not implement one. There is also an option for a custom GUI. We will implement both. We need to define the GUI first and then connect the GUI to its parameters. You can alternate back and forth between the GUIs in the VST Client.

This book covers VST3 only. If you want to get started with VST2, you will need the VST2 SDK (free) and a version of Microsoft Visual Studio (the examples work with VS2008 and VS2010). You can get the SDK at http://www.steinberg.net/en/company/developer.html, and the latest version at the time is 3.6.0. When you unzip the SDK, you will find a hierarchy of sub-folders containing all the base class object files, VSTGUI editor files and sample code. You may place this set of folders anywhere on a local drive, but by suggest placing it in your root directory. The documentation is in HTML in the main directory as index.html—you should open it in your browser and bookmark it; you will be referring to it often. A fundamental issue with the SDK lies in the hierarchical nature of the folders, which manifests itself as #include statements in the files in various folders. In other words, the files are preset to reference each other in this specific directory hierarchy. If you modify the hierarchy, try to move files around, or consolidate or flatten out directories, bad things will happen when you try to either the Steinberg sample projects or any of the projects in this book.

Do not under any circumstances alter the hierarchy of the SDK folders. In some cases you may get away with renaming folders, but in general you should avoid modifying the directories, except in the manner revealed in this chapter.
