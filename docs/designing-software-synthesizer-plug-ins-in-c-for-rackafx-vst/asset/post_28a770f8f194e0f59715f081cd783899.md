# Preface

Many times during the course of the book development, I asked myself what in the world I was thinking. I should write a book with three different plug-in APIs and platforms. Really? In reality, I have very legitimate ulterior motives: to show the three APIs side-by-side in order to demonstrate how similar they really are despite the differences in implementation details. This was one of the points in my first book Designing Audio Effect Plug-Ins in C++, which uses RackAFX exclusively as both a tool and a quick and easy way to get real-time signal processing code up and running it with a minimum of effort. In the last two years, I received correspondence from all over the world regarding that book and the RackAFX software and fortunately it has been very positive. A goal of this book is to get novice programmers with little or no experience in Digital Signal Processing (DSP) into plug-in programming in one semester's work of class time. And since you can compile your RackAFX plug-in into a VST2 product, you can export and run it in other digital audio environments. The idea is after you've trained on RackAFX, you are ready to take on the more complex Application Programming Interfaces (APIs) like VST and Audio Units. It is up to you to filter through the documentation and sample code to figure out functions to processAudioFrame(), interface(), etc. (those RackAFX functions). For many, this was either difficult or impossible, especially when the person had never looked at a commercial API.

I thought back my first API—the Windows 3.1 API from the Software Development Kit (SDK). I had paid for $600 it in 1990. My goal was to learn Windows programming and write an application—if I was in graduate school, I received a ton of floppy disks and a huge set of bound paperback manuals. It seemed like I got my money's worth from the Microsoft Corporation. I eagerly dug into the manuals only to find that there was not one iota of information on how to actually write a Windows application. Nano. Zip. Zero. Of all the functions were completely documented in detail—then you used C programming language to write Windows applications. It was absolutely overwhelming. I was amazed that there was not a chapter called "How to Write a Windows Application" that they said "Step 1: Open Microsoft; Step 2: Start a new project..." If you read my first book, you have seen many step-by-step guides on plug-implementation—experience with the Windows 3.1 API is the reason for that. Nevertheless, I had to get my application running but never this new approach by showing you complete synthesizer projects in all three APIs, side-by-side. You may use whichever one you wish. And I really encourage you to implement at least one of the six projects in all three APIs so you can get a feel for the strengths and weaknesses of each one. I am confident that once you've implemented a synth on all three platforms, you will understand why I wrote the RackAFX software and plug-in API. But this book isn't just a set of synth projects; it teaches how to write plug-ins on each platform and includes chapters on signal processing and synthesis theory. And there is some method including a bit of calculus. Just as in Designing Audio Effect Plug-Ins in C++, I try to keep the heavy math to a minimum, but there's no way to get around it in some places. Another similarity is that this book does not teach C++; you need to have these skills prior to starting the projects. Likewise it is this book not about trick code, optimization, unit testing, or other software theory.

The projects you will write on the following APIs/platforms:

- RackAFX: Windows
- VST: Windows

# Audio Units (AU): MacOS

I chose not to implement the VST3/MacOS versions due to space limitations. Frankly, the code is nearly identical to the Windows version and the VST3 SDK contains sample code on platforms. You may also notice that Avid's AAX API is messy. You must be a registered plug-in developer to develop. This is not a simple process, as you must first prove that you can write and sell plug-ins. In this way, the AAX API is closed and not openly documented like RackAFX, VST3 and AU so I can write the SDK implementation details.

If you read my first, then you know that RackAFX packages itself as a VST2 plug-in by using a C++ wrapper. This obscures the actual implementation details. This body does not work that way—each plug-in is implemented in its native language using the SDK tools; there are no third-party libraries, frameworks or other helpers. You see all the details with nothing obscured. This has the impact on the Audio Units plugins. Their GUIs must be implemented with Cocoa, which is written in Objective C. If you are targeting AU, then you need to know Objective C to understand the programming GUI. We are on that subject, so you should be happy to know all the VST3 and AU plug-ins come with complete pre-built GUIs in the same. In RackAFX, you can use the drag-and-drop editor to create a GUI, but VST3 and AU are different. In VST3 you use the VSTUI design editors. These ship with the SDK. In this body, you use the drag-and-drop editor that VSTUGI offers but is still code for setting up and managing the GUI. In AU plug-ins, you use InterfaceBuilder (IB) that is built into Xcode. If you have created several custom controls for Cocoa so you can create impressive user interfaces. Of course you may use the SDK objects as well.

Another area of improvement in this book came as a suggestion from the first readers. Requested homework assignments. These appear in the form of "Challenges" at the end of each chapter, but not all. This is directly taken from Joe Conway and Aaron Riley in their excellent iOS Big Big Guide, which is the text I use for my iOS class at the University of Miami. The "Challenges" are usually programming assignments and categorized as Bronze, Silver, Gold, Platinum and Diamond from least to most challenging. Solutions are not given, but they should show up at my forum as students and readers implement them.

In the early phases of preparing a book proposal, I needed to make a decision about the synth projects themselves. They could be really simple with plenty of room for expansion or grossly complex with every type of synthesis algorithm possible. The first thing I decided not to feature physical modeling algorithms. The reason is that this could easily turn into a whole book itself and would be much more of a theory book than a programming book. I decided to feature six polyphonic synthesizers using a variety of synthesis techniques. The synths respond to common MIDI controller messages and a modulation matrix that allows you to spin off countless variations on their architectures. I also needed to make sure that there was not overlap of the theory and this book features all oscillators and filter designs. The theory are also different with slightly more examples on analog synthesis.

Chapter 1 is a brief introduction to synthesizer components and basic signal processing in both analog and digital domains. Chapter 2 is the most lengthy in the book; it details how to write plug-ins in all APIs as well as comparing side-by-side and showing the pros and cons of each. The real fun starts in Chapter 3 where you begin your first "training synth" NanoSynth and MIDI messages on your platform. With the MIDI in place, we can move on to the theoretical meat of the book in Chapters 4– Chapter 4 includes the analog and digital signal processing you need to understand the filters and oscillators. Chapter 5 explains the oscillators, and you will add them to NanoSynth project. Next you add the Envelope Generator (EG) and Digital Controlled Amplifier (DCA) in Chapter 6. Chapter 7 introduces the virtual filter models (you will test with different filters); here you add the Mono Ladder Filter for NanoSynth and then you are on to test the other filters. NanoSynth is created in Chapter 8, where you add the modulation matrix and finally make it.
