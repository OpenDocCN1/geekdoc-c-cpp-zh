When you use UML, you can't have two diagrams showing two conflicting associations; thus, we can't have both Figure 3-3 and Figure 3-5 in a single UML model. A UML model must provide a consistent representation of all associations within that model, even when the association would be of a different type in another model.

Another way to look at composition is through ownership. If it makes sense for one object to own another object, this is composition. For example, one LaserPrinter instance would have its own TonerCartridge instance. Another LaserPrinter would have a *different* TonerCartridge instance. That is, the two LaserPrinters cannot share a single TonerCartridge. Thus, you can think of each LaserPrinter instance as owning a TonerCartridge instance. In that case, you can use composition.

# ## Building Components

When you are building software, grouping various classes into *components* is often convenient. This means creating a library of classes. Most operating systems refer to these collections of classes as libraries, but Windows calls them Dynamic Link Libraries, or DLLs, for short. (It's unpronounceable, so we just say "Dee-El-El.") A library is simply a file that contains a bunch of code that other programs can use. The other programs load the library and then call its functions. But nothing particularly magical surrounds the library. It's just a bunch of compiled classes and functions stuffed into a single file. (And it's compiled; it's not source code.)

Or a component might end up in the form of something called a static library. A *static library* is much like any other library in that it contains a bunch of code for your application to use. However, when you build your application, the *linker* (which is the tool that performs the link process) combines the code in the static library directly into your final executable file. This means that your executable file will be bigger than it would be if you link it to a dynamic library; but when you link to a dynamic library, you need to either ship the dynamic library with your application or make sure it's already installed in the user's application. With a static library, you don't need to worry about it. (Incidentally, if you're using a Unix system, a static library gets the `.a` extension, which stands for *archive*, and a dynamic library gets the `.so` extension, which stands for *shared object*.)

If you're doing some sophisticated programming, you can also group classes into a component that you will ultimately put into an ActiveX control or a Component Object Model (COM) object. (These are special kinds of libraries that run on Windows.)

Therefore, you can think of a *component* as a generic way to group classes. Figure 3-6 shows a component. It's a box with a couple of additional little boxes to its left. Inside this component called `MyLibrary`, you can see that we put two classes — one called `Safe` and one called `Lock`.
