## 15.5 文件：全局概览

回顾一下，Linux 中几乎所有东西都是字节序列：文件、目录、I/O 设备、网卡等。此外，Linux 将所有文件都视为字节流，因此它统一地对待所有文件。我们在第 4 章中讨论了 Linux 中目录项的结构——由文件名和 inode 编号组成——以及文件描述符的概念。我们可以通过文件的 inode 在不打开文件的情况下访问文件或其属性。而使用相应的系统调用打开文件后，其内容则通过文件描述符来访问。

### 15.5.1 文件描述符、文件描述符表、文件表和 inode 表

我们在第 4 章和第 9 章中详细讨论了文件描述符的概念。不过，那里的讨论重点是标准文件描述符在 shell 命令的 I/O 和错误重定向中的使用。在本章中，我们从系统程序员的角度聚焦文件描述符的概念与使用，包括标准文件描述符。

文件描述符是以 0 开始的非负整数，用于索引每进程文件描述符表（PPFDTs）。我们在第 4.7–4.9 节以及从第 9.6 节开始的第 9 章中讨论过这一概念。图 4.6 展示了 PPFDTs、系统级文件表（SFTs）、inode 表以及辅助存储上文件内容之间的关系。

多个 Linux 系统调用（包括 open()、creat()、pipe() 和 socket()）会为它们打开或创建的普通文件、管道和套接字返回文件描述符。使用 read() 和 write() 系统调用与这些对象进行通信，就是通过这些描述符完成的。我们将在本章后面讨论 open() 和 creat() 系统调用，并在第 16 章、W20 章和 W21 章中分别描述 pipe() 和 socket() 调用。

进程的数据 I/O 和错误输出也是通过文件描述符进行的，这些描述符对应 Linux 内核为每个进程自动打开的三个文件。正如第 4 章和第 9 章所讨论的，这些文件被称为标准文件：标准输入、标准输出和标准错误。标准输入是进程默认获取输入的位置；标准输出是进程输出默认去向的位置；标准错误是进程产生的错误所发送到的文件。标准输入、标准输出和标准错误的整数值分别为 0、1 和 2。因此，默认情况下，系统调用返回的第一个描述符是 3。但是，如果你关闭了某个标准文件，执行 open()、creat()、pipe() 或 socket() 系统调用时会返回第一个可用描述符，从 0 开始。

### 15.5.2 为什么需要两张表？

Linux 的 PPFDT 跟踪进程已打开的所有文件。SFT 跟踪 Linux 系统中在任意时刻打开的所有文件，并将 PPFDT 与 inode 表连接起来，如图 15.3 所示。

Linux 内核的设计者为什么需要 SFT？为什么不能让 PPFDT 中的条目直接指向 inode 表中的条目？答案是：由于 Linux 允许同一个文件被多次同时打开，它需要跟踪多个读/写文件指针（参见 15.7.5 节）。因此，不能仅靠 inode 来保存一个文件被多次打开时的全部状态，而需要一种单独的数据结构，用于维护那些被多次同时打开的文件的文件指针。SFT 就是由这种数据结构组成的数组（即表），其中每个表项包含一个指向文件 inode 的指针和一个读/写文件指针。

当多个进程同时打开一个文件时，会分配多个 SFT 表项，每个进程一个。进程 P_i 的 SFT 表项包含 P_i 当前读/写文件指针的位置，以及一个指向 inode 的指针。图 15.3 中的示意图显示，student_records 文件已在两个进程 P1 和 P2 中被打开。在 P1 中，该文件的文件描述符是 3，在 P2 中是 5。因为该文件被打开了两次，所以 SFT 中有两个条目，每个条目都指向 student_records 的 inode，并包含相应进程的读/写文件指针位置。

## 15.6 基本文件 I/O 范式

Linux 中基本的文件 I/O 范式是打开、读取、写入和关闭。这意味着进程必须先打开一个文件，然后才能对其执行数据 I/O（即读/写）操作。如果文件不存在，则应先创建并打开它，然后才能对其执行数据 I/O。如果文件是通过 open() 系统调用创建的（关于文件 I/O 系统调用的详细信息，参见 15.7.2 节和表 15.2），则可以按照参数中指定的访问权限创建并打开它。但如果是用 creat() 系统调用创建的文件，则必须先用 open() 系统调用显式打开它，才能使用 read() 和 write() 系统调用进行 I/O。在对文件执行 I/O 的过程中，读/写文件指针的位置可能会改变，以便在文件中所期望的字节位置执行读/写操作。我们将在 15.7.5 节讨论这个问题。读取或写入文件属性则不需要打开文件。我们将在 15.8 节讨论这一主题。

## 15.7 标准 I/O 与底层 I/O

Linux API 为文件 I/O 提供了两个接口：一个通过标准 I/O 库，另一个通过 SCI。由于 SCI 直接位于内核之上，而语言库又构建在 SCI 之上，因此通过 SCI 进行的 I/O 被称为底层 I/O。C 标准库（CSL）接口中的一些函数是独立的，另一些则构建在 SCI 之上。例如，strlen() 是独立的，fopen() 构建在 open() 系统调用之上。通过 CSL 接口中的函数进行的 I/O 称为标准 I/O。

程序员通常更倾向于使用标准 I/O，原因如下：

- a. 库函数在所有系统上都是可移植的。
- b. 通过 SCI 的底层 I/O 接口由于直接与 Linux 内核交互，在时间上可能更高效。但它也很繁琐，因为程序员需要处理缓冲区问题，例如缓冲区的分配/释放以及为 I/O 选择合适的块大小。
- c. 库函数为文件提供带缓冲的 I/O 服务（见 15.7.2 节），而系统调用提供不带缓冲的 I/O 服务。这意味着你可以使用提供带缓冲 I/O 的库函数 fread() 来读取文件数据，也就是说并非每次调用 fread() 都会导致一次 read() 系统调用。因此，如果你的应用需要非常频繁地从文件读取数据，应该使用标准 I/O 函数 fread() 而不是 read()。
