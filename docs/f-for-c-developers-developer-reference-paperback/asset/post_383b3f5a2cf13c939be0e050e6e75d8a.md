# Working with the Asynchronous Programming Model

Even multithreaded programming can solve a number of problems, asynchronous programming is often a better choice. .NET provides support for asynchronous programming via a pattern called the Asynchronous Programming Model (APM). The typical APM has two parts. One is a method called Begin<Operation>—where Operation is the desired name of the asynchronous action—which initializes the operation asynchronously. The other is a method called End<Operation>, which is invoked when the operation finishes. The problem with APM is that it makes the code difficult to understand and maintain because related code is scattered in multiple places.

Asynchronous workflows are designed to solve this problem and simplify asynchronous programming tasks. Listing 6-80 shows how to read a file and write the processed result into a new file asynchronously with an F# asynchronous workflow. If you have a file named tt.txt in c:\MyCode that contains the text "A", the content will become "B" after the execution.

# LISTING 6-80 File with an asynchronous workflow

open System.IO

```fsharp
let encryptFile fn =
    let operation =
        async {
            use fs = new FileStream(fn, FileMode.Open)

            // read the file content
            let data = fs.AsyncRead(int fs.Length)
            let data = data | Array.map(fun n -> n+1)
            use encryptedFile = new FileStream(fn + ".out", FileMode.Create)

            // write the new content to the new file
            do! encryptedFile.AsyncWrite(data)
        }

// start the operation with a three-scenario handler function
Async.StartWithContinuations(operation,
    (fun _ -> printf! "finished"), // print when finished successfully
    (fun e -> printf! "something bad happened, %A" e) // print when exception thrown
    (fun _ -> printf! "user gives up")) // print when operation is cancelled
```

```fsharp
encryptFile @"c:\mycode\tt.txt"
```

There is something unique in Listing 6-80—the let! (pronounced let-bang) and do! (pronounced do-bang). The let! extracts the underlying result of the Async<T>. If you position your pointer over the AsyncRead function, you find its return type is Async<byte>; while the variable data's type is byte[]. The do! is a special case of let!. It is used to handle the Async<unit> type where the return type is unit. The do! is used to start the asynchronous operation. The real computation is started when the operation variable is passed into the Async.StartWithContinuation function. StartContinuation takes four parameters. The first is the asynchronous operation, and the other three are used to specify the normal callback function, exception-handler function, and user-cancellation handler, respectively.

The scattered code no longer exists for let! and do!. You might be thinking that this sounds like the Async and await features in C# 5.0. If so, you are absolutely correct. F# has provided this functionality for many years, and the success of F# asynchronous workflows is the reason C# 5.0 introduces these features.

# Handling Exceptions

The async keyword seems to work nicely with the APM, but how about exception handling? Is it possible to handle the exception as you would code in that that is executed sequentially? The answer is "Yes." Listing 6-81 shows how to handle an exception inside of an asynchronous workflow.

LISTING 6-81 Asynchronous workflow exception handler

```fsharp
open System
let asyncOperationWithException =
    try
        // some operations could throw an exception
        ()
    with
        | DivideByZeroException as e -> printfn "divided by zero"
        | ArgumentException as e -> printfn "this is an argument exception"
```

You might have noticed immediately that this code is not safe. If failwith is put into the try section, the process can be broken down. Catch! The most obvious solution is to add an extra handler function in Listing 6-81. Another approach is to use the Async.StartWithContinuation function, as shown in Listing 6-80. If you like a more F#-oriented approach, examine Listing 6-82, which uses Async.Catch to solve the problem. The FSI result shows that a System.Exception with a "my error" message is caught.

LISTING 6-82 Handling an exception using Async.Catch

```fsharp
open System
let asyncOperationWithException =
    try
        Failwith "my error"
    with
        | DivideByZeroException as e -> printfn "divided by zero"
        | ArgumentException as e -> printfn "this is an argument exception"

asyncOperationWithException
| Async.Catch
| Async.RunSynchronously
| function
    | Choice.1 _ -> printfn "everything is good. No exception"
    | Choice.2 _ ex -> printfn "caught error: %A" ex
```

# Using Cancellation

If everything could be done in the blink of an eye, you might never need cancellation. Listing 6-83 shows how to use a CancellationToken to interrupt execution. Asynchronous workflows can be cancelled when let! or do!. LISTING 6-83 Cancelling an asynchronous workflow

```fsharp
open System.Threading
let syncRoot = ref 0
// define printfn with
let lockedPrintf () =
    printfn "processing... %d" Thread.Current.ManagedThreadId

// with a warning will be generated if used inside a module
let computation(token:CancellationToken) =
    async {
        use! cancelHandler = Async.OnCancel(fun -> cancelPrintf())
        while true do
            lockedProcessingPrintf()
            do! Async.Sleep 100
    }

use ts1 = new CancellationToken()
use ts2 = new CancellationToken()
```

```fsharp
printf "Starting..."

//start the computation with cancellation token
Async.Start(computation ts1, ts1.Token)
Async.Start(computation ts2, ts2.Token)
```

Thread.Sleep(1 * 1000)

```fsharp
lockPrintf "Cancelling..."
ts1.Cancel()
ts2.Cancel()

// give some time for thread to finish
Thread.Sleep(1 * 1000)
```

# Examining Some Asynchronous Workflow Samples

Before proceeding with real-world examples, I first need to present a sample that demonstrates callback and cancellation within an asynchronous workflow. Listing 6-84 presents back-end, callback, and cancellation processes.

# LISTING 6-84 Asynchronous workflow example using back-end, callback, and cancellation processes

```fsharp
open sleep : int -> unit = Thread.Sleep
let print : string -> unit = System.Console.WriteLine

// back-end process
let proc x =
    async {
        print "processing"
        sleep 5000
        print "processed"
        return x + 7
}

// callback function
let callBack i =
    print "in call function function"
    print (sprintf "call value = %A" i)

// async using a back-end process and callback function
let myProcess callbackFunction x =
    async {
        let v = proc x
        callbackFunction v
    }

// function print timer message with cancellation
let timer cancelCallBack =
    async {
        use! cancel = cancelCallBack
        while true do
            print "time..."
            sleep 1000
    }
```
