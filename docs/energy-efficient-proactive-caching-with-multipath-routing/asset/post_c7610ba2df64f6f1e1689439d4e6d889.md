
The constraint (4b) updates from constraint (3d) and M is a sufficiently large number, which represents this node can serve the requests as long as it hosts the required content. For the scenario considering node service capability, M should be replaced by the service rate, i.e. the number of requests that a node can serve during the time period T, which is given by (30). Constraint (4c) replaces constraint (3c) and (3d), where all served flows for content n at AR a should exactly match the number of requests.

Regarding the time complexity of aforementioned models, we have the following theorem:

## Theorem 1. The ILP models (P1) and (P2) fall into the family of NP-hard problems.

Proof. For (P1), we will establish the proof by showing that model (3) is a generalization of the uncapacitated facility location (UFL) problem where UFL is a well-known NP-hard problem. Suppose the network is a tree topology and all users request the same content, then the distance between any two nodes is unique. In addition, the link capacity x_e and y_ea. Consider the case that the caching space and link bandwidth are infinite, i.e. w_i = c_j = +\infty, and hence, constraints (3b) and (3c) can be relaxed. Furthermore, let \lambda_a \ge 1, \forall a \in A. As a result, constraint (3e) is guaranteed by (3b), and \lambda_a can be safely divided on both sides of (3b). In the end, (P1) can be rewritten as a UFL problem as follows:

```
min_{x, y} \sum_{a \in A} s: T_a x_s + \sum_{n \in N} \sum_{a \in A} (b \cdot s - N_n) y_{nae} \quad (5a)
s.t. \quad y_{ae} = x_s, \forall a \in A, e \in e^0; \quad (5b)
\sum_{e \in e^0} y_{ae} = 1, \forall a \in A; \quad (5c)
x_e \in \{0, 1\}, \forall e \in e^0; \quad (5d)
y_{ae} \in \{0, 1\}, \forall a \in A, e \in e^0. \quad (5e)
```

This means (P1) is at least as difficult as UFL. Thus, we have proved that (P1) is NP-hard.

Similarly, by setting \lambda_a = 1 constraint (4c) and relaxing model (4) as above, (P2) can be converted to UFL optimization model, which means (P2) is a generalization of the UFL problem, and consequently (P2) is NP-hard as well. \(\square\)

Therefore, due to the curse of dimensionality it is challenging to solve problems (P1) and (P2) in a reasonable time when the network instances become large. In order to accelerate the computational time and provide decision making that is amenable for real-time operation we propose a Greedy Simulated Annealing Caching (GSAC) algorithm in the next section.

## 4. A metaheuristic optimization algorithm

In GSAC, the original optimization model is decomposed by the content categories and these contents are allocated in descending order, i.e. the network serves the content with the most requests first. Then, for each content assignment, we employ a simulated annealing algorithm to allocate popular content in the most suitable nodes.

Simulated Annealing (SA) [46] is a well-known optimization method for approximating the global optimization of a given function. SA is an annealing process by statistical mechanics concepts, and it is motivated by an analogy with the behaviour of physical systems during the cooling process. It can be deemed as a powerful heuristic method which is suitable for global optimization which requires no particular assumption on the structure of the objective function. Compared with other evolutionary algorithms such as genetic algorithm, SA can provide competitive solutions with faster convergence. The main structure of SA contains two nested loops, where the external is controlled by the temperature and the internal is managed by a Markov-chain length. In each loop a new solution is produced which then compared with the previously stored result. The new solution is accepted if its performance is better than the previous otherwise, the new solution would be accepted with some predefined probability. The iterations continue until meeting the stopping criterion.

Regarding the optimization model (P1), the solution generated in each loop includes the decision variable x_e and y_{ap} (here we deal with the sub-problem oriented towards specific content n, so n is omitted from the subscript notation for simplicity). Note, however, that the decision about those two variables, i.e., x_e and y_{ap} might result in an infeasible allocation. To restore feasibility, we set x_e as the pivot variable. Then, once x_e is allocated, y_{ap} can be determined as follows,

```
[y_{ap} = 1, \quad \text{if } \sum_{e \in e^0} x_e = 0 \text{ and } l_a > 0];
[y_{ap} = 1, \quad \text{if } ((a, p) \in l_a, x_e = 1, 1 \leq N_{na}, b \leq c_j, \forall a \in A, \exists e \in e^0, l \in p \in P_a];
[y_{ap} = 0, \quad \text{otherwise.}
```

If there is a request in RA (i.e. l_a > 0) but all caching nodes e \in e^0 do not host the required content (i.e. \sum_{e \in e^0} x_e = 0), then the request is redirected to the backbone server (via the shortest path (i.e. p = 1)). If there is a request in RA (i.e. l_a > 0), some nodes host the content (i.e. x_e = 1, \exists e \in e^0), and the connected link l guarantees the transmission bandwidth (i.e. b > c), then the request is served by the nearest caching node (i.e. e) to alleviate the network congestion.

The determination of y_{ap} in problem (P2) is as follows:

```
[y_{ap} = \lambda_a, \quad \text{if } \sum_{e \in e^0} x_e = 0 \text{ and } l_a > 0];
[y_{ap} = |c/b|, \quad \text{if } ((a, p) \in l_a, x_e = 1, 1 \leq N_{na}, b \leq c_j, \forall a \in A, \exists e \in e^0, l \in p \in P_a];
[y_{ap} = 0, \quad \text{otherwise.}
```

Similar to the multicast case, all requests are served at the backbone server (0) in the cache-miss case (i.e. \sum_{e \in e^0} x_e = 0, \lambda_a > 0). If some nodes host the content and the link capacity is sufficient to support at least one request transmission, then we keep allocating routing paths according to the bandwidth (i.e. y_{ap} = |c/b|) until all requests are assigned or no more link is available; Otherwise, the routing assignment is neglected.

The details of the proposed GSAC framework is depicted in Algorithm 1. There are four hyperparameters involved as explained in the sequel. The L parameter controls the internal loop from line 8 to 20, whilst parameters T_0, T_{end} and \gamma manage the external loop from line 7 to 21. Moreover, the current temperature T_m influences the acceptance probability, i.e. the external loop of the GSAC algorithm. In line 2, we compute the k-shortest path via Yen’s Algorithm where the time complexity is O(K|E|^2) and symbol | | represents set cardinality. In this paper, we consider the 5-shortest paths, i.e. k = 5, and we require the path for each AR a. Consequently, the time complexity of line 2 becomes O(|A| k |E|^2). For each external iteration of simulated annealing, the temperature is reduced by \gamma from T_0 to T_{end}. Suppose I is the number of external loops, then there is \gamma^I = T_{end} / T_0 when terminating. In most cases, the cooled down factor \gamma is between 0 and 1. Therefore, we have I = \lceil \log_\gamma(T_{end}/T_0) \rceil. It is clear that the number of internal loops is L. In each external loop, the worst case is enumerating the combination of a, e and p when determining decision variable y_{ap}. In addition, the time complexity of checking whether y_{ap} is O(|A||P||E|). Note that we need to assign caching location for each content n \in N^c. In the end, the time complexity of Algorithm 1 becomes O(|L| \cdot |A||P||E|^N + |A||E|^2).

The configuration of hyperparameters depends on the scope of problem. In this paper, after several rounds of grid search and by considering the trade-off between time complexity and performance, the best configuration is recorded as follows: T_0 = 10^6, T_{end} = 10^{-4}, \gamma = 0.9 and L = 300.

## 5. Algorithm deployment

In this section, we first introduce an integrated ICN and MEC platform in a 5G environment for the proposed caching schemes deployment. Then we briefly describe the workflow during a caching time slot.

### 5.1. Architecture of the integrated framework

The amalgamated platform is presented in Fig. 2 based on [47,48], which consists of 5G network, MEC, ICN, and network virtualisation technologies.

Unlike the 4G network, 5G is more than a network; it brings a global ecosystem that promises not only to provide massive data traffic and connectivity with high reliability, but also to support massive communication types. The 5G core network evolves to a service-based architecture (SBA). As shown in the top left of Fig. 2, five key network functions (NFs, i.e. network repository function — NRF, policy control function — PCF, network exposure function — NEF, access and mobility management function — AMF, and session management function — SMF) are connected via a service-based interface (SBI) message bus. In particular, NRF maintains NFs and their profiles; PCF controls network behaviours; NEF exposes services and available resources within and outside core networks; AMF manages end device connection; and SMF is primarily responsible for the session context with the user plane function (UPF). Additionally, UPF is used to route and forward caching content.

MEC refers to the platform that provide computing, caching and other kinds of services at the network edge, which can release backhaul congestion and achieve quality of service (QoS) for the 5G network. On the right-hand side of Fig. 2 are the MEC functional entities. The MEC orchestrator acts as an external application function and communicates with NF via the NEF interface, which is responsible for maintaining the entire system. Moreover, the proposed caching strategies (i.e. optimization model as user QoS) and those behaviour and prediction algorithms are used to achieve prediction accuracy. According to the user request forecast [36–45] and the caching in the MEC orchestrator. After the caching decision is determined, the content and transmission path routing policy can be distributed via the NEF-PCP-SMF-UPF route. The MEC host, which contains a MEC platform and a virtualisation infrastructure, provides compute, storage, and network resources for the MEC applications. Additionally, the ICN caching service is viewed as a MEC application. The network available resource information, like memory space and link bandwidth in the local ICN data network (ICN-DN), is collected by the virtualisation infrastructure manager in the MEC host level, and then is maintained in the MEC orchestrator. To support the caching service, the MEC host can be deployed on access routers, forward routers and even data servers.

### 5.2. Illustration of working process

The proposed algorithm can be extended to various ICN implementations, like Data Oriented Network Architecture (DONA) [49], Content Centric Network (CCN) [50] and Named Data Network (NDN) [51]. Here we use the NDN as an example to further illustrate the workflow. The working process of the proposed algorithm is presented in two phases: the content deployment phase and the flow service phase.

The content deployment phase is presented as follows:

- Step 1: The MEC orchestrator collects the current user behaviour information from access routers and the network available resource status (like storage space and link bandwidth) from all caching nodes.
- Step 2: The MEC orchestrator calls the predicted algorithms, such as user mobility prediction and request preference forecast, to estimate the user behaviour in the next time slot;
- Step 3: Based on the prediction and available network resources, the orchestrator call the proposed algorithm to determine caching locations and relevant routing path;
- Step 4: The orchestrator distributes the routing path to all routers by broadcasting, and proactively pushes the content from the original data server to the routers according to the caching decisions;
- Step 5: Based on the received routing path, the router updates the Forwarding Information Base (FIB) by translating the path to the representation of interface, and caches relevant content in the Content Store (CS).

- Step 1: Access routers receive requests from connected end-users and record for the next time slot estimation;
