The communication transmission energy consumption is measured by the number of hops the network traffic and can be given by,

\(E^t = \sum_{n \in \mathcal{N}} \sum_{a \in \mathcal{A}} \sum_{e \in \mathcal{E}^o} \sum_{p \in \mathcal{P}_{ns}} \beta \cdot N_{nps} \cdot s_n \cdot y_{nps}.\) (2)

# ## 3.3. Optimization model

In this subsection, we consider two types of content delivery mode, i.e. the multicast and the unicast mode. For modelling simplification purposes, the following optimization models are under the assumption that the user's interested content is already known by request prediction, which indicates \(p_{kn}\) becomes a binary indicator to bridge user \(k\) and content \(n\). To lay out how the user request can be predicted, we introduce related algorithms from two perspectives. Please note that this brief introduction is not exhaustive since the request prediction is beyond the scope of this paper. From the view of aggregated content popularity prediction, the Zipf model [36], the shot noise model [37],

and the stochastic block model [38] are widely used models for the case of static popularity, time-varying popularity, and location-dependent popularity, respectively. Recently, deep learning has become an active method for popularity prediction [39–41]. From the aspect of individual user preference prediction, it can be predicted by collaborative filtering [42] which predicts the histories of the similar user and the similarity among users. The typical collaborative filtering model includes matrix factorization [43], latent Dirichlet allocation [44], and probabilistic latent semantic analysis [45]. The influence of the predicted accuracy on system energy consumption is discussed in Section 6. Moreover, in this paper we focus on delay-insensitive requests, such as non-real-time HTTP video downloading and video on demand services. Therefore, the latency constraint for energy-efficient caching is not considered in the latency models and would be studied as a future work.

# ### 3.3.1. Multicast mode

The ILP model is formulated as follows:

\((\text{P1}) \quad \min_{x_{ns}} E\) (3a)
\(\text{s.t.} \quad \sum_{n \in \mathcal{N}} s_n \cdot x_{ns} \le \forall n, \forall e \in \mathcal{E}^o;\) (3b)
\(\sum_{n \in \mathcal{N}} \sum_{a \in \mathcal{A}} \sum_{e \in \mathcal{E}^o} \sum_{p \in \mathcal{P}_{ns}} b_n \cdot B_{nps} \cdot y_{nps} \le \forall l \in \mathcal{L};\) (3c)
\(y_{nps} \le x_{ns}; \forall n \in \mathcal{N}, a \in \mathcal{A}, e \in \mathcal{E}^o, p \in \mathcal{P}_{ns};\) (3d)
\(y_{nps} \le s_{ns}; \forall n \in \mathcal{N}, a \in \mathcal{A}, e \in \mathcal{E}^o, p \in \mathcal{P}_{ns};\) (3e)
\(\lambda_{nu} \sum_{e \in \mathcal{E}^o} \sum_{p \in \mathcal{P}_{ns}} y_{nps} = \lambda_{nu}; \forall n \in \mathcal{N}, a \in \mathcal{A};\) (3f)
\(x_{ns} \in \{0, 1\}, \forall n \in \mathcal{N}, e \in \mathcal{E}^o;\) (3g)
\(y_{nps} \in \{0, 1\}, \forall n \in \mathcal{N}, a \in \mathcal{A}, e \in \mathcal{E}^o, p \in \mathcal{P}_{ns}.\) (3h)

The objective function (3a) aims to minimize the total energy consumption, which is introduced in Section 3.2. Constraint (3b) relates to the storage space used for caching which should not exceed the node capacity. Constraint (3c) satisfies the link bandwidth limitation. We note that \(B_{nps}\) is a binary indicator, where \(B_{nps} = 1\) means that the link \(l\) is in path \(p \in \mathcal{P}_{ns}\), and \(B_{nps} = 0\), otherwise. Therefore, \(\sum_l \sum_p \sum_s B_{nps} \cdot y_{nps}\) selects all links used for content \(n\) delivery. Constraint (3d) limits the source of delivery path should host related contents. Moreover, in constraint (3e) when \(y_{nps} = 0\), \(y_{nps}\) is forced to be 0, which means the delivery path to AR \(a\) should not be assigned if there is no such requirement in that AR and not in constraint (3f) if \(\lambda_{nu} \neq 0\), \(\sum_{e \in \mathcal{E}^o} \sum_{p \in \mathcal{P}_{ns}} y_{nps} = 1\) guarantees that at least one requirement of AR \(y_{nps} = 1\) locate a delivery path since content \(n\) is requested at AR \(y_{nps}\). To locate a delivery path efficiently, it is necessary that when dealing with caching allocation, we only focus on the storage node \(e \in \mathcal{E}^o\) such as constraints (3b) and (3d); however, for the path assignment, we consider both the caching node \(e \in \mathcal{E}^o\) (for cache hitting case) and the core network server (0) (for the cache missing case), like constraint (3c), (3e) and (3f).
