# # How Do I Convince My Manager?

The simple answer is don't. it's easier to ask for permission than to permission. Just do it. When it comes to technical works, why will your manager care? Managers want delivered on time, with budget, and no bugs. They want to please their users and clients. If we use TDD, if we pair, or we have continuous integration? Beside us, no.

If we asked managers, "Does the code need to work? If it is OK if we use TDD every time we check the test?" would their answer be? "Sure, ahead and write the code you can produce. That's what we need. Use the tests only to call and complain if they are unhappy." If your managers say, make sure your code cares about the mental health hospital or find other method.

We are expected to deliver quality solutions. We are expected to deliver good solutions. When it comes to TDD, documentation. Don't put a test on the code before "unit testing." It's not a test. You can't write a test if you don't have any code. Then you have two tasks: one to write this service class and another hour to write unit tests. They aren't separate tasks. In this case you have just a two-hour test to implement a class that works. Regardless, of which type it is, part of the coding and not a separate task.

When you do, make sure you deliver value to your customers. Be transparent and honest about your progress, unless they ask, don't highlighting all the minor details about how you are implementing your code-it's not important. I'm not saying to lie or hide anything, I'm just saying that your manager will care if specific amount of time to write your code or unit tests is totally pointless. What matters for manager when you are going to release the code, is that the code works according to the business specification and is in production (or ready for acceptance testing (UAT)). TDD and refactoring are part of our coding task. The more technical details you expose, the more managers feel they can discourage you.
