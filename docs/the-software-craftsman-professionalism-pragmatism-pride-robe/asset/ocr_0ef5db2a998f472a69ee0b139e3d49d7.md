# # Don't Block the Internet

I've heard about interviewers who don't allow candidates to use the Internet during coding activities. 'That's a good way to measure what they can really doing,' they say. What would happen to these interviewers if they didn't have access to the Internet at work. Do they really expect everything off of their heads? They can really develop systems without searching for anything online?

Being able to research and better ways to solve problems is an essential skill for any software developer. Removing Internet doesn't just make sense. If the interviewer thinks that interview would be jeopardized because the candidate could find the solutions on the Internet, she should probably change her interview.

# # Don't Code on a Piece of Paper

Asking candidates to code on a piece of paper (or on whiteboard) is a very stupid idea when interviewing developers. I don't think interviewers should allow candidates to do that they can't do themselves, or that doesn't reflect the reality that they can do if they get the job. Should the candidate write and refactor the code on paper, too? Should the candidate tear the paper in small pieces and refactor as she gets more understanding about the problem?

There is a difference between being a teacher in high-school—students to produce algorithms in pseudocode—and a professional software. When hiring professionals, we should look for developers who use tools and techniques which can produce well-crafted code through testing and refactoring. We should look at real code with real tools and not some snippets on a piece of paper or whiteboard.

# # Don't Use Algorithms

Which coding exercise should we give to candidates? Although sounds like a very reasonable question, the question to be asked is: what are the values we value most?

Many interviewers choose exercises for their coding interviews. However, not many of them work on systems where a deep knowledge of algorithms is needed. 'I'm checking the candidate's ability to solve,' they say. This is a fair point, interviewers can achieve the same results using exercises that are closely related to their projects.

The majority of the problems I've seen in different systems over the years were not related to how algorithms work. The most common problems were lack of tests, or at least, good tests; design and cohesion lack; refactoring as new features are introduced; constant change of requirements; and deficient domain models, and so on. Those were the real problems I've seen most. By nature, algorithms are procedural and better implemented in a functional style. We don't create classes or model the business when implementing an algorithm.

If the most problems we have in our system are not about algorithms, then we should not use algorithms in our interviews. We should focus on giving candidates exercises where they need to design a solution and solve the business domain. We need developers with good skills in Test-Driven Development and design, we should use exercises that reflect that.

However, if all is about algorithms, then of course, we should definitely test for that. The point is not about not or using algorithms for our coding interviews—it's about testing candidates according to the things we value and what is important for the project.

# # Don't Conduct Phone Interviews

Phone interviews are only needed when the quite process is poor. Many companies conduct them before inviting the candidate for a face-to-face interview. The purpose is to verify whether the candidate can satisfy the minimum of requirements for the job

Although they serve a purpose—avoiding wasting time on much face-to-face interviews—I find them impersonal and somewhat mechanical. Phone interviews tend to be quite, with a sequence of questions and answers, with not much time for a real conversation. The reason is because the interviewer is in a rush to ask the questions she needs to in order to decide if they will or not invite the candidate for a longer interview.
