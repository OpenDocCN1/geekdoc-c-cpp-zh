# We Want to Do the Right Thing

We don't write bad code on pressure but we are constantly trying to find ways to do it. Over time, I realized that we have a wrong notion of time. When we are under pressure, we always feel need to rush. Sometimes pressure is put on us by others but more than not. The pressure is itself. When working with people, in an Agile fashion, where we feel the pressure in the work done, the debt tends to rise when we are on to us. We make our expectations and out our plan. We are OK with them telling us how long things are going to be done. Even then, even then, we always have have to deliver the tasks we commit to. We never have the time to do right

Pressure always be a burden of developer's life, and when we are under pressure, we end up cutting corners. We don't like to do that. We really rarely do that because we feel that we need to go faster. When we feel that we will be doing a good job if we provide the best with the features as fast as we can, we feel like delivering a solution as fast as we. Fast does not mean quality, and unfortunately, we are not understanding the implications of our own decisions. 

# A Busy Time with No Time to Spare

I joined a team in a large organization. The pressure was and the developers were really hard to cope with. First I had very little time to get my environment set. The project was a nightmare to configure in our integrated development environments (IDEs). We were using Java and it was getting me to implement the project. The project had more than 70 classes and many circular dependencies. After a few days, I had very little local experience.

The project was using the Java Enterprise Edition (JEE) container, had dozens of inbound and outbound interfaces with many other systems. When working with one of the guys (who was uncommon, but I insisted it) while he was running the system in our testing environments, placing messages into a queue, and looking at logs, he would look like then he made some changes in the code in making, package the application, copy it to the test environment, deploy the application, place a message in a queue again and look at the logs. It was as if he was in a while loop. He was doing it over and over, adding more logs to the code, which was resulting in the testing environment. I asked him why he was not testing the application on him. He said that it was not possible to run the application so he had to adds logs of statements to the code, then use the testing environment to try figure out what the application was doing. Apparently he had changed something, and the expected change was not arriving expected. After two hours of coding and XML files, adding lots of logs to the application—those types of logs indicate that a certain part of the code was executed—finally found out what we was wanting. So he went back to his local machine, changed the code, changed a few ones to print out more information, and started the application again.
