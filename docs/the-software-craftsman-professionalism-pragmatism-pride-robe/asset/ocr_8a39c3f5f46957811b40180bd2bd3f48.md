Working with legacy code is almost like solving a big jigsaw puzzle. We don't put all the small pieces together at the same time. By separating the pieces into groups, often starting with the corners and then separating the other pieces by color, pattern, and so on, this in turn will help us see a few small pieces and start forming a well-defined model in our heads. What was once a mess (or a big ball of mud) is now a bunch of small pieces of non-related parts. It is not very helpful or confusing, but nonetheless progress is being made. Bit by bit, we start working on one of these groups (or part) and we start putting pieces together (writing tests for the existing code) to help us with understanding of the code, and refactoring.

Once we start putting pieces together, we start to see a bigger picture. We get excited because now it's getting to make sense and we are happy that we are making progress. The more pieces we put, the more we feel, the more we get excited about finishing the jigsaw puzzle. The more pieces we put, the easier it is to get the remaining pieces together. And that is exactly how we feel when working with legacy code. For every piece of code we make, the more we want to make and the investment is now obvious. What was messy before was clearly hard to read and understand now looks like a book, and every developer can understand it, not at all. But when a well-defined code is (covered by tests, easily covered, and well-documented) we will feel helped when adding new frameworks that we wanted to use. We could then use some modern libraries. We could then throw a lot of old code away and replace it with a framework that will not break the other. With that, we don't even need to worry en friends working on green-field projects anymore.

Another interesting thing about legacy code is that it forces us to think in a different way. In green-field projects, when wanting a new feature we can just build it in. In legacy code, we can't even instantiate a class in order to test it all its dependencies. A change in one place can cause an impact on other obscure parts of the application. We have two options here. We can either see all the challenges of working with legacy code as a pain in the neck or see them as interesting problems to solve. I personally prefer the latter. It is easy to say that this piece of code is badly written. It is easy to complain or even laugh. But the question is: are you good enough to make it better?

# Personal and Client Satisfaction

Refactoring code can sometimes be a lot of time and very valuable. However, although it is OK to have fun and enjoy what we are doing, we always need to remember that we are professionals and being paid to help our clients to achieve their business goals. Companies are investing a lot of time and money on software projects. With every investment, clients want to maximize their return and we do our part to make that happen. The more we improve and keep the software clean, the more the client will be able to benefit from it. Stretching the life span of an application maximizing our client's return on investment.

At the end of the day, it does not matter if we are working on a green- or brown-field project. Our attitude towards our job will make it more or less enjoyable.

# Summary

If a piece of software is maintained for more than a few months or weeks, neglecting its quality in order to go fast is an illusion. Many companies become hostages of their own software—their business agility lack of flexibility is totally related to how fast the software can be changed or improved. The worse the quality is, the harder it will be to make changes to it. The longer it takes for a company to change or improve its software, the slower the company will be to react to changing market conditions.

Companies and developers need to understand that regularly taking time to sharpen their tools is not a waste of time. In fact, it is the best way to save time and keep moving forward.
