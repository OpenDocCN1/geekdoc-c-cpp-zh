# Four Rules of Simple Design

Before thinking about architecture, design patterns, generic solutions, or anything else, as a rule, a software craftsman always tries to write code that satisfies the "Four Rules of Simple Design," as defined by Kent Beck

+   1. Pass all tests
2. Clear, expressive, and concise
3. Duplicates no behavior or configuration
4. Minimal methods, classes, and modules

Over the years, many people reowed these four rules (or elements). I personally prefer J. B. Rainberger's version:

+   1. Passes all tests
2. Minimization duplication
3. Maximizes clarity
4. Has fewer elements

There is a lot of debate about the right (in terms of importance) of these elements. As J. B. Rainberger defines it, if we assume that craftsmen practice TDD, rule number one is the obvious, it it can be ignored if we strive to minimize duplication (rule), we would have fewer elements, the fourth rule because irrelevant. With in mind, we just end up with two rules:

+   1. Minimization

I would favor clarity over abstractions that represent business concepts, as a guideline, in order to achieve a simple design, I first focus on good and nice abstractions then focus on removing duplication, which usually leads to a messy and loose-coupled code. When removing duplication, new structures emerge, which forces me to maximize clarity, and then remove duplication. I stay in this cycle, working in very short iterations, until I'm done. This cycle was first described by Rainberger as well

Combined with the knowledge of Domain-Driven Design and the SOLID principles, this approach is normally enough to achieve well-crafted code without following logic of design and architecture.
