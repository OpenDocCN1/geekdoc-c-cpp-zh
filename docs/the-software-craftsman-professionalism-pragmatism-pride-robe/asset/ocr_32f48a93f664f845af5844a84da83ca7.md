# Using Time Wisely

Our clients and employers are interested in software that satisfies their needs. They want software that can be changed almost as fast as they change their minds. It is our job to provide them with that. The way we go satisfying their expectations is up to us. Although they may mention things like testing and Agile methodologies, what they really is a good return on investment. We need to use (our) money and time wisely, whatever we. We can quantify how much time we are spending on repetitive tasks and how much on any new feature. We should prepare the system to handle changes in a nice way, so we can just slide a new feature in, with no friction. We should make sure that whatever code can be easily tested and deployed. When estimating and planning our work, we should make sure that we factor in all the things we need to create not only well-coded code, but also tests. We also want to avoid giving the false impression that we have enough time to foster test cases, unit testing, refactoring, and so on, as optional. The less time we waste testing applications, for slow builds, debugging, to get our IDEs to work nicely with our totally crazy project structure, or by deploying the application, the more we have left to focus on the quality of our applications and make our clients happy.

# A Few Months Later

The team I mentioned above, after a lot of hard work, commitment from management, and a significant amount of investment, managed to turn around and became one of the best teams in their organization. Some of the teams managed to rewrite their entire test suite, replacing an unreliable testing framework with an open source test suite which used to take four hours to run and were always broken, to a point that no one cared. The new test suite covers a much larger part of the system and it takes around 20 minutes to run.

A different team is now close to achieving "one-button" deployment has an extensive test suite, with over 3,000 tests from unit to system tests, that run in under five minutes and with code coverage close to 100 percent.

The business, after comparing what teams had in the past to what they have improved now, is that it was a well-deserved investment.

# Legacy Code

> Attitude is a thing that makes a big difference.
Winston Churchill

During one of my days on Software Craftsmanship asked asked would like to work on a green-field project. Almost everyone raised hands. Then I asked who would like to work with legacy code. Only one or two people, else keep their hands down.

It is always nice to start a project from scratch, but to choose legacy code teaches us about the latest frameworks, and a lot of writing code without breaking existing features. It's great when we can write code without understanding existing code. Working on legacy code is great, especially with an experienced and disciplined team from day one. Projects proceed quickly and naturally.

However, if we are working with code written by people who are long gone, with no tests and no documentation, we went mental. We notice we are going crazy by the number of WTFs that we have to debug. We get moody and hating our job. Frustration becomes a constant. The bad news is that changing jobs rarely helps. In fact, it very rarely does. As soon as we start new jobs we will face more legacy code. The difference between projects in companies is normally just the size of the mess they are.
