
# The Invisible Threat

Starting a new project, everything is great. With a nonexistent code base, developers can quickly start creating new features without the fear of breaking or changing any existing code. Testers are happy everything they need to test is new, they don't need to worry about regression tests. Managers can see new features delivered at a fast rate. However, the team is composed of average developers, selected by matching a set of keywords against their CVS, and it is structured and treated like faction. As time goes by, bugs start to appear (with no apparent reason), and features start taking longer and longer to be developed. Slowly, the quality of the code starts to decline. But this is a slow process. It takes months, sometimes even over a year or two, to be noticed by management.

It's very common to see projects where, at the beginning, a feature of size X takes N number of days to be implemented. Over time, as more code is added, another feature, roughly the same size X, will take much longer to be implemented than it used to take at the beginning of the project. As the quality of the code decreases, the amount of time to implement a new feature, fix a bug, or make a change increases (see Figure 6). The lower the quality, the higher the number of bugs, and the harder it is to test. The lower the quality, the less robust and reliable the application becomes.

# Hostage of Your Own Success

When the code gets into the situation where changes or additional features take too long to be implemented and developers are scared to touch the existing code, action must be taken. This is a very dangerous situation to be in because business progress is impeded or delayed by software instead of being helped by.

In order to increase agility and have a good return on investment, keeping code quality is high.

The cost of dealing with bad code can make companies less competitive—the cost of implementing new features or making the desired changes can be prohibitive. It is totally unacceptable to have bad code quality affecting business decisions.

The biggest problem is that bad code is invisible to everyone except the developers. Members of the team only realize something is wrong when it is too late. It's the developers' responsibility to look after the quality of code. Sometimes developers explain the problem to project timelines, but the request to have some time to refactor the code is often ignored for various reasons including their lack of understanding of impacts of bad code, and the developers' inability to explain it. It is worth noting when developers get to a point where they need to ask for some time to do refactoring, for one reason or another, they neglected the code at some point in the past.

# Hire Craftsmen, Not Average Developers

With the amount of literature, tools, techniques, methodologies, and the infinite information available on the web, it is just unacceptable to have a team of developers who let the code rot. Craftsmen are gardeners. They are constantly looking after the code, quickly refactoring without fear—they are backed by a good set of automated tests that can test the code and provide fast feedback. The contracts or change in requirements will never be an excuse for bad code because they would have used good principles and techniques to ensure the application life span. An empowered team of craftsmen can be the difference between success and failure of any software project. Our industry is finally learning that code quality may not guarantee the success of a project, but it can definitely be the main cause of its failure.

# We Want to Do the Right Thing

We don't write bad code on pressure but we are constantly trying to find ways to do it. Over time, I realized that we have a wrong notion of time. When we are under pressure, we always feel need to rush. Sometimes pressure is put on us by others but more than not. The pressure is itself. When working with people, in an Agile fashion, where we feel the pressure in the work done, the debt tends to rise when we are on to us. We make our expectations and out our plan. We are OK with them telling us how long things are going to be done. Even then, even then, we always have have to deliver the tasks we commit to. We never have the time to do right

Pressure always be a burden of developer's life, and when we are under pressure, we end up cutting corners. We don't like to do that. We really rarely do that because we feel that we need to go faster. Fast does not mean quality, and unfortunately, we are not understanding the implications of our own decisions. We provide the best as we can.

# A Busy Time with No Time to Spare

I joined a team in a large organization. The pressure was and the developers were really hard to cope with. First I had very little time to get my environment set. The project was a nightmare to configure in our development environments (IDEs). We were using Java and it was getting me to implement the project. The project had more than 70 classes and many circular dependencies. After a few days, I had very little local experience.

The project was using the Java Enterprise Edition (JEE) container, had dozens of inbound and outbound interfaces with many other systems. When working with one of the guys (who was uncommon, but I insisted it) while he was running the system in our testing environments, placing messages into a queue, and looking at logs, he would look like then he made some changes in the code in making, package the application, copy it to the test environment, deploy the application, place a message in a queue again and look at the logs. It was as if he was in a while loop. He was doing it over and over, adding more logs to the code, which was resulting in the testing environment. I asked him why he was not testing the application on him. He said that it was not possible to run the application so he had to adds logs of statements to the code, then use the testing environment to try figure out what the application was doing. Apparently he had changed something, and the expected change was not arriving expected. After two hours of coding and XML files, adding lots of logs to the application—those types of logs indicate that a certain part of the code was executed—finally found out what we wanting. So he went back to his local machine, changed the code, changed a few ones to print out more information, and started the application again.
