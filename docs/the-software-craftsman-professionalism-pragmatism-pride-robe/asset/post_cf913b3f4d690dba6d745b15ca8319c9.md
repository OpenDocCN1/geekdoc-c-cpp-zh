## Refactoring

The Boy Scout rule: "Always leave the campground cleaner than you found." This is a value that every craftsman must make when it comes to code.

Developers are inclined to make improvements to code that they find difficult to understand. Because of the fear of breaking the code, developers start introducing small hacks and bugs. The bigger the mess, the bigger it is, This is known as the "broken windows theory." Messy applications make code go slowly, which causes the business to slow down.

Constantly refactoring your code mitigates this risk. Developers will constantly refactor the code they touch. If this practice is accepted and from the beginning of the project, developers will never spend too much time refactoring because the code will be in good state.

However, when working with legacy applications, developers might not be cautious to stop the use of rewriting the entire system in one. In this case, refactoring the code being a better approach.

Refactoring without pragmatism can be dangerous. Professional means means understanding trade-offs. Although we want to make the whole system better, we may not need to. There is no point in refactoring a piece of code that hasn't been changed in years. If we don't need to change it, changes are not to be refactored. Start refactoring when it changes more. The Boy Scout rule should be applied when we need to make a change or understand one area of the code, not everywhere.

A clean and maintainable code enables developers to go fast and reduces the chances of new bugs. That's the value to the business.

## Accountability

Many people are not convinced by some of these practices, when we see the value they bring. Time and I hear again. They say, "These are just practices and many of them are not needed. We can easily develop code without them."

Although this may be, it is also a valid argument. A quick search for "percent of software projects that fail" will give us reports and statistics about projects that, one way or another, have failed. The percent can range from 30 to 70 percent depending on factors.

When someone—whether a developer, a project manager, or from the business—he or she does not want to adopt any of these practices, we should listen. There is no reason to react badly or immediately think that person doesn't know why. We should learn from interaction. After explaining the value of the practices described in the previous section, we should ask: "What do you do (or should we do) that gives us the same or more value than that? What do you do that is better than that?"

We are all accountable for the decisions we make, but only for the decisions of adopting certain practices, but also for the decisions of not adopting them. This is not just about developers. Managers should also be accountable for all teams to adopt certain practices. We should record these decisions and escalate it if necessary.

## Pragmatism

Technologies, methodologies, and practices are constantly emerging and evolving. There is always a better way of doing things. Although we described a set of practices in this chapter, that doesn't mean they are the only practices or that they are suitable in every single context. Things that are considered good today may not be considered as tomorrow. Maybe in a few years. Software Craftsmanship will be strongly encouraging the adoption of a completely different set of practices.

Being pragmatic is one of the best qualities that a software craftsman can have. We should not follow practices just because someone said so, or just for the sake of it. We should constantly look for ways of doing our job better and satisfying our customers. If that means TDD, we should use TDD. Whenever we find something that could give us a quicker feedback loop, then we should use that instead of TDD.

Pragmatic thinking is also a virtue. We should constantly ask ourselves why we are doing what we do. Is there anything better than what we do today? Are the practices we chose for our project? What is their value? Is it time to try something else?

The best way to get better feedback is to compare the value they bring to the project, compare how long they take, and how much effort they should require. If we can't identify the value that certain practices bring, maybe we should not use them. For practices that give similar value, we should choose whatever the team is more comfortable with. It is worth remembering that nothing is set in stone. Choosing to adopt a practice does not mean using it forever if not works for us. As Agile developers have taught us, we should inspect and adapt. If certain practices are found to be better than what we do today, we should adopt that better practice. As software craftsmen, we should always keep an open mind and choose the best technologies, tools, processes, methodologies, and practices for the job.

## Summary

Many developers struggle to convince their managers and other developers to adopt technical practices because they fail to explain the value that those practices bring to the project. Adopting technical practices doesn't come for free. There is a learning curve, and the more we are getting familiar with the new practices, the more they will probably be slower and a bit frustrated of.
