The multimillion-dollar C3 project needed high-caliber developers working, opposed to working in competition and isolation. Beck invited Jeff to the project to help develop and refine these methods. Jeff acted as a catalyst to instill Agile practices in the team which had more Agile practitioners, including Beck Fowler, Martin Beck, and Don. With a big focus on continuous integration and unit testing, they managed to keep the project on track.

During an interview, Beck describes the example of the methods: "The first time I was asked to lead a team, I asked a bit of the things I thought were sensible, like testing them. ## Automated Testing

Automated testing enables us, with a click of the button, to have our entire system tested within few minutes. It gives us confidence to deploy into production after the last change was made. The feedback loop on the correctness of our code is reduced from weeks to minutes. As the system grows, testing phases become longer, the entire system must be manually tested. This may also mean more testers. The increase in speed is due to our confidence to add features without breaking the system. The amount of time the business can save reducing the need for lengthy testing. Automated testing gives us measurable value.

## Test First

Test first helps us to focus one idea at a time; to define the responsibility of modules, and to work in small increments. It gives us assurance our code works according to expectations. Testing first helps us write keeping the code simple.

## Test-Driven Development

Test-Driven Development is an evolution of test. Very common misconception is that TDD does not mandate the granularity to which our tests should be written. There are many different types of tests, many overlapping or conflicting with each other. Let's not worry too much about that. TDD discourages us and design front. However, when our code becomes too complex and difficult to test, it tells us to rethink the design of our code and to refactor it. The feedback loop provided by testing of our code is far more sure than in design meetings. When we get immediate feedback on how maintainable the existing code is, design review is good practice, but it prevents over-engineering. If done infrequently, the problem may be too late to be solved quickly. Design reviews are more effective with TDD, it falls into two parts. Design reviews are more effective when the code is well-defined before practice starts and it provides a new layer of review for the company's evolution. Design review must be done before a big change starts and potentially a few times during the development of a piece of work, but not more than that. If the code is good, it should be broken down into smaller and smaller. Many designs are proposed as some arise. TDD and design review meetings are not mutually exclusive with the line of code, writing problems as they arise. And both are needed, and it is important to compare the value and the length of their feedback loop. TDD's value is to the business it offers us a quick feedback on the design, simplicity, and maintainability of our code. It provides a living and executable documentation for our needs, and as a good effect, a short suite of requirements. That is the value of a quick feedback loop.

## Continuous Integration

On average, have between four to ten developers. In large projects, we may find multiple teams spread across different cities and times. Even if we are working on totally different features, how can we make sure we are not stepping on each other's toes? Although teams may be working on totally different features, how can we know if one of us breaks a different part of the application by introducing an unexpected effect?

One way of making the system working correctly, once all the changes made by developers are integrated, is to have a QA team. While they manually execute a prescribed set of tests and plans, and report back after a few days or weeks there are any bugs or not. But that will be the feedback loop.

Continuous integration, with TDD, can reduce this feedback loop. Every time a developer commits some code, the suite of tests is executed and an error message tells the entire team when that tests fail. This practice needs to be built without a broken build, which means the problem introduced by the latest change needs to be fixed immediately. The advantage of following this practice is that the system is always in a deployable condition and doesn't accumulate problems.

In addition to that, the combination of continuous integration and TDD can make an entire QA team redundant. The best testers could be better utilized to explore new edge cases and to help business analysts and product owners define acceptance criteria for user stories. Good testers can also help the entire team by exploring exploratory testing, which is only humans can do and there is no easy way to make.
