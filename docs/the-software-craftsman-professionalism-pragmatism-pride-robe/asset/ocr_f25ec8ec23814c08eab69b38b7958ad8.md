# 6. Working Software

One of the first things said by the nonbelievers of the Software Craftsmanship movement is that good and clean code is not enough to guarantee the success of a project. And, yes, they are absolutely right. There are innumerable reasons what may cause a software project to fail, ranging from bad business strategy, competitors' superiority, bad project management, high costs to market, technical limitations, and integrations—just to mention a few. Due to the importance of things a software project many organizations do not pay much attention to those that are concerned with less important factors, like the quality of the software being developed. Some believe that with a good project management plan, strict process, and a large amount of good documentation, the project will succeed. Many organizations see software development as a process where the workers (developers) are viewed as lesser than their "highly qualified" and well-paid masters. Software development is then outsourced to workers in cheaper countries, which, if they provide poor quality anyway. With a strong emphasis on down and control management, software development is treated as a detail. Very rarely companies believe that they are able to attract or retain good software developers, leaving their business in the hands of amateurs professionals.

Traditional managers and business consultants can say whatever they want about the importance of a good process and documentation, but the truth is that in a software project, the most important deliverable is the software itself. Anything else is secondary. Fortunately, our industry seems to be evolving and we are all learning from our mistakes, and more companies are realizing the importance of having great people working collaboratively.

In this chapter I discuss why working software is not enough and the invisible impacts of bad software. I also discuss how a change in attitude can help developers to deal with legacy systems and the creation of more low quality software.

# Working Software Is Not Enough

In the Agile Manifesto, we have working software over comprehensive documentation. There are also two principles that mention working software:

+   1. Deliver working software frequently, from a couple of weeks to a couple of months, with a preference to the shorter timescale.
2. Working software is the primary measure of progress.

This is absolutely great and we all agree with these principles. The problem here is that over the years, the idea of working software moved away from high-quality working software, and many Agile projects are producing code that violates the standards expected from an Agile project. All that the code you need to deal with a daily basis counts as working software: Imagine all those applications that take a long time to add a new feature to. All applications are scared to touch code that is poorly coupled. And what applications without an extensive test suite, where are we forced to test? What about the applications that we need to deploy under user acceptance testing (UAT) if we wanted it because we cannot run it locally? They are all working software.

So, what does "working software" mean? Can we consider the applications described above as working software? Is working software enough? Is it acceptable to deliver something that takes a long time to build and go through a long period of manual testing and bug fixing? The story is repeated for every new feature? Has it been forgotten or justively taken for granted?

# Looking After Our Garden

Code is not mechanical. A garden needs constant maintenance. For a garden to look beautiful anyway we need to tend to it, constantly water it regularly, remove some dead plants, plant new ones or rearrange existing so they can stay healthy and the garden stays whole. With basic and regular maintenance, the garden will always look great but if we neglect it, for a short period of time, it will start to look much less enough effort to make it look good again. The longer we neglect it, the harder we will need to bring it back to a state we can enjoy again.

> The Pragmatic Programmer

Code is different. If we don't look after it, the code starts to deteriorate as changes and new features are added. Bad design choices, lack of tests, and poor use of languages and tools will make the code rot faster. Graphually, other parts of the code will also be contaminated to the point that the whole base becomes extremely ill, making it painful and costly to maintain it.
