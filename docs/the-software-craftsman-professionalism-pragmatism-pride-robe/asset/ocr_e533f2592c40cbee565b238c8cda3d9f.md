# Test First

Test first helps us to focus our ideas; to focus one single at a time; to define when the responsibility of modules, classes, and functions; and to work in small increments. It gives us assurance our code works according to expectations. Since each test takes from a few milliseconds (unit tests) to a few seconds (higher-level) to run, test first gives us very quick feedback loops when writing the code. Testing first helps us write enough code to satisfy the requirements, keeping the code simple. It reduces complexity and over-engineering. That's the value it brings to the business.

# Test-Driven Development

Test-Driven Development is an evolution of test. Very common misconception is that TDD does not mandate the granularity to which our tests should be written. There are many different types of tests, with really tens of definitions for each of them—many overlapping or conflicting with each other. Let's not worry too much about that. Let's focus on the TDD trends.

Although TDD has "test" in it, TDD is actually a design practice. When test-driving our code, it becomes difficult to write code. First, because we write just code to satisfy the requirements—test-driven discourages us and design up front (BDF). However, when our code becomes it too complex and bloated and difficult to test, it tells us our bad design choices are high complexity in maintaining and writing new tests. These tests lead us to rethink the design of our code and to refactor it

The feedback loop provided by testing of our code is far more sure and objective than when in design meetings. When we get immediate feedback on how maintainable the existing code is. Design review is good practice, but it prevents overengineering. If done infrequently, the problem may be too late to be solved quickly. Design reviews are more effective. With TDD, it falls into two parts. Design reviews are more effective when the code is well-defined before practice starts and it provides a new layer of review for the company's evolution. Design review must be done before a big change starts and potentially a few times during the development of a piece of work, but not more than that. If the code is good, it should be broken down into smaller and smaller. Many designs are proposed as some arise. TDD and design review meetings are not mutually exclusive with the line of code, writing problems as they arise. And both are needed, and it is important to compare the value and the length of their feedback loop. TDD's value is to the business.

TDD offers us a quick feedback on the design, simplicity, and maintainability of our code. It provides a living and executable documentation for our needs, and as a good effect, a short suite of requirements. That's the value of a quick feedback loop.

# Continuous Integration

On average, have between four to ten developers. In large projects, we may find multiple teams spread across different cities and times. Even if we are working on totally different features, how can we make sure we are not stepping on each other's toes? Although teams may be working on totally different features, how can we know if one of us breaks a different part of the application by introducing an unexpected effect?

One way of making the system is working correctly, once all the changes made by developers are integrated, is to have a QA team. While they manually execute a prescribed set of tests and plans, and report back after a few days or weeks there are any bugs or not. But that will be the feedback loop.

Continuous integration, with TDD, can reduce this feedback loop. Every time a developer commits some code, the suite of tests is executed and an error message tells the entire team when that tests fail.

This practice needs to be built without a broken build, which means the problem introduced by the latest change needs to be fixed immediately. The advantage of following this practice is that the system is always in a deployable condition and doesn't accumulate problems.

In addition to that, the combination of continuous integration and TDD can make an entire QA team redundant.
