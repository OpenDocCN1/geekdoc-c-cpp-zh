## Refactoring

Refactoring for the sake of refactoring is a waste of time. Unless you have nothing else to do, there is no point in refactoring a piece of code that you don't need to change and spend days refactoring it. The Boy Scout says "leave the floor cleaner than you found it"—if not—"clean the whole until you can clean the floor spotless." It is a pure waste of time and not very pragmatic.

When working with legacy code, we should always leave the area of code cleaner than we found it. When we need to add a new feature to the code, I will usually study the code a little bit and refactor it (if needed) so I can accept the new feature more easily and gracefully.

Refactoring the code adding a new feature is a good idea when it is significant. Before adding any feature, I ask myself: "is the code ready to receive this new feature? How many places do I need to change to add this new feature?" If the answer to these two questions are "no" and "many", I will first refactor the code to prepare it for the new feature. I change the code in a way that would make it easy to slide the feature in without opening (or changing) existing behavior, minimizing the impact the new feature will have on the code. I would refactor my code to make it compliant with the "open/closed principle" (OCP), and then add the new feature.

When there are no significant changes to the system, I just write the new code I need, and do a series of small refactorings while I'm doing it—using the refactoring step inside the TDD lifecycle (red, green, refactor). First I make it work, and then I make it better, in all increments.

Improving your system with constant refactorings, justified by necessary changes to the system, is a good and more pragmatic way to improve an application.

## Helping the Business

It is common to be on a project where the business doesn't know what they want. It's common to have a situation where they are trying to figure out what makes sense by engaging with clients (internal or external), getting feedback. Any Agile coach would say that in order to help, developers should engage in conversations, ask questions, and be part of the solution. Then what is said, and it should happen in any situation. But there is far more than we can do.

I was once on a project where the business and the IT department were being pressured by auditors to create a solution to assess the risk associated with their financial operations. This was a program where many systems were being integrated with legacy systems.

The problem was, at a macro level, everyone knew what the goals were. At the detail level, they were very fuzzy and complicated. The challenge was not related to the natural complexity of the requirements or systems involved, it was also related to how the organization was structured. Refining requirements was not just a matter of writing clear criteria for users. These discussions could lead to how to handle it in the business operation.

## A Simple and Quick Solution

Quick doesn't mean dirty. The problem I mentioned was related to an internal web application we were building. As part of the acceptance criteria of each user story, we drew mockups and agreed on the expected behavior with the business. What worked well for a while the mockups didn't really give them the experience of using the real software—mainly because of the user interface behavior we wanted for certain features. They wanted to play with the real application in a safe environment, then demo it to sponsors and users in other parts of the business. They also wanted to live with it every month, or so people could start using the application.
