# Pre-Interview Coding Exercises

Asking candidates to submit some code before the face-interview is a great way to select candidates. However, we should give them some time. Don't ask candidates to submit the code a few hours after giving them the requirements. At this point in selection, the focus is to assess how well the candidate can code with a given set of requirements and how fast they do it. Some time frames will make the candidate to solve the problem instead of writing clean well-coded code.

However, this approach is not suitable for some. Just let the candidates submit the code when they are ready. This can help to build a pool of good candidates over time.

Another approach is to tell candidates when we will start evaluating them. Having a few candidates in hand, we can send the requirements to all candidates at the same time and then tell them in when we will start evaluating the code. This one-week period is not a deadline; it's the date we will start evaluating them. The first to have an acceptable submission will be invited to the next round of interviews. If no one, we keep accepting submissions. Allowing weeks seems like a reasonable amount of time. I prefer to give candidates an amount of time that is one to two weeks.

It is let the candidate choose the deadline in this stage, want to see if the candidate can code well, regardless of the experience. If we are hiring developers who want to use the code with Java or Ruby, the important thing is what techniques are used to solve the problem and not the language or framework. Looking at submitted code is a far better way to filter candidates than looking at CV or conducting interviews.

There will be cases where some candidates decide not to go with the selection process because they don't want to spend much time coding for a job they might not get in. In a way, that's a good thing. At least we know the ones who chose to submit their code can work for us and are taking the selection process seriously.

# Everyone Should Know How to Interview

Interview techniques are a skill we master, both as interviewers and candidates. This is a skill that is rarely taught. Usually companies have a few senior developers who can all the technical interviews. Although that seems to make sense, and work for a period of time, it is not sustainable. A strong team is a team where every developer can conduct interviews, making sure he or she find the talent team expects.

Experienced developers should allow less-experienced developers to join interviews. With watching experienced developers interviewing will help them conduct interviews in the future. Over time, they can switch roles. The less experienced developer will gain experience and the experienced developer will be the observer.

Pairing interviews and interviewers is a good way to keep everyone involved. Being able to interview and select new developers to join the team gives existing developers a great sense of empowerment and team spirit. It gives them the certainty that they are in control of their own project and who is going to work with them.

# Developers Must Interview Developers

I've seen frustrated developers in companies and where they could not choose their own teammates. It's very frustrating when, all of a sudden, our manager comes to us and says 'Guys, this is Steve Jenner. He is joining the team today.'

Good developers do not hire bad developers. They try to find developers who are even better than they are; they know how important it is to hire a great team—not just for the benefit of the company but for their own benefit as well.
