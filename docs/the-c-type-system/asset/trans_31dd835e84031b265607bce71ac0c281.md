## 性能基准

当我们的代码运行速度比预期慢时，仅仅观察运行的应用程序可能会给我们一些启示，但精确测量性能将使我们能够更有效地定位优化工作。

记录代码运行所需的时间——无论是完整的端到端运行还是程序的一部分——被称为基准测试（benchmarking）。更一般地说，基准是用于衡量某物的标准。通过对我们的代码计时，我们建立一个基准，以便与新版本进行比较，确定我们的更改是让代码更快、更慢，还是没有明显效果。

许多单元测试框架会报告测试运行所需的时间，甚至各个测试所花费的时间。关注这些数字当然值得，因为突然增加可能表明某处引入了效率问题。这种方法在自动化持续集成（CI）服务中尤其有价值，在该服务中，来自多个贡献者的更改会自动集成到一个程序中；如果单元测试的计时开始发生变化，我们可以设置CI服务来提醒我们。如果某个通常运行几百毫秒的特定测试开始花费明显更长的时间，我们可以专注于被测代码片段，看看是否值得进一步调查。

一种更细粒度、更精确的测量代码段运行速度的方法是对代码本身进行插桩。基本技术原理很简单：在运行被测代码之前，我们创建一个计时器来记录已经过的时间，当代码运行完后，我们记录计时器的测量值。清单8-1展示了一个使用System.Diagnostics命名空间中的Stopwatch类的简单但朴素的基准测试。

```
// Start the clock
var clock = Stopwatch.StartNew();

// Run the code to be measured
var result = SomeTask();

// Stop the clock, and record elapsed time
clock.Stop();
var millisecs = clock.ElapsedTicks * 1000.0 / Stopwatch.Frequency;
```

清单8-1：一种简单的基准测试方法

Stopwatch类是一个轻量级的高分辨率计时器，可以非常精确地记录经过的时间。Stopwatch.Frequency值是每秒的滴答数，因此通过将经过的滴答数乘以1000.0再除以频率，我们可以用毫秒粒度报告所花费的时间。这种技术只是测量时钟启动以来经过的时间，因此，例如，它无法确定被测量的代码是否在整个时间内实际运行。即使代码被中断（例如，切换到不同线程），时钟也会继续计时。

用计时器对代码进行插桩并将其记录在日志或其他审计跟踪中，可以是测量实时系统中运行的代码的有用方法。然而，测量和报告性能本身也需要时间，所以我们必须确保在相对较高的层级进行测量。例如，测量和报告代码响应HTTP请求或调用远程过程所需的时间可能不会显著影响应用程序的性能。另一方面，在紧密循环中使用这种技术很可能引入比循环本身更大的开销。

基准测试也是在测试环境中探索性能的有用方式，也许可以比较解决特定问题的替代方案。清单8-1中的技术是朴素的，因为它只测量一次代码。更准确的性能测量方法是多次运行代码并报告平均时间。我们可以基于清单8-1编写自己的框架，尽管一些免费的C#库可以为我们完成繁重的工作，生成记录的性能报告以及误差范围等其他有用的统计数据。

## 分析器

基准测试会告诉我们一段代码整体运行的速度，但要确定代码具体做了什么，我们需要一个分析器。将基准测试工具与性能分析相结合，将为我们提供最准确的测量。在可用的几种分析器中，最常见的两种是性能分析器和内存分析器。

内存分析器将向我们展示程序在何处分配内存、使用了多少内存，以及何时被垃圾回收。如果需要找出代码的哪些部分使用了最多的CPU时间，或者哪些方法被调用最频繁，性能分析器将为我们提供精确的测量，使我们能够定位代码中的特定热点，并在必要时优化它们。虽然优化内存使用很重要，但本章我们将重点介绍如何使用性能分析器发现代码中的瓶颈。

性能分析器通常对程序的发布版本进行操作，因此会考虑编译器和JIT编译器应用的任何优化。测量调试版本的性能通常意义不大，不过有时它可能有用：例如，比较相同代码的调试版本和发布版本的分析结果，可以深入了解JIT编译器执行的一些优化。

虽然性能测量可以让我们了解瓶颈可能在哪里拖慢代码，但必须牢记，程序的性能受代码之外的许多因素影响，包括我们使用的CLR版本或软件开发工具包（SDK）的版本。即使在同一台机器上两次运行同一个程序也可能产生不同的结果，具体取决于缓存内存的分配方式或CPU调度器如何对指令进行流水线处理。JIT编译器也可能在每次运行时应用不同的优化，可能进一步影响结果。因此，我们必须谨慎，不要过于看重分析器报告中的绝对时间，而应寻找趋势或明显的异常，例如结果相差一个数量级或更多。

我们将使用性能分析器有选择地测量代码的特定方面，并分析分析器的结果。请记住，本章显示的具体结果特定于执行测试的机器，但我们将尝试多种方法，测量每次尝试，以便我们能够识别结果中一些常见的、可重复的模式。

为了演示这是如何工作的，接下来我们将研究仅更改字段类型如何显著影响依赖使用Equals的代码的性能。

## 使用Equals测量基本性能

Equals方法在C#代码优化中是一个经常被忽视的方面。这个方法之所以是性能测量的好候选者，是因为它总是可用的（因为每种类型都从object基类继承它），而且可自定义（作为object的虚成员）。在本节中，我们测量Equals对简单值类型的默认行为，以便将分析器的结果与我们自己的Equals覆盖实现的结果进行比较。

结构类型从ValueType类继承基于值的相等性比较，覆盖了object通用基类定义的默认实现。这确保了当我们复制一个结构体实例时，副本通过比较每个实例的字段而与原始实例相等。我们可能倾向于依赖这种行为，而不是实现我们自己对Equals方法的覆盖，因为它能使我们的类型定义更短更简单，就像清单8-2中的Color结构一样。

```
public readonly struct Color
{
    public Color(int r, int g, int b)
        => (Red, Green, Blue) = (r, g, b);

    public int Red { get; }
    public int Green { get; }
    public int Blue { get; }
}
```
