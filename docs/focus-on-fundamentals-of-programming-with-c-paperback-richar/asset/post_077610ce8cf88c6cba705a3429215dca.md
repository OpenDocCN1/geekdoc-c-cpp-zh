
## Procedural vs Object-Oriented Approach

### Procedural Approach
- Problems are separated into code and data
- Commands operate on passive data

### Object-Oriented Approach
- Objects define both data and functions
- Objects are responsible for their own behavior
- Functions and data are treated as an entity

## How can Objects be Accessed?
- If objects can be accessed only through their public interface, how, then, is such access permitted?
- One object accesses another object by sending it a message.

## Messages
![](img/0603fdf2eefeabaf26542250cc2fb439_589_0.png)

- Sending a message to an object is the way of asking an object to carry out one of its operations (methods).
- When an object receives a message, it determines whether it has an appropriate method to allow it to respond to the message.
- If it does, it performs the requested operation in any manner it knows.
- The request does not specify HOW an operation is to be performed. Such information is always hidden from the sender.

## Objects Send Messages
- An object-oriented financial application might see CUSTOMER objects sending debit and credit messages to ACCOUNT objects.
- The ACCOUNT objects might then cooperate to maintain cash-on-hand, accounts receivable, and accounts-payable objects.

## Objects and Messages
- Objects respond to messages
- All activity is a result of messages
- Different objects can respond in different ways to the same message.
- The implementation of one object cannot depend on the internal details of another object, only on what messages can be sent to an object and on how the object responds to messages.

## OOP Classes
Sometimes a simulation involves only a single example of a particular kind of object. It is much more common, however, to need more than one object of each kind.

But it would be extremely inefficient to redefine the same methods in every single occurrence of that object.

In OOP, classes abstract out these commonalities: objects that share the same behavior are said to belong to the same class.

## Objects Can Share Behavior
- Savings accounts and checking accounts are both types of bank accounts ... they have balances.
- Lead, silver, and platinum are all metals ... they have atomic weights.
- Elephants, tigers, bears, horses, and cows are all mammals. They are vertebrates, warm-blooded, and have hair on their bodies.

## Classes
- Whereas an individual object is a concrete entity that performs some role in the overall system, the class captures the structure and behavior common to all related objects.
- A class represents a set of objects that share a common structure and a common behavior.

## Classes Define Objects
- Classes serve as templates from which objects can be created.
- Every object belongs to a class that defines the type of object it is.
- An object is an instance of its class.
- Objects of the same class behave the same way and may have different states (data).
- A message to an object is a request that it execute a specific function or algorithm (method).
- Messages an object responds to are methods for the entire class.

## Classes and Objects
- Logically, an object is an indivisible encapsulation of state and operations.
- However, since all objects of a class support the same operations, the operations or methods can be physically associated with the class.
- Only the state or private information relating to a specific object need reside in the object itself.
- Here, each object has its own account number and balance.
- However, the operations for making deposits, withdrawals, and balance inquiries can be shared by all objects and stored in the class.
- When a message is sent to an object, the system searches for the operation in the class of the object.

## Encapsulation
Conceptually, we can characterize objects such as the ball in our example as an encapsulation of both state and operations (behavior).

Encapsulation is the ability to conceptually group together in an object both the state of the object and the allowable operations on that state.

## Information Hiding
Objects and encapsulation adhere to an important fundamental principle for structuring software systems called information hiding.

The idea behind information hiding is that users of an object need not have access to either:
- the representation, or
- the implementation of the operations

Encapsulation hides the details of the implementation of an object.

## Two Views of Objects
- It is useful to think of objects as providing two views of themselves:
  - one to potential users or clients of the object
  - another to implementators of the object

Users of the object may modify its state but only indirectly by invoking the operations supported by the object.

The major advantage of this approach is that it allows an implementator to modify the implementation of an object in a manner that is transparent to users.

Users or clients of the object do not have to be notified of the change.

This separation of the object's user interface from its implementation is essential for the production of maintainable and reusable software.

## Encapsulation
- Localizes within an object both data and the operations that affect the data.
- Public part - tells what objects can do
- Private part - How it does these things
- Concentrate on WHAT want done and not HOW it is done.
- Objects handle implementation.
- New objects to system don't require source code changes.
- Objects are protected against changes in other parts of the program.
- Manages complexity inherent in real-world problems by apportioning that complexity to the individual, pertinent objects.
