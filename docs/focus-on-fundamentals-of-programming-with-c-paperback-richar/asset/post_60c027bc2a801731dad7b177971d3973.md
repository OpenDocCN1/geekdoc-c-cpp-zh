
## Simple Video Game

![](img/0603fdf2eefeabaf26542250cc2fb439_565_0.png)

- The objective of the game is to remove all the bricks from the wall.
- When a ball strikes a brick, the brick disappears.
- The ball can be redirected using the paddle that the player can move to the left or right using the mouse.
- The ball bounces off the sides, bricks, and paddle in a conventional manner.
- A player is provided at most 3 balls (one at a time) to remove the bricks.
- A ball is lost if it passes below the paddle (i.e., the player misses it).
- Demolishing the bricks with the allocated 3 balls is a win. Failure to do so is a loss.

## A Traditional Approach

- The classical top-down stepwise refinement approach to problem solving involves refining a problem solution into greater levels of detail based upon functional decomposition

### Video Game - Phase I

```
while someone wants to play
set initial game display
play a single game
```

- The design could now be refined further by taking some of the abstract functions in the current solution such as:

```
set initial game display
play a single game
```

and decomposing them in a similar fashion.

### Video Game - Phase II

```
set initial game display
    draw wall
    draw sides
    initialize paddles

play a single game
    set score to 0
    set balls left to 3
    while balls left > 0
        play a ball
        decrement balls left
```

- The next step might be to refine the play a ball module

### Video Game - Phase III

```
play a ball
    enter new ball into game
    while ball is in play
        check ball position
        update score and display
        move ball
        move paddle
remove ball from game
```

- We are refining the solution to the problem algorithmically in a step-by-step manner, with each step in the process describing a solution to the problem at a certain level of abstraction.

- Systems refined in this way are most easily described using a diagram where major modules are hierarchically organized and where each module represents a function or sub-problem in the solution.

## Functional Decomposition of the Video Game

- Video Game
  - Set Initial Game Display
    - Draw Wall
    - Draw Sides
    - Initialize Paddle
  - Play a single game
    - Play a Ball
      - Check Ball Position
      - Update Score and Display
      - Move Ball
      - Move Paddle

## Functional Decomposition

- A design produced using a functional decomposition approach fits very nicely with the procedural approach to programming encouraged by languages such as C.

- In general, where the subroutine, procedure, or subprogram is the predominant mechanism for structuring code, there is a direct mapping between functional modules in the design and procedures in the code.

## An Object-Oriented Approach

- An object-oriented solution to this problem would simulate the objects in the real video game.

## Object-Oriented Approach

- Software objects would be constructed to represent:

  - the paddle
  - the ball
  - the sides
  - the bricks in the wall, etc.

- Furthermore, operations on these objects would represent problem-domain tasks such as:

  - moving the ball
  - moving the paddle
  - determining if the paddle has struck the ball
  - whether the ball is lost
  - removing bricks from the wall, etc.

- So our object-oriented approach to this problem is to try to identify not the functions but the objects that will be involved in the computation.

### Object-Oriented Programming

- OOP is programming by simulation

- OOP is programming with objects

### OOP is Programming with Objects

- When you approach a programming problem in an object-oriented language, you no longer ask how the problem will be divided into functions, you ask how it will be divided into objects.

- Thinking in terms of objects, rather than functions, has a surprisingly helpful effect on how easily programs can be designed.

- This results from the close match between objects in the programming sense and objects in the real-world.

## Exactly What is an Object?

- An object is a software “package” that contains a collection of related functions or methods (behavior) and data (state).

- Everything an object “knows” is expressed by its state (data).

- Everything an object can do is expressed in its methods (behavior).

## Objects are Characterized by their State and Behavior

| Object | State | Behavior |
|--------|-------|----------|
| BALL | position, radius | report position, modify position, behind paddle? |
| PADDLE | position, width, height | colliding with ball? |
| SIDE | position, width, height | |
| BRICK | position, width, height | |

### State of Objects

- For example:

  - A ball might consist of a radius and a position
  - A paddle, side, or brick might be described by position, width, and height

- This represents the state of the objects

### Behavior of Objects

- Likewise, each kind of object supports a set of operations that may be applied to the object to modify or interrogate its state.

- For example:

  - A ball responds to requests to report or modify its position.

  - Similarly, a ball can be asked whether it is located behind the game paddle or whether it is colliding with any of the other components in the game.

  - The paddle can be asked whether or not it is colliding with the ball.

### State and Behavior of an Object

- So objects are characterized by their state and the operations that can be performed on that state.

- This fundamental concept distinguishes OOP from procedural programming.

### OOP Objects

- In traditional programming systems, data and procedures are separate entities. The programmer is responsible for applying active procedures to passive data structures, and frequently for ensuring that the procedure will work correctly on the data types to which it is applied.

- By contrast, an OO programming system doesn't view an object just as passive data but as the combination of its private state and the methods that manipulate it.
