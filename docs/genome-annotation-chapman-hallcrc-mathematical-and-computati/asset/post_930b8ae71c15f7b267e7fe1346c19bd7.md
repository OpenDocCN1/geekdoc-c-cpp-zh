### 10.5.2 The Search Widget

Often users will want to retain only part of the output of the analysis for further processing, especially when they filter large data sets down to subsets, which are likely to be relevant to their particular research question. In Seahawk, a conditional service execution is implemented via a new search/filter widget. Visually, the behavior is a hybrid of a highlighting search and a gray-out. Filtering is essential, so that users not use data that do not meet the search criteria; these data will not be available downstream in the equivalent Tavern workflow. To avoid an inconsistent state, filtering is updated as each letter is typed into the search box. The three types of conditions are conditionally supported in Seahawk:

```
if (cond(x)) {f(x)} else {g(x)}
if (cond(x.member1)) {f(x.member2)} else {g(x.member2)}
if (cond(f(x))) {g(x)}
```

The search condition can be in the format of either a plain string or a regular expression (a powerful pattern matching syntax with wildcards).

Conditional type 2 filtering is based on the value of a particular member (x.member1) of the data object. This is accomplished by selecting from document-specific drop-down list at the end of search phrase (Figure 10.10a, bottom right). Any data member (x.member2) in the document can be selected for further processing, using the hyperlinks in the data display, unless they are gray out by the filter and are therefore inaccessible. The demonstration of conditional type 3 requires that the user references x from the output of f(x). In Seahawk, this is implemented by providing a “previous input” service menu item when a filter is applied to service result (i.e., f(x)). In Figure 10.11a, selecting the menu item “MobyGetGenbankSequence” is the logical equivalent of the pseudocode:

```
if (MobyGetNeighborsFromGi(1592258) contains "1589") {
  MobyGetGenbankSequence(1592258)
}
```

If no filter active, the “previous input” option is not displayed, because this is the default interpretation of service history. The set of Taverna workflows required to implement type 3 is nontrivial (Figure 10.11b). These processes include Java code and would almost certainly beyond the capabilities of novice user to create via programming. Other somewhat unusual aspects of the search/filter behavior in Seahawk are page-specific and job-level filtering. Page specification implies that the widget is tied to generic document. This means that when user navigates away from a page, the widget disappears. Upon reentry to the given page, it will reappear. Hiding the search/filter widget disables the filtering, whereas the widget enables last known filter criteria. This stateful, page-specific behavior is essential for different conditions to be applied at different stages of the workflow. Statefulness also means that the output from one service can be filtered multiple ways. This option forking is a variation on the if–else concept. It is accomplished by launching subsequent sequences in new tabs after search has been applied. Job-level filtering reflects the for-each functionality in Seahawk. In a document containing results for inputs (i.e., “jobs”), the filtering decision is to either allow or disallow the subsequent processing of each job individually; they are independent results. Having lists of jobs helps guide the analysis, because users receive immediate feedback on the correctness of positive and negative examples. This is in contrast to traditional programming strategies, where the user must submit the filter expression for arbitrary data.

### 10.5.3 Data Filters and Labels

Data filter processors in Seahawk-generated workflows serve to ensure data type safety, which Taverna normally would not. For example, in Figure 10.9 the “Extract_Moby_Subset” processor ensures that only the data contained in the taxon namespace are passed from “ExplodeCrossReferences” to the “GetTaxNameFromTaxId” service. Without this filter, "GetTaxNameFromId" could also receive an NCBI_gi ID as input (another Xref in Figure 10.8). As the service cannot interpret NCBI-gi at all, Seahawk makes a concerted effort to ensure workflow data safety, in order to minimize problems for the user when executing the workflow in Taverna.

Without downloading and running Taverna, the preview allows users to quickly go back to adjust their Seahawk browsing or filtering if the workflow does not capture their intent.
