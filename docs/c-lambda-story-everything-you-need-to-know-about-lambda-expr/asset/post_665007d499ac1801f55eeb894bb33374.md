
The critical thing to remember is while lambdas make it easy and convenient to create a thread, it’s still the asynchronous execution. Closures are not “special” and also vulnerable to all race conditions and blocking.

This is visible in the following example:

```cpp
#include <iostream>
#include <thread>
#include <vector>

int main() {
    int counter = 0;

    auto maxThreads = std::hardware_concurrency();
    std::vector<std::thread> threads(maxThreads);
    for (int t = 0; t < maxThreads; ++t) {
        threads.push_back([&counter]() noexcept {
            for (int i = 0; i < 1000; ++i) {
                counter++;
                counter--;
                counter++;
                counter--;
            }
        });
    }

    for (auto &thread : threads) {
        thread.join();
    }

    std::cout << counter << std::endl;
}
```

In the example, we’re creating several threads, and each thread performs some computations on the counter variable. The variable is shared among all threads. While we might expect to see 0 as the final value of counter, the result is undefined. One thread can read the value while others might write to it, causing non-deterministic result. To fix the issue, we should use some of atomics as they seem to be the easiest to use.

### Changing atomic value

```cpp
#include <iostream>
#include <thread>
#include <vector>
#include <atomic>

int main() {
    std::atomic<int> counter{0};

    auto maxThreads = std::hardware_concurrency();
    std::vector<std::thread> threads;
    threads.reserve(maxThreads);
    for (int tCounter = 0; tCounter < maxThreads; ++tCounter) {
        threads.push_back([&counter]() noexcept {
            for (int i = 0; i < 1000; ++i) {
                counter.fetch_add(1);
                counter.fetch_sub(1);
                counter.fetch_add(1);
                counter.fetch_sub(1);
            }
        });
    }

    for (auto &thread : threads) {
        thread.join();
    }

    std::cout << counter.load() << std::endl;
}
```

The code above works as expected because increment and decrement operations are now atomic. This means that value cannot interrupt this action. The synchronisation makes code safer but at a price of performance. This is, however, a topic for longer discussion. Another option to solve the problem is to have a local variable in each thread that is computed. Then, before the thread ends, we could update the global value.

In C++20, as we can see, it's quite handy to create a thread with lambda expression. It's local to your thread, and you can do everything like with regular function or object.

### Lambdas with std::async

A second way that you can leverage multithreading is through std::async. This is a high-level API that you set up and call lazily or fully asynchronously. Together with threads in C++11, we rely on the mechanism of std::future. This is an object that handles the synchronisation and guarantees that the results are available when we ask it through .get(). In our case, we schedule the execution of the lambda through std::async, and then we need to call .get() to finish the computations blocking.

Let's convert our example with iota into the async call:

```cpp
#include <iostream>
#include <future>
#include <vector>
#include <numeric>

int main() {
    int startArg = 10;
    auto printThreadID = [](const char* str) {
        std::cout << str << " " << std::this_thread::get_id() << " thread id" << std::endl;
    };

    std::vector<int> numbers(100);
    std::future<std::vector<int>> iotaFuture = std::async(std::launch::async, [&numbers, startArg]() {
        std::iota(numbers.begin(), numbers.end(), startArg);
        printThreadID("iota in");
        return numbers;
    });

    std::vector<int> vec = iotaFuture.get(); // make sure we get the results...
    printThreadID("printing numbers");
    for (const auto &num : vec) {
        std::cout << num << " ";
    }
}
```

However the code above is cheating a little, we're using future<void> and the vector is still passed as the reference captured by lambda. As an alternative you might want to create std::future<std::vector<int>> so that we pass through the future mechanism:

```cpp
std::future<std::vector<int>> iotaFuture = std::async(std::launch::async, []() {
    std::vector<int> numbers(100);
    std::iota(numbers.begin(), numbers.end(), 10);
    std::cout << "calling from: " << std::this_thread::get_id() << " thread id" << std::endl;
    return numbers;
});
auto vec = iotaFuture.get(); // make sure we get the results...
```

It seems that over the years std::async/std::future has earned itself a mixed reputation. It looks like the functionality was a bit too rushed. It works for relatively simple cases but fails with advanced scenarios like:

- continuation
- task merging
- no cancellation/joining
- it's not a regular type
- and few other issues

- code::dive 2016 conference – Sean Parent – Better Code: Concurrency - YouTube

# Lambdas and Parallel Algorithms from C++17

After discussing the threading support in C++11, we can move to further standards: C++17. This time you have a easy-to-use technique that allows you to parallelise most of the algorithms from the Standard Library. All you have to do is to specify the first argument into the algorithm, for example:

```cpp
auto myVec = GenerateVector();
std::sort(std::execution::par, myVec.begin(), myVec.end());
```

Please notice the first argument: std::execution::par. It’s used to enable parallel execution of the sort algorithm.

And we have other options:

| Policy Name | Description |
|---|---|
| sequenced_policy | It is an execution policy type used as a unique type to disambiguate parallel algorithm overloading and require that a parallel algorithm’s execution not be parallelised. |
| parallel_policy | It is an execution policy type used as a unique type to disambiguate parallel algorithm overloading and require that a parallel algorithm’s execution may be parallelised. |
| parallel_unenced_policy | It is an execution policy type used as a unique type to disambiguate parallel algorithm overloading and require that a parallel algorithm’s execution may be parallelised. |

Execution policy declarations and global objects are located in the <execution> header. For each policy we have predefined instances:

- std::execution::par
- std::execution::seq
- std::execution::par_unseq

In C++20, there's also one more execution policy: unsequenced_policy along with the global instance std::execution::unseq. It's used to enable vectorised execution on a single thread.

While we can easily enable parallel sorting, we can also quickly write some bad code:

```cpp
#include <iostream>
#include <vector>
#include <numeric>
#include <execution>

int main() {
    std::vector<int> vec(1000);
    std::iota(vec.begin(), vec.end(), 0);
    std::vector<int> output;
    std::for_each(std::execution::par, vec.begin(), vec.end(), [&](int &elem) {
        if (elem % 2 == 0) {
            output.push_back(elem);
        }
    });

    for (const auto & elem : output) {
        std::cout << elem << ", ";
    }
}
```

By passing a lambda to std::for_each we need to remember that the execution doesn't happen on a single thread and locally. Several threads might be used here, for example, using a thread pool solution. That's why accessing a shared output vector is not the best idea. Not only can you insert elements in a wrong order, but it can crash if several threads attempt to change the vector at the same time.
