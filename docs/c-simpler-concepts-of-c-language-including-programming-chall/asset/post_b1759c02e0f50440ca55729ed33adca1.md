## 15.4.6. Comments and (program) documentation

Almost everyone agrees that a program should have good comments. Unfortunately, few people agree on the definition of a good comment. Some, in frustration, feel that minimal comments are the best. Others feel that line should have two or three comments attached to it. Everyone else wishes they had good comments in their program but never see the time to put them in.

It is rather difficult to characterize a "good comment." In fact, it is much easier to give examples of bad comments than is to discuss comments. The following list describes some of the worst possible comments you can put in a program:

- The absolute worst comment you can put into a program is an incorrect comment. Consider the following Pascal statement:
  `A := 10; { Set 'A' to 11 }`

- It is amazing how many programmers will automatically assume the comment is correct and tries to figure out how this code manages to set the variable "A" to the value 11 when the code obviously sets it to 10.

- The second worst comment you can place in a program is a comment that explains what a statement is saying. The typical example is like `A := 10; {Set 'A' to 10}`. Unlike the previous example, this is correct. But it is still worse than no comment at all it is redundant and forces the reader to spend additional time reading the code (reading time is directly proportional to reading difficulty). This also makes it harder to maintain since slight changes to the code (e.g., "A := 9") require modifications to the comment that would not be required.

- The third worst comment in a program is an irrelevant one. Telling a joke, for example, may seem cute, but does little to improve the readability of a program; indeed, it offers a distraction that breaks concentration.

- The fourth worst comment is no comment at all.

- The fifth worst comment is a comment that is obsolete or out of date (though incorrect). For example, comments at the beginning of the file may describe the current version of a module and who last worked on it. If the last programmer to modify the file did not update the comments, the comments are out of date.

Steve McConnell provides a long list of suggestions for high-quality code. His suggestions include:

- Using comments that don't break down or discourage modification. Essentially, he's saying a comment style that isn't so much people refuse to use it. He gives an example of a block of comments surrounded by asterisks as being hard to maintain. This is a poor example since modern text editors will automatically "outline" the comments for you. Nevertheless, the basic idea is sound.

- Comment as you go along. If you put off until the last moment, then it seems like another task in the software development process and management is likely to discourage the completion of the commenting task in hopes of meeting new deadlines.

- Avoid self-indulgent comments. Also, you should avoid sexist, profane, or other insulting remarks in your comments. Always remember, someone else eventually read your code.

- Avoid putting comments on the same physical line as the statement they describe. Such comments are very hard to maintain since there is very little room. McConnell suggests that endline comments are okay for variable declarations. For some this might be true but many variable declarations may require explanation that simply won't fit at the end of a line. One exception to this rule is "maintenance comments." Comments that refer to a defect tracking entry in the database are okay (note that the CodeWright editor provides a much better solution for this -- buttons that can bring an external file). Endline comments are also useful for marking the end of a control structure (e.g., "endif;")

- Write comments that describe blocks of statements rather than individual statements. Comments covering single statements to discuss the mechanics of that statement rather than discussing what the program is doing.

- Focus paragraph comments on the why rather than the how. Code should explain what the program is doing and why the programmer chose to do that way rather explain each individual statement is doing.

- Use comments to prepare the reader for what is to follow. Someone reading the comments should be able to have a good idea of what the following code does without actually looking at the code. Note that this rule also suggests that comments should always precede the code to they apply.

- When you need to restore to some tricky code, make sure you fully document what you've done.

- Avoid abbreviations. While there may be an argument for abbreviating identifiers that appear in a program, no way does this apply to comments.

- Keep comments close to the code they describe. The prologue to a program unit should give its name, describe the parameters, and provide a short description of the program. It should not go into details about the operation of the module itself. Internal comments should to that.

- Comments should explain the parameters, to a function, assertions about these parameters, whether they are input, or in/out parameters.

- Comments should describe a routine's limitations, assumptions, and any side effects.

## 15.6. SUMMARY

The experience of many projects leads to the conclusion that coding standards makes the project goes smoother. It makes the code readable, easily maintainable and makes it reusable.
