Having generated the object files the next step is to get the executable file generated. That needs combining all the object files and linking the necessary library files. How to do that would be the next question? It is again easier and simple.

```
$ gcc -o main.o add.o sub.o
```

This will now get the execfile generated and can be run as usual like ./execute. Well, What is the problem? Where is the file's role? If the file has to run so many times, it would be difficult to do all the steps as mentioned. Automating the process would be handy and make the job easier. But most important point is when there is change being made in any one of the files, say add.c or sub.c, user should execute the complete cycle again in the normal fashion that is being followed traditionally. So time for execution will be more in than if there are more files in the project, the when file is used, only the files in which the change is made in add.c, only add.c and main.c will be recompiled and will remain untouched if did not undergo any change. This is the biggest advantage and this prevents lot of time from wasted.

If there are 1000 files and in the first run, all the files got compiled, then the user wishes to change 1000 file's content, all the files and it would be restricted only to the files that are changed. i.e., 100 files alone would be re run and final linking making of executable file would happen with already available 900 object files plus newly 100 object files.
