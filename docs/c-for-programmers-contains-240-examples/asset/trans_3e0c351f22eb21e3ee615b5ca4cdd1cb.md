
在此处对它们进行建模。活动图首先从数据库中检索用户账户的可用余额。接下来，`BalanceInquiry`检索账户的总余额。最后，该交易在屏幕上显示余额。此操作完成交易执行。

UML将活动图中的动作表示为动作状态，用矩形建模，其左右两侧替换为向外弯曲的弧线。每个动作状态包含一个动作表达式——例如，“get available balance of user’s account from database”——该表达式指定要执行的动作。带实心箭头的箭头连接两个动作状态，指示动作状态所表示的动作发生的顺序。实心圆（图5.21顶部）表示活动的初始状态——即对象执行所建模动作之前工作流的开始。在此场景中，交易首先执行“从数据库获取用户账户的可用余额”动作表达式。其次，交易检索总余额。最后，交易在屏幕上显示两个余额。包含在空心圆中的实心圆（图5.21底部）表示最终状态——即对象执行完所建模动作之后工作流的结束。

图5.22展示了Withdrawal交易的活动图。我们假设一个Withdrawal对象已被分配了有效的账户号码。我们不建模用户从主菜单中选择取款或ATM将用户返回主菜单的过程，因为这些不是由Withdrawal对象执行的动作。交易首先显示标准取款金额菜单（图2.13）以及取消交易的选项。然后交易输入用户的菜单选择。活动流现在到达一个决策符号。此点根据相关的监护条件确定下一个动作。如果用户取消交易，系统显示适当的消息。接下来，取消流到达一个合并符号，此处该活动流与交易的其他可能活动流汇合（我们稍后讨论）。注意，合并可以有任意数量的传入转换箭头，但只能有一个传出转换箭头。图底部的决策确定交易是否应从开始处重复。当用户已取消交易时，监护条件“cash dispensed or user canceled transaction”为真，因此控制转换到活动的最终状态。

如果用户从菜单中选择取款金额，交易将amount（最初在图4.20中建模的Withdrawal类的一个属性）设置为用户选择的值。交易接下来从数据库获取用户账户的可用余额（即用户Account对象的`availableBalance`属性）。活动流随后到达另一个决策。如果请求的取款金额超过用户的可用余额，系统显示适当的错误消息，告知用户该问题。控制随后与其他活动流合并，然后到达图底部的决策。监护决策“cash not dispensed and user did not cancel”为真，因此活动流返回到图顶部，交易提示用户输入新金额。
