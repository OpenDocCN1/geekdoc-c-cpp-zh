
Code compiled to MSIL can be run in any environment for which the CLR is implemented. This is part of how the .NET Framework accomplishes portability.

Microsoft Intermediate Language is transformed into executable code utilizing a JIT compiler. JIT means "just in time." The procedure works this way: When a .NET program is executed, the CLR activates the JIT compiler. The JIT compiler converts MSIL into native code on an as-needed basis, as each piece of your program is required. Subsequently, your C# program really executes as native code, despite the fact that it was at first compiled into MSIL. This implies your program runs about as quickly as it would if it had been compiled to native code in the first place, however it gains the compactness and security advantages of MSIL. In addition to MSIL, one other thing is produced when you compile a C# program: metadata.

Metadata describes the data utilized by your program and enables your code to interface with other code. The metadata is contained in the same file as the MSIL. Luckily, for the purposes of this book, and for most programming projects, it isn't necessary to discover anything else about the CLR, MSIL, or metadata. C# handles the details for you.

As a rule, when you write a C# program, you are creating what is called managed code. Managed code is executed under the control of the Common Language Runtime, as just described. Since it is running under the control of the CLR, managed code is subject to certain requirements—and enjoys a few benefits. The limitations are easily described and met. The compiler must create an MSIL file targeted for the CLR (which C# does) and utilize the .NET Framework library (which C# does). The advantages of managed code are many, including modern memory management, the ability to mix languages, better security, support for version control, and a clean path for programming components to interact.

The opposite of managed code is unmanaged code. Unmanaged code doesn't execute under the Common Language Runtime. In this manner, all Windows programs before the creation of the .NET Framework use unmanaged code. It is feasible for managed code and unmanaged code to cooperate, so the fact that C# produces managed code doesn't limit its ability to work with previous programs.

At the focal point of C# is object-oriented programming (OOP). The object-oriented approach is intrinsic to C#, and all C# projects are, at least somewhat, object-oriented. Because of its significance to C#, it is valuable to understand OOP's essential principles before you write even a straightforward C# program.

OOP is a ground-breaking approach to the task of programming. Programming techniques have changed drastically since the invention of the computer, basically to accommodate the expanding complexity of projects. For instance, when computers were first invented, computer programming was accomplished by flipping switches to enter binary machine instructions using the computer's front panel. For as long as projects were only two or three hundred instructions in length, this methodology worked. As projects grew, assembly language was invented so that a programmer could deal with bigger, increasingly complex projects, using symbolic representations of the machine instructions. As projects kept on developing, high-level languages, for example, FORTRAN and COBOL, were introduced that gave the programmer more tools with which to deal with complexity. When these early languages started to reach their limit, structured programming was created.

Think about this: At every milestone in the evolution of programming, techniques and tools were made to enable the developer to manage progressively greater complexity. Each step of the way, the new approach took the best components of the past strategies and pushed ahead. The same is true for object-oriented programming. Before OOP, numerous projects were approaching (or even surpassing) the point where the structured methodology no longer worked. A superior method to handle complexity was required, and object-oriented computer programming was the solution. Object-oriented programming took the best ideas of structured programming and combined them with a few new ideas. The result was a different and better method for organizing a program.

In the broadest sense, a program can be organized in one of two different ways: around its code (what's happening) or around its data (what is being affected). Utilizing just structured programming techniques, programs are ordinarily written around code. This methodology can be thought of as "code acting on data." Object-oriented projects work in a different way. They are written around data, with the key principle being "data controlling access to code." In an object-oriented language, you define the data and the routines that are allowed to act on that data. In this manner, a data type defines exactly what kind of tasks can be applied to that data.

To help the principles of object-oriented programming, all OOP languages, including C#, share three characteristics in common: encapsulation, polymorphism, and inheritance.

Encapsulation is a programming mechanism that ties together code and the data it controls, and keeps both safe from outside interference and abuse. In an object-oriented language, code and data can be bound together so that an independent black box is made. Inside the box are all vital data and code. When code and data are connected together in this style, an object is made. In a sense, an object is the device that supports encapsulation.

Inside an object, code, data, or both might be private to that object or public. Private code or data is known to and available by just another piece of the object. That is, private code or data can't be accessed by a bit of the program that exists outside the object. When code or data is public, different pieces of your program can access it, even though it is defined inside an object. Normally, the public parts of an object are utilized to provide a controlled interface to the private components of the object.

C#'s essential unit of encapsulation is the class. A class defines the type of an object. It specifies both the data and the code that will work on that data. C# utilizes a class specification to develop objects. Objects are instances of a class. Along these lines, a class is basically a set of blueprints that determine how to construct an object.

The code and data that comprise a class are called members of the class. In particular, the data defined by the class is referred to as member variables or instance variables. The code that works on that data is referred to as member methods or just methods. "Method" is C#'s term for a subroutine. If you are familiar with C/C++, you might realize that what a C# programmer calls a method, a C/C++ developer calls a function. Since C# is a direct descendant of C++, the term "function" is additionally sometimes utilized when referring to a C# method.

Polymorphism (from Greek, signifying "many forms") is the property that enables one interface to access a general class of operations. A simple example of polymorphism is found in the steering wheel of a vehicle. The steering wheel (the interface) is the same, regardless of what sort of actual steering system is utilized. That is, the steering wheel works the same whether your vehicle has manual steering, power steering, or rack-and-pinion steering. Along these lines, turning the steering wheel left makes the vehicle go left regardless of what sort of steering is utilized. The benefit of the uniform interface is, obviously, that once you realize how to work the steering wheel, you can drive any sort of vehicle.

A similar principle can also apply to programming. For instance, think about a stack (which is a first-in, last-out list). You may have a program that requires three distinct kinds of stacks. One stack is utilized for integer values, one for floating-point values, and one for characters. In this case, the algorithm that implements each stack is the same, even though the data being stored varies. In a non-object-oriented language, you would be required to make three distinct sets of stack routines, with each set utilizing various names. However, as a result of polymorphism, in C#, you can determine the general type of a stack once and afterward use it for each of the three specific circumstances. Along these lines, if you realize how to utilize one stack, you can utilize them all. More generally, the idea of polymorphism is regularly expressed by the phrase "one interface, multiple methods."
