
First, you declare a private field, disposed, to be used to track whether the Dispose method has been called already, initializing disposed to False. In the Dispose method, check whether Dispose has already been called and return if it has. Perform the cleanup and then call the GC.SuppressFinalize() method, passing the reference to the object whose Finalize you need to suppress. Finally, set the field disposed to True.

Most of the time you won't have to implement a destructor or a Dispose method. Managed objects in the CLR will be garbage collected automatically. Implement a destructor and Dispose method if you are sure you need them.

## Implementing Events

Events form the zenith of the Windows object-oriented trinity, with properties and methods forming the base. Events were designed to react to events in code. As with properties and methods, there are two perspectives from which events can be seen, that of the consumer and that of the producer.

When you are writing classes, you will want to define internal events that you want to give consumers a chance to react to. For those events, you will need to declare an event and raise that event when the event occurs. When you are consuming classes, you will need to write event handlers, wire them up to an object's events, and write the code that actually reacts when the event is raised. (Wiring up an event essentially means connecting a method with an event.)

In C++ we use the function pointer idiom and in Delphi we use the procedural type idiom to implement events and event handlers. C# has developed what are effectively raw function pointers. C# implements the delegate idiom. Delegates are special classes that store the function pointer. The difference between a raw function pointer and a delegate is that a delegate can maintain more than one function pointer. Delegates containing more than one function pointer are referred to as multicast delegates.

Actually, the delegate definition describes the signature of a method as a type. Any method with a signature matching the signature of the delegate can be added to the invocation list of a delegate object. Defining a delegate signature is equivalent to defining a function pointer in C++ or a procedural type in Delphi. The following three statements show the similarities.

Each declaration generally represents a function pointer declaration in the respective languages. The difference is that only the C# delegate (or any .NET language delegate) can store more than one address. Function pointers in C++ and procedural types in Delphi can refer only to one function address. You would need to make an array of pointer types in C++ and Delphi to refer to different function addresses. C# effectively contains the array in the type, enabling one delegate to store multiple addresses. That is the huge distinction.

Obviously, if you are a VB6 developer, then you need to know what a function pointer is and then know what is different about a delegate. For C++ and Delphi experts, consider arrays of function pointers with a single signature. Unfortunately, if you don't know what a function pointer is and how to use delegates, then you will write code that is the equivalent of two-legged stools.

### Raising Events as a Producer

Producers raise events. Raising an event in C# is performed by calling a method using the event name. By convention, events are raised by protected members with the same name as the event with "On" as a prefix.

Returning to our original example of the Changed event defined as an EventHandler type, we can match the event with a protected method that raises the event.

The event is named "Changed." Consumers can assign any number of methods that match the signature of the EventHandler delegate to this one event member. Inside the class containing the code, you would call OnChanged anywhere that you need to raise the Changed event. OnChanged checks to ensure that Changed has been assigned to at least one delegate; if it hasn't, then OnChanged returns. Otherwise, Changed is treated like a method by the producer and is called, with the producer passing it the necessary arguments.

When a producer raises an event with a sender parameter, that value is always set to the internal reference to self: this. In our simple example, we pass an empty System.EventArgs parameter because we are not using that value. If you need to pass specific values to a consumer's event handler, then you can create an instance of System.EventArgs or create a delegate that takes a particular subclass of EventArgs.

Think of an event declaration as a field whose type is a delegate type: a delegate. When you assign a delegate to the event, you are embedding the delegate into a list that is a member of the delegate type. When you raise the event by invoking the event as a method call, you are really calling the delegates in that internal list.
