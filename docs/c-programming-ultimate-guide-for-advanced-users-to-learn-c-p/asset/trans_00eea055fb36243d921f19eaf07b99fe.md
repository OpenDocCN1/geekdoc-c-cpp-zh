事已至此，凭借稳定的手和一点恒心，你可以在像 Paint 这样的程序中绘制 Windows 应用程序结构。画布上的艺术作品表现与此完全相同，只不过你已将负责绘制的代码片段规范化。

在 Windows 中，画布被称为设备上下文（DC）。如果你曾用 GDI（.NET 之前的 Windows 编程）编程，那么你使用过需要设备上下文句柄的 API 技术，通常缩写为 hDC。GDI 难以接近的原因在于，GDI 包含在一组杂乱且未分类的结构和 API 策略中；换句话说，GDI 是过程式的。

GDI+ 是 GDI 的一个有条理且分类化的面向对象版本。通过将画布和其他绘图能力的概念具体化为面向对象结构，我们获得了与其他面向对象系统类似的优势。我们得到可重用的类和片段，它们越来越令人满意且易于理解。简而言之，GDI+ 将 GDI 包装成面向对象结构。现在，我们不再需要四处搜寻和啄取，只需查看一个通用区域——构成 GDI+ 的命名空间——并了解这些命名空间中类型和类的关联。

## GDI+ 命名空间

GDI+ 涉及 System.Drawing.dll 中的类，该程序集包含 System.Drawing、System.Drawing.Design、System.Drawing.Drawing2D、System.Drawing.Imaging、System.Drawing.Printing 和 System.Drawing.Text 命名空间。这些命名空间包含有助于三大类图形管理的类和类型：2D 矢量图形、成像和排版。

矢量图形包含由点来表征的基本线条、形状和曲线绘制能力。成像包含对显示难以使用矢量图形渲染的图形的支持，例如计算机照片、位图和符号。此外，排版支持使用各种文本样式、大小和样式来绘制内容。这种广泛的支持为你提供了巨大的适应性，用于渲染基于图形的图片、矢量图形和内容。

## 理解 GDI+ 编程模型

Internet 是无状态环境。在 Internet 时代，许多事物似乎都倾向于无状态。无状态基本上意味着，每当代码进行交互时，都必须被提醒它需要知道什么。（类似于在一个所有人都在合作但彼此陌生的聚会上佩戴身份证。无状态领域意味着你的代码对其他代码来说始终是陌生的。）

无状态对 Internet 很重要，因为它使得为许多关联客户端跟踪状态数据变得困难。我的假设是，被认为适用于 Internet 可能巨大规模的做法，同样可能有利于图形编程的需求。

用合理的说法，无状态意味着每次需要在画布上显示某些内容时，你都需要提醒 GDI+ 使用什么文本样式和画笔。就像一个老态龙钟的祖父，GDI+ 就是记不住。（稍后我们会回到文本样式和画笔。）这意味着你需要替 GDI+ 记住。换句话说，每次绘制某些内容时，你都应该向 GDI+ 说明用什么文本样式和画笔来绘制内容。GDI+ 不仅会忘记你刚才使用的文本样式和画笔，而且不会跟踪你上次撰写内容的位置，甚至还会忽略屏幕大小。信不信由你。如果画布大小在你上次提到 Graphics 对象（想想 DC）时和每次使用该 Graphics 对象之间发生变化，GDI+ 不会刷新关于画布大小的数据。

### 实现 PlayControl

PlayControl 由按钮组成。与标准按钮一样，这些按钮响应 Click 事件。这样，该控件非常直接：单击按钮，调用 Click 事件处理程序，并运行一些代码。

有两个问题使播放器控件在一般意义上可重用，而不是仅用于一个应用程序的单一使用结构。按钮被实现为离散控件，而 PlayControl 本身不做任何事情。每个 Button Click 事件基本上都会调用另一个类上的相关操作，该类实现 IPlayer 接口。（我们尚未讨论 IPlayer 接口；我们马上就会讲到。）例如，如果你单击 Play，那么与 PlayControl 关联的播放器的 Play 过程就会被调用——只要它实现 IPlayer 接口。因此，类使我们能够重用单个控件，而接口使我们能够重用整个部分。也许可以与收音机、录像机或盒式录音机相比较的东西可以使用这个通用部分。

实际上制作高级图形用户界面很费劲。制作迷人且专业的图形用户界面既真正考验人，又需要极高水平的才能，而权威人士比电脑分析师更可能具备这种水平。显然，杰出的工程师也有可能同时是才华横溢的权威人士，而这正是制作像图 3-2 中所示的 Windows Media Player 的 Headspace 皮肤那样的界面所期望的组合。
