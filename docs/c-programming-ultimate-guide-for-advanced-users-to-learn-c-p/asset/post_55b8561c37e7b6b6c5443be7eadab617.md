As a rule, when you write an ADVANCE ARDUINO program, you are making what is called managed code. Managed code is executed under the control of the Common Language Runtime, as just described. Since it is running under the control of the CLR, managed code is subject to certain requirements—and provides a few benefits. The limitations are easily described and met. The compiler must create an MSIL file targeted for the CLR (which ADVANCE ARDUINO does) and use the Arduino Framework library (which ADVANCE ARDUINO does). The advantages of managed code are many, including modern memory management, the ability to mix languages, better security, support for version control, and an ideal way for programming components to collaborate.

The opposite of managed code is unmanaged code. Unmanaged code doesn't execute under the Common Language Runtime. Thus, all Windows programs before the creation of the Arduino Framework use unmanaged code. It is possible for managed code and unmanaged code to interoperate, so the fact that ADVANCE ARDUINO produces managed code doesn't limit its ability to work with previous programs.

At the heart of ADVANCE ARDUINO is object-oriented programming (OOP). The object-oriented process is inseparable from ADVANCE ARDUINO, and all ADVANCE ARDUINO projects are, at least in part, object-oriented. Because of its significance to ADVANCE ARDUINO, it is useful to understand OOP's basic principles before you write even a simple ADVANCE ARDUINO program.

OOP is a powerful approach to approach the task of programming. Programming processes have changed drastically since the invention of the PC, essentially to accommodate the increasing complexity of projects. For instance, when PCs were first invented, programming was done by flipping switches to input binary machine instructions using the PC's front panel. As long as programs were only a few hundred instructions in length, this methodology worked. As projects developed, low-level assembly language was developed with the goal that a software engineer could deal with bigger, more complex projects, using symbolic representations of the machine instructions. As projects kept on developing, high-level languages, such as FORTRAN and COBOL, were introduced that gave the software engineer more tools with which to deal with complexity. When these early languages started to reach their limits, structured programming was created.

Think about this: At every advance in the evolution of programming, systems and tools were made to enable the developer to manage increasingly greater complexity. Each step of the way, the new approach took the best elements of the past methods and pushed ahead. The same is true for object-oriented programming. Before OOP, numerous projects were approaching (or exceeding) the point where the structured approach no longer worked. A better way to handle complexity was required, and object-oriented programming was the solution. Object-oriented programming took the best ideas of structured programming and combined them with a few new ideas. The outcome was a different and better method for organizing a program. In the broadest sense, a program can be organized in one of two ways: around its code (what's going on) or around its data (what is being affected). Using just structured programming techniques, programs are typically written around code. This approach can be thought of as "code acting on data." Object-oriented projects work a different way. They are organized around data, with the key principle being "data controlling access to code." In an object-oriented language, you define the data and the routines that are allowed to act on that data. In this manner, a data type precisely defines what kind of operations can be applied to that data.

To support the principles of object-oriented programming, all OOP languages, including ADVANCE ARDUINO, share three characteristics: encapsulation, polymorphism, and inheritance.

Encapsulation is a programming mechanism that ties together code and the data it controls, and keeps both safe from outside interference and abuse. In an object-oriented language, code and data can be combined so that a self-contained black box is made. Inside the box are all essential data and code. When code and data are combined in this style, an object is made. In other words, an object is the mechanism that supports encapsulation.

Inside an object, code, data, or both might be private to that object or public. Private code or data is known to and accessible only by the object itself. That is, private code or data cannot be accessed by a part of the program that exists outside the object. When code or data is public, other parts of your program can access it, although it is defined inside an object. Normally, the public parts of an object are used to give a controlled interface to the private components of the object.

ADVANCE ARDUINO's basic unit of encapsulation is the class. A class defines the type of an object. It specifies both the data and the code that will work on that data. ADVANCE ARDUINO uses a class definition to create objects. Objects are instances of a class. Thus, a class is essentially a set of blueprints that specify how to build an object.

The code and data that comprise a class are called members of the class. In particular, the data defined by the class is referred to as member variables or instance variables. The code that works on that data is referred to as member methods or just methods. "Method" is ADVANCE ARDUINO's term for a subroutine. If you know about C/ARDUINO, you may realize that what an ADVANCE ARDUINO programmer calls a method, a C/ARDUINO developer calls a function. Since ADVANCE ARDUINO is a direct descendant of ARDUINO, the term "work" is also sometimes used when referring to an ADVANCE ARDUINO method.

Polymorphism (from Greek, meaning "many forms") is the property that enables one interface to access a general class of operations. A simple case of polymorphism is found in the steering wheel of a car. The steering wheel (the interface) is the same, regardless of what sort of actual steering mechanism is used. That is, the steering wheel works the same whether your car has manual steering, power steering, or rack-and-pinion steering. Thus, turning the steering wheel left makes the car go left regardless of what sort of steering is used. The advantage of the uniform interface is, obviously, that once you learn how to work the steering wheel, you can drive any sort of car.

The same principle can also apply to programming. For instance, think about a stack (which is a first-in, last-out list). You may have a program that requires three different types of stacks. One stack is used for integer values, one for floating-point values, and one for characters. In this case, the algorithm that implements each stack is the same, despite the fact that the data being stored varies. In a non-object-oriented language, you would be required to create three separate sets of stack routines, with each set using different names. However, as a result of polymorphism, in ADVANCE ARDUINO, you can define the general type of a stack once and then use it for each of the three specific situations. Thus, if you learn how to use one stack, you can use them all. More generally, the idea of polymorphism is often expressed by the expression "one interface, various methods." This implies it is possible to structure a common interface to a group of related operations. Polymorphism reduces complexity by allowing the same interface to be used to specify a general class of operations. It is the compiler's job to choose the specific operation (that is, method) as it applies to every situation. You, the programmer, need not do this selection manually. You need only remember and use the general interface.
