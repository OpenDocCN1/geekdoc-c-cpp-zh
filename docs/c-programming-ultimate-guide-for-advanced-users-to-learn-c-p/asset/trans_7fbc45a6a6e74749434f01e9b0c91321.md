
娱乐。开发者们理所当然地享有长时间工作的声誉，但很少有人认为他们是受创造热情驱动的。程序员们谈论周末、度假期间以及晚餐时编程，并不是因为他们缺乏想象力，而是因为他们的想象力揭示了他人看不到的世界。

编程同样是一项技能，它构成了为数不多的几种职业的基础，这些职业始终需求旺盛、薪酬合理、允许在工作地点和工作时间上灵活安排，并且以奖励能力而非出生环境为荣。并非每个熟练的程序员都能就业，女性在管理层中代表性不足，开发团队也不是理想化的乌托邦。但总体而言，软件开发是一项极佳的职业选择。

编码，即逐行创建机器执行的精确指令，始终是也是将永远是软件开发的核心活动。我们可以自信地说这一点，因为无论规范语言、概率推理和机器智能如何发展，从客户价值的表述中消除歧义始终是一项细致的工作。

歧义本身对人们来说非常重要（“太美了！”“你绝对找不到杀手，”“自由与正义”）而软件开发，就像起草法律文件一样，是细节被赋予突出地位的地方，而这种突出地位与人们喜欢的沟通方式完全相反。

这并不意味着编码始终是编写高度结构化的文本行。统一建模语言（UML），它规定了适用于各种软件开发任务的各种图表的语法和语义，表达力足够强，可以在其中进行编码。然而，与编写文本行相比，这样做效率极低。另一方面，单一的 UML 图可以在一分钟内解释结构和动态关系，而这些关系如果用文字处理器或调试器来理解则需要几分钟甚至几小时。随着软件系统复杂性的不断增长，没有任何一种表示方法会被证明是普遍高效的，这一点是肯定的。但逐项、一点一点地消除歧义的任务将始终是一个乏味、易出错的过程，其效率取决于一个或多个开发者的才能。

专业软件开发不仅仅是编写代码。计算机程序是人类创造的最复杂结构之一，沟通愿望和约束、协调努力、管理风险，以及最重要的是，维持一个吸引最好的人才并激发他们最大努力的工作环境……嗯，软件项目管理需要一种不寻常的技能组合，这些技能或许比与编码相关的技能更罕见。每个伟大的程序员最终都会发现这一点（通常是在早期），而最好的程序员不可避免地会对软件开发流程及其最佳实践形成强烈的看法。他们成为团队负责人和架构师、构建经理和 CTO，而当这些精英程序员挑战自己完成这些任务时，他们有时会忽视或认为方法行间出现的问题微不足道。

本书止于屏幕边缘。这并不是说建模、流程和协作问题不如编码任务重要；我们作者知道这些事情对成功产品的开发至少与编码一样重要。但营销也是如此。本书中探讨的任务，即专业编码的关注点，很少以语言特定的方式被写出来。

编码的关注点（而非编码的简单细节）很少以语言特定的方式被探讨的一个原因是，几乎不可能对使用 Java 编程的个人的背景做出任何假设。

由于我们不可能对你的背景做出任何假设，我们转而假设你具备一些技能和动机。本书不断地在细节与理论之间来回移动论述层次，这一过程对某些学生来说显然是错误的。然而，快速的抽象层级转换是软件开发不可或缺的一部分。大多数程序员都能体会到这样的经历：在一次高谈阔论的会议上，讨论着“协作”和“新范式”和“钱从天上掉下来”，却突然被一名程序员怀疑地说“Now wait a second... ”然后说出非程序员听不懂的话。

然后另一名程序员作出同样难以理解的回应。这种“talking in code”来回持续了一会儿，怀疑的程序员突然摇头并对经理们宣布：“Oh, you don't see how huge this is!”

这不是一本关于捷径和凑合的书，而是一本关于以专业方式解决难题的书。遵循这一原则，Thinking in Java 在整本书中加快了讨论的节奏。书中早期占据数页对话的问题，在后期的章节中可能只是被随意提及甚至不予评论。当你使用 Java 专业地创建 Web Services 时，你应该能够在该章节所呈现的层面上审视面向对象的结构。

要理解 Java 在编程层面为何占据主导地位，关键在于了解它在商业层面如何占据主导地位，这意味着要谈论软件开发的经济学。

早在艾伦·图灵提出通用计算机的概念，随后约翰·冯·诺依曼提出存储程序的想法以来，软件创建者一直在努力平衡不断提高的抽象层级带来的图像操控能力与现有机器在速度、存储和传输通道容量方面的物理限制。至今仍有在世的人可以谈论如何通过拿着纸板尺子对准示波器来读取当时最现代计算机的输出，并将信号判断为 1 或 0。直到 20 世纪 80 年代中期，广泛使用的最酷的计算机（DEC PDP 系列）可以通过在板上拨动开关来编程，直接控制芯片级信号。此外，直到 1990 年代，一名计算机程序员不可能对各种中断请求和各种设备的内存位置一无所知。

在 20 世纪 60 年代中期，IBM 360 发布以及戈登·摩尔提出其著名定律——特定区域内的晶体管密度将以规律的间隔不断翻倍——之间，单条处理指令的成本已下降约 99.99%。这彻底改变了软件开发的经济学。过去，让程序员使用计算机内部表示的心理模型并牺牲开发时间以换取执行效率是有意义的，而现在，让计算机采用与开发者对任务的内部表示相对应的模型是有意义的，即使该表示并不理想高效。

今天，编程语言的质量可以通过其表达最广泛的问题和解决方案的有效性来判断。按此标准，面向对象、命令式编程语言绝对主导了软件开发的宇宙。命令式语言是指向计算机提供一系列指令的语言：做这个，然后做那个，然后完成另一件事。命令式似乎是编程计算机的“常见”方式，因为它与我们对计算机工作原理的心理模型相关，但正如上文所述，这已不再是拥抱一种编程语言的优秀理由。考虑一下使用电子表格解决某些问题是多么容易，电子表格可以被视为一种非命令式编程的形式。然而，命令式编程深深植根于主流精神中，在不久的将来不太可能被取代。
