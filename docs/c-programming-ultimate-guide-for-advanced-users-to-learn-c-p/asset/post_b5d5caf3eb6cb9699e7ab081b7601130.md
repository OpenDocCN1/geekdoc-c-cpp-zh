The following major step forward in programming languages was Java. Work on Java, which was initially called Oak, started in 1991 at Sun Microsystems. The primary force behind Java's design was James Gosling, Patrick Naughton, Chris Warth, Ed Frank, and Mike Sheridan also played a role.

Java is an object-oriented language with a syntax and semantics derived from C++. The innovative parts of Java were driven less by advances in the art of programming (although some surely were), but rather by changes in the computing environment. Before the mainstreaming of the Internet, most programs were written, compiled, and executed for a particular CPU and a particular operating system.

While it has always been true that programmers like to reuse their code, the ability to easily port a program from one environment to another assumed a lower priority relative to more pressing issues. However, with the rise of the Internet, in which many different kinds of CPUs and operating systems are connected, the old issue of portability became increasingly important. To solve this issue, another language was required, and this new language was Java.

Java achieved portability by translating a program's source code into an intermediate language called bytecode. This bytecode was then executed by the Java Virtual Machine (JVM). In this way, a Java program could run in any environment for which a JVM was available. Moreover, since the JVM is relatively easy to implement, it was readily available for numerous environments.

Although the need for portability was important, there was a second basic issue that had to be settled before Internet-based programming could become a reality. This issue was security. As all Internet users know, computer viruses pose a very real and ongoing threat. What good would portable programs be if nobody could trust them? Who would want to risk executing a program delivered over the Internet? It might contain malicious code. Luckily, the solution to the security issue is also found in the JVM and bytecode. Since the JVM executes the bytecode, it has full control of the program and can prevent a Java program from doing something that it shouldn't. In this way, the JVM and bytecode settled both the issues of portability and security.

It is fundamental to understand that Java's use of bytecode differs from both C and C++, which were always compiled to executable machine code. Machine code is tied to a specific CPU and operating system. Therefore, if you wanted to run a C/C++ program on a different system, it had to be recompiled to machine code specifically for that environment. To make a C/C++ program that would run in a variety of environments, several different executable versions of the program were required. Although this was possible, it was expensive. Java's use of a portable intermediate language was a cost-effective and efficient approach. It was also an approach that C# would adapt for its own purposes.

As mentioned, Java is descended from C and C++. Its syntax is based on C, and its object model is based on C++. Although Java code is neither upwardly nor downwardly compatible with C or C++, its syntax is sufficiently similar that the large pool of existing C/C++ programmers could move to Java with very little effort. Furthermore, because Java built on and improved upon a proven approach, Gosling, et al., were free to focus their efforts on the new and innovative features. Just as Stroustrup did not have to "go over an already solved issue" when creating C++, Gosling did not have to create an entirely new language when creating Java.

## Java Write-Only Properties

A write-only property declaration would have a setter only. Write-only properties are less common than read properties since it is harder to cause harm by reading a property than it is by writing a property.

One occasion where you might want to use writable properties is at the point at which you query for a password. You might not want to give consumers a chance to ask what password was provided after the password is provided. Probably, some wicked developer could snoop objects containing passwords.

The help documentation in Java Studio states not to use write-only properties. Semantically, write-only properties are methods that alter an object without a method to read the changed value. You may invent a phrase for write-only properties that is useful. There is no technical restriction against write-only properties.
