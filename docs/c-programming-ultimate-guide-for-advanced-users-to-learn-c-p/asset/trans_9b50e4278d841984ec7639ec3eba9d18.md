## 使用 SetStyle 方法

PlayControl 模拟了一个我们在界面制作上投入了大量精力的事件。背景图片代表了这种投入。如果用控件覆盖背景图片，那将是一种遗憾。通过允许背景图片透过控件显示，我们可以增强视觉上吸引人的背景。

遗憾的是，控件默认不支持透明背景。因此，我们要么让像 Tracker 这样的控件看起来像我们的背景图片，要么让背景图片显示在另一侧。后一种选择很可能产生最一致的结果，而且实现起来也更便宜。

当你将 Tracker 控件绘制到 PlayControl 上时，可以将 BackColor 设置为 Transparent，这将允许窗体上的背景图片显示在另一侧。实际效果是 Tracker 控件融入了 PlayControl。

计算机编程非常有趣。像音乐一样，它是一种源于天赋与持续练习的玄妙结合的技能。像绘画一样，它可以被塑造成多种目的——商业、艺术和纯粹的娱乐。程序员以长时间工作而闻名，这理所当然，但很少有人认为他们是由创新热情驱动的。程序员在周末、假期和晚餐时谈论软件开发，不是因为他们缺乏想象力，而是因为他们的想象力揭示了别人看不到的世界。

编程也是一种技能，它是少数几个始终需求旺盛、薪酬可观、允许地点和工作时间灵活、并以其重视功绩而非出身而自豪的职业之一。并非每位有才华的程序员都被雇用，女性在管理层中代表性不足，开发团队也不是无视觉障碍的乌托邦。但总的来说，产品开发是一个极好的职业选择。

编码，即逐行编写机器执行的精确指令，现在是并且将永远是软件开发的核心活动。我们可以确信地说这一点，因为无论规范语言、概率推断和计算机智能方面发生什么，从客户价值陈述中消除模糊性始终是一项细致的工作。

模糊性本身对人类来说极其重要（“真漂亮！”“你绝不会错过这场扫兴者”，“人人享有自由与公平”），而软件开发，就像制定法律文件一样，是细节被赋予显著性的地方，这与人们喜欢交流的方式截然相反。

这并不是说编码将总是由高度结构化的文本行组成。

统一建模语言（UML）指定了适用于各种软件开发任务的各类图表的语法和语义，其表达能力足以让人在其中进行编码。然而，与编写文本行相比，这样做极其低效。另一方面，一个 UML 图可以在瞬间阐明使用文字处理器或调试器需要几分钟或几小时才能理解的静态和临时关系。可以肯定的是，随着软件系统在复杂性上持续增长，没有一种单一的表示形式会被证明是普遍高效的。但是，逐任务、逐步地消除歧义的工作将始终是一个繁琐且容易出错的过程，其效率取决于一个或多个程序员的才能。

专业的软件开发不仅仅是编写代码。计算机程序是人类构建过的最复杂的结构之一，而传达愿望和约束、组织协作、管理风险，以及最重要的是维持一个吸引最优秀人才并激发他们最大努力的工作环境…… 嗯，软件项目管理需要一系列非凡的技能，这些技能可能比与编码相关的技能更为罕见。每个程序员最终都会发现这一点（通常很快就会），而最优秀的程序员不可避免地对软件开发过程及其最佳实践形成强烈观点。他们成为团队负责人和架构师、工程经理和 CTO，而当这些精英程序员挑战自己处理这些任务时，他们有时会忽略或轻视出现在函数行之间的挑战。

这本书止步于屏幕边缘。这并不是说建模、流程和协作的问题不如编码任务重要；我们作者知道，这些对成功产品的开发至少与编码一样重要。但营销也是如此。本书中讨论的任务——专业编码的关切——很少以特定语言的方式被详细阐述。

编码的关切（而非编码的简单细节）很少以特定语言的方式被讨论的一个原因是，几乎不可能预料到用 C# 编程的个人的背景。

由于我们无法假设你的任何背景，我们反而对你的技能和动机做一些假设。这本书不断地将讨论层次从细节转移到理论，再回到细节，这一过程对某些学习者来说显然不合适。然而，抽象层次的快速转换是软件开发的一个组成部分。大多数程序员都能体会到这样一次高水平的会议经历：会上讨论“协作”“新范式”和“钱从天花板上掉下来”，突然被一位程序员打断，他怀疑地说：“等等……”然后说出一些对非开发人员来说无比深奥的话。

接着另一位程序员说了同样令人费解的话作为回应。这种“双向对话”来回进行了一会儿，然后那位持怀疑态度的程序员突然回过神来，对代理商们宣布：“哦，你们不明白这有多大！”

这不是一本关于捷径和应付的书，而是一本关于以专业方式处理棘手问题的书。在这个意义上，《Thinking in C#》在整本书中加快了讨论的节奏。早期书中花了大量页数讨论的问题，在后来的章节中可能会被随口提及甚至不加评论。当你专业地使用 C# 开发 Web Services 时，你应该能够在那一章所展示的层面上讨论面向对象设计。

然而，要理解 C# 和 .NET 为什么在编程层面取得成功，重要的是要看到它们在商业层面如何取得成功，也就是说，要讨论软件开发的经济学。
