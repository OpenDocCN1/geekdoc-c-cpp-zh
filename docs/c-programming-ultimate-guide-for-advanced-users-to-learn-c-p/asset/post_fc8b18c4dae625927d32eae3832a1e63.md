## ThreadPool Threading

The ThreadPool is a class that manages a pool of threads for you. Multithreading using threads in the ThreadPool is the same as creating a Thread object. However, your workload is helped a bit, and grabbing a thread from the pool is often somewhat faster than creating an instance of the Thread class because the pool probably has a thread waiting for you to give it work.

To use a thread in the ThreadPool, you simply give the ThreadPool some work to do as a Delegate. In this example, the Delegate acts as a mechanism representing work for the thread to do. Every other part of threading is identical to creating a Thread object yourself. The most important thing to remember is that ThreadPool threads require the same amount of care as Thread instances, particularly with regard to Windows Forms controls. Windows Forms controls are not thread-safe; therefore, you should take additional care when interacting with Windows Forms controls from a thread.

## The Best Way to Understand Overloaded Operators

The best way to understand overloaded operators is to write some simple examples and set breakpoints on the statements that invoke the operator and in the operator method. You will quickly observe that the operation results in a method invocation.

## Overloading Operator Guidelines and Limitations

Be prudent about defining overloaded operators. The most important thing to avoid doing is making operators that are outlandish. For instance, overloading the addition operator to perform subtraction. Do not do this. Following these essential rules for overloading operators will keep you out of trouble:

- Define methods that perform the operation using the op_ prefix followed by the name of the operator to support languages like Visual Basic .NET that don't support operator overloading.
- Implement the overloaded operator by calling the named method. (Why duplicate the operator behavior twice?)
- Overload an operator only in the class the operator applies to.
- Use operator overloading when the operation is intuitive and the result seems logical.
- Overload operators symmetrically. If you implement addition, then implement subtraction.

## Attributes

It is terms like interface and attributes that push us into difficulty as software engineers. The explanation is that these terms carry out double duty. For a long time, "interface" meant essentially the members declared in a class. When COM was introduced, interface took on another meaning; interface became a construct—a great deal like a class. (For VB developers, interfaces and classes blur a lot.)

A similar issue exists for "attribute" and the idiom Attribute. In the general sense, "attribute" is synonymous with "property." An attribute is a property of a type. The .NET Attribute itself is really a class. (There are probably going to be the same number of confusing discussions surrounding attributes as there are about parent and child, superclass and subclass, and object and class.)

In C#, an Attribute with a capital A will be a class that adds metadata to your assembly.

Metadata, or extra information, was added to help eradicate "DLL Hell." Historically, external information that an application required was stored in a library or INI file. Properties enable this supporting cast of information to go with the assembly. Attribute classes enable you to add the metadata to your assemblies, and Reflection enables you to retrieve that metadata when you need it. This closely resembles reading and writing from the library. Because the metadata is cleverly collapsed into the assembly, deploying .NET applications is easier than shipping COM-based applications.

Examples of attributes can be found in the AssemblyInfo.cs module. An example is the AssemblyTitleAttribute class.

By including content between the brackets in the AssemblyTitleAttribute, you can include a title for your assembly that will appear in the Properties dialog. By convention, attribute classes have an Attribute suffix, but the suffix is left off when the attribute is used. The assembly: tag shows this is an assembly-level attribute.

Since attributes are implemented as classes, you generalize existing Attribute classes to make new attributes for new uses. Attributes are used for many things, from giving hints to component properties to requesting security permissions. Numerous new attributes will be made, but the pattern for using Attributes is similar to that for developing an object. Place the name of the Attribute class preceding the element the Attribute describes and pass the arguments defined by the Attribute's constructor. Constructor arguments are referred to as positional arguments. You can likewise initialize properties in an Attribute object by passing named arguments.
