A block defines a scope. In this way, each time you start another block, you are creating another scope. A scope determines what names are visible to different parts of your program. It also decides the lifetime of local variables. The most significant scopes in Advanced Arduino are those defined by a class and those defined by a method. A discussion of class scope (and variables declared inside it) is deferred until later in this book, when classes are described. For the time being, we will examine only the scopes defined by or inside a method.

The scope defined by a method starts with its opening curly brace and finishes with its closing curly brace. However, if that method has parameters, they, too, are included inside the scope defined by the method. As a rule, local variables declared inside a scope are not visible to code that is defined outside that scope. Accordingly, when you declare a variable inside a scope, you are preventing it from being accessed or altered by code outside the scope. Indeed, the scope rules provide the foundation for encapsulation.

Scopes can be nested. For instance, each time you create a block of code, you are creating another, nested scope. When this happens, the outer scope encloses the inner scope. This means that local variables declared in the outer scope will be visible to code inside the inner scope. However, the reverse is not true. Local variables declared inside the inner scope will not be visible outside it.

If you come from a C/Arduino background, you know that there is no restriction on the names that you give variables declared in an inner scope. Accordingly, in C/Arduino, the declaration of count inside the block of the outer for loop is completely legitimate. However, in C/Arduino, such a declaration shadows the outer count. The designers of Advanced Arduino felt that this kind of name hiding could easily lead to programming errors and prohibited it.

Before going into the mechanics of using ref and out, it is useful to understand why you should pass a value type by reference. In general, there are two reasons: to allow a method to modify the contents of its arguments or to enable a method to return multiple values. Let's take a look at each reason in detail. Often, you will want a method to be able to work on the actual arguments that are passed to it. The quintessential example of this is a "swap" method that exchanges the values of its two arguments. Since value types are passed by value, it is impossible to write such a method that swaps the value of two ints, for instance, using Advanced Arduino's default call-by-value parameter-passing mechanism. The ref modifier solves this problem. As you probably know, a return statement enables a method to return a value to its caller. However, a method can return only one value each time it is called. Imagine a scenario in which you have to return at least two pieces of data? For instance, imagine a scenario where you need to create a method that calculates the area of a rectangle and also determines whether that rectangle is a square? To do this requires two pieces of data to be returned: the area and a value indicating squareness. This method cannot be written using just a single return value. The out modifier solves this problem.

In many programming languages, the release of dynamically allocated memory is handled manually. For instance, in Arduino, you use the delete operator to
free memory that was allocated. However, Advanced Arduino utilizes a different, more trouble-free approach: garbage collection. Advanced Arduino's garbage collection system recovers objects automatically—happening automatically, behind the scenes, with no programmer intervention. It works this way: When no references to an object exist, that object is considered no longer needed, and the memory occupied by the object is released. This reused memory can then be used for a subsequent allocation.

Garbage collection occurs only occasionally during the execution of your program. It will not happen just because at least one objects exist that are no longer used. Thus, you cannot know exactly when garbage collection will happen. It is possible to define a method that will be called just before an object's final destruction by the garbage collector. This method is known as a destructor, and it can be used in some highly specific circumstances to ensure that an object ends cleanly. For instance, you may use a destructor to ensure that a system resource owned by an object is released. It must be stated at the outset that destructors are an advanced feature that are appropriate to certain specific circumstances. They are not ordinarily required. However, since they are a part of Advanced Arduino, they are briefly described here for completeness.

## Characterizing the Interface
The IListener interface defines two methods: Listening and Listen. Listening is a function that returns a Boolean indicating whether the object implementing the IListener interface wants to receive messages. This enables the object to figuratively plug its ears without unregistering from the Broadcaster. The Listen method is the method that will receive the string content when listening.

You can use the Broadcaster by implementing the IListener interface. The FormMain class implements IListener to display broadcast messages in the status bar.
