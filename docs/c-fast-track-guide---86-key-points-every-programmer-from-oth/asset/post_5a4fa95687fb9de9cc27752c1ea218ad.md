## 67. How Static Constructors Prepare Static Data Before First Use

![](img/bb6e93ece31f33afd31e933e9dd494be_195_3.png)

Static constructors initialize static members once, automatically before any access to them.

Let’s look at a simple example where a static constructor is used to initialize static data in a class.

[Code Example]

```
using System;

class Config
{
    // Static field shared by all instances
    public static string AppName;

    // Static constructor: runs only once, before any static member is accessed
    static Config()
    {
        Console.WriteLine("Static constructor executed.");
        AppName = "MyAwesomeApp";
    }
}

class Program
{
    static void Main()
    {
        // Accessing static field triggers static constructor
        Console.WriteLine($"Application: {Config.AppName}");
    }
}
```

![](img/bb6e93ece31f33afd31e933e9dd494be_196_0.png)

[Execution Result]

Static constructor executed.

Application: MyAwesomeApp

![](img/bb6e93ece31f33afd31e933e9dd494be_196_1.png)

In C#, a static constructor is a special constructor that doesn't take any parameters and cannot be called directly. It is automatically invoked by the .NET runtime before the first access to any static member in the class or before any instance of the class is created (whichever comes first). It ensures that static members are properly initialized.

Only one static constructor is allowed per class, and it executes exactly once per type, regardless of how many times or from where the type is accessed. If a class contains a static field but no static constructor, C# may still perform "lazy" initialization when the static member is first used.

Also, you can't control when the static constructor is called, nor can you catch exceptions it throws (they are considered fatal).

This mechanism is critical for setting up application-wide configuration, caches, or other global state that should be initialized just once.

![](img/bb6e93ece31f33afd31e933e9dd494be_197_0.png)

### [Supplement]

Static constructors cannot have access modifiers (like public, private) — they are always private by nature.

If no static constructor is defined, the CLR handles default static field initialization.

Static constructors help prevent race conditions during static initialization in multithreaded environments.

## 68. Immutable Structs Using readonly struct

![](img/bb6e93ece31f33afd31e933e9dd494be_198_3.png)

readonly struct ensures that struct fields cannot be modified after creation, making them immutable.

Here’s an example where a struct is made immutable using the readonly keyword, which is helpful for value types like coordinates or colors.

[Code Example]

```
using System;

// Define a readonly struct for immutable data

public readonly struct Point
{
    public int X { get; }
    public int Y { get; }

    // Constructor sets values; fields can't be changed after this
    public Point(int x, int y)
    {
        X = x;
        Y = y;
    }
    public void Print()
    {
        Console.WriteLine($"Point is at ({X}, {Y})");
    }
}
class Program
{
    static void Main()
    {
        Point p = new Point(10, 20);
        p.Print();
        // The following line would cause a compile error if uncommented:
        // p.X = 30;
    }
}
```

![](img/bb6e93ece31f33afd31e933e9dd494be_199_0.png)

[Execution Result]

Point is at (10, 20)

________

![](img/bb6e93ece31f33afd31e933e9dd494be_200_0.png)

In C#, structs are value types. Making them readonly prevents unintended changes after creation. When a struct is marked as readonly, all its fields and properties must also be immutable — this is enforced at compile time.

If you try to assign to any field or property of a readonly struct outside its constructor, you'll get a compiler error. This is great for modeling pure data structures like vectors, dates, or 2D points where immutability is preferred.

One major benefit is that the compiler can optimize readonly structs for performance, especially in scenarios involving passing data around in memory or across threads.

Also, readonly struct helps avoid defensive copies. Normally, when calling methods on a non-readonly struct, the compiler might copy it to avoid mutation. With readonly struct, the compiler knows no mutation occurs, so copying is skipped — leading to better performance.

________

![](img/bb6e93ece31f33afd31e933e9dd494be_200_1.png)

### [Supplement]

Properties with get; set; cannot be used in readonly struct unless the set; is private and only used in the constructor.

You can use with expressions with readonly struct when combined with C# record structs (C# 10+).

Immutability is especially useful when working in multi-threaded environments, reducing bugs caused by shared mutable state.

## 69. SIMPLIFIED NAMESPACE DECLARATION WITH FILE-SCOPED SYNTAX

File-scoped namespaces let you write cleaner, less indented code by removing the need for extra braces when declaring a namespace.

Here's a comparison between the traditional namespace syntax and the newer file-scoped syntax.

[Code Example]

```
// Traditional namespace syntax
namespace MyApp
{
    class Program
    {
        static void Main()
        {
            Console.WriteLine("Hello from traditional namespace!");
        }
    }
}

// File-scoped namespace syntax (C# 10 or later)
namespace MyApp;
class Program
{
    static void Main()
    {
        Console.WriteLine("Hello from file-scoped namespace!");
    }
}
```

### [Execution Result]

Hello from traditional namespace!
Hello from file-scoped namespace!

In traditional C# code, the namespace keyword wraps all the content inside a block, requiring extra indentation and braces {}.

With the introduction of file-scoped namespaces in C# 10, you can now end the namespace declaration with a semicolon ;

which tells the compiler that all subsequent types (classes, interfaces, etc.) belong to this namespace—without needing a block.

This makes files easier to read and avoids deep nesting, especially in large projects.

### Important Notes:

This feature requires C# 10 or later, so make sure your project is targeting .NET 6 or later.

You can only have one file-scoped namespace per file.

This change is purely syntactic—there's no behavioral difference at runtime.

This feature is especially useful for developers transitioning from other languages that use flat or simplified module structures.

### [Supplement]

The syntax namespace Name; was inspired by modern languages that favor simplicity, like Python (which uses modules) and JavaScript (which uses ES modules).

Also, some IDEs (like Visual Studio) may auto-convert traditional namespaces to file-scoped for you when refactoring code.

## 70. Global Using Simplifies Imports Across Files

![](img/bb6e93ece31f33afd31e933e9dd494be_204_3.png)

The global using directive allows you to import namespaces across all files in a project, reducing redundancy and improving consistency.

Here’s how global using removes the need to repeat the same using statements in every C# file.

[Code Example]

```csharp
// File: GlobalUsings.cs

global using System;

global using System.Collections.Generic;

// File: Program.cs

class Program
{
    static void Main()
    {
        List<string> names = new List<string> { "Alice", "Bob" };
        Console.WriteLine(string.Join(", ", names));
    }
}
```

![](img/bb6e93ece31f33afd31e933e9dd494be_205_0.png)

[Execution Result]

Alice, Bob

![](img/bb6e93ece31f33afd31e933e9dd494be_205_1.png)

Before C# 10, every file had to manually declare using directives like:

```
using System;
```

```
using System.Collections.Generic;
```

This gets tedious, especially for commonly used namespaces.

With global using, you can declare such statements once in a single file (commonly GlobalUsings.cs),

and they apply project-wide. This not only saves time but keeps your code DRY (Don't Repeat Yourself).

### Key Points:

- Use global using only for namespaces used throughout many files.
- This feature works best in large projects or shared libraries.
- Keeps code cleaner and avoids forgotten using errors.
