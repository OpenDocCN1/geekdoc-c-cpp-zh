## 54. NATIVE DEPENDENCY INJECTION SUPPORT IN .NET

Dependency Injection (DI) is natively supported in .NET applications, helping to manage class dependencies more cleanly and testably.

This example shows how to use built-in dependency injection in a .NET console application.

### [Code Example]

```csharp
using System;
using Microsoft.Extensions.DependencyInjection;

// Define a service interface
public interface IMessageService
{
    void Send(string message);
}

// Implement the service
public class ConsoleMessageService : IMessageService
{
    public void Send(string message)
    {
        Console.WriteLine("Message sent: " + message);
    }
}

class Program
{
    static void Main()
    {
        // Set up the DI container
        var serviceProvider = new ServiceCollection()
            .AddTransient<IMessageService, ConsoleMessageService>()
            .BuildServiceProvider();

        // Request the service from the container
        var service = serviceProvider.GetService<IMessageService>();
        service.Send("Hello from DI!");
    }
}
```

### [Execution Result]

Message sent: Hello from DI!

DI separates object creation from business logic, increasing modularity.

- ServiceCollection is used to register services in the DI container.
- .AddTransient<TInterface, TImplementation>() registers a new instance each time it's requested.
- You can also use .AddScoped() (per request) and .AddSingleton() (one instance for the app lifetime).
- Microsoft.Extensions.DependencyInjection is a built-in package; no external libraries are needed.

### [Supplement]

ASP.NET Core uses the same DI system by default in controllers, middleware, etc.

DI is essential for writing unit-testable code because dependencies can be mocked or stubbed easily.

This pattern is also crucial for working with services like logging, configuration, and database contexts.

## 55. USING [OBSOLETE] TO MARK DEPRECATED CODE

The [Obsolete] attribute in C# is used to mark code elements (methods, classes, properties, etc.) that should no longer be used. It can show a warning or an error when that code is used elsewhere.

Here is a simple example that shows how to use the [Obsolete] attribute to warn developers about outdated methods.

### [Code Example]

```csharp
using System;

class MyLibrary
{
    // Marked as obsolete, this method should not be used anymore
    [Obsolete("Use NewMethod instead")]
    public static void OldMethod()
    {
        Console.WriteLine("This is the old method.");
    }

    public static void NewMethod()
    {
        Console.WriteLine("This is the new method.");
    }
}

class Program
{
    static void Main()
    {
        MyLibrary.OldMethod(); // This line will generate a compiler warning
        MyLibrary.NewMethod();
    }
}
```

### [Execution Result]

This is the old method.

This is the new method.

(Plus, a compiler warning: 'MyLibrary.OldMethod()' is obsolete: 'Use NewMethod instead')

The [Obsolete] attribute is a metadata tag in C#. When placed above a class, method, or property, it tells the compiler to warn (or error, depending on the setting) when the code is used.

This is incredibly useful for maintaining large codebases, especially when:

- You’re refactoring or improving code.
- You want to avoid accidental usage of outdated functions.
- You need to guide other developers to use updated APIs.

Syntax:

```csharp
[Obsolete("Your message here", true)] // true makes it a compile-time error
```

In the code above, the message "Use NewMethod instead" helps the developer understand what to use in place of the deprecated method.

You can also force the compiler to throw an error instead of just a warning by passing true as the second argument:

```csharp
[Obsolete("Use NewMethod instead", true)]
```

This prevents the deprecated method from compiling at all.

### [Supplement]

- The [Obsolete] attribute is available in all versions of .NET.
- You can mark entire classes, not just methods.
- This attribute is compile-time only — it doesn't affect runtime behavior.
- Many standard .NET APIs use [Obsolete] to guide developers toward newer practices.

## 56. INTRO TO UNIT TESTING: MSTEST, XUNIT, AND NUNIT

Unit testing ensures your code works correctly by checking individual units (like methods) in isolation. In C#, common testing frameworks are MSTest, xUnit, and NUnit.

This is an example using xUnit, one of the most popular unit testing frameworks for C#. We'll test a simple method to ensure it returns correct results.

### [Code Example]

```csharp
// File: Calculator.cs
public class Calculator
{
    public int Add(int a, int b) => a + b;
}

// File: CalculatorTests.cs
using Xunit;

public class CalculatorTests
{
    [Fact] // This attribute marks a test method
    public void Add_ShouldReturnCorrectSum()
    {
        var calc = new Calculator();
        int result = calc.Add(2, 3);
        Assert.Equal(5, result); // Passes if result == 5
    }
}
```

To run the test, use:

```bash
dotnet test
```

### [Execution Result]

Passed! CalculatorTests.Add_ShouldReturnCorrectSum

### What's going on:

xUnit is a .NET testing framework, similar in purpose to Python’s unittest or Java’s JUnit.

A [Fact] attribute marks a method as a test case. It means “this should always pass with no inputs.”

Assert.Equal(expected, actual) checks if the values match. If they don’t, the test fails.

dotnet test will auto-discover and run tests in the project.

### How to set it up:

Install xUnit via NuGet:

```bash
dotnet add package xunit
dotnet add package xunit.runner.visualstudio
```

Create a test project:

```bash
dotnet new xunit -n MyTests
```

### MSTest vs NUnit vs xUnit:

| Feature | MSTest | NUnit | xUnit |

| Built-in to VS | Yes | No | No |
| Community Fav. | No | Some | Yes |
| Syntax Style | Traditional | Familiar | Modern |

xUnit is preferred for new projects due to its modern design and better extensibility.

### [Supplement]

- Unit tests are repeatable and automated — you can run hundreds in seconds.
- Use [Theory] in xUnit for parameterized tests.

## 57. STRONG NAMING AND ASSEMBLY VERSIONING FOR SAFE EXECUTION

Assembly versioning allows multiple versions of a library (DLL) to coexist, while strong naming ensures assemblies are uniquely identified and tamper-proof.

The following example demonstrates how to apply a strong name and understand versioning in C#.

### [Code Example]

```csharp
// AssemblyInfo.cs
// Set assembly version explicitly
[assembly: AssemblyVersion("1.0.0.0")]
// Set strong name by signing with a key
// (You must generate a key file using 'sn.exe -k MyKey.snk' first)
[assembly: AssemblyKeyFile("MyKey.snk")]
// To generate the key file, use this command in Developer Command Prompt:
// sn.exe -k MyKey.snk
// To compile with the strong name:
//
// csc /keyfile:MyKey.snk /target:library MyLibrary.cs
```

### [Execution Result]

Generates a strongly-named DLL with version 1.0.0.0 — e.g., MyLibrary.dll

Can be installed in Global Assembly Cache (GAC) for shared use.

Assemblies in .NET are compiled code (DLLs or EXEs). Without versioning, newer versions can overwrite old ones and break existing apps.

Strong naming solves this by combining the assembly's name, version, culture, and a public key into a unique identity.

Side-by-side execution allows different versions of the same library to run simultaneously, preventing "DLL Hell" — a common issue in older Windows development.

To enable strong naming:

- Use sn.exe to generate a key pair.
- Add [assembly: AssemblyKeyFile("...")] to your AssemblyInfo.cs.
- Compile with the /keyfile: option.

This results in a cryptographic signature. The CLR can now verify the integrity and origin of the assembly.

### [Supplement]

- The Global Assembly Cache (GAC) stores strongly-named assemblies that can be shared across applications.
- Versioning uses the format: Major.Minor.Build.Revision
- Only strongly-named assemblies can be installed in the GAC.
- Weak-named assemblies can be overwritten, which is why strong naming is essential for public/shared libraries.
