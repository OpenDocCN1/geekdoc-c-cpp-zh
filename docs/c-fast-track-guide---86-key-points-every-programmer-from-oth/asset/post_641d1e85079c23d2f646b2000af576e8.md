## 82. SQL Injection Protection with C# ORM

![](img/bb6e93ece31f33afd31e933e9dd494be_240_3.png)

C# ORMs like Entity Framework automatically parameterize SQL queries, helping protect against SQL injection attacks.

This example shows how using LINQ queries with Entity Framework Core automatically avoids SQL injection vulnerabilities.

[Code Example]

```
```csharp
// Assumes a simple EF Core setup with a User model and DbContext
using System;
using System.Linq;
using Microsoft.EntityFrameworkCore;
public class User
{
public int Id { get; set; }
public string Username { get; set; }
}
public class AppDbContext : DbContext
```
```
{
public DbSet<User> Users => Set<User>();
protected override void OnConfiguring(DbContextOptionsBuilder options)
=> options.UseInMemoryDatabase("TestDb"); // In-memory for demo purposes
}
class Program
{
static void Main()
{
using var context = new AppDbContext();

// Seed a user
context.Users.Add(new User { Username = "Alice" });
context.SaveChanges();

// Simulate user input (e.g., from a login form)
string userInput = ""; DROP TABLE Users;--"; // An attack string

// LINQ query is safe: parameters are auto-handled by EF
var user = context.Users.FirstOrDefault(u => u.Username == userInput);
Console.WriteLine(user == null ? "No match found (safe!)" : "User found: " + user.Username);
}
}
```

![](img/bb6e93ece31f33afd31e933e9dd494be_242_0.png)

[Execution Result]

No match found (safe!)

![](img/bb6e93ece31f33afd31e933e9dd494be_242_1.png)

LINQ queries in Entity Framework are translated to parameterized SQL.

This means dangerous inputs like '; DROP TABLE Users;--' are safely escaped and treated as strings.

You must avoid raw SQL or string concatenation—use EF methods instead.

If raw SQL is absolutely necessary, use FromSqlInterpolated or FromSqlRaw with parameters.

![](img/bb6e93ece31f33afd31e933e9dd494be_242_2.png)

[Supplement]

SQL Injection is one of the most common web vulnerabilities.

ORM frameworks like Entity Framework, Dapper, NHibernate offer built-in safety when used correctly.

Never trust user input—always validate and sanitize, even with ORM protections in place.

## 83. IMPROVE CODE QUALITY WITH ROSLYN ANALYZERS

C# developers can use code analyzers powered by Roslyn to automatically detect issues, enforce best practices, and maintain clean code.

The following example shows how to use a Roslyn analyzer to detect an unused variable, and how it appears in a development environment like Visual Studio.

[Code Example]

```
```csharp
// Example C# code that would trigger a Roslyn analyzer warning
using System;
class Program
{
static void Main()
{
int unusedVariable = 42; // This line will trigger a warning from analyzers
Console.WriteLine("Hello, world!");
}
}
```
```

[Execution Result]

A squiggly line appears under 'unusedVariable', and a warning like:
IDE0059: Unnecessary assignment of a value to 'unusedVariable'

Roslyn is the .NET Compiler Platform, which not only compiles code but also exposes powerful APIs to analyze and refactor code. Visual Studio uses Roslyn analyzers internally to give developers real-time feedback on coding issues.

These analyzers detect things like:

- Unused variables or using directives
- Naming convention violations
- Possible bugs (e.g., unreachable code)
- Code style preferences (like spacing, parentheses, or curly braces)
- Performance suggestions

For beginners, it’s important to pay attention to IDE warnings—these are often generated by Roslyn analyzers and help you learn cleaner, safer C# coding habits.

You can also install custom analyzers or create your own using the Roslyn SDK to enforce your team’s rules.

### Supplement

Roslyn analyzers work during both design time (in the editor) and compile time. They're part of what makes modern C# development environments so intelligent. Popular tools like StyleCop Analyzers, SonarAnalyzer.CSharp, and Microsoft.CodeAnalysis.FxCopAnalyzers are all built on Roslyn.

## 84. ENFORCING NULL SAFETY WITH NULLABLE ANNOTATIONS

Nullable reference types allow you to declare whether a variable can hold a null value, helping prevent runtime null reference errors.

Here's a simple example of using nullable annotations to help the compiler catch potential null reference issues.

[Code Example]

```
```csharp
#nullable enable

class User
{
    public string Name { get; set; } // Non-nullable
    public string? Nickname { get; set; } // Nullable
}

class Program
{
    static void Main()
    {
        var user = new User();
        user.Name = "Alice";
        user.Nickname = null;

        // Accessing without null check causes a warning
        Console.WriteLine(user.Nickname.Length); // △ Possible null reference warning
    }
}
```
```

[Execution Result]

Compiler warning: Dereference of a possibly null reference.

## 85. SELF-CONTAINED VS. FRAMEWORK-DEPENDENT DEPLOYMENT IN C#

C# applications can be deployed either by including everything they need (self-contained) or relying on a pre-installed .NET runtime (framework-dependent).

Here’s how to create both types of deployment using the .NET CLI.

[Code Example]

```
# Framework-dependent deployment
dotnet publish -c Release -r win-x64 --self-contained false

# Self-contained deployment
dotnet publish -c Release -r win-x64 --self-contained true
```

[Execution Result]

Creates a /publish folder with either a lightweight app (framework-dependent) or a complete, standalone app (self-contained).

Self-contained deployment means all the required .NET runtime and libraries are included in the published files. The app can run on a machine without .NET installed.

The downside: the output folder is larger because it includes the runtime.

Framework-dependent deployment assumes the target machine already has the correct .NET runtime installed. The output is smaller, but portability depends on external factors.

In both cases:

- -c Release: compiles in release mode (optimized).
- -r win-x64: specifies the runtime identifier (here for 64-bit Windows).
- --self-contained true/false: switches between the two deployment modes.

Choose self-contained for maximum portability (e.g., distributing apps to users). Choose framework-dependent for controlled environments (e.g., enterprise servers).

[Supplement]

.NET apps use Runtime Identifiers (RIDs) to specify the target OS/platform. Examples include win-x64, linux-x64, and osx-arm64.

To list supported RIDs, see the RuntimeIdentifierGraph.json in the .NET SDK folder or visit the official .NET RID catalog.

## 86. BOOSTING PERFORMANCE WITH AOT COMPILATION

C# now supports ahead-of-time (AOT) compilation to turn code into native machine instructions before runtime, speeding up startup and reducing memory usage.

Let’s use .NET's native AOT publishing to compile a simple app into a native executable.

[Code Example]

```
# First, create a basic console app
dotnet new console -o HelloAOT
cd HelloAOT

# Then publish it using Native AOT
dotnet publish -c Release -r win-x64 /p:PublishAot=true
```

[Execution Result]

Produces a native .exe (or platform-specific binary) in the bin\Release\net8.0\win-x64\publish directory.

AOT (Ahead-of-Time) compilation transforms C# code into platform-specific machine code at build time, rather than at runtime (like traditional JIT compilation).

Benefits:

- Faster startup
- Reduced memory footprint

## 87. LIVE CODE UPDATES WITH HOT RELOAD

Hot Reload allows you to apply code changes instantly while debugging, without stopping and restarting your application.

Here’s a simple example using a console app to demonstrate Hot Reload during runtime.

[Code Example]

// Program.cs
using System;
class Program
{
static void Main(string[] args)
{
// This line will be updated during runtime using Hot Reload
Console.WriteLine("Hello, C#!");
}
}
// After starting the app with debugging and applying a change using Hot Reload:
// Modified during runtime
Console.WriteLine("Hello, world! (Hot Reloaded)");

[Execution Result]

Initially prints:

Hello, C#!

After Hot Reload change, prints:

Hello, world! (Hot Reloaded)
