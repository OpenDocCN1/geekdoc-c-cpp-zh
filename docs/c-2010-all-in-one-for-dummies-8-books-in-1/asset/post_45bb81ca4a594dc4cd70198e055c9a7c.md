The introduction of the School class has at least two advantages:

- It corresponds with reality. A University is a School, but it isn't a HighSchool. Matching reality is nice but conclusive.

- It isolates one class from changes or additions to the other. When my boss inevitably requests later that I introduce the commencement exercise to the University, I can add the Speech() method to the University class and not affect HighSchool.

This process of common properties from similar classes is known as factoring. This feature of object-oriented languages is important for the reasons described earlier in this minibook, plus one: reducing redundancy. Let me repeat: Redundancy is bad.

Factoring is legitimate only if the inheritance corresponds to reality. Factoring a class Mouse and Joystick because they're both hardware powering devices is legitimate. Factoring a class Mouse and Display because they make low-level operating-system calls is not.

Factoring can and usually result in many levels of abstraction. For example, a program written for a more developed school hierarchy may have a class structure like the one shown in Figure 7-4.

You can see that I have inserted a pair of new classes between University and School: HigherLearning and LowerLevel. For example, I have subdivided the new class HigherLearning into College and University. This type of multiplied class hierarchy is common and desirable when factoring out relationships. They correspond to reality, and they can teach you some subtle features of your solution.

# The abstract class: Left with nothing but a concept

As intellectually satisfying as factoring, it introduces a problem of its own. Visit (or revisit) BankAccount, introduced at the beginning of this chapter. Think about how you might go about defining the different member methods defined in BankAccount.

Most BankAccount member methods are no problem to refactor because both accounts implement them in the same way. You should implement those common methods in BankAccount. Withdraw() is different, however. The rules for withdrawing from a savings account differ from with withdrawing from a checking account. You have to implement SavingsAccount.Withdraw() differently from CheckingAccount.Withdraw(). But how are you supposed to implement BankAccount.Withdraw()?

Ask the bank manager for help. I imagine this conversation taking place:

- “What are the rules for making a withdrawal from an account?” you ask, expecting.
- "Which type of account? Savings or checking?" comes the reply.
- "From an account," you say. "Just an account."
- [Blank look.] (You might say a "blank blank look.") Then again, maybe not.)

The problem is that the question doesn't make sense. So "just an account" exists. All accounts (in this example) are either checking accounts or savings accounts. The concept of an account is abstract. It factors out properties common to the two concrete classes. It is incomplete because it lacks the critical property Withdraw(). (After you delve into the details, you may find other properties that a simple account lacks.)

The concept of a BankAccount is abstract.
