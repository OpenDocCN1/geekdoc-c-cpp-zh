# 252 Defining Methods

The program begins by creating a new Student object, student. The program invokes the SetName() method, which stores the strings "Stephen" and "Davis" into the data members firstName and last Name. Finally, the program calls the member method ToString(), which returns the name of the student by concatenating the strings.

Look again at the SetName() method, which updates the first and last name fields in the Student object. To see how SetName() modifies this example:

```
Student christa = new Student();           // Here's one student.
Student sarah = new Student();              // And here's a completely different one.
christa.SetName("Christa", "Smith")
sarah.SetName("Sarah", "Jones");
```

The first call to SetName() updates the first and last name of the christa object. The second call updates the sarah object.

Thus, C# methods that operate on the current object. In the first call, the current object is christa; in the second, it's sarah.

# Expanding a method's full name

A subtle but important problem exists with my description of method names. To see the problem, consider this sample code snippet:

```
public class Person {
    public void Address()
{
        Console.WriteLine("Hi");
    }
}
public class Letter {
    string address;
    // Store the address.
    public void Address(string newAddress)
{
        address = newAddress;
    }
}
```

Any subsequent discussion of the Address() method is now ambiguous. The Address() method within Person has nothing to do with the Address() method in Letter. If my programmer tells me to access the Address() method, which Address() does he mean?

The problem lies not with the methods themselves, but with my description. In fact, no Address() method exists as an independent entity — only a Person.Address() and a Letter.Address() method. Attaching the class name to the beginning of the method name clearly indicates which is intended.
