# 556 Using WPF to Lay Out Your Application

# New tech, new terms

It seems everytime Microsoft introduces a new technology, we have to learn a whole new set of terms. WPF is not different! At the root of the change is what we refer to as Forms and Controls in Windows Forms (WinForms). Here are some of the new terms:

+   - Panels are WPF UIElements used for layout.

+   - A Control in WPF is a UElement that can receive focus and respond to user events.

+   - A Content control in WPF can contain only a single item, which in turn be other UIElements.

+   - The WPF Window class is a specialized Content control.

+   - A Form in Windows Forms is referred to as a Window in WPF.

+   - Anything placed on a WinForms Form is called a control, whereas items placed on a WPF Window are referred to as UIElements.

Instead of depending on screen resolution, WPF measures UI Elements in Device Independent Units (DIUs) that are based on the system DPI. This enables a consistent look between many different hardware configurations.

WPF layout is based on relative values and is adjusted at runtime. When you place controls in a layout container (see the next section), the rendering engine considers the height and width as "suggested" values. Location is defined in relation to other controls or the container. Actual rendering is a two-step process that starts with measuring all controls (and querying them for their preferred dimensions) and arranging them accordingly. If controls could, the conversation might go something like this:

> Layout Engine: "Control, how much space would you like to have?"
<This is the Measure Stage>
Control: "I would like 50 DIUs for height, 100 DIUs for width, and a margin of 3 DIUs in the containing Grid cell."
Layout Engine asks all other controls and layout containers.
Layout Engine: "Sorry, you can have only 40 DIUs for height, but I can grant the rest of your requests.\"
<This is the Arrange Stage>"
