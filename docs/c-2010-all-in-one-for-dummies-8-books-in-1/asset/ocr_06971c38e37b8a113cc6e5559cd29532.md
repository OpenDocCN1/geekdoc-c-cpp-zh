# Why You Should Worry about Access Control 267

```
public class Program {
    public static void Main(string[] args) {
        // Open a bank account.
        Console.WriteLine("Create a bank account object");
        BankAccount ba = new BankAccount();
        ba.BankAccount();
        // Make a deposit.
        double deposit = 123.454;
        Console.WriteLine("Depositing {0:C}", deposit);
        ba.Deposit(deposit);
        // Account balance
        Console.WriteLine("Account = {0}", ba.GetBalance());
        // Here's the problem.
        double fractionalAddition = 0.002;
        Console.WriteLine("Adding {0:C}", fractionalAddition);
        ba.Deposit(fractionalAddition);
        // Resulting balance
        Console.WriteLine("Resulting account = {0}", ba.GetBalance());
        // Wait for user to acknowledge the results.
        Console.WriteLine("Press Enter to terminate...");
        Console.Read();
    n}
```

The Main() method creates a bank account and deposits 123.454, an amount that contains a fractional number of cents. Main() deposits a small fraction of cent to the balance and displays the resulting.

The output from this program appears this way:

```
Create a bank account object
Depositing $123.45
Account = $1001 = $123.45
Adding $0.00
Resulting account = $1001 = $123.45
Press Enter to terminate...
```

Users start to complain: "I can't reconcile my paycheck with my bank statement." Personally, I am happy if I can get to the nearest $100, but some people insist that their accounts match to the penny. Apparently, the program has a bug.

The problem, of course, is that $123.454 shows up as $123.45. To avoid the problem, the bank decides to round deposits and withdrawals to the nearest cent. Deposit $123.454 and the bank takes extra 0.4 cent. On the other side, the bank gives up 0.4 amounts that everything balances out in the long run. Well, in theory, it does.
