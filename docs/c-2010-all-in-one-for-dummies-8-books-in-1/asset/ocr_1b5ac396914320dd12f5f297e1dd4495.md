# Making flexible dependencies through interfaces

There must be a way to implement Move() that does not require you to copy a of worms every time a client wants wriggling instead. You can use interfaces, course!

Look at the following code that uses HAS_A, a now-familiar relationship between two classes in which one contains the other:

```
public class Robot
    // This object is used to implement motion.
    protected Motor _motor = new Motor(); // Refers to Motor by name
    //...
    internal class Motor { ... }
```

The point about this example is that the contained is of type Motor, where Motor is a concrete object. (That is, it represents a real item, not an abstraction.) HAS_A sets up a dependency between classes Robot and Motor: Robot depends on the class Motor. A class with concrete dependencies is tightly coupled to them: When you need to replace Motor with something else, code changes. Instead, insulate your code by relying only on the public interface of dependencies, you can depend on dependent objects in a, less dependent way.

# Abstract or concrete: When to use an interface class and when to use an interface

In Chapter 7 of this minbook, in my little discourse about birds, I say, "Every bird out there is a type of Bird." In other words, a duck is an subclass of Bird. Instead you never see an instance of Bird itself — Bird is an abstraction. Instead, you see concrete, physical ducks, sparrows, or hummingbirds. Abstractions are concrete. As living creatures, ducks are real, concrete objects. And, concrete objects are instances of concrete classes. (A concrete class is a class that you can instantiate. It lacks the abstract keyword, and it implements all methods.)
