# Guidelines for code that handles errors well

You should keep the questions in the previous section in mind as you work. These guidelines may help you:

+   * Protect the user's data at all costs. This is the Top Dog guideline. See for the “More Information” sidebar at the end of this chapter Also see the next bullet item.

+   * Don't crash. Recovery if you can, but be prepared to go down gracefully as possible. Don't let your program squeak out a cryptic, geeky message and blow up. Gracefully means as much helpful information as possible before shutting down. Users hate crashes. You probably know that.

+   * Don't let your program continue running if you can't recover from a problem. The program could be unstable or the user's data in an inconsistent state. When all is most certainly lost, you can display a message and call Environment.FailFast() to terminate the program immediately rather than throw an exception. It's a crash — it's deliberate.

+   * Treat class differently from applications. In class libraries, exceptions reach the caller, who is best equipped to decide how to handle the problem. Don't keep the caller in the dark about problems. But in applications, handle any exceptions you can. Your goal is to keep the code running possible and protect the user's data without putting of inconsequential messages in her face.

+   * Throw exceptions when, for any reason, a method cannot complete its task. The caller needs to know about the problem. (The caller may be a method higher up the stack call in your code or a method in code by using your code). If you check input values before using them and they aren't unexpected null value — fix them and continue if you can. Otherwise, throw an exception.

This advice is contrary to what you may see elsewhere, but it comes from Jeffery Richter, one of the foremost on .NET and C# programming. Often you hear statements as “Exceptions are for unexpected situations — don't use them for problems that are likely to occur in the normal course of operations.” That's not accurate. An exception is the .NET way to deal with most types of errors. You sometimes use an error code or another approach — such as having a collection method for “item not found” — but not often. Deed the previous paragraph.

Try to write code that doesn't need to throw exceptions — and correct bugs when you them — rather rely on exceptions to patch it up. But use exceptions as your main method of reporting and handling errors.
