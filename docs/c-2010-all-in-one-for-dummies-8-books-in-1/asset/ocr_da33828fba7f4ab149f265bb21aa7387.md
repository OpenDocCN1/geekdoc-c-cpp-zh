# 450 Pulling Out of the Stream: Using StreamReader

![](bbox=[0.139, 0.131, 0.215, 0.219])

Recall that the current directory that FileRead uses is the \bin\Debug sub- under your FileRead project (not the \bin\Debug directory under the FileWrite program's directory, which is used FileWrite to create some test files in the preceding section). Before you run FileRead to try it, place any plain text file (.TXT) in FileRead's \bin\ Debug and note its name so you can open it. A copy of the TestFile1.txt file created in the FileWrite example would be good.

In FileRead, the user reads and only one file. The user must enter a valid filename for the program to output. No second changes. After the program has it, if the user wants to peek into a second file, she'll have to run the program again. That's a design choice you might make different.

The program starts out all of its code wrapped in an exception handler. In this block, handler tries to call two methods, first to get a StreamReader for the file and then read the file and dump its lines to the console. In the event of an exception, the catch block writes the exception message. Finally, when the exception occurred or not, the finally block makes sure the stream and its files are closed and the variable sr is nulled so the garbage collector can reclaim it (see Book I). I/O exceptions could occur in either method called by this block. This select converts up to Main() looking for a handler. (No need for exception handlers the methods.)

Note the //TODO: comment comes in the catch block. This is a reminder to make the message more user-friendly before releasing the program. Comments marked this way appear in the Visual Studio Task List. In window, select from the drop-down list at the upper left. Double-click an item to open the editor to make that comment in the code.

Because the variable sr is used inside an exception block, you have to set it to null initially—otherwise, the compiler complains about using an initialized variable in the exception block. Likewise, check whether sr is already (or still) null before trying to call its Close() method. Better still, convert the program to use using.

With the GetColorF method, the program gives the user one chance to enter a filename. If the name of the file entered at the console is nothing but a blank, the program throws its error message: You need to enter a filename. If the filename isn't empty, it's used to open a FileStream object in read mode. The File.Open() call here is the same as the one used in FileWrite:

+   * The first argument is the name of the file.

+   * The second argument is the file mode. The FileMode.Open says, "Open the file if it exists, and throw an exception if it doesn't." The other option is OpenNew, which creates a zero-length file if the file doesn't exist. Personally, never saw the need for that mode (who wants to read from an empty file?), but each to his own what I say.
