## 为什么要分类？

你为什么要分类？这听起来很麻烦。而且，人们使用过程化方法已经很久了——现在改变呢？

专门为这个问题设计和建造一台微波炉可能似乎比建造一个独立的、更通用的烤箱要容易。假设你想建造一个只用来烤墨西哥玉米片（nachos）的微波炉。除了一个“开始”键外，你不需要在它上安装前面板。你可能总是以相同的时间烹饪墨西哥玉米片。你可以在选项中省“解冻”和“温度烹饪”之类的废话。烤箱只需要容纳一个平坦的小盘子。三立方英尺的空间将浪费在墨西哥玉米片上。

就至于这一点，你可以省去“微波炉”这个整体。你只需要烤箱的内部。然后，在配方中，你放入让它运行的指令：“将墨西哥玉米片放入盒子里。将红线连接到黑线。将磁控管调节到约 3000 伏。听到轻微的嗡嗡声。如果你打算生孩子，尽量不要靠太近。”此类操作。

过程化方法有这些问题：

- **它太复杂了。** 你不需要制作墨西哥玉米片的细节。如果你无法定义对象并将它们从细节的泥潭中提取出来单独处理，你就必须同时处理问题的所有复杂性。

- **它缺乏灵活性。** 某一天，你可能需要将微波炉更换为另一种类型的烤箱。只要两个烤箱具有相同的接口，你就可以这样做。如果没有清晰的界定和独立开发，一个对象类型就无法干净地移除并替换为另一个。

- **它不可复用。** 烤箱被用来制作许多不同的菜。你不想每遇到一个新配方时就创建一个新烤箱。解决了一个问题后，你希望能够在我的程序其他地方复用它。如果你运气好，你可能在未来的来的程序中也可以复用它。

## 面对象概念 #3：可用的接口

对象必须能够投影出一个足够且尽可能简单的外部接口。这个概念在某种程度上是概念 #4 的反面（在下一节中将描述）。如果设备接口不足，用户可能会开始拆掉设备的顶盖，这直接违反了上帝和社会的法律——或者至少是德克萨斯州伟大州的法律责任法。相信我，你可不想违反德克萨斯州伟大州的法律。反过来，如果设备接口太复杂，没有人会买这台设备，或者没有人会使用它的所有功能。

人们不断抱怨他们的 DVD 播放器太复杂，尽管在今天的屏幕控制下，这个问题并不那么严重。这些设备有太多的按钮，具有许多不同的功能，取决于机器的状态。此外，似乎没有两个 DVD 播放器具有相同的接口。出于什么原因，DVD 播放器投影出的接口对于大多数人来说太困难且非标准，无法使用最基本的功能之外。

对比视频录像机（VCR）和汽车。很难说汽车比视频录像机不复杂。然而，人们开车时并没有遇到太大困难。

所有的汽车都在或相同的地方提供或或少的相同的控制。例如，我姐姐曾经有一辆车（需要我说是一辆法国车吗？），那辆车的大灯控制在方向盘的左侧，那里通常是转向灯手柄的位置。你向下按灯杆来关灯，抬起灯杆来开灯。这种差异可能看起来微不足道，但在那辆车上，我从没有在不关灯的情况下在晚上左转。

设计良好的汽车不会根据汽车的状态使用同一个控制来执行一个以上的操作。我想起这个规则有一个例外：巡航控制上的某些按钮承载了多个功能。

## 面对象概念 #4：访问控制

微波炉的建造方式必须确保，无论你在前面板键盘上输入什么样的按键组合，都不会导致微波炉伤害你。当然，某些组合什么都不会发生。然而，没有任何一组按键序列会de

- **损坏设备：** 你可能让设备进入一种奇怪的状态，在这种状态下，直到你重置它之前它什么都不做（例如，通过跳开内部断路器）。但是，你不应该能够通过前面板损坏设备。

- **导致设备起火：** 你可能让设备进入一种奇怪的状态，直到你重置它之前它什么都不做（例如，通过跳开内部断路器）。但是，你不应该能够通过前面板导致设备起火并烧毁房屋。然而，为了执行这些规则，你可能需要承担责任。几乎所有设备包括微波炉，都有一个密封来防止消费者进入内部。类必须能够对其数据的访问。任何类成员的调用都不应导致你的程序崩溃。类无法确保这种访问，如果外部元素访问了类的内部状态。类必须能够保持关键数据对外部不可。

## C# 如何支持面向对象概念

那么，C# 实现面向对象编程吗？在某种意义上，这是一个错误的问题。C# 是一个面向对象的语言；然而，它并不实现面向对象编程——程序员才实现。你可以在 C# 或任何其他语言中编写非面向对象的程序（例如，将整个 Microsoft Word 写在 Main() 中），这让我想起了“你可以引马饮水”。但你可以很容易地在 C# 中编写面向对象的程序。

这些 C# 特性对于编写面向对象的程序是必要的：

- **访问控制：** C# 控制访问类成员的方式。C# 关键字允许你将某些成员声明为公共，而内部成员受保护，某些秘密则保持私有。注意这些小提示。访问控制在本书的第 5 节中揭示。

- **特异化：** C# 通过继承机制支持特异化。一个类继承另一个类的成员。例如，你可以创建一个 Car 类作为 Vehicle 的一种特定类型。C# 擅长特异化。

- **多态：** 这一功能允许一个执行它想要的操作。Rocket 类型的 Vehicle 实现 Start 操作的方式与 Car 类型的 Vehicle 不同得多。至少，我希望每当我转动车钥匙时都是这样。（对于我的车，你可能不知道）但所有 Vehicle 都有 Start 操作，你可以依靠这一点。本书的第 7 章找到了它描述多态自己的方式。

- **间接性：** 对象经常使用其他对象的服务——通过调用它们的公共方法。但类可能对它们使用的类“知道过多”。这两个类之间被认为“过度耦合”，这使得使用类对被使用类过度依赖。这种设计太脆弱——如果你进行更改，就会损坏。但变化在软件中是不可避免的，所以你应该寻找更间接的方式来连接这两个类。这就是 C# 接口大显身手的地方（你可以在本书的第 8 章获取有关接口的内幕。）
