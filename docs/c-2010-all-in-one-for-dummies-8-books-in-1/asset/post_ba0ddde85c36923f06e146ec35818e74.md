
## Why "SUT"?

The variable name stands for "System Under Test" and is a common convention in unit testing. It clearly delineates what is being tested from other objects that are required for the test.. Why don't the earlier examples use this? Ah, grasshopper — gradual introduction is in play so you aren't drinking from a fire hose.

The second test is much more involved, because it tests the raising of the PropertyChanged event. We have to create a subscriber to listen for this event. Windows (and the WPF rendering engine) automatically attach to this event, and we don't want to re-create the rendering engine just to test one method. To test the event, create a subscriber, raise the event, and then assert that the handler of the event was executed.

Tests of this type are typically done with a mocking framework, such as Mocks (the tool used in the samples). Mocking frameworks allow tests for behavior in addition to state, and since the test need to validate that an event was raised, RhinoMocks is the perfect fit. A deep dive into mocking and behavior testing is beyond the scope of this book. Look at the code, digest, and tinker with it. It's a great way to expand your testing knowledge!

Mocking frameworks create proxy objects based on interfaces. For the single event, create an interface (shown in Listing 4-16) that has the required signature for the handler — in this case, the PropertyChanged event.

### Listing 4-16: The Event Subscriber

```csharp
public interface IPropertyChangedSubscriber
{
    void Handler(object sender, PropertyChangedEventArgs e);
}
```

The test starts off by creating a mock of the subscriber and registering the PropertyChanged event with the handler. The test acts on the Customer object by changing the name and asserts that the handler was called. The Arg<object>.Is.Any syntax tells Mocks not to test the arguments for equality. Again, the test is just verifying that the event is raised when a property on the Customer object is updated. See the code in Listing 4-17.

### Listing 4-17: Testing an Event Was Raised

```csharp
[Test]
public void ShouldRaise_Property_Changed_Event_On_Property_Change()
{
    var sut = new Customer();
    var eventArgs = new PropertyChangedEventArgs(string.Empty);
    var subscriber = MockRepository.GenerateMock<IPropertyChangedSubscriber>();
    sut.PropertyChanged += subscriber.Handler;
    sut.Name = "New Name";
    subscriber.AssertWasCalled(x => x.Handler(Arg<PropertyChangedEventArgs>.Is.Anything()));
}
```

## Model repositories

The repository pattern is commonly used for Life of Business applications to move data between the data store and the model classes. For the sample ViewModel, I've included a very simple interface (shown in Listing 4-18) that has a GetAll and an Update method (not remotely a complete repository, but all that we need for the examples). Note the use of generics to enforce strict typing in the repositories that implement this interface.

### Listing 4-18: The Repository Interface

```csharp
public interface IRepository<T>
{
    IList<T> GetAll();
    bool Update(T model);
}
```

The repositories in the sample return hard-coded values instead of connecting to a data store. It's a common practice to create classes that are used only for testing or prototyping. The convention I prefer is to call out by appending Fake to the name (as shown in Listing 4-19) so other developers have no doubt about their intended purpose. Additionally, the examples er implement the Update methods because they aren't used for the ViewModel samples shown.

## The Add Customer command

Interestingly, using the ViewModel pattern, the commands can be developed prior to the view, enabling Test Driven Development for the commands. Using the same approach discussed in the "Commanding" section earlier in this chapter, a CommandBase class (shown in Listing 4-21) is extracted to handle the common properties and CanExecuteChanged event.

### Listing 4-21: CommandBase Class

```csharp
public abstract class CommandBase : ICommand
{
    public string Text { get; internal set; }
    public abstract void Execute(object parameter);
    public abstract bool CanExecute(object parameter);
    public event EventHandler CanExecuteChanged
    {
        add { CommandManager.RequerySuggested += value; }
        remove { CommandManager.RequerySuggested -= value; }
    }
}
```

The AddCustomerCommand (shown in Listing 4-22) will take the Customer list as a parameter and add another customer to the list. In this example, it's a hard-coded set of values, but in reality you would have another Window (or some data entry mechanism) to gather the required information.

## Defensive programming or try-catch?

Is it better to code extra lines to prevent exceptions, or just wrap the code in a try-catch block? Exceptions are expensive and generally should not be flow-of-control devices. Just like their name, exceptions should be well, exceptional. It is better to code defensensively and wrap your code in try-catch blocks to handle pesky conditions users have such a knack for finding.

Why don't these samples have try-catch blocks? Merely for brevity. Logging and error handling are must in real code, but take a significant amount of space and could send the reader a rabbit hole that would detract from the current section.

The CanExecute event handler checks that the parameter is IList<Customer>. There is an additional check in the Execute method. It is essentially redundant — the code should not execute if the parameter is not an IList<Customer>. However, defensive programming kicks in, and I always check to avoid the possibility of throwing an error.

### Listing 4-22: AddCustomerCommand

```csharp
public class AddCustomerCommand : CommandBase
{
    public AddCustomerCommand() {
        Text = "Add Customer";
    }
    public override void Execute(object parameter) {
        var list = parameter as IList<Customer>;
        if (list == null) {
            return;
        }
        list.Add(new Customer { ID = 4, Name = "New Customer" });
    }
    public override bool CanExecute(object parameter) {
        return parameter is IList<Customer>;
    }
}
```
