# Tradition!

To fully understand how the ViewModel pattern helps, you need to under-stand the parts of a “traditional” application architecture.

# Data Access Layer (DAL)

The DAL is the set of classes and methods that get the data out of the data store (such as SQL Server) and populate the Model (see next item). It is also responsible for persisting any changes to the data back to the data store.

# Model

The Model is the data that composes your application — not the store (for example, the database), but the object graph that represents the data for your application. In a sales application, example objects could be classes like Customer, SalesRegion, and SalesPerson.

# Business Layer (BL)

The BL is the implementation of the business rules for the application. The layer ensures the data in the Model adheres to the law of the land.

# View

The View represents the pieces of the application that interact with the user. For WPF, this is the collection of Windows that compose the application.

The biggest gap with displaying an object graph (Model) in a View is that applications seldom display only one type of object at a time. The Window allows for editing a customer, then it probably needs to display the sales regions, and so forth.

Combining multiple objects into a data object clouds the Model, and placing all code into the view places too much knowledge in the View — not to mention a testability failure. The compilation of the required parts of the object graph should not detract from any other part of the application.

The Command Objects are another consideration. There isn't a tidy place in the traditional application layers to place the custom commands. The code contained in the commands is (typically) Business Logic, but the View needs to bind to the commands, and is therefore specific to the View.
