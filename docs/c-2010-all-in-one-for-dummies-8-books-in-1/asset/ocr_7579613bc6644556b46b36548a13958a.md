# Asynchronous I/O: Is it worth waiting for?

Normally, a program waits for a I/O request to complete before continuing. Call a read() method, and you generally do not control back until the file data is safe in the boat. This is known as synchronous I/O. Type of synchronous meaning "you will wait."
The C# System also supports asynchronous I/O. The read() call returns immediately to the program to continue doing something while the I/O request is completed in the background. The program can check a "done" flag to decide when the I/O has completed.
This is sort like cooking hamburgers. Using synchronous I/O, you put the meat in the pan on|the stovetop and wait until the meat has completely cooked before you go off and start cooking the onions that are on the burgers.|Using asynchronous I/O, you can start up the onions while the hamburger patty is cooking. Every in a while, you peek over to see whether the meat is done. When it is, you stop cooking, take the meat off the grill, and slip it on the buns.
asynchronous I/O can substantially improve performance of the program, but it adds another level of complexity. I don't discuss this further in this minibook.
