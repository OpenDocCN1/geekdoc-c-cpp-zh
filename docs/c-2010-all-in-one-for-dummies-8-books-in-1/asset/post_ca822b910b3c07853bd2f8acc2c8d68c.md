## Introduction

Web Forms applications are loosely coupled programs that expose the server to potential attacks. By loosely coupled, I mean they have a transact-and-wait relationship with the server. Because of this coupling, building security becomes more important than ever. When building Web-based applications, spend less time worrying about authentication (especially if your application is made publicly available) and more time worrying about crackers. Because you are making the server available to the public, your programs are subject to a whole new set of security rules.

## Introduction

The key to protecting a public server is to be honest with yourself about the weaknesses of the system. Don't think, "Well, a cracker could figure it out by doing XYZ, no one would ever do that." The two main types of attacks to be concerned about for Web applications are SQL Injection and script exploits.

## SQL Injection

A SQL Injection attack happens when a hacker enters a line of SQL code into an input field on a Web page (such as the username and password text boxes in a login form). Malicious SQL causes the database to act in an unexpected way or to allow the hacker to gain access to, alter, or damage the database.

## Understanding SQL Injection

The best way to understand how a hacker uses SQL Injection is to see an example. For instance, a Web page has code that accepts a Product ID from the user in text and returns details. The code on the server would look like this:

```csharp
// get ProductID from user
string ProductID = TextBox.Text;
// get information from the database
string selectString = "SELECT * FROM Items WHERE ProductID = '" + ProductID + "';";
SqlCommand cmd = new SqlCommand(selectString, conn);
conn.Open();
SqlDataReader myReader = cmd.ExecuteReader();
// Process results
myReader.Close();
conn.Close();
```

Normally, a user enters the appropriate information into the text box. But a cracker attempting a SQL Injection attack would enter the following string:

```text
FOOBAR'; DELETE FROM Items; --
```

The SQL code that would be run by your code would look like this:

```sql
SELECT * FROM Items WHERE ProductID = 'FOOBAR'; DELETE FROM Items;
```

The SQL Server executes some code you didn't expect; in this case, the code deleted everything in the Items table.

## Preventing SQL Injection

The easiest to prevent SQL Injection is to never use string concatenation to generate SQL. Use stored procedures and SQL parameters. You can read more about that in Chapter 2 of this minibook.

## Script exploits

A script exploit is a security flaw that takes advantage of the JavaScript engine in a user's Web browser. Script exploits take advantage of one of the more common features of public Web Forms applications — enabling interaction among users. For instance, a Web Forms application may enable a user to post a comment that other users of the site can view, or it may allow a user to fill out an online profile.

## Understanding script exploits

If a malicious user were to put some script code in his profile or comment, a hacker could take over the browser of the next user who comes to the site. Some outcomes are possible, and none of them are good.

For instance, the cookies collection is available to JavaScript when a user comes to your site. A malicious user would put some script code in his profile that could copy the cookie for your site to a remote server. This could give the malicious user access to the current user's session because the session identifier is stored as a cookie. The malicious user would then be able to spoof the user's identity.

## Preventing script exploits

Fortunately, ASP.NET prevents users from typing most script code into a form field and posting it to the server. Try it with a basic Web Forms following these steps (you see the error shown in Figure 1-3):

1. Create a new Web Forms project.
2. Add a text box and a button to the default page.
3. Run the script.
4. Type `<script>selectbox()</script>` into the text box.
5. Click the button.

## Best practices for securing Web applications

Aside from making sure that your Web application will prevent SQL Injection and script exploits, you should keep in mind some good practices for securing your applications.

The following list contains some of the most important practices for securing your applications:

- Keep your IIS up to date.
- Back up everything.
- Avoid using Querystring variables.
- Don't leave HTML comments in place. Any user can view the HTML code by viewing Source in a browser.
- Don't depend on client-side validation for security — it can be bypassed.
- Use strong passwords.
- Don't assume the user you came from your form is safe.
- Make sure that error messages don't give the user any information about your application. E-mail yourself the error messages instead of displaying them to the user.

## Using System.Security

* Use Secure Socket Layer.
* Don't store anything useful in a cookie.
* Close all unused ports on your Web server.
* Turn off SMTP over IIS unless you need it.
* Run a virus checker if you allow uploads.
* Don't run your application as Administrator.
* Use temporary cookies, if possible, by setting the expiration date to a past date. The cookie will stay alive only for the length of the session.
* Put a size limit on file uploads. You can do it in the Web.config file:

```xml
<configuration>
  <system.web>
    <httpRuntime maxLength="4096" />
  </system.web>
</configuration>
```

* Remember that the ViewState of Web Forms is easily visible.
