The image in Figure 4-6 contains two combo boxes that need to be populated. One of the tenants of the ViewModel pattern is to provide a one-stop shop for any view. In addition to the main data (Customers), this includes any reference data (Sales Regions). ## Dependency Injection (DI)
The ViewModel in this example depends on getting customer and sales region data. But hard-coding the few repositories is not a good idea in the wild. More than once I have a release of software with a test value still in the code!"I'll change back before release" tends to be forgotten in the release two-step.

Dependency Injection is a technique that injects required dependencies into the class that needs them. They help prevent just such a scenario. A common tool for DI with WPF is Unity, but other high-quality open source tools exist, such as Ninject. Well beyond the scope of this book, DI is an extremely valuable pattern in software development.

## 626 Get Your ViewModel On
The Content hasn't changed from the earlier examples, but the Command and CommandParameter assignments have. The DataContext for all controls roll up the element tree looking for the first DataContext. Because the only DataContext is set at the Window level (the constructor), all elements have their DataContext the ViewModel. So binding is reduced to setting the Path to the property of the ViewModel (in this case, the AddCustomerCmd for the Command, and the Customers property for the Command Parameter).

Likewise, ComboBoxes bind their ItemsSource property to the IList<T> properties in the ViewModel. 4-27 shows the XAML for the ComboBoxes on the Window.

```xml
<ComboBox ItemsSource="Binding Path=Customers"
    DisplayMemberPath="Name" />
<ComboBox ItemsSource="Binding Path=Regions"
    SelectedItem="Binding ElementName=CustomerList, Path=SelectedItem.SalesRegion" />
```

The second ComboBox shows the power of WPF data binding. The SelectedItem should be set to the value of the SalesRegion property for the Customer. To do this binding, the item is set to the SelectedItem of the CustomerList. This returns a Customer object, allowing any property on that Customer to be selected in the Path (in this case, the SalesRegion property).

## Wrap up
I asked recently if using the ViewModel pattern is worth since it "seems like a lot of extra work." This is a common theme among WPF developers, and it's not surprising considering the newest of the pattern, all the current variations in the wild, and conflicting opinions on it.

In short, it is absolutely worth it. The biggest benefit the ViewModel brings to the table is true separation of concerns with a size of testability. Any time you reduce the dependence on manual user testing and increase automatic test coverage, it's a win. Increased code isolation, improved capabilities for code reuse, and reduced complexities all come with the package. And there isn't "more" code developed — it's just moved behind files for the Windows.
