
# Inheriting an Interface

A C# interface can "inherit" the methods of another interface. I use quotes around the word inherit because it's not true inheritance, no matter how it may appear. The following interface code shows a base interface, much like a base class, in its heading:

```csharp
interface IRobozillaSafe : IPet // Base interface
    // Methods not shown here ...
}
```

By having IRobozillaSafe "inherit" IPet, you can let this subset of Robiscilla implement its own "petness" without trying to impose petness inappropriately on all of Robiscilla:

```csharp
class PetRobo : IRobozillaSafe // (also an IPet by inheritance)
    Implement Robo operations.
    Implement IRobozillaSafe operations, then ...
    Implement IPet operations (required by the IPet interface).
```

```csharp
// Hand out a safe reference, not one to PetRobo itself.
IPet myPetRobo = (IPet)new PetRobo();
// ... now call IPet methods on the object.
```

The IRobozillaSafe inherits from IPet. Classes that implement IRobozillaSafe must therefore implement IPet to make their implementation of IRobozillaSafe complete.

This type of inheritance isn't the same concept as class inheritance. For instance, class PetRobo in the previous example, can have a constructor, but no equivalent of a base-class constructor exists for IRobozillaSafe or IPet. Interfaces don't have constructors. More important, polymorphism doesn't work the same way with interfaces. You can then call a method of a subclass through a reference to the base class (class polymorphism), the parallel operation involving interfaces (interface polymorphism) doesn't work: You cannot call a method of the derived interface (IRobozillaSafe) through a base reference (IPet).

Although inheritance isn't polymorphic in the same way that class inheritance is, you can pass an object of a derived interface type (IRobozillaSafe) through a parameter of its base interface type (IPet). Therefore, you can put IRobozillaSafe into a collection of IPet objects. The PassInterface example on this book's Web site demonstrates the ideas in this section.

# Using Interfaces to Manage Change in Object-Oriented Programs

Interfaces are the key to object-oriented programs that bend flexibly with the winds of change. Code will laugh in the face of new requirements.

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_377_0.png)

You have no doubt he said, "Change is a constant." When you need a new program to a bunch of users, they soon request changes. This feature, please. Fix that problem, please. RoboWarrior has feature X, so why doesn't Robozilla? Many programs have a long shelf life — thousands of programs, especially old Fortran and Cobol programs, have been in service for 20 or 30 years or longer. They undergo little of maintenance in extended time span, *which makes planning and designing for change one of your priorities.*

Here's an example: in the Robot class hierarchy, suppose that all robots move in one way or another. *Robocats slither* — at least when operated by a power (hungry) user. *Robosnakes slither*. One way to implement these different modes of travel inheritance: Give the base class, Robot, an abstract *Move()* method. Each subclass overrides the *Move()* method to implement it differently:

```csharp
public class Robot {
    abstract void Move(int direction, int speed);
    // ...
}
public class Rosnake : Robot {
    public override void Move(int direction, int speed) {
        // A real Move() implementation here: slithering,
        // some real code that computes angles and changes
        // snake's location relative to a coordinate system...
    }
}
```

But suppose that you often receive requests to add new types of movement to existing subclasses. "Please make Robosnake undulate rather than slither." (Don't ask me what the difference is.) You now have to open Robosnake class and modify its Move() method directly.

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_377_1.png)

After the Move() method is working correctly, most programmers would prefer not to meddle with it. Implementing slithering is difficult, and changing the implementation can introduce brand-new bugs. If it isn't broke, don't fix it.

# Making flexible dependencies through interfaces

There must be a way to implement Move() that does not require you to copy it every time a client wants to wiggle instead. You can use interfaces!

Look at the following code that uses HAS-A, a relationship between two classes in which one contains the other:

```csharp
public class Robot {
    // This object is used to implement motion.
    protected Motor _motor = new Motor(); // Refers to Motor by name
}
internal class Motor { ... }
```

The point about this example is that the contained is of type Motor, where Motor is a concrete object (That is, it represents a real item, not an abstraction). HAS-A sets up a dependency between Robot and Motor: Robot depends on Motor. A class with concrete dependencies is tightly coupled to them: When you need to replace Motor with something else, code changes. Instead, insulate your code by relying only on the public interface of dependencies, you can depend on dependent objects in a less-dependent way.

Depend on abstractions, not on concrete classes. I show how you.

# Abstract or concrete: When to use an interface and when to use a class

In Chapter 7 of this book, in my little discourse about birds, I say, "Every bird out there is a type of Bird." In other words, every duck is a subclass of Bird. You never see an instance of Bird itself — Bird is an abstraction. Instead you see concrete, physical ducks, sparrows, or hummingbirds. Abstractions are not concrete. As living creatures, ducks are real objects. And concrete objects are instances of classes. (A concrete class is a class that you can instantiate. ![](img/36596fb11aa4233d5cab0d6ddd1d82e8_379_0.png)

You can represent abstractions in two ways in C#: with abstract classes or with C# interfaces. The two differences that can affect your choice of which one to use:

- **Use an abstract class** when you can share an implementation with subclasses — the abstract base class can contribute code that its subclasses can use by inheritance. For instance, maybe class Robot can handle part of the robot's tasks, just not movement. An abstract class doesn't have to be completely abstract. Though it has to have at least one unimplemented method or property, some can provide implementations (bodies). Using an abstract class to provide an implementation for its subclasses to inherit prevents code duplication. That's always a good thing.

- **Use an interface** when you can't share an implementation or your implementing class already has a base class. C# interfaces are purely, totally abstract. A C# interface supplies no implementation of any of its methods. Yet it can also add flexibility that isn't otherwise possible. The abstract class option may not be available because you want to add a capability to a class that already has a base (that you can't modify). For example class Robot may already have a base class in a library that you didn't write and therefore cannot alter. Interfaces are especially helpful for representing completely abstract capabilities, such as movability or displayability, that you want to add to multiple classes that may otherwise have nothing in common — for example, being in the same class hierarchy.
