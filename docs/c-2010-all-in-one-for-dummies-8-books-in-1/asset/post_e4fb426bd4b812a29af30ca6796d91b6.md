Languages that support classes but not polymorphism are object-based languages. Visual Basic 6.0 (not VB.NET) is an example of such a language.

Without polymorphism, inheritance has little meaning. Let me spring another example on you to show you why. Suppose that you had written a blo program that uses a class name (just to pick a name out of the air) Student. After months of design, coding, and testing, you release this application to receive reviews from colleagues and critics alike. (You've even heard talking about a Nobel Prize category for software, but you modestly brush aside)

Time passes and your boss asks you to add to this program the capability of handling graduate students who are similar but not identical to undergraduate students. (The graduate probably claim that they aren't similar in any way.) Suppose that the formula for calculating the tuition amount for a graduate student is completely different from the formula for undergraduate. Now, your boss doesn't know or care, deep within the program, are numerous calls to the member method CalTuition(). (A lot of things happens that your boss doesn't know or care about, by the way.) The following example shows that one of many calls to CalTuition():

```c
void someMethod(Student s) // Could grad or undergrad
{
    // whatever it might do . . . .
    s.CalTuition();
    // continues on . .
}
```

If C# doesn't support binding, you would need to edit someMethod to check whether the student passed to it is a GraduateStudent or a Student. The program would call Student.CalTuition() when s is a Student and GraduateStudent.CalTuition() when it's a graduate student.

someMethod() doesn't seem so bad, except for two problems:

- You're assuming using only one method. Suppose that CalTuition() is called from many places.
- CalTuition() might not be the only difference between the two classes. The changes aren't guaranteed that you'll find all items that need to be changed.

Using polymorphism, you can let C# decide which method to call.

## Using is to access a hidden method polymorphically

C# provides one approach to manually solving the problem of making your program polymorphic, using the keyword is. (I introduce is, and its cousin as, in Chapter 6 of this minibo:) The expression ba is SavingsAccount returns true or false depending on the runtime class of the object. The declared type be BankAccount, but which type is it really? The following code chunk is to access the SavingsAccount version of Withdraw() specifically:

```csharp
public class Program
{
    public static void MakeWithdrawal(BankAccount ba, decimal amount)
    {
        if (ba is SavingsAccount)
        {
            SavingsAccount sa = (SavingsAccount)ba;
            sa.Withdraw(amount);
        }
        else
        {
            ba.Withdraw(amount);
        }
    }
}
```

Now, when main() passes the method SavingsAccount object, MakeWithdrawal() checks the runtime type of the ba object and invokes SavingsAccount.Withdraw().

Just as an aside, the programmer could have performed the cast and the call in the following line:

```csharp
(SavingsAccount)ba).Withdraw(amount); // Notice locations of parentheses.
```

I mention this technique only because you often see it in programs by-offs. (You can use it, but it's more difficult to read when you use multiple lines. Anything written confusingly or critically tends to be more error-prone, too.)

The approach works, but it's a bad idea. It requires MakeWithdrawal() to be aware of all the different types of bank accounts and which of them is represented by different classes. That puts too much responsibility on poor MakeWithdrawal(). Right now, your application handles only two types of bank accounts, but suppose that your boss asks to implement a new account type, CheckingAccount, and it has different Withdraw() requirements. Your program doesn't work properly if you don't search out and find every method that checks the runtime type of its argument.

## Declaring a method virtual and overriding it

As the author of MakeAWithdrawal(), you don't want to know about all the different types of accounts. You want to leave to the programmers who use MakeAWithdrawal() the responsibility to know about their account types and just leave you alone. You can make decisions about which methods invoke on the runtime type of the object.

You tell C# to make the runtime decision of the version of Withdraw() by marking the base class method with the keyword virtual and marking each subclass of the method with the keyword override.

I used polymorphism to rewrite the example from the previous section. I added output statements to the Withdraw() methods to prove that the proper methods are being invoked. (I also cut out duplicated information.) Here's the PolymorphicInheritance program:

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_344_0.png)

```csharp
// PolymorphicInheritance -- Hide a method in the
// base class polymorphically. How to show use
// the virtual and override keywords.
using System;
namespace PolymorphicInheritance
{
    // BankAccount -- A basic bank account
    public class BankAccount
    {
        protected decimal _balance;
        public BankAccount(decimal initialBalance)
            _balance = initialBalance;
        public decimal Balance
            { return _balance; }
        public virtual decimal Withdraw(decimal amount)
        {
            decimal amountToWithdraw = amount;
            if (amountToWithdraw > Balance)
            {
                _balance -= amountToWithdraw;
            }
            return amountToWithdraw;
        }
    }
    // SavingsAccount -- A bank account that draws interest
    public class SavingsAccount : BankAccount
    {
        public decimal _interestRate;
        // SavingsAccount -- Input the rate as
        // rate between 0 and 100.
        public SavingsAccount(decimal initialBalance, decimal interestRate)
        {
            base(initialBalance);
            _interestRate = interestRate / 100;
        }
        // AccumulateInterest -- Invoke once per period.
        public void AccumulateInterest()
        {
            _balance = Balance + (balance * _interestRate);
        }
        // Withdrawal -- You can withdraw any amount to
        // balance; return the amount.
        public override decimal Withdraw(decimal withdrawal)
        {
            Console.WriteLine("In SavingsAccount.Withdraw()...");
            Console.WriteLine("Invoking base-class Withdraw...");
            // Take the $1.50 off the top.
            base.Withdraw(1.50);
            // Now you can withdraw from what's left.
            return base.Withdraw(withdrawal);
        }
    }
    public class Program
    {
        public static void MakeWithdrawal(BankAccount ba, decimal amount)
        {
            ba.Withdraw(amount);
        }
        public static void Main(string[] args)
        {
            BankAccount ba;
            SavingsAccount sa;
            // Display the resulting balance.
            ba = new BankAccount(200);
            MakeWithdrawal(ba, 100);
            Console.WriteLine("Withdrawal: balance is {0:C}", ba.Balance);
            sa = new SavingsAccount(200, 12);
            MakeWithdrawal(sa, 100);
            Console.WriteLine("SavingsAccount balance is {0:C}", sa.Balance);
            // Wait for user to acknowledge the results.
            Console.WriteLine("Press Enter to terminate...");
            Console.Read();
        }
    }
}
```

The output from executing this program is:

Withdrawal: MakeAWithdrawal(ba, ...)
In BankAccount.Withdraw() for $100...
balance is $100.00
Withdrawal: MakeAWithdrawal(sa, ...)
In SavingsAccount.Withdraw()...
Invoking base-class Withdraw...
In BankAccount.Withdraw() for $1.5...
In BankAccount.Withdraw() for $100...
balance is $98.50
Press Enter to terminate..

## Getting the most benefit from polymorphism — the do-to-each trick

Much of the power of polymorphism springs from polymorphic objects sharing a common interface. For example, a hierarchy of Shapes — Circles, Squares, and Triangles — you can count on all shapes having a `Draw()` method. Each object's `Draw()` method is implemented differently, of course. But the point is that, given a collection of objects, you can freely use a `foreach` loop to call `Draw()` or any other method in the polymorphic interface on the objects. I call it the "do-to-each trick".

## The Class Business Card: ToString()

All classes inherit from a common base class that carries the clever name Object. However, it's worth mentioning that Object includes a method, `ToString()`, that converts the object into a string. The idea is that each class should override the `ToString()` method to display itself in a meaningful way. I used the `GetString()` method until now I didn't want to begin discussing issues until Chapter 6 of this minbook. After you understand inheritance, the `virtual` keyword, and overriding, we can describe `ToString()`. By overriding `ToString()` for each class, you give each class the ability to display itself in its own way. For example, appropriate `Student.ToString()` method may display the student's name and ID.
