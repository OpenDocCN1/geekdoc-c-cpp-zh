# Dependency Injection (DI)

The ViewModel in this example depends on getting customer and sales region data. But hard-coding the few repositories is not a good idea in the wild. More than once I have a release of software with a test value still in the code!"I'll change back before release" tends to be forgotten in the release two-step.

Dependency Injection is a technique that injects required dependencies into the class that needs them. They help prevent just such a scenario. A common tool for DI with WPF is Unity, but other high-quality open source tools exist, such as Ninject. Well beyond the scope of this book, DI is an extremely valuable pattern in software development.

Practical WPF

+   Listing 4-25: The View Code-Behind

```
public class CustomerMaintenance : Window
{
    public CustomerMaintenance()
    {
        InitializeComponent();
        DataContext = new CustomerMaintenanceViewModel();
    }
}
```

Wait! Didn't we want to remove all from the code-behind? No, not all. Almost handlers dealt with business logic. But you have to two lines in the constructor: InitializeComponent(), which renders all the XAML, and the DataContext assignment. You might have cases for additional coding in the code-behind, and those cases might be perfectly valid. Just use critical thought before you adding code in places where it can't be tested or reused.

The Command Binding expressions become very different using the ViewModel pattern. They actually become a bit easier as shown in Listing 4-26. Since the base class holds the Command into the SqlCommand, the need for the Windows.CommandBindings is eliminated.

+   Listing 4-26: The Add Customer XAML

```
<Button HorizontalAlignment="Right" Margin="3,0,3,0"
Command="Binding Path=AddCustomerCmd)"
CommandParameter="Binding Path=Customers)"
Content="Binding RelativeSource=(RelativeSource
Mode=Self), Path=Command.Text)"/>
```
