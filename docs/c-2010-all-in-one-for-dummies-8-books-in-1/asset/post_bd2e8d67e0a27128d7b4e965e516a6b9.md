
# 734 Getting Know SOAP

No, I am not kidding. The problem with standards this detailed in scope is that in order to be useful they must either leave a lot to the imagination or define everything. OASIS erred on the side of being too too loose, and the implementations are a mess.

If you are working inside the Microsoft stack — meaning, you are communicating with .NET projects — you are Golden. Within the Microsoft platform-form, everything is defined the same.

However, if you are communicating outside the .NET Framework — say with IBM or Sun — you expect problems if you are using WS-defined functionality.

The take-home is that SOAP includes a lot of standard functionality that isn't found anywhere else. Sure, some distributed message contracts have a lot of features in SOAP, and SOAP might not be completely implemented the everywhere, but there isn't anything else that even tries to provide this functionality in a standardized way.

From perspective, SOAP is a fantastic platform. New transactions, especially transactions? SOAP has them. Need large binary attachments? SOAP has that. Have BPEL requirements? There's a SOAP for that.

# Big, fat, and slow

In the Java world, 100 MB SOAP messages are not uncommon — although that include the payload — and that works to what, 200,000 lines? in one HTTP call? That’s a bit much.

SOAP dramatically increases your overhead. If you don't need the security, federation, and transaction capabilities of SOAP, consider ReSt — covered in Chapter 4. If you are communicating in a homogeneous environment, consider binary encoding.

On the other hand, if you are communicating in moderately heterogeneous environments and in fact need an encrypted, federated transaction using a common enterprise data model, by all means look at SOAP.

# Making an ASMX Service

You can write a SOAP service in ASMX or WCF.

ASMX doesn’t stand for anything — it is ASP with the P changed to an M, which means Service. (Try not to laugh.) It is the extension of an ASP.NET Web file that provides a service rather than a Web page.

The thing is, ASMX allows only for SOAP, WCF does other things. I cover ASMX; I leave ASMX here because WCF’s additional- functionality makes WCF a winner in this race. (For writing in WCF, check out Chapter 3.)

Nonetheless, if you are making a publicly consumable service and it to be straightforward and simple to deploy, ASMX might be for you. Certainly, there is a lot of ASMX service out there which you might have to maintain.

Let’s just start by building one.

# Analyzing the file setup

Note that although Service1.asmx file (and the usual code-behind) is created, the markup file has only one line in it:

```aspnet
<@ WebService Language="C" CodeBehind="Service1.asmx.cs" Class="ANewService.Service1" %>
```

This is design. Nothing in the markup file. All the magic is in the code-behind.

# Breaking down the sample code

The Service1 file does all the work in our new service, starting with the code in the template. Let's run through that code a line at a time:

```csharp
using System;
using System.Collections.Generic;
using System.Linq;
using System.Web;
using System.Web.Services;

namespace AService
{
    /// <summary>
    /// Summary description for Service
    /// </summary>
    [WebService(Namespace = "http://tempuri.org/")]
    public class ScriptService : System.Web.WebService
    {
        [WebMethod]
        public string HelloWorld()
        {
            return "Hello World";
        }
    }
}
```

There are eight things to point out:

- Line 5 brings in the System.Web namespace; it's essential to have the rest of the template.
- Line 12 sets the namespace for the service. The namespace, just like that of .NET classes, can be anything you want. It doesn't refer to a real place on the Web.
- Line 13 sets the Binding, WS-I is the Web Services Interoperability organization who (you guessed) it sets more standards for Web Services. Basic Profile 1.1 is more or less the industry standard. You can find out more at http://www.ws-i.org.
- Line 14 declares the item should be Toolbox item in design. This declares whether it should show up in design environments.
- Line 16 (when uncommented) activates runtime support for AJAX.
- Line 17 is a normal, everyday class definition, but notice it inherits WebService.
- Line 20, you can see the [WebMethod] attribute. This allows you to control what methods are available to the service from the class, and there are a few attributes for fine-grained control.
- The code itself is far boring — the functional code is exactly the same as it would be in a normal class.

# Running the service

Press F5 and run the service. If all goes well, you should see something like Figure 2-2. This is the default visualization that you didn't make a user interface; IIS did this, to make it easier to test. External users can see this.

Click the Service Description gives you the WSDL for the whole service. This is what a .NET application needs to build its proxy. Note all it does is append a ?WSDL to the end of the URL.

Clicking the Hello World link gives you a test implementation for the method. You will have one of these links for every one of the methods in the class marked with WebMethod.
