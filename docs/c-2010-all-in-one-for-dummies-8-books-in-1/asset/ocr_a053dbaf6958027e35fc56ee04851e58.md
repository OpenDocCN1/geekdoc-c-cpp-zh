You can also wrap one method around another, like so:

```
void wrappedMethod() {
    _wrapped.DoSomething();
}
```

Wrapping is a powerful, frequently used technique in programming. A wrapper class looks like this:

In this example, WrappedMethod()'s class HAS_A relationship to whatever the wrapped object is. In other words, the class wraps object. WrappedMethod() delegates all of evening chores to the DoSomething() method on the _wrapped object.

```
class Wrapper {
    private Wrapped _wrapped;
    public Wrapper(Wrapped w) {
        _w = w; // Now Wrapper has a reference to Wrapped.
    }
}
```

Think of wrapping as a way to translate one model into another. The wrapped item may be complicated, or the wrapped item may have an inconvenient interface that you want to make over into a common interface. Generally speaking, wrapping illustrates the Adapter design pattern (which you can find your favorite search example). You can see it in the relationship between StreamWriter and FileStream.

In this example, I used Wrapper's constructor to install the wrapped object, letting the caller provide the wrapped object. You might install it through a SetWrapped()

In many cases, you can wrap one stream around another in order to convert one stream into another.

> Notice that the pattern nulls the reference after closing StreamWriter. A file object is useless after it has been closed. It is good programming practice to null a reference after it becomes invalid so you don't want to use it. (If you do, your code will throw an exception, letting you know about it!) Closing the file and nulling the reference leaves the garbage collector claim (see Book II to meet the friendly collector on your route) and leaves the file available for other programs to open.
