
## 200 Planning Your Exception-Handling Strategy

- In most cases, don't catch exceptions in a particular method unless you can handle them in a useful way, preferably by recovering from the error. Catching an exception that you can't handle is like catching a wasp in your bare hand. Now what? Most methods don't catch exceptions.

- Test your code thoroughly, especially for any category of bad input you can think of. Can your method handle negative input? Zero? A very large empty string? A null value? What could the user do to cause an exception? What fallible resources, such as files, databases, URLs, does your code use? See the two previous bullet paragraphs.

Find out how to write unit tests for your code. It's reasonably easy and lots of fun.

- Catch the most specific exception you can. Don't write catch blocks for high-level exceptions such as ApplicationException. You risk starving handlers up the chain.

- Always put a last-chance exception handler in Main() — or wherever the "top" of your program is (except in reusable class libraries). You can catch Exception in this block and let the last-chance exception handler pick up any straggers. (We explain last-chance handlers in the later section "Grabbing Your Last Chance to Exception.")

- Don't use exceptions as part of the normal flow of execution. For example, don't throw an exception as a way to get out of a loop or exit a method.

- Considering your own custom exceptions if they bring something to the table — such as more information to help debugging or meaningful error messages for users. We introduce custom exceptions in an article on csharp102.info.

The rest of this chapter (along with the articles on csharp102.info) gives you the tools needed to follow those guidelines. For more information, look up exception handling, design guidelines in the Help system, but be prepared for some technical reading.

### How to find out which methods throw exceptions

To find out whether a particular method in the .NET class libraries, as String.IndexOf() — or one of your own methods — can throw an exception, consider these guidelines:

- Visual Studio provides immediate help with tooltips. When you hover the mouse pointer over a method name in the Visual Studio editor, a yellow tooltip lists not only the method's parameters and return type but also the exceptions it can throw.

- If you have used XML comments to comment your own methods, Visual Studio shows the information in IntelliSense just as it does for .NET methods. If you documented the exceptions your method can throw (see the previous section), you see them in a tooltip. The article "Getting Help in Visual Studio" on sharp12.info shows how to use XML comments, and the FactorialException example documenting Factorial() with XML comments.

- The Help provides even more. When you look up a .NET method in Help, you find a list of exceptions that the method can throw, along with additional descriptions not provided by the yellow Visual Studio tooltip. To open the Help page for a given method, click the method name in your code and press F1. You can also supply help for your classes and methods.
