# Using Interfaces to Manage Change in Object-Oriented Programs

Interfaces are the key to object-oriented programs that bend flexibly with the winds of change. Code will laugh in the face of new requirements.

![](bbox=[0.138, 0.252, 0.219, 0.313])

You have no doubt he said, "Change is a constant." When you need a new program to a bunch of users, they soon requesting changes. This feature, please. Fix that problem, please. RoboWarrior has feature X, so why doesn't Robozilla? Many programs have a long shelf life — thousands of programs, especially old Fortran and Cobol programs, have been in service for 20 or 30 years or longer. They undergo little of maintenance in extended time span, *which makes planning and designing for change one of your priorities.*

Here's an example: in the Robot class hierarchy, suppose that all robots move in one way or another. *Robocats slither* — at least when operated by a power (hungry) user. *Robosnakes slither*. One way to implement these different modes of travel inheritance: Give the base class, Robot, an abstract *Move()* method. Each subclass overrides the *Move()* method to implement it differently:

```
public class Robot {
    abstract void Move(int direction, int speed);
    // ...
}
public class Rosnake : Robot {
    public void Move(int direction, int speed);
    // A real Move() implementation here: slithering,
    ... some real code that computes angles and changes
snake's location relative to a coordinate system, say ...
}
```

But suppose that you often receive requests to add new types of movement to existing Robot subclasses. "Please make Robosnake undulate rather than slither," Maybe. (Don't ask me what the difference is.) You now have to open the Robosnake class and modify its *Move()* method directly.

![](bbox=[0.138, 0.794, 0.219, 0.855])

After the *Move()* method is working correctly for most programmers would prefer not to meddle with it. *Implementing slithering is difficult, and changing the implementation can introduce brand-new bugs.* If it isn't broke, don't fix it.
