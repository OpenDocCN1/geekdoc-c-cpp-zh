This solution works: The call ba.Withdraw() now invokes the BankAccount method, just as intended. The problem with this approach is the explicit reference to BankAccount. A future change to the program may rearrange the inheritance hierarchy so that SavingsAccount longer inherits from BankAccount. This type of rearrangement breaks this method in a way that future programmers may not easily find (Heck, I would never be able to find a bug like that).

You need a way to tell C# to the Withdraw() method immediately above in the hierarchy without naming it. That would be the class that SavingsAccount extends. C# provides the keyword for this purpose.

![](bbox=[0.145, 0.503, 0.235, 0.565])

This keyword base is the same one that a constructor uses to pass arguments to its base class constructor.

The C# base code, in the following chunk of code, is the sort of least as this is automatically recast to the base class no matter what that class may be:

```
// Withdraw -- You can withdraw any amount up to the balance; // return the amount withdrawn.
new public decimal Withdraw(decimal withdrawal)

// Take the $1.50 off the top.
base.Withdraw(1.50);
// Now you can withdraw from what's left.
return base.Withdraw(withdrawal);
}
```

The call base.Withdraw() now invokes the BankAccount.Withdraw() method, avoiding the recursive "invoking itself" problem. In addition, this solution doesn't break if the inheritance hierarchy is changed.
