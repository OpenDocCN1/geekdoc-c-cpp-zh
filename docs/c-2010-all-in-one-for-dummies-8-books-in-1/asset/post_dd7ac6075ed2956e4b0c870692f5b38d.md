# Chapter 5: Digging into Web Construction

In This Chapter

- Getting started
- Managing files
- Mastering master pieces
- Testing the testable
- Deploying your masterpiece

> You can know the controls, and you can know the framework, but you don't really know the Web until you understand the little weird bits that make it all work together. No technology has more “glue” components than Web technology.

This chapter is about using some of “glue” components to build an application. It gives you a chance to do things that you'll have to do every time you make a Web application — set up a master page, test your application, and a few others.

ASP.NET shields a lot of that from you, the developer. You don't have to worry about the details of Common Gateway Interface (CGI), for instance. Nonetheless there are a number of details that you have to manage in order to get an application on the Internet, as the following:

- Setting up a Web project can be ... demanding. The default options that Microsoft provides are not immediately obvious, and the need to have it right the first time is high.

- There are templates for ASP.NET sites. These templates provide all those that make a site flow as you navigate through it, like the navigation, advertising, headers, and footers.

- Security for a Web application is ... different. Because a significant percentage of Web applications are available for public access (quite a shift from Windows applications), you have to consider the reality that people are going to try to use your application as a platform for phishing, XSS, and a hundred other hacks.

- Testing Web applications is another consideration, because it is more than unit testing. If your Web application goes viral, you might have 1,000 visitors tomorrow. You don't have to be ready for that day, but you have to know what you need to do to get ready.

- Finally, deploying a Web application is a new pile of joy that you'll get to know and love. I promise. Remember those UML deployment diagrams learned in school? They can be useful after all! You actually use them in the Web world.

# Managing Files

Setting up an ASP.NET project is not trivial, and there are alike of wrong ways to do it. I can't tell you the right way — it depends on your circumstances. What I want to do is give you some of the best practices that will help you form your own path. The idea is to know how the tool works, in order to help you do your work.

# Reviewing project types

The first part of the process is making a new project. With everything else in ASP.NET, this isn't a trivial project. You even have to use a different item to start the project — New Web Site rather than Project, as shown in Figure 5-1.

Figure 5-1: There is even a different menu item!

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_729_0.png)

The New Web Site dialog box includes several items, but we are concerned with only one, the ASP.NET Web site. Here are all the options:

- ASP.NET Web site: This is what we want. It is a file that represents just what it says: a Web site made up of ASP.NET files. Fantastic. Not as simple as it sounds, but it is the right start.

- Silverlight Web: This is not the right place to talk about Silverlight. Like WPF, Silverlight is a XAML (rhymes with "camel") project, but it is designed for the Web. It is Microsoft's answer to Adobe Flash. Don't sweat it now.

- ASP.NET Web service: Don't use this; use WCF for Web Services.

- Empty Web site: Just a folder and a share.

- WCF Service: A Template for a service. Book VII covers these.

- ASP.NET Reports site: Same as the first selection except it includes a bunch of references to the RDL reporting structure.

- Dynamic Link to SQL Web site: This is a simple, auto-generated forms-over-data site. I don't care for them, and they aren't good examples of C#, so I skip them for now. Plus, Link to SQL is end-of-life (meaning Microsoft isn't supporting it any more).

- Dynamic Entities Web site: Again, an auto-generated forms-data site. Not what we are looking for.

If you cancel out of the New Web site dialog box, add a New Project, and then click on the Installed Templates tree view (under C#), a whole new list of goodies. (See Figure 5-2).

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_730_0.png)

Figure 5-2: What's the difference between a Web site and a Web application?

In Visual Studio 2002 and 2003, Web projects worked like all other projects. They had a project file, needed to be compiled and packaged, and so forth. In Visual Studio 2005, that plan was scrapped for the Web site — just a loose collection of files in any folder, which would be treated as a project. No project file, no compilation of a single resource file — more like classic ASP.

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_731_0.png)

Fact is, there is room for both, and in Visual Studio 2008 and 2010, both are offered. So, if you say you want a new Web Site, you get a federation of files in a folder that can be copied over to a Web server. If you want a new Web application, you get a real, compiled application. All the same constraints apply. Here is a breakdown:

- ASP.NET Web Application: How to make a site more like a regular program. With a project file, and so on.

- ASP.NET Web Service Application: Same advice (WCF).

- ASP.NET Ajax Server Control: This allows you to build a new Toolbox for AJAX. A really nice feature, but too in-depth for this minibook. Check MSDN.

- WCF Service Application: How to do service-oriented development in .NET. More in Book VII.

- ASP.NET Server Control: Like the AJAX control, except it allows you to make a normal control.

- ASP.NET AJAX Server Control Extender: A template for changing the functionality of an existing AJAX Toolbox item.

- Dynamic Linq to SQL Web: As earlier, end of life. Don't use it.

- Dynamic Entities Web Application: Just like the Entities site, a real application.

So which do you choose? If it is a site — I use the Web format. If it is an application — I use the Web format. Your mileage may vary. Find out more about the project types at http://webproject.scott.com/.

# Reviewing file types

Make a new ASP.NET site called Chapter5, and save it in the default location. Visual Studio makes a new site for you. Three files are added:

- Default.aspx: This is the starter markup file. Has the HTML and ASP.NET controls.

- Default.aspx.cs: The code-behind file for the Default.aspx file.

- Web.config: The magic configuration file. A lot goes into this.

There is also an App_Data folder. This is used by Visual Studio and ASP.NET to store, for instance, a SQLite database that you might make to store your application data. Just leave it there for a second. You just know a few new files, right? We should add a style sheet, and manage a script file or two. Right-click on the project and select New Item.

You can add an absurd number of files to a site — just like at Figure 5-3. Global Application Class? Silverlight-enabled WCF Service? What are these things? Does anyone actually use this stuff?

Yes, but don't sweat it too much. You need to worry about only a few files to make a good application, like these:

- Master page: This is the template for the site. We handle this in the next section.

- Style sheet: This is the CSS 2.0 style for your application. If you aren't familiar, refer to HTML and CSS For Dummies — great book.

- Jscript file: So because Microsoft can't save JavaScript anymore or the lawyers beat them up.

- Class: Use your basic C class, in its own file.

That's what you need. To organize them.
