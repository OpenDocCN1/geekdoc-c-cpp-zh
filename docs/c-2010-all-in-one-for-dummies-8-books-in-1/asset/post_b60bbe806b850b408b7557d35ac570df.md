## Using fully qualified names

The namespace of a class is a part of the extended class name, which leads to the first way to make classes in one namespace visible in another. This example does not using any directives to simplify referring to classes in other namespaces:

```
namespace MathRoutines // Broken into two segments -- see below.
class Sort {
    public void SomeMethod() {
}
namespace Paint {
    public class PaintColor{
        public PaintColor(int nRed, int nGreen, int nBlue()) {}
        public void Paint() {}
        public static void StaticPaint() {}
    }
}
namespace MathRoutines // Another piece of this namespace
class Test {
    public static void main(string[] args) {
        // Create an object of type Sort from the same namespace
        // we're in and invoke a method.
        Sort obj = new Sort();
        obj.SomeMethod();
        // Create an object in another namespace -- notice that the
        // namespace name must be included explicitly in every
        // class reference.
        Paint.PaintColor black = new Paint.PaintColor(0, 0, 0);
        black.Paint();
        Paint.PaintColor.StaticPaint();
    }
}
```

In this case, the classes Sort and Test are contained within the different namespace, MathRoutines, even though they appear in the different declarations within the file (or different files). That namespace is broken into two parts.

Security is a big topic. Ignoring for a moment all the buzzwords surrounding security. I'm sure you realize that you need to protect your application from people who shouldn't use it. You also need to prevent your application from being used for things it shouldn't be for.

At the beginning of the electronic age, security was usually performed by obfuscation. If you had an application that you didn't want people peeking at, you just had it, and no one would know where to find it. Thus, it would secure. (Remember War Games, the movie in which the military assumed that no one would find the phone needed to connect to its mainframes — but Matthew Broderick's character did?)

Obviously doesn't cut it anymore; now you need to consider security as an integral part of every system that you write. Your application might not contain sensitive data, but it can be used to get other information on the machine. Can it be used to gain access to a network that it shouldn't? The answers to these questions matter.

The main parts to security are authentication and authorization. Authentication is the process of making sure a user is authentic — that the user is who he claims to be. The most common method of authentication is to require the use of a username and password, though other ways exist, such as thumbprint scans. Authorization is the act of ensuring that a user has the authority to do what he asks to. File permissions are a good example of this — users can't delete system-only files, for instance.

## Designing Secure Software

Security takes a fair amount of work to accurately design. If you break the process into pieces, you find that it's a lot easier to accomplish. The Patterns and Practices team (a group of software architects at Microsoft have devise programming best best practices) have created a systematic approach to designing secure programs that I think will feel straightforward, so I describe it in the following sections.

## Determining what to protect

Different applications have different needs that need protection, but if you have a database in your application, that is something that needs protection. If you the most important item to protect. If your application is a server-based application, the server should rate fairly high when you are determining what to protect.

If your program is just a little single-user application, the software should do no wrong — an outsider shouldn't be able to use the application to break into your user's computer.

## Documenting the components of the program

If you think this section's title sounds similar to part of the design process, you're right. A lot of threat modeling is just understanding how the application works and describing it.

First describe what the application does. This description becomes a functional overview. If you follow the commonly accepted Software Development Life Cycle (SDLC), and then the use cases, requirements, or user stories document (depending on your personal methodology) should give you a good starting point.

Next, describe how the application accomplishes all tasks at the highest-level. A Software Architecture Overview (SAO) diagram is a useful way to do it. This diagram shows which machines and services do in your software.
