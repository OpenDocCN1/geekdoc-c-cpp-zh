# Why you should bother with methods

When FORTRAN introduced the function concept — methods, in C # during the 1950s, its purpose was to avoid duplication of code by combining similar sections into a common element. Suppose that you were to write a program to calculate ratios in multiple places. Your program could use the CalculateRatio() method needed, for more or less the sole purpose of avoiding duplication. The savings are not important for a method such as calculateRatio(), but methods can grow much larger. Besides, a common method such as WriteLine() may be invoked in hundreds of different places.

The applications programmer can use CalculateSin() with no concern how this operation is performed internally, which greatly reduces the issues she must monitor. After the number of "variables" is reduced, a large job is accomplished by implementing two, smaller jobs.

Large programs, such as word processors, are built up from many layers of methods at increasing levels. For example, a RedplayDocument() method would undoubtedly call a ReplayParagraph() method to display the paragraph in the document. Repraph() would need to invoke a CalculateWordWrap() method to decide where to wrap the lines that make up the paragraph. CalculateWordWrap() would have to call a LookupWordBreak() method to decide where to break a word at the end of the line, to make the sentences wrap naturally. Each of these methods was described in a single, sentence. (Notice that methods are well named). Quick, a second advantage becomes obvious: Coding a simple method is as easy as coding many — and double easier if the method is small. The CalculateRatio() method includes a check to ensure that the denominator is not zero. If you repeat the calculation code throughout your program, you can easily test this in some cases — and in other places.

Not as obvious is this advantage: A carefully crafted method reduces the complexity of the program. A well-defined method should stand for a concept. You should be able to describe the purpose of the method without using the words and or or. The method should only do one thing.

Without the absolute complex concepts, writing programs of even moderate complexity would find that the task becomes almost impossible — let alone creating an operating system such as Windows, Vista, a word processor such as Word, or a game such as Halo.
