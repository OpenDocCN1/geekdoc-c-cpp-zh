# Configuring

The only downside of WCF is the configuration. Because WCF is the be-all and end-all of the remote procedure call in Windows, there are enough configuration options to handle it all. Gets a little chippy at times.

Fortunately, there is the Service Configuration Editor. Shown in Figure 3-5, the Service Configuration Editor allows you to manage the complex options that are WCF's primary power.

## Using different endpoints

The whole point of WCF is that you can write one service and have IIS accept a lot of different protocols on the same code. Sure, we can do SOAP, which we do in ASMX. We can also do a lot of other protocols. Here is the breakdown of all the different endpoints, according to MSDN:

- * BasicHttpBinding: A binding that is suitable for communicating with WS-Basic Profile conformant Web services (for example, ASMX-based services). This binding uses HTTP as the transport and text/XML as the default encoding.
- * WSHttpBinding: A secure and interoperable binding that is suitable for non-duplex service contracts.
- * DualHttpBinding: A secure and interoperable binding that is suitable for duplex service contracts or communication through SOAP intermediaries.
- * WSFederationBinding: A secure and interoperable binding that supports the WS-Federation protocol that enables organizations that are in a federation to efficiently authenticate and authorize users.
- * NetTcpBinding: A secure and optimized binding for cross-machine communication between WCF applications.
- * NetNamedPipeBinding: A secure, reliable, optimized binding that is suitable for on-machine communication between WCF applications.
- * NetMmqBinding: A secure, reliable, optimized binding that is suitable for on-machine communication between WCF applications.
- * NetMmqBinding: A secure, reliable, optimized binding that is suitable for cross-machine communication between WCF applications.
- * NetPeerTcpBinding: A binding that enables secure, multiple machine communication.
- * NetsmIntegrationBinding: A binding that is suitable for cross-machine communication between WCF application and Message Queuing.
- * BasicHttpPostBinding: A binding that is suitable for communicating with WS-Basic Profile conformant Web services that enables HTTP to be used for exchange context.
- * NetTcpBinding: A secure and optimized binding for cross-machine communication between WCF applications that enables SOAP to be used for exchange context.
- * HttpBinding: A binding used to configure endpoints for WCF services that are exposed through HTTP instead of SOAP messages.
- * WSHttpBinding: A secure and interoperable binding that is suitable for non-duplex service contracts that enables SOAP headers to be used for exchange context.

When do you use what? If you want to use .NET applications or a single application, then use NetTcpBinding. If you are cross-platform, then use HttpBinding. Only if some reason those don't work do you start looking into the others. Or, remember that you may have many endpoints of the same service. Just don't use SOAP layer if you need cross-platform support.

# 756 Creating a WCF Service

Back in Visual Studio-land, open the Web.Config file in the code editor by double-clicking it in the Solution Explorer. You'll see that the ServiceModel section has been edited with your new endpoint. The code looks like this:

```xml
<system.serviceModel>
  <services>
    <service name="SHARPService.Registration">
      <clear />
      <endpoint address="http://localhost" binding="basicHttpBinding" bindingConfiguration="SharpHttp" contract="SHARPService" />
    </service>
  </services>
  <behaviors>
    <behavior>
      <!-- To avoid disclosing metadata information, set the value below to
           false and remove the metadata endpoint before deployment -->
      <serviceMetadata endpointEnabled="true" />
      <!-- To receive exception details for debugging purposes, set the
           value below to true. Set to false before deployment to avoid disclosing
           exception information. -->
      <serviceDebug includeExceptionDetails="false" />
    </behavior>
  </behaviors>
</system.serviceModel>
```

Now, would that have been easier to do in code? Maybe. Why is the service editor around then? Because when you get a lot of bindings, it can get pretty messy in there. Check out the sidebar on other bindings to get an idea.

# Deploying

If you use IIS to host the service, deployment of WCF is the same as ASMX. You can effectively copy the .svc and config files with the compiled binaries and a working Web application.

The better way to deploy in Visual Studio 2010 is to publish the Web tool. If you right-click on the project and select Publish, you'll have the option to set up a repeatable profile so that you don't forget anything. (Figure 3-8).

This panel does all the things that you would have to do yourself:

- Set the URL of the service
- Name the Application (in the site properties in IIS)
- Set up credentials
- Copy the right files
