
# 450 Pulling Out of the Stream: Using StreamReader

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_475_0.png)

Recall that the current directory that FileRead uses is the \bin\Debug sub-under your FileRead project (not the \bin\Debug directory under the FileWrite program's directory, which is used FileWrite to create some test files in the preceding section). Before you run FileRead to try it, place any plain text file (.TXT) in FileRead's \bin\Debug and note its name so you can open it. A copy of the TestFile1.txt file created in the FileWrite example would be good.

In FileRead, the user reads and only one file. The user must enter a valid filename for the program to output. No second-changes. After the program has it, if the user wants to peek into a second file, she'll have to run the program again. That's a design choice you might make different.

The program starts out all of its code wrapped in an exception handler. In this block, handler tries to call two methods, first to get a StreamReader for the file and then read the file and dump its lines to the console. In the event of an exception, the catch block writes the exception message. Finally, when the exception occurred or not, the finally block makes sure the stream and its files are closed and the variable sr is nulled so the garbage collector can reclaim it (see Book I). I/O exceptions could occur in either method called by this block. This selects up to Main() looking for a handler. (No need for exception handlers the methods.)

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_475_1.png)

Note the //TODO: comment comes in the catch block. This is a reminder to make the message more user-friendly before releasing the program. Comments marked this way appear in the Visual Studio Task List. In window, select from the drop-down list at the upper left. Double-click an item to open the editor to make that comment in the code.

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_475_2.png)

Because the variable sr is used inside an exception block, you have to set it to null initially—otherwise, the compiler complains about using an initialized variable in the exception block. Likewise, check whether sr is already (or still) null before trying to call its Close() method. Better still, convert the program to use using.

With the GetColorF method, the program gives the user one chance to enter a filename. If the name of the file entered at the console is nothing but a blank, the program throws its error message: You need to enter a filename. If the filename isn't empty, it's used to open a FileStream object in read mode. The File.Open() call here is the same as the one used in FileWrite:

- The first argument is the name of the file.
- The second argument is the file mode. The FileMode.Open says, "Open the file if it exists, and throw an exception if it doesn't." The other option is OpenNew, which creates a zero-length file if the file doesn't exist. Personally, never saw the need for that mode (who wants to read from an empty file?), but each to his own what I say.
- The final argument indicates that I want to read from this FileStream. The other alternatives are Write and ReadWrite. (It would also seem a bit odd to open a file with FileRead using the Write mode, don't you think?)

The resulting FileStream object fs is then wrapped in a StreamReader obj to provide convenient methods for accessing the text file. The StreamReader is finally passed back to Main() for use.

When the file-open process is done, the FileReadToFileConsole() method, which loops through the file reading lines of text using the ReadLine(). The program echoes each line to the console with the ubiquitous Console.Write() before calling back up to the top of the loop to read another line of text. The ReadLine() returns a null when the program reaches the end of the file. When this happens, the method breaks out of the loop and returns. Main() then closes the object and terminates. (You might say that the reading of this reader is wrapped in a while loop inside a method that's in a try block wrapped in enigma.)

The catch block in Main() exists to keep the exception from propagating up the food chain and aborting the program. If the program throws an exception, I have the catch block write a message and then simply swallow (ignore) the error. You're in Main(), so there's nowhere to rethrow the exception and nothing to do but close the stream and close up shop. The catch is there to let the user know why the program failed and to prevent an unexpected crash. You could have the program loop back and ask for a different line, but is so small that it's simpler to let the user run it.

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_476_0.png)

Providing an exception handler with a catch block that allows the exception from aborting an unintended error. However, use this technique and swallow the exception only if an error would be truly, no fake, nondamaging. See the more extensive discussion in Book II.

# 452 More Readers and Writers

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_477_0.png)

Earlier in this chapter, show you the StreamReader and StreamWriter classes that are little-readable for the use of I/O needs. However, .NET also makes several other reader writer pairs available:

- BinaryReader/BinaryWriter: A pair of stream classes that contain methods for reading and writing each value: ReadChar(), WriteChar(), ReadByte(), WriteByte(), and so on. (Classes are a little more primitive: they don't offer ReadLine()/ReadLine() methods.) The classes are used for reading or writing an object in binary (nonhuman-readable format, as opposed to text). You can use an array of bytes to work with the binary data (For example, you may need to read or write the bytes that make up a bitmap graphic.)

Experiment: Open a file with EXE extension using Notepad. You may see some readable text in the window, but most of it looks like some sort of garbage. That is binary data.

The article "Converting Byte and Char" on my site gives you a brief tour of working with arrays of bytes or chars. Book II includes an example, mentioned earlier, that reads binary data. The example uses a BinaryReader with a FileStream to read chunks of bytes from a file and then writes the data out on the console in hexadecimal (base 16) notation, which I explain in that chapter. Although it wraps a FileStream in the more convenient FileStream itself, they are identical. While the BinaryReader brings nothing to the table in that example, I used it to provide an example of this reader. The example demonstrates reading bytes into a buffer (an array big enough to hold the bytes read).

- StringReader/StringWriter: And now for something a little more exotic: simple reader and writer classes that are limited to reading and writing strings. They let you treat a string like a file, an alternative to accessing a string's characters in the usual ways, such as with a loop

```
foreach(char c in someString) { Console.Write(c); }
```

or with-array bracket notation ([])

```
char c = someString[3];
```
