
## 268 Why You Should Worry about Access Control

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_293_0.png)

```csharp
// DecimalBankAccount -- Create a bank account using a decimal
// Variable to store the account balance.
using System;
namespace DecimalBankAccount
{
    public class Program
    {
        public static void Main(string[] args)
        {
            // Open a bank account.
            Console.WriteLine("Create a bank account object");
            BankAccount ba = new BankAccount();
            ba.InitAccount();
            // Make a deposit.
            double deposit = 123.454;
            Console.WriteLine("Depositing {0:C}", deposit);
            ba.Deposit(deposit);
            // Account balance
            Console.WriteLine("Account: {0}", ba.GetBalance());
            // Now add a very small amount.
            double fractionalAddition = 0.002;
            Console.WriteLine("Adding {0:C}", fractionalAddition);
            ba.Deposit(fractionalAddition);
            // Resulting balance.
            Console.WriteLine("Resulting account {0}", ba.GetBalance());
            // Wait for user to acknowledge the results.
            Console.WriteLine("Press Enter to terminate...");
            Console.Read();
        }
    }
}

// BankAccount -- Define a class that represents a simple account.
public class BankAccount
{
    private static int _nextAccountNumber = 1000;
    private int _accountNumber;
    // Maintain the balance as a single decimal variable.
    private decimal _balance;
    // Init -- Initialize a bank account with the next
    // account id and a balance of 0.
    public void InitBankAccount()
    {
        _accountNumber = ++_nextAccountNumber;
        _balance = 0;
    }

    // GetBalance -- Return the current balance.
    public double GetBalance()
    {
        return (double)_balance;
    }
    // AccountNumber
    public int GetAccountNumber()
    {
        return _accountNumber;
    }
    public void SetAccountNumber(int accountNumber)
    {
        this._accountNumber = accountNumber;
    }
    // Deposit -- Any positive deposit is allowed.
    public void Deposit(double amount)
    {
        if (amount > 0.0) {
            // Round off the double to the nearest cent before depositing.
            decimal temp = (decimal)amount;
            temp = Decimal.Round(temp, 2);
            balance += temp;
        }
    }

    // Withdraw - You can withdraw any amount up to the
    // balance; return the amount withdrawn.
    public double Withdraw(double withdrawn)
    {
        // Convert to decimal and work with decimal.
        decimal decWithdrawn = (decimal)withdrawn;
        if (balance < decWithdrawn)
        {
            decWithdrawn = balance;
        }
        balance -= decWithdrawn;
        return (double)decWithdrawn; // Return a double.
    }

    // GetString - Return the account data as a string.
    public string GetString()
    {
        string s = String.Format("{0} = {1:C}", GetAccountNumber(), GetBalance());
        return s;
    }
}
```

I've converted all internal representations to decimal, a type better adapted to handling balances than double in any case. The Deposit() method now uses Decimal.Round() to route the amount to the nearest cent before making the deposit. The output from the program is now as expected:

```
Create a bank object
Account = $123.45
Adding $0.00
Resulting account = $123.45
Press Enter to terminate...
```

### So what?

You could argue that I should have written BankAccount using decimal to begin with, and I probably agree. The point is that other applications using double as the form of storage a problem arose. The BankAccount class was able to fix the problem internally and make no changes to the application. Notice that the class's public interface didn't change: Balance() and Withdraw() still return doubles, and Deposit() still takes a double parameter.

None of those methods would have to change because the fix was within the confines of the BankAccount class, whose public interface (its public methods) didn't outwardly change. This solution wouldn't been possible if the internal members of the class had been exposed to external methods.

### Defining Class Properties

The GetX() and SetX() methods demonstrated in the previous section are access methods, or simply accessors. Although they signify good programming habits in theory, access methods can become clumsy in practice. For example, the following code line is necessary to increment _accountNumber by 1:

```csharp
SetAccountNumber(GetAccountNumber() + 1);
```

C# defines a construct known as a property, which makes accessing methods much easier than making methods. The following code snippet defines a read-write property, AccountNumber (it’s both a getter and a setter):

```csharp
public int AccountNumber // No parentheses here
{
    get { return _accountNumber; } // The "read" part. Curly braces and semicolon.
    set { _accountNumber = value; } // The "write" part. 'value' is a keyword.
}
```

The get section is called whenever the property is read, and the set section is invoked on the writer. The following Balance property is read-only because only the get section is defined (using a less compact notation):

```csharp
public double Balance
{
    get { return (double)_balance; }
}
```

In use, these properties appear as follows:

```csharp
BankAccount ba = new BankAccount();
// Set the account number property.
ba.accountNumber = 1001;
// Get both properties.
Console.WriteLine("{0} = {1:C}", ba.accountNumber, ba.Balance);
```

The properties accountNumber and Balance look much like public data members; both appear alike. However, properties enable the class to protect internal members (Balance is a read-only property) and hide their implementation (the underlying _balance data is private). Notice that Balance performs a conversion — it could have performed any number of calculations. Properties aren't one-liners.

By convention, the name of a property begins with a capital letter. Note that properties don't have parentheses: It's Balance, not Balance().

Properties aren't necessarily inefficient. The C# compiler can optimize a simple access to the point that it generates no more machine code than accessing the data member directly. This concept is important, not only to an application program but also to C# itself. The C# library uses properties throughout, and you should too.

Use properties to access class data members, even from methods in the class.

### Static properties

A static (class) data member may be exposed through a static property, as shown in this simplistic example (note its layout):

```csharp
public class BankAccount
{
    private static int _nextAccountNumber = 1000;
    public static int NextAccountNumber { get { return _nextAccountNumber; } }
}
```

The NextAccountNumber property is accessed through the class as follows because it's not an instance property (it's declared static):

```csharp
// Read the account number property.
int value = BankAccount.NextAccountNumber;
```

(In this example, value is outside the property, so it isn't a reserved word.)

### Properties with side effects

A get operation can perform extra work than simply retrieving the associated property, as shown here:

```csharp
public static int AccountNumber
{
    // Retrieve the property and set it up for the mimic
    // next by incrementing it.
    get { return ++nextAccountNumber; }
}
```

This property mimics the static account number. This action isn't a good idea, however, because the user of the property has no clue that anything is happening other than the actual reading of the property.
