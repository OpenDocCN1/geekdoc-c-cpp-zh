## Assigning Multiple catch Blocks

I mention earlier in this chapter that you defined your custom exception types. Suppose that you defined a CustomException class. (I describe this process in the article "Creating Your Own Exception Class") which you can consider the catch clause used here:

```c
public void SomeMethod()
  try {
    SomeOtherMethod();
  } catch (CustomException ce) {
}
```

What if SomeMethod() had thrown a simple Exception or another non-CustomException type of exception? It would be like trying to catch a football with a baseball glove — the catch does not match the throw.

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_221_2.png)

Fortunately, C# enables the program to define numerous catch clauses, each designed for a different type of exception. Assuming that this is the right place to handle the other exceptions, you can tack on one another.

Don't be alarmed by my use of the word numerous. In practice, you don't many catch blocks in one place.

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_221_3.png)

Multiple catch for different exception types must be lined up nose to tail the try block. C# checks each catch sequentially, comparing the object thrown with the catch clause's argument type, as shown in this chunk of code:

```csharp
public void SomeMethod()
{
    try {
        SomeOtherMethod();
    } catch (CustomException ce) // Most specific exception type
{
        // All CustomException objects are caught here.
        // You could insert other exception types between these.
    } catch (Exception e) // General exception type
{
        // All otherwise unchecked are caught here.
        // Not that you should always do so - but when it makes sense
    }
}
```

Always like the catch clauses from most specific to general. Place the more general catch clause first, as in this fairly awful bit of code:

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_222_0.png)

```csharp
public void SomeMethod()

{

```

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_222_1.png)

**The general catch clause starves** the catch clause that follows by intercepting any **throw**. The compiler alerts you to this error.

Any class that inherits CustomException IS_A CustomException:

```csharp
class MySpecialException : CustomException
{
    // .. whatever
}
```

Given the chance, a *CustomException* grabs a *MySpecial Exception* object like a frog nabs flies.

## Planning Your Exception-Handling Strategy

It makes sense to have a plan for how your program will deal with errors. Choosing to use exceptions instead of error codes is just one choice to make.

Due to space limitations, we can't fully explore all the options you have in responding to exceptions. This overview — a set of guidelines and some crucial techniques — should get you well oriented. Refer to the article on csharp102.info to dig much deeper into the basic question “What can I do when code throws an exception?”

## Some questions to guide your planning

Several questions should be on your mind as you develop your program:

- **What could go wrong?** Ask this question about each bit of code you write.
- **If it does go wrong, can I fix it?** If so, you may be able to recover from the problem, and the program may be able to continue. If not, you may need to pack your bags and get out of town.
- **Does the problem put the data at risk?**
- **Where should I put my handler?**
- **Which exceptions should I handle?**
- **How robust does my code need to be?**

## Guidelines for code that handles errors well

You should keep the questions in the previous section in mind as you work. These guidelines may help you:

- **Protect the user's data at all costs.**
- **Don't crash.**
- **Don't let your program continue if you can't recover.**
- **Treat class differently from applications.**
- **Throw exceptions when, for any reason, a method cannot complete its task.**
