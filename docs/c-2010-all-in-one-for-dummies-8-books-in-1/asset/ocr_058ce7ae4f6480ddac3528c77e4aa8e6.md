# Why You Should Worry about Access Control 269

```
if (amount > 0.0) {
    // Round off the double to the nearest cent before depositing.
    decimal temp = (decimal)amount;
    temp = Decimal.Round(temp, 2);
    balance += temp;
}

// Withdraw - You can withdraw any amount up to the
// balance; return the amount withdrawn.
public double Withdraw(double withdrawn) {
    // Convert to decimal and work with the decimal version.
    decimal decWithdrawn = (decimal)withdrawn;
    if (balance < decWithdrawn) {
        decWithdrawn = balance;
    }
    balance -= decWithdrawn;
    return (double)decWithdrawn; // Return a double.
}

// GetString - Return the account data as a string.
public string GetString() {
    string s = String.Format("{0} = {1:C}", GetAccountNumber(), GetBalance());
    return s;
}
```

I've converted all internal representations to decimal, a type better adapted to handling account balances than double in any case. The Deposit() method now uses the Decimal.Round() method to route the deposit amount to the nearest cent before making the deposit. The output from the program is now as expected:

```
Create a bank account object
Account = $123.45
Account = #1001 = $123.45
Adding $0.00
Resulting account = #1001 = $123.45
Press Enter to terminate...
```

# So what?

You could argue that I should have written the BankAccount program using decimal arguments to begin with, and I probably would agree. The point is that I didn't. Other applications were using double as the form of storage. A problem arose. The BankAccount class was able to fix the problem internally and make no changes to the application software. (Notice that the class's public interface didn't change: Balance() and Withdraw() still return doubles, and Deposit() and Withdraw() still return a double parameter.)
