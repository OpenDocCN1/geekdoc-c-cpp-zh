## Calling back to base

Check out the `SavingsAccount.Withdraw()` method in the `HidingWithal` example, shown earlier in this chapter. The call to `BankAccount.Withdraw()` from this new method includes the new keyword base.

The following version of the method without the `base` keyword doesn't work:

```csharp
public decimal Withdraw(decimal withdrawal)
{
    decimal amountWithdrawn = Withdraw(withdrawal);
    amountWithdrawn += Withdraw(1.5);
    return amountWithdrawn;
}
```

This call has the same problem as this one:

```csharp
void fn()
{
    fn(); // Call yourself.
}
```

The call to `fn()` from within `fn` ends calling itself (recursive) repeatedly. Similarly, a call to `Withdraw()` from within the method calls itself in a loop, chasing its tail until the program eventually crashes.

This keyword base is the same one that a constructor uses to pass arguments to its base class constructor.

The C# base code, in the following chunk of code, is the sort of least as this is automatically recast to the base class no matter what that class may be:

```csharp
// Withdraw -- You can withdraw any amount up to the balance; // return the amount withdrawn.
new public decimal Withdraw(decimal withdrawal)

// Take the $1.50 off the top.
base.Withdraw(1.50);
// Now you can withdraw from what's left.
return base.Withdraw(withdrawal);
}
```

The call base.Withdraw() now invokes the BankAccount.Withdraw() method, avoiding the recursive "invoking itself" problem. In addition, this solution doesn't break if the inheritance hierarchy is changed.

## Polymorphism

You can overload a method in a base class with a method in the subclass. As simple as this process sounds, it introduces considerable capability, and with capability comes danger.

Here's a thought experiment: Should you make the decision to call BankAccount.Withdrawal() or SavingsAccount.Withdrawal() at compile time or at runtime?

To illustrate the difference, I change the previous HidingWithdrawal program in a seemingly innocuous way. I call this new version HidingWithdrawalPolymorphically. (I've streamed the listing by leaving out the stuff that doesn't change.) The new version is shown here:

```csharp
// HidingWithdrawalPolymorphically -- Hide the Withdraw() method in the base
// class with a method in the subclass of the same name.
public class Program {
    public static void MakeWithdrawal(BankAccount ba, decimal amount) {
        ba.Withdrawal(amount);
    }
    public static void Main(string[] args) {
        BankAccount ba;
        SavingsAccount sa;

        // Create a bank account, withdraw $100
        ba = new BankAccount();
        ba.Withdrawal(100);

        // Create a savings account, withdraw $100
        sa = new SavingsAccount();
        sa.Withdrawal(100);

        // Use the declared type (BankAccount)
        MakeWithdrawal(ba, 100);

        // Use the runtime type (polymorphism)
        MakeWithdrawal(sa, 100);
    }
}
```

## Using the declared type every time (Is that so wrong?)

In some cases, you don't want to choose the declared type. What you want (or, "what you really, want," to quote the popular Spice Girls song) is to make the call based on the real type — the runtime type — as opposed to the declared type. For example, you to use the SavingsAccount stored in a BankAccount variable. This capability to decide at runtime is known as polymorphism, or late binding.

Polymorphism and late binding aren't exactly the same concept — but the difference is:

- Polymorphism refers to the general ability to decide which method to invoke at runtime.
- Late binding refers to the specific way a language implements polymorphism.
