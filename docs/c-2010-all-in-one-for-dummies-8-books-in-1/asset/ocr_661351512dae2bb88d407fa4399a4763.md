# Writing data code

In most enterprise development environments, however, you won't be using the visual tools to build data access software. Generally, an infrastructure is already in place.

The reason for this is that often, enterprise software has specific requirements, and the easiest way to manage these specifications is with unique and customized code. In short, some organizations don't want things done the way Microsoft does them..

# Output of the visual tools

The reason that the visual tools aren't used in enterprise environments is that the code they put out is rather sophisticated. If you switch to Code View and right-click an instance of an object (such as the PartsTableAdapter object) and select Go to Definition, you will see the code behind the designer.

Figure 2-13 shows what you see when you get first in there. The marking the region near the top of the code window is marked as Windows Form Designer generated code, and you can't help notice that the line number before that section is in the twenties and the after that is in the four hundreds. That's a lot of generated code.

Nothing is wrong with this code, but it is purposely generic to support anything that anyone might want to do with it. Enterprise customers often want to make sure that everything is done the same way. For this reason, they often define a specific data code format and expect their software developers to use that, rather than the visual tools.
