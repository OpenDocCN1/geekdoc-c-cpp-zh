## Generating the entity model

To start, you need the model itself. Just follow these steps to generate the entity model:

- 1. Create a new project (I used a Windows Forms project again, called Entity Framework).
- 2. Right-click the project and click Add New in the context menu. ADO.NET Entity Data Model. Name it PartsDatabase.
- 3. Choose from Database Option in the Choose Model Contents window.
- 4. Select the Assets_Database.mdf from the Connection drop-down list. If it isn't there, see "Connecting to a data source."
- 5. If you get a message asking if you would like to copy the database into the project, select No. Copying the database is usually a bad practice, especially if you are on a shared project. If you are building a stand-alone project, and are working alone, it is an acceptable solution.
- 6. Select the Asset_Parts, Assets, Part_Faults, and Parts tables, just for fun. (See Figure 2-14).

## Writing code for the entity model

After you have interesting addition to your coding environment and the database is meshed nicely into the C# object model, you can code with the objects provided in this entity model. To start, follow these steps:

- 1. Go back to the window designer and double-click the window to go to Code View.

Fishing the stream with C# isn't quite thrilling, but it's one of those indispensable skills. File access refers to the storage and retrieval of data on the disk. This chapter covers basic text input/output. Reading and writing data from databases is covered in Chapter 2 of this book, and reading and writing information to the Internet is covered in Chapter 4.

## Going Where the Fish Are: The FileStream

The console applications in this book mostly take their input from and send their output to the console. Programs outside this chapter have better — or at least different — things to do with file manipulation. I don't want to confuse your message with the extra baggage of input/output (I/O). The I/O classes are defined in the System.IO namespace. The basic I/O class is FileStream. In past days, the programmer would open a file. The open command would prepare a file and return a handle. Usually this was nothing more than a number. Every time you wanted to read from or write to the file, presented presented ID.

C# uses a more intuitive approach, associating each file with an object class. The constructor for FileStream opens the file and manages the underlying handle. The methods of FileStream perform the I/O.

## Going Where the Fish Are: The FileStream

FileStream isn't the only class that can perform I/O. However, it represents your basic file that covers 90 percent of your I/O needs. This primary class is the one described in this chapter. If it's good enough for C#, it's good enough for me.

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_461_0.png)

The stream concept is fundamental to C I/O. Think of a parade, which "streams" the clowns, the floats, a band and two horses, and so on. Viewing a file as a stream of bytes (or characters or strings) is much like a parade. You "stream" the data in and out of your program. The .NET classes used in C# include an abstract base class and subclasses for working with files, over a network, or already sitting as chunks of data in memory. Some classes specialize in encrypting and decrypting data, some are provided to help speed I/O operations that might be slow using one of the other streams, and you're free to extend class with your own subclass if you come up with a great idea for a new stream (I warn you that extending Stream is arduous). You give a tour of the stream classes in the later section Exploring More Streams.

## Readers and writers

FileStream, the stream class you probably use most, is a basic class. Open a file, read a block of bytes, and write a block—that's all about you. But reading and writing files down the byte level is a lot of work, something I eschew unfortunately. Fortunately, the .NET library introduces the notion of "readers" and "writers." Objects of these get incredibly simple (and other) I/O.

When you create a new reader (of one of several available types), you associate a stream with it. It is immaterial to the reader whether the stream connects to a file, a block of memory, a network location, or the Mississippi. The reader requests input from the stream, which it gets from—well, whenever. Using readers is quite simple, except that you're sending output to the stream rather than asking for input. The stream sends it to a specified destination. Not always.

The System.IO namespace contains classes that wrap around FileStream (or other streams) to give you easy access and warm feeling:

- **StreamReader/Writer**: A pair of abstract classes for reading characters (text). These classes are the base for two subclasses: StreamReader/StringWriter and StreamWriter/StreamWriter.

Because StreamReader and StreamWriter are abstract, you'll use one of their subclass classes, usually StreamReader/StreamWriter, to do actual work. I explain abstract classes in Book II.

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_461_1.png)

- **StreamReader/StreamWriter**: A more sophisticated text reader and writer for the more discriminating palate — not to mention they aren't abstract, so you can even read and write with them. For example, StreamWriter has a WriteLine() method like that in the Console class. StreamWriter has a corresponding ReadLine() method and a handy ReadToEnd() method that grabs the whole text in one gulp, returning the characters as a string — which you could use with a StringReader (discussed), a foreach loop, String.Split() method. You see StreamReader and StreamWriter in action in the next two sections.
