
# Overloading an Inherited Method

As described in Chapter 3 of this minibook (look up overloading in the index), two or more methods can have the same name as long as the number or type of arguments differs (or as long as both differ).

> ### **It's a simple case of method overloading**
> Giving two methods the same name is overloading, as in "Keeping them straight is overloading my brain."

The arguments of a method become a part of its extended name, as in this example demonstrates:

```csharp
public class MyClass {
    public static void aMethod() {
        // Do something.
    }
    public static void aMethod(int i) {
        // Do something else.
    }
    public static void aMethod(double d) {
        // Do something even different.
    }
    public static void Main(string[] args) {
        aMethod();
        aMethod(1);
        aMethod(2.0);
    }
}
```

C# can differentiate the methods by their arguments. Each of the calls in Main() accesses a different method.

The return type is not part of the extended name. You can't have two methods that differ only in their return types.

## Different class, different method

Not surprisingly, the class to which a method belongs is also part of its extended name. Consider this code segment:

```csharp
public class MyClass {
    public static void aMethod1();
    public void aMethod2();
}
public class UrClass {
    public static void AMethod1();
    public void AMethod2();
}

public class Program {
    public static void Main(string[] args) {
        UrClass.AMethod1(); // Call static method.
        // Invoke the MyClass.AMethod2() instance method:
        MyClass mcObject = new MyClass();
        mcObject.AMethod2();
    }
}
```

The name of a class is part of the extended name of the method. The method MyClass.AMethod1() has about as much as to do with UrClass.AMethod1() as YourCar.StartOnAColdMonitoring() and MyCar.StartOnAColdMonitoring() — at least works.

## Peek-a-boo — hiding a base class method

So in method one class can overload another method in its own class by having different arguments. It turns out, a method can also overload a method in its own base class: a base class method is known as hiding the method.

Suppose that your bank dept making savings accounts different from other types of withdrawals. Suppose, just for the sake of argument, that drawing from a savings account costs $1.50.

Taking the procedural approach, you could implement this policy by setting a flag (variable) in the class to indicate whether the object is a SavingsAccount or a simple BankAccount. Then the withdrawal would have to check the flag to decide whether it needs to charge here:

```csharp
public class BankAccount {
    private decimal _balance;
    private bool _isSavingsAccount; // The flag
    // initialize the initial balance and whether the account
    // you're creating a savings account.
    public BankAccount(decimal initialBalance, bool isSavingsAccount) {
        _balance = initialBalance;
        _isSavingsAccount = isSavingsAccount;
    }

    public decimal Withdraw(decimal amountToWithdraw) {
        // If the account is a savings account ...
        if (_isSavingsAccount) {
            // ...then skim off $1.50.
            _balance -= 1.50M;
        }
        // Continue with the usual withdrawal code:
        if (amountToWithdraw > _balance)
        {
            amountToWithdraw = _balance;
            _balance -= amountToWithdraw;
            return amountToWithdraw;
        }
    }
}

class MyClass {
    public void someMethod() {
        // I want to create a savings account:
        BankAccount ba = new BankAccount(0, true);
    }
}
```

Your method must tell the BankAccount whether it's a SavingsAccount in the constructor by passing a flag. The constructor saves that flag and uses it in the Withdraw() method to decide whether to charge the $1.50.

The more object-oriented approach hides the method Withdraw() in the base BankAccount with a new method of the same name, signature, and hair color in the SavingsAccount class:

```csharp
// HidingWithdrawal -- Hide the withdrawal method in the base
// with a subclass of the same name.
using System;
namespace HidingWithdrawal
{
    // Withdraw -- A very basic bank account
    public class BankAccount
    {
        protected decimal _balance;
        public BankAccount(decimal initialBalance)
        {
            _balance = initialBalance;
        }
        public decimal _balance
        {
            get { return _balance; }
        }
        public decimal Withdraw(decimal amount)
        {
            // Good practice avoids modifying an input parameter.
            // Modify a copy
            decimal amountToWithdraw = amount;
            if (amountToWithdraw > _balance)
            {
                amountToWithdraw = _balance;
            }
            _balance -= amountToWithdraw;
            return amountToWithdraw;
        }
    }
    // SavingsAccount -- A bank account that draws interest
    public class SavingsAccount : BankAccount
    {}
}
```

## Overloading an Inherited Method

```csharp
// ...
public class SavingsAccount : BankAccount
{
    private decimal _interestRate;
    // SavingsAccount -- A bank account that draws interest
    public SavingsAccount(decimal initialBalance, decimal interestRate) : base(initialBalance) {
        _interestRate = interestRate;
    }
    // AccumulateInterest -- Add interest to the balance
    public void AccumulateInterest()
    {
        _balance += _balance * _interestRate;
    }

    // Withdraw -- Call the base method then charge fee
    public new decimal Withdraw(decimal amount)
    {
        decimal result = base.Withdraw(amount);
        result -= 1.50M;
        return result;
    }
}

public class Program
{
    public static void Main(string[] args)
    {
        BankAccount ba = new BankAccount(100);
        SavingsAccount sa = new SavingsAccount(100, 0.05m);

        Console.WriteLine("BankAccount balance: {0:C}", ba._balance);
        Console.WriteLine("SavingsAccount balance: {0:C}", sa._balance);

        ba.Withdraw(20);
        Console.WriteLine("BankAccount balance after withdrawal: {0:C}", ba._balance);

        sa.Withdraw(20);
        Console.WriteLine("SavingsAccount balance after withdrawal: {0:C}", sa._balance);

        sa.AccumulateInterest();
        Console.WriteLine("SavingsAccount balance after interest: {0:C}", sa._balance);
    }
}
```

## Overloading an Inherited Method

### Making the hiding approach better than adding a flag

On the surface, adding a flag to the BankAccount class may seem simpler than all this method-hiding stuff. After all, it's just four lines of code. The problems are manifold. (I had to write several chapters just to be able to use that word.) One problem is the BankAccount class has no business worrying about the details of CheckAccount or CDAccount. All those likely have different withdrawal policies, each requiring its own flag. After adding three or four different types of accounts, the old Withdraw() method looks complicated. Each of those classes should worry about its own withdrawal policies and leave the old BankAccount alone. Classes are responsible for themselves.

### Accidentally hiding a base class method

Oddly enough, you can hide a base class method accidentally. For example, you have a Vehicle.TakeOff() method that starts the vehicle rolling. Later, someone else extends your Vehicle class with an Airplane class. TakeOff is entirely different. In airplane logic, "take off" means more than "start moving." Clearly, this is a case of mistaken identity — the methods have no similarity other than their identical name.

Fortunately, C detects this problem.

C generates an ominous warning when it compiles the HidingWithdrawal program example. The text of the warning message is, here's the important part:

```
...BankAccount.Withdraw(decimal) hides inherited member 'BankAccount.Withdraw(decimal)'
Use the new keyword if hiding was intended.
```

C is trying to tell you that you've written a method in a subclass that has the same name as one in the base class. Is that what you meant to do?

This is just a warning — you don't notice it until you switch over to the Error List to take a look. But you must sort out and fix all warnings. In almost every case, a warning is telling you something about what you can bite if you don't fix it.
