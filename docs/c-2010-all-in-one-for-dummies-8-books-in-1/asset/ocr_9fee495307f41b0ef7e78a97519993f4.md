One way to give other code in the same assembly access to a base class's members — including a subclass in the same assembly — is to mark those members internal rather than protected. That way, you gain the desired level of access from a local subclass while preventing access from an external subclass. Of course, access is allowed from other classes in the assembly. This solution may not be ideal, but it should be more secure — if that is a consideration.

# Protected internal: Being a more generous protector

Making items in the BankAccount class base protected internal, rather than just protected, simply adds a new dimension to the accessibility of items in your program. Using protected alone allows a subclass to access items. Making internal extends the items' accessibility to a class, as long as it's in the same assembly as BankAccount or at least a subclass in some other assembly.

In the ProtectedInternalExample on csharp102.info, you can see this effect. The class AnotherClass's defined within BankAccount's assembly can access the protected internal accessor in the Balance property. However, the identical AnotherClass in a different assembly cannot access Balance's set accessor to the balance.

Make items as inaccessible as possible. Start with some parts of your code need more access than that, increase it selectively. Maybe just protected will work that's a subclass needs). Maybe increase it to internal. If subclasses and classes in the same assembly need access, use protected internal. Use public only for classes (and their members) that should be accessible to every class in the program, regardless of assembly.

The same advice that applies to whole classes also applies to class members: Keep them as inaccessible as possible. Little helper classes, or classes that support the implementation of more public classes, can be limited to no more than internal.

If a class or other type needs to be private, protected, or protected internal, nest it, if you can, inside the class that needs access to it.

# Putting Classes into Namespaces

Namespaces exist to put related classes in one bag and to reduce collisions between names used in different places. For example, you may compile all math-related classes into a MathRoutines namespace.
