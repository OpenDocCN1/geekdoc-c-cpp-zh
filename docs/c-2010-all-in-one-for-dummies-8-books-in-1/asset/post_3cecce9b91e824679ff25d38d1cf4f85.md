
# Generics are type-safe

When you declare an array, you must specify the exact type of data it can hold. If you specify int, the array can't hold anything other than ints or other numeric types that C# can convert implicitly to. You see compiler errors at build-time if you try to put the wrong kind of data into an array. Thus the compiler enforces type-safety, enabling you to fix a problem before it ever gets out of yours.

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_195_0.png)

A compiler error beats the heat of a runtime error. In fact, a compiler error beats everything except a royal flush or a raspberry sundae. Compiler errors are useful because they help you solve problems.

The old-fashioned generic collections are not type-safe. In C#, everything is Object because Object is the base type for all other types, with value-types and reference-types. But when you store value-types (numbers, chars, bools, and structs) in a collection, they must be boxed in and unboxed both ways. It's as though you are putting items in an egg carton and having to stuff them inside the eggs so they fit, and then breaking the eggs to get the items out. (Reference-types such as string, Student, and BankAccount don't undo boxing.)

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_195_1.png)

The first consequence of non-generic lacking type-safety is that you need a cast, as seen in the following code, to get the original object out of the ArrayList it's hidden inside of, or Object:

```
ArrayList list = new ArrayList();
// Add five or six items, then
string myString = (string)list[4]; // Cast to string.
```

Fine, the second consequence is this: You can put eggs in the carton, but you can also add marbles, rocks, diamonds, fudge — you name it. An ArrayList can hold many different types of objects at the same time. So it's legal to write this:

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_195_2.png)

```
ArrayList list = new ArrayList();
list.Add("string"); // OK
list.Add(3); // int OK
list.Add(new Student()); // OK
```

However, if you put a mixture of incompatible types into an ArrayList (or another generic collection), how do you know what type is in, say, aList[3]? If it's a Student and you try to cast it to string, you get a runtime error. It's just like Harry Potter reaching into a box of Bertie Bott's Every Flavor Beans: He doesn't know whether he'll grab raspberry beans or

You can avoid all this extra work using generics. Generic collections work like arrays: You specify the one and only type you can hold when you declare them.

# Generics are efficient

Polymorphism allows the Object to hold any other type — as with the egg carton analogy in the previous section. But you can incur a penalty by putting in value-objects — numeric, char, and bool types and structs — taking them out. That's because value-type objects that you have to be boxed (See Book II for more polymorphism).

Boxing is worthless unless generic is big (although the amount of boxing going on can startle you and be more costly than you imagined). If you're stalling a thousand, or a million, into a generic collection takes about 20 minutes long, plus extra space on the memory heap, reference-type objects are stored. Boxing can also lead to subtle errors that will have you tearing your hair out. Generic collections eliminate boxing and unboxing.

Don't get me wrong: Boxing allows C# to have a unified type system, which has great benefits that usually outweigh the inconvenience and cost of boxing.

# Classy Generics: Writing Your Own

Besides the built-in generic collection classes, C# lets you write your own generic classes, whether they collections or not. The point is that you can create generic versions of classes that you design.

Picture a class definition full of <T>. When you instantiate such a class, you specify a type to replace its generic placeholders, just as you do with the generic collections. How simple these declarations are:

```
LinkedList<int> aList = new LinkedList<int>(); // Built-in LinkedList class
MyClass<int> aClass = new MyClass<int>(); // Custom class
```

Both are instantiations of classes — one built-in and one programmer-defined. Not every class makes sense as a generic; later in this chapter, I show you an example of one that does.

Classes that logically could do the same things for different types of data make the best generic classes. Collections of one sort or another are the prime example. If you find yourself mumbling, "I'll probably have to write a version of this for Student objects, too," it's probably a good candidate for generics.

![](img/36596fb11aa4233d5cab0d6ddd1d82e8_197_0.png)

To show you how to write your generic class, the following example develops a special kind of queue collection, a priority queue.

Here's the scene for an example: a busy warehouse similar to UPS or FedEx. Packages stream in the front door and out the back as they can be processed. Some packages need to be delivered by way of next-day teleportation; others can travel a bit slower, by second-day cargo pigeon; and most can take the snail route: ground delivery in your city's '82 Volvo.

But the packages don't arrive at the warehouse in any particular order, so as they come, you need to expedite them as next-day or second-day. Because some packages are more equal than others, they are prioritized and the folks in the warehouse give the high-priority packages special treatment.

Except for the priority aspect, this situation is tailor-made for a queue structure. A queue is perfect for anything that involves-turning. You've stood (or driven) in thousands of queues in your life, waiting for your turn to buy tickets or pay too much for prescription medicines. You know the drill.

The shipping warehouse scenario is similar: New packages arrive and go to the back of the line — normally. But because some have higher priorities, they're privileged characters, like those Premium Class folks at the airport ticket counter. They get to jump ahead, either to the front of the line or far from the front.

The shipping queue at OOPs deals with high-, medium-, and low-priority packages coming in. Here are the rules:

- High-priority packages (next-day) go to the front of the queue — but behind any other high-priority packages that are already there.
- Medium-priority packages (second-day) go as far forward as possible — but all the high-priority packages, the ones that drop off later.
- Low-priority ground-pounders must join at the back.

C# comes with built-in queues, even generic ones. But it doesn't come with a priority queue, so you have to build your own. How? A common approach is to embed several queues within a wrapper class, sort of like this:

```
class Wrapper // Or PriorityQueue
{
    Queue queueHigh = new Queue();
    Queue queueMedium = new Queue();
    Queue queueLow = new Queue();
    // Methods to manipulate the underlying queues...
}
```

Wrappers are classes (or methods) that encapsulate complexity. A wrapper may have an interface different from the interfaces of what's inside — that's an adapter.

The wrapper encapsulates three actual queues (they could be generic), and the wrapper manages what goes into which queue and how. The standard interface to the Queue class, as implemented in C#, includes these two key methods:

- Enqueue (pronounced "N-Q") inserts items into a queue at the back.
- Dequeue (pronounced "D-Q") removes items from the queue at the front.

For the shaping-priority queue, the wrapper provides the same interface as a normal queue, pretending to be normal itself. It implements an Enqueue method that determines the incoming package's priority and decides which underlying queue gets to join. The Dequeue method finds the highest-priority Package in any of the underlying queues.
