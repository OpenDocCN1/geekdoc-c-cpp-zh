# Focus!

I know the question you're dying to ask: If the user clicks on a menu item, doesn't that menu item then have focus? The answer is "No! That's because menus in WPF work a little bit of magic to determine what UElement has focus before a menu item is clicked.

Unfortunately, this doesn't apply to standard buttons and other command bindable controls. Even though the menu items in Figure 4-4 are enabled, the buttons are not. There are two fixes for this problem. The first is by binding the CommandTarget property in addition to the command to the UElement. This is a single element solution, though. To resolve the issue for all elements, the FocusManager.IsSharedScope property needs to be set to True in the parent container.

# Custom commands

Creating a custom command requires either instantiation of a new RoutedUICommand or coding a new command based on the ICommand interface. Well, you are correct — there are other methods as well. The two most popular are what I discuss here.

# Custom UI commands

Creating a new RoutedUICommand is a simple instantiation, as the code in Listing 4-3 shows.

# Listing 4-3: Creating a Custom RoutedUICommand

```csharp
public static RoutedUICommand SaveCommand = 
new RoutedUICommand("Save", "SaveCommand", 
typeof(UIElement));
```

The first parameter in the constructor populates the Text property, the second parameter is the name used in serialization of the command (I usually append Command to the text from the first parameter), and the last parameter is the UIParent.(In this example, the code states any UElement can be the parent.) There is a fourth parameter in another Constructor (not shown here) that is a list of InputGestures.

Custom RoutedUICommands are usually created as static variables so there is only one instance (and makes binding simpler). Yes, it's still in the code-behind file, so we don't yet have Separation of Concerns, but we're getting there!

# Command bindings

Unlike the built-in commands (which are part of the framework and automatically wired into the CommandManager and the binding system), custom commands are not new. Three changes need to be made in the XAML to support custom commands:

- Add the namespace for the namespace declaration.
- Change the command assignment to a binding expression.
- Add the command to the bindings collection of the container.

As Chapter 1 explains, you can add custom namespace declarations to the Window to allow custom classes and namespaces. The namespace for the custom command (which is the same namespace as the Window if the command is a static variable in the code-behind) needs to be added to the Window, Listing 4-4 shows an example namespace declaration. The bold text is what has changed from the default namespace declarations that are in the standard WPF Window.

# Listing 4-4: Updated XAML for Custom RoutedUI

```xml
<Window x:Class="Chapter4.CommandBindingSample"
xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
xmlns:commands="clr-namespace:Chapter4.Commands"
Title="Command Binding" Height="122" Width="261">
```

After the message is brought into the Window, the command must be inserted into the Window.CommandBindings collection. Three proper properties need to be set and are shown in Listing 4-5:

- Command: The binding to the command object
- CanExecute: Event handler for testing execution status
- Executed: Event handler for the execution of the command

With built-in commands, a simple string assigned to the command to the UIElement. With custom commands, you have to use a binding expression (as discussed in Chapter 3). The format for a static command binding is

```xml
{x:Static NamespaceReference:Class.CommandVariableName}
```

The NamespaceReference is the nickname assigned to the Window tag.
Interestingly, the CanExecute and Executed properties are set to the value
of the methods — no funky binding required!

# Listing 4-5: Window CommandBindings XAML

```xml
<Window.CommandBindings>
<CommandBinding Command="(x:Static
Commands:CommandBindingSample.SaveCommand)"
CanExecute="Save_CanExecute"
Executed="Save_Executed"/>
</Window.CommandBindings>
```

The Command property of the CommandBinding and UIElements use the
same binding expressions as shown in Listing 4-6. When a UIElement has
a command bound to it, the framework looks for the first match in
the CommandBindings section.

# Listing 4-6: Command Assignment to MenuItem and Button

```xml
<MenuItem Command="x:Static
Commands:CommandBindingSample.SaveCommand"/>
<Button Command="x:Static
Commands:CommandBindingSample.SaveCommand"
Content="Binding RelativeSource
Mode=Self}, Path=Command.Text"/>
```

The CanExecute event handler for a RoutedUICommand uses the
CanExecuteRoutedEventArgs instead of returning True or False. Setting
e.Execute to True (can run) or False (cannot run) will enable or disable
the command (or any associated UIElements).

If the command is enabled, the Executed event handler gets executed when
UIElement triggers the command (for example, when a button is clicked).

# Command parameters

The CanExecuteRoutedEventArgs and ExecutedRoutedEventArgs contain a Parameter property that provides a mechanism for passing objects
the Window into the CanExecute and executed event handlers. In
example in Figure 4-5, the text of the TextBox is being passed as the parameter.
The CanExecute property of the CanExecuteRoutedEventArgs in
CanExecute event handler is set to False if the string is empty or null, and
Executed event handler displays it to the user in a message box. Okay,
not a realistic example, but it's a demo!

# Listing 4-8: Updated C# to Display Parameter to Command

```csharp
private void Save_CanExecute(object sender,
CanExecuteRoutedEventArgs e)
{
    e.Execute = !String.IsNullOrEmpty(e.Parameter as
string);
}
private void Save_Executed(object sender,
ExecutedRoutedEventArgs e)
{
    MessageBox.Show(e.Parameter.ToString());
}
```

# Custom commands with ICommand

CustomRoutedCommands solve the problem of getting rid of all those nasty OnClick event handlers, consolidating execution code into one event handler and bringing along the goodness of the CanExecute event handler to enable a more dynamic and intuitive user interface.

To truly achieve Separation of Concerns by removing the implementation from the code behind, implement the commands from the ground up with the ICommand interface. The interface for ICommand contains the CanExecute and the Executed event handlers as well as the CanExecuteChanged event.
