# 7.3.2 Analyzing Performance Statistics

One of the first comparisons to make is real CPU time. If your task is performing real and time CPU time are consistently within 10 to 15% of each other, the limiting factor is probably CPU time, and your task is CPU bound. If there is a large difference between real time and CPU time, the limiting factor is probably I/O, and your process is probably I/O bound. Other valuable information from FULLSTIMER can be gained by analyzing the remaining statistics. A search of support.sas.com for “FULLSTIMER SAS option” will provide more in-depth guidance on how to proceed.

# 7.3.3 Tuning Your Code

As a general rule, if your task reads from a table in a DBMS that has the SAS In-Database Accelerator installed, it will run much faster if you rewrite the data program and execute the thread from a data program using the SET statement. Performance will be even better if the data program output is also a database table and your database is capable of running both the thread and data programs in-database. As of this writing, only Teradata and Hadoop have that capability. If your task sources its data from a DBMS, using DS2_OPTIONS TRADE or OPTIONS SASTRACE or both can identify how much processing is happening in the database and how much movement to the SAS platform for processing was necessary.

In summary, the following

+   - If your task is I/O bound, threading on the SAS platform will likely exacerbate the problem. However, if your task sources its data from a DBMS that has the SAS Database Code Accelerator installed, you can probably significantly improve performance by running the process in-database as a DS2 THREAD program.
- If your task is CPU bound, it can benefit from parallel processing using DS2 threads, even if you do not have in-database processing capability available. Try writing the data program as a thread program, and executing it in parallel from a data program using the SET statement, experimenting with THREADS+ option values.
- Another technique I've found (when my DS2 program uses an SQL query as input to the SET statement) is to create a temporary table using the query and then use the temporary table as input to the DS2 program while troubleshooting. This can help isolate performance degradation to the DS2 or SQL portion of the program.

# 7.4.1 SAS Learning Resources
