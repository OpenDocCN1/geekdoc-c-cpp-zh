## 7.1 Introduction

In this chapter, we will discuss factors that affect performance in our DS2 programs, tools to help determine the cause of performance issues, and programming techniques that we can use to tune the performance of our DS2 programs. Along the way, we'll identify some generally good practices for DS2 programmers.

Specifically, we will cover these points:

- using the DS2_OPTIONS statement with the TRACE option
- using the SAS log to gather and analyze performance data
- finding reference and trouble-shooting resources

  - Communities.sas.com
  - SAS Technical Support

## 7.2 DS2_OPTIONS Statement

### 7.2.1 TRACE Option

If you are experienced using SAS to access data from relational databases, you have probably used the SASTRACE system option to see exactly what SQL code was being sent to the database and to determine how processing was executed in the database versus how was executed on the SAS compute platform. The SAS 9.4 release brought in the new DS2 OPTIONS statement. Running a DS2 program in-database after issuing a DS2_OPTIONS statement with the TRACE option produces significant extra information in the SAS log concerning what is actually taking place when processing DS2 code in-database:

```
proc ds2 ds2accel=yes;
ds2_options trace;
data crs_db.test/overwrite=yes;
 dcl thread t t;
 method run();
  set from t;
 end;
enddata;
run;
quit;
```

## 7.3 Analyzing Performance with the SAS Log

### 7.3.1 Obtaining Performance Statistics

The default option settings in SAS provide a modulus of performance reporting in the SAS log. Here is an example of the default performance statistics reported under Linux (the operating system used by SAS University Edition):

Here is an example of standard performance statistics in the SAS log:

```
NOTE: PROCEDURE DS2 used (Total process time):
real time 2.35 seconds
cpu time 0.17 seconds;
```

You will notice that SAS produces performance statistics only after the QUIT statement for PROC DS2 session, so if you have included several DS2 steps within the boundaries, you only get aggregate results for the entire process. For troubleshooting and tuning, try placing each DS2 program in its own PROC DS2 session to obtain more granular results.

When your performing is poorly, the problem usually boils down to one or more of the factors:

- CPU
- memory
- I/O
- network latency

When tracking performance issues, or trying to tune your code, setting OPTIONS FULLSTEM can provide more detailed information that can help you narrow down the areas where the system might be having problems. You can then try writing code in different ways with the intent of mitigating performance problems by alleviating any problems detected.

Here is an example of the performance statistics reported using FULLER:

```
NOTE: PROCEDURE DS2 used (Total process time):
real time 2.35 seconds
user cpu time 0.10 seconds
system cpu time 0.07 seconds
memory 5738.84k
OS Memory 30268.0k
Timestamp 02/14/2016 10:23:11 AM
Step Count 50
Switch Count 192
Page Faults 0
Page Reclaims 1925
Page Swaps 0
Voluntary Context Switches 2648
Involuntary Context Switches 191
Block Input Operations 0
Block Output Operations 0
```

As you can see, the information that is reported is richer with FULLER turned on. Here is some descriptive information for performance statistics:

Table 7.1: Performance Statistics

| Statistic | Significance |
| --- | --- |
| Real Time | This is the "wall clock" time elapsed while your job was executing—for example, the time you spent waiting for the step to complete. If any other programs are running on your system beside SAS, real time can fluctuate significantly depending on how long SAS has to wait for system resources. |
| CPU Time | When FULLER is not in effect, SAS reports the sum of CPU time and system time as CPU time. When FULLER is in effect, CPU time and system time are reported separately. When parallel processing is in effect, CPU time can be greater than real time. |
| User CPU Time | This is the CPU time expended executing user-written code, including the SAS program that you wrote and built-in SAS processes that support its execution. |
| System CPU Time | This is the CPU time expended by the operating system in support of user-written code. |
| Memory | This is the memory allocated to this job or step, not including SAS system overhead. |
| Involuntary Context Switches | This is the number of times a process releases its CPU time-slice involuntarily. Causes include running out of CPU time before your job is finished or having another task grab your time-slice because it has higher priority. |
| Page Swaps | This is the number of times a process was swapped out of main memory. |

## Mastering the DS2 Procedure: Advanced Wrangling Techniques

When benchmarking performance, it is necessary to run each version of a process several times in separate SAS sessions and average the performance results. It is very helpful to be able to extract performance statistics from the SAS log and save them to a SAS data set for later analysis. The experimental %LOGPARSE macro is available for download from the SAS Support website and can automate this process for you to some extent.

If these techniques do not identify your problem, configuring the SAS logging facility to use some of the DS2 loggers might be useful. Setting up SAS to use these loggers can be a bit intimidating at first, but a lot of detailed information can be gained using this technique. See *SAS DS2 Language Reference* appendix titled “DS2 Loggers.” Also see *SAS Logging: Configuration and Programming Reference*.
