### 26.1 Why Is Object-Oriented Programming Necessary?

Object-oriented programming (OOP) is particularly useful to reduce the amount of code required in advanced applications. Roughly speaking, with no OOP, the code size may grow exponentially as the problem becomes more and more complicated. With OOP, on the other hand, it grows only linearly.

Indeed, suppose that we already have a code that works well for some elementary case (for example, a code that solves a two-dimensional application), and we want to generalize it to apply to a yet more complicated case as well (for example, to a three-dimensional application). If our original code were not an object-oriented code, then we would have to modify each and every function in it to apply to the more advanced case as well (Figure 26.1). This would no doubt require more code (as well as more programming work) in each function, increasing the total amount of code (as well as the total programming time) by a constant factor greater than 1.

Fortunately, our code is an object-oriented code. Therefore, all that is needed to do is to implement well the new objects required in the advanced application (such as the tetrahedron object in the three-dimensional mesh), along with the functions associated with them. After all, the original algorithm implemented in the original code should also work well with these objects, with at most some minor adjustments.

Thus, with OOP, one only needs to add to the original code a limited amount of new code to implement the new objects required in the more general (and complicated) case. Thus, the total amount of code (as well as the total amount of programming work) increases only linearly as the problem is written in more and more general terms to apply to more and more difficult cases (Figure 26.2).

### 26.2 The Object-Oriented Implementation

In what follows, the detailed object-oriented implementation of the three-dimensional mesh is introduced. More precisely, the required mesh of tetrahedra is derived from a linked list of "tetrahedron" objects.

The "tetrahedron" object defined in Section 13.3 is a geometrical object that lies in the three-dimensional Cartesian space. More specifically, it has four corners that form four triangular sides or faces. Once the template symbol "T" in the "mesh" class in Section 13.4 is specified to be the "tetrahedron" object, one obtains the required three-dimensional mesh, implemented as a linked list of tetrahedra.

### 26.3 Adaptive Mesh Refinement

Usually, the initial mesh is too coarse to approximate well the curved three-dimensional domain Ω, in which the original PDE is given. At least one refinement step is therefore necessary to improve on the initial coarse mesh and produce a yet finer and more accurate mesh.

In the refinement step, some of the tetrahedra in the coarse mesh are divided into two subtetrahedra. In fact, only those edges in the coarse mesh over which the discrete solution varies sharply are divided, whereas the other edges remain undivided in the fine mesh as well. This procedure is called adaptive mesh refinement.

### 26.4 Preserving Conformity in the Finer Mesh

It is assumed that the initial coarse mesh is conformal in the sense that two adjacent finer mesh must share an entire edge on each side with each other. To make sure that the finer mesh is conformal as well, one must be careful to divide not only the discrete solution jumps but also all the coarse tetrahedra that share it. This way, the midpoint of this edge serves as the joint corner of all the subtetrahedra resulting from dividing the coarse tetrahedron that share it. With this approach, the finer mesh resulting from the refinement step is conformal as well, as required. This procedure is implemented below, using the present object-oriented approach.

### 26.5 Dividing the Adjacent Tetrahedra

Suppose that we have already decided to divide (or refine) some coarse tetrahedron by dividing one of its edges and connecting its midpoint to the corners that lie across from it to form the two required subtetrahedra. Let us denote the two original endpoints of this edge by "nI" and "nJ", and the midpoint that lies in between them by "nIJ". These nodes are now passed as arguments to the "refineNeighbors" function below to search for every neighbor tetrahedron that shares this edge and refine it as well.

In the case of triangulation implemented in Section 14.5, there may be at most one neighbor triangle to refine. Here, on the other hand, there may be several neighbor tetrahedra that share the edge leading from "nI" to "nJ" in the coarse mesh. All those tetrahedra must be found and refined as well. To do this, it makes more sense to scan the tetrahedron in reverse order, from the last tetrahedron in the underlying linked list backward towards the first. This way, once such a tetrahedron has been found and divided into two subtetrahedra as required, the scanning proceeds backward, avoiding the need to scan these two new subtetrahedra that have just been added to the linked list. This is why the recursive call is made in the beginning of the function, to start dividing neighbor tetrahedra from the far end of the underlying linked list:

```

    ((mesh<tetrahedron>*)next)->
        refineNeighbors(nI,nJ,nIJ);
```

(Because the "next" field is a mere pointer to a linked list of tetrahedra, it must be converted explicitly to a pointer-to-mesh before the recursive call can be made.) This recursive call searches the "tail" of the underlying linked list (which contains all the tetrahedra but the first one) for potential neighbor tetrahedra that share the edge leading from "nI" to "nJ". This recursive call uses a yet inner recursive call to search the yet shorter tail that contains all the tetrahedra but the first and second ones, and so on. As a result, the final recursive call at the top of the stack of recursive calls is executed first, and checks only whether the last tetrahedron in the underlying linked list is a neighbor tetrahedron or not. If it is, then it is refined as well, as required. Then, the previous recursive call is executed, to check the previous tetrahedron and refine it if necessary, and so on, until the first tetrahedron is checked and refined if necessary:

```

int nj = nJ < item;
```

If they are, then this operator also returns their indices in the list of nodes in "item" plus 1. This extra 1 can now be subtracted to give the indices "ni" and "nj" of "nI" and "nJ" in the list of nodes in "item":
