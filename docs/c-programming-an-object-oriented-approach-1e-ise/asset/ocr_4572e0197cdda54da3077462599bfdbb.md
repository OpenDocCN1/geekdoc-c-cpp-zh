Figure 12.4  Two objects in a program when polymorphism is used

```
ptr = new Person (...);
...
delete ptr;        // It deletes Person because ptr is of type Person*.
```

```
ptr = new Student (...);
...
delete ptr;        // It does not delete Student because ptr is of type Person*.
```

In the first case, the pointer *ptr* is a pointer to *Person* type and the *delete* operator can delete the *Person* object. When the *Person* object is deleted, its destructor is called, which in turn calls the destructor of the string class. The characters created in the heap are de-allocated. There is no memory leak.

In the second case, the pointer *ptr* is still a pointer to *Person* type, which means it can delete an object of a *Person* class (which does not exist and nothing happens), but it cannot delete the object of the *Student* class. When the object of the *Student* class is not deleted, its destructor is not called, which means that the destructor of the string class is not called, which means the characters in the heap are not de-allocated. We have memory leak. Note that the memory occupied by the *Student* object will be eventually deallocated when the program goes out of scope, but the pointer to characters becomes a dangling pointer and the system can never delete the memory location created by the characters in the string.

The solution is to make the destructor of the base class virtual, which automatically makes the destructor of the derived class virtual. In this case, the system allows two different member functions with different names to be virtual, and they are both added to the virtual table. Figure 12.5 shows that we have two entries in the virtual table, and when an object in the heap is deleted, the program knows which destructor should be called.

> C++ recommends that we always define an explicit destructor for the base class in polymorphism and make it virtual. Use of virtual destructors prevents possible memory leaks in polymorphism.
