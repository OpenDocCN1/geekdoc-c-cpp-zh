What does all of this have to do with NaN? NaN stands for "Not-a-Number", and it is the result of some operations. Consider this.

```scala
scala> 0.0/0.0
res104: Double = Infinity
```

This is what is happening to cause our error, and it happens when zero test or assignment grades or only one grade have been entered. In general the computer cannot know if this would be out of range so it gives up. The function returns (x-x)/(x-1) where x is Double. How do we fix this? We need to make the average and the averageDropMin function a smaller bit so that we have special cases they should not do division. We can do this by putting expressions in both.

```scala
def average(nums:List[Double]):Double = =
if (nums.isEmpty) 0 else nums.sum/nums.length

def averageDropMin(nums:List[Double]):Double = =
if (nums.isEmpty || nums.tail.isEmpty) 0 else
(nums.sum-nums.min)/(nums.length-1)
```

If you use these versions of the functions things work well. Now to the functional alternative. The imperative version uses var declarations outside of the function. These declarations can be seen by anything in the script that follows them. We properly refer to this as the GLOBAL SCOPE. For small scripts this might not be a problem, but do not want to get into the head of making things global, especially if it is a var or mutable. That is global in a large program can be messed up by any line of code, making it very hard to track certain types of errors. It is better to have our variables declared a LOCAL SCOPE, inside of a function.

If we simply declare the variables inside mainGrades, it will not work when you make a recursive call, you get new versions of all the local variables. Instead, we pass the three lists into the function as arguments. The arguments to a function act just local val declarations except that the value is provided by the calling code.
