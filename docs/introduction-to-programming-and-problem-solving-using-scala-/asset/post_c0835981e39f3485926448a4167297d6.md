Most of the programs that you use on a regular basis would be far less useful if they did not have the ability to read from and write to files. Consider a word processor that could not save your files and let you load them back in later. A program where you had to print output to paper before you closed the program to have any record of what you had done. Such a program would not be very useful, and it would not be used much. That is true even if provided you with a very full set of other capabilities.

The reason for this is that all the work you do without a file sits in the temporary memory of the computer that is given to the application when it runs. When the application is stopped, for any reason, all of memory is lost. It might be given over to other applications or used by the operating system. Whatever happens to it, you no longer have the ability to get it in any useful way.

Files give you the ability to store values from one run of a program to the next. Files can also be used to store information that you do not want to have to write into the source code or just to store amounts of information larger than what will fit in the memory of the machine. Disk drives are much slower than memory so this last part has to be done with a level of care.

# Introduction to Programming and Problem-Solving Using Scala

## 9.1 I/O Redirection

In a certain way, you have already had the ability to make your program deal with files through I/O redirection. When you run the program from the command line as a script, you can have standard input from a file using `<`. You can also make the standard output to a file using `>`. This works nicely if you are going to be entering the same values multiple times or want to preserve the output so you can look at it.

The down side of using I/O redirection is that it is rather limited. You only get to read from one file or write to one. What is, if you decide to read from a file, you cannot also have the user input from the keyboard, or if you decide to have the output to a file, the user will not see anything that is printed on the screen. These limitations make this approach impractical for most applications.

## 9.2 Packages and import Statements

Before we can learn about reading from files and writing to files, we need to learn a little about how code is organized in large projects. Almost everything we have used so far is available in Scala without having to specify where to look. The basic parts of the language are simply available by default. One exception to this was the various read methods. To those without using long names, you can import `io.stdin` at all of the scripts and in the REPL. Similarly, file handling is not available by default. Scala uses packages to organize code. To understand the reason for packages, consider the `List` type that we learned to use in chapter 6. This type is defined by a class written in the Scala libraries that is available to you by default. However, the word `List` is not an uncommon one. Without packages there could be only one type class. Packages allow you to have multiple types that all have the same name, like List, which are differentiated by being in different packages. In the case of List, the one you have been using is technically a `scala.collection.immutable.List`. However, the name `List` could also refer to `java.util.List` or `java.awt.List` from the Java libraries.

These longer names are the fully specified names of types. They specify both a package name and the type name. Packages are typically named in all lower case and the separate subpackages in a hierarchy from broadest to most specific. The List that you have been using sits in the top level package `scala`, which has a subpackage called `collection`, which has a package inside of it immutable. The List type is inside of that subpackage. We will not worry about creating packages in this part. Right now all you need to understand is that they exist and how to use.
