
# Basics of Computers, Computing, and Programming

## 1.5.1 Imperative Programming

The original Programming paradigm was the imperative paradigm. Because this is the paradigm of machine language. So all the initial programs written in machine language were imperative. Imperative programming gives the computer a set of instructions that is to perform. These actions change the state of the machine. This is exactly what you get when you write machine language programs.

The two keys to imperative programming are that the programmer specifically states how to do things and what the values stored by the computer are readily altered during computation. The converse of imperative programming is declarative programming where the programmer states what is to be done, but generally is not specific about how it should be done. The Scala allows imperative style programming and many of the elements of this book will talk about how to use the imperative programming style in solving problems.

## 1.5.2 Functional Programming

Functional programming was born out of the mathematical underpinnings of Computer Science. In the functional programming, the main program is written as a function that receives the program's input as its arguments and delivers the program's output as its result. The first functional languages were based heavily on Alonzo Church's lambda calculus. This is in contrast to imperative programming which bears a stronger resemblance to the Turing machine. "Programming" a Turing machine is only loosely correlated to writing language, but the general ideas of state and having commands that are taken one after the other are present on the Turing machine. Like the lambda calculus, functional languages are fundamentally based on the idea of functions in mathematics. We will see a lot more of the significance of mathematical functions on programming thinking in chapter 4.

Functional languages are typically more declarative than imperative languages. That is that you typically put more effort into describing what is to be done and a less in describing how it is to be done. For a language to be considered purely functional the key is that it has no mutable state, at least not at a level that the programmer notices. What does that mean? It means that functions take values and return values, but do not change anything else along the way. The only thing they do is give you back the result. In an imperative language, little traces of what has been done can be dropped all over the place. Certainly, functional programs have to be able to clean up after themselves. Imperative programs can leave alterations wherever they want, and there is no stipulation that they set things the way they found it. Supporters of functional programming often like say that functional programs are cleaner. If you think of a program as entering your room looking for something, you would never know, because it would leave no trace of its passing. At the end, everything would be as it had started except for the value it returned. The function would have returned the value it was looking for. An imperative program entering your room would not change anything, but more likely than it would move the books and leave your pillow in a different location. The imperative program would change the "state" of your room. The functional one would not.

Scala supports a functional style of programming, but does not enforce it. A Scala program can easily set it up so that it does not leave any trace behind, but if you want to leave traces behind you can. The purpose of this combination is to give you flexibility in how you do things. When a functional implementation is clean and easy you can feel free to use it. However, there are situations where the functional style has drawbacks, and in those cases you can use an imperative style.

## 1.5.3 Object-Oriented Programming

Object-oriented programming is a relative newcomer to the list of programming paradigms. The basic idea of object-oriented programming first appeared in SIMULA67 programming language. As the name implies, it dates back to the 1960s. However, it did not gain much momentum until the 1980s when the Smalltalk language took the ideas further. In the 1990s, object-oriented reality hit it and virtually any new language that is created and expects to use object-oriented features.

The basic idea of orientation is quite simple. It is that data and functions that operate on the data should be bundled together into objects. This idea is encapsulation, and we will discuss it at the end of this book. This might seem like a simple idea, but it enables us of significant extras that do not become apparent until you have worked with it a while.

Object-orientation is not really independent of the imperative and functional paradigms. Instead, object-oriented programs can be done in either a functional or an imperative style. The early object-oriented languages tended to be imperative and most of the ones in use today still are. However, there are a number of functional languages that now include object-oriented features.

Scala is a purely object-oriented language, statement that is not true of many languages. What this means and the implications of it are discussed in detail in later chapters. For most of this book, the fact that Scala is object-oriented will not even be significant to us, but it will always be under the surface.

## 1.5.4 Logic Programming

The fourth paradigm is logic programming. The prime example language is Prolog. Logic programming is completely declarative. As the name implies, programs are written by writing logical statements. It is up to the language/computer to figure out a solution. This is the least used of the paradigms. This is in large part because of significant performance problems. The main use is in artificial intelligence applications. There is indication that logic programming could reappear in languages where it is combined with other paradigms, but these efforts are still in the early stages.

## 1.5.5 Nature of Scala

As indicated in the sections below, Scala provides a mix of different paradigms. It is a truly hybrid language, as the programmer, the ability to solve problems in the way that makes the most sense to you or that best suits the problem at hand. The Scala language directly includes imperative, functional, and object-oriented elements. The name Scala stands for Scalable Language; so, it is not completely out of the question to add them to a library in the future that could support logic programming to some extent if a benefit doing so was found.

## 1.6.1 Summary of Concepts

- Computing has a much longer history than one might expect with roots in mathematics.
- Hardware is the term used for the actual machinery of a computer.
- Software is the term used for the instructions that are run on hardware. Individual pieces of software are often called programs.
- The act of writing instructions for a computer to solve a problem in a language that the computer can understand or that can be translated to a computer understands is called programming.
- Programming is very much an art form. There are many different ways to solve any given problem, and they can be arbitrarily complex. Knowing how to design good programming practices takes.
- There are four broad types or styles of programming called paradigms.
  - The imperative programming paradigm is defined by explicit instructions telling the machine what to do and mutable state values are changed over time.
  - The functional paradigm is based on Church's lambda calculus and functions in a very mathematical sense. Mathematical functions do not involve mutable state.
  - Object-orientation is highlighted by combining data and functionality together into objects.
  - Logic programming is extremely declarative, meaning that you say what you want, but not how to do it.
  - Scala is purely object-oriented with support for both functional and imperative programming styles.
