The number of comparisons in the selection sort and bubble depends only on the size of the data being sorted. It does not depend on the nature of the data. This is not case for the flagged bubble sort or the insertion sort. Sets can vary very different numbers of comparisons depending on the data that is given. For example, if you have a flagged bubble sort array that is already sorted, it will only run it once, doing $n-1$ times. We would call that $O(n)$. Granted, that is a BEST-case scenario.

So what are the average and worst-case behaviors of insertion sort? The outer loop happens $n-1$ times. So we can do a summation much like what we did above. However, the inner loop happens a variable number of times. In the worst-case, which would be getting data in reverse order, the inner loop will run $i$ times and we get the same behavior as with bubble and selection sorts. In the best-case, which is data in the proper order, the inner loop does only one check. $O(n)$, because

```
$C = \sum_{i=1}^{n-1} i = n - 1$.
```

On average we might expect that between extremes, the inner loop will do $i/2$ comparisons. This gives

```
$C = \sum_{i=1}^{n-1} i = \frac{n(n-1)}{4} = \frac{1}{4}n^2 - \frac{1}{4}n$.
```

While this is better than the behavior of the other sorts by a factor of two, it is still $O(n^2)$. This is because doubling the size of the input still makes it four times longer. So good bad is $O(n^2)$? Functions that grow as a polynomial function are referred to in a very general way as being best tractable, because you can use them for fairly large values of $n$ and still expect the calculation to finish in a reasonable time. We will see later on not all algorithms have this behavior. However, we have no problem using these sorts for $Arrays$ with 100 or 1000 values. As you continue to add zeros, these methods will prove to be too slow. Each factor of 10 in the size causes the program to do 10 times as many comparisons and generally leads to it taking 100 times longer to complete. As such, these methods become slow if $n$ gets bigger than a million. Fortunately, there are alternatives.
