# 16.5 Implementing the Pac-Man™ Example

Like the example, our version of Pac-Man is written as an application and is broken across multiple files. Not everything exactly follows the design that was laid out at the beginning of the chapter. This is to be expected. When you go to implement your designs, you often find things that were missed or realize that some pieces do not fit together the way that you expected them to. In this case, we also introduced some Scala concepts between the design presentation and this section that have altered how we built things.

We start by looking at the Game, which has been implemented as a singleton object with a main method that is used to run the program. The main method includes ScalaFX code for the GUI and a timer to make the code run as well as handlers for the keyboard input.

Lines 10-22 have basic declarations, an instance of that type. In the main method on lines 24-61, we use a JFXApp and the normal setup. Much of this should seem familiar from chapters 11 and 12. The logic that seems odd is line 50. In earlier examples, we would have just set lastTime = t. For this example we used the "game ticks" to happen close to 0.1 seconds after posting. The timer would fire times before it got to 0.1 and often got to values around 0.115. The simple form would have caused the time to "slip" by 0.015 seconds in that situation. This might not seem much, but it is a significant fraction of 0.1 seconds that we desire. The extra math on line 50 sets lastTime to the time at 0.1 instead of however far we might have gone past, so the whole game stays close to being. Line 53 shows that conditions for stopping the timer when the player runs out of lives is worth noting that while we are presenting one file at a time, this is not how it was written. Development moves from one file to another and again, as features are added. This approach does not just help with logic, but helps with getting things done. You should run program often to make sure it works. Do not go on to the next feature until you have current state. Focusing on a single task can be challenging, but helps tremendously with process. Next is Maze, which is declared as class. This class does not take any arguments as it sets up default configuration. Lines 4-9 declare a number of private vars, setting them to default, except that lines 11-12 declare initMap and initContents methods that get those values. Earlier iterations of the code set those values at point of declaration, but it is useful to be able to tell them.
