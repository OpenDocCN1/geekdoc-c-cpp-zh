# Introduction to Programming and Problem-Solving Using Scale

One thing to notice about this is that we did not specify the types on x and y. Because Scale knows the second argument to inputAndCount is a function that takes Int values. As, it assumes that x and y must be of Int.

If you remember back to section 4.5 on function literals, will you recall there is an even shorter syntax for declaring them that only works in certain situations. That was the syntax that uses _ as a placeholder for the arguments. This syntax can only be used if each argument occurs once and in order. That is true here, so we are allowed to use the shorthand. This simplifies all the code way down to this.

```
scala= inputAndCount(0, _*)
res5=(Int, Int)= (12,3)
```

Of course, the reason for doing this was that we could also do products without having to write a function. The product function differed from the sum function in that the base case was 1 instead of *. If we make those two changes to what we did above, we will see that we have created a single function that can either sum or product.

```
scala= inputAndCount(1, _*)
res6=(Int, Int)= (60,3)
```

Not only did we succeed here, we did so in a way that feels satisfying to us. Why? Because our abstraction is created in a minimal way and only the essential variations have we expressed. We do not have to do a lot of typing just to use the abstraction. It is not much longer to call inputAndCount than it was to call sumAnd or productCount. In addition, the only things we changed between the two were changing the 0 to 1 and the + to Those were the exact same things we had to change if we had done the full copy and paste of functions. This means that the content we want is coming through clearly and is not complicated with a lot of overhead.

The inputAndCount function is what we call a higher order function. That is because it is a function that uses other functions to operate. We provide it with a function to help it do its job. This type of construct has been found mostly in functional languages. With the addition of lambda expressions, mainstream languages also allows this type of functionality.

You might say you had to duplicate the code to prevent that? Is this really all that smell? The answer, with a sum and a product, is "no". A single code duplication is not the end of the world. However, if I ask you to complete versions that return the minimum or the maximum, what do you do? Without the abstraction, you get to copy and paste two versions of the code and make similar minor changes to them. With the abstraction, you just call inputAndCount with different arguments. The question of whether it is worth it to abstract really depends on how much you expect in the future. If the abstraction does not take much effort it is probably worth doing to start with because it is often hard to predict if you will need to extend something in the future. You might not feel this what we do in this, but it becomes very significant in professional development when you are not told up front exactly what is wanted of you and when you are, the customer is to change their mind later in the process.
