The more you cover your test set, the more confident you are that your code is correct. The levels of coverage in this list are basically minimal standards. If your tests have not gone to every function or statement, then there are parts of the program that you have not tested. Going beyond those you start looking at different ways for things to happen. There are several different places from which a function can be called. Covering conditions makes sure that all the possibilities for why different parts of the code might have been exercised.

If you stop and think about it, you will probably realize getting condition/decision requires quite a few test cases. These options potentially leave a lot of possibilities unchecked as they do not free loops to handle different numbers of times. The ultimate form of coverage, path coverage, is generally unattainable for any program of even modest size. Having path coverage implies that you have tested every path that the execution could through the code. Consider a simple function with three statements after the one. Another path through the code would have all three to true. Another path might have the first true and the last false. There are eight different paths through such a function. If you add another if, the number of paths doubles to 16. Path coverage grows exponentially many cases can be tested as conditional statements are added. If that was not enough, a while loop or recursion generally creates an infinite number of paths the code could execute zero, one, or more times. Each one is a different path through the code. As such, path coverage is typically viewed as an unattainable ideal for beyond simple functions.

Due to the challenges of getting good coverage on large collections of code, it is common to do testing on small blocks at a time. Each unit of the code is a test suite written for it checks its functionality independent of other parts of the code. The test suites are run over and again during development to make sure that no new changes break what was written.

The real advantage of Unit testing is that in a small unit, one can hope to get fairly complete path coverage. However, it is not sufficient to do Unit tests. As the units are assembled, they have to be put through integration tests that test how the pieces work together. It is very possible for two units of code to work perfectly in isolation and fail miserably when they are put together.

numList.filter(_>70).map(_-10).sum

This expression makes two Lists and runs through Lists a total of three times. It first runs through numList with the filter and produces a new List of the elements that pass the filter.
