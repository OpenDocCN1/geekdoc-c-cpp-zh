# 1.5.1 Imperative Programming

The original Programming paradigm was the imperative paradigm. Because this is the paradigm of machine language. So all the initial programs written in machine language were imperative. Imperative programming gives the computer a set of instructions that is to perform. These actions change the state of the machine. This is exactly what you get when you write machine language programs.

The two keys to imperative programming are that the programmer specifically states how to doings and what the values stored by the computer are readily altered during computation. The converse of imperative programming is declarative programming where the programmer states what is to be done, but generally is not specific about how it should be done. The Scala allows imperative style programming and many of the elements of this book will talk about how to use the imperative programming style in solving problems.

# 1.5.2 Functional Programming

Functional programming was born out of the mathematical underpinnings of Computer Science. In the functional programming, the main program is written as a function that receives the program's input as its arguments and delivers the program's output as its result. The first functional languages were based heavily on Alonzo Church's lambda calculus. This is in contrast to imperative programming which bears a stronger resemblance to the Turing machine. "Programming" a Turing machine is only loosely correlated to writing language, but the general ideas of state and having commands that are taken one after the other are present on the Turing machine. Like the lambda calculus, functional languages are fundamentally based on the idea of functions in mathematics. We will see a lot more of the significance of mathematical functions on programming thinking in chapter 4.

Functional languages are typically more declarative than imperative languages. That is that you typically put more effort into describing what is to be done and a less in describing how it is to be done. For a language to be considered purely functional the key is that it has no mutable state, at least not at a level that the programmer notices. What does that mean? It means that functions take values and return values, but do not change anything else along the way. The only thing they do is give you back the result. In an imperative language, little traces of what has been done can be dropped all over the place. Certainly, functional programs have to be able clean up after themselves. Imperative programs can leave alterations wherever they want, and there is no stipulation that they set things the way they found it. Supporters of functional programming often like say that functional programs are cleaner. If you think of a program as entering your room looking for something, you would never know, because it would leave no trace of its passing. At the end, everything would be as it had started except for the value it returned. The function would have returned the value it was looking for. An imperative program entering your room would not change anything, but more likely than it would move the books and leave your pillow in a different location. The imperative program would change the "state" of your room. The functional one would not.
