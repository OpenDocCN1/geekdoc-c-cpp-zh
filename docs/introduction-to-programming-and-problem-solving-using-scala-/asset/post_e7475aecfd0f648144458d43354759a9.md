
# 15.7 Sorts

In chapter 13 we used loops to make our iteration. We only used recursion when working with Lists, and the sorts were longer than the imperative versions. We could also write those sorts recursively using Arrays, but then the use of recursion is only a change in presentation. It does not really affect how the sorts run or how efficient they are. The recursion in these functions is only used for iteration, nothing more. However, recursion also opens the door to more efficient sorts. The next two subsections describe of these.

## 15.7.1 Divide and Conquer Sorts

Recursion that calls itself multiple times opens up a new style of problem solving called DIVIDE AND CONQUER. The idea is exactly what the name sounds like. You take a big problem, divide it up, conquer/solve the pieces, then build a solution to the larger problem from the solutions to the pieces. The divide and conquer approach is very general and can be applied to many types of problems. In this section, we will look at two different algorithms that are all merge.

### 15.7.1.1 Merge Sort

The first sort that we consider is MERGE SORT. The general idea of merge sort is that we have a collection that we break into two roughly equal pieces. Each of those pieces is sorted individually and the results are merged back together. This is a fast algorithm because the merge operation is O(n). The reason for this is when you find the lowest element from each collection, you do not have to go through all the elements, you only need to consider the elements at the two ends. To find the next element you go again and make only n - 1 comparisons. The fact that you are repeatedly cutting the collection in half means that you get down to a single element in log(n) cuts. This gives an overall performance of O(n log n). For large values of n, this is much better than the O(n²) sorts considered earlier.

There is one problem with merge sort: it cannot be in-place. Recall that done in-place means modifying the original collection without additional memory. Merge sort requires additional memory proportional to n to complete. Memory usage to do that is a bit complex so it is not presented in this book. In this chapter, we will use the inability to do in-place as an excuse for using Lists, which are immutable. The first solution that we will look at is recursive. It has a recursive merge function that takes a List [Int] and returns a List [Int]. The sort uses recursive merge to put the pieces together.

Listing 15.3: mergeSort.scala
```scala
def merge(lst1: List[Int], lst2: List[Int]): List[Int] = (lst1, lst2) match {
  case (Nil, _) => lst2
  case (_, Nil) => lst1
  case (h1::t1, h2::t2) =>
    if (h1 < h2) h1 :: merge(t1, lst2)
    else h2 :: merge(lst1, t2)
}
```

```scala
def mergeSort(lst: List[Int]): List[Int] = lst match {
  case h::Nil => lst
  case _ =>
    val (l1, l2) = lst.splitAt(lst.length / 2)
    mergeSort(l1) ::: mergeSort(l2)
}
```

Both functions use pattern matching for the different cases. This makes them nice, short, and easy to read. Unfortunately, the recursive version of merge sort has to allocate a new List for every element. That means this version cannot scale to large sizes. To get around this limitation we need to use a more imperative merge that works with a while loop. Such a version might look like the following:

```scala
def merge(lst1: List[Int], lst2: List[Int]): List[Int] = {
  var l1 = lst1
  var l2 = lst2
  var ret = List[Int]()
  while (l1.isNotEmpty && l2.isNotEmpty) {
    if (l1.head < l2.head) {
      ret += l1.head
      l1 = l1.tail
    } else {
      ret += l2.head
      l2 = l2.tail
    }
  }
  if (l1.isNotEmpty) ret ++ l1 else ret ++ l2
  ret
}
```

This version is not as pretty and is about twice as long. However it handles significantly Lists making it useful if you actually have a large set of data. One thing to note about merge sort is the way in which it works. As the recursive calls go down the stack, very little happens. The input gets split in half and those two halves get passed down. This repeats until a single element remains. The real work happens as the recursion pops up the stack. Before a function can return, it calls merge which does the work. So if you picture in your head the downs are not associated with much work.

## 15.7.1.2 Quicksort

Another divide and conquer is QUICKSORT. The idea of quicksort is to pick a special element the pivot then move it to the correct location with all the elements that are less than it before and all those that are greater than it after. Those elements to either side are not yet sorted so recursive calls are made to sort each of them. The recursion terminates when it gets to a single element.

Unlike merge sort, quicksort can be done in-place. However that is more complex and is not covered in this book. For now we will make the quicksort like our merge sort and work on a List, for which the idea of being in-place does not make sense.

The quality of a quicksort depends largely on the selection of a pivot. A good pivot would be in the middle of the collection to cut in half. A really bad pivot would be the minimum or maximum element which does nothing to split the data and only pulls out the next level of recursion. Keeping with the idea of simplicity for the implementations in this chapter, we will use the first element as the pivot. This is not a good way to do this in general and can lead to very bad behavior on sequences that are already sorted.

With these simplifications we can write a version of quicksort with the following code.

Listing 15.4: quicksort.scala
```scala
def quicksort(lst: List[Double]): List[Double] = lst match {
  case Nil => Nil
  case h::Nil => lst
  case pivot =>
    val (less, greater) = lst.partition(_ < pivot)
    quicksort(less) ::: (pivot :: quicksort(greater))
}
```

The pivot is set to the head of the List. We use partition to split the rest of the elements that are less than the pivot and those that are not. Finally, the quicksort on those two subsets and pulls the whole together into a result. The result is a short and simple sort function that actually works well on random data.

It is worth asking what order of this sort really. Unlike the merge sort, the performance of our quicksort can vary dramatically depending on the input. Like the merge sort, each level of the recursion leads to O(n) work. This case is when the pivot is partition and sticking Lists together. If the pivot is in the middle of the values, each level is cut in half and we get O(log n) levels for recursion and O(log n) overall performance. For random data, this is the expected behavior. However, our simple pivot selection can lead to very poor behavior and this sort is O(n²) when it is already sorted.
