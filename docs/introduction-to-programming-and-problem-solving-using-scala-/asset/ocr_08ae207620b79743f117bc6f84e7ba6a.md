# 4.6 Side Effects

In purely functional programming, a function takes inputs and calculates a value. The value it returns depends only on the arguments the function does not do anything but give back value. Often in programming, functions will do other things as well, or return different values for the same inputs. These types of functions are not technically "functional". When they do other things we refer to them as SIDE EFFECTS. This terminology is like that of medications.

However, it may have other effects called the side effects. While the effects of a medication typically not desired, there are times when effects of functions are desired. The simplest example of such is this printing. The print statement does not return anything. It sends information to output. That is a side effect.

It is possible to have functions that return a value and have side effects. However, quite frequently you will find functions with side effects do not return any. To Scala their result is Unit. The Unit is a type that represents an object that carries no information. The Boolean type is the simplest type that carries information as it could be true or false. The Unit type does not carry any information because there is only one instance of it, which is written as ().

Here is a simple example of a function that includes side effects and results in Unit.

```
scala def introduce(name:String):Unit = {
  println("Hi, my name is "+name+"")
}

introduce:(name:String)Unit
\scala introduce("Lisa")
```

Hi, my name is Lisa.

This is common in non-functional programming. Indeed, some languages include a special construct, the PROCEDURE, for this.
The other form of side effect is an assignment. At this point it means an assignment to a var. One could write a function that has the primary purpose of changing the value of some var that is declared before outside the function. When a var is declared outside of any block of code, it is said to have GLOBAL SCOPE. As was already mentioned, this is a poor way to do things as it is it bug prone, and makes it harder to reuse the function. As a general rule, global scope should be avoided for anything that can be changed.

> Due to the way that Scala scripts are compiled, global vars are actually in scope everywhere, but they are not initialized until the point of declaration. For this reason, you should not use them until after the point of declaration.
