
# Searching for Doubles (Advanced)

Careful readers might have noticed between the section on sorts and the section on searches, a small change was made. The sorting section used an Array[Double] while the searching section used Array[Int]. The choice of Double type for sorting was motivated by the fact that they are easy to generate and visualize. However, they are not for searching. This is due to the nature of the Double type. In our discussions we have only presented the Double type we use for when a fractional part is required. We have glossed over the details of what is happening with the Double type. To understand the reason Doubles are not good for search algorithms requires us to dig a bit deeper into what we-

The Double type stands for DOUBLE PRECISION FLOATING POINT NUMBER. The Float type, which we have generally ignored, is a SINGLE PRECISION FLOATING POINT NUMBER. The Float type can also represent fractional numbers, but it has a smaller range and lower precision. As all numbers on a computer, floating point numbers, be single or double precision, are really stored in binary. The best way to think about floating point is to think of numbers in scientific notation. In decimal, you can think of a number in scientific notation as being in the following form,

(-)*m*10^

where s ∈ [0, 1], 1 ≤ m < 10 or m = 0. We call s, m, and e the exponent. Not much changes when the number goes to binary except that s, m, and e are stored in bits instead of decimal, and we want powers of 2 instead of 10. So scientific notation in decimal would be

(-1)*m*2^

This does not explain why it is hard to do searching with a floating point number. The key to that comes from the fact that we only have a finite number of bits to use to store m. To understand the implication of this, consider a situation where you only have 7 decimal digits to write m. Now try to write the decimal form of the fraction 1/3. You would write (-1)*3.333333*10^-1. This is not exactly the same as 1/3, but it is as close as you get with only 7 digits. The reality is to write 1/3 in decimal you need an infinite number of digits. Lots of fractions require an infinite repeating representation in decimal.

This same thing happens in the binary computer. With infinite binary digits can lead to some interesting results for fractional numbers that cannot be perfectly represented. To understand this, consider the following example from the Scala REPL.

```scala
scala> 0.1 == 1.0 - 0.9
res: Boolean = false
```

Mathematically you expect the expression 0.1 == 1.0 - 0.9 to be true, but the decimal value 0.1 is an infinite sequence in binary. As such it is truncated at some point and we get an approximation. Similarly, 0.9 cannot be represented perfectly either. The result is that subtracting 0.9 from 1 gives a value that is not exactly the same as the approximation of 0.1. To see how different the two we can subtract from one other.

# Sorting as Searching

```scala
scala> 0.1 - (1.0 - 0.9)
res1: Double = 2.775557615628914E-17
```

This is an extremely small number, but it is not zero, and because it is not zero, the two are not equal.

This is a well-known challenge with floating point numbers and people who do numeric work have to check for equality as the results are generally unpredictable because of rounding that is part of even the simplest arithmetic. For our discussion, what we have seen is evidence that == in a search algorithm the Double type is likely to produce unexpected results. The next question is, how we get around that.

The basic idea behind the solution is that we generally consider floating point numbers to be equivalent as long as they are close enough to one. But how close enough? That depends on whether you are working with single or double precision numbers. Math the Greek symbol ε, epsilon, is typically used to represent a vanishing small value. In computer numerics it is used to describe the smallest value you can add to one and get a greater number. If you go smaller than ε, the value will be rounded off in the sum and all you will get is one. Here is code that declares and calculates this for both the Double and Float types.

```scala
scala> val doubleEpsilon = {
  var eps = 1.0
  while (1.0+eps > 1.0) eps *= 0.5
  eps*2.0
}
doubleEpsilon: Double = 2.220446049250313E-16
```

```scala
scala> val floatEpsilon = {
  var eps = 1.0f
  while (1.0f+eps > 1.0f) eps *= 0.5f
  eps*2.0f
}
floatEpsilon: Double = 1.1920982955078125E-7
```

Any single operation can be expected to have errors on the order of ε. When you string many operations the error grows, as so is standard to consider two values as equal if the relative error is less than the square root of ε. This means you only trust the bits of precision in the number. As such, the following values are what you really find important.

```scala
scala> val sqrtDoubleEpsilon=math.sqrt(doubleEpsilon)
sqrtDoubleEpsilon: Double = 1.490161938047656E-8
```

```scala
scala> val sqrtFloatEpsilon=math.sqrt(floatEpsilon)
sqrtFloatEpsilon: Double = 3.452669830124393E-4
```

For simple order of magnitude purposes, you might remember that for Double it about 10^-8 and for Float it is 10^-4. We will use this approximate value in the code. How could we modify our searches to work with the Double type? We simply to replace the check for equality with a check of the relative difference between the two. The linear search would look like the following.

```scala
def linearSearch(a:Array[Double],value:Double):Int = {
  var i = 0
  while (i < a.length && (a(i)-value).abs > 1e-8) {
    i += 1
  }
  if (i > a.length) -1 else i
}
```

# Lists

The sorts so far have been imperative, mutating Arrays. These same sorts can be written in a functional manner using Lists. The fact that the List type is immutable means that we cannot alter the argument passed in. Instead, we have to build a new List that has the values in sorted order, and that sorted List is the result of the function. More efficient sorts with Lists will be explored in chapter 5. As before, we start with bubble sort. The following code shows a bubble sort that stops when it goes through and are no more swaps.

```scala
def bubbleSort(list:List[Double]):List[Double] = {
  def swapper(list:List[Double]):(Boolean, List[Double]) = list match {
    case Nil => (false, Nil)
    case h1::h2::t =>
      if (h1 < h2) {
        val (swap, rest) = swapper(h2::t)
        (swap, h1 :: rest)
      } else (true, h2 :: h1 :: t)
  }
  val (swap, swapped) = swapper(list)
  if (swap) bubbleSort(swapped)
  else swapped
}
```

The swapper returns a Boolean and the List that results from a single pass. The Boolean tells us if there were any swaps done during this pass. The first two cases forming a common theme in these sorts both the empty list and all lists with just one element are sorted, they base cases. If there are at least two elements on the List, we compare them, and if they are in the right order, we do a recursive call on all elements after the first and give back which is first consed onto. In that situation, was not a swap, so the value of Boolean is whatever we get from further down. If the first element should go after the second one, the Boolean is true because there was a swap, and the List is the second element consed onto the element of the recursive call. The whole function works by calling swapper on the result if there was a swap. If it was not a swap, it returns the resulting List. Note that this function does not stop like the imperative version did. This code could be edited to, but it is a bit more challenging. 

Next is the selection sort, which is implemented as a min-sort.

```scala
def minSort(lst:List[Double]):List[Double] = {
  def findAndRemoveMin(lst:List[Double]):(Double, List[Double]) = lst match
    case Nil => throw new Exception("Find and remove from Nil.")
    case h:Nil => (h, Nil)
    case h:t =>
      val (min, rest) = findAndRemoveMin(t)
      if (h < min) h::rest else (min, h::rest)

  lst match {
    case Nil => lst
    case h:Nil => lst
    case h:t =>
      val (min, rest) = findAndRemoveMin(lst)
      min::minSort(rest)
  }
}
```

This code is built around a helper findAndRemoveMin, which returns a tuple of the minimum value in the list and the list elements other than that minimum value. It only makes sense to call on a list with at least one element, hence the case for Nil which throws an exception. The way this function works is that it recurses to the end of the list, and begins returning the minimum and reduced list from the end forward. If the current element is smaller than the min after it, it becomes the min and the old min is consed to the returned list, otherwise the min stay the same and the current element is consed to the returned list.
