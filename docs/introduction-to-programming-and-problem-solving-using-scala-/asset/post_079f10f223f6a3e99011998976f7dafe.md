You can find a full description of L-systems in “The Beauty of Plants”, which can be found on-line at http://algorithmic.org/papers/#abop. The first chapter has all the material that you will need for this project and a later one.

In the last turtle you made it so that you could use a turtle to draw figures from Strings using the characters ‘F’, ‘f’, and ‘+’. L-systems are formal grammars that we will use to generate strings that have interesting representations. An L-system is defined by an initial String and a set of productions. Each production maps a character to a String. So the production F -> F-F++F-F will cause any F in a String to be replaced by F-F++F-F. The way L-systems works is that all productions are applied at the same time to all characters. Characters that do not have productions just stay the same.

So with this example you might start with F. After one iteration you would have F-F++F-F-F. You would have F-F++F-F-F-F++F++F-F-F++F-F after the second iteration. The next iteration will be five times longer than that. The Strings in an L-system grow exponentially in length. As a result, you probably want to have the length of the turtle move for an F or f get exponentially shorter. Start with a good value like 100 pixels and divide by an appropriate value for each generation. For this example dividing by a factor of 3 is ideal. This one also works best with a turn angle of 60 degrees.

The productions for an L-system can be implemented as List[[Char, String]]. You can use the find method on the List and combine that with flatMap to run through generations of your String. You decide how elaborate you want your GUI to be and if users should be able to enter productions or if they will be hardcoded.

Back in chapter 5 we got our introduction to recursion. At that point we used recursion to provide iteration. In chapter 8 we learned how to produce iteration using loops and used that technique more than recursion. If the only capacity of recursion was iteration it would not be of interest in Computer Science because loops would be a complete substitute. However, that is not the case. Recursion allows us to express a lot more than just iteration, and because of this, recursion is a critical tool in writing programs.

## 15.1 Memory Layout To have a proper understanding of recursion, it is helpful to have a mental model of the way that the memory of programs is laid out. The memory of the computer is basically like a huge array of bytes. It is shared between the operating system and many different programs. Different parts of memory can be allocated for different things or associated with different devices. Scala hides some of the intricacies of memory from you. It is not a language designed for low-level programming. At some point in your computer science training you will learn about the details of computer memory and a language that reveals those details. For our purposes here, we will only care about the organization of memory inside of a single program.

The memory for a program is broken into two broad pieces, the STACK and HEAP. These terms were chosen intentionally, and the images they invoke in your mind are probably fairly accurate. A stack is orderly with items placed on top of the previous. A heap is much less organized with items placed at random. Local variables and function arguments are allocated on the stack. As was discussed in section 7.7, the memory model in Programming and Problem Solving Using Scala is such that the variables are references and they refer to objects. In this memory, the objects are allocated on the heap. Every time a new function is called, the memory for the arguments and the local variables, with some memory for bookkeeping, is allocated in a block that is referred to as the STACK FRAME. If that function calls another, another frame is allocated on top of it. When a function returns, the stack frame for that function is freed up. That same memory will be used for another function.

This should help explain the output from a runtime error. The stack implicitly keeps track of those functions stacked on top of the one that called it. That is what gets printed in the file name and line number. This memory of functions that have been called previously and the values of variables in these functions is recursive functions operating properly.

The objects on the heap are allocated in free spaces. The memory for objects is freed automatically when the object is no longer in use. The automatic freeing of memory is accomplished by a process GARBAGE COLLECTION. An object can be collected if it can no longer be reached by following references that start on the stack. Not all languages include garbage collectors. In those that do not, the programmer is responsible for freeing memory that was allocated on the heap.

## 15.2 Power of Recursion To understand the real power of recursion and where this power comes from, we need to revisit some code from the end of chapter 5. Early in that chapter we used a recursive function to count down from a specific number using a single argument. The code for doing that looked like

```scala
def countDown(n:Int):Unit = {
  if (n>=0) {
    println(n)
    countDown(n-1)
  }
}
```

As long as the argument has not gotten below zero, this function prints the number and counts down. We also wrote code to count up using two arguments where one argument was incremented for each subsequent call. At the end of the chapter we were presented with the following code.

```scala
def count(n:Int):Unit = {
  if (n>=0) {
    count(n-1)
    println(n)
  }
}
```

You were told to enter this code and run it to see what it does. If you did, you might have been rather surprised to see that this count counts up. That seems surprising because the argument is clearly decrementing. The reason this is count up has to do with the memory of the computer and in particular the call stack.
