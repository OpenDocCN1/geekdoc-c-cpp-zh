
## Recursion for Iteration

Every call to a function typically takes a little memory on what is called the stack to store the arguments, local variables, and information about where the call came from. If a recursive function calls itself many times, this can add up to more than the amount of memory set aside for this purpose. When this happens, you get a stack overflow and your program terminates.

Scala will optimize this away for recursive functions that have nothing to do after the recursive call. You can convert a recursive function that is not tail recursive to one by passing in additional arguments. This is how we can demonstrate how this would be done on the sumAndCount function on page 113. The original version is not tail recursive because it does one of those which would prevent the function from being tail recursive: addition to after the recursive call. To change this, we can pass in the sum and count as arguments. It produces the following:

```
def sumAndCountTailRec(sum:Int, count:Int):(Int,Int) = {
  var n = readLine()
  if (n!="quit") {
    sumAndCountTailRec(sum+n.toInt, count+1)
  } else {
    (sum, count)
  }
}
```

Note that when you call this function, you have to provide initial values for sum and count, both of which should probably be. It is possible to hide this by nesting functions, but that is a topic for later.

If a function really needs to be tail recursive, you can tell Scala with an annotation. Annot are advanced features that we do not deal with in this book. To do this, you first need to import annotation.tailrec, then you can put @tailrec from any function that must be tail recursive. If Scala cannot make the function tail recursive, it will give an error.

## 5.5 Matching

The if expression is not the only conditional construct in Scala. There is a second, far more expressive, conditional construct, match. While the if construct picks between two different possibilities, based on whether an expression is true or false, the match construct allows you to pick from a larger number of options to see if a particular expression matches any of them. The term “matches” here is vague. Indeed, the power of the match construct comes from something called PAT MATCHING.

The syntax of the match expression in its simplest is as follows:

```
expr match {
  case pattern1 => expr1
  case pattern2 => expr2
  case pattern3 => expr3
```

The value of the expression before the match keyword is checked against each of the different patterns that follow the case keywords in order. The first pattern that matches will have its expression evaluated and will be the value of the whole match expression.

We can use this repeat our example with chapter 3 related to the cost of food at a theme park.

```
def foodMatch(item:String,size:String):Double = item match {
  case "Drink" => size match {
    case "S" => 0.99
    case "M" => 1.29
    case _ => 1.39
  }
  case "Side" => size match {
    case "S" => 1.29
    case "M" => 1.49
    case _ => 1.59
  }
  case "Main" => size match {
    case "S" => 1.99
    case "M" => 2.59
    case _ => 2.99
  }
  case _ => size match {
    case "S" => 4.09
    case "M" => 4.29
    case _ => 5.69
  }
}
```

When an ever function is a single match, it is customary to put the start of the match after the equals sign as one inside. Here we have the four different cases, each with its own match on the size. The thing that might seem odd here is the use of the underscore. underscore as a patterns matches anything. This is done so that the behavior would agree with what we have in the if version it defaulted to "Combo" as the item and "Large" as the size.

This example shows that the match expressions can be nested, and the _ can be used to match anything. There is a lot more to the match expression, the following example shows how to use match cost responses to whether you might buy different food items.

```
def buy(String, Double):Boolean = food match {
  case ("Steak", cost) if (cost < 10) => true
  case ("Steak", _) => false
  case (_, cost) => cost < 1
}
```

This is a very limited example, but food is a tuple, and it demonstrates several aspects of match that are worth noting. It pulls the two items out of that tuple. That is part of pattern matching. We will use this one when we have other things that work as patterns. The second thing we see is that if we put a variable name in the pattern, it will match with anything and it will be bound to the value of that thing. In example, the second element of the tuple in the first and third cases is given the name count variable could appear in the expression for the case as in the last case we will buy anything for a dollar. It can also be part of if that "guards" the case. The pattern in the first case matches anything that has the word "Steak" as the food. However, if it means we will only use that case if the cost is less than 10. Otherwise, it will not.

## match versus switch

If you are familiar with other programming languages you might have heard of switch. On the surface, match seems like switch, but match is far more powerful. Here is a simple example where we do what the name implies. This begins with a try block that does and it is followed by a catch block with different cases.

```
def countDown(n:Int):Unit = n match {
  case "quit" =>
  println("Exiting...")
  case i =>
  println(i)
  countDown(i - 1)
}
```

This recursive function will call itself repeatedly until the user enters a valid integer. This uses a different type of pattern in the case, which one only matches a certain type.

## 5.6 Bad Input, Exceptions, and try/catch

At this point, you have noticed that try/catch is an expression with a value. NumberFormatException is just one of Exception. There are many others that occur, and you can even create your own types. We generally assume users will input invalid data. Here is a very basic example where we try read an integer and give back

```
val num = try {
  readInt()
} catch {
  case => 0
}
```

As this shows, the try/catch is an expression. One point to keep in mind about this is the values given back by different cases need to match the last exception of the try block. If you run this code, you will get a warning about catching all Throwables. Catching with a case is not good form. There are some things that you should not be catching because you cannot do anything to fix them. An example would be OutOfMemoryError. If you run out of memory, just returning zero is not going to save the program. You can fix this by specifying the type of the pattern for the case as shown below.

You could also print the normal from the exception by giving a name to the exception in the case associated with it. All exception objects have a method called printStackTrace.

```
val num = try {
  readInt()
} catch {
  case e =>
  e.printStackTrace()
  0
}
```

This can be especially useful during debugging as that stack trace includes a significant amount of useful information. Both of these examples have the pitfall that they give back a value of zero when anything goes wrong. If you really need to have an integer and only want to handle NumberFormatException, you might consider code like this:

```
def readIntRobust():Int = try {
  readInt()
} catch {
  case e:NumberFormatException =>
  println("That was not an integer. Please try again.")
  readIntRobust()
}
```
