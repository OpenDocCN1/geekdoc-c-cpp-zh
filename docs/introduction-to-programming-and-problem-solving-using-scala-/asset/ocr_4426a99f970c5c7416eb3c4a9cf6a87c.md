There are many different ways to think about object-orientation in programs. It is common to have beginners think of description of the problem and the nouns in the description objects while the verbs are methods on these objects. This is a bit restrictive, but it can be useful. A better description is that you should think of objects as having certain responsibilities, and they package the data and functionality associated with a particular responsibility. Whenever you want to think about it, it helps to go through some examples.

# 16.1.1 Analysis and Design of a Bank

We begin with a very standard example of a bank. Before we can really figure out what the code looks like, we need to know more about the problem that we are trying to solve. Without a proper description of the problem, you really do not have any chance of solving a problem. properly defining the problem that you are going to solve in natural language is called analysis which was introduced in section 6.6. Analysis is one of the first steps in any software development effort. It is something that has generally been done for you in this book.

When designing solutions to problems, programmers often need to be concerned with how user friendly they are for the people who will be using them. However, we are not going to worry too much about the user interface for them, but instead focus on the type of functionality that a simple bank system should have. We need to represent a bank where people have accounts. Our bank example has only two types of accounts: checking and savings. Customers can make deposits to and withdraw from these accounts. Each customer can have multiple accounts. The bank itself needs to provide ways to look up customers and accounts.

A proper analysis of a real bank system would be a much more involved process and you would need to gather more detailed information. What we have here is sufficient for our purposes. We can make details as we go. If you were writing this for a real customer, you would need to get them to actually spell out a lot more details "making it up" would be disastrous.

Once you have a proper natural definition of your problem, you can start thinking about how to break it up and focus on here in your programming language. This is the design phase, and what we really want to focus on here. Our previous efforts have been non-object-oriented. When we thought about the problem, we considered the grouping of data along the functions that we would write to deal with the problem. That changes when we approach the problem from an object-oriented standpoint. All of our functions will change into methods which act on the data members grouped by the type.

Given the analysis from above, there are fairly obvious things that jump out to you. They are the account, the customer, and the bank itself. We will consider each of these and try to figure out what data members and methods each one should have. The data that we will put into them will be similar to what you might have done in our previous treatment of case classes. The real change here is that the logic is no longer in separate functions, but is moved into the classes themselves in the form of methods. As a general rule, functions that deal closely with the data are going to move inside of our type to become methods. Any function that might mutate an object should definitely become a method.
