## 13.2.2 Binary Search

Even computers are very fast, linear search is far from ideal, mainly because searching is that is done so frequently. If the data is not ordered in any way, linear search is your only option. To understand this, imagine you have a manual phone book and asked to find the person who has a given name. Due to the fact that phone books are not ordered by phone numbers, your recourse is to go through every line and check the names against what you are looking for. In reasonably sized city this is something nobody would actually undertake.

If this were the only way to look through a phone book people would not bother to keep them. However, people keep telephone books because they rarely look things up by name. Instead, people normally look up by name and the telephone book is sorted by name. This ordering of the elements can lead to much more efficient searches. You might not be able to write a guide for how really you look up in a telephone book, but we can consider your first step and use as direction for writing an efficient algorithm.

Given a large phone book, you will open it up and look at what is on the page you open. And so is good that you will not get exactly the right page. However, comparing what you are looking for is on the pages gives you a significant piece of information. If what you are looking for comes earlier in the alphabet what is on the page you will only look at other pages before that one. You basically throw everything out of your search without even looking at it. Similarly, if what you are looking for comes after the page you have opened you will only consider pages after the current one. You will generally repeat this process in a manner that is not easy to describe in an algorithm just because your method of picking pages might be impacted by things like the binding of the book and whether one page sticks out a bit than another.

>  Thanks to rapidly changing technology and remarkable changes in computer speed and usability, it is not clear whether people are bothering to keep phone books anyway.

The idea of looking at a location and considering things before or after it based on a sorted order can be used to create fast searching algorithms. The most general of which is the BINARY SEARCH, you keep track of elements that you are considering by two integer indices. We will call them start and end. At any time, you know the value you are looking for, if it is present, it will be an index in the range $i \in [start,end)$. If we are searching the Array, initially start is 0 and end is the length of the Array. We code the midpoint of the range, $mid=(start+end)/2$, and check if the element at mid is what you are looking for. If it is, we return mid. Otherwise we check if we are looking for greater or less than the element at mid and cut down our range accordingly.

To begin with, we will present an imperative version of this algorithm that uses a while and several declarations.

```scala
def binarySearch(a:Array[Int], value:Int):Int = {
  var start = 0
  var end = a.length
  var mid = (end+start)/2
  while (end < start && a(mid) != value) {
    if (value < a(mid)) {
      end = mid
    } else {
      start = mid+1
    }
    mid = (end+start)/2
  }
  if (end < start) -1 else mid
}
```

The loop continues as long as the range contains at least one element and the midpoint is not the value we want. Inside the loop, a check is performed to see if the midpoint is less or greater than what we are looking for. If it is less, we set end=mid. This works because end is exclusive, and we have just verified that the element is not at mid. Otherwise we start mid+1. The start is inclusive so we have to move one element beyond the mid. When the loop is completed we return the value of mid or -1 based on whether the element was found or not.

This version of the code is fairly straightforward, but there is a simpler approach. Binary search happens to be algorithmic which lends itself nicely to a recursive implementation. The following code shows what this might look like.

```scala
def binarySearchRecur(a:Array[Int], value:Int, start:Int, end:Int):Int = {
  if (end < start) -1 else
    val mid = (start+end)/2
    if (a(mid) == value) mid
    else if (value < a(mid)) binarySearchRecur(a, value, start, mid)
    else binarySearchRecur(a, value, mid+1, end)
}
```

Clearly this is shorter than what we had. The logic of the recursive function is identical to the iterative version. Only the approach has changed. The only drawback is that this function has two extras. We use a wrapper function to call this.

```scala
def binarySearch(a:Array[Int], value:Int):Int =
    binarySearchRecur(a, value, 0, a.length)
```

This is typically $O(\log n)$ as the difference between logs of different bases is simply a constant multiplier. This order is generally considered to be quite fast, as it grows slowly as the input gets bigger.

To get a feel for this, let us look at a few examples of how $\log_2 n$ scales with $n$. A list of approximate values for this is given in table 13.1. To really put this in perspective, consider that the first number is the worst case for a sequential search, and the second number is the worst case for a binary search. When $n$ is small, the difference is not all significant. However, as $n$ gets larger the cost savings of a binary search become quite apparent. The last two values of $n$ are large enough to pose a problem even for computers, despite their speed.

Of course, you can only use a binary search on sorted data and attempting an $O(n^2)$ sort on even a million items can be time consuming. The real power of this $O(\log n)$ scaling is purely academic until we discuss some other ways to sort.
