The discussion of top-down approach requires that you keep breaking the problem down until you get to something that is finally simple to solve. This is not just for the problem solving, it turns out that there are good reasons to keep functions short. Long functions are much more likely to include errors than small functions. For this reason, it is generally advised that programmers keep their functions relatively short. But while making your functions long can be a matter of style and personal preference, there is a good rule you can follow that is backed up by research. The result is that functions should be kept short enough that they fit completely on your screen at one. When a function gets long enough that it does not fit on the screen, the programmer begins to rely upon/her memory of what is in the parts that are off screen. Human memory is not a great thing to rely upon, and as a result, the rate of errors goes up significantly when there are parts of the function that you cannot see on the screen.

# Listing 4.4: ItemCost.scala

```scala
def itemCost(item:String, size:String):Double = {
  if (item=="Drink") {
    if (size=="S") 0.99
    else if (size=="M") 1.29
    else 1.39
  } else if (item=="Side") {
    if (size=="S") 1.29
    else if (size=="M") 1.49
    else 1.59
  } else if (item=="Main") {
    if (size=="S") 1.99
    else if (size=="M") 2.59
    else 2.99
  } else {
    if (size=="S") 4.09
    else if (size=="M") 4.99
    else 5.69
  }
}
```

This function does not include reading the inputs from the user. Instead, it is assumed that the code that calls it will read the values and pass them in. In general, passing values into functions and returning values is more flexible than reading them and printing results to output in a function. A function that does reading and/or printing cannot be reused if the values come from something else than standard input or if you want to format the output in a different way.

> ⁵The Double type should not be used for money because it rounds. Remember that numbers in the computer are represented in binary. The value 0.1 in decimal is an infinite repeating binary number. That number gets truncated after a number of bits so the value 0.1 cannot be represented perfectly in a Double. This is fine for most applications, including scientific applications. It is not desirable for an application that deals with real money.

# 4.6 Side Effects

While side effects are typically not desired, there are times when effects of functions are desired. The simplest example of such is printing. The print statement does not return anything. It sends information to output. That is a side effect.

It is possible to have functions that return a value and have side effects. However, quite frequently you will find functions with side effects do not return any. To Scala their result is Unit. The Unit is a type that represents an object that carries no information. The Unit type does not carry any information because there is only one instance of it, which is written as ().

Here is a simple example of a function that includes side effects and results in Unit.

```scala
def introduce(name:String):Unit = {
  println("Hi, my name is "+name+"")
}

introduce("Lisa")
```

Hi, my name is Lisa.

The other form of side effect is an assignment. At this point it means an assignment to a var. One could write a function that has the primary purpose of changing the value of some var that is declared before outside the function. When a var is declared outside of any block of code, it is said to have GLOBAL SCOPE. As was already mentioned, this is a poor way to do things as it is it bug prone, and makes it harder to reuse the function. As a general rule, global scope should be avoided for anything that can be changed.
