## Understanding server management, service monitoring, and replication

Server management encompasses server configuration, monitoring, security management, service replication, and system updates. At the very least, a server administrator should understand how to create and manage users, how to install and secure applications, how to harden servers against attacks, how to use firewalls as an additional level of security, and how to automate logs and log rotations. Services need to be designed in such a way that they are resistant to configuration atrophy, hardened against attempts to compromise functionality, and capable of being restored or reconfigured easily.

The best way to test the ability to replicate a server is to restore it from scratch using only system backups. Where possible, processes should be automated, and where gaps in service are detected new procedures should be put in place. In the cloud environment it is important that failover plans include the ability to move into different availability zones on a single cloud provider or to migrate to other cloud providers. Services such as RightScale simplify this process by supporting a mechanism to replicate servers across multiple providers. Likewise, Amazon features the ability to migrate services via command line tools. As part of this process it is important to understand what services are available in the case of an availability zone outage.

Another approach to server replication that is gaining support in IT departments is automatic configuration and server deployment that does not rely on cloud providers. Server configuration tools such as Puppet and Chef replace the “golden egg” approach with easily deployed configuration scripts. These scripts document each step in the server creation and configuration process up to and including restoration of data and movement into production. Using such “actionable” configuration documentation, IT departments can save a great deal of time by both restoring service quickly and avoiding downtime by using the configuration scripts to monitor operating servers. Automatic configuration is becoming increasingly common in IaaS providers. Amazon (via CloudFormation), Linode, and RightScale all offer built-in scripted configuration services. Although this may not be the best practice for extremely large IT environments that prefer to host their configuration service outside of a given cloud provider, using the built-in service configuration tools goes a long way toward improving service durability without the overhead of learning and managing another IT management tool.

Another important part of working with IaaS services is determining server capacity needs. All IaaS providers discussed here offer a variety of CPU, RAM, and storage space options, but it may be necessary to test application installs on multiple platforms to find the best-performing and most economical configuration. As an example, Uspal et al. (2011) used a multifaceted approach to test AWS server capacities against comparably sized locally virtualized and physical servers. Although there were variations in server CPU capacity and available memory, all three servers used Intel Xeon CPUs running at approximately 2 GHz and had 6–8 GB of RAM. The researchers used an input/output file testing system named Bonnie++ (www.coker.com.au/bonnie++), MySQL database loading routines, and an ImageMagick (www.imagemagick.org) image-processing routine on 10 million images on all three server platforms as a comparison of server performance. Their tests found that the Amazon server outperformed both the local physical and locally virtualized server in all three tests, with the most dramatic differences associated with file input and output operations. For example, in the Bonnie++ test Amazon servers completed read operations at 92K per second as compared with 38K per second for physical and 18K per second for locally virtualized servers. Disk writing and ImageMagick processing showed similar results.

IT service monitoring is another key aspect of efficient service management. Monitoring is increasingly a built-in feature for IaaS systems but often focuses on server monitoring as opposed to application monitoring. Server resource monitoring (e.g., CPU load, hard drive usage, input/output) is important, but so is application monitoring since it allows IT departments to act ahead of application crashes. Large IT departments may have a complex monitoring system, but even small departments need a monitoring solution that ensures services are operational. For organizations seeking a large amount of control, systems such as Nagios (http://nagios.org) provide monitoring for applications, disk utilization, CPU utilization, and a host of other resources. There are also SaaS alternatives to Nagios, including New Relic (http://newrelic.com) and LogicMonitor (http://logicmonitor.com), that offer similar-scale monitoring services. Nagios is an appropriate service for complex monitoring, but each of the IaaS providers profiled in this chapter offers different forms of monitoring. For example, Amazon monitors server and infrastructure status at different levels and provides a wide range of communication methods. SaaS services such as Monitor.Us (http://monitor.us) provide easy web-based service monitoring.

## Ability to budget carefully

Budgeting for IaaS systems is much less predictable than for SaaS and PaaS systems. For example, organizations must be able to predict bandwidth, storage utilization, and CPU requirements for a service and project capacity needs over time. IaaS providers including Amazon offer lower costs for organizations willing to commit for a specified period, so the ability to project resource utilization over one to three years can lead to sizable cost savings. This is a good thing for organizations but requires system administrators to know when organizations need to renew their reserved instance terms. Failing to renew ahead of the expiration date leads to a dramatic unplanned increase in server run-time costs. Though budgeting is often an administrative function, the many moving pieces of an IaaS infrastructure mean that IT personnel are more likely to be asked to determine what it will cost to run an IT service.

## Service Complexity, Sustainability, and Durability

One of the main drawbacks of IaaS platforms is their complexity. Libraries often find that an IaaS service is more complex than traditional server platforms, and they often do not have the IT resources to ensure sustainable services. Some keys to avoiding unnecessarily complex services include using a single server platform and application environment, using a single approach for managing all services, and avoiding complex service tuning that does not add sizable improvements. For example, in a traditional IT environment it is preferable to use a logical volume management (LVM) approach that allows volumes to span across multiple disks. By using LVM, IT departments can dynamically add space to volumes without downtime or complex rebuilding of disk space. The major downside of this approach is that LVM requires configuration files and a static set of disks. In a cloud environment it is much easier to image, increase, detach, and reattach volumes. This to some extent mitigates the benefits offered by LVM and has the added benefit of enabling easy imaging, replication, and restoration of disk images without having to keep track of LVM configuration files and volume associations.
