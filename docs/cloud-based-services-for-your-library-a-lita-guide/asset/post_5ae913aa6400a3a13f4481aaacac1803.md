
These features both enable an enterprise level of support for cloud-based systems and pose problems for libraries seeking to leverage them. For example, no off-the-shelf library applications have been designed to run on PaaS application platforms. Although this may change in the coming years, PaaS application solutions are currently best suited to locally developed applications or specific tailored versions of popular applications. This means that, although SaaS application platforms offer enterprise-level support for service replication and scalability and may offer multiple endpoint or availability zones, they also require the developer to work in a rather narrow development environment using a limited suite of development tools and IT stacks. Some PaaS providers including Heroku address this issue by supporting multiple development platforms and featuring prebuilt services to facilitate everything from database integration to messaging and service monitoring. Clearly these benefits come with their own tradeoffs, requiring more configuration and management of the PaaS service.

## PaaS Provider Examples

At the time of this writing, there are few library-specific solutions that run on application-based PaaS environments and no applications designed to work by default in an application-based PaaS environment. It is likely that open-source and perhaps commercial systems will migrate to PaaS platforms given the benefits of this IT approach and the current use of many of the same platforms (e.g., PHP, Python, Java, MySQL, PostgreSQL, Oracle). Key products in this area include Amazon Elastic Beanstalk, Heroku, Google Apps Engine, CloudFoundry, and Microsoft Azure.

## Amazon Elastic Beanstalk

Amazon Elastic Beanstalk is a service provided within the AWS framework. As of this writing, Beanstalk supports Java, PHP, Python, and .Net applications and leverages the other services in the AWS environment. It uses Amazon computing instances as a distribution platform and supports scaling through multiple-instance levels from micro (1 EC2 Compute Units, 613 MB RAM) to extra-large (26 EC2 Compute Units, 68.4 GB RAM).

Figure 4.3 shows the Elastic Beanstalk management environment via the AWS web console. As with other Amazon cloud services, one of the powerful features of the environment is the ability to deploy and manage resources using both web consoles and command line tools that have been implemented in several languages

## CloudFoundry

CloudFoundry (www.cloudfoundry.com) is owned by VMWare and supports Java- and Ruby-based environments including Java Spring, Ruby on Rails, and Ruby Sinatra. Like Amazon's Elastic Beanstalk, CloudFoundry supports application version control, testing, and notification services. In addition to the commercial

CloudFoundry system, the organization publishes the CloudFoundry stack at CloudFoundry.org, enabling organizations to deploy the PaaS environment in a private cloud.

Instead of supporting a web-based administrative interface, CloudFoundry uses a client application called Micro Cloud Foundry to allow developers to test and deploy their services. This allows developers to move from testing to production quickly but comes with client configuration and database connection requirements. This is certainly an advantage over other PaaS environments that rely on server resources for a testing or development environment and may be seen as a competitive advantage for CloudFoundry.

## Google Apps Engine

Like CloudFoundry, Google Apps Engine (http://code.google.com/appengine/) has both a local testing application and an enterprise deployment platform (figure 4.4). It supports Java, Python, and Go platforms but has customized these deployments to enable close integration with the Google NoSQL database system. Google Apps Engine provides free and premium support levels and bases cost on desired support and service utilization measures. This makes it a good testing and small application deployment environment but also means that libraries may need to review the terms of service carefully if they move from a testing to a production use of the system.

## Heroku

Heroku (http://heroku.com) supports the widest range of development platforms of the reviewed PaaS systems, including Java, Ruby, Python, Clojure, Scala, Play, and Node.js (figure 4.5). Heroku integrates with the Git version control system and uses something called a “dyno manifold” to deploy and run code. Like Google Apps Engine, Heroku features a scalable pricing structure that includes free and premium service levels. Premium features such as SSL, dedicated database support, as well as a host of proprietary add-ons can be added to your service framework in a pay-per-use system. The many add-on services allow the Heroku platform to be tuned to fit a wide range of application models, but determining monthly costs and configuring the service can be more difficult than with other platforms.

By using more standardized platforms and an open application publication framework (Git), Heroku preserves the ability to deploy an application or service on multiple providers easily. But this ability depends on designing the application in such a way that static elements such as digital objects and database elements are accessible by all platforms on which the application is deployed. This is likely to require an external managed database platform such as Amazon’s RDS and long-term digital object storage in a second cloud provider such as Amazon S3 or RackSpace files.

There have been efforts to deploy library-specific applications on Heroku, in particular Blacklight (http://projectblacklight.org). Matienzo (2012) documented his approach for this process on github.com, and a discussion on the Code4Lib discussion board noted several other efforts on Blacklight deployment on Heroku and Amazon Elastic Beanstalk. Some of the challenges discussed in this thread (Code4Lib 2012) include the need to exclude unnecessary files such as SolrMARC and Jetty to reduce deployment size, the need to host SOLR indexing on a different cloud provider (e.g., Amazon IaaS services), and the challenge that comes with managing gem dependencies and configuring an external SOLR indexing service.

Despite these issues, the testing of Blacklight and the presence of other commonly used web-publishing applications indicate that this type of cloud computing shows possibilities. For example content management applications like WordPress have been customized to work on these platforms (Hoofman 2012; Stein 2011) and could easily fill library website needs. In both cases WordPress installation on Heroku utilizes a plug-in that supports PostgreSQL instead of MySQL but is otherwise unmodified. A key concern with this type of approach is whether a service that has been customized to work on a PaaS platform has “forked,” or deviated from the code base to a significant extent. A second major consideration is whether the customized version of the software introduces bugs or future incompatibilities that make support and migration difficult in the future. In the case of the Heroku-customized WordPress application, only a simple plug-in is required to modify the service, and it is possible that library IT departments could find monitoring this one customization worth the increased security and scalability that comes with the adoption of a dedicated PaaS platform.
