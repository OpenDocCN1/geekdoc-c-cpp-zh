An internal IT security policy should include acceptable use, monitoring, privacy remote access, network connectivity, and log retention policies (Limoncelli et al. 2001, 124). In addition, organizations that implement externally virtualized or cloud-based services should obtain or define policies that ensure data integrity, preserve local ownership of resources located in the cloud, and ensure the integrity of the overall cloud platform. Although there are risks associated with operating in a public or community cloud environment, cloud virtualization systems have been designed to ensure the isolation of virtual machines. Vendor assurances can help mitigate the perceived risks of public or community cloud platforms and are good building blocks on which to base a local security policy. For example, Amazon has obtained certifications and accreditations that document its ability to provide secure cloud services (http://aws.amazon.com/security/#certifications). Using these certifications as a base level to evaluate infrastructure security can help organizations identify suitable cloud candidates. In addition, a thorough understanding of the details of these security policies can help organizations focus their work on other areas of vulnerability. More details on provider-level security and assurances are discussed in the legal and policy section of this chapter.

One complication that can come with cloud computing platforms is the need to replicate security measures in each adopted platform or vendor. Therefore, having a clear and consistent policy on what measures are in place and how they are implemented (e.g., how user accounts are created, managed, and audited) helps simplify the adoption of new computing environments. This does not necessarily mean the centralization of security responsibilities but rather that the organization as a whole needs to be well informed about the real risks and management practices required in a cloud environment. For example, in SaaS environments it may make sense to delegate these tasks to a mid-level administrative user rather than routing them through an IT department. In contrast, the level of access and expertise required to administer user accounts in an IaaS environment properly likely means that these tasks need to be managed by staff familiar with the processes and associated risks. In both cases, however, creating a layered security policy can help extend access to the appropriate levels while preventing compromises. In the Amazon EC2 environment, for example, security groups are used as a cloud environment–level firewall that allows the grouping of servers in access groups. This level of security is offered in addition to server-level firewall options and could allow a distributed security management policy in which mid-level administrators have a higher level of access to server resources because there is little risk that they can make their systems vulnerable from outside of the organization's virtual server infrastructure.

The NIST cloud computing model emphasizes several important tasks to undertake to ensure proper cloud security. These include elements mentioned above (e.g., managing access, mitigating risk associated with common IT use through firewalls, and detecting intrusion) in addition to designing applications that leverage cloud features to enhance, rather than undermine, security. There are also client elements such as web browser security and the use of client/server security certificates which, when implemented properly, can ensure a higher level of client/server security (Fang et al. 2011, 39). A final area of key importance, particularly in integrating IaaS and PaaS environments, is the sharing of authentication keys and accounts. RightScale, in particular, relies on the establishment of trusted relationships using administrative accounts and access keys with IaaS cloud platforms. It is worth noting that, once these trust relationships are established, users in the RightScale service have the ability to control at a very granular level the services running in those other environments. Likewise, many of the Amazon application programming interface (API) services rely on preshared keys. If these keys are saved on client machines, direct access to Amazon IaaS elements is available to any user of that machine. Cloud providers are beginning to offer ways to compartmentalize access to resources using identity management tools that allow system administrators to monitor which users access infrastructure-level resources and limit access based on login or key credentials.

## Library-Specific IT Support

Determining local capacity for implementing and administering cloud resources is grounded in an understanding of personnel skill and time availability, technical needs, and financial resources. These factors need to be compared with projected service cost and impact to get an understanding of how important a given service or cloud platform is. As our exploration of infrastructure, application, and platform administration shows, technical skill and capacity play a large role in selecting, implementing, and managing a service. Likewise, depending on the cloud service selected, there may be upper limits to the capacity of that given system. As our exploration of IaaS providers in chapter 5 shows, the approach to and costs of implementing a scalable service on these platforms vary widely. For example Netflix viewed the latency in the Amazon EBS platform as a capacity-limiting factor and so redesigned its web services to utilize Amazon S3 (Cockcroft et al. 2011). Although example emphasizes the ability of IaaS providers to scale in response to demand, it sidesteps the limitations to local expertise, physical infrastructure, or disaster management that can make leveraging these features difficult. Because of this, it is important to be familiar with the elements of IT service management, security, and local capacity so that local and cloud-based capacity can be determined and an appropriate system selected.

One reason often cited for libraries moving to cloud systems is the need for greater IT support than is available locally. In some cases the need focuses on specific platforms, and in others the need focuses on data issues or scalability requirements that are not available in a local IT shop. In choosing to migrate to cloud solutions, however, libraries need to be aware of the IT services that must be provided by local IT. Some examples of service support required by libraries include network infrastructure and Internet access, domain name service (DNS) resolution, organizational authentication, organizational user or patron data, and firewall or VPN service.

In particular, having the ability to work with organizational IT to define new DNS entries for external servers, to open firewall rules to allow easier communication between internal and cloud-based servers, and to employ VPN as a means to limit access to the servers are three key services that facilitate the migration to cloud platforms. These services both form a trusted relationship between organizational IT and the library and demonstrate the limit of support requested by library IT. An SLA that explicitly outlines the types of services supported and the limits of responsibility can go a long way toward redefining the relationship of the library to the organization's IT department and addressing concerns that can initially seem insurmountable.
