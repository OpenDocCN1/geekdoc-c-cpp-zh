
A second key financial consideration is whether a library’s current software licenses and platforms support migration to the cloud. Software licensing is important in both server operating system and higher-level applications. In some cases new licenses are required for cloud computing, particularly in the case of proprietary or managed operating systems (http://aws.amazon.com/windows/; http://aws.amazon.com/rhel/). In other cases, specific services are licensed in an SaaS model (http://salesforce.com). In extreme cases, it may not be possible to implement software in a cloud environment when licensing terms are strictly tied to traditional IT paradigms (e.g., per-CPU, per-user, or license-server models). Although higher-level library application licensing may not be affected by an implementation in cloud computing environments, it is important to check, particularly when a scaling infrastructure is likely to be chosen that would create additional run-time copies of the software.

It is worth noting that, although the shift to cloud computing has posed problems for open-source adoption in libraries, open-source software also simplifies the implementation of IT on cloud platforms given the lack of licensing issues. It is entirely possible to create a cloud infrastructure based wholly on open-source platforms, including operating systems, web publishing systems, and a range of library-specific applications. It is possible to use only open-source solutions in IaaS and PaaS environments, less likely to do so with SaaS solutions. Further, when libraries turn to open sources for operating system and core infrastructure elements (e.g., system backups and web servers), they may also take on additional system management responsibilities. One of the main areas of importance in this situation is the necessity to select open-source components that feature regular security and functional updates. Amazon seeks to make this process more sustainable by offering a certified version of Linux in its server templates (http://aws.amazon.com/amazon-linux-ami/). Other communities such as Ubuntu and CentOS offer regular updates as well. In addition, open-source platforms such as Red Hat (http://redhat.com) offer paid support levels for Linux-based operating systems.

## Determine Actual Cost and ROI

The two ROI models explored in this section come from Reese’s (2009) work on cloud adoption and Feldman’s (2012) exploration of the use of ROI by cloud subscribers. Reese (2009, 50) uses an ROI worksheet that includes categories for up-front, labor, recurring, capital, licensing, and subscription costs associated with both traditional and cloud-based IT. His recommendation is to estimate costs over a three-year period as a way to enable comparison to traditional IT services.

## Selecting and Implementing Solutions

Reese’s approach focuses on itemizing hardware costs and grouping labor costs into a single sum and includes an estimation of the cost of performance loss that may be a factor in selecting capacity in the cloud (e.g., an organization may select a mid-capacity cloud server that just meets current demand rather than overbuying capacity for a physical server). This cost of performance loss can be mitigated by designing scalable systems and actually could be viewed from the other direction (e.g., the capital cost of unutilized capacity).

In contrast, Feldman’s (2012, 19) ROI approach uses capital costs, operational costs, future capital cost (e.g., for savings), staffing impact, time savings for non-IT staff, resource provisioning (e.g., hardware acquisition/setup time), network expenses, implementation cost, and utility costs as factors. Whereas Reese’s calculations describe a wholly local or wholly cloud-based infrastructure in which capital investment savings realized from cloud deployment result in an overall lower total cost for cloud services, Feldman’s ROI analysis suggests that the most economical approach focuses on using private cloud services that support public cloud bursting (e.g., Eucalyptus, OpenStack, or CloudStack) and differentiates long-term investments from short-term capacity need.

### Cloud Bursting

Cloud bursting is the ability to scale computing and storage resources quickly from a private cloud into a public or community cloud environment using the same tools and standards employed in the private cloud. Two providers in particular, Amazon and Rackspace, support cloud bursting using different private cloud platforms. In March 2012, Amazon announced a formal agreement with Eucalyptus to design its cloud system using the same application programming interface tool design that was first deployed by Amazon (Eucalyptus 2012). Likewise, Rackspace was key in the development and release of OpenStack and is building toward the ability to migrate private OpenStack deployments easily to Rackspace services (Moorman 2011). In addition, data centers such as Internap (http://internap.com) are beginning to offer private cloud platforms using the OpenStack platform, enabling a new type of externally sourced private and public cloud architecture.

These conclusions show how difficult calculating ROI can be for cloud services and introduce three distinct approaches: nonvirtualized, private/public cloud, fully public/community cloud. It is worth noting that in making this claim Feldman is pointing to large-scale companies such as DreamWorks and Zynga, both of which have “burst level” capacity needs that far exceed the ongoing resource needs of most libraries for several years (e.g., 10 million CPU hours) (Feldman 2012, 6). This means that many libraries could find that their calculations more closely match Reese’s view, in which an organization saves resources by making a focused investment in just a single type of computing platform. Another factor that complicates cloud cost calculation is the expected duration of the service being implemented. Reese recommends projecting costs over a three-year period; Feldman differentiates “start-up” and “enterprise” adoptions and argues that as organizations move to an enterprise level they are likely to find more cost savings in running a private cloud environment with public cloud bursting capacity. Rather than think in terms of start-up versus enterprise, libraries may want to consider the projected longevity of an information service instead. This can help an organization understand the potential cost savings from up-front capital investments versus ongoing cloud investments in short- and long-term services. It also can make the calculation of ROI more complex. This likely involves choosing or adhering to a depreciation schedule and having a detailed understanding of the technology costs that will and will not go away in a cloud service. To help with these calculations, Reese provides formulas to calculate cost over the life of the service and to determine current technology value (2009, 53, 12). Cloud providers, particularly IaaS providers, may provide cost calculators—for example, Amazon (http://calculator.s3.amazonaws.com/calc5.html), Microsoft Azure (www.microsoft.com/windowsazure/pricing-calculator/), and RightScale (www.rightscale.com/tco-calculator/).

Another important factor in cost calculation, particularly for libraries, is data storage and data transfer costs. A common method for planning for backup costs over time is to estimate the amount of change in data expected over a month and multiply total storage by that percentage (e.g., if you expect a 15 percent change in a month, your backup charges are 1.15 times storage costs). The fact that backed-up data are entirely replicated on cloud services can make storage costs seem very expensive, but many cloud services including Amazon’s S3 and Glacier services include automatic replication and redundancy as part of the storage service. This does not eliminate the need for backups, but for organizations comfortable with this approach to storage the use of version control and unique backups with limited archiving history can lower the overall costs of storage.
