The approach detailed in figure 6.1 also brings technical and configuration challenges. For example, because Amazon does not provide a mechanism for automatic backups in its web console, users must implement a solution using an external vendor or Amazon’s command line tools to take regular snapshots of their server resources. Fortunately, because this is a common issue several approaches are available. For customers seeking to keep backup service scheduling on their server, a simple backup script written using one of the available AWS command line tool platforms (http://aws.amazon.com/articles/) works easily. The AWS tutorial at libcc.org (http://libcc.org) features a backup script using the Python BOTO library (http://code.google.com/p/boto/). Likewise, because Linode does not offer a managed database service, an extra server is included as the database server. This actually may be preferable for libraries that use multiple database platforms in their information systems. Although this solution requires that libraries take on database management, it also offloads backup responsibilities. Linode's managed backup service takes care of the backup scheduling and rotation.

Cloud providers do experience occasional downtime, and this is a considerable risk with a single-vendor cloud. There are ways of mitigating this risk, however, for vendors that include multiple independent cloud zones. In the difficulty experienced in 2011, Amazon customers found out how important a redundant and easily replicated cloud infrastructure can be (Cockcroft et al. 2011; Tonjes 2011). In fact, Netflix's approach was to build a PaaS environment using the Amazon platform as a way of addressing this issue (Cockcroft 2012). In the Netflix architecture, emphasis was put on designing scalability, application publishing, and management using continuous integration tools, database storage using Cassandra (http://cassandra.apache.org), and prebuilt AMIs to deploy operational instances (Chan 2012; Cockcroft 2012). One of the interesting outcomes noted in Cockcroft's presentation on system architecture was a realignment of IT development away from system management roles (e.g. database administration, system administration).

Another challenge with this approach is the inability to move to a new cloud provider without considerable development time and expense. Although these providers support machine and data exports, the reliance on vendor-provided management services means that migration includes considerable learning and design work. Finally, as our cost analysis shows, relying on a single vendor may push libraries into paying for more capacity than they need in certain areas. Vendors have different cost models for network traffic, storage space, server size, and core versus add-on services. A single-vendor cloud would make it difficult to manage these costs over time as service needs change.

## APPROACH TWO: MIXED-CLOUD MANAGEMENT WITH SAAS

Our first approach ties all applications to a single server, requiring the library to manage multiple application stacks and select a server capable of serving all applications. It can be preferable to isolate applications onto separate servers so that downtime or problems with one system do not hinder the others. In addition, libraries may instead want to use a mix of PaaS and IaaS providers to separate out applications on the basis of platform or scalability need.

Although this may lead to a more durable architecture and more efficient use of resources, it can also make it difficult to monitor, audit, and manage these services.

To address these concerns there are an increasing number of vendors that provide value-added support on top of IaaS and PaaS services. Some key areas these SaaS services address are service auditing, server and application monitoring, service management automation/simplification, and administrative notification. In our second cloud model, the Amazon cloud described in the first section is retained but another application is deployed on the Heroku platform. The platform may be in use because of Heroku's ability to scale services easily, because of a good fit with an application stack (e.g., Ruby on Rails), or simply to build in a level of vendor redundancy. In this example, database and digital object storage services continue to be offered via the Amazon RDS and EBS services. Figure 6.3 illustrates this deployment and shows how SaaS services such as Ylastic and Cloudability can be used for monitoring, auditing, backup, and replication.

This model uses Ylastic to provide application monitoring for both Amazon and Heroku cloud platforms and backup and region migration services for the Amazon platform. Cloudability provides cost auditing for both Amazon and Heroku. By monitoring cost and resource utilization, Cloudability allows administrators to get a consistent cross-provider view of their environment. Although it focuses exclusively on Amazon, Ylastic is able to provide advanced auditing for orphan resources such as unattached EBS volumes. This approach capitalizes on adding value to IaaS platforms by tracking overreserved resources and automating complex functions. For example, our first model highlighted the lack of a simplified backup service in the AWS web console. To address this, Ylastic provides a managed backup service for both EBS volumes and AMI creation services. As figure 5.7 shows, Ylastic offers automated and scheduled tasks that can facilitate server management. In addition, it provides a graphical interface for service replication across multiple AWS regions. Given the fact that Amazon's SLA is based on the ability of subscribers to redeploy services in another region, having a service that facilitates this process could be valuable. The automatic scalability of Heroku, the region replication services of Ylastic, and the resource use notification functions of Cloudability are all features that can save money and simplify IT environments by allowing libraries to scale their services on demand. In a traditional IT model, IT service capacity is centered around the notion of “n+1”—that is, always having more capacity than needed. In a well-managed cloud environment, services can scale up or down based on need or can be replicated into new regions when required, making it possible to provide services “just in time.”

Although Ylastic charges for its basic service, some SaaS services do come at no cost for smaller users. Cloudability, for example, provides free cost-auditing services for subscribers with less than $2,500 in cloud expenditures. Likewise, cloud configuration/monitoring services like RightScale and monitoring services including Monitor.Us include a free subscription level. Nevertheless, free services may not be desirable given the lack of local control that often comes with them (see chapter 3).

The benefits of this approach include selective redundancy across multiple cloud providers; automation of infrastructure-level tasks (e.g., backups); clearer understanding of cost and resource utilization; ability to support otherwise unavailable services via SaaS solutions; and automatic scaling, replication, and notification features that allow libraries to move away from the “just in case” models of IT planning to a “just in time” model.
