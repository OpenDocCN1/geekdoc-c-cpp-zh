These kinds of conditions are called **invariants**, for the obvious reason that
they not vary—they are always supposed to be true. One of the ways to write
good code that contains bugs is to figure out what invariants are
appropriate for your classes, and code that makes it impossible to violate
them.

One of the primary things data encapsulation is for is helping to
enforce invariants. The first step is to prevent unrestricted access to the instance
variables by making them private. Then the only way to modify the object is
by accessor functions and modifiers. If we examine all the accessors and
modifiers, and we can show that every one of them maintains the invariants,
then we can prove that it is impossible for an invariant to be violated.

That definition allows loopholes. First, there may be some point in
t middle of the function when the invariant is not true. That's ok, and in
cases unavoidable. As long as the invariant is restored by the end of the
function, it is well.

The other loophole is that we only have to maintain the invariant if it was
true at the beginning of the function. Otherwise, all bets are off. If the invariant
was violated elsewhere in the program, usually the best we can do is detect
t error, output an error message, and exit.
