
## 13.9 SHUFFLING AND DEALING

In Section 13.6 I wrote pseudocode for a shuffling algorithm. Assuming that we have a function called shuffleDeck that takes a deck as an argument and shuffles it, we can create and shuffle a deck:

```
Deck deck; // create a standard 52-card deck
deck.shuffle(); // shuffle it
```

Then, to deal with several hands, we can use subdeck:

```
Deck hand1 = deck.subdeck(0, 4);
Deck hand2 = deck.subdeck(5, 9);
Deck pack = deck.subdeck(10, 51);
```

This code puts 5 cards in one hand, the next 5 cards in the other, and the rest into the pack.

When you thought about dealing, did you think we should give out one card at a time to player in the round-robin style that is common in real card games? I thought about it and it is unnecessary for a computer program. The round-robin convention is intended to mitigate imperfect shuffling and to make it more difficult for the dealer to cheat. Neither of these is an issue for a computer.

This example is a useful reminder of the dangers of engineering metaphors: sometimes we impose restrictions on computers that are unnecessary, or capabilities that are lacking, because we unintentionally extend a metaphor past its breaking point. Beware of misleading analogies.

## 13.10 Mergesort

In Section 13.7, we saw a simple sorting algorithm that turns out to be very efficient. In order to sort n items it has to traverse the n times, and each traversal takes an amount of time that is proportional to n. The total time is proportional to n^2.

In this section I will show a more efficient algorithm called mergesort. To sort n items, mergesort takes proportional to n log n. That may not seem impressive, but as n gets big, the difference between n^2 and n log n can be enormous. Try out a few values of n and see.

The basic idea behind mergesort is this: if you have two subdecks, of which have been sorted, it is easy (and fast) to merge them into a single, sorted deck. Try this with a deck of cards:

- 1. Form two subdecks with about 10 cards each, sort them so that when they face up the lowest cards are on top. Place both decks up in front of you.
- 2. Compare the top card from each deck and choose the lower one. Flip it over and add it to the merged deck.
- 3. Repeat step two until one of the decks is empty. Then take the remaining cards and add them to the merged deck.

The result should be a single sorted deck. Here's what this looks like in pseudocode:

```
Deck merge (const Deck& d1, const Deck& d2) {
  // create a d1 big enough for all the cards
  Deck result (d1.cards.length() + d2.cards.length());

  // use the index i to keep track of where we are
  // the first deck, and the index j for the second deck
  int i = 0;
  int j = 0;

  // the index k traverses the result deck
  for (int k = 0; k <result.cards.length(); k++) {
    // if d1 is empty, d2 wins; if d2 is empty, d1 wins;
    // otherwise, compare the two cards

    // add the winner to the new deck
    return result;
  }
}
```

I chose to merge a nonmember function because the two arguments are symmetric.

The best way to test merge is to build and shuffle a deck, subdeck of two (small) hands, and use the sort routine from the previous chapter to sort the two halves. Then you can pass the two halves to merge to see if it works.

If you can get that, try a simple implementation of mergesort:

```
Deck::mergesort() const {
  // find the midpoint of the deck
  // divide the deck into two subdecks
  // sort the subdecks using sort
  // merge the two halves and return the result
}
```

Notice that the current object is declared const because merge does not modify it. Instead, it creates and returns a new Deck object.

If you get that working, the real fun begins! The magical thing about mergesort is that it is recursive. At the point where you sort the subdecks, why should you invoke the old, slow version of sort? Why not invoke the spiffy new mergeSort you are in the process of writing?

Not only is that a good idea, it is necessary in order to achieve the performance so I promised. In order to make it work, though, you have to add a base case so it doesn't recurse forever. A simple base case is a subdeck with 0 or 1 cards. If mergesort receives a small subdeck, it can return it unmodified, since it is already sorted.

The recursive version of mergesort should look something like this:

```
DeckSort::mergeSort (Deck deck) const {
  // if the deck is 0 or 1 cards, return it
  // find the midpoint of the deck
  // divide the deck into two subdecks
  // sort the subdecks using mergesort
  // merge the two halves and return the result
}
```

As usual, there are two ways to think about recursive programs: you can think through the entire flow of execution, or you can make the "leap of faith." I have deliberately constructed this example to encourage you to make the leap of faith.
