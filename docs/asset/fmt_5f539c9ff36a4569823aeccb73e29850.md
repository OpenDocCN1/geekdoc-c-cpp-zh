
每当你解锁可重定位内存时，移动它，并且如果你在旧位置缓存了垃圾数据，也要处理。如果你在缓存磁盘数据，一旦解锁，就将其写入磁盘并清除缓冲区。如果你在定时器中断（`timer tick`）上与 `TSR` 交互，并且你设置了一个信号量来关闭 `TSR`，请在关闭它的前后的指令上调用定时器中断。

你还想为程序创建一个极其糟糕的环境。如果它能幸存，那么它应该在任何资源变得紧紧张的实际情况下都能生存下来。

`RT-Link` 是一个提供代码交换的链接器，它做得非常完美。你可以用一个可用的代码页运行它，以便所有代码都交换到同一个页中。这确保了每个代码页都会交换到上一个代码页之上。如果任何代码页依赖于另一个代码页同时位于内存中，它会导致程序崩溃。

在任何调用中，如果可能发生错误，就应该对其测试。每个 `malloc` 都应该测试是否返回 `NULL`。这不仅是犯罪行为，因为你将只在低内存系统上引起间歇性的可察觉的错误。

每个打开的文件都要测试句柄是否为 `-1` 的情况，包括创建临时文件。你还应该测试所有文件 I/O 是否成功。我见过一些程序，这些程序假设临时文件的创建和写入总是成功的。我猜开发者的 RAM 盘总是足够大，但我的不是。你甚至需要检查对文件现有部分的读/写操作。如果连接断开，你就无法访问该文件。

对于我写的一个程序，我创建了一个虚拟内存系统（针对 DOS），它会先使用普通内存。如果使用了普通内存，它就会转到 EMS。如果 EMS 用尽了，它就会去磁盘。那么我确定它们是否都运行良好吗？我在调试模式下设置了可以可选地始终从 EMS 或磁盘分配。仅磁盘版本运行很慢（我们说在 486 上有巨大的延迟），但所有函数都能正常工作。通过这种方式，我能够强制程序使用每个内存系统。

如果你的临时文件在 RAM 盘满时会被移动到硬盘，请务必使用一个过小的 RAM 盘测试你的应用程序。在任何你有备份程序以防你用尽首选资源的地方，务必确保你可以使用备份资源测试整个系统。

如果你写了一个使用信号量来防止重入的 `TSR`，在信号量之前和之后，调用该 `TSR` 所在的中断，以确保它不会再次重入自身。秘诀在于看你是否可以破坏自己的代码。

上述所有技巧都是针对它们所测试的代码而特定的。每个程序都有不同的弱点。你需要找到这些弱点然后破坏它们。如果你下心要发现你代码中的那些 MFUs（致命逻辑错误），那么你就能弄清楚如何破坏你的代码。

### 稳如磐石的底层函数

当你两个整数相加时，结果不大于一个整数，你就知道它会工作。想一下如果你不知道这一点，调试将会是什么样。你必须检查在每次加两个数字的地方指令执行了什么，并用各种数字组合对每一种进行测试。你基本上无法编程。

现在让我们提升一个层级。如果你对 `strcpy`（或任何运行时函数）不确定怎么办？你现在至少可以依赖（事实上，我记得 PC 编译器的早期，那时你无法依赖这些函数）。但这并不是一项容易的任务。你的测试和调试工作有了飞跃性的增长。

但你可以信任处理器和运行时（如果你不能强制它切换的话）。然而，每个程序都有一组属于自己的、特定的底层函数。这些底层函数有两个重要的属性。首先，它们贯穿你的整个程序。其中一个函数中的微小 Bug 都是程序中严重的 MFU。

其次，你通常可以测试这些底层函数中程序流的所有组合。彻底测试这些底层函数。你应该能够像依赖 `+-`（加法）一样依赖这些调用。

要做到这一点，请编写测试程序，在调用你的底层函数时使用足够不同的参数组合，以测试所有可能的代码路径组合，并且仅在返回值错误时不才打印到屏幕上。这样，当你对函数进行更改时，再次测试非常容易。

通过对底层函数的详尽测试，你将获得巨大的收益。首先，你的部分代码接近于无 Bug。让部分代码无 Bug 应该降低总 Bug 数。

更重要的是，虽然高层函数中的 Bug 通常只会引起一个问题，但底层函数中的一个 Bug（例如链表管理）会导致整个程序中出现无数 Bug。底层函数是程序的基础和框架——如果它是稳实的，程序就是稳实的。如果它是松动的，无论其他地方如何努力都无法让程序变得稳固。

对所有广泛使用的函数进行测试也是至关重要的，即使它们不是底层的。什么时候一个函数值得进行详尽测试？什么时候可以得出一组测试用例来所有组合？如果你再次审视你的代码，你可能会发现其大部分都可以以此方式测试。你可以以此方式测试数据库中的每个命令、文字处理器中的每个函数、图形包中的每个工具。

当你观察程序逻辑时，很明显少量的测试用例就能执行所有可能的路径。如果你不能这样测试任何内容，你就面临严重的问题。然而，如果你编写了真正干净、分离的（即面向对象风格）代码，你会发现几乎所有的函数都可以以此方式测试。

所以你有一段巨大的代码库，你不想为所有代码编写测试用例。那么不要写。你可以花大约三天时间为 15 到 40 个类似的函数（例如 `strcat`, `strcpy`, `str`）编写测试用例。你会发现很少 Bug，如果没有。然而，你发现的那些将是过去无法复现的 Bug。如果你没有发现 Bug，假设你写了测试程序，那么你现在知道你的底层函数是稳实的。

如果你的大部分代码都可以以此方式测试，那么如果你像这里描述的那样先测试组件，你可能会对最终产品中 Bug 如此少感到惊讶。

这可能是巧合，但当我开始对底层函数进行全面测试时，我看到写的程序 Bug 减少最多。不仅如此，在此之后，我不禁回想起任何一次严重影响整个程序的 Bug。

### 在条件定义中调试

为了保持速度，大多数时候你不会希望所有的条件错误检查都被编译。某些错误检查可能会耗费非常长的时间。（通常情况下，特定的检查并不耗费时间，而是该检查被调用的频率频繁）。

另一个通用原因是，如果你正在向终端或第二个显示器打印调试信息，并且你不希望有用信息被你其他你不感兴趣的信息所刷出屏幕。有时，纯粹的打印量会减慢程序，因为显示器只能以特定的速度写入屏幕，而不能更快。

针对这个问题，你可以采取两种主要方法之一。第一种是不编译额外的调试代码，使其完全不存在，但如果你决定需要找回某些调试打印，你将必须重新编译。下面的程序示例说明了条件编译的使用。

### 使用 DEBUG 的值

```c
#ifdef DEBUG
fast_test ();
#endif
#if (DEBUG > 1)
slow_test ();
#endif
#if (DEBUG > 2)
real_slow_test ();
#endif
```

第二种方法是在调试代码开头测试一个标志位，如果测试失败则跳过它。如果标志位是一个变量，你可以在调试器中更改它的值，从而轻松地在程序运行途中开启调试测试/printf（或在不再需要它们后关闭它们）。

### 使用变量

下面的程序示例说明了调试变量的使用。

```c
#ifdef DEBUG
fast_test();
if (DebugVar > 1)
    slow_test();
if (DebugVar > 2)
    real_slow_test();
#endif
```

尽管有很多花哨的方法可以实现这种条件调试代码，但似乎有两个规则是通。第一，你通常不希望在编译后开启或关闭调试。第二，这两种实现方式在代码编写和执行速度上似乎是一样快的。

对于简单代码，调试通常是一个“开/关”问题。在这些情况下，仅使用 `#ifdef` 通常足够了，任何额外的操作都是浪费时间。对于其他虽然简单但包含几个耗时检查的代码，你可以使用 `DEBUG` 定义的值作为条件编译。

在进行条件调试时，请记住，某些调试测试是相互匹配的。如果你的条件分配在每个分配内存区域的前后设置了签名字节，那么当任何检查堆签名字节的条件定义被执行时，最好也执行该操作。我曾花费了几个小时试图确定为什么某些缓冲区在 CRC 测试失败了——原因是 CRC 创建代码被 `ifdef` 过滤掉了，而检查代码没有。

### 注释你的开放/待解决问题 (Issues)

随着你的开发，某些代码段中会出现问题或疑问：某个函数能在 Super VGA 显示器上工作吗？你如何处理带有特定错误的数据文件？你需要注意某些情况吗？

这些问题无法通过 Traps（陷获）和 IntTests（内部测试）来解决。相反，它们是你认为尚未完全编码的项目，或者在某些情况下你没有写全。在其他情况下，你的程序将在你需要它继续运行的条件下失败。

这些是你某个时候发生的可能逻辑错误。遗憾的是，由于人类思维的局限性，这些错误会被很快遗忘（直到 Bug 出现）。这些 MFU（不可预见的故障）被归类为“该死”。

### 无 Bug

`bugs` - 源于当 Bug 首次报告给负责开发人员时通常听到的短语。

记录这些担忧的地方是代码本身。写在其他任何地方都可能丢失。如果写在代码中——它就是永远的，直到你解决了该问题。

在这些情况下，请放置单行注释，单词“bug”后面跟着你的缩写和日期。你可以在其后加上几行的注释，但第一行应该给出一个合理的描述。

### BUGBUG

下面的程序示例说明了 `BUGBUG` 注释的使用。

```c
// BUGBUG DNT 32/1/92 - 内存不足。我们需要用磁盘吗？
// 目前如果内存耗尽就会失败。然而，
// 如果在大文件上运行，内存不足可能会很。
```

这个 `BUGBUG` 完成三件事：

- 通过在所有文件中对 `BUGBUG` 进行 `grep` 或文本搜索，你可以获得所有开放问题的标题行。（注意：在汇编章节中，展示了一种在编译期间将 `BUGS` 到屏幕的方法。遗憾的是，C 不支持这种方式的编译期间打印。）

- 开放问题随代码迁移。你不会丢失开放项目列表（除非你也丢失了代码）。

- 开放项目就在代码中相关的位置——你不需要搜索所有文件来找到正确的位置。

当你交付产品时，你的代码中不应该有任何 `BUGS`。在上面的示例中，你可能决定改用磁盘。你也可能决定将自己限制在内存中。无论何种情况，问题都解决了。

如果你不使用 `BUGBUG`，你可能会忘记或丢失重要问题。在程序发布后用户报告 Bug 之前，你可能不会记得这个问题。使用 `BUGBUG` 是简单的，而且比在其他地方记录信息更有效率。

### 保持不显眼

让你的调试尽可能不显眼。程序的其余部分应该几乎不受受到调试代码的影响。（程序可能会运行得稍微慢一点，用户可能会看到弹出的调试消息。）良好的调试检查在发现 MFU 之前一直保持隐藏且不干扰。

## 第 4 章

### 基础技巧

现在我们进入实际的编程技巧。对于那些完全不知道如何编程的人，如果你仍然和我们在一起，是时候跳到关于测试的章节了。对于管理层的人，是时候给你的开发者加薪了，然后跳到测试章节了。

本章包含了所有不值得单独成章的技巧。这并不是说这些技巧不重要，而是说可以用更少的文字来解释。在本章以及直到进入测试过程之前的章节中，这些技巧将被通用描述。最重要的是，这些技巧将允许你无痛苦地消除程序中的 Bug。

### TestAll 函数

假设你的程序正在神秘地崩溃。你不知道具体原因。但随后，你在程序中的各个位置放置了 `TestAll` 函数。现在你能够缩小 Bug 的范围。`TestAll` 报告一切正常，然后在 20 行后报告了一个错误。

这个神奇的 `TestAll` 函数是什么？非常简单，它调用你所有的测试函数。至少它会检查空内存位置、整个堆以及剩余的栈空间。它还会断言全局数据结构。在 Windows 程序中，它调用 `ValidateSegments` 和 `ValidateFreeSpaces`。

### TestAll 函数

```c
void TestAll (void)
{
  // 测试系统
  TestHeap();
  TestStack();
  TestNull();
  #ifdef WIN
  ValidateCodeSegments();
  ValidateFreeSpaces();
  #else
  TestEms();
  TestXms();
  #endif

  // 测试全局变量
  AssertBool(bInsertMode);
  AssertDbase(&MainDbase);
}
```

每当你创建一个可以在任何地方（全局）调用以执行测试的测试函数时，该测试都应该添加到 `TestAll` 中。最终，`TestAll` 会变得非常慢，因为这个原因，你很少调用它。在下面的示例中，`funcBad` 因为系统错误而崩溃。但代码看起来是无错误的。通过测试，你可以确定哪个函数是导致了问题。在执行 `funcBad` 之前，你可以查看 `func1` 或 `func2` 是否为真正的罪魁祸首，尽管你直到 `funcBad` 才会看到错误的影响。

### 使用 TestAll

下面的程序示例演示了 `TestAll` 的用法。

```c
funcMfu ()
{
    funcOk ();             // 你知道这个函数是好的
    TestAll ();
    func1 ();               // 可能有 bug
    TestAll ();
    func2 ();               // 可能有 bug
    TestAll ();
    funcBad ();             // 查看错误的影响
}
```

### 恢复系统状态

我们已经使用了所有运行良好的程序，但 DOS 在使用该程序后不久总是锁定。我有一个经常使用的程序，从没有出现过任何坏影响。然而，当我在 Windows DOS 盒上运行它时，每次启动都会导致 UAE。显然，它在操作不属于它自己的内存。

当你的程序准备退出时，你应该对系统进行完全测试。许多程序员并不担心退出时的错误信息，然后之后，你就退出了——谁在乎东西是不是稍微搞乱了呢？

这是一种非常危险的做法。首先，这些错误中的许多是 bug 的症状，在不同的配置或使用下，它们可能会在你运行程序时引发问题。其次，这些错误中的许多对操作系统是有破坏性的。如果你的程序返回到 DOS 但 5 秒后锁定，那仍然是你的错。

- 1. 调用 `TestAll`。这个单次调用应该测试你的系统的完整性。

- 2. 调用 `StackUsed` 函数（后文讨论）。这将告诉你你使用的最大栈大小。每当你退出程序时，打印出使用的最大栈大小以及总栈大小。这可以给你持续的反馈，让你知道你是否适当设置了栈大小。

- 3. 对比中断表以及任何其他操作系统全局变量（作为 BIOS 数据区域中你感兴趣的部分），以确保你离开系统时的状态与你发现时一致。除非你正在编写某些非常脏的代码，否则这不需要担心——在这种情况下，这只是你最最小的问题。`Bounds Checker`（在工具章节讨论）将检查中断表以及 BIOS 数据区域，查看你是否更改了其中任何内容，因此没有相关的示例代码。然而，如果你不使用 `Bounds Checker`，你需要编写一个程序在启动时（在 c-runtime 初始化代码运行之前）保存中断表。然后在退出时，将现有表（在 `c-runtime_end` 函数运行后）与保存的表进行比较。

- 4. 让系统保持在你发现时的状态。这对于确保你的程序每次运行时都不会吞噬资源至关重要。任何打开的文件都应该关闭。任何分配的 DOS、EMS 或 XPS 内存都应该释放。这对 EMS 和 XPS 内存非常关键，因为 DOS 不会在退出时自动释放它们。此外，如果这些内存没有释放，你的程序在运行时就会浪费资源。

- 5. 检查你的堆是否有未释放的 `allallocate` 内存。如果你使用近堆和远堆，请检查两者。在完成操作后，未释放的内存通常表示逻辑错误。即使问题仅仅是你忘记释放一个指针，你仍然在消耗稀缺资源。

- 6. 检查是否仍有打开的文件。这可能指示完成操作时存在逻辑错误。然而，打开的文件句柄与堆作为稀缺资源一样，如果保持开放，要危险得多。如果系统崩溃，部分文件仍在内存中而不是磁盘上，文件可能会损坏。
