## In Depth

自 .NET Framework 1.0 发布以来，Microsoft 一直在持续努力开发和改进 ASP.NET，该技术是 .NET Framework 的一部分，用于构建丰富的 Web 应用程序。此次首发在构建网站时，相较于使用服务器端脚本引擎 Active Server Pages (ASP) 的旧 Microsoft 技术，带来了根本性的变化。尽管 ASP.NET 相较于 ASP 具有许多优势，但由于其复杂性和构建应用程序所需的知识，新程序员发现开始使用 ASP.NET 存在困难。

在 2002 年首次发布后，名为 .NET 1.1 的另一个版本的 .NET Framework 与 Visual Studio 2003 一起发布。大多数人认为此版本只是首次发布的服务包，尽管它在框架和开发环境方面也有新的改进。

后来在 2005 年 11 月，Microsoft 发布了 Visual Studio 2005，其中集成了 ASP.NET 2.0。再次，Microsoft 在此版本中做出了大幅改进，并降低了初始版本的复杂性。此新版本具有许多新的向导和控件，减少了构建应用程序所需的代码量，从而提高了生产力。

现在，Microsoft 的最新发布是 ASP.NET 4.0，其中包含用于创建基于 Web 的应用程序的新功能。

本章探讨 ASP.NET 4.0 的新功能、ASP.NET 的生命周期、其编译过程、ASP.NET 4.0 编码模型以及 ASP.NET Web 页面的语法。

让我们开始探索 ASP.NET 4.0，从其新功能开始。

## New Features in ASP.NET 4.0

ASP.NET 4.0 于 2010 年 4 月 12 日与 Visual Studio 2010 一起发布。它使用与 ASP.NET 3.5 相同的引擎，并具有一些附加功能。ASP.NET 4.0 简化了构建网站的过程，使其比以往更容易。现在让我们讨论添加到 ASP.NET 4.0 的以下新功能：

- ASP.NET 核心服务
- ASP.NET Web 表单
- 动态数据
- ASP.NET 图表控件
- Microsoft AJAX 功能
- 对基于 MVC 的 Web 应用程序的支持
- 改进的 CSS 能力

### ASP.NET Core Services

ASP.NET 4.0 核心服务包括输出缓存和会话状态存储等功能。ASP.NET 核心服务的优点如下：

- **`web.config` 文件的重构** – 规定在此版本的 ASP.NET 中，`web.config` 文件的主要配置元素已移至 `machine.config` 文件。这意味着在此新版本的 ASP.NET 中，`web.config` 文件为空或仅包含一些基本代码，该代码指定应用程序所针对的 Visual Studio Framework 版本。这是因为随着 ASP.NET 中 AJAX、路由和与 IIS 7.0 集成等新功能的加入，配置或启动新 Web 应用程序的过程变得困难。因此，主要配置设置已移至 `machine.config` 文件，以便应用程序可以继承设置并无困难地运行。
- **输出缓存** – 使你能够配置一个或多个输出缓存提供程序。ASP.NET 中的输出缓存功能使开发人员能够将控件和 HTTP 响应的生成输出存储在内存中。这非常有帮助，因为在后续 Web 请求的情况下，内容可以从输出中检索。然而，输出缓存功能在 ASP.NET 的早期版本中并不实用，因为在服务器重负载的情况下，用于输出缓存的内存可能会影响其他 Web 应用程序的功能。因此，在 ASP.NET 4.0 中，你可以为不同的控件选择不同的输出缓存提供程序。这意味着开发人员可以通过完全支持提供程序模型，将页面响应存储在 ASP.NET 工作进程之外。
- Auto-start Web application — Provides a better approach for starting an application pool, initializing an ASP.NET application, and accepting HTTP requests. In the earlier versions of ASP.NET, while loading large amount of data or performing advanced initializing processing, you needed to run initialization code in the `Application_Load` method in the `Global.asax` file. However, in ASP.NET 4.0, a new feature called auto-start has been added, which solves this problem. This feature is available when ASP.NET 4.0 runs on IIS 7.5 and Windows Server 2008.
- Redirecting a page — Removes the unnecessary round trip made by the browser for temporary redirects. In the previous versions of ASP.NET, the `Response.Redirect` method was used to forward a request to a new URL. This method uses the HTTP 302 (temporary redirect) response, which results in an extra HTTP round trip. In ASP.NET 4.0, a new `RedirectPermanent` helper method has been introduced, which uses the HTTP 301 Moved Permanently responses and avoids the round trip.
- Compressing session state — Reduces the size of session-state data. In ASP.NET, there are two options that help in storing session state in a Web form. In the first option, the session-state provider invokes an out-of-process session-state server. In the second option, the session-state provider stores the data in Microsoft SQL Server database. In case of large amount of data saved in session state, the size of serialized data is very large. Therefore, in ASP.NET 4.0, a new compression option has been introduced that can be set using the new `compressionEnabled` attribute of `sessionState` element in the configuration file.
- Range of allowable URLs — Refers to the increase in the size of application URLs. In the previous versions of ASP.NET, the maximum URL path length was 260 characters. In ASP.NET 4.0, you have to increase the URL path length by using the new `httpRuntime` configuration attribute.

### ASP.NET Web Forms

The Web forms form an integral part of ASP.NET applications. It has been enhanced several times since its release. In ASP.NET 4.0, the following new features are introduced in Web forms:

- Setting meta tags by using the `MetaKeywords` and `MetaDescription` properties of the `Page` class.
- Disabling view state for all controls or enabling view state for individual controls on a page by using the `ViewStateMode` property of the `Control` class. This implies that if the view state is disabled for a page, you can use the `ViewStateMode` property to enable view state for an individual control.
- Introducing a new feature called browser capabilities that provide support for new browsers and devices. In ASP.NET, the support for browser applications is represented by `HttpBrowserCapabilities` object in the `HttpRequest.Browser` property. In ASP.NET 4.0 the browser files are updated so that they support the new browsers and devices, such as Google Chrome, Research in Motion BlackBerry smart phones, and Apple iPhone.
- Providing support for custom code to determine browser capabilities. This new feature of ASP.NET 4.0 is referred to as browser capabilities providers, in which you can define the browser capabilities in an XML file, which resides in a machine-level or application level folder.
- Adding a built-in support for routing with Web forms. The routing feature in an ASP.NET application helps you to configure an application to use URLs and not specify the physical file names. The various improvements in routing in ASP.NET 4.0 are:
  - No need of writing custom route handler as the `PageRouteHandler` class is now a simple HTTP handler class, which can be used while defining routes
  - Improvements in `HttpRequest.RequestContext` and `Page.RouteData` properties so that it is easier to access information in the URL parameters
  - No change required in the `web.config` file to enable routing
- Introducing the `ClientIDMode` property that helps in writing client script that references HTML elements for server controls. The `ClientIDMode` property helps you in specifying how the client ID is generated for controls. The `ClientIDMode` property at the page level, when you want to define a default value for all controls in the page. The default value of the `ClientIDMode` property is `AutoID` at page level and at the control level the default value is `Inherit`. If you want to define a default setting for the `ClientIDMode` property, so that the setting is common for all controls in all pages in an application, you can set the `ClientIDMode` value in the configuration file.
- Improving the `GridView` and `ListView` controls. In the previous versions of ASP.NET, if you select 4th item on the 2nd page and then move to the 3rd page, the 4th item in the 3rd page was also selected. This was because the row selection in a `GridView` or `ListView` control was based on the row index on the page. This problem has been solved in ASP.NET 4.0, by including a new feature known as persisted selection in the `GridView` and `ListView` control. This feature can be enabled by setting the `EnablePersistedSelection` property of the control to True. In addition to this, the earlier version of the `ListView` control required you to specify a layout template, which contained a server control with a known ID. This has been removed in the new version of `ListView` control, and it now more easy to work with the control.
- Introducing the `QueryExtender` control that helps in making filtering easy. In ASP.NET, filtering excludes data, which do not meet a specified criterion, from being displayed in the data source control. This requires you to use the `Where` clause. However, in the `LinqDataSource` control, the `Where` clause was not able to expose the full functionality. Therefore, in this version of ASP.NET, the `QueryExtender` control has been introduced, which provides the following advantages:
  - Better filtering of data in comparison to using the `Where` clause
  - Can be used with not only the `LinqDataSource` control but also with `EntityDataSource` control
  - Provides multiple options to filter data, which can be used either individually or together
- Eliminating exceptions that used to arise in the earlier versions of ASP.NET with respect to markup code that did not conform to HTML, XHTML, or accessibility standards

### 对基于 MVC 的 Web 应用程序的支持

.NET Framework 4.0 和 Visual Studio 2010 包含 MVC 框架，它使 Web 应用程序的核心业务模型功能与界面特定应用程序的表示和控制逻辑分离。这种安排使得可以查看 Web 应用程序的同一数据模型的多个视图。在此架构下，数据（Model）和用户界面（View）彼此分离，因此用户界面的任何更改都不会影响数据库中的数据，反之亦然。

在 Visual Studio 2010 中，默认安装 ASP.NET MVC 2 版本。在 ASP.NET 4.0 中，对基于 MVC 的 Web 应用程序的支持有助于开发人员开发易于维护的标准 Web 应用程序。对 Web 应用程序中的 MVC 的支持消除了应用程序层之间的依赖关系。使用 ASP.NET MVC 创建的网站具有模块化架构。因此，开发人员可以处理网站的数据和逻辑，而设计师可以处理其呈现。

## ASP.NET Web 应用程序的结构

ASP.NET Web 应用程序的结构包括应用程序域、应用程序生命周期和应用程序目录结构的概念。应用程序域是在其中运行应用程序的虚拟边界，而应用程序生命周期是应用程序域存在的持续时间。另一方面，应用程序目录结构指定了组织与应用程序相关的各种实体（如引用、资源和代码文件）的目录结构，这些实体被放在单独的目录中。每个目录都有一个合格的名称，反映了其内部存储的内容。现在，让我们逐一探索这些概念。

### 应用程序域

要理解域的概念，我们首先需要了解 Web 应用程序部署后是如何工作的。我们将使用 ASP.NET 创建的 Web 应用程序部署到 Web 服务器，例如 Internet Information Services（IIS）和 Windows Activation Services（WAS）。客户端浏览器向 Web 服务器发送对 Web 应用程序的请求，Web 服务器进一步将请求传递给 ASP.NET 工作进程。然后，工作进程将代码执行分离到不同的应用程序域中，托管在同一虚拟目录上的 Web 服务和 Web 页面。托管在同一虚拟目录上的这些 Web 服务和 Web 页面在同一个应用程序域中执行，而托管在不同虚拟目录上的 Web 服务和 Web 页面则在不同的应用程序域中执行。应用程序域实际上是由通用语言运行时（CLR）实现的，其主要目的是防止并发运行的应用程序进入彼此的域。

因此，应用程序域为应用程序提供了隔离边界，这是确保在一个应用程序中运行的代码不会影响任何其他或不相关应用程序所必需的。

> **注意**
>
> ASP.NET 在称为 ASP.NET 工作进程的进程中运行，该进程允许 ASP.NET Web 应用程序在 Web 服务器上运行。它使程序的不同程序集能够协同工作。

我们从应用程序域的概念中获得了什么？应用程序域最关键的好处是 Web 应用程序的独立执行。没有任何应用程序可以访问同时运行的其他应用程序的内存资源。帮助实现应用程序独立执行的关键组件是虚拟目录。对于 Internet Information Services（IIS）Web 服务器，虚拟目录及其所有子目录是在 IIS 控制台中创建的。存储在虚拟目录中的一些主要应用程序实体是：

- Web 页面 – 在 Microsoft .NET 环境中用作 Web 窗体页面的文件。这些文件的扩展名为 `.aspx`。
- Web 服务 – 使你能够使用 XML Web 服务与其它计算机和平台上的应用程序共享信息的文件。这些文件具有 `.asmx` 扩展名。
- 代码隐藏文件 – 包含 ASP.NET 页面代码的源代码文件，位于单独的类文件中。源代码文件具有 `.cs` 扩展名。
- 配置文件 – 配置文件，例如 `web.config`，它存储 Web 应用程序的配置设置，以及 `machine.config`，它存储 Web 应用程序运行所在机器的配置设置。
- `Global.asax` 文件 – 包含事件处理程序以响应事件的文件，例如 ASP.NET Web 应用程序首次启动。

此外，虚拟目录中还有其他资源，例如图像和 XML 文件。虚拟目录封装了 ASP.NET Web 应用程序的所有这些资源，并在应用程序首次被调用时形成一个应用程序域。

### 应用程序生命周期

应用程序生命周期是指应用程序域持续存在的时间跨度。现在，这并不意味着应用程序生命周期等同于应用程序运行的时间跨度。事实上，应用程序域可能在多种情况下关闭，包括特定错误条件、配置更改或 Web 服务器关闭。因此，应用程序的运行时可能会遇到应用程序域的重复重启。应用程序域可能需要在以下情况下重启：

- 队列中请求过多
- 应用程序内存使用过多
- 应用程序生命周期过长
- `web.config` 文件被修改
- 替换现有的动态链接库（`.dll` 文件）或 Web 文件

应用程序域的关闭在任何方面都不是坏事。事实上，开发人员故意在 `machine.config` 文件中包含特定设置，以确保应用程序域在特定时间间隔内被回收。这有助于监控应用程序的性能。

### 应用程序目录结构

高效设计的目录结构在 Web 应用程序开发中起着关键作用。它将应用程序使用的所有代码和资源分隔到不同的目录中，从而提高开发人员的生产力。让我们举一个例子来说明这一点。假设你正在开发一个 Web 应用程序，其代码已在不同模块下划分，每个模块由不同的团队成员处理。在这种情况下，你只需将团队成员开发的代码放在不同的目录中并运行应用程序即可。在这种方式下，调试过程也可以以更结构化的方式进行。使用目录结构的另一个优点是它增强了应用程序的可重用性。由于其结构化的代码文件和应用程序资源，你在长期内升级应用程序变得更容易。

在 ASP.NET 1.x 版本及更早版本中，应用程序只有一个默认目录和 bin，你必须创建自己的自定义目录（如果有）。然而，在 ASP.NET 4.0 中，支持默认目录结构，它为 Web 应用程序提供了多个内置目录。这些目录如下：

- **`Bin`** – 包含编译后的 .NET 程序集，其中包含预编译的 Web 页面和 Web 服务类。你可以直接在应用程序中使用这些程序集，从而减少为 ASP.NET Web 应用程序编写的代码量。
- **`App_Code`** – 包含源代码文件，这些文件会被动态编译以供 ASP.NET Web 应用程序使用。
- **`App_GlobalResources`** – 包含可在 ASP.NET Web 应用程序的所有 Web 页面以及控件中使用的资源。
- **`App_LocalResources`** – 包含只能由 ASP.NET Web 应用程序的特定 Web 页面访问的资源。
- **`App_WebReferences`** – 包含 ASP.NET Web 应用程序使用的 Web 服务的引用。
- **`App_Data`** – 包含 ASP.NET Web 应用程序的数据库和 XML 文件。
- **`App_Browsers`** – 包含浏览器定义文件，用于识别不同 ASP.NET Web 应用程序的浏览器。
- **`App_Themes`** – 包含 ASP.NET Web 应用程序使用的主题。主题可以应用于控件或 Web 页面，或整个 ASP.NET Web 应用程序。

## ASP.NET 生命周期

ASP.NET 生命周期向您展示 ASP.NET 如何处理 Web 页面以生成动态输出。它还向您展示应用程序和单个页面如何实例化和处理，以及 ASP.NET 如何动态编译页面。我们将在以下部分详细讨论这些方面：

- IIS 7.5 上 ASP.NET 应用程序的生命周期
- ASP.NET Web 页面的生命周期

### IIS 7.5 上 ASP.NET 应用程序生命周期

在本节中，我们将了解在 IIS 7.5 集成模式下运行的 ASP.NET 应用程序的完整应用程序生命周期。IIS 7.5 还支持经典模式，其工作原理类似于在 IIS 6.0 中运行的任何 ASP.NET 应用程序。

在 IIS 7.5 的集成模式下，应用程序资源请求过程与 IIS 6.0 类似。然而，在 IIS 7.5 中，除了 IIS 6.0 中的事件外，在请求处理期间还引发了 `MapRequestHandler`、`LogRequest` 和 `PostLogRequest` 等三个新事件。此外，IIS 7.5 使用统一的请求处理管道来处理整个应用程序资源请求，而 IIS 6.0 中则没有此功能。

> **注意**
>
> IIS 6.0 使用两个单独的管道来处理应用程序资源请求。一个管道用于非托管代码过滤器和扩展；另一个用于托管代码组件。

使用 IIS 7.5 集成管道的好处如下：

- 引发 `HttpApplication` 类的所有事件，以启用 IIS 7.5 中的 ASP.NET 模块。
- 能够配置托管代码和非托管代码模块。此外，使用集成管道，我们可以为所有请求启用或禁用托管代码模块，即使用户请求的是 ASP.NET Web 页面。
- 使网站能够在管道的任何阶段调用托管代码模块，例如在处理用户请求之前、请求处理后或用户请求处理中途。
- 使网站能够通过 `Web.config` 文件注册然后启用或禁用模块。

**表 13.3：IIS 7.5 集成模式下 ASP.NET 应用程序生命周期的阶段**

| 阶段 | 描述 |
|---|---|
| 用户请求应用程序资源 | 指用户在 Web 服务器上请求应用程序资源的阶段。此请求通过统一管道，该管道调用 ASP.NET 模块。现在，即使页面具有 `.htm` 扩展名并且未明确映射到 ASP.NET，此请求仍可利用 ASP.NET 功能，例如嵌入式身份验证和授权过程，以及托管代码。在早期的 IIS 6.0 中，由于使用两条独立的管道，这些进程需要手动配置。 |
| 统一管道接收第一个用户请求。 | 指定当首次收到对应用程序资源的请求时，会使用 `ApplicationManager` 类的对象创建应用程序域。应用程序域是一个进程，用于将应用程序彼此隔离，并支持处理用户请求。在此阶段，当在应用程序域内创建 `HostingEnvironment` 对象时，也可以访问有关应用程序的信息。 |
| 为每个用户请求创建响应对象 | 指的是创建响应对象的阶段，例如 `HttpContext`、`HttpRequest` 和 `HttpResponse`。`HttpContext` 类拥有 `HttpRequest` 和 `HttpResponse` 等对象。这些对象仅对当前用户请求有效。此时，`HttpRequest` 对象保存有关当前请求的信息。`HttpResponse` 对象保存发送给用户的信息，例如 Cookie 和最终输出。 |
| 创建 `HttpApplication` 类的对象并将其分配给请求 | 指的是创建 `HttpApplication` 类的对象时启动应用程序的阶段。但是，如果存在 `Global.asax` 文件，则会创建 `Global.asax` 类的对象，而不是 `HttpApplication` 类的对象。`Global.asax` 类派生自 `HttpApplication` 类，并表示 ASP.NET 应用程序。需要调用的模块取决于父应用程序的托管代码模块。此外，它还取决于 `Web.config` 文件中定义的模块。你可以通过在 `Web.config` 文件的 `system.webServer` 部分的 `modules` 元素中指定模块名称来添加或删除模块。 |
| `HttpApplication` 类处理用户请求。 | 指定 `HttpApplication` 类执行以下任务来处理用户请求：1. 验证用户请求，以确认它不包含任何恶意标记。2. 执行 URL 映射，以确认 `Web.config` 文件的 `UrlMappingsSection` 部分中是否指定了任何 URL。3. 按显示的顺序调用以下事件和方法：- `BeginRequest` - `AuthenticateRequest` - `PostAuthenticateRequest` - `AuthorizeRequest` - `PostAuthorizeRequest` - `ResolveRequestCache` - `PostResolveRequestCache` - `MapRequestHandler` - `PostMapRequestHandler` - `AcquireRequestState` - `PostAcquireRequestState` - `PreRequestHandlerExecute` - 调用 `IHttpHandler` 类的 `ProcessRequest` 方法来处理请求 - `PostRequestHandlerExecute` - `ReleaseRequestState` - `PostReleaseRequestState` - 仅当为 `HttpResponse` 类定义了 `Filter` 属性时才执行响应筛选。- `UpdateRequestCache` - `PostUpdateRequestCache` - `LogRequest` - `PostLogRequest` - `EndRequest` - `PreSendRequestHeaders` - `PreSendRequestContent` |

### ASP.NET 页面生命周期

当用户请求 ASP.NET 网页时，该页面会经历多个阶段，这些阶段统称为 ASP.NET 网页的生命周期。例如，页面的生命周期始于用户请求网页，止于页面完全呈现到浏览器。如果你想在页面的特定阶段执行特定操作，就应该完全理解页面生命周期。此外，如果你正在为项目创建任何自定义控件，则应该透彻了解页面生命周期，因为控件的生命周期取决于页面的生命周期。

现在，我们来了解页面生命周期中涉及的不同阶段。

#### ASP.NET 页面的不同阶段

通常，ASP.NET 网页会经历 8 个阶段。表 13.4 列出了这些阶段：

**表 13.4：ASP.NET 网页的不同阶段**

| 阶段 | 描述 |
|---|---|
| 页面请求 | 指当用户请求网页时页面生命周期开始。当用户第一次请求页面时，ASP.NET 会确定该请求是新请求还是旧请求。如果是新请求，则编译并执行该页面。但是，如果是旧请求，则发送页面的缓存副本而不执行页面。 |
| 开始 | 指配置页面的 `Request` 和 `Response` 属性的阶段。页面还通过使用 `IsPostBack` 属性来确定请求是旧请求还是新请求。在此阶段，还会配置页面的 `UICulture` 属性。 |
| 页面初始化 | 指通过设置 `UniqueID` 属性为页面上的每个控件分配唯一 ID 的阶段。在此阶段，如果有任何主题，则会将其添加到页面中。如果请求是旧请求，则不会加载回发数据，并且仍需将控件属性值还原为视图状态值。 |
| 加载 | 指如果当前请求是旧请求，则页面上的控件属性将从视图状态和控件状态中加载数据。 |
| 回发事件处理 | 指如果发出的请求是旧请求，则可以调用任何事件处理程序。 |
| 验证 | 指页面上使用的验证控件调用 `Validate` 方法的阶段。 |
| 呈现 | 指在呈现页面之前，会保存视图状态和页面上的所有控件。在呈现页面时，它会为页面上的每个控件调用 `Render` 方法，并将呈现阶段的输出写入页面的 `Response` 属性的 `OutputStream` 对象。 |
| 卸载 | 指在此阶段卸载页面的 `Response` 和 `Request` 属性，并执行任何所需的清理操作。 |

#### ASP.NET 页面生命周期事件

在页面生命周期的每个阶段，页面都会引发一些事件，你可以通过运行自己的代码来处理这些事件。为了处理控件事件，你可以通过声明性属性（例如 `onclick` 或代码中的 handle）将事件处理程序绑定到指定事件。

ASP.NET 网页还支持自动事件连接。这意味着，当引发某些事件时，ASP.NET 会搜索与该事件对应的方法，并自动执行这些方法。如果 `@Page` 指令的 `AutoEventWireup` 属性为 True，则页面事件会自动绑定到用于处理这些事件的方法。以下是最常见的页面事件：

##### Preinit 事件

`Preinit` 是页面生命周期中发生的第一个事件。它用于检查页面的 `IsPostBack` 属性，以确定页面是否首次被处理。它还创建或重新创建动态控件，动态设置 `Theme` 属性和母版页。此外，它还会获取和设置配置文件属性值。

> **注意**
>
> 如果发出的请求是回发请求，则控件值尚未从视图状态恢复。如果在此阶段设置控件属性，该值可能会在下一个事件中被覆盖。

##### Init 事件

该事件在所有控件初始化以及应用任何外观设置后引发。它用于读取或初始化控件属性。

##### Load 事件

调用 `OnLoad` 事件方法来设置控件属性和建立数据库连接。`Page` 类在网页上调用 `OnLoad` 事件方法，然后对每个子控件递归执行相同操作，直到页面和所有控件都加载完成。

现在，让我们详细了解代码是如何被解析并编译成一个或多个程序集的。

## ASP.NET 4.0 中的编译

ASP.NET 首先将代码编译成一个或多个程序集，这些程序集不过是扩展名为 `.dll` 的文件。你可以选择多种语言（例如 VB 和 C#）来编写 ASP.NET 代码。编译时，代码会被转换成为一种与语言无关且与 CPU 无关的语言，称为 Microsoft 中间语言（MSIL）。编译提高了 Web 应用程序的性能、安全性、稳定性和互操作性。在运行时，MSIL 会被转换为 CPU 特定的指令，这些指令特定于运行应用程序的计算机的处理器。ASP.NET 4.0 中编译的优点如下：

- 提高性能，因为编译后的代码不需要额外的解析，系统可以更好地识别预编译代码。
- 提供安全性，因为它缺乏可读性和抽象性，因此编译后的代码无法被反向还原。
- 提供稳定性，因为在编译过程中会检查代码是否存在任何类型的语法错误、类型安全性或任何其他问题。
- 提供互操作性，因为 MSIL 代码支持任何类型的 .NET 语言。这意味着在 C# 中创建的 ASP.NET 页面中，你可以添加引用由 Visual Basic 创建的 `.dll` 文件。

ASP.NET 4.0 的编译架构包含众多功能，具体如下：

- 多语言支持 – 指定你可以在单个 ASP.NET 应用程序中使用不同的语言。在 ASP.NET 4.0 应用程序中，会创建多个程序集，每个程序集支持应用程序中使用的每种语言。因此，对于存储在 `App_Code` 文件夹中的代码，你可以为每种语言指定一个子文件夹。
- 自动编译 – 在用户首次请求网站资源时，编译 ASP.NET 应用程序及任何依赖资源。按规则，ASP.NET 应用程序为每个应用程序目录创建一个程序集，并为主目录创建一个程序集。
- 灵活部署 – 指定在部署 ASP.NET 应用程序时，你只需将应用程序的源代码复制到 Web 服务器。ASP.NET 提供了两种预编译选项。首先，你可以在部署之前编译网站，或者其次，你可以在部署之后，但在用户向网站发送请求之前编译它。ASP.NET Merge 工具（`Aspnet_merge.exe`）使你能够组合和管理由 ASP.NET 编译工具（`Aspnet_compiler.exe`）创建的程序集。该工具使你能够为部署到目标位置（例如生产服务器）的 ASP.NET Web 应用程序进行编译。ASP.NET Merge 工具在由 ASP.NET 版本 2.0 或更高版本创建的程序集上工作。它为目标网站中的每个内容文件夹或内容文件创建一个程序集。它还为部署提供了额外的灵活性。Merge 工具使你能够执行以下任务：

  - 为整个网站创建一个程序集
  - 为每个网站文件夹创建一个程序集并为程序集名称添加前缀
  - 为仅网站 UI 元素（如页面和控件）创建一个单一程序集
