
与此同时，NeXT 采取了另一个方向。如果分支像目录，为什么不直接使用目录呢？NeXT 在标准的 UNIX 文件系统之上提供了分支的功能，只需使用目录来代替文件。

被预期视为文件的目录被称为 Bundle。对于原始的低级文件系统操作和其他操作系统，它们看起来像目录。例如，如果你将一个 OS X 应用程序 Bundle 拷贝到 USB 驱动器并在 Windows 上查看，它看起来就像任何其他目录。然而，当你在 Finder 中查看它时，它看起来像单个文件。

你在几乎任何 Objective-C 程序和应用程序中都会使用的两种 Bundle。它们都包含一些可执行代码（程序或共享库）和一组资源。

具体的布局取决于系统。GNUstep 使用旧的 NEXT 样式 Bundle 布局，而 OS X 使用的是稍微简单的一种。你完全可以产生同时具有 GNUstep 和 Cocoa 布局的 Bundle，允许同一个 `.app` 无需重新编译即可在系统间迁移。

你可以通过向 `NSBundle` 发送 `+mainBundle` 消息来获取应用程序的主 Bundle。这是一个用于封装 Bundle 的类。它跟踪所有动态加载的 Bundle。

在 OS X 上，文件系统的布局是非常明确的。你可能会硬编码路径并期望它们正常工作。但如果你将代码移植到其他平台，你会发现事情会发生严重的损坏。

这是 OpenStep 程序员经常遇到的问题之一。例如，在 Solaris、OPENSTEP 和 Windows NT 之间移植代码，需要为每个平台更改许多硬编码路径。

在 Apple 购买 NeXT 后，他们发布了新版本的 OPENSTEP，带有一个 MacOS 兼容层以及一个名为 Rhapsody 的新用户界面。它使用了与 OPENSTEP 相同的 NeXT 文件系统层次结构，并在根目录下包含一个 `/NeXT` 文件夹，该文件夹包含了层次结构中非 UNIX 风格的部分。

随着 Rhapsody DR2，Apple 对目录布局进行了一些重大更改，并引入了现在 OS X 用户熟悉的布局。为了方便使用，并支持 Windows 上的 YellowBox (Cocoa)（该产品在不久后就被停止了），他们引入了 `NSSearchPathForDirectoriesInDomains()` 函数。

此函数返回一个用于特定用途的目录数组。当你调用此函数时，第一个参数描述了你想要的目录类型。这可能是一个应用程序目录、库目录等。第二个参数是文件系统域（domain）。

OS X 像 OPENSTEP 一样将文件系统层次结构划分为若干域，这些域的内容大致相同，但用途不同。这些域是有顺序的，因此你应该优先使用高优先级域中的文件。四个域如下：

- **User (用户)**：该域位于用户主目录内。这里的文件对用户私有，并完全由用户控制。
- **Local (本地)**：包含机器本地文件的域。在 OS X 上，这包括类似 `/Library` 的目录，该目录可以由本地系统管理员修改。
- **Network (网络)**：在该域中看到任何内容是非常稀见的。你将在独立机器或异构网络中的的机器上看不到它。它用于由网络管理员控制的目录。
- **System (系统)**：最后一个域包含系统文件。通常情况下，你永远不应该在该域中的任何位置写入内容，尽管你可以从中读取。你做的任何修改都可能在用户下次更新系统时被撤销。

并不是每个类型的目录都存在于每个域。例如，系统域中没有文档（documents）目录，且在那里这样做是没有意义的。

## 线程

Objective-C 中的线程封装在 `NSThread` 对象中。创建线程有两种方法。第一种类似于标准方法，而第二种旨在类似于 Java。

当你使用 `NSThread` 创建线程时，可以设置它的优先级。最常见的做法是创建一个创建一个释放池。创建线程在 Objective-C 中是一个相对昂贵的操作，就像在 C 中一样。进程必须为线程栈分配内存，创建调度的所有内核数据结构，并为线程本地存储分配额外空间。因此，在创建线程后保持它们运行是一个好主意。

在线程中创建运行循环（run loop）是实现此点的良好方法。你可以注册定时器触发，监控文件描述符的新数据，并在新线程中使用事件驱动的编程风格。POSIX 定义了线程的两种竞争范围。OS X 只实现了系统范围。

`NSThread` 以类方法和实例方法实现了 `threadPriority` 和 `setPriority`。发送给类时，它们控制当前线程的优先级；发送给实例时，它们控制该对象封装的线程的优先级。

线程的优先级决定了它将获得多少 CPU 时间以及在获得访问 CPU 的权限之间等待多久。通过低级 POSIX API 控制线程优先级，你还可以设置调度策略。执行这些操作的函数都是 POSIX 实时扩展的一部分，该扩展还提供了信号队列等。这些尚未被 Objective-C API 暴露（目前）。

使用此 API 设置的优先级是 0 到 1 之间的双精度浮点值。这些值将被缩放到调度器理解的某些整数范围，所以你应该记住微小的差异会被四舍五入。

## 控制线程优先级

较低优先级的进程运行。如果你将线程优先级设置为大于 0.5，请记住这会对系统的其他部分产生不利影响。这仍然不会导致完全的饥饿。在 OS X 10.6 中，对于纯粹的 CPU 密集型任务，最高线程优先级获得的 CPU 时间略高于最低优先级分配的时间的一倍多。大多数任务都会涉及一些时间等待从磁盘读取数据。处于阻塞状态的线程无论其优先级如何，都不会消耗任何 CPU 时间。

OS X 的调度策略与传统的 UNIX 模型相反，在传统模型中，只有超级用户才能提高进程的优先级。有趣的是，在 OS X 的最新版本中，线程优先级对线程获取 CPU 时间的影响实际上大于拥有该线程的进程优先级。这意味着，虽然你不能提高进程的优先级，但可以通过提高进程中所有线程的优先级来实现相同的效果。

防止普通用户增加进程优先级的原始目的是防止一个用户获取不公平的 CPU 时间。OS X 系统倾向于单用户机器，因此这个问题并不那么严重，但你仍然可以夺取同一用户下更重要任务的处理器时间。例如，实时视频捕获对性能非常敏感，如果你的程序决定将其优先级设置为足够高，导致捕获应用程序丢帧，用户可能会非常恼怒。

设置线程优先级时要体贴。通常，你只应该使用 0 到 0.5 之间的范围。只有在绝对没有其他选择的情况下，才将线程设置为高于默认水平。不要仅仅因为你正在执行某些 CPU 密集型操作并希望它运行得快就这样做。

## 同步线程

```
static NSLock *lock;

static NSMutableArray *messages;

void recordLogMessage(NSString *msg)

{

  [lock lock];

  @try

  {

    [messages addObject:msg];

    NSLog("%@", msg);

  }

  @finally

  {

    [lock unlock];

  }

}
```
来自：`lock.m`

你可以通过多种方式同步两个线程。执行此类同步的类都遵循 `NSLocking` 协议。它定义了两个方法：`-lock` 和 `-unlock`。

简单的锁类是 `NSLock`，它实现了互斥锁（mutex）。一次只能有一个线程锁定它，因此向它发送 `-lock` 消息将导致任何其他向同一对象发送 `-lock` 消息的线程阻塞，直到你发送了相应的 `-unlock` 消息。

这对于保护短的临界区域很有用。对于较长的临界区域，`NSRecursiveLock` 通常更有用。如果你在同一个线程向 `NSLock` 发送两个 `-lock` 消息，就会导致死锁。你可以向 `NSRecursiveLock` 发送任意数量的 `-lock` 消息，只要发送相同数量的 `-unlock` 消息即可。这对于从已获取锁的代码以及未获取锁的代码调用的方法非常有用。

传统上讲，这些类的问题在于它们与异常处理结合得并不好。如果你获取了锁然后调用了抛出异常的内容，就会出现问题。锁将永远不会释放。

当 Apple 引入新的异常处理关键字时，它们也引入了 `@synchronized`。它会在任意对象上锁定，并确保在抛出异常时释放锁。

总的来说，使用这个关键字是一个坏主意。尽管 Java 程序员对其很熟悉，但其实现非常低效。它需要将锁与对象关联，而且即使在不理想的情况下也总是使用递归锁。你可以通过确保在 `@finally` 块中发送 `-unlock` 消息来实现相同的效果。

如果你确定所有调用的方法或函数都不会抛出异常，就可以避免使用 `@try` 和 `@finally` 块，但在 GNU 和现代 Apple 运行时，它们没有任何运行时开销。

## 存储线程特定数据

```
NSMutableDictionary *threadDict = [[NSThread currentThread] threadDictionary]; [threadDict setObject:@"default" forKey:@"NewKey"];
```
来自：`threadDict.m`

一旦你有了线程，你通常想为线程私有地存储一些数据。Cocoa 中这方面的例子是当前图形上下文，它必须对任何绘图代码可用，但不能在线程之间共享。

通常，你使用 `pthread_set_specific()` 函数来实现这一点，它存储与当前线程关联的指针。这通常通过将内存区域的地址存储在寄存器中，并使用该区域起始的固定偏移量来处理每个线程特定数据来实现。这意味着你需要为每个线程中的每个线程本地指针留出空间，即使你只将其中一个设置为非 NULL 值。

如果 Cocoa 像这样存储单个图形上下文，那么每个线程都需要一个字大小的空间，尽管大多数程序只需要在一个或可能两个线程中拥有有效的图形上下文。

解决此问题的方案是线程字典（thread dictionary）。这是一个与线程关联的可变字典。你每个线程只需要一个字大小的空间，但你可以在其中存储任意数量的对象。只有与给定键关联了值的线程才需要空间来存储它。

通过向当前线程发送 `-threadDictionary` 消息访问线程字典。然后你可以像操作其他字典一样操作它。当线程退出时，字典会被销毁。由于字典保留其参数，这意味着从线程引用的任何对象将在析构函数运行后被释放。你可以利用此在线程退出时运行代码，但不建议这样做。线程在退出之前会发布 `NSThreadWillExitNotification`，所以如果你想运行某些代码，只需观察它即可。

**注意：** 在大多数平台上，你可以使用 `__thread` 关键字，这是一个将变量存储在线程本地存储 GCC 扩展。Darwin 加载器不支持线程局部，因此在 OS X 上是不可能的。这可能会很快改变，因为类似的功能已经在 C 和 C++ 标准的后续版本中了。
