
调试版本还有几个可以开启的标志，以执行额外的检查。第一个标志是 `ilovebear`（这个名字背后有一个有趣的故事），它会在返回存放在其中的值之前将传递的字符串填充到极限限制。这保证了所有传入的缓冲区都足够长。

调试版本还有 `ValidateSpaces` 调用，它结合 `EnableFreeChecking` 和 `EnableHeapChecking` 标志会对堆进行额外的检查。此调用在 Windows 中会增加约 20% 的开销。然而，它会写入空闲内存。

`ValidateCodeSegments` 调用仅在实模式下有用。如果你的程序将在实模式下运行，那么你应该不时使用此测试。但是，如果你的程序只在保护模式下运行，那么没有理由使用此调用。

Windows 提供了 Stress Applicator（压力测试器）和 Heap Walker（堆遍历器），它们可以用于消耗资源。Stress Applicator 可以耗尽堆，留下固定数量的空闲内存。它可以对全局堆、程序本地堆以及 GDI 堆（通常被称为系统资源）执行。它还可以使用磁盘空间和文件句柄，再次留下有限或没有资源。

Heap Walker 也可以使用全局堆以及可丢弃段。Stress Applicator 和 Heap Walker 均允许你在资源完全耗尽的情况下测试你的应用程序。

### RT-link

RT-Link 值得在这里提到。RT-Link 是一个用于 DOS 程序的复杂链接器，从上看，它不属于这一节。然而，RT-Link 实现了一些工具，展示了正确实现某些错误检查可以有多强大。

RT-Link 允许你链接程序以在 8088 代码上使用虚拟内存（在某些情况下也包括数据），代码保存在磁盘上，并在需要时调入内存。与覆盖链接器不同，RT-Link 维护一个页面列表并将代码加载到 LRU 页面中。

不用俗说，程序每次运行时的加载方式都非常不同。因为调用了其他代码的代码可以被卸载（然后在返回时重新加载），如果任何一个代码页依赖另一个代码页实际上位于内存中，你就处于一种非常危险的局面。

这不是 RT-Link 的 bug。你可以告诉 RT-Link 你认为一个代码页直接访问另一个页是安全的，从而节省通过 RT-Link 虚拟内存管理器带来的性能损失。

然而，如果你在某处错了，你可能会访问一个通常仍在内存中的页面。这会导致只在内存较小的系统上，或在按特定顺序调用一组函数的任何系统上发生的 bug。

RT-Link 包含一个命令 (`VM_MURPHY`)，为所有虚拟内存交换仅分配一个页面。当与此命令链接时，程序运行速度极慢。然而，内存中任何时候都不会多于一个页面。如果一个页依赖于另一个页在内存中，它就会崩溃。

这是一个工具供应商整合有助于发现 bug 技术的值得赞的范例。此外，这个命令是一种只有工具供应商才能整合的技术。如果有更多工具供应商提供这样的功能就好了……

### 调试器

确保你有一个良好的调试器。对我个人而言，我倾向于在 386 上使用 Soft-Ice，在 286 或 8086 上使用 Periscope。然而，我更倾向于用汇编语言进行调试。尽管 Soft-Ice 和 Periscope 都有 C 源码级调试，但通常比编译器厂商提供的源码级显示慢一步步。

当你真的需要在 386 模式下深入研究 Windows 时，你只有两个调试器可选：`wdeb386` 或 Win-Ice（Windows 版的 Soft-Ice）。`wdeb386` 随 Windows SDK 附，是一个优秀的命令行调试器。然而，Win-Ice 是一个全屏调试器，并在源码级工作。

Periscope 有一个 Windows 调试器。然而，对于系统级（在 VxDs 上）调试，它比 Win-Ice 或 WDE386 受限得多。对于应用级调试，它不如 Multiscope。此外，它需要两个通过串口线连接的 80386 系统。

用汇编语言调试的宝贵之处在于，你可以看到最终代码的真实情况。这不仅允许你看到编译器是否生成了糟糕的代码（这偶尔会发生），还能看到代码的效率如何。随着 C++ 的出现，这将变得更加重要，因为一个 `+` 可能会变成一组极其缓慢且复杂的指令。

随编译器附带的源码级调试器（如微软提供的）以低得多的提供了大部分相同的功能。虽然 Soft-ice 会稍微改变系统，但 Periscope 辅助辅助卡对一切都没有影响。这造成了有时是至关重要的区别。

最后，如果你真的需要深入硬件，并且发现 Soft-ice 干扰了某些时序问题，你需要硬件设备。在这种情况下，只有一个选择：Periscope。

### Soft-Ice

由 Bounds Checker 的团队带来，Soft-Ice 利用 386 的功能通过软件为你提供一个 8086 ICE。它非常出色地接近这一目标，但在某些非常微妙的问题上稍有不逮。

如果你正在调试实模式下的 DOS 程序，这个调试器在以后将是无价之宝。你可以设置在程序读取或写入某个内存位置时中断，然后让它以全速运行，直到发生读/写操作（用普通的调试器试试看吧）。

Soft-Ice 使用 80386 的几个功能实现了这一魔术。首先，80386 拥有几个调试寄存器，可用于访问特定内存位置时触发中断。这些寄存器很少，且只能设置在字节到双字范围内的触发中断。

Soft-Ice 还利用了 80386 的分页功能。为了在内存范围内设置断点，Soft-Ice 将内存页标记为“不存在”。然后，当访问该页时，Soft-Ice 会判断页面上的目标范围是否被触。如果是，它就会停止操作；如果不是，它就允许操作并继续。

除非断点范围所在的页面其他内容被频繁访问，否则这种方法是有效的。因为页面是以 4K 为块的，这可能是一个真正的问题。最常见的性能问题是对局部变量的访问设置断点。因为局部变量在栈上，每次栈访问都会导致缺页异常。

Soft-Ice 并非总是完美的调试解决方案。然而，在大多数情况下，它提供了你所需的所有 ICE 能力——而且价格比任何真实的 ICE 都便宜得多。

Soft-Ice 还有一个 Windows 版本，称为 Win-Ice。Win-Ice 不仅调试 Windows 应用程序，还调试 Windows 设备驱动程序、虚拟驱动程序以及在 Windows框中运行的 DOS 程序。简单来说，它的功能和能力范围是惊人的。**

## iscope

一个用于 DOS、Windows 和 OS/2（无论是什么）的调试器。在 Windows 中，它作为一个 Windows 应用程序运行，为你提供了一个极其强大的界面。虽然在底层调试方面并不理想，但在源码级调试应用程序方面它表现优异。

很难用几段话描述 Multiscope。它是市场上最好的调试器。它提供了多种界面，最好的使用方法是它的 Windows 界面。

在 Windows 下，你可以调试 DOS（在框内）和 Windows 程序。你可以调试运行在同一台机器或通过串口线运行在不同系统上的程序。你可以使用双显示器，但如果你的第二个显示器是字符界面而不是 Windows，那么 Multiscope 的魅力之一在于它是基于 Windows 的。通过 Windows 提供窗口化数据而不是使用字符显示，使其比任何其他调试器都有更好的界面。此外，Windows 提供了比80x25 单色适配器（MDA）更好的尺寸和布局。

此外，该界面通常比字符界面更容易用。所有支持基于 Windows 应用的理由都适用。此外，Windows 使得修改内存等操作变得非常简单——点击并输入。

Multiscope 在一个功能上领先所有调试器光年：图形数据显示。它提供了查看数据的常规能力，此外，当你点击结构或指针时，它会显示结构的内容。更棒的是，它还有一个图形数据窗口。

Graphic Data 功能会绘制你的数据的图像。每个结构被绘制成一排框。结构值将位于每个框中。结构中的每个指针将通过名称识别，并有一个指向其指向位置的箭头。有时一图胜于千言，Multiscope 证明了这一点。

遗憾的是，Multiscope 被设计为应用程序调试器。对于调试系统级程序，你需要 Soft-Ice 或 Periscope。但如果你在编写应用程序，这就是要使用的调试器。
