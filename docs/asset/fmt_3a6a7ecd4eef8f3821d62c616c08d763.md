## .NET Framework 4 中的安全更改

安全性是 Web 应用程序的关键功能。安全性可防止 Web 应用程序被未经授权访问或黑客攻击。黑客通常会操纵 Web 应用程序的功能，从而使 Web 应用程序对用户变得无关紧要。安全性还可提供抵御威胁或病毒攻击的防御。没有安全性，开发人员就无法考虑开发 Web 应用程序。因此，.NET Framework 自发布以来就包含安全功能，该功能被广泛用于保护 Web 应用程序。.NET 中存在各种类型的

### 条件性 APTCA

在 .NET Framework 4 中，`AllowPartiallyTrustedCallersAttribute` (APTCA) 允许主机有条件地识别那些希望向部分信任调用者展示的程序集。候选程序集是为部分信任开发的，因此它必须是 APTCA 或完全透明。APTCA 使用 `PartialTrustVisibilityLevel` 枚举来指定 APTCA 程序集的可见性级别。

### 证据对象

任何由安全策略标识的类型对象的对象都称为证据。安全策略由代码组组成。在 .NET Framework 的早期版本中，如果托管代码将其作为证据应用，则几乎所有对象都可以用作证据对象。在运行时，证据对象不被视为对象引用，并且不对它们应用类型安全。这在 .NET Framework 中造成了问题，因为它对可用作证据对象的类型施加了隐式限制。即将用作证据的对象必须可序列化且不为 `null`。如果不是这样，则 CLR 会抛出异常。

为避免异常，.NET Framework 4 包含了 `EvidenceBase` 类，以对可能被视为证据的对象施加约束，并为证据对象添加新的要求和功能。此类确保证据对象应可序列化。

### 证据集合

在 .NET Framework 的早期版本中，CLR 生成的完整证据对象集与程序集在加载时一起使用。证据对象存储在列表中，可用于搜索特定对象。因此，所有证据对象都会显示，无论它们是否被使用。这种行为在 .NET Framework 4 中得到了改进，因为证据集合现在像字典一样运行。现在，无需通过迭代搜索特定的证据对象，而是可以请求特定证据，集合会返回证据。如果请求的证据对象未找到，则证据集合返回 `null`。字典模型在请求时生成证据对象。

### 引入身份验证和授权

当你将应用程序或资源分发给用户时，最先想到的问题是它的脆弱性或安全性如何。根据应用程序或资源的脆弱性，你可能希望限制其对用户的访问。为了限制访问并使应用程序或资源安全，你需要识别并仅允许特定人员或用户访问。其他没有正确访问权限的人员或用户不应能够使用或访问应用程序或资源。为此，你需要识别由有效系统（如计算机上的操作系统）认可的人员或用户。识别应用程序或资源用户的过程称为身份验证。通常，使用用户名和密码的组合来验证用户。如果用户的凭据（用户名和密码）有效，则用户成为已验证用户；否则，用户将被拒绝访问请求的应用程序或资源。

用户经过身份验证后，接下来要考虑的问题是是否提供对请求的应用程序或资源的访问。授予已验证用户的访问权限取决于用户被允许或禁止对请求的应用程序或资源执行的操作或行为。许多应用程序或资源可能面临被其他用户误用或无意操纵的风险。因此，在决定允许已验证用户执行的操作之前，你需要解决用户从访问资源中可能获得什么。在解决此问题后，你可以为已验证用户分配各种操作。此决定已验证用户是否可以访问预期应用程序或资源的过程称为授权。已验证用户的授权取决于用户拥有的特权。图 36.2 显示了 .NET Framework 中身份验证和授权过程的整体图示：

### 基于角色的安全

Web 提供了大量可在不同场景中使用的服务和功能。最近，使用中的 Web 应用程序数量、连接的质量和速度都有急剧增加。由于其连接性和交互性（服务器与客户端之间），存在大量威胁影响 Web 应用程序的安全性和可靠性。第三方用户或应用程序可以通过多种方式获得对 Web 应用程序的访问，然后操纵 Web 应用程序的功能或数据。因此，Web 应用程序需要一个强大且无懈可击的安全机制。Web 开发人员必须彻底了解应用程序的潜在安全风险，然后据此纳入所需的安全措施。Web 应用程序的一些安全风险包括网络钓鱼、黑客攻击和病毒攻击。

Web 开发人员在构建 Web 应用程序的安全系统时应牢记以下事项：

- Web 应用程序如何工作？
- 服务器与客户端之间通信的性质和范围是什么？
- Web 应用程序有哪些安全威胁？
- 这些安全威胁如何影响 Web 应用程序的正常运行？
- 需要实施的安全级别是什么？

根据上述标准，Web 开发人员可以为 Web 应用程序实施安全系统。Web 开发人员可以通过多种方式保护应用程序，其中一些包括在 Web 服务器上配置防火墙和加密 Web 上交换的数据。其中一些，例如防火墙，可能仅在一定程度上有用。在 .NET Framework 中，你可以通过多种方式保护 Web 应用程序（ASP.NET Web 应用程序）。

你构建的应用程序，无论是 Windows 还是 Web 应用程序，都使用大量数据和资源。其中一些数据和资源可能至关重要或敏感，因此你不希望使用应用程序的人能够访问此类数据和资源。如你所知，用户只有在经过身份验证和授权后才能访问应用程序。在许多情况下，身份验证由底层 Windows 操作系统的安全系统完成，该系统检查人员或用户的身份和角色以允许或拒绝访问应用程序或资源。.NET Framework 和 CLR 通过提供基于角色的安全性来利用 Windows 操作系统的安全系统。

基于角色的安全性基于用户和角色的概念，该概念已在大多数现代操作系统中实现。根据用户的身份和用户拥有的角色，用户经过身份验证和授权。已授权用户不仅可以访问整个应用程序，还可以访问应用程序中使用的类和方法。基于角色的安全性在应用程序或资源需要根据用户拥有的角色验证操作时具有主要用途。许多时候，预期操作需要多个人员（多个角色）的授权。现在，让我们以一个组织的真实生活示例为例，其中有具有不同角色的人，例如总经理、团队领导、软件开发人员、软件测试人员和人力资源经理。具有特定角色的人拥有特定特权和权利，而其他角色的人可能拥有也可能不拥有这些特权和权利。例如，批准休假的权利属于总经理，而批准软件应用程序的权利属于团队领导。现实生活中角色的概念被 .NET Framework 的基于角色的安全性所继承。然而，与现实生活场景不同，基于角色的安全性中一个用户的角色或特权可能与其他用户的角色重叠。换句话说，单个用户可能具有多个角色。角色只是一个具有相同特权集的命名用户组。属于特定角色的任何用户都拥有该角色的所有特权。

借助基于角色的安全性，你可以轻松高效地使应用程序安全。基于角色的安全性使用主体、身份和一组角色来验证和授权用户使用应用程序。你将在下一节中了解主体、身份和角色。

### 主体对象

基于角色的安全性围绕主体展开。主体是对用户身份及其所属角色的封装。在 .NET Framework 4.0 中，用户的身份通过任何可用的关联类型表示；用户的角色由权限表示。应用程序在验证和授权用户时考虑主体的角色和身份。请注意，一个主体只能有一个身份，但可以有多个角色。

主体（或主体对象）表示你的应用程序运行的用户特定环境。根据用户的身份和角色，主体为你的应用程序提供更少或更多的安全性。在 .NET Framework 4.0 中，基于角色的安全性允许你使用三种类型的主体：

- Windows 主体 — 指 Windows 操作系统的用户和角色
- 通用主体 — 指除 Windows 主体之外的用户和角色
- 自定义主体 — 指你在应用程序中创建的用户和角色

> **NOTE**
>
> 使用 Windows 主体时，用户和角色必须与 Windows 操作系统上的用户帐户关联。因此，你可能需要在操作系统上创建新的用户帐户。

### Role-Based Security Checks

为了将身份验证和授权用于基于角色的安全性，你需要在应用程序中添加必要的代码；即，将基于角色的安全检查添加到授权用户中。你可以通过以下三种方式包含基于角色的安全检查：

- Accessing the Principal directly
- Using the imperative security check
- Using the declarative security check

你可以直接访问当前线程上的 principal 对象，并使用属性和方法来验证和授权用户。你也可以执行命令式或声明式安全检查。现在，让我们学习两种常用的安全检查。
