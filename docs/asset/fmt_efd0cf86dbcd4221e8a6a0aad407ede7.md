
然而，对于已完成程序部分，严重事项的 Bug 数量每个开发人员应该是个位数。在程序的后期，它应该少于四个。如果你有高 Bug 数量，说明开发人员手中 MFU（缺陷功能）与运行代码的比例过高。

拥有大量充满 MFU 的代码没有太大处。如果你的另一个选择是较小的运行代码量，那么你会好得多。如果 Bug 数量太高，请停止新开发，专注于消灭现有的 Bug。在 Bug 数量恢复到合理水平之前，不要允许新开发。

并且请记住，你无法大幅改变一个开发人员一天能修复的 Bug 数量。如果数量持续上升，即使在全力修复模式下，你也完蛋了。如果数量以相对恒定的速度下降，那么你不能仅仅因为发布日期临近就计划将该速度翻倍。

## 测试流程

你测试流程的成功取决于三点：

- 你的组织水平
- 测试人员的专业知识
- 管理层的支持

有了良好的测试流程，你可以交付出色的软件。如果没有它，你毫无希望；随着每一次带有 Bug 的更新，留用你程序的用户会越来越少，会有更多的人转向那些测试工作做得良好的竞争对手。

## 内部测试

程序由多个小组进行测试。开发人员自己会进行一些测试，通过运行程序查看其新功能是否导致了其他问题。测试团队同时使用自动化和手动测试。最后，用户在 Beta 测试中对程序进行测试。

本节讨论第二组；即内部测试人员执行的测试。虽然测试小组也负责管理 Beta 测试，但本节讨论的是测试小组执行的实际测试。

测试人员分为两组：

- 拥有源代码知识的人（白盒）。这些测试人员查看源代码，并根据代码编写测试程序，试图破坏程序。
- 仅作为高级用户拥有产品知识的人（黑盒）。这些测试人员对程序的内部逻辑一无所知。相反，他们根据程序高级用户会拥有的知识来设计测试。

## 白盒测试

内部测试通常是产品白盒测试的唯一来源。这种测试由程序员执行，他们阅读源代码并根据实际源代码设计一套测试。`TRAPS` 和 `IntTests` 确保了所有代码都已执行，而这些测试则试图确保所有代码路径组合都得到了测试。

白盒测试不能由编写代码的开发人员执行。任何开发人员，无论多优秀，都有盲点。毕竟，起初是他们把所有那些 MFU 放进去的。

虽然白盒测试应该涵盖常见的代码路径，但这是其最不重要的工作。毕竟，如果一个代码路径是常见的，黑盒测试一定会测试它。相反，测试人员应该寻找极少被执行的代码路径。

理想情况下，将为所有可能的代码路径编写测试。然而，由于时间和精手有限，这通常是不可能的。在这种情况下，测试人员必须决定测试哪些代码路径。你有两类基本的测试。

首先，你想要编写测试程序基本功能的测试。这种测试应该确定基础系统（包括所有关键路径）是否正常。这是必要的，以判断开发人员是否作了某些更改，导致无法测试任何内容，因为基础系统处于“托管”（另一个技术术语，意味着你无法对程序进行任何操作）状态。

其次，你想要编写测试你认为最容易崩溃的代码路径。这是测试小组破坏程序的最佳机会。此外，在寻找可破坏的代码路径的过程中，发现错误的测试人员可以引起开发人员注意。这种代码审查也是发现 Bug 的一种方法。

## 黑盒测试

黑盒测试是白盒测试的相反面。测试人员对构成程序的内部代码一无所知。黑盒测试人员保持“纯净”是至关重要的。所谓“纯净”，是指测试人员必须对程序的内部运作一无所知。

在大多数情况下，确保黑盒测试人员纯净的最佳方法是使用非编程人员进行此类测试。即使他们看到代码，他们也不懂。这也减少了从开发人员那里学习的机会。

黑盒测试由程序高级用户设计。与白盒测试人员一样，应该编写两类基本的测试。首先是常见功能的测试。这些设计用于验证程序运行正常。第二次，再次是不常见的代码路径。在黑盒测试中，没有办法知道哪些代码路径比其他路径不稳定。最重要的方法是对提示给出异常的响应。

例如，当提示输入文件名时，尝试 8 个字符的名称。尝试只读文件。尝试损坏的文件。尝试不存在的文件。换句话说，尝试正常文件以外的所有内容。

不常见代码路径的测试在黑盒测试中并不关键，因为 Beta 测试将完成这大部分工作。这种测试中更重要的是为 Beta 过程中发现的 Bug 添加测试。

如果你跟踪初始的黑盒测试，你会发现某些测试人员编写的测试全部成功了，而另一些人编写的测试几乎总是失败。使用最后一组的人继续编写测试，让其他组的人为 Beta 站点报告的 Bug 编写测试。

## 设计测试

测试的寿命通常比它们所测试的代码长。虽然程序在版本之间可能会被完全重写，但用户界面保持基本不变。由于许多测试是为了练习用户界面编写的，这些测试仍然有效，或者易于修改。

此外，当程序转换为另一种语言（人类语言，而非编程语言）时，大多数测试仍然有效，尽管可能需要更改实际的按键输入和结果中的测试以匹配新语言。程序和测试程序一样，编写时考虑了国际化支持。

测试被分为“测试套件”。测试套件无非一组运行的测试。一组套件可以是基本功能测试工作。另一组可以是所有的打印测试用例。

两个测试套件在使用的测试用例上可能会交叉。测试用例是实际测试。测试套件旨在执行一组测试以检查某些内容。如果可能，测试套件应该包含其他测试套件。如果可能，你应该每个基本组准备一个测试套件，以及一个包含所有套件的主套件。主套件将包含每一个测试。

### 零 Bug

测试用例（Test case）测试程序中的一个功能。测试用例是由一组测试场景组成的测试程序。通过运行一个测试用例，你应该通过为该功能编写的所有测试来充分执行该功能。如果打开文件的测试用例通过了，说明它已经通过了你为打开文件所编写的所有测试。测试用例应该尽可能全面——它完整且完全地测试一个功能。

测试场景（Test scenario）是测试用例的一部分。每个场景测试执行函数的一种特定方式。例如，对于打开文件操作，其中一个场景会传入一个不存在的文件；另一个场景会传入一个损坏的文件，以此此类推。测试场景应该尽可能简单——它测试一个特定的代码路径。

测试应该生成其所执行测试的日志，并且如果测试失败，还要生成失败的结果。这些日志应该尽可能清晰简单。最好的日志是在没有错误的情况下，仅显示“测试成功完成”。

测试小组应该设计测试，以将软件推向极限。随机使用软件并不是测试小组的工作。他们应该在充分了解产品的情况下，定义一组能够推软件极限的测试。对于每项测试，他们应该有一组预定义的输入，这些输入对应一个预期的结果。

完成后，自动化测试就是一个运行顺畅的产品。它们能够很好地完成工作并清晰地返回结果。它们易于使用，且只需要极少的用户交互。专业的测试小组提供专业的系列测试套件。

## 运行测试

第一项测试是由测试人员设计并由开发者自己运行的测试。在软件通过这项测试之前，它不会交给测试人员。这项测试的目的不是让开发者去承担测试人员的工作，而是确保在修复 Bug 后程序运行正常。需要有足够的功能运行得足够好，以便测试人员能够实际开展一些工作。

这项测试包含了白盒和黑盒开发的用于测试主代码路径的测试。随着程序越来越多的运行正常，这个初始测试可能会扩大。然而，在任何时候它都不应该包含程序尚未具备的功能。测试的目的不是判断某功能是否是第一次运行，而是为了确保之前检查过的基本功能没有被破坏。

这项测试必须完全自动化。简单来说，开发者不太可能每周运行一次手动测试。然而，他/她可能会运行一个能够报告程序运行是否符合预期的程序。

处理这项测试的最佳方法是每周构建一次产品。一旦产品构建（包括所有人的更改），就会对程序运行自动化测试。如果程序通过，则将其交给测试小组。如果没有通过，则由破坏测试的开发者对程序进行修复。

构建程序和运行基础测试的过程由开发者、专门负责此功能的人员（构建者）或测试人员完成。程序可以被构建并交付给测试人员运行基础测试。然而，如果基础测试失败，开发者的唯一工作就是修复它。在此之前，开发者不进行任何其他开发。

一旦构建通过了基础测试，它就会交给测试小组。测试人员在构建版本上运行他们的自动化和手动测试。第一批测试应该是测试已报告的 Bug 是否已真正修复。如果没有，则将 Bug 退回给相应的开发者。

接下来，如果添加了新功能，应该运行为这些新功能开发的测试。由于测试程序是与开发同步编写的，因此测试新功能的程序应该在新功能完成时（或之前）准备就绪。

这为开发者提供了关于新功能实现良好的即时反馈。他们不需要等待几周甚至几个月（那时忘记了所有实现细节），而是在几天内获得反馈。

最后，应该运行剩余的测试以确保程序中没有引入新的 Bug。这是自动化测试真正发挥作用的地方。每周当一个新的构建版本交付给测试人员时，所有的旧测试都会重新运行——且成本极低。

## 测试平台

测试人员应该确保在实际终端用户条件下进行测试。如果一个产品的大多数用户使用带有 640K RAM 的 80286 机器，那么仅用带有 8M 内存的 50 MHz 80486 系统进行测试会导致很多问题溜。

在最小配置的系统上运行全套测试是很。测试必须在程序可能运行的每一个系统上通过，不仅是硬件，还包括其运行的软件，包括网络、TSR 等。

如果你使用特殊的监视器，请用每种监视器测试程序。寻找引起问题的组合。并寻找可能与你的程序冲突的其他软件包。冲突可能来自 TSR 和设备驱动程序以外的来源。在 Windows 下，你的 DOS 应用程序可能与同时在另一个 DOS 窗口中运行的应用程序不兼容。

确保在各种操作系统环境中进行测试。在 DOS 的情况下，你应该在低内存和高内存 DOS 下进行测试。测试你的程序在低内存和高内存加载（UMB）。你还应该在 Windows DOS 环境下测试程序——这会捕捉到所有非法内存访问。

如果你的产品是网络感知的并在多个网络上运行，在多个网络上对其测试是至关重要的。在一个网络上测试网络程序是确保它在其他任何网络上崩溃的好方法。使用至少三个截然不同的网络。如果你根据网络调用不同的网络 API，请对每个 API 测试至少两个不同的网络。

如果你正在编写 Windows 应用程序，确保它在 286 和 386 模式下都能工作。在每情况下，Windows 都显著不同。而且如果你的程序可以在实模式下运行，请在实模式下进行测试。如果在实模式下测试并不重要，那么允许它在实模式下运行是对客户不负责的。

随着对象链接和嵌入（OLE）在 Windows 应用程序中变得流行，与其他程序的兼容性将变得越来越重要。你会开始看到某些 Bug，只有当你的程序与应用程序 B 有 OLE 连接，且应用程序 B 与应用程序 C 建立动态数据交换（DDE）连接时，程序才会崩溃。

## 无 Bug

尽管如今每个人都有测试版（beta test），但大多数测试的效果并不理想。那么，你希望 Beta 测试实现什么呢？有四个关键点：

- 在多样化的硬件平台上测试你的程序。在世界上 8000 万台 PC 中，有 79,999,998 台每台都与所有其他电脑略有不同。（爱荷华州有两台是完全相同的。）Beta 测试让你能够在内部测试无法触及的更广泛的硬件选择上测试你的程序。
- 这种多样化的测试至关重要。无论公司如何努力在内部测试中使用多样化的硬件，实际上这组硬件是极其相似的。通过使用美国及全球范围内的现有平台，你有机会确保你的程序可以在任何硬件组合上运行。
- 第二，用各种其他程序测试你的程序。再次，除了爱荷华州的那两台 PC 外，世界上所有的计算机运行的一组 TSR（终端驻留程序）、设备驱动程序等，与世界上所有其他计算机运行的程序略有不同。将这些软件产品混合在其中（有些程序非常老旧，自从硬盘、网络或分级文件系统发明以来就没有更新过。不用说，其中一些程序在处理 640k RAM 概念时会有困难，如果使用 USB 它们会“发疯”）。这种软件组合可能导致某些系统上原本完全安全运行发生故障。你实际上可能需要针对其他程序中的 Bug 编写规避性代码（program around）来解决其中一些问题。只有 Beta 测试才能让你的程序针对真正多样化的组合进行测试。
- Beta 测试允许开发者获取对程序的反馈。如果一个功能很难用，Beta 测试员会让你知道。如果缺少了非常重要的功能，他们会告诉你。如果某个功能造成了干扰且不需要，他们也会告诉你。

这让你在最终发布产品之前（那时就太晚无法了）获得反馈。在一个原本非常出色的产品中，缺少一个功能可能会大幅减少销售额。一个糟糕的功能可能会毁掉一个产品的实用性。

开发者感兴趣的是创建产品，测试人员感兴趣的是发现 Bug，但用户感兴趣的是使用它。Beta 测试员试图使用软件来解决问题。一个编写良好、无 Bug 的程序并不意味着就好用。易用性问题与导致程序难以使用的 Bug 一样严重。

- 一小部分 Beta 测试员编写了与你的程序交互的程序。这些用户需要一个预览版本，以便在你发布你的程序时，他们可以向他们的程序发布更新。

这不仅适用于 Windows 和 OS/2 等操作系统。如果有人依赖于你的文件结构，它也适用于文字处理器。它适用于你可以与之通信的 API 的程序。它适用于支持 DDE 和 OLE 的 Windows 应用程序。

这组人的特殊之处有两个原因。第一，这个小组是整个 Beta 测试的子集。第二，根据你的程序变化而纳入必要更改的难度，这些人可能需要在常规 Beta 测试之前获得一个副本。

## 何时进行 Beta

如果你看进行 Beta 测试的前两个原因，你可能在担心由于非常细微的影响导致的 Bug。对这些影响进行测试应该等到开发过程接近尾声时。如果程序发生了重大变化，这些细微的影响就会产生直接作用。你并不关心程序的早期版本是否能与某个 TSR 工作——只关心最终版本是否可以。

如果你看进行 Beta 测试的第三个原因，你关心的是程序的整体表现。通常情况下，Beta 测试的反馈不会发现抛弃大部分现有工作的原因。相反，它会发现细微的不一致之处。或者会发现某些用户以不同的方式或在不同的情况下使用程序，导致需要针对这些情况进行更改。再次，需要一个相对完整的产品才能获得这种反馈。

Beta 测试应该在过程的较晚阶段进行。许多公司犯了一个错误，即过早开始 Beta 以加快产品的发布日期。Beta 测试本身没有发布日期（尽管可能会推迟发布日期）。

没有理由过早开始 Beta 测试。事实上，有许多理由**不要**过早开始 Beta。首先，尽管被标记为 beta，产品的质量也会影响对最终产品的看法。（Windows 7 因为其早期的 Beta 状态曾被标记为多 Bug 产品，尽管最终产品是稳如磐石的。）

此外，如果一个 Beta 产品持续时间足够长，Beta 产品将开始被视为已发布的产品，因为所有的意见领袖都已经在用它这么久了。如果产品仍然有 Bug 或功能缺陷，该产品在发布之前就可能失败。

相反，你不应该等得太久。在发布最终产品前一周启动 Beta 期间，比没用更糟糕。这不仅没有帮助，而且通过告诉管理层你进行过 Beta 测试（而且**不是** Beta 测试），他们可能会认为产品已经准备好发布了。

测试的目的是非常简单：开发者在程序中放置 MFU（用户误用功能）的技巧远高于测试人员发现它们的技巧（抱歉，测试人员）。MFU 存在于代码中——你知道它们存在——而你想找到它们。

那么你如何决定何时开始 Beta 呢？第一步是尽可能自托管。如果你正在写一个操作系统，开发者应该先运行新操作系统进行开发。如果你正在写一个编译器，编译器应该编译它自己。（对于非系统软件，自托管并不总是可能的——有多少开发者使用电子表格呢？）

此外，你应该有一个内部 Alpha 版本，让少数用户（最好是开发产品公司内部的用户）使用它。这样，一小组人（而非测试员）实际上在使用该产品。

理想情况下，这些用户会认为，除了几个 Bug 之外，目前的产品优于他们正在使用的版本。当你达到这一点并修复了发现的小 Bug 后，就是发布第一个 Beta 的完美时机。

如果你的 Alpha 测试员无法使用程序，那么扩大用户群没有任何益处。只要 Alpha 测试员仍在报告 Bug，你就不需要更多人报告相同的 Bug。

最好的指导是内部测试发现了极少数 Bug，且开发者将在未来一两个月内完成编码。换句话说，你需要在下个月内获得一些报告，否则有些人将无事可做。

## 何时发布

当你发送一个 Beta 并且在此之后不需要对核心代码进行任何更改时，你就准备好发布你的最终 Beta 了。

一个编写无 Bug 代码的开发小组通常会有一个到两个 Beta 版本（因为软件通常会与操作系统交互，增加了问题的复杂性）。然而，拥有额外的 Beta 比发布一个会被退货的 Bug 产品要好。

除了最后一个外，所有的 Beta 期间可以持续任何时间，尽管平均是一到两个月。如果你仍然收到大量的新 Bug 报告，那么可能还没到发布新的。如果你有了全新的版本或修复了许多关键 Bug，可能该发布另一个 Beta 了。

最后的 Beta 期间至少应持续一个月，除非收到 Bug ，否则真的应该持续两个月。等待得越久，程序在现场经历的异常组合就越多。

如果你做了你认为是安全的但确实接触了核心代码的最终更改，你可能希望发布限量 Beta。将副本发送给那些发现问题最多的站点。

你可能还会考虑通过 CompuServe 或其他公告服务进行 Beta 测试。如果 Beta 测试员下载了 Beta，那么在 Beta 测试过程中拥有一些中间 Beta 对你来说没有任何成本。

## 选择 Beta 站点

在我们 Beta 站点的标准中，另一个重要特征是多样性。两个具有相同电脑、软件和习惯的用户并不比一个更有用。两个具有完全不同系统和软件的用户则有。

随着 Beta 测试的进行，请跟踪你的测试站点。如果一个测试站点从不报告任何错误，那么它们对你毫无用处，在下次进行 Beta 测试时你不必费力将它们包含进来。对于那些为了自己的产品而需要提前访问你产品的测试站点来说有一个例外。即使他们不报告错误，他们也需要这个测试版。

在 Beta 测试结束后仍报告了错误的测试站点应该得到奖励（至少给一个奖牌）。如果你在最后一次 Beta 测试之后，做了“某种程度上”影响了核心代码的更改，你可能会选择只针对这些站点发布一次测试后的更新。

现在似乎许多公司都在寻求比任何其他计划都更大的 Beta 程序。当站点数量达到一定程度后，增加额外的站点并无益。定一个数字，并极力不要超过这个数字。对于一个销量数百万份的通用产品，我认为拥有超过 5000 个测试站点没有任何优势。

对于一个总共有 1000 个客户的垂直市场应用，50 个测试站点已经绰绰有余（ 20 个可能就够了）。选择正确的测试站点。挑选 20 个实际上并不使用测试版的人是毫无用处的。

跟踪你现有产品中报告错误的人。要求那些前 1% 或 2% 的人（必要时请恳求）成为 Beta 测试员。那些打电话为未来的产品提供良好建议的人也应该是 Beta 测试站点。

你寻找的是质量，而不是数量。
