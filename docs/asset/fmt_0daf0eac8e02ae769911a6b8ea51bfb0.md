`AddItemHelper`定义了一系列代码合约。前条件（preconditions）表示新项 `newItem`不能为空，且添加到购物车的项已不在购物车中。后条件（postconditions）表示新项必须在购物车中，且总成本必须至少不等于该项添加到购物车之前的成本。后条件还表示，如果`AddItemHelper`因为某种原因抛出了`IOException`，那么`totalCost`与方法开始执行时保持不变。`ObjectInvariant`方法是一个私有方法，调用它时，它会确保对象的`m_totalCost`字段永远包含负值。

> **重要：** 在前条件、后条件或不变性测试中引用的所有成员必须是无副作用的（side-effect free）。这是强制要求的，因为测试条件不应该改变对象本身的状态。此外，在前条件测试中引用的所有成员，其访问权限至少要优于定义该前条件的方法。要求此前条件是因为方法的调用者应该能够在调用方法之前验证他们已经满足了所有前条件。另一方面，后条件或不变性测试中引用的成员只要代码可以编译，就可以具有任何访问权限。此处访问权限之所以重要，是因为后条件和不变性测试不会影响调用者正确调用方法的能力。

> **重要：** 在继承方面，派生类型不能重写并更改基类型中虚成员的前条件。同样，实现接口成员的类型不能更改该接口成员定义的前条件。如果某个成员没有显式合约，则该成员有一个隐式合约，其逻辑看起来如下：

```cssharp
Contract.Requires(true);
```

由于合约不能通过新版本变得更严格（这会破坏兼容性），因此在引入新的虚成员、抽象或接口成员时，你应该仔细考虑前条件。对于后条件和对象不变性，可以尽可能添加和删除合约，前提是虚/抽象/接口成员所表达的条件与重写成员所表达的条件在逻辑上是“与”（AND）的关系。

现在你知道如何声明合约了。现在让我们谈谈它们在运行时是如何运作的。你可以在方法的顶部声明所有的前条件和后条件合约。例如，前条件合约会在方法被调用时验证你的测试。然而，我们不希望后条件合约在方法返回之前验证你的测试。为了实现所需的行为，C#编译器生成的程序集必须由代码重写工具（`CCRewrite.exe`，位于`C:\Program Files (x86)\Microsoft\Contracts\Bin`）处理，该工具会生成程序集的修改版本。当你为项目勾选“执行运行时合约检查”（Perform Runtime Contract Checking）复选框后，Visual Studio会在每次构建项目时为你调用此工具。该工具分析你所有方法中的IL并重写IL，以便任何后条件合约都能在方法结束时执行。如果你的方法内部有多个返回点，`CCRewrite.exe`工具会修改你方法的IL，使得所有返回点在方法返回之前都会执行后条件代码。

`CCRewrite.exe`工具会查找任何标记为`[ContractInvariant]`属性的方法。该方法可以有任何名称，按照惯例，人们使用`ObjectInvariant`名称并将方法标记为私有（如我上面做的那样）。该方法必须不接受参数且返回类型为`void`。当`CCRewrite.exe`工具看到带有此属性的方法时，它会在每个公共实例方法的末尾插入代码以调用`ObjectInvariant`方法。这样，在每个方法返回时都会检查对象的状态，以确保没有方法违反其合约。注意，`CCRewrite.exe`工具不会修改`Final`方法或`IDisposable`方法来调用`ObjectInvariant`方法，因为如果对象被认为已销毁或释放，其状态被改变是可以接受的。另外注意，单个类型可以定义多个带有`[ContractInvariant]`属性的方法；这在处理部分类型（partial types）时非常有用。`CCRewrite.exe`工具会修改IL，在每个公共方法的末尾（按未顺序）调用这些方法。

`Assert`和`Assume`方法与其他方法不同。首先，你不应该让它们成为方法签名的一部分，也不需要将它们放在方法的开头。在运行时，这两个方法的执行效果是相同的。它们验证传递给它们的条件是否为真，如果不是，则抛出异常。然而，还有另一个工具——代码检查器（`CCCCheck.exe`），它分析C#编译器生成的IL，尝试静态地验证方法中没有代码违反合约。该工具会尝试防止任何传递给`Assert`的条件为假，但对于传递给`Assume`的条件，它只会假设其为真，并将该条件添加到其“已知真”的事实列表中。通常情况下，你会使用`Assert`，如果`CCCCheck.exe`工具无法静态验证该表达式为真，则将`Assert`更改为`Assume`。

让我们来看一个例子。假设我有以下类型定义：

```cs
internal sealed class SomeType {
    private static string s_name = "Jeffrey";
    public static void ShowFirstLetter() {
        Console.WriteLine(s_name[0]); // 警告：未证明：index < this.Length
    }
}
```

当我在开启“执行静态合约检查”（Perform Static Contract Checking）功能编译此代码时，`CCCCheck.exe`工具会产生注释所示的警告。该警告提醒，查询`s_name`的第一个字母可能会失败并抛出异常，因为无法证明`s_name`始终存在。

因此，我们想在`ShowFirstLetter`方法中添加一个断言：

```cs
public static void ShowFirstLetter() {
    Contract.Assert(s_name.Length >= 1);
    Console.WriteLine(s_name[0]);
}
```

不幸的是，当`CCCCheck`工具分析此代码时，它仍然无法验证`s_name`始终包含一个字符，因此工具产生了类似的警告。由于工具的局限性，工具无法验证断言；未来的版本将能够进行更完整的分析。

为了克服工具的缺陷或声明某些工具永远无法证明的事实，我们可以将`Assert`更改为`Assume`。如果我们确定其他代码会修改`s_name`，那么可以将`ShowFirstLetter`改为：

```cs
public static void ShowFirstLetter() {
    Contract.Assume(s_name.Length >= 1); // 没有任何警告！
    Console.WriteLine(s_name[0]);
}
```

有了这段代码，`CCCCheck`工具直接接受我们的说法，并得出`s_name`始终包含一个字符的结论。这个版本的`ShowFirstLetter`方法通过代码检查。

现在，让我们谈谈代码引用生成工具（`CCRefGen.exe`）。运行`CCWrite`工具启用合约检查可以帮助你更快发现错误，但检查期间产生的所有代码会增大你的程序集并影响其运行时性能。为了改善这种情况，请使用`CCRefGen`工具创建一个独立的引用程序集。当你设置了“合约引用程序集”框时，Visual Studio会自动调用此工具。合约程序集通常命名为`AssemblyName.Contracts.dll`（例如`MSCorLib.Contracts.dll`），这些程序集仅包含元数据和描述合约的IL——不包含其他内容。你可以识别合约程序集，因为它在程序集的定义元数据上应用了`System.Diagnostics.Contracts.ContractReferenceAssemblyAttribute`。当`CCWrite`工具和`CCCCheck`工具执行插桩和分析时，可以使用合约引用作为输入。

## 理解在垃圾回收平台中工作的基础

每个程序都会使用各种资源，如文件、内存缓冲区、屏幕空间、网络连接、数据库资源等。事实上，在面向对象的环境中，每个类型都标识了程序可供使用的某些资源。要使用其中任何一种资源，都需要分配内存来表示该类型。访问资源需要以下步骤：

1. 通过调用中间语言（IL）的`newobj`指令为表示资源的类型分配内存，该指令是在您在C#中使用`new`操作符时发射的。

2. 初始化内存以设置资源的初始状态并使资源可用。该类型的实例构造函数负责设置此初始状态。

3. 通过访问类型的成员来使用资源（根据需要重复此操作）。

4. 拆毁资源的状态进行清理。我将在本章稍后的“Dispose 模式：强制对象清理”节中讨论这个主题。

5. 释放内存。垃圾回收器完全负责这一步。

这个看似简单的范式是编程错误的主要来源之一。程序员有多少次在内存不再需要时忘记释放它？程序员又有多少次在内存已经被释放后尝试使用它？

在原生编程世界中，这些问题通常无法预测其后果或发生时机。对于其他错误，当你看到应用程序运行异常时，只需修复问题即可。但这两种错误会导致资源泄漏（内存消耗）和对象损坏（不稳定性），使应用程序变得不可预测。事实上，有许多工具（如微软的Windows任务管理器、Process Explorer和性能监视器，以及Rational的Purify）是专门为帮助开发者定位此类错误而设计的。

适当的资源管理非常困难且枯燥。它让开发者无法专注于他们正试图解决的实际问题。如果有某种机制能为开发者简化这项枯燥的内存管理任务，那就太棒了。幸运的是，确实有：垃圾回收。

垃圾回收完全让开发者无需再跟踪内存使用情况以及何时释放内存。然而，垃圾回收器并不知道由类型所表示的资源的任何信息，这意味着垃圾回收器不知道如何执行上述列表中的第4步：拆毁资源的状态进行清理。为了让资源正确清理，开发者必须编写知道如何正确清理资源的代码。开发者在`Finalize`中编写这些代码，在本章稍后讨论的，开发者可以使用`Dispose`方法。

到目前为止，由于托管堆由于其实现简单且速度快而优于C运行时堆。但在深入研究之前，你应该了解一个微小的细节。托管堆之所以拥有这些优势，是因为它做了一个非常大的假设：地址空间和存储是有限的。显然，这个假设是荒谬的，因此托管堆必须采用某种机制来允许这种假设的存在。这个机制就是垃圾回收。它的工作原理如下：

当应用程序调用`new`算符创建对象时，该区域可能没有足够的地址空间来分配该对象。堆通过将对象所需的字节数加到地址`NextObjPtr`上来检测这种空间缺失。如果结果值超过了地址空间区域的末尾，则堆已满，必须执行垃圾回收。

> **重要** 我所说的是一种简化。实际上，当第0代填满时就会发生垃圾回收。某些垃圾回收器使用“代”（generations）机制，其目的是提高性能。其核心思想是：新创建的对象属于“年轻代”，而在应用程序生命周期内创建的对象属于“较老代”。第0代中的对象是最近分配且从未被垃圾回收器检查过的对象。存活的对象会被晋升到另一个代（例如第1代）。将对象分为不同的代允许垃圾回收器只收集特定的代，而不是收集托管堆中的所有对象。我将在本章稍后的部分详细解释“代”的概念。在此之前，对你来说最好的想法是：当堆满时就会发生垃圾回收。

## 垃圾回收算法

垃圾回收器检查堆中是否有任何对象不再被应用程序使用。如果存在此类对象，这些对象使用的内存就可以被回收。（如果垃圾回收后堆中没有更多可用内存，则将抛出`OutOfMemoryException`。）垃圾回收器如何知道应用程序是否在使用某个对象？正如你可能想象的，这并不是一个容易回答的问题。

每个应用程序都有一组根（roots）。单个根是一个存储位置，包含一个指向引用类型对象的内存指针。该指针指向托管堆中的一个对象，或者被设置为`null`。例如，静态字段（定义在类型内部）被视为一个根。此外，任何方法参数或局部变量都是根。只有引用类型的变量才被视为根；值类型变量永远被视为根。

现在，让我们来看一个具体的示例，从以下类定义开始：

```cs
internal sealed class SomeType {
    private TextWriter m_textWriter;

    public SomeType(TextWriter tw) {
        m_textWriter = tw;
    }

    public void WriteBytes(byte[] bytes) {
        for (Int32 x = 0; x < bytes.Length; x++) {
            m_textWriter.Write(bytes[x]);
        }
    }
}
```
