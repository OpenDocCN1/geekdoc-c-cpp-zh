# 还有一点

在生成的代码中我们可以看到：在初始化 `i` 之后，循环体将不会执行，因为 `i` 的条件会先被检查，只有在检查之后才能执行循环体。这是正确的。

因为，如果循环条件在开始时不满足，则必须不执行循环体。这在以下情况下是可能的：

```c
for (i=0; total_entries_to_process; i++)
  loop_body;
```

如果 `total_entries_to_process` 为 0，则循环体将完全不会执行。

这就是为什么在执行之前会检查条件。
然而，一个优化过的编译器可能会交换条件检查和循环体，前提是它确定这里描述的情况是不可能发生的（例如我们这个非常简单的例子的情况，以及使用如 Keil、Xcode (LLVM)、优化模式下的 MSVC 等编译器时）。

通常，条件会在循环体之前检查，但编译器可能会对其进行重排，使得条件在循环体之后才检查。

这种情况发生在编译器确定条件在第一次迭代时始终为真，因此循环体至少执行一次：

### 1.23.1 strlen()

让我们再多谈谈循环。`strlen()` 函数通常使用 `while()` 语句来实现。以下是 MSVC 标准库中的实现方式。

```c
int my_strlen(const char *str)
{
    const char *eos = str;
    while(*eos++);
    return(eos - 1);
}

int main() {
    // test
    return my_strlen("hello!");
}
```

### 未优化的 MSVC

让我们来编译：

```assembly
eos = -4          ; size = 4
str$ = 8          ; size = 4

strlen PROC
    push    ebp
    mov     ebp, esp
    push    ecx
    mov     DWORD PTR str$[ebp], eax  ; pointer to string from "str"
    mov     DWORD PTR eos$[ebp], eax  ; place to local variable "eos"

$LN2@strlen:
    mov     ecx, DWORD PTR eos$[ebp]  ; ECX=eos
    ; take 8-byte from address ECX and place it
    ; as 32-bit value to EDI with address sign
    movsx   edx, BYTE PTR [ecx]       ; EAX=eos
    mov     eax, DWORD PTR eos$[ebp]  ; increment EAX
    add     eax, 1
    mov     DWORD PTR eos$[ebp], eax  ; place EAX back to "eos"
    test    edx, edx                  ; EDX is zero?
    je      SHORT $LN2@strlen         ; yes, then finish loop
    jmp     SHORT $LN2@strlen         ; continue loop

$LN1_strlen:
; 在这里我们计算两个指针之间的差
    mov     eax, DWORD PTR eos$[ebp]
    sub     eax, DWORD PTR str$[ebp]
    sub     eax, 1                    ; subtract 1 and return result
    mov     esp, ebp
    pop     ebp
    ret     0
strlen ENDP
```

我们得到了两条指令：`MOVSX` 和 `TEST`。
第一条 `MOVSX`——从内存地址获取一个字节并将值存储在 32 位寄存器中。`MOVSX` 代表 “MOV with Sign-Extend”（带符号扩展的移动）。如果符号为负，`MOVSX` 将从第 8 位到第 31 位的位设置为 1；如果为正则设置为 0。

这是原因所在。
在默认情况下，MSVC 和 GCC 中的 `char` 类型是有符号的。我们有两个值，一个是 `char`，另一个是 `int`（`int` 也是有符号的），如果第一个值包含 -2（编码为 0xFE）并将其复制到 `int` 容器，它会变成 0x0000FFFE，从这一点开始，有符号 `int` 是 254，而不是 -2。在有符号 `int` 中，-2 被编码为 0xFFFFFFFE。如果我们从 `char` 变量将 0xFE 传输到 `int`，必须识别它的符号并进行扩展。这就是 `MOVSX` 起的作用。

很难说编译器是否需要将 `char` 变量存储在 `EDX` 中，它也可以取 8 位寄存器部分（例如示例 `DL`）。显然，编译器的寄存器分配器是这样工作的。

然后我们看到 `TEST EDX, EDX`。你可以在位域章节（第 382 页的 1.28）了解更多关于 `TEST` 指令的信息。在这里，这条指令仅检查 `EDX` 中的值是否等于 0。

### 未优化的 GCC

让我们尝试 GCC 4.4.1：

```assembly
public strlen
proc near
eos               = dword ptr -4
arg_0             = dword ptr 8

push   ebp
mov     ebp, esp
sub     esp, 10h
mov     eax, [ebp+arg_0]
mov     [ebp+eos], eax

mov     eax, [ebp+eos]
movzx   eax, byte ptr [eax]
test    al, al
setnz   al
add     [ebp+eos], 1
test    al, al
jnz     short loc_80483F0

mov     edx, [ebp+eos]
mov     eax, [ebp+arg_0]
mov     ecx, edx
sub     ecx, eax
mov     eax, ecx
sub     eax, 1
```

结果与 MSVC 几乎相同，但我们在这里看到了 `MOVZX` 而不是 `MOVSX`。`MOVZX` 代表 “MOV with Zero-Extend”（带零扩展的移动）。`MOVZX` 从地址拷贝一个字节并将 32 位寄存器的其余位填充为零。

我们看到 `EAX` 现在包含了字符串后面的零字节加 1（因为 `INC EAX` 无论我们是否退出循环都会执行）。与此同时，`EDX` 没有变化，所以它仍然指向字符串的开头。

### 优化 GCC

让我们检查开启优化的 GCC 4.4.1（关键参数为 `-O3`）：

```assembly
public strlen
proc near
arg_0 = dword ptr 8

push    ebp
mov     ebp, esp
mov     ecx, [ebp+arg_0]
mov     eax, ecx

loc_0848418:
    mov     dl, byte ptr [eax]
    test    dl, dl
    jnz     short loc_0848418

    not     ecx
    add     eax, ecx
    pop     ebp
    retn
strlen  endp
```

GCC 与 MSVC 几乎相同，除了存在 `MOVZX`（此处优化为 `mov dl, byte ptr [eax]`）。

也许对于 GCC 的代码生成器来说，记住整个 32 位的 `EDX` 寄存器被分配给字符变量更简单，它可以确保在任何时候最高位都没有异常。

之后我们看到了一条新指令——`NOT`。该指令反转操作数中的所有位。你可以说它是 `XOR ECX, 0xffffffff` 指令的同义词。`NOT` 和随后的 `ADD` 计算指针差并减去 1，只是方式不同。在开始时，`ECX` 存储了指向 `str` 的指针，对其进行取反，并减去 1。

换句话说，在函数循环体结束时，执行了这些操作：

```
ecx = str;
eax = eos;
ecx = (-ecx) - 1;
eax = eax + ecx;
return eax
```

... 而这实际上等同于：

```
ecx = str;
eax = eos;
eax = eax - ecx;
eax = eax - 1;
return eax
```

为什么 GCC 决定这样更好？很难猜。但也许两种变体在效率上是等价的。
