
只有当你将引用 Objective-C 对象的结构体传递给栈时，使用结构体才被认为是安全的。只要这些指针在调用者中保持有效，就可以毫无问题地被带有 `__unsafe_unretained` 修饰符。

你会发现，在使用迁移工具后，不再有任何 `assign` 属性。这些属性将被重写为 `unsafe_unretained` 或 `weak`，取决于你选择的部署目标是否支持弱引用。如果它们被用于打破简单的循环，且你发现弱引用存在性能问题，你可能希望显式地将某些改为 `unsafe_unretained`。

迁移工具会尝试在需要的地方插入 `__bridge` 强制转换，但这些内容值得检查。这些转换用于将对象从 ARC 管理的代码移出。在非 ARC 的 Objective-C 中，你可以自由执行像 `(void*)someObject` 这样的操作，因为对象指针只是可以发送消息的 C 指针。在 ARC 模式下，这种转换不知道 `void*` 的所有权语义应该是什么，因此会被拒绝。

迁移工具会将此重写为 `(__bridge void*)someObject`，但这可能不是你想要的。我们将在“与 C 互操作”部分详细地查看这些强制转换。

## 自动释放池 Autorelease Pools

```objc
id returnObject(void) {
    return [[NSObject new] autorelease];
}

int main(void) {
    @autorelease {
        id object = returnObject();
        [object retain];
        // 对象在此处失效。
        [object release];
        return 0;
    }
}
```

源自：`autorelease.m`

除了循环，引用计数最大的问题是，在某些短时间内，没有对象真正拥有特定的引用。在 C 语言中，判断是由调用者还是被调用者负责分配内存是一个问题。

在像 `sprintf()` 这样的函数中，调用者分配空间。遗憾的是，调用者实际上不知道需要多少空间，因此添加了 `snprintf()` 变体让被调用者知道可用空间。这仍然可能导致问题，因此增加了 `as()` 版本让被调用者分配空间。

如果是由被调用者分配空间，谁负责释放它？推测是调用者，但因为调用者并没有创建它，任何检查 `malloc()` 和 `free()` 调用是否平衡的工具都无法发现内存泄漏。

在 Objective-C 中，这个问题更为常见。许多方法可能会返回临时对象。如果你返回一个临时对象，它需要被释放；但如果你返回的是实例变量的指针，它就不需要。你可以 `retain` 这样的指针，但然后你需要记得 `release` 从方法返回的每一个对象。这很快就会变得令人疲惫。

该问题的解决办法是自动释放池。当你向对象发送 `autorelease` 消息时，它会被添加到当前活跃的 `AutoreleasePool` 实例。当这个实例销毁时，添加到它的每个对象都会收到 `-release` 消息。

`-autorelease` 消息是一个延迟的 `-release` 消息。当你不再需要某个对象的引用但其他地方可能需要时，向它发送该消息。

如果你在使用 `NSRLoop`，自动释放会在每次运行循环迭代开始时创建并在结束时销毁。这意味着在当前迭代结束之前，没有任何临时对象会被销毁。如果你正在执行创建大量临时对象的操作，你可能想要创建一个新的自动释放池，如下：

### 第 3 章：内存管理

```objc
id pool = [NSAutleasePool new];
[object doSomethingThatCreatesObjects];
[pool drain];
```

注意，在销毁自动释放池时，你发送的是 `-drain` 消息而不是 `release` 消息。这是因为当处于垃圾回收模式时，Objective-C 运行时会忽略 `-release` 消息。在这种模式下，`-drain` 消息为垃圾器提供了提示，但不会销毁池。

在 OS X 10.7 中，Apple 将自动释放池成为语言的一部分。显式引用 `NSAutPool` 类的程序在 ARC 模式下被视为无效，编译器将拒绝它们。替代方案是 `@autoreleasepool` 结构。它定义了一个自动释放池有效的区域。在非 ARC 模式下，它将插入与上述代码段完全的代码。在 ARC 模式下，它插入对 `objc_autoreleasePoolPush()` 和 `objc_autoreleasePoolPop()` 函数的调用，这些函数会执行相应的操作。

### 使用自动释放的构造函数

```objc
+ (NSString*)object
{
    return [[self alloc] autorelease];
}
```

源自：`namedConstructor.m`

上一节中提到，通过 `alloc` 创建的对象引用计数为一。事实上，所有通过 `alloc` 创建的对象都是自动释放，但通过命名构造函数创建的对象（如 `stringWithFormat:` 或 `array`）也是自动释放的。如果你创建了这些机制的实例，你必须 `retain` 它。这是一个需要遵守的约定，如果不这样做，它将在自动释放池销毁时被释放。注意，由于这是一个类方法，`self` 将是该类。通过此方法可以自动处理子类。

在 ARC 中，这些约定在方法族中形式化。以 `alloc`、`new`、`copy` 或 `mutableCopy` 开头的方法返回所有权引用，如果不存储则必须释放。其他方法返回非所有权引用，其已自动释放或存储在其他地方，并保证不会被释放。

### 访问器中的自动释放对象

```objc
(NSString*)stringValue
{
    return [[string retain] autorelease];
}
```

源自：`ivar.m`

引用计数（在 Foundation 中实现）的另一个常见问题是，你通常不会保留在栈上引用的对象。假设你有如下所示的代码：

`NSString *oldString = [anObject stringValue]; [anObject setValue:newString];`

如果 `-setValue:` 方法如我之前建议的那样实现，这段代码将会崩溃，因为 `oldString` 引用的对象会在你设置新字符串时被删除。这是一个问题。有两种可能的解决方案，都涉及自动释放池。一种是在设置新值时 `autorelease` 旧值；另一种是本节开始的 `-stringValue` 方法定义。这确保了字符串不会因为对象的任何操作而意外被销毁。另一种常见的惯例是用 `-copy` 消息代替 `-retain`。如果实例变量可能是可变的，这很有用。如果它是不可变的，`-copy` 将等同于 `-retain`。如果是可变的，调用者将获得一个不会随着发送给该对象的其他消息而改变的对象。

### 支持自动垃圾回收

```
$ gcc -c -framework Cocoa -fobjc-gc-only collected.m
$ gcc -c -framework Cocoa -fobjc-gc collected.m
```

从 OS X 10.5 开始，Apple 在 Objective-C 中引入了自动垃圾回收。这可以让程序员的生活更轻松，但在大多数情况下，它伴随着性能代价。Apple 的垃圾器使用大量内存来跟踪活跃引用，因此在 iPhone 上不可用。它也不支持旧版本的 OS X，并且支持有限。

支持 GNUstep，因此如果你想编写可移植的代码，就应该避免使用垃圾回收。

如果你在垃圾回收模式下编译代码，所有的 `-retain`、 `-release` 和 `-autorelease` 消息都会被忽略。编译器会在每个赋值到堆内存的赋值操作中，自动插入对运行时函数的调用。

代码必须在垃圾回收支持下进行编译才能使用垃圾回收器。这会在任何对堆内存的赋值处插入一组函数调用，在 Mac 运行时，这些函数被声明在 `objc-auto.h` 中。

这些函数确保垃圾回收器能够感知到这些写入操作。之所以需要这些函数，是因为回收器是并发的。它会在后台线程中运行，并在无法找到对对象的引用时删除它们。必须通知回收器指针的更新，否则它可能会意外地删除你刚刚创建了引用的对象。

在针对垃圾回收进行编译时，你有两个选项。如果你使用 `-fobjc-gc-only` 标志编译，你的代码将仅支持垃圾回收。如果你使用 `-fobjc-gc-flag` 标志编译，代码将同时支持引用计数和自动垃圾回收。这在编译框架时非常有用。你仍然必须记得在正确的位置添加 `-retain` 和 `-release` 调用，但你框架的用户可以在开启或不开启回收的情况下使用它。

### 与 C 互操作

```
OBJ_EXPORT BOOL objc_atomicCompareAndSwapGlobal(id predicate, id replacement, volatile id *objectLocation)
OSX_AVAILABLE_STARTING(__MAC_10_6, __IPHONE_NA) OBJC_ARC_UNAVAILABLE;
OBJECT_EXPORT BOOL objc_atomicCompareAndSwapBarrier(id predicate, id replacement, volatile id *objectLocation)
OSX_AVAILABLE_STARTING(__MAC_10_6, __IPHONE_NA) OBJC_ARC_UNAVAILABLE;
// atomic update of an instance variable

OSX_AVAILABLE_STARTING(__MAC_10_6, __IPHONE_NA) OBJC_ARC_UNAVAILABLE;
OBJECT_EXPORT BOOL objc_atomicCompareAndSwapInstanceVariableBarrier(id predicate, id replacement, volatile id *objectLocation)
```

源自：`objc-auto.h`

在垃圾回收模式下，并不是所有内存都会扫描。任何通过 `malloc()` 分配的内容对垃圾回收器都是不可见的。如果你将一个对象指针作为 `void*` 参数传递给 C 函数，然后将其存储在 `malloc()` 分配的内存中，它将对回收器不可见，尽管仍有指向它的引用，它也可能被释放。

在 ARC 模式下，编译器将自动为你处理栈上或实例变量中的指针，但它不会跟踪结构体或显式声明为 `unsafe_unretained` 的任何内容的指针。

通常情况下，你会在对象存储到堆上之前向它发送 `-retain` 消息，这在垃圾回收模式下是无效，且在 ARC 模式下是被禁止的。相反，你必须使用 `CFRetain()` 函数。这会增加对象的引用计数，无论回收器是否在运行。回收器只有在对象的引用计数为零且在追踪的内存中找不到对它的任何引用时，才会释放对象。

当你完成一个不在回收器范围内的引用后，你需要调用 `CFRelease()`。

ARC 为此类操作提供了更丰富的内存模型。不再允许从对象到非对象指针类型的显式类型转换。它们必须被*桥接转换*取代。考虑非 ARC 模式下的这段代码：

```
void *aPointer = (void*)someObject;
```

在 ARC 模式下，这将从一个被跟踪的指针创建一个未被跟踪的指针，这并不是你在不经思考的情况下想要做的。

你有三个基本选项。第一种常用于栈上变量，或指向保证在其他地方被引用的变量：

```
void *aPointer = (__bridge void*)someObject;
```

这执行转换但不转移所有权。如果 `someObject` 的所有其他引用都丢失，那么 `aPointer` 将变成一个悬空指针。如果 `void*` 指针将进入某处的堆并应该保留对对象的所有权引用，那么你应该使用保留的桥接转换：

```
void *aPointer = (__bridge_retained void*)nsomeObject;
```

这将一个所有权引用从 ARC 的控制中移出。这大致等于在存储 `someObject` 之前向它发送了 `-retain` 消息。如果你在没有赋值的情况下写下 `(__bridge_retained void*)someObject`，那么这会告诉编译器保留该对象。这样做被认为是非常糟糕的风格。在转换回对象指针时，你应该使用相反的操作：

```
id anotherObjectPointer = (__bridge_transfer id)aPointer;
aPointer = NULL;
```

这会将一个所有权引用转移到 ARC 的控制中。ARC 现在负责释放该对象，所以记住将 C 指针置零非常重要。如果你不获取指针的所有权，则应该使用简单的 `__bridge` 转换。

### 理解对象的析毁

```
@interface Example : NSObject
{
    void *cPointer;
    id objectPointer;
}
@end
@implementation Example
-(void)finalize
{
    if (NULL != cPointer) { free(cPointer);
    [super finalize];
}
-(void)dealloc
{
    if (NULL != cPointer) { free(cPointer);
#if !has_feature(objc_arc)
    [objectPointer release];
#endif
    [super dealloc];
}
@end
```

源自：`dealloc.m`

根据模式的不同，有三种方法在对象析毁期间被调用。其中一个总是运行，但不能由你编写。`cxx_destruct` 方法由 Objective-C 运行时调用，并处理任何 C++ 对象的析毁。

另外两个是 `-finalize` 和 `-dealloc`。在垃圾回收模式下，你不需要对 Objective-C 对象执行任何操作，但你仍然需要清理任何不受回收器管理的资源。这包括关闭句柄、释放通过 `malloc()` 分配的内存等。如果你的类需要这种手动清理，你应该声明 `-finalize` 方法。

**注意：** 垃圾回收器通常在一个特殊的线程中调用 `-finalize` 方法。这意味着 `-finalize` 方法必须是线程安全的。如果它们引用全局资源，则必须确保这样做不会引入竞态条件。

如果你没有使用垃圾回收，则应该在 `dealloc` 方法中清理。方法的内容取决于是否使用 ARC。传统上，`dealloc` 方法充满了向类声明的每个实例变量发送 `-release` 消息。使用 ARC 后，这不再需要。ARC 会在 `cxx_destruct` 中释放对象的引用，因此你只需要在 `dealloc` 中清理非对象的实例变量。

在 GC 和手动引用计数模式下，你都应该向父类传递消息，根据情况调用 `[super dealloc]` 或 `[super finalize]`。在 ARC 模式下，不允许显式调用 `-dealloc`。相反，ARC 会在任何非根类的 `dealloc` 方法末尾插入一个 `[super dealloc]` 调用。

注意本节开头的示例过于复杂。在实际代码中，你可能不需要同时支持 ARC 和手动引用计数模式。它们可以在同一个程序中协作。支持非 ARC 模式的唯一原因是你想支持旧编译器。

### 使用弱引用

```
__weak id weak;
int main(void) {
    id obj = [Object new];
    weak = obj;
    obj = nil;
    objc_collect(OBJC_FULL_COLLECTION);
    fprintf(stderr, "Weak reference: %p\n", weak);
    return 0;
}
```

源自：`weak.m`

Apple 垃圾回收实现中非常好的特性之一是存在置零弱引用。在垃圾回收出现之前的 Objective-C 文档中，未被保留的指针通常被称为“弱引用”。这些引用允许在对象生命周期之外继续存在。遗憾的是，没有自动的方法来判断它们仍然有效。

人们发现弱引用在垃圾回收中非常有用，因此现在 ARC 也支持弱引用，但语义略有不同。为了向后兼容提供的 ARC 实现不支持弱引用，因此只有当你将范围限制在 OS X 10.7 或 iOS 5 及更高版本时，你才能在 Apple 平台上通过 ARC 使用弱引用。

**注意：** 在引用计数环境中，例如引用代理 `delegate` 的情况，弱引用通常用于消除循环引用。在追踪环境中不需要这一点，因此你可以对指向代理的指针以及任何可能出现循环引用的地方使用强引用。

如果你将一个对象指针声明为 `__weak`，你将获得一个置零弱引用。垃圾回收器在判断对象是否仍然存活时不会计入该引用，且在 ARC 模式下赋值时，它不会增加对象的引用计数。如果指向对象的所有引用都是弱引用，它就可以被销毁。之后，读取这些弱引用将返回 `nil`。

弱引用最常用于通知等场景。你会保留一个对象的弱引用，只要它在别处被引用，你就一直向它发送消息，然后以后你可以让它自动清理。

Cocoa 现在提供了一些可以让你存储弱引用的集合。旧版本的 Foundation 框架提供 `NSMapTable` 和 `NSTHashTable` 作为不透明的 C 类型，并带有一组 C 函数来使用它们。这些接口仍然可用，但在 10.5 版本中，Apple 将这两个 C 类型转换成了类。
