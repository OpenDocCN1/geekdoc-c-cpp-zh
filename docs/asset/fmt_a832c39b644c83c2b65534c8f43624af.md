## Native Image Generation

The Native Image Generator (`Ngen.exe`) is a tool used by managed applications to improve the performance of an application. The `Ngen.exe` tool is used to create native images, which are files consisting of compiled processor-specific machine code. This tool also installs these image files on to the local computer, which are then used for compiling the original assembly.

The following are the noteworthy features of the `Ngen.exe` tool:

- Ensures that the dependencies of an assembly are also installed when you install the assembly
- Allows you to share native images across application domains
- Uses the update action to re-create images that have been invalidated

You can skip the JIT compilation by generating a native image for your managed assembly using `Ngen.exe`. After you have generated the native image, the runtime loads the native image instead of generating the image by performing JIT compilation, which reduces the assembly load-up time.

Let’s create the native image of `MultiFileAssembly.exe`, which we have created earlier. Open the Visual Studio command prompt (2010). Navigate to the folder where the `MultiFileAssembly.exe` resides and type the following command:

```
ngen MultiFileAssembly.exe
```

The command creates a native image for your assembly and stores it in native image cache, which is a reserved area of GAC. To see all the native images in the native image cache, write the following command:

```
ngen /show
```

To see all the image files of different versions for a particular assembly in native image cache, specify the assembly name with the show switch. For example, to see all the versions of `MultiFileAssembly.exe` in native image cache, type the following command:

```
ngen /show MultiFileAssembly
```

> TIP
>
> If you navigate to `<WinDir>\assembly` at the command prompt, you would see a folder named `NativeImages_<runtime_version>`, where all the assemblies compiled to a native image reside.

> NOTE
>
> You must always keep in mind that native image compilation does not always give better performing assemblies compared to JIT compiled ones. A JIT compiler improves the performance of an application to a great extent. Therefore, always compare the performance of your applications in both ways (i.e. using the native image compiler and the JIT compiler) before deciding to generate native images for them.

## Delayed Signing

As discussed in the In Depth section, Delayed Signing is used to make changes in the assembly at a later stage. Using the `sn.exe` utility, you can skip signing the assembly with the private key and turn off the assembly’s verification. You can provide the public key to other developers to make changes in an assembly. After the developer completes the entire task with the assembly, the assembly’s verification is turned on and it is signed with the private key before deployment and distribution.

Now, to understand this concept, create a new class library project named `DistAssembly` (also available on the CD-ROM), and perform the following steps:

+ 1. Add the code, shown in Listing 33.14, on the `Class1.cs` file:

### Listing 33.14: Showing the Code for the Class1.cs File

```
using System;
using System.Collections.Generic;
using System.Linq;
using System.Text;

namespace DistAssembly
{
    public class Class1
    {
        void Greeting()
        {
            System.Windows.Forms.MessageBox.Show("Unsigned Distributable Assembly Says Hi!");
        }
    }
}
```

Since the code returns a message box, add the `System.Windows.Forms` reference to this application.

> NOTE
>
> You need to add the reference of the `System.Windows.Forms` in the application.

+ 2. Open the .NET command prompt with the Start→All Programs→Microsoft Visual Studio 2010→Visual Studio Tools→Visual Studio Command Prompt (2010) and change the directory to the `DistAssembly` folder. You need to first create a new and unique public–private key pair file for your assembly.

+ 3. Type the following command at the command prompt:

```
sn /k TheKey.snk
```

The preceding command creates a new key pair file called `TheKey.snk`. If you do not want to give the key pair file containing both private and public keys, you can extract the public key from your key pair file using the `sn` utility by using the following command:

```
sn /p TheKey.snk ThePublicKey.snk
```

The public key is extracted to the file called `ThePublicKey.snk`.

+ 4. Add the following line to the `AssemblyInfo.cs` file of our `DistAssembly` project:

```
[assembly: AssemblyKeyFile("../../ThePublicKey.snk")]
```

> NOTE
>
> You need to add the `ThePublicKey.snk` file in the application.

+ 5. Build the assembly using Build→Build `DistAssembly`. You get the following error during compilation:

+ Error 1 Cryptographic failure while signing assembly 'D:\Black Books\C# 2010\Chapter 33\Code\DistAssembly\DistAssembly\obj\Debug\DistAssembly.dll' -- 'key file '../../ThePublicKey.snk' is missing the private key needed for signing' `DistAssembly`

This error is caused because you have still not set up the assembly to skip the private key signing process.

6. Add the following highlighted line to the `AssemblyInfo.cs` file of the `DistAssembly` project:

```
[assembly: AssemblyDelaySign(true)]
[assembly: AssemblyKeyFile("../../ThePublickey.snk")]
```

Now, build the assembly using Build→Build `DistAssembly`. You can then turn off the verification process for the assembly by using the following command:

```
sn /Vr DistAssembly.dll
```

The preceding command also creates enough free space in the assembly for the signature information so that the assembly can be signed again at a later stage.

Now, you may provide the assembly to another developer, with the public key file. Moreover, after the developer completes his work on the assembly, you can sign the assembly with a private key using the following command:

```
sn /R DistAssembly.dll ../../TheKey.snk
```

> Tip
>
> Delayed Signing can also be performed from the project property's Signing tab.

## Configuring Assembly Lookup

As already learned, private assemblies reside in an application folder; whereas, shared assemblies reside in the system's GAC. However, there are situations when you might need to place your assemblies at some other specific locations. .NET Framework 4.0 allows you to decide a location for your assembly so that you can configure your applications to look up the assemblies at the specified locations. As discussed in the In Depth section, all configurations take place in the assembly configuration files. There are two ways to work with the configuration files. One is through the configuration tools and the other way is doing it manually. Let's explore these methods next.

## Configuring Probing

In this section, we configure the assembly lookup for private assembly (`PrivateAssembly`) and its client (`Displayer`), which we have created earlier in this chapter. Create a new copy of the `Displayer` application and add a subfolder in its `bin\Debug` directory, named `SubDir`. Now, move `PrivateAssembly.dll` to the `SubDir` folder. At this stage, if you try to run the `Displayer` application, a `System.IO.FileNotFoundException` exception occurs. This exception occurs because the `Displayer` application searches the `PrivateAssembly.dll` file in the same folder where it itself resides.
