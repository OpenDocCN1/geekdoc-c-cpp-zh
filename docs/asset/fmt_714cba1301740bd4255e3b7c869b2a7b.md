# 图36.4：ASP.NET 应用程序的安全体系结构

ASP.NET 应用程序的安全性在很大程度上依赖于 IIS 和 .NET Framework 提供的安全机制。在 IIS 6.0、7.0 和 7.5（随 Windows 7 提供）中，ASP.NET 工作进程 `aspnet_wp.exe` 在 `NetworkService` 帐户下运行，IIS 工作进程 `w3wp.exe` 也在此帐户下运行。IIS 工作进程承载 IIS Web 服务器，而 ASP.NET 工作进程承载 ASP.NET 应用程序。`NetworkService` 帐户是一个具有某些有限权限的内置帐户。此帐户可以保护 Web 服务器免受黑客和意图破坏 Web 服务器的用户的恶意攻击。`NetworkService` 帐户用于运行 ASP.NET 工作进程，而不是像以前版本的 IIS 和 Windows (Windows XP) 那样使用 `ASPNET` 用户帐户。

在某些情况下，你可能希望以比 `NetworkService` 帐户更少的权限运行 ASP.NET 工作进程。在这种情况下，你可以通过更改 `machine.config` 文件中的某些相关属性来更改运行 ASP.NET 工作进程的用户帐户。`machine.config` 文件位于计算机上的 `C:\Windows\Microsoft.NET\Framework\v4.0.30319\Config` 文件夹中。`machine.config` 文件是一个 XML 文件，包含定义 .NET 应用程序机器级配置设置的各种标记或元素。你可以在记事本或 Visual Studio 2010 中打开 `machine.config` 文件，并在 `<system.web>` 元素中找到 `<processModel>` 元素。在 `<processModel>` 元素中，你可以设置 `userName` 和 `password` 属性。若要让 ASP.NET 工作进程在 `TestUser` 用户帐户下运行，请按如下方式设置 `userName` 和 `password` 属性：

```
<processModel autoConfig="true" userName="TestUser" password="@kogent30"/>
```

`password` 属性的值是你为 `TestUser` 帐户指定的密码。

#### 注意

> 除了 `NetworkService` 帐户之外，还有 `LocalSystem` 和 `LocalService` 内置帐户。`LocalSystem` 帐户属于 `Administrators` 组，在三个帐户中拥有最大权限。因此，`LocalSystem` 帐户对于 Web 服务器和 Web 应用程序可能不安全。`LocalService` 帐户的权限最少，在应用程序不使用任何远程资源时非常有用。

## 身份验证模式

如你所知，身份验证是指验证用户身份的过程。用户可以是个人、另一个应用程序或服务。ASP.NET 应用程序用户的真实性是共同地由 IIS 和 ASP.NET 应用程序本身决定。当用户请求 Web 页面时，IIS 首先进行身份验证。如果 IIS 对用户进行了身份验证，则由 ASP.NET 应用程序进行身份验证。如果 ASP.NET 应用程序也对用户进行了身份验证并且用户具有授权，则授予用户访问 Web 页面的权限，如图 36.5 所示：

![](img/e073a4882197be4ab61103cbe0bcb394_1678_0.png)

图 36.5：显示 ASP.NET 应用程序的身份验证和授权

可用于 ASP.NET 应用程序的身份验证模式有：

- 匿名身份验证
- Windows 身份验证
- 表单身份验证
- Passport 身份验证

请注意，除了 Passport 身份验证外，其他所有身份验证模式都同时受 IIS 7.5 和 ASP.NET 支持。要允许在 IIS 级别进行身份验证，您需要使用 IIS 管理器并指定所需的身份验证。如果您想在 ASP.NET 应用程序中允许身份验证，则需要使用身份验证提供程序。身份验证提供程序是指包含执行所需身份验证的基本代码的代码模块。ASP.NET 为 Windows、表单和 Passport 身份验证提供身份验证提供程序；匿名身份验证没有身份验证提供程序。

现在，让我们一个一个地学习这些身份验证模式。

### 匿名身份验证

请求 ASP.NET Web 资源（例如 Web 页面）的用户默认情况下被验证为匿名用户，即具有任意随机身份的用户。当用户被验证为匿名用户时，该过程称为匿名身份验证。在这种类型的身份验证中，不需要凭据（用户名和密码）来验证用户。这意味着任何尝试访问 Web 资源的用户都会自动通过身份验证，这就是为什么当您希望 ASP.NET 应用程序对所有用户可用或希望获得更好性能时，匿名身份验证很有用。匿名身份验证提供最少的 安全，因此，您需要谨慎地对 ASP.NET 应用程序的匿名用户进行身份验证。

### Windows 身份验证

考虑这样一种情况：您的 ASP.NET 应用程序位于 Intranet 或本地计算机上，您希望通过网络或计算机上的不同用户来控制对应用程序的访问。因此，授予应用程序匿名访问可能不是可行的解决方案。在这种情况下，您可以使用 Windows 身份验证来控制对 ASP.NET 应用程序的访问。通过 Windows 身份验证，将用户的身份与存储在 Web 服务器上的 Windows 用户帐户进行检查。如果用户的凭据与 Windows 用户帐户的凭据匹配，则用户通过身份验证。您可以在 IIS 以及 ASP.NET 应用程序中使用 Windows 身份验证。默认情况下，所有 ASP.NET 应用程序都使用 Windows 身份验证。您可以在以下代码中看到 `<authentication>` 元素的默认设置：

```
<authentication mode="Windows" />
```

当您在 ASP.NET 应用程序中实现 Windows 身份验证时，应用程序使用 IIS 执行的身份验证。如果未经身份验证的用户请求 ASP.NET 应用程序的 Web 页面，则 IIS 会显示对话框以获取用户的凭据。用户提供 Windows 凭据后，IIS 会将凭据与现有 Windows 用户帐户进行验证。如果 IIS 找到匹配项，则用户通过身份验证；否则，拒绝访问 Web 页面。如果 IIS 对用户进行身份验证，则已验证用户的身份将传递给 ASP.NET 应用程序。

在 ASP.NET 中，Windows 身份验证提供程序负责在应用程序中实现 Windows 身份验证。Windows 身份验证提供程序是存在于 `System.Web.Security` 命名空间中的 `WindowsAuthenticationModule` 类的实例。`WindowsAuthenticationModule` 对象引用 ASP.NET 应用程序中已验证的 Windows 用户的身份。当您在 ASP.NET 应用程序中启用 Windows 身份验证时，`WindowsAuthenticationModule` 对象会创建一个 `WindowsIdentity` 对象来表示已验证的用户，并将其分配给 `HttpContext` 对象的 `User` 属性。

> 注意
>
> 如果您在 IIS 中选择了匿名身份验证并在 ASP.NET 应用程序中启用了 Windows 身份验证，则应用程序将从 `WindowsIdentity` 类的 `GetAnonymous()` 方法的返回值中获取用户的身份。

要在 ASP.NET 中使用 Windows 身份验证，您需要在 IIS 中首先适当地设置身份验证模式。您可以在 IIS 中启用以下任何身份验证模式以在 ASP.NET 应用程序中使用 Windows 身份验证：

- 匿名身份验证
- Windows 身份验证（集成）
- 基本身份验证
- 摘要身份验证

您已经了解到匿名身份验证是 IIS 的默认身份验证模式。现在，让我们学习 IIS 中的 Windows、基本和摘要身份验证模式：

- Windows 身份验证（集成） – 在 IIS 中，Windows 身份验证也称为集成 Windows 身份验证，根据用户 Windows 凭据的真实性对用户进行身份验证。IIS 使用客户端上当前登录用户的 Windows 凭据来验证用户。根据客户端的操作系统和 Web 浏览器，此第一次身份验证尝试可能成功也可能失败。如果第一次尝试不成功，客户端上的 Web 浏览器会显示对话框提示用户输入凭据。对话框中提供的凭据将发送到 Web 服务器进行身份验证。用户最多可以提供三次凭据发送到 Web 服务器。如果用户在第三次尝试时仍无法提供有效凭据，则 Web 浏览器中会出现错误。图 36.10 显示了集成 Windows 身份验证的过程：

当你在 IIS 中启用 Windows 身份验证时，默认情况下使用 Negotiate 身份验证协议。Negotiate 协议与 Web 浏览器协商，以确定使用 NTLM 还是 Kerberos 身份验证。如果 Web 服务器和浏览器都支持 Kerberos，则使用 Kerberos 身份验证；否则，使用 NTLM 身份验证。Kerberos 身份验证使用客户端的 Windows 域控制器，因此，如果用户具有 Windows 用户帐户，则 IIS 可能会使用 Kerberos 身份验证。但是，如果用户是非 Windows 用户，或者 Web 服务器与客户端之间没有服务器代理，则 IIS 可能会使用 NTLM 身份验证。

NTLM 身份验证是 Negotiate 身份验证协议默认使用的身份验证方式。你可以在位于 `C:\Windows\System32\inetsrv\config` 文件夹中的 `applicationHost.config` 文件中看到此默认设置。在 `applicationHost.config` 文件中，有一个 `<windowsAuthentication>` 元素，如以下代码所示：

```xml
<configuration>
.
<system.webServer>
.
<security>
.
<authentication>
.
<windowsAuthentication enabled="false">
<providers>
<add value="Negotiate" />
<add value="NTLM" />
</providers>
</windowsAuthentication>
</authentication>
</configuration>
```

## 摘要身份验证

摘要身份验证与基本身份验证相同，只是它的防御能力比基本身份验证更强。与基本身份验证不同，在摘要身份验证中，用户名和密码不以明文形式发送，而是以 MD5 消息摘要（即 Message Digest 5 (MD5) 哈希）的形式发送。这种 MD5 哈希使得未经身份验证或未经授权的用户难以截获。MD5 哈希是一种加密消息，在 HTTP 标头中发送到 Web 服务器。在本章后面，您将了解更多关于 MD5 的内容。Web 浏览器将 MD5 哈希发送到 Web 服务器，以便 IIS 可以对用户进行身份验证。IIS 接着将 MD5 哈希传递给 Windows 域控制器，然后由域控制器确定用户的真实性。

要在 IIS 中实现摘要身份验证，需要确保 Web 服务器和客户端都是同一个域的成员。此外，Windows 域控制器需要启用可逆加密，才能通过摘要身份验证对用户进行身份验证。

> 注意
>
> 摘要身份验证仅适用于支持 HTTP 1.1 协议的 Web 浏览器。符合 HTTP 1.1 的 Web 浏览器的一些示例包括 Internet Explorer 6、7 和 8。

基本身份验证和摘要身份验证模式都可以在跨代理服务器和防火墙时提供安全性。此外，为了有效实现基本身份验证和摘要身份验证，您需要首先确保在 IIS 中禁用匿名身份验证；否则，将使用匿名身份验证。现在，让我们继续了解 IIS 和 ASP.NET 中的 Forms 身份验证。

## Forms 身份验证

假设有一个 ASP.NET 应用程序，它提供在线买卖（即通过 Internet）的功能。为了进行安全可靠的交易，该应用程序需要唯一标识大量想要买入或卖出的用户。在这种情况下，为每个用户创建 Windows 用户帐户可能不可行。此外，用户可能不知道使用哪些 Windows 凭据来访问该应用程序。在这种情况下，您可能希望允许用户使用自定义凭据进行订阅或注册。您可以将有效凭据存储在后端数据库或应用程序本身中。要对这些拥有非 Windows 凭据的用户进行身份验证，需要允许他们提供凭据以进行身份验证过程，而这在匿名身份验证和 Windows 身份验证模式下是无法实现的。ASP.NET 提供了一种名为 Forms 身份验证的身份验证模式，适用于此类情况。

您可以使用 Forms 身份验证来对独立于 Windows 操作系统的用户进行身份验证。您可以在 ASP.NET 应用程序中编写自己的代码来对用户进行身份验证。在 Forms 身份验证中，如果用户尝试访问网页或资源，您可以将该用户重定向到另一个网页（通常称为登录页）。登录页包含一个 HTML 表单，用户需要在该表单上提供身份验证所需的凭据（用户名和密码）。当登录页提交到 Web 服务器时，将验证凭据。如果用户通过身份验证，则授予该用户访问所请求网页的权限。如果用户未通过身份验证，则再次将用户重定向到登录页以提供正确的凭据。

> 注意
>
> 使用 Forms 身份验证时，用户的用户名和密码会以明文形式传递给 Web 服务器。因此，在使用 Forms 身份验证时，建议在 Web 服务器和客户端之间使用 SSL 连接。

如果用户通过身份验证，则会向用户发送一个身份验证 Cookie，该 Cookie 包含一个票证，票证中保存着已通过身份验证用户的凭据。当用户随后发出任何请求时，此身份验证票证会被发送到 Web 服务器以重新识别该用户。身份验证 Cookie 的生成取决于 Web 浏览器，因为有些 Web 浏览器不支持 Cookie。在这种情况下，您可以采用无 Cookie 的 Forms 身份验证。在无 Cookie 的身份验证情况下，身份验证票证会被加密，然后通过 URL 本身发送给用户。
