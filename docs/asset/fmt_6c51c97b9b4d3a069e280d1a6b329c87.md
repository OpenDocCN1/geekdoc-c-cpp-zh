## 40.9 无锁原子变量

## 40.10 原子标志

标准只保证一种类型是无锁：`atomic_flag`。这是一个用于测试并设置（test-and-set）操作的不透明类型。

它可以被设置或清除。你可以将其初始化为清除：

```c
atomic_flag f = ATOMIC_INIT;
```

你可以通过 `atomic_flag_test_and_set()` 原子化地设置标志，它会设置标志并返回之前的状态（设置为为 true）。

你可以通过 `atomic_flag_clear()` 原子化地清除标志。

这里有一个示例，我们初始化标志，设置两次，然后再次清除它。

```c
#include <stdio.h>
#include <stdbool.h>
#include <atomic.h>

atomic_flag f = ATOMIC_INIT;

int main(void) {
    bool r = atomic_flag_test_and_set(&f);
    printf("Value: %d\n", r); // 0

    r = atomic_flag_test_and_set(&f);
    printf("Value: %d\n", r); // 1

    atomic_flag_clear(&f);
    r = atomic_flag_test_and_set(&f);
    printf("Value: %d\n", r); // 0
}
```

## 40.12 原子指针

这里说明一下指针中原子类型（Atomic）的放置。



## 40.13 内存顺序

`p = &x; // 正确！`

我们之前已经讨论过顺序一致性（sequential consistency），这是这些模式中最合理的一种。但还有其他几种：

| `memory_order` | 描述 |

| --- | --- |

| `memory_order_seq_cst` | 顺序一致性 |

| `memory_order_acq_rel` | 获取/释放 (Acquire/Release) |

| `memory_order_release` | 释放 (Release) |

| `memory_order_acquire` | 获取 (Acquire) |

| `memory_order_consume` | 消费 (Consume) |

| `memory_order_relaxed` | 松弛 (Relaxed) |

你可以通过某些库函数指定其他顺序。例如，你可以这样给原子变量增加一个值：

```cpp
atomic_int x = 0;
x += 5; // 顺序一致性，默认
```

或者你可以使用这个库函数实现相同：

```cpp
atomic_int x = 0;
atomic_fetch_add(&x, 5); // 顺序一致性，默认
```

或者你可以使用显式的内存顺序执行相同的操作：

```cpp
atomic_int x = 0;
atomic_fetch_add_explicit(&x, 5, memory_order_seq_cst);
```

但如果我们不想要顺序一致性呢？由于某种原因，你想要获取/释放语义？只需命名即可：

```cpp
atomic_int x = 0;
```

```cpp
atomic_fetch_add_explicit(&x, 5, memory_order_acq_rel);
```

我们将在下方对不同的内存顺序进行详细说明。除非你确定自己在做什么，否则不要动顺序一致性以外的任何东西。很容易出错并导致非常困难且难以复现的失败。

### 40.1.3 顺序一致性

- 加载（Load）操作执行获取（见下文）。

- 存储（Store）操作执行释放（见下文）。

- 读-修改-写操作先执行获取后释放。

此外，为了维护获取和释放的总顺序，任何获取或释放操作都不会彼此之间重排序。（获取/释放规则并不禁止重排一个释放随后的获取。但顺序一致性规则禁止。）

### 40.13.2 获取 (Acquire)

这是在原子变量上执行加载/读取操作时发生的情况。

- 如果另一个线程释放了这个原子变量，该线程执行的所有写入现在对此线程可见。

- 此线程中发生在该加载操作之后的内存访问不能被重排到它之前。

### 40.13.3 释放 (Release)

这是对原子变量执行存储/写入操作时发生的情况。

- 如果另一个线程获取了这个原子变量，此线程中在原子写入之前的所有内存写入对该另一个线程可见。

- 此线程中发生在该释放操作之前的内存访问不能被重排到它之后。

### 40.13.4 消费 (Consume)

这是一个旧概念，类似于不那么严格的获取版本。它影响依赖于原子变量的数据内存访问。

“数据依赖”模糊地意味着该原子变量被用在计算中。

也就是说，如果一个线程消费了一个原子变量，那么该线程中后续使用该原子变量的所有操作都能够看到释放线程中的内存写入。

与获取（acquire）相比，释放线程中的内存写入将对当前线程中的所有操作可见，而不仅仅是数据依赖的操作。

此外，获取对于哪些可以重排在消费（consume）之前的操作有限制。在获取中，你不能在它之前重排任何内容。在消费中，你不能重排任何依赖于所加载的原子值的内容。

### 40.13.5 获取/释放 (Acquire/Release)

这只适用于读-修改-写操作。它将获取和释放封装在一起了。

- 获取发生在读取阶段。

- 释放发生在写入阶段。

### 40.13.6 松弛 (Relaxed)

没有规则；它是无序的！所有操作都可以重排！线程之间没有任何同步。

对于这种内存顺序，你可以在某些情况下找到它，例如简单的计数器。

你可以使用内存障（fence）来强制对松弛写入进行同步。

## 41.1 函数限定符 (Function Specifiers)

当你声明一个函数时，可以给编译器提供一些关于该函数如何被调用或可能如何被使用的提示。这可以启用或鼓励编译器进行某些优化。

### 41.1.1 使用 `inline` 提高速度——也许吧

你可以这样声明一个内联函数：

```c
static inline int add(int x, int y) {
    return x + y;
}
```

它的目的是鼓励编译器让这个函数调用尽可能快。从历史上看，实现这一点的方法之一是内联（inlining），这意味着函数的体将完整地嵌入到调用它的地方。这可以避免设置函数调用和销毁调用的所有开销，代价是代码体积变大，因为函数被复制到了到处，而不是被复用。

这似乎就是故事的结局了，但事实如此。`inline` 带来了一整套规则，让情况变得变得。我不确定是否理解所有的它们，而且行为似乎随编译器而异。

简短的答案是：在需要的文件中将 `inline` 函数定义为 `static`。然后在一个文件中使用它。你永远不需要担心其他的。

但如果你好奇，这里有更有意思的。让我们尝试去掉 `static`。

```c
#include <stdio.h>

inline int add(int x, int y) {
    return x + y;
}
```

```c
int main(void)
{
    printf("%d\n", add(1, 2));
}
```

`gcc` 对 `add()` 给出了链接错误……除非你用优化进行编译（可能吧！）

看，编译器可以选择是否内联，但如果它选择了内联，它将完全不使用任何函数。除非你定义了优化构建，否则 `gcc` 不会内联。

解决此问题的方法之一是在地方定义一个非内联的外部链接版本的函数，当内联版本不可用时使用它。但由于程序员无法确定会用哪一个，也许吧。如果两个都可用，编译器选择哪一个是未指定的。在 `gcc` 中，如果你用优化进行编译，将使用内联函数，否则将使用非内联的。如果这些函数的体是由……

另一种方法是将函数声明为 `extern inline`。然后它会尝试在此文件中进行内联，但也会创建一个具有外部链接的版本。这样 `gcc` 就会根据优化情况使用其中一个，但至少它们是同一个函数。

除非，当然，你还有另一个源文件包含一个同名的内联函数；它将根据优化情况使用内联函数或具有外部链接的版本。
