## 5 无 Bug

消除 Bug 分为三个步骤：

- 1) 将 Bug 引入代码中（是的，是你把它放进去的）
- 2) 找到这个 Bug
- 3) 修复它

本书名为《无 Bug》，是因为它试图尽量减少第一步，即在程序中引入 Bug。通过在编写代码时减少 Bug 的数量，你可以大幅缩短完成和测试程序所需的时间。书中介绍的大多数技巧实际上并不能阻止你编写带有 Bug 的代码。换句话说，你仍然会犯犯过的同样的错误。但你的程序在发现你的错误时会举起红旗，允许你快速、无痛地修复它们。

大多数技巧都是快速且不干扰操作的。每个人都知道编写无 Bug 的代码至关重要，但大多数开发者在进度紧迫（经理在脑后催促）或有更有趣的代码等待着他们时，不愿花时间去消除 Bug。这些技巧的设计是为了让匆忙的开发者也能使用它们。通过几个小时的练习，你就可以实现书中大部分的代码示例，而且在发现 Bug 之前，你并不会真正看到这些新代码。

## 第 2 章

### 什么是 BUG？

这是全书中最重要的一章。“什么是 bug ？”这个极其简单的问题，实际上有一个非常复杂的答案。本章专门用于回答这个问题。因为，在我们不知道什么是 bug 之前，我们没有机会减少它们。

我认识的一位开发者曾说过：“bug 不应该被称为 bug，它们应该被称为**大烂砸（Massive Fuck-Ups [MFUs]）**。”“Bug”这个词暗示了某种外部力量决定向你的程序中注入 bug，而且好像只要你生活圣洁，在电脑脚下牺牲一些小毛茸茸动物，它们就会消失。

MFU 的存在是因为程序是由人编写的，而人会出错。消除 MFUs 的唯一方法是进入你的代码，找到 bug 并修复它们。

这是最需要理解的概念（也是最经常被忽略的）。你会写出 MFUs。你会坐下来，并带着完全故意的恶意，在你的代码中放入 MFUs。想一想——你知道你自己就是那个把 bug 放进那里的人。所以，当你坐下来写代码时，你就会插入一些 bug。

而且有人需要找到它们并删除它们。无论进行多少的设计、原型制作、CASE、评审、管理等，都无法避免这一点。

这个概念之所以重要，因为它影响了你调试代码的方法。如果你将错误视为“bugs”，你就会希望它们一个也没有被发现（你希望好心仙子路过并洒了仙尘，bug 就此离开了）。如果你将错误视为 MFUs，你就知道它们确实存在，并且你希望找到所有的它们，以便它们被修复。

对于开发者和经理来说，在 MFUs 被发现时感到良好而不是糟糕，是至关重要的。如果他们没有发现任何问题，他们反而应该担心。与其假设你的程序运行良好并等待别人证明反之，开发者应该假设它运行并不良好，并拼命寻找导致它失败的 bug。

所以，目前，你必须接受会在代码中创建 MFUs（我设法在我的代码里偷偷塞进很多）。我不知道任何方法可以避免这一点。诀窍在于尽可能无痛地找到并纠正它们。

顺便提一句，“bug”这个词在开发者的词汇中已经根深蒂固，我没看到 MFU 能取代它的可能。然而，我认为偶尔将 bug 称为 MFUs 是重要的，这可以提醒人们 bug 是由于开发者的错误而“故意”放置在代码中的。

当开发者坚持认为 bugs 不是 MFUs 时，你应该感到担心。为什么？因为他们放弃了找出并修复它们的责任。这时，提醒他们至关重要，要告诉他们：当他们被告诉代码里有一个 MFU 时，比他们被告诉代码里有一个 bug 时，想要逃避责任要困难得多。

那么什么是 bug 呢？嗯，如果你运行程序它格式化了你的磁盘（假设你不是在写一个格式化程序），大多数人会同意是 bug 导致的。从现在起，意见开始产生分歧。我听过此类类的陈述：“没人用那个功能，所以硬盘崩溃了也没关系”；“告诉他们买个并口打印机就行了”；“可以手动同步结果，所以加得不对也没关系”，以及“那不是 bug，那是功能！”那些在自己编写的程序中认为这种类型可以接受的人，转过头就会把他们买的程序中的坏处归类为 bug。

根据我的定义，如果一个理智的人预期程序以某种方式运行某些功能，而它并没有做到——那么就是一个 bug。

### bug 从哪里来

bug 是如何进入程序的？非常简单：是你把它们放进去的。你肆无忌惮地坐下来并在你的程序中输入一些 bug 代码。它们不是自己溜进去。你可能写错了一行。你可能使用了错误的变量。你可能从别处拷贝了一些并不好用的代码。无论如何，都是你你你。

### 10 没有 bug

### 调试代码应当是只读的

我在许多程序中看到的一个常见问题是：程序在开启调试时运行正常，但在关闭调试时就会崩溃。（正如书中讨论的，有很多方法可以开启和关闭调试。然而，最常见的方法是使用 `#ifdef DEBUG` 和 `#endif`。）我甚至知道有一款商业程序在发布时开启了调试，但禁用了它的调试 `printf`，因为它在非调试模式下无法运行。

这个问题通常发生的原因是，代码中的调试检查部分在确定传递了错误的参数时，会从函数返回。然而，如果关闭了调试，同样的检查就不会发生，函数也不会返回错误。

这个问题有一个简单的解决方案。所有的调试代码都应该是只读的。这意味着什么？显然意味着只读取数据，从不写入数据。然而，同样重要的是它不影响代码路径。调试代码会被执行，但它永远不会导致后续代码路径发生变化。调试代码等同于调用一个返回 `void` 的函数。

所有的调试代码都应该放在 `#ifdef DEBUG` 中，以便可以开启和关闭测试。此外，将所有仅在调试模式下使用的函数放在 `#ifdef DEBUG` 中，这样该函数就不会出现在程序的最终版本中。此时，如果你在关闭调试的情况下仍调用调试代码，链接器会提醒你。

### 调试代码

```c
#ifdef DEBUG
void DebugCheck(char *p)
{
    ...
}
#endif
```

在宏的情况下，你可以在 `#ifdef DEBUG` 内部定义调试宏，然后定义一个在 `#else` 中不生成任何代码的宏。使用宏会让你的代码整洁得多。与其在代码中散布大量的 `#ifdef DEBUG` 语句，你只需要宏，结果代码看起来更整洁。下面的示例说明了这些宏的使用。

### 调试宏

```c
#ifdef DEBUG
#define DebugMacro(p) DebugCheck(p)
#else
#define DebugMacro(p)
#endif
```

### 使用调试宏

```c
// 洁洁：
p = GetBuf(0);
DebugMacro(p);
WriteBuf(p);
```

```c
// 太忙乱：
p = GetBuf(0);
#ifdef DEBUG
DebugCheck(p);
#endif
WriteBuf(p);
```

调试代码将应用程序数据视为只读是非常关重要的。实现调试代码的使用时，要确保在调试定义之外执行什么代码都没有产生影响。如果调试代码修复了数据或导致函数执行了不同的路径，那么当调试被移除（或未定义）时，你将得到一个不同的程序——你的调试是在害你而不是帮助你。

如果你的调试代码发现了参数错误，调试代码不应该导致函数返回。如果你想在非调试模式下执行相同的错误检查，正确的方法是在调试检查之后，在你的非调试代码中再次执行检查，然后返回。你调试代码的重点不是最高速度或最小尺寸，而是最大的调试效率。

下面的程序演示了一个只读的代码路径和一个非只读的代码路径。注意，在错误的示例中，只有在 DEBUG 开启的情况下，函数才能处理传入的 NULL 指针。

```c
// 正确（只读）：
#ifdef DEBUG
    if (! pSrc)
        ErrorPrintf("Source String NULL\n");
#endif
if (! pSrc)
    return (NULL);      // 即使 DEBUG 关闭，我们也处理 NULL

// 错误（非只读）：
#ifdef DEBUG
    if (! pSrc)
    {
        ErrorPrintf("Source String NULL\n");
        return (NULL); // 当 DEBUG 关闭时你会死在这里
    }
#endif
```

### 代码路径

难以发现的 bug 通常发生在相对罕见的情况下。毕竟，如果程序每次运行时都会重启你的系统，它通常会修复那个错误。

这些罕见情况中的某些是因为执行了从未执行过的代码路径导致的。当你的程序首次启动时，你通常会执行一两次 `malloc`。你有一段代码会在 `malloc` 失败时执行（你不是假设它会成功吗？），但它真的失败过吗？

如果没有，你就坐等事故的发生。当那个特定的 `malloc` 失败时，你的程序到底做了什么只要你没有测试过某个代码路径，你就没有测试过你的程序。确保你了每一个路径。如果你有一个 `"if () ... else..."` 并且你总是执行 `"else"` 部分，那么 `"if"` 部分 就是一个等待发生的 bug。

测试代码路径最简单的方法是通过宏：`Trap ()` 和 `IntTest`。

### 19 个 Bug

地址。你不仅需要担心传递给 `realloc` 的变量，如果另一个变量也持有指向旧地址（realloc 之前的地址）的指针。

然而，如果在调试模式下，`realloc` 总是返回一个不同的指针，那么你就知道自己会妥善处理它。此外，`realloc` 需要在旧内存位置中填充垃圾数据。否则，指向旧位置的指针在内存内存被再次使用之前仍然能看到合法数据。
