
# CHAPTER 9 Using Classes and Objects

To explicitly declare a destructor, you use an identifier that consists of a tilde (~) followed by the class name. You cannot provide any arguments when you call a destructor; it must have an empty parameter list. As a consequence, destructors cannot be overloaded; a class can have one at most. Like a constructor, a destructor has no return type.

Figure 9-44 shows an Employee class that contains only one field (idNumber), a property, a constructor, and a (shaded) destructor. When you execute the Main() method in the DemoEmployeeDestructor class in Figure 9-45, you instantiate Employee objects, with its own idNumber value. When the Main() method ends, the two Employee objects out of scope, and the destructor for each object is called. Figure 9-46 shows the output.

```csharp
class Employee
{
    public int idNumber {get; set;}
    public Employee(int empID)
    {
        IdNumber = empID;
        WriteLine("Employee object {0} created", IdNumber);
    }
    ~Employee()
    {
        WriteLine("Employee object {0} destroyed!", IdNumber);
    }
}
```

# Understanding GUI Application Objects

The program in Figure 9-45 never explicitly calls the Employee class destructor, yet you can see from the output that the destructor executes twice. Destructors are invoked automatically; you cannot explicitly call one. Interestingly, the last object created is the first object destroyed; the same relationship would hold true no matter how many objects the program instantiated.

An instance of a class becomes eligible for destruction when it is no longer possible for any code to use it—that is, when it goes out of scope. The actual execution of an object's destructor might occur at any time after the object becomes eligible for destruction.

Now, you have little reason to create a destructor except to demonstrate how it is called automatically. Later, when you write more sophisticated C# programs that work with files, databases, or large quantities of computer memory, you might want to perform specific cleanup or close-down tasks when an object goes out of scope. Then you will place appropriate instructions within a destructor.

# Understanding GUI Application Objects

The objects you have been using in GUI applications, as as Forms, Buttons, and Labels, are objects just like others you have studied in this chapter. That is, they encapsulate properties and methods. When you start a Windows Forms application in the IDE and drag a Button onto a Form, a statement is automatically created to instantiate a Button object.

Figure 9-47 shows the code for a new GUI application that a programmer started simply by dragging Button onto a Form. If you click on Form1.Designer.cs in the Solution Explorer and scroll down, you can display the code where the Button is declared. See Figure 9-47.

If you right-click button1 in the code and select Find References from the menu that appears, a list of every reference to button1 in the project is displayed in the Find Symbol Results area at the bottom of the IDE (You might need to resize the window to see the references clearly.). You can double-click each entry in the list to locate all the places where code has been generated for button1. You can also see how the Button's Name, Location, Size, and other properties are set.
