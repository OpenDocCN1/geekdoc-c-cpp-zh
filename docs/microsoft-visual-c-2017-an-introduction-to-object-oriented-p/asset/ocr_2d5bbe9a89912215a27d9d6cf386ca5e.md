The StackTrace begins at the point where an Exception is thrown, not where it is instantiated. This consideration makes a difference when you create an Exception in a class and throw it from multiple methods.

![](bbox=[0.137, 0.408, 0.198, 0.459])

Exceptions can be particularly useful when you throw them from constructors. Constructors do not have a return type, so they have no way to send information back to a calling method.

In C#, you cannot throw an object unless it is an Exception or a descendant of the Exception class. In other words, you cannot throw a double or a BankAccount. However, you can throw any type of Exception at any time, not just Exceptions of your own creation. For example, within any program you can code any of the following:

```
throw(new Exception());
throw(new IndexOutOfRangeException());
throw(new Exception());
```

Of course, you should throw appropriate Exception types. In other words, you should not throw an IndexOutOfRangeException when you encounter division by 0 or an incorrect type; you should use it when an index (subscript) is too high or too low. However, if a built-in Exception is appropriate and suits your needs, you should not create an excessive number of Special Exceptions for your classes, especially if the C# development environment already contains an Exception type that accurately describes the error. Extra Exceptions add a level of complexity for other programmers who will use your classes. Nevertheless, when creating, a specialized Exception class is an elegant way to take care of error situations. Exceptions allow you to separate your error code from the usual, nonexceptional sequence of events and allow for errors to be passed up the stack and traced.
