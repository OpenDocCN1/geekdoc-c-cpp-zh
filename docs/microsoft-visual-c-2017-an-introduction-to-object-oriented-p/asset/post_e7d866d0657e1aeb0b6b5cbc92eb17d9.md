The DivideByZeroException object was generated automatically by C#. It is an instance of DivideByZeroException class that has four ancestors. It is a child of the ArithmeticException class, which descends from the SystemException class. The SystemException class derives from the Exception class, which is a child of the Object class.

Just because an exception occurs and an Exception object is created, you don't necessarily have to deal with it. In the MilesPerGallon class, you simply let the offending program terminate; that is why the error message in Figure 11-2 indicates that the Exception is "Handled". However, the termination of the program is abrupt and unforgiving. When a program divides two numbers, or performs some other task such as playing a game, a user might be annoyed if the program ends abruptly. If the program is used for air-traffic control or to monitor a patient's vitals during surgery, an abrupt conclusion could be disastrous. With exception handling, a program can continue after dealing with a problem. This is especially important in mission-critical applications. The term mission-critical refers to any process that is crucial to an organization. Object-oriented error-handling techniques provide more elegant solutions than simply shutting down.

Programs that handle exceptions appropriately are said to be more fault tolerant and robust than those that do not. Fault-tolerant exceptions are designed so that they continue to operate, possibly at a reduced level, when some part of the system fails. Robustness represents the degree to which a system is resilient to stress, maintaining correct functioning.

## Purposely Causing Exceptions

C# generates SystemExceptions automatically under many circumstances. In the next steps, you purposely generate a SystemException by executing a program that provides multiple opportunities for Exceptions.

-   Start a new project named ExceptionsOnPurpose, and type the following program, which allows you to generate several different Exceptions.
```csharp
using System;
using static System.Console;
class ExceptionsOnPurpose
{
    static void Main()
    {
        int answer;
        int result;
        int zero = 0;
        Write("Enter an integer >> ");
        answer = Convert.ToInt32(ReadLine());
        result = answer / zero;
        WriteLine("The answer is " + answer);
    }
}
```

-   You cannot divide by the unnamed  (by changing the dividing statement to result = answer / 0), nor can you change the variable zero to a named constant (by inserting static at the start of the int declaration). If you made either of these changes, the program would not compile because the compiler can determine that division by zero will occur. Using a variable instead of either an unnamed or named constant, however, the compiler "trusts" that a legitimate value will be provided for the variable before division occurs (although in this case, the trust is not warranted). Save the program, and compile it.

-   Execute the program several times using different input values, and observe the results. The first reports that Windows appear with each execution. Three windows appear that Windows is checking for a solution to the problem, the second reports that it is collecting more information about the problem. This window is soon replaced with a third window as shown in Figure 11-3, which repeats that ExceptionsOnPurpose.exe has stopped working. You would never write a program that purposely divides by zero; you do so here to demonstrate C#'s exception-generating capabilities. If you were executing a professional application, you might be notified about a solution. Because you created this exception on purpose, just click the Close button.

## Comparing Traditional and Object-Oriented Methods

Another advantage to using exception handling instead of decision making to control errors is when a program's main logic is interrupted by a series of if statements and decisions that might detect errors, the program can become more complicated and difficult to understand. The object-oriented approach to error handling separates a program's main tasks from code that deals with rare exceptions.

Programmers use the phrase sunny day to describe a scenario in everything goes well and no errors occur.

## Understanding Object-Oriented Exception Handling

Object-oriented exception handling uses three unique terms: try, throw, and catch.

-   You "try" a procedure that may not complete correctly.
- A method that detects an error condition "throws" an exception.
- The block of code that processes the error "catches" the exception.

When you write a block of code in which something can go wrong, you can place the code in a try block, which consists of the following elements:

-   The keyword try
-   A pair of braces containing statements that might cause exceptions

You must at least one catch block or finally block immediately following a try. (You will learn about finally blocks later in this chapter.) Each catch block can "catch" one type of exception—that is, an Exception object or an object of its child classes. Programmers sometimes refer to a catch block as a catch clause. You can create a catch block by typing the following elements:

-   The keyword catch
-   Parentheses containing an Exception type and, optionally, name an instance of the Exception type
-   A pair of braces containing statements that deal with the error condition
