As an alternative to using a single catch block for multiple Exception types that require the same action, as in Figure 11-17, you could create the class to separate catch blocks, each of which calls the same error-handling method.

The catch block in Figure 11-17 accepts a more generic Exception type that might be thrown by either statement in the try block, so the generic catch block can act as a catch-all block. That is, when either a division arithmetic error or an array error occurs, the thrown error is “promoted” to an Exception in the catch block. Through inheritance, DivideByZeroExceptions and IndexOutOfExceptions are Exceptions.

As stated, some professional programmers recommend that a catch block should not handle general Exceptions. They say if you cannot predict all possible causes of an exception, you should allow the application to terminate instead of handling the exception. Otherwise, it is easier for malicious code to exploit the resulting application state. However, many other professional programmers disagree with this view. Programmers have called blocks that catch all exceptions Pokemon blocks, like in the popular game, “you just catch ‘em all”.

Although a block of code can throw any number of exceptions, many developers believe that it is poor style for a block or method to throw more than three or four types. If it does, one of the following conditions might be:

- Perhaps the code block or method is trying to accomplish too diverse tasks and should be broken into smaller blocks or methods.
- Perhaps the Exception types thrown are too specific and should be generalized, as they are in the TwoErrors program in Figure 11-17.

When you list multiple catch blocks following a try block, you must be careful that some catch blocks don’t become unreachable. Unreachable blocks contain statements that can never execute under any circumstances the program logic “can’t get there.” Programmers also call all unreachable dead code.

For example, if successive catch blocks an Exception followed by DivideByZero, then even DivideByZeroExceptions will be caught by the Exception catch. The second catch block, (DivideByZeroException) is unreachable because the more general Exception catch block is first and in its way, and therefore the class will not compile.

## Examining the Structure of the TryParse() Methods

In 8, you learned about the TryParse() methods that you can use to convert string to another data type, such as int, double, or bool, without fear of generating an exception. A typical TryParse() statement might be as follows:

```csharp
if(!int.TryParse(string, out number))
    number = DEFAULT_VALUE;
```

This statement uses the int version of the TryParse() method. The first argument is the string you want to convert to a number, and the second argument is an out parameter that receives the result if the conversion is successful or 0 if not. Each of the TryParse() methods returns a Boolean value indicating whether the conversion was successful. In the preceding example, the variable number is assigned a constant DEFAULT_VALUE if the method returns false—if, inputString is not an assigned.

Suppose that no TryParse() method existed to convert a string to an integer safely. Using what you have learned so far in this chapter, you could now write your own method. The method handles the exception it might generate so, the client doesn't have to be concerned with exception handling. Figure 11-19 shows a usable method.

## Examining the Structure of the TryParse() Methods

```csharp
public static bool TryParse(string inputString, out int number) {
    bool wasSuccessful = true;
    try {
        number = Convert.ToInt32(inputString);
    } catch (FormatException) {
        wasSuccessful = false;
        number = 0;
    }
    return wasSuccessful;
}
```

**Figure 11-19** A possible TryParse method

The TryParse() method in 11-9 is public static so that other classes can use it. It accepts a string and an out parameter that can hold the result. If aFormatException is thrown, wasSuccessful is set to false. Whether an exception occurred or not, the value of wasSuccessful is returned.

## Using the finally Block

When you act to perform at the end of a try...catch sequence, you can use a finally block, which executes whether or not the block identifies exceptions. Typically, you use the finally block to perform clean-up tasks that may occur, regardless of whether any errors occurred were caught. Figure 11-20 shows the format of a try...catch sequence that uses a finally block.

```csharp
try
{
  // Statements that might cause an Exception
}
catch(SomeException anInstance){
  // What to do about it
}
finally
  // Statements here execute
  // whether an Exception occurred or not
}
```

**Figure 11-20** General form of a try...catch block with a finally block
