# CHAPTER 11 Exception Handling

As an alternative to using a single catch block for multiple Exception types that require the same action, as in Figure 11-17, you could create the class to separate catch blocks, each of which calls the same error-handling method.

The catch block in Figure 11-17 accepts a more generic Exception type that might be thrown by either statement in the try block, so the generic catch block can act as a catch-all block. That is, when either a division arithmetic error or an array error occurs, the thrown error is “promoted” to an Exception in the catch block. Through inheritance, DivideByZeroExceptions and IndexOutOfExceptions are Exceptions.

As stated, some professional programmers recommend that a catch block should not handle general Exceptions. They say if you cannot predict all possible causes of an exception, you should allow the application to terminate instead of handling the exception. Otherwise, it is easier for malicious code to exploit the resulting application state. However, many other professional programmers disagree with this view. Programmers have called blocks that catch all exceptions Pokemon blocks, like in the popular game, “you just catch ‘em all”.

Although a block of code can throw any number of exceptions, many developers believe that it is poor style for a block or method to throw more than three or four types. If it does, one of the following conditions might be:

+   - Perhaps the code block or method is trying to accomplish too diverse tasks and should be broken into smaller blocks or methods.

+   - Perhaps the Exception types thrown are too specific and should be generalized, as they are in the TwoErrors program in Figure 11-17.

When you list multiple catch blocks following a try block, you must be careful that some catch blocks don’t become unreachable. Unreachable blocks contain statements that can never execute under any circumstances the program logic “can’t get there.” Programmers also call all unreachable dead code.

For example, if successive catch blocks an Exception followed by DivideByZero, then even DivideByZeroExceptions will be caught by the Exception catch. The second catch block, (DivideByZeroException) is unreachable because the more general Exception catch block is first and in its way, and therefore the class will not compile.
