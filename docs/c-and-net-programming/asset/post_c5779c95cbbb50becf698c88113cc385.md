## 26.3 Custom Hosting with CLR Objects

- While executing various applications there are multiple ways by which Windows understands that a binary is a .NET application. These techniques depend on versions of Windows. Normally, .exe files are executed by Windows by looking at the PE-Header (Portable Executable). This PE-Header says how it should be loaded into memory, what dependencies it has, and where the entry point is. To know the entry point of a .NET application, Windows uses a certain technique. Actually, the application is in some IL code. Executing that directly will clearly lead to a crash. It is not the IL code that should start executing, but the .NET runtime, which eventually should load the IL code and execute it.

- In newer versions of Windows, .NET comes preinstalled, and Windows has built-in support for recognizing a .NET application. This can be done by simply looking in the PE-Header present in all executables and DLLs. In older versions of Windows, execution is passed to an entry point where boot-strap code is located. The boot-strap, which is native code, uses an unmanaged CLR Hosting API to start the .NET runtime inside the current process and launch the real program, which is the IL code.

### 26.3.1 The CLR Hosting APIs

### Hosting the CLR in an unmanaged app

- Hosting the CLR is fairly straightforward from an unmanaged point of view; it is all just COM (Component Object Model). First, one needs to obtain an instance of ICLRRuntimeHost using whichever API is most appropriate, either CorBindToRuntimeEx() or CLRCreateInstance(). ICLRMetaHost and ICLRRuntimeInfo. Once the runtime host is obtained, it can be connected to the unmanaged host by calling ICLRRuntimeHost::SetHostControl(). With that done, one can provide an implementation of an AppDomainManager, tell the CLR the assembly and type to use, and start the CLR. An important thing to do is in the custom AppDomainManager registration: InitializeNewDomain() is implemented so that the flags are set to tell the CLR to register new application domains with the unmanaged host. It is illustrated in the code below.

```
public override void InitializeNewDomain(AppDomainSetup appDomainInfo)
{
    // let the unmanaged host know about the application
    InitializationFlags = AppDomainManagerInitializationOptions.RegisterWithHost;
}
```

- With that set, the application will get a call into the IHostControl::SetAppDomainManager() method for each application domain that's created. For additional hosting power, one needs to create an interface for communicating between the unmanaged host and the managed AppDomainManager, and possibly one for communicating back the other way.
- When the .NET runtime starts inside a native process, that native application becomes a host for the runtime. This adds .NET capabilities to the native applications.

```
#include <metahost.h>
#include <mscoree.h>
#pragma comment(lib, "mscoree.lib")

ICLRMetaHost *pMetaHost = nullptr;
ICLRRuntimeHost *pRuntimeHost = nullptr;
ICLRRuntimeInfo *pRuntimeInfo = nullptr;
HRESULT hr;

hr = CLRCreateInstance(CLSID_CLRMetaHost,
    IID_ICLRMetaHost, (LPVOID*)&pMetaHost);
hr = pMetaHost->GetRuntimeVersion(IID_PPV_ARGS(&pRuntimeInfo));
hr = pRuntimeInfo->GetInterface(CLSID_CLRRuntimeHost, IID_PPV_ARGS(&pRuntimeHost));
hr = pRuntimeHost->Start();
```

- Now the runtime is running, but it hasn't got any loaded user code yet. Some internal thread scheduler and garbage collector are surely running, because they are part of the CLR runtime.

### 26.3.2 Hosting the CLR in Managed app - Running Managed Code

To start a managed app from the host, the code below can be written:

```
AppDomain.CurrentDomain.ExecuteAssembly(assemblyName);
```

### The Old API

In an early version of the CLR hosting interface, **managed code** was getting executed through an API called GetDefaultDomain, which returned an AppDomain.

```
HRESULT hr = CorBindToRuntimeEx(..., IID_ICorRuntimeHost, (void**)&pRuntimeHost);
hr = pRuntimeHost->Start();
_AppDomain* pCurrentDomain = nullptr;
hr = pRuntimeHost->GetDefaultDomain(&pCurrentDomain);
pCurrentDomain->ExecuteAssembly(assemblyFilename);
```

But for some good reasons this interface has been deprecated. The old API had huge parts in unmanaged code, which proved to be a great disadvantage. Retrieving values or manipulating objects from an AppDomain in unmanaged code resulted in a lot of Marshaling (Serialization), which severely affects performance. The marshaling was also implicit, so it was not always obvious where it took place. Sometimes even the whole AppDomain was marshaled. The new API keeps all the custom code running within an AppDomain.

### New API

The new version of the CLR Hosting interfaces has been reworked. Much of the API has been moved from unmanaged code to managed code. In order to obtain an AppDomain instance, one has to register an AppDomainManager implementation. To register a new AppDomainManager, an interface ICLRControl is required. This interface contains a method, SetAppDomainManagerType, which loads the managed implementation of the AppDomainManager. The code is shown below:

```
ICLRControl* pCLRControl = nullptr;
hr = pRuntimeHost->GetCLRControl(&pCLRControl);
LPCWSTR assemblyName = L"TechAppDomainManager";
LPCWSTR appDomainManagerTypename = L"TechAppDomainManager.CustomAppDomainManager";
hr = pCLRControl->SetAppDomainManagerType(assemblyName, appDomainManagerTypename);
```

That is how it is overridden. **The AppDomain** is not directly used so as to avoid all data marshaling as shown below:

```
hr = pRuntimeHost->Start();
DWORD returnValue = 0;
// Executing public static Start(string arg)
hr = pRuntimeHost->ExecuteInDefaultAppDomain(totalPath, L"TechApp1.Program", L"Start", L"", &returnValue);
hr = pRuntimeHost->Stop();
```

### IHostControl Class

This is a class that the CLR will query for implementation of alternative Managers; one should instantiate customized versions if there are any Managers and return them.

Examples of handlers or managers that can be overridden with a user implementation can be seen below:

- IID_IHostTaskManager
- IID_IHostThreadpoolManager
- IID_IHostSyncManager
- IID_IHostAssemblyManager
- IID_IHostGcManager
- IID_IHostPolicyManager

In the AppDomainManager case, the CLR will actually call IHostControl::SetAppDomainManager with a pointer to the instance of the class that is being told it to create. Earlier above, a method is called with a similar name ICLRRuntimeHost::SetAppDomainType.

## Two Marks Questions with Answers

Q.1 What is an Assembly? What are the different types of Assemblies?

Ans.: An Assembly is a collection of logical units. Logical units refer to the types and resources which are required to build an application and deploy them using the .NET Framework. The CLR uses this information for type implementations. Basically, an Assembly is a collection of EXEs and DLLs. It is portable and executable.

There are two types of Assemblies, Private and Shared.

- Private Assembly, as the name itself suggests, is accessible only to the application. It is installed in the installation directory of the application.
- Shared Assembly can be shared by multiple applications. It is installed in the GAC.

Q.2 Explain the different parts of an Assembly.

Ans.: The different parts of an Assembly include:

- Manifest - It contains the information about the version of an assembly. It is also called assembly metadata.
- Type Metadata - Binary information of the program.
- MSIL - Microsoft Intermediate Language code.
- Resources - List of related files.
