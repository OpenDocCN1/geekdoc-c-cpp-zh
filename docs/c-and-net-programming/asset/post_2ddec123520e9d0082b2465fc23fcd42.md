## 26.1.4 Providing High Security to Assembly

Security can be provided to assembly with the help of **File Signing Tool, signcode.exe**. It attaches a publisher's digital signature to assembly.

**Assembly can be signed with both Strong Name Tool and the File Signing Tool.**

When both Strong Name Tool and the File Signing Tool are used, it should be made sure that Strong Name Tool is used before using the File Signing Tool.

  - Name and Version Information of Assembly.

## 26.1.7 Multi-module Assembly

### Concept

- A multimodule assembly consists of multiple files (zero or one EXE and zero or more DLL files, though one must have at least one EXE or DLL).

### Explanation

- The assembly manifest in this case can reside in a standalone file, or it can be embedded in one of the modules. When the assembly is referenced, the runtime loads the file containing the manifest and then loads the required modules as needed.
- Multi-module assemblies have advantages for real-world programs, especially if they are developed by multiple developers or are very large.
- Building a Multimodule Assembly
- To demonstrate the use of multimodule assemblies, the following example creates a couple of very simple modules that can be combined into a single assembly.
- Example The first module is a Facto class. This simple class will allow to create and manipulate common fraction.

## Example

```
//The Facto class
#region Using directives

using System;
using System.Collections.Generic;
using System.Text;

#endregion

namespace ProgMModule
{
    public class Facto
    {
        private int no;
        private int ft;

        public Facto(int n, int f)
        {
            this.no = n;
            this.ft = f;
        }

        public int CheckRange( Facto f )
        {
            if (f.ft<5000)
                return 1;
            else
                return 0;
        }
        public override string ToString()
        {
            return numerator + "/" + denominator;
        }
    }
}
```

- The second module is NumOps class that works with number operations.

## Example

```
//The NumOps class
#region Using directives
using System;
using System.Collections.Generic;
using System.Text;

#endregion
namespace ProgMModule
{
public class NumOps
{
public int Add( int n1, int n2 )
{
return n1 + n2;
}
public int Mult( int n1, int n2 )
{
return n1 * n2;
}
}
}
```

- **Creating Assembly**
- Notice that the **Facto and NumOps classes** are in the **ProgMModule** namespace. The full name for the class is ProgMModule.Facto. This is sufficient to create an assembly.
- Now, use an **AssemblyInfo.cs** file to add some metadata to the assembly. One can write own AssemblyInfo.cs file, but the simplest approach is to let Visual Studio generate it automatically.
- Visual Studio creates **only single-module assemblies**.
- Multimodule resource is created with **the /addModules** command-line option. The simple way to compile and build a multimodule assembly is with a makefile, which can be created **with Notepad or any text editor**.
- Following example shows the complete makefile (which is explained in detail immediately afterward). To **run this example, put the makefile (with the name makefile)** in a directory together with a copy of NumOps.cs Facto.cs and AssemblyInfo.cs. Start up a .NET command window and cd to that directory. Invoke nmake without any command switch. One can find the MySharedAssembly.dll in the \bin subdirectory.

## Example

```
//Illustration of The complete makefile for a multimodule assembly

ASSEMBLY= MySharedAssembly.dll    // defining the assembly being build

/* defining the directories going to be used, putting the output in a bin directory beneath
   the current directory and retrieving the source code from the current directory*/

BIN=.\bin
SRC=.
DEST=.\bin

CSC=csc /nologo /debug+ /d:DEBUG /d:TRACE

MODULETARGET=/t:module
LIBTARGET=/t:library
EXETARGET=/t:exe

REFERENCES=System.dll

/*The two modules are defined as the two DLLs*/
MODULES=$(DEST)\Facto.dll $(DEST)\NumOps.dll

/* The metadata is defined now.*/
METADATA=$(SRC)\AssemblyInfo.cs

/* Build the assembly */
all: $(DEST)\MySharedAssembly.dll

# Assembly metadata placed in same module as manifest

/* below statement places the assembly (MySharedAssembly.dll) in the destination
   directory (bin). It tells nmake (the program that executes the makefile) that the
   $(DEST)\$(ASSEMBLY) build target depends upon the three other build targets listed,
   and it provides the command line required to build the assembly.*/
/*The compile line builds the library and adds the modules, putting the output into the
   assembly file MySharedAssembly.dll*/

$(DEST)\$(ASSEMBLY): $(METADATA) $(MODULES) $(DEST)
    $(CSC) $(LIBTARGET) /addmodule:$(MODULES: =,) /out:$@ %s

/*Making Module
   nmake should know how to make the modules. Start by telling nmake how to create
   NumOps.dll. NumOps.cs source file is required for this; tell nmake using command line
   to build that DLL*/

# Add NumOps.dll module to this dependency list
$(DEST)\NumOps.dll: NumOps.cs $(DEST)
    $(CSC) $(MODULETARGET) /r:$(REFERENCES: =,) /out:$@ %s

/* same process for Facto.dll*/
# Add Facto
$(DEST)\Facto.dll: Facto.cs $(DEST)
    $(CSC) $(MODULETARGET) /r:$(REFERENCES: =,) /out:$@ %s

$(DEST):
!if !EXISTS($(DEST))
    mkdir $(DEST)
!endif

/*The result of running nmake on this makefile is to create three DLLs: NumOps.dll,
   Facto.dll, and MySharedAssembly.dll. If MySharedAssembly.dll is opened with ILDasm,
   one can see manifest, .*/
```

## File Version

The assembly file version attribute should be incremented automatically when the build is performed. In the beginning of the build process, Build number portion of the file version is incremented before the build label is applied to source control. It is displayed by Windows Explorer and never used by .NET framework for referencing.

## Assembly Version

The assembly version is used by .NET when linking assemblies. Assembly versions are incremented manually when code branching is done for a release. This should be specified in a "shared assembly info" that ensures that all of the various assemblies in the solution have the same assembly versions. CLR looks for this version number at runtime.

## Web API Versioning

Web API Versioning is required as the site size (in terms of coding) grows and business requirement changes with the time. As Web API can be consumed by multiple clients at a time, Versioning of Web API will be necessarily required so that Business changes in the API will not impact the client that are using/consuming the existing API.

Web API Versioning can be done by using the following methods,

- 1. URI
- 2. QueryString parameter
- 3. Custom Header parameter
- 4. Accept Header parameter

- 1. **Web API Versioning using URI :** In this method, Web API URI is changed with the help of routing and is more readable. Suppose there is an existing running API in which one URI returns some response. All Clients are consuming the same API and one client wants some changes by requesting to add new properties. With Versioning, one can achieve the same without breaking the existing API flow. In this case, Web API Versioning using URI is one of the best ways to achieve the same.
- 2. **Web API Versioning using QueryString parameter :** In Web API Versioning using Query String, a query string parameter is added to the query string in order to find the controller or Action to which request is sent. Whenever a request comes, SelectController() method of DefaultHttpControllerSelector Class selects the controller information from the information passed in the URI. In order to achieve the versioning with Query String, we need to create a Custom DefaultHttpControllerSelector and override the SelectController() method.
