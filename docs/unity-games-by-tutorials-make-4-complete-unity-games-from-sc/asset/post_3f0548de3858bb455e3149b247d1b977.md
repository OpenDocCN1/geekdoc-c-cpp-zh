
![](img/fd5c2ca20ea33da76d2b61297cc57f6c_345_0.png)

Arranging sprites is also similar to working with layers when you're editing photos.

Unity uses the order to sort sprite visibility first. Within each layer, it sorts sprites further with an order number as 0, 1, 2 and so on, with 0 being the very bottom sub-layer.

Unity places new sprites on the Default Sorting Layer with an Order in Layer number of 0. If you set a stack of sprites in the same location but don't change this, then you'll get a little rendering density. Because they're sharing the same layer and order, some sprites might be hidden while others randomly appear and disappear.

It's a best practice to define custom Sorting Layer names and assign sprites to the right orders as you create them.

Navigate to Edit > Project Settings > Tags and Layers to bring up the Tags and Layers editor in the Inspector.

Expand the Sorting Layers node. Click the + button three times to add three Sorting Layers. Name them Background, Hazards and Foreground.

The order in which layers appear in this editor determines their render order. Use the handles icons to the left of each layer to drag and re-order so they match the image below:

There's a logic quirk here: The higher in the stack, the lower it renders on screen. For instance, the Background layer will render near the bottom of the stack, and the UI layer will render above everything else.

You'd probably like to know what each layer does in the game:

- Default: A layer provided by Unity.
- Background: Background sprites, such as mountains, scenery or background blocks that don't obstruct the player's path will go here.
- Hazards: Hazards and traps such as the blade will go in this layer.
- Foreground: Super Soy Boy will be placed here with most level elements.
- UI: Another layer that's specifically for rendering UI elements such as buttons and canvases.

As it stands now, your sprites will almost certainly do a funky rendering dance on screen. But now you know what it causes and it probably have some idea of how to fix. In the next few steps, you'll reorganize the sprites with Sorting Layers.

# Prefabs and Resources

Prefabs are essential to fluid gameplay. Rather than creating hundreds (thousands?) of sprites during the game, which nibbles away at processing power, Unity can use prefabs as templates to create various GameObjects on demand.

In the case of Soy Boy, you'll use prefabs to create levels. They consist of multiple copies of a base set of level blocks and shapes. Then you'll just clone these prefabs to make new levels.

Unity has a Resources class that lets you access assets in your project via code — any assets placed in a sub-folder of the Assets folder bears the name Resources can be accessed via Resources.Load() methods.

You're exploring the Resources class now because you'll create your own code for saving and loading that'll let you save a new level to a JSON file. This file will keep references to items used to create the level, e.g., blocks and hazards.

It's impractical to add public fields for every prefab used in a level. The JSON file will call the Resources.Load() methods to find the referenced objects by name.

Create a folder called Resources in the Assets folder. Then create a sub-folder inside named Prefabs. Now you'll create the first few prefabs.

One at a time, drag the single-block, top-left-corner-small, Buzzaw, and SoyBoy GameObject from the Hierarchy, and then drop them into the Prefabs folder.

![](img/fd5c2ca20ea33da76d2b61297cc57f6c_348_0.png)

Unity will allow resource items in game builds, whether they end up used or not. It's important to know because they can sneakily increase your build size.

In the Project Browser, right-click the Scripts folder and create a new C# Script. Name it SoyBoyController Double-click it to open the script in your editor.

At the top of the script, just add the public class SoyBoyController definition, add the following:

```
[Require(typeof(SpriteRenderer), typeof(Rigidbody2D), typeof(Animator))]
```

This line validates that any GameObject attached to this script has the necessary components required to work — it basically pre-qualifies the components. Your SoyBoy GameObject meets the requirement so it will pass with flying colors.
