+   - try to lock the mutex.
+   - delay the lock on the associated mutex.

The following table shows the member functions of a std::unique_lock lk.

**The interface of std::unique_lock**

| Member function | Description |
|---|---|
| lk.lock() | Locks the associated mutex. |
| lk.try_lock() and<br>lk.try_lock_for(relTime) and<br>lk.try_lock_until(absTime) | Tries to lock the associated mutex.<br>Tries to lock the associated mutex for the time duration relTime.<br>Tries to lock the associated mutex until the time point absTime. |
| lk.unlock() | Unlocks the associated mutex. |
| lk.release() | Release the mutex. The mutex remains locked. |
| lk.swap(lk2) | Swaps the locks. Same as std::swap(lk, lk2). |
| lk.mutex() | Returns a pointer to the associated mutex. |
| lk.owns_lock() and<br>operator bool | Checks if the lock lk has a locked mutex. |

lk.try_lock_for(relTime) needs a relative time duration; lk.try_lock_until(absTime) an absolute time point. lk.try_lock_for/lk.try_lock_until calls effectively the member function mutex.try_lock_for/mutex.try_lock_until on the associated mutex. The associated mutex has to support exclusive timed blocking. You should use a steady clock for your time constraint. A steady clock can not be adjusted.

lk.try_lock tries to lock the mutex and returns immediately. On success, it returns true, otherwise false. In contrast, the member functions lk.try_lock_for and lk.try_lock_until block the lock lk until the specified timeout occurs or the lock is acquired, whichever comes first. All three member functions lk.try_lock, lk.try_lock_for, and lk.try_lock_until throw a std::system_error exception if there is no associated mutex or if the mutex is already locked by this std::unique_lock.

lk.release() removes the underlying mutex from the lock object's control and returns a pointer to that mutex. After calling this member function, the caller is responsible for releasing it because the mutex is not associated with the lock object anymore.
