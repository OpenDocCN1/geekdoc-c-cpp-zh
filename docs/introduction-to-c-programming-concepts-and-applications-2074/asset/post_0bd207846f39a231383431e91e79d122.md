## // DEVELOPING ALGORITHMS

To develop the algorithm, you'll follow an approach that is similar to the top-down design approach, but you want to keep the problem as narrow as possible.

Next, you consider the output you want from the algorithm. Clearly, you want to output a move, the best one the algorithm could determine.

If you're faced with making a choice, you have 3 basic steps:
- Make a list of possible valid moves. For Connect 4, each player has 7 moves—any column that's not full.
- Evaluate each of those moves to get measure of how good or bad each is.
- Determine which of those moves is best and return the result.

The purpose of the algorithm is to let a computer determine the best move it can make in a game. With that goal, in mind you want to know at what point during the game? So, the input will be the current state of the game board and an indication of which player's turn it is.

Specifying the input and output clearly is an important part of algorithm design—just as important as the steps of the algorithm itself. Algorithms are often implemented as functions; the steps of the algorithm become the code in function. You can approach this design in a similar way that you would approach top-down program design, looking at the overall challenge and breaking it into simpler parts.

Every time you make a recursive call—that is, every time you decide the best move—you'll do for one more level of recursion than you were previously. And if you reach your maximum, you'll stop making recursive calls. Once you've reached the maximum level of recursion, you just evaluate a board to get a score.

Here's your board evaluation:
- If the game is tied, then you'll give player1 a negative score—the more negative, the more player 1 is winning.
- If player 2 seeks to be winning, you'll give a positive score: the larger the score, the more player 2 has an advantage.
- If one player or the other actually wins, you should have a really negative or really positive score.

The idea here is to think ahead as many moves as possible. You could generate all possible moves at once, but that might become really expensive in terms of memory you need. Instead, you'll need to search the board as one of two: Either you don't want to look ahead many moves and just to see how good the current board position is, or you want to choose what moves are among them.

When you are going to evaluate several moves via recursion, it's not enough to know which move is the next to—you also need to know how good that move is. So, you'll return not just the best move, but also the score for that move; in others, your return information has increased. You'll use that score to call the moves and determine which one is best.

In the event that you're willing to look forward a little more, then you'll need to start this process again from the opponent's point of view; that is, you want to go through this algorithm but now starting from the opponent's moves.

The input to your algorithm is the current board state. The output of the algorithm will be a score for that board. If the board indicates that player 1 wins—that is, if player gets 4 of her pieces in a row, a called connect4—then you return a small number, like -1000. If the board indicates that player 2 has won, then you return a very large number, like 1000. If the game has ended in tie, then you evaluate the board as 0.
