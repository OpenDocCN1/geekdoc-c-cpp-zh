For-oriented design, your first thought should be consider what the objects of interest are. From there, you can figure out what classes you need for those objects.

 a very general sense, you'll probably need
>> some sort of class for a game in general keep track of whose it is, and so on;
>> some game class to hold the current state of the board; and
>> some way to describe what a move will be, where the one all the games will have in common is 2 players taking turns.

Those are all abstract, so they're likely to end up as abstract classes. You'll also need some concrete versions of those classes: the specific classes for Connect 4 and the specific moves for Connect 4 and Reversi. These since sound like subclasses.

Once you've thought about classes, you can start to look for hierarchies. In this case, there are a few obvious relationships. The abstract gameboard be a parent to the concrete Connect 4 and Reversi game. Likewise, the abstract gamemove should be a parent to a Connect 4 and Reversi move.

Once you have a general idea of the hierarchy, you need to think about exactly the member variables and functions each class should have, as which should be public, protected, and private. For your abstract classes, you'll need to think about virtual functions.

To keep track of what you're doing, you can use Unified Modeling Language (UML), which is a notation system developed by object-oriented programmers for creating blueprints in the software industry.

In UML, when you describe a class, you use a rectangle with the class name in a box at the top, followed by 2 other boxes: one giving the member variables, or attributes, and the box at the bottom giving the member functions, also called methods for operations.

| Class name |
|---|---n| VARIABLES: | attributes methods |
| FUNCTIONS: | operations |

There are commonly used abbreviations for designating elements of a class are public (+), private (-), or protected (#).

Italics are used for classes that are abstract and for virtual functions.

At the start and think about what the game class. Overall, a game needs to have a gameboard, which is another class, to keep track of the current state of the board, called board.

A gameboard is going to be an abstract class, which means you'll have to have concrete gameboard classes, such as a Connect 4 or Reversi gameboard.

To store an abstract gameboard in the game class, you'll use a pointer to a gameboard.

> Remember that it's OK to have a pointer to the parent type, even if the object is of the child types.

The gameboard is not something that you want things inside the game meeting directly; you want to make sure only valid moves are made, that players don't make 2 moves in a row, and so on. Because you want to modify any actions that a program running a game can take, this should be a private variable of the game class—that only the game can access directly, and others (whether a player or computer) can only access through game classes.
