The errors that you encounter fall into one of 3 types: syntax errors, logic errors, and runtime errors.

+   A syntax error occurs where you've written something that is not accurate code. These are usually the easiest to find, fix, because the compiler will tell you you have a mistake in your code and will give you a particular line of code where it detected the error.

+   B A logic error occurs when there was something wrong with the thought that went into the code, and that reflected in a mistake. These are some of the toughest to find.

+   C A runtime error is when something unexpected exceptions causes your program to be a big help.

Programming is full of situations, besides a user entering data of the wrong type, where you might run into things that you don't expect.

One common situation is with files: You might try to open a file for reading but the file isn't there. Maybe the name got mistyped or the file is in a different directory. For whatever reason, it's not what you expected, and you cannot open it.

For example, Program 14_4 allows a user for a file name, reads the first element (integer) from the file, and if you run into your program and type the name of a nonexistent file, you might probably get some of nonsensical printed out. Since the file did not exist, it could not be opened and so whatever have been read and then printed out will be.

Often, the source of the error could be due to circumstances outside the programmer's direct control. Perhaps you asked a user to enter a number and he or she typed a word instead of a number. The program will either give a wrong answer or crash.

To avoid this, you could make a much more complicated process for reading a string and then check to see if the string is a positive integer—or so, convert it to an integer, and so on. But doing all of this would be painful!

Trying to access where you might expect might not be what you get. For example, maybe you read in a week's data but user only included the work and not the weekend. What would happen if you tried to access the 6th element?

## USING EXCEPTIONS

The solution to dealing with unexpected, "exceptional" cases is through the use of exceptions. Here's how they work.

When you throw an exception, the function immediately returns. The exception is being "thrown" to the function that called the routine.

```
try {
    // Code to try
}
catch (exception&e) {
    // Code to handle exceptions
}
// Additional code
```

First, you have a function called from somewhere in a program. This call should occur within what's referred to as a try block.

Back in the calling function, the exception is then caught. There is separate code that is executed to handle the exception that occurred.

Somewhere within the function that is called, you encounter an error. This is where you realize some exception has occurred—maybe you've tried to access the end of a vector or what you have entered instead of a number.

If you're going to deal with exceptions, you need 2 parts of code. First, you have a try block, which consists of the curly braces. Whatever code is inside the curly braces is what you will "try" to execute.

In many cases, you're going to be throwing your own exceptions. But there are a few places in standard C++ where exceptions are already thrown.

That function generates an exception, which is basically a special note that something went wrong. In C++, the term for this idea is "throwing". In any programming languages, you might hear this calling an exception.

Let's see how to handle exceptions in 2 cases.

The fstream library supports the ability to throw an exception in the case of trying to read from a nonexistent file.

If the code executes and no exception is thrown, then you go on to whatever additional code follows. On the other hand, there could have been an exception raised.

There is a special command to have run for the fstream: the first member activates the ability for fstreams to throw exceptions. The exceptions function take in input the exceptions that are being activated.

```
my_function
try {
    my_function()
} catch (...) {
}
```

Immediately the try block will be one or more catch blocks—used to "catch" any exception thrown when executing the code in the try block, including in any functions that were called from there. The catch block will take in a parameter, which is going to be the exception that is returned.

![](img/bdf1aaea7e08f6cbf15b0a740771ecdc_165_0.png)

In this case, the exception you care about is a predefined exception called failbit: if the file does not open correctly, then a fail exception is thrown. For this code, because the fstream is named infile, the command you'll write is infile.exceptions(fstream::failbit) (9).

Then, you have a try block (d), where the code you want to run is put inside the catch braces. In this case, the code you're trying is opening the file.

Following that is a catch block (e), which takes in one parameter—reference to an exception, given the name category in this case.

Inside the catch block is the code you want to run if the exception is caught. In this case, you print out a message that there was an opening file. Then, you return a nonzero value. Because you're in the main function, return means that the program ends, and ended with a nonzero value, it indicates that there was an error along the way.

If you run this code and the file does not exist, the open function you tried will generate an exception. And when this exception is caught, you print out Error opening file, and the program ends.

If there was no exception, then you would have skipped over the catch block and gone on to the remaining code in the main function.

```
// Program 14_6
// Exception example - reading a nonexistent file, now with
try/catch
#include <iostream>
#include <fstream>
using namespace std;

int main() {
    fstream infile;
    infile.exceptions(fstream::failbit);
    try {
        infile.open("something.dat", fstream::in);
    }
    catch (exception& category) {
        cout << "Error opening file" << endl;
        return 1;
    }
    int& a;
    infile >> a;
    cout << "Read in: " << a << endl;
}
```

> If you approach debugging steadily and systematically, you will find your errors.

Imagine you have some function, named process_boxes (7), that takes in an integer parameter. It makes no sense if that function is called with no boxes, so in that case, you might want to throw an exception.
