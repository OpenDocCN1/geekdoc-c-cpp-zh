This is a modified version that, in fact, demonstrate polymorphism. Notice that this code is the same as the previous code, except for a few changes:

- In the base class, car, you now have the word virtual in front of your functions that you want to override in the base class (r). The virtual is needed to say "this will be a polymorphic function."
- You have defined a new function, called print_car. This function takes a car parameter—reference—and calls print_info for that car (s).
- The main code is also modified so that you are calling the print_car, passing in a car and an SC300 rather than calling the member functions for each (2, G3).

When you run this code, you indeed see that the specific versions of print_info are called. In words, when you call print_car with a car object, it will end calling the print_info command in the car. And with an SC300 object, it will end calling the print_info command in the SC300 class. This is what you get from polymorphism: the ability to define a different version of a function for different classes. When you call print_car, you get the most descriptive output you.

If you remove the virtual from front of the declarations in the base class, when you run the code, the output when you pass the SC300 object print_info for the car—not the SC300 class! You know this you're not seeing the printout of the various options, and the price is only the base price, not the price with options.

It's a different situation than previously in Program 20_4, when you were calling print_info directly on an object (q). There, you knew that you were calling the function from an SC300 object, so you'd first look up the SC300 definition to see if it is, like what you used, and only if Program 20_4, was not defined unless you looked at the parent to see if it had print_info, and so on.

Note that subclasses don't have to redefine the function if it's virtual; you have the option of redoing if it want to.

No longer have a polymorphic function. Instead, calling the function, print_car says "I have a car object, so I will call the car object's print_info." Without the virtual statement, it won't be able to see if this function has been overridden by a subclass.

Let's look at one other variation, with the virtual base on these functions that they're indeed polymorphic and so that subclasses can redefine the function if they choose.

In this case, you are in a function where you have a car object (t). The compiler is going to look at the car class and find a print_info function defined and use that. It's not going to look further to see if function has been overridden because it was not declared virtual function.

Again, the output shows that the print_info function that called is for the car class, not the for the SC300 class. But it looked like you declared this as a virtual.

On the other hand, when you pass by value, you still have an SC300 defined in the main program that you call print_car, but now it is a parameter that is passed by value.

In the preceding case, you create an SC300 object in your main code and pass this to the print_car function using a pass by reference. When this function is called, the memory for the parameter has a reference stored. This is basically a pointer, and it has a reference to the object that was passed. No data is copied. Because the SC300 class is derived from the car class, it is OK to pass in the SC300 as a reference.

When the function is called, in this case, there is space aside in memory for a car object. Then, the values from the argument are copied into the car object that has been allocated. In this case, the base_price and model_name, which were defined in the car class, but not the various Booleans which packages were selected.

So, when you call print_info within the print_car function, you go to that reference and call print_info on. Because the thing it is referring to the SC300 object that was created before, it will try to call the print_info command for the SC300 class. Because print_info was declared to be virtual, it will look for the most specific version of that function, which is defined in the SC300 class.

Thus, the thing that's sitting in memory is a car-not an SC300; It has no memory of originally coming from SC300; all it knows is it's a car. As a result, when you call print_info on that object, it's going to use the print_info command defined for the car class, not the one defined for SC300 class.

# // PURE VIRTUAL FUNCTIONS

It's possible for the base class to declare a virtual function yet to provide no definition. This is known as a pure virtual function, and it has some major implications for the class itself.

In this code, you are providing classes that can be used to calculate shipping costs for a package. To keep things simple, the class will have no member variables and one member function, `shipping_cost`.

You have one base class, `shipping_company` (6), which is a class that the others inherit from. In the `shipping_company` class, you declare one member function, `shipping_cost` (8). Note that the shipping cost is declared virtual, as expected, and it has a return value, `float`, and takes in a `float` parameter. Notice that the parameter does not have a name declared, because you are not actually defining the function here. This is going to be a pure virtual function, and to designate that, instead of providing the function definition—instead, of body enclosed in curly braces—you use `=0;`.

A pure virtual function will have to be defined in the derived classes. In this case, you have 3 different specific shipping companies. Each of these will have its own version of the `shipping_cost` function.
