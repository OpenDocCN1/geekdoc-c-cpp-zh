And, as you'd expect from a hierarchy, can have more than one derived class from the same base class. For example, in addition to a `measuring_cup`, in Program 19_3, it's been defined as a subclass of `cup`, with one more member variable: Boolean whether it has a lid or not.

You're not confined to inheriting member variables; you inherit member functions.

Say your product class had a member function named `profit_per_unit`. It would be simple, returning the difference between the retail and wholesale prices.

Then, if you have an object of some derived type, like a `measuring_cup`, you can call it just like you would for the base class. In this example, you have a `measuring_cup` named `plastic_cup`, and you call `plastic_cup.profit_per_unit` to get the profit.

Inheritance only goes one way—from the parent to the child. A superclass does not have access to the member variables and functions of the subclasses, and sibling classes don't have access to each other's variables.

## // THE PROTECTED CATEGORY

Up until this point, the examples have had all of the member variables be public. But, as discussed when encapsulation was introduced, the idea of information hiding—not of allowing outsiders to access more information than they need—is important to creating good classes. It helps ensure that a class's variables are only modified in approved ways, so you declare member variables as private and some as public.

When it comes to inheritance, there's a third category that's between public and private: protected.

As before, things that public will get inherited by all of the descendants and public members of all those descendants. Any code can call member functions or access those member variables directly.

The member properties are accessible only to the class they are declared in, and to others. Not the descendants of a class can access those member properties that are considered private. So, although the descendants inherit these variables and functions—that is, they still allocate space for those member variables and can have values stored—they can't actually call the private functions or read the private variables defined in an ancestor.

This is the reason for the protected category. Protected member properties are accessible to the class they are declared in and to the descendants, but nothing outside of the class. In effect, this is like a private member property for everything in the inheritance tree.

Let's create a bank_account class that can be used to keep track of different bank accounts. You'll have a base class called bank_account and 2 derived classes, checking_account and savings_account.

The bank_account class is declared by any other class. It's not inheriting from anything.

Within the bank_account class will be 3 groups of member properties. First, you have private member properties, which in this case are the owner's name, address, and account number. Because these are private, that means the derived classes, checking_account and savings_account, will have those variables but won't be able to access them directly. The only way they'll be able to access these variables is indirectly, through a member inherited from bank_account. Other classes will bank_account not able to access them, either.

You also have a couple members declared protected. There is a protected variable: a double-precision floating-point number named balance. There's also a protected function: a set_account function that sets the account number and the balance.

Because the balance variable and the set_account function are protected, any subclasses you define will be able to access them; bank_account subclasses will be able to modify the balance directly and call the set_account function. But no other classes—and code outside of the bank_account subclasses—will be able to access protected variables or functions. No outside code can call set_account, and no outside code can look at or modify the balance.

Then, you have a few functions: One lets the account number and name changed, and the other prints out the account information. Because both of these are public, they can be called from anywhere. Any other code, from any class or function, can call either of the two public functions.

Now that your bank_account class is all set up, you can turn to subclasses. Suppose you have a checking_account and a savings_account class, each of which inherits from bank_account, as specified with the public bank_account designation.

First, let's look at a way to implement the checking_account, which has few public functions. One of them, begin_account, to indicate that a new account is starting. It calls set_account. Because begin_account is part of the checking_account class and the checking_account inherited from bank_account, it will call the set_account function that was a protected function of bank_account.

The checking_account has functions to deposit and withdraw money. Each of these refers to the protected balance variable that is inherited from bank_account. Again, because this inherits from bank_account, it can access the protected member properties.

All of this runs fine. Within any class, you are accessing only functions and variables that were either defined in that class or were public or protected properties from an ancestor. From outside of the class, you are only accessing public properties of the class.

But there are several things you would not be allowed to do. You could not access a private member of the class, and you could not access any private member function from outside the class.
