Therefore, we should copy all arguments that are expressions themselves (like vector_sum) to avoid stale references. In contrast, containers like vector shouldn't be copied since this would make the ET even slower than the classical operator. Our first idea was thus to distinguish between containers and pure expressions. The former will be referred as before and the latter copied. The advantage of this approach is that only the ET classes must be changed but not the operators returning ET objects. The disadvantage is that the distinction between containers and pure expressions requires explicit declarations in terms of type traits. In our case, these declarations actually didn't cause much extra work since most types were already explicitly categorized. Instead of categorizing a type as a vector, we declared it to be either a vector container or an expression whereas both of which behave like vectors.


This can still cause a stale reference. So, containers passed as rvalues should be copied as well. We can simplify this approach by copying all rvalues and referring all lvalues:

The motivation is that pure expression objects like vector_sum only appear as rvalues in a regular usage. Even in the unlikely scenario that somebody explicitly creates a vector_sum object and passes it to an expression, we wouldn’t encounter a stale reference.
