# Object-Oriented Programming with C++

In the procedure-oriented programming system, procedures are dissociated from data and are not part of it. Instead, they receive structure variables or their addresses and work upon them. The code design is centered around procedures. While this may sound obvious, the programming pattern has its drawbacks.

The drawback with this programming pattern is that the data is not secure. It can be manipulated by any procedure. Associated functions that were designed by the library programmer do not have the exclusive rights to work upon the data. They are not a part of the structure definition itself. Let us see why this is a problem.

Suppose the library programmer has defined a structure and its associated functions as described above. Further, in order to perfect his/her creation, he/she rigorously tested the associated functions by calling them from small applications. Despite his/her efforts, he/she can ensure that an application that uses the structure will be bug free. The application program might modify structure variables, not by the associated function she has created, but by some code inadvertently in the application itself. Compilers that implement the procedure-oriented programming system prevent unauthorized functions from accessing/manipulating structure variables.

Now, let us look at the situation from the programmer's point of view. Consider an application of 25,000 lines (common in the real programming world), in which variables of this structure have been used extensively. During testing, it is found that the date being represented by one of these variables has 29th February 1999! The faulty piece of code that is causing this bug can be anywhere in the program. Therefore, debugging will involve a visual inspection of the entire code (of 25000 lines!) and will be limited to the associated functions only.

The situation becomes especially grave if the execution of the code that is likely to corrupt the data is conditional. For example,

```
if(<some condition>n  d.m++; // d is a variable of date structure... d.m may
  //become 13!)
```

The condition under which the bug-infected code may arise during testing. While distributing his/her application, the application programmer cannot be sure that it will run successfully. Moreover, every new piece of code that accesses structure variables will have to be inspected and tested to ensure that it does not corrupt the members of the structure. After all, compilers that implement procedure-oriented programming systems do not prevent unauthorized functions from accessing/manipulating structure variables.

Let us think of a compiler that enables the library programmer to assign exclusive rights to the associated functions for accessing the data members of the corresponding structure. Here, our problem is solved. If a function is not one of the intended functions accesses the data members of a structure variable, a compile-time error will occur. To ensure a successful compile of his/her application, the application programmer will be forced to remove those statements that access data members of structure variables. Thus, the application that arises out of a successful compile will be the piece of code that is free of any unauthorized access to the data members of the structure variables therein. Consequently, if a runtime-time error occurs, attention can be focused on the associated library functions.

It is the lack of data security of procedure-oriented programming systems that led to object-oriented programming systems (OOPS). This new system of programming is the subject of our next discussion.
