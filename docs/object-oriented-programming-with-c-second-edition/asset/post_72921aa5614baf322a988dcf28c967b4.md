We can see, the name of the destructor is the same as the name of the class prefixed with a tilde sign. Moreover, the destructor does not return anything. The compiler defines the destructor in order to resolve the call to the destructor that it compulsorily places for the object going out of scope.

Destructors do not take any arguments. Therefore, they cannot be overloaded.
Why should we define our own destructor? We must remember that the destructor is also a member function. It is called for objects. Therefore, it can access the data members of the object for which it has been called.

Let us think of a relevant definition for the destructor of the class Distance. What would we like to do for us? What should it do to the data members of the object that is going out of scope? Should we set them to zero?

```cpp
Distance::~Distance()

    iches=0.0;
}
```

But what is the use? The destructor is anyway going out of scope immediately after the destructor executes.

But we must define the destructor for classes whose objects, during their lifetime, acquire resources that are outside the objects themselves. Let us take the example of the class String. We consider the following code block.

```cpp
{
    .
    .
    .
    String s1("abc");
    .
    .
    .
}
```

The memory was allocated to 's1' itself gets deallocated when this block finishes execution. But 's1.cStr' was pointing at a memory block that was dynamically allocated in the heap area. This memory block was outside the memory block occupied by 's1' itself. After 's1' gets destroyed, this memory block remains allocated as a locked up resource. The only pointer that pointing at ('s1.cStr') is no longer available. This is a memory leak. It should be prevented. We should deallocate the memory block at which the pointer any object of the class String is pointing exactly when the pointer goes out of scope. This means that we must call the delete operator for the pointer inside the class String and place this statement inside the destructor. We See Listing 4.13.

## 4.3 Philosophy of OOPS

Now, let us digress and appreciate the basic philosophy of OOPS. One of the aims in OOPS is to abolish the use of fundamental data types. Classes can contain huge amounts of functionality (methods) that free the application programmer from the worry of taking precautions against bugs.

The class String is one such type. By adding some relevant functions, we can conveniently use objects of the class String. Consider adding the following function to the class String.

```cpp
void String::addchar(char c); //function to add a character
//to the string
```

As its name suggests, this function will add a character to the string at which the pointer inside the invoking object points.

```cpp
String s1("abc");
```

As a result of this statement, the pointer inside 's1' points at a memory block of four bytes (last one containing NULL). Now, if we write

```cpp
s1.addchar('d'); //add a character to the string
```

the following things should happen:

- Another block of four bytes should be allocated.
- The string should be appended.
- s1.cStr should be made to point to this new block.
- The memory at which s1.cStr was pointing should be deallocated.

This is shown in Figure 4.5.

The formal argument of setString() is a const char *. The reasons for this have already been discussed under the section on parameterized constructor. When the constructor starts executing, cStr may or not be NULL (it may contain junk value). But if it is not NULL, does not mean that it is pointing at a allocated block of memory. When the setString() function starts executing, cStr is not NULL, then it is definitely pointing at a allocated block of memory. Statements to check this condition and deallocate the memory and nullify cStr and set 'len' to zero should be inserted at the beginning of the setString() function. Otherwise a memory leak will occur.

Defining the addChar() and setString() functions is like an exercise. Let us think of more relevant functions that can be added to the class String. There can be a function that will change the value of a character at a particular position in the string at which the pointer of the invoking object points. Moreover, there can be a function that reads the value from a particular position in the string at which the pointer of the invoking object points.

After we added all functions to the class String, we will get a new data type that will be safe, efficient, and convenient to use.

Suitably defined constructors and destructors have a vital role to play in the creation of such data types. They ensure that

- There are no memory leaks (the destructor frees unwanted memory).
- There are no run-time errors (no two calls to the destructor to free up the same block of memory).
- Data is never in an invalid state and domain constraints on the values of data members are never violated.
