When the statement executes, 'AObj' (the formal argument) whereas this pointer points to 'A2' (the invoking object). Similarly, the other statements where the object is created as a formal argument or returned from a function can also be explained.

But why does the compiler create the formal argument of the default copy constructor as a reference? And when the compiler defines a copy constructor in the expected way, then why should we define one on our own? Both questions are answered now.

First, let us find out which objects are passed by reference to the copy constructor. Suppose formal argument ('AObj') of the copy constructor is not a reference. Now, suppose the following statement executes.

```cpp
A2=A1;
```

The copy constructor will be called for 'A2' and 'A1' will be passed as a parameter to it. Then the copy constructor will be called for 'AObj' and 'A1' will be passed as a parameter to it. This is because 'AObj' is a non-reference formal argument of the copy constructor. Thus, an endless chain of calls to the copy constructor will be initiated. However, if the formal argument of the copy constructor is a reference, then no constructor (not even the copy constructor) will be called for it. This is because a reference to an object is not a separate object. No separate memory is allocated for it. Therefore, a call to a constructor is not embedded for it.

Now we come to a crucial question. Why should we define our copy constructor? After all, the default copy constructor (which is provided free of cost by the compiler) makes a pretty decent job. First, recollect the conditions we decided to implement for all objects of the class String. Suppose an object of the class String is created and at the same time equated to another object of the class. For example,

```cpp
String s1("abc\n");
String s2=s1; //copy constructor is called for s2 and s1
//is passed as a parameter to it
```

Since we have not defined the copy constructor for the class String, the compiler has done it for us. What does this default copy constructor do in the above case? It simply copies the values of 's1' to 's2'! This means the value of 's2.cstr' becomes equal to 's1.cstr'. Thus, both pointers point to the same place! This is a violation of our conditions. The behaviour of the default copy constructor is undesirable in this case. To overcome this problem of the default copy constructor, we must define our copy constructor.

From within the copy constructor of the class String, a separate memory must be first allocated dynamically in the heap. This memory must be equal in length to that of the string at which the pointer of the object passed as a parameter ('s1' in this case) points. The pointer of the invoking object ('s2' in this case) must then be made to point to this newly allocated memory. The value of 'len' of the invoking object should also be set appropriately. However, if the pointer in the object passed as a parameter is NULL, the value of the pointer and 'len' of the invoking object must be set to NULL and zero.

Accordingly, the prototype and the definition of the copy constructor of the class String appear in Listing 4.11.

Listing 4.11 A user-defined copy constructor

```cpp
/*Beginning of String.h*/
#include<iostream>
class String
{
    char * cStr;
    unsigned int len;
public:
    String(const String&); //our own copy constructor
    /* rest of the class String */
    explicit String(const char * const p = NULL);
    const char * getStr();
};
/*End of String.h*/

/*Beginning of String.cpp*/
#include"String.h"
#include<string.h>
String::String(const String& ss) //our own copy constructor
{
    if(ss.cStr==NULL) //if passed object's pointer is NULL
    {
        cStr=NULL;               // ... then nullify the invoking object's pointer too
        len=0;
    }
    else                          // /otherwise...
    {
        len=ss.len;
        cStr = new char[len+1];      //...dynamically allocate a separate memory block...and copy into it
        strcpy(cStr,ss.cStr);
    }
}
String::String(const char * const p)
{
    if(p==NULL)                   // /if default value passed...
    {
        cStr=NULL;                   //...nullify
        len=0;
    }
    else                          // /otherwise...
    {
        len=strlen(p);
        cStr=new char[len+1];      //...dynamically allocate a separate memory block...and copy into it
        strcpy(cStr,p);
    }
}
const char * String::getStr()
{
    return cStr;
}
/*End of String.cpp*/
```

## 4.2 Destructors

The destructor gets called for each object that is about to go of scope. It appears as a member function of class whether we define it or not. It has the same name as that of the class prefixed with a tilde sign. It does not take parameters. It does not return anything (not even void). The prototype of a destructor is

```cpp
~className();
```

The need for a function that guarantees deinitialization of member data and frees resources acquired by the object during its lifetime will be explained soon. Destructors fulfill this.

The compiler embeds a call to the destructor for every object when it is destroyed. We have one more look at the main() function of Listing 4.1.

```cpp
void main()
{
    A ai;
} //ai goes out of scope before the main() function terminates.
```

The compiler embeds a call to the destructor for 'ai1'. It embeds the following.

```cpp
A1~A1(); //destructor called not legal C code
```

The destructor will also be called for an object that has been created in the heap just before the delete operator is applied on the pointer pointing it.

```cpp
A * aptr;
aptr = new A; //object created constructor called
..
delete aptr; //object destroyed destructor called
```

```cpp
aptr->~A(); //destructor called for *aptr
delete aptr; //memory for *aptr released
```

Unlike its name, the destructor does not 'destroy' or deactivate an object that occupies. It is merely a member function that is called for each object before the object goes out of scope (destroyed).

As can be readily observed, the compiler embeds a call to the destructor for every object that is going out of scope. But we did not prototype and define the destructor inside the class. Then was the above call to the destructor resolved? The compiler prototypes and defines the destructor for us. But what statements the definition of such a destructor have? The answer is 'nothing'.
