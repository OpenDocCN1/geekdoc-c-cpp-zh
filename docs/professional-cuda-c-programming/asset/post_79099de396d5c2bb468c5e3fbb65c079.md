## cuFFT versus FFTW versus MKL

The FFTW library boasts excellent performance of single- and multi-dimensional FFTs on multi-core CPUs, claiming performance that is "typically superior to that of other publicly available FFT software, and is even competitive with vendor-tuned codes. Clearly, FFTW targets improved performance as a major goal, and therefore, is a good comparison point for cuFFT. The MKL library also supports FFTs.

NVIDIA's CUDA 5.0 report shows varying performance of FFTs depending on data size, from as low ~30 GFLOPS up to nearly 250 GFLOPS. At some point in the OpenACC parallel region may transition to parallelize work across gangs. In that case, the region enters gang-partitioned mode. In gang-partitioned mode, there is still only one active element and one active worker in each gang, but each vector element is executing a different piece of the parallel region. Hence, the work of this computational region is partitioned across gangs. In CUDA, gang-partitioned mode would be implemented as a single thread in each block processing a separate data point. For vector addition, a CUDA kernel executing in gang-partitioned mode would look like

```cpp
__global void kernel(int *n1, int *n2, int *out, int N) {
    if (threadIdx.x == 0) {
        int i;
        for (i = blockDim.x; i < N; i += gridDim.x) {
            out[i] = n1[i] + n2[i];
        }
    }
}
```

What about worker and vector parallelism? Well, when a single worker is active per gang it is called worker-single mode. When a vector element is active per worker it is called vector-single mode. Both gang-redundant and gang-partitioned modes are therefore worker-single and vector-single modes. In worker-partitioned mode, the work of a parallel region is divided among multiple gangs but also workers. Using all workers in gangs provides G × W-way parallelism. In CUDA, worker-partitioned mode would be implemented by the first thread in each gang:

```cpp
__global void kernel(int *n1, int *n2, int *out, int N) {
    if (threadIdx.x == 0) {
        int workerId = threadIdx.x / warpSize;
        int workersPerBlock = blockDim.x / warpSize;
        int i;
        for (i = blockDim.x * workersPerBlock + workerId; i < N; i += gridDim.x * workersPerBlock) {
            out[i] = n1[i] + n2[i];
        }
    }
}
```

In vector-partitioned mode, the work is divided among gangs, workers, and vector elements, providing G × W × V-way parallelism. This is the mode most similar to what you have been writing. When using OpenACC, compiler directives are inserted by the programmer to indicate regions of code that can be executed in parallel. Compiler directives also indicate the type of parallelism to use. A compiler directive is a single line of source code that, in C/C++, starts with #pragma. OpenACC directives are uniquely identified with the acc keyword. Compiler directives are unique in that they are part of the source code of a program which may may not affect the executable generated by a compiler. If a compiler does not recognize a certain type of #pragma, it will ignore it and compile the application as if the #pragma was not there. If you run any of the examples in this section, you will need an OpenACC-enabled compiler. Currently, PGI, Cray, and HPC compilers support OpenACC directives. The examples in this chapter will use the PGI compiler, but all source code should work across compilers.

OpenACC-enabled compilers interpret the OpenACC directives of a program and perform auto-analysis of the source code to auto-generate accelerator code. As a result, it is possible to automatically execute on the GPU by adding a few lines of directives. For example, consider the following OpenACC vector addition:

```
#pragma acc kernels
for (i = 0; i < N; i++) {
  C[i] = A[i] + B[i];
}
```

The #pragma acc kernels directive marks the following sequential block eligible for execution on an Accelerator (for example, a GPU). If the compiler building this source code is OpenACC-enabled, it analyzes the loop, determines a strategy for parallelizing gangs, workers, and vectors, and then automatically generates the memory copies, kernel launches, and kernel source code to execute the loop in parallel on a GPU. In contrast, hardware (without CUDA unified memory) would require:
1) converting the body of the loop into a CUDA global kernel,
2) explicitly allocating memory with cudaMalloc,
3) copying data to the device with cudaMemcpy,
4) performing a kernel launch, and
5) copying data back to the host. OpenACC, all of this is accomplished with a single #pragma.

In addition to compiler directives, OpenACC also offers a number of library functions. These functions may implement identical functionality, complementarity, or unique functionality compared to the OpenACC compiler directives.

## Using OpenACC Compute Directives

In OpenACC, compute directives are used to communicate to the compiler how a block of code should be parallelized. There are two compute directives: #pragma acc kernels and #pragma acc parallel.

## Using the kernels Directive

#pragma acc kernels takes a more automated and compiler-driven approach than #pragma acc parallel. When the kernels directive is applied to a block of code, the compiler automatically analyzes that block for parallelizable loops. When they are found, the compiler can schedule parallel execution using any configuration of gangs, workers, and vector width on each parallel loop. In other words, the compiler determines when to use gpu-redundant, gang-partitioned mode, worker-partitioned mode, etc. In CUDA, the compiler searches the block of code decorated by the kernels for parallel loops that can be executed in CUDA kernels. Any code within a kernels block that is not parallelized is still executed, but not in parallel.

As a simple example, consider the code in simple-kernels.c available from Wix.com. The core logic is included in the following snippet:

```cpp
#pragma acc kernels
{
    for (i = 0; i < N; i++) {
        C[i] = A[i] + B[i];
    }
    for (i = 0; i < N; i++) {
        D[i] = C[i] * A[i];
    }
}
```

This kernels block contains two loops that can be parallelized. If you have a PGI compiler, this example can be compiled with:

```bash
$ pgcc -acc simple-kernels.c -o simple-kernels
```

Adding the -acc flag enables PGI compiler support for OpenACC, allowing it to recognize any #pragma directives. It is also strongly recommended that you add the -Minofacc flag to the compiler to gain insight into how auto-parallelization is performed.
