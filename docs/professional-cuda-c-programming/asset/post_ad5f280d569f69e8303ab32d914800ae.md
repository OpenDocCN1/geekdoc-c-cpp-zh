
Connecting these values to warp or thread counts depends on the application. Suppose each thread moves one float (4 bytes) from global memory to the SM for computation, you require 18,500 threads or 579 KB to hide all latency on Fermi GPUs:

```
74 KB ÷ 4 bytes/thread = 18,500 threads
```

```
18,500 + 32 threads/warp = 579 warps
```

The Fermi architecture has 16 SMs. Therefore, you require 579 warps + 16 SMs = 36 warps per SM to hide all latency. If each thread performed more than one 4-byte load, fewer threads would be required to hide the memory latency.

Much like instruction latency, you can increase the available parallelism by creating more independent memory operations within each thread/warp, or creating more concurrently active threads/warps.

Latency hiding depends on the number of active warps per SM, which is implicitly determined by the execution configuration and resource constraints (registers and shared memory used in a kernel). Choosing an optimal configuration is a matter of striking a balance between latency hiding and resource utility. You will examine this issue in detail in the next section.

## EXPOSING PARALLELISM

Because the GPU partitions resources among threads, switching between concurrent warps has very little overhead (on the order of one or two cycles) as the required state is already available on-chip. If there are sufficient active warps, you can keep the GPU busy in every pipeline stage every cycle. In this situation, the latency of one warp is hidden by the execution of other warps. Therefore, exposing sufficient parallelism to SMs is beneficial to performance.

A simple formula for calculating the required parallelism is to multiply the number of cores per SM by the latency of one arithmetic instruction on SM. For example, Fermi has 32 single-precision floating-point pipeline lanes and the latency of one arithmetic instruction is 20 cycles, so at minimum 32 x 20 = 640 threads per SM are required to keep your device busy. However, this is a lower bound.

## Occupancy

Instructions are executed sequentially within each CUDA core. When one warp stalls, the SM switches to executing other eligible warps. Ideally, you want to have enough warps to keep the cores of the device occupied. Occupancy is the ratio of active warps to maximum number of warps, per SM.

```
occupancy = \frac{active warps}{maximum warps}
```

You can check the maximum warps per SM for your device using the following function:

```
cudaError_t cudaGetDeviceProperties(struct cudaDeviceProp *prop, int device);
```

Various statistics from your device are returned in the cudaDeviceProp struct. The maximum number of threads per SM is returned in the following variable:

```
maxThreadsPerMultiProcessor
```

You can derive the maximum warps by dividing maxThreadsPerMultiProcessor by 32. Listing 3-2 shows you how to use cudaDeviceProperties to obtain GPU configuration information.

## LISTING 3-2: Simple device property query (simpleDeviceQuery)

```cpp
#include <stdio.h>
#include <cuda_runtime.h>

    int iDev = 0;
    cudaDeviceProp iProp;
    cudaDeviceProperties(&iProp, iDev);

    printf("Device %d: %s\n", iDev, iProp.name);
    printf("Number of multiprocessors: %d\n", iProp.multiiprocessorCount);
    printf("Total amount of constant memory: %.4f KB\n", iProp.totalConstantMemory/1024.0);
    printf("Total amount of shared memory per block: %.4f KB\n", iProp.sharedMemPerBlock/1024.0);

    printf("Maximum number of warps per multiprocessor: %d\n", iProp.maxThreadsPerMultiProcessor/32);

    return EXIT_SUCCESS;
}
```

There are several sections in the Occupancy Calculator. First, you must provide information about your GPU's capacity and your kernel's resource usage.

The registers per thread and shared memory per block resource usage can be obtained from nvcc with the following flag:

```
--ptxas-options=-v
```

Once this data has been entered, the occupancy of your kernel is then shown in the GPU occupancy Data section. The section provides you with the necessary information to adjust your execution configuration and resource usage.

The number of registers used by a kernel can have a significant impact on the number of resident warps. Register usage can be manually controlled using the following nvcc flag:

```
-maxregcount=NUM
```

The option -maxregcount tells the compiler to use no more NUM registers per thread. You can use the number of registers recommended by the Occupancy Calculator in conjunction with this compiler flag to potentially improve the performance of your application.

To enhance occupancy, you may also need to resize the block configuration or re-adjust resource usage to permit more simultaneously active warps and improve utilization of compute resources. Manipulating thread blocks to extreme extent can restrict resource utilization:

- Small thread blocks: Too few threads per block leads to hardware limits on the number of warps per SM to be reached before all resources are fully utilized.
- Large thread blocks: Too many threads per block leads to fewer hardware resources available to each thread.

| GUIDELINES FOR GRID AND BLOCK SIZE |
| Using these guidelines will help your application scale on current and future devices:
| Keep the number of threads per block a multiple of warp size (32).
| Avoid small block sizes: Start with at least 128 or 256 threads per block.
| Adjust block size up or down according to kernel resource requirements.
| Keep the number of blocks much greater than the number of SMs to expose sufficient parallelism to your device.
| Conduct experiments to discover the best execution configuration and resource usage. |
