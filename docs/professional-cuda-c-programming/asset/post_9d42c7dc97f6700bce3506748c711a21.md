# Combining OpenACC and the CUDA Libraries

While CUDA and OpenACC are separate programming models, they can be used in the same application. Doing so requires changes to how the application is compiled. The deviceptr class must be used to share data between CUDA and OpenACC. This section will demonstrate a single application that uses CUDA libraries and OpenACC together in a single source file. The example application can be downloaded from Wrox.com in cuda-openacc.cu.

cuda-openacc.cu can be split into the following steps:

- 1. Matrices are allocated on the device using cudaMalloc and handles are created for both cuRAND and cuBLAS libraries using curandCreateGenerator and cublasCreate.
- 2. The input matrices in device memory are filled with random data using the cuRAND library’s curandGenerateUniform function.
- 3. Using OpenACC directives, a matrix-matrix multiply is performed in parallel on the GPU.
- 4. cublasSasum is used to calculate the sum of all elements in the output matrix by summing each row, and across rows.
- 5. Device memory is freed using cudaFree.

To build cuda-openacc.cu with the PGI OpenACC compiler, use the following command:

```
$ pgcc -acc openacc.cu -o cuda-openacc -Minfo=accel \
-L$CUDA_HOME/lib64 -lcurand -lcublas -lcudart
```

Note that here C++ compiler pgcc is used for compatibility with the CUDA libraries. The same argument is retained to enable OpenACC support, and -Minfo=accel is used to display diagnostic information on the parallelization of the OpenACC computational regions. Additionally, the CUDA library path is added to the path of the compiler so that the definitions of cuRAND, cuBLAS, and CUDA runtime functions can be found. The output of this command is as follows:

```
main:
70, Accelerator kernel generated
70, #pragma accel loop gang blockIdx.x */ /
72, #pragma accel loop vector(32), worker(4) /* threadIdx.x threadIdx.
70, Generating Tesla code
72, Loop is parallelizable
74, Loop is parallelizable
```

Note that a kernel is generated for the lines 70 and 72, with the outermost loop using gang parallelism and the innermost loop using worker and vector parallelism.

Most of this code could look similar to a full chapter on CUDA libraries and OpenACC. Only two items may look new.

First, the deviceptr is used with the parallel directive to explicitly allocate and manage its device memory, and then pass it directly to OpenACC computational regions. In this case, the cuda-openacc application allocates its device memory with cudaMalloc before using cuRAND. deviceptr can then be given to the OpenACC direct access to that same device memory, rather than having to transfer it back to the host using copying. deviceptr is a key component integration between OpenACC and other GPU programming frameworks.

The cuda-openacc.cu example makes use of cublasSetPointerMode to adjust host or device pointers to be used to return scalar results. In this case, cublasSasum returns a result as its last argument. Initially, cublasSetPointerMode is used to set the mode to CUBLAS_POINTER_MODE_DEVICE when summing the rows of the output matrix on the device. When performing the final sum across rows the mode is set to CUBLAS_POINTER_MODE_HOST and the return address is set to a variable in the host application's address space. You may recall a brief explanation about the cuSPARSE version of function, cusparsePointerMode, in the section titled "Important Topics in cuSPARSE."

# Summary of OpenACC

This section introduced you to the OpenACC execution and programming model. OpenACC is a flexible, easy-to-use high-performance programming model that complements CUDA and the CUDA libraries in many ways. Compared to the CUDA libraries, OpenACC is more flexible and allows you to write your own computational functions using the C language. Compared to CUDA, OpenACC is more convenient and requires less manual management of memory and computation than CUDA.

However, OpenACC is not without its downsides. A simple OpenACC implementation that ignores data movement often degrades performance due to unnecessary memory copies. OpenACC by default must be conservative about optimization strategies. With the async, copyin and copyout clauses OpenACC performance often lags behind hand-coded CUDA versions. Additionally, for many domains, OpenACC simply cannot beat the performance and usability of pre-written, expert-tuned CUDA libraries.

Despite these drawbacks, the balance of OpenACC across performance, usability, and customizability makes it an attractive programming model to complement CUDA for rapid development of high-performance GPU applications.

# SUMMARY

This chapter prepared you to make use of cuSPARSE, cuBLAS, cuFFT, cuRAND, and OpenACC to accelerate your application and development process.

The CUDA libraries are powerful in their simplicity, usability, portability, and performance. They were deliberately designed to benefit domain experts with past experience in the fields for which they are most useful. Applications that do not require a large amount of customization can use of these libraries and their component functions as basic building blocks of GPU-accelerated applications.

More importantly, the focus on the general workflow, abstract concepts, and porting process shared among these libraries prepared you to move beyond the scope of this chapter and explore more advanced concepts in these libraries as well as entirely new CUDA libraries. Although the libraries specifically covered in this chapter were selected because of their applicability to a wide range of cases and applications, this chapter could only skim the surface of CUDA library functionality.

On the other hand, OpenACC offers you more control over GPU execution than CUDA libraries while eliminating the more mundane tasks of GPU programming. In OpenACC, many of the same operations supported by the CUDA API can be performed by using simple compiler directives that guide automatic parallelization. In fact, most of the performance lessons taught in this book apply equally to CUDA and OpenACC. Additionally, you can write your own custom GPU kernels in a more intuitive format that is similar to sequential host code. OpenACC reduces complexity relative to CUDA and increases flexibility relative to CUDA libraries.

Overall, this chapter introduced frameworks on top of CUDA that offer a more abstract view of hardware and enable you to get more performance less less. If your application falls inside a domain covered by a CUDA library, the expert-implemented kernels and compatible APIs lead to better performance for less development effort.
