
```
kernel_3<<<grid, block, 0, streams[i]>>>();
kernel_4<<<grid, block, 0, streams[i]>>>();
}
```

The execution configuration for each kernel is launched as a single thread in a single block order to ensure sufficient GPU resources to run all kernels concurrently. Because each kernel launch is asynchronous with respect to the host, you can dispatch multiple kernels using a single host thread at approximately the same time.

To measure elapsed time in this example, two events are also created:

```
cudaEvent_t start, stop;
cudaEventCreate(&start);
cudaEventCreate(&stop);
```

The start event is recorded in the default stream before the loop that launches all kernels. The stop event is recorded in the default stream after all kernels have launched.

```
cudaEventRecord(start);
for (int i = 0; i < n_streams; i++) {
}
cudaEventRecord(stop);
```

After synchronizing on the stop event, elapsed time can be calculated:

```
cudaEventSynchronize(stop)
cudaEventElapsedTime(&elapsed_time, start, stop);
```

## False Dependencies on Fermi GPUs

To demonstrate false dependencies, you can run the code on a Fermi device. The output of simpleHyperQ on a Tesla M2090 is:

```
$ ./simpleHyperQ
> Using Device 0: Tesla M2090 with num_streams=4
> GPU does not support HyperQ
> CUDA kernel will have limited concurrency
> Compute Capability 2.0 hardware with 16 multi-processors
Measured time for parallel execution = 0.342s
```

simpleHyperQ informs you that the Fermi device does not support Hyper-Q, and that the kernel will run with limited concurrency as a result.

Figure 6-6 shows the timeline for the application as Figure 6-5, but run cannot start simultaneously because there is a false dependency between streams on the Fermi device, which is caused by the shared work queue. When is stream i+1 able to start its first task at the same time as stream i starts its last task? Since there are different streams, there are no dependencies between them. When the last task of stream i is launched, the CUDA runtime schedules the next task in the work queue, which is the first task of stream i+1. Because the first task of each stream is not dependent on any earlier tasks and there are available SMs, it can start immediately. The second task of stream i+1 is scheduled, and its dependency on the first task prevents it from executing task execution to block again.

This false dependency is caused by the order in which kernels are dispatched from the host. This application uses the depth-first approach, launching the full set of operations for a stream before starting on the next stream. The task order in the work queue that results from the depth-first approach is illustrated in Figure 6-7. As all streams are multiplexed into a single hardware work queue, the preceding streams block successive streams.

![](img/506ba3a4c9f4512233692f3f20de1f3a_309_0.png)

FIGURE 6-6

To avoid dependencies on Fermi GPUs, you can dispatch job with breadth first in a breadth-first approach:

```
// dispatch job with breadth first way
for (int i = 0; i < n_streams; i++)
kernel_1<<<grid, block, 0, streams[i]>>>();
for (int i = 0; i < n_streams; i++)
kernel_2<<<grid, block, 0, streams[i]>>>();
for (int i = 0; i < n_streams; i++)
kernel_3<<<grid, block, 0, streams[i]>>>();
for (int i = 0; i < n_streams; i++)
kernel_4<<<grid, block, 0, streams[i]>>>();
```

Issue order from host: depth-first

![](img/506ba3a4c9f4512233692f3f20de1f3a_309_1.png)

FIGURE 6-7

Only the three stream edges are independent.

Using breadth-first ordering ensures that adjacent tasks in the work queue are from different streams (shown in Figure 6-8). Therefore, there is no false dependency between any adjacent pairs of tasks and concurrent kernel execution is possible.

## Dispatching Operations with OpenMP

Previous examples dispatched asynchronous CUDA operations to multiple streams using a single host thread. The example in this section will demonstrate dispatching operations to multiple streams using multiple host threads, using one to manage each stream.

OpenMP is a CPU parallel programming model that uses compiler directives to identify parallel regions. Compilers that support OpenMP directives can use them as hints from the programmer as how to parallelize an application. With little effort, multi-core parallelism on the cost of which can be achieved.

You can use CUDA while leveraging OpenMP to improve not only portability and productivity, but also performance of the host code. Instead of dispatching operations with a loop as you did in the simpleHyperq, you can dispatch operations to different streams, as follows:

```
omp_set_threads(n_streams);
#pragma omp parallel
{
    int i = omp_get_thread_num();
    kernel_1<<<grid, block, 0, streams[i]>>>();
    kernel_2<<<grid, block, 0, streams[i]>>>();
    kernel_3<<<grid, block, 0, streams[i]>>>();
    kernel_4<<<grid, block, 0, streams[i]>>>();
}
```

The OpenMP function omp_set_threads is used to specify the CPU cores to be used in OpenMP regions. The compiler directive #pragma omp parallel marks the code between the curly braces as a parallel section. When compiled by a compiler with OpenMP support, the marked section will be run by multiple threads. The omp_get_thread_num function returns a unique ID for each thread, and is used as an index into the streams array to create one-to-one mapping between OpenMP threads and CUDA streams.

Download the simpleHyperqmp from wrox.com. Compile with nvcc, being sure to use the -Xcompiler option to pass flags to the host compiler that enable OpenMP support:

> grid 1 block 1

When dispatching CUDA operations in parallel with OpenMP? In general, if there is additional parallel-work to be completed, or after kernel execution it can be included in the same OpenMP parallel region and overlapped across streams and threads. Doing so makes it apparent that the work performed in each OpenMP thread and the CUDA operations launched from the same thread are related, and makes the code simpler to write optimal performance.

# Adjusting Behavior Using Environment Variables

GPUs that support Hyper-Q maintain multiple hardware work queues between the host and each GPU to eliminate bottlenecks. The maximum number of hardware work queues supported by a Kepler device is limited to eight. However, each connection requires additional memory and resources, setting the default limit to 8 reduce resource consumption for applications that do not require the full 32 work queues. You can use the CUDA_DEVICE_MAX_CONNECTIONS environment variable to adjust the number of concurrent hardware connections, to 32, for a Kepler device.

There are several ways to set this environment variable. In Linux, it can be set using the following commands depending on your shell. For Bash or Bourne Shell:

```
export CUDA_DEVICE_MAX_CONNECTIONS=32
```
