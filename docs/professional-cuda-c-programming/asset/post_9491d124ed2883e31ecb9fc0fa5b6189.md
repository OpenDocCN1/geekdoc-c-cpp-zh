
From 8-6, you can therefore find the values and column indices of row 0 in *M* at offset 0 in *V* and with length 1-0=1. The same process can be applied to row 1 and 2. The total number of non-zero values in *M* can also be retrieved from the last element of *R*.

As a result, CSR is able to store sparse matrices with multiple non-zero entries per row in much less space than Coordinate format. The full CSR representation of the example matrix M is shown in Figure 8-7.

Transferring a CSR-formatted sparse matrix to the GPU for use by a cuSPARSE function is straightforward. First, assume that you already have a CSR-formatted sparse matrix on the host defined by the following arrays:

```
float *h_csrVals;
int   *h_csrCols;
int   *h_csrRows;
```

where *h_csrVals* stores the non-zero values of the sparse matrix, *h_csrCols* stores the column index for each value, and *h_csrRows* stores the row offsets into *h_csrVals* and *h_csrCols*. Then, you simply need to allocate device memory for each array and transfer it to the GPU:

```
float *d_csrVals;
int   *d_csrCols;
int   *d_csrRows;
```

```
cudaMalloc((void **)&d_csrVals, n_vals * sizeof(float));
cudaMalloc((void **)&d_csrCols, n_vals * sizeof(int));
cudaMalloc((void **)&d_csrRows, (n_rows + 1) * sizeof(int));

cudaMemcpy(d_csrVals, h_csrVals, n_vals * sizeof(float), cudaMemHostToDevice);
cudaMemcpy(d_csrCols, h_csrCols, n_vals * sizeof(int), cudaMemHostToDevice);
cudaMemcpy(d_csrRows, h_csrRows, (n_rows + 1) * sizeof(int), cudaMemHostToDevice);
```

## cuSPARSE Storage Formats Summary

Each of the storage formats described in this section is supported by cuSPARSE, and each offers different advantages and disadvantages depending on the characteristics of the data set being processed. A full description of the cuSPARSE data formats is available in Section 3 of the cuSPARSE User Guide. Table 8-3 lists all the currently supported data formats and the optimal use case for each.

## TABLE 8-3: Sparse Matrix Storage Formats

| MATRIX DATA FORMAT | OPTIMAL USE CASE |
|---|---|
| Dense | Dense input data with very few non-zero entries. A dense data format may result in better access locality in the case of dense input data. |
| Coordinate (COO) | A simple and general sparse matrix format, which will represent matrices more efficiently in terms of space than a dense data format, so long as less than one-third of the input matrix is non-zero. |
| Compressed Sparse Row (CSR) | Rather than keeping a single entry for every non-zero value to store its row coordinate, CSR keeps a single entry for every row as offset to that row's and column data. CSR, therefore, is the space efficient relative to COO when row contains more than one non-zero entry. However, it does not allow O(1) lookup of a given row value. |
| Compressed Sparse Column (CSC) | CSC is the same as CSR except in two ways. The first values of the input matrix are stored in column-order. Second, the column coordinates are compressed rather than the row coordinates. CSC would be more efficient than CSR for input data with dense columns |
| Ellpack (ELL) | ELL works by compacting every row in matrix down to its non-zero entries. To retain column information for each value, a separate matrix stores coordinates for each value.mers do not have direct access to ELL matrices, but they are used in HYB-formatted matrices. |
| Hybrid (HYB) | HYB-formatted matrix stores a regular partition of the matrix in ELL and an irregular partition in COO. This hybrid formatting scheme serves to optimize access patterns on the GPU for matrices that have partitions characterized by different sparsity |
| Block Sparse Row (BSR) | BSR uses the same algorithm as CSR, but rather than storing scalar types as values, it supports storing two-dimensional block of scalar values. The BSR format (and very similar BSR format) optimizes subdivision of the matrix between multiple CUDA threads. |
| Extended BSR (BSRX) | BSRX is identical to BSR but uses a slightly different technique for marking the locations of two-dimensional blocks in memory. |

## Formatting Conversion with cuSPARSE

You might recall from the common workflow that there are two stages to converting from the application's native data format to library-supported format and back. These steps are primarily relevant when development effort to convert application to cuSPARSE-supported format is too high. For example, many legacy applications might simply use dense formats. However, performing matrix-vector or matrix-matrix operations in cuSPARSE requires that the inputs and outputs in CSR, BSR, or HYB formats. Note that converting between cuSPARSE data formats introduces overhead in computation to perform the conversion, and space to store the converted copy is logically the same data. Therefore, for optimal performance, you should avoid frequent conversions. Still, cuSPARSE provides a variety of format conversion functions. Table 8-4 lists the supported conversion functions. The top row indicates the format for your input (source) data. The left column indicates the format for your output (destination) data. ## Demonstrating cuSPARSE

This section will walk through an example cuSPARSE application demonstrating matrix-vector multiplication, format conversion, and other cuSPARSE features. You can follow along by downloading the sample code in cusparse.cu from NVIDIA.com. A snippet of the kernel logic is as follows:

```
// Create the cuSPARSE handle
cusparseCreate(&handle);

// Allocate device memory for vectors and the dense form of the matrix A
...

// Construct a descriptor of the matrix A
cusparseCreateMatDes(&desc);
cusparseSetMatType(desc, CUSPARSE_MATRIX_TYPE_GENERAL);
cusparseSetMatIndexBase(desc, desc, CUSPARSE_INDEX_BASE_ZERO);
```

```
// Transfer the input vectors and dense matrix A to the device

// Compute the number of non-zero elements in A
cusparseSnn(handle, SPARSE_DIRECTION_ROW, M, N, descr, dA,
dnnzPerRow, &totalNz)

// Allocate device memory to store the CSR representation of A

// Convert A from dense formatting to a CSR formatting, using the GPU
cusparseDense2csr(handle, M, N, descr, dA, dnnzPerRow,
dCsRowValA, dCsRowPtrA, dCsColIndA)

```

// Perform matrix-vector multiplication using the CSR-formatted matrix A
cusparseScrmv(handle, SPARSE_OPERATION_NON_TRANSPOSE,
M, totalNz, alpha, descr, dCsRowValA, dCsRowPtrA,)
```

```
// Copy the result back to the host
cudaMemcpy(Y, dy, sizeof (float) * M, cudaMemDeviceToHost);
```

cusparse.cu is a miniature of a legacy application with a native dense matrix format, ported to use cuSPARSE and the CSR matrix format. It follows a workflow very similar to the common workflow described previously in the chapter:

- 1. A cuSPARSE library handle is created using cusparseCreate.
- 2. Device memory used to store the input matrix and vectors in dense CSR format is allocated using cudaMalloc.
- 3. The routines cusparseCreateMatDescr and cusparseSetMat* are used to configure matrix properties. cudaMemcpy is used to transfer all inputs into the pre-allocated device memory. The format routine cusparseDense2csr is used to generate the CSR version of the dense matrix with the help of cusparseSnn, which counts the number of non-zero elements in each row or column of a dense matrix as well as in the entire matrix.
- 4. cusparseScrmv is called on the CSR matrix and input vectors to perform the actual matrix-vector multiplication.
- 5. cudaMemcpy is used to retrieve the final results of the computation in the Y vector from device memory. No transformations are necessary as it is stored and processed in a dense format.
- 6. CUDA and cuSPARSE resources are released using cudaFree, cusparseDestroyMatDescr, and cusparseDestroy.
