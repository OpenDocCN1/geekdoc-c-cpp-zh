
# Memory Allocation and Deallocation

The CUDA programming model assumes a heterogeneous system that consists of a host and a device, with its own separate memory space. Kernel functions operate in the device memory space, and the CUDA runtime provides functions to allocate and deallocate device memory. You can allocate global memory on the host using the following function:

```
cudaError_t cudaMalloc(void **devPtr, size_t count);
```

This function allocates bytes of global memory on the device and returns the location of that memory in devPtr. The allocated memory is suitably aligned for any variable type, including integers, floating-point values, booleans, and so on. The cudaMalloc function returns cudaError on failure. The values contained in the allocated global memory are not cleared. It is your responsibility to either fill the allocated global memory with data transferred from the host, or initialize it with the following function:

```
cudaError_t cudaMemset(void *devPtr, int value, size_t count);
```

This function fills each of the count bytes starting at the device memory address devPtr with the value stored in the variable value.

Once an application is no longer using a piece of allocated global memory, it can be deallocated using:

```
cudaError_t cudaFree(void *devPtr);
```

This function frees the global memory pointed to by devPtr, which must have been previously allocated using a device allocation function (such as cudaMalloc). Otherwise, it returns an error cudaErrorInvalidDevicePointer. cudaFree also returns an error if the address has already been freed.

Device memory allocation and deallocation are expensive operations, so device memory should be reused whenever possible to minimize the impact on overall performance.

# Memory Transfer

Once global memory is allocated, you can transfer the data to the device from the host using the following function:

```
cudaError_t cudaMempy(void *dst, const void *src, size_t count,
enum cudaMemcpyKind kind);
```

This function copy bytes from the memory location src to the memory location dst. The variable kind specifies the direction of the copy and can have the following values:

```
cudaMemcpyHostToHost
cudaMemcpyHostToDevice
cudaMempyDeviceToHost
cudaMemcpyDeviceToDevice
```

If the pointers dst and src do not match the direction specified by kind, the behavior of cudaMempy is undefined. This function exhibits synchronous behavior in most cases.

An example that uses cudaMempy is shown in Listing 4-2. This example transfers data back and forth between the host and the device. Global memory is allocated using cudaMalloc and data is transferred to the device using the direction specified as cudaMemcpyHostToDevice. Data is transferred back to the host with cudaMemcpy and a direction of cudaMemcpyDeviceToHost.

# LISTING 4-2: Simple memory transfer (memTransfer.cu)

```
#include <cuda_runtime.h>
#include <stdio.h>

int main(int argc, char **argv) {
    // set up device
    int dev = 0;
    cudaSetDevice(dev);

    // memory size
    unsigned int size = 1<<22;
    unsigned int nbytes = size * sizeof(float);

    // get device information
    cudaDeviceProp deviceProp;
    cudaGetDeviceProperties(&deviceProp, dev);
    printf("%d starting at %s\n", argv[0]);
    printf("%d: %d size %d bytes %.2fMB\n", dev, deviceProp.name, nbytes/(1024.0*1024.0));

    // allocate the host memory
    float *h_a = (float*)malloc(nbytes);

    // allocate the device memory
    float *d_a;
    cudaMalloc((float **)&d_a, nbytes);

    // initialize the host memory
    for(unsigned i=0;i<size;i++) h_a[i] = 0.5f;

    // transfer data to the device
    cudaMemcpy(d_a, h_a, nbytes, cudaMemcpyHostToDevice);

    // transfer data from the device to the host
    cudaMemcpy(h_a, d_a, nbytes, cudaMemcpyDeviceToHost);

    // free memory
    cudaFree(d_a);
    free(h_a);

    // reset device
    cudaDeviceReset();
    return EXIT_SUCCESS;
}
```

```

$ nvprof ./memTransfer
```

The data transfer from the host to the device is labeled HToD, and from the device to the host DToH. Figure 4-3 shows the connectivity of CPU and GPU. From the diagram you can see that the theoretical bandwidth between the CPU and GPU through PCI Express (PCIe) Gen2 bus shows a much lower peak of 8 GB/sec (Gen3 maximum limit is 16 GB/sec). This disparity means that data transfers between the host and device can throttle overall performance if not managed properly. Therefore, as a basic principle of CUDA programming, you should always think to minimize host-device transfers. Allocated host memory is default pageable, which is subject to page fault operations that move data in virtual memory to different locations directed by the operating system. Virtual memory offers the illusion of much more memory than physically available, just as L1 cache offers the illusion of much more on-chip memory. GPU cannot safely access pageable memory because it has no control over the host. When transferring data from pageable host memory to device, the CUDA driver first allocates temporary page-locked memory, copies source data to pinned memory, and then transfers the data from pinned memory to device, as illustrated on the left side of Figure 4-4.

# Pinned Memory

The CUDA runtime allows you to directly allocate pinned memory using:

```
cudaError_t cudaMallocHost(void **devPtr, size_t count);
```

This function allocates counts of host memory that are page-locked and accessible to the device. Since the pinned memory can be accessed directly by the device, it can be read and written with much higher bandwidth than pageable memory. However, allocating excessive amounts of pinned memory might degrade system performance since it reduces the amount of pageable memory available to the host. The following snippet demonstrates allocating pinned memory with error checking and elementary handling:

```
cudaError_t status = cudaMallocHost(void **devPtr, bytes);
if (status != cudaSuccess) {
    fprintf(stderr, "Error returned from pinned memory allocation\n");
    exit(1);
}
```

Pinned memory must be freed with:

```
cudaError_t cudaFreeHost(void *ptr);
```

You can try replacing pageable host memory with pinned memory in the file memTransfer.cu, or you can download the file pinTransfer.cu from CUDA.com. Compile the code using nvcc and run it with nvprof as follows:

```
$ nvcc -O3 pinTransfer.cu -o pinTransfer
$ nvprof ./pinTransfer
```

# MEMORY TRANSFER BETWEEN THE HOST AND DEVICE

- Pinned memory is more expensive to allocate and deallocate than pageable memory, but provides higher throughput for large data transfers.
- The speedup achieved using pinned memory relative to pageable memory depends on device compute capability. For example, on Fermi devices it is generally beneficial to use pinned memory when transferring more than 10 MB of data.
- Batching many small transfers into one larger transfer improves performance because it reduces per-transfer overhead.
- Data transfers between the host and device can sometimes be overlapped with kernel execution. You will learn more about this topic in Chapter 6, "Streams and Currency." You should either minimize or overlap data transfers between the host and device whenever possible.

# Zero-Copy Memory

In general, the host cannot directly access device variables, and the device cannot access host variables. There is one exception to the rule: zero-copy memory. Both the host and device can access zero-copy memory.

GPU threads can directly access zero-copy memory. There are several advantages to using zero-copy memory in CUDA kernels, such as:

- Leveraging host memory when there is insufficient device memory
- Avoiding explicit data transfer between the host and device
- Improving PCIe transfer rates

When using zero-copy memory to share data between the host and the device, you must synchronize memory accesses across the host and device. Modifying data in zero-copy memory from both the host and device at the same time will result in undefined behavior.
