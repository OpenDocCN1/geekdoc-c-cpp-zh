## Using the cuFFT API

cuFFT is used to refer to two separate libraries: the core, high-performance cuFFT library and the portability library, cuFFTW. The cuFFT library is an implementation of FFTs on CUDA that provides its own API. cuFFT, on the other hand, is designed with an identical API to the standard FFTW (Fastest Fourier Transform in the West) host library. Similar to how cuBLAS shares its API with the BLAS library, cuFFT is designed to maximize portability from existing code that uses FFTW. A wide range of the functions in the FFT library are identically supported in cuFFTW. cuFFT assumes all inputs are passed as handles and manages all the allocation (cudaMalloc) and transfers (cudaMempy). Although this might lead to suboptimal performance, it greatly accelerates the porting process. A full list of supported operations in cuFFTW and cuFFT, refer to the cuFFT User Guide.

Configuration of the cuFFT library is done with FFT plans, the terminology that cuFFT uses to refer to its handles. A plan defines a single transform operation to be performed. cuFFT uses plans to derive the internal memory allocations, transfers, and kernel launches that must occur to perform the requested transformation. Different plan creations can be used to generate plans of increasing complexity and dimensionality;

```c
cuffResult cuftPlan1d(cuffHandle *plan, int nx, cufftType type, int batch);
cuffResult cuftPlan2d(cuffHandle *plan, int nx, int ny, cufftType type);
cuffResult cuftPlan3d(cuffHandle *plan, int nx, int ny, int nz, cufftType type);
```

cuFFT also supports a variety of input and output types, including:

- Complex-to-complex
- Real-to-complex
- Complex-to-real

For many real-world applications, the most useful type is real-to-complex, enabling you to input real-valued measurements from real-world systems to cuFFT.

Once a cuFFT plan is configured, it is executed using a cufftExec* function call (for example, cufftExec2c). In general, function calls take as input the plan, the location where inputs are stored, the location to place outputs, and whether this is a forward FFT (time domain to frequency domain) or inverse FFT (frequency domain to time domain).

## Demonstrating cuFFT

This section covers a simple example using the cuFFT API to perform a complex-to-complex, 1D FFT. You can download the sample code in cufft.cu from Wrox.com or follow along in the code snippet below

```c
// Setup the cuFFT plan
cufftPlan1d(&plan, N, CUFFT_C2C, 1);

// Allocate device memory
cudaMalloc(void **)&complexSamples, sizeof(cuffComplex) * N);

// Transfer inputs into device memory
cudaMemcpy(dComplexSamples, complexSamples, sizeof(cuffComplex) * N, cudaMemcpyHostToDevice);

// Execute a complex-to-complex 1D FFT
cufftExec2c(plan, dComplexSamples, dComplexSamples, CUFFT_FORWARD);

// Retrieve the results into host memory
cudaMemcpy(complexFreq, dComplexSamples, sizeof(cuffComplex) * N, cudaMemcpyDeviceToHost);
```

The workflow for a cuFFT application varies depending on the complexity of the transform. At its most basic level, the workflow consists of:

1. Create and configure a cuFFT plan.
2. Allocate device memory to store the inputs and output frequencies from cuFFT using cudaMalloc. Note that this memory must be typed to support the type of transform you are performing (for example, complex-to-complex, real-to-complex, complex-to-real). You can perform an in-place transform using the same device memory for both inputs and outputs.
3. Populate device memory with the input signal samples using cudaMempy.
4. Execute the plan using a cuFFtExec* function.
5. Retrieve the result from device memory using cudaMempy.
6. Release CUDA and cuFFT resources using cudaFree and cufftDestroy.

This example can be built using the following command:

```bash
$ nvcc -lcusufft cufft.cu -o cufft
```

The example provided in cufft.cu generates a sequence of input samples from the function cos (x), converts them to complex numbers, transfers the complex representation to the GPU, and executes a complex-to-complex 1D plan before copying the results. Note that the same memory location dComplexSamples is passed to cufftExec2C for both the input and output-range, this is an in-place FFT operation. A separate output buffer could also be pre-allocated and used to store the output.

## THE cuRAND LIBRARY

Random number generation is a critical part of many scientific, cryptographic, and financial applications. A random number generator (RNG) is a function f that takes no arguments, but on each invocation, returns the next value in a sequence of values. You can visualize it as a pointer traversing an array filled with random values, as shown in Figure 8-10.

cuRAND provides a CUDA-based library for rapid quasi- and pseudo-random number generation.

## Choosing Pseudo- or Quasi-random Numbers

The most important concept to understand is that there is no such thing as true randomness. Because computers are deterministic, they can only produce pseudo-random numbers. A pseudo-random RNG (PRNG) uses an algorithm where each value has an equal probability of being anywhere along the range. For retrieving a value from an integer PRNG, the probability of the returned value being 1 is the same as the probability of it being 2, or 3, all the way to INT_MAX. This is true for every value from the PRNG. This means that just because the last value retrieved was 2 does not mean the probability of the next value is any lower. In other words, each sampling of a pseudo-random sequence is a statistically independent event and does not affect the value observed by future samplings.

This does not hold true for quasi-random generators (QRNG). A QRNG makes an effort to fill the range of the type evenly; if the last value used was 2, then P(2) for the next value has actually decreased. The samplings of a QRNG's sequence are not statistically independent.

## Overview of the cuRAND Library

The cuRAND library can be used to sample values from both pseudo-random and quasi-random sequences. It is unique among the CUDA libraries discussed here in that it has a host API and a device API. This means it can be directly called from both host code and kernel code. Many concepts exposed by the cuRAND library are shared between the two APIs, though some options are added when using the device API.
