From these two indicators, a natural conclusion is that global memory operations in this application might be limiting performance. The next step forward is going much more dependent on application-specific knowledge of how global memory is being used.

So, what objects are stored in global memory? Currently, the input text, crypt and encryption/decryption key are all stored and accessed in global memory. Because chunks of data are being streamed by thread ID, each thread is reading and writing neighboring 8-byte chunks in text and crypt. While 4 bytes would be enough, this should still yield efficient use of cache and bandwidth because the accesses are coalesced and aligned.

The access pattern for key is a very different story. Every thread reads from the location in key at the same time. This would yield much lower global memory utilization, as a full warp of threads will be blocked to read the 4 bytes from global memory. Because key, text and crypt are all stored in the L1 and L2 caches on a GPU multiprocessor, reader might have to read multiple times if it is evicted from cache by writes of text or crypt. Based on this analysis and the metrics reported by nvvp, it seems that optimizing key's usage is a good next step.

One way to do this is by changing the key is stored. In what CUDA memory types read-only data structures are optimized for broadcasting a single element to all threads? That sounds exactly like constant memory! Placing key in constant memory will likely improve both global memory bandwidth and cache efficiency.
