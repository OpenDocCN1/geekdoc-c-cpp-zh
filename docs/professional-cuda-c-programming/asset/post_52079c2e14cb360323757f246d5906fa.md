Earlier in this chapter, you tested a matrix transpose kernel that used a single thread block to write a matrix row in shared memory and read from a column. ## Baseline Transpose Kernel

As a baseline, the following kernel is a naive implementation of matrix transpose that uses only global memory.

```
global void naiveGmem(float *out, float *in, const int nx, const int ny) {
    // matrix coordinate (ix,iy)
    unsigned int ix = blockIdx.x * blockDim.x + threadIdx.x;
    unsigned int iy = blockDim.y + threadIdx.y;

    // transpose with boundary test
    if (ix < nx && iy < ny) {
        out[ix*ny+iy] = in[iy*nx+ix];
    }
}
```

Because ix is the innermost dimension of this kernel's 2D thread configuration, the global memory read is coalesced within a width, while the global memory operation exhibits its str access across neighboring threads. The performance for this naiveGmem kernel is a lower bound that progressive optimizations considered in this section will be measured against.

Changing the write operation to perform coalesced accesses would result in a copy kernel. Because both the read and write operations were coalesced but still performing the same amount of I/O, the copy kernel copyGmem serves as an upper performance bound:

```
global void copyGmem(float *out, float *in, const int nx, const int ny) {
    // matrix coordinate (ix,iy)
    unsigned int ix = blockIdx.x * blockDim.x + threadIdx.x;
    unsigned int iy = blockDim.y + threadIdx.y;

    // transpose with boundary test
    if (ix < nx && iy < ny) {
        out[iy*nx+ix] = in[iy*nx+ix];
    }
}
```

The kernels and code for this section can be found in transposeRectangle.cu on Wrox.com. For these tests, the matrix size is set to 4,096 × 4,096 and a 2D thread block with dimensions 32 × 16 is used.

## Matrix Transpose with Shared Memory

To avoid global memory access, 2D shared memory can be used to cache data from the original matrix. A column from 2D shared memory can be transferred to a transposed row stored in global memory. While a naive implementation will result in shared memory bank conflicts, the performance will be much better than non-coalesced global memory accesses. Figure 5-15 illustrates how shared memory is used in matrix transpose.

- Step 1: Read a row of a block from global memory and write to a row of shared memory.
- Step 2: Read a column from shared memory and write to a row of a block to global memory.

The following kernel implements a matrix transpose with shared memory. It can be viewed as an extension of the setRowReadCol kernel discussed earlier the chapter. The difference between these kernels is that setRowReadCol handles the transpose of a single block of the input matrix using one thread. The kernel transposeSmem extends the transpose operations to use multiple blocks and multiple data.

```
__global void transposeSmem(float *out, float *in, int nx, int ny) {
    // static shared memory
    shared__ float tile[BDIMY][BDIMY];
    // coordinate in original matrix
    unsigned int ix,iy,ti;
    ix = blockIdx.x*blockDim.x + threadIdx.x;
    iy = blockIdx.y*blockDim.y + threadIdx.y;
    // linear global memory index for original matrix
    ti = iy*nx + ix;
    // thread index in transposed block
    unsigned int bix,row,icol;
    bix = threadIdx.y*blockDim.x + threadIdx.x;
    row = bix/blockDim.y;
    icol = bix%blockDim.y;
    // coordinate in transposed matrix
    ix = blockIdx.x * blockDim.y + icol;
    iy = blockIdx.y * blockDim.x + row;
    // linear global memory index for transposed matrix
    to = iy*ny + ix;
    
    if (ix < nx && iy < ny) {
        // load data from global memory to shared memory
        tile[threadIdx.x] = in[ti];
        syncthreads();
        // store data from shared memory to global memory
        out[to] = tile[icol][row];
    }
}
```

kernel transposeSmem can be broken down into the following steps:

- 1. A warp performs a coalesced read from global memory and writes to a row of the 2D shared memory array tile.
- 2. The read from global memory is coalesced and the write to shared memory banks are conflict-free.
- 3. After all read/write operations in shared memory are synchronized, a warp reads from a column from shared memory tile and writes contiguously to global memory.
- 4. The write to global memory is coalesced, but the read from shared memory causes a bank conflict because each warp reads data along a column in tile. The bank conflict will be resolved later in this section using shared memory padding. Figure 5-16 illustrates the index calculations.
