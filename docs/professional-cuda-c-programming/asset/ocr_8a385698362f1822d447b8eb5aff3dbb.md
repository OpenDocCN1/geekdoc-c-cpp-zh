Although each case will hit hardware limits, both cause resources to be underutilized and hinder the creation of sufficient parallelism to hide memory latency. Occupancy focuses exclusively on the number of concurrent threads or warps per SM. However, full occupancy is not the only goal for performance optimization. Once a level of occupancy is achieved for a kernel, further increases may not lead to performance improvement. There are many factors you need to examine for performance tuning. You will learn all these issues in detail in subsequent chapters.

# # Synchronization

Barrier synchronization is a primitive that is common in many parallel programming languages. CUDA, synchronization can be performed at two levels:

+   - **System-level**: Wait for work on both the host and the device to complete.
- **Block-level**: Wait for all threads in a thread block to reach the same point in execution on the device.

Since CUDA API calls and all kernel launches are asynchronous with respect to the host, cudaDeviceSync can be used to block the host application until CUDA operations (copies, kernels, and so on) have completed

```
cudaError_t cudaDeviceSync();
```

This function may return errors from previous asynchronous CUDA operations.

Because threads in a thread block are executed in an undefined order, CUDA provides the ability to synchronize their execution with a block-local barrier. You can mark synchronization points in the kernel:

```
__synctreads();
```

When __synctreads() is called, each thread in the thread block must wait until all other threads in that thread block have reached this synchronization point. All global and shared memory accesses by all threads prior to this barrier will be visible to all threads in the thread block after the barrier. The function is used to coordinate communication between threads in the same block, but it can negatively affect performance by forcing warps to idle.

Threads within a thread block can share data through shared memory and registers. When sharing data between threads you need to be careful to avoid race conditions. Race conditions, hazards, or unordered accesses occur when multiple threads access the same memory location. For example, a read-writer hazard occurs when an unordered read of a location follows a write. Because there is no ordering between the read and the write, it is undefined if the read should have loaded the value before or after the write. Other examples of hazards are read-read or write-writer hazards. While threads in a thread block run logically in parallel, not all threads execute physically at the same time. If thread A tries to read data that is written by thread B in a different warp, you can only be sure that thread B finished writing if proper synchronization is used. Otherwise, a race condition occurs. You will examine these synchronization issues in depth in Chapter 4.
