
using nvprof. First, check the memory read efficiency of the kernel using the gld_throughput metric to observe the differences for each execution configuration:

```
$ nvprof --metrics gld_throughput/sumMatrix 32 32
sumMatrixOnGPU<<< (512,512), (32,32)>>> Global Load Throughput 35.908GB/s
$ nvprof --metrics gld_throughput/sumMatrix 32 16
sumMatrixOnGPU<<< (512,512), (32,16)>>> Global Load Throughput 56.478GB/s
$ nvprof --metrics gld_throughput/sumMatrix 16 32
sumMatrixOnGPU<<< (1024,512), (16,32)>>> Global Load Throughput 81.195GB/s
$ nvprof --metrics gld_throughput/sumMatrix 16 16
sumMatrixOnGPU<<< (1024,1024), (16,16)>>> Global Load Throughput 94.708GB/s
```

While the fourth case has the highest load throughput, it is slower than the second case (which only demonstrates half the load throughput). From this, the reason will be clear when you learn how memory transactions work inside the GPU device in 4.

Next, check the load efficiency using the gld_efficiency_metric, which is the ratio of requested load throughput to required load throughput. It measures how the application's operations use device memory bandwidth. The results are summarized below:

```
$ nvprof --metrics gld_efficiency,/sumMatrix 32 32
sumMatrixOnGPU<<< (512,512), (32,32)>>> Global Memory Efficiency 100.00%
$ nvprof --metrics gld_efficiency/sumMatrix 32 16
sumMatrixOnGPU<<< (512,512), (32,16)>>> Global Memory Efficiency 100.00%
$ nvprof --metrics gld_efficiency/sumMatrix 16 32
sumMatrixOnGPU<<< (1024,512), (16,32)>>> Global Memory Efficiency 49.96%
$ nvprof --metrics gld_efficiency/sumMatrix 16 16
sumMatrixOnGPU<<< (1024,1024), (16,16)>>> Global Memory Efficiency 49.80%
```

From these results, you can explain why the higher load throughput and achieved occupancy of the last two cases did not yield improved performance. Even though the number of loads being performed (that is, throughput) is greater for the last cases, the effectiveness of those loads (that is, efficiency) is lower.

Note that the common feature for the last two cases is that their block size in the innermost dimension is always a multiple of the warp size. As stated earlier, for grid and block heuristics the innermost dimension should always be a multiple of the warp size. Chapter 4 will discuss how half-warp threads impact performance.

# Exposing Parallelism

One conclusion you can draw from the previous section is that the innermost dimension of a block {block.x} should be a multiple of warp size. So drastically improved load efficiency. You might be curious:

- Is it possible to increase the load throughput by adjusting block.x?
- Is it possible to expose more parallelism?

Now that a performance has been established, these questions can be answered by testing sumMatrix with a wider range of thread configurations:

```
$ ./sumMatrix 64 2
sumMatrixOnGPU2D <<(256,8192), (64,2) >>> elapsed 0.033567 sec
$ ./sumMatrix 64 4
sumMatrixOnGPU2D <<(256,4096), (64,4) >>> elapsed 0.034908 sec
$ ./sumMatrix 64 8
sumMatrixOnGPU2D <<(256,2048), (64,8) >>> elapsed 0.036651 sec
$ ./sumMatrix 128 2
sumMatrixOnGPU2D <<(128,8192), (128,2) >>> elapsed 0.032688 sec
$ ./sumMatrix 128 4
sumMatrixOnGPU2D <<(128,4096), (128,4) >>> elapsed 0.034786 sec
$ ./sumMatrix 128 8
sumMatrixOnGPU2D <<(128,2048), (128,8) >>> elapsed 0.046157 sec
$ ./sumMatrix 256 2
sumMatrixOnGPU2D <<(64,8192), (256,2) >>> elapsed 0.032793 sec
$ ./sumMatrix 256 4
sumMatrixOnGPU2D <<(64,4096), (256,4) >>> elapsed 0.038092 sec
$ ./sumMatrix 256 8
sumMatrixOnGPU2D <<(64,2048), (256,8) >>> elapsed 0.000173 sec
Error: sumMatrix.cu:163, code:9, invalid configuration argument
```

Here are some observations and conclusions from these results:

- The last execution with block size (256,8) is invalid. The total threads in a block exceeds 1,024, the hardware limit for this GPU.
- The best results are achieved with the fourth case using block dimensions of (128,2).
- While the first case with block dimension (64,2) launches the most thread blocks, it is not the fastest connection.
- Because the second case with block configuration (64,4) has the same number of threads as the block, the two cases expose the same parallelism on the device. Because this case underperforms relative to (128,2) you can conclude that the innermost of a thread block plays a key role in performance. This repeats the conclusion in the previous section.
- All remaining cases have fewer thread blocks than the best case. Furthermore, more parallelism is an important factor in performance optimization.

You might guess that the least thread blocks report lower achieved occupancy, and examples with the most thread blocks report higher achieved occupancy. This theory can be examined by measuring the achieved_occupancy metric with nvprof:
