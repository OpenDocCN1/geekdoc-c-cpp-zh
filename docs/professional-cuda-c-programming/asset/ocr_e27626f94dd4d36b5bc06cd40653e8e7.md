Now that a performance has been established, these questions can be answered by testing sumMatrix with a wider range of thread configurations:

```
$ ./sumMatrix 64 2
sumMatrixOnGPU2D <<(256,8192), (64,2) >>> elapsed 0.033567 sec
$ ./sumMatrix 64 4
sumMatrixOnGPU2D <<(256,4096), (64,4) >>> elapsed 0.034908 sec
$ ./sumMatrix 64 8
sumMatrixOnGPU2D <<(256,2048), (64,8) >>> elapsed 0.036651 sec
$ ./sumMatrix 128 2
sumMatrixOnGPU2D <<(128,8192), (128,2) >>> elapsed 0.032688 sec
$ ./sumMatrix 128 4
sumMatrixOnGPU2D <<(128,4096), (128,4) >>> elapsed 0.034786 sec
$ ./sumMatrix 128 8
sumMatrixOnGPU2D <<(128,2048), (128,8) >>> elapsed 0.046157 sec
$ ./sumMatrix 256 2
sumMatrixOnGPU2D <<(64,8192), (256,2) >>> elapsed 0.032793 sec
$ ./sumMatrix 256 4
sumMatrixOnGPU2D <<(64,4096), (256,4) >>> elapsed 0.038092 sec
$ ./sumMatrix 256 8
sumMatrixOnGPU2D <<(64,2048), (256,8) >>> elapsed 0.000173 sec
Error: sumMatrix.cu:163, code:9, invalid configuration argument
```

Here are some observations and conclusions from these results:

+   - The last execution with block size (256,8) is invalid. The total threads in a block exceeds 1,024, the hardware limit for this GPU.
- The best results are achieved with the fourth case using block dimensions of (128,2).
- While the first case with block dimension (64,2) launches the most thread blocks, it is not the fastest connection.
- Because the second case with block configuration (64,4) has the same number of threads as the block, the two cases expose the same parallelism on the device. Because this case underperforms relative to (128,2) you can conclude that the innermost of a thread block plays a key role in performance. This repeats the conclusion in the previous section.
- All remaining cases have fewer thread blocks than the best case. Furthermore, more parallelism is an important factor in performance optimization.

You might guess that the least thread blocks report lower achieved occupancy, and examples with the most thread blocks report higher achieved occupancy. This theory can be examined by measuring the achieved_occupancy metric with nvprof:

```
$ nvprof --occupancy ./sumMatrix 64 2

$ nvprof --occupancy ./sumMatrix 64 4

$ nvprof --occupancy ./sumMatrix 64 8
sumMatrixOnGPU2D <<(256,2048), (64,8) >>> Achieved Occupancy 0.753532
$ nvprof --occupancy ./sumMatrix 128 2
sumMatrixOnGPU2D <<(128,8192), (128,2) >>> Achieved Occupancy 0.802598
```
