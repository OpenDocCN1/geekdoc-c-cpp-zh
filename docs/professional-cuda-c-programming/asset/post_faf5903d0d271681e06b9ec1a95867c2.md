## Performance Tuning

There are two goals to strive for when optimizing device memory bandwidth utilization:

- Aligned and coalesced memory accesses that reduce wasted bandwidth
- Sufficient concurrent memory operations to handle memory latency

In the preceding section, you learned how to organize memory access patterns so they are aligned and coalesced. Doing so will ensure efficient use of bytes moving between device DRAM and SM on-chip memory or registers.

Chapter 3 discussed optimizing kernels for instruction throughput. Recalling that maximizing concurrent memory accesses is achieved by:

- Increasing the number of memory operations performed within each thread.
- Experimenting with the execution configuration of a kernel launch to expose sufficient parallelism to each SM.

## Unrolling Techniques

Unrolling loops that contain memory operations adds more independent, memory operations to the pipeline. You are already familiar with unrolling from the example in Chapter 3.

Consider the earlier readOffset example. Review how each thread performs four independent memory operations, follows. Because each of these is independent, you can perform more concurrent accesses.

```cpp
__global void readOffsetunroll4(float *A, float *B, float *C,
  const int n, int offset) {
  unsigned int i = blockIdx.x * blockDim.x * 4 + threadIdx.x;
  unsigned int k = i + offset;
  if (k + 3 * blockDim.x < n) {
    C[i] = A[k];
    C[i + blockDim.x] = A[k + blockDim.x];
    C[i + 2 * blockDim.x] = A[k + 2 * blockDim.x] + B[2 * blockDim.x];
    C[i + 3 * blockDim.x] = A[k + 3 * blockDim.x] + B[k + 3 * blockDim.x];
  }
}
```

You can download the source in readSegmentUnroll.cu from Wrox.com. Compile it with L1 cache (-Xptxas -dlcm=ca) and run the following tests:

```bash
$ /readSegmentUnroll 0
warmup      << 32768, 512 >>> offset      0 0.001990 sec
unroll      << 8192, 512 >>> offset      0 0.000599 sec
$ /readSegmentUnroll 1
warmup      << 32768, 512 >>> offset      11 0.002214 sec
unroll      << 8192, 512 >>> offset      11 0.000615 sec
$ /readSegmentUnroll 2
warmup      << 32768, 512 >>> offset      128 0.001989 sec
unroll      << 8192, 512 >>> offset      128 0.000598 sec
```

Surprised? This unrolling has a tremendous impact on performance, even when address alignment matters. Relative to the original readSegmentExample with no unrolling, test runs demonstrate 3.04 and 3.11 times faster. With an I/O-bound kernel, it seems that exposing sufficient memory access parallelism is a high priority.

Even though 128 threads per block exposes more parallelism, the best block size for the unrolled kernel is 256 threads per block. This is because the Fermi GPU has a limit of 8 blocks per SM, and with 128 threads per block, only 32 warps are used, whereas with 256 threads per block, 48 warps are used, which is the hardware limit.

Now, the test of block size on performance when misaligned accesses are performed. The results show similar behavior to the aligned case, with 128, 256, and 512 threads per block performing very similarly. This suggests that some SM hardware limitations are still playing a role, regardless of alignment.
