
many threads as the current grid. After the child grid is invoked, a barrier point is set for all child grids. Only one child grid is generated by one thread in each block, this barrier point only synchronizes with the one child grid.

```cpp
__global void gpuRecursiveReduce(int *g_idata, int *g_odata,
    unsigned int size) {
    // set thread ID
    unsigned int tid = threadIdx.x;
    // convert global data pointer to the local pointer of this block
    int *idata = g_idata[blockIdx.x*blockDim.x];
    int *odata = &g_odata[blockIdx.x];
    // stop control
    if (size == 2 && tid == 0) {
        g_odata[blockIdx.x] = idata[0]+idata[1];
        return;
    }
    // nested invocation
    int istride = size>>1;
    if (istride > 1 && tid < istride) {
        // in place reduction
        idata[tid] += idata[tid + istride];
    }
    // sync at block level
    __syncthreads();
    // nested invocation to generate child grids
    if(tid==0) {
        gpuRecursiveReduce<<<1, istride>>>(idata, odata, istride);
        // sync all child grids launched in this block
        cudaDeviceSynchronize();
    }
    // sync at block level again
    __syncthreads();
}
```

As shown in the output, there are 2,048 blocks recursions, 16,384 child blocks were created, and intra-block synchronization with __syncthreads was also invoked 16,384 times. A large amount of kernel invocation and synchronization is likely the main cause for such poor performance.

When a child grid is invoked, its view of memory is fully consistent with the parent thread. Because each thread only needs its parent's values to compute the partial reduction, the in-block synchronization performed before the child grid is launched. Removing all synchronization operations performs the following kernel:

```cpp
global void gpuRecursiveReduceNosync(int *g_idata, int *g_odata,
    unsigned int isize) {
    // thread ID
    unsigned int tid = threadIdx.x;

    // convert global data pointer to the local pointer of this block
    int *idata = g_idata + blockIdx.x * blockDim.x;
    int *odata = &g_odata[blockIdx.x];

    // stop condition
    if (isize == 2 && tid == 0) {
        g_odata[blockIdx.x] = idata[0] + odata[1];
        return;
    }

    // nested invoke
    int istride = isize;
    if (istride > 1 && tid < istride) {
        idata[tid] += tid + istride;
        if (tid==0) {
            gpuRecursiveReduceNosync<<<1, istride>>>(idata, odata, istride);
        }
    }
}
```

Performance is still poor compared to the neighbor-parallel kernel. Next, consider how to reduce the overhead caused by the large number of child grid launches. In the current implementation, each block generates a child grid, resulting in a huge number of invocations. If the approach shown in Figure 3-30 was used, the number of threads per child grid would increase while the number of child grids would grow, maintaining the same amount of parallelism.

The following kernel implements this approach: the first thread in the first block of a grid invokes the child grids for each nested step. Comparing the two kernel versions, you will find that argument has been added. At each nested invocation the child size is reduced to half of its parent size, the parent block dimension must be passed to the nested grid. This allows each thread to calculate the correct global memory offset for the workload. Note that in this implementation all idle threads are removed from kernel launch compared to the first implementation where half of all threads are idling during kernel execution at each level. This will free up half of the resources consumed by the first kernel as allow more threads to be active.

```cpp
__global void gpuRecursiveReduce2(int *g_idata, int *godata, int iStride, const int iDim) {
    // convert global data pointer to the local pointer of this block
    int *idata = g_idata + blockIdx.x;
    // stop condition
    if (iStride == 1 && threadIdx.x == 0) {
      godata[blockIdx.x] = idata[0]+idata[1];
      return;
    }
    // in place reduction
    idata[threadIdx.x] += idata[threadIdx.x + iStride];
    // nested invocation to generate child grids
    if(threadIdx.x == 0 && blockIdx.x == 0) {
      gpuRecursiveReduce2<<<gridDim.x, iStride/2, iDim>>(g_idata, godata, iStride/2, iDim);
    }
}
```

This recursive reduction example demonstrates dynamic parallelism. For a given algorithm, you may have several possible implementations using different parallelism techniques. Avoiding a large number of nested invocations helps reduce overhead and improve performance. Synchronization is very important for performance and correctness, reducing the number of in-block synchronizations will likely lead to more efficient nested kernels. The runtime reserves extra memory at each nesting level, the maximum number of kernel nesting will be limited. The extent of that limit is kernel-dependent and may restrict the scale, performance, and other properties of any application that uses dynamic parallelism.

# SUMMARY

In this chapter, you examined kernel execution from the hardware point-of-view. The most distinguished features of the CUDA execution model on GPU devices are:

- Threads are wrapped in warps in SIMT fashion.
- Hardware resources are partitioned among blocks and threads.

These features of the execution model are exposed to you, allowing you to control how your application saturates instruction and memory bandwidth as you increase parallelism and performance. GPU devices with different compute capabilities have different hardware limits; therefore, grid and block heuristics play a very important role in optimizing kernel performance for different platforms.

Dynamic parallelism gives you the ability to create new work directly from the device. It enables you to express recursive or data-dependent parallel algorithms in a natural and easy-to-understand way. To implement an efficient nested kernel, attention must be given to how the runtime works, including child launch strategy, parent-child synchronization, and the depth of nested levels.

In this chapter, you also learned how to dissect kernel performance using the command-line profiling tool, nvprof. The profile-driven approach is particularly important in CUDA programming because a naive kernel implementation may not yield good performance. Profiling provides insights on kernel behavior and helps you focus on the major factors that will deliver the best performance.

In Chapters 4 and 5, you will learn about kernel execution from a different perspective: the CUDA memory model.
