```
kernel_3<<<grid, block, 0, streams[i]>>>();
kernel_4<<<grid, block, 0, streams[i]>>>();
```

The OpenMP function omp_set_num_threads is used to specify the CPU cores to be used in OpenMP parallel regions. The compiler directive #pragma omp parallel marks the code between the curly braces as a parallel section. When compiled by a compiler with OpenMP support, the marked section will be run by multiple CPU threads. The omp_get_thread_num function returns a unique ID for each thread, and is used as an index into the streams array to create one-to-one mapping between OpenMP threads and CUDA streams.

When dispatching CUDA operations in parallel with OpenMP useful? In general, if there is additional parallel-work to be completed, or after kernel execution it can be included in the same OpenMP parallel region and overlapped across streams and threads. Doing so makes it apparent that the work performed in each OpenMP thread and the CUDA operations launched from the same thread are related, and makes the code simpler to write optimal performance.

# Adjusting Behavior Using Environment Variables

GPUs that support Hyper-Q maintain multiple hardware work queues between the host and each GPU to eliminate भेदभाव. The maximum number of hardware work queues supported by a Kepler device is limited to eight. However, each connection requires additional memory and resources, setting the default limit to 8 reduce resource consumption for applications that do not require the full 32 work queues. You can use the CUDA_DEVICE_MAX_CONNECTIONS environment variable to adjust the number of concurrent hardware connections, to 32, for a Kepler device.

There are several ways to set this environment variable. In Linux, it can be set using the following commands depending on your shell. For Bash or Bourne Shell:

```
export CUDA_DEVICE_MAX_CONNECTIONS=32
```
