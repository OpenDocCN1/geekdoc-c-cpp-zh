For compatibility reasons, the cuBLAS library also chooses to use column-major storage. This can be confusing if you use the row-major array layout in C/C++.

On the other hand, one-based indexing simply means that the first element in an array is referenced using the value rather than the zero value, as it is in C and many other programming languages. As a result, the final element in an N-element array is referenced with the index N rather than N-1, in zero-based indexing.

However, the cuBLAS library has no control over the semantics of the C/C++ programming language in which it is built, so it must use zero-based indexing. This leads to an odd hybrid situation where the column-major rule of the original FORTRAN BLAS library applies, but not the one-based indexing.

The cuBLAS library comes with two APIs. The cuBLAS Legacy API is the original implementation of cuBLAS that has been since deprecated. The current cuBLAS API (available since CUDA 4.0) should be used for all new development. For the most part, the differences between them are minor, but it is important to aware that they both exist. All example code in this chapter is from the current cuBLAS API.

In this section, you will find that many concepts from cuSPARSE common workflow carry directly over cuBLAS. You must manage handles, streams, and scalar parameters, and the workflow should look similar as you work through the example in this section.

# Managing cuBLAS Data

Compared to cuSPARSE, the data format and type considerations in cuBLAS are relatively simple. All operations are done on dense cuBLAS vectors or matrices. These vectors and matrices are allocated as contiguous chunks of memory through malloc, but we use cuBLAS routines such as cublasSetVector/cublasGetVector and cublasSetMatrix/cublasGetMatrix to transfer data between the host and device. Although these specialized functions around cudaMemcpy are well optimized to transfer strided and unstrided data. For example, a call to cublasSetMatrix takes the following:

```
cublas_t cublasSetMatrix(int rows, int cols, int elementSize,
const void *a, int lda, void *b, int ldb);
```

The first arguments are self-explanatory: They define the dimensions of the matrix to transfer, the size of each element in the matrix, and the memory location of the column-major source matrix a in host. The sixth argument defines the location of the destination matrix in device memory. The use of the fifth and seventh arguments might be clear. lda and ldb specify the leading dimension of the source matrix a and matrix b. The leading dimension is the total number of rows in the respective matrix. This is useful only if a submatrix of a host matrix is being transferred to GPU. In other words, if the full matrices stored at a and b are transferred, lda and ldb should equal M. If only a submatrix in those matrices is being transferred, the values of lda and ldb should be the row length of the full matrix. lda and ldb should always be greater than or equal to rows.
