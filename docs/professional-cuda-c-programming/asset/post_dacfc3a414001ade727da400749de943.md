Now the information provided for the writing reading thread can be used to analyze the hazard. Recall that the writing thread was at line 50 in the debug-hazards.cu, executing the function simple_reduction. The reading thread was 66 in the same file and function. The relevant lines are highlighted here for:

```
if (tid < N)
{
    local_mem[local_id] = input_values[tid];
}

// Required for correctness
__syncthreads();

/*
* Perform the local reduction across values written to shared memory
* by threads in this block.
*/
if (local_id == 0)
{
    int sum = 0;
    for (i = 0; i < local_dim; i++)
        sum = sum + local_mem[i];
}
```

The conflict is between a write to local_mem[local_id] and a read from local_mem[i]. The reading thread is scanning through every shared memory at the same time as the writing thread is filling one of them. In the case of this application, the desired behavior is to ensure that all writes complete before the reading thread starts scanning memory, and that no additional writes are performed before the scan. Because the error reported was identified as a read-after-write, it must mean that synchronization is missing between the reads being performed as part of the scan and the writes to local memory. You have a condition where reads are being performed on memory locations before they have been written. As a first attempt at eliminating this race condition, try uncommenting the __syncthreads on line 54, rebuild and rerun with the same command. This __syncthreads will ensure that all writes complete before thread 0 starts scanning, preventing a read-after-write hazard.

Looking at the new output log, a warning has appeared. Note that this hazard occurs between the two locations in the code, but is a write-after-read hazard instead. This must mean that now writes are occurring before the scanning can complete. This could only happen if threads proceed to the next iteration of the loop before the scanning completes. The kernel must ensure that any additional writes are done to a memory location, the scanning thread must finish reading its current value. To prevent this, another synchronization point must be inserted at line 73, forcing all threads to wait for scanning to complete. Rebuild and rerun to see if this prevents the write-after-read hazard.

This section briefly covered common use cases for kernel and memory debugging tools in CUDA.

You examined cuda-gdb's ability to inspect running program state on the GPU device, dynamically pausing and resuming threads to check for correctness. An example demonstrated cuda-gdb can be used to debug a memory error.
