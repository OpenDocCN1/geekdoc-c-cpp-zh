need to use a third command-line argument to specify the data size, otherwise you will hit the limit
on thread blocks in a grid.

```
$ ./readSegmentUntil 0 1024 22

$ ./readSegmentUntil 0 512 22

```

The best block size for the unrolled kernel is 256 threads per block, doubling the number of blocks
created compared to the default 512 threads used in the earlier trials.

Even though 128 threads per block exposes more parallelism to the GPU, the performance marginally
worse than 256 threads per block. To understand why, refer to Table 3-2, "Resource Limits for
Compute Capability," in Chapter 3. There are two hardware limits in particular that require attention-
Because the system in this case has a Fermi GPU, the maximum number of concurrent
blocks per SM is 8, and the maximum number of concurrent warps per SM is 48. When using 128
threads per block there are 4 warps per block. Because only 8 blocks can be simultaneously placed
a Fermi SM, this kernel is limited to 32 warps per SM. This potentially leads to underutilization
of the SM resources as the upper 48 warps are not used. You could also use thenCUDA Occupancy tool introduced in
Chapter 3 to reach this same conclusion.

Now, the test of thread block size on performance when misaligned accesses are being per-
formed. The results show similar behavior to the aligned case, with 128, 256, and 512
threads per block performing very similarly. This suggests that some-SM hardware resource
limitations are still playing a role in kernel performance, regardless of access-alignment.

# MAXIMIZING BANDWIDTH UTILIZATION

There are two major factors that influence the performance of device memory
operations:

+   Efficient use of bytes moving to avoid wasting memory bandwidth, memory access patterns should
be aligned and coalesced.
Number of memory operations concurrently in-flight: Maximizing the number
of in-flight memory operations is possible through either 1) yielding
more independent memory accesses per thread, or 2) modifying the execution
configuration of a kernel launch to expose more parallelism to each SM.
