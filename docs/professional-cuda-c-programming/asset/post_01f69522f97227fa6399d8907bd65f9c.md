To explore atomic instructions, you will be examining some simple examples. First, it is interesting to compare the behavior and performance of atomic operations to unsafe accesses. You can download, build, and run-atomic-ordering.cu from Wrox. This small application contains two kernels, named atomics and unsafe. The atomics performs atomic operations from every thread on a single shared variable, saving the old value at the target location:

```
values_read[tid] = atomicAdd(shared_var, 1);
```

The kernel unsafe performs the same additions on the same variable, but does not use atomic functions:

```
int old = *shared_var;
*shared_var = old + 1;
values_read[tid] = old;
```

That means threads running the unsafe kernel performing global reads and writes without any mechanisms to prevent overwriting each other. Both kernels also store the old value at the target location, thread conflicts can be visualized as duplicated old values. A sample output is as follows:

The difference in performance is obvious: The version that uses atomics over 300 times longer to run. The final output shows that not all of the operations performed in the unsafe version were written to global memory; many are overwritten and never read by other threads. Conflicts are made more obvious by the values listed in the last two lines of output. The atomic version shows threads with unique increment values, each of the first ten threads version incremented from the same value of zero and will therefore all write the same value. Note that some additions in the unsafe version still complete because the final output was not, so some threads successfully returned to global memory and had their values read back.

This example illustrates the steep tradeoff in performance and correctness you will face when deciding where atomic operations are a necessity and where unsafe accesses are an option. You must be very careful when making this evaluation; deciding to use unsafe accesses is not a recommended programming practice, and should only be done if you are certain correctness is maintained.

# Limiting the Performance Cost of Atomic Operations

Fortunately, when atomic operations are necessary, there are techniques you can use to reduce the performance loss. You can aggregate atomic operations with local steps that generate intermediate result from threads in the thread block. This enables the use of local, lower-latency resources such as instructions or shared memory to produce partial results from each thread block before combining partial results into a final, result using atomic operations. Of course, for this to be valid, the operation must be commutative (that is, the order of operations must not affect the final result). # Atomic Floating-Point Support

One point of note with atomic functions is they are mostly declared to operate on integer types, such as int, unsigned int, or unsigned long int. Of all the atomic functions, only atomicch and atomicAdd have existing support for single-precision floating-point values. None of the atomic functions support double-precision. Fortunately, if your application needs there are techniques to manage multi-threaded access to shared floating-point variables, there implementing floating-point atomic operations. At a high level, the idea is to store the bits of a floating-point value in a supported type and use atomic CAS operations using that supported type.

An example will make this clearer. The following is a version of myAtomicAdd implemented for single-precision floating-point numbers:

```
myAtomicAdd(float *address, float incr) {
// Convert address to a supported type of the same size
unsigned int *typeAddress = (unsigned int*)address;
// Stoke the expected and desired float values as an unsigned int
float currentVal = *address;
unsigned int expected = float32_rn(currentVal);
unsigned int desired = float32_rn(currentVal + incr);

int oldIntValue = atomicCAS(typeAddress, expected, desired);
while (oldIntValue != expected) {
  expected = oldIntValue;
```

- Convert the value read from typedAddress to a float, increment, and then convert back to an unsigned int

```
desired = _float2uint_rn(_uintfloat_rn(oldIntValue) + incr);
oldIntValue = atomicCAS(typedaddress, expected, desired);
}
return _uint2float_rn(oldIntValue);
```

Much of this code could be familiar from the previous myAtomicAdd example. The main difference here is the translation of values passed and returned from atomicCAS using a variety of type-conversion utilities provided by CUDA. This particular example uses:

- 1. A cast to change the type of the address pointer from float to unsigned int
- 2. The use of _float2uint_rn to convert the initial guess, _address, and the desired value, _address + incr, to unsigned ints containing the same bytes
- 3. The use of _uint2float_rn to retrieve a floating-point number from the unsigned int returned by atomicCAS and calculate what the new desired value is, in case of failure

All of this conversion is necessary because these are the types required by the application (float) and the atomicCAS function (unsigned int). CUDA provides a wide range of other type-specific conversion functions including double_as_long, __long_as_double, __double_2float_rn, and more. These functions are invaluable for implementing a range of floating-point atomic operations in CUDA. The full list is available with the CUDA Math API Documentation.
