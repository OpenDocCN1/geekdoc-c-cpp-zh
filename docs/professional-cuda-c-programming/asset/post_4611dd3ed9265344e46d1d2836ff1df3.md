
```cpp
/*
 * If the cuRAND state hasn't been initialized yet, construct a cuRAND
 * host generator and pre-allocate memory to store the generated random
 * values in.
 */
curandCreateGenerator(&randGen,
    CURRAND_RNG_PSEUDO_DEFAULT);
cudaMalloc((void **)&dRand, sizeof(float) * dRand_length);
hRand = (float*)malloc(sizeof(float) * dRand_length);
}

if (dRand_used == dRand_length) {
    /* If all pre-generated random numbers have been consumed, regenerate a
     * new batch using curandGenerateUniform;
     */
    curandGenerateUniform(randGen, dRand, dRand_length);
    cudaMemcpy(dRand, dRand, sizeof(float) * dRand_length,
               cudaMemcpyDeviceToHost);
    dRand_used = 0;
}
```

```cpp
// Return the next pre-generated random number
return hRand[dRand_used++];
}
```

Working with the device API is slightly more involved and includes the following steps:

- 1. Pre-allocating a set of cuRAND state objects in memory for each thread to manage its RNG's state.
- 2. Optionally, pre-allocating device memory to store the random values generated by cuRAND if they are intended to be copied back to the host or be persisted for later kernels.
- 3. Initializing the state of all cuRAND state objects in device memory with a CUDA kernel.
- 4. Executing a CUDA kernel that calls a cuRAND device function (for example, curand_uniform) and generates random values using the pre-allocated cuRAND state objects. This step and the previous can be merged into a single kernel, but you must be careful that you do not reinvent the state objects on every kernel call if you want later values in the random sequences.
- 5. Optionally, transferring random values back to the host device memory pre-allocated in step 2 for retrieving random values.

Both of these works are illustrated by the replace-rand.cu example. In replace-rand.cu, there are three different functions for retrieving a random, single-precision-floating-point value between 0.0f and 1.0f. host_rand simply fetches a random value from the host’s system call. cuda_host_rand uses curRAND’s API to pre-generate a batch of random values and iterates over that batch in successive calls to cuda_host_rand. It keeps track of the number of values that were pre-generated and the number of values already used, and uses these to determine when a new batch must be generated. cuda_device_rand uses the curRAND device API to perform the same task by pre-allocating a set of curRAND state objects on the device, using those objects to generate batches of random numbers and managing the data in the same way that cuda_host_rand does.

One item of note with the curRAND implementation provided in this example is the jitter caused by creating bursts. While the majority of calls to cuda_host_rand and cuda_device_rand will be fast and consist of only an array reference and a counter increment, every call will need to regenerate a batch of random numbers using the GPU and will take much longer. This unexpected and unpredictable performance might be undesirable in certain applications. To end, a slightly modified example is provided in replace-streams.cu on wrox.com uses CUDA streams and the curRAND ability to bind to a CUDA stream and asynchronously run number generation on the GPU while the application is running. Given sufficient work in the host application to overlap with the random number generation work on the GPU, this enables a new batch of random numbers to be ready before the last batch runs out.

## Generating Randomness for CUDA Kernels

You can follow along with this example by downloading the sample code in rand-kernel.cu from Wrox.com. In contrast to the replace-rand.cu and replace-rand-stream.cu examples from the previous section, this example uses the cuRAND host and device APIs to generate random values for consumption by a CUDA kernel.

The host_api_function uses the cuRAND host API to pre-generate N random values calling a simple CUDA kernel that consumes those random values. Note that this requires multiple kernel calls from the host program and curRAND. The code snippet below shows the generation of random values into dOut using curandGenerateUniform, passing those values to host_api_kernel, and then transferring the final output of host_api_kernel from the device (dOut) to the host (hOut).

```cpp
// Generate random values from a uniform distribution
curandGenerateUniform(randGen, dOut, N);

// Consume the values generated by curandGenerateUniform
host_api_kernel<<block_grid, threads_per_block>>>(dRand, dOut, N);

// Retrieve outputs
cudaMemcpy(hOut, dOut, sizeof(float) * N,
cudaMemcpyDeviceToHost);
```

The device_api_function uses the cuRAND device API to perform on-demand generation of random values on the GPU. Note that it only requires a single kernel call that includes all cuRAND initialization and execution and also does not require CUDA device memory to be allocated to store the random values. The CUDA kernel is able to consume any generated random values. The code snippet below shows the execution of the device_api_kernel on the device states and the transfer of that kernel's final output from the device to the host.

```cpp
// Execute a kernel that generates and consumes its own random numbers
device_api_kernel<<block_grid, threads_per_block>>>(states, dOut, N);

// Retrieve the results
cudaMemcpy(hOut, dOut, sizeof(float) * N,
cudaMemcpyDeviceToHost);
```

## Important Topics in cuRAND Development

cuRAND is a simple and flexible API to use. The most important part of cuRAND-based projects is to understand your randomness requirements.

For example, selecting different RNGs or different distributions can drastically impact application performance, correctness, and results. Particularly for applications like Monte Carlo simulations which success is heavily based on the random values used, ensuring that you have properly configured your cuRAND environment to produce the type of random values you expect is important. There is no simple guide to the correct choice for the breadth of applications that rely heavily on randomness.

## CUDA FEATURES INTRODUCED IN CUDA 6

CUDA 6 adds two useful features to CUDA libraries: Drop-In Libraries and Multi-GPU Libraries.

### Drop-In CUDA Libraries

Drop-In Libraries enable seamless replacement of existing host libraries with certain CUDA libraries. As long as the CUDA library adheres to identical API to the host library, you can link your application directly to a Drop-In Library. In fact, with Drop-In Libraries the application code does not even need to be recompiled.

Only two CUDA libraries currently support being dropped into an existing application. NVBLAS is a subset of the cuBLAS library that can be dropped any Level 3 BLAS function. cuFFTW can be dropped to replace calls to the FFT library.

There are two ways to force the use of a Drop-In Library in place of BLAS or FFTW. First, you can link to the CUDA library rather than the standard library. For instance, if you have an application built from a source file `app.c` that uses the BLAS library, it would normally be using the following command:

```bash
$ gcc app.c -lblas -o app
```

If you wanted to recompile all BLAS 3 library calls in `app` with their cuBLAS equivalents, `app` would need to be rebuilt using the cuBLAS library by linking it in place of the BLAS library, as follows:

```bash
$ gcc app.c -lnvblas -o app
```

A second technique for using CUDA Drop-In Libraries on Linux environments is to force the CUDA library to be loaded before the host library. This can be done using the `LD_PRELOAD` environment variable, which directs the operating system to look for function definitions in the specified library before checking default locations. This is done using the `env` shell command, followed by the command you normally use to run the application. For instance, if `app` from the previous example took no line arguments and you did not want to recompile it, you could still replace all BLAS 3 routines with their CUDA equivalents using the following command to execute app:

```bash
$ env LD_PRELOAD=libnvblas.so ./app
```
