You can download the full example in simpleMultiAddBreadth.cu wrox.com. Figure 6-17 shows the timeline generated on a K40 device using only one hardware queue. There is no significant difference compared to the depth-first approach because Kepler's bidirectional scheduling mechanism eliminates false dependencies. If you run the same test on a Fermi device, you will see that overall performance of the breadth-first approach is worse than the depth-first approach. The false dependencies caused by contention on the host-to-device copy prevent any kernels from starting before all host-to-device transfers complete.

Therefore, for Kepler devices you do not need to worry about job order in most cases. On Fermi devices you need to be more aware of these issues and evaluate different scheduling options for your workload.
