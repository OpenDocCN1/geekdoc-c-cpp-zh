## Accessing Row-Major versus Accessing Column-Major

The first two kernels you will investigate were also used in the square case:

```
__global void setRowReadRow(int *);
__global void setColReadCol(int *);
```

You need to pay careful attention to the declaration of the rectangular shared memory array in each kernel. The length of the innermost dimension of the shared memory array tile is the same as the innermost dimension of the 2D thread block:

```
__shared__ int tile [BDIMX][BDIMY];
```

In the kernel setColReadCol, the length of the innermost dimension of the shared memory array tile is the same as the outermost dimension of the 2D thread block:

```
__shared__ int tile [BDIMX][BDIMY];
```

You can download the code for this example in the checkSmemRectangle.cu from Wrox.com. Compile it and check the bank results with the following nvprof metrics:

```
shared_load_transactions_per_request
shared_store_transactions_per_request
```

The results on a K40 are reported as follows:

```
Kernel:setRowReadRow(int*)
  1 shared_load_transactions_per_request 1.000000
  1 shared_store_transactions_per_request 1.000000
Kernel:setColReadCol(int*)
  1 shared_load_transactions_per_request 8.000000
  1 shared_store_transactions_per_request 8.000000
```

The store and load requests to shared memory are serviced by one transaction in the kernel setReadRow. The requests are serviced by eight transactions in the kernel setColRead. The Kepler K40 band width is eight words, and 16 4-byte elements in a column are arranged into banks, as illustrated in Figure 5-6; therefore, the operation reports an eight-way conflict.

## Writing Row-Major and Reading Column-Major

In this section, you will implement a kernel that writes to shared memory in row-major order and reads from shared memory in column-major order using a rectangular shared memory array. This kernel is applicable in real-world applications; it performs a transpose using shared memory to improve performance by maximizing-latency loads and stores, and coalescing global memory

The 2D shared memory tile is declared as follows:

```
__shared int tile [BDIMY] [BDIMX];
```

The kernel has three memory operations:

- Write to a shared memory row with each warp to avoid bank conflicts.
- Read from a shared memory column with each warp to perform a matrix transpose.
- Write to a global memory row from each warp with coalesced access.

The procedure for calculating the proper shared and global memory accesses is as follows. First, the 2D thread index of the current thread is converted to a 1D global thread ID:

```
unsigned int idx = threadIdx.y * blockDim.x + threadIdx.x;
```

This 1D, row-major mapping ensures that global memory accesses are coalesced. Because data elements in the output global memory are transposed, you need to calculate the new coordinate in the transpose matrix, as follows:

```
unsigned int irow = idx / blockDim.y;
unsigned int icol = idx % blockDim.y;
```

You initialize the shared memory tile by storing the global thread IDs to the 2D shared memory tile as follows:

```
tile[threadIdx.y][threadIdx.x] = idx;
```

At this point, the data in shared memory is stored linearly from 0 to BDIMX*BDIMY-1. Each warp performs row-major writes to shared memory, there is no bank-conflict during the write operation.

Now, you can access the shared memory data to transpose with the coordinates earlier. By accessing shared memory using swapped irow and icol, you can transpose the data using the global 1D thread IDs. As shown in the following snippet, a warp reads data elements from one column in shared memory, and performs a coalesced write to global memory.

```
out[idx] = tile[icol][irow];
```

The complete kernel code is as follows:

```
__global__ void setRowCol(int *out) {
    // shared memory
    __shared int tile[BDIMY][BDIMX];

    // mapping from 2D thread index to linear memory
    unsigned int idx = threadIdx.y * blockDim.x + threadIdx.x;

    // convert idx to transposed coordinate (row, col)
    unsigned int row = idx / blockDim.y;
    unsigned int ncol = idx % blockDim.y;

    // shared memory store operation
    tile[threadIdx.y][threadIdx.x] = idx;

    // wait for all threads to complete
    syncthreads();

    // shared memory load operation
    out[idx] = tile[ncol][row];
}
```

When you measure transactions with nsprof, it reports the following:

```
Kernel:setRowCol(int*)
1 shared_load_transactions_request 8.000000
1 shared_store_transactions_request 1.000000
```

The store operation is conflict-free and the load operation reports an eight-way conflict. You can print out the contents of the generated matrix with the following command:
$ ./smemRectangle 1

Notice that all of the elements in global memory are transposed.

## DynamicallyDeclared Shared Memory

Because dynamic shared memory can only be declared a 1D array, a new index is required to convert from 2D thread coordinates to 1D shared memory indices when writing by rows and reading by columns:

```
unsigned int col_idx = ncol * blockDim.x + irow;
```

Because ncol corresponds to the innermost dimension of the thread, this conversion yields column-major access to shared memory, which results in bank conflicts. The kernel code is as follows:

```
__global__ void setRowColDyn(int *out) {
    // dynamic shared memory
    extern shared int tile[];

    // mapping from thread index to global memory
    unsigned int idx = threadIdx.y * blockDim.x + threadIdx.x;

    // convert idx to transposed (row, col)
    unsigned int row = idx / blockDim.y;
    unsigned int col = idx % blockDim.y;

    // convert back to smem idx
    unsigned int col_idx = col * blockDim.x + row;

    // shared memory store operation
    tile[idx] = idx;

    // wait for all threads to complete
    syncthreads();

    // shared memory load operation
    out[idx] = tile[col_idx];
}
```

Shared memory size must be specified as part of the kernel launch:

```
setRowColDyn(cgrid, BDIMX * BDIMY * sizeof(int)>(d_C);
```

When you check the shared memory transactions via nvprof, the following is reported:

```
Kernel: setRowColDyn(int*)
1 shared_load_transactions_per_request 8.000000
1 shared_store_transactions_per_request 1.000000
```

The write operation is conflict-free, while the load operation reports an eight-way conflict. Dynamically allocating shared memory does not affect bank conflicts.

## Padding Statically Declared Shared Memory

You can use shared memory padding to resolve bank conflicts for rectangular shared memory. However, for Kepler devices, you must calculate how many padding elements are needed. For the case of coding, use a macro to define the number of padding columns added to each row:

```
#define NPAD 2
```

The padded shared memory is declared as follows:

```
__shared int tile[BDIMY][BDIMX + NPAD];
```

The setRowReadCol kernel is identical to setRowCol, except for the shared memory padding:

```
global_ void setRowColPad(int *out) {
    // static shared memory
    __shared int tile[BDIMY][BDIMX+NPAD];
    // mapping from 2D thread index to linear memory
    unsigned int idx = threadIdx.y * blockDim.x + threadIdx.x;
    // convert idx to transposed coordinate (row, col)
    unsigned int row = idx / blockDim.y;
    unsigned int col = idx % blockDim.y;
    // ... (rest of kernel)
}
```
