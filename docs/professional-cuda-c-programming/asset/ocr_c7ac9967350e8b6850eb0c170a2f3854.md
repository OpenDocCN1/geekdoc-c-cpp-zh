```
cudaMemcpyAsync(&gpuRef[offset],&d_C[offset],iBytes,
cudaMemcpyDeviceToHost, stream[i]);
}
```

Because these memory copies and kernel launches are asynchronous with respect to the host, the full
workload is distributed among streams without any blocking. However, dependencies between input
vectors, the kernel computation, and the output vector are maintained by placing data transfer
computation on the same stream.

This example also uses a blocking implementation to calculate a baseline performance for
comparison:

```
sumArrays<<<grid, block>>>(d_A, d_B, d_C, nElem);
```

You can download this example in the file SimpleMultiDepth.cu from Wrox.com. After
compiling, use nvvp to display the timeline of kernels and copies:

```
$ nvvp ./simpleMultiAddDepth
```

Figure 6-15 shows a typical timeline for Tesla K40. Eight hardware queues are used,
and four CUDA streams are used to overlap kernel execution with data transfer. Streamed execution
reaches nearly a 40 percent performance improvement over blocking execution on the default
stream. Figure 6-15 shows the following three types of overlap:

+   - Kernels in different streams overlapping with each other
- Kernels overlapping with data transfers in other streams
- Data transfers in different streams and in different directions overlapping with each other

Figure 6-15 also shows the following two types of blocking behavior:

+   - A kernel blocked by preceding data transfers in the same stream
- Data transfers from the host to the device blocked by a transfer of the same direction

Though data transfers from the host to the device are executed in four different streams, the time-
 show that they are executed sequentially because they are actually executed through the same
copy copy engine.

queues to one and rerunning. Figure 6-16 shows the timeline generated on the Tesla K40 device.
that there is no significant difference between Figure 6-16 (with one queue) and 6-15

Decreasing the number of work queues in the K40 creates a similar difference to a Fermi GPU: one
work queue and two copy queues. If you run the test on a Fermi GPU, you will find that
dependencies do exist. This is a result of Kepler's work dispatch mechanisms, implemented in the
Grid Management Unit (GPU). The GPU is responsible for managing and prioritizing work sent to
the GPU. Analysis performed by the GPU helps reduce false dependencies.
