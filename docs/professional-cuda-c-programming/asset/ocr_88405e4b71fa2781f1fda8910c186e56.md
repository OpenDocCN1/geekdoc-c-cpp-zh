Recompile the code with L1 cache enabled and run the following commands to measure the performance of these two kernels. The results are summarized in Table 4-5.

```
$ ./transpose 2
$ ./transpose 3
```

# TABLE 4-5: Effective Bandwidth of Kernels (L1 Cache Enabled)

| KERNEL | BANDWIDTH | RATIO TO PEAK BANDWIDTH |
|---|---|--|
| NaiveRow : Load rows/store columns | 64.16 GB/s | 36.13% |
| NaiveCol : Load columns/store rows | 81.64 GB/s | 45.97% |

The NaiveCol approach performs better than the NaiveRow approach. As explained earlier, one likely cause of this performance difference is that the strided reads into L1 cache by a certain access are not used at all, however, they remain in cache and may cause a cache hit for a future access. To verify this, try recompiling with L1 cache disabled (-xpt -dlcm=cg).

Run the following commands to obtain the performance of all kernels without L1 cache loading enabled. The results in Table 4-6 clearly show that disabling cache loading has a dramatic impact on strided access patterns.

```
$ ./transpose 0
$ ./transpose 1
$ ./transpose 2
$ ./transpose 3
```
