# Multi-GPU Libraries

Some applications contain sufficient parallelism to justify using more GPUs to improve performance. Chapter 9, "Multi-GPU Programming," covers more details about how to use native CUDA APIs for multi-GPU acceleration. It is important to discuss the use of GPUs by CUDA libraries as it requires less advanced understanding from the programmer and can lead to performance gains and better hardware utilization.

Multi-GPU Libraries (also known as the XT Library Interfaces) were introduced in CUDA 6. They enable a single library to be automatically executed across multiple GPUs. Because executing across multiple GPUs inherently partitioning the work across devices, a multi-GPU library can operate on datasets larger than GPU memory. As a result, even if your system has only one GPU, you will be able to operate on input data sizes that overflow the limit of global memory available by swapping data partitions in and out of the GPU.

In CUDA 6, multi-GPU execution is supported for some functions in cuFFT and for all Level 3 cuBLAS functions. As a performance optimization, cuBLAS Level 3 multi-GPU library calls automatically overlap memory transfers with kernel computation.

Using the multi-GPU libraries will require additional development effort. Download the example cufft-multi.cu from Wrox or follow along with the following code snippet. cufft-multi.cu runs the same example as cufft.cu using the CUFFT API to spread the work across all GPUs in the system.

```
int nGPUS = getAllGPUs(&gpu);
GPUS = nGPUS > 2 : nGPUS;
workSize = (size_t *)malloc(sizeof(size_t) * nGPUS);

// Setup the CUFFT Multi-GPU plan
cufffftCreate(&plan);
cufffftSetGPUs(plan, 2, gpu);
cufffftMakePlan(plan, N, CUFFT_C2C, 1, workSize);

// Generate inputs
generate_samples(N, &samples);
real_to_complex(samples, &complexSamples, N);
cuComplex *complexFreq = (cuComplex *)malloc(
sizeof(cuComplex) * N);

// Allocate memory across multiple GPUs and transfer the inputs into it
cufffftXtMalloc(plan, dcomplexSamples, CUFFT_FORMAT_INPLACE);
cufffftXtMempy(plan, dcomplexSamples, complexSamples,
CUFFT_COPY_TO_DEVICE);

// Execute a complex-to-complex 1D FFT across multiple GPUs
cufffftXtExecDescriptorC2(plan, dcomplexSamples, dcomplexSamples,
CUFFT_FORWARD);

// Retrieve the results from multiple GPUs into host memory
cufffftXtMempy(plan, dcomplexSamples, complexSamples,
CUFFT_COPY_DEVICE_TO_HOST);
```

The primary differences between cufft.cu and cufft-multi.cu are:

- - An extra step is to list all of the GPUs in the current system (using the provided function getAllGPUs) and configure the plan to use them (cuffXtSetGPUs)
- The use of cufftXtMalloc using cudaMalloc to allocate memory across multiple GPUs and as it with the same cufft plan. Note that the allocation information is stored in a cudaLibDesc object rather than a simpler pointer.
- The use of cufftXtMempy using cudaMempy to transfer data from host memory to multiple GPUs and back. Note that cufftXtMempy supports copying between a host array and a cudaLibDesc object well as between two cudaLibDesc objects. cufftXtMempy takes directionality just like cudaMemcpy, which is CUFFT_COPY_TO_HOST, CUFFT_COPY_TO_DEVICE, or CUFFT_COPY_TO_DEVICE used for multi-GPU execution with CUFFT. Any device locations are expressed as cudaLibDesc objects.
- The use of a cufftExecDescriptor library call rather than cufftExec* to perform the actual FFT transformation

This example can be built using:

```
$ nvcc -lcufft cufft-multi.cu -o cufft-multi
```

The CuFFT uses prior knowledge about FFT functions to distribute data between GPUs without breaking the validity of the FFT results (and will do something similar to cuBLAS across multiple GPUs as well).

Adding multi-GPU support requires careful attention during the porting process. If your application exposes selfish parallelism, then using the multi-GPU CUDA XT interfaces is much straightforward than developing your own custom multi-GPU implementation. The XT Interface for cuBLAS and cuFFT libraries is a powerful addition to the CUDA.

# A SURVEY OF CUDA LIBRARY PERFORMANCE

Implementing an application in CUDA is always motivated by performance. There, the usability of the CUDA libraries is meaningless if it sacrifices the performance acceleration that you expect from GPU execution. This section briefly covers existing literature on CUDA library performance relative to standard libraries. Keep in mind, with all performance results, your experimental might vary from the ones listed here depending on compilers, hardware, or other environment-factors.

# cuSPARSE versus MKL

Arguably, the gold standard for performance in sparse linear algebra is the Math Kernel Library (MKL). MKL is optimized for both dense and sparse linear algebra on multi-core Us using vector instructions. There is a large amount of literature comparing MKL and cuSPARSE on a variety of computational kernels.

As part of the CUDA 5.0 release, NVIDIA performed a comprehensive performance comparison between cuSPARSE and MKL across multiple computational kernels and multiple datasets. They found that cuSPARSE performance uplifted varied sparse-dense vector multiplication from 1.1 times to 3.1 times relative to MKL. Multiplying a sparse by multiple datasets yielded better relative performance, ranging from a little over 3 times speed to more than 12 times performance improvement. Finally, when comparing tridiagonal solvers between cuSPARSE and MKL, improvements of up to 17 times were reported, dending on dataset size and primitive types (see Figure 8-11).

For the CUDA 6.0 release, NVIDIA performed a similar performance review of the CUDA libraries. Results improved across the board, with sparse-dense vector multiplication achieving 1.8 times to 5.4 times speedup and performance improvements to triangular solvers, Incomplete-LU, and Cholesky pre-conditioners.

Clearly, the cuSPARSE library is highly usable, maintains the performance benefits expected of GPU hardware, and is continually being improved.

# cuBLAS versus MKL BLAS

Because MKL includes hand-optimized versions of the BLAS routines, it is a natural comparison for cuBLAS as well. cuSPARSE has received a large amount of scrutiny in its comparison to MKL.

In the CUDA 5.0 performance report, cuBLAS was evaluated across the full range of BLAS Level 3 routines. Speedup relative to MKL varied from -2.7 times up to -8.7 times speedup (shown in Figure 8-12). Deep investigation into GEMM demonstrated that cuBLAS maintains a significant performance advantage (> 5 times speedup) over MKL across a wide range of matrix sizes ranging from 512 x 512 to 4,096 x 4,096.

In the CUDA 6.0 performance report, NVIDIA reported 6 to 17 times speedup relative to the latest MKL BLAS. cuBLAS also maintained similar performance improvements relative to MKL for ZGEMM. With the introduction of the multi-GPU cuBLAS-XT library, NVIDIA demonstrated scalability of cuBLAS across multiple GPUs (shown in Figure 8-13).
