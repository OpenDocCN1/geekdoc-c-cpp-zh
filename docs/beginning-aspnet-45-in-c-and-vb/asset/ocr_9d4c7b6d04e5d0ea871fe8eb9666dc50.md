# How It Works

To expose a WCF service to the client-side script in your application, you need to register it in the Web.config file. In addition, you need to apply the correct attributes to the service class. Both actions are carried out for you when you add an AJAX-enabled WCF service to your project. If you look at the Web.config file you see something like this:

```
```xml
<system.serviceModel>
  <behaviors>
    <endpointBehaviors>
      <behavior name="NameServiceAspNetAjaxBehavior">
        <enableWebScript />
      </behavior>
    </endpointBehaviors>
  </behaviors>
  <serviceHostingEnvironment aspNetCompatibilityEnabled="true" multipleSiteBindingsEnabled="true" />
  <services>
    <service name="NameService">
      <endpoint address="" behaviorConfiguration="NameServiceAspNetAjaxBehavior" binding="webHttpBinding" contract="NameService" />
    </service>
  </services>
</system.serviceModel>
```
```

The service element defines a single service; the NameService in this case. If your site has more services available, you would add them to the same <services> element as the NameService. The binding and contract attributes tell the run time that this service is callable over HTTP and is implemented by the NameService class. The address attribute is left empty, which means the run time takes care of assigning an address. For more advanced scenarios you can enter a relative or absolute address here. The behaviorConfiguration points to a behavior called NameServiceAspNetAjaxBehavior defined under the behaviors node. WCF separates behaviors from the actual service definition so you can reuse the same behavior across multiple services. In this case, the behavior is created to enable the service to be called by a web page through the enableWebScript element.
