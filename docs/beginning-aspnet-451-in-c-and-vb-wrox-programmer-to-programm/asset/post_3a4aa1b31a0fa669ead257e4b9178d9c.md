## Nesting Master Pages

It is also possible to nest master pages. A nested master page is a master that is based on another master page. Content pages can then be based on the nested master page. This is useful if you have a website that targets different areas that need to share a common look and feel. For example, you can have a corporate website that is separated by departments. The outer master page defines the global look and feel of the site, including corporate logo and other branding elements. You can then have different nested master pages for different departments. For the example, the department’s section could be based on a master inside the marketing department’s, enabling each to have their own identity to the section of the site. VS 2013 has excellent Design View support for nested master pages, giving you a good look at how the final page will end.

Creating a nested master page is easy: select the Master Page check box when you add a master page as you do when you add a normal content page to the site. Then mark up ContentPlaceholder controls to the Content controls at locations that you want to override in the content pages. Finally, you choose your nested master page as the master for new content pages you create. Inside the content page, you only see the ContentPlaceholder controls from the nested master page, not from its parent.

## Master Page Caveats

Although master pages are great and save you a lot of work, you need to be aware of some caves.

For starters, the ASP.NET runtime changes the client ID of your controls in the page. This is the id attribute that is used in client script to access controls from JavaScript in browser and with CSS selectors. With normal ASPX pages, the server-side ID of a control is usually inserted as is in the final HTML. Finally, a Button with a server-side ID of Button1 in a normal ASPX page defined with this code:

```asp
<asp:Button ID="Button" runat="server" Text="Click Me" />
```

ends up with a client-side ID like this in the final HTML:

```html
<input type="submit" name="Button" value="Click Me" id="Button" />
```

However, the same button inside an <asp:Content> control ends up like this:

```html
<input type="submit" name="ct100$cpMainContent$Button" value="Click Me" id="cpMainContent_Button" />
```

The name attribute has been prefixed with the auto-ID of the master page (ct100) and both the name and the ID attributes the control of the ContentPlaceholder control (cpMainContent_).

This means that any client-side code that previously referred to Button should now refer to cpMainContent_Button.

Note that this is not just a master page problem. You’ll also run into this behavior in other situations; for example, when working with user controls (discussed in Chapter 8) and data-bound controls (discussed in Chapter 13 and onwards).

The second caveat is related to the first. Because the name and id of the HTML elements are changed, they could also be problematic for a single control, but once you have pages with lots of controls, this could impact the performance of your site. The problem gets worse with nested master pages, where both are appended to the ID. To mitigate the problem, you should keep the IDs of your Content controls as short as possible. To improve readability, this book uses longer names, like cpContent.

> NOTE ASP.NET 4 introduced a new feature called ClientID that helps minimize the problems typically associated with changing client-side. You will learn about this feature in Chapter 8.

Master pages enable you to define the general look and feel of your site in a single location, improving the consistency and maintainability of your site. However, there is another way to improve consistency: customize the behavior of the pages. You can do this with so-called base page, which is discussed next.

## USING A CENTRALIZED BASE PAGE

In Chapter 5 you learned that, by default, all ASPX pages derive from a class System.Web.UI.Page. This means all of your pages have the behavior defined in this class.

In some cases this behavior is not what you want and you need to add some stuff to the mix. For example, you may have the need to add some behavior to each and every page in your site. Instead of adding this behavior to each and every page, you can create a custom base page. All the pages in your site can then inherit from this intermediate page instead of the standard base page class. The right half shows a situation where the ASPX page inherits from a class BasePage, which in turn inherits from.

To have your pages inherit from this base page, you need to do two things:

- Create a class that inherits from System.Web.UI.Page in the App_Code folder of your website.
- Make the pages in your site inherit from this base page instead of the standard base page class.

In an upcoming exercise you will create a new base class inside the App_Code folder. For now, the sole purpose of this class is to control the Title of the page at runtime to stop pages from showing an empty or a meaningless title like "Untitled Page" making to the browser. Giving your pages a unique and helpful title helps the search engines index them, so it's recommended to always include a title in your web pages. Checking the title programmatically is relatively easy to do, which enables you to focus on the concept of inheritance rather than on the actual code. In the section that discusses themes later in this chapter, you will modify the base page once more, to retrieve the user's preference for a theme.
