## How It Works

EF comes with an object-relational designer (accessible in VS) that enables you to create an object model that is accessible through code based on the tables in your database. By adding tables to this designer, VS generates code for you to access the data in the database without writing a lot of code. The classes that are added to the designer are stored in the .edmx file and in .Code files.

The .tt files are T4 Template Files used to generate code dynamically—look at the data in the .edmx file and genres generated on the fly. If you look in the Code Behind of PlanetWrox.tt, you'll see two classes called Genre and Review, which are generated based on two tables from the database you added. Likewise, the Code Behind of PlanetWrox.Context contains a class that inherits from DbContext, the main object in EF that provides access to your database. In the preceding exercise, this class is PlanetWroxEntities (named after the .edmx file) and you use it to access the data in the tables you added to.

The designer is smart enough to detect the relationships in the database and is able to create the necessary relationships in code as well, as shown in Figure 14-2. The model defines two main object types, Review and Genre, both of which have collection counterparts Reviews and Genres, respectively. On English versions of VS the designer correctly pluralized the names of the Genre and Review tables (Reviews and Genres, respectively), making it easier to see what is a collection (Reviews) and what is a single instance of an object (Review). For other versions of VS, you have to adapt this logic using the Entity Designer.

After the model has been generated, you can execute LINQ queries to get data out of the underlying database. To access the data, you need an instance of the DbContext class, which is the base class for the model. Using block in the code. Using block (using in C#) is used to wrap code that creates a variable that must be disposed of (from memory) as you've done with it. Because the myEntities variable holds a connection to the SQL server, it's a good idea to wrap the code that uses it in a Using block, so the object is destroyed at the end of the block and the connection is released. This myEntities object exposes your data (such as reviews and genres) that you can use in:

## VB.NET

```
Using myEntities As New PlanetWroxEntities()
Dim authorizedReviews = From myEntities.Reviews
Where review.Authorized = True
Order By review.DateTime Descending
Select review
End Using
```

Under the hood, the team converts this LINQ query into its SQL counterpart and executes it against the underlying database. In this query, the variable review in the Clause is used to refer to the review in the other parts of the query (Where, Order By, and Select), enabling you to specify the select, filter, and ordering criteria.

What's important to remember is EF uses a mechanism called lazy loading, which means sub objects are not loaded until you tell them to. What this means is that in the previous example the Genre properties of the Review objects you've queried are null in C# and Nothing in VB.NET and not contain any data. As soon as your code accesses them, they are loaded by executing another query to the database. This can greatly improve performance if you don't need these objects. However, if you're sure you need them in your query beforehand, executing a separate SQL statement for each item results in a lot of overhead. In that case, you can preload the objects with the initial query. To express that you want to include these objects, use the Include method for the types you want to

## VB.NET

```
Dim authorizedReviews = From review In myEntities.Reviews.Include("Genre*")
Where review.Authorized = True
```

## C#

```csharp
var authorizedReviews = from review in myEntities.Include("Genre*")
```

With this addition to the query, the Review objects now have their Genre property correctly filled with data. This might seem a little counterintuitive and counterproductive at first, it is quite a nice feature. If you don't need the extra Genre property in a specific page, you don't have the performance hit of selecting and returning these objects. If you do need them, all you need to add is a single call to Include.

You may not conclude from these code snippets, that the variables authorizedReviews are still strongly typed and not just a variable with an undefined type.

> NOTE Strongly typed refer to the fact that the type is explicitly defined when it's declared. Once you've defined the type for a variable (using Dim in VB or the type in C#) you cannot change it anymore at run time. Strongly typed languages—such as C# and VB.NET—bring many advantages, including the ability to check the types being used at compile time, something that a weakly programming language cannot do.

Because the code didn't state the type for authorizedReviews (the example used Dim or var instead), NET needs a solution to determine the type. This is done by a concept called type inference, where the compiler is to infer the type of a variable by looking at the right side of the assignment. In C#, the compiler sees that a list of Review objects will be returned from the query, and quickly types the authorizedReviews as a generic IQueryable(Of Review) in VB.NET syntax or IQueryable<Review> in C#. Although this looks a scary and incomprehensible at first, it becomes much easier to understand if you simply read it as "a bunch of Review objects of the type instead of using var or a statement without a data type, but exceptions do exist, as you'll see when anonymous objects are discussed.
