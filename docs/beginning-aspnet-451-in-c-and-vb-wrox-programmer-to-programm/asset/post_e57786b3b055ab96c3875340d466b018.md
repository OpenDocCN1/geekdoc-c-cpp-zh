When you enter the details of a picture and click Insert, the ListView calls the InsertMethod, defined as follows:

```VB.NET
Public Sub ListView_InsertItem(QueryString("PhotoAlbumId") photoAlbumId As Integer)
    Dim picture As New Picture()
    TryUpdateModel(picture)
    If ModelState.IsValid Then
        Using myEntities As New PlanetWroxEntities()
            picture.PhotoAlbumId = photoAlbumId
            myEntities.Pictures.Add(picture)
            myEntities.SaveChanges()
        End Using
    End If
End Sub
```

```C#
public void ListView_InsertItem(QueryString("PhotoAlbumId") int photoAlbumId)
{
    Picture picture = new Picture();
    TryUpdateModel(picture);
    if (ModelState.IsValid)
    {
        using (var myEntities = new PlanetWroxEntities())
        {
            picture.PhotoAlbumId = photoAlbumId;
            myEntities.Pictures.Add(picture);
            myEntities.SaveChanges();
        }
    }
}
```

This is almost the same as the code that was used to create a new photo album. The difference here is another QueryString attribute that is populated with the ID of the photo album. The Include Key Columns option in Entity Framework you enabled earlier in this chapter has given you a PhotoAlbumId property on the Picture class that enables you to directly set the ID of the PhotoAlbum (which you retrieved from the query string). This in turn relates the picture in the database to a specific photo album in the PhotoAlbum table. If you hadn't enabled that option, the property would not have been there, and you would have had to assign a PhotoAlbum instance to the PhotoAlbum property of the picture by querying the photo album from the database based on its ID. Using the Foreign Key Columns makes this process a lot easier because you can simply assign the ID of the album you want to add this picture to.

When you click the Delete button for picture, the ListView finds the DeleteMethod that looks as follows:

```vb.net
Public Sub ListView_DeleteItem(ByVal id As Integer)
    Using myWeb As New PlanetWroxEntities()
        Dim picture = (From p in myWeb.Pictures
                       Where p.Id = id
                       Select p).Single()
        myEntities.Pictures.Remove(picture)
        myEntities.SaveChanges()
    End Using
End Sub
```

```csharp
public void ListView_DeleteItem(int id)
{
    using (var entities = new PlanetWroxEntities())
    {
        var picture = (from p in entities.Pictures
                        where p.Id == id
                        select p).Single();
        entities.Pictures.Remove(picture);
        entities.SaveChanges();
    }
}
```

This method creates a new PlanetWroxEntities instance and then uses a LINQ query to find the correct picture. It then calls the Remove method on the Pictures collection and sends it to the fetch. then calls SaveChanges. But how does the ListView know how to populate the ID parameter of this method? The answer is in the DataKeyNames attribute defined on the ListView:

```asp

```

The ListView stores the ID of each individual item in ViewState. Then when you click the Delete button, it's alert to extract the correct ID for the picture you want to delete, which then it sends to the DeleteItem method in the Code Behind.

The final part of this exercise you need to take a look at the CSS code you added to the theme's CSS files to display the items in an organized way. By setting the class attribute of the <ul> control to that list:

```css
.ItemContainer
{
  width: 600px;
  list-style-type: none;
  clear: both;
}
```

The first property sets the entire width of the list to 600 pixels and the second declaration removes the bullet from the items in the list. Each item in the list is then displayed within a <li> element, to which the following CSS is applied:

```css
.ItemContainer li
{
  height: 300px;
  width: 200px;
  float: left;
}
```

Each item gets a forced width of 200 pixels. The `float` property tells the <li> elements to float next to each other. Within the parent area of 600 pixels you can fit three <li> elements of 200 pixels each, causing the fourth and further elements to be placed on their own line. This is a great alternative to presenting data with HTML tables, which generally needs a lot markup to achieve the same effect.

Finally, each image within the <li> element gets a forced width of 180 pixels and 10 pixels of margin at the top and bottom, 20 pixels on the right (to create some room between the images), and none at the left side:

```css
.ItemContainer img
{
  width: 180px;
  margin: 10px 20px 10px 0px;
}
```

In the DarkGrey, the width of the ItemContainer is set to only 400 pixels. This way, the <div> is just enough to display two images side by side.

The code in the ListView uses Bind and Eval statements to get data in and out of the Picture objects that you're assigning to the controls. ASP.NET 4.5 introduced a new way to set up these bindings. See how to use these bindings next.

# Using Strongly Typed-Data Controls

When you added the code to the ListView, you used Bind and Eval statements like this:

```asp
<asp:TextBox ID="ToolTip" runat="server" Text='<%# Bind("ToolTip") %>' />
<asp:Label ID="ToolTip" runat="server" Text='<%# Eval("ToolTip") %>' />
```

As you learned in the "How It Works" section, Bind is for two-way binding (for insert and edit scenarios) and Eval is for read-only scenarios. Notice how the name of property is placed between quotes. Using literals makes your code more prone to errors. First of all, it's easy to miss the name. Because a string cannot be checked by VS at development time, you won't notice this error until you view the page in the browser.

Fortunately, there is a solution. The data-bound controls (such as the ListView, Repeater, GridView, DetailsView, and FormView) have been extended with an ItemType property that you can point to the type of object you're assigning. In this example, this type would have been Picture. Once you've set this property, the data-bound control gets two new properties, Item and BindItem, that are of the type you assigned. The first one serves as a replacement for Eval and the second replaces Bind. When you miss a name of property, or rename it, you will get an error in the Error List, giving you the chance to fix the problem.

Although this is an excellent feature that will help you write better code, you can only use this solution when working with a strongly typed object such as Picture from an EF model, or other classes you or third-party developers create. It doesn't work in situations such as:

- When using the DataSource control. This control an object under the head that doesn't expose strongly typed properties that map to columns (such as ToolTip and Description), and as such you cannot access these columns or properties through the Item and BindItem properties.
- When using anonymous objects. Because the anonymous object doesn't have a name, you cannot assign its name to the ItemType property.
