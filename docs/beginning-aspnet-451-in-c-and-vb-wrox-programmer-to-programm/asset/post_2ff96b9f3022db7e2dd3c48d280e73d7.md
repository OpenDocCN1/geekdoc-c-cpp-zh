Before you implement the base class, you need to know more about the ASP.NET life cycle, an important concept that describes the process a web page goes through when requested by a browser.

# An Introduction to the ASP.Net Life Cycle

When you think about how a page is served by a server and the browser of this process as the life cycle of a page, you can probably come up with a few important moments in the page's life. Similarly, when the page has sent its HTML to the browser, it may seem to end. However, more interesting events are going on in the page's life cycle. The following table describes eight broad phases the page goes through. In each phase, one event is raised that enables a developer to hook into the page's life cycle and perform actions at the right moment. You see an example of this in the next exercise.

| PHASE | DESCRIPTION |
| :--- | :--- |
| Page request | A request to an ASPX page starts the life cycle of that page. When the web server is able and allowed to return a cached copy of the page, the entire life is not executed. In all other situations, the page enters the start phase. |
| Start | In this phase, the page gets access to properties like Request and Response that are used to interact with the page's environment. In addition, during this phase the PreInit event is raised to signal that the page is about to go into the initialization phase. You use this event later to set the theme of a page. |
| Page initialization | During this phase, the controls you have set up in your page or added programmatically become available. Additionally, the Page class fires three events: Init, InitComplete, and PreLoad. |
| Load | During this phase, the control properties are loaded from View State and Control State during a postback. For example, when you choose the selected item in a DropDownList and then cause a postback, this is the moment where the correct item gets preselected in the drop-down list again, which you can then work with in your server-side code. Also, during this phase the page raises the Load event. |
| Validation | In the validation phase, the Validation controls used to validate user input are processed. You learn about validators in Chapter 9. |

| PHASE | DESCRIPTION |
| :--- | :--- |
| Postback event handling | During this phase, the controls in your page may raise their own events. For example, the DropDownList may raise a SelectedChanged event when the user has chosen a different option in the list. Similarly, a TextBox may raise the TextChanged event when the user has changed the text before posted back to the server. When all event processing is done, the page raises the LoadComplete event. Also during this phase the PreRender event is raised to signal that the page is about to render the browser. Shortly after that, SaveStateComplete is raised to indicate that the page is storing all the relevant data for the controls in View State. |
| Rendering | Rendering is the phase where the controls (and the page itself) output their HTML to the browser. |
| Unload | The unload is really a clean-up phase. This is the moment where the page and controls can release resources they were holding on. During this phase, the Unload event is raised so you can handle any cleanup you may to do. |

One thing that's important to realize is that all these events fire at the server, not at the client. So, even if you say, the text of a text box at the client, the TextChanged event of the TextBox control will fire at the server after you have posted back the page.

Now you may wonder why you need to know all of this. The biggest reason is to have some understanding of the page life cycle is that certain actions can be performed at specific stages in the page life cycle, as you'll see. To understand the ASP.NET page life cycle, you need to know a little more about controls, state, events, and so on. Therefore, you'll revisit the page life again in Chapter 15 where you get a good look at all the different events that fire, and in what order.

In the next exercise, you use the PreRender event of the Page to set the title. Because a developer could set the page programmatically during many events, checking for a correct title should be done as late as possible in the page life cycle, which is PreRender the best event for this.

# Implementing the Base Page

Implementing a base page is pretty easy: all you need to add a class to your App_Code folder, and you're done. It's a bit more difficult is to make sure each page in your site inherits from this base page instead of using the System.Web.UI class. Unfortunately, there is no way to configure the application to this for you automatically when using Code Behind, so you need to modify each page manually. Visual Studio makes it a little easier for you enabling you to export a page template that already contains your code. In the next exercise, you add a base page to the site and in a later exercise you see how to export a form to a template so you can add files that use the base page in no time.

# TRY IT OUT Creating a Base Page

- 1. Right-click the App_Code folder in the Solution Explorer and choose Add Add New Item. Select Class in the Templates and name the file BasePage.
- 2. Clear the contents of the file, and then add the following code:
```vb.NET
Public Class BasePage
    Inherits System.Web.UI.Page

    Private Sub Page_PreRender(sender As Object, e As EventArgs) Handles Me.PreRender
        If String.IsNullOrEmpty(Me.Title) OrElse Me.Title.Equals("Untitled Page", StringComparison.CurrentCulture) Then
            Throw New Exception("Page title cannot be empty string.")
        End If
    End Sub
End Class
```
```csharp
using System;
public class BasePage : System.Web.UI.Page
{
    private void Page_PreRender(object sender, EventArgs e)
    {
        if (string.IsNullOrEmpty(this.Title) || this.Title.Equals("Untitled Page", StringComparison.CurrentCulture))
        {
            throw new Exception("Page title cannot be empty string.");
        }
    }
    public BasePage()
    {
        this.PreRender += Page_PreRender;
    }
}
```
- 3. Save the file and open the Login page. Open the Code file and change the Inherits code (the colon in C#) so the login page inherits from the BasePage you created:
```vb.NET
Partial Class Login
    Inherits BasePage
End Class
```
```csharp
public partial class Login : BasePage
{
}
```
- 4. Save the page and request it in the browser by pressing Ctrl+F5. If you haven't changed the title of the page, or add one if needed, you will be greeted by the error shown in Figure 6-8 in your browser.
img/9e033e3b9560597824f8b229416d8bb.png
- 5. Go back to VS and open the login page in Markup View. Locate the Title attribute in the @ Page directive (or add one if it isn't) and set its value to Log in Planet Wrox. The following snippet shows the VB.NET version of the @ Page directive but the C# version is almost identical:
```vb
<Page Title="Log in Planet Wrox" Language="VB"
MasterPageFile="~/Pages/Frontend.master" AutoEventWire="false"
CodeFile="Login.aspx.vb" Inherits="Login">
```
- 6. Repeat steps 3 and 5 for all the pages in your site. To make this a quicker, you can use Find and Replace to quickly replace all the occurrences of System.Web.UI.Page with BasePage. Make sure you don't accidentally editing the BasePage in the App_Code folder itself. To prevent this from happening, make sure you search only in Code Behind files, like this:
- Open the Replace dialog box, press Ctrl+Shift+H or select Edit Find Replace in Files.
- In the Find what box, enter System.Web.UI.Page. In the Replace text box, enter BasePage.
- Under the Look dropdown, make sure that Entire Solution is selected.
- Expand the Find section and look in the Look at These Files text box, enter *.aspx.vb or *.aspx.cs depending on the language you use. This leaves the BasePage file, which has a single extension of .vb or .cs, alone.
- Click Replace All and then click Yes to confirm the Replace operation.
