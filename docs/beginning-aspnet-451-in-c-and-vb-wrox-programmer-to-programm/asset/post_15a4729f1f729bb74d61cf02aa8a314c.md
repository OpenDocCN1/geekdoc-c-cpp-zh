## How It Works

Two important parts are worth examining in this exercise. The first part is the ASP.NET run hides the "Yellow Screen of Death" with the error details from the user with use of custom error pages. Second, it helps you protect potentially private data like passwords or information about database connections that might end up in the error message. Second, it shields your users from cryptic error messages they probably don't understand anyway and gives you the chance to display a good-looking error page that integrates with the site's look and feel.

The only thing you need to do to make this work is enable custom errors in the Web.config file and provide one or more pages you want to display for errors that may occur in your site. The configuration element lets you set different pages for different exceptions:

```xml
<customErrors mode="On" redirect="/Errors/OtherErrors.aspx"
  redirectMode="ResponseRewrite">
  <error statuscode="404" redirect="/Errors/Error404.aspx" />
</customErrors>
```

When .NET encounters a 404 error (when you request a page that cannot be found), the contents of the Error404.aspx page are shown. The name and content of this page are completely up to you, giving you the option to provide your own explanation to the user what went wrong. Note that this works only for files that are registered with ASP.NET, .aspx files. It does not work out of the box for .html files or when you are not using the Integrated Pipeline IIS, Microsoft's web server. You may also use the Integrated Pipeline IIS in the next chapter.

This exercise contains two key elements to SEO. First, notice how the redirectMode is set to ResponseWrite. The other option is ResponseRedirect. Remember the difference between Server Transfer and Response.Redirect from Chapter ?? These two settings are on the same principles. If you set redirectMode to ResponseRedirect, the browser (and thus a search engine) is redirected to the error page. The error then returns a 404 code so the search engine thinks the page could not be found. If, however, you set redirectMode to ResponseWrite, the originally requested page contents of the Error404.aspx page are streamed to the browser. This enables search engines to correctly update their indexes. The downside of ResponseWrite is that you can't use Page in the profile or as a page it is based on. As you saw earlier, the workaround is to set the code in the Code Behind of Error404.aspx. That code sets the HTTP status code to 404 to indicate the page could not be found on the server. Without these two lines of code, search engines will think the page doesn't exist and will keep to index it.

Notice that only the custom error page is redirected to its own page. All other exceptions cause the generic OtherErrors.aspx to be loaded. You can, however, add multiple <error /> elements to the <custom-Errors> element, each for a different status code: http://support.microsoft.com/default.aspx/kb/94389

Note the call to Response.TrySerializeCustomErrors. This tells IIS that it should not try to render its own custom error pages. Without this setting, you may get IIS's generic error pages instead of the one you defined. Here you won't notice the difference with IIS Express, so this won't come into play until you deploy your site to a production version of IIS as in the next chapter.

The main part of this exercise is the code in Global.asax that fires when an unexpected exception occurs. In this case, the Application event handler is triggered. With this handler, you can retrieve the exception that occurred with this code:

### VB.NET

```vb
If HttpContext.Current.Server.GetLastError() Is Not Nothing Then
  Dim myException As Exception =
    HttpContext.Current.Server.GetLastError().GetBaseException()
```

### C#

```csharp
if (HttpContext.Current.Server.GetLastError() != null)
{
  Exception myException =
    HttpContext.Current.Server.GetLastError().GetBaseException();
}
```

## The Basics of Debugging

Debugging is the process of finding and fixing bugs in your code. Although that may sound easy, it often isn't. Some bugs are obvious and easy to spot and thus easy to fix. Others are much harder to find and require knowledge about the execution environment of your program. The debugging tools in Visual Studio help you understand this execution environment by giving you direct access to the inner workings of your program or web page.

Debugging with VS is like snapping your fingers to stop time. When you do that, everything halts, except you can walk around the code, investigate variables, look into objects, try methods, and execute new code. To tell VS what to halt, you need to set one or more breakpoints in your code. When the breakpoint is about to be executed, VS stops the execution of the application so you can diagnose the code and its environment.

You set a breakpoint by pressing F9 on the code where you want to halt. Instead of the F9 shortcut key, you can also click the margin of the code, where the big dots appear in Figure 18-6, or you can choose Debug-Toggle Breakpoint from the main menu. Press F9, clicking the point in the margin, or choosing the menu item again toggles the presence of the breakpoint. To clear all breakpoints in your entire website, press Ctrl+Shift+F9.

To give you an idea of how debugging works, and to help you, the following exercise shows the basics of debugging. Later parts of this chapter give you a detailed look at the numerous debugging tools and windows that shift with VS.
