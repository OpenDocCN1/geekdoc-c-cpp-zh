# How It Works

Just like the login controls, the WSAT eventually tells the provider you configured in the Web.config file. In the case of the Planet Wrox application, it talks to the DefaultMemberProvider and the DefaultRoleProvider, which in turn talks to a SQL Server LocalDB database identified by connection string. The users and roles you create are stored in tables within the database. Users that you create end up in the same location as created with the CreateUserWizard. In fact, the WSAT uses the CreateUserWizard to create new accounts. Any user that you use in the WSAT is able to log in using your login Login page. For example, you can use the Manager account you created in this exercise to log into the site and access the Management folder.

To use the role you created in this exercise, you have a few options at your disposal. First, you can use the role name to access specific users in your web application through settings in the Web.config file. Secondly, you can use the role in controls like the LoginView to present different content to different users. Finally, you can use the role API to check whether the current user is in a specific role. This gives you fine control over the content or functionality you offer to certain privileged users.

You see how to block access to the Management folder and modify the LoginView in the next section; using the Role API is discussed in a later exercise.

# Configuring the Web Application to Work with Roles

On the Security page of WSAT, you saw a section called Access Rules. This part of the tool enables you to block or open resources in your site. It enables you to define rules as “This folder is blocked for anyone except for users in the Managers role,” or “Anyone can access this file, except for the users in the Members role and the Join account.” The tool is quite intuitive, so it isn’t difficult to set the different rules. However, it has one downside: it stores the security settings in separate Web.config files, one for each subfolder you configure.

This makes somewhat difficult to get an overview of all the different settings in your site. Fortunately, ASP.NET allows you to configure the same settings in the main web.config using <location> elements. A <location> element has a path attribute that points to a file or folder you want to configure differently. You can use the <location> element for many (but not all) settings from Web.config as well (for example, you could set the theme attribute of the <pages> element for the Management folder in the main web.config). For the following exercise, you only set the children of <location> to those related to security.

# TRY OUT Blocking Access to the Management Folder

Obviously, you don’t want to manage with reviews and generics that you have posted on your website. Therefore, it’s important to block access to the Management folder to anyone except managers assigned to the Managers role. In this exercise, you see how to modify Web.config to block the folder so only the user account you assigned to the Managers role can easily access this folder and the files it contains.

1. Open the Web.config file at the root of the site. Scroll all the way down to the closing </configuration> tag and right before you type a <location> element. Add a path attribute to the element and set its value to Management. Note that IntelliSense kicks in to help you complete the element.

```xml
<location path="Management">
<system.web>
<authorization>
<allow roles="Managers" />
<deny users="*" />
</authorization>
</system.web>
</location>
```

2. Save and close the Web.config file.
