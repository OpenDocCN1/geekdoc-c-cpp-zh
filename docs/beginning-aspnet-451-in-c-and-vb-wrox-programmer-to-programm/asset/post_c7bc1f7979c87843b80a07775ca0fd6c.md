# How It Works

When you dragged the user control onto the design surface of the master Page, VS performed two tasks: first it added the @ Register directive to the page where to look for the user control. It then added the control declaration right below the drop-down list.

When the page loads, the ASP.NET runtime executes the control declaration and renders the output of the control at the specified location. In this example, the Panel, the <asp:Image element, and the Image are inserted in the sidebar region of the page. If you look at the HTML for the page in the browser, you see the following code:

```
<div id="Banner_VerticalPanel">
<a href="http://p2-worx.com" target="_blank">
<img id="Banner_Image" src="Images/Banner120x240.gif"
alt="this is a sample banner" />
</a>
</div>
```

The Panel has been transformed into an HTML <div> element and the Image control into an <img> element. The AlternateText property has been changed to an alt attribute. Because the anchor <a> was defined with plain HTML in the user control, it ends up exactly as you write it.

Notice how the id of the panel has changed from VerticalPanel to the clientid_Banner_VerticalPanel. This is necessary to give the <div> a unique client-side id attribute that is used in client-side scripting. The same has happened to the id of the <img> element. You see more about this in later section of this chapter.

When you add a control to a page, VS usually refers to the control using a relative path. In this exercise, this path contains dots (...) to indicate the parent folder, followed by the Controls folder, and finally by the name of the control:

```
<% Register Src="../Controls/Banner.ascx" TagName="Banner" TagPrefix="uc" %>
```

By changing the two dots to the tilde, it becomes easier to move your pages in your site because the Src attribute always points to the Controls folder at the application’s root, no matter where the page consumes the control. If your Src attribute already contained the tilde, you don’t have to change anything.

Though the tilde syntax makes your pages with user controls a little easier to manage, there is an even easier way to register your user controls sitewide.

# Sitewide Registration of User Controls

If you have a control that you expect to use often on separate content pages in your site, the banner in the previous examples you can register the control globally in the Web.config file. This way it becomes available throughout the entire site, without the need to register it on every page. The following exercise shows how to do this.

# Registering User Controls in the Web.config File

### TRY OUT

In this exercise, you register the Banner.ascx user control in the Web.config file. You can then remove the @ Register directive from the master page because it isn't needed anymore. After you have changed the Web.config file, adding the same user control to other pages will no longer add the @ Register directive to the page.

- 1. Open the Web.config file from the root of the site. If you're familiar with versions of ASP.NET prior to .NET 4, you will find the Web.config looking worry empty. But don't worry; the functionality it has not been removed from .NET. The configuration information placed in the website's Web.config file has now been moved to the central Web.config and Machine.config files that apply to the entire machine instead. This gives you a much cleaner configuration file, making it easy to focus on your own stuff that you put in there.

- 2. Locate the <pages> element you used in Chapter 6 to apply the theme, and within its tags add the following code that contains a <controls> element with a child <add/> element. You may need to change the self-closing tag of the <pages> element to a full closing tag.

- 3. Save the changes and close the file.

- 4. Open the master page again in Markup View and locate the Banner control in the sidebar area. Change ucl to Wrox:

```
<pages theme="Monochrome">
  <controls>
    <add tagPrefix="Wrox" tagName="Banner" src="~/Controls/Banner.ascx" />
  </controls>
</pages>
```

```
<Wrox:Banner ID="Banner1" runat="server" />
```

If the declaration for your user control has its own closing tag, VS updates the closing tag for you automatically:

```
<Wrox:Banner ID="Banner1" runat="server"/></Wrox:Banner>
```

- 5. Scroll all the way up in the master page file and remove the entire line with the @ Register directive.

- 6. Save and close the master page.

- 7. Open Default.aspx again in your browser. Note that the banner is still present in the sidebar area.

> **COMMON MISTAKES** If you get an error, verify you added the correct code at the right location to the Web.config file. Also make sure that you changed ucl to Wrox in the control declaration and that you deleted the @ Register directive from the master page.

# How It Works

Without the @ Register directive in the master page, the ASP.NET runtime scans the Web.config file for controls that have been registered there. It then finds the registration of the Wrox:Banner control so it is able to successfully find the file using the src attribute and add it to the page hierarchy.

With the control registration added to the Web.config file, it is much easier to move or rename the control. Instead of finding and replacing the @ Register directive in all pages that use, the only thing you need to change is the registration in the Web.config file. When you make a change, all pages using the control will automatically find the new location or name.

Useful as user controls, they have a few caveats that you need to be aware of.

# User Control Caveats

Earlier you saw that the ID of the Panel control that you added to the page was modified by the ASP.NET runtime. Instead of getting a <div> element with its id set to VerticalPanel, you got the following id:

```
<div id="Banner1_VerticalPanel"></div>
```

In many cases, this is not problematic because you often don't need the client id. However, if you need to access this control from client-side JavaScript or CSS, it's important to understand why this id is modified.

# Understanding and Managing Client IDs

By design, all elements in an HTML page need to be unique. Giving them an id attribute is not required, but if you do so, you avoid conflicts in the final HTML code of the page, ASP.NET ensures that each server-element control gets a unique id by prefixing it with the name of its naming container. Within a panel container all elements should have unique IDs. VS warns you when you try to add a control that doesn't have a unique ID. For example, you get an error when you try to add a second panel to a page with an id of VerticalPanel or one in the master page and another in the content of the page; potentially, you could end up with two client:<div> elements with an ID of VerticalPanel. To avoid this problem, ASP.NET prefixes each element with the ID of its nearest container. For the panel inside the user control it means it's prefixed with Banner1, the server-side ID of the user control in the master page.

You can use the ClientID of control to get its full client-side id. The following snippet shows how to display the ClientID of the Panel control on a fictitious Label control within the Banner.ascx user control:

```
VB.NET
Label.Text = VerticalPanel.ClientID
```

```
C#
Label.Text = VerticalPanel.ClientID;
```
