Now SQL Server and your user accounts are configured correctly, the final step is to configure the website to use this user account.

- 1. Open the Web.config file of the Planet Wrox application from the C:\BegASP\Release folder.

- 2. Modify the <connectionStrings> string so it ends like this:

```xml
<connectionStrings>
  <add name="PlanetWroxConnectionString" connectionString="Data Source=ServerName;Initial Catalog=PlanetWrox;Trusted_Connection=True" providerName="System.Data.SqlClient" />
  <add name="PlanetWroxEntities" connectionString="metadata;res:*/App_Code.PlanetWrox.csdl;*/App_Code.PlanetWrox.ssdl;*/App_Code.PlanetWrox.msl;provider connectionString="Data Source=ServerName;Initial Catalog=PlanetWrox;Trusted_Connection=True" providerName="System.Data.EntityClient" />
</connectionStrings>
```

In your configuration, each connection string should be on a single line. Don't forget to replace the ServerName in the Data Source with a valid name. Depending on your server and configuration, this could be as simple as (local) or \.SqlServer to point to a SQL server on the network called DatabaseServer, or something like DatabaseServer\Sql2012 that points to an instance called sql2012 on a machine called.

- 3. Save the changes and open the site by starting your browser and going to http://localhost. Everything will still work as expected, but the site no longer uses the database in the App_Data folder; it uses the SQL Server defined in your connection strings instead through Windows Authentication, as the Trusted_Connection=True attribute in the connection string.

- 4. To make this new connection string remain in future updates of the site, you should also add it to the file Web.local.config in the website in Visual Studio.

If you get an error when browsing the site, you may need to turn off custom errors in the Web.config file (or set it to RemoteOnly) to see the actual error message. Possible reasons for the error are an incorrect server name in the connection string and an incorrectly configured database membership for the configured account.

Once you find out the correct account and configured SQL Server correctly, using Windows Authentication isn't hard. In fact, your connection string becomes a little easier and more secure, because you don't need to use a username and password in it anymore.

# CONFIGURING APPLICATION SERVICES

In this book you learned that the ASP.NET application services use a SQL Server database. You also saw how to make your own website and the application services use the same database.

If you choose not to merge the database and the one used by the applications, your site uses two databases: your one and one aspnetdb.mdf. However, you can still merge them later if you want. In earlier versions of ASP.NET, this involved quite a bit of work, including changes to the Web.config file and running command-line tools. However, with the updated providers this is now pretty simple. Follow these steps to let the application services use your own database:

- 1. First, make sure the application services point to a connection you want to use. By this, you need to use the connectionConnectionString to a connection string defined in your config file. The following example shows how to do this for the Membership, but the other services follow a similar pattern:

```xml
<membershipProvider="DefaultMembershipProvider">
<providers>
<add name="DefaultMembershipProvider"
type="System.Web.Providers.DefaultMembershipProvider,System.Web.Providers,Version=1.0.0.0,neutral,PublicKeyToken=31bf3851"
enablePasswordReset="true"
requiresQuestionAnswer="false"
requiresUniqueEmail="false"
maxInvalidPasswordAttempts="5"
RequiredPasswordLength="7"
minRequiredAlphanumericCharacters="1"
passwordAttemptWindow="10"
applicationName=""/>
</providers>
</membership>
```

Notice how connectionName matches the connection string PlanetWroxConnectionString1, defined elsewhere in the config file.

- 2. Make sure the account used by the web server has permissions to alter the database schema. You can accomplish this by adding the account to the db_ddladmin group, shown in Figure B-6. This grants the account permissions to execute Data Definition Language statements, which means you can create and alter other objects in the database.

- 3. Restart IIS. To do this, start the IIS Server Manager (type inetmgr in the Start menu or Start screen), click your server name, and then click Restart in the Actions panel on the right. To minimize impact on the server, you could recycle the application pool used by the site by right-clicking and choosing Recycle.

- 4. Browse to your site and register the Login page. Try to log in with a username and password. At this stage, the .NET runtime will modify the database and add the necessary tables to it. If you look at the database defined in the connection string used by the membership services, you'll notice it now contains the tables that are used by Membership, Roles, and Profile.

- 5. For security reasons, you should remove the account from the db_ddladmin group because Membership at run time does not require these permissions.
