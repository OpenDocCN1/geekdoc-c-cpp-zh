## How It Works

Identical to the other data-bounds, you hook up the DetailsView to a data source control by setting the DataSourceID property. Because you are working with a SqlDataSource control for the page, you can see that. DetailsView exposes different views, for read-only, and edit modes. By setting the DefaultMode to Insert, you force the control to switch to insert mode, which means you automatically get a UI for entries details of the control, and Insert and Cancel links. The DetailsView control is actually pretty smart. When you point it to the SqlDataSource control, it is able to figure out the DataKeyNames property, which you set it to Id:

```
<asp:DetailsView Id="DetailsView" runat="server" AutoGenerateRows="False" DataKeyNames="Id" DataSource="SqlDataSource" ... />
```

It also understands that the Id is a column in the database, and therefore hides it in the Insert screen (shown in Figure 13-6) by setting InsertVisible to False. The database generates it automatically, there is no point in letting the user enter a value for it.

When you enter values and click the Insert link, a process similar to updating with the Grid takes place. The DetailsView gets the relevant information from the page's controls (the Name and the SortOrder) and forwards them to the SqlDataSource. This control in turn pushes the new values in the parameters for the INSERT statement and then sends the command off the database, which inserts the new row in the Genre table. If you click the Insert link without entering a name or order, you will get an error. And in this chapter later you will see how to modify the data-bound controls to include validation functionality.

When you dropped the Genre table on the Genres.aspx earlier in this chapter, VS not only created a bunch of controls for you, but it also stored information about the database in your Web.config file. The next section explains how this works and why it is important.

## Storing Your Connection Strings in Web.config

The first time you dropped the Genre table on your page, VS created a SqlDataSource control for you. To tell this control how to access the database, VS also created a connection string in the Web.config file under the <connectionStrings> element and pointed the SqlDataSource to this connection string. The string in Web.config looks like this:

```
<connectionStrings>
  <add name="PlanetWroxConnectionString1" connectionString="Data Source=(localdb)\mssv1.0;AttachDbFilename=|DataDirectory\PlanetWrox.mdf;Integrated Security=True"
  providerName="System.Data.SqlClient" />
</connectionStrings>
```

The SqlDataSource uses this connection as follows:

```
<asp:SqlDataSource Id="SqlDataSource1" runat="server"
ConnectionString="<% ConnectionStrings:PlanetWroxConnectionString1 %>">
```

This code uses expression syntax to refer to the connection string in the Web.config. It asks the Web.config file for the connection string that listens to the name PlanetWroxConnectionString1. It also reads the providerName attribute to figure out how its internal code should talk to the database.

> NOTE: In addition to the expression syntax that uses <% %> to bind control values to resources like a connection string, you'll also come across similar syntax that uses <% # %>. This is called data-binding expression syntax and it enables you to bind control values to data that comes from data sources like a database. You see more about data-binding expression syntax in this and the next two chapters.

Storing your connection strings in Web.config is considered a very good practice. By centralizing your connection strings you make it much easier to modify them when your database changes (for example, when you switch from a development environment to a production server). Never store your connection strings directly in Code Behind or in the markup of the page. You will seriously regret the day you have to change your connection string and have to wade through all the pages in your site looking for them.

The Express LocalDB SQL Server you have used so far enables you to work with databases that are attached to SQL Server on the fly when you need. Take a look at an actual connection string to see how this works:

```
DataSource=(localdb)\MSSQLLDB;AttachDb=|DataDirectory|PlanetWW.mdf;IntegratedSecurity=True;
```

This connection string consists of three parts (which are all in your config file). The value of the first part contains the data source to identify the SQL Server that is targeted, in this case is a LocalDB instance of SQL Server. Other valid data sources you may come across include (just a dot, to target the local machine), \Expression, to target a named instance of SQL Server running on the local machine (where SQLServer is the instance name), or something like Name\InstanceName to target a remote machine or a named instance on a remote machine.

Attach to your SQL Express database. The |DataDirectory| placeholder is used to hold the full and physical path of the App_Data folder at runtime. So, when you load the pages and the SqlDataSource connects to the database, it will open the file PlanetWro.mdf in C:\AspNet\YourSite\App_Data\. As an alternative to AttachDbFileName you will come across Initial Catalog in other settings. The Initial Catalog to a database available on the SQL Server you are using. You see more of this in Appendix B.

The last part of the connection string has to do with security. With Integrated Security, the account used by the web server is used to connect to the database. In the case of VS and IIS Expression, this account is the one you use to log on to your machine. If you're using the full version of IIS, this account is named after an Application Pool in IIS, or a special account called Network Service. Chapter 19, which deals with deployment, and Appendix B, which explains how to connect to SQL Server, dig deeper into security-related issues.
