You can't make an omelet without breaking eggs and you cannot write code without creating bugs. No matter how hard you try and how good you are, your code will contain problems that affect the behavior of your website.

Of course you should strive to minimize the impact of these bugs, aiming for a “zero bug count.” To aid you in this, the ASP.NET run time and Visual Studio provide you with a number of tools.

First of all, the languages supported by .NET implement exception handling, a methodology to identify and handle errors that occur at run time. By handling these errors, you can present your users a friendly error message. At the same time, you can log these errors, giving you a chance to fix them before they recur. In this chapter, you will see how exception handling works, and how to log your errors.

Before your code goes into production, you need to write and debug it. To help you debug your code, VS comes with a rich toolset that allows you to step through your code by line, look at your variables and objects at run, and change them as you go. The toolset also provides you with valuable information about the execution path your code follows: the path that your application takes through your code, following methods, event handlers, if-else statements, and so on. In this section, you learn more about exception handling, while the debugging tools are discussed later in this chapter.

# EXCEPTION HANDLING

Whenever you write code, there is a chance things won't turn out as expected, resulting in code that does not compile, a crash, or otherwise unexpected behavior of your application. Things can go wrong for a large number of reasons: you introduce a typo in your code, the database server you're connecting to run suddenly goes down, you got your logic mixed up and accidentally deleted all rows from a database table instead of just one, you try to delete a row from a database table that still has associated rows, you try to delete a row from a database table that still has associated rows, you try to delete a row from a database table that still has associated rows, you try to delete a row from a database table that still has associated rows.

To understand these problems and solve them, you first need to understand different types of errors. The remainder of this section is spent discussing how to avoid them.

# Different Types of Errors

You can broadly categorize errors into the following:

- Syntax errors—errors that prevent the code from compiling.
- Logic errors—errors that seem fine but produce unexpected results.
- Runtime errors—errors that cause the application to crash.

# Syntax Errors

Compile errors are always the easiest to find because they happen during development. The compiler tells you where the error occurs. To go to the location where the error occurred, double-click the error in the Error List. To cycle through the errors and the code where the error occurs, press F8.

You can force the compiler to give you an up-to-date list of all the errors. To do this, from the main menu choose Build Site. When you want VS to compile the entire site (which is slower but recompiles files that have changed), choose Rebuild Site instead.

# Logic Errors

Logic errors are often harder to find because they become fine but only hidden during the execution of your code. Consider the following example:

# VB.NET

vb
Dim fromAddress As String = "@example.com"
Dim toAddress As String = EmailAddress.Text
myMessage.From = New MailAddress(toAddress)
myMessage.To.Add(New MailAddress(fromAddress))
```

# C#

csharp
string fromAddress = "@example.com";
string toAddress = EmailAddress.Text;
myMessage.From = new MailAddress(toAddress);
Message.To.Add(new MailAddress(fromAddress));
```

Although it's easy to see what the problem is in this example (the To and From addresses are switched), it may be harder to find in a file with 250 lines of code. Additionally, because the compiler happily accepts your mistake, you won't notice the error until you see a message in your Inbox that you thought you sent to your visitors.

The best way to track down and solve logic errors is using the built-in debugging capabilities of VS. You get an in-depth look at those issues later in the chapter.

# Runtime Errors

Runtime errors occur at run, which makes them incredibly difficult to track. Imagine you have a site that contains a bug that's hidden somewhere in a page. You haven't found it yet, but one of your visitors did and got a nasty error message (on more than those) instead. What can you do? Probably not much, because there's a fair chance your visitor won't even inform you about the mistake.
