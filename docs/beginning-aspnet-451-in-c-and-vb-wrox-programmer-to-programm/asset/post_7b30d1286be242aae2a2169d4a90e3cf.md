# How It Works

Technically, this exercise isn't complicated. You set up a bunch of event handlers for the various controls in your page. Inside the event handler you call a method that checks whether the page is currently loading for the first time or due to a postback. To make it easy to add the name of the calling method to the Label control, the handlerName parameter of the method has a special CallerMemberName attribute, like this:

# VB.NET
```vb
Private Sub WriteMessage(<CallerMemberName> Optional handlerName As String = "*")
```

# C#
```csharp
private void WriteMessage([CallerMemberName] string handlerName = "*")
```

This attribute has been introduced in .NET 4.5 and can be used as optional parameters (identified in VB.NET with the Optional keyword and a default value, and in C# simply by assigning it a default value). When no value is passed to the WriteMessage method for this parameter (as is the case for most of the handlers except the last one used), .NET fills it with the name of the calling method. This is very useful for debugging purposes because it enables you to figure out which method called WriteMessage, in each call. In earlier versions of .NET you had to pass the name of the calling method manually making this code a bit more tedious. Also, because this attribute only has an effect when no value is passed in, you can still supply your value yourself, as is the case with the Page_PreRenderComplete handler. Beside the method name, this code also passes the line break and the dashed line and, as you have to supply the value.

The WriteMessage method then updates one of the two Label controls with the name of the event that triggered the event.

What's also interesting about this exercise is the order in which the events occur. Take a look at the first list, displayed when the page loads:

First Page Load is triggered. Then the GridView sees that it's hooked up to a SqlDataSource and asks for control for this data. This causes the Selecting events to be triggered. When the GridView receives the data from the SqlDataSource, it fires its DataBinding event to signal it about to bind the data to the control. The GridView starts to create rows. For each item in the data source, it creates a row, RowCreated binds the item's data to, and finally calls RowDataBound. If you carefully count the number of times that RowCreated and RowDataBound are called, you'll notice that the total number of calls is the actual number of items are in the data source plus two. This is because the same event is also raised when the control creates its header and footer rows. You you how to distinguish between these rows inside the GridView inside an event handler in a later exercise.

Finally, when the GridView is done creating and binding all the rows in the data source, it fires its DataBound event.

On postback, the story looks quite different. When you click the button to cause a postback, the following events are raised:

```
GridView_RowCreated
GridView1_RowCreated
GridView1_RowCreated
GridView1_RowCreated
Page_Load
Button_Click
Page_PreRenderComplete
```

Note that this list contains no RowDataBound or DataBound events, and the SqlDataSource is also nowhere to be seen. The GridView is to reconstruct the entire control from ViewState, eliminating the need to access the database again. While getting the data from View State, the GridView still needs to recreate each row, so you still see the RowCreated events. Toward the end of the list you see the Page_Load event followed by the Button's click. It's important to understand and remember that user-triggered events like a Button's click or a SelectedChangedEventArgs of a DropList occur after the Load event of the Page. This Load event isn't the start of the Page's life cycle. Before Load, the Page is already instantiated and has its Init event. You could add a handler for this event to the code to confirm this.
