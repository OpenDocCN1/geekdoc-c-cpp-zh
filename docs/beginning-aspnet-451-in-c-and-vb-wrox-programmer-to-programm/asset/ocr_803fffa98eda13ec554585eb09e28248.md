```
</behavior>
</endpointBehaviors>
<behaviors>
<serviceHostingEnvironment aspnetCompatibilityEnabled="true">

</serviceHostingEnvironment>

```

The service defines a single purpose, the NameService in it. If your site has more services available, you would add them to the same <services> element as NameService. The binding and contract attributes tell the run that this service is callable over HTTP and is implemented by the NameService class. The address attribute is empty, meaning the run time takes care of assigning an address. For more scenarios you can use a relative address here. The behaviorConfigurations points to a behavior NameServiceAspNetAjaxBehavior defined under the behaviors node. WCF fetches behaviors from the actual service definition so you can reuse the same across multiple services. In this case, the behavior is created to be enabled by a web page through the enableWebScript element.

Once the service is registered in the web.config file, you can register it with the ScriptManager. You could do this in the <Services> element of the ScriptManager in the master page. The downside of registering the web service in the master page is that its JavaScript is referenced in each and every page in your site. For a service you use once or twice, it's much better to add a ScriptManagerProxy to the specific page(s) and register the service there. Within your page, the ScriptManagerProxy controls and acts like a normal ScriptManager control. However, it is just a proxy that relays all its services to the true ScriptManager. In the master page, combining the settings for both controls. You used the ScriptManagerProxy for controls to set up the <services>:

```
<asp:ScriptManagerProxy ID="ScriptManagerProxy" runat="server">
<Services>
<asp:ServiceReference Path="/Services/NameService.svc" />
</Services>
</asp:ScriptManagerProxy>
```

All you need to refer to the service by setting the Path property. With as other server-side URLs you have seen in this book so far, you can use the link (tilde) to refer to the application's root.

Once you have registered the service, it becomes available in your client-side code. Now IntelliSense is smart enough to discover the WCF services you have defined and registered. As soon you typed NameService followed by a client-side script block, IntelliSense kindicked in again and showed the methods it found. This makes it extremely easy to find the correct services you have defined in your site.
