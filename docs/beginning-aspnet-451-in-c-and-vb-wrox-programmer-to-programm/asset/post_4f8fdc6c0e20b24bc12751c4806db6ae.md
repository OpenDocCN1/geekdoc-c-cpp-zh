
# How It Works

The DetailsView and the SqlDataSource controls care of most of the hard work for you. You set up different templates that enable a user to insert new rows and update existing ones then the two controls take care of the rest. When you click the Insert link, the controls are validated using JavaScript as you saw in previous chapters. The same validation is carried out at the server by the DetailsView control to ensure the submitted data meets your criteria. If the data is valid, the DetailsView control inserts or updates data, depending on the mode. To see how this work, take a look at the InsertItemTemplate Title column:

```
<InsertItemTemplate>
<asp:TextBox Id="TextBox" run="server" Text='<%# Bind("Title") %>' />
</asp:TextBox><asp:RequiredFieldValidator ControlToValidate="TextBox" ErrorMessage="Enter a title"
run="server" />
</asp:RequiredFieldValidator></InsertItemTemplate>
```

The most important piece of code in this snippet is the Text property of the TextBox is bound. Earlier you saw the one-way binding using Eval which basically outputs the value of a bound column. With Bind, however noticed something something more powerful. Bind enables you to express a data binding between column from the SqlDataSource and a control in the page in two directions. In this case, the Title column of a review is bound to the TextBox. This means when the control must display its data (for example, when updating an existing row), it must display the Title of a review. But more importantly, on postback, after you click the Update link, the control understands the relationship between the TextBox control and the Title column. So, when you click Update after making changes to the review in the page, the DetailsView collects all the bound data from the form (the Title, Summary, Body, GenId, and which item is authorized) and then sends it to the SqlDataSource control that has parameters set for each of the relevant columns of the Review table:

```
<asp:SqlDataSource Id="SqlDataSource1" run="server">

<UpdateParameters>
<asp:Parameter Name="Title" Type="String" />
<asp:Parameter Name="Summary" Type="String" />
<asp:Parameter Name="Body" Type="String" />
<asp:Parameter Name="GenId" Type="Int32" />
<asp:Parameter Name="Authorized" Type="Boolean" />
<asp:Parameter Name="UpdateDateTime" Type="DateTime" />
<asp:Parameter Name="Id" Type="Int32" />
</UpdateParameters>
</asp:SqlDataSource>
```

Eventually, the SqlDataSource gathers all the parameter values, injects them into the UpdateCommand, and sends them to the database.

This works for all columns of the Review table but you may have noticed that DateTime was not a part of any of the SqlDataSource commands. What about the other columns? The database is set up to today's date and time automatically, there's no need to include it in the code. The UpdateDateTime column is a different story. Obviously, you don't want your users to enter the value for this column manually. The system should help keep track of it automatically. That's why you hid the control from the user interface by setting its Visible property to False. However, the Insert and Update commands expect a value for this column, you need to find a different way to insert it. Here's where the Inserting and Updating events come into play. Take a look at the ItemInserting event handler to get a general understanding of how this works:

```
VB.NET
Protected Sub DetailsView1_ItemInserting(sender As Object,
    e As DetailsViewInsertEventArgs) Handles DetailsView1.ItemInserting
    e.Values("UpdateTime") = DateTime.Now
End Sub
```

```csharp
protected void DetailsView1_ItemInserting(object sender,
    DetailsViewInsertEventArgs e)
{
    e.Values["UpdateTime"] = DateTime.Now;
}
```

As you aware, ItemInserting fires right before the InsertCommand is sent to the database. This is a perfect location to supply (default) values to the columns that have no corresponding control in the user interface, as is the case with UpdateDateTime. This code simply sets the UpdateDateTime to today's date and time. This value is sent to the database where it is used to assign a value to the Review table's UpdateDateTime column.

The same principle applies to the Updating command. Within that event, you need to index the NewValues collection instead of the Values collection, but the principle is the same.
You might argue that in an Insert command, you don't need to set the UpdateDateTime. After all, the database inserts a value for automatically when you insert a new row. To make the distinction between inserting and updating, you need to do a more manual work. You have to remove the column from the InsertCommand and then remove the column from the <InsertParameters> collection as well. Although in this itself is not a lot of work, you get into trouble when you try to modify the SQL commands for the SqlDataSource, because the Insert and Update commands are out of sync. Simply setting the UpdateDateTime code, as in this, solves many of these problems.

When the SqlDataSource control is when inserting or updating, it fires its ItemInserted or Updated events, respectively. Inside these events, the code checks if e.Exception is null/None. Without this check, the user would be redirected to the Reviews.aspx page regardless of whether an error occurred. With this check, the user is taken back to Reviews.aspx page by calling EndEditing()

# VB.NET

```vb
Private Sub EndEditing()
    Response.Redirect("Reviews.aspx")
End Sub
```

# C#

```csharp
private void EndEditing()
{
    Response.Redirect("Reviews.aspx");
}
```

A typical reason for an error during the update might be an incorrect genre ID. If you didn't set up the DropDownList correctly, the database would have an invalid genre ID and the INSERT or UPDATE would fail. By not redirecting when an error occurs, the error message is displayed on-screen so you can get to fix it.

With the discussion of the various controls, now, you should have a reasonably good understanding of how to perform CRUD operations using the GridView, DetailsView, and SqlDataSource controls.
Useful as the SqlDataSource control may be, many developers don't like to use it. One of the biggest drawbacks of this control is the fact that your SQL statements end up directly in your pages. This can be problematic if you are just starting your database schema. Even if you think there's no need to change, you can be pretty sure you'll need to change it one day. Once you do, things are likely to break. For example, if you rename the Name column of the Genre to Description, your application will break. You won't notice until you run time because VS is not able to check the database schema against the command texts defined in the SqlDataSource controls. You have few ways to work around this. One solution is to build strongly typed objects and work with the ObjectDataSource instead. Details of this solution are beyond the scope of the book, but you're invited to check out my website where I've published an article series demonstrating this concept: http://bit.ly/3weD7D. The concepts presented in this series are quite advanced, so you may want to postpone digging into it until you've finished this book.
Another alternative is to make use of the ADO.Net Entity Framework, the topic of the next chapter that also shows you how to Model Binding and the ListView and DataPager controls to perform similar actions without the need for embedded SQL queries in your code.

# PRACTICAL TIPS FOR DISPLAYING AND UPDATING DATA

The following list provides some practical tips for displaying and updating data:

- Always store your connection strings in the Web.config file. Although it might seem easy to store them directly in the SqlDataSource control in page, you'll get in trouble when you need to make changes to your connection string later.

- Always consider adding validation controls to your data entry pages. It makes it at easier for your users to find out what data is required, and in what format they should deliver, while you protect your system from receiving and processing incorrect data.
