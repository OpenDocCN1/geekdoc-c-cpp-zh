
## WORKING WITH WEB FORMS

Web Forms, represented by .aspx files, are the core of ASP.NET Web Forms website. They are the actual pages that users see in their browsers when they visit your site.

As learned in the previous chapter, Web Forms can contain a mix of HTML, ASP.NET Server Controls, client-side JavaScript, CSS, and programming logic. To make it easier to see all the code ends up in the browser, VS offers a number of different views on your pages.

## The Different Views on Web Forms

VS enables you to look at your Web Form from different angles. When you have a file with markup—like a Web Form or master page—open in the Document Window, you see three buttons at the bottom-left corner of the window. With these buttons, visible in Figure 2-9, you can switch between the different views. This figure shows a master page, which you will learn about in Chapter 6.

Source View is the default view when you open a page. It shows you the raw HTML and other markup for the page, and is very useful if you tweak the contents of a page and you have a good idea of what you want to change and where. As explained in the previous chapter, I use the Markup View rather than Source View to refer to the markup of ASP and HTML pages.

The Design button enables you to switch the Document Window into Design View, which gives you an idea of how the page will end up. In Design View, you can use the Visual Aids and Formatting Marks submenus from the Main menu to control visual markers like line breaks, borders, and spaces. But submenus offer a menu item called Show that enables you to turn the visual aids on or off. Turning them off is useful if you want to have an idea of how the page ends up in the browser. You should, however, use Design View to get an idea of how the page will end up. Although VS has a great rendering engine that shows the pages in Design View pretty well, you should always check your pages in browsers as well, because what you see in VS is the markup for the page before it gets processed. Server controls on the page emit HTML that changes the look of the page in the browser. Therefore, it's recommended to view the page in the browser as often as possible so you can check if it's going to look the way you want it. It's also recommended to test your site in as many browsers as you can get your hands on, because there may be small differences between them in the way they render a web page. The Planet Wrox website has been developed and tested against recent versions of Microsoft Internet Explorer, Firefox, Google Chrome, Safari, and Opera. You'll see screenshots of these browsers at various places in the book. In Chapter 18 you will be introduced to Browser Link, which makes browser testing a lot easier.

The Split enables you to look at Design and Markup View at the same time, as you can see in Figure 2-10.

Split View is great if you want to see the code that VS generates when you add controls to the Design View of your page. The other way around is very useful too: When you make changes to the markup of the page in Markup View, you can see how it ends up in Design View. Sometimes Design View becomes out of sync with Markup View. If that's the case, a message appears at the top of Design View. Simply clicking the message or saving the page is enough to update the Design View. You can cycle through the three different modes using Ctrl+Page Up and Ctrl+Page Down keys.

If you want pages to open in a different view than Markup View, choose Tools Options. Then expand HTML Designer, and in the General category, select your preferred view. Alternatively, enter HTML Designer General in the Quick launch box (which you can access by pressing Ctrl+Q) at the top-right of VS and click the item in that list that appears.

> NOTE Initially, Visual Studio has two editors for markup-based files. For Forms (and User Controls, which you'll meet later in the book) Visual Studio uses the older editor shipped with earlier versions of Visual Studio. This editor supports Design View. The new HTML editor has a strong focus on code-only editing and does not support Design View. This means that you can switch to Design View for Web Forms, but not for regular HTML files. If you want Design View for HTML files as well, you can associate the .htm extension with the HTML (Web Forms) editor under Tools Options Text Editor File Extension.

In addition to the HTML and other markup you see in the Markup View window, a Web Form can also contain code in either C# or Visual Basic .NET. Where this code is placed depends on the type of Web Form you create. The next section explains the two options you have in more detail.

## Choosing Code Behind and Pages with Inline Code

Web Forms come in two flavors: either as .aspx file with a Code Behind (a file named after the Web Form with an additional .vb or .cs extension) or as .aspx files that have their code embedded, referred to as Web Forms with inline code. Although you won't see much code until Chapter 5, it is important to understand the difference between these types of Web Forms. First, Web Forms with inline code make a little easier to understand. Because the code needed to program your website is of the very same Web Form, you can clearly see how the code relates to the file. However, if your page gets larger and you need more functionality, it's often easier if you have the code in a separate file. That way, it's completely separate from the markup, enabling you to focus on the task at hand.

In the next exercise, you two files demonstrate the difference between Code Behind and inline code.

## TRY IT OUT Adding Web Forms with Code to Your Site

The files you use in this exercise aren't needed for the final application. To avoid cluttering your project, you should put them in a separate Demos folder.

- 1. In the Solution Explorer, right-click your website and choose Add -> New Folder. Name the folder Demos and press Enter.
- 2. Right-click the Demos folder and choose Add -> New Item. In the dialog box that appears, choose your programming language on the left, click the Web Form template, and name the file CodeBehind.aspx. ### VB.NET

```
Protected Sub Page_Load(sender As Object, e As EventArgs) Handles Me.Load

End Sub
```

### C#

```
protected void Page_Load(object sender, EventArgs e)
{
}
```

Although this code may look a little scary at this point, don't worry about it too much now. In most cases, VS adds it for you automatically, as you just saw. In later chapters, you will see exactly how this code works, but for now it's important to realize that the code you're going to place between the lines that start with Protected and End Sub in Visual Basic and between the curly braces in C# will be executed when the page is requested in the browser.

All examples you see from now include a Visual Basic (VB.NET) and a C# version, so always pick the one that matches your programming language.

Note that as you type the L for Label, you will get a list with options to choose from. This is part of Visual Studio's IntelliSense, a great tool that helps you write code instead. Instead of typing the word Label you simply type the letter or the letters La and then you pick the appropriate item from the list, visible in Figure 2-12.

To complete the selected word, you can press Enter or Tab or even period. In the latter case, you immediately get another list that enables you to pick the word by simply typing the first few letters. This feature is a real productivity tool because you can write code with many fewer keystrokes. IntelliSense is available in many other file types as well, including ASPX, HTML, CSS, JavaScript, and XML. In many cases, the list with options pops up automatically if you begin typing. If it doesn't, press Ctrl+Spacebar to invoke it. If the list covers some of your code in the window, press and hold the Ctrl key to make the window transparent.
