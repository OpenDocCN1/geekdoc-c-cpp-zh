# How It Works

The File System option simply creates a copy of all files that make up your website. In this exercise, you saw how to copy the files to the local filesystem. This is a great way to create a copy that is detached from the development environment and run on a different machine. You'll see how to make use of these files later in this chapter. The Web Deploy and FTP options enable you deploy your changes to a live server, while Web Deploy Package lets you create a setup file that can be run by an administrator over a running IIS and Web Deploy for Hosting Servers.

On the Settings tab of the dialog you can choose the option Precompile During Publishing under the Publish Options. When you click Configure for that option you can further define the precompilation process. When you enable, all the code in the Code Behind of your ASPX pages, code in App_Code, and so is compiled into .NET assemblies — files with a .dll extension, stored in the folder of your site. The main benefits of precomp are protection (with access to the server can't look into your source) and an increased performance the first time a page is requested. Pages that are not precompiled are compiled on the fly when they are requested the first time, which takes a little bit of time. Remember that regular visitors to your site will never be able to see the source of your application. They'll be able to see the final HTML that gets sent to the browser. When you select Precompiled to be Updated in the Advanced Settings, Visual Studio compiles all VB.NET and C# code into assemblies and places them in a folder at the root of your site. It leaves the markup and ASCX files alone. However, with this option turned off, the markup is compiled into .dll files as well. The actual files still need to be deployed to the server, but their content has been replaced with placeholder text: "This is a marker generated by the precompilation process, and should not be deleted". When the page is requested by a browser, the ASP.NET run finds the appropriate content of the assemblies in the bin folder and serves it as if it were a normal page. This latter is especially great if you want to prevent other people with access to your server from altering your site after it has been deployed. Because the source and markup is compiled into .dll files, there is no way to change it on the server anymore without uploading a new set of published files.

When you complete the Publish Wizard, Visual Studio stores the settings in a Profile file (with a .pubprofile extension) in the Profiles folder under App_Data. This file is then used whenever you publish to the site, so you don't have to enter all the details again. Visual Studio uses the profile also to maintain multiple versions of your Web.config file, as you will see next.

# Introducing Web.config Transformations

If you take a look at the current Web.config file you've been working with so far, you're likely to have a few settings that will be different on your production server. For example, your connection string will be different from the production server, and so are the settings for the mail server and maybe even the e-mail addresses you added earlier in this chapter. After overwriting the changes in the production server, developers often skip deploying the Web.config to the production server, and then manually update the settings in that file. However, this is far from ideal because you're likely to forget to add settings to the production server that you have added in production. To overcome this problem, Microsoft has introduced Web.config Transformations, a mechanism to generate a Web.config file from the main Web.config in your project, but adjusted with settings that are specific for the production server (or other environments, such as a test server).
