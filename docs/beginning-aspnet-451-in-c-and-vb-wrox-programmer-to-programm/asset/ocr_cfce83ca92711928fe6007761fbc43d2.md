First Page Load is triggered. Then the GridView sees that it's hooked up to a SqlDataSource and asks for control for this data. This causes the Selecting events to be triggered. When the GridView receives the data from the SqlDataSource, it fires its DataBinding event to signal it about to bind the data to the control. The GridView starts to create rows. For each item in the data source, it creates a row, RowCreated binds the item's data to, and finally calls RowDataBound. If you carefully count the number of times that RowCreated and RowDataBound are called, you'll notice that the total number of calls is the actual number of items are in the data source plus two. This is because the same event is also raised when the control creates its header and footer rows. You how to distinguish between these rows inside the GridView inside an event handler in a later exercise.

Finally, when the GridView is done creating and binding all the rows in the data source, it fires its DataBound event.

On postback, the story looks quite different. When you click the button to cause a postback, the following events are raised:

```
GridView_RowCreated
GridView_RowCreated
GridView_RowCreated
GridView_RowCreated
Page_Load
Button_Click
Page_PreRenderComplete
```

Note that this list contains no RowDataBound or DataBound events, and the SqlDataSource is also nowhere to be seen. The GridView is to reconstruct the entire control from ViewState, eliminating the need to access the database again. While getting the data from View State, the GridView still needs to recreate each row in the grid, so you still see the RowCreated events. Toward the end of the list you see the Page_Load event followed by the Button's click. It's important to understand and remember that user-triggered events like a Button's click or a SelectedChangedEventArgs of a DropDownList occur after the Load event of the Page. This Load event isn't the start of the Page's life cycle. Before Load, the Page is already instantiated and has its Init event. You could add a handler for this event to the code to confirm this.

At the end of the exercise, you clicked a column header to sort the data that is displayed. In this time, the GridView knows must sort what is being displayed. It cannot do that, so instead it asks the SqlDataSource for a fresh copy of the data in the order you requested. Just as you did the first time the page loaded, you see the various RowCreated and DataBound events fire after each other, and before the SqlDataSource gets its data. What's interesting to see is that the Sorting and Sorted events fire after each other. The reason for this is that the GridView doesn't handle the sorting here; it merely exposes the sorting parameters (the sort expression and the direction) to other controls. With a SqlDataSource, sorting takes place at the database level, but it retrieves the sorting parameters from the GridView.
