
# How It Works

When you added the CustomValidator ID="CustomValidator" you set up two event handlers, for the client-side and one for the server-side validation control, both in the following snippet:

```aspsharp
<asp:CustomValidator ID="CustomValidator" runat="server" ErrorMessage="Enter your
home or phone number" ClientValidationFunction="validatePhoneNumbers"
OnServerValidate="CustomValidator_Validate"
Display="Dynamic" /></asp:CustomValidator>
```

If you're using VB.NET, you won't see the OnValidationError attribute that is set up in the Code Behind with the handlers used.

The JavaScript validatePhoneNumbers that you set in the ClientValidationFunction is triggered when you click the button. This function is defined in the markup section of the control and contains references to the text boxes for the phone numbers:

```javascript
var phoneHome = document.getElementById('<PhoneHome.ClientID %>');
var phoneBusiness = document.getElementById('<PhoneBusiness.ClientID %>');
```

The calls to the ID are wrapped in a server-side c# block. This code runs at the server, and returns the ID of the control to use. If you look at the HTML for the Contact page in the browser, you find the following:

```javascript

var phoneHome = document.getElementById('cpMainContent_Form_PhoneHome');
var phoneBusiness = document.getElementById('cpMainContent_Form_PhoneBusiness');
if (phoneHome.value != '' || phoneBusiness.value != '')
```

Here you can use the server-side ID properties of the controls which have been transformed into their client counters. This is a much better than hard-coding the id attributes of the text boxes in the HTML, which can be changed easily by the ASP.NET runtime. You see how and why this is important in the preceding chapter.

To make the JavaScript you possess in the browser shorter and easier to read, you can use the ClientID property to "fix" the IDs of the phone number controls. Because you will likely have two TextBox controls in a single page, you can assume that you won't end up with two controls with the same name if you fix the control IDs. To do this, you will need to set the ClientID for these two controls to Static, like this:

```aspsharp
<asp:TextBox ID="Phone" runat="server" ClientID="Static" />
<asp:TextBox ID="Business" runat="server" ClientID="Static" />
```

Because the controls are now fixed, they end up as-is in the final HTML:

```javascript
var phoneHome = document.getElementById('PhoneHome');
var phoneBusiness = document.getElementById('PhoneBusiness');
```

Eventually, the IDs are passed to the JavaScript function getElementById on the document object to get a reference to their respective text in JavaScript. In Chapter 11, which deals with jQuery, I discuss an alternative to using getElementById. If one of them is not an empty string, the validation succeeds. 

The code examines the value properties of these two TextBox controls. But how does the validatePhoneNumbers method report back to the validation mechanism whether the validation succeeded or not? When the ASP.NET validation mechanism calls the validatePhoneNumbers method it passes two arguments: source, which is a reference to the actual CustomValidator in the HTML, and args. The args object exposes an IsValid property that enables to determine whether or not the validation succeeded:

```javascript
if (phoneHome.value != '' || phoneBusiness.value != '') {
  args.IsValid = true;
} else {
  args.IsValid = false;
}
```

With this code, if both boxes are empty, IsValid is set to false so validation won't stop form from being submitted. If at least one of the text boxes contains a value, IsValid is set to true. In this example, source argument is not used, but you could use it to highlight or otherwise change validation based on whether or not At the server, the CustomValidator calls the server-side validation method which performs the same check:

```vb
If String.IsNullOrEmpty(PhoneHome.Text) OrElse
Not String.IsNullOrEmpty(PhoneBusiness.Text) Then
  args.IsValid = True
Else
  args.IsValid = False
End If
```

```csharp
if (!string.IsNullOrEmpty(PhoneHome.Text) ||
    !string.IsNullOrEmpty(PhoneBusiness.Text)) {
  args.IsValid = true;
} else {
  args.IsValid = false;
}
```

By checking the data at the client and at the server, you ensure your system accepts only valid data. Even when the browser doesn't support JavaScript (possibly the user turned it off), your data is still checked at the server. However, it's important to realize that you still need to check whether the page is valid before you work with the data submitted to it. You do this by checking the IsValid property of the page:

```vb
If Page.IsValid Then
  // OK to proceed
End If
```

```csharp
if (Page.IsValid) {
    // OK to proceed
}
```

The IsValid property returns True when all the controls in the page are valid. By checking the IsValid property on the server before you work with the data, you can be sure that the data is valid according to your validation controls even if the user turned off JavaScript in the browser and sent the form to the server without any client-side checks. # Understanding Request Validation

By design, ASP.NET throws an error whenever one of the controls on a page contains content that looks like HTML tags. For example, see the error shown in Figure 9-10 when you enter `<h1>Hello World</h1>` or `<script>alert('Hello World');</script>` as the contents of the text box in the contact form.

![](img/9e03e3b9560597824f8b22941d6dbb_357_0.png)
FIGURE 9-10 ASP.NET runtime prevents users entering HTML or JavaScript that can potentially mess with the design or working of your website or could lead to security risks. If you're sure you want to allow users to enter HTML, you have a few options. First, you can disable request validation by setting the ValidateRequest attribute in the Page directive to False:

```aspsharp
@Page Inherits="Contact" Title="Contact" ValidateRequest="False" %>
```

With setting it to False, users can enter HTML. In previous versions of ASP.NET, this was the only way to enable a user to send HTML to your page. The downside of this solution is that it is all or nothing. By turning off request validation at the page level, all controls in the page will now open up your page for potential abuse. As a good security mechanism, you should allow HTML only for specific fields that you determine.

Fortunately, since ASP.NET 4.5 this is very easy; the Control class (from which controls as TextBox inherit) has been extended with a ValidateRequestMode property that controls for invalid data. When set to Enabled, the control does not accept HTML; set to Disabled the control does accept HTML, similar to how ValidateRequest enables this for all controls in the page. The final value for ValidateRequestMode Inherit gives it the value by the parent of the control such as a Placeholder. This is convenient because you can wrap multiple controls that should accept HTML in a Placeholder and then the ValidateRequestMode on the container instead of each individual control.

Before you set this on a control, make sure you really want to allow users to submit HTML in your controls. This opens up your site for Cross Site Scripting attacks if you're not careful. Depending on the situation, you may need to sanitize the data by removing dangerous pieces of code such as <script> elements. When displaying the data on a page, you could use a Literal control, with its Mode to Encode in order for the HTML to be encoded and rendered harmless. With this property, the text is displayed verbatim, without being interpreted as HTML or JavaScript.

# PROCESSING DATA AT THE SERVER

The information that a user inputs on your Web Forms is typically the only data that makes your website an interactive, data-driven system. In most websites, you have information coming from other sources such as databases, XML files, and web services. In addition, there is also data coming out of your system. You may want to send an e-mail to the owner of the website when someone posts information through the contact page, or you may want to notify people whenever you add a new feature or review to the website. For these scenarios, it's important to understand how ASP.NET enables you to send e-mail. This is discussed in the next section.

# Sending E-mail from Your Website

Writing code that sends e-mail from an ASP.NET page is pretty straightforward. Inside the .Net namespace you find a number of classes that make it easy to create and send e-mail messages. These classes enable you to create new messages; addressees in the To, CC, and Bcc fields; add attachments; and, of course, send the messages.

The following table describes four classes that you typically work with when sending e-mail from a .NET application.

| CLASS | DESCRIPTION |
|--- |--- |
| MailMessage | This class represents the message you're going to send. It has properties such as Subject and Body to set the message contents; To, CC, and Bcc properties to set the addressees; and an Attachments collection to attach files to the message. |
| MailAddress | This class represents a sender or receiver address used in the e-mail. It has a few constructors that enable you to set the e-mail address and display name. |
