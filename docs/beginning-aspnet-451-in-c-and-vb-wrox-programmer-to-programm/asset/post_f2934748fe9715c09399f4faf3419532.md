## PREPARING YOUR WEBSITE FOR DEPLOYMENT

When you're working on the first edition of your website in a development environment, managing the site and its source code is pretty straightforward. You have only a single version of the site's source, making it easy to maintain. However, as soon as you put your site in production, you have two versions of it: one running in the production environment and the one you use for development. It makes it difficult to keep things synchronized. For example, you probably use a different database and connection string in your production environment. You're also likely to use different e-mail addresses for the e-mail that is sent by the site. Finally, you may want to disable the error e-mails from the Global.asax file in a development environment. If you make all of these changes directly when you put your site on a production server, there's a fair chance that you will overwrite some settings during the next update, which can lead to unwanted results.

This section shows how to manage different versions of the same website a little easier. You will see how to move some of the hardcoded settings, as e-mail addresses, to the Web.config file. The code in your application reads these values at runtime. The only difference between your development and production environments is a single configuration file, making it easy to have different settings in both environments. You will see later how you can use it.

### Avoiding Hard-Coded Settings

Hard-coding settings in this manner makes it difficult to give them values in different environments. Fortunately, ASP.NET comes with a great solution: the Web.config file, expression syntax, and the WebConfigurationManager class.

## The Web.config File

You've used the Web.config file number of times in this book to store information about connection strings, membership, roles and more. You also briefly saw the <appSettings> element that enables you to store simple information, such as an e-mail address. For example, to store an e-mail address, you can add the following to your Web.config:

```xml
<appSettings>
  <add key="FromAddress" value="webmaster@example.com" />
</appSettings>
```

The <appSettings> element is placed outside the <system.web> element in the Web.config file, yet still within the <configuration> element.

Obviously, you need a way to access the data in <appSettings> at runtime. You can do this in a couple of ways, expression syntax and the WebConfigurationManager class, both of which are discussed next.

## Expression Syntax

Expression syntax enables you to bind control properties to resources, such as found in the <appsettings> element in Web.config, connection strings, localization resource files, and various routing settings in URL rewrite scenarios. To display data from the <appSettings> element, you use the syntax, where AppSettings:Key refers to a key in Web.config:

<%= AppSettings:KeyName %>

You can display this in a Literal control like this:

```asp
<Literal ID="Literal1" Text="<%= AppSettings:Copyright %> />
```
