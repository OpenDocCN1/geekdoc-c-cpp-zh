## 3 无 Bug

这是在 PC 早期，当时我还没有把书中列出的所有想法应用到程序编写中。我们在处理文件格式时出现了一些 Bug。我我知道这一点，但似乎找不到这些 Bug —— 至少找不到全部。

最后，在走投无路的情况下，我编写了一些代码来检查文件的一致性，并在发现问题时对其进行纠正。随着时间的推移，我在常规代码中发现了额外的 Bug，并修复了它们，将其添加到了一致性检查和错误修正逻辑中。

## 5 无 Bug

## 第 2 章

### 什么是 BUG？

这是全书中最重要的一章。“什么是 bug ？”这个极其简单的问题，实际上有一个非常复杂的答案。本章专门用于回答这个问题。因为，在我们不知道什么是 bug 之前，我们没有机会减少它们。

我认识的一位开发者曾说过：“bug 不应该被称为 bug，它们应该被称为**大烂砸（Massive Fuck-Ups [MFUs]）**。”“Bug”这个词暗示了某种外部力量决定向你的程序中注入 bug，而且好像只要你生活圣洁，在电脑脚下牺牲一些小毛茸茸动物，它们就会消失。

MFU 的存在是因为程序是由人编写的，而人会出错。消除 MFUs 的唯一方法是进入你的代码，找到 bug 并修复它们。

这是最需要理解的概念（也是最经常被忽略的）。你会写出 MFUs。你会坐下来，并带着完全故意的恶意，在你的代码中放入 MFUs。想一想——你知道你自己就是那个把 bug 放进那里的人。所以，当你坐下来写代码时，你就会插入一些 bug。

而且有人需要找到它们并删除它们。无论进行多少的设计、原型制作、CASE、评审、管理等，都无法避免这一点。

这个概念之所以重要，因为它影响了你调试代码的方法。如果你将错误视为“bugs”，你就会希望它们一个也没有被发现（你希望好心仙子路过并洒了仙尘，bug 就此离开了）。如果你将错误视为 MFUs，你就知道它们确实存在，并且你希望找到所有的它们，以便它们被修复。

对于开发者和经理来说，在 MFUs 被发现时感到良好而不是糟糕，是至关重要的。如果他们没有发现任何问题，他们反而应该担心。与其假设你的程序运行良好并等待别人证明反之，开发者应该假设它运行并不良好，并拼命寻找导致它失败的 bug。

所以，目前，你必须接受会在代码中创建 MFUs（我设法在我的代码里偷偷塞进很多）。我不知道任何方法可以避免这一点。诀窍在于尽可能无痛地找到并纠正它们。

顺便提一句，“bug”这个词在开发者的词汇中已经根深蒂固，我没看到 MFU 能取代它的可能。然而，我认为偶尔将 bug 称为 MFUs 是重要的，这可以提醒人们 bug 是由于开发者的错误而“故意”放置在代码中的。

当开发者坚持认为 bugs 不是 MFUs 时，你应该感到担心。为什么？因为他们放弃了找出并修复它们的责任。这时，提醒他们至关重要，要告诉他们：当他们被告诉代码里有一个 MFU 时，比他们被告诉代码里有一个 bug 时，想要逃避责任要困难得多。

那么什么是 bug 呢？嗯，如果你运行程序它格式化了你的磁盘（假设你不是在写一个格式化程序），大多数人会同意是 bug 导致的。从现在起，意见开始产生分歧。我听过此类类的陈述：“没人用那个功能，所以硬盘崩溃了也没关系”；“告诉他们买个并口打印机就行了”；“可以手动同步结果，所以加得不对也没关系”，以及“那不是 bug，那是功能！”那些在自己编写的程序中认为这种类型可以接受的人，转过头就会把他们买的程序中的坏处归类为 bug。

根据我的定义，如果一个理智的人预期程序以某种方式运行某些功能，而它并没有做到——那么就是一个 bug。

### bug 从哪里来

bug 是如何进入程序的？非常简单：是你把它们放进去的。你肆无忌惮地坐下来并在你的程序中输入一些 bug 代码。它们不是自己溜进去。你可能写错了一行。你可能使用了错误的变量。你可能从别处拷贝了一些并不好用的代码。无论如何，都是你你你。

### 调试代码应当是只读的

我在许多程序中看到的一个常见问题是：程序在开启调试时运行正常，但在关闭调试时就会崩溃。（正如书中讨论的，有很多方法可以开启和关闭调试。然而，最常见的方法是使用 `#ifdef DEBUG` 和 `#endif`。）我甚至知道有一款商业程序在发布时开启了调试，但禁用了它的调试 `printf`，因为它在非调试模式下无法运行。

这个问题通常发生的原因是，代码中的调试检查部分在确定传递了错误的参数时，会从函数返回。然而，如果关闭了调试，同样的检查就不会发生，函数也不会返回错误。

这个问题有一个简单的解决方案。所有的调试代码都应该是只读的。这意味着什么？显然意味着只读取数据，从不写入数据。然而，同样重要的是它不影响代码路径。调试代码会被执行，但它永远不会导致后续代码路径发生变化。调试代码等同于调用一个返回 `void` 的函数。

所有的调试代码都应该放在 `#ifdef DEBUG` 中，以便可以开启和关闭测试。此外，将所有仅在调试模式下使用的函数放在 `#ifdef DEBUG` 中，这样该函数就不会出现在程序的最终版本中。此时，如果你在关闭调试的情况下仍调用调试代码，链接器会提醒你。

### 调试代码

```
#ifdef DEBUG
void DebugCheck(char *p)
{
    ...
}
#endif
```

在宏的情况下，你可以在 `#ifdef DEBUG` 内部定义调试宏，然后定义一个在 `#else` 中不生成任何代码的宏。使用宏会让你的代码整洁得多。与其在代码中散布大量的 `#ifdef DEBUG` 语句，你只需要宏，结果代码看起来更整洁。下面的示例说明了这些宏的使用。

### 调试宏

```
#ifdef DEBUG
#define DebugMacro(p) DebugCheck(p)
#else
#define DebugMacro(p)
#endif
```

### 使用调试宏

```
// 洁洁：
p = GetBuf(0);
DebugMacro(p);
WriteBuf(p);
```

```
// 太忙乱：
p = GetBuf(0);
#ifdef DEBUG
DebugCheck(p);
#endif
WriteBuf(p);
```

调试代码将应用程序数据视为只读是非常关重要的。实现调试代码的使用时，要确保在调试定义之外执行什么代码都没有产生影响。如果调试代码修复了数据或导致函数执行了不同的路径，那么当调试被移除（或未定义）时，你将得到一个不同的程序——你的调试是在害你而不是帮助你。

如果你的调试代码发现了参数错误，调试代码不应该导致函数返回。如果你想在非调试模式下执行相同的错误检查，正确的方法是在调试检查之后，在你的非调试代码中再次执行检查，然后返回。你调试代码的重点不是最高速度或最小尺寸，而是最大的调试效率。

下面的程序演示了一个只读的代码路径和一个非只读的代码路径。注意，在错误的示例中，只有在 DEBUG 开启的情况下，函数才能处理传入的 NULL 指针。

```
// 正确（只读）：
#ifdef DEBUG
    if (! pSrc)
        ErrorPrintf("Source String NULL\n");
#endif
if (! pSrc)
    return (NULL);      // 即使 DEBUG 关闭，我们也处理 NULL

// 错误（非只读）：
#ifdef DEBUG
    if (! pSrc)
    {
        ErrorPrintf("Source String NULL\n");
        return (NULL); // 当 DEBUG 关闭时你会死在这里
    }
#endif
```

### 代码路径

难以发现的 bug 通常发生在相对罕见的情况下。毕竟，如果程序每次运行时都会重启你的系统，它通常会修复那个错误。

这些罕见情况中的某些是因为执行了从未执行过的代码路径导致的。当你的程序首次启动时，你通常会执行一两次 `malloc`。你有一段代码会在 `malloc` 失败时执行（你不是假设它会成功吗？），但它真的失败过吗？

如果没有，你就坐等事故的发生。当那个特定的 `malloc` 失败时，你的程序到底做了什么只要你没有测试过某个代码路径，你就没有测试过你的程序。确保你了每一个路径。如果你有一个 `"if () ... else..."` 并且你总是执行 `"else"` 部分，那么 `"if"` 部分 就是一个等待发生的 bug。

测试代码路径最简单的方法是通过宏：`Trap ()` 和 `IntTest`。

### 19 个 Bug

地址。你不仅需要担心传递给 `realloc` 的变量，如果另一个变量也持有指向旧地址（realloc 之前的地址）的指针。

然而，如果在调试模式下，`realloc` 总是返回一个不同的指针，那么你就知道自己会妥善处理它。此外，`realloc` 需要在旧内存位置中填充垃圾数据。否则，指向旧位置的指针在内存内存被再次使用之前仍然能看到合法数据。

每当你解锁可重定位内存时，移动它，并且如果你在旧位置缓存了垃圾数据，也要处理。如果你在缓存磁盘数据，一旦解锁，就将其写入磁盘并清除缓冲区。如果你在定时器中断（timer tick）上与 TSR 交互，并且你设置了一个信号量来关闭 TSR，请在关闭它的前后的指令上调用定时器中断。

你还想为程序创建一个极其糟糕的环境。如果它能幸存，那么它应该在任何资源变得紧紧张的实际情况下都能生存下来。

RT-Link 是一个提供代码交换的链接器，它做得非常完美。你可以用一个可用的代码页运行它，以便所有代码都交换到同一个页中。这确保了每个代码页都会交换到上一个代码页之上。如果任何代码页依赖于另一个代码页同时位于内存中，它会导致程序崩溃。

在任何调用中，如果可能发生错误，就应该对其测试。每个 `malloc` 都应该测试是否返回 `NULL`。这不仅是犯罪行为，因为你将只在低内存系统上引起间歇性的可察觉的错误。

每个打开的文件都要测试句柄是否为 -1 的情况，包括创建临时文件。你还应该测试所有文件 I/O 是否成功。我见过一些程序，这些程序假设临时文件的创建和写入总是成功的。我猜开发者的 RAM 盘总是足够大，但我的不是。你甚至需要检查对文件现有部分的读/写操作。如果连接断开，你就无法访问该文件。

对于我写的一个程序，我创建了一个虚拟内存系统（针对 DOS），它会先使用普通内存。如果使用了普通内存，它就会转到 EMS。如果 EMS 用尽了，它就会去磁盘。那么我确定它们是否都运行良好吗？我在调试模式下设置了可以可选地始终从 EMS 或磁盘分配。仅磁盘版本运行很慢（我们说在 486 上有巨大的延迟），但所有函数都能正常工作。通过这种方式，我能够强制程序使用每个内存系统。

如果你的临时文件在 RAM 盘满时会被移动到硬盘，请务必使用一个过小的 RAM 盘测试你的应用程序。在任何你有备份程序以防你用尽首选资源的地方，务必确保你可以使用备份资源测试整个系统。

如果你写了一个使用信号量来防止重入的 TSR，在信号量之前和之后，调用该 TSR 所在的中断，以确保它不会再次重入自身。秘诀在于看你是否可以破坏自己的代码。

上述所有技巧都是针对它们所测试的代码而特定的。每个程序都有不同的弱点。你需要找到这些弱点然后破坏它们。如果你下心要发现你代码中的那些 MFUs（致命逻辑错误），那么你就能弄清楚如何破坏你的代码。

### 稳如磐石的底层函数

当你两个整数相加时，结果不大于一个整数，你就知道它会工作。想一下如果你不知道这一点，调试将会是什么样。你必须检查在每次加两个数字的地方指令执行了什么，并用各种数字组合对每一种进行测试。你基本上无法编程。

现在让我们提升一个层级。如果你对 `strcpy`（或任何运行时函数）不确定怎么办？你现在至少可以依赖（事实上，我记得 PC 编译器的早期，那时你无法依赖这些函数）。但这并不是一项容易的任务。你的测试和调试工作有了飞跃性的增长。

但你可以信任处理器和运行时（如果你不能强制它切换的话）。然而，每个程序都有一组属于自己的、特定的底层函数。这些底层函数有两个重要的属性。首先，它们贯穿你的整个程序。其中一个函数中的微小 Bug 都是程序中严重的 MFU。

其次，你通常可以测试这些底层函数中程序流的所有组合。彻底测试这些底层函数。你应该能够像依赖 `+-`（加法）一样依赖这些调用。

要做到这一点，请编写测试程序，在调用你的底层函数时使用足够不同的参数组合，以测试所有可能的代码路径组合，并且仅在返回值错误时不才打印到屏幕上。这样，当你对函数进行更改时，再次测试非常容易。

通过对底层函数的详尽测试，你将获得巨大的收益。首先，你的部分代码接近于无 Bug。让部分代码无 Bug 应该降低总 Bug 数。

更重要的是，虽然高层函数中的 Bug 通常只会引起一个问题，但底层函数中的一个 Bug（例如链表管理）会导致整个程序中出现无数 Bug。底层函数是程序的基础和框架——如果它是稳实的，程序就是稳实的。如果它是松动的，无论其他地方如何努力都无法让程序变得稳固。

对所有广泛使用的函数进行测试也是至关重要的，即使它们不是底层的。什么时候一个函数值得进行详尽测试？什么时候可以得出一组测试用例来所有组合？如果你再次审视你的代码，你可能会发现其大部分都可以以此方式测试。你可以以此方式测试数据库中的每个命令、文字处理器中的每个函数、图形包中的每个工具。

当你观察程序逻辑时，很明显少量的测试用例就能执行所有可能的路径。如果你不能这样测试任何内容，你就面临严重的问题。然而，如果你编写了真正干净、分离的（即面向对象风格）代码，你会发现几乎所有的函数都可以以此方式测试。

所以你有一段巨大的代码库，你不想为所有代码编写测试用例。那么不要写。你可以花大约三天时间为 15 到 40 个类似的函数（例如 `strcat`, `strcpy`, `str`）编写测试用例。你会发现很少 Bug，如果没有。然而，你发现的那些将是过去无法复现的 Bug。如果你没有发现 Bug，假设你写了测试程序，那么你现在知道你的底层函数是稳实的。

如果你的大部分代码都可以以此方式测试，那么如果你像这里描述的那样先测试组件，你可能会对最终产品中 Bug 如此少感到惊讶。

这可能是巧合，但当我开始对底层函数进行全面测试时，我看到写的程序 Bug 减少最多。不仅如此，在此之后，我不禁回想起任何一次严重影响整个程序的 Bug。

### 在条件定义中调试

为了保持速度，大多数时候你不会希望所有的条件错误检查都被编译。某些错误检查可能会耗费非常长的时间。（通常情况下，特定的检查并不耗费时间，而是该检查被调用的频率频繁）。

另一个通用原因是，如果你正在向终端或第二个显示器打印调试信息，并且你不希望有用信息被你其他你不感兴趣的信息所刷出屏幕。有时，纯粹的打印量会减慢程序，因为显示器只能以特定的速度写入屏幕，而不能更快。

针对这个问题，你可以采取两种主要方法之一。第一种是不编译额外的调试代码，使其完全不存在，但如果你决定需要找回某些调试打印，你将必须重新编译。下面的程序示例说明了条件编译的使用。

### 使用 DEBUG 的值

```
#ifdef DEBUG
fast_test ();
#endif
#if (DEBUG > 1)
slow_test ();
#endif
#if (DEBUG > 2)
real_slow_test ();
#endif
```

第二种方法是在调试代码开头测试一个标志位，如果测试失败则跳过它。如果标志位是一个变量，你可以在调试器中更改它的值，从而轻松地在程序运行途中开启调试测试/printf（或在不再需要它们后关闭它们）。

### 使用变量

下面的程序示例说明了调试变量的使用。

```
#ifdef DEBUG
fast_test();
if (DebugVar > 1)
    slow_test();
if (DebugVar > 2)
    real_slow_test();
#endif
```

尽管有很多花哨的方法可以实现这种条件调试代码，但似乎有两个规则是通。第一，你通常不希望在编译后开启或关闭调试。第二，这两种实现方式在代码编写和执行速度上似乎是一样快的。

对于简单代码，调试通常是一个“开/关”问题。在这些情况下，仅使用 #ifdef 通常足够了，任何额外的操作都是浪费时间。对于其他虽然简单但包含几个耗时检查的代码，你可以使用 DEBUG 定义的值作为条件编译。

在进行条件调试时，请记住，某些调试测试是相互匹配的。如果你的条件分配在每个分配内存区域的前后设置了签名字节，那么当任何检查堆签名字节的条件定义被执行时，最好也执行该操作。我曾花费了几个小时试图确定为什么某些缓冲区在 CRC 测试失败了——原因是 CRC 创建代码被 ifdef 过滤掉了，而检查代码没有。

### 注释你的开放/待解决问题 (Issues)

随着你的开发，某些代码段中会出现问题或疑问：某个函数能在 Super VGA 显示器上工作吗？你如何处理带有特定错误的数据文件？你需要注意某些情况吗？

这些问题无法通过 Traps（陷获）和 IntTests（内部测试）来解决。相反，它们是你认为尚未完全编码的项目，或者在某些情况下你没有写全。在其他情况下，你的程序将在你需要它继续运行的条件下失败。

这些是你某个时候发生的可能逻辑错误。遗憾的是，由于人类思维的局限性，这些错误会被很快遗忘（直到 Bug 出现）。这些 MFU（不可预见的故障）被归类为“该死”。

### 无 Bug

bugs - 源于当 Bug 首次报告给负责开发人员时通常听到的短语。

记录这些担忧的地方是代码本身。写在其他任何地方都可能丢失。如果写在代码中——它就是永远的，直到你解决了该问题。

在这些情况下，请放置单行注释，单词“bug”后面跟着你的缩写和日期。你可以在其后加上几行的注释，但第一行应该给出一个合理的描述。

### BUGBUG

下面的程序示例说明了 BUGBUG 注释的使用。

```
// BUGBUG DNT 32/1/92 - 内存不足。我们需要用磁盘吗？
// 目前如果内存耗尽就会失败。然而，
// 如果在大文件上运行，内存不足可能会很。
```

这个 BUGBUG 完成三件事：

- 通过在所有文件中对 BUGBUG 进行 grep 或文本搜索，你可以获得所有开放问题的标题行。（注意：在汇编章节中，展示了一种在编译期间将 BUGS 到屏幕的方法。遗憾的是，C 不支持这种方式的编译期间打印。）

- 开放问题随代码迁移。你不会丢失开放项目列表（除非你也丢失了代码）。

- 开放项目就在代码中相关的位置——你不需要搜索所有文件来找到正确的位置。

当你交付产品时，你的代码中不应该有任何 BUGS。在上面的示例中，你可能决定改用磁盘。你也可能决定将自己限制在内存中。无论何种情况，问题都解决了。

如果你不使用 BUGBUG，你可能会忘记或丢失重要问题。在程序发布后用户报告 Bug 之前，你可能不会记得这个问题。使用 BUGBUG 是简单的，而且比在其他地方记录信息更有效率。

### 保持不显眼

让你的调试尽可能不显眼。程序的其余部分应该几乎不受受到调试代码的影响。（程序可能会运行得稍微慢一点，用户可能会看到弹出的调试消息。）良好的调试检查在发现 MFU 之前一直保持隐藏且不干扰。

### 基础技巧

### TestAll 函数

假设你的程序正在神秘地崩溃。你不知道具体原因。但随后，你在程序中的各个位置放置了 TestAll 函数。现在你能够缩小 Bug 的范围。TestAll 报告一切正常，然后在 20 行后报告了一个错误。

这个神奇的 TestAll 函数是什么？非常简单，它调用你所有的测试函数。至少它会检查空内存位置、整个堆以及剩余的栈空间。它还会断言全局数据结构。在 Windows 程序中，它调用 ValidateSegments 和 ValidateFreeSpaces。

### TestAll 函数

```
void TestAll (void)
{
  // 测试系统
  TestHeap();
  TestStack();
  TestNull();
  #ifdef WIN
  ValidateCodeSegments();
  ValidateFreeSpaces();
  #else
  TestEms();
  TestXms();
  #endif

  // 测试全局变量
  AssertBool(bInsertMode);
  AssertDbase(&MainDbase);
}
```

每当你创建一个可以在任何地方（全局）调用以执行测试的测试函数时，该测试都应该添加到 TestAll 中。最终，TestAll 会变得非常慢，因为这个原因，你很少调用它。在下面的示例中，funcBad 因为系统错误而崩溃。但代码看起来是无错误的。通过测试，你可以确定哪个函数是

### 使用 TestAll

### 恢复系统状态

我们已经使用了所有运行良好的程序，但 DOS 在使用该程序后不久似乎总是会锁定。我有一个经常使用的程序，从没有出现过任何坏影响。然而，当我在 Windows DOS 盒上运行它时，每次启动都会导致 UAE。显然，它在操作不属于它自己的内存。

当你的程序准备退出时，你应该对系统进行完全测试。许多程序员并不担心退出时的错误信息，然后之后，你就退出了——谁在乎东西是不是稍微搞乱了呢？

这是一种非常危险的做法。首先，这些错误中的许多是 bug 的症状，在不同的配置或使用下，它们可能会在你运行程序时引发问题。其次，这些错误中的许多对操作系统是有破坏性的。如果你的程序返回到 DOS 但 5 秒后锁定，那仍然是你的错。

小心在所有条件下捕获程序的退出。在 DOS 中，如果不监控 `CTRL-C`，当默认的 `CTRL-C` 处理程序退出程序时，你会被调用。在 Windows 下，你不仅检查关闭应用程序的情况，还需要检查 Windows 在应用程序活动运行时自身关闭的情况。

- 1. 调用 `TestAll`。这个单次调用应该测试你的系统的完整性。

- 2. 调用 `StackUsed` 函数（后文讨论）。这将告诉你你使用的最大栈大小。每当你退出程序时，打印出使用的最大栈大小以及总栈大小。这可以给你持续的反馈，让你知道你是否适当设置了栈大小。

- 3. 对比中断表以及任何其他操作系统全局变量（作为 BIOS 数据区域中你感兴趣的部分），以确保你离开系统时的状态与你发现时一致。除非你正在编写某些非常脏的代码，否则这不需要担心——在这种情况下，这只是你最最小的问题。`Bounds Checker`（在工具章节讨论）将检查中断表以及 BIOS 数据区域，查看你是否更改了其中任何内容，因此没有相关的示例代码。然而，如果你不使用 `Bounds Checker`，你需要编写一个程序在启动时（在 c-runtime 初始化代码运行之前）保存中断表。然后在退出时，将现有表（在 `c-runtime_end` 函数运行后）与保存的表进行比较。

- 4. 让系统保持在你发现时的状态。这对于确保你的程序每次运行时都不会吞噬资源至关重要。任何打开的文件都应该关闭。任何分配的 DOS、EMS 或 XPS 内存都应该释放。这对 EMS 和 XPS 内存非常关键，因为 DOS 不会在退出时自动释放它们。此外，如果这些内存没有释放，你的程序在运行时就会浪费资源。

- 5. 检查你的堆是否有未释放的 `allallocate` 内存。如果你使用近堆和远堆，请检查两者。在完成操作后，未释放的内存通常表示逻辑错误。即使问题仅仅是你忘记释放一个指针，你仍然在消耗稀缺资源。

- 6. 检查是否仍有打开的文件。这可能指示完成操作时存在逻辑错误。然而，打开的文件句柄与堆作为稀缺资源一样，如果保持开放，要危险得多。如果系统崩溃，部分文件仍在内存中而不是磁盘上，文件可能会损坏。如果这些内存没有释放，你的程序在运行时就会浪费资源。

小心在所有条件下捕获程序的退出。在 DOS 中，如果不监控 `CTRL-C`，当默认的 `CTRL-C` 处理程序退出程序时，你会被调用。在 Windows 下，你不仅检查关闭应用程序的情况，还需要检查 Windows 在应用程序活动运行时自身关闭的情况。

- 1. 调用 `TestAll`。这个单次调用应该测试你的系统的完整性。

- 2. 调用 `StackUsed` 函数（后文讨论）。这将告诉你你使用的最大栈大小。每当你退出程序时，打印出使用的最大栈大小以及总栈大小。这可以给你持续的反馈，让你知道你是否适当设置了栈大小。

- 3. 对比中断表以及任何其他操作系统全局变量（作为 BIOS 数据区域中你感兴趣的部分），以确保你离开系统时的状态与你发现时一致。除非你正在编写某些非常脏的代码，否则这不需要担心——在这种情况下，这只是你最小的问题。`Bounds Checker`（在工具章节讨论）将检查中断表以及 BIOS 数据区域，查看你是否更改了其中任何内容，因此没有相关的示例代码。然而，如果你不使用 `Bounds Checker`，你需要编写一个程序在启动时（在 c-runtime 初始化代码运行之前）保存中断表。然后在退出时，将现有表（在 `c-runtime_end` 函数运行后）与保存的表进行比较。

- 4. 让系统保持在你发现时的状态。这对于确保你的程序每次运行时都不会吞噬资源至关重要。任何打开的文件都应该关闭。任何分配的 DOS、EMS 或 XPS 内存都应该释放。这对 EMS 和 XPS 内存非常关键，因为 DOS 不会在退出时自动释放它们。此外，如果这些内存没有释放，你的程序在运行时就会浪费资源。

- 5. 检查你的堆是否有未释放的 `allallocate` 内存。如果你使用近堆和远堆，请检查两者。在完成操作后，未释放的内存通常表示逻辑错误。即使问题仅仅是你忘记释放一个指针，你仍然在消耗稀缺资源。

- 6. 检查是否仍有打开的文件。这可能指示完成操作时存在逻辑错误。然而，打开的文件句柄与堆作为稀缺资源一样，如果保持开放，要危险得多。如果系统崩溃，部分文件仍在内存中而不是磁盘上，文件可能会损坏。

- 7. 如果你使用的是 Windows，请确保你释放了所有资源。

### 对象面向编程

面向对象编程（简称 OOP）是当下的流行词汇。它将解决你所有的编程问题，带给你无限的财富，并让你对异性产生不可抵抗的魅力（实际上，无限的财富足够了）。

OOP 的主题值得专门写一本书。在书中，我们将讨论 OOP 如何防止 Bug 出现。同时，讨论 OOP 的哪些部分带带给你这些优势也是同样重要的。

OOP 不需要任何特定的语言。你可以用汇编语言编写 OOP 代码。但像 C++ 这样的语言会强制你采用许多面向对象的实践，并让某些其他实践变得非常容易实现。

在最简单的层次，OOP 意味着保持你的函数相互独立。例如，处理圆的函数中没有关于正方形的代码或数据；正方形的代码中没有关于圆的代码或数据。绘制某个物品的代码中没有关于圆或正方形的代码或数据——但知道如何调用绘制圆或正方形的函数。

程序中的这种可分离性使得易于对对象中的几乎所有函数进行详尽测试。这种可分离性也意味着一个对象的改变不会影响任何其他对象。使用 OOP 的方法进行编码。它将带来一个更易于测试的产品。

尽管如此，要意识到 OOP 并不是万灵药。它让某些类型的测试变得更容易，但它并没有消除对测试的需求。它还引入了一些通常在 C 或汇编语言中不会看到的新 Bug。

### 填充缓冲区

另一个存在感极少被察觉的 Bug 是在缓冲区初始化之前或释放（free）之后使用缓冲区。当你这样做时，大多数情况下，缓冲区仍然包含正确的数据。很多时候，缓冲区会包含合法的数据，尽管不是它应该包含的数据——这导致了非常微妙的 Bug。

### 36 无 Bug 

每当缓冲区被认为为空时，用一个 ID 字节（或者如果你愿意，也用字符串）填充它。这个 ID 字节应该是一个对于被填充结构来说是无效的值（通常 `-2` 适用于所有情况）。这样，如果你在填充缓冲区后访问它，你将获得数据，希望这些数据足够错误，以至于导致立即可见的 MFU（内存访问错误）。

这在文件读取之前非常有价值，可以确保你在成功获取部分读取时处理了文件末尾。填充传入的缓冲区也是一种很好的检查，可以确保传入的缓冲区足够长。如果一个函数返回字符串，且其中一个参数是字符串的最大长度，那么先填充缓冲区将确保在传入的缓冲区太短时产生 Bug。

此外，当你释放一个缓冲区时，先填充它。这可以防止因访问已释放缓冲区而导致的 Bug，因为释放的缓冲区通常持有着旧数据。这不仅适用于释放你分配的缓冲区，也适用于内部缓存缓冲区、结构等。每当你完成任何类型内存的使用时，在释放它之前先填充它。

通过释放内存，如果你在释放后访问这块内存，你保证会得到坏值，希望这能引起明显的 MFU。如果你不填充它，那么当你在内存释放后访问它时，只有在内存被重用到你释放后访问的极少数情况下，你才会看到 Bug。

在不同的时间尝试 `DEBUG_FILL_CHAR` 的多个值。在某些情况下 0 是致命的；在另一些情况下则完全无害。使用 `0x00`、`0x7E` 和 `0xFE` 测试你的整个程序。我发现大多数情况下 `0xFE` 的破坏性最大。我不使用 `0xFF`，因为在很多情况下 `-1` 有特殊的、有时是无害的含义。

### CRC 检查

个人而言，我从未认为有必要进行 CRC 检查。然而，我非常尊重的一位开发者对此深信不疑，所以我由你来决定。我相信在某些情况下它是会有回报的。

使用 CRC 检查第一个场所是数据结构（尤其是那些缓冲通用数据的结构）。通过执行 CRC 检查，你获得了两个额外的检查。首先，如果无法对缓冲区进行一致性检查（缓冲区正在读取一个二进制文件——任何值都是合法的），我们仍然可以验证数据是正确的。

其次，如果我们想确保结构没有变成另一组一致的数据，CRC 将告诉我们，即使我们所信赖的数据集通过了我们的一致性测试，它是否真的发生了变化。

另一个有用的检查是验证你没有写到 `CONST` 段中。如果你使用了 `Bounds Checker`（参见工具章节）或运行在保护模式操作系统下（例如标准模式或增强模式下的 Windows 应用程序），它将为你完成这一工作。但是，如果你没有这些选项，可以在启动时对这些段内存进行 CRC 检查，然后在你的 `TestAll` 函数和程序退出时进行比较。

在这两种情况下，这通常是由于指针松散导致的。请记住，某些第三方库使用了自修改代码，这会使这种测试变得困难。然而，由于 80286 及后续芯片具有芯片预取队列，自修改代码已成为一种越来越少使用的危险做法。

### 断言整个世界 (ASSERT THE WORLD)

几年前，我正在编写一段代码，对一个我正在遍历的缓冲区执行一些非常复杂的操作。我有几个指针，它们之间存在着非常特定的关系。如果其中一个指针相对于其他指针有偏差，我就会得到严重的错误。

我在这段代码上花费了好几天时间，每次发现一个 bug 都会追溯其原因。几乎每当我发现一个 bug 时，另一个 就会产生。最后，在绝望中，我写了一个函数，在每次循环开始前检查这些指针之间的关系。如果指针不匹配，我会打印出每个局部变量的值。

在几小时内，我找到了剩余的 bug 并让该函数正常工作。我将断言代码封装在 `#ifdef DEBUG` 中并将其留在那里。代码中随后出现的 bug 会自动暴露自己。

从那时起，我几乎在任何地方都使用这种实践（断言）。它不仅可以节省你几天追踪 bug的时间，还能发现那些否则无法发现的 bug。最后，对于那些从未发现过 bug 的断言，你可以感到代码更加安全——你确定某些部分正在运行正常。

当你检查代码时，你会在某些地方知道变量持有某个值，在某些地方你认为一个变量持有某个值。不幸的是，你可能在某些地方*希望*一个变量持有某个值（严重的 MFU 警报）。在大多数情况下，诚实的答案是，你认为一个变量持有某个值。

“不知道”这一事实是编程的一部分。如果你编写一个底层函数，你无法控制调用你函数的代码。在一个复杂的过程中，你认为自己理解代码可能采取的每条路径，但你无法确定。


### 断言救急

为了解决这个问题，我们大量使用了断言能力。一个 `assert` 函数检查一个布尔表达式，如果为真，则调用警告信息函数。例如，你可以在将字符串拷贝到 16 字节的静态缓冲区之前放置 `assert(strlen(pStr) < 16);`。如果字符串长度超过了 15 字节，断言宏将打印一条信息，列出导致错误的源文件路径和行号。

### Assert 宏



下面的程序示例说明了标准 `assert` 的用法。

```
#ifdef DEBUG
#define assert(b) ( b ? printf("##b in File: %s, Line: %d\n", __FILE__, __LINE__) : )
#else
#define assert(b)
#endif
```

在大多数情况下，断言中的代码是非常快的，所以要在代码中到处使用断言。你不会看到很大的性能影响。但当断言失败时，它会直接指向错误，并显示文件名和行号。

在大多数情况下，诚实的答案是你认为一个变量持有某个值。

“不知道”这一事实是编程的一部分。如果你编写一个底层函数，你无法控制调用你函数的代码。在一个复杂的过程中，你认为自己理解代码可能采取的每条路径，但你无法确定。

### 无 Bug

你假设某些情况不会发生，或者在代码的某些地方必须发生。在代码中放置一个断言来测试这种情况，并在不可能发生或确定情况失败时进行打印。放置这些断言的最佳方法是在完成后查看函数函数并问自己可能会出现问题。通常代码中的一个或多个地方会引起你的注意。在那里放置一个。在调试过程中，你还会遇到本可以通过 `assert` 解决的 bug。在那里放置一个，并在下次放置断言时记住这种情况。

例如，如果你假设两个 `int` 相乘的结果始终是一个 `int`，那么就 `assert((long)i * (long)i < 0x7FFF);`。当你遍历树时，如果你假设某个指针总是有效的，那么就 `assert(pTree != NULL);` 或 `assert(pTree->uID == ID_TREE);`。最重要的断言之一是在调用函数或返回结构体时，检查结构体的 ID。

### 断言字符串

下面的程序示例说明了字符串断言的用法。

```
#ifdef DEBUG
```

```cpp
#define DebugAssertStr(pStr) CheckStr(pStr, __FILE__, __LINE__);
#else
#define DebugAssertStr(pStr)
#endif
```

每个结构都有自己的 `Check` 函数。你可以使用断言宏，然后在 `__line__` 进行检查。这不仅会导致程序变大，还使得复杂的检查变得不可能。

如果 `Check` 函数中存在问题，它会调用 `AssertPrintf`。这也会通过 `__FILE__` 和 `__LINE__` 信息传递。断言的方式都是相同的。例如，在 Windows 中，你可以使用 `MessageBox` 并显示文件：`dave.c`，行号：`23`。

当断言失败时，我们如何知道你是否指向了数据结构？`Check` 函数的第一部分是检查：

- 你是否真的指向了数据结构？
- 数据结构是否持有有效值？
- 值是否是否一致？

有时你无法真正判断是否指向了数据结构，因此你所做的就是检查它持有有效数据。

所以看看我们可以如何检查复杂的结构。但对于简单的数据呢？大多数 `int` 都会在一个范围内的值。如果你在维护一个百分比计数（例如设置程序中的进度条），该变量应该 ≥0 且 ≤100。（它还应该随着变化而增加，但该规则特定于计数）。因此，你可以在断言中添加最小值和最大。如果两者都为 0，则不要检查范围。

### AssertBool

你可以简单地断言布尔值。布尔值应该是 `TRUE` 或 `FALSE`。`TRUE` 定义为非零值，但在几乎每个程序中，它通常是一个特定的值。如果布尔是字节（byte），那么随机值为 `TRUE` 或 `FALSE` 的概率只有 1/128。如果布尔是整数，持有合法值的概率更低。

所以 `CheckBool` 可以检查 `TRUE` 和 `FALSE`。随机值始终无法通过测试。尽管 `CheckBool` 并不完美，但它提供了很大的帮助。

### Assert a Boolean

程序示例说明了断言布尔值。

```c
BOOL CheckBool(char *pFile, int iLine, BOOL bVal)
{
    if (bVal != TRUE && (bVal != FALSE))
    {
        AssertPrintf(pFile, iLine, "BOOL = %d", bVal);
        return (TRUE);
    }
    return (FALSE);
}
```

### Assert an Integer

程序示例说明了断言 `int`。

```c
BOOL CheckInt (char *pFile, int iLine, int iVal, int iMin, int iMax)
{
  // 查看是否已初始化
  if (iVal == DEBUG_FILL_WORD)
  {
    Assertf(pFile, iLine, "iVal == DEBUG_FILL_WORD");
    return (TRUE);
  }

  // 查看是否需要检查最小/最大
  // 如果两者都为 0，则不要检查
  if ((! iMin) && (! iMax))
    return (FALSE);
  // 检查最小/最大
  if ((iMin <= iVal) && (iVal <= iMax))
    return (FALSE);
  // 不是 - 告诉用户
```

### 参数验证

参数验证是断言的一种。在进入每个函数时，对传入的每个参数进行断言。通过这种方式，你确保了所有传入的参数都是有效的。

### DEBUG PRINTSFS

我们现在编写了一些例程来帮助发现和消除 MFU（主要故障单元）。然而，我们需要某种方式让这些代码与我们进行通信。同时，我们不希望调试输出与正常输出混杂。因此，我们需要用于显示信息的调试函数。

一组有效的调试打印函数决定了调试信息是帮助你调试，还是会成为你的障碍。本章将展示如何显示调试信息，而不会干扰程序对数据的正常显示。

你需要调试打印主要有两个原因：

- 第一，用于消息框（Message Boxes）。它可以告诉用户发生了错误，然后要求用户在继续之前按一个键。通常，当断言或参数检查失败时，应该使用消息框，让用户停在错误处。

- 第二，用于信息性消息。这些消息告诉你程序当前正在做什么，程序在打印每条消息后应该在无人干预的情况下继续运行。列出正在处理的 Windows 消息就是一个信息性消息的好例子。

调试 printf 是消除代码 Bug 过程中的重要工具。当出现问题时，你应该尽可能直接地显示错误。在用户面前弹出的消息框可以很好地满足这一需求。创建一个易于格式化和调用的此类弹出函数是非常重要的，这样它就能出现在任何需要的地方和任何需要的时间。

然而，同样重要的是一种整洁且易于列出信息性调试消息的方法。如果实现得当，这些消息将允许你将程序内部的操作与监视器显示的操作进行比较。如果调试 printf 显示你正在编辑一个文档，而你的程序显示的却是另一个，那么可能可能出了问题。

下面的程序并没有将调试 printf 写入串行终端，而是写入单色显示器，该显示器被划分为多个窗口。因为显示器被划分为窗口，向一个窗口的 printf 不会将另一个窗口中的有用信息滚出屏幕。

条件调试 printf 仅在开启时打印。它们可以通过编译时定义或运行时变量（在第3章介绍）来开启或关闭。使用定义要简单得多，但需要你重新编译程序来开启或某些调试打印。使用调试变量稍微复杂，但它们允许你在不重新编译程序的情况下开启和关闭调试。

本章讨论了这三个过程：调试弹出消息框、打印到第二个显示器的调试 printf 以及条件调试 printf。这些功能的几乎所有代码都列在附录中。由于没有办法将代码拆分成小块，因此我没有在书中间放置一大块代码，而是将这些代码移动到了附录。

### 消息框 (Message Box)

即使在 Windows 下，一个良好的消息框函数也需要一些编码。在 DOS 的情况下，它需要大量工作。你使用两个消息框函数：DebugMessageBox 和 DebugMessageRes。DebugMessageBox 的参数与 printf 相同。DebugMessageRes 使用资源（resource）而不是格式化字符串。

这种资源将格式字符串从默认数据段移动出来。如果你大量使用断言和参数检查（你应该这样做），你可能会发现所有对 DebugMessageBox 调用的格式字符串消耗了默认数据段的很大比例，可能导致你空间不足。因为调试代码的工作是解决问题而不是引起问题，所以你应该将字符串存储为资源而不是数据。

因为 DOS 与 Windows 不同，没有资源，因此字符串存储在远数据段（far data segment）中，并带有其的资源号。当调用 DebugMessageRes 时，字符串从远数据段复制到缓冲区中，然后调用 DebugMessageBox。这样一来，字符串仍然不在默认数据段中。

DOS 有两种类型的消息框。第一种简单地在屏幕上执行 printf。第二种会在屏幕上弹出一个框，在用户按一个键后消失，并将之前被框住的内容放回屏幕。弹出框在显示框之前会强制屏幕切换到 80 x 25 模式，完成后将屏幕切回之前的模式。因此，即使你的程序没有处于字符模式，只要它使用 ROM BIOS 进行屏幕切换，弹出框就应该正常工作。

当框出现时，你只能按 <CR> 或 ESC。如果你按 <CR>，程序将继续。如果你按 ESC，程序将退出到 DOS，并将消息框留在屏幕上。如果你遇到了一个让你想要退出的错误——例如，继续运行可能会导致你的硬硬盘被重新格式化——那么 ESC 就很有用了。它还具有将调试信息留在屏幕上的额外好处。

Windows 使用 Windows MessageBox 函数。它以 TASKMODAL 状态引入，因此你的程序被停止了，但你仍然可以使用系统上的其他程序。退出一个 Windows 应用会导致大量消息被处理，在 Windows 中按 ESC 不会退出程序。相反，它会关闭 MessageBox 处理，以便后续消息不再被显示。

这证明了 DOS 和 Windows 之间功能上的差异。然而，我发现 Windows Windows 下，一个错误导致后续 50 到 100 条错误消息是常见现象。然而，我可能想在第一个错误发生后继续测试，而不需要按 100 次 <CR>。在 DOS 下，这种级联错误要少得多。这是环境差异的本质属性。

调试消息可以用另一种方式打印。使用本章稍后描述的 DebugPrintf，调试消息显示在调试监视器中，然后等待按键。使用此系统的 Windows 3 时，程序的显示完全不受影响。

### 条件打印

一旦你向程序中添加了资源、`DebugPrint` 以及上述其他功能，请将它们移除。你永远不知道何时会再次需要它们——而且，移除它们是一项额外工作。相反，请使用一种方法来开启和关闭调试代码。

你可以通过两种方式实现这一点：使用 `#if` 来决定是否编译某些调试代码，或者使用调试变量在运行时决定是否执行某些调试代码。

通常，如果你在每次需要切换调试开关时都要重新编译，并且对于想要执行的哪些调试代码有一套非常简单的规则，请使用 `#if`。如果情况更复杂，请使用变量。两种方法都列在下方。

### 条件定义

通常，在我使用条件定义的代码中，`DEBUG` 和 `VERBOSE` 设置了我想要执行的错误检查数量，而 `VERBOSE` 设置了我想发送到 MDA 的信息量。

错误检查需要时间。在许多情况下，检查只需查看指针是否为 `NULL` 或结构体 ID 是否正确。这些检查都不占用多少时间或空间。

另一方面，对缓存中的所有缓冲区进行 CRC 是非常昂贵的——特别是如果检查被频繁调用。因此，随着 `DEBUG` 值的增大，程序会变慢。我建议使用以下值：

```
DEBUG == 0    无调试
DEBUG == 1    测试版保留
DEBUG == 2    快速检查
DEBUG == 3    中等检查
DEBUG == 4    慢检查
DEBUG == 5    极慢检查
```

对于你的第一个版本，将使用 `-DEBUG=1` 进行编译。作为性能略微下降的代价，断言、参数检查等将由测试人员检查。

这并不意味着对大多数代码都使用这些值。在大多数调试代码中，检查是非常快的，所以如果 `DEBUG > 0` 就执行检查。如果你使用这种方法，请确保当 `DEBUG == 0` 时没有任何调试代码会被编译。

测试之外的问题是你想发送到 MDA 的信息量。如果某个模块出现问题，你不希望看到该模块的调试打印。

另一种方案是使用变量。这种方法带给你一些优势：

### 观察栈

几乎每个人都写过栈空间耗尽的程序。我们大多数人是如何发现这一点的呢？我以前的做法是，如果开始遇到一些奇怪的错误，例如局部变量或返回地址突然被覆盖，我会增加栈的大小。如果问题消失了，我就认为问题解决了。

另一个相关问题是使用未初始化的局部变量。在 C 语言中，所有未初始化的全局变量都被设置为 0，因此从某种意义上说它们被初始化了。然而，局部变量初始是随机值。这使得重复此类问题变得极其困难。

本章包含一种在调试模式下初始化所有局部变量的方法。这样，如果你的代码在设置值之前使用了某个局部变量，该 bug 将变得可复现。

### 栈空间

你的程序使用了多少栈空间？这是程序面临的最关键问题之一，却是答案最少的问题之一。如果你的程序栈空间太小，它会在随机时间“崩溃”，导致各种问题。如果栈太大，你虽然不会遇到栈问题，但限制了本可以用于其他用途的内存。你从不使用的额外 1K 或 2K 栈（有时是 4K 或 8K）在内存紧张（即 `malloc` 失败）时可能会产生巨大影响。

那么，大多数程序的栈大小是如何确定的呢？在大多数情况下，开发者从默认大小开始。如果出现错误，开发者将其归因于栈溢出，或者通过任意增加栈的大小来解决。想一想：在你最后发布的程序中，栈的利用率有多多少？

栈的大小不仅对你自己的程序至关重要。当发生硬件中断时，中断处理程序将使用你的栈。许多 TSR 都是这样做的。你通常应该有一个足够大的栈，以至于你使用了它的最后 512 字节。这让你在带有 BIOS 或比你系统使用更多栈的 TSR 的系统上有一定的回余地。512 字节是一个在 DOS 使用小栈（256 字节）之前的安全数字，如果 TSR 使用了超过 256 字节，那么该 TSR 可能会导致 DOS 崩溃。

对于其他简单的顺序程序，没有办法在每种情况下都测量栈的使用。但是，你可以在每次运行程序时轻松地测量栈的使用。通过观察各种情况下的使用情况，你可以获得整体使用的理想值。

你还可以在每次进入函数时检查栈，看是否剩余足够的空间。如果空间紧张，你可以使用 `DebugMessageBox` 警告你已耗尽栈。通过这里描述的两个工具，你可以确保你的栈既不过大也不太小，而是恰好合适（类似于“金发姑娘和三只熊”）。

栈工具是非常特定编译器的。我所知的每个编译器都有一个变量值或位置，允许你确定栈的开始和结束。每个编译器还有一个调用，可以放在每个函数的开头，以检查是否为该函数的局部变量留了足够的空间。下面的代码适用于 Microsoft C 7。

### 监控堆（HEAP）

我们现在来到臭名昭著的堆。这似乎是 C 语言中最常见 bug 的根源。即使是松散指针（loose pointer）bug，通常也是由于指针至少在理论上应该指向堆中的内存导致的。幸运的是，本章列出了一些技巧，我们可以利用这些技巧让堆几乎变得无坚不摧。

大多数程序员都曾（通常不止一次）因覆盖堆而创建过 bug。其他严重问题还包括为 `malloc` 分配的指针传递错误值、在 `free` 之后使用指针，以及留下不再需要的已分配内存，这会迅速耗尽你的堆。

本章将教你如何监控分配内存末尾（或开头）是否被覆盖。以下代码以两种模式运行。第一种是调试模式，它将使内存分配花费更长时间并占用更多空间。第二种用于最终发布，它不会为内存分配增加任何开销——无论是时间还是空间。在消除任何堆问题之前，使用调试模式，然后切换到非调试模式。

### 代码背后的概念

该代码实现了四个简单的概念。

- 1. 它在所有 `malloc` 分配的内存前后放置特殊的单词。如果你覆盖或划了 `malloc` 分配的内存，这些特殊单词的值就会改变，当下次检查这些特殊单词时，你就会发现非法访问。

- 2. 它维护一个分配内存的双链表。每个 `malloc` 都会进入列表，每个 `free` 都会被移除。这个列表使得你可以随时遍历链表，以检查或转储所有 `malloc` 分配的内存。

- 3. 它存储了最初 `malloc` 或重新分配堆内存的调用位置（源模块文件名和行号）。所有影响堆的 `malloc` 调用（`malloc`、`realloc`、`free` 等）都会传入它们调用所在的文件名和该文件中的行号。然后，文件名和行号与所分配的内存一起存储。因此，当显示堆中的特定 `malloc` 条目时，它会列出创建、调整大小或释放它的调用位置。这使得你很容易确定代码中列出的分配是在哪里被 `malloc`、重新分配和 `free` 的。

- 4. 在每次 `malloc` 用的开始处，函数会遍历堆并检查是否有被覆盖或损坏的内存。由于这些检查频繁执行，你通常可以在动态内存被覆盖或损坏后的 10 或 20 行内发现。这通常会让调试变得相对简单。

### 句柄跟踪

Unfortunately, you cannot place headers and titles on EMS/XMS memory as you can on the heap. However, you can still implement most of the checking you can have with the heap.

First of all, for each EMS/XMS allocate, we allocate a header like the one we use with the heap. However, this memory is generated by a malloc in regular memory. We use this malloc memory to track our usage of EMS and XMS memory (as well as file handles in the next chapter).

These structures hold the handle of the malloced memory. Because each handle is unique, you have a linked list for EMS and another for XMS. This adds a small amount of processing. With heap memory, you know where the structure is when passed a pointer. With EMS and XMS, you have to walk the appropriate linked list to find the handle you were passed.

To do this, we create a set of handle calls. The first creates a linked list. Each linked list has a different data size to store the information associated with a given set of handles. This becomes important when used with files where you want to store the filename, which can be 74 bytes long.

### 扩展内存 (XMS)

在所有从 XMS 的拷贝操作中，验证传递给 `copy` 的字节数是否为偶数。这是 XMS 规范的要求。然而，在某些 XMS 处理程序上被强制，而在另一些上没有。传递奇数字节会导致某些系统上出现错误。

如果你锁定了 XMS 内存，务必跟踪锁定情况。锁定会导致 XMS 内存碎片化，使其可用性大大降低。在释放 XMS 时，如果内存仍被锁定，你应该弹出一个框。如果在程序结束时未释放的内存仍锁定，你也应该将其列出来。

### 文件 I/O

只写程序可能是存在的最具致命性的 MFU（内存功能单元）之一。只写程序可以将数据保存到文件中，但无法读回。这要么是写入方式有 Bug，要么是读回的代码有 Bug。然而，当用户意识到问题时，通常已经太晚了——数据已经丢失。（Sysos 在这方面臭名昭著，你可以将数据备份到带上，但只需尝试恢复其中的。）

### Seek (跳转)

`Seek` 非常有趣。在 DOS 中，它仅仅更新文件表中的一个值。它没有进行任何形式的验证。如果你跳转到文件末尾之外关闭文件，文件不会增长到新的 seek 位置。如果你跳转到可用磁盘空间之外，不会返回错误。

你可以通过两种方式查看 `seek`：

- 1. 除了检查句柄外，你可以不对其进行任何测试。你可以在读写操作内部检查，查看你是否越过了文件末尾。
- 2. 你可以检查每次 `seek`，看它是否将指针放置在文件之外。

### Read (读取)

在 `read` 上你可以最重要的测试是在读取完成后进行断言。如果可能，对每次 `read` 进行断言。这种断言比所有其他测试都有价值。话如此（不幸的是，这通常被忽略了），可以在任何 `read` 上进行测试。`read` 应该包含进入时检查句柄。它应该包含完成后检查 `errno`。如果 `errno` 为任何非零值，应弹出提示。在文件末尾，`errno` 为 0，因此错误是异常事件。此外，你应该检查是否正在读取文件末尾。如果已经在 `seek` 中包含了此项，则不需要将其放入 `read` 中。然而，由于测试如此简单，我建议也将其放在 `read` 中。你应该在 `read` 中放置额外的测试。首先是在执行 `read` 之前填充缓冲区。这样，如果你假设接收了一个完整块，显然会看到垃圾数据。否则，你的程序可能不会崩溃。此外，如果 `read` 返回了错误的字节数，你的程序再次看到错误数据。尽管在 DOS 中这从未有问题，但网络和磁盘缓存并不可靠。这让你遵循里根的格言：*信任但要验证*。下面的程序示例说明了从文件读取。

### 构造函数和析构函数

在构造函数中，记得执行以下操作。通过这些操作，c++ 自动化了我们在 c语言中必须显式执行的结构设置。

- 1. 将所有变量设置为 FILL_CHAR。小心，因为类中的数据并不总是连续的。虚函数地址可能会潜伏在变量之间（通常当变量是一个类时）——如果你覆盖了它们，你是在制造 bug 而不是发现 bug。解决这个问题的简单方法是将所有数据放在一个结构中。你可以直接访问元素（大多数编译器也支持匿名结构），然后用 FILL_CHAR 填充结构。
- 2. 在调试模式下，为每个类添加一个 ID 字节或字）。在构造函数中，将 ID 设置为已知值（每个类不同）。由于 C++ 自动调用构造函数，你就可以保证已经设置了 ID 元素。

### string 构造函数

下面的程序示例说明了字符串构造函数的用法。

```c
#define STRING_ID 0x13
class string
{
private:
    struct s_string
    {
        char str[20];
        char len;
    } vars;
#if DEBUG
    char ID;
#endif
    :

string :: string ()
{
#if DEBUG

    ID = STRING_ID;

}
```

### 字符串析构函数

作用域内，你现在正在检查每一个变量。这是一个强大的工具。

其次，你用 `FILL_CHAR` 填充数据结构。然后，如果你在变量被销毁后访问它，你将获得垃圾数据。你还会重写 ID，导致 ID 错误。你特意重写了 ID，以确保 `memset` 实例的 `FILL_CHAR` 等于正确的 ID 值。

下面的程序示例说明了字符串析构函数的使用。

```cpp
// note - 在非调试模式不需要析构函数
#if DEBUG
string() : ::string ()
{
    // 确保 ID 是正确的
    if (ID != STRING_ID)
        DebugBox("Bad String ID returned");

    memset(&vars, FILL_CHAR, sizeof(s_string));
    ID = ~STRING_ID;
}
#endif
```

通过在构造函数和析构函数中使用上述实践，你就可以从我们所有的类中消除以下类型的错误。如果你使用了未初始化的变量，将得到一个坏值（`FILL_CHAR`）。如果你得到了一个错误的指针，在销毁错误的指针时，你会收到一条消息。最后，如果你覆盖了数据，也会收到一条消息。如果你尝试在变量超出作用域后访问它，将得到坏数据。

仅仅通过在每个构造函数和析构函数中放置少量代码，我们就获得了所有这些强大的功能。而且性能影响微乎其微。

### 基类断言

大多数 C++ 程序员使用一个所有类都派生的基类。仅在调试模式下，为基类添加两个方法。第一个是 `Assert` 函数。你只需调用 `inst.Assert()` 对类的任何实例进行断言。在非调试模式下，`Assert` 应该定义为空空函数，这样就不会为断言调用生成代码。

这把断言放在了它应该，作为类定义的一部分。随着类的变化，它的断言也会之变化。它也使得断言任何实例变得非常简单。

### 创建局部变量

局部变量通常是汇编语言程序中错误的源头。当你添加变量或更改其大小时，可能会引入错误。其中一条代码路径可能在返回之前没有从栈中消除新变量。另一个代码路径可能会引用变量的旧位置——即在新变量移动栈中所有内容之前使用的位置。最后，你没有像在 C 语言中那样初始化局部变量。

我们通过创建一个持有局部变量的结构体来解决这些问题。然后，对于一个函数，替换结构体的大小以为局部变量留空间。返回时，加上结构体的大小。由于大小的变化，增加或减少局部变量不会产生问题。

我们还将 `BP` 设置为局部变量的基地址。你就可以可以使用结构体来访问所有局部变量。这有几个优势：

- 如果局部变量在结构体中移动，你仍然在正确的位置访问它。你不需要遍历并更改所有的 `[bp + 8]` 为 `[bp + 10]`，`[bp + elem]` 将继续有效。

- 如果你删除了一个局部变量，你将在汇编阶段知道是否仍然在使用它。因为变量已从结构体中删除，仍然访问该元素的代码将编译失败，因为该元素已被移除。

- 这确保了变量大小的类型检查。如果你尝试从字大小的寄存器或结构体中的字节大小元素移动，汇编器将报错。

在调试模式下，你还用 `FILL_CHAR` 填充局部变量。同时，你应该捕获任何未初始化的局部变量。

### 测试过程

你已经写好了程序，而且它可以运行良好。那么接下来要做什么？发布它！开个玩笑——那是老办法了。本章以及接下来的章节描述了创建程序的后半部分——测试过程。这些章节与编码过程本身对于交付一个良好的产品同样重要。

这些章节将阐述你的测试过程应该如何运作。如果没有这些实践，你将得到一个可能看起来不错，但由于其中仍存在大量 MFU（低级错误）而无法使用的程序。那么，流程是什么呢？

它非常简单：你现在必须找到并移除你在代码中放入的所有 MFU。无论你自己在尝试编写无 bug 代码时做得有多出色，你总会有 bug。你的整个测试过程取决于你是否遵循这一哲学。如果你不把测试视为寻找你自己在代码中引入的 MFU 的过程，你就无法发现它们。

### 开发人员与测试人员

大多数开发者在写完代码后，都希望不要发现 bug。毕竟，他们的乐趣在于编写新代码。追踪和纠正 bug，以及向系统中引入新的 bug，通常是一个非常痛苦的过程。当 bug 被发现时，开发者通常会对被提醒这些问题感到恼火。然而，如果开发者以这种态度对待 bug，你可能会发布一个健壮的产品。

但是，如果测试人员采取这种态度，你就能保证发布一个充满 bug 的产品。测试人员必须采取这样的方法：如果他们没有找到 bug，他们就失败了。他们应该由于过了糟糕的一天而沮丧地回家。如果他们发现一个接一个 bug，他们应该高兴地回家，兜里还揣着奖金。

重复一遍：测试小组的工作不是证明产品是 bug 的。测试小组的工作是尝试找到产品中所有的 MFU。每天，测试人员都应该努力寻找新方法来破坏他们正在测试的产品。一个优秀的测试人员是极的愤世嫉俗——无论开发者做什么，测试人员都会找到让它崩溃的方法。

测试人员还要验证产品是否如广告所言。当营销人员忙于根据新功能推销即将上市的产品时，测试人员必须检查每个功能是否都在产品中，以及它们是否符合预期。

### 瑕疵并存

bug 确实存在。测试人员的目标应该是识别出每一个。他们的工作是为我们提供程序当前状态的完整画面。

你可能决定不修复某些 bug，但在发布之前，你必须**知晓**每一个存在的 bug。如果你不知道代码中有什么 bug，那么在发布后几乎肯定会出现很多糟糕的 bug，并导致“每周修复光盘”综合征——你每周都要发布一个光盘来修复用户发现的某个 bug。这通常会形成恶性循环。当你发布所有原始 bug 的修复程序时，你会开始收到由于修复而引入新 bug 的报告。

从同样的标准来看，如果你想运行一系列手动测试，测试人员需要一个非常充分的理由才值得投入的时间和金钱。然而，重新运行一系列自动化测试只需要有人启动它们即可。事实上，由于测试人员花费了时间编写这些测试，他们会尽可能地运行这些测试。

每当程序发生更改时，无论这种更改是多么微小和无关紧要，在项目后期（即只允许修复重大 bug 的时候），这可能变得至关重要。

如果想得没错，测试人员会将大部分时间花在首次开发自动化测试上，而实际进行测试的时间很少。与此同时，测试系统几乎在不断运行，自动执行它们的测试。

### Bug 报告

bug 报告过程也应该是自动化的。当一个 bug 被报告时，应该尽可能将关于 bug 的信息传递给相关的开发人员。

一个能够报告发现 bug 的所在系统所有信息的程序是一个非常有用的功能。除外，它应该包含系统 `config.sys` 和 `autexec.bat` 文件的副本，主板和 ROM-BIOS 制造商等。它应该告诉你任何可能与 bug 相关的信息。

将信息写入日志文件的能力是程序调试版本中应包含的另一个有用功能。当发现 bug 时，日志文件的内容通常会提供所有所需的信息。虽然这对于在最终产品中不是一个适当的功能，但在 Beta 程序中非常有价值，特别是如果它可以被关闭（为了速度）。

测试人员在将 bug 交给开发人员之前，需要先重现该 bug。如果测试人员无法重现该 bug，那么他们或开发人员都没有办法验证它是否已被修复。

如果 bug 只发生在一个系统上，那么测试人员和开发人员将不得不使用该系统。如果该系统位于 Beta 现场，这可能会成为一个问题。在这种情况下，如果 bug 足够严重，则需要将计算机运送到开发现场。

当 bug 被修复后，开发人员需要通知测试人员。这种通信通道应该是自动化的（电子邮件非常适合此类）。测试人员可以进行测试以查看 bug 是否真的被修复。测试人员是决定 bug 是否已真正修复的人。

如果没有自动化测试来发现已修复的 bug，那么测试人员应该强烈考虑将其添加到现有的测试中，或者编写一个测试来检查该 bug。如果它发生过一次，它可能会再次发生。这种“回归测试”可能是至关重要的。很多时候，修复一个 bug 会引入一个新的 bug。在修复新 bug 时，另一个开发人员可能会在无意中重新引入旧 bug。

### Bug 数据库

跟踪 bug 与发现 bug 一样关键。如果发现了一个 bug 但从未被修复，那么程序并不会好转。如果一个开发人员在工作一周后确定某个 bug 无法修复，你不希望另一个开发人员再花费一周时间去重新发现相同的问题。

如果两个人报告了同一个 bug，你不希望由两个不同的开发人员去修复它。如果一个 bug 被修复，然后在另一个较晚的版本中重新出现，引用早期的报告应该引导开发人员找到真正的 bug。

Bug 数据库不仅仅是计算机上的一个简单数据库。它部分是通信程序，部分是流程，部分是数据库。它是跟踪 bug 的手段。

虽然一个人的努力可以简化这一过程的大部分，但实际过程仍然应该存在。独立工作的开发人员/测试人员仍然需要跟踪 bug。

如果可能的话，应该由一个人将所有 bug 输入系统。这个人是 Bug 主管（Bug Master），是整个开发过程中最不受感谢的工作之一。发现 bug 的个人应该将 bug 报告通过电子邮件发送到 bug 邮箱（假设你有电子邮件）。

项目上的所有开发人员和测试人员都应该在这个别名列表中，并应该阅读所有发送该别名的邮件。很多时候，开发人员或测试人员会知道 bug 的答案，并可以向发送者和 Bug 主管发送回复，从而节省大量时间。

这一点值得重复。开发人员的工作不是等待分配 bug。开发人员的工作是帮助发现他们置于程序中的所有 MFU（用户功能故障/缺陷）。获取每个 bug 报告的副本，即使大多数报告在阅读第一行或两行后被丢弃，对这一过程来说也是至关重要的。

虽然每个人都阅读发送给 bug 别名的邮件，但 Bug 主管是执行操作的人。他或她将 bug 输入数据库。在数据库中输入 bug 应该包含分配给该 bug 的开发人员和测试人员的姓名。这应该会向他们以及报告 bug 的人同时生成电子邮件。

当 bug 被指派时，它还会被分配一个“严重程度”（severity）。这种严重程度通常应该是小范围内的一个数字，清晰地说明该 bug 的关键程度：

- 等级 1：程序导致灾难性的破坏（例如，格式化你的硬盘）
- 等级 2：某些主要功能无法工作（例如，你无法打印）
- 等级 3：某些次要功能无法工作（例如，无法自动备份）
- 等级 4：程序可以运行但有问题（例如，无法到驱动器）
- 等级 5：设计缺陷
- 等级 6：未来的建议（例如，允许通配符）

按严重程度分类有两个原因很重要。首先，它允许开发人员优先处理 bug。其次，随着发布日的临近，只有低程度的 bug 会被修复。因为修复 bug 可能会引入新的、更严重的 bug，你在最后时刻需要非常小心。

你可以随时更改 bug 的严重程度。然而，这种对级别的评定对于管理层判断何时可以发布非常重要。

当 bug 被修复后，开发人员需要将修复细节输入数据库。这为该 bug 再次出现时提供了参考。它在尝试解决类似的 bug 时也有用。

开发人员发送电子邮件给测试人员和 Bug 主管，表示他认为 bug 已修复。此时，bug 被分配给测试人员。现在，由测试人员负责确定 bug 是否已消除。理想情况下，当开发人员修复 bug 时，测试人员正在编写针对该 bug 的自动化测试。

如果多个开发人员在同一个程序上工作，通常更有效的方法是每周（有时更多或更少）构建一次程序，并将该构建交给测试人员。（构建提取所有人提交的代码并创建一个大家使用和测试程序版本。）测试人员可以对该构建进行测试。

定期的（通常是每周）构建带来了巨大的优势。首先，在测试 bug 是否被修复时，测试人员测试的是该周进行的所有更改，而不仅仅是修复该 bug 的一个小更改。其次，可以在新构建上运行整个自动化测试套，允许测试人员判断修复是否破坏了其他部分。

最后，如果测试人员确定 bug 已修复，那么他或她将向 Bug 主管和开发人员发送公告。该 bug 在数据库中随后被标记为已修复。

有时开发人员会确定某个 bug 无法修复。这个决定可能会由管理层审查，但如果最终决定该 bug 无法修复，那么它在数据库中就会被标记为“无法修复”。在这种情况下，在数据库中充分记录该 bug 变得更加至关重要，因为它可能会再次被报告。




最后，时间限制可能导致 Bug 无法被修复。5 级和6 级的 Bug 通常不值得投入时间。即使值得投入，发布之前可能也没有足够的剩余时间。无论何种情况，这些 Bug 都应该被处理为推迟。推迟的 Bug 列表将成为下一个版本建议功能列表的一部分。

在整个过程中，Bug 主管（以及开发人员和测试人员）需要定期检查整个数据库，以发现重复的 Bug 报告。有时，她或他还会发现已解决或无法解决的开启状态 Bug。

所有分配的 Bug 都被视为开启状态。这才是关键的 Bug 数量。（拥有 1000 个实际上是功能增强的推迟 Bug 并不是一个很有意义的数字。拥有1级和2级 Bug 是严重问题的标志。）这个 Bug 数量每周都需要下降。如果这个数量不受控制，你的发布日期将进一步向未来推迟。

尽管数量有时会上升（例如，在 Beta 版本发布后不久），但必须将其重新纳入控制。实际数量取决于 Bug 的严重程度、项目开发人员人数以及开发阶段。

然而，对于已完成程序部分，严重事项的 Bug 数量每个开发人员应该是个位数。在程序的后期，它应该少于四个。如果你有高 Bug 数量，说明开发人员手中 MFU（缺陷功能）与运行代码的比例过高。

拥有大量充满 MFU 的代码没有太大处。如果你的另一个选择是较小的运行代码量，那么你会好得多。如果 Bug 数量太高，请停止新开发，专注于消灭现有的 Bug。在 Bug 数量恢复到合理水平之前，不要允许新开发。

并且请记住，你无法大幅改变一个开发人员一天能修复的 Bug 数量。如果数量持续上升，即使在全力修复模式下，你也完蛋了。如果数量以相对恒定的速度下降，那么你不能仅仅因为发布日期临近就计划将该速度翻倍。

### 测试流程

你测试流程的成功取决于三点：

- 你的组织水平
- 测试人员的专业知识
- 管理层的支持

有了良好的测试流程，你可以交付出色的软件。如果没有它，你毫无希望；随着每一次带有 Bug 的更新，留用你程序的用户会越来越少，会有更多的人转向那些测试工作做得良好的竞争对手。

### 内部测试

程序由多个小组进行测试。开发人员自己会进行一些测试，通过运行程序查看其新功能是否导致了其他问题。测试团队同时使用自动化和手动测试。最后，用户在 Beta 测试中对程序进行测试。

本节讨论第二组；即内部测试人员执行的测试。虽然测试小组也负责管理 Beta 测试，但本节讨论的是测试小组执行的实际测试。

测试人员分为两组：

- 拥有源代码知识的人（白盒）。这些测试人员查看源代码，并根据代码编写测试程序，试图破坏程序。
- 仅作为高级用户拥有产品知识的人（黑盒）。这些测试人员对程序的内部逻辑一无所知。相反，他们根据程序高级用户会拥有的知识来设计测试。

### 白盒测试

内部测试通常是产品白盒测试的唯一来源。这种测试由程序员执行，他们阅读源代码并根据实际源代码设计一套测试。TRAPS 和 IntTests 确保了所有代码都已执行，而这些测试则试图确保所有代码路径组合都得到了测试。

白盒测试不能由编写代码的开发人员执行。任何开发人员，无论多优秀，都有盲点。毕竟，起初是他们把所有那些 MFU 放进去的。

虽然白盒测试应该涵盖常见的代码路径，但这是其最不重要的工作。毕竟，如果一个代码路径是常见的，黑盒测试一定会测试它。相反，测试人员应该寻找极少被执行的代码路径。

理想情况下，将为所有可能的代码路径编写测试。然而，由于时间和精手有限，这通常是不可能的。在这种情况下，测试人员必须决定测试哪些代码路径。你有两类基本的测试。

首先，你想要编写测试程序基本功能的测试。这种测试应该确定基础系统（包括所有关键路径）是否正常。这是必要的，以判断开发人员是否作了某些更改，导致无法测试任何内容，因为基础系统处于“托管”（另一个技术术语，意味着你无法对程序进行任何操作）状态。

其次，你想要编写测试你认为最容易崩溃的代码路径。这是测试小组破坏程序的最佳机会。此外，在寻找可破坏的代码路径的过程中，发现错误的测试人员可以引起开发人员注意。这种代码审查也是发现 Bug 的一种方法。

### 黑盒测试

黑盒测试是白盒测试的相反面。测试人员对构成程序的内部代码一无所知。黑盒测试人员保持“纯净”是至关重要的。所谓“纯净”，是指测试人员必须对程序的内部运作一无所知。

在大多数情况下，确保黑盒测试人员纯净的最佳方法是使用非编程人员进行此类测试。即使他们看到代码，他们也不懂。这也减少了从开发人员那里学习的机会。

黑盒测试由程序高级用户设计。与白盒测试人员一样，应该编写两类基本的测试。首先是常见功能的测试。这些设计用于验证程序运行正常。第二次，再次是不常见的代码路径。在黑盒测试中，没有办法知道哪些代码路径比其他路径不稳定。最重要的方法是对提示给出异常的响应。

例如，当提示输入文件名时，尝试 8 个字符的名称。尝试只读文件。尝试损坏的文件。尝试不存在的文件。换句话说，尝试正常文件以外的所有内容。

不常见代码路径的测试在黑盒测试中并不关键，因为 Beta 测试将完成这大部分工作。这种测试中更重要的是为 Beta 过程中发现的 Bug 添加测试。

如果你跟踪初始的黑盒测试，你会发现某些测试人员编写的测试全部成功了，而另一些人编写的测试几乎总是失败。使用最后一组的人继续编写测试，让其他组的人为 Beta 站点报告的 Bug 编写测试。

### 设计测试

测试的寿命通常比它们所测试的代码长。虽然程序在版本之间可能会被完全重写，但用户界面保持基本不变。由于许多测试是为了练习用户界面编写的，这些测试仍然有效，或者易于修改。

此外，当程序转换为另一种语言（人类语言，而非编程语言）时，大多数测试仍然有效，尽管可能需要更改实际的按键输入和结果中的测试以匹配新语言。程序和测试程序一样，编写时考虑了国际化支持。

测试被分为“测试套件”。测试套件无非一组运行的测试。一组套件可以是基本功能测试工作。另一组可以是所有的打印测试用例。

两个测试套件在使用的测试用例上可能会交叉。测试用例是实际测试。测试套件旨在执行一组测试以检查某些内容。如果可能，测试套件应该包含其他测试套件。如果可能，你应该每个基本组准备一个测试套件，以及一个包含所有套件的主套件。主套件将包含每一个测试。




140 零 Bug

测试用例（Test case）测试程序中的一个功能。测试用例是由一组测试场景组成的测试程序。通过运行一个测试用例，你应该通过为该功能编写的所有测试来充分执行该功能。如果打开文件的测试用例通过了，说明它已经通过了你为打开文件所编写的所有测试。测试用例应该尽可能全面——它完整且完全地测试一个功能。

测试场景（Test scenario）是测试用例的一部分。每个场景测试执行函数的一种特定方式。例如，对于打开文件操作，其中一个场景会传入一个不存在的文件；另一个场景会传入一个损坏的文件，以此此类推。测试场景应该尽可能简单——它测试一个特定的代码路径。

测试应该生成其所执行测试的日志，并且如果测试失败，还要生成失败的结果。这些日志应该尽可能清晰简单。最好的日志是在没有错误的情况下，仅显示“测试成功完成”。

测试小组应该设计测试，以将软件推向极限。随机使用软件并不是测试小组的工作。他们应该在充分了解产品的情况下，定义一组能够推软件极限的测试。对于每项测试，他们应该有一组预定义的输入，这些输入对应一个预期的结果。

完成后，自动化测试就是一个运行顺畅的产品。它们能够很好地完成工作并清晰地返回结果。它们易于使用，且只需要极少的用户交互。专业的测试小组提供专业的系列测试套件。

### 运行测试

第一项测试是由测试人员设计并由开发者自己运行的测试。在软件通过这项测试之前，它不会交给测试人员。这项测试的目的不是让开发者去承担测试人员的工作，而是确保在修复 Bug 后程序运行正常。需要有足够的功能运行得足够好，以便测试人员能够实际开展一些工作。

这项测试包含了白盒和黑盒开发的用于测试主代码路径的测试。随着程序越来越多的运行正常，这个初始测试可能会扩大。然而，在任何时候它都不应该包含程序尚未具备的功能。测试的目的不是判断某功能是否是第一次运行，而是为了确保之前检查过的基本功能没有被破坏。

这项测试必须完全自动化。简单来说，开发者不太可能每周运行一次手动测试。然而，他/她可能会运行一个能够报告程序运行是否符合预期的程序。

处理这项测试的最佳方法是每周构建一次产品。一旦产品构建（包括所有人的更改），就会对程序运行自动化测试。如果程序通过，则将其交给测试小组。如果没有通过，则由破坏测试的开发者对程序进行修复。

构建程序和运行基础测试的过程由开发者、专门负责此功能的人员（构建者）或测试人员完成。程序可以被构建并交付给测试人员运行基础测试。然而，如果基础测试失败，开发者的唯一工作就是修复它。在此之前，开发者不进行任何其他开发。

一旦构建通过了基础测试，它就会交给测试小组。测试人员在构建版本上运行他们的自动化和手动测试。第一批测试应该是测试已报告的 Bug 是否已真正修复。如果没有，则将 Bug 退回给相应的开发者。

接下来，如果添加了新功能，应该运行为这些新功能开发的测试。由于测试程序是与开发同步编写的，因此测试新功能的程序应该在新功能完成时（或之前）准备就绪。

这为开发者提供了关于新功能实现良好的即时反馈。他们不需要等待几周甚至几个月（那时忘记了所有实现细节），而是在几天内获得反馈。

最后，应该运行剩余的测试以确保程序中没有引入新的 Bug。这是自动化测试真正发挥作用的地方。每周当一个新的构建版本交付给测试人员时，所有的旧测试都会重新运行——且成本极低。

### 测试平台

测试人员应该确保在实际终端用户条件下进行测试。如果一个产品的大多数用户使用带有 640K RAM 的 80286 机器，那么仅用带有 8M 内存的 50 MHz 80486 系统进行测试会导致很多问题溜。

在最小配置的系统上运行全套测试是很。测试必须在程序可能运行的每一个系统上通过，不仅是硬件，还包括其运行的软件，包括网络、TSR 等。

如果你使用特殊的监视器，请用每种监视器测试程序。寻找引起问题的组合。并寻找可能与你的程序冲突的其他软件包。冲突可能来自 TSR 和设备驱动程序以外的来源。在 Windows 下，你的 DOS 应用程序可能与同时在另一个 DOS 窗口中运行的应用程序不兼容。

确保在各种操作系统环境中进行测试。在 DOS 的情况下，你应该在低内存和高内存 DOS 下进行测试。测试你的程序在低内存和高内存加载（UMB）。你还应该在 Windows DOS 环境下测试程序——这会捕捉到所有非法内存访问。

如果你的产品是网络感知的并在多个网络上运行，在多个网络上对其测试是至关重要的。在一个网络上测试网络程序是确保它在其他任何网络上崩溃的好方法。使用至少三个截然不同的网络。如果你根据网络调用不同的网络 API，请对每个 API 测试至少两个不同的网络。

如果你正在编写 Windows 应用程序，确保它在 286 和 386 模式下都能工作。在每情况下，Windows 都显著不同。而且如果你的程序可以在实模式下运行，请在实模式下进行测试。如果在实模式下测试并不重要，那么允许它在实模式下运行是对客户不负责的。

随着对象链接和嵌入（OLE）在 Windows 应用程序中变得流行，与其他程序的兼容性将变得越来越重要。你会开始看到某些 Bug，只有当你的程序与应用程序 B 有 OLE 连接，且应用程序 B 与应用程序 C 建立动态数据交换（DDE）连接时，程序才会崩溃。





### 无 Bug

尽管如今每个人都有测试版（beta test），但大多数测试的效果并不理想。那么，你希望 Beta 测试实现什么呢？有四个关键点：

-   在多样化的硬件平台上测试你的程序。在世界上 8000 万台 PC 中，有 79,999,998 台每台都与所有其他电脑略有不同。（爱荷华州有两台是完全相同的。）Beta 测试让你能够在内部测试无法触及的更广泛的硬件选择上测试你的程序。
-   这种多样化的测试至关重要。无论公司如何努力在内部测试中使用多样化的硬件，实际上这组硬件是极其相似的。通过使用美国及全球范围内的现有平台，你有机会确保你的程序可以在任何硬件组合上运行。
-   第二，用各种其他程序测试你的程序。再次，除了爱荷华州的那两台 PC 外，世界上所有的计算机运行的一组 TSR（终端驻留程序）、设备驱动程序等，与世界上所有其他计算机运行的程序略有不同。将这些软件产品混合在其中（有些程序非常老旧，自从硬盘、网络或分级文件系统发明以来就没有更新过。不用说，其中一些程序在处理 640k RAM 概念时会有困难，如果使用 USB 它们会“发疯”）。这种软件组合可能导致某些系统上原本完全安全运行发生故障。你实际上可能需要针对其他程序中的 Bug 编写规避性代码（program around）来解决其中一些问题。只有 Beta 测试才能让你的程序针对真正多样化的组合进行测试。
-   Beta 测试允许开发者获取对程序的反馈。如果一个功能很难用，Beta 测试员会让你知道。如果缺少了非常重要的功能，他们会告诉你。如果某个功能造成了干扰且不需要，他们也会告诉你。

这让你在最终发布产品之前（那时就太晚无法了）获得反馈。在一个原本非常出色的产品中，缺少一个功能可能会大幅减少销售额。一个糟糕的功能可能会毁掉一个产品的实用性。

开发者感兴趣的是创建产品，测试人员感兴趣的是发现 Bug，但用户感兴趣的是使用它。Beta 测试员试图使用软件来解决问题。一个编写良好、无 Bug 的程序并不意味着就好用。易用性问题与导致程序难以使用的 Bug 一样严重。

-   一小部分 Beta 测试员编写了与你的程序交互的程序。这些用户需要一个预览版本，以便在你发布你的程序时，他们可以向他们的程序发布更新。

这不仅适用于 Windows 和 OS/2 等操作系统。如果有人依赖于你的文件结构，它也适用于文字处理器。它适用于你可以与之通信的 API 的程序。它适用于支持 DDE 和 OLE 的 Windows 应用程序。

这组人的特殊之处有两个原因。第一，这个小组是整个 Beta 测试的子集。第二，根据你的程序变化而纳入必要更改的难度，这些人可能需要在常规 Beta 测试之前获得一个副本。

### 何时进行 Beta

如果你看进行 Beta 测试的前两个原因，你可能在担心由于非常细微的影响导致的 Bug。对这些影响进行测试应该等到开发过程接近尾声时。如果程序发生了重大变化，这些细微的影响就会产生直接作用。你并不关心程序的早期版本是否能与某个 TSR 工作——只关心最终版本是否可以。

如果你看进行 Beta 测试的第三个原因，你关心的是程序的整体表现。通常情况下，Beta 测试的反馈不会发现抛弃大部分现有工作的原因。相反，它会发现细微的不一致之处。或者会发现某些用户以不同的方式或在不同的情况下使用程序，导致需要针对这些情况进行更改。再次，需要一个相对完整的产品才能获得这种反馈。

Beta 测试应该在过程的较晚阶段进行。许多公司犯了一个错误，即过早开始 Beta 以加快产品的发布日期。Beta 测试本身没有发布日期（尽管可能会推迟发布日期）。

没有理由过早开始 Beta 测试。事实上，有许多理由**不要**过早开始 Beta。首先，尽管被标记为 beta，产品的质量也会影响对最终产品的看法。（Windows 7 因为其早期的 Beta 状态曾被标记为多 Bug 产品，尽管最终产品是稳如磐石的。）

此外，如果一个 Beta 产品持续时间足够长，Beta 产品将开始被视为已发布的产品，因为所有的意见领袖都已经在用它这么久了。如果产品仍然有 Bug 或功能缺陷，该产品在发布之前就可能失败。

相反，你不应该等得太久。在发布最终产品前一周启动 Beta 期间，比没用更糟糕。这不仅没有帮助，而且通过告诉管理层你进行过 Beta 测试（而且**不是** Beta 测试），他们可能会认为产品已经准备好发布了。

测试的目的是非常简单：开发者在程序中放置 MFU（用户误用功能）的技巧远高于测试人员发现它们的技巧（抱歉，测试人员）。MFU 存在于代码中——你知道它们存在——而你想找到它们。

那么你如何决定何时开始 Beta 呢？第一步是尽可能自托管。如果你正在写一个操作系统，开发者应该先运行新操作系统进行开发。如果你正在写一个编译器，编译器应该编译它自己。（对于非系统软件，自托管并不总是可能的——有多少开发者使用电子表格呢？）

此外，你应该有一个内部 Alpha 版本，让少数用户（最好是开发产品公司内部的用户）使用它。这样，一小组人（而非测试员）实际上在使用该产品。

理想情况下，这些用户会认为，除了几个 Bug 之外，目前的产品优于他们正在使用的版本。当你达到这一点并修复了发现的小 Bug 后，就是发布第一个 Beta 的完美时机。

如果你的 Alpha 测试员无法使用程序，那么扩大用户群没有任何益处。只要 Alpha 测试员仍在报告 Bug，你就不需要更多人报告相同的 Bug。

最好的指导是内部测试发现了极少数 Bug，且开发者将在未来一两个月内完成编码。换句话说，你需要在下个月内获得一些报告，否则有些人将无事可做。

### 何时发布

当你发送一个 Beta 并且在此之后不需要对核心代码进行任何更改时，你就准备好发布你的最终 Beta 了。

一个编写无 Bug 代码的开发小组通常会有一个到两个 Beta 版本（因为软件通常会与操作系统交互，增加了问题的复杂性）。然而，拥有额外的 Beta 比发布一个会被退货的 Bug 产品要好。

除了最后一个外，所有的 Beta 期间可以持续任何时间，尽管平均是一到两个月。如果你仍然收到大量的新 Bug 报告，那么可能还没到发布新的。如果你有了全新的版本或修复了许多关键 Bug，可能该发布另一个 Beta 了。

最后的 Beta 期间至少应持续一个月，除非收到 Bug ，否则真的应该持续两个月。等待得越久，程序在现场经历的异常组合就越多。

如果你做了你认为是安全的但确实接触了核心代码的最终更改，你可能希望发布限量 Beta。将副本发送给那些发现问题最多的站点。

你可能还会考虑通过 CompuServe 或其他公告服务进行 Beta 测试。如果 Beta 测试员下载了 Beta，那么在 Beta 测试过程中拥有一些中间 Beta 对你来说没有任何成本。

### 选择 Beta 站点

在我们 Beta 站点的标准中，另一个重要特征是多样性。两个具有相同电脑、软件和习惯的用户并不比一个更有用。两个具有完全不同系统和软件的用户则有。




随着 Beta 测试的进行，请跟踪你的测试站点。如果一个测试站点从不报告任何错误，那么它们对你毫无用处，在下次进行 Beta 测试时你不必费力将它们包含进来。对于那些为了自己的产品而需要提前访问你产品的测试站点来说有一个例外。即使他们不报告错误，他们也需要这个测试版。

在 Beta 测试结束后仍报告了错误的测试站点应该得到奖励（至少给一个奖牌）。如果你在最后一次 Beta 测试之后，做了“某种程度上”影响了核心代码的更改，你可能会选择只针对这些站点发布一次测试后的更新。

现在似乎许多公司都在寻求比任何其他计划都更大的 Beta 程序。当站点数量达到一定程度后，增加额外的站点并无益。定一个数字，并极力不要超过这个数字。对于一个销量数百万份的通用产品，我认为拥有超过 5000 个测试站点没有任何优势。

对于一个总共有 1000 个客户的垂直市场应用，50 个测试站点已经绰绰有余（ 20 个可能就够了）。选择正确的测试站点。挑选 20 个实际上并不使用测试版的人是毫无用处的。

跟踪你现有产品中报告错误的人。要求那些前 1% 或 2% 的人（必要时请恳求）成为 Beta 测试员。那些打电话为未来的产品提供良好建议的人也应该是 Beta 测试站点。

你寻找的是质量，而不是数量。

### 处理错误报告

当测试站点来电报告错误时，Beta 测试计划实际上发挥了它的价值。同样重要的是，在此期间，Beta 测试员会收到反馈，这些反馈将鼓励或挫败他们未来的工作。

当一个错误报告进来时，测试人员需要检查相同的错误是否已经报告。如果没有，测试人员需要确保报告了足够的信息来复现该错误。不完整的错误报告毫无用处。

如果 Beta 测试员来电报告错误，或者测试人员需要致电测试站点获取额外信息，测试人员必须让测试站点感到被感激。感谢他们发现错误；不要对他们大吼，并告诉他们现在因为他们发现的东西你必须通宵工作了。

让他们知道你感谢他们测试和报告错误所花费的时间。如果没有这种积极的反馈，测试站点可能不会报告他们发现的下一个错误。让他们觉得自己是开发团队中重要且受重视的成员。

该错误需要输入到错误数据库中。这允许将其分配给开发人员进行修复。此时应特别注意确保此错误没有被报告过。

你可能还想在将其输入数据库之前，让测试人员复现该错误。报告的错误中有很多是来自早期版本的，或者根本就不是错误。另一些是特定于用户使用的硬件的。在任何情况下，在错误能够被复现之前，让开发人员尝试修复它是没有意义的。

当错误被解决时，设法方法让测试站点知道它已被修复，并再次感谢他们。如果他们是第一个报告错误的人，也让他们知道这一点。如果测试站点认为你忽视了他们的报告，他们就会放弃。人们惊讶地愿意通过测试我们的程序来帮助我们帮助。然而，如果他们认为自己被忽视了，几乎没有人愿意这么做。

如果你有用户通讯报，请在其中为你的前 10 个测试站点颁奖。如果你有用户小组会议，请给 Beta 测试员颁奖牌。找某种方法在他们的同伴面前表达你的赞意。让每个用户都渴望发现比任何人都更多的错误。

你的 Beta 测试计划的成功主要取决于三点：你找了谁作为 Beta 测试员，他们发现错误的动力有多大，以及你如何处理报告的错误。

## 第 15 章

### 发布产品

本章试图解决所有问题中最困难的一个：何时最终发布产品。我用“尝试”，是因为这是所有问题中最难回答的。

然而，它也是关键问题之一，如果不是的话。发布得太早，计划中的主要用户（MFUs）将迫使你修复磁盘。发布得太晚，别人可能比你先抢占市场。至少，你延迟了可能可能生存所需的收入。

这个问题之所以困难，是因为在有充分测试的情况下（你遵循了上一章，对吧？），你永远不会没有错误。相反，你正试图给出一个没有到足以阻碍你发布程序的版本。

当你接近完成软件的最终 Beta 版本时，你将构建一个候选发布版本（release candidate）。你将其作为最终产品发布——除非发现了严重的错误。（如果开发人员仍在对程序进行错误修复，那么你现在就接近候选发布版本阶段。）

你应该让这个候选发布版本通过完整的回归测试（你所有的自动化和手动测试）。如果软件通过了回归测试，那么项目中的每个人（测试员和非测试员）都应该尝试弄坏程序。他们应该花几天时间除了折腾这个产品之外什么都不做。

在此时，你需要将这个“微 Beta”候选发布版本发送给公司里的每个人以及选定的测试站点。正如我之前提到的，将它发送给过去发现最多错误的测试站点。你可能还想把测试版放在 CompuServe 或另一个公告板上供 Beta 测试员下载。这不需要你花费任何费用，并能为你提供一个额外的测试员池。

这项最终测试应该至少持续一周。如果你对程序的核心部分或其文件结构更改了更改，这项测试应该持续一个月。根本没有办法缩短这段时期；用户需要时间以不同的方式操作程序，以测试代码的独特组合。

当程序通过了测试后，它就准备好交付给制造商了。让“制造部门”向你发送制作出的前 10 套磁盘。拿过这些磁盘，让你小组中的每个人都从磁盘中安装程序并再次测试。确保你发送给制造部门的东西和你收回的东西一样。仅仅比较磁盘是不够的；你应该确保程序可以运行。

### 发布还是不发布

如果候选发布版本未能通过任何回归测试，你必须决定该错误是否是发布终止者。修复一个错误可能会引入新的、未知的错误。如果你做了更改，你需要花时间重复整个周期。你需要完全偏执地认为，修复可能在程序中引入了一个细微但非常严重的错误。如果更改发生在任何有意义的区域，你需要将程序发送进行“微 Beta”。

即使你担心无论哪种方式都会失去客户，也要修复这些错误。如果你发布，你会失去客户，并获得产品多错误（不可用）的声誉。如果你发布得太晚，你会失去客户，但你会获得软件可靠的声誉。

开发主管希望完成开发，而 bug 的发现延长了整个过程。

至少，测试人员主管应该向与开发人员主管相同的上级汇报：即负责交付成功产品的人员。这样，测试人员就是向一个对产品成功负责的人汇报，而不是对完成开发的人汇报。

如果测试人员不属于技术支持小组，那么他们应该与该小组频繁交流。技术支持需要与测试人员紧密合作，以最大限度地减少程序中的问题。与其增加技术支持人员，不如让程序变得更易用要便宜得多。很多时候，技术支持可以发现通过对程序进行细微而易的修改就可以减少大量的技术支持请求。

### 总结以上

上述所有内容都回到了你的起点：测试的目标是识别程序中的 bug。你可能无法修复所有的 bug（在某些情况下，这样做是不可能的），但你很清楚它们是什么。

这使得项目成员能够对修复哪些以及放弃哪些做出明智的决策。更重要的是，它允许项目管理层对何时发布新产品做出明智决策。没有经过适当的测试，管理层将只能根据猜测来决定何时发布——然后等待不可避免的 bug 报告。

PC 软件开发在过去几年里进步巨大。用户已经开始期望操作系统（DOS 5 和 Windows 3.1）中没有 bug，而用户会在这些程序中看到几个 bug。

流行的软件应用也正在达到这一步。Lotus 最近 推出了适用于 Windows 的 1-2-3 表格程序，由于其 bug 程度不得不召回，而这种 bug 程度在两年前是无关无痒的。一年后，用户将期望他们所有的通用应用程序都达到同样的稳健性水平。早晚（不会更晚），用户将看到一个与他们目前使用的应用程序看似无 bug 的替代品。而且他们会购买它。

一旦用户认为他们的通用应用程序在他们看来是无 bug 的，他们就会要求他们的特定应用也摆脱 bug。编写垂直市场或公司内部应用程序的开发者只有一到两年的时间来开发良好的、无 bug 的特定应用。用户并不愚蠢。如果你的文字处理器设计良好、功能完备且无 bug，而你的垂直市场应用不是，那么将非常痛苦而显易地看出它没有达到应有的水平。

两年后，成功的软件公司将建立良好的测试程序并使用它们。他们所做的将遵循大部分（如果不是全部）这里列出的内容——不一定是因为所有员工都读了这本书，而是因为他们遵循了这里列举的观点。

### Bounds Checker

每隔一段时间，就会出现一类新程序：带有第一个表格程序的 VisiCalc，带有第一个 Unerase（取消擦除）的 Norton，现在现在是带有第一个边界检查器的 Mega。任何不使用 Bounds Checker 测试测试程序的开发者都犯了严重的失职，并浪费了大量额外的时间去追踪某类 bug。

Bounds Checker 实际上非常简单。它利用 386 的内存映射和页错误为程序设置边界。它将你的代码区域标记为只读，将数据区域标记为可读写，并标记所有其他内存限制。如果你的程序写入了数据区域以外的任何地方，或从代码或数据区域以外的任何区域读取，就会发生页错误，Bounds Checker 会向你显示哪条指令访问了越界内存。

当程序发出中断时，Bounds Checker 会关闭。中断的代码通常不是程序的一部分，因此 Bounds Checker 合法地访问了程序区域之外内存。它甚至足够智能到跟踪你进行的任何 DOS alloc 和 free，并允许你只访问当前 malloc 的内存。

你可以列出程序可以访问的区域，例如 BIOS 数据区域、显存和 EMS。如果你只需指定 EMS 而不是特定范围， Bounds Checker 甚至会自动确定 EMS 页帧的位置。这些异常区域可以是任何大小（对于 BIOS 数据区域，我列出了我读取的字节）；它们可以被列为只读、可读写或只写；并且你可以允许程序的任何部分访问这些范围，或仅允许特定模块访问。

当它发现错误时，Bounds Checker 会告诉你你代码的哪部分违反了规程，以及你正在访问哪些内存，它还会列出调用栈等信息。调用栈非常有价值，因为由于是 `memcmp` 导致了违规，调用栈会向你显示带坏指针调用 `memcmp` 的程序。这些违规会在程序退出时写入日志文件，允许测试人员使用 Bounds Checker 而无需完全理解它。

 Bounds Checker 也有一些限制。它是为用 C 等高级语言编写的前台应用程序设计的。它允许一个代码区域后跟一个数据区域（每个区域可以 > 64K）。这是最严重的限制。TSR 需要比前台应用程序更多的功能。理想情况下，Nu-Mega 将提出一种处理 TSR 并允许代码和数据区域交错的方法。

BoundsChecker 还需要对段更具区分性。数据区域应将常量数据标记为只读。EMS 内存只有在属于它的页被映射时才能被访问。

然而，上述内容将是锦上添花：它们会让一个无价的产品变得更加不可或缺。Nu-Mega 已经在进行多项改进。就目前而言，Bounds Checker 几乎可以发现你所有的指针。

MemCheck 通过许多简单的机制来发现这些 Bug。执行这些操作几乎不对你现有的代码产生影响。你只需要在源文件中包含 `memcheck.h` 并添加两个调用即可。仅此。

虽然 MemCheck 可以针对调试和非调试模式切换开启或关闭，但你也可以将包含文件和两个函数调用放在 `#if DEBUG` 语句中，这样它们在非调试模式下就会消失了。

MemCheck 提供了两个基础功能。

首先，它实现了第 8 章“监控堆分配”中描述的功能。所有的分配在其的前后都放置了检查字节（check bytes）。所有的分配都记录了它们 `malloc` 时的源代码文件名和行号。凭借此功能，MemCheck 会告诉你你是否越界访问或覆盖了已分配的内存。它还可以在退出时为你列出任何未释放的内存——防止你忘记释放内存。

其次，MemCheck 包含了它自带的所有基本字符串和内存调用的库。你只需调用 MemCheck 的 `strlen` 和 `memcpy`，而不是你编译器运行时库中的版本。

每当这些函数之一接收到指针时，它都会确定该指针是否在堆中。如果是，MemCheck 将会检查该指针指向的内存是否足够函数使用。如果你动态分配了一个 26 字节的指针，然后尝试向其 `strcpy` 27 字节，MemCheck 将发现该错误。

遗憾的是，MemCheck 只对动态 `malloc` 生成的指针有效。有一个 `mc_register`，你可以用它来列出全局和局部变量的基地址和范围（你也可以取消注册，这对于局部变量至关重要）。然而，这需要为每个变量调用一次函数。很遗憾，MemCheck 无法读取 `.EXE` 文件中的代码信息——它会列出所有变量以及它们的基地址和范围。

MemCheck 包含了检查写入 `NULL` 的功能。它还可以随时检查整个堆。这两项都是 `TestAll` 的良好补充。

它还允许你提供一个函数来替换 `printf`，MemCheck 使用它来显示错误。如果你的程序使用了窗口系统，你可以让错误消息在消息框中弹出，或者写入调试监视器中。

MemCheck 让你用极小的时间或精力获得大量的检查。如果你还没有用于进行参数验证的代码，请使用 MemCheck。它只检查动态 `malloc` 的指针，但这比检查非指针要好得多。

这是一个良好的无 Bug 工具的精髓：在它发现 Bug 之前，你基本上可以忘记它的存在。

### Windows 调试版本

Windows 软件工具包（SDK）包含一个 Windows 调试版本。在 Windows 3.0 中，这区别很大，因为调试版本会执行参数检查，而零售版不会。

调试版本仍然执行零售版未进行的额外检查。Windows 应用应该在 Windows 调试版本上运行，甚至不会产生警告。在测试 Windows 应用时，请使用 Windows 调试版本以及连接到你串口的串口终端（调试内核将写入该终端）。

调试版本还有几个可以开启的标志，以执行额外的检查。第一个标志是 `ilovebear`（这个名字背后有一个有趣的故事），它会在返回存放在其中的值之前将传递的字符串填充到极限限制。这保证了所有传入的缓冲区都足够长。

调试版本还有 `ValidateSpaces` 调用，它结合 `EnableFreeChecking` 和 `EnableHeapChecking` 标志会对堆进行额外的检查。此调用在 Windows 中会增加约 20% 的开销。然而，它会写入空闲内存。

`ValidateCodeSegments` 调用仅在实模式下有用。如果你的程序将在实模式下运行，那么你应该不时使用此测试。但是，如果你的程序只在保护模式下运行，那么没有理由使用此调用。

Windows 提供了 Stress Applicator（压力测试器）和 Heap Walker（堆遍历器），它们可以用于消耗资源。Stress Applicator 可以耗尽堆，留下固定数量的空闲内存。它可以对全局堆、程序本地堆以及 GDI 堆（通常被称为系统资源）执行。它还可以使用磁盘空间和文件句柄，再次留下有限或没有资源。

Heap Walker 也可以使用全局堆以及可丢弃段。Stress Applicator 和 Heap Walker 均允许你在资源完全耗尽的情况下测试你的应用程序。

### RT-link

RT-Link 值得在这里提到。RT-Link 是一个用于 DOS 程序的复杂链接器，从上看，它不属于这一节。然而，RT-Link 实现了一些工具，展示了正确实现某些错误检查可以有多强大。

RT-Link 允许你链接程序以在 8088 代码上使用虚拟内存（在某些情况下也包括数据），代码保存在磁盘上，并在需要时调入内存。与覆盖链接器不同，RT-Link 维护一个页面列表并将代码加载到 LRU 页面中。

不用俗说，程序每次运行时的加载方式都非常不同。因为调用了其他代码的代码可以被卸载（然后在返回时重新加载），如果任何一个代码页依赖另一个代码页实际上位于内存中，你就处于一种非常危险的局面。

这不是 RT-Link 的 bug。你可以告诉 RT-Link 你认为一个代码页直接访问另一个页是安全的，从而节省通过 RT-Link 虚拟内存管理器带来的性能损失。

然而，如果你在某处错了，你可能会访问一个通常仍在内存中的页面。这会导致只在内存较小的系统上，或在按特定顺序调用一组函数的任何系统上发生的 bug。

RT-Link 包含一个命令 (`VM_MURPHY`)，为所有虚拟内存交换仅分配一个页面。当与此命令链接时，程序运行速度极慢。然而，内存中任何时候都不会多于一个页面。如果一个页依赖于另一个页在内存中，它就会崩溃。

这是一个工具供应商整合有助于发现 bug 技术的值得赞的范例。此外，这个命令是一种只有工具供应商才能整合的技术。如果有更多工具供应商提供这样的功能就好了……

### 调试器

确保你有一个良好的调试器。对我个人而言，我倾向于在 386 上使用 Soft-Ice，在 286 或 8086 上使用 Periscope。然而，我更倾向于用汇编语言进行调试。尽管 Soft-Ice 和 Periscope 都有 C 源码级调试，但通常比编译器厂商提供的源码级显示慢一步步。

当你真的需要在 386 模式下深入研究 Windows 时，你只有两个调试器可选：`wdeb386` 或 Win-Ice（Windows 版的 Soft-Ice）。`wdeb386` 随 Windows SDK 附，是一个优秀的命令行调试器。然而，Win-Ice 是一个全屏调试器，并在源码级工作。

Periscope 有一个 Windows 调试器。然而，对于系统级（在 VxDs 上）调试，它比 Win-Ice 或 WDE386 受限得多。对于应用级调试，它不如 Multiscope。此外，它需要两个通过串口线连接的 80386 系统。

用汇编语言调试的宝贵之处在于，你可以看到最终代码的真实情况。这不仅允许你看到编译器是否生成了糟糕的代码（这偶尔会发生），还能看到代码的效率如何。随着 C++ 的出现，这将变得更加重要，因为一个 `+` 可能会变成一组极其缓慢且复杂的指令。

随编译器附带的源码级调试器（如微软提供的）以低得多的提供了大部分相同的功能。虽然 Soft-ice 会稍微改变系统，但 Periscope 辅助辅助卡对一切都没有影响。这造成了有时是至关重要的区别。

最后，如果你真的需要深入硬件，并且发现 Soft-ice 干扰了某些时序问题，你需要硬件设备。在这种情况下，只有一个选择：Periscope。

### Soft-Ice

由 Bounds Checker 的团队带来，Soft-Ice 利用 386 的功能通过软件为你提供一个 8086 ICE。它非常出色地接近这一目标，但在某些非常微妙的问题上稍有不逮。

如果你正在调试实模式下的 DOS 程序，这个调试器在以后将是无价之宝。你可以设置在程序读取或写入某个内存位置时中断，然后让它以全速运行，直到发生读/写操作（用普通的调试器试试看吧）。

Soft-Ice 使用 80386 的几个功能实现了这一魔术。首先，80386 拥有几个调试寄存器，可用于访问特定内存位置时触发中断。这些寄存器很少，且只能设置在字节到双字范围内的触发中断。

Soft-Ice 还利用了 80386 的分页功能。为了在内存范围内设置断点，Soft-Ice 将内存页标记为“不存在”。然后，当访问该页时，Soft-Ice 会判断页面上的目标范围是否被触。如果是，它就会停止操作；如果不是，它就允许操作并继续。

除非断点范围所在的页面其他内容被频繁访问，否则这种方法是有效的。因为页面是以 4K 为块的，这可能是一个真正的问题。最常见的性能问题是对局部变量的访问设置断点。因为局部变量在栈上，每次栈访问都会导致缺页异常。

Soft-Ice 并非总是完美的调试解决方案。然而，在大多数情况下，它提供了你所需的所有 ICE 能力——而且价格比任何真实的 ICE 都便宜得多。

Soft-Ice 还有一个 Windows 版本，称为 Win-Ice。Win-Ice 不仅调试 Windows 应用程序，还调试 Windows 设备驱动程序、虚拟驱动程序以及在 Windows框中运行的 DOS 程序。简单来说，它的功能和能力范围是惊人的。**

##iscope

一个用于 DOS、Windows 和 OS/2（无论是什么）的调试器。在 Windows 中，它作为一个 Windows 应用程序运行，为你提供了一个极其强大的界面。虽然在底层调试方面并不理想，但在源码级调试应用程序方面它表现优异。

很难用几段话描述 Multiscope。它是市场上最好的调试器。它提供了多种界面，最好的使用方法是它的 Windows 界面。

在 Windows 下，你可以调试 DOS（在框内）和 Windows 程序。你可以调试运行在同一台机器或通过串口线运行在不同系统上的程序。你可以使用双显示器，但如果你的第二个显示器是字符界面而不是 Windows，那么 Multiscope 的魅力之一在于它是基于 Windows 的。通过 Windows 提供窗口化数据而不是使用字符显示，使其比任何其他调试器都有更好的界面。此外，Windows 提供了比80x25 单色适配器（MDA）更好的尺寸和布局。

此外，该界面通常比字符界面更容易用。所有支持基于 Windows 应用的理由都适用。此外，Windows 使得修改内存等操作变得非常简单——点击并输入。

Multiscope 在一个功能上领先所有调试器光年：图形数据显示。它提供了查看数据的常规能力，此外，当你点击结构或指针时，它会显示结构的内容。更棒的是，它还有一个图形数据窗口。

Graphic Data 功能会绘制你的数据的图像。每个结构被绘制成一排框。结构值将位于每个框中。结构中的每个指针将通过名称识别，并有一个指向其指向位置的箭头。有时一图胜于千言，Multiscope 证明了这一点。

遗憾的是，Multiscope 被设计为应用程序调试器。对于调试系统级程序，你需要 Soft-Ice 或 Periscope。但如果你在编写应用程序，这就是要使用的调试器。
