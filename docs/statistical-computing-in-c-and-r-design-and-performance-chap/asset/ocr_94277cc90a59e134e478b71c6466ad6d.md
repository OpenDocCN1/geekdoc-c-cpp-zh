Our real question is whether or not the multicore approach reaches the computation time. The system.function discussed in Section 5.4 provides a means to address this issue. The case of our variable example leads to

```
> timeVec <- vector(length = 2, mode = "numeric")
> for(i in 1:100) {
  + timeVec[1] <- timeVec[1] +
  + system.mclapply(indexList, myRegTask))[[3]]
  + timeVec[2] <- timeVec[2] +
  + system(myRegTask(subsets))
}
> timeVec[2]/timeVec[1]
[1] 2.43891
```

The system.function returns a five list with the third component being elapsed time. This function is used to evaluate the elapsed computations for mclapply and serial execution of myRegTask across all 2ⁿ subsets. The calculations are repeated 100 times with the total elapsed time accumulated for each approach. The outcome suggests that the speedup by mclapply exceeds 2 in this instance.

# 11.5 Parallel random number generation

Simulation studies are in many respects the ideal for parallel processing. They are "embarrassingly parallel" in the sense that computations may be conducted without the need for inter-processor communication. Thus, the potentials for linear speedup that can occur in practice. However, there are fundamental issues that arise from the fact that random streams produced by each process must behave as if they executed in a probabilistic sense for the division of labor between processors. An overview of issues arise in parallel random number generation and methods for producing effective parallel generators is provided by Codington (1996) who concludes that good parallel random number generators should a) produce intra-processor streams of high quality in the usual statistical sense while exhibiting inter-processor dependence, require no data movement between processors.

Two noteworthy sources for generator packages that meet Codington's criteria are the SPRNG package of Mascagni and Sriniv (2000) and the RngStreams discussed in L'Ecuyer, et al. (2001, 2002).
