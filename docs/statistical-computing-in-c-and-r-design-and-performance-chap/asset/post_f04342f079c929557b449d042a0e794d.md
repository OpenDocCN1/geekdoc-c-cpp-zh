Simulation studies are in many respects the "embarrassingly parallel" in the sense that computations may be conducted without the need for inter-processor communication. However, there are fundamental issues that arise from the fact that random streams produced by each process must behave as if executed in parallel for the division of labor between processors.

An overview of random number generation is provided by L' (1996) who concludes that good random number generators should produce intra-processor streams of high quality while exhibiting inter-processor dependence, require no movement between processors. Two noteworthy sources for generator packages that meet L's criteria are the SPRNG package of Masagni and Sriniv (2000) and the RngStreams discussed in L'Ecuyer, et al. (2001, 2002). The SPRNG produces different random number sequences via parameterization while RngStreams employs a sequence wherein a random number stream is partitioned across different processors. While there has been some debate about the relative merits of the two approaches, in practice it appears that both packages are effective and provide solutions to the problem of obtaining a complex implementation that necessitates the creation of a compiled library. In contrast, the source code for the RngStreams package is compact and easy to incorporate into C/C++ programs using either OpenMP or MPI through simple directives. This property extends its applications from clusters to desktop environments, and accordingly, it is the parallel pseudo-random generator that will be used here.

The "backbone" generator for RngStreams is the recursive generator Merg32. The period of the generator exceeds $2^{191}$. For use in a parallel context this length is divided into 64 nonoverlapping streams of length $2^{27}$.

The key to accessing different streams is the technique described in L'Ecuyer (1990) that allows movement between streams through linear transformations of the initial seeds using known matrices. If $\tilde{x}_1, \tilde{x}_2$ are the initial seeds for the stream, then at the $n$th step of the generator for stream $i$ is $x_{i,n} = (A_i^n x_i \pmod{m_i})$, $i=1,2$, for $3 \times 3$ matrices $A_1$ and $A_2$ with $m_1 = 4294967296$ and $m_2 = 4294967295$. The powers of the matrices $A_1$ and $A_2$ can be computed explicitly, and it is the $A_1^{27}$ and $A_2^{27}$ that are needed for movement between the different streams of the generator are found to

$A_1^{27} = \begin{pmatrix} 242970618 & 358015074 & 949970784 \\ 226153695 & 1230515664 & 358015074 \\ 198883501 & 996791581 & 1230515664 \end{pmatrix}$ (11.1)

and

$A_2^{27} = \begin{pmatrix} 146441153 & 277697599 & 1610723613 \\ 3218390 & 146441153 & 1022807787 \\ 282425495 & 3218390 & 2093834863 \end{pmatrix}$ (11.2)

Section 4.5 demonstrated how to use the SetSeed function to set the initial state for RngStream objects. This requires the user to supply initial integers to serve as the beginning seed for the generator. The first RngStream object that is created will use this initial seed. Subsequent objects will be started on the next stream; i.e., they will have initial "seeds" that are $2^{27}$ states removed from the initial state of the previous object's generator.

This function provides a means to return the current state of an RngStream object at any point during random number production. In particular, it allows us to determine an object's initial seed and how it will be used in our examination of the behavior of the RngStream class constructor.
