To insert a node into a red-black tree, we begin by inserting it as if the tree were an ordinary binary search tree and coloring the node red. At this point, actions become contingent restoring any of the invariant conditions that may have been violated.

If the node was inserted at the root, then the node must have been inserted into an empty tree. The first invariant is violated and restored by recoloring the node as black.

If the new node is inserted as a leaf, there are two possibilities: its parent is black or red. In the first instance, all invariants are satisfied and there is nothing to do. If the parent node is red, matters become considerably more complicated as we describe.

First, let us consider the scenario in Figure 9.11. The subtree consists of four nodes: a new node to be inserted (indicated by c, for child, in the figure) that is initially given the color red (indicated by r for black), the parent node (indicated by p in the figure), its parent or, equivalently, the grandparent (or gp) of the new node and a sibling (i.e., aunt/uncle denoted by an) of the new node's parent. The parent and aunt/uncle are both red in this case while the grandparent is black. To restore the invariant in this subtree, recolore the parent and aunt/uncle as designates the grandparent as being red. This provides a local fix and restores the third invariant. There will be a problem if the grandparent is red. This is recursively resolved by treating the grandparent as if it were a new node being added to the tree at its location. In respect, the general scenario will involve the case where the “new” node as well as its parent and aunt/uncle have other children. Unless stated otherwise these relationships will not need to be changed, and as a result, not explicitly appear in the figures or other discussion.

The next possibility is that the parent node is red while the aunt/uncle is black. The procedure for restoring the invariant involves either a right or left rotation depending on whether the parent is a left or right child of the grandparent. We will deal with the case that the parent is a left child here and provide the treatment of the other scenario as an (Exercise 9.34).

1. replace the grandparent with the parent while coloring it,
2. replace the parent with the child,
3. replace the aunt/uncle with the grandparent as its right child and recolor it red
4. make the right child of the parent, should one exist (e.g., the dotted node in Figure 9.12), the left child of the grandparent.

These steps restore the third invariant without changing the number of black nodes on either branch of the tree. The process of rearranging the nodes in Figure 9.12(a) to have the form in 9.12(b) is called a right rotation.

All that remains is the case where the new node is a right child of its parent. In that instance, the steps are to

1. swap the child node with its parent,
2. make the former parent the left child,
3. attach the left child of the “new” node, should one exist (e.g., the dotted node in Figure 9.13(a)), as the right child of former parent and
4. perform a right rotation with former parent occupying the role of the “new” node.

9.13(b) shows the result from applying Steps 1-3 to the tree in 9.13(a). The outcome is analogous to the tree in 9.12(a) except that the former parent has taken the place of the “new” node. Thus, the invariant can be restored by a right rotation. The removal of a red-black tree is more complicated than insertion although it involves similar operations. Details are provided for Cormen, et al. (2003). It turns out that the additional information needed for red-black trees is not needed if the requirement for each operation is replaced with an amortized bound. One such data structure that achieves logarithmic time per operation is the splay tree discovered by Sleator and Tarjan (1985). Unlike the red-black tree, splay operations are quite simple. The basic outline is that after every access to a node, a series of rotations used to float the node to the root of the tree. For example, if a small number of nodes is accessed frequently, they will tend to stay close to the root and its depth is reduced significantly. See Sedgewick (1998) for more details.

## 9.5 Pointer arithmetic, iterators and templates

In this final section we lay the stage for C++ Standard Library (STL) containers in the next chapter. These classes have two features of particular importance: they are all implemented as templates and they contain internal pointer-like objects called iterator that provide the means to navigate inside a container. To appreciate and understand iterators one must write code that creates and uses them. That is a task undertaken in this section and our development mirrors the STL to allow the nodes in the container to have keys and data components of arbitrary types.

## 9.5 Iterators

On one hand pointers are probably the most difficult aspect of the C and C++ languages. On the other, they provide a powerful tool for creating adaptive programs through the use of an (somewhat) intuitive array structure. We have used the array connection to access the information that resides in the memory location that reports the actual value of a pointer. Specifically, if p is a pointer, p[0] will return the value stored in the memory location pointed to p. The transition from p to p[0] is called dereferencing. In many cases we have considered p[0] corresponds to the beginning of consecutive blocks of memory.

The ith block in this sequence can be accessed or dereferenced by the array syntax p[i].

In Section 3.5 we mentioned that a pointer can also be dereferenced with the * operator; for a pointer both *p and p[0] produce the same result. There is an alternative to access the ith component in a sequence of consecutive blocks of memory, as well. If the sequence begins at the value of the pointer p, the syntax (*p + i) gives the same result p[i]. This approach uses what is generally referred as pointer arithmetic. The idea is that p + i is a pointer to the memory location i blocks from p and *(p + i) dereferences this pointer. In contrast to the array dereferencing, this makes a pointer look more like an index variable and we use that perspective to generalize the pointer concept.

The simple program below illustrates the use of pointer arithmetic.

```cpp
int main() {
    int* p = new int[5];
    for(int i = 0; i < 5; i++)
        *(p + i) = 3*i;

    for(int i = 0; i < 5; i++)
        cout << *(p++) << " ";
    cout << endl;
    
    return 0;
}
```

Both the addition and postfix increment operators are used here to traverse the memory that has been allocated to a pointer to int. The output from the program is:

0 3 6 9 12

A somewhat different spin on the previous code uses the pointer directly in the indexing process.

```cpp
int main() {
    int* begin = new int[5];
    int* end = begin + 5;
    int i = 0;
    for(int* iter = begin; iter != end; iter++) {
        *iter = 3*i;
        cout << *iter << " ";
        i++;
    }
    cout << endl;

    return 0;
}
```

Here the role of the integer allocated and the pointer to int are reversed. The pointer now travels across the memory locations allocated to the pointer begin with its value restricted to lie between begin and another pointer. The end pointer refers to the one-pass-end memory location discussed in Section 3.5 that always exists and can be pointed to without dereferenced. An equivalent formulation of the previous listing that uses a while loop is

```cpp
int main() {
    int* begin = new int[5];
    int* end = begin + 5;
    int* iter = begin;
    int i = 0;
    while(iter != end){
        *iter = 3*i;
        cout << *iter << " ";
        iter++;
        i++;
    }
    cout << endl;
    return 0;
}
```
