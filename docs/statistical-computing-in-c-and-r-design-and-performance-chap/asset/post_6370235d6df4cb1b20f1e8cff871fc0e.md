# 9.2.4 Hash tables

A hash table is a data structure that solves the problem of efficiently mapping a sparse set of keys, not integers, into an array while conserving storage. Knuth (1998b) is one of the best references for hashing. An overview of the topic from a C++ perspective is provided by Sedgewick.

The main ideas of a hash table are the hash function and a mechanism for collision resolution. The hash function is a mapping: K -> Nm, where K is the key space (of all possible keys) and Nm = {1,...,m} for some integer m. A given key is said to hash to h(k). The data is stored in an array A = [A[1],...,A[m]] indexed by Nm with the consequence that m is the size of the table.

To insert an object with a key a into the hash table, first compute the value h(a.key), and then there is an already object stored in A[h(a.key)], either the object has already been inserted into the table or there is collision where two different keys map to the same slot in the table. Collisions are generally impossible to avoid. But, by careful design their frequency can be kept to a minimum. Chaining and addressing are two methods that can be used to deal with collisions. The collision resolution system enters the entries of the table (i.e., $A[1], \dots, A[m]$ not individual objects, but rather linked lists that are sometimes called buckets). Each bucket contains all the objects whose hash to the same location. The contents of a bucket are searched linearly with the consequence that the average access for an object is half the length of the list where it resides; that is, half the number of elements that have hashed into the bucket (Exercise 9.16). On the other hand, after initial look-up, insertion takes constant time.

Note the LookUp method called by $A[i]$ is the one in Algorithm 9.4. Thus, the look-up operation in a chaining table is primarily an application of the linked list. The look-up operation in a chaining table might look like:

```
Algorithm 9 LookUp(key): Look-up in a chaining table
i := h(key)
return A[i].keyUp
```

For a hash table consisting of linked lists $A[1], \dots, A[m]$, an implementation of look-up operation in a hash table first requires an application of Algorithm 9.8. Then a check is made to see whether the location LookUp already contains an object with given key. If so, an error is reported. The idea is summarized in Algorithm 9.9.

```
Algorithm 9.9 insert(a): Insert in a chaining table
b := lookUp(a.key)
if b.next == NULL then
b.next := a
else if b.key == a.key
return Error: duplicate key
```

Assume the hash function maps each key to a location chosen at random and independently of the locations to which other keys are mapped. If there are $n$ elements at a table of size $m$, the average length of a list is equal to the load factor $f = n/m$ as the average number of queries for look-up operation is decreased by a factor of $m^{-1}$ relative to the linked list. Depending on the load factor, insertion in a chaining table can be (roughly) constant time. For example, Knuth (1998b) demonstrates that the average number of operations for look-up and insertion are approximately $1 + f/2$ and $1 + f^2$, respectively.

Of course the uniform location condition is not possible to achieve with a well-defined deterministic function. Still, there exist very simple functions that satisfy this criterion. In opening addressing, no storage is used beyond the array itself; i.e., all slots of the array $A$ are available to store the data. The slots of the array will be filled with objects that are accessible by the indexing operator or will evaluate to NULL. In contrast to the chaining scenario, when a collision occurs, the object is not inserted into the location indicated by the hash value. Instead, it is placed in an alternate location determined by another rule. The simplest rule is linear probing. After a collision occurs at h(k), the positions $h(k) + 1, h(k) + 2$, etc., are tried until an empty location is found. A more complex alternative is to try the sequence $h(k) + s, h(k) + 2s$, etc., for some $s$ relatively prime to $m$. A generalization of this approach, double hashing, is the topic of Exercise 9.17.

Algorithm 9.10 implements the look-up operation using linear probing with shift $s$. The search continues until the target key is found or an empty slot is located. Until one of these two conditions is satisfied, we continue shifting the location by $s$ for best performance depends on the size $m$ of the array in which the table is stored. For example, the insertion of many elements that all have the same hash value will be possible to fill the whole array (Exercise 9.29).

```
Algorithm 9.10 lookup[key]: Hash look-up with linear probing and shift s
i := h(key)
while A[i] != NULL and A[i].key != key do
    i := i + s
end
return A[i]
```

With open addressing the load factor is at most 1. Under the assumption of uniform hashing Knuth (1998b) shows that the average number of operations is approximately $(1/(1-f)^2)$ for insertion and look-up when $s=1$. So, (near) constant insertion and look-up can also be expected for linear probing.

# 9.2.4 Choosing a hash function

A good hash function should possess two important properties: it should be easy to compute and its values should in some sense distribute uniformly across the range of the table size. Normally, a hash function should be designed for the individual type of keys that are used for the objects that will be stored. If more detailed knowledge of the keys is available, this can be used to improve performance.

Example 9.1. Suppose the keys are floating-numbers in the range (0, 1). In this instance, the function defined by $h(x) = [mx]$ is a natural candidate for the hash function to use with an m-element table.

Example 9.2. A hash function for integers that is very efficient and distributes the values well is given by the modulo operation; to hash the key $k$ into a table of size $m$, just take $h(k) = k \pmod m$.

The table size may have an influence on the behavior of a hash function. Suppose the simple hash function of Example 9.2 is used on integers with a table of size $2^k$. In that case, the $k$ bits of least significance will be ignored, which is quite undesirable. As noted in the previous section, this other bad configuration can be avoided by having a table size and shift that are relatively prime. Satisfying this condition avoids cycling before the table is completely filled. Most such problems can also be avoided by picking a prime number for the table size.
