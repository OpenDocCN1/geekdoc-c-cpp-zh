# 9.2.4.5 Extensions

We have not discussed how to remove elements from a hash table above. Some choices in designing a hash table lead to easier implementation of this operation than others. If the hash table uses chaining for collision resolution, it is easy to delete an element: just remove it from the linked list where it is found (e.g., Exercise 9.11). Open addressing presents a more difficult challenge: finding the hash entry $x$ that is to be deleted, it is to move any elements with the same value as $x$ that may have been inserted after $x$. This becomes complicated due to the possibility that additional collisions may have happened after the probe at the location of $x$. We must least find the end of the probe and relocate the last inserted element with hash value equal to that of $x$. This is not all; that may have caused other collisions which must now be tracked down. The simplest approach is to replace the deleted element with a *sentinel* value indicating a deletion has occurred. This lets the look-up operation skip this location while also letting the insert procedure use the location (Exercise 9.19).

A hash table may need to be resized if it gets close to full. There is no cheap way to do it; every entry must be reinserted into a table. On the other hand, this is not done frequently. A standard way to maintain a hash table of dynamically changing size is to double its size when it becomes full and to halve it when it becomes less than a quarter or eighth full. This prevents resizing and in an amortized sense does not increase the number of operations by more than a constant factor.

# 9.3 AD priority queue

In many situations the set needs to be represented or managed in a computer program has additional structure and is used to organize this structure. In this setting components are both inserted and removed during operation. a *priority queue*. Associated with each element is a numerical attribute that represents its *relative* priority which dictates the sequencing of its removal.

The objects stored will again be assumed to consist of key and data modules with an element's key now being synonymous with its priority. Under this formulation, each removal step will result in the object with the smallest (highest priority) being removed from the queue.

Situations where priority queues are useful are frequent in practice. For example, the business distributes products to dealerships be prioritized in terms of past performance. The scheduling of jobs a cluster is likely to be managed with a priority queue. The future event that arise in a discrete event simulation are often handled using priority heaps (discussed in the next section) or one of its variants (e.g., Mansharamer 1997). The problem of finding the shortest route between two locations is an example of the shortest path problem from graph theory. In setting, Dijkstra's algorithm for finding the optimal path benefits greatly from an efficient priority queue implementation (Exercise 9.32).

The operations that are supported by priority queue are

+   *insert(key)* that inserts an object with priority level *key* into the queue,
* *minimum()* which returns the object with the smallest key in the queue and
* *extractMin()* that both returns and extracts the object with the smallest.
