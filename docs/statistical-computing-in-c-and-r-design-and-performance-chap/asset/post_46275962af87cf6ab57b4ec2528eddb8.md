The code list below provides an example of using a pragma to parallelize a block of code.

### Listing 11.1 ompEx.cpp

```cpp
//ompEx.cpp
#include <omp.h>
#include <iostream>

int main () {
    int nP = omp_get_num_procs();
    omp_set_num_threads(nP);
    int myNumber;
    #pragma omp parallel private(myNumber)
    {
        myNumber = omp_get_thread_num();
        std::cout << "Hi ya'll from thread " <<
        myNumber << "!" << std::endl;
    }
    return 0;
}
```

The first thing to observe in Listing 11.1 is the inclusion of the OpenMP header file omp.h. Then, two OpenMP functions `omp_get_num_procs` and `omp_set_num_threads` are used to return the number of processors and set the number of threads, respectively. In this case the number of threads to be used in each parallel section has been specified as being the same as the number of processors.

The block of code in Listing 11.1 is created using a parallel directive with the variable myNumber being given a memory location for each of the n threads through use of a private clause. When the master thread forks at the beginning of a pragma every thread gets a unique ID starting with 0. The value of a particular thread is identified using `omp_get_thread_num` which is written into the variable myNumber in the program. Since myNumber had not been designated as private, its value would have been stored in a single memory location that was accessible by all threads shared and the resulting behavior of the program would be unpredictable with one thread able to write its value for myNumber into the space of time prior to accessing the value and using omp to write its message to standard output.

Compilation of OpenMP programs follows the `-fopenmp` compiler option. The command line for a program `programName.cpp` would look like

```bash
g++ -fopenmp programName.cpp -o executableName
```

This has the effect of creating executableName as the executable version of the program. For example, Listing 11.1 was compiled and executed with

```bash
$ g++ -fopenmp ompEx.cpp -o ompEx
./ompEx
Hi ya'll from thread 1!!
Hi ya'll from thread 2!!
Hi ya'll from thread 0!!
Hi ya'll from thread 3!!
```

## PARALLEL COMPUTING IN C++ AND RANG

This is certainly not the output we expected. But, it is not difficult to see what has transpired. The object is shared by all four threads that have been created to execute the parallel block of code. The result is a so-called race condition where all four threads attempt to access the shared object simultaneously. This problem can be resolved through use of a critical directive which has the form

```cpp
#pragma omp critical
```

This pragma forces the execution of the corresponding block of code to take one processor at a time. Thus, if the previous output statement is replaced with

```cpp
#pragma omp critical
{
    std::cout << "Hi ya'll from thread " <<
    myNumber << "!" << std::endl;
}
```

the result is:

- Hi ya'll from thread 1!
- Hi ya'll from thread 2!
- Hi ya'll from thread 0!
- Hi ya'll from thread 3!

Notice from that that the threads do not necessarily execute the program in sequence with their number.

Although using critical solved our output, it had the side effect of making the program execute in a serial, rather than parallel, mode when reached the point of writing to the shell. There was nothing gained by using the parallel construct. This observation holds more generally with the implication that the use of critical directives will have adverse performance consequences.

An alternative parallel implementation of greeting our program might include such as

```cpp
#pragma omp parallel for private(myNumber)
for(int i = 0; i < n; i++) {
    myNumber = omp_get_thread_num();
    #pragma omp critical
    std::cout << "Hi ya'll from thread " <<
    myNumber << "!" << std::endl;
}
```

with n value obtained from user input. In particular, the choice of n = 7 produced

- Hi ya'll from thread 0!
- Hi ya'll from thread 1!
- Hi ya'll from thread 2!
- Hi ya'll from thread 3!
- Hi ya'll from thread 1!
- Hi ya'll from thread 2!

To conclude this section will consider a simple optimization problem involving the function. As the aim is to find the global minimum of this function the non-template version of the Opt class will be employed to accomplish this goal. What will make the approach different from our previous development is that it will be carried out in parallel. The idea is that the domain of the function is partitioned into contiguous intervals of equal size with n being the number of processors. The threads are then assigned different intervals and find their respective local minima using the golden section method. The code that was used to accomplish this is collected in Listing 11.2.

### Listing 11.2 ompOptDriver.cpp

```cpp
//ompOptDriver.cpp
#include <iostream>
#include <cmath>
#include <omp.h>
#include "functor.h"
#include "optim.h"

using namespace std;
double pi = acos(-1.0);

double f(double theta) {
    return theta * pi * theta;
}

int main(int argc, char** argv) {
    Functor func(&f);

    int nEvals;
    cin >> nEvals;

    int nP = omp_get_num_procs();
    omp_set_num_threads(nP);

    double myMin;
    double* pMin = new double[nP];
    double myLow, myUp;
    int myRank;
    Opt Opt(nEvals);

    #pragma omp parallel private(myRank, myMin, myLow, myUp)
    {
        myRank = omp_get_thread_num();
        myLow = (double)myRank / (double)nP;
        myUp = (double)(myRank + 1) / (double)nP;
        myMin = Opt.gold(func, myLow, myUp);
        pMin[myRank] = myMin;
    }

    double min = pMin[0];
    for(int i = 1; i < nP; i++) {
        if(func(pMin[i]) < func(min)) min = pMin[i];
    }
    cout << pMin[0] << endl;

    cout << "The minimizer is " << min << endl;
    return 0;
}
```

There are a number of subtle aspects about this program that merit concern. First note that for an object or variable to be referenced in the private clause it must first be declared or initialized. The reason is that Opt, myRank, myMin, myLow and myUp were declared in the serial section before the parallel construct. Once a parallel block is encountered each thread receives its own versions of all the private variables and objects. In case of objects, thread-specific variables are created using the default constructor. As a result, an object must come from a class having a default constructor for it to be used in a private clause. On the other hand, the default destructor is called at the end of a parallel block and do not persist throughout the program or carry over to other regions.

The `pMin` pointer in Listing 11.2 provides access to many locations in shared memory as the threads then perform their optimization tasks and write the outcomes into distinct locations by their thread number. The scope of `pMin` is all of main which continues to exist after the end of the parallel block allowing minimum element to be declared as a global minimizer.

For minimization purposes each thread should have its own Opt and Functor class and object must be initialized with the same values. However, problems arise if we try to assign a pre-initialized object as private than one that has merely declared. The objects for threads other than the master (thread number 0) are created using the default constructor which means they will be initialized correctly. On the other hand, if an object of type Opt and Functor were simply declared prior to the parallel region there would be no way to initialize inside the region. The firstprivate clause that was used here provides the solution to such difficulties. In general, a statement of the

```cpp
#pragma omp firstprivate(variableName)
```

will cause each thread to receive their own copy of the variable varName with the value that it had prior to the beginning of the parallel block. For Listing 11.2 the firstprivate clause with the Opt class object ensures every thread receives an independent object with the number of iterations for each thread (cf. Listing 8.7). Similarly, each thread will have its own Functor object initialized with the address of.
