Two additional method functions are introduced initially with numeric arguments and first arguments that are missing and ANY. Neither of the functions (not any of the previous method functions for func) has signatures that will match a call to func with a single argument (and implicitly missing second) whether its value is from character or numeric. The combination of a character and numeric argument results in a call that will match two of the method function signatures: our previous one with a character and numeric argument and the new one with argument of ANY and numeric. The character and numeric arguments for the former method function are more specific, and they conform more closely (in, exactly) the types that were supplied to the function. Therefore, this is the function that is evaluated. If the first argument is explicitly omitted in the func(, 2) statement, the method function with the missing argument will be dispatched for numeric object2 data types; implicit omission of a leading argument will not work and generates an error message. The other option is to assign a numeric value for object2 as demonstrated with the func(object2 = 2) statement. Finally, a method function with ANY as the class for object1 and missing as the data type for object2 will respond when only a single argument is supplied to func; since the type of the first argument is provided, the hub version of func has enough information to call an appropriate method function whose signature will match the first argument (or more generally, the types of the arguments that have been supplied to the function) with other arguments (or just object2 in this instance) that are designated as missing.
Arguments need not be explicitly specified when one defines a method function; those that are not specified are implicitly assigned data type ANY. For example,

```
> setMethod("func", signature("ANY", "ANY")
+ func(object1, object2) print("ANY and ANY")
[1] "func"
```

and

```
> setMethod("func", signature("ANY"))
+ func(object1) print("just ANY")
[1] "func"
```

are functions with the same signature.

# 210 CREATING CLASSES AND METHODS IN R

Let us now apply some of what we have learned about creating generic methods to our regrFit classes of the previous section. Our first illustration will use the S4 function show that can be used either explicitly or implicitly to print out information about an object. It is called implicitly when an object's name is entered on the command line.

At present, a default version of show would be applied to regr objects that employs appropriate versions of show for the objects that occupy its slot. For large data sets this is likely much more output than necessary, for example the entire X matrix and response vector would be exhibited. As a result, it is probably worthwhile to extend show to regr objects in a way that produces succinct and interpretable output.

To create a new method for show the arguments must be known for its parent or hub generic function that will be used for method dispatch. To discover this information function name can be entered on the command line as the beginning of the section. If there are R manual pages for the function these will also provide argument details. Still another option is use of the args function as in

```
args(show)
function(object)
NULL
```

This tells us that show has a single named object. With this knowledge in hand, a (very) terse show method for regr objects

```
show.regr <- function(object){
cat("An object of class regr with,", ncol(object@X),
"predictors", "\n")
}
```

that uses the function as described in Section 5.2 for printing output. This is installed as a new method function

+ * setMethod("show", signature("regr"), show.regr)

Then,

+ * regrCar
Object of class regr with 3 predictors
+ * regrFit
Object of class regr with 3 predictors

which demonstrates that the new version of show is now being used for regr objects. As regrFit is a derived class of regr, this version of show will also work for regrFit objects.

In some cases it is of interest to perform a transformation on the dependent variable when conducting regression analysis. Numeric objects are raised to a power in R with the ^ operator. A check with generics reveals that ^ is an S4 function in the base package that is loaded whenever an R session is started. An application of args produces

+ * args("")
function(e1, e2)

Thus, new method functions may be defined that have the arguments e1 and e2. A new method function that will produce a regr object with a power transformed variable is to be

+ * setMethod("-", signature("regr", "numeric"), function(e1, e2)
+ regr(e1@X, e1@y^e2)

There is a bit more to the ~ operator that has been mentioned here. It is part of a generic class Arith that includes arithmetic operators as +, -, *, *. Group generics are collections of functions that perform related operations and have comparable mathematical structure in terms of, e.g., the number of arguments. With generic functions it is possible to simultaneously extend all operators in the group to work with objects of a given class. We will illustrate this in the next section using the Compare generic.

The @ and slot function provide us with a means of accessing the slots of an object. However, as for the C++ setting, it is generally preferable to use accessor functions that are simple and named. For example, we might create an accessor function for the coefficient of an regr object with

```
> setGeneric("bHat", function(object) standardGeneric("bHat")
[1] "bHat"
> setMethod("bHat", signature = "regr", function(object) object@b)
[1] "bHat"
```

An examination of the coefficients from our running example suggests that the regrCar can be simplified to (20,-5,1). Thus, we might need to perform the operation

```
> regrCar <- c(20, 0, -5, 1)
> bHat(regrCar)
Error: could not find function "bHat-"
```

This error message is a bit confusing as we just wrote and successfully used our bHat accessor function. The problem is that we are not using bHat here, instead, attempting to use its replacement version bHat<- that has not been defined for the regr class. This oversight is easy to correct

```
> setGeneric("bHat-", function(x, value) standardGeneric("bHat-"))
```

We then replace the name of the method using

```
> setMethod("bHat-", "regr", function(x, value)
+ {x@b <- value;}
[1] "bHat-"
```

Then, the alternative version of the coefficient vector can be installed with

```
> bHat(regrCar) <- c(20, 0, -5, 1)
> bHat(regrCar)
[1] 20 0 -5 1
```
