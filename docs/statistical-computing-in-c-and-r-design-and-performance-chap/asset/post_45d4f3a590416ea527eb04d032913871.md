Let us now assume that the drawing results from the Guess5 game data all be stored in the format shown above. If regular analysis is to be conducted on this data, time and energy can be conserved by creating a data analysis structure that is tailored to dealing with data of this type. A natural way to accomplish this is by building Guess5 related classes and functions and that is the approach that will be taken.

The first step in the design process is to consider what classes would be useful and suitable for Guess5 data. In representing the smallest data “unit” might be viewed as the results of a particular draw. It is important to be able to access the information about each individual draw for historical purposes as well as diagnostic analysis related to unusual draws that occur at various points in time. This suggests each draw has its own “identity”, and in mind a natural starting point would be the creation of a Guess5 class to hold the information about a single Guess5 draw.

In creating a Guess5 class we need to consider what information to retain about the draw results. The results can exhibit structural problems from wear and tear and machines malfunction. Thus, it may be necessary to look at subsets of the data that correspond to different sets and machines. Also, the date of the draw provides a unique identifier that can aid in sorting and locating data in a file suggesting that information of this nature should be included. These considerations lead to a “wish list” for properties that might be built into Guess5 class objects:

- a) Guess5 object should contain the results of a single night’s draw.
- b) Class members should include identifiers for the drawing machine and ball set that were used to carry out the draw. Other possible class members might represent information on the date and the day of the week for the draw.
- c) The actual drawing results (i.e., the numbers for all the balls that are drawn in the Guess5 draw and pretend experiments) should be available in a form that is easy to manipulate for data analysis purposes; e.g., as a matrix.

An R class that adheres to our design guidelines for Guess5 drawing results might be established with something like

```
> setClass("g5", representation = "Date",
+ mName = "character", sNo = "integer", Day = "character",
+ data="matrix")
[1] "g5"
```

This creates a base class g5 with class members for the date of the draw (drawDate), the machine name (mName), ball set number (sNo) and the day of the week (Day). All members derive from the R classes. We worked with the Date class previously in Section 5.6. The actual drawing results will be stored in the slot as a matrix object.

The next step is to create a constructor for the class. There are various ways this could be accomplished on the way the draw data can be accessed. Let us suppose here that the data come in the form of a 54-element array: the first four entries provide the date, machine name, ball set number and day of the week, respectively, and the next 50 giving the results. A constructor that will work for that scenario is

# CREATING CLASSES AND METHODS IN R

```
g5 <- function(a){
  drawdate <- as.Date(a[1])
  mname <- a[2]
  sno <- as.integer(a[3])
  day <- a[4]
  A <- matrix(as.integer(a[5:50]), 10, 5, byrow = TRUE)
  g50bj <- new("g5", drawDate = drawdate, mName = mName, sno = sno,
  day = day, data = A)
}
```

The first four elements of the input array are used to set the values that will be used to fill the drawDate, mName, and Slot for the g5 object. Then the next 50 elements are converted from character to integer using the as.integer function and reshaped into a 10 x 5 matrix. This information is used in the constructor function to create a new object.

A validity check function should be installed to ensure that constructor has produced a valid g5 object. A function that will work for that purpose is

```
validG5 <- function(object){
  if(object@mName != "A" & object@mName != "B")
    return(paste("Incorrect machine for date", object@drawDate))
  if(object@sNo < 1 | object@sNo > 10)
    return(paste("Incorrect set number for date", object@drawDate))
  if(object@Day != "M" & object@Day != "T")
    return(paste("Incorrect day for date", object@drawDate))
  if(any(object@data < 1 | object@data > 40))
    return(paste("Incorrect ball number for date", object@drawDate))
  return(TRUE)
}
```

This can be set as the function to check for incorrect input data through the command

```
setValidity("g5", validG5)
```

The effect will not be rejection unless the ball set, machine or day entries do not coincide with appropriate game. Similarly a check is performed to see that all the ball numbers are between 1 and 40. The calculations in this case are carried out using any function that takes a logical array as its argument and returns TRUE if elements evaluate as TRUE. If there are any number values that fall outside the 1 to 40 range, will return TRUE and the date of the draw where error has been found will be printed to help locating the problem and correcting it in the file.

Eventually we will create a function that can sort a collection of g5 objects. The critical ingredient in accomplishing this is having order relationships that allow us to compare g5 object to another. For our purposes the result will be in terms of drawDate slot that will produce a chronologically sorted arrangement. Rather define ==, <=, etc., individually is possible to define all operators simultaneously with a slight modification of our previous approach for defining methods. The difference is that now the method functions will be defined for a group or collection of functions named Compare in this. Other group generics include those with Arith, Logic, Math and Summary as described on the R page for S4 groupGeneric. For Compare the help page describes the functions in the group having the basic form

```
Compare(e1, e2)
```

Thus, they are all functions with two arguments e1 and e2. All of them can be extended to the g5 class using

```
> setMethod("Compare", e1 = "g5", e2 = "g5")
+ function(e1, e2) callGeneric(e1@drawDate, e2@drawDate)
[1] "Compare"
```

The callGeneric that appears here is for method dispatch; it will call the current generic function that is appropriate for the Date class objects e1@drawDate and e2@drawDate in instance. This will be sufficient because all the functions in the Compare generic have methods that apply to the Date class as indicated in the R help page gives results as

```
> g50bj1 > g50bj2
[1] FALSE
> g50bj1 < g50bj2
[1] TRUE
> g50bj1 == g50bj2
[1] FALSE
> g50bj1 <= g50bj2
[1] TRUE
```

The fact that for g50bj1 (i.e., 1952-01-17) is earlier than the date for g50bj2 (i.e., 1952-01-21) shows that the comparator operators are working correctly.
