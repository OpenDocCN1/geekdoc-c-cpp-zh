There are two packages that provide RngStreams: reclyer and rstream. The former is actually a feature in Rmpi and readily accessed as

```r
> Library (Rmpi)
> mpi.spawn.Rslaves(nslaves = 4)
> 4 slaves are spawned successfully. 0 failed.
> master (rank 0, comm 1) of size 5 is running on: cos
> slave1 (rank 1, comm 1) of size 5 is running on: cos
> slave2 (rank 2, comm 1) of size 5 is running on: cos
> slave3 (rank 3, comm 1) of size 5 is running on: cos
> slave4 (rank 4, comm 1) of size 5 is running on: cos
> mpi.setup.rstream(seed = 1:6)
> Loading required package: reclyer
> mpi.remote.exec(runif(1))
X1 X2 X3 X4
1.000109498 0.701715 0.476142 0.04690119
```

Note the reclyer package needs to be installed before this approach will work. If that is the case, the effect of mpi.setup.rstream is to replace R's default number generator with the backbone generator from RngStreams. It appears that the reclyer implementation of rstream is slower than the rstream package. As our result, our discussions will focus on rstream from this point forward. Further discussion of both topics with their use new and snow can be found in Karl, et al. (2011).

The first step is to load the rstream package

```r
> library (rstream)
```

This has the effect of introducing the S4 class rstream into the current R workspace. Instances of rstream class may be created from the derived class rstream.mrg32k3a which provides access to the now familiar RngStreams backbone generator. A new rstream object, created using syntax of the form

```r
newRstreamObj <- new("rstream.mrg32k3a", seed = Seed)
```

With a seed-component vector of integers. Subsequent rstream.mrg32k3a objects created will automatically have initial seeds that are 2^27 states removed from the most recently created object. The rstream.sample function returns a sample of n random numbers from the object newRstreamObj via the command

```r
rstream.sample(newRstreamObj, n)
```

Because rstream objects are stored as pointers in the underlying language code, it is necessary to "pack" before they can be sent to another node in Rmpi. The same process is also to save an rstream object so that it will be available in a future R session. Packing is accomplished with

```r
rstream.packed(newRstreamObj) <- TRUE
```

Before they can be packed objects must be unpacked by

```r
rstream.packed(newRstreamObj) <- FALSE
```

Beyond this, the process of actually using rstream with Rmpi is relatively straightforward. For the case of p processes, one carries out the following sequence of steps:

- 1. create instances of the rstream.mrg32k3a class,
- 2. pack each object using rstream.packed.
- 3. load the rstream package on each processor,
- 4. send the rstream objects to the p processors using mpi.send.Robj,
- 5. receive the objects on each processor with mpi.recv.Robj,
- 6. unpack the rstream objects on each processor with the rstream.packed function.

At this point the random numbers on each node will correspond to “independent” streams and can be used in whatever order the tasks may be assigned.

An illustration of the scheme we have laid out for rstream with R is given in the excerpt from rstream shown below.

```r
> library (rstream)
> library (rmpi)
> mpi.spawn.Rslaves(nclaves = 3)
3 slaves are spawned successfully. 0 failed.
master (rank 0, comm 1) of size 4 is running on: localhost
> slave1 (rank 1, comm 1) of size 4 is running on: localhost
> slave2 (rank 2, comm 1) of size 4 is running on: localhost
> slave3 (rank 3, comm 1) of size 4 is running on: localhost
> create a list of lists. rstream.mg32k3 objects
> rgList <- vector(length = 4, mode = "list")
> rgList <- c(new("rstream.mg32k3a", c(1, 2, 3, 4, 5, 6)), replicate(3, "rstream.mg32k3a"))
> pack the objects that will be sent to the processors
> for(i in 1:4) rstream.packed(rgList[[i]]) <- TRUE
> load the package and send the packed rstream objects
> library(rstream)
> for(i in 1:3) mpi.send.Robj(rgList[[i]])
> mpi.setup.rstream(seed = 1:6)
> mpi.recv.Robj(myRng)
> unpack the objects on the processors
> rstream.packed(myRng) <- FALSE
> generate the random numbers
> mpi.remote.exec(rstream.sample(myRng, 1))
X1 X2 X3 X4
1.000109498 0.701715 0.476142 0.0469019
> rstream.sample(rgList[[1]], 1).
```

The initial steps are to import rstream and rmpi packages. Three slaves are spawned and a vector of lists is created to hold rstream objects that will be sent to the processors. The first rstream object is created using the new function with the vector (1, 2, 3, 4, 5) and placed in the first component of rgList. The remaining three rstream objects are created similarly using replicate and used to automate the remaining rgList entries. rgList[[1]] belongs to the master process and the packing of the list elements does not have to be packed. The next step is to load the rstream package on each of the slaves. This is accomplished with mpi.bcast.cmd function. A for loop is used in conjunction with mpi.send.Robj function to send the packed rstream objects to the slaves after the processors receive them with mpi.recv.Robj. The mpi.bcast.cmd function is employed to tell each slave to unpack its rstream object by an application of mpi.remote.exec with rstream.sample functions to produce the first random uniform of each number stream. A comparison of these values with those obtained in MPI and OpenMP examples shows that we reproduced the streams that were previously obtained in these settings.

The use of rstream is even simpler with the multicore package. The same random numbers that were produced with Rmpi can be obtained by using mclapply as in the code below.

```r
> library(rstream)
> library(multicore)
> rngList <- vector(length = 4, mode = "list")
> rngList <- c(new("rstream.mg32k3a", seed = c(1, 2, 3, 4, 5, 6)), replicate(3, new("rstream.mg32k3a")))
> mclapply(rngList, function(a) rstream.sample(a, 1))
```

[1]
[1] 0.000109498
[2]
[1] 0.701715
[3]
[1] 0.476142
[4]
[1] 0.0469019

Thus, we have produced the same random number streams with OpenMP, MPI, Rmpi and multicore.

11.4. The MPI "broadcast" function has prototype

```cpp
void MPI::COMM_WORLD.Broadcast(void* buf, int count, MPI_Datatype datatype, int root)
```

This function provides more immediate communication between processors allows us to avoid the loops that were used with Send and Recv. The arguments are the same as those for Send until the root argument is reached in the prototype. This latter parameter represents the rank of the processor whose buf is to be distributed to all the processors. All processors must call Bcast.

11.5. The opposite effect of Bcast can be obtained from the MPI function Gather. It collects information from all processors into a single processor that is usually taken to be processor 0.

```cpp
void MPI::COMM_WORLD.Gather(void* sendbuf, int count, MPI_Datatype datatype, void* recvbuf, int count, MPI_Datatype datatype);
```

The quantity sendbuf is a pointer to count locations that is sent from each processor to 0. This is then gathered into recvbuf which needs to be defined on processor 0 and have size equal to the product of count and the number of processors (including processor 0). As was the case with Bcast, the function Gather must be called by all processors.
