## 6.3 Generic methods

As compared to the C++ setting, functions are linked to a particular class and access only through a class object, functions in R may extend across multiple classes. This allows us to write a function that operates on objects from a given class and subsequently extend function to work on and produce different types of output for some other class. In this generic or "template" functions are created with the same name that take arguments from different classes. This section presents details on how functions are created in the R language. Since R comes with a number of predefined generic functions, there are basically problems that must be addressed: how to extend one of the defined generics to a new class and how to define a new generic function.

As noted at the beginning of the chapter there are two ways to create generic functions in R: the S3 and S4 systems. The syntax for creating and extending functions under the systems is quite different. Then, the first step in extending an existing function is to ascertain whether it is of the S3 or S4 variety. One way to make a determination is through use of the isS4 or isGeneric functions that returns TRUE when applied to the names of 4 generic functions. In the case of the functions show and coefficients discussed in Appendix B this produces

Let us turn to the case of S4 generics. To see the currently available generic use getGeneric() on the R command line. New methods for the functions whose names appear in the resulting list may be created using setMethod. For functions that are not present, new generic function must be created by first using setGeneric and then invoking setMethod

```r
setGeneric(name, signature)
```

and

```r
setMethod(name, signature, definition)
```

with a character string that represents the name of the function, function specification and signature a character array that defines data types for the non-ellipsis arguments of the generic function specified in. To illustrate the use of setGeneric and setMethod we will initially focus on a simple "toy" example that will demonstrate the ideas with a minimum of technical detail. suppose that a new two-argument function func is to introduced into our R session. This is accomplished with the command

```r
> setGeneric("func", function(object1, object2, ...)
+ standardGeneric("func"))
```

This establishes a generic function having three arguments: object1, object2 and the ellipse. The presence of standardGeneric in the body of the function indicates that incarnation of func will serve as the function for methods dispatch. it represents hub or "traffic control center" that directs calls to the appropriate method function. It performs this operation based on the non-ellipse arguments or object1 and object2 in this instance. To remove a generic function from the workspace use removeGeneric: e.g.,

```r
> removeGeneric("func")
[1] TRUE
```

This will remove func as well as any method functions it might have. If only a particular method function be removed, removeMethod can be used. To see how method dispatch considers the introduction of two new methods from func via

```r
> setMethod("func", signature("numeric", "numeric")
+ function(object1, object2) object1*object2)
+ object2 = c("numeric", function(object1, object2))
+ print(paste(object1, object2)))
[1] "func"
```

The signature arguments for the two method functions have been specified using two different but equally valid ways: the first case employs the signature function that returns a list of classes that will be matched in order to the arguments of the hub function while the second just specifies the argument array directly. The signatures that have been given for the two method functions tell us that the first will work for cases where both object1 and object2 are from class numeric while the second is intended for cases object1 is of type character and object2 is numeric. The first method function will compute the product of its two arguments while the second prints out values. An application of func will now produce results as

```
func(2,3)
[1] 6
func("Hi ya'll!", 3)
[1] "Hi ya'll!" 3
func(as.character(2), 3)
[1] "2" 3
func("Hi", ya'll")
```

```
Error in function (classes, fdef, mtable) :
unable to find an inherited method for function "func"
for signature "character", "character"
```

Thus, the hub method for func matches the data types for the arguments that are supplied to func with its method signatures to determine (if any) are appropriate and invokes the most appropriate one to "answer" the call to func. If there are no method functions with signatures that can match the given arguments, an error message is generated.

Method dispatch cannot be based on additional arguments that come in the ellipse. This is illustrated by

```r
func(2,3)
[1] 6
setMethod("func", signature("numeric", "numeric"),nfunc(object1, object2, object3) object1*object2*object3)
[1] "func"
func(2,3)
Error in object1 * object2 * object3 : 'object3' is missing
func(2, 3, 4)
[1] 24
```

Initially the func function with two numeric arguments is used. Then, a three-argument method function with numeric data types for object1 and object2 is introduced to replace the two-argument version. The conclusion is that only the types of the non-ellipse arguments can serve as a means to distinguish between different method functions.

It is possible to have missing arguments by specifying them to be of type missing. In order for functions with missing arguments to be called, one of three things needs to be true:

- they are explicitly missing; e.g., a comma separated empty argument is present,
- the nonmissing arguments are specified by name or
- only trailing arguments from func's list are missing.

The opposite effect from using missing is achieved by specifying an argument as data type ANY. In this latter an object from any class can be provided as the argument's value. An illustration of this is provided in the R output below.

```r
setMethod("func", signature("missing", "numeric"),nfunction(object1, object2) print("missing and numeric")
[1] "func"
setMethod("func", signature("ANY", "numeric"),nfunction(object1, object2) print("ANY and numeric")
[1] "func"
func("a")
```
