# Verifying the vulnerability

First need to verify the vulnerability with the page. When we first arrive at the page, we see the login screen. When we type random things into the page, we see that our login fails, but when we try entering the string ' or l=1 -- into the login field, we get access to the application. We need to make sure to include the space after the two dashes in Microsoft SQL Server as well to ensure that the comment is interpreted properly. While gaining access to the application may prove to be interesting, we may be able to do more with this flaw.

The next step with this application is to check if xp_cmdshell is enabled. If we can't see the output, though, how do we know it is running? One way to determine if SQLi is working when we can't see it is by using a timing approach. This is called blind SQLi we cannot see what is happening; we have to determine success in other ways. To check to if xp_cmdshell is running, we can use the ping command. But why ping? sends one packet per second by default. So, if we send out five packets, we should expect the execution of the script to hang for 5 seconds. Let’s formulate a new SQLi string with the xp_cmdshell syntax.

```
' or l=1; exec xp_cmdshell 'ping -n 5 127.0.0.1' --
```

When we run the query, the script doesn't hang at all. What we have tried to do is calling the xp_cmdshell stored procedure to ping 127.0.0.1 five times, causing the script to wait for 5 seconds. Unfortunately, xp_cmdshell isn't enabled. Hopefully, we are logged as an admin user. If we are not, we are going to find another way to exploit this machine. To check to see if we are an admin, we modify our injection string.

```
' or l=1; if is_srvrolelemember('sysadmin') > 0 wait for delay '0:0:5' --
```

This new string takes advantage of conditional capabilities within the SQL server. We use the is_srvrolelemember procedure to query the database as to whether we are a sysadmin.
