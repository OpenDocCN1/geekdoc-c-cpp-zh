# What is RFI?

RFI happens when the user of an application gains control of a variable that allows user-specified code to be executed instead of the code intended by the application developer. What differentiates RFI from Local File Inclusion (LFI) is that the code can be on another server.

In PHP applications, there are typically two problems that lead to RFI vulnerabilities. Usually, these vulnerabilities are due to files that are expected to be included as part of another page that includes other files. If the file is specified as part of the request, a user may be able to change that value so they specify which page is loaded, and if the Web server is not configured properly that could allow the attacker to include files on remote systems.

When the logic error is caused with insecure PHP settings as `register_globals` and `allow_url_include`, the logic problem becomes an RFI vulnerability. `Register_globals` tells the Web server to take GET and POST variables and define them as variables. This means that if a file expected `$config_dir` to be defined in another file, and that file is not included, specifying `config_dir` as part of GET or POST requests will allow the application user to specify it. This alone would be just an LFI, but when `allow_url_include` is set as well, we can now use URL file locations.

Once we can include our own files, the application is no longer the developer’s application, but ours. Through using PHP shells, custom code, or even Metasploit, we can include our own logic into applications to gain additional access to the host or the network, and we can leverage this to gain additional access to the enterprise.
