This chapter focuses on how PowerShell can be handy in certain penetration testing situations. After discussing the execution policies and the code for bypassing them, the chapter talks about how to get on the system and what can be done with PowerShell once there. it goes over some example uses for PowerShell, such as controlling processes and services, interfacing with the event logs, getting and sending files over the network, and interfacing with the Registry, and then closes with examples of what can be done using PowerShell and the Metasploit attack framework.

In Chapter 1, Introduction to command scripting, we spent a good bit of time discussing Microsoft's PowerShell and how we can use it to develop shell scripts. Some of these scripts, if developed a bit further, could be useful for general tasks such as collecting information on hosts and the networks on which they reside. In this chapter, we will dive directly into the nitty-gritty of using PowerShell as a hacking tool.

Until fairly recently, PowerShell was not generally seen as a tool that could be used for attacks. It has a very restrictive set of permissions that limit what we can run on a system, as we discussed in Chapter 1, Introduction to command shell scripting, and we have to relax these permissions in order to get even the most basic scripts and commands to run. In addition, we really can't do much on a system with PowerShell without taking steps to disable these security measures ... or so it was thought.

At DEF CON18 in 2010, David Kennedy and Josh Kelley gave a presentation [1] on PowerShell and discussed how it might be used as an attack tool, how we can bypass the security measures in place, and some of the interesting uses which we can put PowerShell in a penetration testing scenario. Given the efforts of Kennedy, Kelley, and the others who worked on the code discussed in this presentation, we are on a much better footing to use PowerShell in new and interesting ways. Let's jump in and see what we can make PowerShell do for us.

## Dealing With Execution Policies in PowerShell

As mentioned in this chapter, and discussed in Chapter 1, Introduction to command shell scripting, there are execution policies that dictate what we can do in PowerShell. In Chapter 1, Introduction to command shell scripting, we had to change the execution policy to RemoteSigned in order to work with our scripts, but we didn't really talk about the individual policies, or what exactly each of them does. We will go over that now.

### Execution Policies

There are four execution policies: Restricted, AllSigned, RemoteSigned, Unrestricted, and Bypass. The Restricted policy, which is also the default execution policy, prevents us from running any PowerShell scripts, but does allow us to use the shell interactively. AllSigned policy allows us to run scripts that have been digitally signed by a trusted publisher. The RemoteSigned policy allows us to run scripts that we have created, but scripts we download must be digitally signed by a trusted publisher. The Unrestricted policy carries no restrictions at all, and allows us to run unsigned scripts from any source but will warn when a script has been downloaded from the Internet. The Bypass policy allows us to run scripts from anywhere, and will execute the scripts without regard to the source. These execution policies can be changed in the manner we discussed in Chapter 1, Introduction to command shell scripting.

The signing on which some of the execution policies refers to is the digital signatures on the scripts themselves. The signatures need to come from a trusted publisher in order to bring them into compliance with the various execution policies.

### Tip

We can actually create a self-signed certificate to use for signing our scripts, but we will still get a warning when the script runs, at the very least for the first time. This is a bit of an involved process, but articles and tutorials are available on the Internet that will walk us through it.¹ In a penetration test, we are often better off just working around the execution policy, as we will discuss in Bypassing the Policies section.

> ¹http://www.hanselman.com/blog/SigningPowerShellScripts.aspx.

In an ideal world, we would like to have the execution policy set to Unrestricted, Bypass, or at least to RemoteSigned, so that we can run our scripts on the target system. However, as we discussed in Chapter 1, Introduction to command shell scripting, this requires that we make some changes to the system if the execute policy is not already set in this way. In a penetration test, we may not want to be able to change the settings in the system. Frankly, there is a way around this issue that requires no changes at all, and leaves us to run any script we like.

## Bypassing the Policies

In order to get around the restrictions imposed by the execution policies that govern PowerShell, we can use the CreateCMD code developed by Peters, Kelley, and Kennedy [2]. The following example is the same code developed by the aforementioned authors, minus a few comments and usage for the sake of brevity.

```query
param($Filenames);
if (-not $Filenames)
{
    Write-Host "Usage: createcmd.ps1 [-Filenames] <string[]"
    return;
}
$contents = gc $Filenames;
$ms = New-Object IO.MemoryStream
    $cs = New-Object IO.Compression.DeflateStream ($ms, IO.Compression.CompressionMode]::Compress)
    $sw = New-Object IO.StreamWriter ($cs,[Text.Encoding]::ASCII);
    $contents | % {
        $sw.WriteLine($_);
    }
}
$sw.Close();
```

```query
$code = [Convert]::Base64String($ms.ToArray());
$command = "Invoke-Expression `$(New-Object IO.StreamReader (\
  `$(New-Object IO.Compression.DeflateStream (\
    $,([Convert]::FromBase64String(`$code`)),
    [IO.Compression.CompressionMode]::Decompress))\n  ), [Text.Encoding]::ASCII)).ReadToEnd())` Load complete.\`"
$command = "powershell.exe "[1]"";
$command -f "Command",command.Replace("\", ""\\")
```

Let's have a quick look at what we're doing. The first line that takes in the arguments for the script, make make using the method we used in param. This is essentially the same thing as we used in Chapter 1, Introduction to command shell scripting, but with slightly less code. In this case we are taking the filenames from the command line. We use gc, which reads the contents of the file in $Filenames (very much like cat in Linux), and places them into $contents. The variable $ms is a handle for the IO.MemoryStream object that we will use shortly for a bit of storage. We set up $cs and $sw as handles for the IO.Compression.DeflateStream and StreamWriter objects, respectively. Once we have our objects all set up, we write the compressed contents to our memory stream and close the stream writer.

Now that our script contents are in storage we can convert them. The Base64-converted string of $ms, is assigned to the $code variable. This is the code that we pass off to Invoke-Expression in the context of the shell.

Ultimately, we will execute createcmd.ps1 with fileout.ps1 | Out-File fileout.bat ascii. Our test script, fileout.ps1, should contain only the line Set-Content -Encoding utf8 test.txt "test", which will output a file so that we have something to see as a result. We should end up with a file fileout.bat which, when run, will execute our original code. This code allows us to completely bypass the execution policies and execute our code, no matter what the source is and no matter what the execution policy level is set to. Just to make things clear, we are not actually changing the execution policy level, and we are not making any configuration changes in the system. We are simply bypassing the signed script security measures.

## Warning

At present, CreateCMD code works very nicely to get us around the policy restrictions that Microsoft has placed on PowerShell scripts as a security measure. We, of course, have no guarantee that this will continue to be the case forever and that Microsoft will not release a patch or a new PowerShell version that closes this particular loophole. If we find the CreateCMD code fails entirely, or does not work on certain versions of PowerShell, it might be worth a bit of checking to see if this has indeed happened.

With this capability in hand, PowerShell quickly becomes more useful from a penetration testing perspective. Although we could certainly carry out attacks using social engineering techniques or tools such as a Trojan horse in order to have the user change the execution policy for PowerShell, we would rather not take such steps if we have another way to get to where we need to be.

One caveat to using this process to get around the execution policies is that, although we can effectively ignore the execution policies using this method, this is not a magic bullet. There are still activities in PowerShell, which will require us to have administrative access, and we may be stuck if we have not been able to gain it.
