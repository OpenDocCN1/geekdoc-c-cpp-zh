## Adding /dev/tcp/support to Bash

We can do a quick recompile of bash in order to get the /dev/tcp support we need. This may sound a bit scary to some, but it's really not that bad. Here are the steps to recompile bash on Kali 2.0:

- 1. Download the most recent source files for bash. Presently this is bash 4.3.30 and can be found at ftp.gnu.org. We can pull this down with wget, like so:
```bash
wget https://ftp.gnu.org/gnu/bash/bash-4.3.30.tar.gz
```
- 2. Extract the files from the archive and change to the directory:
```bash
tar -xvzf bash-4.3.30.tar.gz
cd bash-4.3.30
```
- 3. After extracting the files, configure and install bash:
```bash
./configure --enable-net-redirections
make && make install
```
- 4. Swap out the existing bash for the newly compiled version:
```bash
mv /bin/bash /bin/bash-orig
ln -s /usr/local/bin/bash /bin/bash
```
- 5. Test your effort with this command:
```bash
cat </dev/tcp/time.nist.gov/13
```
which should return something along the lines of:
`55647 15-10-22 15:41:57 50 0 75.2 UTC (NIST) *`

# Building a Port Scanner With Bash

Here is the code for a simple port scanner constructed with bash. The script takes three arguments: a hostname or IP address, the port at which we wish to start our scans, and the port at which we wish to stop our scans. We would run it like /portscanner.sh 10.0.0.1 1 100.

```bash
#!/bin/bash
#populate our variables from the arguments
host=$1
startport=$2
stopport=$3
#function pingcheck
#ping a device to see if it is up
function pingcheck
{
  ping=`ping -c 1 $Host | grep bytes | wc -l`
  if [ "$ping" -gt 1 ]; then
    echo "$host is up"
  else
    echo "$host is down quitting"
    exit
  fi
}
#function portcheck
#test a port to see if it is open
function portcheck
{
  for ((counter=$startport; counter<=$stopport; counter++))
  do
    echo >/dev/tcp/$host/$counter > /dev/null 2>&1 && echo "$counter open"
  done
}
#run our functions
pingcheck
portcheck
```

At the top of the script, we find the shebang to indicate the interpreter we wish to use, and a few lines to assign the values from the argument to the host we wish to scan (host), the starting port (startport), and the stopping port (stopport). On the second line, we also encounter the comment mark we can use in bash: #. The command allows us to direct the interpreter to ignore anything on the line after the #. We then have two functions: pingcheck to check if our host is available on the network and portcheck to test for open ports.

In the pingcheck function, we are to check if our host is available on the network and placing the final result in the ping variable. The backticks `` ` `` indicate we are performing command substitution. Command substitution passes the code between the pair of backticks to the shell to be executed, then substitutes results of the command. In this case, we are stringing together a series of commands by using pipe, which passes the output of one command to another. Our command executes `ping -c 1 $host`. The -c flag allows us to limit the number of packets that are sent. We send a single packet to the host we are operating on using -c 1. Then we pass the output of that command to grep, which searches for the string "bytes". We then pass that output to wc. The wc command counts the number of words in whatever is sent to it. We run the ping command, and we will find the string "bytes" at least once. This happens whether it fails or succeeds. But on a successful ping, we will find it than once. We are using the wc command in order to count the occurrences of the string, indicating a successful ping to the host. If the ping succeeds, we echo a message to the console and return to the main body of the script. If the ping fails, we echo a message to the console and quit.

In the portcheck function, we set up a simple for loop in order to see if they are open. Here we use for from the starting port to the stopping port, taken from the arguments with which the script was run. This line makes use of the /dev/tcp device enabled earlier. In essence, we attempt to echo nothing to /dev/tcp/host/port; if that works, we take the results of that command and send them to /dev/null. In addition, we use the && operator in order to echo the port number to the console. Ultimately this allows us to detect whether a port is open.

# Improving the Script

There are a number of ways we can improve the port scanner to make it more efficient and functional:

- We presently handle multiple hosts. We could add this capability by including additional arguments, or by reading hosts or IPs from a file.
- In pingcheck function, when we encounter a device that does not respond, we have to wait several seconds for the ping command to return and tell us so. If we include a timeout command, we can likely shorten this considerably.
- In portcheck function, we are only testing Transmission Control Protocol (TCP) ports. If we want to test User Datagram Protocol (UDP) ports as well, we can make use of /dev/udp in a very similar fashion to our existing code. We would also need to include the appropriate arguments to indicate whether we need to scan TCP ports, UDP ports, or both. These are only a few of the many additional features we might add in order to increase functionality, make the script work more efficiently, and generally make the tool more useful and usable.

# Windows Scripting

Microsoft operating systems hold 85% of the desktop operating system market as of 2015. As penetration testers, we would be foolish to ignore the scripting capabilities of this enormous share of the market. Fortunately, Microsoft operating systems currently have a very well-developed and strong capability to conduct administrative operations from the command line and provide us with tools such as PowerShell to use in our efforts.

# Shell Availability and Choices

On Microsoft operating systems, due to the generally closed nature of the operating system and standard applications and utilities present, we will often find ourselves with access to built-in text-based shells. Even so, this leaves us with several choices when we need to put together scripts for Windows, including scripting with the cmd.exe and PowerShell, as well as Cygwin or any other custom solutions we might find installed.

# Command.com and CMD.exe

Command.com and CMD.exe are the two main shells available in almost every Microsoft operating system. In the newer 64-bit versions of these operating systems, command.com is not available at the time of this writing, and may continue to be unavailable in the future.

Ultimately, command.com and CMD.exe are two different tools. CMD.exe is a text-based interface to the operating system. It is not a DOS shell, and does not provide the same functionality as such shells. Command.com is actually a version of 16-bit DOS running in a shell and provides a similar but not identical set of functionality. One of the noticeable differences when using the two shells is that command.com does not support long file names, forcing the use of constructs such as PROGRA to address directories as Program Files.

# Batch files

Batch files have been around since the early days of MS-DOS and have continued through the most recent Microsoft operating systems. These scripts, designated by a .bat extension, are used for a variety of tasks, mostly in the nature of small utility functions, although if we look back to older operating systems, we can find them actually used in starting parts of the operating system.

Batch file scripting has a language of its own which, although not terribly complex, can still be useful for some things. We can use Notepad to put together a quick batch script that will ping a list of IP addresses from a file. To open Notepad in Windows 8, press the Windows key or type in "notepad" and hit enter.

```batch
@echo off
setlocal EnableDelayedExpansion
for /f "tokens=* delims=" %a in (hosts.txt) do (
  ping %a
)
```
