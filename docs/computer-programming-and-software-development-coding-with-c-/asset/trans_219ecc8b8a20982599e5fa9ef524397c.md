

接口内部的自动属性。对于我们这两种方法，GetPerimeter 和 GetArea，它们也只是声明。因此，提供 NumberOfSides、SideLength、GetPerimeter 方法和 GetArea 方法的实现是实现类的责任。

```
namespace Polygons.Library
{
    public interface IRegularPolygon
    {
        int NumberOfSides { get; set; }
        int SideLength { get; set; }

        double GetPerimeter();
        double GetArea();
    }
}
```

你可能会注意到，这个接口的成员没有任何访问修饰符，public、protected、private 或 internal。我们如果愿意可以为成员添加访问修饰符。如果我们不提供它们，它们默认是 public。并且为了让你了解其中的区别，对于类，我们的具体类和抽象类，默认是 private。所以如果我们在类的成员上不提供访问修饰符，它默认为 private。如果我们在接口的成员上不提供，它默认为 public。你经常会看到接口成员没有显式修饰符，这意味着它们是 public。其原因是在 C# 8 之前，接口中的所有内容都是自动公开的。我们将在最后一章更详细地讨论其他访问修饰符。现在，重要的是要理解接口的默认值与类的默认值不同。为了看到接口的实际使用，我们来看 Octagon 类，在这里，我们可以看到 Octagon 实现了 IRegularPolygon 接口。注意，我说的是实现了接口，而不是继承自接口。关于 C# 需要记住的一点是，如果

我们没有提供基类，一切都继承自 Object。所以我可以更新语法，说 Octagon 继承自 Object 并实现 IRegularPolygon。这件好事之一是，一个类可以实现它需要的任意多个接口。因为我们的接口没有提供任何实现代码，我们必须在 Octagon 类中提供所有这些。因此我们有两个属性，NumberOfSides 和 SideLength，只是为了让人困惑，这些在这里是自动属性，因为它是一个类。我真的希望这两种东西的语法不同，但不幸的是，这就是我们目前拥有的。除属性外，我们还有一个构造函数来填充这些值，我们有 GetPerimeter 方法，还有 GetArea 方法，所有这些都有实现代码。如果我们回到控制台应用程序，我们可以添加一个 Octagon。这创建了我们的 Octagon 类的一个实例，SideLength 为 5，并且当我们运行应用程序时，我们会看到所有值都输出。抽象类和接口之间一个很大的相似之处是，我们必须为任何尚未提供实现的内容提供实现。

```
using System;

namespace Polygons.Library
{
    public class Octagon : Object, IRegularPolygon
    {
        public int NumberOfSides { get; set; }
        public int SideLength { get; set; }

        public Octagon(int length)
        {
            NumberOfSides = 8;
            SideLength = length;
        }

        public double GetPerimeter()
        {
            return NumberOfSides * SideLength;
        }

        public double GetArea()
        {
            return SideLength * SideLength * (2 + 2 * Math.Sqrt(2));
        }
    }
```

这意味着，在我们的 Octagon 类中，我们必须提供所有这些实现。如果我注释掉 GetPerimeter 方法并尝试构建应用程序，我们会得到一个构建错误。并且如果我们查看错误，它会说，'Octagon' 未实现接口成员 GetPerimeter()。所以就像抽象类中的抽象成员一样，如果我们不提供接口所需实现，我们会得到编译器错误。

## 第 2 章 面向抽象编程

现在我们已经看到了接口是什么，是时候开始了解为什么我们想要使用它们了。一个很大的优势是接口可以使我们的代码更灵活。这在面对变化时提供了弹性，而应用程序不断变化以满足用户需求。这种弹性意味着当我们在应用程序的一个部分进行更改时，我们减少或消除了在应用程序其他部分进行更改的需求。我们的代码会弯曲而不是断裂。这也使我们的代码与实现细节隔离。我们可以通过关注功能的结果而不是深入功能本身的细节来在更高层次处理代码。当然，如果需要，我们可以深入这些细节，但它们被放在一边，这样我们只有在需要时才这样做。有一种通用的建议在许多情况下都适用，即面向抽象编程而不是面向具体类型。当我们处理抽象时，我们处理的是更高层次的代码，我们可以避免陷入细节。在我们的示例中，我们将这种建议翻译为面向接口编程而不是面向具体类。接口是一种抽象，它为我们的代码添加了一个缝隙，这就是我们可以专注于更高层次功能的方式。我们可以盲目地遵循这一建议，但这会导致麻烦。最好理解其背后的原因，然后我们就可以决定何时遵循建议以及何时可以安全地忽略它。接口是工具，有时它们有用，有时它们没有用。我们之前看到具体类只是我们每天使用的常规类。这些可以是我们自己创建的类，也可以是各种库中的类。对于下一个示例，我们将使用 .NET 集合类。这里是我们可用的不同类型的集合列表。
