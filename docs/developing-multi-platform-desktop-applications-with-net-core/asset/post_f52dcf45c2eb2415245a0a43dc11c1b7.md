### Specifications (and requirements gathering)
Do not overlook the specifications phase because it will define the architectures and technologies choices. During this phase you will:
- make the analysis (possibly with tools like UML).
- retrieve the user's stories (requirements).
- and possibly define form design (functional).

### Architecture and coding
During this phase you will define the software architecture needed for matching the specifications done previously. You will have to integrate also environment constraints (company) to define them. Once the target architecture is defined the coding of each functionality can be done. The use of design patterns is useful if you plan to use several developers on the same part of the program. This phase includes also unit testing for the validation of each piece of code produced by the development team.

### Integrations and Tests
The test phase is important, because it allows the programmer(s) to verify if each brick developed for the project works well with the others, and thus, provides the expected result software. It is not possible to deliver quality software without testing it; there is always an issue, or worse a bug (yes it happens). Tests can be automated by the use of a Continuous Integration tool (like TFS DevOps).

### Validation by user(s)
The users have to validate the final product. It is an important step, but underestimated by most big companies (because of the architecture of their development structure). It is important that the general feelings of the final user match the expectations set during the specifications phase. This validation also improves the perception of quality of the final software for the users.

### Release and deployment
During this phase the software is already produced (at least an executable is available) but the development of the project is not yet finished. In many cases, especially for desktop applications, the final software has to be integrated into a setup/install package that will allow smooth distribution to users. This is a crucial step in a multiplatform project (because of the specifics of each OS regarding the software installation process).

Each iteration in the cycle aims to fix bugs, integrate new features or changes in the specifications, improve performances. In this context, this cycle iterates throughout the life of the software.

## 3.3 DEFINE MULTIPLE ENVIRONMENTS

It is important during a project to separate developments into several environments. It helps the developer to maintain coherence and continuity between the different bricks he should develop to achieve his goals, without conflict with other developed parts of the project.

These environments correspond to a computer (or a virtual machine) or simply to a repository (or a folder) for storing the data needed during development (such as documentation, database scripts, specifications...).

A dedicated Wiki (website) for each environment could often be pertinent. The use of a Wiki aims to keep a knowledge base for each element or specific technique used during development. The Wiki website is especially useful for projects with a small team or with remote human resources.

Besides the knowledge base regarding development, the project, during its evolution, will need several distinct environments to fulfill the requirements of each phase.

The usual habit in that domain is to define 3 environments:

- Development: In this environment the developer can create side projects for validating complex parts of the project. It is an informal environment dedicated to coders and only to them.

- Test: In this environment the developers will release the project for validation; usually this environment should be the same as the Release environment. Here bugs are identified, performances are evaluated, and points for review go back to development.

- Release: This environment is the one where the software should run in production. In our case, desktop/laptop computers with no previous specific installation done (that can interfere with the developed software). The Release environment will allow validation of both the Install/setup module and the software itself.

For multiplatform development needs, there will be 3 (Development, Test and Release) environments on the main development platform (the Windows station), and 2 (only Test and Release) on Ubuntu and macOS.

## 3.4 SOURCE CONTROL

Another important aspect to consider before starting development is to integrate tools for source code management. The source code of your project is the main achievement of hard coding work and should be considered precious.

In this context, the use of a source control tool is mandatory for professional development (for personal work as well); this tool will be especially useful for:

- Avoid losing source code.
- Avoid releasing faulty code.
- Keep versioning.
- Allow code analysis.

You can implement source control tools on your servers (many open source solutions are available such as Git, SVN, Subversion...). We recommend installing the source code repository on a dedicated computer other than a developer station, where possible.

But you can also use online integrated solutions such as Microsoft Azure DevOps, GitHub, or others... Using an external repository improves the security of your source code. By using remote source code, you can recover very quickly in case of general failure or catastrophic event.

Here is a quick review of the mainstream solutions for integrating these benefits into your project development.

### A) Microsoft Azure DevOps

Using Microsoft Azure DevOps includes many advantages in addition to the source control tool. This environment is furnished freely (up to 5 users, after which you must subscribe to services offering much more capabilities) by Microsoft. It can be used to manage your project cycles and serve as the central repository for your source code; it includes:

- Source versioning.
- Project tracking (can be connected to MS Project).
- Assign tasks to developers.
- Request management (new features, bugs, specs...).
- Compilation of your project.
- Integration of automated build and testing modules (with pipelines).

Azure DevOps offers, for free, different types of source control tools, such as classic TFS and Git, and different methodologies for guiding your project (Agile, Scrum...).

In the complete version (with subscription), Azure DevOps offers a complete solution for managing your resources and source code professionally.

Integration with Visual Studio is native and makes it much easier for developers to use software development methodologies across the architecture and coding phases.

This is only a glimpse of the features freely offered by Azure DevOps, so we recommend using this tool; you can discover all the details of the offer from the reference link.

### B) GitHub

GitHub offers a free distributed source control tool. GitHub comes from the open source world and offers to host your project sources for free. These sources will be accessible to the “public,” and an unlimited number of “contributors” can participate in the project (ideal for open source projects).

If you do not want your sources to be public, you can create a “private” repository, but this one (at least in the free version) will have to support constraints such as the number of contributors limited to 3 (and others).

By default, the repository will be accessible to the public if you only use the free version, but GitHub allows you to work with no limit on team size.
