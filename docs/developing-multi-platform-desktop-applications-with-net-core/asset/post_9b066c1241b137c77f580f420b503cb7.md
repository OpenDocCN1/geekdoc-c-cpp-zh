
As the company is specialized in the setup making area, Bitrock's customer support can also provide precious help and advice for the development of your multiplatform setup program.

Added to its well-thought user interface, this product used an XML file format for the scripting of the install process for each platform, allowing to reuse code snippet(s) from the InstallBuilder user's community and support team.

Here is a sample snippet of the scripting language used in InstallBuilder.

```
<folder>
    <description>OS X Files and scripts</description>
    <destination>${installdir}</destination>
    <name>osxfiles</name>
    <platforms>osx</platforms>
    <distributionFileList>
        <distributionFile>
            <origin>/path/to/osx.pkg.gz</origin>
        </distributionFile>
        <distributionFile>
            <origin>/path/to/osx-script.sh</origin>
        </distributionFile>
    </distributionFileList>
</folder>
<folder>
    <description>Windows Files and scripts</description>
    <destination>${installdir}</destination>
    <name>windowsfiles</name>
    <platforms>windows</platforms>
    <distributionFileList>
        <distributionFile>
            <origin>/path/to/windows.zip</origin>
        </distributionFile>
        <distributionFile>
            <origin>/path/to/windows-script.bat</origin>
        </distributionFile>
    </distributionFileList>
</folder>
```

This script snippet targets macOS and Windows systems for the install.

### 11.3 RECOMMENDATIONS FOR THE PACKAGING AND THE DEPLOYMENT TOOLS OF YOUR APPLICATION

The packaging is a crucial point for a smooth and harmonious deployment of your .NET Core 3 application. The packaging of your application will depend on:

- The type of release you want to distribute: CLR, single EXE or machine native.
- The type of dependencies your application relies on: GTK, QT, ... (and you have to include in your installer)
- The platforms you want to target.
- The context of the deployment: is your software a commercial application? a shareware? or a tool that has to be deployed only on the computers of your company?
- The features you want to include in the package (MultiLingual, autoUpdate, License protection, ...).

This list is not exhaustive, as many projects have their own constraints.

The complexity inherent to the choice of a setup tool for multiplatform application is a great deal for every developer (or team) and should not be disregarded during the installer making task of the project.

In many software development projects, especially in the multiplatform environment, this phase is underestimated and produces tools that do not flatter the application installed.

We can recommend that the development team work as soon as possible in the SDLC (software development life cycle) on the installer program they plan to use for their application distribution and deployment.

As they are separate projects, the installer coding (yes, the setup program is a project by itself) can be done simultaneously during the project coding phase. This way of doing allows to validate if the tool(s) chosen match the requirements for the installation of the software developed (setup of the dependencies, checking configuration, environment ...). In a professional context, a dedicated resource could be dedicated to this task in an exclusive manner.

The use of freely available tools on each platform will benefit applications packaged under the native format. The user will have a complete solution adopting his familiar OS interface (for the installer and the application). But this solution introduces the use of several distinct development tools, one for each OS and multiplies the Installer project as much as the number of OS targeted.

On the other hand, the use of a tool (InstallBuilder) for centralizing every project (one for each OS targeted) can provide better coherence to the project itself and ease the management of this one. Nevertheless, this solution implies investing a not negligible budget for this specific task.

But most of all, do not underestimate the value of a proficient setup program; do not forget that the program will be the user's first contact with the application, which can induce a positive or negative perception of the application.

You have to be sure that the effect your installer solution will provide to the user will be in sync with the targeted experience you want to bring to the user with the use of your software.

## Chapter 12. PERSPECTIVES FOR THE SOLUTIONS REVIEWED

As we have seen along this book, the multiplatform development capabilities offered by the third version of the .NET Core are simply amazing. Even if .NET Core 3 does not provide any multiplatform desktop GUI API, the existing tools already available for developers can respond today to each and every requirement for its project.

The well-thought architecture of this new framework brings enough flexibility for addressing any kind of developer's application needs.

The multiplatform development area, since long reserved to a few highly technical people, is now accessible to the C# developer community.

The ability of .NET Core 3 to produce native executables (with CoreRT) for each platform (Windows, Linux, macOS) provides at the same time the capability to use executable compression and optimization tools, dedicated since a long time to a developer elite.

The latest coding techniques reviewed previously along this book are the perfect illustration of the abundance of innovative solutions that can be used with .NET Core 3.

Each technology presented has its own development history and origin that will predetermine, in part, its usage and maintainability in the future.

Terminal.GUI could be used in many cases for providing a user-friendly experience in place of a console application (not really user-friendly, especially for prime users). You can also consider using it for the development of containerized application services (continuously running in a dedicated environment) where it can provide secure monitoring capabilities directly from the container where it is executed (in this case you should have access to the container).

Electron.NET is a wrapper around Electron. Electron is a Google-promoted tool for expanding the field of application for its Node.JS development environment and community. It is not sure that Google will continue to maintain a tool for its use with the .NET Core. The current stability among each version of this product is neither very good. So, it would not be a surprise if the Electron.NET wrapper will not support future releases of .NET Core. Indeed, developers who choose this solution could have to choose between a complete Node.JS solution development (complete Electron) or the use of .NET Core. But these are speculations; we are not there yet.

LibUI is a quite discreet (not so trendy) GUI toolkit (mostly known by C++ users) but it provides great performance, small dependency size, and the community around this tool is still quite active. On the other hand, the implementation of the interface has to be done manually (by code), reserving the use of this tool for a category of developers only. The general quality of the wrapper could also be improved in future versions. The wrapper uses .NET Standard, thus it will be usable in future versions of .NET Core anyway.

The GTK toolkit has a quite long development history, and even if some periods of development are very quiet (stable), the GTK community keeps it still alive and kicking. The number of deployed applications in production will guarantee (at least for some time) the continuity of the product's evolution. Moreover, the GTK# wrapper is implemented using .NET Standard, so it will be usable by future releases of .NET Core.

The QT framework has a large community, and since 2014 a company guarantees its continuous development in the future.
