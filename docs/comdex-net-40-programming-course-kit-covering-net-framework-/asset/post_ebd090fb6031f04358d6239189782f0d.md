## Describing Output Caching

Output caching, also known as page level caching, is the simplest technique of caching in ASP.NET. In output caching, if a client requests a Web page for the first time, the requested Web page is accessed from the Web server and sent to the client; and a copy of that requested Web page is stored in cache. Now, if the same Web page is requested again by the client, then it is accessed from cache, instead of being accessed from the Web server. In case if a copy of the Web page is not found in cache, the Web page is accessed from the Web server and a copy of the Web page is stored in the cache memory for later use.

Output caching is also very useful when you have static pages (whose content does not change). This is because the engine, also known as cache server, caches the data which is rendered (or displayed) on the Web page. This engine acts as a server that stores Web pages and other Internet content locally. At subsequent request for a Web page, the engine retrieves a copy of the Web page from the cache itself, instead of retrieving it from the Web server. This reduces the load on the Web server.

You can easily implement output caching by just adding the @ OutputCache directive at the top of a Web page, as shown in the following code snippet:

```aspx
<%@ OutputCache Duration="10" VaryByParam="none" %>
```

You can also define the location, client-side, server-side, or proxy server, where you want to cache the data by including the location attribute in the @ OutputCache directive, as shown in the following code snippet:

```aspx
<%@ OutputCache Duration="90" Location="Any | Client | Downstream | Server | None" VaryByParam="none" %>
```

Other than the Location attribute, the @ OutputCache directive also contains some more attributes. All the attributes supported by the @ OutputCache directive are listed in Table 9.3:

**Table 9.3: Attributes Supported by @ OutputCache Directive**

| Attribute | Description |
|---|---|
| CacheProfile | Contains the name of the cache settings associated with a Web page; this is an optional attribute and by default, it contains an empty string. |
| Duration | Defines the time duration in seconds for the Web page or the user control that is being cached. This attribute is required. |
| Location | Defines the location where cache is created. The possible values are Any, Client, Downstream, Server, and None. |
| NoStore | Contains a Boolean value that determines whether to prevent secondary storage of sensitive information or not. |
| Shared | Sets a Boolean value that allows you to share the output of cached control with multiple pages. |
| SqlDependency | Contains a string value, which identifies a set of database and table name pairs, on which the output cache of the Web page depends. |
| VaryByControl | Contains a semicolon-separated list of strings that is used to vary the output cache. These strings represent ID of the property value of the ASP.NET server controls on a user control; if you are working with user controls and not using the **VaryByParam** attribute, then the **VaryByControl** attribute is necessary (this attribute is not supported for ASP.NET Web pages). |
| VaryByCustom | Defines custom strings for the custom output caching requirements. |
| VaryByHeader | Defines a semicolon-separated list of HTTP headers, used to vary the output cache. |
| VaryByParam | Defines a semicolon-separated list of strings, used to vary the output cache. This attribute is required. |
| VaryByContentEncodings | Defines a semicolon-separated list of strings used to vary the output cache. This attribute is used by the Accept-Encoding header to determine how cached responses are served for different content encodings (changing the format of the content to some other format). |

Now, let’s discuss some important attributes of the **@ OutputCache** directive in detail.

### The Location Attribute

The **Location** attribute is used to define the location where the item needs to be cached. It can be on the server side or on the client side or can even be on the proxy server. The **Location** attribute takes its values from the **OutputCacheLocation** enumeration. All the possible values of the **OutputCacheLocation** enumeration are listed in Table 9.4:

**Table 9.4: Possible Values for the OutputCacheLocation Enumeration**

| Value | Description |
|---|---|
| Any | Specifies that the output cache can be stored anywhere, such as on the client browser, proxy server, or Web server itself |
| Client | Specifies that the output cache is only located on the client browser |
| Downstream | Specifies that the output cache can be stored in any of the HTTP 1.1 cache-capable devices, other than the originating server, which can be a proxy server or the client that made the request |
| None | Disables the output cache of the requested page |
| Server | Specifies that the output cache is only located on the Web server |
| ServerAndClient | Specifies that the output cache is stored on the Web server as well as on the client browser |

The Location attribute does not support the @ OutputCache directive included in the user controls (.ascx files). Therefore, this attribute can be used only for Web pages.

### The Shared Attribute

The **Shared** attribute allows you to share the output of cached control with multiple pages. It contains a Boolean value, which is either **True** or **False**. Table 9.5 lists a detailed description of these values:

| Value | Description |
|---|---|
| False | Allows the caching engine to keep separate copies of user controls, even if they are used on multiple pages. No sharing of cache is allowed between multiple pages. This is the default value of the **Shared** attribute in the `@ OutputCache` directive. |
| True | Allows multiple pages of a Web site to access cached user controls. By setting the value to **True**, the caching engine saves a single copy of the user controls and makes it accessible for multiple pages of a Web site. This technique saves a large amount of memory. |

### The VaryByCustom Attribute

The **VaryByCustom** attribute is used to define custom strings to manage customized caching requirements. For example, if **browser** is specified as the value of this attribute, the caching engine saves multiple copies of data, depending on the type of browser. This is very useful when you want to cache different content for different browsers, such as IE-optimized HTML pages for Internet Explorer 7 (IE7), and Mozilla-optimized pages for Mozilla Firefox.

You can also implement a custom logic to store different copies of data based on the conditions defined in custom logic. If you are planning to implement a custom logic, then you must override the **HttpApplication.GetVaryByCustomString** method in the **Global.asax** file of your Web site, as shown in the following code snippet:

```aspx
<script runat="server">
public override string GetVaryByCustomString(HttpContext context, string arg)
{
    //your own custom logic;
    //INSTANT C# NOTE: Inserted the following 'return' since all code paths must return a
    //value in C#:
    return null;
}
</script>
```

### The VaryByParam Attribute

The **VaryByParam** attribute is used to cache different copies of a page, when the page is generated dynamically, based on the parameters received in the Uniform Resource Locator (URL).

Let’s consider an example to understand the use of **VaryByParam** attribute. Suppose, you have an ASP.NET Web page that generates personal records of an employee based on the parameter named **EmployeeID**, which is received through a query string. Now, imagine a situation where a user requests for the personal records of an employee with the **EmployeeID** parameter as 14 and with the **VaryByParam** attribute set to its default value: **None**. In this case, the Web page is rendered and its output is cached. However, suppose that another user requests for the records of the employee with the **EmployeeID** parameter 25. In this case, the caching engine is unable to differentiate between the two requests and sends the cached output for the **EmployeeID** parameter 14 to the user.

To overcome this problem, you can use the **VaryByParam** attribute and specify that the caching engine should vary its cache on the **EmployeeID** parameter by specifying **VaryByParam** as **EmployeeID**. You can also define more than one parameter names in the **VaryByParam** attribute. The caching process then checks and keeps different copies of the Web page for each parameter defined in the **VaryByParam** attribute.
