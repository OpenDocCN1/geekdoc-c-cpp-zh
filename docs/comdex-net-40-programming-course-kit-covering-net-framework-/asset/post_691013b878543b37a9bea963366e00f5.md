The components of WF architecture, as shown in Fig.VB-6.1, are as follows:

Let’s discuss each of these components, one by one.

## Workflow

A workflow is a declarative program wherein each program statement is represented in terms of a component called **activity**. In other words, a workflow defines the business logic on which a program is based. Workflows that are created to automate interactions among applications are known as **system workflows**. Such workflows are relatively static, which means that they follow a predefined structure. In contrast to system workflows, there are workflows that allow a user to interact with that particular application. It means that the user can provide input or generate the output. Such workflows are known as **human workflows**. Applications that involve human interactions generally need more flexibility than others, because people may change their minds, introduce new ideas and exceptions, and cancel a process unexpectedly.

In .NET Framework 4.0, you can create the following two types of workflows:

- The Flowchart workflow
- The Procedural workflow

Let’s discuss these two types of workflows, one by one.

### The Flowchart Workflow

A flowchart workflow helps you to create workflows by using common flowchart elements. A flowchart is a common standard to design programs. It allows you to create flexible workflows in which you can navigate back to previous steps as well as skip steps based on conditions within the workflow. In WF, the **Flowchart** activity is generally used to implement a non-sequential workflow. However, it can also be implemented as a sequential workflow provided that you are not using **FlowDecision** nodes.

![](img/9862a98a1a2d3bb14334137965a1ec60_229_0.png)

**The FlowDecision node is a node that decides the sequence of a workflow according to the specified conditions and accordingly transfers the control to the particular nodes.**

The Flowchart activity contains a collection of flow nodes that are inherited from the FlowNode class. The following types of nodes or elements can be a part of a flowchart:

- **FlowStep:** Shows one step of execution in the flowchart
- **FlowDecision:** Shows the execution on the basis of a Boolean condition. It is similar to the **If** construct
- **FlowSwitch:** Shows the execution on the basis of an exclusive switch. It is similar to the **Switch** construct

Next, let’s discuss about the procedural workflows.

### The Procedural Workflow

A procedural workflow helps you to create workflows by using basic and sequential execution standards. In WF, procedural workflows use flow control constructs, such as **If, While, ForEach,** and **Switch**. These flow control constructs are similar to branching statements that are found in procedural languages. Procedural workflows can also consist of other flow control activities, such as **Flowchart** and **Sequence**.

Next, let’s learn about the activity component in WF architecture.

## Activity

In WF, an activity is the basic unit of composition and execution of a workflow. In other words, an activity represents a unit of work in WF. Each activity in a workflow consists of its own variables and arguments and is a subclass of the Activity class. The variables in an activity are used to store the data in an activity while the arguments in an activity are used to move data in and out of an activity.

Workflows in WF can be created by implementing the abstract class, **CodeActivity**, for basic activity functionality, such as implementing control flow, conditions, event handling, and state management. In addition, the abstract class, **NativeActivity**, can be implemented to develop custom activities for basic activity functionality that implement specific behavior.

Next, let’s learn about the built-in activity library component in the WF architecture.

## Built-In Activity Library

The built-in activity library is a collection of activities that are used to create workflows. In .NET Framework 4.0, WF includes a new activity library with expanded functionality.

Table 6.1 lists the different types of activities available in the built-in activity library:

| Activity Type | Description | Examples |
|---|---|---|
| Control flow activities | Allow you to control the flow of execution within a workflow | If, ForEach, While, DoWhile, Parallel, ParallelForEach, Pick, and Switch |
| Flowchart activities | Allow you to control the execution and branching within a flowchart | FlowChart, FlowDecision, and FlowSwitch |
| Messaging activities | Enable workflows to send and receive Windows Communication Foundation (WCF) messages | Send, SendReply, Receive, and ReceiveReply |
| Runtime activities | Allow you to access workflow runtime features, such as persistence and termination | Persist and TerminateWorkflow |
| Primitives activities | Allow you to perform some common tasks, such as assigning a value to a variable and writing a line of text to the console | Assign, Delay, InvokeMethod, and WriteLine |
| Transaction activities | Allow you to model transactions, compensation, and cancellation | CancellationScope, CompensableActivity, Compensate, Confirm, TransactionScope, and TransactedReceiveScope |
| Collection activities | Allow you to work with collection objects in a workflow | AddToCollection, ClearCollection, ExistsInCollection, and RemoveFromCollection |
| Error handling activities | Allow you to implement error handling and recovery | Rethrow, Throw, and TryCatch |
| Migration activity | Allows you to migrate workflows created in previous versions of WF | Interop |

## Host Process

A host process is an executable program that hosts a workflow. It may be a Windows application, a Web application, or a Web service application. A host process interacts with a workflow by using the WorkflowInvoker class and invokes the workflow as a method. The workflow is stored and run within the host process. You can use Web services in the host process or remoting to enable other applications to communicate with the workflow.

## Runtime Engine

A runtime engine is not a separate service or process; it runs within the host process and is responsible for executing each workflow instance. A host process can have multiple runtime engines running concurrently and each engine can execute multiple workflow instances simultaneously.

## Runtime Services

Runtime services consist of predefined and user-defined classes that are available to the workflow runtime engine during execution of the workflow. The following are the important runtime services provided by WF:

- **Persistence services:** Enable you to save the state of a workflow for later use. You can restart the workflow according to your requirements, even after weeks of inactivity.
- **Transaction services:** Provide the transaction support needed for data integrity.
- **Scheduling services:** Allow you to control the number of available threads, their execution time, and the order in which they execute.
- **Tracking services:** Enable you to monitor the state of the workflows. This is particularly useful when multiple workflows are active at the same time (for example, in a shopping cart application).
- **Timer service:** Manages the timing required by the `DelayActivity` activity.
