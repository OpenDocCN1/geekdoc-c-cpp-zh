
## Using the Bin Directory

The code for a specific functionality in a Web page of a Web application can be made accessible to all the Web pages by storing the code file in the bin directory. Since the introduction of the first version of ASP.NET, the bin directory is used for sharing the code. The bin directory is similar to the App_Code directory except that it stores the precompiled assemblies of the code files that are required by all the Web pages of a Web application. You can use this method when you need to reuse the code written in other Web applications. In this case, you need to include the executable or the Dynamic Link Library (DLL) file in the bin directory.

## Using the Global Assembly Cache

You can use the global assembly cache to implement a specific functionality to all the Web pages of a Web application. .NET framework provides various assemblies that are stored in the global assembly cache. These assemblies can be accessed by all the Web pages of the Web application. You need to write the following code in the web.config file of a Web application to register or add the required assemblies in the global assembly cache:

```xml
<configuration>
    <system.web>
        <compilation>
            <assemblies>
                <add assembly="System.Data, Version=1.0.2411.0,
                    Culture=neutral,
                    PublicKeyToken=b77a5c561934e089"/>
            </assemblies>
        </compilation>
    </system.web>
</configuration>
```

## Compiling an ASP.NET 4.0 Web Application

ASP.NET first compiles code into one or more assemblies that are nothing but the files with the extension .dll. You can select multiple languages, such as VB and C#, to write ASP.NET code. When the code is compiled, it is converted into a language-independent and CPU-independent language called Microsoft Intermediate Language (MSIL). Compilation enhances performance, security, and interoperability of a Web application. At runtime, MSIL is translated into CPU-specific instructions, which are specific to the processors of computers running the applications. The advantages of compilation in ASP.NET 4.0 are as follows:

- Improves performance as the compiled code does not require additional parsing.
- Provides stability as during compilation, the code is checked for any type of syntax errors, type safety, or any other problem.
- Provides interoperability as the MSIL code supports any type of .NET language. This implies that in an ASP.NET page created in C#, you can add reference of .dll file, which is created using Visual Basic.

The compilation architecture of ASP.NET 4.0 includes numerous features, which are as follows:

- Multiple language support
- Automatic compilation
- Flexible deployment
- Extensible build system

## Multiple Language Support

Multiple language support specifies that you can use different languages, such as C#, and VB.Net, in a single ASP.NET application. This helps the developers to build Web sites in multiple languages. The code written in one language can interact with the code written in another language. In an ASP.NET 4.0 application, multiple assemblies are created, where each assembly supports each language used in the application. You can specify a subfolder in the App_Code folder for each language.

## Automatic Compilation

Automatic compilation refers that the ASP.NET application and any dependent resource are automatically compiled by the Common Language Runtime (CLR) environment. This compilation is carried out at the first instance when a user requests a resource from the Web site. As a rule, an ASP.NET application creates an assembly for each application directory and one for the main directory.

## Flexible Deployment

Flexible deployment specifies that in case of deploying your ASP.NET application, you can just copy the source code of the application to the Web server. There are two precompilation options provided by ASP.NET. First, you can compile the Web site before deploying it and second, you can compile it after it has been deployed. The ASP.NET Merge tool (Aspnet_merge.exe) enables you to combine and manage assemblies that are created by the ASP.NET Compilation tool (Aspnet_compiler.exe). This tool enables you to compile an ASP.NET Web application for deployment to a target location, such as a production server. The ASP.NET Merge tool works on assemblies that have been created by using ASP.NET version 2.0 or advanced versions. It creates one assembly for either each content folder in the target Web site or content file. It also gives you additional flexibility for deployment. The Merge tool enables you to do the following tasks:

- Creates an assembly for the entire Web site
- Creates an assembly for each Web site folder and adds a prefix to the assembly name
- Creates a single assembly for the Web site UI elements, such as pages and controls

The syntax for using the Merge tool is as follows:

```
aspnet_merge    [-?]
                applicationPath
                [-keyfile filename [-design]]
                [-o assemblyname | -w assemblyname | -prefix prefix]
                [-copyattrs [assemblyfile]]
                [-debug]
                [-nologo]
                [-errorstack]
                [-r]
                [-xmldocs]
                [-a]
                [-logfile logfile]
                [-allowattrs textfile]
```

## Extensible Build System

Extensible build system refers to the customization of ASP.NET build system to compile custom resources. The BuildProvider class is used by ASP.NET applications to build .aspx pages (ASP.NET Web pages), .ascx files (Web User control file), and global resources. You can extend and customize the ASP.NET build system to compile custom resources by creating classes that inherit from the BuildProvider class. For example, you can add a new file type and then write a BuildProvider that builds that particular type.

## Understanding Dynamic Compilation in ASP.NET 4.0

When you create an ASP.NET page, the entire content of the page is compiled into a class, which is an instance of the System.Web.UI.Page class. When a user requests for the page, the ASP.NET framework first searches for the .NET class to execute it. If the class is not located, then it can be compiled into a new .NET class, which is stored in a temporary ASP.NET folder.

If a request is sent to the same page again, then the page is not compiled again and the .NET class, which has already been compiled, is executed. This process of not compiling the same page again is called ASP.NET dynamic compilation. If any modification is done in the ASP.NET page, the .NET class is delegated automatically. In other words, dynamic compilation helps in modifying the source code and recompiling the files, without compiling the code, before deploying a Web application.

The following topics help you to familiarize with dynamic compilation in ASP.NET 4.0:

- Compiling on first request
- Recompiling on change
- Compilation dependencies
- Compilation output
- Multiple language support
- Optimizing dynamic compilation
- Disadvantages of dynamic compilation

### Compiling on First Request

In ASP.NET, Web pages and code files are compiled dynamically, by default, when users first request a resource. A resource can be an ASP.NET page (.aspx file), which the user requests from a Web site. ASP.NET supports the dynamic compilation of ASP.NET pages (.aspx files), ASP.NET Web services (.asmx files), ASP.NET HTTP handlers (.ashx files), and ASP.NET application files (Global.asax), as well as other files, such as source code and class files.

### Recompiling on Change

If you make any changes to a dynamically compiled ASP.NET file, it automatically invalidates the file's cached compiled assembly and triggers recompilation of all the affected resources, such as .dll files. Now, when the request to the application is made again, ASP.NET recognizes that the code has been changed and recompiles the affected resources of the Web application. This process enables you to quickly develop applications with a minimum of compilation overhead. The decision to compile a single page or the entire Web site depends on the percentage of changes made to resources.

### Compiling Dependencies

ASP.NET compiles files in a particular order when a request is made to an application. The items to be compiled first are referred as the top-level items. After the first request, the top-level items are recompiled only if the dependency changes. Top-level items include the App_GlobalResources folder, App_WebResources folder, profile properties, App_Code folder, and Global.asax file. After compiling the top-level items, ASP.NET compiles additional items. These items include the App_LocalResources folder, individual ASP.NET pages (.aspx files), ASP.NET user controls (.ascx files), ASP.NET HTTP Handlers (.ashx files), ASP.NET HTTP modules (.asmx files), themes, master pages, and other source files.

### Compiling Output

After the code is compiled, the generated assemblies are cached in a folder on the server. This folder is the default Temporary ASP.NET Files folder, which is the subdirectory of the location where you have installed the .NET framework. For example, if you have installed the .NET framework 4.0 in the C:\ drive of your computer, the location of the Temporary ASP.NET Files folder is as follows:

```
C:\Windows\Microsoft.NET\Framework\v4.0.30319\Temporary ASP.NET Files
```

The Temporary ASP.NET Files folder is created, by default, when you install .NET framework. A separate subfolder is also created for each ASP.NET application in the Temporary ASP.NET Files folder. The root location of this subfolder can be configured in an ASP.NET application by using the tempDirectory attribute of the compilation section of the configuration file.
