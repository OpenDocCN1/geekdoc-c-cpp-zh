## Derived Class Functionality

- We've seen how inheritance allows reuse of existing code to hold information about each class of object.
- But derived classes of a base class not only inherit data attributes (name, ss#, etc), but also inherit the behavior of the base class, the operations or functionality of the base class.
- In fact, derived classes may also add new functionality or behavior, or even override or redefine existing behavior.

### Message Interpretation

- One of the most important characteristics of OO programming is that:
  - The interpretation of a message is in the hands of the object.
  - i.e., The same message can be interpreted in different ways by different receivers (objects).

## Polymorphism

Polymorphism is the ability of two or more classes of objects to respond to the same message, each in its own way.

This means that an object does not need to know to whom it is sending a message. It just needs to know that many different kinds of objects have been defined to respond to that particular message.

Different objects respond in object-specific manner to the same general message.

![](img/7f36c52b5170b89b142dbb7b1ea4666b_607_0.png)

## Pseudo-Code Example

```
❖ Non-Polymorphic Code:
for each item x             // loop over all items
  if x is a car             // depending on what x is
    call stopCar            // call different function
  else if x is a bike
    call stopBike           // for each different type
  else if x is a plane      // send a specific stop
    call stopPlane          // message
```

```
❖ Polymorphic Code:
for each item x             // loop over all items
  x.stop()                  // send general message
                            // to x
```

❖ This polymorphic solution is more adaptable to change and reuse.

## Polymorphic Solution

- What is the effect on each solution of a request to handle a new type of vehicle to stop?
- In both solutions, we would provide the new vehicle with all of the operations provided by the other vehicles.
- However, in the traditional solution, we must also modify all operations on vehicles since they all contain logic similar to the previous solution.
- In every situation, a new else or case must be added.
- In a large system, this kind of activity is extremely error-prone. Chances are that we will fail to make one or more of the necessary changes.
- In the object-oriented system, the changes required are localized. We simply implement the necessary operations on vehicles without changing anything else.

### Another Example

It's interesting to analyze how polymorphism is implemented by an object-oriented language.

Consider an application where various kinds of geometric figures such as rectangles, triangles, squares, and circles are to be displayed and manipulated.

In a non object-oriented language, we might say something like this:

```
for each figure x
    if x is a rectangle
        call displayRectangle
    else if x is a triangle
        call displayTriangle
    else if x is a square
        call displaySquare
    else if x is a circle
        call displayCircle
```

## Static (Compile-Time) Binding

- Because the association between x and each figure-specific procedure must be made at compile time, the coupling between the two is known as early binding or static binding.
- In a similar fashion, we could define operations to move a given figure or compute its area.
- These procedures would share the same style logic as the display operation shown above.

## Dynamic (Run-Time) Binding

- In an object-oriented language, this is not necessarily the case.
- Messages can be thought of as late-bound procedure calls, where the actual method or procedure to be invoked is not determined until the message is actually sent to a specific receiver.
