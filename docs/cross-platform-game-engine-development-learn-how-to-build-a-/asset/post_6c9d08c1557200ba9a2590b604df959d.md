## Tile Map Asset

Tile maps are highly common in 2D games. They consist of constructing the game world using regular-shaped images called tiles. Some popular games like Super Mario, Pacman or even Zelda use this technique to build their levels. Tile maps can also be mapped to a logical grid in addition to performance improvements, and can be used in many ways within the game logic (e.g., handling collisions, implementing AI) or to construct a level editor. [20]

![](img/2763810ed0a1572c2bec59ee52dd75be_113_0.png)

Figure 27 Tile Map

The most effective and most used way to store a set of tiles is through tile sets. It is literally all the tiles you need put together in a single light image file. When it's time to draw a tile, on the screen, only a small part of the larger image is used. Below is the tile set used to create the scene above.

![](img/2763810ed0a1572c2bec59ee52dd75be_114_0.png)

Figure 28 Tile set

The tile map in our game engine will be composed of multiple entities with a tile component attached to them. It gives us the ability to add more components to tile to achieve more advanced game effects. For example, we can choose to only add a collider component to some tiles to handle collisions only on those tiles. It will reduce the number of collision tests that have to be conducted, and it will result in a better performance for the end product.

Note: I always use "struct" instead of "class" because I just like structures. They remind me of C. Feel free to use the classes if you want. The only difference is that the member variables and functions defined by a structure are public by default.

## Asset Registry

Now that we've defined all our asset types, we'll need to create an asset registry to keep track of all of the assets we add to the game engine. Next is a code snippet that shows how the asset registry is defined.

The get() function is used to retrieve a specific asset from the registry using its asset_id and its type. All assets are stored in the member variable _data, which is a map of std::vector of asset pointers.

To retrieve an asset, we first check if there is an array for that specific asset's type available. We do that by checking if the typeid of asset is available on the map. If there is no array available, we simply return NULL. But if the array is found, we will proceed to search for the asset with the id passed as an argument. The next function is get_id(), which takes the name of the asset as an argument and its type name as a template parameter. This function will search for the asset and return its asset_id.

We also want to have the ability to add assets to our registry because some assets, like the tile map, and the animation, are not initially loaded from a source file, like textures, fonts, and audios. That's why we have the add() function.

If you take a closer look at all the asset types we have defined, you will see that they all have a default constructor. It's to make sure that the add() function can create a default version of that asset.

engine/src/assets/registry.h
```cpp
#pragma once
#include "font.h"
#include "audio.h"
#include "tilemap.h"
#include "texture.h"
#include "animation.h"
#include "core/typeid.h"

namespace fuse {
struct asset_registry {
    FUSE_INLINE void clear() {
        for(auto& [_, list] : _data) {
            for(auto a : list) { FUSE_DELETE(a); }
        }
        _data.clear();
    }
    template <typename T>
    FUSE_INLINE T* get(asset_id id) {
        FUSE_STATIC_ASSERT(std::is_base_of<asset, T>::value);
        const auto type = type_id<T>();
        if(!_data.count(type)) { return NULL; }
        for(auto& asset : _data.at(type)) {
            if(asset->id == id) { return static_cast<T*>(asset); }
        }
        return NULL;
    }
    template <typename T>
    FUSE_INLINE T* get(const std::string& name) {
        asset_id id = get_id(name);
        FUSE_STATIC_ASSERT(std::is_base_of<asset, T>::value);
        const auto type = type_id<T>();
        if(!_data.count(type)) { return NULL; }
        for(auto& asset : _data.at(type)) {
            if(asset->id == id) { return static_cast<T*>(asset); }
        }
        return NULL;
    }
    template <typename T>
    FUSE_INLINE asset_id get_id(const std::string& name) {
        FUSE_STATIC_ASSERT(std::is_base_of<asset, T>::value);
        const auto type = type_id<T>();
        if (!_data.count(type)) { return INVALID_ID; }

        for (auto& asset : _data.at(type)) {
            if (!asset->name.compare(name)) { return asset->id; }
        }
        return INVALID_ID;
    }

    template <typename T>
    FUSE_INLINE T* add(const std::string& name) {
        auto asset = new T();
        asset->name = name;
        _data[type_id<T>()].push_back(asset);
        return asset;
    }

private:
    std::unordered_map<asset_typeid, std::vector<asset*>> _data;
};
}
```

To give your ecs::system access to the asset registry we just created in the scene, update your system as indicated below. This will be important later when we start adding systems like the sprite renderer and the animator, etc.

engine/src/ecs/system.h
```cpp
#pragma once
#include "entity.h"
#include "assets/registry.h"

namespace fuse::ecs {
struct system {
    FUSE_NO_INLINE virtual ~system() = default;

    FUSE_NO_INLINE void prepare(registry* rg, SDL_Renderer* rd, asset_registry* as) {
        this->rg = rg;
        this->renderer = rd;
        this->_assets = as;
    }

    template<typename T>
    FUSE_NO_INLINE auto view() {
        std::vector<entity> entities;
        for (auto& e : _registry->view<T>()) {
            entities.push_back(entity(e, _registry));
        }
        return entities;
    }

    FUSE_NO_INLINE virtual void update(float) {}
    FUSE_NO_INLINE virtual void start() {}

protected:
    SDL_Renderer* _renderer = NULL;
    asset_registry* _assets = NULL;
    registry* _registry = NULL;
};
};
```
