# Output File Format

It is important for us to have an idea of the structure of the file we will get at the end when everything is serialized because it helps us to know how to implement our serializer.

Below is a file that shows the example scene serialized from our game.

```
# list of assets
assets:
  - texture:
      id: 2234281881859053318
      name: bg
      source: assets/bg1.png
  - audio:
      id: 17441928881988725071
      name: music
      source: assets/song.mp3
#list of entities with their components
entities:
  - info_component:
      uuid: 1262126381375044817
      name: player
    transform_component:
      translate: [126. 666664, 325. 714661]
      rotation: 0
      scale: [0.150000006, 0.150000006]
  - info_component:
      uuid: 2536376052334560951
      name: background
      tag: default
    transform_component:
      translate: [-5, -5]
      rotation: 0
      scale: [1, 1]
    sprite_component:
      sprite: 2234281881859053318
      flip: 0
```

This file has two main parts: "assets" and "entities". Our focus, for now, is only on the "entities" part. As you can see, a new entity starts with a minus character ("-") followed by its components. The entityid is not serialized because it is a runtime value. Comments can be added using the router character "#". Each component is stored with its name as key and its data fields as values to the key. Each field will simply be addressed by its key just as we would access a field
