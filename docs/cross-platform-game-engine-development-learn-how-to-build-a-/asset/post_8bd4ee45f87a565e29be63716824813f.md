
## Tile Map Renderer System

The tile map system only has an update() function and as you can see it starts by getting the list of all entities with a tilemap_component, then we have a loop where all entities with a tile_component are retrieved and rendered.

In the second loop, we check if the current tile belongs to the current tile map, and we also make sure the tile set of that tile is also part of the tile map. When the test is passed, we will make sure we update the tile’s position based on the tile map’s position. We could do the same for the rotation and the scale.

The last step is to call the draw_tile() function to render the tile. The draw function will get the texture, define a src_rect based on the row and column of the tile. The src_rect is the viewport that defines which part of the tile set should be rendered.

To see the tile map grid, we use the SDL function SDL_RenderDrawRect() to render the dst_rect. There is also SDL_RenderFillRect() which renders a filled rectangle instead.

```
engine/src/ecs/systems/tilemap_renderer_system.h
#pragma once
#include "ecs/system.h"

namespace fuse::ecs {
struct tilemap_render_system: system {
    FUSE_INLINE void update(float) {
        for (auto& e : view<tilemap_component>()) {
            auto& tr = e.get_component<transform_component>();
            auto& tm = e.get_component<tilemap_component>().tilemap;

            // get tilemap asset
            auto& tilemap = _assets->get<tilemap_asset>(tm)->instance;

            // render current tilemap's tiles
            for (auto& tile_entt : view<tile_component>())
            {
                // check if tile belongs to current tilemap
                auto& tile = tile_entt.get_component<tile_component>();
                if (tile.tilemap != tm && tile.tilemap.tilesets.count(tile.tileset)) {
                    continue;
                }

                // tile position
                float x = tile.offset_x + tr.translate.x;
                float y = tile.offset_y + tr.translate.y;

                // render tile
                draw_tile(tile.tileset, x, y, tile.row, tile.col,
tilemap.tilesize, tile.flip);
            }
        }
    }

private:
    FUSE_INLINE void draw_tile(asset_id tileset_id, float x,
float y, int row, int col, int size, SDL_RendererFlip flip) {
        SDL_Rect dst_rect = {x * size, y * size, size, size};
        SDL_Rect src_rect = {row * size, col * size, size, size};
        auto& tileset = _assets->get<texture_asset>(tileset_id)->instance;
        SDL_RenderCopyExF(_renderer, tileset.data, &src_rect,
&dst_rect, 0, NULL, flip);

        // render rectangle
        SDL_RenderDrawRectF(_renderer, &dst_rect);
    }
};
}
```

## Potential Optimizations

This way of rendering tiles is efficient, but it can be optimized in many ways. Here are some possible techniques you can apply to optimize your rendering.

### Tile Batching

One solution would be to group all tiles using the same tile set and render them all together without having to always retrieve the tile set from the asset registry for each tile because having to retrieve the tile set from the asset registry for each tile is quite inefficient. We haven't implemented the start function for any system so far. We could use the start function to achieve that before entering the game-loop, but we would also be in charge of keeping track of tiles that are destroyed.

### Clipping Space

Another solution that could drastically improve the performance would be to only render tiles that are inside the screen viewport. Any object outside of the frame will not be rendered to the screen. This can be done using a camera. Creating a camera for a 2D game is easy compared to 3D games. The camera is a 2D game is just a rectangular shape that is used to tell the renderer which part of the scene to render to the screen. The following picture visualizes the concept.

![](img/2763810ed0a1572c2bec59ee52dd75be_153_0.png)

Figure 33 Clip Space

### Tile Buffering

Another solution that I think is good but not easy to implement is to render your tiles into a texture buffer and then render only one texture instead of many tiles. But this technique is more suitable for static and small tile maps because there are limitations to the size of texture buffers which can be different from system to system.

Each solution has advantages and disadvantages, but it is up to you to know what fits the most for your game. We are not going to spend time on that because this book is not about optimization techniques but rather to establishing a foundation that the reader can build upon.

## Chapter 11 Physics

### Physics

Because of advancements in computer technology, we can now use computer science to simulate real-world physics behaviors. Simulating physics is usually a close approximation of genuine physics where calculations are made using discrete values. It will happen in games that some physics laws will be deviated from for a better gameplay experience. A popular example is allowing the character to double jump without touching the ground.

Rigid bodies and soft bodies are the two most common forms of physics simulations. A rigid body simulation is less performance intensive since Soft-body physics is the process of simulating various portions of an object to make it behave more realistically. We will only implement rigid body simulation in our engine.

![](img/2763810ed0a1572c2bec59ee52dd75be_156_0.png)

There are libraries like Box2D that can be used to achieve better physics simulations in our engine. To keep things simple, we are going to implement a simple physics system to perform our physics simulations.

Box2D is a 2D rigid body simulation library for games. Programmers can use it in their games to make objects move in realistic ways and make the game world more interactive. From the game engine's point of view, a physics engine is just a system for procedural animation. Box2D is written in portable C++. Most of the types defined in the engine begin with the b2 prefix. Hopefully, this is sufficient to avoid name clashes with your game engine [1].
