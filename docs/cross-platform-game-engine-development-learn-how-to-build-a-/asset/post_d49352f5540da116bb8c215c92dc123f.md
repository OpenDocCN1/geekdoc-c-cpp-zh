### Animation

In simple terms, the animation is just rendering one image after another within a specific time interval to give the impression of motion. You are going to see how simple it is to create an animation in this game engine. The process remains the same, we create a component, then the system, and finally, we create an entity in the scene for testing.

### Animation Component

Again, you must update the code inside of the header file **graphics.h** by adding the code snippet below, which shows how the animation component is defined. This component is similar to the sprite component in that it also only takes an **asset_id** for the animation we want to play.

engine/src/ecs/components/graphics.h

```
struct animation_component {
    FUSE_INLINE animation_component(const animation_component&) = default;
    FUSE_INLINE animation_component() = default;
    SDL_RendererFlip flip = SDL_FLIP_NONE;
    asset_id animation = INVALID_ID;
};
```

### Animation System

Below is the code for the animation system. The two lines highlighted are the only ones that need an explanation because the rest is the same as in the sprite renderer system.

We are using the function macro get_ticks_ms() to get the amount of time elapsed since the initialization of SDL in milliseconds. If you remember, in the chapter about Window and Events, we mentioned the fact that our animation and motion would not be frame-based but time-based instead. This is it; we use the current time to calculate which frame of the animation must be rendered to the screen. The modulo “%” in the formula is to make sure we never get a frame index above the frame count of the current animation.

If you look at the definition of the animation, you will notice that it has an array of asset_ids. The frame index calculated is used to retrieve the asset_id of the frame we want to render from that array. The retrieved asset_id is then used to get the texture asset from the asset registry.

We are going to use the following frames to test the animation system. Feel free to use any free asset you find online. Sorry am not a graphic artist*.

engine/src/ecs/systems/frame_animation_system.h

```
#pragma once
#include "ecs/system.h"

namespace fuse::ecs {
struct frame_animation_system : system {
    FUSE_INLINE void update(float) {
        for (auto& e : view<animation_component>()) {
            // get components
            auto& tr = e.get_component<transform_component>();
            auto& an = e.get_component<animation_component>();

            // get animation from asset registry
            auto& anim = _assets->get<animation_asset>(an.animation)->instance;

            // compute current frame
            int index = (get_ticks_ms() / anim.speed) %
            anim.frames.size();
            auto& frame = _assets->get<texture_asset>(anim.frames[index])->instance;

            // define target viewport
            SDL_FRect dst {
                tr.translate.x, tr.translate.y,
                frame.width * tr.scale.x, frame.height * tr.scale.y
            };

            // render sprite
            SDL_RenderCopyExF(_renderer, frame.data, NULL, &dst,
                tr.rotation, NULL, an.flip);
        }
    }
};
}
```

### Quick Test

Go to your scene register the system you just created and use the following code to add an entity in your scene with an animation component.
Below is a code snippet that shows how you can add an entity with an animation component to the scene. As you can see, we register the system, load all textures or frames for our animation, then we create an animation asset in the asset registry to which we add the asset_id of each frame to the list of frames, and finally, we add an entity with an animation component that takes the animation's asset_id as parameter.

- engine/src/ecs/scene.h

```
#pragma once
#include "ecs/systems/text_renderer_system.h"
#include "ecs/systems/sprite_renderer_system.h"
#include "ecs/systems/frame_animation_system.h"

namespace fuse::ecs {
struct scene {
    FUSE_INLINE scene(SDL_Renderer* rd): _renderer(rd) {
        register_systems<ecs::frame_animation_system>();
        register_systems<ecs::sprite_renderer_system>();
        register_systems<ecs::text_renderer_system>();
    }

    FUSE_INLINE void start() {
        // load animation textures
        auto f1 = _assets.load_texture("assets/f1.png", "f1", _renderer);
        auto f2 = _assets.load_texture("assets/f2.png", "f2", _renderer);
        auto f3 = _assets.load_texture("assets/f3.png", "f3", _renderer);

        // add animation asset
        auto animation = _assets.add<animation_asset>("dance");
        animation->instance.frames.push_back(f1->id);
        animation->instance.frames.push_back(f2->id);
        animation->instance.frames.push_back(f3->id);
        animation->instance.speed = 300;

        // add entity with animation component
        ecs::entity entity = add_entity("entity");
        auto& a = entity.add_component<ecs::animation_component>();
        a.animation = animation->id;

        // start systems
        for (auto& sys : _systems) { sys->start(); }
    }
};
}
```

### Tile Map Renderer

A tile-based video game is a type of game or video game where the playing area consists of small square (or, much less often, rectangular, parallelogram, or hexagonal) graphic images referred to as tiles laid out in a grid. That the screen is made of such tiles is a technical distinction and may not be obvious to people playing the game. The complete set of tiles available for use in a playing area is called a tile set. Tile-based games usually simulate a top-down, side view, or 2.5D view of the playing area, and are almost always two-dimensional.

Much video game hardware from the late 1970s through the mid-1990s had native support for displaying tiled screens with little interaction from the CPU. [24]

You can already have an idea of how we are going to implement this feature in our engine. If you remember in section (0), we spoke about the fact that each tile would be an entity with a tile component. The tile map itself is also going to be an entity with a tile map component. So, let’s create both components.

The next component we will add to the **graphics.h** header file is the **tile map component**. This component, just as the **sprite_component** or even the **animation component**, simply stores the **asset_id** of a tile map asset. There isn't much we can say about this component.

### Tile Component

The tile component needs a little bit more data compared to the tile map component. First, a tile needs to know which tile map it belongs to, Secondly, it is important for that tile to also know from which tile set its texture is coming from; it also has to know which part of that tile set to render and, finally, where it will be rendered on the screen. Since the tile set is simply a grided texture, we can simply store the row and the column of the tile. The following image gives a visual idea of the concept.

![](img/2763810ed0a1572c2bec59ee52dd75be_148_0.png)

As you can see, the counting of rows and columns starts at zero and ends at n-1. Below is the code for the tile component. Add the code to your graphics.h header file right after the tile map component.
engine/src/ecs/components/graphics.h

```
struct tile_component {
    FUSE_INLINE tile_component( const tile_component& ) = default;
    FUSE_INLINE tile_component() = default;
    SDL_RendererFlip flip = SDL_FLIP_NONE;
    asset_id tilemap = INVALID_ID;
    asset_id tileset = INVALID_ID;
    float offset_x, offset_y = 0;
    int row, col = 0;
};
```
