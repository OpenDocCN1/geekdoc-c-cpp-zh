### Sprite Renderer

You'll see how simple it is to add new features to our engine from now on.
This chapter will go through how to render textures. We will create a sprite component that takes the asset_id of a texture asset. That component will be attached to an entity and will be drawn to the screen via a sprite renderer system.
Before we get to render the texture or even create the component, we want to see how to load them from source files.

### Loading Textures

We already have an asset registry defined. So, let's add a function to load textures. Below is a code snippet that shows how a texture can be loaded to the asset registry. Make sure to update your asset registry accordingly.

```cpp
// ...
engine/src/assets/registry.h
// ...
FUSE_INLINE texture_asset* load_texture(const std::string& src,
const std::string& name, SDL_Renderer* rd) {
texture texture;
texture.data = IMG_LoadTexture(rd, src.c_str());
texture.filename = src;
if (!texture.data) {
FUSE_ERROR("%s", IMG_GetError());
return NULL;
}
SDL_QueryTexture(texture.data, NULL, NULL, &texture.width,
&texture.height);
auto asset = new texture_asset();
asset->instance = texture;
asset->name = name;
_data[type_id<texture_asset>()].push_back(asset);
return asset;
// ...
}
```

IMG_LoadTexture() is a built-in function in SDL_image that loads pixel data from files. It supports a variety of image formats, including PNG, TIFF, JPG, and JPEG. This method loads the pixel data into a memory block and returns the address to the first pixel data.

In order for us to know the size of a texture, we need to explicitly query it using the SDL_QueryTexture() function. This function takes a pointer to a texture and two integer pointers for the width and the height to store the requested size.

The load_texture() function also takes the name of the asset as an argument. This makes sure that every asset has a name that can be used to find it. Two assets can have the same name, but they will never have the same asset_id. That's why we don't have to worry about an asset being overwritten due to its name already being used.

### Sprite Component

If you remember from the ECS chapter, we said we would create our components in categories to reduce the number of inclusion statements because it has a beneficial effect on the compile time. The first category we created was found in ecs/components/common.h.

Let's now create another category in a new file called graphics.h. We will create all the components related to graphics in this file. Below is the code snippet of the sprite component.

```cpp
engine/src/ecs/components/graphics.h
#pragma once
#include "assets/asset.h"
namespace fuse::ecs {
struct sprite_component {
    FUSE_INLINE sprite_component( const sprite_component& ) = default;
    FUSE_INLINE sprite_component() = default;
    SDL_RendererFlip flip = SDL_FLIP_NONE;
    asset_id sprite = INVALID_ID;
};
}
```

This component only has an asset_id and a flag called "flip," which defines the orientation of the sprite. SDL_RendererFlip is an enumeration of flags that can be used to set the orientation of a sprite while rendering it. Here are the possible values it could take:

| SDL_FLIP_NONE | do not flip |
|---|---|
| SDL_FLIP_HORIZONTAL | flip horizontally |
| SDL_FLIP_VERTICAL | flip vertically |

Only when required will the texture associated with the asset id be fetched and utilized. This method is useful for serialization. We can serialize components that have assets without knowing the contents of the asset itself. It also paves the way for multithreading. Because, for example, while loading a scene, we may delegate the loading of assets and components to multiple threads. This will improve our engine's capacity to load scenes and assets.

It is best practice to include a default constructor and a copy constructor in all your components because you want to be able to attach the component to an object without having to write any code.

### Sprite Renderer System

Now that we can load the texture, and that we have our sprite component ready, let's create a system that will target all entities with a sprite component and render their sprites to the screen.

```cpp
engine/src/ecs/systems/sprite_renderer_system.h

#pragma once
#include "ecs/system.h"

namespace fuse::ecs {
struct sprite_renderer_system : system {
    FUSE_INLINE void update(float) {
        for (auto& e : view<sprite_component>()) {
            // get components
            auto& tr = e.get_component<transform_component>();
            auto& sp = e.get_component<sprite_component>();

            // get texture from asset registry
            auto& sprite = _assets->get<texture_asset>(sp.sprite)->instance;

            // define target viewport
            SDL_FRect dst{
                tr.translate.x, tr.translate.y,
                sprite.width * tr.scale.x, sprite.height * tr.scale.y
            };

            // render sprite
            SDL_RenderCopyExF(_renderer, sprite.data, NULL, &dst,
                tr.rotation, NULL, sp.flip);
        }
    }
};
}
```

We are retrieving the list of entities with a sprite component, and we loop through the list and render each entity's sprite. We start by getting the transform component because we want to know where and how the sprite will be rendered to the screen. We then proceed to get the sprite component, which gives us the asset_id of the sprite to render. We then retrieve the texture asset from the asset registry.

To render the sprite, we use the function SDL_RenderCopyExF(). This function takes a pointer to the target renderer as its first argument. The renderer was created alongside the window and was passed to the scene's constructor as an argument, which also passed to the system::prepare() function. The second argument is a pointer to the texture buffer. The third argument is a const pointer to an SDL_FRect, which is the source viewport of the texture. It defines which part of the texture should be copied and rendered. We are passing NULL because we want to render the entire sprite, not just a specific part of it.

The next argument, which is also related to the previous one, is the destination viewport. It defines the box or viewport in which the sprite will be rendered on the screen.

The fifth parameter is the angle or rotation of the sprite on the screen. We also have the ability to change the center of the object we are currently rendering by passing a pointer to an SDL_Point, which is just a point in 2D space that specifies the point around which the sprite should be rotated. We are passing NULL because we want to keep the SDL's default origin which is the top left corner of the sprite.

**Note:** Remember to include your component categories in `system.h` so that every system can access all the components to perform its task.

Just like that, the sprite renderer system has been added to our engine. All we must do is go into our scene, register the system, create an entity with a sprite component, and run the whole to see the result.

Below is the code that shows which part of your scene has to be updated to test the sprite renderer system we just created.

```cpp
engine/src/ecs/scene.h

#pragma once
#include "ecs/systems/sprite_renderer_system.h"
namespace fuse::ecs {
struct scene {
    FUSE_INLINE scene(SDL_Renderer* rd): _renderer(rd) {
        register_systems<ecs::sprite_renderer_system>();
    }
    // ...
    FUSE_INLINE void start() {
        // load texture asset
        auto sprite = assets::load_texture("assets/test.png",
            "test", _renderer);
        // create entity
        ecs::entity entity = add_entity("entity");
        // add sprite component
        entity.add_component<ecs::sprite_component>().sprite = sprite->id;
        // start systems
        for (auto& sys : _systems) { sys->start(); }
    }
    // ...
};
}
```

We start by registering the system in the scene's constructor. We then go on to load the texture from a file and add an entity with a sprite component in the start() function.
