When you ask the computer to find something in memory at a specific address, it will not only copy what you ask for, but it will also copy other data around what you asked for and store it all in Cache memory. So, the next time you ask for something else, the computer will just grab it from cache rather than fetch it from RAM again. The fact that data is saved inconsistently in memory drastically reduces CPU-Cache usage, resulting in a performance hit.

## Component-Oriented Design

The following picture shows how a component-oriented design is made. As you can see, each game object will have a list of components that define its behaviour. All components like Transform, Sprite, etc. will inherit an abstract class called Component.

This technique will not solve the problem of memory and CPU-cache usage of the OO design, but it takes away the virtual lookup table for virtual functions and offers the ability to have a boss that can also be a player because being a player or a boss is just a matter of components added or removed. This will perform better than OO.

## Data Oriented Design

Things start to sound right with the data-oriented design because it offers a contiguous memory layout, no virtual lookup table, and better CPU-cache usage. This design is also known as Entity-Component (EC) design. The next picture describes the most vital component of the EC design.

![](img/2763810ed0a1572c2bec59ee52dd75be_90_0.png)

### Figure 24 Data Oriented Design

Each game object is represented by a number. That number is used to know which component belongs to that entity. You can see that all components of the same type for all entities are stored together in a contiguous manner. This will have a positive impact on the CPU cache. Many game engines use this design because it offers reliable performance and maintaining it is also not difficult.

## ECS Architecture

Even though the ECS design is well-known for its high performance and ease of use in terms of maintenance, memory, and CPU cache usage, it lacks a specific implementation approach. I usually divide the approach of implementing ECS into two categories: pure ECS and hybrid or mixed ECS.

In a pure ECS, the component has no logic. Only the system holds logic to update the components. The hybrid ECS allows components to have logic to update themselves.

We are going to build a pure ECS in this book.

![](img/2763810ed0a1572c2bec59ee52dd75be_91_0.png)

What makes the ECS design different from the data-oriented design is the fact that the entity, the component, and the system are all separated. The entity is just a unique identifier (number) that stands for a specific game object in the scene. It is often a 32-bit or 64-bit unsigned integer. The component is simple structure that store all data require for the logic. The system targets all entities with a specific set of components (signature) and update their components.

### Advantage ECS:

- ECS is a user-friendly approach to multi-threading because each system can be assigned to a specific thread.
- shorter and less complicated code.
- Ease integration of scripting languages.
- Makes unit testing and mocking ease.
- New features can be easily implemented.

### Disadvantages ECS

- No standard implementation method defined.
- Difficult to implement correctly and easily abused
- Not well known by most game developers.

You can learn more about ECS here [16] and here [9]. We now have enough theoretical knowledge. So, let's implement our own custom ECS.

```cpp
#pragma once
#include "core/typeid.h"

namespace fuse::ecs {
    using entityid = size_t;
    using componentid = uint32_t;
    using signature = std::set<uint32_t>;
    using entitylist = std::set<entityid>;

    // component array interface
    struct array_instance {
        FUSE_NOLINE virtual ~array_instance() = default;
        virtual void erase(entityid) = 0;
    };

    // component array's data entry
    template<typename T> struct array_entry {
        FUSE_NOLINE array_entry(entityid e, const T& d): entity(e),
        data(d) {}
        FUSE_NOLINE operator entityid() const { return entity; }
        entityid entity = INVALID_ID;
        T data;
    };

    // component array
    template<typename T>
    struct component_array : array_instance {
        FUSE_NOLINE T& push(entityid e, const T& data) {
            if (exists(e)) { return get(e); }
            _data.push_back(array_entry(e, data));
            return _data.back().data;
        }

        FUSE_NOLINE void erase(entityid e) {
            auto it = std::find(_data.begin(), _data.end(), e);
            if (it != _data.end()) { _data.erase(it); }
        }

        FUSE_NOLINE bool exists(entityid e) {
            return std::find(_data.begin(), _data.end(), e) != _data.end();
        }

        FUSE_NOLINE T& get(entityid e) {
            FUSE_ASSERT(exists(e) && "entity out of range!");
            return (*std::find(_data.begin(), _data.end(), e)).data;
        }

        private:
            std::vector<array_entry<T>> _data;
    };
}
```

The definitions of some essential elements required for our entity component system are contained in the header file ecs.h. We want to know which and how many components belong to an entity. That is why we have the signature, which is nothing more than a set of components id. A signature will be assigned to each entity which is represented by a 64-bit unsigned integer under the name: entityid. The element is the array_entry. This template structure stores a component of type "T" and the entity it belongs to. We've defined a cast operator to entityid because, while searching for a component in the component_array, we will simply use the entityid to search for the component. This structure also represents how components will be stored in the component_array. Since we want to store our components in memory in a cache-friendly way, we must create a custom component array to store them. Each component type will have its own component array. That's why we created an interface called array_instance which for now only has a single virtual function called erase(). We then use that interface to create a template structure called component_array that takes the type of the component to store as a template parameter. If you look closely, you will see that this component array is nothing but a wrapper around the C++ std::vector container. It contains functions like push, remove, and get, just like a standard array.

engine/src/ecs/registry.h

```cpp
#pragma once

#include "ecs.h"

namespace fuse::ecs {
struct registry {
    FUSE_INLINE void clear() {
        for (auto& [_, a] : _components) { FUSE_DELETE(a); }
        _components.clear();
        _signatures.clear();
        _nextid = INVALID_ID;
    }

    FUSE_INLINE entityid add_entity() {
        entityid entity = _nextid++;
        _signatures[entity] = signature();
        return entity;
    }

    FUSE_INLINE void destroy(entityid e) {
        for (auto& [_, a] : _components) {
            a->erase(e);
        }
        _signatures.erase(e);
    }

    FUSE_INLINE bool is_alive(entityid e) {
        return _signatures.count(e);
    }

    template <typename T> FUSE_INLINE entitylist view() {
        entitylist list;
        for (auto& [entity, sig] : _signatures) {
            if (sig.count(type_id<T>())) {
                list.insert(entity); continue;
            }
        }
        return list;
    }

    template <typename T>
    FUSE_INLINE T& get_component(entityid e) {
        FUSE_ASSERT(_signatures.count(e) && "out of range!");
        return get_component_array<T>()->get(e);
    }

    template <typename T, typename... Args>
    FUSE_INLINE T& add_component(entityid e, Args&&... args) {
        FUSE_ASSERT(_signatures.count(e) && "out of range!");
        T data(std::forward<Args>(args)...);
        _signatures[e].insert(type_id<T>());
        return get_component_array<T>()->push(e, data);
    }

    template <typename T>
    FUSE_INLINE void remove_component(entityid e) {
        _signatures.at(e).erase(type_id<T>());
        get_component_array<T>()->erase(e);
    }

    template <typename T>
    FUSE_INLINE bool has_component(entityid e) {
        return _signatures.count(e) && _signatures.at(e).count(type_id<T>());
    }

    template <typename T>
    FUSE_INLINE component_array<T>* get_component_array() {
        component_id type = type_id<T>();
        if (_components.count(type)) {
            return static_cast<component_array<T>*>(_components.at(type));
        }
        auto array = new component_array<T>();
        _components[type] = array;
        return array;
    }

private:
    std::unordered_map<component_id, array_instance*> _components;
    std::unordered_map<entityid, signature> _signatures;
    entityid _next_id = INVALID_ID;
};
}
```
