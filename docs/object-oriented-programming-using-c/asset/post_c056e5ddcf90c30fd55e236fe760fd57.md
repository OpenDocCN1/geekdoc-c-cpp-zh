## Testing the GetClient method

We of course test all of the methods in our system including the GetClient() method.

One case we need to perform is to test that an exception is thrown if we try to retrieve a client that does not exist. To test this we create an new empty BookOfClients and try to retrieve a client from this – any client!

In this instance we would hope our system generates an unknown client exception. Since we have initialised our test by creating an empty book we should not be able to retrieve any clients unless we first add them.

### Feedback 1
We cannot determine if the GetClient() method has failed before we have invoked ... hence we cannot place an Assert. Fail at point A or B.

When we invoke this method an exception should be generated as our client book is empty. The try block should be terminated at this point and the catch block initiated if the code reaches point D the test has succeeded not failed. However if the code reaches point C it indicates that the expected exception was not generated and hence we can assert that the GetClient() method has failed at this point.

Below is a simple test to test the AddMoney() method...

```csharp
[TestMethod]
public void AddMoney_TestAdd10ToBalance_FinalBalShouldBe20()
{
    c.AddMoney(10);
    Assert.AreEqual(20, c.Money, "Balance after adding 10 is not as expected. Expected: 20: "+c.Money);
}
```

The above uses the Assert.AreEqual() method. If the first two parameters are equal then our code has passed the test. If they are not equal then our code has failed and the third parameter is the error message to be displayed. To be as helpful as possible the error message specified the balance we expected and the actual balance after the AddMoney() method was invoked.

In all of the tests we have written if the test method ends without failing any assertions then the test is passed.

## Testing the ToString() method

One way of implicitly testing that ALL the attributes client have been stored correctly is to test the ToString() method returns the value expected. This is a little tricky because the format of the string must match exactly including every space, punctuation symbol, and newline.

The alternative is to test the value of every property.

### Activity 2
Assuming the ToString() method of the Class is defined as below create a test method to test the value returned by the ToString() method is as expected.

```csharp
public String ToString() {
    return ("Client name:" + Name + "\nBalance:" + Balance);

```
Hint: We have already initialised client tests by creating a client with a name "Simon" and a balance of 10.

One solution to this exercise is given below.

```csharp
[TestMethod]
public void ToString_TestClientValues() {
    Assert.AreEqual("Client name: Simon\nBalance: 10", c.ToString(),
"String returned is not as expected. Expected: Client name: Simon\nBalance: 10 Actual: " + c.ToString());
}
```

Here we assume the string returned from c.ToString() is equal to the string we are expecting. This is quite tricky because the format of the string must match exactly including every space, punctuation symbol, and newline.

This test is of course implicitly testing that ALL the attributes have been stored correctly which would be particularly useful if we used to check a client has been retrieved from the book of clients correctly.

## 10.12 Test Driven Development (TDD)

While very useful for regression testing Test Driven Development (TDD) is a technique mainly associated with 'agile' development processes. The Test Driven Development approach is to

- 1) Write the tests (before writing methods).
- 2) Set up automated testing, which fails because the classes haven't been written!
- 3) Write the classes so the tests pass

## 10.13 TDD Cycles

When undertaking driven development the test will initially cause a compilation error as the method tested doesn't exist!

Creating a stub method enables the test to compile but the test will 'fail' because the actual functionality tested has not been implemented.

We implement the correct functionality of the method so that the test succeeds.

For a complex method we may have several cycles: write test, fail, implement functionality, pass, extend test, extend functionality, pass... to build up the solution.

## 10.14 Claims for TDD

Among the advantages claimed for TDD are:

- testing becomes an intrinsic part of development rather than an often hurried afterwards.
- it encourages programmers to write simple code directly addressing the requirements
- a comprehensive suite of unit tests is compiled in parallel with the code development
- a rapid cycle of "write test, write code, run test," each for a small developmental increment, increases programmer confidence and productivity.

In conventional software lifecycles if a software project is running late financial pressures often result in the software being rushed to market not having been fully tested and debugged. With Test Driven Development this is not possible as the tests are written before the system has been implemented.
