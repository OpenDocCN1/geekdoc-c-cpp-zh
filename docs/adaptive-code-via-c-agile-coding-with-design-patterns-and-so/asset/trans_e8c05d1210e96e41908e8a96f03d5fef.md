

## 使用 Mock 进行测试

并不需要太强的想象力就能意识到，通过编写 fake（伪造对象）来进行 mock 会很快变得非常繁琐。想象一下你可能编写的所有单元测试组合，以及你的 SUT（被测系统）可能需要用到的所有不同接口。这仅仅是为了支持单元测试，就要编写大量额外代码。

还有另一种方法可以模拟 `IAccountRepository`，但它需要使用外部的 mocking 框架。编写 fake 的一个优点是，你可以在不依赖任何第三方库的情况下独立编写它们。然而，如今 mocking 框架已经很普遍，而且有很多可供选择。下面的示例使用了其中最流行的一个：Moq。它的发音有多种，如 Moh-kyoo 和 Mok。

通过 NuGet，你可以在在线源中搜索 Moq 的包，从而快速添加对它的引用。Moq 的神奇之处在于，它可以为你要求模拟的任何接口创建动态代理。你将修改现有测试，用 Moq mock 代替手动编写的 fake，如清单 4-17 所示。

## 清单 4-17 像 Moq 这样的 mocking 框架可以让你非常轻松地创建 mock。

点击此处查看代码图片

```
[TestMethod]
public void AddingTransactionToAccountDelegatesToAccountInstance()
{
    // Arrange
    var account = new Account();
    var mockRepository = new Mock<IAccountRepository>();
    mockRepository.Setup(r => r.GetByName("Trading Account")).Returns(account);
    var sut = new AccountService(mockRepository.Object);

    // Act
    sut.AddTransactionToAccount("Trading Account", 200m);

    // Assert
    Assert.AreEqual(200m, account.Balance);
}
```

测试中的改动以粗体标出。现在，你不再实例化自己的 fake 存储库，而是创建一个新的 `Mock<IAccountRepository>()` 对象。这个对象非常强大，允许你在被模拟的接口上设置各种预期和行为。这个类并没有实现你的接口，因此与你的 fake 不同，它不是 `IAccountRepository` 的直接可用实例。这是因为公共语言运行时（CLR）不允许类从泛型参数继承。相反，mock 与它创建的代理实例之间是组合关系。`Object` 属性允许你访问底层被模拟的接口，在本例中，该接口被传递给了 `AccountService`。

在将 mock 提供给 SUT 之前，你需要指定它的行为方式。默认情况下，

Moq 定义的是*宽松*（loose）mock，这意味着它们的所有返回值都是默认值。任何引用类型的默认值都是 null，`Account` 类也不例外。宽松 mock 的替代方案是*严格*（strict）mock，每当遇到你尚未指定的方法调用或属性访问时，它都会抛出异常。但这两个选项都不是你所需要的，因此你必须手动设置一些预期行为。

`Mock` 实例的 `Setup` 方法非常巧妙。它接受一个 lambda 表达式，该表达式将底层被模拟类型的一个实例作为上下文参数提供。通过在该类型上调用一个方法，你实际上是在指定：当该方法以所提供的精确参数被调用时，你希望发生某件事情。你选择指定什么，取决于你的测试场景。Moq 允许你在方法调用上设置以下预期：

- 调用某个其他 lambda 表达式。
- 返回一个特定值。
- 抛出指定类型的异常。
- 验证该方法确实被调用过。

对于这个测试，你需要的是第二个选项：返回一个指定值。`Mock.Setup` 方法调用的流畅接口允许你链式调用 `Returns` 方法。这提高了可读性，并缩减了测试中本已相当庞大的 Arrange 阶段。`Returns` 方法接收你已经创建好的 `Account` 实例，至此，你就完成了对这个 mock 的预期设置。简而言之，你给了这个 mock 以下指令：

> 当针对这个 `IAccountRepository` 实例调用 `GetByName` 方法，并且提供的账户名称为“Trading Account”时，返回这个 `Account` 类的实例。

## Mock 与测试的过度指定

使用 mock 进行测试是一种常见但可能相当繁重的实践。依赖 mock 的测试很容易变得*过度指定*（over-specified）。过度指定的测试是脆弱的，但你可以通过改变断言的内容来避免这种脆弱性。问题出现在测试包含了被测系统（SUT）如何工作的内部细节时。换句话说，当一个测试了解的是 SUT 的*实现*而非其预期*行为*时，它就是过度指定的。

使用 mock 的单元测试可能确实需要知道 SUT 是如何实现的。然而，你应该始终牢记，单元测试是预期行为的规格说明，因此应避免引入针对实现细节的测试。这类细节包括对 SUT 可能依赖的其他接口的调用。如果你断言接口上的某个方法必须被调用，那么这个测试就不再绑定于某种行为，而是绑定于特定的实现了。

过度指定的测试不可取，因为它们会阻碍对所测试的生产代码进行重构。一个方法或类附带一套全部通过的单元测试，是该方法或类的实现可以被放心修改的信号：只有当代码的预期行为被破坏时，测试才会失败。过度指定的测试无法提供这种保证，因为即使预期行为保持不变，只要方法或类的实现发生变化，它们也会失败。

在使用 mock 进行测试时，有两种方法可以避免测试过度指定。第一种是只测试行为。基于状态的测试是测试预期行为的最佳示例。如果一个方法接受数据作为输入，并返回修改后的数据作为输出，那么在测试时可以将该方法视为一个黑盒。如果该方法接受输入 A、B、C，并返回输出 X、Y、Z，那么它如何得出这些答案，对测试来说并不重要。这样，该方法就可以在不破坏单元测试的情况下被重构。

第二种选择不那么吸引人，但有时是唯一的选择。你可以将单元测试及其所测试的实现视为一个原子单元：如果其中一个发生变化，另一个也必须随之变化。这相当于承认单元测试是过度指定的，并计划在将来需要重构时，将单元测试与生产实现一起丢弃。这并不像看上去那么浪费。正如你将在第二部分“编写 SOLID 代码”中看到的，SOLID 代码会产生更小、更有针对性的类，而这些类反正永远不会被修改。

## 进一步测试

你使用 TDD 方法完成一个可用的 AccountService 的首次尝试已经成功了。还有一些潜在问题需要进一步的测试来确保这个方法更加健壮。到目前为止，你只测试了*快乐路径*（Happy Path）：即代码中不会产生错误、也不会引发问题的执行路径。有几个缺口需要解决：

- 如果账户存储库是空引用怎么办？
- 如果存储库找不到该账户怎么办？
- 如果账户方法抛出异常怎么办？

你每多写一个测试，要么会发现实现中存在的缺陷（如果测试失败），要么会增加额外的信心，确信你的实现不仅对快乐路径是正确的，对错误路径也是正确的（如果测试通过）。
