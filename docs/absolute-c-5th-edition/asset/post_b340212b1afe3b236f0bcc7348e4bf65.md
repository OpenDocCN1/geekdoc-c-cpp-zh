# Efficiency of Sets Using Linked Lists

We can analyze the run-time efficiency of our data structure in terms of the fundamental set operations. Adding an item to the set always inserts a new node on the front of the list. This requires only one link on the linked list. The contains iterates through the entire set for the target, which may require examining every node in the list. When we invoke the union function for sets A and B, it iterates through both sets and adds each item into a new set. If there are n items in set A and m items in set B, this requires examining n + m items. However, there is a high cost because the add function searches through its list for any duplicates before a new item is added. This cost becomes significant as the number of items added to the set increases. Finally, the intersection function applied to sets A and B invokes the contains function of B for each item in set A. Since the contains function requires examining up to m nodes for each item in set A, then intersection requires examining at most m nodes. These are inefficient functions. A different approach to represent the set—for example, one that used hash tables instead of a linked list—could in a setIntersection function that examines at most n + m nodes. Nevertheless, our linked list implementation would probably be fine for an application that uses small sets or for an application that does not invoke the setIntersection function, and we have the benefit of relatively simple code that is easy to understand. If we needed the efficiency, we could maintain the same interface to the Set<T> class but replace our linked list implementation with something else. If we used the hash table implementation from Display 17.25, the contains function would run much more quickly. Switching to a hash table makes it more difficult to retrieve the set of items. Instead of traversing a single linked list must now iterate through the hash table array, and for each index in the array, iterate through the linked list that was not necessary in the linked list implementation of a set. So while we decreased the number of steps it takes to iterate over every item, we have increased the number of steps. If this were troublesome, you could overcome this problem with an implementation of Set<T> that used a linked list (to facilitate iteration) and a hash table (fast lookup). However, the complexity of the code is significantly increased using such an approach. You are asked to explore the hash table implementation in Programming Project 17.10.

# Pointers as Iterators

The basic idea, and in fact the prototypical model, for iterators can easily be seen in the context of linked lists. A linked list is one of the prototypical data structures, and a pointer is a prototypical example of an iterator. You can use a pointer as an iterator by moving through the linked list one node at a time starting at the head of the list and cycling through all the nodes in the list. The general outline is as follows:

```cpp
Node *iterator;
for (iterator = Head; iterator != NULL;
    iterator->Link)
do whatever you want with the node pointed to by iterator;
```

where Head is a pointer to the head node of the linked list and Link is the name of the member variable of a node that points to the next node in the list.
For example, to output the data in all the nodes in a linked list of the kind we discussed in 17.1, you could use the following:

```cpp
IntNode *iterator;
for(iterator = head; iterator != NULL;
    iterator = iterator->getData()
cout << iterator->getData());
```

The definition of IntNode is given in Display 17.4.
Note that to see if two pointers are pointing to the same node by comparing them with the equal operator, ==. A pointer is a memory address. If two variables contain the same name, then they compare as equal and to the same node. Similarly, you can use != to compare two pointers if they do not point to the same node.
