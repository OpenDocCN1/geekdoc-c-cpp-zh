One advantage of using assert is that you can turn assert invocations out. You can use assert invocations in your program to debug your program, and then turn off so that users do not get error messages that they might not understand. Doing so reduces the overhead performed by your program. To turn off all the #NDEBUG assertions in your program, add #define NDEBUG before the include directive, as follows:

#define NDEBUG

```cpp
#define NDEBUG
#include <cassert>
```

Thus, if you insert #NDEBUG in your program after it is fully debugged, assert invocations in your program will be turned off. If you change your program and debug it again, you can turn the assert-vocations back on by deleting the #NDEBUG line (or commenting it out).

Not all assertions can be easily translated into C++ Boolean expressions. Preconditions are more likely to translate easily than postconditions. Thus, the assert macro is not a cure-all for debugging your functions, but it can be very useful.

## Stubs and Drivers

Each function should be designed, coded, and tested as a separate unit from the rest of the program. When you treat each function as a separate unit, you transform one big task into a series of smaller, more manageable tasks. But how do you test a function outside the program or how it is intended? One way is to write a special program to test the unit. For example, Display 4.9 shows a program to test the unitPiece that was used in the program in Display 4.5. Programs like this one are called driver programs. These driver programs are temporary tools and can be quite minimal. They do not have fancy input routines. They do not perform all the calculations of the final program will perform. All they need do to obtain reasonable values for the function arguments in as simple way as possible—typically from the user—execute the function and show the result. A loop, as in the program in Display 4.9, will allow you to test the function on different arguments having returned to the program.

driver program

If you test each function separately, you will find many of the mistakes in your program. Moreover, you will find out which functions contain the mistakes. If you were to test only the entire program, you would probably find out if there were a mistake, but not where the mistake is. Even worse, you might think you know where the mistake is, but be wrong.

Once you have fully tested a function, you can use it in the program for other function. Each function should be tested in a program in which it is the only untested function. However, it is fine to use a fully tested function when testing some other function. If a bug is found, you know the bug is in the untested function.

It is sometimes impossible or inconvenient to test a function using some other function that has not yet been tested. In this case, you can use a simplified version of the missing or untested function. These simplified functions are stubs. These stubs will not necessarily perform the correct calculation, but they will deliver values that suffice for testing, and they are stub simple enough that you can have confidence in their performance.

Using a program outline with stubs allows you to test and flesh out the basic outline, rather than write a completely new program to test each function. For this reason, a program outline with stubs is usually the most efficient method of testing. A common approach is to use drivers to test some basic functions, as input and output, and then use a program with stubs to test the remaining functions. The stubs are replaced by functions one at a time: One stub is replaced by a complete function and tested; once a function is fully tested, another stub is replaced by a full function definition, and so forth, until the program is produced.

> The Fundamental Rule for Testing Functions
Every function should be tested in a program in which every other function in that program has already been fully tested and debugged.

## Chapter Summary

- A formal parameter is a kind of placeholder that is filled in with an argument when the function is called. In C++, there are two methods of performing this substitution, by value and by reference, and so are two basic kinds of parameters: call-by-value parameters and call-by-reference parameters.
- A call-by-value parameter is a local variable that is initialized to the value of its argument when the function is called. Occasionally, it is useful to use a call-by-value parameter as a local variable.
- In the call-by-reference substitution mechanism, the argument should be a variable, and the entire variable is substituted for the argument.
- A call-by-value parameter is indicated by the absence of ampersand. A call-by-reference parameter: The way to indicate a call-by-reference parameter in a function definition is to attach the ampersand sign (&), to the type of the formal parameter. (A call-by-value parameter is indicated by the absence of ampersand.)
- An argument corresponding to a call-by-value parameter cannot be changed by a function call. An argument corresponding to a call-by-reference parameter can be changed by a function call. If you want to change the value of a variable, then you must use a call-by-reference parameter.
- You can give multiple definitions to the same function name, provided that the different functions with the same name have different numbers of parameters or some parameter position with differing types, or both. This is called overloading the function.
- You can specify a default argument for one or more call-by-value parameters in a function. Default arguments are always in the rightmost argument positions.
- The assert macro can be used to help debug your program by checking whether or not assertions hold.
- Every function should be tested in a program in which every other function... has already been fully tested and debugged.
