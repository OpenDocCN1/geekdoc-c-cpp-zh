# TIP: Exception Classes Can Be Trivial

In the following, we have reproduced the definition of the exception class DivideByZero from Display 18.4:

```cpp
class DivideByZero
{};
```

This exception class has no member variables and no member functions (other than the default constructor). It has nothing but its name, but that is useful enough. Throwing an object of the class DivideByZero can activate the appropriate catch block, as it is in Display 18.4.

When using a trivial exception class, you normally do not have anything to do with the exception (the thrown value) once control gets to the catch block. The exception is just being used to get you to the catch block. Thus, you can omit the catch-block parameter. In fact, you can omit the catch-block parameter any time you do not need it, whether the exception is trivial or not.

# Throwing an Exception in a Function

Sometimes it makes sense to delay handling an exception. For example, you might have a function with code that throws an exception if there is an attempt to divide by zero, but you may not want to catch the exception in that function. Perhaps some programs use that function should simply end if the exception is thrown, and other programs use the function to do something else. Thus, you would not know what to do with the exception if you caught it inside the function. In these cases, it makes sense not to catch the exception in the function definition, but to have any program (or other code) that uses the function to place the invocation in a try block and catch the exception in a catch block that follows that try.

Look at the program in Display 18.5. It has a try block, but there is no throw statement visible in the try block. The statement that does the throwing in that program

```cpp
if (bottom == 0)
    throw DivideByZero( );
```

# Exception Specification

If a function cannot catch an exception, it should at least warn programmers that any invocation of the function might possibly throw an exception. If there are exceptions that might be thrown but not caught in the function, those exceptions should be listed in an exception specification, which is illustrated by the following function declaration from Display 18.5:

```cpp
double safeDivide(int top, int bottom) throw (DivideByZero);
```

As illustrated in Display 18.5, the exception specification should appear in both the function declaration and the function definition. If a function has more than one function declaration, then all the function declarations must have identical specifications. The exception specification for a function is also called the throw list.

If more than one exception can be thrown in the function definition, the exception types are separated by commas, as illustrated in what follows:

```cpp
void someFunction() throw (DivideByZero, SomeOtherException);
```

# PITFALL: Exception Specification in Derived Classes

![](img/f4b6fc3d28ec32a6e3350e2846d6e0d1_874_0.png)

When you redefine or override a function definition in a derived class, it should have the same exception specification as it had in the base class, or it should have an exception specification whose exceptions are subset of those in the base class specification. Put another way, when you redefine or override a function definition, you cannot add any exceptions to the exception specification (but you can delete some exceptions if you want). This makes sense, since an object of the derived class can be used anywhere an object of the base class can be used, and so a redefined or overwritten function must fit any code written for an object of the base class.
