# Chapter 7

We are accessing the dSum attribute from the threads without any protection! Let's
illrate what can happen:

| T | Thread A on CPU_0 | Thread B on CPU_1 | | |
|---|---|---|---||
| | | | address | value |
| 0 | MOV RAX, [4004] | MOV RAX, [4004] | 1008 | 5.036 |
| 1 | ADD RAX, [1008] | ADD RAX, [2016] | 2016 | -3.047 |
| | | | 4004 | 42.56 |

A wants to add a value of Allele(i) to dSum. Both Allele(i) and dSum are
memory locations that have a certain address. Let's assume that the address of dSum is
4004 and its value is 42.56; assume that the address of Allele(i) for thread A
1008; thread B wants to add its own Allele(i) value on the current dSum value;
dSum is the same, which is 4004, while the address of thread B Allele(i) is
different than that of thread A (assume it is 2016); thread A is executing (for example) on
CPU 0 while thread B is executing on CPU 1.

The statement at time 0 for thread A RAX = 42.56 while thread B it RAX = 42.56
You can see. The statement at time 1 for thread A RAX = 42.56 + 5.036, which is 47.596,
while for thread B it RAX = 42.56 + (-3.047), which is 39.513. As you can see, this is totally
wrong! The value of dSum won't be 44.549 as it should be after we add both the values, as
the idea. Again, the correct application design is crucial with concurrency in action!

We must change the Evaluate method in a manner such that it follows the logic needed
for the calculation of Schwefel's function, but at the same time, we must respect the
mithreaded execution, or else we'll most get correctness or liberalism!
The correct implementation is follows:

```
DWORD WINAPI StartAddress(LPVOID lpParameter)
{
ThreadParams* params = (ThreadParams*)lpParameter;

unsigned uChunk = ((unsigned)params->this_ptr->Size()) / ThreadNumber;
unsigned uMax = (params->uThreadIndex + 1) * uChunk;

double dSum = 0;
double dMin = DBL_MAX;
```
