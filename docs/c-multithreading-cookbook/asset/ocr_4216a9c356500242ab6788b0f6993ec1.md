However, there are disadvantages too. The application developed using any framework, such as .NET or Java Runtime Environment (JRE), is much slower than an application developed using native code. This happens because managed code is executed over a CLR layer, which is then executed on the machine hardware. When you use a framework, it is easier to develop the application, but you will never have complete control over the application's execution, along with its interaction with the machine itself. The best you can do is what the framework provides you with.

To conclude, you should need a native approach whenever you need fast execution and/or complete over the application execution, while the framework should be whenever you need an application that targets UI and simpler development. Over the years, Microsoft has done an excellent job with the .NET framework, but it will never be able to provide everything you can do with the native approach. That's why we are focusing on managed code in one chapter, and that of the chapters are covered with a native approach.

Note that everything you can do with frameworks you can achieve with a native approach. You would need more time and more effort—but it is double. You can't do everything with a managed approach, not even a part of what you can do with native code. To explain this better, let's examine two scenarios. First, we need to create software that will control nuclear power plants. The second task is to create software that will use a cluster to render DVDs. The first task should be developed using native C++ (or the assembly language) to provide extremely fast and precise execution. This is because, and you would agree with me, nuclear energy is so sensitive thing to be taken lately. On the other hand, DVD software should look good (so that you can sell it), and the execution time doesn't need to be in micro or nanoseconds. It is enough to be user friendly and work correctly, so we could use .NET to develop faster and with lesser effort.
