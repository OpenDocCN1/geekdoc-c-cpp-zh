Even though we duplicate a number of threads, for each task, we will create two instead of one thread, we will still maintain the number of threads. The thread created for the execution of the task will create one more thread and wait for it, only to have more control over the task execution. We will call the first thread worker and we will call the second thread, which will be created, context thread. The idea behind such an approach is that we will have more control; if the context thread has been terminated, the worker that waits for it will query its exit code and notify the dispatcher that something went wrong. If the context thread hangs or it is unresponsive, the worker will notice that something went wrong and will perform an appropriate action, while we try to resolve the dispatcher. This granularity gives us more control and makes the pool much smarter.

Our example will target a scenario where a deadlock will be intentionally created and we will try to resolve such a situation.
