# Non-blocking synchronization

Many features of .NET programmers must be aware of certain CLR behavior so as to avoid mistakes when using multiple threads. Both, the Microsoft CLI/C++ compiler as well as CLR can reorder certain statements at runtime for the sake of improving efficiency or caching optimizations. For these reasons, it is not always enough to organize the code, it must be protected as well. That's why .NET provides MemoryBarrier that prevents the effects of instruction reordering and read/write caching, as in the following class:

```cpp
ref class TestClass
{
public:
    TestClass()
    {
        bState = false;
        iValue = 0;
    }
    static void SetMethod()
    {
        iValue = 5;
    }
```
![](img/412b0f5bbb36adcce2ddd2d5b7416516_305_0.png)

```cpp
    static void GetMethod()
    {
        if (bState)
        {
            MessageBox::Show(Convert::ToString(iValue));
        }
    }
private:
    static volatile bool bState;
    static int iValue;
};
```

```cpp
ref class TestWorker
{
public:
    TestWorker()
    {
        Task^ _t1 = gcnew Task(gcnew Action^(&SetMethod));
        _t1->Start();
        Task^ _t2 = gcnew Task(gcnew Action^(&GetMethod));
        _t2->Start();
    }
};
```

In your opinion, is it possible that GetMethod shows 0 for iValue? Well, the simplest solution is to create a memory fence or surround usage with MemoryBarrier statements, as shown in the following code:

```cpp
static void SetMethod()
{
    iValue = 5;
    Thread::MemoryBarrier();
    bState = true;
}
static void GetMethod()
{
    if (bState)
    {
        Thread::MemoryBarrier();
        MessageBox::Show(Convert::ToString(iValue));
    }
}
```

This is called full fence, and it takes around 10 nanoseconds for the execution of this protection. There is another feature that the C++ compiler provides: volatile keyword. The use of volatile keyword instructs the compiler to create an acquire fence for each read operation on a volatile memory location, and a release fence for each write operation on a memory location is declared as volatile. The acquire fence prevents read/write operations to be moved above the fence, and the release fence prevents read/write operations to be moved below the fence. Implementation using volatile memory location could be as follows:

```cpp
ref class TestClass
{
public:
    TestClass()
    {
        bState = false;
        iValue = 0;
    }
    static void SetMethod()
    {
        iValue = 5;
        bState = true;
    }
    static void GetMethod()
    {
        if (bState)
        {
            MessageBox::Show(Convert::ToString(iValue));
        }
    }
private:
    static volatile bool bState;
    static int iValue;
};
```

Using volatile memory objects or so-called half fences is much faster due to more space for runtime optimization.

# Signaling with Wait and Pulse

In one of our examples, we've used the Lock class whose implementation uses Monitor::Enter and Monitor::Exit. Another feature of the Monitor object is very important: Monitor::Wait and Pulse (and PulseAll methods). These methods also make their ability to wait until a signal is received from another thread makes them excellent for usage. One of the most important features is that they prevent switching, because of which no processor thread is active. The only constraint is that they must be enclosed with locks (Monitor::Enter and Monitor::Exit). Once again, we're introducing the Lock class in order to gain exclusive access to shared objects.

Our following example will show you how to use the static Wait and Pulse methods as a technique to synchronize threads.
