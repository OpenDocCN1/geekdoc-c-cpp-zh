It will take the ownership of the mutex, get the element from the queue, to write shared file mapping, and then it will release the mutex. When a reply is prepared, it will write to the pipe using the WriteFile API, and again wait for the client's reply using ReadFile. After receiving the calling result from an external process, it will release the used resources and exit.

Inside WindowProcedure, we've changed so that creating threads we create processes—as there are elements in the queue. It would be wiser if we had not one working process to calculate and receive tasks one by one, but we wanted to point out important parts of Interprocess Communication as well as synchronization—so an example designed like this makes more sense.

Now, let's review the client process: first, it will try to connect to the pipe. As our main application creates processes, with a 0.1 second gap between them, there is a great possibility that you'll try to connect to the pipe simultaneously. Well that is impossible, and you'll probably get an ERROR_INVALID_HANDLE error! That's why the process will loop, with a 0.1 second delay until it is connected. After successful connection, the process will use the ReadFile API to wait until a request is made. If the requested format is 0x12345, where 12345 stands for its process identifier, it will ask for the ownership of the mutex, and when the process gets it, it will read coordinates from the shared file mapping and respond using WriteFile. After it responds, it will release the mutex and write its result to the console.
