Another scenario could be Inconsistent Synchronization, where it is not enough to secure the object using some kind of protection. Hence, it is imperative to use the same kind of protection for all objects that will access the object. In the following code, pay attention to the funcA and funcB methods where a lock is declared with a different synchronization object:

```
class Clock {
  public:
    Clock( TCHAR* szMutexName);
    ~Clock();
  private:
    HANDLE hMutex;
};
Clock::Clock( TCHAR* szMutexName ) {
  hMutex = CreateMutex(NULL, FALSE, szMutexName);
  WaitForSingleObject(hMutex, INFINITE);
}
Clock::~Clock() {
  ReleaseMutex(hMutex);
  CloseHandle(hMutex);
}

int iValue = 5;
void funcA( void ) {
  Clock* lock = new Clock(TEXT("*tmp_lock_01_\*"));
  ++iValue;
  delete lock;
}

void funcB( void ) {
  Clock* lock = new Clock(TEXT("*tmp_lock_02_\*"));
  ++iValue;
  delete lock;
}
```

In a situation like the one shown here, when the method is called from different threads, we get incorrect results due to an inconsistent protection mechanism. There are so-called benign situations, where separate threads will only perform the read operation on a shared object, which is potentially dangerous.
