The kernel development must be performed with extreme caution, even if the smallest of mistakes can lead to Blue Death (BSOD) or a machine crash. That's why we are using the _try -except block, which is slightly different from catch that we are used to.

Handles created in the kernel are not the same as handles created in the user. The space returned by PsCreateSystemThread cannot be used for the KeWaitForSingleObject routine. We need to initialize an event that will be signaled (events will be explained in detail in Chapter 3, Managing Threads) from the thread itself when KeWaitForSingleObject returns. Every call to PsCreateSystemThread must have its matching call to the ZwClose routine. A call to ZwClose closes the kernel handle and prevents memory leaks.

Finally, we need to implement KSTARTROUTINE or a thread start address where instructions for the thread execution will start. An example of this is as follows:

```
VOID (_stdcall* KSTART_ROUTINE (PVOID StartContext);
```

We have passed pointer to KEVENT via the parameter of PsCreateSystemThread. Now, using DbgPrint, we simply write a message to the user with the corresponding thread ID. After that, we will set an event so that the corresponding KeWaitForSingleObject call return and safely exit the driver. Make sure PsTerminateSystemThread does not return. The kernel will clean the thread object on unloading the driver.

# There's more...

While the kernel solves some problems, they do not solve all of them. For example, what happens when a multithreaded process creates another multithreaded process? Does the new process have as many threads as the old one, or just one? In many cases, the best choice depends on what the process needs next. If it is going to start a new process, probably one thread is the correct choice, but if it continues to execute, reproducing all threads is the right thing to do.
