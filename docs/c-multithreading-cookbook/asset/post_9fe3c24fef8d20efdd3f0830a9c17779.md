# How it works...

The previous example demonstrates synchronization from the application that operates over the MySQL database. The example shows only one way to achieve this, while there was another way to use synchronization through Database Management System (DBMS) itself, using table locks. The important thing here was disabling the thread to read or write in the same time as another thread performing a read or write operation. We assumed that two of our three threads have to read, the third one has to write certain data. You could assume that after reading, the thread has to signal the main application or some other handler with the data, to continue processing. The same stands for the thread that has to write-it would obtain data from some handler and perform the necessary operation. For thread synchronization, we were using a critical section object. A detailed explanation of a critical section object will be presented in Chapter 5, Managing Threads.

# There's more...

As we said, there was another, easier way to synchronize threads while they operate over the MySQL database. With today's MySQL DBMS, we can achieve this using table locking. To give a hint to the user, we will demonstrate one way of performing query from two threads but at the same time to retain synchronized read and write operations, without interference from one another.

- 1. Read thread:
   lock table TABLE_NAME read;
   select something from TABLE_NAME;
   unlock tables;

- 2. Write thread:
   lock table TABLE_NAME write;
   insert into TABLE_NAME values( _ );

```sql
update TABLE_NAME set something;
unlock tables;
```

- 3. Both operations from a single thread–others must wait:
lock table TABLE_NAME TABLE_ALIAS read, TABLE_NAME write;
select from TABLE_NAME as TABLE_ALIAS;
insert into TABLE_NAME values ...
unlock tables;

Pay attention that there are many MySQL engine models (InnoDB, MyISAM, Memory, and so on), and thread locking and locks granularity varies between engines.

# Implementing threads in user space

There are two ways to implement a thread's package: in the user space and in the kernel. The choice is moderately controversial and a hybrid implementation, where it is also possible to use a combination of kernel and user thread.

We will now describe these methods, along with their advantages and disadvantages. The first method is to put the threads package entirely in the user space. The kernel knows nothing about them. As far as the kernel is concerned, it is managing ordinary, single-threaded processes. The first and most obvious advantage is that a user-level package can be implemented on an operating system that does not support threads.

Traditional operating systems used to fall into this category, and even now, still do. With this approach, threads are implemented by a library. All of these implementations have the same general structure. The threads run on top of a runtime system, which is a collection of procedures that manage threads. We have seen a few of these already (CreateThread, TerminateThread, and others), but, there are more.

The following example will demonstrate thread usage in user space. We want to copy large files. We don't want to read it entirely first and write it after that. No, it would be more optimized to read it by piece, at the same time writing whatever piece was previously read. This scenario demonstrates the Producer-Consumer problem, mentioned earlier in the Interprocess Communication recipe.

```cpp
#include "ConcurrentFileCopy.h"

HWND hWnd;
WNDCLASSEX wc;
MSG msg;
DWORD dwFileSize;
DWORD dwBlockSize;
HANDLE hThread;
HANDLE hMutex;
COPYDETAILS copyDetails;

int WINAPI WinMain(HINSTANCE instance, HINSTANCE hPrev, LPSTR lpCmdLine, int nShow)
{
    wc = {0};
    wc.cbSize = sizeof(WNDCLASSEX);
    wc.style = CS_HREDRAW | CS_VREDRAW;
    wc.lpfnWndProc = WndProc;
    wc.cbWsExtra = 0;
    wc.cbWndExtra = 0;
    wc.hInstance = instance;
    wc.hIcon = LoadIcon(instance, IDR_ICON);
    wc.hCursor = LoadCursor(NULL, IDC_ARROW);
    wc.hbrBackground = (HBRUSH)(COLOR_WINDOW + 1);
    wc.lpszMenu = NULL;
    wc.lpszClassName = szWindowClass;
    wc.hIconSm = LoadIcon(instance, IDR_ICON);

    if (!RegisterClassEx(&wc))
    {
        MessageBox(NULL, T("Cannot register class!"), T("Error!"), MB_OK);
        return 0;
    }

    hWnd = CreateWindow(szWindowClass, T("ConcurrentFileCopy"), WS_OVERLAPPEDWINDOW,
        DEFAULT_USE, DEFAULT_USE, 400, 300, NULL, NULL, instance, NULL);

    if (!hWnd)
    {
        MessageBox(NULL, T("Cannot create window!"), T("Error!"), MB_OK);
        return 0;
    }

    ShowWindow(hWnd, nShow);
    hMutex = CreateMutex(NULL, FALSE, MUTEX_NAME);
    hThread = CreateThread(NULL, 0, (LPTHREAD_START_ROUTINE)ReadRoutine, &copyDetails, 0, NULL);

    while (GetMessage(&msg, NULL, 0, 0))
    {
        TranslateMessage(&msg);
        DispatchMessage(&msg);
    }

    CloseHandle(hThread);
    CloseHandle(hMutex);
    UnregisterClass(szWindowClass, instance);
    return (int)msg.wParam;
}
```

```cpp
LRESULT CALLBACK WndProc(HWND hWnd, UINT uMsg, WPARAM wParam, LPARAM lParam)
{
    switch (LOWWORD(wParam))
    {
    case BUTTON_CLOSE:
    {
        DestroyWindow(hWnd);
        break;
    }
    case WM_DESTROY:
    {
        PostMessage(0);
        break;
    }
    default:
    {
        return DefWindowProc(hWnd, uMsg, wParam, lParam);
    }
    }
    return 0;
}
```

```cpp
DWORD WINAPI ReadRoutine(LPVOID lParameter)
{
    COPYDETAILS pCopyDetails = (COPYDETAILS)lParameter;
    HANDLE hFile = CreateFile(pCopyDetails->szReadFileName, GENERIC_READ, FILE_SHARE_READ, OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL, NULL);
    if (hFile == (HANDLE)INVALID_HANDLE_VALUE)
    {
        MessageBox(hWnd, T("Cannot open file!"), T("Error!"), MB_OK);
        return FALSE;
    }
    dwFileSize = GetFileSize(hFile, NULL);
    dwBlockSize = GetBlockSize(dwFileSize);
    hThread = CreateThread(NULL, 0, (LPTHREAD_START_ROUTINE)WriteRoutine, pCopyDetails, 0, NULL);
    return TRUE;
}
