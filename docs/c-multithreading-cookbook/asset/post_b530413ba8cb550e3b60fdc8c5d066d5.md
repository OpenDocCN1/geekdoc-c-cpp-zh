## How it works

First, we created a Win32 application but only for demonstration purposes. We won't have a UI, not a message log. We simply want to load a driver into the kernel; then we will show the ShellAbout dialog to give the user time to read the DbgView output (detailed explanation about DbgView can be found in the Appendix), and after the user closes the ShellAbout dialog, the driver is unloaded and the application ends.

The Win32 application that we created can only load and unload the driver, so no further explanation will occur. Now, let's review the DriverApp project. After the proper setting of Visual Studio project for driver compilation (detailed explanation about compilation settings for Visual Studio can be found in the Appendix), we have declared the two main routines that every driver must have in the DriverApp.h header file:

```cpp
DRIVER_INITIALIZE DriverEntry;
DRIVER_UNLOAD Onload;
```

These two routines are the driver entry point and driver unload routine. We will use driver entry point to initialize a driver object and start the kernel thread. A newly created thread will return unique identifier immediately. Further, the kernel exploration and development is not part of this book. We only wanted to give a taste of the kernel thread. As the driver is compiled as /TC2, we had to make sure that all variables are declared before the first command. This is shown in the following code:

```cpp
HANDLE hThread = NULL;
NTSTATUS ntStatus = 0;
OBJECT_ATTRIBUTES ThreadAttributes;
KEVENT kEvent = { 0 };
PTHREAD pThread = 0;
```

Then, we have to unload the routine:

```cpp
theDriverObject->DriverUnload = OnUnload;
```

Now, before we can create the kernel thread, we need to initialize the ThreadAttribute object by calling the InitializeObjectAttributes routine first:

```cpp
InitializeObjectAttributes(&Threadattributes, NULL,
OBJ_KERNEL_HANDLE, NULL, NULL);
```

The kernel development must be performed with extreme caution, even if the smallest of mistakes can lead to Blue Death (BSOD) or a machine crash. That's why we are using the _try -except block, which is slightly different from catch that we are used to.

Handles created in the kernel are not the same as handles created in the user. The space returned by PsCreateSystemThread cannot be used for the KeWaitForSingleObject routine. We need to initialize an event that will be signaled (events will be explained in detail in Chapter 3, Managing Threads) from the thread itself when KeWaitForSingleObject returns. Every call to PsCreateSystemThread, we need to handle the thread. An example is:

```cpp
VOID ThreadStart(PVOID lpStartContext) {

    (ULONG)PsGetCurrentThreadId());
```
