
# Threads in the .NET Framework

When you use a framework, answers to these questions depend on the framework itself. Microsoft provides a Thread class as well as a Task class and a collection of auxiliary types that reside in the System::Threading namespace.

The Task class represents abstraction of concurrent operations. CLR implements the Thread object and schedules them for execution using the ThreadPool class. Multithreaded design can be performed using the Thread class, which resides in the System::Threading namespace. For Windows 8 and the Windows store application, the Task class is not available. You should use the Task class because it provides powerful abstraction of multithasking, and if you design an application that creates a specific (but finite) number of threads, your application won't be scalable. In other words, if the number of threads exceeds the number of cores, you could get stuck with unresponsive behavior. CLR helps you implement concurrent tasks in the best way with respect to the number of cores. When your application creates a Task object, an actual task is added to the working queue. When a thread becomes available, the task is removed from the queue and the available thread executes. The ThreadPool class implements several optimization techniques and uses an algorithm for the work-stealing strategy for better thread scheduling.

Work-stealing is a feature of the scheduling algorithm, where problems are analyzed and then the execution (for solving the problem) is performed. Considering the number of quantums and the calling depth, it is easy to solve, then it is directly solved. If the problem is considered complex, it is split into smaller parts using already-created, available threads from other CPU cores, for task solving. Later, the subresults are merged into the final result. The idea is to use (steal) available threads, of course, possible.

Now, we will create our first application using Visual Studio, before 2012 and 2013, the C++ Windows Forms template included. Our first example will create a simple application, which will calculate the factorial (the product of all positive integers less than or equal to n) with n number of iterations, where the working thread will calculate while the main thread will update the progress bar only to demonstrate the basic CLR program and explain a very important feature: cross-thread operations.

# How it works...

Let's explain MyForm.h first. Every (one or more) namespaces; in our case, we are using the CLRAApplication namespace (produced by the designer). As we want to use the framework's features, we need to specify libraries (also called assemblies) and so in the following code:

```cpp
using System;
using System::Collections;
using System::Windows::Forms;
using System::Drawing;
using System::Threading::Tasks;
```

Then, we will derive our UI tools to use as forms, points, and location objects from the System::Windows::Forms::Form base class. Pay attention to the MyForm constructor, where the first command is to call InitializeComponent. After our code, InitializeComponent loads the page of a component and initializes base values, such as size, type, and padding. InitializeComponent resides in a region Windows Form generated code. The designer generates a destructor under the protected scope of our class, and a single variable under the private scope, which encapsulates zero or more components (controls). The code follows:

```cpp
System::ComponentModel::Container *components;
```

We've added label, progress, and N variables for the progress bar, label control, and the iterations N respectively. The InitializeApp method creates a new label and sets its location (the x and y coordinates on the parent control). It also creates a new progress bar and initializes it, size (the width and height), step (how many steps the progress bar will update after calling its PerformStep method), maximum (the maximum value that progress can have), and a starting value. After that, we will add these two controls to the main form by calling the Add method:

```cpp
this->Controls->Add(label);
this->Controls->Add(progress);
```

Now, it is time to create our thread (task). As in the native approach, we must specify its start address, if needed, we pass an argument to its starting routine. As our start routine is marked static, we will pass the pointer to the routine in order to use our class instance. The task constructor expects a pointer to the Action object, and if the Action<Object>* is overloaded, it also expects a parameter constructor. We will create a pointer to Action<Object>* as follows:

```cpp
gcnew Action<Object*>*(&MyForm::StartAddress)
```

The Action constructor explains the delegate (function pointer) to pass on, and we are providing the address of StartAddress method.

Now, let's explain the StartAddress method. First, we need to instantiate a delegate that will later be used for invoking the main thread (similar to void*); next, we will instantiate a delegate that will be used for invoking the main thread to update the progress bar. This is very important to understand! Unlike the native approach, CLR pays attention to which thread creates what, and only the thread that created a control can manipulate it. As the main thread has created the progress bar in the Initialize method the main thread can manipulate it. If you try to update the progress bar from another thread, you'll get an error Cross-thread operation not valid: Control 'progress' accessed from a thread other than the thread it was created on. In other words, the working thread has to ask the main thread to update it, because the main thread created the progress bar. This can be achieved using the Invoke and BeginInvoke methods. These two methods are doing the same thing; they execute a delegate on the thread that controls the underlying handle was created. The difference between them is that BeginInvoke does asynchronously, while Invoke does that by waiting for the operation to return. Then, we will need to iterate n times, and at the end of each iteration we will call BeginInvoke to update the progress bar. After the iterations completed, we will perform the same task for setting the label text.

As we said earlier, we will instantiate a delegate for both the previously described operations. In order to achieve that, we must declare delegates and methods to be invoked. The declarations are shown in the following code:

```cpp
delegate void UpdateProgressBarDelegate();

System::Void UpdateProgressBar()
{
    progress->PerformStep();
}
```
