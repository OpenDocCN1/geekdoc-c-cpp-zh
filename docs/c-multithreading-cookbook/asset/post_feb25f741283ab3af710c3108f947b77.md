After the user gives the input, control is returned to the application. Only now can the application continue the execution. In order to overcome such an issue, we can create concurrent threads that will handle the user input. In this way, the application does not stall and is responsive all the time. After a thread handles its task, it can signal that a user has performed the requested operation to the application.

Every time we have an operation that needs to be executed separately from the main execution flow, we have to think about a separate thread. The simplest example is when we have some calculations, and we want to have a progress bar where the calculation progress will be shown. If the same thread probably wouldn't work. This occurs because, if both work and a UI update are performed from a single thread, such threads cannot interact with OS painting adequately; so almost always, the UI thread separate from the working threads.

Let's review the following example. Assume that we have created a function that we will calculate something, for example, sines or cosines of some angle, and we want to display progress in every step of the calculation:

```
void calculateSomething(int iCount)
{
    int iCounter = 0;
    while (iCounter++ < iCount)
    {
        //make calculation
        //update progress bar
    }
}
```

As commands are executed one after another inside iteration of the while loop, the operating system doesn't have the required time to properly update the user interface (in this case, the progress bar), so we would see an empty progress bar. After the function returns, a fully filled progress bar appears. The solution for this is to create a progress bar on the main thread. A separate thread should execute the calculate function; in each step of iteration, it should somehow signal the main thread to update the progress bar step by step. As we said, threads are switched extremely fast on the CPU, so we can get the impression that the progress bar is updated at the same time as the calculation is performed.

To conclude, each time we have to make a parallel task, for some kind of user, or for an external dependency such as response from a remote server, we create a separate thread so that our program won't hang and unresponsive.

In future examples, we will discuss static and dynamic libraries, let's say a few words about static. A static library (*lib) is usually some code placed in separate files and already compiled for use. We will add it to the project when we want to use some of its features. When we include <iostream>, the compiler will include a static library which implements input stream functions. A static library is built into the executable at compile time before actually run the program. A dynamic library (.dll) is similar to a static library, but the difference is that it is not resolved during compilation; it is linked later when we start the program, or at-runtime. Dynamic libraries are very useful when we have functions that a lot of programs will use. So, we don't need to include dynamic library. A good example is User32.dll, where the Windows OS placed a majority of GUI functions. So, if we create two programs where both have a window (GUI form), we do not need to include CreateWindow in both programs. We will simply link User32.dll at runtime, the CreateWindow API will be available.

# How it works...

We created the ComplexAdd function that has six parameters or three complex numbers. The first two parameters are the real and imaginary parts of the first complex number, parameters three and four are the real and imaginary parts of the second complex number, and the fifth and sixth parameters are the real and imaginary parts of the complex number that will represent the result or the sum of the first two complex numbers. Note that the fifth and sixth parameters are passed by reference. We also created a Rand function that will return a real number from a range between dMin and dMax.

As you can see, we have achieved what we wanted; however, you'll agree that the given code is not very readable and the ComplexAdd function has many parameters. Also, we have six variables in the main function, so the conclusion is that this kind of approach is not very 'friendly'. Let's review a slightly different approach by using structures, as shown:

```
#include <stddef.h>
#include <iostream>

using namespace std;

struct SComplex
{
    double dReal;
    double dImg;
}

SComplex ComplexAdd(SComplex c1, SComplex c2)
{
    SComplex c;
    c.dReal = c1.dReal + c2.dReal;
    c.dImg = c1.dImg + c2.dImg;
    return c;
}

double Rand(double dMin, double dMax)
{
    double dVal = (double)rand() / RAND_MAX;
    return dMin + dVal * (dMax - dMin);
}
int _main(int argc, TCHAR* argv[])
{
    SComplex c1;
    c1.dReal = Rand(-10, 10 );
    c1.dImg = Rand(-10, 10 );
}
```
