Let's review the main routine now. For, the WNDCLASS object that is needed for the application window is created, initialized, and registered with the RegisterClassEx call. After we created a window with the CreateWindow API, we have to create four windows where the threads will perform the paint action. Calls to UpdateWindow and ShowWindow follow. We will use the STATE_SYNC and STATE_CONTINUOUS flags merged using the operator, OR |, then we will use the user data pointer to the window handle, which will be used to identify the portion of the window that it needs to paint

The call SetWindowLongPtr associates user data (with the provided flag GWLP_USERDATA) with the window identified by the first parameter—in our case, the main application window. The third parameter is for specific user data that needs to be associated with the window. We will pass the Thread address, so that we can use it in WindowProcedure, after processing the message loop.

InWindowProcedure, we process two cases: when the user closes the application and when the window needs to be destroyed. The case WM_CLOSE is where we need to wait for threads to safely join. First, we obtain the address of the thread array by GetWindowLongPtr, where we saved its address before. As is enough that only one thread calls the method Alert. All threads that are listening for an event signal will receive it. Then, we will call Join for each thread and exit the program.

# Using synchronized threads

Contrary to the previous recipe, there are a lot of situations where parallel tasks need to occur with dependency on each other. Such situations could occur in an application with a user interface dialog for displaying customers and for the selected customer payment history. For example, the application window, there is a list with customers. Below, there is a list with payment history for the selected customer. When loading the initial set of customers, we need to display the customer's (selected on load) payment history. We'll start one thread for loading the customer list. At the same time, another thread is responsible for loading a specific customer payment history will also start. Until the first customer is loaded, the payment history must wait for the customer ID.

Now, let's go back to the example from the previous recipe. We'll assume the same situation, but this time, with limited system resources, we have to initialize the main application window, and then we need to create four child windows. For each window, we will create a separate thread; this time, we will have only one brush for painting each window respectively.

```cpp
LRESULT CALLBACK WindowProcedure(HWND hWnd, UINT uMsg, WPARAM wParam, LPARAM lParam)
{
    switch (uMsg)
    {
    case WM_DESTROY:
    {
        PostQuitMessage(0);
        break;
    case WM_CLOSE:
    {
        Thread* pThread = (Thread*)GetWindowLongPtr(hWnd, GWLP_USERDATA);
        pThread->Alert(0);
        for (int iIndex = 0; iIndex < THREADS_NUMBER; iIndex++)
        {
            threads[iIndex].Join();
        }
    }
    DestroyWindow(hWnd);
    break;
    {
    default:
    {
        return DefWindowProc(hWnd, uMsg, wParam, lParam);
    }
}
return 0;
```
