
Well, we could also query the queue count so as to the SetThreadProcessor to start more threads than necessary, but you'll get the point. We are also using the SetThreadIdeal API in order to tell the system to schedule the thread to the selected processor. This routine specifies a thread ideal processor and provides a hint to the scheduler about the preferred processor for a thread. The scheduler runs the thread on the thread ideal when possible, but without guaranteeing a given number. In a situation where the selected processor is busy and our thread is next for execution, the system will schedule it on the next available core.

The answer to the second question is as follows: what is the shared object that all threads use? Well would certainly be the queue object. The Queue::Dequeue operation is performed from each thread in parallel. That place would be an application bottleneck without proper synchronization, so we must take care of it. We use a mutex when we want to gain exclusive access to one thread. That is perfect for our Dequeue operation because at any instant of time, only one thread should obtain an object from the queue. By using a mutex, we are providing exclusive access to the shared object, in this example Dequeue, and its operation Dequeue.
