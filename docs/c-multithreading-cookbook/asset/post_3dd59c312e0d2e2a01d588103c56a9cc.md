The automatic reset event always releases only one thread at each signal before resetting. It could be useful for a program where the main thread prepares for other working threads. Each time a new set of data is ready, the main thread sets the event and the working threads are released. Other threads remain waiting in a queue to get a new task.

In addition to setting and resetting, the event can be pulsed. A pulse sets a signal for a very short time and then turns it off. When you pulse a manual reset event, we allow all the threads that are waiting to continue, and then the event is reset. Pulsing an automatic event allows only one thread that is waiting to pass, and resets the event. If no thread is waiting, neither will pass. Setting an automatic event, on the other hand, will cause the event to leave its signal while a thread is waiting. As soon as one thread passes, the event resets.

The following are the routines for event usage. To create or open an event object, you can use CreateEvent or CreateEventEx:

```
HANDLE WINAPI CreateEvent(
SECURITY_ATTRIBUTES lpEventAttributes,
BOOL                bManualReset,
BOOL                bInitialState,
LPCTSTR            szName,
);
HANDLE WINAPI CreateEventEx(
SECURITY_ATTRIBUTES lpEventAttributes,
LPCTSTR            szName,
DWORD               dwFlags,
DWORD               dwDesiredAccess
);
```

For the CreateEvent API, you can set the security attributes or leave it for the default values. The bManualReset parameter is set to TRUE, ResetEvent must be used to set the state to nonsignaled. The bInitialState sets the state of an event. If the value is set to TRUE, the object is set to the signaled state immediately. The event must be supplied.

On the other hand, CreateEventEx works pretty much the same way, only its terminology is different. Apart from the attributes, which are the same, you need to supply the name and value for dwFlags, which have defined macros for the initial set and manual reset event types: CREATE_EVENT_INITIAL_SET and CREATE_EVENT_MANUAL_RESET. The only real difference is that dwDesiredAccess can set the access mask for the event object. For a complete list of Synchronization Object Security and Access Rights, refer to MSDN http://msdn.microsoft.com/en-us/windows/desktop/ms68660%28v=vs.859.aspx.

It is possible to open an existing event object using OpenEvent:

```
HANDLE WINAPI OpenEvent(
    DWORD dwDesiredAccess,
    BOOL  bInheritHandle,
    LPCTSTR szName
);
```

If the event does not exist, the routine fails and returns NULL. Calling OpenEvent enables multiple threads to handle the same event, but only if the event was previously created by calling CreateEvent or CreateEventEx.

For setting an event object, SetEvent is used:

```
BOOL WINAPI SetEvent(
    HANDLE hEvent
);
```

It has one argument—handle to the event object previously created by CreateEvent and CreateEventEx, or opened by OpenEvent. The manual reset event state remains nonsignaled until it is explicitly set to nonsignaled, by calling the ResetEvent API.

To reset an event object, ResetEvent is used:

```
BOOL WINAPI ResetEvent(
    HANDLE hEvent
);
```

It has one argument—handle to the event object previously created by CreateEvent and CreateEventEx, or opened by OpenEvent. The manual reset event state remains nonsignaled until it is explicitly set to signaled, by calling the SetEvent API.

To pulse an event object, PulseEvent is used:

```
BOOL WINAPI PulseEvent(
    HANDLE hEvent
);
```

This method sets the event object to the signaled state and then resets it to the nonsignaled state, releasing a specific number of waiting threads.

# Synchronization object – critical section

A critical section performs the same function as a mutex, except that a critical section can't be shared. It is visible only within a single process. Both the critical section and the mutex allow only one thread to own it, but critical section works much faster and with less overhead.

The routines that operate with critical sections do not use the same terminology as the ones that work with a mutex, but they do mostly the same thing.

Unlike other objects that have been waiting for one of the wait functions, the critical section object works in different way. The critical section object enters its unsignaled state.

After it is released, the critical section object enters its signaled state.

In order to use the critical section, first we need to declare it:

```
CRITICAL_SECTION cs;
```

After that, we need to initialize it:

```
void WINAPI InitializeCriticalSection(
    LPCITICAL_SECTION lpCriticalSection
);
```

Then, we can use it by asking a thread to enter the critical region by calling the EnterCriticalSection or TryEnterCriticalSection API:

```
void WINAPI EnterCriticalSection(
    LPCITICAL_SECTION lpCriticalSection
);
BOOL TryEnterCriticalSection(
    LPCITICAL_SECTION lpCriticalSection
);
```

After the thread finishes its task, it must leave the critical region by calling the LeaveCriticalSection API:

```
void WINAPI LeaveCriticalSection(
    LPCITICAL_SECTION lpCriticalSection
);
```

After that, it needs to free the resources by calling the DeleteCriticalSection API:

```
void WINAPI DeleteCriticalSection(
    LPCITICAL_SECTION lpCriticalSection
);
```

# Introduction

To explain the Message Passing Interface (MPI), we need to understand the operating system well. As we mentioned in Chapter 1, Introduction to C++ Concepts and Features, modern Windows operating systems are designed as event-driven systems.

An event-driven system is the one where some action occurs as a response to some signal sent to the operating system. For example, when you move a mouse, cursor X-coordinate change and cursor Y-coordinate change are raised (we say an event is raised, not occurred). When you press any keyboard, another event is raised–pressed and so on.

At the operating system level, a large number of events are raised every few milliseconds, hidden from the user. Programming without events would be very difficult, especially for synchronization tasks.

One form of an event is the message at the operating system level. When you press your mouse button, the operating system calls the window procedure (event handler) for the window in which region (area) the click occurred. Parameters that define a message, event event-specific details, such as click coordinates, are passed to the window procedure that's being called.

# Message Passing

Every application that has a UI must have some form of a window. Top-level windows must implement top-level window handlers or window procedures, which will handle application events (messages), for example, button click, window paint, and others.

To be able to process messages for the window, an application must implement the event handler that the OS will call each time an event is raised. If you remember that every application must have its primary thread, then you can use the primary thread to process messages from other threads. In other words, you can use the window procedure from the main application to receive messages from other threads to communicate with each other.

There are other ways to pass a message to the thread, such as the PostMessage API, but the thread to which the message is posted must have created a message queue. We will explain this approach too, later in this chapter. However, using the window message queue is easier, in cases when your application has a UI.

This chapter will explain in detail how to use message passing for various tasks, especially for synchronization between threads.
