made up of 30 cycles outside the subroutine loop plus 10 cycles from 1 pass through the loop. Substituting these values into the formula gives us the following.

f_{CPU} = \frac{10000(40+1)}{1}
= 410000

The value from the calculation works out to 410kHz, which is used in the code at the top of the macro that tests for F_CPU limits, as follows.

```
...
.elif (F_CPU < 410000)
    .error "F_CPU too low for M_WAIT_MS macro. Minimum 410kHz"
.elif (@0 < 1)
    .error "Time delay too low for M_WAIT_MS macro. Minimum 1ms"
...
```

Looking back at main.asm, repeated below, we can see that wait_ms_macro.inc is included at the top of the code in which the macro is used. This makes the macro available to us in the main.asm file. Although F_CPU is used in wait_ms_macro.inc, it is defined below where wait_ms_macro.inc is included. The reason that this does not cause an error is because the assembler is a multi-pass assembler. This means that on the first pass through the file, the assembler builds up a symbol table. In this way it knows about F_CPU when it passes through the source code again. This is usually referred to as forward referencing.

```
wait_ms_macro.asm : main.asm

.include "wait_ms_macro.inc"
.equ    F_CPU    = 1000000

start:
    sbi     DDRB, DDB4        ; Set pin PB4 as output

loop:
    sbi     PORTB, PORTB4    ; Set LED pin high
    mWAIT_MS 200             ; LED on delay
    cbi     PORTB, PORTB4    ; Clear LED pin low
    mWAIT_MS 500             ; LED off delay
    rjmp    loop

.include "wait_ms_macro.asm"
```

Because our M_WAIT_MS macro calls the wait_ms_macro subroutine, the file that this subroutine is found must be included at the bottom of the file that the M_WAIT_MS macro is used in.
