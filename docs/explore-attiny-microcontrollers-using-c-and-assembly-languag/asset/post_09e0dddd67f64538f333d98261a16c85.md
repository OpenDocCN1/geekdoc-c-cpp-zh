
As can be seen in the previous code, the loop still executes in 7 clock cycles with the switch closed, so the timing of the loop remains the same. The only changes that occur is that the SBIC instruction at the top of the loop now skips over the CBI instruction that follows it, and the SBIS instruction does not skip the CBI instruction that follows it. Remember that this code sets up an internal pull-up resistor on pin PB3. When the switch attached to PB3 is open, a logic level 1 is read. When the switch is closed, a logic level 0 is read on pin PB3.

The total number of clock cycles that the code takes to execute from top to bottom is therefore 6 cycles above the loop, plus 7 cycles in the loop which totals 13 cycles. This takes 13µs to execute from the top of the code to the bottom of the loop on an ATtiny25/45/85, and 10.833µs on an ATtiny13(A), using the default clock frequencies.

If an SBIC or SBIS instruction is followed by a two-word or 32-bit wide instruction, then it takes 3 clock cycles to execute if the condition that is tested is true, in other words if it skips the instruction that follows it. For example, if the switch on PB3 is open and the SBIS instruction testing it is followed by an LDS instruction, we get the following.

```
sbis PINB, PINB3 ; 3 clock cycles, if skip over next instruction
lds r1, 0x60 ; 32-bit instruction
```

In the above code if the switch is open, a logic 1 is read in PINB3, in other words PINB3 is set, SBIS therefore skips the LDS instruction. In this case SBIS takes 3 clock cycles to execute.

If the switch is closed, the SBIS instruction does not skip the next instruction and takes only one clock cycle, as we saw in the read_switch_asm examples.

```
sbis PINB, PINB3 ; 1 clock cycle, next instruction is executed
lds r1, 0x60 ; 32-bit instruction
```

## The Simulation Cycle Counter and Stop Watch

When running the AVR simulator in Microchip Studio, a Cycle Counter and Stop Watch can be found near the top of the Processor Status window, as shown in Figure 10.1. For the Stop Watch to work properly, the frequency in the Frequency field above the stop watch must be set to the correct value for the ATtiny or other AVR part being used. This can be done by clicking on the value in the Frequency field to edit it. The default frequency value is 1MHz, shown as 1.000 MHz at the left of Figure 10.1, which is fine for an ATtiny25/45/85 with default settings, but must be changed to 1.2MHz for an ATtiny13(A), and is shown changed to 1.200 MHz at the right of Figure 10.1. The Cycle Counter keeps a running total of the number of clock cycles used up in the code being debugged. When stepping over an instruction that takes one clock cycle, one is added to the Cycle Counter total. When stepping over an instruction that takes two clock cycles to execute, two is added to the Cycle Counter total, and so on.

![](img/83ef13a6c66cc7882b2f357e97f451dc_210_0.png)

Figure 10.1: Cycle Counter and Frequency in the Processor Status Window

The Stop Watch field contains the number of clock cycles from the Cycle Counter multiplied by the period of one clock cycle. The Stop Watch field can not be edited during debugging, but the Cycle Counter field can be edited. This allows the Cycle Counter to be zeroed during debugging to measure the number of clock cycles that a certain part of code takes to execute. If the Cycle Counter is zeroed, then the Stop Watch is also automatically zeroed, because it is the product of the Cycle Counter value and the clock period.

Take note that the Cycle Counter and Stop Watch are only available in the simulator and not when using a hardware debugger, such as the Atmel-ICE.

## Simulator Cycle Counter Bug

At the time of writing, the simulator has a bug that causes it to skip counting the first clock cycle of a program. The Cycle Counter is therefore not updated with this first clock cycle. This does not occur with all AVR parts, but does occur with the ATtiny25/45/85 and ATtiny13(A). The result is that if the first instruction in a program takes one clock cycle to execute, then the Cycle Counter reads zero after stepping over it, as shown in Figure 10.2, where the first LDI instruction was stepped over that takes one clock cycle to execute. If the first instruction in a program takes two clock cycles to execute, the Cycle Counter is only updated by one, and so on. Note that the code in the following figures is code from the previous chapter that was modified to remove the first RJMP instruction and place the CSEG data below the main code. This is why the first instruction executed is the LDI instruction instead of an RJMP.

![](img/83ef13a6c66cc7882b2f357e97f451dc_211_0.png)

![](img/83ef13a6c66cc7882b2f357e97f451dc_211_1.png)

In Figure 10.3 it can be seen that after stepping over the second single cycle LDI instruction, the Cycle Counter now reads 1. It should read 2 at this stage because it should contain the sum of the cycles used by the instructions stepped over so far.

The bug occurs again if zeroing the Cycle Counter anywhere in the program. In this case, the first clock cycle of the next instruction executed after zeroing the Cycle Counter is not counted. The solution to this problem is not to zero the Cycle Counter, but rather to set it to a value of one. This can also be done when starting a debug session, just set the Cycle Counter to a value of one after using the Start Debugging and Break tool icon. After this, the Cycle Counter displays the correct number of instruction cycles when stepping over the rest of the instructions in a program.

## 10.2 Assembly Language Time Delay

In some of the example assembly language programs in this book we used a basic software time delay subroutine that uses a loop within a loop to generate a simple time delay. Timing for this subroutine was never calculated and it was used because it gave an acceptable time delay for the cases in which it was used. We now calculate the time delay of this subroutine, and then write a new subroutine that gives us a specific delay period.

### 10.2.1 Calculating a Software Delay Subroutine Time Delay

The code for the delay subroutine that we have been using is included below, with the number of clock cycles used by each instructions included.

```asm
; Delay subroutine
delay:
 ldi  r16, 0xff    ; 1 clock cycle
delloop1:
 ldi  r17, 0xff    ; 1 clock cycle
delloop2:
 dec  r17          ; 1 clock cycle
 brbc SREG_Z, delloop2 ; 1 or 2 clock cycles, if false (1), if true (2)
 dec  r16          ; 1 clock cycle
 brbc SREG_Z, delloop1 ; 1 or 2 clock cycles, if false (1), if true (2)
 ret             ; 4 clock cycles
```

Two methods of calculating the total number of clock cycles for this delay subroutine are 1) debug the code with the simulator selected in Microchip Studio and use the cycle counter to find the number of clock cycles used by the code, and 2) work out a mathematical formula to calculate the number of clock cycles the code uses. Once the number of clock cycles for the code is known, the time delay that it generates can be calculated by multiplying the number of clock cycles by the clock period, as we have already seen in some of the preceding examples of this chapter. We look at these two methods for calculating the number of clock cycles of the above code next.

Before continuing, it is worth mentioning that another method of calculating the delay subroutine is to use an instrument such as an oscilloscope to measure the on and off times of the LED when running the full code from the led_blink_asm project that uses the delay subroutine. With the default clock derived from the internal RC oscillator, this method is not accurate. This method is only useful if the AVR is clocked from a more accurate clock source, so it won't be considered further in this chapter.

### 10.2.1.1 Delay Subroutine Cycle Counter Measurement

Instead of writing a new program, simply open the led_blink_asm project in Microchip Studio, or copy the code from this project to the test_asm project so that we can use the simulator that is already set up in this project. If you do open the led_blink_asm project directly, then be sure to select the simulator instead of the hardware tool that you may have used with this project.

In the led_blink.asm code in Microchip Studio, insert a breakpoint on the first LDI instruction of the delay subroutine. This line of code looks as follows.

```
ldi r16, 0xff
```

Place a second breakpoint on the RET instruction at the end of the delay subroutine. Make sure that the simulator is selected as the tool for the project. Build the project and then click the Start Debugging toolbar icon, or press the F5 keyboard key to start the debugger.

After starting the debugger, the code executes and stops at the first breakpoint and the Cycle Counter in the Processor Status window displays a value of 6. This value is actually incorrect because of the cycle counter bug already described in this chapter — the cycle counter value should be 7 at this stage in the program execution.

In order to measure the number of cycles that the delay subroutine takes, we need to reset the cycle counter value. Because of the bug, we must reset the Cycle Counter to 1 instead of to 0 in order to properly measure the number of cycles used by the delay subroutine. Click in the field containing 6 next to the Cycle Counter in the Processor Status window. Edit this number by changing it to 1 and then hit the Enter keyboard key. Click somewhere else in the Processor Status window, for example in the R00 field, to move the focus off the Cycle Counter value. This makes the value easier to read.
