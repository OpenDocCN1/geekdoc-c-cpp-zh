```asm
; Millisecond delay subroutine - delay time set by MS_TIME_DEL
; F_CPU must be set to the frequency that the AVR is operating at

.if (F_CPU > 20000000)
.error "F_CPU too high for wait_ms subroutine. Maximum 20MHz"
.elif (F_CPU < 210000)
.error "F_CPU too low for wait_ms subroutine. Minimum 210kHz"
.elif (MS_TIME_DEL < 1)
.error "MS_TIME_DEL too low for wait_ms subroutine. Minimum 1ms"
.elif (((((MS_TIME_DEL * 1000) - 10) / 10) > 0xFFFFFFF)
// Maximum MS_TIME_DEL is 2,147,483s @ 20MHz and 204,522,525 @ 210kHz
// Maximum MS_TIME_DEL calculated by: (10,000 * 2^32) / F_CPU
.error "MS_TIME_DEL too big for wait_ms subroutine."
.endif

.equ WAIT_MS_CYCLES = ((((F_CPU * MS_TIME_DEL) / 1000) - 10) / 10)

wait_ms:
ldi R16, low (WAIT_MS_CYCLES)
ldi R17, byte2(WAIT_MS_CYCLES)
ldi R18, byte3(WAIT_MS_CYCLES)
ldi R19, byte4(WAIT_MS_CYCLES)

wait_ms_loop:
subi R16, 1
sbci R17, 0
sbci R18, 0
sbci R19, 0
mov R20, R16
or R20, R17
or R20, R18
or R20, R19
brbc SREG_Z, wait_ms_loop
nop
nop
ret
```

In the above code, tests for high and low limits are done using the .if directive, followed by a number of .elif directives. A .elif directive means “else if”. From the top of the code, the tests are 1) if F_CPU is greater than 20MHz, flag an error, 2) else if F_CPU is less than 210kHz, flag an error, 3) else if MS_TIME_DEL is less than 1ms, flag an error, 4) else if the WAIT_MS_CYCLES calculation results in a too big value, flag an error. Because the .elif directive is used in this way, the first error that is found will stop the build process. After the error is fixed, the programmer can build the project again. If any other error is present, it will be caught after the second build of the project, and so on until all the limit errors have been corrected.

The wait_ms subroutine from the wait_ms.asm file can be tested using the following code from main.asm of the project. A number of test values have been placed in the code to test the upper and lower limits by uncommenting these values. The maximum and minimum F_CPU values can be used in conjunction with various MS_TIME_DEL values. Only one value of each type can be uncommented at a time, so be sure to comment out the current value when testing a new value.

```asm
main.asm : main.asm

.equ  F_CPU   = 20000000  ; Maximum frequency
.equ  F_CPU   = 20000001  ; Above maximum frequency
.equ  F_CPU   = 210000    ; Minimum frequency
.equ  F_CPU   = 209999    ; Below minimum frequency
.equ  MS_TIME_DEL = 1     ; Below minimum millisecond value
.equ  MS_TIME_DEL = 0     ; Millisecond value
.equ  MS_TIME_DEL = 2147483 ; Upper millisecond limit @ 20MHz
.equ  MS_TIME_DEL = 2147484 ; Upper millisecond limit + 1 @ 20MHz
.equ  MS_TIME_DEL = 20452252 ; Upper millisecond limit @ 210kHz
.equ  MS_TIME_DEL = 20452253 ; Upper millisecond limit + 1 @ 210kHz
.equ  MS_TIME_DEL = 0x4522523 ; Highest positive value in ms
.equ  MS_TIME_DEL = 0x7FFFFFFF ; Highest positive value in ms
.equ  MS_TIME_DEL = 0x80000000 ; Negative value after 1 added to above
.equ  MS_TIME_DEL = 0xFFFFFFFF ; -1
```

Test the code using the values found at the top of the above listing, and also try some of your own values. Remember to save the file after making changes and then build the project to make sure that an error is flagged when expected, and not flagged when expected. Testing the upper and lower F_CPU values with a MS_TIME_DEL of 0 results in an error in both cases, as expected. Using an F_CPU value above 20MHz or below 210kHz also flags an error. Using one plus the maximum MS_TIME_DEL for 20MHz with an F_CPU of 20MHz results in an error, but using the same MS_TIME_DEL value with an F_CPU of 20kHz does not result in an error because at lower the time delay can be much bigger. ## 10.2.4 Passing a Value to a Subroutine

The wait_ms subroutine that we developed in the previous section is more useful than the fixed 1 second subroutine before it, but it still has limitations. The time delay that it is set at is fixed in the code once set. Every time that it is used in the code, it delays for the same period.

It does not take too much effort to modify the wait_ms subroutine code so that it can be passed a millisecond delay value, that it will then delay for. Each time that it is used in the code, it can be passed a different value and will then delay for that time.

### 10.2.4.1 Simplest Way to Pass a Value

The mechanism for passing a value to a subroutine is to put the value to pass to it in a known location, either in memory or in a register. A modified version of the wait_ms_asm project called wait_pass_val.asm follows, that shows the simplest method of passing a value to a subroutine.

```asm
wait_pass_val.asm : wait_pass_val.asm

wait_pass_val:
  subi  R16, 1
  sbci  R17, 0
  sbci  R18, 0
  sbci  R19, 0
  mov   R20, R16
  or    R20, R17
  or    R20, R18
  or    R20, R19
  brbc  SREG_Z, wait_pass_val
  nop
  nop
  nop
  ret
```

In the above code, the wait_ms subroutine has been modified. Firstly, it has been renamed to wait_pass_val. The code that was added to test the limits of values used with the subroutine have been removed simply for clarity, as we are looking at the method used for passing a value to this subroutine. Where previously the registers that contained the number of cycles to use up in the subroutine were loaded with values at the top of the subroutine, they have now been removed. By removing the registers, a single label is needed to jump to, which also happens to be the entry point of the subroutine. The idea of removing the register loading from the subroutine is to load the values in the code before the subroutine is called. In this way, a new value can be passed to the subroutine each time that it is called. This is shown in the main.asm listing of the wait_pass_val_asm project below.

```asm
wait_pass_val.asm : main.asm

.equ	F_CPU		 = 1000000
.equ	MS_DELAY_1	 = (((F_CPU * 200) / 1000) - 10) / 10 ; 200ms
.equ	MS_DELAY_2	 = (((F_CPU * 500) / 1000) - 10) / 10 ; 500ms

start:	sbi	DDRB, DDB4		 ; Set pin PB4 as output

loop:	sbi	PORTB, PORTB4		 ; Set LED pin high
	ldi	R16, low (MS_DELAY_1)	 ; Pass 32-bit value
	ldi	R17, byte2(MS_DELAY_1)	 ; to the wait_pass_val
	ldi	R18, byte3(MS_DELAY_1)	 ; subroutine
	ldi	R19, byte4(MS_DELAY_1)	 ;
	rcall	wait_pass_val		 ; LED on delay
	cbi	PORTB, PORTB4		 ; Clear LED pin low
	ldi	R16, low (MS_DELAY_2)	 ; Pass 32-bit value
	ldi	R17, byte2(MS_DELAY_2)	 ; to the wait_pass_val
	ldi	R18, byte3(MS_DELAY_2)	 ; subroutine
	ldi	R19, byte4(MS_DELAY_2)	 ;
	rcall	wait_pass_val		 ; LED off delay
	rjmp	loop

.include "wait_pass_val.asm"
```

At the top of the code, two names are equated with values that are worked out using the formula that we are now familiar with. The first value works out the number of cycles for the subroutine to delay for to generate a 200ms delay, and the second for a 500ms delay. These values are then loaded to registers R16 to R19 before wait_pass_val is called. In this way, the values have been passed to the wait_pass_val subroutine because the subroutine uses these values to generate the time delays.

Note that in the above code, if measuring the number of cycles used by the subroutine in the simulator, the cycles must be measured starting from where the first part of the 32-bit number is loaded to R16. The reason for this is that the formula for calculating the number of cycles to generate has not been modified to remove the cycles used to pass the value to the subroutine. In any case, this may be the behavior we prefer, as these instructions still use up cycles that can be considered part of the delay that we are generating.
