
wait_ms_macro:
    subi    R16, 1
    sbci    R17, 0
    sbci    R18, 0
    sbci    R19, 0
    mov     R20, R16
    or      R20, R17
    or      R20, R18
    or      R20, R19
    breq    SREG_Z, wait_ms_macro
    ret     ; 4 clock cycles, but is effectively 3 clock cycles

In the above code, the only instruction that falls outside of the loop is the RET instruction. This instruction executes in 4 clock cycles on an AVR CPU that has a PC that is less than 22 bits wide. BRBC uses up 2 clock cycles, except for the last time it is executed, when it uses up 1 clock cycle. Because of this, one clock cycle is borrowed from the clock cycles used up outside the loop to effectively make the last time that BRBC is executed also use up 2 clock cycles. For this reason, we subtract 1 clock cycle from RET, which then effectively uses up 3 clock cycles instead of 4. Add these 3 clock cycles to the 27 clock cycles added up from the body of the macro, and we get a total of 30 clock cycles used up outside the loop of wait_ms_macro. In the previous project code, only 10 clock cycles were used up outside the loop of the delay subroutine. Because we did not simplify the equation that calculates the number of loops through the delay subroutine, we can directly replace the 10 cycles in the calculation with 30, as shown in the following code.

```
ldi    R16, low (((((F_CPU * (@0) / 1000) - 30) / 10))
```

As the clock cycles outside the loop work out to 30, which is a multiple of 10, there is no need to keep the NOP instructions in the code that we previously added. These NOP instructions were previously added to make the clock cycles outside the loop add up to a value of 10.

Because a value in the above calculation changed, we need to recalculate the minimum CPU frequency that our time delay macro and subroutine will work with. We use the formula below, as was previously used.

![](img/83ef13a6c66cc7882b2f357e97f451dc_256_0.png)

We know that the minimum value that t_ms can be is 1ms. The minimum value that C_T can be is if we make one pass through the delay subroutine. This value is now 40 clock cycles made up of 30 cycles outside the subroutine loop plus 10 cycles from 1 pass through the loop. Substituting these values into the formula gives us the following.

f_{CPU} = \frac{10000(40+1)}{1}
= 410000

The value from the calculation works out to 410kHz, which is used in the code at the top of the macro that tests for F_CPU limits, as follows.

```
...
.elif (F_CPU < 410000)
    .error "F_CPU too low for M_WAIT_MS macro. Minimum 410kHz"
.elif (@0 < 1)
    .error "Time delay too low for M_WAIT_MS macro. Minimum 1ms"
...
```

Looking back at main.asm, repeated below, we can see that wait_ms_macro.inc is included at the top of the code in which the macro is used. This makes the macro available to us in the main.asm file. Although F_CPU is used in wait_ms_macro.inc, it is defined below where wait_ms_macro.inc is included. The reason that this does not cause an error is because the assembler is a multi-pass assembler. This means that on the first pass through the file, the assembler builds up a symbol table. In this way it knows about F_CPU when it passes through the source code again. This is usually referred to as forward referencing.

```
wait_ms_macro.asm : main.asm

.include "wait_ms_macro.inc"
.equ    F_CPU    = 1000000

start:
    sbi     DDRB, DDB4        ; Set pin PB4 as output

loop:
    sbi     PORTB, PORTB4    ; Set LED pin high
    mWAIT_MS 200             ; LED on delay
    cbi     PORTB, PORTB4    ; Clear LED pin low
    mWAIT_MS 500             ; LED off delay
    rjmp    loop

.include "wait_ms_macro.asm"
```

Because our M_WAIT_MS macro calls the wait_ms_macro subroutine, the file that this subroutine is found must be included at the bottom of the file that the M_WAIT_MS macro is used in.

When a macro is used in a program, the macro is expanded in the code where it is used. Macro expansion means that the code that makes up the macro is effectively pasted into the place where the macro is used. The following code shows how the macros used in the previous code were expanded.

```
00000000 sbi DDRB, DDB4 ; Set pin PB4 as output
loop:
00000001 sbi PORTB, PORTB4 ; Set LED pin high
M_WAIT_MS 200 ; LED on delay
00000002 push R16
00000003 push R17
00000004 push R18
00000005 push R19
00000006 push R20
00000007 ldi R16, 0x1D
00000008 ldi R17, 0x4E
00000009 ldi R18, 0x00
0000000A ldi R19, 0x00
0000000B rcall wait_ms_macro
0000000C pop R20
0000000D pop R19
0000000E pop R18
0000000F pop R17
00000010 pop R16
00000011 cbi PORTB, PORTB4 ; Clear LED pin low

00000015 push R19
00000016 push R20

```

As can be seen in the above listing, the macros were expanded in the two places that they were used. The code from the macro is essentially pasted into the two places that the macro was used. This code includes the pushing and popping of the registers used, the LDI instructions used to load the delay count value to the registers, and the call to the wait_ms_macro subroutine. Each time that the macro is used, the full macro code is substituted into its place. Only one instance of the wait_ms_macro subroutine exists which is called by both expanded macros. The code for the wait_ms_macro subroutine is shown in the following listing. By making a call to wait_ms_macro, instead of including this code directly in the macro, we save some space in memory. If the wait_ms_macro code were placed in the macro, rather than calling it as a subroutine, it would be expanded fully each time that it is used. This would use up extra memory.

```
wait_ms_macro:
00000022 subi R16, 1
00000023 sbci R17, 0
00000024 sbci R18, 0
00000025 sbci R19, 0
00000026 mov R20, R16
00000027 or R20, R17
00000028 or R20, R18
00000029 or R20, R19
0000002A breq SREG_Z, wait_ms_macro
0000002B ret
```

The reason that we can't put the PUSH and POP instructions in the wait_ms_macro subroutine is because the pushed registers must be loaded with values in the macro, otherwise we would just have another fixed time subroutine. This means that these registers are modified in the macro, so must be pushed before modifying.

It may look like the POP instructions could be put into the subroutine instead of leaving them in the macro, however this is not possible. What happens is the registers are first pushed onto the stack, then modified by loading the value to pass to the subroutine. When the subroutine is called after this, the return address for the subroutine is automatically pushed onto the stack. If we then tried to pop the registers before returning from the subroutine, we would actually pop the return address of the subroutine first because it is the last thing pushed onto the stack. When the subroutine returns and automatically pops its return address from the stack, it would actually be popping the values from the first two registers that were pushed. Obviously this would cause the subroutine to return to the wrong address, causing the program to malfunction.

Finally note that the M_WAIT_MS macro produces a cycle accurate delay for values that are multiples of 10. This can again be checked using the simulator in Microchip Studio.

## 10.3 Calling an Assembly Subroutine from C Code

It is easy to call an assembly language subroutine from a C code program. The most important information to have when calling a subroutine from C code is the registers used to pass values to a subroutine and registers used to return values from a subroutine. Register usage by C compilers may be different for different compilers, even for the same microcontroller. This information is available for the avr-gcc compiler in an application note called Atmel AT1886: Mixing Assembly and C with AVRGCC available from: ww1.microchip.com/downloads/en/Appnotes/doc4255.pdf

In the example that follows in the next section, an assembly language subroutine is called from C code and passed a 32-bit value. In the section after the next section, an assembly language subroutine called from C code returns a value.

### 10.3.1 Passing a Value to an Assembly Subroutine from C

The following subroutine code is taken from the wait_ms_macro_asm project in section 10.2.4.2 of this chapter. Some modifications have been done to the code to make a C program able to call the assembly language subroutine. The subroutine is the code that we put into a macro and generates a variable millisecond time delay. In the modified code the subroutine is called wait_ms because this name is short and descriptive. Don’t confuse this subroutine with an earlier subroutine that had the same name. The project consists of three files. Create a new GCC C Executable Project in Microchip Studio called wait_ms.c. Replace the code in main.c of the project with the following code.

```
wait_ms_c : main.c

#define F_CPU 12000000

#include <avr/io.h>
#include "wait_ms.h"

int main(void)
{
    DDRB |= (1 << DDB4);    // Set up pin PB4 as an output

    while (1)
    {
        PORTB |= (1 << PORTB4);    // Set pin high (LED on)
        wait_ms(WAIT_MS_TIME(200));    // LED on delay
        PORTB &= ~(1 << PORTB4);    // Set pin low (LED off)
        wait_ms(WAIT_MS_TIME(1000));    // LED off delay
    }
}
```
