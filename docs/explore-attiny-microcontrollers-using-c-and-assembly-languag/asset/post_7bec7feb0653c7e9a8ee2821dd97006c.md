## 9.3.1 Specifying Code and Data Locations

The AVRASM2 Assembler program supports a combination of directives that allow code and data to be placed at the desired addresses and in the specified memory type. These are the ORG, CSEG, DSEG and ESEG directives, described further in the subsections that follow.

### 9.3.1.1 ORG Assembler Directive

ORG is an assembler directive that is short for *origin* and is used to set the program origin or start address of a section of memory. ORG can be written in upper case or lower case letters, but must start with a dot when used in a program. .ORG and .org both work. The simple code snippet below shows how ORG can be used to set the program’s start address.

```
.ORG 0
sbi DDRB, DDB4    ; LED on pin PB4
sbi PORTB, PORTB4 ; Switch LED on
loop:
rjmp loop         ; Infinite loop
```

In the code snippet .ORG is set to 0 which sets the start address of the program code to 0. Code is placed at address 0 by default, which is why none of the programs so far have needed to use the ORG directive.

As another example, we can put our code at address 0x40, leaving the Flash memory above it free. We do need to put an RJMP instruction at address 0 that jumps to our program code at address 0x40 because at reset, code starts executing at address 0. The following code snippet shows how this is done.

```
.ORG  0
rjmp   0x48

.ORG  0x40
sbi    DDRB, DDB4    ; LED on pin PB4
sbi    PORTB, PORTB4 ; Switch LED on

loop:
rjmp   loop
```

Enter the above code in the test_asm project that we used previously. Run it in the debugger using either the simulator, or real hardware with a USB debugger. Start debugging and break, then open the Disassembly window (Alt + 8). Notice in the Disassembly window that the first RJMP instruction is visible at the very top of the window at address 0. After stepping over the RJMP instruction using the F10 key, program execution continues at address 0x40, and 0x40 can be seen in the program counter in the Processor Status window. Flash memory from address 0x01 to 0x3F is unused.

In the above code snippet, the first .ORG 0 can be left off, as 0 is the default start address of code in an assembly language program. Leaving .ORG 0 in is optional, but does inform anyone reading the code that the programmer intentionally wrote code that follows to start at address 0. Notice that the RJMP instruction jumps to the specified address in hexadecimal format. This can be done instead of using a label. .ORG 0x40 specifies that the code following it will be placed in memory starting from address 0x40.

ORG becomes more useful when used in conjunction with segment directives (CSEG, DSEG and ESEG). Segment directives are used to specify into which memory either code or data is to be placed. Using ORG with segment directives allows code and data to be placed at specific addresses in the desired memory. There are three types of segment directives in AVR assembly language, namely CSEG (Code Segment), DSEG (Data Segment) and ESEG (EEPROM Segment). Anything placed in a CSEG will be placed in Flash memory and could be code or data. Data placed in a DSEG will be put into SRAM data memory. An ESEG holds data that is placed in the EEPROM of the AVR.

### 9.3.1.2 CSEG Code Segment Directive

CSEG is the default segment type, and defines the start of a code segment in Flash memory. As can be seen in the code snippet that follows, the CSEG directive does not have any parameters that follow it.

```
.CSEG
.ORG  0
sbi   DDRB, DDB4
sbi   PORTB, PORTB4
loop:
rjmp  loop
```

In the above code snippet, the ORG directive is used in conjunction with the CSEG directive which tells the assembler program to put the code that follows into Flash program memory starting at address 0. Of course both of these are the default settings of an assembly language program, so they could be left off in the above example.

ORG and CSEG directives become more useful when placing code at a location other than address 0, or if data from other segments is placed above program code. An assembly language program can consist of more than one code segment, each segment specified by its own CSEG directive and used either with or without the ORG directive.

### 9.3.1.3 DSEG Data Segment and BYTE Directives

DSEG defines the start of a data segment that will be placed in the SRAM of the AVR microcontroller. DSEG is usually followed by a label so that data can easily be accessed using the label name in a program. DSEG is also usually used in combination with the BYTE directive, which reserves bytes in memory. The data segment can not automatically be initialized with values, but rather reserves bytes of memory to be accessed by code.

In the code snippet that follows, a byte of memory is reserved in SRAM using the DSEG and BYTE directives. This effectively creates a named variable in SRAM that can be used in the assembly language code that follows, which is similar to declaring a variable in the C language.

```
.DSEG
count: .BYTE 1
.CSEG
ldi   r16, 0xAB
sts   count, r16
loop:
rjmp  loop
```

At the start of the code in the listing, the DSEG directive is used to define the start of a data segment. Below this, the BYTE directive reserves one byte of SRAM by specifying 1 as operand. The BYTE directive is preceded by the count label, which allows this one byte of data in SRAM to be accessed by this name in the code that follows.

After the DSEG data segment, the CSEG directive specifies that code to be placed in Flash memory follows. The code first loads 0xAB to R16 using LDI. STS is then used to write the value that is in R16 into the count variable, or in other words, load the value in R16 into the byte labeled count which is found in SRAM. Refer back to the code snippet in section 5.4.1 of Chapter 5 where the STS instruction is used to load a value from R16 to address 0x60. We are now doing the same thing, but using a named variable. As with the code snippet from Chapter 5, we can also use the LDS instruction to copy the value from SRAM into a register. For example, to load the value in count to R0, we can do the following.

```
lds r16, count
```

Run the previous code snippet in the simulator, just as we did in section 5.4.2 of Chapter 5. Select data IRAM in the Memory window to see the value from R16 being written to the SRAM when stepping over the STS instruction. It so happens that if an address for the reserved count byte in SRAM is not specified using the ORG directive, it is placed at the beginning of SRAM, at address 0x60. This address location should be in view after selecting data IRAM as the memory to view in the debugger, if it is not in view, scroll until it is. Add the above line of code to the program below the STS instruction to see the count value from SRAM being written to register R0.

As can be seen in this example, it is much easier to let the Assembler reserve memory for us, and use a label as a name for the memory, rather than access the memory by address and have to keep track of which addresses we are using. This is especially true when assembly language programs start getting bigger.

### 9.3.1.4 ESEG EEPROM Segment Directive

ESEG is a directive that defines the start of an EEPROM segment. Data placed in an ESEG ends up in the internal EEPROM of an AVR.

## 9.3.2 Reserving Memory

There are several assembler directives for reserving memory that can be used in AVR assembly language programs. We have already seen one of these directives, the BYTE directive, used in conjunction with DSEG in section 9.3.1.3. The subsections that follow summarize the assembler directives for reserving memory in order to show that various different directives are available for this purpose.

### 9.3.2.1 BYTE

BYTE reserves one or more bytes in SRAM or EEPROM, and therefore is used in conjunction with the DSEG and ESEG directives. We have already seen an example of how to reserve one byte of SRAM memory in section 9.3.1.3.

### 9.3.2.2 DB – Define Constant Byte

DB defines one or more constant bytes in Flash program memory (CSEG) or in EEPROM (ESEG).

## Modified Harvard Architecture

Although the Microchip/Atmel documentation states that AVR microcontrollers have a Harvard architecture, AVRs actually have a modified Harvard architecture. While a Harvard architecture, as shown in Figure 6.5 of section 6.3 in Chapter 6 has completely separate buses for program and data memory, AVRs can actually store constant data in the Flash program memory and read that data in a program. This is because of its modified Harvard architecture.
