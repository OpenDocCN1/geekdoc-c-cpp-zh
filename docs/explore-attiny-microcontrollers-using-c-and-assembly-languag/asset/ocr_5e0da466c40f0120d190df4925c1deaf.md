Only the minimum F_CPU and minimum MS_TIME_DEL need to be checked in addition to the maximum number of cycles calculated. The reason for this is because if F_CPU and/or MS_TIME_DEL are too big, then the maximum number of cycles calculated will be too high and will be detected by the previous code that we modified to test whether the calculated value is bigger than 0xFFFFFFFF. By testing for a maximum F_CPU we give the user of our subroutine more clues as to what the problem may be if a too big value is assigned to these items which triggers an error.

We must test that the value of MS_TIME_DEL is at least 1. MS_TIME_DEL can be higher than the value we calculated using 20MHz for F_CPU, if a lower clock frequency is used. The highest value that MS_TIME_DEL can be is at the lowest F_CPU. This is calculated as follows using 210KHz for F_CPU and 2^22 - 1 for C_T.

```
t_ms = \frac{10000(C_T+1)}{f_{CPU}}
= \frac{10000(2^{32}-1+1)}{210 \times 10^3}
= 204,522,252
```

The maximum value calculated for t_ms at 20MHz is useful when testing the code. Although the wait_ms subroutine can be used with frequencies higher than 20MHz, it was designed for use on ATtiny devices that have the AVRe CPU and instruction timing. If the subroutine is to be used with other AVR devices, it may need to be modified by increasing the 20MHz frequency limit and selectively add clock cycles to the subroutine, depending on the AVR device used. For this exercise, we don't do these modifications and do check for a maximum CPU frequency of 20MHz. To summarize, we now have the following.

+   - Check that the provided F_CPU value does not exceed 20MHz: this gives the user a clue as to which parameter is exceeded should an error message trigger. It also clamps the input value that is to be fed into the total clock cycle formula.
+   - Test for F_CPU lower than 210kHz.
+   - Test for MS_TIME_DEL less than 1ms.
+   - Test that WAIT_MS_CYCLES does not exceed 2^25 - 1: this catches too high MS_TIME_DEL values.
