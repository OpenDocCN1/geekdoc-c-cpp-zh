
After discovering the truncation limits on numbers, the next obvious step is to test whether these 32-bit numbers are also limited by being signed numbers rather than unsigned numbers.

```
.equ NUM1 = 0xFFFFFFFF
.equ NUM2 = 0x00000001

.if (NUM1 < NUM2)
.warning "NUM1 is less than NUM2."
.endif

.if (0xFFFFFFFF < 0x00000001)
.warning "0xFFFFFFFF is less than 0x00000001."
.endif
```

In the above code, NUM1 has a value of 0xFFFFFFFF which is 4,294,967,295 or 2^32 – 1 if the number is treated as an unsigned 32-bit integer. If instead NUM1 is treated as a signed 32-bit integer, then the value 0xFFFFFFFF assigned to it gives it a value of –1 in 2’s complement format. When the above code is inserted into the source code of a Microchip Studio AVR assembly language project, and the project is built, the first comparison evaluates to true, and the warning message appears at the bottom of Microchip Studio. Note that this comparison uses the less-than operator (<) to determine if NUM1 is less than NUM2. NUM1 can only be less than NUM2 if NUM1 is 0 or a negative number. This proves that the equated numbers are treated as signed 32-bit integers, rather than unsigned 32-bit integers. In the second comparison in the above code, the same values that were assigned to NUM1 and NUM2 are directly compared. This comparison results in false, which means that the warning message does not appear at the bottom of the Microchip Studio window for the second comparison.

A final test for signed numbers is shown in the following code.

```
.equ NUM1 = 0x7FFFFFFF
.equ NUM2 = 0x00000001

.if (NUM1 < NUM2)
.warning "NUM1 is less than NUM2"
.endif
```

In the above code, NUM1 is assigned a value of 0x7FFFFFFF, which is the maximum positive value that a signed 32-bit number can have. In this number, all bits are set, except for the most significant bit, which is used as the sign bit. Because of this, the number is effectively a 31-bit number because the most significant bit is not used. The maximum value of this number is therefore calculated as 2^31 – 1 which is 2,147,483,647 or 0x7FFFFFFF. In the code, the warning message is not triggered because this positive value is bigger than the value of NUM2, which is 1. If a value of 0x80000000 is used for NUM1, by commenting out the first line of code and uncommenting the second line of code, then the warning message is triggered. Adding 1 to 0x7FFFFFFF gives us a value of 0x80000000. This 32-bit number has its most significant bit set, so is a negative number if it is treated as a 32-bit 2’s complement signed number. It has a decimal value of –2,147,483,648, and is therefore a negative number with a value less than 1, which is the value of NUM2 in the code. This is the reason why the warning message is triggered with this value.

## Solution to Flagging Out of Range Upper Values

Now that we understand the integer size limitations of the assembler program, we can devise a solution for flagging out of range values used with the time delay subroutine. One way to do this is to test the value of MS_TIME_DEL to make sure that it is less than the maximum value of 2,147,483 that we calculated. This value is much less than the maximum positive value that a 32-bit signed integer can hold, so it will never be treated as a negative number. Even values much bigger than 2,147,483 will not be treated as negative numbers, so if the user tries to use a MS_TIME_DEL of even 1000 times this value, it can be tested with no side effects. The only problem with this solution is the maximum value of MS_TIME_DEL was calculated using a 20MHz F_CPU. This means that if used with say a 1MHz F_CPU, the value of MS_TIME_DEL will also be limited to 2,147,483, whereas in reality MS_TIME_DEL would be able to be much higher when using a 1MHz F_CPU.

Another solution is to take advantage of the fact that the assembler program does not treat values that are not assigned a name using .equ or #define as 32-bit signed integers. The following code, from the top of the wait_ms.asm file, shows that directly placing the calculation into the comparison, circumvents the result of the calculation becoming a 32-bit signed integer. The value that is 2^32 – 1, or 0xFFFFFFFF is also used directly in the comparison.

```
; Millisecond delay subroutine - time set by MS_TIME_DEL
.if ((((F_CPU * MS_TIME_DEL) / 1000) - 10) / 10) > 0xFFFFFFFF)
.error "F_CPU MS_TIME_DEL combination out of range in wait_ms subroutine."
.endif
.equ WAIT_MS_CYCLES = (((F_CPU * MS_TIME_DEL / 1000) - 10) / 10)
```

## Flagging Out of Range High and Low Values

It is necessary to detect the minimum MS_TIME_DEL value and minimum F_CPU value in addition to the testing the result of the WAIT_MS_CYCLES calculation. We know that the subroutine is limited to the following values.

- **F_CPU maximum value of 20MHz, chosen as maximum ATtiny frequency.**
- **MS_TIME_DEL maximum value calculated as 2,147,483ms @ 20MHz.**
- **MS_TIME_DEL minimum value of 1ms. Anything less than 1ms is meaningless. Testing the code with MS_TIME_DEL set to 1 does produce a 1ms time delay.**

The only thing that we need to calculate is the minimum F_CPU value that can be used with the wait_ms subroutine. We arrived at the following intermediate formula during the manipulation of the formula previously.

```
f_{CPU} \times t_{ms} = 10000(C_T+1)
```

This formula can easily be manipulated to calculate the value of f_cpu by dividing each side by t_ms to get rid of t_ms on the left. The result is the following.

```
f_{CPU} = \frac{10000(C_T+1)}{t_{ms}}
```

We know that the minimum value that t_ms can be is 1ms. The minimum value that C_T can be is if we make one pass through the wait_ms subroutine. This value is 20 clock cycles. Substituting these values into the above formula gives us the following.

```
f_{CPU} = \frac{10000(20+1)}{1}
= 210000
```

The calculated value of 210,000 is 210kHz. We now have the following to work with.

- F_CPU max 20MHz
- F_CPU min 210kHz
- MS_TIME_DEL max 2,147,483ms @20MHz
- MS_TIME_DEL min 1ms

Only the minimum F_CPU and minimum MS_TIME_DEL need to be checked in addition to the maximum number of cycles calculated. The reason for this is because if F_CPU and/or MS_TIME_DEL are too big, then the maximum number of cycles calculated will be too high and will be detected by the previous code that we modified to test whether the calculated value is bigger than 0xFFFFFFFF. By testing for a maximum F_CPU we give the user of our subroutine more clues as to what the problem may be if a too big value is assigned to these items which triggers an error.

We must test that the value of MS_TIME_DEL is at least 1. MS_TIME_DEL can be higher than the value we calculated using 20MHz for F_CPU, if a lower clock frequency is used. The highest value that MS_TIME_DEL can be is at the lowest F_CPU. This is calculated as follows using 210KHz for F_CPU and 2^22 - 1 for C_T.

```
t_ms = \frac{10000(C_T+1)}{f_{CPU}}
= \frac{10000(2^{32}-1+1)}{210 \times 10^3}
= 204,522,252
```

The maximum value calculated for t_ms at 20MHz is useful when testing the code. Although the wait_ms subroutine can be used with frequencies higher than 20MHz, it was designed for use on ATtiny devices that have the AVRe CPU and instruction timing. If the subroutine is to be used with other AVR devices, it may need to be modified by increasing the 20MHz frequency limit and selectively add clock cycles to the subroutine, depending on the AVR device used. For this exercise, we don't do these modifications and do check for a maximum CPU frequency of 20MHz. To summarize, we now have the following.

- Check that the provided F_CPU value does not exceed 20MHz: this gives the user a clue as to which parameter is exceeded should an error message trigger. It also clamps the input value that is to be fed into the total clock cycle formula.
- Test for F_CPU lower than 210kHz.
- Test for MS_TIME_DEL less than 1ms.
- Test that WAIT_MS_CYCLES does not exceed 2^25 - 1: this catches too high MS_TIME_DEL values.
