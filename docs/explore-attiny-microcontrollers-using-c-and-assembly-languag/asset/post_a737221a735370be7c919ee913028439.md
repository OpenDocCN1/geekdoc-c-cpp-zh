
2,147,484 and substitute it back into the Cr formula, we get a value of 4,294,967,999, which is 704 bigger than 2^32 - 1. We can therefore use a value of 20MHz and 2,147,483 milliseconds with our wait_ms subroutine, but if a value of 20MHz and 2,147,484 or bigger is used, our wait_ms subroutine will fail.

## Posing Value Limits in Assembly Language

A common way of posing limits on fixed values used in assembly language code is to use assembler directives to detect the limits and generate an error or warning, should the limits be out of range. The following code added to the top of the wait_ms.asm file from the wait_ms_asm project shows how this is done.

```
wait_ms.asm : wait_ms.asm - top part of code
; Millisecond delay subroutine - time set by MS_TIME_DEL
.equ WAIT_MS_CYCLES = (((F_CPU * MS_TIME_DEL) / 1000) - 10) / 10
.if (WAIT_MS_CYCLES > (exp2(32) - 1))
    .error "F_CPU MS_TIME_DEL combination out of range in wait_ms subroutine."
.endif
wait_ms:
ldi R16, low (WAIT_MS_CYCLES)
ldi R17, byte2(WAIT_MS_CYCLES)
ldi R18, byte3(WAIT_MS_CYCLES)
ldi R19, byte4(WAIT_MS_CYCLES)
...
...
```

The first modification made at the top of the wait_ms.asm code was to give a name to the formula that calculates the number of cycles for the wait_ms function to generate. This name is WAIT_MS_CYCLES and is equated at the top of the code as shown below.

```
.equ WAIT_MS_CYCLES = (((F_CPU * MS_TIME_DEL) / 1000) - 10) / 10
```

This simply means that whenever WAIT_MS_CYCLES is used, the result of the formula is substituted. Because of this, WAIT_MS_CYCLES is put at the top of the wait_ms subroutine in every place that the formula was previously placed, as follows.

```
wait_ms:
ldi R16, low (WAIT_MS_CYCLES)
ldi R17, byte2(WAIT_MS_CYCLES)
ldi R18, byte3(WAIT_MS_CYCLES)
ldi R19, byte4(WAIT_MS_CYCLES)
```

Now that the result of the formula is easily available as WAIT_MS_CYCLES, assembler directives are used to detect if this value is out of range or not. This is done with the following code.

```
.if (WAIT_MS_CYCLES > (exp2(32) - 1))
    .error "F_CPU MS_TIME_DEL combination out of range in wait_ms subroutine."
.endif
```

In the above code, the .if directive is used to determine if the 32-bit value calculated by the formula and equated to WAIT_MS_CYCLES is within range. We know that the maximum value that a 32-bit number can be is 2^32 - 1. The AVR assembler program supports a function called exp2() that calculates 2 to the power of the number passed to it. In the code, exp2() is used to calculated the biggest 32-bit value by passing it 32. One is then subtracted from the result which gives us the highest number that a 32-bit number can hold. In other words, the following code calculates 2^32 - 1.

```
(exp2(32) - 1)
```

Within the brackets after the .if directive, the greater-than operator (>) is used to determine if the value of WAIT_MS_CYCLES is bigger than the result of the above calculation, as shown below.

```
.if (WAIT_MS_CYCLES > (exp2(32) - 1))
```

In the above line of code, if WAIT_MS_CYCLES is less than 2^32 - 1, then the code between the .if directive and the closing .endif directive is ignored. On the other hand, if the value of WAIT_MS_CYCLES is bigger than 2^32 - 1, then the code between the .if directive and the .endif directive is executed. This code contains the .error directive followed by a text string. The .error directive flags an error in Microchip Studio and prints the text string that follows the .error directive. This message is our own message that describes what the problem is. As can be seen, the message states that the F_CPU MS_TIME_DEL combination is out of range in the wait_ms subroutine, which is a good description of the problem. We can test this code using the limits that we calculated. To avoid any confusion, the full modified code from the wait_ms.asm project follows.

### wait_ms_asm : main.asm

```
.equ  F_CPU       = 20000000
.equ  MS_TIME_DEL = 2147483   ; upper limit
.equ MS_TIME_DEL = 2147484   ; upper limit + 1

start:
    sbi   DDRB, DDB4        ; Set pin PB4 as output
loop:
    sbi   PORTB, PORTB4     ; Set LED pin high
    rcall wait_ms           ; LED on delay
    cbi   PORTB, PORTB4     ; Clear LED pin low
    rcall wait_ms           ; LED off delay
    rjmp  loop

.include "wait_ms.asm"
```

### wait_ms_asm : wait_ms.asm

```
; Millisecond delay subroutine - time set by MS_TIME_DEL
.equ  WAIT_MS_CYCLES = (((F_CPU * MS_TIME_DEL) / 1000) - 10) / 10
.if (WAIT_MS_CYCLES > (exp2(32) - 1))
.error "F_CPU MS_TIME_DEL combination out of range in wait_ms subroutine."
.endif

wait_ms:
    ldi   R16, low (WAIT_MS_CYCLES)
    ldi   R17, byte2(WAIT_MS_CYCLES)
    ldi   R18, byte3(WAIT_MS_CYCLES)
    ldi   R19, byte4(WAIT_MS_CYCLES)

wait_ms_loop:
    subi  R16, 1
    sbci  R17, 0
    sbci  R18, 0

    mov   R20, R16
    or    R20, R17

    or    R20, R19

    nop
    nop
    ret
```

The main.asm code has been set to use a value of 20MHz for F_CPU and the maximum value for MS_TIME_DEL is set to the maximum value that we calculated as 2,147,483. When these values are used, we expect the .if directive in the wait_ms.asm file to evaluate to false and the error message not to be printed. With the code in the wait_ms.asm project modified, as per the previous listings, build the project and no error message should appear in Microchip Studio.

When the value of MS_TIME_DEL is incremented above the value of 2,147,483, for example 2,147,484 then we expect to see an error in Microchip Studio when the project is built. Comment out the first instance where MS_TIME_DEL is equated to 2,147,483 at the top of main.asm, and uncomment the second instance of MS_TIME_DEL below it which equates it to a value of 2,147,484 which is one greater than the maximum limit. Save the changes and build the project. Microchip Studio now flags the error because the .if directive evaluates to true and the .error directive flags the error. Double-clicking the error message at the bottom of Microchip Studio opens the wait_ms.asm file and places the cursor on the line that contains the .error directive and message.

## Number Size Limits in the Assembler Program

With the previous explanation, and in an ideal world, the mechanism used to flag an error in the code for out of limits values appears to be intuitive and solid. In the real world values are subject to limits, and therefore it is important to thoroughly test all real code using values that exceed basic test values that we have thus far used. Further testing of the previous code reveals that when certain values are assigned to MS_TIME_DEL, the error message at the .if directive does not trigger when it should. For example giving WAIT_MS_CYCLES a value of 3221225, causes the error message to trigger as expected. Assigning 3221226 to WAIT_MS_CYCLES, which is 1 greater than the previous value, results in the error message not being triggered when the code is built. It turns out that the cause of this problem is due to integer size limits in the AVRASM2 assembler program. There is more than one limit that causes the above described problem. Firstly the exp2() function does not work properly if passed a value of 32. We expect exp2(32), which is 2^32, to result in 0x100000000, but it results in 1 instead, as the following code proves.

```
.if (1 == exp2(32))
.warning "Numbers are equal: 1 == exp2(32)."
.endif
```

Adding the above code into the source code of the project causes the warning message to be generated when the project is built, proving that exp2(32) evaluates to 1. The == operator in the code works as it does in C, and tests whether the value on the left is equal to the value on the right, and if they are equal, prints the warning message.

In addition to the above, integer (whole number) values are truncated to 32-bits when using the .equ or #define directives, as the following code proves.

```
.equ NUM1 = 0x0000000F    ; 32-bit number (15)
.equ NUM2 = 0x100000000   ; 33-bit number (4,294,967,296)

.if (NUM1 > NUM2)
.warning "NUM1 is greater than NUM2."
.endif
```

In the above code, a small value is assigned to NUM1 using .equ, and a very big value is assigned to NUM2 in the same way, with the decimal values shown in the comments. The comparison at the .if directive should never evaluate to true because NUM2 is greater than NUM1, rather than the other way around. The reason that the comparison does evaluate to true is because NUM2 is truncated to a 32-bit number, which means that it loses its most significant bit. This causes it to have a value of 0 (zero). 15 is bigger than 0, and this is why the expression evaluates to true. We can prove that NUM2 was truncated to 0 using the following code.

```
.if (NUM2 == 0)
.warning "NUM2 is equal to 0."
.endif
```

In the code above, with NUM2 assigned the same value as in the code before it, the expression at the .if directive evaluates to true, causing the warning message to be printed when the project is built. This proves that NUM2 was truncated to 32-bits and the resulting value equal to 0.

Using the same values as in the previous code, but putting the values directly in the comparison, instead of assigning a name using .equ or #define, the comparison works as expected. Comparing the values that were assigned to NUM1 and NUM2 directly in the following code results in a false result as expected, and the warning message does not get triggered.

```
.if (0x0000000F > 0x100000000)
.warning "0x0000000F is greater than 0x100000000."
.endif
```
