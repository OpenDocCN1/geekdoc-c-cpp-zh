
The previous line of C code is converted by the C compiler to the following line of assembly language:

```
sbi DDRB, DDB4
```

This particular example happens to convert from one line of C code to one line of assembly language code. In other cases a line of C code may convert to more than one line of assembly code. In this section, we look at the assembly language code that the C compiler and linker generated from the led_count.c project, and that actually gets loaded to the Flash memory of the AVR. Although binary machine code is ultimately loaded to Flash memory, we look at the assembly language code after the disassembly of these machine code instructions. This is done in the debugger in Microchip Studio. Start the debugger using Start Debugging and Break with either the actual hardware and hardware programmer/debugger, or using the simulator. After the debugger starts, select Debug ▶ Windows ▶ Disassembly from the top menu, or use the keyboard shortcut Alt + 8 — there is also a Disassembly icon on the second from top toolbar. After opening the disassembly window, the disassembled code comes into view in Microchip Studio. The first part of this disassembled code is shown in the listing below for an ATtiny13(A).

```

00000006 RJMP PC+0x000A Relative jump
```

The disassembly window displays disassembled code from Flash memory. At the top is the interrupt vector table that was inserted automatically by the C tools. We don't look at interrupts in detail here. For now just know that the first entry in the interrupt vector table is the reset vector. The instruction at this location simply causes a jump to the entry point of the C code. When the AVR is powered up or reset, it runs this instruction first, which causes the program to jump over the rest of the vector table entries and start running the C code from the beginning. The other vector table entries also cause the program to jump to the reset vector, but by first jumping to another jump instruction. The code listing shows the first two sections of the disassembly. Note that this code has been built for the ATtiny13(A), which has a smaller interrupt vector table of 10 entries from address 0 to address 9. If you build the same code for the ATtiny25/45/85, you will notice that the vector table has 15 entries, from address 0 to 14 (0x000E). At the left of each assembly language instruction is the address in Flash program memory of the instruction. Looking at the first entry in the disassembly, we have the reset vector at address 0 and an RJMP instruction next to it as follows.

```
00000000 RJMP PC+0x000A Relative jump
```

It can be seen that this relative jump instruction jumps to the address at PC + 0x000A, which is the current program counter (PC) value plus 0x000A. At reset, the PC contains zero and therefore this first jump instruction jumps to the address 0x000A. In the disassembly listing, CLR R1 is found at address 0x000A in the grc1.S section. The remainder of the interrupt vector table from address 0x0001 to 0x0009 also contain relative jump instructions that all jump to address 0x0010. At address 0x0010 is yet another RJMP instruction that jumps back 0x10 addresses, indicated by the negative sign next to the address as follows.

```
00000010 RJMP PC-0x0010 Relative jump
```

0x10 is 16 in decimal, and 16 addresses back from the current address of 0x10 is 0, or the reset vector at address 0 of the vector table. This means that if any interrupt were triggered, program execution would simply restart at address 0. In the previous disassembly listing, the second section in the code is from grc1.S, as indicated in the listing. This code is automatically linked in by the C tools. In the name grc1.S, crt stands for C Runtime, which is code that performs initialization required before calling the C main() function. The C runtime code starts by clearing the status register by first clearing R1 and then loading R1 to address 0x3F (which is the status register) as follows.

```
0000000A CLR R1 Clear Register
0000000B OUT 0x3F,R1 Out to I/O location
```

In the Register Summary section of the ATtiny13(A) and ATtiny25/45/85 datasheet, SREG (status register) is found at the top of the table at address 0x3F. After clearing the status register, the C runtime code sets the stack pointer to point to the end of SRAM data memory. For the ATtiny13(A), this is 0x9F – refer back to Figure 5.3 in Chapter 5 for the memory map. As shown in the following code, 0x9F is loaded to register R28. R28 is then loaded to address 0x3D, which is the SPL, or stack pointer low register.

```
0000000C LDI R28,0x9F      Load immediate
0000000D OUT 0x3D,R28      Out to I/O location
```

Finally, main() is called using a Relative Call to Subroutine RCALL instruction as follows.

```
0000000E RCALL PC+0x0003   Relative call subroutine
```

This jumps to the address PC + 0x0003, which is the current address of 0x000E + 3, in other words address 0x0011. As can be seen in the remainder of the disassembly listing that follows, address 0x0011 is the first instruction inside main(). The remainder of the listing shows the C code mixed with the assembly language that it was converted to.

```
--- C: \ ... ... ... ./.../main.c

00000013 LDI R24,0x00        Load immediate
00000014 PORTB = count;      // Display count on LEDs
00000014 OUT 0x18,R24        Out to I/O location
--- C: \ ... ... ... ./.../delay.h
--- builtin_avr_delay_cycles(__ticks__dc);
00000015 LDI R18,0xF7        Load immediate
00000016 LDI R19,0xA9        Load immediate

00000019 SBCI R19,0x00       Subtract immediate with carry
0000001A SBCI R25,0x00       Subtract immediate with carry
0000001B BNE PC-0x03         Branch if not equal
0000001C RJMP PC+0x0001      Relative Jump

0000001E SUBI R24,0xFF       Subtract immediate

00000020 RJMP PC-0x000C      Relative Jump
```

A top level view of the above listing shows that the code for the delay library function from delay.h was placed in the middle of the code from main.c. At the start of the disassembled code, it can be seen that the code is similar to the led_count_asm project code. 0x1F is loaded to R24, and then sent to address 0x17 using the OUT instruction as follows, with the line of C code shown above the two lines of assembly language that it converted to.

```
DDRB = 0b00011111;
00000011 LDI R24,0x1F Load immediate
00000012 OUT 0x17,R24 Out to I/O location
```

0x17 is the address of the DDRB register, as can be seen from the Register Summary section of the datasheet. These two lines of code perform the same function as the first two lines of code in the led_count_asm project, except that the above code uses R24 and hexadecimal notation, while the led_count_asm project uses R16 and binary notation.

In the next line of code at address 0x0013, R24 is used as the count variable, and set to an initial value of zero, as follows.

```
uint8_t count = 0; // Clear count
00000013 LDI R24,0x00 Load immediate
```

The above line of code was converted from one line of C code which is shown above it. Notice that the C compiler placed this line of code below the initialization of the DDRB register. In the original C source code, the count variable was declared and initialized before the initialization of DDRB. By changing the order of these lines of code, R24 is first used to initialize DDRB, and then used again as the count variable.

At address 0x0014, the count value from R24 is written to address 0x18, which is the PORTB register. Once again, the address of PORTB is found in the Register Summary section of the datasheet. This line of code writes 0 (the count value in R24) to the LEDs, switching them off and was converted from one line of C code, shown above it.

```
PORTB = count; // Display count on LEDs
00000014 OUT 0x18,R24 Out to I/O location
```

Code from address 0x0015 to 0x001D, which is the _delay_ms() function, is run next, creating the delay that leaves the current count value displayed on the LEDs for a while.
