
subroutine. Ignoring the NOP instructions, the RET instruction adds four more clock cycles to the subroutine. This totals eight clock cycles used outside of the loop. These additional clock cycles must be subtracted from F_CPU before it is divided by 10, so that the subroutine delays for exactly the right number of clock cycles. A problem occurs when subtracting 8 from an F_CPU value that is a multiple of 10, and then dividing the result by 10. For example when using 1MHz for F_CPU, we get (1,000,000 - 8) / 10 = 99,999.2 which has a fractional value. In order to get the wait_1s subroutine to use up the exact number of clock cycles that we require when F_CPU is a multiple of 10, two extra clock cycles are added before the RET instruction by adding two NOP instructions. This causes the total number of clock cycles before and after the loop to add up to 10. We therefore must subtract 10 from F_CPU before dividing it by 10. For a frequency of 1MHz, we now have (1,000,000 - 10) / 10 = 99,999 which is a whole number. When this number is loaded to R16 to R19, then the wait_1s subroutine uses up exactly 1 million clock cycles.

### 10.2.2.4 Testing the Code in Microchip Studio

Microchip Studio and the AVR simulator can be used to test the wait_1s subroutine to verify that it uses up the correct number of clock cycles for the given frequency. Use the wait_1s.asm code in a Microchip Studio project with the simulator for testing purposes. After entering the code, be sure to set the desired value for F_CPU at the top of the code, for example set it to 1000000 for an AVR running at 1MHz. Build the code and select the simulator as the tool to use, as we have done previously. Place a breakpoint on the first instruction in the wait_1s subroutine, and on the RET instruction at the end. Use Start Debugging (F5) to start the code running, which will then stop at the first breakpoint.

When the simulator stops at the first breakpoint, set the Cycle Counter in the Processor Status window to 1 to compensate for the bug, as previously discussed. Set the Frequency field in the Processor Status window to the frequency that F_CPU was set to. Run the code again so that execution stops on the second breakpoint on the RET instruction. Because the RET instruction has not executed yet, the Cycle Counter is now at the correct value minus four, for example a 1MHz frequency, the counter is at 999996. Step over the RET instruction using the Step Over icon or F10. The cycle counter now contains the correct value for the chosen frequency, 1000000 for 1MHz. This means that on a real ATtiny device, 1 second of time is used up. This is cycle accurate, but may not be time accurate on devices that are using the internal RC oscillator because this oscillator is not very accurate. Note also that the AVR simulator does not run in real time, so will actually use more time to execute wait_1s when using a higher F_CPU.

## 10.2.3 A Changeable Software Time Delay Subroutine

Now that we have a software time delay subroutine that compensates for the frequency that the microcontroller is running at, it does not take too much effort to modify the time delay subroutine to make its delay time changeable. In addition to modifying the previous time delay subroutine, the next project splits the code up into two files, putting the new time delay subroutine into its own file. The code listings for the two files follow.

```
wait_ms.asm : main.asm

.equ  F_CPU     = 1000000   ; Frequency of CPU
.equ  MS_TIME_DEL = 500     ; Time delay in milliseconds

start:  sbi   DDRB, DDB4      ; Set pin PB4 as output
loop:   sbi   PORTB, PORTB4   ; Set LED pin high
        rcall wait_ms         ; LED on delay
        cbi   PORTB, PORTB4   ; clear LED pin low
        rcall wait_ms         ; LED off delay
        rjmp  loop

.include "wait_ms.asm"
    ; Must put newline here
```

```
wait_ms.asm : wait_ms.asm

; Millisecond delay subroutine - time set by MS_TIME_DEL
wait_ms:
    ldi   R16, low ((((F_CPU * MS_TIME_DEL) / 1000) - 10) / 10)
    ldi   R17, byte2((((F_CPU * MS_TIME_DEL) / 1000) - 10) / 10)
    ldi   R18, byte3((((F_CPU * MS_TIME_DEL) / 1000) - 10) / 10)
    ldi   R19, byte4((((F_CPU * MS_TIME_DEL) / 1000) - 10) / 10)
wait_ms_loop:
    subi  R16, 1
    sbci  R17, 0
    sbci  R18, 0
    sbci  R19, 0
    mov   R20, R16
    or    R20, R17
    or    R20, R18
    or    R20, R19
    brbc  SREG_Z, wait_ms_loop
    nop
    nop
    ret
```

### 10.2.3.1 Splitting an Assembly Language Project into Files

As the previous code listings show, an AVR assembly language project can be split up into more than one file by adding a new file to the project. The new file is then included in the project using the .include directive in the main assembly language file. Because the AVRASM2 assembler program that comes with Microchip Studio does not have a linker, assembly language projects have to use this simple method of including additional assembly language files. As can be seen in the previous code listing, the wait_ms.asm file that was added to the project is included at the bottom of the main.asm file.

Including files using the .include directive effectively pastes the contents of the included file at the position in the file that uses the .include directive. In our example code, the file containing the wait_ms subroutine was included at the end of main.asm, effectively pasting this code below the code in main.asm. If wait_ms.asm were included at the top of the main.asm file, then the wait_ms subroutine would be placed in Flash program memory starting at address 0, where the start of the code from main.asm should be. If .org 0 were used at the start of the code in main.asm to force it to start at address 0, the project would give build errors because the first code found is placed at address 0. With wait_ms.asm included at the top of main.asm, the delay subroutine is the first code and is assigned to start at address 0 before the AVRASM2 assembler program finds .org 0 in the main assembly language file. This means that we are asking the assembler program to put two different pieces of code into memory starting at address 0. The result is that the assembler program flags overlap errors during the build process. The solution to including the external assembler file at the top of the main assembler file is to use a jump instruction as follows.

```
.rjmp start
.include "wait_ms.asm"

start:
    sbi   DDRB, DDB4    ; Set pin PB4 as output
...
```

In the above code, an RJMP instruction is placed at the top of the main.asm file, which means that it is at address 0 and is the first instruction to run on the microcontroller. This instruction jumps to the start label, and over any code that is included between it and the start label.
