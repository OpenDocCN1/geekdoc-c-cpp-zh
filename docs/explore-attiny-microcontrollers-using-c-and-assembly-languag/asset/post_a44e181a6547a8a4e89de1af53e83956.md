
## 9.3.5 Conditional Assembly

Conditional assembly includes the IF, IFDEF, IFNDEF, ELIF, ELSE, and ENDIF assembly directives. Conditional assembly directives run at assembly time, and not at run-time when the code is running on the AVR. An example follows that uses just two of the above mentioned conditional assembly commands, IFDEF and ENDIF. This code is a modified version of the code from the push and pop example of section 6.6.2 in Chapter 6.

```
; Initialize the stack pointer
ldi r16, low(RAMEND)
out spl, r16
.IFDEF SPH
ldi r16, high(RAMEND) ; Remove for ATtiny13(A) and ATtiny25
out sph, r16 ; Remove for ATtiny13(A) and ATtiny25
.ENDIF
ldi r16, 0x5A ; Load a value to R16
push R16 ; Save R16 to the stack
clr R16 ; R16 gets modified
pop r16 ; Restore R16 from the stack
loop:
rjmp loop
```

In the original version of the above code, two lines of code had to be removed if the code was to be run on an ATtiny13(A) or ATtiny25. This code has to do with loading a value to the high byte of the stack pointer, or SPH. On the ATtiny13(A) and ATtiny25, SPH does not exist because there is not enough SRAM on these devices for the SPH to be needed. The above code takes advantage of this fact and uses IFDEF (if defined) to check if SPH is defined. In this way it makes the code universal, allowing it to be built for any ATtiny AVR device without the need to delete certain lines of code. It effectively automates the removal of the code that initializes the SPH for certain devices, while leaving these lines of code for other devices. For an ATtiny45 or ATtiny85, SPH is defined in the tn45def.inc, or tn85def.inc file found under Dependencies in the Solution Explorer pane of Microchip Studio. We have already looked at this file – refer back to Figure 8.1 in section 8.1.1 of Chapter 8, or Figure 9.1 in section 9.2 of the current chapter for a reminder. SPH is not defined in the include files for ATtiny13(A) and ATtiny25 devices. When the assembler program is run and it finds .IFDEF SPH in the file, it checks to see if SPH is defined. If SPH is defined, it includes the two lines of code between IFDEF and ENDIF. If SPH is not defined, the code between IFDEF and ENDIF is not included in the assembly process, and does not appear in the final machine code instructions.

The code from the previous listing can be entered into main.asm from the test_asm project in order to verify how the IFDEF directive works. If you have been following along with this book, the test_asm project is set up to use the simulator and is set up to assemble code for the ATtiny45. After building the project for the ATtiny45, start debugging and break as we have been doing. Open the disassembly window and note that code is found in this window that initializes SPH, as follows.

```
ldi     r16, low(RAMEND)      Load immediate
00000000 LDI R16,0x5F
out     SPL, r16              Out to I/O location
00000001 OUT 0x3D,R16
ldi     r16, high(RAMEND)     ; Remove for ATtiny13(A) and ATtiny25
00000002 LDI R16,0x01         Load immediate
out     SPH, r16              ; Remove for ATtiny13(A) and ATtiny25
00000003 OUT 0x3E,R16         Out to I/O location
ldi     r16, 0x5A             ; Load a value to R16
00000004 LDI R16,0x5A         Load immediate
```

The listing, as shown above from the Disassembly window, has one line from the original assembly language code, followed by what it disassembled to. The disassembled line starts with the address location of the 16-bit instruction in program memory. We can see that the first LDI instruction and OUT instruction are present that initialize SPL, as expected. Because this program was assembled for the ATtiny45, which does have an SPH register, we expect the code that initializes SPH to be present. These two lines are present at addresses 2 and 3. The program continues with the LDI instruction that loads 0x5A to R16. Code below this has not been included in the above listing.

Stop debugging the code for the ATtiny45. We will now change the project to build for the ATtiny13, ATtiny13A, or ATtiny25, all of which do not have the SPH register. Click ATtiny45 on the toolbar in Microchip Studio, or click Project ▸ test_asm Properties... from the top menu, and then Device at the left of the page that opens. On this page, click the Change Device... button near the middle of the top of the page. This opens the Device Selection dialog box. Select either the ATtiny13, ATtiny13A, or ATtiny25 in this dialog box, the description that follows assumes that the ATtiny25 was selected. Use the search field at the top right of the dialog box to search for the desired device, then click it in the main pane of the dialog box. Click the OK button when done. Save after making the changes and then build the project. If needed, select the simulator as the tool again by clicking the hammer icon next to the ATtiny device that we just changed. This may not be necessary.

Now that the test_asm project has been changed to build for the ATtiny25, SPH is no longer defined for the project. This means that when the assembler program reaches the line with .IFDEF SPH, it does not include the two lines of code between IFDEF and ENDIF. We can check this with the start debug and break button in Microchip Studio, and then by opening the Disassembly window as we did before. The disassembled code now looks as follows.

```
ldi    r16, low(RAMEND)
00000000 LDI R16,0xDF    Load immediate
out    SPL, r16
00000001 OUT 0x3D,R16    Out to I/O location
ldi    r16, 0x5A    ; Load a value to R16
00000002 LDI R16,0x5A    Load immediate
push   R16        ; Save R16 to the stack
```

Only two instructions appear before the LDI instruction that loads 0x5A to R16, as can be seen in the disassembled code above. The first two lines of code initialize SPL, but the code that initializes SPH has been left out, as expected because of the conditional assembly directives IFDEF and ENDIF.

Stop the debugger and change the device for the test_asm project back to ATtiny45. Click the button on the toolbar that should now say ATtiny25, and then use the Change Device... button to select the ATtiny45 again. Save and rebuild the project.

## 9.4 Other Assembly Language Elements

The AVR Assembler program does have more assembler directives and other elements that it recognizes, such as preprocessor directives, functions and operators. We did see the left shift operator (<<) in use when looking at DB. We have also used the high() and low() functions to get the high and low bytes of 16-bit numbers. All of these elements are used to make programming in assembly language easier. This chapter has been an introduction to how some of these elements can be useful. There is no point in covering every possible assembly language element in this book, as it will just result in an information overload. Further elements of assembly language are covered and used in practical programs throughout the remaining chapters. The AVR Assembler document from Microchip can be used as a reference when using the AVRASM2 assembly program, and also to learn about other assembly language elements.

## 9.6 Summary

- AVRASM2 is the name of the default AVR assembler program used by Microchip Studio.
- The preprocessor can be used to include external files in an assembly language program.
- The correct header file is automatically included in an assembly language project in Microchip Studio for the AVR part selected when creating the project.
- Assembler directives are available for use in assembly language programs, and allow the programmer to specify code and data locations, select type of memory to place data in, reserve bytes for data in memory, name registers, and more.
- Assembler directives always start with a dot (.) when used in an assembly language program.
- Use the AVRASM2 AVR Assembler manual or document to find technical information on the AVRASM2 assembler program.
