I've implemented two functions in the control program to create new COM+ objects (`GetUnknown()`) and query COM+ interfaces (`GetInterface()`) on the objects. I will not describe these functions in any detail because they are standard implementations for creating objects and querying interfaces.

In the `main()` function, I create the event server and event sink objects. Note that the event server object is created out-of-process and the event sink object is created in-process. This is not a necessity of the COM+ event model, but it is the standard implementation.

The event source is typically an ActiveX control that has events, and the event sink is the client application that wants to be notified of the events in the OLE control. The OLE control might be a grid control, and the client might be a dialog that has the control embedded within its client area. The dialog might want to receive notification when the grid control is double-clicked. The dialog would implement an event sink interface defined by the grid control. The OLE control would receive a pointer to the dialog’s event sink when the dialog calls the `IConnectionPoint::Advise()` method. When the grid is double-clicked, the grid control calls the event sink methods of the dialog, thus producing the notification.

In order to call the `IConnectionPoint::Advise()` method, the client must first receive an interface pointer to the `IConnectionPointContainer` interface. This is done in Listing 6.13 with the first call to the `GetInterface()` function.

With the `IConnectionPointContainer` interface, I can now call the method `IConnectionPointContainer::FindConnectionPoint()` to retrieve the `IConnectionPoint` object.

Now that I have the `IConnectionPoint` interface, I can call `IConnectionPoint::Advise()` to set up the event notification. Note that I pass a pointer to a DWORD to the `IConnectionPoint::Advise()` method. This is a cookie that I can later use to call the `IConnectionPoint::Unadvise()` method to terminate the event notification.

The next step is to retrieve an interface pointer for the `IEventTrigger` interface. In Listing 6.13, this is the second call to the `GetInterface()` function. After I have the `IEventTrigger` interface, I can call the `IEventTrigger::Fire()` method to fire the event. When the method is fired, the code in `MyEventSink::Hello()` is called.

Running the application should produce the following command-line output:

```text
Start
The event was fired.  Hurray!
End
```

That wasn’t so hard. The code looks a little funny and complicated, but there really isn’t that much code to deal with. The only problem is that this type of event sink will not work with Visual Basic.

## Events and Visual Basic

I fired the event in the previous example using the vtable. Visual Basic generates automation code only for its event sinks and does not generate any vtable code to capture event notifications. That means I must call the `IDispatch::Invoke` method in order to fire the event in a Visual Basic client.

### Black Hole of Events

This is one of the big black holes in Microsoft's object-oriented architecture. How is the programmer supposed to know which interface to fire the event with, the dispatch or the vtable interface? It is simply not possible without imposing limits on the model. You could impose a rule on COM servers that they must call both the vtable and dispatch interface, but this would result in additional client code to ensure that an event was not received twice. The only rule that works is to limit everyone to using the dispatch interface when invoking event sink methods. This removes any advantage of using the vtable and increases the learning curve by requiring developers to understand automation in order to use events.

Listing 6.14 shows the necessary code to call the `IDispatch::Invoke` method in order to invoke events using the dispatch interface.

### LISTING 6.14 Call Event Handler Through IDispatch Interface

```cpp
VARIANTARG* pvars = new VARIANTARG[1];
for (int i = 0; i < 1; i++)
{
    VariantInit(&pvars[i]);
}
IUnknown** pp = m_vec.begin();
while (pp < m_vec.end())
{
    if (*pp != NULL)
    {
        pvars[0].vt = VT_I4;
        pvars[0].lVal = lFlags;
        DISPPARAMS disp = { pvars, NULL, 1, 0 };
        IDispatch* pDispatch = reinterpret_cast<IDispatch*>(*pp);
        pDispatch->Invoke(0x1, IID_NULL, LOCALE_USER_DEFAULT,
                          DISPATCH_METHOD, &disp, NULL, NULL, NULL);
    }
    pp++;
}
delete[] pvars;
```

## Rewriting the Event Source

A few things must be rewritten in the event source in order to comply with this event model. The IMyEventSink interface must be rewritten as a dispatch interface. Listing 6.15 shows the content of the new IDL file.
