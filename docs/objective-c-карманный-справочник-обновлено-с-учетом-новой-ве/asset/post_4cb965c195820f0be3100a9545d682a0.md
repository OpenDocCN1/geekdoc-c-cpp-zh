# Asserting Expectations

```objc
@interface IgnoreAsserts : NSAssertionHandler
@end
@implementation IgnoreAsserts
-(void)handleFailureInFunction:(NSString*)functionName
	file:(NSString*)fileName
	line:(NSInteger)line
	description: (NSString *)format, ...
{
  NSLog(\@"Ignoring assert on line %d of %@ in %@", line, functionName, fileName);
}
@end

int main(void)
{
  [[AutoreleasePool new];
  [[NSThread currentThread] threadDictionary
    setObject:[IgnoreAsserts new] autorelease
    forKey:NSAssertionHandlerKey];
  NSAssert(1 == 2, @"This might not be true");
  return 0;
}
```

From: assert.m

In code, the standard library provides an assert() macro, which logs a message and calls abort() when the predicate argument evaluates to false. The Objective-C versions are slightly more useful.

Foundation provides two macros, NSAssert() and NSCAssert(). If you are using C99 (which you should) then these are variadic, otherwise you will need to use the variants, like NSAssert(), that take fixed numbers of arguments. NSAssert() references self and so can only be used in an Objective-C method body. NSCAssert() can be used in C functions. Unlike the C variants, these do not abort when the assertion is false. Instead, they send a message to a per-thread assertion handler object. This object is, by default, an instance of NSAssertionHandler and throws an NSInternalConsistencyException when you hit assertion. You can catch this and recover, but most often it will reach the top of the stack and cause the program to abort.

You can create your own subclass of NSAssertionHandler and override one or both of the assertion-handling methods if you want some other behavior. This example ignores assertions in C functions, just logging a message when they are encountered.

# Logging Debug Messages

```objc
- (void) log {
  NSLog("%s:%d:%s (%@) Log message", __FILE__, __LINE__, PRETTY_FUNCTION__, self);
}
```

From: nslog.m
We've used the NSLog() function in quite a bit of code already. When you run an application in the terminal, messages passed to NSLog() go to the standard error stream. On OS X, NSLog() in graphical applications sends messages to the system console. On Microsoft Windows, with GNUstep, they go to the system event monitor.
The NSLog() function writes a format string, prepended by the date, time, process name, and process ID. When you put the %@ format specifier in a format string, it uses exactly the same method as the debugger to get a string representation of the object.

# The Objective-C Runtime

As I said at the start of this book, an Objective-C implementation consists of two parts: the compiler and the runtime library. The compiler takes source code and turns the dynamic bits into calls to the runtime library.

The runtime library is written in C, which means that it is written in a subset of Objective-C. All of the interfaces to the runtime library, including the ones that are called by code generated by the compiler, are accessible to Objective-C code.

Everything dynamic in Objective-C is implemented by the runtime library. The most obvious example of this is message sending. When you send a message, the runtime is responsible for deciding what should handle it.

This is not the only responsibility of the runtime library. It also handles all of the introspection features of the language. It keeps track of all class metadata and exposes this to programmers.

When you use key-value coding, you are (indirectly) using the runtime to look up methods.

# Sending by Name

```objc
id obj = [NSObject new];
sel = NSSelectorFromString("release");
IMP release = [obj methodFor:sel];
release(obj);
```

From: methodName.m
Objective-C methods are C functions that are called via message sends. Exactly how this is implemented varies a bit between runtimes. With the NeXT and Apple runtimes, simple message sends are implemented using objc_msgSend().

Unfortunately, this is not the only function that you need. With the GNU runtimes, this is much simpler. There is no objc_msgSend() function. Instead, you call objc_lookup() and then call the returned function, after casting it to the correct types.

The easiest way of doing this that is portable between runtimes is to use the -methodFor: method on NSObject. This returns a pointer to the method, which you can then call. This takes two arguments: the receiver and the selector.

This is almost enough to call a method by name. The missing part is some mechanism for turning strings into selectors. NSSelectorFromString() function does exactly this. It takes an NSString as an argument and returns a selector. You can then pass this to -methodFor:, and as the second argument to the returned function.

# Finding Classes by Name

```objc
Class nsview = NSClassFromCString("NSView");
if (Nil == nsview)
{
    NSLog("Not linked against AppKit");
}
else
{
    id view = [nsview new];
    NSLog("View: %@", view);
}
```

From: weakClass.m
One of the runtime's responsibilities is storing a table of all loaded classes. You can enumerate this table, looking at every class in turn, or you can use it to look up a class by name.

The latter is particularly useful for implementing weak class references. These are supported directly via the Modern Apple runtime, but the support is not yet exposed via the language, so it's not particularly useful. The idea behind a weak class reference is that you can optionally use a class.

You might, for example, write some code in a framework that used Foundation classes and could use AppKit classes if you linked against AppKit. This framework would then work anywhere that had a Foundation implementation, but would take advantage of AppKit features if they were available. You can also use this mechanism to avoid a dependency on third-party frameworks.
