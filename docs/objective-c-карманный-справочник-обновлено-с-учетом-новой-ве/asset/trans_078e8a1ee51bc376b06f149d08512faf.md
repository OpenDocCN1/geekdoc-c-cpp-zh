## 错误处理

大多数代码都包含 bug。良好的代码会意识到这一点并优雅地处理它们。真正优秀的代码使用形式化来证明没有 bug，但大多数人负担不起真正优秀的代码。

书中的大多数示例代码都假装错误从未发生。这本书的页数很短，为任何一个示例编写适当的错误处理代码会很快填满页面，而这些内容与示例的要点大部分无关。

大多数可以在运行时检测到的错误源于一个函数或方法使用无效输入调用另一个。处理此问题的最佳方法很大程度上取决于语言。例如，Erlang 不鼓励在模块级进行防御性编程；如果你的模块处于未定义状态，你应该杀死它并创建一个新版本。在 C 中，你被鼓励验证每个输入并检查每个返回值。在 Java 中，你可以通过异常来推迟错误处理。Lisp 和 Smalltalk 允许你在发生错误时检查堆栈，并动态修复提供错误输入的代码。

Objective-C 在这方面介于 C 和 Java 之间。某些错误最好在靠近产生源的地方处理，而另一些错误只能通过报告原因并退出来处理。Objective-C 从 NEXT 时代开始就有所谓的“异常”机制，但直到过去几年，它们的行为才变得像其他语言中的异常一样。然而，作为 C 的超集，Objective-C 支持你在 C 中找到的所有形式的错误报告。

## 异常的运行时差异

异常处理的实现非常困难。当你抛出一个异常时，你需要回溯抛出处和捕获处之间的每一个栈帧。有几种方法可以实现这一点。在像 Smalltalk 这样具有栈内省能力的语言中，这相对容易。异常可以查看每个栈帧并执行回溯。在 Java 和类似的语言中，通常通过返回两个值来实现。在典型的 Java VM 中，一个寄存器将预留用于返回异常对象。在每次调用之后，JVM 都会检查该寄存器是否为零，如果不是，则跳转到异常处理代码。

这在 Objective-C 中是不可能的，因为你需要能够与 C 交互。在抛出异常处和捕获处之间的某些栈帧可能是 C，而你不能期望系统上所有的 C 代码在抛出异常时都修改为返回另一个。

另一个选项是类似于微软的结构化异常处理（SEH），在进入和退出异常处理块时，会压入和弹出清理代码地址的链表。当抛出异常时，使用该栈来找到要运行的清理代码并跳转到栈中的正确位置。这本可以是 Objective-C 的一个选项，但它的开销非常大。它要求你在每次进入和退出异常处理块时运行某些代码，然后在抛出异常时再运行一些代码。

不过，C 确实包含一对调用可以让你执行诸如栈回溯的操作。`setjmp()` 调用存储当前的 CPU 寄存器，包括栈指针和帧指针。`longjmp()` 重新加载它们。这样做的效果是将栈重置为 `setjmp()` 被调用时的状态。这就是 Objective-C 异常传统的实现方式。

不支持在中间栈帧中执行清理操作。如果你的 Objective-C 代码调用了某些 C++ 代码，然后 C++ 代码再次调用了 Objective-C 代码，你可以通过 `longjmp()` 跳过 C++ 代码。

 GCC 的基于 DWARF 的异常处理提供解决此的方法。它使用存储在二进制中的表来描述如何回溯栈。当抛出异常时，运行时在表中查找当前的指令指针以找到适当的清理代码。这比 setjmp/longjmp 高得多，因为除非实际上抛出异常，否则它不需要任何工作。

基于 DWARF 方法还允许运行 C++ 析构函数。当栈回溯时，运行时会调用所有超出作用范围对象的析构函数。这就是为什么 Objective-C 可以与 C++ 异常相互操作。

DWARF 方法的缺点是实现起来很复杂。编译器必须生成这些表，运行时必须解析它们。然而，对于大多数现代语言来说，这是处理异常的首选方法。

## 异常的运行时差异 241

在 Objective-C 中，64 位平台使用基于 DWARF 的方法。在 32 位 Intel 平台上，某些情况下仍在使用旧的 setjmp/longjmp 方法，但基于 DWARF 的方法也是可用的。

基于 DWARF 方法与 setjmp/longjmp 方法之间的主要区别在于如何回溯栈。setjmp/longjmp 是一种“强制”回溯，它简单地跳回到保存的状态。基于 DWARF 的回溯是“结构化”回溯，它遍历栈帧并沿路执行清理代码。

## 异常的运行时差异 242

两种方法之间的性能差异显著。setjmp/longjmp 每次调用 setjmp 都有成本，因为必须保存寄存器。基于 DWARF 的回溯在没有抛出异常时几乎没有成本，但在抛出异常时非常昂贵。这就是为什么在预计异常罕见的语言中，首选基于 DWARF 的方法。

在 Objective-C 中，异常通常用于真正的异常情况，因此基于 DWARF 的方法非常合适。然而，如果你将异常用于控制流，setjmp/longjmp 方法可能会更快。

## 抛出和捕获异常

```objectivec
NSArray *array = [NSArray array];
@try {
    [array objectAtIndex:0];
} @catch (NSException *e) {
    NSLog(@"Caught exception %@", e);
}
```

来自：exception.m

上面的代码显示了 Objective-C 中 @try-catch 的基本用法。`@try` 块包含可能抛出异常的代码。`@catch` 块包含异常异常时运行的代码。你可以有多个 `@catch` 块，每个异常类型一个。

```objectivec
@try {
    [array objectAtIndex:0];
} @catch (NSRangeException *e) {
    NSLog(@"Caught out of bounds %@", e);
} @catch (NSIndexOutOfRangeException *e) {
    NSLog(@"Caught out of range %@", e);
} @catch (NSException *e) {
    NSLog(@"Caught exception %@", e);
}
```

`@catch` 块从具体到不通用进行尝试。第一个匹配异常类型的块将被执行。

你还可以使用 `@finally` 块，无论是否抛出异常，它都会运行。

```objectivec
@try {
    [array objectAtIndex:0];
} @catch (NSException *e) {
    NSLog(@"Caught exception %@", e);
} @finally {
    NSLog(@"Cleaning up...");
}
```

`@finally` 块用于清理资源，例如关闭文件或释放内存。

## 抛出和捕获异常 244

要抛出异常，使用 `@throw` 关键字。

```objectivec
[NSException raiseWithName:@"MyException" 
                      reason:@"Something went wrong" 
                         code:0];
```

你还可以通过类 `NSException` 创建自己的异常类。

```objectivec
@interface MyException : NSException
@property (copy, retain) NSString *customData;
@end

@implementation MyException
- (instancetype)initWithReason:(NSString *)reason code:(NSInteger)code customData:(NSString *)customData {
    self = [super initWithReason:reason code:code userInfo:nil];
    if (self) {
        _customData = customData;
    }
    return self;
}
@end
```

然后你可以抛出你的自定义异常：

```objectivec
MyException *e = [[MyException alloc] initWithReason:"Error" code:404 customData:@"Some data"];
@throw e;
```

通常不建议将抛异常用于控制流。使用返回码或结果对象更好。异常应该用于真正的异常情况。
