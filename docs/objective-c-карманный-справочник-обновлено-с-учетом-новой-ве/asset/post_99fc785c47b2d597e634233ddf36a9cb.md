## Handling Errors

Most code contains bugs. Good code is aware of this and will handle them gracefully. Really good code uses formal methods to prove that there are no bugs, but most people can’t afford really good code.

Most of the sample code in this book pretends that errors never happen. This book has quite small pages, and proper error-handling code for any of the examples would fill them up very quickly with things that are largely irrelevant to the point of the example.

Most errors that can be detected at run time come from one function or method calling another with invalid inputs. The best way of handling this depends a lot on the language. For example, Erlang discourages defensive programming at the module level; if your module is in an undefined state, you should kill it and create a new version. In C, you are encouraged to validate every input and check every return value. In Java, you can defer error handling by using exceptions. Lisp and Smalltalk let you inspect the stack when an error occurs and dynamically fix the code that gave you the wrong input.

Objective-C fits somewhere between C and Java in this respect. Some errors are best handled very close to their cause, whereas others can only be handled by reporting the cause and exiting. Objective-C has had things called exceptions since the NEXT days, but they've only behaved like exceptions in other languages for the last few years. As a superset of C, however, Objective-C has support for all of the forms of error reporting that you find in C.

## Runtime Differences for Exceptions

Exception handling is quite difficult to implement. When you throw an exception, you need to unwind every stack frame between where the exception was thrown and where it is caught. There are a few ways of doing this. In a language with stack introspection like Smalltalk, it's relatively easy. The exception can look at each stack frame and perform the unwinding. In Java and similar languages, it is commonly implemented by returning two values. In a typical Java VM, one register will be reserved for returning the exception object. After every call, the JVM will check that this register is zero, and branch to the exception-handling code if it isn’t.

This is not possible in Objective-C, because you need to be able to interoperate with C. Some of the stack frames between where the exception is thrown and where it is caught might be C, and you can’t expect all C code on the system to be modified to return another value if an exception is thrown.

Another option is something like Microsoft’s structured exception handling (SEH), where a linked list of cleanup code addresses is pushed and popped as exception-handling blocks are entered and left. When an exception is thrown, this stack is used to find the cleanup code to run and to jump to the correct location in the stack. This would have been an option for Objective-C, but it’s quite expensive. It requires you to run some code whenever you enter and exit an exception-handling block, then some more when you throw an exception.

C does include a pair of calls that let you do something like stack unwinding, though. The `setjmp()` call stores the current CPU registers, including the stack and frame pointers. `longjmp()` reloads them. This has the effect of resetting the stack to the state when `setjmp()` was called. This is how Objective-C exceptions were traditionally implemented.

As you can imagine, this was far from ideal.

There was no support for performing cleanup actions in intervening stack frames. If your Objective-C code called some C++ code, which then called Objective-C code again, you could `longjmp()` over the C++ code.

The DWARF-based exception handling, introduced by GCC, provides a way to solve this. It uses a table stored in the binary to describe how to unwind the stack. When an exception is thrown, the runtime looks up the current instruction pointer in the table to find the appropriate cleanup code. This is much more efficient than setjmp/longjmp because it doesn't require any work unless an exception is actually thrown.

The DWARF-based approach also allows for C++ destructors to run. When the stack is unwound, the runtime calls the destructors for all the objects that are out of scope. This is why Objective-C can interoperate with C++ exceptions.

The downside of the DWARF approach is that it is complex to implement. The compiler must generate the tables, and the runtime must parse them. However, for most modern languages, this is the preferred way to handle exceptions.

## Runtime Differences for Exceptions 241

In Objective-C, the DWARF-based approach is used on 64-bit platforms. On 32-bit Intel platforms, the older setjmp/longjmp approach is still used in some cases, but the DWARF-based approach is also available.

The main difference between the DWARF-based and setjmp/longjmp approaches is how the stack is unwound. Setjmp/longjmp is a "forced" unwinding that simply jumps back to a saved state. DWARF-based unwinding is a "structured" unwinding that traverses the stack frames and executes cleanup code along the way.

## Runtime Differences for Exceptions 242

The performance difference between the two approaches is significant. Setjmp/longjmp has a cost every time setjmp is called, because it must save the registers. DWARF-based unwinding has almost no cost when no exception is thrown, but it is very expensive when an exception is thrown. This is why the DWARF-based approach is preferred for languages where exceptions are expected to be rare.

In Objective-C, exceptions are often used for truly exceptional circumstances, so the DWARF-based approach is a good fit. However, if you are using exceptions for control flow, the setjmp/longjmp approach might be faster.

## Throwing and Catching Exceptions

```objectivec
NSArray *array = [NSArray array];
@try {
    [array objectAtIndex:0];
} @catch (NSException *e) {
    NSLog(@"Caught exception %@", e);
}
```

From: exception.m

The above shows the basic usage of @try-catch in Objective-C. The `@try` block contains the code that might throw an exception. The `@catch` block contains the code that runs if an exception is thrown. You can have multiple `@catch` blocks, one for each type of exception.

```objectivec
@try {
    [array objectAtIndex:0];
} @catch (NSRangeException *e) {
    NSLog(@"Caught range out of bounds: %@", e);
} @catch (NSIndexOutOfRangeException *e) {
    NSLog(@"Caught index out of range: %@", e);
} @catch (NSException *e) {
    NSLog(@"Caught exception: %@", e);
}
```

The `@catch` blocks are tried from most specific to least general. The first block that matches the exception type is executed.

You can also use a `@finally` block, which runs regardless of whether an exception was thrown or caught.

```objectivec
@try {
    [array objectAtIndex:0];
} @catch (NSException *e) {
    NSLog(@"Caught exception: %@", e);
} @finally {
    NSLog(@"Cleaning up...");
}
```

The `@finally` block is useful for cleaning up resources, such as closing files or releasing memory.

## Throwing and Catching Exceptions 244

To throw an exception, use the `@throw` keyword.

```objectivec
[NSException raiseWithName:@"MyException" 
                          reason:@"Something went wrong" 
                             code:0];
```

You can also create your own exception classes by subclassing `NSException`.

```objectivec
@interface MyException : NSException
@property (copy, retain) NSString *customData;
@end

@implementation MyException
- (instancetype)initWithReason:(NSString *)reason code:(NSInteger)code customData:(NSString *)customData {
    self = [super initWithReason:reason code:code userInfo:nil];
    if (self) {
        _customData = customData;
    }
    return self;
}
@end
```

Then you can throw your custom exception:

```objectivec
MyException *e = [[MyException alloc] initWithReason:@"Error" code:404 customData:@"Some data"];
@throw e;
```

Throwing exceptions is generally discouraged for control flow. It is better to use return codes or result objects. Exceptions should be used for truly exceptional circumstances.
