当你再次调用 linkedCounters() 函数时，你将获得一对新的块，它们引用一个新的计数器变量。请注意 `static` 和 `__block` 存储限定符的区别。它们都有相似的效果，都会将变量从栈上移出，并允许其生命周期比函数更长，但它们的工作方式非常不同。

当你将一个变量声明为 `static` 时，对它的每一个引用都将指向同一块内存。当你将一个变量声明为 `__block` 时，来自同一作用域对它的每一个引用都指向同一块内存，但每当你进入声明该变量的作用域时，你都会获得一个新副本。

## 使用 Blocks 管理内存

```
block int counter;
int(^block)(void) =
^(void) { return counter++; };
block = [block copy];
Block_release(block);
```

来源：blockMemory.m

Cocoa 的内存管理传统上使用引用计数。Blocks 的工作方式相同。有两个函数控制块的引用计数。`_Block_copy()` 函数增加其引用计数，而 `_Block_release()` 函数则减少它。

第一个函数没有命名为 `_Block_retain()`，是为了显式表示返回的块可能不是作为参数传递的那个块。在某些情况下，块可能会被分配在栈上，然后在被复制时复制到堆上。大多数时候，你不会直接调用这些函数。相反，你将使用不带下划线前缀的宏。这些宏封装了函数并确保返回值与参数类型相同。

在 Objective-C 中，你也可以向块发送 `-retain`、`-release` 和 `-autorelease` 消息，就像对待任何其他对象一样。事实上，你可以向块发送任何你想要的消息，但它们只响应少数几个。如果你向块发送任何消息，编译器不会给出警告，但你会得到一个运行时异常。

你应该非常小心地向块发送 `-retain` 消息。该方法的契约要求它返回接收者。你必须使用 `-copy` 来确保栈上的块被复制到堆上。这在垃圾收集模式下尤为重要，在那种模式下 `-retain` 消息会被静忽略。在 ARC 模式下，你完全不需要调用这些函数或发送这些消息：ARC 会为你处理块中所有的内存管理。

块引用的变量的内存管理可能更难理解。`blockRetain.m` 示例展示了两个引用对象的块。第一个获取了对象指针的拷贝，第二个由于 `__block` 存储限定符而获得了共享引用。

```
id a = [@"a" mutableCopy];
_block b = [@"b" mutableCopy];
unsigned long (^refCountA)() = ^(
{ return [a retainCount]; };
unsigned long (^refCountB)() = ^(
{ return [b retainCount]; };
printf("%ld%ld\n", refCountA(), refCountB());
refCountA = Block_copy(refCountA);
refCountB = Block_copy(refCountB);
printf("%ld%ld\n", refCountA(), refCountB());
[refCountA release]; [refCountB release];
printf("%ld%ld\n", [a retainCount], [b retainCount]);
```

来源：blockRetain.m

第二个块的情况并非如此。该块已经被释放，因此向它发送消息将产生未定义行为。在这次特定的运行中，它从随机内存位置返回了一些数据。它也可能导致崩溃。

确保对象在一个或多个块持续存在期间保持有效是你的责任。要正确做到这一点非常困难，因为与对象不同，块没有注册清理代码的方法。如果你在 ARC 模式下编译，这个问题就会解决。块会自动保留存储在它们的绑定变量中的任何对象，并在块本身销毁时释放它们。

当块引用其他指针时，这也是一个问题。即使指针没有 `__block` 存储限定符，它所引用的内存也不会被。这意味着你必须像跟踪 C 中的任何其他内存一样跟踪它，增加的复杂性在于，包含该引用的块可能会持续很长时间。

## 在后台执行操作

```
dispatch_queue_t q =
    dispatch_get_global_queue(0,0);
__block int count;
dispatch_async(q, ^(void){count++;});
sleep(1);
NSAssert(count == 1,
    @"Counter incremented in background");
```

来源：libdispatch.m

如果你在 OS X 10.6 上使用 Cocoa 或在 FreeBSD 上使用 GNUstep，那么你可以选择 libdispatch（Apple 命名为 Grand Central Dispatch）进行并发处理。该库由 Apple 编写并在 Apache 2 下发布。如果你使用 libdispatch，你不需要手动管理线程，而是管理工作队列。

工作队列执行代码单元。队列有两种类型：并发队列（concurrent）和先进先出（FIFO）。并发队列将按照它们被添加到队列的顺序开始执行工作单元，但可能会同时执行多个。FIFO 队列会在启动下一个单元之前等待每个单元完成。线程之间的上下文切换相对昂贵。它的开销显然至少相当于 `setjmp()`，因为需要保存当前状态并在稍后恢复，但还有一些不显见的成本。不同的线程可能同时访问程序数据的不同部分，因此切换线程也会导致大量的缓存和 TLB 缺失。

使用工作队列模型，单个线程可以运行来自一个队列的单元，然后运行另一个队列的单元，而无需不断在工作集之间切换。如果你有更多的核心，你可以增加并发程度以利用它们，而不会增加上下文切换的次数。当系统忙碌时，你可以减少应用程序使用的线程数，使其能够有效利用一个核心。所有这一切都由 libdispatch 自动完成。

Grand Central 不依赖于块，但结合块一起使用要容易得多。在最简单的情况下，你只需要将块推入工作队列并让它们在后台执行。这就是本节开头示例所做的的。它获取了默认优先级队列的句柄并将块推入其中。队列会在有空闲 CPU 时间后在后台执行它。

## 创建自定义工作队列

```
dispatch_queue_t q =
dispatch_queue_create("Example",0);
__block int count;
dispatch_async(q, ^(void){ count++; });
dispatch_async(q, ^(void){ count++; });
dispatch_async(q, ^(void){ count++; });
dispatch_async(q, ^(void){ printf("%d\n", count); });
```

来源：libdispatch

FIFO 自带三个并发队列，这些是默认创建的。这些队列注册在三个优先级级别：低、默认和高。每个队列上并发运行的任务数量取决于系统的负载和可用的 CPU 核心数。你可以使用上一节中看到的 `dispatch_get_global_queue()` 函数获取其中一个队列的句柄。
