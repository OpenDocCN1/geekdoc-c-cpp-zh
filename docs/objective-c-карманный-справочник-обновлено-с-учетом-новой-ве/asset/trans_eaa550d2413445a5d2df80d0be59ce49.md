

# 使用异常对象

```
[NSException raise: NSGenericException format: "@This is an example"];
```

来自：throwexception.m

NSException 类曾用于实现一个 `longjmp()` 缓冲区栈，并在需要时跳转到栈顶部的缓冲区。现在，回栈操作已完全由运行时和回栈库完成，但 NSException 仍然用于封装异常。

异常包含三个部分：名称（name）、原因（reason）和用户信息字典（user info dictionary）。名称是该类型异常的唯一标识符。它只是一个字符串，但通常会使用符号常量（例如 `NSRangeException`），以便在捕获异常时可以对异常名称进行指针比较。

描述（description）是一段人类可读的描述。这通常只用于调试，因此本地化并不重要。你理解发生了什么比你的用户理解发生了什么更重要。最后，用户信息字典是一个包含某些键值对的 `NSDictionary`。这里的内容完全取决于抛出异常的代码，尽管大多数抛出异常的方法都会说明它们会在用户信息字典中放入什么内容。

你可以用此将任意信息传递到捕获异常的地方。因为它是字典，你可以决定稍后添加一些额外的键，而不会破坏与现有代码的二进制兼容性。这是通常使用不可变字典（即 `NSDictionary` 而不是 `NSMutableDictionary`）的情况之一，因为捕获异常的代码并不期望能够修改它。如果你要为异常附加一个字典，通常会使用 `NSDictionary` 的 `+dictionaryWithValuesAndKeys:` 构造函数来创建一个一次性的不可变字典并抛出。

在最近版本的 OS X 上，异常对象还包含一些用于调试的额外信息。向它发送 `-callStackReturnAddresses` 消息将给你一个包含 `NSNumber` 的 `NSArray`，这些数字指向栈上所有函数的返回地址。这并不特别有用，但 OS X 10.6 引入的 `-callStackSymbols` 方法就很有用。它能提供异常创建时栈上所有函数的名称。

后者方法由未处理异常的处理器（unhandled exception handler）使用，每当异常回栈未被捕获时，它就会被调用，在程序中止前打印堆栈跟踪。你可能希望使用 `NSUncaughtExceptionHandler()` 函数将该处理器替换为你自己的程序。如果你有错误报告机制，那么拥有未处理异常的堆栈跟踪将非常有用。

# 使用统一异常模型

```
try {
    @throw @"An exception!";
} catch (int a) {
    NSLog(\@"Caught: %d", a);
} catch (id exception) {
    NSLog(\@"Caught: %@", exception);
}
```

来自：tryCatch.mm

在早期的 Objective-C++ 实现中，Objective-C 和 C++ 的异常模型是完全不同且不兼容的。你可以使用 `throw` 抛出 C++ 异常并使用 `catch` 捕获它们。你可以使用 `@throw` 抛出 Objective-C++ 异常并使用 `@catch` 捕获它们。你可以在程序中混合这两种，但不能在同一个函数内，也不能针对同一个异常。

在最近的实现中，Objective-C++ 使用统一的异常模型。带有 Objective-C 类型的 `catch` 语句可以捕获由 `@throw` 抛出的对象。同样，带有 Objective-C 类型的 `throw` 语句产生的异常可以被 `@catch` 捕获。

本节开头的代码片段在一个简单易用的案例中展示了这种操作。旧的 Objective-C++ 编译器会拒绝它。你可以用它来检查你的目标是否支持统一异常模型。

# 使用异常管理内存

```
id pool = [NSAutoreleasePool new];
id array = [NSArray new];
@try
{
    throw(array);}@catch (id e)
{
    NSLog("Caught exception %@", e);
    e = [e retain];
    [pool drain];
    [e autorelease];
    pool = nil;
    @throw;
}
finally
{
    [array release];
    [pool drain];
}
```

来自：releaseexcept.m

异常处理让内存管理变得稍微复杂。如果你在方法中创建了一个新对象并在结束时释放它，你必须考虑到异常实际上是一种浅伪装的非局部跳转（non-local goto），并且突然有很多方法可以从你的方法返回。每一个函数调用或消息发送都变成了一个潜在的返回路径。你可以通过在 `@try` 块末尾添加 `@finally` 块来轻松地解决这个问题。无论是通过到达末尾退出 `@try` 块还是通过抛出异常退出，该块中的代码始终会被执行。

你可能遇到的异常遇到的另一个问题是重新抛出已释放的异常。异常对象通常是自动释放的（autoreleased）。这意味着，在手动内存管理下，它们会在当前 `autorelease` 池被删除时被删除。

在大多数代码中这不是问题。你通常使用的 `autorelease` 池持续于整个运行循环（run loop）。然而，有时你会创建自己的 `autorelease` 池。

如果你在 `@finally` 块中释放了你的 `autorelease` 池（这似乎是显而易见的解决方案），你就会遇到一个问题。异常对象会在回栈穿过你的栈帧时被删除，而上上一个栈帧可能会在查找异常类型时由于引用了悬空指针而崩溃。

为了避免这种情况，你需要确保在删除 `autorelease` 池之前 `retain` 异常对象，并在之后对其进行 `autorelease`。这就是为什么抛出 `NSArray` 对象以外的任何内容都是坏主意之一。任何遵循 Apple 文档中此类建议的人最终得到的代码只能处理 `NSArray` 对象，并过早地破坏任何其他对象类型。

注意：在 Java 中，将异常作为局部跳转的通往 VM 的路径是不寻常的，通过在同一个方法中抛出并捕获异常来实现。在 Objective-C 中这也是可能的，但效率极低。`@throw()` 语句会调用 `obj_exception_throw()` 函数，该函数会调用一个回栈库函数。

这将读取栈帧的 DWARF 数据并调用 Objective-C 的个性函数（personality function）。该函数将随后读取更多 DWARF 数据，比较异常的类与 `catch` 块的类，并将指令指针指向 `catch` 语句的地址。

在 Java 中，VM 将将其翻译为到 `catch` 块的无条件跳转。如果你必须使用这种模式，请在 Objective-C 中使用 C `goto` 语句。然而，通常最好完全避免它，并找到不忽略结构化编程思想的解决方案。

# 传递错误代理

```
NSFileManager *fm = [NSFileManager defaultManager];
[fm copyPath:source toPath:destination handler:[ErrorHandler new]];
```

来自：errorderelegate.m

在 Common Lisp 中，你有可恢复异常（resumable exceptions）的概念。这些与 Objective-C、Java、C++ 等语言发现的回栈异常形成对比。可恢复异常不会回栈；它运行异常处理代码然后继续执行。
