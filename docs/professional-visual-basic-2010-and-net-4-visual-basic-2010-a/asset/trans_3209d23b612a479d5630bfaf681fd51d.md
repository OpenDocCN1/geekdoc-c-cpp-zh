

## 对元数据的更好支持

与 Visual Basic 6 组件关联的元数据分散在多个位置并使用多种格式存储：

- 指示 Visual Basic 运行时如何行为的元数据（如 Unattended Execution 属性）被编译到 Visual Basic 生成的可执行文件中。
- 基本 COM 属性（如所需的线程模型）存储在注册表中。
- COM+ 属性（如所需的事务支持）存储在 COM+ 目录中。

.NET 在三个重要方面改进了应用程序中元数据的使用：

- .NET 整合了与组件关联的元数据。
- 因为 .NET 组件不需要注册，安装和升级组件更容易且问题更少。
- .NET 对应仅在编译时设置的属性和可在运行时修改的属性做出了更清晰的区分。

> 与 Visual Basic 组件关联的所有属性都以通用格式表示并整合在构成程序集的文件中。

由于 COM/COM+ 组件的大部分元数据与可执行文件分开存储，安装和升级组件可能会有问题。COM/COM+ 组件必须注册以更新注册表/COM+ 目录后才能使用，并且 COM/COM+ 组件可执行文件可以在不升级其关联元数据的情况下升级。

安装和升级 .NET 组件的过程大大简化了。因为与 .NET 组件关联的所有元数据都必须驻留在包含该组件的文件中，因此不需要注册。将新组件复制到应用程序目录后即可立即使用。由于组件及其关联的元数据不可能不同步，升级组件的问题大大减少。

COM+ 的另一个问题是，应仅在编译时设置的属性可能在运行时重新配置。例如，COM+ 可以为中性组件提供序列化支持。不需要序列化的组件必须设计为能够同时处理来自多个客户端的多个请求。你应该在编译时知道组件是否需要运行时序列化支持。然而，在 COM+ 下，描述是否应序列化客户端请求的 attribute 可以在运行时更改。

.NET 对应应设置在编译时的属性和应设置在运行时的属性做出了更好的区分。例如，.NET 组件是否可序列化是在编译时确定的。此设置不能在运行时覆盖。

## 属性

属性用于用附加信息装饰实体，例如程序集、类、方法 和 属性。属性可用于多种目的。它们可以提供信息、在运行时请求特定行为，甚至从另一个应用程序调用特定行为。以下代码块中定义的 Demo 类的使用可以演示这一点：

```
Module Module1
    <Serializable()> Public Class Demo
        <Obsolete("Use Method2 instead.")> Public Sub Method1()
            ' Old implementation …
        End Sub
        Public Sub Method2()
```

```
' New implementation ...
End Sub
End Class
Public Sub Main()
    Dim d As Demo = New Demo()
    d.Method1()
End Sub
End Module
```

> 代码片段来自 ProVB_Attributes\Module1.vb

通过选择 File ⇨ New Project 并选择 Windows Forms Application 创建 Visual Basic 的新控制台应用程序，然后通过将上述代码复制到 Module1 将新类添加到示例文件中。最佳实践是将每个类放在其自己的源文件中，但为了简化此演示，类 Demo 已在主模块中定义。

Demo 类上的第一个属性用 Serializable 属性标记该类。基类库将为 Demo 类型的实例提供序列化支持。例如，ResourceWriter 类型可用于将 Demo 类型的实例流式传输到磁盘。第二个属性与 Method1 关联。Method1 已被标记为已过时，但仍然可用。当方法被标记为已过时时，有两个选项之一是 Visual Studio 应阻止应用程序编译。然而，对于大型应用程序来说，更好的策略是首先将方法或类标记为已过时，然后在下一个版本中阻止其使用。前面的代码会导致 Visual Studio 在应用程序中引用 Method1 时显示 IntelliSense 警告，如图 4-1 所示。不仅带有 Method1 的行有问题的视觉提示，而且任务窗口中也自动添加了一个任务。

## 反射 API

.NET Framework 提供了反射 API 来访问与托管代码关联的元数据。你可以使用反射 API 检查与程序集及其类型关联的元数据，甚至检查当前执行的程序集。

System.Reflection 命名空间中的 Assembly 类可用于访问程序集中的元数据。LoadFrom 方法可用于加载程序集，而 GetExecutingAssembly 方法可用于访问当前执行的程序集。然后可以使用 GetTypes 方法获取程序集中定义的类型集合。

也可以直接从该类型的实例访问类型的元数据。因为每个对象都派生自 System.Object，所以每个对象都支持 GetType 方法，该方法返回一个 Type 对象，可用于访问与该类型关联的元数据。

Type 对象公开了许多方法和属性来获取与类型关联的元数据。例如，你可以通过调用 GetMembers 方法获得类型公开的属性、方法、字段和事件的集合。对象的基类型的 Type 对象也可以通过调用 DeclaringType 属性获得。

一个展示反射强大功能的良好工具是 Lutz Roeder 的 Reflector for .NET（见 www.red-gate.com/products/reflector）。除了核心工具之外，你还可以在 www.codeplex.com/reflectoraddins 找到与该工具相关的多个插件。

## IL 反汇编器

随 Visual Studio 一起提供的众多实用工具之一是 IL 反汇编器（ildasm.exe）。它可用于浏览模块内的元数据，包括模块公开的类型及其属性和方法。IL 反汇编器还可用于显示模块中包含的 IL。

你可以在 Visual Studio 2010 的安装目录下找到 IL 反汇编器；默认路径为 C:\Program Files\Microsoft SDKs\Windows\v7.0A\Bin\ILDasm.exe。启动 IL 反汇编器后，选择 File → Open。打开 mscorlib.dll，它位于你的系统目录中，默认路径为 C:\Windows\Microsoft.NET\Framework\V4.0.21006\mscorlib.dll。加载 mscorlib.dll 后，ILDasm 将为此程序集中的每个命名空间显示一组文件夹。展开 System 命名空间，然后展开 ValueType 命名空间，最后双击 Equals 方法。将显示一个类似于图 4-3 的窗口。

IL 反汇编器是学习特定模块如何实现的实用工具，但它可能会危及公司的专有逻辑。毕竟，有什么能阻止某人使用它来逆向工程你的代码呢？幸运的是，Visual Studio 2010 与之前版本的 Visual Studio 一样，附带了一个名为混淆器的第三方工具。混淆器的作用是确保 IL 反汇编器无法构建你应用程序逻辑的有意义表示。

对随 Visual Studio 2010 一起提供的混淆器的完整讨论超出了本章的范围，但要访问此工具，请选择 Tools 菜单并选择 Dotfuscator Community Edition。混淆器针对你的编译后应用程序运行，获取你的 IL 文件并删除编译过程中默认嵌入的许多项目。
