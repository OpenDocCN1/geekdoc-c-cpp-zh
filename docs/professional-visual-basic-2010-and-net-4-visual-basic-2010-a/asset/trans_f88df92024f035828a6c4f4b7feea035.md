对于不熟悉 ProgID 术语的读者，了解 ProgID 是用于标识组件的开发者友好字符串就足够了。例如，Word.Application 描述的是 Microsoft Word。ProgID 可以与组件的目标版本一起完全限定——例如，Word.Application.10——但这是一种有限的能力，并且依赖于应用程序本身以及使用者是否选择此可选附加项。正如你在第 7 章中将会看到的，一个命名空间是基于 ProgID 的基本元素构建的，但提供了更强大的命名系统。

对于许多应用程序而言，.NET 已消除了在机器上的中央注册表中标识每个程序集版本的需要。然而，一些程序集是安装一次后被多个应用程序使用。.NET 提供了全局程序集缓存（GAC），用于存储 intended for use by multiple applications 的程序集。CLR 为 GAC 中加载的所有组件提供版本支持。

CLR 为安装在 GAC 内的程序集提供了两个功能：

- Side-by-side versioning — 可以同时在 GAC 中存储同一组件的多个版本。
- Automatic Quick Fix Engineering (QFE) — 也称为热修复支持，如果 GAC 中有与旧版本兼容的新组件版本可用，CLR 将加载更新的组件。版本号由创建引用程序集的开发者维护，驱动此行为。

程序集的清单包含引用程序集的版本号。CLR 在运行时使用程序集的清单来定位每个引用程序集的兼容版本。程序集的版本号采用以下形式：

```
Major.Minor.Build.Revision
```

## Major.Minor.Build.Revision

对程序集的主版本号和次版本号的更改表示程序集与之前的版本不再兼容。CLR 不会使用主版本号或次版本号不同的程序集版本，除非明确指示这样做。例如，如果一个程序集最初是针对版本号为 3.4.1.9 的引用程序集编译的，那么 CLR 不会从 GAC 加载程序集，除非其主版本号和次版本号分别为 3 和 4。

递增修订号和内部版本号表示新版本仍与之前版本兼容。如果具有递增修订号或内部版本号的新程序集被加载到 GAC 中，则 CLR 仍可以为引用了之前版本的应用程序加载此程序集。

## Better Deployment

使用早期版本的 Visual Basic 和 COM 编写的应用程序通常部署起来很复杂。应用程序引用的组件需要安装和注册（此信息存储在注册表中）；对于 Visual Basic 组件，还需要有正确的 Visual Basic 运行时可用。组件部署工具有助于创建复杂的安装包，但如果在安装无关产品期间客户端计算机上的依赖组件被意外替换为不兼容的版本，应用程序很容易被破坏。

在 .NET 中，大多数组件无需注册。当引用外部程序集时，应用程序决定是使用全局副本（必须位于开发者的系统上的 GAC 中）还是将组件本地复制。对于大多数引用，外部程序集是本地引用的，这意味着它们包含在应用程序的本地目录结构中。使用外部程序集的本地副本使 CLR 能够支持同一组件不同版本的并行执行。如前所述，要引用全局注册的程序集，该程序集必须位于 GAC 中。GAC 提供了一个足够强大的版本系统，允许同一外部程序集的不同版本并存。例如，一个应用程序可以使用更新版本的 ADO.NET，而不会对依赖于早期版本的另一个应用程序产生不利影响。

只要客户端安装了 .NET 运行时（只需安装一次），.NET 应用程序就可以使用如下简单命令进行分发：

```
xcopy \\server\appDirectory "C:\Program Files\appDirectory" /E /O /I
```

前面的命令会将 \\server\appDirectory 的所有文件和子目录复制到 C:\Program Files\appDirectory，并会传输文件的访问控制列表（ACL）。

除了复制应用程序的能力外，Visual Studio 还提供了一个内置工具来构建简单的 .msi 安装。部署设置可以为你的项目解决方案进行自定义，使你能够将部署项目与应用程序输出集成。此外，Visual Studio 2005 引入了创建“ClickOnce”部署的能力。

ClickOnce 部署提供了一种全新的部署方法，称为 *smart-client deployment*。在智能客户端模型中，你的应用程序放置在中央服务器上，客户端从该服务器访问应用程序文件。智能客户端部署基于你正在学习的 XML Web Services 架构。它具有集中式应用程序维护的优势，结合了更丰富的客户端界面和更少的服务器通信需求，所有这些你都在 Windows Forms 应用程序中熟悉过。

## CROSS-LANGUAGE INTEGRATION

在 .NET 之前，使用其他语言编写的代码进行互操作是具有挑战性的。重用其他语言开发的功能基本上只有两种选择：COM 接口或导出 C 函数的 DLL。至于在 Visual Basic 中公开功能，唯一的选择是创建 COM 接口。

由于 Visual Basic 现在建立在 CLR 之上，因此它能够与用其他 .NET 语言编写的代码进行互操作。它甚至能够从用其他语言编写的类派生。为了支持这种功能，CLR 依赖于一种表示类型的方式，以及可以描述这些类型的丰富元数据。

### The Common Type System

每种编程语言似乎都带来自己的数据类型岛。例如，早期版本的 Visual Basic 使用基本或二进制字符串（BSTR）结构表示字符串，C++ 提供 char 和 wchar 数据类型，而 MFC 提供 CString 类。此外，由于 C++ int 数据类型是 32 位值，而 Visual Basic 6 Integer 数据类型是 16 位值，因此在不同语言编写的应用程序之间传递参数变得困难。

为了解决这个问题，C 已成为多语言程序之间接口的最低公分母。用 C 编写的导出函数，公开简单的 C 数据类型，可以被 Visual Basic、Java、Delphi 和各种其他编程语言使用。事实上，Windows API 以一组 C 函数的形式公开。

不幸的是，要访问 C 接口，你必须显式地将 C 数据类型映射到语言的本机数据类型。例如，Visual Basic 6 开发者会使用以下语句来映射 GetUserNameA Win32 函数（GetUserNameA 是 GetUserName 函数的 ANSI 版本）：

```
’ Map GetUserName to the GetUserNameA exported function
’ exported by advapi32.dll.
’     BOOL GetUserName(
’         LPTSTR lpBuffer, // name buffer
’         LPDWORD nSize // size of name buffer
’     );
Public Declare Function GetUserName Lib "advapi32.dll" _
Alias "GetUserNameA" (ByVal strBuffer As String, nSize As Long) As Long
```

此代码显式地将 lpBuffer C 字符数组数据类型 LPSTR 映射到 Visual Basic 6 String 参数 strBuffer。这不仅繁琐，而且容易出错。偶然将声明为 Long 的变量映射到 lpBuffer 不会产生任何编译错误，但调用该函数很可能会导致难以诊断的、间歇性的运行时访问冲突。

COM 提供了一种更精细的语言间互操作方法。Visual Basic 6 引入了所有支持 COM 的应用程序的通用类型系统（CTS）——即变体兼容的数据类型。然而，对于非 Visual Basic 6 开发者来说，变体数据类型与构成变体数据类型的底层 C 数据结构（如 BSTR 和 SAFEARRAY）对于 Visual Basic 开发者一样繁琐。结果是，未托管语言之间的接口仍然比必要的更复杂。

CTS 为所有编程语言提供了一组通用数据类型。它为运行在 .NET 平台上的每种语言提供一组基本类型，以及扩展这些类型的机制。这些类型可以实现为类或结构体，但在任何情况下，它们都派生自通用的 System.Object 类定义。

由于 CTS 支持的每种类型都派生自 System.Object，因此每种类型都支持一组常见的方法，如表 4-1 所示。

### TABLE 4-1: Common Type Methods

| METHOD | DESCRIPTION |
|---|---|
| Boolean Equals(Object) | 用于测试与另一个对象的相等性。引用类型应在其 Object 参数引用同一对象时返回 True。值类型应在其 Object 参数具有相同值时返回 True。 |
| Int32 GetHashCode() | 生成对应于对象值的数字。如果两个相同类型的对象相等，则它们必须返回相同的哈希码。 |
| Type GetType() | 获取可用于访问类型相关元数据的 Type 对象。它也是 Reflection API 暴露的对象层次结构导航的起点（稍后讨论）。 |
| String ToString() | 默认实现返回对象类的完全限定名称。此方法通常被重写以输出对类型更有意义的数据。例如，所有基本类型都将其值作为字符串返回。 |

### Metadata

元数据是使组件能够自描述的信息。它用于描述 .NET 组件的许多方面，包括类、方法和字段，以及程序集本身。元数据被 CLR 用于促进各种行为，例如在程序集执行前验证程序集，或在托管代码执行时执行垃圾回收。Visual Basic 开发者多年来在开发和使用应用程序中的组件时就一直使用元数据：

- Visual Basic 开发者使用元数据来指示 Visual Basic 运行时如何行为。例如，你可以设置 Unattended Execution 属性来确定未处理的异常是在屏幕上的消息框中显示还是写入事件日志。
- Visual Basic 应用程序中引用的 COM 组件具有伴随的类型库，其中包含有关组件、其方法和其属性的元数据。你可以使用对象浏览器查看此信息。 （类型库中包含的信息是驱动 IntelliSense 的内容。）
- 可以通过将组件安装在 COM+ 中来与其关联额外的元数据。存储在 COM+ 中的元数据用于声明组件在运行时需要的支持，包括事务支持、序列化支持和对象池。
