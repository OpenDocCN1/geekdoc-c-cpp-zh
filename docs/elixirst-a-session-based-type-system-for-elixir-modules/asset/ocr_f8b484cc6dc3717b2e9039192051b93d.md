# 3.1. The actor model

Elixir uses the actor concurrency model [2,3]. It describes computation as a group of concurrent processes, called actors, which do not share any memory and interact exclusively via asynchronous messages. Every actor is identified via a unique process identifier (_pid_) which is used as the address when sending messages to a specific actor. Messages are communicated asynchronously, and stored in the mailbox of the addressee actor. An actor is the only entity that can fetch messages from its mailbox, using pattern matching. This allows us to provide a static behavioural abstraction for public functions used for the service handler design pattern. Apart from sending and reading messages, an actor can also spawn other actors and obtain their fresh _pid_ as a result; this _pid_ can be communicated as a value to other actors via messaging, which allows for a dynamically linked structure amongst active actors.

# 3.2. Session types

The ElixirST type system assumes the standard expression types, including basic types, such as boolean, number, atom and pid, and inductively defined types, such as tuples, {_T_<sub>1</sub>, ..., _T<sub>n</sub>_}, and lists, [_T_]; these already exist in the Elixir language and they are dynamically checked. The type system extends these with (binary) session types, which are used to statically check the message-passing interactions.

Expression types  \( T ::= \text{boolean} \mid \text{number} \mid \text{atom} \mid \text{pid} \mid \{T_1, \dots, T_n\} \mid [T] \)

Session types  \( S ::= \&\{?l_1(\vec{T}).S_l\}_{l \in I} \quad \text{Branch} \)
\( \mid \oplus\{!l_1(\vec{T}).S_l\}_{l \in I} \quad \text{Choice} \)
\( \mid \text{rec X . S} \quad \text{Recursion} \)
\( \mid \text{X} \quad \text{Variable} \)
\( \mid \text{end} \quad \text{Termination} \)

The branching construct, \(\&\{?l_1(\vec{T}).S_l\}_{l \in I}\), requires the code to be able to receive a message that is labelled by any one of the labels _l<sub>i</sub>_, with the respective list of values of type \(\vec{T}_i\) (where \(\vec{T}\) stands for _T_<sup>1</sup>, ..., _T<sup>k</sup>_ for some \(k \ge 0\)), and then adhere to the continuation session type _S<sub>i</sub>_. The choice construct is its dual and describes the range and format of outputs the code is allowed to perform at that point of execution. In both cases, the labels need to be pairwise distinct. Recursive types are treated equi-recursively [10], and used interchangeably with their unfolded counterparts. For brevity, the symbols \& and \(\oplus\) are occasionally omitted for singleton options, e.g., \(\oplus\{!\text{(number)}.S\}\) is written as \(!\text{(number)}.S\); similarly end may be omitted as well, e.g., ?_l_1 stands for ?_l_1().end. The dual of a session type _S_ is denoted as \(\overline{S}\) (shown in Definition 3.1).

# Definition 3.1 (Duality).

\(\overline{\&\{?l_1(\vec{T}).S_l\}_{l \in I}} = \oplus\{!l_1(\vec{T}).\overline{S_l}\}_{l \in I} \qquad \overline{\text{rec X . S}} = \text{rec X . } \overline{S}\)

\(\overline{\oplus\{!l_1(\vec{T}).S_l\}_{l \in I}} = \&\{?l_1(\vec{T}).\overline{S_l}\}_{l \in I} \qquad \overline{\text{X}} = \text{X} \qquad \overline{\text{end}} = \text{end} \quad \blacksquare\)

# 3.3. Elixir syntax

Elixir programs are organised as modules, i.e., `defmodule m do` \(\vec{P}\) `end`. Modules are defined by their name, _m_, and contain two sets of public \(\vec{D}\) and private \(\vec{P}\) functions, declared as sequences. Public functions, `def f(y,`\(\vec{x}\)`) do end`, are defined by the `def` keyword, and can be called from any module. In contrast, private functions, `defp f(y,`\(\vec{x}\)`) do end`, can only be called from within the defining module. Functions are defined by their name, _f_, and their body, _t_, and parametrised by a sequence of `distinct` variables, \(y, \vec{x}\), the length of which, \(|y, \vec{x}|\), is called the arity.
