**DEFINITION 12:** An execution graph $P$ is a directed graph with form $P(V,E)$ where $|V|$ is an MRJ, $|E|=|e|=\{MRJ_i, MRJ_j \mid MRJ_j, MRJ_i \in V\}$.

Given we say $MRJ_j$ depends on $MRJ_i$, and only if $MRJ_i$'s output is a direct input of $MRJ_j$. A directed edge is added from $MRJ_i$ to $MRJ_j$ in $P$ to specify the execution order. On the contrary, two MRJs are considered independent if they do not connect to the same edge in $P$. According to $P$, independent MRJs can be executed in parallel as long as their direct inputs are ready. MRJ that has a predecessor(s) must wait until its predecessor(s) are finished.

We summarize the general framework of our solution. We map a SPARQL query to MRJs, each of which is either a Join or an Mjoin, and execute the MRJs according to the corresponding $P$. Since there could be many $P$ generated for different selections of Join over $G$, we want to find such a $P$ that guarantees a minimum query processing time. Formally, we define the problem as follows:

**Problem definition:** Given a platform configuration $\Delta$, RDF data statistics $S$, and a query pattern $G$ obtained from a SPARQL query $Q$, find a function $F(\Delta,S,G) \to P(V,E)$ such that

- 1. MRJ's execution time be $t_i$. Let $(i,j)$ denote a path from $MRJ_i$ to $MRJ_j$ in $P$, and the weight of this path be $W_{i,j} = \sum_{k\in i,j} t_k$.
- 2. The $Max\{W_{i,j}\}$ is minimized.

In the problem definition, $W_{i,j}$ indicates the possible minimal execution time from $MRJ_i$ to $MRJ_j$. Therefore, by minimizing the maximum $W_{i,j}$, the overall minimum execution time of $P$ is achieved.

### 9.4.5.1 MRJ Identification and Ordering

The identification and scheduling of MRJs are based on the generated query graph of a SPARQL query. Given $G$, the challenge lies in identifying MRJs such that the corresponding query execution plan $P$ guarantees a minimum query answering time. Even for queries with small BPs and variables, it is impractical to enumerate all possible $Ps$ to find out the optimal solution. Therefore, instead of addressing the generation of $P$ directly, we introduce a tree structure, APJ tree, to represent all possible $P$'s for examination.

First, we consider how two vertices $v_i$ and $v_j$ in $G$ are selected together. If $v_i$ and $v_j$ are the nearest neighbors to each other, no other vertices need to be involved. Otherwise, $v_i$ and $v_j$ together with all the vertices residing on at least one connecting path between $v_i$ and $v_j$ need to be selected. For clear illustration purposes we introduce the Var-BQP concept, which has generalized MRJ types (covers both Pjoin and Mjoin).

**Definition 13:** $e_l^{\{var\}} = \{var\}:\{BQP\}$ is a Var-BQP entity, where $\{var\}$ represents a set of edges labeled with elements of $\{var\}$ in $G$. If $BQP \in \{BQP\}$ does not only incident to edges labeled with elements from $\{var\}$, $BQP$ is marked as optional in $\{BQP\}$, denoted by capping $BQP$, with a wave symbol.

For example, consider a Var-BQP entity “a:{1,2,3}” from Figure 9.8. BQP 2 and 3 are not only incident to edges labeled with “a,” they are considered to be optimal and capped with the wave symbol. Now we can answer the one-step selection condition of vertices $v_i$ and $v_j$ with the Var-BQP concept. Selecting $v_i$ and $v_j$ to compose an MRJ is equivalent to selecting a Var-BQP entity $e$, where $v_{i,j} \in [BQP]$. As described in Section 3, MRJs are identified by iteratively selecting and marking vertices from $G$ until all BJs are marked. Correspondingly, it is an iterative procedure of Var-BQP entities until all BKPs are selected. Then we first define the generic semantic of Var-BQP entities and present steps to build the APJ tree based on the join of Var-BQP entities. We then prove that all possible selection of MRJs are derived from the APJ tree.

**Definition 14:** Two Var-BQP entities $e_i^{\{var\}} = \{var\}:\{BQP_i\}$, and $e_j^{\{var\}} = \{var\}:\{BQP_j\}$ can be joined together if and only if $\{var\} \in \{var\}\pi_i$ or $BQP \in \{BQP\}\pi_j$. Join of two joinable Var-BQP entities is defined as:

```
$e_i^{\{var\}} \bowtie e_j^{\{var\}} = (\{var\}:\{BQP_i\}:\{var\}:\{BQP_j\}) \quad (9.11)
```

Intuitively, if $e_i^{\{var\}}$ and $e_j^{\{var\}}$ do not share a common variable, then there is no index of join. Furthermore, if they do not share a common BQP, there is no overlapping of source data. Thus, the join of $e_i^{\{var\}}$ and $e_j^{\{var\}}$ is logically invalid.

Based on this join semantic of Var-BQP entities, we describe a top-down approach to build an API tree, as presented in Algorithm 9.3. Assume $G$ has $m$ vertices and $n$ edges with distinct labels ($n$ variables). By traversing $G$ and grouping BPs on different variables, we can easily obtain $\{e^j\} = \{e^j\}$. If we apply the join semantics earlier, we can further obtain $\{e^j, e^k\}$. By making each entity a node, and directing edges, we can obtain a tree structure.
