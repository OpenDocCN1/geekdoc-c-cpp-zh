Each application requires a different service procedure. $M$ computing servers are employed to process $M$ classes of applications, in which computing server $i$ is dedicated to service requests for class $i$ application. Since the VMS can be dynamically provisioned and released in the cloud, the number of computing servers can be dynamically changed according to the number of applications. For class-$i$ application, the average task size is denoted by $F_i$ and the execution time is a random variable, which is assumed to follow exponential distribution with average $F_i/C_i$ [32,33]. To maintain a stable queue, the constraint $\lambda^i < C_i/F_i$ must be satisfied. The response time at computing server $i$ is given

```
$T_{FCFS}^{com(i)(t)} = \frac{F_i/C_i}{1-\lambda^i/C_i}$
```

Therefore, the average response time in computation phase can be formulated as

```
$T_{FCFS}^{com(t)} = \mathbf{\hat{A}}(1/\lambda^i \cdot T_{FCFS}^{com(i)(t)}) = \mathbf{\hat{A}} \frac{F_i/C_i}{\lambda^i(1-\\lambda^i/C_i)}$
```

After processing, all service results are sent to the transmission queue. Since a result is requested for each and the service is a closed system, the average arrival rate of the results at the transmission queue is $\lambda$$. For class-$i$ application, the average result size is denoted by $D_i$. Different applications have different result sizes, leading to different transmission time. The transmission time for the class-$i$ service is exponentially distributed with mean service time $D_i/B$, where $B$ is the bandwidth resource at the transmission server. Therefore, the transmission queue can be viewed as a queuing system in which service results are grouped into a single arrival stream and the service distribution is a mixture of $M$ exponential distributions. In fact, the service time follows hyperexponential distribution [30]. The transmission queue is actually an $M/H_M$ queuing system, where $H_M$ represents a hyperexponential $M$ distribution.
