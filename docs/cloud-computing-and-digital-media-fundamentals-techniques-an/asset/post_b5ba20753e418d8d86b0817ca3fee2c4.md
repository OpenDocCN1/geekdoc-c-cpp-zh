**Constructing $G$** By applying Algorithm 9.1, we can minimize the time to evaluate a chain theta-join query using MRJ. However, usually a group of MRJs is needed to evaluate multiway theta-joins. Therefore, we now discuss the construction of $G$, which is a subgraph of the path graph $G_{\sigma}$ and sufficient to serve the evaluation of N-join query $Q$. As already discussed in Section 9.3.2, computing is to enumerate all possible no-edge-repeating paths between any pair of vertices. In fact, a subset of the entire edge collection in $G_{\sigma}$ can be further improved in $T_{opt}$. Therefore we propose two pruning conditions to effectively reduce the search space in this section.

The first intuition is the case that many join conditions are covered by multiple MRJs in $T_{opt}$ is not preferred, because each join condition needs to be evaluated only once. However, it does not imply that MRJs in $T_{opt}$ should strictly cover disjoint sets of join conditions. Because sometimes, by including extra join conditions, the output volume of intermediate results can be reduced. Therefore, we exclude MRJ($e_{\sigma}$) on the only condition that there are other efficient ways to evaluate all the join conditions. Formally, we state the pruning condition in Lemma 1.

> **Lemma 1** $e$ should not be considered if there exists a collection of edges $ES$, and the following conditions are satisfied: (1) $L(e) \subseteq \Omega \cup \bigcup_{\sigma \subseteq ES} L(\sigma)$ (2) $w(e) > M \max_{\sigma \subseteq ES} \{w(\sigma)\}$ and (3) $s(e) \geq \hat{A}_{\sigma \subseteq ES} s(\sigma)$

Lemma 1 is straightforward. If an MRJ can be substituted with some other MRJs that cover at the same number of join conditions and be evaluated more efficiently with less demands on processing units, this MRJ cannot appear in $T_{opt}$. Because $T_{opt}$ is the optimal collection of MRJs to evaluate the query, containing any substitutable MRJ makes $T_{opt}$ sub-optimal. For the second pruning method, we present the lemma that further reduces the search space:

> **Lemma 2**: Given two edges $e$ and $e'$, if $e'$ is not considered and $L(e') \subseteq L(e)$, then $e$ should not be considered either.

PROOF: Since $e$ is not considered, it implies that there is a better solution to cover $L_{e'} \setminus L_e$ and this solution can be employed together with $L_{e'} - L_e$, which is more efficient than computing $L_{e'}$; in one step. Therefore, $L_{e'}$ should not be considered.

Note that Lemma 2 is orthogonal to Lemma 1. Since Lemma 1 decides whether an MRJ should be considered a member of $T_{opt}$, if the answer is negative, we can employ Lemma 2 to directly prune more undesired MRJs. By employing the two lemmas proposed earlier, we develop an algorithm to construct $G$ efficiently in an incremental manner, as presented in Algorithm 9.2.

## Algorithm 9.2: Constructing $G^*$

- **Data:** $G^*$ containing $n$ vertices and $m$ edges, $G^* = \Delta$, a sorted list $WL = \varnothing$;
- **Result:** $G^*$
1. for $i = 1 : n$ do
2. for $j > i$ do
3. for $L = 1 : m$ do
4. if there is an L-hop path from $R_i$ to $R_j$ then
5. $e' \leftarrow$ the L-hop path from $R_i$ to $R_j$
6. if $WL \neq \varnothing$; then
7. scan $WL$ to the first group of edges that cover $e'$
8. apply Lemma 1 to decide whether to report $e'$ to $G^*$
9. if $e'$ is not reported then
10. break // Lemma 2 plays the role
11. insert $e'$ into $WL$ that $WL$ maintains a sequence of edges in the ascending order of $w(e')$

Since we do not care about the direction of a path, meaning $e(v_i, v_j) = e(v_j, v_i)$, we compute the pairwise join paths following a fixed order of vertices (relations). In Algorithm 9.2, we employ the linear scan of a sorted list to help decide whether a path should be reported in $G$. One tricky part in the algorithm is line 4. A straightforward way is to employ distributed file systems (DFS) search from a given starting vertex. The time complexity is $O(m+n)$. However, it introduces redundant work for every vertex to perform this task. A better solution is to run Algorithm 9.2. We first traverse $G_v$, once and record the L-hop neighbor of every vertex. It only $O(m+n)$ time complexity. Then, line 4 can be determined in $O(1)$ time. Overall, the worst time complexity of Algorithm 9.2 is $O(n^2m)$. This happens when $G_v$ is a complete graph. In real practice, due to the sparsity of the graph, Algorithm 9.2 is quick enough to generate $G^*$ for a given $G_v$. As observed in the experiments, $G^*$ can be generated in the time frame of hundreds of microseconds.

After $G^*$ is obtained, we select $T_{opt}$ following the methodology presented in Reference 29, which gives $O[\ln(n)]$ approximation ratio of the optimum.

### 9.4.1 RDF Data Model

As of the World Wide Web Consortium (W3C) standards for describing Web resources and metadata, RDF is designed as a flexible representation of schema-relax or even schema-free information for the semantic-relational model. An RDF triple consists of three components: Subject, Predicate (Property), and Object (Value), which represent that two entities connected by a relationship have a certain value on some property. Thus, RDF data can be visualized as a graph by treating entities as vertices and relationships as edges. Figure 9.7 shows an example of RDF data describing authors and their publications.
