In our implementation, we have designed three types of FileInputFormat with their relevant RecordReader to help control the input for mapper, as shown in Figure 11.12.

In the figure, SRPPartMultiInput and SRMultiFileInputFormat extend MultiInputFormat which is provided by the Hadoop library. Both of them split input files into collections, at least one in a collection. To be different, SRPPartMultiInput reads just part of a file, maybe the first 50 bytes or simply the file name of a file. For instance, when we extract the focal information from a jpg file, we just need to extract the Exif (image format) of the jpg file and then the RecordReader treats the file name as key and the information from Exif as value. SRMultiFileInput is simple, which splits a file from beginning to end. The RecordReader will set the file name as key and the content of the file as value. SRLineTextInputFormat extends TextInputFormat, which is used for text operation. Different from TextInputFormat, SRLineTextInputFormat treats each line as record and attaches additional information such as ID with it. Then RecordReader will define the ID as key and the line as value.

### 11.3.2 Scene Reconstruction Pipeline

This section discusses our system, including four MapReduce modules and the input/output result of each module. In Figure 11.13, we can see the whole reconstruction pipeline.

### 11.3.3 Extract Focal Length

This is the first MapReduce module invoked in our pipeline, and here we assume that all the input images have been uploaded to HDFS. This step is simple: the image is split into N splits, possibly more than map workers. The RecordReader reads the Exif value of each image and then passes to the mapper. In Map function, the system reads the Exif and extracts the focal length of each image. Then FileFileOutput collects the name and focal length of each file and writes it into a single file for future use.

### 11.3.3.4 SIFT Detector

Since no source code is provided from SIFT, the only way to apply SIFT on Hadoop is to invoke external files with the appropriate parameters. The command line format probably looks like:

```
sift $IMAGE_DIR/$PGM_FILE $KEY_DIR/$KEY_FILE
```

Here, sift is the executable file of SIFT and $IMAGE_DIR/$PGM_FILE indicates the position of the input pgm file in the file system and $KEY_DIR/$KEY_FILE defines the position of the output key. If the parameter $KEY_DIR/$KEY_FILE does not exist, sift will output the key to the standard output.

Because our images are mostly jpg images, we must transfer jpg images into pgm images. In our implementation, each input jpg file is treated as a split, and RecordReader will read the whole content of jpg file as value and pass to the mapper. Then two external files are invoked in Map function. First, we throw the content of jpg image into an image transform program and then it will generate a pgm format image. Second, we redirect the output of transform program into SIFT, and then compute the key feature of the relevant pgm image.

### 11.3.3.5 Feature Match

In this MapReduce module, the key list file generated by SIFT is treated as input file. The FileFormat reads each line as value and attributes a line number as key. In the mapper phase, the computed key is implied read: first, all key files are copied to local file system and then mapper invokes the external executable file FeatureFullMatch to find matches between one stationary image and the other images. FeatureFullMatch program is different from provided Bundler-0.3 source, with some modification: only the image that is appointed by ID will execute match function instead of matching all in the list. Then FeatureFullMatch tries to find the key designated in the key list file and generate the match table for that image. After mapper, the generated table will be uploaded to HDFS with the name of “ID.matches.init.” In the reduce phase, each key-value pair will generate one option file that includes the path of match table and some configuration parameters needed for computing F- and H-matrix, named as “ID.options.txt.”

Noting that the latter map job will run much less time than its previous map job because a map job with a small ID will have to compare more images than map job with large ID. For instance, an image set of 415 images, a map job with an ID 1 will try to find matches among 414 images, whereas a map job with a large ID only needs to find matches among 15 images.

### 11.3.3.6 Computing F- and H-Matrix

In this phase, the option file generated by feature match creates a map job. In Map function, similar to feature match, we invoke external files to compute H-matrix. Since F-matrix, H-matrix, and refined matches as well are parallel computed, we must determine what data should be uploaded to HDFS.

### 11.3.3.7 The Left Part of Scene Reconstruction

In scene reconstruction pipeline, two steps are still not transplanted to the Hadoop framework in my implementation:
- (1) computing tracks
- (2) SfM

For the first, since tracks are founded using breadth-first search of features, which is a little hard to parallel, moreover, the wall time cost in this step is very small, about 30 seconds in a total of 23 hours. However, for the second, it is over my knowledge of implementing parallel computing due to its high algorithm complexity. One possible solution proposed in Reference 1 is to divide images into subsets and run more incremental SfMs at the same time. But how the way to divide image set is more reasonable is still hard to figure out. More theory supporters are therefore required to combine the reconstructed scenes into a big one.
