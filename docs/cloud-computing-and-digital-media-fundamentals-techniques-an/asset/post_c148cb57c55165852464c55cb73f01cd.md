According to the definition of $G_{\mathfrak{x}}$, any edge $e'$ in $G_{\mathfrak{x}}$ is a collection of connecting edges in $G_{\mathfrak{J}}$. Thus, $e'$ implies a subgraph of $G_{\mathfrak{J}}$. $G_{\mathfrak{x}}$ edge set represent all the possible MRJs that can be employed to evaluate the original query $Q$. Let $T$ denote a set of MRJs that are selected from $G_{\mathfrak{x}}$ edge set. Intuitively, the MRJs in $T$ cover all the joins of the original query. Formally, we define that $T$ is "sufficient" as follows:

> **Definition 4:** *$T$, a collection of MRJs, is sufficient to evaluate $Q$ iff $U \subseteq G_{\mathfrak{J}}, G_{\mathfrak{E}}$, where $M \in MRJs \neq Q$.

Since it is trivial to check whether $T$ is sufficient, for the rest of this work, we only consider that $T$ is sufficient. Given, $T$, we define our execution plan as a specific execution sequence of MRJs, which minimizes the time span of using $T$ to evaluate the original query $Q$. Formally, we can define our problem as follows:

**Problem definition:** Given an $N$-join query $Q$ and $k_p$ processing units, we want to create a join-path graph $G_{\mathfrak{J}}$ is built. We want to select a collection of edges from $G_{\mathfrak{x}}$ that correspondingly form a set of MRJs, denoted as $T_{opt}$, which minimizes the query evaluation time. Obviously, there are many different choices of $T$ to evaluate $Q$. With limited processing units, different execution plans yield different evaluation time spans. In fact, the determination of MRJ execution order is non-trivial; we give the detailed analysis of the hardness of our problem in the next subsection. As we shall elaborate later, given $T$ and $k_p$ available processing units, we adopt an approximation method to determine line in time.

**Problem hardness:** According to the problem definition, we need two steps to find $T_{opt}$. (1) generate $G_{\mathfrak{J}}$ from $G_{\mathfrak{x}}$, and (2) select MRJs for $T_{opt}$. Neither of these two steps is easy to solve.

For the first step, construct $G_{\mathfrak{J}}$ we need to enumerate all no-edge-repeating paths between any pair of vertices in $G_{\mathfrak{J}}$ Assume has “Eulerian trail” [24], which is a way to traverse the graph with every edge visited exactly once. For any pair of vertices $v_i$, and $v_j$, any different no-edge-repeating path between them is a “subpath” of a Eulerian trail. If we know all the no-edge-repeating paths between any pair of vertices, we can enumerate all the Eulerian trails in polynomial time. Therefore, the complexity of constructing $G_J$ is at least as hard as enumerating all the Eulerian trails of a given graph, which is known to be #complete [25]. Moreover, we find that $G_J$ does not have an Eulerian trail and the problem complexity is not reduced at all, as we elaborate in the proof of the following theorem.

**THEOREM 1:** Generating $G_{J}$ from a given $G_J$ is a #complete problem.

**PROOF:** If $G_J$ has the Eulerian trail, constructing $G_{J}$ is #complete (see the discussion above).$\square$

On the contrary, if $G_J$ does not have the Eulerian trail, it implies that there are $r$ vertices having odd degrees, where $r > 2$. Now consider that we have one virtual vertex and connect it with $r-1$ vertices of odd degrees. Now the graph must have an Eulerian trail. If we can easily construct the join-path of the new graph, the original graph $G_{J}$ can be computed in polynomial time. We elaborate with following example, as shown in Figure 9.4. Assume $v_s$ is added to the original $G_J$. By computing the joinpath of the new graph, we know all the no-edge-repeating paths between $v_i$ and $v_j$. Then, a no-edge-repeating path between $v_i$ and $v_j$ cannot exist if it has $v_s$ involved. By simply removing all the enumerated paths that go through $v_s$, we can obtain the $G_{J}$ of the original $G_J$. Thus, the dominating cost of constructing $G_{J}$ is still the enumeration of all Eulerian trails. Therefore, this problem is #complete.

Although it is difficult to compute the exact G', we find that a subgraph of G', which contains all the vertices and is denoted as G'', could be sufficient to guarantee the optimal quality evaluation efficiency. We take the following principle into consideration. Given the same number of processing units, if it takes longer time to evaluate $R_i \⊉ R_j \⊉ R_k$ compared to the total time cost of evaluating $R_i \⊉ R_j$ and $R_j \⊉ R_k$ separately and merging the results, we not not $R_i \⊉ R_j \⊉ R_k$ into consideration. By following this principle, we can avoid enumerating all the possible no-edge-repeating paths between any pair of vertices. As a matter of fact, we can obtain such a sufficient G in polynomial time.

The second step of our solution is to select $T_{opt}$. Assume the G computed from the first step provides a collection of edges; accordingly, we have a collection of MRJ candidates to evaluate the query. Although each edge in G is associated with a weighted minimum time cost to evaluate the join conditions contained in this edge, it is just an estimated time span over the condition that there are enough processing units. However, when a T is chosen, the number of processing units is limited, the time cost of answering Q needs to be reestimated. We can find the time cost estimation of T, denoted as $C(T)$. The problem is to find an optimal $T_{opt}$ from all possible Ts, which has the minimum time cost. Apparently, this is a variance of the classic set cover problem, which is known to be NP-hard [26]. Therefore, there are some heuristics and approximation algorithms that can be adapted to solve the solution problem.

As clearly indicated in the problem definition, the solution lies in the construction of G'' and smartly selects T based on the cost estimation of a group of MRJs. Therefore, for the rest of the chapter, we shall first elaborate our models for a single MRJ and a group of MRJs. We then present our detailed solution for the N-join query evaluation.

## 9.3.3 Cost Model

We have already presented the execution time model for single MRJ in Section 9.2. In this section, we present a generalized analysis on the execution time of a group of MRJs. In the context of G' construction and T selection, we study the estimation of w (Θ), we G' (Θ), and C(T), which is the time to evaluate T.

There have been some works exploring the optimization opportunity among MRJs running in parallel, as References 4, 5, and 11, by defining multiple types of correlations among MRJs. For instance, Reference 5 defines “input correlation,” “transit correlation,” and "job flow correlation,” targeting the shared input scan and intermediate data partition. In fact, their techniques can be directly plugged into our solution framework.

Given $T$ and $k_p$, we concern processing units, the execution plan that guarantees the minimum task execution order is usually subjected to $k_p$. For instance, the determination of $T$ in Figure 9.5 $MR(e_i)$, $M R(e_j)$, and $M R(e_k)$ can be accomplished in 5, 7, and 9 if units are, 4, and 8 tasks are assigned to them, respectively. Thus, if there are over 16 available processing units, these three MRJs can be scheduled to run in parallel and with no computing competition. On the contrary, if there are not enough processing units, parallel execution of MRJs can lead to very poor time efficiency. It is exactly the classic problem of scheduling independent malleable parallel tasks over bounded parallel processors, which is NP-hard [27]. In this work, we adopt the methodology presented in Reference 27. The method guarantees that for any given $\varepsilon > 0$, it takes linear (in terms of $[T]$, $k_{ps}$ and $\varepsilon^{-1}$) to compute a schedule that promises the evaluation time is at most $(1 + \varepsilon)$ times the scheduling one.
