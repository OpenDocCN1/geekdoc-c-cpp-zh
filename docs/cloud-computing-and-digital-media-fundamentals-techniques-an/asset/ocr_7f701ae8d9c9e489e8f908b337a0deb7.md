# 11.3.3.5 Feature Match

In this MapReduce module, the key list file generated by SIFT is treated as input file. The FileFormat reads each line as value and attributes a line number as key. In the mapper phase, the computed key is implied read: first, all key files are copied to local file system and then mapper invokes the external executable file FeatureFullMatch to find matches between one stationary image and the other images. FeatureFullMatch program is different from provided Bundler-0.3-source, with some modification: only image that is appointed by ID will execute match function instead of matching all in the list. Then FeatureFullMatch tries to find the key designated in the key list file and generate the match table for that image. After mapper, the generated table will be uploaded to the HDFS with the name of “ID.matches.init.” In the reduce phase, each key-value pair will generate one option file that includes the path of match table and some configuration parameters needed for computing F- and H-matrix, named as “ID.options.txt.”

Noting that the latter map job will run much less time than its previous map job because a map job with a small ID will have to compare more images than map job with large ID. For instance, an image set of 415 images, a map job with an ID 1 will try to find matches among 414 images, whereas a map job with ID 400 only needs to find matches among 15 images. This kind of parallel operation will not influence the wall time cost significantly because image number is much larger than the map workers. So there may exist different map numbers data nodes, but almost finish the map jobs at the same time.

Another weak point of this kind of parallel computation is the overhead of I/O and hardware storage, since all map workers will copy the key files from HDFS into local file system for once. However to the large amount of time of running this step, the influence will be relatively small.
