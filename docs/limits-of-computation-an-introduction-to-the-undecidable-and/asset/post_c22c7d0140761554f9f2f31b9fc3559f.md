**Note:** This is really O(|V|²)? What about the steps in “if v is not in
Reachable(v), add it to the set?” Can one check that it is not in
the set in O(1)? Can one add it to the set in O(1)? The answer
to those questions depends on the implementation of the set

added to the set it can be done in O(1) if it is added to
head of the list. In either case, the algorithm is still polynomial,
then perhaps O(|V|²).

## 3.12 BEST AND AVERAGE CASE ANALYSIS

The standard analysis bounds the number of steps taken by any input of
n, so that it is a worst case analysis—if an algorithm is O(n), then the
algorithm takes no more than Kf(n) steps on any input of size n, including
the worst case.

Sometimes it is also useful to speak about the best case, the number of
steps required to solve the easiest instance of size n, or the average
case, the number of steps required over all possible inputs. For
example, in an algorithm to find an element in an unordered list, the best
case finds it in the first position, the worst finds it in the last (or not all), and on average, it should be found approximately in the middle.

The average case can be tricky. For example, consider the case above
of finding an element in a list of length n. If the element is in the first position, one test for equality is required; if in the n. So, for elements the last average number of tests is (1 + 2 + ... + n)/n = (n + 1)/2. But,
if the element is not in the list—in any such case, n tests are done.
So, to do a better case analysis, it would be necessary to know the
probability that the element is found in the list. Here, if it is known that
the item is found in the list p fraction of the time (0 ≤ p ≤ 1), then the average number of tests is p((n + 1)/2) + (1 - p)n.

There is another kind of average that would be more useful—that is, for actual inputs to a real-life problem, what is the average running time? For example, in a situation where elements are almost always found, where most recently used elements are moved to the front of the list, and searches are often for recently used elements, the actual average number of tests for equality done on real inputs might be much less than n/2, maybe even be 2 or 3. This kind of analysis is rarely possible by theorists, since it is not usually possible to describe actual average input. However, in some cases, experimental evidence can be quoted to give usual running times for algorithms used in practice.

## 3.13 TRACTABLE AND INTRACTABLE

The words tractable and intractable have precise definitions in computer science. These roughly correspond to their meanings in English—if something is tractable, it is well behaved; if something is intractable, it is wild, hard to control, and definitely does not have good manners.

## Definition 3.8

A problem is tractable (or feasible) if it has an algorithm of O(p(n)) for some polynomial p(n) in n, the length of the input, and there is a constant K so that no input of size n requires more than Kp(n) steps.

The class P will be the set of decision problems that have O(p(n)).

## Definition 3.9

A problem is intractable (or infeasible) if it has no algorithm of O(p(n)) for any polynomial p(n). Note: This means some problems are proven to be intractable, but many others thought to be intractable but no proof is known.

## COMMENTS

1. What about O(n³)? Is such an algorithm really practical? For some problems, maybe yes. For example, multiplying n matrices has n algorithms.
2. What about intractable problems? Won't they become tractable when someone finds a good algorithm? For some problems, maybe yes. For example, for a long time, linear programming had no known algorithm. Also, the problem PRIME = {p | p is prime integer} was only recently found to have a polynomial algorithm.
3. This definition of tractable has good closure properties—we would like, for example, if f and g are in the set, so is f+g, f*g. As we will see in the next chapter, that is true under this definition.
