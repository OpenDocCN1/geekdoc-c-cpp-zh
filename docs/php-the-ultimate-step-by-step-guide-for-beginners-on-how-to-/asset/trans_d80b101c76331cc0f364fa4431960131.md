

# 第 10 章：数据库最佳实践

既然你已经运行了 MySQL 并创建了数据库，我们应该谈谈数据库设计和保护你的数据库。正如你可能已经意识到的，对数据进行备份是非常关重要的。将 MySQL 加入 PHP 并为你的动态网站整合应用程序是一个极不起的开始。然而，准确地构建你的数据库将非常有帮助。如果你拥有安全性、信息完整性和备份，你就拥有了数据库最重要的部分。我们将在稍后的章节中讨论安全性。

## #10.1 数据库设计

正确地设计数据库对于你应用程序的卓越性能至关重要。就像把打印机放在离办公室很的地方是无效的一样，在糟糕的连接中设置信息会降低工作效率，因为你的数据库服务器将浪费时间搜索信息。在考虑数据库时，请考虑当数据库被使用时会进行哪些类型的查询。例如，某个待购物品的详情是什么？或者，这是否是一个合法的用户名和密码？

## 关系型数据库

MySQL 是一个关系型数据库。关系框架的一个关键元素是信息可以分布在几个表中，而不是像我们的电话目录示例那样。相关信息存储在孤立表中，并允许你通过利用两个表的键将它们组合起来。键就是表之间的连接。选择主键是在设计另一个数据库时你做的最基础选择中最突出的之一。

你必须理解的核心思想是，你必须确保所选的键是唯一的。如果可能两条记录（过去、现在或未来）在某个属性上具有相同的值，请不要使用该属性作为主键。从另一个表中计数键字段以形成表与表之间的连接被称为外键关系，类似于主管与工人，或客户与买家之间的关系。

由于你有了存储相关信息的孤立表，你必须考虑每个表中与不同表中项目相对应的项目数量。

## 关系类型

数据库连接通过以下分类进行量化：

- 一对一连接
- 一对多连接
- 多对多连接

我们将讨论这些每种连接并给出示例。如果你在考虑关系时考虑到家庭结构，那么你就掌握了要领。当你只和一位父母在一起度过时，这是一种特定的关系；当你和父母双方在一起度过时，这是另一种关系。当你获得一个重要的伴侣，你们每一个人——父母、你和你的伴侣——一起做某事时，这就是另一种关系。这与整体的相似性没有区别。所有这些不同类型的连接类似于存放连接流的特定容器。在数据库世界中，这就是你创建的信息。

## 一一对一关系

在一对一关系中，每个项目仅与另一个项目相关联。在在线书店的实例中，客户与其送货地址之间存在协调关系。每个客户必须恰有一个收货地址。

## 标准化

思考你的信息如何连接以及安排它们的最有效方法被称为标准化。信息的标准化是根据连贯的关系将其拆分，以尽可能地减少信息的重复。在大多数情况下，复制的信息会浪费空间并使维护成为一个问题。如果你更改了复制的数据，可能会漏掉某部分并导致数据库中出现不一致。然而，拥有很多东西也是件好事；但数据库将每条信息都放在它们自己的表中将花费大量的处理时间，并且查询会变得复杂。目标是在中间找到平衡。虽然电话目录示例非常简单，但你通过网站准备的类型信息可以从智能收集相关信息中极大获益。我们继续使用在线书店网站。网站需要了解客户信息，包括登录、地址和电话号码，以及关于书籍的数据，包括标题、作者、页数和我们获取的时间。从将大部分此类数据放在一个表中开始。虽然将信息合并到一个表中似乎是一个明智的主意，但它会浪费数据库空间并使信息更新变得重复。所有的客户信息在每次购买时都会重复。一本书受限于两个作者。在这种情况下，我们使用的是具有两个作者的书，而不是仅仅一个。此外，如果客户搬家，他的位置就会改变，表中的每个条目都必须重新设计。

## 规范化的类型

要标准化数据库，请从最基本的标准化原则开始并规律地进行。标准化的过程分为三个阶段，称为结构。

第一步称为第一范式（1NF 或 FNF），必须在第二范结构之前完成。同样，第三种普通结构不能在第二种结构之前完成。标准化过程包括使你的信息与三个动态结构保持一致。

- 第一范式

为了使你的数据库符合第一范式，它必须满足三个要求。任何表不能有包含相同类型信息的重复段，且所有段必须包含唯一值。必须有一个主键来唯一地标识列。它可以是一个段或几个段，取决于预期用多少个段来唯一地标识列。

- 第二范式

虽然第一范式处理了扁平列中信息的重复，但第二范式（或 2NF）处理的是垂直段中信息的重复。

普通结构是动态的。为了实现第二范式，你的表必须处于第二范结构中，你必须识别任何在多个列中重复其属性的段。这些段应该设置在它们自己的表中，并通过第一个表中的键值进行引用。另一种想法是，如果表中存在不属于主键的属性。

- 第三范式

如果你遵循了第一范式和第二范式的过程，你就不需要对你的数据库进行任何操作来满足第三范式（或 3NF）的原则。在第三范式中，你正在寻找表中不完全依赖于主键但依赖于表中另一个值的信息。这适用于你的表何处并不显而易见。在表 8-8 中，地址的部分可以被认为与客户没有直接关联。街道地址取决于邮政分区，邮政分区最后城市取决于州。第三范式要求将这些拆分到孤立表中。

正如你所看到的，第三范式消除了更多的信息重复，尽管是以牺牲易用性和性能为代价的。在这个示例中，你真的预计城市和街道名称会频繁更改吗？在这种情况下，第三范式仍然防止了城市和街道名称的拼写错误。因为这是你的数据库，你决定标准化之间的平衡水平以及你数据库的速度或易用性。
