Let's say, for the values of x, y and z, we use some limited representation (similar to that introduced above) that can only represent numbers between zero and 255, and let's take the case where x = 200 and y = 150. Then,

```
z = \sqrt{200^2 + 150^2}\n= \sqrt{40000 + 22500}\n= \sqrt{62500}\n= 250
```

From this, we can see that, even though the inputs and outputs (150, 200, 250) may be representable, intermediate steps of the calculation may produce overflow execution. Without taking into account this sort of hidden numerical overflow, a program could produce wildly incorrect results without obvious cause (although some programming languages raise exceptions on overflow, many don't). Fortunately, experience of such issues makes us equipped to avoid them: as turns out, the Pythagorean formula above can be rearranged differently, with the following algebra:

```
z = \sqrt{x^2 + y^2}\n=\sqrt{x^2(1 + (y/x)^2)}\n=|x|\sqrt{1 + (y/x)^2}
```

In this formulation, as long the inputs are chosen such that |x| \ge |y|, we have mitigated the danger of overflow from squaring large numbers. In fact, this particular case of overflow crops so often that most programming languages have some sort of using hypot(x,y) function that does just this rearrangement behind the scenes. A good knowledge of the mathematical functions available to a language (not to mention of the maths itself) can help to reduce or remove such problems.

# Loss of precision

One of our Pythagorean example left unexplained is that the square roots of many numbers are not themselves, but real (fractional) numbers; however, so far we've only mentioned integers. Integers can be precisely represented in binary, but real numbers are not straightforward. The simplest way of demonstrating this is by asking a computer to perform some simple arithmetic with real numbers and seeing what happens. Below, we used the interactive command prompt for the Python programming language to ask for the result of the trivial calculation 0.1 + 0.2.

```
>>>0.1 + 0.2\n0.30000000000000004
```

Instead of producing the seemingly obvious value of 0.3, Python returns a number very close to it: 0.30000000000000004. This represents a minuscule error, but an error nonetheless. It isn't Python's fault: we would get the same from Ruby, or JavaScript, or any other programming language we might care to try. So how could a computer make a mistake with such a simple calculation?
