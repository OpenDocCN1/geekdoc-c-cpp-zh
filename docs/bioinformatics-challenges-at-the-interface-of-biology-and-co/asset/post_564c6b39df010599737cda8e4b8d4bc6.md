## 6.3.2 When computers go bad

We'll return to efficiency later in this chapter in the context of designing and implementing algorithms, but we must first concentrate on potentially dangerous technological minefields.

### Numerical overflow

As we've already mentioned, modern computers represent numbers in binary form in their memory and storage. The choice of representation on the platform (processor architecture) is used, and the type of number that needs to be represented. Figure 6.4 shows a variety of decimal integers represented as pure binary digits in 8-bit unsigned integer form. Note that the restriction of eight bits provides upper and lower bounds for the numbers we're able to represent: we can store anything from zero to 255.

We can see that if a number were outside the acceptable range, this representation would break down; what exactly would happen, and how would a program cope? Well, just like a vehicle's odometer, when the number increments beyond the available digits, the digits register overflow back to zero and start again. Under these cases, no matter how unintu it may be, it's possible that 255+1 = 0. It seems obvious that we shouldn't choose a representation that can't handle values we require; in practice, however, it can be difficult to tell what values we need. The moment we start using functions by someone else, what's going 'under the hood' is no longer evident, and some functions could be introducing numerical overflow without us aware of it. Conversely, we may make use of naive calculations that would increase the chance of overflow, when alternative methods may be available to circumvent the risk.

Take, for example, a slightly more complex task: finding the length of the hypotenuse of a right-angled triangle, given the lengths of the other two sides. As you probably know, we can use the Pythagorean formula z = x² + y² to calculate the length, which can be rearranged, as specified:

$z = \sqrt{x^2 + y^2}$

Let's say, for the values of x, y and z, we use some limited representation (similar to that introduced above) that can only represent numbers between zero and 255, and let's take the case where x = 200 and y = 150. Then,

```
z = \sqrt{200^2 + 150^2}
= \sqrt{40000 + 22500}
= \sqrt{62500}
= 250
```

From this, we can see that, even though the inputs and outputs (150, 200, 250) may be representable, intermediate steps of the calculation may produce overflow execution. Without taking into account this sort of hidden numerical overflow, a program could produce wildly incorrect results without obvious cause (although some programming languages raise exceptions on overflow, many don't). Fortunately, experience of such issues makes us equipped to avoid them: as turns out, the Pythagorean formula above can be rearranged differently, with the following algebra:

```
z = \sqrt{x^2 + y^2}
=\sqrt{x^2(1 + (y/x)^2)}
=|x|\sqrt{1 + (y/x)^2}
```

In this formulation, as long the inputs are chosen such that |x| \ge |y|, we have mitigated the danger of overflow from squaring large numbers. In fact, this particular case of overflow crops so often that most programming languages have some sort of using hypot(x,y) function that does just this rearrangement behind the scenes. A good knowledge of the mathematical functions available to a language (not to mention of the maths itself) can help reduce or remove such problems.

### Loss of precision

One of our Pythagorean example left unexplained is that the square roots of many numbers are not themselves, but real (fractional) numbers; however, so far we've only mentioned integers. Integers can be precisely represented in binary, but real numbers are not straightforward. The simplest way of demonstrating this is by asking a computer to perform some simple arithmetic with real numbers and seeing what happens. Below, we used the interactive command prompt for the Python programming language to ask for the result of the trivial calculation 0.1 + 0.2.

```
>>>0.1 + 0.2
0.30000000000000004
```

Instead of producing the seemingly obvious value of 0.3, Python returns a number very close to it: 0.30000000000000004. This represents a minuscule error, but an error nonetheless. It isn't Python's fault: we would get the same from Ruby, or JavaScript, or any other programming language.

The precise representation in memory is somewhat more complicated than this illustration might suggest (see Box 6.1 for an explanation of the floating-point); however, the most important aspect of such fractional systems is their 'coverage'. There are a finite number of values in any integer range, allowing sufficiently wide binary representation to encode all values. However, there are an infinite number of values in any non-trivial real and no representation can encode an infinite number of values in a finite number of bits. This means that there are 'holes' in the real line that a given representation simply cannot encode. In fact, necessarily there are an infinite number of unencodable values. In practice, unencodable values are rounded up or down to the nearest representable number, otherwise practically no calculation would ever succeed. Unencodable numbers are so common that it is almost impossible to come across them in everyday calculations. As we will see at the start of this section, this is true of even the simplest, most common decimals: the value defined using the IEEE 754 single-precision floating-point representation (see Box 6.1). The nearest representable number is the long-wind 0.100000001490116384765625. This represents an error of more than one in a billion. These rounding errors, introduced in the course of everyday computation with floating-point numbers, can cause problems if they're not expected. Even when they are expected, they can be difficult to manage, depending on the application: even minor errors can grow exponentially over the course of a program's lifetime, while each subsequent calculation can multiply that while introducing error itself, pushing the result further away from the ideal mathematical value.
