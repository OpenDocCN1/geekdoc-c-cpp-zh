## 6.4.2 Resource scarcity: complexity of algorithms

In addition to the subtleties of bubble sort introduced above, there are more important qualities of algorithms that result directly from the reality of modern computation. The most obvious answer to a process requires time: there will usually be a time-scale in which a task is expected to complete. This is normally achieved by some interaction with a human being (who, for example, might not wish to wait ten minutes while a computer sorts a scheduler's values), also can be restricted by the needs of other computer systems. Many biological databases, as discussed in Chapter 3, hold quantities of data, and are growing exponentially. Taking, for example, ENA's tally of >230 terabytes of data (Section 3.1), it's clear that developing algorithms for dealing with these size is of paramount importance.

The speed of an algorithm can be described by its time complexity: a measure of how well it performs, in relation to the size of the data it's meant to work on. This measure is often described using the ‘big O notation’, which is mathematical terminology used to describe the behaviour of a function as a particular value (in our naive bubble sort example tends to infinity). In general, it can be thought of as a measure of the algorithms with scaled-up input.

Counting the number of comparisons required in a sorting algorithm is often the best measure of performance; in the algorithm in Figure 6.7, $n-1$ pairs are compared with each other in $n-1$ passes. For a list of size $n$, $(n-1)(n-1)$ comparisons are required to sort the list. The largest-order component $n^2-2n+1$, is $n^2$; therefore, as $n$ tends to infinity, this dominates the behaviour of the algorithm. This gives us bubble sort formulation a time complexity of $O(n^2)$. Even if the naivety were removed, and the algorithm implemented as efficiently as possible, thereby speeding up the general case, it would still exhibit a time complexity of $O(n^2)$. Table 6.1 shows the ordering of some big O magnitudes, and how they measure an algorithm's behaviour (here, the time it takes to complete) as the input size changes.

For small inputs, this tends not to be an issue: modern computers are fast enough, and have enough RAM, to be able to mitigate the effects of inefficient algorithms. However, with increased input sizes, complexity begins to dominate, and efficiency becomes more important. A time complexity of O(n²) means that each time the size of input doubles, the time taken to process effectively quadruples; this increase could cripple a program if expected to process very large amounts of data.

### Table 6.1
Descriptions of how some big O magnitudes behave when the size of input changes. The list begins with the best possible behaviour, O(1), and gets progressively worse.

| Complexity | Description |
| :--- | :--- |
| O(1) | The measure remains constant regardless of the size of input. |
| O(log n) | The measure behaves logarithmically in relation to the input size. |
| O(n) | The measure is linearly proportional to the input size. |
| O(n log n) | Linearith behaviours fall between linear and polynomial. |
| O(n²) | Doubling the input size quadruples compared with input size. |
| O(2^n) | The measure increases exponentially compared with input size. |
| O(n!) | The measure increases factorially compared with input size. |

The other resource an algorithm uses very efficiently is space: during execution, an algorithm must have free access to a certain amount of physical memory. The amount of space required depends on how much data must be manipulated, and how that manipulation takes place. How the required amount of space changes with the size of input is the space complexity of an algorithm, and also described using the big O notation, as a measure of memory usage rather than of time. Even our naïve bubble sort actually does well when measured this way: aside from the space required to store the original list (which doesn't feature in our calculation of memory usage), only one more value in memory is required – the temporary value used during swap. If each item takes one binary unit, then this algorithm uses one extra n to perform its sorting function on a list of size n. This constant gives bubble sort a best-in-show space complexity of O(1); it will always use the same amount of space, regardless of input size.

From here, it is easy to see that an algorithm may be efficient in terms of one resource, but terribly inefficient in terms of another. Indeed, choosing (or designing) the right algorithm for a given task will inevitably involve a compromise between different resources, a compromise that must be made in the context of the specific problem at hand and of its limits.

## 6.4.3 Choices, choices

The example we've been using in this chapter is of a very simple problem (sorting list of numbers) and a very simple solution (the bubble sort algorithm). If this were the only available solution, our jobs would be much straightforward. However, there are many sorting algorithms, each with their own qualities, quirks and complexities in space and time: some work in place, others rely on the fact that their arrays arrive by item; some work better with already partially ordered lists, others rely on specific data. Some of the most used sorting algorithms and their related complexities are shown in Table 6.2, which illustrates the worst-, average-, and best-case complexities and the space complexity, in big O notation.

### Table 6.2
Complexities of some common sorting algorithms.

| :--- | :--- | :--- | :--- | :--- |
| Bubble sort* | O(n²) | O(n²) | O(n) | O(1) |
| Quicksort | O(n²) | O(n log n) | O(n log n) | O(log n) |
| Insertion sort | O(n²) | O(n²) | O(n) | O(1) |
| Merge sort | O(n log n) | O(n log n) | O(n log n) | O(n) |

We see, that when choosing or designing appropriate algorithm to solve a particular problem, we must take into account a range of criteria that may not be apparent on first inspection. Most, include:

- Size of input: This directly affects the speed of the algorithm; the more data there are, the longer the processing.
- Scalability of input: Beyond the speed of scalability: if the input will always be on small scale, time and space complexities can be practically ignored; however, the algorithm could receive a wide range of inputs, then complexity becomes an issue.
- Nature of input: Sometimes, the exact nature of the input (whether a list is already sorted) can dramatically affect the efficiency of the algorithm; it may be necessary to consider whether those cases are likely to occur.
- Frequency: If an algorithm must execute only once a month, its efficiency in time may not too big issue. However, if it must be executed every time a user moves the mouse pointer, every time the computer screen refreshes, or whenever some highly frequent event occurs, efficiency in time becomes one of the most important.
- Maintainability: Even if an algorithm is efficient in time and space, if it's highly complex in terms of its required data structures and required processing, it may be advisable to choose less efficient but less complex alternative. Complex code leads to more bugs, potentially losing stability.

Of course, everything we've discussed so far about choosing or designing algorithms has revolved around the deceptively simple task of sorting a sequence of items. In many ways, this is one of the simplest faced by a software developer; yet, choosing the right algorithm can be almost an art form.
