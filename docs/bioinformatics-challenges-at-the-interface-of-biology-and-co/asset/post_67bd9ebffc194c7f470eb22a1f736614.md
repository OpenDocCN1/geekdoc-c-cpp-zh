### Searching within a binary tree

Imagine a nicely balanced binary tree of records that have been ordered according to some unique identifier, as seen in Figure 6.10. Starting at the root node, we can search for a given identifier by following some simple rules:

- 1 Let the root node be the current node under scrutiny.
- 2 Check whether node's item is the item being sought. If it is, we've found the item in the tree. Then we can stop.
- 3 Otherwise, compare that item with the item sought.
- 4 If it's less than the item being sought, the item must be in the right-hand sub-tree, in which case, let the right-hand child node become the current node under scrutiny. Go to #2 and continue the search.
- 5 Otherwise, if the item is in the left-hand sub-tree, in which case, the left-hand child node become the current node under scrutiny. Go to #2 and continue the search.
- 6 If there are no appropriate child nodes, the search has failed: the sought-after item does not appear in the tree.

With each subsequent node comparison, after which we choose to look at the left or right sub-trees, we're effectively halving the search space; this is the ability to find that fast indexes into large-datasets. For relatively balanced trees, doubling the size of the tree only requires a single extra comparison to perform during the search, and this gives the binary tree logarithmic complexity of O(log n). In practical terms, this means searching with a million items requires, at worst, twenty comparisons. We can do this same task using a linked list of a million items: this would require, at worst, a million comparisons. For large datasets, the difference between complexities O(n) and O(log n) can be very great.

Let's, for example, the 70 million annotated sequences held in the DNA nucleotide archive in January 2016. If these entries were stored as a linked list, then searching through this list to find a particular entry would require us to visit each and node to see if it was the one we wanted. The worst-case scenario (if we are at the end of the list, or it is missing from the list) we would have to perform 70 million comparison operations before we were satisfied. However, were the entries to be stored in a balanced binary tree, each comparison would halve the search space; our worst-case scenario would drop to only 30 comparison operations (because a binary tree with a depth of 30 levels can hold $2^{30}$-1 billion items). This would make accessing over 23 million times faster. A quick improvement!
