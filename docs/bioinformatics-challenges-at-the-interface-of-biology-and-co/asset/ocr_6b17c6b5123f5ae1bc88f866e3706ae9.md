# Box 7.10 HTTP and RESTful Web services

HTTP is based on a controlled vocabulary of nine verbs that define the actions a Web client (or a Web browser) can request to be carried out on a resource defined by a URI. Four of these verbs-HEAD, TRACE, OPTIONS, CONNECT- are essentially for housekeeping, allowing the client and server to optimise their communication and set secure connections. Of the remaining four, the most common one is a GET: / to fetch from the server so that it can be interpreted by the client; this interaction with the server happens when we type the address of a Web page into a browser. Typically, when we fill in a form on a page and submit it, the browser is invoking the POST verb, which sends the text that we are sending over data that we want to store in relation to a resource. The remaining three-PUT, DELETE, PATCH-allow the client to create, remove, or partially update a resource, and are used primarily for web-browsing: generally speaking, more interactions involve GETting something in the background, and potentially POSTing data back to the server (with various bits of housekeeping going on in the background). A typical Web-service session involves GETting a lot of content and occasionally POSTing a little back, the architecture of the Web service is designed to create, modify and delete resources.

Representational State Transfer (commonly abbreviated as REST) is an architectural style (Field, 2000), designed to encapsulate how a well-behaved Web-based application should operate. The architecture is based around the idea of hierarchically organised resources, identified using URIs, which are modified using the verbs provided by HTTP. Central to this architecture is the notion of Hypermedia where clients interact by GETting a particular resource and discovering what other resources are available as a result of that. There are similarities between RESTful services and Linked Data, but the two paradigms are not the same (see Page e et al., 2011).

It's common for Web-based services to return data in a machine-readable format as a result of GETting a URI to be described as RESTful; but unless the service implements all the constraints of the REST architecture, this is technically incorrect: REST is not a synonym for 'ad hoc Web service that uses URIs to retrieve information in JSON/XML/RDF', but specifically to services that adhere to the HATEOAS architecture.

The variations and some of the subtleties of the different Web service paradigms, it's first necessary to understand a little about HTTP itself. As the name suggests, HTTP is a protocol for transferring 'hypertext' between systems; and hypertext is simply a document (typically text, images and other media) structured in such a way as to have hyperlinks to others. When humans interact with the Web, our browser software uses HTTP to request a document identified by a given URL from a particular server; the server finds or creates the document (or more generally, the 'resource'), and returns it to the browser, which interprets it and renders it in a human-readable format. The 'human-readable' component of this process, however, is not fundamental to HTTP; rather, it is a side-effect of the fact that browsers are programmed to render documents that come in a certain format (usually HTML) in a way that's palatable to humans. As far as HTTP is concerned, it is simply retrieved a resource and delivered to the requester.
