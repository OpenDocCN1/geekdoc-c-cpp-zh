# 6.6.2 Choice of language

Not all programming languages are created equal. Languages, and the standard tools they make available, can differ considerably in their expressivity and convenience.

Expressivity of programming language

In a formal mathematical sense, most programming languages have equivalent expressivity: *i.e.*, they're capable of solving the same set of problems, although potentially in different ways. There are, however, programming languages that are *less* expressive than their counterparts: *i.e.*, there are problems that such languages cannot solve, otherwise could be solved had a different language been made.

At first glance, this might look like a disadvantage that would make such languages undesirable. After all, why would we want to use a language that's less able to solve problems? The answer lies in the Halting Problem introduced in Section 6.2.1, which stated that it is impossible to know whether an algorithm will complete in a finite time, or continue forever. In practice, software engineers strive to avoid such situations, so the fact that they are theoretically seldom causes problems. The ability to prove mathematically that an algorithm will complete in a finite time is very important, especially in highly critical systems that require extraordinarily thorough verification (such as online financial systems like *Bitcoin*). In cases like these, standard programming languages are, at least mathematically, one too unpredictable for the task. Although such cases are rare in practice, knowing they exist can inform the creation of more predictable code.

Expressivity of standard tools

By contrast the abstract computability concerns above, there are more concrete expressivity concerns that are likely to cause problems in the field of bioinformatics. The most common come from the use of regular expressions for parsing textual data. Regular expressions (see Box 6.2) allow text patterns to be matched and extracted—they're often used when parsing from some serialised data (either a data file, or network traffic). They, however, have limited applicability, so it's important to understand when regular expressions are not applicable.

Regular expressions are capable of parsing any regular language, a very term in language theory that describes mathematically the structures within the language ('language' covers not just programming languages, but any informational language). The most common example of such a structure is recursion: regular expressions are mathematically incapable of parsing recursive data structures. This is important, because there are many formats in use today that are not regular languages in the formal sense, and hence regular expressions are incapable of parsing them. XML, HTML and JSON, the three most pervasive formats in use today, are worth noting context-free languages that cannot be parsed with regular expressions. This is repeating so because of the frequency with which it is attempted: regular expressions alone cannot parse XML, HTML or JSON. Having said that, most regular libraries provide extensions that, while not sufficiently powerful to invalidate the above statement, provide extra expressivity, and allow wider application

Most programming languages have regular-expression functionality either built in or available as a standard tool; in most cases, the particular combination of regular-expression extensions is specific to this language and version. Whether those extensions provide better support for non-ASCII text, or are non-regular extensions to the language itself, knowing what's available helps us to choose an applicable language
