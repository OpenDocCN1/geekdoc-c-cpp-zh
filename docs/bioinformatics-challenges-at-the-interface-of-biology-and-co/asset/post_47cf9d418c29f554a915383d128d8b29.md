### Lightening loops Loops such as for or while loops, allow us to repeat execute some code over different data; by their very nature, allow us to efficiently process a large amount of processing in a relatively small amount of code. A corollary of this is that it is easy to understand how long a program will spend in a loop, and what might need during execution. We therefore be careful not to do any unnecessary processing within a loop. For example, take the hypothetical code:

```python
#Cycle through the list of vectors
let count=vector_list.length()
for index in 1..:
# Make a rotation matrix
let matrix(0, 1, 0)
# Get the item of interest from the list of vectors
let v=vector_list[index]
# Multiply by the matrix and store back in the list
vector_list[index]=v
end for
```

The thing to notice here is that the matrix constructed within the loop (on line 5) is always the same matrix and it never changes during execution. We are therefore needlessly creating a new matrix every time we go around the loop, only to have it destroyed again before the next iteration. Each iteration, construction and destruction is to take time, not because of the code it will undoubtedly be executing behind the scenes, but because of the memory that needs to be allocated and deallocated each time. This is compounded in the case of nested loops.

Such issues can be effected by a simple re-ordering of code: in this case, making the matrix construction out of the loop so that it ever gets executed once:

```python
1 # Make a rotation matrix
2 let matrix(0, 1, 0)
3
4 # Cycle through the list of vectors
5 let count=vector_list.length()
6 for index in 1..count:
7 # Get the item of interest from the list of vectors
8 let vector=vector_list[index]
9 # Multiply by the matrix and store back in the list
10 vector_list[index]=vector
11 end
```

Another good candidate for this is the declaration of any temporary variables used inside the loop. Even though their values might be different from one iteration to the next (such as v above), let the memory that they aren't being continually deallocated and allocated each time stay around. Better yet, don't use a variable at all if it's not needed:

```python
1 # Make a rotation matrix
2 let matrix(0, 1, 0)
3
4 # Cycle through the list of vectors
5 let count=vector_list.length()
6 for index in 1..count:
7 # Multiply the current vector by the matrix and
8 # store it back in the list
9 vector_list[index]=vector_list[index]
10
```

### When a function is a macro When writing, we're likely to make use of functions by someone in order to provide the intended functionality. This kind of re-use is perfectly normal, for a good deal of the code of any software system, is a Good Thing. Sometimes though, not knowing the details of how such functions are written can present problems to those trying to use them (something we touched on Section 6.3), especially if the function isn't a function at all, but a macro. Macros, short for macroinstructions (not to be confused with macros in popular word-processing software), specifically how certain input can be mapped to replacement output code. The difference between using a function and a macro is a question of when the parameters are evaluated. A function's parameters are evaluated before that function is called, while a macro is inserted into the surrounding code and the parameters are replaced before evaluation. Simple examples can be seen in Figure 6.14 and Figure 6.15, where a function and a macro are defined, both attempting to ascertain the maximum of two values. In each case, we use them to find the maximum of the square roots of two arbitrary numbers (m and n). For the function max(a,b) of Figure 6.14, the parameters are evaluated before the function is called, so the two auxiliary calls to sqrt(a) and sqrt(b) are executed only once.

Operator-circuiting is a method many languages use when computing Boolean (true or false) expressions — it amounts to the premature ending of evaluation when the result is known with certainty. Expressions can represent anything that might be true or false, and appear in one form or another in any program that has make decisions: they might be a given amino acid hydrophobic or hydrophilic, the length of a protein sequence is larger than some threshold. For simplicity, in the following expressions, we replace these concepts with single-letter symbols, of which A-H reduce to either true or false:

A and B and C and D (1)
E or F or G or H (2)

Most programming languages would process expressions from left to right; looking at example (1), we see that first A is evaluated, followed by B, by C, followed finally by D. However, if A resolves to false, the are irrelevant, the overall result is guaranteed to be false. In fact, as soon as we come across a sub-expression that evaluates to false, we become certain of the falsity of the expression. We can therefore skip evaluation of those subsequent expressions. Example (2) is similar: the first sub-expression to resolve allows us to short-circuit the subsequent evaluations, as it can be seen that the overall expression must then evaluate to true. Of course, this behaviour regardless of our intent, so how can it be used intelligently to optimize some code? Again, we appeal to our knowledge of any application of logic; specifically, how heavyweight operations are, and the likelihood of a given sub-expression being true or false. Take example (3) below: we have four conditions that must be true in order for the expression to be true.
