
## 6.5.1 Structural consequences

As name suggests, data structures store information in a structured way, for a specific purpose. Some data structures do nothing more than group values that pertain to the same conceptual entity (say, an individual's name, address and date of birth) into a self-contained record; others represent the relationships between data, whether those data represent simple values or more complex records – such structures are often called containers, a general term for what it is, in fact, a large and varied costly of data.

Table 6.3 shows a number of the most commonly used containers, categorised according to how their contained items relate to one another. Each provides a different way of relating a group of items, promising differing things and behaving differently when used. For example, some data structures are explicitly unordered (such as a set) and provide no guarantees about the order of the items they hold; others exhibit stable ordering (such as a linked list), allowing us to be sure that, removing an item from the container will not change the order of the remaining items. Matching these qualities to the problem is then relatively simple. Comparing behaviour, on the other hand, is a much more involved task; nevertheless, a container's behaviour is essentially tied to the methods used to manipulate it:

- inserting new items;
- finding existing items;
- deleting items;
- Mutation modifying existing items;
- Restructuring – changing the relationship between existing items.

To show how these categories of manipulation allow us to evaluate behaviour, we'll now explore the inner workings of three container types: the vector, the linked list and the binary tree.

A vector is a one-dimensional container that stores its items consecutively in memory, allowing the whole to reside in a single contiguous memory block. In practice, a vector usually allocates more than it needs, in the case number of items needs to change throughout the lifetime of the program. Figure 6.8 shows how a simple vector of integers could appear in memory. In terms of our five measures of behaviour, how a vector might look internally in terms of its memory usage. Most data structures hold some housekeeping information, with the vector usually needing to know how much contiguous memory has been reserved (its capacity), and how much is currently being used (its size).

The vector does quite badly in all but one of the cases. Accessing individual items according to their position – or random access – is extremely fast; each item takes an equal amount of memory (let's call it $p$). Therefore, given the address of the first item (which we call $p_0$), we can calculate the memory address of the $i^{th}$ item, $p_i$, by the simple formula below. Here, the index $i$ is zero-based, as is usual in computer science, that $i=0$ for the first item, $i=1$ for the second item, and so on:

```
$p_i = p_0 + (i \times s)
```

This makes accessing items by their positions exhibit a constant complexity of O(1): it doesn't matter how many items the vector holds, takes the same amount of time to find the $i^{th}$ item, regardless of the value of $i$. Of course, this only helps if we already know the position of each item we wish to find. If we wanted to search for an arbitrary item, given criteria (not knowing its position), we would have to inspect each item until we found one that fulfilled those criteria, giving instead a worse complexity of O(n).

Appending an item to a vector that has enough memory reserved is also a quick operation: knowing the previous size of the vector, we can calculate the position of the next memory location in constant time. Likewise, removing the item at the end of the vector can amount to little as reducing its size by one, and cleaning up the unused space; this can be done in constant time. Inserting or deleting items anywhere along the vector, is a relatively time-consuming operation, as existing items need to be shifted about in memory to make room for the new item, or to reclaim room for the changing complex sequences of items, unless new items are ever appended, and old items are only removed from the end (this exactly describes the behaviour of a stack, first-in, last-out (FIFO) data structure designed for this scenario in mind). Mutating items is straightforward, and requires no reorganisation of the vector.

One optimisation is if we know how many items a vector will need to hold during its lifetime, the right amount of memory can be reserved upfront. This is important because the allocation of memory is relatively expensive operation, reducing the number of memory allocations is a worthwhile task. If a vector needs to grow larger than the space reserved for it, it must then allocate a larger, contiguous block of memory; copy the items from the old block into the new block; de-allocate the old memory block, and return it to the operating system. Although most vector implementations choose sensible sizes for these reallocations, if the maximum size is required beforehand, no such expensive re-allocation and copying is needed.

## Anatomy of the linked list

One solution to the expense of reorganising a vector is the linked list. In contrast with the single contiguous block of memory used to store its items, a linked list stores each item in a separately allocated block of memory called a node, each node storing the item in question and a pointer to the next node in the list. Then, given a pointer to the initial node in the list, we can traverse the links between nodes, investigating each item in turn, the end of the list signified by a node with a null 'next' pointer. Reorganising such a list becomes a task of reorganising individual items, but rather of the links between them. Figure 6.9 shows how such a list might appear in memory. Given that these pointers tend to be relatively small compared with the items a linked list might hold, the benefits are clear in terms of not having to shuffle around potentially large of memory.

One disadvantage of their linked nature is that random access is not directly supported: to find the nth node in a linked list, we must begin at the initial node and traverse the links until the required node is reached. For large lists, this can become an expensive operation, as it has a time complexity of O(n). Having found a particular node, manipulation is straightforward, with insertion, deletion and mutation performing in constant O(1). Most linked list implementations store not only a pointer to the initial node, but also a pointer to the final node; this makes appending items a trivial task (we needn't traverse the entire list to find the final node); coupled with the ease of removing the first item, this provides precisely the qualities needed for a data structure such as a queue: first-in, first-out (FIFO). Another disadvantage of linked lists: each insertion and deletion causes, respectively, a memory allocation and a de-allocation. If the contents of the linked list are expected to change often, with insertions and deletions occurring frequently, this overhead might become a problem.

The sort of fact bi-directional traversal provided by doubly linked lists can be very useful when implementing algorithms.

## Anatomy of the binary tree

Aside from being structured differently in memory, the binary tree data structure differs from previous examples in that it mandates an explicit ordering of its items. The ordering is explicit in two ways:

- 1. Items in a binary tree must be comparable, such that, given two items, A and B, we can deduce the truth of the expression A < B. With both the vector and linked list examples, this doesn't have to be true; the ordering of those items can be arbitrary;
- 2. When manipulating the items and the data structure as a whole, it's up to us to maintain a correct ordering: we can't simply place an item anywhere we wish.

This may seem like a lot of work, but the result is highly efficient and often-used data structure. Figure 6.10 shows how a binary tree is built from a hierarchy of nodes, unlike the linked list, structures its items in a series of parent-child relationships. In a binary tree, any given node, N, will have two pointers: a left pointer will point to its left-hand child node, L, and a right pointer will point to its right-hand child node, R. Most implementations also maintain a third pointer that points to its parent node, P. In terms of the items embedded in these nodes, the comparison relation introduced above (<), we find the following relationship true for every node in the tree:

> L < N < R < P
