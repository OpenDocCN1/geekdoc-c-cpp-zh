On the face of it, this might seem like a neat way of generating a unique identifier for the amino acid sequences we've been asked to manage in this scenario. But there are a number of pitfalls.

The first is that a number of flaws in the MD5 algorithm means that there is nowhere as 'collision resistance' as first thought, and that it's actually quite straightforward to artificially construct two input sequences that 'collide' to give the same output. For security applications, this is disastrous, but means that MD5 is a risk that's not worth asking. Other, more recent hashing algorithms (such as SHA-256) are much more resistant to collisions, and therefore more suitable replacements for MD5.

Whereas the first pitfall is one of balancing probabilities – the risk of an accidental collision or the consequences of malicious manipulation – the second concern is much more fundamental, and hinges on the idea that hashing to generate an identity breaks the principle of opacity discussed in Section 7.3. Although 2277d9c488b-82cf17dc1908fb338a appears opaque to humans, and in that there is no way of figuring out what sequence it refers to just by inspecting the hexadecimal signature, using this mechanism creates a strong semantic link between the sequence and the identifier (as the latter was generated from the former). This is always a bad thing to do. If for example, consider a situation where an error is found in the amino acid sequence, such that it is computationally possible to see that an update to the original sequence has happened (rather than by just fixing the sequence in it), even with a semantically untied situation, as the hashed signature is now inconsistent with the sequence of bytes that generated it in the first place. Does this really matter if we treat it as being semantically opaque, but in that case, worthy with the hashing at all? As it might sound, an integer incremented for each record, and quite suited with a namespace would have done the job far better and with fewer chances of confusion.
