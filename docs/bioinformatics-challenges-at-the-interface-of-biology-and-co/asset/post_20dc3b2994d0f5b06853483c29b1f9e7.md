
## Bioinformatics challenges at the interface of biology and computer science

The first thing we can anticipate is that the requirements placed on a format – any format – will inevitably evolve. Unless we do a perfect job describing data that will never change (and we can be fairly certain we haven't done yet), we will, at some point, have to modify the format to include new information, or remove/correct what is obsolete or wrong with it. This means, at the very least, allow users to keep track of the version of the format they are using, and means including that information inside the data file. It is not good enough to make that information how implicit from the source of the data file, as the file will probably be transferred around, and its internal provenance lost; it's also no real help to include the version in the filename, as that can, and will, be changed many times (not to mention that files transferred across a network often don't have filenames, as it's the content that's transferred, not their metadata). The best possible place would be in the data itself, perfectly up-front, and in a simple way that can be guaranteed to remain unchanged in perpetuity. That way, clients designed to consume such data can check the version before they read the rest of the file.

So, the inevitable fact that formats will change, must make sensible choices to try to make such changes as painless as possible. Below, we list the most important considerations:

- **Version everything.** Data and formats change over time. These changes must be captured so that we can correctly understand their meaning, and how meaning has changed over time. Master a version-control system such as git will feel like hard work at first, but will save you significant pain later on; and, most importantly, make sure that any formats or schemas you create, the elements they contain, are versioned (ideally using an ontology, as one of those described in Box 7.8).
- **Don't define arbitrary limits.** Often, formats limit their content arbitrarily, by declaring a maximum length for text strings, or enforcing order or lower case for certain fields (recall the problems caused by the change in Swiss-Prot's format in Section 5.6). If there are no reason for such limits, they shouldn't be in the first place.
- **Support character sets from day one.** At some point, someone will need to encode data from a language other than yours: whether it be the name of an author written in Japanese Kanji, or descriptive blocks written in a Cyrillic language, the need to use non-ASCII characters is more or less guaranteed – adding such support as an after-thought will bring nothing but. In practice, this means learning how Unicode and its various character encodings work, this seeming daunting at first, but it is worth it, and most modern programming languages provide excellent support for Unicode, either natively or through libraries.
- **Qualify as much.** Each individual datum – or subset of data – is qualified with a name in the format, then adding new data is straightforward: we need only a name for the new data and it alongside our old data. The two-character field names of the EMBL format and its derivatives are (admittedly limited) example of this kind of extensibility.
- **Use standards wherever you can.** Someone has probably spent a lot of time thinking about how to represent at least something related to what you are creating; make sure you know formats, schemas already exist, and make your work compatible with whatever possible.

## Box 7.4 Machine- and human-readable formats

The terms machine readable and human readable, when applied to electronic formats, are open to some interpretation. At some level, most digital documents can be processed and thus 'read' by a machine; similarly, most documents aren't binary-encoded or compressed or encrypted they can be to some degree, 'read' by a human.

The real question is to extent the format makes it easier than just possible for it to be read and understood by a machine or a person. The important point to keep in mind is that humans and computers speak very different languages, and have different requirements when it comes to reading them. For example, it is rare, if not impossible, to make something that works well for both kinds of consumer.

In a literal sense, XML, RDF and JSON are machine-readable formats, in that they are encoded as characters that a machine can inspect in a text editor, and with experience, interpret and understand; these formats (especially RDF) are certainly not easy to read, and they're designed for consumption by machine. Conversely, the text-based formats for bioinformatics data are reasonably easy for a human to read on an 80-character terminal, but as we've seen through the book, are quite quite difficult to parse by machine. Regardless, the days when it made sense to design a file format that could be read by a human are long gone, and it is better to assume that the primary consumer data for that format will be for a machine, not a person; generating a human-readable version of a machine-readable format is quite harder.

- *Make everything easily readable.* It's hard to emphas this point enough: assume that your data will eventually be consumed in huge quantities by a computer, with no human intervention, and make it not just possible for a machine to read it (see Box 7.4 and the following section). Also, as tempting it may be to allow information to be encoded in a free-text 'comments' field, when information turns out to be really interesting, you'll regret having to resort to text-mining techniques in order to extract the knowledge you've abandoned to free-text format.

When you create data-exchange formats or schemes to be shared with others, you must expect that, at some point, other people will write code that utilises them; even if a new feature you're about to introduce is really exciting, no one will tell you if your change causes systems to fail. In computing, a change to one part of a system that causes another to fail is known as a breaking change. Sometimes these are inevitable, but, with foresight, the principles outlined in this section, and using the extensible frameworks described next, will reduce the chances of this happening.

### 7.4.2 Contemporary data-representation paradigms

Reading and writing even the most trivial file format can be quite a complex task, and to understand the issues that have arisen historically, and the modern solutions to those problems, it's useful to think of the process as consisting of three distinct stages: we'll call this lexical, grammatical and semantic. The first of these – lexical analysis – involves converting the individual bytes or characters into what are called tokens. Imagine a file format where each line contains a list of words or integer numbers separated by commas and terminated by a full stop. The lexical analysis of a line such as:

```
384, Rhodopsin, Rho.
```

yield a sequence of tokens of the form shown in Figure 7.4.

### Figure 7.4
Lexical analysis of 384, Rhodopsin, Rho.

| Number | Comma | Word | Comma | Word | Fullstop |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 384 | | Rhodopsin | | Rho | . |

The second stage is grammatical analysis, where we apply some rules governing the ordering of the tokens. In our trivial case, we want to encapsulate the notion that a list contains any number of 'items' separated by commas and ending with a full stop, where each 'item' is either a number or a word. For example:

384 Rhodopsin, Rho.

is lexical valid (it consists of numbers, words and commas that are all acceptable tokens), but would break our grammar rule because there's no comma between the first and second 'item'. In combination, lexical and grammatical analysis define the syntax of our format.

The final stage is semantic interpretation, where we infer from a-syntactically valid stream of tokens. In our hypothetical example, we might decide that the line describes a protein, the first numbers define the length of its amino acid sequence, the next word gives its common name, and the final word its associated gene.

Even with this apparently trivial file format, there is a plethora of potential pitfalls when it comes to defining the lexical and grammatical rules, especially if we keep an eye out for future evolution of the format. If we want to be really about parsing this file, we might include a rule in our code that says each line should consist of exactly five tokens in the order described above; but then, at a later date, if we wanted to extend the format to have an additional (and perhaps optional) 'free-text' at the end of the line, we'd hit two problems:

1. we have to go back and modify the grammatical element of our parser to allow an extra comma and subsequent 'free text';
2. we would have a conflict if allowed commas within our free text, as we have chosen to use this as a token in its own right.

You'll probably spotted that we're ignoring quite a number of details here: how do we know that '384' forms an integer, or 'Rhodopsin' a valid word in the first place? What whitespaces between the different components?
