## Compiler optimisation

Broadly, there are two strategies for executing the kind of high-level instructions seen throughout this chapter: compilation and interpretation. Interpreted languages—often known as scripting languages—are parsed and executed by a Virtual Machine (VM), a layer of software that runs between the executing program and the physical processor, translating the high- and low-level instructions on-the-fly. Compiled languages need no such, as they are compiled into machine code (similar to that seen in Figure 6.3), meaning that they can be executed directly on the processor. There advantages and disadvantages to both strategies: interpreted software, encumbered by its VM, executes more slowly than compiled software, which needs no layer; compiled software will only work on a machine that matches the processor architecture and operating system of the compiler, whereas interpreted software can run on any machine that has an appropriate VM. Choosing the right strategy for a given task is just a case of balancing speed, portability and cost of development.

The operations we saw in Figure 6.3 (mov, noi, etc.) represent individual instructions that can be given to a processor, which make up the machine code into which high-level languages are compiled. The set of instructions provided by a processor is called, surprisingly, its instruction set, and there are various competing instruction sets in use. Different compilers are written for different instruction sets, but in each case, make use the optimisations outlined above. In addition to the core instructions of the main instruction set, most processors also provide extensions that make of highly specific circuits for performing often-used calculations.

An example extension would be one that provides SIMD functionality: Single Instruction Multiple Data. The instructions found in most standard instruction sets are Single Instruction Single Data (SISD), meaning that each individual machine-code instruction performs one operation on one item of data (this encompasses integer multiplication, as even though two numbers are involved, only one calculation is being performed). Conversely, SIMD instructions apply one operation to a number of items of data simultaneously, thereby potentially increasing calculation speed by as many times as there are simultaneous calculations. An example of a SIMD operation is vector addition: the simultaneous pair-wise addition of two identically sized arrays of values. Without SIMD instructions, the kind of addition seen below must be performed as four separate calculations, each row being calculated separately and in sequence:

```
$$\begin{matrix} 1 & 7 & 8 \\ 2 & 3 & 5 \\ 4 & 5 & 9 \\ 8 & 1 & 9 \end{matrix}$$
```

SIMD extensions, can be performed as one operation on the four rows simultaneously, providing a roughly four-fold increase in speed relative to the SIMD formulation. Some compilers can automatically take advantage of SIMD extensions, but can only do so if code happens to fulfil certain requirements. In many circumstances, to make use of such vector arithmetic (or any of the other SIMD operations that may be available), we must explicitly write assembly to define that part of the algorithm. This is not a trivial task, but can improve the efficiency of any code that is amenable to optimisations.

It can be seen, then, that many strategies can be employed to implement better algorithms, from taking advantage of language quirks (or avoiding their pitfalls), by writing code that's more amenable to modern compiler optimisations, or making use of processor-set extensions.

### 6.6.4 Parallelisation

Many algorithms are sequential by nature: they're made of a sequence of steps that must be carried out, in the correct order, to solve a particular problem. Some algorithms exhibit parallel qualities: i.e., some steps are independent of each other, and can be done in any order, or crucially, at the same time. In our world of multi-core and multi-processor machines, server clusters and distributed systems, the ability to execute parts of an algorithm simultaneously (in parallel) allows us to dramatically reduce the time to solve some problems. So what kinds of algorithm can be parallelised?

## Divide and conquer

The bubble sort algorithm discussed in Section 6.4.1 is a good example of a sequential algorithm: each iteration through the loop assumes that previous iterations have already completed, as it relies on the previous iteration's result to work properly. If the steps were done in any other order, the algorithm would fail to function properly; it can't be parallelised.

However, there's an algorithm called Quicksort that takes a divide-and-conquer approach to sorting. Each iteration of Quicksort splits the list into two, ensuring that all elements of the left partition (L) are less than all elements of the right partition (R), although the partitions themselves are not internally ordered.

```python
def quicksort(Input):
    if len(Input) <= 1:
        return Input
    f, b = 0, (len(Input)/2), -1
    pivot = sorted([Input[f], input[b], input[m]])[1]
    left = [r for r in input if r < pivot]
    right = [r for r in input if r > pivot]
    pivots = [p for p in input if p == pivot]
    return quicksort(left) + pivots + quicksort(right)
```

## Figure 1.6

A simple implementation of Quicksort. The input is partitioned into two sub-lists, using a pivot. There are several ways to choose a pivot, such as arbitrarily choosing the first (f) of the input list, the last, or a random element, or the median of the first, middle (m) and last (b) elements (the approach used in this example). Depending on the level of disorder in the input, different choices can give good or bad results, but we are anyway trying to get a relatively equal number of elements before and the pivot.

Mathematically, we'd say that (∀r ∈ L)(∀r ∈ R)<r; this can be seen in the code in Figure 1.6. Once we have our partitions, each partition can be sorted individually (using Quicksort), and independently, and the results concatenated to the final ordered list.

At each iteration of Quicksort, we need to halve the number of lists we sort, while doubling the number of lists to sort, a trade-off that makes Quicksort very efficient. The O(n) cost of partitioning the input lists and the log n depth of the recursive call tree makes Quicksort a time complexity of O(n log n). However, because we end up with independently sorted lists after each partitioning step, these tasks can be carried out in any order, or in parallel. This means that we can take advantage of multi-threaded systems to speed up the algorithm by roughly a factor of the number of simultaneously runnable executions of code.

Any algorithm that makes a divide-and-conquer approach can be similarly parallelised; knowing this can help us choose when to take advantage of multi-core approaches and when not to. Also, with the ever-increasing number of cores available in modern machines, this is a very good way of making full of current technology.
