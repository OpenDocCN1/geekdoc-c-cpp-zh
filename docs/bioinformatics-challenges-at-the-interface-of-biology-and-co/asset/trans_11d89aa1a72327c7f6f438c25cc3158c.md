

## 生物学与计算机科学交叉领域的生物信息学挑战

我们首先可以预见到的一点是，对格式——任何格式的要求将不可避免地演变。除非我们能够完美地描述永远不会改变的数据（而我们相当确定自己目前还没有做到这一点），否则在某个时刻，我们都不得不修改格式以包含新信息，或者删除/纠正其中已经过时或错误的内容。这意味着，至少要允许用户跟踪他们正在使用的格式版本，并且意味着要将这些信息包含在数据文件中。仅仅让这些信息相对于数据文件源是如此隐式是不够的，因为文件可能会在传输过程中转移，导致其内部出处丢失；将版本号包含在文件名中也没有真正的帮助，因为文件名可以并且将会被多次更改（更不用说跨网络传输的文件通常没有文件名，因为传输的是内容而非其元数据）。最好的位置是在数据本身中，完美地列在最前面，并以一种可以保证永久不变的简单方式。这样，设计用于消费此类数据的客户端就可以在读取文件其余部分之前检查版本。

因此，格式将会改变这一不可避免的事实，要求我们做出明智的选择，尽量让这种变化尽可能不痛苦。下面我们列出最重要的考虑因素：

- **万物版本化。** 数据和格式随时间变化。这些变化必须被捕获，以便我们能够正确理解它们的含义，以及含义随时间发生的变化。掌握如 git 这样的版本控制系统起初感觉很辛苦，但以后将为你节省大量的痛苦；最重要的是，确保你创建的任何格式或模式（schemas）及其包含的元素都是版本化的（理想情况下使用本体论，如 Box 7.8 中描述的那些）。
- **不要定义任意限制。** 格式往往会任意限制其内容，例如通过为文本字符串声明最大长度，或对某些字段强制执行顺序或小写化（回想第 5.6 节中 Swiss-Prot 格式更改引起的问题）。如果没有理由设置此类限制，那么它们从初就不应该存在。
- **从第一天起支持字符集。** 在某个时刻，某人需要编码来自非你母语言的数据：无论是用日语汉字写的作者名，还是用西里尔字母编写的描述性块，使用非 ASCII 字符的需求或多是肯定的——事后才添加此类支持只会徒劳无功。在实践中，这意味着要学习 Unicode 及其各种字符编码是如何工作的，这起初看起来令人敬畏，但它是值得的，而且大多数现代编程语言通过原生支持或库都为 Unicode 提供了很好的支持。
- **尽可能限定。** 每一个单独的数据项——或数据子集——在格式中通过一个名称进行限定，这样添加新数据就很简单了：我们只需要为新数据一个名称，并让它与旧数据放在一起。EMBL 格式及其衍生格式的双字符字段名就是这种扩展性的（尽管有限的）例子。
- **在可能的地方使用标准。** 有可能已经有人花了大量时间思考如何表示与你所创作的相关某些内容；确保你了解已存在的格式、模式，并让你的工作尽可能与任何格式兼容。

## 框 7.4 机器可读和人类可读格式

“机器可读”和“人类可读”这两个术语在应用于电子格式时，有几种解释空间。在某种程度上，大多数数字文档都可以被机器处理并因此被“读取”；同样，大多数文档并不是二进制编码、压缩或加密的，它们可以在某种程度上被人类“读取”。

真正的问题是，格式在多大程度上让机器或人读取和理解变得比“可能”更简单。需要记住的关键点是，人类和计算机使用的语言非常不同，而且在读取它们方面有不同的要求。例如，这种情况很罕见，如果是不让机器或人读取和理解的话。
