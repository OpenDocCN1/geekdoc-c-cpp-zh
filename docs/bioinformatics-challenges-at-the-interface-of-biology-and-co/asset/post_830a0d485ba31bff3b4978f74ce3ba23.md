## Convenience of programming language

For a variety of reasons, writing code in some languages is simply easier than in others; inevitably, however, this advantage is accompanied by disadvantages that make the choice of language less straightforward. Some examples of the competing qualities of different languages are outlined below:

- * Python context blocks are denoted by indentation, and not by the usual braces { } found in most other languages. This reduces the size of code and can make development quicker, but introduces confusion if a combination of spaces and tabs is used for indentation.
- Perl has extended expressions built directly into the language, making text processing particularly effective. However, the mechanism relies heavily on global variables and side-effects, making maintenance difficult without a relatively high degree of expertise.
- Ruby has a pragmatic approach to declaring data structures that allows to extended easily at the expense of a loss of control from the original developer.
- By contrast with the languages mentioned so far, C and C++ are very low-level, fine-tuned access to memory, allowing developers to produce exceptionally efficient code, however many aspects of memory management are in the developers' hands, the scope for mistakes and bugs is drastically increased.
- Java hides many of the complexities that make C and C++ difficult to learn, making programming simpler and more robust in the process. Memory management is entirely dealt with Java, reducing the chance of mistakes, but at the same time limiting us in cases where a greater degree of control is required.

Alongside these specific comparisons, it's also worth cautioning about the ability to write compact and quick code in various languages. For example, in C, the following two excerpts of code are equivalent:

```
int x;
if (x <= 3) {
    a = 3;
} else if (x <= 0) {
    a = 0;
} else {
    a = x;
}
int a = x >=3 ? 3 : x <=0 ? 0 : x;
```

Clearly, the second is much shorter, but it loses the clarity of the more verbose first excerpt. It is up to us to weigh the competing advantages and disadvantages of different languages when choosing to which best serves any given problem.

## 6.6.3 Mechanical optimisation

It's sometimes tempting to assume that by the time the quantities of data we need to manage an issue, computers will be so much larger (in terms of memory) and faster than they are today that they'll be able to cope. For many reasons, this is a false assumption, and it's worth mentioning why.

In an article published in 1965, the co-founder of Intel, Gordon E. Moore, famously formulated what has become known as Moore's Law:

The complexity for minimum component costs has increased at a rate of roughly a factor of two per year... Certainly over the short term this rate can be expected to continue, if not increase. Over time the rate of increase is a bit more uncertain, although there is no reason to believe it will remain nearly constant for at least 10 years.

Moore's prediction, subsequently revised to suggest that the number of components on an integrated circuit chip doubled every 18 months, has remained remarkably accurate, and also applicable to other measures of technology (speed, memory size, etc.). So, does this affect our previous discussion of algorithm complexity? Well, in a purely mathematical way, it doesn't affect it at. Complexity, as defined above, is a measure of how algorithm behaves in relation to increased input. That behaviour is independent of the speed of the computer on which it is executed: an algorithm with time complexity of $O(n^2)$ will always have time complexity, regardless of how much faster computers may get. Yes, a faster computer will probably make sooner, but algorithms will still degrade in the same way (logarithmic, polynomial, exponential, etc.) in the face of increased input.

In absolute terms, Moore's Law suggests that, as our input sizes remain constant, our ability to process them will increase exponentially. Unfortunately, as discussed in Chapter 3, the amounts of data we expect to process are also increasing exponentially, thus wiping out any benefit we may have gained from technological advances. But at least we've not taken a step back, have we? Unfortunately, maths is never so forgiving: any algorithm with worse time complexity O(n) (or space complexity) will properly degrade over time in the face of current technical advances.
