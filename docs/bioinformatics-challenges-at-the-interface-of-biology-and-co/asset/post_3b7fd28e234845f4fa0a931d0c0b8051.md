## 7.6 Web services

So far in this chapter, we've explored techniques for representing and giving meaning to data, focusing on how to make these ideas accessible to a computer. In this section, we'll examine how these ideas can be applied to one of the most common tasks in modern bioinformatics: creating or consuming what have become informally as 'Web services'.

The basic idea of a Web service is straightforward enough: a program running on one machine needs to access a service provided by another program somewhere else on the Internet. There are many circumstances where accessing a service remotely like this is preferable to creating the necessary infrastructure to do the job locally:

- The data-sets involved may be too large to be hosted locally;
- The data could be changing too for maintenance of a local copy to be practicable;
- The computational load could require specialist hardware;
- The software stack required to run the service locally could be prohibitively complex to implement.

At some level, accessing a Web service is conceptually the same as invoking a function or procedure: data passed by way of input parameters; some kind of calculation is performed; and, some time later, results are returned to the caller. Within a single program executing on a processor, this is almost trivially straightforward concept – but expand the notion to programs interacting in today's highly distributed, highly heterogeneous computing, and the story becomes much more complex. To understand what it means to interact with the Web, it is first necessary to understand, in bit detail, what it means to interact with the Web; and we need to know a little more about distributed systems, and the architecture of the Web specifically.

It's surprisingly hard to pin down a precise definition of a distributed system; besides, being too pedantic about what is and what isn't 'distributed' to obscure, rather than illuminate, the points we're discussing. So rather than worrying about trying to create a rule that definitively distinguishes a distributed system from a non-distributed one, we'll offer some principles that will allow us to arrange systems on a kind of spectrum of 'distributedness'. The overall idea is that a distributed system consists of multiple independent, largely self-sufficient computational components that, spatially separated, exchange information in order to coordinate and co-operate in achieving a common goal. With the difficulty defining a distributed system along just lines, however, there are many different configurations and architectures that have some of these properties to some extent or other.

At one extreme, are multi-core processors: individual CPUs that are capable of executing multiple instructions simultaneously, which programs executing in parallel via shared access to the system's RAM. Although it could be argued that a multi-core CPU has several 'computational components', the fact that these are highly dependent on shared hardware, and that they exist on a single minuscule wafer of silicon would rule this out as being in any sense a distributed system. Stepping up in physical scale, it's increasingly common for a motherboard to support multiple CPUs (which may, in turn, be multicore devices), sharing the same RAM and other resources. Also, here, the 'spatial separation' has increased from nanometers to centimeters, it still feels hard to justify as being particularly distributed. Scaling up even further, we encounter 'cluster' and 'grid' computing, where multiple computers, with their own power supply, memory, and so on, are connected by a dedicated network infrastructure in order to co-operate in solving a specific task. At this point, we rely in a grey area: after all, there's certainly a sense of geographic distribution here – the computers could be in different rooms or even buildings – but there's still a sense of 'centralisation' (e.g., it is common for clusters to be 'centrally administered'). Finally, at the other extreme, we have systems like the Web – which spans the entire globe, and has no central authority or administration – where the distributed nature is more obvious.

## Bioinformatics challenges at the interface of biology and computer science

As it's quite hard to pin down the exact nature of a distributed system by saying what it is, it's sometimes defined in what it isn't, what are commonly known as the 'Fallacies of Distributed Computing', namely that:

1. The network is reliable.
2. Latency is zero.
3. Bandwidth is infinite.
4. The network is secure.
5. Topology doesn't change.
6. There is one administrator.
7. Transport cost is zero.
8. The network is homogeneous.

According to Peter Deutsch, one of the creators of the list,
Essentially everyone, when they built a distributed application, makes [these]... eight assumptions. All prove to be false in the long run and all cause big trouble and painful experiences.

An eminent scientist noted that 'a distributed system is one in which the failure of a computer you don't even know can render your own computer unusable (Lamport, 1987)¹⁰ – for systems that make these assumptions, it's all too often. It's important to note that some of these fallacies can equally apply to non-distributed systems (e.g., at the level of chip design, it would be silly to assume that 'latency is zero' or 'bandwidth is infinite'); but if we have an architecture where none of these things are true, we can be certain we have a distributed system.

Another way to think about the 'distributedness' of an architecture is to consider it from the point of view of what happens to the overall system when a part fails, and the frequency with which that's likely to happen. In the case of a multicore processor, or a multi-CPU motherboard, these systems are expected to function perfectly during a well-defined life span (typically with number of years), and eventually to fail catastrophically; all the hardware components depend on extent on the others, so when one breaks, the whole system. In the case of a computing cluster, there's more scope for 'graceful degradation' of service, and in a well-designed setup, the failure of one machine needn't necessarily bring the entire cluster down. Then there is the Web: when was the last time the Web – the whole Web, not just your favourite corner of it – broke for everyone?

### 7.6.1 The architecture of the Web

The Web is an implementation of the Client/Server architecture design pattern. The idea is that a particular task is conceptually partitioned into two parts: a server implements a particular function, which it performs at the request of one or more clients. The defining characteristic of the client/server model is that each component has a particular role, as either client or server, and client components can communicate with the server, not directly with each other. This is in contrast to the Peer to Peer (P2P) model, where every node is considered equal, and can communicate with any other node.
