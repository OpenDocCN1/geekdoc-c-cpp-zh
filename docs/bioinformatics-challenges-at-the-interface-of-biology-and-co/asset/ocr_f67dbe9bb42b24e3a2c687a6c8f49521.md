In JSON, we can dispense with much of the syntactic fluff, as the '>', ';', and '*' characters are just there in order for parsers to be distinguish between the different parts of the file. All that we really care about is:

+   1 This is a protein
2 Its identifier is HBA_HUMAN
3 It's got a human-readable description
4 It's got an amino acid sequence

In JSON syntax, we could encode this as:

```
{
  "type": "protein",
  "identifier": "HBA_HUMAN",
  "description": "Hemoglobin subunit alpha gene=Homo sapiens HBA1 PE=1 SV=2",
  "sequence": "MLVSPDKTNVVKWKGGAHAGEYGAEALERFMSFTTKTYFPHDLSAQVKGHGRKVYDAATNAVVDMPNPALSALHHKRLVDPNFKLLSHCLLTAALAEPTPAVHASSDLDKFLAVSVSTLTKYR"
}
```

Although, in some ways it might more verbose – the benefit of encoding the data in this way is that there's no need to write a bespoke parser. Instead, you simply load the data into a standard JSON parser, and then interrogate to retrieve the 'type', 'identifier', 'description' and 'sequence', and use them in whatever way is meaningful for your application. What we've created here is a single JSON dictionary (defined by the order [ ]) which are part of the JSON syntax), containing four key/value pairs separated by ': (type is a key,protein is a value), pair for each of the four properties we want to record. The keys we chosen here are completely arbitrary, and would only mean to our particular application – the JSON parser doesn't care what they are, as they are represented using the right syntax.

If we wanted, at a later date, to extend the number of properties we recorded for this protein, it would simply be as of adding a new key/value pair using the JSON syntax. Tools built prior to this extension would continue to work seamlessly; the JSON parser would read happily in the new key/value pairs, but it wasn't programmed to do so. # XML

Extensible Markup Language, XML shares some common goals with JSON, that it allows objects and their properties to be encoded in a well-defined language that can be created and consumed by standard parsers. XML badges itself as a 'language', rather than as a 'notation', and is considerably richer and more complex than JSON. Based on an earlier and much more complex markup language, SGML (Goldfarb, 1990), XML presents a set of highly regular rules for how to encode hierarchically structured data.
