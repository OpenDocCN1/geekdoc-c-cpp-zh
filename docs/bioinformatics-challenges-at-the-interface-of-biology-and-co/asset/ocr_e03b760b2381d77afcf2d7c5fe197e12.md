    return quicksort(left) + pivots + quicksort(right)

A simple implementation of Quicksort. The input is partitioned into two sub-lists, using a pivot. There are several ways to choose a pivot, such as arbitrarily choosing the first (f) of the input list, the last, or a random element, or the median of the first, middle (m) and last (b) elements (the approach used in this example). Depending on the level of disorder in the input, different choices can give good or bad results, but we are anyway trying to get a relatively equal number of elements before and the pivot.

Mathematically, we'd say that (∀ ∈ L)(∀ ∈ R)<r; this can be seen in the code in Figure 1.6. Once we have our partitions, each partition can be sorted individually (using Quicksort), and independently, and the results concatenated to the final ordered list.

At each iteration of Quicksort, we need to halve the number of lists we sort, while doubling the number of lists to sort, a trade-off that makes Quicksort very efficient. The O(n) cost of partitioning the input lists and the log n depth of the recursive call tree makes makes Quicksort a time complexity of O(n log n). However, because we end up with independently sorted lists after each partitioning step, these tasks can be carried out in any order, or in parallel. This means that we can take advantage of multi-threaded systems to speed up the algorithm by roughly a factor of the number of simultaneously runnable executions of code.

Any algorithm that makes a divide-and-conquer approach can be similarly parallelised; knowing this can help us choose when to take advantage of multi-core approaches and when not to. Also, with the ever-increasing number of cores available in modern machines, this is a very good way of making full of current technology.

# Big data and homogenous processing

When our task is to process large amounts of data in a uniform manner, it's often to split the data and process processes simultaneously. Take, for example, the task of matching a short protein sequence fragment against a database using UniProtBK. Each protein sequence from the database needs to be individually checked to see whether it contains the target fragment, but these checks are entirely independent. Whether a sequence matches no relation to which any of the other sequences would match. There would therefore be possible to check all 55 million sequences in UniProtBK simultaneously.
