# Box 6.4 MapReduce

Anne Elk's Theory on Brontosaurus* states that all Brontosaures are thick at one end, much thicker in the middle, and then at the far end. Curiously, Elk's theory also turns out to be true of many parallel tasks as you start up with simple piece of data to analyse that's usually in place; you split the job of analysing the data into little bits that can be executed independently, and spread these out over a large number of processors; and finally, you get all the results in a single block that you can inspect.

MapReduce is a paradigm for co-ordinating the processing of a parallelizable problem. It consists of two stages. First, in the Map phase, a master node takes the input, splits it into smaller-problems, and sends them to worker nodes. Depending on the architecture of the system, a worker node might receive the output of another, passing these on to other nodes to create a tree-like network of workers. The worker nodes process their part of the job, and when complete, return results to the master node. Then, during the Reduce phase, the master node collects the answers to all the sub-problems and combines them in some way to form the output.

# Non-trivial parallisation

Unfortunately, there are many bioinformatics problems that cannot be divided and conquered in a straightforward framework. In these cases, we cannot resort to off-the libraries, such as MapReduce, to provide this benefit; we need to do the highly complex task of writing parallel programs ourselves. Unlike with MapReduce, where each sub-problem works on its own copy of the data processed, it is often that multiple simultaneous threads access the same data in memory, ensuring that simultaneous manipulations do not conflict becomes a task we must carry out. This usually means using locks (known as mutexes) to prevent such conflicting access, causing some threads to temporarily pause while updating the memory, and waking up those threads once the update is complete. This general dance of synchronisation, if not done correctly, can very easily cause parallel programs to lock forever, as two threads wait for the other to unlock the same resource – a situation known as deadlock. Avoiding-deadlock, keeping even the simplest of parallel programs running smoothly, takes a great deal of knowledge and experience. If we were to expand the problem to a distributed environment, even the most experienced software engineers would have difficulty keeping up.
