## 6.5.2 Marrying form and function

As we see, accessing or manipulating a relatively simple task; however, when it comes to something a little more complicated, as a binary tree, just interacting with the data structure requires quite specific and complicated algorithms. Conversely, we could use a general algorithm (as bubble sort, introduced in Section 6.4.1) for many different structures, but in doing so, we would not probably perform equally. If we've learned it so far, the distinction between the algorithm and the data structure on which it operates is not as clear as we might have thought.

Until now, the most complicated data structure we've discussed is the binary tree. It's not only complicated in its structure, but also in the methods required to access and manipulate it. However, as we've just seen, if used correctly, the binary tree provides benefits that justify the effort invested, simpler data structures are unable to provide. The two different sides of the same coin: the data structure is the algorithm's footprint in memory.

# Too clever for our own good

With the help of complex data structures, and making sensible assumptions about the input, it is possible to design complex algorithms that can perform well in time and space. However, it could be argued that such solutions might not always be the best.

How an algorithm performs in a computer system is clearly important; however, unless it is perfectly implemented, it will never be changed, somebody, at time, we will probably go back and modify how it works. A rule of thumb here is that the more complex the algorithm, the more fragile its implementation: fragile to unseen bugs and fragile to future changes. Sometimes, even with rigorous commenting the only way to follow a complex algorithm is to watch the flow of control, and keep track of multiple values in memory. Sometimes, the only course of action is to throw away the algorithm and start again from scratch. In such cases, it might be sensible (depending on how important its requirements are) to choose a less complex, less efficient algorithm, if it's more amenable to maintenance.

## 6.6 Implementing algorithms

In committing an algorithm to digital form, a new vista of interesting problems becomes apparent that can have a drastic impact on how well that algorithm performs. Some of these problems are relatively high-level, and can be offset by the type of problem, and solution, we have seen before. Choosing an appropriate programming language—if we are at liberty to do so—can lead to significant benefits in terms of efficiency and ease of development; however, in most cases, our choice is limited or even prescribed by factors beyond the algorithm.

So can we make such decisions? Programming techniques can be categorised at every level of abstraction, on many ways, and can be either descriptive or prescriptive; such can be helpful when choosing the right tools for a job. These range from the high-level choice of programming paradigm, to what we'll call here low-level quirks of the language.

## 6.6.1 Programming paradigm

At their highest level of abstraction, programming languages can be categorised according to how multiple instructions are put together to form complex programs. Imperative programming languages execute commands sequentially, in a linear manner. Imperative languages are also procedural in nature, as they make use of procedures (named blocks of sequential instructions) that may be executed multiple times by called from the main control flow. This parcelling of reusable code can make writing software efficient.

Object-oriented languages allow related groups of data to be bundled with the logic needed to process them. Objects tend to manage their own state, interaction being mediated by procedures methods, which ensure an object's internal consistency. Most imperative languages provide object-oriented facilities, although a purely object-oriented languages exist. This allows us to formalise and restrict the interaction between objects, preventing undesirable behaviour and allowing for better verification of a program's correctness. Object-oriented languages can therefore rely on contracts 'stateful' objects.

Functional languages organise their code around the concept of a mathematical function (similar to the procedures above), building complex code by composing functions together and using recursive approaches to deal with sequential data. Unlike the paradigms above, functional languages are highly restrictive in terms of what can be expected when calling functions; a function that's given a particular input is always expected to return the same output, fundamentally disallowing internal state. Although this may seem a huge disadvantage, there are functional techniques that circumvent it. With the object-oriented paradigm, functional approaches can centre on contracts between functions and their callers.

The final of the four language paradigms is that logic programming, where code is organised around logical sentences. Logic programming is primarily used for logic tasks – such as that of artificial intelligence and natural language processing – that require complex decisions to be made based on a wide variety of data.

These four paradigms require developers to think in fundamentally different ways when designing, and can have a huge impact on the resulting formation.

Many languages provide more than one of these programming paradigms (see Table 6,5), either through direct support or through extensions, so it's possible to mix different approaches in a single solution.
