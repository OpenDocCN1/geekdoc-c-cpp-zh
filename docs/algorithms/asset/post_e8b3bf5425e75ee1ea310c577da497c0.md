# Chapter 1
Algorithms with numbers

One of the main themes of this chapter is the dramatic contrast between two ancient problems that at first seem very similar:

- FACTORING: Given a number $N$, express it as a product of prime factors.
- PRIMALITY: Given a number $N$, determine whether it is a prime.

Factoring is hard. Despite centuries of effort by some of the world's smartest mathematicians and computer scientists, the fastest methods for factoring a number $N$ take exponential time in the number of bits of $N$.

On the other hand, we shall soon see that we can efficiently test whether $N$ is prime! And (it gets even more interesting) this strange disparity between the two intimately related problems, one very hard and the other very easy, lies at the heart of the technology that enables secure communication in today's global information environment.

In route to these insights, we need to develop algorithms for a variety of computational tasks involving numbers. We begin with basic arithmetic, an appropriate starting point because, as we know, the word algorithms originally applied only to methods for these problems.

## 1.1 Basic arithmetic

### 1.1.1 Addition

We were so young when we learned the standard technique for addition that we would scarcely have thought to ask $why$ it works. But let's go back now and take a closer look.

It is a basic property of decimal numbers that

> The sum of any three single-digit numbers is at most two digits long.

Quick check: the sum is at most $9 + 9 + 9 = 27$, two digits long. In fact, this rule holds not just in decimal but in any base $b \ge 2$ (Exercise 1.1). In binary, for instance, the maximum possible sum of three single-bit numbers is 3, which is a 2-bit number.

# Bases and logs

Naturally, there is nothing special about the number 10—we just happen to have 10 fingers, and so 10 was an obvious place to pause and take counting to the next. The Mayans developed a similar positional system based on the number 20 (no shoes, see?). And course today computers represent numbers in binary.

How many digits are needed to represent the number $N \ge 0$ in base $b$? Let’s see—with $k$ digits in base $b$ we can express numbers up to $b^k - 1$; for instance, in decimal, three digits get all the way up to $999 = 10^3 - 1$. By solving for $k$, we find that $[\log_b(N+1)]$ digits (about log $N$, digits or take 1) are needed to write $N$ in base $b$.

How much does the size of a number change when we change bases? Recall the rule for converting logarithms from base $a$ to base $b$: $\log N = \log_b N$. The size of integer $N$ in base $a$ is the same as it is in base $b$, times a constant factor $\log_b a$. In Big-O notation, the base is irrelevant, and we write the size as $O(1)$.

Incidentally, the function $\log N$ appears repeatedly in our subject. Here’s why:

1. $\log N$ is, of course, the number of times you must halve $N$ to get 1.
2. $\log N$ can be seen as the number of bits in $N$.
3. $\log N$ is the depth of a complete binary tree.
4. $\log N$ is the number of nodes in a tree.
5. $\log N$ is the power to which you must raise 2 to get $N$.

In any case, $\log N$ is the number of digits needed to represent $N$ in binary.

Algorithms with numbers 

Suppose $x$ and $y$ are each $n$ bits long; in this chapter we use $n$ for size. The running time for addition is therefore of the form $c_0 n + c_1$, where $c_0$ and $c_1$ are some constants. Instead of worrying about the precise values of $c_0$ and $c_1$, we focus on the big picture and denote the running time as $O(n)$.

Now that we have a working algorithm for addition, we inevitably wander to the question of whether there is something better. **Is there a faster algorithm?**

For addition, the answer is no: to add two $n$-bit numbers we must least read and write down the answer, and that requires $n$ operations. So addition is optimal, up to multiplicative constants. Why $O(n)$ operations? Isn't binary addition something computers perform by just one instruction? There are two answers. First, it is truly true that in a single instruction we can add integers whose size is within the word length of today's computers–32 perhaps. But, as will appear later in this chapter, it is often useful and necessary to handle numbers larger than this, perhaps thousand bits long. Adding and multiplying large numbers on real computers is very much like performing the operations by bit. Second, when we want to understand algorithms, it makes sense to study the basic algorithms that are encoded in the hardware of today's computers. In doing so, we shall focus on the *bit complexity* of the algorithm, the number of elementary operations on bits—because this reflects the amount of hardware, transistors and wires, necessary for implementing the algorithm.

## 1.1.2 Multiplication and division

Onward to multiplication! The grade-school algorithm for multiplying two numbers $x$ and $y$ is to create an array of intermediate sums, each representing the product of $x$ by a single digit of $y$. These values are appropriately left-shifted and then added up. Suppose for instance that we want to multiply $13 \times 11$, or in binary notation, $x = 1101$ and $y = 1011$. The multiplication would proceed thus.

|0 0 0 0 (1101 times 0, shifted twice) |
