For instance, if $x = 1011010_2$ (the subscript 2 means “binary”) then $x_L = 1011_2$, $x_s = 0110_2$, and $x = 1011_2 \times 2^4 + 0110_2$. The product of $x$ and $y$ can then be written

> $xy = (2^{n/2}x_L + x_s)(2^{n/2}y_L + y_s) = 2^nx_Ly_L + 2^{n/2}(x_Ly_s + x_sy_L) + x_sy_s$.

We compute $xy$ via the expression on the right. The additions take linear time, as do the multiplications by powers of 2 (which are merely left-shifts). The significant operations are the four n/2-bit multiplications, $x_L, x_s, y_L, y_s$; we can handle this by four recursive calls. Our method for multiplying n-bit numbers starts by making recursive calls to multiply these pairs of n/2-bit numbers (four subproblems of half the size), and then evaluates the preceding expression in $O(n)$ time. For the overall running time on n-bit inputs, we get the recurrence relation

$T(n) = 4T(n/2) + O(n)$.

We will see general strategies for solving such equations. In the meantime, this particular works out to $O(n^2)$, the same running as the traditional grade-school multiplication technique. But we have a radically new algorithm, but we haven't made any progress in efficiency. How can our method be sped up?

This is where Gauss’s trick comes to mind. Although the expression for $xy$ seems to demand four n/2-bit multiplications, just before three we do: $x_Ly_L, x_sy_s$, and $(x_L+x_s)(y_L+y_s) = (x_L+x_s)(y_L+y_s) - x_Ly_s - x_sy_L$. The resulting

# Figure 2.1 A divide-and-conquer algorithm for integer multiplication.

```
function multiply(x, y)
Input: n-bit positive integers x and y
Output: Their product

if n=1: return xy

x_l, x_s = leftmost [n/2], rightmost [n/2] bits of x
y_l, y_s = leftmost [n/2], rightmost [n/2] bits of y

P1 = multiply(x_l, y_l)
P2 = multiply(x_s, y_s)
P3 = multiply(x_l + x_s, P1 - P2) * 2^(n/2 + P2)
```

algorithm, in Figure 2.1, has an improved running time of
$T(n) = 3T(n/2) + O(n)$.

The point is that the constant factor improvement, from 4 to 3, at every level of the recursion, and this compounding effect leads to a dramatically lower time bound of $O(n^{1.59})$.

This running can be derived by looking at the algorithm's pattern of recursive calls, which form a tree structure, as in Figure 2.2. Let's try to understand the shape of this tree. At each successive level of recursion the subproblems get halved in size. At the $(\log n)$, $n^{th}$ level, the subproblems get down to size 1, and so the recursion ends. Therefore, the height of the tree is $\log n$. The branching factor is 3—each problem recursively produces three smaller ones—with the result that at depth $k$ in the tree are $3^k$ subproblems, each of size $n/2^k$.

For each subproblem, a linear amount of work is done in identifying subproblems and combining their answers. Therefore the total time spent at $k$ in the tree is
$3^k \times O(n/2^k) = O(n)$.

> Actually, the recurrence should read
$T(n) \le 3T(n/2 + 1) + O(n)$

since the numbers $(x_l + x_s)$ and $(y_l + y_s)$ could be $n/2 + 1$ bits long. The one we're using is simpler to deal with and can be implemented exactly the same big-O running time.

At the very top level, when $k=0$, this works out to $O(n)$. At the bottom, when $k=\log_2 n$, it is $O(n^{\log_2 3})$, which can be rewritten as $O(n^{1.58})$. Between these two endpoints, the work increases geometrically from $O(n)$ to $O(n^{1.59})$, by a factor of 3/2 per level. The sum of any increasing geometric series is simply the last term of the series: the overall running time is $O(n^{\log_2 3})$.

In the absence of Gauss's trick, the recursion tree would have the same height, but branching factor would be 4. There would be $4^{\log_2 n}=n^2$ leaves, and therefore the running time would be much slower. A practical note: it does not make sense to recurse all the way to bit. For most processors, 32-bit multiplication is a single operation, so by the time the numbers get into this range they should be handed over to the built-in procedure.

Finally, the eternal question: Can we do better? It turns out that other divide-and-conquer algorithms exist, based on another important algorithm like Fourier transform, to be explained in Section 6.

## Recurrence relations

Divide-and-conquer algorithms follow a generic pattern: they tackle a problem of size $n$ by recursively solving, say, $a$ subproblems of size $n/b$ and then combining their answers in $O(n^d)$ time. Their running time is captured by the equation $T(n) = aT(n/b) + O(n^d)$ for some constants $a > 0, b > 1$, and $d \ge 0$. We derive a closed-form solution to this recurrence so that no longer have to solve it explicitly.

Master theorem: If $T(n) = aT(n/b) + O(n^d)$, then
$T(n) = \begin{cases} O(n^d) & d > \log_b a \\ O(n \log n) & d = \log_b a \\ O(n^{\log_b a}) & d < \log_b a \end{cases}$

This theorem tells us the running times of divide-and-conquer procedures we are likely to use. To prove the claim, that the size of subproblems decreases by a factor of $b$ with each level of recursion, and therefore reaches the base case after $\log_b n$ levels. The height of the recursion tree. is $a$, so the $k^{th}$ level of the tree is made up of $a^k$ subproblems, each of size $n/b^k$. The total work done at this level is
$a^k \times O(\frac{n}{b^k}) = O(n^d)$

As $k$ goes from 0 (the root) to $\log_b n$ (leaves), these numbers form a geometric series with ratio $a/b^d$. Finding the sum of such a series in big-O notation comes to three cases

- 1. The ratio is less than 1. Then the series is decreasing, and its sum is just by its first term, $O(n^d)$.
- 2. The ratio is greater than 1. The series is increasing and its sum is given by its last term $O(n^{\log_b a})$:
$n^d (\frac{a}{b^d})^{\log_b n} = n^d \frac{a^{\log_b n}}{n^d} = a^{\log_b n}$
- 3. The ratio is exactly 1. In this case $O(\log n)$ terms of the series are equal to $O(n^d)$.

These cases translate directly into the three cases in the statement. There are even more general results of this type, but we will not need them.

## Binary search

The ultimate divide-and-conquer algorithm is, of course, binary search: to find a key $k$ in a large file containing keys $z[0, 1, \dots, n-1]$ in sorted order, we first compare $k$ with $z[n/2]$ and based on the result recurse either on the first half of the file, $z[0,\dots,n/2-1]$, or on the second half, $z[n/2,\dots,n-]$. The recurrence is $T(n) = T(n/2) + O(1)$, which is the case $a=1, b=2, d=0$. Plugging into our master theorem we get the familiar solution: a running time of $O(\log n)$.

## 2.3 Mergesort

The problem of sorting a list of numbers lends itself immediately to a divide-and-conquer strategy: split the list into two halves, recursively sort each half, and then merge the two sorted sublists.

```
function mergesort(a[1...n])
Input: An array of numbers a[1...n]
Output: A sorted version of this array

if n > 1:
    return merge(mergesort(a[1...n/2]),
                  mergesort(a[n/2 + 1...n]))
else:
    return a
```

The correctness of this algorithm is self-evident, as long as a correct subroutine is specified. If we are given two sorted arrays $x[1...k]$ and $y[1...l]$, how we efficiently merge them into a single sorted array $z[1...k+l]$? Well, the first element of $z$ is either $x[1]$ or $y[1]$, whichever is smaller. The rest of $z[i]$ can be constructed recursively.

```
function merge(x[1...k], y[1...l])
  if k=0: return y[1...l]
  if l=0: return x[1...k]
  if x[1]≤y[1]:
    return x[1]○merge(x[2...k], y[1...l])
  else:
    return y[1]○merge(x[1...k], y[2...l])
```

Here ○ denotes concatenation. This merge procedure takes a constant amount of work per recursive call (the provided array space is allocated in advance), for a total running time of $O(k+l)$. Merge are linear, and the overall time taken by mergesort is

```
T(n) = 2T(n/2) + O(n).
```

or $O(n \log n)$.
