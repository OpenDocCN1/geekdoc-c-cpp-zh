# Bases and logs

Naturally, there is nothing special about the number 10—we just happen to have 10 fingers, and so 10 was an obvious place to pause and take counting to the next. The Mayans developed a similar positional system based on the number 20 (no shoes, see?). And course today computers represent numbers in binary.

How many digits are needed to represent the number $N \ge 0$ in base $b$? Let’s see—with $k$ digits in base $b$ we can express numbers up to $b^k - 1$; for instance, in decimal, three digits get all the way up to $999 = 10^3 - 1$. By solving for $k$, we find that $[log_b(N+1)]$ digits (about log $N$, digits or take 1) are needed to write $N$ in base $b$.

How much does the size of a number change when we change bases? Recall the rule for converting logarithms from base $a$ to base $b$: $\log N = \log_b N$. The size of integer $N$ in base $a$ is the same as it is in base $b$, times a constant factor $\log_b a$. In Big-O notation, the base is irrelevant, and we write our size as $O(\log N)$. We do not specify base, as we almost never will, we mean $\log N$.

Incidentally, this function $\log N$ appears repeatedly in our subject, in many guises. Here’s a sampling:

+   1. $\log N$ is, of course, the power to which you need 2 in order to obtain $N$.
2. Going back, it can also be seen as the number of times you must halve $N$ to get down to 1 (More precisely: $[\log N]$). This is useful when a number is halved at each iteration of an algorithm, as in examples later in the chapter.
3. It is the number of bits in the binary representation of $N$. (More precisely: $[\log(N+1)]$).
4. It is also the depth of a complete binary tree with $N$ nodes. (More precisely: $[\log N]$).
5. It is the sum $1+\frac{1}{2}+\frac{1}{4}+\cdots+\frac{1}{2N}$ to within a constant factor (Exercise 1.5).

This simple rule gives us to add two numbers in any base: align their right hands, and perform a single right-to-left pass in which the sum is computed by digit, magnifying the overflow as a carry. We know each individual sum is a two-digit number, the carry is always a single digit, and so at any step, three-digit numbers are added. Here’s an example showing the addition $53+35$ in binary.

| Carry | 1 | 1 | 1 | 1 |
| --- | --- | --- | --- | --- |
| | 1 | 0 | 0 | 1 | (53) |
| | 1 | 0 | 0 | 1 | (35) |
| | 0 | 1 | 1 | 0 | (88) |

Ordinarily we would spell out the algorithm in pseudocode, but in this case it is familiar to do not repeat it. We move straight to analyzing its efficiency.

Given two binary numbers $x$ and $y$, how long does our algorithm take to add them? This is the kind of question we will persistently be asking throughout this book. We want the answer as a function of the size of the input: the number of bits of $x$ and $y$, the number of keystrokes to type them in.
