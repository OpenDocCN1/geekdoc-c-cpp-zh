
## 1.5 Universal hashing

We end this chapter with an application of number theory to the design of hashing functions. Hashing is a very useful method of storing data items in a table so as to support insertions, deletions, and lookups.

Suppose, for instance, that we need to maintain an ever-changing list of about 250 IP (Internet protocol) addresses, perhaps the addresses of the currently active customers of a Web service. Recall that an IP address consists of 32 bits encoding the location of a computer on the Internet, usually broken down into 8-bit fields, for example, (128.32.168.20). We could obtain fast lookups if we maintained the records in an array indexed by IP address. But this would be wasteful of memory: the array would have $2^{32} \approx 4 \times 10^9$ entries, the majority of them blank. Alternatively, we could use a linked list of the 250 records. But then accessing records would be very slow, taking time proportional to 250, the total number of customers. Is there a way to get the best of both worlds, to use an amount of memory that is proportional to the number of customers and yet achieve fast lookups? This is exactly hashing comes in.

### 1.5.1 Hash tables

Here's a high-level view of hashing. We will give a "nickname" to each of the $2^{32}$ possible IP addresses. You can think of this short name as a number between 1 and 250 (we will later adjust this range slightly). Many IP addresses will inevitably have the same nickname; however, most of the 250 IP addresses of our particular customers are assigned distinct names, and we will store their records in an array of size 250 indexed by these names. What if there is more than one record associated with the same name? Easy; each entry of the array points to a linked list containing all records with that name. So the total amount of storage is proportional to 250, the number of customers, and independent of the total number of possible IP addresses. Moreover, if not many customer IP addresses are assigned the same name, lookup is fast, because the average size of the linked list we have to scan is small.

But how do we assign a short name to each IP address? This is the role of a hash function: in our example, a function $h$ that maps IP addresses to positions in a table of length 250 (the expected number of data items).

IP address $x$ is thus $h(x)$, and the record for $x$ is stored in position $h(x)$ of the table. As described above, each position of the table is in a bucket, a linked list that contains all current IP addresses that map to it. Hopefully, there will be few buckets that contain more than a handful of IP addresses.

### 1.5.2 Families of hash functions

Designing hash functions is tricky. A hash function must in some sense be "random" (so that it scatters data around), but it should also be a function and therefore "consistent" (so that we get the same result every we we apply it). And the statistics of the data items may work against us. In our example, one hash function would map an IP to its last segment: $h(128.32.168.20) = 80$. A table of $n=256$ buckets would be required. But is this a good hash function? Not if, for example, the first segment of an IP address tends to be small; then buckets would be required—for example, if most of our customers come from Asia. There is nothing inherently wrong with: if 250 IP addresses were uniformly drawn from all $2^{32}$ possibilities, these functions would behave well. Conversely, there is no single hash function, no matter how sophisticated, that behaves well on all sets of data. Since a hash function maps $2^{32}$ addresses to 250 names, there must be a collection of at least $2^{32}/250 \approx 16,000,000$ IP addresses that are assigned the same name (or, in hashing terminology, "collision"). If many of these show up in our list, we're in trouble. Obviously, we need some kind of randomization. Here's an idea: let us pick a hash function at random from some class of functions. We will then show that, no matter what set of 250 IP addresses we care about, most choices of the function will give few collisions. To end this, we turn to number theory. Let us take the number of buckets to be $n=257$—a prime number! And consider every IP address $x$ as a quadruple $(x_1, x_2, x_3, x_4)$ of integers between 0 and $n-1$, so we define a function $h$ from IP addresses to a number mod $n$ as follows: for any four numbers $a_1, a_2, a_3, a_4 \in \{0, \dots, n-1\}$, define $h$ to be the following function:

$$h(x_1, x_2, x_3, x_4) = \sum_{i=1}^4 a_i x_i \pmod n.$$

We will show that if we pick these coefficients $a$ at random, $h_a$ is very likely to be good in the following sense:

**Property.** Consider any pair of distinct IP addresses $x = (x_1, x_2, x_3, x_4)$ and $y = (y_1, y_2, y_3, y_4)$. If the coefficients $a = (a_1, a_2, a_3, a_4)$ are chosen uniformly from $(0, \dots, n-1)$,

$$Pr[h_a(x_1, x_2, x_3, x_4) = h_a(y_1, y_2, y_3, y_4)] = \frac{1}{n}.$$

In other words, the chance that $x$ and $y$ collide under $h_a$ is the same as if each were assigned randomly and independently. This condition guarantees that the expected lookup time for any item is small. Here's why: if we wish to look up $x$ in our hash table, the time required is determined by the size of its bucket, that is the number of items assigned the same name as $x$. But there are only 250 items in the hash table, and the probability that any item gets the same name as $x$ is $1/n=1/257$. Therefore the expected number of items that are assigned the same name as $x$ by a randomly chosen hash function $h_a$ is $250/257 \approx 1$, which makes the expected size of $x$'s bucket less than 2.

Let us now prove the property.

**Proof.** Since $x = (x_1, x_2, x_3, x_4)$ and $y = (y_1, y_2, y_3, y_4)$ are distinct, these quadruples must differ in some component; without loss of generality we assume $x_4 \neq y_4$. We wish to compute the probability $Pr[h_a(x_1, x_2, x_3, x_4) = h_a(y_1, y_2, y_3, y_4)]$, that is the probability that $\sum_{i=1}^4 a_i x_i = \sum_{i=1}^4 a_i y_i \pmod n$. This equation can be rewritten as

$$\sum_{i=1}^4 a_i (x_i - y_i) \equiv 0 \pmod n.$$

Suppose that we draw a random function $h_a$ by picking $a = (a_1, a_2, a_3, a_4)$ at random. We start by drawing the first number $a_1, a_2$, and $a_3$, and then think: What is the probability that the last number $a_4$ is such that the equation holds? Since the far left side of the equation evaluates to some number, call it $c$. Since $n$ is prime and $x_4 \neq y_4$, $(y_4 - x_4)$ has a unique inverse modulo $n$. Thus for the equation to hold, the last number $a_4$ must be $c \cdot (y_4 - x_4)^{-1} \pmod n$, out of $n$ possible values. The probability of this happening is $1/n$, and it is complete.
