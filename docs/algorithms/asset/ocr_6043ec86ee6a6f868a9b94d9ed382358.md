The correctness of this algorithm is self-evident, as long as a correct subroutine is specified. If we are given two sorted arrays x[1...k] and y[1...l], how we efficiently merge them into a single sorted array[1...k+l]? Well, the first element of z is either x[1] or y[1], whichever is smaller. The rest of z[i] can be constructed recursively.

```
function merge(x[1...k], y[1...l])
  if k=0: return y[1...l]
  if l=0: return x[1...k]
  if x[1]≤y[1]:
    return x[1]○merge(x[2...k], y[1...l])
  else:
    return y[1]○merge(x[1...k], y[2...l])
```

Here ○ denotes concatenation. This merge procedure takes a constant amount of work per recursive call (the provided array space is allocated in advance), for a total running time of O(k+l). Merge's are linear, and the overall time taken by mergesort is

```
T(n) = 2T(n/2) + O(n).
```

or O(n log n).\ Looking back the mergesort algorithm, we see that all the real work is done in merging, which doesn't start until the recursion gets down to singleton arrays. The singletons are merged in pairs, to yield arrays with two elements. Then pairs of 2-tuples are merged, producing 4-tuples, and so on. Figure 2.4 shows an example.

This viewpoint also suggests how mergesort might be iterative. At any given moment, there is a set of "active" arrays—initially, the singletons—which are merged in pairs to give the next batch of arrays. These arrays can be organized in a queue, and processed by repeatedly removing arrays from the front of the queue, merging them, and putting the result at the end of the queue.

In the following pseudocode, the primitive operation inject adds element to the end of the queue while removes and returns the element at the front of the queue.

```
function iterative-mergesort(a[1...n])
Input: elements a1, a2,...,an to be sorted

Q = [ ] empty queue
for i=1 to n:
  inject(Q, [ai])
while |Q| > 1:
  inject(Q, merge(eject(Q), eject(Q)))
return eject(Q)
```
