# 7.6 The simplex algorithm

Finding the cost is quick, just dot product, and checking whether it is a true vertex involves solving a system of n equations in n unknowns (that is, satisfying the n inequalities equally) and checking whether the result is feasible. By Gaussian elimination (see the following box) this takes O(n²) time, giving an unappetizing running time of O(mn³) per iteration.

Fortunately, there is a much better way, and this mn factor can be improved by mn, making simplex a practical algorithm. Recall our earlier discussion (7.6.2) about rewriting the LP from vertex u. It turns out that the per-iteration overhead of rewriting the LP in terms of the current local coordinates is O((m+n)n); this exploits the fact that the local views change only slightly between iterations, one of its definitions.

Next, to select the best neighbor, we recall that the (local view) of the objective function is of “max cu + y” where cu is the value of the objective function at u. This immediately identifies a promising direction to move: pick any ci (if there is none, then the current vertex is optimal and simplex halts). Since the rest of the LP has been rewritten in terms of the y-coordinates, it is easy to determine how yi can be increased before any other inequality is violated. (And if we can increase yi indefinitely, we know the LP is unbounded).

It follows that the running time per iteration of simplex is O(mn). But many iterations could there be? Naturally, there can be more than (mⁿ), which is an upper bound on the number of vertices. This upper bound is exponential in n. And in fact, there are examples of LP for which simplex does indeed take an exponential number of iterations. In other words, simplex is an exponential-time algorithm. However, it does not occur in practice, and it is this fact that makes simplex so valuable and widely used.

# Linear programming in polynomial time

Simplex is not a polynomial time algorithm. Certain kinds of linear programs cause it to go from one corner of the feasible region to a better one and to a still better one, and so on for an exponential number of steps. For a long time, linear programming was considered a paradox, a problem that could be solved in practice, but not in theory!

In 1979, a Soviet mathematician Leonid Khachian came up with the ellipsoid algorithm, which is very different from simplex, extremely simple in its conception (sophisticated in its proof) and yet one can solve any linear program in polynomial time. Instead of changing the solution from one corner of the polyhedron to the next, Khachian’s algorithm confines to smaller and smaller ellipsoids (skewed high-dimensional balls). When this was announced, it became one of “mathematical Sputnik,” a splashy achievement that had the U.S. establishment worried, in the height of the Cold War, about the scientific superiority of the Soviet Union. The ellipsoid algorithm turned out to be an important theoretical, but did not compete with simplex in practice. The paradox of linear programming deepened: with two algorithms, one that is efficient in theory, and one that is efficient in practice!
