# Reductions

Sometimes a computational task is sufficiently general that any subroutine for it can also be used to solve a variety of other tasks, which at glance might seem unrelated. For instance, we saw in Chapter 6 how an algorithm for finding the longest path in a dag, surprisingly, also be used for finding increasing subsequences. We describe this phenomenon by saying that the longest increasing subsequence problem reduces to the longest path in a dag. In turn, the longest path in a dag reduces to the shortest path in a dag; here how a subroutine for the latter can be used to solve the:

```
function LONGEST_PATH(G)
negate all edge weights of G
return SHORTEST_PATH(G)
```

Let's step back and take a slightly more formal view of reductions. If any subroutine for task Q also be used to solve P, we say P reduces to Q. Often, P is solvable by a single call to Q's subroutine, which means any x of P can be transformed into an instance y of Q that P(x) can be deduced from Q(y):

Do you believe the reduction from P = LONGEST PATH to Q = SHORTEST PATH follows this schema? If the pre- and preprocessing procedures are efficiently computable then this creates an efficient algorithm for P out of any algorithm for Q!

Reductions enhance the power of algorithms: Once we have an algorithm for Q (which could be shortest path, for example) we can use it to solve other problems. In fact, most of the computational we study in this book are considered core computer science problems precisely because they arise in so many applications, which is another way of saying that many problems reduce to this. This is especially true of linear programming.

One cautionary observation: our LP has one variable for every possible path between the users. In a larger network, there could easily be exponentially many paths, and therefore this particular way of translating the network problem into an LP will not scale well. We will see a clever and more scalable formulation in Section 7.2.
