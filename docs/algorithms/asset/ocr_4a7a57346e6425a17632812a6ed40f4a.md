IP address x is thus h(x), and the record for x is stored in position h(x) of the table. As described above, each position of the table is in a bucket, a linked list that contains all current IP addresses that map to it. Hopefully, there will be few buckets that contain more than a handful of IP addresses.

# 1.5.2 Families of hash functions

Designing hash functions is tricky. A hash function must in some sense be "random" (so that it scatters data around), but it should also be a function and therefore "consistent" (so that we get the same result every we apply it). And the statistics of the data items may work against us. In our example, one hash function would map an IP to the 8-bit number that is its last segment: h(128.32.168.80) = 80. A table of $n=256$ buckets would be required. But is this a good hash function? Not if, for example, the segment of an IP address tends to be small (single-digit); then numbered buckets would be required. Taking the first segment of the IP address invites disaster—for example, if most of our customers come from Asia.

There is nothing inherently wrong with these two. If 250 IP addresses were uniformly drawn from all $N=2^{32}$ possibilities, then these functions would behave well. The problem is that we have no guarantee that the distribution of IP addresses is uniform.

Conversely, there is no single hash function, no matter how sophisticated, that behaves well on all sets of data. Since a hash function maps $2^{32}$ IP addresses to 250 names, there must be a collection of at least $2^{32}/250 \approx 2^{24} \approx 16,000,000$ IP addresses that are assigned the same name (or, in hashing terminology, "collision"). If many of these show up in our customer list, we're in trouble.

Obviously, we need some kind of randomization. Here's an idea: let us pick a hash function at random from some class of functions. We will then show that, no matter what set of 250 IP addresses we actually care about, most choices of the function will give very few collisions among these addresses.

To end this, we need to define a class of hash functions from which we can pick at random; and this is where we turn to number theory. Let us take the number of buckets to be not 250 but $n=257$—a prime number! And consider every IP address $x$ as a quadruple $(x_1,...,x_4)$ of integers modulo $n$—recall that it is in fact a quadruple of integers between 0 and 255, so there is no harm in this. We define a function $h$ from IP addresses to a number mod $n$ as follows: fix any four numbers mod $n=257$, say 87, 23, 125, and 14. Now we map the IP address $(x_1,...,x_4)$ to $(87x_1+23x_2+125x_3+4x_4) \pmod{257}$. Indeed, any four numbers mod $n$ define a hash function.

For any four coefficients $a_1,...,a_4 \in \{0,...,n-1\}$, write $a=(a_1,a_2,a_3,a_4)$ and define $h$ to be the following hash function:

```
$h(x_1,...,x_4) = \sum_{i=1}^4 a_i \cdot x_i \pmod n.$
```
