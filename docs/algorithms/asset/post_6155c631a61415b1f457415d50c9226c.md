As can be expected, make is a constant-time operation. On the other hand, find follows parent pointers to the root of the tree and takes time proportional to the height of the tree. The tree actually gets built via the third operation, union, and we must make sure that this procedure keeps trees shallow.

Merging two sets is easy: make the root of one point to the root of the other. But we have a choice here. If the representatives (roots) of the sets are $r_x$ and $r_y$, we make $r_x$ point to $r_y$ or the other way around? Since tree height is the main impediment to computational efficiency, a good strategy is to make the root of the shorter tree point to the root of the taller tree. This way, the overall height increases only if the two trees being merged are equally tall. Instead of explicitly computing heights of trees, we will use the rank of their root nodes—which is why this scheme is called union by rank.

```
procedure union(x, y)
  rx = find(x)
  ry = find(y)
  if rx = ry: return
  if rank(rx) > rank(ry):
    π(ry) = rx
  else:
    π(rx) = ry
    if rank(rx) = rank(ry): rank(ry) = rank(ry) + 1
```

Figure 5.6 for an example.

By design, the rank of a node is exactly the height of the subtree rooted at that node. This means, for instance, as you move up a path toward a root node, the rank values along it are strictly increasing.

- Property 1: For any $x$, $rank(x) < rank(\pi(x))$.

A root node with rank $k$ is created by the merger of two trees with rank $k-1$. It follows by induction (try it!)

- Property 2: Any root node of rank $k$ has at least $2^k$ nodes in its tree.

This extends to internal (nonroot) nodes as well: a node of rank $k$ has at least $2^k$ descendants. After all, any internal node was once a root, and neither its rank nor its set of descendants has changed since then. Moreover, different rank-$k$ nodes cannot have common descendants, since by Property 1 any element has at most one ancestor of rank $k$.

- Property 3: If there are $n$ elements, there can be at most $n/2$ nodes of rank $k$. This last observation implies, crucially, the maximum rank is $\log n$. Therefore, all the trees have height $\le \log n$, and this is an upper bound on the running time of find and union.

With the data structure presented so far, the total time for Kruskal's algorithm is the bottleneck. But can we perform union and find faster than $\log n$? The answer is, being more careful to maintain our data structure in good shape. As any housekeeper knows, a little extra effort into maintenance can pay off handsomely in the long run, by forestalling calamities. We have in mind a particular operation for our union-find data structure, intended to keep the trees—during each find, when a series of pointers is followed to the root of the tree, we will change all pointers so they point directly to the root (Figure 5.7). This path compression heuristic only slightly increases the time needed for a find and is easy to code.

```
function find(x)
  if x ≠ π(x): π(x) = find(π(x))
  return π(x)
```

The benefit of this simple alteration is long-term rather instantaneous and thus necessitates a particular kind of analysis: we need to look at sequences of find and union operations, starting from an empty data structure, and measure the average time per operation. This amortized cost turns out to be barely more O(1), from the early $O(\log n)$.

Think of the data structure as having a “top level” consisting of the root nodes, below it, the insides of the trees. There is a division of labor: find operations, with path compression, only touch the insides of trees, whereas union operations look at the top level. Thus path compression has no effect on union operations and leaves the top level unchanged.

We know that the ranks of root nodes are unaltered, but about what nonroot nodes? The key point is here that once a node ceases to be a root, it never resurfaces, and its rank is forever fixed. Therefore the ranks of all nodes are unchanged by path compression, even though these numbers can no longer be interpreted as tree heights. In particular, properties 1-3 (from page 133) still hold.

If there are $n$ elements, their rank value can range from 0 to $\log n$ by Property 3. Let's decide the nonzero part of the range, which will soon become clear: the total time is $O(|E|\log|V|)$ for sorting edges (remember, $|E| \approx |V|$) plus for the union and find operations that dominate the rest of the algorithm. So there seems to be little incentive to make our data structure more efficient.

But if the edges are given unsorted? Or if the weights are small, can sorting be done in linear time? Then the data structure becomes the bottleneck, and it is useful to think about improving its performance beyond $\log n$. As it turns out, the improved data structure is useful in many other applications.
