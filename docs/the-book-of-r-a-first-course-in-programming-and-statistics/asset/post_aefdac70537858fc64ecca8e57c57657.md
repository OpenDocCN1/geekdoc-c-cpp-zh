# 12.1 Exception Handling

When there's an unexpected problem during execution of a function, R will notify you with either a warning or an error. In this section, I'll demonstrate how to build these constructs into your own functions where appropriate. I'll also show how to try a calculation to check whether it's possible without an error (that is, to see whether it'll even work).

# 12.1.1 Formal Notifications: Errors and Warnings

In Chapter 11, you made your functions print a string (for example, "no valid matrices") when they couldn't perform certain operations. Warnings and errors are more formal mechanisms designed to convey these types of messages and handle subsequent operations. An error forces the function to immediately terminate at the point it occurs. A warning is less severe. It indicates that the function is being run in an atypical way but tries to work around the issue and continue executing. In R, you can issue warnings and can throw errors with the stop command.

The two functions show an example of each:

```
warn_test <- function(x){
  if(x<0){
    warning('*x' is less than or equal to 0 but setting it to 1 and continuing')
    x <- 1
  }
  return(5/x)
}

error_test <- function(x){
  if(x<=0){
    stop('*x' is less than or equal to 0... TERMINATE')
  }
  return(5/x)
}
```

Both warn_test and error_test divide 5 by x. They both expect x to be positive. In warn_test, if x is nonpositive, the function issues a warning, and x is overwritten to 1. In error_test, on the hand, if x is nonpositive, the function throws an error and terminates. The two commands warning and stop are used with a character string, which becomes the message printed to the console. You can see these notifications by calling the functions follows:

```
R> warn_test(0)
[1] 5
Warning message:
In warn_test(0) : '*x' is less than or equal to 0 but setting it to 1 and continuing
R> error_test(0)
Error in error_test(0) : '*x' is less than or equal to 0... TERMINATE
```

Notice that warn_test has been executed and returned the value 5 after setting x to 1. The call to error_test did not return anything because R exited at the stop command.

Warnings are useful when there's a natural way for a function to save itself when it doesn't get the input it expects. For example, in Section 10.1.3, R issued a warning when you supplied a logical vector to if statement. Remember that if statement expects a single logical value, but rather than quit when a logical vector is instead, it continues execution using just the first entry in the vector. That, sometimes it's more appropriate to throw an error and stop execution. Let's go back to myfibrec from Section 11.3. This function expects a positive integer (the position of Fibonacci number it should return). Suppose that if the user supplies a negative integer, the user actually means the positive version of the term. You can add a warning to handle this situation. Meanwhile, if the user enters 0, which doesn't correspond to any position in the series, the code will throw an error. Consider these modifications:

```
myfibrec2 <- function(n){
  if(n<0){
    warning("Assuming you meant 'n' is positive -- doing that instead")
    n <- -1
  } else if(n==0){
    stop("n is uninterpretable at 0")
  }

  if(n==1|n==2){
    return(1)
  } else {
    return(myfibrec2(n-1)+myfibrec2(n-2))
  }
}
```

In myfibrec2, you now check whether n is negative or zero. If it's negative, the function issues a warning and continues execution after swapping the argument's sign. If n is zero, an error halts execution with a corresponding message. Here you can see the responses for few different arguments:

```
R> myfibrec2(6)
[1] 8
R> myfibrec2(-3)
[1] 2
Warning message: in myfibrec2(-3) : Assuming you meant 'n' is positive -- doing that instead
R> myfibrec2(0)
Error in myfibrec2(0) : n is uninterpretable at 0
```

Note that the call to myfibrec2(-3) has returned the Fibonacci number.

Broadly speaking, both errors and warnings signal that something has gone wrong. If you're using a certain function or running chunks of code and encounter these kinds of messages, you should look carefully at what has been run and what may have caused them.

**NOTE** Identifying and repairing erroneous code is referred to debugging, for which there are various strategies. One of the most basic strategies involves print or calling commands to inspect various questions as they are calculated during live execution. R has some more sophisticated debugging tools; if you're interested, check out the excellent discussion of them in *Chapter 13 of The Art of R Programming by Mattheloff (2011).* A more general discussion can be found in *The Art of Debugging by Mattheloff and Saltman (2008).* As you gain more experience in R, understanding error messages or locating potential problems in code before they arise becomes much easier, a benefit you get partly because of R's interpretive nature.

# 12.1.2 Catching Errors with try Statements

When a function terminates with an error, it also terminates any other functions. For example, if function A calls function B and B halts because of an error, this halts execution of A at the same point. To avoid this severe consequence, you can use a try statement to attempt a function call and check whether it produces an error. To specify alternative operations, rather than allowing all processes to cease.

For example, if your myfibrec function from early passes 0, the function throws an error and terminates. But watch what happens when you pass that function as the first argument to try:

```
R> try(myfibrec(0),silent=TRUE)
```

Nothing seems to happen. What happened to the error? In fact, the error has still occurred, but try has suppressed the error message to the console because you passed the argument silent set to TRUE. The error information is stored in the object try, which is of class "try-error". To see, simply print try to the console:

```
R> try(myfibrec(0))
[1] "Error in myfibrec(0) : 'n' is uninterpretable at 0\n"
attr("class")
[1] "try-error"
attr("condition")
<simpleError in myfibrec(0) : 'n' is uninterpretable at 0>
```

You would have seen this printed to the console if you'd left silent to FALSE. Catching an error this way can be really handy, especially when a function produces the error in the body code of another function. Using try, you can handle the error without terminating that parent function.
