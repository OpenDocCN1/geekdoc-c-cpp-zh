## 11.2.3 Checking for Missing Arguments

The `missing` function checks the arguments of a function to see if all required arguments have been supplied. It takes an argument tag and returns a logical value of TRUE if the specified argument is not found. You can use `missing` to avoid the error you saw in an earlier call to multiples, when stri was required but not supplied.
In some situations, the `missing` function can be particularly useful in the body code. Consider another modification to the example function:

```r
multiples3 <- function(x,mat,stri,str2){
  matrix.flags <- sapply(x,FUN=is.matrix)

  if(any(matrix.flags)){
    if(missing(stri)){
      return("str1' was missing, so this is the message")
    } else {
      return(stri)
    }
  }

  indexes <- which(matrix.flags)
  counter <- 0
  result <- list()
  for(i in indexes){
    temp <- x[[i]]
    if(ncol(temp)==nrow(mat)){
      counter <- counter+1
      result[[counter]] <- temp%%mat
    }
  }

  if(counter==0){
    if(missing(str2)){
      return("str2' was missing, so this is the message")
    } else {
      return(str2)
    }
  } else {
    return(result)
  }
}
```

The differences between this version and multiples1 are in the first and last if statements. The first statement checks whether there are no matrices in x, in which case it returns a string message. In multiples1, that message was always stri, but now you use another statement with `missing(stri)` argument that has a value first. If not, the function returns another character string saying that stri was missing. A similar alternative is defined for str2. Here it is once more importing the function and using foo, bar, and baz:

```r

R multiples3(baz,diag(2))

```

Using this way permits arguments to be left unspecified in a given function call. It is primarily used when it's difficult to choose a default value for a certain argument, yet the function still needs to handle cases when argument is not provided. In the current example, it makes more sense to define defaults for stri and str2, as you did for multiples2, and avoid the extra code required to implement missing.

## 11.2.4 Dealing with Ellipses

In Section 9.2.5, I introduced the ellipse, also called dot-dot-dot notation. The ellipsis allows you to pass in arguments without having to first define them in the argument list, and these arguments can then be passed to another function call within the code body. When included in a function definition, the ellipse is often (but not always) placed in the last position because it represents a variable number of arguments.

Building on the fib3 function from Section 11.1.1, let us use the ellipse to plot the specified Fibonacci numbers.

```r
myfibplot <- function(thresh,plot=TRUE,...)
  fibseq <- c(1,1)
  counter <- 2
```

```r
repeat{
  fibseq <- c(fibseq,fibseq[counter-1])
  counter <- counter+1
  if(fibseq[counter]>thresh){
    break
  }
}

if(plot){
  plot(1:length(fibseq),fibseq,...)
} else {
  return(fibseq)
}
```

In this function, an `if` statement checks whether `plot` is TRUE (which is the default value). If so, then call `plot`, passing `1:length(fibseq)` for the x-axis and the Fibonacci numbers themselves for y-axis. After these coordinates, you also pass the ellipsis directly into plot. In this case, the ellipsis represents any additional arguments a user might pass to control the execution of plot. Importing `myfibplot` and executing the following line, the plot in Figure 11-1 pops up in graphics device.

```r
R myfibplot(150)
```

If you want to unpack the arguments passed in through an ellipsis you can use the `list` function to convert these arguments into a list. Here's an example:

unpackme <- function(...) {
  x <- list(...)

  print(x)
  cat("\nThe names of ... are:")
}
