
For example, say you call matrix and pass in the argument data, as follows:

```R
R youspeak <- matrix(c("OMG","LOL","WTF","YOLO"),nrow=2,ncol=2)
R youspeak
```

```
[1] [2]
[1] "OMG" "WTF"
[2] "LOL" "YOLO"
```

Calling this function creates a local environment containing the data vector. When you execute the function, it begins looking for data in this local environment. That means R isn't confused by other objects named in other environments (such as the data function manually loaded from the utils package environment). If a required item isn't found in the local environment, only then R begins to wait a little more in search for that (I'll discuss this feature in Section 9.1.2). Once the function has completed, this local environment is automatically removed. The same comments apply to the now or arguments.

## 9.1.2 Search Path

To access data and functions from environments other than the immediate global environment, R follows a search path. The search path lays out the environments that a given R session has available to it.

The search path is basically a list of environments that R will search when an object is requested. If the object isn't found in one environment, R proceeds to the next one. You can view R's search path at any time using search().

```R
R search()
[1] "GlobalEnv" "tools:RGUI" "package:stats"
[4] "package:graphics" "package:Devices" "package:utils"
[7] "package:datasets" "package:methods" "Autoloads"
[10] "package:base"
```

From the command prompt, this path will always begin at the global user environment (.GlobalEnv) and end the base package environment (package:base). You can think of these as belonging to a hierarchy, with an arrow pointing from left to right each pair of environments. For my current session, I request a certain object at the R prompt, the program will inspect .GlobalEnv -> tools:RGUI -> stats ... -> package:base in turn, stopping the search when the desired object is found and retrieved. Note that, depending on your operating system and whether you're using the built-in GUI, tools:RGUI might not be included in your search path.

If R doesn't find what it's looking for among the environments in the search path, the empty environment is reached. The empty environment is not explicitly listed in the output from search(), but it's always the final destination package:base. This environment is special because it marks the end of the search path.

For example, if you call the following, a number of things happen internally.

```R
R baz seq(from=0,to=3,length.out=5)
R baz
[1] 0.00 0.75 1.50 2.25 3.00
```

R first searches the global environment for a function called seq, and when this isn't found, it goes to search in the enclosing environment, which is the next level up in the search path (according to the left-to-right arrows mentioned earlier). It doesn't find it, so R keeps going through the path to the next environment, searching the packages that have been loaded (automatically or otherwise) until it finds what it's looking for. It searches in the built-in base package environment. Then it executes the seq (creating a temporary local environment) and assigns the results to a new object, baz, which resides in the global environment. In the subsequent call to print baz. R begins searching the global environment and immediately finds the requested object.

You can look up the enclosing of any function environment, as follows:

```R
R environment(seq)
<environment: namespace:base>
R environment(arrows)
<environment: namespace:graphics>
```

Here, I've identified the package namespace of base as the owner of the seq function and the graphics package as the owner of the arrows.

Each environment has a parent, to direct the order of the search path. Examining the earlier output from the call search(), you can see that the parent of package:stats, for example, is package:graphics. The specific parent-child structure is dynamic in the sense that the search path changes when additional libraries are loaded or data frames are attached. When you load a contributed package with a call to library, this essentially inserts the desired package in the search path. For example, in Exercise 8.1 on page 161, you installed the contributed package car. After loading this, your search path will include its contents.

```R
R library("car")
R> search()
[1] ".GlobalEnv" "package:car" "tools:RGUI"
[4] "package:stats" "package:graphics" "package:grDevices"
[7] "package:utils" "package:datasets" "package:methods"
[10] "Autoloads" "package:base"
```

Note the position of the car package environment in the path—inserted directly after the global environment. This is where each subsequently package will be placed (followed by any additional packages it depends upon for its own functionality).

As earlier, R will stop searching once it has exhausted the entire search path and reached the empty environment. If you request a function or object that you've defined, that doesn't exist, or that is perhaps in a contributed package you've forgotten to load (this is quite a common mistake), then an error is thrown. "cannot find" errors are recognizable for both functions and other objects.

```R
R> here()
Error: could find function "here"
R> there
Error: object 'there' not found
```

Environments help compartmentalize the huge amount of functionality in R. At that point, masking, discussed in Section 12.3, comes into play. As you get more comfortable with R and want more precise control over how it operates, it's worth investing in how environments.

A few terms are strictly forbidden from being used as names. These reserved names are necessary to protect fundamental operations.

The following identifiers are reserved:

- if and else
- for, while, and in
- function
- repeat, break, and next
- TRUE and FALSE
- Inf and -Inf
- NA, NaN, and NULL

I haven't covered some of the terms on this list. These items represent the core logical values (Section 4.1) and special terms used to represent infinity and missing entries (Section 6.1).

If you try to assign a new value to any of reserved terms, an error occurs.

```R
R NaN <- 5
Error in NaN <- 5 : invalid (do_set) left-hand side to assignment
```

Because R is case sensitive, it's possible to assign values to any case-variant of the reserved names, but this can be confusing and is generally not advisable.

```R
R False <- "confusing"
R nan <- "this is"
R cat(nan,False)
this is confusing
```

Be wary of assigning values to T and F, the abbreviations of TRUE and FALSE. The full identifiers TRUE and FALSE are reserved, but the abbreviated versions are not.

```R
R T <- 42
R F <- TRUE
R F&TRUE
[1] TRUE
```

Assigning values to T and F this way will affect any subsequent code that intends to use T and F to refer to TRUE and FALSE. The second assignment (f <- TRUE) is perfectly legal in R's eyes, but it's extremely confusing the normal usage of F as an abbreviation: the line F&TRUE represents a TRUE&TRUE comparison!

If you've been following along with the examples in your R console, it's prudent to clear the global environment (deleting thereby the objects False, nan, T, and F from your workspace). To do this, use the rm function as shown: ls(), supply a character vector of all objects in the argument list.

```R
R ls()
[1] "bar" "baz" "F" "False" "foo" "nan"
[7] "T" "youthspeak"
R rm(list=ls())
R ls()
character(0)
```

Now the global environment is empty, calling ls() returns an empty character vector (character(0)).
