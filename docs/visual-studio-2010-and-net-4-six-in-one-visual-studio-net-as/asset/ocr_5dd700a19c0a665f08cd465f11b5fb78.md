In addition to updating, the DataContext also supports tracking insertions and deletions. To add a new item to the entity, you can call the insertEntity method and the removeEntity method to remove one. In these cases, the changet will contain Sys.Data.ChangeOperationType.insert and Sys.Data.ChangeOperationType.remove actions. DataContext also supports generation for insertions with its getIdentityMethod and getNewIdentity properties.

It is often requested that the cache be refreshed from the server, and you can complete this by calling the fetchData method of the DataView object — for example, in a click event handler of a button:

```
<input type="button" value="Refresh from server" onclick="$$(CountryList).fetchData(null, null,Sys.Data.MergeOption.overwriteChanges)" />
```

The DataView finds calls to the DataContext, which also has a fetchData method, because it implements the Sys.Data.IDDataProvider interface.

However, because the data on the client is already being tracked for changes, it is important to define how the data on the client and from the server should be merged. You can set this with a Sys.Data.MergeOption value in the third parameter. If you set MergeOption.appendOnly, changes are preserved on the client, and will not be overwritten by the data from the server. If you set MergeOption.overwriteChanges, then values obtained from the server will overwrite the ones on the client.

As you can see, the DataContext is a very complex object with convenient usage. You can use it in even simpler-client code: just pass your object to its trackData method, and the full power of the tracking engine is added to your object.

# Working with ADO.NET Data Services

Earlier, you saw how easy it is to access a web service on the server, from JavaScript, because script generation and JSON serialization is automatically provided by the runtime. However, it may happen that you need a more lightweight, flexible and fully RESTful interface, and Microsoft recommends ADO.NET Data Services (formerly known Astoria) for this purpose. ADO.NET Data Services has many specialties over, and the Microsoft Ajax Library contains classes to support these features.

The Sys.Data.AdonetServiceProxy is a low-level class that inherits from Sys.Net.WebServiceProxy, implements the Sys.Data.IDDataProvider interface, and provides methods and properties for interacting with ADO.NET Data Services. It supports the query, insert, update, and remove operations, and also optimistic concurrency. Although you can use the WebServiceProxy to call an ADO.NET Data Service, it is more convenient with this class, because it handles the HTTP commands and HTTP headers automatically. Under the hood, it uses the Sys.Data.AdonetQueryBuilder class for creating data services. However, if you want, you can use this class directly from your code.
