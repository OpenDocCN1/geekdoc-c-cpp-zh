Here, a Receive activity is instantiated that sets up its ServiceContractName and OperationName properties to the same as used by the Send activity in Listing 11-18. The CanCreateInstance property is set to true, indicating that a new workflow is created to process the message that does not correlate to an existing workflow instance. These settings provide that the approval workflow receives the message sent by the client. It extracts the "request" message parameter and puts it into the request variable.

The workflow is simple. After it receives the request it delays for 10 seconds, emulating a long process. Then the ApproveDomainNameRequest activity is invoked to approve or deny the domain name. The response is sent back to the client by the SendReply activity.

You can see that SendReply extracts its Request property from the message received. When sending the response back to the caller, SendReply extracts the correlation mechanism. Then extracts the correlation information from the received message and puts it into the response. The caller will use this information to correlate the request with the matching response.

You can also see that the Receive activity does not specify either a endpoint address or a binding. The activity inherits these settings from the WorkflowServiceHost.

The ApproveDomainNameRequest's logic is very simple. It approves all domain names ending with "*" and denies any others. Listing 11-20 shows the source code of this activity.
