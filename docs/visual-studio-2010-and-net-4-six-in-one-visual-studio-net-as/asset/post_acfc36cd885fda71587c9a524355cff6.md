The project stores two kinds of data in its back-end database. It waits for the request approval, the states of workflow instances representing new requests are persisted into the database with the built-in SqlWorkflowInstanceStore. When a workflow instance completes, the related information is removed from the database. The requests are also stored in a user table (DNRequest). This table persists the request data even after the related workflow instance completes.

This workflow is instantiated and started when the customer clicks the Send Request button (see Figure 11-19). It invokes the following activities:

- 1. The CreateDomainNameRequest wraps the request into a DNRequest, and saves it into the database.
- 2. The first InvokeMethod calls the AddDNRequestToList method that appends the new request to the list of request (that is, in the middle of Figure 11-19).
- 3. The WaitForApproval suspends the current workflow instance and forces the workflow run-time to persist to the database. After the decision-maker approves denies the request, the workflow instance is reloaded from the database, and the workflow is resumed.
- 4. The second InvokeMethod activity calls the UpdateDNRequest method that updates the state of the request in the list.

# Preparing the Workflow Database

The workflow will save its state in a SQL Server database using the SqlWorkflowInstanceStore built-extension. This extension allows you to set the expected database schema (tables, views, and stored procedures). You must access a SQL Server database where you have rights to create a database. The easiest way is to use SQL Server 2008 on your computer.

Open the Server Explorer (View Server Explorer). Right-click on Data Connections and invoke the Create New Server database. Specify the name you intend to use, and the database name (for, example, DomainName). Figure 11-20 shows the dialog to set up the new database information.

Open the SqlWorkflowInstanceSchema.sql file. You can locate it in the SqlScripts folder of the RequestClient project. In the code editor, right-click and start the Execute SQL command. Specify the database login parameters, and in the Connection Properties tab, type DomainData (or the name of the database you created) in the "Connect to database" field, and then click Next. When the switch completes, in Server Explorer, you can check the tables, views, and stored procedures created.

In addition to the scripts created, the DomainNameWorkflow will use a custom table (DNRequest) to store entity information about domain name requests. Run the DNRequest.sql script (it's also located in the SqlScripts folder)

# Storing a New Request into the Database

When the user clicks the Send Request, the first step of the workflow saves it into the DNRequest table of the database. This step is executed by an instance of the CreateDomainNameRequest activity, as shown in Listing 11-12.

LISTING 11-12: CreateDomainNameRequest.cs

```csharp
using System.Activities;
using DomainNameClient.Activities

namespace RequestClient.Activities
{
{ public sealed class CreateDomainNameRequest: CodeActivity {
    public InArgument<string> DomainName { get; set; }
    public OutArgument<DNRequest> Request { get; set; }

    protected override void Execute(CodeContext context) {
    using (var dataContext = new DomainNameDataEntities()) {
        var request = new DNRequest {
        WorkflowID = context.WorkflowInstanceId,
        RequestedName = DomainName.get(context),
        Status = "New"
    };
    dataContext.AddToToDNRequest(request);
    dataContext.SaveChanges();
    Request.Set(context, request);
}
}
}
```

Code file [CreateDomainNameRequest.cs] available for download at Wrox.com

This activity is a CodeActivity, and its Execute method does the job. It accepts an input argument with DomainName, and it returns a DNRequest entity representing the request. The record is created and stored with Entity Framework 4.0, where an especially important line in Listing 11-12:

```csharp
WorkflowID = context.WorkflowInstanceId
```

It saves the identifier of the current workflow instance into the WorkflowID field. The instance is a GUID, and later, in this example, it will be used to resume the appropriate workflow when someone approves or denies the domain request.

# Communicating with the Host Application

Two steps in the workflow are simple InvokeMethod activities that update the user interface. The first is run as soon as the request is queued; the second, when it is approved. The workflow must communicate with the UI. It sounds easy, but there are two issues to solve:

- The workflow instance must know the main window (a singleton) in order to communicate with it.
- Any UI updates should happen in the UI thread.

There are several alternatives for solving the first issue. In this example, this is done by static class RequestProxy that forwards requests to the main window. Listing 11-13 shows the implementation of this class.

```csharp
using DomainNameDAL;

namespace RequestClient
{
    public static class RequestProxy
    {
        public static MainWindow AppInstance { get; set; }

        public static void AddDNRequestToList(DNRequest request)
        {
            AppInstance.AddDNRequestToList(request);
        }

        public static void UpdateDNRequest(int requestId, string status)
        {
            AppInstance.UpdateDNRequest(requestId, status);
        }
    }
}
```

As you can see, the AppInstance property of this class accepts an instance of the main window, and both method calls (AddDNToList and UpdateDNRequest) are forwarded to that instance. The following extract from MainWindow.xaml shows how these methods are implemented:
