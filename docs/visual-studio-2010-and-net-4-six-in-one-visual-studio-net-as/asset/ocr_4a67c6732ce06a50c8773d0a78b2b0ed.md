CLR level, and in addition to the support for “No-PIA Deployment,” it also provides the capability for you to create applications with loose type-coupling and versed resiliency.

To interoperate with a certain COM interface, you must use a .NET type wrapping the functionality of that interface. Building these wrappers manually is laborious, especially when you have hundreds of COM interfaces (for example, in the case of using the Microsoft Office automation model). PIAs are .NET assemblies generated from COM interfaces to facilitate strongly typed interoperability. For large objects models, the related PIAs are as large as well, these assemblies can easily bloat the size of your application. They can cause version issues when they are distributed independently of your application.

The No-PIA feature allows you to continue using PIAs at design time without having them around at run-time. The C compiler will append the small part of the PIA that a program actually uses to its assembly. At run-time, the PIA does not have to be loaded.

Let’s create a simple example to help understand the concept of type equivalence. This application will create a Document and insert some text and a table into it.

Start Visual Studio 2010 and create a new C# Console Application with the name TypeEqualityDemo. Add a new C# Class Library project with the name WordHelper to the solution, and a reference to this project from TypeEqualityDemo.
