
```csharp
out result ? result : default(T);
set { _Storage[new SparseIndex { Row = row, Column = column }] = value; }
```

This matrix allows you to omit the column value from the indexer. For example, you could write the following:

```csharp
var matrix = new SparseIndex();
// Initialize the matrix
Console.WriteLine(matrix[123]);
```

Although you can even omit the row information, you cannot omit all the indexes altogether. The following code would raise a syntax error:

```csharp
Console.WriteLine(matrix[]); // --- This is not allowed
```

If your index has only one parameter and you declare it as an optional, the compiler will display a warning. For example, you can have a SparseVector class similar to SparseArray with the following indexer:

```csharp
public T this[int row = 0]
{
    get
    {
        T result;
        return _Storage.TryGetValue(row, out result)
            ? result : default(T);
    }
    set { _Storage[row] = value; }
```

Here row cannot be used as an optional parameter, because indexers cannot be used with zero parameters; they must have at least one. The warning you receive will reveal your intention.

# Using Named Parameters

In versions of C#, method, constructor, and indexer arguments could be passed only by their position. C# 4.0 now allows passing arguments by names. The method invocation may contain arguments that match the name of the parameter in the method declaration. Use the name of the parameter, followed by a colon, to signal that you want to pass those by names, and not by position.

For example, you can call the DoWork method declared with the following signature:

```csharp
public void DoWork(int taskID,
string taskType = "Cleanup",
int timeOut = 10000,
bool useMultipleCores = false);
```

You use these invocations to use only the taskID and useMultipleCores parameters:

```csharp
DoWork(123, useMultipleCores: true);
DoWork(taskID: 123, useMultipleCores: true);
```

As you can see, positional and named arguments can be mixed in the same call. However, no positional arguments can be used after named arguments. In the following code snippet, the second call will raise a compile time error:

```csharp
DoWork(123, useMultipleCores: true);
DoWork(useMultipleCores: true, 123);
```

The reason behind this requirement is obvious. The named parameter explicitly signals the caller's intention to diverge from the original sequential positions. Could you tell the number of the position for 123 in the second method call?

# Overload Resolution

The introduction of named and optional parameters changed the way of resolving overloaded method invocations. Let take a deeper look at these changes.

# Abstract and Virtual Members

C# allows using parameter names in overrides that are different than in the abstract or virtual definitions. For example, in the following sample, MyMethod has different parameter names in the base and the derived class:

```csharp
public class BaseClass
{
    public virtual void MyMethod(int firstPar, string secondPar) {}
}

public class ChildClass : BaseClass
{
    public override void MyMethod(int firstArg, string secondArg) {}
}
```

How should MyMethod be called with named parameters? How should parameter names in BaseClass or in ChildClass be passed? Any of them be used? The language specification says, "the parameter names are the ones that appear in the most specific order of the function member with respect to the static type of the target of the member access." To understand this rule, here is a short example showing how to use these names:

```csharp
// Most specific context: BaseClass
var myClass = new BaseClass();
myClass.MyMethod(firstPar: 1, secondPar: "Hello");
myClass.MyMethod(firstArg: 1);
```

```csharp
myClass.MyMethod(firstPar: 1, secondPar: "Hello");

// --- Most specific context: ChildClass
var childClass = new ChildClass();
childClass.MyMethod(firstArg: 1, secondArg: "Hello");
```

When the myClass variable is initialized, the compiler infers its type as BaseClass. So, both MyMethod calls use the parameter names in the most specific override that can be found by BaseClass. The childClass variable is a type of ChildClass, so when calling MyMethod through childClass, the context for parameter name resolution is ChildClass.

# Resolving Applicable Signatures

When you have a method with more than one overload, the compiler must resolve it during the build process. The compiler first filters the overloads to which are applicable to the method call context. If there are more candidates, the compiler uses "betterness" rules to select the best one.

With named and optional arguments, this process changed a bit from C# 3.0 to C# 4.0.

- A signature is applicable if all its parameters are optional, or have exactly one corresponding argument (by name or position) that is convertible to the parameter type.
- "Betterness" rules are only applied for arguments that are explicitly given — omitted arguments are ignored for betterness purposes.
- If two signatures are equally good (by terms of "betterness"), one that does not omit optional parameters is preferred.

Here is a short sample to demonstrate the resolution steps. MyClass defines four overloads for MyMethod:

```csharp
public class MyClass {
    MyMethod(string s, int i = 1) {}
    MyMethod(object o) {}
    MyMethod(int i, string s = "") {}
    MyMethod(int i) {}
}
```

The question is which method should be called in the following code?

```csharp
var myClass = new MyClass();
myClass.MyMethod(10);
```

Now, you can see how the rules work. MyMethod(string, int) is not applicable, because 10 matches int. MyMethod(int, string) is applicable because second parameter is optional. Because there are three candidates, "betterness" rules are applied. MyMethod(int, string) and MyMethod(int) are both better than MyMethod(object) because the conversion from 10 to int is better than object.

So, only two candidates remain. Finally MyMethod(int) is better than MyMethod(int, string) because optional arguments are omitted, and therefore, MyMethod(int) is called.

# COM-SPECIFIC INTEROPERABILITY FEATURES

The dynamic lookup in C# 4.0 solves a lot of issues related to interoperability, which is especially true for COM objects like the Office Automation API or the Visual Studio Extension API (DTE). Optional and named parameters also add value to reduce the syntax noise of using COM API from C#.

The C# language design team felt they should polish the COM interoperability story in version 4.0, and they added a few pieces of the puzzle to complete the picture. In this section, you can get a closer look at these mechanisms, with really, powerful features.

# Dynamic Import

A majority of methods accept and return variant types. The Primary Interoperability Assemblies (PIAs) represent arguments and return values of the System.Object type. In a majority of cases, you already know the static type of a returned object from the call context, but explicitly you must perform a cast on the returned value. For example, when you access cells in Excel, you write the following:

```csharp
var excel = new Excel.Application();
Excel.Range topLeftCell = (Excel.Range)excel.Cells[1,1];
```

Even if Cells[] returns an instance of Excel.Range, you must explicitly cast it to the expected type.

To rid of this syntax noise, you now choose to import these COM APIs in such a way that variants are represented using the type dynamic. Many PIAs shipped with Visual Studio are created with dynamic—including Microsoft PIAs.

This means you can access members of a returned object, or assign it to a strongly typed local variable, without having to cast. Instead of casting an Excel Cells value to the type Excel.Range, you can now say the following:

```csharp
var excel = new Excel.Application();
var oldValue = excel.Cells[1,1];
excel.Cells[1,1].Value = "Set To New Value";
```
