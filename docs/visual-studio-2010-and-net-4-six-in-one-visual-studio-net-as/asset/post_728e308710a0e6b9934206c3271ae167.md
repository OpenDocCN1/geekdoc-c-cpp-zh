
Looking for the Imports statements in the previous snippets, you will find that namespaces used with types declared in Visual Studio and .NET framework assemblies (such as Env.System.Windows.Forms). Modules, classes, and references for the assemblies used are stored in a unit called a macro project that is physically a binary file with .vsmac extension.

Visual Studio uses macros as the smallest unit of deployment. Deploying all information in a single .vsmac file is easy. If you want to extract the code from macro projects, you can export modules and classes into standard .vb files.

At the highest level, Visual Studio works with zero, one, or more macro projects into a logical container called a macro system. It resembles a Visual Studio solution, but it is different. When the IDE, the macro system's projects are loaded independently of what kind of solution and projects are opened. The projects are not tied to any of your concrete projects. You can handle them if they belong to the IDE itself.

Projects of the macro system are totally independent of each other. You cannot make references among them unless you cross-reference projects in a Visual Studio solution.

## Using the Macro Explorer

If you want to look at the macro system, the easiest tool is the Macro Explorer which can be accessed through the Tools -> Macro -> Explorer function. As shown in Figure 6-6, this window displays a hierarchy of projects, modules, and classes, and, of course, macros in the system.

As you can see, the hierarchy contains the following two projects. (Both of them are installed with Visual Studio 2010.)

- MyMacros is displayed in bold to show that this project is the recording project. When you record a macro, it will be put into the recording project.
- Samples is a great source for getting started with macro programming. It contains more than 50 working macros with basic explanations and comments. Examining the samples can help a lot understanding the philosophy of Visual Studio's automation method and solving complex tasks.

## Using the Project Explorer and Class View

The Project Explorer contains a hierarchical list of projects and modules just like Macro Explorer. However, here you cannot see macros in the list. The Project Explorer contains some project-specific information not visible in Macro Explorer, such as the list of assemblies and a module called EnvironmentEvents. Figure 6-10 shows the Project Explorer displaying the assemblies in Samples.

You might find disturbing to have two UIs for displaying the structure. The logic behind this approach is that you only need Macro Explorer to have a great overview about macros and, if you need any of them, you can immediately start from this tool. The Project Explorer is built up very similarly to Solution Explorer. The view it provides is a development-time view where your main focus is to edit, try, and debug.

From the user experience point of view, these two are synchronized. Just as you have a Class View for your source code in Solution Explorer, you also have a Class View tool in Macros IDE to see your code's structure. Figure 6-11 shows the MyMacros project with the methods of the Greetings class.

You can use the Class View for browsing your own modules, classes, and members, as well as objects in the referenced assemblies. You can see a few objects in Figure 6-11 that have names starting with an underscore (for example, _ApplicationObject and _Startup, _Utility). These are hidden modules that were created along the macro project and are responsible for the run-time integration of macros with the Visual Studio IDE.
