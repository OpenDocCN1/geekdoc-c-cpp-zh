The term “customization” here means that you can use some built-in UI to change the behavior of the application. “Configuration” means editing or adding some application-specific information. A very thin line separates these two concepts, the term “customization” will be used here to cover both of them.

Many third-party tools (for example, documentation generators, refactoring tools, and so on) creating new functionality by customizing the tool, and Visual Studio also provides a few ways. One of them is the capability to use snippets to insert frequently used patterns as you are editing the source.

Just because no traditional coding is required to customize Visual Studio, you should not underestimate the power of customization and configuration! Let's take a look at two short samples.

## Code Snippets Sample

You are not constrained to using only the snippets that ship with Visual Studio. You are also able (and encouraged) to develop your own. By creating a new snippet, you can add something new to the IDE — for example, a function that was not available before you developed.

For example, you can create a C# snippet to add a file header when you write a file with a .snippet extension, and import it into the Code Snippet Manager:

```xml
<?xml version="1.0" encoding="utf-8"?>
<CodeSnippets xmlns="http://schemas.microsoft.com/VisualStudio/2005/CodeSnippet">
<CodeSnippet Format="1.0">
<Header>
<Title>File Header Comment</Title>
<Author>Ivan Novak (http://divedeeper.dotoneeters.net)</Author>
<Description>This snippet provides a file header comment</Description>
<Keywords>
<Keyword>File</Keyword>
<Keyword>Header</Keyword>
<Keyword>Comment</Keyword>
</Keywords>
<Shortcut>headacom</Shortcut>
</Header>
<Snippet>
<Code Language="C#">
<![CDATA[
//====================================================================
// $FileName$
//
// $Description$
//
// Created by: NI
//====================================================================
]]>
</Code>
```

```xml
<Declarations>
  <Literal>
    <ID>FileName</ID>
    <Tooltip>Specify the name of the file</Tooltip>
    <Default>!FileName!</Default>
  </Literal>
  <Literal>
    <ID>Description</ID>
    <Tooltip>Provide a description of the file</Tooltip>
    <Default>!FileName!</Default>
  </Literal>
</Declarations>
</Snippet>
<CodeSnippets>
</CodeSnippets>
```

When you import the file, the corresponding declaration gets a part of the available C# snippets. Figure 6-2 shows the dialog you see after importing the file.

## GhostDoc Sample

Many third-party tools also have been designed and implemented with extensibility in mind. One favorite is GhostDoc, which helps you to intelligently generate XML comments for code elements like methods and properties. As shown in Figure 6-3, GhostDoc has a set of rules describing how to generate the comments for a certain source code object.

![](img/b5597c749e848b27b0d305153ae16106_248_0.png)

**FIGURE 6-3:** GhostDoc rules configuration

When you select "Default documentation" in the "Constructors" category, and then click the Edit button, the dialog shown in Figure 6-4 appears, allowing you to edit the rules related to constructor methods. Figure 6-4 shows how the <summary> comment rule is set up for an instance constructor.

![](img/b5597c749e848b27b0d305153ae16106_249_0.png)

FIGURE 6-4: Instance Constructor Rules

Let’s say that you have an uncommented constructor like this:

```csharp
public SimplePackagePackage()
{
    }
```

GhostDoc generates the following comment according to the rule:

```csharp
/// <summary>
/// Initializes a new instance of the <see ref="SimplePackagePackage"/> class.
/// </summary>
public SimplePackagePackage()
{}
```

The almost 20-year-old automation mechanism uses a simple (and great) idea. An object model is provided above the internal functions of product, enabling the user to exploit them.
