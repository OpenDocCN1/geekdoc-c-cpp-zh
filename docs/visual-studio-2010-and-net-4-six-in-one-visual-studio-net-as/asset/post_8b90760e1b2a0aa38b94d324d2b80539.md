With the proxy class, call the web service when the page is fully loaded. Before that, take a moment to reconsider what is happening under the hood.

The only way to initiate an HTTP request from the client is to use the XMLHttpRequest object in the browser, and that the Sys.Net.WebService proxy class uses are asynchronous. However, all service methods accept a success and a failure callback method reference. This means that, although the GetCountriesByName method does not have any parameter on the server, when you call it on the client, you must pass at least a success callback to process the results:

```
function pageLoad()
{
  CountryService.GetCountriesByName(onSuccess)
}

function onSuccess(results)
{
  $find('countryList').set_data(results);
}
```

The dataProvider of the DataView class can point to a JSON Web Service URI, or to an instance of a Sys.Net.WebService object, or any class that implements the Sys.DataProvider interface. In the fetchoperation property, you define the name of the method that you can call. By setting the autofetch property to true, you can ensure that you do not have to update the DataView manually. It will retrieve the data immediately from the source when it loads, or when the dataProvider or the fetchoperation is changed.

If you want to call a method that expects parameters, you must set the fetchParameters property as well:

  </li>
</</ul>
</ul>

# Updating Data on the Server

If you want to implement a read-write scenario, you must delegate all data management to the new `Sys.DataContext` class. This class encapsulates everything required to retrieve the data from the server, changes on the client, and then modify the data back to the server. The `DataContext` implements an `IDataProvider` interface, which means you can use a `DataContext` instance directly as a source for your DataView:

```
<ul
class="sys-template"
sys:attach="dv"
dv:autofetch="true"
dv:dataProvider={executionContext}
dv:fetchoperation="GetCountriesByName">
<li>
  {{ Name }} {{ Capital }}
</li>
</</ul>
```

As you can see, the `dataProvider` property does not point to the web service directly any more. Instead, it is wrapped by a `DataContext` instance that is created when the page loads. (You will see that in a minute.)

You may notice that, although the service URI is encapsulated by the DataContext, the name of the web method is still defined on the ViewData. If you find this bit confusing, you are not alone, and this will likely change in the next previews or the RTM release.

The only thing is the DataContext instance. The DataContext resides in MicrosoftAjax.js file, and because it resides on a bunch of other files, it is best to use the new Script Loader to load the required files on the page:

```

<script type="javascript">

  Sys.require([Sys.components.DataView, Sys.components.dbContext]);
  Sys.onReady(function() {
    dataContext = Sys.create.DataContext({
      serviceURI: "../Services/CountryService.asmx"

  });
</script>
```
