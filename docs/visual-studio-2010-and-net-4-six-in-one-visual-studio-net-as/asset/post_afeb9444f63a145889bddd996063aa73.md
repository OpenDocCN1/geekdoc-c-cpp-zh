## Extending the Model with Validation Metadata

The Book class is automatically generated by the ADO.NET Entity model class. You could theoretically decorate the model classes with the attributes in Table 18-1, but when you change the model, these attributes will be lost.

Automatic code generation is a frequently used technique in software development, and many Visual Studio items also use this technique. MVC is prepared for this, and allows you to assign metadata to model classes through an associated metadata provider class.

Add a new class to the Models folder and name it BookMetadata.cs. Listing 18-17 shows the code you should put into this new file.

```c
using System;
using System.ComponentModel.DataAnnotations;

namespace AcmeLibrary.Models
{
    [MetadataType(typeof(BookMetadata))]
    public partial class Book
    {
        // --- Augmentation of the Book class in the model
    }

    public partial class BookMetadata
    {
        public int Id { get; set; }

        [Required(ErrorMessage = "Please provide the author(s) name")]
        public string Author { get; set; }

        [Required(ErrorMessage = "Please provide a title")]
        public string Title { get; set; }

        [RegularExpression("^[0-9]{13}$$",
            ErrorMessage = "ISBN must be exactly 13 digits")]
        public string ISBN { get; set; }

        public DateTime Published { get; set; }

        public string Publisher { get; set; }
    }
}
```

The partial Book class in Listing 18-17 is the same class as generated by the ADO.NET entity model file (AcmeLibraryModel.edmx). To match the partial definition, the code fragment in listing decorates this class with a MetadataType attribute telling that BookMetadata contains data annotation attributes for Book. BookMetadata defines placeholder properties having the same name and type as the ones in Book. As a result of this definition, decorating the BookMetadata properties are considered by the MVC framework as if those attributes were added directly to Book.

## Preparing the Controller for Validation

The current implementations of controller actions execute the related database transactions and let the database operation raise an exception. This approach is not correct for the following reasons:

- There is no using clause on database operations if the properties are invalid. This can be done before talking to the database.
- It might be that the database transactions are alert, because the action does not hurt the consistency of data. However, the current state of the model — the set of its properties may hurt business rules.

You can check the validity of the model before executing the action valid data. The key is the ModelState property of controller that is a ModelDictionary instance. Using the IsValid property of ModelState, you can avoid starting an operation with invalid data. For example, you can use the Create action to avoid creating a new book with wrong data:

```csharp
[HttpPost]
public ActionResult Create(Book newbook)
{
    if (ModelState.IsValid)
    {
        try
        {
            using (var context = new AcmeLibraryDataEntities())
            {
                context.AddToBooks(newbook);
                context.SaveChanges();
            }
            return RedirectToAction("Index");
        }
        catch (Exception)
        {
            return View(newbook);
        }
    }
    return View(newbook);
}
```

The ModelState property contains a detailed state describing model properties and related validation errors based on the data annotations and implicit metadata belonging to the model class. If your controller has more business rules to check, you can do further validation checks.

For example, the publication date cannot be ahead of the current calendar date by more than 180 days, you can add the following check to the Create method:

```csharp
[HttpPost]
public ActionResult Create(Book newBook)
{
    if (newBook.Published != null &&
        (newBook.Published.Value - DateTime.Now).TotalDays > 180)
    {
        ModelState.AddModelError("Published",
            "A future publication date cannot be more than 180 days");
    }
    if (ModelState.IsValid)
    {
        try
        {
            using (var context = new AcmeLibraryDataEntities())
            {
                context.AddToBooks(newBook);
                context.SaveChanges();
            }
            return RedirectToAction("Index");
        }
        catch (Exception)
        {
            return View(newBook);
        }
    }
    return View(newBook);
}
```

As you see, the validation check precedes checking for.IsValid.

## Managing Business Rules

The check for the future publication date you have added recently is a rule that should also be checked for Edit action. One option is to copy and paste the validation code into the Edit method. However, when you have many rules to check, you can become confused and forget about checking each rule at the Create and Edit actions. The best solution is validation to the model level.

There are several ways to solve this, depending on the architecture pattern — style — you intend to use in your application. There is one solution that adds a validation method to the Book entity class:

Add a new file BookValidation.cs to the Models folder. Extend the Book entity class with a Validate method, as shown in Listing 18-18.

# LISTING 18-18: BookValidation.cs

```csharp
using System;
using System.Web.Mvc;

namespace AcmeLibrary.Models
{
    public partial class Book
    {
        public void Validate(ModelState modelState)
        {
            if (Published != null &&
                (Published.Value - DateTime.Now).TotalDays > 180)
            {
                modelState.AddAddModelError("Published",
                    "A future publication date cannot be ahead more than 180 days");
            }
        }
    }
}
```
