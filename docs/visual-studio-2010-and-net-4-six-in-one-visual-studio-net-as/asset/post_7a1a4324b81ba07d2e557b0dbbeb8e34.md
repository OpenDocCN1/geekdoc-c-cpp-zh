To interoperate with a certain COM interface, you must use a .NET type wrapping the functionality of that interface. Building these wrappers manually is laborious, especially when you have hundreds of COM interfaces (for example, in the case of using the Microsoft Office automation model). PIAs are .NET assemblies generated from COM interfaces to facilitate strongly typed interoperability. For large objects models, the related PIAs are as large as well, these assemblies can easily bloat the size of your application. They can cause version issues when they are distributed independently of your application.

The No-PIA feature allows you to continue using PIAs at design time without having them around at run-time. The C compiler will append the small part of the PIA that a program actually uses to its assembly. At run-time, the PIA does not have to be loaded.

## Equivalence Insert of Equality

Accomplishing the aforementioned task would not be possible in any CLR prior to CLR 4.0. But it's available in CLR 4.0, because of the type equivalence feature. Behind the scenes, you can run the following line of code:

```csharp
TableHelper.InsertTable(word, 3, 2);
```

This results in the following compiling:

```csharp
TableHelper.InsertTable((Word.Application)word, 3, 2);
```

In this code, the WordHelper uses the type. The type equivalence feature means that the CLR is able to carry out the specified cast. ## Equivalence in CLR

As discussed, CLR 4.0 supports embedding type information into managed assemblies, instead of obtaining that type information from interoperability assemblies. The compiler generates concise code, and the embedded type information includes only the types and members that are actually used. Because of this behavior, two assemblies might have different views of the same COM type. Each assembly has a different System.Type object to represent its view of that type.

From the CLR's perspective, type equivalence means a COM object that is passed from one assembly to another can be cast to the appropriate managed type in the receiving assembly.

The CLR supports equivalence only for COM types, and as a limitation, for interfaces, structures, enumerations, and delegates. Classes are not subject to this behavior. Two COM types are taken into account as equivalent ones, where the following criteria are met:

- The types are both interfaces or structures or enumerations or delegates.
- Both types are COM import types.
- If they are interfaces, they should be decorated with ComImportAttribute and GuidAttribute.
- The assemblies in which they are defined (that are generally two separate ones) have either the ImportedFromTypeLibAttribute or the PrimaryInteropAssembly.
- The GuidAttribute values of these types are equal.

During the build process, the compiler checks if a type is used in a context where type equivalence is assumed. In this case, it checks if the criteria are met. In cases when there are issues, the compiler raises appropriate error messages.

The compiler decodes the type declarations with the TypeIdentifierAttribute and the CompilerGeneratedAttribute attributes.
