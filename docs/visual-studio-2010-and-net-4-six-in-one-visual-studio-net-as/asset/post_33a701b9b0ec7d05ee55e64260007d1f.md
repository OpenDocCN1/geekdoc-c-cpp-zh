## Authorization

Before executing any action, the controller checks attributes implementing the IAuthorizationFilter interface:

```
public interface IAuthorizationFilter
{
    void OnAuthorization(AuthorizationContext filterContext);
}
```

If the user executes an OnAuthorization and signals that authorization fails, an HttpUnauthorizedResult is set for the current context, and the further execution is interrupted. There are a few attributes implementing IAuthorizationFilter. Let's take a look at few of them. Of course, you can create your own AuthorizationFilter attributes.

## AuthorizationAttribute

By default, any user can execute an action. However, you can restrict the scope of authorized users by decorating an action with the AuthorizeAttribute:

```
[Authorize(Users="Joe, Zana", Roles="Admins, Managers")]
{
    public ActionResult CheckAccount()
}
```

This example shows how easy it is to use this attribute. You can define the users allowed to execute an action by their user name or the names of roles they are in. CheckAccount can be executed by all users that are named Joe or Zana, or all users having at least one of the Admins and Managers roles.

AuthorizationAttribute allows authorization on the logged-in user's name or role membership. This attribute can be applied at class or method level; multiple definitions are allowed at one place.

## ChildOnlyAttribute

You can create an action whose purpose is to be invoked from other action as a child action. In this case, it doesn't make sense for anyone to invoke an action directly through an HTTP request. The ChildOnlyAttribute blocks an execution if it is not a child action of another action. This means that, with a URL, this is not callable, but it's callable during the rendering of a view through the HtmlHelper's class or RenderAction methods.

```
[ChildActionOnly]
public ActionResult RenderSiteStatistics()
{}
```

If somebody navigates to a URL that maps to RenderSiteStatistics, the filter will block the request by throwing an InvalidOperationException, saying, "The action 'RenderSiteStatistics' is accessible only by a child request."

## RequireHttpsAttribute

This attribute checks the current HTTP IsSecureConnection property, and only allows the action to execute when the request was done through a secure connection (such as the HTTPS protocol).

```
[RequireHttpsAttribute]
public ActionResult LoginUser(string username, string clearTextPassword)
{}
```

## ValidateAntiForgeryTokenAttribute

This attribute checks the presence of a specially formatted cookie and hidden form field's value. if all the required data is valid, the action can be executed.

This attribute tries to prevent an action from getting executed during a cross-site scripting (XSS) attack. ValidateAntiForgeryTokenAttribute should be only applied to an action that is allowed to execute during an HTTP POST request. As a prerequisite, a call must be made to the HtmlHelper class's AntiForgery method, which puts the required data into the action's result.

```
[HttpPost]
[ValidateAntiForgeryToken]
public ActionResult XSSProtectedAction ()
{}
```

The related view should look like this:

```
<% using (Html.BeginForm()) { %>
<%= Html.AntiForgeryToken() %>
<!-- Form field definitions -->
<% } %>
```

This view will be rendered something like the following HTML fragment:

```
<form action="/View/Edit" method="post">
<input name="__RequestVerificationToken" type="hidden" value="Ac/BHD5D4K/as67G..." />
<!-- Form field definitions -->
</form>
```

## ValidateInputAttribute

If you want to disable validation for a specific action method or across a specific controller, you can use the ValidateInputAttribute:

```
[ValidateInput(EnableValidation=false)]
public ActionResult ThisMethodCanContainDangerousRequestData()
{}
```

Unfortunately, to use ValidateInputAttribute with .NET 4, you must also make a further configuration change. To successfully disable request validation, you must add the following to your web.config file:

```
<configuration>
  <system.web>
    <httpRuntime ValidationMode="2.0"/>
  </system.web>
</configuration>
```

This is because the request processing pipeline was changed in .NET 4.

## Action and Role Filtering

When the user is authorized to execute an action (all attributes IAuthorizationFilter allowed to go with the execution), the real action is wrapped by objects implementing IActionFilter:

```
public interface IActionFilter{
  void OnActionExecuting(ActionExecutingContext filterContext);
  void OnActionExecuted(ActionExecutedContext filterContext);
}
```

The methods implementing these two interface methods are attributes decorating the action method. The MVC framework provides the abstract ActionFilterAttribute class to derive your filter attributes.

First, all OnActionExecuting methods are called. This method receives the execution context as its argument. It can return an ActionResult or a null if the filter does not want to alter the result. A Cancel property is defined in the ActionExecutingContext class that the method can flag the cancellation of the action to prevent it from being executed.

After the execution of the action, the OnActionExecuted is invoked — in the reverse order as ActionExecuting methods were called. At this point of execution, there is some kind of ActionResult available.

Before returning the result to the user, the next step of the processing pipeline is to use the IResultFilter interface:

```
public interface IResultFilter{
  void OnResultExecuting(ResultExecutingContext filterContext);
  void OnResultExecuted(ResultExecutedContext filterContext);
}
```

You can use the ActionFilterAttribute class to derive your result filtering attributes, just as in the case of action filtering. The execution logic of OnResultExecuting and OnResultExecuted methods is exactly the same as the logic for OnActionExecuting and OnActionExecuted. The Cancel property or the ActionResultContext passed to these methods can be set to true to prevent the other filters in the row from being invoked.

Both the OnActionExecuted and OnResultExecuted methods can receive the exception thrown by the action, and they can process them.

## Exception Filtering

If an exception was thrown during OnActionExecuted and OnResultExecuted methods, it's available for examination in the OnException. If an exception can be handled, the ExceptionHandled property of the executing context can be set to true. If it does not happen, the exception will be propagated up in the exception chain.

If there is an unhandled exception raised during execution, the IExceptionFilter interface:

```
public interface IExceptionFilter
{
    void OnException(ExceptionContext filterContext);
}
```

The framework invokes the OnException method of all attributes implementing IExceptionFilter. The framework provides you with an error page that displays the exception. Of course, you may create your own exception filters if you need them.

## ActionResult

You have already met the ActionResult class, which is the one generally retrieved by action methods. There is a plethora of classes representing the results (outcomes). All these classes inherit the ActionResult class having the following simple definition:

```
public abstract class ActionResult
{
    public abstract void ExecuteResult(ControllerContext context);
}
```

MVC 2 ships with about a dozen classes deriving from ActionResult, as shown in Table 18-5.

### TABLE 18-5: ActionResult Derived Classes

| TYPE | DESCRIPTION |
| --- | --- |
| EmptyResult | This class represents a result instructing the controller to take no action. Returning an EmptyResult.Instance from your action is like returning a null from a method. In this case, nothing will be written into the response. You may have several reasons to use this type. For example, it can be a result of a security-related action where you don't want to expose anything to the end user. |
| UnauthorizedResult | This class represents the result of an unauthorized request. If you return a new instance of this class, it will end up in an HTTP 401 message (which is the standard code for unauthorized access). Usually, the result is returned from a class implementing the IAuthorizationFilter. |
| ContentResult | This class represents a user-defined content type that is the result of an action method. You can have arbitrary content and set it through the Content, ContentType, and Encoding properties. |
| JavaScriptResult | The name of the class speaks itself, as it retrieves JavaScript content. You can use Script property to set the script to return. |
| JsonResult | This class is suitable to serialize a .NET class for client-side consumption (for example, as a result of an Ajax call). With the properties this class provides, you can be in total control of how the data should be serialized to the client. This class has a property JsonRequestBehavior that, by default, denies the execution of an action for the HTTP GET verb. If you want to allow an action to return JavaScript Object Notation content for a GET request, you should set this property to JsonRequestBehavior.AllowGet. |
| RedirectResult | This can be used to redirect the user to another URL at the end of the action. One of the examples is when you have finished editing a book selection and you're redirecting the user to the Book list view. |
| RedirectToRouteResult | This result is similar to RedirectResult, but instead of a hard-coded URL, you can refer to one of the registered routes within the application. |
