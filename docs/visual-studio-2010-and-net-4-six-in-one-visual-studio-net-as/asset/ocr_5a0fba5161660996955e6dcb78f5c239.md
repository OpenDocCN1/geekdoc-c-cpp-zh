If you do not have this kind of a database bottleneck, there is one thing that cannot be solved without changing architecture. Although you may have a large number of processors, the response time of one user request cannot be decreased below a certain threshold. If the algorithm the user request runs sequentially (it can run only on a single thread), having a hundred CPUs can cannot reduce the response time below that threshold.

The advantages of (many-core) CPUs cannot be utilized in the case of desktop applications, where the architectural constraints allow only sequential execution. Of course, having multiple cores means multiple applications can run in parallel, but that won't help to decrease the running time of slow applications. These kinds of applications cannot benefit from putting two, four, or even more cores into the desktop machine.

So, it's not worth to use multiple cores for applications designed and implemented with "sequential-style." The multi-core opens new horizons—but requires software architected in order to achieve the potential benefits.

From this aspect, a majority of today's software is the weakest link.

# Issues with Multi-Threading

If you want to develop an application supporting concurrent execution of certain parts of algorithms, you cannot avoid directly using threads. Managing multiple threads is definitely challenging. You're faced with several tasks to solve correctly in order to build a robust and bug-free application. Multiple threads introduce situations where you to handle variable and resource synchronization, flow control that utilizes data structures designed with sequential usage in mind, race-conditions, deadlocks, lock-offs, and many more.

The literature discussing concurrent programming is vast, handles all aspects, and even suggests design patterns for pattern contexts—but does not simplify multi-threading. Even if you find a simple principle or pattern to transform a task into a parallel one, you must still cope with a few more difficulties, including the following:

+   The aspect of parallelism will spread through the task. You must find the principle to split the task into smaller independent parallelizable tasks. You must wrap these parts into threads, and take care of managing common resources, synchronizing their access. The flow control among tasks should be managed carefully—for example, if the end, tasks should wait while each of them finishes its work.

+   In the final code that enables your algorithm to benefit from parallelism, the real business code (that is, code implementing the business functionality) will be mixed up with the code originating from the parallel aspect. The latter can significantly boost the size of business code by a number of code lines. Any further change in the code requires extra development resources, because the entire code is longer. You have a greater likelihood to be lost in the code, or a touch of the infrastructure code, instead of the business code.

+   Testing this code is more challenging and resource-waste. To keep the level of code coverage at a certain point, you must write more unit test cases. The correctness of parallelism infrastructure (for example, avoiding race conditions) also requires additional test cases.
