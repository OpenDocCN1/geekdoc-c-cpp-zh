Instead, for COM methods, the C# 4.0 compiler will allow you to pass arguments by value to a method, and automatically generate temporary variables to hold the passed-in values. The subsequently discards them when the call returns. Listing 24-2 carries out the same task more intuitively:

```cs
var word = new Word.Application();
word.Visible = true;
word.Documents.Add();
```

In this way, the caller sees value semantics and not experience any side effects, but the called method still gets a reference.

## Indexed Properties

COM has a concept called parameterized properties that does not exist in C#. Until now, you had to use get_X() and set_X() methods to access the values of an indexed property x. For example, you could set the top-left cell of an Excel sheet as follows:

```cs
var excel = new Excel.Application();
excel.get_Range("A1").SetValue(Type.Missing, "Name");
```

Earlier, without indexed properties support, you would have to use the ugly Value2 property, because otherwise would have to call get_Value() or set_Value():

```cs
var excel = new Excel.Application();
excel.get_Range("A1").Value2 = "Name";
```

Now, in C# 4.0, you can use parameterized properties declared in COM using the indexer syntax. For example, instead of get_(), you can now write x[]. With this syntax, you can now set the cell value in the most intuitive way, just as scripts and dynamic languages do:

```cs
var excel = new Excel.Application();
excel.Range["A1"].Value = "Name";
```

This is just syntax. The compiler still emits calls to the get_ and set_ acceptors of the day. This syntax does not mean that you can create indexed properties in C#, because this feature still does not exist in the language. The designers encourage you to use indexers and do not plan to introduce indexed properties.

## Compiling Without PIAs

To interoperate with a certain COM interface, you must use a .NET type wrapping the functionality of that COM interface. Building these wrappers manually is very laborious, especially when you have hundreds of COM interfaces — for example, in the case of the Microsoft Office automation model.

PIAs are .NET assemblies generated from COM interfaces to facilitate strongly typed interoperability. For large objects, the related PIAs are also large. At runtime, these large assemblies can easily bloat your program. They can also cause versioning issues when they are distributed independently of your application.

For example, the Word 2007 interoperability assembly has a size about 800 KB, while the Excel binary (which you saw earlier in this chapter) takes only 18 KB. It is normal to deploy 2 MB of overhead (PIAs) for an application with a size of 18 KB.

The no-PIA feature allows you to continue using PIAs at design time without having them around runtime. Instead, the C# compiler will generate a small part of the program that acts directly to the assembly. At runtime, the PIA does not have to be loaded.

You can turn on or off this feature for each interoperability assembly. Select the assembly in Solution Explorer and set the Embed Interop Properties to True (to turn on) or False (to turn off) no-PIA. ## Type Substitution

Without a check, you would follow the following declarations are legal, although the second one is invalid:

```cs
List<string> stringList = new List<string>();
IList<object> objectList = stringList; // --- No implicit cast!
```

The main reason is that the following kinds or relationships between types are often confused:

- *Inheritance — A type descends from another type.*
- *Realization — A type implements an interface.*
- *Generic parameter substitution — a generic type's type parameters substitute with (closed) types.*

Although List<string> realizes IList<string> (that is, a closed form of IList<T>) just as List<object> realizes IList<object>(that is, a closed form of IList<T>), it does not mean that IList<string> is assignable to an IList<object>. Figure 24-5 shows a relationship diagram to help explain why this is so.

![](img/b5597c749e848b27b0d305153ae16106_1129_0.png)

FIGURE 24-5: List<T> Relationship Diagram

Wait, the most common ancestor of these types is System.Object. The solid lines represent inheritance, dashed lines mark realization, and double lines stand for parameter substitution. While traversing through inheritance and realization in linear inheritance (like son, father, and grandfather in a family), parameter substitution means collateral relation (such as a cousin in a family).

IList<string> and IList<object> are in collateral relation. At first sight, developers take it into account as linear inheritance because they share the same generic as a kind of ancestor. There is a false expectation that IList<string> is assignable with a variable of IList<object>.

It is not an unnecessarily strict check of the compiler; the discussed assignment can even lead to hurting type safety. Look at the following code:

```cs
IList<string> strings = new List<string> { "zero", "one", "two", "three", "four" };
IList<object> objects = strings;
objects[3] = 3;
string three = string[3];
```

If the objects = strings assignment were allowed, the objects[3] = 3 assignment, an int would be inserted into a list of strings and subsequently extracted as a string. This would be a type-safety violation, so that the assignment is invalid and results in compilation error.

Note that the whole situation is about how you can substitute instances of types with instances of other types. It is natural for OOP developers to think that substitutions are allowed by linear inheritance, but there are other cases where theoretically collateral (and other types of) substitutions can be done.

The following code mirrors such a situation:

```cs
IList<string> strings = new List<string>();
IEnumerable<object> objects = strings;
```
