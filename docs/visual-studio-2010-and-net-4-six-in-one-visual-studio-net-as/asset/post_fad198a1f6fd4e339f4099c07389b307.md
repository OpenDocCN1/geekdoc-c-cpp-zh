The classifier's constructor initializes the classification types and the dictionary of file associations. The _fileAssociations stores file extensions with their content type. This container is initialized with a LINQ expression that looks up the registry and collects the interesting file extensions. Here you also store the maximum length of registered extensions, because it plays an important role in the algorithm recognizing the extensions in the text.

The lion's share of work is in the GetClassificationSpans method. First, it gets the text of the snapshot span, and then looks up all extensions.

There are many ways to do that. The algorithm used here seems a bit complicated; you may create a simpler solution. However, there are two important things to keep in mind when programming the GetClassificationSpan method:

- The spans returned be ordered by their starting position and non-overlapping, in order to be displayed correctly in the editor.
- The algorithm must be efficient, because keystroke triggers running it.

You may think efficiency is not critical in this case, but that may not be the case. For one sample run, the test machine had 690 file extensions, and the first one was not quick enough. When the tester kept a key pressed, the editor started to clog up.

A better algorithm would start searching for the dot if it does not find the dot in the span, the work is done. If it is found, the algorithm extracts the maximum number of available characters the dot — keeping in mind the length of file extension. It then extracts the extra characters in the _fileAssociations dictionary. If that is not found, a shorter string is searched, unless the file extension to search becomes empty. This is important, because, if you type something like .file.csfg and .cs are valid extensions, and in this case, you would have to highlight the longer one, namely .cs.

After finding an extension, a new element is added to the classification list with the appropriate type, depending on the content type of the _fileAssociations dictionary, and the search goes on as long as there is new extension to find.

# SUMMARY

Visual Studio is not only a tool but a real development platform you can customize and extend to turn it into your ultimate tool. From its first version, Visual Studio was designed with extensibility in mind, and you have many options to change or enhance built-in functions, as well as creating new ones.

Although developers generally do not take into account customization and configuration as methods of extending applications, this is a real alternative. Many third-party tools (such refactoring tools, document generators, and so on) provide GUIs, configuration files to customize them in order to create functionality. Code snippet management is a good example showing that Visual Studio itself supports this option.

Macros provide the easiest way to extend Visual Studio. You can automate repetitive tasks in a few minutes by the macro recording capabilities of Visual Studio. Macros access the Visual Studio automation object model, and easily combine the IDE commands and objects to establish the desired behavior. Although macros are great for task automation, they are not the right tools to create totally new functionality. When using macros, you should be aware of the fact that anyone can see the source code of your macro. Macros do not extend the UI or the services of Visual Studio.

Add-ins are much more powerful for developing Visual Studio extensions, because, in addition to accessing the Visual Studio automation objects, you can add new user interface to the IDE (such as window, menu and toolbar, and so on). Add-in is actually a COM implementing two interfaces. You can integrate into the IDE so that you do not know how they are implemented as add-ins when you use them. The functions you add with an add-in as if they were part of the IDE. An add-in is a compiled (managed or native) binary, you can use the same intellectual property guarding techniques for any other native or native binaries.

While extensibility through macros and add-ins are built into Visual Studio out-of-the-box, by installing the VS SDK, you can use other options.

The most powerful way of developing Visual Studio extensions is to integrate Visual Studio packages into the IDE. These packages are not limited to the automation model, or only to a few services, but can access the whole infrastructure of Visual Studio just like the packages created by the development team at Microsoft. Your VS SDK provides the Managed Package Framework to let you create VSPackages with managed code either C# or VB. The VSPackage helps you create skeleton code for your packages in a few minutes.
