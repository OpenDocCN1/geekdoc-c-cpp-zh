## Networking

Because Silverlight is a client-side technology that (mostly) lives in the browser, it must connect to the server (or the cloud) to work. Silverlight offers a range of communication tools from low-level sockets, to HTTP connections, to WCF and WCF RIA Services. These networking stacks work similar to what .NET developers are used to from the "big” framework. However, there are two key differences between the lightweight, sandboxed, and browser-based nature of Silverlight.

The first difference is security. By default, Silverlight (just like Flash or JavaScript) only allows connections back to the server it downloaded from. The reason for this is to mitigate threat of denial of service (DoS) attacks, domain name server (DNS) attacks, reverse-tunnel attacks, cross-site attacks, and so on. If a server wants to allow a Silverlight (or Flash) application to use its resources, create a policy file that controls access. Silverlight also takes Flash's crossdomain.xml files into account, therefore making sites available to Silverlight that have only been allowed to be accessed via the Flash crossdomain.xml file. Policy files can also be used by socket connections, but in this case, the policy files will be downloaded from a different socket port.

The second important difference between standard. .NET and Silverlight network access is that every server communication is asynchronous. This might seem a bit restrictive, but synchronous server communication would block the UI thread most of the time, stopping animations or freeing the browser — so a background thread and callback mechanism would have to be created for most cases anyway.

## Communicating via HTTP

Apart from the WebClient class, there are two completely separate stacks for HTTP communication: BrowserStack and HttpClientStack.

As the name implies, BrowserStack utilizes the hosting browser to make HTTP calls to the web. This means that browser restrictions (such as maximum number of connections to a given server, and so on) are in effect for the browser stack. Also, the browser stack only GET and POST for the HTTP method — PUT or any other verb result in a NotSupportedException. To create a Request object that uses the browser stack, use the WebRequestCreator.BrowserHttp class:

```c
WebRequest rq = BrowserHttp.Create(new Uri
("http://www.response.hu");
```

HttpClientStack (introduced in Silverlight 3) allows customizing response status codes, request methods, authentication, bodies and headers, and sending HTTP requests requests as SOAP and REST services. ClientHttpStack also allows manipulation of cookies. Creating a HttpRequest for the client stack is very similar to how the HttpRequest for the browser stack is

```c
WebRequest rq = WebRequest.ClientHttpStack.Create(new Uri
("http://www.response.hu"));
```

## WCF RIA Services

WCF RIA Services (formerly called .NET RIA Services) builds upon of WCF and aims to make data transfer between a .NET server and a Silverlight client as transparent as possible. W RIA Services addresses CRUD (Create-Read-Update-Delete) schemas while retaining type safety through the layers. Middle-tier entities have corresponding client-side code generated, along with domain contexts that allow access to data through Language Integrated Query (LINQ). Service methods can also be invoked. The tier can connect to any database provider, including Entity Framework, LINQ-to-SQL, and POCO (Plain Old CLR Objects). RIA Services can connect the client-side LINQ query to the server, and translate to T-SQL for the database layer.

> Essentially, it is possible to write LINQ queries using Intellisense in Silverlight to access the database layer, without breaking the architectural integrity, or introducing hand-composed SQL queries that pose serious security problems.

A common problem with client-server scenarios is that part of the application logic (such as validation) must be duplicated. The validation should run on the client for immediate feedback to the user — but also on the server to ensure that the validation cannot be skipped by a malicious client. WCF RIA Services addresses this situation by using attributes and code sharing. This is possible because the same framework runs on the client and the server (the Silverlight client not have all the .NET libraries, of course), this source code can be shared.

WCF RIA Services also integrates with the ASP.NET membership-provider models. It makes it easy to add a Silverlight application to an existing website with authentication, authorization, and profile requirements, or re-use the proven ASP.NET membership infrastructure — including the management tools — for the Silverlight application.
