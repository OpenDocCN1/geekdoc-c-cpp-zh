## Areas

An ASP.NET project organizes source files into folders — one for models, another for controllers, and another for views, and so on. If you have dozens of them, you can feel that your development environment is getting messy. It becomes quite difficult to keep track of how each item relates to a specific area of application functionality.

To reduce this, ASP.NET MVC lets you organize your project into areas, where each area represents a functional group of your application (for example, reporting, site administration, social features, asset management, and so on).

## Metadata Providers

MVC heavily uses metadata associated with your models. If the data annotations attributes defined in the System.ComponentModel.DataAnnotations namespace don't meet your needs, you can create your own custom metadata provider by creating a class that inherits from the ModelMetadataProvider, AssociatedMetadataProvider, or DataAnnotationsModelMetadataProvider classes.

## Value Providers

ASP.NET MVC has a concept called value providers to help you extract data from coming different sources into models. You can implement your own IProvider-based implementation to create a custom value provider, or use one of the following value providers out-of-the-box:

- QueryStringValueProvider — This value provider extracts values from the query string part of the incoming URL.
- RouteDataValueProvider — This value provider extracts values from the route data of the matched route.
- FormValueProvider — This value provider extracts values from the form fields of an HTML form. Obviously, this can only work for HTTP POST actions.
- HttpFileCollectionValueProvider — This value provider extracts values from a posted file collection, the values from INPUT type FILE tags.

## Model Binders

When your controller is about to invoke one of its action methods and is trying to find suitable values for the method's parameters, it uses value providers and model binders. While value providers represent the supply of data items available to your controller, model binders are responsible for taking all these data items and trying to map them onto whatever type of parameter method takes.

You can create your own model binders by implementing the IModelBinder interface, or using (reusing) one of the available model binders (ByteArrayModelBinder, LinqBinaryModelBinder, or HttpPostedFileModelBinder).

## Child Actions

MVC 2 has a new concept called child action, which is an action that can be invoked from inside a view, using the Html.RenderAction helper method. RenderAction retrieves a result, and is rendered inside the view that invoked it.

## Asynchronous Controllers

By the nature of IIS, when a request arrives, it is processed by a thread picked up from the thread pool. Until the request is processed, the associated thread is blocked. Long-running requests may cause the thread pool to run out of available threads, and incoming requests to be queued. An asynchronous controller (that is, a controller derived from the AsyncController class) resolves this situation using two separate methods for each action:

- The first method receives the input and launches the body belonging to the action asynchronously on a separate thread.
- The second method (callback method) is invoked automatically by the MVC framework when the asynchronous operation started by the first method completes. This method takes care of sending the response back to the caller of the action.

## UNDERSTANDING AJAX

Let's see what happens in the background. When the user clicks on the Buy button, the browser sends a request to the server that processes the request, updates the user's basket in the database, and creates the response. This is called a round-trip, and you can see that, depending on the network latency and the application complexity, it may take a long time.

What happens, after the response is received by the browser, the whole page is refreshed (to update the content of the basket) and scrolled to the top.
