The next snippet is an example about dynamically pumping data into a WPF window’s data grid:

```
[Export]
public partial class WindowWithDataGrid : Window,
IPartImportsSatisfiedNotification
{
    [Import]
ICustomerList CustomerRepository { get; set; }

public ListingsWindow()
{
    InitializeComponent();
}

public void OnImportsSatisfied()
{
    Dispatcher.Invoke(new Action() => {
        dataGrid.ItemsSource = CustomerRepository.GetAllCustomers();
    });
}
```

WindowWithDataGrid is an exported part, and when it is assigned to import by MEF, the default constructor is called. At that moment, CustomerRepository is a null reference, because MEF has not yet satisfied this import. As soon as it is, the OnImportsSatisfied method is called that sets the grid’s ItemSource on the UI thread with the Dispatcher class.

# Recomposition

Many applications are designed to dynamically change at run-time. For example you can download a new component from a web site, and that component functions without restarting your application. Or, a rule system can be extended by components describing new or changed rules by dropping an assembly to a folder holding the rule repository.
MEF was designed with these scenarios in mind, and it is prepared to handle them. This concept is called recomposition, changing values of imports after the initial composition.

Depending on your application logic, recomposition can be explicit (you explicitly tell MEF to recompose binds among parts), or event-driven (a catalog changes—for example, a new assembly has been copied to a watched folder). You can imagine that parts supporting recomposition may need to be implemented differently from that that support only an initial composition.
