
| NODE | DESCRIPTION |
|---|---|
| <ClassName> | This is the fully qualified name of the class implementing the add-in. Visual Studio uses this to load the COM object, naming your class in the code editor also requires changing the class name here. |
| <LoadBehavior> | This value determines whether or not the add-in is loaded at Visual Studio startup time. 0 specifies that the add-in must be started manually, because the IDE does not load it. 1 means the IDE loads the add-in at startup. |

## Using the Automation Model

Visual Studio has its automation model to access functionality through COM objects. The automation is provided through the Development Tools Extensibility (DTE) API that is part of Visual Studio (but not of the VS SDK) for the long time. The key to the extensibility of Visual Studio is DTE. The first version of Visual Studio .NET which remains in Visual Studio 2010. Visual Studio .NET (released in April, 2002) had no extensibility point.

Visual Studio macros and add-ins heavily use the automation model of DTE, and packages also obtain value through the automation model. Having a good object of this knowing and how to look it up for tasks is key to add-development (as well as macro programming).

The full graph of automation model hierarchy contains almost two hundred objects with many important methods and properties. This discussion does not examine all types, or even the most important ones. Instead of going into detail, this discussion provides starting points that you will be able to discover the object model yourself.

Table 6-5 shows functional grouping of object types, and recommends a few types of properties to start with. Here, "properties" refers to the objects belonging to the DTE object type.
