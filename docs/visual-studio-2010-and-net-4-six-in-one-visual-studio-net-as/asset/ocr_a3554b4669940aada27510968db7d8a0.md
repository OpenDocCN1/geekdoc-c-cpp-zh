You may notice that, although the service URI is encapsulated by the DataContext, the name of the web method is still defined on the ViewData instance. If you find this bit confusing, you are not alone, and this will likely change in the next previews or the RTM release.

The only thing is the DataContext instance. The DataContext resides in the MicrosoftAjaxDataContext.js file, and because it resides on a bunch of other files, it is best to use the new Script Loader to load the required files on the page:

```
<script src="Start.debug.js" type="javascript"></script>
<script type="javascript">
  var dataContext;
  Sys.require([Sys.components.DataView, Sys.components.dbContext\]);
  Sys.onReady(function() {
    dataContext = Sys.create.DataContext({
      serviceURI: "../Services/CountryService.asmx"
    });
  });
</script>
```

After the required scripts are downloaded and initialized, a new Sys.Data.DataContext instance is created, and this serviceURI property is used to set the web URI.

If you test the code you have at point, you will not notice any change in the browser. The data is downloaded and displayed on the page; nothing fancy so far. However, if you change the ViewData and provide input controls for the users, you can utilize the benefits of the DataContext class.

So, first rewrite the ViewData template to display textboxes of static text, and use live bindings that are, by default, two-way to notify the data source — in this case, the DataContext — if the data is modified by the user:

```
<div
  id="countryList"
  class="sys-template"
  sys:attach="dv"
  dv:autofetch="true"
  dv:dataprovider={dataContext}
  fetchoperation="GetCountriesByName"
  <div>
    Name:
    <input type="text" sys:value="{ binding Name }" />
    Capital:
    <input type="text" sys:value="{ binding Capital }" />
  </div>
</div>
```
