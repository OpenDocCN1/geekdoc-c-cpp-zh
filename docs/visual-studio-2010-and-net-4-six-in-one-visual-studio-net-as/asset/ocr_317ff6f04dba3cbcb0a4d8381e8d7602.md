The UserGreeting class does not know where it gets an IContextInfo-aware service object. If you decorate the ContextInfo property with the Import attribute, the composition container binds the right object to the property.

This simple example has shown just a taste of how MEF helps in composing applications. To understand what's behind the scenes, it's time to dive a deeper into MEF concepts.

# Basic MEF Concepts

As you have seen, programming with MEF is easy. However, architecting your applications so that they can easily leverage the potential of MEF requires an understanding of the primary concepts.

The fundamental concept of MEF is parts. An application is built of parts. During construction, you do the following:

+   - Export the services parts offer to be utilized by other parts
- Import the services you intend to use
- Compose the parts so they provide the functionality you want to achieve

# Parts and Controls

Parts export other parts may need, and optionally import services offered by other parts. MEF's default discovery mechanism to identify parts is based on .NET attributes defined in the System.ComponentModel.Composition namespace. Parts are decorated with the Export or Import attributes. To be recognized as a part, the corresponding entity must contain at least one export. Entities containing only parts are not taken into account as parts.

The loosely coupled nature of dynamic applications works with the data that parts do not depend directly on one another. The thing that determines this dependency is called a contract. Parts explicitly mark their intentions to be bound with other parts using contracts. Exported parts say, "Hey, I implement the contract named Foo. If there is anyone wanting to use Foo, here I am." Having Import attributes says, "In order to work, I need a part supporting the contract Foo. Is there anyone who could provide an implementation for me?"
