The clear separation of these responsibilities is provided by the following roles:

- The IDE uses the concept of a window frame that is responsible for hosting the client area of the window, called a window pane. This frame integrates the pane with the IDE and controls the visual properties and behavior of the pane.
- The window provides a window pane object that can be hosted in a window frame instantiated by the IDE. This pane works as a controller for implementing the interaction logic behind the UI.
- The window frame can also provide a toolbar for commands understood by the pane. At initialization, the pane tells that a toolbar should be displayed in the window. When a command is invoked, the frame notifies the pane, giving it a chance to respond to that command.

## Tool Windows

Most of the windows displayed in the Visual Studio IDE are tool windows. They generally surround document windows used to edit source code, or to design forms and web pages. The Server Explorer, Output window, Error List, Properties window, and Solution Explorer are only few examples of them. Tool windows are typically single-instanced. However, they can be multi-instanced, like the web browser window shown in Figure 5-3.

![](img/b5597c749e848b27b0d305153ae16106_172_0.png)

When Visual Studio runs, there are generally a number of tool windows displayed on the screen, with a majority of them containing valuable information or resources used by developers. Tool windows can float, or they can be docked to the edges of the main window to provide a practical workbench. They can also be dubbed with other windows, or they can be put to the area of document windows. Docked tool windows can be set to hide when the mouse leaves them. ## Document Windows

The other type of windows supported by the IDE is called document window. In contrast to tool windows, document windows are always multi-instanced. They can occupy only the middle area of the main window, optionally surrounded by tool windows. Although document windows cannot be docked, they can float, and can also be split into horizontal and vertical groups, as shown in Figure 5-5.

![](img/b5597c749e848b27b0d305153ae16106_174_0.png)

FIGURE 5-5: Document windows in horizontal tabs

The term "document window" reflects that any instance of them is associated with a document and is owned by a so-called hierarchy. The document and the hierarchy are abstractions that can have many physical manifestations.

For example, the documents behind document windows in Figure 5-5 are the in-memory representations of the source files named in the title. The source files are not the documents; they are only persisted forms of the abstraction called "document". You should edit the database within the IDE, for a document window would have an in-memory representation of the document that is persisted as a SQL server.

The hierarchy represents a collection of documents and other resources that are used to build the artifacts of a solution composed from one or more projects. A project is the smallest unit of related documents that can be used to build an artifact (for example, C# source files and referenced assemblies that can be compiled into a class). In Solution Explorer, each project is a hierarchy.

The documents in Figure 5-5 are owned by the project (hierarchy) in the Solution Explorer. The hierarchies in the Server Explorer also offer document windows. For example, through data connections created in Server Explorer, you can edit the content of SQL tables or modify stored procedures. Document windows in this case are owned by the hierarchy representing the data connection.

The fact that document windows are owned by hierarchies and are associated with documents adds a lot of functionality out-of-the-box. For example, you can have multiple document windows (or, with another term, views) for the same document. When you want to close the last open document window associated with the same document, Visual Studio prompts you with a dialog asking if you want to save or ignore all the changes. Another example is that document windows know if they have been modified since you opened them, and this is how the Save All function knows which documents are to be saved.

## Arranging Windows

Depending on the phase of the software development lifecycle you are in, or on the tasks you are assumed to do, you may need to arrange your windows in the workspace differently. For example, while writing code, you may not need the toolbar or Server Explorer, and you may want to provide much space for the code windows as you can. When you are debugging you probably move the application to the second monitor and dock many tools around the code you are debugging to see local variables, the call stack, and debug history.

Visual Studio provides several ways to arrange windows in the IDE:

- You can tabdock document or tool windows to the editing frame.
- You can dock tool windows to the edge of the IDE, or tab-dock them to the editing frame.
- You can float windows over or outside of the IDE.
- You can display windows on multiple monitors.
- You can minimize (auto-hide) tool windows along the edge of the IDE.
- At any time, you can reset window position to the original layout with the Window ↩ Reset Layout command.

## Floating Windows

If you have document or tool windows docked to the editing frame or move to other frames, you can make them easily float. Drag the title bar of the docked window and move it to another position within or outside of the IDE. You can even move a window to another monitor. When you double-click the title bar, the window gets maximized on the current day. Double-clicking on a maximized window will return it to its position, and size it as was before maximized.

When you press the Ctrl key while double-clicking the window, it is docked back to the frame it was docked before you undocked — and it works independently of how many times you have moved, maximized, or resized the floating window.

For example, if you drag the LIREcord.cs file in Figure 5-5 to a floating position, move it around, and move it by double-clicking its title bar. As soon as you press Ctrl and double-click it, LIREcord.cs will return to its original docked position as you see it in Figure 5-5.

When several windows are docked side-by-side (for example, Solution Explorer and Team Explorer in Figure 5-5), dragging them by the title bar will move all the windows in the same frame. If you move the Solution Explorer in Figure 5-5 by the title bar, the Team Explorer will move with it. If you want to move only one of the windows sharing the same frame, instead of dragging the title bar, drag the tab of the window.
