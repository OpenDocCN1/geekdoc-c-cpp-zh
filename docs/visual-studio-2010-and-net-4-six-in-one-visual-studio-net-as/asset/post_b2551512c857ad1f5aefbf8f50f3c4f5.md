## The Challenge of Many-core Shift

In accordance with Moore's law, the tendency to double the number of transistors placed on a unit of chip surfaces continues. However, this is not true for the CPU clock speed! Every further increase of clock speed implies more heat, to dissipate, and cooling processors is becoming a big issue for manufacturers. Also, there are some physical limits — light isn't getting faster.

Although the speed of CPUs cannot be increased significantly, the number of transistors per unit of area can still be. Manufacturers will put two or four CPU cores in the chip with the same area they used to put only one. So, if the clock speed of CPUs cannot be improved according to Moore's law, their processing capacities can!

## Software: The Weakest Link

Improving the computing capacity by increasing the number of CPU cores can be utilized well with web applications. The architecture of web servers easily allows assigning user requests to separate processors. Developers do not have to do any special coding to allow the web to scale up when adding new cores. However, putting a bottleneck in the database layer of web applications can put the brakes on scaling.

If you do not have this kind of a database bottleneck, there is one thing that cannot be solved without changing architecture. Although you may have a large number of processors, the response time of one user request cannot be decreased below a certain threshold. If the algorithm the user request runs sequentially (it can run only on a single thread), having a hundred CPUs cannot reduce the response time below that threshold.

The advantages of (many-core) CPUs cannot be utilized in the case of desktop applications, where the architectural constraints allow only sequential execution. Of course, having multiple cores means multiple applications can run in parallel, but that won't help to decrease the running time of slow applications. These kinds of applications cannot benefit from putting two, four, or even more cores into the desktop machine.

So, it's not worth to use multiple cores for applications designed and implemented with "sequential-style." The multi-core opens new horizons—but requires software architected in order to achieve the potential benefits.

From this aspect, a majority of today's software is the weakest link.

## Issues with Multi-Threading

If you want to develop an application supporting concurrent execution of certain parts of algorithms, you cannot avoid directly using threads. Managing multiple threads is definitely challenging. You're faced with several tasks to solve correctly in order to build a robust and bug-free application. Multiple threads introduce situations where you to handle variable and resource synchronization, flow control that utilizes data structures designed with sequential usage in mind, race-conditions, deadlocks, lock-offs, and many more.

The literature discussing concurrent programming is vast, handles all aspects, and even suggests design patterns for pattern contexts—but does not simplify multi-threading. Even if you find a simple principle or pattern to transform a task into a parallel one, you must still cope with a few more difficulties, including the following:

- The aspect of parallelism will spread through the task. You must find the principle to split the task into smaller independent parallelizable tasks. You must wrap these parts into threads, and take care of managing common resources, synchronizing their access. The flow control among tasks should be managed carefully—for example, if the end, tasks should wait while each of them finishes its work.

- In the final code that enables your algorithm to benefit from parallelism, the real business code (that is, code implementing the business functionality) will be mixed up with the code originating from the parallel aspect. The latter can significantly boost the size of business code by a number of code lines. Any further change in the code requires extra development resources, because the entire code is longer. You have a greater likelihood to be lost in the code, or a touch of the infrastructure code, instead of the business code.

- Testing this code is more challenging and resource-waste. To keep the level of code coverage at a certain point, you must write more unit test cases. The correctness of parallelism infrastructure (for example, avoiding race conditions) also requires additional test cases.

After development, these multi-threaded applications generate more work during their support phase. If it happens the application does not work according to the requirements, some bugs are caught (for example, a suspect of race condition), parallelism adds some extra tasks to troubleshooting, including the following:

- You must guess as to whether the issue is in the design or the implementation.

- Debuggers and tracing tools do not provide enough to step through multi-thread programs. Just think about placing a breakpoint in a code line used by several threads! Sometimes it is not easy to tell the debugger where to stop when a certain thread reaches that breakpoint.

Once you have a few years of experience with concurrent programming, you may be able to avoid some common pitfalls. Unfortunately, many developers do not have this kind of background.

## The Microsoft Approach

There are many approaches to the shift from sequentially running applications toward parallel ones. These specialized programming languages, pattern libraries, and tools examining the code and restructuring it, parallel-aware compilers, and so on.

Microsoft has a different approach that is based on the "80/20." Its own solution (called Parallel Computing Platform) provides a technology effectively addressing the issues coming from the use of multiple CPU cores. Instead of specification in threading models, or automating parallelism and hiding it from developers, this uses a declarative approach. It provides a simple model to allow developers to explicitly declare that certain parts of their programs can be executed in parallel. The platform take care of implementation.

The Parallel Computing Platform is built on the following simple design goals:

- Developers should be free from the complexity of parallel coding tasks to focus on solving business issues, and so their productivity could improve.

- The process of creating properly working, maintainable, and scalable parallel applications must be significantly simplified.

- Expectations both from native and managed code developers must be taken into account.

These are three main pillars (features) of this approach:

- High-level parallel programming concepts and abstractions allow leveraging values of parallel programming with minimal change in existing code.

- The approach lowers the entry barriers developers need to start dealing with parallel programming.

- The approach provides tools that, in addition to expressing parallelism, ensure great support (debugging, profiling, and so on) for developers.
