# Composition

Parts only declare their intention to be exported. Composition is the mechanism that makes the matching among the parts. This matchmaking is triggered by any of the parts — primarily by the MEF host — explicitly or importly.

When you have a large number of parts with connections among them — by means of exports and imports — the composition can become expensive. The default composition container is frugal with usage, and joins only the dependencies of the part triggering the matchmaking process.

# Explicit and Implicit Composition

Earlier, in Listing 10-21, explicit composition was used:

```csharp
class Program
{
    [ImportMany]
    private IEnumerable<IGreetings> Greetings { get; set; }

    // ...
    private void Run()
    {
        var catalog = new AssemblyCatalog(Assembly.GetExecutingAssembly());
        var container = new CompositionContainer(catalog);
        container.ComposeParts(this);
        // ...
    }
}
```

The ComposeParts call on a container explicitly triggered the composition for the current Program instance, and as a result, the Greetings property's value was set — in MEF terms, "the import was satisfied."

You could use implicit composition by querying the composition container for a specific part:

```csharp
class Program
{
    // ...
    private void Run()
    {
        var catalog = new AssemblyCatalog(Assembly.GetExecutingAssembly());
        var container = new CompositionContainer(catalog);
        var greetings = container.GetExportedValues<IGreetings>();
        // ...
    }
}
```

As these small examples show, the matchmaking can be started with a concrete part (explicit composition) or with a contract type (implicit composition). During this process, the dependencies of the initiating contract or part are resolved. If necessary, this resolution traverses through the graph of all direct and indirect dependencies.

# Part Instantiation

When exports and imports are resolved, the composition container may need to create new object instances for a variety of reasons:

- An entire class is an exported part, and an import referencing a related contract must be satisfied. In this case, the exported class is instantiated, and this instance is assigned to the import.

- A property (or field) of a class is exported. To satisfy a related import, this class is instantiated, and then the appropriate property's value (or field value) is assigned to the import.

- A method of class is exported. In this case, the hosting class is created, and a delegate to the exported method is assigned to the import.

Of course, if exported parts are members of static classes, you do not have the same control, as in the case when instantiation occurs behind the scenes, you are the one who explicitly creates those instances. By default, MEF uses the default constructor of the class (the constructor with no parameters). If there is no default constructor, MEF looks for a constructor of exactly one decorated with the `ImportingConstructor` attribute. If there is such a constructor, its parameters are taken into account as imports. MEF satisfies those imports, and you use those parameters with which to call the constructor. If there is no such constructor, MEF raises an exception, because it cannot create an instance.

Earlier in 10-25, the import of an `IContextInfo` part was implemented in this way:

```csharp
[Export(typeof(IGreeting))]
class UserGreeting{
    [Import]
    IContextInfo ContextInfo { get; set; }

    public string SayHello() {
        string username;
        var props = ContextInfo.Get();
        props.TryGetValue("Username", out username);
        return "Hello " + username ?? "<None>";
    }
}
```

With `ImportingConstructor`, it could also be done as follows:

```csharp
[Export(typeof(IGreeting))]
class UserGreeting{
    IContextInfo ContextInfo { get; set; }

    [ImportingConstructor]
    public UserGreeting(IContextInfo contextInfo)
    {
        ContextInfo = contextInfo;
    }

    public string SayHello()
    {
        // ... Omitted for the sake of brevity
    }
}
```

You may wonder why it is useful to have two constructs for the same task. Well, there is an important difference between the Import property and ImportingConstructor approach.

When you use the Import property, the declaring class is instantiated with the default constructor, and MEF assigns the imported value to the property. This means that you cannot use the property's value in the constructor body. Contrast this to instantiating the class with ImportingConstructor. This means you are able to use the imported values, because those are passed as constructor parameters.

# Lazy Instantiation

As you learned earlier, during composition of a part, an import will trigger the instantiation of a part (parts) that expose the necessary exports for the original requested part. In the case of imported properties and fields, this means that their values are set before they are used. In many situations, it may happen that the properties are not used at all, or are used later after their construction. If the instantiation of property is expensive (takes a relatively long time, consumes many CPU cycles, a large amount of resources, and so), it is a good approach to delay this instantiation — and prevent the recursive composition down graph.

MEF supports called lazy instantiation. To use it, all you must do is import a type `System.Lazy<T>` instead of T directly. For example, the UserGreeting class in 10-25 could be implemented with lazy instantiation:

```csharp
[Export(typeof(IGreeting))]
class UserGreeting : IGreeting
{
    [Import]
    Lazy<IContextInfo> ContextInfo { get; set; }

    public string SayHello()
    {
        string username;
        var props = ContextInfo.Value.Get();
        props.TryGetValue("Username", out username);
        return "Hello " + username ?? "<None>";
    }
}
```

As you can see from the SayHello method, the imported part behind ContextInfo is accessed through Value. The actual instantiation of the part is carried out when Value is first queried, and subsequent queries use that instance.

# Import Notification

There are situations where you need an explicit notification about the fact that all imports have been satisfied and you can safely use them (such a situation is known as recomposition, and will be discussed shortly). In this case, you must implement the IPartSatisfiedNotification interface which has only one method named OnSatisfied.

The next snippet is an example about dynamically pumping data into a WPF window’s data grid:

```csharp
[Export]
public partial class WindowWithDataGrid : Window,
IPartSatisfiedNotification
{
    [Import]
    ICustomerList CustomerRepository { get; set; }

    public WindowWithDataGrid()
    {
        InitializeComponent();
    }

    public void OnSatisfied()
    {
        Dispatcher.Invoke(new Action(() => {
            dataGrid.ItemsSource = CustomerRepository.GetAllCustomers();
        });
    }
}
```

WindowWithDataGrid is an exported part, and when it is assigned to import by MEF, the default constructor is called. At that moment, CustomerRepository is a null reference, because MEF has not yet satisfied this import. As soon as it is, the OnSatisfied method is called.

# Recomposition

Many applications are designed to dynamically change at run-time. For example you can download a new component from a web site, and that component functions without restarting your application. Or, a rule system can be extended by components describing new or changed rules by dropping an assembly to a folder holding the rule repository.
MEF was designed with these scenarios in mind, and it is prepared to handle them. This concept is called recomposition, changing values of imports after the initial composition.

Depending on your application logic, recomposition can be explicit (you explicitly tell MEF to recompose binds among parts), or event-driven (a catalog changes—for example, a new assembly has been copied to a watched folder). You can imagine that parts supporting recomposition may need to be implemented differently from that that support only an initial composition. To let your component set the AllowRecomposition property of the Import attribute to true. The WindowWithDataGrid sample you’ve seen is a great candidate to demonstrate this.
