When you run this application, it does exactly what you assume from the source code — it creates a Word document and inserts the "This is a table", followed by a table of three rows and two columns. The interesting thing is how this is done. Because of the No-PIA mode, a few types are added to both the TypeEquivalentDemo and WordHelper assemblies representing Word interoperability in the Microsoft.Application.Interop.Word assembly. Such a type is Word.Application.

But, if there are two Word.Application declarations (by the compiler) in two separate assemblies, the .NET Framework's Common Type System handles them as separate, unrelated types. In this case, how do pass a Word.Application instance defined in the TypeEquivalentDemo assembly when calling TableHelper.InsertTable that is defined in the WordHelper assembly and expecting a Word.Application type also defined there?

# Equivalence Insert of Equality

Accomplishing the aforementioned task would not be possible in any CLR prior to CLR 4.0. But it's available in CLR 4.0, because of the type equivalence feature. Behind the scenes, you can run the following line of code:

```
TableHelper.InsertTable(word, 3, 2);
```

This results in the following code compiling:

```
TableHelper.InsertTable((Word.Application)word, 3, 2);
```

In this code, the Word.Application uses the type generated in the WordHelper assembly. The type equivalence feature means that the CLR is able to successfully carry out the specified cast.

The last two statements of the Main method in Listing 10-6 compare the two Word.Application types for equality (using the "equals" operator) and for equivalence (using the Type.IsEquivalentTo). The first comparison returns false, and the second results are true, as shown in Figure 10-8.
