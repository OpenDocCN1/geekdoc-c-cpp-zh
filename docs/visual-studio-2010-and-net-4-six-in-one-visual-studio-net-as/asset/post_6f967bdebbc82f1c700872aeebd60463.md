The .vsct file tells us all how Visual Studio is architected, how it solves the coupling of functions (commands, and interface elements).

- Commands (to execute) are separated from the user interface triggering the command. The command can be assigned to different menus and toolbars. They will use the action name.

- Commands together can be grouped and simply merged into existing menus using the command group representation. It is much easier than coupling commands with hosting menus one-by-one.

- Elements are identified by symbols rather than explicit values. This makes the coupling less error-prone. Values of symbols must be defined only once, and the VSCT compiler can check for mistyping.

The root element of a .vsact file is the CommandTable element. As you can see, all elements are defined by the http://schemas.microsoft.com/VisualStudio/2005-10-18/CommandTable namespace. No doubt, the most important element is Commands, which these defines nodes, their initial layout, and behavior.

Any command in the Visual Studio IDE needs to the IDE itself or to a package. To assign a command to the appropriate (owning) package, the package attribute of the Commands element means the GID of the corresponding package.

The Commands node can have a few child elements; each has a very specific role.

Group elements define command groups, each of which is a logical set of related commands that visually stand today. In the preceding .vsact file, you have a Group element that holds only a Button. A button represents a piece of user interface element the user can interact with – in this case, an item that can be clicked. The Parent element defines the relationship between elements – for example, the Button element defined earlier is parent in the Group.

Toolbars and menus would be poor without icons to help the user associate a small image with the function. The Bitmap nodes defining the visual elements (icons) used in menus.

The symbols section is a central place in the .vsct file. You can use the GuidSymbol element to define the identifiers to be used in the other parts of the logical GUID, and the nested IDSymbol to provide optional identifiers within the logical container. The name and value attribute of these elements do exactly what you would expect — associate the symbol name with its value.

# EXTENDING THE NEW EDITOR

The new code editor of Visual Studio 2010 is not just a piece of the Shell that is re-architected to leverage WPF technology and managed code. It is also a great subject of extensibility. Extending the behavior of the old code editor (built into Visual Studio 2005 or 2008) was painful because of the lack of documentation and complex interfaces.

This is no longer true for the new editor. Using the templates provided by the VS SDK, it takes just a few clicks to create a working skeleton of an extensible editor component.

# Extending the Editor with the Managed Extensibility Framework

The key technology enabling the creation of custom editor components new in .NET 4 is the Managed Extensibility Framework (MEF). The MEF is not a part of Visual Studio 2010. However, Visual Studio 2010 is one of the first Microsoft products that uses the MEF. The following discussion does not go into detail about the MEF, but provides a very brief overview to help you understand what it is and how it works.

Simply said, the MEF as a technology is intended to enable greater reuse of applications by turning these parts dynamically. In the case of extending the Visual Studio, the host is Visual Studio, and the custom parts are the.

The MEF uses attributes for cooperation. These attributes can be found in System.ComponentModel.Composition namespace.

# Using Export Attributes

The intention that a component offers a service to be consumed by other components is expressed with the Export attribute. For example, if you have an abstract service described with the IGreeting interface, a custom part looks like this:

```cs
[Export(typeof(IGreetings))]
class SimpleGreeting : IGreetings
{
    public string SayHello()
    {
        return "Hello from Visual Studio";
    }
}
```

The parameter of the Export attribute defines the contract it satisfies. When the MEF composes the parts, it uses this attribute to recognize that SimpleGreeting satisfies the IGreeting contract. When any other component or the host application queries the composition container for parts, SimpleGreeting is also retrieved.

# Accessing Services with Import Attribute

Generally, compos parts not only offer functions to other parts, but also intend to use services provided by other parts. This intention is expressed with the Import attribute.

Let's assume you want to modify the SimpleGreeting component so that it can work with an IContextInfo-aware component, like UserInfo in the following declaration:

```cs
[typeof(IContextInfo)]
class UserInfo: IContextInfo
{
    public IDictionary<string, string> GetContextInfo()
    {
        return new Dictionary<string, string>
        {
            {"Username", Environment.UserName}
        };
    }
}
```

The IContextInfo is a service from SimpleGreeting's point of view, and this is expressed like this:

```cs
[typeof(IGreeting)]
class SimpleGreeting : IGreeting
{
    [Import(typeof(IContextInfo))]
    IContextInfo ContextInfo { get; set; }

    public string SayHello()
    {
        string userName;
        var props = ContextInfo.GetContextInfo();
        props.TryGetValue("Username", out userName);
        return "Hello " + (userName ?? "<null>") + " from Visual Studio 2010";
    }
}
```

The Import attribute here applied on the ContextInfo property, which is used in the SayHello method. The MEF takes care during the composition phase that ContextInfo will be set up and not remain uninitialized.

The Visual Studio editor offers about three dozen services that can be accessed using the pattern just described. Later in this chapter, you will see a sample to learn how the editor's classification type registry service is consumed.
