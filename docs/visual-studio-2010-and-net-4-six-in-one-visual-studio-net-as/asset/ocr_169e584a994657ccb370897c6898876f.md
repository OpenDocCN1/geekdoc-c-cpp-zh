As a general guideline, you should use the light syntax wherever possible, and only resort to normal syntax elements when absolutely necessary. The light syntax encourages a cleaner, shorter, and more robust coding style because of the added significant whitespace, your code becomes easier to maintain.

# Naming Conventions

In addition to writing F# applications or F# libraries to be used by F# applications, you can use F# very effectively for writing libraries that you consume from .NET languages. This is especially true in domains where functional programming excels over other paradigms, including numerical and symbolic computing, data traversal and processing, parallel and asynchronous computations, and all so — which you expose as a Windows Forms or web application with C# or VB UI code.

Using for .NET components and libraries makes the naming conventions defined in the standard .NET Design Guidelines for libraries prevail, and indeed, this is the recommended way to program. F# itself has come a long way since its beginnings to wear off many of its early influences from OCaml, especially when it comes to naming conventions.

At a short summary, here are some naming and coding style recommendations that will help you to produce code that is easy to maintain and from all .NET languages:

+   Always use PascalCase for type names and type parameters (for example: MyCustomer<'T>). Note that most of the F# type abbreviations (which you see all the time in F# code, as 'T list', 'T array', 'T option') are safe "exceptions" to this rule. They will ultimately map to the underlying .NET type names that are PascalCase.

+   Always use PascalCase for namespaces, modules, exceptions, class members (properties and methods), discriminated union cases, record labels, and, in general, everything that will be part of a API.

+   Always use camelCase for function and method parameters, and (internal) let values.

+   Avoid using underscores. There has been a strong movement motivated by .NET naming conventions to eliminate underscores from the F# core libraries, and in all, you should avoid them as well.

# Using Comments

Comments in F# are the same as in C#. Thus, you have the following:

+   Comments in between (* and *) — These comments can be nested.

+   Single-line comments starting with // — These comments apply from the comment opener to the end of the current line. Used for documenting inner code.

+   Doc comments starting with /// — Used to define comments for public APIs, such as member or type names, argument types, return types, member description, and so on.
