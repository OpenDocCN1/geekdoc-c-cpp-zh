The architects of Visual Studio implemented the package load mechanism so that packages are loaded into memory the first time an event requiring the package is raised. These events can be one of the following:

+   * Command activation — The user (or some running code) activates a menu or toolbar command served by a package that has not been loaded. It doesn't matter if the user clicked on a menu item or the running code has activated it with a "virtual click"; the result is the same.

+   * Object or service request — The Shell is built to use an object or a service in a package not yet loaded — for example, a tool window that should be displayed, or service function that should be executed.

+   * Context change — The Shell can enter certain UI contexts. For example, when you start debugging a project, the Shell enters into the Debugging context. When a solution with single project is loaded, the Shell enters into the SolutionAsSingleProject context. Visual Studio has a few predefined contexts, but you can define your own.

So, if you do not need a package during the entire IDE, it does not consume any memory. You should click on a menu item activating a command sitting in a package that has not been loaded, the IDE will immediately load and initialize it. It should ask you for a tool window in a package not yet in memory, the IDE will start loading it.

This architecture is powerful. With packages, you can write new functionality for Visual Studio with almost the entire set of APIs and components developed by the development team at Microsoft. The resulting binary is integrated into the Shell in the same way as any other packages created by Microsoft or third parties.

> To create packages, install the Visual Studio Software Development Kit (VS SDK) available for free at the Microsoft Visual Studio Extensibility Development Center (http://msdn.com/vsx).

# EXTENSIBILITY OUT OF THE BOX

While the Visual Studio architecture is powerful (because it is designed with extensibility in mind), it would be complicated to extend Visual Studio if you only have choices for creating packages. Of course, Visual Studio provides other mechanisms that support extension in much easier ways, enabling you to save time and the amount of work invested.
