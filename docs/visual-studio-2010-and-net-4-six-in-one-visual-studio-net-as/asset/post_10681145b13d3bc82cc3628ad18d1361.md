# WORKING WITH DYNAMIC OBJECTS

.NET developers are familiar with the fact that types and operations are strictly checked during the compilation process. The compiler generates Microsoft Intermediate Language (MSIL) code that explicitly carries out those operations by invoking methods. This behavior of the compiler is early binding.

Early binding has the following characteristics:

- Early-bound objects (objects that have been assigned their values with early binding) allow the compiler to make important optimizations that yield more efficient applications.
- Early-bound objects are significantly faster than late-bound objects and make your code easier to read and maintain by stating exactly what kind of objects are being used.
- Early binding enables useful features such as automatic code completion and Dynamic Help because the Visual Studio integrated development environment (IDE) can determine exactly what type of object you are working with as you edit the code.
- Early binding reduces the number and severity of run-time errors because it allows the compiler to report errors when a program is compiled.

There is no other galaxy in the universe of programming dynamic languages. The compiler makes only a few checks over types and their operations. The majority of them are postponed to the execution of the corresponding operation at run-time.

In addition to the dynamic languages, there are script languages and object models (for example, COM objects over the Microsoft Office functionality, the DTE object in Visual Studio, the HTML DOM in Internet Explorer, and so on) that also check at run-time.

In this complex world, these tools and languages should interact so that they can provide boosted performance. Scripting tools and languages such as JavaScript, PowerShell, and many others, as well as dynamic languages as Python or Ruby, are very popular today.

Visual Basic was very strong in interoperating with COM object models, because of the late binding mechanism provided by the compiler and the Visual Basic run-time. In Visual Basic 2010, this mechanism has been enhanced, so developers can bind to objects from dynamic languages such as IronPython and IronRuby easier than ever before.

> For a long time, C# could not compete with the interoperability features of Visual Basic, because the C# compiler did not know late binding. C# 4.0 improved C# by introducing a new variable called dynamic to enable late binding. Chapter 24 describes how this works in C#.

# Late Binding in Visual Basic 2010

Visual Basic implemented the mechanism of late binding a long time ago. When you compile your program with Option Strict Off, and you assign an object to a variable declared by type Object, the compiler generates code that postpones the assignment and other operations with that object until run-time. Listing 22-3 shows a simple console application utilizing this feature.

# LISTING 22-3: Module1.vb: Console Application Demonstrating Late Binding

![](img/b5597c749e848b27b0d305153ae16106_1063_0.png)

```vb
Option Strict Off
Module Module1

Sub Main()
Dim xlApp As Object
Dim xlBook As Object
Dim xlSheet As Object
xlApp = CreateObject("Excel.Application")
xlBook = xlApp.Workbooks.Add
xlSheet = xlBook.Worksheets(1)
xlSheet.Activate()
xlSheet.Cells(1, 1) = "I"
xlSheet.Cells(1, 2) = "*I*"
For i = 1 To 10
xlSheet.Cells(i + 1, 1) = i
xlSheet.Cells(i + 1, 2) = i * i
Next
xlSheet.Application.Visible = True
End Sub

```

End Module

> Code file [Module1.vb] available for download at Wrox.com

This application creates an Excel worksheet with a small table and displays it using Microsoft Excel automation objects.

The xlApp, xlBook and xlSheet variables are declared as type of Object. At build time, the compiler does not know what kind of objects will be present at run-time. For example, it does not know how to execute the following assignment:

```vb
xlBook = xlApp.Workbooks.Add
```

This is because it does not know how to access the Workbooks operation of xlApp and the Add operation from the xlApp.Workbooks operation. The compiler does not even know which kind of operations (method invocation or property access) they are.

The compiler emits code that uses the types in the Microsoft.VisualBasic.CompilerServices namespace heavily to resolve and execute these operations at run-time. When you run the application, the following actions are carried out:

1. The run-time recognizes that xlApp is an Excel automation object (COM object)
2. It asks xlApp to execute the Workbooks operation and retrieves its result.
3. When the Workbooks object is returned, the run-time asks this object to execute its Add operation.
4. When Add is executed, the result is stored in xlBook.

The same mechanism is carried out by the run-time executes operations on xlSheet.

Visual Basic 2010 improves this mechanism by integrating the binding with the Dynamic Language Run-time (DLR). If a late-bound call is made to an object that implements the IDynamicMetaObjectProvider interface of the System. Dynamic namespace, Visual Basic binds to the object by using dynamic. If a late-bound call is made to an object that does not implement the IDynamicMetaObjectProvider interface, or if the call to the IDynamicMetaObjectProvider interface fails, Visual Basic binds to the object by using the late-binding capabilities of the Visual run-time—just as it did before DLR integration.

From a Basic syntax point of view, the DLR integration is transparent. You cannot see any difference between a late-bound COM object or a dynamic object (an implementing IDynamicMetaObjectProvider). What you can observe is now Visual Basic binds to objects from dynamic languages such as IronPython and IronRuby. The world within which you operate from Visual Basic is definitely larger than it was before.

# THE DYNAMIC LANGUAGE RUN-TIME

> An important component in the underlying implementation of dynamic lookup is the Dynamic Language Run-time (DLR), which is a part of .NET Framework 4.0. DLR is a run-time environment that allows a set of services for dynamic languages to the Common Language Run-time (CLR), and makes it easier to develop dynamic languages to run on the .NET Framework, as well as to develop dynamic features to statically typed languages. DLR is built on top of CLR, and uses run-time binders to access the physical object model addressed by dynamic expressions. Chapter 10 provides more details about DLR.
