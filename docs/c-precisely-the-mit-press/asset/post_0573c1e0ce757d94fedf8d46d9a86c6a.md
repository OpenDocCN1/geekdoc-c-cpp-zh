
## 28.8 Extension Methods on non-generic Enumerable (C# 3.0)

Static class System.Linq.Enumerable defines extension methods on non-generic interface IEnumerable (section 27.2.2):

- `IEnumerable<U> Cast<U>()` returns an IEnumerable<U> obtained by casting each item of the given non-generic enumerable to type U. This is used to implement explicitly typed range variables in from and join queries (section 28.1.2). Throws InvalidCastException if some item of the given enumerable cannot be cast to type U.
- `IEnumerable<U> Of<U>()` returns an IEnumerable<U> that produces only those items of the given non-generic enumerable that can be cast to type U. That is, it ignores items that would cause Cast<U> to throw InvalidCastException.

## 28.9 Static Methods to Generate Enumerables (C# 3.0)

Static class System.Linq.Enumerable provides static methods to generate enumerables:

- `IEnumerable<T> Empty<T>()` returns an enumerable that generates no items.
- `static IEnumerable<int> Range(int i, int n)` returns an enumerable that generates the n integers i, i+1,...,i+n. Throws ArgumentOutOfRangeException if n<0.
- `static IEnumerable<T> Repeat(T x, int n)` returns an enumeration that generates n times x. Throws ArgumentOutOfRangeException if n<0.

In general, enumerables can be conveniently generated using the yield return statement in the iterator block (section 13.12).

## 29 Namespaces

A program may be divided into namespaces. A type t declared inside a namespace N may be used unqualified, simply as t, within the namespace. Outside the namespace, references to t must be prefixed by the namespace, as N.t, or must follow the clause using N.

Namespace declarations may be nested: giving rise to composite namespaces such as N1.N2. A namespace-declaration can appear only at top level in a compilation unit or inside a namespace declaration, cannot have access modifiers, and has this form, where declarations can appear in any order:

```namespace
namespace N {
  class-declarations
  struct-declarations
  interface-declarations
  enum-type-declarations
  delegate-type-declarations
  namespace-declarations
}
```

The namespace identifier N may be composite, as in N1.N2. A namespace may consist of separate and mutually dependent declarations. Top-level declarations (of classes, struct types, interfaces, enum or delegate types) not within a namespace declaration belong to the default namespace.

### 29.1 The Using Directive

A using directive can open a namespace, or introduce an alias for a namespace, or introduce an alias for a type (for abbreviating constructed types; see section 26.9). A using directive must appear before any member of a compilation unit or a namespace declaration. A using directive has one of these forms:

```sharp
using N;
using M = N;
```

The first form opens namespace N. The second form means that any namespace type member N.T can be referred to as M.T, which is useful if N is N1...Rn. The third form means that the type will be referred to as T, where T is a type and t is any type, possibly of form N.tl or possibly constructed.

A using directive does not affect other directives. Using N1,N2 opens the namespace N1,N2, using N1; N2 does not. Even after using N1, one must refer to N2.C by its fully qualified name, not by N2.C. It is a compile-time error for using two directives to the same name.

A local declaration (of a variable, struct, delegate type or enum type) may hide a declaration of the same name from another namespace, or as from a using directive.

Namespace's .NET Framework class library, which is used with C#, is divided into many namespaces. Namespace System contains classes such as Object, Math, Random, and String, struct types such as Int32, and enum types such as DayOfWeek. Namespace System.Text contains classes such as StringBuilder. After opening the namespace with using one may use the unqualified name StringBuilder instead of the fully qualified name System.Text.StringBuilder.

## 30 Partial Type Declarations

The declaration of a class or struct may consist of several parts. This is useful when parts of a declaration are created in different ways. For instance, one part may consist of code generated by a program, and another part may contain customization. By separating them, the generated code can be re-generated without destroying the customization code.

Apart from these cases, a generic type (section 26) or interface or struct declared in several parts, each member (field, method, property, indexer, operator, delegate type, enum type) must be completely contained in one part.

A partial type declaration must have the prefix part before class or interface or struct:

```sharp
class-modifiers partial class C class-base-clause
class-body
interface-modifiers partial interface I base-interfaces
{ ... }
struct-modifiers partial struct S struct-interfaces
struct-body
```

The following rules apply to partial type declarations:

- All parts of a type declaration must be declared in the same namespace.
- A modifier (new, sealed, abstract, public, ...) on one part of a partial type declaration applies to the entire result. The modifiers must be non-conflicting: a class declaration cannot have one part that is sealed and another part that is abstract.
- All parts of a partial type declaration that have access modifiers have the same access modifiers (public, protected, internal, private). If no part any access modifier, the resulting type has default access: internal for top-level types, private for nested types. The absence of an access modifier on a part does not imply default access.
- All parts of a class declaration that specifies a base class must specify the same base class. This is the base class of the resulting type, if any base class was specified; otherwise it is Object.
- The interfaces of a part must be implemented by the resulting type, not by that part in isolation. Different parts may list different base interfaces. The list of base interfaces of the resulting type is the union, without duplicates, of the interfaces of the parts.
- If a generic type (section 26) is declared in parts, then all parts must have the same type parameters. All parts that have parameter constraints (section 26.4) must have the same constraints, in some order; these are the parameter constraints of the generic type.
- An attribute (section 32) on a part applies to the entire type, not only to that part. The list of attributes of the resulting type is the concatenation, in some order and possibly with duplicates, of the attributes of the parts.
