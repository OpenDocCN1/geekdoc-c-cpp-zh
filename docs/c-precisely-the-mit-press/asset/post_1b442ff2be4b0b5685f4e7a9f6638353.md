# Example 211 Generic QuickSort Using a Delegate to Compare Elements

This generic method is a faster and more typesafe version of the delegate-sorting method in example 153. It sorts an array of type T where T is a type parameter, as in example but the element ordering is determined by a delegate of type DComparer<T> (example 210). Note that all type casting, boxing, and unboxing can be avoided, even when sorting of simple type such as integers.

```csharp
private static void QSort<T>(T[] arr, DComparer<T> cmp, int a, int b) {
    while (cmp(arr[i], x) < 0) i++;
    while (cmp(x, arr[j]) < 0) j--;
}
```

# 26.10 Generic Struct Types

A declaration of a generic type struct S<T1,...,Tn> is very similar to the declaration of a generic class.
It has one of these forms:

```csharp
struct-modifiers struct S<T1,...,Tn> struct-interfaces
    struct-body
```

In both cases, the T1,...,Tn are type parameters as for generic classes (section 26.3), and the struct-modifiers and struct-body are for non-generic struct types (section 14). The parameter-constraints are as for generic classes (section 26.4).

A type constructed from the generic struct has form S<t1,...,tn>, where the t1,...,tn are types. The t1,...,tn must satisfy the parameter-constraints on the generic struct, if any, as described in section 26.4.

Generic struct types are used in the generic collection library, for instance to represent key/value pairs in dictionaries (section 27.8 and example 221).

# 26.11 The Implementation of Generic Types and Methods

Generic types and methods in C# type templates and function templates, resemble generic types and methods in Java 1.5. However, the design and implementation of C# generics provide better safety and less code duplication than C++ templates, but better performance and more features than Java 1.5 generic types and methods.

In C# type declaration or generic method declaration can be fully type-checked before any constructed type is created for type arguments, and then the typecheck is valid for all possible arguments. Hence type errors are discovered as early as possible. In C++ a class template or function template cannot be type-checked before a instance is created for generic parameters, and the typecheck must be performed for every set of generic parameters.

In each constructed struct, such as Pair<double, int> (see Pair in example 214), principle gives rise to a new type (in the run-time system) with its own field layout; this permits unbounded storage of fields. To save space and code duplication, every of argument types will share the same field layout; all references have the same size regardless of. Thus the two constructed types Pair<Object, String> and Pair<String, String> have the same field layout. On the other hand, combinations of argument types that vary require different field layouts at run-time, values of different value types take different amounts of memory. For instance, the constructed struct Pair<double, int> and Pair<int, int> have different field layouts.

This implementation for C# has the considerable advantage that it permits generic types and methods to handle value types unboxed, which reduces memory usage and increases speed. By contrast, Java 1.5 implementation uses boxed representation of all values, which requires costly boxing when accessing the values. On the other hand, C# implementation has the disadvantage that it may cause code duplication (at run-time), but this problem is less pronounced than C++ templates.

### Example 216 A Generic Struct to Represent Missing Values

Option<T> can represent a value of type T that may be missing. Sometimes null reference is used to mean "missing", but this is impossible for value types. The generic struct Nullable<T> serves a similar purpose but is used only for reference types. Note that the default value of HasValue field is false, so the Option<T>() constructor constructs a missing value.

```csharp
public struct Option<T> {
    public readonly bool HasValue;
    private readonly T value;
    public Option(T value) { this.HasValue = true; this.value = value; }
    public T Value() {
        if (this.HasValue) return value;
        else throw new InvalidOperationException("No value");
    }
    public static operator Option<T>(T value) { return new Option<T>(value); }
    public static explicit operator T(Option<T> option) { return option.Value(); }
    public override string ToString() { return HasValue ? value.ToString() : "[No value]"; }
}

public static Option<double> Sqrt(double x) {
    return x >= 0 ? new Option<double>(Math.Sqrt(x)) : new Option<double>();
}
```

# 26.12 Variance of Type Parameters (C# 4.0)

A type parameter T of a generic interface (section 26.5) or generic delegate type (section 26.8) may be declared covariant (out) or contravariant (in):

```csharp
interface-modifiers interface Ivariance-modifier T1,...>
delegate-modifiers returntype delegate Ivariance-modifier T1,...>(formal-list);
```

Here a variance-modifier is out, meaning covariant; or in, meaning contravariant; or absent, meaning invariant. To understand the effect of such a declaration, assume that type C is a subtype of type B.

If I has a covariant type parameter T, then I<C> is a subtype of I<B>; intuitively, if an I<T> can be seen to produce T objects, then a producer I<C> of objects can be used where a producer I<B> of objects is expected, because C is a subtype of B.

Conversely, if I has a contravariant type parameter T, then I<B> is a subtype of I<C>; intuitively, if an I<T> can be consumed or input T objects, then a consumer I<B> of objects can be used where a consumer I<C> of objects is expected, because C is a subtype of B.

Note that subscripting between variance types C and B is not related to relations between primitive types. For instance, I<int> is never a subtype of I<double>, although there is no implicit conversion from int to double.

There are restrictions on variance declarations: A type parameter declared covariant T must not appear as an input type, and a type parameter declared contravariant I must not appear as an output type. These restrictions preserve the soundness of subtyping ("value of a supertype is expected") without having to introduce further run-time checks.

Roughly, the return type of a method is an output type, and its arguments are input types. A type parameter may be both an output type and an input type at the same time; in that case, the type must be invariant (neither nor out) in the declaration. For instance, type parameter T in IList<T> (section 27.4) must be invariant because it appears as an input type, in method Add(T), and also as an output type, in the get-indexer[i].

*   A type t is an output type in a method signature if it returns the return type of the method signature, or as an input type in another type expression that itself appears as an output type, or as an output type in another type expression (such as t[] or IList<t>) in the signature.
*   Similarly, a type t is an input type in a method signature if it appears as a parameter t of the method signature, or as an input type in another type expression that itself appears as an output type, or as an output type in another type expression (such as t[] or IList<t>) in the signature.

A type is an input type (output type) in an interface if it is an input type (output type) of some method on the interface. A type is an input type (output type) in a delegate declaration if it is an input type (output type) in the delegate signature.
