## Example 163 Multiple Threads
The main program creates a new thread, binds it to u, and starts it. Now two threads are executing concurrently: one executes Main, and another executes Run. While the Main method is blocked waiting for keyboard input, the new thread increments i. The new thread executes Sleep(0) to make sure that the other thread is allowed to run (when not waiting for keyboard input).

```csharp
using System;using System.Threading;
class ThreadDemo {
    private static int i;
    public static void Main() {
        Thread u = new Thread(ThreadStart());
        u.Start();
        Console.WriteLine("Repeatedly press Enter to get the current value of i:");
        for (;;) {
            Console.ReadLine(); // Waits for keyboard input
            Console.WriteLine(i);
        }
    }
    private static void Run() {
        for (;;) { // Forever
            i++; // increments i
            Thread.Sleep(0); // yields to other thread
        }
    }
}
```

## 21.2 Locks and the lock Statement

Concurrent threads are executed independently. Therefore, when multiple threads access the same fields or array elements, there is danger of creating an inconsistent state (example 165). To avoid this, threads may synchronize the shared state, such as objects and arrays. A single lock is associated with every object, array, and class. A lock can be held by one thread at a time. A thread may explicitly request a lock by executing a lock statement, which has this form:

```
lock (expression)
    block-statement
```

The expression must have reference type. The expression must evaluate to a non-null reference o; otherwise a NullReferenceException is thrown. After the evaluation of the expression, the thread begins Locking on object o (see page 131). When the thread holds the lock on object o (if ever), the thread becomes blocked and may returning until the block-statement terminates or is exited by return or continue or goto or by throwing an exception, then the lock on o is released.

That is, the thread will execute the block-statement only when it has obtained the lock on the current object. It will hold the lock until it leaves the block-statement, and release it. Moreover, it may temporarily release the lock by calling Monitor.Wait(o); see below and section 21.3.

When one or more static methods of a class C must ensure exclusive access to static fields, they can obtain the lock on the unique object of class Type that represents class C in the run-time system. This object is obtained by evaluating typeof(C). Hence the critical sections may be enclosed in a lock statement as this:

```
lock (typeof(C))
    block-statement
```

That is, the thread will execute the method body only when it has obtained the lock on the returned object by typeof(C), which is the unique object of class Type associated with class C; see section 12.21.

Mutual exclusion is ensured only if all threads accessing the shared object make sure to hold the lock for instance. if an unsynchronized method RogueTransfer were added to a bank object (example 165), one can no longer be that a thread calling the synchronized method Transfer has exclusive access to the bank object; many of threads could be calling RogueTransfer at the same time.

A monitor is object whose fields are private and manipulated only after obtaining the object's lock, that all field is subject to synchronization (example 166).

If a thread needs to wait for some condition, or for a resource to become available, it may temporarily release the lock by calling Monitor.Wait(o). The thread must hold the lock on object o, otherwise SynchronizationAccessException is thrown. The thread will be added to the wait set of o, that is, the thread waiting for notification on o. This notification must come from some other of thread that has obtained the lock on o and executes Monitor.Pulse(o) or Monitor.PulseAll(o). The notifying thread does not release its lock on o. After being notified, u must obtain the lock on o again before can proceed. When the call to Monitor.Wait returns, thread u will hold the lock on o just as before the call (example 166).

## Example 164 Mutual Exclusion
A Printer thread forever prints a (-) followed by a (/). If one creates and runs two concurrent printer threads by executing new Thread(new ThreadStart(Printer.Run)).Start() twice, then only one of them can hold the lock on object mutex at a time, so no other objects can be printed by (-) and (/) in one iteration of the loop, and the program must print --/-/-/, and so on. If the lock statement is removed, it may print --/-/-/---/-/-/, and so on. The call Util.Pause(100,300) pauses between 100 and 300 ms to enhance the inherent non-determinism of synchronized concurrency.

```csharp
class Printer {
    static readonly Object mutex = new Object();
    public static void Run() {
        for (;;) {
            lock (mutex) {
                Console.Write("-");
                Thread.Sleep(100, 300);
                Console.Write("/");
                Thread.Sleep(100, 300);
            }
        }
    }
}
```

## Example 165 Synchronized Methods in an Object
This bank has two accounts. The Transfer method is synchronized, so that only one thread can access the accounts at a time. If the lock statement is removed, the total sum may differ. 

```csharp
class Bank {
    private int account1;
    private int account2;
    public synchronized void Transfer(int amount) {
        account1 += amount;
        account2 -= amount;
    }
}
class Clerk {
    private Bank bank;
    public Clerk(Bank bank) {
        this.bank = bank;
    }
    public void Run() {
        for (;;) {
            bank.Transfer(10);
            Thread.Sleep(100);
        }
    }
}
Bank bank = new Bank();
Clerk clerk1 = new Clerk(bank);
Clerk clerk2 = new Clerk(bank);
new Thread(new ThreadStart(clerk1.Run)).Start();
new Thread(new ThreadStart(clerk2.Run)).Start();
```

## 21.3 Operations on Threads
The current thread, whose state is Running, may call these methods. More Thread methods are described in the .Net Framework Class.

Let u be an object of Thread:

-   * Thread.Sleep(n) sleeps for n milliseconds. The current thread becomes Sleeping, and after n milliseconds becomes Enabled. If it is 0, then it becomes Enabled immediately.
-   * Thread.CurrentThread() returns the current thread.
-   * u.Start() changes the state of u to Enabled, so that the delegate from which it was created will be called
-   * u.Interrupt() interrupts the thread u. If u is Running or Enabled, then its interrupted status is set to true. If u is Sleeping or Joining, or if u is Waiting, then it will Locking (and then throw ThreadruptedException).
-   * u.Join() waits for u to die. May throw ThreadruptedException if the current thread is interrupted waiting.
-   * u.Join(n) works as u.Join() but times out and returns after at most n milliseconds. There is no indication whether the call returned because of a timeout or because u died.

## 21.4 Operations on Locked Objects
A thread that holds the lock on an object o may call the following methods from the Monitor class in the System.Threading namespace. The methods throw ArgumentNullException if o is null and SynchronizationException if the thread does not hold the lock on o.

-   * Monitor.Wait(o) releases the lock on o, changes its state to Waiting, and adds itself to the set of threads waiting for notification on o. When notified by Pulse or PulseAll(if ever), the thread must obtain the lock on o, so when the call returns, it holds the lock on o. May throw ThreadruptedException if the thread is interrupted while sleeping.
-   * Monitor.Wait(o, n) works as Monitor.Wait(o), except that the thread will change state to Locking after n milliseconds regardless of or not there has been a notification on o. There is no indication whether the state change was caused by a timeout or because of a notification.
-   * Monitor.Pulse(o) chooses an arbitrary thread among those waiting for notification on o (if any) and changes the state of that thread to Locking. The chosen thread cannot actually obtain the lock on until the current thread has released it.
-   * Monitor.PulseAll(o) works as Monitor.Pulse(o), except that it changes the state of all threads waiting for notification on o.
