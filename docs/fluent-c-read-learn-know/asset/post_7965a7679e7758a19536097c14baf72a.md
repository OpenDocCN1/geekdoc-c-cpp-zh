
## EXPLICIT ITERATION

The C# for command is most often used to execute a block of statements a specific number of times. But the syntax is quite flexible, and it can be used for other things.

The initialization section of the statement is usually a declaration statement. The variable declared here is called the CONTROL VARIABLE.

The condition section is a single Boolean expression. The statement block will be executed until this expression evaluates to false.

If the statement is false to begin with, the statement block will never be executed at all.

The loop section typically manipulates the control variable in some way.

```
for (<initialization>; <condition>; <loop>)
<statement>
```

```
for (Int32 x = 1; x <=5; x++)
MessageBox.Show("x = " + x.ToString());
```

The control variable defined in the initialization section is only accessible within the for statement itself, not outside it.

## HOW'D YOU DO?

There are lots of ways to solve this one. Here are a few possibilities

```
for (Int32 x = 0; x != 5; x++)
MessageBox.Show(x.ToString());
```

- OR

```
for (Int32 x = 1; x < 6; x++)
MessageBox.Show(x.ToString());
```

- OR

```
for (Int32 x = 0; x < 5; x++, MessageBox.Show(x.ToString()))
;
```

In the real world, one of these will work better for you. The difference is the value of x the first time through the loop.

## MY VIEW

Because both the initialization and loop sections of a for command can contain multiple statements separated by commas, some programmers think it's cool to stick everything inside the for statement and do nothing in the statement block.

There are situations in which this syntax can save a lot of code, but there aren't many, and it's much harder to read and debug. Do yourself a favor: Use it only when it makes the code more understandable, not because it's what you think the big boys do.

## CONDITIONAL LOOPS

The for command contains a Boolean expression that is used to determine whether the statement block will be executed. But in a classic for loop, the condition section only evaluates the control variable. If your condition is more complicated, it's usually clearer to use one of the two conditional iterations statements that are specifically designed for that purpose.

```
do
{
    <statement>;
} while (<condition>);
```

The braces are always required in do and while statements.

```
while (<condition>)
{
    <statement>;
}
```

You need a semicolon after the while at the end of a do statement, but not at the end of the while statement. Do you know why?

```
do
{
    MessageBox.Show(x.ToString());
    x++;
} while (x <= 5);
```

```
while (x <= 5)
{
    MessageBox.Show(x.ToString());
}
```

### PUT ON YOUR THINKING HAT

The syntax of the two conditional loops is almost the same, and so is their behavior, with one important difference. Can you figure out what it is?

## HOW'D YOU DO?

![](img/1dcd2af4ae4fa0eb5cf4ed5437ff121a_206_0.png)

The difference between the do and while statements is when the condition is evaluated. The while statement evaluates the condition at the beginning of the loop, and if the condition is false, never executes the statement block at all. The do statement, on the other hand, evaluates the condition at the end of the loop, so the statement block will always be executed at least once.

```
Int32 x = 5;
do
{
    MessageBox.Show("Inside do");
} while (x < 5);

while (x < 5);
{
    MessageBox.Show("Inside while");
}
```

Can you predict what this code will do? That's right: it displays a single MessageBox with the text "Inside do". The MessageBox displaying "Inside while" never gets displayed.

## GOTO...WHEREVER

The goto statement gets a lot of bad press, and you will sometimes hear people say that it’s the sign of poorly designed code. I’ve even heard it said that it’s “evil” and its use should be avoided at all cost. That’s not entirely fair. It’s true that the goto statement is a heavy-handed tool, and like a chainsaw, you should use it with caution. But you wouldn’t trim a tree with a carving knife, and there are some situations (admittedly, only a few) where goto is an effective tool.

```
goto <label>;
```

In C#, a label is an identifier followed by a colon. The case xx: syntax of a switch command is an example, but you can create a label outside a switch using the same syntax.

### PUT ON YOUR THINKING HAT

The code snippet below would be a lot easier to understand if it were written as a switch statement, but there’s no way to duplicate the if (x == 2 | x == 3) condition as a constant. You could just duplicate the statement block for each value, but that’s a really bad idea from a maintenance standpoint. The goto command provides a way around the problem. Can you solve it?

```
if (x == 1)
x++;
else
{
if (x == 2 | x == 3)
x--;
else
x = y;
}
```

## HOW'D YOU DO?

Here's what we started with:

```
if (x == 1)
    x++;
else
    {
    if (x == 2 | x == 3)
        x--;
    else
        x = y;
    }
```

Here's a solution using switch and goto commands:

```
switch (x)
{
    case 1:
        x++;
        break;
    case 2:
        x--;
        break;
    case 3:
        goto case 2;
    default:
        x = y;
        break;
}
```

This sends control back to the code in the case 2 clause. It's not a perfect solution, but it works.

## HOW NOT TO USE GOTO

One of the reasons the goto statement gets such a bad rap that older languages didn't support conditional iteration. For example, without a do command, you'd have to do something like the following:

```
TopOfLoop:
x++;
if (x < 5)
    goto TopOfLoop;
```

That sample isn't too bad; you can understand what it's supposed to be doing fairly easily, but the other problem with the goto in older languages is that you could goto anywhere you wanted to stick a label. All too often the result was code that took hours to decipher, assuming you could figure it out at all. If you ever found yourself having to wonder where a goto statement leads, you can be pretty sure you're not looking at tight, well-written code; you're looking at a plate of spaghetti. Fix it.

![](img/1dcd2af4ae4fa0eb5cf4ed5437ff121a_211_0.png)

```
Retest:
if (x == 3)
{
x++;
goto Retest;
}
else
{
if (x == 4)
{
x--;
}
else
goto Problem;
}
```

> What's happening here? You can't possibly know without remounting an expedition into some other part of the code. This is a really, really bad idea.
