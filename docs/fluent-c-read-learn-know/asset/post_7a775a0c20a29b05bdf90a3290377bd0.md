
## EVENT ARGUMENTS

When we explored POCO events in Chapter 14, we saw that in .NET, an event always receives two parameters: the first is the object that raised the event, and the second is an instance of System.EventArgs or one of its descendants. That basic pattern doesn't change when you're working with routed events, but the second argument will be an instance of RoutedEventArgs or one of its descendants (RoutedEventArgs itself descends from EventArgs). Just as with POCO events, the argument can tell you a lot about the event and with routed events, it can also let you control how the event behaves. ## HOW'D YOU DO?

What do you think the Handled property does?

If Handled is set to true inside an event handler, the event will stop tunneling or bubbling. (But there's a way around this, as you'll see.)

MSDN says that InputEventArgs is used for “input-related events”. What do you think those are?

Input events are those that are triggered by a real person interacting with the application via the keyboard, mouse, stylus, or anything else. (Do you want a Microsoft Surface mouse as much as I do?)

Source is one of the parameters to a RoutedEvent. Why do you think the RoutedEventArgs class adds two more source properties?

Because the event can bubble up and down the element tree, the element that originally triggered the event (OriginalSource), the element that sent the event (Source), and the element handling the event (Sender) may not be the same.

OriginalSource and Sender will be the same in most situations, but OriginalSource will often be some component of a complex control (and in WPF, almost all elements are composites).

![](img/1dcd2af4ae4fa0eb5cf4ed5437ff121a_644_1.png)

The Source is the element that triggered the event.

The Sender is the object that's handling the event.

OriginalSource is often a Border or some other element that's part of the control's element tree.

## EXPLORING ROUTEDEVENTARGS

In reality, you won't have to use the Sender parameter and source properties all that often, but when you need them, you really need them, so let's spend a little time playing with them. To test your new and improved version of the method:

### CREATE A WPF PROJECT

You can call it anything you like.

### CREATE AN EVENT HANDLER

We'll start by building a routine that will display the three parameters. Here's my version, but you can do something fancier. If you're feeling inspired, you might try building a Window to display the values in TextBox elements. The important thing is that your method has the same signature as mine. (This is the standard signature for any routed event handler.)

```
private void ShowArguments(object sender, RoutedEventArgs e)
{
    StringBuilder eventDetailsSB = new StringBuilder();
    eventDetailsSB.AppendLine("Event: " + e.RoutedEvent.Name);
    eventDetailsSB.AppendLine("Sender: " + sender.GetType().ToString());
    eventDetailsSB.AppendLine("Source: " + e.Source.GetType().ToString());
    eventDetailsSB.AppendLine("Original: " + e.OriginalSource.GetType().
    ToString());

    MessageBox.Show(eventDetailsSB.ToString());
}
```

### TRIGGER THE EVENT

We'll look at different ways to trigger events in a minute, but for now, just set the Loaded event property of your main window (in the Events section of the Properties window in XAML view) to the name of your method.

### TEST IT

Run the application to make sure everything you've done so far is working properly. The Sender, Source and OriginalSource should all be the name of your Window class.

## ADD EVENT HANDLERS

There are three ways to add an event handler for a RoutedEvent in WPF. You can do it in XAML (that's the easy way), you can do it using some C# syntactic sugar, or you can do it by calling the AddHandler() method (that's the most flexible). We'll try all three.

### ADD A HANDLER IN XAML

The events that are defined by an object are exposed as properties in XAML. To add a handler, you just set the property to the name of your handler. There's an example in the Window code on the previous page, but let's replace the Loaded event with the MouseDown event. You can do this either directly in the XAML, or in the Properties window. (Visual Studio will keep them synchronized.)

### ADD A HANDLER USING THE C# OPERATOR

Almost as easy as adding an event handler in code is to use the C# += operator. The only thing you have to remember is that you assign a RoutedEventHandler to the event, so you'll have to create one in the code. The basic syntax is:

```
<object>.<Event> += new RoutedEventHandler(<Method>);
```

You can create the RoutedEventHandler separately, but there's no real point.

Add our generic handler to the button1.Click event in the MainWindow() constructor, after the call to InitializeComponent().

### ADD A HANDLER USING ADDHANDLER()

The final method to add an event handler is by calling the AddHandler() method that's defined by the UIElement class. There are two overloads of the AddHandler() method:

```
<object>.AddHandler(<Event>, new RoutedEventHandler(<Method>));
or
<object>.AddHandler(<Event>, new RoutedEventHandler(<Method>, <HandledEventsToo>));
```

You need to use the name of the event identifier here, which is the one with 'Event' at the end of its name.

We explore that second overload in a bit. For now, use the first AddHandler() method to add our generic handler to the MouseDown event of the ListBox1 element.

### TRY IT OUT

Your MainWindow() constructor should look like this now (allowing for differences in what you called your method and the elements on your form ).

```
public MainWindow()
{
    InitializeComponent();
    button1.Click += new RoutedEventHandler(ShowArguments);
    listBox1.AddHandler(MouseDownEvent, new RoutedEventHandler(ShowArguments));
}
```

Before you run the application, think about what you expect to happen if Click and MouseDown are bubbling events (and they are). What do you think will happen when you click on each of these places?

- On the Window, outside any control
- On the Button
- On the ListBox
- Anyplace else
- On a ListBoxItem

In theory, the MessageBox should be displayed for the MouseDown on the Window, and then the Click event on the Button, right? And the ListBox should display the MessageBox for the MouseDown, and then (when the event bubbles up to the Window), it should be displayed again. The Window should catch the MouseDown everywhere else. At least, that's what I expected to happen when I was first learning about routed events.

Now run the application and try clicking different things. The results aren't going to be what you expect; that doesn't mean you've made a mistake. What happens when you click on each of these parts of the form? (Make sure you click on the ListBox background, as well as on the items it contains.)
