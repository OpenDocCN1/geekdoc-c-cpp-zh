# # MODEL-VIEW-PRESENTER

The Model-View-Presenter (MVP) pattern is a direct descendant of MVC, and is a better match for platforms where the interface widgets themselves have significant functionality such as Windows desktop applications or Rich Internet Applications written using a technology such as Silverlight.

Dependency inversion is used to keep the Presenter ignorant of a specific view. This usually requires the definition of a custom interface, but might only mean that all Views need to descend from a common base class like a WPF window.

When the user interacts with the MVP View, it can raise events to which the Presenter responds (the preferred method), or call methods on the Presenter. The second approach has the disadvantage of coupling the View to the Presenter, but in reality, most Views are designed for a specific Presenter.

Because the MVP View can handle some input itself, the MVP Presenter is primarily responsible for implementing the data-handling logic required to mediate between the View and the Model.

The MVP View consists of the interface widgets and the code to forward actions to the Presenter. Unlike a MVC View, an MVP View can receive input directly, and handle functions that only concern the UI (like changing the size of a pane in the window, for example), without consulting the Presenter.

The View and Model have no knowledge of one another. If any widgets are data-bound, they are bound to properties of the Presenter, not the Model.

As in all of the presentation patterns, the Model is only responsible for maintaining the data.
