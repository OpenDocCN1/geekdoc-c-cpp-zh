
## EXTENDING THE DEFAULT

Despite what the MSDN documentation says about the new and override keywords, neither one actually extends the default implementation provided by the base class, at least not in the sense of “do that, and do this too”. But extending the implementation in that sense is a perfectly reasonable and sometimes necessary thing to do, and the base keyword allows you to do just that.

```
public class MyParent()
{
    public virtual void SayHello()
    {
        MessageBox.Show("Hello");
    }
}
```

```
public class MyChild() : MyParent
{
    public override void SayHello()
    {
        base.SayHello();
        MessageBox.Show("World");
    }
}
```

```
MyChild x = new MyChild();
x.SayHello();
```

This code calls the MyChild.SayHello() method displays two MessageBox windows.

That's a reasonable guess, but in fact it more closely resembles the syntax for inheritance:

```
public MyClass : MyBase
{
    MyClass() : base()
    {
        //more code here
    }
}
```

If the constructor takes arguments, you put them within the parentheses, like any method call. (Constructors are, after all, just a special type of method.)

## PREVENTING INHERITANCE

At the opposite end of the inheritability spectrum from the abstract classes and members that must be inherited are sealed classes. The syntax to seal a class is straightforward. Just mark a class with the sealed keyword and other classes can't inherit from it:

```
public sealed class mySealed {}
```

Classes are easy, but those tricky keywords new and override get involved when you want to seal individual methods within a class. Here's how that works:

```
public class myBase
{
    public virtual void DoSomething() {}
    public void DontTouchMe() {}
}
```

A non-virtual method is effectively sealed, but...

...it can be re-defined using the new keyword, and...

```
public class myNew : myBase
{
    public new void DontTouchMe() {}
}
```

```
public class mySealed : myBase
{
    public sealed override void DoSomething() {}
}
```

...a virtual method can only be sealed for further inheritance when combined with override (not new).

## TO SEAL OR NOT TO SEAL...IS THAT REALLY THE QUESTION?

You can get yourself in a terrible muddle over when to seal, what to seal, when to virtualize, and whether to override or replace functionality. And, as always, the answers aren't easy. In fact, there's a huge debate in the professional development community over sealing. We call these "religious debates" (and they happen a lot in the programming world) because people get dogmatic and throw around words like "evil". If you're interested in the great debate, here are two blogs with well-presented arguments to get you started:

Chris Sells at www.sellsbrothers.com/Posts/Details/12564
Eric Lippert at blogs.msdn.com/b/ericlippert/archive/2004/01/22/61803.aspx

My advice? Relax. Here are the rules of thumb I use:

- When you're designing a hierarchy, it will be obvious that some classes are intended to be base classes.
- If an obvious base class can or should provide some default functionality, make it a concrete class with virtual methods; otherwise, make it abstract.
- Leave your remaining concrete classes unsealed so that they can be extended with new functionality, but leave their methods sealed (non-virtual).

My reasoning for that last point might need some explanation--as Eric Lippert points out, a virtual method can be dangerous when the class gets modified (and it will). Unsealing a class later if you need to won't have any side effects. But sealing it later when you discover you were wrong could break other code. So making the class inheritable but the methods non-virtual is the path of least resistance. You don't waste a lot of time during initial development testing for things that might never happen, but you can always change your mind down the road with minimal pain.

## EXTENDING CLOSED CLASSES

There's one last twist to working with classes in .NET: extension methods. EXTENSION METHODS behave as though they were standard instance methods, but they're defined in a separate class (and usually a separate namespace). They allow you to add new methods to a class without re-compiling or inheriting from it, so you can extend the functionality of sealed classes and classes, like those in the BCL, that you can't or shouldn't change directly. Let's look at how they work:

- It isn't required, but you'll usually define your extension methods in a new namespace in order to simplify referencing them in your code. You'll usually call the namespace something like <Project>Extensions.
- Declare a public static class to contain the methods.
- Declare each method using the public static keywords as well.
- The first parameter of the method must be the name of the class the method extends, preceded by the keyword this. You omit this parameter when you call the method in your code.
- In the code that's going to use the extension method, reference the namespace you declared with the standard using <namespace>; syntax
- You can call the method just as though it were an instance method. (Remember, you omit that first parameter specifying the class.)

![](img/1dcd2af4ae4fa0eb5cf4ed5437ff121a_429_0.png)

## HOW'D YOU DO?

How'd you do? It doesn't matter if you chose a different name for the namespace. And IntelliSense will help you with matching all the brackets, too. But did you get the declarations correct?

```
namespace RecipeSystemExtensions
{
    public static class RecipeExtensions
    {
        public static void PrintRecipeCard(this Recipe)
        {
        }
    }
}
```

To call the method, you'll need to reference the namespace:

```
using RecipeSystemExtensions;
```

Then it behaves just like a normal instance method:

```
Recipe myRecipe = new Recipe();
myRecipe.PrintRecipeCard();
```

## UNDER THE MICROSCOPE

You won't create extension methods nearly as often as you'll use the ones created for you in the BCL. But it's good to know that they're there when you need them. But there are a few things to be aware of:

You cannot re-define a method using extension methods. The compiler will always give precedence to the instance method, so your override will simply never be called.

You can define a method with a different signature, but you can't use the base keyword and you can't reference private or protected members of the class you're extending.
