In the example on the previous page, I used the this keyword to avoid a programmer error (as opposed to a programming error). But this isn't always optional; you'll use it whenever you need to refer to the instance of the object from within the method. Say, for example, that once the scheduling component of our desert application is implemented, it exposes a method called Schedule that takes as an argument the component to be scheduled. The method signature would look like this:

```
.public void Schedule(Component component)
```

Inside the Allocate() method, you could call the Schedule() method and pass the current Component using the this keyword:

```
Schedule(this);
```

BEST PRACTICES — BUILDING METHODS

You should try to keep the method body to less than 50 statements. More than that and it becomes difficult to read.

You should try to keep the number of parameters to less than 6. After 3 or 4, the method becomes tedious to call. After 6 or 7, it's almost impossible to keep everything straight, even with the help of Intellisense. (In the next chapter we'll look at Structures, which are a good way to avoid the endless parameter list.)

As a general rule, every method should have a single return statement. Some people will argue that it's an inviolable rule, but you've already seen me break it by adding a return statement for invalid arguments. My rule is "aim for one return, unless adding more makes the code easier to understand. In my world, "easier to understand" is always a higher priority than following conventional heuristics.
