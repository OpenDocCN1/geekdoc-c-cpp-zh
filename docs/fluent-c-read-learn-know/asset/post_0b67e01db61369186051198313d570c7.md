
## AS-IS POLYMORPHISM

We've seen that you can cast from a type to one of its ancestors or an interface it implements by prefixing the object with the destination type in parentheses:

```
(NewType) oldType
```

We've also seen that the Object.GetType() method (inherited by every type in the .NET Framework) returns an instance of the Type class, so you can do something like this to check whether two objects are of the same type:

```
if (MyStandardRecipe.GetType() == MyRecipe.GetType())
```

This test certainly has its place, but it compares the types of two objects, and it's an absolute test. What if you wanted to test whether an object is a certain type, but don't have an instance of that type lying around? You could use the Name property of the Type object returned by GetType():

```
if (MyStandardRecipe.GetType().Name == "StandardRecipe")
```

That's a little more useful, but it still doesn't tell you whether your object can be safely cast to the desired type. That's where the is operator comes in:

```
if (MyRecipe is BakedGoodRecipe)
```

Notice that you're using the type name here as an identifier, not a string. Because type identifiers are known to the editor, that makes it a lot less prone to typos.

Even better, the is operator returns true if the specified object has an IsA relationship with the specified type, which as you know, isn't quite the same as being an instance of the type. It can be used to test an object before casting:

```
if (MyStandardRecipe is Recipe)
    Recipe myDish = (Recipe) MyStandardRecipe;
```

The C# as operator performs a similar operation: It casts the object if possible, or returns a null (rather than throwing an exception) if the cast isn't possible:

```
BakedGoodRecipe myBread = theRecipe as BakedGoodRecipe;
if (myBread != null)
...
```

You still need to test for null, but you've avoided the possibility of displaying one of those scary runtime exceptions to your application user.

## TYPE MODIFIERS

We've seen that modifiers like public and private control the visibility of a type member. C# exposes another set of modifiers and keywords that control how types interact within a class hierarchy.

### STATIC

The static keyword declares a member that belongs to the type itself, not an instance of the type. If all the members of a class are static, the class itself can also be declared static. You cannot create an instance of a static class.

```
public class Recipe
{
    public static Int32 TabsToTsps(Int32 tabs)
    {
        return tabs * 3;
    }
}
```

```
Int32 asTsps = Recipe.TabsToTsps(15);
```

Static members are called directly on the type.

### SEALED

The sealed keyword, which only applies to classes, indicates that the class cannot be used as the base for any other class.

```
public sealed class Recipe
{
}
```

```
public NewRecipe : Recipe
{
}
```

You can't do this...

### ABSTRACT

The abstract keyword declares a member that must be implemented by an inheriting class, or a class all of whose members must be implemented by an inheriting class.

```
public abstract class Recipe
{
    public abstract void DoSomething();
}
```

The abstract definition doesn't include any implementation code.

```
public NewRecipe : Recipe
{
    public override void DoSomething()
    {
        MessageBox.Show("Something!");
    }
}
```

The defining class must include an implementation and use the override keyword.

### VIRTUAL

While the abstract keyword indicates a class or member that must be implemented by the child class, members declared as virtual can be overridden, but need not be.

```
public class Recipe
{
    public virtual void DoSomething()
    {
        MessageBox.Show("Something!");
    }
}
```

```
public NewRecipe : Recipe
{
}
```

The inheriting class can provide a new implementation, but it doesn't have to.

```
public RecipeChild : Recipe
{
    public override void DoSomething()
    {
        MessageBox.Show("Something Else!");
    }
}
```

## TYPES OF TYPES

The abstract, virtual and sealed modifiers let you place types and members along a continuum from the completely abstract class that provides only the definition of a class and no implementation, to the completely concrete sealed class that implements all of its members and cannot be inherited.

### ABSTRACT CLASSES

When a class is marked as abstract, the class must be inherited. It cannot be instantiated directly.

### VIRTUAL MEMBERS

A class with virtual members provides a default implementation, but the members can be replaced in classes that inherit from it using the new or override keywords.

### STATIC CLASSES & MEMBERS

In theory, a static class can be inherited and a static member can be overridden, but best practice dictates that they should also be sealed.

### SEALED MEMBERS

Sealed members cannot be inherited, although the class itself can.

### SEALED CLASSES

Sealed classes cannot be inherited at all.

## STATIC CLASSES & MEMBERS

Both classes and class members can be marked as static. static members belong to the class as a whole, not a particular instance. That means that there can only be a single instance of a static property, and static members can be called without creating an instance. (In fact, they’re called on the class itself. We’ve already seen several examples of static members.)

A static class can only contain static members. Static classes cannot be instantiated, but they can be inherited unless they’re also marked as sealed (as they almost always should be).

You probably won’t find yourself using the static keyword all that often, but it is useful in certain situations:

- WHEN THERE SHOULD ONLY EVER BE A SINGLE INSTANCE OF THE OBJECT.
  This is called the SINGLETON PATTERN. The .NET Framework Application class, for example, provides methods and properties that let you manage your application as a whole. Since there’s only ever one instance of the application itself within the application scope, Application is a static class.

- TO GROUP GENERAL-PURPOSE CONSTANTS AND METHODS
  As an example, the .NET Framework System.Math class provides a constants like PI and general mathematical functions like calculating the natural logarithm of a number. In our cooking example, constants like the number of teaspoons in a tablespoon or a cup might be a good candidate for a static class.

- TO CONTAIN GLOBAL VARIABLES
  As you’ve seen, one of the basic principles of OOP is encapsulation, the hiding of information from outsiders. It’s a principle for a good reason, but sometimes you need certain values to be available to every object in the application. The name of the current user, for example, or the user’s interface preferences are good examples of this kind of information. A static class is a good option for storing this kind of information.
