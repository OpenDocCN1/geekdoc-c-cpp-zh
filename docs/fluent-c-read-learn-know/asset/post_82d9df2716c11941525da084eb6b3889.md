## ABSTRACT CLASSES & INTERFACES

An abstract class is very like an interface. It defines the members that must be implemented by an inheriting class, but doesn't usually provide any implementation. So how do you decide which to use? In practice, it isn't that difficult. Just remember that interfaces represent a CanDo relationship, while classes (abstract or otherwise) represent an IsA relationship.

Let's look at an example. Remember that weekly production schedule that Neil and Gordon need to prepare? We've added it to the basic Recipe class hierarchy. The only relationship the Schedule class has to the other classes in the hierarchy is that it HasA collection of Recipe items, but, like a Recipe, it can print itself.

IPrintable is clearly an interface. It's something that otherwise unrelated classes CanDo.

RecipeBase defines members that all recipes must implement in order to be a recipe. A class that inherits from RecipeBase IsA recipe.

![](img/1dcd2af4ae4fa0eb5cf4ed5437ff121a_419_0.png)

### MAKE A NOTE

By convention, an abstract class should have “Base” at the end of its name, as in RecipeBase (or, as we’ll see, .NET Framework classes like ButtonBase). Classes that descend from the abstract class should have the object appended to their names: StandardRecipe, or ToggleButton.

## ABSTRACT SYNTAX

![](img/1dcd2af4ae4fa0eb5cf4ed5437ff121a_420_0.png)

You can add an abstract class from the Class Designer, but you can't define abstract members. You have to do that in code.

![](img/1dcd2af4ae4fa0eb5cf4ed5437ff121a_420_1.png)

Where the Class Designer really comes into its own when working with abstract classes is in implementing the necessary members in their descendents. Simply right-click an inheriting class and choose Implement Abstract Class from the Intellisense menu.

As you might expect, the code for implementing an abstract class or abstract member looks very like the code for an interface. Only the signature is defined, without any implementation, marked with the abstract keyword.

```csharp
public abstract class myClass
{
    public int myProperty {get; set;}
    public abstract int myAbstractProperty {get; set;}
    public abstract void DoSomething();
}
```

Abstract classes can contain concrete code. This is an auto-implemented non-abstract property.

Only the abstract keyword sets this property apart from the concrete version.

The compiler will complain if you try to put code in an abstract method declaration.

## SEMI-ABSTRACT CLASSES

C# doesn't restrict you to “re-implement everything” (abstract) classes or “re-implement nothing” (concrete) classes. The virtual keyword allows (but doesn't require) a derived class to re-implement the method. This allows you to provide a default implementation of your methods. If the derived class doesn't redefine the method using the new or override keywords, the implementation provided by the base class is used.

The new and override keywords can be tricky. Here's how MSDN defines them:

- new is used to hide an inherited member from a base class member
- override is required to extend or modify the abstract or virtual implementation of an inherited member

Doesn't really tell you much, does it? What's the difference between “extend or modify” and “hide”?
