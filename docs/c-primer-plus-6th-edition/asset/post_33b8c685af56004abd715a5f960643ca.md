## valarray Upgrade

The valarray template was developed independently of the STL, and its original design precluding using range-based STL algorithms with valarray objects. C++11 adds two functions, begin() and end(), that each take a valarray argument. They return iterators to the first and one past the last element of a valarray object, allowing one to use range-based STL algorithms (see Chapter 16).

## export Departs

C++98 introduced the export keyword in the hope of creating a way to separate template definitions into interface files containing the prototypes and template declarations and implementation files containing the template function and methods definitions. This proved to be impractical, and C++11 ends that for export. However, the Standard retains export as a keyword for possible future use.

C++11 removes that requirement:

## The Rvalue Reference

The traditional C++ reference, now called an lvalue reference, binds an identifier to an lvalue. An lvalue is an expression, such as a variable name or a dereferenced pointer, that represents data for which the program can obtain an address. Originally, an lvalue was could appear on the left side of an assignment statement, but the advent of the const modifier allowed constructs that cannot be assigned to but which are still addressable:

```
* pt = new int;
const int b = 101; // can't assign to b, but &b is valid
int & n = n; // n identifies datum at address &
int & rt = *pt; // pt identifies datum at address pt
const int & rb = b; // b identifies datum at address &
```

C++11 adds the rvalue reference (discussed in Chapter 8), indicated by &&, that can bind to values—that is, values that can appear on the right-hand side of an assignment expression for which one cannot apply the address operator. Examples include literal constants (like C-style strings, which evaluate as addresses), expressions such as x+y, and function return values, providing the function does not return a reference:

```
int x = 10;
int y = 23;
int && r1 = 13;
int && r2 = x + y;
double && r3 = std::sqrt(2.0);
```

Note that r2 really binds to the value to which x + y evaluates at that time. That is, r2 binds to the value 23, and r2 is unaffected by subsequent changes to x or y.

Interestingly, binding an rvalue to an rvalue reference results in the value being stored in a location whose address can be taken. That is, although you cannot apply the & operator to 13, you can apply it to r1. This binding of the value to particular addresses is what makes it possible to access the data through the rvalue references.

Listing 18.1 provides a short example illustrating some of these points about value references.

## Move Semantics and the Rvalue Reference

One of the main reasons for introducing the rvalue reference is to implement move semantics, the next topic in this chapter.

Now let's move on to topics we haven't discussed. C++11 enables a technique called move semantics. This raises some questions, such as what are move semantics, how C++11 enable them, and why do we need them? We'll begin with the last question.

## The Need for Move Semantics

Let's look into the copying process as it worked prior to C++11. Suppose we start with something like this:

```
vector<string> vstr;
// build up a vector of 20,000 strings, each of 1000 characters
```

```
vector<string> vstr_copy1(vstr); // make vstr_copy1 a copy memory allocation, so they
```

Both the vector and the string class use dynamic memory, so they will have copy constructors defined that use some version of new. To initialize vstr_copy1 object the vector<string> copy constructor will use to allocate memory for 20,000 objects, and each string object, in turn, will call the string copy constructor, which will use to allocate memory for 1000 characters.Then 20,000 characters will be copied from the memory controlled by vstr to the memory controlled by vstr_copy1. That lot of work, but if it's to be done, then it's to be done.

But does it "got to be done?"There are times when the answer is no. For instance, suppose we have a function that returns a vector<string> object:

```
vector<string> allcaps(const vector<string>& & vs)
{
vector<string> temp;
// code that stores an all-uppercase version of vs in temp
return temp;
}
```

Next, suppose we use this way:

```
vector<string> vstr;
// build up a vector of 20,000 strings, each of 1000 characters
vector<string> vstr_copy1(vstr); // #1
vector<string> vstr_copy2(allcaps(vstr)); // #2
```

Superficially, statements #1 and #2 are similar; each uses an existing object to initialize a new vector<string> object. If we take this code at face value, allcaps() creates a temp object managing 20,000,000 characters, the vector and string copy constructors go through the effort of creating a 20,000,000-character duplicate, then the program deletes the temporary object returned by allcaps(). (A really uninspired compiler even copy temp to a temporary return object, delete temp, and then delete the return object.) The main point is that a lot of effort is wasted. Because the temporary object is deleted, it would be better if it could transfer ownership of the data to vstr_copy2? That is, instead of copying 20,000,000 characters to a new location and deleting the old location, leave the characters in place and attach the vstr_copy2 label to them. This would be similar to what happens when you move a file from one directory to another: Such an approach is called move semantics. Paradoxically, move semantics actually avoids moving the data; it just adjusts the bookkeeping.

To implement move semantics, we need a way to let the compiler know when it needs to do a real copy and when it doesn't. Here's where the rvalue reference comes into play. We define two constructors: one, the regular constructor, can use the const lvalue reference as parameter. This reference will bind to lvalue arguments, as vstr in statement #1.The other, called a move constructor, can use an rvalue reference, and can bind to rvalue arguments, as allcaps() in statement #2.The copy constructor can do deep copy, while the move constructor can just adjust the bookkeeping.A move constructor may alter its identity in the process of transferring ownership to a new object, and this implies that an rvalue reference should not be const.
