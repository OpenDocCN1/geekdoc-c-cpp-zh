
## Generic Programming

Here is the output of the program in Listing 16.11:

fine fish fashion fate
fine fish fashion fate busy bays
silly singers fine fish fashion fate busy bays

The first copy() copies the four strings from s1 into words. This part works in base because words is declared to hold four strings, which equals the number of strings being copied. Then the back_insert_iterator inserts the strings from s2 into front of the end of the words array, expanding the size of words to six elements. Finally, the insert_iterator inserts the two strings from s3 in front of the first element of words. If the program attempted to copy s2 and s3 into words using words.end() and words.begin() as iterators, there would be no room for the new data, and the program would probably abort because of memory violations.

If you're feeling overwhelmed by all the iterators, keep in mind that they will make them familiar. Also keep in mind that these predefined iterators expand the generality of the STL algorithms. Thus, not only can you copy() copy information from one container to another, it can copy information from a container to the output stream and from the input stream to another container. And you can use copy() to insert material into another container. So you wind up with a single function doing the work of many. And because copy() is just one of several STL functions that use an iterator, the predefined iterators multiply the capabilities of those functions, too.

## Kinds of Containers

The STL has both container and container types. The concepts are general categories with names such as container, sequence container, and associative container. The container types are templates that you can use to create specific container objects. The original 11 container types are deque, list, queue, priority_queue, stack, vector, map, multimap, set, multiset, and bitset. This chapter does not discuss bitset, C++11 adds forward_list, unordered_map, unordered_set, and unordered_multiset.

## Container Concepts

No type corresponds to the basic concept, but the concept describes elements common to all container classes. A container is an object that stores other objects, which are all of a single type. The container class doesn't guarantee that its elements are stored in any particular order or that the order doesn't change. In particular, the type has to be copyible and assignable—unless the class definition makes one or both of the copy constructor and assignment operator. C++11 refines the concepts, adding terms as CopyInsertable and MoveInsertable, but we'll take a more precise, overview. All containers provide certain features and operations. Table 16.5 summarizes several of these common features. In the table, x represents a container (such as vector), T represents the type of object stored in the container, a represents values of type x (that is, if x represents vector<int>, u is vector<int>).

The Complexity column in Table 16.5 describes the time needed to perform an operation. This list lists three possibilities, from fastest to slowest, are as follows:

- Compile time
- Constant time
- Linear time

If the complexity is compile time, the action is performed during compilation and uses no execution time. A constant complexity means the operation takes place during runtime but doesn't depend on the number of elements in an object. Linear complexity means the time is proportional to the number of elements. If a and b are containers, a == b has linear complexity because the == operation may have to be applied to each element of the container. Actually, that is a worst-case scenario. If two containers have different sizes, no individual comparisons need to be made.

## Constant-Time and Linear-Time Complexity

Imagine a long, narrow box with large packages in a line, and suppose the box is open at one end. Suppose your task is to unload the package at the end. This is a constant task. Whether there are 10 packages or 100 packages behind the end one at the end makes no difference.

Now suppose your task is to fetch the package at the closed end of the box. This is a linear task. If there are 10 packages altogether, you have to unload 10 packages to get the end at one closed end. If there are 100 packages, you have to unload 100 packages at the end. Assuming you are a tireless worker who can move only 1 package at a time, this task will take 10 times longer than the first one.

Now suppose your task is to fetch an arbitrary package. It might happen that the package you are supposed to get is the first one at hand. However, on the average, the number of packages you have to move is still proportional to the number of packages in the container, so the task still has linear-time complexity.

Replacing the long, narrow box with a similar box having open sides would change the task to constant-time complexity because you could move directly to the desired package and remove it without moving the others.

## The string Class and the Standard Template Library

The idea of time complexity describes the effect of container size on execution ignores other factors. If a superhero can unload packages from a box with one end 1,000 times faster than you can, the task still has linear-time complexity. In this case, the superhero's linear time performance with a closed box (open end) would be faster than your constant time performance with an open box, as long as the boxes didn't have too many packages.

Complexity requirements are characteristic of the STL. Although the details of an implementation may be hidden, the performance specifications should be public so you know the computing cost of doing a particular operation.
