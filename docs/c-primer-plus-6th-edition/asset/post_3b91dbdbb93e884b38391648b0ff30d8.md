
# Chapter 9 Memory Models and Namespaces

C++ has altered the rules for constant types to make life easier for you. Suppose, for example, you have a set of constants that you'd like to place in a header file and that you use this header in several files in the same program. After the preprocessor includes the header file in each source file, each source file will contain definitions like this:

```cpp
const int fingers = 10;
const char * warning = "Wak!";
```

If global constants had external linkage as regular variables, would this be an error because of the one definition rule. That is, only one file can contain the declaration, and the other files have to provide reference declarations using the extern keyword. Moreover, the declarations without the extern keyword would be able to initialize values:

```cpp
// would be required if const had external linkage
extern int fingers; // can't be initialized
extern const char * warning;
```

You would need one set of definitions for one file and a different set of declarations for other files. Instead, because externally defined const has internal linkage, you can use the same declarations in all files.

Internal linkage also means that each file has its own set of constants rather than sharing. Each definition is private to the file that contains it. This is why it's a good idea to put constant definitions in a header file. That, as long as you include the header file in two source code files, they receive the same set of constants.

If, for some reason, you want to make a constant external linkage, you can use the extern keyword to override the default internal linkage:

```cpp
extern const int states = 50; // definition with external linkage
```

You must use the extern keyword to declare the constant in all files that use the constant. This differs from regular external variables, which you don't have to use the extern when you define a variable, but you use extern in other files using the variable. Keep in mind, however, now that a single const is shared among files, only one can use a file initialization.

When you declare a const within a function or block, it has block scope, which means the constant is usable only when the program is executing code within the block. This means that you can create constants within a function or block and not to worry about the names conflicting with constants elsewhere.

# Functions and Linkage

Like variables, functions have linkage properties, although the selection is more limited than variables. C++, like C, does not allow you to define one function inside another, so all functions automatically have static storage duration, meaning they are all present as long as the program is running. By default, functions have external linkage, meaning they can be shared across files. You can, in fact, use the keyword extern in a function prototype to indicate that the function is defined in another file, but that is optional. (For the program to find the function in another file, that file must be one of the files compiled as part of the program or a library file searched by the linker.) You can also use the keyword static to give a function internal linkage, confining it to a single file. You would apply this keyword to the prototype and to the function definition:

```cpp
static int private (double x);
...
static int private (double x)
{
...
}
```

This means the function is known only in that file. It also means you can use the same name for another function in a different file. As with variables, a static function overrides an external definition for the file containing the static declaration, so a file containing a static function definition will use that version of the function even if there is an external definition of a function that has the same name.

The one definition rule extends to non-inline functions, too. Therefore every program shall contain exactly one definition of every non-inline function. For functions with external linkage, this means that only one file of a multiple program can contain the function definition. (This file could be a library file rather than you supply.) However, each file that uses the function should have the function prototype.

Inline functions are excepted from this rule to allow you to place inline function definitions in a header file. Thus, each file that includes the header file ends up having the inline definition. However, C++ does require that all the inline definitions for a particular function be identical.

# Where C++ Finds Functions

Suppose you call a function in a particular file in a program. Where does C++ look for the function definition? If the function prototype in file indicates that the function is static, the compiler (and the linker) looks in all the program files. If it finds two definitions, the compiler sends you an error message because you have only one definition for an external function. If it fails to find any definition in the files, the function searches the libraries. This implies that if you define a function that has the same name as a library function, the compiler uses your version rather than the library version. (However, C++ reserves the names of the standard library functions, so you shouldn't reuse them.) Some compiler-linkers need explicit instructions to identify which libraries to search.

# Language Linking

Another form of linking, called language linking, affects functions. First, a little background. A linker needs a different symbolic name for each distinct function. In C, this is simple to implement because there can be only one C with a given name. For internal purposes, a C compiler might translate a C function name such as spiff to _spiff. The C approach is termed C++ language linkage. However, C++ can have several functions with the same C++ name that have to be translated to symbolic name mangling or name decoration (as discussed in Chapter 8) to generate different names for overloaded functions. For example, it can convert spiff(int) to spiff_i, and spiff(double) to _spiff_d.

When the linker looks for a function to make a function call, it uses a different look-up method than it does for a C library in a C++ program. For example, suppose you have this code:

```cpp
spiff(); // want spiff from C library
```

Its hypothetical symbolic name in the C library is _spiff, but for our hypothetical linker, the C++ look-up connection is different. To get around this, you can use the function prototype to identify which protocol to use:

```cpp
extern C void spiff();      // use C protocol for name-up
extern void spiff();         // use C++ protocol for name-up
extern "C++" void spiff();  // use C++ protocol for name-up
```

The first and third examples use C++ language linkage; the second does by default. C and C++ language linkage are the only specifiers required by the C++ Standard. Implementations have the option of providing additional language specifies.

# Storage Schemes and Dynamic Allocation

You've seen the five schemes, excluding threaded memory, C++ uses to allocate memory for variables (including arrays and structures). They do not apply to allocate memory using the C++ new operator (or using the older malloc() function). We call that kind of memory dynamic memory. As you saw in Chapter 4, dynamic memory is controlled by the new and delete, not by scope and linkage rules. Thus, dynamic memory can be allocated from one function and freed from another.
