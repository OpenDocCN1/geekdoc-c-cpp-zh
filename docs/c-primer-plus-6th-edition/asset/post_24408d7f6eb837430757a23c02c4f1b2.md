# Header Management

You should include a header file just once in a file. That might seem to be an easy thing to remember, but it's possible to include a header file several times without knowing you. For example, you might use a header file that includes another header file. There's a standard C/C++ technique for avoiding multiple inclusions of header files. It's based on the preprocessor #if not defined directive. A code segment like the following means "process the statements between the #ifdef and #endif only if the name COORDIN_H_ has not been defined previously by the preprocessor #define directive:

```cpp
#ifndef COORDIN_H_
...
#endif
```

Normally, you use the #define statement to create symbolic constants, in the following:

```cpp
#define MAXIMUM 4096
```

But simply using #define with a name is enough to establish that a name is defined, as in the following:

```cpp
#define COORDIN_H_
```

The technique that Listing 9.1 uses is to wrap the file contents in an #ifdef:

```cpp
#ifndef COORDIN_H_
#define COORDIN_H_
// place include file contents
#endif
```

The first time the compiler encounters the file, the name COORDIN_H_ should be undefined. (I chose a name based on the include filename, with few underscore characters tossed to create a name that is unlikely to be defined elsewhere.) That being the case, the compiler looks at the material between the #ifdef and the #endif, which is what you want. In the process of including the material, the compiler reads the line definition COORDIN_H_. The compiler notes that COORDIN_H_ is defined and skips to the line following the #endif. Note that this method does not keep the compiler from including a file twice. Instead, it makes the compiler ignore all but the first inclusion. Most of the standard C and C++ header files use this guarding scheme. Otherwise you might get the same structure twice in one file, and will produce a compile error.

# Listing 9.3 file2.cpp

```cpp
// file2.cpp -- contains functions called in file1.cpp
#include <iostream>
#include <cmath>
#include <coord.h> // structure templates, function prototypes

// convert rectangular to polar coordinates
polar rect_to_polar(rect xypos)
{
    using namespace std;
    polar answer;

    answer.distance =
    sqrt(xypos.x * xypos.x + xypos.y * xypos.y);
    answer.angle = atan2(xypos.y, xypos.x);
    return answer; // returns a polar structure
}

// show polar coordinates, converting angle to degrees
void show_polar(polar dapos)
{
    using namespace std;
    const double Rad_to_deg = 57.29577951;

    cout << "distance = " << dapos.distance;
    cout << ", angle = " << dapos.angle * Rad_to_deg;
    cout << " degrees\n";
}
```

# Scope and Linkage

Scope describes how widely visible a name is in a file. For example, a variable defined in a function can be used in that function but not in others, whereas a variable defined in a function above the function can be used in all the. Linkage describes how a name can be shared in different units. A name with external linkage can be shared across files, and a name with internal linkage can be shared by functions within a single file. Names of automatic variables have no linkage because they are not.

A C++ variable can have one of several scopes. A variable that local scope (also block scope) is known only within the block in which it is defined. Recall that a block is a series of statements enclosed in braces. A function, for example, is a block, but you can have other blocks nested within the function body. A variable that has global scope (also file scope) is known throughout the file after the point where it is defined. Automatic variables have local scope, and a static variable can have either scope, depending on how it is. Names used in a function prototype scope are known just within the parentheses enclosing the argument. (That's why it doesn't really matter what they are or if they are present). Members of a class have class scope (see Chapter 10, "Objects and Classes"). Variables declared in a namespace scope (Now that namespaces have been added to the C++ language, the global scope has become a special case of class scope or namespace scope, including global scope, but they can't have local scope. (Because a function can't be defined inside a block, if a function were to have local scope, it could only be known to itself and hence couldn't be called by another function. Such a function couldn't.)

The various C++ storage choices are characterized by their duration, their scope, and their linkage. Let's look at C++ storage classes in terms of these properties. We begin by examining the situation before namespaces were added to the mix and then see how namespaces modify the picture.
