
## Beginning with a Simple Class 719

Ordinarily, C++ requires references and pointer types to match the assigned types, but this rule is relaxed for inheritance. However, the relaxation is just in one direction. You cannot assign base-class objects and addresses to derived-class references and pointers:

```
TableTennisPlayer player("Betsy", "Bloop", true);
RatedPlayer & rr = player;      // NOT ALLOWED
RatedPlayer * pr = player;      // NOT ALLOWED
```

These sets of rules make sense. For example, consider the implications of having a base-class reference to a derived object. In this case, you can use the base-class reference to invoke base-class methods for the derived-class object. Because the derived class inherits the base-class methods and data members, this causes no problems. Now consider what would happen if you could assign a base-class object to a derived-class reference. The derived-class reference would be able to invoke derived-class methods for the base object, and that could cause problems. For example, applying the RatedPlayer::Rating() method to a TableTennisPlayer makes no sense because the TableTennisPlayer object doesn't have a rating.

The fact that base-class references and pointers can refer to derived-class objects has some consequences. One is that functions defined with base-class reference or pointer arguments can be used with either base-class or derived-class objects. For instance:

```cpp
void Show(const TableTennisPlayer & rt)
{
	std::cout << "Name: " << rt.Name();
	std::cout << "Table: ";
	if (rt.HasTable())
		std::cout << "yes\n";
	else
		std::cout << "no\n";
}
```

The formal parameter rt is a reference to a base class, so it can refer to a base-class object or a derived-class object. Thus, you can use Show() with either TableTennisPlayer or RatedPlayer argument:

```cpp
TableTennisPlayer player1("Tara", "Boom", false);
RatedPlayer player1("Mallory", "Duck", true);
Show(player1); // works with TableTennisPlayer argument
Show(player1); // works with RatedPlayer argument
```

A similar relationship would hold for a pointer-to-base-class formal parameter; it could be used with either the address of a base-class object or the address of a derived-class object as an argument:

```cpp
void Show(const TableTennisPlayer * pt); // function with pointer parameter
TableTennisPlayer player1("Tara", "Boom", false);
RatedPlayer player1("Mallory", "Duck", true);
Show(&player1); // works with TableTennisPlayer * argument
Show(&player1); // works with RatedPlayer * argument
```

The reference compatibility also allows you to initialize a base-class object from a derived-class object inadvertently. Suppose you have this code:

```cpp
RatedPlayer player1("Olaf", "Loaf", true);
TableTennisPlayer player2(player1);
```

The exact match for initializing player2 would be a constructor with its prototype:

```cpp
TableTennisPlayer(const RatedPlayer &); // doesn't exist
```

The class definitions do not include this constructor, but there is an implicit copy constructor:

```cpp
// implicit copy constructor
TableTennisPlayer(const TableTennisPlayer &);
```

The formal parameter is a reference to the base type, so it can refer to a derived type. Thus, the attempt to initialize player2 to player1 using this constructor copies the firstname, lastname, and hasTableMember. In other words, it initializes player2 to the TableTennisPlayer object embedded in the RatedPlayer object player1. Similarly, you can assign a derived-class object to a base-class:

```cpp
RatedPlayer player1("Olaf", "Loaf", true);
TableTennisPlayer winner;
winner = player1; // assign derived to base object
```

In this case, the program uses the implicit overloaded assignment operator:

```cpp
TableTennisPlayer &operator=(const TableTennisPlayer&) const;
```

Again, a base-class reference refers to a derived-class object, and the base-class portion of player1 is copied to winner.

## Inheritance: An Is-a Relationship

The special relationship between a derived class and a base class is based on an underlying model for C++ inheritance. Actually, C++ has three varieties of inheritance: public, protected, and private. Public inheritance is the most common form, and it models an is-a relationship. This is shorthand for saying that an object of a derived class should also be an object of the base class. Anything you do with a base-class object, you should be able to do: store the weight and caloric content of a fruit. For example, if you have a Fruit class. Because a banana is a particular kind of fruit, you can derive a Banana class from the Fruit class. The new class will inherit all the data members of the original class, so a Banana object would have representing the weight and caloric content of a banana. The new Banana class might also add members that apply particularly to bananas and not to fruit in general, such as the Banana Peel Index. Because the derived class can add features, it's probably more accurate to describe the relationship as an is-kind-of relationship, but is-a is the usual term.

To clarify is-a relationships, let's look at some examples that don't match the model. Public inheritance doesn't model a has-a relationship. A lunch, for example, might contain a fruit. But a lunch, in general, is not a fruit. Therefore, you should not derive a Lunch class from the Fruit class in an attempt to place fruit in a lunch. The correct way to handle putting fruit into a lunch is to consider the matter as a has-a relationship: a lunch has a fruit. As you'll see in Chapter 14, that's most easily modeled by including a Fruit object as a data member of a Lunch class (see Figure 13.3).

Public inheritance doesn't model an is-like-a relationship—that is, it doesn't smile. It's pointed out that lawyers are like sharks. But it is not literally true that a lawyer is a shark. Therefore, you shouldn't derive a Lawyer class from a Shark class.

## Chapter 13 Class Inheritance

Public inheritance doesn't model an implemented-as-a relationship. For example, you could implement a stack using an array. However, it wouldn't be proper to derive a Stack class from an Array class. A stack is not an array. For example, a stack could be implemented in some other way, such as a linked list. A proper approach would be to hide the array implementation by giving the stack a private Array object.

Public inheritance doesn't model a uses-relationship. For example, a computer can use a laser printer, but it doesn't make sense to derive a Printer class, or vice versa. You might have to devise friend functions or classes to handle communication between Printer and Computer objects.

Nothing in the C++ language prevents you from using public inheritance to model has-as, implemented-as-a, or uses-a relationships. However, doing so usually leads to programming problems. So let's stick to is-relationships.
