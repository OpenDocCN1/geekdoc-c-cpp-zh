That calls for using the transform() version with a unary function argument, like the example shown earlier: transform(gr8.begin(), gr8.end(), out, sqrt);

The multiplies() function can do the multiplication, but it's a binary function. So you need a function adapter that converts a binary function that has two arguments to one that has one. The argument TwoBig example shows one way, but the STL has automated the process with the binderlist and binder2nd classes, which convert binary functions to adaptable functions.

Let's look at binderlist. Suppose you have an adaptable binary function object f2(). You can create a binder object that binds a particular value, called val, to be used as the first argument to f2():

```
binderlist(f2, val, f1);
```

Then, invoking f1() with its first argument returns the same value as invoking f2() with val as its first argument (x) and f1()'s argument as its second argument. That is, f1(x) is equivalent to f2(val, x), except that it is a unary function instead of a binary function. The f2() function has been adapted. Again, this is possible only if f2() is an adaptable function.

This might seem a bit awkward. However, the STL provides the binderlist() function to simplify using the binderlist class. Give it the function name and value used to construct a binderlist object, and it returns an object of that type. For example, you can convert the binary function multiplies() to a unary function that multiplies its argument by 2.5. Just do this:

```
binderlist(multiplies<double>(), 2.5)
```

Thus, the solution to multiplying every element in gr8 by 2.5 and displaying the result is:

```
transform(gr8.begin(), gr8.end(), out, binderlist(multiplies<double>(), 2.5));
```

The binder2nd class is similar, except that it assigns the constant to the second argument instead of the first. It has a helper function called binder2nd that works analogously to bind1st.

## Algorithms

The STL contains many functions for working with containers. You've seen a few of them: sort(), copy(), find_each(), random_shuffle(), set_union(), set_intersection(), set_difference(), and transform(). You've probably noticed they feature the same overall design, using iterators to identify ranges to process and identify where results to go. Some also take a function object to be used as part of the data processing.

There are two generic components to algorithm designs. First, they use templates to provide generic types. Second, they use iterators to provide a generic representation for accessing data in a container. The copy() function can work with a container that holds double values in an array, with a container that holds string values in a linked list, or with a container that stores user-defined objects in a struct. Because pointers are special cases of iterators, STL functions such as copy() can be used with ordinary arrays. The uniform design allows meaningful relationships between containers of different kinds. For example, you can use copy() to copy values from an ordinary array to a vector, from a vector to a list object, and from a list to a set object. You can use == to compare contents, so a deque object and a vector object test as equal if they have the same content in the same order.

## Algorithm Groups

The STL divides the algorithm library into four groups:
- Nonmodify sequence operations
- Mutating sequence operations
- Sorting and related operations
- Generalized numeric operations

The first three groups are described in the algorithm (formerly algo.h) header file, and the fourth group, specifically oriented towards numeric data, gets its own header file called numeric. (Formerly, they, too, were in algo.h).

Nonmodifying sequence operations operate on each element in a range. For example, find() and for_each() belong to this category.

Mutating sequence operations also operate on each element in a range. As the name suggests, however, they can mutate or change the contents of the container. The change can be in values or in the order in which the values are stored. The transform(), random_shuffle(), and copy() functions fall into this category.

Sorting and related operations include several sorting functions (including sort()) and a variety of other functions, including the set operations.

The numeric operations include functions to sum the contents of a range, calculate the inner product of two containers, calculate partial sums, and calculate adjacent deferences. Typically, these are operations that are characteristic of arrays, so vector is the container most likely to be used with them.

## General Properties of Algorithms

As you've seen again and again in this chapter, STL functions work with iterators and iterator ranges. The function prototype indicates the assumptions made about the iterators. For example, the copy() function has this prototype:

```cpp
template<class InputIterator, class OutputIterator>
OutputIterator copy(InputIterator first, InputIterator last,
                               OutputIterator result);
```

Because the InputIterator and OutputIterator are template parameters, they could easily have been T and U. However, the STL documentation uses the template names to identify the concept that the parameter models. This declaration tells you that the ranges must be input iterators or the iterator indicating where the result goes must be an output parameter.

One way of classifying algorithms is on the basis of where the algorithm works: in place some create copies. For example, when the sort() function is used, the result occupies the same location as the original data. So sort() is an in-place algorithm. The copy() function, however, sends the result of its work to another location, so it is a copying algorithm. The transform() function can do both. Like copy(), it uses an output iterator to indicate where the results go. Unlike copy(), transform() allows the output iterator to point to a location in the input range, so it can copy the transformed values over the original values.

Some algorithms come in two versions: an in-place version and a copying version. The STL convention is to append _copy to the name of the copying version. The latter version takes an additional output iterator parameter to specify the location to write the copy output. For example, there is a replace() function that has this prototype:

```cpp
template<class ForwardIterator, class T>
void replace(ForwardIterator first, ForwardIterator last,
    const T& old_value, const T& new_value);
```

It replaces each instance of old_value with new_value. Because this algorithm both reads from and writes to container, the iterator type has to be ForwardIterator or better. The copying version has this prototype:

```cpp
template<class InputIterator, class T>
OutputIterator replace_copy(InputIterator first, InputIterator last,
    OutputIterator result,
    const T& old_value, const T& new_value);
```

This time the resulting data is copied to a new location, given by result, so the only input iterator is sufficient for the range. Note that replace_copy() returns an OutputIterator. The convention for copying algorithms is that they return an iterator pointing to the location past the last copy.

Another variation is that some functions have a version that performs an action conditionally, depending on the result of applying a function to a container element. These versions typically append _if to the function name. For example, replace_if() replaces an old value with a new value if applying a function to the value returns true true. Here's the prototype:

```cpp
template<class ForwardIterator, class Predicate>
void replace_if(ForwardIterator first, ForwardIterator last,
    Predicate pred, const T& new_value);
```

(Recall that a predicate is a unary function that returns a bool value.) There's also a version called replace_copy_if(). You can probably figure out what it does and what its prototype is like.

As InputIterator, Predicate is a parameter name and could as easily be called F or U. However, the STL chooses to use Predicate to remind the user that the actual argument should be a model of the Predicate concept. Similarly, the STL uses terms such as Generator and BinaryPredicate to identify arguments that should model other function concepts.
