# How Many Workers?

Suppose you begin by deriving SingingWaiter from Singer and Waiter: class SingingWaiter: public Singer, public Waiter {...};

Because both Singer and Waiter inherit a Worker component, SingingWaiter winds up with two Worker components (see Figure 14.4).

As you expect, this raises problems. For example, ordinarily you can assign the address of a derived-class object to a base-class pointer, but this becomes ambiguous when:

```
SingingWaiter ed;
Worker * pw = &ed; // ambiguous
```

Normally, an assignment sets a base-class pointer to the address of the base-class object within the derived object. But ed contains two Worker objects, so there are two addresses from which to choose. You could specify which object by using a type cast:

```
Worker * pw1 = (*Waiter) &ed; // the Worker in Waiter
Worker * pw2 = (*Singer) &ed; // the Worker in Singer
```

This clearly complicates the technique of using an array of base-class pointers to refer to a variety of objects (polymorphism).

Having two copies of a Worker object causes other problems, too. However, the real issue is why you should have two copies of a Worker object at all? A singing waiter, like any other, should have just one name and one ID. When C++ added MI to its bag of tricks, it added a virtual base to make this possible.
