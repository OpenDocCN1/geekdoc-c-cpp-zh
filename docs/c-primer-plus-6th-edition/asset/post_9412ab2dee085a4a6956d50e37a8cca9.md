## Procedural and Object-Oriented Programming

Although in this book we occasionally explored the OOP perspective of programming, we will usually stick pretty close to the standard procedural approach of languages as C, Pascal, and BASIC. Let's look at an example that clarifies the OOP outlook differs from that of procedural programming.

As the newest member of the Giants softball team, you've been asked to keep the team statistics. Naturally, you turn to your computer for help. If you were a procedural programmer, you might think along these lines:

> Let's say, I want to enter name, times at bat, number of hits, batting averages (for those who don't follow baseball or softball, the batting average is the number of hits divided by the player's official number of times at bat; at a bat terminates when a player gets on base or makes out, but certain events, such as getting a walk, don't count as official times at bat), and all those other basic statistics for each player. Wait, the computer is supposed to make life easier for me, so I want to figure it out of that, such as the batting average. Also I want the program to report the results. How should I organize this? I guess I do things right and use functions. Yeah, I make `main()` call a function to get the input, another function to make the calculations, and then a third function to report the results. what happens when I get data from the next? I don't want to start from scratch again. Okay, I can add a function to update the statistics. Maybe I'll need a `main()` Hmmm...how am I going to represent the data? I could use an array of strings to hold the players' names, another name to hold the hits at bats each player, another name to hold the hits, and so on. No, that's dumb. I can design a structure to hold all the information for a single player and use an array of structures to represent the whole team.

In short, with a procedural approach, you will concentrate on the procedures you will follow and think about how to represent the data. (So that you don't have to keep the program running the whole season, you probably want to be able to save data to a file and read data from a file.)

## Abstraction and Classes

Now let's see how your perspective changes when you don your OOP hat (in an attractive polymorphic design). You begin by thinking about the data. Furthermore, you think about the data not only in terms of how to represent it, but in terms of how it's to be used:

Let's see, what I am keeping track of? A ball player, of course. So I want an object that represents the whole player, not just his batting average or times at bats. Yeah, it'll be the fundamental data unit, an object representing the name and statistics for a player. I'll need some methods to handle this object. Hmm, I need a method to get basic information into this unit. The computer should calculate some of the stuff, like the batting averages—I can add methods to calculations. And the program should do those calculations without the user having to remember to ask them have done. I'll also need methods for updating and displaying the information. So the user gets three ways to interact with the data: initialization, updating, and reporting. That's the user interface.

In short, with an OOP approach, you concentrate on the object as the user perceives it, thinking about the data you need to describe the object and the operations that will describe the user's interaction with the data. After you develop a description of that, you may decide on how to implement the interface and data storage. Finally, you put together a program to use your new design.

## Abstraction and Classes

Life is full of complexities, and one way to cope with complexity is through simplifying abstractions. You are a collection of more than an octillion atoms. Students of the world would say that your mind is a collection of several semi-autonomous agents. But it's much simpler to think of yourself as a single entity. In computing, abstraction is the crucial step of representing information in terms of its interface with the user. That is, in terms of the softball statistics example, the interface describes how the user initializes, updates, and displays the data. From abstraction, is a short step to the user-defined type, which in C++ is a class design that implements the abstract interface.

## What Is a Type?

Let's think a little more about what constitutes a type. For example, what is a nerd? If you subscribe to the popular stereotype, you might think of a nerd in visual terms—thick, black-rimmed glasses, pocket full of pens, and so on. After a little reflection, you might conclude that a nerd is better defined operationally—for example, in terms of how he responds to an awkward social situation. You have a similar situation, if you don't mind stretched analogies, with a procedural language like C. At first, you think of a data type in terms of its appearance—how it is stored in memory. A char, example, is 1 byte of memory, and a double is often 8 bytes of memory. But a little reflection leads you to conclude that a data type is also defined in terms of the operations that can be performed on it. For example, the int type can use all the arithmetic operations. You can add, subtract, multiply, and divide integers. You can also use the modulus operator (%) with them.

- It determines how much memory is needed for a data object.
- It determines how the bits in memory are interpreted. (A long and float use the same number of bits in memory, but they are translated into numeric values differently.)
- It determines what operations, or methods, can be performed using the data object.

For built-in types, the information about operations is built in the compiler. When you define a user-defined type in C++, you have to provide the same kind of information yourself. In exchange for this extra work, you gain the power and flexibility to custom your new data types to match real-world requirements.

## Classes in C++

A class is a C++ vehicle for translating an abstraction to a user-defined type. It combines data representation and methods for manipulating that data into one package. Look at a class that represents stocks.
First, you have to think a bit about how to represent stocks. You could take one share of stock as the basic unit and define a class to represent a share. However, that implies that you would need 100 objects to represent 100 shares, and that's not practical. Instead, you can represent a person's current holdings in a particular stock as a basic unit. The number of shares would be part of the data representation. A realistic approach would have to maintain records of such things as initial purchase price and date of purchase for tax purposes. It would also have to manage events like stock splits. This seems a bit ambitious for a first effort at idealized view of matters. In particular, you can limit the operations you perform to the following:

- Acquire stock in a company.
- Buy more shares of the same stock.
- Sell stock.
- Update the per-share value of a stock.
- Display information about the holdings.
