# 异常规范遇上 C++11

有时一个想法在原则上看起来很有前景，但在实践中却效果不佳。异常规范就是这样一个故事，该特性由 C++98 添加，随后在 C++11 中被弃用。这意味着该特性仍在标准中，但未来可能不再存在，因此建议不要使用它。

然而，在忽略异常规范之前，你至少应该知道它们长什么样：它们看起来像这样：

```
double harm(double a) throw(bad_thing);    // throw bad_thing exception
double harm(double) throw();                           // doesn't throw an exception
```

throw()，带或不带类型列表，是异常规范，它会出现在原型和函数定义中。

异常规范的一个原因是提醒用户可能需要 try 块。然而，这可以用注释同样容易地实现。第二个原因是允许编译器添加运行时检查代码以查看是否违反了异常规范。这很容易发生。例如，marm() 可能会抛出异常，但它可能会调用一个调用抛出异常的函数。而且也许当你编写代码时该函数没有抛出异常，在库更新后它现在会抛出异常。无论如何，在编程社区中，特别是那些在编写异常安全代码方面最努力的人中，形成了共识，认为该特性被忽略了。你也可以在 C++11 的祝福下忽略异常规范。

然而，C++11 允许一种特殊规范——新的关键字 noexcept 可用于表示不抛出异常的函数：

```
double marm() noexcept; // doesn't throw an exception
```

关于该规范的必要性和有用性存在一些争论，所以感觉最好避免使用它（至少在大多数情况下）。但感觉强烈到足以引入一个新关键字。认为知道函数不应该抛出异常可以帮助编译器优化代码。这种用法应被视为函数程序员做出的承诺。

还有一个 noexcept() 运算符（参见附录 E），它报告其操作数是否可能抛出异常。

# 展开栈

假设 try 块不直接包含调用抛出异常的函数，但它调用了一个调用抛出异常的函数。执行会从抛出异常的函数跳转到包含 try 块和处理程序的函数。我们现在将讨论展开栈。

首先，让我们看看 C++ 通常如何处理函数调用和返回。C++ 通常通过在栈上放置信息来处理函数调用（参见第 9 章“内存模型和命名空间”）。特别是，程序将调用函数指令的地址（返回地址）放在栈上。当被调用函数完成时，程序使用该地址来确定程序执行的继续位置。函数调用还将任何参数放在栈上，在那里它们被视为自动变量。如果被调用函数创建任何新的自动变量，它们也会被添加到栈上。如果被调用函数调用另一个函数，其信息会被添加到栈上，依此类推。当函数终止时，程序执行传递到函数被调用时存储的地址，并且栈顶部被释放。该函数通常返回调用它的函数，每个函数在终止时释放其自动变量。如果自动变量是类对象，则如果有的话，其析构函数会被调用。

假设一个函数通过抛出异常而不是返回调用而终止。同样，程序会从栈中释放内存。但它不会在栈上的第一个返回地址处停止，而是继续释放栈，直到到达位于 try 块中的返回地址。控制传递到块末尾的异常处理程序，而不是传递到函数调用后的第一个语句。此过程称为展开栈。throw 机制的一个重要特性是，就像函数返回一样，栈上由该函数放置的任何自动类对象的类析构函数会被调用，而 throw 语句会处理由 try 块和 throw 之间的整个函数调用序列放置在栈上的对象。如果没有展开栈特性，throw 会使中间函数调用放置在栈上的自动类对象的析构函数未被调用。

清单 15.12 提供了展开栈的一个示例。在其中，main() 调用 mean()，后者又调用 hmean() 和 gmean()。mean() 函数，为了做点什么，计算算术、调和和几何平均值的平均值。main() 和 mean() 都创建 demo 类型的对象（一个喋喋不休的类，宣布其构造函数和析构函数的使用），以便你可以看到当抛出异常时这些对象会发生什么。main() 中的 try 块捕获 bad_hmean 和 bad_gmean 异常，means 中的 try 块仅捕获 bad_hmean 异常。此 catch 块具有以下代码：

```
catch (bad_hmean & bg) // start of catch block
{
  bg.mesg();
  std::cout << "Caught in mean()\n";
  throw;              // rethrows the exception
}
```
