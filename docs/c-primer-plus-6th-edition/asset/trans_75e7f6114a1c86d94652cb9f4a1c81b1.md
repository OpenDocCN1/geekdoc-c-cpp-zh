

## 智能指针模板类

如果清单 16.5 代表了你编程抱负的巅峰，那么这三种智能指针中的任何一种都能满足你的需求。但故事远不止于此。

## 智能指针的考量

为什么有三种智能指针？（实际上有四种，但我们不讨论 weak_ptr。）为什么 auto_ptr 被弃用了？

先从赋值开始考虑：

```
auto_ptr<string> ps (new string("I reigned lonely as a cloud."));
auto_ptr<string> vocation;
vocation = ps;
```

赋值会 accomplish 什么？如果 ps 和 vocation 是普通指针，结果将是两个指针指向同一个字符串对象。这不可接受，因为程序最终会尝试两次删除同一个对象——一次在 ps 失效时，另一次在 vocation 失效时。有几种方法可以避免这个问题：

- 定义赋值运算符使其进行深拷贝。这样会得到两个指向两个不同对象的指针，其中一个是另一个的拷贝。
- 引入 *所有权* 的概念，只允许一个智能指针拥有特定对象。只有智能指针拥有该对象，其析构函数才会删除该对象。然后赋值转移所有权。这是 auto_ptr 和 unique_ptr 使用的策略，尽管 unique_ptr 有些更严格。
- 创建一个更智能的指针，跟踪有多少个智能指针引用特定对象。这称为 *引用计数*。例如，赋值会将计数增加一，而指针的失效会将计数减少一。当最后一个指针失效时就会调用 delete。这就是 shared_ptr 的策略。

我们对赋值讨论过的策略，当然也适用于拷贝构造函数。
每种方法都有其用途。清单 16.6 显示了 auto_ptr 不合适的示例。

## 智能指针模板类

差异发生在程序的这一部分：
shared_ptr<string> pwin;
pwin = films[2];

这次 pwin 和 films[2] 指向同一个对象，并且引用计数从 1 增加到 2。在程序结束时，最后声明的 pwin 是其析构函数被调用的对象。析构函数将计数减少到 1。shared_ptrs 的成员被释放。films [2] 的析构函数将计数递减到 0 并释放先前分配的空间。

因此，使用 shared_ptr，清单 16 运行正常。使用 auto_ptr 它经历了运行时崩溃。如果使用 unique_ptr 会怎样？像 auto_ptr 一样，unique_ptr 采用所有权模型。不是析构，unique_ptr 版本会对这一行产生编译时错误：

```
pwin = films[2];
```

显然，有必要进一步研究这最后两种类型之间的差异。

## 为什么 unique_ptr 比 auto_ptr 更好

考虑以下语句：

```
auto_ptr<string> p1(new string("auto")); //#1
auto_ptr<string> p2; //#2
p2 = p1; //#3
```

当在语句 #3 中，p2 接管字符串对象的所有权时，p1 被剥夺了所有权。这，回顾一下，是好的，因为它防止 p1 和 p2 的析构函数都尝试删除同一个对象。但如果程序随后尝试使用 p1 也是坏的，因为它不再指向有效数据。

现在考虑 unique_ptr 的等价物：

```
unique_ptr<string> p3(new string("auto")); //#4
unique_ptr<string> p4; //#5
p4 = p3; //#6
```

在这种情况下，编译器不允许语句 #6，因此避免了 p3 不指向有效数据的问题。因此，unique_ptr 更安全（编译时错误 vs 潜在的程序崩溃）。

但也有时候将一个智能指针赋给另一个不会留下危险的孤儿。假设我们有这个函数定义：

```
unique_ptr<string> demo(const char * s)
{
    unique_ptr<string> temp(new string(s));
    return temp;
}
```

假设我们然后有这段代码：

```
unique_ptr<string> ps;
s = demo("Uniquely special");
```

这里，demo() 返回一个临时的 unique_ptr，然后 ps 接管了由返回的 unique_ptr 最初拥有的对象的所有权。然后返回的 unique_ptr 被销毁。这是可以的，因为 ps 现在拥有字符串对象的所有权。但还有一件好事发生了。因为 demo() 返回的临时 unique_ptr 很快被销毁，所以没有被误用以访问无效数据的可能性。换句话说，在这种情况下没有理由禁止赋值。而且，奇迹般地，编译器允许它！

简而言之，如果程序尝试将一个 unique_ptr 赋给另一个，编译器允许它如果源对象是临时值并且如果源对象有某些持续时间则不允许它：

```
using namespace std;
unique_ptr<string> ps1(new string "Hi ho!");
unique_ptr<string> ps2;
ps2 = ps1; // #1 not allowed
unique_ptr<string> ps3;
ps3 = unique_ptr(new string "Yo!"); // #2 allowed
```

赋值 #1 会留下悬空的 unique_ptr（即，可能的恶作剧来源）。赋值 #2 不会留下 unique_ptr，因为它调用了 unique_ptr 构造函数，该构造函数构造了一个在所有权转移到 ps3 时被销毁的临时对象。这种选择性行为是 unique_ptr 优于 auto_ptr 的一个迹象，后者会允许这两种形式的赋值。这也是 auto_ptr 被禁止（按建议，而不是编译器）用于容器对象，而 unique_ptrs 被允许的原因。如果容器尝试对 unique_ptrs 容器中的内容执行类似赋值 #1 的操作，你会得到编译错误。如果算法尝试执行类似赋值 #2 的操作，那是可以的，程序继续进行。使用 auto_ptrs，#1 这样的情况可能导致未定义行为和神秘的崩溃。

当然，可能你真的想做类似语句 #1 的操作。赋值是不安全的，除非你以智能的方式使用被放弃的指针，例如取消引用它。但你可以使用 C++ 的标准库函数 std::move() 安全地进行，因为它允许你将一个 unique_ptr 赋给另一个。这里有一个使用前面定义的 demo() 函数的示例，该函数返回一个 unique_ptr<string> 对象：

```
using namespace std;
unique_ptr<string> ps1, ps2;
ps1 = demo("Uniquely special");
ps2 = move(ps1); // enable assignment
ps1 = demo("and more");
cout << *ps2 << " " << *ps1 << endl;
```
