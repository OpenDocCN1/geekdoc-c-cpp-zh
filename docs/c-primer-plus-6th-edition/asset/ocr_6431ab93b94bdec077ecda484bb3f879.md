# Automatic Conversions and Type Casts for Classes

```
Stonew jennySt(9, 12);
Stonew bennySt(12, 8);
Stonew total;
total = jennySt + bennySt;
```

Also given the Stonew (double) constructor, each form lets you do the following:

```
Stonew jennySt(9, 12);
double jennyD = 176.0;
Stonew total;
total = jennySt + jennyD;
```

But only the friend function lets you do this:

```
Stonew jennySt(9, 12);
double bennyD = 146.0;
Stonew total;
total = pennyD + jennySt;
```

To see why, you can translate each addition into the corresponding function calls. First,

```
total = jennySt + bennySt;
```

In either case, the actual types match the formal arguments. Also the member-function is invoked, as required, by a Stonew object.

```
total = jennySt.operator+(bennySt); // member function
total = operator+(jennySt, bennySt); // friend function
```

```
total = jennySt + jennyD;
```

```
total = jennySt.operator+(jennyD); // member function
total = operator+(jennySt, jennyD); // friend function
```

Again, the member function is invoked, as required, by a Stonew object. This time, in each case, one argument (jennyD) is type double, which invokes the Stonew(double) constructor to convert the argument to a Stonew object.

By the way, an operator double() member function defined would create confusion at this point because that would create another option for interpretation. Instead of converting jennyD to double and performing Stonew addition, the compiler could convert jennySt to double and perform double addition. Having too many-conversion functions creates ambiguities.
