## Type Cast Operators

### Tip

If you find yourself using typeid in an extended series of if else statements, you should check whether you should instead use virtual functions and dynamic_cast.

### Type Cast Operators

The C type cast operator, in Bjarne Stroustrup's view, is too lax. For example, consider the following:

```
struct Data
{
    double data[200];
}
struct Junk
{
    int junk[100];
}
Data d = (2.5e33, 3.5e-19, 20.2e32);
char * pch = (char*) (&); // type cast #1 - convert to string
char ch = char (&); // type cast #2 - convert address to a char
Junk * pj = (Junk*) (&); // type cast #3 - convert to Junk pointer
```

First, which of these three type casts makes any sense? Unless you resort to the implausible, none of them make sense. Second, which of these three type casts are allowed? In C, all of them are. Stroustrup's response to this laxity was to tighten up what is allowable for a general type cast and add four type cast operators that provide more discipline for the casting process:

```
dynamic_cast
const_cast
static_cast
reinterpret_cast
```

Instead of using a general type cast, you can select an operator that is suited to a particular purpose. This documents the intended reason for the type cast and gives the compiler a chance to check that you did what you thought you did.

You've already seen the dynamic_cast operator. To suppose, High and Low are two classes, that ph is type *, and that pl is type *. Then the following statement assigns a Low * pointer to pl only if Low is an accessible base class (direct or indirect) to High:

```
pl = dynamic_cast<Low *> ph;
```

Otherwise, the statement assigns the null pointer to pl. In general, the operator has this syntax:

```
dynamic_cast < type-name > (expression)
```

The purpose of this operator is to allow upcasts within a class hierarchy such type casts being safe because of the is-a relationship and to disallow other casts. The operator is for making a type cast with the sole purpose of changing whether a value is const or volatile. It has the syntax as the dynamic_cast operator.

```
const_cast < type-name > (expression)
```

The result of making such a type cast is an error if any other of the type is altered. That is, type_name and expression must be of the same type, except that they can differ in the presence of const or volatile. Again, suppose High and Low are two classes:

```
High bar;
const High * pbar = &bar;

High * pb = const_cast<High *>(pbar); // valid
Low * pl = const_cast<Low *>(pbar); // invalid
```

The first type cast *pb a pointer that can be used to alter the value of the bar; it removes the const label. The second type cast is invalid because it attempts to change the type from const High * to Low *.

The reason for this operator is that you occasionally may need a value that is constant most of the time but can be changed occasionally. In such a case, you can declare the value as const and use const_cast when you need to alter the value. This could be done using the general type cast, but the general type cast also simultaneously change the type:

```
High bar;
const High * pbar = &bar;

High * pb = (High *) (pbar); // valid
Low * pl = (Low *) (pbar); // also valid
```

Because the simultaneous change of type and constancy may be an unintentional programming slip, using the const_cast operator is safer. The const_cast is not powerful. It can change the pointer access to a quantity, but the effect of attempting to change a quantity that is declared const is undefined. Let's clarify this statement with the short example shown in 15.19.

```
void change(const int * pt, int n);

```

```
void change(const int * pt, int n)
{
    int * pc;

    pc = const_cast<int *>(pt);
    *pc += n;
}
```

The const_cast operator can remove the const from const int * pt, thus allowing the compiler to accept the following statement in change:

```
*pc += n;
```

However, because pop2 is declared as const, the compiler may protect it from any change, as is shown by the following sample output:
pop1, pop2: 38383, 2000
pop1, pop2: 38280, 2000

As you can see, the change to pop1 but not pop2. The pointer is declared as const *, so it cannot change the value of the pointed-to-int. The pointer pc has const cast away, so it can be used to change the pointed-to-value, but only if that value itself wasn't const. Therefore, pc can be used to alter pop1 but not pop2.

The static_cast operator has the same syntax as the other operators:
static_cast <type-name> (expression)

It's valid only if type_name can be converted implicitly to the same type that expression has, or vice versa. The type cast is an error. Suppose that High is a base class to Low and that Pond is an unrelated class. Then conversions from High to Low and Low to High are valid, but a conversion from Low to Pond is disallowed:

Low blow...

```
High * pb = static_cast<High *>(&blow); // valid upcast
Low * pl = static_cast<Low *>(&bar); // valid downcast
Pond * pmer = static_cast<Pond *>(&blow); // invalid, Pond unrelated
```

The first conversion is valid because an upcast can be explicit. The second conversion, from a base-class pointer to a derived-class pointer, can't be without an explicit conversion. But because the type cast in the other can be made without a type cast, it's valid to use static_cast for a downcast.

Similarly, an enumeration value can be converted to an integral type without a type cast, an integral type can be converted to an enumeration value with static_cast. You can also use static_cast to convert double to int, to float to long, and to perform the other numeric conversions.

The reinterpret_cast operator is inherently risky type casts. It doesn't let you cast away const, but it allows other unsafe things. Sometimes a programmer to do implementation-dependent, unsafe things, and using the reinterpret_cast operator makes it impossible to keep track of such acts. It has the same syntax as the other three operators:

```
reinterpret_cast <type-name> (expression)
```

Here is a sample use:

```
struct {long a; short b;};
long value = 0xA224B1B;
dat * pd = reinterpret_cast<dat *>(&value);
cout << hex << pd->da; // display first 2 bytes of value
```

Typically, type casts would be used for low-level, implementation-dependent programming and would not be portable. For example, one system may store the bytes in a multibyte value in a different order than does another system.

The reinterpret_cast operator doesn't allow just anything, however. For example, you can cast a pointer to an integer type that's large enough to hold the pointer representation, but you can't cast a pointer to a smaller integer or to a floating-point type. Another restriction is that you can't cast a function pointer to a data pointer or vice versa.

The plain type cast in C++ is also restricted. Basically, it can do anything the other type casts do, with some combinations, as a static_cast or reinterpret_cast followed by a const_cast, but it can't do anything else. Thus, the following type cast is allowed in C but, typically not in C++ implementations the char is too small to hold a pointer implementation:

```
char ch = char (&value); // type cast #2 - convert address to a char
```

These restrictions make sense, but if you found such enforced judgment oppressive, you still have C available.
