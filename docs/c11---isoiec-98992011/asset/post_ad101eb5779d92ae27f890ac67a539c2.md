# 7.1.4 Use of library functions

+ Each of the following statements applies a function unless explicitly stated otherwise in the detailed descriptions that follow: if an argument has an invalid value (such as a value outside the domain of the function, or a pointer outside the address space of the program, or a null pointer, or a pointer to non-modifiable storage where the corresponding parameter is not const-qualified) or a type (after promotion) not expected by a function with variable number of arguments, the behavior is undefined. If a function argument is described as an array, the pointer actually passed to the function shall have a value such that all computations and accesses to objects (that would be valid if the pointer pointed to the first element of such array) are in fact valid. Any function declared in a header may be additionally implemented as a function-like macro defined in the header, so if a function is declared explicitly when header is included, one of the techniques shown below can be used to ensure the declaration is not affected by such macro. A macro definition of a function can be supported locally enclosing the name of the function in parentheses, because then it is not followed by the left parenthesis that indicates expansion of a macro name. For the same syntactic reason, it is permitted to take the address of a function even if it is also defined as a macro.¹185) The use of #undef remove any macro definition will also ensure that an actual function is returned. Any invocation of a function that is implemented as a macro shall expand to evaluate each of its arguments once, fully protected by parentheses where necessary, it is generally safe to use arbitrary expressions as arguments.¹186) Likewise, those function-like macros described in the following subclauses may be invoked in an expression where a function with a compatible return type may be called¹187) All object-like macros listed as expanding integer constant expressions shall additionally be suitable for use in #if preprocessing directives.

185) This means that an implementation should provide an actual function for each library function, even if it also provides a macro for that function.

186) Such macros might not contain the sequence that the corresponding function calls.

187) Because external identifiers and some macro names beginning with an underscore are reserved, implementations may provide special semantics for such in-line code. For example, the identifier _BUILTIN_abs could be used to indicate generation of in-line code for the abs function. Thus, the appropriate coder should specify

```
#define abs (x) BUILTIN_abs (x)
```

for a compiler whose code generator will accept it.

In this manner, a user desiring to guarantee that a given library function such as abs will be a genuine function may write

```
#undef abs
```

whether the implementation's header provides a macro implementation of abs or a built-in implementation. The prototype for the function, which proceeds and is hidden by any macro definition, is revealed also.

+ 3 There is a sequence point immediately before a library function returns.

+ 4 The functions in the standard library are not guaranteed to be reentrant and may modify objects with static or thread storage duration.

+ 5 Unless explicitly stated otherwise in the detailed descriptions that follow, library functions shall prevent data races as follows: A library function shall not directly or indirectly access objects by threads other than the current thread unless the objects are accessed directly or indirectly via the function's arguments. Implementations may share their own internal objects between threads if the objects are not visible to users and are protected against data races.

+ 6 Unless specified, library functions shall perform all operations solely within the current thread if those operations have effects that are visible to users.

# 7.2 Diagnostics <assert.h>

+ The header <assert.h> defines the assert and static_assert macros and refer-no, the assert and static_assert macros and refer to another macro,

NDEBUG
is not defined by <assert.h>. If NDEBUG is defined as a macro name at the point in the source file where <assert.h> is included, the assert macro is defined simply as

```
#define assert(ignore) ((void))
```

The assert macro is redefined to the current state of NDEBUG each time <assert.h> is included.

+ The assert macro shall be implemented as a macro, not as a function. If the macro definition is suppressed in order to access an actual function, the behavior is undefined.

+ The macro

```
static_assert
expands to _Assert.
```

# 7.2.1 Program diagnostics

# 7.2.1.1 The assert macro

Synopsis

```
#include <assert.h>
void assert (scalar expression);
```

Description

+ The assert macro puts diagnostics into programs; When it is executed, the expression (which will be a scalar type) is false (that is, equal to 0), the assert macro writes information about the particular call (including the text of the argument, the name of the source file, the line number, and the name of the enclosing function) on the standard error stream in an implementation-defined format.¹191) It calls the abort function.

191 The message written might be of the form:

Assertion failed: expression, function abc, file xyz, line nnn.

# 7.3 Complex arithmetic <complex.h>

# 7.3.1 Introduction

+ 1 The header <complex.h> defines macros and declares functions that support complex arithmetic.¹192)

+ 2 Implementations that define the macro __STDC_NO_COMPLEX__ need not provide this header support for any of its facilities.

+ 3 Each synopsis specifies a family of functions consisting of a principal function with one or more double complex parameters and a double complex or double return value; and other functions with the same name but with f and l suffixes which are corresponding functions with float and long double parameters and return values.

+ 4 The macro

complex
expands to _Complex; the macro

_Complex_I
expands to a constant expression of type const float _Complex, with the value of the imaginary unit.¹¹⁹³

+ 5 The macros

imaginary
and
_Imaginary_I
are defined and only if the implementation supports imaginary types;¹⁹⁴ if defined, they expand to _Imaginary and a constant expression of type const float _Imaginary with the value of the imaginary unit.

+ 6 The macro

I
expands to either _Imaginary_I or _Complex_I. If _Imaginary_I is not defined, I shall expand to _Complex_I.

+ 7 Notwithstanding the provisions of 7.1.3, a program may undefined and then redefine the macros complex, imaginary, and I.

192 See "future directions" (7.31).

193 The imaginary unit is a number such that i² = -1.
