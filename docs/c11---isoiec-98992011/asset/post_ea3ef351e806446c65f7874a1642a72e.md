## F.8.6 Changing the environment

+   Operations defined in 6.5 and functions and macros defined for the standard libraries changing floating-point status flags and control modes as indicated by their specifications (including conformance to IEC 60559). They do not change flags or modes (so as to be detectable by the user) in any other cases.

+   If the argument to the feraiseexcept function in \<fenv.h&; represents IEC 60559 valid coincident floating-point exceptions for atomic operations (namely “overflow” and “inexact”, or “underflow” and “inexact”), then “overflow” or “underflow” is raised before “inexact”.

## F.9 Optimization

+   This section identifies code transformations that might subtle IEC 60559-specified behavior, and those that do not.

### F.9.1 Global transformations

+   Floating-point arithmetic operations and external function calls may entail side effects which optimization shall honor, at least where the state of the FENV_ACCESS pragma is “on”. The flags and modes in the floating-point environment may be regarded as global variables; floating-point operations (+, *, etc.) implicitly read the modes and write the flags.

+   Concern about side effects might inhibit code motion and removal of seemingly useless code. For example,

```c
#include <fenv.h>
#pragma STDC FENV_ACCESS ON
void f(double x)
{
    /* ... */
    for (int i = 0; i < n; i++) x += 1;
    /* ... */
}
```

x + 1 might raise floating-point exceptions, so cannot be removed. And since the loop body might not exist (maybe 0 ≥ n), x + 1 cannot be moved out of the loop. (Of course these optimizations are valid if the implementation can rule out the troublesome cases.)

+   This specification does not support for trap handlers that maintain information about the order or cost of floating-point exceptions. Therefore before function calls, floating-point exceptions need not be precise: the actual order and occurrences of floating-point exceptions (> 1) may vary from the code expressions.

the preceding loop be treated as

```c
if (0 < n) x = x + 1;
```

### F.9.2 Expression transformations

+   x/2 ↔ x × 0.5 Although similar transformations involving inexact constants generally do not yield numerically equivalent expressions, if the constants are exact such transformations can be made on IEC 60559 machines and others that round perfectly.

+   1 x and x/1 → x The expressions 1 x, and x/1 are equivalent (on IEC 60559 machines, among others).³ 368

+   x/x ↔ 1.0 The expressions x/x and 1.0 are not equivalent if x be zero, infinite, or Nan.

+   x - y ↔ x + (-y) The expressions x - y, x + (-y), and (-y) + x are equivalent (on IEC 60559 machines, among others).

+   x -y ↔ -(y) The expressions x - y and (-y) x are not equivalent because 1 − 1 is +0 (-1 in 1) is -0 (in the default rounding direction).³ 369

+   x - x ↔ 0.0 The expressions x - x and 0.0 are not equivalent if x be a NaN or infinite.

+   0 × x ↔ 0.0 The expressions 0 x and 0.0 are not equivalent if x is a NaN, infinite, or -0.

+   x + 0 → x The expressions x + 0 and x are not equivalent if x be -0, because (-0) + (+0) yields +0 (in the default rounding direction), not -0.

+   x - 0 → x (+0)- (+0) yields -0 when rounding is towards (∞), or otherwise, and (-0)-(+0) always yields -0; so, if the state of the FENV_ACCESS pragma is “off”, default rounding, then the implementation can replace x −0 by x, even if x might be zero.

+   -x ↔ 0 - x The expressions -x and 0 - x are not equivalent if x is +0, because (+0) yields -0, but 0-(0) yields +0 (unless rounding is downward).

> 368 Strict support for signaling NaNs — not required by this specification — would invalidate these and other transformations that require arithmetic operations.

> 369 IEC 60559 prescribes a sign zero to preserve mathematical identities across certain discontinuities. Examples include:
> 1/(1 ±0) is ±0
 and conj(sqrt(z)) is sqrt(conj(z)), for complex z.

### F.9.3 Relational operators

+   * x \neq x → false  The expression $x \neq x$ is true if $x$ is a NaN.
*   x = x → true  The expression $x = x$ is false if $x$ is a NaN.

$x < y \to isless(x,y)$ (and similarly for $\le$, $>$) Though numerically equal, these expressions are not equivalent because side effects when $x$ or $y$ is a NaN and the state of the `FENV_ACCESS` access is "on". This transformation, which would be desirable if extra code were required to cause the "invalid" floating-point exception for unordered cases, could be performed the state of the `FENV_ACCESS` pr is "off".

The sense of relational operators should be maintained. This includes handling unordered cases as expressed by the source code.

+   * EXAMPLE
// calls g and raises "invalid" if a and b are unordered
if (a < b)
    f();
else
    g();
is not equivalent to
// calls f and raises "invalid" if a and b are unordered
if (a >= b)
    g();
else
    f();
nor to
// calls f without raising "invalid" if a and b are unordered
if (isarequal(a,b))
    g();
else
    f();
nor, unless the state of the FENV_ACCESS pr is "off", to
// calls g without raising "invalid" if a and b are unordered
if (isless(a,b))
    f();
else
    g();
but is equivalent to

```c
if (! (a < b))
    g();
else
    f();
```

### F.9.4 Constant arithmetic

+   1 The implementation shall honor floating-point exceptions raised by execution-time constant wherever the state of the FENV_ACCESS pragma is “on”. (See F.8.4 and F.8.5.) An operation on constants that raises no floating-point exception can be folded during translation, except if the state of the FENV_ACCESS pragma is “on”, a further check is required to ensure that changing the rounding direction to downward does not alter the result.
