```
Here, we use the approach with function overloading, as introduced in Section 9.4, on page 46. That is, inside a helper class we declare two overloaded function templates named `test()` with different return types and declare a `Type` member for the class of the resulting trait:

```
```cpp
template<class T> static std::true_type test(void*);
template<class T> static std::false_type test(...);

using Type = decltype(test<T>(nullptr));

template<typename FROM, typename TO>
struct IsConvertible : IsConvertible<FROM, TO>
```
```

As usual, the first `test()` overload is designed to match only if the requested check succeeds, while the second overload is a fallback. Thus, the goal is to make the first `test()` overload valid if and only if type `FROM` converts to type `TO`. To achieve this, again we give our first declaration of `test` a dummy (unnamed) template argument initialized with a construct that is valid if and only if the conversion is valid. This template parameter cannot be deduced, and we will not provide an explicit template argument for it. Therefore, it will be substituted, and if the substitution fails, that declaration of `test()` will be discarded.

Again, note that the following doesn't work:
```

```cpp
static void test(T);
template<typename = decltype(std::declval<T>())>
static char test(...);
```
```

Here, `FROM` and `TO` are completely determined when this member function template is used, and therefore a pair of two function templates is not viable for overload resolution if one of them is not valid, and this declaration of `test()` will be discarded.

For that reason, we introduce `r` as a specific member function template parameter:
```

```cpp
static void eval(T);
```

```

and provide the `FROM` type as an explicit template argument in the call to `test()` that appears in the initialization of `value`!
```

```cpp
static constexpr bool value = decltype(test<T>(nullptr))
```
```

Note how `std::declval`, introduced in Section 19.3.4 on page 15, is used to produce a value without calling any constructor. If that value is convertible to `TO`, the call to `test()` is valid, and this declaration of `test()` matches. Otherwise, a SFINAE failure occurs and only the fallback declaration will match.

As a result, we can use the trait as follows:
```

# Handling Special Cases

There cases are not yet handled correctly by `IsConvertible`:

+   1. Conversions to array types should always yield `true`, but in our code, the parameter of type `T` in the declaration of `test()` will just decay to a pointer type and therefore enable a "true" result for some incorrect types.
+   
+   2. Conversions to function types should always yield `false`, but just as with the array case, our implementation just treats them as decayed types.
+   
+   3. Conversion to `(const/volatile-qualified) void` types should yield `true`. Unfortunately, our implementation above doesn't even successfully instantiate the case where `T` is a `void` type because parameters of type `void` are not valid.
