## 28.5 ORACLES

Tracers are relatively simple and effective, but they allow us to trace the execution of templates only for specific input data or for a specific behavior of its defined functionality. We may wonder, for example, what conditions must be met by the comparison operator for the sorting algorithm to be meaningful (or correct), but in our example, we have only tested a comparison operator that behaves exactly like less-than for integers.

An extension of tracers is known in some circles as oracles (or run-time adaptive debuggers). They are tracers that are connected to an inference engine—a program that can remember assertions and reason about them to infer certain conclusions.

Oracles allow us, in some cases, to verify template algorithms dynamically without fully specifying the substituting template arguments (the oracles are the arguments) or the input data (the inference engine may request some sort of input information when it gets stuck). However, the complexity of the algorithms that can be analyzed in this way is still modest (because of the limitations of the inference engine), and the amount of work is considerable. For these reasons, we do not delve into the development of oracles, but the interested reader should examine the publication mentioned in the aftermath (and the references contained therein).

## Appendix A

## The One-Definition Rule

Affectionately known as the ODR, the one-definition rule is a cornerstone for the well-formed structure of C++ programs. The most common consequences of the ODR are simple enough to remember and apply: Define non-inline functions or objects exactly once across all files, and define classes, inline functions, and inline variables at most once per translation unit, making sure that all definitions for the same entity are identical.

However, the devil is in the details, and when combined with template instantiation, these details can be daunting. This appendix is meant to provide a comprehensive overview of the ODR for the interested reader. We also indicate when specific related issues are expounded on in the main text.

### A.1 TRANSLATION UNITS

In practice we write C++ programs by filling files with “code.” However, the boundary within a file is not strongly important in the context of the ODR. Instead, what matters are translation units. Essentially, a translation unit is the result of applying the preprocessor to a file you feed to your compiler. The preprocessor drops declarations of code not selected by conditional compilation directives (#if, #ifdef, and friends), drops comments, inserts #include files (recursively), and expands macros.

Hence, as far as the ODR is concerned, having the following two files

```cpp
// == header.hpp:
#ifndef DEBUG
#define debug(x) std::cout << x << '\n'
#else
#define debug(x)
#endif

void debugInit();
// == myprog.cpp:
#include "header.hpp"

int main()
{
    debugInit();
    debug("string");
}
```

is equivalent to the following single file:

```cpp
// == header.cpp:
void debugInit();

int main()
{
    debugInit();
    debug("string");
}
```

Connections across translation unit boundaries are established by having corresponding declarations with external linkage in two translation units (e.g., two declarations of the global function debugInit()).

Notice that the excerpt of a translation unit is a little more abstract than just a “programmed file.” For example, if we were to add a preprocessor file to a compiler to form a single program, it would bring into that program two distinct translation units (there is no point in doing so, however).

### A.2 DECLARATIONS AND DEFINITIONS

The terms declaration and definition are often used interchangeably in common “programmer talk.” In the context of the ODR, however, the exact meaning of these words is important.

A declaration is a C++ construct that (usually) introduces or reintroduces a name in your program. A declaration can also be a definition, depending on which entity it introduces.

- **Namespaces and namespace aliases:** The declaration of namespaces and their aliases is always a definition, although the term definition is unusual in this context because the list of members of a namespace is “extended” at a later time.
- **Classes, functions, member functions, and member function templates:** The declaration is a definition if and only if it includes a body enclosed by braces (in the case of functions), or a declaration list enclosed by braces (in the case of classes with an inline function-like entity).
- **Enumerations:** The declaration is a definition if and only if it includes the brace-enclosed list of enumerators.
- **Local variables and nonstatic data members:** These entities can always be treated as definitions, although the distinction rarely matters. Note that the declaration of a function parameter in a function definition is itself a definition because a function's parameters are local variables, but a function parameter in a function declaration that is not a definition is not a definition.
- **Global variables:** If the declaration is not directly preceded by a keyword like `extern` and does not have an initializer, the declaration is also a definition of that variable. Otherwise, it is not a definition.
- **Static data members:** The declaration is a definition if and only if it is preceded by the class or class template of which it is a member by a declaration list or enclosed in braces, or in a class or class template.
- **Explicit and partial specializations:** The declaration is a definition if and only if the declaration is a declaration of a class template or a function template, except that the explicit specialization of a static data member or static data member template is a definition only if it includes an initializer.
- **Other declarations are not definitions.** That includes type aliases (with `typedef` or `using`), using declarations, using directives, template parameter declarations, explicit instantiation declarations, `static_assert` declarations, and so on.

### A.3 THE ONE-DEFINITION RULE IN DETAIL

As we implied in the introduction to this appendix, there are many details to the actual ODR. We organize the rule's contents by topic as follows:

### A.3.1 One-per-Program Constraints

There can be at most one definition of the following items per program:

- Noninline functions and noninline member functions (including full specializations of function templates)
- Noninline variables (variables, including those declared in a namespace scope or in the global scope, and without the `static` specifier)
- Noninline static data members

For example, a C++ program consisting of the following two translation units is invalid:

Click here to view code image

```cpp
// --- translation unit 1:
int counter;

// --- translation unit 2:
int counter;   // ERROR: defined twice (ODR
               // violation)
```

This rule does not apply to entities with internal linkage (generally, entities declared with the `static` specifier in the global scope or in a namespace scope, as well as entities declared in an unnamed namespace) as long as they are not referenced outside their translation unit. For example, even if two entities with the same name but internal linkage are declared in the same translation unit, they are considered distinct if they appear in different namespaces. In C++11 and later, such entities also have internal linkage by default, but for purposes of the ODR, they are still distinct. If both are used in the same translation unit, they are distinct if they appear in different namespaces.

For example, the following two translation units can be combined into a valid C++ program:

```cpp
// --- translation unit 1:
static int counter = 2; // unrelated to other translation units
namespace {
    void unique() {}
}

// --- translation unit 2:
static int counter = 3; // unrelated to other translation units
namespace {
    void unique() {}
}

// ---
int main() {
    counter = 4;
    unique();
}
```
