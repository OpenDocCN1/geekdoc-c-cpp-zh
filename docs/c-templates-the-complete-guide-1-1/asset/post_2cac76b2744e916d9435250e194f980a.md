
```cpp
int main()
{
    double value = implicit_cast<double>(-1);
}
```

If we had reversed the order of the template parameters in this example (in other words, if we had written `template <typename T, typename Date_t>`, a call of `implicit_cast` would have to specify both template arguments explicitly.

Moreover, such parameters can't usefully be placed after a template parameter pack or appear in a partial specialization, because there would be no way to explicitly specify or deduce them.

Click here to view code image

```cpp
template<typename T, int N>
void f(double (&a)[N], T* p) // cannot be deduced because N
{
}
```

Because function templates can be overloaded, explicitly providing all the arguments for a function template may not be sufficient to identify a single function: In some cases, it identifies a set of functions. The following example illustrates a consequence of this observation:

Click here to view code image

```cpp
template<typename Func, typename T>
void apply(Func f, T x)
{
    f(x);
}

template<typename T> void single(T);
template<typename T> void multi(T);
template<typename T> void multi(T*);

int main()
{
    apply(single<int>, 3); // OK
    apply(multi<int>, 3);  // ERROR: no unique
}
```

In this example, the first call to `apply()` works because the type of the expression is an unambiguous function type. As a result, the template argument for `T` can be inferred. The second call, however, `multi<int>` could be one of two different types and therefore cannot be deduced in this case.

Furthermore, it is possible that substituting template arguments in a function template results in an attempt to construct an invalid C++ expression. Consider the following overloaded function template and the error specified below:

Click here to view code image

```cpp
template<typename T> void f(typename T::x);
template<typename T> void f(T);

f(42);
```

The expression causes substitution to fail in the first function template because type `int` has no member type. However, the second template has no such problem. Therefore, the expression is well-formed. The fact that the substitution of `int` into the first template fails does not make the expression invalid. This SFINAE (substitution failure is not an error) principle is an important ingredient to make the overloading of function templates practical and is discussed in Section 8.4, on page 139 and Section 5.7, on page 284.

## 12.3.2 Type Arguments

Template type arguments are the “values” specified for template type parameters. Any type (including `void`, function types, reference types, etc.) can, in general, be used as a template argument, but their substitution for a template parameter must lead to valid constructs.

Click here to view code image

```cpp
template<typename T>
void show(T value)
{
    T* p = 0; // required that the unary * be applicable
}

int main()
{
    int a;
    show(a); // ERROR: int doesn't support the unary *
}
```

## 12.3.3 Nontype Arguments

Nontype template arguments are the values substituted for nontype parameters. Such a value must be one of the following things:

- acceptable only if the corresponding parameter has a type that matches that of the value or a type to which the value can be implicitly converted without narrowing. For example, a char value can be provided for an int parameter, but not an int value for an 8-bit char parameter.
- The name of an external variable or function preceded by the built-in address-of operator (`&`). For functions and array variables, the `&` can be left out. Such template arguments must not be.
- The previous kind of argument but without a requirement for a valid argument of a type parameter of reference type. Here too, C++17 relaxed the constraint to permit any constant-expression pointer or reference.
- A pointer-to-member constant; in other words, an expression of the form `&C::m` where C is a class type and m is a nonstatic member (function or data). Any constant-expression evaluating to a matching pointer-to-member is accepted. Any constant-expression evaluating to a matching pointer-to-member is accepted.
- A null pointer constant is a valid argument for a non-type parameter of pointer or pointer-to-member type.

For nontype parameters of integral type—probably the most common kind of nontype parameter—implicit conversions to the parameter type are considered. With the introduction of constexpr conversion functions in C++11, this means that the argument before conversion can have a class type.

Prior to C++17, when matching an argument to a parameter that is a pointer or reference, user-defined conversions (constructors for one argument and conversion operators) and derived-to-base conversions are not considered, even though in other circumstances they would be valid in pointer conversions. Implicit conversions that make an argument more const and/or more volatile are fine.

Here are some valid examples of nontype template arguments:

Click here to view code image

```cpp
template<typename T, T nontype>
class C;

int i;              // integer type
int* p = &i;        // address of an external variable

void f(int);
void (*pf)(int) = &f;   // address of a function

void g(int) {}

// name of a function: overload resolution
// is implied

template<typename T> void tempfunc();

C<decltype(tempfunc), &tempfunc> c;  // function template
// instantiation also function

struct A {
    static bool b;
    int n;
};

template<> operator ...
```

C++ also considers other arguments that are acceptable variable/function names:

- A pointer-to-member type.
- A string literal (Prior to C++11, null pointer constants were not permitted either).

One of the problems with string literals is that two identical literals can be stored at two distinct addresses. An alternative (but unnecessary way) to express template instantiation over constant string addresses involves introducing an additional variable to hold the string:

Click here to view code image

```cpp
template<char const* str>
class Message {
};

static char const hello[] = "Hello World!";
char const hello[] = "Hello World!";

Message<hello> msg;
```

```cpp
// declares in namespace std:
template<typename T, typename Allocator = allocator<pair<const T, T>>>
class map;
// namespace std
template<typename T, typename Allocator = allocator<pair<const T, T>>>
class multimap;
template<typename T, class Allocator = allocator<T>>
class vector;
```

```cpp
template<typename T,
         class Allocator = allocator<T>>

  ...
};
```

```cpp
class AnotherClass;

  class AnotherClass;
}
```


The fact that a parameter of C++ only has a default if it is used in a declaration of a template parameter does not indicate that only class templates declared with the keyword class are allowed to be substituted as arguments. Indeed, struct, union, and class templates are all valid arguments for a template parameter (template parameters also accept built-in types, pointer types, and so on). This is similar to the observation that any type can be used as a template parameter, whether declared with the keyword class or not.

### 3.2.3.5 Equivalence

Two sets of template arguments are equivalent when the values of the arguments are identical for one or more types. For instance, `template<typename T, int N>` and `template<class T, int N>` are equivalent.

Click here to view code image

```cpp
template<typename T, int N>
class C;

C<int, 5> x;       // ok
C<int, 5> y;       // ok
C<int, 5> z;       // ok
```

To be clear in this example, no definition is needed to establish the equivalence of a template argument list.

In a template-dependent context, however, the “value” of a template argument cannot always be established definitively, and the rules for equivalence become a little more complicated. Consider the following example:

Click here to view code image

```cpp
template<typename T, int N>
class C;

C<int, 5> x;       // ok
C<int, 5> y;       // ok
C<int, 5> z;       // ok
```

Only declarations of `N` are exactly equivalent, and not just the declarations for `x`, `y`, and `z` (respectively), and not just the declaration `template<typename T, int N>`. Thus the two declarations are equivalent and define the same function template.

Declarations of `x`, `y`, and `z` are not equivalent. In particular, the declaration of `x` and the declaration of `y` are not equivalent. The declaration of `z` and the declaration of `x` are not equivalent. The declaration of `y` and the declaration of `z` are not equivalent.

A function generated from a function template is never equivalent to an ordinary function even though they may have the same name and the same type. This has two important consequences for class members:

- 1. A function generated from a member function template never overrides a virtual function.
- 2. A constructor generated from a constructor template is never a copy constructor. Similarly, an assignment generated from an assignment template is never a copy-assignment or a move-assignment operator. (However, this is less prone to problems because implicit calls of copy-assignment or move-assignment operators are less common.)

This is also good and bad. See Section 13.2 on page 632 and Section 5.4 on page 102 for details.
