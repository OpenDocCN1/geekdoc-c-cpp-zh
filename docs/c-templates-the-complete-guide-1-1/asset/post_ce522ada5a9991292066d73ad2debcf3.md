
```
T value(Type<T>) // no definition needed
```

Let's start with the definition of `isValid`: It is a constexpr variable whose type is a lambda's closure type. The declaration must necessarily use a placeholder type (`auto` in our code) because C++ has no way to express closure types directly. Prior to C++17, lambda expressions could not appear in constant expressions. With C++17, this ability is also available in constant expressions. With C++17, since `isValid` has a closure type, it can be invoked (i.e., called), but the item that it returns is itself an object of a lambda closure type, produced by the inner lambda expression.

Before delving into the details of this inner lambda expression, let's examine a typical use of `isValid`:

```
constexpr auto isDefaultConstructible
    = isValid([] (auto x) -> decltype(std::declval<decltype(x)>())
        { return {}; });
```

We already know that `isDefaultConstructible` has a lambda closure type and, as the name suggests, it is a function object that checks the trait of a type being default-constructible (we'll see why in what follows). In other words, `isValid` is a traits factory. A component that generates traits checking objects from its arguments.

The type helper variable template allows us to represent a type as a value. I use a `type` variable that you can turn back into the original type with `decltype(value)` and that's exactly what is passed to `isValid` above. If that extracted type cannot be default-constructed, the `decltype(value)` is invalid, and we will either get a compiler error, or an associated default function will be substituted, and the latter effect is what we will achieve thanks to the details of the definition of `isValid`.

`isDefaultConstructible` can be used as follows:

```
isDefaultConstructible(type<int>)                 // true (int is
                                                     // default-constructible)
isDefaultConstructible(type<std::unique_ptr<int>&>)   // false (references
                                                     // are not default-constructible)
```

So now all the pieces work together, consider what the inner lambda expression in `isValid` becomes with a call to a parameter `t` bound to the generic lambda argument specified in the definition of `isDefaultConstructible`. By performing the substitution in `isValid`'s definition, we get the equivalent of

```
constexpr auto isDefaultConstructible
    = [] (auto... args) {
        return decltype([] (auto x) -> decltype(std::declval<
            decltype(args)>()); 
        });
      };
```

If we look back at the first declaration of `isValid` above, we note that it includes a default template argument of the form

```
decltype([](decltype(auto) t) -> decltype(std::declval<T>()));
```

which attempts to invoke a value of the type of its first template argument, which is the closure type of the lambda in the definition of `isDefaultConstructible`, with a value of the type of the arguments (`decltype(std::declval<...>())`). In the type of the first argument to `isValid`, a regular lambda expression is made; its return type is specified as `decltype(std::declval<...>)`, as shown above. When the expression is substituted, the call is valid if the first declaration of `isDefaultConstructible` is well-formed. If it is not, the expression substitution fails, and SFINAE'd out. That leaves just the second declaration, which would otherwise be a lesser match, which produces a false value. Moreover, `isDefaultConstructible` produces a false type when `type<T&>` is passed. If instead `type<T>` is passed, the substitution does not fail and the first declaration of `isValid<T>()` is selected, producing a true value.

Recall that for SFINAE to work, substitutions have to happen in the immediate context of the substituted templates. In this case, the substitution templates are the first declaration of `isValid<T>` and the call operator of the generic lambda passed to `isValid`. Therefore, the construct to be tested has to appear in the return type of that lambda, not in its body!

Our `isDefaultConstructible` trait is a little different from previous trait implementations in that it requires function-object instances instead of specifying template arguments. That is arguably a more usable notation, but prior style can be obtained also:

```
template<typename T>
using isDefaultConstructible = decltype(isValid(type<T>{}));
```

### 19.9.4 SFINAE-Friendly Traits

In general, a type trait should be able to answer a particular query without causing the program to become ill-formed. SFINAE-based traits address this problem by carefully trapping potential problems within a SFINAE context, turning those would-be errors into negative results.

However, some traits presented thus far (such as the `PlusResultT` trait described in Section 19.3.4 on page 434) do not behave well in the presence of errors. Recall the definition of `PlusResultT<>` from that section:

```
template<typename T1, typename T2>
struct PlusResult {
  using Type = decltype(std::declval<T1>() + std::declval<T2>());
};

template<typename T1, typename T2>
using PlusResultT = typename PlusResult<T1, T2>::Type;
```

In this definition, the `+` is used in a context that is not protected by SFINAE. Therefore, if a program attempts to evaluate `PlusResult<T>` for types that do not have a suitable `+` operator, that evaluation of `PlusResult<T>` itself will cause the program to become ill-formed, as in the following attempt to declare the return type of adding arrays of unrelated types `A` and `B`:

```
template<typename T>
class Array {
};

template<typename T1, typename T2>
Array<PlusResultT<T1, T2>>
operator+(Array<T1> const&, Array<T2> const&);
```

Clearly, using `PlusResultT<>` here will lead to an error if no corresponding operator `+` is defined for the array element.

```
class A {
};

class B {
};

void add(Array<A> const&, Array<A> const&);

// declare a + for arrays of different element types:
template<typename T1, typename T2>
Array<PlusResultT<T1, T2>>
operator+(Array<T1> const&, Array<T2> const&);

// no int = arrayA + arrayB   // ERROR? depends on
// whether the compiler              // instantiations
// ...
```

If the compiler can determine that the second declaration of `operator+` is a valid match without performing deduction and substitution on the first (template) declaration of `operator+`, it will accept this code.

However, while deducing and substituting a function template candidate, anything that happens during the instantiation of the definition of a class template is not part of the immediate context of that function template substitution, and SFINAE does not protect us from attempts to form invalid types or expressions there. Instead of just discarding the function template candidate, an error is raised right away because we try to call `operator+` for two elements of types `T1` and `T2`.

```
template<typename T1, typename T2>
struct PlusResultT {
    using Type = decltype(std::declval<T1>() + std::declval<T2>());
};
```

To solve this problem, we have to make the `PlusResultT` SFINAE-friendly, which means to make it more suitable by giving it a suitable definition even when its `decltype` expression is ill-formed.

Following the example of `HasResultT` described in the previous section, we define a `HasPlusTrait` that allows us to detect whether there is a suitable `+` operation for the given types:

```
#include <utility>      // for declval
#include <type_traits>   // for decltype, false_type,
                         // true_type

// primary template
template<typename T1, typename T2, typename = std::void_t<>>
struct HasPlusT : std::false_type
{
};

// partial specialization (may be SFINAE'd away)
template<typename T1, typename T2>
struct HasPlusT<T1, T2, std::void_t<decltype(std::declval<T1>() +
                                             std::declval<T2>())>>
  : std::true_type
{
};
```

If it yields a true result, `PlusResultT` can use the existing implementation. Otherwise, `PlusResultT` needs a safe default. The best default for a trait that has no meaningful result for a set of template arguments is to not provide any member `Type` at all. That way, if the trait is used within a SFINAE-context—such as the return type of the error `operator+`—the missing member `Type` will make template argument deduction fail, which is precisely the behavior desired for the array `operator+` template.

The following implementation of `PlusResultT` provides this behavior:

```
#include "HasPlus.hpp"

template<typename T1, typename T2, bool = HasPlusT<T1, T2>::value>
struct PlusResultT {                 // primary template, used ...
    using Type = decltype(std::declval<T1>() + std::declval<T2>());
};

template<typename T1, typename T2>
struct PlusResultT<T1, T2, false> {    // partial specialization
```
