```cpp
}
```

It is instructive to try to call this `min()` function with various types with different `<` operators (or mixing the operator entirely), as in the following example:

```cpp
struct X1 { };

bool operator< (X1 const&, X1 const&) { return true; }

struct X2 { };

bool operator<(X2, X2) { return true; }

struct X3 { };

bool operator<(X3, X3&) { return true; }

struct BoolConvertible {
  operator bool() const { return true; } // implicit conversion to bool
};

struct X5 { };

BoolConvertible operator< (X5 const&, X5 const&)
{
  return BoolConvertible();
}

struct NotBoolConvertible { // no conversion to bool
};

{
  return NotBoolConvertible();
}

struct BoolLike {
  explicit operator bool() const { return true; } // explicit conversion to bool
};

  min(X4(), X4()); // ERROR: X4 cannot be passed to min()

  min(X5(), X5()); // X5 can be passed to min()

  min(X6(), X6()); // ERROR: X6 cannot be passed to min()

  min(X7(), X7()); // UNEXPECTED ERROR: X7 cannot be passed to min()
```

When compiling this program, notice that while there are errors for four of the different `min()` calls—`X3`, `X4`, `X5`, and `X7`—the errors do not come from the body of `min()`, as they would have with the non-instantiation-safe variant. Rather, they complain that there is no suitable `min()` function because the only option has been eliminated by SFINAE. Clang produces the following diagnostic:

```text

  ‘min(int, int)’

/min.hpp:81:1: note: candidate template ignored: substitution failure

  ...
```

Thus, the result is only allowing instantiation for those template arguments that meet the requirements of the implementations of the template (`T2`, `T3`, and `T5`), so we never get an error from the body of `min()`. Moreover, if we had some other overload of `min()` that might work for these types, overload resolution could have selected one of those instead of throwing an error.

The last type in our example, `X7`, illustrates some of the subtleties of implementing instantiation-safe templates. In particular, if `X7` is passed to the non-instantiation-safe `min()` function, instantiation will succeed. However, the instantiation-safe `min()` rejects it because no value is implicitly convertible to `bool`. The distinction here is particularly subtle: An explicit conversion to `bool` can be used implicitly in certain contexts, including in Boolean conditions for control-flow statements (`if`, `while`, `for`, and `do`), the built-in `!=`, `==`, and `!` operators, and therefore the value is said to be contextually converted to `bool`.

However, our insistence on having a general, implicit conversion to `bool` has the effect that our instantiation-safe templates are overconstrained; that is, we specified requirements that the template needs to instantiate properly. (It is, on the other hand, underconstrained if we had entirely forgotten the conversion-to-`bool` requirement, and it would have allowed some template arguments that could cause an instantiation failure for types such as `X6`.)

To fix the instantiation-safe `min()`, I need a trait to determine whether a type is contextually convertible to `bool`. The control-flow statements are not a helpful way of defining this trait, because statements cannot occur within a SFINAE context, nor are the logical operators, which can be overloaded for an arbitrary type. Fortunately, the ternary operator `?:` is an expression and is not overloadable, so it can be exploited to test whether a type is contextually convertible to `bool`:

Click here to view code image

```cpp
#include <utility>      // for declval()
#include <type_traits>   // for true_type and false_type

template<typename T>
class IsContextualBool {
  private:
    template<typename U> static auto test(int)
      -> decltype(std::declval<U>() ? std::true_type() : std::false_type());

    template<typename> static auto test(...) -> std::false_type;

  public:
    static constexpr bool value = decltype(test<T>(nullptr))::value;
};
```

With this new trait, we can provide an instantiation-safe `min()` with the correct set of requirements in the SFINAE:

Click here to view code image

```cpp
#include "is_contextual_bool.hpp"
#include "is_convertible.hpp"

template<typename T>
EnableIf<IsContextualBool<T>, T const&>
min(T const& x, T const& y)
{
    if (y < x) {
        return y;
    }

    return x;
}
```

The techniques used here to make this instantiation-safe can be generalized to require requirements for multiple template parameters by composing various requirement checks into traits that describe entire classes of types, each of which is used as a requirement. Doing so has the advantages of both better overloading behavior and the elimination of the error “novels” that compilers tend to produce while printing errors deep within a nested template instantiation. On the other hand, the error messages provided tend to lack specificity regarding which particular operation failed. Moreover, as our small `main()` example shows, carefully determining and encoding the exact requirements of the template can be a daunting task. We explore debugging techniques that make use of these traits in Section 8.2 on page 54.

## 20.6 IN THE STANDARD LIBRARY

The C++ standard library provides iterator tags for input, output, forward, bidirectional, and random-access iterators, which we have used in our presentation. These iterator tags are part of the standard iterator traits (`std::iterator_traits`) and the requirements placed on iterators, so they can be safely used for tag dispatching purposes.

The C++11 standard library `std::enable_if` class template provides the mechanism used by the `EnableIf` class template presented here. The only difference is that the standard uses a lowercase member type named `type` rather than our uppercase `Type`.

Algorithm specialization is used in a number of places in the C++ standard library. For example, both the `std::advance()` and `std::distance()` have several variants based on the iterator category of their iterator arguments. Most standard library implementations tend to use tag dispatching, although, more recently, some have adopted `std::enable_if` to implement this algorithm specialization. Moreover, a number of C++ standard library implementations also use these techniques internally to implement algorithm specialization for various standard algorithms. For example, `std::copy()` can be specialized to call `std::memcpy()` or `std::memmove()` when the iterators refer to contiguous memory.

As introduced in Section 8.4 on page 13, the C++ standard library also has traits to determine if a type is a usable object type or an iterator, using SFINAE-based techniques in its requirements. For example, `std::vector` uses a constructor template to allow a vector to be built from an iterator sequence:

**Click here to view code image**

```cpp
using iterator_type = std::iterator_traits<Iterator>::value_type;
static_assert(std::is_same<iterator_type, typename Allocator::value_type>::value, "...");
```

with the requirement that “if the constructor is called with an input iterator whose `value_type` does not match the allocator's `value_type`, then the constructor shall not participate in overload resolution” (see §23.2 para 34 [C++11]). This phrasing is vague enough to allow the most efficient techniques of the day to be used for the implementation, but at the time it was added to the standard, the use of `std::enable_if` was envisioned.

## 20.7 AFTERNOTES

Tag dispatching has been known in C++ for a long time. It was used in the original implementation of the STL (see [Stepanov1995, STL]), and is often used alongside traits. The use of SFINAE and EnableIf is much newer: The first edition of this book (see [VandevoordeJosuttis]) introduced the term SFINAE and demonstrated its use for detecting the presence of member types, for example.

The “enable if” technique and terminology was first published by Jaakko Järvi, Jeremiah Willcock, Howard Hinnant, and Andrew Lumsdaine in [Vandevoorde2003], which describes the “dropout” technique to implement function overloading with `EnableIf` (and `DisableIf`) pairs, and how to use `enable_if` with class template partial specializations. Since then, `SFINAE` and similar techniques have become ubiquitous in the implementation of advanced template libraries, including the C++ standard library. Moreover, the popularity of these techniques motivated the extended SFINAE behavior in C++11 (see Section 17 on page 184).
