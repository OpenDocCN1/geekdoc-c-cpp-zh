
```cpp
template<int N> struct X {
    static int const c = 2;
};

template<> struct X<0> {
    typedef int c;
};

template<typename T> struct Y {
    static int const c = 3;
};

static int const c = 4;

int main()
{
    std::cout << X<10>::c << '\n';
    std::cout << X<0>::c << '\n';
}
```

This is a valid C++98 program that outputs 0. It is also a valid C++11 program, but there are three different ways to interpret the parameterized expressions, and the output is 0 0.

A similar problem existed because of the existence of the digraph `<:` as an alternative for the `[` character (which is not available on some traditional keyboards). Consider the following example:

```cpp
template<typename T>
struct S { };

S<::T> s;              // valid since C++11, but an error before
```

Before C++11, that last line of code was equivalent to `S[:T>` which clearly was invalid. Another “lexical hack” was added to address that problem. When a compiler sees the characters `<::` not immediately followed by `:` or `>`, the leading pair of characters `<:` is not treated as a digraph to `[`. This applies only when the sequence is not followed by one of those characters.

```cpp
#define R(x) #x

int main()
{
    int i = 1, 2, 3, i = 1;    // valid in C++98/03, but an error
                                // in C++11
}
```

To understand this, note that the “digraph hack” applies to preprocessing tokens, which are the kinds of tokens acceptable to the preprocessor (they may not be acceptable after preprocessing has completed), and they are decided before macro expansion completes. With that in mind, the C++98/C++03 conditionally transforms `<::` into `[` in the macro invocation, and the definition of `x` transforms to:

```cpp
int a[ ] = { 1 };
```

which is perfectly fine in C++11. However, C++11 does not perform the digraph transformation because, before macro expansion, the sequence `<::` is not followed by `:` or `>`. Without the digraph transformation, the concatenation operator is used and the result is a preprocessing token.

## 13.3.2 Dependent Names of Types

The problem with names in templates is that they cannot always be sufficiently classified. In particular, one template cannot look into another template because the contents of that other template can be made invalid by an explicit specialization. The following contrived example illustrates this:

```cpp
class Vector {
public:
    ...
    void pod() {}
    T* xp; // declaration of multiplication?
    ...
};

template<>
class Trapezoid : public Vector {
public:
    void f(int) {}
    // Error: no type here
};

void f(Vector& v, bool b)
{
    v.pod(); // OK
}
```

At the point where the compiler is parsing line 42, it must decide whether it is declaring a declaration or a multiplication. This decision in turn depends on whether the dependent qualified name `Trapezoid<T>::x` is a type name. It may be tempting to look in the template at the point of definition first, and assuming line 41, `T* x` is a type and `x` is what would be chosen if there were no specialization. However, a rule to this effect would make the following code invalid (we show this in this case where `v` is valid). In this case, `T` is a template. In this case, `T::x` is a dependent type because the type depends on the template parameter. Moreover, `T::x` refers to an unknown specialization described in Section 13.2.4 on page 220, which means that the compiler cannot safely look inside the template to determine whether the name `Trapezoid<T>::x` is a type or not. Had the code specified `typename` at line 42, `T::x` would be treated as a type. The compiler could have looked up the template definition, but that specialization could intervene. Also, when the parsing code is entered, the entire translation unit is available in memory. However, the compiler has to parse the entire translation unit in order to understand the meaning. This task would be enormous if it required the compiler to parse all the template definitions each time it encountered a template-id. Therefore, the compiler parses a template-id as equivalent to a qualified name lookup for nondependent types.

However, as illustrated by the example, name lookup into an unknown specialization is still a problem. The language definition addresses this issue by stating that names in a template definition are assumed not to name types unless a name is qualified with the keyword `typename`. If this rule fails, or without rebinding template arguments, the name is not the name of a type, the program is ill-formed and your C++ compiler should complain at instantiation time. Note that this rule does not provide any help; it just gives an indication as to whether a type is involved. The typename prefix to a name is required when the name satisfies all of the following conditions:

- 1. It is qualified and not itself followed by `::` to form a more-qualified name.
- 2. It is not part of an elaborated-type-specifier (i.e., a type name that starts with one of the keywords `class`, `struct`, `union`, or `enum`).
- 3. It is not used in a base class specification or in a list of member initializers (including a mem-initializer).
- 4. It is dependent on a template parameter.
- 5. It is a member of an unknown specialization, meaning that the type named by the qualified name refers to an unknown specialization.

Furthermore, the typename prefix is not allowed unless at least the first two previous conditions hold. To illustrate this, consider the following erroneous example:

```cpp
template<typename T>
struct S {
    typedef int X;
};
template<typename T>
class C {
    typename T::X x1; // declaration of pointer
    typename T::X x2; // multiplication?
    S<int>::X x3;
    typename S<int>::X x4;
};
typedef int Y;
using OldType = Y;
typename OldType x5;
```

Each occurrence of `typename`—correct or not—is numbered with a subscript for easy reference. The first, `typename`, introduces a template parameter. The previous rule does not apply to this first use. The second and third occurrences are in error. They are intended to be type names. The fourth occurrence is in error. The fifth occurrence is correct because the qualified name is dependent. The sixth occurrence is in error because of condition 2: the name is part of an elaborated-type-specifier. The seventh occurrence is in error because the name is dependent, but the keyword `typename` is required.

Rules for determining whether a type refers to a current instantiation or an unknown specialization were given in the previous section. In such cases, it is safest to simply add the `typename` keyword to indicate that you intend the qualified name that follows to be a type. The `typename` keyword, even if it's optional, will provide documentation of your intent.

## 13.3.3 Dependent Names of Templates

A problem very similar to the one encountered in the previous section occurs even when a name of a template is dependent. In general, a C++ compiler is required to treat a `<` following the name of a template as the beginning of a template argument list; otherwise, it is a less-than operator. As is the case with type names, a compiler has to assume that a dependent name does not refer to a template unless the programmer provides extra information using the keyword `template`.

```cpp
template<typename T>
class Shell {
public:
    template<int N>
    class In {
    public:
        template<int M>
        class Deep {
        public:
            virtual void f() {};
        };
    };
};

template<typename T, int N>
class Weird {
public:
    void case1(
        Shell<T>::template In<N>::template
        Deep<>* p) {
        p->template Deep<0>::f(); // explicit virtual call
    }

    void case2(
        typename Shell<T>::template In<N>::template
        Deep<>* p) {
        p->template Deep<0>::f(); // explicit virtual call
    }
};
```

This somewhat intricate example shows how all the operators that can qualify a name (`.`, `->`, `::`, and `>`) may need to be followed by the keyword `template`. Specifically, this is the case whenever the type of the object or expression preceding the qualifying operator is dependent on a template parameter and refers to an unknown specialization, and the name that follows the operator is a template (in other words, a template name followed by template arguments using angle brackets). For example, in the expression

`p->template Deep<0>::f();`

the type of `p` depends on the template parameter `T`. Consequently, a C++ compiler cannot look up `Deep` to see if it is a template, and the user must explicitly indicate that `Deep` is a template by inserting the prefix `template`. Without this prefix, `p->Deep<N>` is parsed as the less-than operator. Note also that this may need to happen multiple times within a qualified name because qualifiers themselves may be qualified with a dependent qualifier. (This is illustrated by the declaration of the parameters of `case1` and `case2` in the previous example.)

If the keyword `template` is omitted in cases such as these, the opening and closing angle brackets are parsed as less-than and greater-than operators. As with the `typename` keyword, one can safely add the `template` prefix to indicate that the following name is a template, even if the template prefix is not strictly needed.

## 13.3.4 Dependent Names in Using Declarations

Using declarations can bring in names from two places: namespaces and classes. The namespace case is not relevant in this context because there are no such things as namespace templates. Using declarations that bring in names from classes, on the other hand, can bring in names only from a derived class. Such using declarations behave like members of the derived class to access the base class members, allowing them to be accessed as if they were actually members declared in that derived class. A short but important example illustrates the difference between these two versions:

```cpp
class X {
public:
    void f(int);
    void f(char const*);
    void g();
};

class DX : private X {
public:
    using X::f;
};
```

The previous using declaration brings in the name `f` of the base class `X` into the derived class `DX`. In this case, this name is associated with two different declarations, thus emphasizing that we are dealing with a nondependent name. Note also that this kind of using declaration can also be used to introduce names into a class template. The base class `X` and its members are private to the class `DX`, except that the functions `f` have been introduced to the public interface of `DX` and are therefore available to the clients of `DX`.
