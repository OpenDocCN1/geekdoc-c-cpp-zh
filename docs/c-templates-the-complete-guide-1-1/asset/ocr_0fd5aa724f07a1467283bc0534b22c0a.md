In this version of `PlusResult`, we add a template parameter with a default argument that determines if the first two parameters support addition as determined by our `HasPlusT` trait above. We then partially specialize `PlusResult` for false values of that extra parameter, and our partial specialization definition has no members at all, avoiding the problem we described. For cases where addition is supported, the default argument evaluates to true and the primary template is selected, with our existing definition of the `Type` member. Thus, we fulfill the contract that `PlusResult` provide the result type only if in fact the `+` operation is well-formed. (Note that the added template parameter should never have an explicit template argument.)

Consider again the addition of `Array<T>` and `Array<T>`: With our latest implementation of the `PlusResult` template, the instantiation of `PlusResult<Array<T>, Array<T>>` has a `Type` member whose `Type` is `Array<T>`, but we are not able to add `Array<T>` objects. Therefore, the result type of the array `operator+` template is invalid, and SFINAE will eliminate that function template from the overload set. The result of the function template `operator+` will therefore be chosen.

As a general design principle, a trait template should never fail at instantiation time if given reasonable template arguments as inputs. And the general approach is often to perform the corresponding check twice:

+   1. Once to find out whether the operation is valid
+   2. Once to compute its result

We saw that already with `PlusResult<T>`, where we call `HasPlusT<T>` to find out whether the call of `operator+` in `PlusResult<T>` is valid.

Let's apply this principle to `IsConvertible` to introduce a section of traits again. In practice, we form a container type having a member type `value_type`. Since the corresponding type is `true`, while `false` is chosen if the container type has no such a `value_type` member:

[Click here to view code image]

```
template<typename C, bool = HasValueTypeT<C>::value>
struct IsConvertibleT {
  using Type = typename C::value_type;
};

template<typename C>
struct IsConvertibleT<C, false> {
};
```

A third example of making traits SFINAE-friendly is shown in Section 19.7.2 on page 444, where `HasNoexceptMoveConstructorT` first has to check whether a move constructor exists before checking whether it is declared with `noexcept`.

# 19.5 IS CONVERTIBLE

Details matter. And for that reason, the general approach for SFINAE-based traits might become more complicated in practice. Let's illustrate this by defining a trait that can determine whether a given type is convertible to another given type—for example, if we expect a certain base class to be one of its derived classes. The `IsConvertibleT` trait should determine whether we can convert a passed first type to a passed second type:
