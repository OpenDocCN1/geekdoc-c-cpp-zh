
```cpp
// special cases to avoid endless recursion with templates
template<>
struct IsPrime<0> { static constexpr bool value = false; };

template<>
struct IsPrime<1> { static constexpr bool value = false; };

template<>
struct IsPrime<2> { static constexpr bool value = true; };

template<>
struct IsPrime<3> { static constexpr bool value = true; };
```

The `IsPrime<>` class template returns in its `value` member whether the passed template parameter is a prime number. To achieve this, it instantiates `IsPrime<n>::value`, which recursively expands to an expression checking for each divisor between 2 and `p/2` whether this divisor divides the number without remainder.

For example, the expression

`IsPrime<9>::value`

expands to

`DoIsPrime<9,4>::value`

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_105_0.png)

`9%4 != 0 && DoIsPrime<9,3>::value`

which expands to

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_105_1.png)

`9%4 != 0 && 9%3 != 0 && DoIsPrime<9,2>::value`

which expands to

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_105_2.png)

`9%4 != 0 && 9%3 != 0 && 9%2 != 0`

which evaluates to `false`.

As this chain of instantiation demonstrates:

- We use recursion expansion of `DoIsPrime<>` to iterate over all divisors from `p/2` down to 2 to find out whether any of these divisors divide the given integer exactly, i.e. without remainder.
- The partial specialization of `DoIsPrime<>` for `d` equal to 2 serves as the criterion to end the recursion.

Note that all this is done at compile time. That is,

`IsPrime<9>::value`

expands to `false` at compile time.

The template syntax is arguably clumsy, but code similar to this has been valid since C++98 (and earlier) and has proven useful for quite a few libraries.

See Chapter 3 for details.

### 8.2 COMPUTING WITH CONSTEXPR

C++11 introduced a new feature, `constexpr`, that greatly simplifies various forms of compile-time computation. In particular, given proper input, a `constexpr` function can be evaluated at compile time. While C++11 `constexpr` functions were introduced with stringent limitations (e.g., each `constexpr` function definition was essentially limited to consist of a return statement), most of these restrictions were removed with C++14. Of course, successfully evaluating a `constexpr` function still requires that all computation steps be possible and valid at compile time. Currently, that excludes things like heap allocation or throwing exceptions.

Our example to test whether a number is a prime number could be implemented as follows in C++14:

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_105_3.png)

```cpp
constexpr bool
doIsPrime (unsigned p, unsigned d)  // p is number to check
{
    return d > 2 ? (p%d != 0 && doIsPrime(p,d-1))  // check
                 : (p%2 != 0);                     // end of recursion
}
```

```cpp
constexpr bool isPrime (unsigned p)
{
    return p < 4 ? p > 1 : (p % 2) ? doIsPrime(p, p/2) : false; // handle special cases and start recursion
}
```

Due to the limitation of having only one statement, we can only use the conditional operator as a selection mechanism, and we still need recursion to iterate over the elements. But the syntax is ordinarily C++ function code, making it more accessible than our first version relying on template instantiation.

With C++14, constexpr functions can make use of most control structures available in general C++ code. So, instead of writing overly templated code or somewhat arcane one-liners, we can now just use a plain for loop:

```cpp
constexpr bool isPrime (unsigned int p)
{
    for (unsigned int d=2; d<=p/2; ++d) {
        if (p % d == 0)
            return false;   // found divisor without remainder
    }
    return p > 1;           // no divisor without remainder
}
```

With both the C++11 and C++14 versions of our `constexpr isPrime()` implementations, we can simply call

`isPrime(5)`

to find out whether 5 is a prime number. Note that it can do so at compile time, but it must not necessarily do so. In a constant expression—a compile-time value (e.g., an array length or a non-type template argument)—the compiler will attempt to evaluate a call to a constexpr function at compile time and use its result if it is found to be possible (or can be produced in the end). In other contexts, the compiler may or may not attempt the evaluation at compile time. But if such an evaluation fails, no error is issued and the call is left as a run-time call instead.

For example:

```cpp
constexpr bool b1 = isPrime(5);   // evaluated at compile time
```

will compute the value at compile time. The same is true with

```cpp
const bool b2 = isPrime(3);       // evaluated at compile time if isPrime is constexpr
```

provided `b2` is defined globally or in a namespace. At block scope, the compiler can decide whether to compute it at compile or run time. This, for example, is also the case here:

```cpp
bool fIsPrime(int p)
{
    return isPrime(5);            // evaluated at compile time
}
```

the compiler may or may not evaluate the call to `isPrime` at compile time.

On the other hand:

```cpp
int x;
std::cout << isPrime(x);          // evaluated at run time
```

will generate code that computes at run time whether `x` is a prime number.

### 8.3 EXECUTION PATH SELECTION WITH PARTIAL SPECIALIZATION

An interesting application of a compile-time test such as `isPrime()` is to specialize at compile time between different implementations.

`boxes/len1.cpp`

```cpp
// number of elements to a raw array:

template<typename T, unsigned N>
size_t len (T (&)[N])
{
    return N;
}
```

```cpp
// number of elements for a type having size_type:

template<typename T>
typename T::size_type len (T const& t)
{
    return t.size();
}
```

Here, we define two function templates len() taking one generic argument and then:

- The first function template declares the parameter as `T (&)[N]`, which means that the parameter has to be an array of N elements of type T.
- The second function template declares the parameter simply as `T`, which places no constraints on the parameter but returns type `T::size_type`, which requires that the passed argument type has a corresponding member `size_type`.

When passing a raw array of string literals, only the first function template `len()` matches:

```cpp
int a[10];
std::cout << len(a);        // OK: only len() for array matches
std::cout << len("type");   // OK: only len() for array matches
```

According to its signature, the second function template also matches when substituting (respectively) `int[]` and `char const (&)[?]`, but those substitutions lead to invalid code in the return type `T::size_type`. The second template is therefore ignored for these calls.

When passing an `std::vector<>`, only the second function template matches:

```cpp
std::vector<int> v;
std::cout << len(v);   // OK: only len() for a type with
                      // size_type matches
```

When passing a raw pointer, neither of the templates match (without a fallback). As a result, the compiler will complain that no matching `len()` function is found.

```cpp
int* p;
std::cout << len(p);   // ERROR: no matching len() function found
```

Note that this differs from passing an object of a type having a `size_type` member, but no `size()` member function, as, for example, is the case for `std::allocator<T>`:

```cpp
std::allocator<T> x;
std::cout << len(x);   // ERROR: len() function found,
                      // but can't call size()
```

```cpp
// fallback for all other types

std::size_t len (...)
{
    return 0;
}
```

Here, we also provide a general `len()` function that always matches as the worst match (match with ellipsis (`...`)) in overload resolution (see Section C.2 on page 653).

So, for arrays and vectors, we have two matches where the specific match is the better match. For pointers, only the fallback matches so that the compiler no longer complains about a missing `len()` for this call. But for the allocator, the second and third function templates match, with the second function template as the better match. So, still, this results in an error that no `size()` member function can be called:

```cpp
int a[10];
std::cout << len(a);          // OK: len() for array is
                              // best match
std::cout << len(&a[0]);       // OK: len() for array is best
                              // match

std::vector<int> v;
std::cout << len(v);           // OK: len() for a type with
                              // size_type is best match

std::list<int> v;
std::cout << len(v);           // OK: only fallback len()
                              // is used

std::allocator<int> a;
std::cout << len(a);           // ERROR: 2nd len() function
                              // matches best,
                              // but can't be called
```

Because for a `std::allocator`, no `size()` can be called.

See Section 19.4 on page 674 for a more detailed discussion of SFINAE and some applications of SFINAE.

### SFINAE and Overload Resolution

Over time, the SFINAE principle has become so important and so prevalent among template designers that the abbreviation has become a verb. We say “we SFINAE out a function” if we remove a function from the overload set by exploiting the SFINAE mechanism to ensure that function templates are ignored for certain constraints by instrumenting the template code to remain invalid for some constraints. And whenever you read in the C++ standard that a function template “shall not participate in overload resolution unless...” it means that SFINAE is used to “SFINAE out” that function template for certain cases.

For example, class `std::thread` declares a constructor:

```cpp
namespace std {
class thread {
public:
    template<typename F, typename... Args>
    explicit thread(F&& f, Args&&... args);
};
}
```

with the following remark:

> **Remark:** This constructor shall not participate in overload resolution if `decay_t<F>` is the same type as `std::thread`.

This means that the template is constrained to be ignored if it is called with a `std::thread` as first and only argument. The reason is that otherwise a member template like this sometimes might better match than any predefined copy or move constructor (see Section 6.2 on page 95 and Section 16.2.4 on page 353 for details). By SFINAE'ing out the constructor template when called for a thread, we ensure that the predefined copy or move constructor always wins when a thread gets constructed from another thread.
