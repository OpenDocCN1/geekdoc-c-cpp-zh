
name, we don't know whether it's the name of a type, a template, or something else.

[Click here to view code image](#)

```cpp
template<typename T>
class X {
 public:
   using MyType = T;
   template<typename U>
   struct Magic;
};
```

Again, if we want a dependent name to be brought in by a using declaration to denote a type, we must explicitly say so by inserting the keyword `typename`. Strangely, the C++ standard does not provide for a similar mechanism to mark such dependent names as templates. The following snippet illustrates the problem:

[Click here to view code image](#)

```cpp
template<typename T>
class X {
 public:
   using B = X<T>::template Magic; // error: not a standard
};
```

The standardization committee has not been inclined to address this issue. However, C++11 alias templates do provide a partial workaround:

[Click here to view code image](#)

```cpp
template<typename T>
class X {
 public:
   template<typename U>
   using Magic = X<T>::template Magic<U>;
};
```

This is a little unwieldy, but it achieves the desired effect for the case of class templates. The case of function templates (arguably less common) remains unaddressed, unfortunately.

### 13.3.5 ADL and Explicit Template Arguments

Consider the following example:

[Click here to view code image](#)

```cpp
namespace X {
  class X {
  };
  template<int I> void select(X*);
}

void g (X::X* xp) {
  select<3>(xp);  // ERROR: no ADL!
}
```

In this example, we may expect that the template `select<>` is found through ADL in the call `select<3>(xp)`. However, this is not the case because a certain amount of code that is a function call argument will not be parsed until it has decided that `<3>` is a template argument list. Furthermore, a compiler cannot decide that `<3>` is a template argument list until it has found `select` (to be a template). Because this chicken-and-egg problem cannot be resolved, the expression is parsed as `select < 3 > (xp)`, which makes no sense.

This example may give the impression that ADL is disabled for template-ids, but it is not. The code can be fixed by introducing a function template that is named `select` within the call:

[Click here to view code image](#)

```cpp
template<typename T>
void select(T);

void g (X::X* xp) {
  select<>(xp);
}
```

Even though it doesn't make any sense for the call `select<>(xp)`, the presence of this function template ensures that `select<>` will be parsed as a template-id. ADL will then find the function template `X::select`, and the call will succeed.

### 13.3.6 Dependent Expressions

Like names, expressions themselves can be dependent on template parameters. An expression that depends on a template parameter can behave differently from one instantiation to the next—for example, selecting a different overloaded function or producing a different type or constant value. Expressions that do not depend on a template parameter, in contrast, are constant, and provide the same behavior in all instantiations.

An expression can be dependent on a template parameter in several different ways. An expression is not type-dependent if it is a nondependent name for which name lookup can be completely determined at the time that the template is parsed.

### 13.3.7 Compiler Errors

A C++ compiler is permitted (but not required) to diagnose errors at the time the template is parsed when all of the instantiations of the template would produce that error. Let's expand on the `f(x)` example from the previous section to explore this further:

Click here to view code image

```cpp
void f() {
}

template<typename T> void nondependentCall()
{
    f(x);        // x is value-dependent, so f() is nondependent
}
```

Here, the call `f(x)` will produce an error in every instantiation because `f` is a nondependent name and the only visible `f` accepts zero arguments, not one. A C++ compiler can produce an error when parsing the template body right away, while it can produce an instantiation-dependent error only when the template is instantiated.

Click here to view code image

```cpp
template<typename T>
void instantiationDependentSound()
{
    constexpr int x = sizeof(T);
    constexpr int y = sizeof(T) + 1;
    int a[x - y];       // x-y will always have a negative size
                        // in all instantiations
}
```

## 13.4 INHERITANCE AND CLASS TEMPLATES

Class templates can inherit from one or be inherited from. For many purposes, there is nothing significantly different between the template and nontemplate classes. However, there is one important subtlety when deriving a class template from a base class referred to by a dependent name. Let's first look at the simplest case of a nondependent base class.

### 13.4.1 Nondependent Base Classes

In a class template, a nondependent base class is one with a complete type that can be determined without knowing the template arguments. In other words, the name of this base is treated using a nondependent name. Let's start with an example.

Click here to view code image

```cpp
template<typename T>
class Base
{
    int b;
    using X = int;
};

class D1 : public Base<double> {      // not a template
public:
    void f() { b = 3; }               // normal access to
};                                    // inherited member
```

Nondependent bases in templates behave very much like bases in ordinary nontemplate classes, but there is a slightly unfortunate surprise: When an unqualified name is looked up in the template definition, the nondependent bases are considered before the list of template parameters. This means that in the previous example, the member `b` is found in the base class.

Click here to view code image

```cpp
void g() {
    D2<int> d2;
    d2.strange = p;        // error: type mismatch
}
```

This is counterintuitive and requires the writer of the derived template to be aware of names in the independent base from which it derives—even when that derivation is indirect or the names are private. It would probably have been preferable to have template parameters in the scope of the entity that defines the template.

### 13.4.2 Dependent Base Classes

In the previous example, the base class is fully determined. It does not depend on a template parameter. This implies that a C++ compiler can look up any unqualified names in these base classes as soon as the template definition is seen. An alternative—not allowed by the C++ standard—would result in deferring the lookup of such names until the template is instantiated. In a template, a nondependent name is looked up as soon as it is encountered. Keeping this in mind, consider the following example:

Click here to view code image

```cpp
template <class T>
class DB : public Base<T> {        // dependent base
public:
    void f() {
        basefield = 0;             // ? basefield
    }
};

template<>                            // explicit specialization
class Base<double> {
public:
    int i;
};

void g (DB<double>& d)
{
    d.f();                            // ? scope?
}
```

At point 1 we find our reference to a nondependent name basefield. It must be looked up right away. Suppose we look it up in the template Base and bind it to the int member that we find there. However, shortly after this we override the specialization definition of Base with an explicit specialization. At this point, this specialization changes the meaning of the basefield member to which we originally committed. So, when we instantiate the definition of DB at point 3, we find that we too eagerly bound the nondependent name at point 1. There is no modifiable basefield in DB<double> that was specialized at point 2, and an error message should have been issued.

To circumvent this problem, standard C++ says that nondependent names are not looked up in dependent base classes (but they can still be looked up as soon as they are encountered). So, a standard C++ compiler must emit a diagnostic at point 1. To correct the code, it suffices to make the name a dependent name (by introducing a dependency) so that the name is looked up only at the time of instantiation, and at that time the concrete base instance that must be used is specified. For example, at point 3, the compiler will know that the base class of DB<double> is Base<double> and thus has been explicitly specialized by the programmer. In this case, our preferred way to make the name dependent is as follows:

Click here to view code image

```cpp
// Variation 2:
template<class T>
class DB : public Base<T> {
public:
    void f() {
        this->basefield = 0;        // lookup delayed
    }
};
```

An alternative consists in introducing a dependency using a qualified name:

Click here to view code image

```cpp
// Variation 3:
template<typename T>
class DB : public Base<T> {
public:
    void f() {
        if (Base<T>::basefield = 0) {  // lookup delayed
        }
    }
};
```

Care must be taken with this solution, because if the unqualified nondependent name is used to form a virtual function call, then the qualification inhibits the virtual call semantics and the meaning of the program changes. Nonetheless, there are situations when the first variation cannot be used and this alternative is appropriate:

```cpp
template<typename T>
class DB : public Base<T> {
public:
    void f() {
        DB<T>::basefield = 0; // lookup delayed
    }
};
```

Now we have used DB<T>:: instead of Base<T>:: in this example. In this case, either one works. In multiple-inheritance cases, however, we may not know which base class provides the desired member (in which case using the derived class for qualification works) or multiple base classes may declare the same name (in which case we may have to use a specific base class name for disambiguation).
