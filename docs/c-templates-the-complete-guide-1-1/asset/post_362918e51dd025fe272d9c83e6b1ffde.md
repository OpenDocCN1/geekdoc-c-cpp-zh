
## 15.6 RVALUE REFERENCES

C++11 introduced rvalue references to enable move semantics, including move construction and perfect forwarding. This section describes the interactions between rvalue references and deduction.

### 15.6.1 REFERENCE COLLAPSING RULES

Programmers are not allowed to directly declare a reference to a reference:

Click here to view code image

```cpp
int const& r = 42;
int const& & r2 = r;  // ERROR: reference to reference is not allowed
```

However, when composing types through the substitution of template parameters, type aliases, or decltype constructs, such situations are permitted. For example:

Click here to view code image

```cpp
using T = int&;
int&& r = 42;
T&& r2 = r;       // T&& is then int&
```

The rules that determine the type resulting from such a composition are known as the reference collapsing rules. If `&` and `&&` are combined in a type, the resulting reference is always an lvalue reference. If two rvalue references are combined, the result is an rvalue reference. Table 15.1, which can be summarized as “if either reference is an lvalue reference, so is the resulting type; otherwise, it is an rvalue reference.”

| Inner reference | Outer reference | Resulting reference |
|---|---|---|
| `&` | `&` | `&` |
| `&` | `&&` | `&` |
| `&&` | `&` | `&` |
| `&&` | `&&` | `&&` |

*Table 15.1. Reference Collapsing Rules*

One more example shows these rules in action:

Click here to view code image

```cpp
using T = int const&;
volatile T&& r1 = 42;  // OK: && type int const&
using R = int&&;
R&& r2 = 42;
```

Here `volatile` is applied on top of the reference type (`T` alias for `int const`) and is therefore discarded. An rvalue reference is then placed on top of that type, but since the underlying type is an lvalue reference and lvalue references “take precedence” in the reference collapsing rule, the overall type remains `int const&`. (Of course, this is equivalent to applying `const` on top of `r1`.) The `volatile` is discarded, and applying an rvalue reference on top of the resulting lvalue reference type still leaves `r2` with an rvalue reference type in the end (which is able to bind an rvalue like 42).

### 15.6.2 FORWARDING REFERENCES

As introduced in Section 6.6 on page 61, template argument deduction behaves in a special way when a function parameter is a forwarding reference (an rvalue reference to a template parameter of that function template). In this case, template argument deduction considers not just the type of the function call argument but also whether that argument is an lvalue or an rvalue. In the cases where the argument is an lvalue, the type determined by template argument deduction is an lvalue reference to the argument type, and the reference collapsing rules (see above) ensure that the parameter type is an lvalue reference to that type. For example:

Click here to view code image

```cpp
template<typename T> void f(T&& p); // p is a forwarding reference

void g()
{
    int i;
    int& r = i; // An lvalue reference
    f(i);       // argument is an lvalue: T is int&
    f(r);       // argument is an lvalue: T is int&
    f(1);       // argument is an rvalue: T is int
}
```

In the call `f(i)`, the template parameter `T` is deduced to `int&`, since the expression is an lvalue of type `int`. Substituting `T` for `int&` in the parameter type `T&&` implies reference collapsing, and we apply the rule `& + & = &` to resolve the resulting parameter type `int&`, which is the parameter type used for the call `f(i)`. In the call `f(1)`, the argument is an rvalue and the template parameter is therefore deduced to be `int`, so the parameter type is `int&&`.

Click here to view code image

```cpp
template<typename T> void f(T&& p) // p is a forwarding reference
{
    T&& x; // For passed lvalues, x is a reference
    ...
}
```

This means that the definition of the function `f` above needs to be carefully written to ensure that all uses of `T` (including the return type) are written in a way that works properly with lvalue arguments. To deal with this situation, the `std::is_lvalue_reference()` type trait is frequently used to determine whether `T` is a reference.

Click here to view code image

```cpp
template<typename T> void f(T&& p) // p is a forwarding reference
{
    static_assert(!std::is_lvalue_reference<T>::value,
                  "T is not a reference");
    ...
}
```

### 15.6.3 PERFECT FORWARDING

The combination of the special deduction rule for rvalue references and the reference collapsing rules makes it possible to write a function template with a parameter that accepts almost any argument and captures its special properties (its type and whether it is an lvalue or an rvalue). The function template can then "forward" the argument along to another function as follows:

Click here to view code image

```cpp
class C {
    ...
};

void g(C& c1)
{
    C c2;
    f(c1); // forwards C&
    f(c2); // forwards C&
    f(C()); // forwards C&&
}

template<typename T>
void f(T&& x)
{
    g(std::forward<T>(x)); // forward x to g()
}
```

The technique illustrated above is called perfect forwarding, because the result of calling `g()` indirectly through `f()` will be the same as if the code had called `g()` directly. No additional copies are made, and the same overloads (if any) will be selected.

In the case of `g()`, a function call with the function `f(C())` requires some additional explanation. In such an instantiation of `f`, the parameter `x` will have rvalue reference type or lvalue reference type. Regardless, the expression `x` will be an lvalue of the type that the argument had (reference) or will be an lvalue reference (if the original argument was an lvalue), so the result of the `static_cast` has the same type and lvalue- or rvalue-ness as the original argument, thereby achieving perfect forwarding.

As introduced in Section 6.1 on page 91, the C++ standard library provides a function template `std::forward<T>()` in header `<utility>` that should be used in place of `static_cast` for perfect forwarding. Using that utility template better documents the programmer's intent than the `static_cast` construct shown above and prevents errors such as omitting one of `T`; that is, the example above is more clearly written as follows.

Click here to view code image

```cpp
#include <utility>

template<typename T> void forwardTo(T&& x)
{
    g(std::forward<T>(x));    // forward x to g()
}
```

### PERFECT FORWARDING FOR VARIADIC TEMPLATES

Perfect forwarding combines with variadic templates, allowing a function template to accept any number of function call arguments and forward each of them along to another function:

Click here to view code image

```cpp
template<typename... T> void forwardTo(T&&... x)
{
    g(std::forward<T>(x)...);    // forward all x to g()
}
```

The arguments in a call to `forwardTo()` will independently deduce a type for this parameter pack `T&&` (see Section 5.5 on page 55) so that the types and lvalue- or rvalue-ness of each argument is captured. The pack expansion (see Section 12.4.1 on page 291) in the call to `g()` will then forward each of these arguments using the perfect forwarding technique explained above.

Despite its name, perfect forwarding is not, in fact, “perfect” in the sense that it does not capture all interesting properties of an expression. For example, it does not distinguish whether an rvalue is a bit-field value, nor does it capture whether the expression has a specific constant value. The latter causes problems particularly when we're dealing with the null pointer constant, which is usually of integer type but which would be the constant value zero. Since the constant value of an expression is not captured by perfect forwarding, overload resolution in the following example will behave differently for the direct call `g(0)` than for the forwarded call to `g()`:

Click here to view code image

```cpp
void g(int*);
void g(...);

template<typename T> void forwardTo(T&& x)
{
    g(std::forward<T>(x));    // forward x to g()
}

void foo()
{
    g(0);                     // calls g(int*)
    forwardTo(0);             // essentially calls g(...)
}
```

This is yet another reason to use `nullptr` (introduced in C++11) instead of `NULL` pointer constants:

Click here to view code image

```cpp
g(nullptr);                 // calls g(int*)
forwardTo(nullptr);          // essentially calls g(int*)
```

All of our examples of perfect forwarding focus on the use of function arguments while maintaining their precise type and whether it is an lvalue or rvalue. The same problem occurs when forwarding the return value of a call to another function, with precisely the same type and value category—a generalization of lvalues and rvalues discussed in Appendix B. The `decltype` facility introduced in C++11 (and described in Section 15.10.2 on page 596) enables this use as well:

Click here to view code image

```cpp
template<typename T>
auto forwardTo(T&& x) -> decltype(g(std::forward<T>(x)))
{
    return g(std::forward<T>(x));    // forward all x to g()
}
```

Note that the expression in the return statement is copied verbatim into the `decltype` type, so that the exact type of the return expression is computed. Moreover, the trailing return type is used (i.e., the `auto` placeholder before the function name and the `->` indicate the return type) so that the function parameter pack is in scope for the `decltype` type. This forwarding function “perfectly” forwards all arguments to `g()` and then “perfectly” forwards its result back to the caller.
