
code. However, we may know that from a low-level point of view, the code for `List<int>::append()` and `List<double>::append()` is the same. The template mechanism should generate essentially the same machine code, performing the same operations, and only the type of the parameter is different. Although this cannot be expressed in C++, we can achieve something similar by avoiding that all `List`s of pointers should be instantiated from a different template definition.

Click here to view code image

```cpp
template<typename T>
class List { // §
private:
    ListNode<T>* impl;

public:
    // ...
    inline void append(T x) {
        impl->append(x);
    }

    inline auto length() const {
        return impl->length();
    }
};
```

In this context, the original template at point x is called the primary template, and the later definition is called a partial specialization because the template arguments for which this template definition must be used are more specialized than those of the primary template. That is, our partial specialization is a specialization of a template parameter list declaration (`template<...>`) and a set of explicitly specified template arguments on the name of the class template (T in our example).

Our code contains a problem because `ListNode<T>` innocently contains a member of that name (see `ListNode<T>` type). To break the cycle, we can prevent the partial specialization with a full specialization:

Click here to view code image

```cpp
template<>
class List<void*> { // §
    void* append(void* p);
    size_t length() const;
};
```

This works because matching full specializations are preferred over partial specializations. As a result, all member functions of `List<T*>` are now defined (though usually inefficiently) in terms of the implementation of `List<void*>`. This is an effective way to combat code bloat (of which C++ compilers are often accused).

There exist several limitations on the parameter and argument lists of partial specialization declarations. Some of these are as follows:

- 1. The arguments of the partial specialization must match in kind (type, template, or value) the corresponding parameters of the primary template.
- 2. The parameter list of the partial specialization cannot have default arguments; the default arguments of the primary class template are used instead.
- 3. The non-type arguments of the partial specialization should be either dependent values or plain template parameter types. You cannot make more complex dependent expressions like `2*N` (where N is a template parameter).
- 4. The list of template arguments of the partial specialization should not be identical (ignoring renaming) to the list of parameters of the primary template.
- 5. If one of the template arguments is a pack expansion, it must occur at the end of a template argument list.

An example illustrates these limitations:

Click here to view code image

```cpp
template<typename T, int I = 3>
class C {
    // primary template
};

template<typename T>
class C<T, 3> {
    // ERROR: parameter kind mismatch
};

template<typename T, int I>
class C<T*, I> {
    // ERROR: no default arguments
};

template<typename T, int I>
class C<T, I, I> {
    // ERROR: no template argument difference from primary template
};

template<typename T, int I>
class C<T, I> {
    // ERROR: no significant difference from primary template
};

template<typename... Ts>
class C<Ts, 0> {
    // ERROR: pack expansion not at the end of the list
};

template<typename T, typename U, typename... Ts>
class C<T, U, Ts..., 0> {
    // ERROR: pack expansion not at the end of the list
};
```

Every partial specialization—like every full specialization—is associated with the primary template. When a template is used, the primary template is always the one that is looked up, but then the arguments are also matched against those of the associated specialization(s) (using template argument deduction, as described in Chapter 5) to determine which template implementation is picked. Just as with function template argument deduction, the SFINAE principle applies here: if, while attempting to match a partial specialization, an invalid construct is formed, that specialization is silently abandoned and another candidate is examined if one is left available. If no matching specializations are found, the primary template is used. If multiple matching specializations are found, the most specialized one (in the sense defined for overloaded function templates) is selected; if none can be called most specialized, the program contains an ambiguity error.

Finally, we should point out that it is entirely possible for a class template partial specialization to have more or fewer parameters than the primary template. Consider our generic template `List`, declared at point 2, again. We have already discussed how to optimize the list-of-pointers case, but we may want to do the same with certain pointer-to-member types. The following code achieves this for pointer-to-member-pointers:

```cpp
// partial specialization for any pointer type

class List<C*> { // #4
public:
    using ElementType = void*;

    void append(ElementType p) {
        impl->append(p);
    }

    inline std::size_t length() const {
        return impl->length();
    }
};
```

In addition to our observation regarding the number of template parameters, note that the common implementation defined at #4 to which all classes are transformed by this mechanism at point #5 is indeed a partial specialization (for the simple pointer case it is a full specialization). However, it is clear that the specialization at point #5 is more specialized than that at point #4; this is a partial ordering problem.

Moreover, it is even possible that the number of explicitly written template arguments can differ from the number of template parameters in the primary template. This can happen both with default template arguments and, in a far more useful manner, with variable templates:

```cpp
template<typename... Elements>
class Tuple {}; // primary example

template<typename T1>
class Tuple<T1> {}; // one-element tuple

template<typename T1, typename T2, typename... Rest>
class Tuple<T1, T2, Rest...> {}; // tuple with two or more
```

### 16.5 PARTIAL VARIABLE TEMPLATE SPECIALIZATION

When variable templates were added to the draft C++ standard, several of their specifications were overlooked, and some of those issues were not yet formally resolved. However, actual implementations generally agree on the handling of these issues.

Perhaps the most surprising of these issues is that the standard refers to the ability to partially specialize variable templates, but it does not describe how they are declared or what they mean. What follows is thus based on C++ implementations in practice (which do permit such partial specializations), and not on the C++ standard.

### 16.6 ALTERNATES

Full template specialization was part of the C++ template mechanism from the start. Function template overloading and class template partial specialization, on the other hand, came much later. The HP aC++ compiler was the first to implement function template overloading, and EDG's C++ front end was the first to implement class template partial specialization. The partial-ordering process described in this chapter was originally invented by Steve Adamczyk and John Spicer (who are both of EDG).

The ability of template specialization to terminate an otherwise infinitely recursive template definition (such as the IsPrime<> example presented in Section 14.1 on page 246) was known for a long time. However, Erwin Unruh deserves the credit for noting that this could lead to the interesting possibility of computing results at compile time using the template instantiation mechanism to perform nontrivial computations at compile time. We devote Chapter 17 to this topic.

You may legitimately wonder why only class templates and variable templates can be partially specialized. The reasons are mostly historical. It is probably possible to define the same mechanism for function templates (see Chapter 17). In some ways, the effect of overloading function templates is similar, but there are also some subtle differences. These differences are mostly related to the fact that only the primary templates need to be looked up when a use is encountered. The specializations are considered only afterward, to determine which implementation should be used. In contrast, all overloaded function templates must be brought into an overload set by looking them up, and they may come from different namespaces or classes. This increases the likelihood of unintentionally overloading a template name somewhat.

Conversely, it is also imaginable to allow a form of overloading of class templates and variable templates. Here is an example:

Click here to view code image

```cpp
// invalid overloading of class templates
template<typename T1, typename T2> class Pair;
template<int N1, int N2> class Pair;
```

However, there doesn't seem to be a pressing need for such a mechanism.
