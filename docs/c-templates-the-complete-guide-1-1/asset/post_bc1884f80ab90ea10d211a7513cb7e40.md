## Chapter 28 Debugging Templates

Templates raise two classes of challenges when it comes to debugging them. One set of challenges is definitely a problem for writers of complex software: How can we ensure that the templates we write will function for any template arguments that satisfy the conditions we document? The other class of problems is almost exactly the opposite: How can a user of a template find out which of the template parameters are involved in the problem?

Before we discuss these issues in depth, it is useful to contemplate the kinds of constraints that may be imposed on template parameters. In this chapter, we deal mostly with the constraints that lead to compilation errors when violated, and we call these constraints syntactic constraints. Syntactic constraints can include the need for a certain kind of constructor to exist, for a particular function call to be unambiguous, and so forth. The other kind of constraint we call semantic constraints. These constraints are much harder to verify mechanically. In the general case, it may even be impractical to do so. For example, we may require that there be a certain definition to a template type parameter (which is a syntactic constraint), but usually we’ll also require that the operator actually defines some sort of ordering on its domain (which is a semantic constraint).

The term concept is often used to denote a set of constraints that is repeatedly required in a template library. For example, the C++ standard library relies on such concepts as random access iterator and default constructible. With this terminology in place, we can say that debugging template code involves identifying a significant amount of determining how concepts are violated in the template implementation and in their use. This chapter delves into both design and debugging techniques that can make templates easier to work with, both for template authors and for template users.

### 28.1 Shallow Instantiation

When template errors occur, the problems are often found after a long chain of instantiations, leading to lengthy error messages like those discussed in Section 9.4 on page 143. To illustrate this, consider the following somewhat contrived code:

```cpp
template<typename T>
void f(T p)
{
    p = 0; // assumes T is pointer-like type
}

template<typename T>
void code(T p)
{
    clear(p);
}

template<typename T>
void shell(T const& p)
{
    code(p);
}

template<typename T>
void shell(T const& env)
{
    typename T::index i;
    middle(env);
}
```

This example illustrates the typical layering of software development: High-level definition templates like shell() rely on components that are lower-level; which themselves make use of basic facilities like code(). When we instantiate shell(), all the layers below it are also forced to be instantiated. In this example, a problem is revealed in the deepest layer: code() is instantiated with type int (from the use of T::index in shell()) and attempts to dereference a value of that type, which is an error.

The error is only detectable at instantiation time. For example:

```cpp
class Client
{
public:
    using Index = std::int32_t;

private:
    Client mClient;
    std::uint64_t mId;
};
```

A good generic diagnostic includes a trace of all the layers that led to the problem, but we also need to see to which information can appear naturally.

An excellent discussion of the core issues surrounding this problem can be found in [Fairbanks02], in which Bryce Adelstein Lelbach identifies two classes of approaches to determine whether a class template argument is valid: a syntactic one that attempts to identify the validity of an expression (e.g., `std::is_constructible`), and a semantic one that checks whether a given type is a legitimate match for a given template parameter. He also mentions that the resulting code is not always as efficient as the original code.

In our previous example, we could add in a small check that attempts to determine whether a value is a type.

```cpp
template<typename T>
void f(T t) {
    if constexpr (is_valid<T>) {
        ...
    }
    else {
        ...
    }
}
```

```cpp
template<typename T>
void f(T t) {
    if constexpr (std::is_class<T>::value) {
        ...
    }
    else {
        ...
    }
}
```

If the type that we pass in doesn't have the default constructor, an error is now diagnosed on the line where `std::is_class` was called. Not because the class is not actually true, but because the compiler attempts to instantiate the template for a type that doesn't have a default constructor. Unfortunately, many compilers still don't implement `std::is_class` well enough (or at least not correctly), and this approach still doesn't work. We can define a type to be used as a template parameter and use `std::is_class` to check whether the type is a class. This approach still doesn't work because of the first issue.

### Concept Checking

Clearly, the development of the dummy code in our example can become tedious. We need a better way to check whether a given template argument satisfies the syntactic requirements of a template. To meet this complexity, it is natural to introduce a concept in the language to check whether a type is valid for a template. The concept is a compile-time predicate that can be used to check whether a template argument is valid. This approach is more efficient than previous approaches and is the one currently used by the Standard Library. The most popular such library is Boost (see [Boost]).

Unfortunately, the technique isn't particularly portable (the way errors are diagnosed differs considerably from one compiler to another) and sometimes masks issues that cannot be expressed at a higher level.

Once we have concepts in C++ (see Appendix A), we will have other ways to specify requirements and expected behavior.

### 28.2 Static Assertions

The `static_assert` macro is often used in C++ code to check that some particular condition holds at a certain point within the program's execution. If the condition does not hold, the program is (mostly) halted by the compiler and an error message is issued.

```cpp
static_assert(sizeof(void*) >= 8, "64-bit code generation required for this library.");
```

Static assertions can be used to provide useful error messages when a template argument does not satisfy the constraints of a template. For example, using the techniques described in Section 19.6, we can create a type trait to determine whether a given type is dereferenceable.

```cpp
template<typename T>
struct is_dereferenceable
{
    static constexpr bool value = ...;
};
```

```cpp
template<typename T>
class HasDereference {
private:
  template<typename U> struct Identity;

  template<typename U>
  static auto test(int) -> decltype(std::declval<U>());

  template<typename>
  static std::false_type test(...);

public:
  static constexpr bool value = decltype(test<T>(nullptr))::value;
};
```

Now, we can introduce a static assertion into `shell()` that provides a better diagnostic if the `shell()` template from the previous section is instantiated with a type that is not dereferenceable:

```cpp
template<typename T>
void shell() {
  static_assert(HasDereference<T>::value, "T is not dereferenceable");

  typename T::index i;
  middle(i);
}
```

With this change, the compiler produces a significantly more concise diagnostic indicating that the type `T` is not dereferenceable.

Static assertions can drastically improve the user experience when working with template libraries, by making error messages both shorter and more direct.

Note that you can also apply them to class templates and use all type traits discussed in Appendix D.

```cpp
template<typename T>
class C {
  static_assert(HasDereference<T>::value, "T is not dereferenceable");
  static_assert(std::is_default_constructible<T>::value,
                "T is not default constructible");
};
```

### 28.3 Archetypes

When writing a template, it is challenging to ensure that the template definition will compile for any template arguments that meet the specified constraints for that template. Consider a simple `find()` algorithm that looks for a value within an array, along with its documented constraints:

```cpp
// T must be EqualityComparable, meaning
// objects of type T can be compared with == and
// the result converted to bool
template<typename T>
int find(T const* array, int n, T const& value);
```

We could imagine the following straightforward implementation of this function template:

```cpp
template<typename T>
int find(T const* array, int n, T const& value) {
  int i = 0;
  while (i < n && array[i] != value)
    ++i;
  return i;
}
```

There are two problems with this template definition, both of which will manifest as compilation errors when given certain template arguments that technically meet the requirements of the template yet behave slightly differently than the template author expected. We will use the notion of archetypes to test our implementation's use of its template parameters against the requirements specified by the `find()` template.

Archetypes are user-defined classes that can be used as template arguments to test a template definition's adherence to the constraints it imposes on its corresponding template parameter. An archetype is specifically crafted to satisfy the requirements of the template in the most minimal way possible, without providing any extraneous operations. If instantiation of a template definition with the archetype is to compile, then we have the template definition meet the requirements of the template.
