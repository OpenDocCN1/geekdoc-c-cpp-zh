The header identifiers are then bound to the elements of that. You can think of (a, b, c) as introducing names for the pieces of (x, y, z) we have seen; detailed in the binding rules.

Sometimes, a structured binding may also have an & type-specifier (either & or && ; no cv-qualifiers) or a [ ] combination (and so on; no const or volatile qualifiers) in the declarator. It is followed by a list containing at least one identifier consisting of the 'operator' in that list. It may then be followed by an initializer.

Three different kinds of entities can introduce a structured binding:

+   1. The first case is the simple case, where all the non-static data members of the entity to be decomposed are also public and direct members of the entity to be decomposed, all the non-static data members have to be public (or all be directly in the class itself or in the same unambiguous public base class; no anonymous unions may be involved). In that case, the number of identifiers must equal the number of members, and using each one of them in a structured binding corresponds to introducing names for the corresponding member of the object described by e (with all the access properties, e.g., the decomposing member is not a bit-field, it is possible to take its address).

+   2. The second case corresponds to arrays. Here is an example:

![](bbox=[0.1, 0.28, 0.45, 0.288])

```
```
int a[2];
double d[2];
int b[2] = { 1, 2 };
auto [ x, y ] = b; // x = 1, y = 2
auto [ u, v ] = d; // u = 0.0, v = 0.1
```
```

Unsurprisingly, the bracketed initializers are just shorthand for the corresponding elements of the unnamed array variable. The number of array elements must equal the number of bracketed initializers.

Here is another example:

![](bbox=[0.1, 0.41, 0.45, 0.418])

```
```
struct S { int x, y; };
S s = { 1, 2 };
auto [ x, y ] = s; // x = 1, y = 2
```
```

List is special: Unusually, the entity a declared earlier would be default-initialized from the following code:

```
```
auto s = S{};
```
```

However, that would declare the default pointer to the array, which is not what happens when performing the intended binding of an array. Instead, it is declared as a variable of array type corresponding to the elements of the type of the expression e, which is declared earlier. In other words, the corresponding entity is declared as follows:

```
```
int a[2];
```
```

Finally, and to be complete, the names for the expressions [ x ] and [ y ], respectively. Also, note that the identifiers must be unique.

List 2, does not introduce any mapping and follows the usual rules for auto. So the hypothetical is declared as follows:

```
```
auto [ x ] = s;
```
```

which yields a reference to an array, and x and y again become aliases for the expressions [ x ] and [ y ], respectively (which are lvalue references referring to the elements of the array produced by the call to s).

+   3. Finally, std::tuple-like classes (std::tuple-like classes have their data elements decomposed through a template-based protocol using get<>()). The main use of this type of decomposition is when the object to be decomposed is a std::pair or std::tuple. In this case, the number of identifiers must equal the number of tuple elements. The actual mapping is described in terms of the get<int>() function (the first int is the index, the second int is the type). For example, the following code:

![](bbox=[0.1, 0.79, 0.45, 0.798])

```
```
std::tuple<int, int, int> t { 1, 2, 3 };
auto [ a, b, c ] = t; // a = 1, b = 2, c = 3
```
```

if the number of names is less than the number of elements, the remaining elements are not decomposed. For example:

![](bbox=[0.1, 0.87, 0.45, 0.878])

```
```
std::tuple<int, int, int> t { 1, 2, 3 };
auto [ a, b ] = t; // a = 1, b = 2
```
```

otherwise, if the number of names is greater than the number of elements, the program is ill-formed.

auto [ a, b, c, d ] = t; // error: too many names
