## Appendix E

## Concepts

For many years now, C++ language designers have explored how to constrain the parameters of templates. For example, in our prototypical `max()` template, we'd like to express that it shouldn't be called for types that aren't comparable using the less-than operator. Other templates may want to require that they be instantiated with types that are valid “iterator” types (for some formal definition of them) or valid “arithmetic” type (which could be a broader notion than the set of built-in arithmetic types).

A concept is a named set of constraints on one or more template parameters. While C++14 was being developed, a very rich concept system was designed for it, but integrating the feature into the language specification ended up requiring too many committee resources, and that version of concepts was eventually dropped from C++11. Some time later, a different design of the feature was proposed, and it appears that it will eventually make it into the language in some form. In fact, just before this book went to press, the standardization committee voted to integrate the new design into the draft for C++20. In this appendix, we describe the main elements of that newer design.

We already motivated and showed some application of concepts in the main chapter of this book:

- Section 6.5 on page 133 illustrates how to use requirements and concepts to enable a constructor only if the template parameter is convertible to a string (to avoid accidentally using a constructor as a copy constructor).
- Section 8.4.8 on page 275 shows how to use concepts to specify and require constraints on types used to represent geometry objects.

### E.1 USING CONCEPTS

Let's examine how to use concepts in client code (i.e., the code that defines templates without necessarily defining the concepts that apply to the template parameters).

### Dealing with Requirements

Here is our habitual two-parameter `max()` template equipped with a constraint:

Click here to view code image

```cpp
template<typename T>
requires requires(T x, T y) {
  return x < y;
}
```

The only addition is the `requires` clause

Click here to view code image

```cpp
requires LessThanComparable<T>
```

which assumes that we have previously declared—not likely through a header inclusion—the concept `LessThanComparable`.

Such a concept is a Boolean predicate (i.e., an expression producing a value of type `bool`) that evaluates to a constant-expression. This is important because the constraints are evaluated at compile time and therefore produce no overhead in terms of generated code. This constrained template will produce code that is just as fast as the unconstrained version we have discussed elsewhere.

When we attempt to use this template, it will not be instantiated until the requires clause has been evaluated and found to produce a true value. If it produces a false value, an error might be emitted explaining which part of the requirement failed (or, a matching overloaded template that fulfills the requirements might be selected).

Requires clauses do not have to be expressed in terms of concepts (though doing so is good practice and tends to produce better diagnostics). Any Boolean constant-expression can be used. For example, as discussed in Section 6.5, the following template could use a constrained copy constructor:

Click here to view code image

```cpp
public:
    template<typename STR>
    requires std::is_convertible_v<STR, std::string>
    explicit Person(STR&& s)
        : m_name(std::forward<STR>(s))
    {
        std::cout << "EMPL-COPY? for " << m_name << "\n";
    }
```

Here, not using a named concept (see Section 6.2 on page 72) can be appropriate, because the ad hoc Boolean expression (using a type trait in this case) `std::is_convertible_v<STR, std::string>` is used to fix the problem that a template constructor might be used instead of a copy constructor. Details of how to organize concepts and constraints are still an active field of exploration by the C++ community, and will likely evolve over time, but there seems to be general agreement that concepts should reflect what code means and not whether it compiles.

### Dealing with Multiple Requirements

In the example above, there is only one requirement, but it's not uncommon to have multiple requirements. For example, one might imagine a Sequence concept that requires a sequence of element values of some kind, and a template that finds a matching value in the sequence. This might be defined as follows:

Click here to view code image

```cpp
template<typename Seq>
    requires Sequence<Seq> &&
             EqualityComparable<std::ranges::range_value_t<Seq>>
typename Seq::iterator find(Seq const& seq,
                            const value_type& val)
{
    return std::find(seq.begin(), seq.end(), val);
}
```

Here, any call to this template will first check each requirement in turn and only if all requirements produce true values can the template be selected for the call and be instantiated (provided, of course, overload resolution does not discard the template for other reasons, such as another template being a better match).

It is also possible to express “alternative” requirements using `||`. This is rarely needed and should not be done too casually because excessive use of the `||` operator in requirements does make portability somewhat less certain (especially when compilation is not guaranteed). However, it can be quite convenient in some situations. For example:

Click here to view code image

```cpp
template<typename T>
    requires Integral<T> ||
             FloatingPoint<T>
T power(T b, T p)
{
    // ...
}
```

A single requirement can also involve multiple parameters, and a single concept can express a predicate over multiple template parameters. For example:

Click here to view code image

```cpp
template<typename T>
requires Concept<T, U>
// ...
```
