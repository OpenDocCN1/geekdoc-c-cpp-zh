### 5.10.2 Expressing the Type of an Expression with decltype

While `auto` and `decltype` work in a way that is often the same, the type that is deduced for `auto` is not always the same as the type that is deduced for `decltype`. The type that is deduced for `auto` may differ from the type that is deduced for `decltype` due to a different treatment of the value category of an expression. For example, `decltype` produces the type of the expression; that is, the type of the expression including the value category of the expression. The type that is deduced for `auto` is a different type, because `auto` deduces the type of the expression without the value category. The type that is deduced for `decltype` is a different type, because `decltype` deduces the type of the expression including the value category.

```cpp
auto x = 2;
auto y = x + 1;
decltype(x) y2 = x + 1;
```

Depending on the initializer for `x`, `y2` may or may not have the same type as `x`. If derived on `decltype`, `y2` has the same type as `x`. If derived on `auto`, `y2` has the same type as `x`. The type of `decltype((x))` is `int&`, while the type of `decltype(x)` is `int`.

- If `e` is an lvalue of type `T`, `decltype(e)` produces `T&`.
- If `e` is an xvalue of type `T`, `decltype(e)` produces `T&&`.
- If `e` is a prvalue of type `T`, `decltype(e)` produces `T`.

See Appendix A for a detailed discussion about value categories. The difference can be demonstrated by the following example:

```cpp
void f(int& i, int&& j)
{
    // check the type of i:
    static_assert(std::is_same<decltype(i), int&>::value, "i"); // i
    static_assert(std::is_same<decltype(i), int&&>::value, "i"); // i

    // check the type of j:
    static_assert(std::is_same<decltype(j), int&&>::value, "j"); // j
    static_assert(std::is_same<decltype(j), int&>::value, "j"); // j
}
```

In the first two expressions, `decltype` is applied to the variable `i`.

```cpp
decltype(i) // deduced type of entity designated by i
```

which means that `decltype` produces the declared type of `i`, `int&`. In the last two expressions, the operand of the `decltype` expression is not just a name because in every case the expression is `(i)`, which is a parenthesized name. In that case, the type refers to the value category of `i`:

```cpp
decltype((i)) // deduce the value category of (i)
```

This expression refers to a variable `(i)` and thus is an lvalue, and, by the rules above, this means that `decltype((i))` is `int&`, and, as a consequence, `int&` is preferred to `int` when initializing the reference `i` of type `int&`. This is one of the few places in C++ where parenthesizing an expression changes the meaning of the program rather than affecting the associativity of operators.

The fact that `decltype` composes the type of an arbitrary expression means that `decltype` deduces the type of the expression, but it also propagates the value category of the expression to the caller of the function. For example, consider a simple forwarding function `g()` that returns the result of calling `f()`.

```cpp
decltype(f()) g()
{
    return f();
}
```

The return type of `g()` depends on the return type of `f()`. If `f()` were to return an lvalue, the return type of `g()` would be an lvalue reference as well. This is because the expression `f()` is an lvalue, and therefore the `decltype` of the expression preserves that value category. Similarly, if the return type of `f()` were an rvalue reference, the return type of `g()` would be an rvalue reference. This can be especially useful when forwarding the result of a function.

`decltype` can also be useful when the value-producing `auto` deduction is not sufficient. For example, assume we have a variable `pos` of some unknown iterator type, and we want to use a variable `element` that refers to the element stored by `pos`. We could use:

```cpp
auto x = *pos;
```

However, this will always make `x` a copy of the element. If we instead try:

```cpp
auto& element = *pos;
```

then we will always receive a reference to the element, but the program will fail if the element's `operator*` returns a value. To address this problem, we can use `decltype(auto)` so that the value- or reference-ness of the iterator's `operator*` is preserved:

```cpp
decltype(auto) element = *pos;
```

This will use a reference when the iterator supports it and copy the value when the iterator does not. The `decltype` approach requires the initializer expression to be written twice: once in the actual initializer and once in the `decltype` expression. C++14 introduces the `decltype(auto)` construct to address that issue.

### 5.10.3 decltype(auto)

C++14 adds a feature that is a combination of `auto` and `decltype`: `decltype(auto)`. Unlike the `auto` type specifier, it is a placeholder type, and the type of a variable, return type, or template argument is determined from the type of the expression. However, unlike `auto`, which uses the rules for template argument deduction to determine the type of interest, the actual type is determined by applying the `decltype` construct directly to the expression. An example illustrates this:

```cpp
int i = 42;              // i has type int
int const& ref = i;      // ref has type int const& and is a
                         // reference to i
auto x = ref;            // x has type int and is a new
                         // independent copy
decltype(auto) y = ref;  // y has type int const& and
                         // also refers to i
```

The type of `y` is obtained by applying `decltype` to the initializer expression here, which is `int const&`. In contrast, the rules for `auto` type deduction produce `int`.

Another example shows the difference when indexing a `std::vector` (which produces an lvalue):

```cpp
std::vector<int> v = { 4, 12 };
auto x = v[0];             // x denotes a new object of
                           // type int
decltype(auto) y = v[0];   // y is a reference (type int&)
```

This neatly addresses the redundancy in our previous example:

```cpp
decltype(auto) element = *pos;
```

```cpp
return contains(buf);
}
```

`if constexpr (IsInt)` produces an `int`; we want to pass that `int` by value (say, no more bytes to take an address of it). That exposes an important property: the return type of a function with deduced return type can depend on the value of its arguments. For example, `decltype(auto)` (see Section 8.1.4 on page 183) produces an `int` for this function if we call it with `int` (or `short`):

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_213_0.png)

```cpp
decltype(auto) g = [](auto& maybeIsInt) // IsInt
{
    int i = 1024;
    return maybeIsInt; // MAYBE int
};
```

Note that parentheses in the initializer may be significant (they are significant for the `decltype` semantics as discussed in Section 8.1.4 on page 183).

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_213_1.png)

```cpp
int i1;
decltype(auto) a = g(i1); // object of type int
decltype(auto) b = g(42); // reference of type int&&
```

This essentially means that parentheses can have an impact on the validity of return statements.

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_213_2.png)

```cpp

decltype(auto) f() {
    int i = 0;
    return (i); // RUNTIME ERROR: reference to temporary

```

Since `i` and `(i)` differ in type, they can be used for notable template metaprogramming techniques (see Section 8.1.4 on page 183). The following example illustrates that:

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_213_3.png)

```cpp
template<typename T> class S {
private:
    T value;
public:
    constexpr S(T const& v) : value{ v } { }
    constexpr T const& get() const {
        return value;
    }
};
S<int> s = 42;
S<decltype(s)>* p = &s; // does not work
S<decltype((s))>* q = &s; // works
```

In line 2, the lack of parentheses around `s` causes the deduced type to be `S<int>`, not a reference. Because `s` is a non-`const` expression of type `S<int>`, this expression is an lvalue, so `(s)` is an lvalue, so `decltype((s))` is `S<int>&`. This means `p` has the type `S<S<int>>`, which means we cannot use it in the same way we handle the typical use of `decltype`. Thus, with this declaration the class template depends on a reference to `S`, and any change of value might impact the behavior of `(class S)`. (See Section 8.1.4 on page 183 for details.) But `(s)` is an lvalue, so `decltype((s))` is a reference type, `(s)` is an lvalue, and the resulting type is `S<int>&`. In other words, `decltype((s))` and `decltype(s)` are of the same type here. Note that the nature of the two cases is somewhat different; `decltype((s))` is a reference type, so `q` can be a reference to an `S` object.

Finally, a comment about using `decltype` with non-type template parameters:

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_213_4.png)

```cpp
template<int N> struct S { };
template<int N> void f(int(&)[N]) { }
int a[] = { 1, 2, 3, 4, 5 };
int b[10];
f(a); // OK
```

In this example, the type of the parameter `f` of function template `f` is `int(&)[N]`. This is deduced from the type of the template parameter `N`. If `a` is passed to `f`, `N` must be `5`, because `a` is an `int[5]` declared with `[]` and `int` elements. Note that the type of the parameter is deduced from the argument type. This is a reference to an array. However, note that for `b`, `N` is `10`.

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_213_5.png)

```cpp
template<int N> struct S { };
int a[] = { 1, 2, 3, 4, 5 };
int b[10];
S<decltype(a)> s1; // OK
S<decltype(b)> s2; // ERROR: decltype(a) is a reference type
```

In this case, `decltype(a)` is a non-deduced context. There is no unique way to deduce `N` from `a`; `a` is an array of `int` and is of type `int[5]`, and `b` is of type `int[10]`. Therefore, the non-type template parameter `N` must be explicitly specified to be able to call this function.
