
However, if a function has a more specific parameter as follows

```cpp
template<typename T>
void deduce(const initializer_list<T>&);

deduce({2, 3, 4}); // OK, T deduced as int
deduce(2); // Error
```

Here deduction succeeds, copy-initializing `{2, 3, 4}` to the `initializer_list` variable; initializer-list deduction is therefore defined in terms of the more specific parameter.

```cpp
auto primes = { 2, 3, 5, 7 }; // primes is initializer_list<int>
deduce(primes); // deduced as int
```

Before C++17, the corresponding direct-initialization of an `auto` variable (e.g., when the `=` token was not used) also worked, but this was changed in C++17 to better match the behavior expected by most programmers:

```cpp
auto i = { 0, 6, 15 }; // OK: i has type std::initializer_list<int>
auto j{ 0, 6, 15 };    // ERROR (since C++17): too many elements
auto k{ 0 };           // OK: k has type int
```

Prior to C++17, both initializations were valid, initializing both `i` and `j` as `std::initializer_list<int>`.

Interestingly, returning a braced initializer list for a function with a deduced placeholder type is invalid:

```cpp
auto list() {
    return { 1, 2, 3 }; // ERROR
}
```

This is because an initializer list in a function scope is an object that points into an underlying array object (the element values passed to the list) that exists when the function returns. Allowing the construct would thus encourage what is in effect a dangling reference.

Another special situation occurs when multiple variable declarations share the same `auto`, as in the following:

```cpp
auto first = container.begin(), last = container.end();
```

In such cases, deduction is performed independently for each declaration. In other words, there is a separate template parameter `T` for `first` and another template parameter `T2` for `last`. Only if both deductions succeed, and the deductions for `T` and `T2` are the same type, are the declarations well-formed. This can produce some interesting errors:

```cpp
char c;
auto *p = &c, d = 0; // OK
auto e = &c, f = 0; // ERROR: deduction mismatch char vs int
```

Here, two pairs of variables are declared with a shared `auto` specifier. The deduction of `p` and `d` deduces the same type `char`, so this is valid. For `e` and `f`, however, deduction of `e` yields `char*` while deduction for `f` yields `int`, so the combination is an error.

A somewhat parallel special situation can occur with placeholder for deduced return types. Consider the following example:

```cpp
auto f(bool b) {
    if (b) {
        return 42.0; // deduces return type double
    } else {
        return 0; // ERROR: deduction conflict
    }
}
```

In this case, each return statement is deduced independently, but if different types are deduced, the program is invalid. If the returned expression calls the function recursively, deduction cannot occur and the program is invalid unless a prior deduction has determined the return type. That means that the following code is invalid:

```cpp
auto f(int n) {
    if (n > 1) {
        return n * f(n-1); // ERROR: type of f(n-1) unknown
    } else {
        return 1;
    }
}
```

But the following otherwise equivalent code is fine:

```cpp
auto f(int n)
{
    if (n <= 1) {
        return 1;             // return type is deduced to be
                               // int
    }
    else {
        return n*f(n-1);       // OK: type of f(n-1) is int and
                               // so is type of n*f(n-1)
    }
}
```

Deduced return types have another special case with no counterpart in declared variable types or deduced non-type parameter types:

```cpp
auto f1() { return; }       // OK: return type is void
auto f2() { return {}; }     // OK: return type is void
```

Both `f1()` and `f2()` are valid and have a `void` return type. However, if the return type pattern cannot match `void`, such cases are invalid:

```cpp
auto* f3() { return; }      // ERROR: auto* cannot deduce as void
```

As you would expect, any use of a function template with a deduced return type requires the immediate instantiation of that template to determine the return type. That, however, has a surprising consequence when it comes to SFINAE (described in Section 8.1.8 on page 129 and Section 15.7 on page 824). Consider the following example:

```cpp
template<typename T, typename U>
auto add(T t, U u) -> decltype(t+u)
{
    return t + u;
}

void add(...);

struct X
{
};

using AddResultA = decltype(add(X{}, X{})); // OK: SFINAE removes this add()
```

However, if we use `decltype(auto)` rather than `decltype(t+u)` for `add()`, an error occurs during overload resolution:

```cpp
template<typename T, typename U>
auto add(T t, U u) -> decltype(auto)
{
    return t + u;
}

void add(...);

struct X
{
};

using AddResultB = decltype(add(X{}, X{})); // ERROR: ...
```

The function body of the `add()` template must be fully instantiated to determine its return type. That instantiation is not in the immediate context (see Section 15.7.1 on page 828) of the call to `add()` and therefore does not fall under the SFINAE filter but results in an outright error. It is therefore important to remember that deduced return types (even if you use `decltype(auto)`) are not subject to SFINAE filtering during overload resolution.

## 5.10.5 Structured Bindings

C++17 added a few features known as structured bindings. It is most easily illustrated with a small example:

```cpp
struct MaybeInt { bool valid; int value; };
MaybeInt get();
auto const [b, v] = get(); // This is...
```

The call to `get()` produces a value (in this case a simple class aggregate of type `MaybeInt`) that can be decomposed into “elements” (in this case, the data members of `MaybeInt`). The value of that call is produced as if the bracketed list of identifiers were replaced with a corresponding declaration.

The declared identifiers are then bound to the elements of that object. You can think of `auto [b, v]` as introducing names for the pieces of the value produced by `get()`; the details are described by the binding rules.

A structured binding declaration may also use a reference qualifier (`&` or `&&`) and may include `const`/`volatile` on the `auto`. It is followed by a bracketed list of at least one identifier, and then by an initializer.

Three different kinds of entities can introduce a structured binding:

- 1. The first case is the simple case, where all the non-static data members of the entity to be decomposed are public and direct members of the class itself or of the same unambiguous public base class (no anonymous unions may be involved). In that case, the number of identifiers must equal the number of members, and each identifier names the corresponding member of the object described by `e` (with all the access properties; e.g., if a member is not a bit-field, it is possible to take its address).

- 2. The second case corresponds to arrays. Here is an example:

```cpp
int a[2] = { 1, 2 };
double d[2] = { 0.0, 0.1 };
auto [ x, y ] = a; // x = 1, y = 2
auto [ u, v ] = d; // u = 0.0, v = 0.1
```

Unsurprisingly, the bracketed identifiers are just shorthand for the corresponding elements of the unnamed array variable. The number of array elements must equal the number of bracketed identifiers.

Here is another example:

```cpp
struct S { int x, y; };
S s = { 1, 2 };
auto [ x, y ] = s; // x = 1, y = 2
```

The array case is special: normally, an `auto` declaration would decay the array to a pointer. That decay does not happen when performing a structured binding of an array. Instead, the hidden entity is declared as a variable of array type corresponding to the type of the expression `e`. In other words, the corresponding entity is declared as follows:

```cpp
int a[2];
```

Finally, `x` and `y` are the names for the expressions `a[0]` and `a[1]`, respectively. Also, note that the identifiers must be unique. This case does not introduce a tuple-like `get` mapping and follows the usual rules for `auto` except that the array does not decay.

- 3. Finally, `std::tuple`-like classes have their data elements decomposed through a template-based protocol using `get<>()`. The main use of this type of decomposition is when the object to be decomposed is a `std::pair` or `std::tuple`. In this case, the number of identifiers must equal the number of tuple elements. The actual mapping is described in terms of the `get<>()` function (the first template argument is the index, and the result type is the corresponding tuple element type). For example, the following code:

```cpp
std::tuple<int, int, int> t { 1, 2, 3 };
auto [ a, b, c ] = t; // a = 1, b = 2, c = 3
```

If the number of identifiers is less than the number of elements, the program is ill-formed:

```cpp
std::tuple<int, int, int> t { 1, 2, 3 };
auto [ a, b ] = t; // ERROR: too few names
```

Similarly, if the number of identifiers is greater than the number of elements, the program is ill-formed:

```cpp
std::tuple<int, int, int> t { 1, 2, 3 };
auto [ a, b, c, d ] = t; // ERROR: too many names
```

Of course, as noted above, a temporary is created for the object, and the names are bound to the temporary’s elements. The identifiers declared in the structured binding are also aliases for the elements. The identifiers in the structured binding are not references, but if you use them in an expression, they are lvalues. For example, the following code:
