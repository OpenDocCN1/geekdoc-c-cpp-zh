
In this version of `PlusResult`, we add a template parameter with a default argument that determines if the first two parameters support addition as determined by our `HasPlusT` trait above. We then partially specialize `PlusResult` for false values of that extra parameter, and our partial specialization definition has no members at all, avoiding the problem we described. For cases where addition is supported, the default argument evaluates to true and the primary template is selected, with our existing definition of the `Type` member. Thus, we fulfill the contract that `PlusResult` provide the result type only if in fact the `+` operation is well-formed. (Note that the added template parameter should never have an explicit template argument.)

Consider again the addition of `Array<T>` and `Array<T>`: With our latest implementation of the `PlusResult` template, the instantiation of `PlusResult<Array<T>, Array<T>>` has a `Type` member whose `Type` is `Array<T>`, but we are not able to add `Array<T>` objects. Therefore, the result type of the array `operator+` template is invalid, and SFINAE will eliminate that function template from the overload set. The result of the function template `operator+` will therefore be chosen.

As a general design principle, a trait template should never fail at instantiation time if given reasonable template arguments as inputs. And the general approach is often to perform the corresponding check twice:

- 1. Once to find out whether the operation is valid
- 2. Once to compute its result

We saw that already with `PlusResult<T>`, where we call `HasPlusT<T>` to find out whether the call of `operator+` in `PlusResult<T>` is valid.

Let's apply this principle to `IsConvertible` to introduce a section of traits again. In practice, we form a container type having a member type `value_type`. Since the corresponding type is `true`, while `false` is chosen if the container type has no such a `value_type` member:

```cpp
template<typename C, bool = HasValueTypeT<C>::value>
struct IsConvertibleT {
  using Type = typename C::value_type;
};

template<typename C>
struct IsConvertibleT<C, false> {
};
```

A third example of making traits SFINAE-friendly is shown in Section 19.7.2 on page 444, where `HasNoexceptMoveConstructorT` first has to check whether a move constructor exists before checking whether it is declared with `noexcept`.

## 19.5 Is Convertible

Details matter. And for that reason, the general approach for SFINAE-based traits might become more complicated in practice. Let's illustrate this by defining a trait that can determine whether a given type is convertible to another given type—for example, if we expect a certain base class to be one of its derived classes. The `IsConvertibleT` trait should determine whether we can convert a passed first type to a passed second type:

```cpp
traits/isconvertible.hpp

#ifndef ISCONVERTIBLE_HPP
#define ISCONVERTIBLE_HPP

#include <utility>      // for declval

template<typename FROM, typename TO>
struct IsConvertibleHelper {
private:
  // test() trying to call the helper using arg
  static void test(TO);

  template<typename T>
  static auto test(T&&) -> decltype(
      std::declval<T>());

  static std::false_type test(...);

public:
  using Type = decltype(test(std::declval<FROM>()));
};

template<typename FROM, typename TO>
using IsConvertible = std::is_same<typename IsConvertibleHelper<FROM, TO>::Type, void>;

template<typename FROM, typename TO>
constexpr bool isConvertible = IsConvertible<FROM, TO>::value;
```

Here, we use the approach with function overloading, as introduced in Section 9.4, on page 46. That is, inside a helper class we declare two overloaded function templates named `test()` with different return types and declare a `Type` member for the class of the resulting trait:

```cpp
template<typename T>
static std::true_type test(void*);

template<typename T>
static std::false_type test(...);

using Type = decltype(test<FROM>(nullptr));

template<typename FROM, typename TO>
struct IsConvertible : IsConvertibleHelper<FROM, TO>::Type
{
};
```

As usual, the first `test()` overload is designed to match only if the requested check succeeds, while the second overload is a fallback. Thus, the goal is to make the first `test()` overload valid if and only if type `FROM` converts to type `TO`. To achieve this, again we give our first declaration of `test` a dummy (unnamed) template argument initialized with a construct that is valid if and only if the conversion is valid. This template parameter cannot be deduced, and we will not provide an explicit template argument for it. Therefore, it will be substituted, and if the substitution fails, that declaration of `test()` will be discarded.

Again, note that the following doesn't work:

```cpp
static void test(TO);
template<typename = decltype(std::declval<FROM>())>
static char test(...);
```

Here, `FROM` and `TO` are completely determined when this member function template is used, and therefore a pair of two function templates is not viable for overload resolution if one of them is not valid, and this declaration of `test()` will be discarded.

For that reason, we introduce `T` as a specific member function template parameter:

```cpp
static void test(TO);
template<typename T, typename = decltype(std::declval<T>())>
static char test(...);
```

and provide the `FROM` type as an explicit template argument in the call to `test()` that appears in the initialization of `value`!

```cpp
static constexpr bool value = decltype(test<FROM>(nullptr))::value;
```

Note how `std::declval`, introduced in Section 19.3.4 on page 15, is used to produce a value without calling any constructor. If that value is convertible to `TO`, the call to `test()` is valid, and this declaration of `test()` matches. Otherwise, a SFINAE failure occurs and only the fallback declaration will match.

As a result, we can use the trait as follows:

```cpp
IsConvertible<int, int>::value;                  // true
IsConvertible<int, std::string>::value;           // false
IsConvertible<char const*, std::string>::value;   // true
IsConvertible<std::string, char const*>::value;   // false
```

### Handling Special Cases

Three cases are not yet handled correctly by `IsConvertible`:

- 1. Conversions to array types should always yield `true`, but in our code, the parameter of type `T` in the declaration of `test()` will just decay to a pointer type and therefore enable a "true" result for some incorrect types.
- 2. Conversions to function types should always yield `false`, but just as with the array case, our implementation just treats them as decayed types.
- 3. Conversion to `(const/volatile-qualified) void` types should yield `true`. Unfortunately, our implementation above doesn't even successfully instantiate the case where `T` is a `void` type because parameters of type `void` are not valid.

Handling all these special cases with partial specializations for arrays, functions, and cv-qualified volatile qualifiers quickly becomes unwieldy. Instead, we can add an additional template parameter to our helper class template as follows:

```cpp
template<typename FROM, typename TO,
         bool = IsVoid<TO>::value
             || IsArray<TO>::value
             || IsFunction<TO>::value>
struct IsConvertibleHelper {
  using Type = std::integral_constant<bool,
                                      IsVoid<TO>::value
                                      && ...>;
};
```

The extra Boolean template parameter ensures that for all these special cases the implementation of the primary helper trait is used. It yields `false_type` if we convert it across our functions (because then `IsVoid<T>::value` is false) or if `T` provides `void` and `T` is not `void`. For these types we produce `false_type`. All other cases produce a false argument for this third parameter and therefore pick up their partial specialization, which corresponds to the implementation we already discussed.

See Section 19.8.2 on page 433 for a discussion of how to implement `IsArray<T>` and Section 19.8.3 on page 454 for a discussion of how to implement `IsFunction<T>`.

The C++ standard library provides a corresponding type trait `std::is_convertible`, which is described in Section D.3 on page 737.

## 19.6 Detecting Members

Another fancy use of SFINAE-based traits involves creating a trait (or, rather, a set of traits) that can determine whether a given type `T` has a member of a given name (a type or a non-type member).

### 19.6.1 Detecting Member Types

Let's first define a trait that can determine whether a given type `T` has a member type `size_type`:

```cpp
#include <type_traits> // defines true_type and false_type

// helper to ignore any number of template parameters
template<typename...> using Void = void;

// primary template:
template<typename T, typename = void>
struct HasSizeTypeT : std::false_type
{
};

// partial specialization (may be SFINAE'd away):
template<typename T>
struct HasSizeTypeT<T, Void<typename T::size_type>>
{
};
```

Here, we use the approach to SFINAE out partial specializations introduced in Section 19.4.2 on page 420.

As usual for predicate traits, we define the general case to be derived from `std::false_type`, because by default a type doesn't have the member type.

In this case, we only need one construct:

```cpp
template<typename...> using Void = void;
```

This construct is valid if and only if type `T` has a member type `size_type`, which is exactly what we are trying to determine. If, for a specific `T`, the construct is invalid (i.e., type `T` has no member type `size_type`), SFINAE causes the partial specialization to be discarded, and we fall back to the primary template. Otherwise, the partial specialization is valid and preferred.
