
Concepts are much like the concept variable templates of type `bool`, but the type is not explicitly specified:

Click here to view code image

```cpp
template<typename T>
concept LessThanComparable =
  requires (T x, T y) {
    { x < y } -> bool;
  };
```

Here’s “...” could perhaps be replaced by an expression that uses various traits to establish whether type `T` is indeed comparable using the `<` operator, but the concepts proposal provides a tool to simplify this task: the requires expression (which is distinct from the requires clause described above). Here is how the concept’s complete definition may look like:

Click here to view code image

```cpp
template<typename T>
concept LessThanComparable = requires(T x, T y) {
  { x < y } -> bool;
};
```

Note how the requires expression can include an optional parameter list: these parameters are never replaced by arguments but can instead be thought of as a set of “dummy variables” usable to express requirements in the body of the requires expression. In this case, there is just one such requirement expressed by the phrase

Click here to view code image

```cpp
{ x < y } -> bool;
```

This syntax means that (a) the expression `x < y` must be valid in a SFINAE manner and (b) the result of that expression must be convertible to `bool`. In a phrase of this form, the keyword `noexcept` can be inserted before the `->` token to express that the expression in the braces should be known not to throw an exception (i.e., `noexcept` applied to that expression should return `true`). Implicit conversion of the phrase (i.e., `-> type`) can be left out altogether if no such constraint is needed, and if only the validity of the expression must be checked, the braces can be dropped, so that this phrase reduces to just an expression. For example,

Click here to view code image

```cpp
template <typename T>
concept Swappable = requires(T x, T y) {
  swap(x, y);
};
```

Requires expressions can also express the need for associated types. Consider the Sequence concept type-hypothesized earlier. In addition to requiring the validity of expressions like `seq.begin()`, it also requires corresponding sequence iterator types. That can be expressed as follows:

Click here to view code image

```cpp
template<typename Seq>
concept Sequence = requires (Seq seq) {
  typename Seq::iterator;
  { seq.begin() } -> Seq::iterator;
  seq.begin() == seq.end();
};
```

So the phrase `typename type;` expresses the requirement that `type` exists (this is called a type requirement). In this example, the type that has to exist is a member of the concept template parameter, but that need not always be the case. We could, for example, require that there exist a type `Iterator<Seq>::type`; indeed, and that will make whatever this type requirement phrase

Click here to view code image

```cpp
typename IteratorFor<Seq>::type;
```

The Sequence concept definition above shows how phrases can be combined by just listing them one after another. There is a third class of requirement-phrase, which consists in just invoking another concept. For example, let’s assume that we have a concept for the notion of an iterator. We want our Sequence concept to require not only that `Seq::iterator` be a type, but also that that type satisfies the constraints of the `Iterator` concept. That is expressed as follows:

Click here to view code image

```cpp
template<typename Seq>
concept Sequence = requires (Seq seq) {
  typename Seq::iterator;
  requires Iterator<Seq::iterator>;
  seq.begin() == seq.end();
};
```

That is, we can list all requires clauses for requirements (and this sort of phrase is called a nested requirement).

## 5. OVERLOADING ON CONSTRAINT

Let’s assume for a moment that we have defined concepts `IntegralLike<T>` and `StringLike<T>`, and we decide to write two templates to print out values of types of either concept. We could do that as follows:

Click here to view code image

```cpp
template<typename T> void print(T val);  // #1
template<StringLike T> void print(T val);  // #2
```

If it weren’t for such differing constraints, these two declarations would become the same template. However, the constraints are part of the template signature and allow the templates to be distinguished. This lets the more constrained template be selected. For example, assuming `int` satisfies `Integral` and `EuclideanRing` but not `Field`,

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_501_0.png)

```cpp
int main()
{
    print(1);       // select template #1
    print('c');     // select template #2
}
```

We could imagine a string-like type that supports integer-like comparisons. For example, `String` is `Integral` and `EuclideanRing` but not a `Field` — though it could provide the same value as `Int`. Such a type might satisfy both `IntegralLike` and `StringLike` and, therefore, a call like `print("42")` would be ambiguous.

### E.3.1 Constraint Subsumption

Our first description of overloaded function templates distinguished two kinds of constraints: those that are satisfied by all types and those satisfied by only a few. For example, `int` does not satisfy `Field` but does satisfy `IntegralLike`, and `StringLike` would ensure that such concepts, but we expect that no one would use `int` in a template parameter for a string. In this case, `int` is not a `StringLike` and, therefore, a call like `print("42")` would be ambiguous.

However, there are, of course, sets of concepts that are not entirely exclusive but where one subsumes the other. The classic example of this is the standard library's iterator category: input iterator, forward iterator, bidirectional iterator, random access iterator, and so on. However, we use a definition for `ForwardIterator`:

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_501_1.png)

```cpp
template<typename T>
concept ForwardIterator =
    requires(T t) {
        ...
    };
```

Thus, the "more refined" concept `BidirectionalIterator` might be defined as follows:

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_501_2.png)

```cpp
template<typename T>
concept BidirectionalIterator =
    ForwardIterator<T> &&
    requires(T t) {
        { ++t } -> ...;
        { --t } -> ...;
        { t-- } -> ...;
    };
```

This would enable us to apply specific operations—on top of the capabilities already provided by `ForwardIterator`.

Consider how the `distance()` algorithm (which we call `distance`?) is overloaded for forward iterators and for bidirectional iterators:

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_501_3.png)

```cpp
template<ForwardIterator T, typename D>
void distance(T first, T last, D& d)
{
    d = 0;
    while (first != last) {
        ++d;
        ++first;
    }
}

template<BidirectionalIterator T, typename D>
void distance(T first, T last, D& d)
{
    if (first == last) return;
    d = 0;
    if (first != last) {
        ++d;
        ++first;
    }
}
```

When calling `distance()` with a plain forward iterator (i.e., one that is not a bidirectional iterator), only the constraint of the first template is satisfied, and overload resolution is straightforward. The first template is selected. However, a bidirectional iterator will also satisfy the constraints of the first template, because the constraints of the first template are a subset of those of the second. This is the essence of the subsumption relationship: a bidirectional iterator is a forward iterator (it can be used as one) but not the reverse. This makes the second template more refined, and the second template is preferred when called with a bidirectional iterator.

### E.3.2 Constraints and Tag Dispatching

Before that, Section 10.2 on page 10? we explained the basis for overloading: We can use tag dispatching (see Section 10.3 on page 10?) to select an overload. This mechanism can be integrated into constraint templates in a fairly elegant way. For example, input iterators and forward iterators are not distinguished through their syntactic interface. So instead, we can reach for tags to determine the iterator category.

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_501_4.png)

```cpp
template<typename T>
concept ForwardIterator =
    InputIterator<T> &&
    requires(T t) {
        ...
    };
```
