
With the keyword `decltype` (introduced in C++11), it is possible to check the value category of any C++ expression. For any expression `x`, `decltype((x))` (note the double parentheses) yields:

- `T&` if `x` is an lvalue
- `T&&` if `x` is an xvalue
- `T` if `x` is a prvalue

The double parentheses in `decltype((x))` are needed to avoid producing the declared type of a named entity in case where the expression `x` does indeed name an entity (in other cases, the parentheses have no effect). For example, if the expression `x` simply names a variable `y`, the output without parentheses becomes `decltype(y)`, which produces the type of variable `y` rather than a type reflecting the value category of the expression `x` referring to that variable.

The same traits for void expressions, you can check its value category as follows:

[Click here to view code image](#)

```cpp
if constexpr (std::is_lvalue_reference_v<decltype((x))>) {
    std::cout << "expression is an lvalue";
}
else if constexpr (std::is_rvalue_reference_v<decltype((x))>) {
    std::cout << "expression is an xvalue";
}
else {
    std::cout << "expression is a prvalue";
}
```

See Section 15.10.2 on page 598 for details.

### B.4 REFERENCE TYPES

Reference types in C++—such as `int&`—interact with value categories in two important ways. The first is that a reference may limit the value category of an expression it is bound to. For example, a non-const lvalue reference of type `int&` can only be initialized with an expression that is an lvalue of type `int`. Similarly, an rvalue reference of type `int&&` can only be initialized with an expression that is an rvalue of type `int`.

The second way in which value categories interact with references is with the return types of functions, where the use of a reference type as the return type affects the value category of the call to that function. In particular:

- A call to a function whose return type is an lvalue reference yields an lvalue.
- A call to a function whose return type is an rvalue reference yields an xvalue.
- A call to a function that returns a nonreference type yields a prvalue.

We illustrate the interaction between reference types and value categories in the following example. Given:

```cpp
int& lvalue();
int&& xvalue();
int prvalue();
```

both the value category and type of a given expression can be determined via `decltype`. As described in Section 15.10.2 on page 598, it uses reference types to describe when the expression is an lvalue or xvalue.

[Click here to view code image](#)

```cpp
std::is_same<decltype(lvalue()), int&>    // yields true because result is lvalue
std::is_same<decltype(xvalue()), int&&>    // yields true because result is xvalue
std::is_same<decltype(prvalue()), int>      // yields true because result is prvalue
```

Thus, the following calls are possible:

[Click here to view code image](#)

```cpp
int& ref1 = lvalue();       // OK: lvalue reference can
                             // bind to an lvalue
int&& ref2 = xvalue();      // OK: rvalue reference can
                             // bind to an xvalue
const int& ref3 = prvalue(); // OK: const reference can
                              // bind to a prvalue

int& ref4 = xvalue();       // ERROR: lvalue reference
                            // can't bind to an xvalue
int&& ref5 = lvalue();      // ERROR: rvalue reference
                            // can't bind to an lvalue
const int& ref6 = lvalue(); // OK: const reference can
                            // bind to an lvalue
```

- 1. User-defined literals can lead to lvalues or rvalues, depending on the return type of the associated literal operator.
- 2. Which unfortunately means that the terms are synonymous.
- 3. In the world of C++11 value categories, the phrase glvalue-to-prvalue conversion would be more accurate, but the traditional term remains more common.

## Appendix C

## Overload Resolution

Overload resolution is the process that selects the function to call for a given call expression. Consider the following simple example:

Click here to view code image:

```cpp
void display_num(int i);    // #1
void display_num(double d); // #2

int main()
{
    display_num(39);   // #1 matches better than #2
    display_num(3.99); // #2 matches better than #1
}
```

In this example, the function name `display_num()` is said to be overloaded. When this name is used in a call, a C++ compiler must therefore distinguish between the various candidate uses of `display_num()`. Unfortunately, mostly, this information is the types of the call arguments. In our example, it makes intuitive sense to call the `int` version when the function is called with an integer argument and the `double` version when a floating-point argument is provided. The formal process that attempts to model this intuitive choice is the overload resolution process.

The general idea behind the rules that guide overload resolution are simple enough, but the details have become quite complex during the C++ standardization process. This complexity was driven mostly by the desire to support various well-used examples that intuitively (to a human) seem to have an “obviously best match,” but when trying to formalize this intuition, various subtleties arose.

In this appendix, we provide a reasonably detailed survey of the overload resolution rules. However, the complexity of this process is such that we do not aim to cover every part of the topic.

### C.1 WHEN DOES OVERLOAD RESOLUTION KICK IN?

Overload resolution is just one part of the complete processing of a function call. In fact, it is not part of every function call. First, calls through function pointers and calls through pointers to member functions are not subject to overload resolution because the function to call is entirely determined (at run time) by the pointers. Second, function-like macros cannot be overloaded and are therefore not subject to overload resolution.

At a very high level, a call to a named function can be processed in the following way:

- The name is looked up to form an initial overload set.
- If necessary, this set is adjusted in various ways (e.g., template argument deduction and substitution occurs, which can cause some function template candidates to be discarded).
- Any candidate that doesn't match the call at all (even after considering implicit conversions and default arguments) is eliminated from the overload set. This results in a set of viable function candidates.
- Overload resolution is performed to find a best candidate. If there is one, it is selected; otherwise, the call is ambiguous.
- The selected candidate is checked. For example, if it is a deleted function (i.e., one defined with `= delete`) or an inaccessible private member function, a diagnostic is issued.

Each of these steps has its own subtleties, but overload resolution is arguably the most complex. Fortunately, a few simple principles clarify the majority of situations. We examine these principles next.

### C.2 SIMPLIFIED OVERLOAD RESOLUTION

Overload resolution ranks the viable candidate functions by comparing how each argument of the call matches the corresponding parameter of the candidates. For one candidate to be considered better than another, the better candidate must not have any of its parameters be a worse match than the other candidate. The following example illustrates this idea:

Click here to view code image:

```cpp
condition<...> ? 21 : // ambiguous?
```

In this example, the call to construct is ambiguous between the first constructor that matches the first argument (the string literal) and the second constructor that matches the second argument (the double). We would again need an explicit cast to force the call to match the constructor that accepts the second argument, but C++ does not attempt to resolve a call to a function or constructor that has multiple possible matches.

Given this principle, we are left with specifying how well a given argument matches the corresponding parameter of a viable candidate. As a first approximation, we can rank the possible matches as follows (from best to worst):

- 1. A perfect match. The parameter has the type of the expression, or it has a type that is a reference to the type of the expression (possibly with added `const` and/or `volatile` qualifiers).
- 2. Match with minor adjustments. This includes, for example, the decay of an array variable to a pointer to its first element, or the addition of `const` to match an argument of type `int**` to a parameter of type `int const* const*`.
- 3. Match with promotion. Promotion is a kind of implicit conversion that converts a small integral type to an `int` (or larger), and the conversion of `float` to `double`, `bool` to `int`, and the conversion of a scoped enum to its underlying type.
- 4. Match with standard conversions only. This includes any sort of standard conversion (such as `int` to `double`) but does not include a conversion to another user-defined type. A conversion to `bool` from a type that has an explicit conversion to `bool` is allowed.
- 5. Match with user-defined conversions. This allows any kind of implicit conversion.
- 6. Match with ellipsis. An ellipsis parameter can match almost any type (but non-POD class types may not be allowed through an ellipsis; a constructor or conversion operator may or may not be used).

The following contrived example illustrates some of these matches:

Click here to view code image:

```cpp
List<int> l1;
List<double> l2;
List<Int> l3;
f(l1); // ok: f(List<int>) perfect match (l2 requires
       // a standard conversion)
f(l2); // ok
f(l3); // ok: f(List<int>) match with promotion
```

Next, consider:

```cpp
class X {
public:
  X(int);
  X(long);
};

f(X(1)); // ok: f(X) perfect match
f(2);    // ok: f(X) match with user-defined
         // conversion
f(1);    // ok: f(X) match with user-defined
         // conversion
```

Note that overload resolution occurs after template argument deduction, and this deduction does not consider all these sorts of conversions. For example:

Click here to view code image:

```cpp
template<typename T>
class MyClass {
public:
  MyClass(T const&); // converting constructor
  // ...
};

template<typename T>
MyClass<T> f(T const&);
```

The implicit conversion provided through the converting constructor is not considered during template argument deduction. The assignment to `x1` below is valid because `f` performs an implicit conversion in its argument:

```cpp
MyClass<int> x1 = f(1); // ok
MyClass<int> x2 = f(1); // ok
```

In the context of template argument deduction, we still also note that an rvalue reference to a parameter can deduce to an rvalue reference. For example:

Click here to view code image:

```cpp
template<typename T> void acceptT(T&);
template<typename T> void acceptR(T&&);
```
