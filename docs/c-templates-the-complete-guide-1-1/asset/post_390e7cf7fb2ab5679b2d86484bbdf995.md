
```cpp
A_Mult<double, A_Scalar<double>, Array<double>>
```

Hence, the type of the expression to the right of the assignment token is

```cpp
Array<double,
    A_Mult<double,
      A_Mult<double, A_Scalar<double>, Array<double>>>>
```

This type is matched to the assignment operator template of the Array template:

```cpp
template<typename T, typename Rep = Array<T>>
class Array
{
public:

    // assignment operator for arrays of different type
    template<typename T2, typename Rep2>
    Array& operator= (const Array<T2, Rep2>& x)
    {
        for (int i=0; i<size; ++i)
            rep_[i] = x[i];

        return *this;
    }
};
```

The assignment operator computes each element of the destination x by applying the subscript operator to the representation of the right side, the type of which is

```cpp
A_Mult<double,
   A_Mult<double, A_Scalar<double>, Array<double>>,
   Array<double>>
```

Carefully noting this subscript operator shows that for a given subscript i, it computes

```cpp
(1.2*x[i]) + (x[i][y][idx])
```

which is exactly what you want.

## 27.2.5 Expression Template Assignments

It is not possible to instantiate write operations for an array with a 3-argument A_Subscript that is built on our example A_Mult and A_Scalar expression templates. (Indeed, it makes no sense to write to an A_Mult expression; it is entirely reasonable to write other expression templates for which assignment-write semantics are possible. For example, indexing with an array of integer values would intuitively correspond to subset selection. In other words, the expression

```cpp
x[i] = 2*y[i]
```

should mean the same as

```cpp
for (int i=0; i < D; i++)
    x[i] = 2*y[i];
```

Enabling this implies that an array built on an expression template becomes an lvalue (i.e., writable). The expression template component for this is not fundamentally different from, say, A_Mult, except that both const and non-const versions of the subscript operators are provided, and they may return lvalue references.

```cpp
template<typename T, typename A1, typename A2>

class A_Subscript
{
public:

    // constructor initializes references to operands
    A_Subscript (A1 const& a, A2 const& b)
        : a1(a), a2(b) { }

    // process subscript in rhs via repeated
    decltype(auto) operator[](std::size_t id) const
    {
        return a1[a2[id]];
    }

    decltype(auto) operator[](std::size_t lhs)
    {
        return a1[a2[lhs]];
    }

    // size is size of inner array
    std::size_t size() const {
        return a2.size();
    }

private:
    A1 const& a1;    // reference to first operand
    A2 const& a2;    // reference to second operand
};
```

Again, decltype(auto) comes in handy to handle subscripting of arrays independently of whether the underlying representation produces values or references.

The extended subscript operator with array semantics that was suggested earlier would require that additional subscript operators be added to the library template. One of these operators could be defined as follows (a corresponding const version would presumably also be needed):

```cpp
template<typename T, typename R>
template<typename T2, typename R2>
Array<T, A_Subscript<T, R> >
Array<T, R>::operator[](Array<T2, R2> const& b) {
    return Array<T, A_Subscript<T, R> >
        (A_Subscript<T, R2>(a1, b));
}
```

## 27.3 PERFORMANCE AND LIMITATIONS OF EXPRESSION TEMPLATES

To justify the complexity of the expression templates described here, we have analyzed the greatly enhanced performance on array-view operations. As you read what happens with the expression templates, you'll find that many small inline functions call each other and that many small expression template objects are allocated on the call stack. The optimizer must perform complete inlining and elimination of the small objects to produce the best performance as well as manually written code. In the first edition of this book, we reported that few compilers could achieve such optimization. Since then, the situation has improved considerably, no doubt due in part to the fact that the technique has proven popular.

The expression templates technique does not resolve all the problematic situations involving numeric operations on arrays. For example, it does not work for matrix-vector multiplications of the form

`x = A*x;`

where x is a column vector of size n and A is an n×n matrix. The problem here is that a temporary must be used because each element of the result is computed from each element of the original. Unfortunately, the expression template technique cannot handle this situation: it must use the newly computed element to compute the second element, which is wrong. The slightly different expression

`x = A*y;`

on the other hand, does not need a temporary if x and y aren't aliases for each other, which implies that a solution would have to know the nature of the operands at run time. This in turn suggests creating a run-time structure that represents the expression tree instead of reducing it to operator overloading. The expression templates from the NewMat library of Robert Davies (see [NewMat]) are well known long before expression templates were developed.

## 27.4 AFTERNOTES

Expression templates were developed independently by Todd Veldhuizen and David Vandevoorde (Todd coined the term) at a time when member templates were not yet part of the C++ programming language (and it seemed at the time that they would never be added to C++). This caused some problems in the implementation, particularly with regard to access. It had to be parameterized for the expression template. One technique to work around this introduced in the expression templates a conversion operator to a C++ class parameterized with the expression template but inheriting from a base class that was parameterized only in the element type. This base class then provided a (virtual) copy_to interface to which the assignment operator could refer.

Here is a sketch of the mechanism (with the template names used in this chapter):

```cpp
template<typename T>
class CopierInterface
{
public:
    virtual void copy_to(Array<T>&) const = 0;
};
```

```cpp
template<typename T, typename X>
class Copier : public CopierInterface<T>
{
public:
    Copier (X const& x) : expr_(x) {}

    virtual void copy_to(Array<T>& dest) const
    {
        // implementation of assignment loop
        ...
    }

private:
    X const& expr_;
};
```

```cpp
template<typename T, typename A1, typename A2>
class A_Mult
{
public:
    A_Mult (Copier<T, A_Mult<T, A1, A2> >);
    ...
};
```

This adds another level of complexity and some additional run-time cost to expression templates, but even so, the resulting performance benefits were impressive at the time.

The C++ standard library contains a class template valarray that was meant to be used for applications that would justify the techniques used here to any template developed in this chapter. A precursor of our array may have been designed with the intention that compilers aiming at the market for scientific computation would recognize the array type and use highly optimized internal code for their expressions. Such compilers would have “understood” the types in some sense. However, this never happened (in part because the market in question is relatively small and in part because the problem grew in complexity as a result) became a time-consuming task.

The valarray proposal came late in the C++ standardization process and practically overwrote all the text regarding the standard. It was rejected as a result, and instead, a few tokens were added to the existing text to allow implementations based on expression templates. However, the exploitation of this allowance remains much more cumbersome than what was discussed here. At the time of this writing, no such implementation is known, and standard arrays are, generally speaking, quite inefficient at performing the operations for which they were designed.

Finally, it is worth observing here that many of the pioneering techniques presented in this chapter, as well as what later became known as the STL, were all originally implemented on the same compiler: version 4.4 of the Borland C++ compiler. This was perhaps the first compiler that made template programming broadly popular in the C++ programming community.
