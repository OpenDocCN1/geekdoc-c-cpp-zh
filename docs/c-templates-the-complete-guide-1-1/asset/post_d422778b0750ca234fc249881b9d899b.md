### 8.4.1 Expression SFINAE with decltype

It's not always easy to find out and formulate the right expression to SFINAE out function templates for certain conditions.

Suppose, for example, that we want to ensure that the function template `len()` is ignored for arguments of a type that has a `size_type` member but not a `size()` member function. Without any form of requirements for a `size()` member function, the function template is selected, and its instantiation then results in an error:

```cpp
template<typename T>
auto len (T const& t)
    -> decltype(t.size())
{
    return t.size();
}

std::cout << len(x);       // ERROR: len() selected, but x has no size()
```

There is a common pattern in order to deal with such a situation:

- Specify the return type using the trailing return type syntax (use `auto` at the front and `->` before the return type at the end).
- Define the return type using `decltype` and the comma operator.
- Formalize all expressions that must be valid at the beginning of the comma operator.
- Define an object of the real return type at the end of the comma operator.

For example:

Click here to view code image

```cpp
template<typename T>
auto len (T const& t) -> decltype(t.size())
{
    return t.size();
}
```

Here the return type is given by

Click here to view code image

```cpp
decltype((void)(t.size()), typename T::size_type())
```

The operand of the `decltype` operator is a comma-separated list of expressions, so that the last expression yields a value of the desired return type (which `decltype` uses to convert into the return type). Before the last comma, we have the expressions that must be valid, which in this case is just `t.size()`. The comma expression is void to avoid the possibility of a user-defined comma operator overloaded for the type of the expression.

Note that the argument of `decltype` is an unevaluated operand, which means that you, for example, can create dummy objects without calling constructors, which is discussed in Section 11.2.3 on page 116.

## 8.5 COMPILE-TIME IF

Partial specialization, SFINAE, and `std::enable_if` allow us to enable or disable templates as a whole. C++17 additionally introduces a compile-time `if` statement that allows us to enable or disable specific statements based on compile-time conditions. With the syntax `if constexpr(...)`, the compiler uses a compile-time expression to decide whether to apply the `then` part or the `else` part (if any).

As a first example, consider the variadic function template `print()` introduced in Section 4.3.1 on page 55. It prints its arguments (if arbitrary types) using recursion. Instead of providing a separate function to end the recursion, the recursive/iterative function uses a double newline to continue the recursion:

Click here to view code image

```cpp
if constexpr (sizeof...(args) > 0) {
    print(args...);       // code only available if sizeof...(args) > 0
}
```

Here, if `print()` is called for one argument only, `args` becomes an empty parameter pack so that `sizeof...(args)` becomes 0. As a result, the recursive call of `print()` becomes a discarded statement, for which the code is not instantiated. Thus, a corresponding function is not required to exist and the recursion ends.

The fact that the code is not instantiated means that only the first translation phase (the definition time) is performed, which checks for correct syntax and means that dependent names are not instantiated (see Section 1.1.3 on page 6). For example:

Click here to view code image

```cpp
template<typename T>
void foo(T t)
{
    if constexpr (std::is_integral_v<T>) {
        if (t > 0)
            foo(t-1);    // OK
    }
    else {
        undeclared();    // error if not declared and not
                         // instantiated
        static_assert(std::is_integral_v<T>, "No integers");
    }
}
```

Note that `if constexpr` can be used in any function, not only in templates. You only need a compile-time expression that yields a Boolean value. For example:

Click here to view code image

```cpp
int main()
{
    if constexpr (std::numeric_limits<char>::is_signed) {
        foo(42);
    }
    else {
        undeclared();    // error if undeclared
        static_assert(std::is_signed<char>::value,
                      "char is unsigned");
    }
}
```

With this feature, we can, for example, use our `isPrime()` compile-time function, introduced in Section 8.2 on page 125, to perform additional code if a given size is not a prime number.

Click here to view code image

```cpp
template<typename T, size_t N>
void foo (std::array<T, N> const& coll)
{
    if constexpr (!isPrime(N)) {
        // special additional handling if the passed array
        // has no prime number as size
    }
}
```

See Section 9.4.6 on page 253 for further details.

## 8.6 SUMMARY

- Templates provide the ability to compute at compile time (using recursion to iterate and partial specialization or operator `?` for selections).
- With `constexpr` functions, we can replace most compile-time computations with “ordinary functions” that are callable in compile-time contexts.
- With partial specialization, we can choose between different implementations of class templates based on certain compile-time constraints.
- Templates are used only if needed and substitutions in function-template declarations do not result in invalid code. This principle is called SFINAE (substitution failure is not an error).
- Since C++17, a `constexpr-if` allows us to enable or discard statements according to compile-time conditions (error outside templates).

## Chapter 9: Using Templates in Practice

Template code is a little different from ordinary code. In some ways template code is somewhat better mannered than ordinary (non-template) code. Although this may be an oversimplification, it has consequences not only for the way we write algorithms and data structures using templates but also for the day-to-day logistics of exposing and analyzing programs involving templates.

In this chapter we address some of these practicalities without necessarily delving into the technical details that underlie them. Many of these details are explored in Chapter 4. To keep the discussion simple, we assume that our C++ compilation systems consist of fairly traditional compilers and linkers (C++ systems that don't fall in this category are rare).

## 9.1 THE INCLUSION MODEL

There are several ways to organize template source code. This section presents the most popular approaches: the inclusion model.

### 9.1.1 Linker Errors

Most C and C++ programmers organize their nontemplate code largely as follows:

- Classes and other types are entirely placed in header files. Typically, this is a file with a `.hpp` (or `.h`, `.hh`, `.hxx`) filename extension.
- For global (noninline) variables and (noninline) functions, only a declaration is put in a header file, and the definition goes into a file compiled as its own translation unit. Such a CPP file typically is a file with a `.cpp` (or `.c`, `.cc`, `.cxx`, `.c++`) filename extension.

This works well: It makes the needed type definition easily available through the program and avoids duplicate definition errors for various other programs from the linker.

With these conventions in mind, a common error about which beginning template programmers complain is illustrated by the following (nonreusable) little program. As usual for "ordinary code," we declare the template in a header file:
