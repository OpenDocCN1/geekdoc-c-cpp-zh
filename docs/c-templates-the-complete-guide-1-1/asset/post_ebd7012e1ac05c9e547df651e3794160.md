
```cpp
}
ListModeIterator<T>* current = nullptr;
}
```

ListModeIterator provides all of the correct operations and nested types needed in a forward iterator, and requires very little code to implement them. Most of the hard work, defining member functions for all of the required operations, requires only a small amount of extra work.

### Hiding the interface

One drawback in our implementation of ListModeIterator is that we have to expose as public all of the operations that are used by the algorithms (operator*, operator++, operator==, and so on). To maintain this requirement, we can rework IteratorFacade to perform all of its operations in the derived class through a separate access class, which we call IteratorFacadeAccess:

Click here to view code image

```
Iterator/IteratorFacadeChecked.hpp
```

```cpp
// "friend" this class to allow IteratorFacade access
// to the operations of IteratorFacadeAccess
class IteratorFacadeAccess
{
  // only IteratorFacade can use these definitions
  template<typename Derived, typename Value, typename
    Reference, typename Difference>
  friend class IteratorFacade;

  // required of all iterators
  template<typename Reference, typename Iterator>
  static Reference dereference(Iterator const& i) {
    return i.dereference();
  }

  // required of bidirectional iterators
  template<typename Iterator>
  static void decrement(Iterator& i) {
    return i.decrement();
  }

  // required of random-access iterators
  template<typename Iterator, typename Distance>
  static void advance(Iterator& i, Distance n) {
    return i.advance(n);
  }

  // ...
};
```

This class provides static member functions for each of the core iterator operations, calling the corresponding (static) member function of the provided iterator. All of the static member functions are private, with the access only granted to IteratorFacade itself. Therefore, our ListModeIterator can make IteratorFacadeAccess a friend and keep the interface nested in the facade:

Click here to view code image

```cpp
friend class IteratorFacadeAccess;
```

### Iterator Adaptors

Our IteratorFacade makes it easy to build an iterator adaptor that takes an existing iterator and modifies its behavior. This provides even more flexibility when faced with reusing an iterator over a transformed view of the underlying sequence. For example, we might have a container of Person objects:

Click here to view code image

```
Iterator/iterator_adaptor.hpp
```

```cpp
std::string firstName;
std::string lastName;

friend std::ostream& operator<<(std::ostream& stm,
    const Person& p) {
    return stm << p.firstName << " " << p.lastName;
}
```

However, rather than iterating over all of the Person values in the container, we only want to see the first names. In this section, we develop an iterator adapter called ProjectionIterator that allows us to “project” the values of an underlying (base) iterator to some pointer-to-data member, for example, Person::firstName.

A projection iterator is an iterator defined in terms of the base iterator (Iterator) and the type of value that will be exposed by the iterator (T).

Click here to view code image

```
iterator/projector-iterator-1.cpp
```

```cpp
template<typename Iterator, typename T>
class ProjectionIterator
{
public:
    typedef typename
        std::iterator_traits<Iterator>::value_type
        value_type;

    typedef typename
        std::iterator_traits<Iterator>::difference_type
        difference_type;

    typedef typename
        std::iterator_traits<Iterator>::reference
        reference;

    typedef typename
        std::iterator_traits<Iterator>::pointer
        pointer;

    using Base = typename std::iterator_traits<Iterator>::value_type;
    using Class =
        typename std::iterator_traits<Iterator>::difference_type;

    Iterator iter;
    T Base::* member;

    friend class IteratorFacadeAccess;

    // implement core iterator operations for Iterator
public:
    ProjectionIterator(Iterator iter, T Base::* member)
      : iter(iter), member(member) {}
};

template<typename Iterator, typename T>
auto project(Iterator iter, T Base::* member) {
    return ProjectionIterator<Iterator, T>(iter, member);
}
```

Each projection iterator stores two values: it stores the iterator into the underlying sequence of (base values) and, more importantly, a pointer-to-data-member describing which member to project through. With that in mind, we consider the template arguments provided to the Iterator facade class. The first is the Iterator (base iterator) itself (to handle C++). The second (T) and third (T&) arguments are the value and reference types of our projection iterator, defining this as a sequence of T values. Base is the type of the underlying iterator’s value type. Therefore, our projection iterator will be an InputIterator when its base iterator is an input iterator, a Bidirectional Iterator when its base iterator is a bidirectional iterator, and so on. A project() function makes it easy to build projection iterators.

The only missing pieces are the implementations of the core requirements for ProjectionIterator. The most interesting is operator==(), which differentiates the underlying iterator and then projects through the pointer-to-data member.

Click here to view code image

The remaining operations are implemented in terms of the underlying iterator:

Click here to view code image

```cpp
void increment() {
    ++iter;
}

bool equal(const ProjectionIterator& other) const {
    return iter == other.iter;
}

void decrement() {
    --iter;
}
```

For brevity, we've omitted the definitions for random access iterators, which follow analogously.

That's it! With our projection iterator, we can print out the first names of a vector containing Person values:

Click here to view code image

```
*include/projectioniterator.cpp*
```

```cpp
#include <vector>
#include <algorithm>
#include <iterator>

int main()
{
    std::vector<Person> authors = {
        {"David", "..."},
        {"Nicolas", "..."},
        {"Douglas", "..."}
    };

    std::copy(project(authors.begin(), &Person::firstName),
              project(authors.end(), &Person::firstName),
              std::ostream_iterator<std::string>(std::cout, "\n"));
}
```

This program produces:

- David
- Nicolas
- Douglas

The facade pattern is particularly useful for creating new types that conform to some specific interface. New types need only expose some small number of core operations (between three and six for our iterator facade) and the facade takes care of providing a complete and correct public interface using a combination of CRTP and the Barton-Nackman trick.

## 2.1.3 MIXINS

Consider a simple Polygon class that consists of a sequence of points:

Click here to view code image

```cpp
class Point
{
public:
    double x, y;
    Point() : x(0), y(0) { }
    Point(double x, double y) : x(x), y(y) { }
};

class Polygon
{
public:
    std::vector<Point> points;

public:
    // public operations
};
```

This Polygon class would be more useful if the user could extend the set of information associated with each Point to include application-specific data such as the color of each point, or perhaps associate a label with each point. One option to make this extension possible would be to parameterize Polygon based on the type of the point:

Click here to view code image

```cpp
template<typename T>
class Polygon
{
private:
    std::vector<T> points;

public:
    // public operations
};
```

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_345_0.png)

```cpp
class LabeledPoint : public Point
{
public:
    std::string label;
    LabeledPoint() : Point(), label("") { }
    LabeledPoint(double x, double y) : Point(x, y), label("") { }
};
```

This implementation has its shortcomings. For one, it requires that the type `Point` be exposed to the user so that the user can derive from it. Also, the author of a labeled `Point` needs to be careful to properly use the same interface as `Point` (e.g., inheriting or providing all of the same constructors as `Point`). A `LabeledPoint` will not work with a type that expects a `Point` because it does not have the same interface.

This constraint becomes more problematic if `Point` changes from one version of the C++ template to another! The addition of a new `Point` constructor could require each derived class to be updated.

Mixins provide an alternative way to customize the behavior of a type without inheriting from it. Mixins essentially invert the normal inheritance hierarchy, because the new classes are “mixed in” to the inheritance hierarchy as base classes of a class template rather than being created as a few derived classes. Although the mixin classes are not directly inherited from, they are used to provide additional behavior and data members and other operations without requiring any duplication of the interface.

A class template that supports mixins will typically accept an arbitrary number of extra class types from which it will derive:

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_345_1.png)

```cpp
template<typename... Mixins>
class Point : public Mixins...
{
public:
    double x, y;
    Point() : Mixins()..., x(0.0), y(0.0) { }
    Point(double x, double y) : Mixins()..., x(x), y(y) { }
};
```

Now, we can “mix in” a base class containing a label to produce a `LabeledPoint`:

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_345_2.png)

```cpp
class Label
{
public:
    std::string label;
    Label() : label("") { }
};

using LabeledPoint = Point<Label>;
```

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_345_3.png)

```cpp
class Color
{
public:
    unsigned char red = 0, green = 0, blue = 0;
};

using MyPoint = Point<Label, Color>;
```

With this mixin-based `Point`, it becomes easy to introduce additional information to `Point` without changing its interface, so `Polygon` becomes easier to use and evolve. Users need only apply the implicit conversion from the point specialization to their mixins (label or color), or access to access that data or interface. Moreover, the `Point` class can be entirely hidden, with the mixins provided to the `Polygon` class template itself.

![](img/58b3b6b55f5326ebb5db11acf6ac18cf_345_4.png)

```cpp
template<typename... Mixins>
class Polygon
{
public:
    std::vector<Point<Mixins...>> points;
    // ...
};
```

Mixins are useful in cases where a template needs some small level of customization—such as decorating internally stored objects with user-specified data—without requiring the library to expose and document their internal data types and their interfaces.
