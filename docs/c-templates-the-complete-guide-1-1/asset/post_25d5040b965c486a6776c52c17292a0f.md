
```cpp
parse(42);            // OK: T deduced as int (4)
                      // (also the type of arg)
```

However, the special rules for type deduction may result in some surprises:

```cpp
std::string const c = "hi";
parse(c);                 // OK: T deduced as std::string const&
parse("hi");              // OK: T deduced as char const (&)[3]
const char arr[4];        // also the type of arg
parse(arr);               // OK: T deduced as char const (&)[4]
```

In each of these cases, inside parse(), the parameter arg has a type that is “known” whether we passed an rvalue (the two occurrences) or a non-const or const lvalue. This is the only way to pass an argument, such that it can be used to distinguish behavior of all of these three cases.

This gives the impression that declaring parameter as a forwarding reference for all cases is important. But beware, there is no free lunch.

For example, this is the only way where template parameter T implicitly can become a reference type. As a consequence, it might become an error to use T to declare a local object without initialization:

```cpp
template<typename T>
void foo(T&& arg)
{
    T x;
    ...
}

foo(42);        // OK: T deduced as int
int i;
foo(i);         // ERROR: T deduced as int&, which makes the
                // declaration of x in foo() invalid
```

See Section 35.6.2 on page 279 for further details about how you can deal with this situation.

## 7.3 USING STD::REF() AND STD::CREF()

Since C++11, you can let the caller decide, for a function template argument, whether to pass it by value or by reference. When a template is declared to take arguments by value, the caller can use std::cref() and std::ref(), declared in header file <functional>, to pass the argument by reference. For example:

```cpp
template<typename T>
void print(T arg)
{
    ...
}

std::string const s = "hello";
print(s);                 // pass by value
print(std::cref(s));      // pass as "by reference"
```

However, note that std::cref() does not change the handling of parameters in templates. Instead, it uses a trick: It wraps the passed argument by an object that acts like a reference. In fact, it creates an object of type std::reference_wrapper<> referring to the original argument and passes this object by value. The wrapper more or less supports only one operation: an implicit type conversion back to the original type, yielding the original object. So, whenever you have a valid operator for the passed object, you can use the reference wrapper instead. For example:

```cpp
#include <functional>       // for std::cref()
#include <string>
#include <iostream>

void printString(std::string const& s)
{
    std::cout << s << '\n';
}

template<typename T>
void print(T arg)
{
    printString(arg);        // might convert arg back
}

int main()
{
    std::string s = "hello";

    print(s);              // print s passed by value
    print(std::ref(s));    // print s passed by ref
}
```

The last call passes by value an object of type std::reference_wrapper, which then passes the parameter as the underlying type. This is what happens when there is an implicit conversion back to its underlying type.

Note that the compiler has to know that an implicit conversion back to the original type is necessary. For this reason, std::ref() and std::cref() usually only work with types for which an operator<< is defined.

```cpp
template<typename T>
void print(T& arg)
{
    std::cout << arg << '\n';
}

std::string s = "hello";
print(s);                 // OK
print(std::ref(s));       // ERROR: no operator << for
                          // reference wrapper defined
```

Also, the following isless example fails because you can't compare a reference wrapper with a char const*:

```cpp
template<typename T1, typename T2>
bool isless(T1 arg1, T2 arg2)
{
    return arg1 < arg2;
}

std::string s = "hello";
if (isless(std::ref(s), "world"))
{
    // ERROR
}
if (isless(std::cref(s), std::string("world")))
{
    // ERROR
}
```

It also doesn't help to give arg1 and arg2 a common type T:

```cpp
template<typename T>
bool isless(T arg1, T arg2)
{
    return arg1 < arg2;
}
```

because then the compiler gets conflicting types when trying to deduce T for arg1 and arg2.

The final effect is: a reference wrapper is a reference as a first-class object, which you can copy and therefore pass by value to function templates. You can also use it in classes, for example, to hold references to objects in a container. But you always finally need a conversion back to the underlying type.

## 7.4 DEALING WITH STRING LITERALS AND RAW ARRAYS

So far, we have seen the different effects for template parameters when using string literals and raw arrays:

- Call-by-value decays so that they become pointers to the element type.
- Any form of call-by-reference does not decay so that the arguments become references that still refer to arrays.
- Both can be passed by value. When decaying arrays to pointers, you lose the ability to distinguish between handling pointers to elements from handling passed arrays.

On the other hand, when dealing with parameters whose arguments are literals, not decaying can become a problem, because string literals of different sizes have different types. For example:

```cpp
template<typename T>
void foo(T const& arg1, T const& arg2)
{
    ...
}

foo("hi", "guys"); // ERROR
```

Here, foo("hi", "guys") fails to compile, because "hi" has type char[3], while "guys" has type char[5]. But the template requires them to have the same type T. Only if the string literals were to have the same length would code compile. For this reason, it is strongly recommended not to use string literals of different lengths in test cases.

```cpp
template<typename T>
void foo(T arg1, T arg2)
{
  ...
}
foo("hi", "guys"); // compiles, but...
```

But that doesn't mean that all problems are gone. Even worse, compile-time problems may have become run-time problems. Consider the following code, where we compare the passed argument using arg1 == nullptr:

```cpp
template<typename T>
void foo(T arg1, T arg2)
{
  if (arg1 == nullptr) { // compare addresses of passed arrays
    ...
  }
}
foo("hi", "guys"); // compiles, but...
```

As written, you have to know that you should interpret the passed character pointers as strings. But that's possibly not the case anyway, because the template also is called with arguments coming from string literals that have been decayed already (e.g., by calling from another function or by value or by using std::array/std::span, both of which are a typical way to pass a sequence of chars).

Nevertheless, in many cases, dealing with foo() carefully—especially for checking whether a pointer is passed or a sequence of pointers or even a pointer to an array, and the other argument expecting the argument to have converted to the same type—is complicated. One typical way is to prefer forwarding references if you want to use a forwarding function to deal with multiple types. Another approach is to use type traits. In those cases, you might explicitly decide the arguments using type traits such as std::is_pointer<> (which is also true for pointers; see Section 7.5 on page 278).

Note that other type traits such as std::is_array<> simply don't apply, as is also the case for std::is_pointer<> (see Section 7.5 on page 279 and Section D.6 on page 716).

### 7.4.1 SPECIAL IMPLEMENTATIONS FOR STRING LITERALS AND RAW ARRAYS

You might have to distinguish your implementation according to whether a pointer or an array was passed. That, of course, requires that a passed array wasn't decayed yet.

To distinguish those cases, you have to detect whether arrays are passed. Basically, there are two options:

- You can declare template parameters so that they are only valid for arrays:

```cpp
template<typename T, int sz>
void foo(T (&arg1)[sz])
{
  ...
}
foo("hi"); // OK (deduce T as const char, sz as 3)
```

- You can use type traits to detect whether an array (or a pointer) was passed:

```cpp
template<typename T>
void foo(T& arg1, T& arg2)
{
  if (std::is_array<T>::value) { // compiles for arrays of different type
    ...
  }
}
```

Due to this special handling, often the best way to deal with arrays in templates is to use std::array or std::span. Another benefit of std::array is that it does not support the misuse of the call. However, all this is not a general guarantee. In fact, arrays, like any string literal, are raw arrays, so we always have to take them into account.

## 7.5 DEALING WITH RETURN VALUES

For return values, you can also decide between returning by value or by reference. However, returning a reference has the potential of a nasty side effect. The caller might be able to modify an object of your function. There are a few cases where returning references is common programming practice:

- Returning elements of containers or strings (e.g., by operator[] or front())
- Granting write access to class members
- Returning objects for chained calls (e.g., operator<< and operator>> for streams and operator= for class objects in general)
