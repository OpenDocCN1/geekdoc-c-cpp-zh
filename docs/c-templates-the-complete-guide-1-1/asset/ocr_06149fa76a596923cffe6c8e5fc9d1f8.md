Look carefully at the use of InsertionSort: The actual typelist to be sorted is a list of indices into the typelist, constructed with MakeIndices<T>. Therefore, the result of the insertion sort is a set of indices into the tuple, which is then provided to select(). ```

Here, indices contains indices into the vector strings. The sort() operation sorts the actual indices, so the lambda provided as the comparison operation accepts two unsigned values (rather than their string values). However, the body of the lambda uses those unsigned values as indices into the strings vector, and the sorting is actually occurring in the context of the strings, rather than at the end of the sort, and indices provides indices into strings, sorted based on the values in strings.

Our use of InsertionSort for the tuple sort: (1) employs the same approach. The Adapter template functor expects a template metafunction (its metaApply) that accepts two indices (Column 1) and then expands the indices into the corresponding elements from its tuple argument. In a sense, the member template Apply has "expanded" the typelist provided to its argument, and is the same way that the lambda captured the strings vector from its enclosing scope. Apply performs the same function on the enclosing scope by passing the element types to the underlying Metafunction, completing the adaptation.

Notice that all of the computation for the sort is performed at compile time, and the resulting tuple is sorted directly, with no erroneous copying of values at run time.
