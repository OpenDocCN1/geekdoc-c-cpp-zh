However, it is not difficult to add specializations of `at_least` to handle `int`, `double`, `std::complex`, and a function template or function template parameter pack that will make this mechanism work for an arbitrary class or enumeration type. For example:

```cpp
template <std::size_t N>
constexpr bool at_least() {
    return N <= 1;
}

template <class... Args, std::size_t N>
constexpr bool at_least() {
    return sizeof...(Args) >= N;
}

template <class T, class... Args>
struct at_least<std::tuple<T, Args...>> {
    static constexpr std::size_t value = 1 + at_least<Args...>::value;
};

template <class... Args>
struct at_least<std::tuple<Args...>> {
    static constexpr std::size_t value = sizeof...(Args);
};

template <class... Args>
constexpr bool at_least<Args...>::value;
```

Note that you only need to include `<tuple>` to use the two tuple-like access helper functions `at_least` and `tuple_size`.

In addition, note that the third one above (using the tuple-like protocol) works for all tuples. For example, it does not apply to an ordinary type such as `int`. As a result, you can use this implementation to check whether the type is a tuple or not. This is not only an interesting but also useful implementation, as it can also be used to detect the type of a tuple. For example, a container type such as `std::array<int,4>` is not a tuple, but it can be converted to one by using `std::tuple_size` and `std::tuple_element`. ## 15.6.10 GENERIC LAMBDAS

Lambdas have quickly become one of the most popular C++11 features, in part because they significantly ease the use of the functional constructs in the C++ standard library and in many other modern C++ libraries, such as Boost.Asio, which is partly based on the Boost.Asio library. Lambdas are a powerful feature in part because they can be used to define small, self-contained functions that are not necessarily small and self-contained. For example, consider a function template that finds the first negative value from a sequence:

```cpp
template<typename Sequence>
auto findNegative(const Sequence& seq) -> decltype(seq.begin()) {
    return std::find_if(seq.begin(), seq.end(),
        [](const auto& value) {
            return value < 0;
        });
}
```

In this function template, the most complicated part of the lambda (by far) is its parameter type: C++14 introduced a concept of "generic" lambdas, where one or more of the parameters use `auto` to deduce the type rather than using a specific type:

As you can see, a parameter of a lambda is handled similarly to an `auto` by the type of a variable with an initializer. It is replaced by an invented type parameter. However, unlike in variable `auto` deduction, the deduction isn't performed immediately because the lambda isn't called to know the argument types. Instead, the closure type is not fully defined, and the invented type parameter is added to its template parameter list. Thus, the lambda clone can be invoked with any argument type, as long as that argument type supports the operations whose semantics is controlled by the body. For example, the lambda could be called with either an `int` or a C++ string.

```cpp
[](int i) {
    return i < 0;
}
```

The C++ compiler translates this expression into an instance of a newly-invented class specific to this lambda. This instance is called a closure or closure object, and the class is called a closure type. The closure type has a function call operator, and hence the closure is a function object. For this lambda, the closure type would look something like the following (we leave out the conversion function to a pointer-to-function value for brevity and simplicity):

```cpp
class SomeCompilerSpecificName
{
public:
    SomeCompilerSpecificName() = delete; // only callable by the
                                          // compiler

    bool operator()(int i) const
    {
        return i < 0;
    }
};
```

If you check the cppreference for a lambda, `std::is_class_v` will yield true (see Section 2.1 on page 70).

A lambda expression thus results in an object of this class (the closure type). For example:

```cpp
foo([]
{
    int i;
    return i < 0;
});
```

creates an object (the closure) of the internal compiler-specific class `SomeCompilerSpecificName`:

```cpp
foo(
    SomeCompilerSpecificName{});  // pass an object of
                                    // the closure type
```

If the lambda were to capture local variables:

```cpp
int x, y;

[=](int i) {
    return i < x && i < y;
}
```

those captures would be modeled as initializing members of the associated class type:

```cpp
class SomeCompilerSpecificName
{
private:
    int x, y;

public:
    SomeCompilerSpecificName(int x, int y) // only
                                           // callable by the compiler
        : x{x}, y{y} {}

    bool operator()(int i) const
    {
        return i < x && i < y;
    }
};
```

For a generic lambda, the function call operator becomes a member function template, as in our simple generic lambda

```cpp
[](auto i) {
    return i < 0;
}
```

is transformed into the following class (again, ignoring the conversion function, which becomes a conversion function template in the generic lambda case):

```cpp
invoke([]() auto x auto y {
    std::cout << x + y << "\n";
}, 21, 21);
```

Here the lambda expression appears in `main()`, and that's where an associated name is created. However, the call operator of the closure is instantiated at that point. Instead, the `invoke()` function template is instantiated with the closure type as the first parameter type and `int` (the type of the `x` and `y` used above) as the second type. The instantiation of the `invoke()` is called with a copy of the closure (which is still a closure associated with the original lambda), and it instantiates the `operator()` template of the closure to satisfy the call.

## 15.11 ALIAS TEMPLATES

Alias templates (see section 2.8 on page 39) are "transparent" with respect to deduction. That means that whenever an alias template appears with some template arguments, that alias's definition (i.e., the type to the right of the `=` sign) is substituted with the arguments, and the resulting pattern is what is used for the deduction. For example, template argument deduction succeeds in the following three calls:

```cpp
template<typename T, typename Cont>
class Stack
{
};

template<typename T>
using DequeStack = Stack<T, std::deque<T>>;

template<typename T, typename Cont>
void f1(Stack<T, Cont>);

template<typename T>
void f2(DequeStack<T>);

template<typename T>
void f3(Stack<T, std::deque<T>>);  // equivalent to f2

void f4(DequeStack<int> intStack)
{
    f1(intStack);   // OK: T deduced to int, Cont deduced
                    // to std::deque<int>
    f2(intStack);   // OK: T deduced to int
    f3(intStack);   // OK: T deduced to int
}
```

In the first call (to `f1()`), the use of the alias template `DequeStack` in the type of `intStack` has no effect on deduction: The specified type `DequeStack<int>` is treated as its substituted type `Stack<int, std::deque<int>>`. The second and third calls have the same deduction behavior, because `DequeStack<int>` is an equivalent for `Stack<int, std::deque<int>>`. For purposes of template argument deduction, template aliases are transparent: They can be used to simplify code without affecting deduction.

Note that this is possible because alias templates cannot be specialized (see Chapter 5 for details on the type of template specialization). Suppose the following were possible:

```cpp
template<typename T> using A = T;
template<> using A<int> = void;  // ERROR, but suppose it
                                   // were possible.
```

Then we would not be able to match `A<T>` against type `void` and conclude that `T` must be `void` because both `A<int>` and `A<void>` are equivalent to `void`. The fact that this is not possible guarantees that each use of an alias can be generically expanded according to its definition, which allows it to be transparent for deduction.
