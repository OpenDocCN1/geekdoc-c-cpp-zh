## Server 2

hapi is a framework used for building applications and services. Behind every service, there is a server; something that serves the client needs. hapi is at its core a superset of an HTTP server. Everything around hapi is tied to this fact, so we kick off this book talking about the main functionality. It's from this everything else is configured and makes a difference. We're going to be talking about lot of concepts that are related to the server, plugins, handlers, testing, and more.

In this chapter we look at how to set up a server and how we've set up the server for our hapi-plugins.com example. We're going to teach you the ins and outs of the server in the hapi framework. You'll know how to set up caching. You'll get a first glimpse into plugins and how to add methods that will be available throughout your application. ### Setting up a simple server

Of course we can't start a book without first having a hello world example. Well, yes we can actually, but we're not going to. It's important to know how to set up a server in its simplest configuration before advancing to more complex setups.

```javascript
var Hapi = require('hapi');
var server = new Hapi.Server();
server.connection();
server.route({
    method: 'GET',
    path: '/',
    handler: function (request, reply) {
        return reply('hello hapi');
    }
});

server.start(function (err) {
  console.log(server.info.uri);
});
```

We created an instance of a hapi server. We don't actually have to do anything at all to configure it. The next step is to get a connection to the server. The connection is the host and port that the server is listening to. By default, the host is set to localhost and the port is generated randomly on ports that don't require system administrator access, and that are available. Since we don't know what the port is, we print the URI out at the end so we can see where our server is listening.

We add a route so that we have somewhere we can actually send a request. We'll go a lot further into routes in Chapter 3, but for now, think of a route as a configured path that the request from the client (browser) can take in order to have a particular response served.

At this point we start the server, and log the server URI so that we know what the server started on.
The next logical steps would be to set a port for our server to start on so that we know it's the same each time. This can be accomplished by using the options for the connection: `server.connection({ port: 8088 });`

### Setting up the server for hapi-plugins

Now we have a basic understanding of how to set up a server, let's examine what we'll need to do up the server for hapi-plugins.

A typical architecture for a Single Page Application (SPA) is to have some HTML templates served through a front-end framework such as Ember, AngularJS, React or others. We've chosen to use React for our front-end. The information served through back-end methods of API serving to the data, but a cleaner approach is to have a separate API server handle the data and this is the approach we have decided to use.

```javascript
var internals = {
  servers: {
    http: 8080,
    host: '0.0.0.0',
    labels: ['http']
  },
  api: {
    port: 8088,
    host: '0.0.0.0',
    labels: ['api']
  },
  options: {
    files: {
      relativeTo: __dirname
    }
  }
};
```

We're putting the main HTTP server on port 8080 and the API server on port 8088. They're both running and listening on 0.0.0.0 which is used for binding to all ip addresses for the connections. When the server starts up, this will only be running one process. The labels in the configuration are for labeling the connection so that the appropriate plugins can be loaded. Hapi is a framework that's plugin-centric, meaning that everything is designed to be architected around plugins. You can find more details about plugins in Chapter 6, but for now, let's realize an important concept. All of the methods available on the server are also available on anything passed to the plugin. It's the first argument to a plugin register object. Sometimes the argument name is plugin and other times it's server. We will call it a plugin.

For hapi.com we are setting up two connections for our server. One is for HTML content, and the other is for our API.

We begin by loading our libraries that we're going to. We've organized our code as Models, Routers, and Controllers. We also have code specifically for our API.
What's new here are the labels. They serve as an indicator for the system that can be used to decide which plugins listen for each connection. We are likely to have only some plugins listen to one connection and not the other. Some may listen to both, such as a /heartbeat type call, but in general unless one is using SSL/TLS and the other encrypted there should be little duplication. You can read more about how to select plugins and how to manage plugins in Chapter 6. This is done using the server.register().
