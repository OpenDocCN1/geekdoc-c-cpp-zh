## Writing a hapi test

hapi was designed with testing in mind. In order to ship a release, every line and every code path must have a test for it. As a result, there are quite a lot of tests in hapi and its dependencies. In order to help speed up the time it takes to run tests, as well as avoid issues with file descriptor limits, hapi has built-in mock request support. This is delivered through a function named inject provided by the module shot. To help illustrate the power of shot at the test below. Also notice that instead of using experimental style of testing, the test is written with test shortcuts for the BDD style.

```javascript
// Load modules
var Code = require('code');
var Hapi = require('hapi');
var Lab = require('lab');
```

```javascript
var lab = exports.lab.script();
var describe = lab.describe;
var it = lab.it;
var expect = Code.expect;
```

```javascript
describe('inject', function () {
  it('returns the response result', function (done) {
    var handler = function (request, reply) {
      return reply('hello');
    }

    var server = new Hapi.Server();
    server.connection();
    server.route({
      method: 'GET',
      path: '/',
      config: { handler: handler }
    });

    server.inject('/', function (res) {
      expect(res.statusCode).to.equal(200);
      expect(res.result).to.equal('hello');
      done();
    });
  });
});
```

In the previous example the server.start function wasn't executed. As a result, no socket was created or attached to the server. However, a request was made to the server and a response was received. The request object includes all of the properties that a server cares about. Similarly, the response object passed to the inject callback includes the response body and relevant headers and status code.

Unless you are creating information from a socket, the best solution is to use inject. If this is the approach you take then tests should execute much faster than if they relied on a real socket. Also, it makes much easier to avoid the setup and teardown associated with a socket. Speaking of which, if you need to use a socket, pass 0 as the port to the connection function in order to ensure that the port is used. Notice that the port that ends being used can be retrieved from the server.info.port property after a server is started.

```javascript
// Load modules

var Code = require('code');
var Hapi = require('hapi');
var Lab = require('lab');
var Wreck = require('wreck');
```

```javascript
var lab = exports.lab.script();
var describe = lab.describe;
var it = lab.it;
var expect = Code.expect;
```

```javascript
describe('real request', function () {

  it('returns a real response', function (done) {

    var handler = function (request, reply) {
      return reply('hello');
    }

    var server = new Hapi.Server();
    server.connection({ port: 0 });
    server.route({
      method: 'GET',
      path: '/',
      config: { handler: handler } };

    server.start(function () {
      Wreck.get('http://localhost:' + 
        server.info.port,
        function (err, res, payload) {
          expect(res.statusCode).to.equal(200);
          expect(payload).to.equal('hello');
          server.stop(done);
        }
      );
    });
  });
});
```

Wreck is a lightweight HTTP/HTTPS client wrapper that was designed for hapi. This is the module of choice when doing any requests. That being said, the request module is completely supported as well. Locally, the difference in test time between the inject example and the wreck example is around 18ms. Even 18ms on its own isn't a lot, all of the tests you can create quickly add up.

## Code coverage

Aside from all of previous features that go into lab, code coverage is one of its strongest features. Code coverage in lab depends on the espree module for generating the AST. Other typical line by line coverage, lab will also determine if different branches are executed by tests. This can be anything from many conditionals within the if statement to standard ternary statements. Furthermore, lab will also determine if a code path is to be executed, and can be deleted.
The 'html' and 'console' reporters are the most heavily tested when it comes to showing code coverage. By default, code coverage isn't enabled when you run lab. To enable it you need to pass in the -c or --coverage flags. The flag will enable code coverage reporting and that the tests cover 100% of the code. If you less than 100% code coverage then you can use the -t or --threshold flag following by a number that represents the percent of code covered before error. If the tests fail to pass the threshold, lab exits with an error code.

## Reporters

Using coverage is a must when it comes to developing modules in the hapi ecosystem. All of the modules published under hapi organization demand 100% code coverage. Therefore, if you plan to contribute any changes or enhancements to these modules you must add tests for the changed code. There may naysayers when come to code coverage, but it's the mechanism that has been chosen to gauge code works. In addition to adding tests that cover every line and code path in a module, hapi maintainers also review the tests to help ensure its accuracy.

Lab comes packed with numerous reporters as well as support for any custom reporters. The reporters have evolved over the years from feedback from the community. Currently, lab supports the following reporters:

- console - CLI output
- html - report to an html stream, pipe to a file
- json - JSON formatted report
- junit - JUnit XML format
- tap - TAP format
- lcov - lcov format
- clover - clover XML format
- custom

Previously, in the code coverage section, the 'console' and 'html' reporters were demonstrated as it relates to reporting coverage. However, the 'html' reporter does more, it also reports on the tests run and how long each took. An example of the 'html' reporter as it relates to individual tests is shown here:
