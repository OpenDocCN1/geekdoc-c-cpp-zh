# History of lab

For best results, hapi works with the lab runner. Lab is the testing framework that was developed for use hapi and hapi plugins. hapi originally used mocha and chai to execute tests. However, when Node.js 0.10 was released, hapi added support for the new release and incorporated domains. Domains have a hairy feature ever since their release, testing support excluded. When 0.10 was released, mocha was slow to adapt support for adequately testing domains. As a result of the desire for hapi to use domains, something had to be done. As a result, lab was created. Originally, lab was a fork of mocha. Features that were not needed for hapi were trimmed and more features were added.

Code coverage is an essential factor for ensuring that quality code is committed to repositories. Therefore, code support needs to be baked in the testing framework as a simple flag when you run tests.

Before lab was, mocha tests in hapi were being run with the blanket coverage module. Blanket itself relies on esprima to create abstract syntax trees (AST) of the code in order to help identify statements to insert for code coverage analysis. Blanket was carried over into lab was created. However, over time, code coverage was baked into lab, instead of being delivered through a third party.

Code reporting also evolved as a result of incorporating the analysis within lab. This helps to make code coverage a first class citizen in lab reports. As a result, the HTML reporter now indicates to the develop lines in their code that will never be reachable by tests.

It makes it easy to identify areas of code that are dead and can be deleted, making your code even more maintainable as a result.

When hapi was mocha for testing, it was also using chai to help structure the assertions. The hapi maintainers favor writing tests using the expect style, as opposed to should or assert. Over time, the use of chai surfaced a couple of edge case function names that weren't consistent with the larger framework. For example, the exist property isn't executed as a function, unlike some of the other parts of the syntax. These inconsistencies led to a few bugs popping up from time to time. These bugs had to do with the fact that it was too easy to forget a method () and would result in an assertion that was never executed. Because it was never executed, it passed incorrectly.

As a result, the assertion library named code was created. Code takes the chai syntax and may exist become function, just as all of the truth checks for true, false, and null functions. Below you can see the differences between chai and code.

First our chai example is:

```
expect(foo).to.exist;
expect(bar).to.be.true;
```
