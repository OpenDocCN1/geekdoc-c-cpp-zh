
# Organizing handlers

There are many ways to organize code. For simple routes, perhaps it makes sense to throw everything in a route. Here is the simplest example:

```javascript
server.route({
  method: 'GET',
  path: '/',
  handler: function (request, reply) {
    reply.view('index');
  }
});
```

However, when working on large projects, we have found that it can get cluttered to do this way. This is where we use the route configuration (see Chapter 3) to make life easier for us.

We have organized the code into /lib/routes.js, which is our destination for all of our routes. Whenever we add a new route, or need to see the routes, we have all in this one simple location. A nice convention to follow. It doesn't have to be a routes.js file, we could also put them in lib/index.js. This clearly named file, however, makes it obvious to everyone where it is.

A typical setup has the config for the route living in a completely different file instead, and in that file is where the handler resides. Our hapi-plugins.com example, has only this in the routes file:

```javascript
server.route({
  method: 'GET',
  path: '/',
  config: Controllers.Home.get
},
// ...
});
```

When architected correctly the handlers are large, putting each route in their own file can really make the code easier to read. Starting a new route, a file with conventions, can be copied over and the handler itself modified. It makes for a very clear and easy to read structure.

More discussion on the above example can be found in Chapter 6 if you want more details.

# Built-in handlers

## File

File handlers are used to generate static endpoints for serving up files. You are likely to use this with single files that don't fit in the directory handler explained shortly.

We are using the file handler to serve up the favicon, or the little specific icon that browsers use to associate a website.

We add the favicon to our lib/routes.js file as follows:

```javascript
{
  method: 'GET',
  path: '/favicon.ico',
  handler: Controllers.Static.favicon
}
```

There are multiple ways of using the file handler, all of which involve modifying lib/controllers/handlers/static.js in our particular setup.

### STRING

This is how we're using the handler for hapi-plugins.com and is the most straight forward approach.

```javascript
exports.favicon = {
  file: dirname + '../../public/favicon.ico'
};
```

### CALLBACK

A callback takes the request object as an argument that returns the absolute or relative path.

```javascript
exports.favicon = {
  file: function (request) {
    return dirname + '../../public/favicon.ico'
  }
};
```

### OBJECT

An object with several options.

```javascript
exports.favicon = {
  file: {
    // a path string or function as described above
    path: __dirname + '/../../public/favicon.ico',
    filename: '??',
    mode: false,
    lookupCompressed: false
  }
};
```

Our path indicates where to find the file to serve up. This can also be set to the callback function as discussed above.

The filename is an optional filename to specify if sending a "Content-Disposition" header. This defaults to the basename of the path.

Mode specifies whether or not the "Content-Disposition" will be included. By default this is set to false, which means it's not included.

lookupCompressed, if true, looks for the same filename with the '.gz' suffix for a precompressed version of the file to serve if the request supports content encoding. It defaults to false.

### DIRECTORY

A more likely use-case than the file handler is the directory to serve up multiple files. It is common in order to serve files as images, CSS or JavaScript files used for the front-end. Similar to our file handler, the route is set up in lib/routes.js and in this case, we are doing images and CSS as follows:

```javascript
{ method: 'GET', path: '/css/{path}', handler: Controllers.Static.css },
{ method: 'GET', path: '/img/{path}', handler: Controllers.Static.img },
{ method: 'GET', path: '/js/{path}', handler: Controllers.Static.js },
// ...
```

The handler is defined in a way that we are only going to look at the first one as an example:

```javascript
exports.css = {
  directory: {
    path: __dirname + '/../../public/css',
    index: false
  }
};
```

The path is where the actual data we would like to retrieve and display. There is a number of options that can be set here as well. We are first foremost setting index to false. In the folder, the options for directory are as follows:

- path - See handler for an explanation of the various ways of setting this
- index - Can be true, false, or a string representing the name of the index file and it is set to true.
- listing - Determines whether a directory should show in the absence of an index. Defaults to false.
- showHidden - Determines if hidden files should be displayed by listing. Defaults to false.
- redirectToSlash - if there's a trailing slash, this will be redirected without the slash.
- lookupCompressed - If true, looks for the same filename with the '.gz' suffix for a precompressed version of the file to serve if the request supports content encoding. Defaults to false.
- defaultExtension - a string that is appended to the file if the requested file is not found. Defaults to empty string.

# VIEWS HANDLER

The views handler displays templates. In practice, this option isn't very used. The more common approach is configuring the server with the views option, and then using the regular handler for reply.views(). Because hapi supports both, we'll take a look at the views handler and focus more on how to configure the server directly with reply.views(). For our hapi-plugins project, we are not using a views handler, but it should be mentioned how it can use. In both cases, the server is configured with views:

```javascript
plugin.views({
  engines: {
    module: require('handlebars')
  },
  path: __dirname + '/views'
});
```

We are setting the rendering engine and specifying the relative path from which we will be reading the templates. The property in engines configuration sets the file extension that will be used for that particular rendering engine. A very basic use-case would look like the following:

```javascript
exports.terms_of_service = {
  view: 'terms_of_service'
}
```

Here view just takes a string with the template filename. Where we would want to override the server's views configuration, it would be more elaborate with the view taking an object:

```javascript
exports.terms_of_service = {
  view: {
    template: 'terms_of_service',
    context: {
      serviceType: 'provider'
    }
  }
}
```

For a quick point of clarity, context is the json object with the actual data that is sent to your template. In this case, your template terms_of_service can refer to serviceType in your template and it will fill in the value. More discussion on templating is in Chapter 9, and depending on the templating engine, this syntax will differ.

If there's no context passed to the object, then it is set to a context object with the following properties:

- payload - containing request.payload
- params - containing request.params
- query - containing request.query
- pre - containing request.pre

The view object can also contain an options property, which can serve to override the server view settings.

# REGULAR HANDLER USING SERVER.VIEWS

Using reply.view() is the most common way to render a template. For the main page of hapi-plugins, we are rendering just an index file and we're displaying a random quote on the page.

```javascript
module.exports.get = {
  handler: function (request, reply) {
    reply.view('index', {
      finalmsg: internals.quotes[Math.floor(Math.random() * internals.quotes.length)]
    });
  }
};
```

And in the template we see the following:

```html
<div id="finalfrontier" class="col-md-12">
  {{finalmsg}}
</div>
```

If you would like to know more about handlebars, you can read more at: handlebarsjs.com.

# proxy

Many starting out with a proxy can be an easy way to start in a project. You have some legacy service that you want to replace, and a proxy can be a good way to start. In fact, the proxy feature was the most heavily used feature of hapi. This is precisely how we started to use hapi at WalmartLabs. Below is an example of how you could proxy Google.

```javascript
server.route({
  method: '*',
  path: '/path*',
  config: {
    handler: {
      proxy: {
        host: 'google.com',
        port: 80,
        protocol: 'http',
        // 6th redirect get a 300 redirect
        redirects: 5,
        passThrough: true,
        xforward: true
      }
    }
  }
});
```
