If an entity does not have its primary key and you want the primary key to be generated for the table based on the relationships and surrogate primary keys of the parent tables, make sure you create the primary key for the entity and select all the relationships for its columns before clicking Engineer To Relational. Otherwise, the child table will not have a primary key. See Chapter 8 for an example of generating data warehouse fact tables (Figures 8-1, 8-2, and 8-3).

If the relationship is on the cardinality of many-to-many (m:n), a new table will be created to resolve the m:n cardinality, and a new column on the primary key attribute in each table will be created. A primary key for the new table is created based on these columns. Also, new one-to-many relationships are created for both tables involved.

If a relationship has its own attributes, some tools will create new table with all original relationships and attributes from the relationship. Data Modeler does not add the attribute as a column to the child table and creates a dependent constraint for (for more than in the next section). If you do not want the column to be added to the child table, do not create an attribute for the relationship but to the entity you want it to belong. It might mean you need to create a new entity.

If an attribute is multivalued such as a phone number (home, office, cell phone), there are a couple of choices. You can create a user-defined data type (collection) and use that for the data type for the attribute (see Chapter 4 for more information), or you can split the attribute into several attributes for the entity or create a new entity for the multivalued attribute. Usually a new entity is recommended because it is more flexible, but sometimes you need to limit the values to a certain number (maybe a Person is allowed to have no more than three phone numbers), and then it is better to use that number of attributes in the original entity. The solution depends on the requirements and how far the model needs to be normalized.

If an attribute is composite (structured) such as an address (StreetName, Number, City, ZIP, Country), there are again a couple of choices. You can create a user-defined data type (structured) and use that for the data type for the attribute (see Chapter 4 for more information), or you can split the attribute into several attributes into the entity or create a new entity for the composite attribute. Usually a new entity is recommended because it is more flexible, and you might find other attributes for that entity (AddressType, AddressValidUntil, and so on), but sometimes you need to denormalize to avoid joins and end up adding the attributes to the original entity (in this case, make sure your solution meets all the requirements). The solution depends on the requirements and how far the model needs to be normalized.
