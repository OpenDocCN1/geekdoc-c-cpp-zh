# Tuning and Refactoring Your Model

Sooner or later you need to make changes to your model. Especially when the system development methodology is agile, there will be many changes in the logical model after the first version; the design work is iterative. The more you check the models in every phase, the better the outcome will be.

Problems with refactoring are not usually with the database and its objects on top of that: test cases, programs, data classes, migrations, and so on. It is good to find the main concepts and their relationships as early as possible and to understand them correctly. Splitting an entity or fixing a problem in later phases of the process usually a lot of work. In the sense of database objects, refactoring is easy, if you have a tool like Data Model. You just make your changes to the logical model and engineer to the relational model. Your changes will go to your physical model, and you will produce the new DDL scripts easily. My opinion is that you should always follow the procedures no matter busy you are: make a change in the logical model and then engineer to the relational model. Never make the changes first in the relational model or database. With a tool you can course of that, but it is not wise. Why? First, processes are made to get done systematically, and if you break them, you take a risk that some of the work is not actually done (for instance, documentation for an entity or an attribute). Second, even though the tool provides all possible comparisons between different models and databases, I do not see it a full-time job for anybody trying to find differences. And if there are differences, how do you know things actually should if the processes are not followed? It is the same thing with the same data in many databases: One of the sources must be the master, and all the rest are copies of the master. If they are not the same, the master is correct. The entity is master in database design.

During the logical database design process, you can make decisions about denormalization to get better performance, but make sure each decision is wisely and documented. A typical optimization strategy in logical database design is splitting or merging tables. Splitting a table that is vertically divided into two (or more) tables. Merging tables that two (or more) tables are merged to avoid joins and that get better performance. Operations are usually done for the relational model, and they have no effect on the logical model. Dataeler supports both operations.

To split, select the table in the relational model diagram and click the Split Table icon in the relational model toolbar to start the Split Table Wizard. Enter the name for the new table (table Name), type any comments needed for the Add Comments For The New Table property, and click Next. Then select the foreign keys to be added to the new table from a list and click Next. Select other columns to be added to the new table from a list and click Finish.
