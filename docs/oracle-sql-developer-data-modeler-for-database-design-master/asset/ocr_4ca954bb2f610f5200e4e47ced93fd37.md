# Oracle SQL Developer Data Modeler for Database Design Mastery

database design is the process of producing detailed entity-relationship (ER) diagrams and data flow diagrams (DFDs) in order to produce the data language (DDL) scripts that will create the objects needed for the database. Database design consists of requirements analysis, conceptual design, logical design, physical design, and, depending on who you ask, transaction design. (This book will not discuss transaction design.) The process is incremental and iterative, meaning all these phases will be done repeatedly. The backbones of database design are logic and relational theory.

Database design is about all the data, namely, how to save the data and retrieve it. Data integrity and quality design should be high priorities when designing a database, and you must consider future needs as well. Even though an application user interface might change every five to ten years, the database behind must continue perform well for years to come.

The process of database design is changing as application development processes are getting more agile and iterative. Management demands results, so IT projects must be completed faster than ever before. Database designers often do not have time to analyze everything before starting to design, and sometimes systems are launched into production later in, without having the analysis completed. In fact, sometimes databases are created with no time spent on design and without thought to the principles of relational theory. Even with the world getting faster every day, when designing a database, you need to know the full picture of what the database is. For that, the only way to survive is to use a tool that meets all of today’s needs, helping you create databases quickly but with the “big picture” in. Without a tool, you cannot be as agile as needed.

Though Ive monitored application development processes, I want to be clear that database design is not the same as application design. The database should not be designed as a side product of application design. When saving to time and money, people think they will design only the ER model or the Unified Modeling Language (UML) model and then generate the other. Although it is good they realize need two models (one for the database and the other for the application), it is not just a question of which to choose; the perspectives are very different and so are the goals. For example, let’s look at table code files. For the application designer, it might be easier to find all the lookup information in files, but the database designer will definitely want them in tables. Why? The database person is in charge of data integrity, which cannot be controlled if some of the important data is in files somewhere out of the reach of the database.

I often hear people arguing about what is better, ER or UML. To me this question is irrelevant. ER diagrams are for designing databases, and UML is for designing user interfaces.
