
## 224 Oracle Developer Data Modeler for Database Design Mastery

> NOTE
> To avoid conflicts, remember to commit your changes after you finish working with them. Never leave Data Modeler without either committing or reverting your changes.

Here is an example of conflict: User2 creates a new table user2 and adds a new column to the table CUSTOMERS called User2Column but does not remember to commit it to version control. Meanwhile, User1 creates and adds a new table user1 and adds a new column to the table CUSTOMERS called User1 in the same design and commits the changes to version control. User2 comes back to work, opens Data Modeler, and sees their outgoing changes. Because User2 knows the process, the next thing User2 does is click Refresh Incoming and notices that there are also incoming changes. User2 can now see that the changes are shown in red, both incoming and outgoing, and knows that there is a conflict. If User2 does not realize it and tries to commit, User2 will get the error message shown earlier in Figure 9-5. The Merge user must do next is to build the wanted version of the design. Because the Merge preference is to Local, the version be built in the local working directory. User2 will start with the incoming changes. As shown earlier in Figure 9-3, User2 can see that there is a new column to be added to the local version of the design (User1Column) and the local copy has a column (User2Column) that does not exist in the version in Subversion. User2 now decide the following:

- Is the column User1Column correct, and should it be added to the local version?
- Is the column User2Column correct, or should it be removed?

If User2 wants to keep the column User1 (User1Column), User2 lets it be selected on the XML Comparator screen. If User2 does not want to keep it, User2 will disable it. If User2 still to add the column User2Column, it should be disabled on the XML Metadata Comparator screen. But if User2 does not want to add it anymore, it should be selected. After User2 has made their mind on what to do with the changes, User2 clicks Merge and saves the design. Now the local working copy has been built the way User2 wants.

User2 sees red text in Incoming Changes because there is the issue about the new table. Like with the columns, User2 must now decide what to do with the table that User1 added and what to do with the table User2 added. After making the decision, User2 clicks Merge and saves the design. If there are still some changes on the Incoming Changes tab not in red, User2 updates them to the working copy and saves the design. The complete version is in User2's working directory. User2 will commit all the changes to Subversion on the Outgoing Changes tab, and User1 will see them the next time User1 opens the design and checks Incoming Changes. There might be a real-life conflict that User1 realizes User2 removed the table User1 added earlier earlier. User1 can see the changes on the Incoming Changes and can add the table again based on their local working copy or later restore the table from previous revisions.

> TIP
> Remember that you have not committed to version control yet, you can always cancel the changes by right-clicking the outgoing change in the Pending Changes pane and selecting Revert or Revert All or by choosing Team | Revert. You can use these options when trying to solve a conflict that is complicated.

## Making Changes Based on an Older Revision

You can change your design based on an older revision. The change can be just a single change or several changes, or you can go back to the design from a certain point in time. If you want to change an element or one thing, go to that element in the Browser pane, select the two revisions you want to compare, right-click, and choose Compare or Compare As Text. Now you can see the differences between the two revisions and can decide whether something should be merged to the current revision from the older one. If you want to revert to an old revision, either permanently or temporarily, you can select Check Out or Export in Versions, as explained earlier. You might want to get the DDLs or see the logical model of a certain version of the design. If you want to unlink the working directory with version control, remove the .svn directory.

> TIP
> If you want to recover a deleted element from previous revisions of a design, you can choose Team | Design Version History.

## Understanding Branches, Changes, and Synchronizing

Some development teams like to keep a certain version of the design untouched and easily available so they save it in the tags directory (remember to document that in Comment), and some teams want to have two separate development tracks (trunk and branch) that can be merged afterward. A separate track from the main track will be saved in the branch directory. As explained earlier in this chapter, you can create a new branch or tag by right-clicking the source location in the Versions browser and selecting Branch/Tag, depending on whether you save it to the tag or branch directory, this gives the meaning of a version being a tag or a branch. The other possibility is to select the source location in the Versions browser and then choose Team | Branch/Tag.

If you want to merge a branch to the main line design totally or partially, there are many ways to do it. You can use the Merge Design functionality found in the Teams menu to compare and merge the changes from the version in Subversion to your local working copy, or can you use the compare/merge functionalities to merge two local working versions of the designs and then commit the changes.

If you want to merge a branch to the main line design follow these steps:

1. Get the incoming changes, and if there is not available, select Update Working Copy.
2. Commit all outgoing changes and save the design.
3. Use the branch functionality.
4. Use the Merge Design.
5. In the branch pane, select the branch.
6. In the Action screen, right-click and choose Merge.
7. In the XML Metadata Comparator, select the changes.
8. Save the design.

Data Modeler sometimes causes conflicts when merging designs. As mentioned earlier, Data Modeler has directories for each type (table, entity, view), but the directory is created only when the first of kind element is created, and therefore a conflict may arise. For example, let's assume there is the trunk and branch, and in both a new element has been created for the first time let's say it's a view. So, somebody creates a view for the branch, and somebody else creates another view for the trunk. Now the directory for views has been created in both versions for the first time. You try to merge the designs and get an error saying there is a conflict. That is correct; there is a conflict: A directory for views has been created in both versions, and you must decide which one is correct. What you need to do now is to remove the directory from the local target design by right-clicking in Action screen below the Revision screen in Merge Design and deleting Local Folder. If there are outgoing changes, commit them and update the working copy. Now there should be no more conflict, and the merge can be completed. Everything is OK you get back what was in the local directory you deleted. You can do this by choosing Team | Design Version History. Select and then restore the view file that was in the removed directory. After that you should have a complete merge to the trunk.

Every element-type directory includes a subdirectory called seg_0, and if there are more than 70 elements of the same type, a new subdirectory of the same level is created (seg_1). Other directory can have only 70 files. This is for performance reasons. Data Modeler creates the new subdirectory when needed and removes it when a Save As is performed if there is no need for that subdirectory anymore.
