There are three ways to implement the inheritance in a relational model: specialization (table) for each entity), generalization (single table), or neither of those (table child). There is no right way to model an inheritance; it always depends on what the requirements are.

Specialization of an entity that will be divided into subtypes. For instance, an entity Customer may be divided into Person and Customer. All common attributes will be in the Customer entity. Person and Customer will have only the specific attributes for those entities. This is similar to what you saw in the arc solution in Figure 4-16. In Data Modeler this is called Table For Each, (see Figure 4-20) to Table For Entity, and you can select it by setting the Subtype Generation option in the Entity Properties dialog (see Table For Each Entity). When Table For Entity is selected, all entities in the current subtype will be selected for engineering.

There are several questions you should ask to be sure that the solution is the right one. Can a Person be a company? Usually this is not a good solution in the sense of performance because probably need to join these tables quite often.

Generalization of an entity that will be created for a set of entities. It is possible that a subtype has attributes that are not suitable for all entities generalized under this supertype. Let you have entities called Customer, Company, and Person. You can generalize all of these under a supertype called Customer. This supertype now generalizes the subtypes. The subtype inherits the attributes from the supertype and possibly has attributes of its own. In Data Modeler, this is called Single Table, and you can select it by setting the Subtype Generation option in the Entity Settings dialog to Single Table. In Data Modeler, the Engineer To for this property will be set, and it will be cleared for all subtypes in the current subtype.

In reality, you will probably need a new attribute to describe which type of Customer each customer is, such as a CustomerType attribute, because there is probably a requirement for that. In Data Modeler, you will use a discriminator column

for that purpose. If you select Generate Discriminator, a discriminator column will be generated for your table automatically. In Use Attribute, you can define which existing attribute will be used as a discriminator; in this case, that would be CustomerType. If you want to define a name for the column, use the Name property. This property defines the name of the generated discriminator column. If you do not specify a name, the template is used. You can define the discriminator value for each subtype in the Discriminating Value property. For instance, for Person, the discriminator value could be P and for Company it could be C. If you do not define a value, the entity name or name is used. If you want the subtypes to be complete, select Complete Subtypes. This property has impact on generated arcs and the list of possible values for the discriminator column. If the list of subtypes is not complete, then optional arcs are generated, and the value for the supertype entity is also included in the permitted list of values for the discriminator column. The problem with generalization is that only the common attributes can be defined, not null. So, mandatory attributes in subtype entities become optional columns, and an independence dependency constraint is generated in addition to the list of value constraints for the discriminator column. Generalization is probably the most popular solution, and it usually works if most of the attributes are common and the business rules are similar to all the subtype entities.

# Subviews

Subviews are diagrams created to represent different areas and to make a big diagram more readable. Any changes made to elements in a subview will be automatically made to the logical diagram since the elements are the same. You can create as many subviews as you want by selecting SubView from the Browser pane, right-click, and choosing New SubView. Or right-click the canvas and choose Diagram | Create SubView. After right-clicking and selecting Diagram, you can also delete subviews (Delete Sub). Subviews also have properties, and it is wise to name all the additional subviews to make finding the correct one easier. A subview can be named via its properties.

All new entities are automatically added to the logical diagram. Only changes that are made to an object that already exists in other subviews will be shown there. Relationships between entities that have been selected on a subview will be; if not all the entities needed have been selected, the relationship will not be shown. You can add new entities and relationships and make any changes in any of the subviews, and all the changes will be made automatically in all the relevant subviews. All the objects are in Data Modeler once, and subviews are just an interface to them. But there is one exception: you can delete the whole object either from your design or from one subview.
