In addition to supporting alternative credential providers, LogonUI can load additional network provider DLLs that need to perform secondary authentication. This capability allows multiple network providers to gather identification and authentication information all at once during normal logon. A user logging on to a Windows system might simultaneously be authenticated on a Linux server. A user would then be able to access resources of the UNIX server from the Windows machine without requiring additional authentication. Such a capability is known as one of single sign-on.

# Winlogon initialization

During system initialization, before any user applications are active, Winlogon performs the following steps to ensure it controls the workstation once the system is ready for user interaction:

- 1. It creates and opens an interactive window station (for example, \Sessions\WindowsStation in the object manager to represent the keyboard, mouse, and monitor. Winlogon creates a security descriptor for the station that has one and only one ACE containing only the system SID. This unique security descriptor ensures that no other process can access the workstation unless explicitly allowed by Winlogon.

- 2. It creates and opens two desktops: an application desktop (\Sessions\WindowsWinSta0\Default, also known as the interactive desktop) and desktop (\Sessions\WindowsWinSta0\Winlogon, also known as the Secure Desktop). The security on the Windows desktop is created so that only Winlogon can access that desktop. The other desktops also allow Winlogon users to access it. This arrangement means any time the Winlogon desktop is active, no other process has access to any active code or data associated with the desktop. Windows uses this feature to protect the secure operations that involve passwords and locking and unlocking the desktop.

- 3. Before anyone logs on to a computer, pressing the SAS sequence (by default, Ctrl+Alt+Del) switches the desktop from Default to Winlogon and launches LogonUI.(This explains why all the windows on your interactive desktop seem to disappear when you press Ctrl+Alt+Del, and return when you dismiss the Windows Security dialog box.) Then, the SAS brings up a Secure Desktop controlled by Winlogon.

- 4. It establishes an ALPC connection with Lsas. This connection will be used for exchanging information during login, logout, and password operations, and is made by calling LsaLoginProcess.

- 5. It registers the Winlogon RPC message server, which listens for SAS, logoff, and workstation lock notifications from Win32k. This measure prevents Trojan horse programs from gaining control of the screen when SAS is entered.

> Note The Wininit performs steps similar to 1 and 2 to allow legacy interactive services running on session 0 to display windows, but it does not perform any other steps because session 0 is not available for user login.

# How SAS is implemented

The SAS is secure because no application can intercept the Ctrl+Alt+Del keystroke combination or prevent Winlogon from receiving it. Win32k.sys reserves the Ctrl+Alt+Del key combination so that whenever the Windows input system (implemented in the raw input thread in Win32k) sees the combination, it sends an RPC message to Logon's message server, which listens for notifications. The keystrokes mapped to a registered key are not sent to any process other than the one it registered, and only the thread that registered a key can unregister it, so a Trojan horse application cannot dem Logon's ownership of the SAS.

A function, SetWindowsHookEx, enables an application to install a hook procedure every time a keystroke is pressed, even when hot keys are pressed, and allows the hook to squash keystrokes. However, the Windows hot key processing code contains a special case for Ctrl+Alt+Del that disables the keystroke sequence cannot be intercepted. In addition, if the interactive desktop is locked, only keys owned by Winlogon are processed.

Once the Winlogon desktop is created during initialization, it is the active desktop. When the Winlogon desktop is active, it is always locked. Winlogon unlocks the desktop only to switch to the application desktop or the screen-saver desktop. (Only the Winlogon process can lock or unlock a desktop.)

# User logon steps

Logon begins when a user presses the SAS (Ctrl+Alt+Del). After the SAS is pressed, Winlogon starts LogonUI, which calls the credential providers to obtain a user name and password. Winlogon also creates a unique local SID for this user, which it assigns to this instance of the desktop (keyboard, screen, and mouse). Winlogon passes this SID to Lsa as part of the LogonUser call. If the user is successfully logged on, this SID will be included in the process token—a step that protects access to the desktop. For example, another logon to the same account but on a different system will be unable to write to the first machine's desktop because this second logon is not in the first machine's desktop token.

When the user and password have been entered, Winlogon returns a handle to the package by calling the Lsa function LsaLookupAuthenticationPackage. Authentication packages are listed in the registry under HKLM\SYSTEM\CurrentControlSet\Control\Lsa. Winlogon passes logon information to the authentication package via LsaLogonUser. Once a package activates, Winlogon continues the logon process for that. If none of the authentication packages indicates a successful logon, the process is aborted.

Winlogon uses two standard authentication packages for interactive username/password-based logons:

- MSV1_0: The authentication package on a stand-alone Windows system is MSV1_0 (.dll), an authentication package that implements LM Manager 2 protocol. Lsass uses MSV1_0 on domain-member computers to authenticate to pre–Windows 2000 domains and computers that cannot locate a controller for authentication. (Computers that are disconnected from the network fall into this category.)

- Kerberos: The Kerberos authentication package, Kerberos.dll, is used on computers that are members of Windows domains. The Windows Kerberos package, with the cooperation of Kerberos services running on a controller, supports the Kerberos protocol. This protocol is based on Internet RFC 1510. (See the Internet Engineering Force [IETF] website at http://www.ietf.org for detailed information on the Kerberos standard.)

# MSV1_0

MSV1_0 the authentication package takes the user name and a hashed version of the password and sends a request to the local SAM to retrieve the account information, which includes the hashed password, the groups to which the user belongs, and any account restrictions. MSV1_0 first checks the account restrictions, such as hours or time of accesses allowed. If the user can't log because of the restrictions in the SAM database, the logon call fails and MSV1_0 returns a failure status to the LSA.

MSV1_0 then compares the hashed password and user name to that from the SAM. In the case of a cached domain logon, MSV1_0 accesses the cached information by using Lass functions that store and retrieve from the LSA database (SECURITY hive of registry). If the information matches, MSV1_0 generates a GUID for the logon session and creates the logon session by calling Lass, associating this unique identifier with the session and passing the information needed to ultimately create an access token for the user. (Recall that an access token includes the user's SID, group SIDs, and assigned privileges.)
