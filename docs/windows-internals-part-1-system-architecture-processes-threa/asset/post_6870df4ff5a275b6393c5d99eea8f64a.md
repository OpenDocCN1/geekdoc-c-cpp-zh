
- The token will contain four security attributes (see the section on attribute-based access control earlier in this chapter) that identify this token as associated with a UWP packaged application. These attributes are added by the DcomLaunch service as indicated earlier, which is responsible for the activation of UWP applications. They are as follows:

- WIN://PKG identifies this token as belonging to a UWP packaged application. It contains an integer value with the application's origin as well as some flags. See Table 7-13 and Table 7-14 for these values.

- WIN://SYSAPPID This contains the application identifiers (called package monickers or string names) as an array of Unicode strings.

- WIN://PKHOSTID identifies the UWP host ID for packages that have an explicit host integer value.

- WIN://BGKO this is only used for background hosts (such as the generic background host BackgroundTask.exe) that can store packaged UWP services running COM providers. The attribute's name stands for background and contains an integer value that stores its explicit host ID.

The TOKEN_LOWBOX (0x4000) flag will be set in the token's flags member, which can be queried with various Windows and kernel APIs (such as GetTokenInformation). This allows components to identify and operate differently under the presence of an AppContainer token.

> Note A second type of AppContainer exists: a child AppContainer. This (or parent AppContainer) wishes to create its own nested AppContainer to further lock down the security of the application. Instead of eight RIDs, a child AppContainer has four additional RIDs (the first eight match the parent's) to uniquely identify it.

## TABLE 7-13 Package origins

| Origin | Meaning |
|---|---|
| Unknown (0) | The package origin is unknown. |
| Unsigned (1) | The package is unassigned. |
| Inbox (2) | The package is associated with a built-in (in) Windows application. |
| Store (3) | The package is associated with a UWP application downloaded from the store. This origin is validated by checking if the DACL of the file with the main UWP application's executable contains a trust ACE. |
| Developer Unsigned (4) | The package is associated with an unsigned developer key. |
| Developer Signed (5) | The package is associated with a signed developer key. |
| Line-of-Business (6) | The package is associated with a side-loaded line-of-business (LOB) application. |

| Flag | Meaning |
|---|---|

## EXPERIMENT: Viewing UWP process information

There are several ways to look at UWP processes, some more obvious than others. Process Explorer can highlight processes that use the Windows Runtime in color (cyan by default). To see this in action, open Process Explorer, open the **Options** menu, and **Configure Colors**. Make sure the **Immersive Processes** check box is selected.

![](img/ff0e6a9d867a3a6e9527eb1d946810fc_705_0.png)

Immersive process is the original term used to describe WinRT (now UWP) apps in Windows 8 (They were mostly full screen, and therefore "immersive.") This distinction is available by calling the IsImmersiveProcess API.

Run Calc.exe and switch to Process Explorer. You should see several processes highlighted in cyan, including Calculator.exe. Minimize the Calculator app and notice that the highlight has turned gray. This is because Calculator has been suspended. Restore Calculator's window, and it's back to cyan.

You should have similar experiences with other apps—for example, Cortana (Search.exe). Click or tap the Cortana icon on the taskbar and close it. You should see the gray to cyan and back to gray transition. Or, click or tap the Start button. ShellExperienceHost.exe highlights in a similar fashion.

The presence of some cyan-highlighted processes might surprise you, such as TaskMgr.exe, RuntimeBroker.exe. These are not real apps, but use Windows APIs, and so classified as immersive. (The role of RuntimeBroker will be discussed shortly.)

Finally, make sure the Integrity column is visible in Process Explorer and search by column. You will find processes as Calculator.exe and SearchUI.exe with AppContainer level. Notice that Explorer and TaskMgr are not there, clearly showing they are not UWP processes, and so under different rules.
