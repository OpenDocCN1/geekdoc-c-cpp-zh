You can also specify other device drivers to be mapped with large pages by adding a multicast registry value LargePageDrivers to the key HKL\SYSTEM\CurrentControlSet\Control\SessionManager\Memory Management and specifying the names of the drivers as separately null-terminated strings.

Attempts to allocate large pages may fail after the operating system has been running for an extended period because the physical memory for each large page must occupy a significant number (refer to Table 5-1) of physically contiguous pages. This extent of physical pages must furthermore begin on a large page boundary. For example, physical pages 0–511 could be used as a large page on an x64 system, pages 512–1023, could not. Free physical memory thus becomes fragmented as the system runs. This is not a problem for allocations with small pages but can cause large pages to fail.

The memory is also non-pageable because the file system does not support large pages. Because the memory is non-pageable, the caller is required to have the SeLockMemoryPrivilege be able to allocate large pages. The allocated memory is not considered part of the process working set (described in the "Working sets" later in this chapter); nor large page allocations subject to job-wide limits on virtual memory usage.

On Windows 1600 x164 and Server 2016 systems, large pages may also be mapped with huge pages, where 1 GB is in size. This is done automatically if the allocation requested is larger than 1 GB, but it does not have to be a multiple of 1 GB. For example, an allocation of 1040 MB would result in one huge page (1024 MB) plus 8 "normal" large pages (16 MB divided by 2 MB).

There is an unfortunate effect of large pages. Each page (whether large, huge, or small) must be mapped with a single protection that applies to the entire entity. If a large page contains, for example, both read-only code and read/write data, the page must be marked as read/write, meaning that the code could be writable. As a result, device drivers or other kernel-mode code could, either maliciously or due to a bug, modify what is supposed to be read-only operating system or driver code without causing a memory access violation. If small pages are used to map the operating system's kernel-mode code, the read-only portions of Ntoskrnl.exe and Hal.dll can be mapped as read-only pages. Using small pages reduces efficiency but if a driver (or other kernel-mode code) attempts to modify only one part of the operating system, the system will crash immediately with the information pointing at the offending instruction in the driver. If it were allowed to occur, the system would likely crash (a harder-to-diagnose way) when other component tried to use the corrupted data.

If you are experiencing kernel corruptions, enable Driver Verifier (described in Chapter 6, "I/O system"), which will disable the use of large pages.

> Note The term large page used in this and later chapters refers to a small page unless otherwise indicated or apparent by context.
