## Logical processors per group

Generally, Windows assigns 64 processors per group. But you can also customize this configuration by using different options such as the /GROUPSIZE option, which is configured through the groupsize BCD element. By specifying a number that is a power of 2, you can force cores to contain fewer processors than normal for purposes such as testing group awareness in the system. For example, with system logical processors can be made to appear as one, two, or four groups. To force the issue, /FORCEGROUPWARE option (bcd element groupaware) causes the kernel to avoid group 0 whenever possible, assigning the highest number available in actions such as thread and DPC affinity selection and process group assignment. You should avoid setting group size of 1 because this will force all applications to behave as if they're running on a uniprocessor machine. This means the kernel sets the affinity mask of a given process to only one core unless the application requests otherwise (which applications will not)

Other than significant driver and application compatibility problems—which are designed to identify and root out, when went by developers—these options have an even greater impact on the machine: They force NUMA behav to span multiple groups, as shown in the assignment algorithms. If the kernel is creating artificially small groups, those groups must each have their own NUMA node. For example, on a quad-core processor with a group size of 2, this will create two groups, and two NUMA nodes, which will be subnodes of the main node. This will affect scheduling and memory-management policies in the same way as true NUMA system, which can be useful for testing.

## Scheduler scalability

On a multiprocessor system, one processor might need to modify another processor's per-CPU scheduling structures—for example, inserting a thread that would need to run on another processor. For this reason, you synchronize these structures using a per-PRCB spinlock, which is held at DISPATCH_LEVEL. Then selection can occur while locking any individual processor's PRCB. If needed, one more processor's PRCB can also be locked, as in scenarios of thread stealing (described later). Thread context switching is also synchronized using a finer-grained per-thread spinlock.

There is also a per-CPU list of threads in the deferred ready state (DeferredLinkedList). This represents threads that are ready to run but have not been read for execution; the actual operation has deferred to a more appropriate time. Because each processor manipulates its own per-processor deferred ready list, this list is not synchronized by the PRCB spinlock. The deferred ready list is processed by KiDeferredReadyList after a function has already done modifications to process or thread affinity (including due to priority boosting), or quantum values.

This function calls KiDeferredReadyThread for each thread on list, which performs the algorithm shown later in this chapter in the “Processor selection” section. This could cause the thread to not run immediately; to be put on the ready list of the processor; or, if the processor is unavailable, to potentially put on a different processor's deferred ready list, in a standby state or immediately executed. This property is used by the core parking engine when parking a core: All threads are put into the deferred ready list, and it is then processed. Because KiDeferredReadyThread skips parked cores it causes all of this processor's threads to wind up on other processors.
