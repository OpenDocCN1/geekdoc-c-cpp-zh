Several fields are for several PFN types, but others are specific to a given type of PFN. The following fields appear in more than one PFN type:

- **Address**: This is the virtual address of the PTE that points to the page. Also, since PTE addresses will always be aligned on a 4-byte boundary (8 bytes by 64-bit systems), the lower-order bits are used as a locking mechanism to serialize access to the PFN entry.
- **Reference count**: This is the number of references to this page. The reference count is increased when a page is added to a working set and/or when the page is locked in memory for I/O (for a device driver). The reference count is decremented when the share count becomes 0 or when pages are unlocked from memory. When the share count becomes 0, the page is no longer owned by a working set. Then, if the reference count is zero, the PFN database entry that describes the page is updated to add to the page, standby, or modified.
- **Type**: This is the type of page represented by this PFN. (Types include active/valid, standby, modified-no-write, free, zeroed, bad, and transition).
- **Flags**: The information contained in flags is shown in Table 5–20.
- **Priority**: This is the priority associated with this PFN, which will determine on standby list it will be placed.
- **Original PTE contents**: All PFN database entries contain the contents of the PTE pointed to the page (which could be a prototype PTE). Saving the contents of the PTE allows it to be restored when the physical page is no longer resident. PFN entries for allocations exceptions; store the AWE reference count in this field instead.
- **PFN of PTE**: This is the physical page number of the page table containing the PTE that points to this page.
- **Color**: Besides linked together on a list, PFN database entries use an additional field to link physical pages by "color," which is the page's Numa number.
- **PFN**: A second field is used to encode additional information on the PTE. These flags are described in Table 5-21.

The remaining fields are specific to the type of PFN. The first PFN in Figure 5-39 represents a page that is active and part of working set. The share count field represents the number of PTEs that refer to this page. (Pages marked read-only, copy-on-write, or shared/read/write can be shared by multiple processes.) For page table fields, this is the number of validation and PTEs in the page table. As long as the share count is greater than 0, the page is not eligible for removal from memory.

The working set index field is an index in the process working set list (or the system or working set list, zero or not in any working set) the virtual address that maps this physical page resides. If the page is a private page, the working set index field refers directly to the entry in the working set list because the page is mapped only on a single virtual address. In the case of a shared page, the working set index is a hint to be correct only for the first process that made the page valid. (Other processes will try to use the same index where). The process that initializes this field is guaranteed to refer to the proper index and doesn't need to adding a working set list hash entry This guarantee reduces the size of the working set hash tree and makes searches faster for these.

The second PFN in Figure 5-39 is for either the standby or the modified list. In this case, the forward and backward link fields link the elements together with the list. This linking allows pages to be easily manipulated to satisfy page faults. When a page is one of lists, the count is defined by 0 (no working set is using the page) and therefore can be overlaid with the backward link. The reference count is 0 if the page is one of the ones. If it is non-zero (because an I/O could be in progress for the page—for example, when the page is being written to disk), it is first removed from the list.

The third PFN in Figure 5-39 is for a page that belongs to a kernel stack. As mentioned earlier, kernels in Windows are dynamically allocated, expanded, and freed whenever a callback to user mode is performed and/or, when a driver performs a callback and requests stack expansion. These PFNs, the memory manager must keep track of the thread actually associated with the kernel stack, or if it is free it keeps a link to the next free-aside stack.

The fourth PFN in Figure 5-39 is for a page that has an I/O in progress (for example, a page read). While the I/O is in progress, the first field points to an event that will be signaled by the I/O completes. If an in-page error occurs, this field contains the Windows status code representing the I/O error. This PFN type is used to resolve collided page faults.
