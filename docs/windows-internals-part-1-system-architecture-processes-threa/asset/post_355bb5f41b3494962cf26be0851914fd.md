
![](img/ff0e6a9d867a3a6e9527eb1d946810fc_394_0.png)

FIGURE 5-19 Accessing the TLB.

Frequently used virtual addresses are likely to have entries in the TLB, which provides extremely fast virtual-to-physical address translation and, therefore, fast memory access. If a virtual address is not in the TLB, it might still be slower, but multiple memory accesses are needed to find it, which makes the time slightly slower. If a virtual page has been paged out of memory or if the memory manager changes the PTE, the memory manager is required to explicitly invalidate the TLB entry. If a process accesses it again, a page fault occurs, and the memory manager brings the page back into memory (if needed) and re-creates its PTE (which then results in an entry for it in the TLB).

## EXPERIMENT: Translating addresses

To clarify how translation works, this experiment shows an example of translating a virtual address on an x86 PTE system using the available tools in the kernel debugger to examine the PDPT, page directories, page tables, and PTEs. In this example, you will work with a process that has virtual address 0x3166004, currently mapped to a valid physical address. In later examples, you'll see how to follow address translation for invalid addresses with the kernel debugger.

First convert 0x3166004 to binary and break it into the three fields used to translate an address. In binary, 0x3166004 is 11.0001.0110.0110.0000.0100. Breaking it into the component fields yields the following:

| 31 30 29 | | 21 20 | | 12 11 | | 0 |
|---|---|---|---|---|---|---|
| 00 | | 00.0111.000 | 1.0111.0110 | 0000.0100 | | |
| Page Directory Pointer Index (0) | Page Directory Index (24) | Page Table Index (0x166 or 358) | Byte Offset (4) | | |

To start the translation process, the CPU needs the physical address of the process's PDPT. This is found in the CR3 register where a thread is running. You can display this address by looking at the DirBase field in the output of the !process, as shown here:

```
1kd> !process -1 0
PROCESS 99a3040 SessionId:2 Cid:1690 Peb:03159000 ParentCid:0920
 DirBase:0x0124800 ObjectTable:b3b386c0 HandleCount:<Data Not Accessible>
 Image:wndbg.exe
```

The DirBase field shows that the PDPT is at physical address 0x0124800. As shown in the preceding illustration, the PDPT index field in the virtual address is 0. The PDPT entry contains the physical address of the relevant page directory is the first entry in the PDPT, at physical address 0x0124800.

The kernel debugger !pte command displays the PDE and the PTE that describe a virtual address, as shown here:

```
1kd> !pte 31660004
 VA 03166004
 PDE at 0xC060C060 PTE at 0xC018B30
 contains 000000056238867 contains 800000005de61867
 pfn 56238 --- pfn 5de61 ---UU-V
```

The debugger does not show the PDPT, but it is easy to display its physical address:

```
1kd> !dq 0x0124800 L.4
 # 0124800000000053c88901 0000000053c89801
 # 0124810000000053c8a801 0000000053c8801
```

Here we use the debugger !dq. This is similar to the dq command (display as quad) but lets us examine memory by physical rather than virtual. Because the PDPT is only four entries long, we use L 4 to keep the output uncluttered. As illustrated, the PDPT index (the most significant bits) you want is the first displayed quad. PDPT entries have format equal to 0, similar to PDEs and PTEs, so you can see that this one contains a PFN of 0x53c880 (always page-aligned), for physical address of 0x53c880. That is the physical address of the page directory. The !pte output shows the PDE address 0xC060C00 at virtual address, not physical. In x86 systems, the first page directory starts at virtual address 0xC00000. In this case, the PDE address is 0xC—that is, 8 (size of an entry) times 24 to the page directory. Therefore, the page directory index of the virtual address is 24. That means you're looking at the 25th PTE in the page directory. The PDE provides the PFN of the needed entry. In this example, the PFN is 0x5623800, so the page table starts at physical address 0x5623800. Then the MMU will add the page table index (0x166) from the virtual address multiplied by 8 (the size of a PTE in bytes). The resulting address of the PTE is 0x56238B30. The debugger shows that this PTE is at virtual address 0xC018B30. Notice that the byte offset (0xB30) is the same as that from the physical address, as in translation. Because the memory manager maps page tables starting at 0xC0000000, adding 0xB30 to 0xC018000 (the 0x18 as you've seen) the virtual address shown in the kernel output: 0xC018B30. The debugger shows that the PFN field of the PTE is 0x5DE61. Finally, you can consider the byte offset from the original address. Now, the MMU concatenates the byte offset by the PFN from the PTE, giving a physical address of 0x5DE6104. This is the physical address that corresponds to the original virtual address of 0x3166004. The bits from the PTE are interpreted to the right of the PFN number. The PTE that describes the page has flags of UW-V. Here, A stands for accessed (the page has been read), U for user-mode accessible (as opposed to kernel-mode accessible), W for writable (rather than just read), and V for valid (the PTE represents a valid page in physical memory).

To confirm the calculation of the physical address, look at the memory in question via both its virtual and its physical address. First, using the debugger's dd (display words) command on the virtual address, you see the following:

```
1kd> dd 31660004 L 10
03166004 00000034 00003020 0000004e
03166014 00000000 00020020 000a00a0 00000014
```

And with the dd 5DE6104 L 10:

```
1kd> dd 5DE6104 L 10
#5DE61004 00000006 00003020 0000004e
#5DE61014 00000000 00020020 000a00a0 00000014
```

You could similarly compare the displays from the virtual and physical addresses of the PTE and PDE.

## x64 virtual address translation

Address translation on x64 is similar to x86, with a fourth level. Each process has a top-level extended page called the page map level 4 table that contains the physical locations of 512 third-level structures, called page directory pointers. The parent directory is analogous to the x86 PAE PDPT, but there are 512 of them instead of just one, and each page directory is an entire page containing 512 entries instead of four. Like the PDPT, each parent directory enters the locations of second-level page directories, each of in turn contains the locations of the individual page tables. Finally, the page tables, each of which contains 512 page table entries, contain the physical locations of the pages in memory. All the "physical locations" in the preceding description are stored in these structures as PFNs.

Current implementations of the x64 architecture limit virtual addresses to 48 bits. The components that make up this 48-bit virtual address and the connection between the components for translation purposes are shown in Figure 5-20, and the format of an x64 hardware PTE is shown in Figure 5-21.

## ARM virtual address translation

Virtual address translation on ARM 32-bit processors uses a single page directory with 1024 entries, each 32 bits in size. The translation structures are shown in Figure 5-22.

![](img/ff0e6a9d867a3a6e9527eb1d946810fc_398_0.png)

FIGURE 5-22 ARM virtual translation structures.

Every process has a single page directory, with its physical address stored in the TTBR register (similar to the CR3 x86/x64 register). The 10 most significant bits of the virtual address select a PTE that points to one of 1,024 page tables. A specific PTE is selected by the next 10 bits of the virtual address. Each valid PTE points to the start of a page in physical memory, where the offset is given by the lower 12 bits of the address (just as in the x86 and x64 cases). The scheme in Figure 5-2 suggests that the addressable physical memory is 4 GB when each PTE is smaller (32 bits) than the x86/x64 case (64 bits), and indeed only 20 bits are used for the PFN. ARM processors do support PAE (similar to x86), but Windows does not use this functionality. Future Windows versions may support the ARM 64-bit architecture, which will alleviate the physical address limitations as well as dramatically increase the virtual address space for processes and the system.
