## Trustlet identity

Trustlets have multiple forms of identity that they can use on the system:

- **Trustlet identifier or Trustlet ID** This is a hard-coded index in the Trustlet’s policy metadata, which must also be used in the Trustlet process-creation attributes. It ensures that the system knows there are only a handful of Trustlets, and that the callers are calling the expected one.
- **Trustlet instance** This is a cryptographically secure 16-byte number generated by the Secure Kernel. Without the use of a collaboration ID, the Trustlet instance is what’s used to guarantee that Secure Storage APIs will only allow this one of the Trustlet to get/put data into its storage blob.
- **Collaboration ID** This is used when a Trustlet would like to allow other Trustlets with the same ID, or other instances of the same Trustlet, to share access to the same Secure Storage blob. When this ID is present, the instance ID of the Trustlet will be ignored when calling the Get or Put APIs.
- **Security version (SVN)** This is used for Trustlets that require strong cryptographic proof of provenance of signed or encrypted data. It is used when encrypting AES256/GCM data by Credential and Key Guard, and also used by the Crypt Report service.
- **Scenario ID** This is used for Trustlets that create name (identity-based) secure kernel objects, such as secure sections. This GUID validates that the Trustlet is creating such objects as part of a predetermined scenario, by tagging them in the namespace with this GUID. As such, other Trustlets wishing to open the same named objects would thus to have the same scenario ID. Note that more than one scenario ID can actually be present, but no Trustlets currently use more than one.

## Isolated user-mode services

The benefits of running as a Trustlet not include protection from attacks from the normal (VTL 0) world, but also access to privileged and protected secure system calls that are only offered by the Secure Kernel to Trustlets. These include the following:

- **Secure Devices (IumCreateSecureDevice, IumDmaMapMemory, IumGetDmaEnabler, IumMapSecureIo, IumProtectSecureIo, IumQuerySecureDeviceInformation, IumOpMapSecureIo, IumUpdateSecureDeviceState) These provide access to ACPI and/or PCI devices, which cannot be accessed from VTL 0 and are exclusively owned by the Secure Kernel (and ancillary Secure HAL and PCI services). Trustlets with the relevant capabilities (the "Trustlet policy metadata" section earlier in this chapter) can map the registers of such a device in VTL 1 IUM, as well as potentially perform Direct Memory Access (DMA) transfers. Additionally, Trustlets can serve as user-mode drivers for hardware by using the Secure Device Framework (SDF) in SDFHost.dll. This functionality enables Secure for Biometrics for Windows Hello, such as Secure USB Smartcard (over PCI) or Webcam/Finger Sensors (over ACPI).

- **Secure Sections (IumCreateSecureSection, IumFlushSecureSection, IumGetExposedSection, IumOpenSecureSection) These provide the ability to share physical pages with a VTL 0 driver (which would use Vtl1CreateSecureSection) through exposed secure sections, as well as share data within VTL 1 named secure sections (leveraging the identity-based mechanism described earlier in the "Trustlet identity" section) with Trustlets or other instances of the same Trustlet. Trustlets require the Secure capability described in the "Trustlet policy metadata" section to use these features.

- **Mailboxes (IumPostMailbox) This enables a Trustlet to share out slots of up to 4 KB of data with a component in the normal (VTL 0) kernel, which can call via Retrieve identifier and secret mailbox key. For example, Vys in VTL 0 uses this to retrieve various secrets used by the vTPM feature from the Vmsp.exe kernel.

- **Identity Keys (IumGetId) This allows a Trustlet to obtain either a unique identifying decryption key or signing key. This key material is unique to the machine and can be obtained only from a Trustlet. It is an essential part of the Credential Guard feature to uniquely authenticate the machine and credentials coming from IUM.

- **Cryptographic Services (IumCrypto) This allows a Trustlet to encrypt and decrypt data with a local/or post-boot session generated by the Secure Kernel that is only available to IUM, to obtain a TPM binding handle, to get the FIPS mode of the Secure Kernel, and to obtain a random number generator (RNG) not generated by the Secure Kernel for IUM. It also enables a Trustlet to generate an ID-signed, SHA-2 hashed, and timestamped report with the identity and SVN of the Trustlet, a dump of its policy metadata, whether or not it was ever attached to a debugger, and any other Trustlet-controlled data requested. This can be used as a sort of TPM-like measurement of the Trustlet to prove it was not tampered with.

- **Secure Storage (IUMSecureStorageGet, IUMSecureStoragePut) allows Trustlets that have the Secure Storage capability (described earlier in the "Trustlet policy metadata" section) to store arbitrarily sized blobs and to retrieve them, either based on their unique Trustlet instance or by sharing the same collaboration ID as another Trustlet.**

## Trustlet-accessible system calls

The Secure Kernel attempts to minimize its attack surface and exposure, it only provides a subset (less than 50) of the hundreds of system calls that a normal (VTL 0) application can use. These system calls are the strict minimum necessary for compatibility with the system DLLs that Trustlets use (refer to the section "Trustlet structure to see these), as well as the specific services required to support the RPC runtime (Rpcrt4.dll) and ETW tracing.

- Worker Factory and Thread APIs support this Thread Pool API (used by RPC) and TLS Slots used by the Loader.
- Process Information API supports this TLS Slots and Thread Stack Allocation.
- Event, Semaphore, Wait, and Completion APIs support Thread Pool and Synchronization.
- Advanced Local Procedure Call (ALPC) APIs support these Local RPC over the ncrpc transport.
- System Information API supports reading Secure Boot information, and NUMA system information for Kernel32.dll and Thread scaling, performance, and subsets of time information.
- Token API provides minimal support for RPC impersonation.
- Virtual Memory Allocation APIs support these allocations by the User-Mode Heap Manager.
- Section APIs support the Loader (for DLL Images) as well as the Secure Section functionality (once created/exposedthrough secure system calls shown earlier).
- Trace Control API supports this ETW.
- Exception and Continue API supports this Structured Exception Handling (SEH).
