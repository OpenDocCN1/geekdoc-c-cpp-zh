## DLL name resolution and redirection

Name resolution is the process by which the system converts the name of a PE-format binary to a physical file in locations where the caller has not specified or cannot specify a unique identity. Because the locations of various directories (the application directory, the system directory, and so on) cannot be hardcoded at link time, this is the resolution of all binary dependencies as well as LoadLibrary functions where the caller does not specify a full path.

When resolving binary dependencies, the basic Windows application model locates files in a search path—a list of locations that are searched sequentially for a file with a matching name—although various system components override the search path mechanism in order to extend the default application model. The notion of a search path is holdover from the era of the command line, when an application's current directory was a meaningful notion; this is somewhat anachronistic for modern GUI applications.

However, the placement of the current directory in this ordering load operations on binaries to be overridden by placing multiple binaries with the same base name in the application's current directory, a technique known as binary planting. To prevent security risks associated with this behavior, a feature known as safe search mode was added to the path computation and is enabled by all processes. Under safe mode, the current directory is moved behind the three system directories, resulting in the following path order:

- 1. The directory from which the application was launched
- 2. The native windows system directory (for example, C:\Windows\System32)
- 3. The 16-bit Windows system directory (for example, C:\Windows\System)
- 4. The Windows directory (for example, C:\Windows)
- 5. The current directory at application launch time
- 6. Any directories specified by the %PATH% environment variable

The DLL search path is recomputed for each subsequent DLL operation. The algorithm used to compute the search path is the same as the one used to compute the default search path, but the application can change specific path elements by using the %PATH% variable or changing the current directory using the SetCurrentDirectory API, or using the SetDefaultDirectory to specify a directory for the process. When a DLL is specified, the directory replaces the current directory in the search path and the loader ignores the safe DLL search mode for the process.

Callers can also modify the default DLL search operations by using the LOAD_ALTERED_SEARCH_PATH flag to the LoadLibraryEx API. When this flag is enabled and the DLL name specified to the API uses a full path, the path containing the DLL file is used in place of the application directory when computing the search path for the operation. Note that if the path is a relative path, this behavior is undefined and potentially dangerous. When Desktop (Centennial) applications load, this flag is ignored.

Other flags that applications can specify to LoadLibraryEx include LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR, LOAD_LIBRARY_SEARCH_APPLICATION_DIR, LOAD_LIBRARY_SEARCH_SYSTEM32, and, in the LOAD_WITH_ALTERED_SEARCH_PATH flag, each of these flags modifies the search order to only specify the specific directory (or directories) that the flag references, or the flags can be combined to search multiple locations. For example, combining the application, system32, and user directories in LOAD_LIBRARY_SEARCH_DEFAULT_DIRS. Furthermore, these flags can be globally set using the SetDefaultDirectory API, which will affect all library loads from point on.

Another search-path order can be affected if the application is packaged or if it is not a packaged service or legacy Silverlight 8.0 Windows application. In these conditions, the DLL search will not use the traditional method and APIs, but will be restricted to the package-based search graph. This is also the case when the LoadedPackedLibrary API is used instead of the regular LoadLibraryEx function. The package-based graph is computed based on the <Package-dependency> entries in the UWP application's manifest file <Dependencies> and guarantees that no arbitrary DLLs can accidentally load in the package.

Additionally, when a packaged application is loaded, as it is not a Desktop application, all application-configurable DLL path ordering APIs, such as we we saw earlier, will be disabled, and only the default system behavior will be used (in combination with only looking package dependencies for most UWP applications as the above).

Unfortunately, even with safe mode and the default path search algorithms for legacy applications, which always might be copied from its usual location to a user-accessible location (for example, from c:\windows\system32\notepad.exe to c:\temp\notepad.exe, an operation that does not require administrative rights), an attacker can place a specially crafted DLL in the same directory as the application, and due to the ordering, it will take precedence over the system DLL. This can then be used for persistence or otherwise elevating the application, privileged (especially if the user, unaware of the change, is elevating it under UAC). To defend against this, processes and/or administrators can use a process-mitigation policy (see Chapter 7 for more information on these) called Prefer System32 Images, which inverts the order above between points 1 and 2, as the name suggests.

## DLL name redirection

Before attempting to resolve a DLL name string to a file, the loader attempts to apply DLL redirection rules are used to extend or override portions of the DLL namespace—which normally corresponds to the Win32 file system namespace—to extend the Windows application model. In order of application, these are:

- **MinWin API redirection**: The API set mechanism is designed to allow different versions of Windows to change the binary that exports a given API in a manner that is transparent to applications, by introducing the concept of contracts. This mechanism is briefly touched upon in Chapter 2, and will be further explained in a later section.
- **LOCAL redirection**: The .LOCAL redirection mechanism allows applications to redirect all copies of a specific DLL name, regardless of whether a full path is, to a local copy of the DLL in the application directory—either by creating a copy of the DLL with the same name followed by .local (for example, MyLibrary.dll.local) or by creating a file folder with the name .local under the application directory and placing a copy of the DLL in the folder (for example, C:\MyApp\MyLibrary.dll). DLLs redirected by .LOCAL mechanism are handled individually to those redirected by SxS. (See the next bullet point.) The loader handles LOCAL redirection of DLLs only when the executable does not have an associated manifest, either embedded or external. It is not enabled by default.
- **Fusion (SxS) redirection**: Fusion (also referred to as side-by-side, or SxS) is an extension to the Windows application model that allows components to process more detailed dependency information (usually including version information) by embedding binary resources as manifests. The Fusion mechanism was first used so that applications could load the correct version of the Windows controls when binary was split into different versions that could be installed alongside one another; other binaries built have since been versioned in the same fashion. As of Visual Studio 2005, applications could use the Microsoft linker use Fusion to locate the C runtime libraries, while Visual Studio 2015 and use API Set redirection to implement the idea of the universal CRT.
