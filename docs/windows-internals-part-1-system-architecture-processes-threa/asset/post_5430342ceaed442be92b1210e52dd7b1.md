## Plug-and-play driver installation

If the PnP manager encounters a device for which no driver is installed, it relies on the user-mode PnP manager to guide the installation process. If the device is detected during the system boot, a devnode is defined for the device, but the loading process is postponed until the user-mode PnP manager starts. (The user-mode PnP manager service is implemented in Pnpmgr.dll host in a standard Svchost instance.)

The components involved in a driver installation are shown in Figure 6-42. Dark-shaded objects in the figure correspond to components generally supplied by the system, whereas lighter-shaded objects are those in a driver installation files. First, a bus informs the PnP manager of a device it enumerates using a Device ID (1). The PnP manager checks the registry for the presence of a corresponding driver function, and when it doesn't find one, it informs the user-mode PnP manager (2) of the new device by its Device ID. The user-mode PnP manager tries to perform an automatic install without user intervention. If the installation process involves the posting of dialog boxes that require user interaction and the currently logged-on user has administrator privileges, the user-mode PnP manager launches the Rund32.exe application (the same application that has classic.cpl Control Panel utilities) to execute the Hardware Installation Wizard (3) (%SystemRoot%\System32\Devnew.dll). If the currently logged-on user doesn't have administrator privileges (or no user is logged on) and the installation requires user interaction, the user PnP manager defers the installation until a privileged user logs on. The Hardware Installation Wizard uses Setup.ini and Cfgmgr32.dll (configuration manager) API functions to locate INF files that contain drivers that are compatible with the detected device. This process might involve having the user insert media containing a vendor INF, or the wizard might locate a suitable INF in the driver store (%SystemRoot%\System32\DriverStore) that contains drivers that ship with Windows or others that are downloaded through Windows Update. Installation is performed in two steps. In the first, the party developer imports the driver package into the driver store, and in the second, the system performs the actual installation, which is always done through the %SystemRoot%\System32\Drwrist process.

To find drivers for the device, the installation process gets a list of hardware IDs (discussed earlier) and compatible IDs from the bus driver. Compatible IDs are more generic—for example a USB mouse from a specific vendor might have a special button that does something, but a compat ID for a generic mouse can utilize a more generic driver that ships with Windows if the specific driver is not available and at least provide the basic, functionality of a mouse.

These IDs describe all the various ways hardware might be identified in a driver installation file (INF). The lists are ordered to ensure the most specific description of the driver is listed. If matches are found in multiple lists, the following points apply:

- More-precise matches are preferred over less-precise matches.
- Digitally signed INFs are preferred over unsigned ones.
- Newer signed INFs are preferred over older signed ones.

> Note: If a match is found based on a compatible ID, the Hardware Installation wizard can prompt for media in case a more up-to-date driver comes with the hardware.

The INF file locates the driver files and contains instructions that fill in the driver's enumeration and class in the registry, copy required files, and the INF file may direct the Hardware Installation Wizard to (4) launch class or co-installer DLLs that perform class-specific or device-specific installation steps, as displaying configuration dialog boxes that let the user specify settings for a device. Finally, the drivers that make up a devonode load, the device/driver stack is built (5).

## EXPERIMENT: Looking at a driver's INF file

When a driver or other software that has an INF file is installed, the system copies its INF file to the %SystemRoot%\INF directory. One file that will always be Keyboard.inf because it's the INF file for the keyboard class driver. View its contents by opening it in Notepad and you will see something like this (after a semicolon):

;

;

; KEYBOARD.INF -- This file contains descriptions of Keyboard class devices

;

; Copyright (c) Microsoft Corporation. All rights reserved.

```ini
[Version]
Signature ="Windows NT"
Class =Keyboard
ClassGUID ={4D36E968-E325-11CE-BFC1-08002BE10318}
Provider =%MSFT%
DriverVer=06/21/2006,10.0.10586.0
```

```ini
[SourceDiskNames]
3426=windows cd
```

```ini
[SourceDiskFiles]
i8042prt.sys = 3426
kbdclass.sys = 3426
kbdhid.sys = 3426
```

An INF has the classic INI format, with sections in square brackets and underneath are key-value pairs separated by an equal sign. An INF is not "executed" from start to end sequentially; it's built more like a tree, where certain values point to sections with the value name execution continues. (Consult the WDK for the details.)

If you search for .sys, you'll come across sections that direct the user-mode PnP manager to install the i8042prt.sys and kbdclass.sys drivers:

...

```ini
[i8042prt.CopyFiles]
i8042prt.sys,,,0x100
```

...

```ini
[Kbdclass.CopyFiles]
kbdclass.sys,,,0x100
```

Before installing a driver, the user-mode PnP manager checks the system's driver-signing policy. If the settings specify that the system should block or warn of the installation of unsigned drivers, the user-mode PnP manager checks the driver's INF file for an entry that locates a catalog (file with the .cat extension) containing the driver's digital signature.

Microsoft's WHQL tests the drivers included with Windows and submitted by hardware vendors. When a driver passes the WHQL tests, it is "signed" by Microsoft. This means that WHQL obtains a hash, or unique value representing the driver files, including its image file, and cryptographically signs it with Microsoft's private-signing key. The hash is stored in a catalog file and included on the Windows installation media or returned to the vendor that submitted the driver.

## EXPERIMENT: Viewing catalog files

When you install a component such as a catalog file, Windows copies the catalog file to a directory under %SystemRoot%\System32\Catroot. Navigate to that directory in Explorer, and you will find a subdirectory that contains .cat files. For example, Nt.cat and NtSph.cat store the signatures and page hashes for Windows system files.

If you open one of the catalog files, a dialog box opens with two pages. The page labeled "General" shows information about the signature on the catalog file, and the Security Catalog page hashes of components that are signed with the catalog file. Screenshot of a catalog for an Intel audio driver shows the hash for the audio driver system. Other hashes in the catalog are associated with the various support DLLs that ship with the driver.

![](img/ff0e6a9d867a3a6e9527eb1d946810fc_590_0.png)

As it installs a driver, the user-mode PnP manager extracts the driver's signing signature from its catalog file, decrypts the signature using the public half of Microsoft's driver-signing private/public key pair, and compares the resulting hash with a hash of the driver file it is about to install. If the hashes match, the driver is verified as having passed WHQL testing. If a driver fails the signature verification, the user-mode PnP manager acts according to settings of the system driver-signing policy, either failing the installation attempt, warning the user that the driver is unsigned, or silently installing the driver.
