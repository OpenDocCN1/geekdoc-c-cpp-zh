
# Prioritization strategies

Internally, the five I/O priorities are divided into two I/O prioritization modes, called strategies. These are the hierarchy prioritization and the idle prioritization strategies. Hierarchy prioritization deals with all the I/O priorities except Very Low. It implements the following strategy:

- All-critical I/O must be processed before any high-priority I/O.
- All high-priority I/O must be processed before any normal-priority I/O.
- All normal-priority I/O must be processed before any low-priority I/O.
- All low-priority I/O is processed after any higher-priority I/O.

As application generates I/Os, IRPs are put on I/O queues based on their priority, and the hierarchy strategy dictates the ordering of the operations.

The idle prioritization strategy, on the other hand, uses a separate queue for non-idle I/O. Because the system processes all prioritized I/O before idle I/O, it's possible for the I/Os in the queue to be served, as long as there's even a single non-idle I/O on the system in the hierarchy strategy queue.

To avoid this situation, as well as control back-off (the sending rate of I/O transfers), the idle strategy uses a timer to monitor the queue and guarantee that at least one I/O is processed per unit of time (typically, half a second). Data written using non-idle I/O also causes the cache manager to write directly immediately and bypass its read-ahead head read operations that would otherwise preemptively read the file being accessed. The prioritization strategy also waits for 50 milliseconds after the completion of the last non-idle I/O in order to issue the next I/O. Otherwise, idle I/Os would occur in the middle of non-idle streams, causing costly seeks.

User-mode applications can set I/O priority on three different objects. The functions SetPriorityClass (with the PROCESS_MODE_BACKGROUND_BEGIN value) and SetThreadPriority (with the THREAD_MODE_BACKGROUND_BEGIN value), set the priority for all the I/Os generated by either the process or specific threads (the priority is stored in the IRP of request). These functions work on the current process or thread and lower the I/O priority to Very Low. In addition, these also lower the scheduling priority to 4 and the memory priority to 1. The function SetFileInformationHandle can set the priority for a specific file object (the priority is stored in the file object). Drivers can also set I/O priority directly on an IRP by using the IoSetPriority API.

Note The I/O priority in the IRP and/or file object is a hint. There is no guarantee that the I/O priority will be respected or even supported by the different drivers that are part of the storage stack.

The prioritization strategies are implemented by two different types of drivers. The hierarchy is implemented by the storage drivers, which are responsible for all I/Os on a specific port, such as ATA, SCSI, or USB. The ATA port driver (Atatop.sys) and USB port driver (Ubsport.sys) implement this strategy, while the SCSI and storage port drivers (Sciport.sys and Storport.sys) do not.

Note All port drivers check specifically for Critical I/Os and move ahead of their queues, even if they do not support the full hierarchy mechanism. This mechanism is in place to support critical memory paging I/Os to ensure system reliability.

This means that consumer mass storage devices as IDE or SATA drives and USB flash disks will take advantage of I/O prioritization, while devices based on SCSI, Fibre Channel, and iSCSI will not.

On the other hand, it is the system class device driver (Classpnp.sys) that enforces the idle strategy, so it automatically applies to I/Os directed at all devices, including SCSI drives. This separation ensures that idle I/O be subject to back-off algorithms to ensure a reliable system during operation under high idle I/O usage and that applications that use them can make forward progress. Placing support for this strategy in the Microsoft-provided class driver avoids performance problems that would have been caused by lack of support for it in legacy-party port drivers.

# I/O priority inversion avoidance

### Avoid I/O priority inversion

If an ERESOURCE is acquired by a thread with low I/O priority, and there are currently waits on the ERESOURCE with normal or higher priority, the current thread is temporarily boosted to normal I/O priority using the PsBoostThreadTo API, which increments the IoBoostCount in the ETHREAD structure. It also notifies Autoboot if the I/O priority was boosted or the thread was removed. (Refer to Chapter 4 for more on Autoboot).

It calls the IoThreadToPriority API, which enumerates all the IRPs requested the target thread (recall that each thread has a list of pending IRPs) and checks whether one has a lower priority than the target priority (normal in this case), identifying pending I/O priority invers. In turn, the device object responsible for those IRPs is identified, and the I/O manager checks whether a priority callback has been registered, which drivers can do through the IoRegisterPriorityCallback and by setting the DO_PRIORITY_CALLBACK_ENABLED flag on their device. Depending on whether the IRP is being paged I/O, this mechanism allows threaded paging boost. Finally, if no matching IRPs were found, but the thread has at least some pending IRPs, all are boosted regardless of device object or priority, which is called blanket boosting.

# I/O priority boosts and bumps

Windows uses a few modifications to normal I/O paths to avoid starvation, inversion, or otherwise unwanted scenarios when I/O priority is being used. Typically, these modifications are done by boosting I/O priority when needed. The following scenarios exhibit this behavior:

- When a driver is called with an IRP targeted to a particular file object, Windows makes sure that the request comes from kernel mode, the IRP uses normal priority even if the object has a lower I/O priority hint. This is called kernel bump.

- When reads or writes to the paging file are occurring (through IoPageRead and IoPageWrite), Windows checks whether the request comes from kernel mode and is not performed on behalf of Superfetch (which always uses idle I/O). In this case, the IRP uses normal priority even if the current thread has a lower I/O priority. This is called a paging bump.
