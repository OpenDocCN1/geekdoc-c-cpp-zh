
Although the format of these prototype PTEs is the same as that of the PTEs described earlier, the prototype PTEs are a layer between the page table and the PFN database and never appear directly in page tables.

By having all copies of a potentially shared page point to a prototype PTE to resolve faults, the memory manager can manage shared pages without updating the page tables of each process sharing it. For example, a shared code or data page might be paged out to disk at some point. When the memory manager retrieves the page from disk, it only needs to update the prototype PTE to point to the page's new location. The PTEs in each of the processes sharing the page remain the same, with the valid bit set and pointing to the prototype PTE. Later, as processes reference the real PTE, the real PTE will get updated.

## In-paging I/O

In-paging occurs when a read operation is issued to a file to satisfy a page fault. Because page tables are themselves pageable, the processing of a page fault can incur additional I/O if the system is loading the page table that contains the PTE or the prototype PTE that describes the original page.

The in-paging I/O operation is synchronous—that is, the thread waits on the I/O and is not interruptible by asynchronous procedure call (APC) delivery. The pager uses a special modifier in the I/O request to indicate paging. Upon completion, the system triggers an event which wakes up the pager and allows it to continue paging.

While the I/O operation is in progress, the faulting thread doesn't own any critical synchronization objects. Threads within the process can issue virtual memory functions and handle page faults while the I/O takes place. But there are a few interesting conditions that the pager must recognize when the I/O completes:

- Another thread in the same process or a different process could have faulted the same page (called a collided page fault and described in the next section).
- The page could have been deleted and remapped from virtual address space.
- The protection on page could have changed.
- The fault could have been for a prototype PTE, and the page that maps out of the working set.

The pager handles these conditions by saving enough state on the thread's kernel stack before paging. When the request is complete, it can detect these conditions and if necessary, dismiss the page fault without making the page valid. The PTE is reevaluated in its new state.

## Collided page faults

The case when another thread in the same process or a different process faults a page that is currently paging is known as a collided page fault. The pager detects and handles collided faults optimally; they are common occurrences in multithreaded systems. If another faults the same page, the pager detects the collided page fault, noticing that the page is transition and that a read is in progress (This information is in the PFN database entry). In this, the pager may wait on the event specified in the PFN database entry. Alternatively, it chooses to issue a parallel I/O to protect the file systems from deadlocks. (The first I/O to complete "wins", and the others are discarded.) This event was initialized by the first thread that issued the I/O needed to resolve the fault.

When the I/O operation completes, all threads waiting on the event have their wait satisfied. The first thread to acquire the PFN database lock is responsible for performing the in-page completion operations. The operations consist of checking I/O status to ensure that the I/O operation completed successfully, clearing the read-in-progress bit in the PFN database, and updating the PTE.

When subsequent acquire the PFN database lock to complete the collided page fault, the pager recognizes that the initial updating has been performed because the read-in-progress is clear and checks the in-page error flag in the PFN database element to ensure that in-page I/O completed successfully. If the in-page error flag is set, the PTE isn't updated, and an in-page error exception is raised in the faulting thread.

## Clustered page faults

The memory prefetches large clusters of pages to satisfy page faults and populate the system cache. The fetch operations read directly into the system's cache instead of a workset in virtual memory. Therefore, the prefetched data does not consume virtual address space, and the size of the fetch operation is not limited to the amount of virtual address space that is available.

Also, expensive TLB-flushing inter-processor interrupt (IPI) is needed if the page will be repurposed. The prefetched pages are put on the standby list and marked as transition in the PTE. If a prefetched page is subsequently referenced, the memory manager adds it to the working set. However, if it is never referenced, no system resources are required to release it. If the prefetched cluster is already in memory, the memory manager does not read them. Instead, it uses a dummy page to represent them so that an efficient large I/O can still be issued, as shown in Figure 5-27.
