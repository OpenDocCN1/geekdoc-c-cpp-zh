## Credential Guard

To understand the security boundary and protection that Credential Guard provides, it is important to understand the various components that provide access to a user's resources and login capabilities on a networked environment:

- **Password**: This is the primary used by interactive users to identify themselves on the machine. This credential is used for authentication and to derive the other components of the credential model. It is the most highly sought piece after a user's identity.
- **NT one-way function (NT OWF)**: This is a hash used by legacy components to identify the user (after a successful password login) using the NT LAN Manager (NTLM). While modern networked systems no longer use NTLM to authenticate the user, many local components still do, to some types of legacy network components (such as NTLM-authenticating protocols). Because NTOWF is an MD4 hash, its algorithmic complexity in the face of today's hardware, and its lack of anti-repeatability protection, means that intercepting the hash leads to instant compromise and even possible recovery of the password.
- **Ticket-granting ticket (TGT)**: This is the equivalent of the NTOWF when a more modern authentication mechanism is used: Kerberos. It is the default on Windows Active Directory-based domains and is enforced on Server 2016. The TGT and a corresponding key are provided to the local machine after a successful login (just like the NTOWF on NTLM), and intercepting both components will result in instant compromise of the user's credentials, although phrase and password recovery will not be possible.

Without Credential Guard enabled, some or all of these components of a user's authentication credentials are present in the memory of Lsass.

> Note: To enable Credential Guard on Windows 10 Enterprise and Server 2016 editions, open the Group Policy editor (gpedit.msc), choose Computer Configuration, select Administrative Templates, choose System, Device Guard, and select Turn on Virtualization Based Security. In the top-left part of the dialog box that appears, select Enabled. Finally, select one of the Enabled options in the Credential Guard configuration box.

## Protecting the password

The password, encrypted with a local symmetric key, is stored to provide single sign-on (SSO) capabilities over protocols such as WDigest, used for HTTP-based authentication in Windows XP or Terminal Services/RDP. As these protocols use plaintext authentication, the password must be kept in memory, which is accessible through code injection, debugger, or other techniques, and decrypted. Credential Guard cannot change the nature of these inherently unsafe protocols. Therefore, the only solution, which Credential Guard employs, is to disable functionality for such protocols. This causes a loss of compatibility and forces the user to re-authenticate.

Obviously, a preferable solution is to remove the usage of a password completely, which Windows Hello, described in the "Windows Hello" section in this chapter, allows. Authenticating with biometric credentials as a user's face or fingerprint removes the need to ever type a password, securing the interactive credential against hardware key loggers, kernel sniffing/hooking tools, and other mode-based spoofing applications. If the user never has a password to type, there is no password to steal. Another secure credential is the combination of a smart card and associated PIN. While a PIN may be stolen as its typed, the smart card is a physical element which cannot be intercepted without a complex hardware-based attack. This is a type of two-factor authentication (TFA), of which many other implementations exist.

## Protecting the NTOWF/TGT key

Even with protected credentials, a successful login results in a domain controller's key distribution center (KDC) returning the TGT and its key, as well as the NTOWF for legacy applications. Later, the user employs the NTOWF for accessing legacy resources and the TGT to generate a service ticket. This can be used to access remote resources (such as files on a share), as shown in Figure 7-3.

Thus, with either NTOWF or the TGT and the key (stored in Lsass) in the attacker's hands, access to resources is possible even with the smart card, PIN, or user face or fingerprint. Protecting Lsass from access by an attacker is thus one option that can be used, and is possible using the Protected Process (PPL) architecture described in Chapter 3.

Lsas can be configured to run protected by setting the DWORD value RunAsPPL in the HKLM\System\CurrentControlSet\Console\Lsass registry key to 1 (This is not a default option, as legitimate party authentication providers [DLLs] load and execute in the context of Lsass, which would not be protected). Unfortunately, this protection would guard the NTOWF and TGT from user-mode attackers.

## Secure communication

As shown in Chapter 2, VTL 1 has a minimal attack surface, as it does not have access to I/O of any kind. As such, isolated ISA, the LS process, which is VTL 1, cannot directly communicate with the KDC. This is still responsibility of the LS process to authenticate and receive the TGT and its key for generation of service tickets. This leads to two questions: how does LS send and receive the secrets from isolated ISA, and how can we prevent an attacker from doing the same?

To answer the first question, recall Chapter 3, "Processes and jobs," which services are available to Trusts. One uses the Advanced Local Procedure Call (ALPC), which the Secure kernel supports by proxying the NT to the Kernel. Now, the Isolated User Mode environment supports the RPC runtime library (Rpc.dll) over the ALPC protocol, which allows VTL 0 and 1 to communicate using local RPC just like any other application and service. In Figure 7-4, you can see the Lsass.exe, which has a handle to the LS_ISO_RPC_SERVER ALPC port. This is used to communicate with the Lsass.exe process (See Chapter 8 in Part 2 for more information on ALPC).

To answer the second question, some understanding of cryptographic protocols and challenge/response models is required. If you are already familiar with some of the basics SSL/TLS technology and its use in Internet to prevent man-in-the-middle (MitM) attacks, you can think of the KDC and isolated ISA in a similar way. Lsass sits in the middle as a proxy and, it would only see encrypted traffic between the KDC and isolated ISA, without the ability to understand its contents. Because isolated ISA establishes a local "session key," which only lives in VTL 1, and then uses a secure protocol to send this session encrypted with another key, which only the KDC, can then respond with the TGT and its key encrypting it with the isolated L session key. Therefore, Lsass sends an encrypted message to the KDC (which it cannot decrypt) and an encrypted message from the KDC (which it cannot decrypt).
