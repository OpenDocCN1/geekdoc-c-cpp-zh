This model can be used to protect legacy NTLM authentication, which is based on a challenge/response model. When a user uses login with a plaintext credential, LSA sends it isolated to LSA, which encrypts the encrypted credential with its session key and returns to Lsass, when an NTLM challenge/response is required. Lsass sends the NTLM challenge and the previously encrypted credentials to isolated LSA. At this point, only isolated LSA has the encryption key, so it decrypts the credentials and generates an NTLM response based on the challenge.

Note, that four physically possible attacks exist in this model:

- If the machine is already physically compromised, the plaintext password can be intercepted either as it is input or as it is sent to isolated LSA (if LSA is already compromised). Using Windows Hello can mitigate this attack.
- As mentioned, NTLM does not have replay-properties. Therefore, if the NTLM response is captured, it can be replayed for the same challenge. Alternatively, if the attacker compromises Lsass after login, it can capture the encrypted credential and force isolated LSA to generate new NTLM responses for arbitrary NTLM challenges. This attack, only works until reboot, because isolated LSA generates a new session key at that point.
- In case of Kerberos logon, the NTOWF (which is not encrypted) can be intercepted and then reused, just like in a standard pass-the-hash attack. Again, however, this requires an already compromised machine (or physical network intersection).
- The user, with physical access, may be able to disable Credential Guard. In this situation, the legacy authentication model is used (a so-called “downgrade attack”), and older attack models may now be employed.

# UEFI lock

Because disabling Credential Guard (which is ultimately nothing more than a registry setting) is trivial for an attacker, Secure Boot and UEFI can be leveraged to prevent a non-physically present administrator (such as malware with admin rights) from disabling Credential Guard. This is done by enabling Credential Guard with UEFI Lock. In this mode, an EFI runtime variable is written to firmware memory and a reboot is required. At the reboot, the Windows loader, which operates in EFI Boot services, will write an EFI boot variable (which has the property of not being readable or writeable once EFI Boot services is exited) to record the fact that Credential Guard is enabled. Additionally, a BCD Configuration Database (BCD) option will be recorded.

When the kernel boots, it will automatically rewrite the Credential Guard registry key in the presence of the BCD option/or UEFI runtime variable. If deblown by an attacker, BitLocker (if enabled) and TPM-based remote attestation (if enabled) will detect and require physical input of the admin’s recovery key booting, which will restore the BCD option based on the UEFI runtime variable. If the UEFI runtime variable is deleted, the Windows boot loader will restore it based on the EFI boot variable. As such, without special code to delete the UEFI boot variable—which can only be done in EFI Boot services—there is no way to disable Credential Guard in UEFI lock.

The only code that exists is in a Microsoft binary called SecComp.exe. This is downloaded by the administrator, who must then either boot the computer from an alternate-based device and manually execute it (which will require the BitLocker recovery key well as physical access) or modify the BCD (which will require the BitLocker recovery key). At the reboot, SecComp.exe will require user confirmation when in UEFI mode (which can be only done by a physical user).

# Authentication policies and armored Kerberos

Using a security of “secure, unless already compromised before login or by a physical administrator” is definitely an improvement over the traditional non-Credential Guard-based security model. Some enterprises and organizations may want an even stronger security guarantee: that even a compromised machine cannot be used to fake or replay a user’s credentials, and that if a user’s credentials have been compromised, they cannot be used outside specific systems. By leveraging a Server 2016 feature called Authentication Policies, and armored Kerberos, Credential Guard can operate in this heightened security model.

In this mode, the VTL 1 Secure Kernel will collect the TPM (as a file on disk can also be used, but makes the security moot), a special machine ID key. This key is used to generate a TGT during the initial domain join operation as the machine is provisioned (obviously, it is important to ensure the machine is in a trusted state during provisioning), and this TGT is sent to the KDC. Once configured, when the user logs in with his or her credential, it is combined with the machine-credentials (which only isolated LAS has access to), which forms a proof-of-origin key. The KDC will then reply with the NTOWF and TGT and its key after encrypting it with the proof-of-origin key. In this mode, two security guarantees are provided:

- The user is authenticating from a known machine If the user, or an attacker, has the original credentials, and attempts to use them on a different machine, their TPM-based credential will be different.
- The NTLM response/user ticket is coming from isolated LSA and has not been manually generated from Lsass This guarantees Credential Guard is enabled on the machine, even if the physical user can disable it in some way.

Unfortunately, once again, if the machine is compromised in such a way that the proof-of-origin-encrypted KDC response uses the user TGT and it is intercepted, it can be stored and used to request key-encrypted service tickets from isolated LSA. This can then be sent to a file server (for example) to access until a reboot is issued to wipe the session key. As, on a system with Credential Guard, it is recommended to reboot each time a user logs off. Otherwise, an attacker may be able to issue valid tickets even after the user is no longer present.

# Future improvements

As discussed in Chapter 2 and Chapter 3, the Secure Kernel in VTL 1 is currently undergoing improvements to add support for specialized classes of PCI and USB hardware, which can be communicated with the hypervisor and VTL 1 using the Secure Device Framework (SDK). Combined with Biolso.exe and Flso.exe, which are new Trustlets to securely obtain biometric data and video frames (from a webcam), a VTL 0 kernel mode-based component cannot intercept the contents of a Windows authentication attempt that we've classified as safe to capture a user's plaintext password, but still technically capable through custom-driver-interception. Once released, Windows credentials will be guaranteed at the hardware level to never be available for VTL 1. In this mode, LSA will not need to be involved in a Windows authentication. Isolated LSA will obtain the credentials directly from the biometrics or isolated frame service.

> Note The Secure Device Framework (SDF) is the WDF-equivalent for VTL 1 drivers. This framework is not currently public, but is shared with Microsoft partners only for creating VTL 1 drivers.

# Device Guard

While Credential Guard is concerned with safeguarding the user's credentials, Device Guard has a completely different goal: protecting the user's machine itself from different kinds of software- and hardware-based attacks. Device Guard leverages the Windows Code Integrity services, as Kernel-Mode Code Signing (KMCS) and User-Mode Code Integrity (UMCI), and strengthens them through Hypervisor Code Integrity (HVCI). (See Chapter 8 in Part 2 for more information on Credential Integrity.)

Additionally, Device Guard is fully configurable, thanks to Custom Code Integrity (CCI) and signing policies that are protected by Secure Boot and defined by the enterprise administrator. These policies, which are explained in Chapter 8, allow enforcement of inclusion/exclusion lists that are based on cryptographically sound information (such as certificate singers or SHA-2 hashes) instead of file paths or file names as with AppLocker policies. (See the section "AppLocker later in this chapter for more on AppLocker.)
