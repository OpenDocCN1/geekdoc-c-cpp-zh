
# The page hashing algorithm

The algorithm that the system uses to calculate an 8-bytes page hash (CRC) is the following: two 64-bit large prime numbers are multiplied together, and the result is used as the starting hash. The page is scanned from the beginning to the end; the algorithm hashes 64 bytes per cycle. Each read 8-byte value from the page in question is added to the starting hash, then the hash is rotated right prime-number of bits (starting with 2, 3, 5, 7, 11, 13, 17 and 19). 512 memory operations (4096/8) are needed to complete a page hash.

# The classification phase

When all the hashes of the pages belong to a NUMA node have been successfully calculated, the second part of the algorithm commences. The goal of this phase is to process each CRC/PFN entry in the list and organize them in a strategic way. The page sharing algorithm minimize the contexts used, and is as fast as possible.

The MiProcessC1 routine starts by sorting the CRC/PFN list by hash (using a quick sort algorithm). Another data structure, combine block, is used to keep track of all the pages that share the same hash, and, more importantly, to store the new prototype PTE that will have the new combined Each CRC/PFN of the new sorted list is processed in order. The system needs to verify if the current hash is common (belonging to a zero or complete-filled page) and if it's equal to the previous or next hash (memory that is sorted). If this is not the case, the system checks if a combine block already exists in the PCS structure. If so, a combined block has already been identified in a previous execution of the algorithm or in another node of the system. Otherwise it is not combined, and the CRC is unique and the page couldn't be combined, the algorithm continues to the next page in the list.

If a common hash has never been seen before, the algorithm allocates new empty combine block (used for the master PFN) and inserts it into a list by the page-sharing code (next stage). If the hash already existed (the page is not the master copy), a reference to the combine block is added in the current CRC/PFN entry.

At this point, the algorithm has prepared all that the page-sharing algorithm needs: a list of combine blocks used to store the physical pages and their prototype PTEs, a list of CRC/PFN entries organized by the working set, and some physical memory to store the content of the new shared pages.

The algorithm then obtains the address of the physical page (that should exist, due to the initial check performed previously by the MiCombine routine) and searches a data structure used to store all the pages that belongs to the working set (from now on we will call this WS code code). If this doesn't exist, it allocates a new one and inserts it in an AVL tree. The CRC/PFN and virtual address of the page are linked together inside the WS code code.

After all the identified pages have been processed, the system allocates the physical memory for the new shared pages (using an MDL), and processes each WS code code; for performance reasons, the candidate pages located inside the node are sorted by their original virtual address. The system is now ready to perform the actual page combining.

# The page combining phase

The page combining phase starts with a WS CRC node structure that contains all the pages that belong to a specific working set and are all candidates for combining, and with a list of free combine blocks, used to store the prototype PTE and the actual shared page. The algorithm attaches to the target process locks its working (raising IRQL to dispatch level). In this way, it will be able to directly read and write each page without the need to remap it.

The algorithm processes some time, it checks the CRC/PFN entry in the list, but since it's running at dispatch level IRQL and execution could take some, it checks if the processor has DPCs or scheduled items in its queue (by calling KeShieldYieldProcessor) before analyzing the next entry. If the answer is yes, the algorithm does the right thing and takes appropriate precautions to maintain state.

The actual page sharing strategy expects three possible scenarios:

- The page is active and valid, but it contains all zeros, rather than combining, it replaces its PTE with a demand-zero PTE. Recall that this is the initial state of normal VirtualAlloc-memory allocation.

- The page is active and valid, but it is not zeroed out, meaning it has to be shared. The algorithm checks if the page has been promoted to the master: if the CRC/PFN entry has a pointer to a valid combine block, it means it is not the master page; otherwise, the page is the master copy. The master page hash is rechecked and a new physical page is assigned for the sharing. Otherwise, the already existing combine block is used (and its reference count incremented). The system is now ready to convert the private page into a shared one, and calls the MiConvert-PrivateProto to perform the actual job.

- The page is in the modified or standby. In this case, it's mapped to a system address as a valid page and its hash recalculated. The algorithm performs the same step as the previous scenario, with the only difference being that the PTE is converted from shared to prototype using the MiConvertStandbyToProto route.

When the sharing of page ends, the system inserts the combine block of the master copy into the PCS structure. This is important because the combine block becomes the link between each private PTE and the combined page.

# From private to shared PTE

The goal of MiConvertPrivateToProto is to convert a PTE of an active and valid page. If the routine detects that the prototype PTE is zero, it means the master page must be created. The system maps the shared page and sets the page priority of the PFN. The result is that the private PTE is again a valid hardware PTE.

Next, the system needs to modify the PTE of the private page so that it is valid, its protection mask changed to copy-write, and the PTE inside the combine block is marked as deletion. Finally, the TLB is flushed and the process working set size is decremented.

Otherwise (the PTE inside the combine block is non-zero), it means that the private page should be a copy of the master. The system is now ready to convert the private page into a shared one, and calls the MiConvert-PrivateProto to perform the actual job. If the two pages don't match, the function stops and returns. Otherwise, it unmaps the shared page and sets the PFN to the higher of the two.

The algorithm now calculates the software PTE that should be inserted into the process page table. To do that, it reads the address of the hardware PTE that maps the shared page (in the combine block), shifts it, and sets the Prototype and Combined bits. A check is made that the share count of the private PFN is 1. If it is not, processing is aborted. The algorithm writes the new software PTE in the private page table of the process and decrements the count of the page table of the old private PFN (keep in mind that an active PFN always has a pointer to its table). The target process working set size is decremented by one page and the TLB is flushed. The old private page is moved into the transition state, and its PFN is marked as deletion. Finally, the system uses another trick to prevent trimming on the shared pages by simulating a page fault. That way the share count of the shared PFN is again incremented, and no would occur at a time the process will try to read the shared page. The result is that the private PTE is again a valid hardware PTE. Figure 5-48 shows the effect of a soft page fault on the second page, making it valid and incrementing the share count.
