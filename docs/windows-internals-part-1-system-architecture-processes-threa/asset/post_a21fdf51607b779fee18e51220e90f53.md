While active, each IRP is usually in an IRP list associated with the thread that requested the I/O. (Otherwise, it is stored in the file object when performing thread-agnostic I/O, which is described in the “Thread agnostic I/O” section in this chapter). Additionally, paging I/O IRPs are also associated with the faulting thread (although they are not cancellable). This allows Windows to use the thread-agnostic I/O optimization—when an asynchronous procedure call (APC) is not used to complete I/O if the current thread is the initiating thread. This page faults occur inline without requiring APC delivery.

## IRP flow

IRPs are typically created by the I/O manager, and then sent to the first device on the target device node. Figure 6-13 shows a typical IRP flow for hardware-based device drivers.

![](img/ff0e6a9d867a3a6e9527eb1d946810fc_535_0.png)

FIGURE 6-13 IRP flow.

The I/O manager is the only entity that creates IRPs. The Plug and Play manager and the manager are also responsible for creating IRPs with major function code IRP_MJ_PNP and IRP_MJ_, respectively.

Figure 6-13 shows an device node with six layered devices: two filters, the FDO, and the PDO. This means an IRP that device is created with I/O stack locations—one for each. An IRP is always delivered to the highest layered device, even if a handle was opened to a named device that is lower in the device stack.

A driver that receives an IRP can do one of the following:

- * Can complete the IRP then and calling IoCompleteRequest. This could be the IRP has some invalid parameters (for example, insufficient buffer size or bad I/O code), because the operation is quick and can be accomplished immediately, as getting some status from the device or reading a value from the registry. The driver calls IoGetIrpStackLocation to get a pointer to the stack location that it should refer to.

- * Can forward the IRP to the next layer after doing some processing. For example, an upper filter can do some logging of the operation and send the IRP down to be executed normally. Before sending the request, the driver must prepare the next I/O stack location that it will be looked at by the next driver in line. It can use the IoSkipIrp-StackLocation macro if it does not wish to make changes, or it can make a copy with IoCopy-Irp-StackLocationNext and make appropriate changes. Once the next I/O stack location is prepared, the driver calls IIoCallDriver.
- * As an extension of the previous, the driver can also register for a completion by calling IoSetCompletionRoutine.

The IRP flow continues with various drivers handling the IRP as it travels down the stack.
