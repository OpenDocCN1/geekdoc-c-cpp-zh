## Page priority

Every physical page in the system has a page priority value assigned to it the memory manager. The page priority is a number in the range 0 to 7. Its main purpose is to determine the order in which pages are consumed from the standby list. The memory manager divides the standby list into eight sublists that each stores pages of a particular priority. When the memory manager wants to take a page from the standby list, it takes pages from low-priority lists first.

Each thread and process in the system is also assigned a page priority. A page priority usually reflects the page priority of the thread that causes its allocation. (If the page is shared, it reflects the highest page priority among the sharing threads.) A thread inherits its page-priority value from the process to which it belongs. The memory manager uses lower priorities for pages it reads from disk speculatively when anticipating a process's memory accesses.

By default, processes use a page-priority value of 5, but the SetProcessInformation and SetThreadInformation use functions to change process and thread priority values. These functions call the NetSetInformationProcess and NetSetInformation-Thread functions. You can look at the memory priority of a thread with Process Explorer (per-page priority can be displayed by looking at the PFN entries, which you will see later in the chapter). Figure 5-38 shows Process Explorer's threads tab information about Winlog's memory. Although the thread priority is high, the standard is 5.

## Modified page writer and mapped page writer

The memory manager employs two system threads to write pages back to disk and those pages back to standby lists (based on their priority). One system writes modified pages (ModifiedPageWriter) to the paging file, and a second writes modified pages to mapped files (MappedPageWriter). Two threads are required to avoid creating a deadlock. This would occur if the writing of mapped files caused a page fault that in turn required a free page when no free pages were available, thus requiring the modified page writer to create more free pages. By having the modified page writer perform I/Os from a second system thread, it can wait without blocking regular I/O.

Both threads run at priority 1, and after initialization they wait for separate event objects to trigger their operation. The mapped page writer waits on objects:

- An exit event, signaling the exit (not relevant to this discussion).
- The mapped writer event, stored in the global variable MySystemPartition.MappedPageWriterEvent (on Windows 8.x and Server 2012). This event is signaled in the following instances:
- During a page list operation (MiInsertPageList), this routine inserts a page into one of the lists (standby, modified, etc.) based on its input. Routine this event if the number of file-system-destined pages on the modified list has reached more than 16 and the number of available pages has fallen below 1024.
- In an attempt to free pages (ObtainFreePages).
- By the memory manager's working manager (WorkingSetManager), which runs as part of the kernel's balance manager (once every second). The working manager signals this event if the number of file-system-destined pages on the modified list has reached more than 800.
- Upon a request to flush all modified pages (FlushAllPages).
- Upon a request to flush all file-system-destined pages (FlushAllFileSystem). In most cases, writing modified pages to their backing store does not occur if the number of mapped pages on the modified list is less than the maximum cluster size, which is 16 pages. This check is not made in FlushAllPages.
- An array of 16 events called ListEvent, stored in MySystemPartition.Pages.MappedListHead (MappedListHead on Windows 8.x and Server 2012). Each time a mapped page is dirtied, it is inserted into one of these 16 page lists based on a bucket number, stored in MySystemPartition.WorkingSetControl.CurrentMappedPageBucket (MappedPageBucket on Windows 8.x and Server 2012). This bucket number is updated by the working manager when it considers that mapped pages have gone old enough, which is currently 100 (stored in the MiWriteGapCounter variable in the same structure MiWriteGapCounter on Windows 8.x and Server 2012) and incremented whenever the working manager runs. The reason for these additional events is to reduce data loss in the case of a system crash or power failure by eventually writing out modified mapped pages if the modified list hasn't reached its threshold of 800 pages.

The modified page writer writes on two events: the first is an Exit event, and the second in MySystemPartition.Modifier.ModifiedPageWriterEvent (on Windows 8.x and Server 2012) on a kernel gate stored in ModifiedPageWriterGate, which can be signaled in the following scenarios:

- A request to flush all pages has been received.
- The number of available pages—stored in MySystemPartition.Vm.AvailablePages (AvailablePages on Windows 8.x and Server 2012)—drops below 128 pages.
- The size of the zeroed and free pages below 20,000, and the number of modified pages destined for the paging file is the smaller of one-sixteenth of the available pages or 64 MB (16,384 pages).
- When a working set is being trimmed to accommodate additional pages, if the number of available pages is less than 15,000.
- During a list operation (MiInsertPageList). This routine signals event if the number of page-file-destined pages on the modified page list has reached more than 16 pages and the number of available pages has fallen below 1,024.

Additionally, the modified page writer writes on two other events after the preceding event is signaled. One is used to indicate rescanning of the paging file is required (for example, a new page may have been created), stored in MySystemPartition.Modifier.RescanPageFilesEvent (RescanPageFilesEvent on Windows 8.x and Server 2012). The second event is internal to the paging file header (MySystemPartition.Modifier.PagingFileHeader (PagingFileHeader on Windows 8.x and Server 2012)), which allows the system to manage request flush out of the paging file when needed.

When invoked, the modified page writer writes as many pages as possible to disk with a single I/O request. It accomplishes this by examining the original PTE of the PFN database for pages on the modified list to locate locations on the disk. Once a list is created, the pages are removed from the modified list, an I/O request is issued, and at successful completion of the I/O request, the pages are placed at the tail of the standby list corresponding to their priority.

Pages that are in the process of being written can be referenced by another thread. When this happens, the reference count and the share count in the entry that represents the physical page are incremented to indicate that another process is using the page. When the I/O operation completes, the modified page writer notices that the reference count is no longer 0 and does not place the page on any standby list.
