These results depend on Limithave been linked with the /LARGEADDRESSWARE. Had it not been, the results would have been about 2 GB for each. Sixty-four-bit applications linked without /LARGEADDRESSWARE constrained to the first 2 GB of the process virtual address space, just like 32-bit applications. (This flag is set by default in Visual Studio for 64-bit builds.)

# x64 virtual addressing limitations

As discussed, 64 bits of virtual address space allow for a possible maximum of 16 EB of memory — a notable improvement over the 4 GB offered by 32-bit addressing. Obviously, neither today's computers nor tomorrow's are close to requiring support for that much memory.

Accordingly, to simplify chip architecture and avoid unnecessary—particularly in address translation (described later)—AMD’s and Intel’s current x64 processors implement only 256 TB of virtual address space. That is, only the lower-order 48 bits of a 64-bit virtual address are implemented. However, virtual addresses are 64 bits wide, occupying 8 bytes in registers or when stored. The high-order 16 bits (bits 48 through 63) must be set to the same value as the highest-order implemented bit (bit 47), in a manner similar to sign extension in two's complement arithmetic. An address that conforms to this rule is said to be a canonical address.

Under these rules, the half of address space starts at 0x0000000000000000 as expected, but ends at 0x00FFFFFFFFFFFFFF. The upper half of the address space starts at 0xFF80000000000000 and ends at 0FFFFFFFFFFFFFF. Each canonical region is 12 TB. As newer processors implement more of the address bits, the lower half of memory will expand upward toward 0xFFFFFFFFFFFFFF, while the upper half will expand downward toward 0x8000000000000000.

# Dynamic system virtual address space management

Thirty-bit versions of Windows manage the system address space through an kernel virtual allocator, described in this section. 64-bit versions of Windows have no need to use the allocator for virtual address space management (and thus bypass the cost) because each region is statistically defined (refer to Figure 5-13).

When the system initializes, the MiInitializeVirtual function sets up the dynamic ranges and sets the available virtual images to available kernel space. It then initializes the space for boot loader images, process space (https), and the HAL with the MiInitializeSystemVaRange function, which is used to set hard-coded address ranges (on 32-bit systems only). Later, when non-pooled pool is initialized, this function is used to reserve the virtual address ranges for it. Finally, when a driver loads, the address range is released to a driver-image range instead of a boot-loaded range.

After this point, the rest of the system virtual address space can be dynamically requested and released through MiAllocateVa (and an analogous MiAllocateInSession and MiReturnSystemVa). Operations such as expanding the system cache, the PTEs, non-pooled pool, pooled pool, and/or special pool; mapping memory with pages, creating the PFN database; and creating a new session all result in dynamic virtual address allocations for a specific region.
