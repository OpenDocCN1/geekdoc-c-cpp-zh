# Windows client memory limits

64-bit Windows client editions support different amounts of memory as a differentiating feature, with the low end being 4 GB increasing to 2 TB for Enterprise and Professional editions. All 32-bit Windows client editions, support a maximum of 4 GB of physical memory, which is the highest physical address accessible with the standard x86 memory management mode.

Although client SKUs PAE addressing modes on x86 systems in order to provide hardware no-execution protection (which would allow access to more than 4 GB of physical memory), revealing that systems would crash, hang, or become unbootable some device drivers, commonly those for video and audio devices found on clients but not servers, were not programmed to expect physical addresses larger than 4 GB. As result the drivers truncated addresses, resulting in memory corrections and corruption side effects. Server systems commonly have more generic, with simpler and more stable drivers, and therefore had not generally revealed these problems. The problematic client ecosystem led to the decision for client editions to ignore physical memory that remains above 4 GB, even though they could theoretically address it. Driver developers are encouraged to test their systems with the nomem option, which will force the kernel to use physical addresses above 4 GB only if sufficient memory exists on the system to allow it. This will immediately lead to the detection of such issues in faulty drivers.

Although 4 GB is the licensed for 32-bit clients, the effective limit is actually lower and depends on the system's chipset and connected devices. This is because the physical address map includes not only RAM but also device memory, and x86 and x64 systems map all device memory below the 4 GB address boundary to remain compatible with 32-bit operating systems that don't how to handle addresses larger than 4 GB. Newer chipsets do support PAE-based device remapping, but client editions of Windows do not support this for the driver compatibility problems explained earlier. (Otherwise, drivers would receive 64-bit pointers to their device memory).

# Memory compression

The Windows 10 memory managers implement a mechanism that compresses private and page-file-backed section pages that are modified on the manager page list. The primary candidates for compression are private pages belonging to UWP apps because compression works well with the working set swapping and emptying that occurs for such applications if memory is tight. After an application is suspended its working set can be emptied at any time and dirty pages can be compressed. This will create additional available memory that may be enough to hold another application in memory without making the first application's pages leave memory.

> Note Experiments have shown that pages compress to around 30–50 percent of their original size using Microsoft’s Xpress algorithm, which balances speed with size, thus resulting in considerable memory savings.

The memory compression architecture must adhere to the following requirements:

- A page cannot be in a compressed and uncompressed form because this would waste physical memory due to duplication. This means that whenever a page is compressed, it must become a free page after successful compression.
- The compression store must maintain its data structures and store the compressed data that it is always saving memory for the system. This means that if a page doesn't compress well enough, it will not be added to the store.
- Compressed pages must appear as available memory (because they can be repurposed if needed) to avoid creating a perception that compression increases memory consumption.

Memory compression is enabled by default on client SKUs (phone, PC, Xbox, and so on). Server SKUs do not currently use memory compression, but that is likely to change in future versions.

> Note In Windows 2016, Task Manager still shows a numerous in compressed memory, but that number is always zero. Also, the memory process does not exist.

During system startup, the SuperFetch service (sysmain, hosted in svchost.exe instance, described in the upcoming "Proactive memory management (SuperFetch)") section instructs the Store Manager in the executive to call NetSystemInformation to create a single system store (always the first store to be created), to be used by non-UWP applications. Upon startup, each UWP application communicates with the SuperFetch service and requests the creation of a store for itself.
