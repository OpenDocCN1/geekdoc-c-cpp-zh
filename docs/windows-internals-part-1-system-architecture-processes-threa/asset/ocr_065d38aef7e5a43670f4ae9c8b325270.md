Other entries are prefixed with uap, rescap, and wcap. One of these (rescap) refers to capabilities that require special onboarding from Microsoft and custom approvals before being allowed on the store. In Cortana's case, these include capabilities such as accessing SMS messages, emails, contacts, location, and user data. Windows capabilities, on the other hand, refer to capabilities that are reserved for Windows and system applications. No store application can use these. UAP capabilities refer to standard capabilities that anyone can request on the store. (Recall that UAP is the old name for UWP).

Unlike the first set of capabilities, which map to hard-coded RIDs, these capabilities are implemented in a different fashion. This uses a list of well-known RIDs to be constantly maintained. Instead, with this mode, capabilities can be fully updated and customized on the fly. To do this, they simply take the capability string, convert it to upper-case format, and take a SHA-2 hash of the resulting string, like AppContainer package SIDs are the SHA-2 hash of the package marker. Again, SHA-2 hashes are 32 bytes, this results in 8 RIDs for each capability, following the well-known SECURITY_CAPABILITY_RID (3).

Finally, you'll need a device ID. These refer to device classes that the UWP application will need to access, and can be identified through well-known strings as the ones you see above or by a GUID that identifies the device class. Rather than using one of the two methods of SID creation already described, one uses a third: for types of capabilities, the GUID is converted into a binary format and mapped out into four RIDs (because a GUID is 16 bytes). On the other hand, if a well-known name was specified, it must first be converted to a GUID. This is done by looking at the HKLM\Software\Windows\Access\Mappings registry key, which contains a list of registry keys associated with device capabilities and a list of GUIDs that map to these capabilities. The GUIDs are converted to a SID as you've seen.

> Note For an up-to-date list of supported capabilities, see https://msdn.microsoft.com/en-us/windows/uwp/packaging/app-capability-declarations.

As encoding of all these capabilities into the token, two additional rules are applied:

+   - As you may have seen in the earlier experiment, each AppContainer token contains its own package SID as a capability. This can be used by the capability system to specifically lock down access to a particular app through a common security check instead of validating the package SID separately.

+   - Each capability is re-encoded as a group RID through the use of the SECURITY_CAPABILITY_APPRID (1024) RID as an additional sub-authority preceding the eight-capability hash RIDs.

After the capabilities are encoded into the token, various components of the system will read them to determine whether an operation being performed by an AppContainer should be permitted. You'll note most of the APIs are undocumented, as communication and interoperability with UWP applications is not fully supported and are left to broker services, inbox drivers, or kernel components. For example, the kernel and drivers can use the Rt1Capability API to authenticate access to hardware interfaces or APIs.
