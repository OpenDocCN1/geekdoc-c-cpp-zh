Perhaps the most interesting among the idle process is that Windows reports the priority of the idle threads as 0. In reality, however, the values of the idle threads' priority members are irrelevant these threads are selected for dispatching only when there are no other threads to run. Their priority is never compared with that of any other thread. Nor is it used to put an idle thread on a ready queue, and idle threads are never part of ready queues. (Only one thread per Windows system is actually running at priority 0—the zero page thread, explained in Chapter 5)

Just as the idle threads are special cases in terms of execution, they are also special cases for preemption. The idle thread routine, KiIdleLoop, performs a number of operations that preclude it from being preempted by another thread in the usual fashion. When non-idle threads are available to run on a processor, the thread is marked as idle in its PRCB. After that, if a thread is selected for execution on the idle processor, the thread address is stored in the NextThread pointer of the idle processor's PRCB. The idle thread checks this pointer on each pass through its loop.

Although some details of the flow vary between architectures (this is one of the few routines in assembly and not C), the basic sequence of the idle thread is as follows:

+   1. The idle thread enables pending interrupts to be delivered, and disables them (using the STI and CLI instructions on x86 and x64 processors). This is desirable because significant parts of the idle thread execute with interrupts disabled.
2. On the debug build some architectures, the idle thread checks whether a kernel debugger is trying to break into the system. If so, it gets access.
3. The idle thread checks whether any DPCs (described in Chapter 6) are pending on processors. DPCs could be pending if a DPC interrupt was not generated when they were generated. If DPCs are pending, the idle loop calls KiRetireList to deliver them. This will also perform timer expiration, as well as deferred reading; the latter is explained in the upcoming "Multiprocessor systems". KiRetireList must be entered with interrupts disabled, which is why interrupts are left disabled at the end of step I. KiRetireList exits with interrupts disabled as well.
4. The idle thread checks whether quantum expiration has been requested. If so, QuantumEnd calls to process the request.
5. The idle thread checks whether a thread has been selected to run on the next processor. If so, it dispatches that thread. This could be because, for example, a DPC or timer expiration processed in step 3 resolved the case of a waiting thread, or if another processor selected the thread for this processor to run while it was already in the idle loop.
6. If requested, the idle thread checks for threads ready to run on other processors and, if possible, schedules one of them locally. (This operation is explained in the upcoming "Idle scheduler")
7. The idle thread calls the registered power-management processor idle routine (in any case power-management functions need to be performed), which is either in the processor driver (such as intelppm.sys) or in the HAL if such a driver is unavailable.
