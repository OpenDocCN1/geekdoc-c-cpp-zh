Although each Windows process has its own private memory space, the kernel-mode OS and device-driver code share a single virtual address space. Each page in virtual memory is tagged to indicate what access mode the processor must be in to read/write the page. Pages in system space are accessible from kernel mode, whereas all pages in the user mode and kernel mode. Read-only pages (as as those containing static data) are not writable from any mode. Additionally, on processors that support no-execute memory protection, Windows marks pages containing data as non-executable, preventing inadvertent or malicious code execution in areas (if this feature, Data Execution Prevention [DEP] is enabled).

Windows doesn't provide any protection for read/write memory being used by processes running in kernel mode. In other words, in kernel mode, OS and device-driver code share complete system-space memory and can bypass Windows security to access objects. Because the bulk of the Windows OS code runs in kernel mode, it is vital that components be carefully designed and tested to ensure they do not violate system security or quality system stability.

This lack of protection also emphasizes the need to remain vigilant when using a third-party device driver, especially if it's unsigned, once in kernel mode, the driver has access to all data. This risk was one of the reasons the driver-signing mechanism introduced in Windows 2000, which warns (and, if configured as such, blocks) the driver if an attempt is made to add an unsigned plug-and-play driver (see Chapter 6, "I/O system", for more information on driver driving), and does not affect other types of drivers. Also, a mechanism called Driver Verifier device–driver finds bugs, such as overflows or memory leaks, that can cause security or reliability issues. (Chapter 6 closes Driver Verifier).

On 64-bit and ARM versions of Windows 8.1, the kernel-mode code-signing (KMCS) policy dictates that all drivers (not just plug-and-play) must be signed with a cryptographic key by one of the major code certification authorities. The user cannot explicitly force the installation of an unsigned driver, even as an administrator. As a one-time exception, however, this restriction can be disabled manually. This allows drivers to be self-signed and tested, places a watermark on the desktop wallpaper labeled "Test Mode," and disables digital rights management (DRM) features.

On Windows 10, Microsoft implemented an even more significant change, which was enforced starting one year after release as the July Anniversary Update (version 1607). As of time, all Windows 10 drivers must be signed by only the two code certification authorities with a SHA-2 Extended Validation (EV) hardware certificate instead of the regular file-based SHA-1 certificate and its0 authorities. Even unsigned, the hardware driver must be submitted to Microsoft through the System (Dev) portal for attestation signing, which will see the driver receive a Microsoft signature. As such, the kernel will only allow Microsoft-signed Windows 10 drivers with exceptions except the aforementioned Test Mode. Drivers signed before the date of Windows 10 (July 2015) can continue to load with their signature for the time being.

With Windows 2016, the operating system takes its strongest stance yet. On top of the aforementioned requirements, mere attestation is insufficient. For a Windows 10 driver to load on a server system, it must pass through stringent Windows Hardware Quality Labs (WHQL) certification as part of the Hardware Compatibility Kit (HCK) and be submitted for formal evaluation.
