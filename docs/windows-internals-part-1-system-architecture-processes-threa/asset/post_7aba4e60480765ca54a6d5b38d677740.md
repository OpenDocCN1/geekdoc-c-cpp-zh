
## Context switching

A thread's context and the procedure for context switching vary depending on the processor's architecture. A typical context switch requires saving and reloading the following data:

- Instruction pointer
- Kernel stack pointer
- A pointer to the address space in which the thread runs (the process's page table directory)

The kernel saves this information from the old thread by pushing it onto the current (old thread)'s) kernel-mode stack, updating the stack pointer, and saving the stack pointer in the old thread's KTHREAD structure. The kernel stack pointer is then set to the new thread's kernel stack, and the new thread's context is loaded. If the new thread is in a different process, it loads the address of its page table directory into a special processor register so that its address space is available. (See the description of address translation in Chapter 5.) If a kernel APC needs to be delivered, an interrupt at IRQL1 is requested. (For more information on APCs, see Chapter 8 in Part 2.) Otherwise, control passes to the new thread's restored instruction pointer and the new thread resumes execution.

## Direct Switch

Windows 8 and Server 2012 introduced an optimization called Direct Switch, which allows a thread to donate its quantum and boost to another thread, which is then immediately scheduled on the processor. In synchronous client/server scenarios, this can produce significant throughput improvements because the client/server threads are not migrated to other processors that may be idle or parked. Another way to think about this is that at any given time, only the client or the server thread is running, so the thread scheduler should treat them as a single logical thread. The scheduler has no way of knowing the first thread (T1 in Figure 4-13) is waiting on state signaling any synchronization object that the second thread (T2) is waiting on. Therefore, a special function must be called to let the scheduler know that this is the case (atomic signal and wait).

If possible, the KiDirectSwitch function performs the actual switch. It's called by KiDispatcher with a flag indicating to use Direct Switch if possible. Priority donation, if the first thread's priority is "donated" to the second thread (if the latter's priority is lower than the first), is applied by yet another flag to KiDispatcher. In the current implementation, these flags are always specified (or not alone), meaning in any Direct Switch attempt, priority donation is attempted as well. Direct Switch can fail—for example, if the target thread's affinity precludes it from running on the current processor. However, if it succeeds, the quantum of the first thread is transferred to the target thread and the first thread loses its quantum.

Direct Switch is used in the following scenarios:

- If a thread calls the SignalAndWaitWait Windows API (or its kernel equivalent NtWaitForSingleObject)
- ALPC (described in Chapter 8 in Part 2)
- Synchronous procedure call (RPC) calls
- COM remote calls (currently MTA [multithreaded apartment]) to MTA only

## Scheduling scenarios

Windows answers the question of "Who gets the CPU?" based on thread priority, but how does this approach work in practice? The following sections illustrate how priority-driven preemptive multi-tasks work on the thread level.

## Voluntary switch

A thread might voluntarily relinquish use of the processor by entering a wait state on some object (such as a mutex, a semaphore, an I/O completion port, a thread, and so on) by calling one of the Windows wait functions as WaitForSingleObject or WaitForMultipleObjects. (Waiting for objects is described in Chapter 8).

Figure 4-14 illustrates a thread entering a wait state and Windows selecting a new thread to run. Figure 4-14, the top block (thread) is voluntarily relinquishing the processor so that the next thread in the ready queue can run. Although it might appear from this figure that the relinquishing thread's priority is reduced, it's not. It's just moved to the wait queue of the objects it is waiting for.

## Preemption

In this scheduling scenario, a lower-priority thread is preempted when a higher-priority thread becomes ready. This situation might occur for a couple of reasons:

- A higher-priority thread's wait completes (the event that the other thread was waiting for).
- A thread priority is increased or decreased.

In either of these cases, Windows must determine whether the currently running thread should continue to run or be preempted to allow a higher-priority thread to run.

Note: Threads in user mode can preempt threads in kernel mode. The mode in which the thread is running doesn't matter; the thread priority is the determining factor.

When a thread is preempted, it is put at the head of the ready queue for the priority it was running at (see Figure 4-15).

## Quantum end

When the running thread exhausts its CPU quantum, Windows must determine whether the thread's priority should be decremented and whether another thread should be scheduled on the processor.

If the thread priority is reduced (for example, because of some event it received before), Windows looks for a more appropriate thread to schedule, such as one in a ready queue with higher priority than the currently running thread. If the thread priority isn't reduced and there are other threads in the ready queue at the same priority, Windows selects the next thread in the ready queue at that priority level. It moves the previously running thread to the tail of that queue, giving it a new quantum value and changing its state from running to ready. This is illustrated in Figure 4-16.

As you saw, instead of relying on a clock interval–based quantum to schedule threads, Windows uses an accurate CPU cycle count to maintain quantum targets. Windows also uses this count to determine whether quantum is currently appropriate for the thread—something that might have happened previously and is important to discuss.

Using a scheduling model that relies only on the clock interval timer, the following situation can occur:

- Threads A and B become ready to run during the middle of an interval (Scheduling code runs not just at each clock interval, so this is often the case.).
- Thread A starts running but is interrupted for a while. The time spent handling the interrupt is charged to the thread.
- Interrupt processing finishes and thread A starts again, but it quickly hits the next interval. The scheduler can assume only that thread A had been running all this time and now switches to thread B.
- Thread B starts running and has a chance to run for a full clock interval (barring preemption interrupt handling).

In this scenario, thread A was unfairly penalized in two different ways. First, the time it spent handling a device interrupt counted against its CPU time, even though the thread probably had nothing to do with the interrupt. (Interrupts are handled in the context of whichever thread was running at the time, as discussed in Chapter 6.) It also was unfairly penalized for the time the system was idling before it was scheduled. Figure 4-17 illustrates this scenario.

![](img/ff0e6a9d867a3a6e9527eb1d946810fc_275_0.png)

FIGURE 4-17 Unfair time slicing in pre-Vista versions of Windows.

Windows keeps an accurate count of the exact number of CPU clock cycles spent doing what the thread was scheduled to do (which means excluding interrupts). It also keeps a quantum target of clock cycles that should have been spent by the thread at the end of its quantum. Both of the decisions that would have been made against thread A as described in the preceding paragraph will not happen in Windows. Instead, the following situation occurs:

- Threads A and B become ready to run during the middle of an interval.
- Thread A starts running but is interrupted for a while. The CPU clock cycles spent handling the interrupt are not charged to the thread.
- Interrupt processing finishes and thread A starts running, but quickly hits the next clock interval. The scheduler looks at the number of CPU clock cycles charged to the thread and compares them to the expected CPU clock cycles that should have been charged at quantum end.
- Because the number is much smaller than it should be, the scheduler assumes that thread A started running in the middle of a clock interval and might have been additionally interrupted.
- Thread A gets its quantum increased by another clock interval, and the quantum target is recalculated. Thread A now has its chance to run for a full clock interval.
- At the next clock interval, thread A has finished its quantum, and thread B gets a chance to run.
