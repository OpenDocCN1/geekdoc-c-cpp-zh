+   - If the calling thread can be granted all the permissions, it would get back a valid handle and then call WaitSingleObject to wait for the process to exit. However, another thread in the process, perhaps with fewer privileges, can use the same handle to do other operations with the process, as terminate prematurely with TerminateProcess; because the handle allows all operations on the process.

+   - The call can fail if the calling thread does not have sufficient privileges to be granted all possible access and the result is an invalid handle, meaning no access to the process. This is unfortunate, because the thread just needed to ask for the SYNCHRONIZE access mask. That has a much better chance of succeeding than asking for PROCESS_ALL_ACCESS.

The simple conclusion here is that a thread should request the exact access it requires—no more, less.

Another event that causes the object to execute access validation is when a process references an existing handle. Such references often occur infrequently, as a process calls on a Windows API to manipulate an object and passes an object handle. For example, a thread opening a file can request permission to the file. If the thread has permission to access the object in this way, as dictated by its security context and the security settings of the file, the object creates a handle—representing itself—in the handle of the thread's process. The types of accesses the threads in the process are granted through the handle and are stored with the object manager.

Subsequently, the thread could attempt to write to the file using the WriteFile function, passing the file handle as a parameter. The system service WriteFile calls Ntdll.dll, uses the object manager ObjectReferenceByHandle (documented in the WDK) to obtain a pointer to the file object from the handle. ObjectReferenceByHandle accepts the access that the caller wants as a parameter. After finding the handle entry in the process handle table, ObjectReferenceToObjectByHandle compares the access being requested with the access granted at the time the file was opened. ObjectReferenceToObjectByHandle will indicate that the write operation would fail because the caller did not obtain write access when the file was opened.

The security functions also enables Windows to define their own objects and to call the services of the SRM (the AuthZ user-mode APIs, described later) to enforce the Windows security model on those objects. Many kernel-mode functions that the object manager and other executive components use to protect their objects are exported as Windows user-mode equivalent of SeAccessCheck. API AccessCheck. Windows applications can therefore leverage the flexibility of the security model and transparently integrate with the authentication and administrative interfaces that are present in Windows.

The essence of the SRM's security model is an equation that takes three inputs: the security identity of a thread, the access that thread wants to an object, and the security settings of the object. The output is yes or no and indicates whether the security model grants the access it desires.
