# Thread suspension

Threads can be suspended and resumed explicitly with the SuspendThread and ResumeThread API functions, respectively. Every thread has a suspend count, which is incremented by suspension and decremented by resuming. If the count is 0, the thread is free to execute. Otherwise, it will not execute.

Suspension works by queuing a kernel APC to the thread. When the thread is switched to execute, the APC is executed first. This puts the thread in a wait state until an event is signaled when the thread is finally resumed.

This suspension mechanism has a noticeable drawback if the thread is in a wait state when a suspension comes in, because it means that the thread needs to wake up just to be suspended. This (if the thread's kernel stack was swapped out) can result in a kernel stack今回. Windows 8.1 and Server 2012 R2 added a mechanism called Lightweight Suspend to allow for the suspension of a thread that is in a wait state without using the APC mechanism, but by directly manipulating the thread's object in memory and marking it as suspended.

# (Deep) freeze

Freezing is a mechanism by which processes enter a suspended state that cannot be changed by calling ResumeThread on the threads. This is useful when the system needs to suspend a UWP app. This happens when a Windows app goes to the background—for example, another app goes to the foreground or the app is in suspended mode. In this case, the system gives the app roughly five seconds to work, typically to save application state. Saving is important because Windows apps may be killed without notice if memory resources become low. If the app is killed, the state can be reloaded on the next launch and the user would have the perception that the app never went away. Freezing a process means suspending all threads in such a way that ResumeThread is not able to wake. A flag in the KTHREAD structure indicates whether a thread is frozen. For a thread to be able to execute, its suspend count must be 0 and the Frozen flag must be clear.

Deep freeze adds another constraint: Newly created threads the process cannot start as fast. For example, if a call to CreateThread is used to create a new thread in a deep-frozen process, the thread will be frozen before actually starting. This is the typical use of the freezing capability.

Process- and thread-freezing functionality is not exposed directly to user mode. It is used internally by the Process State Manager (PSM) service that is responsible for issuing the requests to the kernel for freeing and thawing (unfreezing).

You can also freeze processes using jobs. The ability to freeze and unfreeze a job is not publicly documented, but it's possible to do so using the standard SetInformationJob system call. This is typically used for Windows apps, as all Windows apps are contained in jobs. Such a job may contain a single process (the Windows app itself), but it can also contain background task-hosting processes related to the same Window app so that freezing or thawing (unfreezing) all processes under that job can be done in a single stroke.
