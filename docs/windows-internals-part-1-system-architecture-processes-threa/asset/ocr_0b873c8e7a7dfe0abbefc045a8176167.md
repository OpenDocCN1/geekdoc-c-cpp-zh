The rest of the driver ensures that the information stays consistent by tracking detections, renaming operations, truncations, and the reuse of file keys by implementing sequence numbers.

At any time during tracing, the rebalancer may be invoked to repopulate pages differently. The decisions are made by analyzing information such as the distribution of memory within working sets, the zero page list, the modified page list and the standby page lists, the number of faults, the state of PTE bits, the per-page usage traces, current virtual address consumption, and working set size.

A given trace can be a page-access trace, in which the tracer uses the access to keep track of which pages were accessed by the process (both file page and private memory). Or, it can be a logging-trace, which monitors the file name—to-file mapping updates to the actual file on disk. These allow SuperFetch to map a page associated with a file object.

Although SuperFetch trace only keeps track of page accesses, the Super-Fetch service processes this trace much deeper, adding its own richer information such as where the page was loaded (for example, in resident memory or a hard fault), whether this was the initial access to page kept, and what the rate of access actually is. Additional information, such as the system state, is also kept, as well as information about recent scenarios in which the trace was last referenced. The generated trace information is kept in memory by logging into data structures—in the case of page-access traces—identify traces, a virtual address—to-working set pair, or in the case of a name-logging trace, a file-to-offset pair. SuperFetch can keep track of which range of virtual addresses for a given process have page-related events and which range of offsets for a given file have similar events.

# Scenarios

One aspect of SuperFetch that is distinct from its primary page prioritization and prefetching mechanisms (covered in more detail in the next section) is its support for scenarios, which are active actions on the machine for which Fetch strives to improve the user experience. These scenarios are as:

+   - **Hibernation** The goal of hibernation is to intelligently decide which pages are saved in the hibernation file other than the existing-working pages. The goal is to minimize the amount of time it takes for the system to be responsive after a resume.
- **Standby** The goal of standby is to completely remove hard faults after resume. Because a typical system can resume in less than 2 seconds, but can take 5 seconds to spin up the hard drive after a long sleep, a single hard fault could cause such a delay in the resume cycle. SuperFetch prioritizes pages needed after a standby to remove this.
- **Fast switching** The goal of fast switching is to keep an accurate priority and understanding of each user's memory. That way, switching to another user will cause the user's session to be immediately usable, and won't require a large amount of time to allow pages to be faulted.

Each of these scenarios has different goals, but all are centered around the main purpose of minimizing or removing hard faults.
