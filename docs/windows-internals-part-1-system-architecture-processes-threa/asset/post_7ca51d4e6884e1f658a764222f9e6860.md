
# LiveKd tool

LiveKd is a free tool from Sysinternals that enables you to use the standard Microsoft kernel debuggers just described to examine the running system without booting the system in debugging mode. This approach might be useful when kernel-level troubleshooting is on a machine that wasn't booted in debugging mode. Certain issues might be hard to reproduce reliably; a reboot with the debug option might not readily exhibit the error.

You run LiveKd just as you run WinDbg or kd. LiveKd passes any command-line options you specify to the debugger you run. By default, LiveKd runs the command-line kernel debugger (kd). To have it run WinDbg, use the -w switch. To see the help files for LiveKd switches, use the ? switch.

LiveKd presents a simulated crash dump to the debugger so you can perform any operations in LiveKd that are supported on a crash dump. Because LiveKd relies on physical memory to back the simulated dump, the kernel debugger might run into situations where data structures are in the middle of being changed by the system and are inconsistent. If you want to refresh the snapshot, enter the q to quit the debugger. LiveKd will ask you whether you want to start again. If the debugger enters a loop in printing output, press Ctrl+C to interrupt the output and quit. If it hangs, press Ctrl+Break, which will terminate the debugger process. LiveKd will tell you whether you want to run again the debugger.

# Windows Driver Kit

The Windows Driver Kit (WDK) is also available through the MSDN subscription program. Just like the Windows SDK, it is available for free download. The WDK documentation is included in the MSDN Library.

Although the WDK is aimed at developers of device drivers, it is an abundance of Windows internals information. For example, although Chapter 6 describes the I/O system architecture, driver model, and basic device driver data structures, it does not describe the individual kernel support functions in detail. The WDK documentation contains a comprehensive description of all Windows kernel support functions and mechanisms used by device drivers in both tutorial and reference form.

In addition to including the documentation, the WDK contains header files (in particular, ntdll.h, wdm.h) that define key internal data structures and constants as interfaces to many internal system routines. These files are useful when exploring Windows internal data structures with the kernel debugger although the general layout and content of these structures are shown in this book, detailed field-level descriptions (such as size and data types) are not. A few of these data structures—such as object dispatcher headers, wait blocks, events, mutants, semaphores and so on—are, however, fully described in the WDK.

If you want to dig into the I/O system and driver model what is presented in this book, read the WDK documentation—especially the Kernel-Mode Driver Architecture Design Guide and Kernel-Mode Driver Reference manuals. You may also find useful Programming the Windows Driver Model, Second Edition by David Debor (Microsoft Press, 2002) and Developing Drivers with the Windows Driver Foundation by Penny Orrell and Guy Smith (Microsoft Press, 2007).

# System architecture

Now that you've learned the terms, concepts, and tools you need to be familiar with, it's time to start exploring the internal design goals and structure of the Microsoft Windows operating system (OS). This chapter explains the overall architecture of the system—the key components, how they interact with each other, and the context in which they run. To provide a framework for understanding the system, let's first review the requirements and goals of Windows.

# Requirements and design goals

The following requirements drove the specification of Windows:

- Provide a true multitasking environment.
- Run on multiple architectures.
- Scale well on symmetric multiprocessing.
- Be a great client and server.
- Meet POSIX standards.
- Meet security requirements.

To meet these, Windows adopted the following design goals:

- Extensibility: The code must be written to comfortably grow.
- Portability: The system must be able to move to new hardware with relative ease.
- Reliability and robustness: The system should protect itself from both internal malfunction and external tampering.
- Compatibility: Windows should be compatible with older versions.
- Performance: Within the constraints of the other design goals, the system should be as fast and responsive as possible.

# Operating system model

In most multiuser operating systems, applications are separated from the OS. The kernel code runs in privileged processor mode (referred to as kernel mode in this book), with access to system data and hardware. Application code runs in non-privileged processor mode (called user mode), with a limited set of interfaces to system data and no direct access to hardware. When a user-mode program calls a system service, the processor executes a special instruction that switches context to kernel mode. When the system service completes, the OS switches the thread back to user mode and allows the caller to continue.

Windows is similar to most UNIX systems that it is a monolithic OS in the sense that the bulk of the OS and device driver share the same kernel-protected memory space. This means any OS component or device driver can corrupt data used by other system components. However, as we saw in Chapter 1, "Concepts and tools," Windows addresses this through attempts to strengthen the quality and constrain the performance of third-party drivers through programs such as WHQL and enforcement through KMCS, while incorporating additional kernel protection technologies such as virtualization-based security and the Device Guard and Hyper Guard features.

The kernel-mode components of Windows also embody basic object-oriented design principles. For example, in general they don't reach into each other's data structures to access information maintained by individual components. Instead, they use formal interfaces to pass parameters and access/or modify structures.
