
- A flag indicating whether the process belongs to a Windows application (so that Csrss can determine whether to show the startup cursor)
- UI language information
- DLL redirection and .local flags (discussed in the "Image loader" section later in the SDK manual)
- Manifest file

When it receives this message, the Windows subsystem performs the following steps:

- 1. CsCreateProcess duplicates a handle for the process and the thread. In this case, the usage count of the process and the thread is incremented from 1 (which was set at creation time) to 2.
- 2. The Csrss process structure (CSR_PROCESS) is allocated.
- 3. The new process's exception port is set to the general function port for the Windows subsystem so that the Windows subsystem will receive a message when a second-chance exception occurs in the process. (For information on exception handling, see Chapter 8 in Part 2.)
- 4. If a new process group is to be created with the new process as the root (CREATE_NEW_PROCESS_GROUP flag in CreateProcess), then it's set in CSR_PROCESS. A process group is useful for sending a control event to a set of processes sharing a console. See the Windows documentation for CreateProcess and GenerateConsoleEvent for more information.
- 5. The Csrss thread structure (CSR_THREAD) is allocated and initialized.
- 6. CsCreateThread inserts the thread in the list of threads for the process.
- 7. The count of processes in this session is incremented.
- 8. The process shutdown level is set to 0x280, the process default shutdown level. (See SetProcess-ShutdownParameters in the Windows SDK documentation for more information.)
- 9. The new Csrss process structure is inserted into the list of Windows subsystem-wide processes.

After Csrss has performed these steps, CreateInternal checks whether the process was ran (which meant it was executed through ShellExecute and the AppInfo service after the consent dialog box was shown to the user). This includes checking whether the process was a setup process. If it, the process is opened, and the virtualization is turned on so that the application is virtualized (See information on virtualization in Chapter 7?) If the application contained elevation shifts or had a requested elevation level in its manifest, the process is destroyed and an elevation request is sent to the AppInfo service.

Note that most of these checks are not performed for protected processes. Because these processes must have been designed for Windows Vista or later, there is no reason they should require elevation, virtualization, or application-compatibility checks and processing. Additionally, allowing mechanisms as the shim engine to use its usual hooking and memory-patching techniques on a protected process would result in a security hole if one could figure how to insert that modify the behavior of the protected process.

# Stage 6: Starting execution of the initial thread

At this point, the process environment has been determined, resources for its threads to have been allocated, the process has a thread, and the Windows subsystem knows about the new process. Unless the caller specified the CREATE_SUSPENDED flag, the initial thread is now resumed so that it can start running and perform the remainder of the process-initialization work that occurs in the context of the new process (stage 7).

# Stage 7: Performing process initialization in the context of the new process

The new thread begins running the kernel-mode thread routine KiStartThread. KiStartThread lowers the IRQL from deferred procedure call (DPC) to APC level and then calls the system initial thread routine, PspUserThreadStartup. The user-specified thread start address is passed as a parameter to this routine. PspUserThreadStartup performs the following actions:

- It installs an exception chain on x86 architecture. (Other architectures work differently in this regard, see Chapter 8 in Part 2.)
- It lowers IRQL to PASSIVE_LEVEL (which is the only IRQL user code is allowed to run).
- It disables the ability to swap the process context at runtime.
- If the thread was killed on startup (for whatever reason), it's terminated and no further action is taken.
- It sets the locale ID and the ideal processor in the TEB, based on the information present in kernel-mode data structures, and then checks whether thread creation actually failed.
- It calls DbgCreateThread, which checks whether notifications are sent for the new process. If they weren't, and notifications are enabled, an image notification is sent first to the process and then for the image load of Ntdll.dll.

> Note: This is done in this stage rather than when the images are first mapped because the process ID (which is required for the kernel calls) is not yet allocated at that time.

- Once these checks are completed, another check is performed to see whether the process is a debugger. If it is and debugger notifications have not been sent, then a create process message is sent through the debugger object (if one present) so that the process debug event (CREATE_PROCESS_DEBUG_INFO) can be sent to the appropriate debugger process. This is followed by a thread debug event and another debugger event for the image load of Ntdll.dll. DbgCreateThread then waits for a reply from the debugger (via the ContinueDebug function).
- 8. It checks whether application prefetching is enabled on the system, and if so, the prefetcher (and Superfetch) to process the prefetch instruction file (if it exists) and prefetch pages referenced during the first 10 seconds the last time the process ran. (For details on the prefetcher and Superfetch, see Chapter 5.)
- 9. It checks the system-wide cookie in the SharedUserData structure has been set up. If it hasn't, it generates on hash of system information such as the number of interrupts processed, DPC deliveries, page faults, interrupt time, and a random number. This system-wide cookie is used in the internal decoding and encoding of pointers, such as in the heap manager to protect against classes of exploitation. (For more information on the heap manager security, see Chapter 5.)
- 10. If the process is secure (IUM process), then a call is made to Hv1StartSecureThread that controls the secure kernel to start thread execution. This function only returns when the thread exits.
- 11. It sets up the initial thread context to the image-loader initialization routine (LdrInitializeThunk in Ntdll.dll), as well as system-wide thread startup (LdrUserThreadStart in Ntdll.dll). These steps are done by editing the content of the thread in process and then using an exit from system operation, which loads the specially crafted user context. LdrInitializeThread initializes the loader, the heap manager, N tables, thread-local storage (TLS) and fiber-local storage (FLS) arrays, and critical section structures. It then loads all DLLs and calls the DLL entry points with the DLL_PROCESS_ATTACH function code.

Once the function returns, NtContinue restores the new user context and returns to user mode. Thread execution now starts.

RtUserThreadStart uses the address of the actual image entry point and the start parameter and calls the application's entry point. These two parameters have already been pushed onto the stack by the kernel. This complicated sequence of events has two purposes:

- It allows the loader inside Ntdll.dll to set up the process internally and behind the scenes so that other user-mode code can run properly. (Otherwise, it would have no heap, thread-local storage, and so on.)
- Having all threads begin in a common route allows them to be wrapped in exception handling so that they crash, Ntdll.dll is aware of that and can handle the unhandled exception inside Kernel32.dll. Application developers can also set SetUnhandledExceptionFilter to add their own unhandled exception-handling code.
