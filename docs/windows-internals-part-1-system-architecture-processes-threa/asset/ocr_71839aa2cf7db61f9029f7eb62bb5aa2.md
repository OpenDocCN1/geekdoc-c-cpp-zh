# AppContainer security environment

One of the biggest side-effects caused by the presence of an AppContainer SID and related flags is that the access check algorithm you saw in the "Access checks" earlier in this chapter is modified to essentially ignore all regular user and group SIDs that the token may contain, essentially treating them as deny-only SIDs. This means that even though Calculator may be launched by a user John Doe belonging to the Users and Everyone, it will fail access to John Doe's SID, the Users SID, or the Everyone group. In fact, the only SIDs that are checked during the discretionary access check will be that of the AppContainer SID, followed by the capability access check algorithm, which will look at any capability SID part of the token.

Taking even further merely treating the discretionary SIDs as deny-only, AppContainer tokens effect one further critical security change to the access check: a NULL DACL, typically treated as an allow-any situation due to the lack of any information (recall that this is different from an empty DACL, which is a deny-only situation and ignored and treated as a deny situation). To make matters simpler, the only types of objects that an AppContainer can access are those that explicitly have an allow ACE for its AppContainer SID or for one of its capabilities. Unexpected (NULL DACL) objects are out of the game.

This situation causes compatibility problems. Without access to the most basic file system, registry, and object manager resources, how can an application ever function? Windows takes this into account by creating a custom execution environment, "jail" if you will, specifically for each AppContainer. These jails are as follows:

> Note So far we've implied that each UWP packaged application corresponds to one AppContainer token. However, this doesn't necessarily that only a single executable file can be associated with an AppContainer. UWP packages can contain multiple executables, all of which belong to the same AppContainer. These allow them to share the same SID and capabilities and exchange data between each other, such as a micro-service back-end and a front-end executable.

+   - The AppContainer SID's string representation is used to create a subdirectory in the object manager's namespace under \Sessions\AppContainerNamedObjects. This becomes the primary directory of named kernel objects. This specific subdirectory object is ACled with the AppContainer SID associated with the AppContainer that has an allow-all access. This is in contrast to desktop apps, which all use the \Sessions\BasedObjects subdirectory (within the same session x). We'll discuss the implications of shortly, as well as the requirement for the token to now handle stores.

+   - The token will contain a LowBox number, which is a unique identifier for an array of LowBox Number entries that store the kernel stores in the g_SessionLowBoxArray variable. Each of these maps to the SEP_LOWBOX_NUMBER_ENTRY structure that, most importantly, contains an atom table unique to this AppContainer, because the Windows Subsystem Kernel Driver (Win32k.sys) does not allow AppContainers access to the global atom table.
