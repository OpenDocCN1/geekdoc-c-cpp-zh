Thus, with either NTOWF of the TGT and the key (stored in Lsass) in the attacker's hands, access to resources is possible even with the smart card, PIN, or user face or fingerprint. Protecting Lsass from access by an attacker is thus one option that can be used, and is possible using the Protected Process (PPL) architecture described in Chapter 3.

Lsas can be configured to run protected by setting the DWORD value RunAsPPL in the HKLM\System\CurrentControlSet\Console\Lsass registry key to 1 (This is not a default option, as legitimate party authentication providers [DLLs] load and execute in the context of Lsass, which would not be protected). Unfortunately, this protection would guard the NTOWF and TGT from user-mode attackers, it does not protect against kernel attackers or user-mode attackers that leverage vulnerabilities in any of the millions of drivers that are produced monthly. Credential Guard solves this problem by using another process, Lsass.exe, which runs as a Trustlet in VTL 1. This process therefore stores the user's secrets in its memory, not in Lsass.

# Secure communication

As shown in Chapter 2, VTL 1 has a minimal attack surface, as it does not have the full "NT" kernel, nor does it have drivers or access to I/O of hardware of any kind. As such, isolated ISA, the LS process, which is a VTL 1 trust, cannot directly communicate with the KDC. This is still responsibility of the LS process to authenticate and receive the TGT and the key NTOWF, as communicating with the file server by using service ticket. This seemingly results in a problem: the TGT and its key/NTOW transient pass through LS authentication, and the keys are available for the generation of service tickets. This leads to two questions: how does LS send and receive the secrets from isolated ISA, and how can we prevent an attacker from doing the same?

To answer the first question, recall Chapter 3, "Processes and jobs," which services are available to Trusts. One uses the Advanced Local Procedure Call (ALPC), which the Secure kernel supports by proxying the NTpc to the Kernel. Now, the Isolated User Mode environment supports the RPC runtime library (Rpc44.dll) over the ALPC protocol, which allows a VTL 0 and 1 VTL to communicate using local RPC just like any other application and service. In Figure 7-4, you can see the Lsass.exe, which has a handle to the LS_ISO_RPC_SERVER ALPC port. This is used to communicate with the Lsass.exe process (See Chapter 8 in Part 2 for more information on ALPC).

To answer the second question, some understanding of cryptographic protocols and challenge/response models is required. If you are already familiar with some of the basics SSL/TLS technology and its use in Internet to prevent man-in-the-middle (MitM) attacks, you can think of the KDC and isolated ISA in a similar way. Lsass sits in the middle as a proxy and, it would only see encrypted traffic between the KDC and isolated ISA, without the ability to understand its contents. Because isolated ISA establishes a local "session key," which only lives in VTL 1, and then uses a secure protocol to send this session encrypted with yet another key, which only the KDC, can then respond with the TGT and its key encrypting it with the isolated L session key. Therefore, Lsass sends an encrypted message to the KDC (which it cannot decrypt) and an encrypted message from the KDC (which it cannot decrypt).
