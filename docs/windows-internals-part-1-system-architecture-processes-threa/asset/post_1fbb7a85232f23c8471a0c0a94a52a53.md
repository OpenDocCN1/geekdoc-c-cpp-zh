
- Cancelling synchronous I/Os: A thread can call CancelSynchronousIo. This enables create (open) operations to be cancelled when supported by a device driver. Several drivers in Windows support this functionality. These include drivers that manage network file systems (for example, MUP, DFS, and SMB), which can cancel operations to network paths.

- Cancelling asynchronous I/Os: A thread can cancel its own asynchronous I/Os by calling CancelIo. It can cancel all asynchronous I/Os issued to a specific file handle, regardless of which thread initiated it, in the same process with CancelIo. CancelIoEx also works on operations associated with I/O completion ports through the aforementioned thread-agnostic support in Windows. This is because the I/O system keeps track of a completion port's outstanding I/Os by linking them with the completion port.

# I/O cancellation for thread termination

The other scenario in which I/Os can be cancelled when a thread exits, either directly or as a result of its process terminating (which causes the threads of the process to terminate). Because every thread has a list of IRPs associated with it, the I/O manager can walk this list, look for cancelable IRPs, and cancel them. Unlike CreateFile, which does not wait for an IRP to be cancelled before returning, the process manager will not allow thread termination to proceed until all I/Os have been cancelled. As a result, if a driver fails to cancel an IRP, the process and thread object will remain active until the system shuts down.

Note: Only IRPs for which a driver sets a cancel routine are cancelable. The process manager waits until all I/Os associated with a thread are either cancelled or completed before deleting the thread.

# I/O completion parts

Writing a high-performance server application requires implementing an efficient threading model. Having either too few or too many threads to process client requests can lead to problems. For example, if a server creates a thread to handle all requests, clients can become starved because the server will be tied up processing one request at a time. A single thread could simultaneously process multiple requests, switching from one to another as I/O operations are started. However, this architecture introduces complexity and can't take advantage of systems. The goal of a server is to have as few context switches as possible, and utilize the CPUs to their full capacity.

# The IoCompletion object

Applications use the IoCompletion object, which is exported to the system as a focal point for I/O. When a thread is given a packet from the completion port, it will go off and start the request, becoming an active thread. A thread will block many times during its processing, as it needs to read or write data to a file on disk or it synchronizes with other threads. Windows detects this activity and recognizes that the port has one less active thread. Therefore, when a thread becomes inactive it blocks, a thread waiting on the completion port will be awakened if there is a packet in the queue.

# Using completion ports

Figure 6-24 shows a high-level illustration of completion-port operation. A completion port is created with a call to the CreateCompletionPort API function. A thread that blocks on a port becomes active and is awakened in last, first out (LIFO) so that the thread blocked most is the one that is given the next packet. Threads that block for long periods of time can have their stacks swapped out to disk, if there are more threads associated with a port than there is work to process, the in-memory footprints of threads blocked are minimized.
