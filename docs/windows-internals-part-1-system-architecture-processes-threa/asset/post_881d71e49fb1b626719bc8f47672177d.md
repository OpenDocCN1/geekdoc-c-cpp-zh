The scheduler also has two special AdjustBoost events, which are part of the lock-ownership priority mechanism. These booths attempt to fix situations in which a caller that owns the priority x ends up releasing the lock to a waiting thread at priority < x. In this situation, the new owner thread must wait for its turn (if running at priority x), or worse, it might not even get to run at all if its priority is lower than x. This means the releasing thread continues its execution, though it should have caused the new owner to wake up and take control of the processor. The following two dispatcher events cause an AdjustBoost dispatcher event:

- An event is set by KeSetEventBoostPriority interface, which is used by the ERESOURCE reader-writer kernel lock.
- A gate is set by the KeSignalGate interface, which is used by various internal mechanisms when releasing gate lock.

## Unwait boosts

Unwait boosts attempt to decrease the latency between a thread waking up due to an object being signaled (thus entering the ready state) and the thread actually beginning its execution to process the unwait (thus entering the running state). Generally speaking, it is desirable that a thread wakes up from a waiting state be able to run as soon as possible.

The various Windows header files specify recommended values that kernel-mode callers of APIs such as KeReleaseMutex, KeSetEvent and KeReleaseSemaphore, which correspond to definitions such as MUTANT_INCREMENT, SEMAPHORE_INCREMENT, and EVENT_INCREMENT. These three definitions have always been set to 1 in the headers, so it is safe to assume that most unwaits objects result in a boost of 1. In the user-mode API, an increment cannot be specified, nor the native system calls such as NtEvent have parameters to specify a boost. Instead, when these APIs call the underlying Ke interface, they automatically use the default _INCREMENT definition. This is also the case when mutexes are abandoned or reset due to a system change: The default boost that would normally have been applied when the mutex would have been released. Finally, the APC boost is completely up to the caller. I/O completion.

> Note: Some dispatcher objects don't have boosts associated with them. For example, when a timer is set or expires, or when a process is signaled, no boost is applied.

All these boosts of 1 attempt to solve the initial problem by assuming that both the releasing and waiting threads are at the same priority. By boosting the waiting thread by one priority level, the waiting thread should preempt the releasing thread as soon as the operation completes. Unfortunately, on uniprocessor systems, if this assumption does not hold, the boost might not do enough. For example, if the waiting thread is at priority 4 and the releasing thread is at priority 8, waiting at priority 5 won't do reduce latency and force preemption. In multiprocessor systems, however, due to the stealing and balancing algorithms, this higher-priority thread may have a better chance of getting picked up by another logical processor. This is due to a design choice made in the initial NT architecture, which is not to track ownership (a few locks). This means the scheduler can't be sure really owns an event and it's really being used as a lock. Even with lock-ownership tracking, ownership is not usually passed (to avoid convoy issues) other than in the executive resource cache, explained in an upcoming section.

For certain kinds of lock objects that use events or gates as their underlying synchronization object, the lock-ownership boosts the dilemma. Also, on a multiprocessor machine, the ready thread might get picked up on another processor (due to the processor-distribution and load-balancing schemes you'll see later), and its high priority might increase the chances of it running on second-processor.

## Priority boosting after I/O

Other differences between lock-ownership and await boost will be exposed in the next section. Chapter 6 shows the mechanism of I/O completion in depth. For example, the important detail is that the kernel implements the code IoCompleteRequest through the use of either an APC (for asynchronous I/O) or an event (for synchronous I/O). When a driver passes in—for example, IO_DISK_INCREMENT to IoCompleteRequest for an asynchronous read—the kernel calls InsertQueueApc with the boost parameter. In turn, when the thread's wait is broken by the APC, it receives a boost of 1.

Be aware the boost values given in Table 4-3 are merely recommendations by Microsoft. Driver developers are free to ignore them, and certain specialized drivers can use their own values. For example, a driver handling ultrasound from a media device, which must use a user-mode visualization of new data, would probably use a boost value of 8 as well, to satisfy the latency as a sound card.

### TABLE 4-3 Recommended boost values

| Device | Boost |
| :--- | :--- |
| Disk, CD-ROM, parallel, video | 1 |
| Network, mailslot, serial | 2 |
| Keyboard, mouse | 6 |
| Sound | 8 |

## Boost during waiting on executing resources

When a thread attempts to acquire an exclusive resource (RESOURCE; see Chapter 8 in Part 2 for more information on kernel-synchronization objects) that is already owned exclusively by another thread, it must enter a wait state until the other has released the resource. To limit the risk of deadlocks, the execute performs waits in this intervals of 500 ms instead of doing an infinite wait on the resource.
