
Scenarios are hardcoded, and SuperFetch manages them through the NtSetSystemInformation and NtQuerySystemInformation APIs. For SuperFetch pulls, a special information class, SystemSuperFetchInformation, is used to control the kernel-mode components and generate requests such as starting, ending, and querying a scenario or associating one or more traces with a scenario.

Each scenario is defined by a plan file, which contains, at minimum, a list of pages associated with the scenario. Page priority values are also assigned according to rules (described next). When a scenario starts, the scenario manager is responsible for the event by generating the list of pages that should be brought into memory and at which priority.

## Page priority and rebalancing

You've already seen that the memory manager implements a system of page priorities to define which standby pages will be repurposed for a given operation and in list a given page will be inserted. This mechanism provides benefits when processes and threads have associated priorities—for example, ensuring that a defragmenter process doesn't pollute the standby page list and/or pages from an interactive foreground process. But its real power is unleashed without SuperFetch's page-prioritization schemes and rebalancing, which don't require manual application input or hardcoded knowledge of process importance.

SuperFetch assigns page priority on an internal score it keeps for each page, part of which is based on frequency-based usage. This usage counts how many times a page was used in given time intervals, such as hour, day, or week. The system also keeps track of time of use, recording how long it's been since a page comes from access. Finally, such data from where this page comes from (which list) and other access patterns are used to compute this score.

The score is translated into a priority number, which can be from 1 to 6. (A priority 7 is used for another purpose, described later.) Going down each level, the lower standby page priorities are repurposed first, as shown in the "Prioritized standby lists". Priority 5 is typically used for normal applications, while priority 1 means for background applications that third-party developers can mark as such. Finally, priority 6 is used to keep a number of high-importance pages as far away from repurposing. The other priorities are a result of the score associated with each page.

Because SuperFetch "learns" a user's system, it can start from scratch with no historical data and slowly build an understanding of the difference pages accessed by the user. This would result in a significant learning curve whenever a new application, or service pack was installed. By using an internal tool, Windows can pre-train SuperFetch to capture SuperFetch data and turn it into prebuilt traces. These prebuilt traces contain access and patterns that all users will probably encounter, such as clicking the Start menu, opening Control Panel, or using the File/Save dialog box. This data was saved to history files (which ship as Sysmain.dll) and is used to prepare the special priority 7 list. This list is the most critical data and is rarely repurposed. Pages at priority 7 are pages kept in memory even after the process has exited and even across reboots (being repopulated at the next boot). Finally, pages with priority 7 are static, in that they are never reprioritized, and SuperFetch never dynamically load pages of priority 7 other than the static pretrained.

The prioritized list is loaded into memory (or prepopulated) by the rebalancer, but the actual act of rebalancing is handled by both SuperFetch and the memory manager. As shown, the prioritized standby list mechanism is internal to the memory manager, and decisions on which pages to throw out and which to protect are innate, based on the priority number. The rebalancer does not by manually rebalancing memory but by reprioritizing it, which causes the memory manager to perform the needed tasks. The rebalancer is also responsible for reading the actual pages from disk, if needed, so that they are present in memory (prefetching). It assigns the priority that is mapped by each agent, and the memory manager ensures that the page is treated according to its importance.

The rebalancer can take action relying on any other agents—for example, if it notices that the distribution of pages paging lists is suboptimal or the number of repurposed pages across different priority levels is detrimental. The rebalancer can also trigger-trimming, which might be required for creating an appropriate budget of pages that will be used for SuperFetch prepopulated cache data. The rebalancer will typically cache low-utility pages—such as those that are already marked as low priority, that are zeroed, or that have value content but not in any working set and have unused—and build a more useful set of pages in memory, given the budget it has allocated itself. After the rebalancer has decided which pages to bring into memory and at what priority level they need to be (as well as which pages can be thrown out), it performs the required disk reads to prefetch them. The memory consumption by prefetching is backed by standby pages. As described in the discussion of page dynamics, standby memory is available memory because it can be repurposed as free memory for any allocator at time. In other words, if SuperFetch is prefetching the wrong data, there is no real impact on the user because memory can be reused and doesn't consume resources.

Finally, the rebalancer also runs periodically to ensure that pages it has marked as high priority have actually been used recently. Because these pages will rarely (sometimes never) be repurposed, it is important not to waste them on data that is rarely accessed but may have appeared to be frequently accessed during a certain period. If such a situation is detected, the rebalancer runs again to push those pages down in the priority lists.

A special agent called the application launch agent is involved in a different kind of prefetching mechanism, which attempts to predict application launches and builds a Markov chain that describes the existence of other application launches within a time segment. These segment are divided across periods of time roughly 6 hours—morning, noon, evening, and night—by weekday or weekend. For example, if on Saturday and Sunday evening a user typically launches after launched Word, the application launch agent will likely prefetch Outlook based on the high probability of it running after Word during weekend evenings.

Because systems today have sufficiently large amounts of memory—on average more than 2 GB (although SuperFetch works well on low-memory systems, too)—the actual amount of memory that frequently used processes on a machine need resident for optimal performance ends being a manageable subset of their entire memory footprint. Often, SuperFetch can fit all the pages into RAM. When it can't, technologies such as ReadyBoost and ReadyDrive can prevent further disk usage.

## Robust performance

A final performance-enhancing functionality of SuperFetch is called robustness, or robust performance. This component—managed by the user-mode SuperFetch service but ultimately implemented in the kernel (PF routines)—watches for specific file I/O access that harm system performance by polluting the standby lists with unused data. For example, if a process were to copy a large file across the system, the standby list would be populated with the file's contents, even though that file might never be accessed again (or not for a long period of time). This would throw out other data within that priority—and if this was an interactive and useful program, changes to its priority would be at 5.

SuperFetch responds to two kinds of I/O access patterns:

- **Sequential file access**: With this type of I/O access pattern, the system goes through all the data in a file.
- **Sequential directory access**: With this type of I/O access, the system goes through every file in a directory.

When SuperFetch detects that a certain amount of data past an internal threshold has been populated in the standby list as this kind of access, it applies aggressive deprioritization (robustion) to the pages being used to map this file. This occurs within the targeted process only as penalize other applications. These pages, which are said to be robust, essentially reprioritized to priority 2.

Because this component of SuperFetch is reactive and not predictive, it does some time for the robust to keep track of this process for the next time it runs. Once SuperFetch has determined that this process always performs this kind of sequential access, it remembers this and robust files as soon as they're remapped instead of waiting for the reactive behavior. At this point, the entire process is now considered robust for future access.

Just by applying this logic, however, SuperFetch could potentially hurt many legitimate applications or user scenarios that perform sequential access in the future. For example, by using the Sysintern Strings.exe you can look for a string in all executables that are part of a directory. If there are many files, SuperFetch would likely perform robustness. Next time you run Strings with a different search pattern, it would run just as slowly as the first time you'd expect it to run much faster. To prevent this, SuperFetch keeps a list of processes that it watches into the future, as well as an internal hard-coded list of exceptions. If a process is detected to later re-access robust files, robustness is disabled on the process to restore to the expected behavior.
