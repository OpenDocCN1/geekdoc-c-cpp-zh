+   If the process is triggered or an JIT engine enabled to allocate executable memory, the corresponding bits will be set to (1, 1), meaning that all memory is considered a valid call target.

+   For 32-bit applications, the expected call target is __stdcall1 (calling convention), but an attacker can change the indirect call target to __cdec1 (C calling convention), the stack will become corrupt, as the C function will not perform cleanup of the caller's arguments, unlike a standard call function. Because CFG cannot differentiate between the different calling conventions, this results in a corrupt stack, potentially with an attacker-controlled return address, bypassing CFG mitigation.

+   Similarly, compiler-generated jmp/longjmp calls behave differently from true indirect calls. CFG cannot differentiate between the two.

+   Certain indirect calls are harder to protect, such as the Import Address Table (IAT) or Delay-Load Address Table, which is typically in a read-only section of the executable.

+   Exported functions may not be desirable indirect function calls.

Windows 10 introduces advancements to CFG that address all these issues. The first is to introduce a new flag to the VirtualAlloc1c function called PAGE_TARGETS_INVALID and one to VirtualProtect that allocate executable memory will not see all their allocations' set to the (1, 1) state. They must manually call the ProcessValidCallTargets function (which calls the NetSetInformationVirtualMemory function), which may allow them to specify the actual function targets of their Jitted code. Additionally, this function is marked as a suppressed call with DELSPEC_GUARD_SUPPRESS, making sure that attackers cannot use an indirect CALL or JMP to redirect into it, even its function (Because it is an inherently dangerous function, calling it with a controlled stack or registers could result in the bypassing of CFG).

Next, CFG changes the default flow in the beginning of this section with a more refined flow. In this, the loader does not implement a simple "verify target, return" function, but rather a "verify target, call stack, check return" function, which is used in a subset of places on 32-bit applications (and/or running under WoW64). This improved flow is shown in Figure 7-32.

Next, CFG adds additional tables inside the executable, such as the Address Taken IAT table and the Long Jump Address table. When longjmp and IAT protection are enabled in the compiler, these tables are used to store addresses for these specific types of indirect calls, and the relevant functions are not placed in the regular function table, therefore not figuring in the bitmap. This means that if code is attempting to jump/call to one of these functions, it will be treated as an illegal transition. Instead, the Runtime and linker will validate the targets of, say, the longjmp function, by manually checking this. Although it is more efficient than a bitmap, there should be little to no in these tables, making the cost bearable.

Finally, improved CFG includes a feature called export suppression, which must be supported by the compiler and enabled by process-mitigation policy. (See the section "Process-mitigation policies" for more on process mitigations.) With this feature enabled, a new bit is implemented (called listed has (0, 1) as an undefined state). This state indicates that the function is valid export-suppressed, and it will be treated differently by the loader.
