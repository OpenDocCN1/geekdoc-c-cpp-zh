
These results depend on whether they been linked with the /LARGEADDRESSWARE. Had it not been, the results would have been about 2 GB for each. Sixty-four-bit applications linked without /LARGEADDRESSWARE constrained to the first 2 GB of the process virtual address space, just like 32-bit applications. (This flag is set by default in Visual Studio for 64-bit builds.)

## x64 virtual addressing limitations

As discussed, 64 bits of virtual address space allow for a possible maximum of 16 EB of memory — a notable improvement over the 4 GB offered by 32-bit addressing. Obviously, neither today's computers nor tomorrow's are close to requiring support for that much memory.

Accordingly, to simplify chip architecture and avoid unnecessary—particularly in address translation (described later)—AMD’s and Intel’s current x64 processors implement only 256 TB of virtual address space. That is, only the lower-order 48 bits of a 64-bit virtual address are implemented. However, virtual addresses are 64 bits wide, occupying 8 bytes in registers or when stored. The high-order 16 bits (bits 48 through 63) must be set to the same value as the highest-order implemented bit (bit 47), in a manner similar to sign extension in two's complement arithmetic. An address that conforms to this rule is said to be a canonical address.

Under these rules, the half of address space starts at 0x0000000000000000 as expected, but ends at 0x00FFFFFFFFFFFFFF. The upper half of the address space starts at 0xFF80000000000000 and ends at 0FFFFFFFFFFFFFFFFFF. Each canonical region is 12 TB. As newer processors implement more of the address bits, the lower half of memory will expand upward toward 0xFFFFFFFFFFFFFF, while the upper half will expand downward toward 0x8000000000000000.

## Dynamic system virtual address space management

Thirty-bit versions of Windows manage the system address space through a kernel virtual allocator, described in this section. 64-bit versions of Windows have no need to use the allocator for virtual address space management (and thus bypass the cost) because each region is statistically defined (refer to Figure 5-13).

When the system initializes, the MiInitializeVirtual function sets up the dynamic ranges and sets the available virtual images to available kernel space. It then initializes the space for boot loader images, process space (heap), and the HAL with the MiInitializeSystemVaRange function, which is used to set hard-coded address ranges (on 32-bit systems only). Later, when non-pooled pool is initialized, this function is used to reserve the virtual address ranges for it. Finally, when a driver loads, the address range is released to a driver-image range instead of a boot-loaded range.

After this point, the rest of the system virtual address space can be dynamically requested and released through MiAllocateVa (and an analogous MiAllocateInSession and MiReturnSystemVa). Operations such as expanding the system cache, the PTEs, non-pooled pool, pooled pool, and/or special pool; mapping memory with pages, creating the PFN database; and creating a new session all result in dynamic virtual address allocations for a specific region.

Each time the kernel virtual address allocator obtains virtual memory ranges for a certain type of virtual address, it updates the MiSystemVaType array, which contains the virtual address type for the newly allocated address. The values that can appear in MiSystemVaType are shown in Table 5-8.

### 5-8 System virtual address types

| Region | Description | Limitable |
|---|---|---|
| MiVaused (0) | Unused | N/A |
| MiVaSessionSpace (1) | Addresses for session space | Yes |
| MiVaProcessSpace (2) | Addresses for process address space | No |
| MiVaLoaded (3) | Addresses for images loaded by the boot loader | No |
| MiVaPfnDatabase (4) | Addresses for the PFN database | No |
| MiVaNonPagedPool (5) | Addresses for the non-paged pool | Yes |
| MiVaPagedPool (6) | Addresses for theaged pool | Yes |
| MiVaSpecialPoolPaged (7) | Addresses for the special pool (paged) | No |
| MiVaSystemCache (8) | Addresses for the system cache | No |
| MiVaPtes (9) | Addresses for system PTEs | Yes |
| MiVaHal (10) | Addresses for the HAL | No |
| MiVaGlobalSpace (11) | Addresses for session global space | No |
| MiVaDriverImages (12) | Addresses for loaded images | No |
| MiVaSpecialPoolNonPaged (13) | Addresses for the special pool (non-paged) | Yes |
| MiVaSystemPtesLarge (14) | Addresses for large page PTEs | Yes |

Although the logic to dynamically reclaim virtual space on demand allows better management of virtual memory, it would be useless without the ability to free this memory. As such, when the paging pool or system cache can be shrunk, or special pool and large page mappings are freed, the associated virtual address is freed. Another case is when the boot registry is released. This dynamic management of memory depends on each component. Additionally, components can reclaim memory through ReclaimSystemVa, which requests virtual addresses associated with the system cache to be freed (through the dereference segment thread) if virtual address space has dropped below 128 MB. Reclaiming can be satisfied if initial non-paged pool has been freed.

In addition to proportion and better management of virtual addresses dedicated to different kernel consumers, the dynamic virtual address allocator has advantages when it comes to memory footprint. Instead of manually pre-allocate static entries and page tables, paging-related structures are allocated on demand. On both 32-bit and 64-bit systems, this reduces boot-time usage because unused addresses won't have their page tables. It also means that on 64-bit systems, the address space regions that are reserved don't need to have their page tables in memory. This allows them to have arbitrarily large limits, especially on systems that have physical RAM to back the paging structures.
