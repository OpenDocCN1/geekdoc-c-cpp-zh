When an image is loaded, the system selects an image offset valid for the current base. This offset is selected from a bucket of 256 values, all of which are 64 KB aligned.

# Image randomization

For executables, the load offset is computed by a delta value each executable is loaded. This is a pseudo-random 8-bit number from 0x10000 to 0xFE000; by taking the current process's timestamp counter (TSC), shifting it by four places, and performing a division module 254 and adding 1. This number is multiplied by the allocation granularity of 64 KB discussed earlier. By adding 1, the memory manager ensures that the value can never be 0, so executables will never load at the address in the PE header if ASLR is used. This delta is added to the executable's preferred load address, creating one of 256 possible locations within 16 MB of the image address in the PE header.

For DLLs, computing the load offset begins with a delta value each executable is loaded. This is a pseudo-random 8-bit number from 0x10000 to 0xFE000; by taking the current process's timestamp counter (TSC), shifting it by four places, and performing a division module 254 and adding 1. This number is multiplied by the allocation granularity of 64 KB discussed earlier. By adding 1, the memory manager ensures that the value can never be 0, so executables will never load at the address in the PE header if ASLR is used. This delta is added to the executable's preferred load address, creating one of 256 possible locations within 16 MB of the image address in the PE header.

For DLLs, computing the load offset begins with a system-wide value called the image bias. This is computed by InitializeRelations and stored in the global structure (MI_SYSTEM_INFORMATION) in MiState.Sections.ImageBias (MiImageBias variable in Windows 8.x). This value corresponds to the TSC when shifted and masked into an 8-bit value. There are 256 possible values on 32-bit systems; computations are done for 64-bit systems with more possible values as the address space is vast. Unlike executables, this is computed once per boot and shared across the system to allow DLLs to remain in physical memory relocated once. If DLLs were remapped at different locations, the code could not be shared. The loader would have to fix up addresses for each process. Each process using a DLL would have to have its own copy of the DLL in physical memory.

Once the offset is computed, the memory manager initializes a bitmap named ImageBase (MiImageBitmap variable in Windows 8.x). This bitmap is used to represent ranges from 0x50000000 to 0x78000000 for 32-bit systems (64-bit systems below), and each bit represents a 64 KB unit. Whenever the memory manager loads a DLL, the appropriate bit is set to mark its location in the system. When the same DLL is loaded again, the memory manager shares with the already relocated information.

As each DLL is loaded, the system scans the bitmap from top to bottom for free bits. The ImageBias value is used as a start index from the top to randomize the load across different boots. Because the bitmap will be entirely empty until the first DLL (which is always ntdll.dll), its load address can be easily calculated (64-bit systems have their own bias).

- 32 bit: 0x78000000-(ImageBias+NtdllSize64K) * 0x10000
- 64 bit: 0xFFFFFF00-(ImageBias+NtdllSize64K) * 0x1000

Each subsequent DLL will load in a 64 KB chunk. Because of this, if the address of ntdll.dll is known, the addresses of other DLLs could easily be computed. To mitigate this, the order in which DLLs are mapped by the Session Manager during initialization is also randomized with Smss.exe. Finally, if no free space is available in the bitmap (which would mean most of the region for ASLR is in use), the DLL relocation defaults to the executable code at a 64 KB chunk within 16 MB of its preferred address.

# Experiment: Calculating the load address of ntdll.dll

With what you learned in the previous section, you can calculate the load address of ntdll.dll with the kernel variables. The following calculation is done on a Windows 10 x86 system:

1. Start local kernel debugging.
2. Find the ImageBias value:
`1kd> ?ntstate`
Evaluate expression: -211337360 = 820879c0
`1kd> nt!mi_system_information sections.imagebias 820879c0`
0x6e
+0500 Sections
+00dc ImageBias

3. Open Explorer and find the size of ntdll.dll in the System32 directory. In this system, it's 1547 KB = 0x182c00, so the size in 64 KB is 0x19 (always rounding up). The result is 0x78000000-(0x6E+0x19)*0x100000 = 0x77799000.

4. Open Process Explorer, find any process, and look at the load address (in the Base columns) of ntdll.dll. You should see the same value.

5. Try to do the same for a 64-bit system.

# Stack randomization

The next step in ASLR is to randomize the location of the initial thread stack and, subsequently, of each new thread. This randomization is enabled unless the StackRandomizationFlag was disabled for the process, and consists of first selecting one of 32 possible stacks separated by either 64 KB or 256 KB. You select this base address by finding the first appropriate memory region and then choosing the xt value where x is generated based on the current processor's TSC shifted and masked into a 5-bit value (this allows for 32 possible locations).

When this base address is selected, a new TSC-derived value is calculated—this one 5 bits long. The value is multiplied by 4 to maintain alignment, which means it can be as large as 2,048 bytes (half a page). It is added to the base address to obtain the final stack base.

# Heap randomization

ASLR randomizes the location of the initial process heap and subsequent heaps when created in user mode. The RtlHeap function uses another pseudo-random TSC-derived value to determine the base address of the heap. This value, 5 bits, is multiplied by 64 KB to generate the final base address, starting at 0, giving a possible range of 0x00000000 for the initial heap. Additionally, the range heap base address is manually deallocated to force an access violation if an attack is a brute-force sweep of the entire heap address range.
