# Windows 10 and Win32k.sys

The basic window-management requirements for Windows 10–based devices vary considerably depending on the device in question. For example, a full desktop running Windows needs all the window manager’s capabilities, such as resizable windows, owner windows, child windows and so forth. Windows Mobile 10 running on phones or tablets doesn’t need many of these features because there’s only one window in the foreground and it be minimized or resized. The same goes for IoT devices, which may not even have a display at

For reasons, the functionality of Win32k.sys has been split among several kernel modules that not all modules may be required on a specific system. This significantly reduces the attack surface of the window manager by reducing the complexity of the code and eliminating any of its legacy pieces. Here are some examples:

+   - On phones (Windows Mobile 10) Win32k.sys loads Win32kMin.sys and Win32kBase.sys.

+   - On full desktop systems Win32k.sys loads Win32kBase.sys and Win32kFull.sys.

+   - On IoT devices, Win32k.sys might only need Win32kBase.sys.

Applications call the standard USER functions to create user-interface controls, such as windows and buttons, on the display. The window manager communicates these requests to the GDI, which passes them to the graphics drivers, where they are formatted for the display device. A display driver is paired with a miniport driver to complete video display support.

The GDI provides a set of two-dimensional functions that let applications communicate with graphics without knowing anything about the devices. GDI functions mediate between applications and graphics devices as display drivers and printer drivers. The GDI interprets application requests for graphic output and sends the requests to graphics drivers. It also provides a standard interface for applications to use graphics output devices. This interface enables application code to be independent of the hardware and drivers. The GDI tailors its messages to the capabilities of the device, often dividing the request into manageable parts. For example, some devices can understand directions to draw an ellipse; others require the GDI to interpret the command as a series of pixels placed at certain coordinates. For more information about the graphics and video driver architecture, see the "Design Guide" of "Display (Adapters and Monitors)" chapter in the WDK.

Because of the subsystem—in particular, display I/O—runs in kernel mode, only a few Windows functions result in sending a message to the Windows subsystem process: process and thread creation and DOS device drive letter mapping (such as through subst.exe).
