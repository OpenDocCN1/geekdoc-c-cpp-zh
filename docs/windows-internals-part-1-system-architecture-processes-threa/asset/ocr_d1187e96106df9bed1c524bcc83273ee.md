Windows makes impersonation available through several mechanisms. For example, if a server communicates with a client through a named pipe, the server can use the ImpersonateNamedPipeClient to tell the SRM it wants to impersonate the user on the other end of the pipe. If the server is communicating with the client through Dynamic Data Exchange (DDE) or RPC, it can make similar impersonation requests using DDeImpersonateClient and RpcImpersonateClient. A thread can create an impersonation token that simply a copy of its process with the ImpersonateSelf function. The thread can then alter its impersonation token, perhaps to disable SIDs or privileges. A Security Support Provider Interface (SSPI) package can impersonate its clients with ImpersonationContext. SSPI implement a network authentication protocol such as LAN Manager version 2 or Kerberos. Other interfaces such as COM expose impersonation through APIs of their own, such as CoCreateClient.

After the server finishes it reverts to its primary security context. These forms of impersonation are convenient for carrying out specific actions at the request of a client and for ensuring that objects are audited correctly (For example, the audit that generates the identity of the impersonated client rather than that of the server). The disadvantage to these forms of impersonation is that they cannot access files or printers unless is a delegation-level impersonation (described shortly) and has sufficient credentials to authenticate the remote machine, the file or printer supports null sessions. (A null session is one that results from an anonymous token.)

If an entire application must execute in a client security context or access network resources without impersonation, the client must be logged on to the system. The LogonUser API function enables this action. LogonUser takes an account name, a password or computer name, a logon type (such as interactive, batch, or service), and login input, and returns a primary token. A server can adopt the token as an impersonation token, or the server can start a program that has the client's credentials as its primary token. From a security standpoint, a process created using the token returned from an interactive login via LogonUser, such as with the CreateProcess API, looks like a program starts logging onto the machine interactively. The disadvantage to this approach is that a server must obtain the user's account name and password. If the server transmits this information over the network, the server must encrypt it securely so that a malicious user sniffing traffic cannot capture it.

To prevent the misuse of impersonation, Windows does not let server impersonation without a client's consent. A client process can limit the level of impersonation by specifying a security quality of service (SQOS) when connecting to the server. For instance, when opening a named pipe, a process can specify SECURITY_ANONYMOUS, SECURITY_IDENTIFICATION, SECURITY_IMPERSONATION, or SECURITY_DELEGATION flags for the Windows CreateFile function.
