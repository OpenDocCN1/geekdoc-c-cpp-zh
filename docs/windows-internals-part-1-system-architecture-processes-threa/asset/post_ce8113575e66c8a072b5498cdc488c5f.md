
- 4. The last step that is required to “activate” the enclave is achieved with the InitializeEnclave function. At that point, code that was configured to execute within the enclave can start executing.
- 5. Unfortunately, executing the code in the enclave is not wrapped by the API. Direct use of assembly language is required. The ENTER instruction forces execution to the enclave and the EXIT instruction returns to the calling function. Abnormal termination of the enclave is also possible with Asynchronous Enclave Exit (AEX), such as a fault. The exact details are beyond the scope of this book, as they are not Windows-specific. Consult the SGX document to get the final details.
- 6. Finally, to destroy the enclave, a normal VirtualFree (Ex) function can be used on the pointer to the enclave obtained in CreateEnclave.

## Memory initializations

During boot, Winload (the Windows Boot Loader) calls Os1EnclavePageRegions, which first checks if SGX is supported by the CPUID. If it is, it issues instructions to enumerate Enclave Page Cache (EPC) descriptors. EPC is the protected memory provided by the processor for paging and enclaves. For each enumerated EPC, Os1EnclavePageRegions calls Mm-AddEnclavePageEnclaveMemory to add the page range to a sorted list of memory descriptors of type Loader_PARAMETER_BLOCK This list is eventually stored in the MemoryDescriptorListHeader of the LOADER_PARAMETER_BLOCK structure used to pass information from the boot loader to the kernel.

During phase 1 initialization, the memory manager CreateEnclaveRegions is called to create an AVL tree for the discovered enclave regions (allowing lookups when needed); the tree is stored in the MiState.Hardware.Enclave data. The kernel obtains a new enclave page list, a special flag to InsertPageFreeOrZeroList enables functionality to utilize this list. However, since the memory manager has no list of identifiers (3 are used for a maximum of 8 values, all taken), the kernel actually identifies these pages as “bad” pages currently suffering an in-page error. The memory manager never uses bad pages, calling enclave pages “bad” from being used by normal memory management operations, and so such pages end up in the bad page list.

## Enclave construction

The CreateEnclave API ends calling NtCreateEnclave in the kernel. As noted, a SECS structure must be passed in, designed by Intel SGX in Table 5-24.

NtCreateEnclave first checks if memory enclaves are supported by looking at the AVL tree (not by using the CPUID instruction). It creates a copy of the passed-in structure (as is usual for kernel functions obtaining data from user) and attaches to the target process (KeStackAttachProcess) if the enclave is created in a different process than the caller’s. Then it transfers control to MiCreateEnclave to begin the actual work.

## TABLE 5-24 SECS structure layout

| Field | Offset (bytes) | Size (bytes) | Description |
| --- | --- | --- | --- |
| SIZE | 0 | 8 | Size of enclave in bytes; must be power of 2 |
| BASEADR | 8 | 8 | Enclave base address must be naturally aligned to size |
| SSFRAMISE | 16 | 4 | Size of one SSA frame in bytes (including XSAVE, pad, GPR, and MISC) |
| MRSIGNER | 128 | 32 | Measurement register extended with the public key that verified the enclave. See SIGSTRUCT for proper format |
| RESERVED | 160 | 96 | Product ID of enclave |
| ISVPROID | 256 | 2 | Security version number (SVN) of the enclave |
| ISVSN | 258 | 2 | Enclave identifier |
| EID | Implementation dependent | 8 | Padding pattern from the signature (used for key derivation strings) |
| PADDING | Implementation dependent | 352 | |
| RESERVED | 260 | 3836 | Includes EID, other non-zero reserved field and must-be-zero fields |

The first thing MiCreateEnclave allocates the Address Window Extension (AWE) information that A APIs also utilize. This is because of AWE functionality, an enclave allows user-mode application to directly access physical pages (that is, the physical pages that are EPC pages based on the detection described). Anytime a user-mode application has direct control over physical pages, AWE data structures and locks must be used. This data is stored in the AweInfo field of the EPROCESS structure.

Next, MiCreateEnclave calls MiAllocateEnclaveVAD to allocate an enclave-type VAD describing the virtual memory. This VAD has the VAD flag (as all VADs) but also an enclave flag, to differentiate it from a true VAD. Finally, as part of VAD allocation, this is where the user-mode address for enclave memory is (if not explicitly specified in the original CreateEnclave call).

The next step in MiCreateEnclave is to acquire an enclave page regarding the enclave size or initial commitment. This is because, by Intel's SGX documentation, all enclaves require at least a one-page control structure to be associated with them. MiGetEnclavePage is used to obtain the required allocation list described, and extracts one page as needed. The returned page is mapped using a system PTE stored as part of the enclave VAD; the MiInitializeEnclave function returns the related PFN data structure and marks it ActiveAndValid.

There are no actual bits that would help you differentiate enclave PFN from any other region of memory (such as non-paged pool). This is where the enclave AVL tree comes into play, and MI_PFN_IS_ENCLAVE is a function that the kernel uses whenever it needs to check if a PFN is indeed describing an EPC region.

With the PFN initialized, the system PTE is converted to a global kernel PTE, and its result-ing virtual address is computed. The final step in MiCreateEnclave is to call KeCreateEnclave, which will now do the low-level kernel creation steps, communicating with the actual SGX hardware implementation. One job that KeCreateEnclave is responsible for filling in the base address required by the SECS structure if the caller did not specify one, it must be set in the SECS structure before communicating with the SGX hardware to create an enclave.

## Loading data into an enclave

Once an enclave has been created, it's time to load information into it. The LoadEnclaveData function is exposed for that purpose. The function merely forwards the request to the underlying executive function, NtLoadEnclaveData. The function performs a combination of memory copy operation over virtualalloc attributes (such as page protection).

If the enclave created with CreateEnclave doesn't have any committed enclave pages, they must first be obtained, which will result in zero memory added to the enclave, which can then be filled with non-zero memory from outside the enclave. Otherwise, if an initial pre-committed initialization size was passed, then the enclave's pages can be directly filled in non-zero memory from outside of the enclave.

Because enclave memory is described by a VAD, may the traditional memory management APIs will function, at least partially, on this memory well. For example, calling Virtualalloc using NtAllocateVirtualMemory on an address with the MEM_COMMIT flag will result in MiCommitEnclavePages being called, which will validate that the protection for the new pages is compatible (i.e., a combination of read, write, and execute, without any special caching or writing flags), and then call MiAddPagesToEnclave, passing a pointer to the enclave VAD associated with the address range, the protection mask that was specified to Virtualalloc, and the PTE addresses that correspond to the virtual address range being committed.

MiAddPagesToEnclave checks if the VAD has any EPC pages associated with it, and if there are enough of them to satisfy the commit. If MiReserveEnclavePages is called to obtain a sufficient amount, MiReserveEnclavePages looks at the current enclave page list and counts the total. There aren't enough physical EPC pages provided by the processor (based on the information obtained at boot), the function fails. Otherwise, it calls MiGetEnclavePage in a loop for the required amount of pages.

For each PFN that is retrieved, it is linked to the PFN array in the enclave VAD. Essentially, this means that once an enclave PFN is removed from the enclave page list and into the enclave, into an active state, the enclave VAD acts as the list of active enclave PFNs.

Once the required committed pages have been obtained, MiAddPagesToEnclave translates the page post to LoadEnclaveData into its SGX equities. Next, it reserves the appropriate number of system PTEs to hold paging information for each EPC pages that will be required. With this information in hand, it will eventually call AddEnclavePage that calls the SGX hardware to do the actual page adding.
