Much of the additional code in the checked-built binaries is a result of the ASSERT and/or NT_ASSERT macros, which are defined in the WDK header file Wdm.h and documented in the WDK documentation. These macros test a condition, such as the validity of a data structure or parameter. If the expression evaluates to FALSE, macros either call the kernel-mode function RtAssert, call DbgPrint to send the text of the debug message to a message buffer, or issue an assertion interrupt, which interrupt 0xB on x64 and x86 systems. If a kernel debugger is attached and the appropriate samples are loaded, this message is displayed automatically by a prompt asking the user to doubt the assertion failure (breakpoint, ignore, terminate process, or terminate). If the system wasn't booted with the kernel debugger (using the debug option in the Boot Configuration Database) and no kernel debugger is currently attached, failure of an assertion test will bug-crash (crash) the system. For a small list of assertion checks made by some of the kernel support routines, see the section "Checked Built ASSERTs" in the WDK documentation (although this list is unmaintained and outdated).

The checked build is also useful for system administrators for the additional detailed information tracing that can be enabled for components. (For detailed instructions, see the Microsoft Knowledge Base Article number 31473, titled "HOWTO: Enable Verbose Debugging in Drivers and Subsystems") This output is sent to an internal debug message buffer using the DbgPrintEx function referred to. To view the debug messages, you can either attach a kernel debugger to the target system (which requires booting the target system in debug mode) using the !dbg while performing local kernel debugging, or use the DebugView.exe tool from Sysinternals. Most recent versions of Windows have moved away from this type of debug, however, and use a combination of Windows preprocessor (WPP) tracing or TraceLogging technology, both of which are built on top of Event Tracing for Windows (ETW). The advantage of these new logging mechanisms is that they are not so limited to the checked versions of components (especially useful now that a full checked build is longer available) and can be seen by using tools such as Windows Performance Analyzer (WPA), formerly known as XPerf or Windows Performance Toolkit, TraceView (from the WDK), or the !wmi print extension in the kernel debugger.

Finally, the checked build is also useful for testing user-mode code only because the system is different. (This is because of the additional checking taking place within the kernel and the fact that the components are compiled without optimizations). Often, multithread synchronization bugs are reduced to specific timing conditions. By running your tests on a system running the checked build (or at least the kernel and HAL), the fact that the timing of the whole system is different might cause latent bugs to surface that do not occur on a normal retail system.

# Virtualization-based security architecture overview

As you saw in Chapter 1 and in this chapter, the separation between user mode and kernel mode provides protection for the OS from user-mode code, whether malicious or not. However, if an unwanted piece of kernel-mode code makes it into the system (by some un-patched kernel or driver vulnerability or because the user is tricked into installing a malicious or vulnerable driver), the system is entirely compromised because all kernel-mode code has access to the entire system. The technologies outlined in Chapter 1, which leverage the hypervisor to provide additional guarantees against attacks, make up a set of virtualization-based security (VBS) capabilities, extending the processor's natural privilege-based separation through the introduction of Virtual Trust Levels (VTLs). Beyond simply sometimes introducing a new orthogonal way of isolating access to memory, hardware, and processor resources, VTLs also require new code and components to manage the levels of trust. The regular kernel and drivers, running in VTL 0, cannot be permitted to control and define VTL 1 resources; this would defeat the purpose.

With Windows 1607 and Server 2016 releases, it's always active by default if supported by hardware. For older versions of Windows 10, you can activate it by using a policy or with the Add Features dialog box (select the Isolated User Mode).

As shown in Figure 2-3, the user/kernel code discussed earlier is running on top of a Hyper-V hypervisor, just like in Figure 2-1. The difference is that with VBS enabled, a VTL of 1 is now present, which contains its own secure kernel running in the privileged processor mode (that is, ring 0 on x86/x64). Similarly, a run-time user environment mode, called the Isolated User Mode (IUM), now exists, which runs in unprivileged mode (that is, ring 3).

In this architecture, the secure kernel is its own binary, which is found under the name securekernel.exe on disk. It's both an environment that restricts the allowed system calls that regular user-mode DLLs can make (thus limiting which of these DLLs can be loaded) and a framework that adds special secure system calls that can execute only under VTL 1. These additional system calls are exposed in a similar way as regular system calls: through an internal system library named securedll.dll (the VTL 1 version of Ntdll.dll) and a Windows subsystem-facing library named secure.dll). This implementation, mostly sharing the same standard Win32 API libraries, allows for the reduction of the memory overhead of VTL user-mode applications because essentially the user-mode code is present in VTL 0 counters. As an important note, copy-on-write mechanisms, which you'll learn more about in Chapter 5, prevent VTL 0 applications from making changes to binaries used by VTL 1.

With VBS, the regular user kernel rules apply, but are now augmented by VTL considerations. In other words, kernel-mode code running at VTL 0 cannot touch user mode running at VTL 1 because VTL 1 is more privileged. Yet, user-mode code running at VTL 1 can touch kernel mode at VTL 0. A simple way to achieve this is as follows: privilege levels (user versus kernel) enforce power. VTLs, on the other hand, enforce isolation. Although a VTL 1 user-mode application is not more powerful than a VTL 0 driver, it is isolated from it. In fact, VTL 1 applications aren't just more powerful; in cases, they have much less. Because the secure kernel does not implement a full range of system calls, it backs whatever system calls it forwards to the VTL 0 kernel. (Another name for secure kernel is proxy kernel). Any kind of I/O, file, network, and registry-based, is completely prohibited. Graphics, as another example, are out of the question. Not a single driver is allowed to be communicated with.

The secure kernel however, by running at VTL 1 and being in kernel, does complete access to VTL 0 memory and resources. It can use the hypervisor to limit the VTL 0 OS to access certain memory locations by leveraging CPU support as Second Level Address Translation (SLAT). SLAT is the basis of Credential Guard technology, which can store secrets in such locations. Similarly, the secure kernel can use SLAT to intercept and control execution of memory locations, a key covenant of Device Guard.

To prevent normal device drivers from leveraging hardware devices to directly access memory, the system uses another piece of hardware known the I/O memory management unit (MMU), which effectively virtualizes memory access for devices. This can be used to prevent device drivers from using direct memory access (DMA) to directly access the hypervisor or secure kernel's physical regions of memory. This would bypass SLAT because no memory is involved.

Because the hypervisor is the first system to be loaded by the boot loader, it can grant the SLAT and I/O MMU as it sees fit, defining the VTL 0 and 1 execution environments. Then, while in VTL 1, the loader runs, loading the secure kernel, which can configure the system further to its needs. If the VTL is dropped, which will see the execution of the normal kernel, now living in VTL 0 jail, unable to escape.
