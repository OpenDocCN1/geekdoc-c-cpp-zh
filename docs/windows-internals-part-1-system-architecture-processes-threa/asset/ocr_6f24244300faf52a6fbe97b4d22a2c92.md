Here is the sequence of events as outlined in Figure 6-14:

+   1. A client application calls a Windows API such as ReadFile. Read calls the NtReadFile (in Ntdll.dll), which makes the thread transition to kernel mode to the executive NtReadFile (these steps have already been discussed in this chapter).

+   2. The I/O manager, in itsReadFile implementation, performs some sanity checks on the request, such as whether the buffer provided by the client is accessible with the right page protection. Next, the I/O manager locates the associated driver (using the file handle provided), allocates and initializes an IRP, and calls the driver in the appropriate dispatch routine (in this case, corresponding to the IRP_MJ_READ index) using IoCall1Driver with the IRP.

+   3. This is the first time the driver calls the IRP. This is usually invoked using the requesting thread; the only way for that not to happen is if an upper filter is held over to the IoCall1Driver from a different thread. For the sake of this discussion, we will assume this is not the case (and in cases involving hardware devices, this does not happen; even if there are upper filters, they do processing and call the lower driver immediately from the same thread). The dispatch routine callback in the driver has two tasks on its hand: first, it should perform more checking than the I/O manager because it has no idea what the request really means. For example, the driver could check if the buffer provided to a read or write is large enough; for a DeviceControl operation, the driver could check whether the I/O control provided is a supported one. If any check fails, the driver completes the IRP (IoCompleteRequest) with the failed status and returns immediately. If the checks pass OK, the driver calls its Start I/O routine to initiate the operation. However, if the hardware device is busy (handling a previous IRP), then the IRP is inserted into a queue managed by the driver and a STATUS_PENDING is returned without completing the IRP. The I/O manager caters for such a scenario with the IoStartPacket function, that checks a busy bit in the device object and if the device is busy, inserts the IRP into a queue (part of the device object structure). If the device is not busy, it sets the device as busy and calls the registered Start I/O routine (recall that there is a member in the driver object that would have been initialized in DriverEntry). Even if a driver chooses not to use IoStartPacket, it would still follow similar logic.

+   4. If the device is not busy, the Start I/O routine is called from the dispatch routine directly—meaning it's still the requesting thread that is making the call. Figure 6-14, shows that the Start I/O routine is called in an arbitrary thread context; this will be proven to be true in the general case when we look at the DPC routine in step 8.
