# # Heap security features

As the heap manager has evolved, it has taken an increased role in early detection of heap usage errors and in mitigating effects of potential-based exploits. These measures exist to lessen the security effect of potential vulnerabilities in applications. Both the NT-heap and the segment-heap implementations have multiple mechanisms that reduce the likelihood of memory exploitation.

The metadata used by the heaps for internal management is packed with a high degree of randomization to make it difficult for an attempted exploit to patch the internal structures to prevent crashes or conceal the attack method. These blocks are also subject to an integrity-check mechanism on the header to detect simple corruptions such as buffer overflows. The heap uses a small degree of randomization the base address of heap. By using the HeapSetInformation API with the Heap-EnableTerminationCorruption class, processes can operate in an automatic termination for detected inconsistencies avoiding executing unknown code.

As an effect of block metadata randomization, using the debugger to simply dump a block header as an area of memory is not useful. For example, the size of the block and whether it is busy is not easy to spot from a random sample. The dump applies to LFH blocks. They have a different type of metadata stored in the header, also partially randomized. To dump these details, the !heap -i command in the debugger does all the work to retrieve the metadata fields from a block, also flagging checksum or free-list inconsistencies if they exist. The command works for both LFH and regular heap blocks. If the current heap context were different, the decoding of the header would be incorrect. To set the proper context, the same !heap -i command with the heap handle as an argument must be executed.
