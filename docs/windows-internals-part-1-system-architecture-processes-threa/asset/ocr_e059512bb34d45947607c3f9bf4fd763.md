# Environment subsystems and subsystem DLLs

The role of an environment subsystem is to expose some subset of the base Executive system services to application programs. Each subsystem can provide access to different subsets of the native services in Programs. That means some things can be done from an application built on one subsystem that can't be done by an application built on another subsystem. For example, a Windows application can't use the SUA function.

Each executable (.exe) is bound to one and only one subsystem. When an image is run, the process creation code examines the subsystem code in the header so that it can notify the proper subsystem of the new type. This code is specified with the /SUBSY linker option (or the SubSystem entry in the Linker/System property page of the project's properties).

As mentioned, applications do not call Windows DLLs directly. Instead, they go through one or more subsystems which export the documented interface that the programs linked to that subsystem can call. For example, the Windows subsystems (such as Kernel32.dll, Advapi32.dll, User32.dll, and Gdi32.dll) implement the Windows API functions. The SUA subsystem (Psdll.dll) is used to implement the API functions (on Windows versions that supported POSIX).
