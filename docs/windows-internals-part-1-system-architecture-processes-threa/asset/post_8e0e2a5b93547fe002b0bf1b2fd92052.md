### Control Flow Integrity

Data Execution Prevention (DEP) and Arbitrary Code Guard (ACG) makes it hard for exploits to place executable code on the heap or stack, to allocate new executable code, or to change existing executable code. As a result, memory/data-attacks become much more interesting. Such attacks allow the modification of pointers to memory to redirect control flow, as modifying return addresses on the stack or indirect pointers stored in memory. Techniques such as return-oriented-programming (ROP) and jump-oriented-programming (JOP) are often used to violate the control flow of the program and redirect it to known locations of interesting code "gadgets".

Because such snippets are present in the middle or end of various functions, when control flow is redirected in this way, it must be restricted to the middle or end of a legitimate function. By employing Control Flow Integrity (CFI) technologies—which can, for example, validate the target of an indirect JMP or CALL instruction is the beginning of a real function, or that a RET instruction is pointing to an expected location, or that a RET instruction is issued after the function was entered through its beginning—the operating system and compiler can detect and prevent most classes of exploits.

### Control Flow Guard

Control Flow Guard (CFG) is an exploit-mitigation mechanism first introduced in Windows 8.1 Update 3 that exists in enhanced version in Windows 10 and Server 2016, with further improvements released on various updates (up to including the latest Creators Update). Originally implemented only for user-mode code, CFG also exists as Kernel CFG (KCFG) on the Creators Update. CFG addresses the indirect CALL/JMP part of CFI by verifying that the target of an indirect call is at the start of a known function (or momentarily). If the target is not at the start of a known function, the process is simply terminated. Figure 7-31 shows the conceptual operation of CFG.

![](img/ff0e6a9d867a3a6e9527eb1d946810fc_757_0.png)

FIGURE 7-31 Conceptual view of Control Flow Guard.

CFG requires the cooperation of a supported compiler that will add the call to the validation code before indirect changes in control flow. The Visual C++ compiler has an option, /guard:cf, that must be set for images (or even on a C++ source file) to be built with CFG support (this option is also available in Visual Studio's GUI for the C++/Generation/Control Flow Guard setting in the project's properties). This setting should also be set in the linker settings, as both components of Visual Studio are required to support CFG.

Once these settings are present, images (EXEs and DLLs) are compiled with CFG-enabled indicate in their PE header. In addition, they contain a list of functions that are the valid indirect control targets (by default merged by the linker in the .rddata section). This list is built by the linker and contains the relative virtual address (RVA) of all functions in the image. This includes those that might not be called by indirect by the code present in the image because there is no way of knowing if outside code does somehow legitimately know the address of a function and is attempting to call it. This is especially true for exported functions, which can be called after obtaining their pointer through GetProcAddress.

That being said, programmers can use a technique called CFG suppression, which is supported by the DECLSPEC_GUARD_SUPPRESS annotation, and which marks the function in the table of valid functions with a special flag indicating that the programmer never expects such a function to be the target of any indirect call or jump.

Now that a table of valid functions exists, all that simple function would need to do is compare the target of the CALL or JMP instruction with one of the functions in the table. Algorithmically, this would result in an O(n) algorithm, where the number of functions needed to check would be equivalent, in the worst case, to the number of functions in the table. Clearly, linearly scanning an array over every single indirect change in control flow would bring a program to knees, so operating system support is needed to perform CFG checks efficiently. We'll see in the next section how Windows can achieve this.

### The CFG bitmap

As we saw earlier, forcing the process to iterate through a list of function calls for every instruction would not be practical. Instead of an algorithm that requires linear time O(n), performance requirements dictate that an O(1) algorithm be used instead—one where constant lookup time should be used, regardless of how many functions are present in the table. This constant lookup time should be as small as possible. A clear winner of such a requirement would be an array indexable by the get-function's address, which is an indication of whether it is valid or not (such as a simple BOOL). With 128 TB of addresses, such an array would itself have to be 128 TB size(BOOL), which is an unacceptable storage size—bigger than the address space itself. How can we do?
