# TABLE 4-3 Recommended boost values

| Device | Boost |
| --- | --- |
| Disk, CD-ROM, parallel, video | 1 |
| Network, mailslot, named pipe, serial | 2 |
| Keyboard, mouse | 6 |
| Sound | 8 |

> Note You might intuitively expect better responsiveness from your video card or disk than boost of 1. However, the kernel is in fact trying to optimize for latency, to which some devices (as well as human inputs) are more sensitive than others. To give you an idea, sound cards data around 1 ms to play back music without perceptible glitches, while a video card needs to output at only 24 frames per second, or about every 40 ms, before the human eye can notice glitches.

As hinted, these I/O completion boosts rely on the wait boosts in the previous section. Chapter 6 shows the mechanism of I/O completion in depth. For example, the important detail is that the kernel implements the code in IoCompleteRequest API through the use of either an APC (for asynchronous I/O) or an event (for synchronous I/O). When a driver passes in—for example, IO_DISK_INCREMENT to IoCompleteRequest for an asynchronous disk read—the kernel calls KeInsertQueueApc with the boost parameter set. In turn, when the thread's wait is broken by the APC, it receives a boost of 1.

Be aware the boost values given in Table 4-3 are merely recommendations by Microsoft. Driver developers are free to ignore them, and certain specialized drivers can use their own values. For example, a driver handling ultrasound from a media device, which must use a user-mode visualization of new data, would probably use a boost value of 8 as well, to satisfy the latency as a sound card. In most cases, due to the Windows driver stack are built (again, see Chapter 6 for more information), driver developers often write minidrivers, which call into a Microsoft-owned driver that supplies its boost to IoCompleteRequest. For example, RAID or SATA controller developers call StorPortCompleteRequest to complete their requests. This does not have any parameter for a boost value, because the Storport.sys file driver in the right value when calling the kernel. Whenever any file system driver (identified by its device type to FILE_DEVICE_DISK_FILE or FILE_DEVICE_NETWORK_FILE_SYSTEM) requests its, a boost of IO_DISK_INCREMENT is always applied if the driver passed in IO_NO_INCREMENT (0) instead. This boost value has less of a relevance to I/O and more of a requirement enforced by the kernel.

# Boost during waiting on executing resources

When a thread attempts to acquire an exclusive resource (RESOURCE; see Chapter 8 in Part 2 for more information on kernel-synchronization objects) that is already owned exclusively by another thread, it must enter a wait state until the other has released the resource. To limit the risk of deadlocks, the execute performs waits in this intervals of 500 ms instead of doing an infinite wait on the resource.
