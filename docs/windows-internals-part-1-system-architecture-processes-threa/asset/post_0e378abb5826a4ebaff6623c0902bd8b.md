
If physical memory is full when a page fault occurs, Windows uses a replacement policy to determine which virtual page must be removed from memory to make room for the new page. Replacement policies include least recently used (LRU) and first in, first out (FIFO). The LRU algorithm (also known as the clock algorithm, as implemented in most versions of UNIX) privileges the virtual memory system to track when a page is in memory. When a new page is required, the page that has not been used for the greatest amount of time is removed from the system. The FIFO algorithm is somewhat simpler: it removes the page that has in physical memory for the greatest amount of time, regardless of how often it's been used.

Replacement policies can be further characterized as either global or local. A global replacement policy allows a page fault to be satisfied by any page frame, regardless of that frame is owned by another process. A global replacement policy using the FIFO algorithm would locate the page that has in memory the longest and would free it to satisfy a page fault. A local policy would limit its search for the oldest page of the set of pages already owned by the process that incurred the page fault. Beware that global replacement policies make processes vulnerable to the behavior of other processes. For example, an ill-behaved application can undermine the entire operating system by inducing paging activity in all processes.

Windows implements combinations of local and global replacement policies. When a working set reaches its limit and needs to be trimmed by demands for physical memory, the memory manager removes pages from working sets until it has determined there are free pages.

## Working set management

Every process starts with a default working set of 50 pages and a working set maximum of 345 pages. Although it has little effect, you can change these working set limits with the WindowsWorkingSetSize function, although you must have the increase scheduling priority (SeBasePriorityPrivilege) privilege to do this. Unless you have configured the process to use these limits, these limits are ignored. The memory manager will permit a process to grow beyond its maximum if it is paging and there is ample memory (Conversely the memory manager will shrink a process below its minimum if it is not paging and there is demand for physical memory on the system). You can set working limits using the SetWorkingSize function along with the QUOTA_LIMITS_HARDWARE_MAX_ENABLE flag, but it is always better to let the system manage your set.

On 32 bit systems, the working set size can't exceed the system-maximum capacity implemented at initialization time, stored in the MiMaximumWorkingSet kernel variable. On x64 systems, physical memory would be the upper limit, as the virtual address space is so vast.

When a page fault occurs, the process's working set limits and the amount of free memory on the system are examined. If conditions permit, the memory manager allows a process to grow to its working set maximum (or beyond if the process does not have a hard working set limit and there are enough free pages available). However, if memory is tight, Windows replaces rather adds pages in a working set when a fault occurs.

Windows attempts to keep memory available by writing modified pages to disk. Still, when modified pages are being generated at a very high rate, more memory is required to meet demands. Therefore, when physical memory is low, the working set manager, a routine that runs in the context of the balance set manager system thread (described in the next section), initiates automatic working set trimming to increase the amount of free memory available in the system. You can also initiate trimming of your process—for example, after process initialization—the Windows SetProcessWorkingSize function.

The working set manager examines memory and decides which, if any, working sets need to be trimmed. If appropriate, the working set manager calculates how many pages could be removed from working sets if needed. If trimming is needed, it looks at sets that are above their minimum setting. It also dynamically adjusts the rate at which it trims working sets and arranges the list of processes that are candidates to be trimmed in an optimal order. For example, processes with many pages that have not been accessed recently first; larger processes that have been idle are considered smaller processes that are running more often; the process running the foreground application is considered last; and so on.

When the working set manager finds processes that are using more than their minimums, it looks for pages to remove from the working sets, making the pages available for other users. If the amount of memory is still too low, the working set manager continues removing pages from processes' working sets until it achieves a minimum number of free pages on the system.

The working set manager tries to remove pages that haven't been accessed recently by checking the access bit in PTE to see whether a page has been accessed. If the bit is clear, the page is said to be aged. A count is incremented indicating that the page hasn't been referenced since the last working trim scan. Later, the age of pages is used to locate pages to remove from the working set.

If the hardware PTE accessed is set, the working set manager clears it and goes to examine the next page in the working set. In this way, if the access is clear the next time the working set manager examines the page, it knows that the page hasn't been accessed since the last time it was examined. This scan for pages remove continues through the working set list until either the desired pages have been removed or the scan has returned to the starting point. The next time the working set is trimmed, the scan picks up where it left off.

## EXPERIMENT: Viewing process working set sizes

You can use Performance Monitor to examine process working set sizes by looking at the performance counters shown in the following table. Other process viewer utilities (such as Task Manager and Process Explorer) also display the process working set size.

| Counter | Description |
|---|---|
| Process: Working Set | This notes the current size of the selected process's working set in bytes. |
| Process: Working Set Peak | This tracks the peak size of the selected process's working set in bytes. |
| Process: Page Faults/Sec | This indicates the number of page faults for the process that occur each second. |

You can also find the total of all processes working by selecting the _Total in the instance box in Performance Monitor. This process isn't real; it's simply a total of the process-specific for all processes currently running on the system. The total you see larger than the actual RAM being used, however, because the size of each process working set includes pages shared by other processes. Thus, if two or more processes share a page, the page is counted in each process's working set.
