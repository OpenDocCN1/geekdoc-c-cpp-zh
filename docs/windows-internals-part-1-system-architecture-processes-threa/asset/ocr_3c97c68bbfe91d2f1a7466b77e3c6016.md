+   3. If the process needs to be created protected, it also checks the signing policy.

+   4. If the process to be is modern, a licensing check is done to make it's licensed and allowed to run. If the app is inbox (preinstalled with Windows), it's allowed to run regardless of license. If sideloading apps is allowed (configured through the Settings app), then any signed app can be executed, not just from the store.

+   5. If the process is a Trustlet, the section object must be created with a special flag that allows the secure kernel to use it.

+   6. If the executable file specified is a Windows EXE, NtCreateProcess tries to open and create a section object for it. The object is not mapped into memory, but it is opened. Just because a section object has successfully created not mean the file is a Windows image, it could be a DLL or a POSIX executable. If the file is a POSIX executable, the call fails, because POSIX is no longer supported. If the file is a DLL, CreateProcessInternal fails as well.

+   7. Now NtUserProcess has found a valid Windows executable, as part of the process creation code in the next section, it looks in the registry under HKLM\SOFTWARE\Microsoft\NT\CurrentVersion\Image File Execution Options to see whether a subkey with the file name and extension of the executable image (but without the directory and path information—example, Notepad) exists. If it does, PspAllocate-Process looks for a named debugger for that. If this value is present, the image to be run becomes the string in that value and CreateProcessInternal restarts at stage 1.

> You can take advantage of this process-creation behavior and debug the startup code of Windows services before they start rather than attach the debugger after starting, which doesn't allow you to debug the startup code.

+   8. On the other hand, if the image is not a Windows EXE (for example, if it's an MS-DOS or a Win16 application), CreateProcessInternal goes through a series of steps to find a Windows support image to run it. This process is necessary because non-Windows applications aren't run directly. Windows uses one of a few special images that, in turn, are responsible for actually running the non-Windows process. For example, if you attempt to run an MS-DOS or a Win16 executable (32-bit Windows only), the image to run becomes the Windows executable Ntdvm.exe. In short, you can't directly create the activated image as a process that is not a Windows process. If Windows can't find a way to resolve the activated image (as shown in Table 3-8), CreateProcessInternal fails.
