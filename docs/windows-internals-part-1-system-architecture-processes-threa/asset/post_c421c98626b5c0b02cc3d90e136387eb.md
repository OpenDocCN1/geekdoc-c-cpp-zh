
## Priority boosts for multimedia applications and games

Although Windows' CPU-starvation priority boosts might be enough to get a thread out of abnormally long wait state or priority deadlock, they simply cannot deal with the resource requirements imposed by a CPU-intensive application such as Windows Media Player or a 3D game.

Skipping and other audio glitches have long been a common source of irritation among Windows users. The Windows user-mode audio stack exacerbates this because it offers even more chances for preemption. To address this, this client version of Windows uses the MMCSS driver (described earlier in this chapter), implemented in %SystemRoot%\System32\Drivers\MMCSS.sys. Its purpose is to glitch-free multimedia playback for all applications that register with it.

> Note Windows 7 implements MMCSS as a service (rather than a driver). This posed a potential risk, however. If the MMCSS managing thread blocked for any reason, the threads managed by it would retain their time-priority, potentially causing system-wide starvation. The solution was to move the code to the kernel where managing the thread (and other resources used by MMCSS) could not be touched. There are other benefits to being a kernel driver, such as holding a direct pointer to process and thread objects rather than IDs or handles. This bypasses searches based on IDs and faster communication with the scheduler and Power Manager.

Client applications can register with MMCSS by calling AvSetThreadCharacteristics with a task name that must match one of the subkeys under HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Multimedia\SystemProfile\Tasks. (The list can be modified by OEMs specific tasks as appropriate.) Out of the box, the following tasks exist:

- Audio
- Capture
- Distribution
- Games
- Low Latency
- Playback
- Pro Audio
- Window Manager

Each of these tasks includes information about the properties that differentiate them. The most important one for scheduling is called the Scheduling Category, which is the primary factor determining the priority of threads registered with MMCSS. Table 4-4 shows the various scheduling categories.

## TABLE 4-4 Scheduling categories

| Category | Priority | Description |
| --- | --- | --- |
| High | 23–26 | Audio threads running at a higher priority than any other thread on the system except for critical system threads |
| Medium | 16–22 | The threads of a foreground application such as Windows Media Player |
| Low | 8–15 | All other threads that are not part of the previous categories |
| Exhausted | 4–6 | Threads that have exhausted their share of the CPU and continue running if no lower-priority threads are ready to run |

The main mechanism MMCSS boosts the priority of threads inside a registered process to the priority level matching its scheduling category and relative priority within this category for a guaranteed period. It lowers then threads to the exhausted category so that other, non-multimedia threads on the system can also get to execute.

By default, multimedia receives 80 percent of the CPU time available, while other threads receive 20 percent. (Based on a sample of 10 ms, that would be 8 ms and 2 ms, respectively.) You can change this percentage by modifying the SystemResponsiveness value under the HKLM\SOFTWARE\Microsoft\Windows\Multimedia\SystemProfile key. The value can range from 10 to 100 percent (20 is the default; setting a value lower than 10 evaluates to 0), which changes the CPU percentage guaranteed to the system (not the registered audio apps). MMCSS scheduling thread runs around priority 27 because they cannot prevent any Pro Audio threads to lower their priority to the exhausted category.

As discussed, changing the relative priority within a Process does not usually make sense, and no tools allow this because only developers understand the importance of the various threads in their programs. On the other hand, because applications must manually register with MMCSS and provide it with information about what kind of thread this is, MMCSS has the necessary data to change these relative priorities—and developers are well aware that this will happen.

## EXPERIMENT: MMSS priority boosting

In this experiment, you will see the effects of MMCSS priority boosting.

1. Run Windows Media Player (wmplayer.exe). (Other playback programs might not take advantage of the API calls required to register with MMCSS).
2. Play some audio content.
3. Using Task Manager or Process Explorer, the affinity of the Wplayer.exe process so that it runs on only one CPU.
4. Start the Performance Monitor tool.
5. Using Task Manager, change Performance Monitor’s priority class to Realtime so it will have a better chance of recording activity.
6. Click the Add Counter toolbar button or press Ctrl+I to open the Add Counters dialog box.
7. Select the Thread object and then select the Priority Current.
8. In the Instances box, type Wmplayer, click Search, and then select all its threads.
9. Click the Add button and click OK.
10. Open the Action menu and choose Properties.
11. On the Graph tab, change the maximum vertical scale to 32. You should see one or more priority-16 threads inside Wmplayer, which will be constantly running unless there is a higher-priority thread requiring the CPU after they are dropped to the exhausted category.
12. Run CPU Stress.
13. Set the activity level of thread 1 to Maximum.
14. The priority of thread 1 is Normal. Change it to Time Critical.
15. Change the CPUSTRES priority class to High.
16. Change the CPUSTRES affinity to use the same CPU used for Wmplayer. The system should slow down considerably, but the music playback should continue. Every so often, you'll be able to get back some responsiveness from the rest of the system.

MMSS' functionality does not stop at priority boosting; because of the nature of network de-I/O priority (see Chapter 6 for I/O priority), long-running network driver can interrupt playback during a game. MMCSS sends a special command to the network stack, to throttle network packets during the duration this throttling is designed to maximize playback performance—at the cost of some loss in network throughput. (The exact mechanisms behind it do not belong to any area of the scheduler, we will leave them out.)

MMSS also supports a feature called deadline scheduling. The idea is that an audio-program does not need the highest priority in its category. If a program uses buffering (obtaining audio data from disk or network) and then plays the buffer while building the next, deadline scheduling allows a client to indicate when it must get the highest priority to avoid glitches, but with a slightly lower priority (within its category) in the meantime. A thread can use the AvTaskYield to indicate the time it must get the highest priority, specifying the time it needs. Until that time, it gets the lowest priority within its category, potentially freeing CPU time for the system.

## Autobost

Autboost is a framework targeted at the priority-inversion problem described in the previous section. The idea is to track lock owners and lock waiters in such a way that would boost the appropriate threads' priorities (I/O priority as needed) to allow threads to make forward progress. The lock information is stored in a static array of KLOCK_ENTRY objects inside the KTHREAD structure. The current implementation uses a maximum of six entries. Each KLOCK_ENTRY contains two binary trees: one for locks owned by the thread and the other for locks waited on the thread. These trees are keyed by priority so constant time is required to determine the highest priority which should be applied. If boosted, the owner's priority is set to the waiter's. It also boost I/O priority if these were used with low priority. (See Chapter 6 for I/O priority.) As all priority boosts, the maximum priority achievable by Autobost is 15. (The priority of real-time threads is never boosted.)

Current implementation uses the Autobost framework for pushlocks and guarded synchronization primitives, which are exposed to kernel code (See Chapter 8 in Part 2 for more on these objects). Future versions of Windows may implement Autobost for user-mode objects that have an owner-ship concept, such as critical sections.
