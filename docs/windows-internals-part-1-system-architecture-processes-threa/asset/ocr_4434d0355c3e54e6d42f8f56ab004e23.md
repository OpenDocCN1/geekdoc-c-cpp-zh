There are four debuggers included in the tools: cdb, nstd, kd, and Winbg. All are based on a single debugging engine implemented in DbgEng.dll, which is documented fairly well in the help file for the tools. Here's a brief overview of the debuggers:

+   - cdb and nstd are user-mode debuggers based on a console user interface. The only difference between them is that nstd opens a new console window if activated from an existing window, while cdb does not.
- kd is a kernel-mode debugger based on a console user interface.
- Winbg can be used as a user-mode or kernel-mode debugger, but not both at the same time. It provides a GUI for the user.
- The user-mode debuggers (cdb, nstd, and Winbg, when used as such) are essentially equivalent. Usage of one or the other is a matter of preference.
- The kernel-mode debuggers (kd and Winbg, when used as such) are equivalent as well.

# **User-mode debugging** The tools can also be used to attach to a user-process and to examine/or change process memory. There are two options attaching to a process:

+   - Invasive Unless otherwise specified, when you attach to a running process, you use the DebugActive Windows function to establish a connection between the debugger and the debugger. This permits you to examine/or change process memory, set breakpoints, and perform other debugging functions. Windows allows you to stop debugging without killing the target process as long as the debugger is detached, not killed.
- Noninvasive With this option, the debugger simply opens the process with the OpenProcess function. It does not attach to the process as a debugger. This allows you to examine/or change memory in the target process, but you cannot set breakpoints. This also means it is possible to attach noninvasively even if another debugger is attached invasively.

You can also user-mode process dump files with the debugging tools. User-mode dump files are explained in Chapter 8 in Part 2 of the section on event dispatching.

# **Kernel-mode debugging** As mentioned, there are two debuggers that can be used for kernel debugging: a command-line view (Kd.exe) and a GUI version (Winbg.exe). You can perform three types of kernel debugging with these tools:

+   - Open a crash dump file created as a result of a Windows system crash. (See Chapter 15, "Crash dump analysis," in Part 2 for more information on crash dumps)
- Connect to a live, running system and examine the system state (or set breakpoints if you're debugging device code). This requires two computers: a target (the system being debugged) and a host (the system running the debugger). The target system can be connected to the host via a null modem cable, an IEEE 1394, USB 2.0/3.0 debugging cable, or the local network. The target system must be booted in debugging mode.
