## Heap security

As the heap manager has evolved, it has taken an increased role in early detection of usage errors and in mitigating potential-based exploits. These measures exist to lessen the effect of vulnerabilities. Both the NT heap and segment-heap implementations have multiple mechanisms that reduce the likelihood of exploitation. The metadata used by the heaps for internal management is packed with a high degree of randomization to make it difficult for an attempted exploit to patch the internal structures to prevent crashes. By using the HeapSetInformation API processes can operate with automatic termination for detected corruptions such as buffer overflows. As an effect of block randomization, using the debugger to simply dump a block header as an area of memory is useful. For example, the size of the block and whether it is busy is not easy to spot from a random sample. The dump applies to LFH blocks. They have a different type of metadata stored in the header, also partially randomized. To dump these details, the !heap -i command in the debugger does all the work to retrieve the metadata fields from a block, flagging free-list inconsistencies if they exist. The command works for both LFH and regular heap. The total size of the blocks, the user-requested size, the heap owning the block, and the header checksum are available in the following sample. The randomization algorithm uses heap granularity, the !heap -i command should be used only in the proper context of the heap. In the example, the heap handle is 01. If the current heap context were different, the decoding of the header would be incorrect. To set the proper context, the same !heap -i command with the heap handle as an argument must be executed.

## Segment heap-specific security features

The segment heap implementation uses security mechanisms to make it harder to corrupt memory or allow code injection by an attacker. Here are some of them:

- **Fail fast on linked node corruption** The segment heap uses linked lists to track segments and sub-segments. As the NT heap, chunks are added to the list insertion and removal to prevent arbitrary memory writes due to corrupted nodes. If a corrupted node is detected, the process is terminated at `tlFailFast`.

- **Fail fast on red-black (RB) tree node corruption** The segment heap uses RB trees to track back end and VS allocations. Node insertion and deletion functions validate nodes involved or, if corrupted, invalidate the fail-fast mechanism.

- **Function pointer decoding** Some of the segment heap allow for callbacks (in VsContext and LfhContext structures, part of the _SEGMENT_HEAP structure). An attacker can override these callbacks to point to his own code. However, the function pointers are encoded by using a XOR function with random heap key and the context address, both of which cannot be guessed in advance.

- **Guard pages** When LFH and VS sub-segments and large blocks are allocated, a guard page is added at the end. This helps to detect overflows and corruption of adjacent data. See the section "Stacks" later in this chapter for more information on guard pages.

## Heap debugging features

The heap manager includes several features to help detect bugs by the following heap settings:

- **Enable tail checking** The end of each block carries a signature that is checked when the block is released. If a buffer overflow destroys the signature entirely or partially, the heap will report this error.

- **Enable free checking** A free block is filled with a pattern that is created at various points when the heap manager needs to access the block, such as at removal from the free list to satisfy allocate request. If the process continues to write to the block after freeing it, the heap manager will detect changes in the pattern and the error will be reported.

- **Parameter checking** This function consists of extensive checking of the parameters passed to the heap functions.

- **Heap validation** The entire heap is validated at each heap call.

- **Heap tagging and stack traces support** This function supports the specification of tags for allocation/or captures user-mode stack traces for the heap calls to help narrow the possible causes of a heap error.

The first three options are enabled by default if the loader detects that a process is started under the control of a debugger (a debugger can override this and turn off features). You can specify the debugging features for an executable image by setting various flags in Gflags (See the next example and the section "Windows flags" in Part 2). Alternatively, you can enable heap debugging using the !heap command in the standard debuggers (See the debugger help for more information.)

## Pageheap

Because the tail and free checking options described in the preceding sections might discover corruptions that occurred before the problem was detected, an additional debugging capability, called pageheap, is provided. Pageheap directs all or part of the heap calls to a different heap manager. You can enable pageheap using the Gflags tool (part of the Debugging Tools for Windows). When enabled, the heap manager places allocations at the end of pages and reserves the page that immediately follows. Because reserved pages are not accessible, a buffer overflow that will cause an access violation, making it easier to detect the offending code. Optionally, pageheap allows for the placement of blocks at the beginning of the pages, with the preceding reserved page, to detect overrun problems (a rare occurrence). Pageheap can also protect free pages against any access to detect references to heaps after they have been freed.
