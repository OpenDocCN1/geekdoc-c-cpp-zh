You can also connect through a named pipe—when debugging Windows 7 or earlier versions through a virtual machine product such as Hyper-V, VirtualBox, or VMware Workstation—by exposing the guest operating system's serial port as a named device. For Windows 8 and later, you use local debugging by exposing a host-only network using a NIC in the guest operating system. This will result in 1,000x performance gain.

+   * Windows systems also allow you to connect to the local system and examine the system state. This is called local kernel debugging. To initiate kernel debugging with WinDbg, first make sure the system is set to debug mode (by running msconfig.exe, clicking the Boot tab, selecting Advanced Options, selecting Debugging, and restarting Windows). Launch WinDbg with admin privileges and open the File menu, choose Kernel Debug, the Kernel tab, and click OK (or use bcdedit). Figure 1-6 shows a sample output screen on a 64-bit Windows 10 machine. Some kernel debugger commands do not work in local kernel debugging mode, such as setting breakpoints or capturing a memory dump with the .dump command. However, the latter can be done with LiveKd, described later in this section.

Once connected to kernel-debugging, you may use one of the many debugger extensions—also known as bang commands, which are commands that begin with an exclamation point (!)—to display the contents of internal data structures such as threads, processes, I/O packets, and memory management information. Throughout this book, the relevant debugger commands and output are indicated as they apply to each topic being discussed. An excellent reference is the Debugger.ch help file, contained in the WinDbg installation folder, which documents all the debugger functionality and extensions. In addition, the dt (display type) command can format more than 1,000 kernel structures because the kernel symbol files for Windows type provide information that the debugger can use to format structures.
