
- 1. Load DLL referenced in the import table of the process's executable image.

- 2. Check whether the DLL has already been loaded by checking the module database. If it doesn't it in the list, the loader opens the DLL and maps it into memory.

- 3. During the mapping operation, the loader first looks at the various paths where it should attempt to load this DLL, and whether this is a known DLL, meaning the system has already loaded it at startup and provided a global memory mapped file for accessing it. Certain dependencies from the standard lookup algorithm can also occur, either through the use of a local file (which forces the loader to use in the local path) or through a manifest file, which can specify a redirected DLL to use to guarantee a specific version.

- 4. After the DLL has been found on disk and mapped, the loader checks whether the kernel has loaded it somewhere—this is called relocation. If the loader detects relocation, it parses the relocation information in the DLL and performs the operations required. If no relocation information is present: DLL loading faults.

- 5. The loader then creates a loader data table entry for this DLL and inserts it into the database.

- 6. After a DLL has been mapped, the process is repeated for this DLL to parse its import table and al all its dependencies.

- 7. After each DLL is loaded, the loader parses the IAT for specific functions that are being imported. This is usually by name, but it can also be by ordinal (an index number). For each name, the loader parses the export table of the imported DLL and tries to create a match. If no match is found, the operation is aborted.

- 8. The import table of an image can also be bound. This means that at link time, the developers already assigned static addresses pointing to imported functions in external DLLs. This removes the need to do the lookup for each name, but it assumes that the DLLs the application will use will be located at the same address. Because Windows uses address randomization (see Chapter 5 for more information on ASLR), this is usually not the case for system applications and libraries.

- 9. The export table of an imported DLL can use a forwarder entry, meaning that the function is implemented in another DLL. This must essentially be treated like an import or dependency, so after parsing the export table, each DLL referenced by a forwarder is also loaded and the loader goes back to step 1.

After all imported DLLs (and their dependencies, or imports) have been loaded, all the required imported functions have been looked up and found, and all forwarders have also been loaded and tprocess is complete: All dependencies that were defined at compile time by the application di its various DLLs have now been fulfilled. During execution, delayed dependencies (called delay load), as well as run-time operations (such as calling LoadLibrary) can call into the loader and repeatedly repeat the same tasks. Note, however, that a failure in these steps will result in an error loading t application if they are done during startup. For example, attempting to run an application requires a function that is not present in the current version of the operating system can result in a message similar to the one in Figure 3-12.

## Post-import process initialization

After the required dependencies have been loaded, several initialization tasks must be performed to fully finalize the application. In this phase, the loader will do to the following:

- 1. These steps begin with the LdrIniState set to 2, which means imports have loaded.

- 2. The initial debugger breakpoint will be hit when using a debugger such as Winbg. This is where you had to type g to continue execution in earlier experiments.

- 3. Check if this is a Windows subsystem application, in which case the BaseThreadInUiThunk function should have been captured in the early process initialization steps. At this point, it is called and checked for success. Similarly, the TermSrvGetWindowsDirectory function, which should have been captured earlier (on a system that supports terminal services), is now called, which resets the System and Windows directories path.

- 4. Using the distributed graph, recurse through all dependencies and the initializers for all of the images static imports. This is the step that calls the D11Main routine for each DLL which might include loading new DLLs at run time as well processes the TLS initializers of each DLL. This is one of the last steps in loading an application can fail. If all the loaded DLLs do not return a successful code after finishing the D11Main routines, the loader aborts the application.

- 5. If the image has any TLS, call its TLS initializer.

- 6. Run the post-initialization shim engine callback if the module is being shimmed for application compatibility.

- 7. Run the associated subsystem DLL post-initialization routine registered in the PEB. For Windows applications, this does Terminal Services–service checks, for example.

- 8. At this point, an ETW event indicating that the process has loaded successfully.

- 9. If there is a minimum stack count, touch the thread stack to force an in-page of the committed pages.

- 10. Set LdrInstanceState to 3, which means initialization done. Set the PEB’s ProcessInitializing field to 0. Then, update the LdrProcessInitialized variable.

## SwitchBack

As new version of Windows fixes bugs as race conditions and incorrect parameter validation checks in API functions, an application-compatibility risk is created for each change, no matter how minor. Windows makes use of a technology called SwitchBack, in the loader, which enables software developers to embed a GUID to the Windows version they are targeting in their executable manifest.

For example, if a developer wants to take advantage of improvements added in Windows 10 to a given API, she would include the Windows 10 GUID in her manifest, while if a developer has a legacy application that depends on Windows 7–specific behavior, she would put the Windows 7 GUID in the manifest instead.

SwitchBack parses this information and correlates it with embedded information in SwitchBack-compatible DLLs (in the .sb_data section) to decide which version of an affected API should be called by the module. Because SwitchBack works at the loaded-module level, it enables a process to have both legacy and current DLLs concurrently calling the same API, yet observing different results.

## SwitchBack GUIDs

Windows defines GUIDs that represent compatibility settings for every version from Windows Vista:

## SwitchBack compatibility modes

As a few examples of what SwitchBack can do, here's what running under the Windows 7 context affects:

- RPC components allow the Windows thread pool instead of a private implementation.
- DirectDraw Lock cannot be acquired by the primary buffer.
- Blitting on the desktop is not allowed without a clipping window.
- A race condition in GetOverappedFile is fixed to pass a "downgrade" flag to receive exclusive open to a file even when the caller does not have write privilege, which causes NtCreateFile to not receive the FILE_DISALLOW_EXCLUSIVE flag.

Running in Windows 10, on the other hand, subtly affects how the Low Fragmentation Heap (LFH) behaves, by forcing LFH sub-segments to be fully consolidated and padding allocations with a header block under the Windows 10 GUID is present. Additionally, in Windows 10, using the Raise Exception on Invalid Handle Close (see Chapter 7 for more information) will result in CloseHandle and RegClose respecting the behavior. On the other hand, on previous systems, if the debugger is not attached, this behavior will be disabled before calling NtClose, and then re-enabled after the call.
