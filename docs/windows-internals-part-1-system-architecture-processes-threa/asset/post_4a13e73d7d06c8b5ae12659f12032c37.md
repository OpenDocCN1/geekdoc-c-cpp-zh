
- The large rectangle consisting of the four blocks (labeled Dispatch Routine, Start I/O Routine, ISR, and DPC Routine) represents the driver-provided code. All other blocks are provided by the system.

- The figure assumes the hardware device can handle one operation at a time, which is true of many types of devices. Even if the device can handle multiple requests, the basic flow of operations is still the same.

Here is the sequence of events as outlined in Figure 6-14:

- 1. A client application calls a Windows API such as ReadFile. Read calls the NtReadFile (in Ntdll.dll), which makes the thread transition to kernel mode to the executive NtReadFile (these steps have already been discussed in this chapter).

- 2. The I/O manager, in its Read implementation, performs some sanity checks on the request, such as whether the buffer provided by the client is accessible with the right page protection. Next, the I/O manager locates the associated driver (using the file handle provided), allocates and initializes an IRP, and calls the driver in the appropriate dispatch routine (in this case, corresponding to the IRP_MJ_READ index) using IoCallDriverDriver with the IRP.

- 3. This is the first time the driver calls the IRP. This is usually invoked using the requesting thread; the only way for that not to happen is if an upper filter is held over to the IoCallDriver from a different thread. For the sake of this discussion, we will assume this is not the case (and in cases involving hardware devices, this does not happen; even if there are upper filters, they do processing and call the lower driver immediately from the same thread). The dispatch routine callback in the driver has two tasks on its hand: first, it should perform more checking than the I/O manager because it has no idea what the request really means. For example, the driver could check if the buffer provided to a read or write is large enough; for a DeviceControl operation, the driver could check whether the I/O control provided is a supported one. If any check fails, the driver completes the IRP (IoCompleteRequest) with the failed status and returns immediately. If the checks pass OK, the driver calls its Start I/O routine to initiate the operation. However, if the hardware device is busy (handling a previous IRP), then the IRP is inserted into a queue managed by the driver and a STATUS_PENDING is returned without completing the IRP. The I/O manager caters for such a scenario with the IoStartPacket function, that checks a busy bit in the device object and if the device is busy, inserts the IRP into a queue (part of the device object structure). If the device is not busy, it sets the device as busy and calls the registered Start I/O routine (recall that there is a member in the driver object that would have been initialized in DriverEntry). Even if a driver chooses not to use IoStartPacket, it would still follow similar logic.

- 4. If the device is not busy, the Start I/O routine is called from the dispatch routine directly—meaning it's still the requesting thread that is making the call. Figure 6-14 shows that the Start I/O routine is called in an arbitrary thread context; this will be proven to be true in the general case when we look at the DPC routine in step 8. The purpose of the Start I/O routine is to use relevant parameters and use them to program the hardware device (for example, by writing to its ports or registers HAL hardware access routines such as WRITE_PORT_UCHAR, WRITE_REGISTER_ULONG, etc.). After the Start I/O completes, it returns, and no particular code is running in the driver, the hardware is working and "does its thing." While the hardware device is working, more requests can come to the device (if using asynchronous operations) or other threads that also opened handles to the device. In this case the dispatch routine would realize the device is busy and insert the IRP into the queue as mentioned, where one way to achieve this is with a call to IoStartPacket.

- 5. When the device is done with the current operation, it raises an interrupt. The kernel trap handles the CPU context for whatever thread was running on the CPU that was selected to handle the interrupt, raises the IRQL of that CPU to the IRQL associated with the interrupt (DIRQL) and jumps to the registered ISR for the device.

- 6. The ISR, running at Device IRQL (above 2) does as little as possible, telling the device to stop the interrupt and signaling the status or other required information from the hardware. As its last act, the ISR queues a DPC for further processing at a lower IRQL. The advantage of using DPC to perform most of the device servicing is that any interrupt whose IRQL lies between Device IRQL and DPC IRQL is allowed to occur. Intermediate-level interrupts are served more promptly than they otherwise would, and reduce latency on the system.

- 7. After the interrupt is dismissed, the kernel notices that the DPC queue is empty and uses a software interrupt at DPC_LEVEL to jump to the DPC loop.

- 8. Eventually, the DPC is dequeued and executed, performing two main operations:
- It gets the IRP in the queue (if any) and starts the new operation for the device. This is done to prevent the device from being idle for too long. If the dispatch routine uses IoStartPacket, the DPC calls its counterpart. If an IRP is available, the Start I/O routine is called in an arbitrary thread. If there are no IRPs in the queue, the device is marked busy—ready for the next request that comes in.
- It completes the IRP by the driver calling IoCompleteRequest. From that point, the driver is no longer responsible.

- 9. The requesting thread needs to be notified of the completion. Because the current thread executing the DPC is arbitrary, it's not in the original address space. To execute code in the context of the requesting thread, a special kernel APC is issued. When the requesting thread gets CPU time, the special kernel APC executes first (at APC_LEVEL). (For more on APCs, see Chapter 8.)

A final note about I/O completion: the asynchronous I/O functions ReadFileEx and WriteFileEx allow a caller to supply a callback function as a parameter. If the caller does, the I/O manager queues a user mode APC to the caller's APC queue as the last step of I/O. This feature allows a caller to specify a subroutine to be called when an I/O request is completed or canceled. User-mode completion routines execute in the context of the requesting thread and are delivered only when the thread enters an alert wait state (by calling functions such as SleepEx, WaitForSingleObjectEx, or WaitForMultipleObjects).

## User address space access

As shown in Figure 6-14, there are four driver functions involved in processing an IRP. Some of these routines may need to access the buffer in user space provided by the client. When an application or device driver invokes an IRP using the NtReadFile, NtWriteFile, or NtDeviceIoControl systems (or the Windows API functions corresponding to these services which are ReadFile, WriteFile, and DeviceIoControl), the pointer to the user's buffer is provided in the UserBuffer member of the IRP. However, accessing this buffer directly can only be done in the requesting thread context (the client process address is visible) and in IRQL 0 (paging can be handled normally).

As discussed in the previous section, the dispatch routine meets the criteria of running in the requesting thread context and in IRQL 0. Even this is not always the case—it's possible for an upper filter to hold on the IRP and not pass it down immediately, possibly passing it later using a different thread, or even when the CPU IRQL is 2 or higher.

The other functions (Start I/O, ISR, DPC) clearly run on an arbitrary thread (could be any thread), and with IRQL 2 (DIRQL for the ISR). Accessing the user's buffer directly from any of these routines is mostly fatal. Here's why:

- Because the IRQL is 2 or higher, paging is not allowed. Since the user's buffer (or part of it) may be paged out, accessing the non-resident memory would crash the system.
- Because the thread executing these functions could be any thread, and thus a random process address space would be visible, the original user's address has no meaning and would likely lead to an access violation, or worse—accessing data from some random process (the parent process of whatever was running at the time).

Clearly, there must be a safe way to access the user's buffer in any of these routines. The I/O manager provides two options, for it does the heavy lifting. These are known as Buffered I/O and Direct I/O. A third option, which is not really an option, is called Neither I/O, in which the I/O manager does nothing special and lets the driver handle the problem on its own.

A driver selects the method in the following way:

- For read and write operations (IRP_MJ_READ, IRP_MJ_WRITE), it sets the Flags member with a boolean operation so not to disturb other flags of the device object (DEVICE_OBJECT) to DO_BUFFERED_IO (for buffered I/O) or DO_DIRECT_IO (for direct I/O). If neither flag is set, neither I/O is implied. (DO is short for device object).
