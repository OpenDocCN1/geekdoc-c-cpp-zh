# Birth of a thread

A thread life cycle starts when a process (in the context of some thread, such as the thread running the main function) creates a new thread. The request filters down to the Windows executive, where the process manager allocates space for a thread object and calls the kernel to initialize the thread control block (KTHREAD). As mentioned, various thread-creation functions eventually end up at CreateRemote-ThreadEx. The following steps are taken inside this function in Kernel32.dll to create a Windows thread.

- 1. The function converts the Windows API parameters to native flags and builds a native structure describing object parameters (OBJECT_ATTRIBUTES, described in Chapter 8 in Part 2).

- 2. It builds an attribute list with two entries: client ID and Teb address. (For more information on attribute lists, see the section "Flow of CreateProcess" in Chapter 3.)

- 3. It determines whether the thread is created in the calling process or another process indicated by the handle passed in. If the handle is equal to the pseudo handle returned from GetCurrentProcess (with a value of -1), then it is the same process. If the handle is different, it could still be a valid handle to the same process, so a call is made to NtQueryInformationProcess (in NtThread) to find out that it is indeed the case.

- 4. It calls NtCreateThread (in Ntdl) to make the transition to the executive in kernel mode and continues inside a function with the name and arguments.

- 5. NtCreateThreadEx (inside the executive) creates and initializes the user-mode thread context (its structure is architecture-specific) and then calls PsCreateThread to create a suspended thread object. For a description of the steps performed by this function, see the descriptions of stage 3 and stage 5 in Chapter 3 in the section "Stage 7: Flow of CreateProcess". Then the function returns, ending back in user mode at CreateRemoteThreadEx.

- 6. CreateRemoteThreadEx allocates an activation context for the thread used by side-by-side assembly. It joins the activation stack if it requires activation and activates it if needed. The activation stack pointer is seeded in the new thread's TEB.

- 7. Unless the caller created the thread with the CREATE_SUSPENDED flag, the thread is now resumed so that it can be scheduled for execution. When the thread starts, it executes the steps described in Chapter 3 in the section "Stage 7: performing process initialization in the context of the new process" before calling the actual user's specified start address.

- 8. The thread handle and the thread ID are returned to the caller.

# Examining thread activity

Examining thread activity is especially important if you are trying to determine why a process that is hosting services is running (such as Svchost.exe, Dllhost.exe, or Lass.exe) or why a process has stopped responding.

There are several tools that expose various elements of the system of Windows: WinDbg (in user-process attach and kernel-debugging mode), Performance Monitor, and Process Explorer. The tools that show thread-scheduling information are listed in the section "Thread scheduling."

To view the threads in a process with Process Explorer, select a process and double-click it to open its Properties dialog box. Alternatively, right-click the process and select the Properties menu item.

Then click the Threads tab. This shows a list of threads in the process and four columns of information for each thread: its ID, the percentage of CPU consumed (based on the refresh interval configured), the number of cycles charged to the thread, and the thread start address. You can sort by any of these four columns.

New threads that are created are highlighted in green, and threads that exit are highlighted in red. (To configure the highlight duration, open the Options menu and choose the Duration.)

As you select each thread in the list, Process Explorer displays the ID, start time, state, CPU time, number of context switches, ideal processor and group, I/O priority, priority, base (dynamic) priority. There is a Kill button, which terminates an individual thread, but this should be used with extreme care. Another option is the Suspension button, which prevents the thread from execution. However, this can also lead to deadlocks and should be used with the same care as the Kill button. Finally, the Permissions button allows you to see the security descriptor of the thread. (See Chapter 7, "Security," for more information on security descriptors.)

Unlike all process monitoring tools, Process Explorer uses the cycle counter for thread time accounting (described later in this chapter) instead of the clock interval timer, so you will see a significantly different view of CPU consumption using Process Explorer. This is because threads run for short times that they are seldom (if ever) running when the clock interval timer overruns. As a result, they are not charged for much of their CPU time, leading cycle-based tools to perceive a CPU usage of 0 percent. On the other hand, the total number of cycles represents the actual number of cycles that each thread in the process accrued. It is independent of the clock interval timer's resolution and updated at each interrupt entry. (A final accumulation is done before a context switch.)

The thread start address is displayed in the module function, where module is the name of the EXE or .DLL. The function relies on system files for the module (see the section "Experiment: Viewing process details with Process Explorer" in Chapter 1, "Concepts and tools.") If you are unsure what the module is, click the Module button to open an Explorer Properties dialog for the module containing the thread's start address (example, the .EXE or .DLL).
