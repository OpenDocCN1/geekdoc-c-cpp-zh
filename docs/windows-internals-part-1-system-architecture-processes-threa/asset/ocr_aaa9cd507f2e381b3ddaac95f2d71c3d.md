Second, a check is made to see if export suppression is enabled. If it is, the target address is checked against the list of export-suppressed addresses, which is once again indicated with another flag that is added to the guard table entry. If this is the case, the loader validates that the target address is a forwarder reference to the export table of another DLL, which is the only allowed case of an indirect call toward image with suppressed exports. This is done by a complex check that makes sure the target address is in a different image, that its loaded directory has export suppression, and that this is in the import directory of image. If these checks match, the kernel is called through the SetInformationVirtualMemory described earlier, to change the bit state to (1, 0). If any of these checks fail, or suppression is not enabled, the process is terminated.

For 32-bit applications, an additional check is performed if DEP is enabled. (See Chapter 5 for more DEP!) Otherwise, because there are no exception guarantees to weigh, the incorrect call is allowed, as it may be an older application calling the heap or stack for legitimate reasons.

Because large sets of (0, 0) bit states are not committed to save, space, if checking the bitmap lands on a reserved page, an access violation exception occurs. On x86, where exception is enabled, instead of being handled as part of the verification code, it is left to propagate normally. (See Chapter 8 in Part 2 for more exception dispatching).The user-mode dispatcher, KernelDispatcher, has specific checks for recognizing bitmap access exceptions within the validation function and will automatically resume execution if the exception code was STATUS_IN_PAGE_ERROR. This simplifies the code in LdrpValidateUserCallTarget and LdrpDispatchUserCallTarget(ES), which do not to include exception handling code. # Kernel CFG

Although drivers compiled with Visual Studio and /guard:cf also ended up with the same properties as user-mode images, the first versions of Windows 10 did not do anything with this data. Unlike the user-mode CF bitmap, which is protected by a higher, there is nothing that can truly "protect" the kernel CFG bitmap if one were to be created. A malicious exploit could simply edit the PTE that the page containing the desired bits to modify, mark it as read/write, and proceed with the indirect call or jump.
