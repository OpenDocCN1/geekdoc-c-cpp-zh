
To create these pages, the following steps are taken:

- 1. Page table entries are created in the appropriate page tables to map the initial pages.
- 2. The number of pages is deducted from the kernel variable MmTotalCommittedPages and added to MmProcessCommit.
- 3. The system-wide default process minimum working size (PsMinimumWorkingSet) is deducted from MmResidentAvailablePages.
- 4. The page table pages for the global system (that is, other than the process-specific pages we just described, except exception-specific memory) are created.

## Stage 3C: Creating the kernel process structure

The next stage of PspAllocateProcess is initialization of the KPROCESS structure (the Pcb member of the EPROCESS). This work is performed by KeInitializeProcess, which does the following:

- 1. The doubly linked list, which connects all parts of the process (initially empty), is initialized.
- 2. The initial value (or reset value) of the process default quantum (which is described in more detail in "Thread scheduling") is hard-coded to 6 until it is initialized later by (PspQuantumAndPriority).

- The default initial quantum differs between Windows client and server systems. For more information on thread quantums, turn to the discussion in the section "Thread scheduling" in Chapter 4.

- 3. The process's base priority is set on what was computed in stage 3A.
- 4. The default processor affinity for the threads in the process is set, as is the group affinity. The group affinity was calculated in stage 3A or inherited from the parent.
- 5. The process-swapping state is set to resident.
- 6. The thread seed is based on the ideal processor that the kernel has chosen for this process (which is based on the previously created process's ideal processor, effectively modifying this in a round-robin manner). Creating a new process will update the seed in KeNodeBlock so that the new process will get a different ideal processor seed.
- 7. If a process is secure process (Windows 10 and Server 2016), then its secure ID is created now by calling HvCreateSecureProcess.

## Stage 3D: Completing the setup of the process address space

Setting up the address space for a new process is somewhat complicated, let's look at what's involved one step at a time. To get the most out of this section, you should have some familiarity with the intervals of the Windows memory manager, described in Chapter 5.

The routine that does most of the work in setting the address space is MmInitializeProcess-AddressSpace. It also supports cloning an address space from another process. This capability will be useful at the time to implement the POSIX fork system call. It may also be leveraged in the future to support Unix-style fork (which is how fork is implemented in Windows Subsystem for Linux in Redstone 1). The following steps do not describe the address space functionality, but focus on normal process address initialization.

- 1. The virtual memory manager sets the value of the process's last trim to the current time. The working manager (runs in the context of the balance set manager thread) uses this value to determine when to initiate set trimming.
- 2. The memory manager initializes the process's working set list. Page faults can now be taken.
- 3. The section (created when the image file was opened) is now mapped into the new process's address space, and the process section base is set to the base address of the image.
- 4. The Process Environment Block (PEB) is created and initialized (see the section stage 3E).
- 5. Ntdll.dll is mapped into the process. If this is a Wow64 process, the 32-bit Ntdll.dll is also mapped.
- 6. A new session, if requested, is created for the process. This special step is simply implemented for the benefit of the Session Manager (Smss) when initializing a new session.
- 7. The standard handles are duplicated and the new values are written in the process structure.
- 8. Any memory reservations listed in the attribute list are now processed. Additionally, two flags allow the bulk reservation of the first 1 or 16 MB of the address space. These flags are used internally for mapping, real-mode vectors and ROM code (which must be in the low ranges of virtual address space, where normally the heap or other process structures could be located).
- 9. The user process parameters are written into the process, copied, and fixed up (that is, they are converted from absolute form to a relative form that a single memory block is needed).
- 10. The affinity information is written into the PEP.
- 11. The MinWin API redirection is mapped into the process and its pointer is stored in the PEP.
- 12. The process unique ID is now determined and stored. The kernel does not distinguish between unique process and thread IDs. The process and thread IDs (handles) are stored in a global handle table (PspCidTable) that is not associated with any process.
- 13. If the process is secure (that is, it runs in IUM), the secure process is initialized and associated with the kernel process object.

## Stage 3E: Setting up the PEB

NtCreateProcess calls MiCreatePeb, which maps the system-wide National Language Support (NLS) tables into the process's address space. It calls MiCreatePebOr to allocate a page for the PEB and initializes a number of fields, most based on internal variables that are configured through the registry, such as MinHeap* values, MiCriticalSectionTimeout, and MinStackCommitInBytes. Some of these fields can be overridden by settings in the linked executable image, such as the Windows version in the PE header or the affinity mask in the load configuration of the PE header.

If image header characteristics IMAGE_FILE_SYS_ONLY flag is set (indicating that the image can run only on a uniprocessor system, a CmpRtlProcessorNumber is chosen for all the threads in this new process to run on). The selection process is performed by simply cycling through the available processors. Each time this type of image is run, the next processor is used. In this way, these types of images are spread evenly across the processors.

## Stage 3F: Completing the setup of the executive process

Before the handle to the new process can be returned, a few setup steps must be completed, which are performed by PsInsertProcess and its helper functions:

- If system-wide auditing of processes is enabled (because of either local policy settings or group policy from a domain controller), the process's creation is written to the Security event log.
- If the parent process was contained in a job, the job is recovered from the job level of the parent and bound to the session of the newly created process. Finally, the new process is added to the job.
- The new process is inserted at the end of the Windows list of active processes (PsActiveProcessHead). Now the process is accessible via functions like EnumProcesses and OpenProcess.
- The process debug flag of the parent process is copied to the new process unless NoDebugFlag is set (which can be requested when creating the process). If a debug port was specified, it is attached to the new process.
- Job objects can specify restrictions on which group or groups the threads within the processes of a job can run on. Therefore, PsInsertProcess must make sure the affinity associated with the process would not violate the group affinity associated with the job. An interest-secondary issue to consider is if the job's permissions grant access to modify the process's affinity permissions, because a less-privileged job object might interfere with the more privileged process.
- Finally, PsInsertProcess creates a handle for the new process by calling OpenObjectByPointer, and then returns this to the caller. Note that no process-creation callback is sent until the first thread within the process is created, and the code sends process callbacks before sending object managed-based callbacks.
