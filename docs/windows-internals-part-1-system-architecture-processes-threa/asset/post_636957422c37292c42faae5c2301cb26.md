ObpGrantAccess passes to ObGetObject the security credentials of the thread opening the object, the types of access to the object that the thread is requesting (read, write, delete, and so forth, object-specific operations), and a pointer to the object. ObGetObject locks the object security descriptor and the security context of the thread. The security lock prevents another from changing the security context while the check is in progress. The lock on the thread's security context prevents another thread (from that process or a different process) from altering the security identity of the thread while validation is in progress. ObGetObjectAccess then calls the security method to obtain the security settings of the object. (See Chapter 8 in Part 2 for a description of object methods.) The call to the security method might invoke a function in a different executive component. However, many executive objects rely on the system's default security management support.

When an executive component defining an object doesn't want to override the SRM's security policy, it marks the object as having default security. Whenever the SRM calls an object's security method, it first checks whether the object has a default security. With default security stores its security information in its header, and its security method is SeDefaultToObject. An object that does not rely on default security must have its own security information and supply a specific security method. Objects that rely on default security include mutex, events, and semaphores. A file object is an example of an object that overrides default security. The I/O manager, which defines the file type, the file system driver which chooses (or not to implement) the security for its files. Thus, when the system queries the security on a file object that represents a file on an NTFS volume, the I/O manager file object security method retrieves the security using the NTFS file system driver. Note, however, ObGetObject isn't invoked when files are opened because they reside in separate namespaces. The system invokes an object's security method only when a thread explicitly queries or seeks security on a file (with the Windows SetFileSecurity or GetFileSecurity functions, for example).

After obtaining security information, ObGetObject invokes the SRM function SeAccessCheck. SeAccessCheck is one of the functions at the heart of the Windows security model. Along the input parameters SeAccessCheck checks the object's security information, the security identity of the thread as captured by ObGetObject, and the access that the thread is requesting. SeAccessCheck returns true or false, depending on whether the thread is granted the access to the object.

Here is an example: Suppose a thread wants to know when a specific process executes (or terminates in some way). It needs to handle the target process by calling the OpenProcess API, passing two important arguments: the unique process ID (let's assume it's known or has been obtained in some way) and an access mask indicating the operations that the thread want using the returned handle. Lazy developers may use PROCESS_ALL_ACCESS for the access mask, specifying what they want possible access rights for the process. One of the following two results would occur:

- If the calling thread can be granted all the permissions, it would get back a valid handle and then call WaitSingleObject to wait for the process to exit. However, another thread in the process, perhaps with fewer privileges, can use the same handle to do other operations with the process, as terminate prematurely with TerminateProcess; because the handle allows all operations on the process.

- The call can fail if the calling thread does not have sufficient privileges to be granted all possible access and the result is an invalid handle, meaning no access to the process. This is unfortunate, because the thread just needed to ask for the SYNCHRONIZE access mask. That has a much better chance of succeeding than asking for PROCESS_ALL_ACCESS.

The simple conclusion here is that a thread should request the exact access it requires—no more, less.

Another event that causes the object to execute access validation is when a process references an existing handle. Such references often occur infrequently, as a process calls on a Windows API to manipulate an object and passes an object handle. For example, a thread opening a file can request permission to the file. If the thread has permission to access the object in this way, as dictated by its security context and the security settings of the file, the object creates a handle—representing itself—in the handle of the thread's process. The types of accesses the threads in the process are granted through the handle and are stored with the object manager.

Subsequently, the thread could attempt to write to the file using the WriteFile function, passing the file handle as a parameter. The system service WriteFile calls Ntdll.dll, uses the object manager ObjectReferenceByHandle (documented in the WDK) to obtain a pointer to the file object from the handle. ObjectReferenceByHandle accepts the access that the caller wants as a parameter. After finding the handle entry in the process handle table, ObjectReferenceToObjectByHandle compares the access being requested with the access granted at the time the file was opened. ObjectReferenceToObjectByHandle will indicate that the write operation would fail because the caller did not obtain write access when the file was opened.

The security functions also enables Windows to define their own objects and to call the services of the SRM (the AuthZ user-mode APIs, described later) to enforce the Windows security model on those objects. Many kernel-mode functions that the object manager and other executive components use to protect their objects are exported as Windows user-mode equivalent of SeAccessCheck. API AccessCheck. Windows applications can therefore leverage the flexibility of the security model and transparently integrate with the authentication and administrative interfaces that are present in Windows.

The essence of the SRM's security model is an equation that takes three inputs: the security identity of a thread, the access that thread wants an object, and the security settings of the object. The output is yes or no and indicates whether the security model grants the access it desires. The following sections describe the inputs in more detail and then document the model's access-validation algorithm.

## EXPERIMENT Viewing access masks

Process Explorer can show the access mask associated with open handles. Follow these steps:

- 1. Open Process Explorer.
- 2. Open the View menu, choose Lower Pane View, and select Handles to configure the lower pane to show handles.
- 3. Right-click the column headers of the lower pane and choose Select Columns to open the dialog box shown here:
img/ff0e6a9d867a3a6e9527eb1d946810fc_640_0.png
- 4. Select the Access Mask and Decoded Access Mask check (the latter is available in 16.10) and click OK.
- 5. Select Explorer.exe and look at the lower pane handles. Each handle has an access mask, indicating the access granted using this handle. To help interpreting the bits of the access mask, the decoded access mask column shows a textual representation of the access masks for many types of objects:
img/ff0e6a9d867a3a6e9527eb1d946810fc_640_1.png

Notice there are access rights (for example, READ_CONTROL and SYNCHRONIZE) and specific ones (for example, KEY_READ and MODIFY_STATE). Most of the specific ones are shortened versions of the actual definitions in the headers (for example, MODIFY_STATE instead of EVENT_MODIFY_STATE, TERMINATE instead of PROCESS_TERMINATE).
