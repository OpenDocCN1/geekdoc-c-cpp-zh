# UEFI lock

Because disabling Credential Guard (which is ultimately nothing more than a registry setting) is trivial for an attacker, Secure Boot and UEFI can be leveraged to prevent a non-physically present administrator (such as malware with admin rights) from disabling Credential Guard. This is done by enabling Credential Guard with UEFI Lock. In this mode, an EFI runtime variable is written to firmware memory and a reboot is required. At the reboot, the Windows loader, which operates in EFI Boot services, will write an EFI boot variable (which has the property of not being readable or writeable once EFI Boot services is exited) to record the fact that Credential Guard is enabled. Additionally, a BCD Configuration Database (BCD) option will be recorded.

When the kernel boots, it will automatically rewrite the Credential Guard registry key in the presence of the BCD option/or UEFI runtime variable. If deblown by an attacker, BitLocker (if enabled) and TPM-based remote attestation (if enabled) will detect and require physical input of the admin’s recovery key booting, which will restore the BCD option based on the UEFI runtime variable. If the UEFI runtime variable is deleted, the Windows boot loader will restore it based on the EFI boot variable. As such, without special code to delete the UEFI boot variable—which can only be done in EFI Boot services—there is no way to disable Credential Guard in UEFI lock.

The only code that exists is in a Microsoft binary called SecComp.exe. This is downloaded by the administrator, who must then either boot the computer from an alternate-based device and manually execute it (which will require the BitLocker recovery key well as physical access) or modify the BCD (which will require the BitLocker recovery key). At the reboot, SecComp.exe will require user confirmation when in UEFI mode (which can be only done by a physical user).

# Authentication policies and armored Kerberos

Using a security of “secure, unless already compromised before login or by a physical administrator” is definitely an improvement over the traditional non-Credential Guard-based security model. Some enterprises and organizations may want an even stronger security guarantee: that even a compromised machine cannot be used to fake or replay a user’s credentials, and that if a user’s credentials have been compromised, they cannot be used outside specific systems. By leveraging a Server 2016 feature called Authentication Policies, and armored Kerberos, Credential Guard can operate in this heightened security model.

In this mode, the VTL 1 Secure Kernel will collect the TPM (as a file on disk can also be used, but makes the security moot), a special machine ID key. This key is used to generate a TGT during the initial domain join operation as the machine is provisioned (obviously, it is important to ensure the machine is in a trusted state during provisioning), and this TGT is sent to the KDC. Once configured, when the user logs in with his or her credential, it is combined with the machine-credentials (which only isolated LAS has access to), which forms a proof-of-origin key. The KDC will then reply with the NTOWF and TGT and its key after encrypting it with the proof-of-origin key. In this mode, two security guarantees are provided:

+   The user is authenticating from a known machine If the user, or an attacker, has the original credentials, and attempts to use them on a different machine, their TPM-based credential will be different.
