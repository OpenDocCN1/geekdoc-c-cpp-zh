
Despite pervasive use of objects to represent shared system resources, Windows is not an object-oriented system in the strict sense. Most of the kernel-mode OS is written in C for portability. The C programming language doesn't directly support object-oriented constructs such as polymorphic functions or class inheritance. Therefore, the C-based implementation of objects in Windows borrows from, but not depend on, features of particular object-oriented languages.

In Figure 2-1, first notice the line dividing the user-mode and kernel-mode parts of the Windows OS. The boxes above the line represent user-mode processes, and the components below the line are kernel-mode OS services. As mentioned in Chapter 1, user-mode threads execute in a private process address space (although they are accessing system space). Thus, system processes, service processes, processes, and environment subsystems have their own process address space. A second dividing line between kernel-mode parts of Windows and the hypervisor is also visible. Strictly speaking, the hypervisor still runs with the same CPU privilege level (0) as the kernel, but because it uses CPU instructions (VT-x on Intel, SVM on AMD), it can isolate itself from the kernel while monitoring it (and applications). For these reasons, you may often hear the term ring -7 thrown around (which is inaccurate).

The four basic types of user-mode processes are described as follows:

- **User processes** These processes can be one of the following types: Windows 32-bit or 64-bit (Windows Apps running on top of the Windows Runtime in Windows 8 and later are included in this category), Windows 3.1 16-bit, MS-DOS 16-bit, or POSIX 32-bit or 64-bit. Note these can run only on 32-bit Windows, and POSIX applications are no longer supported as of Windows 8.

- **Service processes** These are processes that host Windows services, such as the Task Scheduler and Print Spooler services. Services generally have the requirement that they run independent of users. Many Windows server applications, such as Microsoft SQL Server and Microsoft Exchange Server, also include components that run as services. Chapter 9, "Management mechanisms," in Part 2 describes services in detail.

- **System processes** These are fixed, or hardwired, processes, such as the logon and the Session Manager, that are not Windows services. That is, they are not started by the Service Control Manager.

- **Environment subsystem server processes** These implement all of support for the OS environment, or personality, presented to the user and programmer. Windows NT originally shipped with three subsystems: Windows 2000, POSIX, and OS/2. However, the OS/2 subsystem last shipped with Windows 2000 and POSIX last shipped with Windows XP. The Ultimate and Enterprise versions of Windows 7 client as well as all of the versions of Windows 2008 R2 include support for an enhanced POSIX subsystem called Subsystem for UNIX-based applications (SUA). The SUA is now deprecated and is no longer an optional part of Windows (either client or server).

Windows 10 Version 1607 includes a Subsystem for Linux (WSL) in beta for developers only. However, this is not a true subsystem as described in this section. This chapter will discuss WSL and the related Pico providers in more detail. For information about Pico processes, see Chapter 3, "Processes and jobs."

In Figure 2-1, notice the Subsystem DLLs below the Service Processes and User Processes. Under Windows, user applications do not call the native OS directly. Rather, they go through one or more subsystem dynamic-link libraries (DLLs). The role of subsystem DLLs is to translate a documented function into the appropriate internal (and generally undocumented) native system calls implemented mostly in ntdll.dll. This translation might involve sending a message to the environment subsystem that is serving the user process. The kernel-mode components of Windows include the following:

- **Executive** The Windows executive contains the base OS services, such as memory management, process and thread management, security, I/O, networking, and inter-process communication.

![](img/ff0e6a9d867a3a6e9527eb1d946810fc_64_0.png)

- **Windows kernel** This consists of low-level OS functions, such as thread scheduling, interrupt dispatching, and multiprocessor synchronization. It also provides a set of routines and objects that the rest of the executive uses to implement higher-level constructs.

- **Device drivers** This includes both hardware drivers, which translate user I/O calls into specific device/O requests, and non-hardware device drivers, such as file system and network drivers.

- **Hardware Abstraction Layer (HAL)** This is a layer of code that isolates the kernel, the device drivers, and the rest of the Windows executive from platform-specific hardware (such as differences between motherboards).

- **Windowing and graphics system** This implements the graphical interface (GUI) functions (better known as USER and GDI functions), such as dealing with windows, user controls, and drawing.

- **Hypervisor layer** This is composed of a single component: the hypervisor itself. There are no drivers or other modules in this environment. That being said, the hypervisor is itself composed of multiple internal layers and services, such as its own memory manager, virtual process scheduler, interrupt and timer management, partitions (virtual machine instances) management and inter-partition communication (IPC), and more.

## Portability

Windows was designed on a variety of hardware architectures. The initial release of Windows NT supported the x86 and MIPS architectures. Support for the Digital Equipment Corporation (which was bought by Compaq, which later merged with Hewlett-Packard) Alpha was added shortly thereafter. (After Alpha became a 64-bit processor, Windows NT ran in 32-bit mode. During the development of Windows 2000, a native 64-bit version was running on Alpha, but this was never released.) Support for another market demand, the Motorola PowerPC, was added in Windows NT 3.51. Because of changing market demands, however, support for the MIPS and PowerPC architectures dropped before Windows 2000. Later, Compaq withdrew support for the Alpha architecture, resulting in Windows 2000 being supported only on the x86 architecture. Windows XP and Windows Server 2003 added support for two 64-bit processors: the Intel Itanium IA-64 family and the AMD64 family with their equivalent Intel 64-bit Extension Technology (EM64). The latter implementations are called 64-bit extended systems and they are referred to as x64. (How Windows runs 32-bit applications on 64-bit is explained in Chapter 8 of Part 2.) Additionally, as of Server 2003, IA-64 are no longer supported by Windows.

Newer editions of Windows support the ARM processor. For example, Windows RT was a version of Windows 8 that ran on ARM architecture, although that has been discontinued. Windows 10 Mobile—the successor to Windows 8.x operating systems—runs on ARM-based processors, such as Qualcomm Snapdragon models. Windows 10 runs on both x86 and ARM devices such as Raspberry Pi 2 (which use an ARM Cortex-A7 processor) and Raspberry Pi 3 (which use the ARM Cortex-A53). As ARM hardware has advanced to 64-bit, a new processor called AArch64, or ARM64, may also be at some point, as an increasing number of devices run on.

Windows achieves portability across hardware architectures and platforms in two primary ways:

- **By using a layered design** Windows has a layered design, with low-level layers of the system that are architecture-specific or platform-specific isolated into separate modules so that upper layers of the system can be shielded from the differences between architectures and hardware platforms. The two key components that provide OS portability are the kernel (contained in ntoskrnl.exe) and the HAL (contained in Hal.dll). Both components are described in more detail later in this chapter. Functions that are architecture-specific, as thread context switching and trap dispatching, are implemented in the kernel. Functions that differ within the same architecture (for example, motherboards) are implemented in the HAL.

- **By using C** The majority of Windows is written in C, with some portions in C++. Assembly language is used only for those parts of the OS that need to communicate directly with system hardware (such as the interrupt handler) or that are extremely performance-sensitive (such as context switching).
