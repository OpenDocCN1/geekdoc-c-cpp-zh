# Security auditing

The object manager can generate audit events as a result of an access check, and Windows functions available to user applications can generate them directly. Kernel-mode code is always allowed to generate an audit event. Two privileges, SecurityPrivilege and SeAuditPrivilege, relate to auditing. A process must have the SeSecurityPrivilege to manage the security event log and view or see an object's ACL. Processes that call system services, however, must have the SeAuditPrivilege to successfully generate an audit record.

The audit policy of the local system controls the decision to audit a particular type of security event. The audit policy, also called the Local Security Policy, Lsass maintains on the local system. It is configured with the Local Security Policy editor as shown in Figure 7-13. The audit policy configuration (both the basic settings under Local Policies and the Advanced Audit Policy Configuration) is stored in the registry as a bitmapped value in the HKEY_LOCAL_MACHINE\SECURITY\Policy\PolAdEv key.

Lsass sends messages to the SRM to inform it of the auditing policy at system-initialization time and when the policy changes. Lass is responsible for receiving audit records generated by the audit events from the SRM, editing the records, and sending them to the event logger. Lass (instead of the SRM) sends these records because it adds pertinent details, such as the information needed to completely identify the process that is being audited.

The SRM sends audit records via its ALPC connection to Lass. The event logger then writes the audit record to the security event log. In addition to the SRM passes, both Lass and the SAM generate audit records that Lsass sends directly to the event logger, and the AuthZ APIs allow for applications to generate application-defined audits. Audit records are put on a queue to be sent to the LSA as they are Received. They are not submitted in batches. The audit records are moved from the SRM to the security subsystem in two ways. If the audit record is small (less than the maximum ALPC message size), it is sent as an ALPC message. The audit records are copied from the address space of the SRM to the address space of the Lsass process. If the audit record is large, the SRM uses shared memory to make the access available to Lsass and simply passes a pointer in an ALPC message.

# Object access auditing

An important use of the auditing mechanism in many environments is to maintain a log of accesses to secure objects—in particular. For do this, the Audit object access policy must be enabled, and there must be audit ACEs in system access control lists that enable auditing for objects in question.

When an access attempts to open a handle to an object, the SRM first determines whether the attempt is allowed or denied. If object access is enabled, the SRM scans the system ACL of the object. There are two types of audit ACEs: access allowed and access denied. An audit ACE must match any of the security IDs held by the acceptor, it must match any of the access requested, and its type (access allowed or access denied) must match the result of the access check to generate an object access audit record.

Object access audit records include not just the fact of access allowed or denied, but also the reason for the success or failure. This “reason for access” reporting generally takes the form of an access control entry, specified in Security Descriptor Definition Language (SDDL), in the audit record. This allows for a diagnosis of scenarios in which an object to which you believe access should be denied is being permitted, or vice versa, by identifying the specific access control entry that caused the attempted access to succeed or fail.

As shown in Figure 7-13, object access auditing is disabled by default (as are all other auditing policies).

# EXPERIMENT: Object access auditing

You can observe access auditing by following these steps:

- 1. In Explorer, navigate to a file to you would normally have access (such as a text file), open its Properties dialog box, click the Security tab, and select the Advanced settings.
- 2. Click the Auditing tab and click through the administrative privileges warning. The resulting dialog box allows you to add auditing of access control entries to the file’s system access control list.

![](img/ff0e6a9d867a3a6e9527eb1d946810fc_696_0.png)

- 3. Click the **Add** button and choose **Select a Principal.**
- 4. In the resulting Select User or Group dialog box, enter your owner name or a group to which you belong, such as **Everyone**. Click **Check Names** and then click **OK**. This presents a dialog box for creating an Audit access control entry for this user or group for this file.

![](img/ff0e6a9d867a3a6e9527eb1d946810fc_696_1.png)

- 5. Click **OK** three times to close the file Properties dialog box.
- 6. In Explorer, double-click the file to open it with its associated program (for example, Notepad for a text file).
- 7. Click the **Start** menu, type **event**, and choose **Event Viewer.**

- 8. Navigate to the Security log. Note that there is no entry for access to the file. This is because the audit policy for object access is not yet configured.
- 9. In the Local Security Policy editor, navigate to Local Policies and choose Audit Policy.
- 10. Double-click Audit Object Access and click Success to enable auditing of successful access to files.
- 11. In Event Viewer, click Action and Refresh. Note that the changes to audit policy resulted in audit records.
- 12. In Explorer, double-click the file to open it.
- 13. In Event Viewer, click Action and Refresh. Note that several file access audit records are now present.
- 14. Find one of the file access audit records for Event ID 4656. This shows up as "a handle to an object was requested." (You can use the Find option to search for the file name you.)
- 15. Scroll down in the text box to find the following example shows two access methods, READ_CONTROL, SYNCHRONIZE, ReadAttributes (extended attributes), and ReadData were requested. READ_CONTROL was granted because the ancestor was the owner of the file. The others were granted because of the implicit control entry.

# Global audit

In addition to object-ACEs on individual objects, a global audit policy can be defined for the system that has access auditing for all-system objects, registry keys, or for both. a security auditor can be certain that the desired auditing will be performed, without having to set or examine SACLs on all the individual objects. As with changes to objects changing these requiresSecurityPrivilege.

# EXPERIMENT: Setting global audit policy

You can use the Auditpol command to enable global audit policy.

- 1. If you didn't already do so in the previous experiment, open the Local Security Policy editor, navigate to the Policy settings (refer to Figure 7-13), double-click **Audit Object Access**, and enable auditing for both success and failure. On most systems, SACLs specifying access auditing are uncommon, so few if any object-access audit records will be produced at this point.
- 2. In an elevated command prompt window, enter the following command. This will produce a summary of the commands for setting and querying global audit policy.

```
C:\> audittpol /resourceSACL
```

- 3. In the same command prompt window, enter the following commands. On a typical system, each of these commands will report that no global SACL exists for the resource type. (Note that the File and Key keywords are case-sensitive).

```
C:\> audittpol /resourceSACL /type:File /view
C:\> audittpol /resourceSACL /type:Key /view
```

- 4. In the same elevated command prompt window, enter the following command. This will set a global audit policy that all attempts to open files for write (F) by the indicated user will result in audit records, whether the attempt succeed or fail. The user name can be a specific user name on the system, a group such as Everyone, a domain-qualified user name such as domain\username, or a SID.

```
C:\> audittpol /resourceSACL /set /type:File /user:username /success
/failure /access:FW
```

- 5. While running under the user indicated, use Explorer or other tools to open a file. Then look at the security log in the system log to find the audit records.
- 6. At the end of the experiment, use the auditpol command to remove the global SACL you created in step 4, as follows:

```
C:\> audittpol /resourceSACL /remove /type:File /user:username
```
