After the Start I/O completes, the returns, and no particular code is running in the driver, the hardware is working and "does its thing." While the hardware device is working, more requests can come to the device (if using asynchronous operations) or other threads that also opened handles to the device. In this case the dispatch routine would realize the device is busy and insert the IRP into the queue as mentioned, where one way to achieve this is with a call to IoStartPacket.

+   5. When the device is done with the current operation, it raises an interrupt. The kernel trap handles the CPU context for whatever thread was running on the CPU that was selected to handle the interrupt, raises the IRQL of that CPU to the IRQL associated with the interrupt (DIRQL) and jumps to the registered ISR for the device.

+   6. The ISR, running at Device IRQL (above 2) does as little as possible, telling the device to stop the interrupt and signaling the status or other required information from the hardware device. As its last act, the ISR queues a DPC for further processing at a lower IRQL. The advantage of using a DPC to perform most of the device servicing is that any blocked interrupt whose IR lies between the Device IRQL and the DPC/dispatch IRQL (2) is allowed to occur before lower-priority DPC processing occurs. Intermediate-level interrupts are served more promptly than they otherwise would, and would reduce latency on the system.

+   7. After the interrupt is dismissed, the kernel notices that the DPC queue is empty and uses a software interrupt at IRQL DPC_LEVEL (2) to jump to the DPC processing loop.

+   8. Eventually, the DPC is dequeued and executed at IRQL 2, performing two main operations:

+   * It gets the IRP in the queue (if any) and starts the new operation for the device. This is done to prevent the device from being idle for too long. If the dispatch routine uses IoStartPacket, the DPC routine calls its counterpart, IoStartPacket, which does just that. If an IRP is available, the Start I/O routine is called in an arbitrary thread context. This is why in the general case, the Start I/O routine is called in an arbitrary thread context. If there are no IRPs in the queue, the device is marked busy—that is, ready for the next request that comes in.
* It completes the IRP, whose operation has finished by the driver calling IoCompleteRequest. From that point, the driver is no longer responsible for the IRP and it shouldn't be touched, as it can be fed at any moment after the call. IoCompleteRequest calls any completion routines that have been registered. The I/O manager frees the IRP (it's actually using a completion routine of its to do that)

+   9. The original requesting thread needs to be notified of the completion. Because the current thread executing the DPC is arbitrary, it's not the original with its original address space. To execute code in the context of the requesting thread, a special kernel APC is issued to the thread. An APC is a function that is forced to execute in the context of a particular thread. When the requesting thread gets CPU time, the special kernel APC executes first (at IRQL APC_LEVEL=1). What that needs, is releasing the thread from waiting, signing an event that registered in an asynchronous operation, and so on. (For more on APCs, see Chapter 8 in Part 2.)
