Note that this assumes the threads in a process are doing an equal amount of work. This is typically not the case in a multithreaded process, which normally has one or more housekeeping threads and numerous worker threads. a multithreaded application that wants to take full advantage of the platform might find it advantageous to specify the processor groups for its threads by using SetThreadIdealProcessor function. To take advantage of processor groups, developers should call SetThreadIdealProcessorEx instead, which allows selection of a group number for the affinity.

In 64-bit Windows, the Stride field in the NODE is used to balance the affinity of newly created threads within a process. The stride is a scale number that represents the number of affinity bits within a Numa node that must be skipped to attain a new independent logical processor slice, where independent means another core (if dealing with an SMT system) or another package (if dealing with a non-SMT multicore system). Because 32-bit Windows doesn't support large processor-configurations it doesn't use a stride. It simply selects the next processor number, trying to avoid sharing the same SMT set if possible.

## Ideal node

On NUMA systems, when a process is created, an ideal node for the process is selected. The first process is assigned to node 0, the second process to node 1, and so on. Then the ideal processors for threads in the process are chosen from the process's ideal node. The ideal processor for the first thread in a process is assigned to the first processor in the node. As additional threads are created in processes with the same ideal node, the next processor is for the next thread's ideal processor, and so on.

## CPU sets

You've seen affinity (sometimes referred to as hard affinity) can limit threads to certain processes, which is always honored by the scheduler. The ideal processor mechanism tries to run threads on their ideal processors (referred to as soft affinity), generally expecting to have the thread's state part of processor's cache. The ideal processor may or not be used, and it does not prevent the thread from being scheduled on other processors. But these mechanisms don't work on system-related activity, such as system threads activity. Also, there is no easy way to set affinity to all processes in a system in one stroke. Even the process would not work. System processes are generally protected from external affinity changes because they require the PROCESS_SET_INFORMATION access, which is not granted for processes.

Windows 10 and Server 2016 introduce a mechanism called CPU sets. These are a form of affinity that you can set for the system as a whole (including system threads affinity), processes, and individual threads. For example, a low-latency application may want to use a processor exclusively while the rest of the system is diverted to other processors. CPU sets provide a way to achieve that.

The documented user API is somewhat limited at the time of this writing. GetSystemCpuSet-Information returns an array of SYSTEM_CPU_SET_INFORMATION that contains data for each CPU set.

These IDs are the ones that must be passed to SetDefaultCPUs and SetThreadCPUs to function default CPU sets for a process and a CPU for a specific thread, respectively.

An example for setting CPU set would be for an "important" thread that should not be interrupted if possible. This thread could have a CPU set that contains one CPU, while setting the default process CPU set to include all other CPUs.

One missing function in the Windows API is the ability to reduce the system CPU set. This can be achieved by a call to the NtSystemSystemInformation system call. For this to succeed, the caller must haveSeIncreasePriorityPrivilege.
