
- They allow for the specification of a custom memory partition, which enables usage of the Memory Partitioning API described in Chapter 5.

- They serve as a key enabler for features such as Run As (Secondary Logon), Application Boxing, and Program Compatibility Assistant.

- They provide part of the security sandbox for applications such as Google Chrome and Microsoft Office Document Converter, as well as mitigation from denial-of-service (DoS) attacks through Windows Management Instrumentation (WMI) requests.

## Job limits

The following are some of the CPU-, memory-, and I/O-related limits you can specify for a job:

- **Maximum number of active processes** This limits the number of concurrently existing processes in the job. If this limit is reached, new processes assigned to the job are blocked from creation.

- **Job-wide user-mode CPU time limit** This limits the maximum amount of user-mode CPU time that the job can consume (including processes that have run and exited). Once this limit is reached, by default all the processes in the job are terminated with an error code and no new processes can be created in the job (unless the limit is reset). The object is signaled, so any waiting threads for the job will be released. You can change this behavior with a call to SetInformationToObjectToEndJobAction member of the JOBOBJECT_END_OF_JOB_TIME_INFORMATION structure passed with the JobObjectOfTimeInformation information class and request a notification to the job's completion port inserted.

- **Per-process user-mode CPU time limit** This allows each process in the job to accumulate only a fixed maximum of user-mode CPU time. When the maximum is reached, the process terminates (with no chance to clean up).

- **Job processor affinity** This sets the processor affinity mask for each process in the job. (Individual threads can alter their affinity to any subset of the job affinity, but processes cannot alter their affinity setting.)

- **Job affinity** This sets a list of groups to which the job can be assigned. Any affinity changes are then subject to the group selection imposed by the limit. This is treated as a group-aware version of the job processor affinity limit (legacy), and prevents limit from being used.

- **Job process priority class** This sets the priority class for each process in the job. Threads can't increase their priority relative to the class (as they normally can). Attempts to increase thread priority are ignored. (No error is returned on calls to SetThreadPriority, but the increase doesn't occur).

- **Default working set minimum and maximum** This defines the specified working minimum and maximum for each process in the job. (This setting is not job-wide. Each process has its own working set with the same minimum and maximum values.)

- **Process and job committed virtual memory limit** This defines the maximum amount of virtual address space that can be committed by either a single process or the entire job.

- **CPU rate control** This defines the maximum amount of CPU time that the job is allowed to use before it experiences forced throttling. This is used as part of the scheduling group postscript in Chapter 4.

- **Network bandwidth rate control** This defines the maximum outgoing bandwidth for the entire job before throttling takes effect. It also enables a differentiated services code (DSCP) tag for QoS services for each network packet sent by the job. This can only be set for one job in a hierarchy, and affects all its child jobs.

- **Disk I/O bandwidth rate control** This is the same as network bandwidth rate control, but is applied to disk I/O and can control either itself or the I/O operations per second (IOPS). It can be set for a particular volume or for all volumes on the system.

With many limits, the job can control specific thresholds, at which point a notification will be sent (or, if no notification is registered, the job will be killed). Additionally, rate controls allow tolerance ranges and rate intervals—example allowing a process to go beyond 20 percent of its bandwidth limit for up to 10 seconds or 5 minutes. These notifications are denied by queuing an appropriate message to the I/O completion port for the job. (See the Windows SDK documentation for details.)

Finally, you can place user-interface limits on processes in a job, including restricting processes from opening handles to windows owned outside the job, reading and writing to the clipboard, and changing the user-interface parameters via the Windows System-ParametersInfo function. These user-interface limits are managed by the Windows subsystem GDI/USER driver, Win32k.sys, and are enforced through one of the calls that it registers with the process manager, the job callout. You can gain access for all processes in a job to specific user handles (for example, window handle) by calling the UserHandleAccess function; this can only be called by a process that is not part of the job in question (naturally).

## Working with a job

A job object is created using the CreateJobObject API. The job is initially created empty of any process. To add a process to a job, call the AssignProcessToJobObject, which can be called multiple times to add to the job or even add the same process to multiple jobs. This last option creates a nested job, described in the next section. Another way to add a process to a job is to manually handle the job object by using the PS_JOB_LIST process-create attribute described earlier in this chapter. One or more handles to job objects can be specified, which will be joined.

The most interesting API for jobs is SetInformationJobObject, which allows the setting of the various limits and settings mentioned in the previous section, and contains internal information classes used by mechanisms such as Containers (Silo), the DAM, or Windows UWP applications. These values can be read with QueryInformationJobObject, which can provide interested parties with the limits on a job. It's also necessary to call limit notifications have have been set (as described in the previous section) for the caller to know precisely which limits were violated. Sometimes-useful function is TerminateJobObject, which terminates all processes in the job (as TerminateJobProcess was called on each process).

## Nested jobs

Until Windows 7 and Windows Server 2008 R2, a process could only be associated with a single job, which makes jobs less useful than they could be, as in some cases an application could not know advance whether a process it needed to manage happened in a job or not. Starting with Windows 8 and Windows Server 2012, a process can be associated with multiple jobs, effectively creating a job hierarchy.

A child job holds a subset of processes of its parent job. Once a process is added to more than one job, the system tries to form a hierarchy, if possible. A current restriction is that jobs cannot form a hierarchy if any of them set UI limits (SetInformationJobObject with JobObjectBasicIRestrictions).

Job limits for a child job cannot be more permissive than its parent, but they can be more restrictive. For example, if a parent job sets a memory limit of 100 MB for the job, any child job cannot set a higher memory limit (such requests simply fail). A child job can, however, set a more restrictive limit for its processes (and any child jobs it has), such as 80 MB. Any notifications that target the I/O completion port for a job will be sent to the job and all its ancestors. (The job itself does not have to have an I/O completion port to be sent to ancestors).

Resource accounting for a parent job includes the aggregated resources used by its direct processes and all processes in child jobs. When a job is terminated (TerminateJobObject), all processes in the job and in child jobs are terminated, starting with the child jobs at the bottom of the hierarchy.
