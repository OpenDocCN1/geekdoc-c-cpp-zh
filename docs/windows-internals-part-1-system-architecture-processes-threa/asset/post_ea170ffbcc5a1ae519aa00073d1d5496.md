You can describe the names of these exported functions more easily if you understand the naming convention for Windows system routines. The general format is

<Prefix><Operation><Object>

In this format, Prefix is the internal component that exports the routine, Operation tells what is being done to the resource, or Object, identifies what is being operated on.

For example, AllocatePoolWithTag is the executive support routine to allocate a paged or non-paged pool. InitializeThread is the routine that allocates and sets up a kernel thread.

## System processes

The following system processes appear on every Windows 10 system. One of these (Idle) is not a process at all, and three—System, Secure System, and Memory Compression—are full processes because they are not running a user-mode executable. These types of processes are called minimal processes and are described in Chapter 3.

- Idle process this contains one thread per CPU to account for idle CPU time.
- System process this contains the majority of the kernel-mode system threads and handles.
- Secure System process this contains the address space of the secure kernel in VTL 1, if running.
- Memory Compression process this contains this compressed working set of user-mode processes, as described in Chapter 5.
- Session manager (Smss.exe).
- Windows subsystem (Csrss.exe).
- Session 0 initialization (Winitinit.exe).
- Logon process (Winlogon.exe).
- Service Control Manager (Services.exe) and the child process it creates are such as the system-generated generic-host process (Svchost.exe).
- Local Security Authentication Service (Lass.exe), and if Credential Guard is active, the Isolated Local Security Authentication Server (Laiso.exe).

## System process and system threads

The system process (process ID 4) is the home for a special kind of thread that runs only in kernel mode: *kernel-mode system thread*. System threads have all the attributes and contexts of regular user-mode threads such as a hardware context, priority, and so on, but differ in they run only in kernel-mode executing code in system space, whether that is in Ntoskrnl.exe or in other loaded device driver. In addition, system threads don't have a user address space and must allocate dynamic storage from OS heaps, such as a non-paged pool.

> Note On Windows 1511, Task Manager calls the process System and Compressed Memory. This is because of a new feature in Windows 10 that compresses memory rather than paging it out to disk. This mechanism is further described in Chapter 5. You will remember the System process refers to this one, no matter the name displayed by this tool or other. Windows 10 Version 1607 and Server 2016 revert the name of the System process to System. This is because a new process called Memory Compression is used for compressing memory. Chapter 5 discusses this in more detail.

System threads are created by the PsCreateSystemThread or IoCreateSystemThread functions, both documented in the WDK. These threads can be called only from kernel mode. Windows, as well as various device drivers, create system threads during system initialization to perform operations that require thread context, such as indexing and waiting for I/Os or other objects or polling a device. For example, the memory manager uses system threads to implement such functions as writing dirty pages to the page file or mapped files, swapping processes in and out of memory, and so forth. The kernel creates a thread called the balance set manager that wakes up once per second to possibly initiate scheduling and memory-related events. The cache manager also uses system threads to implement both read-ahead and write-behind I/Os. The file server driver (Srv2.sys) uses system threads to respond to I/O requests for file data on disk partitions shared to the network. Even the floppy driver has a system thread to poll the floppy device. (Polling is more efficient in this case an interrupt-driven floppy driver consumes a large amount of system resources.) Further information on system threads is included in the chapters in which the corresponding component is described.

By default, system threads are owned by the System process, but a device driver can create a system thread in any process. For example, the Windows subsystem device driver (Win32k.sys) creates a system thread inside the Canonical Display Driver (Cdd.dll) part of the Windows subsystem process (Csrss.exe) so that it can easily access data in the user-mode address space of that process.

When you're troubleshooting or going through a system analysis, it's useful to map the execution of individual system threads back to the driver or even to the subroutine that contains the code. For example, on a heavily loaded server, the System process will likely consume considerable CPU time. But knowing that the System process is running, "some thread" is running is not enough to determine which driver or OS component is running.

So if threads in the System process are running, first determine which ones are running (for example, with the Performance Monitor or Process Explorer tools). If you find the (or threads) that are running, look up which driver thread began execution. This at least tells you which driver likely created the thread. For example, in Process Explorer, right-click the System process and select Properties. In the Threads tab click the CPU column to view the most active thread. Select this thread and click the Module button to see the file with the code on top stack is running. Because the System process is protected in recent versions of Windows, Process Explorer is unable to show a call stack.

## Secure System process

The Secure process (variable process ID) is technically the name of the VTL 1 kernel address space, handles, and threads. That said, because scheduling, object management, and memory management are owned by the VTL 0 kernel, no such entities will be associated with this process. Its only role is to provide a visual indicator to users (for example, in tools such as Task Manager and Process Explorer) that VBS is currently active.

## Memory Compression process

The Memory Compression process uses its user-mode address space to store the compressed pages of memory that correspond to standby memory that has been evicted from the working sets of certain processes. Unlike the Secure System process, the Memory Compression process actually hosts a number of system threads, usually seen as SmWorker and SmReadThread. Both of these belong to the Store Manager that manages memory compression.

Additionally, unlike the other processes in this list, which also stores its memory in the user-mode address space. This means it is subject to working trimming and will potentially cause large virtual memory usage in system-monitoring tools. In fact, if you view the Performance tab in Task Manager, which now shows both in-use and compressed memory, you should see that the size of the Memory Compression process's working set is equal to the amount of compressed memory.
