6. If the process is part of a job object, the process flags requested a virtual Desktop machine (VDM), the flag is ignored.

7. The security attributes for the process and initial thread that were supplied to the CreateProcess function are converted to their internal representation (OBJECT_ATTRIBUTES structures, documented in the WDK).

8. CreateProcessInternal checks whether the process should be created modern. The process is to be created modern if so specified by attribute (PROC_THREAD_ATTRIBUTE_PACKAGE_FULL_NAME) with the full package name or the creator is itself modern (and a parent process has not been explicitly specified by the PROC_THREAD_ATTRIBUTE_PARENT_PROCESS attribute). If so, a call is made to the internal BaseAppExtension to gather more contextual information on the modern app described by a structure called APX_PROCESS_CONTEXT. This context holds information such as the package name (internally referred to as package moniker), the capabilities associated with the app, the current directory for the process, and whether the app should have full trust. The option of creating full trust modern apps is not publicly exposed, and is reserved for apps that have the modern look and feel perform operations. A canonical example is the Settings app in Windows 10 (SystemSettings.exe).

9. If the process is to be created modern, the security capabilities (provided by PROC_THREAD_ATTRIBUTE_CAPABILITIES) are recorded for the initial token creation by the internal BaseCreatebox function. The term LowBox refers to the sandbox (AppContainer) under which the process is to be executed. Note that although creating modern processes by directly calling CreateProcess is not supported (instead, the COM interfaces described be used), the Windows SDK and MSDN provide the ability to create AppContainer legacy applications by passing this attribute.

10. If a modern process is to be created, then a flag is set to the kernel to skip manifest detection. Modern processes should never have an embedded manifest as it is simply not needed. (A modern app has a manifest of its own, unrelated to the embedded manifest referenced here.)

11. If the debug flag has specified (DEBUG_PROCESS), the Debugger value under the Image File Execution options key (discussed in the next section) for the executable is marked to be skipped. Otherwise, a debugger will never be able to create its debugger process because the creation will enter an infinite loop (trying to create the debugger process over and again).

12. All windows are associated with desktops, the graphical representation of a workspace. If no desktop is specified in the STARTUPINFO structure, the process is associated with the caller’s current desktop.

> Note The Windows 10 Virtual Desktop feature does not use multiple desktop objects (in the kernel object). There is still one desktop, but windows are shown and hidden as required. This is in contrast to the Sysinternals desktops.exe tool, which really creates up to four desktop objects. The difference can be felt when moving a window from one desktop to another. In the case of desktops.exe, it can't be done, as such an operation is not supported in Windows. On the other hand, Windows 10's Virtual Desktop allows it, since there is no real "moving" going on.

13. The application and command-line arguments passed to CreateProcessInternalW are analyzed. The executable path name is converted to the NT name (for example, c:\temp\a.exe turns into something \device\harddiskvolume\temp\a.exe) because some functions require it in that format.

14. Most of the gathered information is converted into a large structure of type RTL_USER_PROCESS_PARAMETERS.

Once these steps are completed, CreateProcessInternalW performs the initial call to NtCreateUserProcess to attempt creation of the process. Because Kernel32.dll has no image at this point whether the application image name is a real Windows application or a batch file (.bat or .cmd), 16-bit, or DOS application, the call might fail, at point CreateProcessInternalW looks at the error reason and attempts to correct the situation.

# Stage 2: Opening the image to be executed

At this point, the creating thread has switched into kernel mode and continues the work within the NtCreateUserProcess system implementation.

1. NtCreateUserProcess validates first arguments and builds an internal structure to hold all creation information. The reason for validating arguments again is to make sure the call to the executive did not originate from a hack that managed to simulate the Ntdll.dll makes the transition to the kernel with bogus or malicious arguments.

2. As illustrated in Figure 3-11, the next stage in NtCreateUserProcess is to find the appropriate Windows image that will run the executable file by the caller and to create a section object to later map it into the address space of the new process. If the call fails for any reason, it returns to CreateProcessInternalW with a failure state (look ahead to Table 3-8) that causes CreateProcessInternalW to attempt execution again.

3. If the process needs to be created protected, it also checks the signing policy.

4. If the process is to be modern, a licensing check is done to make it's licensed and allowed to run. If the app is inbox (preinstalled with Windows), it's allowed to run regardless of license. If sideloading apps is allowed (configured through the Settings app), then any signed app can be executed.

5. If the process is a Trustlet, the section object must be created with a special flag that allows the secure kernel to use it.

6. If the executable file is a Windows EXE, NtCreateProcess tries to open and create a section object for it. The object is not mapped into memory, but it is opened. Just because a section object has successfully created not mean the file is a Windows image, it could be a DLL or POSIX executable. If the file is a POSIX executable, the call fails, because POSIX is no longer supported. If the file is a DLL, CreateProcessInternal fails as well.

7. Now NtProcess has found a valid Windows executable, as part of the process creation code in the next section, it looks in the registry under HKLM\SOFTWARE\Microsoft\NT\CurrentVersion\Image Execution Options to see whether a subkey with the file name and extension of the executable image (but without the directory and path information—example Notepad) exists. If it does, PspAllocateProcess looks for a named debugger for that. If this value is present, the image to run becomes the string in that value and CreateProcessInternal restarts at stage 1.

> Note You can take advantage of this process-creation behavior and debug the startup code of Windows services before they start rather than attach the debugger after starting, which doesn't allow you to debug the startup code.

8. On the other hand, if the image is not a Windows EXE (for example, if it's an MS-DOS or a Win16 application), CreateProcessInternal goes through a series of steps to find a Windows support image to run it. This process is necessary because non-Windows applications aren't run directly. Windows uses one of a few special images that, in turn, are responsible for actually running the non-Windows process. For example, if you attempt to run an MS-DOS or a Win16 executable (32-bit Windows only), the image to run becomes the Windows executable Ntdvm.exe. In short, you can't directly create the activated image as a process that is not a Windows process. If Windows can't find a way to resolve the activated image (as shown in Table 3-8), CreateProcessInternal fails.
