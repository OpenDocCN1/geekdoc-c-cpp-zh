Although the format of these prototype PTEs is the same as that of the PTEs described earlier, the prototype PTEs are a layer between the page table and the PFN database and never appear directly in page tables.

By having all copies of a potentially shared page point to a prototype PTE to resolve faults, the memory manager can manage shared pages without updating the page tables of each process sharing it. For example, a shared code or data page might be paged out to disk at some point. When the memory manager retrieves the page from disk, it only needs to update the prototype PTE to point to the page's new location. The PTEs in each of the processes sharing the page remain the same, with the valid bit set and pointing to the prototype PTE. Later, as processes reference the real PTE, the real PTE will get updated.

The second page is in the paging file—the prototype PTE contains its exact location. The process PTE (and any other processes with that page mapped) points to this prototype PTE.

# In-paging I/O

In-paging I/O occurs when a read operation be issued to a file (paging or mapped) to satisfy a page fault. Because page tables are themselves pageable, the processing of a page fault can incur additional I/O if necessary when the system is loading the page table page that contains the PTE or the prototype PTE that describes the original page referenced.

The in-paging I/O operation is synchronous—that is, the thread waits on the I/O completes—and isn't interruptible by asynchronous procedure call (APC) delivery. The pager uses a special modifier in the I/O request to indicate paging I/O. Upon completion of paging I/O, the I/O system triggers an event, which wakes up the pager and allows it to continue paging.
