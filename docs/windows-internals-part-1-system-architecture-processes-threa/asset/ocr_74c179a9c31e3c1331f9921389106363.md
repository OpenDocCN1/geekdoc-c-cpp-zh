# EXPERIMENT: Viewing a device stack

The !device kernel debugger shows you the device stack of layered device objects associated with a specified device object. This example shows the device stack associated with a device object, 'device\keyboardclass0, which is owned by the keyboard class driver:

```
1kd !devstack keyboardclass0
!DevObj             !DevObj             ObjectName
 > fff9c8c04244400\Driver\keyboardclass
fff9c8c0424c247c\Driver\khdhid
fff9c8c042410060\Driver\shkidmf
1kdDevMethods         fff9c8c04245290 [AFD]
fff9c8c0424c4910     fff9c8c0424141b0 000003f
DeviceInst is "HID\MSHw0029c101\S1599b1c7&00000"
ServiceName is "kbdhid"
```

The output highlights the entry associated with KeyboardClass to the character in the first column. The entries above that line are layered above the keyboard class driver, and those below are layered beneath it.

# EXPERIMENT: Examining IRPs

In this experiment, you will find an incomplete IRP on the system, and will determine the IRP type, where it is directed, the driver that manages the device, the thread that issued the IRP, and which process thread belongs to. On a 32-bit system with non-local kernel debugging. This experiment is best performed with local kernel debugging as well, as IRPs may complete during the period when commands are issued, so some instability of data can be expected.

At any time, there are at least a few incomplete IRPs on a system. This occurs because there are many devices to which applications can issue IRPs that a driver will complete only when a particular event occurs, such as data becoming available. One example is a blocking read from a network endpoint. You can see the IRPs on the system with irfind kernel debugger (may take some time; you can stop after some IRPs appear):
