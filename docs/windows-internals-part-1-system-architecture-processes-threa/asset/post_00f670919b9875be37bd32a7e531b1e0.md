
# AppContainer security environment

One of the biggest side-effects caused by the presence of an AppContainer SID and related flags is that the access check algorithm you saw in the "Access checks" earlier in this chapter is modified to essentially ignore all regular user and group SIDs that the token may contain, essentially treating them as deny-only SIDs. This means that even though Calculator may be launched by a user John Doe belonging to the Users and Everyone, it will fail access to John Doe's SID, the Users SID, or the Everyone group. In fact, the only SIDs that are checked during the discretionary access check will be that of the AppContainer SID, followed by the capability access check algorithm, which will look at any capability SID part of the token.

Taking even further merely treating the discretionary SIDs as deny-only, AppContainer tokens effect one further critical security change to the access check: a NULL DACL, typically treated as an allow-any situation due to the lack of any information (recall that this is different from an empty DACL, which is a deny-only situation and ignored and treated as a deny situation). To make matters simpler, the only types of objects that an AppContainer can access are those that explicitly have an allow ACE for its AppContainer SID or for one of its capabilities. Unexpected (NULL DACL) objects are out of the game.

This situation causes compatibility problems. Without access to the most basic file system, registry, and object manager resources, how can an application ever function? Windows takes this into account by creating a custom execution environment, "jail" if you will, specifically for each AppContainer.

> Note So far we've implied that each UWP packaged application corresponds to one AppContainer token. However, this doesn't necessarily mean that only a single executable file can be associated with an AppContainer. UWP packages can contain multiple executables, all of which belong to the same AppContainer. These allow them to share the same SID and capabilities and exchange data between each other, such as a micro-service back-end and a front-end executable.

- The AppContainer SID's string representation is used to create a subdirectory in the object manager's namespace under \Sessions\AppContainerNamedObjects. This becomes the primary directory of named kernel objects. This specific subdirectory object is ACLed with the AppContainer SID associated with the AppContainer that has an allow-all access. This is in contrast to desktop apps, which all use the \Sessions\BasedObjects subdirectory (within the same session). We'll discuss the implications of shortly, as well as the requirement for the token to now handle stores.

- The token will contain a LowBox number, which is a unique identifier for an array of LowBox Number entries that store the kernel stores in the g_SessionLowBoxArray variable. Each of these maps to the SEP_LOWBOX_NUMBER_ENTRY structure that, most importantly, contains an atom table unique to this AppContainer, because the Windows Subsystem Kernel Driver (Win32k.sys) does not allow AppContainers access to the global atom table.

- The file system contains a directory in %LOCALAPDATA%\Packages. Inside it are the package monikers (the string version of the AppContainer SID—that is, the package name) of all the installed UWP applications. Each of these directories contains application-specific directories, such as TempState, RoamingState, Settings, LocalCache, and others, which are ACLed with the specific AppContainer SID to the application, and set to allow-allow access.

- Within the Settings directory is a Settings.dat file, which is a registry file that is loaded as an application hive. (You will learn more about application hives in Chapter 9 in Part 2). The hive acts as the local registry for the application, where WinRT APIs serve the various persistent state of the application. Once again, the ACL on the registry keys explicitly grants allow-allow access to the associated AppContainer SID.

These joins allow AppContainers to secure, locally, and store their file system, registry, and atom without requiring access to sensitive user and system areas on the system. That said, without the ability to access, at least in read-only mode, critical files (such as Ntdll.dll and Kernel32.dll) or registry keys (such as the ones these will need), or even objects (such as the RPC ControlAPC port used for DNS lookups?) It would not make sense, each UWP application or installation, to re-acl entries, registry keys, and namespaces to add or remove various SIDs.

To solve this problem, the subsystem understands a specific group SID ALL APPLICATION PACKAGES, which automatically binds itself to any AppContainer token. Many system locations, such as %SystemRoot%\System32 and HKLM\Software\Microsoft\Windows\CurrentVersion, will have this SID as part of their DACL, typically with a grant or read-and-execute access mask. Certain objects in the object manager have this name, such as the DNSResolver LPC port in the \RPC Control object manager. Other examples contain COM objects, which grant the execution right. Although not officially documented, third-party developers, who create non-UWP applications, also interact with UWP applications by applying this SID to their resources.

Unfortunately, UWP applications can load any Win32 DLL as part of their needs (because WinRT is built on top of Win32, as you saw), and because it's hard to predict what an individual UWP application might need, many system resources have the ALL APPLICATION PACKAGES SID installed as a precaution. When means there is no way for a UWP developer, to prevent DNS lookups from their application. This greater-needed access is also helpful for exploit writers, which could leverage it to escape the AppContainer sandbox. Newer versions of Windows 10, starting with version 1607 (Anniversary Update), contain an additional element of security to combat this: Restricted AppContainers.

By using the PROC_THREAD_ATTRIBUTE_ALL_APPLICATION_PACKAGES_POLICY process attribute and setting it to PROCESS_CREATE_ALL_APPLICATION_PACKAGES_OUT during process creation (Chapter 3 for more information on process attributes), the token will not be associated with any ACEs that specify the ALL APPLICATION PACKAGES SID, cutting off to many system resources that would otherwise be accessible. Such tokens can be identified by the presence of a fourth token attribute named W:\//NOALLAPPKG with an integer value set to 1.

Of course, this takes us back to the same problem: How would an application be able to load Ntdll.dll? Windows 10 version 1607 introduces a new group, called ALL RESTRICTED APPLICATION PACKAGES, which takes care of this problem. For example, the System32 directory also contains this SID, also set to run and execute permissions, because loading DLLs in this directory is key to the most sandboxed process. However, the DNSResolver ALPC port does not, so an AppContainer would lose access to DNS.
