In this architecture, the secure kernel is its own binary, which is found under the name curekernel.exe on disk. It's both an environment that restricts the allowed system calls that regular user-mode DLLs can make (thus limiting which of these DLLs can be loaded) and a framework that adds special secure system calls that can execute only under VTL 1. These additional system calls are exposed in a similar way as regular system calls: through an internal system library named dumpdll.dll (the VTL 1 version of Ntdll.dll) and a Windows subsystem-facing library named lumbar.dll). This implementation, mostly sharing the same standard Win32 API libraries, allows for the reduction of the memory overhead of VTL user-mode applications because essentially the user-mode code is present in VTL 0 counters. As an important note, copy-on-write mechanisms, which you'll learn more about in Chapter 5, prevent VTL 0 applications from making changes to binaries used by VTL 1.

With VBS, the regular user kernel rules apply, but are now augmented by VTL considerations. A simple way to achieve this is as follows: privilege levels (user versus kernel) enforce power. VTLs, on the other hand, enforce isolation. Although a VTL 1 user-mode application is not more powerful than a VTL 0 application or driver, it is isolated from it. In fact, VTL 1 applications aren't just more powerful; in cases, they have much less so. Because the secure kernel does not implement a full range of system calls, it-backs whatever system calls it forwards to the VTL 0 kernel. (Another name for secure kernel is proxy kernel). Any kind of I/O, file, network, and registry-based, is completely prohibited. Graphics, as another example, are out of the question. Not a single driver is allowed to be communicated with.

The secure kernel however, by running at VTL 1 and being in kernel, does complete access to VTL 0 memory and resources. It can use the hypervisor to limit the VTL 0 OS to access certain memory locations by leveraging CPU hardware support as Second Level Address Translation (SLAT). SLAT is the basis of Credential Guard technology, which can store secrets in such locations. Similarly, the secure kernel can use SLAT to intercept and control execution of memory locations, a key covenant of Device Guard.

To prevent normal device drivers from leveraging hardware devices to directly access memory, the system uses another piece of hardware known the I/O memory management unit (MMU), which effectively virtualizes memory access for devices. This can be used to prevent device drivers from using direct memory access (DMA) to directly access the hypervisor or secure kernel's physical regions of memory. This would bypass SLAT because no memory is involved.

Because the hypervisor is the first system to be loaded by the boot loader, it can grant the SLAT and I/O MMU as it sees fit, defining the VTL 0 and 1 execution environments. Then, while in VTL 1, the loader runs, loading the secure kernel, which can configure the system further to its needs.
