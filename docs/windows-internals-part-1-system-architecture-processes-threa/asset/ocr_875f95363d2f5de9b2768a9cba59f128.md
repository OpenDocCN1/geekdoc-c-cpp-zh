# I/O completion port operation

Windows applications create completion ports by calling the CreateIoCompletionPort Windows API and specifying a NULL completion port handle. This results in the execution of the NtCreateIoCompletion system. The executive's IoCompletion object contains a kernel synchronization object called a kernel queue. Then, the system creates a completion port object and initializes a queue object in the allocated memory (A pointer to this points to the queue object because the queue is the first member of the completion port). A kernel queue object has a concurrency value that is specified when initializes it, and in this case the value that used is the one that was passed to CreateIoCompletionPort. KeInitializeQueue is the function that NtCreateIoCompletion initializes a completion port's queue object.

When an application calls CreateIoCompletionPort to associate a handle with a port, the NtSetInformationFile system is executed with the file handle as the primary parameter. The information class is set FileCompletionInformation, and the completion port's handle and the CompletionKey parameter from CreateIoCompletionPort are the data values. NtSetInformationFile references the file handle to obtain the file object and allocates a completion context structure.

Finally, NtSetInformationFile sets the CompletionContext field in the file object to point at the context structure. When an asynchronous I/O operation operates on a file object, the I/O manager checks whether the CompletionContext in the file object is not-NULL. If it, the I/O manager allocates a completion packet and queues it to the completion port by calling KeInsertQueue with the port on which to insert the packet (which because the completion port object and queue object have the same address).

When a server invokes GetQueuedCompletionStatus, the NtRemoveIoCompletion system is executed. After validating parameters and translating the completion port handle to a pointer to the, NtRemoveIoCompletion calls RemoveIoCompletion, which eventually calls KeRemoveQueueEx. For high-performance scenarios, its possible that multiple I/os may have been completed, and although the thread will not block, it will still call the kernel each time to get item. The GetQueuedCompletionStatus or GetQueuedStatusEx API allows applications to retrieve more than one I/O status at the same time, reducing the number of user-kernel roundtrips and maintaining peak efficiency. Internally, this is implemented through the NtRemoveIoCompletion function. It calls RemoveIoCompletion with a count of queued items, which is passed to KeRemoveQueueEx.

As you can see, KeRemoveQueueEx and KeInsertQueue are the engine behind completion ports. They are the functions that determine whether a thread reading an I/O completion packet should be activated. Internally, a queue object maintains a count of the current number of active threads and the maximum number of active threads. If the current number equals exceeds the maximum when a thread calls KeRemoveQueueEx, the thread will be put (in LIFO order) on a list of threads waiting for a turn to process a completion packet. The list of threads hangs off the queue object. A thread's control data structure (KTHREAD) has a pointer in it that references the queue object of a queue that it is associated with; if the pointer is NULL, the thread isn't associated with a queue.
