Another question is: if applications launch in essentially a "service" session, how can they be interactive and process input and output? First, it is important to note that there is no GUI possible permitted launching under a Windows container, and attempting to use Remote Desktop (RDP) to access a container will be impossible. As such, only command-line applications can execute. Even such applications normally need an "interactive" session. So how can they function? The secret lies in a special process, CExec.exe, which implements the container execution service. This service uses a named pipe to communicate with the Docker and Vcompute services on the host, and is used to launch the actual containerized applications in the session. It is also used to emulate the console functionality that is normally provided by Hostexec, piping the input and output through the named pipe to the actual command prompt (or PowerShell) window that was used in the first place to execute the docker command on the host. This service is also used when using commands such as docker cp to transfer files from or to the container.

# Container template

Even if we take into account all the device objects that can be created by drivers as silos are created, there are still countless other objects, created by the kernel as well as other components, with which services running in silo 0 are expected to communicate, and vice-versa. In user mode, there is no silo monitor system that would allow components to support this, and forcing every driver to create a specialized device object to represent each silo wouldn't make sense.

If a santo to play music on the sound card, it shouldn't have to use a separate device object to represent the exact same sound card as every other silo would access, and as the host itself. This would only be needed if, say, per-silo object sound isolation was required. Another example is AFD. Although it uses a silo monitor, this is to identify user-mode service hosts the DNS client that needs to talk to kernel-mode DNS requests, which will be per-silo, and not to create separate \Silos\Device\AFD objects, as there is one network/Winsock inside the system.

Beyond drivers, the registry also contains various pieces of global information that must be visible and across all silos, the VReg container then provide sandboxing around.

To support all the needs, the silo namespace, registry, and file system are defined by a specialized container file, which is located in %SystemRoot%\System32\Containers\wsc.def by default, once the Windows Containers features are enabled in the Add/Remove Windows Features dialog box. This file describes the object manager and registry rules and ruling surrounding it, allowing the definition of symbolic links as needed to the true objects on the host. It also describes which job object, volume mount points, and network isolation policies should be used. In theory, future use of silo objects in the Windows operating system could allow different files to be used for other kinds of containerized environments.
