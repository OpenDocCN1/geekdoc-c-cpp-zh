## Protected processes

In the Windows security model, any process that is protected is denied certain access rights that would normally be granted to administrators. At the kernel level, support for protected processes is twofold. First, the bulk of process creation occurs in kernel mode (The flow for both protected and standard process creation is described in the next section). Protected processes (and their extended cousin, PPL, described in the next section) have special bits in the EPROCESS structure that modify the behavior of the process manager. In fact, the only access rights granted for protected processes are PROCESS_QUERY/SET_LIMITED_INFORMATION, PROCESS_TERMINATE and PROCESS_SUSPEND/RESUME. Access rights are also denied for threads running inside protected processes. We will look at these rights in Chapter 4. Because Process Explorer uses user-mode APIs to query information on process internals, it is unable to perform operations on such processes. On the other hand, a tool like Winbg in kernel-debugging mode, uses kernel-mode infrastructure to obtain this information, will be able to display complete information. See the experiment in the "Thread internals" section of Chapter 4 on how Process Explorer behaves when confronted with a protected process.

> Note As mentioned in Chapter 1, to perform kernel debugging, you must boot in debugging mode (enabled by bcdedit /dev or by using the Msconfig advised boot options). This mitigates debugger-based attacks on protected processes and the PMP. When booted in debugging mode, high-definition content playback will not work.

Limiting these access rights reliably allows the kernel to sandbox a protected process from user-mode access. On the other hand, a protected process is indicated by a flag in the EPROCESS structure; an administrator can still load a kernel-mode driver that modifies this. However, this would be a violation of the PMP model and considered malicious, and such a driver would likely eventually be blocked from loading on a 64-bit system because the kernel-mode code-signing policy prohibits the signing of malicious code. Additionally, kernel-mode patch protection, known as PatchGuard (described in Chapter 7), as well as the Protected Environment and Authentication Driver, protect the integrity of the kernel.
