## Terminating a process

A process is a container and a boundary. This means resources used by one process are not necessarily visible in other processes, so some inter-process communication mechanism needs be used to pass information between processes. Therefore, a process cannot accidentally write arbitrary bytes on another process's memory. That would require explicit call to a function such as WriteProcessMemory. However, to get that to work, a handle with the proper access mask (PROCESS_VM_WRITE) must be opened explicitly. Natural isolation between processes may or not be granted. If some exception happens in one process, it will have no effect on other processes. The worst that can happen is that the same process would crash, but the rest of the system remains intact.

A process can exit gracefully by calling the ExitProcess function. For many processes—the startup code for the first thread calls ExitProcess on the process's behalf when returns from its main function. The term *gracefully* means that DLLs loaded into the process get a chance to do work by getting notified of the process exit using a call to their DMain function with DLL_PROCESS_DETACH.

ExitProcess can be called only by the process itself asking to exit. An ungraceful termination of a process is possible using the TerminateProcess function, which can be called from outside the process.(For example, Process Explorer and Task Manager when requested.) TerminateProcess requires a handle to the process that is opened with the PROCESS_TERMINATE access mask, which may or not be granted. It's not easy (or it's impossible) to terminate some processes (for example, Csrss—the handler with the required access mask cannot be obtained by the requester.)

The meaning of ungraceful here is that DLLs don't get a chance to execute code (DLL_PROCESS_DETACH is not sent) and all threads are terminated abruptly. This can lead to data loss in some cases—for example, if a file cache has no chance to flush its data to the target file.

In whatever way a process ceases to exist, there can never be any leaks. All process's private memory is freed by the kernel, the address space is destroyed, handles to kernel objects are closed. If open handles to the process still exist (the PROCESS structure exists), other processes can gain access to process-management information, such as the process exit code (GetExitCode). Once these handles are closed, the PROCESS is destroyed, and there's truly nothing left of the process.

That being, if third party makes allocations in kernel memory on behalf of a process—say, due to an IOCTL or merely due to a process notification—it is responsibility to free any pool memory on when. Windows does not track or clean process-owned kernel memory (except for memory objects by handles that the process created). This would typically be done through the IRP_MJ_CLOSE or IRP_MJ_CLEANUP notification to tell the driver that the device object has closed, or through a process termination notification. ## Image loader

We have just seen, when a process is started on the system, the kernel creates an object to represent it and performs various kernel-related initialization tasks. However, these tasks do not result in the execution of the application, merely in the preparation of its context and environment. In fact, unlike drivers, which are kernel-mode code, applications execute in user mode. Most of the actual initialization work is done outside the kernel. This work is performed by the *image loader*, internally referred to as Ldr.

The image loader lives in the user-mode system *Ntdll.dll* and not in the kernel library. Therefore, it behaves just like standard code that is part of a DLL, and it is subject to the restrictions in memory access and security rights. This makes this code special the guarantee that it will always be present in the running process (Ntdll.dll is always loaded) and it is the first piece of code to run

Because the loader runs before the actual application code, it is usually invisible to users and developers. Although the loader's initialization tasks are hidden, a program typically does interact with its interfaces during the run time of a program—for example, whenever loading or unloading a DLL or querying the base address of one. One of the main tasks the loader is responsible for:

- Initializing the user-mode state for the application, such as creating the initial heap and setting up the thread-local storage (TLS) and fiber-local storage (FLS) slots.
- Parsing the import table (IAT) of the application to load for all DLLs it requires (and then recursively parsing the IAT of each DLL), followed by parsing the export table of the DLLs to make sure the function is actually present. (Special forwarder entries can redirect an export to another DLL.)
- Loading and unloading DLLs at run time, as well as on demand, and maintaining a list of all loaded modules (the module database).
- Handling manifest files, needed for Windows Side-by-Side (SxS) support, as well as Multiple Language User Interface (MUI) files and resources.
- Reading the application compatibility database for any shims, and loading the shim engine DLL if required.
- Enabling support for API Sets and API redirection, a core part of the One Core functionality that allows creating Universal Windows Platform (UWP) applications.
- Enabling dynamic runtime mitigations through the Switch as well as interfacing with the shim and Verifier mechanisms.

As you can see, most of these tasks are critical to enabling an application to actually run. Without them, everything from calling external functions to using the heap would immediately fail. After the process has been created, the loader calls the NtContinue API to continue execution on an exception frame as an exception handler would. This exception frame, built by the kernel as we saw in an earlier section, contains the entry point of the application. Therefore, because the loader doesn't use a standard call or jump into the running application, you will never see the loader initialization functions as part of the call tree for a thread.
