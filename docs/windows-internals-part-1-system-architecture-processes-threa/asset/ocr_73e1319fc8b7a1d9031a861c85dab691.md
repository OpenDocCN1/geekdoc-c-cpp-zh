Unfortunately, even with safe mode and the default path search algorithms for legacy applications, which always might be copied from its usual location to a user-accessible location (for example, from c:\windows\system32\notepad.exe to c:\temp\notepad.exe, an operation that does not require administrative rights), an attacker can place a specially crafted DLL in the same directory as the application, and due to the ordering, it will take precedence over the system DLL. This can then be used for persistence or otherwise elevating the application, which privileged (especially if the user, unaware of the change, is elevating it under UAC). To defend against this, processes and/or administrators can use a process-mitigation policy (see Chapter 7 for more information on these) called Prefer System32 Images, which inverts the order above between points 1 and 2, as the name suggests.

# DLL name redirection

Before attempting to resolve a DLL name string to a file, the loader attempts to apply DLL redirection rules are used to extend or override portions of the DLL namespace—which normally corresponds to the Win32 file system namespace—to extend the Windows application model. In order of application, these are:

+   * **MinWin API redirection** The API set mechanism is designed to allow different versions of Windows to change the binary that exports a given API in a manner that is transparent to applications, by introducing the concept of contracts. This mechanism is briefly touched upon in Chapter 2, and will be further explained in a later section.
* **LOCAL redirection** The .LOCAL redirection mechanism allows applications to redirect all copies of a specific DLL name, regardless of whether a full path is, to a local copy of the DLL in the application directory—either by creating a copy of the DLL with the same name followed by .local (for example, MyLibrary.dll.local) or by creating a file folder with the name .local under the application directory and placing a copy of the DLL in the folder (for example, C:\MyApp\MyLibrary.dll). DLLs redirected by .LOCAL mechanism are handled individually to those redirected by SxS. (See the next bullet point.) The loader handles LOCAL redirection of DLLs only when the executable does not have an associated manifest, either embedded or external. It is not enabled by default.

+   * **Fusion (SxS) redirection** Fusion (also referred to as side-by-side, or SxS) is an extension to the Windows application model that allows components to process more detailed dependency information (usually including version information) by embedding binary resources as manifests. The Fusion mechanism was first used so that applications could load the correct version of the Windows controls when binary was split into different versions that could be installed alongside one another; other binaries built have since been versioned in the same fashion. As of Visual Studio 2005, applications could use the Microsoft linker use Fusion to locate the C runtime libraries, while Visual Studio 2015 and use API Set redirection to implement the idea of the universal CRT.
