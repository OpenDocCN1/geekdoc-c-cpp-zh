+   The PnP manager works closely with the I/O manager and a type of device driver a bus driver to guide the allocation of hardware resources as well as detect and respond to the arrival and removal of hardware devices. The PnP manager and bus drivers are responsible for loading a driver when the device is detected. When a device is added to a system that doesn't have an appropriate device driver, the executive Plug and Play component calls on the device-installations of the user-mode PnP manager.

+   The power manager also works closely with the I/O manager and the PnP manager to guide the system, as well as individual device drivers, through power-state transitions.

+   WMI support routines, called the Windows Driver Model (WDM) WMI provider, allow drivers to act as providers, using the WDM WMI provider as an intermediary to communicate with the WMI service in user mode.

+   The registry serves as a database that stores a description of basic hardware devices attached to the system as well as driver initialization and configuration settings. (See the section "Registry" in Chapter 9 Part 2 for more information.)

+   INF files, which are designated by the .inf extension, are driver-installation files. INF files are the link between a particular hardware device and the driver that assumes primary control of that device. They are made of script-like instructions describing the device they correspond to, the source and target locations of driver-installation modifications, and driver-dependency information. Digital signatures that Windows uses to verify that a driver has passed testing by the Microsoft Windows Quality Labs (WHQL) are stored in .cat files. Digital signatures are also used to prevent tampering of the driver or its INF file.

+   The hardware abstraction layer (HAL) isolates drivers from the specifics of the processor and interrupt controller by providing APIs that hide differences between platforms. In essence, the HAL is the bus driver for all the devices soldered onto the computer's motherboard that aren't controlled by other drivers.

# The I/O manager

The I/O manager is the core of the I/O system. It defines the orderly framework, or model, within which I/O requests are delivered to device drivers. The I/O system is packet driven. Most I/O requests are represented by an I/O request packet (IRP), which is a data structure that contains information completely describing an I/O request. The IRP travels from one I/O system component to another (As you'll discover in the section "Fast I/O", fast I/O is the exception; it doesn't use IRPs). The design allows an individual application thread to manage multiple I/O requests concurrently. (For more information on IRPs, see the "I/O request packets" later in this chapter.)

The I/O manager creates an IRP in memory to represent an I/O operation, passing a pointer to the correct driver and disposing of the packet when the I/O operation is complete. In contrast, a driver receives an IRP, performs the operation or IRP specified, and passes the IRP back to the I/O manager, either because the requested I/O operation has been completed or because it must be passed to another driver for further processing.
