This system is not running the checked build, because Debug property shown says False.

Much of the additional code in the checked-built binaries is a result of the ASSERT and/or NT_ASSERT macros, which are defined in the WDK header file Wdm.h and documented in the WDK documentation. These macros test a condition, such as the validity of a data structure or parameter. If the expression evaluates to FALSE, macros either call the kernel-mode function RtAssert, call DbgPrint to send the text of the debug message to a message buffer, or issue an assertion interrupt, which interrupt 0xB on x64 and x86 systems. If a kernel debugger is attached and the appropriate samples are loaded, this message is displayed automatically by a prompt asking the user to doubt the assertion failure (breakpoint, ignore, terminate process, or terminate). If the system wasn't booted with the kernel debugger (using the debug option in the Boot Configuration Database) and no kernel debugger is currently attached, failure of an assertion test will bug-crash (crash) the system. For a small list of assertion checks made by some of the kernel support routines, see the section "Checked Built ASSERTs" in the WDK documentation (although this list is unmaintained and outdated).

The checked build is also useful for system administrators for the additional detailed information tracing that can be enabled for components. (For detailed instructions, see the Microsoft Knowledge Base Article number 31473, titled "HOWTO: Enable Verbose Debugging in Drivers and Subsystems") This output is sent to an internal debug message buffer using the DbgPrintEx function referred to. To view the debug messages, you can either attach a kernel debugger to the target system (which requires booting the target system in debug mode) using the !dbg while performing local kernel debugging, or use the DebugView.exe tool from Sysinternals. Most recent versions of Windows have moved away from this type of debug, however, and use a combination of Windows preprocessor (WPP) tracing or TraceLogging technology, both of which are built on top of Event Tracing for Windows (ETW). The advantage of these new logging mechanisms is that they are not so limited to the checked versions of components (especially useful now that a full checked build is longer available) and can be seen by using tools such as Windows Performance Analyzer (WPA), formerly known as XPerf or Windows Performance Toolkit, TraceView (from the WDK), or the !wmi print extension in the kernel debugger.

Finally, the checked build is also useful for testing user-mode code only because the system is different. (This is because of the additional checking taking place within the kernel and the fact that the components are compiled without optimizations). Often, multithread synchronization bugs are reduced to specific timing conditions. By running your tests on a system running the checked build (or at least the kernel and HAL), the fact that the timing of the whole system is different might cause latent bugs to surface that do not occur on a normal retail system.
