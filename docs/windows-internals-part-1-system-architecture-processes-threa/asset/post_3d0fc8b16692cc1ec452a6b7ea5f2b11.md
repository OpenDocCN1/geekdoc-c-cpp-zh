## Silo isolation boundaries

The aforementioned components provide the user-mode isolation environment. However, as the host Ntdll.dll component which talks to the host kernel and drivers, it is important to create isolation boundaries, which the kernel provides to differentiate one silo from another. As such, each server silo will contain its isolated:

- **Micro shared user data (STLO_USER_SHARED_DATA in the symbols)** This contains the system path, isolation ID, foreground PID, and type/size. These are elements of the original KUSER_SHARED_DATA that cannot come from the host, as they reference information relevant to the host OS image instead of the base OS image, which must be used. Various components and APIs were modified to read the silo shared data instead of the user shared data when they look up such data. Note that the original KUSER_SHARED_DATA remains in its usual address with its original view of the host details, this is one way that host "leaks" inside container state.
- **Object directory root namespace** This has its own SystemRoot link, \Device directory (which is how all user-mode components access device drivers indirectly), map device mappings (which is how user-mode applications access network mapped drivers, example), \\Sessions directory, and more.
- **API Setting mapping** This is based on the API Set schema of the base OS WIM, and not the one stored on the host OS file system. As you've seen, the loader uses API Settings to determine which DLL, if any, implements a certain function. This can be different from one SKU to another, and applications must use the base OS SKU, not the host's.

- **Logon session** This is associated with the SYSTEM and Anonymous local ID (LUID), plus the LUID of a virtual service account describing the user in the silo. This essentially represents the token of the services and application that will be running inside the container session created by Smss. For more information on LUIDs and logon sessions, see Chapter 7.

- **ETW tracking and logging contexts** These are for isolating ETW operations to the silo and not exposing or leaking states between the containers and/or the host OS itself. (See Chapter 9 in Part 2 for more on ETW.)

## Silo contexts

While these are the isolation boundaries provided by the core OS kernel itself, other components inside the kernel, as well as drivers (third party), can create data silos by using the PsCreateSilo API to set custom data with a silo or by associating an existing object with it. Each silo context will utilize a silo slot that will be inserted in all running, and future, silos, storing a pointer to the context. The system provides 32 built-in system-wide storage slots, plus 256 extra slots, providing lots of extensibility options.

As each silo is created, it receives its own silo-local (SLS) array, like a thread that has thread-local storage (TLS). Within this array, the different entries correspond to slot indices that have been allocated to silo contexts. Each silo will have a different pointer at the slot index, but will always store the same context at that index. (For example, driver "Foo" will own index 5 in all silos, and can use it to store a different pointer/context in each silo.) In some cases, built-in kernel components, as the object manager, security reference monitor (SRM), and Configuration Manager use some of these slots, while others are used by index drivers (as the Ancillary Function Driver for Windows, Afd.sys.)

Just like dealing with the server shared user data, various components and APIs have been updated to access data by getting from the relevant silo context instead of using a global variable. As an example, each container will now host its own Lsass.exe process, while the kernel's SRM needs to own to handle Lsass.exe process (see Chapter 7 for more information on Lsass and the SRM), this can no longer be a singleton store in a global variable. As such, the handle is now accessed by the SRM querying the silo context of the active server silo, and getting the variable from the data structure that returned.

This leads to an interesting question: What happens with the Lsass.exe that is running on the host OS itself? How will the SRM access the handle, as there's no server silo for this set of processes and session (that is, session itself)? The kernel now implements a root host silo. In other words, the host itself is preserved to be part of a silo! This isn't in the true sense of the word, but a clever trick to querying silo contexts for the current silo work, even when there is no current silo. This is implemented by storing a global variable named PsHostSilo-Global, which has its own Slot Local Storage Array, as well as other silo contexts built-in by kernel components. When various silo APIs are called with a NULL pointer, "NULL" is treated instead as "no silo—i.e., use the host silo."

## EXPERIMENT: Silo monitors and contexts

To understand how silo monitors are used, let's take a look at the monitor. First, let's dump the data structure that represents the monitor. Unfortunately, it is not in the symbol, so we must do this as raw data.

```
lkd> dps poi(afdAMonitor)
ffff387*a97c1f0 fffff387*a7d70c0
ffff387*a97c2f8 fffff387*a7b54b0
ffff387*a97c1390 00000010
ffff387*a97c13c8 fffff387*be4b510
ffff387*a97c1440 fffff387*be4e40
```

Now get the slot (9 in example) from the host silo. Silos store their SLS in a field called Storage, which contains an array of structures (slot entries), each storing a pointer, and some flags. We are multiplying the index by 2 to get the offset of the slot entry, then accessing the next field (+1) to get the pointer to the context:

```
lkd> r?@$0 = (nt!ERSILO_GLOBALS*)@masm(nt!PspHostiloGlobals)
lkd> ?? (void**@$0->Storage) [9 = 2 + 1]
void == 0xffff88fab185941
```

Note that the permission flag (0x2) is ORed into the pointer, mask it out, and then use the !object extension confirm that this is a silo context.

```
lkd> !object(0xffff88fab185941 & -2)
Object: fffff88fab185940 Type: (ffff888faac9f20) PsSiloContextNonPaged
```

## Creation of a server silo

When a server silo is created, a job is first used, as mentioned, in silos are a feature of job objects. This is done through the standard CreateJobObject API, which was modified as part of the Anniversary Update to have an associated job ID, or JID. The JID comes from the pool of numbers as the process and thread ID (PID and TID), which is the client ID (CID) table. As such, a JID is unique among not only other jobs, but also processes and threads. Additionally, a container GUID is automatically created.
