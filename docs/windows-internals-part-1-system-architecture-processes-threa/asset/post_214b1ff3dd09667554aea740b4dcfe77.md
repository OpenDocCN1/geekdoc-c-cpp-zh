
The main point to remember when thinking about robustness—and SuperFetch optimizations in general—is that SuperFetch constantly monitors patterns and updates its understanding of the system to avoid fetching useless data. Although changes in a user's daily activities or application startup might cause SuperFetch to pollute the cache with irrelevant data or throw out that it might think is useless, it quickly adapts to any pattern changes. If the user's actions are erratic and random, the worst that can happen is that the system will behave in a similar state as if SuperFetch were not present at all. If SuperFetch is ever in doubt or cannot track reliably, it quiets itself and doesn't make to a given process or page.

## ReadyBoost

These days, RAM is easily available and relatively cheap compared to a decade ago. Still, it doesn't beat the cost of secondary storage such as hard drives. Unfortunately, mechanical hard disks contain many moving parts, they are fragile, and more importantly, are relatively slow compared to RAM, especially during seeking. As a result, storing active SuperFetch data on the drive would be as bad as paging out a page and hard-fault inside memory.

Solid state and hybrid drives offset some of these disadvantages but they are pricier and slower than RAM. Portable solid media such as USB flash disk (UFD), CompactFlash, and Secure Digital cards, however, provide a useful compromise. They are cheaper than RAM and available in larger sizes, but also have shorter times than mechanical hard drives because of the lack of moving parts.

> Note: In practice, CompactFlash and Secure Digital cards are almost always faced through a USB adapter, so they all appear to the system as USB flash disks.

Random disk I/O is especially expensive because disk seek time puts rotational latency typical desktop hard drives total about 10 milliseconds—an eternity for today's 3 or 4 GHz processors. Flash memory, however, can service read up to 10 times faster than a typical hard drive. Windows includes a feature ReadyBoost to take advantage of flash storage devices by creating an intermediate caching layer on them that logically sits between memory and disks.

ReadyBoost (not to be confused with ReadyBoost) is implemented with a driver of (%System-Root%\System32\Drivers\Readyboost.sys) that is responsible for writing the cached data to the non-volatile RAM (NVRAM). When you insert a USB flash disk into a system, ReadyBoost looks at the device to determine its performance characteristics and the results of its insert in HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Endmgmt (End is for external memory, the working name for ReadyBoost during its development).

If the new device is between 256 MB and 32 GB in size, it has a transfer rate of 2.5 MB per second or higher for random 4 KB reads, and has a transfer rate of 1.75 MB per second or higher for random 512 KB writes, ReadyBoost will ask you if you'd like to dedicate some of the space for caching. If you agree, ReadyBoost creates a file named ReadyBoost.scache in the root of the device, which it uses to store cached pages.

After initializing cache, ReadyBoost intercepts all reads and writes to local hard disk volumes (C:\ for example) and copies any data being read or writing into the cache file that we created. There are exceptions—for example, data that hasn't been read in a long while or data that belongs to a 2:1 Volume Snapshot. Data stored on the cached drive is compressed and typically a 4 GB cache file will contain 8 GB of data. Each block is encrypted as it is written using Advanced Encryption Standard (AES) encryption with a randomly generated per-boot key to guarantee the privacy of the data in the cache if the device is removed from the system.

When ReadyBoost sees reads that can be satisfied from the cache, it services them from there. However, because hard disks have better sequential read access than flash memory, it lets reads that are part of sequential patterns go directly to the disk if the data is in the cache. Likewise, when reading the cache, if I/Os must be done, the on-disk cache will be read instead.

One disadvantage of depending on flash memory is that the user can remove it at any time, which means the system can never solve critical data on the media. (As you've seen, always goes to the secondary storage first.) A related technology, ReadyDrive, covered in the next section, offers additional benefits and solves this problem.

## ReadyDrive

ReadyDrive is a Windows feature that takes advantage of hybrid hard disks (H-HDDs). An H-HDD is a disk embedded with NVRAM. Typical H-HDDs have between 50 MB and 512 MB of cache.

Under ReadyDrive, the drive's flash memory does not act as an automatic, transparent cache, as does the RAM cache common on most hard drives. Windows uses ATA-8 commands to define the disk data to be held in the flash memory. For example, Windows saves boot data to the cache when the system shuts down, allowing for faster restarting. It stores portions of hibernation file data in the cache when the system hibernates so the subsequent resume is faster. Because the cache is enabled even when the disk is spun down, Windows can use the flash memory as a disk-write cache, which avoids spinning up the disk when the system is running on battery. Keeping the disk spindle turned off can save much of the power consumed by the disk drive under normal usage.

Another consumer of ReadyDrive is SuperFetch. It offers the same advantages as ReadyBoost with enhanced functionality; such as not requiring an external flash device and having the ability to work persistently. Because the cache is on the actual hard drive, a user typically cannot remove while the computer is running, the hard drive controller doesn't have to worry about the data disappearing and can avoid making writes to the actual disk using the cache.

## Process reflection

There are cases where a process exhibits problematic behavior, but because it's still providing service, suspending it to generate a full memory dump or interactively is undesirable. The length of time a process is suspended to generate a dump can be minimized by taking a minidump, which captures registers and stacks along with pages of memory referenced by registers, but that dump type has a very limited amount of information, which many times is sufficient for diagnosing crashes but not for troubleshooting general problems. With process reflection, the target process is suspended long enough to generate a suspended cloned copy of the target, and the larger dump that captures all of a process's valid user-mode memory can be generated from the clone while the target is allowed to continue execution.

Several Windows Diagnostic Infrastructure (WDI) components use of process reflection to capture memory dumps of processes when their heuristics identify suspicious behavior. For example, the Memory Leak Diagnoser of Windows Resource Exhaustion Detection and Reporting (also known as RADAR), generates a reflected dump of a process that appears to be leaking virtual memory so it can be sent to Microsoft via Windows Error Reporting (WER). WDI's hung process heuristic does the same for processes that appear to be deadlocked on another. Because these components use heuristics, they can't be certain the processes are faulty and therefore can't suspend them for long periods of time.

The RtCreateProcessReflection function in Ntdll.dll drives the implementation of process reflection. It works as follows:

- 1. It creates a shared memory section.
- 2. It populates the shared memory section with parameters.
- 3. It maps the shared memory section into the current and target processes.
- 4. It creates two event objects and duplicates them into the target process so that the current process and target process can synchronize their operations.
- 5. It injects a thread into the target process via a call to RtCreateProcessUserThreadEx. The thread is directed to begin execution in Ntdll.dll's RtProcessReflectionStartup function. (Because Ntdll.dll is mapped at the same address (randomly generated at boot) into every process's address space, the current process can simply pass the address of the function it obtains from its own Ntdll.dll mapping.)
- 6. If the caller of RtCreateProcessReflection specified that it wants a handle to the cloned process, RtCreateProcessReflection waits for the remote thread to terminate, otherwise it returns to the caller.
- 7. The injected thread in the target process allocates an additional event object that it will use to synchronize with the cloned process after it's created.
- 8. The injected thread calls Clone, passing parameters it obtains from the memory mapping it shares with the initiating process.
