
Here is a quick rundown of the members:

- **IoStatus** is the status of the IRP, consisting of two members; Status, which is the actual code itself and Information, a polymorphic value that has meaning in some cases. For example, a read or write operation, this value (by the driver) indicates the number of bytes read or written. This same value is the one reported as an output value from the functions ReadFile and WriteFile.

- **MdlAddress** is this optional pointer to a memory descriptor list (MDL). An MDL is a structure that represents information for a buffer in physical memory. We'll discuss its main usage in device drivers in the next section. If an MDL was not requested, the value is NULL.

- **I/O stack locations count and current stack** These store the total number of I/O stack objects and point to the current one that this driver layer should look at, respectively. The next section discusses I/O stack locations in detail.

- **User buffer** is this pointer to the buffer provided by the client that initiated the I/O operation. For example, it is the buffer provided to the ReadFile or WriteFile functions.

- **User event** is this kernel event object with an overlapped (asynchronous) I/O operation (if any). An event is one way to be notified when the I/O operation completes.

- **Cancel route** is this function to be called by the I/O manager in case the IRP is cancelled.

- **AssociatedIrp** is this union of three fields. The SystemBuffer member is used in the I/O manager used buffered I/O technique for passing the user's buffer to the driver. The next section discusses buffered I/O, as well as other options for passing user mode buffers to drivers. The MasterIrp member provides a way to create a "master IRP" that splits into sub-IRPs, where the master is considered complete when all its sub-IRPs are completed.

## I/O stack locations

An IRP is fulfilled by one or more I/O stack locations. The number of stack locations is equal to the number of layered devices the IRP is destined for. The I/O operation information is split between the IRP body (main structure) and the current I/O stack location, where *current* is the one set up for the particular layer of devices. Figure 6-12 shows the important fields of an I/O stack location. When an IRP is created, the number of requested I/O stack locations is passed to IoAllocateIrp. The I/O manager then initializes the IRP body and the first I/O stack location, destined for the most-device in the device node. Each layer in the device node is responsible for initializing the next I/O stack location if it decides to pass the IRP down to the next device.

Here is a rundown of the members in Figure 6-12:

- **Major function** is this code that indicates the type of request (read, write, create, Plug and Play, and so on), also known as dispatch route code. It is one of 28 constants (0 to 27) starting with IRP_MJ_, in wdm.h. This index is used by the I/O manager into the MajorFunction array of function pointers in the device object to jump to the routine within the driver.

Most drivers dispatch routines to handle only subset of possible major function codes, including create (open), read, write, I/O control, power, Plug and Play, system control (for WMI commands), cleanup, and close. File-system drivers are an example of a driver type that often fills in most or all of its dispatch points with functions. In contrast, a simple USB driver would probably fill in the routines needed for open, close, read, write, and sending I/O controls. The I/O manager sets any dispatch points that a driver needs to fill to its Iop1DeviceRequest, which completes the IRP with an error status indicating that the major function in the IRP is invalid for that device.

- **Minor function** This is used to augment the major function code for some functions. For example, IRP_MJ_READ (read) and IRP_MJ_WRITE (write) have no minor functions. But Plug and Power IRPs have a minor IRP write code that specializes the general major code. For example, the Plug and IRP_MJ_PnP code is too generic; the exact instruction is given by the minor function, such as IRP_MN_START_DEVICE, IRP_MN_REMOVE_DEVICE, and so on.

- **Parameters** This is a monstrous of structures, each of which validates for a particular major function code or a combination of major/minor codes. For example, a read operation (IRP_MJ_READ), the Parameters Read structure holds information on the request, such as the buffer size.

- **File object Device Object** These point to the associated FILE_OBJECT and DEVICE_OBJECT for this I/O request.

- **Completion routine** This is an optional function that a driver can register with the IoSetCompletionRoutine(Ex) Ddl, to be called when the IRP is completed by a lower layer driver. At that point, the driver can look at the completion status of the IRP and do any needed post-processing. It can even undo the completion (returning the special value STATUS_MORE_PROCESSING_REQUIRED from the function) and resend the IRP (perhaps with modified parameters) to the device node—even a different device node—again.

- **Context** This is an arbitrary value set with the IoSetCompletionRoutine(Ex) call that is passed, as is, to the completion routine.

The split of information between the IRP body and the I/O stack location allows for the changing of I/O stack location parameters for the next device in the device stack, while keeping the original request parameters. For example, a read IRP targeted at a USB device is often changed by the function driver to a device I/O control request where the buffer argument of the device control points to a USB request packet (URB) that is understood by the lower-layer USB bus driver. Also, note that completion routines can be registered by any layer (except the bottom-most), each having its own I/O stack location (completion routine is stored in the next lower I/O stack location).
