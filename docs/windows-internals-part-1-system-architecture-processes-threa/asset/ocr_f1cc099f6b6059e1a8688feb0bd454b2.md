ObpGrantAccess passes to ObGetObject the security credentials of the thread opening the object, the types of access to the object that the thread is requesting (read, write, delete, and so forth, object-specific operations), and a pointer to the object. ObGetObject locks the object security descriptor and the security context of the thread. The security lock prevents another from changing the security context while the check is in progress. The lock on the thread's security context prevents another thread (from that process or a different process) from altering the security identity of the thread while validation is in progress. ObGetObjectAccess then calls the security method to obtain the security settings of the object. (See Chapter 8 in Part 2 for a description of object methods.) The call to the security method might invoke a function in a different executive component. However, many executive objects rely on the system's default security management support.

When an executive component defining an object doesn't want to override the SRM's security policy, it marks the object as having default security. Whenever the SRM calls an object's security method, it first checks whether the object has a default security. With default security stores its security information in its header, and its security method is SeDefaultToObject. An object that does not rely on default security must have its own security information and supply a specific security method. Objects that rely on default security include mutex, events, and semaphores. A file object is an example of an object that overrides default security. The I/O manager, which defines the file type, the file system driver which chooses (or not to implement) the security for its files. Thus, when the system queries the security on a file object that represents a file on an NTFS volume, the I/O manager file object security method retrieves the security using the NTFS file system driver. Note, however, ObGetObject isn't invoked when files are opened because they reside in separate namespaces. The system invokes an object's security method only when a thread explicitly queries or seeks security on a file (with the Windows SetFileSecurity or GetFileSecurity functions, for example).

After obtaining security information, ObGetObject invokes the SRM function SeAccessCheck. SeAccessCheck is one of the functions at the heart of the Windows security model. Along the input parameters SeAccessCheck checks the object's security information, the security identity of the thread as captured by ObGetObject, and the access that the thread is requesting. SeAccessCheck returns true or false, depending on whether the thread is granted the access to the object.
