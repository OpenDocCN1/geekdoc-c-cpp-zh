
Windows requests the remote user's user identity. On domain-joined systems, Windows honors all the user's group memberships by requesting the user's administrative identity. Executing an image that requests administrative rights causes the application information service (AIS, contained in %SystemRoot%\System32\Appinfo.dll), which runs inside a standard service host process (Svchost.exe), to launch %SystemRoot%\System32\Consent.exe. ## Requesting administrative rights

There are a number of ways the system and applications identify a need for administrative rights. One that shows up in the Explorer interface is the Run as Administrator context menu command and shortcut option. These items also include a blue and gold shield icon which should be placed next to any button or menu item that will result in an elevation of rights when it is selected. Choosing the Run as Administrator command causes Explorer to call the ShellExecute API with the run verbs.

The vast majority of installation programs require administrative rights, so the image loader, which initiates the launch of an executable, includes installer-detection code to identify legacy installers. Some of the heuristics it uses are as simple as detecting internal version information or whether the name has words "install" or "update" in its name. More sophisticated methods of detection involve scanning for byte sequences that are common to third-party installation wrappers. The image loader also calls the application-compatibility library to see if the target executable requires administrator rights. The library looks in the application-compatibility database to see whether the executable has the ReqAdministrator or RunAsInvoker flag associated with it.

The most common way for an executable to request administrative rights is for it to include a requestedExecutionLevel tag in its manifest. This attribute can have one of the three values shown in Table 7-17.

| Elevation Level | Meaning | Usage |
| :--- | :--- | :--- |
| invoker | No need for elevation; never ask for elevation. | Typical applications |
| highestAvailable | Request approval; if the user is a standard user, a UAC prompt will appear. | Applications that need administrative rights |
| requireAdministrator | Always request administrative rights; if the user is logged in as a standard user, a UAC prompt will be shown. | Applications that require administrative rights |

The presence of trustInfo element within a manifest (which you can see in the dump of eventwr.exe) denotes an executable that was written with UAC and the uiAccess attribute is where accessibility applications use this.

```
sigcheck -m C:\Windows\eventwr.exe
<trustInfo xmlns="urn:schemas-com:asmv3">
  <security>
    <requestedPrivileges>
      <requestedExecutionLevel
        level="highestAvailable"
        uiAccess="false"/>
    </requestedPrivileges>
  </security>
</trustInfo>
<asmv3:application>
  <asmv3:windowsSettings xmlns="http://schemas.microsoft.com/SMI/2005/WindowsSettings">
    <asmv3:autoElevate>true</autoElevate>
  </asmv3:windowsSettings>
</asmv3:application>
```

## Auto-elevation

In the default configuration, the next section for executables and control panels do not result in elevation prompts, even if they need administrative rights. This is because of a mechanism called auto-elevation. Auto-elevation is intended to preclude administrative users from seeing elevation prompts for most of their work; it has several requirements. One is that the executable in question must be considered a Windows executable. This means it must be signed by the Windows publisher (not by Microsoft—Windows-signed is considered more privileged than Microsoft-signed). It must also be in one of several directories considered secure: %SystemRoot%\System32 and most of its subdirectories, %SystemRoot%\Home, and a small number of directories under %ProgramFiles% (for example, containing Windows Defender and Windows Journals).

There are additional requirements, depending on the type of executable. EXE files other than Mmc.exe auto-elevate if they are requested via an auto-elevate element in their manifest. The manifest shown earlier of eventnr.exe in the previous section illustrates this.

Finally, COM (out-of-process server) can request administrative rights within their registry key. To do so requires a subnet named Elevation with a DWORD value named Enabled. Both the COM class and its instantiating executable must meet the Windows executable requirements, although the executable not have requested auto-elevation.
