The size of the virtual address space varies for each hardware platform. On 32-bit x86 systems, the total virtual address space has a theoretical maximum of 4 GB. By default, Windows allows the lower half of this address space (addresses 0x00000000 through 0x7FFFFFFF) to processes for their private storage and the upper half (addresses 0x80000000 through 0xFFFFFFFF) for its own OS memory utilization. The mappings of the lower half reflect the virtual address space of the currently executing process, but (most of) the upper half always consist of the OS's virtual memory. Windows uses boot-time options, such as the increaseusers qualifier in the Boot Configuration Database (described in Chapter 5), that gives processes running specially marked programs the ability to use up to 3 GB of private address space, leaving 1 GB for the OS. (By "specially marked," we mean the large address space–aware flag must be set in the header of the executable image.) This option allows applications such as database servers to keep larger portions of the database in the process address space, thus reducing the need to map views of the database on disk and therefore increasing overall performance (in certain cases, the level of 1 GB for the system can cause more pronounced system-wide performance losses). 3 GB is better than 2 GB, but it's still not enough virtual address space to map very large (multigigabyte) databases. To address this need on 32-bit systems, Windows provides a mechanism called *Address Windowing Extensions* (AWE), which allows a 32-bit application to allocate up to 64 GB of physical memory and then map views of, into its 2 GB virtual address space. Although using AWE puts the burden of managing of virtual to physical memory on the developer, it does address the need to directly access more memory than can be mapped at any time in a 32-bit process address space.

64-bit Windows provides a much larger address space for processes: 128 TB on Windows 8.1, Server 2012 R2, and later systems.
