# Structure of a driver

The I/O system drives the execution of device drivers. Device drivers consist of a set of routines that are called to process the various stages of an I/O request. Figure 6-9 illustrates the key driver-function routines, which are described next.

![](img/ff0e6a9d867a3a6e9527eb1d946810fc_514_0.png)

FIGURE 6-9 Primary device driver routines.

- An initialization routine WDK The I/O manager executes a driver initialization routine, which is set by WDK DriverEntry when it loads the driver into the operating system. DriverEntry initializes the compiler's protection against stack-overflow errors (called a cookie) and then calls DriverEntry, which is what the driver writer must implement. The routine fills data structures to register the driver's routines with the I/O manager and performs any necessary global initialization.

- An add-device routine A driver that supports Plug and Play implements an add-device routine. The PnP manager sends a notification to the driver whenever a device for which the driver is responsible is detected. In this routine, a driver typically creates a device object (described later in this chapter) to represent the device.

- A set of dispatch routines Dispatch routines are the main entry points that a device driver provides. Some are open, close, read, write, and Plug and Play. When called to perform an operation, the I/O manager generates an IRP and a driver through one of the driver's dispatch routines.

- A start I/O routine A driver can use a start I/O routine to initiate a data transfer to or from a device. This routine is defined only in drivers that rely on the I/O manager to queue their incoming requests. The I/O manager serializes IRPs by ensuring that the driver processes only one IRP at a time. Drivers can process multiple IRPs concurrently, but serialization is required for most devices because they cannot concurrently handle multiple I/O requests.

- An interrupt service routine ISR When a device interrupts, the kernel's interrupt controller transfers control to the ISR (DIRQL). In the Windows I/O model, ISRs run at device interrupt level so they perform as little work as possible to avoid blocking lower IRQL interrupts (as discussed in the previous section). An ISR usually queues a DPC, which runs at a lower IRQL (DPC/dispatch level) to execute the remainder of interrupt processing. Only drivers for interrupt-driven devices have ISRs; a file-system driver, for example, does not.

- An interrupt-servicing DPC A DPC performs most of the work in handling a device interrupt that executes the ISR. The DPC executes at IRQL 2, which is a "compromise" between the high DIRQL and the low level (0). A typical DPC routine completes initialization and starts the next I/O operation on a device.

Although the following routines are not shown in Figure 6-9, they're found in many types of device drivers:

- One or more I/O completion routines A layered driver might have I/O completion routines that notify it when a lower-level driver finishes processing an IRP. For example, the I/O manager calls a file-system driver's I/O completion routine after device driver finishes transferring data to or from a file. The completion routine notifies the file-system driver about the operation's success, failure, or cancellation, and allows the file-system driver to perform cleanup operations.

- A cancel I/O routine If an I/O operation can be canceled, a driver can cancel one or more cancel I/O routines. When the driver receives an IRP for an I/O request that can be canceled, it assigns a cancel route to the IRP. The IRP goes through various stages of processing, the routine can change or disappear if the current operation is not cancelled. If a thread that issues an I/O request before the operation is completed or the operation is canceled (for example, the CancelIo or CancelIoEx functions), the I/O manager executes the IRP's cancel routine if it is assigned to it. A cancel routine is necessary to release any resources acquired during the processing that has already taken place for the IRP as well as for completing the IRP with a canceled status.

- **Fast-dispatch routines** Drivers that use the cache manager, such as file-system drivers, typically provide these routines to the kernel to bypass typical I/O processing when accessing the driver. (See Chapter 14, "Cache manager," in Part 2, for more information on the cache manager). Operations, such as reading or writing can be quickly performed by accessing the cache data directly instead of taking the I/O manager's usual path that generates discrete I/O operations. Fast dispatch routines are also used as a mechanism for callbacks from the memory manager and cache manager to file-system drivers. For instance, when creating a section, the memory manager calls back into the file-system driver to acquire the file exclusively.

- **An unload routine** An unload routine releases any system resources in use so that the I/O manager can remove the driver from memory. Any resources acquired in the initialization routine (DriverEntry) are usually released in the unload routine. A driver can be loaded and unloaded while the system is running if the driver supports it, but the unload routine will be called only after all files to the device are closed.

- **A system shutdown notification routine** This routine allows driver cleanup on system shutdown.

- **Error-logging routines** When unexpected errors occur (for example, when a disk block goes bad), a driver's error-logging routines note the occurrence and notify the I/O manager. The I/O manager writes this information to an error log file.

# Driver objects and device objects

When a thread opens a handle to a file object (described in the "I/O processing" section later in this chapter), the I/O manager must determine the file name which driver it should call to process the request. Furthermore, the I/O manager must be able to locate the information the next time ahead uses the same file handler. The following system objects fill this need:

- **A driver object** This represents an individual driver in the system (DRIVER_OBJECT structure). The I/O manager obtains the address of each of the driver's dispatch routines (entry points) from the driver object.

- **A device object** This represents a physical or logical device on the system and describes its characteristics (DEVICE_OBJECT structure), such as the alignment requirements for buffers and the location of its device queue to hold incoming IRPs. It is the target for all I/O operations because this object is what the hardware communicates with.
