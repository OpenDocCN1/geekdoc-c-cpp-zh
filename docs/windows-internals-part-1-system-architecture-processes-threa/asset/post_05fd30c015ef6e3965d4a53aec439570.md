
# Other subsystems

As mentioned, Windows originally supported POSIX and OS/2 subsystems. Because these subsystems are no longer provided with Windows, they are not covered in this book. The general concept of subsystems remains, however, making the system extensible to new subsystems if such a need arises in the future.

# Pico providers and the Windows subsystem for Linux

The traditional subsystem model, while extensible and clearly powerful enough to have supported POSIX and OS/2 for a decade, has important technical disadvantages that made it hard to reach broad usage of non-Windows binaries beyond a few specialized cases:

- As mentioned, because subsystem information is extracted from the Portable Executable (PE) header, it requires the source code of the original binary to rebuild it as a Windows executable file (.exe). This will also change any POSIX-style dependencies and system calls into Windows-imports of the Psxdll.dll library.

- It is limited by the functionality provided either by the Win32 subsystem (which sometimes piggybacks) or the NT kernel. Therefore, the subsystem wraps, emulates or of emulates, the behavior required by the POSIX application. This can sometimes lead to subtle compatibility flaws.

Finally, it's also important to point out that as the name says, the POSIX subsystem/SUA was designed with POSIX/UNIX applications in mind, which dominated the market decades ago, not true Linux applications, which are common today.

Solving these issues required a different approach to building a subsystem—one that did not require the traditional user-mode wrapping of the other environments' system call and the execution of traditional PE images. Luckily, the Bridgewater project from Microsoft Research provided the vehicle for an updated view on subsystems. It resulted in the implementation of the Pico model.

Under this model, the idea of a Pico provider is defined, which is a custom kernel-driver that receive access to specialized kernel interfaces through the PsRegisterPicoProviderAPI. The benefits of these specialized interfaces are two-fold:

- They allow the provider to create processes and threads while customizing their execution contexts, segments, and store data in their respective EPROCESS and THREAD structures (see Chapter 3 and Chapter 4 for more on these structures).

- They allow the provider to receive a rich set of notifications whenever such processes or threads engage in system actions such as system calls, exceptions, APCs, page faults, termination, context changes, suspension/resume, etc.

With Windows 1607, one Pico provider is present: Lxss.sys and its partner Lxcore.sys. As the name suggests, this refers to the Windows Subsystem for Linux (WSL) component, and these drivers make up the Pico provider interface for it.

Because the Pico provider receives almost all transitions transitions from user and kernel mode (be system calls or exceptions, for example), as long as the Pico (or processes) running underneath it has an address space that it can recognize, and has code that can natively execute within it, the "true" kernel below doesn't really matter as long as these transitions are handled in a fully transparent way. As such, Pico processes running under the WSL provider, as you will see in Chapter 3, are different from normal Windows processes—namely, the Ntdll.dll that is loaded into normal processes. Instead, their memory structures such as a vDoS, a special image seen only on Linux/BSD systems.

Furthermore, if the Linux processes are to run independently, they must be able to execute without requiring compilation as PE Windows executables. Because the Windows kernel does not know how to map other image types, such images cannot be launched through the CreateProcess API by a Windows process, nor do they call such APIs themselves (because they have no idea they are running on Windows). Their interoperability support is provided by both the Pico provider and the LXSS Manager, which is a user-mode service. The former implements a COM-based interface that it uses to communicate with the specialized launcher, currently known as Bash.exe, and with a management process, called Lxrun.exe. Providing support for a wide variety of Linux applications is a massive undertaking. Linux has hundreds of system calls—about as many as the Windows kernel itself. Although the Pico provider can leverage features of Windows—many of which were built to support the original POSIX subsystem, such as fork() support—in some cases, it must re-implement functionality on its own. For example, even though NTFS is used to store the actual file system (and not EXTFS), the Pico provider has an entire implementation of the Linux Virtual File System (VFS), including support for inodes, inify(), and /dev, and other Linux-style file-based systems with corresponding behaviors. Similarly, while the Pico provider can leverage Windowsockets for Kernel (WSK) for networking, it has complex wrapping around actual socket behavior, that it can support UNIX domain sockets, Linux Netlink sockets, and standard sockets.

In other cases, if Windows facilities were simply not adequately compatible, sometimes in subtle ways. For example, Windows has a named pipe driver (Npfs.sys) that supports the traditional IPC mechanism. Yet it is subtly different enough from Linux pipes that applications would break. This required a from-scratch implementation of pipes for Linux applications, without using the kernel's Nufs.sys driver.

# Ntdll.dll

Ntdll.dll is a special support library primarily for use of subsystem DLLs and native functions. (*Native in this context refers to images that are not tied to any subsystem.) It contains two types of functions:

- System service stubs to Windows executive services

- Internal functions used by subsystems, subsystem DLLs, and other native functions

The first group of functions provides the interface to the Windows executive services that can be called from user mode. There are more than 450 functions, such as NtCreateFile, NtSetEvent, and so on. As noted, most of the functions are accessible through the Windows API. (A number are not, however, and are for use only by OS-internal processes)

For each of these, Ntdll.dll contains an entry point with the same name. The code contains the architecture-specific instruction that causes a transition into kernel to invoke the system service dispatcher. (This is explained in more detail in Chapter 8 in Part 2.) After verifying some parameters, this system service dispatcher calls the actual kernel-mode system service that contains the real code inside Ntoskrnl.exe. # EXPERIMENT: Viewing the system dispatcher code

Open the version of WinDbg that corresponds to your architecture (for example the x64 version on 64 bit Windows). Then open the File menu and select Open Executable. Navigate to %SystemRoot%\System32 and select Notepad.exe.

Notepad should launch and the debugger should be in the initial breakpoint. This is very early in the life of the process, which you can witness by executing the k (call) command. You should see a few functions starting with Ldr, which indicates the loader state. The main function for Notepad has not executed yet, which you won't see in Notepad's window.

Set a breakpoint in the NtCreateFile inside Ntdll.dll (the debuggers are not sensitive):

```
bp ntdll!NtCreateFile
```

Enter the g (command) or press FS to let Notepad continue execution. The debugger should break almost immediately, showing something like this (x64):

```
Breakpoint 0 hit
tdll!NtCreateFile
0007ffa9f4eb10 4c8bd1	mov r10,rcx
```
