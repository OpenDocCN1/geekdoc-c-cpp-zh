
After this, root directory namespace is created with another information class and call to SetInformationJobObject requires the trusted computing base (TCB) privilege. As silos are normally created only by the Vmcservice, this is to ensure that virtual objects are not used maliciously to confuse applications and potentially break them. When namespaces is created, the object manager creates or opens a new virtual root under the root (\) and appends the JID to create a new virtual root (e.g., \Silo\1). When it creates the Kernel-Objects, ObjectTypes, GLOBAL\ROOT, and DosDevices the root is stored as a silo context with whatever slot index is in PsObjectDirectorySiloToContextSilo, which was allocated by the object manager at boot.

The next step is to convert this silo into a server silo, which is done with another call to Set-InformationJobObject and another information class. The PsConvertSiloToServerSilo function in the kernel runs, which initializes the ESERVSILO_GLOBAL\SILOS we also as part of the experiment dumping the PsSiloToGlobal with the Silo command. This initializes the shared user data, API Set mapping, SystemRoot, and the various silo contexts, as the one used by the SRM to initialize the Lsass process. While process is session, silo monitors that have registered and started their callbacks receive a notification, such that they can add their own silo context data.

The final step, is to “boot up” the server silo by initializing a new server session for it. You can think of this as session 0, but for the server silo. This is done through an ALPC message sent to SmApiPort, which contains a handle to the job object created by Vmcservice, which has become a server silo job object. Just when creating a real user session, Sms will call a copy of itself, which the time will be associated with the job object at creation. This will trigger all Sms to copy all the contained elements of the server silo. Sms will be session 0 and perform its usual duties, such as launching CSRss, Wininit, Lsass, etc. The “boot” process will continue as normal, with Wininit then launching the Service Control Manager (Services.exe), which will then launch all automatic services, and so on. New applications can now execute in the server silo, which will run with a login session associated with a virtual service account LUID, as described earlier.

## Ancillary functionality

You may have noticed that the short description we've seen so far would not result in this “boot” process succeeding. For example, as part of its initialization, it will want to create a named pipe called nsvcs, which requires communicating with \Device\NamedPipe, or as Services see it, \Silo\JID\Device\NamedPipe. But no such device exists!

As in order for drivers must register their own silo monitors, which then use the notifications to create their own per-silo device objects. The kernel provides an API, PsAttachSiloToCurrent-Thread (and matching PsDetachSiloFromCurrent-Thread), which temporarily sets the Silo field of the ETHREAD object to the passed-in job object. This will cause all access, such as to the object manager, to be treated as if it were coming from the silo. The named pipe, for example, use this function to create a NamedPipe object within the \Device namespace, which will now be part of \Silo\JID\.

Another question is: if applications launch in essentially a "service" session, how can they be interactive and process input and output? First, it is important to note that there is no GUI possible permitted launching under a Windows container, and attempting to use Remote Desktop (RDP) to access a container will be impossible. As such, only command-line applications can execute. Even such applications normally need an "interactive" session. So how can they function? The secret lies in a special process, CExec.exe, which implements the container execution service. This service uses a named pipe to communicate with the Docker and Vcompute services on the host, and is used to launch the actual containerized applications in the session. It is also used to emulate the console functionality that is normally provided by Hostexec, piping the input and output through the named pipe to the actual command prompt (or PowerShell) window that was used in the first place to execute the docker command on the host. This service is also used when using commands such as docker cp to transfer files from or to the container.

## Container template

Even if we take into account all the device objects that can be created by drivers as silos are created, there are still countless other objects, created by the kernel as well as other components, with which services running in silo 0 are expected to communicate, and vice-versa. In user mode, there is no silo monitor system that would allow components to support this, and forcing every driver to create a specialized device object to represent each silo wouldn't make sense.

If a santo to play music on the sound card, it shouldn't have to use a separate device object to represent the exact same sound card as every other silo would access, and as the host itself. This would only be needed if, say, per-silo object sound isolation was required. Another example is AFD. Although it uses a silo monitor, this is to identify user-mode service hosts the DNS client that needs to talk to kernel-mode DNS requests, which will be per-silo, and not to create separate \Silos\Device\AFD objects, as there is one network/Winsock inside the system.

Beyond drivers, the registry also contains various pieces of global information that must be visible and across all silos, the VReg container then provide sandboxing around.

To support all the needs, the silo namespace, registry, and file system are defined by a specialized container file, which is located in %SystemRoot%\System32\Containers\wsc.def by default, once the Windows Containers features are enabled in the Add/Remove Windows Features dialog box. This file describes the object manager and registry rules and ruling surrounding it, allowing the definition of symbolic links as needed to the true objects on the host. It also describes which job object, volume mount points, and network isolation policies should be used. In theory, future use of silo objects in the Windows operating system could allow different files to be used for other kinds of containerized environments. The following is an excerpt from wsc.def for a system for which containers are enabled:

