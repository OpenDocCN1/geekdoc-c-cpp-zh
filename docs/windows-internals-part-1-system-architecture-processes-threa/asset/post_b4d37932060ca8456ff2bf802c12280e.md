
If the ready thread cannot be run right, it is moved into the ready state on the shared or local queue (as appropriate base on affinity constraints), where it will await its turn to run. As seen in the scheduling scenarios earlier, the thread will be inserted either at the head or the tail of the queue, based on whether it entered the ready state due to preemption.

> Note Regardless of the underlying scenario and various possibilities, threads are mostly put on their ideal processor's per-processor ready queues, guaranteeing the consistency of the algorithms that determine which logical processor picks a thread to run.

# Heterogeneous scheduling (big.LITTLE)

The kernel assumes SMP system, as previously described. However some ARM-based processors contain multiple cores that are not the same. A typical ARM CPU (for example, from Qualcomm) contains some powerful cores, which should run for short periods at a time (and consume more energy); and set of weaker cores, which can run for longer periods (and consume less energy). This is sometimes called big.LITTLE.

Windows 10 introduced to distinguish between these cores and schedule based on the core's size and policy, including the foreground status of the thread, its priority, and its expected runtime. Windows initializes the set of processors when the Power Manager is initialized by calling pInitializeHeteroScheduler (and if processors are not added to the system). The function allows the simulation of hetero systems (for, testing purposes) by adding keys under the registry HKLM\System\CurrentControlSet\SessionManager\Kernel1\KGroups as follows:

- A key should use two decimal digits to identify a processor group number. (Recall that each group holds at most 64 processors). For example, if 0 is the first group, 1 is the second, (On most systems, one group suffices).

- Each key should contain a DWORD value named SmAllProcessorMask that is a mask of processors that would be considered small. For example, if the value is 3 (the first two bits are on) and the group has six total processors, that would mean 0 and 1 (3 or 2 are small), while the other four processors are big. This is essentially the same as an affinity mask.

# Group-based scheduling

The previous section described the standard thread-based scheduling implementation of Windows. Since its appearance in the first release of Windows NT (with scalability improvements done with each subsequent release), it has reliably served every general and server scenarios. However, because thread-based scheduling attempts to fairly share the processor or processors only competing threads of the same priority, it does not account for higher-level requirements such as the distribution of threads to users and the potential for certain users to benefit from more CPU time at the expense of other users. This is problematic in terminal-services environments, where

An important parameter maintained by a scheduling group is called *rank*, which can be considered a scheduling priority of the entire group of threads. A rank with a value of 0 is the highest. A higher-rank number means the group has used more CPU time and is less likely to get more CPU time.

Rank always trumps priority. This means given two threads with different ranks, the lower value rank is preferred, regardless of priority. Equal-rank threads are compared based on priority. The rank is adjusted periodically as cycle usage increases.

Rank 0 is the highest (it wins out) against a higher number rank, and is implicit for some threads. This can indicate one of the following:

- The thread is not in any scheduling group ('normal') threads
- Under-quota threads
- Real-time priority threads (16–31)
- Threads executing at IRQL APC_LEVEL (1) within a kernel context or guarded region (see Chapter 8 in Part 2 for on APCs and regions)

At various scheduling groups (for example, KQuantum), the decision of which thread scheduled next to the scheduling group (if any) of the current and ready threads. If a scheduling group exists, the lowest value wins out, followed by priority (if ranks are equal), followed by the first arriving thread (if priorities are equal); round-robin at quantum end.

# Dynamic fair share scheduling

Dynamic fair share scheduling (DFSS) is a mechanism that can be used to distribute CPU time among sessions running on a machine. It prevents one session from potentially monopolizing the CPU if some threads running under that session have a relatively high priority and a run lot. It is enabled by default on a Windows Server system that has the Remote Desktop role. However, it can be configured on any system, client or server. Its implementation is based on group scheduling described in the following section.

During the very last parts of system initialization, the registry SOFTWARE is initialized by Smss, the process manager initializes the final post-boot initialization in BootPhaseComplete, calls PspDFSSEnabled. Here, the system decides which of the two quota mechanisms (DFSS or legacy) will use. For DFSS to be enabled, EnabledQuota registry value must be set to a non-zero value in both of the quotas. The first of these is HKLM\SOFTWARE\Policies\Microsoft\Windows\SessionManager\Quota, System\ControlSet\Control\SessionManager\Quota determines whether the system supports the functionality (which, by default, is set to TRUE on Windows Server with the Remote Desktop role).

If DFSS is enabled, the PspEnabled global variable is set to TRUE, which makes all threads belonging to scheduling groups (except session Processes). DFSS configuration parameters are read from the aforementioned groups by a call to PspReadDfssConfigurationValues and stored in global variables. These keys are monitored by the system. If modified, the notification callback calls PspReadDfssConfigurationValues again to update the configuration values.
