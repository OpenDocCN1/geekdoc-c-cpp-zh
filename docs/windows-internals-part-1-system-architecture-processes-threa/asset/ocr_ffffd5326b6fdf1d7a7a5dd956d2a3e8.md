# Assuredured authentication

A fundamental problem with password-based authentication is that passwords can be revealed or used by malicious third parties. Windows includes a mechanism that strengthens the authentication of how a user authenticated with the system, which allows objects to be protected from access if a user did not authenticate securely. (Smartcard authentication is considered to be a stronger form of authentication than password.)

On systems that are joined to a domain, the domain administrator can specify a mapping between an object identifier (OID a unique numeric representing a object type) on a certificate used for authenticating a user (such as a smartcard or hardware security token) and a SID that is placed into the user's access token when the user successfully authenticates with the system. An ACE in a DACL on an object can specify which SID be part of the user's token to gain access to the object. Technically, this is known as a group claim. In other words, the user is claiming a claim based upon the authentication mechanism. This feature is not enabled by default, and it must be configured by the domain administrator in a domain with certificate-based authentication.

Assured authentication builds on Windows security features a which provides a great level of flexibility to IT administrators and anyone concerned with enterprise IT security. The enterprise decides which OIDs to embed in the certificates it uses for authenticating users and the mapping of particular OIDs to Active Directory universal groups (SIDs). A user's group membership can be used to identify whether a certificate was used during the login operation. Different certificates can have difference policies and, thus, different levels of security, which can be used to protect highly sensitive objects (such as files or anything else that have a security descriptor).

Authentication protocols (APs) retrieve OIDs from certificates during certificate-based authentication. These OIDs are mapped to SIDs, which are in processed during group membership expansion, and placed in the access token. The mapping of OID to universal group is specified in Active Directory.

As an example, an organization may have several certificate-issue policies named Contractor, Full Time Employee, and Senior Management, which map to the universal groups Contractor-Users, FTE-Users, and SM-Users, respectively. A user named Abby has a smartcard with a certificate issued using the Senior Management policy. When she logs into her smartcard, she receives an additional group membership (is represented by SID in her access token) indicating that she is a member of the SM-Users group.
