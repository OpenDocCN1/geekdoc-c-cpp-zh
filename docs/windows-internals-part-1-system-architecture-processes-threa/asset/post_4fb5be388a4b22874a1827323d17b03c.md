
As another example, the Spell Checking Facility will return NULL for languages which don't have a spell checker, which it returns an "empty" spell checker on Windows 8.1. Similarly, the implementation of the function IShellLink::Resolve returns E_INVALIDARG when operating in Windows compatibility mode when giving a relative path, but will not contain this check in Windows 7 mode.

Furthermore, calls to GetVersionEx or the equivalent functions in NTDLL will return the maximum version number that corresponds to the SwitchBack Context GUID that was specified.

Note: These APIs have been deprecated, and calls to GetVersionEx will return 6.2 on all versions of Windows 8 and later if a higher SwitchBack GUID is not provided.

## SwitchBack behavior

Whenever a Windows API is affected by changes that might break compatibility, the function's entry code calls the SbSwitchProcedure to invoke the SwitchBack logic. It passes along a pointer to the SwitchBack module table, which contains information about the SwitchBack mechanisms employed in the module. The table contains a description of each branch-point that identifies it with a name and a comprehensive description, also with an associated mitigation tag. Typically, there will be several branch-points in a module, for Windows Vista behavior, or for Windows 7 behavior, etc.

For each branch-point, the required SwitchBack context is given—it is this context that determines which of the two (or more) branches takes at runtime. Finally, each of descriptors contains a function pointer to the actual code that each branch should execute. If the application is running on the Windows 10 GUID, this will be part of its SwitchBack context, and the SbSelectProcedure API, upon parsing the module table, will find the module entry descriptor for the context and calls the function pointer.

SwitchBack uses ETW to trace the selection of given SwitchBack contexts and branch-points and feeds the data into the Windows AIT (Application Impact Telemetry) logger. This data can be periodically collected by Microsoft to determine the extent to which each entry is used, identifying applications (if a full trace is provided), and third-party vendors. As mentioned, the compatibility level of application is stored in its memory. At load time, the loader parses the manifest, creates a context structure, and caches it in the PEB. This context contains the associated GUIDs that this process is executing and determines which version will be executed.

## API Sets

Whenever SwitchBack uses API redirection for specific application-compatibility scenarios, there is a more pervasive mechanism used in Windows for all applications. Its purpose is to enable fine-grained categorization of Windows APIs into DLLs instead of having large-purpose DLLs. For example, Figure 3-14 shows a screenshot of Dependency Walker where Kernel32, a core Windows library, normally makes up the entire API surface exposed by Kernel32.dll, imports from multiple DLLs that span thousands of APIs that might not be needed on all Windows systems today and in the future. This technology, developed mainly to support refactoring of the bottom-most layers of the Windows architecture, gets hand with Kernel32.dll and Advapi32.dll.

First, this allows applications to link only with API libraries that provide the functionality. Second, if Microsoft were to create a version of Windows that did not support localization (say, a non-user-facing, English-only system), it would be possible to simply remove sub-DLL and modify the API set. This would result in a smaller Kernel32 binary, and Figure 3-14 API set for kernel32.dll.

## Processes and jobs

With this technology, a "base" system called MinWin is defined (and built at source level), with a minimum set of services includes processes such as CSRSS and the Service Control Manager, and a handful of Windows services. However, removing components from Windows leaves dangling-code paths that are entirely self-contained. When the process manager initializes, it calls the PspInitializeApiMap function, which is responsible for creating a section object of the API redirection table, which is stored in %SystemRoot%\System32\ApiSchema.dll. The DLL contains no executable code, but it has a section that contains setting data that maps virtual API sets to DLLs that implement the APIs. Whenever a new process starts, the process manager maps the section object into the process's address space and sets the ApiSet field in the PEB to the base address where the section was mapped.

In the loader, LdrLoadFileName function, which is normally responsible for local and Sx/Fusion redirection that was mentioned earlier, also checks for API redirection whenever a new import library has a name starting with API- (either dynamically or statically). The API table is organized by library with each entry describing in which DLL the function can, and that DLL gets loaded.
