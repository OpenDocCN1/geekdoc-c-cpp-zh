## Termination

When a thread finishes running (either because it returned from its main routine, called Exit, or was killed with Terminate), it moves from the running state to the terminated state. If there are no handles on the thread object, the thread is removed from the process thread list and the associated data structures are deallocated and released.

## Idle threads

When no runnable thread exists on a CPU, Windows dispatches CPU's idle thread. Each CPU has its own dedicated idle thread. This is because on a multiprocessor system, one CPU can be executing a thread while other CPUs might have threads to execute. Each CPU's idle thread is found via a pointer in CPU's PRCB.

All the threads belong to the idle process. The idle process and idle threads are special cases in many ways. They, of course, represented by PROCESS/KERNEL and ETHREAD/KTHREAD structures, but they are not executive manager processes and threads. Not the idle process on the process list. (This is why it does not appear in the kernel debugger's ! process 0 0 command.). However, the idle thread or their process are found in other ways.

> EXPERIMENT: Displaying the structures of the idle threads and idle process
You can find the idle thread and process structures in the kernel debugger via the !pcr command (PCR is short for processor control region). This command displays a subset of information from the PCR and the associated PRCB. !pcr takes a single numeric argument, which is the number of the CPU PCR is to be displayed. The boot processor is 0. It is always present, so !pcr 0 should always work. The output shows the results of this command from a local kernel debugging session for a 64-bit, eight-processor system:

Although some details of the flow vary between architectures (this is one of the routines in assembly and not C), the basic sequence of the idle thread is as follows:

+   1. The idle thread enables pending interrupts to be delivered, and disables them (using the STI and CLI instructions on x86 and x64 processors). This is desirable because significant parts of the idle thread execute with interrupts disabled.
2. On the debug build some architectures, the idle thread checks whether a kernel debugger is trying to break into the system. If so, it gets access.
3. The idle thread checks whether any DPCs (described in Chapter 6) are pending on processors. DPCs could be pending if a DPC interrupt was not generated when they were generated. If DPCs are pending, the idle loop calls KiRetList to deliver them. This will also perform timer expiration, as well as deferred reading; the latter is explained in the upcoming "Multiprocessor systems". KiRetList must be entered with interrupts disabled, which is why interrupts are left disabled at the end of step I. KiRetList exits with interrupts disabled as well.
4. The idle thread checks whether quantum expiration has been requested. If so, QuantumEnd calls to process the request.
5. The idle thread checks whether a thread has been selected to run on the next processor. If so, it dispatches that thread. This could be because, for example, a DPC or timer expiration processed in step 3 resolved the case of a waiting thread, or if another processor selected the thread for this processor to run while it was already in the idle loop.
6. If requested, the idle thread checks for threads ready to run on other processors and, if possible, schedules one of them locally. (This operation is explained in the upcoming "Idle scheduler")
7. The idle thread calls the registered power-management processor idle routine (in any case power-management functions need to be performed), which is either in the processor driver (such as intelppm.sys) or in the HAL if such a driver is unavailable.
