
At the end of 500 ms, if the resource is still owned, the executive attempts to prevent CPU starvation by acquiring the dispatcher lock, boosting the owning thread or threads to 15 (if the original owner priority is less than the waiter's and not 15), resetting their quantums, and performing another await.

Because resources can be either shared or exclusive, the kernel boosts the exclusive owner and checks for shared owners and boosts all of them. When the waiting thread enters the wait state again, the hope is that the scheduler will schedule one of the owners, which will have enough time to complete its work and release the resource. Note that this boosting mechanism is used only if the resource doesn't have the Boost flag; developers can choose to set if the priority-in mechanism described here works well with their usage of the resource.

Additionally, this mechanism isn't perfect. For example, if the resource has multiple shared owners, the executive boosts all threads to priority 15. This results in a surge of high-priority threads on the system, with all full quantums. Although the initial owner will run first (because it was the first to be boosted and therefore is first on the ready list), the other shared owners will run next because the waiter's priority was not boosted. After all the shared owners have had a chance to acquire it and their priority has been decreased while waiting, the waiter will finally get to acquire the resource. Because shared owners can promote or convert their ownership from shared to exclusive as soon as the exclusive releases the resource, it's possible for this mechanism not to work as intended.

## Priority boosts for foreground threads awaits

As will be described shortly, whenever a thread in the foreground process completes a wait operation on a kernel object, the kernel boosts its current (not base) priority by the current value of PrioritySeparation (The system is responsible for determining which process is considered to be in the foreground.) As described earlier in this chapter in the section "Controlling the quantum," Priorityation reflects the quantum-table index used to select quantums for the threads of foreground applications. However, in this case, it is being used as a priority boost.

The reason for this boost is to improve the responsiveness of interactive applications. By giving the foreground application a small boost when it completes a wait, it has a better chance of running right away, especially when other processes at the same base priority might be running in the background.

## Priority boosts after GUI threads wake up

Threads that own windows receive an additional boost of 2 when they wake up because of windowing activity such as the arrival of window messages. The windowing system (Win32k.sys) applies this boost when it calls KeSetEvent to an event used to wake up a GUI thread. The reason for this boost is similar to the previous one: to favor interactive applications.

> EXPERIMENT: Watching priority boosts on GUI threads
You can see the windowing system apply its boost of 2 for GUI threads that wake up to process window messages by monitoring the current priority of a GUI application and moving the mouse across the window. Just follow these steps:

- 1. Open the **System** utility in Control Panel.
- 2. Click the **Advanced System Settings** label, click the **Advanced** tab, click the **Settings** button in the Performance section, and click the **Advanced** tab.
- 3. Select the **Programs** option. This gives PrioritySeparation a value of 2.
- 4. Run Notepad.
- 5. Start the Performance Monitor tool.
- 6. Click the Add Counter toolbar button or press Ctrl+I to open the Add Counters dialog box.
- 7. Select the Thread object and then select the Priority Counter.
- 8. In the Instances box, type Notepad.
- 9. Scroll down to the Notepad/0 entry, click the Add button, and then OK.
- 10. As in the previous experiment, change the maximum scale to 16. You should see the priority of thread 0 in Notepad at 8 (Because Notepad entered a state shortly after receiving the boost of 2 it might not yet decayed from 10).
- 11. With Performance Monitor in the foreground, move the mouse across the window. Notice that the priority remains at 10 and sometimes at 9, for the reasons explained.

> Note You won't likely catch Notepad at 8. This is because it runs so little after receiving the boost of 2 that it never experiences more than one priority level of decay.

- 12. Bring Notepad to the foreground. You should see the priority rise to 12 and remain there. ## Priority boosts for CPU starvation

Imagine the following situation: A priority 7 thread is running, preventing a priority 4 thread from receiving CPU time. However, a priority 11 thread is waiting for some resource that the priority 4 thread has locked. Because the priority 7 thread in the middle is eating up all the CPU time, the priority 4 will never run long enough to finish whatever it's doing and release the resource blocking the priority 11 thread. This scenario is known as priority inversion.
