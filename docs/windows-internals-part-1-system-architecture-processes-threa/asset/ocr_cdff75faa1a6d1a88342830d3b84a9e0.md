# Security assertions

Earlier, we described how Control Guard will terminate the process. We also explained how
other mitigation or security features will raise an exception to kill the process. It is important to be ac-
curate with exactly what happens during these security violations because these descriptions hide
important details about the mechanism.

In fact, when a security-related breach occurs, as when CFG detects an indirect call or
jump, terminating the process through the standard TerminateProcess mechanism would not be an\adequate path. There be no crash generated, and no telemetry sent to Microsoft. These are both
important tools for the administrator to understand that a potential exploit has executed or that an
application issue exists, as well as for Microsoft track zero-day exploitation in the wild.
On the flip side, while raising an exception would achieve the desired result, exceptions are callbacks,
which can be:

+   - Potentially hooked by attackers if /SAFESH and SEHOP are not enabled, causing the
security check to be the one that gives control to an attacker in the first place—or an attacker
can simply "swallow" the exception.
- Potentially hooked by legitimate parts of the software through an exception filter or
vectored exception handler, both of which might accidentally swallow the exception.
- Same as, but intercepted by a third-party product that has injected its own library into
the process. Common to many security tools, this can also lead in the exception not being cor-
rect delivered to Windows Error Reporting (WER).
