Rt1CloneUserProcess finishes by calling Rt1CreateUserProcess, the user-mode function responsible for general creation, passing flags that indicate the new process should be a clone of the current one. Rt1CreateUserProcess in turn calls ZwCreateUserProcess to request the kernel to create the process.

When creating a cloned process, ZwCreateUserProcess executes most of the code paths as when it creates a new process, with the exception PsAllocateProcess, which it calls to create the process object and initial thread, calls MmInitializeAddressSpace with a flag specifying that the address should be a copy-on-write copy of the target process instead of an initial address space. The memory manager uses the same space it provides for the Services for Unix Applications to efficiently clone the address space. Once the target process continues execution, any changes to its address space are seen only by it, not the clone. This enables the clone's address space to represent a consistent point-in-time view of the target process.

The clone's execution begins at the point after the return from Rt1CreateUserProcess. If the clone's creation is successful, it returns the STATUS_PROCESS_CLONED code, whereas the cloning thread then synchronizes with the target and, at last calls a function optionally passed to Rt1CreateProcessReflection, which performs analysis of the process and reports the results back to the thread that calls Rt1CreateProcessReflection. If no function failed, the thread suspends or terminates, depending on the flags passed to Rt1CreateProcessReflection.

When RAD and WDI process reflection, asking for the function to return a handle to the cloned process and for the clone to suspend itself after it has initialized, they generate a dump of the target process, which suspends the target for the dump generation. Next, they generate a more comprehensive dump of the cloned process. After they generating the dump of the clone, they terminate the clone. The target process can execute during the time window between the minidump's completion and the creation of the clone, but for most scenarios any inconsistencies do not interfere with troubleshooting. The Procdump utility from Sysinternals also follows these steps when you specify the -r switch to create a reflected dump of a target process.

This chapter examined how the Windows memory manager implements virtual memory management. With as most modern operating systems, each process is given access to a private address space, protecting one's process memory from another by allowing processes to share memory efficiently and securely. Advanced capabilities, such as the inclusion of mapped files and the ability to sparsely allocate memory, are also available. The Windows environment subsystem makes most of the memory manager's capabilities available to applications through the Windows API.

# I/O system components

The design goals for the Windows I/O system are to provide an abstraction of devices, both (physical) and software (virtual or logical), to applications with the following features:

- Uniform security and naming across devices to provide shareable resources. (See Chapter 7, "Security," for a description of the Windows security model.)

- High-performance asynchronous packet-based I/O to allow for the implementation of scalable applications.

- Services that allow drivers to be written in a high-level language and easily ported between different machine architectures.

- Layering and extensibility to allow for the addition of drivers that transparently modify the behavior of other drivers or devices, without requiring any changes to the behavior or device

- Dynamic loading and unloading of device drivers so that drivers can be loaded on demand and not consume system resources when needed.

- Support for Plug and Play, where the system locates and installs drivers for newly detected hardware, assigns them hardware resources they require, and allows applications to discover and activate device interfaces.

- Support for power management so that the system or individual devices can enter low-power states.

- Support for multiple installable systems, including FAT (and its variants, FAT32 and exFAT), the CD-ROM file system (CDFS), the Universal Disk Format (UDF) file system, the Resilient File System (ReFS), and the Windows file system (NTFS). (See Chapter 13, in Part 2 of this book for more specific information on file types and architecture).

- Windows Instrumentation (WMI) support and diagnostics so that drivers can be managed and monitored through WMI applications and scripts. (WMI is described in Chapter 9, "Management mechanisms," in Part 2.)

# The I/O manager

The I/O manager is the core of the I/O system. It defines the orderly framework, or model, within which I/O requests are delivered to device drivers. The I/O system is packet driven. Most I/O requests are represented by an I/O request packet (IRP), which is a data structure that contains information completely describing an I/O request. The IRP travels from one I/O system component to another (As you'll discover in the section "Fast I/O", fast I/O is the exception; it doesn't use IRPs). The design allows an individual application thread to manage multiple I/O requests concurrently. (For more information on IRPs, see the "I/O request packets" later in this chapter.)

The I/O manager creates an IRP in memory to represent an I/O operation, passing a pointer to the correct driver and disposing of it when the I/O operation is complete. In contrast, a driver receives an IRP, performs the operation or IRP specified, and passes the IRP back to the I/O manager, either because the requested I/O operation has been completed or because it must be passed to another driver for further processing.
