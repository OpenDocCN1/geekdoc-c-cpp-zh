# Bandwidth reservation (scheduled file I/O)

I/O bandwidth-reservation support is useful for applications that desire consistent I/O throughput. For example, using the SetFileBandwidthReservation call, a media player application can ask the I/O system to guarantee it the existing capability to read data from a device at a specified rate. If the device can deliver data at the requested rate and existing reservations allow it, the I/O system gives application guidance as to how fast it should issue I/Os and how large the I/Os should be.

The I/O system won't service other I/Os unless it can satisfy the requirements of applications that have made reservations on the target storage device. # Container notifications

Container notifications are specific classes of drivers that can register for an asynchronous callback mechanism using the IoRegisterContainerNotification API and the notification class that interests them. For such, one class is implemented in Windows: IoSessionNotification. This class allows drivers to have their registered callback invoked whenever a change in the state of a given session is registered. The following changes are supported:

- A session is created or terminated.
- A user connects to or disconnects from a session.
- A user logs on or off from a session.

By specifying a device object that belongs to a specific session, the driver callback will be active only for that session. In contrast, by specifying a global device object (or no device object at all), the driver will receive notifications for all events on a system. This is particularly useful for devices that participate in the Plug and Play device redirection functionality that is provided through Terminal Services, which allows a remote device to be visible on the connecting host's Plug and Play manager as well (such as audio or printer device redirection). Once the user disconnects from a session with audio playback, for example, the device driver needs a notification in order to stop redirecting the source audio stream.

# Driver Verifier

Driver Verifier is a mechanism that can be used to help find and isolate common bugs in device drivers or other kernel-mode system code. Microsoft uses Driver Verifier to check its own drivers as well as all device drivers vendors submit that the drivers submitted are compatible with Windows and free from common driver errors. (Although not described in this book, there is also a corresponding Application Verifier tool that has resulted in quality improvements for user-mode code in Windows.)

Driver Verifier settings are stored in the registry under HKLM\System\CurrentControl\SessionManager\Memory Management. The VerifierLevel value contains a bitmask that represents the options that are enabled. The Driver values contain the names of the drivers. (These values do not exist in the registry until you select drivers to verify.) If you choose to verify all drivers (which you should never do, since this will cause considerable system slowdown), VerifierDrivers is set to an asterisk (*) character. Early in the boot process, the memory manager reads the Driver Verifier registry values to determine which drivers to verify and which Driver Verifier options are enabled.(Note that if you are in safe mode, any Driver Verifier settings are ignored.) If you've selected at least one driver for verification, the kernel checks the name of every device driver it loads into memory against the list of drivers you've selected. For every driver that appears in both cases, the kernel invokes VfLoadDriver function, which calls other Vf* functions to replace the driver's references to a number of kernel functions with references to Verifier-equivalent versions of those functions. For example, ExAllocatePool is replaced with a call to VerifierAllocatePool. The window system driver (Win32k.sys) also makes similar changes to use Verifier-equivalent functions.
