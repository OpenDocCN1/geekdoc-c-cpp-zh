

Dispatch/DPC (2) (DISPATCH_LEVEL) 这是内核调度器运行的 IRQL 。这意味着如果一个线程将当前 IRQL 提高到 2（或更高），该线程本质上将拥有无限的时间片，且不会被另一个线程抢占。实际上，在 IRQL 降到 2 以下之前，调度器无法在当前 CPU 上唤醒。这意味着了几几点：

- 当 IRQL 处于 2 级或以上时，任何对内核调度器对象（如互斥锁、信号量和事件）的等待会导致系统崩溃。这是因为等待的线程可能会进入等待状态，并在同一块 CPU 上应该调度另一个线程。然而，由于调度器未在此级别运行，这种情况不会发生；相反，系统将发生蓝化（bug-check）（唯一的例外是等待超时为零，意味着没有请求等待，只是获取对象的受信号状态）。

- 无法处理页错误。这是因为页错误需要将上下文切换到其中一个被修改的页面写入程序。然而，系统不允许切换上下文，系统将会崩溃。运行在 IRQL 2 或以上的代码只能访问非分页内存——通常从非分页池分配，根据定义，它驻留在物理内存中。

设备 IRQL (x86 为 3–6；x64 和 ARM 为 3–12) (DIRQL) 这些是分配给硬件中断的级别。当发生中断时，内核陷阱会调用相应的中断服务程序 (ISR) 并将其 IRQL 提高到关联中断的级别。由于此值始终高于 DISPATCH_LEVEL (2)，所有适用于 IRQL 2 的规则也适用于 DIRQL。

运行在特定的 IRQL 会屏蔽具有较低 IRQL 的中断。例如，IRQL 为 8 的 ISR 不会干扰 IRQL 为 7 或更低的（任何 CPU）。具体来说，没有用户模式代码能够运行，因为它运行在 IRQL 0。这意味着在通常情况下，在高 IRQL 下运行是不理想的；尽管在某些特定场景下（我们将在本章中查看），这种做法是合理的，而且实际上对于系统的正常运行是必须的。

# 延迟过程调用 (Deferred Procedure Calls)

延迟过程调用 (DPC) 是一种封装了在 IRQL DPC_LEVEL (2) 下调用函数的对象。DPC 的存在主要是为了在中断后处理，运行在 DIRQL 级别，（从而）屏蔽了其他待处理的中断。ISR 会完成尽可能少的工作，主要是读取设备状态并告诉其停止中断信号，通过请求 DPC 将处理延迟到较低的 IRQL (2)。“延迟”(Deferred) 一词意味着 DPC 不会立即执行——它无法执行，因为当前 IRQL 高于 2。然而，如果 ISR 返回，则没有待处理的中断需要处理，CPU IRQL 将降到 2，并将执行已累积的 DPC（可能只有一个）。图 6–5 显示了当代码在某些 CPU 上以 IRQL 0 正常执行时，来自硬件设备的中断（具有异步性，意味着它们可以任何时间到达）可能发生的事件序列的简化示例。

- 2. 一个 IRQL 为 5 的硬件中断到达。由于 5 大于零（当前 IRQL），保存 CPU 状态，IRQL 提高到 5，并调用与中断相关的 ISR。注意没有发生上下文切换；执行的是同一个线程（如果线程在用户模式，则切换到内核模式）。

- 4. 假设另一个 IRQL 为 8 的中断到达。系统决定由 CPU 处理。由于 8 大于 5，代码再次被中断，保存 CPU 状态，IRQL 提高到 8，CPU 跳到 ISR。注意如果 IRQL 为 2 或更高，调度器无法唤醒。
- 5. ISR 正在执行。在完成之前，ISR 会在较低的 IRQL 下进行一些处理，以便 IRQL 小于 8 的中断可以被处理。
- 6. 作为最后操作，ISR 插入自己的 DPC 通过调用 `KeInsertDpc` 函数进行后处理。（我们将在下一节讨论此。）然后 ISR 返回，恢复进入之前的之前的 CPU 状态。
- 7. 在此点，IRQL 降到之前的级别（5），CPU 继续执行被中断的 ISR。
- 8. 在 ISR 完成之前，它将所需的后处理 DPC 队列。这些 DPC 被收集在尚未检查的队列中。然后 ISR 返回，恢复启动之前的 CPU 状态。
- 9. 在此点，IRQL 将降到零。然而，内核注意到有待处理的 DPC，并将 IRQL 降到 2 (DPC_LEVEL)，进入 DPC 处理循环。
- 10. 最后，IRQL 可以回到零，恢复最初被中断的用户或内核代码执行。再次，这意味着 ISR 和 DPC 程序不依赖于任何特定线程（以及进程的一部分）来执行其代码。

# 设备驱动

为了与 I/O 管理器和其他 I/O 系统组件集成，设备驱动必须符合特定设备类型及其在管理设备中扮演角色的实现指南。本节讨论了 Windows 支持的设备驱动类型以及设备驱动的内部结构。

> 注意：大多数内核模式设备驱动是用 C 编写的。从 Windows Driver Kit 8.0 开始，驱动也可以用 C++ 编写，新的编译器专门支持内核模式 C++。非常不建议使用汇编语言，因为它增加了复杂性并导致驱动难以移植到 Windows 支持的硬件架构（x86、x64 和 ARM）。

# 设备驱动类型

Windows 支持各种设备驱动类型和编程环境。即使在特定类型的驱动中，编程环境也取决于驱动针对的具体设备类型。

驱动最广泛的分类是用户模式驱动还是内核模式驱动。Windows 支持两种用户模式驱动：

- Windows 子系统打印机驱动：将设备无关请求转换为打印机特定命令。这些命令随后转发到内核模式端口驱动，即通用串行（USB）打印机端口驱动 (Usbprint.sys)。

- 用户模式驱动框架 (UMDF) 驱动：运行在用户模式下的硬件驱动。它们通过高级本地过程 (ALPC) 与内核模式 UMDF 库通信。更多信息请参见本章稍后的“用户模式驱动框架”部分。

在本章中，重点是内核模式设备驱动。内核模式驱动有很多类型，可以分为以下基本类别：

- 文件系统驱动：接受对文件的 I/O 请求，并通过向质存储或网络设备驱动发出自己的显式请求来满足这些请求。

- 即插用驱动：与硬件工作，并与 Windows 电源管理器和 PnP 管理器集成。它们包括用于质存储设备、视频适配器、输入设备和网络适配器的驱动程序。

- 非即插用驱动：这些包括内核扩展，即扩展系统功能的模块。它们通常不与 PnP 管理器或电源管理器集成，因为它们通常不管理实际硬件。示例包括网络 API 和协议驱动。Sysinternals 的 Process Monitor 有一个驱动程序，它是非 PnP 驱动的示例。

在内核模式驱动类别中，根据驱动遵循的驱动模型及其在服务设备请求中的作用进一步进一步分类。

# WDM 驱动

WDM 驱动是遵循 Windows Driver Model (WDM) 的设备驱动。WDM 包含了对 Windows 电源管理、即插用和 WMI 的支持，大多数即插用驱动都遵循 WDM。WDM 驱动分为三种：

- 总线驱动：管理逻辑或物理总线。总线的示例包括 PCMCIA、PCI、USB 和 IEEE 1394。总线驱动负责检测并向 PnP 管理器报告连接总线的设备，并管理总线的电源服务。这些通常由微软开箱提供。

- 功能驱动：管理特定类型的设备。总线驱动通过 PnP 管理器将设备呈现给功能驱动。功能驱动是向操作系统导出设备接口的驱动。通常，它是对设备操作最了解的驱动。

- 过滤器驱动：它们在逻辑上层叠在功能驱动之上（称为下层过滤器或功能过滤器）或总线驱动之上（称为下层过滤器或总线过滤器），增强或更改设备或其他驱动的行为。例如，键盘实用程序可以通过叠加在键盘功能驱动之上的键盘过滤器驱动来实现。
