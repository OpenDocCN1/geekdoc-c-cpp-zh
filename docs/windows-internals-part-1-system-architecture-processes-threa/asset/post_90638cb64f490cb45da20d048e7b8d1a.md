
# TABLE 5-6 Pool columns

| Column | Explanation |
|---|---|
| Tag | This is a four-byte tag given to the pool allocation. |
| Type | This is the pool type (padded or non-padded). |
| Alocs | This is a count of all allocations. The number in parentheses shows the difference in the Allocs column since the last update. |
| Frees | This is the count of all frees. The number in parentheses shows the difference in the Frees column since the last update. |
| Diff | This is the count of allocations minus frees |
| Bytes | This is the total bytes consumed by this tag. The number in parentheses shows the difference in the Bytes column since the last update. |
| Per Alloc | This is the size in bytes of a single instance of this tag. |

For a description of the meaning of the pool tags used by Windows, see the Pooltag.txt file in the Triage subdirector where the Debugging tools for Windows are located. Because third-party device driver tags are not listed in this file, you can use the -c switch the 32-bit version of Poolmon that comes with the WDK to generate a local pool tag file (Localtag.txt). This file will contain pool tags used by drivers after it was loaded, including third-party drivers. (Note if a device-driver has been deleted after it was loaded, its pool tags will not be recognized.)

Alternatively, you can search the drivers on your system for a pool tag using the Strings.exe tool from Sysinternals. For example, the following command searches drivers that contain the string "abcd":

```
strings %SYSTEMROOT%\system32\drivers\*.sys | findstr /i "abcd"
```

Device drivers do not necessarily have to be located in %SystemRoot%\System32\Drivers. They can be in any folder. To list the full path of all loaded drivers, follow these steps:

- 1. Open the Start menu and type Msinfo32 (System Information should appear).
- 2. Run System Information.
- 3. Select Software Environment.
- 4. Choose System Drivers. If a device driver has been loaded and deleted from the system, it will not be listed here.

An alternative way to view pool usage by device driver is to enable the pool-tracking feature of Driver Verifier, explained in Chapter 6. While this mapping from pool tag to device driver unnecessary, it does require a reboot (to enable Verifier on the desired drivers). After rebooting with pool tracking enabled, you can run the Driver Verifier Manager (%SystemRoot%\System32\Verifier.exe) or use the Verifier /log command to send the pool-usage information to a file.

Finally, you can view pool usage with the kernel debugger poolused command. The poolused2 command shows non-paged pool sorted by pool tag using the most amount of pool. The !poolused !used2 command lists pool-usage, again sorted by pool tag using the most amount of pool. The following example shows the output from these two commands:

# EXPERIMENT: Troubleshooting a pool leak

In this experiment, you will find a real aged leak on your system so that you can use the techniques described in the previous section to track down the leak. The leak will be generated by Myfault tool. Follow these steps:

- 1. Run Myfault.exe for your OS bit (for example, 64-bit system).
- 2. Myfault.exe loads the Myfault.sys device driver and presents a diag with the Crash selected. It should look like this: Not My Fault![](img/ff0e6a9d867a3a6e952eb1d94680fc346.png)

- 3. Ensure that the Leak/Second setting is set to 1000 KB.
- 4. Click the Paged button. This causes Myfault to begin sending requests to the Myfault device driver to allocate pool. The Paged pool is not normally released when you close a program that has caused it (interacting with buggy driver). However, to make testing easier, Myfault detects that the process was closed and frees its memory.
- 5. While the pool is leaking, open Task Manager, click the Performance tab, and select the Memory label. Notice the Paged Pool value climbing. You can also check this with Process Explorer (select the View menu, choose System Information, and click the Memory tab).
- 6. To determine which pool is leaking, run Pool and press the B key to sort by number of bytes.
- 7. Press P twice so that Pool shows only paged pool. Notice the Leak tag climbing to the top of the list.
- 8. Click the Stop Paged button so that you don't exhausted pool.
- 9. Using the technique described in the previous section, run Strings (from Sysinternals) to look for binaries that contain the Leak tag. This should display a match on Myfault.sys, confirming that the driver uses the Leak tag.

```
Strings %SystemRoot%\system32\drivers\*.sys | findstr Leak
```

# Look-aside lists

Windows provides a fast-allocation mechanism called look-aside lists. The basic difference between pools and look-aside lists is that while general pool allocations can vary in size, a look-aside list contains only fixed-sized blocks. Although the general pools are more flexible in what they supply, look-aside lists are faster because they don't use spinlocks.

Executive components and device drivers create look-aside lists that match the size of frequently allocated data structures by using ExInitializePagedList (for non-paged allocations) and ExInitializePagedList (for paged allocations functions). To minimize the overhead of multiprocessor synchronization, several executive subsystems create separate look-aside lists for each processor for their frequently accessed data. The executive also creates a general per-processor and non-paged look-aside list for small allocations (256 bytes or less).

If a look-aside list is empty (as it is when first created), the system must allocate from the pool or non-paged pool. If it contains a free block, the cache can be satisfied very quickly. The list grows as blocks are returned to it. The pool-allocation routines tune the number of free blocks aside how often a device driver or executive subsystem allocates from the list. The more frequent the allocations, the more are stored on a list. Lookaside lists are automatically reduced if they aren't being allocated from (This check happens once per second when the manager thread wakes up and calls ExAdjustListFunction).
