## Native images

Some images (executables) do not link to any subsystem. In other words, they don't link against a set of subsystem DLLs, as Kernel32.dll for the Windows subsystem. Instead, they link to Ntdll.dll, which is the lowest common denominator that spans subsystems. Because the native API exposed by Ntdll.dll is mostly documented, these kind of images are typically built only by Microsoft. One is the Session Manager process (Smss.exe, described in more detail later in this chapter). Smss.exe is the first user-mode process created (by the kernel), so it cannot be dependent on the Windows subsystem Csrss.exe (the Windows subsystem process) has not started. In fact, Smss.exe is responsible for launching Csrss.exe. another example is the Autoch utility which sometimes runs at startup to check disks. Because it relatively early in the boot process (launched by Smss.exe, in fact), it cannot depend on any subsystem.

## Executive

The Windows is the upper layer of Ntoskrnl.exe (The kernel is the lower layer). The executive includes the following types of functions:

- *Functions that are exported and called from user mode*: These functions are called system services and are exported via Ntdll.dll (such as NtCreateFile from the previous experiment). Most of the services are accessible through the Windows API or the APIs of any environment subsystem. A few services, however, aren't available through any documented subsystem function (Examples include ALPC and various query functions such as NtQueryInformationProcess, specialized functions such as NtCreateOpenFile, and so on).

- *Device driver functions that are called through the DeviceControl function*: This provides a general interface from user mode to kernel mode to call functions in device drivers that are not associated with a read or write. The driver used for Process Explorer and Process Monitor are good examples of that.

- *Functions that can be called from kernel mode that are exported and documented in the WDK*: include the functions that called by the boot driver, which start with Dev.

- *Functions that are internal to a module that are not exported*: These functions are used exclusively by the executive.

- *Functions defined as global symbols are not exported*: include internal support functions within Ntoskrnl.dll, as those that start with Io (internal memory/O or) (internal memory functions).

The executive contains the following major components, each of which is covered in detail in a subsequent chapter:

- *Configuration manager*: The configuration manager, explained in Chapter 9 Part 2, is responsible for implementing and managing the system registry.

- *Process manager*: The process manager, explained in Chapter 3 and Chapter 4, creates and terminates threads. The underlying support for processes and threads is implemented in the Windows kernel; the executive adds additional semantics and functions to these lower-level objects.

- *Security Resource Monitor (SRM)*: The SRM, described in Chapter 7, enforces security policies on the local computer. It guards OS resources, performing runtime-object protection and auditing.

- *I/O manager*: The I/O manager, discussed in Chapter 6, implements device-independent I/O and is responsible for dispatching to the appropriate device drivers for further processing.

- *Plug and Play (PnP) manager*: The PnP manager, covered in Chapter 6, determines which drivers are required to support a particular device and loads those drivers. It retrieves the hardware resources for each device, the PnP manager assigns the appropriate hardware resources as I/O ports, IRQs, DMAs, and memory locations. It is also responsible for sending proper notification for device changes (the addition or removal of a device) on the system.

- *Power manager*: The power manager (explained in Chapter 6), processor power management (PPM), and power management framework (PoFx) coordinate power management I/O notifications to device drivers.
