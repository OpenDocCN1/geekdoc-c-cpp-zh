
What does Windows do to address this situation? An ideal solution (at least in theory) would be to track locks and owners and boost the appropriate threads that forward progress can be made. This idea is implemented with a feature called Autoboost, described later in this chapter in the section "Autoboost." However, for general starvation scenarios, this mitigation is used.

You saw how the code for exclusive resources manages this scenario by boosting the owner threads so that they have a chance to run and release the resource. However, exclusive resources are only one of the many synchronization constructs available to developers, and the boosting technique will not apply to any primitive. Therefore, Windows includes a generic CPU starvation-relief mechanism as part of a thread called the balance-set manager (This is a system that exists to perform primary memory-management functions and is described in more detail in Chapter 5.) Once per second, this thread scans the ready queues for any threads that have been in the ready state (that is, haven't run) for approximately 4 seconds. If it finds such a thread, the balance-set manager boosts the thread's priority to 15 and sets the quantum target to an equivalent CPU clock cycle count of 3 quantum units. After the quantum, the thread's priority decays immediately to its original baseline priority. If the thread wasn't finished and a higher-priority thread is ready to run, the decayed thread returns to the ready queue, where it becomes again eligible for any boost after another 4 seconds.

The balance-set manager doesn't actually scan all the ready threads every it runs. To minimize the CPU time it uses, it scans 16 ready threads. If there are more threads at priority level, it remembers where it left off and picks up again on the next pass. Also, it boosts 10 threads per pass. If it finds more than 10 threads meriting this particular boost (which indicates an unusually busy system), it stops the scan and picks up again on the next pass.

> Note: As mentioned, scheduling decisions in Windows are not affected by the number of threads and are made in constant time. Because the balance-set manager must scan ready queues constantly, this operation depends on the number of threads on the system; more threads require more scanning time. However, the balance-set manager is not considered part of the scheduler or its algorithms and is simply an extended mechanism to increase reliability. Additionally, because of the cap on threads and queues to scan, the performance impact is minimized and predictable in a worst-case scenario.

# Applying boosts

Back in KiEditDispatcher, you saw that KiThreadWait is called to process threads in the deferred list. It is here that boost information passed by the caller is processed. This is done by looping through DeferredReady, unlinking its wait blocks (only Active blocks are unlinked), and setting two key values in the kernel's control block: Reason and AdjustIncrement. The reason is one of the possibilities seen earlier, and the increment completes the boost. This makes the thread ready for execution by running two algorithms: the quantum selection algorithm and processor selection algorithm (which is shown later in this chapter).

Let's first look at when the algorithm applies boosts, which happens only in cases when a thread is not real-time priority. For AdjustWait boost, it will be applied only if the thread is not experiencing a boost and the clock interrupt did not fire. Another situation that can disable boosting is if the kernel has realized that the thread has actually exhausted its quantum but the wait lasted less than two ticks.

If these situations are not true, the new priority of the thread will be computed by adding the AdjustIncrement to its base priority. Additionally, if the thread is known to be part of the foreground (meaning the priority is set to MEMORY_PRIORITY_FOREGROUND), this is where the priority-separation boost (PsSeparation) is applied by adding its value to the new priority. This is also known as the foreground boost.

Finally, the kernel checks whether this newly computed priority is higher than the current priority of the thread, and limits this to an upper bound of 15 to avoid crossing into the real-time range. It then sets this value as the new priority. If any separation boost was applied, it sets this value in the ForegroundBoost of KTHREAD, which results in a PriorityDecrement equal to the boost.

For AdjustBoost, the kernel checks whether the thread's priority is lower than the current priority and below 13. If so, and boosts are not disabled for the thread, the AdjustIncrement is used as the new priority, limited to a maximum of 13. Meanwhile, the UnusualBoost of KTHREAD contains the boost value, which results in a PriorityDecrement equal to the boost.

In all cases where PriorityDecrement is present, the value of the thread is also reconstructed to be the equivalent of one tick based on KiLockTarget. This ensures that foreground and unusual boosts will be lost after one tick instead of two, as will be shown in the next section. This also happens when an AdjustBoost is requested by the thread that is running at priority 13 or 14 without boosts.

After this work is complete, AdjustReason is now set to AdjustNone.

# Removing boosts

Removing boosts is done in KiDeferredReady as quantum recomputations are applied (as shown in the previous section). The algorithm first begins by checking the type of adjustment being done.

For AdjustNone scenario, which means the thread became ready due to preemption, the thread's quantum will be recomputed if it already hit its target but the clock interrupt has not noticed, as long as the thread was running at a dynamic priority level. Additionally, the thread's priority will be recomputed.

For AdjustWait or AdjustBoost scenario on a non-real-time thread, the kernel checks whether the thread exhausted its quantum (as in the prior section). If so, or the thread was running with a base priority of 14 or higher, or no PriorityDecrement is present and the thread has completed a wait longer than two cycles, the quantum of the thread is recomputed, as is its priority.

Priority recomputation happens on non-real-time threads. It is done by taking the thread's current priority, subtracting its foreground boost, subtracting its unusual boost (the combination of these last two items is the PriorityDecrement), and finally subtracting 1. This new priority is bounded with the base priority as the lowest bound and any existing priority decrement is zeroed out (clearing unused and foreground boosts). This means that in the case of a lock-ownership boost or any of the unusual boosts explained, the entire boost value is lost. On the other hand, for a regular AdjustWait boost, the priority naturally trickles down by 1 due to the subtraction by 1. This lowering eventually stops when the boost is hit due to the lower bound.

There is another instance where boosts must be removed, which goes through the KiRemoveBoost function. This is a special-case boost removal that occurs due to the lock-ownership boost rule, which specifies that the setting thread must lose its boost when donating its current priority to the waking thread (also used to undo the deferred procedure calls (DPCs) as well as the boost due to targeted starvation). The only special detail about this routine is when computing the new priority, it takes special care to separate the ForegroundBoost and UnusualBoost components of the PriorityDecrement to maintain any GUI foreground-separation boost that the thread accumulated. This behavior, appearing starting with Windows 7, ensures that threads relying on the lock-ownership boost do not behave erratically when running in the foreground, or vice-versa.
