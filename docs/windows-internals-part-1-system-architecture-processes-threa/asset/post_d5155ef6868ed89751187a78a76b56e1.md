
- A callback whenever a fault during a probe and lock operation on a memory descriptor list (MDL) occurs inside a Pico thread

- A callback whenever a caller is requesting the name of a Pico process

- A callback whenever Event Tracing for Windows (ETW) is requesting the user-mode stack trace of a Pico process

- A callback whenever an application attempts to open a handle to a Pico process or Pico thread

- A callback whenever someone requests the termination of a Pico process

- A callback whenever a Pico thread or Pico process terminates unexpectedly

Additionally, a Pico provider leverages Kernel Patch Protection (KPP), described in Chapter 7, to protect its callbacks and system calls as well as prevent fraudulent or malicious Pico providers from registering on top of a legitimate Pico provider.

It now becomes clear that with such unparalleled access to any possible user-kernel transition or vis-kernel interactions between a Pico process/thread and the world, it can be fully encapsulated by a Pico provider (and relevant user-mode libraries) to wrap a completely kernel implementation that of Windows (with some exceptions, of course, as scheduling rules and memory management rules, such as commit, still apply). Correctly written applications are not supposed to be sensitive to internal algorithms, as they are subject to change even within the operating system normally.

Therefore, Pico providers are essentially custom-written kernel modules that implement the necessary callbacks to respond to the list of possible events (shown earlier) that a Pico process can cause to arise. This is how WSL is capable of running unmodified Linux binaries in user-mode, limited only by the completeness of its system call emulation and related functionality.

## Trustlets (secure processes)

As covered in Chapter 2, Windows contains new virtualization-based VBS features such as Device Guard and Credential Guard, which enhance the safety of the operating system and user data by leveraging the hypervisor. We saw how one feature, Credential Guard (which is discussed in length in Chapter 7), runs in new isolated User Mode environment, while still unprivileged (ring 3), has a virtual trust level of 1 (VTL 1), granting it protection from the regular VTL 0 in which both the NT kernel (ring 0) and applications (ring 3) live. Let's investigate how the kernel sets up such processes for execution, and the various data structures processes use.

## Trustlet structure

To begin with, although Trustlets are regular Windows Portable Executables (PE) files, they contain IUM-specific properties:

- They can import only from a limited set of Windows DLLs (C/C++ Runtime, KernelBase, Advapi, Rpc Runtime, CNG Base Crypto, and NTDLL) all calls that are available to Trustlets. Note that mathematical DLLs operate only on the restricted number of system structures (such as NTFS, ASN.1) are also used, as they don't perform any system calls.
- They can import from an IUM-specific system DLL that is made available to them, called Iabase, which provides the Base IUM System API, containing support for slots, store boxes, cryptography, and more. This library ends up calling into lumdll.dll, which is the VTL 1 version of Ntdll.dll, and contains secure system calls (system calls that are implemented by the Secure Kernel, and not passed to the Normal VTL 0).
- They contain a PE section named .Policy with an exported global variable s_PolicyMetadata. This serves as metadata for the Secure Kernel to implement policy settings around permitting VTL 0 access to the Trustlet (such as debugging, crash dump support, etc.).
- They are signed with a certificate that contains the Isolated User Mode EKU (1.3.6.1.4.311.10.3.37). Figure 3-9 shows the certificate data for Lalse.exe, showing its IUM EKU.

Additionally, Trustlets must be launched using a specific process attribute when using CreateProcess—both to request their execution in IUM as well as to specify launch properties. We will describe the policy metadata and the process attributes in the following sections.

## Trustlet policy metadata

The policy metadata includes various options for configuring how "accessible" the Trustlet will be from VTL 0. It is described by a structure at the s_IumPolicyMetadata export mentioned earlier, and contains a version number (currently set to 1) as well as the Trustlet ID, which is a unique number that identifies this specific Trustlet among the ones that are known to (for example, Bios.exe is Trustlet ID 4). Finally, the metadata has an array of policy options. Currently, the options listed in Table 3-4 are supported. It should be obvious that as policies are part of the signed executable data, attempting to modify them would invalidate the IUM signature and prohibit execution.
