MMSS' functionality does not stop at priority boosting; because of the nature of network drivers on Windows and the NDIS stack, DPCs are quite common mechanisms for delaying work after an interrupt has been received from the network card. Because DPCs run at an IRQL level higher than user-mode code (see Chapter 6 for more information on DPCs and IRQLs), long-running network card driver can still interrupt playback—example, during network transfers or when playing a game.

MMSS sends a special command to the network stack, to throttle network packets during the duration of the media playback. This throttling is designed to maximize playback performance—at the cost of some small loss in network throughput (which would not be noticeable for network operations usually performed during playback, as playing an online game). The exact mechanisms behind it do not belong to any area of the scheduler, we will leave them out of this mechanism.

MMSS also supports a feature called deadline scheduling. The idea is that an audio-program does not need the highest priority in its category. If a program uses buffering (obtaining audio data from disk or network) and then plays the buffer while building the next buffer, deadline scheduling allows a client to indicate when it must get the highest priority to avoid glitches, but with a slightly lower priority (within its category) in the meantime. A thread can use the AvTaskYield to indicate the time it must be run, specifying the time it needs to get the highest priority within its category. Until that time, it gets the lowest priority within its category, potentially freeing CPU time for the system.

# Autobost

Autobost is a framework targeted at the priority-inversion problem described in the previous section. The idea is to track lock owners and lock waiters in such a way that would boost the appropriate threads' priorities (I/O priority as needed) to allow threads to make forward progress. The lock information is stored in a static array of KLOCK_ENTRY objects inside the KTHREAD structure. The current implementation uses a maximum of six entries. Each KLOCK_ENTRY contains two binary trees: one for locks owned by the thread and the other for locks waited on the thread. These trees are keyed by priority so constant time is required to determine the highest priority which should be applied. If boosted, the owner's priority is set to the waiter's. It also boost I/O priority if these were used with low priority. (See Chapter 6 for I/O priority.) As all priority boosts, the maximum priority achievable by Autobost is 15. (The priority of real-time threads is never boosted.)

Current implementation uses the Autobost framework for pushlocks and guarded synchronization primitives, which are exposed to kernel code (See Chapter 8 in Part 2 for more on these objects). The framework is also used by some executive components for specialized cases. Future versions of Windows may implement Autobost for user-mode objects that have an owner-ship concept, such as critical sections.
