Scenarios are hardcoded, and SuperFetch manages them through the NtSetSystemInformation and NtQuerySystemInformation APIs that For SuperFetch pulls, a special information class, SystemSuperFetchInformation, is used to control the kernel-mode components and generate requests such as starting, ending, and querying a scenario or associating one or more traces with a scenario.

# Page priority and rebalancing

You've already seen that the memory manager implements a system of page priorities to define which standby pages will be repurposed for a given operation and in list a given page will be inserted. This mechanism provides benefits when processes and threads have associated priorities—for example, ensuring that a defragmenter process doesn't pollute the standby page list and/or pages from an interactive foreground process. But its real power is unleashed without SuperFetch's page-prioritization schemes and rebalancing, which don't require manual application input or hardcoded knowledge of process importance.

SuperFetch assigns page priority on an internal score it keeps for each page, part of which is based on frequency-based usage. This usage counts how many times a page was used in given time intervals, such as hour, day, or week. The system also keeps track of time of use, recording how long it's been since a page comes from access. Finally, such data from where this page comes from (which list) and other access patterns are used to compute this score.

The score is translated into a priority number, which can be from 1 to 6. (A priority 7 is used for another purpose, described later.) Going down each level, the lower standby page priorities are repurposed first, as shown in the "Prioritized standby lists". Priority 5 is typically used for normal applications, while priority 1 means for background applications that third-party developers can mark as such. Finally, priority 6 is used to keep a number of high-importance pages as far away from repurposing. The other priorities are a result of the score associated with each page.

Because SuperFetch "learns" a user's system, it can start from scratch with no historical data and slowly build an understanding of the difference pages accessed by the user. This would result in a significant learning curve whenever a new application, or service pack was installed. By using an internal tool, Windows can pre-train SuperFetch to capture SuperFetch data and turn it into prebuilt traces. These prebuilt traces contain access and patterns that all users will probably encounter, such as clicking the Start menu, opening Control Panel, or using the File/Save dialog box. This data was saved to history files (which ship as Sysmain.dll) and is used to prepare the special priority 7 list. This list is the most critical data and is rarely repurposed.
