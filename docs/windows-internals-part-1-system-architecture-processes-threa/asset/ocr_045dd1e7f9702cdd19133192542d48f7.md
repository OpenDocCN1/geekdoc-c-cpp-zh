The routine that does most of the work in setting the address space is MmInitializeProcess-AddressSpace. It also supports cloning an address space from another process. This capability will be useful at the time to implement the POSIX fork system call. It may also be leveraged in the future to support Unix-style fork (which is how fork is implemented in Windows Subsystem for Linux in Redstone 1). The following steps do not describe the address space functionality, but focus on normal process address initialization.

+   1. The virtual memory manager sets the value of the process's last trim to the current time. The working manager (runs in the context of the balance set manager thread) uses this value to determine when to initiate set trimming.

+   2. The memory manager initializes the process's working set list. Page faults can now be taken.

+   3. The section (created when the image file was opened) is now mapped into the new process's address space, and the process section base is set to the base address of the image.

+   4. The Process Environment Block (PEB) is created and initialized (see the section stage 3E).

+   5. Ntdll.dll is mapped into the process. If this is a Wow64 process, the 32-bit Ntdll.dll is also mapped.

+   6. A new session, if requested, is created for the process. This special step is simply implemented for the benefit of the Session Manager (Smss) when initializing a new session.

+   7. The standard handles are duplicated and the new values are written in the process structure.

+   8. Any memory reservations listed in the attribute list are now processed. Additionally, two flags allow the bulk reservation of the first 1 or 16 MB of the address space. These flags are used internally for mapping, real-mode vectors and ROM code (which must be in the low ranges of virtual address space, where normally the heap or other process structures could be located).

+   9. The user process parameters are written into the process, copied, and fixed up (that is, they are converted from absolute form to a relative form that a single memory block is needed).

+   10. The affinity information is written into the PEP.

+   11. The MinWin API redirection is mapped into the process and its pointer is stored in the PEP.

+   12. The process unique ID is now determined and stored. The kernel does not distinguish between unique process and thread IDs. The process and thread IDs (handles) are stored in a global handle table (PspCidTable) that is not associated with any process.

+   13. If the process is secure (that is, it runs in IUM), the secure process is initialized and associated with the kernel process object.
