
First, we can leverage the fact that compilers ought to generate x64 function code on 16-byte boundaries. This reduces the size to the required array to 8 TB *. But using an entire BOOL (which is 4 bytes in the worst case or 1 byte in the best) is extremely wasteful. We only need one single, valid or invalid, which only needs to use 1 bit. This makes the calculation 8 TB / 8, or simply 1 TB. Unfortunate, however, there's a snag. There's no guarantee that the compiler will generate all functions on a 16-byte binary. Hand-crafted assembly code and certain optimizations might violate this rule. As such, we'll have to figure out a solution. One possible option is to use another bit to indicate if the function begins *somewhere* on the next 15 bytes instead of on the 16-byte boundary. Thus, we have the following possibilities:

- (0,0) No valid function begins inside this 16-byte boundary.
- (1,0) A valid function begins exactly on this aligned 16-byte address.
- (1,1) A valid function begins somewhere inside this 16-byte address.

Thanks to this setup, the attacker attempts to call a function that was marked as 16-byte aligned by the linker, the 2-bit state will be (1, 0), while the required bits (that is, bits 3 and 4) in the address will be (1, 1) as the address won't be 16-aligned. Therefore, an attacker will only be able to call an arbitrary instruction in the first 16 bytes of the function if the linker did not generate the function aligned in the first place (bits would then be (1, 1), as shown above). Even, this instruction must somehow be useful to the attacker without crashing the function (typically some sort of pivot or gadget that ends in a ret instruction)

With this understanding in mind, we can apply the following formulas to compute the size of the CFG bitmap:

- 32-bit application on x86 or x64: 2 GB / 16 * 2 = 32 MB
- 32-bit application with /LARGEADDRESSWARE, booted in 3 GB mode on x86: 3 GB / 2 = 48 MB
- 64-bit application: 128 TB / 16 * 2 = 2 TB
- 32-bit application with /LARGEADDRESSWARE, on x64: 4 GB / 16 * 2 = 64 MB, plus the size of the 64-bit bitmap, which is needed to protect 64-bit Ntdll.dll and Wo64 components: 2 TB + 64MB

Allocating and filling out 2 TB of bits on every single process execution is a tough performance overhead to swallow. Even though we have the fixed cost of the indirect call itself, process startup cannot be allowed to take so long, and 2 TB of committed memory would exhaust the commit limit instantly. Therefore, two memory-saving and performance-helping tricks are used.

First, the memory manager will only reserve the bitmap, basing itself on the assumption that the CFG validation function will treat an exception during CFG bitmap as an indication that the bit state is (0,0). As long as the region contains 4 KB of bit states that are all (0,0), it can be reserved, and only with pages that have at least one bit (1, X) need to be committed.

Next, as the ASLR section of Chapter 5, "Memory management," the system performs the randomization/relocation of libraries typically once at boot, as a performance-saving measure to avoid repeated relocations. As such, a library that supports ASLR has loaded once at a given address, it will always be loaded at that same address. This also means that the relevant bitmap sets have been calculated for the functions in that library, which will be identical in all other processes that load the same binary. As such, the memory manager treats the CFG bitmap as a region of pagefile-backed shareable memory, and the physical pages that correspond to the shared bits only exist in RAM once.

This reduces the cost of the committed pages in RAM and that only the bits corresponding to private copy-on-write memory. In regular applications, private memory is not executable unless someone has patched a library (which will not happen at image load), so the cost of loading an application, if it shares libraries with as previously launched applications, is met. ## CFG bitmap construction

Upon system initialization, the MiInitializeCfg function is called to initialize support for CFG. The function creates one or two objects (MmCreateSection) as reserved memory with size appropriate for the platform, as shown. For 32-bit platforms, one bitmap is enough. For x64 platforms, two bitmaps are required—one for 64-bit processes and the other for Wow64 processes (32-bit applications). The section pointers are stored in global variables.

After a process is created, the appropriate section is mapped into the process address space. This means that the section cannot be unmapped by code within the process or have its protection changed. The user mode CFG bitmap(s) are populated in the following scenarios:

- During image mapping, images that have been relocated due to ASLR (see Chapter 5) will have their indirect call metadata extracted. An image does not have indirect call metadata, meaning it was not compiled with CFG, it is assumed that every address within the image can be directly called. Because dynamically relocated images are expected to load at the same address in every process, the memory manager uses the shared section to populate the CFG bitmap.
- During image mapping, special cases are needed for non-dynamically relocated images and images not mapped at their preferred base. For such images, the relevant pages of the CFG bitmap are private and populated using the CFG metadata from the image. For images whose CFG bits are present in the shared CFG bitmap, a check is made to ensure that all relevant CFG bitmap pages are still shared.
- When virtual memory is allocated or re-protected as executable, the relevant pages of the CFG bitmap are made private and initialized to all 1 by default. This is needed for cases such as just-in-time (JIT) compilation, where code is generated on the fly and executed (for example, .NET or Java).

## Strengthening CFG

Although CFG does an adequate job to prevent types of exploits that leverage indirect calls or jumps, it could be bypassed through the following ways:

- If a JIT engine allocates executable memory, the corresponding bits will be set to (1, 1), meaning that all memory is considered a valid call target.
- For 32-bit applications, the expected call target is __stdcall (calling convention), but an attacker can change the indirect call target to __cdecl (C calling convention); the stack will become corrupt as the C function will not perform cleanup of the caller's arguments. Because CFG cannot differentiate between different calling conventions, this results in a corrupt stack, potentially with an attacker-controlled return address, bypassing CFG mitigation.
- Similarly, compiler-generated jmp/longjmp calls behave differently from true indirect calls. CFG cannot differentiate between the two.
- Certain indirect calls are harder to protect, such as Import Address Table (IAT) or Delay-Load Address Table, which are typically in a read-only section of the executable.
- Exported functions may be desired.

Windows 10 introduces advancements to CFG that address all these issues. The first is to introduce a new flag to the VirtualAlloc function called PAGE_TARGETS_INVALID and one to VirtualProtect that allocate executable memory will not see their allocations set to the (1, 1) state. They must manually call the ProcessValidCallTargets function (which calls the SetInformationVirtualMemory function), which may allow them to specify the actual function targets of their JITed code. Additionally, this function is marked as a suppressed call with GUARD_SUPPRESS, making sure that attackers cannot use an indirect CALL or JMP to redirect into it, even its function (because it is an inherently dangerous function, calling it with a controlled stack or registers could result in the bypassing of CFG).

Next, CFG changes the default flow in the beginning of this section with a more refined flow. In this, the loader does not implement a simple "verify target, return" function, but rather a "verify target, call stack, check return" function, which is used in a subset of places on 32-bit applications (and/or running under WoW64). This improved flow is shown in Figure 7-32.

Next, CFG adds additional tables inside the executable, such as the Address Taken IAT table and the Long Jump Address table. When longjmp and IAT protection are enabled in the compiler, these tables are used to store addresses for these specific types of indirect calls, and the relevant functions are not placed in the regular function table, therefore not figuring in the bitmap. This means that if code is attempting to jump/call to one of these functions, it will be treated as an illegal transition. Instead, the Runtime and linker will validate the targets of, say, the longjmp function, by manually checking this. Although it is more efficient than a bitmap, there should be little to no in these tables, making the cost bearable.

Finally, improved CFG includes a feature called export suppression, which must be supported by the compiler and enabled by process-mitigation policy. With this feature enabled, a new bit is implemented (called listed has (0, 1) as an undefined state). This state indicates that the function is valid export-suppressed, and it will be treated differently by the loader.
