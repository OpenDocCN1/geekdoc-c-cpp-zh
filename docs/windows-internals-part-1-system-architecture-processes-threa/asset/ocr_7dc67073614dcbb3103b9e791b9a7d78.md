The prioritized list is loaded into memory (or prepopulated) by the rebalancer, but the actual act of rebalancing is handled by both SuperFetch and the memory manager. As shown, the prioritized standby list mechanism is internal to the memory manager, and decisions on which pages to throw out and which to protect are innate, based on the priority number. The rebalancer does not by manually rebalancing memory but by reprioritizing it, which causes the memory manager to perform the needed tasks. The rebalancer is also responsible for reading the actual pages from disk, if needed, so that they are present in memory (prefetching). It assigns the priority that is mapped by each agent, and the memory manager ensures that the page is treated according to its importance.

The rebalancer can take action relying on any other agents—for example, if it notices that the distribution of pages paging lists is suboptimal or the number of repurposed pages across different priority levels is detrimental. The rebalancer can also trigger-trimming, which might be required for creating an appropriate budget of pages that will be used for SuperFetch prepopulated cache data. The rebalancer will typically cache low-utility pages—such as those that are already marked as low priority, that are zeroed, or that have value content but not in any working set and have unused—and build a more useful set of pages in memory, given the budget it has allocated itself. After the rebalancer has decided which pages to bring into memory and at what priority level they need to be (as well as which pages can be thrown out), it performs the required disk reads to prefetch them. The memory consumption by prefetching is backed by standby pages. As described in the discussion of page dynamics, standby memory is available memory because it can be repurposed as free memory for any allocator at time. In other words, if SuperFetch is prefetching the wrong data, there is no real impact on the user because memory can be reused and doesn't consume resources.

Finally, the rebalancer also runs periodically to ensure that pages it has marked as high priority have actually been used recently. Because these pages will rarely (sometimes never) be repurposed, it is important not to waste them on data that is rarely accessed but may have appeared to be frequently accessed during a certain period. If such a situation is detected, the rebalancer runs again to push those pages down in the priority lists.

A special agent called the application launch agent is involved in a different kind of prefetching mechanism, which attempts to predict application launches and builds a Markov chain that describes the existence of other application launches within a time segment. These segment are divided across periods of time roughly 6 hours—morning, noon, evening, and night—by weekday or weekend. For example, if on Saturday and Sunday evening a user typically launches after launched Word, the application launch agent will likely prefetch Outlook based on the high probability of it running after Word during weekend evenings.
