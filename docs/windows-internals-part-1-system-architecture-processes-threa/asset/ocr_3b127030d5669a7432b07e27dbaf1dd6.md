At this point you may be wondering what prohibits a malicious process from claiming it is a protect-ed and shielding itself from anti-malware (AM) applications. Because the Windows Media DRM Certificate is no longer necessary to run as a protected process, Microsoft extended its Code Integrity module to understand two special enhanced key (EKU) OIDs for code signing certificate: 1.3.6.1.4.1.311.10.3.22 and 1.3.6.1.4.1.311.10.3.20. Once one of these EKUs is present, hardcoded Google and Issuer strings in the certificate, combined with additional possible EKUs, for example, the Microsoft Windows Issuer can grant the PsProtectedWindows protected signer value, but only if the EKU for Windows System Component Verification (1.3.6.1.4.1.311.10.3.6) is also present. As an example, Figure 3-7 shows the certificate for Smss.exe, which is permitted to run as WinTcb.

Finally, note that the protection level of a process also impacts how DLLs will be allowed to load—otherwise through a logic bug or simple file replacement or replacing, a legitimate-ed process could be coerced into loading a third party or malicious library, which would now execute with the same protection level as the process. This is checked by granting each process a "Signature Level," which is stored in the SignerLevel field of EPROCESS, and using an inter-nal lookup to find a corresponding "DLL Signature Level," stored in SectionSignatureLevel in EPROCESS. Any DLL loading in the process will be checked by the Code Integrity component in the same way that the main executable is verified. For example, a process with "WinTcb" as its executable signer will only load "Windows" or higher signed DLLs.
