The main drawback of UMDF is increased latency because of the kernel/user transitions and communication required (as described shortly). Also, some types of drivers, such as high-speed PCI devices, are simply not to execute in user mode and thus cannot be written with UMDF.

UMDF is designed specifically to support protocol device classes, which refers to drivers that use all the standardized, generic protocol and offer specialized functionality on top of it. These protocols currently include IEEE 1394 (FireWire), USB, Bluetooth, interface devices (HIDs) and TCP/IP. Any driver running on top of these (or connected to a network) is a potential candidate for UMDF. Examples include portable music players, input devices, cell phones, cameras and webcams, and on other types of UMDF are SideShow-composite devices (auxiliary displays) and the Windows Portable Device (WPD) Framework, which supports USB-removable storage bus transfers. Finally, with KMDF, it's possible to implement software-only drivers, such as a virtual device, in UMDF.

Unlike KMDF, which run as driver objects representing a SYS image file, UMDF drivers run in a driver host process (running the %SystemRoot%System32\UMDFHost.exe), similar to a service-hosting process. The host process connects the driver itself, the User-Mode Driver Framework (implemented as DLL), and a run-time environment (for I/O dispatching, driver loading, device-stack management, communication with the kernel, and a thread).

As in the kernel, each UMDF driver runs as part of a stack. This can contain multiple drivers that are responsible for managing a device. Naturally, because user-mode cannot access the kernel address space, UMDF includes components that allow this access to occur through a specialized interface to the kernel. This is implemented by a kernel-mode side of UMDF that uses an efficient inter-process communication mechanism to talk to the run-time environment in the user-mode driver host processes.(See Chapter 8 in Part 2 for more information on ALPC.)
