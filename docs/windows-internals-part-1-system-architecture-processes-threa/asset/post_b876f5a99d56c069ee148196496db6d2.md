
For each of these objects, KMDF objects can be attached. Some objects have only one or two valid parents, others can be attached to any parent. For example, a WDFINTERRUPT object must be associated with a WDFDEVICE, but a WDFSPLOCK or WDFSTRING object can have any object as a parent. This allows for fine-grained control over their validity and the reduction of global state variables. Figure 6-44 shows the entire KMDF object hierarchy.

![](img/ff0e6a9d867a3a6e9527eb1d946810fc_599_0.png)

**Figure 6-44** KMDF object hierarchy.

The associations mentioned earlier and shown in Figure 6-44 are not necessarily immediate. The parent must simply be on the hierarchy chain, meaning any of an ancestor nodes must be of this type. This relationship is useful to implement because object hierarchies affect not only the object's locality but also its lifetime. Each time a child object is created, a reference count is added to it by its link to its parent. Therefore, when a parent object is destroyed, all the child objects are also destroyed, which is why objects such as WDFSTRING or WDFMEMORY with a given object instead of the WDFDRIVER object can automatically free up memory and state information when the parent object is destroyed.

Closely related to the concept of hierarchy is KMDF's notion of object context. Because KMDF objects are opaque (as discussed) and are associated with a parent object for locality, it becomes important to allow drivers to attach their own data to an object in order to track specific information outside the framework's capabilities or support. Object context allows all KMDF objects, which permit multiple layers of code inside the same driver to in different ways. In WDM, the device extension custom data structure allows such information to be associated with a given device, but with KMDF a spinlock or string can contain context areas. This extensibility allows each library or layer of code responsible for processing an I/O request independently of other code, based on the context that it works with.

Finally, KMDF objects are also associated with a set of attributes, shown in Table 6-12. These attributes are usually configured to their default, but the values can be overridden by the driver when creating the object by specifying a WDF_OBJECT_ATTRIBUTES structure (similar to the object manager’s OBJECT_ATTRIBUTES structure that was used when creating a kernel object).

## KMDF I/O model

The KMDF I/O model follows the WDM mechanisms discussed earlier in this chapter. In fact, you can even think of the framework as a WDM driver, since it uses kernel APIs and WDM to abstract KMDF and make it functional. Under KMDF, the framework driver sets its own WDM-style dispatch routines and takes control of all IRPs sent to the driver. After being handled by one of KMDF I/O handlers (described shortly), it packages these requests in the appropriate queues KMDF objects (if required), and performs driver callback if the driver is interested in these events. Figure 6-45 describes the flow of I/O in the framework.

![](img/ff0e6a9d867a3a6e9527eb1d946810fc_601_0.png)

FIGURE 6-45 KMDF I/O flow and IRP processing.

Based on the IRP discussed previously for WDM drivers, KMDF performs one of the following three actions:

- It sends the IRP to the I/O handler, which processes standard device operations.
- It sends the IRP to the PnP and power handler that processes these kinds of events and notifies other drivers if the state has changed.
- It sends the IRP to the WMI handler, which handles tracing and logging.

These components notify the driver of any events it registered for, potentially forward the request to another handler for further processing, and then complete the request based on an internal handler action or as the result of a driver call. If KMDF has finished processing the IRP but the request itself has not been fully processed, KMDF will take one of the following actions:

- For bus and driver functions, it completes the IRP with STATUS_INVALID_DEVICE_REQUEST.
- For filter drivers, it forwards the request to the next lower driver.

I/O processing by KMDF is based on the mechanism of queues (WDFQUEUE, not the queue object discussed in this chapter). KMDF queues are highly scalable containers of I/O requests (packed as WDFREQUEST objects) and provide a rich feature set beyond merely sorting I/Os for a given device. For example, queues track currently active requests and I/O cancellation, I/O concurrency (the ability to perform and complete more than one I/O request at a time), and I/O synchronization (as noted in the list of object attributes in Table 6-12). A typical KMDF driver creates at least one queue (if not more) and associates one or more queues with each event, as well as some of the following options:

- The callbacks registered with the events associated with this queue.

- The power management state for the queue. KMDF supports power-managed and non-managed queues. For the former, the I/O handler wakes up the device when required (and when possible), the idle timer when the device has no I/Os queued, and calls the driver's I/O cancellation routines when the system is switching away from a working state.

- The dispatch method for the queue. KMDF can deliver I/Os from a queue in sequential, parallel, or manual mode. Sequential I/Os are delivered one at a time (KMDF waits for the driver to complete the request), while parallel I/Os are delivered to the driver as soon as possible. In manual mode, the driver must manually retrieve I/Os from the queue.

- Whether the queue can accept zero-length buffers, such as incoming requests that don't contain any data.

> Note The dispatch method only affects the number of requests that can be active. It does not determine whether the event callbacks will be called concurrently or serially. That behavior is determined through synchronization object.

By the mechanism of queues, the KMDF driver handler upon receiving a create, close, write, read, or device control (IOCTL) request:

- For create requests, the driver can be immediately notified through EvtFileCreate event, or it can create a non-manual queue to receive requests. Finally, if none of these methods are used, KMDF will simply complete the request with a success code.

- For cleanup and close requests, the driver will be immediately notified through EvtFileCleanup and EvtFileClose callbacks, if registered. Otherwise, the framework will simply complete with a success code.

- For write, read, and IOCTL requests, the flow shown in 6-46 applies.

## User-Mode Driver Framework

Windows provides a growing number of drivers that run in user mode, using the User-Mode Driver Framework (UMDF). UMDF version 2 is aligned with KMDF in terms of object, programming model and I/O model. The frameworks are not identical, however, because of the inherent differences between user mode and kernel mode. For example, some KMDF objects listed in Table 6-12 don't exist in UMDF, WDFCHILDLIST, DMA-related objects, WDFLOOKASIDELIST (look-aside lists can be allocated only in kernel mode), WDFORESLIST, WDFIOREQLIST, WDFDPC, and WMI objects. Still, most KMDF objects and concepts apply equally to UMDF 2.x.

UMDF provides several advantages over KMDF:

- UMDF drivers execute in user mode, so any unhandled exception crashes the UMDF host process, not the entire system.
- The UMDF host process runs with the Local Service account, which has limited privileges on the local machine and only anonymous access in network connections. This reduces the security attack surface.
- Running in user mode means the IRQL is always 0 (PASSIVE_LEVEL). Thus, the driver can take page faults and use kernel dispatcher objects for synchronization (events, mutex, and so on).
- Debugging UMDF drivers is easier than debugging KMDF drivers because the debugging setup does not require two separate machines (virtual or physical).
