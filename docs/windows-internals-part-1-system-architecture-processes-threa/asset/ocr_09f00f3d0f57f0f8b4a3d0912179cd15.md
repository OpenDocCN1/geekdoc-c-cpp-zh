When the scheduler needs to refer to a processor in the extended affinity masks, it first de-references the correct bitmask by its group number and accesses the resulting affinity directly. In the kernel API, extended affinity masks are not exposed; instead, the caller of the API inputs the group number as a parameter and receives the legacy affinity mask for that group. In the Windows API, on the other hand, only information about a single group is usually queried, which is the group of the currently running thread (which is fixed).

The extended affinity mask and its underlying functionality are also how a process can escape the boundaries of its original assigned processor group. Using the extended affinity APIs, a process can choose affinity masks on other processor groups. For example, if a process has four threads and the machine has 256 processors, thread 1 can run on processor 4, thread 2 can run on processor 68, thread 3 on processor 132, and thread 4 on processor 196, if each thread sets an affinity mask of 0x10 (01000 in binary) on group 0, 1, 2, and 3. Alternatively, the threads can set an affinity of all 1 bits (0xFFFF...) for their group, and the process can then execute its threads on any available processor on the system (with the limitation that each is restricted to running within its own group).

You take advantage of extended affinity at creation time by specifying a group number in the thread attribute list (PROC_THREAD_ATTRIBUTE_GROUP_AFFINITY) when creating a new thread or by setting ThreadGroupAffinity on an existing thread.

# System affinity mask

Windows drivers usually execute in the context of the calling thread or an arbitrary thread (that is, not in the safe confines of the System process). Therefore, currently running driver code might be subject to affinity rules set by the application developer. These are not relevant to the driver code and might prevent correct processing of interrupts and queued work. Driver operators have a mechanism to temporarily bypass user thread affinity settings, by using KeSetSystemAffinityThread(Ex)/KeSetGroupAffinityThread and KeRevertToAffinityThread(Ex)/KeRevertToGroupAffinityThread APIs.

# Ideal and last processor

Each thread has CPU numbers stored in the kernel thread control block:

+   - **Ideal processor** This is the preferred processor that thread should run on.
- **Last processor** This is the processor that the thread ran on.
- **Next processor** This is the processor that the thread will be or is running on.

The ideal processor for a thread is chosen when a thread is created using a seed in the process control block. The seed is incremented each time a thread is created so that the ideal processor for each new thread rotates through the processors on the system. For example, the first thread in the first process is assigned an ideal processor of 0 and the second thread in process is assigned an ideal processor of 1. However, the next process in the system has its first thread's ideal processor set to 1, the second to 2, and so on. In that way, the threads within each process are spread across the processors.
