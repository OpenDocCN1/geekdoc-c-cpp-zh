

除了创建和销毁 IRP 之外，I/O 管理器提供了不同驱动程序通用的代码，驱动程序可以调用这些代码来执行它们的 I/O 处理。通过在 I/O 管理器中整合任务，单个驱动程序变得更加简单和紧凑。例如，I/O 管理器提供了一个允许一个驱动程序调用其他驱动程序的函数。它还管理 I/O 请求的缓冲区，并记录哪些可安装文件系统已加载到操作系统中。I/O 管理器大约有 100 种不同的例程可以被设备驱动程序调用。

I/O 管理器提供了灵活的 I/O 服务，允许环境子系统（如 Windows 和 POSIX，后者已不再支持）实现它们各自的 I/O 功能。这些服务包括对异步 I/O 的支持，允许开发者构建可扩展、高性能的应用程序。

驱动程序呈现的统一、模块化接口允许 I/O 管理器调用任何驱动程序，而无需对其其结构或内部细节有任何特殊了解。操作系统将所有 I/O 请求处理为指向文件；驱动程序将对虚拟文件提出的请求转换为特定硬件的请求。驱动程序可以相互调用（使用 I/O 管理器）以实现对 I/O 请求的分层、独立处理。

除了标准的打开、关闭、读、写函数外，Windows I/O 系统提供了若干高级功能，例如异步、直接、缓冲和分散/聚集 I/O，这些功能在本文章的“I/O 类型”节中进行了描述。

## 典型 I/O 处理

大多数 I/O 操作不涉及 I/O 系统的所有组件。一个典型的 I/O 请求始于应用程序执行与 I/O 相关的函数（例如从设备读取数据），该函数由 I/O 管理器、一个或多个驱动程序以及 HAL 进行处理。

如前所述，在 Windows 中，线程在虚拟文件上执行 I/O。虚拟文件指的是任何被视为文件的 I/O 源或目标（例如设备、目录、管道和邮件队列）。用户模式客户端调用 `CreateFile` 或 `CreateFile2` 函数来获取虚拟文件的句柄。该函数名称有点误导性——它不仅仅关乎文件，它在对象管理器中名为 `GLOBAL*` 的目录中被称为符号链接。`CreateFile*` 中的后缀 "File" 实际上意味着一个虚拟文件对象 (`FILE_OBJECT`)，它是内核执行这些函数结果后创建的实体。图 6-2 显示了 WinObjSymbols 工具针对 `GLOBAL` 的截图。

如图 6-2 所示，如 `C:` 之类的名称只是指向设备对象管理器下内部名称的符号链接（在此情况下为 `\Device\HarddiskVolume7`）。关于对象管理器和对象管理器命名空间的更多信息，请参见第二部分第 8 章“系统机制”。`GLOBAL*` 中的所有名称都是 `CreateFile2` 参数的候选。内核模式客户端（如设备工具）可以使用类似的 `ZwOpenFile` 来获取虚拟文件的句柄。

高级别的抽象（如 `GLOBAL`）拥有自己的用于处理文件和设备的 API（例如 .NET 中的 `System.IO.File` 类或 WinRT 中的 `Storage.File` 类），但它们最终会调用 `CreateFile()` 来获取它们隐藏在表层下的实际句柄。

`GLOBAL??` 对象管理器目录有时被称为 `DosDevices`，这是一个旧名称。`DosDevices` 仍然有效，因为它被定义为指向对象管理器命名空间根目录下 `GLOBAL??` 的符号链接。在驱动程序代码中，`??` 通常用于指代 `GLOBAL??` 目录。

操作系统将所有 I/O 请求视为对虚拟文件的操作，因为 I/O 管理器对文件一无所知，因此使得驱动程序的责任是将面向文件的命令（打开、关闭、读、写）转换为特定于设备的命令。这种抽象使得应用程序的设备接口变得通用化。用户模式应用程序调用记录的函数，这些函数反过来调用内部 I/O 系统函数来读取文件、写入文件并执行其他操作。I/O 管理器动态地将这些虚拟文件请求定向到相应的设备驱动程序。图 6-3 了一了典型 I/O 读流的基本结构。（其他类型的 I/O 请求，如写，也是类似的；它们只是使用不同的 API。）

## 中断请求级别和延迟过程调用

在继续之前，我们必须介绍 Windows 内核中两个非常重要的概念，它们在 I/O 系统中起着重要作用：中断请求级别 (IRQL) 和延迟过程调用 (DPC)。关于这些概念的讨论将在第二部分第 8 章进行，但本节将提供足够理解后续 I/O 处理的信息。

## 中断请求级别

IRQL 在某些情况下有两种不同的含义：

- 中断请求级别 (IRQL) 是分配给硬件中断源的优先级（由 HAL 与中断控制器设置）。
- 每个 CPU 有自己的 IRQL 值。它被认为是 CPU 的一个寄存器。

IRQL 的基本规则是，低 IRQL 代码无法干扰高 IRQL 代码，反之亦然——高 IRQL 代码可以抢占运行低 IRQL 的代码。你很快就会看到这种工作的示例。Windows 支持的架构的 IRQL 列表如图 6-4 所示。注意 IRQL 与线程优先级。

> 注意 IRQL 不等于中断请求 (IRQ)，中断控制器。请参见第二部分第 8 章获取更多关于中断、IRQ 和 IRQL 的信息。

通常，处理器的 IRQL 为 0。在这方面没有“特殊”情况发生，内核调度器根据优先级调度线程，如第 4 章“线程”所述。在用户模式下，IRQL 可以为 0。没有方法从用户模式提升 IRQL。（这就是为什么用户模式文档完全没有提到 IRQL 概念。）

内核模式代码可以使用 `KeRaiseIrql` 和 `KeLowerIrql` 函数来提升或降低当前 IRQL。然而，大多数函数是在 IRQL 提升到某些预期级别时调用的，正如我们稍后讨论驱动程序的典型 I/O 处理时将看到的。
