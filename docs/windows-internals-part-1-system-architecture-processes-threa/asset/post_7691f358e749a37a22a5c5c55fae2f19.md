# Windows subsystem

Although Windows was designed to support multiple independent environment subsystems, from a practical perspective, having each subsystem implement all the code to handle windowing and displaying I/O would result in a large amount of duplicate system functions that, ultimately, negatively affect both system size and performance. Because Windows was the primary subsystem, the designers decided to locate these basic functions there and have other subsystems call the Windows subsystem to perform I/O. Thus, the SUA subsystem calls services in the Windows subsystem to perform I/O.

As a result of this design decision, the Windows subsystem is a required component for any Windows system, even on server systems with no interactive users logged in. Because of this, the process is marked as a critical process (which means if it exits for any reason, the system crashes).

The Windows subsystem consists of the following major components:

- For each session, an instance of the environment subprocess process (Csrss.exe) loads four DLLs (Basesrv.dll, Winsrv.dll, Xssvr.dll, and Crsrv.dll) that contain support for the following:
  - housekeeping tasks related to creating and deleting processes and threads
  - Shutting down Windows applications (through the ExitWindows API)
  - Containing .ini file to registry location mappings for backward compatibility
  - Sending certain kernel notification messages (such as from the Plug-and-Play manager) to Windows applications as Window messages (WM_DEVICECHANGE)
  - Ports of the Side-by-Side (SxS)/Fusion and manifest cache support for 16-bit virtual DOS (VMD) processes (32-bit Windows OS)
  - Several natural language support functions, to provide caching

> Note Perhaps most critical, the kernel mode code that handles the raw input thread and desktop thread (responsible for the mouse cursor, keyboard input, and of the desktop window) is hosted inside threads running Winsrv.dll. Additionally, the Csrss.exe instances with interactive user sessions contain a fifth DLL called the Canonical Display Driver (Cdd.dll). CDD is responsible for communicating with the DirectX support in the kernel (the the upcoming discussion) on each vertical refresh (VSync) of the visible desktop state without traditional hardware-accelerated GPU.

- A kernel-mode device driver (Win32k.sys) that contains the following:
  - The window manager, which controls window displays; manages screen output; collects input from keyboard, mouse, and other devices; and passes user messages to applications
  - The Graphics Device Interface (GDI), which is a library of functions for graphics output devices and includes functions for line, text, figure drawing and graphics manipulation
  - Wrappers for DirectX support that is implemented in another kernel driver (Dxgkernel.sys)

- The console host process (Conhost.exe), which provides support for console (character cell) applications

- The Desktop Window Manager (Dwm.exe), which allows for compositing window rendering into a single surface through the CDD and DirectX

- Subsystem DLLs (as Kernel32.dll, Advapi32.dll, User32.dll, and Gdi32.dll) that translate documented Windows API functions into the appropriate and undocumented (for user-mode) kernel-mode service calls calls in Ntoskrnl.exe and Win32k.sys

- Graphics drivers for hardware-dependent graphics displays, printer drivers, and video miniport drivers

> Note As part of a refactoring effort in the Windows architecture called MinWin, the subsystem DLLs are now generally composed of specific libraries that implement API Sets, which are then linked together into the subsystem and resolved using a special redirection scheme. For more information on this refactoring, see the "Image loader" section in Chapter 3.

# Console window host

In the original Windows subsystem design, the subsystem process (Csrss.exe) was responsible for managing console windows. Starting with Windows 7, a separate process is used for each console window: the console host (Conhost.exe). (A single console window can be shared by multiple applications, as you launch a command). The details of the Windows 7 console host are explained in Chapter 2.

With Windows 8 and later, the console architecture changed again. Conhost.exe is now a child process, but is now spawned from the console-based process (rather than Csrss.exe) the console driver (Windows\System32\Drivers\ConDrv.sys). The process in question communicates with Conhost.exe using the console driver (ConDrv.sys), by sending write, I/O control and other I/O requests. Conhost.exe is designated as a server and the process using the console is the client. This client needs the for Csrss.exe to receive keyboard input (as part of the raw input), send it through Win32k.sys to Conhost.exe, and use LPC to send it to Cmd.exe.
