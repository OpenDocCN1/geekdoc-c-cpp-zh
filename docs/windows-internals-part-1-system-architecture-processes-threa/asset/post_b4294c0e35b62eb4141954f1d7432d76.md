## Heap manager

Most applications allocate smaller blocks than the 64-KB minimum allocation granularity possible using page-granularity functions such as VirtualAlloc. Allocating such a large area for relatively small allocations is not optimal from a memory usage and performance standpoint. To address this, Windows provides a component called the heap manager, which manages allocations inside memory areas reserved using the page-memory-allocation functions. The granularity in the heap manager is relatively small: 8 bytes on 32-bit systems, and 16 bytes on 64-bit systems. The heap manager has been designed to optimize memory usage and performance in the case of these smaller allocations.

The heap manager exists in two places: Ntdll.dll and Ntosnl.exe. The subsystem APIs (such as the Windows heap APIs) call the functions in Ntdll.dll, and various executive components and device drivers call the functions in Ntosnl.exe. Its native interfaces (prefixed with Rt) are available only for use within Windows components or kernel-mode drivers. The Windows API interfaces to the heap (prefixed with Heap) are forwards to the native functions in Ntdll.dll. In addition, legacy APIs (prefixed with either Local or Global) are provided to support older Windows applications. These also call the heap manager, using some of its specialized interfaces to support legacy behavior. The most common Windows heap functions are:

- HeapCreate or HeapDestroy: These create or delete, respectively, an initial request and size can be specified at creation.
- HeapAlloc: This allocates this block. It is forwarded to Rt1AllocateHeap in Ntdll.dll.
- HeapFree: This frees a block previously allocated with HeapAlloc.
- HeapReAlloc: This changes the size of an existing allocation, growing or shrinking an existing block. It is forwarded to Rt1ReAllocHeap in Ntdll.dll.
- HeapLock and HeapUnlock: These control mutual exclusion to heap operations.
- HeapWalk: Enumerates the entries and regions in a heap.

## Process heaps

Each process has at least one heap: the default heap. The default heap is created at process startup and is never deleted during the process's lifetime. It defaults to 1 MB in size, but you can make it bigger by specifying a starting size in the image file using the /HEAP linker flag. This is just the initial reserve, however, it will expand automatically as needed. You can also specify the commit size in the image file.

The default heap can be explicitly used by a program or implicitly used by some Windows internal functions. An application can query the default process heap by making a call to the Windows GetProcess-Heap function. Processes can also create additional private heaps with the HeapCreate function. When a process no longer needs a private heap, it can recover the virtual address space by calling HeapDestroy. An array with all heaps is maintained in each process, and a thread can query them with the Windows GetProcessHeaps function.

A Universal Windows Platform (UWP) app process includes three heaps:

- The default process heap created.
- A shared heap used to pass large arguments to the process's csrss instance. This is created by the CsrClientConnectToServerNtdll.dll function, which executes early in the process initialization by Ntdll.dll. The heap is available in the global variable CsrPortHeap (in Ntdll.dll).
- A heap created by the Microsoft C runtime. Its handler is stored in the global variable _crtheap (in the msvcrt module). This is the one used by the C/C++ memory-allocation functions as malloc, free, operator new, and delete.

A heap can manage allocations in either memory regions reserved from the memory manager via virtualAlloc or from memory-mapped file objects in the process address space. The latter approach is used in practice (and is not exposed by the Windows API), but it's suitable for scenarios where the content of the blocks needs to be shared between processes or between kernel-mode and a user-mode component. The Win32 GUI subsystem (Win32k.sys) uses a heap for sharing GDI and USER objects with user mode. If a heap is built on a memory-mapped file region, certain constraints apply with respect to the component that can call heap functions:

- The internal heap uses user pointers, and therefore do not allow remapping to different addresses in other processes.
- The synchronization across multiple processes or between a kernel component and a user-process support is not supported by the heap functions.
- In the case of a shared heap between user mode and kernel mode, the user-mode mapping should be read-only to prevent user-mode code from corrupting the heap's internal structures, which would result in a system crash. The kernel-mode driver is also responsible for not putting sensitive data in a shared heap to avoid leaking it to user mode.

## Heap types

Until Windows 10, the heap manager used one type, the NT heap. Windows 10 introduced a new type called the Low Fragmentation Heap (LFH). For large heaps, a significant percentage of allocations are handled by the LFH. The LFH avoids fragmentation by managing allocated blocks in predetermined-size buckets. When a process allocates memory from the heap, the LFH chooses the bucket that maps to the smallest block enough to hold the required size (the smallest is 8 bytes). The first bucket is used for allocations between 1 and 8 bytes, the second for allocations between 9 and 16 bytes, and so, until the 32nd bucket, which is used for allocations between 249 and 256 bytes, followed by the 33rd bucket, which is used for allocations between 255 and 272 bytes, and so on. Finally, the 128th bucket, which is the system, is used for allocations between 15,873 and 16,384 bytes (this is known as binary buddy system). If the allocation is larger than 16,384 bytes, the LFH forwards it to the underlying heap back end. Table 5-7 summarizes the different buckets, their granularity, and the range of sizes they map to.

| Buckets | Granularity | Range |
|--- | --- | --- |
| 1–32 | 8 | 1–256 |
| 33–48 | 16 | 257–512 |
| 49–64 | 32 | 513–1,024 |
| 65–80 | 64 | 1,025–2,048 |
| 81–96 | 128 | 2,049–4,096 |
