The I/O manager is the only entity that creates IRPs. The Plug and Play manager and the manager are also responsible for creating IRPs with major function code IRP_MJ_PNP and IRP_MJ_, respectively.

Figure 6-13 shows an device node with six layered devices: two filters, the FDO, and the PDO. This means an IRP that device is created with I/O stack locations—one for each. An IRP is always delivered to the highest layered device, even if a handle was opened to a named device that is lower in the device stack.

A driver that receives an IRP can do one of the following:

+   * Can complete the IRP then and calling IoCompleteRequest. This could be the IRP has some invalid parameters (for example, insufficient buffer size or bad I/O code), because the operation is quick and can be accomplished immediately, as getting some status from the device or reading a value from the registry. The driver calls IoGetIrpStackLocation to get a pointer to the stack location that it should refer to.

+   * Can forward the IRP to the next layer after doing some processing. For example, an upper filter can do some logging of the operation and send the IRP down to be executed normally. Before sending the request, the driver must prepare the next I/O stack location that it will be looked at by the next driver in line. It can use the IoSkipIrp-StackLocation macro if it does not wish to make changes, or it can make a copy with IoCopy-IrpStackLocationNext and make appropriate changes. Once the next I/O stack location is prepared, the driver calls IIoCallDriver to do the actual IRP forwarding.

+   * As an extension of the previous point, the driver can also register for a completion routine by calling IoSetCompletionRoutine(Ex) before passing down the IRP. Any layer except the bottom-most one can register a completion routine (there is no point in registering for the bottom-most layer since that driver creates the IRP, so no callback is needed). IoCompleteRequest is called by a lower-driver, the IRP travels up (refer to Figure 6-13), calling all completion routines on the way up in reverse order of registration. If, the IRP originator (I/O manager, PnP manager, or power manager) use this mechanism to do any post-IRP processing and freely free the IRP.

Because the number of devices on a given stack is known in advance, the I/O manager allocates one stack location per device driver on the stack. However, there are situations in which an IRP might be directed into a new driver stack. This can happen in scenarios involving the filter manager, which allows one to redirect an IRP to another filter (for example, going from a local file system to a network file system). The I/O manager exposes an API, IoAdjustStackSizeForRedirection, that enables this functionality by adding the required stack locations because devices present on the redirected stack.
