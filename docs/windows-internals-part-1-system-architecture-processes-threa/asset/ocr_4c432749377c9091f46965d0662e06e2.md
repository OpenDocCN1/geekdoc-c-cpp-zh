Closely related to the concept of hierarchy is KMDF's notion of object context. Because KMDF objects are opaque (as discussed) and are associated with a parent object for locality, it becomes important to allow drivers to attach their own data to an object in order to track specific information outside the framework's capabilities or support. Object context allows all KMDF objects, which permit multiple layers of code inside the same driver to in different ways. In WDM, the device extension custom data structure allows such information to be associated with a given device, but with KMDF a spinlock or string can contain context areas. This extensibility allows each library or layer of code responsible for processing an I/O request independently of other code, based on the context that it works with.

Finally, KMDF objects are also associated with a set of attributes, shown in Table 6-12. These attributes are usually configured to their default, but the values can be overridden by the driver when creating the object by specifying a WDF_OBJECT_ATTRIBUTES structure (similar to the object manager’s OBJECT_ATTRIBUTES structure that was used when creating a kernel object).

# TABLE 6-12 KMDF object attributes

| Attribute | Description |
|---|---|
| ContextSize | This is the size of the object area. |
| ContextType | This is the type of the object area. |
| EvtCleanupCallback | This is the callback to notify the driver's cleanup before deletion (References may still exist). |
| EvtDestroyCallback | This is the callback to notify the driver's imminent deletion (The reference count will be 0). |
| ExecutionLevel | This describes the maximum IRQL at which the callbacks may be invoked by KMDF. |

# KMDF I/O model

The KMDF I/O model follows the WDM mechanisms discussed earlier in this chapter. In fact, you can even think of the framework as a WDM driver, since it uses kernel APIs and WDM to abstract KMDF and make it functional. Under KMDF, the framework driver sets its own WDM-style dispatch routines and takes control of all IRPs sent to the driver. After being handled by one of KMDF I/O handlers (described shortly), it packages these requests in the appropriate queues KMDF objects (if required), and performs driver callback if the driver is interested in these events.
