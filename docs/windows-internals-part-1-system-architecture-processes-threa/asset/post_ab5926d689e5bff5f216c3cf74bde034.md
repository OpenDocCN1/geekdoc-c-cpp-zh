Security descriptors (SDs) can be programmatically retrieved using various functions, such as GetSecurityInfo, KernelGetObjectSecurity, GetFileSecurity, GetNamedSecurityInfo, and other esoteric functions. After retrieval, the SD can be manipulated and the relevant Set function called to make the change. Furthermore, a descriptor can be constructed using a string in a language called Security Descriptor Language (SDDL), which is capable of representing a security descriptor using a compact string. This string can be converted to a true SD by calling ConvertStringToSecurityDescriptor. As you might expect, the convert function exists as well (ConvertSecurityDescriptorToSecurityDescriptor). The Windows SDK for a detailed description of the SDDL.

An access control (ACL) is made up of a header and zero access control entry (ACE) structures. There are two types of ACLs: DACLs and SACLs. In a DACL each ACE contains a SID and an access mask (a set of flags, explained shortly), which typically specifies the access rights (read, write, delete, and so) that are granted or denied to the holder of the SID. There are nine types of ACEs that appear in a DACL: access allowed, access denied, allowed object, denied object, allowed callback, denied callback, allowed object, denied object, and conditional classes. As you would expect, the access-allowed ACE grants access to a user, and the access-denied ACE denies the access rights specified in the access mask. The callback ACEs are used by applications that make use of the AuthZ API (described later) to register a callback that AuthZ will call when it performs an access checking this ACE.

The difference between allowed object and access allowed, between denied object and access denied, is that the object types are used only unique identifier (GUID) field that identifies the ACE applies only to objects or subclasses that have GUID identifiers (GUID is a 128-bit identifier guaranteed to be unique). In addition, another optional GUID indicates what type of child object will inherit the ACE when a child is created in an Active Directory that has the ACE applied to it. The conditional classes ACE is stored in a -callback type ACE structure and is described in the section on the AuthZ APIs.

The accumulation of access rights granted by individual ACEs forms the set of access rights granted by an ACL. If no DACL is present (null DACL in a security descriptor, everyone has full access to the object). If the DACL is empty (it, has zero ACEs), no user has access to the object.

The ACEs in DACLs also have a set of flags that control and specify characteristics of the ACE related to inheritance. Some namespaces have containers and objects. A container can hold other container objects and leaf objects, which are its child objects. Examples of containers are directories in the file system and keys in the registry namespace. Certain flags in an ACE control the child objects associated with the ACE. Table 7-6, reproduced in part from the Windows Server, lists the inheritance rules for ACE.

## TABLE 7-6 Inheritance rules for ACE flags

| Flag | Inheritance Rule |
| --- | --- |
| CONTAINER_INHERIT_ACE | Child objects that are containers, such as directories, inherit the ACE as an effective ACE. The inherited ACE is inheritable unless the NO_PROPAGATE_INHERIT_ACE bit is also set. |
| INHERIT_ONLY_ACE | This flag indicates an inherit-only ACE that does not control access to the object it is attached to. If this flag is not set, ACE controls access to the object it is attached. |
| INHERIT_ACE | This flag indicates the ACE was inherited. The system sets this bit when it propagates an inheritance to a child object. |
| NO_PROPAGATE_INHERIT_ACE | If the ACE is inherited by a child object, the system clears the OBJECT_INHERIT_ACE and CONTAINER_INHERIT_ACE flags in the inherited ACE. This action prevents the inheritance from inheriting objects. |
| OBJECT_INHERIT_ACE | Non-container child objects inherit the ACE as an effective ACE. For child objects that, the ACE is inherited as an inherit-only ACE unless the NO_PROPAGATE_INHERIT_ACE bit is also set. |

A SACL contains two types of ACEs: system audit-object ACEs and system audit-access ACEs. These ACEs specify which operations performed on the object by specific users or groups should be audited. Audit information is stored in the system audit log. Both successful and unsuccessful attempts can be audited. Their DACL object-specific ACE cousins, system audit-object ACEs specify a GUID indicating the propagation of the ACE to particular child object types. If a SACL is not set, no auditing takes place on the object. (Security auditing is described later in this chapter). The inheritance rules that apply to DACL ACEs also apply to system audit and audit-object ACEs.
