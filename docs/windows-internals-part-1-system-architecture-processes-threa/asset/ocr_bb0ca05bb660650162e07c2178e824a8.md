# Applying boosts

Back in KiEditDispatcher, you saw that KiThreadWaitList is called to process threads in the deferred list. It is here that boost information passed by the caller is processed. This is done by looping through each DeferredReady, unlinking its wait blocks (only Active and Bypassed blocks are unlinked), and setting two key values in the kernel's thread control block: Reason and AdjustIncrement. The reason is one of the two Adjust possibilities seen earlier, and the increment completes the boost value. KiDeferredReady is then called. This makes the thread ready for execution by running two algorithms: the quantum and priority selection algorithm (which you are about to see in two parts) and the processor selection algorithm (which is shown in the "Processor selection" section in this chapter).

Let's first look at when the algorithm applies boosts, which happens only in cases when a thread is not in the real-time priority. For an AdjustUnwait boost, it will be applied only if the thread is not experiencing an unusual boost and if the thread is not disabling boosting by calling SetThreadPriority, which sets the DisableBoost flag in the KTHREAD. Another situation that can disable boosting in this case is if the kernel has realized that the thread has actually exhausted its quantum (but the clock interrupt did not fire to consume it) and it comes out of a wait that lasted less than two ticks.

If these situations are not true, the new priority of the thread will be computed by adding the AdjustIncrement to the thread's base priority. Additionally, if the thread is known to be part of a foreground process (meaning the memory priority is set to MEMORY_PRIORITY_FOREGROUND, which is configured for Win32 apps when focus changes), this is where the priority-separation boost (PsPrioritySeparation) is applied by adding its value on the new priority. This is also known as the foreground priority boost, which was explained earlier.

Finally, the kernel checks whether this newly computed priority is higher than the current priority of the thread, and it limits this to an upper bound of 15 to avoid crossing into the real-time range. It then sets this value as the thread's new priority. If any separation boost was applied, it sets this value in the ForegroundBoost field of KTHREAD, which results in a PriorityDecrement equal to the separation boost.

For AdjustBoost, the kernel checks whether the thread's priority is lower than the current priority is below 13. If so, and priority have not been disabled for the thread, the AdjustIncrement is used as the new current priority, limited to a maximum of 13. Meanwhile, the UnusualBoost field of the KTHREAD contains the boost value, which results in a PriorityDecrement equal to the ownership boost.

In all cases where a PriorityDecrement is present, the value of the thread is also reconstructed to be the equivalent of one tick, based on the value of KiLockQuantumTarget. This ensures that foreground and unusual boosts will be lost after one tick instead of two (or other configured value), as will be shown in the next section. This also happens when an AdjustBoost is requested by the thread that is running at priority 13 or 14 or without boosts disabled.

After this work is complete, AdjustReason is now set to AdjustNone.
