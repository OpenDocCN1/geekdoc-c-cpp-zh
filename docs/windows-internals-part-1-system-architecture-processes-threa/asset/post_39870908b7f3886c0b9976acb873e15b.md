
Note There is a Control Panel applet (System) that provides control over the size, number, and locations of paging files. Its nomenclature suggests virtual memory is the same as the paging file. This is not the case. The paging file is only one aspect of virtual memory. In fact, even if you run with no page file at all, Windows will still be using virtual memory. This distinction is explained in more detail later in the chapter.

## Memory manager components

The memory manager is part of the Windows executive and exists in the file Ntoskrnl.exe. It's the largest component in the executive, hinting at its importance and complexity. No parts of the memory manager exists in the HAL. The memory manager consists of the following components:

- A set of executive services for allocating, deallocating, and managing virtual memory, most of which are exposed through the Windows API or kernel-mode device interfaces
- A translation-not-valid and access fault trap handler for resolving hardware-detected memory management exceptions and making virtual pages resident on behalf of a process
- Six key-level routines, each running in one of six kernel-mode threads in the System process:
    - The balance set manager (KeBalanceSetManager, priority 17) calls an inner routine, the working manager (MiWorkingSetManager), once per second as well as when memory falls below a certain threshold. The working manager drives the overall memory-management policies, such as working trimming, aging, and modified page writing.
    - The process/stack swapper (KeSwapProcessorStack, priority 23) performs this process and kernel thread swapping and outswapping. The balance manager and the thread-scheduling code in the kernel activates when an swap or outswap needs to take place.
    - The modified page writer (MiModifiedPageWriter, priority 18) This writes pages on the modified list back to the appropriate paging files. This thread is awakened when the size of the modified list needs to be reduced.
    - The mapped page writer (MiMappedPageWriter, priority 18) This writes pages in mapped files to disk or remote storage. It is awakened when the size of the modified list needs to be reduced or if pages for mapped files have been on the modified list for more than 5 minutes. This second modified page writer thread is necessary because it generates faults that results in free pages. If there were no pages and only one modified page writer thread, the system could deadlock waiting for free pages.
    - The segment reference thread (MiDereferenceSegmentThread, priority 19) This is responsible for cache reduction as well as for page growth and shrinkage. For example, there is no virtual address space for paged pool growth, this thread trims the page cache so the paged pool used to anchor it can be freed for reuse.
    - The zero page thread (MiZeroPageThread, priority 0) This zeroes out the page list so that a cache of zero pages is available to satisfy demand-zero page faults. In some cases, memory zeroing is by a faster function MiZeroInParallel. See the note in the “Page list dynamics” section later in this chapter.

Each of these components is covered in more detail later in the chapter except for the segment dereference thread, which is covered in Chapter 14, Cache manager,” in Part 2.

## Large and small pages

Memory management is done in distinct chunks called pages. This is because the hardware management unit translates virtual to physical addresses at the granularity of page. Hence, a page is the smallest unit of protection at the hardware level. (The various page-protection options are described in the section “Protecting memory” later in this chapter.) The processors on Windows support two page sizes: small and large. The actual sizes vary based on the processor architecture, and they are listed in Table 5-1.

TABLE 5-1 Page sizes
| Architecture | Small Page Size | Large Page Size | Small Pages per Large Page |
|---|---|---|---|
| x86 (PAE) | 4 KB | 2 MB | 512 |
| x64 | 4 KB | 2 MB | 512 |
| ARM | 4 KB | 4 MB | 1024 |

> Note Some processors support configurable page sizes, but Windows does not use this feature.

The primary advantage of large pages is speed of address translation for references to data within the large page. This advantage exists because the first reference to any byte within a large page will cause the hardware’s translation look-aside buffer (TLB) (described in the section “Address translation” later in this chapter), to have in cache the information necessary to translate to any other byte within the large page. If small pages are used, more TLB entries are needed for the same range of virtual addresses, increasing the recycling of entries. In turn, this means to go back to the page tables when references are made to virtual addresses outside the scope of a small page whose translation has changed. The TLB is a very small cache; large pages make better use of this limited resource.

To take advantage of large pages on systems with more than 2 GB of RAM, Windows maps with large pages the core operating system images (Ntoskrnl.exe and Hal) as well as core system data (such as the part of non-paged pool and the data structures that describe the state of each physical memory). Windows automatically maps I/O space (by MmMapIoSpace) with large pages if the request is of a satisfactorily large page length and alignment. In addition, Windows allows applications to map their images, private memory, and page file-backed sections with large pages (the MEM_LARGE_PAGES flag on the VirtualAlloc, VirtualAllocEx, VirtualAllocEx functions). You can also specify other device drivers to be mapped with large pages by adding a multicast registry value LargePageDrivers to the key HKL\SYSTEM\CurrentControlSet\Control\SessionManager\Memory Management and specifying the names of the drivers as separately null-terminated strings.

Attempts to allocate large pages may fail after the operating system has been running for an extended period because the physical memory for each large page must occupy a significant number (refer to Table 5-1) of physically contiguous pages. This extent of physical pages must furthermore begin on a large page boundary. For example, physical pages 0–511 could be used as a large page on an x64 system, pages 512–1023 could not. Free memory thus becomes fragmented as the system runs. This is not a problem for allocations with small pages but can cause large pages to fail.

The memory is also non-pageable because the file system does not support large pages. Because the memory is non-pageable, the caller is required to have the SeLockMemoryPrivilege be able to allocate large pages. The allocated memory is not considered part of the process working set (described in "Working sets" later in this chapter); nor large page allocations subject to job-wide limits on virtual memory usage.

On x64 systems large pages may also be mapped with huge pages, where 1 GB is in size. This is done automatically if the allocation is larger than 1 GB, but it does not have to be a multiple of 1 GB. For example, an allocation of 1040 MB would result in one huge page (1024 MB) plus 8 "normal" large pages (16 MB divided by 2 MB).

There is an unfortunate effect of large pages. Each page (whether large, huge, or small) must be mapped with a single protection that applies to the entire entity. If a large page contains, for example, both read-only code and read/write data, the page must be marked as read/write, meaning that the code could be writable. As a result, device drivers or other kernel-mode code could, either maliciously or due to a bug, modify what is supposed to be read-only operating system or driver code without causing a memory access violation. If small pages are used to map the operating system's kernel-mode code, the read-only portions of Ntoskrnl.exe and Hal.dll can be mapped as read-only pages. Using small pages reduces efficiency but if a driver (or other kernel-mode code) attempts to modify only one part of the operating system, the system will crash immediately with the information pointing at the offending instruction in the driver. If it were allowed to occur, the system would likely crash (a harder-to-diagnose way) when other component tried to use the corrupted data.

If you are experiencing kernel corruptions, enable Driver Verifier (described in Chapter 6, "I/O system"), which will disable the use of large pages.

> Note The term large page used in this and later chapters refers to a small page unless otherwise indicated or apparent by context.
