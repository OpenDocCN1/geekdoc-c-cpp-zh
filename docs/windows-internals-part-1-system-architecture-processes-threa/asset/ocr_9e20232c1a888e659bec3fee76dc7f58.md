+   Logon session This is associated with the SYSTEM and Anonymous local ID (LUID), plus the LUID of a virtual service account describing the user in the silo. This essentially represents the token of the services and application that will be running inside the container session created by Smss. For more information on LUIDs and logon sessions, see Chapter 7.

+   ETW tracking and logging contexts These are for isolating ETW operations to the silo and not exposing or leaking states between the containers and/or the host OS itself. (See Chapter 9 in Part 2 for more on ETW.)

# Silo contexts

While these are the isolation boundaries provided by the core OS kernel itself, other components inside the kernel, as well as drivers (third party), can create data silos by using the PsCreateSilo API to set custom data with a silo or by associating an existing object with it. Each silo context will utilize a silo slot that will be inserted in all running, and future, silos, storing a pointer to the context. The system provides 32 built-in system-wide storage slots, plus 256 extra slots, providing lots of extensibility options.

As each silo is created, it receives its own silo-local (SLS) array, like a thread that has thread-local storage (TLS). Within this array, the different entries correspond to slot indices that have been allocated to silo contexts. Each silo will have a different pointer at the slot index, but will always store the same context at that index. (For example, driver "Foo" will own index 5 in all silos, and can use it to store a different pointer/context in each silo.) In some cases, built-in kernel components, as the object manager, security reference monitor (SRM), and Configuration Manager use some of these slots, while others are used by index drivers (as the Ancillary Function Driver for Windows, Afd.sys.)

Just like dealing with the server shared user data, various components and APIs have been updated to access data by getting from the relevant silo context instead of using a global variable. As an example, each container will now host its own Lsass.exe process, while the kernel's SRM needs to own to handle Lsass.exe process (see Chapter 7 for more information on Lsass and the SRM), this can no longer be a singleton store in a global variable. As such, the handle is now accessed by the SRM querying the silo context of the active server silo, and getting the variable from the data structure that returned.

This leads to an interesting question: What happens with the Lsass.exe that is running on the host OS itself? How will the SRM access the handle, as there's no server silo for this set of processes and session (that is, session  itself)? The kernel now implements a root host silo. In other words, the host itself is preserved to be part of a silo! This isn't in the true sense of the word, but a clever trick to querying silo contexts for the current silo work, even when there is no current silo. This is implemented by storing a global variable named PsHostSilo-Global, which has its own Slot Local Storage Array, as well as other silo contexts built-in by kernel components. When various silo APIs are called with a NULL pointer, "NULL" is treated instead as "no silo—i.e., use the host silo.
