
## Commit charge and page file size

The counters in Table 5-13 can assist you in choosing a custom page file size. The default policy based on the amount of RAM works acceptably for most machines, but depending on the workload, it can result in a page file that's unnecessarily large or not enough.

To determine how much page-file space your system really needs based on the mix of applications that have run since the system booted, examine the peak commit charge in the Memory of Explorer's System Information display. This number represents the peak amount of page file space since the system booted that would have been needed if the system had to out the majority of private virtual memory (rarely happens).

If the page file on your system is too big, the system will not use it any more. In other words, increasing the size of the page file does not change system performance. It simply means the system can have more committed virtual memory. If the page file is too small for the mix of applications you are running, you might get a "system running on low memory" error message. In this case, check to whether a process has a memory leak by examining the process pool size. If a device driver is leaking paging pool, this might also explain the error. Refer to the "Troubleshooting a pool leak" experiment (Kernel-mode heaps (system pools)) section for information on troubleshooting a pool leak.

## Stack

Whenever a thread runs, it has access to a temporary storage location in which to store parameters, local variables, and the return address after a function call. This part of memory is called a stack. On Windows, the memory manager provides two stacks for each thread: the user stack and the kernel stack, as well as per-processor stacks DPC stacks. Chapter 2 briefly discussed how system calls cause the thread to switch from a user stack to its kernel stack. Now we'll look at some extra memory manager provides to efficiently use stack space.

## User stacks

When a thread is created, the memory manager automatically reserves a predetermined amount of virtual memory, by default 1 MB. This amount can be configured in the call to the CreateThread or CreateRemoteThread(Ex) function or when compiling the application using the /STACK: reserve switch in the Microsoft C/C++ compiler, which stores the information in the image header. 1 MB is reserved, only the first page of the stack will be committed (unless the PE header of the image specifies otherwise), with a guard page. When a thread's stack grows enough to touch the guard page, an exception occurs, causing an allocator to allocate another. Through this mechanism, a user stack doesn't immediately consume 1 MB of committed memory but instead grows with demand. (However, it will never shrink back.)

## EXPERIMENT: Creating the maximum number of threads

With only 2 GB of user address space available to 32-bit process, the relatively large memory that is reserved for each thread's stack allows for an easy calculation of the maximum number of threads that a process can support: little less than 2048, for a total of 2 GB of memory (unless increaseRCB option is used and the image is large address space). By forcing each new thread to the smallest possible stack reservation size, 64 KB, the limit can grow to 30,000 threads. You can test this for yourself by using the TestUtility from Sysinternals. ## Kernel stacks

Although user stack sizes are typically 1 MB, the amount of memory dedicated to the kernel stack is significantly smaller: 12 KB on 32-bit systems and 16 KB on 64-bit systems, followed by another guard page, for total of 16 or 20 KB of virtual address space. Code running in the kernel is expected to have less recursion than user code, as well as more efficient variable and keep stack buffer sizes low. Because kernel stacks live in system address space (which is shared by all processes), their memory usage has a bigger impact on the system.

Although code is usually not recursive, interactions between graphics system calls handled by Win32 and its subsequent callbacks into user mode can cause recursive re-entries in the kernel on the same stack. As such, Windows provides a mechanism for dynamically expanding and shrinking the kernel stack from its initial size. As each graphics call is performed on the same thread, another 16 KB stack is allocated. (This happens anywhere in system address space. The memory manager provides the ability to jump stacks when nearing the guard page.) Whenever each call returns to the caller (unwinding), the memory manager frees the additional kernel stack that has been allocated, as shown in Figure 5-28. This mechanism allows reliable support for recursive system calls as well as efficient use of system address space. It is provided for developers performing recursive calls through the KeExpandKernelStackAndCallout(Ex) APIs, as necessary.
