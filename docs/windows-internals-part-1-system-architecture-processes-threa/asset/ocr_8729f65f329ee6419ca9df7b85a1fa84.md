+   - Dynamic creation there enabled.

+   - The number of available workers is lower than the maximum number of workers configured for the factory (default 500).

+   - The worker factory has bound objects (for example, an ALPC port that this thread is waiting on) or a thread has been activated into the pool.

+   - There are pending I/O request packets (IRPs; see Chapter 6 for more information) associated with a worker thread.

In addition, it will terminate threads whenever they become idle—that is, they haven't processed any work item—more than 10 seconds (by default). Furthermore, although developers have always been able to take advantage of many threads as possible (based on the number of processors on the system) through the old implementation, it is now possible for applications using thread pools to dynamically take advantage of new processors added at runtime. This is through its support for dynamic processors in Windows Server (as discussed earlier in this chapter).

# Worker factory creation

The worker factory support is mostly a wrapper to manage mundane tasks that would otherwise have been performed in user mode (at a loss of performance). Much of the logic of the new thread-pool code remains in Ntdll.dll side of this architecture.(Theoretically, by undocumented functions, a different thread-pool implementation can be built around worker factories). Also, it is not the worker factory that provides the scalability, wait intervals, and efficiency of worker process. Instead, it is a much older component of Windows: I/O completion ports, or more correctly, kernel queues (QUEUE). In fact, when creating a worker factory, an I/O completion port must already have been created by user thread, and the handle needs to be passed in.

It is through calling this I/O completion port that the user-mode implementation will queue and wait for work—by calling the worker factory system instead of the I/O completion port APIs. However, the “release” worker factory call (which queues work) is a wrapper around SetIoCompletion, while the “wait” call is a wrapper around RemoveIoCompletion. Both routines call into the kernel queue implementation. The job of the worker factory code is to manage either a persistent, static, dynamic thread pool; wrap the I/O completion port model into interfaces that prevent stalled workers by creating dynamic threads; and simplify cleanup and termination operations during a factory shutdown request (as well as block new requests from the factory in such a scenario).

The executive function that creates the worker factory, NtCreateWorkerFactory, accepts several arguments that allow control of the thread pool, such as maximum threads to create and the initial committed and reserved stacks. The CreateThreadpool Windows API, however, uses the default stacks embedded in the executable image (just like a default CreateThread would). The Windows API does not, however, provide a way to override these defaults. This is somewhat unfortunate, in many cases thread-pool threads don't require deep calls, and it would be beneficial to allocate smaller stacks.
