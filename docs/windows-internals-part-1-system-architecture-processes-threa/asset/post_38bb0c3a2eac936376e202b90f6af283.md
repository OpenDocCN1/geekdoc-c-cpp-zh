To summarize, the order of driver loading for a device is as follows:

- 1. The bus driver is loaded, creating the PDO.
- 2. Any lower filters listed in the Hardware instance key are loaded, in the order listed (multi string), creating their filter device objects (FIDs) in Figure 6-34).
- 3. Any lower filters listed in the corresponding Class key are loaded in the order listed, creating their Fidos.
- 4. The driver list listed in the Service value is loaded, creating the FDO.
- 5. Any upper filters listed in the Hardware instance key are loaded, in the order listed, creating their Fidos.
- 6. Any upper filters listed in the corresponding Class key are loaded in the order listed, creating their Fidos.

To deal with multifunction devices (such as all-in-one printers or cell phones with integrated camera and music player functionalities), Windows also supports a container ID property that can be associated with a devnode. The container ID is a GUID that is unique to a single instance of a physical device and shared between all devnodes that belong to it, as shown in Figure 6-38.

The container ID is a property, similar to the instance ID, is reported back by the bus driver of the corresponding hardware. Then, when the device is enumerated, all devnodes associated with the same container ID share the ID. Because Windows already supports many buses out of the box—such as PnP, Bluetooth, and USB—most devices can simply return the bus-specific ID, from which Windows will generate the corresponding container ID. For other kinds of devices or buses, the driver can generate its own ID through software.

Finally, when device drivers do not supply a container ID, Windows can make guesses by querying the topology for the bus when available, through mechanisms such as ACPI. By understanding whether a certain device is a child of another, and whether it is removable, hot-pluggable, or user-reachable (as opposed to a motherboard component), Windows is able to assign container IDs to reflect multifunction devices correctly.

The benefit of grouping devices by container IDs is visible in the Devices and Printers UI. This feature allows to display the scanner, printer, and components of an all-in-one printer as a single element instead of three distinct devices. ## Driver support for Plug Play

To support Plug Play, a driver must implement a Plug and Play dispatch routine (IRP_MJ_PNP), a power management dispatch routine (IRP_MJ_POWER, described in the section “The power manager” later in this chapter), and an add-device routine. Bus must support Plug Play requests that are different than the ones that function or filter drivers support. For example, the PnP manager guides device enumeration during system boot, it asks bus drivers for a description of the devices they find on their respective buses by PnP IRPs.

Function and filter drivers prepare to manage their devices in their add-device routines but they don't actually communicate with the device hardware. Wait for the PnP manager to send a start-device command (IRP_MJ_START_DEVICE) to deliver to their dispatch routine. Before sending the start-device command, the PnP manager performs arbitration to decide what resources to assign the device. The start-device command includes resource assignment. When a driver receives a start-device command, it can configure its device to use the specified resources. If an application tries to open a device that hasn't finished starting, it receives an error indicating that the device does not exist.

After a device has started, the PnP manager can send the driver additional Plug and Play commands, including ones related to the device's removal from the system or resource reassignment. For example, when the user removes the device using the event utility shown in 6-40 (by clicking the USB icon in the taskbar area), to tell Windows to eject a USB flash drive, the PnP manager sends a query-removal notification to any applications that have registered for Plug and Play notifications for the device. Applications typically register for notifications on their handles, which they close during query-removal.

When the PnP manager needs to reason further about a device's resources, it first asks the driver whether it can temporarily suspend it by sending the driver a query-stop command (IRP_MN_QUERY_STOP_DEVICE). The driver agrees to the request (if doing so won't cause data loss or corruption) or denies the request. As a query-remove command, if the driver agrees to the request that can't be aborted and subsequently restarted, the driver typically queues I/O requests for the device and won't initiate I/O requests for the device so that the resource reshuffling is transparent to applications currently accessing the device. The PnP manager then sends the driver a stop command (IRP_MN_STOP_DEVICE). At that point, the PnP manager can direct the driver to assign different resources to the device and again send the driver a start-device command for the device.

The various Plug and Play commands essentially guide a device through an operational state machine, forming a well-defined state-transition table, which is shown in Figure 6-41. (The state diagram reflects the state machine implemented by function drivers. Drivers implement a more complex state machine.) Each transition in Figure 6-41 is marked by its minor IRP constant without the IRP_MN_prefix. One state that we haven't shown is the one that results from the PnP manager's command (IRP_MN_SURPRISE_REMOVAL). This command results when a user removes a device without warning, as when the user removes a PCMC card without using the remove/eject utility, or the device fails. The command tells the driver to immediately cease all interaction with the device because the device is no longer attached to the system and to cancel any pending I/O requests.
