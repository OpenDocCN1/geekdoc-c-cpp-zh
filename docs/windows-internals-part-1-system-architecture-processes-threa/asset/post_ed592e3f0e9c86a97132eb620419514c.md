
## Performance Options

Data Execution Prevention (DEP) helps protect against damage from viruses and other security threats. How does it work?

- Turn on DEP for essential Windows programs and services only

| BCD nx Value | Option on Data Execution Prevention Tab | Explanation |
|---|---|---|
| OptIn | Turn on DEP for Essential Windows Programs and Services Only | This enables DEP for core Windows system images. It enables 32-bit processes to dynamically configure DEP for their lifetime. |
| OptOut | Turn on DEP for All Programs and Services Except Those I | This enables DEP for all executables except those specified. It enables 32-bit processes to dynamically configure DEP for their lifetime. It enables system compatibility fixes for DEP. |
| AlwaysOn | There is no dialog box option for this setting | This enables DEP for all components with no ability to exclude certain applications. It enables dynamic configuration for 32-bit processes and disables system compatibility fixes. |
| AlwaysOff | There is no dialog box option for this setting | This disables DEP (not recommended). It disables dynamic configuration for 32-bit processes. |

On Windows client versions (both 64-bit and 32-bit), execution protection for 32-bit processes is configured by default to apply only to core Windows operating system executables. That is, the nx BCD option is set to OptIn. To avoid breaking 32-bit applications that might rely on execute code in pages not specifically marked as executable, such as self-extracting or packed applications. On Windows server systems, execution protection for 32-bit applications is configured by default to apply to all 32-bit processes. That is, the nx BCD option is set to OptOut.

Even if DEP needs to be enabled, there are still other methods through which applications can disable DEP for their own images. For example, regardless of which execution-protection options are enabled, the image loader will verify the signature of the executable against known copy-protection mechanisms (such as SafeDisc and SecuROM) and disable execution protection to provide compatibility with other copy-protected software such as computer games. (See Chapter 3 for more information about the image loader).

## EXPERIMENT: Looking at DEP protection on processes

Process Explorer can show the current DEP status for all the processes on your system, including whether the process is opted in or benefiting from permanent protection. To look at the DEP status, right-click any column in the process tree, choose Select Columns, and then select DEP Status on the Process Image tab. There are three possible values:

- DEP (permanent) This means the process has enabled DEP because it is a "necessary Windows program or service."

- DEP This means the process opted in DEP. This may be due to a system-wide policy to opt in for all 32-bit processes, because of an API call such as SetProcessDEPPolicy or because the /COMPAT linker flag was set when the image was built.

- Nothing If the column displays no information for this process, DEP is disabled because either a system-wide policy or an API call or shim.

Additionally, to provide compatibility with older versions of the ATL Framework (version 7.1 or earlier), the Windows kernel provides an ATL emulation environment. The environment detects ATL thread code that have caused the DEP exception and emulates the expected operation. Application developers can request that ATL emulation not be applied using the latest Microsoft C++ compiler and specifying the /COMPAT flag (which sets the IMAGE_DLL_NX_COMPAT flag in the PE header), which tells the system that the executable fully supports DEP. DEP emulation is disabled if the AlwaysOn value is set.

Finally, if the system is in OptIn or OptOut mode and executing a 32-bit process, the SetDEPPolicy allows a process to dynamically disable DEP or to permanently enable it. When is enabled through this API, DEP cannot be disabled programmatically. This function can also be used to dynamically disable ATL emulation if the image wasn't compiled with the /COMPAT flag. On 64-bit processes or systems with AlwaysOff or AlwaysOn, the function always returns a failure. The GetProcessDEPPolicy function returns the 32-bit process DEP policy (it fails on 64-bit systems, where the policy is the same—always), GetSystemDEPPolicy can be used to return a value corresponding to the policies in Table 5-3.

## Copy-on-write

Copy-on-write page protection is an optimization the memory manager uses to conserve physical memory. When a process maps a copy-on-write view of a section that contains read/write pages, the memory manager delays the copying of pages until the page is written instead of making a private copy at the time the view is mapped. For example, in Figure 5-4, two processes are sharing three pages, marked copy-on-write, but neither of the two processes has attempted to modify any data of the pages.

![](img/ff0e6a9d867a3a6e9527eb1d946810fc_338_0.png)

FIGURE 5-4 The "before" of copy-on-write.

If a either process writes to a page, a memory-management fault is generated. The memory manager sees that the write is to a copy-on-write page, so instead of reporting the fault as an access violation, it does the following:

1. It allocates a new read/write page.
2. It copies the contents of the original page to the new page.
3. It updates the mapping information to point to the new location.
4. It dismisses the exception, causing the instruction to be re-executed.

This operation succeeds. However, as shown in Figure 5-5, the newly copied page is now private to the process.

![](img/ff0e6a9d867a3a6e9527eb1d946810fc_338_1.png)

FIGURE 5-5 The "after" of copy-on-write.

Copy-on-write is one example of an evaluation technique called lazy evaluation the memory manager uses as often as possible. To examine the rate of copy-on-write faults, see Write/Sec performance counter in Memory category.

## Address Extensions

Although the 32-bit version of Windows can support up to 6 GB of physical memory (refer to Table 2-2), each 32-bit user process has only 2 GB address space by default. (You can configure this to 3 GB using the increaseuser option, described in the section "Virtual address space layouts.") An application that needs to make more than 2 GB (or 3 GB) of data easily available in a single process could do so via file mapping, remapping a part of its address space into a file.

For higher performance (and more finer-grained control), Windows provides a set of functions Address Extensions (AWE). These functions allow to allocate more physical memory than can be represented in its virtual address space. It can then access the physical memory by mapping portions of its address space at various times.

You allocate and use memory via the AWE functions in three steps:

- You allocate the physical memory to use. The application uses the Windows functions AllocateUserPages or AllocateUserPagesNum. (These require the SeLockMemoryPrivilege.)

- You create one or more regions of virtual address space to map views of the physical memory. The application uses the Win32 VirtualA1Alloc, VirtualA1AllocEx, or VirtualA1Allocnum with the MEM_PHYSICAL flag.

- Steps 1 and 2 are, generally speaking, initialization steps. To actually use the memory, the application uses MapUserPhysicalPages or MapUserPhysicalPagesScatter to map a portion of the physical region allocated in step 1 into one of the regions, or allocated in step 2.
