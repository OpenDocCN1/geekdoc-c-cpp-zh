
The computer never directly transitions between states S1 and S4 (because that requires code execution, but the CPU is off in these states); instead, it must move to state S0 first. As illustrated in Figure 6-49, when the system is moving from any of states S1 through S5 to state S0, it's said to be waking, and it's transitioning from state S0 to any of states S1 through S5, it's said to be sleeping.

For devices, ACPI defines power states, from D0 through D3. State D0 is fully on, while state D3 is fully off. The ACPI standard leaves it to individual drivers and devices to define the meanings of states D1 and D2, except that state D1 must consume an amount of power less or equal to that consumed in D0, and when the device is in D2, it must consume power less or equal to that consumed in D1.

Windows 8 (and later) splits the D3 state into two sub-states, D3-hot and D3-cold. In D3-hot state, the device is mostly turned off, but not disconnected from its main power source, and its parent bus controller can detect the presence of the device on the bus. In D3-cold, the main power source is removed from the device, and the bus controller cannot detect the device. This state provides another opportunity for saving power. Before Windows 8, devices could only reach D3-hot state when the system is fully on (S0). The transition to D3-cold was implicit when the system went into a sleep state. Starting with Windows 8, a device's power state can be set to D3-cold while the system is fully on. The driver that controls the device cannot put the device into D3-cold state directly; it can put the device into D3-hot state, and then, depending on other devices on the same bus entering D3-hot states, the bus driver and firmware may decide to move all devices to D3-cold. The decision to move to D3-cold depends on two factors: the actual activity of the bus driver and firmware, and second the driver that must enable the transition to D3-cold by specifying that in the installation INF file or by calling the SetD3ColdSupport function dynamically.

Microsoft, in conjunction with the major hardware OEMs, has defined a series of power management reference specifications that specify the power states that are required for all devices in a particular class (for the major device classes: display, network, SCSI, and so on). For some devices, there's no intermediate power state between fully on and fully off, which results in these states being undefined.

## Connected Standby and Modern Standby

You may have noticed in the experiment above system state called Connected Standby (S0 Low Power Idle). Although not an official ACPI state, it is a variant of S0 known as Connected Standby on Windows 8.x and later enhanced in Windows 10 (desktop and mobile devices) and called Modern Standby. The "normal" state (S3 above) is sometimes referred to as Legacy Standby.

The problem with Legacy Standby is that the system is not working, and therefore, for the user receives an email, the system can't up without waking to S0, which may or may not, depending on configuration and device capabilities. Even if the system wakes up to get that email, it won't go immediately to sleep again. Modern Standby solves both issues.

Systems that support Modern Standby go into this state. The system is technically at S0, meaning the CPU is active. However, most UWP apps are suspended, but background tasks are allowed to execute. Note that not all systems support Modern Standby, as it depends on the chipset and other platform components. For more information on Modern Standby, consult the Windows Hardware documentation. This state is sometimes referred to as Instant On.

## Power manager operation

Windows power-management policy is split between the power manager and the individual device drivers. The power manager is the owner of the system power policy. This ownership means the power manager decides which system state is appropriate at any point, and when a sleep, hibernation or shutdown is required, the power manager instructs the power-capable devices to perform system-state transitions.

The power manager decides when a system-state transition is necessary by considering several factors:

- System activity level
- System battery level
- Shutdown, hibernate or sleep requests from applications
- User actions, as pressing the power button

When the PnP manager performs device enumeration, part of the information it receives about a device is its power-management capabilities. A driver reports whether its devices support device states D1 and D2, and the latencies, or times required to move from states D1 through D3. To help the power manager determine when to make power-state transitions, drivers also return a table that implements a mapping between each of the system power states (S0 through S5) and the device power states that it supports.

The table lists the lowest possible device power state for each system state when the machine sleeps or hibernates. For example, a bus that supports various power planes when the machine sleeps all four device states might return the mapping table shown in Table 6-14. Media drivers return their devices completely off (D3) when sleeping S0 to minimize power consumption when the machine isn't in use. Some devices, however, as network adapter cards, support the ability to wake the system from a sleeping state. This ability, along with the lowest device power state in which capacity is present, is also reported during device enumeration.
