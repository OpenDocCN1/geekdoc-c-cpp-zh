

- 一个标志位，指示该进程是否属于 Windows 应用程序（以便 Csrss 能够决定是否显示启动光标）
- UI 语言信息
- DLL 重定向和 .local 标志（在 SDK 手册后后的“映像加载器”部分进行了讨论）
- 清清单文件

当接收到此消息时，Windows 子系统执行以下步骤：

- 1. CsCreateProcess 为进程和线程复制一个句柄（handle）。在这种情况下，进程和线程的引用计数从 1（在创建时设置）增加到 2。
- 2. 分配 Csrss 进程结构 (CSR_PROCESS)。
- 3. 将新进程的异常端口设置为 Windows 子系统的通用函数端口，这样当进程中发生第二次机会异常时，Windows 子系统将接收到消息。（有关异常处理的信息，请参阅第 2 部分的第 8 章。）
- 4. 如果要以新进程为根创建一个新的进程组（CreateProcess 中的 `CREATE_NEW_PROCESS_GROUP` 标志），则在 CSR_PROCESS 中进行设置。进程组用于向共享控制台的一组进程发送控制事件。更多信息请参阅 Windows 关于 CreateProcess 和 GenerateConsoleEvent 的文档。
- 5. 分配并初始化 Csrss 线程结构 (CSR_THREAD)。
- 6. CsCreateThread 将线程插入进程的线程列表。
- 7. 该会话中的进程计数增加。
- 8. 将进程关机级别设置为 0x280，即进程默认关机级别。（更多信息请参阅 Windows SDK 文档中的 SetProcess-ShutdownParameters。）
- 9. 将新的 Csrss 进程结构插入到 Windows 子系统全局范围的进程列表中。

在 Csrss 完成这些步骤后，CreateInternal 会检查进程是否已运行（这意味着它是在向用户显示同意对话框后，通过 ShellExecute 和 AppInfo 服务执行的）。这包括检查该进程是否为安装程序。如果是，则打开进程并开启虚拟化，以便对应用程序进行虚拟化处理（参阅第 7 章关于虚拟化的信息？）。如果应用程序包含提升切换（elevation shifts）或在它的清单文件中有请求的提升级别，则会销毁进程并向 AppInfo 服务发送提升请求。

请注意，大多数这些检查不会对保护进程执行。由于这些进程必须是为 Windows Vista 或更高版本设计的，因此没有理由它们需要提升、虚拟化或应用程序兼容性检查和处理。此外，允许 shim 引擎在保护进程上使用其常用的钩（hooking）和内存补丁技术，如果有人发现如何插入修改保护进程行为的代码，会导致安全漏洞。

## 第 3 章 进程与作业 147

# 第 6 阶段：启动初始线程的执行

此时，进程环境已经确定，线程资源已分配，进程已拥有一个线程，并且 Windows 子系统已获知新进程。除非调用者指定了 `CREATE_SUSPENDED` 标志，否则初始线程现在将恢复，以便它可以开始并在新进程上下文中执行剩余的进程初始化工作（第 7 阶段）。

# 第 7 阶段：在新进程上下文中执行进程初始化

新线程开始运行内核态线程例程 KiStartThread。KiStartThread 将 IRQL 从延迟过程调用 (DPC) 降低到 APC 级别，然后调用系统初始线程例程 PspUserThreadStartup。将用户指定的线程起始地址作为参数传递给此例程。PspUserThreadStartup 执行以下操作：

- 它在 x86 架构上安装异常链。（其他架构在此方面的机制不同，请参阅第 2 部分的第 8 章。）
- 它将 IRQL 降低到 PASSIVE_LEVEL（这是用户代码允许运行的唯一 IRQL）。
- 它禁用运行时交换进程上下文的能力。
- 如果线程在启动时被杀死（无论出于什么原因），将被终止且不再采取后续操作。
- 它根据内核态数据结构中的信息在 TEB 中设置区域设置 ID 和理想处理器，然后检查线程创建是否真的失败。
- 它调用 DbgCreateThread，该函数会检查是否向新进程发送了通知。如果未发送且启用了通知，则会先向进程发送映像通知，然后针对 Ntdll.dll 的映像加载发送通知。

> 注意：这是在这个阶段完成的，而不是在映像首次映射时完成的，因为此时尚未分配内核调用所需的进程 ID（process ID）。

- 一旦完成这些检查，将进行另一项检查，以查看进程是否为调试器。如果是调试器且尚未发送调试器通知，则将通过调试器对象（如果存在）发送创建进程消息，以便将进程调试事件 (`CREATE_PROCESS_DEBUG_INFO`) 发送到适当的调试器进程。随后是线程调试事件以及针对 Ntdll.dll 映像加载的另一个调试器事件。DbgCreateThread 然后等待调试器的响应（通过 `ContinueDebug` 函数）。
- 8. 它检查系统是否启用了应用程序预取，如果是，则由预取器（以及 Superfetch）处理该进程上一次运行期间前 10 秒内引用的预取指令文件（如果存在）并预取页面页。（有关预取器和 Superfetch 的详情，请参阅第 5 章。）
- 9. 它检查 SharedUserData 结构中的系统级 cookie 是否已设置。如果没有，它将生成一个系统信息的哈希值，例如处理的中断次数、DPC 交付、缺页错误、中断时间和随机数。此系统级 cookie 用于指针的内部解码和编码（例如在堆管理器中），以防止几类利用。（有关堆管理器安全的更多信息，请参阅第 5 章。）
- 10. 如果进程是安全的（IUM 进程），将调用 Hv1StartSecureThread，该函数控制安全内核启动线程执行。此函数仅在线程退出时才返回。
- 11. 它将初始线程上下文设置为映像加载器初始化例程（Ntdll.dll 中的 `LdrInitializeThunk`）以及系统级线程启动（Ntdll.dll 中的 `LdrUserThreadStart`）。这些步骤通过编辑进程中的线程内容并使用系统退出操作完成，该操作会加载特殊构造的用户上下文。LdrInitializeThread 初始化加载器、堆管理器、N 表、线程本地存储 (TLS) 和纤线程本地存储 (FLS) 数组，以及关键节结构。然后它加载所有 DLL 并带带有 `DLL_PROCESS_ATTACH` 函数代码调用 DLL 入口点。

一旦函数返回，NtContinue 将恢复新的用户上下文并返回用户态。线程执行现在开始。

RtUserThreadStart 使用实际映像入口点的地址和起始参数，并调用应用程序的入口点。这两个参数已经由内核推入堆栈中。这一系列复杂的事件有两个目的：

- 它允许 Ntdll.dll 内部的加载器在内部和后台设置好进程，以便其他用户态代码可以正常运行（否则，它将没有堆、线程本地存储等）。
- 让所有线程从一个公共路径开始，允许它们被封装在异常处理中，以便当它们崩溃时，Ntdll.dll 能感知并在 Kernel32.dll 内部处理未处理的异常。应用程序开发者也可以设置 SetUnhandledException 来添加自己的未处理异常处理代码。
