conditions that the pager must recognize when the I/O completes are exposed:

+   - Another thread in the same process or a different process could have faulted the same page

The pager handles these conditions by saving enough state on the thread's kernel stack before
paging the I/O request when the request is complete, it can detect these conditions, and
necessary, dismiss the page fault without making the page valid. When and if the faulting instruction is
issued, the pager is again invoked and the PTE is reevaluated in its new state.

# Collided page faults

The case when another thread in the same process or a different process faults a page that is cur-
ently in-paging is known as a collided page fault. The pager detects and handles collided page
faults optimally they are common occurrences in multithreaded systems. If another
rocess faults the same page, the pager detects the collided page fault, noticing that the page is
transition and that a read is in progress.(This information is in the PFN database entry.) In this,
pager may wait a operation on the event specified in the PFN database entry. Alternatively, it
choose to issue a parallel I/O to protect the file systems from deadlocks. (The first I/O to complete
"wins", and the others are discarded.) This event was initialized by the first thread that issued the I/O
needed to resolve the fault.

When the I/O operation completes, all threads waiting on the event have their wait satisfied.
the first thread to acquire the PFN database lock is responsible for performing the in-page completion
operations. The operations consist of checking I/O status to ensure that the I/O operation completed
successfully, clearing the read-in-progress bit in the PFN database, and updating the PTE.

When subsequent acquire the PFN database lock to complete the collided page fault, the
pager recognizes that the initial updating has been performed because the read-in-progress is clear
and checks the in-page error flag in the PFN database element to ensure that the in-page I/O completed
successfully. If the in-page error flag is set, the PTE isn't updated, and an in-page error exception is
raised in the faulting thread.

# Clustered page faults

The memory prefetches large clusters of pages to satisfy page faults and populate the system
cache. The fetch operations read directly into the system's cache instead of a work-
set in virtual memory. Therefore, the prefetched data does not consume virtual address space, and
t size of the fetch operation is not limited to the amount of virtual address space that is available.
