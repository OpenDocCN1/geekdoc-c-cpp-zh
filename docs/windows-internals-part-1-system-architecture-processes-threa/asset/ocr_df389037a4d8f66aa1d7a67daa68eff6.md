# The IoCompletion object

Applications use the IoCompletion execution object, which is exported to the Windows API as a completion port, the focal point for the completion of I/O associated with multiple handles. Once a file is associated with a completion port, any asynchronous I/O operations on the file result in a completion packet being queued to the completion port. A thread can wait for any outstanding I/Os to complete on multiple files by waiting for a completion port to be queued to the completion port. The Windows API provides similar functionality with the WaitMultipleObjects function, but completion ports have one important advantage: concurrency. Concurrency refers to the number of threads that an application has actively serving client requests, which is controlled with the aid of the system.

When an application creates a completion port, it specifies a concurrency value. This value indicates the maximum number of threads associated with the port to be running at any given time. As stated earlier, the ideal is to have one active at any time for every process in the system. Windows uses the concurrency value associated with a port to control how many threads have active status. If the number of active threads associated with a port equals the concurrency value, a thread that is waiting on the completion port won't be allowed to run. Instead, an active thread will finish processing its current request, after which it checks whether another packet is waiting at the port. If one is, the thread simply grabs the packet and goes off to process it. When this happens, there is no context switch, and the CPUs are utilized to their full capacity.

# Using completion ports

Figure 6-24 shows a high-level illustration of completion-port operation. A completion port is created with a call to the CreateCompletionPort API function. A thread that blocks on a port becomes active and is awakened in last, first out (LIFO) so that the thread blocked most is the one that is given the next packet. Threads that block for long periods of time can have their stacks swapped out to disk, if there are more threads associated with a port than there is work to process, the in-memory footprints of threads blocked are minimized.

A server application will utilize client requests via network endpoints that are identified by file handles. Examples include Windows Sockets 2 (Winsock2) or named pipes. As the server creates its endpoints, it associates them with a completion port and its threads for incoming requests by calling GetQueuedCompletionStatus(Ex). When a thread is given a packet from the completion port, it will go off and start the request, becoming an active thread. A thread will block many times during its processing, as it needs to read or write data to a file on disk or it synchronizes with other threads. Windows detects this activity and recognizes that the port has one less active thread. Therefore, when a thread becomes inactive it blocks, a thread waiting on the completion port will be awakened if there is a packet in the queue.
