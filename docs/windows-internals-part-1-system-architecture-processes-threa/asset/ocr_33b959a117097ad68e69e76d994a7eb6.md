The input structure also provides an optional event handler that can be passed in, and if signaled (by another thread), will abort the page combining. Currently, the SuperFetch (see the section "SuperFetch" at the end of this chapter for more information) has a special thread, running in low priority (4) that initiates memory combining for the entire system partition when the user is active, or if the user is busy, every 15 minutes.

In the Creators Update, if the amount of physical memory is higher than 3.5 GB (3584 MB), built-in Svchost hosts a single service in each Svchost process. This creates dozens of processes out of the box but the likelihood of one service affecting another (either because of instability or security issues). In this scenario, the Service Control Manager (SCM) uses one of the memory combining API, and initiates page combining in each of the Svchost processes every three minutes by utilizing a page pool timer running with base priority of 6 (ScPerfCombineImages routine). The rationale is to reduce RAM consumption that may be higher with few Svchost instances. Note that non-Svchost services are not page combined, nor are services with per-user or private user accounts.

The MiIdent is the actual entry point to the page combining process. For each NUMA node of the memory partition, it allocates and stores a list of pages with each CRC inside the page combining support (PCS) structure, which is the one managing all the needed information for the page combining operation. The request is then to run on CPUs belonging to the NUMA node, and its affinity is modified if needed. We divide the memory combining algorithm into three stages to simplify the explanation: search, classification, and page sharing. The following sections assume that a complete page combining is requested (rather than the current process) and for all pages (not just the common pages); the other cases are similar in principle, and somewhat simpler.

# # The search phase

The goal of this initial stage is to calculate the CRC of all the physical pages. The algorithm analyses each physical page that belongs to the active, modified, standby list, skipping the zeroed and free pages (since they are effectively unused).

A good candidate for memory combining should be an non-shared page that belongs to a working set, and should not map a paging structure. The candidate could even be in the standby or modified state, but needs to have a reference counter of 0. Basically, the system identifies three types of pages for combining: user process, page pool, and session space. Other types of pages are skipped.

To correctly calculate the CRC of the page, the system should map the physical page to an address (because the process context is vastly different from the calling thread, making the page inaccessible in lower-mode (address views)) using a new system PTE. The CRC of the page is then calculated with a customized algorithm (MiComputeHash64 routine), and the system PTE freed (the page is now unmapped from system address space).
