# Hints for Analyzing Problems

Unfortunately, analyzing real-world problems is not as easy as analyzing the problems found in a textbook. The analysis step is the most difficult of the problem-solving steps, and it requires a lot of time, patience, and effort. If you are having trouble analyzing a problem, try reading the problem several times, as it is easy to miss information during the first reading. If the problem is still unclear to you, do not be shy about asking the user for more information. Remember, the more you understand a problem, the easier it will be for you to write a correct and efficient solution.

When reading a problem specification, it helps to use a pencil to lightly cross out the information you feel is unimportant to the solution, as shown in Figure 2-6. Doing this reduces the amount of information you need to consider in analysis. If you are not sure which item of information is important, ask yourself this question: If I didn't know this information, could I solve the problem? If your answer is Yes, then the information is superfluous and you can ignore it. If you find later that the information is important, you can erase the pencil line.

# Step 2—Plan the Algorithm

As a programmer, it is important to distinguish between information that is truly missing in the problem specification and information that is simply not stated, in the problem specification—that is, information that is implied. For example, consider the problem specification shown in Figure 2-8. To solve the problem, you need to calculate the area of a rectangle; you do this by multiplying the rectangle's length by its width. Therefore the area is the output, and length and width are the input. Notice, that the words length and width do not appear in the problem specification. Although both items are not stated explicitly in the problem specification, neither is considered missing information. This is because the formula for calculating the area of a rectangle is common knowledge. (The formula can also be found in any math book or on the Internet.) With practice, you will be able to “fill in the gaps” in a problem specification.

# Step 2—Plan the Algorithm

The second step in the problem-solving process is to plan the algorithm that will transform your input into its output. Record the algorithm in the Processing column of the IPO chart. Each instruction in the algorithm will describe an action that the computer needs to take. Therefore, each instruction should start with a verb. Most algorithms begin with an instruction to enter the input items into the computer. Next, you usually record instructions to process the input items to achieve the problem's output. The algorithm in Figure 2-9 is composed of short English sentences, referred to as pseudocode. The word pseudocode means false code. It's called false code because although it represents programming language instructions, pseudocode cannot be understood by a computer. Programmers use pseudocode to help them while they are planning an algorithm. It allows them to jot down ideas using a human-readable language without worrying about the syntax of the programming language. The pseudocode is used as a guide when the programmer codes the algorithm. Coding the algorithm is the fourth step in the problem-solving process and is covered in Chapters 3 and 4. Pseudocode is standardized; every programmer has his own version, but you will find similarities among the various versions. Although the word pseudocode may be unfamiliar to you, think about the last time you gave directions to someone. You wrote down each direction on paper, in your words. Your directions were a form of pseudocode.

Besides pseudocode, programmers use flowcharts when planning algorithms. Unlike pseudocode, a flowchart uses standardized symbols to visually depict an algorithm. You can draw the flowchart by hand; or use the drawing and features in a word processor. You can use a flowchart program, such as SmartDraw or Visio.
