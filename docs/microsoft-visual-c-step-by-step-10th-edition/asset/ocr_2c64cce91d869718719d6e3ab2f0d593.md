```
j = i;
doAddAdditionalProcessing();
data[i] = j;
doMoreAdditionalProcessing();
```

The code looks innocuous enough. This method copies the current value of the loop i (the index identifying which iteration of the loop is running) into the variable j, and later it stores the value of j in the element of the data array indexed by i. If i contains 5, j is assigned the value 5, and later the value of j is stored in data[5]. But between assigning the value to j and later reading it, the code does more work: it calls the doAdditionalProcessing method. If this method takes a long time to execute, the runtime might suspend the thread and schedule another task. A concurrent task's running another iteration of the Parallel.For construct might run and assign a new value to j. Consequently, when the original task resumes, the value of j is not the value stored, and the result is data corruption. More troublesome is that sometimes this code might run as expected and produce the correct results, but at other times it might not; all depends on how busy the computer is and when the various tasks are scheduled. Consequently, these types of bugs can lie dormant during testing and then suddenly manifest in a production environment.

The variable j is shared by all the concurrent tasks. If a task stores a value in j and later reads it, it must ensure that no other task has modified j in the meantime. This requires synchronizing access to the variable across all concurrent tasks that can access it. One way you can achieve synchronized access is to lock data.
