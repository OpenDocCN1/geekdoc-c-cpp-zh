
Despite the change in the data binding to two-way mode, the email address displayed in the narrow view hasn't been updated; it's still john@contoso.com.

Clearly, nothing is working correctly! The problem now is that the data hasn't been updated but rather the view isn't displaying the latest version of the data. If you reinstate the breakpoint in the set accessor for the EmailAddress property of the Customer class and run the app in the debugger, you'll see the debugger reach the breakpoint whenever you change the value of the email address and move the focus away from the TextBox control. Despite appearances, the data-binding process is not magic, and a data binding doesn't know when the value to which it has bound changed. The object needs to inform the data binding of any modifications by sending a PropertyChanged event to the UI. This event is part of an interface named INotifyPropertyChanged, and all objects that support two-way data binding should implement this. You'll implement this interface in the next exercise.

## The nameof demonstrated in the Customer class is a little-used

The nameof operator is a little-used valuable feature of C# in code such as this. It returns the name of the variable passed in as its parameter as a string. Without using the nameof operator, you've had to use hard-coded string values. For example:

Click here to view code image

```csharp
public int CustomerID
{
    get { return this._customerID; }
    set
{
        this._customerID = value;
    }
}
```

Although using string values requires less typing, consider what would happen if you needed to change the property at some point. Using the string approach, you'd need to change the string as well. If you change the property but forget to change the argument, the code would still compile but the value would not be notified, leading to difficult-to-find bugs. If you use the nameof operator, the code won't compile, alerting you immediately to an error.

## Using data binding with a ComboBox control

Using data binding with a control such as a TextBox or TextBlock is relatively straightforward. On the other hand, ComboBox controls require a little more attention. The issue is that a ComboBox control actually displays two things:

- A list of values in the dropdown list that the user can select from
- The value of the currently selected item

If you implement data binding to display a list of items in the dropdown list of a ComboBox control, the value that the user selects must be member of this. In the Customers app, you can configure data binding for the selected value in the title ComboBox control by setting the SelectedValue property, like this:

Click here to view code image

```xml
<ComboBox ... x:Name="title" ... SelectedValue="{Binding Title}" ... />
```

However, remember that the list of values for the dropdown list is hard coded into the XAML markup, like this:

Click here to view code image

```xml
<ComboBox ... x:Name="title" ...>
  <ComboBoxItem Content="Mr"/>
  <ComboBoxItem Content="Mrs"/>
  <ComboBoxItem Content="Ms"/>
  <ComboBoxItem Content="Miss"/>
</ComboBox>
```

This markup is not applied until the control has been created, so the value specified by the data binding is not found in the list because the list does not yet exist when the data binding is constructed. The result is that the value is not displayed. You can try this if you like—configure the binding for the SelectedValue property as shown and run the app. The title ComboBox will be empty when it's initially displayed, despite the fact that the customer has the title of Mr.

There are several solutions to this problem, but the simplest is to create a data source that contains the list of valid values and specify that the ComboBox control should use this list as its set of values for the dropdown. Also, you need to do this before the data binding for the ComboBox control is applied.
