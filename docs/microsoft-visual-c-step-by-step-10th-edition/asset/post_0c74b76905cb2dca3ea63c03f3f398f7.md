This level of abstraction was a deliberate design decision on the part of the Microsoft development team, and it removes the need for you to understand the low-level threading and scheduling details when you build applications that require concurrent tasks. But this abstraction comes at a cost. Although it all appears to work magically, you must make some effort to understand how your code runs; otherwise, you can end up with applications that exhibit unpredictable (and erroneous) behavior, as shown in the following example. (This sample is available in the ParallelTest project in the folder containing the code for this chapter.)

```csharp
using System;
using System.Threading;
class Program
{
    private const int NUMELEMENTS = 10;
    static void Main(string[] args)
    {
        SerialTest();
    }

    static void SerialTest()
    {
        int[] data = new int[NUMELEMENTS];
        int j = 0;
        for (int i = 0; i < NUMELEMENTS; i++)
        {
            j = i;
            doAdditionalProcessing();
            data[i] = j;
            doMoreAdditionalProcessing();
        }
    }

    for (int i = 0; i < NUMELEMENTS; i++)
    {
        Console.WriteLine($"Element {i} has value {data[i]}");
    }
}
```

```csharp
static void doAdditionalProcessing()
{
    Thread.Sleep(10);
}
static void doMoreAdditionalProcessing()
{
    Thread.Sleep(10);
}
```

The SerialTest method populates an integer array with a set of values (in a long winding way) and then iterates through this list, printing the index of each item in the array together with the value of the corresponding item. The doAdditionalProcessing and doMoreAdditionalProcessing methods simply simulate the performance of long-running operations as part of the processing that might cause the runtime to yield control of the processor. The values assigned to each item in the data array are not always the same as those generated by SerialTest method. Additionally, further runs of ParallelTest method can produce different results. If you examine the logic in Parallel.For construct, you should see where the problem lies. The lambda expression contains the following statements:

Click here to view image

```csharp
j = i;
doAdditionalProcessing();
data[i] = j;
doMoreAdditionalProcessing();
```

The code looks innocuous enough. This method copies the current value of the loop (identifying which iteration of the loop is running) into the variable j, and later stores the value of j in data[i]. But between assigning the value to j and later reading it, the code does more work: it calls doAdditionalProcessing. If this method takes a long time, the runtime might suspend the thread and schedule another task. Another iteration of Parallel.For construct might run and assign a new value to j. Consequently, when the original task resumes, the value of j is not the value stored. More troublesome is that sometimes this code might run as expected and produce the correct results, but at other times it might not; depends on how busy the computer is and when various tasks are scheduled. Consequently, these types of bugs can lie dormant during testing and then suddenly manifest in a production environment. The variable j is shared by all concurrent tasks. If a task stores a value in j and later reads it, it must ensure that no other task has modified j in the meantime. This requires synchron access to the variable across all concurrent tasks. One way you can achieve synchronized access is to lock data.

# Locking data

The C# language provides locking semantics through the lock keyword, which you can use to guarantee exclusive access to resources. You use the lock keyword like this:

Click here to view image

```csharp
object myLockObject = new object();
...
lock (myLockObject)
{
  // Code that requires exclusive access to a shared resource
  ...
}
```

The lock object attempts to obtain mutual-exclusion lock over the specified object (you can actually use any reference type, not just object), and it blocks execution if same object is currently locked by another thread. When the thread obtains the lock, the code following the lock statement runs. At the end of this block, the lock is released. If another thread is blocked waiting for the lock, it can then grab the lock and continue its processing.

# Synchronization primitives for coordinating tasks

The lock keyword is fine for many simple scenarios, but in some situations, you might have complex requirements. The System.Threading namespace includes some additional synchronization primitives that you can use to address these situations. These synchronization primitives are classes designed for use with tasks; they expose locking mechanisms that restrict access to a resource while a task holds the lock.

These primitives support a variety of locking techniques that you can use to implement different styles of concurrent access, ranging from simple exclusive locks (where a single task has sole access to a resource), to semaphores (where multiple tasks can access a resource simultaneously but in a controlled manner), to reader/writer locks (which enable different tasks to share read-only access to a resource while guaranteeing exclusive access to a thread that needs to modify the resource). # ManualResetEventSlim

The ManualResetEventSlim class provides functionality by which one or more tasks can wait for an event. A ManualResetEventSlim object can be in one of two states: signaled(true) and unsignaled(false). A task creates a ManualResetEventSlim object and specifies its initial state. Other tasks can wait for the ManualResetEventSlim object to be signaled by calling the Wait method. If the Wait method blocks the tasks, another task can change the state of the ManualResetEventSlim object to signaled by calling the Set method. This action releases all tasks waiting on the ManualResetEventSlim object, which can then resume. The Reset method changes the state of the ManualResetEventSlim object back to unsignaled.

# SemaphoreSlim

You can use the SemaphoreSlim class to control access to a pool of resources. A SemaphoreSlim object has an initial value (non-negative) and an optional maximum value. Typically, the initial value of a SemaphoreSlim object is the number of resources in the pool. Tasks accessing the resources in the pool first call the Wait method. This method attempts to decrement the value of SemaphoreSlim object. If the result is nonzero, the thread is allowed to continue and can take a resource from the pool. When it has finished, the task should call the Release method on the SemaphoreSlim object. This action increments the value of the SemaphoreSlim.
