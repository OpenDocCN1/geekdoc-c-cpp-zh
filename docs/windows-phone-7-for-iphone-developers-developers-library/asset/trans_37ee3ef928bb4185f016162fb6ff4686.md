
“我们得调用Web服务！”他们恳求道。“根本无法孤立地测试这段代码！”他们抱怨道。这些实际上都是对编写单元测试尝试的非常有建设性的回应。当你听到自己说这些话时，你就知道需要进行一些重构了。你需要重构代码，使其变得可模拟（mockable）。

可模拟的类是与依赖项松散耦合的类。在理想情况下，所有依赖功能都由符合接口或契约的类执行。在更理想的情况下，这些依赖的实现会在运行时通过构造函数、属性，或在许多情况下通过控制反转（IoC）框架（如Castle Windsor或Microsoft Unity）提供给类。

IoC框架的工作是查看一个类，找出所有依赖项（符合配置文件中引用的接口的属性或构造函数参数），并注入该依赖的适当实现。这些框架通常可以配置为在运行时注入真实实现，在测试时注入模拟实现。

因为，在撰写本书时，由于Windows Phone 7在反射方面的限制，我无法让依赖注入或控制反转框架在其上正常工作，所以我们不得不以老式方式创建模拟：编写它们。

假设你想为一个名为TaxHandler的类创建单元测试。该类接受一个产品的库存量单位（SKU）和投递邮政编码，并返回一个十进制数，表示该商品应收取的销售税。

作为第一反应，我们可能会创建一个名为TaxHandler的类。在这个类内部，包含一个名为InventoryClient的Web服务代理，它与库存服务通信以获取完整的定价信息。此外，另一个名为TaxClient的Web服务代理与公司的内部税务服务通信，获取特定邮政编码的销售税率。TaxHandler类在ComputeTax方法中调用这两个客户端，该方法接收产品SKU和邮政编码作为参数。

当我们为这个应用编写单元测试时，我们可能会手动去弄清楚邮政编码90210的销售税率，计算出价格99.99美元产品的税额，然后运行ComputeTax方法。我们的断言是返回值与预期值匹配。作为优秀的小开发人员，我们随后会再写两个测试：一个验证错误的值不会匹配实际输出（例如，我们故意将预期设置错误并断言失败，从而创建一个通过的测试），另一个测试使用完全伪造的参数，如无效的邮政编码。我们在这里的断言是会抛出异常。当该异常被抛出时，我们的测试通过。

我们运行测试，稍等片刻后，得到绿灯。那么问题出在哪里？我们得到了绿灯，所以根据“红灯、绿灯、重构”规则应该没问题，对吧？错。每次执行这个测试，我们都在向两个不同的Web服务发出两次网络调用。我们测试ComputeTax方法的目的不是测试Web服务，而只是测试ComputeTax方法是否使用我们指定的参数调用了这些Web服务。这起初有点难以接受。单元测试的目的是*孤立地*（例如，作为一个单元）测试每小段代码。我们必须假设另一套单元测试已经证明了每个Web服务都按预期工作。因此，我们需要模拟这些客户端，以便我们的单元测试不会离开逻辑区域，更不用说跨越整个应用程序层级了。

如果我们修改TaxHandler类的构造函数，使其不再创建具体的Web服务客户端代理实例，而是接受实现契约的对象实例，会怎么样？这些契约可以对应Web服务的功能，但它们只是契约。现在实现由使用TaxHandler类的客户端决定。在我们的例子中，客户端要么是真实应用程序，要么是一套单元测试。

所以，在C#中，我们可能会将构造函数改为这样：

```
public TaxHandler(ITaxService taxService, IStockService stockService)
{
    this.TaxService = taxService;
    this.StockService = stockService;
}
```

现在，当客户端代码调用ComputeTax方法时，TaxHandler类将调用实现契约的对象上的方法。TaxHandler类与支持它的应用程序层的物理实现之间将不会有任何紧密耦合。

无论我们使用依赖注入框架来自动提供受配置控制的这些对象实例，还是我们的测试方法定义这些契约自己的实现，最终结果都是一样的：我们现在可以单独测试ComputeTax方法，并验证它是否按我们预期的方式工作——它会调用两次Web服务，并返回一个聚合结果的结果。

本章稍后我将向你展示更多的测试实现，并逐步讲解更多重构紧密耦合类的示例，以便将其依赖项剥离出来，使我们能够进行隔离测试。当我们想要测试像前一章中创建的视图模型类时，这尤其有用。

## 单元测试iOS应用程序

在iPhone开发的早期，Xcode中随附的用于桌面Mac开发的单元测试框架SenTest在iPhone上无法正常工作。然而，随着iOS SDK的更新版本，单元测试功能已直接内置于Xcode中，适用于你的任何iOS项目。幸运的是，你无需安装任何额外软件，也无需进行任何额外配置。正如你将在本章后面看到的，在单元测试领域，微软有点“初版病”（v1-itis），其工具的第一个版本在TDD和单元测试的内置支持方面还不够成熟。

Xcode中的单元测试支持基于开源单元测试框架SenTestingKit。该框架具有类和命令行工具，可帮助你构建自动化测试，并理想情况下在iOS应用中拥抱TDD。

你可以在iOS中编写两种不同类型的单元测试：逻辑测试或应用程序测试。通常，你可以将逻辑测试视为我们可能认为的传统单元测试，而应用程序测试则可视为集成测试或UI自动化测试。

## 逻辑测试

要在你的iOS应用程序中设置逻辑测试，你需要创建一个新目标。我喜欢在目标名称末尾加上后缀“Test”（或者更好的是“LogicTest”），这样我可以快速轻松地确定目标的用途，而无需依赖备忘单。过去，我遇到过Xcode应用有太多不同目标的情况，我不得不在附近放一张纸，说明每个目标及其用途。如果你作为iOS开发者遇到这种情况，要知道如果你继续走这条路，你可能会在时空结构本身撕裂一个洞。

创建逻辑测试目标包后，将其设置为活动目标。接下来，通过选择“文件”、“新建文件”菜单选项，并从可用模板中选择“iOS”、“Cocoa Touch Class”、“Objective-C测试用例类”来创建一个新文件。无论我是为iOS还是WP7编写测试，我都更喜欢为单个目标类使用单个测试类。换句话说，如果我有一个名为Porsche的类并且想测试它，我会创建一个名为PorscheTests或PorscheLogicTests的单个测试类。清空类头文件，使其包含一个空接口，如下所示：

```
#import <SenTestingKit/SenTestingKit.h>
#import <UIKit/UIKit.h>

@interface PorscheLogicTests : SenTestCase {
}
@end
```

接下来，清空实现，只保留一个通过的测试方法，如下所示：

```
#import "PorscheLogicTests.h"

@implementation PorscheLogicTests
- (void) testPassesAlways {
    STAssertTrue(TRUE, @"This test always passes.");
}
@end
```
