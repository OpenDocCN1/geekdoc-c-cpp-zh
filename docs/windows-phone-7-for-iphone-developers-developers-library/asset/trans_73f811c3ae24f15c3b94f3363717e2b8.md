

CLR（以及通过它，C#）做的事情叫做 *根计数*。每当你在托管堆上使用强引用创建一个对象（作用域内的一个变量包含指向该新对象的指针）时，运行时会跟踪该实例化。在内存中，它维护着一个对象根的图。因此，你可能有一个 Car 对象，其中包含一个指向 Wheel 对象的成员变量，而 Wheel 对象又包含一个指向 Brakepad 对象的成员变量，依此类推。CLR 知道从 Car 对象到 Brakepad 对象存在一条根路径。

如果在应用程序运行时，变量 `myBrakePad`（它曾持有对 `BrakePad` 类实例的引用）被设为 null，那么 `myBrakePad` 变量曾经指向的对象就会成为孤立对象。换句话说，不再有从任何“存活”对象到该新孤立对象的根路径。这意味着该对象将被垃圾回收，*但不一定立即进行。*

在它选择的时间（一种过于复杂且超出本章范围的算法），CLR 的垃圾收集器会遍历托管堆。在此过程中，它会发现 `BrakePad` 类的实例正孤零零地躺在那里没有任何根（没有“存活”对象直接或间接引用该对象）。这时垃圾收集器会决定最终释放与该对象关联的内存。

## Garbage Collection in Depth

如果你真的想了解 CLR 中针对 Silverlight 或桌面和服务器运行时垃圾收集器的工作原理的来龙去脉，你应该查阅以下书籍：*Essential .NET, Volume I - The Common Language Runtime*，作者 Don Box 和 Chris Sells。这是一本较老的书，但它对垃圾收集器工作原理的介绍是无与伦比的。

我认为在这里暂停一下，让这些内容沉淀下来是合适的；C 和 C++ 程序员在这个阶段常常会非常困惑，因为这与他们习惯的内存释放方式不同。这也为下一节关于终结化的内容提供了很好的引子。

CLR 中的垃圾收集是一个异步过程，完全独立于应用程序正在执行的操作。会尽一切努力推迟垃圾收集事件，直到合适的、最好是空闲的时刻。然而，如果堆已满，CLR 将执行一次垃圾收集（GC）遍历。GC 遍历对应用程序本身要求极高，在 GC 遍历期间性能可能会大幅下降。

我之所以提到这一点并如此强调，是因为在用 .NET 构建桌面应用程序，甚至 Silverlight 应用程序（它们仍然运行在桌面处理器和桌面内存上）时，开发人员常常忘记垃圾收集器的存在。事情只是正常工作，而且通常工作得相当好，所以很少有人会停下来思考优化内存使用的问题。对于移动开发者来说，这变得更加重要，因为一次特别长且耗费的 GC 遍历可能会导致你的应用卡住并在几秒钟内停止响应。

下面的列表包含了一些你在构建 WP7 应用程序时应牢记在心的事项，以使其尽可能对 GC 友好：

- 移动应用程序的一个简单规则：不要持有不需要的内存。不要在不需要时创建任何实例的实例。如果你来自桌面开发的世界，“对象很便宜”，这个习惯可能特别难以打破。
- 大数据很容易分配，垃圾回收却很慢。务必确保你没有保留对应用程序当前不需要的东西的引用。所说的“大”不仅仅指字节大小，我指的是图复杂度。如果你有一个对象指向另一个对象，再指向另一个对象，等等，这会增加需要跟踪的根的数量，并在该对象被收集时增加在收集遍历期间需要遍历的根路径的数量。
- 尽量将抖动降到最低：不要在一个循环中实例化一堆东西，然后将它们的引用设为 null，然后再实例化更多东西。所说的“抖动”是指在短时间内产生大量孤立对象。一次包含几千个小对象的 GC 遍历可能与一次针对大型对象图的 GC 遍历一样耗费。
- 分析你的应用。Visual Studio 内提供了一系列工具（超出本书范围，但该主题的参考资料和书籍比比皆是），可让你分析你的应用程序以及应用程序的堆性能。你甚至可以观察收集遍历发生的时机。不要跳过这一步。你可以在初始开发和原型设计阶段推迟它，但不要将应用推送到市场，除非你知道你的应用与堆相处融洽。

## Cleaning Up After Yourself—Object Finalization

终结化与垃圾收集的执行直接相关。在 C++ 等语言中，对象是通过所谓的确定性终结化来释放的。所有这一切真正意味着的是，当你“释放”或“释放分配”一个对象时，它就消失了。它在那个确切的时间点消失，并且在内存被回收之前还会调用一个名为终结器的清理方法。这不是 CLR 和 C# 的工作方式。

当一个对象超出作用域，或指向该对象的变量被设为 null 时，该对象最终将被垃圾回收。你绝对无法保证对象何时会被释放，也无法保证其释放的顺序。

C# 开发者经常利用一个名为 IDisposable 的接口（有关接口和类的更多内容将在下一章讨论）。当一个对象实现此接口时，意味着其 Dispose() 方法将在垃圾收集器回收该对象的内存之前由运行时调用。这给了你的对象一个机会，在爸爸发现它把乐高散落一地之前清理它造成的混乱。

我不会在本书记载太多关于构建可释放对象的细节，除非在举例说明其他示例时适当提及。如果你好奇所有这些是如何工作的，以及 C# 语言本身的其他详细机制，你可能想买一本 *C# 4.0 Unleashed*，作者 Bart De Smet。

## Finalization Order

运行时不保证标记为可释放的对象的终结化顺序。回到具有指向轮子对象的指针的汽车对象，而轮子对象又具有指向制动片对象的指针，你无法保证制动片对象会在轮子对象之前被释放。你甚至无法保证汽车对象会被最后释放。

如果你编写在对象被释放时执行的代码（记住，在被标记为收集之后某个任意时间），该代码绝不能访问也将被释放的成员变量，因为这样做可能会“重新唤醒”成员变量，短路收集过程，并阻止对象被收集，从而造成只有 iPhone 开发者才能真正欣赏的内存泄漏。看吧，有托管堆并不意味着你不能因内存问题而崩溃你的应用。

## Why OOP?

如果你正在阅读这本书，你可能不需要被说服面向对象编程是一件好事。然而，正如本章中 Bjarne Stroustrup 的引语所优雅地指出的那样——并非所有 OOP 都是好事。像任何工具一样，如果使用不当，它会让任何出于好意的项目变得一团糟。

我们创建类是为了将逻辑相关的数据和行为分组，所有这些都旨在执行特定任务。当这些类被正确编写时，它们体现了 OOP 的好处：提高重用性并创建可测试、可靠、可预测的应用程序，易于构建、易于维护、易于更改。

在移动设备上，我们有类封装了各种事物的信息和行为，从读取 GPS 坐标，到显示文本，到接受输入。如果没有一套精心设计的类来抽象设备的各种功能，我们将无法快速可靠地为该设备生产软件。
