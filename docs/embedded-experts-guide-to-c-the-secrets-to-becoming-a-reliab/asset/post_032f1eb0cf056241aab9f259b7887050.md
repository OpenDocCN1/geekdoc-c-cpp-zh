
Inline functions may be declared by qualifying the function definition with the keyword inline. An inline function is one which eliminates a function call by replacing the call with the body of the function. Qualifying a function with the inline keyword does not guarantee the replacement will take place; rather it serves as a hint to the compiler the programmer would like the replacement to take place if possible and the compiler may choose not to inline the function at all or to inline only in some instances. Inline functions are a good alternative to function-like macros and do not require the special precautions needed when writing macros. One disadvantage of inline functions is they can be difficult to resolve across translation units and this can lead to linker errors or unreachable code being. To avoid such problems, it may be best to limit the scope of every inline function to the translation unit in which it is defined by making it static. Furthermore, inlining, while potentially beneficial for code speed, can increase the size of the compiled code. Inlining is most beneficial for small helper functions which are called relatively frequently, where the overhead of a function call is comparable to the code of the function itself.

```
/* Square a number. Make the function inline so
 * the compiler knows it can omit the function
 * call. */
static inline square(int value)
{
return value * value;
}
```

Fig 9.3 - Declaring a function as inline hints to the compiler that, rather than generating a function call, the body of the function may be expanded and used in place of the function call. Inline functions can therefore be used as safe (both in terms of type-safety and the manner in which they are evaluated) alternatives to function-like macros. The compiler is not required to perform the inlining, furthermore, some compilers may be able to inline functions even when the inline qualifier is not used.

There are also two keywords which you might expect to improve performance, but which are more likely to create issues than resolve them and therefore better avoided. These are register and restrict.

The register keyword is one of the original storage classifiers included in the C. It indicates a variable should be stored in a way which allows the fastest possible access to the variable; in most cases, particularly on older systems, this is achieved by storing the variable in a CPU register. The compiler, however, is free to store the variable in main memory if it chooses. However, most modern compilers will store variables in registers wherever possible by default, so the keyword is effectively redundant and unlikely to result in any noticeable improvement to code performance. There is, however, one important side effect of qualifying a variable using the register keyword, since registers are not addressable in the same way as other memory, it is not possible to reference a variable using pointers. This is true whether the compiler ultimately places the variable in a register or in main memory. Given this restriction and the lack of any benefit in most cases, there is little reason to use the register keyword.

You may come across pointers qualified using the restrict keyword. The purpose of restrict is to indicate to the compiler, for the lifetime of the pointer, the restricted pointer is the only pointer used to access the referenced variable. Initially this would seem to be useful, since it allows the compiler to make optimisations which would not otherwise be possible, particularly in relation to loading and storing variables which could reside at the same memory location. Qualifying a pointer using restrict signals that it can be assumed the restricted pointer will never be aliased by another pointer. The problem is the compiler is not required to enforce the restriction in any way: it is entirely the programmer's responsibility to ensure the pointer is not aliased and failing to do so results in undefined behaviour. Several functions in the C Standard Library are defined using pointers, but the use of restrict is discouraged in user code because of the risks associated with it.

## Loops

The repetitive nature of loops makes them a good candidate for optimisation. Even a short loop run many times can slow a program down; in fact, short loops can often benefit the most from relatively simple optimisations. One of the most common optimisations is known as loop unrolling. Every loop iteration ends with a conditionally executed branch instruction back to the start of the loop (except for infinite loops, where the branch is unconditional); the idea of loop unrolling is to reduce the number of condition evaluations and jumps by combining multiple iterations into one. To do this, it is obviously necessary to know the total number of iterations which will be performed, or at least to know a factor of the number of iterations. Compilers can often be relied upon to perform loop unrolling; however, the programmer may have some knowledge about the number of iterations to be performed which is not necessarily available to the compiler, in which case, manual unrolling may be necessary. There may also be redundancy in the results of calculations performed during the iterations which can be exploited; these are unlikely to be known to the compiler, but the programmer should exploit them wherever possible.

```
/* Copy lemons into oranges. */
for (index = 0; LAST > index; ++index)
{
orange[index] = lemon[index];
}
/* The same loop unrolled, assuming the length
 * of the arrays is a multiple of four. */
for (index = 0; LAST > index; index += 4)
{
orange[index] = lemon[index];
orange[index + 1] = lemon[index + 1];
orange[index + 2] = lemon[index + 2];
orange[index + 3] = lemon[index + 3];
}
```

Fig 9.4 - Loops where the number of iterations is known can be completely unrolled – although for large loops this is probably impractical. Even where the total number of iterations is not known, unrolling may still be performed if some information regarding the total is known – in this example, the number of iterations is always a multiple of four. If the required information is available to the programmer but not the compiler, the unrolling must be done manually.

Even when a loop cannot be unrolled, there are often other optimisations which can be made. Expressions which do not change from one iteration to the next can be moved outside of the loop so they do not need to be repeatedly evaluated. Even though this may require the declaration of additional, temporary variables (which may well be stored in a register anyway), this can still result in a significant performance boost. Similarly, conditional statements which are evaluated within a loop can be moved outside the loop if the evaluation does not change between iterations. This can result in an increase in code, with similar loops appearing within if and else blocks, but can result in a substantial speed increase because the conditional statements are not being repeatedly evaluated within the loop.

Other restructurings of loops can also have a significant impact. A do ... while loop requires fewer jumps than an equivalent while loop; this may even be true if the do ... while loop must be wrapped in an if block to achieve the same result. Merging two loops which always iterate the same number of times but are otherwise independent of each other (or where any dependencies will not be affected by merging the loops), immediately halves the number of evaluations and jumps which must be performed. If a greater number of loops can be merged, then the number of evaluations and jumps will decrease proportionally. It may also occasionally be possible to improve performance of nested loops by swapping the inner and outer loops; such gains, however, are usually platform dependent and difficult to predict. Where possible, it can be useful to reduce the overhead associated with function calls within loops by moving the loop inside the function; this can significantly improve performance, since each function call adds at least two additional instructions (a call and return) and, usually, some manipulation of memory; alternatively, using inline functions within loops can avoid this additional overhead.
