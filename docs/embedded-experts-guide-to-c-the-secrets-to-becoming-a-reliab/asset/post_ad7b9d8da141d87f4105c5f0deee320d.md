
IO interrupts are used so any pieces of hardware can request a response from the processor. For instance, a keyboard may send an interrupt signal to indicate a key has been pressed and the keyboard buffer is ready to be read, or an emergency stop button may be connected directly to a non-maskable interrupt pin rather than through the same interface as other controls. It is not unusual for various pieces of hardware to share the same interrupt signal. In such cases, it is often necessary to arbitrate the interrupt signals so the source can be unambiguously identified or a decision can be made as to which interrupt to service first if they arrive simultaneously; this can be a far from trivial task and many dedicated hardware solutions have been produced to address the problem.

Microcontrollers and system-on-chip processors can respond to interrupts generated by on-chip peripherals. These behave in a similar fashion to generic IO interrupts, but occur within one piece of hardware. This often simplifies the software requirements associated with handling interrupts, since many more signals can be made available internally than are typically available on the chip package. On-chip timers and communication peripherals will have their own interrupt, eliminating the need for interrupt sharing or arbitration.

## When and how to use interrupts

Although interrupts are often used when a fast response to an event is required, invoking an interrupt service routine is often more expensive than a normal function call. The unpredictable timing of interrupts means it is essential for the code to save all processor registers before entering an ISR and to restore them after exiting – a process often referred to as context switching. Although this process may be required for a normal function call, there are some registers which do not need to be preserved during a function call (but do in the case of an event; with those which do need to be preserved, the compiler can often be more flexible or may even be able to eliminate the call entirely – this is simply not possible when invoking an ISR. The problem is worse when multiple interrupt sources share a single interrupt signal to the CPU, since there will be additional overhead incurred when determining which ISR to transfer control to. If an interrupt is triggered too frequently or if too many interrupts are used then the time spent switching between normal code and ISRs becomes significant – although it can be tempting to use interrupts to respond to every event, this does not always result in the performance benefits you might hope for.

Limiting the number of interrupts you use is a relatively straightforward way to reduce the overhead associated with them. Slow hardware can be periodically polled using a single timer interrupt rather than interrupting on each change of state. This is unlikely to cause issues; for example, although a user may expect an “immediate” response to a keyboard input, the average human’s idea of immediate is significantly less restrictive than a modern microprocessor’s and a few milliseconds delay will go completely. Similarly, whenever it is necessary to simply wait for a piece of hardware to be ready, using a busy-wait to poll the device may be preferable to an interrupt, particularly if demand for the resource is not high; this need not prevent the processor performing other useful tasks if multiple threads and an appropriate scheduler are used.

Interrupt service routines handle time-critical elements of a program and therefore should be kept short wherever possible. What is meant by “short” is application dependent; in real-time control applications, a timer interrupt may be used to measure an input before calculating and outputting a new output, yet in many other instances this would be an inappropriate amount of processing for a single ISR and the processing may be better offloaded to code running outside of the ISR. As a rule, an ISR should only perform what is absolutely necessary before returning control to the process it interrupted. A UART interrupt may only need to copy data from the UART buffer for instance; actual processing of the data can be deferred until it is required. Where possible, avoid loops and function calls within ISRs as these add additional overhead and loops in particular can introduce a degree of unpredictability into the interrupt timing. Minimising the time spent servicing interrupts prevents the processor from spending too much time in any single interrupt and helps to mitigate the disruption to normal processing caused by servicing interrupts; it also helps to reduce the risk of jitter – where events which are supposed to be periodic are not triggered at the correct time, often because some other process is blocking them.

In extreme cases, usually because of misconfigured software or hardware, an interrupt storm may occur. In these cases, most processor time is allocated to servicing interrupts and other processing progresses very slowly or not at all as a result. It is also possible for race conditions to arise, particularly where multiple interrupts are used concurrently. There are two types of race condition of interest:

- The first is determining the order in which simultaneous interrupts should be serviced; this is a complex problem, often addressed through specialised hardware, and the programmer may have limited control over how it is solved beyond changing interrupt priorities.
- The second type of race condition occurs when the order in which instructions are executed is important but can change dependant on when an interrupt occurs. Such a situation might arise if an interrupt which modifies a variable occurs when the same variable is being modified during normal program flow. The simplest solution is to identify the critical sections of code where such data can be modified and disable interrupts until the modification is complete. It would be better to avoid the situation entirely by only allowing variables to be shared in one direction between the ISR and main program (or between), although there is no way for the language itself to enforce this so it would be entirely the programmer's responsibility to do so.

## Callbacks

Related to interrupts are callbacks. Whereas an interrupt allows you to defer the decision of when to invoke a function to runtime, callbacks allow you to defer the decision of which function to call. Consider a calculator for instance; while you could use if ... else or switch statements to determine which operator to apply, you could also use callbacks for each operator and choose which to invoke when required; although there may not be much difference between a switch and a callback in this case, callbacks can be used to produce efficient and modular code which cannot be easily achieved using the more familiar conditional statements.

```
/* Define the available operators. */
typedef enum
{
op_add = 0,
op_subtract,
op_multiply,
op_divide
} operator_t;
/* The calculator function - using a
* switch/case. */
float calculate(operator_t operator, float lh_f, float rh_f)
{
float result_f= 0.0F;
switch (operator)
{
case op_add:
result_f= lh_f + rh_f;
break;
case op_subtract:
result_f= lh_f - rh_f;
break;
case op_multiply:
result_f= lh_f * rh_f;
break;
case op_divide:
result_f= lh_f / rh_f;
break;
default:
/* Do nothing. */
break;
}
return result_f;
}
```
