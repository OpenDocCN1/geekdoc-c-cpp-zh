
Although there is a degree of overlap between the two topics, it is important to distinguish between them. Integrity is important to any system where data errors may cause unwanted or potentially dangerous behaviour; the data need not be sensitive and there may be no need for such a system to be secure. Conversely, a secure system may not always need to pay close attention to data integrity even when that data may be regarded as sensitive. However, the two often go hand-in-hand and many of the methods used to ensure data integrity are also useful in ensuring its security.

## Data encoding

Before diving into a discussion of specialist methods used for ensuring the integrity of data, it is worth mentioning the need for data encoding. Many older communications protocols designed for connecting systems were not intended for transmitting arbitrary binary data; they expect to send and receive text, with certain character codes interpreted as control codes. Many assume 7-bit ASCII encoding (or default to it) and any arbitrary data must first be encoded to match. A considerable number of so-called binary-to-text encodings exist for this purpose. Although many newer protocols do not require such encodings, it is still worth having a basic understanding of them when setting up communications between systems; not only are the encodings still widely used to ensure compatibility but encoding data can also be useful when it needs to be mixed with control codes (to indicate the beginning and end of a stream, for instance).

One popular encoding is known as Base64. The basic principle, which is similar to the method used in many other common encodings, is that the underlying data is broken into 6-bit words (which gives 64 possible words), each of which is subsequently mapped to a subset of a character set that can be represented by 7-bits (typically ASCII). Thus, if the underlying data is represented as 8-bit bytes in memory, three bytes are represented as four Base64 characters. Several variations exist – there are a total of 62 alphanumeric characters in ASCII, so two additional characters must also be used, the choice of which varies for different applications; some implementations use an additional padding character when the total number of bits in the data to be encoded is not a multiple of six.

```c
/* Generate a lookup table of Base64
 * encodings. */
static uint8_t const b64_table =
{
    65U, 66U, 67U, 68U, 69U, 70U,
    71U, 72U, 73U, 74U, 75U, 76U,
    77U, 78U, 79U, 80U, 81U, 82U,
    83U, 84U, 85U, 86U, 87U, 88U,
    89U, 90U, 97U, 98U, 99U, 100U,
    101U, 102U, 103U, 104U, 105U, 106U,
    107U, 108U, 109U, 110U, 111U, 112U,
    113U, 114U, 115U, 116U, 117U, 118U,
    119U, 120U, 121U, 122U, 48U, 49U,
    50U, 51U, 52U, 53U, 54U, 55U,
    56U, 57U, 43U, 47U
};
/* Encode an array of bytes in Base64. */
size_t base64_encode(uint8_t * p_in,
                     uint8_t * p_out, size_t in_size)
{
    size_t out_size;
    uint8_t index[4];
    /* Handle the input three bytes at a time. */
    while (3U <= in_size)
    {
        /* Generate an index to lookup each output
         * byte. */
        index[0] = p_in[0] >> 2;
        index[1] = ((p_in[0] & 0x3U) << 4) |
                   (p_in[1] >> 4);

        index[2] = ((p_in[1] & 0xFU) << 2) |
                   (p_in[2] >> 6);
        index[3] = p_in[2] & 0x3FU;
        /* Assign output bytes from the lookup
         * table. */
        p_out[0] = b64_table[index[0]];
        p_out[1] = b64_table[index[1]];
        p_out[2] = b64_table[index[2]];
        p_out[3] = b64_table[index[3]];
        in_size -= 3U;
        out_size += 4U;
        p_in += 3;
        p_out += 4;
    }

    if (1U == in_size)
    {
        /* One input byte is left - encode it. */
        index[0] = p_in[0] >> 2;

        index[1] = (p_in[0] & 0x3U) << 4;
        p_out[0] = b64_table[index[0]];
        out_size += 2U;
    }
    else if (2U == in_size)
    {
        /* Two input bytes are left – encode
         * them. */
        index[0] = p_in[0] >> 2;
        index[1] = ((p_in[0] & 0x3U) << 4) |
                   (p_in[1] >> 4);
        index[2] = ((p_in[1] & 0xFU) << 2);
        p_out[0] = b64_table[index[0]];
        p_out[1] = b64_table[index[1]];
        p_out[2] = b64_table[index[2]];
        out_size += 3U;
    }
    else
    {
        /* All input bytes have been encoded. */
    }
    /* Return the size of the output. */
    return out_size;
}
```

Fig 6.1 - Encoding of data to Base64 can be achieved by using a lookup table to find the corresponding character for each six bits of the original data. Every three bytes of input produce four bytes of output. Several improvements could be made to this example – but it has been made deliberately verbose to better illustrate the methods being used. The output does not include any padding bytes in the output – although not required for accurate decoding of the output, these are sometimes added to the output until the total length is a multiple of four bytes in length. The character (ASCII code 61) is commonly used. Decoding can be achieved in a similar way; the simplest and fastest solution is to use an array to provide a reverse lookup table, although this is not a particularly efficient use of memory – about half of the array will be populated by values that do not correspond to any Base64 character.

Encoding data in this way does not provide any security benefits; the encodings are merely an alternative representation and no special knowledge is required to extract the information contained within them. The data integrity benefits are also minimal – it will be possible to detect corruption of the data only if the result is an invalid character sequence, but many errors will not cause a problem and the encodings themselves are not designed to detect errors.

## Error detection

Error detection methods are nothing. The simplest method is to use a parity bit – a single bit appended to a word that indicates whether an even or odd number of ‘1’ bits in the data. This is sufficient to detect a single bit error, or any odd numbers of bit errors, but will fail when the number of errors is even. A parity bit cannot help in identifying which bit has changed; the data itself could even be intact, with the parity bit being in error. The parity bit may be calculated from an arbitrary number of bits, although the likelihood of errors going undetected increases as the number of bits increases. Despite their limitations, parity bits are widely used, particularly in many simple communications protocols.

```c
/* Calculate a parity word LRC. */
uint8_t parity(uint8_t * p_data, size_t data_length)
{
    uint8_t parity_word = 0U;
    /* Ex-or each input byte with the parity
     * word. */
    while (0U < data_length)
    {
        parity_word ^= *p_data;
        ++p_data;
        --data_length;
    }
    return parity_word;
}
```

```c
/* Calculate an 8-bit LRC value from the two's
 * complement of the summed data. */
uint8_t lrc8(uint8_t * p_data, size_t data_length)
{
    uint8_t check = 0U;
    /* Add each data byte to the check value. */
    while (0U < data_length)
    {
        check += *p_data;
        ++p_data;
        --data_length;
    }
    /* Get the two's complement of the check
     * value. Don't use check = -check; */
    check = ~check;
    check += 1U;
    return check;
}
```

Fig 6.2 - A longitudinal redundancy check (LRC) is quick to calculate and can provide some protection to errors. To verify the data, calculate the LRC value again and compare with the original value. Note the use of an unsigned value for the LRC in the data sum version, even though the value is negated at the end – this is necessary, primarily because signed integer overflow is undefined behaviour but also because it would be bad practice to mix signed and unsigned types or to assume the target platform uses two’s complement representation for negative numbers (even though almost all modern platforms do).

The idea of a parity bit may be extended to a parity word, which can be more efficient than calculating parity bits for each word for large amounts of data. The parity word is the exclusive-or of the words in the original data. An alternative approach is to calculate the sum of all the words in the data, treating them as unsigned integers and truncating the sum to be the same length as the words it is calculated from. In this case it is common to append the two’s complement negative of the sum, rather than the sum itself, to the data. Both these methods are basic examples of checksums and often referred to as Longitudinal Redundancy Checks (LRC).

While simple to implement, these basic checksums are limited in their ability to detect certain types of error; for instance, an arbitrary number of words with the value zero may be added or removed from the data without changing the checksum value. The order of the words in the original data is also unimportant, so although rearranging them could significantly change their meaning, it will not change the checksum. The value of these checksums vary only slightly for a small change in the input data, so a relatively small number of errors can easily cancel out causing the checksum to appear correct.
