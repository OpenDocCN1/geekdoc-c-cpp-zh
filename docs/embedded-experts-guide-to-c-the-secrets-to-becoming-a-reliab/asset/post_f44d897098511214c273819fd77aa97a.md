```c
/* Debounce a switch by checking
 * for five consecutive 'true' inputs. */
bool debounce(bool state)
{
    static int sample_count = 0U;
    static bool debounced_state = true;
    /* If it's time to restart sampling, reset the

    * state variables. */
    if (!(debounced_state || (5U == sample_count)))
    {
        debounced_state = true;
        sample_count = 0;
    }
    /* AND the current state with the stored
     * state, then increment the number of
     * samples. */
    debounced_state &= state;
    ++sample_count;
    /* Return true after five true inputs. */
    return debounced_state &&
        (5U == sample_count);
}
```

Fig 5.3 - A switch may be periodically sampled and debounced in software. This example shows a simple function which can be called each time the switch is sampled and will return 'true' after five consecutive 'true' inputs.

As with inputs, outputs may be updated periodically or only when required and the appropriate choice is largely determined by their purpose. Most outputs will be digital; either single signals which may be either on or off, or multiple outputs, often referred to as an output which may carry binary. However, this is not always the case and many platforms include analogue outputs as well.

Simple outputs can include LEDs, sounders, solenoids and These may all be controlled using single outputs which switch them on and off; although it is also possible to vary properties such as the intensity of an LED or speed of a motor by rapidly switching between on and off states, with the relative time in each state determining the output – a technique known as Pulse Width Modulation. For outputs requiring limited bandwidth, this can be achieved without any specialist hardware, although PWM modules are a common feature in modern microcontrollers. More precise analogue outputs may be achieved, either by using PWM at a higher switching frequency or by using a dedicated digital-to-analogue converter (DAC).

```c
/* Generate simple PWM signals. The bandwidth
 * of the input must be much less than the
 * frequency at which the compare signal
 * wraps-around. */
bool pwm(uint8_t input)
{
 static uint8_t counter = 0U;
 /* Increment counter. The value wraps back to
 * zero when it exceeds 255. */
 ++counter;
 /* Return true when the input exceeds the
 * counter value. */
return (input >= counter);
}
```

Fig 5.4 - Low-frequency PWM can be implemented using a counter and comparing the value to the modulating signal. This approach works well for outputs such as indicator LEDs that only require a modulation frequency of about 100 Hz, but hardware support is required for better performance. The modulating signal must have a lower bandwidth (by a factor of five or more) than the carrier signal. The carrier signal frequency is the frequency at which the function is called divided by the number of increments before the counter wraps-around.

## Buses

A bus is the physical means by which data is transferred between peripherals and devices. It is a broad term which covers both hardware and protocols used to interconnect, which may be either parallel or serial and either synchronous or

A parallel bus is one which transfers multiple bits simultaneously using separate physical connections for each; conversely, a serial bus transfers a single bit at a time using one physical connection. The bandwidth of parallel buses can be increased simply by increasing the number of connections, thus allowing more bits to be transmitted at once. Historically this was seen as an advantage and serial communication was used when low-cost, rather than high-performance, was an important requirement; however, for high-speed buses, matching the electrical characteristics of each interconnection is a significant challenge and serial buses are often preferred except in specialist applications. Synchronous buses are those where devices also share a clock signal to control data transfer timings, whereas asynchronous buses control timing by some other means. Many common buses, such as Ethernet and USB are asynchronous, serial buses; although today they are less familiar to the average end-user, RS232 and RS485 are also asynchronous, serial buses and are still used in many embedded systems. Synchronous, serial buses such as SPI and I2C are often found internally within devices. Parallel buses are now much less common than they once were, at least for implementing general purpose communications.

Most buses can, at least in theory, be implemented using a technique known as bit-banging – that is, the use of software to emulate the behaviour of dedicated. While this may occasionally be necessary, it is often inefficient, cumbersome and entirely impractical at anything other than the most modest data rates, particularly when used with serial protocols. Furthermore, certain requirements of a protocol may be difficult or even impossible to emulate in software; for instance, data may be required to be written on the rising edge of a clock signal and read on the falling edge (or vice versa), which is straightforward (at least in theory) to achieve in hardware but not in software. Since cheap microcontrollers which include at least a Universal Asynchronous Receiver-transmitter, SPI, or I2C module are commonplace, as are a wide range of peripherals which communicate using these protocols, the use of dedicated hardware should be preferred in almost all circumstances.

```c
/* The bus itself is defined somewhere else. */
extern spi_bus_t g_spi;
/* Send and receive one byte of data using an
 * SPI bus at the maximum possible data
 * rate. */
uint8_t spi_transceive(uint8_t data_in, uint8_t device)
{
    uint8_t data_out = 0U;
    /* Set the device address pins to the selected
     * device. Device selects are active low. */
    g_spi.n_cs = ~device;
    /* Send and receive data bit-by-bit. To lower
     * the data rate, add delays. */
    for (bit = 0U; 8U > bit; ++bit)
    {
        /* Write one bit, set clock high. */
        g_spi.mosi = data_in & 0x80U;
        g_spi.clk = 1U;
        /* Shift input and output bits to the
         * right. */
        data_in <<= 1;
        data_out <<= 1;
        /* Set clock low, read one bit. */
        g_spi.clk = 0U;
        data_out |= g_spi.miso;
    }
    /* Set all device address pins high to
     * deselect. */
    g_spi.n_cs = 0xFFU;
    /* Return the data read from the device. */
    return data_out;
}
```

Fig 5.5 - Bit-banging is a technique for meeting the requirements of a bus in software and reading and writing bits directly rather than via hardware. This example shows how this might be achieved for an SPI bus. Bit-banging does have a number of challenges. Note, for instance, that the example makes no effort to precisely control the bus timing; this could be addressed using a timer interrupt or by inserting “NOP” (no-operation) instructions between statements, but dedicated hardware avoids the need to do so entirely and should always be the preferred option when it is available.

Individual devices on a bus may be represented in software using structures containing fields for the information required to communicate with them; this includes identifying information, transmit and receive buffers and callback functions to be invoked when data is received or an error occurs. These structures should be visible to the relevant device and bus driver modules only and should only be referenced indirectly in application code using pointers. Such a pointer may be referred to as a device. There are two good reasons to do this.

- Firstly, it provides a degree of abstraction between the implementation of the device and how the application interfaces with it, which both simplifies developing applications and makes them more portable.

- Secondly, it prevents the programmer either accidentally or naively altering the implementation.
