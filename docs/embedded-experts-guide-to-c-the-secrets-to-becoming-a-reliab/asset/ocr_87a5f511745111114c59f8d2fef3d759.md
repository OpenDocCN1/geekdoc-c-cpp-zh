There are usually options available in the compiler settings to control the level of optimisation which will be performed. Even on the lowest optimisation setting, some basic changes are likely to be made; for instance, expressions which can be evaluated to a constant value at compile time will usually be replaced by the appropriate The highest optimisation settings can sometimes cause compilation to fail or the compiled program to behave incorrectly – compiler optimisation tends to be very unforgiving of any ambiguities introduced by any undefined and unspecified behaviours which are encountered. It is also worth noting many optimisations are not usually performed for debug builds, so code which appears to be reliable during debugging may not always behave correctly when compiled using production build settings. It usually makes more sense to write code in a way which aids compiler optimisation rather than to attempt writing optimised code manually.

Optimisation begins in the design phase, before any code is written. Knowing the requirements of the software you are developing and planning how to implement it is critical to performance. This is one reason I do not advocate for “agile” development methods where continuous reviews are used to tweak initially poor Hardware has a significant impact on which optimisations are appropriate; an 8-bit platform, for instance, will always incur a performance penalty when performing 16-bit or 32-bit arithmetic, whereas a 32-bit platform may not make the most efficient use of memory when working with single bytes. Similarly, a platform which lacks a floating point unit will not perform well if it is required to execute a significant number of floating point calculations. The choice of an appropriate platform is more significant a factor in determining performance than any number of optimisations.
