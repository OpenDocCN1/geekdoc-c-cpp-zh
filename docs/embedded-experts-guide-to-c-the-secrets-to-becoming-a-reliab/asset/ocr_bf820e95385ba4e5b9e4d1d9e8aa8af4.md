It is often the case optimisation can be achieved through a better choice of algorithm, particularly for calculations which are performed many times or require multiple iterations to arrive at a result. While this will require a change to the software, it is not so much the code which is being optimised, but the process it implements. For instance, an FFT algorithm can usually be expected to perform faster than a DFT of the same size despite yielding the same result. Although writing your own FFT function may not be appealing, it’s worth taking a moment to consider if a calculation (even simple ones) can be rewritten in a way which could execute faster. If in doubt, you can always run a test to compare the different versions. Note that the number of lines of code is not usually important; the total number of operations which must be performed is a better predictor of the time a piece of code will take to run. In choosing an algorithm, you will need to consider the complexity of each available option, ideally choosing an algorithm with constant, logarithmic or linear Bear in mind, however, many algorithms which perform faster on large inputs may not perform so well on smaller inputs. For instance, a four-point DFT may actually run faster than a four-point FFT on a particular platform but increase the input size and the results are quickly reversed.

Once you have selected an appropriate platform and the right algorithms, it is still important to question when optimisation is justified. Most of the time, we simply shouldn’t bother; as Donald Knuth once put it: “We should forget about small efficiencies, say about 97% of the time: premature optimization is the root of all evil. Yet we should not pass up our opportunities in that critical 3%.”
