
The final phase of the translation process is called linkage and is performed by a linker. Although the output of Phase 7 is machine code, it is not useful machine code because it cannot be run immediately. The linker has several important tasks to perform:

- Firstly, if a program is built from multiple source files, the linker must combine these into a single piece of executable code. At this point, all references to external functions and variables must be resolved.

- Secondly, the linker must determine how the machine code should be arranged in the target platform’s address space. This is not simply a case of arranging blocks of code – jump instruction and variable addresses will need to be changed in order to complete this stage.

- The linker may need to generate some code. This code will typically create an initial stack for the program to use, may also create a heap and any additional code to determine how the program starts executing. This may be as simple as a jump instruction from the reset vector (the first address accessed by the processor after powering on or a reset) to the main function for software intended to run outside of a hosted environment.

We will now explore the phases of translation in detail.

## The Preprocessing stage

The preprocessor is responsible for completing the first four phases of translation. The input to the preprocessing stage is a source file and any header and source files referenced using #include directives. The C Standard names this a “preprocessing translation unit” and calls the output simply a “translation unit.”

During Phase 1, the character set used during editing is converted to a character set which the compiler can understand. Every character in the source file is mapped to a supported character in the target set. This may seem a trivial and unimportant step, but it is important to realise this is done in an implementation defined manner. If you have written the source code in an editor which supports the full Unicode codespace but your compiler is expecting ASCII, there is the possibility for information to be lost if any characters not found in ASCII are Although this may not be a major concern, it is worth restricting your editor to use only those characters supported by the rest of the tools you are using. If in doubt, choose ASCII since this is usually supported.

Any trigraph sequences are also replaced with their single character equivalents during Phase 1. Trigraphs are a feature of the C language, intended to help programmers with keyboards which do not support some of the characters found on a standard US layout, which we have largely ignored since they are prone to cause confusion and make code more difficult to read. Even without these issues, the implementation of trigraphs in C is frankly poor and their use should be strongly discouraged. Nonetheless, it is worth being aware trigraphs are replaced at this point.

Phase 2 of the translation process removes superfluous newlines from the source code. Any instance of a backslash followed by a newline is deleted. This is nothing more than a piece of housekeeping on the part of the preprocessor and of little concern to the programmer.

Preprocessor tokenisation is the next step of translation. Tokenisation is the process of analysing and decomposing source code into its constituent parts – in the same way as a sentence may be analysed to identify nouns, verbs and other types of word, code may be analysed to extract identifiers, operators and other classes of token. The tokenisation process in C is context-sensitive – the token class may not be unambiguously resolved based solely on a sequence of characters. Occasionally this can lead to some cryptic errors, such as a typedef alias being treated as a variable name because an appropriate typedef is not found in the correct place. The fact the tokenisation process is context-sensitive will not stop the code from being interpreted in a different way to what seems obvious to the programmer: just try compiling a program which includes the line a=b/*c; or something similar.

Digraphs are also replaced during the preprocessor tokenisation phase. Digraphs are a slight improvement over the trigraphs replaced in Phase 1, in part because each digraph must form a full token on its own or it will not be substituted. Nonetheless, their use is still discouraged since they do not introduce any new functionality and will tend to confuse programmers unfamiliar with them.

Preprocessor directives are not evaluated until the final phase of the preprocessing stage. If a #include directive is encountered, the preprocessing stage of translation is therefore a potentially recursive one and this is one reason why only header files should be included in this way and why header files should not contain any instances of the #include directive. #pragma and #define directives are also executed. Any _Pragma operators are executed. Finally, preprocessor directives are deleted.

## The compilation stage

The compiler is responsible for translating source code into a format which can be understood by the target platform. This may take place in two stages: a compiler may first translate source code statements into a series of assembly statements and then call an assembler to translate the result into binary opcodes. Since there is generally a very close (often one-to-one) relationship between instructions in assembly and opcodes, the compiler may be able to generate machine code directly without the intervention of an assembler. The programmer is rarely interested in the finer details of the process, so for simplicity, we will assume the latter scenario.

Before translating statements, it is first necessary to convert any literals into a format which can be stored on the target. While this is unlikely to be of much significance for numeric literals, string literals do require some manipulation. Phase 5 of the translation process involves mapping the characters used for writing the source code into the execution character set. This is a distinct step from the character mapping in Phase 1.

- Firstly, the character set understood by the compiler need not be the same as the execution character set, although in most cases it is probably safe to assume both support at least the basic ASCII characters.

- Secondly, escape sequences are replaced by their character equivalents at this point, e.g. the escape sequence is replaced with During Phase 6 of the translation process, adjacent string literals are concatenated. From the programmer’s perspective, this step is of little significance since it should have no impact on the functionality of the software.

Actual translation from source code (in the form of tokens) to machine code takes place during Phase 7. This includes another round of tokenisation (according to the C Standard, preprocessing tokens are translated to tokens – it probably isn’t worth worrying about the difference between a preprocessing token and a plain token), followed by syntactic and semantic analysis so machine code may be produced.

At this point, the output is machine code, or a “translated translation unit” to use the C Standard terminology. Further steps are still required in order for the code to run, but these do not have to be completed now. For instance, translation may be halted at this point if the code is to be used as a precompiled library – since there is no intention for the library to run in a stand-alone fashion, no further steps need be taken; indeed, in such a scenario it makes little sense to attempt any further steps, since there would be no way to properly call any of the functions within the library without additional software anyway.

For software which is intended to be loaded to the target and to run immediately, the final stage in the process is linkage. Despite being presented as only a single phase in the C Standard, this is a crucial, and potentially complex, step.
