
The C preprocessor provides directives to allow conditional compilation. These are the #else and #elif (else-if) directives. A preprocessor #if block must be explicitly closed using the #endif directive. Braces are not used to delimit the blocks of code between conditional directives. The #if directive is used to check whether a condition is true at compile time; if the condition evaluates to true, the code which follows will be included in the translation unit until the preprocessor encounters another conditional directive or if the condition evaluates to false, the code will be removed. The code between the directives may be C, preprocessor directives or a combination of both. Conditional compilation is most useful when relatively small amounts of code need to be changed based on conditions which will only be known at compile-time. These conditions can vary significantly – they could be compiler specific; platform specific, such as the processor being used; or even application specific, where you may not wish to include certain features within a particular version of a product. Anything which would normally be allowed within a C file is acceptable within a conditional compilation block. As well as blocks of C, this includes defining macros and including header files. Functions and variables may be declared or defined within conditional compilation blocks but bear in mind any references to these will also need to be conditional. If required, conditional compilation may also be used to abandon compilation if certain prerequisites are not met.

The previously mentioned defined operator is now useful, since we can combine this with the conditional directives to compile different versions of the code depending on which preprocessor symbols are present. This is such a common requirement two additional shorthand directives exist: #ifdef and #ifndef, which determine whether a symbol is or is not defined, respectively.

```
/* Check if this header is already included and
* guard against it being included again. */
#ifndef HEADER_H__

#define HEADER_H__
/* Check if a C++ compiler is being used. */
#ifdef __cplusplus
/* Tell C++ to use C linkage for the
* functions. */
extern "C" {
#endif
/* Function prototypes. */
int c_linked_function(int apples, int pears);
/* End the C linkage block for C++
* compilers. */
#ifdef __cplusplus
}
#endif
#endif
```

Fig 7.4 - Conditional compilation should be used in every header file to prevent multiple inclusions of the same file. Conditional compilation is also required for compatibility with C++ compilers.

One of the most common uses of conditional compilation is in header files. It is usual for the entire contents of the file to be wrapped in a #ifndef ... The #ifndef is invariably followed by a definition of the very symbol being checked. This is known as an include guard and prevents the file from being included more than once – after the first inclusion subsequent evaluation of the #ifndef directive will be false and the contents of the file is therefore ignored. It is good practice to use include guards in every header file.

The symbols to be checked need not be defined in the code itself. Various preprocessor symbols may be defined in the development environment, either as a requirement of the C Standard or as implementation specific additions. There is also usually an option to define custom symbols within the environment without having to edit the files being compiled. For instance, since C95, the C Standard requires the symbol __STDC_VERSION__ to be defined with a value which indicates which version of the standard the compiler is designed to work with. C++ implementations are required to define the symbol which is commonly checked in header files for libraries written in C to ensure the code is correctly

The conditional part of #if and #elif directives is not limited to checking for definitions. Any statement which can be evaluated prior to compilation can be used. This functionality is not used as widely as simply checking for a definition, but is still useful; for instance, if a piece of code requires a compiler to meet a particular version of the C Standard but alternative code can be used for other compilers.

A statement such as #if __STDC_VERSION__ == 199901L can be used in such instances (in this case, the statement will be evaluated as true for a C99 compiler).

Possibly the most underappreciated of the directives is the #error. On encountering this directive, the preprocessor stops the build process and returns a custom error. It is only useful within conditional compilation blocks since it would otherwise make compilation impossible. It may seem odd to consider this directive underappreciated, but the ability to abandon compilation and return a useful error message is incredibly helpful and can prevent wasting significant amounts of time attempting to resolve issues which are easy to spot with a little preprocessor assistance. It is much easier to diagnose a single, clear error than it is to interpret multiple generic compiler messages, or worse, the unexpected runtime behaviour which occurs when a default case is assumed. Some preprocessors also include a means of issuing custom warnings without abandoning compilation.

While this can be useful, warnings are more easily ignored than errors and no method of issuing custom warnings has yet been included as part of the C Standard, so vendors have chosen to implement this in various inconsistent ways.

```
/* Ensure C99 or newer is supported. */
#if __STDC_VERSION__ < 199901L
# error Use a compiler that supports C99.
#endif
```

## The #pragma directive

Of the preprocessor directives, #pragma is probably the least useful. It is used to provide the programmer a level of control over implementation behaviours, which would be somewhat more helpful if almost all #pragma instances were not implementation defined. Many of these directives are unusual in that, although classed as preprocessing directives, their effects are not necessarily limited to the preprocessor; #pragma directives can be used to control how source code is compiled, rather than being limited to changing what is compiled.

There are only three uses of #pragma defined by the C Standard (since C99); all of them are concerned only with optimising floating point and complex number calculations. Although some other directives are widely implemented, they are not standardised and their effects are implementation defined; specifically, The C Standard states they “might cause translation to fail or cause the translator or the resulting program to behave in a non-conforming manner.” The C Standard also states the preprocessor should ignore any unrecognised #pragma directives, although in many cases a warning may be generated in practice. Since C99, the C Standard has also included a _Pragma preprocessor operator. Although the syntax used differs, when it appears by itself, the behaviour of the operator is no different to the #pragma directive; however, the operator form may also be used within macro definitions, while the directive form cannot.

The three C Standard #pragma directives are:

- #pragma STDC which is used to signal to the compiler floating point expressions which would usually require multiple instructions may be contracted to a shortened form where an appropriate instruction is
- #pragma STDC which is used to control access to the floating-point allowing the programmer a greater degree of control over how floating-point operations are performed; and,
- #pragma STDC which is used to control how some complex number calculations are performed and optimised.

All are followed by one of the allowed values: OFF or ON. An in-depth understanding of when and how to use these directives is not required for most embedded programming.

Common, but non-standard directives include #pragma once and #pragma pack. #pragma once is used as an alternative to include guards to indicate a file which should be included only once; personally I never bother with it, since it is non-standard and as a result the include guards are still required. In theory, it should result in a reduction in compilation times, although I suspect the actual impact is small for most modern compilers. #pragma pack is used to alter the alignment of variables in memory – it accepts an integer argument to determine the amount of padding between variables in memory which do not fill all the space between two memory boundaries. While this can improve memory efficiency to an extent, it almost invariably comes at the cost of increased code size and decreased speed, so this is not really a good reason to use it unless memory is in particularly short supply. You may also come across #pragma which is used to manually exercise control over the amount of loop unrolling the compiler performs. While loop unrolling is a valid optimisation technique, the compiler is often better able to recognise when it will be beneficial, so overriding the default behaviour should be done with care.

Other common uses for #pragma directives include disabling specific compiler warnings or issuing custom errors or warnings.
