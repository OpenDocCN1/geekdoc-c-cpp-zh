A few systems even use a mixed-endian system; for instance, the PDP-11 stores 16-bit values as two 8-bit bytes in little-endian order, but 32-bit values, comprising of two 16-bit values (in little-endian order), are stored in big-endian order. Endianness is implementation defined; while values stored in memory will probably be stored in little-endian order by default (in the same way signed values will probably be represented using the twos complement method), the C Standard does not require it.

Internally, endianness is usually of little consequence; the problem arises when there is a need to convert from one word order to another, either because a specific piece of external hardware or a communication protocol requires it. Although some processors may include instructions to swap the order of bytes in a register, the C language does not include a single statement capable of doing this. The most intuitive way is to use masking, bit-shifting and OR-ing to change the order of the bytes. Alternatively, it is possible to use a union to split a larger word into individual bytes and swap them – take care, however; this may be a common practice, but is strictly unspecified behaviour according to the C Standard, although many compilers do support it.

```
/* Swap the order of bytes in a 16-bit word using
* masking and shifting. */
uint16_t byte_swap(uint16_t input)
{
uint32_t output = 0;
/* Swap bytes by masking and shifting. */
output = ((input & 0x00FFU) << 8) |
((input & 0xFF00U) >> 8);
return output;
}
```

## Type punning

Type punning – changing the type of a variable without changing its representation in memory – is generally frowned upon; however, it is also often unavoidable when writing code to interact with hardware. For instance, if you wish to send 32-bit floating point values using a communications protocol which can only send a single byte at a time, you first need to convert from a float to a type which can be manipulated byte by byte; this typically means it must be treated as an integer type in software. Since type casting changes the representation used, type punning must be used.

A word of warning is necessary here: no method of type punning can be considered compliant with the C Standard. Compilers generally support such methods only because they are widely used and no alternative is defined within the standard.

There are two commonly used methods of type punning. You can type cast a pointer to an object so it dereferences to the intended type or you can use a union. The former method is potentially undefined behaviour, except when the object address is cast to a pointer to a char. Converting from a pointer to char to another pointer type, however, can still result in undefined behaviour – the requirement given in the C Standard is, when casting pointers, the types pointed to must have compatible alignment in memory.

Note that even if two types are the same size, the rules governing their alignment in memory may still differ and casting from one to the other may still cause problems. The latter method of using a union is sometimes mistakenly believed to be allowed by the C Standard, but this is not strictly true; it is implementation defined behaviour in C89 and unspecified behaviour C99 and Type punning should only ever be undertaken with the greatest care; it is important to document any assumptions made in doing so and to use preprocessor directives or other available methods to enforce them wherever possible.

```
/* Read a (signed) 32-bit word from an array of
 * bytes. */
int32_t int32_from_bytes(uint8_t * p_bytes)
{
/* Cast p_bytes to a pointer to an int32 then
 * dereference and return. */
return *((int32_t *) p_bytes);
}
```

## Basic inputs and outputs

The most basic input and output functions are provided by General Purpose Input/output (GPIO) connections. These are inputs and outputs with no predetermined purpose – they can be used in any way the programmer sees fit, provided it is within the capabilities of the device. Exactly how these IO connections are implemented varies from one platform to the next, but they can typically be accessed either individually or in groups and, although in some instances there may be some input only or output only connections, their configuration can usually be changed, often even at runtime. Typical input sources used with GPIOs include components such as switches or jumpers (pins which may either be connected or disconnected as a means of configuring a device). Output loads include components such as LEDs and other indicators. Groups of GPIO connections can often be used to implement more complex interfaces. These simple examples are by no means all that can be achieved with GPIO, although it is often preferable to use dedicated hardware interfaces for many tasks.

Although it is occasionally necessary for an input to generate an interrupt when its state is changed, most inputs can be continuously polled, or sampled, without requiring dedicated interrupts or service routines. Sampled inputs are those which are checked to determine their value; these may be digital inputs or the inputs to dedicated analogue-to-digital converters. Crucially, it is usually possible to read multiple inputs simultaneously which significantly reduces the code complexity associated with them. Sampling is most commonly periodic and driven by a timer interrupt, although alternative methods of triggering a sample are possible. Where periodic sampling is used, the sampling frequency is primarily determined by the bandwidth of the signal being captured; any signal must be sampled at least twice the bandwidth of the signal. Oversampling – sampling at a higher frequency than the minimum required – is a common practice since it simplifies the design of hardware and can be used to increase precision of the samples when used appropriately. Sampling which is not periodic may be used when it is important to know the value of an input at a precise moment, but continuous updates are not required; this approach is potentially useful in low-power applications which only need to update readings occasionally or for very slowly varying inputs, such as potentiometers or thermistor readings where the precise sampling time is non-critical.

Where available, Direct Memory Access (DMA) can be useful for ADC inputs which require a high sample rate; this allows the CPU to spend less time servicing interrupts and to treat samples in batches rather than individually. Similarly, when oversampling, hardware may be used to sum or average samples without requiring any action from the CPU if such hardware is available. Such features are not supported directly through the C Language, but libraries to provide them should be available where the required hardware is present.

Switches and other similar components such as relays can present an unexpected challenge to those who assume their behaviour is ideal. Although many processors include interrupt-on-change capabilities for digital inputs, these are usually not the best choice for these types of input and periodic polling of the inputs is often more appropriate. The problem is the contacts “bounce” – after changing state, there is a delay before they settle definitively into the new state, resulting in multiple, rapid transitions. This process can take several milliseconds to complete and potentially dozens of transitions can occur during that time. The spurious transitions may be filtered in hardware, but this requires a minimum of two additional components, and probably more, for each input. Alternatively, it is relatively straightforward to periodically sample the inputs and implement debouncing in software in an efficient manner – all switches can potentially be sampled in one go and collectively debounced without requiring any additional hardware.
