Undefined behaviour should never be allowed to occur. This is much
easier to state than it is to achieve, but it is critical that you take steps to
avoid writing code that results in undefined behaviour. Later, we will
explore tools and techniques that you can use to help you.

Slightly less serious, but still a concern, are unspecified behaviours. These
arise in situations where the C Standard “provides two or more
possibilities” and “imposes no further requirements on which is chosen.”
The choice does not have to be documented; it is even possible (although
unlikely) that the compiler may make a different choice for each instance
of an unspecified behaviour. Many unspecified behaviours are not easily
avoidable – for example, the order of evaluation of subexpressions is
unspecified and if the programmer were to always ensure a specific
ordering then the resulting code will often be both verbose and
unnecessary; in most cases, it does not matter which of a group of
subexpressions is evaluated first. This does not, however, mean you
should not be concerned by unspecified behaviours. There are occasions
where they can easily create serious issues: for instance, if a variable is
