
Many #pragma directives are entirely vendor specific and therefore not portable. Unfortunately, these are also often the most useful for embedded programming, since they are used for a variety of essential purposes such as setting processor configurations, mapping symbols to specific memory locations and identifying interrupt service routines. Many of these tasks are inherently application and platform specific and therefore do not have portable solutions, which does make the non-portability of the directives irrelevant to some extent. However, this is not much help if you simply change from one compiler vendor to another without changing the hardware you are working with or if you are trying to support legacy code.

## Other Directives

There are two other preprocessing directives: the null directive and the #line directive. The null directive does nothing; it serves no purpose, at least not when the preprocessor is used as part of the normal translation process for C. The #line directive is used to change the apparent line number and, optionally, apparent file name which replace occurrences of the __LINE__ and __FILE__ macros. Although this may not seem particularly useful, the preprocessor will often insert the #line directive (or at least generate an output consistent with having done so) so the apparent locations in the preprocessor output match the locations of lines of source code; for instance, when header files are included. It also finds use in code generation systems. Manual use of this directive is uncommon.

## Chapter 8: Understanding the Translation Process

So far, we have focussed solely on writing software. There has been no discussion on the topic of how source code is transformed from the human-readable format understood by the programmer to a binary format understood by a microprocessor. While for most purposes such in-depth discussion is not required, understanding the process can give valuable insight to the reader and aid understanding of the advanced topics which will make up the remainder of this book.

When we talk about compiling software, we are usually not talking about compilation alone, but the complete process of producing executable machine code from source code written in C. Compilation is only actually one step in the process, although the distinction is often ignored for brevity and commonly understood to describe the whole process. Most IDEs do honour the distinction – the process of generating executable code is generally described as building, rather than compiling. In the various editions of the C Standard, the process is referred to as translation.

There are eight phases of translation in total defined in the C Standard:

- Source file character mapping.
- Line splicing.
- Tokenisation.
- Preprocessor directive execution.
- Character constant and string literal mapping.
- String concatenation.
- Translation.
- Linkage.

In practice, multiple phases may be combined into one, but a conforming C implementation is required to behave as though they occur individually and in sequence. We are also not generally concerned with some of the stages – line splicing and string concatenation, for instance, are of little interest to the programmer and serves only to convert source code which was (presumably) intended to be human-readable to a more concise format for the compiler. To simplify matters, we may group the phases into larger stages. There are a minimum of three stages worth of understanding, and these are usually completed by distinct pieces of software, although modern IDEs will generally bundle them together and allow them to be executed as one task as far as the programmer is concerned:

- Preprocessing.
- Compilation.

Preprocessing refers to the work performed by the C Preprocessor and corresponds to the first four phases of translation described in the C Standard. Crucially, this is the stage where any #define macros are expanded and substituted. It is important to remember this stage is completed before the source code is compiled and this is the root of much of the confusion and risk arising from improper macro usage. Any #pragma and conditional preprocessor statements are evaluated at this point. Any C source code which is contained within an #if directive which evaluates to false will at this point be discarded and as a result will have no impact on the output of the build process. Any #error directives must either execute at this stage or be discarded. Custom errors defined in this manner may not be invoked during a later stage. Following completion of phase four of the translation process, preprocessor directives are deleted. At this point, the preprocessor outputs what is known as a Translation Unit in the C Standard.

The compiler takes translation units as input and produces executable machine code as output. This corresponds to Phases 5 through 7 of the translation process. Phases 5 and 6 are concerned with the storage of character constants and string literals. What we generally think of as compilation takes place in Phase 7 – the output of which is machine code. In some cases, Phase 7 may actually be split into two stages: The compiler may output assembly code rather than machine code. This will then be processed by an assembler to produce machine code. Although this is not an uncommon way to implement the translation phase, it is sufficient in most cases to assume the compiler takes a translation unit and produces machine code without considering the generation of intermediate assembly.
