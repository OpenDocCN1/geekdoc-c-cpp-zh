
Other lengths of Hamming code are possible. As the code length increases, so does the efficiency of the code; a 255-bit Hamming code includes 247 bits of data. These longer codes are still only capable of correcting a single-bit error.

There are also other error correcting codes that offer other improvements – for instance, one common implementation of the Reed-Solomon algorithm can transmit 223 bytes of data for every 255 bytes sent. Reed-Solomon codes are also particularly useful for correcting the common problem of burst errors – errors that affect several consecutive bits – which repetition and Hamming codes are poorly suited for. They are, however, computationally expensive to encode and decode, which can limit the maximum possible data-rate on resource-constrained

To an extent, burst error performance can be improved using a technique known as interleaving. This involves re-ordering the data to be transmitted before sending so that if a series of errors do occur, their effects are spread through the data when the order is corrected on reception. This will not necessarily help in recovering the lost data but is a useful technique when either a small amount of loss over the entire transmission is acceptable or when the corrupt data can be inferred by some other means. There are some disadvantages to interleaving: first, all data must be interleaved before transmitting, which introduces some additional latency in the transmission, and all data must be received before it can be de-interleaved, adding more latency; second, in some cases it may be preferable to have the errors localised, rather than spread throughout the data – in this case, interleaving is not appropriate.

## Encryption

Encryption is not merely the process of obfuscating data. There are plenty of ways in which data can be obfuscated without adding meaningful security; the difference with encryption is that the process should be infeasible to reverse without access to a valid decryption. In modern cryptography, there are two main classes of encryption algorithm (ciphers): symmetric key and asymmetric (or public) key algorithms. Symmetric key ciphers use the same key for both encryption and decryption; asymmetric key ciphers use a pair of keys, only one of which needs to remain secret – a public key for encryption and the other private key for decryption; the private key may also be used for encryption – this provides no security but guarantees the authenticity of the data.

The benefit of asymmetric key is that they overcome the problem of needing to securely share keys; one of the keys can be made public for anyone to use, while the other remains private without compromising security. However, they are also usually much more computationally expensive to use than symmetric key ciphers and are far more reliant on the properties of the key to work securely – the best-known asymmetric ciphers require key pairs to be generated by starting with two large prime numbers.

Although asymmetric encryption is an interesting and important topic, it won’t be covered here since it is also a specialised area, requiring implementations of large integers (thousands of bits long) and an understanding of mathematical methods that, although not overly difficult to work with, are beyond the scope of this book. There are also a very limited number of asymmetric algorithms and many libraries already exist to implement

Symmetric key ciphers may further be split into two types of algorithm: block ciphers and stream ciphers. As the names suggest, block ciphers work on blocks of data, whereas stream ciphers work with an arbitrary-length sequence of individual bits or bytes. Stream ciphers are typically faster than block ciphers but must constantly update their state in order to secure data (the key to a stream cipher is essentially a seed value to a function that generates a much longer key), which requires storing state information relating to the cipher. The state information of the cipher is then combined with the plaintext using a simple XOR to generate the ciphertext. In contrast, block ciphers are stateless. The fixed sized blocks used in block ciphers makes them inherently resistant to the malicious insertion or deletion of data and have high diffusion – meaning that each byte of ciphertext depends on the entire plaintext block rather than only one byte, as is the case with a stream cipher.

A block cipher should not be used to encrypt more than one block of data without either changing the key used for each block or adding an additional “mode of operation” to the cipher. The problem is that given the same input, a block cipher will always produce the same output; although the precise data will be concealed, any patterns in the plaintext will be identifiable, potentially compromising the security of the ciphertext. Cipher Block Chaining (CBC) is a simple and common mode of operation: each plaintext block is XORed with the previous ciphertext block prior to encryption. Since there is no previous ciphertext to use, the first block is XORed with an initialisation

Decryption in CBC is the reverse – decrypt the block, then XOR the plaintext with the ciphertext of the previous block, or the initialisation vector when decrypting the first block. The initialisation vector is a – usually random (or more likely, pseudorandom) – value of the same size as the cipher block size. CBC has the advantage that each ciphertext block only directly influences encryption of the next block; thus, if one block is corrupted or lost, decryption will only fail on that block and the block immediately following it. This fact can be exploited to avoid having to share the initialisation vector (you will, however, still need to share the key) – simply fill the first plaintext block with arbitrary values; when decrypting, the initialisation vector is only required for the first block, so everything from the second block onwards will decrypt correctly and since the first block contains no actual data, you can discard it.

Other modes of operation exist, the most common of which are Cipher Feedback (CFB), Output Feedback (OFB) and Counter (CTR). These modes are interesting because they can be used to convert a block cipher to a stream cipher and CTR mode is particularly useful when a high data rate is required. The details of how these modes can be implemented can easily be found online.

## Generating random numbers

Random number generation, or more correctly, pseudorandom number generation, is an important function for many cryptographic protocols; it is crucial to generating keys, initialisation vectors and salts. Unfortunately, it is incredibly difficult to generate a truly random number, so most algorithms for doing so are, in fact,

It is easy to generate a sequence of numbers that appear random – Linear Feedback Shift Registers (LFSR) are one of the most common means of doing so, have been extensively analysed and are adequate for many purposes. However, most pseudorandom number generators are not suitable in cryptographic applications since if enough information is known about their state at a given time, it is trivial to determine their past and future states. Additionally, they have two flaws that cause their outputs to deviate from being statistically (as opposed to truly) random: first, the output sequence will eventually return to its starting value and begin to repeat; second, within a single period of the sequence, no value will appear more than once.

```
/* SEED can be any number other than 0. */
#define SEED 0x12345678UL
/* Generate a 32-bit pseudorandom number using
 * an XOR shift LFSR. */
uint32_t lfsr32(void)
{
    static uint32_t state = SEED;
    /* The number of bits to shift can change, but
     * should be chosen to give a maximal-length
     * LFSR. */
    state ^= state << 13;
    state ^= state >> 17;
    state ^= state << 5;
    return state;
}
```
