Both processes and threads refer to units of independent instruction sequences which can be run concurrently with other instruction sequences. Processes are typically entirely independent of each other – they do not share memory and in most cases cannot communicate with each other, if one process is required to send a message to another, some special mechanism must be available for this purpose. Conversely, threads form part of processes and the demarcation between individual threads within a process is much less clear – two threads from the same process share memory; they can often communicate directly with each other and special care must be taken to avoid unwanted interactions between them. It is entirely possible to use multiple threads, even if only a single process is executing. There is also no reason why multiple, single-threaded processes cannot run concurrently. So far in this book, we have treated all the software we have discussed as though it is the only process running, usually consisting of only one thread.

Since process may be used (almost) synonymously with program, within the scope of this chapter, we are primarily concerned with threads. We have stated threads within a process share memory. Although this is true, each thread still requires its own stack, registers and program counter. If we wish to switch execution from one thread to another, the state of the running thread must be stored and the state of the thread replacing it must be loaded into the processor's registers. Many processors include hardware to support fast thread switching, although hardware support is not essential to run multithreaded code. To an extent, we have already introduced multithreading – interrupt service routines are threads, distinct and separate from the primary thread responsible for the routine running of a program.
