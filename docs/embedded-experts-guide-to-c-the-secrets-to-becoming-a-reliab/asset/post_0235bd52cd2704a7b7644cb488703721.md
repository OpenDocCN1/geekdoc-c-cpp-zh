## What exactly is C?

You already know that C is a programming language (if you did not, I would be very surprised that you chose to pick up this book), but that is only a partial description. A more complete explanation would be that C is a general-purpose, procedural programming language – it does not attempt to limit the type of programs that can be written in the language and each program consists of building-blocks known as functions. Every C program has at least one function – almost always called – but most have more; indeed, too much code in the main function (or any other function) is generally a sign of a poorly written piece of software. From a more practical perspective, before diving into how we use C, it is worth clarifying a few points.

When we refer to C it may appear as though we are referring to a single programming language. Although this is true to an extent, it is necessary to be aware that there are no fewer than five versions of standardised (ISO) C, not including amendments: The most recent of which (at the time of writing) is C18 (the 2018 version). You may also come across ANSI C, which was the first attempt at standardisation. ANSI C ("C89") and the first version of ISO C (“C90”) are, from a practical standpoint, equivalent.

In addition to ANSI and ISO versions, the language existed prior to the first published standard; this version is usually referred to as “K&R C” since it is the version used in “The C Programming Language.” However, K&R C is not a standard and should not be treated as such – there is no such thing as a K&R compiler. While there is a degree of compatibility between different versions of the language, it is not guaranteed and certainly should not be relied upon. Features are added with each new edition and some others are deprecated. The behaviour of the language may also be clarified or refined whenever a new version of the standard is published.

The question of which version you should use is not easy to answer. Compilers typically lag by a few years when it comes to implementing the latest version of the standard and many deliberately target earlier versions of the standard as a way of maintaining compatibility. Furthermore, few compilers are truly faithful to the standards anyway; most vendors will include additional features, and many choose not to implement the standard in full. As far as embedded systems are concerned, you are unlikely to be using a compiler that implements anything more recent than C99, although there may be many vendor specific extensions included to help with common problems. For some platforms, it may be that you are restricted to C90 or C95 (more accurately: C90, Amendment 1). You will need to check your compiler documentation to be sure. For the majority of this book, C99 is assumed unless otherwise stated. Whenever the “C Standard” is mentioned without additional clarification, it is the 1999 version that is being referred to.

Much of the advice and guidance found in this book is based on additional coding standards, particularly MISRA C and Barr C. Despite their applicability to professional embedded programming, neither receives much acknowledgement in general programming literature. MISRA C is a standard specifically produced to aid in writing safety-critical C programs. Barr C is similar, in that it focusses on software reliability and safety, and does not conflict with the MISRA C rules. Barr C is available free of charge from the Barr Group website. There is a charge for a copy of MISRA C, but it is remarkably affordable and worth the investment if you are involved in writing any high-reliability embedded software.

## Stylistic conventions used in the book

Like most programming books, this one uses certain stylistic conventions when mixing text and code. Keywords, function and variable names and code fragments are all written using monospaced font. This highlights them so that they can easily be identified as code snippets; it is also consistent with the display style of development environments. On occasion, unimportant pieces of code are omitted and replaced with a placeholder: ...; Where this placeholder appears, you may simply assume that the code it replaces is legal C and unimportant to the example in question.

One area of (mostly pointless) debate among programmers, for no particularly good reason, is the bracing and indentation style that should be used. There are people with strong opinions on the subject and this has resulted in such nonsense as one style being dubbed the “One True Bracing and some programmers boasting of “correcting” the style of others. Becoming evangelical about such things is pointless; there are multiple styles and all result in valid code. Personally, I prefer to place opening and closing braces on their own line, indented to the same level as the preceding (or following) code, with additional indentation between the braces; this is the style I use in examples throughout this book. As far as I am concerned, you are free to pick any style which appeals to you. If you work as a team, agree a style and then have the team use it consistently. Ultimately, the style you use hardly matters, but consistency does.

There is less debate around the placement of parentheses after function names and control statements, although some people do still have strong feelings about this too. ## What’s in this book?

This book started life as a one-day training course entitled “C Programming for Embedded Systems”. The course, and this book, explores many aspects of the C language with a particular emphasis on embedded systems, although this book adds some additional material not present on the course. It assumes a certain level of familiarity with the language and is not an entry level book – what this book will not help you with is the basics of the C language; there already exist many books and courses for that purpose and the best way to learn is to begin experimenting.

You may choose to read this book from cover-to-cover, or you may choose only to read those chapters or sections which you find particularly interesting or useful. That decision is yours alone. Either way it is worth quickly outlining what each chapter covers:

- The first chapter, “Trust the Programmer” - Issues with C, will help you to understand why C has developed such a poor reputation where safe programming is concerned.
- The second chapter, Writing Safer C, will introduce a combination of techniques and tools you can use to make your software safer and more reliable rather than relying on extensive debugging.
- Chapter three, Managing Memory, provides practical guidance on how memory housekeeping in embedded systems. It shows you how to implement common memory management techniques and helps you decide when it is appropriate to use them.
- Chapter four, Interrupts and Callbacks, will help you write better interrupt service routines, as well as understand the problems and risks that can arise as a result of the change in program flow and how to overcome them.
- Chapter five, Interacting with Hardware, describes the best-practice approach to writing hardware drivers, as well as introducing you to common communication protocols you are likely to encounter in embedded systems.
