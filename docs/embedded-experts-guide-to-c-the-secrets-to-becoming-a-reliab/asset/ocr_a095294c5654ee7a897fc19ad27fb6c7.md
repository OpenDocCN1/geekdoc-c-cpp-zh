Fig 6.2 - A longitudinal redundancy check (LRC) is quick to calculate and can provide some protection to errors. To verify the data, calculate the LRC value again and compare with the original value. Note the use of an unsigned value for the LRC in the data sum version, even though the value is negated at the end – this is necessary, primarily because signed integer overflow is undefined behaviour but also because it would be bad practice to mix signed and unsigned types or to assume the target platform uses two’s complement representation for negative numbers (even though almost all modern platforms do).

The idea of a parity bit may be extended to a parity word, which can be more efficient than calculating parity bits for each word for large amounts of data. The parity word is the exclusive-or of the words in the original data. An alternative approach is to calculate the sum of all the words in the data, treating them as unsigned integers and truncating the sum to be the same length as the words it is calculated from. In this case it is common to append the two’s complement negative of the sum, rather than the sum itself, to the data. Both these methods are basic examples of checksums and often referred to as Longitudinal Redundancy Checks (LRC).

While simple to implement, these basic checksums are limited in their ability to detect certain types of error; for instance, an arbitrary number of words with the value zero may be added or removed from the data without changing the checksum value. The order of the words in the original data is also unimportant, so although rearranging them could significantly change their meaning, it will not change the checksum. The value of these checksums vary only slightly for a small change in the input data, so a relatively small number of errors can easily cancel out causing the checksum to appear correct.
