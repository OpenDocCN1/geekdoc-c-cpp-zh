Other frustrating linker errors might occur where there is a circular dependency between code from different files. While this is another error which should not occur in well-managed projects, if it does the simplest solution may be attempting to recompile the various source files – the programmer’s equivalent of “turning it off and on again.” You may also find the order in which files are linked matters. Both these scenarios are likely to manifest themselves as undefined reference errors which can make them particularly difficult to find when they do occur.

Multiple definitions do not always cause an error. This is the case, for instance, if you define a function with the same name as a standard library function, the linker will assume you intended to do it. Any calls to the library function will be replaced with calls to your function, whether it is what you intended or not. This is known as interpositioning and despite the tendency to create hard (or impossible) to find defects this way, it is an intended feature of the language. Unless you have memorised the entire C Standard Library, it is surprisingly easy to be caught out. If you have an identifier name which could feasibly clash with an identifier found in the C Standard Library, it is probably best to either check or not use it. Now you know it can be done, you might be tempted to start supplanting some of the standard library functions with your own versions – don’t! Unless you have an exceptionally good reason and know what you are doing (and document it), it is a very bad idea.

Worryingly, some linkers may not actually complain about duplicate definitions at all. Linkers are often intended to work with a variety of different languages – since the linker does not work with C source code anyway, there is no need to restrict it to work only with C compiler outputs. Some languages (such as FORTRAN) expect global variables to be defined multiple times. In fact, C does not explicitly forbid multiple definitions for uninitialised global variables, which is possibly more worrying than the fact the linker might not complain about them. Check the documentation for your linker – hopefully there will be an option to enforce a one definition rule to help prevent the issues which might arise from having multiple definitions.

Finally, the linker may fail despite its best efforts and there being nothing wrong with any of the code it is attempting to link. If your code takes up more space than is available on the target, then there is obviously nothing the linker can do. If this happens, your options are rather limited: you can attempt to recompile with different optimisation settings, remove some functionality from your program, rewrite your code so it occupies less space, or find a target with sufficient available space. The last option is the only one which is guaranteed to work.

## Manipulating the linker

Often it is sufficient to simply allow the linker to do its job without interference, but now we have some understanding of the linker, it is worth discussing how we can change its behaviour. This is achieved through customised linker scripts. Most vendors will provide default linker scripts for the targets their tools are intended to work with, and these can often be used without any editing. Indeed, unless you have some special requirements, using the supplied linker script is probably your best option.

Unfortunately, the language used for linker scripts is not standardised and many vendors have developed their own language and syntax to work with their linker. Nonetheless, since all linkers perform the same function, there is some commonality between them and once the principles of one are understood, it should be possible to translate the scripts from one linker to another. Fortunately, many linkers are based on the Unix linker, ‘ld’, which makes this worthwhile considering in a little more detail. If you intend to do any further reading on this subject, you will probably find most readily available information refers to the GNU rather than the Unix version; from the perspective of learning how to use it, this is not a major

There is quite a lot more to writing linker scripts than is described here, and since it is a task which you hopefully won’t find yourself repeating too often, we will introduce some of the more important features and concepts, and allow you to investigate further if you wish.

### Memory regions

The MEMORY command is used to define memory regions. As well as giving each region a name and setting its size and start address, you can set attributes to let the linker know how the region can be used – whether it is a read only or read-write and whether or not it can contain executable instructions.

A linker script may contain only one use of the MEMORY keyword, but multiple regions may be defined at once.

### Memory segments

You can define memory segments using the SECTIONS keyword. There are some standard segments you will come across repeatedly: text, data and BSS. Text is the name given to segments which contain executable code. Data is used for storing initialised global variables and BSS for uninitialised data. I have also seen linker scripts where the BSS region is used to store the call stack and heap (if one is used at all). You can use an additional attribute after a segment definition to instruct the linker to place segments in a specified region.

### Symbols

It is also possible to use a linker script to define symbols. If these symbols are assigned a value as part of a SECTIONS command, then they can be given external linkage and can be referenced in code, although some additional commands may be required to ensure this is the case. Actually referencing the variable is unlikely to be as straightforward as it sounds; linker symbols are neither variables nor object-like macros and, crucially, where a symbol is intended to be used as a variable name, the value assigned to that symbol by the linker is the address where the variable will be stored (the symbol is not a pointer to that address), not the value stored at that address, which is, at least as far as the linker is concerned,

It is also possible to use expressions when assigning a value to symbols. This is useful if you need a symbol to be placed at a non-specific address but one which has certain properties; for instance, you require a symbol to be aligned with a word boundary. Linker expressions have a similar syntax to C expressions and use many of the same operators, but it is important to remember they are distinct. Linker expressions are used to calculate addresses and you need to take care to ensure the result is an address you want to (and can) use.

```
/* Ensure _start runs first. */
ENTRY(_start)
/* Define how big the stack needs to be
 * (1kB). */
STACK_SIZE = 0x400;
MEMORY
{
/* 64kB of ROM (read only), 64kB of RAM
 * (read/write). */
ROM (rx) : origin = 0x00000000,
length = 0x00010000
RAM (rwx) : origin = 0x10000000,
length = 0x00010000
}
SECTIONS
{
/* Put all 'text' sections from compiled
 * code in ROM. */
.text :
{
KEEP(*(.vector*))
*(.text*)
} > ROM
/* 'bss' data goes in RAM. */
.bss :
{
/* Create symbol __bss_start and set to the
 * current address counter value ('.'). */
__bss_start = .;
/* Reserve space for uninitialised global
 * data. */
*(.bss*)
/* Deal with multiple definitions. */
*(COMMON)
/* Align the address counter to a 32-bit
 * boundary then create a symbol for the end
 * of the BSS section. */
. = ALIGN(4);
__bss_end = .;
} > RAM
/* Allocate RAM space for the stack. */
.stack :
{
/* The stack grows down, so allocate space
 * first. */
. += STACK_SIZE;
. = ALIGN(4);
/* Create a symbol for the top of the
 * stack. */
__stack_top = .;
} > RAM
}
```
