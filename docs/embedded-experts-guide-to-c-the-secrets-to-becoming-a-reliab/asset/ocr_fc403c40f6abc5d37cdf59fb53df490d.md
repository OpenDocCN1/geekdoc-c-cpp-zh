In embedded systems, the (roughly) equivalent piece of software is usually known as a board support which in some cases does include a bootloader as well as providing the necessary hardware interface routines.

To be compatible with a bootloader, a program must include some additional data alongside the code to be loaded; this must include a means of identifying the code as something appropriate for the bootloader to copy, often referred to as a boot signature, and some information regarding the size of the code to be Initialisation requirements for global variables and constants may also be included if the initialisation is not performed by the loadable code itself; exactly what information is required and how it should be presented will depend on the bootloader being used. Alternatively, a two-stage bootloader may be used. In this case the first-stage bootloader is generic and responsible only for loading the second-stage bootloader, which is designed to be specific to the application being loaded. The obvious disadvantage to this approach is the additional space required to store the second bootloader and the additional time overhead required to run both bootloaders before the intended application can run; however, the technique is common on more complex systems where single-stage bootloaders would be difficult to design with all the desired flexibility, such as where the application is stored outside of main memory (such as on a hard drive or memory card) and the first bootloader has limited information about exactly what should be loaded. Using a second bootloader also helps to mitigate any problems that may arise from an inability to update the primary bootloader, which is usually only possible if physical access to the hardware and suitable programming tools are available.
