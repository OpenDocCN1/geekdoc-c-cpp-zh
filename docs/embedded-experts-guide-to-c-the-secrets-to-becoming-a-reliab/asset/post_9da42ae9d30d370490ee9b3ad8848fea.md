Like other variables (except arrays), structures are “pass-by-value” by default in C, so when passing structures to or from functions, it is usually preferable to use pointers rather than passing the structures themselves. This avoids the overhead of making a copy of the structure when calling or returning from the function. Furthermore, when passing any pointer or array which you do not intend to modify to a function, remember to qualify it as const. This allows the compiler to assume the variable pointed to will not change and therefore it does not need to store any copies of the variable currently stored in registers back to main memory only to reload them once the function returns. Any register copies may still be lost, but the compiler at least has the option of trying to avoid the additional work required.

### Caveat Lector: using assembly language for optimisation

It is often claimed efficient code is best written using an assembler. It is certainly true a skilled programmer familiar with both the instruction set and the hardware can improve performance this way, occasionally resulting in speed-ups of 10% or more. However, it is error prone and rarely worth the effort. Furthermore, reaching the necessary level of familiarity with an assembler to consistently write more efficient software than when using a compiler necessarily limits the programmer, since assemblers are always platform specific (which also severely limits portability). If you find you do need them, C does support inline assembly instructions – the only way to do this according to the C Standard is to use the asm keyword, although because it is somewhat limited, most compilers also include extensions for better integrating assembly with C.

### Caveat Lector: a note on undefined behaviours

Compilers are entitled to assume undefined behaviours will not occur. While this is less of an issue with compilers which perform little or no optimisation (although undefined behaviour certainly remains an issue, many compilers now exploit this assumption in order to perform aggressive optimisations which can completely change the behaviour of a program. Note that the optimisations do not prevent undefined behaviour – they simply compile the code assuming it cannot occur, even if that assumption is unwarranted. The C Standard allows any compiler to make such changes, since the result of undefined behaviour is, exactly as the name suggests, undefined. Unfortunately, the compiler is often better at spotting potential undefined behaviours than the programmer. To make matters worse, the order in which a compiler performs optimisations can also change the result and there is no standard order for performing optimisations.

Although it is entirely possible to introduce undefined behaviour by accident, the likelihood of doing so increases significantly if you attempt to perform your own optimisations, particularly those which involve relying on the low-level representation of types or assumptions about how code will be compiled. Try to be too clever, and you will quickly run into issues which can be incredibly difficult to resolve – even good debug tools can struggle to make sense of heavily optimised code and the compiled output could well have little in common with the original code. If you do choose to attempt manual optimisations, do so with care. The most useful tool you can have in these circumstances is a static analyser or “lint” – it’s a good idea to be using one anyway, as it will pick up on a plethora of errors that are easily missed.
