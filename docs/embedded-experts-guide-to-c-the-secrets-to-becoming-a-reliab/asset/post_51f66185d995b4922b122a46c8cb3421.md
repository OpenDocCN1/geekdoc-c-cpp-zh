Fortunately, even the humblest of microcontrollers include at least a handful of interrupts. Interrupts are a key tool in transforming code from being purely procedural to incorporating event-driven functionality.

Simply put, an interrupt does exactly what its name implies – it interrupts the program; the processor will store its internal state to be retrieved later and transfer control from the current procedure to an Interrupt Service Routine (ISR). When the ISR is finished, the processor restores its previous state and returns control to the procedure which was interrupted.

There is some overlap between interrupts and callbacks which are another type of function intended to be called indirectly. However, whereas the choice of when to execute an interrupt is deferred to runtime, callbacks are used when you wish to defer the choice of which function to call (or whether a function should be called at all). Furthermore, whereas an interrupt should be invoked through hardware and not user code, a callback may be called in the same way as any other function if implemented using function pointers; although the syntax may not be familiar to you if you have not seen it used before, it is supported by the C Standard and it is therefore possible to write portable callbacks.

## Using interrupts

Interrupts, broadly speaking, fall into one of two categories: maskable and non-maskable. A maskable interrupt is one which can be disabled through software, usually by writing to a specific register. Some processors also have a dedicated instruction to disable or enable all maskable interrupts. It can be helpful to define a macro to execute these instructions using a meaningful symbol name when required: something like #define DISABLE_INTERRUPTS asm “di” will do the job (this particular macro will work with PIC32 microcontrollers, the appropriate instruction for enabling interrupts is. Such macros, or an equivalent function, may already be defined as a compiler extension or as part of a platform-specific library. Non-maskable interrupts cannot be disabled; therefore it is appropriate to use them when an event will always need to be responded to even if the processor is currently servicing another interrupt, such as an emergency stop signal. A reset signal is also an interrupt of sorts, although the programmer has limited control over exactly how the processor will respond.

Where multiple interrupts are used, each will generally be assigned a priority relative to the others. This prevents conflicts when more than one interrupt requires attention; the highest priority interrupt will be serviced first. The reset signal will always have the highest priority – no other interrupt may prevent the processor from responding to it. Non-maskable interrupts will usually have a higher priority than maskable interrupts. On most processors, it is possible to change the relative priorities of the various interrupt sources to fit the application.

ISRs may be reentrant. It is usual for further interrupts to be disabled when entering an ISR and this may even be handled by the processor when an interrupt is encountered. A reentrant ISR is one which subsequently re-enables other interrupts before it returns. In other words, it is possible for the ISR to be interrupted. While re-enabling interrupts as early as possible is a good way to mitigate the risk of missed interrupts, it does cause some problems. For instance, usually a reentrant function should not reference any global or static variables, but because it is not possible to pass variables to or return them from an ISR, the only way of allowing communication with an ISR and other parts of the code is to use global variables. When writing a reentrant ISR it is essential to first identify the so-called critical sections of code – these are the parts which should never be interrupted. It is also best not to share variables between ISRs – give each ISR dedicated global variables for communicating with other parts of code. If there is a possibility an ISR might be interrupted by itself then passing variables should be performed using queues. Read and write operations to global variables should always be atomic – i.e., they should always be performed in a way which guarantees they cannot be interrupted.

## Types of interrupt

Interrupts may be triggered by a wide variety of events. Common sources include timers, communications peripherals and IO signals; some processors have dedicated interrupt pins which are used exclusively for these purposes, but many microcontrollers can be configured to allow some or all of their general-purpose IO pins to be used as interrupts. Software interrupts may also be generated by the processor itself– such interrupts are often referred to as traps or exceptions and on processors which support them may be used to catch illegal instructions, memory access violations or an attempt to execute an instruction with invalid arguments. There may also be one or more dedicated interrupt instructions available; where available these can be used in a similar way to a trap or exception or to make calls to an operating system or kernel routine. The focus of this chapter will be on interrupts which are generated as a result of hardware events; other than for making system calls (which will not be covered here), other types of interrupt are primarily of interest in developing low-level libraries or operating systems.

Timer interrupts are used for periodic events; reasons for using them may include ADC sampling, output updating, task schedulers and hardware polling. Consider a set of traffic lights; obviously, it would be useless to continuously cycle through the possible light states without some delay between them. In a simple application, a delay could be implemented with a simple loop with a fixed number of iterations or by continuously polling a counter until the correct amount of time has passed. However, a more reliable approach would be to use an interrupt to determine when the state needs to change.

One other common use of timer interrupts is to implement a watchdog timer – in this case, the ISR is not intended to be invoked during normal operation; instead, the timer is supposed to be regularly reset before the (almost always non-maskable) interrupt is generated. If the timer is not reset on time, the interrupt will occur and the ISR will be invoked. Such timers are used to detect hardware or software errors which prevent time-critical operations from being performed and force a response from the processor.
