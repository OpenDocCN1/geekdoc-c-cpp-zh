
## The linkage stage

If you have not considered the concept of linkage before, you may wonder why this stage is required at all. A compiler is supposed to produce executable machine code, so what do we need a linker for?

A naïve compiler could simply produce machine code intended to run immediately. While such an approach would appear intuitive and does simplify the process of generating executable software, it has some significant drawbacks. Crucially, this is a very rigid approach: all function and variable addresses must be known when the compiler runs, making it difficult to precompile modules or to reference libraries which have already been compiled. The entire executable must be built as one, and any (even minor) changes to one module require recompilation of the whole project. In fact, even if all the relevant information were available at compile time, given how most software is developed, such a compiler would probably not work.

Source files should not be referenced using a #include directive – only header files should be referenced this way. Assuming we are using each file type appropriately (usage is the only meaningful distinction between the two!), a header file tells us nothing about the contents of any function – it tells us only the type of the return variable and any variables passed to the functions. It also tells us nothing about any functions which are not listed in the header but still feature in the source file. A header file is essentially a contract between the programmer and the compiler: it is a list of promises on behalf of the programmer that at some point, actual functions, rather than just prototypes will be available in some form. In return for the promises, the compiler generates code as if those functions are available, even though it does not know where to find them.

The main purpose of a linker is to fulfill each contract – it resolves the references between different source files. It is able to do this because all necessary information is available at link time. By this point, all source files will have been compiled and all functions will be available. The linker can therefore replace each call instruction generated by the compiler – which call an arbitrary address – with a call instruction to the correct address. If for some reason the required information is not available, the linker will fail and generate an error.

The linker is also responsible for deciding where in memory functions and variables should reside. This can only be done at link-time, since, as we have already discussed, much of the required information is not available at compile time. To achieve this, the linker must first group symbolic references to functions and variables into groups. Each group can then be allocated to a segment in memory. The number of segments and their names will depend on which linker you are using, but in general there are at least three memory segments:

- The code segment, which contains executable instructions,
- The data segment, where global and static variables are stored,
- The call stack, where local variables are stored.

In addition to these three segments, there may also be a heap, where dynamically allocated variables are stored. The linker does not actually need to know anything about what is stored on either the call stack or the heap (nor can it, since their usage is not determined until run-time), but it does need to decide the start addresses of these segments. There may also be an additional read-only data (or “rodata”) segment in some cases, and, particularly where software is compiled to run in a hosted environment, the data segment may be split into initialised and uninitialised segments.

How the linker determines the arrangement of instructions and data also depends on the system architecture. If the system is based around a processor using von Neumann architecture, then the processor accesses only one bus for both instructions and data. The linker must decide where in memory instructions and variables need to be stored, but there is only a single address space to consider. In a Harvard architecture system, there are not only distinct memory sections for data and instructions but the two are physically separate and accessed through separate buses – there is a physical address space for instructions and another for data. While most modern general-purpose processors behave as though they use a von Neumann architecture, many DSPs and microcontrollers use a Harvard architecture.

As well as determining all global and static variable and function addresses, it is also necessary to add some startup code to the software. This is often achieved by linking some standard boilerplate code into the software. This is code which will perform essential initialisation before calling user code. As a minimum, this means loading an initial address into the stack pointer followed by calling the main() (or equivalent) function. For most software it also includes initialising static and global variables. In a hosted environment, some initialisation may be performed by the operating system’s loader, but the startup code will be responsible for passing any arguments from the environment to the program and for returning a value to the environment upon termination. You can write your own boilerplate code if required – this will typically be done in assembler and as such the code will be platform specific.

```
/* This label serves as a function name so the
* linker knows where to put the code. It should
* be made visible to the linker. */
_start:
/* Initialise global memory space. The C
* Standard does not require this to be done,
* but it's a good idea anyway. It is assumed
* the space to be cleared is a multiple of
* four bytes in size. */
ldr r0, =__bss_start
ldr r1, =__bss_end
ldr r2, #0x0
ldr r3, #0x4
/* Clear the first four bytes. */
str r2, [r0]
/* Clear the rest of the global space four bytes
* at a time. */
cglob: add r0, r0, r3
str r2, [r0]
cmp r0, r1
bne cglob
/* Set up the stack pointer. */
ldr sp, =__stack_top
/* Call main with argv = 0 and argc = NULL (0).
* Assumes the calling convention used is for
* arguments to be passed using registers where
* possible. */
ldr r0, #0x0
ldr r1, #0x0
call main
/* If main returns, this is where we end up. Not
* much to do now, so loop forever. */
end: b end
```

Fig 8.1 - A simple, and probably not particularly practical, example of startup code written in ARM assembly. The code clears the space used for uninitialised global data, sets up the stack pointer, and calls main. If main ever returns, the code will loop until the processor is reset. Named constants will need to be defined somewhere – usually by the linker or as assembler directives.

## Linker errors

As with any other part of the build process, linkage can fail or, worse, succeed but produce a result that is not what the programmer intended. Linker errors can be particularly frustrating to resolve since they often have little or nothing to do with the source code you are trying to build. Many linker errors are caused by incorrect configurations, in which case you will need to check your linker documentation to determine the solution. Other than these, the two main types of error you are likely to come across are:

- Multiple definitions of an identifier,
- Missing definitions of an identifier.

You may wonder why neither of these errors are picked up earlier in the build process. In many cases they will, or at least should. However, information not available during earlier stages is available to the linker – prior stages do not import source code from external libraries, so cannot see all the referenced identifiers and function calls in those files. The linker does import these files, so is able to detect errors which did not impact the compiler but make linking impossible.

To illustrate how multiple definitions can remain undetected until linkage, consider a source file which references a header file. At compile time, the actual code corresponding to the header is not required. However, the code is required at link-time. This code may reference other code, which the compiler knew nothing about while dealing with the first file, but which the linker requires in order to complete its job. If a function is defined in the original source file and a function with the same name is defined in the third file then the linker has no way of determining which of these functions is the correct one to use when it is called from the second file. Multiple definitions can easily creep into complex projects if we are not careful in establishing meaningful naming conventions.

Understanding how a definition can be missing and not detected at compile-time is a little more straightforward. The most likely cause is an external identifier is present in a header file but, for whatever reason, is not present in the code which corresponds to that header. Of course, this situation should not occur in well-managed projects, but it still can. One possible cause is the header references either an older or newer version of the code given to the linker. Check you are linking the correct files.
