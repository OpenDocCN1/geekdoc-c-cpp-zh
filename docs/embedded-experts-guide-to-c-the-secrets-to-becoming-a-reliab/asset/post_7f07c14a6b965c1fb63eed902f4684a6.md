
## Bootloaders

Another topic which has not so far been addressed is that it has been assumed the intended application already resides in program memory and it can be run directly. This is often the case, but it is also possible for a program to be stored externally to program memory and loaded when the system is first activated; this is achieved using a bootloader. More generally, a bootloader is any program which loads other programs into memory so they can run; these are usually included as an essential part of most operating systems. Bootloaders are not suitable for all platforms; some microcontrollers are unable to support them and in other cases it may not be appropriate because of the type of memory or because resources are too constrained.

The primary benefit of bootloaders is they offer flexibility; the application code can be loaded from any source the bootloader understands and if multiple possible sources are present it should be possible to choose between them – a feature which could be used, for example, to implement both “normal” and “maintenance” modes. Furthermore, because the loadable code is not launched directly, it becomes possible for programs to be loaded without the need for specialist development tools while also, with a well-designed bootloader, mitigating the risks of self-modifying code.

The most basic bootloaders serve no function other than to identify and copy the bootable program from its source into program memory before branching to the program entry point. Such a bootloader is severely limited; a functional bootloader should at least include a means of verifying the integrity of the code it is loading and determining which code should be loaded if numerous options are available. More advanced bootloaders are also used – the BIOS (basic input/output system) found in older PCs (it has now largely been replaced in new designs) is, primarily, a bootloader but also performs self-test routines, initialises hardware and provides hardware access routines which remain available even after system control has been passed to the loaded software. In embedded systems, the (roughly) equivalent piece of software is usually known as a board support package which in some cases does include a bootloader as well as providing the necessary hardware interface routines.

To be compatible with a bootloader, a program must include some additional data alongside the code to be loaded; this must include a means of identifying the code as something appropriate for the bootloader to copy, often referred to as a boot signature, and some information regarding the size of the code to be loaded. Initialisation requirements for global variables and constants may also be included if the initialisation is not performed by the loadable code itself; exactly what information is required and how it should be presented will depend on the bootloader being used. Alternatively, a two-stage bootloader may be used. In this case the first-stage bootloader is generic and responsible only for loading the second-stage bootloader, which is designed to be specific to the application being loaded. The obvious disadvantage to this approach is the additional space required to store the second bootloader and the additional time overhead required to run both bootloaders before the intended application can run; however, the technique is common on more complex systems where single-stage bootloaders would be difficult to design with all the desired flexibility, such as where the application is stored outside of main memory (such as on a hard drive or memory card) and the first bootloader has limited information about exactly what should be loaded. Using a second bootloader also helps to mitigate any problems that may arise from an inability to update the primary bootloader, which is usually only possible if physical access to the hardware and suitable programming tools are available. If a bootloader is being used to help facilitate field updates to software, then including version and revision identifiers is also a good idea – this allows an out-of-date application to be quickly and automatically identified and an update to be initiated. Including a checksum of the code is also a good idea; the bootloader should calculate its own checksum as part of the load process and only if the two values are equal should it attempt to launch the code.

The bootloader is always the first code to run after power is turned on or the processor is reset. The bootloader checks for new software - if there is a new application available, it overwrites the old one (possibly using some of the free space). If no new application is available, or if loading has been completed, the bootloader calls the application entry function and the application runs as normal.

Fig 11.1 - A simple bootloader sits alongside the application (sometimes called the “bootloadable”) within program memory. When the system is first activated, the bootloader checks for new software and either overwrites the application or allows it to run. More advanced bootloaders can choose from multiple applications at run-time. How the bootloader knows if there is new software available varies considerably from system to system – some bootloaders will only run if hardware is configured correctly through special boot pins, others always run and either perform a check for new software (by attempting to contact a server or other external device) or have a predefined timeout before handing execution over to the application.

## Working with operating systems: what the C Standard says

Many (but not all) embedded operating systems differ from their more familiar relatives in one very significant way – they are not intended to act as a stand-alone piece of software for managing a system; instead, they provide a base upon which specific applications can be built and those applications are often fully integrated into a single executable piece of code with the operating system – from the target system’s point of view, both operating system and application are a single program. As a result, many such operating systems consist of relatively little or no code beyond the kernel – the portion of the operating system responsible for providing crucial functions, but not those such as user interfaces. Some newer embedded operating systems, however, appear more like slimmed-down versions of their desktop equivalents than the specialised programs they have historically been; this is a change which is being at least partially driven by an increase in the number of small but flexible consumer devices, the expansion of the “Internet of Things” and the wider availability of devices and development kits aimed at educational and hobbyist, rather than professional, markets.

Operating systems can simplify writing programs which require multitasking or have complex IO requirements, such as an Ethernet stack, a file system or graphical user interface. They may also provide protection against some (but by no means all) software defects, such as stack overflows, memory access violations and illegal operations. The operating system itself can introduce new system-specific behaviours but may also mitigate some platform-specific behaviours by providing a common interface layer when used on different devices. Much of the interaction between applications and the operating system can be through wrapper functions provided as part of Application Programming Interface (API) specific to the operating system being used. There are also some features within the C Standard Library which can help, although their behaviour will still vary depending on the compiler and operating system being used.

In very simple cases, the only communication between the operating system and an application will occur when the application's main function is called and when it returns. In a hosted environment, the main function may, dependent on the operating system and compiler, be able to accept arguments and return a value; usually the return value is an int and the arguments are an int to communicate the number of arguments being passed, and a char ** which points to an array of strings containing the arguments, but exact details are implementation defined. If such is present, then it allows some configuration of the application to be performed immediately before the program begins to run as well as allowing it to return a value to the operating system when it terminates. Although any value may be returned, the C Standard provides two macros, EXIT_FAILURE and EXIT_SUCCESS, to indicate whether the program ran successfully or not, and any other return value is interpreted in an implementation defined manner. The C Standard Library also provides some functions which allow the program to terminate without returning from main: abort, which causes an abnormal termination, and exit, which causes normal termination. There is also the atexit function, which is used to register callback functions to be invoked when the program terminates normally. There is also _Exit, which causes normal program termination but without invoking any functions registered using atexit.
