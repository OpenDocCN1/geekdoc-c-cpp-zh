## Chapter 5: Interacting with Hardware

Embedded programming, unlike applications programming, tends to involve a much closer coupling between software and hardware. No discussion of embedded programming would therefore be complete without also considering how to write code which interacts with hardware. Such code is necessarily implementation specific; it requires knowledge of the underlying system and the hardware which is available. Unfortunately, this means it can only be covered superficially here since a more in-depth discussion would necessarily be devoted to a single platform. For general-purpose programming, C includes the stdio.h header, which provides functions for reading and writing the standard streams (known as stdin, stdout and stderr) – for most implementations these are typically associated with a keyboard and a display – and files. However, extending the concept of standard streams to embedded systems is not particularly helpful given the wide variations the programmer is likely to encounter. Furthermore, the streams themselves are abstractions which require an implementation to make them meaningful – this is most often provided by an operating system. It is necessary, therefore, for the embedded programmer to be adept at writing software which interacts directly with hardware rather than relying on the functionality provided within the C language.

Hardware in embedded systems tends to be fixed – the original specification is intended to be suitable throughout the life of the system. This does simplify software development somewhat, since drivers do not need to cope with unexpected changes or upgrades which could change their functionality. Peripherals for which drivers are required can be broadly separated into input, output and combined input/output devices. The names are self-explanatory: input devices include peripherals such as keyboards and analogue to digital converters; displays and relays are examples of output devices and input/output devices include data storage and most communications and networking hardware. In the case of microcontroller based systems or system-on-chip platforms the peripherals are often included in the same device as the CPU. On more complex systems, the peripherals are usually separate hardware. In practice it is usually necessary to have at least some hardware which is not integrated.

Peripherals may be either memory-mapped or port-mapped; memory-mapped peripherals are those which can be accessed using the same bus as the CPU uses for memory accesses whereas port-mapped peripherals require a separate bus and, at the lowest level, special machine code instructions to access. Memory-mapped IO has the advantage of being easily accessed using pointers and without the need for any special instructions, which requires either inline assembly code or a precompiled library. In addition, compiler extensions will often allow the address of a variable to be specified, eliminating the need for pointers, and CPU specific header files will often map peripherals to a meaningful structure type.

This chapter shall cover the methods required to interact with memory-mapped IO. The application-specific nature of port-mapped IO makes it difficult to cover in any meaningful depth. It is also not possible to consider every type of hardware you may encounter, so while you may find the information here useful, it will still be necessary to adapt it to the applications you work with.

### Fixed Addresses

Peripherals, unlike variables, typically reside at a fixed location in memory which needs to be known at compile time. In principle, it is easy to map a variable to such a peripheral – simply define a pointer and assign the base address of the peripheral to it. Unless it has function scope, such a pointer should be qualified as static to restrict its visibility. The address the variable pointed to should be const qualified and it may also be a good idea to make the value pointed to volatile. This can result in a rather odd-looking definition, perhaps something like static uint32_t volatile * const p_hw = (uint32_t *)

If you use those sorts of definitions regularly, you can always make them more readable using a typedef. Your compiler may also have a more succinct alternative which will often allow you to avoid the need for tedious and repetitive dereferencing – this may well be preferred from a readability perspective, although it does so by sacrificing portability. Alternatively, similar behaviour can be achieved using a preprocessor definition, such as #define HW_REG (*((uint32_t *) 0x1234)).

You shouldn't, however, be using any of these regularly if you can avoid it; although there's nothing wrong with such a definition in the sense they have a well-defined meaning, they should only be used where it is necessary to access a specific address, for normal variables the compiler is much better placed to choose where a variable should be stored. It's also important to pay close attention to types since how the compiler addresses consecutive words in memory is implementation defined; this is not usually a problem if the words are the same width as the CPU register widths, but for shorter words the compiler may decide it is more efficient to insert padding bytes between words, which can quickly result in a mismatch between the address you think you are accessing and the one you are actually accessing. This will not impact the base address, although errors may occur if it results in misalignment, but many peripherals occupy multiple memory locations so functionality can still be affected if you are not careful.

When accessing peripherals occupying a range of addresses, you have a few options. You could treat the base pointer as an array, preferably replacing fixed-value indices with meaningful names where they appear in the code. This will work and is easy to implement, but it is unusual and may be misunderstood by anybody who happens to review your code in future. It is much more common to use a structure, although it is important to ensure the layout in memory used by the compiler is correct. Where bits within a hardware register are used as flags, it is common to read and write them through bit-fields; however, bit-fields are a particularly poorly defined area of the C Standard and the same results can be achieved in a more robust way using bit-masking – i.e. by using the |= and &= assignment operators to set or clear bits, or even the ^= operator to toggle them, and by using the bitwise-and operator to select appropriate bits before checking their value.

### Endianness

An important issue when communicating between different pieces of hardware – but one which is often overlooked by inexperienced programmers – is endianness. This refers to the order in which individual words of a multi-word variable are stored in memory or appear in a transmission.
