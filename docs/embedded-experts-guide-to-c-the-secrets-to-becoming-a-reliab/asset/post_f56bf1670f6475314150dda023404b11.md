
More advanced methods exist – the best known of which is probably a family of algorithms known as Cyclic Redundancy Checks (CRC). These tend to be slower to calculate than the simple checksums but offer improved reliability in detecting errors. CRC algorithms are based on division rather than addition. The divisor cannot be zero, so the CRC is initialised with a value known as a generator. Understanding the underlying mathematics is not, but it is important to note that for any given length of CRC, there are multiple different polynomials that can be used – therefore there is no canonical 32-bit CRC, 16-bit CRC or any other length CRC. It's also worth noting that the generator polynomial is always one bit longer than the length of the CRC, i.e. an 8-bit CRC uses a 9-bit polynomial and a 32-bit CRC uses a 33-bit polynomial.

```c
/* Define the CRC constants. */
#define CRC16_POLY (0x8005U)
#define CRC16_START (0x0000U)
#define CRC16_MSB (0x8000U)
/* Externally defined functions to reverse bit
 * order. */
```

```c
extern uint8_t reflect8(uint8_t data);
extern uint16_t reflect16(uint16_t data);
/* A slow implementation of the CRC-16
 * algorithm. */
uint16_t crc16(uint8_t const * p_data, int data_size)
{
uint16_t reflection;
uint16_t remainder = CRC16_START;
for (int byte = 0U; data_size > byte; ++byte)
{
/* Reflect the next byte in the message,
 * then shift and XOR with the
 * remainder. */
reflection =
    (uint16_t) reflect8(p_data[byte]);
remainder ^= (uint16_t) reflection << 8;
/* Bit-by-bit division, modulo 2. */
for (int bit = 8; 0 < bit; --bit)
{
    remainder <<= 1;
    if (0U != (remainder & CRC16_MSB))
    {
        remainder ^= CRC16_POLY;
    }
}
/* Reflect the result. Some CRC variants also
 * add an additional XOR at the end. */
return reflect16(remainder);
}
```

Fig 6.3 - Cyclic redundancy checks are widely used for data verification and provide more reliable checking than LRC algorithms. Calculation is slow by comparison, although lookup tables of precomputed values are commonly used to improve performance.

Checksums are related to, and often considered to be, hash functions – a class of functions that map arbitrary amounts of data into a single, fixed-size value, sometimes referred to as a. Such functions have a wide variety of uses – error detection being only one of them. Of particular interest in this context are the cryptographic hash. These tend to be larger than other error detection codes and have three properties that distinguish them from more general hash functions:

- Given a desired hash value, it is practically impossible to find an input to produce that value,
- Similarly, it is practically impossible to find an input that produces the same hash value as any other input,
- A small change in the input will result in a hash value that appears completely uncorrelated with the original hash value.

These properties make cryptographic hash functions suitable for a wide range of applications where either data integrity, security or both are important. While it is trivial to find an input that produces a particular CRC value, and therefore to alter data in such a way that it appears unchanged, it is infeasible to do the same with a cryptographic hash; providing the expected hash value can be independently verified, this prevents not just unintended corruption, but malicious manipulation of the data as well. One common use of such functions is to store and verify. They can also be used to verify the source of data, but only when the hash also includes an additional piece of secret information and are therefore important when implementing some types of digital signature.

## Error correction

More advanced than error detection codes are codes that allow you to attempt error correction. Whereas error detection codes will typically add only a small overhead – a 32-bit CRC may be used (mostly successfully) for detecting errors in blocks of a data several megabits in size – error correction codes substantially increase the amount of data transmitted. The simplest such code involves repeating each bit three times; this allows many transmission errors to be corrected but triples the number of bits that must be sent. Additional repetitions incur greater overheads and repeating only twice provides no benefit compared to no repetition. Slightly more efficient is the Hamming (7,4) code, which encodes four input bits into a seven-bit output – each additional bit is a parity bit for three of the four original data bits – while still allowing all single-bit errors to be corrected. Other Hamming codes exist which can be used to not only correct single errors but to detect double errors as well at the expense of increased overhead.

```c
/* Calculate the parity bit for one byte. */

uint8_t parity (uint8_t byte)
{
    byte ^= byte >> 4;
    byte ^= byte >> 2;
    byte ^= byte >> 1;
    return byte & 1U;
}
```

```c
/* Encode an array of bytes using Hamming (7,4)
 * code. */
void h74_encode(uint8_t *p_in,
                uint8_t *p_out, size_t size)
{
    uint8_t t_half;
    uint8_t b_half;
    uint8_t parity_bits;
    size_t index;
    size_t out_index;
    for (index = 0U; size > index; ++index)
    {
/* Two output bytes are required for each
 * input one. */
out_index = 2U * index;
/* Split the input byte into two
 * nibbles. */
t_half = (p_in[index] & 0xF0U) >> 4;
b_half = p_in[index] & 0xFU;
/* Shift bit 3 into position 4 for both
 * nibbles. */
t_half = (t_half & 0x7U) |

((t_half & 0x8U) << 1);
b_half = (b_half & 0x7U) |
((b_half & 0x8U) << 1);
/* Get the parity bits. */
parity_bits = parity(t_half & 0x15U) << 6;
parity_bits |= parity(t_half & 0x13U) << 5;
parity_bits |= parity(t_half & 0x07U) << 3;
/* Merge the parity bits and the data
 * bits. */
t_half |= parity_bits;
/* Repeat for the second nibble. */
parity_bits = parity(b_half & 0x15U) << 6;
parity_bits |= parity(b_half &
0x13U) << 5;
parity_bits |= parity(b_half &
0x07U) << 3;
b_half |= parity_bits;
/* Put the results in the output array. */
p_out[out_index] = t_half;
p_out[out_index + 1U] = b_half;
}
}
```

```c
/* Decode an array of Hamming (7,4) encoded bytes. */
void h74_decode(uint8_t * p_in,
uint8_t * p_out, size_t size)
{
uint8_t error_bit;
uint8_t t_half;
uint8_t b_half;
size_t index;
size_t out_index = 0U;
for (index = 0U; size > index; index += 2U)
{
/* Decode the first input byte. */
error_bit = parity(p_in[index] & 0x55U);
error_bit |= parity(p_in[index] &
0x33U) << 1;
error_bit |= parity(p_in[index] &
0x0FU) << 2;
/* Correct any bit errors, remove the parity
* bits and put bit 4 back in
* position 3. */
t_half = p_in[index] ^
(0x80U >> error_bit);
t_half = (t_half & 0x7U) |
((t_half & 0x10U) >> 1);
/* Repeat for the second input byte. */
error_bit = parity (p_in[index + 1U] &
0x55U);
error_bit |= parity (p_in[index + 1U] &
0x33U) << 1;
error_bit |= parity (p_in[index + 1U] &
0xFU) << 2;
b_half = p_in[index + 1U] ^
(0x80U >> error_bit);
b_half = (b_half & 0x7U) |
((b_half & 0x10U) >> 1);
/* Combines nibbles into one output
* byte. */
p_out[out_index] = (t_half << 4) | b_half;
++out_index;
}
}
```

Fig 6.4 - Hamming codes are easily computed error correcting codes; the most common is the Hamming (7,4) variant. Bit usage is more efficient than with basic repetition, but the total number of output bits is still almost twice the number of input bits. The encoding interleaves the three error checking bits with the four data bits in such a way as to produce a systematic code. This improves performance when decoding – the error-checking not only identifies if an error has occurred, but can also directly identify which bit has changed value. Furthermore, the example always “corrects” at least one-bit: since the Hamming codes are seven bits long, the most significant bit of the eight-bit bytes used can be changed without causing any problems. Other error correcting codes have been developed which are substantially more efficient, but also considerably more difficult to implement.
