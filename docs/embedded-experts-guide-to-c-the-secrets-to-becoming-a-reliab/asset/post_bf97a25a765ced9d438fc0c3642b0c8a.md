
The period will probably crumble to dust long before it repeats itself – but knowing the current state and configuration, which can be determined by observing only a handful of outputs, is enough to predict the next output.

Several algorithms have therefore been developed to address this – these are known as cryptographically secure pseudorandom number generators. These can most easily be implemented by using the key stream generated by a stream cipher or encrypting a free-running counter output using a block cipher, in both cases using the key as the seed value. Other methods are based on hard mathematical problems, often the same as those used in asymmetric encryption, but these tend to be slow to compute. Alternatively, a true random number generator can be created by measuring some external variable that varies unpredictably, such as thermal noise; these are easy to compute, but slow because it is necessary to accumulate the measurements over a long period. Some algorithms combine both approaches to provide a degree of true randomness by periodically reseeding the generator while also benefiting from the speed advantages of performing encryption compared to accumulating random data.

For purely algorithmic approaches, regardless of the method used to generate a random number, there will always be the problem of choosing an initial seed value to initialise the algorithm. If the same value is used repeatedly, the sequence of random numbers will always be the same. The seed value itself, therefore, needs to be sufficiently random. At the very least, it must be sourced from somewhere independent of the code that uses it; some suggested sources are timers with a period derived from a source other than the CPU clock, unused ADC inputs that have been made deliberately noisy or specialised random number generators. It is still possible for these sources to exhibit bias in the outputs they produce if they are not implemented with care.

## Sharing keys

Key sharing has long been a significant hurdle to secure cryptography and was one of the main motivations for developing asymmetric ciphers. You may be tempted to ship your embedded products with a hard-coded key. Although simple, this approach has a number of weaknesses. First, every device produced should have its own key, otherwise compromising one device will compromise every other device as well. Second, if a device is compromised it becomes useless, since it is not trivial to change the key. Finally, a database of every device and its key must be maintained and copied to every other device that may wish to communicate with the device.

An alternative might be to generate a symmetric cipher key with a limited lifetime (often called a session key) and to send this to the device you wish to communicate with, first encrypting it using an asymmetric cipher with the public key for that device. This eliminates the need to have a hard-coded secret key stored on every device since a public key can be freely distributed. Frequently changing the key improves security and since it can be discarded once it is no longer required the risk of it being compromised is reduced. However, such a scheme lacks a property known as perfect forward secrecy – if the private key used to decrypt the short-term key is ever compromised, all past and future keys can be recovered from a record of the communications between devices.

Many cryptographic protocols aspire to the higher standard imposed by perfect forward secrecy; even if the private key is compromised, it should not be possible to recover past session keys or the messages encrypted with them. At first, this might appear to be an impossibly high standard – it requires that the session key can never be directly communicated between devices. It is, however, entirely possible to achieve; the Diffie-Hellman key exchange was the first such scheme to be publicly proposed and continues to see widespread use.

Other key exchange algorithms exist. They will not be covered in detail here because, like asymmetric ciphers, there are already a number of libraries for implementing them. There also remains the problem of verifying that the key exchange is taking place with the correct party, which is not a trivial problem to solve. A degree of trust is required for most solutions; for instance, the X.509 certificate standard is a critical part of the TLS protocol used to secure network traffic, but ultimately relies upon a number of trusted certificate authorities to vouch for the authenticity of the certificate; if a certificate authority is compromised in some way (which has been known to happen), then certificates issued by that authority may no longer be relied upon.
