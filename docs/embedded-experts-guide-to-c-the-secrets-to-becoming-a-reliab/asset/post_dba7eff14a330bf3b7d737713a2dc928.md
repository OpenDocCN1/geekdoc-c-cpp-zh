
Whenever a new task is added to the queue, its expected time to completion must be compared to the other tasks, including the running task. Only if the new task is expected to take less time to complete than the currently running task will the scheduler switch execution to the new task.

STCF scheduling has the advantage of context switching (which is generally an expensive operation in terms of processing time) being reduced compared to round-robin scheduling and average turnaround time is improved. However, average response time is likely to increase significantly and with a long running time may be repeatedly pre-empted in favour of shorter ones. STCF is an example of a dynamic scheduler – one which allows task priorities to change after they have been added to the task queue. Dynamic schedulers are usually an unsuitable choice for embedded systems – they require significant scheduling overhead and are much less deterministic than static schedulers. However, the scheduling principle behind STCF – that the shortest task should be the first to run – can be used to determine the relative priorities of statically scheduled tasks. We shall return to this later.

Regardless of which scheduler you use, multitasking is not without risk. Sharing variables between tasks is not trivial – reads and writes to these shared variables must be atomic. Functions which are shared between threads should ideally be reentrant, although functions which are restricted to a single thread need not where this is not possible, the functions must use some alternative means, such as a mutex, to prevent concurrent accesses to shared resources. Most functions in the C Standard Library are not guaranteed to be reentrant.

In most instances it is desirable to allow the scheduler to pause one task and pre-empt it with another, otherwise there would be little point in using the scheduler at all. However, there are times when a task must not be pre-empted – some parts of a task may be deemed critical which must be allowed to run.

This is the case when accessing global variables, for instance. Ideally, a single atomic operation would be used to prevent issues arising from pre-emption, but this is not always possible. For instance, if the data to be accessed is a structure or array, multiple read or write operations will be required, even if the word size of individual members or elements is the same as the processor word size.

In this situation, the easiest way to prevent pre-emption is often to disable interrupts. This must be done in a way which does not disrupt future scheduler timings, so if it is not possible for the interrupt to remain pending until the code has exited the critical section, it may also be necessary to stop the timer which drives the scheduler interrupt for the duration of the critical section, or to use an alternative workaround mechanism. Merely disabling interrupts does not work on multi-processor or multi-core systems, where concurrent access to resources will remain possible on many architectures. Furthermore, unless only specific interrupts are disabled, then no interrupts may be serviced during the critical sections. This may be the intended result, since an interrupt service routine could potentially require access to the same shared resources, but as a general rule, interrupts should be disabled only when necessary and not merely for convenience.

This is where mutexes and semaphores, concepts introduced earlier in this chapter, become important. As has already been mentioned, mutexes and semaphores must be implemented in an atomic manner. Many processors include special instructions to facilitate this: examples include special test-and-set and compare-and-swap instructions. However, these may not be available, particularly if you are not using a processor with significant built-in support for multitasking. Careful programming and a proven library are crucial to developing multithreaded code for accessing shared resources.

What does a task queue look like?

We have mentioned having a task queue several times, but so far have not discussed how one could be implemented. This may not be a problem – when using a third-party library to implement multitasking, such details are often of little interest to the programmer. However, even if you do not intend to implement your own scheduler, understanding the essentials can help clarify some of the other concepts we have covered.

In its simplest form, a task queue could be implemented as an array of task contexts or task handles. Each task handle is a struct storing all the information required about the task it relates to: at the very least, it must store a reference to the task entry function, the current program counter and stack pointer being used by the task and the values to be stored in other registers when the task is running. It also makes sense to include some additional information about the task, such as flags to indicate whether the task is suspended or waiting for an external resource.

The task reference itself is easily implemented using a pointer to a function, although the syntax can appear arcane if you have not seen it before (it is common to use a typedef to improve readability). This requires the entry function of every task uses a common function signature – often the function will be called with no parameters and will not return a value, although this need not be the case provided all tasks are called and return in the same manner. This raises the question of how data is passed between tasks. Global variables can be used, but the usual precautions associated with them apply; indeed, the running of multiple tasks concurrently increases the risks associated with using global variables. Furthermore, using global variables prevents the tasks from being re-entrant.

Although the queue may be implemented as a simple array, if we wish to add and remove tasks from the queue in a logical manner, using a linked list to store the task handles seems a more logical approach. Each entry in the list therefore stores the task handle and a pointer to the next entry. Interface functions for adding and removing tasks will need to be provided in the scheduler library, but these are no more complicated than the add and remove functions for any other linked list.

```
/* A minimal struct to contain the task list
* entries. */
typedef struct task_s
{
/* Pointer to the next task list entry. */
struct task_s * p_next_task;
/* Pointer to the task reentry point.
* Initialise to the task's entry function.
* Save/restore the CPU's link register
* here. */
void (*p_reentry)(void);
/* Pointer to the task stack. Initialise to
* the start of the task's stack. Save/restore
* the CPU's stack pointer here. */
char * p_stack;
/* Stored contents of other CPU registers;
* assumes 'int' is same width as a CPU
* register. NUM_GPR is the total number of
* general purpose registers (excludes the
* program counter, stack pointer and link
* registers). */
unsigned int cpu_register[NUM_GPR];
} task_t;
```

Fig 10.2 - A minimal example of how tasks can be stored in memory. When first added to the list, the next task should be set to either NULL or to point to the first task in the list, p_reentry should point to the entry function of the task, p_stack to the task's stack space. The values stored in the cpu_register array need not be explicitly set, although setting them to zero does guarantee that they will have defined values when the task is first run. When switching to another task, the contents of CPU registers (other than the program counter) are copied into the appropriate structure members. The scheduler then retrieves the next task (or the first task, if the entry is the last task in the list) and loads the contents of structure members into the appropriate registers. On returning from the scheduler, the CPU will jump to the address in the link register – because this value has been set to the re-entry address of the next task, control can be passed to a different function to the one which had been executing before the scheduler was invoked.

## Priority task scheduling

Both the coroutine and round-robin scheduling examples we have discussed so far are adapted from a basic first-in, first-out - the tasks in the queue is serviced in the order in which they arrive. Indeed, if tasks complete before their allotted processing time has passed in the round-robin case or do not yield in the cooperative case, both are equivalent to a FIFO based scheduler. The disadvantage of this approach is it is desirable for a task to “jump the queue,” yet the scheduling algorithms we have discussed have no mechanism for allowing this.

The relatively straightforward round-robin scheduler may be adapted to allow tasks with varying priorities to be scheduled.
