# Chapter 2:
Writing Safer C

Having explored some of the reasons C has a reputation for being an unsafe programming language, it seems reasonable to look for ways in which we can make it safer and more reliable to use. This can certainly be done, and in this chapter, I intend to outline some of the techniques you can use; but as with anything, it is a process that takes practice, and those techniques need to be consistently applied. Before proceeding, it is important to recognise that few, if any, programmers can truly claim to be experts in C. ¶Do not fall into the trap of thinking that this, or any other, book provides a definitive guide to writing perfect C; such a guide simply does not exist.

The hypothetical guide-to-C would necessarily include many more “do not” statements than it would “do” statements. The sheer number of undefined, unspecified and implementation defined behaviours and often questionable syntax in the C Standard makes writing it almost impossible to use all the features of the language without finding yourself caught out at some point. This may be succinctly summed up by stating that although there is no single right way to write C, there are many wrong ways. “Good code” is not just code that works – it is code that can be understood and maintained and, ideally, ported from one system to another with minimal There are, of course many things that you should do: every variable should be initialised before being used, for instance, since the compiler makes no guarantees regarding their initial value.
