# Caveat Lector: a note on undefined behaviours

Compilers are entitled to assume undefined behaviours will not occur. While this is less of an issue with compilers which perform little or no optimisation (although undefined behaviour certainly remains an many compilers now exploit this assumption in order to perform aggressive optimisations which can completely change the behaviour of a program. Note that the optimisations do not prevent undefined behaviour – they simply compile the code assuming it cannot occur, even if that assumption is unwarranted. The C Standard allows any compiler to make such changes, since the result of undefined behaviour is, exactly as the name suggests, undefined. Unfortunately, the compiler is often better at spotting potential undefined behaviours than the programmer. To make matters worse, the order in which a compiler performs optimisations can also change the result and there is no standard order for performing optimisations.

Although it is entirely possible to introduce undefined behaviour by accident, the likelihood of doing so increases significantly if you attempt to perform your own optimisations, particularly those which involve relying on the low-level representation of types or assumptions about how code will be compiled. Try to be too clever, and you will quickly run into issues which can be incredibly difficult to resolve – even good debug tools can struggle to make sense of heavily optimised code and the compiled output could well have little in common with the original code.
