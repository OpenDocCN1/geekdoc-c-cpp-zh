Dynamic (heap) memory allocation is generally considered bad practice in embedded systems. This was hinted at in the previous section, where the lack of type safety was mentioned, and above, with reference to the issue of dangling pointers. One other major issue with dynamic allocation is memory fragmentation – that is, as portions of memory are allocated and freed, there may be a significant amount of free space that is unsuitable for further allocations because it is non-contiguous. When space is relatively limited, as is the case with most embedded systems, it can quickly become exhausted by repeated dynamic allocations, even if the space appears to be available. Later, we will explore some alternatives that can be used to provide heap-like allocation in a more reliable manner. For now, it is best to accept that functions such as malloc should not be used, no matter how useful you may have found them in the past.

## There are no runtime checks in C!

Part of C’s appeal is that it typically compiles to efficient machine code; this is achieved, in part, because of the absence of any significant runtime environment and the associated software overhead. The downside of this is that no runtime checks are performed to prevent problematic code from being executed – even checks for common errors are not performed. Although in a hosted environment some code will trigger operating system intervention, this is generally very limited and, when it does occur, there is often nothing the operating system can do other than terminate the program. For standalone programs, there is no operating system to intervene. In the case of the most serious errors, hardware may behave unpredictably, become unresponsive or, in some cases, force a reset (which is, perhaps, the least problematic of possible responses!). Since the result is not desirable in either case, the programmer clearly has a motivation to include any necessary runtime checks in their code.

No code is generated to prevent null pointer dereferencing or division by zero, for instance. Nor is code produced to protect against integer overflows or a myriad of other potential problems. It may be the case that you wish to exploit integer overflow behaviour, but if you do not, it is your responsibility to prevent it, not the compiler’s.

To make matters worse, there are minimal checks performed at compile time, so many problematic pieces of code will not even be accompanied by a. If a program is syntactically valid C, there is a good chance it will compile, even if it contains multiple instances of undefined behaviour.

As we have already seen, the C Standard allows and, in some cases, even requires some seemingly odd behaviours.

## Chapter 2: Writing Safer C

Having explored some of the reasons C has a reputation for being an unsafe programming language, it seems reasonable to look for ways in which we can make it safer and more reliable to use. This can certainly be done, and in this chapter, I intend to outline some of the techniques you can use; but as with anything, it is a process that takes practice, and those techniques need to be consistently applied. Before proceeding, it is important to recognise that few, if any, programmers can truly claim to be experts in C. Do not fall into the trap of thinking that this, or any other, book provides a definitive guide to writing perfect C; such a guide simply does not exist.

The hypothetical guide-to-C would necessarily include many more “do not” statements than it would “do” statements. The sheer number of undefined, unspecified and implementation defined behaviours and often questionable syntax in the C Standard makes writing it almost impossible to use all the features of the language without finding yourself caught out at some point. This may be succinctly summed up by stating that although there is no single right way to write C, there are many wrong ways. “Good code” is not just code that works – it is code that can be understood and maintained and, ideally, ported from one system to another with minimal. There are, of course many things that you should do: every variable should be initialised before being used, for instance, since the compiler makes no guarantees regarding their initial value.
