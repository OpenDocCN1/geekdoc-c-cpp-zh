The major disadvantage when using callbacks is they are still pointers and therefore come with all the same problems as other pointers – crucially, it is still the programmer's responsibility to ensure the pointer is valid. In fact, there is an additional risk when using callbacks compared with other pointers – attempting to dereference an invalid pointer to a function will result interpreting whatever happens to be at the pointed-to address as executable instructions, which could have catastrophic consequences (and is most definitely an example of undefined behaviour).

Callbacks are implemented using pointers to functions. This allows a reference to the function to be treated as any other variable would be: the function pointed to can be changed and the reference can be passed to other functions as an argument or it can be stored in an array of similar references as required. The syntax for calling a function using a pointer is no different to calling it directly, except the name of the pointer takes the place of the function name in the call; similarly, it is not necessary to explicitly take the address of a function when assigning to a pointer to a function, the function name alone (not followed by any parentheses or arguments) is sufficient. From the programmer's perspective, the name of the reference becomes an alias of the function it refers to.

Callbacks can be used to extend or alter the functionality of other functions; for example, a generic sorting function may contain code to loop through an array of values; a callback may then be used to determine how to sort them on each iteration, as is the case with the qsort function in the C Standard. Note that it does not matter to the calling function what type is stored in the array (although it usually does matter how much memory each instance of the type occupies) – this is only important to the callback. This allows common code to be reused using only a single function while the task-specific code can be contained within callbacks – using the example of the same function can be used to sort arrays of any type and in any way which the programmer desires simply by varying the callback used. The required callback, in these cases, is passed to the other function as a parameter when calling and this is the simplest example of their use. A more complex example would take multiple possible callbacks and determine the correct one to call; this could be as simple as a callback to be used if an operation is successful and another to be used if the operation fails, but any number of callbacks can be used allowing much more complex applications, such as the calculator example from earlier, to be implemented in this way.

Callbacks may be combined with interrupts and this can be useful when the action which needs to be taken when servicing the interrupt varies – this could be, for instance, because there are multiple periodic events which must be cycled through, because several resources share a single interrupt or because an external bus is being used to communicate with multiple external devices. An ISR can select the appropriate callback itself or can retrieve the required reference from a global variable which has been assigned to elsewhere in the code. Alternatively, the callback need not be invoked during the ISR; the direction of communication can be reversed and the ISR can either store a reference to the desired callback in an appropriate global variable, or store the information required for the callback to be selected by other code. The callback can then be invoked when necessary, without causing additional, potentially unpredictable, time servicing the interrupt. This is achieved using an event loop somewhere within a function which runs within the context of the main program control flow – a loop which waits for and responds to new events being registered, essentially another example of busy-waiting.

## Software interrupts

Software interrupts are interrupts which are intentionally triggered through software by executing an interrupt instruction. They have so far not been discussed in this chapter. There are two reasons for this: first, they are of relatively limited use outside of a hosted environment (one which includes an operating system), and second, the concept can be a difficult one to grasp at first because they initially appear to be little more than a means of calling a function indirectly, which can lead them to be confused with callbacks.

The limited use of software interrupts outside of a hosted environment is largely because there is little need for them when the entire memory space is available to the programmer since they can be replaced with a normal function. One of the most common uses for software interrupts is to make system calls – i.e., to request some action from the operating system which the program itself does not have permission to perform – which is not necessary if the required functions can be called directly. At this point, such functionality is of little use or interest, but when working with an operating system it becomes relevant.
