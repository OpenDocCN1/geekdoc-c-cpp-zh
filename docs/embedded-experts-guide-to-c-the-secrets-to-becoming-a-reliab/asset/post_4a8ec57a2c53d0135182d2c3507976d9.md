
Some variables may also be stored and shared by the operating system.
These are referred to as environment variables are always stored as a string and cannot be accessed directly, although the C Standard Library provides the getenv function for reading them (but no function to create or modify them). This function accepts a pointer to a string as argument and returns a char * pointing to the relevant environment variable, or a NULL pointer if the variable cannot be found. Do not attempt to modify the array pointed to by the result of a call to getenv – this is undefined behaviour.

An operating system may also provide a command processor which is capable of interpreting and executing high-level instructions; if this is the case, a program may request the operating system executes another program or system function and returns the result using the system function. The system function accepts a pointer to a string as argument; if a NULL pointer is provided, then the return value will be non-zero only if a command processor is available. If a pointer is provided, then the function passes the contents of the pointed-to string to the command processor in an implementation-defined manner and returns an implementation-defined value – the actual behaviour will be determined by both the compiler and the command processor which is present and the C Standard imposes no requirement on either other than the compiler should document its behaviour. The C Standard also warns any program calling system may “behave in a non-conforming manner or ... terminate”.

Signals provide a limited but efficient method for the operating system and application to communicate; the operating system (or in some cases, the application itself) generates a signal, which is then caught by the application. When a signal is caught by the application normal program flow is suspended and the signal can either be handled by a default signal handler or a custom signal handler may be invoked. The C Standard defines six signals:

- SIGABRT (abort),
- SIGFPE (floating point error),
- SIGILL (illegal instruction),
- SIGINT (interrupt),
- SIGSEGV (segmentation violation), and
- SIGTERM (terminate).

```

/* The signal handler. */

/* Do something with the signal. */
}

/* main() registers the handler and then loops. */
void main(void)
{
/* Register the SIGINT handler.
* Assume this is successful; a more complete

}
```

Other signals may also be available, but their meanings will be implementation defined. If the application wishes to generate a signal of its own, it can do so using the raise function, which results in an indirect call of the relevant signal handler. If and when signals are raised, other than by a call to the raise function, is implementation defined. ## Working with operating systems: the reality

Although useful for general purpose programming, the previous section is not especially helpful for many embedded operating systems, particularly more resource-constrained platforms. The C Standard has very little to say on interacting with operating systems and what it does say is almost invariably accompanied by the caveat that the behaviour is implementation defined – if the implementation chooses to define it at all. Applications on embedded systems are often intended to run indefinitely without returning and even when an operating system is present, the prototype for main is often still void since there is little, if anything, the operating system can do with the returned value and very limited means for providing arguments to main. Similarly, such operating systems may not implement any means of storing and accessing environment variables or sending and receiving signals. Furthermore, many embedded operating systems are designed to be statically linked to the applications running on them – the operating system and application are compiled together as a single program. Operating system functions are largely available to call from the application in the same way as any other function and as a result there is relatively little need to communicate indirectly with the operating system.

Embedded operating systems still provide useful functionality. They typically include a scheduler and implement mutexes and semaphores as a minimum and often memory management routines will also be provided. Most will also include a Hardware Abstraction Layer (HAL); essentially a library of functions which allow software to interact with the platform’s hardware without requiring knowledge of how it works. This is arguably beneficial, not only in terms of reducing the time and risk involved in writing the necessary code yourself, but also for making software more portable. More advanced operating systems go further and provide even more complex functionality, such as filesystems and inter-process communication.

Historically, embedded operating systems have mostly also been real-time operating systems – they are guaranteed to run tasks according to strict time constraints. Despite this, there is still relatively little standardisation of how operating systems implement these functions, particularly for simpler operating systems, and software written to work with one system is unlikely to be easily portable to another. Examples of embedded operating systems which behave in a proprietary manner are:

- Azure RTOS (previously ThreadX).
- FreeRTOS. (and the related),
- SAFERTOS and
- OPENRTOS.

There have been some efforts to standardise operating systems, the most successful of which is POSIX. This is briefly described in the next section, although operating systems which are truly POSIX compliant are relatively rare and somewhat more complex than can be supported by smaller embedded systems.

## POSIX

The histories of the C language and the Unix operating system are thoroughly intertwined; they were initially developed almost in parallel and computer scientist Dennis Ritchie was heavily involved in both. As computers became more affordable and widespread, many new variants of Unix and other Unix-like operating systems emerged; this led to efforts to develop a standardised interface for operating systems to maintain compatibility between them and ensure portability of programs from one operating system to another. This resulted in the IEEE publishing the first version of the POSIX (Portable Operating System Interface) standard in 1988. Development has continued and the most recent version of the POSIX standard (at the time of writing) was in 2017.

POSIX was developed with C compatibility in mind and the C Standard Library includes features to provide compatibility with POSIX. Standard methods are provided for creating and managing inter-process messaging, and many other common tasks. A number of additional signals are also introduced by POSIX; although these are not part of the C Standard they are common across all POSIX operating systems so remain relatively portable. Simply, POSIX allows the C Standard Library to be significantly expanded in a way which is portable, provided the target system runs a POSIX compliant operating system. This makes POSIX compliant operating systems a good choice when deciding which system to use. The unistd.h header file provides much of the POSIX API for the C language.
