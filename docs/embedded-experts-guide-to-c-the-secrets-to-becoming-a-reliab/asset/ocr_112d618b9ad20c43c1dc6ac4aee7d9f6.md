ISRs may be It is usual for further interrupts to be disabled when entering an ISR and this may even be handled by the processor when an interrupt is encountered. A reentrant ISR is one which subsequently re-enables other interrupts before it returns. In other words, it is possible for the ISR to be interrupted. While re-enabling interrupts as early as possible is a good way to mitigate the risk of missed interrupts, it does cause some problems. For instance, usually a reentrant function should not reference any global or static but because it is not possible to pass variables to or return them from an ISR, the only way of allowing communication with an ISR and other parts of the code is to use global variables. When writing a reentrant ISR it is essential to first identify the so-called critical sections of code – these are the parts which should never be interrupted. It is also best not to share variables between ISRs – give each ISR dedicated global variables for communicating with other parts of code. If there is a possibility an ISR might be interrupted by itself then passing variables should be performed using queues. Read and write operations to global variables should always be atomic – i.e., they should always be performed in a way which guarantees they cannot be interrupted.
