## Chapter 10: Multitasking

We are all used to the idea of computers performing many tasks at any one time. As well as being able to run multiple applications, modern operating systems run numerous background processes. Although servicing interrupts could be considered a basic form of multitasking, a more general ability to balance multiple concurrent processes which have no clear interrupt mechanism is necessary in many embedded systems. There are times when this functionality is required and understanding how to properly implement a system running multiple processes is a valuable skill for any embedded engineer to have.

Consider a simple system which must handle a small number of tasks: communicate with external systems through a UART, read user input from a control panel and update a display. Initially there might appear to be two ways to structure your program: perform each task sequentially in a loop so each task runs once in each loop iteration; use interrupts to handle each task as required – you could use a buffer full/empty interrupt for the UART, an interrupt-on-change to handle the user input and a timer interrupt to update the display. So far in this book we have assumed one of these approaches (or a combination of the two) is sufficient to tackle any programming problem we might face.

The major disadvantage of the first approach is three essentially unrelated and asynchronous tasks are being run one after the other – the rate at which the UART communicates has nothing to do with the rate at which user input arrives. A large amount of processing time is also potentially wasted monitoring tasks which do not need attention.

Using the second approach, we handle each task as required, but without considering whether or not the task needs handling at that moment – a delay of a few milliseconds when reading user input or updating a display is unlikely to be noticeable to the user, and waiting until a buffer is full is not the ideal way to read data from the UART. In this case, processing time is also wasted, this time in doing nothing. Both approaches also risk one task from “blocking” another – it is hardly desirable for data to be lost from the UART because the buffer is full, but the processor is busy updating the display!

A third approach is to introduce a supervisory task, called a scheduler, responsible for balancing the needs of the various tasks. This is the basic principle behind multitasking. Software multitasking is most useful when a system is expected to perform multiple distinct tasks which need not be synchronous. That is not to say the tasks cannot be related, or even interdependent, to each other; but there must be sufficient demarcation between them so they need not be run sequentially. Multitasking is particularly beneficial in situations where it is not feasible for all tasks to be either interrupt-driven or background tasks suitable for running in the main program loop. This may not be the case in our simple three task example, but as the number of tasks increases, so too does the difficulty of developing a predominantly interrupt-driven solution to managing them – you quickly run out of interrupts and the likelihood of those you do have conflicting with each other rapidly increases.

There are two main multitasking paradigms: cooperative multitasking and pre-emptive multitasking. Under the cooperative model, the scheduler is responsible for starting each task, but once a task is running, it will continue to do so until it voluntarily yields control back to the scheduler. Under the pre-emptive model, the scheduler can interrupt a running task and transfer control to the next one. Cooperative multitasking is easier to implement and typically requires less memory to keep track of processes but can cause issues if poorly coded processes refuse to yield control for an unnecessarily long length of time. Pre-emptive multitasking overcomes this issue at the expense of a more complex scheduler and increased memory usage; greater care is also required when writing processes to work with a pre-emptive scheduler. Like an interrupt, a pre-emptive scheduler disrupts the normal control flow of the program. There may be times when this disruption is problematic; for instance, if we extend the example from earlier to include two processes using the UART, we would not want one of these processes to pre-empt the other mid-transmission. To prevent such a situation from arising, we need to protect certain shared resources from being accessed by different tasks simultaneously.

Most modern general-purpose operating systems adopt a pre-emptive approach to multitasking, although the cooperative model is still used in many embedded systems and some specialist applications. Although operating systems will typically include a scheduler, therefore making implementation easier, an operating system is not strictly required for multitasking. Likewise, some hardware has features designed to aid multitasking, but hardware support is not essential.

If the compiler you are using does not support C11 or later, there is no in-built support for multithreading unless it is provided as a compiler specific extension. C11 introduced two optional additions to the C Standard Library: threads.h and stdatomic.h which provide new functions to aid in developing multitasking software. Third-party libraries are often available, one of the better known is the pthreads (or threads) library. Most multithreading libraries require operating system support.

One specific benefit of multitasking is it can be used to eliminate many instances of busy waiting from code. Busy waiting (also known as spinning) is a technique used to wait for a resource to become available. It will often take the form of an empty while loop which continuously checks to see if the required resource is available. No other processing can take place while a busy wait is running, which is often considered undesirable, although there are times when no alternative is possible.

```
/* Start a new conversion. */
adc_start_conversion();
/* Wait for sampling to finish. */
while (!adc_finished())
{
/* Stay in the loop until done. */
}
/* Make a copy of the sample and continue. */
new_sample = adc_read();
```

Fig 10.1 - A simple busy wait loop; in this case, the software is waiting for an ADC conversion to complete; the ADC hardware is queried on each loop iteration to determine if the sampling has completed. Depending on the hardware and sample frequency used, this could take some time, during which the CPU could devote cycles to other, useful activities.

### Processes and threads

Before launching into an in-depth discussion of how multitasking can be implemented, it is worth defining some key terms. You will repeatedly hear the words process and thread when talking about multitasking, but what are they? Both processes and threads refer to units of independent instruction sequences which can be run concurrently with other instruction sequences. Processes are typically entirely independent of each other – they do not share memory and in most cases cannot communicate with each other, if one process is required to send a message to another, some special mechanism must be available for this purpose. Conversely, threads form part of processes and the demarcation between individual threads within a process is much less clear – two threads from the same process share memory; they can often communicate directly with each other and special care must be taken to avoid unwanted interactions between them. It is entirely possible to use multiple threads, even if only a single process is executing. There is also no reason why multiple, single-threaded processes cannot run concurrently. So far in this book, we have treated all the software we have discussed as though it is the only process running, usually consisting of only one thread.

Since process may be used (almost) synonymously with program, within the scope of this chapter, we are primarily concerned with threads. We have stated threads within a process share memory. Although this is true, each thread still requires its own stack, registers and program counter. If we wish to switch execution from one thread to another, the state of the running thread must be stored and the state of the thread replacing it must be loaded into the processor's registers. Many processors include hardware to support fast thread switching, although hardware support is not essential to run multithreaded code. To an extent, we have already introduced multithreading – interrupt service routines are threads, distinct and separate from the primary thread responsible for the routine running of a program.
