
Like the logical operators, the comma operator also inserts a sequence point between operands; indeed, this is the only purpose of this operator. This may at first seem useful, since it allows you a degree of control over the order in which subexpressions are evaluated, but that additional control is minimal and probably not worth the trouble: the comma is probably the most poorly understood of all the operators and has the lowest precedence, which can lead it to behave in unexpected ways. The most fitting description I have come across (from an anonymous author) is it’s “mostly useful for obfuscation.” It makes code difficult to read, is rarely used and is never necessary. It should be avoided entirely.

Although not strictly counter-intuitive, the behaviour of an else statement when nesting if statements is not necessarily obvious, and a problem known as a “dangling else” can arise – how should an if statement followed by a nested if statement followed by an else statement be interpreted? Should the else statement be associated with the first or the second if statement?

```
/* Will the ‘else’ path run? */
bool has_apples = false;
bool has_pears = true;
if (has_apples)
if (has_pears)
...
else
...;
```

Fig 1.3 - A “dangling else” statement is guaranteed to cause confusion – even for someone familiar with the rules of the language, it can be confusing to look at. Worse – it's impossible to know what the programmer intended!

This is not a problem for the compiler: in practice, an else statement is always paired with the nearest if. Rather, the problem is one of ambiguity in what was intended by the programmer. Without additional information, there is no way of knowing if the observed behaviour is the intended behaviour or not. There is a simple way to remove this ambiguity: always enclose the code controlled by an if or else statement in braces, even if it consists of only a single statement. This not only eliminates the ambiguity associated with the dangling else, it reduces the likelihood of many other common mistakes being made as well. In fact, this advice does not only apply to if statements, it applies to loops as well. Including the braces will not have a negative impact on the performance of your code. It will make it less likely that avoidable errors creep in and less prone to misinterpretation later.

## Type safety

C requires all variables to have a type when declared. This, however, does not make the language type safe. In fact, the language's reputation when it comes to type safety is rather poor. Many aspects of C's type system are unspecified, multiple features of the language are inherently type unsafe and with a little knowledge it is possible to bypass the type system entirely. This is not surprising, given C's origins as an alternative to assembly languages; providing the low-level features of C in a type safe manner would be incredibly. In addition to the obvious semantic ambiguity that can arise, violations of the type system can cause other software safety issues: treating a pointer to a char as a pointer to a for instance, can result in accessing memory that has not been allocated or has been allocated for another variable.

Before discussing specific type safety issues, it is worth mentioning the typedef keyword. Although typedefs are useful and you should use them when appropriate, don’t be lured into a false sense of security – using typedef creates an alias for an existing type, it does not create a new type. When evaluating the type of a variable, C treats the alias as being interchangeable with the underlying type and with any other alias for that type. Using a typedef may make understanding and debugging code easier, but it will not help the compiler detect mistakes on your behalf.

Some type safety issues are quite subtle, such as the rules for mixing different integer types. When performing operations on integer types, the C Standard (since C99) states: “if an int can represent all values of the original type, the value is converted to an int; otherwise it is converted to an unsigned int.” This is known as integer promotion and can cause some unexpected behaviour. For instance, it is not possible to directly compare an int to an unsigned int; if asked to perform an operation of this sort, the compiler will first perform a type cast on the int so that it is comparing two unsigned values. If both values are positive, this should not cause any issues. But what if the signed value was initially negative?

The cast from an int to an unsigned int is well defined. In the case of a platform using two’s complement representation for signed numbers (by far the most common representation) the bit-pattern of the signed value is therefore all negative signed values are cast to positive unsigned values in the upper half of the available range – the result is that a negative signed value can be larger than a positive unsigned value! Clearly this result is mathematical nonsense, but it is the result according to the C Standard. Integer promotion rules apply to short and char types as well – but these will always be cast to a (signed) int. This can cause even more confusion – comparing a negative signed char to an unsigned char with the same underlying bit-pattern will show that the two are not equal, which is mathematically correct, but shows you can’t even rely on the bits being unchanged!

The lesson here is that you don’t mix signed and unsigned types – it will only cause you trouble. If you absolutely must do it then make the casts explicit rather than relying on the implicit casting that results from the integer promotion rules.

```
int oranges = -1;
unsigned int stop = 1;
/* Integer promotion causes odd behaviour:
 * This loop will never run! */
while (oranges < stop)
{
++oranges;
...;
}
```

Fig 1.4 - Integer Promotion can cause some very odd behaviour – comparisons between different sized integer types, or signed and unsigned types of the same size, can give strange results – such as causing a loop to terminate unexpectedly (or not run at all).

Less subtle examples of type safety violations also occur; many are the result of the versatility granted to the programmer by pointers. Probably the most explicit example of this is type punning where a pointer to one type is cast to a pointer to another type. While in many cases this is strictly undefined behaviour, it is such a common practice that many compilers will allow it. Even if the compiler does prevent a direct cast, the C Standard allows any pointer to be cast to a pointer to void and a pointer to void to be cast to a pointer to any other type.

An alternative method of type punning is to write to a union member of one type and subsequently read the data from a member of another type. This also results in undefined behaviour according to the C Standard but is another example of a widespread practice that most compilers will allow. Type punning is sometimes necessary, but the problem with the available methods is that they rely on multiple implementation defined and unspecified behaviours, so they are far from guaranteed to behave the way you expect them to. Furthermore, using these methods, you can bypass the type system entirely. When you do need to use type punning, there are some steps you can take to make it safer; we will explore these later.

Any function that returns a pointer to void (and almost any function that expects to be passed one when called) exposes a type safety risk, including those included in the C Standard Library. Such functions should be used with care. Notable examples in the C Standard Library are malloc, calloc and realloc – as a consequence of this, dynamic memory allocation is not type safe in C.

## Memory safety

C has no built-in mechanism to ensure memory safety and violations are probably the most common source of serious programming errors. Countless bugs and security vulnerabilities have been caused by memory safety violations. The infamous “Heartbleed” vulnerability in the OpenSSL library, first publicly disclosed in 2014, was caused by a buffer over-read error. A buffer overflow vulnerability was discovered in the kernel of multiple Apple operating systems in 2018. In May 2019 it was reported that Facebook’s popular messaging application, WhatsApp, had a memory safety vulnerability. Sir Tony who was the first person to propose using null references as a means of protecting memory in 1965, later described his invention as “my billion-dollar mistake.”

In C, pointers are the cause of many memory safety violations. As C’s only native reference type, programmers have little option but to use them, despite the well-documented risks associated with them. In this case, the pointer is said to be “dangling.” Dereferencing either a wild or dangling pointer is undefined behaviour, as is dereferencing the null pointer.
