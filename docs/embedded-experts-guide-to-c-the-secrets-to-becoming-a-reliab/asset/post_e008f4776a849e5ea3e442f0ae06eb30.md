
Fig 7.1 - As mentioned previously, files to be included can be determined by defining a preprocessor symbol. It may not be immediately clear how this is useful; but when the symbol is defined externally, either in another included file or using a compiler option (check your compiler documentation), it can aid in porting software from one platform to another or in simplifying the migration from one version of an included library to another.

Unlike C statements, macros need not be (nor should they be) terminated using a semicolon, although a macro consisting of several statements will require all but the last of those statements to be terminated. The preprocessor will treat the definition as complete once it encounters a newline character. If it is desirable for your macro to span multiple lines, then this can be achieved by ending all but the final line with a backslash.

It is particularly important to remember the preprocessor is primarily a text substitution tool. Object-like macros are not objects and function-like macros are not functions. Occurrences of both cease to exist once the preprocessor's task has been completed, their contents having been expanded and substituted in their place. Function-like macros cause particular confusion, since once defined their usage appears identical to normal functions although there are important differences in how they behave. While it may be tempting to think a macro can be used to create a type-agnostic function, the “function” itself is not defined, can never be called and arguments are not passed to it; rather, the macro text is expanded and substituted in place of the function “call” within the code. This can cause unexpected behaviour if the arguments used are not limited to individual variables and can be particularly problematic if an expression with side-effects is used as an argument, since the expression will be evaluated each time it appears in the macro rather than only once as it would be in a function call. Poorly written macros can easily result in undefined behaviour. Best practice is therefore to limit each argument to appearing only once within the body of the macro.

```
/* Select the larger of two values. */
#define MAX(VA_, VB_) \
((VA_) > (VB_) ? (VA_) : (VB_))
/* Select the smaller of two values. */
#define MIN(VA_, VB_) \
((VA_) < (VB_) ? (VA_) : (VB_))
```

Fig 7.2 - This example demonstrates how macros to find the maximum and minimum of two values could be implemented. However, both macros are severely flawed because one of the arguments will always be evaluated twice. If neither argument has side effects this is not an issue, but consider what would happen if the macro is invoked through the statement MAX(++apples, ++pears). Either apples or pears (but not both in this case) will be incremented twice, which is unlikely to be what the programmer intended and is certainly not consistent with the macro name.

It is often difficult or even impossible to implement even seemingly straightforward statements in a way which is guaranteed to be safe using macros; in such cases it is always much safer to use a function instead.

When writing function-like macros, the entire macro and any instances of the arguments used should be surrounded by parentheses. Failure to do this can result in the macro behaviour changing depending on the surrounding code when it is referenced. Multi-statement macros cannot be surrounded by a single set of parentheses; in such cases, you may come across macros contained within a do ... while (0) loop. This unusual and seemingly unnecessary loop is used for one reason only: so the macro can be terminated with a semicolon and still used immediately following an if statement. Although it is a relatively common practice, if you always use braces with if statements, you will never need it.

The stringising operator is used when there is a need to treat an argument as a string. The operator encloses the exact text of the argument within quotation marks and replaces any special characters which appear with their escaped equivalents. The token pasting operator is used to create a new token from two existing tokens. The new token must be valid; you could use #define ADD_EQ + ##= to define an alternative to the += operator (although there is no reason why you would ever need to do this), but attempting #define ADD_TWO + ##= 2 (which would be equally unnecessary) will not result in a new token. You may occasionally come across these operators, although they are relatively rare. Probably their most common use is in writing macros to aid with debugging. Their use is often discouraged, first because the way in which they are implemented can be confusing and is often inconsistent between vendors and secondly because many people are unfamiliar with their use. If you do use them, be sure to leave clear comments to explain what they are being used to achieve.

```
/* Make a string. */
#define STRINGIFY(EXP_) #EXP_
/* An extra macro is required whenever EXP_
* needs to be expanded. */
#define MAKE_STRING(EXP_) STRINGIFY(EXP_)
/* Paste two tokens together. */
#define PASTE(PRE_, SUF_) PRE_ ## SUF_
/* This macro is required for the same reason
* as MAKE_STRING. */
```

```
#define NEW_TOKEN(PRE_, SUF_) PASTE(PRE_, SUF_)
/* This version and revision of the
* software. */
#define MAJOR_VERSION 2
#define REVISION 5
#define VERSION_NUMBER NEW_TOKEN(MAJOR_VERSION, REVISION)
/* Make software information available as a
* string. */
#define VERSION_STRING MAKE_STRING(VERSION_NUMBER)
```

Fig 7.3 - This rather convoluted example shows how the stringising and token pasting operators can be used – and how confusing they can be. VERSION_STRING will expand to “25” (with quotation marks included).

Note how, not only is VERSION_NUMBER not defined as VERSION ## REVISION and VERSION_STRING not defined as #VERSION_NUMBER but an additional, seemingly redundant, macro is required for each operator. Neither of the more intuitive definitions would work and neither would omitting the additional macros – the stringising and token pasting operations take place before macro expansion is performed on the operands and the only workaround is to use an additional macro to expand any operands which require it first.

By default, macros have global scope once defined. The only way of limiting the scope of a macro is to subsequently undefine it. This is achieved by using the #undef directive, which can also be used if there is a need to redefine a macro; although multiple definitions of the same macro often result in warnings rather than errors, it is still best for multiple conflicting definitions of a macro not to be present and to avoid redefining macros without a very good reason. Whether intended for removing a macro entirely or redefining it, #undef should be used with care. When using it, the programmer needs to be sure the macro being undefined is not being used elsewhere and they are undefining the intended macro; other than in very exceptional circumstances, the macro should be undefined in the same file in which it is defined.

The global scope of macros also means they must be named with care to avoid redefining existing symbols. Names should be chosen so they are unlikely to clash with other names; one common means of achieving this is to use only uppercase characters for macro names, while using lowercase characters for other symbol names. The names must still be chosen so they do not clash with any reserved names; you should not define your own NULL macro, for instance.

Another common convention is to append an underscore to the macro name since this further reduces the likelihood of clashes. It is, however, bad practice to put an underscore in front of the macro name: all names beginning with an underscore followed by an uppercase character are reserved. Argument names in function-like macros do not cause redefinition if they clash with other symbol names; however, a similar approach to naming these can be helpful in reducing confusion. In the rare case where it is necessary to include a variable declaration within a macro definition, the variable should also be named to avoid clashes. In these instances, it is also a good idea to limit the scope of the variable so it cannot be referenced outside of the macro.
