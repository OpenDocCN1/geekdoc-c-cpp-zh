# The linkage stage

If you have not considered the concept of linkage before, you may wonder why this stage is required at all. A compiler is supposed to produce executable machine code, so what do we need a linker for?

A naïve compiler could simply produce machine code intended to run immediately. While such an approach would appear intuitive and does simplify the process of generating executable software, it has some significant drawbacks. Crucially, this is a very rigid approach: all function and variable addresses must be known when the compiler runs, making it difficult to precompile modules or to reference libraries which have already been compiled. The entire executable must be built as one, and any (even minor) changes to one module require recompilation of the whole project. In fact, even if all the relevant information were available at compile time, given how most software is developed, such a compiler would probably not work.

Source files should not be referenced using a #include directive – only header files should be referenced this way. Assuming we are using each file type appropriately (usage is the only meaningful distinction between the two!), a header file tells us nothing about the contents of any function – it tells us only the type of the return variable and any variables passed to the functions. It also tells us nothing about any functions which are not listed in the header but still feature in the source file. A header file is essentially a contract between the programmer and the compiler: it is a list of promises on behalf of the programmer that at some point, actual functions, rather than just prototypes will be available in some form. In return for the promises, the compiler generates code as if those functions are available, even though it does not know where to find them.
