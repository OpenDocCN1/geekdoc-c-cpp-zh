Collectively, the code to manage waiting for multiple events quickly becomes an undecipherable mess – an example of what is commonly termed spaghetti Not only is this error prone, but it is not a particularly effective way to write event-driven software either.

```
/* This should be volatile to prevent the
 * compiler optimising out evaluation. */
bool volatile g_resource__ready = false;
/* Assume g_resource__ready can be changed
 * elsewhere, e.g. in an interrupt service
 * routine. */
void use_resource(void)
{
    /* Wait for the resource to be ready. */
    while (!g_resource__ready)
    {
        /* Don't do anything here - just wait! */
    }
    /* Now the resource is ready, continue. */
```

Fig 4.1 A busy wait can be placed prior to an event that the processor is waiting for. The software continually checks to determine if the event has occurred or not, but does nothing useful between checks. The processor is kept “busy” only in the sense that it is unavailable during the wait.

Fortunately, even the humblest of microcontrollers include at least a handful of interrupts. Interrupts are a key tool is transforming code from being purely procedural to incorporating event-driven functionality.
