The basic idea of a mutex is it must be acquired before accessing a resource and only one task may hold a mutex for a shared resource at one time. Another issue is a task may be suspended part-way through an operation. While this is not always a problem, there are certain operations which must not be interrupted – accessing volatile data, for instance. In such cases, atomic operations may be suggested as a solution. An atomic operation is one which executes in such a way it cannot be interrupted. Single processor instructions are always atomic, at least on single-processor, single-core contexts. In general, any operation requiring multiple processor instructions is not atomic, but there are ways to make such operations behave as though they are atomic. Acquiring a mutex is an example of an operation which must be atomic, since partially acquiring it would result in the resource becoming either permanently locked or not locked at all.

Related to mutexes are semaphores, which aid in resource allocation by keeping a record of resource availability. Crucially, adjusting the record must be “safe” in the same way locking and unlocking a mutex must be safe – the adjustment cannot be interrupted and the record should remain accurate. A semaphore which only shows whether a resource is available or not is known as a binary semaphore and is conceptually similar to a mutex. Where multiple copies of a resource are available, a counting semaphore is used to track the number of available copies. Semaphores and mutexes differ: a mutex controls access to a resource, while a semaphore is used only to track its availability.

Simple coroutines could potentially be implemented using the setjmp and longjmp functions and you may come across code which is written this way – or even potentially expanded to provide a complete multitasking environment. Such an implementation will be full of undefined behaviours; it relies on a likely implementation of setjmp and longjmp rather than behaviour guaranteed by the C Standard. A function which has exited through a call to longjmp should not be re-entered – the stack frame it was using is invalidated by the jump and there is no guarantee it will be preserved. Furthermore, a second stack frame can be difficult to create. One method is to use an intermediary function which allocates a large array - but the use of such a function is likely to create confusion for anyone unfamiliar with the technique. I strongly advise against using it, even if you are not required to comply with any standards which explicitly forbid the use of those functions.

A more robust but less portable implementation could be achieved by using assembly language to write our own functions for creating new routines and yielding from a routine back to the scheduler – these should provide a stack switching mechanism, eliminating the need for the confusing intermediary function. With this approach, you will also need to write some assembly to save and restore the processor state when tasks yield and resume, similar to the way the jmp_buf types are used in the example code.

If writing your own assembly language libraries is not for you, then your only real option is to find a third-party library which is verified to do what you want to do – there is no support for coroutines in the C Standard Library.

## Pre-emptive multitasking

The coroutine multitasking we have already discussed is an example of cooperative multitasking. The simplicity of cooperative scheduling makes it appealing in applications with limited resources and where there is a clear point at which a task can regularly yield to the next one, since this step must be explicit and it is undesirable for one task to have exclusive use of the processor for too long. This is perfectly adequate in many circumstances, particularly where a small number of tasks of equal priority are required, but it can be difficult to manually determine an appropriate balance between progressing one task and allowing others to progress as well.

Pre-emptive multitasking is a much more flexible alternative. A pre-emptive scheduler can interrupt tasks in order to allow other tasks to run. This immediately frees the programmer from determining the best point in the code at which to yield control, immediately solving the problem of one task taking a disproportionate amount of processor time in comparison to others. In addition, more advanced pre-emptive schedulers can schedule tasks based on their importance.

One of the better known and easiest to implement scheduling methods is the round-robin algorithm. Tasks are allowed to run for a fixed amount of time before execution is handed to the next one. Once all tasks have used their allocated time, execution returns to the first task – this is known as cyclic processing. The cycle continues until all tasks in the queue are complete. If a new task is initiated, it joins the back of the task queue. In its simplest form, a round robin scheduler does not allow tasks to be ordered by priority, but there are variants which do factor in the relative importance of tasks.

Correctly implemented, a round robin scheduler has the advantage of being starvation free: no task is denied access to resources because they are always in use by another task. The algorithm is also deterministic – if a task is in the queue, it is guaranteed to be allocated some time to run. The major disadvantage of the round robin approach is, in its basic form, it does not take account of either priority or size of a task – the scheduler always steps through the task queue in the same order and allocates the same time for each task regardless of how long the task needs to run.

Considering the round-robin scheduler allows each task to run for a fixed amount of time before handing execution to the next task in the list, it seems sensible the scheduler should be implemented using a timer interrupt (this is true of many other scheduling algorithms as well). The interrupt service routine must determine which task should be running and whether the task has already been started. If the scheduler forces a task to yield control, then the machine state must be saved – this means all register values, including the program counter and stack pointer, must be moved to non-register memory. If the next task in the queue has not already been started, the scheduler will need to create a new stack frame for the task before calling the entry function for the task (the entry function is the equivalent of the main() function for a task). If the task has previously been started, the scheduler needs to retrieve the machine state from the last time the task yielded from memory and restore it. Dealing with a task which ceases execution through a return statement can create problems if not handled with care. Without compiler support, the return statement will be treated as it would in any other function and the stack may not be correctly restored. It is therefore essential to ensure either tasks do not return in the traditional sense and instead use a different method to cease execution, which is difficult to guarantee in practice without compiler support, or for the scheduler to manage stack restoration when tasks do return. The requirement to manipulate the stack pointer and program counter directly makes it impossible to write a pre-emptive scheduler using only the C Standard Library.

The round-robin scheduler is not the only possible scheduler you could use. It generally performs well on one metric – response time. This is the average time between a task arriving in the queue and execution of the task beginning. If we consider a different metric, turnaround time – the average time between a task arriving in the queue and finishing execution – then performance is generally poor. If we wish to improve turnaround time, then an alternative such as a Shortest Time-to-completion First (STCF) scheduler is more appropriate. Unlike a round-robin scheduler, a STCF scheduler does not regularly switch tasks by default (although it must regularly monitor waiting tasks). As the name implies, STCF scheduling works by selecting the task which is expected to take the least time to complete and runs it first.
