## Pools

A pool is a memory block of fixed size which may be allocated and freed as required. While this may, at first, appear no different to allocating memory using a call to malloc. A careful implementation can avoid the issues associated with more general methods of allocating memory. Firstly, it is important to note that the pools are of a fixed size – therefore, either a pool is available for allocation or it is not; memory fragmentation, although not eliminated, is no longer a problem. The space required for the pools themselves can be statically allocated. Secondly, the overhead of tracking the amount of allocated and free space is significantly reduced, since it is only necessary to know whether a given pool is free, rather than maintaining a complete map of free memory blocks and their size. The problem of dangling pointers, however, remains and is difficult to completely resolve.

A pool may be either generic or resource specific. A generic pool consists of an array of char arrays, while a resource specific pool consists of an array of whatever the most appropriate type is (which may itself be a collection type, such as an array or structure). The implementation in both cases can be the same. One simple implementation is to use what is known as a free list. A free list consists of individual pools connected to form a linked list. When a pool is allocated, it is removed from the list. When the pool is freed, it is added back into the list. No overhead needs to be associated with the link pointers in each pool: when the pool is allocated, the pointer can be overwritten with the data the pool is used to store as the list only contains the free pools. Using a union to combine the pointer and the pool data as a single variable is therefore a logical method to use when implementing pools.

```c
/* Implement a pool allocator for TOTAL_POOLS
 * pools. Each pool is a block of POOL_SIZE
 * chars. */
/* Create the basic pool type from a union. When
 * allocated, p_next_pool can simply be
 * overwritten. */
typedef union pool_u
{
    union pool_u * p_next_pool;
    char pool_data[POOL_SIZE];
} pool_t;
/* Create an array of pools. */
static pool_t pools[TOTAL_POOLS];
/* Create a pointer to track the next pool to
 * be allocated. */
static pool_t * p_pool_head = &pools[TOTAL_POOLS - 1];
/* This function must be called before the pools
 * can be used. */
static void init_pools(void)
{
/* Point each pool to the next available
 * pool. */
for (int index = TOTAL_POOLS - 1; 0 < index;
--index)
{
pools[index].p_next_pool =
&pools[index - 1];
}

/* No pools are available after pool[0] is
 * allocated so point it to NULL. */
pools[0].p_next_pool = NULL;
}

/* Allocate a pool - return a pointer to the
 * pool, or NULL if no pool is available. */
char * pool_alloc(void)
{
static bool pools_ready = false;
char * p_new_pool = p_pool_head;
/* Initialise the pools on the first run. */
if (!pools_ready)
{
init_pools();
pools_ready = true;
}
/* Point p_pool_head to the next available
 * pool. */
if (NULL != p_pool_head)
{
p_pool_head = p_pool_head->p_next_pool;
}
return p_new_pool;
}
```

```c
/* Free a pool. This function does not check
* p_pool points to a valid pool to add back to
* the list of free pools (but does check it does
* not point to NULL). */
void pool_free(void * p_free_pool)
{
if (NULL != p_free_pool)
{
p_free_pool->p_next_pool = p_pool_head;
p_pool_head = p_free_pool;
}
}
```

Fig 3.5 - Pools can provide a flexible means of allocating blocks of memory, similar to other methods of dynamic allocation. However, the size of each pool is fixed, so memory fragmentation does not occur.

Allocating a pool is straightforward using the free list implementation. The pool needs to be removed from the list and the allocator function returns a pointer to the first address in the pool. The last pool in the free list should point to NULL as the next pool and this should be returned in the event of pool allocation failure. Adding a pool back to the free list is equally straightforward; however, it is important to remember this alone will not protect the pool from being accessed in future, since any pointers to the pool remain valid, and any such accesses risk corrupting the entire free list.

Pools are the most dynamic method of memory management which will be discussed here; they overcome many of the risks and inefficiencies associated with general purpose dynamic allocation by allocating only fixed-size blocks of memory, but this comes at the expense of the flexibility. There is, however, one other important advantage to pool allocation schemes – it is possible to implement the allocation and freeing functions so they always take a fixed amount of time to run. This is not possible with general purpose allocation methods.

## Chapter 4: Interrupts and Callbacks

C is a procedural programming language; that is to say, a C program is built of procedures, known as functions, which can be invoked from elsewhere in the code, run, and eventually return to the location from which they were called. The functions themselves consist of statements which outline the computational steps the function is required to perform. The order in which the procedures and the statements contained within them are invoked is entirely determined by the code.

But what if you need a way of changing the deterministic flow of a program? Say the device is supposed to be operated by a user. Would it be acceptable to the user if they were required to wait until the program was ready to respond to their input, or would they prefer the response to be, or at least to appear, instantaneous? Most people, at least when they are the user, would prefer the latter option, but this responsiveness is not an inherent feature of procedural programming. What is required is not a procedural program, but an event-driven one where control-flow is determined by conditions at runtime; an event, in this context, is any change in condition which requires the timely attention of the processor.

To achieve such a responsive program, you could use a method known as busy waiting – this requires a loop which continuously monitors, blocking all other program activity, until the user input is detected. While this will work, it is clearly an inefficient way to write software. It also assumes there are no other events which the program may need to respond to –
