## Chapter 1: “Trust the Programmer” – Issues with C

It is, perhaps, surprising that it seems nobody has ever published a book of the “Greatest C Programming Mistakes.” It may be that the subject matter is somewhat niche; but there is certainly a market for other books on C Programming. Perhaps it is that the language is seen as somewhat esoteric, even in professional programming circles: it has essentially been replaced by Java and C# in general applications programming and it has never had much of a role to play in web applications. In the Internet Age, you could be forgiven for thinking that C was more or less extinct – an anachronism, curious for its undeniable influence rather than its usefulness; little more than a plaything for overly keen hobbyists.

But there are two areas where C programming continues to dominate: operating systems and embedded programming. C compiles to efficient machine code and it provides many flexible, low-level features that modern programming languages lack. Although it would be entirely possible to develop a new language capable of competing with C on a technical level, it would not be so easy to convince programmers to switch allegiances following their 50 year alliance with “portable assembly.” For embedded systems, having low-level functionality while avoiding the need to write tediously verbose assembly is precisely what makes C so attractive. The same is true for operating systems.

But it is precisely that combination of unrestricted low-level functionality, portability and, above all else, the philosophy of “trust the programmer” that makes C such a potentially dangerous language. Like those responsible for mixing nitroglycerin for Alfred Nobel, the C programmer’s work is probably best done sat upon a one-legged stool to ensure they remain alert. Mistakes are easy to make and often remain undetected by the default tools available to the programmer, inviting disaster at some arbitrary point in the future.

No treatment of the C programming language would be complete without a discussion of its shortcomings. It is impossible to become a good C programmer without first developing an acute awareness of the dangers inherent in the language. That is precisely what this chapter aims to do.

### Undefined and unspecified behaviours

One of the C’s most celebrated qualities is that it can be compiled into efficient machine code on a wide range of platforms. The compiler does not typically generate more code than is required to achieve what the programmer has asked for. If the programmer asks the compiler to generate code to divide two integers, the compiler will generate that code and aim to make it efficient – that is, the generated machine code should run as fast as possible. What the compiler will not do is generate any code to check if the operation can be performed or if the result makes any sense. So, what happens when you ask the generated code to divide an integer by zero?

Try this in C# or Java or whatever your preferred “modern” programming language is and you can expect an exception to be thrown – you don’t need to write the checks yourself, they’re part of the language. But in C, what you get is “undefined behaviour” – you have no way of knowing what will happen until you attempt to run the code, and there is no way of knowing if you will see the same result if you run it again.

Undefined behaviours are the result of code that is syntactically correct but semantically meaningless, either inherently or because of the data you give it to work with. According to the C Standard, undefined behaviour is caused when you attempt to execute “a non-portable or erroneous program construct” or by providing a valid program with “erroneous data.” There are almost 200 undefined behaviours listed in Annex J of the standard. The name “undefined behaviour” is fitting: if a behaviour is undefined, then the C Standard “imposes no requirements” – in other words, you are entirely at the mercy of the compiler, which is entitled to assume that undefined behaviour will not occur and may, or may not, generate meaningful machine code when it is encountered. Indeed, compilers may even produce code that behaves exactly as the programmer intended. There are a few broad categories of undefined behaviour: memory access violations, signed integer overflow, strict aliasing violations, unsequenced modifications, race conditions and certain non-terminating loops. Some of the common instances you will encounter include null-pointer dereferencing, out-of-bounds array accesses and “type punning.”
