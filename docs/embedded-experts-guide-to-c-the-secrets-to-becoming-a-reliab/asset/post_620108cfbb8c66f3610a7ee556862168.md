## Know the operators

You will often hear you can improve execution speed by carefully selecting the operators you use. For instance, multiplication or division by a power of two is often claimed to be more efficient as either a left or right shift, respectively. This technique, however, is only valid for unsigned integer types and, at least in the case of multiplication, is not guaranteed to result in any increase in speed.

It is worth having at least an idea of the relative performance of the different operators. Generally, for integer arithmetic: addition, subtraction and bitwise operations will typically perform the fastest, shifts usually have similar performance, multiplication will usually, but not necessarily, be slower (this largely depends on whether the CPU includes a hardware multiplier) and the division and modulo operators will almost invariably be the slowest. For floating point arithmetic, multiplication may be marginally faster than both addition and subtraction but is likely to have similar performance, and division is much slower.

For floating point calculations (but not integer ones) it can sometimes be quicker to multiply by the reciprocal of a number than to divide directly.

The relative performance of integer and floating-point operations will largely be determined by the presence of a floating point unit; if one is present, integer and floating point arithmetic will probably have similar performance, otherwise, expect floating point calculations to take significantly longer (potentially by a factor of 100 or more) than integer ones. In both cases, it would seem reasonable to minimise the number of divisions wherever possible and, for integers, it may be helpful to reduce the number of multiplications as well. For any non-trivial equations, it is often a good idea to write them out by hand and some cast operations have little or no cost associated with them, but this is not always true. Casting between different integer types is fast, as is casting from a pointer to one type to a pointer to another type, because changes to the underlying data are minimal. Casting from an integer type to a floating-point type (or vice versa), however, does incur a more substantial performance penalty and the number of such casts should be kept to a minimum.

```
/* ADC offset and scaling constants. */

#define SCALE (7.5F)
#define OFFSET (2.0F)
/* A function to average 10 ADC samples. */
float average_samples(int16_t * p_adc_sample)
{
float sum = 0.0F;
/* Correct, scale and add each sample to the
* sum. */
for (int sample = 0; 10 > sample; ++sample)
{
sum += SCALE * (((float) p_adc_sample[sample]) -
OFFSET);
}
/* Divide by the number of samples (10), then
* return. */
return sum / 10.0F;
}
```

```
/* ADC offset and scaling constants. */
#define SCALE (0.75F)
#define OFFSET (-20L)
/* A function to average 10 ADC samples. */
float average_samples(int16_t * p_adc_sample)
{
int32_t sum = OFFSET;
/* Calculate the sum of the samples. */
for (int sample = 0; 10 > sample; ++sample)
{
sum += (int32_t) p_adc_sample[sample];
}
/* Cast to a float and scale. */
return SCALE * ((float) sum);
}
```

Fig 9.1a & b - These two functions, which look very similar and are both intended to calculate the average of 10 ADC samples, are likely to perform very differently. The first example is a very intuitive implementation, but requires an assignment, 10 conversions from an integer to a float, 20 floating point additions, 10 floating point multiplications and a floating-point division. With a little thought, this can be rewritten to improve performance considerably. The constants must be recalculated for the second example, but it requires an assignment, 10 integer-to-integer conversions, 10 integer additions, a single conversion from an integer to a float and a single floating-point multiplication. The number of operations has been almost halved and many of those operations are faster than in the first example, especially if no floating-point unit is available. As additional, but less intuitive, benefit of the second example is that it is potentially more accurate as there is less opportunity for floating point rounding errors to creep in.

In theory, it is possible to optimise the performance of logical operators to an extent by exploiting the short-circuit evaluation technique used in C. The idea is because the logical-and operator only evaluates the right-hand argument if the left hand argument evaluates as true (or false, in the case of the logical-or operator) then the average speed of evaluation can be reduced by carefully choosing the order of the arguments: if an expression is relatively slow to evaluate, it is best used as the right-hand argument; if one argument is more likely to be false than the other, it is best used as the left-hand argument of a logical-and operation; and if one argument is more likely to be true than the other, it is best used as the left-hand argument of a logical-or operation. The principle is sound enough, but in practice, there are probably not many opportunities to make significant performance gains in this manner and there are other considerations which should take priority, such as ensuring the right-hand argument does not have any side-effects.

```
/* Short-circuit evaluation ensures pp_apple is
* checked before dereferencing to check the
* pointer it points to. */
if ((NULL == pp_apple) || (NULL == *pp_apple))
{
/* Handle the NULL pointer error. */
}
```

Fig 9.2 - In this example, short-circuit evaluation is used to ensure correct behaviour of the code rather than to improve performance; because two levels of indirection are used, both pp_apple and *pp_apple must be checked to ensure neither is NULL. However, pp_apple must always be checked first, and the second check should only be performed if it is not NULL. Although this is valid C, it is still not ideal – a programmer unaccustomed with short-circuit evaluation will not realise that the second check is performed only when the first fails.

## Optimising keywords

The C language includes some keywords which can aid optimisation. Strictly speaking, the keywords themselves do not usually cause any optimisation to take place; rather, they serve as hints to the compiler as to where optimisation might be possible. The compiler may choose not to perform the optimisation or, conversely, to perform the optimisation even if the keyword was not used.

The dubiously named const keyword is one which you should be familiar with and use wherever possible. Despite the name, a variable declared const is not necessarily constant (a true constant has a value which can be known at compile time); rather, it is better described as being read-only, although even this may not be considered entirely accurate. Whether the name is accurate or not, this keyword indicates to the compiler the variable may not be assigned to. In most cases this means the compiler can assume the value will not change and this can be used to optimise loading and evaluation of the variable, perhaps even to the extent of eliminating the need for the variable entirely. Although it is unrelated to optimisation, most of the time, const can be used with a variable definition as an alternative to using #define. However, because such variables are not considered true constants, there are a few circumstances where this cannot (or should not) be done: when the constant is used to set the length of a bit-field or the size of an array, or following a case statement, where a true constant must be used; and when initialising a static variable or another constant.

The volatile keyword is used to indicate to the compiler a variable’s value should be expected to change unexpectedly. This means a volatile variable must be loaded and evaluated whenever it is encountered and essentially prevents any of the optimisations which might apply to other variables from occurring. While this may seem unnecessary, you will find many variables need to be declared as volatile when using even relatively modest levels of compiler optimisation or the compiler may simply assume their value does not change and optimise accordingly, even if the variables are not volatile. Occasionally a variable may be, seemingly paradoxically, both const and volatile. This signals to the compiler the value of the variable may not be changed by the code, but the value may change unexpectedly anyway and is most widely used when interacting with hardware. Although it is often not necessary, I have a rule of qualifying all global variables – at least those which are shared across multiple translation units – as either volatile or const. My rationale for this is if the value of a global variable cannot change unexpectedly (i.e., it is not volatile), it need not be global in the first place, the exception being the variable is a constant and only has global scope so it does not need to be defined multiple times.
