## Chapter 7: The C Preprocessor

Understanding the C preprocessor is an often-neglected part of C programming. In most cases, the programmer's exposure to the preprocessor is through preprocessing directives (the small number of language keywords which begin with a “ # ”; in speech, these are often called prefixed with the word “hash,” e.g. hash-define or hash-pragma), although the handling of directives is only a small part of the preprocessor’s role. It is important to appreciate this, since running the preprocessor is the first step performed during translation of a C program. The full translation process, including the various tasks performed by the preprocessor are described later in this book; this chapter focusses primarily on the various preprocessor directives and their proper usage.

Before describing the directives in detail, it is important to recognise the preprocessor is primarily a text substitution tool; this is often the cause of confusion for less experienced programmer's and even seasoned veterans may find themselves making mistakes. Over-reliance on the preprocessor is a certain way to cause yourself trouble – it complicates the task of diagnosing compiler errors and warnings and can make debugging difficult. The syntax of the language used by the preprocessor is distinct from C and, unlike C, the preprocessor language is not Turing

Originally the C preprocessor included only two directives: #include and #define. Additionally, macro definitions could not initially accept arguments, i.e. only constant macros could be defined. The originally limited functionality has since been extended substantially, both in its standardised form and through vendor-specific extensions. Perhaps unexpectedly, the preprocessor is not limited to being used only with C; it can be (and usually is) implemented as a standalone program, without the need for a C compiler, and as such has sometimes been used for processing other types of files. You may occasionally come across files written in assembly which contain C preprocessor commands for this reason.

Beyond including additional files and defining constants, the preprocessor (from the programmer's perspective) is used to control conditional compilation of code, issue custom errors and, in generally implementation-defined ways, determine how code is compiled. These are the topics we will be exploring in this chapter.

### The #include directive

Source files may reference other files for inclusion using the #include directive. The most common use is to reference “header” files, those which typically use a file extension. Although header files may contain any valid C, they normally use a limited subset of the language to declare functions (referred to as and define macros and typedefs relevant to the code being referenced. The full source is usually found elsewhere, either as a precompiled library or as a file, usually with the same name as the Occasionally the source is provided by a file written in assembly language, but this does not require any changes to the header file.

When the preprocessor encounters a #include directive, it simply replaces the directive with the contents of the referenced file. This is performed recursively: any directives found in the referenced file are also replaced. It is therefore possible to inadvertently include a file more than once. When this occurs, the result is duplicate declarations or definitions, which invariably create issues. This possibility must therefore be handled within the included files; we will see how this is achieved shortly. This is the only significant risk associated with the #include directive.

There are two variants of the #include directive: The first contains the name of the file to be included in quotation marks: #include The second variant places the name of the file between angled brackets: #include These two forms are not intended to be completely interchangeable. The first variant is used, the search path for the file includes the current source directory. The second variant limits the search path to the standard include path, which is where the C Standard Library header files can be found. The distinction is of less importance than it once was; on modern systems the additional delay involved in searching a greater number of paths is relatively small. Nonetheless, using the angled bracket form can be a useful reminder to the programmer the included files may differ from the originally intended version and the source code itself may not be available.

It is possible to use conditional compilation, which is described shortly, to defer determining which files are included until compile-time based on which preprocessor symbols are present. Alternatively, it is possible to use computed where a preprocessor symbol is defined which contains the name of the file to be included and this symbol, rather than the actual filename, follows the #include directive. Both methods can be useful and it is often not necessary to define the symbols as part of the code, since IDEs usually have features for defining project-specific preprocessor symbols and compilers generally allow them to be defined through command-line arguments; however, many modern IDEs are very good at checking code syntax and highlighting problems as you work without needing to compile, which can be confusing if many symbols are not resolved until the last moment.

There is no technical reason why file inclusion should be limited only to header files. Complete C source files may be included, but this is unnecessary, since the source itself does not need to be included, and is considered bad practice, since it exposes the entire contents of the source file, including static functions and variables which were intended to be hidden. Other file types can, and occasionally are, included. The only restriction is the file can be understood by either the preprocessor, the C compiler or a combination of both. At times this has resulted in some unusual filetypes being developed; for example, the XBM image format, which is actually a C file containing a monochrome bitmap as an array.

### The #define directive

The #define directive is used to create macros which may then be referenced throughout the rest of the code. Macros may be of one of two forms; they are either object-like macros or function-like macros. Object-like macros are generally used to define symbols and constants, whereas function-like macros are able to accept arguments and can therefore be used elsewhere in a similar way to normal C functions, although it is important to remember the macros themselves are not functions.

Of the preprocessor directives, #define is by far the easiest to misuse, particularly when working with function-like macros. There is also a #undef directive, which is used to remove a definition created using #define. In addition, there are three preprocessor operators: ## and #. The # or “stringising” operator is used to convert a token into a string literal. The ## or “token pasting” operator, is used to combine two tokens into one. The defined operator is not much use within definitions but may be used elsewhere to check whether a macro has been defined; it is common when performing conditional compilation, i.e. deciding which code to compile based on some criteria which is known at compile-time but not necessarily before.

Object-like macros are often used to define constants with symbolic names. This is generally considered a part of good practice since it avoids the use of "magic numbers" – numbers which appear in source code with no clear origin or meaning. It also allows those constants to be changed without having to search through the entire source for each instance.

These constants do not have a type, nor are they limited to only representing a value. Each instance of the macro in the code is replaced with the text of the macro and the macro may therefore contain anything, including multiple complete statements, provided the result when expanded is valid. A macro may even reference another macro, in which case the preprocessor will attempt to iteratively replace the macro instances until all are fully resolved. It is also acceptable to define an empty macro. Although these expand to "0" by default, in practice they are rarely (and should never be) used in this way; instead, it is common to check whether the definition exists as a means of controlling other preprocessor operations. In such instances, the value of the macro is unimportant.

/* Define which header is to be used. */
#define FRUITS_LIB "mango.h"
/* Include the chosen library. */
#include FRUITS_LIB
