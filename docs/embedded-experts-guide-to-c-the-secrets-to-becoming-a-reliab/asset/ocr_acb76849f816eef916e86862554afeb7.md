Whenever a new task is added to the queue, its expected time to completion must be compared to the other tasks, including the running task. Only if the new task is expected to take less time to complete than the currently running task will the scheduler switch execution to the new task.

STCF scheduling has the advantage of context switching (which is generally an expensive operation in terms of processing time) being reduced compared to round-robin scheduling and average turnaround time is improved. However, average response time is likely to increase significantly and with a long running time may be repeatedly pre-empted in favour of shorter ones. STCF is an example of a dynamic scheduler – one which allows task priorities to change after they have been added to the task queue. Dynamic schedulers are usually an unsuitable choice for embedded systems – they require significant scheduling overhead and are much less deterministic than static schedulers. However, the scheduling principle behind STCF – that the shortest task should be the first to run – can be used to determine the relative priorities of statically scheduled tasks. We shall return to this later.

Regardless of which scheduler you use, multitasking is not without risk. Sharing variables between tasks is not trivial – reads and writes to these shared variables must be atomic. Functions which are shared between threads should ideally be reentrant, although functions which are restricted to a single thread need not where this is not possible, the functions must use some alternative means, such as a mutex, to prevent concurrent accesses to shared resources. Most functions in the C Standard Library are not guaranteed to be reentrant.

In most instances it is desirable to allow the scheduler to pause one task and pre-empt it with another, otherwise there would be little point in using the scheduler at all. However, there are times when a task must not be pre-empted – some parts of a task may be deemed critical which must be allowed to run.
