The basic idea of a mutex is it must be acquired before accessing a resource and only one task may hold a mutex for a shared resource at one time. Another issue is a task may be suspended part-way through an operation. While this is not always a problem, there are certain operations which must not be interrupted – accessing volatile data, for instance. In such cases, atomic operations may be suggested as a solution. An atomic operation is one which executes in a such a way it cannot be interrupted. Single processor instructions are always atomic, at least on single-processor, single-core contexts. In general, any operation requiring multiple processor instructions is not atomic, but there are ways to make such operations behave as though they are atomic. Acquiring a mutex is an example of an operation which must be atomic, since partially acquiring it would result in the resource becoming either permanently locked or not locked at all.

Related to mutexes are semaphores, which aid in resource allocation by keeping a record of resource availability. Crucially, adjusting the record must be “safe” in the same way locking and unlocking a mutex must be safe – the adjustment cannot be interrupted and the record should remain accurate. A semaphore which only shows whether a resource is available or not is known as a binary semaphore and is conceptually similar to a mutex. Where multiple copies of a resource are available, a counting semaphore is used to track the number of available copies. Semaphores and mutexes differ: a mutex controls access to a resource, while a semaphore is used only to track its availability.

Simple coroutines could potentially be implemented using the setjmp and longjmp functions and you may come across code which is written this way – or even potentially expanded to provide a complete multitasking environment. Such an implementation will be full of undefined behaviours; it relies on a likely implementation of setjmp and longjmp rather than behaviour guaranteed by the C Standard.
