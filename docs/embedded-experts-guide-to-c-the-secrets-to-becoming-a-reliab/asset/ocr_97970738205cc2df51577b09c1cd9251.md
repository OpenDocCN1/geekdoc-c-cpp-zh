# Commenting practice

All formal training for programmers will include encouraging them to include comments in their code. Unfortunately, many programmers quickly slip into the habit of ignoring this advice or attempt to add comments once the code has been written. Alternatively, they may include comments with little thought as to whether those comments are helpful or The most useful comments avoid stating the obvious, while providing information about what the code is supposed to do – comments should explain give an overview of how the code works, rather than explaining exactly what is being done step-by-step. The occasional why comment is also justified to highlight parts of code that may need some special consideration; for instance, if a piece of code relies upon the wrap-around behaviour of unsigned integers, this should be stated somewhere. Comments should also be clear. Clarity is more easily achieved when you write comments as full sentences, rather than the rushed shorthand that is often seen. It is also perfectly acceptable to reference other sources and documents where appropriate to avoid excessively verbose comments while ensuring all relevant information is accessible.

Comments should not be written retrospectively – the only time this is acceptable is during code reviews when it becomes apparent that a comment is needed. It is helpful to write some comments before any code is written – these then provide an outline of what the code will do and help you structure the program. Such comments should appear before each function within a source file explaining what the function does, what arguments it expects and what value it should return.
