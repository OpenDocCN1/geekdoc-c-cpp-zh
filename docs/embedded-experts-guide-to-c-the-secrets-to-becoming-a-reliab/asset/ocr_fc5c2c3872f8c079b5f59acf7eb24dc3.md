Using the second approach, we handle each task as required, but without considering whether or not the task needs handling at that moment – a delay of a few milliseconds when reading user input or updating a display is unlikely to be noticeable to the user, and waiting until a buffer is full is not the ideal way to read data from the UART. In this case, processing time is also wasted, this time in doing nothing. Both approaches also risk one task from “blocking” another – it is hardly desirable for data to be lost from the UART because the buffer is full, but the processor is busy updating the display!

A third approach is to introduce a supervisory task, called a scheduler, responsible for balancing the needs of the various tasks. This is the basic principle behind multitasking. Software multitasking is most useful when a system is expected to perform multiple distinct tasks which need not be synchronous. That is not to say the tasks cannot be related, or even interdependent, to each other; but there must be sufficient demarcation between them so they need not be run sequentially. Multitasking is particularly beneficial in situations where it is not feasible for all tasks to be either interrupt-driven or background tasks suitable for running in the main program loop. This may not be the case in our simple three task example, but as the number of tasks increases, so too does the difficulty of developing a predominantly interrupt-driven solution to managing them – you quickly run out of interrupts and the likelihood of those you do have conflicting with each other rapidly increases.

There are two main multitasking paradigms: cooperative multitasking and pre-emptive multitasking.
