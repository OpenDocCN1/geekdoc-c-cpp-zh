## Coding standards

A coding standard, in its most basic form, is a document that sets out a series of rules to be followed when programming. These rules should cover both stylistic and technical usage of the language. In terms of style, although it generally does not matter too much which style you use, consistency is important. For instance, repeatedly changing the bracing style you use will impair the readability of your code. Technical rules are used to outline requirements on how the language is used. These may include restriction on the standard library functions, types and keywords that can be used (using the goto keyword, for instance, is often strongly discouraged). In most cases, which coding standard you use is not overly important; pick one, learn the rules and stick to them. Take the time to understand the rules as well – blind compliance to any standard, however thorough, is not going to help you write good code.

Following a good coding standard will help you to reduce the number of defects in your code and to write code that is easily understood and maintained. Some coding standards are considerably better than others – many are nothing more than a statement of rules based solely on the personal preferences of the authors. If a coding standard does not include at least some objective justification for the rules it contains, you should probably look for another one. You can, of course, write your own, but be sure not to fall into the trap of simply listing your own stylistic preferences. Ideally it should also be possible to enforce the rules in any coding standard using automated tools.

If you are struggling to find a suitable standard and would rather not write your own, then the BARR C coding standard is a good place to start; the rules are intended specifically to reduce coding defects and explanatory notes are included. If you are working with safety critical systems (where code defects could cause injury or even death), then I strongly recommend that you follow the guidelines in MISRA C, although you will also need to find (or write) a separate style guide to accompany it. No standard can be expected to eliminate defects entirely, but BARR C and MISRA C are both written to help programmers safely navigate the more dangerous aspects of the C

## Whitespace

There are three different kinds of whitespace that you will encounter in a C program: new lines, indentations, and single spaces. In most cases, the presence (or absence) of whitespace does not affect tokenisation of the C program. There are a few occasions when this is not the case, but more importantly, even when the tokenisation is well-defined according to the C Standard, it may be difficult to read or even ambiguous from a programmer's perspective. The solution is to use whitespace to make your intentions clear. The additional whitespace is ignored by the compiler and there is a negligible cost associated with it in terms of both storage of the source code and compilation time. Doing so will also successfully prevent problems arising from the instances where whitespace does change the tokenisation of the code.

Statements in C are terminated with a semicolon; from the compiler's perspective there is no need to follow these with a newline. It is perfectly valid C to write multiple statements on a single line, although it quickly becomes difficult to read and statements should therefore each appear on a line of their own. It is also possible to spread a single statement across multiple lines, which can be useful for unusually long statements, although it may be better to split the statement into multiple smaller ones to ensure that the meaning is clear. Newlines are also useful for grouping functionally related statements; for instance, you might include an additional newline following a series of variable declarations. Additional newlines around conditional and loop statement blocks are also helpful for highlighting the start and end of those blocks.

```
/* Space following conceptual blocks is good for
 * readability. */
int apples;
int pears;
int times = 2;
int all_fruit;
/* Everything's defined - now do something. */
apples = fetch_apples();
pears = fetch_pears();
/* Splitting compound statements helps too. */
all_fruit = apples + pears;
all_fruit *= times;
/* This could have been:

 * all_fruit = (apples + pears) * times; */
```

Newlines in preprocessor statements cause different behaviour: these statements are terminated by a newline rather than a semicolon, and as a result, where a newline is required in such a statement, it should be immediately preceded by a single backslash. Although this is valid at any point in the code, it is most often found in multi-statement macro definitions, where it allows the macro to be written in a similar style to the rest of the code.

```
/* Newlines do nothing in C statements:
 * This is a single statement. */
all_fruit =
apples + pears;
/* But newlines terminate preprocessor statements:
 * This won't work: */
#define MORE_APPLES apples +
1
```

It is conventional to use indentation (and in some cases necessary) to demarcate blocks of code in most programming languages. In C, the indentation itself does not change how the code behaves, since blocks are opened and closed using braces. Indentation is purely for the programmer’s benefit – nonetheless, it is a useful visual indicator that allows you to immediately identify related lines of code. This does, of course, assume that the indentation is correct. This is less of a problem than it once was since formatting tools are available that can correctly align the code and most IDEs can determine the appropriate level of indentation as you type. It is generally recommended that you use individual spaces to create indents, rather than a tab; however, this is also handled by most modern IDEs, which will encode a tab as a predetermined number of spaces rather than as a single tab character. The reason for this recommendation is that the width of a tab can vary from system to system or even between programs on the same system, whereas the width of a sequence of spaces is consistent, and tabs may or may not be encoded as spaces depending on the editor. While this has no effect on the code behaviour, it can result in some odd-looking code. The number of spaces recommended for an indent varies between coding standards and IDEs, but generally falls between two and eight (and many IDEs will have an option to configure it somewhere).

Indentation may also be used to improve readability of preprocessor blocks. Although it is conventional for the # preceding preprocessor directives to be located at the start of the line, this may be followed by whitespace without changing the meaning of the directives that follow; this can be useful in the same way that indentation of blocks within the code is useful when using conditional macro definitions or other directives within a #if block.

```
/* Indentation of preprocessor directives is
 * allowed - but the ‘#’ may still be placed at
 * the start of the line. */
#if defined(APPLES)
# define PEARS
#endif
```

The most common and most important type of whitespace is the humble space character. This is the character most likely to change the behaviour of a program. The main reason for using spaces is to make code more readable, however, there are a few instances where a lack of spacing will result in an unintended tokenisation of the code. C's tokenisation rules stipulate that when tokenisation is ambiguous, the compiler should build the tokens, starting from the left, using the largest number of characters possible, regardless of the context – this is often referred to as the “maximal munch” rule. This means that, for instance, the statement x++++++y; will never compile; even though x+++ ++y; may be a perfectly valid statement, the sequence will always be interpreted as x+++ ++ which is invalid. The statement a=-b; could also cause strange behaviour – in early implementations of C, rather than being treated as two separate tokens, =- and += were each treated as a single token with the same purpose as the more common and unambiguous -= and += compound assignment operators; although this was changed early on, some compilers continued to interpret them this way for some time (it’s relatively unlikely that you’re using one of them, but if you are you could spend a very long time trying to solve the problems it causes). The solution is to use whitespace to make the tokens unambiguous. Not only does this prevent the compiler from misinterpreting the code, but also makes it more readable.
