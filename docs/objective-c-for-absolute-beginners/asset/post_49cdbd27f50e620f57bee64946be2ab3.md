## If Things Go Wrong

Allocating memory through the standard C mechanisms or the Objective-C allocation methods works most of the time. However, the programmer cannot assume that allocating an object or allocating memory works all time. When memory allocation fails, it's generally a sign that bigger problems are at hand, and the program may not be too much longer (it will crash because of memory issues). However, even though the program may be getting into a bad state because it can't allocate memory, the program should not ignore the memory allocation signs. Here are some conventions used to test if memory allocation failed:

```c
int main(void)
{
    char *data2 = malloc(100);
    if (data2 == NULL) // Malloc returns NULL (0x00000000) if allocation fails.
        // Application detected a major failure;
}
```

In this standard C example, if the malloc function fails, a NULL pointer is returned. Recall that NULL is nothing more than a pointer that points to location 0x00000000. NULL is used to indicate a bad allocation. In Objective-C, there are two main areas that we need to perform validity checks. Here's the first:

```objc
int main(void)
{
    MyObject* obj = [[MyObject alloc] init];
    if (obj == nil) // If the object is valid...
        // Application detected a major failure;
}
```

In this example, we try to create an object, but check to see if the pointer returned is nil. Recall that nil is basically a default object used as a placeholder to mean "empty" or "nothing". Don't confuse this with an empty MyObject. The second validity check only applies to objects we've created. This check is done in the init method of the class:

```objc
- init
{
    self = [super init];
    if (self != nil)
        // Do initialization here on a valid object.
    return self;
}
```

In this example, the object's init method tests to see if self returns a value that is not nil. If self is not nil, things are OK, and the method can continue initializing the object. The method then returns self, which can be nil or not. The important thing to note here is that we are testing to ensure that the call to [super init] works before proceeding to work on self.

## Introducing the Xcode Debugger

Xcode is fantastic! Not only is this tool provided free of charge on Apple's developer site, but it is actually really, really good! Aside from being able to create the next great Mac OS X, iPhone, or iPad app, Xcode has a fantastic debugger right into the tool.

So, what exactly is a debugger? First of all, let's get something straight—programs do exactly what they are written to do. Sometimes, what is written isn't exactly what the program is really meant to do. Sometimes, this means the program crashes or doesn't do something that is expected. Whatever the case, when a program doesn't work as planned, it is said to have bugs. The process of going through the code and fixing these problems is **debugging**.

There is still some debate as to the real origin of the term "bug," but one-documented case from 1947 involved the late Admiral Grace Hopper, a Naval reservist and programmer at the time. Hopper and her team were trying to solve a problem with the Harvard Mark II computer. One member found a moth in the circuitry that was causing the problem with one of the relays. Hopper was later quoted as saying, "From then on, when anything went wrong with a computer, we said it had bugs in it."¹

Regardless of the origin, the term and programmers all over the world use debuggers, as Xcode, to find bugs in programs. People are the real debuggers; debugging tools merely help programmers locate problems. No debugger, whatever the name might imply, fixes problems all on its own.

This chapter will highlight some of the most important features of the Xcode debugger and will explain how to use them. Once you are finished this chapter, you should have a good enough understanding of the Xcode debugger and of the debugging process in general to allow you to search for and fix the majority of programming issues.
