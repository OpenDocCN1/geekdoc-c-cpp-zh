
# Listing 13–7. Allocating an Objective-C Object.

```
1 int main(void)
2 {
3 NSString* myString = [[NSString alloc] initWithUTF8String:"Hello World!"];
4 // Code to modify with the string...
5 [myString release];
6 myString = nil;
7}
```

In this example, line 3 allocates a new object alloc. This line is actually very important in this situation; the reason will be explained in a bit. So line 3 created the new string. As it's created, the Objective-C system automatically sends a retain message to the object. At this point, the myString variable points to an object that has one retain so far.

Line 5 issues a release to the myString object. The release subtracts one from the current retain count (which is 1). As mentioned before, the retain count reaches zero, the object is deallocated. so once line 5 has finished, the myString variable points to deallocated memory.

Line 6 sets our original variable to nil to indicate that the pointer is empty.

# Using the Retain/Release Model

The process of retaining and releasing memory is something that Objective-C uses extensively to manage memory. The alternate name of this process, reference counting, is a little more descriptive because the process of retaining and releasing memory is a way of counting how many times the memory has been retained than released. Note the term "memory" is used here generically. Memory management in Objective-C allocates memory for objects instead of blocks of memory. The Objective-C base class NSObject, which most Objective-C objects are derived from, keeps track of the retain count.

> NOTE: If you are looking for exactness, the NSObject protocol actually defines the reference counting messages. NSObject implements that protocol.

So far, things sound fairly simple: for every retain, there needs to eventually be a release. This doesn’t sound too tricky, right? Well, its not always straightforward to know when an object is retained. Consider the example in Listing 13–8.

# Listing 13–8. A Retain Count.

```
1 NSMutableDictionary *dict = [[NSMutableDictionary alloc] init]; dict retainCount = 1
2 NSObject *today = [[NSDate alloc] init];      today retainCount = 1
3 [dict setObject:today forKey:@"TODAY"];
4                                              retainCount = 2
5 [dict release];                                 retainCount = 1
6 today = nil;
7 [dict removeObjectForKey:@"TODAY"];      today deallocated
8 [dict release];                             dict deallocated
```

Looking at Listing 13-8, the retain counts of the dict and today objects are shown. The dict object has a retain count of 1 whenever the object is created. The same is true for the today object on line 2.

In line 4, things looks a little odd. For some reason, the retain count is 2. What happened? Well, if we look closely at the NSMutableDictionary documentation for the setObject:forKey: method, we see, in the documentation for the setObject: part of the message that "the object receives a retain message before being added to the receiver."

According to the documentation, before an object is added to the dictionary, the object is sent a retain message. This is why the dictionary has a retain count of 2.

Why does the dictionary do this? The answer is quite simple. If we add an object to the dictionary, the dictionary should be responsible for it; we basically hand it over to that class. We can release any local variables to objects we add to the dictionary. To ensure this, the dictionary becomes the owner of the objects. NSMutableDictionary class sends all the data it stores a retain message so that the system knows someone is using that object.

Since dict is managing the object, line 5 is used to release our object. The dictionary still has the same message that the today object has: we've just told the system that we're finished with it. Had the dictionary not sent a retain message, line 5 would have actually deallocated the memory by way of a release. The rule is plenty simple: Once the retain count of an object reaches zero, the object is sent a dealloc message, and the memory to that object is actually deallocated.

Line 7 removes the object by way of the key TODAY. When an object is removed from a dictionary, the object is automatically sent a release message. At this point, the today that used to point to it is sent a release message. Since this now makes the retain count of the object zero, the object is also sent a dealloc message to deallocate its memory.

Line 8 sends a release message to the dict object. This will deallocate the memory of the object, since nowhere else is the object retained.

# Working with Implied Retain Messages and Autorelease

How do we know which objects need to be released and which don't? The answer basically falls under the rule of object ownership. If an object is created that has alloc, copy, or new you own the object, and it, therefore, needs to be released once the program is finished it. There are other examples, but no hard and fast rules unfortunately. Deallocating memory takes an understanding of the objects and what messages result in an explicit retain.

While an object can be sent an explicit retain message, in the examples so far, there isn't one case where there are automatic or implied retain messages. For example, whenever the message setObject:forKey: is sent to the dictionary object, the object we add is automatically sent a retain message. As mentioned previously, whenever we are allocating a retain is implied:

```
NSMutableDictionary *dict = [[NSMutableDictionary alloc] init];
```

Other calls are not so obvious, as seen in the following example:

```
NSDate* today = [NSDate date];
```

In the case above, the object has allocated but has in implied release—called autorelease. As mentioned above, anything with an alloc, copy, new requires that the program manually releases the object. For anything else, the object is released automatically.

The key is that the return value is a new date object. Because it's a new object, it receives a sort of implied retain message. But more importantly, it will automatically released since the object wasn't created with an alloc/copy/new method. The program could just have been written as follows:

```
NSDate* today = [[NSDate alloc] init] autorelease];
```

This code would yield the exact same results. The difference is that, in the second example, we are explicitly allocating the memory marking it as autorelease. The Objective-C run-time system will automatically release the memory. While autorelease seems like the best way to handle releasing memory, it may not be what is needed. Variables that are marked autoreleased don't stick around very. iOS and some Mac applications have a run-loop. Basically, an application for the most part just waits for input. If you touch the screen, the application will perform some function and then eventually go back to waiting for input. When the application goes back to wait for more input, all autorelease variables are released; this could easily be as short as 1/60th of a second. So, autorelease should be used with caution and only in an area where the need for a variable is within the span of the current run-loop. If the program needs to have an autorelease variable stick around for a while, then either don't use autorelease (use the standard alloc and init) or simply send a retain message to the object.

Listing 13-9. Keeping an Autorelease Variable Available.

```
- (NSDate *)getDate
{

    // Release the memory for the current_date.

}
```

Notice on line 9 that the getDate method is called and then we send a retain message to the object. This is because getDate is set as autorelease. If the program didn't do this, the memory to current_date would been autore autore.

> NOTE: In any iOS application developed before Xcode 4.2, there is a line in the .m file that looks as follows:

AutoreleasePool * pool = [[AutleasePool alloc] init];

This is the mechanism the program uses to autorelease memory that has been sent an autorelease message when it was allocated, like our example. The [NSDate date] returns its memory which is automatically added to this autorelease pool and then automatically deallocated at the next run-loop.

# Sending the dealloc Message

Under normal circumstances, your program should never send a dealloc message to another object. There are some exceptions. One of these is handling the dealloc message itself. You will be dealing with the dealloc message only for objects you create. Listing 13–10 is a snippet of code that shows how a typical dealloc message is coded. Every object that you create should implement a dealloc message except when using ARC, garbage collection, or if there's nothing to release. Listing 13-10. A typical dealloc implementation.

```
- (void)dealloc
{
    self.iVar = nil;           // If we have ivars, make sure they are deallocated.
// This instance variable is a property (Chapter 10)
    [iVar release];            // Another example. We release an instance variable
// that we were using - it wasn't a property.
// We finally tell the proper to deallocate itself.
    [super dealloc];          // This is one of the few times dealloc will be called
```
