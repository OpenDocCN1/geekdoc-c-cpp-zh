
# 并行编程与并发计算

并行编程通过在多个单元上同时计算不同部分，允许计算更快完成。速度的提升与单元数量之间最好是线性的。为了实现线性提升（或任何提升），并行算法必须经过仔细的设计和实现。

一个简单但基础的例子是变换，它在 C++ 标准库的 `transform()` 函数中实现，其中某些函数 `$f$` 应用于源集合 `$S$` 中的所有元素，以产生目标集合 `$D = \{y_i = f(x_i)\}$`。这种变换很容易通过“分治”惯用法进行并行转换：将 `$S$` 划分为若干子集 `$\{S_j\}$`，并在不同的单元上同时对不同的子集进行变换。

下面的图表展示了在 2 个单元上对 8 个元素的变换：

| | 单元 1 | 单元 2 | 单元 3 | 单元 4 |
| :--- | :--- | :--- | :--- | :--- |
| **步骤 1** | $y_1 = f(x_1)$ | $y_2 = f(x_2)$ | $y_3 = f(x_3)$ | $y_4 = f(x_4)$ |
| **步骤 2** | $y_5 = f(x_5)$ | $y_6 = f(x_6)$ | $y_7 = f(x_7)$ | $y_8 = f(x_8)$ |

## 并发编程框架

并发编程通常是实现并行算法的首选框架。本文侧重于并发编程，不涵盖分布式编程。并发计算并非没有限制；它受限于单台计算机上的可用处理单元，并且由于分布式内存模型，它在设计上是不安全的。

线程在共享内存中可能会相互干扰，导致崩溃、结果错误、速度变慢或死锁等严重问题，因此，开发者有责任实现安全的设计和正确的同步以防止这些问题。标准线程库 `Standard Threading Library` 提供了一个框架和多种工具，以有助于实现正确的并发编程。该库及其在开发安全、高效并行算法中的应用，是本文的主题。

### GPU 并行化

并发计算的一种特殊形式是 GPU 图形处理器单元 并行化。现代 GPU 为有限的硬件执行提供了海量的处理单元。GPU 最初被设计用于处理二维和三维图形的计算，后来演变为提供通用计算能力。特别是 Nvidia 英伟达，提供了一种免费的类 C++ 语言 `CUDA` 计算统一设备架构，用于对其芯片进行编程。

如今，GPU 编程已应用于图形设计和视频游戏之外的许多科学和商业应用中。特别是，GPU 加速了许多机器学习和金融风险管理软件。金融行业的可靠来源报告称，生产环境蒙特卡洛代码的速度提升了 50 倍左右；例如参见 [16]。

GPU 编程显然不是标准的 C++。除了特殊的硬件和软件外，有效的 GPU 编程还要求算法以特定方式编写以适应 GPU 的设计和限制。GPU 并行化可能带有无比拟的硬件，但也面临高昂的开发成本。由于原因，GPU 近期在金融行业某种程度上失宠；例如参见 [17]。

CPU 中央处理器 制造商如 Intel 英特尔 近年来系统地增加了其芯片上的核心数量，以便 CPU 可以与 GPU 协同计算，而不需要专门的 GPU 编程。高端现代工作站现在包含多达 48 个核心。CPU 核心是真正的独立单元，因此不同的核心可以执行独立、不相关的工作。GPU 核心并没有那么灵活。CPU 核心通常也比其对应的 GPU 核心快得多。更重要的是，CPU 并行是使用标准 C++ 编写的。

此外，在 GPU 上有效运行内存密集型算法如 `AAD` 非常有挑战性。算法自动微分 `AAD` 可以在常数时间内产生风险敏感性。AAD 是过去十年金融行业中实现的最有效的加速。在并行 CPU 上实现 AAD 并不特别困难。我们将在第三部分介绍这一点。另一方面，据我们所知，尽管最近亚琛工业大学 RWTH Aachen University 的 Uwe Naumann 给出了鼓励，但 AAD 尚未在 GPU 上得到说服力的实现。

出于这些原因，我们不再进一步探索 GPU 并行，而是专注于 CPU 并发。对学习 GPU 编程感兴趣的读者请参考许多现有的 CUDA 教书之一。

## 多线程与 SIMD

最后，并发 GPU 编程本身分为两种截然不同且相互兼容的并行形式：多线程 `MT` 和 SIMD 单指令多数据流。

多线程 `MT` 由在运行在不同核心上的不同线程上并发执行某些计算的不同部分组成。核心实际上是独立的 CPU，因此它们可以并发运行不相关的计算而不会损失性能。例如，集合的转换可以通过在不同线程转换不同的子集来实现多线程化。在这种情况下，不同的核心将执行相同的指令序列，但处理的是不同的数据。

多线程是一种特别灵活、高效的 CPU 编程形式，也是第三章的主题。在第二部分中，它被应用于加速金融模拟。

相比之下，SIMD 指现代 CPU 或 GPU 中的每个核心都能同时将同一条指令应用于多个数据上的能力。例如，在一次转换中，单个核心可以同时将函数 `$f$` 应用到多个 `$x$` 上。SIMD 使用 CPU 指令一次转换一个数据向量，而不是单个数据。由于这个原因，它也被称为“向量化”。现代主流实现 `AVX2` 可以一次处理四个双精度浮点数 `32 字节，256 位`。

> 4 在我们看来，AAD 是自 FDM 以来金融领域实现的最有效的算法。
> 5 尽管我们在本部分后面会看到，它们可能会通过共享内存和缓存产生干扰。

高端 CPU `AVX512` 可以在单条指令中处理八个双精度浮点数 `64 字节，512 位`。

SIMD 可以与多线程结合，这一过程被称为“GPU on CPU”，因为 GPU 实现了类似的技术。对于集合的转换，可以在运行在不同核心上的不同线程上处理多个子集，每个核心在单条指令中对子集的多个元素执行 SIMD。

将 MT 与 SIMD 结合的理论加速效果是核心数与 SIMD 向量宽的乘积。在带有 `AVX2` 的标准 8 核工作站上，这个值是 32。在带有 `AVX512` 的 18 核高端 iMac Pro 上，这个值是达到了令人惊人的 144。

SIMD 的限制非常大：只有应用于简单类型的简单函数才能向量化。此外，数据必须是连续的且对齐的。例如，对集合 `$S = \{x, 1 \le i \le n\}$` 的简单转换 `$x \to \cos$` 可以被向量化，Visual Studio 会自动向量化实现此转换的循环。对于不同的函数，如如果 `$x > 0$` 则为 `log x`，否则为 `-log x`，则该转换无法被向量化。

SIMD 层次级较低，接近方法并行化。它没有在标准 C++ 中实现，也没有在标准库中支持。SIMD 是在编译器中实现的。与多线程不同，它是在运行时调度的。是在编译时是否发生分解。像 Visual Studio 这样的标准编译器对 SIMD 的支持有限。Visual Studio 自动向量化简单循环，并可以报告哪些循环被向量化了哪些没有。其他编译器如 Intel 的通过设置和 pragma 的形式为向量化提供了更广泛的支持

Intel 还提供了其集成性能原语 `IPP` 和数学内核库 `MKL` 供免费下载。这些库包含了许多向量化的数学函数和算法。与蒙特卡洛模拟直接相关，IPP 提供了反正态分布的向量化实现 `ippsErfnv_64f_a26(6)`。

> 6 插入代码体中的特殊指令，它们不是要编译的 C++ 代码，而是关于如何编译代码的某些指令。因此，pragma 是特定于编译器的。

因此，尽管 Visual Studio 支持对循环进行偶尔的自动向量化，但要实现有效的、系统化的向量化，需要专门的编译器和专门的第三方库。

此外，为了系统性地从 SIMD 中受益，代码必须以特殊方式编写，以便数学操作能够在底层同时应用于数据。SIMD 加速是侵入性的。我们将在第二部分中看到，MT 多线程 的情况并非如此。我们在不修改模型或产品代码的情况下实现仿真。要对仿真向量化，我们需要完全重写模型和产品中的仿真代码。

只有当完全相同的 CPU 指令应用于不同的数据时，才能实现完全的 SIMD 加速。当代码中出现控制流 `if、while` 等时，SIMD 最多只能被部分应用。部分并行是并行编程中一个为人知的陷阱。当某个算法的比例 `$\mu$` 实现了完美并行通过单元数量 `$p$` 加速时，仍有 `$1-\mu$` 的比例保持为串行执行，导致全局加速倍数为 `$p/[\mu+(1-\mu)]$`，这与可能直观的但完全错误的 `$p\mu$` 大相径庭。

产生的加速通常是违背直觉的。例如，一个算法 75% 的部分在 8 个单元上进行完美并行实现，加速因子仅为 2.9，令人非常失望，远低于可能预期的 6 倍。当算法的 90% 以 100% 的效率进行并行时，产生的全局加速仅为 4.7，并行效率低于 50%。

> 7 这一结果被称为阿姆达尔定律。显而易见，当串行计算时间为 `$\Delta$` 时，并行计算时间为 `$\Delta[\mu/p+(1-\mu)]$`，结果随之得出。
> 8 加速率与并行单元数量的比率被称为“并行效率”。并行效率始终在 0 排除 和 1 包含 之间。并行算法的目的是实现尽可能接近 1 的效率。

最后，最重要的一点是，将 SIMD 与 AAD 结合是极具挑战性的。向量化 AAD 可能是未来论文的主题，但这超出了本书的范围。相比之下，MT 与 AAD 自然地结合，正如第 12 章中详细演示的那样，我们在该章对多线程仿真应用了 AAD。

我们看到，MT 与 SIMD 的结合提供了与 GPU 相似的性能，但面临着同样的限制。这并非巧合——GPU 本质上是大量具有宽 SIMD 能力的较慢核心的集合。系统化的向量化需要使用专门的编译器和专门的库将代码重写到低。当然，这一切都需要专门技能。我们不会详细介绍 SIMD，也不会尝试为 SIMD 加速编写专门的代码。相反，我们将在第 3 章详细研究 MT，并在本文的其余部分实现它。

我们还会应用偶然的向量化，即通过某种编写循环的方式鼓励编译器对其进行自动向量化，例如，尽可能使用标准 C++ 库的通用算法如 `transform()` 或 `accumulate()` 来代替手写的循环。这些算法经过了优化，包括在可能的情况下向量化，通常会产生更快的代码。此外，它使得我们的代码更具表现力且易于阅读。尽可能使用 STL 标准模板库 算法是一个通用原则。C++ 程序员必须了解这些算法以及如何使用它们。我们在本文的其余部分使用了许多 STL 算法，对学习 SIMD 感兴趣的读者可以参考 Intel 的文档。

## 并发编程框架演进

并发编程存在许多框架。线程的管理和调度属于操作系统。在 C++11 之前，实施了两项提供可移植框架的倡议：`OpenMP` 和 `Boost.Thread`。`OpenMP` 提供编译时并发，并支持包括 Windows 在内的所有现代编译器。它由许多称为 pragma 指令的编译器指令组成，指示编译器自动生成并行代码。`OpenMP` 在大多数编译器中都是开箱即用的，我们在第 1 章中提供了一个示例。

然而，对于复杂结构化代码的多线程，我们需要线程库的全灵活性。`Boost.Thread` 提供了这样的库，具有运行时并行，客户端代码使用它创建和管理线程并发送任务并发执行。它提供了一致的 API，同时封装了特定操作系统的逻辑。许多开发者认为 Boost 已经是标准，使用 `Boost.Thread` 编写的应用通常被认为是可移植的。然而，编译器并没有内置 Boost。使用 `Boost.Thread` 的应用程序必须包含 Boost 头文件并链接 Boost 库。这不是一种特别友好的体验，尤其在 Windows 上。在大型项目中更新 Boost 库也很，例如升级到新版本的 Visual Studio。
