# 第三部分 核心类型

无法获取所有被调用回调方法的返回值。但这并不是局限性。如果被调用的委托之一抛出异常或长时间阻塞会发生什么呢？由于算法是顺序调用链中的每个委托的，其中一个委托的出现“问题”会停止链中所有后续委托的调用。显然，这种算法并不健壮。

对于该算法不足以满足的场景，`MulticastDelegate`类提供了一个实例方法`GetInvocationList`，你可以使用它通过任何符合你需求的算法来显式地调用链中的每个委托：

```csharp
public abstract class MulticastDelegate : Delegate {
  // 创建一个委托数组，每个元素都引用
  // 一个委托
  public sealed override Delegate[] GetInvocationList();
}
```

`GetInvocationList`方法作用于派自`MulticastDelegate`的对象，并返回`Delegate`引用数组，其中每个引用指向链中的一个委托对象。在内部，`GetInvocationList`构建一个数组并对其进行初始化，每个元素都引用链中的一个委托；然后返回该引用。如果`invocationList`字段为`null`，则返回的数组包含一个元素，该引用链中唯一的委托：即委托实例本身。

你可以轻松地编写一个显式调用数组中每个对象的算法。以下代码演示了：

```csharp
using System;
using System.Text;
```

```csharp
// 定义一个 Light 灯组件。
internal sealed class Light {
  // 此方法返回灯的状态。
  public String SwitchPosition() {
    return "The light is off";
  }
}
```

```csharp
// 定义一个 Fan 风扇组件。
internal sealed class Fan {
  // 此方法返回风扇的状态。
  public String Speed() {
    throw new InvalidException("The fan broke due to overheating");
  }
}
```

```csharp
// 定义一个 Speaker 声器组件。
internal sealed class Speaker {
  // 此方法返回声器的状态。
  public String Volume() {
    return "The volume is loud";
  }
}
```

```csharp
public sealed class Program {
  // 允许查询组件状态的委托定义。
  private delegate string GetStatus();
  public static void Main() {
    // 声明一个委托链。
    GetStatus getStatus = null;
    // 构建三个组件，并将它们的方法添加到委托链中。
    getStatus += new Light().SwitchPosition;
    getStatus += (String)new Fan().Speed;
    getStatus += (String)new Speaker().Volume;
    // 显示反映三个组件状况的合并报告。
    Console.WriteLine(GetComponentReport(getStatus));
  }
  // 查询多个组件并返回报告的方法
  private static String GetComponentReport(GetStatus status) {
    // 如果链为空，则无事可做。
    if (status == null) return null;
    // 使用此构建报告。
    StringBuilder report = new StringBuilder();
    // 获取一个数组，其中每个元素都是链中的一个委托。
    Delegate[] arrayOfates = status.GetInvocationList();
    // 遍历数组中的每个委托。
    foreach (Delegate d in arrayOfates) {
      // 将合并报告返回给调用者。
      report.Append(d.DynamicInvoke());
    }
    return report.ToString();
  }
}
```

Failed to get status from Fan.Speed: The fan broke due to overheating
The volume is loud

## 委托定义（泛型委托）

许多年前，当.NET Framework刚刚开始开发时，微软引入了委托的概念。当程序员们向FCL（功能类库）添加类时，他们会定义新的委托类型。随着时间的推移，定义了许多委托。事实上，仅在`mscor.dll`中就定义了许多委托。事实上，仅在`mscor.dll`中就定义了接近50个委托。让我们看看这些：

- delegate void TryCode(userData);
- delegate void WaitCallback(Object state);
- delegate void TimerCallback(Object state);
- delegate void ContextCallback(Object);

你发现这些委托定义之间有什么相似之处吗？
- delegate void ParameterizedStart(Object);

现在建议使用这些委托类型。事实上，由于现在支持泛型，.NET Framework提供了从0到16个参数的Action委托：

- delegate void Action();
- delegate void Action<T>(Object);
- delegate void Action<T1, T2>(T1, T2);
- delegate void Action<T1, T2, T3>(T1, T2, T3);
- delegate void Action<T1, ..., T16>(T1, ..., T16);

所以.NET Framework提供了从无参数到16个参数的Action委托。如果你需要调用超过16个参数的方法，将被定义自己的委托，但这非常不利。

除了Action委托之外，.NET Framework还提供了Func委托，它们允许回调方法返回一个值：

- delegate TResult Func<>();
- delegate TResult Func<T>(T);
- delegate TResult Func<T1, T2>(T1, T2);
- delegate TResult Func<T1, T2, T3>(T1, T2, T3);
- delegate TResult Func<T1, ..., T16>(T1, ..., T16);

在使用带有泛型参数和返回值的委托时，逆变和协变会发挥作用。建议你利用这些功能，因为它们没有副作用，并且能让你的委托在更多场景中使用。有关此的更多信息，请参见第12章“泛型”中的“委托和接口的逆变和协变泛型类型参数”节。

现在建议尽可能使用这些委托类型，而不是开发更多的委托类型。这减少了系统的类型数量并简化了代码。然而，如果你需要使用`ref`或`out`关键字传递引用，你可能必须定义自己的委托：

```csharp
delegate void Bar(ref Int32 z);
```

如果你想通过C#的`params`关键字让委托接受变数量的参数，或者你想为任何委托指定默认值，或者你需要约束委托的泛型类型，如下所示：

```csharp
delegate void EventHandler<TEventArgs>(object sender, TEventArgs e);
where TEventArgs : EventArgs;
```

> **注意** 0到8个参数的Action和Func委托定义在`mscor.dll`中，因为具有此类参数的方法相当常见。然而，9到16个参数的Action和Func委托定义在`System.Core.dll`中，因为具有此类参数的方法很少。而且事实上，这些委托定义大多由动态编程语言内部使用，通常不由开发者直接使用。

# 第三部分 核心类型

第一行代码背后的思想是将`button1_Click`方法的地址注册到按钮控件中，这样当按钮被点击时，就会调用该方法。对于大多数程序员来说，仅仅为了指定`button1_Click`方法的地址就构造一个`EventHandler`委托是非常不自然的。这个对象提供了一个包装器，确保该方法只能以类型安全的方式调用。该包装器还允许调用实例方法和链式调用。遗憾的是，大多数程序员不想考虑这些细节。程序员更倾向于像如下所示编写上述代码：

```
button1_Click += button1_Click;
```

幸运的是，微软的C#编译器在处理委托时提供了一些快捷方式。我将在本节中解释所有的这些快捷方式。在开始之前最后一点一点：我即将描述的内容归根结底就是C#的语法糖；这些新的语法快捷方式只是为程序员提供了一种更简单的方法来生成生成的IL（中间语言），以便CLR和其他编程语言能够处理委托。这意味着我将要描述的内容是C#特有的；其他编译器可能不会提供这些额外的语法快捷方式。

## 语法快捷方式 #1：无需构造委托对象

如前所示，C#允许你指定回调方法的名称，而无需构造委托对象。这里是另一个示例：

```c
internal sealed class AClass {
    public static void CallbackWithoutNewingDelegateObject() {
        ThreadPool.QueueUserWorkItem(SomeAsyncTask, 5);
    }
    private static void SomeAsyncTask(Object o) {
        Console.WriteLine(o);
    }
}
```

在这里，`ThreadPool`类的`QueueUserWorkItem`方法期望一个`WaitCallback`委托对象的引用，该对象包含`SomeAsyncTask`方法的引用。由于C#编译器能够推断这一点，它允许我省略构造`WaitCallback`委托对象的代码，使代码更具可读易理解。当然，当代码被编译时，C#编译器会产生实际上实例化`WaitCallback`委托对象的IL——我们只是获得了一个语法快捷方式。

## 语法快捷方式 #2：无需定义回调方法

在上面的代码中，回调方法的名称`SomeAsyncTask`被传递给`ThreadPool`的`QueueUserWorkItem`方法。C#允许你内联编写回调方法的代码；它不需要写在方法体内部。例如，上面的代码可以重写如下：

```csharp
internal sealed class A {
    public static void CallbackWithoutNewDelegateObject() {
        ThreadPool.QueueUserWorkItem((obj) => Console.WriteLine(obj));
    }
}
```

注意`QueueUserWorkItem`方法代码的第一个“参数”是一个C# Lambda表达式，并且很容易检测到对C# Lambda运算符`=>`的使用。你可以在编译器通常期望看到委托的地方使用Lambda表达式。而且，当编译器看到对这个Lambda表达式的使用时，编译器实际上自动定义了一个新方法（在本例中为`ASC`）。这个新方法被称为匿名函数，因为编译器会自动创建方法的名称，而且通常你并不知道它的名称。然而，你可以使用如`ILasm.exe`等工具来检查编译器生成的代码。在我写完代码并编译后，我通过`ILasm.exe`发现C#编译器将此方法命名为`<CallbackWithoutNewDelegateObject-b_0>`，并确保该方法接受单个`Object`参数并返回`void`。

编译器选择以`<`符号开始方法，是因为在C#中，标识符不包含`<`符号；这确保了你不会意外定义与编译器为你选择的`<`符号冲突的方法。顺便提一下，如果C#允许`<`作为标识符，CLR是允许的，这就是为什么这样做可行。另外请注意，虽然你可以通过传递字符串方法名称通过反射访问该方法，但C#语言规范规定不保证编译器如何生成它。例如，每次编译代码时，编译器都可能为方法生成不同的名称。

使用`ILasm.exe`，你可能还会注意到C#编译器对此方法应用了`System.Runtime.CompilerServices.CompilerGeneratedAttribute`，以向各种工具和程序表明该方法是由编译器而不是程序员生成的。`=>`运算符右的代码放置在该编译器生成的方法中。

> **注意：** 在编写Lambda表达式时，无法对编译器生成的方法应用你的自定义属性。此外，你不能对方法应用任何自己的修饰符（如`unsafe`）。但这通常不是问题，因为编译器生成的匿名方法最终始终是私有的，并且该方法是静态还是非静态取决于它是否访问了任何实例成员。不需要对方法应用`public`、`protected`、`internal`、`virtual`、`sealed`、`override`或`abstract`等修饰符。

最后，如果你写了上述代码并编译，就好像C#编译器重写了你的代码，看起来像这样（注释由我插入）：

```csharp
internal sealed class ACLASS {
    // 创建了此私有字段用于缓存委托对象。
    // 回调 CallbackWithoutNewingDelegateObject 在每次调用时
    // 都不会再创建一个新对象。
    // 缓存的对象永远不会被垃圾回收
    [CompilerGenerated]
```
