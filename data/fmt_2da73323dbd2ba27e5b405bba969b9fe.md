## 3.5 使用模型

我们设计了一个由操作系统选择的 COMPASS 着色器。通过性能分析（profiling），操作系统可以选择最佳的 COMPASS 着色器。另一方面，操作系统还可以提供一个 API 来调用独立应用程序，以从着色器库中选择 COMPASS 着色器。厂商还可以通过另一个 API 调用提供特定应用程序的 COMPASS 着色器。该 API 调用提供了其自定义 COMPASS 着色器的指针。当操作系统调度目标线程时，它在 MAP 的着色器寄存器中设置该指针（图 2）。这种执行模型意味着，如果应用程序与图形无关，开发人员仍然可以通过编写预取着色器代码并在运行时加载它来使用 GPU 增强性能。

## 4. COMPASS 着色器设计

在本节中，我们描述了 COMPASS 着色器的设计并分析了设计的权衡。首先，我们评估了三种基于表的方法：PC 索引预取 [4]、标记预取 [19] 和基于增量索引的相关性预取 [22]。另一方面，我们评估了一种区域预取技术 [23]，以展示 COMPASS 的独特特性，并对针对内存密集型应用进行了评估。

在缺失时激活一个线程。在这种情况下，预取表的每个条目都用一个线程建模。线程消耗两个寄存器来维护主历史并自行生成预取。由于我们只在 64 个线程中使用了 1 个，该着色器代码对 GPU 的利用率很低。

如前所述，应用程序可以编写自己的 COMPASS 预取并通过 API 调用将其传递给操作系统。第二种设计是多线程 COMPASS，它在波次（wave）内激活线程。尽管这些线程共享一个条目，但存储在这些寄存器中的 `tag`、`地址` 和 `步长` 必须为每个线程进行复制。由于每个条目只需要一个寄存器，寄存器压力小于单线程 COMPASS 着色器。因此，多线程 COMPASS 可以获得更好的占有率和性能。如果 `D` 不是 2 的幂次，我们使用一组 `D` 线程来评估预取表，其中 `D` 是大于原值的最小 2 的幂次。例如，为了评估步长为 2 的预取，我们使用两个线程组而不是一个，以便该组可以评估预取表。发现此类非活动线程是效率低下的根源。

需要解决的问题之一是 GPU 着色器代码中指令的长延迟。COMPASS 的设计原理是针对吞吐量进行优化。通过利用大量的线程并行性来隐藏延迟。尽管连续执行 COMPASS 着色器之间，指令的分发速度为每指令 8 个 GPU 周期。这显然不是性能瓶颈，但对于数据预取引入缺失的缓存行来说，这是一个问题。另一方面，GPU 代码可能比本文假设的 COMPASS 时钟 [?] GPU 频率慢。COMPASS 的速度快得多。在我们的乐观假设下，我们在 COMPASS 着色器的两个 VLIW 指令之间使用 16 个周期。

另一方面，COMPASS 的一个局限性是吞吐量。COMPASS 无法处理计算密集型场景，即在着色器完成之前预取就会被请求（注意这是我们的着色器）。如果存在未满足的，理想的步长 COMPASS 可能是致命的。我们将在讨论 COMPASS 时关注这一问题。

### 4.1 步长 COMPASS

在步长 COMPASS 的实现中，我们使用三个寄存器来保存 `tag`、`关联地址` 和 `步长`。在缺失时，设置引擎使用 GPU 标记进行预取，这被视为硬件预取。着色器生成 `$d$` 次预取，其中 `$d$` 是预取距离。

### 4.4 简化的区域预取

此外，我们实现了区域预取的简化版本 [23]。原始区域预取技术监控缓存利用率，并通过侧带发送预取信号。这避免了细粒度的监控和预取，我们不希望在当特定页面是 64 个线程或特定波前的匹配项时通过预取整个页来处理这些操作。如图 7 所示，预取波前为 `P+6 × i` ，其中 `P` 代表发生缺失的页基地址。波前中的其他缺失将检查缓存行是否在同一页内（缓存行大小为 64 字节，页大小为 4KB）。暴力的非锁缓存预取可以用于所有应用程序。然而，由于其算法的灵活性仍然具有挑战性，因为 `j (< i)` 需要代码来查找匹配。这种查找需要顺序访问。为了实现这一点，我们使用 delta COMPASS 线程，使得线程 `j` 维护许多 `$\sum\delta_i$`，应通过查找匹配来实现。我们可以将 delta 总和计算为最后一个值 (`$\delta_i$`) 之和，并通过回到预取缓冲器的头部来轻松维护。当线程找到匹配时，它广播其 delta 总和 `$\sum\delta_i$` 及其 ID。在其他 ID 上，线程接收此值，通过减去线程的旧 delta 总和来计算 `$\sum\delta_i$`。然后线程从每次匹配更新执行过程。

```

2: prefetch = pageAddr + * i
4: prefetch
```
